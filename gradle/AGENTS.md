# Tuist Gradle plugin

Settings plugin written in Kotlin. `TuistBuildInsights` uploads build reports; `BuildExecutionTelemetry` collects execution and cache operations.

- Register the build insights service only through the configuration-cache-aware `onOperationCompletion` registry. A single service provider cannot hold both task and operation subscriptions. Keep it an operation-only listener so configuration reuse restores the correct subscription.
- Completion events are ordered. Propagate nested cache metadata to parents until the owning task finishes; do not depend on start events from this registry.
- Internal Gradle APIs can change. Catch unavailable operations without failing the build, and mark incomplete telemetry honestly. Integration tests must exercise real builds and configuration-cache reuse.
- Exclude machine counter reads from configuration input tracking and restore tracking in a finally block. Linux `/proc` counters are telemetry, not configuration inputs, and change between builds.
- Cacheability is task capability, not global build-cache availability. Fall back to `@CacheableTask` for disabled-cache or skipped lookups, while honoring observed task-specific disabled reasons.
- The build cache declares `tuist-checksum-sha256` (lowercase hex SHA-256 of the exact body) on every store. It hashes Gradle's entry writer in a separate pass before sending, because `HttpURLConnection` already buffers the body; the writer copies from a packed file and is repeatable. A 422 refusal retries the store once with a fresh checksum. On load, a well-formed `tuist-checksum-sha256` response header is verified when the body reaches end of stream; a mismatch, including a truncated body, is logged and returned as a miss. Gradle only unpacks an entry whose `readFrom` completed, so the partial download is discarded and the task runs. Responses without the header are not verified.
- Requests to Tuist go through `TuistRetry` with the `RetryPolicy` of `TuistHttpClients`: 4 attempts, waits of about 250 ms, 1 s and 2 s (20% jitter, each capped at 2 s; a `Retry-After` replaces the wait, capped at 2 s). Connection refused, no route to host and 503 are always retried. Replay-safe requests also retry dropped connections (reset, closed, unexpected end of stream), 502 and 504. Timeouts (a connect timeout is 30 s), cancellation, interruption and other statuses are never retried, and a failure an inner retry gave up on (a token refresh inside a request) is not replayed by the enclosing one. Replay-safe: GETs, cache PUTs (content-addressed), shard plan creation (the server serves a reference's latest plan), the stress plan (read-only), Git history uploads (stored commits and heads are skipped), token refresh (the server answers a refresh token presented again within 60 s of its exchange with the same tokens) and build/test report POSTs (each report carries a client-generated UUID `id`, created once per report and resent by every attempt, and the server stores a replayed `id` only once). A server older than that contract may store a replayed report twice or refuse a replayed refresh. Cache load/store throw `BuildCacheException` once attempts run out, so Gradle disables the remote cache for the build; an entry body is read once, outside the retries. Only 400/401/403 from token refresh mean not authenticated; other refresh failures are `IOException`s. Shard planning, shard lookup and the stress plan use `ServerConfigurationProvider`: authenticated, without cache endpoint discovery. A failed quarantine lookup warns and applies no quarantine. Tests pass `RetryPolicy(sleeper = {})`.
- Run tests with `./gradlew test --no-build-cache --no-watch-fs`. When validating source changed outside Gradle's file watcher, force compilation with `--rerun-tasks`.

- `ReportConfigurationProvider` resolves publishing destinations independently of cache endpoint discovery. Build/test reporting may omit genuinely absent credentials only after `GET /.well-known/tuist.json` advertises boolean `network_trusted_report_publishing: true`; cache and shard planning remain authenticated. Discover during execution without credentials/actor claims or redirects; do not persist the policy in the configuration cache. There is no client opt-in. Retain the deprecated `buildInsights.networkTrustedPublishing` property as an ignored compatibility shim for existing build scripts. Unsigned tests omit existing-build, shard, stress/history references. Unsigned build/test JSON omits Git origins before serialization; signed behavior is unchanged. Report response decoders must tolerate missing/null actor metadata, unknown future fields and open provenance strings, including configuration-cache reuse. Quarantine lookup is skipped only when the optional credential resolver confirms genuine absence, not merely because the instance supports unsigned reporting, so authenticated runs preserve their behavior. Credential-free reports must refuse the default hosted destination when the self-hosted server URL is missing, preserving ordinary sign-in guidance for signed-out hosted users. Existing invalid credentials must not become anonymous retries, including after an authenticated 401 when refresh loses credentials. Refuse known hosted destinations and `*.tuist.dev` before credential-free uploads, normalizing case and trailing dots. Credentials reads normalize case/trailing dots and match legacy hostname aliases; refresh writes back to the selected file so the CLI never keeps a stale duplicate. Inspect credentials and every directory ancestor with strict NIO operations: only a genuinely missing path is absence; access errors, non-directories and dangling links fail closed. Keep real POSIX permission-denial and hostname-alias regressions. Token resolution uses validated credential reads and preserves corrupt files, so cache/test initialization cannot delete invalid credentials and turn the next build report into an anonymous submission.
- Build/test report POSTs may include an unverified `x-tuist-actor-id`: explicit environment `TUIST_ACTOR_ID`, then `buildInsights.actorId`. Never infer usernames or send a claim by default. Empty/invalid overrides omit the claim instead of falling back. Keep the optional service parameter configuration-cache compatible; never change credentials, report JSON, cache/quarantine/shard requests or endpoint discovery for attribution. Older servers ignore the header.

- Initialize local end-to-end demo projects as Git repositories and commit their fixture sources before recording builds, so branch and commit metadata is present in dashboard examples.

- Build reports include `started_at` using the same origin as `duration_ms`, including configuration-cache reuse, so the server can align operations with machine samples.

- Keep requested work separate from executed work, as a build-system-independent concept. `requested_tasks` preserves the original invocation in order through configuration-cache-compatible service parameters. Never replace it with resolved task-graph paths: selectors expand across projects and included builds contribute their own internal requests. Executed work belongs in `tasks`, including included-build tasks. With no explicit task request, report an empty requested list rather than inferring intent from execution.

- Machine monitoring takes initial and final samples, including builds shorter than the periodic interval. Network and disk counters are normalized by actual elapsed sampling time. Never backdate samples to cover operations before monitoring began.

- `TuistMachineMetricsService` is eagerly started when the settings plugin is applied and passed as a managed service provider to build insights. Keep collector state out of configuration-cache parameters; every restored build needs fresh samples. Preserve the report service’s operation-only subscription.

- Timestamp machine samples and report fallbacks with Gradle’s operation clock (`Time.currentTimeMillis`), not the system wall clock; long-lived daemons can have different offsets between those clocks.

- Report time bounds cover the recorded operations and machine measurements, rather than unrelated internal callbacks. Keep earlier recorded operations intact, and include the final measurement in the reported duration. The reporter owns the early collector until its completion queue drains; the sampler’s independent Gradle close hook must not stop it prematurely.

- A stop-time reading less than 200 ms after a periodic reading replaces that periodic reading, with rates measured from the reading before it, to avoid unstable rates from a tiny final interval. Do not omit the stop-time reading instead: the last task can finish after the periodic reading, and monitoring must cover the reported build end. Preserve start/stop readings when no periodic sample was collected, including short builds. Downsampling keeps the first and last samples.

- `tuistPrepareTestShards` sends the module names of the projects that have the sharded test tasks, with suite granularity, and the server resolves each module's suites from test insights history. It does not depend on compiled test classes, so planning never compiles. The module list is a provider over each project's test task names, resolved when the task graph is built, after every project is configured. The prepare task calls `evaluationDependsOn` for every subproject when it is configured, because configuration on demand leaves subprojects unconfigured when `:tuistPrepareTestShards` is requested by path. Keep that in the task configuration, not in `apply`, so other builds keep configuration on demand.

- BuildFailureTelemetry retains only normalized failure categories. Configuration failures must report failure even without a failed task. Recovered cache-operation errors do not fail the build; infrastructure evidence takes precedence over verification. Preserve custom metadata limits and explicit category overrides.

Build infrastructure observations use existing `custom_metadata.values`; `BuildEnvironmentMetadata` probes allowlisted runtime values only at reporting time. Read effective Gradle workers at execution time even on configuration-cache reuse. Explicit values win and automatic values only fill spare slots. Stay at 20 values unless credential-free destination discovery advertises up to 64; no metadata-triggered POST retry, auth forwarding or persistent discovery cache. Discover and enrich before the shared report retry loop so replay-safe transport retries retain the same metadata payload and build ID without repeating discovery. Runner names require `TUIST_BUILD_METADATA_RUNNER_NAME=1`. See `server/docs/build-metadata.md` for rollout, semantics and privacy.

Automatic cache work avoided sums nonnegative original execution time minus observed restoration duration for local/remote task hits. Missing timings or incomplete telemetry omit the build estimate; never call cumulative work elapsed build time saved. Preserve explicit metadata and the 20-entry limit.

- Modules are named as test insights reports them (`testModuleName`), so the server matches them against historical suites. A shard configures each test task's filter from its project's assigned suites and skips test tasks with none. The server makes the plan's final shard a catch-all for plugin versions it knows support it, read from the `x-tuist-gradle-plugin-version` header, as it does for the CLI's version header: the catch-all has no modules, runs every test task, and excludes the suites listed in `skip`, so suites without history still run. The minimum version is `@suite_catch_all_minimum_gradle_plugin_version` in `TuistWeb.API.ShardsController`, and it must be the first plugin release that handles the catch-all. A plan without history has a single catch-all shard. Test insights records a nested class (`Outer$Inner`) as its own suite, and the server folds it into its top-level class when planning, because a filter on a class also includes or excludes its nested classes. Set the filter during configuration, never in `doFirst`: the filter is then part of the test task's cache key, and shards cannot load each other's results from the remote cache.

- `tuistPrepareTestShards` supports the configuration cache: its action never reads `project`. The root directory, the shard matrix output directory, and the `tuistBuildInsights` service (declared with `usesService`) are task properties set when the task is configured.

- A non-catch-all shard adds the test tasks of projects without suites in the shard to `startParameter.excludedTaskNames` from `projectsEvaluated`, so they leave the task graph with the dependencies only they need (test compilation). Add only exact paths of registered tasks: Gradle fails on an excluded path that matches no task. Gradle resolves exclusions after `projectsEvaluated`, except with configuration on demand, where it resolves them before configuring any project; there the exclusion is skipped and the `onlyIf` skip remains. Keep the `onlyIf` skip as the fallback, and keep the suite filters configured at configuration time so they stay in the test task's cache key.

- Resolve report credentials before collecting or publishing Git history, including the stress gate's early publication. Credential-free CI reports skip every history endpoint and omit history context from their JSON; authenticated opt-in reports retain ordinary history publication. Keep the same report-only configuration provider for history and report requests, without cache discovery.
- On CI, the test report carries the run's Git history (`GitHistoryService` over `GitHistoryReader`, a port of the CLI's `GitHistoryService` outside coverage): merge base, base branch head, and the commits reachable from the head and the checkout's base head within the server's window. It is collected during execution, never configuration, so it is not a configuration-cache input. `GitHistoryPublisher` in `TuistTestInsightsService` collects once per build and uploads the commits the server lacks (oldest first, branch heads on the last request, the base head even when unlisted) before the stress gate asks for its plan and before the run report; it is marked published only on success, so a failed early attempt is retried before the report. History is never fetched or deepened: the merge base comes only from the checkout, and a base branch the checkout lacks has its head read with one `git ls-remote` bounded by `deepen_budget_seconds`, killed with its children at the deadline. Base branch and pull request number come from CI variables only. Best effort: logged at info/debug, never a warning or a failed build. `TUIST_GIT_UPLOAD_ENABLED=false` collects nothing; `TUIST_GIT_UNSHALLOW_ENABLED=false` never contacts the remote. Stress repetitions never report, so never collect. Commit file listings are coverage-only and not collected. On a pull request's merge ref (`refs/pull/N/merge`) `ProcessGitInfoProvider.commitSha` reports HEAD^2, the pull request's head, as the CLI does, since the merge commit exists only in the checkout; a shallow checkout without that parent reports HEAD. When `GITHUB_SHA` (GitHub's merge commit) is set and is not HEAD, the workflow checked out another commit, and HEAD is reported.
