# Tuist Gradle plugin

Settings plugin written in Kotlin. `TuistBuildInsights` uploads build reports; `BuildExecutionTelemetry` collects execution and cache operations.

- Configure features through `GradleLifecycle` isolated actions, using immutable settings snapshots and each project's own tasks. The tested minimum is Gradle 8.12.1; older versions lack internal APIs used by telemetry. Keep service configuration in managed parameters and resolve linked build IDs while tests execute, before services close.
- Register the build insights service only through the configuration-cache-aware `onOperationCompletion` registry. A single service provider cannot hold both task and operation subscriptions. Keep it an operation-only listener so configuration reuse restores the correct subscription.
- Completion events are ordered. Propagate nested cache metadata to parents until the owning task finishes; do not depend on start events from this registry.
- Internal Gradle APIs can change. Catch unavailable operations without failing the build, and mark incomplete telemetry honestly. Integration tests must exercise real builds and configuration-cache reuse.
- Exclude machine counter reads from configuration input tracking and restore tracking in a finally block. Linux `/proc` counters are telemetry, not configuration inputs, and change between builds.
- Cacheability is task capability, not global build-cache availability. Fall back to `@CacheableTask` for disabled-cache or skipped lookups, while honoring observed task-specific disabled reasons.
- The build cache declares `tuist-checksum-sha256` (lowercase hex SHA-256 of the exact body) on every store. It hashes Gradle's entry writer in a separate pass before sending, because `HttpURLConnection` already buffers the body; the writer copies from a packed file and is repeatable. A 422 refusal retries the store once with a fresh checksum. On load, a well-formed `tuist-checksum-sha256` response header is verified when the body reaches end of stream; a mismatch, including a truncated body, is logged and returned as a miss. Gradle only unpacks an entry whose `readFrom` completed, so the partial download is discarded and the task runs. Responses without the header are not verified.
- Requests to Tuist go through `TuistRetry` with the `RetryPolicy` of `TuistHttpClients`: 4 attempts, waits of about 250 ms, 1 s and 2 s (20% jitter, each capped at 2 s; a `Retry-After` replaces the wait, capped at 2 s). Connection refused, no route to host and 503 are always retried. Replay-safe requests also retry dropped connections (reset, closed, unexpected end of stream), 502 and 504. Timeouts (a connect timeout is 30 s), cancellation, interruption and other statuses are never retried, and a failure an inner retry gave up on (a token refresh inside a request) is not replayed by the enclosing one. Replay-safe: GETs, cache PUTs (content-addressed), shard plan creation (the server serves a reference's latest plan), the stress plan (read-only), Git history uploads (stored commits and heads are skipped), token refresh (the server answers a refresh token presented again within 60 s of its exchange with the same tokens) and build/test report POSTs (each report carries a client-generated UUID `id`, created once per report and resent by every attempt, and the server stores a replayed `id` only once). A server older than that contract may store a replayed report twice or refuse a replayed refresh. Cache load/store throw `BuildCacheException` once attempts run out, so Gradle disables the remote cache for the build. The exception is a store answered 403: the credential may read but not write, so the service logs one warning and skips later stores without throwing, keeping loads; an entry body is read once, outside the retries. Only 400/401/403 from token refresh mean not authenticated; other refresh failures are `IOException`s. Shard planning, shard lookup and the stress plan use `ServerConfigurationProvider`: authenticated, without cache endpoint discovery. A failed quarantine lookup warns and applies no quarantine. Tests pass `RetryPolicy(sleeper = {})`.
- The server closes keep-alive connections idle for 15 s. OkHttp clients share the `ConnectionPool` of `TuistHttpClients` (5 idle connections, kept 10 s); derive clients with `newBuilder()` so they keep it. `HttpURLConnection` (cache, reports, history) keeps an idle connection 5 s when the server sends no `Keep-Alive: timeout` (the server and its ingress send none), and 60 s through a proxy. `http.keepAlive.time.*` are JVM-wide and read once, so the plugin does not set them. `TuistHttpClientsTest` pins both behaviours.
- Run tests with `./gradlew test --no-build-cache --no-watch-fs`. When validating source changed outside Gradle's file watcher, force compilation with `--rerun-tasks`.

- `ReportConfigurationProvider` resolves publishing destinations independently of cache endpoint discovery. Build/test reporting may omit genuinely absent credentials only after `GET /.well-known/tuist.json` advertises boolean `network_trusted_report_publishing: true`; cache access requires the independent `network_trusted_cache_access: true` policy, and shard planning remains authenticated. Discover during execution without credentials/actor claims or redirects; do not persist the policy in the configuration cache. There is no client opt-in. Retain the deprecated `buildInsights.networkTrustedPublishing` property as an ignored compatibility shim for existing build scripts. Unsigned tests omit existing-build, shard, stress/history references. Unsigned build/test JSON omits Git origins before serialization; signed behavior is unchanged. Report response decoders must tolerate missing/null actor metadata, unknown future fields and open provenance strings, including configuration-cache reuse. Quarantine lookup is skipped only when the optional credential resolver confirms genuine absence, not merely because the instance supports unsigned reporting, so authenticated runs preserve their behavior. Credential-free reports must refuse the default hosted destination when the self-hosted server URL is missing, preserving ordinary sign-in guidance for signed-out hosted users. Existing invalid credentials must not become anonymous retries, including after an authenticated 401 when refresh loses credentials. Refuse known hosted destinations and `*.tuist.dev` before credential-free uploads, normalizing case and trailing dots. Credentials reads normalize case/trailing dots and match legacy hostname aliases; refresh writes back to the selected file so the CLI never keeps a stale duplicate. Inspect credentials and every directory ancestor with strict NIO operations: only a genuinely missing path is absence; access errors, non-directories and dangling links fail closed. Keep real POSIX permission-denial and hostname-alias regressions. Token resolution uses validated credential reads and preserves corrupt files, so cache/test initialization cannot delete invalid credentials and turn the next build report into an anonymous submission.
- The build cache exchanges its credential for a project-scoped cache token (`POST /api/cache/token`, `GetCacheTokenService`) once per expiry, as the CLI's cache clients do, so a cache node verifies it locally and attributes the request's origin. Any failure other than 402 falls back to the credential for a minute; 402 is a `BuildCacheException`, never a fallback, because the credential may still carry cache grants. A 401 on a request that sent the cache token (a node that cannot verify it locally, such as the legacy cache service, asks the server, which never accepts a cache token as a credential) switches to the credential for the rest of the build. Network-trusted access sends no credential and exchanges nothing.
- A stored access token that has not expired is read without the cross-process refresh lock; only a refresh (or a forced one after a 401) takes it. The lock's `flock` goes through JNA, which starts `ldconfig -p` the first time it loads on Linux, and build cache lookups run while Gradle configures (compiled build scripts), where a process start discards the configuration cache. Keep JNA off that path.
- Build/test report POSTs may include an unverified `x-tuist-actor-id`: explicit environment `TUIST_ACTOR_ID`, then `buildInsights.actorId`. Never infer usernames or send a claim by default. Empty/invalid overrides omit the claim instead of falling back. Keep the optional service parameter configuration-cache compatible; never change credentials, report JSON, cache/quarantine/shard requests or endpoint discovery for attribution. Older servers ignore the header.

Related: `server/lib/tuist/gradle/AGENTS.md`.

- Initialize local end-to-end demo projects as Git repositories and commit their fixture sources before recording builds, so branch and commit metadata is present in dashboard examples.

- Build reports include `started_at` using the same origin as `duration_ms`, including configuration-cache reuse, so the server can align operations with machine samples.

- Keep requested work separate from executed work, as a build-system-independent concept. `requested_tasks` preserves the original invocation in order through configuration-cache-compatible service parameters. Never replace it with resolved task-graph paths: selectors expand across projects and included builds contribute their own internal requests. Executed work belongs in `tasks`, including included-build tasks. With no explicit task request, report an empty requested list rather than inferring intent from execution.

- Machine monitoring takes initial and final samples, including builds shorter than the periodic interval. Network and disk counters are normalized by actual elapsed sampling time. Never backdate samples to cover operations before monitoring began.

- `TuistMachineMetricsService` is eagerly started when the settings plugin is applied and passed as a managed service provider to build insights. Keep collector state out of configuration-cache parameters; every restored build needs fresh samples. Preserve the report service’s operation-only subscription.

- Timestamp machine samples and report fallbacks with Gradle’s operation clock (`Time.currentTimeMillis`), not the system wall clock; long-lived daemons can have different offsets between those clocks.

- Report time bounds cover the recorded operations and machine measurements, rather than unrelated internal callbacks. Keep earlier recorded operations intact, and include the final measurement in the reported duration. The reporter owns the early collector until its completion queue drains; the sampler’s independent Gradle close hook must not stop it prematurely.

- A stop-time reading less than 200 ms after a periodic reading replaces that periodic reading, with rates measured from the reading before it, to avoid unstable rates from a tiny final interval. Do not omit the stop-time reading instead: the last task can finish after the periodic reading, and monitoring must cover the reported build end. Preserve start/stop readings when no periodic sample was collected, including short builds. Downsampling keeps the first and last samples.

- `tuistPrepareTestShards` sends module names with suite granularity; the server resolves their suites from test insights history. Each project publishes a small descriptor of its test task names after configuration. Planning consumes these project artifacts, never compiled test classes or another project's task container, and honors `tuistShardTestTask`. Dependency resolution configures the producers on demand.

- BuildFailureTelemetry classifies the build into a normalized failure category and renders each failed task's and configuration operation's `failure`: the exception message and cause chain as the console prints them (`MultiCauseException` causes included, messages a wrapper repeats skipped), never stack traces or task output, with paths under the root directory made relative, at most 16 KiB (UTF-8 safe) and 32 per build. A failure an enclosing operation rethrows is reported once, by the first operation that finished with it. Credential-free reports omit failures: servers that predate the field refuse unknown nested keys from unsigned publishers. Configuration failures must report failure even without a failed task. Recovered cache-operation errors do not fail the build; infrastructure evidence takes precedence over verification. Preserve custom metadata limits and explicit category overrides.

Build infrastructure observations use existing `custom_metadata.values`; `BuildEnvironmentMetadata` probes allowlisted runtime values only at reporting time. Read effective Gradle workers at execution time even on configuration-cache reuse. Explicit values win and automatic values only fill spare slots. Stay at 20 values unless credential-free destination discovery advertises up to 64; no metadata-triggered POST retry, auth forwarding or persistent discovery cache. Discover and enrich before the shared report retry loop so replay-safe transport retries retain the same metadata payload and build ID without repeating discovery. Runner names require `TUIST_BUILD_METADATA_RUNNER_NAME=1`. See `server/docs/build-metadata.md` for rollout, semantics and privacy.

Automatic cache work avoided sums nonnegative original execution time minus observed restoration duration for local/remote task hits. Missing timings or incomplete telemetry omit the build estimate; never call cumulative work elapsed build time saved. Preserve explicit metadata and the 20-entry limit.

- Modules are named as test insights reports them (`testModuleName`), so the server matches them against historical suites. A shard configures each test task's filter from its project's assigned suites and skips test tasks with none. The server makes the plan's final shard a catch-all for plugin versions it knows support it, read from the `x-tuist-gradle-plugin-version` header, as it does for the CLI's version header: the catch-all has no modules, runs every test task, and excludes the suites listed in `skip`, so suites without history still run. The minimum version is `@suite_catch_all_minimum_gradle_plugin_version` in `TuistWeb.API.ShardsController`, and it must be the first plugin release that handles the catch-all. A plan without history has a single catch-all shard. Test insights records a nested class (`Outer$Inner`) as its own suite, and the server folds it into its top-level class when planning, because a filter on a class also includes or excludes its nested classes. Set the filter during configuration, never in `doFirst`: the filter is then part of the test task's cache key, and shards cannot load each other's results from the remote cache.

- `tuistPrepareTestShards` supports the configuration cache: its action never reads `project`. The root directory, the shard matrix output directory, and the `tuistBuildInsights` service (declared with `usesService`) are task properties set when the task is configured.

- Shard assignments come from a settings `ValueSource`: unchanged assignments permit configuration-cache reuse; changed assignments invalidate it before task filters are restored. Ignore expiring artifact URLs when comparing assignments. Keep suite filters configured before execution so shards cannot reuse each other's cached test results.
- Without Isolated Projects or configuration on demand, a non-catch-all shard adds exact registered test task paths of unassigned projects to `startParameter.excludedTaskNames` from `projectsEvaluated`, pruning their otherwise unused compilation dependencies. With either feature enabled, retain the project-local `onlyIf` fallback instead of reading another project's task container.

- Resolve report credentials before collecting or publishing Git history, including the stress gate's early publication. Credential-free CI reports skip every history endpoint and omit history context from their JSON; authenticated opt-in reports retain ordinary history publication. Keep the same report-only configuration provider for history and report requests, without cache discovery.
- On CI, the test report carries the run's Git history (`GitHistoryService` over `GitHistoryReader`, a port of the CLI's `GitHistoryService`): merge base, base branch head, and the commits reachable from the head and the checkout's base head within the server's window. It is collected during execution, never configuration, so it is not a configuration-cache input. `GitHistoryPublisher` in `TuistTestInsightsService` collects once per build and uploads the commits the server lacks (oldest first, branch heads on the last request, the base head even when unlisted) before the stress gate asks for its plan and before the run report; it is marked published only on success, so a failed early attempt is retried before the report. What reaches the remote is `GitHistoryLimits.remoteAccess`, chosen by `GitHistoryEnvironment.remoteAccess(coverage)` as the CLI's `GitHistoryService.remoteAccess(coverage:)` does. Without coverage (`BASE_HEAD`) history is never fetched or deepened: the merge base comes only from the checkout, and a base branch the checkout lacks has its head read with one `git ls-remote` bounded by `deepen_budget_seconds`. A coverage run (`HISTORY`, `coverageEnabled()` in `TuistTestInsightsService`) ports `GitController+History.swift` (see `cli/Sources/TuistGit/AGENTS.md`) and must stay in step with it: `GitHistoryReader.read` fetches a base branch the checkout lacks and deepens a shallow clone until the merge base is found, and `GitHistoryReader.connect` (called by `GitHistoryService.collect`, which asks `commits/missing`; a server that cannot be asked counts as having them) deepens through the base branch, or the run's own on a push, while the server lacks a first parent the clone stops at. Every fetch names one branch, uses `--filter=blob:none`, steps 50 then doubling within the history window, stops at a failed fetch, and shares one `deepen_budget_seconds` budget per phase; the gap-closing fetch passes `--refmap=` so the checkout's `origin/<branch>` does not move. `--deepen` deepens from every commit the clone stops at, so on a depth-1 `refs/pull/N/merge` checkout it also fetches the merge commit's second parent, the pull request's head, which is then uploaded. Collection only runs on CI, which is what keeps a developer's clone from becoming a partial one. Every remote command (`GitRunner.captureWithin`, `fetchWithin`) still running at its deadline gets SIGTERM, so git removes its lock files (a killed deepening leaves `shallow.lock`), with the processes it started (`git-remote-https`, `ssh`, `index-pack`), and SIGKILL a second later. Base branch and pull request number come from CI variables only. Best effort: logged at info/debug, never a warning or a failed build. `TUIST_GIT_UPLOAD_ENABLED=false` collects nothing; `TUIST_GIT_UNSHALLOW_ENABLED=false` never contacts the remote, coverage or not. Stress repetitions never report, so never collect. Commit file listings are coverage-only and not collected. `ProcessGitInfoProvider.commitSha` reports the checkout's HEAD, as the CLI does: on a pull request's merge ref (`refs/pull/N/merge`) that is the merge commit the run measured, which the server keeps on the pull request's ref, off the branch.

- Coverage (`TuistCoverage.kt`, on with `tuist { coverage { enabled = true } }` or `TUIST_TEST_COVERAGE`, which wins) applies `jacoco` to JVM projects and loads the `coverageListener` source set's jar (Java 8, embedded as a resource, copied by content hash under the Gradle user home) into test JVMs as a `-javaagent`, so JUnit Platform loads its listener as a service. The listener takes and resets JaCoCo's probes at every test and class boundary, appends them back to the agent's execution data file under a lock, and writes each segment with its scope to the task's local state, so the execution data still holds everything and only executed tasks carry evidence. Keep the jar a `@Classpath` input and the evidence directory `@Internal`/local state, so neither path reaches the cache key. A test task whose JaCoCo `includes` are empty gets the repository's packages in `doFirst`, once the classes exist, as `pkg.*` only where no dependency on its classpath has classes in or under `pkg` and class by class otherwise (each jar's packages are cached per daemon); reach its `JacocoTaskExtension` through a provider, because `Task.extensions` at execution time fails with the configuration cache. Test tasks are recorded in `onlyIf`, which runs before up-to-date and cache checks, and their outcome comes from `onTaskCompletion`: restored tasks report measured coverage from their restored execution data and no evidence. A shard that already reported its plan and index from this checkout (marker under `.gradle/tuist/shard-reports/`) and executed no test does not report again. What a run left out mirrors the Xcode CLI: `--tests` (Gradle's internal command-line patterns) names the tests run in `only_test_identifiers`, a partial selection of projects names the projects (a test task with no unit test sources is never left out: one with a same-named Java source set reads that set, others read AGP's `android.sourceSets` and Kotlin's `kotlin.sourceSets` through reflection, unit test sets only, and count as having tests when neither model exists; a test task the build reached is part of the run even when its own configuration skipped it, so outcomes are kept for every listed test task, not only recorded ones), `-x` names skipped projects, and a shard or quarantine names nothing. Execution data under a product class's name that matches no repository class of that name is a mismatch (partial) unless a non-repository classpath entry holds that name (a stand-in for a dependency's class). A jar whose manifest says `Multi-Release: true` adds each `META-INF/versions/N/` class as another class of its name, mapped to its own compilation's source file; every other `META-INF/` entry is ignored. Every reason the run is partial is logged in one warning (`CoverageResult.partialReasons`). `CoverageUploader` sends the coverage and then the evidence inline or uploads them as tuist_ex does (server threshold and what the 49 MB report budget leaves each; evidence as NDJSON to `evidence_upload_url`, falling back to inline, then inline without lines, then none). Coverage is best effort and credential-free reports omit it, so a credential-free build whose test tasks were all restored reports nothing. `TuistCoverageFunctionalTest` exercises the scenarios through real builds with the configuration cache; see `server/docs/code-coverage.md#gradle`.
