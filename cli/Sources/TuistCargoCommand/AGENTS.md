# Cargo decoration

`tuist cargo` forwards Cargo's command line without redefining its test semantics. Plain `cargo test` (including doctests) reports validated standard libtest outcomes on stable Rust. `test --no-run` with shard-count options plans target-level shards; `TUIST_SHARD_INDEX` applies assignments to `test`. Plain tests enforce shared mute/skip quarantine. Nextest remains optional for richer timing, retries, and archive sharding. The same command can be installed as a mise Cargo wrapper. `test-build` is Tuist's build-once nextest shard planner; `nextest run` applies a shard only when explicitly configured.

## Compilation cache

- The implementation is Swift in this module, not a vendored engine, external cache tool, Rust executable, or mechanical translation. There are two exceptions, both embedded C built into the cache: `CargoReadRecorder`'s interposer, which must be a library loaded into rustc and build scripts (built with `xcrun clang` on macOS and `cc` on Linux), and `CargoHookServer`'s client (macOS only, built with `xcrun clang`). Cargo starts that client for every rustc instead of the Swift binary; it carries no cache logic. It asks the outer command over a private Unix socket, writes a hit's messages, or runs the command the server returns and streams rustc's stderr through the server, which certifies metadata before returning the bytes to forward. After rustc exits, the server admits and certifies the outputs (and stores and shims a build script's compilation, which Cargo runs next) before reporting the exit, then publishes on the connection's thread. Everything else waits until Cargo has heard the exit, because Cargo starts dependents only then and nothing reads it before the build ends: the build report's compilation row, measurements, a replaced source list, and a build-script run's store (which hashes every read and copies `OUT_DIR`, and for `aws-lc-sys` held back the crates that wait on it). The session waits for those publications before reporting and collecting units. The client stays rustc's parent so jobserver descriptors, stdin and the process group are Cargo's. It drops `DYLD_*` on entry as the `/bin/sh` wrapper it replaces did (SIP), runs from its stable path in the cache (Cargo keys `.rustc_info.json` on the wrapper's path and modification time, so a per-session copy would make Cargo probe rustc on every build; recorded build-script runs drop it from `RUSTC_WRAPPER` because it equals `TUIST_CARGO_SCRIPT`), and runs `tuist cargo __compiler` when the server is unreachable before rustc started; once rustc ran, a lost connection exits with rustc's status. The pruner never evicts the client or the recorder: Cargo starts them by path for every compilation of a running build. Server-side probes drop `CARGO_MAKEFLAGS`/`MAKEFLAGS`/`MFLAGS`, and `CommandRunner` inherits jobserver descriptors only when they are pipes: in the server the hook's descriptor numbers name its own sockets and kqueues, and inheriting them would fail every probe and silently turn the per-crate cache off. Preparation failures other than a refusal are logged under `TUIST_DEBUG`. `tuist cargo __compiler` remains the invocation-local compiler wrapper. Keep it free of authentication and command-event publication. Keep debug diagnostics on stderr rather than bootstrapping the generic Noora logger; stdout belongs to Cargo/rustc's protocol.
- `CargoCacheSetup` reads Tuist's existing configuration, resolves `CacheURLStore` and `GetCacheTokenService`, and refreshes a private mode-0600 token file. Failed remote setup leaves an isolated local cache. Support-cache pruning runs at most hourly (stamp `.tuist-cargo-pruned` in the `Cargo` category): walking every support cache costs more than a warm build. Reporting metadata (one `git rev-parse` for the commit and branch, the origin URL, and the rust version from the session's toolchain identity) is gathered alongside the build, and the `cc` shim's `xcrun`/`otool` probe is remembered per developer directory and compiler identity. Inject endpoint/token services, `CacheDirectoriesProviding`, and `FileSysteming`. Store entries in the shared `Cargo` cache category so `XDG_CACHE_HOME`, normal cache cleaning, support-cache retention, and runner byte budgets apply. The shared pruner addresses individual action/blob files and staging entries beneath each project, not the perpetually hot project directory. Every layer stores blobs through `CargoBlobStore` (`blobs/<hash>`, published by clone, hash and atomic `rename`); reads renew a blob's modification time when it is more than an hour old, so active contents stay recent without changing the identity verified digests are recorded with. Index and record files go through `CargoBlobStore.write` (a temporary file and `rename`, without Foundation's `fsync`): a seed build writes thousands, and flushing each slowed every rustc running beside it. Readers verify or decode what they read, so a record a crash loses is only a miss. There is no `[cargo]` configuration section or enablement knob. Clear inherited internal cache settings. Remote reads and writes use Kura's shared REAPI transport and server-issued cache grants; do not add client-side CI-provider or branch eligibility gates. Denied uploads preserve the local entry and never fail the build.
- `CargoCacheInvocation` admits pure libraries emitting dep-info and metadata, with an rlib or without one (`cargo check` and `cargo clippy`, the inner loop of editors and agents), including workspace/path libraries and generated sources. `--emit` is keyed with the other arguments, so a metadata-only entry never serves a compilation that links, nor the other way around. Registry leaves retain the full-package fast path. Other libraries hash every source an earlier compilation's dep-info named (including non-Rust includes), found through a source list under a declared key (relocated arguments, keyed environment, root source and extern digests) in `CargoReadIndex`, locally and remotely, plus the entries of every directory holding a source so a file that would change module resolution misses. Without a list the compilation runs first and is keyed afterwards from the dep-info rustc writes anyway (sources must predate preparation, checked with `stat` because Foundation on Linux has no attribute modification date); there is no separate discovery run of rustc unless no cache directory exists. A served hook does not wait for rustc to finish, as Kache does not: rustc's `dep-info` artifact notification arrives right after macro expansion, the server keys the compilation from that file and looks the key up (locally, then remotely) while rustc goes on, also when a remembered list missed and dep-info names other sources. On a hit the client kills rustc (a strict library compilation writes its outputs itself, with no linker child, so Kache's stop-and-check for linking compiles does not apply) and the server restores the entry once rustc exited, removing objects rustc began writing; when restoration fails, the client runs rustc again. Until the lookup ends, rustc's standard error is held back, so Cargo sees only a hit's replayed messages: the metadata notification waits for the lookup and is certified when released, never forwarded for a compilation that is then discarded. A deferred compilation also runs recorded where the recorder exists: only after rustc does admission see every source, and when it refuses one (assembly or `#[link]` in a submodule) the same build stores the recorded result instead. When dep-info names other sources than the list, the list is replaced and the compilation is published under the new key on the same build. `cli/Tests/Fixtures/CargoCache/sources_e2e.sh` covers added and edited submodules and ambiguous modules. Keys also cover complete direct extern artifacts, compiler/toolchain libraries (the sysroot's top-level `lib` files plus the host `lib/rustlib/<host>` tree from `--print target-libdir`, excluding its linker-only `bin`; other installed targets and `rust-src` stay out of keys), arguments, working directory and the keyed build environment (an allowlist: `CARGO_*` except `CARGO_INCREMENTAL`, `RUSTC*`, `RUST_*`, `RUSTFLAGS`, `OUT_DIR`, `SDKROOT`, `RUSTUP_TOOLCHAIN` and `*_DEPLOYMENT_TARGET`). Package metadata rustc itself never reads (`CARGO_PKG_*` other than the name and version, and `CARGO_PRIMARY_PACKAGE`) is keyed only where the crate read it (`isKeyedWhenRead`): strict keys take the reads from dep-info's `# env-dep:` lines into the source list (which publication checks against dep-info), recorded keys from the recorder and dep-info, so editing a description misses only for crates that embed it. So are the variables that only start compilations (`launchEnvironment`): `RUSTC_WORKSPACE_WRAPPER` and what rustup's proxy sets when `cargo clippy` starts `cargo-clippy` (`RUST_RECURSION_COUNT`, `CARGO_HOME`), which rustc never reads, so dependencies `cargo clippy` compiles with rustc share `cargo check`'s entries. Registry leaves are keyed before rustc runs and keep every other variable (their manifest is keyed by content anyway); one whose dep-info names a launch variable is not cached. The name and version stay keyed: rustc reads `CARGO_PKG_VERSION_*` itself, and `-C metadata` changes with them. The one unstable option strict admission takes is a single valid `-Z threads=<0-255>`, which keys as `-Zthreads=0` in both keys: rustc marks it untracked, so counts share entries, but its presence stays keyed (a toolchain that rejects `-Z` fails with it), and malformed or repeated ones stay as given (strict bypasses them) so a cached success cannot hide rustc's error. So do all of them beside a `-j`/`--jobs*` option (which `-Z unstable-options` enables, and recorded keys admit): rustc fails when the thread count exceeds the job count. An exported `RUSTFLAGS` variable still keys its count. Never hash the concurrently changing `target/.../deps` directory. Exclude Tuist credentials/reporting settings and bounded CI metadata prefixes only when compiler dep-info proves the crate did not read them (including unset `option_env!` inputs). Version-7 keys are relocatable; keep Command/Action and invocation key versions aligned. Recheck fingerprints before publication and restoration. Resolve bare and absolute compiler paths like the process launcher. Accept the known rustup proxy only with a pinned toolchain, including both proxy and compiler bytes; arbitrary custom launchers bypass caching.
- A dependency can export generic MIR or macros with backend filesystem reads absent from dep-info. Require every explicit `.rlib`/`.rmeta` extern to have a private session-local admission certificate tied to its exact artifact digest (in memory for a served session, like its input digests; otherwise a file in the session). Publish certificates only after source/dependency validation and fingerprint rechecking. Certify atomically installed metadata before forwarding rustc's metadata artifact notification: Cargo starts pipelined dependents at that boundary, before upstream codegen finishes. This certificate establishes input admission, not compilation success; never publish cache entries for failed compilations. Certify rlibs after successful compilation and both artifacts after verified restoration. A metadata-only compilation passes the same admission and certifies its metadata under its own digest: it never stands in for a build's metadata, and its dependents still need a certificate for every extern. Admission propagates through the dependency closure; missing/corrupt certificates bypass caching, not compilation. Scan every discovered input for assembly (including `naked_asm`), native-link attributes and identifier concatenation; ordinary `concat!` remains supported. Match code tokens only: comments and string/char literal contents are blanked first, and sources that do not lex bypass caching. `link` is rejected only as `link(`, so identifiers and prose such as "symbolic link" stay eligible. Strict admission rejects proc-macro consumers transitively, native search paths/bundling, nonstandard codegen, custom targets and executables; recorded invocations (below) take what it rejects. Do not substitute metadata-only output equality for this contract: changing rustc's emit modes changes metadata, and metadata does not cover backend reads.
- Incremental compilation is cacheable. Cargo passes `-C incremental=<dir>` to every workspace crate in the `dev` profile, and those crates are usually a build's critical path, so rejecting it left most of a workspace build uncached. Both keys leave the argument out (`CargoCacheInputs.withoutIncremental`) and the `CARGO_INCREMENTAL` variable too (`ignoredEnvironment`, and the unit manifest key). Cargo folds the incremental setting into `-C metadata` of each unit it compiles incrementally, so workspace crates built with and without incremental compilation (CI usually sets `CARGO_INCREMENTAL=0`) have different arguments and never share entries; dependencies, which Cargo never compiles incrementally, do. On CI (`Environment.isCI`) with a toolchain older than Cargo 1.99, which turns incremental compilation off by default when `CI` is set, a miss runs without `-C incremental` when its target neither compiled the unit before nor holds a session of the crate (`CargoCacheInputs.withoutFirstIncrementalSession`, which remembers units under `<incremental>/.tuist-compiled`, hits included): that compilation is a full one anyway, building a session costs about a quarter more, and its entry holds 16 codegen units' objects instead of 256, so restoring it is cheaper too. Not locally: after a fresh target the misses are mostly crates with local changes, which are edited next, and without a session the first edit of `codex-core` took 134–196 s instead of 17 s. Other misses run incrementally, and a recorded run may write its incremental session. An incremental crate leaves an unpacked debug object per codegen unit (256) beside its rlib, so entries hold up to `CargoCompilationCache.maximumOutputFiles` files; a lower bound silently stops large workspace crates from being stored, and since rustc's incremental output is not byte-identical across builds, every dependent then misses too. Restoring a hit leaves that session as it was: rustc revalidates it on the crate's next compilation.
- `CargoClippy` admits what `cargo clippy` runs through Cargo's workspace wrapper, `clippy-driver rustc <arguments>`, for metadata-only libraries, in both strict and recorded keys, when the driver is the one of the compiler's sysroot and `SYSROOT` is unset (the driver would pass it as `--sysroot`); other workspace wrappers, and Clippy's proc macros and build scripts, stay uncached. The key adds what changes a successful run's output beyond its arguments: `clippy-driver --version` (once per session) and the driver's content, `CLIPPY_ARGS`, `CLIPPY_CONF_DIR`, `CLIPPY_DISABLE_DOCS_LINKS`, the package's `Cargo.toml` and the `.clippy.toml` or `clippy.toml` Clippy would load (from `CLIPPY_CONF_DIR`, else the manifest directory, upwards), read again on every fingerprint; a hit replays Clippy's diagnostics like rustc's. These variables are keyed only for driver compilations, which dep-info shows reading `CLIPPY_ARGS`. The `cargo` lint group runs `cargo metadata`, which reads every manifest and the lockfile, so naming it (in arguments, `CLIPPY_ARGS` or a source, including joined flags such as `-Wclippy::cargo` and hyphenated lint names, which rustc reads as underscores; `cargo clippy` joins `CLIPPY_ARGS` with `__CLIPPY_HACKERY__`) bypasses strict caching, and a recorded run refuses the spawn. The unit cache takes `clippy` as a command kind of its own (version 5: earlier `check` manifests recorded no certificates, since no check metadata was certified then), which also gives its compilations relocation roots and the recorder. `cli/Tests/Fixtures/CargoCache/check_e2e.sh` covers check and Clippy reuse, replayed warnings, certification of restored metadata, and Clippy's misses.
- Every crate compilation the cache cannot take (test harnesses, unsupported flags) is counted as `unconsulted` with a task record (`CargoCacheMeasurement.uncached`), so task misses and the hit rate cover every crate that compiled. Probes (`--print`) and compilations without a cache directory are not counted.
- Reject grouped Rust short options such as `-gL` that hide search paths or codegen/unstable flags; supported joined codegen, search and lint operands remain eligible. Strict and recorded compilations and build-script runs bypass caching under loader settings `CargoToolchainIdentity.admitsLoader` refuses: hashing their string values cannot cover injected code or its reads. Cargo sets `LD_LIBRARY_PATH` for every process it starts, so the predicate admits what Cargo builds: an empty value, or absolute entries (split on `:` and `;`, as glibc does) whose resolved paths are the toolchain's `lib` or host target libdir or lie inside `TUIST_CARGO_TARGET_DIR`. Paths compare resolved because rustup names a linked toolchain through its link and an in-target search path can link elsewhere. Without that directory (no unit cache scope, as for `--target` builds) or with a `build.build-dir` outside it, Cargo's own entries bypass. Any other entry (an inherited `/usr/local/lib`, an empty entry, which searches the working directory), `LD_PRELOAD`, `LD_AUDIT` and every `DYLD_*` bypass. For rustc, Cargo also adds the in-target native search paths of a proc macro's dependencies, and ld.so loads those libraries without libc calls an `LD_PRELOAD` recorder sees, so the Linux recorder keys by content every library a recorded process loaded (`dl_iterate_phdr`, below). Only the recorder sets `DYLD_INSERT_LIBRARIES` (macOS) or `LD_PRELOAD` (Linux) itself, for the processes it records; an inherited `LD_PRELOAD` still bypasses.
- `CargoRelocation` makes keys and stored text path-free, like Bazel's execroot-relative actions. It maps the sysroot, Cargo home, `TUIST_CARGO_TARGET_DIR` and `TUIST_CARGO_WORKSPACE_ROOT`, plus their `/private` spellings on macOS only (on Linux a `/private` root would turn placeholders back into paths that do not exist, which key every recorded read as absent) (a root before any root its path contains, otherwise in a fixed order: keys hold the mappings, and ordering by length made a checkout whose target directory is longer than the sysroot miss) to `@@TUIST_*@@` placeholders in every key input, dep-info file and stored stderr, and every hooked compilation runs with matching `--remap-path-prefix` flags (the workspace maps to `.`, not an empty path: rustc then omits the compilation directory, ld64 leaves such compile units out of a binary's debug map, and lldb found no workspace crate even in a fresh link). Remapping does not cover what a crate embeds itself (for example `env!("CARGO_MANIFEST_DIR")` in a proc macro): `boundRoots` scans outputs for root paths, ignoring the Mach-O `__LINKEDIT` segment and a dylib's own `LC_ID_DYLIB` install name, and an output naming a root its key did not include is not stored (a recorded binary's `.dSYM` holds debug information only, so `CargoRecordedInvocation.unkeyedRoots` leaves it unscanned). A file's scan is remembered under its identity (`boundRoots(of:)`): keying a recorded compilation, publishing it and collecting units after Cargo exits scan the same outputs, and rescanning a seed's gigabytes of rlibs per root delayed its end by several seconds. Units bound to a root restore only where that root is the same.
- `CargoRecordedInvocation` keys what strict admission cannot key in advance (proc-macro consumers, including their metadata-only and Clippy compilations, assembly, native libraries and their dependents, and linked binaries, stored with their executable bit; a build script's binary is stored before `CargoBuildScript` shims it, and a hit installs the shim), like Bazel's dependency discovery or blaze's read tracking. A linked binary whose debug map names objects (debug information unpacked, Cargo's macOS default) is stored with the `.dSYM` that `xcrun dsymutil` writes while those objects exist, its `Info.plist` and DWARF only: ld64 writes the objects' absolute paths, which `--remap-path-prefix` does not change, so a binary restored into another checkout or after `cargo clean` named objects that were elsewhere or gone, and lldb prefers a UUID-matched `.dSYM` beside the binary. `dsymutil` runs only once the run is known to be cacheable (the session waits for it), and overwrites an earlier bundle in place: Cargo uplifts the bundle beside the profile's binary as soon as it hears the exit, so a fresh link's profile has none until a later build, while a hit's bundle is restored before Cargo uplifts it. Removing the bundle first could race that uplift and fail the build. Restoration replaces the bundle whole. It runs `dsymutil --linker parallel` (about half the classic linker's time on Codex's 1 GB binary; `dwarfdump --statistics` matches except for local variables with no location, which it drops) and the classic linker where that fails, such as an older toolchain. A failed `dsymutil` leaves the binary unstored. `-oso_prefix` was not used: relative object paths resolve only from the profile directory, and not at all once the objects are gone. On arm64 macOS, `CargoReadRecorder` compiles its embedded C interposer with `xcrun clang` into the cache as a universal arm64/arm64e dylib and injects it with `DYLD_INSERT_LIBRARIES`. With System Integrity Protection off, as on many CI machines, macOS no longer strips `DYLD_*` from its protected arm64e programs (`/bin/sh`, `/usr/bin/cc`, `xcrun`, `git`), and dyld terminates any process whose inserted library lacks its slice. The recorder then stands down in any program whose file has the restricted flag: it logs nothing and removes `DYLD_*` from the environment, as SIP would, so runs record the same events on every machine (otherwise the session's `cc` shim's hook client would log its socket connection and refuse every link). The compiler arguments name the dylib, so changing them rebuilds it without changing recorded keys; it logs file opens, stats, directory listings, `readlink`, environment reads, process spawns and network connections. Each process buffers its events and writes them in batches: before it spawns, forks or execs, so a child's events follow its parent's, and when it exits or execs, followed by an `F` event (a forked child, which never logged `P`, writes as it goes; a restricted program the recorder stands down in logs nothing). `CargoReadSet` refuses a run in which a process that logged `P` has no later `F` (a failed exec's `Y` or `Z` reopens it), so a process that died before writing its events cannot leave reads out of the key. The exit and exec writes take the lock with a bounded wait, so a signal handler that exits mid-append loses its `F` instead of hanging. On a mise seed this saved about 3 s of kernel time (about 1%); the rest of the seed's extra kernel time is not the recorder's writes. Recorded processes exec the resolved binary directly because SIP strips `DYLD_*` through `/usr/bin/env`; reentrancy uses a pthread key because `__thread` aborts dyld. Reads under `/dev/` are not inputs (`/dev/null`'s modification time changes whenever anything writes to it). Spawns are counted only when they happen: `posix_spawn`/`posix_spawnp` log after succeeding (with the guard held, since one searches PATH through the other), and an `execve` that returns logs `Y` to withdraw its attempt, so PATH searches do not make build scripts that run `rustc` uncacheable. A `POSIX_SPAWN_SETEXEC` spawn replaces the process, so it is logged like `execve`. Processes of allowed programs (the linker) do not count towards the processes that loaded the recorder. Every recorded process also logs its parent (`p`), so the processes of a modeled program and their children are left out of the run's events, including the programs they start: without SIP `/usr/bin/ar` loads the recorder and runs Xcode's `ar`, which runs `ranlib`, and a forked child's `execve` attempt is dropped once the program it started names a modeled parent. Protected programs the recorder cannot load into are modeled from a `Q` event (the program that ran, working directory, how its environment differs from the one the process started with, arguments), logged for `posix_spawn`/`posix_spawnp` and, as `J`, for `execve`, which a forked child's `execvp` tries once per `PATH` directory (`Z` withdraws a failed attempt); Rust forks that way whenever a command sets its own `PATH`, as cc-rs does for `xcrun`. Read-only queries (`git describe`/`rev-parse`/`log`/`status` and similar, `xcrun --show-sdk-*`/`--find`, `xcode-select -p`, `sw_vers`, `uname`) are keyed by their exit status and relocated output, run again at lookup with the run's environment and the logged changes, and never from a directory a `chdir` file action changes (a run's read of `.git/index` in a working tree whose state such a query printed, `describe --dirty`, `status` or `diff`, is not an input: its bytes hold every file's inode and times, as bat's `git_version!` reads it only to make Cargo rerun; the rest of `.git` stays keyed); transforming tools (`CargoTool`: ad hoc `/usr/bin/codesign` of files the run wrote, a single-file `swiftc` with an allowlisted flag set, `/usr/bin/ar`/`ranlib` building an archive) key the sources they name like recorded reads, make their outputs the run's own, and key their environment changes, the OS build, plus the Xcode build for the archivers and the Xcode and SDK builds and the compiler's `--version` for `swiftc`. Any other argument keeps the run uncacheable. A recorded build script's `cc` goes through the protected `/bin/sh` shim, so the hook starts the selected clang recorded again (with `SDKROOT` as `xcrun` would set it, and `-fdebug-prefix-map` for the relocation roots ahead of the script's arguments, so debug information a crate embeds does not bind it to the checkout) when `TUIST_CARGO_READ_SCRIPT` names the request's log: such compilations are cached with the script's run, not one by one. Refusals explain themselves under `TUIST_DEBUG`. `CargoReadSet` refuses to cache when a child did not load the recorder, on any network connection, or on writes outside the outputs. Keys take two steps: a declared key (relocated arguments, keyed environment, externs by content, toolchain identity including the linker for proc macros and binaries) selects the read set of an earlier run in `CargoReadIndex` (local and REAPI), and that set's current contents, missing paths and directory listings complete the key. The unrecorded linker searches a link's `native=`/`all=` directories, so the declared key also holds the content of every native library in them outside the sysroot (more than 64 in one directory bypass caching). A link reads every rlib of its closure whole, so those reads stay in its read set even under the target directory: a `-sys` crate's bundled archive changes its rlib but not the metadata of the crates between it and the binary. Never certify recorded outputs for strict dependents. A run is stored only when no recorded file changed after it started (`CargoReadSet.changedInput`, named in the refusal); directories it merely looked up are exempt when they existed before the run started (their birth time, `st_birthtimespec` or Linux `statx`; without one they are checked like files), since git creates files in `.git` while a query runs, and listed directories are keyed by their listing.
- On x86_64 and arm64 Linux (glibc), `CargoReadRecorder` builds the same source with the first `cc` on `PATH` (`-shared -fPIC`, linking `-ldl -lpthread` for glibc before 2.34; the source refuses to compile before glibc 2.33, whose headers make `stat` an inline wrapper, which leaves recording off) and injects it with `LD_PRELOAD`. The library's file name hashes the glibc version, architecture and `cc` path too, so a shared or upgraded cache directory never reuses one built for other wrappers; a library that does not load into `/bin/sh` and log is never installed, since the loader only warns on stderr. Interposition is by symbol name: each wrapper reaches glibc through `dlsym(RTLD_NEXT)` (`dlvsym` for symbols such as `__xstat64` that newer glibc exports only in their old version, which rustc still calls). glibc's functions call each other internally, not through these symbols, so each entry point is wrapped on its own: `open`/`open64`/`openat`/`__open`/`__open_2` and friends, `creat`, `fopen`/`freopen`, `stat`/`lstat`/`fstatat` and their `64` and `__xstat` forms, `statx` (Rust's `metadata`), `access`/`faccessat`/`euidaccess`, `readlink`/`readlinkat`, `realpath`/`canonicalize_file_name` (both the path and what it resolves to) and the fortified `_chk` forms of these, `opendir`/`fdopendir`/`scandir`, `getenv`/`secure_getenv`, the whole `exec*` family (`execvp`/`execvpe` search `PATH` themselves), `posix_spawn`/`posix_spawnp` and glibc 2.39's `pidfd_spawn`/`pidfd_spawnp`, `system`/`popen` (as `/bin/sh` spawns), `connect` and the `mkstemp` family with its `64` forms. Tree walks (`nftw`, `ftw`, `fts_open`/`fts64_open`, `glob`), `scandirat`, `getdents64`/`getdirentries`, `open_by_handle_at`, `execveat`, `wordexp` (which expands variables and runs command substitutions inside glibc) and `syscall()` with a number that names a path or starts a process log `?`, so a run that uses them is not cached. Rust's `env::vars` reads `environ` without a function call: the recorder logs a whole-environment read when `strlen` measures an entry of the block the process started with. That covers the run's own program, rustc or the build script, which reads variables through `getenv`; shells, `make` and interpreters take theirs from `environ` directly, and glibc reads `LANG`, `TZ` or `POSIXLY_CORRECT` without `getenv`. So `CargoReadSet` keys the whole environment, minus volatile variables, of any Linux run in which a second program loaded the recorder: every link (`cc`, `collect2`, `ld`) and every build script that starts a program. Such entries hit only where the environment matches. The reentrancy count is static `__thread` storage in the initial-exec model, never a pthread key: jemalloc in rustc reads its settings through `secure_getenv` while initializing, and allocating the count there deadlocks it; `secure_getenv` raises it around glibc's internal `getenv`. Every recorded process logs its executable and the libraries it loaded (`dl_iterate_phdr`) when it starts and again when it seals its events, so the C library, CRT objects, the linker and libraries opened with `dlopen` (a linker plugin) are inputs; a library closed again before then is not seen, and `dlopen` is not wrapped because a wrapper would become the caller whose `RUNPATH` the loader searches. Unlike macOS, `cc`, `collect2`, `ld`, `ar` and the C compiler a build script starts all load the recorder, so links key their whole toolchain by what it read instead of `CargoToolchainIdentity.linker` (macOS only), nothing is allowed to run unrecorded, and only `git` and `uname` are modeled as queries (`CargoReadRecorder.modeledPrograms`). A process's own `/proc` directory (`self`, `thread-self` or its pid) names something else in every process, so its files are never keyed by path: the status files Rust's standard library and allocators read to size thread pools (`stat`, `status`, `cgroup`, `mountinfo`, `maps` and similar, `CargoReadSet.processStatus`) and a listing of `fd` are not inputs, `environ` keys the whole environment, and anything else there (`cwd/…`, `root/…`, `fd/3`) refuses the run. `/sys/fs/cgroup/` and `/sys/devices/system/cpu/` are not inputs either; other `/proc` and `/sys` files are, and their times keep such runs unstored. Not observed: statically linked programs, which have no loader to preload into (the run started them, logged no `P`, and is refused); system calls a dynamically linked program makes without libc (inline system-call instructions, io_uring); and the loader's own search, so a library that appears earlier in an `LD_LIBRARY_PATH` directory than the one a run loaded is not seen (the libraries it did load are keyed by content). Go binaries are usually static, so they fall in the first, refused, case. Without the hook server, build-script runs go through `tuist cargo __script`, whose `TUIST_DEBUG` lines Cargo keeps in the run's `stderr` file.
- `CargoBuildScript` caches build-script runs, like a Bazel action whose outputs are `OUT_DIR` and stdout. After compiling a `build_script_<stem>` crate (Cargo names it after the script's file stem, so `build = "build/main.rs"` gives `build_script_main`), it moves the binary to `*.tuist-real`, records its declared hash in `*.tuist-made-of` and installs a shell shim that runs `$TUIST_CARGO_SCRIPT cargo __script`. In a served session that is the hook client, which sends an `S` request so the outer process decides and stores the run (no Swift startup per script); otherwise it is `tuist cargo __script`. The runner records the run, stores the relocated `OUT_DIR`, stdout and stderr under `script-actions/`, and restores them only into an empty `OUT_DIR` when the recorded reads still match. Cargo's `rerun-if` handling stays authoritative for when a script runs.
- `CargoInputHasher` shares compiler/toolchain and immutable extern digests only inside the outer command's private session, publishing bounded identity/digest records atomically, and keeps the records it read or wrote in memory so hooks served by the same process skip the record files and their locks. A session served by the hook server keeps its records in memory only, seeded from the persistent toolchain records (tree records become file records too, since hooks look toolchain files up one by one), and writes no record files; a hook in another process (the fallback) hashes for itself. Source admission remains invocation-local. Batch toolchain memo reads without caching directory discovery or skipping per-file identity checks. Serialize toolchain tree hashing per session with an advisory file lock so concurrent compilers reuse one hasher's records instead of all hashing the toolchain at once; lock failure only loses that sharing. Recheck device/inode/size/mode and exact mtime/ctime on every use; coarse timestamps require rehashing and mutations during reads reject the entry. Missing/corrupt/unwritable session records fall back to hashing. The outer command resolves the toolchain and linker identities and hashes the toolchain files strict keys take into those records while Cargo is probed and units restore, before any hook starts; hooks still recheck every record's identity. The toolchain identity is also recorded under the sysroot compiler's absolute path, which build scripts name in `RUSTC`, and asks that compiler for `-vV` directly. With a pinned rustup toolchain its answers persist in the cache with what selects them (the name, the pinned toolchain and its directory, the program `PATH` finds) and the identity of the compiler that answered `-vV`; the linker identity's `xcrun` answers persist in the cache with the developer directory and the identities of its `clang`, `ld` and `SDKSettings.json`, unless `SDKROOT` or `TOOLCHAINS` select them. One `rustup show active-toolchain` names the toolchain directory Cargo is taken from. Source admission uses a complete bounded read and its exact digest in the key; do not independently read one source version for admission and another for hashing. Keep stat/streaming operations narrow because FileSystem does not expose this identity. Reject file/output symlinks, incomplete or oversized input sets; toolchain file links may resolve only within the toolchain. Inputs must remain stable through probing, compilation and reuse.
- Compiler dep-info must agree with the discovered source set before publication (the registry-leaf fast path requires package-local dependencies). Exclude volatile wrapper/session/jobserver settings only when dep-info proves they were not read. Never cache failed compiler executions. Ignore valid terminal-width arguments in keys. Publish and restore only empty stdout and stderr made of rustc's JSON messages (artifact notifications, diagnostics, future-incompatibility reports, and the unused-extern reports Cargo 1.100 requests with `--json=unused-externs-silent` for its `unused_dependencies` lint; a hit replays them so the lint still sees cached crates). Stored diagnostics carry a leading `tuist-diagnostic-width` marker with the width they were rendered at, and restore only at that width (a hit replays them, so Cargo still shows a cached crate's warnings); invalid/duplicate width arguments retain their original keys, in recorded keys too. Output without rendered diagnostics reads the same at every width and is stored under the key's entry, shared by terminal and piped builds; a future-incompatibility report holds rendered warnings and counts as diagnostics. Diagnostics rendered at a terminal width go to that width's own entry (the action's command adds `diagnostic-width=<n>`), so builds at different widths keep theirs instead of replacing one another's; a piped build's go to the key's entry, which a terminal build tries first and skips. A terminal build's miss therefore makes two lookups. An explicit empty project-write grant in the server-issued token is an advisory session-local read-only hint, refreshed with the token; skip known-denied remote publication without changing local caching or Kura's authoritative authorization. Unknown token formats still attempt uploads. Hits must not become compiler-observation rows.
- `CargoCompilationCache` uses the existing `TuistREAPI` transport with project-scoped SHA-256 Command/Action indexes and content blobs, never a new HTTP protocol. Verify every output digest and the complete expected output set, including bounded crate-prefixed split-debug objects, before materialization: blobs through the persistent identity memo (`<cache>/verified`) before they are cloned, as units are, and the fingerprint once more after staging, right before outputs move into place. Restored outputs' digests are recorded for the session, since their dependents key them next. Probe the complete local cache before constructing a remote transport. Kura's tenant/account header and REAPI project instance name are separate: `owner/project` becomes header `owner` plus instance `project`, never instance `owner/project`. Cache metadata calls use a one-second request timeout; large artifacts retain the shared transfer guards. A failed remote read disables publication for that compiler and opens a private session-scoped circuit so later compilers do not repeatedly wait on the same unavailable endpoint; a new Cargo command retries normally. Publish remote action results only after all referenced blobs exist. Corrupt, missing, unsupported, or unavailable entries fall back to compilation. Cache failures must not replace Cargo/compiler failures.
- `CargoFlight` keeps builds that share the cache (worktrees, agents, separate target directories) from compiling one key at once, like Kache's flights. After the local and remote misses, a compilation or build-script run takes an advisory `flock` on `flights/<key>` (the key, or for deferred, recorded and script runs, which learn theirs only from the compiler, the declared key that finds their inputs) and holds it until its result is stored locally or it fails; the kernel releases it when the holder dies. Whoever takes the flight, at once or after waiting, looks in the local store again before compiling: a peer may have stored and released the key after this build looked, and such a duplicate compilation can produce outputs that change every dependent's key. Waits are bounded (`CargoFlight.maximumWait`) and fall back to compiling, as does an unusable lock file. A release unlinks the file before unlocking, and a claim checks that its descriptor still names the path, so a waiter that locked the unlinked file never shares ownership. A waiter that finds nothing stored marks the key `.unstored` (an output the cache refuses, or aws-lc-sys's build script), and builds stop waiting for each other on it: otherwise every concurrent build runs such a key serially after its peer.
- `CargoClangInvocation` shares that storage through `CargoCacheAction` for individual native C compilations inside build scripts. Initial support is arm64 macOS with the default Apple `cc`, not C++, arbitrary compilers, or script execution; on Linux a build script's C compilations are recorded with its run instead. Preserve explicit compiler selection and pass through cc-rs probes/non-C actions. Install a stable project-cache wrapper path so cc-rs's environment tracking does not invalidate no-op builds; keep its compiler identity outside the `.xctoolchain` path to preserve cc-rs's flag generation. Keys include the fresh driver plan, complete expanded preprocessor output, discovered source/header contents, resolved SDK metadata, real compiler binary, OS build, arguments, cwd and environment. Repeat discovery before restoration and after successful compilation; rehash inputs before publication/materialization. Admit only parsed known flags, empty or identifier-only literal asm templates, and no config files, injected libraries/options, modules/PCH, plugins, external assemblers or auxiliary outputs. `cargo __native` uses the same early dispatch, failure fallback and bounded measurements as the Rust hook. Its tests are in `cli/Tests/Fixtures/CargoCache/native_e2e.py`; do not claim Linux, x86-64 or cross-worker qualification.
- Native version-3 keys re-resolve input symlinks at every fingerprint and include both the original path and resolved target path/content. This admits SDK header links without relaxing the output-symlink restriction. Remote native admission initially requires a source of at least 32 KiB as a cost heuristic: small cc-rs actions often compile faster than remote discovery/transfer. The stable shell wrapper bypasses those small inputs without starting Swift; failed size probes still use full admission. Preserve inherited shell options and explicit compiler selection. Local-only caching retains the full native admission above. The threshold is a cost heuristic, not a correctness condition or prediction of every compilation's cost. Reject unsupported Rust extern types before toolchain discovery. Keep the registry fast path's stricter source validation before permissive root validation: digest-bound admission memoization is not interchangeable between policies.
- Install native interception only through the stable `cc` PATH shim, never a higher-priority `CC_<target>` override. Preserve compiler selection performed later by build scripts and cc-rs. When executing the shim, remove its own directory from the current PATH and resolve the compiler again; preserve other PATH entries and bypass caching for non-Apple selections. Do not shadow cc-rs's separate `clang` selection.
- Hooks served by `CargoHookServer` use the session's REAPI connection directly. `CargoRemoteCache` shares it with hooks in other processes (the shell-wrapper fallback) through bounded atomic request/response files in a private command-session directory; the broker runs only when there is no hook server. Only transport is shared; each hook still owns admission, fingerprints, output verification and measurements. Reserve metadata lookups and cache-hit downloads separately from publication at request admission and execution. Wait cancellation-aware for local capacity before starting the remote-operation deadline; normal concurrency must not bypass hits or declare the endpoint unhealthy. Count server-owned lane reservations until backend execution and cancellation cleanup finish, even when clients remove their requests. Start the client's bounded response wait after server acceptance, with a separate local-delivery margin; pre-acceptance stalls and local materialization failures must not open the remote-failure circuit. Keep remote metadata waits short and transfer waits bounded. Cancel and await the server before deleting its session directory; unavailable transport must fall back to compilation. Standalone compiler hooks retain direct REAPI transport.
- Negotiate REAPI capabilities in the session relay alongside Cargo startup, including compression and split/splice support. Mark connection preparation separately from readiness so compiler hooks do not spend their metadata deadline waiting for negotiation. Cancel and await preparation when Cargo completes, including no-op builds. If creating the relay directory fails, keep children local-only rather than negotiating per compiler. Missing or corrupt entry blobs remain counted failures but do not open the endpoint circuit.
- `TUIST_CARGO_KEY_TRACE=<directory>` writes each strict key's relocated inputs as `<crate>-<key>.json`, and each recorded compilation's declared and recorded keys as `<crate>-declared-<key>.json` and `<crate>-recorded-<key>.json`, and each build-script run's key as `<build directory>-run-<key>.json`, like blaze's `BLAZE_KEY_TRACE`, so two builds' misses can be diffed.
- `CargoCacheVerification` is an opt-in canary for hits, like kache's `KACHE_VERIFY_INPUT_PREDICTIONS` and `KACHE_VERIFY`, off unless set. `TUIST_CARGO_VERIFY=sampled|always` checks a hit's inputs: a strict hit keyed by a remembered source list runs rustc for dep-info only and is still served when the sources agree; a recorded compilation or build-script run runs recorded and compares its reads with the read set that keyed it. `TUIST_CARGO_VERIFY_RECOMPILE=sampled|always` compiles hits and compares outputs with the stored entry (`ok`, `path-debug` for a Mach-O image's link-edit data only, `content`). Do not tolerate other path-like differences, as kache does: an output naming a machine root is bound to it by its key, so a correct hit differs in no path, and the tolerance hid changed dates, git refs and URLs. Incremental codegen is not reproducible (codegen units are named after the session), so when either side is incremental only `.rmeta` and `.d` are compared, and the finding says so. Blobs are read one at a time; entries can be gigabytes. `sampled` checks 1 in 64 units chosen by a digest of what names the unit (crate, types, package, cfgs, package-relative root source; the package and target for a run), never a counter, key or path, so the same units are checked on every build and in every checkout. A sampled hit that needs a compilation compiles in place instead of restoring, exactly as an uncached build would, so builds use fresh outputs. Verification never stores or replaces the checked unit's entry, but its dependents key its fresh outputs: when those differ by a byte, the dependents miss and are stored as in an uncached build. Findings print as `Tuist Cargo cache: verified <unit> <check>: <outcome>` under `TUIST_DEBUG`. Checked compilations count as `verifications` (task misses on the server); build-script runs write `verification` task records but no `verifications` count, because a restored run is never counted as a hit. Unkeyed reads, content differences and a failure the hit hid count as `divergences`; a run whose process never reported an exit (`CargoHookRun.abandon`) or whose output exceeds the cache's bound is reported as `failed`, never as divergent. Native C compilations are not verified, and Linux has no recorder, so there only strict source lists are checked. `cli/Tests/Fixtures/CargoCache/verify_e2e.sh` covers it.
- `CargoUnitCache` follows blaze v1's dependency units: around the outer Cargo command, it restores registry/git dependency units (their `deps` outputs, `build/<unit>` script runs and `.fingerprint/<unit>`) into the target profile before Cargo starts, and publishes them after a successful build, alongside the build report (`settle`; neither reads what the other does) once the hooks have drained. Units restored here skip rustc, build scripts and proc macros entirely, and are path-independent because Cargo's unit hashes and fingerprints contain no checkout path. Cargo stays the freshness authority: it rebuilds units whose fingerprints disagree, so the key (`rustc -vV`, profile, command kind, unit-selecting options, flag/profile environment and every discovered Cargo config file) only selects a manifest, it does not certify units. Like blaze's per-project list, the key leaves out `Cargo.lock`: a manifest accumulates units across lockfiles and feature sets (newest first, at most 4000), and restoration skips units whose registry package (`<name>-<version>`, from dep-info) the current lockfile lacks. A unit is a dependency only when every dep-info source is in Cargo home's registry/git checkouts (or the target directory); a build-script run additionally needs every compiled unit of its package to qualify. Paths into the checkout, the target directory or Cargo home in its output beyond its `OUT_DIR` (a `-sys` crate's registry `include` directory, another crate's `OUT_DIR`) and absolute `rerun-if-changed` paths inside those roots bind the unit to them, as for compiled outputs; absolute `rerun-if-changed` paths outside every root keep the run from being a unit. Publish only units created during this command, so stale leftovers of a local target never enter a manifest; units restored by this command that Cargo left untouched (same size and restoration time, no extra fingerprint files) keep their manifest records without being read again. Blobs are cloned into the store and hashed once; restoration and collection run on four threads (APFS serializes directory updates, so more threads multiply kernel time). Restoration `clonefile`s each blob straight into an absent destination and verifies the blob through a persistent identity memo (`<cache>/verified`, seeded when a blob is stored) rather than rehashing it. Blob use marks renew only when older than an hour, after verification, and the verified digest is recorded again under the blob's new ctime. A target without the profile directory is restored from a snapshot instead: the first file-by-file restoration of a selection into an absent profile clones the profile into `<cache>/snapshots/<selection digest>` (two kept) with every file's identity; later ones check those identities and `clonefile` the whole directory, renamed into place with `RENAME_EXCL`. Snapshot checks and the untouched-unit check read one `fts` walk with `lstat`, never Foundation's enumerator, which reads every entry's extended attributes. A served session records the digest of every restored file under its clone's identity while the file keeps its restoration time and size, so hooks do not hash externs and script outputs restoration just verified. A snapshot whose files changed, or that holds anything besides the selection's files and directories, is discarded and the build restores file by file; restoration recomputes the absent units under Cargo's lock and saves a snapshot only when it wrote every one of them, so a Cargo that built in the profile meanwhile keeps its units and they never enter a snapshot. The manifest also carries Cargo's `.rustc_info.json`, restored when absent so Cargo skips its rustc probes. A build whose manifest equals the one it restored from publishes nothing; reading a local manifest renews its use marks instead of rewriting it, as a per-crate hit does for its entry. Write outputs before fingerprints, share one modification time per restoration, verify every blob digest, and hold Cargo's `.cargo-lock` while restoring or collecting. Target-triple builds bypass it. Cargo 1.100's build-directory layout keeps a whole unit in `build/<package>/<hash>` (`fingerprint`, compiler outputs or a run's `OUT_DIR` in `out`, a run's records in `run`, with `stdout` where earlier versions wrote `output`) and no `deps`; units of both layouts are collected and restored, each judged by its own fingerprint directory, since one target directory can hold both. The earlier layout's `deps` holds tens of thousands of files: collection indexes it once by unit hash (`byUnitHash`), and a compilation lists its own outputs by name prefix with `readdir` (`CargoCacheInputs.entries`), not `FileManager`, once per publication. Failures fall back to an ordinary Cargo build. `cli/Tests/Fixtures/CargoCache/units_e2e.sh` covers moved checkouts, snapshots, other lockfiles, configuration misses and corrupt blobs.
- `CargoCacheMeasurement` emits version-1 bounded aggregate and public inspection records. Key timings measure actual index operations, not compilation, hashing, or artifact transfers. CAS timings describe the measured batch operation shared by its blobs; byte counts describe uncompressed content. Transfers are observed, not inferred from task hits. The shared client distinguishes blobs actually uploaded from objects already present. No predictions or estimated savings are implemented.
- `CargoCacheJournal` follows blaze: no build waits for the network. Hooks append the cache-relative index files they use (`actions/`, `script-actions/`, `reads/`) to `$TUIST_CARGO_SESSION/cache-used`; the outer command records them, capped, in the unit manifest. The next build fetches that manifest as soon as its key is known (the remote connection is negotiated while Cargo is probed) and downloads the listed index files and their outputs in parallel while units restore and Cargo runs, skipping entries whose outputs a restored unit already carries. With a remote, the outer command sets `TUIST_CARGO_WRITE_BEHIND=1`: hooks write publications under the session instead of uploading, and the outer command uploads their blobs in one batch and then their action results after Cargo exits, including when the build fails. A hook that cannot record a publication uploads it itself. Prefetch only warms the local store; every entry is still verified as on any other lookup.
- Keep `CargoCacheReport` and `CargoCacheDetailsReport` bounded by file count, bytes, records, keys, and wire size. They read records with `JSONSerialization`: `JSONDecoder`'s first decodes cost more than a warm build's few records. Every hooked compilation writes one report file and one inspection file, so both readers accept up to 4096 files within their 8 MB budgets; a smaller inspection file cap would truncate ordinary builds. Mark details truncated only when a bound actually drops records, including when the aggregate scan is cut short. Never collect arbitrary compiler arguments, environment values, or credentials in telemetry, or infer local/remote hit provenance. Historical server payload fields remain compatible, but unsupported counters stay zero.

## Cargo and nextest semantics
- Build metadata reuses `custom_metadata`, `TUIST_BUILD_TAGS` and `TUIST_BUILD_VALUE_*`; explicit values override allowlisted live-wrapper observations. Because older Cargo receivers had no metadata field, omit the entire field until credential-free discovery advertises expanded support (greater than 20), even for small maps. Runner names require opt-in. See `server/docs/build-metadata.md`.

- Project, server, and network configuration comes from `tuist.toml` or, when there is none, the root manifest's `[workspace.metadata.tuist]` (or a workspace-less package's `[package.metadata.tuist]`), plus environment overrides, even in checkouts with `Tuist.swift`. Cargo ignores `metadata` tables without warning; a top-level table would warn on every Cargo command. The manifest Tuist reads is the nearest ancestor `Cargo.toml` with `[workspace]`, as Cargo resolves it, never a member's. Use `ConfigLoader.loadCargoConfig`; do not extend ProjectDescription for Cargo settings.
- Dispatch Cargo before generic flag stripping and command analytics. Preserve Cargo's quiet/verbose flags, output, argument order, failures, and signals. Nested Cargo commands must not recursively decorate a session.
- Compiler observers record actual executions only. Preserve existing global compiler wrappers without interpreting their results as compiler executions; they bypass Tuist caching/observation. Leave custom workspace wrappers authoritative.
- Inherit terminal stdio for the primary command, except standard plain-Cargo test reporting, which tees bounded stdout/stderr through `CommandRunner.runWithOutputHandler` (synchronous, backpressured readers, no stderr collector) (stdin and foreground process group remain inherited; automatic color detection can differ). Nonexecuting, quiet, Cargo-verbose (`-v`/`-vv`/`--verbose` or `CARGO_TERM_VERBOSE`), alternate-format, and uncaptured-output test commands retain inherited stdio; `CARGO_TERM_QUIET` also bypasses observation. Pin rustup's default toolchain before Cargo changes directories. Forward nightly `-C` without observation; sharding rejects it rather than executing an unfiltered suite.
- `CargoTestService` observes explicit `test`/`t` invocations without adding harness flags, nightly requirements, or nextest. `CargoTestReport` aligns independent stdout sections and stderr headings after execution, validates summary counts/statuses, and uniquely attributes binaries through package-relative Cargo metadata paths and explicit package selections. When packages share a target's name and package-relative source (`tests/tests.rs` as `integration`), the binary's package decides: `build/<package>/<hash>/out` since Cargo 1.100, `.fingerprint/<package>-<hash>` before. A doctest section belongs to the package holding its tests' files, which Cargo names relative to the workspace root; alignments that differ only in where empty sections go count as one. Count summary outcomes in a single pass and explicitly unwrap decimal totals with `Int(..., radix: 10)` before comparing them. FileSystem's `INCITS_4_1986` adds throwing unlabeled string initializers for `Int`/`Int64`/`UInt`/`UInt64`; Swift 6.2 (Linux CI) prefers these in comparisons, unlike Xcode's Swift 6.3. Removing `filter` alone does not fix the overload resolution. Integration-test identities match nextest's `<package>::<target>` IDs; never prefer a cwd-relative path over a sibling package. Reject unresolved package selections rather than widening them: `--no-deps` metadata omits non-member dependencies that `cargo test -p` can execute. Combined workspace/package selections must retain all workspace candidates. Omit absolute doctest names so checkout paths never become identities. Edition-2024 merged doctest sections belong to one `<package>::doctest/<library>` module, disjoint from nextest integration IDs such as `<package>::doc`. If descendants retain pipes beyond the post-exit drain window, discard the capture without waiting for them. Unknown/custom harnesses, incomplete or ambiguous reports, and exceeded capture/parser limits produce no test report, never invented passing cases. Only suite elapsed times are measured: case and namespace durations use the shared contract's zero fallback, without concurrency calibration, retries, or enumeration. The `cargo test`/`cargo test · <label>` scheme is the server's untimed-case signal: exclude those case timings from rolling histories and aggregate duration analytics, but retain outcomes and measured zero timings from other runners. Escape nextest labels that collide with the reserved untimed schemes using the `cargo nextest run · ` prefix; preserve ordinary labels. Self-hosted servers need this feature's migration and ingestion changes before upgrading the CLI. Preserve Cargo failures even when collection/reporting fails. `cli/Tests/Fixtures/CargoTestReporting/AGENTS.md` covers the real stable Cargo fixture.
- Plain `test`/`t` build reports use the latest provisional `Finished ... profile ... target(s) in ...` stderr timestamp, confirmed by the subsequent `Running`/`Doc-tests` heading, or by successful command completion with complete empty stdout for packages without runnable tests. A completion line alone is not proof of successful outer compilation: Cargo can dump nested Cargo output after a build-script failure. Stop scanning at `--- stdout`/`--- stderr` transcript boundaries, and stop at the first runtime heading so later harness output cannot become a build boundary. Retain the confirmed timestamp independently of bounded test output so failed tests, oversized capture, or inherited-pipe drain timeouts do not discard it. Exclude compiler rows ending beyond the measured build window, allowing one millisecond for independent rounding, so nested compilations inside tests do not leak into the outer build timeline. If both the boundary and a parsed test report are absent, a failed command with an observed failed compiler invocation can produce a failed build only while the scanner remains in the compile phase, with complete bounded capture and empty stdout. Discarded capture, oversized stderr lines, runtime headings, or test stdout must not turn nested compiler failures into outer build failures. Never infer a failed build from task cancellation. Otherwise omit unmeasured builds instead of guessing from the command exit or successful compiler rows, and explain missing measurements when `TUIST_DEBUG=1`. Executing tests with inherited-stdio reporting bypasses (including list, quiet, verbose, alternate-format and uncaptured-output modes) omit build reports too. `test --no-run` remains a build-only report. Start the shared command/compiler-observation clock after cache setup, and freeze command completion before metadata collection or upload.
- Nextest enumeration is not execution. Never report tests omitted by fail-fast as passing. Nextest commands do not submit build reports because their wall time includes tests; `test-build` reports the compile-once/archive phase.
- Stable identities use nextest binary IDs and Rust namespaces, not artifact hashes or checkout paths.
- Nextest binaries are concurrent module-level units, not Xcode suite-level units. Declare `concurrent_modules` and reuse the shared measured-concurrency planner with a longest-binary floor. Binary/suite timings use complete attempt timestamp windows, including retry delays and ignoring skips. Omit concurrency evidence when timestamps or wall time are missing; never infer utilization from CPU count or thread limits.
- Analytics failures must not change Cargo's exit status. Planning/downloading failures must fail a shard rather than execute the entire suite.
- Plain Cargo selection always executes through Cargo, preserving target runners and doctest environments. Muting keeps the original package selection and adds `--no-fail-fast` only when absent. Sharding and skip quarantine require one selected package: narrowing a multi-package command changes Cargo's unified dependency features. Resolve workspace default members and the current manifest before validating only selected harnesses, including library/bin targets selected by `--benches`; reject target-name patterns before enumeration. Keep package/target/test-filter intersections exact, report empty assignments without executing tests, and reject ambiguous inventories, custom harnesses and incompatible plans. Only exit 101 with complete parsed failures all quarantined and bounded ordinary-termination diagnostics may be muted; inspect Cargo stderr and Rustdoc stdout for abnormal termination. Compilation failures, signals and incomplete captures remain failures. Quarantine lookup failures warn and run without quarantine. `TUIST_TEST_SKIP_QUARANTINE` disables enforcement. Rustdoc splits test arguments on whitespace, so doctest exclusions must be proven not to filter enabled examples or fail explicitly, including partial exclusions with `--exact`. `CargoTestReporting/e2e.rb` checks the public CLI with real stable Cargo and a loopback API receiver.
- Repeatable archive upload/download, exactly-once shard execution, merged reports, and fail-closed checks live in `cli/Tests/Fixtures/CargoSharding/AGENTS.md`.
- Keep docs aligned with the deliberately narrow experimental cache. Do not claim parity with a general compiler cache, undeclared-input sandboxing, cross-worker qualification, or selective testing. Plain Cargo sharding builds on each worker; it does not distribute compiled test products.
- Code coverage (`CargoCoverage`, contract in `server/docs/code-coverage.md#cargo`) is opt-in: `[test_insights.coverage] upload = true` in that configuration, which `TUIST_COVERAGE_UPLOAD` overrides. Every test run sends `coverage_enabled`. With the compiler hook in the chain, the hook instruments only repository libraries, binaries and test harnesses (not build scripts or proc macros) before keying them, so dependencies keep plain keys; nothing coverage sets (the runner variable, `LLVM_PROFILE_FILE`, `TUIST_*`) may reach compile or unit-cache keys. Cargo cannot see that flag, so before Cargo starts `CargoCoverage.reconcile` swaps the other variant's units (identified by `.tuist-coverage` markers beside their outputs) into the profile's `.tuist-coverage` directory together with their fingerprint directories, and moves the wanted variant back; a unit always moves with its fingerprint, so Cargo, not Tuist, decides whether a restored variant is fresh. Without the hook (a custom `rustc-wrapper`) coverage falls back to `build.rustflags`. Attribution needs every test process to start through the stable runner in the cache directory, which chains an environment runner and stands down for a configured `target.*.runner`. Nextest's wrapper scripts are experimental, so don't use them. macOS profiles carry no binary IDs, so a process's recorded arguments, not its profile, say which binary and test it was. Nextest processes yield `test` and `target` evidence; plain `cargo test` processes yield `target` evidence and `overlapped_tests`; doctests yield none. Only the caller's arguments narrow a run (`only_test_identifiers`); a shard's share and quarantine never do, and a fail-fast failure makes it partial. A shard's archive is extracted into the session so `llvm-cov` can read it after the run. Its coverage maps name sources in the checkout that built the archive, so `NextestInventory.sourceRemaps` maps each path package's build root (`package-id`) to its worker root (`cwd`) before resolving; without it a CI worker uploads no files. Profiles of processes no runner started go to the session, never the working directory: a stray `default_*.profraw` litters it, though only changed tracked files make a run dirty (its coverage never counts). `coverage-complete` is a Tuist subcommand because the Linux CLI has no `tuist coverage`. `cli/Tests/Fixtures/CargoCoverage/AGENTS.md` covers the real-toolchain checks.
