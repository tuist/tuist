# TuistGenerator (Project Generation)

This module implements the project generation pipeline (transforming manifests into Xcode projects/workspaces).

## Responsibilities
- Build descriptors (`ProjectDescriptor`, `WorkspaceDescriptor`, `SchemeDescriptor`) used to write `.xcodeproj`.
- Orchestrate side effects required for generation (e.g., writing schemes, side-effect descriptors).
- Translate `ProjectDescription`/graph models into `XcodeProj` structures.

## Related Context
- Core domain models: `cli/Sources/TuistCore/AGENTS.md`
- Manifest loading: `cli/Sources/TuistLoader/AGENTS.md`

## Invariants
- `ProjectDescriptor`/`WorkspaceDescriptor` are the handoff types to XcodeProj writers.
- Side effects are collected explicitly and executed outside pure mapping.
- Both `.pbxproj` and `.xcproj` writers serialize with stable references and compare bytes before rewriting unchanged project bodies. Switching formats removes the stale body file; project side effects run after references are finalized.
- Compiler-cache debugging runs through the native scheme mapper for both project and workspace Run/Test actions, including autogenerated schemes. Keep explicit debugger settings and disabled debugger attachment intact. When no custom initializer exists, load `~/.lldbinit-Xcode` falling back to `~/.lldbinit` before writing Tuist's source map; never source both home files. Home files load through LLDB's command-file API without echoing commands or stopping on errors, but with diagnostics visible. Read reverse prefix mappings from the selected action's `TARGET_TEMP_DIR/compilation-prefix-map.json`. Do not shell-parse exported mapping settings: Xcode expands path variables after tokenizing lists, so quotes and backslashes introduced by expansion are literal path characters. Write the source map with `settings set`, ahead of an action's explicit custom initializer: Xcode keeps one LLDB process across runs and sources the initializer into its global settings, so appending leaves earlier runs' maps, including other checkouts', ahead of the current ones. This replaces home-file source maps while preserving other home settings; source-map entries meant to survive belong in the scheme's custom initializer, which is sourced afterwards and can extend or override the map. Resolve the source map into a temporary file before writing the initializer, so a prefix map that cannot be read still leaves the user initializer sourced. Order the entries the way the compilers resolve prefixes (most specific directory first and, for the same directory, the mapping Xcode passes last), because LLDB maps a breakpoint's path back through the first entry that contains it. Whenever compilation caching is enabled, also point LLDB at the cache (`symbols.cas-path` under `COMPILATION_CACHE_CAS_PATH`, and `symbols.cas-plugin-path` only for the plugin CAS): Xcode does not, and without it LLDB cannot load the modules that cached compilations reference by CAS ID, so expressions fail. Xcode does not export the default `COMPILATION_CACHE_CAS_PATH` to scheme actions, so fall back to `DERIVED_DATA_DIR/CompilationCache.noindex` (the DerivedData root, above the project's directory) and only then to the directory above `BUILD_DIR`, which is where `-derivedDataPath` builds keep it. A wrong `symbols.cas-path` is worse than none: LLDB finds the builtin CAS at the default location by itself, and a path that does not exist breaks that.
- Preserve `Derived/TuistCacheDebugging` during project cleanup: another workspace sharing the project may still reference those per-scheme files. Each action refreshes its own initializer before debugging.
- Preserve real directories for generated sources, Info.plists, and entitlements during early Derived cleanup so unchanged files retain their mtimes. Unlink directory symlinks, including dangling links, before writing generated files; never clean through a symlink root. After their generating mappers run, describe stale-file cleanup from the mapped targets; execution removes only obsolete Tuist-owned files and compares active paths using the volume's case-sensitivity.
- Targets with buildable folders exclude `.gitkeep` and `.DS_Store` through Xcode build settings, preserving existing exclusions. Xcode enumerates synchronized folders independently of Tuist's filtered globs, including files added after generation.
- When modules need companion resource bundles, catalogs discovered in buildable folders retain synchronized membership in both targets. swift-build moves source-generating Resources entries into Sources for asset/string symbol generation when enabled; `PACKAGE_RESOURCE_BUNDLE_NAME` suppresses main-target catalog compilation. Swift string extraction is independently gated by `SWIFT_EMIT_LOC_STRINGS`, not catalog membership or `PACKAGE_RESOURCE_TARGET_KIND`. Do not promote discovered catalogs to extra references. Explicit catalog sources/resources take precedence: exclude their implicit membership on the corresponding target rather than dropping explicit tags, platform conditions, or compiler flags.
- Explicitly dynamic native package products remain linked by hosted tests, independently of embedding. Tuist omits a test's explicit embed when the host embeds that product under the same platform condition; Xcode may synthesize automatic-product embedding separately. Static targets still receive build-only dependencies.
- With `enableCaching` on Xcode 27+, `XcodeCachePrefixMappingWorkspaceMapper` gives every project `SWIFT_OTHER_PREFIX_MAPPINGS`/`CLANG_OTHER_PREFIX_MAPPINGS` for the SwiftPM scratch directory (`/^spm`), build directories (`/^intermediates`, `/^products`), and the Tuist root directory (`/^root`, located from the workspace path like the scratch directory, so a workspace generated below the root still keeps `Tuist/.build` relative). `XcodeCacheSettingsProjectMapper` leaves `SWIFT/CLANG_ENABLE_PROJECT_PREFIX_MAPPING` off unless a project sets them: their `/^src`, `/^derived`, `/^built`, and `/^workspace` name a different directory in every project, and the debugger's single source map resolves them against the debugged target's project only. The workspace-wide mappings cover the same directories; a project outside the located root keeps relocatable cache keys only by turning the per-project mappings on. An external package's `PROJECT_DIR` is `tuist-derived/Projects/<name>` while its sources stay in `checkouts/`. The root directory goes in `TUIST_PREFIX_MAPPING_ROOT_DIR` and each mapping is a quoted `"$(TUIST_PREFIX_MAPPING_ROOT_DIR)/…=/^…"` token: Xcode splits unquoted list elements at spaces, so expanded paths must be absolute and normalized. Compilation-cache scanners sort nested prefixes ahead of their parents; declaration order is not what picks the winning mapping.
- Targets of `Project.packages` don't read project settings: Xcode 27 passes only `SWIFT_ENABLE_COMPILE_CACHE` down to them. Environment variables reach them only for settings without a spec default, and `-xcconfig`, `XCODE_XCCONFIG_FILE` and command-line overrides reach every target. When a workspace has such packages, the mapper adds `"$(TUIST_SOURCE_PACKAGES_DIR:standardizepath)=/^packages"` (`$(INDEX_DATA_STORE_DIR)/../../SourcePackages`, which unlike `OBJROOT` stays put in archives) to the shared mappings and writes them to `XcodeCachePackagesXCConfig` inside the `.xcworkspace`, with `$(inherited)` lists and `*_ENABLE_PREFIX_MAPPING = $(inherited:default=<coverage gating>)`, so the file is a no-op for generated targets. With the CAS plugin, it also carries the plugin settings copied from the projects as `$(inherited:default=…)` (they have no spec default, so any value set below the xcconfig wins), and the `tuist-instance`/`tuist-upload` options in `TUIST_PACKAGE_CAS_PLUGIN_FLAGS_$(TUIST_GENERATED_PROJECT)`, which the mapper sets to `YES` in generated projects so only package targets resolve the flags. Don't key that on `COMPILATION_CACHE_ENABLE_CACHING`: its default comes from Xcode's `COMPILATION_CACHE_ENABLE_CACHING_DEFAULT`. It removes the file otherwise. Don't pass a quoted list through `:default=`: the quotes become literal characters.
- Coverage builds disable prefix mapping by default for `xccov` compatibility. `enableCoveragePrefixMapping` keeps the mappings enabled only for teams explicitly remapping coverage themselves; do not switch Tuist's coverage reader implicitly.
