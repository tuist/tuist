# TuistHTTP

Shared file transfers, middleware, and authentication helpers for API clients.

- File transfers treat non-2xx responses as fatal errors.
- `FileClient.download` writes to `<destination>.partial`, and a later call on the same client for the same URL and destination resumes from the bytes a failed attempt kept (`Range` plus `If-Range` with the first response's strong `ETag` or `Last-Modified`), so wrap it in the retry loop rather than recreating the client per attempt. A 200, a 416 or a 206 whose `Content-Range` start or validator does not match restarts from zero; keep the 206 validator comparison, because Tigris ignores `If-Range` and answers 206 for a changed object; responses without a validator, or decoded through a `Content-Encoding`, are never resumed.
- `FileClient.downloadInParallel` (shard artifacts) probes the first range for the object's size and validator, then fetches the rest as up to eight concurrent ranges, each on its own `tuistLargeTransfer(lane:)` session so HTTP/2 hosts cannot multiplex them onto one connection. A retry on the same client asks each range only for its missing bytes. Every 206 must start where asked and carry the probed validator; anything else (a 200, a 416, a changed object) falls back to `download`.
- `FileClient.downloadInOrder` streams an object's bytes in order for consumers that process them as they arrive (the shard's shared artifact extracts while it downloads). It uses the same ranges, lanes, and validator checks, fetches at most eight ranges ahead of the consumer, and retries each range on its own. It has no fallback of its own: when the first range is not a validated 206 it fails with `OrderedDownloadError.rangesNotServed` before yielding anything, so the caller can switch to `downloadInParallel`.
- Default URL session uses explicit request/resource timeouts.
- Apple session factories always install the twelve-key SPKI deny policy after native trust/hostname evaluation. Filter blocked custom anchors and inspect the entire evaluated chain, preserving unrelated system/private roots. Direct Foundation callers use `tuistDefault` or `tuist(configuration:)`; never fall back to an unprotected session. Linux FoundationNetworking requires separate qualification. Local wire tests use OpenSSL 3 without changing host trust; public controls require `TEST_RUNNER_TUIST_TRUST_LIVE=1`.
- Every Tuist session closes a connection idle for 10 seconds (Darwin `_connectionCachePurgeTimeout`, set only when the configuration responds to its setter), below the server's 15-second keep-alive idle timeout, so a request is not written on a connection the server is closing. FoundationNetworking (Linux) exposes no idle timeout, so Linux sessions keep libcurl's connection reuse.
- `URLSession.tuistDiscovery` creates an isolated session honoring runtime proxy/private-CA settings, with 10-second request/resource limits, no cookies or credential storage, and no redirects (including with a custom CA).
- `TuistURLSessionTransport` materializes the whole response body before returning, so every body a client middleware receives is re-iterable and a failed transfer is replayed from the start rather than resumed. The exception is `streaming: true` (`Client.authenticated(serverURL:streaming:)`), for long-lived responses such as sandbox log streams: the body arrives line by line, can be read once, and uses its own session with a one-hour resource timeout; callers resume such streams themselves.
- [Hypertext Transfer Protocol (HTTP)](https://developer.mozilla.org/en-US/docs/Web/HTTP) retry behavior uses one shared policy with environment-configurable retry count and base delay, with bounded attempts and per-attempt delay. `RetryMiddleware` defaults to five attempts over about three to four seconds so a server rollout is ridden out; `RetryProvider` wrappers keep their own shorter defaults so the two layers do not multiply into a long wait.
- `RetryMiddleware` replays GET/HEAD and caller-listed idempotent operation IDs after any transport error or 408/429/5xx. Any other request is replayed only when the server never processed it: a connection that could not be established, or 429/503. A `CredentialAcquisitionError` from an authentication middleware is never replayed and its underlying error is rethrown: each refresh path retries itself, so replaying the request would multiply the refreshes sent.
- A numeric `Retry-After` longer than the remaining retries can wait (each waits at most 30 seconds) returns the response at once, including on unforwarded cache-activation retries. Do not lower the cutoff to a single retry's delay: current servers send quota hints, such as 60 seconds for report publishing, that the remaining retries ride out.
- `HTTPRetryPolicy.isRetryable` is the shared classifier for wrapped retries: errors without a status are retryable except a cancelled `URLError`, and `HTTPStatusCodeError`s follow their own `isRetryable`. `HTTPRetryPolicy.run` applies it to transfers outside the server client, and `FileClient` downloads surface non-2xx responses as status-carrying errors so they classify. Cancellation is never retried.
- Default proxy mode comes from runtime HTTP settings, and the shared session is resolved lazily, reused process-wide, and invalidated when those runtime settings change.
- Cache integrations may opt into replaying re-iterable uploads only after an explicit pre-forwarding activation rejection. Do not retry ordinary upload failures or transport errors through that exception.
