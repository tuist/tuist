# TuistXCResultService (CLI Module)

This module provides XCResult handling helpers for test results.

## Responsibilities
- Model test results (`TestCase`, `TestModule`, `TestStatus`) and failures.
- Provide structures to parse and surface xcresult data.
- Read the bundle's `xccov` line coverage on its own (`coveredFilePaths` / `parseCoverage`), separately from `parse`, so callers that only need test results (the stress gate, selective-testing target names) never spawn `xccov`. Coverage is processed where the bundle is processed: in remote mode the upload boundary writes an `XcodeCoverageManifest` (checkout root spellings, the covered files' Git blob ids, partial-run flag) into the bundle and the server's macOS processor reads the coverage; in local mode the client reads it with the same shared parser, streamed to a file of one JSON object per source file (`parseCoverage(path:manifest:into:)`, memory flat in the bundle's size), then `TuistKit.CoverageUploadService` DEFLATE-compresses it and either sends it inline with the run (up to the server's `inline_threshold_bytes`, from `GET .../tests/coverage/settings`) or PUTs it to a signed URL from `POST .../tests/coverage/uploads` under a client-chosen run id and references it with `xcode_coverage_storage_key`. The manifest is only built when the `COVERAGE` client feature flag is on (`TUIST_FEATURE_FLAG_COVERAGE=1`, early access), the bundle has coverage and the upload is on (`Tuist.swift` `testInsights: .testInsights(coverage: .coverage(upload:))`, overridden by `TUIST_COVERAGE_UPLOAD`). A coverage read failure is reported as a warning and dropped: coverage only enriches a run.

## Invariants
- Test results track status, duration, and structured failures for reporting.
- The parsers live in the shared `XCResultParser` package under `server/native/xcresult_nif`, so the CLI and the server's xcresult processor read bundles the same way.
- `TestExecutionModes` (shared package) records whether a run executed its tests in parallel or serially, per target: `TuistKit.TestExecutionModeResolver` resolves it from `-parallel-testing-enabled` and the xctestrun's `ParallelizationEnabled` (from `-xctestrun`, `-testProductsPath` or the derived data's build products) and writes `tuist_execution_modes.json` into the result bundle before the upload; the shared parser applies the file to the summary (`applying(executionModes:)`, run and per module), so the local-mode payload and the server's processor record the same `execution_mode`. Without an xctestrun or the flag nothing is guessed.
- Coverage carry-forward learns what a run skipped from the run's `skip_test_identifiers` (the caller's and quarantine's skips) and the selective-testing hits on its command event, and takes each skipped target's tests from earlier runs on the server. The client runs no extra xcodebuild pass to list a run's tests.
- `TestCoverageEvidence` (shared package) is which files each test executed. The test targets link the TestCoverageAttribution package (https://github.com/tuist/TestCoverageAttribution: XCTest observed once the bundle loads, Swift Testing through its `.coverageAttribution` trait), which records the coverage counters each test moves; nothing is injected into the test hosts. With `TUIST_COVERAGE_EVIDENCE=1`, `TuistKit.TestCoverageEvidenceService` tells the test processes where to write (`TEST_RUNNER_TEST_COVERAGE_ATTRIBUTION_DIR`, through `XcodeBuildEnvironment.additionalVariables`, task-local, merged into xcodebuild's environment; macOS and the iOS simulator only, since a device cannot write to the Mac), and right after the run, before a stress pass replaces the profile, reduces what it wrote: counters to functions (`CoverageObserverOutput`, from `__llvm_prf_data`/`__llvm_prf_names`; the reader expects TestCoverageAttribution's record version 1, counter indices plus how much each moved), functions to files (`xcrun llvm-cov export -format=lcov` over each instrumented image with the derived data's newest `Coverage.profdata`, streamed, only `SF:`/`FN:`/`DA:` kept). Lines come from the counter deltas: `CoverageMapping` decodes the image's `__llvm_covmap`/`__llvm_covfun`, and `VerifiedCoverageMapping` trusts it only for the files whose executable and covered lines, computed from the profile, match the `DA:` lines `llvm-cov` reported; those files give each scope `lines` (flattened inclusive ranges), the rest keep file-level evidence. A test's scope is the union of its attributable records, a suite's is what ran in the gaps around its tests, a target's is everything its processes executed; the tests left with no scope because every record of theirs overlapped another go up as `overlapped_tests` (module, suite, name). The evidence carries a `status`: `collected` when scopes came out, `not_linked` when no test process made its output directory (no test target links TestCoverageAttribution), `failed` when processes made one but none holds an image table (the package removes its output when recording fails), there is no `Coverage.profdata`, reading the output throws, or the reduction yields no scopes. The result goes into the bundle as `tuist_test_coverage_evidence.json` with the compiler's paths; whoever parses the bundle ties them to the repository with the coverage manifest (`inRepository(manifest:)`: the client in `uploadTestSummary`, the parser when the manifest is in the bundle), and the run reports it as `coverage_evidence`.
- Everything the client does for coverage and test selection is behind the `COVERAGE` client flag (`TUIST_FEATURE_FLAG_COVERAGE=1`, `ClientFeatureFlags.contains("COVERAGE")`): the coverage manifest and upload, the Git history, the build sources, the execution modes, the coverage evidence (which also needs `TUIST_COVERAGE_EVIDENCE=1`) and `tuist coverage complete`. Without it a run is exactly what it was before the feature existed: no sidecar is written, no extra xcodebuild invocation runs, nothing is injected. New client work for the feature goes behind the same flag.
