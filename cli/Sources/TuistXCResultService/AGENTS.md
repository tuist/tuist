# TuistXCResultService (CLI Module)

This module provides XCResult handling helpers for test results.

## Responsibilities
- Model test results (`TestCase`, `TestModule`, `TestStatus`) and failures.
- Provide structures to parse and surface xcresult data.
- Read the bundle's `xccov` coverage on its own (`coveredFilePaths` / `coverageTargets` / `parseCoverage`), separately from `parse`, so callers that only need test results (the stress gate, selective-testing target names) never spawn `xccov`. The run's coverage is measured on the client by `TuistKit.CoverageExportService` right after the test action (before a stress pass replaces the derived data's profile), on every path that runs tests: `tuist test` on a scheme, `tuist test --without-building` on a shard or an `.xctestproducts` bundle (`TestService.runCollectingCoverage`; the export and the evidence read the profile under the job's `-derivedDataPath`, from `--derived-data-path` or after `--`: without one, xcodebuild writes it to a `DerivedData/<container>-<hash>` folder whose hash follows the bundle's location, a fresh temporary directory for a shard, so the run falls back to the bundle's report), and `tuist xcodebuild test` (`XcodeBuildTestCommandService.runCollectingCoverage`): the targets, their products and which target compiled each file come from the project graph when the run has one (`tuist test`: `CoverageBuildTargets` lists the tested schemes' closure from the graph as it was before the binary cache replaced any target, with each target's product name, test flag and sources, and for a replaced target the slices of the xcframework the generated project links; `CoverageBuildSourcesService.record` keeps them in `RunMetadataStorage.coverageBuildSources` and `write` carries them into the `.xctestproducts` bundle; at export, `CoverageExportService.targets` finds each product in the products directory the run's bundles are in (the derived data's `Build/Products/<configuration>`, or an `.xctestproducts` bundle's `Binaries/<n>/<configuration>`), or the xcframework slice of that directory's platform) and from `xccov view --report --json` otherwise (`tuist xcodebuild test`, `coverageTargets`), which lists only the targets the action built, never a cached one; and `xcrun llvm-cov export -format=lcov` over every Mach-O product with the newest `Build/ProfileData/*/Coverage.profdata` gives the lines, counts and functions (`xccov` reports only the targets the action built, so code from the binary cache or compiled with a coverage prefix map is missing from its report, while the images' coverage mappings carry it). Static products are archives `llvm-cov` cannot read; their code sits in the images that link them. Function names are demangled with `swift-demangle -compact -simplified` (xccov's `Type.method(label:)` shape) and a function's executable and covered lines are counted within the span its product's coverage mapping gives it (`CoverageMapping`, read from the image or from each object in a static archive; nested closures included, as xccov counts), or until the next function starts without one; covered lines are read off the file's own line counts, the way the server recomputes them when merging shards, so a line inside a closure that never ran is uncovered for the enclosing function too, where xccov counted it covered. Products `llvm-cov` finds no coverage data in (built without instrumentation) report no files, as with xccov; archives and universal images are read for the host's architecture (`-arch`). Paths the compiler recorded under an alias are mapped back before anything is tied: `/TUIST_SOURCE_ROOT` (`XcodeCoverageManifest.sourceRootPlaceholder`, what a binary built for the cache records with `-coverage-prefix-map <checkout>=/TUIST_SOURCE_ROOT`) is one of every manifest's root spellings (`UploadResultBundleService.rootSpellings`), so relativizing handles it for the coverage and for the evidence; Xcode's own prefix mapping (`/^src/…`, under `enableCoveragePrefixMapping`) is reversed by `CompilationPrefixMaps` through each target's `compilation-prefix-map.json` under the derived data's intermediates (the product's own target first, then the first map whose result exists); a test job that tests products built elsewhere has no intermediates, so `CoverageBuildSourcesService.write` copies the build's maps into the `.xctestproducts` bundle's `tuist_coverage_build.json` (`CoverageBuildSources.prefixMaps`, which also reaches shards through the shared archive), and those win over the derived data's, so an opted-in project keeps cross-checkout compilation-cache reuse and its coverage still reaches Tuist, while `xccov` and Xcode's coverage UI still see the mapped paths. The coverage evidence goes through the same maps (`TestCoverageEvidenceService` remaps each image's `llvm-cov` report and its decoded mapping before verifying and tying them), so test and suite scopes survive mapping too. The export goes into the bundle as `tuist_coverage_export.ndjson` (one `XcodeCoverageFile` per line with the compiler's paths); at upload the client ties it to the repository with the `XcodeCoverageManifest` (checkout root spellings, the covered files' Git blob ids, partial-run flag: `CoverageExport.tie`), then `TuistKit.CoverageUploadService` DEFLATE-compresses it and either sends it inline with the run (up to the server's `inline_threshold_bytes`, from `GET .../tests/coverage/settings`) or PUTs it to a signed URL from `POST .../tests/coverage/uploads` under the run's id and references it with `coverage.storage_key`. The run carries it as the build-system-neutral `coverage` block with `tool` `llvm-cov` and the Xcode version as `tool_version`, in both processing modes: in remote mode the manifest written into the bundle says `client_reported`, so the server's macOS processor ties only the coverage evidence against it and leaves the bundle's own report alone. Without an export (no profile, an image `llvm-cov` cannot read, a pre-export bundle) the client falls back to `xccov`: in local mode it reads the bundle with the shared parser, streamed to a file of one JSON object per source file (`parseCoverage(path:manifest:into:)`, memory flat in the bundle's size) and sends it as `coverage` with `tool` `xccov`; in remote mode the manifest goes into the bundle without the flag and the server's processor reads the coverage as it always did. The export and the manifest are only built when the `COVERAGE` client feature flag is on (`TUIST_FEATURE_FLAG_COVERAGE=1`, early access), the bundle has coverage and the upload is on (`Tuist.swift` `testInsights: .testInsights(coverage: .coverage(upload:))`, overridden by `TUIST_COVERAGE_UPLOAD`). A coverage read or export failure is reported as a warning and dropped: coverage only enriches a run.

## Invariants
- Test results track status, duration, and structured failures for reporting.
- The parsers live in the shared `XCResultParser` package under `server/native/xcresult_nif`, so the CLI and the server's xcresult processor read bundles the same way.
- `TestExecutionModes` (shared package) records whether a run executed its tests in parallel or serially, per target: `TuistKit.TestExecutionModeResolver` resolves it from `-parallel-testing-enabled` and the xctestrun's `ParallelizationEnabled` (from `-xctestrun`, `-testProductsPath` or the derived data's build products) and writes `tuist_execution_modes.json` into the result bundle before the upload; the shared parser applies the file to the summary (`applying(executionModes:)`, run and per module), so the local-mode payload and the server's processor record the same `execution_mode`. Without an xctestrun or the flag nothing is guessed.
- Coverage carry-forward learns what a run skipped from the run's `skip_test_identifiers` (the caller's skips; quarantined tests Tuist skipped are left out, since they are outside the suite) and the selective-testing hits on its command event, and takes each skipped target's tests from earlier runs on the server. The client runs no extra xcodebuild pass to list a run's tests.
- `TestCoverageEvidence` (shared package) is which files each test executed. The test targets link the TestCoverageAttribution package (https://github.com/tuist/TestCoverageAttribution: XCTest observed once the bundle loads, Swift Testing through its `.coverageAttribution` trait), which records the coverage counters each test moves; nothing is injected into the test hosts. Whenever the run uploads coverage (`uploadsCoverage`; linking the package is the opt-in, and it does nothing unless told where to write), `TuistKit.TestCoverageEvidenceService` tells the test processes where to write (`TEST_RUNNER_TEST_COVERAGE_ATTRIBUTION_DIR`, through `XcodeBuildEnvironment.additionalVariables`, task-local, merged into xcodebuild's environment; macOS and the iOS simulator only, since a device cannot write to the Mac), and right after the run, before a stress pass replaces the profile, reduces what it wrote: counters to functions (`CoverageObserverOutput`, from `__llvm_prf_data`/`__llvm_prf_names`; the reader expects TestCoverageAttribution's record version 1, counter indices plus how much each moved), functions to files (`xcrun llvm-cov export -format=lcov` over each instrumented image with the derived data's newest `Coverage.profdata`, streamed, only `SF:`/`FN:`/`DA:` kept). Lines come from the counter deltas: `CoverageMapping` decodes the image's `__llvm_covmap`/`__llvm_covfun`, and `VerifiedCoverageMapping` trusts it only for the files whose executable and covered lines, computed from the profile, match the `DA:` lines `llvm-cov` reported; those files give each scope `lines` (flattened inclusive ranges), the rest keep file-level evidence. A test's scope is the union of its attributable records, a suite's is what ran in the gaps around its tests, a target's is everything its processes executed; the tests left with no scope because every record of theirs overlapped another go up as `overlapped_tests` (module, suite, name). The evidence carries a `status`: `collected` when scopes came out, `not_linked` when no test process made its output directory (no test target links TestCoverageAttribution), `failed` when processes made one but none holds an image table (the package removes its output when recording fails), there is no `Coverage.profdata`, reading the output throws, or the reduction yields no scopes. The result goes into the bundle as `tuist_test_coverage_evidence.json` with the compiler's paths; whoever parses the bundle ties them to the repository with the coverage manifest (`inRepository(manifest:)`: the client in `uploadTestSummary`, the parser when the manifest is in the bundle), and the run reports it as `coverage_evidence`.
- Everything the client does for coverage and test selection is behind the `COVERAGE` client flag (`TUIST_FEATURE_FLAG_COVERAGE=1`, `ClientFeatureFlags.contains("COVERAGE")`): the coverage manifest and upload, the commit file listings, the Git history outside CI, the build sources, the execution modes, the coverage evidence and `tuist coverage complete`. Without it a run is exactly what it was before the feature existed: no sidecar is written, no extra xcodebuild invocation runs, nothing is injected. New client work for the feature goes behind the same flag. On CI the Git history itself is collected for every run (`GitHistoryService.enabled`), since the server places runs on the default branch's history with it; its commits and branch heads go up before the server reads the graph (`GitHistoryService.publish`, from the stress gate before its plan and from the report before the run is created), once per process (`GitHistoryCache`); Outside coverage it never fetches history: it reads the checkout, and asks the remote for the base branch's latest commit (`git ls-remote`) when the checkout lacks it (`GitHistoryRemoteAccess.baseHead`); only coverage, which needs the merge base, fetches the base branch and deepens a shallow clone (`.history`). `TUIST_GIT_UPLOAD_ENABLED=false` turns collection off and `TUIST_GIT_UNSHALLOW_ENABLED=false` keeps every run to the checkout (`.none`).
