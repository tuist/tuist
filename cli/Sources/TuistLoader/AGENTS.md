# TuistLoader

## Manifest and package contracts
- Mark script-generated `.generated(...)` sources with `SourceFile.contentHashIsPlaceholder = true`. Keep their existing path-derived hash unchanged for artifact and selective-testing compatibility; it is not proof of generated bytes. Resource-accessor content hashes remain actual byte checksums.
- Scheme build-action targets and Build For override keys use the same resolved project paths. Merge purposes for aliases of the same target and keep one target entry in first-occurrence order.
- Map the manifest's `coverage` options (`enabled`, `prefixMapping`) into generated-project configuration unchanged; both default to off, and coverage prefix mapping stays disabled by default for `xccov` compatibility. The CLI overrides `enabled` per command (`BinaryCacheCoverage.resolved`), never here.
- Preserve native package dynamic-linkage hints and their platform conditions when mapping manifest dependencies; do not infer linkage from the embedding role.
- Swift package bundle identifiers preserve underscores as hyphens, including leading, trailing, and repeated underscores, so targets such as `IssueReporting` and `_IssueReporting` can coexist as embedded dynamic frameworks.
- `ManifestLoader` uses start/end tokens to parse manifest output and caches results.
- Package target settings reference checkout and scratch-directory paths through `$(SRCROOT)`, never as absolute paths, including the SwiftPM prebuilt (swift-syntax `MacroSupport`) search paths that SwiftPM records absolutely. Target settings are binary-cache hash inputs, so an absolute path splits the cache per checkout location (for example, per CI agent build directory). A macro cached from one checkout keeps an unused LC_RPATH to the warming checkout's prebuilt `lib` directory; that is harmless only while SwiftPM ships MacroSupport as a static library, so revisit it if MacroSupport becomes dynamic.
- SwiftPM prebuilts (swift-syntax `MacroSupport`): macros and macro tests link the prebuilt on every platform. Other targets that only macros reach, such as `CasePathsMacrosSupport` (even when exported as a library product), follow swift-build's host-platform filtering: they link it only on macOS (selected through `PLATFORM_NAME` and `IS_MACCATALYST`, since Mac Catalyst shares `sdk=macosx*`) and keep their source swift-syntax products elsewhere. Macros and macro tests also take the prebuilt settings of the package targets they link (targets that use a macro run it as a plugin and don't link it), and macro-reached targets take those of the products they consume from other packages, so `PackageInfoMapper.prebuiltTargets` plans every package before the loader maps them concurrently. If a target outside the macros' closure depends on a swift-syntax-using target that a macro also reaches, or a macro test links such a target outside that closure, the package keeps source products: Tuist doesn't impart the prebuilt's search paths and library to that target's consumers, so macOS apps could not import or link it, and a macro test can't link both. For the same reason, a package whose product that links the prebuilt is consumed by another package's target outside its macros' closure, or by a project target through `.external(name:)`, keeps source products. `ManifestGraphLoader` passes those names in, including the products that local packages mapped into projects link, so it merges those projects before loading the package graph. Like swift-build, the targets of another package's product that only prebuilt targets (macros, macro tests, and the targets they reach) consume, such as a swift-syntax helper library or swift-macro-testing under local macro tests, are macro-reached too and link the prebuilt on macOS; `prebuiltTargets` starts from every consumed product and drops those that any other target or a project consumes; a package that keeps source products only drops those its targets outside its would-be prebuilt targets consume, so a transient fallback can't settle the graph below the most prebuilts. Like SwiftPM 5.2+, a `.byName` dependency that names no target of its package is a product dependency on the package with that name, both when counting consumers and when propagating source swift-syntax. Tests are host-only only when they link a macro or nothing but targets macros reach; a test that also links an app library builds for the apps' platforms. A package whose macros or macro tests reach a target (their own, one only macros reach, or one shared with apps) that consumes another package's product built against source swift-syntax (directly or transitively, including from packages without macros) keeps source products, since one binary can't link both copies. `ExternalProjectsPlatformNarrowerGraphMapper` drops external dependencies whose condition excludes all of the target's narrowed platforms, such as the non-macOS source swift-syntax edge of a macOS-only helper, from both the graph's edges and the target's own dependencies: binary-cache hashing reads the latter but orders targets by the former, so leaving one fails `tuist cache` and cached `tuist generate` with a missing dependency hash.
- `SwiftPackageManagerGraphLoader` spells absolute workspace-state paths (local packages, artifacts, prebuilts) under `/var` or `/tmp` like the scratch directory, with or without `/private`. Workspace states can mix both spellings, and Tuist relativizes paths lexically, so a mismatch yields relative paths that cross the symlink and don't resolve. Don't rewrite them to one fixed spelling; the package-info cache only uses a spelling-insensitive form as a lookup key.
- `SwiftPackageManagerGraphLoader` uses only prebuilts whose directory name starts with `swiftlang-<version>-` for the `xcrun swift` (Xcode) compiler: SwiftPM names them after the `swift` that resolved, which may be another toolchain (for example swiftly's), and Xcode cannot load their binary modules. Dropped prebuilts warn and their packages build from source; when the version cannot be determined, all are kept, and so are SwiftPM 6.1's, whose directories (`6.1-MacroSupport-<platform>`) carry no compiler tag.
- Swift package targets using tools version 5.9 or newer carry their package name compiler argument in target settings so graph transformations preserve package access.
- Opted-in local package test targets may reference external products resolved from `Tuist/Package.swift`; map these through the same dependency path as production targets. Remote package tests remain excluded. Missing external products on tagged local package tests identify the test and product and direct users to declare the providing package in `Tuist/Package.swift` and run `tuist install`.
- A local path package overrides remote packages with the same identity and remote packages whose identity (the name part of a registry `scope.name`) matches its manifest name, since its own identity comes from its directory name. `.product(name:package:)` references to an overridden `scope.name` resolve against the local package. Remote packages that only share a manifest name are never merged.
- Source-built manifest evaluation and helper compilation search both `Modules/` and the dylib's directory for `ProjectDescription.swiftmodule`, supporting native SwiftPM and Swift Build outputs without modifying build artifacts.
