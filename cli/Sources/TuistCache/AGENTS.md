# TuistCache

## Generated client
- `OpenAPI/cache.yml`, `Types.swift` and `Client.swift` are generated from Kura's HTTP API definition (`kura/openapi/cache.yml`) with `mise run generate-cli-client` from `kura/`. Change the definition there, not these files.

## Invariants
- Only cacheable products are hashed (frameworks, static frameworks, static libraries, dynamic libraries, bundles, macros).
- Test bundles are excluded from binary cache hashing, but test-support frameworks and libraries that link XCTest or Swift Testing can be hashed.
- Explicit cache warm target selection scopes transitive cache candidates from non-test roots only.
- Caller-owned cache-warm scratch directories reject foreign build misses because their scripts control output locations.
- Cache version bumps invalidate incompatible artifacts. Format 9 includes Debug dSYMs and schema-2 per-slice `tuist-debugging.json` source identities (multiple verified DWARF spellings per source); exact and SDK fingerprints must cold-miss incompatible older products, including experimental format 8.
- Debugging metadata records declared source/header checksums and observed DWARF paths, not source bytes. Include generated `SourceFile.contentHash` identities, buildable-folder files and sibling additive memberships. Admission hashes only observed declared files; publication rehashes actual built generated contents. Script-generated `.generated(...)` inputs have path fingerprints, not content checksums: the graph marks these with `contentHashIsPlaceholder`, capture excludes those unknown bytes, admission retains sources and warming skips that target's publication after validating its known inputs. Resolve existing ancestors for not-yet-written generated paths. Match exact declared/canonical identities and evaluated compiler mappings, including parent-directory symlink aliases; never infer ownership from filename suffixes. Missing, unsupported, malformed, ambiguous or mismatching debugging metadata retains sources, and cancellation propagates. Keep this admission check independent of the resolved ordinary/instrumented coverage variant; scheme coverage and test plans must not silently override variant selection.
- `BinaryCacheCoverage.on` keys repository-owned targets (those without a `Project.externalHash`: the workspace's projects and packages referenced by path, which resolve without one) on a coverage dimension, in the exact hash and the per-SDK fingerprints alike. Packages from source control or a registry keep the plain key, since coverage is never kept for their code, and Release configurations keep it too, since they are never warmed with coverage. The variant is the command's (`TUIST_COVERAGE_ENABLED` > `Tuist.swift`'s `coverage.enabled`, behind the `COVERAGE` client feature flag), never the run's `-enableCodeCoverage` or scheme, so `tuist cache`, `tuist hash cache`, `tuist generate` and `tuist test` read and warm the same keys everywhere. With it off, the coverage dimension must not change keys within the same artifact-format namespace.
- XCFramework compatibility fingerprints are per SDK variant and independent of unrelated consumers. Initial coverage is iOS device/simulator, Catalyst, and macOS using standard architectures; other platforms and custom architecture settings use exact-target REAPI actions.
- Per-SDK REAPI action results reference immutable output trees. All required SDK results must exist before materializing an XCFramework. Verify CAS digests, directory safety, and actual slice coverage before reuse; do not publish subset indexes.
- XCFramework coverage is read through `XCFrameworkCoverageServicing`, implemented by the filesystem-backed `Services/XCFrameworkCoverageService.swift`. It reads declared architectures and checks binary existence; binary integrity validation is separate.
- Action records live under `Binaries/action-<digest>/result.pb`, sharing the binary-cache budget and cleanup with CAS blobs and materialized outputs.
- Remote warming retains successful targets but reports any failed publications through `CacheUploadError`, including configured endpoints that fail capability validation. Local-only warming remains independent of remote availability.
- All modern binary products use REAPI/CAS. Non-sliceable outputs retain their complete artifact tree under an exact-target action. Old module archives are cold misses; selective-test storage and explicit legacy mode keep their existing implementations.
