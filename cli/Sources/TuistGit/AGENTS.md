# TuistGit

- `GitController` uses the system to execute git commands and tolerates missing repos.
- CI environment variables are used to infer branch and PR refs when git data is unavailable. The branch is `TUIST_GIT_BRANCH`, then the CI provider's variables, then `git branch --show-current`; a detached checkout has no branch, never the literal `HEAD` that `git rev-parse --abbrev-ref HEAD` prints. `GitController.ciBranch(environment:)` is the environment part, for reporters that ask git themselves (Cargo). The Gradle plugin (`ProcessGitInfoProvider.branch`) and `tuist_ex` (`Env.git_branch/1`) also drop `HEAD` and let `TUIST_GIT_BRANCH` win. `gitInfo` reports the checkout's HEAD: on a pull request merge ref (`refs/pull/N/merge`) that is the merge commit the run measured, which the server keeps on the pull request's ref, off the branch. The Gradle plugin (`ProcessGitInfoProvider.commitSha`) and `tuist_ex` (`Env.git_commit_sha/2`) apply the same rule.
- Providers that pass build parameters in files rather than the environment are read by `CIBuildParameters` and looked up by name in the same lists as environment variables. For TeamCity that is the `.xml` copy (Java's XML properties format, parsed with `XMLParser` without resolving its DTD) the agent writes next to both the build parameters file (`TEAMCITY_BUILD_PROPERTIES_FILE`) and the configuration parameters file it names, so no `.properties` escaping is handled here.
- `GitController+History.swift` collects a run's Git history for the server's commit graph and coverage baselines (`gitHistory`: object format, merge base with the base branch, the base branch's commit as the checkout saw it (`baseHeadSHA`, listed with its commits so the server can move the default branch to it), deepening a shallow clone within a budget only with `GitHistoryLimits.remoteAccess` `.history` (with `.baseHead`, a checkout without the base branch gets its latest commit from one `git ls-remote`, raced against the budget like the fetches; with `.none` nothing reaches the remote) (the base branch named on every fetch, `--filter=blob:none`, the steps together within the window), the commits within the window, with a shallow clone's boundary commits (listed in its `shallow` file) given the parents their commit objects store, read in one `git log --no-walk --no-decorate --format=raw` call because `git log` lists them without parents and the raw format ignores the shallow grafts (in a depth-1 clone the head is such a commit, so without this a push uploads nothing; when the parents cannot be read the boundary commits are left out rather than stored as roots)) and the commit's file listing (`commitFiles`: every blob of the reported commit's tree from `git ls-tree -r --full-tree <sha>` with its mode, at most the server's limit, marking the listing truncated beyond it; the tree rather than the index because the reported commit need not be the checkout's; the server keys it by repository and commit, so it is uploaded once per commit). `GitHistoryParser` parses the `git log` (including the raw format's `commit`/`parent` headers) and `git ls-tree` output. Every fetch of the merge-base recovery (the base branch's, then each `--deepen`) shares the deepen budget and is raced against what is left of it: one still running at the deadline is cancelled through `CommandRunning.runInOwnProcessGroup`, which tears down `git fetch` together with the `git-remote-https`/`ssh`/`index-pack` processes it started, and the run reports the base branch as not fetched, or the merge base as not found, "within Ns". `connectedGitHistory` then closes the gap a shallow clone leaves between the run's commits and the server's: the server places a commit on its branch from the parents it has when the commit arrives, so a depth-1 push whose parent another run has not uploaded yet would leave that parent off the branch for good. It takes the first parents the clone stops at on the first-parent chain of each head the run reports (the commit, and the base branch's when the checkout has it; a chain that ends at a root or at the history window has none), asks the caller which of them the server lacks (`GitHistoryService` asks `commits/missing`), and while any is missing deepens through the given branch with the same steps and bounds as the merge base (`--filter=blob:none`, 50 then doubling, within the window and one budget, stopping at a failed fetch; with `--refmap=`, so the checkout's `origin/<branch>` does not move) and lists the commits again; a parent a fetch leaves out of reach (the remote's branch was rewritten) is dropped rather than fetched for again. Only with `.history` access and a branch to name, which `GitHistoryService` passes as its full ref (`refs/heads/<branch>`, never read as a tag or an option), and only on CI: the fetch turns the clone into a partial one, which a developer's own clone must not become. Everything is best effort: a missing piece is reported as a reason with the run, never an error.
- `GitController+TestImpact.swift` diffs the checkout against a coverage-selection baseline (`changedFiles`). It counts only files Git tracks: untracked ones are neither changed files nor make the diff `dirty`, matching the coverage run's `git_dirty` (`uncommittedTrackedFiles`, `git status --untracked-files=no`), which `TestImpactSelector` also uses to decide whether a cached diff can be reused. A new source file that isn't committed therefore selects no tests. Each file the working tree changed (from `git diff HEAD`) is marked `dirty`; files only the commits changed are not. See [`server/docs/coverage-test-selection.md`](../../../server/docs/coverage-test-selection.md).
