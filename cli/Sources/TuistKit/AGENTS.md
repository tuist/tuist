# TuistKit (CLI Commands)

This module houses CLI command definitions, command wiring, and high-level orchestration.

## Responsibilities
- Define the root command (`TuistCommand`) and subcommand groups.
- Load config, server URL, and trackable command execution lifecycle.
- Centralize error handling, logging, and Noora integration.

## Boundaries
- Keep orchestration here; domain logic lives in feature modules (e.g., generator, cache, server).
- Avoid direct file system or graph logic that belongs in `TuistCore`, `TuistGenerator`, or `TuistSupport`.

## Invariants
- Credential-free Xcode publishing parses activity logs and XCResult locally, posts completed structured reports, and never uploads archives, attachments, coverage/history, shard/stress references, existing-build associations or cache-processing hints. Skip enrichment that requires authenticated reads. Branch only after the shared report-mode credential resolver proves genuine absence; present or rejected credentials retain authenticated/error behavior.
- `tuist xcodebuild` may reorder a supported action for Tuist's subcommand parser, but must restore its original position before forwarding arguments to xcodebuild. Preserve the caller's action sequence, including `clean` and repeated actions, and exclude consumed Tuist-only options from the forwarded arguments.
- Swift flag deduplication must preserve top-level `-Werror` and `-Wwarning` pairs in their original order, including repetitions, in both ordinary and platform-conditioned build settings. Do not mistake a forwarded option such as `-Xcc -Werror` for a top-level warning-group flag.
- `TuistCommand` groups commands into: Get started, Develop, Share, Account, Other.
- Open-source generation honors `includeGenerateScheme` and configures compilation-cache debugging after automatic workspace schemes are created.
- ProjectAutomation's package projection keeps its existing product-name and embedding shape. Explicit native package linkage hints remain in the generation graph; they do not add new package variants to this projection.
- `TuistCommand.main` initializes cache directories, parses the command, loads config, resolves server URL, and runs `TrackableCommand`. Commands conforming to `ProjectPathProviding` use their parsed path (including environment defaults) for both configuration and analytics; other commands and plugin dispatch retain raw-argument path resolution.
- `graph`, `clean`, `dump`, and both `hash` subcommands conform to `ProjectPathProviding`, just like generation, cache warming, editing, installing, building, and testing. Keep their parsed project paths consistent with entry-point configuration and analytics.
- Background analytics uploads receive the resolved project path through the hidden `analytics-upload --project-path` option so optional-authentication policy is loaded from the same config as the original command. Legacy invocations without it retain the raw-argument fallback.
- Noora logging is reinitialized after command execution to ensure logs are captured in verbose logs.
- Cache warm selection is scoped from explicit non-test roots; focused test roots may remain in the graph but do not expand binary cache candidates.
- Cache setup serializes cooperating setups under cancellable `cas-setup.lock`, registers policy before startup, installs the version-selected stable launcher, and starts/verifies the proxy. Only the adopting managed proxy refreshes the plugin, never setup merely selecting a new target. An older checkout must not downgrade the stable plugin. The LaunchAgent runs `/bin/sh cas-launcher.sh cas-launch-target.json cache-proxy ...`, not the setup-time CLI. Leave a current agent running when only the target advances; the proxy exits itself after its requests and publications drain, and its replacement atomically refreshes the stable plugin. If the managed plugin is missing, explicit idle setup marks the agent stale to retry the refresh in a replacement proxy. Credential helpers follow the selected target even while the old proxy drains. Explicit setup can still replace changed configuration, so run it with builds idle. Generation only advances an existing launch target when caching is enabled and this CLI bundles both components; it never installs, authenticates, copies a plugin, or restarts a service. Custom plugin/proxy/socket/registry overrides skip advancement. Custom plugin/proxy overrides and non-semver source builds use an explicit CLI launch configuration, include the executable and resolved components in launch freshness checks, and copy their plugin only after starting their replacement. They disable managed selection after readiness. Teardown stops the proxy before disabling the launcher, preserving restartability on bootout failure, and retains the plugin. Inject `XcodeCacheInstallationStoring`; keep persistence in TuistCAS.
- Cache readiness probes keep their read side open until the daemon responds or closes the connection. Closing immediately after connecting can crash SwiftNIO on Darwin before it accepts the socket.
- `tuist cache-proxy` hands over to `tuist-cas-proxy` with `posix_spawn` and `POSIX_SPAWN_SETEXEC`, clearing the signal mask and resetting every signal to its default action, never with a plain `execv`. The handoff runs on a Swift concurrency thread, which blocks SIGTERM, and `execv` would pass that on, so the proxy would ignore `launchctl bootout`.
- When selective testing skips every test, publish a completed empty test run with the selected scheme name, recovering pruned workspace schemes from the initial graph. A build-only sharding run must also publish it when emitting an empty shard matrix, because no test job will follow.

## Related Context
- CLI entry point: `cli/Sources/tuist/AGENTS.md`
- Core domain models: `cli/Sources/TuistCore/AGENTS.md`
- Project generation: `cli/Sources/TuistGenerator/AGENTS.md`
- Server integration: `cli/Sources/TuistServer/AGENTS.md`
- `BinaryCacheCoverage.resolved(config:)` picks a command's binary-cache variant: `TUIST_COVERAGE_ENABLED`, then `Tuist.swift`'s `coverage.enabled`, and off without the `COVERAGE` client feature flag. There is no command-line flag, so every command that generates (`tuist cache`, `tuist hash cache`, `tuist generate`, `tuist test`, `tuist build`, `tuist run`, `tuist inspect dependencies`, `tuist hash selective-testing`) resolves the same variant in one environment. Every `GeneratorFactorying` method takes the resolved variant and writes it into the config's `coverage.enabled` (`Tuist.resolvingCoverage`) before building mappers, so the linker setting, automatic-scheme coverage and binary-cache keys (`BinaryCacheCoverage(config:)` in `CacheGraphMapperFactory`) all follow one value. A Release warm always warms plain. `tuist test` warns when a run that collects coverage (passthrough `-enableCodeCoverage`, else the tested scheme's test action) linked repository targets from the cache as plain binaries (`CacheItem.instrumented == false`).
- A warm with coverage on fills the coverage variant of the binary cache: the hash pass and the warm-project generator take `BinaryCacheCoverage.on`, the repository's frameworks and libraries get the `TUIST_BINARY_CACHE_COVERAGE` marker, and the binary (not bundle or macro) builds get `InstrumentedBinaryCacheWarm.buildSettings` as passthrough xcodebuild arguments, raw strings rather than `.xcarg` because the settings hold `$(…)` references and xcodebuild runs without a shell. The checkout root comes from `CoverageBuildSourcesService.root(from:)`, the same rule `tuist test` ties coverage with.
- Cache warming carries the preload graph's SDK fingerprints through archiving and publication; do not recompute them from the graph after binary replacement. Preserve these publication fingerprints even when profile exclusions prevent handing precomputed target hashes to the warm-project generator.
- When the default generator runs focus without filters (for example, during build), it preserves eligible local package tests and their dependencies for their effective platforms. Ordinary unfocused generation relies on the narrowing and pruning mappers. Test automation saves the graph before focus for platform inference and passes includedProducts for unit/UI tests; a selected scheme keeps its own test roots and does not add package tests outside the scheme.

- Cache setup derives known hosted URLs locally and discovers one main URL for self-hosted servers, without registering demand. Hosted cache requests activate capacity through their derived URL. Empty discovered configurations allow ordinary builds and the Xcode proxy to use local storage with a warning; malformed endpoints and authentication errors remain failures.
