# Make Atlas generic and self-hostable

Status: reviewed implementation proposal with the first installation slice implemented and verified on 2 October 2026. Remaining phases below track outstanding decoupling work.

## Outcome and scope

An organization should be able to install Atlas, establish its own administrator, configure its identity and integrations, and use the domains it needs without a Tuist account, Tuist infrastructure, or a fork of the application. Tuist should run the same release with an explicit organization configuration and Tuist connector.

Start with **one organization per installation**, with its own database, encryption keys, storage, credentials, and network boundary. Customer accounts in `Atlas.Accounts` are customers of that organization, not Atlas installation tenants. Do not turn those records into installation organizations. Shared hosting of multiple organizations would require a separate isolation design covering every query, job, search index, token, and public link.

Keep the existing domain contexts and shared application. Introduce small, typed configuration boundaries and connector contracts where the code already needs variation. Do not build a general plugin runtime, arbitrary executable configuration, or a universal business workflow designer. Remaining inside the monorepo is compatible with self-hosting; splitting the repository is not a prerequisite.

First release scope: accounts and contacts, notes, tasks, engineering projects/domains/specifications/postmortems, hardware and insurance records, audit, permissions, and built-in agent tools. Documents require a supported durable storage configuration. Banking, billing synchronization, email delivery and ingestion, Slack, postal delivery, inference, semantic search, error ingestion, and Tuist analytics are optional capabilities. A disabled automation or integration must not prevent use of the underlying manual records where those records are useful independently. Distinguish disabling an entire domain from disabling its external delivery or enrichment.

## What the inspection found

Atlas already has useful seams: configurable bank sources in `finance/config.ex`, a document storage wrapper, optional ClickHouse startup, optional language model configuration, configurable upstream tool servers, scoped roles, and GitHub repository records. Reuse them. The blockers are organization defaults spread across configuration, workers, prompts, templates, public pages, schemas, and deployment assets. Some provider integrations are reusable already; their presence is not itself Tuist coupling.

The highest-priority boundaries are:

1. **Access and bootstrap:** The original inspection found Google sign-in pinned to `tuist.dev` and no supported first-administrator command. These two defaults are now addressed by the completed installation slice below. New authenticated users receive no role; role seed migrations cannot assign an administrator who did not exist when they ran.
2. **External side effects:** unset settings can still select Tuist Slack channels, mail identities, upstream servers, repositories, and an individual operator.
3. **Product data and commercial policy:** analytics collectors, feature catalogs, nudges, overview metrics, sales vocabulary, and license formats assume the Tuist product.
4. **Packaging and operation:** the existing chart explicitly targets a managed Tuist cluster and private secrets infrastructure. Development setup also inherits monorepo tooling.
5. **Historical setup:** migrations and demo seeds contain organization policy, so changing current runtime defaults alone cannot produce a clean installation.

Paths below are relative to `atlas/` unless they begin with `infra/` or `.github/`. Directory references represent a boundary to inspect during implementation, not a claim that every file in that directory is coupled.

## Proposed boundaries

### Organization profile and policy

Use an installation-level organization profile for display/legal names, internal email domains, website, public support contacts, branding assets, legal links, locale/time zone, and legal entities. Keep product positioning and commercial vocabulary in a separate product profile. A display name cannot express product-specific feature attribution or legal policy.

Use environment configuration for boot-critical settings, keys, connection addresses, and initial configuration import. Start with one audited, typed installation-settings store for profile and policy sections rather than separate profile subsystems. Store operator-editable templates and destinations in the database where their existing lifecycle needs records, with validated schemas and versioned exports. Secrets stay in the existing encrypted storage or externally supplied secrets; ordinary exports contain references, never decrypted credentials. Make precedence explicit: boot environment overrides where supported, then saved settings, then neutral defaults. Show the resolved source to administrators.

Tuist policy must be explicitly imported/applied, never selected by hostname, environment, presence of a token, or project name. Applying a policy is idempotent and must not overwrite operator edits without a visible diff and approval. Checked-in examples contain no real people, channel identifiers, signatures, or private legal templates.

### Capabilities and connectors

Introduce one shared availability facade over explicitly enabled capabilities and validated adapter configuration. Derive disabled, needs configuration, ready, and degraded states for diagnostics instead of persisting a second lifecycle state machine. Declare dependencies and safe diagnostic reasons. Reuse existing `configured?` and `enabled?` seams behind this facade. Keep **capability enablement separate from user authorization**. The same decision must control startup children, scheduled jobs, routes/actions, navigation, tool discovery, tool invocation, search, and brief adapters. For the first release, schedulable capability enablement is boot configuration only and changes require a restart. Generate the background scheduler from that configuration. Database-edited profiles, policies, destinations, and credentials affect execution-time readiness but cannot enable a previously disabled scheduler. Display this distinction to operators; also check capability and readiness at execution so already inserted work cannot bypass disablement. A future live scheduling control would require explicit scheduler reconciliation.

Jobs recheck enablement when executing. Disabling a connector stops new work and prevents queued retries from sending. Preserve already recorded evidence and delivery history. Define cancellation/draining rules for in-flight requests; do not claim disabling configuration can retract a request already accepted by a provider. Re-enabling a sync resumes using existing checkpoints instead of duplicating imports.

Start connectors with narrowly scoped behaviors for product observations, bank sync, billing sync, inbound mail, delivery, and contract catalogs where needed. Keep provider-specific authentication, query shapes, retry classification, and checkpoints inside the adapter. Shared contexts own records, audit, idempotency, and policy. Existing wrappers should gain explicit error/availability contracts rather than being replaced wholesale.

The Tuist connector owns `Atlas.TuistServer`, Tuist overview queries, feature catalog/collectors, Tuist-specific signals, licensing compatibility, and privileged tool proxy configuration. Keep it compiled in the shared release initially, registered only when enabled. Retain existing tool names and consumer payloads for Tuist; generic names can be additive later. No runtime installation of executable third-party extensions is needed.

### Packaging and deployment

Publish versioned, immutable Atlas images usable without private registry credentials, with documented supported processor architectures and a tested source build. Noora can remain a Tuist-owned dependency. The existing monorepo-root Docker build already copies both Atlas and Noora; that is valid packaging, not a defect by itself. Document the required build context, ship all runtime assets, and test the image independently. An eventual repository extraction would require a packaged Noora dependency. Replace moving source requirements such as Boruta `master` with a fixed release/commit policy and keep the lockfile reproducible. The third-party `emcp` fork is already pinned to a commit; document why it exists and how it will be updated, rather than treating it as unpinned.

Provide a minimal Docker Compose deployment: Atlas, PostgreSQL, reverse-proxy guidance, and an explicitly configured compatible object store when file domains are enabled. Reuse the current object-storage adapter first and optionally bundle a tested local object-storage service; production local-disk support is deferred. Documents, support attachments, letters, and finance files use `Documents.Storage`, so verify all consumers with the same store. Keep ClickHouse, vector search, inference, and Cloudflare relay in optional profiles. Ensure browser/text extraction tools included in the image work without privileged containers. Validate production storage and upload/download paths rather than promoting test-only storage by changing a flag. The completed agent execution inventory found no remote coding or Kubernetes sandbox workflows. The chart grants no pod/exec permissions and disables automatic Kubernetes API token mounts. `infra/helm/atlas/templates/agent-sandboxes.yaml` retains only legacy namespace/service-account objects for a non-destructive managed upgrade; the namespace must receive its retention annotation before an operator disables that legacy flag. Ordinary model/tool sessions execute in-process. No Kubernetes sandbox access is required for manual records.

Then generalize the Helm chart: neutral values, optional ingress/certificate and external-secret integrations, existing-secret support, external PostgreSQL support, optional managed database operator, optional Tuist token projection, and independently enabled analytics/vector components. Move current values into Tuist-managed deployment configuration and update the release workflow to pass it explicitly. Keep managed operational setup separate from public self-host instructions.

## Delivery sequence and acceptance gates

Effort bands indicate relative size, not calendar commitments. Each phase should land in focused changes with its own verification and a maintained coupling register.

### Phase 1: stop implicit Tuist access and make bootstrap real (medium)

- Inventory effective defaults in configuration, module constants, seeds, migrations, and chart templates. Classify each as neutral, required configuration, reusable provider, or Tuist policy.
- First make Tuist's current production configuration explicit for every default to be removed, including module-level destinations and operator identity. Deploy that configuration before removing fallback behavior.
- Remove generic defaults for Tuist endpoints, sender identities, embedding origins, channel identifiers, repositories, and upstream servers. Empty tool proxy configuration means no upstreams, not fallback discovery.
- Add configuration validation and diagnostics; incomplete enabled integrations fail validation or become visibly unready according to whether they are boot-critical. Optional unconfigured integrations do not retry indefinitely.
- Repeat the completed empty-database migration check when packaging the supported deployment, and inspect remaining historical policy imports before selecting a migration strategy.
- Test unrestricted and restricted token issuance and invocation before designing scope changes; inventory the actual access each grants. Audit and enforce read/write scopes across dashboard, downloads, built-in tools, domain mutation boundaries, and privileged connector tools.
- Compare Tuist production effective behavior before and after explicit configuration, including notifier module constants that an environment-variable diff would miss. Use sanitized config summaries and delivery fixtures, never secret dumps.
- Complete verified identity/admission settings, invitation policy, and administrator recovery. The one-time first-administrator bootstrap and configurable Google sign-in domain are implemented; recovery remains a separate operator workflow. Verify provider claims and admission boundaries before treating identity as complete.
- Keep demo seeds separate from the implemented neutral bootstrap. Review remaining policy-bearing seeds and migrations; production bootstrap creates no customers, channels, campaigns, repositories, or sample documents.

**Gate:** every declared authorization area is enforced across its dashboard actions and built-in tools, or an intentional authenticated-only policy is explicitly documented and tested. Restricted and unrestricted token call-path tests pass, including privileged Tuist access. An empty production database can be migrated and administered with organization-owned identity configuration, without Tuist secrets or contacts. Startup, job ticks, tool discovery, and ordinary page loads produce no unexpected Tuist requests or deliveries. Existing Tuist access and destinations remain unchanged under explicit deployment configuration.

### Phase 2: profile, capability model, and Tuist connector (large)

- Introduce organization/product profile readers and shared branded email/public-page rendering. Replace all public and internal company wording, not just logos.
- Add the shared availability facade and apply it across all entry points, workers, supervisors, domain adapters, and permission-sensitive tool surfaces.
- Move Tuist analytics, overview, catalog, signal rules, and privileged tools into an explicit connector while preserving its persisted keys and interfaces. Design the normalized cross-product interface during the pilot rather than before a second consumer exists.
- Add namespaced external identities and migrate current Tuist handles with collision reporting. Do not destructively replace existing associations.
- Keep base overview and account pages useful without product analytics; display unavailable/stale state distinctly from measured zero.

**Gate:** a fictional organization can use the base domains with no Tuist branding or analytics assumptions. A connector disabled after scheduling cannot send when its queued jobs execute. Tuist upgrade fixtures preserve analytics history and tool/credential compatibility.

### Phase 3: business policy and optional integration lifecycle (large, split by domain)

- Extract outreach segments/topics/scoring, agent business context, commercial vocabulary, briefing subscriptions, and detector policy.
- Replace contract placeholder catalog assumptions with a validated operator-managed catalog; isolate jurisdiction-specific postal templates and Tuist license format.
- Finish manual/import workflows and setup/diagnostics for banking, billing, documents, mail, Slack, repository ingestion, postal delivery, and inference.
- Keep irreversible outbound activity behind explicit setup and existing human review flows. New capability enablement does not auto-run outreach, publish content, or import organization policy.
- Validate finance/documents/hardware/insurance dependencies, permissions, search, evidence resolution, and agent-session visibility end to end.

**Gate:** a second product with different terminology and campaign policy can use the same code without editing modules.
