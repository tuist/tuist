# Account renames

An account's current name belongs in its client endpoints. Kura's configured tenant is a separate, permanent storage identity: changing it changes hashed object keys, workload names and peer CA selection. Renaming an account changes the regional client hostnames and authorization handle while preserving its storage, workload and peer identity.

The control plane persists `accounts.kura_tenant_id` and reserves current and historical handles in `account_handle_reservations`, separately recording each old client URL's `client_url_expires_at` deadline. Database triggers initialize the identity, prohibit changing it, and enforce reservation ownership even during a rolling server deployment. A different account cannot claim a retained handle.

## Endpoint migration

1. The account rename reserves both names. The desired `KuraInstance` keeps its name, tenant, selectors, peer addresses and CA; its current client hostname changes and `clientHostAliases` includes historical names whose 90-day URL window is still open. A revision suffix causes the server to apply this client-plane change even when the runtime image is unchanged.
2. The controller renders every hostname into DNS, TLS and HTTP/gRPC ingress. All names route to the same Service. Private gateways keep the same CIDR restrictions. No StatefulSet template or volume change is needed, and an existing operator `OnDelete` pause is preserved.
3. The existing activation path waits for the new public hostname's authoritative DNS and HTTPS probe before updating the published server URL. Endpoint discovery continues returning the previous URL until then. Private gateways use their existing controller readiness observation. Custom self-hosted URLs remain owner-configured.
4. Enrollment, managed discovery and self-hosted heartbeat responses carry the current `account_handle`, all `account_aliases`, and `endpoint_redirects` for activated public endpoints. The runtime replaces these together in one atomic snapshot, without restarting. Every retained name authorizes against the current account's grants; storage and replication continue using the configured tenant. Intermediate aliases work after repeated renames, and all unexpired ready redirects point directly at the latest name.
5. Existing HTTP clients and gRPC clients continue using an old hostname as a routing alias. HTTP clients that explicitly send `x-tuist-accept-endpoint-redirect: 1` receive **307 Temporary Redirect**, preserving method, encoded path and query, with `Cache-Control: no-store`. Health/internal routes and gRPC are never redirected. The capability means the client can replay its body and safely reattach credentials to the discovered account endpoint; generic redirect libraries can drop Authorization across hosts. This change does not opt existing CLI, Gradle or Bazel clients into that capability. They migrate via endpoint discovery or continue using the working alias. Permanent cached redirects would create loops on rename-back, so 301/308 are deliberately avoided.

Signed analytics ingestion resolves original, intermediate and current account handles through the reservation owner when finding the project. This includes REAPI events whose absent tenant header falls back to `config.tenant_id`, plus events queued before a rename; their producer-supplied handle remains diagnostic history while `project_id` identifies the current project.

Endpoint discovery accepts a retained account handle only after authorizing access to its owning account. An alias never grants access by itself. Signed cache tokens embedding old-handle grants must be refreshed to carry current-handle grants; routing aliases do not rewrite signed claims. Opaque credentials are evaluated for the new authorization target. Changes propagate at the mesh refresh cadence, so authorization can temporarily fail until a successful refresh. Missing optional fields from older servers preserve learned identity; a changed handle without ready-target data clears stale redirects.

This implements today's regional endpoints. [Spec #95: Per-account cache hostname steered by proximity](https://atlas.tuist.dev/engineering/specs/95) proposes a region-independent hostname and proximity DNS. That future hostname should use the same current-name/retained-alias policy, but its DNS advertisement and regional drain mechanism are not implemented here.

## Alias retirement

Old client URLs retire **90 days after the account renames away from that name**. The database rename trigger sets `client_url_expires_at` atomically with name reservation; the current name has no deadline. Further renames do not extend earlier deadlines. Renaming back clears that name's deadline, and renaming away from it again starts a fresh 90-day window.

At the deadline the old name drops from desired client aliases and redirect targets. That changes the manifest revision, so the ordinary reconciliation loop withdraws its DNS records, HTTP/gRPC ingress rules and TLS host/certificate configuration without an image change or restart. Withdrawal occurs on successful reconciliation and propagates through ingress, certificate and DNS updates; it is not a synchronized connection cutoff at the exact second. Existing streams can finish. DNS pruning still removes retired names when no healthy gateway target is available, while retaining current names' last known targets.

**Name reservations do not expire with the URL.** Another account cannot register or rename itself to the old name, case-insensitively, before or after the 90-day window. Keep the original storage tenant, authorization aliases, endpoint discovery's account-handle lookup and historical analytics attribution bound to the same account. Clients that refresh discovery can obtain the new URL; clients hardcoding the old URL must migrate within 90 days. Reservation rows remain for the account lifetime and cascade on account deletion; existing endpoint cleanup must finish before a deleted name is reused. There is no manual retirement API in this change.

For names already historical at migration time, the actual rename dates are unknown. They receive a full 90-day window starting at the expiry migration, rather than expiring immediately or inferring a date from the reservation's backfill timestamp.

## Migration and rollout

1. Audit all non-destroyed `kura_servers.provisioner_node_ref` values against the existing workload tenant, including archived rows. The migration recognizes a frozen set of historical Kubernetes name suffixes and aborts on unknown references, conflicting identities across regions, duplicate permanent identities or reservation collisions. It holds the accounts table lock while backfilling; measure duration on a production-sized snapshot before deployment. Do not bypass an abort by guessing an identity.
2. Audit already-renamed self-hosted-only accounts separately: without a managed server reference the database has no historical tenant evidence and defaults to the current name. Such accounts need an explicitly reviewed backfill before this migration. Manual tenant overrides and previously reused historical handles also require review. Intermediate historical names missing from existing data cannot be reconstructed by the migration.
3. Install the additive CRD and compatible controller in every serving cluster before enabling renames. An old CRD can prune `clientHostAliases`; an old controller cannot retain its routing. Deploy the migration and server with `kura_account_rename` disabled. Avoid renames until every server process has the application gate.
4. Deploy compatible Kura binaries to all serving managed and self-hosted nodes. Old runtimes ignore additive fields but cannot authorize the new handle. Verify peer discovery and real authenticated cache reads before enabling the per-account flag in production/canary. For already-renamed accounts, server reconciliation can begin endpoint migration as soon as this server code is deployed; install the CRD/controller first and keep the rollout pause below.
5. Verify that old and new client hosts both serve the same stored object, TLS covers both, endpoint discovery changes only after readiness, unrelated grants are denied, and the StatefulSet template, volumes, CA and configured tenant remain unchanged.

For an already-renamed mesh, restoring discovery can unblock a pending StatefulSet rollout. Keep an existing `OnDelete` pause in place until a separate recovery validates the standby's data and readiness and authorizes replacement of the serving pod. This PR does not change a live workload or resume a rollout.

## Rollback

The identity and URL-expiry migrations are forward-only. Retain identity bindings, reservations and per-name deadlines. Disabling the rename flag stops future renames; it does not undo completed ones. Keep a compatible controller, CRD and expiry-aware server while aliases exist: rolling either back can remove old routing or certificates. Rolling back the server or runtime to code predating this protocol can restore the original discovery/authorization failure. Recover with compatible code, without rewriting tenant IDs or volumes. Rename-back remains possible for the same account; its URL becomes current again, its deadline clears, and non-cacheable redirects avoid permanent loops. Rolling back to a server that ignores expiry can re-publish expired URLs.

## Local regression

Build Kura, then run `KURA_RENAME_TEST_BIN=/absolute/path/to/kura shellspec spec/e2e/account_rename_spec.sh` from `kura/`. It starts a loopback control-plane fixture and a native node with peer TLS in an isolated temporary directory, stores an object, performs repeated renames and a rename-back through discovery, reads the same bytes through every alias, tests negotiated redirects and denies unrelated account/project requests without restarting. Host overrides exercise runtime behavior; controller tests separately verify DNS/TLS/ingress rendering and unchanged StatefulSet resources. Live DNS propagation and a production TLS cutover require staged rollout validation.
