# Luft

Struo workspace for Luft, a Rust-core client developed alongside the shipping apps in `../app/` and `../android/`. It reports to the Tuist project `tuist/luft`. Native frontend sources live in `apple/`, `ios/`, `macos/`, and `android/`; the GPUI desktop frontend lives in `gpui/`. The GPUI web edge in `gpui-web/` runs the GPUI views in the browser and is served by the Luft server at `https://luft.work/app/`; mobile browsers are pointed at the native apps. Keep standalone Vite/TypeScript sources in `web/` and their wasm/Struo targets intact for future work; the Luft server neither serves nor builds them. Keep shared business logic in Rust crates, platform UI in Swift/Kotlin/GPUI, and UI dependencies out of the shared core. See `README.md` for build commands and coexistence boundaries.

The apps display as **Luft** and use the `dev.tuist.guild` identity (Android application ID and package, Linux app ID), except the iOS and macOS bundle ID, which stays `dev.tuist.code` so the existing App ID and signing profiles keep working, with the `luft://oauth-callback` scheme. Distribution is internal-preview-only: no store uploads, public releases, production deep-link registrations, or changes to shipping client behavior. iOS device previews and macOS previews are signed after the build by `ios/distribution/bundle.sh` and `macos/distribution/bundle.sh` on a copy of the bundle; only the trusted `main` publication step receives the signing secrets.

- Default native sign-in and API traffic to `https://luft.work`. Desktop overrides use `LUFT_URL`, not `TUIST_URL`. Custom origins must advertise the fixed Luft native client ID through `/.well-known/luft.json`; do not accept a Tuist server as a Luft origin.
- Use Luft's public PKCE client (`tuist_oauth::LUFT_CLIENT_ID`) and `/oauth2/authorize|apple|google|github` plus `/oauth2/token`. Native clients hold Luft credentials (`iss=luft`); the Luft server brokers scoped Tuist OIDC and keeps Tuist tokens encrypted server-side. Add upstream capabilities through the Luft server's allowed/requested scopes as documented in `../luft-server/README.md`.

Luft keeps its own session on every platform. Do not read or write the shipping apps' credentials: other apps' Keychain items prompt for the login keychain password, and spending their refresh tokens signs those apps out. Mobile vault migration drops profiles without a Luft access-token issuer. GPUI appends `/luft` to its config/state/data bases; preserve that isolation from CLI credentials and selected Tuist origins.

## Architecture

Luft follows the [native edges](https://tuist.dev/blog/2026/11/02/native-edges) principles (source: `../server/priv/marketing/blog/2026/11/02/native-edges.md`): a headless Rust core and thin native edges, one per platform.

- **Only what needs the platform lives outside Rust.** Edges render UI and provide platform services: SwiftUI, Android platform views and GPUI views, the Keychain or Android Keystore, presenting the browser for OAuth, platform TLS, installing previews, and other OS integrations. Everything else (sessions and profiles, token refresh, API calls and their validation, pagination, filtering, routing, and deciding what a screen shows) belongs in Rust. Before adding logic to Swift or Kotlin, check whether another platform would need it or whether it could be tested without launching the app; if so, it belongs in the core. Move existing edge logic into the core when you touch it.
- **Stay horizontal to use every CPU core.** Prefer many small Rust crates and Struo targets with explicit dependencies over a deep chain or one large crate, so independent nodes compile, test, and cache in parallel and an edit rebuilds only its dependants. Each edge depends only on the core build it needs; no edge depends on another, and no library crate depends on UI. Add a crate or target at a real dependency boundary (a new server API, a feature with its own state), not per file.
- **Parallelize at runtime too.** Run independent requests and computation concurrently and off the UI thread. Serialize only invariants that require it, such as refresh-token rotation, vault writes, and session replacement, and reject stale results by session generation. Do not extend one serialized queue or global lock across unrelated operations.
- **Keep the bridge small.** Edges call the core through `crates/core` operations (C ABI for Swift, JNI for Kotlin; GPUI calls Rust directly), documented in `crates/core/README.md`. The core declares what it needs from the platform as host actions and returns plain values; edges decide only how to present them.

New Apple copy belongs in `apple/Resources/en.lproj/Localizable.strings`; new Android copy belongs in `android/res/values/strings.xml`. Platform code owns localization; the Rust core exposes stable destination IDs through the C/JNI bridge. Struo builds must not import Swift CLI modules or the shipping Gradle app. Run tasks with the root mise config excluded as documented in the README.
