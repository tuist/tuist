# EU East cache outage on 2026-09-22

## Outcome and confidence

At 14:50 and 14:51 UTC (16:50 and 16:51 Berlin), all 22 public EU East
`/ready` endpoints returned HTTP 200, `ready: true`, and `state: serving`.
All 44 runtime pods subsequently reported Ready. That recovery was temporary:
at 15:16 UTC all 22 public endpoints returned 503 again. All 44 warm processes
survived without replacement, but Kubernetes marked their pods unready after
node heartbeat loss. At 15:21 UTC only five public endpoints returned 200.
At 15:25 UTC 16 of 22 endpoints returned 200, while six still returned 503.
The incident therefore remained open. Readiness checks establish recovery of
public routing and runtime readiness, not an authenticated end-to-end cache
download. The reported `tuist generate --verbose` request was not available
for reproduction.

The initiating failure was severe network degradation between the Warsaw
host and remote destinations, including the Kubernetes control plane. The
evidence points upstream of the local node, but does **not** establish an exact
provider router, failed link, congestion source, or routing change. Recovery
did not repair that network path. The application changes below address the
failure amplification and the missing availability boundary.

## Evidence

The affected node is `tuist-tuist-ovh-fleet-eu-east-nh9pb-p4qn2`,
`57.128.235.80`. Its PodCIDR is `192.168.42.0/24`. Production config declares
one EU East host, and both replicas of all 22 instances were placed there.
Their `scw-local-nvme` volumes bind them to that node.

| Observation | Consequence |
| --- | --- |
| Node events record 22 `NodeNotReady` occurrences from 13:09:03 to 14:08:24 UTC, with another partition during recovery | This was repeated loss of node connectivity, not one slow application startup |
| Cilium logged API heartbeat failures and HTTP/2 connection loss to `91.98.8.79:443` | Control-plane communication was affected independently of Kura's DNS lookup |
| CPU about 1%, memory about 19%, no current pressure conditions, no NIC error accumulation or meaningful local queue backlog in the samples | The sampled evidence does not support CPU, memory, or local traffic-shaper saturation; it cannot rule out earlier transient saturation |
| Normal and absolute server DNS lookups timed out within a three-second budget; direct server Service IP access returned HTTP 200 in about 0.6–2 seconds | DNS-dependent bootstrap was an additional recovery obstacle |
| A blocked replica began serving after mapping the same server hostname to its existing Service IP | Restoring control-plane name resolution was sufficient to unblock that replica without a runtime release |
| Host TCP connections to the API showed RTTs of 275–343 ms, with roughly 331 KB and 28 KB retransmitted on two sampled sockets | Network impairment persisted after application recovery; these cumulative counters are not a packet-loss percentage |

Bounded host-network tests after recovery gave:

| Destination | Samples | RTT min / average / max |
| --- | --- | --- |
| Local gateway `100.64.0.1` | 6 | 0.104 / 0.153 / 0.199 ms |
| Cloudflare anycast `1.1.1.1` | 5 | 0.949 / 0.969 / 0.983 ms |
| Kubernetes API `91.98.8.79` | 6 | 290.591 / 315.926 / 322.386 ms |
| OVH US East peer `40.160.26.218` | 5 | 438.548 / 461.417 / 468.548 ms |

Those short ICMP samples had no loss; earlier application timeouts and TCP
retransmissions remain separate evidence. The API traceroute was fast through
`be101.waw1-oza1-g2-nc5.pl.eu` (1.177 ms) and
`waw-wa2-sbb1-nc5.pl.eu` (0.895 ms), then approximately 320 ms at
`be103.fra-fra15-sbb1-8k.de.eu` and onward to
`core23.fsn1.hetzner.com`. Router reply handling, ECMP, and asymmetric return
paths mean this is not proof that the Warsaw–Frankfurt link itself is faulty.
It is a concrete route to escalate and compare from both ends.

A simultaneous comparison starting at 15:35:51 UTC used the same host-network
ICMP probe and destination, `91.98.8.79`, from four OVH regions:

| Source region | Source IP | Replies / sent | RTT min / average / max |
| --- | --- | --- | --- |
| Warsaw | `57.128.235.80` | 7 / 10 | 518.844 / 527.807 / 536.580 ms |
| US East | `40.160.26.218` | 10 / 10 | 93.683 / 93.707 / 93.747 ms |
| US West | `15.204.109.107` | 10 / 10 | 163.676 / 163.696 / 163.751 ms |
| Singapore | `15.235.229.63` | 10 / 10 | 187.350 / 187.362 / 187.384 ms |

All four nodes reported Ready when checked during this run; the comparison
nodes had no recent Ready transition. The Warsaw control probe to `1.1.1.1`
captured four replies at 0.955–0.980 ms, but its output ended before the final
summary, so no complete loss statistic is claimed for that control. The
API sample does show three missing replies out of ten; it is not a sustained
30% loss estimate. Different geography prevents treating the other regions'
RTTs as Warsaw's expected baseline, but Warsaw being markedly slower than
all three distant sources strengthens the case for an impaired path.

OVH's public status page listed Warsaw electrical maintenance that day, but
the affected rack was not matched to this server and the node's boot ID did
not change during the observed recovery. Do not assign the outage to that
maintenance without provider confirmation.

## Later recovery observations

At approximately 16:03 UTC, an explicitly approved, Warsaw-only host OUTPUT
redirect sent API connections for `91.98.8.79:443` to the existing control-plane
member `91.99.121.226:6443`. It preserved the original endpoint's TLS identity,
cluster CA verification, and credentials. Human access continued through the
Pomerium gateway. A host-local timed rollback was armed before the change;
at 16:12 UTC it was deliberately extended to 16:42:22 UTC.

Initial verified API requests completed in 81–116 ms, the node renewed its
lease, and Cilium's recent API warnings stopped. At 16:15 UTC, all 11 then
published regional readiness endpoints returned 200. The original inventory
had changed through independent instance lifecycle activity; these checks
must not be compared as though all original 22 instances still existed.

Application recovery remained incomplete. An authentication probe with a
deliberately invalid, non-secret token returned the expected 401 in 82 ms on
a replica with the existing server-hostname mapping, but 503 after 6.1 seconds
on the replica still depending on DNS. These were backend-reachability probes,
not successful authenticated cache downloads. Absolute hostname and direct
Service-IP probes also showed intermittent connection failures, so a DNS
bypass alone does not establish a repaired network.

At 16:31 UTC, the node still had a fresh lease and 23 of 26 regional pods were
Ready, but another API probe timed out and the failing replica again returned
an authentication-backend 503. Direct control-plane probes at 16:32 UTC ranged
from 133 ms to 2.03 seconds. The workaround is temporary and does not establish
incident resolution. Further hostname mappings were prepared but had not been
applied under the API-route-only elevation.

## Failure chain

1. The node repeatedly lost timely contact with the Kubernetes API. DNS and
   remote peer/control-plane requests were also slow or timed out.
2. Kubernetes' admission-injected 300-second `NoExecute` tolerations expired.
   Both colocated replicas could be deleted in the same partition. A
   disruption budget does not serialize taint-based deletion.
3. These were local-volume pods: deleting them did not move their volumes or
   produce a replica on an independent healthy host. It discarded warm
   processes and forced bootstrap on the same impaired node.
4. Restarted runtimes required initial managed discovery before becoming
   Ready. DNS-dependent requests could not complete, extending the outage
   after the node reconnected. Initial discovery must remain a readiness
   gate; bypassing it would serve from an incomplete peer view.
5. The regional ingress had no Ready backend for affected instances and
   returned 503. A stalled Cilium agent also blocked placement until it was
   replaced. Restarting Cilium restored agent readiness but did not remove
   the measured upstream latency.

A separate template rollout changed the OTLP hostname to an absolute name
around 14:19 UTC and added replacement activity. It happened after the
recorded network failures began; it is not evidence of the initial cause.

The standby placement is intentional: `instancePodAffinity` prefers
colocation for rollout continuity and local replication. The architecture
expects cross-region recovery for box loss. Replica count therefore cannot
be used as a statement of host-level availability.

## Recovery and remaining temporary state

Under the human-approved, one-hour production elevation starting at 14:27 UTC:

- Set all 22 EU East StatefulSets to `OnDelete` to stop automated rolling
  replacement during recovery.
- Pointed `KURA_CONTROL_PLANE_URL` and `KURA_AUTH_TUIST_URL` in the 22 instance
  specs at the verified existing server Service, `http://10.143.50.132:80`.
  Existing containers retain their original environment until replacement.
- Added marked `/etc/hosts` entries for the server hostname on four blocked
  running replicas; each entry carried an incident marker for removal.
- Replaced the stalled node-local Cilium pod; the replacement became Ready.
- Added indefinite node-loss tolerations to the instance specs and live pods.
  The first live-pod patch incorrectly appended them after the admission
  defaults. Follow-up source review found that the eviction controller uses
  the first matching entry. Corrected 42 existing pods by removing the
  300-second deadlines in place; the other two already had the intended
  policy. Verified the first match for both taints is indefinite on all 44.

No data volumes were deleted and no application release was shipped.
Original strategy, URL, CR toleration, and pod toleration values were saved
in the incident session's `/tmp/kura-*20260922*` backups and
`/tmp/kura-east-pod-tolerations-before-correction.json`. Those local files are
operational backups, not a substitute for this checked-in account.

At 15:22 UTC a further host probe measured API RTTs of 534.7–536.2 ms
(two replies from three probes), while all three probes to `1.1.1.1` answered
in 0.966–0.995 ms. This is a small sample, not a sustained loss estimate.
Cilium continued logging Kubernetes probe timeouts. No further restart was
performed during this recurrence.

The IP overrides and rollout pauses remain temporary. Follow
[the recovery runbook](../node-local-recovery.md) to remove them only after
DNS and control-plane connectivity are stable, one standby at a time. A
controller rollback does not undo those explicit live CR settings. Do not
resume all paused StatefulSets at once.

## Durable changes and rollout

### Implemented: prevent futile node-local eviction

The controller now supplies indefinite `NoExecute` tolerations for the two
node-loss taints on `scw-local-nvme` workloads. Explicit finite or wildcard
instance policies win; network-backed storage is unchanged. It does not
relax scheduling taints, liveness, readiness, or pressure eviction.

Defaults are adopted on creation or runtime-image change, and then retained.
This follows the controller's existing approach for probe changes: shipping
the controller alone must not roll the whole cache fleet. Existing EU East
instances already have the explicit live policy. Other existing instances
adopt it with a subsequent runtime rollout, so controller deployment alone
must not be described as fleet-wide protection.

Indefinite toleration leaves confirmed lost-node recovery to explicit storage
evacuation/recovery. This is appropriate because a bound local PV cannot
relocate on timed deletion. It does not guarantee continued public routing
while Kubernetes marks the node or pod unready.

Validation covers new and existing local instances, image-change adoption,
repeated reconciliation, network/unspecified storage, explicit finite and
wildcard policies, overriding a previously retained default, unchanged
existing pod templates, and preservation of an operator's `OnDelete` pause.
The image-replacement escape hatch now also respects `OnDelete` and positive
rolling partitions, waits for the desired template, and uses UID/resource
version preconditions when deleting a stale unready pod. Recovery pauses
must cover this explicit deletion path as well as StatefulSet rolling updates.
The full controller Go test suite and `go vet ./...` both passed locally.
No production partition has been injected to validate this patch.

### Required operational fix: repair the upstream path

Escalate the source/destination IPs, timestamps, two socket retransmission
samples, traceroute, and fast local/anycast controls to OVH. Obtain a reverse
path sample and provider confirmation of the impaired route. Do not replace
disks, flush Cilium state, change MTU, or increase application timeouts on the
assumption that one of those repairs the measured underlay problem.

Success means stable API heartbeats and DNS, restored regional network
latency, and no renewed eviction/bootstrap cycle under ordinary traffic.
The provider ticket has not been sent as part of this work.

### Follow-up: stable endpoint routing

Client endpoint selection and failover are outside this change. The routing
work is tracked by [spec 95: Per-account cache hostname steered by proximity](https://atlas.tuist.dev/engineering/specs/95),
which proposes one stable account hostname with region-specific DNS records
and health-based steering. This PR changes no CLI code, endpoint-cache
behavior, or client retry policy.

Spec 95's proposed health checks are per-box TCP checks. A gateway can accept
TCP while its application cannot reach an authentication backend, as happened
in this incident. Validation of that work should explicitly cover this partial
failure; a healthy alternative serving region and a signal that detects the
failure remain necessary for effective failover.

Separate-node replica placement and gateway failover are explicitly deferred
to a separate specification. That work must cover local PV migration,
replication lag/read-after-write behavior, network egress, fencing, routing,
and shared regional faults. Merely adding a second host does not implement it.

### Prepared: distinguish lost redundancy from no service

The original `Kura instance below its replica count` rule waits 30 minutes
and describes one surviving replica. Its expression also matches zero Ready
replicas. Treat zero Ready replicas as a separate availability incident, with
a short pending period (proposed two minutes), alongside external serving
probes. Keep the existing warning for reduced redundancy. Correlate regional
failures with node heartbeat loss and DNS/TCP observations.

The PR includes a paused Grafana provisioning payload and a test that feeds
its exact PromQL expression into `promtool`. Rule syntax and fixtures for a
sustained outage, a brief rollout, recovery, a surviving standby, scaled-zero
instances, missing metrics, and missing cluster labels all passed. The rule
is not installed by Helm and is not live: resolve the Grafana folder and
data-source UIDs, preview historical incident data, verify notification
routing and a controlled non-production failure, then enable it. External
HTTP/gRPC probes remain necessary; Ready replica count alone does not prove
that public ingress can reach the process.
