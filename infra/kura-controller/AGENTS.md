# Kura Controller

This module contains the Kubernetes controller that reconciles Kura account endpoint custom resources.

## Scope

- API group: `kura.tuist.dev`
- Primary resource: `KuraInstance`
- Controller output: Kubernetes workload resources for one account-region Kura deployment. The customer plane is fronted by a shared regional ingress (deployed via Helm), not a per-account gateway.

## Deployment Topology

- **Cache traffic (HTTPS)**: each `KuraInstance` with `spec.publicHost` set gets an nginx Ingress on `spec.ingressClassName` (managed regions default to dedicated shared regional Kura ingress controllers). The controller creates a cert-manager `Certificate` per public host against `--grpc-cluster-issuer`; ingress-nginx terminates TLS and streams uploads/downloads to the instance's internal ClusterIP Service on the runtime's plain HTTP port (`4000`). The backend Service is not a Hetzner `LoadBalancer`.
- **gRPC for Bazel (single host)**: gRPC (Bazel REAPI) co-hosts on `spec.publicHost` — there is no separate `grpc.<host>` hostname, and inside the pod there is no separate gRPC listener either: the runtime serves REAPI h2c on the same co-hosted cache port as the HTTP API (`KURA_PORT`, `4000`). Any non-private `KuraInstance` with `spec.publicHost` set gets a second nginx Ingress (same Kura ingress class) on `spec.publicHost`, path-routed to the gRPC service prefixes (`/build\.bazel\.remote\.execution\.v2\.`, `/google\.bytestream\.`) via the `use-regex` annotation, routing to the internal Service's `http` port with `backend-protocol: GRPC` — the Ingress exists only so ingress-nginx renders those paths with `grpc_pass` instead of `proxy_pass`. `spec.grpcPublicHost` is retained only for backward compatibility and is ignored. This second Ingress declares no TLS of its own; the public `Certificate`/Secret covers the shared host. No dedicated gRPC `Certificate` is provisioned (the old `<name>-grpc-tls` cert/Secret are deleted on reconcile). Regex paths are required: a plain `Prefix` path renders as `location /build.bazel.remote.execution.v2./`, which a real method path (`…v2.Capabilities/GetCapabilities`) would not match. The path values start with `/` (the Ingress API rejects a path that does not); ingress-nginx prepends the `^` anchor itself under `use-regex`, rendering `location ~* "^/build\.bazel\.remote\.execution\.v2\."`. **Hard dependency on ingress-nginx:** the path-split relies on the `nginx.ingress.kubernetes.io/*` annotations (`use-regex`, per-location `backend-protocol`), which only ingress-nginx honors — so the IngressClass the Kura Ingress targets must be served by ingress-nginx (Tuist's shared regional Kura ingress controllers are). On a non-nginx controller (Traefik/Contour/HAProxy/Cilium) those annotations are ignored and gRPC silently routes to the HTTP backend via `proxy_pass`. The controller cannot enforce this — it emits the annotations regardless of which controller backs the class — so single-host tightens the ingress-nginx assumption that split-host could have side-stepped per gRPC host. The cutover from the old dedicated `50051` listener was a hard one (no version gate, no legacy Service port), with one transitional exception: the controller still sets `KURA_GRPC_PORT=50051` in the pod env, because pre-cohosted images hard-require it (`required_value` in their config) and would otherwise crash-loop — taking the HTTP cache down, not just gRPC — the moment the new controller rewrites their pod template. With the env present, an instance still pinned below the co-hosted floor starts cleanly and binds its dedicated listener in-pod; it only loses in-cluster gRPC reachability (no Service port routes there anymore), which is the accepted blast radius because Kura is a cache and Tuist is its only operator. Co-hosted images ignore the variable. Remove the env entry (and this note) once the fleet is fully past the co-hosted floor (tracked in #11654).
- **Single-AZ Hetzner**: each managed product region is one Hetzner location (`fsn1`/`ash`/`hil`) represented by a dedicated node pool in the main production workload cluster. Topology spread is hostname-only — three replicas tolerate one node loss, but a location-wide outage takes the regional Kura endpoint down. Cross-region failover is the user's responsibility (provision Kura in multiple regions; CLI/Bazel can target any of them).
- **Primary-pod routing**: the public HTTP/gRPC backend Service selects a single pod via `statefulset.kubernetes.io/pod-name`, not the whole StatefulSet. The mesh replicates writes between pods asynchronously, so fanning a public endpoint across all replicas means a read can land on a pod that has not yet received a just-written blob. Pinning every region's traffic to one primary makes steady-state reads read-your-writes consistent without touching the pure-async write path. Selection is sticky: the controller keeps the current primary (read back from the Service selector) while it stays runtime-routable: Kubernetes Ready, `/status/rollout` serving, writer lock owned, and enough ring visibility for the replica count. If the primary is Ready but runtime-isolated, the controller fails over to the lowest-ordinal runtime-routable pod. If runtime probes are unavailable, the controller falls back to Kubernetes Ready so reconciliation does not flap on transient probe failures. A pod watch re-runs selection on readiness changes. The headless Service keeps the broad selector so peer replication still reaches every pod. This trades read scaling (one pod serves a region's reads) for consistency; deploys stay zero-downtime because the role hands off only to a pod that can see the mesh.
- **Liveness recovery**: planned termination retains the full Kura drain budget, but the liveness probe has a separate 30-second termination grace period. Kubernetes invokes `preStop` for liveness failures too; inheriting the rollout budget would leave an already-unhealthy primary unavailable for minutes before restart.
- **Startup budget**: the startup probe grants 300 seconds (`failureThreshold: 30` at the 10s period), matching `kura/ops/helm/kura/templates/statefulset.yaml` so controller-managed and chart-managed pods agree. Kura opens its store, RocksDB WAL replay included, before it binds the listener that answers `/up`, so store recovery is spent against this budget and not the liveness one. Keep the threshold at the `startupProbe()` call site: `httpProbe` also backs the readiness probe and `livenessProbe()`, where a wider threshold would slow a wedged pod's restart instead.
- **Peer replication mTLS**: by default each `KuraInstance` gets a controller-owned `<instance>-peer-tls` Secret with a private per-instance CA and a peer certificate valid for that StatefulSet's pod DNS names. The runtime mounts that Secret and uses `https://...:7443` plus `KURA_INTERNAL_TLS_*` for artifact replication and internal status traffic.
- **Cross-region peer discovery**: the controller still supports an explicit `spec.peerTLSSecretName` escape hatch that mounts externally managed shared peer material and injects account-scoped discovery (`KURA_GLOBAL_DISCOVERY_DNS_NAME`). Do not enable it by default until the shared certificate SAN model matches the DNS name Kura advertises in `KURA_NODE_URL`. Controller-managed mesh publication uses the public peer plane described below instead of this escape hatch.
- **Public peer publication**: controller-managed mesh instances can expose `spec.meshPublicPeerHost` for self-hosted peers. Cloud regions use a per-instance LoadBalancer Service. Host-network regions keep a per-instance ClusterIP peer Service behind the regional Server Name Indication demultiplexer and publish a `DNSEndpoint` to the region address. Migration from the former account-wide peer LoadBalancer is a restart-safe state machine stored on that legacy Service: repair the fallback first, verify both public paths, observe public Domain Name System cut over, then retain the fallback for two record cache lifetimes before deletion. Deleting the last matching instance also removes that ownerless fallback. Production server builds keep warm handoffs disabled until a stable account-region endpoint binding can switch the customer plane atomically.
- **Per-tenant egress class (shared-tree floors/ceilings)**: for every shaped instance (a `kubernetes.io/egress-bandwidth` pod annotation or `spec.egressGuaranteedMbps > 0`) the controller allocates a stable per-account HTB classid minor (range `0x100`–`0xFFFE`, FNV hash of the account handle + linear probe, persisted as the `kura.tuist.dev/egress-class-id` CR annotation so it never changes for a live account) and renders the `tuist.dev/egress-class` pod annotation (`{"classid","floor_mbps","burst_mbps"}`). The annotation is inert until `infra/egress-tree-agent/` runs on the pod's node; that agent is the only consumer, and the kernel-level enforcement of floors, ceilings, and the node box cap lives there (tuist/tuist#12363) — deliberately not as a per-pod qdisc, which could not arbitrate between tenants and would throttle node-local replica sync. All instances of an account share one id — it keys the tenant's class on every node — so allocation looks across the namespace's KuraInstances and adopts an existing claim before probing. Do not derive the id from anything mutable and do not reuse a live account's id.
- **Per-tenant isolation**: a `NetworkPolicy` per `KuraInstance` restricts ingress to (a) pods of the same instance, (b) same-account Kura peers on the mTLS peer port, and (c) cluster-namespaced peers reaching the co-hosted `http` port only. Egress is unrestricted because the runtime needs to reach the Tuist API and the OTLP collector.
- **Telemetry defaults**: controller-managed Kura pods always get the Prometheus scrape annotations expected by `infra/helm/k8s-monitoring`, the controller injects the cluster deployment environment through `KURA_OTEL_DEPLOYMENT_ENVIRONMENT`, and when the controller's `--otlp-traces-endpoint` flag is set they also get a default `KURA_OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`. Kura uses the same deployment environment for Sentry when `KURA_SENTRY_DSN` is present in `kura-shared-secrets`. `spec.extraEnv` stays authoritative for per-instance overrides.
- **Authorization material**: the pod's `envFrom` on `kura-shared-secrets` carries the credentials that must not live in a `KuraInstance` spec, since anyone with list/watch on the CR can read one. That is the control-plane client secret and `KURA_AUTH_JWT_PUBLIC_KEY`. It must still **never** carry `KURA_AUTH_JWT_SECRET`: a shared secret signs as well as it verifies, and the server's Guardian key also signs API credentials, so a node holding it could mint those — and these nodes are internet-facing. What it carries instead is the public half of a dedicated cache-token keypair (`Tuist.CacheGuardian`, private half `TUIST_SECRET_KEY_CACHE_TOKENS`, ES256), which reads a cache token and cannot mint one. A node that cannot read a token — holding no key, or one from either side of a rotation — falls back to introspection (`Tuist.OAuth.Introspection`) rather than refusing it, so wrong or stale material costs the round-trip saving and not the answers. The value may hold two concatenated PEM blocks while a key is being rotated, because server pods do not roll on this Secret and Kura pods do.
- **Cache-token key rollout order**: the key is installed before it is used, in two separate rollouts, and the Kura side sits between them. First `server.config.cacheTokenKey.enabled`, which only teaches server replicas to verify tokens signed with the pair and changes nothing a client sees. Then `kuraController.cacheTokenPublicKey.externalSecret.enabled`, which puts the public half in `kura-shared-secrets`; the pod template carries that Secret's `resourceVersion` (`kura.tuist.dev/shared-secrets-resource-version`) and the controller watches the Secret, so editing it rolls the StatefulSet and pods pick the value up. `envFrom` is resolved at pod start, so without that annotation an edit would never reach a running node. Only then `server.config.cacheTokenKey.signing`, which starts issuing them. Flipping issuance together with installation means a token minted by a replica holding the key can be introspected by one that does not, reported inactive, and 401 a request that was valid. Unwinding runs backwards, and removing the key waits for the longest cache-token lifetime after issuance stops, or tokens still in flight stop verifying.
- **Retiring a cache box**: annotate the node `tuist.dev/kura-evacuate` and the controller moves that box's cache pods off it one replica at a time (`controllers/node_evacuation.go`). A cache PV is a local-path directory pinned to its host, so a pod cannot follow its volume; the volume is abandoned and rebuilt from a peer. The sequence closes the three ways doing this by hand goes wrong: at most one replica moves per pass, the primary moves LAST (so traffic never lands on an empty volume), and the next move waits for the previous pod to report `backfill_initial_cycle: complete` on `/status/rollout` rather than merely being Ready. Readiness is not the same signal: a pod latches ready at a ring-fullness threshold, so it can be ready and still filling. It is a deliberate annotation rather than the node's cordon, unlike the runner fleet's equivalent: reaping an idle runner poller is free, while moving a cache pod spends a region's warm cache, so an operator cordoning a box to look at something must not trigger it. With nowhere to land (no Ready, unmarked node matching the instance's `nodeSelector`) it does nothing, since Pending pods and an unreachable region are worse than a box that stays up until its replacement joins. The `kura-cache-skip` `MachineDrainRule` covers the other path, where a box is deleted without evacuating first: it stops the drain deadlock but gives up the cache.
- **Per-account disk ceiling**: `spec.storageSize` is both the PVC's requested size and the enforced ceiling. On the local-path cache pools the PV is a directory on the node's `/data`, so the size on the claim bounds nothing by itself; the provisioner's setup hook turns it into an XFS project quota (byte + inode) on that directory, and refuses to create the PV if it cannot verify one on a node that could enforce it. The pod's `ephemeral-storage` request is separate and stays a *request*: it is what the scheduler bin-packs against, while the quota is what the kernel enforces. Do not add an `ephemeral-storage` limit to close the gap: a limit is enforced against the pod's writable layer, logs and emptyDir, none of which is where the cache lives, so it would evict on the wrong signal while leaving real consumption unbounded. See `infra/helm/tuist/templates/kura-fleet-storage.yaml` and the disk-layout section of `infra/cluster-api-provider-tuist/AGENTS.md`.
- **PVC retention**: the StatefulSet uses `whenDeleted: Delete` so a destroyed `KuraInstance` releases its hcloud volumes, and `whenScaled: Retain` so a replica scaling event keeps its cache.
- **Resource limits**: the controller sets bounded snapshot, manifest, and metadata read-cache budgets sized for the managed memory profile. It deliberately does **not** set `KURA_METADATA_STORE_WRITE_BUFFER_POOL_BYTES`: pinning it to 32 MiB (here and in `values-managed.yaml`) came out of #12117's memory-pressure work rather than any RocksDB requirement, and because the pool is built with `allow_stall = true`, a pool that small saturates on one write burst and blocks every writer inside RocksDB (#12556). Left unset it derives `memory_limit / 32` clamped to `[16, 128]` MiB, which scales with the instance instead of being uniform regardless of size. `spec.extraEnv` remains authoritative when an instance needs a different cache budget. It deliberately does **not** set `KURA_FILE_DESCRIPTOR_POOL_SIZE`, `KURA_MEMORY_SOFT_LIMIT_BYTES`, or the other runtime-shaped limits: Kura derives those at startup from the pod's control-group memory limit and open-file resource limit. Tune the pod-level memory profile instead. A pod picks up a changed limit only on restart, because Kura reads its cgroup once at boot.
- **Memory floor and ceiling**: `spec.memoryFloorMib` is the pod's `requests.memory` and `spec.memoryCeilingMib` its `limits.memory` (defaults 2Gi/4Gi when unset, which is the shape every CR had before the profile existed). They are deliberately unequal, so pods are Burstable, not Guaranteed.
  - The **ceiling** is what the runtime reacts to: Kura's soft and hard watermarks are 60% and 85% of the cgroup limit, and the public response-stream admission pool is half of what remains above the hard watermark. That makes the ceiling the knob that sets how large a client burst a pod absorbs before it sheds with `503`. Those pools are semaphores, not allocations, so ceiling headroom costs nothing until a burst arrives.
  - The **floor** is the standing reservation the scheduler bin-packs against node allocatable. It is sized from an instance's idle footprint rather than its peak: the shared bare-metal boxes already reserve several times the working set the fleet peaks at, and over-reserving is what caps how many tenants fit.
  - Because ceilings exceed floors, the ceilings on a box oversubscribe its memory and the native `requests.memory` bin-pack cannot see them. `spec.memoryCeilingBinPacked` makes the pod additionally request its ceiling as the `tuist.dev/memory-ceiling-mib` extended resource, which the CAPI provider advertises as a bounded multiple of node allocatable (`shared.MemoryCeilingOversubscription`). It is separate from the ceiling *value* because a pod that requests an extended resource its node does not advertise never schedules — only pools the provider patches may turn it on, while every region still wants a right-sized ceiling.
  - **The floor is only as real as the kubelet makes it.** A pod's request reaches the kernel as cgroup v2 `memory.min` / `memory.low` only when the kubelet runs with the `MemoryQoS` feature gate; without it the floor is advisory and a box that runs out resolves contention by evicting Burstable pods ranked by usage above request — the same fairness ordering, but a kill rather than a throttle. The Linux fleets enable it, along with the node reservations that have to precede it; see `infra/cluster-api-provider-tuist/AGENTS.md`. Any node pool that does not is still correct, just less protected.

## Development

- Run tests with `go test ./...` from this directory.
- Keep generated CRDs in `infra/helm/tuist/crds/` aligned with API changes.
- Keep the controller independent from the Scaleway Apple Silicon CAPI provider. Kura endpoint lifecycle is a product workload concern, not a macOS node infrastructure concern.
- cert-manager must be installed in the cluster before turning on `--grpc-cluster-issuer`. The controller does not provision the issuer itself. The flag name is historical: it now issues only the single public-host `Certificate` (gRPC co-hosts on it; there is no separate gRPC certificate).
