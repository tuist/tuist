# Kura Controller

This module contains the Kubernetes controller that reconciles Kura account endpoint custom resources.

## Scope

- API group: `kura.tuist.dev`
- Primary resource: `KuraInstance`
- Controller output: Kubernetes workload resources for one account-region Kura deployment. The customer plane is fronted by a shared regional ingress (deployed via Helm), not a per-account gateway.

## Deployment Topology

- **Cache traffic (HTTPS)**: each `KuraInstance` with `spec.publicHost` set gets an nginx Ingress on `spec.ingressClassName` (managed regions default to dedicated shared regional Kura ingress controllers). ingress-nginx terminates TLS and streams uploads/downloads to the instance's internal ClusterIP Service on the runtime's plain HTTP port (`4000`). The backend Service is not a Hetzner `LoadBalancer`.
- **One wildcard certificate for the whole fleet**: `--public-tls-secret-name` names a shared TLS Secret in the watched namespace, and every public Ingress terminates on it. The managed clusters point it at `kura-public-wildcard-tls`, a `*.kura.tuist.dev` Certificate the controller itself maintains from `--public-tls-dns-names` (`controllers/public_wildcard_certificate.go`, configured by `kuraController.publicWildcardCertificate`). Onboarding an account then issues nothing: its endpoint serves the moment the Ingress exists, one renewal every 60 days covers the fleet, and the ACME "certificates per registered domain per 168h" limit no longer tracks how fast the fleet grows. The switch is gated on that Secret holding a leaf that passes `VerifyHostname` for the instance's public host, so an instance keeps its own `<name>-public-tls` Certificate against `--grpc-cluster-issuer` until the wildcard actually covers it, and the flag and the Certificate can be deployed in either order. That gate is also what keeps a host the wildcard cannot span on its own certificate, since an ACME wildcard matches exactly one label. The per-instance `Certificate` is deleted only on a pass that reads the live Ingress already referencing the shared Secret, which stops the renewal that instance would otherwise spend every 60 days. Its issued Secret stays: nothing references it, ingress-nginx watches Ingresses and Secrets independently so deleting it would race that controller's own view of the cutover, and it is what makes the cutover reversible, since recreating the `Certificate` over a still-valid Secret adopts it instead of ordering again. Issuance is gated on the wildcard rather than on that read-back, or a freshly created Ingress that has not reached the cache yet would order a certificate for a host the wildcard already covers. The Certificate is a controller-maintained singleton with no owner reference, and it is deliberately not a chart resource. `server-deployment.yml` passes `--rollback-on-failure`, which defaults Helm 4's wait strategy to `watcher`: every resource in the release counts toward readiness, custom resources included, so a Certificate in the chart makes any first issuance slower than the release timeout fail the deploy and roll it back. That is not hypothetical, it took the 2026-09-09 cascade down. Owning it in the controller also keeps it off any one `KuraInstance`, whose deletion would otherwise garbage-collect the fleet's certificate. It is created and repaired but never deleted, since a deploy that momentarily renders no configuration must not drop the certificate every tenant terminates on.
  - The wildcard covers the customer plane only. The public peer hosts (`peer.<handle>-<region>.kura.tuist.dev`) are two labels deep and deliberately have no ACME certificate: that path is SNI passthrough (cloud LoadBalancer, or the region's `ssl_preread` demux) onto Kura's own `:7443` listener, which authenticates both ends against the per-account CA in `reconcilePeerTLSSecret`. A publicly trusted leaf there would have no client half to match.
  - Staging, canary and production each run their own cert-manager and each request the same `*.kura.tuist.dev`. Two limits follow: the duplicate-certificate limit is 5 per week for an identical name set (three environments plus a re-issue is most of it, so do not force one by deleting the Secret), and all three solve DNS-01 at the same `_acme-challenge.kura.tuist.dev` TXT record, so let each environment's Certificate reach `Ready` before deploying the next.
- **gRPC for Bazel (single host)**: gRPC (Bazel REAPI) co-hosts on `spec.publicHost` — there is no separate `grpc.<host>` hostname, and inside the pod there is no separate gRPC listener either: the runtime serves REAPI h2c on the same co-hosted cache port as the HTTP API (`KURA_PORT`, `4000`). Any non-private `KuraInstance` with `spec.publicHost` set gets a second nginx Ingress (same Kura ingress class) on `spec.publicHost`, path-routed to the gRPC service prefixes (`/build\.bazel\.remote\.execution\.v2\.`, `/google\.bytestream\.`) via the `use-regex` annotation, routing to the internal Service's `http` port with `backend-protocol: GRPC` — the Ingress exists only so ingress-nginx renders those paths with `grpc_pass` instead of `proxy_pass`. `spec.grpcPublicHost` is retained only for backward compatibility and is ignored. This second Ingress declares no TLS of its own; the public `Certificate`/Secret covers the shared host. No dedicated gRPC `Certificate` is provisioned (the old `<name>-grpc-tls` cert/Secret are deleted on reconcile). Regex paths are required: a plain `Prefix` path renders as `location /build.bazel.remote.execution.v2./`, which a real method path (`…v2.Capabilities/GetCapabilities`) would not match. The path values start with `/` (the Ingress API rejects a path that does not); ingress-nginx prepends the `^` anchor itself under `use-regex`, rendering `location ~* "^/build\.bazel\.remote\.execution\.v2\."`. **Hard dependency on ingress-nginx:** the path-split relies on the `nginx.ingress.kubernetes.io/*` annotations (`use-regex`, per-location `backend-protocol`), which only ingress-nginx honors — so the IngressClass the Kura Ingress targets must be served by ingress-nginx (Tuist's shared regional Kura ingress controllers are). On a non-nginx controller (Traefik/Contour/HAProxy/Cilium) those annotations are ignored and gRPC silently routes to the HTTP backend via `proxy_pass`. The controller cannot enforce this — it emits the annotations regardless of which controller backs the class — so single-host tightens the ingress-nginx assumption that split-host could have side-stepped per gRPC host. The cutover from the old dedicated `50051` listener was a hard one (no version gate, no legacy Service port), with one transitional exception: the controller still sets `KURA_GRPC_PORT=50051` in the pod env, because pre-cohosted images hard-require it (`required_value` in their config) and would otherwise crash-loop — taking the HTTP cache down, not just gRPC — the moment the new controller rewrites their pod template. With the env present, an instance still pinned below the co-hosted floor starts cleanly and binds its dedicated listener in-pod; it only loses in-cluster gRPC reachability (no Service port routes there anymore), which is the accepted blast radius because Kura is a cache and Tuist is its only operator. Co-hosted images ignore the variable. Remove the env entry (and this note) once the fleet is fully past the co-hosted floor (tracked in #11654).
- **Single-AZ Hetzner**: each managed product region is one Hetzner location (`fsn1`/`ash`/`hil`) represented by a dedicated node pool in the main production workload cluster. Topology spread is hostname-only — three replicas tolerate one node loss, but a location-wide outage takes the regional Kura endpoint down. Cross-region failover is the user's responsibility (provision Kura in multiple regions; CLI/Bazel can target any of them).
- **Primary-pod routing**: the public HTTP/gRPC backend Service selects a single pod via `statefulset.kubernetes.io/pod-name`, not the whole StatefulSet. The mesh replicates writes between pods asynchronously, so fanning a public endpoint across all replicas means a read can land on a pod that has not yet received a just-written blob. Pinning every region's traffic to one primary makes steady-state reads read-your-writes consistent without touching the pure-async write path. Selection is sticky: the controller keeps the current primary (read back from the Service selector) while it stays runtime-routable: Kubernetes Ready, `/status/rollout` serving, writer lock owned, and enough ring visibility for the replica count. If the primary is Ready but runtime-isolated, the controller fails over to the lowest-ordinal runtime-routable pod. If runtime probes are unavailable, the controller falls back to Kubernetes Ready so reconciliation does not flap on transient probe failures. A pod watch re-runs selection on readiness changes. The headless Service keeps the broad selector so peer replication still reaches every pod. This trades read scaling (one pod serves a region's reads) for consistency; deploys stay zero-downtime because the role hands off only to a pod that can see the mesh.
- **Liveness recovery**: planned termination retains the full Kura drain budget, but the liveness probe has a separate 30-second termination grace period. Kubernetes invokes `preStop` for liveness failures too; inheriting the rollout budget would leave an already-unhealthy primary unavailable for minutes before restart.
- **Startup budget**: the startup probe grants 300 seconds (`failureThreshold: 30` at the 10s period), matching `kura/ops/helm/kura/templates/statefulset.yaml` so controller-managed and chart-managed pods agree. Kura opens its store, RocksDB WAL replay included, before it binds the listener that answers `/up`, so store recovery is spent against this budget and not the liveness one. Keep the threshold at the `startupProbe()` call site: `httpProbe` also backs the readiness probe and `livenessProbe()`, where a wider threshold would slow a wedged pod's restart instead.
- **Peer replication mTLS**: by default each `KuraInstance` gets a controller-owned `<instance>-peer-tls` Secret with a private per-instance CA and a peer certificate valid for that StatefulSet's pod DNS names. The runtime mounts that Secret and uses `https://...:7443` plus `KURA_INTERNAL_TLS_*` for artifact replication and internal status traffic.
- **Cross-region peer discovery**: the controller still supports an explicit `spec.peerTLSSecretName` escape hatch that mounts externally managed shared peer material and injects account-scoped discovery (`KURA_GLOBAL_DISCOVERY_DNS_NAME`). Do not enable it by default until the shared certificate SAN model matches the DNS name Kura advertises in `KURA_NODE_URL`. Controller-managed mesh publication uses the public peer plane described below instead of this escape hatch.
- **Public peer publication**: controller-managed mesh instances can expose `spec.meshPublicPeerHost` for self-hosted peers. Cloud regions use a per-instance LoadBalancer Service. Host-network regions keep a per-instance ClusterIP peer Service behind the regional Server Name Indication demultiplexer and publish a `DNSEndpoint` to the region address. Migration from the former account-wide peer LoadBalancer is a restart-safe state machine stored on that legacy Service: repair the fallback first, verify both public paths, observe public Domain Name System cut over, then retain the fallback for two record cache lifetimes before deletion. Deleting the last matching instance also removes that ownerless fallback. Production server builds keep warm handoffs disabled until a stable account-region endpoint binding can switch the customer plane atomically.
- **Per-tenant egress class (shared-tree floors/ceilings)**: for every shaped instance (a `kubernetes.io/egress-bandwidth` pod annotation or `spec.egressGuaranteedMbps > 0`) the controller allocates a stable per-account HTB classid minor (range `0x100`–`0xFFFE`, FNV hash of the account handle + linear probe, persisted as the `kura.tuist.dev/egress-class-id` CR annotation so it never changes for a live account) and renders the `tuist.dev/egress-class` pod annotation (`{"classid","floor_mbps","burst_mbps"}`). The annotation is inert until `infra/egress-tree-agent/` runs on the pod's node; that agent is the only consumer, and the kernel-level enforcement of floors, ceilings, and the node box cap lives there (tuist/tuist#12363) — deliberately not as a per-pod qdisc, which could not arbitrate between tenants and would throttle node-local replica sync. All instances of an account share one id — it keys the tenant's class on every node — so allocation looks across the namespace's KuraInstances and adopts an existing claim before probing. Do not derive the id from anything mutable and do not reuse a live account's id. Per-account overrides (set by staff per region on the ops account page) arrive through the fields that already carry the region's numbers — `spec.egressGuaranteedMbps` and the `kubernetes.io/egress-bandwidth` entry of `spec.podAnnotations` — rendered by the server at the account's effective rates. There is deliberately no separate override field: one number per knob, so the request the scheduler bin-packs, the ceiling Cilium paces and the class this annotation declares cannot describe different limits. Both are pod-spec state, so a retune rolls that region's replicas. The region is only a default; the cap is the box's advertised `tuist.dev/egress-mbps` budget, which the ops form validates a floor against (per node, against everything reserved on it) and `infra/egress-tree-agent` applies.
- **Customer DNS follows the primary**: on host-network regions the gateway is a DaemonSet across every box, so `reconcilePublicDNSEndpoint` publishes a per-account `DNSEndpoint` naming one box, and the account's requests land there. It must name the box running the *primary*, because that is the pod the public Service pins. The pod affinity only *prefers* co-locating an account's replicas, so they can straddle two boxes; targeting whichever pod the API server listed first then named the wrong box, and every request took a cross-box hop that the per-instance NetworkPolicy dropped (see below). List order is also unstable, so such an account's record flipped between boxes each reconcile and external-dns republished the churn. `instanceNodeIP` takes the pod to prefer and otherwise falls back by sorted name, never List order. The peer `DNSEndpoint` reconciles before the primary is known and passes no preference, so it gets the stable fallback only.
- **Replicas may straddle boxes, and that is not a fault**: the pod affinity only *prefers* co-location and the StatefulSet uses `Parallel` pod management, so a region with more than one box can place an account's two replicas apart. A cache PV is a local-path directory with hard node affinity, so once that happens it holds for the life of those volumes rather than settling. Do not reconverge them. Serving is unaffected, because the customer record follows the primary (below); the replicas replicate over the peer mesh on pod identities the per-instance NetworkPolicy already admits; and un-splitting means deleting a warm volume to refill it from a peer, which spends a real cache for placement aesthetics and gives up the box-loss resilience a straddling instance has and a co-located one does not. `releaseNodeLocalVolume` stays for node evacuation, where abandoning the volume is the point. `status.peerRoles[].node` publishes the box each pod is on, so "is the record pointing at a box that can serve" is one read rather than a join across pods, Endpoints and DNS.
- **Per-tenant isolation**: a `NetworkPolicy` per `KuraInstance` restricts ingress to (a) pods of the same instance, (b) same-account Kura peers on the mTLS peer port, and (c) cluster-namespaced peers reaching the co-hosted `http` port only. Egress is unrestricted because the runtime needs to reach the Tuist API and the OTLP collector. Rule (c) does not admit the regional Kura gateway: that runs host-network, so Cilium labels its traffic `host` on its own box and `remote-node` from any other, and a `namespaceSelector` selects pod identities only. Cilium always admits `host`, which is why a one-box region worked and a two-box region answered 504 for every pod the gateway did not share a node with. `infra/helm/platform/templates/kura-gateway-network-policy.yaml` grants that path as a `CiliumNetworkPolicy`, the only construct that can name those identities; an `ipBlock` cannot, because CIDR selectors skip in-cluster node addresses unless `policy-cidr-match-mode` is set.
- **Telemetry defaults**: controller-managed Kura pods always get the Prometheus scrape annotations expected by `infra/helm/k8s-monitoring`, the controller injects the cluster deployment environment through `KURA_OTEL_DEPLOYMENT_ENVIRONMENT`, and when the controller's `--otlp-traces-endpoint` flag is set they also get a default `KURA_OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`. Kura uses the same deployment environment for Sentry when `KURA_SENTRY_DSN` is present in `kura-shared-secrets`. `spec.extraEnv` stays authoritative for per-instance overrides.
- **Authorization material**: the pod's `envFrom` on `kura-shared-secrets` carries the credentials that must not live in a `KuraInstance` spec, since anyone with list/watch on the CR can read one. That is the control-plane client secret and `KURA_AUTH_JWT_PUBLIC_KEY`. It must still **never** carry `KURA_AUTH_JWT_SECRET`: a shared secret signs as well as it verifies, and the server's Guardian key also signs API credentials, so a node holding it could mint those — and these nodes are internet-facing. What it carries instead is the public half of a dedicated cache-token keypair (`Tuist.CacheGuardian`, private half `TUIST_SECRET_KEY_CACHE_TOKENS`, ES256), which reads a cache token and cannot mint one. A node that cannot read a token — holding no key, or one from either side of a rotation — falls back to introspection (`Tuist.OAuth.Introspection`) rather than refusing it, so wrong or stale material costs the round-trip saving and not the answers. The value may hold two concatenated PEM blocks while a key is being rotated, because server pods do not roll on this Secret and Kura pods do.
- **Cache-token key rollout order**: the key is installed before it is used, in two separate rollouts, and the Kura side sits between them. First `server.config.cacheTokenKey.enabled`, which only teaches server replicas to verify tokens signed with the pair and changes nothing a client sees. Then `kuraController.cacheTokenPublicKey.externalSecret.enabled`, which puts the public half in `kura-shared-secrets`; the pod template carries that Secret's `resourceVersion` (`kura.tuist.dev/shared-secrets-resource-version`) and the controller watches the Secret, so editing it rolls the StatefulSet and pods pick the value up. `envFrom` is resolved at pod start, so without that annotation an edit would never reach a running node. Only then `server.config.cacheTokenKey.signing`, which starts issuing them. Flipping issuance together with installation means a token minted by a replica holding the key can be introspected by one that does not, reported inactive, and 401 a request that was valid. Unwinding runs backwards, and removing the key waits for the longest cache-token lifetime after issuance stops, or tokens still in flight stop verifying.
- **Retiring a cache box**: annotate the node `tuist.dev/kura-evacuate` and the controller moves that box's cache pods off it one replica at a time (`controllers/node_evacuation.go`). A cache PV is a local-path directory pinned to its host, so a pod cannot follow its volume; the volume is abandoned and rebuilt from a peer. The sequence closes the three ways doing this by hand goes wrong: at most one replica moves per pass, the primary moves LAST (so traffic never lands on an empty volume), and the next move waits for the previous pod to report `backfill_initial_cycle: complete` on `/status/rollout` rather than merely being Ready. Both routed roles are demoted off a marked node, from one shared node listing (`evacuatingPodNames`): the primary conditionally, only once a replica that is staying is caught up, and the gateway unconditionally, because `chooseGatewayPod` falls back to the primary when nothing else is eligible so the region never loses the role — and because gating it would deadlock the sequence, the standby that has to move first being exactly the pod the complement rule names. Deletion then waits on both planes having actually let go: another pod serving the client Service (`servedByAnotherPod`) and the public peer Service no longer selecting this pod with an address behind the new one (`peerPlaneReleased`). A repointed selector is a write; an endpoint is the fact. Readiness is not the same signal: a pod latches ready at a ring-fullness threshold, so it can be ready and still filling. It is a deliberate annotation rather than the node's cordon, unlike the runner fleet's equivalent: reaping an idle runner poller is free, while moving a cache pod spends a region's warm cache, so an operator cordoning a box to look at something must not trigger it. With nowhere to land (no Ready, unmarked node matching the instance's `nodeSelector`) it does nothing, since Pending pods and an unreachable region are worse than a box that stays up until its replacement joins. The `kura-cache-skip` `MachineDrainRule` covers the other path, where a box is deleted without evacuating first: it stops the drain deadlock but gives up the cache.
- **Rollout health aggregate** ([spec #79](https://hive.tuist.dev/specs/79)): each reconcile polls `/status/rollout` on every pod (one pass, shared with primary selection) and publishes `status.rolloutHealth` with explicit per-field semantics — Ready/Serving as conjunctions over the expected replicas, a ring-consistency flag comparing the runtime's `ring_fingerprint` (digest of the sorted member identities — equal ring *sizes* cannot prove the views match; size comparison remains only as the fallback for runtimes predating the fingerprint), summed counters with per-pod reset clamping (in controller memory; a restart restarts the accumulation), max memory pressure, and the OLDEST per-pod sample timestamp so a frozen report reads as stale. A pod that stops answering keeps contributing its last-known report with its old timestamp. The server's `Tuist.Kura.Rollouts` consumes this as the health authority for the progressive rollout gate.
- **Per-account disk ceiling**: `spec.storageSize` is both the PVC's requested size and the enforced ceiling. On the local-path cache pools the PV is a directory on the node's `/data`, so the size on the claim bounds nothing by itself; the provisioner's setup hook turns it into an XFS project quota (byte + inode) on that directory, and refuses to create the PV if it cannot verify one on a node that could enforce it. The pod's `ephemeral-storage` request is separate and stays a *request*: it is what the scheduler bin-packs against, while the quota is what the kernel enforces. Do not add an `ephemeral-storage` limit to close the gap: a limit is enforced against the pod's writable layer, logs and emptyDir, none of which is where the cache lives, so it would evict on the wrong signal while leaving real consumption unbounded. See `infra/helm/tuist/templates/kura-fleet-storage.yaml` and the disk-layout section of `infra/cluster-api-provider-tuist/AGENTS.md`.
- **PVC retention**: the StatefulSet uses `whenDeleted: Delete` so a destroyed `KuraInstance` releases its hcloud volumes, and `whenScaled: Retain` so a replica scaling event keeps its cache.
- **Two paths replace a data volume, and the signal between them must stay unambiguous**: `reconcileDataStorageResize` replaces volumes one ordinal at a time behind the standby for a grown claim, and `reconcileStaleDataStorage` drops the whole StatefulSet and both PVCs for a claim that can never bind (wrong storage class, or a PV pinned to a node that no longer exists). The stale path runs first of the two and short-circuits the rest of the reconcile, `reconcileStatefulSet` included, so anything it treats as its own trigger it also takes priority over. What both paths do *not* short-circuit is role resolution and the Services that carry it (`selectPrimaryPod`, `selectGatewayPod`, and the client, gRPC, internal-peer, external and public-peer Services), which run above them. A rebuild deletes one ordinal's pod per pass and keeps reporting in progress until the replacement has bootstrapped, so anything left underneath it is frozen for the length of the rebuild — and a Service pinned to a single pod is only correct while it names a live one. With the peer Service pinned to the gateway, which on a two-replica region is the ordinal the primary is not, whichever ordinal a rebuild starts with leaves one of the two pins naming a deleted pod. Hoisting the pins rather than teaching the storage paths to skip the pinned ordinal is the only order that terminates: the pin moves when the pod it names stops being routable, which only happens after the rebuild takes it down, so a rule that refused to take down the pinned pod would refuse forever. The early returns also republish `status.peerRoles` (`publishPeerRoles`), since the server hands every node its role from that document. Nothing hoisted touches a PVC or the StatefulSet, so the storage paths keep the priority their own triggers assume. A terminating PVC is therefore not a trigger: deleting one is the resize path's ordinary first step, and reading it as evidence of a prior recreate escalated a rolling rebuild into a full teardown within the same second (a us-west instance, 2026-09-07). It survives only as a continuation, gated on the StatefulSet being absent, which is true during a teardown and not during a rebuild. The substantive reasons need no gate, because a PVC terminating for one of them still carries it. The stale path also deletes the pods for the ordinals whose PVCs it deletes rather than trusting its foreground StatefulSet delete to collect them: the resize path's Orphan re-template strips exactly that ownership, and an un-owned pod holds its claim open through `pvc-protection` forever.
- **Resource limits**: the controller sets bounded snapshot, manifest, and metadata read-cache budgets sized for the managed memory profile. It deliberately does **not** set `KURA_METADATA_STORE_WRITE_BUFFER_POOL_BYTES`: pinning it to 32 MiB (here and in `values-managed.yaml`) came out of #12117's memory-pressure work rather than any RocksDB requirement, and because the pool is built with `allow_stall = true`, a pool that small saturates on one write burst and blocks every writer inside RocksDB (#12556). Left unset it derives `memory_limit / 32` clamped to `[16, 128]` MiB, which scales with the instance instead of being uniform regardless of size. `spec.extraEnv` remains authoritative when an instance needs a different cache budget. It deliberately does **not** set `KURA_FILE_DESCRIPTOR_POOL_SIZE`, `KURA_MEMORY_SOFT_LIMIT_BYTES`, or the other runtime-shaped limits: Kura derives those at startup from the pod's control-group memory limit and open-file resource limit. Tune the pod-level memory profile instead. A pod picks up a changed limit only on restart, because Kura reads its cgroup once at boot.
- **CPU floor and ceiling**: the pair works the way egress does, a floor that is guaranteed and a ceiling that is enforced, with one asymmetry: the floor is measured and the ceiling is granted. `requests.cpu` is observed per instance and no plan sets it; `spec.cpuCeilingMilli` becomes `limits.cpu` and comes from the plan (`Regions.cpu_ceiling_milli/1`), gated with the memory profile since both are per-tier sizing of the same box. The ceiling is keyed into the server's manifest revision (`cpu_revision_suffix`), because the reconciler re-applies an existing instance only when the desired revision differs from the annotation on the live resource: a manifest field that does not move the revision reaches new instances only, and retuning a plan's number would sit unapplied on every instance already on it. Each reconcile reads the instance's pods from metrics-server's `metrics.k8s.io` API, takes the highest figure across them, and folds it into a ring of 28 six-hour windows held in `status.cpuAutosize`. The request is that ring's peak plus a quarter, rounded up to the next entry of a fixed band ladder whose ends bound the reservation (50m so an idle pod keeps a real share under contention, 3000m so one instance cannot reserve a whole box). Those ends bound what is *reserved*; what an instance may *use* is the plan ceiling below. Four properties matter. The peak is per instance rather than per pod because the pod template is shared and primary selection can hand the serving role to either replica, so both are sized for whichever is busiest. Growth applies on the pass that observes it, while shrinkage waits for eight windows that actually carry a reading, because an instance that looks idle may not have been watched through its busy hours yet. A window that closed unobserved holds `-1`, not zero: it still ages older readings out by wall-clock time, but it is not history, so a gap cannot pass the shrink gate on its own and an outage longer than the ring cannot discard a peak on the first reading back. A reading that could not be taken is not a reading of zero: on a metrics-server error, on the read's own 2-second timeout, or when no pod of the instance reported, the ring is left untouched, since folding zeros in would age real samples out and shrink the whole fleet at once. The timeout is not optional. This read runs before primary selection on the single reconcile worker, so a metrics-server that accepts a connection and never answers would stall failover for every instance in the namespace, not just this one. And the ring lives in status rather than controller memory because the controller restarts on every deploy, and a restart that began the observation again would resize the fleet from no history. A cluster with no metrics-server degrades to the cold-start constant (100m), which is a flat reservation rather than a broken one.
  - **The first decision is seeded from the pod already running, not from the cold start.** An instance the controller has never sized arrives with no `status.cpuAutosize` and a template carrying whatever it ran before, and comparing the first reading against the cold-start constant would drop it there on one quiet sample: the shrink gate would never cover the largest move of all, the one away from the value being replaced. `seedCPURequest` adopts the highest request among the instance's pods before the first observation, so the gate holds that value until enough windows justify moving it. It is a starting point rather than a floor: once a decision is persisted it governs, or an instance that legitimately shrank would be dragged back up by pods still running the value it shrank from. A brand-new instance has no pods to read and keeps the cold start.
  - **The template is the only writer.** The controller resolves the request into the StatefulSet pod template it already owns and rewrites every pass. In-place resize (`pods/resize`, available on this cluster) was considered and not used: it cannot remove the roll, because the template must still carry the value for a *newly created* pod to be bin-packed correctly, and a StatefulSet's revision hash covers the whole template, so a resources change rolls the pods regardless. Resizing as well would add a second writer whose value the next pod creation discards, for the sake of the window between the decision and the roll. Banding is what keeps that roll rare: load has to cross a band boundary, not merely move, before the template changes.
  - **A raise the box cannot fit is bounded, not held.** `status.cpuAutosize.scheduleCapMilli` caps the template request at what the scheduler has shown it will admit. Without it a raise past node headroom deletes the running pod, leaves the replacement Pending, and then holds forever, because a Pending pod reports no metrics and the observation that asked for the raise never moves: a single-replica instance stays down. The cap is set from the request of an unschedulable pod (one band below it, or straight to a scheduled sibling's request, which is proof of what fits), and it is remembered rather than re-derived, or the next pass would raise the request again and roll the pod straight back into Pending. It applies **only when the scheduler names CPU among what it could not fit**: `Unschedulable` is the reason for every scheduling failure, and the short resource appears only in the condition message, so matching the reason alone would shrink an instance blocked on disk, a taint or affinity, which places nothing and leaves the reduced guarantee outliving the real cause. It expires after 24 hours so a box that has since freed up is retried. Note this is recovery rather than admission: the controller's cache is scoped to its own namespace (`--watch-namespace`), so it cannot see the system pods sharing a node and cannot compute real headroom to gate a raise on.
  - **The ceiling is sized against the CFS cliff, not against real use.** `limits.cpu` is a quota refilled every 100ms, and unlike HTB's `ceil` it is not work-conserving: a container that spends the period's budget in the first 20ms stalls for the remaining 80, on an idle box as much as a contended one. So each ceiling sits several times over its plan's measured peak (4000m/2000m/1000m against peaks of 631m/53m/2m), close enough to bound a runaway on the smallest managed box and far enough that a legitimate burst never reaches it. `cpu.max.burst` would soften the cliff further; Kubernetes does not expose it through the pod API, so it is not an option here. **The signal that a ceiling is too low is `container_cpu_cfs_throttled_periods_total` rising on a Kura pod.** It was always zero before this field existed, so any nonzero value is this change.
  - A request above the ceiling is clamped down to it, since the API rejects a limit under its request. That makes the plan ceiling, not the band ladder's top entry, the real bound on what an instance reserves wherever a plan grants one. Zero grants no ceiling and sets no limit, which is what an ungoverned region wants.
  - The ceiling is deliberately **not** bin-packed. There is no CPU equivalent of `tuist.dev/memory-ceiling-mib` and there should not be: putting a burst bound back into the scheduler's arithmetic is the over-reservation this sizing exists to remove. The other three bin-packed dimensions (`tuist.dev/memory-ceiling-mib`, `ephemeral-storage`, `tuist.dev/egress-mbps`) are untouched, and the memory pair stays per-plan in `server/lib/tuist/kura/regions.ex` for the reasons in the next bullet.
- **Memory floor and ceiling**: `spec.memoryFloorMib` is the pod's `requests.memory` and `spec.memoryCeilingMib` its `limits.memory` (defaults 2Gi/4Gi when unset, which is the shape every CR had before the profile existed). They are deliberately unequal, so pods are Burstable, not Guaranteed.
  - The **ceiling** is what the runtime reacts to: Kura's soft and hard watermarks are 60% and 85% of the cgroup limit, and the public response-stream admission pool is half of what remains above the hard watermark. That makes the ceiling the knob that sets how large a client burst a pod absorbs before it sheds with `503`. Those pools are semaphores, not allocations, so ceiling headroom costs nothing until a burst arrives.
  - The **floor** is the standing reservation the scheduler bin-packs against node allocatable. It is sized from an instance's idle footprint rather than its peak: the shared bare-metal boxes already reserve several times the working set the fleet peaks at, and over-reserving is what caps how many tenants fit.
  - Because ceilings exceed floors, the ceilings on a box oversubscribe its memory and the native `requests.memory` bin-pack cannot see them. `spec.memoryCeilingBinPacked` makes the pod additionally request its ceiling as the `tuist.dev/memory-ceiling-mib` extended resource, which the CAPI provider advertises as a bounded multiple of node allocatable (`shared.MemoryCeilingOversubscription`). It is separate from the ceiling *value* because a pod that requests an extended resource its node does not advertise never schedules — only pools the provider patches may turn it on, while every region still wants a right-sized ceiling.
  - **The floor is only as real as the kubelet makes it.** A pod's request reaches the kernel as cgroup v2 `memory.min` / `memory.low` only when the kubelet runs with the `MemoryQoS` feature gate; without it the floor is advisory and a box that runs out resolves contention by evicting Burstable pods ranked by usage above request — the same fairness ordering, but a kill rather than a throttle. The Linux fleets enable it, along with the node reservations that have to precede it; see `infra/cluster-api-provider-tuist/AGENTS.md`. Any node pool that does not is still correct, just less protected.

## Private runner entrance

Runner instances share the managed StatefulSet rollout, preferred co-location, disruption budget, primary routing, mesh and drain. Kubernetes defaults new sets to RollingUpdate; leave a live operator-set update strategy intact. Primary selection prefers full ring visibility but falls back to a fresh Ready/serving writer when no fully joined member remains, so a restarting sibling cannot pin traffic to a dead pod.

`privateHost` opts a private instance into the existing HTTP/gRPC ingress and certificate path, with a host-network ingress class and valid nonempty `clientCIDRs`. Private gateways retain their per-instance certificate and do not select the shared public wildcard, even if a legacy publicHost remains. Private client DNS prefers the selected primary's node initially, then retains its healthy published gateway. Pod List order cannot move it. Public peer DNS stays public. Private gateway-backed pods carry `tuist.dev/host-network-gateway=true`; the managed Helm CiliumNetworkPolicy admits only cache-port traffic from host/remote-node identities, while nginx enforces external client CIDRs.

`controllers/client_gateway.go` observes endpoint availability independently of ring completeness. Shared routing and the endpoint observation run before storage maintenance can return early. `endpointLastCheckedAt`, `endpointReason`, and `endpointMessage` describe the observation; `lastReconciledAt` still describes full workload convergence. The server persists the controller observation time and uses one freshness window for activation and dispatch. Ready certificate conditions may omit observedGeneration, but explicit stale generations are rejected and the hostname must match. Gateway discovery is cached per ingress class for 30 seconds; DNS is cached per host for 60 seconds, with five-second negative caching and a two-second deadline. Keep [private-runner-rollouts.md](private-runner-rollouts.md) current. There is no runner-specific rollout policy or pod deletion engine.
