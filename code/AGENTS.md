# Tuist Code

Once workspace for Tuist Code, a Rust-core client developed alongside the shipping apps in `../app/` and `../android/`. It reports to the Tuist project `tuist/code`. Native frontend sources live in `apple/`, `ios/`, `macos/`, and `android/`; the GPUI desktop frontend lives in `gpui/`. Keep shared business logic in Rust crates, platform UI in Swift/Kotlin/GPUI, and UI dependencies out of the shared core. See `README.md` for build commands and coexistence boundaries.

The apps display as **Tuist Code** and use the `dev.tuist.code` identity (bundle ID, Android application ID and package, Linux app ID) with the `tuist-code://oauth-callback` scheme. Distribution is internal-preview-only: no store uploads, public releases, production OAuth/deep-link registrations, or changes to shipping client behavior beyond the shared macOS session below. iOS device previews and macOS previews are signed after the build by `ios/distribution/bundle.sh` and `macos/distribution/bundle.sh` on a copy of the bundle; only the trusted `main` publication step receives the signing secrets.

On macOS the native client shares the shipping Tuist app's Keychain session and takes the same `credential-refresh-<fnv1a64(canonical server URL)>` file lock before every refresh; the Tuist app's `MenuBarRootView` uses the file-backed `CachedValueStore` so the lock is cross-process. Keep the item layout, lock key, and refresh rules byte-compatible with `cli/Sources/TuistServer/Utilities/ServerCredentialsStore.swift` and `ServerAuthenticationController.executeRefresh`, and never create or delete the Tuist app's items.

## Architecture

Tuist Code follows the [native edges](https://tuist.dev/blog/2026/11/02/native-edges) principles (source: `../server/priv/marketing/blog/2026/11/02/native-edges.md`): a headless Rust core and thin native edges, one per platform.

- **Only what needs the platform lives outside Rust.** Edges render UI and provide platform services: SwiftUI, Android platform views and GPUI views, the Keychain or Android Keystore, presenting the browser for OAuth, platform TLS, installing previews, and other OS integrations. Everything else (sessions and profiles, token refresh, API calls and their validation, pagination, filtering, routing, and deciding what a screen shows) belongs in Rust. Before adding logic to Swift or Kotlin, check whether another platform would need it or whether it could be tested without launching the app; if so, it belongs in the core. Move existing edge logic into the core when you touch it.
- **Stay horizontal to use every CPU core.** Prefer many small Rust crates and Once targets with explicit dependencies over a deep chain or one large crate, so independent nodes compile, test, and cache in parallel and an edit rebuilds only its dependants. Each edge depends only on the core build it needs; no edge depends on another, and no library crate depends on UI. Add a crate or target at a real dependency boundary (a new server API, a feature with its own state), not per file.
- **Parallelize at runtime too.** Run independent requests and computation concurrently and off the UI thread. Serialize only invariants that require it, such as refresh-token rotation, vault writes, and session replacement, and reject stale results by session generation. Do not extend one serialized queue or global lock across unrelated operations.
- **Keep the bridge small.** Edges call the core through `crates/core` operations (C ABI for Swift, JNI for Kotlin; GPUI calls Rust directly), documented in `crates/core/README.md`. The core declares what it needs from the platform as host actions and returns plain values; edges decide only how to present them.

New Apple copy belongs in `apple/Resources/en.lproj/Localizable.strings`; new Android copy belongs in `android/res/values/strings.xml`. Platform code owns localization; the Rust core exposes stable destination IDs through the C/JNI bridge. Once builds must not import Swift CLI modules or the shipping Gradle app. Run tasks with the root mise config excluded as documented in the README.
