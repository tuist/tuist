# tuist-cas-plugin

A Rust `cdylib` implementing the LLVM CAS plugin ABI (`llcas_*`, v0.1) that Xcode's compilation caching loads via `COMPILATION_CACHE_PLUGIN_PATH`. It wraps Xcode's bundled `libToolchainCASPlugin.dylib` for local storage, hashing, and digest handling, and adds Tuist-remote (kura) read-through and write-through on top.

## Why it exists

Xcode's own remote-caching mode (`COMPILATION_CACHE_REMOTE_SERVICE_PATH`, the gRPC socket its built-in remote mode uses, previously served by the now-removed `tuist cache start` daemon) is net-negative on deep module graphs: the remote choreography inside Apple's closed plugin stalls in 30-50s bursts, taking a 274s no-cache build to 325-445s even with all cache hits served in ~2ms. This plugin bypasses that path entirely: the build system runs in its fast plugin-local mode (no remote service path configured), and all remote traffic happens inside this plugin. Measured on the same fixture: warm remote 113.6s against a 105.5s local-replay floor (~8s over, after the kura serving fixes narrowed an earlier ~145s), and 50.4s vs 87.8s no-cache on a shallow-graph app project, which runs at its 50.1s floor.

## Architecture

The crate builds two artifacts from shared modules: the `cdylib` (`libtuist_cas_plugin.dylib`) loaded into compiler frontends, and the `tuist-cas-proxy` binary (the per-machine daemon).

- `src/types.rs` - C ABI types mirroring `llvm-c/CAS/PluginAPI_types.h` (v0.1).
- `src/upstream.rs` - dlopen table for the wrapped Apple plugin. Symbols are split required/optional: Apple's plugin does not export `llcas_cas_store_from_filepath`, `llcas_loaded_object_export_data_to_filepath`, or the on-disk size/prune entry points, so those have fallback implementations in `lib.rs`.
- `src/lib.rs` - the exported `llcas_*` surface. Every string returned to the client is allocated by this crate (the client frees through our `llcas_string_dispose`); upstream strings are copied and released immediately. Read-through: action-cache gets and object loads probe the local CAS first, resolve from the remote on miss (one unix-socket round trip to the proxy), record the association locally IF its graph has landed, and answer. A local action-cache hit whose value object is missing counts as a miss and falls through to that remote path — see the unbacked-hit and write-through-ordering invariants below. Write-through happens ONLY on `llcas_actioncache_put_for_digest`: it writes a durable write-ahead record and fire-and-forget notifies the proxy. Do not intercept `llcas_cas_store_object` for uploads: the compiler stores input-file ingests and dependency-scan trees on every build (warm included), and mirroring those re-uploads the world (~21k redundant uploads per warm build when we tried).
- `src/proxy_proto.rs` - the length-prefixed wire protocol between the plugin and the proxy over a unix socket (RESOLVE / PUBLISH / INVALIDATE / FETCH_OBJECT / DRAIN ops), guarded by a `PROTOCOL_VERSION` byte so a stale proxy left running across a CLI upgrade is rejected rather than misparsed (the plugin degrades to a local miss). v2 changed RESOLVE's semantics (see the non-blocking resolve bullet), which is exactly the kind of change the version byte exists for. DRAIN was NOT such a change and did not bump it: the frame layout is untouched and a proxy that predates the op answers `bad op` through the STATUS_ERROR its caller already handles, where a bump would instead make a stale launchd proxy reject every request from every build on the machine until it restarts.
- `src/proxy.rs`, `src/bin/tuist-cas-proxy.rs` - the per-machine proxy: one long-lived process owns the REAPI channel(s), the resolved-key map, the global known-local set, and all publications, multiplexing every project on the machine by REAPI instance (`account/project`). It opens the same on-disk local CAS the compilers use and materializes fetched value graphs into it. Keeping per-process cost thin here is what holds warm builds near the local-CAS floor: any fixed cost is multiplied by thousands of short-lived frontends.
- **Non-blocking resolve** (protocol v2): action-cache gets are issued from swift-build's task-setup path — the llbuild engine thread that schedules every task in the build, verified by sampling (`BuildEngine::build → demandRule → CommandTask::start → ClangCachingMaterializeKeyTaskAction.taskSetup → getCachedCompilation → llcas_actioncache_get`) — so a RESOLVE must never wait on a graph fetch. The proxy replies with the value digest right after the action lookup and moves the fetch+store to a background materializer pool. Correctness holds through `pending_objects`: before any reply, every graph node's fetch instructions (blob digest or server-inlined bytes) are registered, and a demand load that outruns the materializer produces its object through FETCH_OBJECT (present → yes; pending → fetched inline on the compiler's worker thread; otherwise a genuine not-found — which Swift downgrades to a `cache replay failed` warning + recompile, while clang fails the build, which is why fetch instructions are retained after materialization and also cover locally-published graphs via the publisher's node cache). Retained instructions are capped (~100B each, cleared past a ~100MB backstop no real workload reaches) because they stopped being the last line of defense: a digest neither map knows is reconstructed from the instance snapshot's node table — which also covers a RESTARTED proxy, whose maps are empty while Apple's persistent local action cache keeps serving associations that never pass through RESOLVE (FETCH_OBJECT even re-binds the path and triggers the snapshot fetch when it arrives before any resolve).
- `src/reapi.rs` - the remote transport: the Bazel Remote Execution API (REAPI) over gRPC/HTTP-2 to kura (TLS with system roots for public `https`, plaintext h2c for private-network endpoints). An llcas action key `K` maps to the ActionCache key `Digest{sha256(K), len(K)}`; each llcas node is one CAS blob whose content is the zstd-compressed `"TCP0" | u32 ref_count | (u32 len | digest)* | data` frame, addressed by sha256 of that content; the ActionResult is the closure manifest (one OutputFile per node, `path` = the node's llcas digest in hex root-first, `digest` = the blob's sha256), so a reader learns every blob it needs in one round trip. The lookup sends kura's `inline_output_files: ["*"]` extension, so against a current kura the response also carries the blobs' frame bytes inline (best-effort, within the server's response budget) and the whole resolve is a single round trip; blobs the server did not inline (older kura, budget exhausted) are fetched via `BatchReadBlobs` as a fallback batch. Publish-path existence probes use `probe_action` (the same lookup without the inline hint) so they don't make the server materialize graphs whose bytes the publisher discards. Retries: gRPC calls retry up to 3 times (first retry immediate, then short backoff); `Internal`/`Cancelled` retry only when the status's error-source chain shows a local h2/hyper transport failure (kura's graceful GOAWAY connection rotation), so trailer-borne server errors and the client's own RPC timeout stay terminal. Publication is `FindMissingBlobs` -> `BatchUpdateBlobs` (missing only, so cross-process upload dedup is server-side) -> `UpdateActionResult` LAST, so a reader can never observe an entry whose graph is incomplete.
- `src/prefetch.rs` - a shared worker-pool primitive used for the prefetcher (walks ref graphs after an entry hit so demand loads along deep module chains are local instead of one round trip per node; droppable on dispose) and the publisher/uploader. Bounded drain on teardown; anything still queued is left as a durable write-ahead record that a later process or the proxy sweeps, so uploads survive short-lived compiler frontends exiting.
- **Snapshot pre-materialization**: when a snapshot lands, the proxy queues graph materialization on a dedicated small pool (demand-priority jobs never queue behind it) — bulk content warming with no local state. Warming follows the snapshot's wire order (the server encodes newest-first) and stops at a node budget: a shared namespace's snapshot carries every project's history, and warming all of it pulled several times one build's content over the link the demand loads share; the newest keys — the ones a build about to run actually needs — warm first, and everything past the budget stays resolvable per key and self-heals on demand. This replaced the deleted read-ahead/keylog mechanism, which pre-resolved the PREVIOUS build's key list from a machine-local log: that was memoization of a prior local build faking a remote warm pull, useless on a cold machine, and the serial-demand problem it mitigated (measured 702s warm vs an 88s floor at ~60ms RTT) is now solved structurally by the snapshot plus non-blocking resolve.
- **Action-cache snapshot**: at startup (for every instance the persisted registry knows) or on an instance's first resolve, the proxy fetches, in the background, kura's instance-wide snapshot — the complete key→value map with a deduplicated node table, served through a reserved action key (`tuist-actioncache-snapshot/v2`) on the ordinary `GetActionResult` surface (an old kura answers not-found and the per-key path continues unchanged; the server serves a cached index instantly and reconciles it in the background on a ~60s freshness window, so fetches cost transfer, not a namespace scan). Once ready, resolves answer locally from it, full manifest included, so fetch instructions register synchronously and there is no unknown-object window; materialization flows through the background jobs and batched blob reads. This is the Bazel complete-metadata-up-front model taken further (Bazel pays one `GetActionResult` per action; this answers every key from one round trip), and it makes a completely cold machine — no keylog, no prior build, an agentic sandbox — resolve like a warm one. Keys the snapshot lacks (published after it was taken) fall through to the per-key path. The proxy's maintenance loop keeps snapshots fresh and BOUNDED: delta refreshes every ~2 minutes (a `tuist-snapshot-after:<watermark>` hint returns entries at-or-after the watermark — inclusive, since millisecond versions are not unique; boundary re-sends merge idempotently and only genuinely new keys are pre-materialized), a full refetch every ~30 minutes (deltas only add — the full fetch re-applies the server's eviction gate), an hourly retry for instances whose server had no snapshot support, and cache bounds of at most 8 instances with idle ones evicted after an hour.
- **Per-key overhead**: presence checks use `llcas_cas_contains_object`, never a data load — probes run once per served hit and once per manifest entry, so loading bytes put real I/O on the resolve path. Publish churn is suppressed at two layers: the proxy drops spool records whose `(key, value)` its resolved map already holds (the client re-puts replayed results at the end of its job — thousands per warm build, measured 12k → ~500), and each frontend skips puts matching associations it received from the proxy in-process. A genuinely recomputed value (different digest for the same key) still publishes.
- **Runner regime**: with the correct configuration (the kura client flag reaching `tuist generate`, so the plugin settings branch bakes `tuist-instance`), a wiped-CAS warm build on a runner VM measures **96.8s ± 3.9 against a 77-83s floor and 193.6s no-cache** — near-floor with NO cache volume, 13.5k hits, zero proxy misses, every blob inlined in the action responses. Persistent `CompilationCache.noindex` (per-account cache volumes) remains a further optimization (75.5s, at the floor), not a dependency. Cautionary tale (2026-07-11): a full day of earlier runner numbers (~240s, worse than no-cache) measured a misconfigured benchmark — generation without the kura flag takes the legacy daemon settings branch (no `tuist-instance`), and the proxy's unprimed-instance path silently answered every resolve as a miss. The proxy now logs unprimed requests; treat a "plugin barely beats no-cache" runner result as a routing failure until proven otherwise.
- `src/analytics.rs` - the proxy's per-node transfer analytics, written to `cas_analytics.db` (bundled SQLite, WAL, background writer) in the exact schema the Swift `CASAnalyticsDatabase` defines, so the existing build-report upload + server (xcactivitylog NIF) pipeline is unchanged.
- `src/token.rs` - bearer acquisition for the REAPI endpoint. The proxy holds no auth logic; it caches a bearer and, when it needs one, shells out to `tuist auth token` (the CLI owns keychain, refresh, and the cross-process lock). Refetched only when the cached JWT is within a small window of its `exp`.

## Hard-won invariants

- Panics must never cross the `extern "C"` boundary or skip worker bookkeeping. Both llcas entry points run under `catch_unwind`; the worker loop decrements its in-flight counter even when a job panics (a skipped decrement wedges the drain-on-dispose and hangs the build service); and the async paths guarantee the client callback fires exactly once.
- The plugin and builtin caching modes use different local CAS directories (`CompilationCache.noindex/plugin` vs `/builtin`); numbers from one do not carry to the other.
- `llcas_cas_dispose` must stop/drain the worker pools before disposing the upstream CAS and freeing state - workers hold references to both.
- A local action-cache HIT does not imply its value graph is present, so its ROOT is probed before it is served. Two independent authors: the store chains generations and a size-driven prune ROTATES rather than deleting in place, copying a graph forward only when it is LOADED (`OnDiskGraphDB::FaultInPolicy` is `FullTree`; `llcas_cas_contains_object` faults nothing in, and this crate probes rather than loads on purpose — see "Per-key overhead"); and the write-through in `actioncache_get_impl` USED TO record the association while the graph was still materializing (see the write-through ordering invariant below). Either way the association outlives the objects it names and NOTHING can retract it: the ABI has no delete at the association or object level, the only deletion primitive is the whole-store `llcas_cas_prune_ondisk_data`, and re-putting a key with a different value is refused while the original survives (`put_for_digest` does not validate that the value exists, which is how the dangling record is written in the first place). Serving such a hit hands the compiler `missing object '0~...'` — a warning plus a recompile on the Swift lane, fatal on the clang one — permanently, because the local hit is what shadows the remote on every later get (tuist/tuist#12245). So `verified_local_get` probes the ROOT (`contains_object`, never a load; always `globally = false`, since a healthy remote answers yes to a global probe and would mask exactly the condition being detected) and reports an unverifiable hit as NOTFOUND so the remote path takes over. It is the ONLY place the local decision lives: the async entry point delegates to `actioncache_get_impl` rather than keeping its own copy of the lookup, which is how it once came to be missing this check. The ROOT only — an interior node that is gone is still served and still fails at load time. The fix for that is NOT a graph walk on the task-setup thread but the two write-side invariants below, which make a present root mean a complete closure at the moment it is published; a walk would spend a load per node, transitively, on the serial path to rediscover what the writer already knew. That is also the repair: a resolve returns the closure manifest and materializes the very objects the association names. Cost is ~12ns per served hit, measured; `tests/unbacked_local_hit.rs::probe_cost` is the record, and the reason the verdict is not memoized.
- The write-through records `key -> value` ONLY when the value's ROOT is already present locally. A RESOLVE replies before materialization finishes — protocol v2 is non-blocking on purpose, because gets run on the serial task-setup path — so putting unconditionally made `actioncache_get_impl` an author of the very dangling associations `verified_local_get` exists to catch, with no prune involved. Reproduced end to end on a real build over an EMPTY store: the store began with nothing, resolves succeeded, materialization did not land, and the build ended holding 9 distinct dangling roots that only the read guard kept out of the compiler. Skipping the put costs one extra resolve for that key, ONCE — the materialized root persists on disk, so the next build's resolve finds it present and records the association then — and costs nothing at all on the warm snapshot path, where the graph is already materialized when the resolve is answered. Deliberately the same ROOT-only depth as the read guard: an interior node that never landed is still recorded and still relies on the load path's FETCH_OBJECT. `deferred_puts` counts the skips on its own dispose line, deliberately NOT folded into `degraded:` — a deferral is the expected outcome whenever a resolve outruns its materialization, so a cold build defers routinely and reporting that as degradation would train the reader to ignore the line that does mean something. The signal is the trend across builds: a count that stays high means graphs are not landing at all, which is a materialization or auth failure rather than a cache one.
- Materialization publishes a value graph's ROOT last, and only when every other node in the closure landed. Skipping a node is a designed outcome (`materialize_manifest` continues past a blob the server did not return, or bytes that do not decode, keeping the fetch instructions registered so a demand load retries), which is what makes "root present, child absent" reachable in normal operation rather than only after a prune — and that shape is invisible to a reader, since the get path probes the root and nothing deeper. Storing the root first therefore published a graph already known to be incomplete. Ordering it last means MATERIALIZATION never publishes a root over a closure it failed to complete, so it stops being an author of the shape the read guard catches. Scope that claim carefully: it is a property of this writer, NOT an invariant of the store. `fetch_object` is a second door into the same store and stores whatever single node it is asked for, with no closure check — necessarily so, since checking one there costs exactly the transitive walk the root-only probe exists to avoid. A withheld root keeps its `pending_objects` instruction (including inlined bytes), so the demand load that follows the served value stores it standalone and the root is present again with the hole intact. From then on the read guard's probe passes and the association is recorded. So "present root implies complete closure" holds for the materializer, and only until the first demand load of that root; what the ordering buys is that this crate no longer CREATES the state unconditionally, not that the state is unreachable. Repair is per object and on demand, not a re-run of materialization: the skipped node's fetch instructions stay registered, and the load that actually needs it fetches it. A long-lived proxy will NOT re-materialize the graph on the next build, because the `resolved` fast path treats a value with registered instructions as good as present (`load_present(value) || fetchable(value)`) and returns the cached Hit without enqueuing another job. That is repair latency, not a safety hole: nothing dangling is published down that path. `stats_incomplete_closures` counts it, on `stats_line` as well as per event, and the outcome is decided AFTER the pass rather than at the root's turn in the loop, in three shapes, because deciding at its turn saw only the first: `incomplete closure, root withheld` when a child was skipped; `incomplete closure, root unavailable` when the children landed and the root's own blob was missing, undecompressible, or undecodable, which means retrying is pointless until the remote can serve that root; and `incomplete closure, root already local` when the root was on disk before this pass (so `missing` never contained it and there was nothing to withhold), which is the shape the read guard cannot catch and therefore the one most worth counting. Counts are against `missing`, the set the pass was responsible for, not `manifest`. Persistently non-zero means the remote is serving entries whose blobs it cannot produce, which is kura's cascade to fix, not this crate's.
- **A snapshot stops serving once its gate is stale.** The per-key path is gated at the server on every call — kura refuses to serve an `ActionResult` whose blobs are gone (`first_evicted_output`). The snapshot bypasses that by construction: it is a bulk dump, gated once when the index was built, so the client's copy is the only thing between an evicted entry and a compiler that fails the build on it. Its authority is therefore how recently it was gated, and that is measured from the last FULL fetch, NEVER the last delta — deltas only ADD, so a view kept current by deltas alone looks continuously fresh while never re-applying the eviction gate. Past `SNAPSHOT_SERVE_MAX_AGE` (twice the full cadence, so a healthy refresh never trips it) resolves take the per-key path instead. What that catches is a refresh loop that stopped, which is reachable rather than theoretical: refreshes are held off on a loaded machine and while a build is active, and CI runners are both. Dropping the snapshot at the call site rather than inside `resolve` also suppresses the view refresh a per-key hit would otherwise queue — that refresh re-ranks a key that fell out of a CURRENT view, which means nothing when the view is stale. Reported once per instance (`should_report_stale_snapshot`), because otherwise the effect is silent: resolves keep succeeding, just a round trip each, so a stuck refresh would surface only as "builds got slower" with nothing naming it.
- A refused (`cache poisoned`) action-cache put is NOT fatal, at either put site. The verification above deliberately drives recompiles on the keys whose associations are stale, so a recompile that is not byte-reproducible reaches this often, and failing there would just trade `missing object` for `cache poisoned`. The exported put reports success and still publishes remotely (the remote becomes the healed truth later builds resolve to, since the local association can never be changed); the internal put in `actioncache_get_impl` serves the resolved value uncached. Such a key stays uncacheable until the store generation rolls — the tombstone sidecar that would fix that properly is not built. Detection matches the error message because the ABI reports every put failure identically, so every put failure is logged and a missed variant surfaces in `TUIST_CAS_LOG` instead of failing a build.
- A store that is COPIED to other machines may not be promoted ahead of its publications. On a Tuist runner the CAS store is folded into the cache image that becomes the account's master, so every host that later clones it inherits this store's `key -> value` associations while its only repair path for an object the store does not hold is the remote. An association whose blobs were still in the publish spool when the VM halted is therefore one NO host can satisfy — and by the invariant above nothing retracts it, so it fails every later build of that key until the store generation rolls. That is the write side of the unbacked-association problem: the read guard stops the crash, this stops the cause. `OP_DRAIN` is what the promoting side asks (`tuist-cas-proxy --drain <cas path>`, exit 0 drained / 3 owed / anything else "could not ask" — deliberately not 1, which is what a failing wrapper returns): it sweeps the path first, because the plugin writes its record BEFORE notifying the proxy and a frontend that died between the two leaves one nothing has queued, then waits for the publisher to go quiet, then counts what the spool still holds. A record is deleted only by a publication that SUCCEEDED, so the count is exact. Two things this deliberately is not. It is not per-instance: the publisher pool is machine-wide and a drain waits out every instance's publications, which is right for the one caller that exists (a runner VM has a single one) and cheaper than tracking in-flight items by path. And it is not a guarantee — a host that panics or a job cancelled mid-upload promotes without ever reaching it, which is why removing the read guard "because promotes are gated now" would be a mistake. It also does not touch the prune's authorship: a graph that rotated forward root-present/interior-missing was never in a spool, so no drain can catch it.
- A per-blob `RESOURCE_EXHAUSTED`/`UNAVAILABLE` on a `BatchReadBlobs` response entry means the server is briefly declining a blob it holds (kura zeroes its per-request REAPI materialization budget under memory pressure), NOT that the blob is gone. `batch_read` must re-request those with bounded backoff; the action-result materialization path also retries `NOT_FOUND`, because the action result may be visible a moment before its blob. Ordinary demand fetches still treat `NOT_FOUND` as a cache miss. The RPC-level retry (`retry_call`) does not cover these per-blob statuses: the call itself returns OK with the rejection riding on each entry. Only persistent pressure declines arm a per-`Remote` backoff so a build's thousands of reads do not pile the retry ladder onto an already-struggling node.

## Configuration (environment)

The plugin never talks to kura itself: all remote work goes to the per-machine proxy over a unix socket. It finds the proxy at `TUIST_CAS_PROXY_SOCKET`, falling back to the well-known socket so a build started outside `tuist` (⌘B) still reaches it. Without a proxy the plugin is a pure passthrough to the upstream plugin, local CAS only.

The proxy is what makes the machine's caching coherent: it holds one REAPI connection and token for every build, sees every publication from both the Swift and Clang lanes (so `upload: false` can be enforced in one place), and owns the trunk snapshot and its ingestion. A per-compiler-process channel could do none of that.

- `TUIST_CAS_UPSTREAM_PLUGIN` - path to the wrapped plugin (default: `$DEVELOPER_DIR/usr/lib/libToolchainCASPlugin.dylib`).
- `TUIST_CAS_PROXY_SOCKET` - unix socket of the per-machine proxy; unset falls back to the well-known socket.
- `TUIST_CAS_ACCOUNT`, `TUIST_CAS_PROJECT` - the `account/project` this build's cache belongs to, used to declare the instance to the proxy. Lower precedence than the `tuist-instance` plugin option (see below); when neither is present the proxy falls back to its `cas_path -> instance` registry.
- `TUIST_CAS_REMOTE_GRPC_URL`, `TUIST_CAS_TOKEN` - REAPI endpoint + bearer. Read by the proxy (one endpoint/token, many instances); the plugin ignores them.
- `TUIST_CAS_UPLOAD` (default true) - upload policy from `xcodeCache(upload:)`. When false the plugin still serves remote read hits but publishes nothing (no value graphs to proxy or remote). Lower precedence than the `tuist-upload` plugin option (see below).
- `TUIST_CAS_PREFETCH` (default `full`) - how much of the trunk snapshot the proxy pulls before a build asks for it. `full` fetches the snapshot and materializes its whole byte closure ahead of the build. `keys` fetches only the snapshot (one round trip, orders of magnitude lighter than the bytes) and pulls no bytes ahead of time; `tuist setup cache` selects it on CI, where the proxy and the build start together so there is no window to warm in. `0` (also `off`/`false`/`no`/`none`) disables both layers: no snapshot, no warm, every resolve a per-key round trip and every object on demand. Anything unrecognized reads as `full`, so a typo cannot quietly turn caching down.
- `TUIST_CAS_LOG` - append per-process stats (hits, misses, prefetched, cache get/put latency) on dispose.

## Configuration (plugin options)

Xcode passes `-cas-plugin-option <name>=<value>` flags to the plugin via `llcas_cas_options_set_option`, sourced from build settings (`tuist generate` bakes them into `OTHER_SWIFT_FLAGS`). Unlike the environment, these reach **every** compiler frontend — including an Xcode ⌘B build that carries no CLI environment — which is how the plugin learns its instance without the CLI.

- `tuist-instance=<account/project>` - the instance this build routes to; takes precedence over `TUIST_CAS_ACCOUNT`/`TUIST_CAS_PROJECT`. `tuist-*` options are consumed here and never forwarded to the wrapped plugin.
- `tuist-upload=false` - disables publishing for this build (`xcodeCache(upload: false)`); read hits are unaffected. Takes precedence over `TUIST_CAS_UPLOAD`. This is the carrier that reaches a ⌘B build (the per-machine proxy env can't express a per-project setting).

## Development

A source-built `tuist` has nothing bundled beside it, so `ResourceLocator` and the generation mapper find no dylib and fall back to local-only caching. Point them at your `cargo`-built artifacts with two overrides:

```sh
cd cas-plugin && mise run build   # → target/release/{libtuist_cas_plugin.dylib, tuist-cas-proxy}
export TUIST_CAS_PLUGIN_PATH="$PWD/target/release/libtuist_cas_plugin.dylib"
export TUIST_CAS_PROXY_PATH="$PWD/target/release/tuist-cas-proxy"
```

**Through a dev `tuist` (recommended).** With both exports set and logged in (`tuist auth`), run the proxy foregrounded (it resolves the kura endpoint and auto-refreshes the token, like production), then generate + build in another shell:

```sh
tuist cache-proxy --url https://tuist.dev   # hidden command; Ctrl-C to stop
tuist generate                              # bakes the dev dylib path + tuist-instance
```

`tuist setup cache` / `tuist teardown cache` install and remove the same thing as a launchd agent (honoring `TUIST_CAS_PROXY_PATH`).

**Plugin/proxy only (fastest Rust loop).** Run the proxy binary directly and hand `xcodebuild` the dev dylib; the plugin auto-finds the proxy at the default socket. You supply the kura gRPC URL yourself (no endpoint resolution):

```sh
TUIST_CAS_REMOTE_GRPC_URL="<kura grpc url>" TUIST_CAS_TUIST_BIN="$(which tuist)" \
TUIST_CAS_SERVER_URL="https://tuist.dev" ./target/release/tuist-cas-proxy
xcodebuild ... \
  COMPILATION_CACHE_ENABLE_CACHING=YES COMPILATION_CACHE_ENABLE_PLUGIN=YES \
  COMPILATION_CACHE_PLUGIN_PATH="$PWD/target/release/libtuist_cas_plugin.dylib" \
  COMPILATION_CACHE_REMOTE_SERVICE_PATH="<proxy socket>" \
  COMPILATION_CACHE_ENABLE_DIAGNOSTIC_REMARKS=YES \
  OTHER_SWIFT_FLAGS="-cas-plugin-option tuist-instance=<account>/<project>"
```

`COMPILATION_CACHE_REMOTE_SERVICE_PATH` is what `tuist generate` sets, and leaving it out of a hand-run bench measures a different product: it is the only thing gating the build system's Clang lane (`CASOptions.hasRemoteCache`), so without it C and Objective-C cache locally and never remotely. The plugin consumes the matching option rather than forwarding it, so the socket never reaches Xcode's own remote client.

Requires `SWIFT_ENABLE_EXPLICIT_MODULES` and works with Xcode 26.x. `TUIST_CAS_LOG=/tmp/cas.log` appends per-process stats on dispose and `COMPILATION_CACHE_ENABLE_DIAGNOSTIC_REMARKS` prints Xcode's hit/miss remarks in the build log. In a shipped CLI all of this is automatic (`tuist setup cache` + `tuist generate`; the dylib and proxy ship next to `tuist`).

## Kura placement (on-host vs PN node)

The proxy can point at kura wherever it runs; two placements were measured on the CLI fixture (8-core runner VM, all kura perf fixes):

- **On-host** — one kura per runner Mac (served to the VM over the loopback/bridge). Warm build **113.6s** (median of 5). This placement is **not bandwidth-constrained**: the bridge measured 2.34 GB/s and loopback is effectively unbounded, so a very cache-heavy build or many concurrent frontends never contend on a shared NIC.
- **PN node off-host** — a shared kura on a nearby Private Network fleet node (0.89ms). Warm build **118s** (median of 3) — only ~5s slower, since sub-ms LAN is the same latency regime as the bridge. Simpler operationally (one kura per region instead of per-Mac), at the cost of a shared node NIC that could bottleneck under enough concurrent runners.

Build time only diverges at true WAN latency (66ms → warm ~0.76x of no-cache but ~65s over the local floor, since the ~2.5GB namespace fetch costs real round-trips).

**Current decision: rely on the PN kura node** — it is not meaningfully slower and avoids running kura on every Mac. On-host remains the documented fallback for when guaranteed non-bandwidth-constrained per-runner cache is needed.
