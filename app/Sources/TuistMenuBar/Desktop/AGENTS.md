# macOS Desktop

This directory contains the native macOS interface and the shared application lifetime. It lives in `TuistMenuBar` to reuse installation, device discovery, authentication, and progress services without exposing their internals across targets.

- `MacApplicationModel` owns one authentication service, device service, progress reporter, and Sparkle updater for the desktop and menu-bar companion. Its published `DesktopWindow` route follows the authentication service: logged-out users get only the compact welcome window, signed-in users get the main window. Route launch, Dock reopen, Open Tuist, menu-bar actions, and preview-link activation through this state. Both scenes disable automatic restoration and implicit Window-menu commands so the main window cannot be restored or opened while logged out. Authentication changes open the appropriate window and dismiss the other; main-window content is also guarded. Register URL observation once, before any window is presented. OAuth callbacks must not be treated as preview installation links.
- `DesktopLoginView` mirrors the iOS welcome screen's icon, background, copy, primary Tuist action, provider actions, and separate self-hosted entry, while retaining native macOS buttons and an anchored system authentication session. It is not content inside the project window. Render the monochrome Tuist button logo as a template so its contrast follows native button text when the window becomes inactive; preserve original colors for provider logos. Keep the existing HTTPS validation, PKCE, cancellation behavior, and shared credentials store.
- `MacApplicationEnvironment` scopes app requests to a shared Keychain credentials store and in-process API cache. Do not accidentally use the CLI's filesystem credentials or cache defaults on macOS. Use it for structured desktop requests; `ErrorHandling.fireAndHandleError` applies it to user actions.
- `DesktopView` owns authenticated model lifetime and loads project/preview data. `DesktopWorkspaceView` uses a two-column `NavigationSplitView` for Home and a three-column `NavigationSplitView` for Previews, with shared model and navigation state owned above the changing layouts. Home fills the main area with a project heading, adaptive build/test/flaky activity cards from `TuistHome`, and a flat section of three recent previews, rather than a boxed card in a narrow middle column beside an empty detail pane. Own `HomeActivityModel` above layout changes, capture `MacApplicationEnvironment` at construction, and keep its requests/errors independent from previews. Home refresh updates both feeds; browser refresh remains preview-only. Previews retains its native resizable columns for the paginated list and detail. Keep Home extensible without placeholder product sections.
- `DesktopNavigation` keeps section and preview selection independent of view layout. Opening a recent preview switches to Previews and selects it, clearing browser filters only if they would hide that preview. Returning Home hides selection-specific toolbar/menu actions without discarding the browser's selection. Returning to Previews preserves valid selection and filters; project changes clear detail selection while preserving the active section.
- The signed-in navigation shell owns a `TuistProjects.ProjectContext`, displayed above sidebar sections using `ProjectSwitcher`. Selection is scoped to the window; persisted selection/recents are scoped by server and account. Keep account/settings outside project scope.
- `DesktopPreviewsModel` consumes the project context and owns paginated preview data. Search and the native Track pop-up filter loaded previews locally; the toolbar prompt and result count explicitly identify that scope. Tracks are the API's release channels, not Git tags. Load subsequent pages automatically when the list-end progress row enters the clipped AppKit viewport, including when local filters have no loaded matches. Do not treat row creation as visibility: accessibility can instantiate offscreen List rows. Do not add a fixed pagination footer or Load More button. Show an inline retry on page failure without discarding existing rows or retrying in a loop. Reject non-advancing pages and deduplicate overlaps before appending. Filtered result counts belong beside the filter controls, not in a permanent bottom bar. Loading another page expands both results and track choices. Project switching clears search, track filters, and preview detail selection while preserving the active sidebar section. Home stays unfiltered. Request identities and project checks prevent stale responses from replacing a newer selection.
- Define preview actions once in the navigation shell's window toolbar with explicit placement. Share and Open in Browser must not create a second toolbar inside the detail Form. `DesktopCommands` exposes equivalent actions in the Preview menu using the focused window's selection. Keep account controls outside project context. Do not reserve a permanent footer for an idle Ready message; show window-wide activity in the toolbar only while operations are active.
- `DesktopPreviewDetail` reuses `DeviceService` to install previews. Device selection and progress must remain shared with the menu-bar companion. The window's toolbar activity shows installation progress even when no preview is selected, including installations started from a deep link or the menu bar.
- `DesktopSettingsView` lives in the native `Settings` scene and uses a standard macOS `TabView` with General and Account panes, not one tall form or a custom tab strip. General contains the shared `showMenuBarExtra` preference (off by default), update checks, and documentation; account actions remain independent of the selected project. Account always shows the connected server address and lazily displays the optional deployment version through `AppServerInfoService`; missing metadata must not block settings or authentication. The companion is only inserted while authenticated. About is provided by the standard application menu. The main window remains available from the Dock and app menus even when the menu-bar companion is hidden.

Prefer standard SwiftUI macOS controls, system typography, keyboard navigation, selectable lists, contextual actions, and toolbars rather than mobile navigation or custom menu-row styling in desktop screens.

Tests belong in `app/Tests/TuistMenuBarTests/Desktop/` and use Swift Testing. Run the focused `TuistMenuBarTests/DesktopPreviewsModelTests`, `TuistMenuBarTests/DesktopProjectPickerTests`, and `TuistMenuBarTests/DesktopWorkspaceTests` suites with the macOS `TuistApp` scheme. Picker and workspace tests render offscreen AppKit windows with mocked project discovery and storage, without launching the authenticated app or accessing credentials. Workspace tests cover Home/browser layout, selection, filtering, project switching, resizing, scroll-triggered pagination, and finding matches on later pages, and attach screenshots explicitly labeled as sample data.
