# Browser SDK packaging

Once does not import AARs. `dependencies.lock.json` pins the complete published
compile/runtime POM closure of `androidx.browser:browser:1.9.0`: 27 artifacts,
including 16 AARs and 11 JARs. Each entry records its download URL, SHA-256,
source POM URL/digest, and the original requested dependency versions. Conflicts
select the highest requested fixed version per coordinate, not Maven's nearest
dependency. In particular, Core resolves to 1.13.0 and Concurrent Futures to 1.1.0.
The JVM companion artifacts of multiplatform Annotation and Collection are
included. Kotlin stdlib artifacts are excluded because the pinned compiler
already supplies them; Coroutines is a separate runtime dependency and is included.

The lock was generated from real Google Maven/Maven Central POMs and artifact
bytes. Its bounded, one-time resolver accepted fixed versions and exact `[version]`
constraints, compile/runtime dependencies, and only Kotlin-stdlib exclusions.
No dependency required property interpolation or inherited dependency versions.
Dependency-management declarations were not treated as new dependency edges.
The temporary resolver is deliberately not part of normal builds: upgrades require
explicitly resolving and reviewing a new lock, never an implicit online resolution.

## Prepare before Once analysis

From `app/`:

```sh
python3 android/dependencies.py prepare
python3 android/dependencies_test.py
```

Only `prepare` downloads, and only the URLs in the reviewed lock. Every invocation
checks SHA-256, including cached downloads. A mismatch fails without silently
redownloading. Extraction is staged before replacing prepared outputs; a failed
download/digest/extraction check leaves the previous prepared output intact.
Successful preparation removes stale resources and retired artifact directories.

All generated bytes and temporary work live on the workspace filesystem:

```text
.once/vendor-browser/
  downloads/<group>-<artifact>-<version>.<aar|jar>
  index.json
  <group>-<artifact>/
    classes.jar
    res/
    AndroidManifest.xml   (AARs only)
    R.txt                 (when published in the AAR)
```

For example, Browser is `androidx.browser-browser/`, Core is
`androidx.core-core/`, and Coroutines Android is
`org.jetbrains.kotlinx-kotlinx-coroutines-android/`. The coordinate's colon becomes
a hyphen; dots and artifact hyphens remain unchanged. `index.json` records the
coordinate, version, prepared directory, manifest package (null for JARs), and digest.
No binary SDK files belong in source control. AAR `classes.jar` and embedded
`libs/*.jar` become one deterministic `classes.jar`; Java service descriptors and
Kotlin metadata are preserved. Unsafe paths, symlinks, duplicate classes, oversized
ZIP contents, and currently unsupported native/asset/prefab payloads fail closed.

## Once provider/resource integration

The provider consumes every prepared `classes.jar`. Pass all 16 AAR manifests in
stable sorted path order with a declared compiled-resource output for each:

```sh
python3 android/dependencies.py build \
  <SDK36-aapt2> <platforms/android-36/android.jar> <javac> <jar> \
  <browser-r.jar> <R.txt> <resources.apk> \
  <library/AndroidManifest.xml> <compiled-library.zip> ...
```

The seven initial arguments and following manifest/output pairs match the Atlas
resource-script convention. The script links application resources first, then
the library resource archives in the exact supplied order. It uses package
`dev.tuist.app.preview`, min SDK 26, target SDK 35, version code 1/name 0.1.0.
Supply SDK 36's platform JAR and tools; this does not raise the target SDK.
Keep these values/order aligned with the application graph. Outputs are the
library-only R-class JAR, full app/library symbol table, linked resource APK, and
each declared compiled-resource ZIP. Once generates its own application R classes.
Compile/runtime JAR providers include both prepared JARs and `browser-r.jar`;
compiled-resource providers include the ZIPs in the same order as the build call.

The script extracts, but does **not** merge, library manifests. Browser itself
adds no application components. The transitive Core manifest declares its signature
dynamic-receiver permission and CoreComponentFactory. Startup/ProfileInstaller
declare an initialization provider, profile-initializer metadata and a DUMP-gated
profile receiver. These are not implicitly installed by this resource-only
provider; application manifest policy/merging is a separate explicit integration
decision. Do not assume `aapt2 link --extra-packages` merges components or permissions.

After producing the **final APK**, gate delivery on:

```sh
python3 android/dependencies.py verify <aapt2> <R.txt> <final.apk>
```

This compares every app-namespace resource ID in the generated symbol table to
`aapt2 dump resources` of the delivered APK, including AndroidX resources and
normalized dotted style names. Missing/changed IDs and an empty check fail the
build. Successful R-class compilation alone is not a resource-ID validation.
