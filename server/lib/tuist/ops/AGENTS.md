# Ops

## Responsibilities
- Schedule Slack reports for daily/hourly business metrics.
- The hourly sign-up report posts new users and organizations to `#gtm` every day, including weekends. Slack API failures must propagate to Oban for retries.
- Each sign-up report covers the completed UTC hour preceding the job's immutable `inserted_at`, with inclusive start and exclusive end. Never derive its window from retry time or `scheduled_at`. Slack digests show at most 20 accounts with bounded lines and an omitted count so large batches cannot exceed Slack's section-text limit.
- Internal reports authenticate with `TUIST_SLACK_TUIST_TOKEN`, sourced by ESO from `SLACK/tuist_token` in the per-environment `tuist-k8s-<env>` 1Password vault. An `account_inactive` response requires restoring the Slack identity or replacing that credential; code retries cannot repair it. After a secret replacement, ESO must sync and the server pods must reload their environment before validating `auth.test` and channel delivery.
- Query growth stats for users, orgs, projects, and command events.
- Provide bounded, read-only ClickHouse queries and schema discovery for internal operations consumers.
- `FeatureFlags` exposes only its explicit catalog through Atlas workload-authenticated routes. Atlas must authorize dedicated `feature_flags:read/write` scopes and derive the human actor and interface from its authenticated execution context. Customer API credentials cannot use these routes. Shared-identity Slack agents are denied by Atlas, and server writes accept only the `mcp`, `worker` and `api` interfaces.
- Resource evaluation accepts exactly one positive Tuist account/project ID. Resolve a project's owning account in the same query, then batch only applicable shared rules and those actors' overrides. Pass the resulting flag map through the actual feature/identity helpers without touching FunWithFlags' evaluation cache; do not duplicate environment defaults, dependencies or kill-switch inversion in the ops layer. The query budget is two core reads plus at most two rename-eligibility existence checks. Return the serving environment, source flag and effective feature explicitly; these decisions are neither historical exposure nor proof of sticky controller activation or cache convergence. Keep the scoped observability context isolated from the caller.
- Mutations require a current revision, reason and change UUID. Serialize gate writes in PostgreSQL and persist the request, workload principal and before/after state atomically. Identical retries return the original result; conflicting UUID reuse and stale revisions return 409. Publish cache invalidation only after commit. Acquire FunWithFlags' per-flag percentage advisory transaction lock before the table lock, including for clears/resets. This serializes the legacy adapter's entire percentage read-modify-write without reversing its lock order. Advisory/table lock timeouts return `persistence_failed` (503) after rollback; unexpected database errors must still raise. Reject account/project IDs above PostgreSQL int8's maximum before querying and percentages whose normalized ratio underflows to zero before constructing a gate.
- Rollout uses FunWithFlags 1.13's deterministic percentage-of-actors gate, not percentage-of-time. Set a percentage strictly between 0 and 100; explicit actor exclusions retain precedence. Global disable preserves actor/percentage gates; scoped clear restores inheritance. `clear/all` removes every gate, but is not universal feature-off: enabling a kill switch stops its feature, and environment defaults/dependencies can override ordinary gates. Read the catalog description before choosing a rollback.
- Control reads return persisted rules, not a promise of every replica's current decision. PubSub invalidation is best effort and evaluation cache TTL is 600 seconds; storage failures can retain stale cache values. Correlate observed evaluations with target account/project and release, never infer exposure from today's configuration. No automatic health scheduler or correlation-based rollback policy is installed by these tools. A monitored ramp requires explicit baseline/window/minimum exposure and rollback criteria before an agent writes; an error sample alone is not an error rate or causal proof.
- `RunnerConcurrencyLimits` gives Atlas the ops dashboard's runner limit control over the same workload-authenticated routes, alongside a handle-to-account-ID lookup. Writes change one platform through `Runners.Concurrency.update_limits/2` under the limit rows' `FOR UPDATE` locks, require the current revision (which hashes values, `updated_at` and the last change, so dashboard edits invalidate it), a reason and change UUID, and persist request, principal and before/after state atomically. Identical retries return the recorded result; stale revisions and reused UUIDs return 409.
- `KuraRollouts` (`GET /atlas/kura/rollout`, optional `id`) gives Atlas a read-only view of the `/ops/kura/rollouts/:id` page: the active rollout (else the latest), its waves, its unconverged servers with account, observed image and rollout deployment, and its newest events. Resume and abort stay on the ops page.
- `RunnerBilling.update_trial/3` (`PUT /atlas/accounts/:id/runner-trial`) gives Atlas the ops account page's runner trial buttons through `Runners.Trials.start/1` and `cancel/1`, with the `AccountPlans` revision, reason, change UUID and replay contract and its own `runner_trial_changes` audit. The revision is the runner billing read's. Restarting a running trial is refused (`already_on_trial`) because it would move the start and make covered usage read as billable. Cancelling an account with no paid plan is refused (`paid_plan_required`) unless the request sets `confirm_air_limits`: it would drop the account back to Air's caps with no subscription to bill its runner usage on, which is how an account loses runner access by accident. The ops page asks for confirmation in the same case. `add_runner_items` (Atlas only, no ops page button) adds the runner items to a Pro or Enterprise subscription that lacks them on an account off trial, such as one that predates runner Prices, through `Trials.start_billing/1`; it stamps `runner_trial_ended_at` so the day splits there and earlier usage stays unbilled. The trial transition reconciles Stripe inside the request's transaction, so a failure records nothing and leaves the trial as it was.
- `RunnerBilling.activate/3` (`PUT /atlas/accounts/:id/runner-billing`) grants a prepaid pool once, with the same revision, reason, change UUID and replay contract, checkpointing the grant and the cutoff schedule in `runner_prepaid_activations`. The start date cannot be in the future. An order paid in monthly instalments passes an optional `instalments` (2–12) with the **first** instalment's invoice: its USD subtotal times `instalments` must equal `paid_cents`, and the whole balance is granted at activation, however many instalments are paid. That invoice must come from a separate Stripe subscription on the same customer marked `tuist_runner_prepaid_instalments = "true"` (refused with `instalment_subscription_required` otherwise): the strict cutoff schedule is only safe on a runner-only subscription, and `Billing.on_subscription_change/1` ignores marked subscriptions so they never become the account's plan. The grant records the invoice, instalment count and instalment subscription ID. Tuist does not follow later instalments: a failed instalment is collected by Stripe's dunning on that subscription and does not withdraw credit.
- `RunnerBilling.top_up/3` (`PUT /atlas/accounts/:id/runner-billing/top-ups`) adds credit to the account's live pool (applied, started, ending after today; `no_live_pool` otherwise) under the same contract, audited in `runner_prepaid_top_ups`. `grants` lists one entry per platform with its own `paid_cents` and `credit_multiplier`; each becomes a grant scoped to that platform's Prices, expiring with the pool and spent before it (priority 40 against the pool's 50). When the pool covers cache (`covers_cache`), the Linux grant is also scoped to the cache Prices at its own multiplier, since an order's cache rates follow its Linux rates; a top-up without a Linux grant adds no cache credit. The invoice must be the customer's, in USD, with a subtotal equal to the grants' total, and not already used by an activation or top-up. Each platform's grant is checkpointed in `grant_ids` and reconciled by the top-up's change UUID in grant metadata, so a resumed top-up never grants a platform twice. Change UUIDs are unique across activations and top-ups. Prepaid usage notices count applied top-ups in the pool's budget.
- `AccountPlans` gives Atlas the ops account page's plan buttons through `Billing.upgrade_to_enterprise/2`, `start_open_source_plan/1` and `cancel_subscription_at_period_end/1` with the same revision, reason, change UUID and replay contract. Its revision hashes the live subscription rows (including `updated_at`) and the last change, so webhooks and ops page changes invalidate it. Writes lock the account row and insert the change row before calling Stripe, so concurrent requests and reused UUIDs cannot reach Stripe twice; Stripe effects themselves are not transactional, and a request that fails after Stripe accepted it records nothing (the webhooks reconcile the subscription rows). Enterprise upgrades require the Stripe customer's name, email and address or request billing details, as the ops modal does. `schedule_pro` has no ops page button: `Billing.schedule_pro_plan/3` attaches a Stripe subscription schedule that keeps a live Enterprise or Open Source subscription as it is until `starts_at`, then swaps in `get_subscription_items("pro", account)`, restarts the billing cycle and charges automatically. It requires the customer's default payment method, and the plan read does not show the pending schedule; Stripe does. `switch_to_usd` (Atlas only) recreates a live $0 Enterprise subscription priced in another currency in USD through `Billing.switch_enterprise_subscription_to_usd/2`, since Stripe cannot change a subscription's currency and the runner Prices are USD only: it cancels without proration, creates the USD Enterprise items on the same customer with the old collection method and period end, recreates the old items if Stripe refuses, and refuses subscriptions with metered items, seats or an open invoice.

## Boundaries
- Internal ClickHouse inspection uses its own repository and dedicated read-only credentials.
- `Tuist.Release.migrate` reconciles the dedicated ClickHouse user, role, grants, password, and limits before managed rollouts.

## Guardrails
- Preserve the ClickHouse query limits and keep external table functions, cluster table functions, and unrestricted system metadata inaccessible.
