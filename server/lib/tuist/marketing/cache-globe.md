# Cache globe

The public marketing page at `/globe` turns cache reuse into a live display. `/globe?demo=true` runs a clearly labeled illustrative demonstration. Demo data never enters the database or the shared statistics service.

## Data

`CacheGlobe.snapshot/1` reads `kura_usage_events`, which already stores the serving region, request count, byte count, and reporting window. It exposes only totals for the seven public managed serving regions (the ones Kura enables in production), each placed at its datacenter's city. Private runner regions, unknown regions, uploads, and peer replication are excluded. Region coordinates represent serving areas; they are not developer locations or precise machine locations.

The large counter is **download requests**, not unique binaries, builds, or estimated time saved. Requests can include partial or repeated downloads and different cache artifact kinds. The byte total measures delivery, not unique stored bytes. Both cover reporting windows starting since midnight in Coordinated Universal Time. The recent total covers windows starting in the last five minutes. Usage is reported in batches, so neither the counter nor the lights claims to represent individual transfers at their exact occurrence time.

Hit rates cover the same daily window using existing analytics: Xcode module reuse from `generate` command events (local and remote hits divided by cacheable targets), Gradle local and remote task hits divided by cacheable tasks in build summaries, and Bazel action-cache hits divided by hit/miss lookups. Uploads, content downloads and other clients do not enter the Bazel rate. The overall rate divides summed hits by summed reuse opportunities across Xcode targets, Gradle tasks and Bazel lookups rather than averaging percentages. These analytics describe reported reuse, including local Xcode module and Gradle task reuse; they are separate from the public-region delivery totals. Missing opportunities yield a dash, while measured misses yield 0%. Only aggregate percentages enter the public snapshot.

The delivery query uses `FINAL` to deduplicate retried rollups in the existing replacing table. It has a ten-second execution bound, a fifteen-second client timeout, two query threads, and a 256-mebibyte memory limit. Each hit-rate source is queried independently with the same resource bounds plus a five-million-row read ceiling. These queries read daily windows from monthly partitions without tenant filters, so a busy partition may exceed that ceiling. Query failures are logged and leave only the affected rate and the overall rate unavailable; the other rates and delivery totals continue updating. Each source’s hits are capped at its reported opportunities so inconsistent older reports cannot inflate percentages above 100%. Gradle delivery events are not used for rates because they do not reliably record misses. A single Oban unique worker (`CacheGlobeRefreshWorker`, hosted cron once a minute) is the only process that runs the ClickHouse query and writes the snapshot into `KeyValueStore` (Redis when configured, otherwise Cachex). Every web replica's `Stats` GenServer only *reads* that cache about every 30 seconds and broadcasts over local PubSub — it never takes a cross-replica Redis lock around the refresh. That single-writer design avoids the multi-replica lock stampede that previously raised `RedisMutex.Error`. Viewer count does not change polling frequency. No new customer data or retention policy is introduced. The cached snapshot contains public region totals, fleet-wide reuse percentages, and country-to-serving-region playback estimates. It contains no account, project, node or IP identifiers. The existing older marketing artifact counter remains separate because its underlying daily aggregate counts both uploads and downloads.

### Estimated origins and delayed playback

`CacheGlobeOrigins` reads complete, deduplicated public download windows from ClickHouse and loads the active accounts' origin evidence in one PostgreSQL batch. An account's last seven UTC dates of cache-using runs determine its origin shares; endpoint-resolution shares are used only when it has no run evidence. Each account's own measured downloads are allocated proportionally across its shares, then aggregated across accounts. There is no cross-account fallback: accounts without origin evidence are omitted rather than assigned to a random country. Stored labels without coordinates have their shares omitted, not redistributed to known ones. Shares are normalized over attributed observations only; the existing rollups do not count unattributed observations, so their fraction cannot be recovered and the resulting distribution is explicitly an estimate. Subdivision labels collapse to country-level representative coordinates from Google's canonical DSPL country dataset (BSD-3-Clause, attribution retained in `CacheGlobeLocations`). This is a static country-to-coordinate table, not an IP-geolocation database or a new collection path.

The public origin entries contain only country coordinates, serving region, reporting-window start and duration, and estimated download volume. They are not exact downloader locations, individual request paths, or a measurement of download volume per country. The geography is inferred from control-plane observations, which may reflect CI or corporate egress locations. These estimates never change the measured daily counters or hit rates. A country-to-region reporting-window cell is first published only when at least **three distinct accounts** contribute positive estimated volume and **no account contributes more than 50%** of its estimated volume. Multiple labels, nodes or rows from the same account are combined before the dominance check and do not increase the contributor count. Sparse or dominated cells are omitted, not reassigned; contributor identities, counts and dominance statistics never enter the public snapshot. These are publication safeguards, not a claim of formal anonymity or differential privacy.

The unique refresh worker freezes each released cell's value in a shared Redis playback journal (`marketing-cache_globe-playback-v1`, 20-minute TTL). Late reports or changed origin mixes never revise an already released cell, preventing subtraction of successive values from isolating one late contributor. This deliberately undercounts late arrivals in the visualization without changing measured counters. Old entries are pruned to the sixteen-minute source horizon and the journal is bounded to 10,000 cells. On a missing, corrupt or expired journal, the worker establishes a new watermark and never re-releases windows starting before it. New windows warm up normally through the playback buffer. The journal is written successfully before any new cells enter the public snapshot.

Country flows require shared Redis and fail closed if the journal cannot be read or written; they never use per-replica Cachex fallback, which would allow inconsistent re-publication. Measured counters retain the existing Redis/Cachex behavior. The journal contains only already-public cells and its watermark, not account identifiers or private allocation inputs. There are two bounded Redis calls per refresh and no added distributed lock.

The canvas plays each reporting window **at least five minutes behind** its original timestamp. Its delay is `max(300, window_seconds + 240)` seconds: four minutes after the window closes to cover the 60-second Kura flush, delivery and ingest, minute cron, bounded queries, and 30-second web poll, with margin. A normal 60-second window plays five minutes behind; a 300-second window plays nine minutes behind. A batch's estimated volume is spread steadily across its original duration. The backend retains sixteen minutes of windows, covering the longest supported delay plus the longest window and refresh/poll margin. Future windows wait for their turn. The browser advances playback every second, independently of the minute worker refresh and 30-second cache polling, without restarting on repeated snapshots or reconnects. A server-time anchor advanced by `performance.now()` avoids kiosk wall-clock skew and adjustments. A fresh snapshot is not marked stale until its query-cutoff timestamp is more than three minutes old, allowing for the refresh, bounded queries and polling. A valid delayed window can continue playing after current five-minute measured activity becomes idle, including across midnight when today's measured totals are zero. The canvas preserves each route's fractional emission progress across updates and reads initial origins on mount. Arcs keep the measured serving region rather than rerouting to a visually quieter region. Actual quiet periods, missing origin evidence, and reports arriving too late for playback remain gaps: the delay is a buffer, not a claim that sparse or missing activity is continuous. The page labels both estimation and the delay explicitly.

The origin query uses the existing ten-second, two-thread, 256-mebibyte bounds, a five-million-row read ceiling, and a 25,000-row result ceiling. The PostgreSQL read has a five-second statement timeout and the same result ceiling. Expansion stops above 10,000 public playback entries rather than publishing a partial allocation or building an unbounded payload. Origin-read failures add no new cells; already-frozen windows may continue their bounded replay. Journal failures disable arcs without blocking delivery counters or hit rates. Only the existing unique refresh worker runs these reads; viewer count never creates new database queries. No origin estimates are stored in a new database table. The shared snapshot expires 120 seconds after writing; the playback journal expires after 20 minutes. The browser's three-minute stale cutoff measures age from the query cutoff, not from the cache write.

When no snapshot exists, the page shows waiting and no invented value. Query failures preserve the last successful snapshot and mark it unavailable. Browser disconnects and aging observations have distinct reconnecting and delayed states. The globe pauses activity lights when its data is no longer current.

## Visual direction

The page follows the redesigned marketing site's frame without its chrome: only the wordmark linking home above the cache page's hero skeleton (copy bottom-left on a 600px card) and an activity frame of hairline rows for the counters, the seven serving regions, the status line and the display controls. No shared navbar, footer or CTA, so it can stay on a screen. Everything uses Noora tokens and works in both themes.

The globe is the cache page's `DitherGlobe` hook — the stippled sphere on the marketing dither ramp — placed on the hero's right side and bleeding into the card's fade. The page's `CacheGlobe` hook feeds it the seven public serving regions as markers (`data-markers`, then `dither-globe:markers` events): a region with downloads in the last five minutes pulses, an idle one keeps a dim core. Estimated request origins draw as small white dots that launch arcs to their serving region at the delayed reporting window's rate. Live region cells show measured totals since midnight UTC; estimated arc arrivals do not increment them. Only demo arrivals advance illustrative totals. The large counter and regional cells use the same daily window; five-minute counts drive activity lights and main-counter extrapolation between snapshots, while live arc rates come from the reporting windows selected for playback. Full localized regional totals scale together to their cell width using the longest total, instead of spilling into neighboring regions or being abbreviated; the row keeps a uniform figure size and unclipped glow. A snapshot from a new UTC day resets the main counter's extrapolation, so a display left open overnight does not carry yesterday's total forward. Live snapshots carry backend-estimated country origins only where there is existing evidence; demo mode uses illustrative city origins. Nothing connects regions to invented destinations.

Earlier research into Shopify's BFCM globes (layered atmosphere, aggregate-once-then-distribute streaming) informed the data flow; none of that imagery ships with the page.
