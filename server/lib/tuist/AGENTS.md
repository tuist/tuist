# Tuist (Business Logic)

This directory contains the core business logic and domain modules for the server.

## Responsibilities
- Metric automations accept a one-time `trigger_config.apply_actions_to_existing_matches` request on create/update. A fresh request starts a baseline generation even when the condition is unchanged. Baselines recheck matches in bounded batches and serialize publication per alert with a session advisory lock. Each action runs outside a row-lock transaction, between a short preflight check and a durable checkpoint; edits may cancel the remaining work while an authorized action finishes. Clear the request on completion. Silent publication deduplication tokens include the sorted test ID set so changed payloads on retry are not dropped. Read-only match counts enumerate bounded pages and share the baseline metric, trusted-branch validation, and current-state eligibility logic. Condition edits require a fresh opt-in. Omitting the request preserves pending work; explicit false cancels remaining actions. Baseline attempt generations invalidate stale workers; nullable `event_generation` separately scopes recovery history (falling back to `baseline_generation` for existing rows), so opt-ins and cancellations retain active recovery events. Returned action errors are logged and checkpointed without publishing a successful trigger, allowing the baseline and subsequent evaluation to progress.
- Build task summaries can omit CAS-output ID arrays. Expanded-task lookups resolve those arrays inside ClickHouse using both build ID and task key, group duplicate outputs by node ID, and return 20 rows plus a next-page indicator. Neither request parameters nor task summaries should carry the stored ID arrays.
- Machine metrics retain nullable `offset_ms` from the activity log start during archive processing, independently of the upload timestamp, so recorded samples align with build steps. Older samples without offsets keep their standalone charts.
- `Tuist.Builds.Steps` serves paginated, filtered metadata and individual logs to the HTTP API and MCP. Both transports authorize build-read access first. IDs are decimal strings scoped to a build, and list queries never select log text. Availability distinguishes absent step data from a search with no matches.

- Ecto schemas, contexts, and domain services.
- `Kura.Origins` discards counts for deleted accounts when persisting a batch. It locks surviving account keys within the write transaction so concurrent deletion cannot invalidate the batch or discard other accounts' counts.
- External test ingestion uses `Tests.get_test_case_states_at/3` for historical quarantine attribution; current test controls continue using the current-state projection.
- Git history (`Tuist.GitHistory`): the commit graph is keyed by **repository** (`git_repositories` in PostgreSQL: the normalized remote a run reports — host, owner, name — scoped to the account, created on first sight by `repository_id/2`; several projects share one, a fork gets its own), with `git_commits` (generation numbers), `git_commit_parents` and `git_branch_heads` within a window from `settings/1` (server defaults, `TUIST_GIT_HISTORY_*` environment, per-project `git_history_*` columns). Runs record `git_repository_id` (from `git_remote_url_origin`, in `Tests.create_test/1`) and `git_dirty` (uncommitted changes: a dirty run's coverage stays at run level). Clients name the repository by its remote URL on every request: `POST .../tests/git-history/commits/missing` and `.../commits` for the graph (`missing_shas/2`, `record_commits/3`, `record_branch_head/3`), `.../listings/missing` and `.../listings` for a commit's file listing (`missing_listings/2`, `record_listing/4`: every `git ls-files --stage` entry with its blob and mode, in ClickHouse `git_commit_files` keyed by repository and commit, with `git_commit_listings` in PostgreSQL recording which commits have one; uploaded once per commit by a clean checkout, in parts, capped by `commit_file_limit`/`TUIST_GIT_HISTORY_COMMIT_FILE_LIMIT`), and `GET .../tests/git-history/settings` tells them how much to collect. The listing is what coverage measures against (`Coverage.Commits` counts the source files no run measured), where the project's tracked files come from (`tracked_files/3`: `projects.tracked_file_globs` applied to the listing at read time, no server defaults, no per-run snapshot) and where an ancestor's blobs are read (`blobs_at/3`). `ancestors/3`, `nearest_ancestor/4`, `ancestor?/4`, `merge_base/4`, `first_parent/2` and `first_parent_chain/3` (a branch's own history: `branch_commits/3` from the recorded head) walk the graph, pruned by the lowest candidate generation; `prune/2` drops commits beyond the window. Test runs carry `base_branch`, `merge_base_sha`, `is_pull_request`, `pull_request_number`, `git_object_format`, `history_source` and `history_fallback_reason`, and their changed files with hunks land in `test_run_changed_files` (ClickHouse, buffered) for patch coverage. When a run arrives without all of that and the project has a connected GitHub repository with `git_history_provider_fallback` on, `GitHistory.enqueue_completion/2` (called from the tests create endpoint; skipped for a run from another repository than the connected one) schedules `GitHistory.Workers.CompleteHistoryWorker` (queue `git_history`), which runs `GitHistory.Completion` over the `GitHistory.Provider` behaviour (`Providers.GitHub`: pull request, compare and commits endpoints, bounded by `provider_page_budget`) to fill the base branch, merge base, changed files and graph (writing into the connected repository's graph, `repository_id_for_connection/1`), then rewrites the run with `history_source` `provider`/`mixed` and a `history_fallback_reason` for what is still missing. The execution mode rides with the run too (`test_runs.execution_mode` and `test_module_runs.execution_mode`: `parallel`, `serial` or empty), which the CLI derives from the xcodebuild arguments and the xctestrun.
- Test case control-plane flags are `state` (`enabled`/`muted`/`skipped`), `is_flaky` and `is_unskippable` (test selection must always run the test, whatever passing evidence it has). All three flow as `test_case_events` (`marked_unskippable`/`unmarked_unskippable` for the last) through `test_case_states_mv_v2` into the `test_case_states` ledger and `test_case_current_states_mv_v2` into the `test_case_current_states` aggregate, each event moving only its own column; `is_unskippable` is a virtual field on `TestCase`, resolved from the aggregate and never stored on `test_cases`. Exposed on the REST `PATCH .../test-cases/:id`, the MCP `update_test_case` tool, the webhook event enum and the test case page.
- Code coverage (`Tuist.Tests.Coverage`) uses one model for every build system: `coverage_files` holds one row per file per shard report, tagged with `build_system`, the run's `git_commit_sha`, a `scope_kind`/`scope_id` (`run` today; `target`, `suite`, `test` once tests are attributed; part of the sort key), an `evidence_kind` (`observed`; `cached` and `carried` are reserved for reused evidence), `in_repository` (repository-relative and known to Git: the only files evidence may rely on), per-line execution counts, function arrays and branch counters (`xccov` leaves them empty; JaCoCo and LCOV fill them). The #13199 tables `xcode_coverage_files`/`xcode_coverage_runs` are left in place, unread and unwritten (no data was copied; a follow-up migration drops them). `coverage_runs` carries the run totals with `coverage_tool`, `coverage_tool_version` (the Xcode version for `xccov`), `git_object_format` (`sha1`/`sha256`, read off the blob ids), `scheme` and `git_commit_sha`. **Coverage is a property of a commit**: `coverage_commits` (`Tuist.Tests.CoverageCommit`, written by `Coverage.Commits.recompute/3`, scheduled a few seconds after each report by `Coverage.Workers.CommitWorker`, one pending job per commit) holds the union of every run that measured the commit (`Coverage.merged_files_query_for_runs/3`: per path, a line is covered when any run covered it, a file counts once however many schemes compiled it; runs from a dirty checkout never contribute; partial runs do) with the measured set (`schemes`, `partial_schemes`, `test_run_ids`), `unmeasured_files_count` from the commit's listing, `complete`/`completeness` (`signal` from `POST .../tests/coverage/commits/:sha/complete`, the client's `tuist coverage complete`, which `Commits.signal_complete/2` records and which enqueues the gate verdict; `inferred` is reserved) and a `version` bumped per republish, retained like run totals. Retention is a time-to-live per table from `TUIST_COVERAGE_FILE_RETENTION_DAYS` (90: `coverage_files`, `git_commit_files`) and `TUIST_COVERAGE_RUN_RETENTION_DAYS` (365: `coverage_runs`, `coverage_commits`), set at creation and re-applied by `mix tuist.coverage.retention`. Xcode coverage is read from the result bundle by the shared Swift parser (`xccov` report + archive) wherever the bundle is processed: the macOS xcresult processor for uploaded bundles (the CLI writes a `tuist_coverage_manifest.json` with root spellings, the covered files' Git blob ids and a partial flag into the bundle), or the client in local mode (sent as `xcode_coverage`, the API schema `TuistWeb.API.Schemas.Tests.XcodeCoverage`). The parser streams: `xccov`'s output goes to disk, `JSONStreamScanner` walks it one value at a time (the report twice, names first and functions per target second; the archive indexed by byte offset), and each file is written as one JSON line to an NDJSON file, so memory stays flat in the bundle's size (70 MB on the Tuist CLI's bundle and 108 MB at 20× its size, against 416 MB and 7.9 GB when both documents were decoded whole). The NIF returns `coverage_path`/`coverage_partial`/`coverage_file_count` instead of the rows; `XCResultProcessor` moves the file out of the bundle's temporary directory (`relocate_coverage/1`) and `ProcessXcresultWorker` hands it to the run as `xcode_coverage: %{path, partial}` and deletes it after. `Tuist.Tests.Coverage.rows/2` turns that into a lazy stream and `publish/4` inserts and folds totals in one pass, keeping a file's lines only when another shard reported the same path. A report's rows share `inserted_at`, readers use only each shard's latest run-scoped report (so retries replace rather than add), and merge shards per path as the union of lines. Shards report concurrently, so nothing rewrites merged totals on `test_runs`: the run page derives them from the reports, and each report publishes its totals over the shards reported so far to `coverage_runs`, versioned by shards included then newest report, which readers take with `argMax(…, version)`; those totals stay partial until every shard of the plan reported coverage. Only the repository's own code is kept: the parser drops files outside the checkout and dependency checkouts (`.build`, DerivedData, SourcePackages, Pods, Carthage), and in a Git checkout any file Git ignores. Test code (files only `.xctest` bundles compiled, flagged `is_test` by the parser from xccov's `buildProductPath`) is stored with counts only (no line or function arrays) and excluded from totals, targets and files. Excluded paths (`Coverage.ExcludedPaths`: `projects.coverage_excluded_path_globs`, per project only, nothing excluded by default; for generated code) are stored like any file but left out of every figure: `publish/4` folds them out of `coverage_runs`, the readers (`run_summary`, `merged_files`, `targets_for_run`, `list_files`, `line_counts`, and their commit-level twins in `Coverage.Commits`, which take `excluded:` to reuse a pattern) filter them with ClickHouse `match` over one RE2/PCRE-compatible pattern, and the comparison recomputes both sides' totals from their retained files. Changing the globs enqueues `Coverage.Workers.RecomputeTotalsWorker`, which republishes `coverage_runs` in batches (`TUIST_COVERAGE_RECOMPUTE_BATCH_SIZE`, 500) from the runs' retained reports with `version + 1` and the original `inserted_at` (retention unchanged; a later shard report still outranks it) and re-enqueues the affected commits; runs past the file retention keep their totals. Local-mode uploads are deflate-compressed by the CLI. The whole feature is in early access behind `Tuist.FeatureFlags.xcode_coverage_enabled?/1` (FunWithFlags `:xcode_coverage` per account on canary/production, on elsewhere): ingestion drops `xcode_coverage`, the xcresult processor removes the manifest before parsing, and the run page tab is hidden when it is off.
- Coverage comparisons (`Tuist.Tests.Coverage.Comparison`) are **commit against ancestor**: a head (`from_run/2` or `from_commit/2`: the commit, its repository, base branch, merge base and pull request identity as its runs recorded them) is compared with the nearest measured ancestor of its merge base with the base branch (`base_branch`, else the project's default branch; the merge base from the run, or `GitHistory.merge_base/4` from the recorded branch head), walked **first-parent** (`GitHistory.first_parent_chain/3`) within the history window; a commit on the base branch itself starts from its first parent. The branch's own earlier pushes lie between the merge base and the head and are excluded by construction, never by a stored mark (a fast-forward merge, a stacked branch or a rebase would break one), and a commit is never its own baseline. `baseline/2` returns `{:error, %{kind: ...}}` (`no_history`, `no_merge_base`, `no_measured_commits`, `no_ancestor_commit`, `measured_set_mismatch` when the nearest measured ancestor measured a different set of schemes) rather than picking another commit, and `reason_text/1` words it for comments and check runs. `compare/3` gives the commit's union figure (`commit`), the total delta only when both commits measured the same schemes and the head measured them all fully, each scheme's own totals side by side (`schemes`, the rows shown under "any scheme"), per-target and per-file deltas over the unions (on a partially measured head only files some test executed), patch coverage (executable lines inside the hunks of the commit's newest run that recorded changed files × the commit's per-line counts; off on partial measurements unless `coverage_patch_partial_runs`; a changed file whose blob differs from the measured one is `stale`, one without line data `no_line_data`, a truncated diff `truncated`, an unmeasured file `not_instrumented`, a file the project excludes `excluded`) and gaps (changed files with executable changed lines none of which ran); a run without a commit is described alone. `Coverage.History` reads a branch from the graph: `branch_history/3` (the first-parent walk from the recorded head with each commit's measurement or `measured: false`, falling back to the measured commits labelled with the branch in time order, `ordered_by: :time`, when no head is recorded; a measured commit **chains** when it is complete or measured the same set as the previous chained commit, the first one trivially), `branch_points/3` (the chained commits, oldest first, with the commit's pooled totals), `commit_page/3` (that walk paginated, cut at the merge base with the default branch for a branch other than it, or the commits its runs were labelled with once the default branch contains it), `latest/3`, `branch_names/2`, `refs/2` (every branch and pull request with its newest measured commit), `branches/2` (each branch's head measurement against the default branch's) and `pull_request_commits/3`. MCP mirrors the pages: `get_commit_coverage`, `get_commit_coverage_comparison`, `list_commit_coverage_files` and `get_commit_coverage_file` for a commit, their `test_run` equivalents for one run, plus `list_coverage_history`, `list_coverage_branches` and `get_pull_request_coverage`; a file's per-line detail is API- and MCP-only, never a page. `Coverage.Gates` holds the per-project gates (`coverage_gates_enabled`, `coverage_gate_min_patch_coverage`, `coverage_gate_max_total_drop`, off by default) and `evaluate/2` (neutral when a gate cannot be evaluated). The check is one per commit: once the last shard of a pull request run published its coverage, `Coverage.publish/4` enqueues `Coverage.Workers.CoverageGateWorker` with `trigger: "run"`, which posts a **pending** `tuist/coverage` check on the PR head until the commit is complete and does nothing once it is (the verdict never changes after the signal); `Commits.signal_complete/2` enqueues it with `trigger: "signal"`, which compares and posts the verdict. `publish/4` also re-enqueues the PR comment, whose Xcode tests section gains a Coverage block per commit (`Tuist.VCS.get_coverage_body/1`: headline, per-scheme rows when several measured it, and a note while the pipeline has not signalled completion); the comment job is unique among pending jobs only and a later enqueue reschedules it, so coverage that lands after the run (local-mode uploads) still reaches the comment.
- Coverage surfaces: `TuistWeb.CoverageLive` (`/tests/coverage`, tabs Overview (the default branch's latest chained commit and the commit-ordered trend, with a scheme filter defaulting to Any), Branches (each branch's head commit), History (the branch's commits from the graph, unmeasured ones included, with the change per chained commit), Files and targets (at the latest commit), Runs; `/tests/coverage/commits/:sha` for one commit against its baseline, with the runs that measured it, and `/tests/coverage/pull-requests/:number` for a pull request's head commit with a commit selector) is the one place for coverage, and `TuistWeb.ProjectCoverageSettingsLive` (`/settings/coverage`, a Project Settings tab for Xcode projects with coverage enabled, `project_update` only) holds its settings: gates, patch coverage on partial runs, Git history window, provider fallback and tracked files, excluded paths; the tests overview and the Test Runs page keep no pooled coverage widget (the Test Runs coverage column and filter, and the per-run Coverage tab, stay). `TuistWeb.API.CoverageController` serves the same figures under `/tests/coverage`: `runs/:id` (totals, targets, Git history, the commit's baseline or reason), `runs/:id/files`, `runs/:id/file?path=`, `runs/:id/comparison` (the run's commit against its baseline), `commits/:sha`, `commits/:sha/files`, `commits/:sha/file?path=`, `commits/:sha/comparison`, `POST commits/:sha/complete` (the completion signal), `history?branch=` and `branches` (no scheme parameter: the head commit's union, with the measured set), and `pull-requests/:number` (its commits and the comparison of one); the MCP tools `get_test_run_coverage`, `list_test_run_coverage_files`, `get_test_run_coverage_file`, `get_test_run_coverage_comparison`, `get_commit_coverage`, `get_commit_coverage_comparison`, `list_coverage_history`, `list_coverage_branches` and `get_pull_request_coverage` (schemas in `Tuist.MCP.Components.Tools.CoverageSchemas`) return the same shapes, all built by `Tuist.Tests.Coverage.Report`, where a missing baseline or patch comes with a `kind` and a sentence.
- Internal Slack delivery succeeds only when Slack returns `ok: true`; API errors must propagate to reporting workers even when the HTTP status is 200.

- Module-cache daily hits, misses, miss reasons and distinct module counts can be derived from the full invalidation breakdown with `module_timeseries_from_breakdown/2`. Derive these before filtering out hit-only modules or applying a list limit; count a module name once across products within the selected cohort. The old raw `module_invalidation_timeseries/1` and `modules_timeseries/1` queries are retained solely as independent test oracles.

Module-cache invalidation reads discover names with grouped aggregation, then batch independent module histories without splitting their date ranges. Window reads dictionary-encode repeated names and branches to bound memory. Dependency-graph reads identify the latest eligible commit before fetching its targets, preserve branch/environment filters and delayed uploads, and skip graph reads when no dependency edges exist. Blast radius is resolved after the module list is cut to its limit, so the graph is walked only for the modules a page shows and is not read at all for a page that shows none; the dependents time series reverses the graph once per distinct daily graph rather than once per day.
- Xcode build steps (`Tuist.Builds.Step`, `build_steps`) are collected by default for every processed Xcode build, for reuse across build analytics, retain only current-invocation leaf intervals for 90 days, are streamed from the parser sidecar through per-worker ClickHouse writes bounded by 8 MiB of encoded rows or 1,000 rows (an oversized individual row is written alone), and are read with retry deduplication. Each log has an independent 64 KiB allowance and preserves its beginning and end when truncated. `Tuist.Builds.Timeline` opens with the full build visible and permits zooming back out to the entire duration, loading all individual interval metadata once. Zoom, pan and search run locally; there is no range-loading endpoint. The metadata response derives its distinct project/target count from the fetched intervals without a second query. Keyboard navigation queries all steps; browser search reuses the initial full-build metadata. Parser telemetry ends before the consumer starts; ingestion has its own span. Logs share that retention and are fetched separately by build and event ID.

## Boundaries

- Application startup and shutdown ordering: `server/lib/tuist/application/AGENTS.md`.

- Bazel profile processing needs `SELECT` on `bazel_profile_uploads` and
  `UPDATE` on `compressed`, `state`, `error`, and `updated_at`. Keep the
  migrate-time processor grants and CNPG fallback SQL in sync; profile upload
  creation and expiration remain web-runtime responsibilities.

- Build ingestion no longer reads `feature_flags`. Its processor read grant in
  `Release` and `infra/cnpg/tuist-processor-grants.sql` remains for compatibility
  with older processor releases during rolling deployments and rollbacks.

- `ClickHouseDictionarySource` builds escaped local dictionary sources for migrations.
  Its query options suppress application SQL logging without overriding managed
  ClickHouse logging policy; server password masking requires valid dictionary DDL.

- Web controllers and LiveView code live in `server/lib/tuist_web`.
- Data migrations live in `server/priv`.
- `Processor.XCActivityLogParser` runs the MuonTrap executable through
  `System.cmd` in a timed task, collecting the parser's inherited stderr without
  MuonTrap's output acknowledgement protocol. This avoids `:epipe` on fast exits
  while retaining process cleanup when the task times out or its caller dies.
- `Processor.BuildProcessor` maps known archive-corruption errors from
  `:zip.unzip` (`:bad_eocd`, `:bad_eocd64`, `:bad_central_directory`,
  `:bad_local_file_header`, and per-entry `:bad_crc`) to
  `{:error, :corrupt_archive}`. `ProcessBuildWorker` discards those jobs on
  the first attempt and marks the build as `failed_processing` right away,
  since the archive is a bad upload and retries won't heal it. Other
  extraction errors still bubble up as `{:error, reason}` so Oban retries
  them and the final attempt marks the build as `failed_processing`.

- Runner Kura participates in account disk sizing and plan memory/CPU profiles. New and returning instances pin the account claim; the enrollment migration immediately pins unpinned live runner instances to their account-sized claim (or plan default), capped at the historical 50Gi to avoid bypassing growth admission. The runner pool does not advertise `tuist.dev/memory-ceiling-mib`, so keep `memory_ceiling_bin_packed` disabled there. - `Kura.Lifecycle` reclaims an active public instance that has stored nothing since it entered service once `Environment.kura_unused_days/0` has passed. The evidence is `kura_storage_rollups` covering the whole service life: snapshots on every full day since the service start, and no day with live segment bytes or evictions. Missing telemetry is never read as empty. An `:unused` archival is provisioned again only by demand recorded after it, and the project-creation seed declines while `Demand.unused_hold?/1` holds.
