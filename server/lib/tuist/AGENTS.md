# Tuist (Business Logic)

This directory contains the core business logic and domain modules for the server.

## Responsibilities
- `Projects.projects_by_full_handles/1` is the batch lookup for signed analytics ingestion. Resolve current and retained account handles through `account_handle_reservations` to the owning account ID so queued events and Kura storage-tenant fallbacks survive renames. This is attribution, not authorization.
- Metric automations accept a one-time `trigger_config.apply_actions_to_existing_matches` request on create/update. A fresh request starts a baseline generation even when the condition is unchanged. Baselines recheck matches in bounded batches and serialize publication per alert with a session advisory lock. Each action runs outside a row-lock transaction, between a short preflight check and a durable checkpoint; edits may cancel the remaining work while an authorized action finishes. Clear the request on completion. Silent publication deduplication tokens include the sorted test ID set so changed payloads on retry are not dropped. Read-only match counts enumerate bounded pages and share the baseline metric, trusted-branch validation, and current-state eligibility logic. Condition edits require a fresh opt-in. Omitting the request preserves pending work; explicit false cancels remaining actions. Baseline attempt generations invalidate stale workers; nullable `event_generation` separately scopes recovery history (falling back to `baseline_generation` for existing rows), so opt-ins and cancellations retain active recovery events. Returned action errors are logged and checkpointed without publishing a successful trigger, allowing the baseline and subsequent evaluation to progress.
- Build task summaries can omit CAS-output ID arrays. Expanded-task lookups resolve those arrays inside ClickHouse using both build ID and task key, group duplicate outputs by node ID, and return 20 rows plus a next-page indicator. Neither request parameters nor task summaries should carry the stored ID arrays.
- Machine metrics retain nullable `offset_ms` from the activity log start during archive processing, independently of the upload timestamp, so recorded samples align with build steps. Older samples without offsets keep their standalone charts.
- `Tuist.Builds.Steps` serves paginated, filtered metadata and individual logs to the HTTP API and MCP. Both transports authorize build-read access first. IDs are decimal strings scoped to a build, and list queries never select log text. Availability distinguishes absent step data from a search with no matches.

- Ecto schemas, contexts, and domain services.
- `Kura.Origins` discards counts for deleted accounts when persisting a batch. It locks surviving account keys within the write transaction so concurrent deletion cannot invalidate the batch or discard other accounts' counts.
- External test ingestion uses `Tests.get_test_case_states_at/3` for historical quarantine attribution; current test controls continue using the current-state projection.
- Git history (`Tuist.GitHistory`): the commit graph is keyed by **repository** (`git_repositories` in PostgreSQL: the normalized remote a run reports — host, owner, name — scoped to the account, created on first sight by `repository_id/2`; several projects share one, a fork gets its own), with `git_commits` (generation numbers, and `ref_id`/`position` on the first-parent tree), `git_commit_parents` and `git_refs` within a window from `settings/1` (server defaults, `TUIST_GIT_HISTORY_*` environment, per-project `git_history_*` columns). Runs record `git_repository_id` (from `git_remote_url_origin`, in `Tests.create_test/1`) and `git_dirty` (uncommitted changes: a dirty run's coverage stays at run level). Clients name the repository by its remote URL on every request: `POST .../tests/git-history/commits/missing` and `.../commits` for the graph (`missing_shas/2`, `record_commits/3`, `record_branch_head/4`), `.../listings/missing` and `.../listings` for a commit's file listing (`missing_listings/2`, `record_listing/4`: every `git ls-files --stage` entry with its blob and mode, in ClickHouse `git_commit_files` keyed by repository and commit, with `git_commit_listings` in PostgreSQL recording which commits have one; uploaded once per commit by a clean checkout, in parts, capped by `commit_file_limit`/`TUIST_GIT_HISTORY_COMMIT_FILE_LIMIT`), and `GET .../tests/git-history/settings` tells them how much to collect. The listing is what coverage measures against (`Coverage.Commits` counts the source files no run measured), where the project's tracked files come from (`tracked_files/3`: `projects.tracked_file_globs` applied to the listing at read time, no server defaults, no per-run snapshot) and where an ancestor's blobs are read (`blobs_at/3`). `ancestors/3`, `nearest_ancestor/4`, `ancestor?/4`, `merge_base/4`, `first_parent/2`, `first_parent_chain/3` and `first_parents_to_segment/3` walk the graph, pruned by the lowest candidate generation. **Refs** (`git_refs`, `Tuist.GitHistory.Ref`) place branches and pull requests (`pull/<number>`) on the first-parent tree: `advance_ref/5` (the client's branch heads through `record_branch_head/4`, and every commit fold for the refs its runs reported) walks a new head's first parents back to the first commit the ref or its parent owns and numbers what it added (`position`); the default branch is the only root and the only ref that takes over another's commits (a fast-forward), whose ref then forks again, so refs never trade commits back and forth; a branch's commits are `ref_commits/2` and where a commit sits is `position/2`; `prune/2` drops commits beyond the window. Test runs carry `base_branch`, `merge_base_sha`, `is_pull_request`, `pull_request_number`, `git_object_format`, `history_source` and `history_fallback_reason`, and their changed files with hunks land in `test_run_changed_files` (ClickHouse, buffered) for patch coverage. The execution mode rides with the run too (`test_runs.execution_mode` and `test_module_runs.execution_mode`: `parallel`, `serial` or empty), which the CLI derives from the xcodebuild arguments and the xctestrun.
- Code coverage (`Tuist.Tests.Coverage`) uses one model for every build system: `coverage_files` holds one row per file per shard report, tagged with `build_system`, the run's `git_commit_sha`, a `scope_kind`/`scope_id` (`run` today; `target`, `suite`, `test` once tests are attributed; part of the sort key), an `evidence_kind` (`observed`; `cached` and `carried` are reserved for reused evidence), `in_repository` (repository-relative and known to Git: the only files evidence may rely on), per-line execution counts, function arrays and branch counters (`xccov` leaves them empty; JaCoCo and LCOV fill them). The #13199 tables `xcode_coverage_files`/`xcode_coverage_runs` are left in place, unread and unwritten (no data was copied; a follow-up migration drops them). `coverage_runs` carries the run totals with `coverage_tool`, `coverage_tool_version` (the Xcode version for `xccov`), `git_object_format` (`sha1`/`sha256`, read off the blob ids), `scheme` and `git_commit_sha`. **Coverage is a property of a commit**: `coverage_commits` (PostgreSQL, beside the graph: `Tuist.Tests.CoverageCommit`, written by `Coverage.Commits.recompute/3`, which folds outside any transaction and writes under a per-commit advisory lock only while the row is still the version it read (otherwise it folds again, and after three attempts folds under the lock), then advances the refs its runs reported; it keeps copies of the commit's `ref_id`, `position` and `committed_at`, synced on every ref move, so trends and baselines are range queries and outlive the graph; scheduled a few seconds after each report by `Coverage.Workers.CommitWorker`, one pending job per commit) holds the union of every run that measured the commit (`Coverage.merged_files_query_for_runs/3`: per path, a line is covered when any run covered it, a file counts once however many schemes compiled it; runs from a dirty checkout never contribute; partial runs do) with the measured set (`schemes`, `partial_schemes`, `test_run_ids`), `unmeasured_files_count` from the commit's listing, `complete`/`completeness` (`signal` from `POST .../tests/coverage/commits/:sha/complete`, the client's `tuist coverage complete`, which `Commits.signal_complete/2` records; `inferred` is reserved) and a `version` bumped per rewrite; `Commits.prune/1` drops rows past `TUIST_COVERAGE_COMMIT_RETENTION_DAYS` (1095) or, for a pull request's own commits, `TUIST_COVERAGE_PULL_REQUEST_COMMIT_RETENTION_DAYS` (90). ClickHouse retention is a time-to-live per table from `TUIST_COVERAGE_FILE_RETENTION_DAYS` (90: `coverage_files`, `git_commit_files`) and `TUIST_COVERAGE_RUN_RETENTION_DAYS` (365: `coverage_runs`), set at creation and re-applied by `mix tuist.coverage.retention`. Xcode coverage is read from the result bundle by the shared Swift parser (`xccov` report + archive) wherever the bundle is processed: the macOS xcresult processor for uploaded bundles (the CLI writes a `tuist_coverage_manifest.json` with root spellings, the covered files' Git blob ids and a partial flag into the bundle), or the client in local mode (sent as `xcode_coverage`, the API schema `TuistWeb.API.Schemas.Tests.XcodeCoverage`). The parser streams: `xccov`'s output goes to disk, `JSONStreamScanner` walks it one value at a time (the report twice, names first and functions per target second; the archive indexed by byte offset), and each file is written as one JSON line to an NDJSON file, so memory stays flat in the bundle's size (70 MB on the Tuist CLI's bundle and 108 MB at 20× its size, against 416 MB and 7.9 GB when both documents were decoded whole). The NIF returns `coverage_path`/`coverage_partial`/`coverage_file_count` instead of the rows; `XCResultProcessor` moves the file out of the bundle's temporary directory (`relocate_coverage/1`) and `ProcessXcresultWorker` hands it to the run as `xcode_coverage: %{path, partial}` and deletes it after. `Tuist.Tests.Coverage.rows/2` turns that into a lazy stream and `publish/4` inserts and folds totals in one pass, keeping a file's lines only when another shard reported the same path. A report's rows share `inserted_at`, readers use only each shard's latest run-scoped report (so retries replace rather than add), and merge shards per path as the union of lines. Shards report concurrently, so nothing rewrites merged totals on `test_runs`: each report publishes its totals over the shards reported so far to `coverage_runs`, versioned by shards included then newest report, which readers take with `argMax(…, version)`; those totals stay partial until every shard of the plan reported coverage. Only the repository's own code is kept: the parser drops files outside the checkout and dependency checkouts (`.build`, DerivedData, SourcePackages, Pods, Carthage), and in a Git checkout any file Git ignores. Test code (files only `.xctest` bundles compiled, flagged `is_test` by the parser from xccov's `buildProductPath`) is stored with counts only (no line or function arrays) and excluded from totals, targets and files. Excluded paths (`Coverage.ExcludedPaths`: `projects.coverage_excluded_path_globs`, per project only, nothing excluded by default; for generated code) are stored like any file but left out of every figure: `publish/4` folds them out of `coverage_runs`, the readers (`merged_files`, `list_files`, `line_counts`, and their commit-level twins in `Coverage.Commits`, which take `excluded:` to reuse a pattern) filter them with ClickHouse `match` over one RE2/PCRE-compatible pattern. Changing the globs enqueues `Coverage.Workers.RecomputeTotalsWorker`, which republishes `coverage_runs` in batches (`TUIST_COVERAGE_RECOMPUTE_BATCH_SIZE`, 500) from the runs' retained reports with `version + 1` and the original `inserted_at` (retention unchanged; a later shard report still outranks it) and re-enqueues the affected commits; runs past the file retention keep their totals. Local-mode uploads are deflate-compressed by the CLI. The whole feature, test selection's data included, is in early access behind `Tuist.FeatureFlags.xcode_coverage_enabled?/1` (FunWithFlags `:xcode_coverage` per account on canary/production, on elsewhere), and **every new piece of it goes behind the same flag**: while it is off a run stores nothing of the feature (ingestion drops `xcode_coverage`, the enumerated tests and the evidence; the run joins no Git repository and its changed files are not recorded; the xcresult processor removes the manifest before parsing), the API answers 404 (`TuistWeb.Plugs.RequireCoveragePlug` on the coverage and Git history controllers), and the pages and the settings tab are hidden. `test/tuist/tests/coverage/early_access_test.exs` holds the contract. The flag comes out only after the feature has run in production for some days.
- Test enumeration (`Tuist.Tests.Enumeration`): the tests a run could have executed, which the client lists without running any (`xcodebuild -enumerate-tests` over the built products, with the run's arguments minus its filters, so `-only-testing` does not narrow it) and writes into the result bundle as `tuist_test_enumeration.json`; the shared parser attaches it to the summary (`enumerated_tests`), so the local-mode payload and the xcresult processor report the same list. `test_run_enumerated_tests` stores it keyed by the test case's stable id (`Tests.generate_test_case_id/4`, the one `test_case_runs` carries: module, the innermost suite, and the name as the bundle reports it), so "enumerated and not run" is a set difference. xcodebuild lists a Swift Testing test by its function and the bundle by its display name (`@Test("…")`): the shared parser renames each enumerated test the run executed and sends its `function`, stored as `function_name`, and `Enumeration.record/2` gives a test the run skipped (which arrives as its function) the display name an earlier run recorded for it. A generated project that prunes skipped targets lists only what is left in the workspace. Retained like the coverage file detail. Nothing reads it yet: test selection will.
- Per-test coverage evidence (`Tuist.Tests.Coverage.Evidence`): which files each test of a run executed, reported by the client as `coverage_evidence` (`paths` once, scopes referring to them by index; from the local-mode payload or the xcresult processor, which reads `tuist_test_coverage_evidence.json` beside the coverage manifest). Stored in `coverage_files` under the scopes reserved for it: `test` (`scope_id` the module, suite and name joined by a unit separator, the fields the test case's stable id is made of), `suite` (module and suite: what ran around a suite's tests and belongs to none) and `target` (the module: everything the target's processes executed, the floor for each of its tests). Evidence rows hold a path and the lines the scope ran when the client could tell them (no counts; the blob is read off the run's own row for the path), every coverage reader filters on the `run` scope so they never reach a total, and a report's rows share one `inserted_at` so readers can take each shard's latest. A test case run whose report holds the test's own evidence is flagged `test_case_runs.has_coverage_evidence` at ingestion (`tests_with_evidence/2`, set in `Tests.create_test/1` beside `record/3`), so a test's newest evidence can be found through its runs rather than by scanning `coverage_files`. Reported coverage (`Coverage.Reported`) reads it to carry forward the tests a selective run skipped, from the nearest measured ancestor merged-in commits included (`Commits.nearest_measured_ancestor/3`: a probe per segment of the ref tree, `Commits.nearest_on_segments/5`, bounds the ancestry walk to the first-parent distance it found, and only a commit none of whose first parents within the window was measured walks the whole window); test selection will read it too.
- Coverage surfaces: `TuistWeb.CoverageLive` (`/tests/coverage`: the default branch's latest chained commit and its trend over the period, the branch's recent commits from the graph with the unmeasured ones in place, and where its latest commit is thinnest), `TuistWeb.CoverageDetailLive` (`/tests/coverage/commits/:sha`: one commit's totals, targets, files and runs) and `TuistWeb.CoverageFileLive` (`/tests/coverage/files/*path?commit=`: a file's lines and functions at a commit); the project overview shows the default branch's coverage and trend. `TuistWeb.ProjectCoverageSettingsLive` (`/settings/coverage`, a Project Settings tab for Xcode projects with coverage enabled, `project_update` only) holds the tracked files and excluded paths (the history window is the server's). The Test Runs page, a run's page and the Tests page show no coverage. `TuistWeb.API.CoverageController` serves what clients need to send coverage (`settings`, `uploads`) and `POST commits/:sha/complete`, the completion signal, which returns the commit's coverage as `Tuist.Tests.Coverage.Report.commit/2` shapes it.
- Internal Slack delivery succeeds only when Slack returns `ok: true`; API errors must propagate to reporting workers even when the HTTP status is 200.

Derive these before filtering out hit-only modules or applying a list limit; count a module name once across products within the selected cohort. Keyboard navigation queries all steps; browser search reuses the initial full-build metadata. Parser telemetry ends before the consumer starts; ingestion has its own span. Logs share that retention and are fetched separately by build and event ID.

  Its query options suppress application SQL logging without overriding managed
  ClickHouse logging policy; server password masking requires valid dictionary DDL.

- Data migrations live in `server/priv`.
- `Processor.XCActivityLogParser` runs the MuonTrap executable through
  `System.cmd` in a timed task, collecting the parser's inherited stderr without
  MuonTrap's output acknowledgement protocol. This avoids `:epipe` on fast exits
  while retaining process cleanup when the task times out or its caller dies.
- `Processor.BuildProcessor` maps known archive-corruption errors from
  `:zip.unzip` (`:bad_eocd`, `:bad_eocd64`, `:bad_central_directory`,
  `:bad_local_file_header`, and per-entry `:bad_crc`) to
  `{:error, :corrupt_archive}`. `ProcessBuildWorker` discards those jobs on
  the first attempt and marks the build as `failed_processing` right away,
  since the archive is a bad upload and retries won't heal it. Other
  extraction errors still bubble up as `{:error, reason}` so Oban retries
  them and the final attempt marks the build as `failed_processing`.

## Related Context

- Kura's moderate retention correction supplements the existing 30-day shrink: 14 complete post-resize days with snapshots, at least seven meaningful eviction days and two ring budgets of turnover can reduce the account claim by 10–25%. Discount known idle whole days from shed age and ring span; require at least 4.5 days of adjusted retention and project toward the 3-day floor plus 25% headroom. Today's short or unmeasured evictions veto the correction, and every known pinned region must supply a shrink verdict. Neither a smaller region's pin nor a deeper shrink elsewhere bypasses the 25% correction cap. Every apply restarts the evidence window, including when it only converges regional pins. Retain the slower occupancy and clearly excessive-retention paths.

- Kura capacity admission refuses on two readings that are not interchangeable. `Capacity.pressure_line_gib/1` is region-wide and says the region is out of room (`:capacity_exhausted`, answered by another machine). `Capacity.placeable?/2` is per node and says the scheduler cannot place the instance's replicas where their local volumes pin them (`:capacity_unplaceable`, answered by moving the instance or freeing that box). Free space and the instance's own replicas come from one node-wide reading, the same one `room_for?/2` uses, so a resize counts back only what that reading already charged. Each box is charged for every declared replica no other box holds, because a replica mid-rollout is in no pod list but its volume brings it back. A per-node reading that is missing admits: a false refusal there blocks every claim growth in the region and shows up nowhere the account would see.

- An account's Kura claim has one resolution, `PlacerClaims.effective_claim_size/1`: the largest claim pinned on its live storage-governed instances (volumeless statuses excluded), then the sized claim in `kura_placer_claims`, then the plan default. Provisioning, cold returns, warm-handoff targets, runner caches and the claim sizing baseline all read it, so an expansion is built at the claim sizing measures. Do not resolve a new instance's claim from the sized row alone: pins without a sized row exist, and a smaller ring in one region shortens retention for content replicated from the others until sizing raises it. The sweep reads the same inputs in batch through `PlacerClaims.region_claims/1` and `resolve_claim_size/3`.

- `ClaimSizing` measures each region against the claim pinned in that region, never the account's largest pin: that pin funds the ring the region's rollups describe, and scaling a 16Gi ring's shortfall by a 50Gi pin sizes it as if it ran 50Gi. The account still has one claim. A growth whose target the account's claim already covers recommends that claim, so a region pinned under it is raised rather than left short, and applying any proposal moves every volume-holding governed instance to the recommendation in one transaction, raising some and lowering others, and rewrites the sized row so the evidence window restarts. Shrinking reads occupancy for a ring that never fills and retention for one that rotates: every region kept what it shed for three retention floors on every day of 30. A retention shrink projects from each region's own pin and shortest span, at most halves the claim in a step unless another region already runs the account on a smaller claim with that retention, and never goes under the plan's starting claim. Keep a shrink slower to confirm than any growth. Today's live row is passed over by a shrink window only while it has measured nothing against the shrink: one that already evicted (occupancy) or shed content younger than the threshold (retention) vetoes it. `ClaimSizingWorker` tries every open proposal, growths first, and spends its hourly budget only on applies that land, so proposals the cluster keeps refusing cannot starve the ones behind them.

- Runner Kura participates in account disk sizing and plan memory/CPU profiles. New and returning instances pin the account claim; the enrollment migration immediately pins unpinned live runner instances to their account-sized claim (or plan default), capped at the historical 50Gi to avoid bypassing growth admission. The runner pool does not advertise `tuist.dev/memory-ceiling-mib`, so keep `memory_ceiling_bin_packed` disabled there. The region retains a conservative 50Gi accounting fallback for legacy rows without a pin or loaded account; governed creation and cold return pin the sized account budget before rendering. Disk sizing remains account-scoped across public and runner regions, including their telemetry and resize history.

- Cache-endpoint resolution with no Kura endpoint enqueues `Workers.ProvisionOnDemandWorker` (one per account at a time), which runs `Lifecycle.provision_account/2` with the tick's eligibility rules, applies each instance coming up via `Reconciler.reconcile_server/1`, and hands it to `Workers.AwaitActivationWorker`, which checks `Reconciler.activate_when_ready/1` about twice a second and never applies. Activation asks whether the public host's record is published through `Tuist.DNS.record_published/1`, which queries the zone's authoritative nameservers instead of the pod's caching resolver. The tick hands every `:provisioning` server whose deployment it applies to the same worker; rollouts of serving instances are not polled. The minute tick stays the authority for everything these paths miss.
- `Kura.Lifecycle` reclaims an active public instance that has stored nothing since it entered service after `Environment.kura_air_unused_hours/0` (24 hours) on Air or `Environment.kura_unused_days/0` (seven days) on Pro, checked hourly by default. Air caps the unused-path tracking grace at its unused window; inactivity and Pro retain the full tracking grace. Enterprise and keep-warm instances remain exempt. Both plans require `kura_storage_rollups` with snapshots on every full service day, at least 90% of the expected 15-minute snapshots across the region's replicas, and no live segment bytes or evictions. Each date's contribution is capped at the elapsed service time on that date. Partial boundary days may be absent because provisioning and rollup delivery can cross midnight; sparse telemetry or a missing full day is never read as empty. An `:unused` archival is provisioned again only by demand recorded after it, and the project-creation seed declines while `Demand.unused_hold?/1` holds.

- `Kura.StableEndpoint` derives managed stable-host intent independently of image rollouts, including drain-pending rows. `FeatureFlags.kura_stable_hostname_enabled?/1` uses the single `kura_stable_hostname` account/global FunWithFlags opt-in in staging and production, absent by default. Canary enables automatically. No server rollout environment switches or account allowlist remain. Gate both advertising intent and hand-out so unselected accounts publish no stable records; disabling the flag requests withdrawal through the existing drain. Placement demotion does not alter advertising. Retirement waits for a stable-ready survivor; the controller owns provider-confirmed withdrawal and the post-withdrawal drain. Persist readiness in `kura_servers.stable_endpoint` so the reconciler and every web replica share it even without Redis. Endpoint requests use this projection, preserving the original controller timestamp and checking generation at observation; absent/stale evidence falls back to regional URLs after three minutes. Archival and cold return clear the projection. See `../../../infra/cache-dns/README.md`.
- Stable readiness tolerates up to 30 seconds of forward controller clock skew.
  Intent synchronization is bounded to eight concurrent workers and avoids
  unchanged projection writes; it still runs during flag rollback to withdraw
  existing CR intent. Endpoint resolution reuses the managed-server projection
  and reads the account flag once. Custom URLs are appended only after stable
  hand-out, preserving the absent-instance provisioning and fallback paths.

- `Runners.CacheVolumes` owns Linux snapshot identities, publication generations
  and user-visible usage history. Authorize against the actual executed runner
  job and GitHub App metadata. PRs read private clones; only successful trusted
  default-branch jobs publish. Deletion locks the same volume row
  as publication and increment the generation. Allocation admission and report
  validation, measurement updates, and lifecycle decisions remain inside their
  caller's transaction and locks when extracted into private helpers. Browser reads/mutations are
  account-scoped. Agents acknowledge physical deletion separately; do not treat
  invalidation as erasure. See
  [`infra/runners-controller/cache-volumes.md`](../../../infra/runners-controller/cache-volumes.md).
