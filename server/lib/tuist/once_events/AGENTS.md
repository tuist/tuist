# Once run events

This subsystem projects Once lifecycle events into run summaries and declared actions for the live build pages.

## Shared test-report publication

- Commit the legacy admission reservation, publication intent and dedicated `once_test_reports` Oban job together. Snapshot preparation runs in the worker, not on the stream's hot run-row lock. For new intents only `TestReportPublication.state == "published"` is completion; the old `test_report_published_at` column still fences legacy writers during rollout.
- Preserve immutable captured chunks and persisted tokens, write the parent last, and checkpoint each acknowledged chunk. Never automatically resend an uncertain in-flight write based on a finite deduplication window or a lagging read. Unknown outcomes remain visible for explicit reconciliation. Do not replace children with fresh IDs.
- The age-independent publication sweep resumes durable preparing/pending/expired work; the separate two-hour terminal-run sweep covers missed intents. Historical old-writer reservations are not silently repaired. Only finalized test runs qualify, not abandoned/lost partial runs.
- Deferred webhook enqueueing and its checkpoint share a PostgreSQL transaction. Optional downstream notifications and webhook delivery are not exactly once. The capture hook is process-local and must not change ordinary ingestion.
- Preparation claims/counts survive a killed worker; commit the snapshot only for its current owner. Known permanent errors or eight unsuccessful attempts enter `failed_preparation`, emit failure telemetry and stop automatic sweeps. `retry_preparation/1` is an explicit, payload-free operator retry, never an uncertain-write reset.
- Check a three-minute monotonic budget before starting a chunk, including preparation time. Yield only between acknowledged chunks and snooze for resumption; the five-minute hard timeout still fails closed if an in-flight write becomes uncertain.
- Keep required event projection failures as resync errors. Shared-report preparation/publication failure must not reject an already persisted completion event; retain its durable source/intent and expose the failure instead.
- See [publication recovery](publication-recovery.md) for rollback, schema evolution, observability and the maintenance-only reconciliation preconditions.

## Event projection

- For projects opted into `:build_entities`, `TargetInstance` and `TargetQueued` persist idempotent run-local mappings (`once_target_instances`, `once_target_executions`) so completed actions resolve to declared slots (`target_id`, `capability`, `action_index`) in one joined query. Disabled projects do not write these mappings; native projection remains unchanged.
- `RunCompleted` calls `OnceEvents.publish_build_entities/1`: lock the PostgreSQL run, skip published/nonterminal/disabled runs, synchronously insert the complete ClickHouse batch, then mark `build_entities_published_at`. Concurrent completion/recovery attempts serialize on the durable row, not a replica-local lock. Failed writes leave the marker unset. A crash after the ClickHouse acknowledgment and before the PostgreSQL commit can still replay, so deterministic IDs and replacement-safe reads remain necessary; this is not a cross-database exactly-once transaction.
- The hourly stale-run worker retries only unpublished finalized/lost runs in a fixed two-hour window, with 100-run `(finalized_at, id)` keyset batches and a concurrent partial unpublished-terminal index. Repeated successful sweeps write no additional observations. This finite recovery window is not permanent durable delivery or an unbounded backfill. Preserve recorded action outcomes, propagate failures for retry, and keep the global `:build_entities_kill_switch` effective. The diagnostic `identifier` is not identity; reordering a target's declared actions changes slot identities.
- Only `ActionCompleted` creates an action row. `TargetCompleted` is a target summary and must not create a substitute action or overwrite action zero.
- An action is identified by run, target execution, capability, and action index. Replayed completion events must not increment run counters again.
- `ActionCompleted.display_name` and `source_files` are presentation only. Keep `identifier` and action identity intact; missing/empty names fall back to legacy labels and missing files to an empty list. Action and cache-action search include both names and source paths; name sorting uses the display name with identifier fallback.
- Accept both numeric and decoded enum forms of terminal results.
- Keep durations and cache outcomes from the individual action events. Do not infer them from the enclosing target or command.
- Regression coverage lives in `test/tuist/once_events_test.exs`.
- Action search and filters apply to the whole run before pagination. Counts and rows share the same scoped query; sorting uses allowed fields and deterministic tie breakers.
- The transport resends a batch whenever an ack is lost, so every write here has to be idempotent and every run-level roll-up has to be guarded by the insert actually having happened. Never increment a counter from an upsert whose `on_conflict` does not touch `updated_at`; derive it instead.
- Never ack a batch whose projection failed. `NEEDS_RESYNC` without advancing the high-water mark is the retry signal; `ACCEPTED` after a failure loses the event.
- `run_id` is chosen by the client, so anything keyed by it (ack store, pub/sub topic) must also be keyed by `project_id`.
- `priv/proto/once/events/v1/events.proto` is a copy of the client's file in `tuist/once`. Sync it from there rather than hand-editing `proto/once/events/v1/events.pb.ex`, then regenerate with `mix protobuf.generate --include-path=priv/proto --output-path=lib/tuist/once_events/proto --plugin=ProtobufGenerate.Plugins.GRPC priv/proto/once/events/v1/events.proto` followed by `mise run format`, which is why the checked-in file does not match the generator's raw output byte for byte. The generated modules live in the `Once` boundary (`lib/once.ex`).
- Authentication reuses `Tuist.Authentication.SubjectCache` snapshots resolved by the shared authentication context, so a login session, an account token and a project token all work. A project token identifies its project. Every other credential names it in the `once-project-id` call metadata (`account/project`, the key RFC 0008 defines in `tuist/once`), and `Tuist.Authorization` `:run_create` decides access. Never add a separate token lookup here.
- Unknown projects and projects without access must return the same message, and handles are validated for shape and length before any database lookup.
- Check the original snapshot's monotonic deadline and verified wall-clock expiry before every batch, including empty batches. Reauthenticate and recheck project access when due, at most 60 seconds from the subject fill, never a new minute from stream admission. Revocation/membership changes may remain stale until that deadline. Refreshed credentials must still resolve the same project; attribution keeps the original actor.
- Subject caching is isolated from display/membership invalidation, successful-only and keyed by HMAC. Backend failure after the deadline refuses with `:unavailable` and counts telemetry through `refuse!/3`; it must not become invalid credentials or stale access. Each client address is limited per minute (`once_events_rate_limit_bucket_size`, keyed on ingress `x-forwarded-for`). Unknown projects run the same permission check against a placeholder as forbidden projects.
- Refuse a call through `refuse!/3` in `RunEventService`, never a bare `raise GRPC.RPCError`. It counts the refusal (`tuist_once_events_refused_total` by call, stage and status), and `Tuist.OnceEvents.GRPCExceptionFilter` keeps `unauthenticated`, `permission_denied` and `resource_exhausted` out of error reporting, because elixir-grpc's Cowboy adapter logs every `GRPC.RPCError`, raised or returned, at error level. Alert on the counter, not on error issues.

- Record the authenticated credential account on the first RunStarted in nullable `once_runs.account_id`; project credentials and historical runs remain unattributed. Replays must never replace the original actor, including with a different credential. This is server attribution and does not change the client event protocol.

- `Query` serves the REST run reads and MCP tools from the same shapes, listing through `Analytics.list_invocations/3` and reading one run by project and `run_id`. The REST detail path parameter is `once_run_id` because `LoaderPlug` treats `run_id` as a command event.

- Native build listings opt into the virtual failure-category column from `BuildMetrics`. Use the shared classifier before database filtering, sorting and pagination, scope evidence to the selected project, and leave stored records and legacy listing defaults unchanged.

- Proof-cache failures are availability failures too, including admission before a snapshot exists. Preserve `UnavailableError` as gRPC `:unavailable` through `refuse!/3`, never `:unauthenticated` or a direct bcrypt fallback.
