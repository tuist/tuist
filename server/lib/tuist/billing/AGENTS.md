# Billing (Context)

This context owns billing, plan management, and Stripe integration.

## Responsibilities
- Define plan metadata (Air/Pro/Enterprise) and pricing thresholds.
- Create Stripe customers, billing portal sessions, and manage subscriptions.
- The Stripe account is shared with Atlas, which creates customers for its own invoicing, so webhooks arrive for customers no Tuist account links to. `Billing.create_customer/1` tags every customer Tuist creates with `metadata.tuist_account_id`. `TagStripeCustomersWorker` backfilled the tag on existing customers. `Billing.on_unlinked_customer/1` ignores untagged unknown customers and reports tagged ones, because a tagged customer with no linked account is an orphan that Stripe may still be billing. `Accounts.create_customer_when_absent/1` locks the account row so concurrent requests don't create duplicate customers.
- Record usage-based metering events (e.g., remote cache hits).
- Create and read Stripe billing credit grants (`Tuist.Billing.CreditGrants`), the money-denominated balance behind prepaid runner access. The runner-specific policy on top of it lives in `Tuist.Runners.Prepaid`.
- Usage-based pricing (`Tuist.Billing.UsagePricing`, measured by `Tuist.Billing.UsageMeters`) is enabled per account by the `:usage_based_pricing` flag. For those accounts the nightly sync reports `cache_egress_megabytes`, `cache_requests`, and `passing_test_cases` instead of `remote_cache_hit`, and the usage and billing pages show the new charges. Cache egress and requests come from Kura (`kura_usage_events`) plus the compilation cache endpoints registered in `cache_endpoints` (`cas_events`); traffic from private runner-cache regions is halved before reporting. Passing test cases exclude runs linked to Tuist Runners jobs, matched on run id together with the project handle (`test_runs.ci_run_id`/`ci_project_handle` = `runner_jobs.workflow_run_id`/`repository`), because a Buildkite build number is only unique within its pipeline. Everything is attributed to the project owner and read over half-open windows.
- Rolling an account onto usage-based pricing takes three steps. `mix billing.provision_usage_meters` creates the Stripe Meters and Prices from `UsagePricing.meter_prices/0`, idempotently, and refuses live mode without `--live`. `Billing.hold_usage_based_pricing_for_existing_subscriptions/0` sets a per-account off gate for every subscription that is not Air, so the flag can then be enabled for everyone without moving them. `Billing.switch_to_usage_based_pricing/1` swaps one subscription's plan usage Price for a subscription item per meter and enables that account's own gate. Run it at a renewal: the Price it removes has to have been invoiced, and the meters start the cycle at zero. `SwitchUsageBasedPricingWorker` runs daily over the active and past due Pro subscriptions and switches the ones whose account has `:usage_based_pricing_switch` enabled, so that flag decides both who moves and when. Enabling it just after an account renews keeps the accounting whole, since the usage Price leaves without being settled for the period it is removed in. Enterprise and open source subscriptions are never switched by the schedule.
- The Air free-tier limit (`Billing.cache_access_blocked?/1` and `cache_blocked_account_ids/1`) follows the pricing an account is on. On the previous pricing it is 200 remote cache hits; on usage-based pricing it is either cache allowance, checked against `accounts.current_month_cache_egress_megabytes` and `current_month_cache_requests`, which the nightly usage refresh writes from `UsagePricing.metered_cache_usage/3` over the same free-tier window as the hits. The limit reads only those columns and an in-memory flag lookup, so the cache authorization path never reaches ClickHouse. `reset_free_tier/1` zeroes all three counters.
- Existing Air accounts are split before the global gate goes on: `Billing.hold_usage_based_pricing_for_impacted_air_accounts/2` holds the ones whose metered cache usage over a reference period reached an allowance, and every other Air account moves with the gate. `Billing.release_usage_based_pricing_holds/0` is the call for the day the previous pricing ends: it clears the holds of accounts on Air now and enables `:usage_based_pricing_switch`, leaving held Pro accounts to the switch and held enterprise and open source accounts held. The subscription webhook closes the one gap the one-off holds cannot: a Pro subscription that arrives carrying the hit Price for an account only the global gate reaches (checkout fixes line items when the page opens, so one opened before the flip and paid after lands like this) is held on arrival. It never holds an Air or open source subscription, whose usage Price bills nothing, or an account with a gate of its own, so a late webhook listing a switched account's old items cannot put it back.
- Subscription statuses are mirrored from Stripe as-is. `Billing.live_subscription_statuses/0` (`active`, `trialing`, `past_due`) are the ones an account keeps its plan through: `past_due` is a renewal Stripe is still retrying. `unpaid`, `canceled`, `incomplete`, `incomplete_expired`, and `paused` carry no plan, so the account resolves to Air. An account with an `unpaid` subscription and no live one is `Billing.payment_failed?/1`: when it is over the Air free tier, the API and the cache nodes (`cache_payment_failed` in cache tokens and introspection) refuse it with a payment-failed message instead of the Air upgrade message. `Billing.update_plan/1` changes a live subscription, `past_due` included, in place. Only an account with no live subscription and an `unpaid` one is redirected to the open invoice (or the billing portal) from `Billing.outstanding_payment_url/1`, because a Checkout would create a second subscription beside the one that owes. `/billing/pay` uses the same URL for `past_due` accounts too. Query live subscriptions through `live_subscription_statuses/0` rather than listing statuses. Stripe is configured to retry a failed renewal with Smart Retries and then mark the subscription `unpaid` (not cancel it), leaving the invoice open. Its own failed-payment emails are off: `invoice.payment_failed` on the first attempt of an automatically charged subscription invoice queues `PaymentFailedNotificationWorker` for the account's admins (`PaymentFailedNotifications`). The email promises no date or duration for the plan: that is Stripe's retry window, a dashboard setting that can change and that the API does not expose. When a subscription turns `unpaid` (the transition, detected in `on_subscription_change/1` against the stored status, so a redelivered event sends nothing), `SubscriptionUnpaidNotificationWorker` tells the same admins the account moved to Air and that paying the open invoice restores the plan.
- Air usage notifications run after the daily account usage refresh, at 80% and 100% of the independent remote-cache and runner-minute allowances. An account on usage-based pricing is warned about the cache egress and cache request allowances instead of remote cache hits, with egress tracked in megabytes because the notification columns are 32-bit. Runner usage reads `Tuist.Runners.Billing.compute_milliseconds/3` directly and truncates to baseline minutes, matching dispatch without its cached read. The configured limit comes from `Tuist.Runners.Allowance`, and active runner trials are excluded. Queue the highest reached threshold for all organization admins (or the personal account owner). A durable row per recipient, metric, threshold, and counting-period start records successful delivery to prevent resends after job pruning. Undelivered rows can be requeued when no active delivery job remains; a mid-month free-tier reset starts a new period only for cache usage. Runner notifications always reset on the UTC calendar month. Delivery workers recheck plan, role, period, and usage to suppress obsolete emails, send outside database transactions, and store the usage snapshot actually sent. Delivery is at least once: a crash after provider acceptance but before recording success can still cause a retry.

## Guardrails
- Billing data is customer data; update `server/data-export.md` for schema or usage changes.
- Kura reports a download it serves twice: as a usage rollup, and to `/webhooks/cache`, which writes a CAS event. `UsageMeters` counts CAS events only from the endpoints registered in `cache_endpoints`, which is the path with no rollup. Widening that filter bills every Kura-served Xcode download twice.
- Never blank a runner Price id in `stripe.prices.runners` once it has gone live. `configured_runner_price_ids/0` filters empty ids, so a later plan change would stop recognising the existing runner subscription item, delete it, and lose the cycle's accrued usage.
- The allowances and rates in `Tuist.Billing.UsagePricing` must match the tiers of the Prices under `stripe.prices.usage_meters`. A key there with an empty Price id reports usage without charging it; the Meter must exist in Stripe before the flag is enabled for any account.
- Credit grants move money. Anything that creates one must stay idempotent against webhook redelivery and job retries.
- A runner trial is not a credit grant. It is the absence of a runner subscription item (`Tuist.Runners.Trials`), which is what makes runner usage unbillable open-endedly. Anything that builds subscription items must keep asking `Trials.on_trial?/1`, or a trial account silently starts being billed.
- The prepaid marker lives on the Stripe invoice *line*, not the invoice, and a grant is funded from the marked line's amount. A prepaid charge shares an invoice with that month's metered usage, so funding from `amount_paid` would convert the whole bill into runner credit.
- An invoice's `lines` are paginated and the webhook payload carries only the first few. Read them through `Tuist.Billing.Invoices.list_lines/1` rather than off the payload, or a prepaid line further down a busy bill goes unseen.
