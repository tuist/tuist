# Shard workflows

- `Tuist.Shards` computes immutable assignments from eventually consistent timing history. PostgreSQL-owned workflows are stored by `Workflows`; `Workflow` presence permanently selects the authority for that plan. Legacy ClickHouse plans remain readable during the compatibility rollout.
- `:postgres_shard_plans` is a default-off, account-scoped **creation** gate. Enable only after all web, build-processor and xcresult-processor runtimes support this path and have the new database grants. Once a reference has a PostgreSQL-owned plan, subsequent plans for that reference stay on PostgreSQL even when the gate is disabled. See `server/docs/shard-workflow-consistency.md` for rollout and follow-ups.
- The canonical merged-run UUID is allocated with the plan. Module/suite assignments and one row per shard index are committed atomically before returning the plan. PostgreSQL reports never consult ClickHouse for a mapping, merge base or completion decision.
- Stage and synchronously flush core report facts before committing completion. Keep heavy ingestion outside the short plan-row transaction. Under the row lock, merge the latest PostgreSQL snapshot and shard statuses and assign a database-clock version strictly greater than the previous one. A repeated initial `processing` upload must not supersede a terminal report.
- Queue `ProjectWorkflowWorker` in the same transaction as the control-state write. Executing jobs must not absorb updates published while they run. Projection replay is at least once: plan aggregates deduplicate plan IDs, shard aggregates collapse latest reports, and test-run replacements use the monotonic snapshot timestamp. Deduplication tokens are an optimization with a finite destination window, not an exactly-once guarantee. Acknowledge `projected_version` monotonically only after publication succeeds. The hourly stale-run worker also repairs up to 500 unacknowledged workflows via the partial pending-projection index, even when an earlier Oban job was discarded/pruned.
- Do not project assignment rows to ClickHouse for PostgreSQL-owned plans. Detail reads attach the authoritative plan and its already-loaded assignments; timing history, execution facts and charts remain in ClickHouse.
- The stale-run reaper handles PostgreSQL plans under the same row lock and excludes them from the legacy ClickHouse reaper. A stale analytics copy must never roll a completed authoritative run back to failure.
- Test with independent PostgreSQL sessions for concurrent first/final reports, stale or absent ClickHouse rows, delayed outbox delivery/replay and buffer-flush failure. Ordinary sandbox-shared tests serialize requests and do not establish row-lock correctness across replicas.
