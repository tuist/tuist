# Test sharding

- `Tuist.Shards` computes immutable assignments from eventually consistent timing history. Version-1 plans store complete assignments in the plan row, and their UUID is the canonical merged test-run UUID. Never allocate this identity by racing report writers.
- `:immutable_shard_reports` is a default-off, account-scoped creation gate. Persisted `reporting_version`, not the current flag, selects report behavior. All web/build/xcresult runtimes and both ClickHouse deployments must understand the contract before enrollment. See `server/docs/shard-workflow-consistency.md` for rollout requirements and limitations.
- Account enrollment requires a producer rollout first: new executions reusing a plan must send monotonically increasing `shard_attempt` values, and terminal corrections must increase `shard_report_revision`. Wire-compatible zero defaults cannot order CI re-runs. The CLI's attempt-independent plan reference is not an execution version; keep enrollment off until compatible producers are deployed.
- Version-1 shards append `TestReport` observations. `latest_shard_test_reports` orders each shard by producer attempt, phase, revision and deterministic digest. Receipt clocks and read/modify/write summaries are not authority. Initial processing or failed-processing retries cannot supersede a parsed result in the same attempt. Terminal corrections require an increased revision and the full execution payload.
- Use `Test.query/0` and `ShardRun.query/0` for derived run/shard reads; `get_test/2` keeps physical legacy point lookups without `FINAL` and falls back to `Test.immutable_query/0`. Schema sources remain physical write targets. Do not rewrite a version-1 merged `test_runs` row, including in detached flakiness follow-ups or the legacy stale-run reaper.
- When adding run metadata, keep the physical run/report schemas and all explicit summary-view column lists compatible; adding a field only to `Test` can break immutable inserts and union reads.
- Deduplicate child execution payloads on read, preserving occurrence-scoped IDs and original receipt timestamps. Raw reports retain the producer's upload UUID for bundle export/lookup after job pruning.
- `Tuist.Ingestion.Batch` flushes request-local core facts before report publication and assigns deterministic fact IDs. The report identifies its fact set; current-run detail views exclude older attempts and unpublished facts. Historical execution analytics remain separate. Preserve `shard_report_id` when copying/correcting physical case-run rows.
- Summaries derive incomplete-run expiry after six idle hours. A late complete set repairs the result without mutable expiry rows. Events remain observation-driven and best effort, not durable aggregate-state transitions.
- One immutable plan row avoids partial assignment publication; it does not establish native replica read-after-write or synchronize the detached mirror. Test engine-specific freshness/durability independently. Temporary stale aggregates must converge when the facts become visible.
- Test concurrent first/final reports with independent ClickHouse connections, duplicate replays, reversed receipt clocks, producer ordering, stale expiry/recovery and failed fact/report writes. A single-server race is not a replicated-cluster partition or failover test.
