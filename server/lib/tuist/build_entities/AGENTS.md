# Persistent build inventories

## Boundary
- `Tuist.BuildEntities` owns run-independent identities and bounded cross-run observation queries. Native facts remain authoritative for execution details.
- Supported resources: Gradle tasks, Xcode modules, declared Once action slots, Bazel BEP actions, Mix files and Mix modules. Xcode compilation-cache keys and Bazel digests are not stable logical identities and are deliberately excluded; preserve their native run/cache routes.
- Identities use a versioned length-prefixed encoding, deterministic project/system/kind UUIDs and deterministic observation IDs. Preserve identity field order and collision fixtures. Gradle includes root project/build/task paths and type; Xcode includes project/target; Once requires declared target/capability/index mappings; Mix uses reported paths or qualified module names. Bazel actions use the exact target label, mnemonic and primary output (including its configuration prefix); never truncate these identity fields or substitute action/cache digests. BEP start time distinguishes attempts within one invocation. Older payloads without identity or a valid start remain accepted but unindexed.

## Rollout and writes
- `FeatureFlags.build_entities_enabled?/1` requires the project's `:build_entities` opt-in and an inactive `:build_entities_kill_switch`, in every environment. Check before producer mapping, Once mapping persistence and all new public surfaces. Native ingestion and legacy pages must continue while disabled. Tests opt in their own project with `FunWithFlags.enable(:build_entities, for_actor: project)`; never enable the flag globally in async tests.
- Batch observations through `Observation.Buffer`; never query or upsert the catalog during ingestion. A materialized view derives duplicate-insensitive identity/min/max/name states. Evaluate rollout flags once per distinct project in each batch.
- Once publication uses `record/2` with `sync: true`, a PostgreSQL run lock and `build_entities_published_at`. Mark only after ClickHouse acknowledges the whole run batch. Replayed completion and overlapping recovery sweeps skip published runs. A crash after the ClickHouse acknowledgment but before the PostgreSQL commit can still replay: deterministic IDs and replacement-safe reads remain required. See [../once_events/AGENTS.md](../once_events/AGENTS.md).
- Missing trustworthy identity skips derivation, not previously accepted reports. Retry invariance requires the same native parent/event identity; a newly minted build ID denotes a new execution.

## Replacement and query invariants
- Observations use `ReplacingMergeTree(inserted_at)` with stable `(project_id, system, kind, entity_id, id)` sorting, independent of mutable observed time. Insert-time partitions can contain versions of one observation in different months.
- Every observation read resolves the whole latest row with `FINAL` before time/cohort predicates, retaining NULL clears. `bounded_query/3` centrally adds non-overridable replacement settings: `do_not_merge_across_partitions_select_final: 0`, `optimize_move_to_prewhere_if_final: 0`, `use_skip_indexes_if_final: 0`.
- Explicit `PREWHERE` may select only whole replacement groups by project/system/kind/entity ID, never observed time, insertion partition or other mutable evidence. Catalog range/search candidates safely overapproximate matching entity IDs; exact membership/counts still use latest observations.
- Preserve bounded time windows, threads/memory/spill/deadline budgets, page sizes, 100-parent lookups and the 10,000-plus-one scatter bound. Query-limit failures are real errors, not empty facts or not-found responses.
- Inventory/history count-plus-page uses windows with an empty-page fallback; history totals precede cursor filtering. Filtered inventories join counts from one FINAL pass; unfiltered inventories keep catalog-only membership. Analytics combines period/daily aggregates with GROUPING SETS. Inventory analytics scan the entire project/system/kind cohort with kind-scan budgets, independently of table search/sort/pagination. Count distinct active entity IDs over the whole period and separately per day; daily distinct counts are not additive. Count explicit success/failure outcomes separately so unknown outcomes remain distinguishable from zero failures. Inventory `executions` counts uncached success/failure observations, excluding hits and skipped/up-to-date/no-source/cancelled/unknown outcomes, independently of optional duration samples. Gradle, Once and Bazel use it for execution widgets, trends and charts; Mix counts reported compiled files/modules, including untimed records. Inventory duration scatter uses kind-scan budgets and latest-row cohort filtering before a 10,000-plus-one sample cap. Include entity names/identities from the same resolved observation, not per-point catalog lookups. Deduplicate Mix module points by native parent/file execution before the cap; missing references must not collapse unrelated observations.

## Evidence and presentation
- Bazel derives inventory observations only from signed BEP action diagnostics, never trace-profile phases or REAPI traffic. Require all-actions publication for complete coverage and retain best-effort/drop semantics; do not call the resulting counts a complete target inventory. Measured BEP zero durations remain zero; absent/invalid end times stay untimed. Read string invocation IDs in one bounded project-scoped latest-row batch, with no inferred actor. Native diagnostics and cache pages remain unchanged while inventory collection is off.
- Never invent timing, outcome, cache, environment or actor evidence. Cache writes are not misses, cache hits/skipped Gradle tasks have no execution duration, and zero measured values differ from unavailable metrics.
- Xcode modules share project/target identities across graph cache resolutions and activity-log compilations. Graph observations report binary-cache outcomes without timing/status; build observations report measured positive `compilation_duration` and the target's recorded outcome, never a guessed cache miss. Activity-log zero compilation time means no work and is omitted. Build observations use discriminator `compilation:<ordinal>` and execution reference `build_target:<ordinal>` with the native build ID; graph observations retain their command-event parent. Resolve Xcode parent context in two bounded native batches and link compilation history/scatter to Build Runs, not command runs. Mix module duration is its containing file's measured compilation, shared with sibling modules and not additive across them.
- Inventory table filters reuse history's allowlisted Branch/Outcome/Cache predicates, applied to the same latest resolved observation before membership, metric aggregation, sorting and pagination. An entity matches when an observation in the selected cohort satisfies every predicate, not when unrelated observations independently match each field. Ignore unsupported fields/operators and parameterize values. Keep table filters out of inventory analytics/scatter options and preserve public metadata-only response shapes.
- Dashboard inventory rows also derive Last status/Last ran at in the existing single observation scan, after replacement/cohort/table filtering. Exclude cache hits; Gradle/Once/Bazel require explicit executed success/failure, Xcode requires measured compilation evidence, and Mix compilation reports count even without timing or outcome. Keep both fields tied to the latest qualifying execution using observed time plus observation-ID tie breaks; unknown latest outcomes never fall back to an older success. Missing executions yield null status/time, not catalog Last seen. Sort Last ran at before pagination with nulls last in both directions. These fields remain dashboard-only when `include_metrics: false` preserves public REST/MCP shapes.
- Inventory rows include measured average/p50/p90/p99 and sample counts for the selected period/environment/branch. Aggregate latest replacement rows before sorting and paging; missing durations sort last in both directions and genuine measured zeros remain numeric. Preserve catalog-only membership without cohort filters. The dashboard defaults to descending p90; API default ordering remains unchanged.
- Parent context is optional metadata, fetched in one project-scoped native-parent batch and one recorded-user batch. Missing/deleted/org actors remain unknown, with no viewer/project-owner fallback. For explicit report provenance, resolve only `actor_account_id` as a verified account and carry opaque claims/provenance into the shared actor badge; only empty-provenance parents retain legacy publisher/user attribution. Latest native nullable fields use `argMax(tuple(value), version).1`; plain argMax would resurrect cleared values.
