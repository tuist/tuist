# Build automations

Detect cache-key inconsistency for the same reported build unit and commit, without tags or a user-defined invalidation model.

- `CacheKeyMonitor` compares CI observations in a bounded 30-day window, within one project and source. Missing commits, keys, or identities are not evidence. Once excludes explicitly dirty and active runs.
- Gradle identity includes root project, build path, task path, and type. Explicit unknown/non-cacheable telemetry is excluded.
- Bazel uses target, mnemonic, configuration, and output path. Never group only by target/mnemonic: one target can have several legitimate action digests. Older events without output identity are skipped.
- Xcode module identity uses project/target names, product metadata, sorted reported destinations and explicit configuration/profile arguments, without separating producer and consumer commands. Compilation includes configuration/scheme, compiler kind and the reported description; missing descriptions and descriptions with multiple hashes within a build are skipped. This intentionally sacrifices coverage for ambiguous telemetry, and does not infer source identity from a digest.
- Once uses its reported target execution, capability, action index, and identifier. Do not use display names as identity.
- Collapse retries per unit/run. Compare only units with a single reported key within each run. Detection uses distinct keys across distinct runs, not arrival order. Never compare output content hashes as input cache keys.
- Scan comparable commits incrementally with a one-hour overlap, frozen upper bounds, durable commit/identity checkpoints and daily full 30-day sweeps for late child telemetry. Process at most ten commits/source and 120 seconds/job, then resume through Oban snooze, not the next scheduling cadence. Suppress first-backfill Slack delivery until all sources complete, sending one summary.
- Page aggregation in the source database at 1000 findings/page. Use indexed parent-ID sets, FINAL for versioned parents, min/max checks after collapsing each run, and one atomic evidence tuple. Xcode module reads use the project-indexed target view to obtain exact insertion timestamps and prune raw target primary-key ranges without dropping identity fields. Cap each commit to the latest 32 CI runs (128 command events for module caching), so repeated main-HEAD builds cannot grow scans without bound. ClickHouse limits are 2 threads, 512 MiB and 15 seconds/query (20 seconds/request). Commit-level ClickHouse execution/memory limits (159/241) are counted/logged and skipped until the next full sweep, visibly surfaced on the detail page, never represented as successful empty evidence. Reset the count for each full sweep. Connection outages, timeouts and other failures propagate for prompt job retries.
- `Finding` is a PostgreSQL ledger keyed by rule, source, and SHA-256 of the version-prefixed (`v1:`) serialized identity. Changing identity semantics requires an explicit ledger migration/version decision, not an accidental re-alert of every unit. The first evidence includes a commit, two different cache keys, and their source-native run IDs. Recurrences, including across commits, do not notify again. Findings have no inferred recovery; they remain until their automation/project is deleted.
- Serialize evaluation and Slack delivery with global/per-rule session advisory locks on a direct PostgreSQL connection, not transaction-pooler connections or a row lock held through an external call. Isolate scanning in the build evaluation queue. Global-lock contenders and continuations both snooze a jittered 1–5 seconds, rather than losing every gap in a large sweep or polling in lockstep; per-rule contention snoozes 30 seconds. Worker failure backoff is fixed at 30 seconds despite long Oban snooze chains. Check the current rule before delivery. Mark notified only after success; Slack delivery is at-least-once if the process dies after delivery but before checkpointing.
- Atomically stamp all pending findings with a delivery batch UUID, count them and load three samples. Deliver one bounded summary and checkpoint only that batch after success; concurrent insertions remain pending. Revoked/invalid destinations remain pending but do not cause hot retry loops. Transient failures propagate.
- Build findings have their own ledger rather than manufacturing test-case IDs in the test alert event table. Rule configuration, Slack channel selection, edit history, scheduling, and action execution remain shared.
- Update `server/data-export.md` when changing retained evidence.
