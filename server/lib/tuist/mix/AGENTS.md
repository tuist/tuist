# Mix builds and dependency caching

- `Tuist.Mix` ingests builds, diagnostics, file dependencies, steps and machine samples. The client-generated build ID is scoped to its project everywhere.
- `Cache` validates dependency observations before the build is inserted, then writes `CacheEvent` rows through the standard ingestion buffer. Accept only the supported outcomes/reasons and bounded durations/digests; repeated dependency names in one report are invalid.
- `local_hit` and `remote_hit` both count as hits. CAS digests, output links, server counts and throughput come exclusively from the shared `Tuist.ReapiCache` queries over signed Kura records, scoped to Mix kind and project/build identity; never invent them from local observations or action-input hashes.
- The cache observations table retains data for 90 days and deduplicates `(project_id, build_id, dependency)` with `ReplacingMergeTree` and `FINAL` reads. All analytics and event pagination apply project, half-open period and environment filters before aggregation. Search applies to the event table, not analytics totals.
- Hits divided by hits plus misses gives hit rate. Exclude bypasses and do not invent misses for old clients or up-to-date dependencies. No lookups means no rate. Preserve nullable savings and measured zero independently.
- `saved_duration_ms` is the client's estimate of cumulative compilation avoided from the original compilation, not elapsed build savings. Only a hit can carry it. The server stores observations, not artifacts, configuration values or absolute checkout paths; remote artifacts use Bazel's shared Kura REAPI store, with a local snapshot fallback. Artifacts may embed compile-time values and producer paths; telemetry does not include those values.
- Optional paired `read_bytes`/`read_duration_us` describe successful local or remote hits; `write_bytes`/`write_duration_us` describe successful publications on misses. Nullable `read_source`/`write_source` identify `local` copies or `remote` client CAS transfers. Validate source/outcome/measurement consistency; legacy sources remain null, never inferred. Remote timing excludes local installation; local timing includes verification and installation. Validate nonnegative bounded values and reject incomplete pairs or incompatible outcomes. Legacy rows remain null, not zero. `Cache.io_analytics/2` scopes/deduplicates like other analytics, sums copied bytes, averages operation latency (microseconds converted to milliseconds), and derives throughput from total bytes over total measured operation time (bytes/second), with daily series and preceding-period trends. Never treat compilation duration as cache latency or describe local copies as network traffic.
- `Cache.hit_rate_analytics/2` averages individual build rates and calculates p50/p90/p99, daily series, and relative trends against the preceding equal-length period with identical filters. Exclude builds without lookups and preserve unavailable comparisons. Deduplicate observations before calculating per-build rates; this dashboard average is not the overall lookup-weighted rate returned by `summary/2`.
- `Cache.recent_builds/2` reads seven builds by default, with a configurable limit capped at 50, in the selected project/period/environment, including legacy builds without observations. `recent_hit_rate/1` averages the available per-build rates. Batch-load their accounts and aggregate deduplicated dependency observations for those IDs; never query once per row. Retries and client-selected IDs shared by different projects must not duplicate or leak rows. Missing cache observations stay unavailable.
- `Cache.hit_rate_scatter_data/2` aggregates a weighted hit rate per build from deduplicated observations under the same project/half-open period/environment filters. Exclude builds with no lookups, keep measured 0%, group points by local/CI, and fetch one extra build to distinguish exactly 10,000 points from a truncated dataset. Return timestamps and group identities, not translated labels or chart configuration.
- `Cache.build_summary/2` includes nullable copy byte totals and average/p50/p90/p99 operation timings in microseconds for the build detail. `Cache.build_events/3` supports validated dependency-name sort direction; project event reads retain their existing timestamp order unless a sort is requested. `Cache.build_summary/2` and `Cache.build_events/3` scope every `FINAL` read to both project and client build ID. Build identity replaces the period/environment filters used by project analytics. Search, outcome and pagination affect only the entry table, never summary totals. Preserve nullable estimates for legacy and non-lookup builds.
- `MixCacheLive` exposes the project-scoped data at `/mix-cache`. UI configuration, filtering and formatting belong in the web layer; aggregation stays here.
- Update `server/data-export.md`, the controller schema, and the generated API client when the wire/storage contract changes. Cache-only builds remain valid without a compiled-file profile.
