title: GitLab merge requests can now save cache volumes
description: "GitLab CI and Buildkite jobs now save cache volume changes from every branch, like GitHub Actions. With an API access token on the GitLab connection, merge request pipelines save too."

Cache volumes keep the Xcode, module and Gradle caches, plus any directories you choose, between jobs on Tuist runners. Until now, GitLab CI and Buildkite saved changes only from the default branch, so feature work never refreshed the cache other jobs start from.

GitLab CI and Buildkite now follow the same rules as GitHub Actions. Successful jobs from your own project save their changes on every branch:

- **GitLab CI:** push, schedule and web pipelines.
- **Buildkite:** webhook and schedule builds, including pull requests from the pipeline's repository.

Fork pull requests and fork merge requests never save. Tags never save either.

On GitLab, merge request pipelines can save too. Create a project or group access token with the `read_api` scope and add it as the **API access token** on the GitLab CI connection in **Settings → Integrations**. Tuist uses it to check where each merge request comes from. Pipelines of merge requests opened from a branch of your project save under that branch. Without a token, merge request pipelines still use the cache but discard their changes.

![The Connect GitLab CI form with the GitLab URL and runner authentication token marked as required, and the help tooltip of the new API access token field open](/marketing/images/changelog/2026.10.21-gitlab-merge-request-cache-volumes.png)

To save only from some branches, turn on **Limit to specific branches** on the runner profile your jobs use. That setting now applies to GitLab CI and Buildkite as well. See the [cache volumes guide](https://tuist.dev/en/docs/guides/features/runners/cache-volumes#saving-changes) and the [GitLab CI guide](https://tuist.dev/en/docs/guides/features/runners/ci-providers/gitlab-ci#merge-request-pipelines) for details.
