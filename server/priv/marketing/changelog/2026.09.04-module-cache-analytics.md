Module Cache reported how often the cache was hit, but not which parts of a project were responsible. A hit rate tells you there is room to improve; it does not tell you where to start. A new **Modules** section answers that directly: which modules miss most often, why they miss, and how much of the project rebuilds when each one changes.

## Ranking modules by how often they miss

The Modules page lists every module the cache knows about, ordered by cache misses, with its hit rate and its number of dependents. Sort by any of those columns from the header, search for a module by name, and scope the whole page to CI or local builds and to a date range. Above the table, three figures summarize the same window: how many modules the project has as of the latest commit on its default branch, how many builds were served from cache, and how many were misses. Selecting one swaps the chart beneath it, so each number can be read as a trend rather than a snapshot.

Dependents is the column worth lingering on. It counts how many modules transitively depend on the one in the row, which is the number of modules that have to be rebuilt when it changes. A module with a middling miss count and a long list of dependents often costs more than a module that misses constantly but sits at the edge of the graph. Ranking by misses alone hides that; having both side by side makes the trade-off visible.

## Why a module missed

Every cache miss now carries a reason, and the reasons are counted separately rather than lumped together.

**Changed** means the module's own content moved: its sources, resources, settings, or any other input that belongs to it. This is the expected kind of miss. Work changed, so the module was rebuilt.

**Upstream** means the module's own content was untouched and only a dependency changed. This is the interesting kind. These rebuilds are the ones better module boundaries can remove, because nothing about the module itself required the work.

**Cold** means there was nothing to compare against: the first build of that module on that branch, or an entry that was no longer in the cache. On a busy repository this bucket is often larger than teams expect, which is why it is reported as its own number instead of being folded silently into the others.

Each miss is classified by comparing a build against the previous build of the same module **on the same branch**, so a feature branch is never diffed against the trunk. Pick a reason from the dropdown on the Misses figure to see just that kind, or leave it on the total.

## Every build a module took part in

Opening a module shows the same figures for that module alone, and beneath them a **Builds** table: one row per build the module appeared in, newest first, with the scheme, whether the module was a local hit, a remote hit or a miss, the reason if it missed, the branch, the commit, and when it ran. Rows link through to the run.

![The module detail page in the Tuist dashboard, showing cache analytics for a module and the list of builds it took part in](/marketing/images/changelog/2026.09.04-module-cache-analytics.png)

Filter the table by branch, by a commit SHA prefix, or by reason, and sort it in either direction by time. This is where an aggregate becomes actionable: a module showing a high upstream share leads to the specific builds and commits where a dependency, rather than the module itself, forced the rebuild.

## Getting the dependency graph

The misses ranking, hit rates, and reason breakdown work with the data the CLI already reports. The **Dependents** column and the graph behind it need dependency edges, which newer CLI versions send with each build. Until a project has reported them at least once, dependents reads zero and everything else on the page behaves normally. No configuration is required beyond running a CLI version that sends them.

Find it under **Module Cache › Modules** in the dashboard.
