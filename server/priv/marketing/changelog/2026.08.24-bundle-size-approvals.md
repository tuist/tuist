---
title: Decide who gets to accept a bundle size increase
description: "A size threshold that anyone can wave through is a suggestion. You can now limit accepting one to the GitHub users you name."
category: "Product"

---

When a pull request pushes your app past a size threshold, Tuist fails the `tuist/bundle-size` check run and puts an Accept button on it, so an increase you meant to make does not need a second commit to get through. The button is the release valve for a check whose whole job is to stop the merge.

Until now that valve had no lock. GitHub offers a check run's action to everyone with write access to the repository, and Tuist added nothing on top, so the threshold held against people who respected it and no one else. Teams that wanted the check to mean something asked us for a way to narrow it.

**Settings > Bundles** now carries an Approvals policy.

![The Approvals section of a project's bundle settings, with the policy set to selected GitHub users and one approver listed](/marketing/images/changelog/2026.08.24-bundle-size-approvals.png)

**Anyone** is the default and keeps today's behaviour: anyone with write access to the repository. **Selected GitHub users** narrows it to a list you keep on the project. When someone who is not on the list presses Accept, the check run stays failing and tells them who can accept instead, and the button stays where it is so that someone who can will find it. Every acceptance is recorded with the account that made it, so the question of who let a size increase through has an answer later.

The list holds GitHub usernames rather than Tuist members, which is deliberate. Matching a GitHub user to a Tuist account needs the two to have been linked, and on the teams most likely to want this, almost nobody has done that: they sign in through SSO and have never had a reason to connect GitHub as well. A policy keyed on Tuist membership would have looked right in the settings page and denied nearly everyone at the check run. Matching on the username asks nothing of your members and works the same however they sign in.

If your rule is one Tuist does not model, such as requiring a review from a specific team, leave the policy on **Anyone** and gate on a check of your own that reads the `tuist/bundle-size` conclusion alongside whatever else you require. Tuist reports the size; the merge decision stays yours.

Learn more in the [bundle size documentation](https://tuist.dev/en/docs/guides/features/bundle-size#size-thresholds-approvals).
