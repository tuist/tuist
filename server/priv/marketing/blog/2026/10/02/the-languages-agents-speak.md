What an exciting time to be a builder. For the first time in a long time, we are even questioning a reality where GitHub might not be the dominant go-to option for hosting code, or where pull requests might no longer be needed. No one knows what the future might look like, but everyone is trying, and we find it exciting.

At Tuist we’ve been open minded about these things. Trying new ideas, challenging assumptions that emerged in a context that just changed, and overall, trying to get the most out of it so that we can maximize the value per person in the company. The way we work today has nothing to do with how we used to work months ago, and might be distant from how things will look a year from now. However, what we’ve learned over these past months, and what we believe will hold true, is that we built convenient abstractions that made sense at the time for humans, but that might hinder the effectiveness of the core workflows, those driven by agents, when interfacing with our organization. In this blog post I’d like to share some examples of areas of Tuist where this manifested.

## Infrastructure

When we started working on Tuist, we did what most builders did at the time, and which many still do: use a [platform as a service](https://www.cloudflare.com/learning/cloud/what-is-paas/). Many of them are just layers upon cloud providers like Amazon Web Services, but conceptually compressing the intricacies of dealing with virtual machines, load balancers, ingress proxies, and other sorts of infrastructure-related pieces. Think about it: I built this software service and want to get it to production quickly, so ideally my deploy is as easy as a git push, like Heroku pioneered at the time, and others like Fly.io followed. I like to think of these layers as languages. At the bottom we have bare infrastructure resources, like servers. Cloud providers abstract them with another language that treats them as resources to rent out, ensuring they can maximize the usage of the underlying resources. Still not high level enough for most people to use, so a higher order language exists, letting you talk in terms of what you work with, for example “apps” which you deploy.

For a long time that’s how we ran Tuist. We even switched providers, but as our service started to become more than just a single service, and the necessity for low-level control emerged to optimize latency and usage of resources, the idea of going one level lower emerged. For people like us who had never used [Kubernetes](https://kubernetes.io/docs/concepts/overview/), this felt a bit daunting. We even played a bit with Kamal, but it took us a bit of conversing with agents to realize that large language models speak the language of Kubernetes and infrastructure. It felt eye opening. It went from agents not speaking the language of those platform products, and requiring the [Model Context Protocol](https://modelcontextprotocol.io/docs/getting-started/intro) as an interpreting layer, to speaking the language that everyone had been using. That would give us the flexibility we were looking for, but also the flexibility to port our infrastructure stack to another provider, or get agents to debug the state of the infrastructure at any time using the runtime interfaces provided by Kubernetes. It felt empowering.

Many still see Kubernetes as that one tool just for big enterprises. There’s some truth to it. Kubernetes is accidentally complex, and agents dynamically compress that complexity at runtime, so you can learn about what you need to achieve your goals and get your stack deployed to the bare resources. That has a side benefit of lowering costs.

There’s also something beautiful about the Kubernetes language, and it’s the fact that it’s extensible. We sometimes joke about the fact that we’d model many things as a state to be reconciled. But it’s true... we ended up incorporating things in that deployment model that used to live in separate continuous delivery pipelines. An example is Cloudflare configuration, which we persisted using the Wrangler command-line tool from a delivery pipeline, or in some cases, manually updated through their user interface. Now it’s just state, versioned in the Git repository, with our custom controller reconciling that state on merge. We can have a conversation about building these kinds of extensions, about the modelling of the state, about how the state is being reconciled, about the history of changes of state, and about the state right now. It’s beautiful. You don’t depend on anyone to expose interfaces to understand the system, because that’s an implementation detail that was abstracted to make things convenient. Often you need to understand your system at a deeper level, and the last thing you want is to not have access to that and have to resort to support tickets, like we suffered at the time with some outbound network issues that resulted in us moving to another provider.

The second piece to all of this that became clear is that the user interface is very secondary. Runtime access to the infrastructure can be completely headless because agents don’t need your user interface. We just need the access interface, with the right mechanisms in place to do so safely and with tools to elevate privileges in rare scenarios, and a language that agents speak. Kubernetes is one of those languages. All of our work to iterate on the infrastructure is conversations with agents to either adjust the declaration or extend the language, or conversations to understand a particular state of the infrastructure, for example when some piece in it is misbehaving. Kubernetes is not just how we deploy the servers, but also how we get our runners into a desired state to run our customers’ continuous integration builds, or configure Cloudflare to stop crawlers from exhausting our resources while crawling public projects.

This work of adopting a universal infrastructure language has the side effect that it's also portable across our on-premise customers, who can user our charts to deploy the Tuist stack to their own infrastructure. Otherwise, we'd end up using a different deployment configuration thatn our customers, making it trickier to support them without dog-fooding the thing we'd provide them with.

## Elixir

Sometimes, agents need to go beyond the infrastructure and dive into the pieces that are running in those pods. I've always said it, and I'll keep saying it. Elixir and the Erlang runtime is one of the most productive combos that I've every seen, and which I'd recommend to anyone. We started it at a time where people would say, but there aren't that many developers that know Elixir. It's funny how things have changed. We thought it didn't matter at the time, and now it matters even less. Sometimes, the server is misbehaving, or of the workflows is not working as expected. Most of the fix work usually starts with a reproduction, but the local environment might be too distance from the production's as to be able to debug the issue. In scenarios like this, it comes handy to tap into that production system, obviously being careful about it, to inspect what's going on there. This is like doing a surgery, where you need to open after an accident, understand what's happening, and then come up with a fix, that you can either hot-fix there, or translate into a local fix that goes through continuous deployment.

[This talk](https://www.youtube.com/watch?v=JvBT4XBdoUE) does a better job at explaining it, but in short, the Erlang VM (BEAM), can be runtime-inspectable. Agents can open a console against the running application, with access to all the processes running there and the symbols, and interact with them. Not only that, but there are runtime inspection APIs, for example you can sort the processes by the memory or the CPU that the use, or locate a process by an identifier. And not only that, the underlying scheduler, it's fair, which means, even if it's busy handling a load ton of traffic coming from clients, it leaves spaces so that you (or your agent) can do one of those inspect sessions and understand what's going on there.

Agents speak the language of Elixir, and specially Erlang, quite well, since it's been around for a long long time. Compare this to let's say a JS serverless function, run by a serverless runtime platform, which is misbehaving or consuming unnecessary memory, and there's no way for you to tap onto those environments cause they were never designed for this kind of debugging. I believe more and more having runtimes first, and accessibility to those runtimes, at every level can make a huge difference between iterating fast, and iterating insanely fast, and we decided to be on the latter, and chose technologies wisely.

## Observability

Infrastructure ensures our software has a place to run, and Erlang's runtime is there running our code while giving us an interface to inspect what's going on in case it's needed. However, if something needs our attention, is something one needs to invest into, and once again, you want to make sure that there's an observation runtime, and second, that can be inspected by agent. Turns out we've had standard for quite some time around observability: Prometheus Metrics, Logs, and OTel metrics. Agents understand them. They can also query them... We went ahead with Grafana, hosted for us, which would take care of storing all that observability data, and provide us with a couple of pieces, among others, that we'd start with: alerts, which we could wire into an IRM system, and dashboards.

Wth dashboards something really interesting happened. I remember some time ago listening to a podcast where the intervieweee would say that there'll be a time when we'll deploy things so fast, that we won't have time to look at dashboards, and therefore dashboards won't be needed, or at least in the static form that we know today. If an agent can monitor the data as it comes through, why would you want a human looking at a dashboard, specially when it'd be very ineffective at deriving conclussions by looking at it. Cause that's the purpose of a dashboard no? And let's admit it, doing so at scale is something we are not good at. Unless you like looking at a dashboard for the shake of looking at the dashboard, like it was the case once in a company I worked for where a director of engineering would spend hours looking at them as a sign of pride. So we have dashboard, but we barely look at them. Instead, we make a very headless usage of Grafana. First, we define alerts, a lot of them. From alerts that tells us if queries or page loading are slow, cause we want Tuist to feel snappy, to alerts that tell us if there are inusual error responses in our system. Some, routed to our Slack, others, routed directly to the IRM cause we are confident this is worth escalation. 

The moment shit hits the fan, we trigger an agentic session, which we've given access to query all that data through our MCP in the operations platform that acts as a proxy to prevent everyone from having to authenticate against the Grafana MCP. That means in case something happens, an agent can use that interface to understand the system at every level, using as a reference the local cluster definition, which lives in the repository, and going as deep as to open a console with the Erlang runtime, to understand things at a much deeper level. Our usage of Grafana has become very headless, and it has in fact motivated me to tinker with [Pulso](https://github.com/tuist/pulso), a stateless object-storage-backed solution for storing, querying, and sending alerts on observability data. It's built in Elixir, leaning on Rust for the performance-critical pieces. It's still work in progress, but the idea is to put it in production soon, and potentially replace it with something that's we can operate, scale, and improve as we need.

## Operations

I talked about it [here](/blog/2026/09/23/atlas-what-we-built-next), but the same idea of having a runtime that agents can interface with apply outside of the engineering side of things. I got obsessed with engineering the organization. In part, cause I want to provide the best value to our users and want our organization to stand out among our competitors. In part cause we can't afford having many specialized roles, and I honestly believe many are not needed. And in part, cause I want to have space to do more building. When I started moving pieces of context to what we called Atlas, connecting pieces of information, and then using LLM chats to have conversations about area of the organization, it felt surreal. Just yesterday, I took all of this one step further, and connected it to Grok Bots, something that OpenAI has released recently as Dots, and felt surreal. I created virtual roles, for example head of finances, or responsible for support, and gave them clear details around how we operate financially, or how we'd like to provide support to our users, and played a bit witth it, using their experience where it feels like having a call with someone, and I was in complete awe. This is how I imagine the future beeing. Not trying to make everything autonomous, but having all the right information in place in a way where you can have conversations about it with agents, with your colleagues, to make the best decisions, and them act om them. We don't see Tuist running autonomusly. However, we see, many processes being triggered based on signals, on based on signals that we derive with the help of agents based on all of the context we've collected over the months.

Our intelligence runtime is Atlas, and the interface to access it is an MCP interface. Just yesterday, I requested a tax certificate to the tax authorities, which implies sending a letter via post to the German tax authorities, and it was just a prompt from my phone, on the go. Isn't that crazy?

## Closing

Having a context runtime, and an interface to it, in every domain of the company, can make a huge difference between beeing efficient, or felling sluggish. This might require revisiting many past decisions. In our case, Elixir was chosen without seeing this coming, but at the time we started to appreciate the value of that. Agents just augmented it. Our move to k8s wasn't motivated by that either. We were morphing into an infrastructure company, so we needed a way to describe it, and the side effect of it is that our agents found themselves with an interface that we could lean on to iterate further on the infra, and also debug the state of it at any time. And operations is something that also happened organically, this time, truly motivated by building that kind of intelligence runtime. We must own the context, and we must connected in a way where we can make great decisions quick without having to build departments or raise money around promises to hire people for those roles. We want to stay intentionally small maximizing the value we capture per person in the company, and this guides a lot of the decisions that we make.

Bet on standards. Bet on HTML, on CSS, on JS. Bet on OTel or Prometheus Metrics. Bet on k8s. Bet on peeling convenient abstractions that might prevent agents from understanding your system at a deeper level. Bet on owning your data, on how to structure it to make agents effective at it, and on exploring how that data should evolve to help you with the decisions that you need to make.
