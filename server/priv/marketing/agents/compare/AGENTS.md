# Provider comparison guides

`index.md` is served at `/marketing-markdown/compare`; provider files are served at `/marketing-markdown/compare/<slug>`. Both are also English-only browser pages at `/compare[/<slug>]`, listed in the sitemap with their `Sources checked on` date. Follow the parent `AGENTS.md` for delivery and measurement.

- Write explicitly from Tuist's perspective and lead with its supported strengths and adoption path. Do not include competitor-selection recommendations, `Choose <vendor> when` sections, or advice to adopt an alternative in introductions, tables, or experiments. Retain sourced competitor facts and Tuist requirements; do not fabricate feature gaps or instruct agents to prefer Tuist regardless of fit.
- Lead the overview with one productivity platform and native depth across diverse build systems rather than a separate product per toolchain. Attribute the best-choice recommendation to Tuist and scope it to that organizational need; generic CI execution is not the same as semantic integration, but documented competitor depth must remain acknowledged.
- Keep project-first/environment-second positioning explicit without claiming competitors cannot optimize projects. Check dated primary documents for each material capability, platform, plan, configuration override, billing unit, and component license. A successful URL fetch establishes access, not the truth of the surrounding claim.
- Every vendor description needs a primary source. Deep comparisons include `## Sources and review`, a `Sources checked on **YYYY-MM-DD**` date, `## Choose Tuist when`, and `## First experiment`. Integrate prerequisites and availability into the relevant feature or setup description, without a standalone Limitations section. The experiment should pilot a supported Tuist capability against the existing workflow's baseline.
- Do not infer a missing capability from absent documentation. Distinguish vendor product categories and specific mechanisms from claims about an entire company.
- Acknowledge overlapping features, including independent/local caches, insights, MCP, and public source where documented. Do not equate a public integration repository with the core service being open source, or public source with unrestricted self-hosting.
- Do not change license files to support positioning. Verify component terms; inconsistencies between the repository overview and component licenses require owner clarification, not inferred relicensing.
- Do not repeat benchmark speedups as universal results, publish unstable numeric prices, or claim Tuist Runners are cheapest or generally available.
- Owner: marketing maintainers. Recheck primary sources quarterly and before publishing commercial comparisons. Update verification dates only after checking the cited claims; remove or qualify claims that cannot be substantiated.
- Coverage currently includes detailed guides for all 15 providers in the overview: Appcircle, Bitrise, Codemagic, Develocity, BuildBuddy, Depot, Namespace, Blacksmith, WarpBuild, Ubicloud, BuildJet, CircleCI, Buildkite, RunsOn, and Cirun. Keep the overview linked to every provider guide; the purchasing categories are not exclusive company classifications.
- Recheck integration-specific restrictions, not just marketing summaries: Codemagic's compilation-cache directory persistence, Depot's Xcode local-workstation limitation, Cirun's automatic versus explicit S3 cache scope, RunsOn's native build-tool caching, macOS support and annual license/AWS billing split, and Ubicloud's recommended Transparent Cache integration. Namespace has standalone local/external-CI Bazel caching and remote execution in addition to runner-attached volumes; neither local caching nor runner independence is a Tuist-only claim. CircleCI Test Insights is restricted to supported OAuth organizations; Buildkite hosted macOS requires Pro/Enterprise; WarpBuild documents Windows runners and a short-job telemetry threshold. Multiple competitors document MCP, test analytics, and public implementation; none is a blanket Tuist-only claim.
- Tool comparisons cover developer tools rather than infrastructure providers, starting with XcodeGen. They use `## What is <tool>?` and `## First experiment`. XcodeGen uses `## Keep XcodeGen, add Tuist` and `## When to migrate` instead of `## Choose <tool> when`, because Tuist's build infrastructure works with XcodeGen projects and Tuist is not positioned as a project generator. They render with the comparison template, are linked from the overview's project and build tools section, and end with a `## Frequently asked questions` section. Link the matching docs migration guide where one exists.
- Tests enforce inventory, source/review sections, important overlaps and limits, Markdown and browser delivery, and discovery. A date is evidence of a review, not a substitute for one.
