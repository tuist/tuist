# Build-system augmentation guides

These English-only guides explain how Tuist infrastructure augments Xcode, Gradle, Bazel, Mix/Elixir, and Once. Follow the parent [agent-guide contract](../AGENTS.md).

- Lead with the supported Tuist integration, then distinguish what the build system already provides from the shared infrastructure Tuist adds. Do not imply that local caching or profiling is absent from the underlying tool.
- Position Tuist as one productivity platform for organizations with diverse build systems, with breadth through native depth rather than a separate product per toolchain or a lowest-common-denominator shell integration. Make the Tuist-authored recommendation explicit and scoped to this organizational need; keep supported capabilities, setup requirements, and canary status precise.
- Contrast toolchain-aware optimization of the work executed inside build/test runtimes with job-level compatibility and buying more capacity. Do not claim all CI providers lack depth or infer private intentions from compute billing. Link the comparison overview for sourced billing incentives and overlapping capabilities.
- Frame Bazel around native depth, organizational breadth, and developer experience together. Contrast the tool/experience fragmentation of Bazel-only products with command-only CI compatibility, while acknowledging providers with real Bazel depth. Cite recorded timelines, critical paths, and cache behavior as evidence for teams' graph improvements, not automatic graph rewriting.
- Every guide should explain the contribution path: open-source tooling and public infrastructure code, source repository, contribution guide, and the Openness page for component licenses. Contrast closed hosted implementations without inventing a market-wide count or describing every Tuist component as identically licensed open source.
- Do not add Limitations sections to any build-system guide. Lead with supported capabilities and concrete adoption steps, including version/setup requirements where relevant.
- Keep project optimization first and execution-environment optimization second. Provide a small, measurable first experiment without requiring a CI migration or Tuist Runners.
- Link primary build-system documentation and feature-specific English Markdown docs. Review inputs, prerequisites, version boundaries, authentication, and unsupported features. Date source reviews; link success alone does not validate a claim.
- Once is described at `https://buildonce.dev/`. Label Tuist's Once integration as canary until rollout is explicitly confirmed. Do not infer general availability from Once release tags or prescribe a canary installation flag that its documentation does not provide. Lead its guide with cacheable scripts and caching for build systems without native support, preserving project sources and native build definitions. Script annotations/wrappers and provider setup are adoption steps, not a project rewrite. Describe Tuist remote execution as coming soon. Keep the canary status brief in the introduction. Cache, execution providers, live action reporting, and general test analytics are separate capabilities.
- `index.md` maps to the `/build-systems` document key; other files map to `/build-systems/<slug>`. Delivery is only `/marketing-markdown/build-systems[/<slug>]`. Discover through the Markdown homepage and the dedicated `/llms.txt` section, not HTML pages, browser navigation, sitemap entries, or localized alternates.
- Validate inventory, source/contribution contracts, positive positioning without Limitations sections, Markdown delivery, discovery, and browser exclusion through the existing `MarketingMarkdown.decision_guides/0` suites.
