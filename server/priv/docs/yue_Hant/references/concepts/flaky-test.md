# 乜嘢係不穩定測試？{#what-is-a-flaky-test}

不穩定測試係一種自動化測試，喺針對同一份代碼運行時，有時通過、有時失敗，而待測代碼同測試本身都冇任何改變。佢嘅結果取決於測試無法控制嘅因素，例如時間、測試運行嘅順序、其他測試遺留嘅狀態、運行機器，或者透過網絡調用嘅服務。因此，不穩定嘅失敗並不能可靠地反映被測變更嘅情況，這正係不穩定測試成本高昂嘅原因：每個紅色結果都必須經過調查或重試，先至有人會相信佢。

不穩定性喺各種規模下都好常見。Google 報告指，佢哋所有測試運行中約有 1.5% 產生不穩定結果，而且近 16% 嘅測試顯示出某種程度嘅不穩定性（[Flaky Tests at Google and How We Mitigate Them](https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html)，2016）。

## 不穩定測試點樣出現{#how-flaky-tests-show-up}

只有當一個測試對同一輸入產生兩種不同結果時，先至知道佢係不穩定嘅。實際上，呢啲證據來自以下三個地方之一：

- **運行內嘅重試。** 測試失敗，runner 重試佢，然後重試通過。這係成本最低嘅信號，大多數測試 runner 都能產生呢種信號。
- **同一 commit 嘅運行結果不一致。** 同一 commit 同配置嘅兩次 CI 運行對某個測試報告咗不同結果，例如喺 pull request 上嘅一次運行，同某人點擊重試後嘅再次運行。
- **刻意重複運行。** 故意連續多次運行一個測試，睇下佢會唔會失敗。團隊就用呢種方法來確認疑似嘅不穩定問題，或者喺合併新測試之前檢查佢係咪穩定。

只有當所有重要因素都相同時，結果先至算係不穩定性嘅證據：commit、構建配置、設備或模擬器、操作系統版本，以及工具鏈。如果一個測試喺 iOS 17 上失敗但喺 iOS 18 上通過，可能係其中一個系統存在真實且確定性嘅 bug。

## 每個構建系統如何檢測不穩定測試{#how-it-works-per-build-system}

每種工具鏈都可以重試同重複運行測試，但佢哋記錄同報告結果嘅方式唔同。

### Xcode{#xcode}

`xcodebuild`同測試計劃支持測試重複。`-retry-tests-on-failure`會重新運行失敗嘅測試，`-test-iterations <n>`設定允許嘅嘗試次數，而`-run-tests-until-failure`會重複運行測試直到失敗，這對於復現疑似嘅不穩定問題好有用。測試計劃提供同測試重複模式相同嘅選項，另外仲有一個以隨機順序運行測試嘅選項，可以揭示隱藏嘅順序依賴關係。

每次嘗試都會儲存喺`.xcresult`bundle 入面，所以一個失敗後經重試通過嘅測試喺嗰度係可見嘅。Xcode 唔會跨運行保留歷史記錄，所以要檢測從未喺同一運行中重試嘅不穩定問題，就需要比較同一 commit 不同運行嘅結果 bundle。

### Gradle{#gradle}

Gradle 嘅`Test`task 本身唔會重試失敗嘅測試。[Test Retry plugin](https://github.com/gradle/test-retry-gradle-plugin)（`org.gradle.test-retry`）會為`Test`task 添加一個`retry`塊，包含`maxRetries`同`failOnPassedAfterRetry`等選項。一個失敗後又通過嘅測試會喺測試報告同 JUnit XML 中顯示兩次嘗試。測試框架會添加自己嘅重複工具，例如 JUnit 5 嘅`@RepeatedTest`。

Gradle 嘅構建緩存亦可能掩蓋不穩定性：一個可緩存嘅`Test`task 如果輸入冇變，就會從緩存恢復而唔係實際運行，所以一個曾經通過嘅測試會繼續顯示通過而無需執行。當你測量不穩定性時，請使用`--rerun-tasks`強制運行測試，或者喺禁用構建緩存嘅情況下運行`Test`task。

### Bazel{#bazel}

Bazel 內置咗支持。將測試 target 標記為`flaky = True`會讓 Bazel 最多運行佢三次，並且只有當所有嘗試都失敗時先至判定為失敗。`--flaky_test_attempts`標誌喺唔改變 target 嘅情況下設定嘗試次數，當測試喺一次失敗嘗試後通過時，target 嘅結果會報告為`FLAKY`。為了刻意測量不穩定性，`--runs_per_test=<n>`會多次運行測試，而當至少有一次運行通過且有一次失敗時，`--runs_per_test_detects_flakes`會將分片報告為`FLAKY`。

Bazel 以同緩存構建輸出相同嘅方式緩存測試結果。使用相同輸入通過嘅測試會被報告為`(cached) PASSED`而唔會再次運行，無論係本地定係從遠程緩存。當你需要全新執行時，請使用`--cache_test_results=no`（或`--nocache_test_results`）。Bazel 文檔亦建議唔好依賴`flaky = True`，因為佢會永久隱藏佢所重試嘅失敗。

### 其他測試 runner{#other-test-runners}

幾乎到處都存在相同嘅模式：pytest 有`pytest-rerunfailures`插件，Jest 有`jest.retryTimes()`，而 Elixir 嘅 ExUnit 有`mix test --repeat-until-failure`並打印佢使用嘅隨機種子，以便可以使用`--seed`重播依賴順序嘅失敗。

## 不穩定測試嘅常見原因{#common-causes}

一項針對開源項目中不穩定測試嘅實證研究（[Luo et al., FSE 2014](https://doi.org/10.1145/2635868.2635920)）發現，異步等待、併發性以及測試順序依賴係最常見嘅根本原因。下面嘅列表涵蓋咗呢啲原因以及團隊最常遇到嘅其他原因。

- **異步等待同固定休眠。** 測試等待固定時間讓工作完成，例如`sleep(1)`或帶有短超時嘅期望，但工作有時需要更長時間，特別係喺負載較高嘅 CI 機器上。應該直接等待條件本身，並設置一個寬鬆嘅上限。
- **併發性。** 兩個線程或任務喺共享數據上發生競爭，或者測試喺背景操作完成之前就進行斷言。呢類失敗通常取決於 CPU 數量同負載，所以佢哋會出現喺 CI 上，而唔係喺快速嘅筆記本電腦上。
- **測試順序依賴同共享狀態。** 一個測試依賴另一個測試創建或忘記清理嘅狀態：單例、數據庫行、磁盤上嘅文件、`UserDefaults`、環境變量，或者被 mock 嘅全局變量。以隨機順序或並行運行測試會暴露呢個問題。
- **時間同日期。** 使用真實時鐘嘅測試會喺午夜、月底、夏令時變更期間，或者喺其他時區失敗。改為注入一個時鐘對象。
- **未設種子嘅隨機性同無序集合。** 冇記錄種子嘅隨機數據，或者依賴哈希映射或集合迭代順序嘅斷言。
- **網絡同外部服務。** 當呢啲服務緩慢或不可用時，調用真實 API、包註冊表或共享預發環境會失敗。喺邊界處將佢哋 stub 掉，並保留少量明確嘅集成測試。
- **資源壓力同環境狀態。** 機器緩慢或過載、模擬器或仿真器未重置、磁盤已滿，或者端口已被另一個作業使用。當許多無關嘅測試同時失敗時，應該先懷疑環境而唔係測試本身。
- **UI 測試。** 端到端同 UI 測試將上述大多數原因與動畫、渲染時機同系統對話框結合在一起，所以佢哋比單元測試更經常出現不穩定情況。

更改後持續失敗嘅測試唔係不穩定；佢係回歸錯誤。不穩定標籤應該只保留畀嗰啲喺相同代碼上產生咗兩種結果嘅測試。

## 修復、重試同隔離{#fixing-retrying-and-quarantining}

團隊通常會結合三種應對方式，將佢哋分開處理會更有幫助：

- **修復**根本原因。呢係唯一可以恢復測試價值嘅應對方式。記錄嘅嘗試次數、失敗訊息以及每次失敗運行嘅條件都係指向原因嘅證據。
- **重試**以保持流水線推進。重試係有用嘅檢測信號，但無差別嘅重試會掩蓋問題並增加每次失敗運行嘅機器時間。通過嘅重試仍然應該被記錄為不穩定結果，而唔係默默丟棄。
- **隔離**已知嘅不穩定測試，以便喺修復期間佢唔再阻塞合併。被隔離嘅測試要么繼續運行但忽略其失敗（靜音），從而繼續產生證據；要么完全唔運行（跳過），從而移除其覆蓋率。隔離需要指定負責人同退出條件，否則被隔離嘅測試會積累，覆蓋率會悄悄縮小。

## 如何衡量不穩定性{#how-to-measure-flakiness}

按每個測試追蹤不穩定性，而唔係只按流水線：

- **不穩定率。** 產生不穩定結果嘅測試運行比例：即失敗後重試通過，或者結果與同一提交同配置嘅另一次運行不一致。
- **影響。** 一個測試阻塞或減慢咗多少條流水線、拉取請求或合併隊列條目，以及佢嘅重試消耗咗多少機器時間。一個不穩定率低但喺每條流水線中都運行嘅測試，可能比一個非常不穩定但很少運行嘅測試成本更高。
- **趨勢。** 新引入嘅不穩定測試是否比修復舊嘅更快。喺合併之前將新更改嘅測試重複運行幾次，可以喺源頭捕獲許多不穩定情況。

確認測試穩定所需嘅運行次數比直覺建議嘅更多。如果測試每次運行失敗嘅概率為*p*，那麼喺*n*次運行中至少看到一次失敗嘅機率係 1 − (1 − p)ⁿ。對於一個失敗率為 1% 嘅測試，10 次運行只有約 10% 嘅機率捕獲到它，而需要約 300 次運行才能以 95% 嘅置信度捕獲到它。少數幾次綠色重 run 係修復有效嘅弱證據。

## 何時唔值得做{#when-it-isnt-worth-it}

唔係每個不穩定測試都值得調查，亦唔係每個團隊都需要不穩定測試工具：

- **低價值測試。** 如果一個不穩定測試重複咗其他測試已經提供嘅覆蓋率，刪除它可能係正確嘅修復方法。無人信任嘅測試反正亦提供唔到任何覆蓋率。
- **基礎設施問題。** 當失敗集中喺某一臺機器、runner 鏡像或一天中嘅某個時段時，修復環境比逐個修復測試更便宜。
- **小型、快速嘅測試套件。** 對於擁有快速套件同一個已知不穩定測試嘅小團隊，共享備忘錄並喺本週修復比使用追蹤系統更好。當套件規模、貢獻者數量或流水線數量使得無人能記住哪些失敗係噪聲時，專用嘅檢測同隔離就會帶來回報。
- **關鍵路徑。** 對於保護支付、數據完整性或安全嘅測試，隔離係錯誤嘅工具。呢啲測試應該一直阻塞直到被修復，即使這樣會造成不便。
