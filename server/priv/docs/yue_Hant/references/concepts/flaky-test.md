# 乜嘢係不穩定測試？ {#what-is-a-flaky-test}

不穩定測試係一種自動化測試，喺針對同一套代碼運行時，有時通過、有時失敗，而被測代碼同測試本身都冇改動過。佢嘅結果取決於測試控制唔到嘅因素，例如時機、測試執行順序、其他測試遺留嘅狀態、運行機器，或者透過網絡呼叫嘅服務。因此，不穩定失敗並唔能可靠反映被測變更嘅情況，亦正係因為咁，不穩定測試成本高昂：每個紅色結果都必須經過調查或重試，先至可以令人信服。

不穩定性喺任何規模都好常見。Google 報告指，佢哋大約有 1.5% 嘅測試運行產生不穩定結果，而幾乎 16% 嘅測試出現某種程度嘅不穩定性（[Flaky Tests at Google and How We Mitigate Them](https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html)，2016）。

## 不穩定測試點樣顯現 {#how-flaky-tests-show-up}

只有當一個測試針對相同輸入同時產生通過同失敗兩種結果時，先至會被認定為不穩定。實際上，呢類證據通常來自以下三個來源之一：

- **運行內重試。** 測試失敗後，runner 會重試，而重試通過。呢個係成本最低嘅信號，大多數測試 runner 都能夠產生。
- **同一 commit 嘅不同運行結果不一致。** 同一 commit 同配置嘅兩次 CI 運行對某個測試報告唔同結果，例如 PR 上嘅一次運行同人手點擊重試後嘅另一次運行。
- **刻意重複執行。** 故意連續多次運行某個測試，睇下佢會唔會失敗。團隊就用呢種方法來確認懷疑嘅不穩定問題，或者喺合併新測試之前檢查其穩定性。

只有當所有關鍵因素都相同時，結果先至算係不穩定性嘅證據：commit、構建配置、設備或模擬器、作業系統版本，以及工具鏈。如果一個測試喺 iOS 17 失敗但喺 iOS 18 通過，可能其中一個版本存在真實且確定性嘅 bug。

## 各構建系統如何檢測不穩定測試 {#how-it-works-per-build-system}

每種工具鏈都可以重試同重複執行測試，但佢哋記錄同報告結果嘅方式唔同。

### Xcode {#xcode}

`xcodebuild` 同測試計劃支援測試重複執行。`-retry-tests-on-failure` 會重試失敗嘅測試，`-test-iterations <n>` 設定允許嘅嘗試次數，而 `-run-tests-until-failure` 會重複執行測試直到失敗為止，這對重現懷疑嘅不穩定問題好有用。測試計劃提供同測試重複模式相同嘅選項，另外仲可以選擇以隨機順序運行測試，從而暴露隱藏嘅順序依賴關係。

每次嘗試都會儲存喺 `.xcresult` bundle 入面，所以失敗後重試通過嘅測試喺嗰度清晰可見。Xcode 唔會跨運行保留歷史記錄，因此要檢測從未喺同一運行中重試嘅不穩定問題，就需要比較同一 commit 唔同運行嘅結果 bundle。

### Gradle {#gradle}

Gradle 嘅 `Test` task 本身唔會重試失敗嘅測試。[Test Retry plugin](https://github.com/gradle/test-retry-gradle-plugin)（`org.gradle.test-retry`）會向 `Test` tasks 加入 `retry` 區塊，並提供例如 `maxRetries` 同 `failOnPassedAfterRetry` 等選項。失敗後重試通過嘅測試會喺測試報告同 JUnit XML 中顯示兩次嘗試。測試框架亦會提供自己嘅重複執行工具，例如 JUnit 5 嘅 `@RepeatedTest`。

Gradle 嘅構建快取亦可能掩蓋不穩定性：如果一個可快取嘅 `Test` task 輸入冇變，就會直接從快取恢復而唔係實際運行，導致曾經通過嘅測試即使唔執行亦會持續顯示通過。當你要衡量不穩定性時，請使用 `--rerun-tasks` 強制運行測試，或者喺禁用構建快取嘅情況下運行 `Test` task。

### Bazel {#bazel}

Bazel 內置支援。將測試 target 標記為 `flaky = True` 會讓 Bazel 最多運行三次，並且只有當所有嘗試都失敗時先至判定為失敗。`--flaky_test_attempts` 標誌可以設定嘗試次數而唔改變 target，而當測試喺失敗嘗試後通過時，target 結果會報告為 `FLAKY`。如果要刻意衡量不穩定性，`--runs_per_test=<n>` 會多次運行測試，而 `--runs_per_test_detects_flakes` 則會喺至少有一次運行通過且有一次失敗時，將分片報告為 `FLAKY`。

Bazel 快取測試結果嘅方式同快取構建產物一樣。使用相同輸入並通過嘅測試會報告為 `(cached) PASSED` 而唔會再次運行，無論係本地定係從遠程快取。當你需要全新執行時，請使用 `--cache_test_results=no`（或 `--nocache_test_results`）。Bazel 文件亦建議唔好依賴 `flaky = True`，因為佢會永久隱藏被重試嘅失敗。

### 其他測試 runner {#other-test-runners}

幾乎處處都有類似模式：pytest 有 `pytest-rerunfailures` 插件，Jest 有 `jest.retryTimes()`，而 Elixir 嘅 ExUnit 有 `mix test --repeat-until-failure` 並會列印所用嘅隨機種子，以便可以使用 `--seed` 重現依賴順序嘅失敗。

## 不穩定測試嘅常見成因 {#common-causes}

一項針對開源項目中不穩定測試嘅實證研究（[Luo et al., FSE 2014](https://doi.org/10.1145/2635868.2635920)）發現，異步等待、併發性以及測試順序依賴係最常見嘅根本原因。下面嘅列表涵蓋咗呢啲原因以及其他團隊最常遇到嘅成因。

- **異步等待同固定休眠。** 測試會等待一段固定時間讓工作完成，例如 `sleep(1)` 或帶有短超時嘅預期，但工作有時需要更長時間，特別係喺負載較高嘅 CI 機器上。應該直接等待條件本身達成，並設定一個寬鬆嘅上限。
- **併發性。** 兩個線程或任務喺共享數據上發生競爭，或者測試喺背景操作完成之前就進行斷言。呢類失敗往往取決於 CPU 數量同負載，所以佢哋通常出現喺 CI 環境，而唔係快速嘅筆記本電腦上。
- **測試順序依賴同共享狀態。** 測試依賴另一個測試創建或忘記清理嘅狀態：例如單例、數據庫記錄、磁盤上嘅文件、`UserDefaults`、環境變量，或者被 mock 嘅全局變量。以隨機順序或並行方式運行測試可以暴露呢類問題。
- **時間同日期。** 使用真實時鐘嘅測試可能會喺午夜、月底、夏令時變更期間，或者喺其他時區失敗。應該注入一個時鐘來代替。
- **未設定種子嘅隨機性同無序集合。** 隨機數據冇有記錄種子，或者斷言依賴哈希映射或集合嘅迭代順序。
- **網絡同外部服務。** 當真實 API、套裝註冊表或共享暫存環境緩慢或不可用時，對佢哋嘅調用會失敗。應該喺邊界處將佢哋 stub 掉，並保留少量明確嘅集成測試。
- **資源壓力同環境狀態。** 機器緩慢或過載、模擬器或仿真器未重置、磁盤已滿，或者端口已被另一個作業使用。當許多無關嘅測試同時失敗時，應該先懷疑環境問題，而唔係測試本身。
- **UI 測試。** 端到端同 UI 測試結合咗上述大多數成因，再加上動畫、渲染時機同系統對話框，所以佢哋比單元測試更常出現不穩定情況。

如果一個測試喺更改後持續失敗，佢並唔係不穩定；而係回歸錯誤。不穩定標籤應該只保留給嗰啲喺相同代碼上產生過兩種結果（通過同失敗）嘅測試。

## 修復、重試同隔離 {#fixing-retrying-and-quarantining}

團隊通常會結合三種應對方式，將佢哋分開處理會更有幫助：

- **修復**根本原因。呢係唯一可以恢復測試價值嘅應對方式。記錄下來嘅嘗試次數、失敗訊息以及每次失敗運行嘅條件，都係指向根本原因嘅證據。
- **重試**以保持流水線繼續運行。重試係有用嘅檢測信號，但無差別嘅重試會掩蓋問題，並為每次失敗運行增加機器時間。即使重試通過，仍然應該將其記錄為不穩定結果，而唔係靜默丟棄。
- **隔離**已知嘅不穩定測試，以便喺修復期間佢不再阻塞合併。被隔離嘅測試要么繼續運行但忽略其失敗（靜音），從而繼續產生證據；要么完全唔運行（跳過），從而移除其覆蓋範圍。隔離需要指定負責人同退出條件，否則被隔離嘅測試會不斷累積，導致覆蓋範圍悄然縮小。

## 如何衡量不穩定性 {#how-to-measure-flakiness}

按每個測試追蹤不穩定性，而唔係只按流水線：

- **不穩定率。** 產生不穩定結果嘅測試運行比例：例如失敗後重試通過，或者結果與同一提交同配置嘅另一次運行不一致。
- **影響。** 一個測試阻塞或延緩咗多少條流水線、拉取請求或合併隊列條目，以及其重試消耗咗多少機器時間。一個不穩定率低但喺每條流水線中都運行嘅測試，可能比一個極不穩定但很少運行嘅測試成本更高。
- **趨勢。** 新引入嘅不穩定測試是否比舊嘅修復得更快。喺合併之前多次重複運行新的或更改過嘅測試，可以從源頭捕捉到許多不穩定情況。

確認測試穩定所需嘅運行次數比直覺認為嘅要多。如果一個測試每次運行失敗嘅概率為 *p*，那麼喺 *n* 次運行中至少看到一次失敗嘅機率係 1 − (1 − p)ⁿ。對於一個失敗率為 1% 嘅測試，10 次運行只有約 10% 嘅機率能捕捉到它，而要達到 95% 嘅置信度則需要約 300 次運行。少數幾次綠色嘅重 run 並唔足以證明修復有效。

## 何時唔值得做 {#when-it-isnt-worth-it}

並唔係每個不穩定測試都值得調查，亦都唔係每個團隊都需要不穩定測試工具：

- **低價值測試。** 如果一個不穩定測試重複咗其他測試已經提供嘅覆蓋範圍，刪除它可能係正確嘅修復方法。反正冇人信任嘅測試亦都提供唔到任何覆蓋範圍。
- **基礎設施問題。** 當失敗集中出現喺某台機器、runner 鏡像或特定時間段時，修復環境比逐一修復測試更划算。
- **小型、快速嘅測試套件。** 對於擁有快速測試套件且只有一個已知不穩定測試嘅小型團隊，一份共享筆記並喺本週內修復，比建立追蹤系統更有效。當測試套件規模、貢獻者數量或流水線數量達到令人無法記住哪些失敗係噪音嘅程度時，專用嘅檢測同隔離措施才會顯現價值。
- **關鍵路徑。** 對於保護支付、數據完整性或安全嘅測試，隔離係錯誤嘅工具。呢類測試應該一直阻塞直到被修復，即使這樣會帶來不便。

## 使用 Tuist 進行不穩定測試檢測 {#flaky-test-detection-with-tuist}

[Tuist](https://tuist.dev)記錄來自 Xcode、Gradle、Bazel、Elixir 及其他支持集成嘅每次測試嘗試，當測試喺相同代碼上失敗又通過時（無論係喺重試過程中，還係對於支持嘅集成喺同一提交嘅不同 CI 運行之間），將其標記為不穩定，並允許團隊喺修復期間手動或通過自動化方式靜音或跳過已知嘅不穩定測試。支持情況同要求因工具鏈而異：

- <.localized_link href="/guides/features/test-insights/flaky-tests">不穩定測試</.localized_link>解釋咗檢測、隔離同對新測試進行壓力測試嘅工作原理，並提供咗每種工具鏈嘅指南。
- <.localized_link href="/guides/features/test-insights">測試洞察</.localized_link>涵蓋咗首先記錄測試結果嘅相關內容。
- [我嘅測試不穩定](https://tuist.dev/solutions/flaky-tests)係一份實用指南，指導團隊如何診斷同控制不穩定測試。
