# 乜嘢係不穩定測試？ {#what-is-a-flaky-test}

不穩定測試係一種自動化測試，喺針對同一份代碼運行時，有時通過、有時失敗，而待測代碼同測試本身都冇任何改變。其結果取決於測試無法控制嘅因素，例如時間、測試執行順序、其他測試遺留嘅狀態、運行機器，或者透過網絡調用嘅服務。因此，不穩定失敗並唔能可靠反映被測試變更嘅問題，這正係不穩定測試成本高昂嘅原因：每個紅色結果都必須經過調查或重試，先至值得信賴。

不穩定性喺各種規模下都好常見。Google 報告指出，佢哋大約 1.5% 嘅測試運行會產生不穩定結果，而且幾乎 16% 嘅測試顯示出某種程度嘅不穩定性（[Flaky Tests at Google and How We Mitigate Them](https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html)，2016 年）。

## 不穩定測試點樣出現 {#how-flaky-tests-show-up}

只有當一個測試針對相同輸入產生兩種不同結果時，先至知道佢係不穩定嘅。實際上，呢類證據通常來自以下三個來源之一：

- **運行內嘅重試。** 測試失敗後，運行器會重試，而重試通過。這係成本最低嘅信號，大多數測試運行器都能提供。
- **同一提交嘅不同運行結果不一致。** 同一提交同配置嘅兩次 CI 運行對某個測試報告咗不同結果，例如拉取請求中嘅一次運行，以及有人點擊重試後嘅另一次運行。
- **刻意重複執行。** 故意連續多次運行某個測試，以觀察佢是否會失敗。團隊用呢種方法來確認疑似嘅不穩定問題，或者喺合併新測試之前檢查其穩定性。

只有當所有相關因素都相同時，結果先至算係不穩定性嘅證據：包括提交、構建配置、設備或模擬器、操作系統版本同工具鏈。如果一個測試喺 iOS 17 上失敗但喺 iOS 18 上通過，可能係其中一個系統存在真實且可確定嘅錯誤。

## 各構建系統如何檢測不穩定測試 {#how-it-works-per-build-system}

每種工具鏈都可以重試同重複執行測試，但佢哋記錄同報告結果嘅方式有所不同。

### Xcode {#xcode}

`xcodebuild` 同測試計劃支持測試重複執行。`-retry-tests-on-failure` 會重跑失敗嘅測試，`-test-iterations <n>` 設定允許嘅嘗試次數，而 `-run-tests-until-failure` 會重複執行測試直到失敗為止，這對於復現疑似嘅不穩定問題很有用。測試計劃提供咗同測試重複模式相同嘅選項，另外仲提供隨機順序運行測試嘅選項，從而暴露隱藏嘅順序依賴關係。

每次嘗試都會儲存喺 `.xcresult` 捆綁包中，因此喺重試中先失敗後通過嘅測試可以喺嗰度看到。Xcode 唔會跨運行保留歷史記錄，因此要檢測從未喺同一運行中重試過嘅不穩定測試，就需要比較同一提交不同運行嘅結果捆綁包。

### Gradle {#gradle}

Gradle 嘅 `Test` 任務本身唔會重試失敗嘅測試。[Test Retry plugin](https://github.com/gradle/test-retry-gradle-plugin) (`org.gradle.test-retry`) 會向 `Test` 任務添加 `retry` 區塊，並提供諸如 `maxRetries` 同 `failOnPassedAfterRetry` 等選項。先失敗後通過嘅測試會喺測試報告同 JUnit XML 中顯示兩次嘗試。測試框架亦提供自己嘅重複執行工具，例如 JUnit 5 嘅 `@RepeatedTest`。

Gradle 嘅構建緩存亦可能掩蓋不穩定性：如果 `Test` 任務嘅輸入未變且可緩存，佢會直接從緩存恢復而非實際執行，導致曾經通過嘅測試無需執行就持續顯示通過。當你測量不穩定性時，請使用 `--rerun-tasks` 強制運行測試，或者喺禁用構建緩存嘅情況下運行 `Test` 任務。

### Bazel {#bazel}

Bazel 內置咗支持。將測試目標標記為 `flaky = True` 會讓 Bazel 最多運行三次，並且只有當所有嘗試都失敗時先至標記為失敗。`--flaky_test_attempts` 標誌可以設定嘗試次數而無需更改目標，當測試喺一次失敗嘗試後通過時，目標結果會報告為 `FLAKY`。為了刻意測量不穩定性，`--runs_per_test=<n>` 會多次運行測試，而 `--runs_per_test_detects_flakes` 會喺至少有一次運行通過且有一次運行失敗時，將分片報告為 `FLAKY`。

Bazel 以同緩存構建輸出相同嘅方式緩存測試結果。使用相同輸入通過嘅測試會被報告為 `(cached) PASSED` 而無需再次運行，無論係本地定係從遠程緩存。當你需要全新執行時，請使用 `--cache_test_results=no`（或 `--nocache_test_results`）。Bazel 文檔亦建議唔好依賴 `flaky = True`，因為佢會永久隱藏佢所重試嘅失敗。

### 其他測試運行器 {#other-test-runners}

幾乎到處都存在類似模式：pytest 有 `pytest-rerunfailures` 插件，Jest 有 `jest.retryTimes()`，而 Elixir 嘅 ExUnit 有 `mix test --repeat-until-failure` 並會打印所用嘅隨機種子，以便可以使用 `--seed` 重現依賴順序嘅失敗。

## 不穩定測試嘅常見原因 {#common-causes}

一項針對開源項目中不穩定測試嘅實證研究（[Luo et al., FSE 2014](https://doi.org/10.1145/2635868.2635920)）發現，異步等待、併發性同測試順序依賴係最常見嘅根本原因。下面嘅列表涵蓋咗呢啲原因以及其他團隊最常遇到嘅原因。

- **異步等待同固定休眠。** 測試等待固定時間讓工作完成，例如 `sleep(1)` 或帶有短超時嘅期望，但有時工作需要更長時間，特別係喺負載較高嘅 CI 機器上。應該直接等待條件本身，並設定一個寬鬆嘅上限。
- **併發性。** 兩個線程或任務喺共享數據上發生競爭，或者測試喺後台操作完成之前就進行斷言。呢類失敗通常取決於 CPU 數量同負載，因此佢哋會喺 CI 環境中出現，而唔係喺快速嘅筆記本電腦上。
- **測試順序依賴同共享狀態。** 測試依賴另一個測試創建或忘記清理嘅狀態：例如單例、數據庫行、磁盤上嘅文件、`UserDefaults`、環境變量或被模擬嘅全局變量。以隨機順序或並行方式運行測試可以暴露呢個問題。
- **時間同日期。** 使用真實時鐘嘅測試會喺午夜、月底、夏令時變更期間或其他時區失敗。應該注入一個時鐘來代替。
- **未設定種子嘅隨機性同無序集合。** 沒有記錄種子嘅隨機數據，或者依賴哈希映射或集合迭代順序嘅斷言。
- **網絡同外部服務。** 當真實 API、包註冊表或共享預演環境緩慢或不可用時，對佢哋嘅調用會失敗。應該喺邊界處模擬（stub）呢啲服務，並保持少量明確嘅集成測試。
- **資源壓力同環境狀態。** 機器緩慢或過載、未重置嘅模擬器或仿真器、磁盤已滿，或者端口已被另一個作業使用。當許多無關嘅測試同時失敗時，應該先懷疑環境問題而唔係測試本身。
- **UI 測試。** 端到端同 UI 測試將上述大多數原因同動畫、渲染計時以及系統對話框結合在一起，因此佢哋比單元測試更常出現不穩定情況。

如果一個測試喺更改後持續失敗，佢並唔係不穩定；而係回歸錯誤。不穩定標籤應該保留畀嗰啲喺相同代碼上產生兩種結果（通過同失敗）嘅測試。

## 修復、重試同隔離 {#fixing-retrying-and-quarantining}

團隊通常會結合三種應對方式，將佢哋分開處理會更有幫助：

- **修復**根本原因。這係唯一能恢復測試價值嘅應對方式。記錄下來嘅嘗試次數、失敗訊息以及每次失敗運行嘅條件，都係指向根本原因嘅證據。
- **重試**以保持流水線繼續運行。重試係有用嘅檢測信號，但無差別嘅重試會掩蓋問題並增加每次失敗運行嘅機器時間。通過重試後通過嘅測試仍然應該被記錄為不穩定結果，而唔係靜默丟棄。
- **隔離**已知嘅不穩定測試，以便喺修復期間停止阻塞合併。被隔離嘅測試要么繼續運行但忽略其失敗（靜音），從而繼續產生證據；要么完全唔運行（跳過），從而移除其覆蓋率。隔離需要指定負責人同退出條件，否則被隔離嘅測試會積累，導致覆蓋率悄悄下降。

## 如何衡量不穩定性 {#how-to-measure-flakiness}

按每個測試追蹤不穩定性，而唔係僅按流水線追蹤：

- **不穩定率。** 產生不穩定結果嘅測試運行比例：即失敗後重試通過，或者結果與相同提交和配置嘅另一次運行不一致。
- **影響。** 一個測試阻塞或減慢咗多少條流水線、拉取請求或合併隊列條目，以及其重試消耗咗多少機器時間。一個不穩定率低但喺每條流水線中都運行嘅測試，可能比一個極不穩定但很少運行嘅測試成本更高。
- **趨勢。** 新引入嘅不穩定測試是否比修復舊嘅更快。喺合併之前多次重複新測試或更改過嘅測試，可以從源頭捕獲許多不穩定問題。

確認測試穩定所需嘅運行次數比直覺認為嘅要多。如果一個測試每次運行失敗嘅概率為 *p*，那麼喺 *n* 次運行中至少看到一次失敗嘅概率係 1 − (1 − p)ⁿ。對於一個失敗率為 1% 嘅測試，10 次運行只能以約 10% 嘅概率捕獲到它，而需要約 300 次運行才能以 95% 嘅置信度捕獲到它。少數幾次綠色嘅重運行列並唔係修復有效嘅有力證據。

## 何時不值得这样做 {#when-it-isnt-worth-it}

並唔係每個不穩定測試都值得調查，亦都唔係每個團隊都需要不穩定測試工具：

- **低價值測試。** 如果一個不穩定測試重複咗其他測試已經提供嘅覆蓋率，刪除它可能係正確嘅修復方法。反正沒人信任嘅測試提供唔到任何覆蓋率。
- **基礎設施問題。** 當失敗集中喺某台機器、運行器鏡像或特定時間段時，修復環境比逐個修復測試更便宜。
- **小型、快速嘅測試套件。** 對於擁有快速測試套件且只有一個已知不穩定測試嘅小團隊來說，共享筆記並喺本週修復比使用追蹤系統更有效。當測試套件規模、貢獻者數量或流水線數量使得無人能夠記住哪些失敗係噪音時，專用嘅檢測同隔離措施才會帶來回報。
- **關鍵路徑。** 對於保護支付、數據完整性或安全性嘅測試，隔離係錯誤嘅工具。呢啲測試應該一直阻塞直到被修復，即使這樣會造成不便。

## 使用 Tuist 進行不穩定測試檢測 {#flaky-test-detection-with-tuist}

[Tuist](https://tuist.dev) 記錄來自 Xcode、Gradle、Bazel、Elixir 及其他支持集成嘅每次測試嘗試，當測試喺相同代碼上失敗並通過時（無論係喺重試過程中，定係對於支持嘅集成喺相同提交嘅 CI 運行之間），將其標記為不穩定，並允許團隊喺修復期間手動或通過自動化方式靜音或跳過已知嘅不穩定測試。支持情況和要求因工具鏈而異：

- <.localized_link href="/guides/features/test-insights/flaky-tests">不穩定測試</.localized_link> 解釋咗檢測、隔離同對新測試進行壓力測試嘅工作原理，並提供咗每種工具鏈嘅指南。
- <.localized_link href="/guides/features/test-insights">測試洞察</.localized_link> 涵蓋咗首先記錄測試結果嘅內容。
- [我嘅測試不穩定](https://tuist.dev/solutions/flaky-tests) 係一份實用指南，指導團隊如何診斷和控制不穩定測試。
