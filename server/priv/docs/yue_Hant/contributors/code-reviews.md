# 程式碼審查 {#code-reviews}

審查拉取請求（pull request）係一種常見嘅貢獻方式。雖然持續整合（CI）可以確保程式碼執行預期功能，但並唔足夠。有些貢獻特質無法自動化：設計、程式碼結構同架構、測試質量，或者錯別字。以下章節代表程式碼審查流程嘅不同方面。

## 可讀性 {#readability}

程式碼會唔會清晰表達其意圖？**如果你需要花大量時間先至搞清楚程式碼做緊乜，就表示程式碼實現需要改進。** 建議將程式碼拆分為更易理解嘅細小抽象。作為最後手段，亦可以加入註釋解釋背後嘅理由。問下自己，喺冇周圍上下文（例如拉取請求描述）嘅情況下，將來會唔會仍然能夠理解呢段程式碼。

## 小型拉取請求 {#small-pull-requests}

大型拉取請求難以審查，容易遺漏細節。如果拉取請求變得太大而難以管理，建議作者將其拆分。

> [!NOTE]
> **例外情況**
>
> 有少數情況無法拆分拉取請求，例如當變更緊密耦合并且無法分割時。在這些情況下，作者應該提供清晰嘅變更說明同背後理由。


## 一致性 {#consistency}

保持變更與項目其餘部分一致非常重要。不一致會增加維護難度，因此我哋應該避免。如果有向用戶輸出訊息或報告錯誤嘅既定方法，我哋應該遵循。如果作者不同意項目標準，建議佢哋開啟一個議題（issue），以便進一步討論。

## 測試 {#tests}

測試令到我哋可以有信心地修改程式碼。拉取請求中嘅程式碼應該經過測試，並且所有測試都應該通過。好嘅測試係指能夠穩定產生相同結果，並且易於理解同維護嘅測試。審查者大部分時間都花在實現程式碼上，但測試同樣重要，因為佢哋亦係程式碼。

## 破壞性變更 {#breaking-changes}

破壞性變更會對 Tuist 用戶造成不良體驗。除非絕對必要，否則貢獻應該避免引入破壞性變更。我哋可以利用許多語言特性來演進 Tuist 嘅介面，而無需進行破壞性變更。一項變更是咪具有破壞性可能並不明顯。驗證變更是否具破壞性嘅一種方法，係針對 fixtures 目錄中嘅示例項目運行 Tuist。這需要我哋換位思考，想像這些變更會如何影響用戶。
