# 代碼審查 {#code-reviews}

審查拉取請求（pull request）係一種常見嘅貢獻方式。雖然持續整合（CI）可以確保代碼執行預期功能，但並不足夠。有些貢獻特質無法自動化：設計、代碼結構同架構、測試質量，或者錯別字。以下章節代表代碼審查流程嘅唔同方面。

## 可讀性 {#readability}

代碼有無清晰表達其意圖？**如果你需要花大量時間先至搞清楚代碼做乜，就表示代碼實現需要改進。** 建議將代碼拆分為更易理解嘅小型抽象。作為最後手段，亦可以添加註釋解釋背後嘅推理。問下自己，如果冇拉取請求描述等周圍上下文，你喺不久將來仲能否理解呢段代碼。

## 小型拉取請求 {#small-pull-requests}

大型拉取請求難以審查，容易遺漏細節。如果拉取請求變得太大而難以管理，建議作者將其拆分。

> [!NOTE]
> **例外情況**
>
> 有好少情況下無法拆分拉取請求，例如當變更緊密耦合且無法拆分時。在這些情況下，作者應該提供清晰嘅變更說明同背後嘅推理。


## 一致性 {#consistency}

確保變更與項目其餘部分保持一致非常重要。不一致會令維護複雜化，因此我哋應該避免。如果有向用戶輸出訊息或報告錯誤嘅既定方法，我哋應該遵循。如果作者不同意項目標準，建議佢哋開啟一個 issue 以便進一步討論。

## 測試 {#tests}

測試令我哋有信心修改代碼。拉取請求中嘅代碼應該經過測試，並且所有測試都應該通過。好嘅測試係指能夠一致產生相同結果，並且易於理解同維護嘅測試。審查者大部分時間花喺實現代碼上，但測試同樣重要，因為佢哋亦係代碼。

## 破壞性變更 {#breaking-changes}

破壞性變更會對 Tuist 用戶造成不良體驗。除非絕對必要，否則貢獻應該避免引入破壞性變更。我哋可以利用許多語言特性來演進 Tuist 嘅接口，而無需進行破壞性變更。變更是否具有破壞性可能並不明顯。驗證變更是咪具有破壞性嘅一種方法，係喺 fixtures 目錄中針對 fixture 項目運行 Tuist。這需要我哋換位思考，想像變更會點樣影響用戶。
