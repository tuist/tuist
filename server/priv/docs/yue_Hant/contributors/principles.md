# 原則 {#principles}

本頁介紹 Tuist 設計與開發的核心原則。這些原則會隨著專案演進，以確保成長可持續，並與專案基礎保持一致。

## 預設採用約定 {#default-to-conventions}

Tuist 之所以存在，其中一個原因在於 Xcode 在約定方面較弱，導致專案變得複雜、難以擴展與維護。因此，Tuist 採取不同做法，預設採用簡單且經過深思熟慮的約定。**開發者可以選擇不遵循這些約定，但這是需要刻意做出的決定，感覺並不自然。**

例如，有一個約定位於透過提供的公開介面來定義目標之間的依賴關係。這樣做可確保 Tuist 生成的專案具備正確的設定，使連結能夠正常運作。開發者也可以透過建置設定來定義依賴關係，但這種做法是隱式的，因而會破壞依賴某些約定才能運作的 Tuist 功能，例如 `tuist graph` 或 `tuist cache`。

我們預設採用約定的原因是：能替開發者做的決定越多，他們就能越專注於為應用程式打造功能。當像許多專案那樣缺乏約定時，我們就必須做出與其他決定不一致的選擇，結果會產生難以管理的意外複雜性。

## Manifest 檔案是唯一真相來源 {#manifests-are-the-source-of-truth}

多層設定以及它們之間的合約，會導致專案設定難以理解與維護。試想一個典型專案：專案定義位於 `.xcodeproj` 目錄中，CLI 邏輯位於腳本（例如 `Fastfiles`）中，而 CI 邏輯位於管線中。這三層之間存在需要維護的合約。*你是否經常遇到這種情況：修改了專案中的某些內容，過了一週才發現發佈腳本壞掉了？*

我們可以透過單一真相來源（即 manifest 檔案）來簡化這一點。這些檔案提供 Tuist 生成 Xcode 專案所需的資訊，讓開發者可以用來編輯檔案。此外，它還允許使用標準命令，從本地或 CI 環境建置專案。

**Tuist 應承擔複雜性，並提供簡單、安全且令人愉悅的介面，盡可能明確地描述專案。**

## 將隱式變為顯式 {#make-the-implicit-explicit}

Xcode 支援隱式設定。一個很好的例子是推斷隱式定義的依賴關係。雖然隱式設定在設定簡單的小型專案中尚可接受，但隨著專案規模擴大，可能會導致速度變慢或出現異常行為。

Tuist 應為隱式的 Xcode 行為提供顯式 API。它也應支援定義 Xcode 的隱式行為，但實作方式應鼓勵開發者選擇顯式做法。支援 Xcode 的隱式行為與細微之處有助於推動 Tuist 的採用，之後團隊可以花時間逐步消除隱式設定。

依賴關係的定義就是一個很好的例子。雖然開發者可以透過建置設定與階段來定義依賴關係，但 Tuist 提供了一個優雅的 API，鼓勵大家採用。

**將 API 設計為顯式，讓 Tuist 能夠對專案執行一些否則無法進行的檢查與最佳化。** 此外，它還啟用了诸如 `tuist graph`（匯出依賴圖的表示）或 `tuist cache`（將所有目標快取為二進位檔）等功能。

> [!TIP]
> 我們應將每個從 Xcode 移植功能的要求視為機會，透過簡單且顯式的 API 來簡化概念。


## 保持簡單 {#keep-it-simple}

擴展 Xcode 專案的主要挑戰之一在於：**Xcode 向使用者暴露了大量複雜性。** 因此，團隊的「巴士係數」很高，只有少數人理解專案以及建置系統拋出的錯誤。這種情況很糟糕，因為團隊過度依賴少數人。

Xcode 是個出色的工具，但多年的改進、新平台與程式語言都反映在其表面上，使其難以保持簡單。

Tuist 應把握機會保持簡單，因為處理簡單的事物既有趣又能激勵我們。沒有人願意花費時間去除錯發生在編譯過程最後階段的錯誤，或搞清楚為何無法在裝置上執行應用程式。Xcode 將任務委派給底層建置系統，在某些情況下，它在將錯誤轉化為可操作項目方面做得很差。你是否曾經遇到 *「找不到 framework X」* 錯誤卻不知如何處理？想像一下，如果我們能得到一份潛在根本原因清單，該有多好。

## 從開發者體驗出發 {#start-from-the-developers-experience}

Xcode 周圍缺乏創新（或者換句話說，不如其他程式環境那麼多）的部分原因在於：**我們經常從現有解決方案開始分析問題。** 因此，如今我們找到的大多數解決方案都圍繞著相同的想法與工作流程。雖然將現有解決方案納入考量是好的，但我們不應讓它們限制我們的創造力。

我們喜歡像 [Tom Preston](https://tom.preston-werner.com/) 在 [這集 podcast](https://tom.preston-werner.com/) 中所說的那樣思考：*「只要符合宇宙的限制，大多數事情都能實現；你腦海中的想法，很可能都可以用程式碼實現。」* 如果 **我們想像理想的開發者體驗應該是什麼樣子**，實現它只是時間問題——從開發者體驗出發分析問題，能為我們提供獨特的視角，引導我們打造出使用者喜愛的解決方案。

我們可能會忍不住跟風，即使這意味著要忍受大家一直抱怨的不便。讓我們別這麼做。我會如何想像為應用程式建立封存檔？我希望程式碼簽署的流程是什麼樣子？我可以用 Tuist 幫助簡化哪些流程？例如，加入對 [Fastlane](https://fastlane.tools/) 的支援是某個問題的解決方案，而我們需要先理解這個問題。我們可以透過不斷問「為什麼」來找出問題的根本原因。一旦釐清動機來源，我們就能思考 Tuist 如何提供最佳協助。也許解決方案是與 Fastlane 整合，但重要的是，在做出取捨之前，我們不應忽視其他同樣可行的方案。

## 錯誤確實會發生 {#errors-can-and-will-happen}

我們開發者天生容易忽視錯誤可能發生的事實。結果，我們在設計和測試軟體時，往往只考慮理想情境。

Swift、其型別系統以及架構良好的程式碼或許能防止某些錯誤，但無法防止所有錯誤，因為有些錯誤超出我們的控制範圍。我們不能假設使用者永遠有網路連線，或系統指令一定會成功執行。Tuist 執行的環境並非我們可控管的沙箱，因此我們需要努力了解這些環境可能如何變化並影響 Tuist。

處理不當的錯誤會導致糟糕的使用者體驗，使用者可能會對專案失去信任。我們希望使用者享受 Tuist 的每一個環節，甚至包括我們呈現錯誤的方式。

我們應該換位思考，想像自己希望錯誤訊息告訴我們什麼。如果程式語言是錯誤傳播的溝通管道，而使用者是錯誤的接收端，那麼錯誤訊息就應該以目標對象（使用者）熟悉的語言撰寫。它們應包含足夠的資訊讓使用者了解發生了什麼事，並隱藏不相關的資訊。此外，它們應具備可操作性，告訴使用者可以採取哪些步驟來恢復。

最後但同樣重要的是，我們的測試案例應涵蓋失敗情境。這不僅能確保我們按預期處理錯誤，也能防止未來的開發者破壞這項邏輯。
