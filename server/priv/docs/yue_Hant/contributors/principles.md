# 原則 {#principles}

本頁介紹 Tuist 設計與開發的核心原則。這些原則會隨項目演進，以確保可持續增長，並與項目基礎保持一致。

## 預設採用約定 {#default-to-conventions}

Tuist 之所以存在，其中一個原因是 Xcode 在約定方面較弱，導致項目複雜、難以擴展和維護。因此，Tuist 採取不同做法，預設採用簡單且經過深思熟慮的約定。**開發者可以選擇不遵循這些約定，但這是刻意決定，感覺並不自然。**

例如，有一項約定是透過提供的公開介面來定義目標之間的依賴關係。這樣做能確保 Tuist 生成正確的配置，使連結順利運作。開發者亦可選擇透過構建設置來定義依賴關係，但這種做法屬於隱式定義，因而會破壞依賴某些約定的 Tuist 功能，例如 `tuist graph` 或 `tuist cache`。

我們預設採用約定的原因在於：我們能替開發者作出的決定越多，他們就越能專注於為應用程式打造功能。當許多項目缺乏約定時，我們不得不作出與其他決定不一致的選擇，結果產生難以管理的意外複雜性。

## 清單檔案是唯一真相來源 {#manifests-are-the-source-of-truth}

配置層級繁多且彼此之間存在合約，會令項目設置難以理解和維護。試想一般項目：項目定義位於 `.xcodeproj` 目錄，CLI 邏輯位於腳本（例如 `Fastfiles`），而 CI 邏輯則位於流水線。這三層之間存在需要維護的合約。*你有沒有遇過這種情況：修改了項目中的某些內容，一週後才發現發布腳本出錯？*

我們可以透過單一真相來源（即清單檔案）來簡化這一點。這些檔案為 Tuist 提供所需資訊，以生成 Xcode 項目，讓開發者用來編輯檔案。此外，它亦支援從本地或 CI 環境使用標準命令來構建項目。

**Tuist 應承擔複雜性，並提供簡單、安全且易用的介面，盡可能明確地描述項目。**

## 將隱式變為顯式 {#make-the-implicit-explicit}

Xcode 支援隱式配置。一個好例子是推斷隱式定義的依賴關係。雖然隱式做法在配置簡單的小型項目中尚可接受，但隨著項目規模擴大，可能會導致速度變慢或出現異常行為。

Tuist 應為隱式的 Xcode 行為提供顯式 API。它亦應支援定義 Xcode 的隱式行為，但以鼓勵開發者選擇顯式方式的方式實現。支援 Xcode 的隱式行為及細微之處有助於推動 Tuist 的採用，之後團隊可以花時間逐步消除隱式設定。

依賴關係的定義就是一個好例子。雖然開發者可以透過構建設置和階段來定義依賴關係，但 Tuist 提供了優雅的 API，鼓勵大家採用。

**將 API 設計為顯式，讓 Tuist 能夠對項目執行一些否則無法進行的檢查和優化。** 此外，它亦啟用如 `tuist graph`（匯出依賴關係圖的表示）或 `tuist cache`（將所有目標快取為二進制檔案）等功能。

> [!TIP]
> 我們應將每個從 Xcode 移植功能的請求視為機會，透過簡單且顯式的 API 來簡化概念。


## 保持簡單 {#keep-it-simple}

擴展 Xcode 項目時的主要挑戰之一在於：**Xcode 向用戶暴露了大量複雜性。** 因此，團隊的「巴士係數」很高，只有少數人理解項目及構建系統拋出的錯誤。這種情況不利，因為團隊過度依賴少數人。

Xcode 是一款出色的工具，但多年的改進、新平台和程式語言都反映在其表面上，使其難以保持簡單。

Tuist 應把握機會保持簡單，因為處理簡單的事物既有趣又能激勵我們。沒有人願意花時間去調試在編譯過程最後階段發生的錯誤，或弄明白為何無法在裝置上運行應用程式。Xcode 將任務委派給底層構建系統，而在某些情況下，它在將錯誤轉化為可操作事項方面表現欠佳。你是否曾遇到 *「找不到 framework X」* 錯誤卻不知如何處理？想像一下，如果我們能獲得一份潛在根本原因清單，情況會有多大的改善。

## 從開發者體驗出發 {#start-from-the-developers-experience}

Xcode 周圍缺乏創新（或者換句話說，不如其他程式環境那麼多）的部分原因在於：**我們經常從現有解決方案開始分析問題。** 結果，現今找到的大多數解決方案都圍繞相同的想法和工作流程。雖然將現有解決方案納入考量是可取的，但我們不應讓它們限制我們的創造力。

我們喜歡像 [Tom Preston](https://tom.preston-werner.com/) 在 [這集播客](https://tom.preston-werner.com/) 中所說的那樣思考：*「只要符合宇宙的約束，大多數事情都能實現；你腦海中的想法，很可能都可以用代碼實現。」* 如果 **我們想像理想的開發者體驗應該是什麼樣子**，實現它只是時間問題——從開發者體驗出發分析問題，為我們帶來獨特的視角，引領我們找到用戶喜愛的解決方案。

我們或許會忍不住跟風，即使意味著繼續忍受眾人不斷抱怨的不便。讓我們不要這樣做。我期望如何歸檔我的應用程式？我希望代碼簽名流程是怎樣的？我可以透過 Tuist 簡化哪些流程？例如，加入對 [Fastlane](https://fastlane.tools/) 的支援是解決某個問題的方案，但我們需要先理解該問題的本質。我們可以透過問「為什麼」來追尋問題根源。一旦釐清動機來源，我們就能思考 Tuist 如何提供最佳協助。解決方案可能是整合 Fastlane，但在權衡取捨之前，我們不應忽視其他同樣可行的方案。

## 錯誤難免發生 {#errors-can-and-will-happen}

我們開發者天生傾向忽視錯誤可能發生的事實。結果，我們在設計和測試軟體時，往往只考慮理想情境。

Swift、其類型系統以及架構良好的代碼或許能防止部分錯誤，但無法防止所有錯誤，因為有些錯誤超出我們的控制範圍。我們不能假設用戶永遠有網路連線，或系統指令一定會成功返回。Tuist 運行的環境並非我們可控的沙盒，因此我們需要努力了解它們可能如何變化並影響 Tuist。

處理不當的錯誤會導致糟糕的用戶體驗，用戶可能會對項目失去信任。我們希望用戶享受 Tuist 的每一個環節，包括我們呈現錯誤的方式。

我們應換位思考，想像我們期望錯誤訊息告訴我們什麼。如果程式語言是錯誤傳播的溝通渠道，而用戶是錯誤的接收者，那麼錯誤訊息應以目標對象（用戶）所使用的語言編寫。它們應包含足夠資訊讓用戶了解發生了什麼事，並隱藏不相關的資訊。此外，它們應具備可操作性，告知用戶可以採取哪些步驟來恢復。

最後但同樣重要的是，我們的測試案例應涵蓋失敗情境。這不僅確保我們按預期處理錯誤，也能防止未來的開發者破壞該邏輯。
