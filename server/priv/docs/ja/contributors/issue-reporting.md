# 問題の報告 {#issue-reporting}

Tuist のユーザーとして、バグや予期しない動作に遭遇することがあります。その場合は、修正できるよう報告してください。

## GitHub Issues がチケット管理プラットフォームです {#github-issues-is-our-ticketing-platform}

問題は Slack や他のプラットフォームではなく、[GitHub issues](https://github.com/tuist/tuist/issues) として GitHub で報告してください。GitHub は問題の追跡と管理に適しており、コードベースに近く、進捗を追跡できます。さらに、問題の詳細な説明を促すため、報告者は問題を考え、より多くのコンテキストを提供する必要があります。

## コンテキストが重要です {#context-is-crucial}

十分なコンテキストがない問題は不完全とみなされ、追加のコンテキストを求められます。提供されない場合、問題はクローズされます。次のように考えてください：提供するコンテキストが多いほど、問題を理解して修正しやすくなります。したがって、問題を修正してほしい場合は、可能な限り多くのコンテキストを提供してください。以下の質問に答えてみてください：

- 何をしようとしていましたか？
- グラフはどのように見えますか？
- どのバージョンの Tuist を使用していますか？
- これはあなたをブロックしていますか？

最小限の **再現プロジェクト** の提供も必須です。

## 再現プロジェクト {#reproducible-project}

### 再現プロジェクトとは何ですか？ {#what-is-a-reproducible-project}

再現プロジェクトは、問題を演示するための小さな Tuist プロジェクトです。この問題はしばしば Tuist のバグによって引き起こされます。再現プロジェクトには、バグを明確に示すために必要な最低限の機能のみを含めるべきです。

### なぜ再現テストケースを作成すべきですか？ {#why-should-you-create-a-reproducible-test-case}

再現プロジェクトにより、問題の原因を特定でき、これが修正への第一歩となります！バグレポートで最も重要なのは、バグを再現するために必要な正確な手順を記述することです。

再現プロジェクトは、バグを引き起こす特定の環境を共有する優れた方法です。あなたの再現プロジェクトは、助けたい人々を助ける最良の方法です。

### 再現プロジェクトを作成する手順 {#steps-to-create-a-reproducible-project}

- 新しい git リポジトリを作成します。
- リポジトリディレクトリで `tuist init` を使用してプロジェクトを初期化します。
- 見たエラーを再現するために必要なコードを追加します。
- コードを公開し（GitHub アカウントが適しています）、問題を作成する際にリンクします。

### 再現プロジェクトの利点 {#benefits-of-reproducible-projects}

- **影響範囲の縮小：** エラー以外をすべて削除することで、バグを探す必要がなくなります。
- **秘密のコードを公開する必要がありません：** メインサイトを公開できない場合があります（多くの理由で）。その一部を再現テストケースとして再作成することで、秘密のコードを公開せずに問題を公に示すことができます。
- **バグの証明：** 時々、バグはマシン上の設定の組み合わせによって引き起こされます。再現テストケースにより、貢献者がビルドを取得して自分のマシンでテストできます。これにより、問題の原因を検証し絞り込むのに役立ちます。
- **バグ修正の支援を得る：** 他の人があなたの問題を再現できれば、問題を修正する可能性が高まります。まず再現できなければ、バグを修正することはほぼ不可能です。
