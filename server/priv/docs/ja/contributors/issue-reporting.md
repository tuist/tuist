# 問題の報告 {#issue-reporting}

Tuist のユーザーとして、バグや予期しない動作に遭遇することがあります。その場合は、修正できるよう報告してください。

## GitHub Issues をチケット管理プラットフォームとして利用しています {#github-issues-is-our-ticketing-platform}

問題は Slack やその他のプラットフォームではなく、[GitHub issues](https://github.com/tuist/tuist/issues) として GitHub で報告してください。GitHub は問題の追跡と管理に適しており、コードベースに近く、問題の進捗を追跡できます。さらに、問題の詳細な説明を促すため、報告者は問題について考え、より多くのコンテキストを提供することになります。

## コンテキストが重要です {#context-is-crucial}

コンテキストが不十分な問題は不完全と判断され、作成者に追加のコンテキストが求められます。提供されない場合、その問題はクローズされます。次のように考えてください：提供するコンテキストが多いほど、問題を理解して修正しやすくなります。したがって、問題を修正してほしい場合は、可能な限り多くのコンテキストを提供してください。以下の質問に答えてみてください：

- 何を行おうとしていましたか？
- グラフはどのような構造ですか？
- 使用している Tuist のバージョンは何ですか？
- これは作業をブロックしていますか？

また、最小限の **再現可能なプロジェクト** の提供も必須です。

## 再現可能なプロジェクト {#reproducible-project}

### 再現可能なプロジェクトとは何ですか？ {#what-is-a-reproducible-project}

再現可能なプロジェクトは、問題をデモするための小さな Tuist プロジェクトです。この問題は、多くの場合 Tuist のバグによって引き起こされます。再現可能なプロジェクトには、バグを明確に示すために必要な最低限の機能のみを含めるべきです。

### なぜ再現可能なテストケースを作成すべきですか？ {#why-should-you-create-a-reproducible-test-case}

再現可能なプロジェクトにより、問題の原因を特定でき、それが修正への第一歩となります！バグ報告で最も重要なのは、バグを再現するために必要な正確な手順を記述することです。

再現可能なプロジェクトは、バグを引き起こす特定の環境を共有する優れた方法です。あなたの再現可能なプロジェクトは、あなたを支援したい人々を助ける最良の方法です。

### 再現可能なプロジェクトを作成する手順 {#steps-to-create-a-reproducible-project}

- 新しい git リポジトリを作成します。
- リポジトリディレクトリで `tuist init` を使用してプロジェクトを初期化します。
- 確認したエラーを再現するために必要なコードを追加します。
- コードを公開し（GitHub アカウントが適しています）、問題を作成する際にそのリンクを貼ります。

### 再現可能なプロジェクトの利点 {#benefits-of-reproducible-projects}

- **影響範囲の縮小：** エラー以外をすべて除去することで、バグを探す手間が省けます。
- **機密コードを公開する必要がない：** メインサイトを公開できない場合（多くの理由があります）があります。その一部を再現可能なテストケースとして再作成することで、機密コードを公開せずに問題を公に示すことができます。
- **バグの証明：** バグは、マシン上の設定の組み合わせによって引き起こされる場合があります。再現可能なテストケースにより、コントリビューターがビルドを取得して自分のマシンでテストできるため、問題の原因を検証し絞り込むのに役立ちます。
- **バグ修正の支援を受けられる：** 他の人が問題を再現できれば、その問題を修正できる可能性が高まります。まず再現できなければ、バグを修正することはほぼ不可能です。
