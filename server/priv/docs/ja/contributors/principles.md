# 原則 {#principles}

このページでは、Tuist の設計と開発の基盤となる原則を説明します。これらの原則はプロジェクトとともに進化し、プロジェクトの基盤と整合した持続可能な成長を実現することを目的としています。

## 規約をデフォルトとする {#default-to-conventions}

Tuist が存在する理由の一つは、Xcode が規約に弱く、その結果としてスケールや保守が難しい複雑なプロジェクトになりがちだからです。そのため、Tuist はシンプルかつ入念に設計された規約をデフォルトとする異なるアプローチを採用しています。**開発者は規約からオプトアウトできますが、それは自然ではない意識的な選択となります。**

例えば、提供される公開インターフェースを使用してターゲット間の依存関係を定義するための規約があります。これにより、Tuist はリンクが正しく動作するための適切な設定でプロジェクトが生成されることを保証します。開発者はビルド設定を通じて依存関係を定義することもできますが、それは暗黙的に行われるため、いくつかの規約に従うことに依存する `tuist graph` や `tuist cache` といった Tuist の機能を壊すことになります。

私たちが規約をデフォルトとする理由は、開発者に代わって下せる決定が増えれば増えるほど、彼らはアプリの機能構築に集中できるようになるからです。多くのプロジェクトで見られるように規約がない状態では、他の決定と一貫性のない判断を下すことになり、その結果として管理が難しい偶発的な複雑さが生まれてしまいます。

## マニフェストを唯一の情報源とする {#manifests-are-the-source-of-truth}

多数の設定レイヤーとその間の契約が存在すると、理解や保守が難しいプロジェクト構成になってしまいます。一般的なプロジェクトを少し考えてみてください。プロジェクトの定義は `.xcodeproj` ディレクトリに、CLI はスクリプト（例: `Fastfiles`）に、CI のロジックはパイプラインにあります。これらは維持すべき契約を持つ3つのレイヤーです。*プロジェクトで何かを変更した後、1週間後にリリーススクリプトが壊れていることに気づいた経験はどのくらいありますか？*

これを簡素化するには、マニフェストファイルを唯一の情報源とします。これらのファイルは、開発者がファイルを編集するために使用できる Xcode プロジェクトを生成するために Tuist が必要とする情報を提供します。さらに、ローカル環境または CI 環境からプロジェクトをビルドするための標準コマンドを使用可能にします。

**Tuist は複雑さを内部に抱え込み、プロジェクトを可能な限り明示的に記述するためのシンプルで安全、かつ使いやすいインターフェースを提供すべきです。**

## 暗黙的なものを明示化する {#make-the-implicit-explicit}

Xcode は暗黙的な設定をサポートしています。その良い例が、暗黙的に定義された依存関係の推論です。暗黙性は設定がシンプルな小規模プロジェクトでは問題ありませんが、プロジェクトが大規模になると、遅延や奇妙な動作を引き起こす可能性があります。

Tuist は、暗黙的な Xcode の動作に対して明示的な API を提供すべきです。また、Xcode の暗黙性を定義することもサポートすべきですが、その実装は開発者が明示的なアプローチを選択するよう促すものであるべきです。Xcode の暗黙性と複雑さをサポートすることは Tuist の採用を促進し、その後チームは暗黙性を取り除くための時間を取ることができます。

依存関係の定義はその良い例です。開発者はビルド設定やフェーズを通じて依存関係を定義できますが、Tuist はその採用を促す優れた API を提供しています。

**API を明示的に設計することで、Tuist は otherwise 不可能だったプロジェクトのチェックや最適化を実行できます。** さらに、依存関係グラフの表現をエクスポートする `tuist graph` や、すべてのターゲットをバイナリとしてキャッシュする `tuist cache` などの機能を有効にします。

> [!TIP]
> Xcode から機能を移植する各リクエストを、シンプルで明示的な API で概念を簡素化する機会として捉えるべきです。


## シンプルさを保つ {#keep-it-simple}

Xcode プロジェクトをスケールさせる際の主な課題の一つは、**Xcode がユーザーに多くの複雑さを露出させている**という事実から来ています。そのため、チームのバス係数が高くなり、プロジェクトやビルドシステムが出力するエラーを理解できる人がチーム内に少数しかいません。チームが少数の人に依存することになるため、これは望ましくない状況です。

Xcode は優れたツールですが、長年にわたる改善、新しいプラットフォーム、プログラミング言語の追加が表面に反映され、シンプルさを維持するのに苦労してきました。

Tuist は物事をシンプルに保つ機会を活用すべきです。なぜなら、シンプルなもので作業するのは楽しく、やる気を高めてくれるからです。コンパイルプロセスの最後で発生するエラーのデバッグに時間を費やしたり、デバイスでアプリを実行できない理由を理解しようとしたりしたい人はいません。Xcode はタスクを基盤となるビルドシステムに委譲しますが、場合によってはエラーを実行可能な項目に変換するのが非常に下手です。*“framework X not found”* というエラーが出て、どうすればよいかわからなかった経験はありませんか？バグの潜在的な根本原因の一覧が表示されたらどうでしょうか。

## 開発者の体験から始める {#start-from-the-developers-experience}

Xcode 周辺でイノベーションが不足している理由、あるいは言い換えれば他のプログラミング環境ほどではない理由の一部は、**既存のソリューションから問題の分析を始めることが多い**ためです。その結果、現在見られる解決策の多くは同じアイデアやワークフローを中心としています。既存のソリューションを考慮に入れることは良いことですが、それらが私たちの創造性を制約しないようにすべきです。

私たちは [Tom Preston](https://tom.preston-werner.com/) が [このポッドキャスト](https://tom.preston-werner.com/) で語っているように考えることを好みます。*「ほとんどのことは達成可能であり、頭にあるものは宇宙の制約内で可能であればコードで実現できる」*。**開発者体験をどのようにしたいかを想像する**ならば、それを実現するのは時間の問題です。開発者体験から問題の分析を始めることで、ユーザーが愛用してくれるようなソリューションへと導く独自の視点が得られます。

皆がやっていることに追随したくなる誘惑に駆られるかもしれませんが、それが皆が不満を続けている不便さを我慢することにつながるとしてもです。そうはしないようにしましょう。アプリのアーカイブをどのように行いたいでしょうか？コード署名はどのようにあるべきでしょうか？Tuist でどのようなプロセスを効率化できるでしょうか？例えば、[Fastlane](https://fastlane.tools/) のサポートを追加することは、まず理解すべき問題に対する解決策です。「なぜ」という問いを繰り返すことで、問題の根本原因にたどり着くことができます。動機の出所を絞り込めば、Tuist がどのように最善の支援ができるかを考えられます。解決策が Fastlane との統合である可能性もありますが、トレードオフを検討する前に検討できる他の同等に有効な解決策を無視しないことが重要です。

## エラーは発生しうる {#errors-can-and-will-happen}

私たち開発者は、エラーが発生しうることを無視してしまう固有的な誘惑に駆られがちです。その結果、理想的なシナリオのみを考慮してソフトウェアの設計とテストを行ってしまいます。

Swift、その型システム、そして適切に構造化されたコードは、いくつかのエラーを防ぐのに役立ちますが、すべてを防げるわけではありません。一部のエラーは私たちの制御外にあるためです。ユーザーが常にインターネット接続を持っていること、またはシステムコマンドが常に成功することを想定できません。Tuist が実行される環境は、私たちが制御するサンドボックスではないため、それらがどのように変化し Tuist に影響を与えるかを理解する努力が必要です。

エラー処理が不十分だとユーザーエクスペリエンスが悪化し、ユーザーはプロジェクトへの信頼を失う可能性があります。私たちは、ユーザーが Tuist のあらゆる側面を楽しめるようにしたいと考えており、エラーの提示方法さえも含まれます。

ユーザーの立場に立ち、エラーから何を伝えられることを期待するかを想像すべきです。プログラミング言語がエラー伝播の通信チャネルであり、ユーザーがエラーの受け手であるなら、エラーメッセージは対象（ユーザー）が話す同じ言語で記述されるべきです。何が起こったかを知るために十分な情報を含み、関連のない情報は隠すべきです。また、回復のために取れる手順をユーザーに示すことで、実行可能なものであるべきです。

最後に、テストケースは失敗するシナリオも考慮すべきです。これにより、私たちが適切にエラーを処理していることを保証するだけでなく、将来の開発者がそのロジックを壊すことを防ぎます。
