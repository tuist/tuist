# 原則 {#principles}

このページでは、Tuist の設計と開発の基盤となる原則について説明します。これらの原則はプロジェクトとともに進化し、プロジェクトの基盤と整合した持続可能な成長を保証することを目的としています。

## 規約をデフォルトとする {#default-to-conventions}

Tuist が存在する理由の一つは、Xcode が規約に弱く、その結果としてスケールアップや保守が困難な複雑なプロジェクトを生み出すためです。そのため、Tuist はシンプルかつ綿密に設計された規約をデフォルトとする異なるアプローチを採用しています。**開発者は規約からオプトアウトできますが、それは自然ではない意識的な選択です。**

例えば、提供される公開インターフェースを使用してターゲット間の依存関係を定義するための規約があります。これにより、Tuist はリンクが正しく動作するように適切な設定でプロジェクトを生成することを保証します。開発者はビルド設定を通じて依存関係を定義することもできますが、それは暗黙的に行われるため、いくつかの規約に従うことに依存する `tuist graph` や `tuist cache` といった Tuist の機能を壊すことになります。

私たちが規約をデフォルトとする理由は、開発者に代わって決定を下せるほど、彼らがアプリの機能構築に集中できるからです。多くのプロジェクトで見られるように規約がない場合、私たちは他の決定と一貫性のない決定を下すことになり、その結果、管理が難しい偶発的な複雑さが生じます。

## マニフェストが唯一の信頼できる情報源 {#manifests-are-the-source-of-truth}

多くの設定レイヤーとその間の契約が存在すると、理解や保守が困難なプロジェクト構成になります。平均的なプロジェクトを少し考えてみてください。プロジェクトの定義は `.xcodeproj` ディレクトリに、CLI はスクリプト（例：`Fastfiles`）に、CI のロジックはパイプラインにあります。これらは維持すべき契約を持つ3つのレイヤーです。*プロジェクトで何かを変更した後、一週間後にリリーススクリプトが壊れていることに気づいた状況はどれくらいありましたか？*

これを簡素化するには、マニフェストファイルを唯一の信頼できる情報源とします。これらのファイルは、開発者がファイルを編集するために使用する Xcode プロジェクトを生成するために Tuist が必要とする情報を提供します。さらに、ローカル環境または CI 環境からプロジェクトをビルドするための標準コマンドを使用できるようになります。

**Tuist は複雑さを引き受け、プロジェクトを可能な限り明示的に記述するためのシンプルで安全、かつ使いやすいインターフェースを提供すべきです。**

## 暗黙的なものを明示化する {#make-the-implicit-explicit}

Xcode は暗黙的な設定をサポートしています。その良い例は、暗黙的に定義された依存関係を推論することです。暗黙性は設定がシンプルな小規模プロジェクトでは問題ありませんが、プロジェクトが大きくなるにつれて、遅延や奇妙な動作を引き起こす可能性があります。

Tuist は、暗黙的な Xcode の動作に対して明示的な API を提供すべきです。また、Xcode の暗黙性を定義することもサポートすべきですが、開発者が明示的なアプローチを選択するよう促すような実装にする必要があります。Xcode の暗黙性と複雑さをサポートすることは Tuist の導入を容易にし、その後チームは暗黙性を取り除くための時間を取ることができます。

依存関係の定義はその良い例です。開発者はビルド設定やフェーズを通じて依存関係を定義できますが、Tuist はその採用を促す美しい API を提供します。

**API を明示的に設計することで、Tuist は otherwise 不可能だったプロジェクトに対するチェックと最適化を実行できます。** さらに、依存関係グラフの表現をエクスポートする `tuist graph` や、すべてのターゲットをバイナリとしてキャッシュする `tuist cache` などの機能を有効にします。

> [!TIP]
> Xcode から機能を移植する各リクエストを、シンプルで明示的な API で概念を簡素化する機会として捉えるべきです。


## シンプルに保つ {#keep-it-simple}

Xcode プロジェクトをスケールさせる際の主な課題の一つは、**Xcode がユーザーに多くの複雑さを露出させている**という事実から来ています。そのため、チームのバス係数が高くなり、プロジェクトとビルドシステムがスローするエラーを理解しているのはチーム内の少数の人だけになります。チームが少数の人に依存しているため、これは望ましくない状況です。

Xcode は優れたツールですが、長年の改善、新しいプラットフォーム、プログラミング言語の追加が表面に反映され、シンプルさを保つのに苦労しています。

Tuist は物事をシンプルに保つ機会を活用すべきです。なぜなら、シンプルなもので作業するのは楽しく、やる気が出るからです。コンパイルプロセスの最後に発生するエラーのデバッグに時間を費やしたり、デバイスでアプリを実行できない理由を理解しようとする人は誰もいません。Xcode はタスクを基盤となるビルドシステムに委譲し、場合によってはエラーを実行可能な項目に変換するのが非常に下手です。*“framework X not found”* というエラーが発生してどうすればよいかわからない経験はありますか？バグの潜在的な根本原因のリストが表示されると想像してみてください。

## 開発者の体験から始める {#start-from-the-developers-experience}

Xcode 周辺でのイノベーション不足、あるいは他のプログラミング環境ほどではない理由の一部は、**既存のソリューションから問題の分析を始めることが多い**ためです。その結果、現在見つかるほとんどのソリューションは同じアイデアとワークフローを中心に展開されています。既存のソリューションを考慮に入れることは良いことですが、それらが私たちの創造性を制約しないようにすべきです。

[Tom Preston](https://tom.preston-werner.com/) が [このポッドキャスト](https://tom.preston-werner.com/) で述べているように考えるのが好きです：*「ほとんどのことは達成可能です。頭の中にあることは、宇宙の制約内で可能であれば、コードで実現できるでしょう」*。**開発者体験をどのようにしたいかを想像するなら**、それを実現するのは時間の問題です。開発者体験から問題の分析を始めることで、ユーザーが喜んで使いたくなるようなソリューションにつながる独自の視点が得られます。

誰もがやっていることに追随したくなる誘惑に駆られることがありますが、それが皆が不満を続けている不便さを甘受することにつながるとしてもです。そうしないようにしましょう。アプリのアーカイブをどのように行いたいか想像してみてください。コード署名はどのようにあるべきでしょうか？Tuist でどのようなプロセスを効率化できるでしょうか？例えば、[Fastlane](https://fastlane.tools/) のサポートを追加することは、まず理解すべき問題に対する一つの解決策です。「なぜ」という問いを繰り返すことで、問題の根本原因にたどり着くことができます。動機の出所を絞り込めば、Tuist がどのように最善の支援ができるかを考えられます。解決策が Fastlane との統合である可能性もありますが、トレードオフを検討する前に、検討対象となる他の同等に有効な解決策を無視しないことが重要です。

## エラーは発生し得る {#errors-can-and-will-happen}

私たち開発者は、エラーが発生し得ることを軽視しがちな傾向があります。その結果、理想的なシナリオのみを考慮してソフトウェアを設計・テストしてしまいます。

Swift、その型システム、そして適切に設計されたコードは、いくつかのエラーを防ぐのに役立ちますが、すべてを防げるわけではありません。制御できない要因もあるからです。ユーザーが常にインターネット接続を持っていること、またはシステムコマンドが常に成功することを前提にはできません。Tuist が実行される環境は私たちが制御するサンドボックスではなく、そのため、それらがどのように変化し Tuist に影響を与えるかを理解する努力が必要です。

エラー処理が不十分だとユーザー体験が悪化し、プロジェクトへの信頼を失う可能性があります。私たちは、ユーザーが Tuist のあらゆる側面、エラーの提示方法さえも楽しめるようにしたいと考えています。

ユーザーの立場に立ち、エラーから何を伝えられるべきか想像すべきです。プログラミング言語がエラーを伝達する通信チャネルであり、ユーザーがエラーの受け手であるなら、エラーメッセージはターゲット（ユーザー）が話す同じ言語で記述されるべきです。何が起こったかを把握するのに十分な情報を含み、関連のない情報は隠すべきです。また、回復のために取れる手順を示すことで、実行可能なものにするべきです。

最後に、私たちのテストケースは失敗するシナリオも考慮すべきです。これにより、想定通りにエラーを処理していることを保証するだけでなく、将来の開発者がそのロジックを壊すのを防ぎます。
