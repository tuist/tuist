# 認証 {#authentication}

サーバーと対話するには、CLIは[ベアラ認証](https://swagger.io/docs/specification/authentication/bearer-authentication/)を使用してリクエストを認証する必要があります。CLIは、ユーザーとして、アカウントとして、またはOIDCトークンを使用して認証することをサポートしています。

## ユーザーとして {#as-a-user}

マシン上でローカルにCLIを使用する場合は、ユーザーとして認証することをお勧めします。ユーザーとして認証するには、次のコマンドを実行する必要があります。

```bash
tuist auth login
```

このコマンドを実行すると、Webベースの認証フローが開始されます。認証が完了すると、CLIは長寿命のリフレッシュトークンと短寿命のアクセストークンを`~/.config/tuist/credentials`に保存します。ディレクトリ内の各ファイルは、認証対象のドメインを表しており、デフォルトでは`tuist.dev.json`になります。このディレクトリに保存される情報は機密性が高いため、**安全に保管してください**。

CLIは、サーバーへのリクエストを行う際に自動的に資格情報を参照します。アクセストークンの有効期限が切れている場合、CLIはリフレッシュトークンを使用して新しいアクセストークンを取得します。

> [!NOTE]
> 組織でシングルサインオンを使用している場合は、ブラウザでエンタープライズログインオプションを選択し、職場のメールアドレスを入力してください。Tuistは、既存の組織メンバーシップまたは<.localized_link href="/guides/integrations/authentication/sso#verify-a-login-email-domain">検証済みのログインメールドメイン</.localized_link>からプロバイダーを検出できます。

## OIDCトークン {#oidc-tokens}

OpenID Connect (OIDC) をサポートするCI環境では、Tuistは長寿命のシークレットを管理する必要なく自動的に認証できます。サポートされているCI環境で実行する場合、CLIはOIDCトークンプロバイダーを自動的に検出し、CIによって提供されたトークンをTuistアクセストークンと交換します。

### サポートされているプロバイダー {#supported-ci-providers}

Tuistは以下のCIプロバイダーを認識し、リポジトリ接続を通じてそれらのトークンをプロジェクトにマッピングします。

- GitHub Actions
- CircleCI
- Bitrise

OpenID Connectトークンを発行する他のすべてのアイデンティティプロバイダーは、アカウント内の現在および将来のすべてのプロジェクトに対して一度設定する[ワークロードアイデンティティ信頼ポリシー](#workload-identity-trust-policies)を通じて認証できます。例えば[Fly.io Machines](#flyio-machines)などです。

### OIDC認証の設定 {#setting-up-oidc-authentication}

GitHub Actions、CircleCI、およびBitriseの場合：

1. **リポジトリをTuistに接続する**：<.localized_link href="/guides/integrations/gitforge/github">GitHub統合ガイド</.localized_link>に従って、GitHubリポジトリをTuistプロジェクトに接続します。

2. **`tuist auth login`を実行する**：CIワークフローで、認証が必要なコマンドの前に`tuist auth login`を実行します。CLIはCI環境を自動的に検出し、OIDCを使用して認証します。

プロバイダー固有の設定例については、<.localized_link href="/guides/integrations/continuous-integration">継続的インテグレーションガイド</.localized_link>を参照してください。

### ワークロードアイデンティティ信頼ポリシー {#workload-identity-trust-policies}

信頼ポリシーにより、デプロイメントプラットフォーム、Kubernetesクラスター、またはセルフマネージドCIシステムなどの別のアイデンティティプロバイダーからのワークロードが、長寿命のTuistシークレットなしでプロジェクトにアクセスできるようになります。プロバイダーは以下の条件を満たす必要があります。

- パブリックアドレスでHTTPS経由で到達可能であること。Tuistはリダイレクトを追跡せず、プライベートまたは内部ネットワークアドレス（セルフホストされたTuistサーバーからのものを含む）には接続しません。
- 非対称鍵で署名されたJWTを発行すること。例えば`RS256`または`ES256`などです。署名されていないトークンや共有シークレットで署名されたトークン（`HS256`など）は拒否されます。
- 署名鍵を固定されたHTTPS URLでJSON Web Key Set (JWKS) として公開すること。レスポンスは最大64 KiBであり、最大20個の鍵を含んでいる必要があります。
- すべてのトークンに有効期限 (`exp`) を含めること。

GitHub Actions、CircleCI、およびBitriseの発行者は、上記のリポジトリベースのフロー用に予約されており、信頼ポリシーでは使用できません。

> [!NOTE]
> セルフホスト展開の場合、ワークロードアイデンティティを設定したりジョブを移行したりする前に、データベースマイグレーションを適用し、稼働中のすべてのTuistサーバーレプリカをアップグレードしてください。その後、CLIまたはElixir統合を`TUIST_OIDC_TOKEN`および`TUIST_OIDC_ACCOUNT`をサポートするバージョンにアップグレードします。既存のGitHub Actions、CircleCI、およびBitriseジョブはリポジトリベースの認証を引き続き使用し、アカウントハンドルは必要ありません。本番ジョブを切り替える前に、意図したワークロードでの短寿命トークンの交換とキャッシュ操作を確認してください。新しい交換を停止するには、ポリシーを削除してください。すでに発行されたTuistアクセストークンが失効するまで最大1時間かかります。ポリシーを削除しても、これらのトークンは直ちに取り消されません。

#### ポリシーの作成 {#create-a-trust-policy}

Tuistダッシュボードで、アカウントの**設定** > **認証**を開き、**ワークロードアイデンティティ**セクションを見つけます。アカウント管理者（または個人アカウントの所有者）である必要があります。各アカウントには最大20のポリシーを設定できます。アカウント全体のCIアクセスのためにアイデンティティを一度設定します。プロジェクトの選択は不要です。

**ワークロードアイデンティティ**横のスイッチを使用してポリシーフォームを開きます。アカウントに保存されたアイデンティティがある場合、スイッチはオンから始まり、保存後もオンのままになります。アイデンティティがないアカウントの場合、スイッチはオフから始まります。組織の場合、このセクションは**SCIMプロビジョニング**の下に表示されます。フォームを非表示にしても下書きは保持され、ワークロード認証は無効になりません。保存されたアイデンティティカードとセットアップドキュメントリンクは表示されたままになります。各カードには、アイデンティティの名前、発行者およびJWKS URL、オーディエンス、正確なJSONクレーム、アカウント全体のスコープ、および作成時間が表示されます。カード上のアクションを使用してアイデンティティを削除します。

以下のフィールドを入力するには**カスタムプロバイダー**を選択するか、組織のスラッグおよび数値の組織IDとアプリケーションIDから生成するには**Fly.io Machines**を選択します。Flyテンプレートでは、生成された発行者、JWKS URL、およびクレームを**詳細設定**の下で編集可能です。テンプレートまたはヘルパー値を変更しても、手動で編集したフィールドは保持されます。発行者、JWKS URL、またはクレームがテンプレートを上書きする場合、Tuistは**詳細設定**を展開し、警告を表示して、保存されるポリシーを確認できるようにします。Flyヘルパーなしで続行するには、**カスタムプロバイダー**に戻ります。テンプレートは設定を入力するだけであり、Tuistがトークンを検証する方法は変更しません。

| フィールド | 説明 |
| --- | --- |
| 名前 | ポリシーを識別するためのラベル。アカウント内で一意である必要があります。 |
| 発行者URL | トークンの`iss`クレーム。末尾のスラッシュを含め、完全に一致する必要があります。 |
| JWKS URL | プロバイダーの署名キーのHTTPS URL。TuistはこのURLを直接使用し、プロバイダーのOpenID Connectディスカバリードキュメントを読み取らないため、`jwks_uri`をプロバイダーのドキュメントまたは`<issuer>/.well-known/openid-configuration`からコピーしてください。 |
| オーディエンス | トークンが発行されるべきオーディエンス。デフォルトは`tuist`です。トークンの`aud`はこれと等しいか、`aud`がリストの場合はこれを含んでいる必要があります。他のサービス向けに発行されたトークンがここで再利用されないよう、Tuistのみが受け入れる値を使用してください。 |
| クレーム | トークンに含まれる必要がある1〜10個のクレームを持つJSONオブジェクト（例：`{"sub": "system:serviceaccount:ci:builder"}`）。JSON入力は8 KiBまでに制限されます。値は文字列、符号付き64ビット整数、またはブール値である必要があり、型を含めて完全に一致する必要があります。`"123"`は`123`と一致しません。ネストされたオブジェクト、リスト、および`iss`、`aud`、`exp`、`nbf`、`iat`、`jti`などの時間またはトークン関連のクレームは許可されません。 |

各ポリシーは、個別のプロジェクトを選択することなく、**アカウントが所有する現在および将来のすべてのプロジェクト**へのCIアクセスを付与します。最初のプロジェクトを作成する前にアイデンティティを設定できます。これにより、アカウント管理や他のアカウントへのアクセスが付与されるわけではありません。

一致するクレームを持つトークンを取得できるすべてのワークロードは、それらのプロジェクトすべてにアクセスできるため、プロバイダーが保証し、誰も再利用できないクレームを選択してください。削除後に名前変更や再登録が可能な名前よりも、安定した数値IDを優先してください。

> [!WARNING]
> 共有アイデンティティプロバイダーでは、ポリシーを組織またはテナント**および**対象のアプリケーション、プロジェクト、またはサービスアカウントにバインドしてください。`main`などのブランチ名、`production`などの環境、または一般的なロールだけではアイデンティティの境界にはなりません。別のテナントが同じ値を持つトークンを取得する可能性があります。例えば、GitLab.comのポリシーには、`ref`だけでなく、対象プロジェクトの安定した`project_id`を含める必要があります。一致するトークンはキャッシュ書き込みを含むアカウント全体のCIアクセスを付与するため、無関係なワークロードを信頼するポリシーはキャッシュポイズニングを許容する可能性があります。

Tuistは、発行者、オーディエンス、有効期限、not-before時間（最大60秒の時計ずれまで）、およびすべてのクレームを確認した後、トークンに署名したキーを独自のJWKS URLが保持しているポリシーに対してのみアクセスを付与します。発行された1時間有効のCIトークンはアカウント全体を対象とし、プロジェクトIDのスナップショットではありません。発行後に作成されたりアカウントに転送されたプロジェクトも含まれます。プロジェクトの承認には依然として現在のアカウント所有権が必要であるため、プロジェクトを外部に転送すると、そのアカウントのトークン下でのアクセスは削除されます。

#### ワークロードを認証する {#authenticate-a-workload}

1. ポリシーのオーディエンスを使用して、プロバイダーからアイデンティティトークンをリクエストします。
2. `TUIST_OIDC_TOKEN`をそのトークンに設定し、`TUIST_OIDC_ACCOUNT`をプロジェクトを所有するTuistアカウントのハンドルに設定します。アカウントはすべての信頼ポリシー交換に必要です。これは検索場所を選択するだけであり、それ自体では何も付与しません。
3. `tuist auth login`を実行します。Elixirプロジェクトの場合、代わりに`mix tuist.login`を使用するか、`TUIST_TOKEN`または有効な保存済み資格情報がない場合にElixir統合が自動的にトークンを交換するようにします。

結果として得られるTuistアクセストークンは`ci`スコープグループのみを持ち、選択されたアカウントが所有する現在および将来のすべてのプロジェクトをカバーします。アカウント内の20を超えるポリシーが同じトークンに一致する場合、または2つを超える異なるJWKS URLを使用する場合、交換は失敗します。

Tuistはこれらのセッションを更新しません。アクセストークンは1時間後に失効し、リフレッシュトークンはありません。プロバイダーのアイデンティティトークンは通常数分間しか有効ではないため、古い`TUIST_OIDC_TOKEN`を保持することは更新戦略にはなりません。1時間以上実行されるジョブの場合、Tuistセッションが失効する前に新しいアイデンティティトークンをリクエストし、再度ログインしてください。ポリシーを削除すると新しい交換は停止しますが、すでに発行されたアクセストークンは失効するまで有効です。

Tuistは、専用のサイズ制限付きキャッシュで正常にフェッチした後、最大15分間プロバイダーの署名キーをキャッシュします。エントリは早期に削除され、再度フェッチされる場合があります。失敗したフェッチはキャッシュされません。プロバイダーがキーを回転させる場合、キャッシュされたセットにないキーで署名されたトークンはキャッシュが失効するまで拒否されるため、そのキーでトークンに署名する少なくとも15分钟前にJWKSで新しいキーを公開する必要があります。キーID（`kid`）のないトークンは、JWKSに単一の適格な署名キーが含まれている場合のみ受け入れられます。JWKSにキーIDが存在する場合、それは最大256バイトの文字列である必要があります。

> [!NOTE]
> `TUIST_OIDC_TOKEN`は汎用トークン入力であり、サーバー信頼を回避する方法ではありません。これはCIプロバイダー検出より優先され、サーバーは組み込みプロバイダーと一致する信頼ポリシーを持つアイデンティティのみを受け入れます。Tuist資格情報を想定する`TUIST_TOKEN`にアイデンティティトークンを入れないでください。

交換が失敗した場合、ポリシー内の発行者、オーディエンス、およびすべてのクレームがトークンと完全に一致すること、JWKS URLがトークンに署名したキーを提供していること、ポリシーが削除されていないこと、および`TUIST_OIDC_ACCOUNT`がプロジェクトを所有するアカウントを指していることを確認してください。どのアイデンティティが信頼されているかを公開しないよう、Tuistはこれらのすべてのケースで同じエラーを返します。

### Fly.io Machines {#flyio-machines}

[Fly.ioはOIDCワークロードアイデンティティをサポートしています](https://docs.fly.io/reference/openid-connect/)。Machineは、Fly APIトークンや長寿命のTuistシークレットなしで、ローカルの`/.fly/api` Unixソケットから短命の署名付きアイデンティティトークンをリクエストできます。Flyトークンはソースリポジトリではなく組織とアプリケーションを識別するため、GitHubリポジトリを接続する代わりに信頼ポリシーを使用してください。

1. Fly Machine内部で発行されたアイデンティティトークンから、発行者（`iss`）、組織ID（`org_id`）、およびアプリケーションID（`app_id`）を取得します。発行者は`https://oidc.fly.io/<organization-slug>`です。組織名やアプリ名ではなく、数値IDを使用してください。
2. **Fly.io Machines**テンプレートを使用して[信頼ポリシーを作成](#create-a-trust-policy)し、組織スラッグと両方の数値IDを入力します。これにより以下の値が入力され、IDは文字列として保持されます。**カスタムプロバイダー**を使用して手動で入力することもできます。クレーム内のID周围的の引用符は保持してください。

   | フィールド | 値 |
   | --- | --- |
   | 発行者URL | `https://oidc.fly.io/<organization-slug>` |
   | JWKS URL | `https://oidc.fly.io/<organization-slug>/.well-known/jwks` |
   | オーディエンス | `tuist` |
   | クレーム | `{"org_id": "<organization-id>", "app_id": "<application-id>"}` |

3. Machine内部で、`TUIST_OIDC_ACCOUNT`をプロジェクトを所有するTuistアカウントハンドル（Fly組織スラッグではない）に設定し、オーディエンス`tuist`でトークンをリクエストし、`TUIST_OIDC_TOKEN`を使用して`tuist auth login`に渡します。

```bash
set -euo pipefail
export TUIST_OIDC_ACCOUNT="my-tuist-account"

TUIST_OIDC_TOKEN="$(curl --fail --silent --show-error \
  --unix-socket /.fly/api \
  -X POST http://localhost/v1/tokens/oidc \
  -H 'Content-Type: application/json' \
  --data '{"aud":"tuist"}')"
export TUIST_OIDC_TOKEN

tuist auth login
unset TUIST_OIDC_TOKEN
```

初期設定では、トークンをエクスポートした後、アンセットする前に、ローカルでアイデンティティフィールドのみを検査できます。これにより構成用のクレームをデコードします。Tuistは認証中に署名を別途検証します。

```bash
python3 - <<'PY'
import base64, json, os
payload = os.environ["TUIST_OIDC_TOKEN"].split(".")[1]
claims = json.loads(base64.urlsafe_b64decode(payload + "=" * (-len(payload) % 4)))
print(json.dumps({key: claims[key] for key in ("iss", "org_id", "app_id")}, indent=2))
PY
```

トークン自体を出力したりコミットしたりしないでください。承認されたFlyアプリ内のすべてのMachineは、Tuistアカウント内の現在および将来のすべてのプロジェクトに対して認証できます。追加のアプリごとに個別のポリシーを作成してください。Flyアイデンティティトークンは約10分後に失効するため、長時間実行されるMachineでは、1時間のTuistセッションが失効する前に新しいトークンをリクエストし、`tuist auth login`を再度実行してください。

### OIDCトークンスコープ {#oidc-token-scopes}

OIDCトークンには`ci`スコープグループが付与されます。GitHub Actions、CircleCI、Bitriseの場合、これはリポジトリに接続されているすべてのプロジェクトへのアクセスを提供します。ワークロードアイデンティティ信頼ポリシーの場合、これは選択されたアカウントが所有する現在および将来のすべてのプロジェクトへのアクセスを提供しますが、プロジェクト作成、プロジェクト管理、ランナー管理、またはアカウントメンバー管理は付与しません。`ci`スコープに含まれるものの詳細については、[スコープグループ](#scope-groups)を参照してください。

> [!TIP]
> **セキュリティ上の利点**
>
> OIDC認証は長寿命トークンよりも安全です。その理由は次のとおりです。
> - 回転や管理が必要なシークレットがない
> - トークンは短命である
> - 認証はリポジトリアイデンティティまたは明示的に承認されたワークロードアイデンティティに紐付けられている


## Gradleプラグイン認証 {#gradle-plugin-authentication}

GradleプラグインはTuist CLIの認証状態を使用し、個別のログインフローを定義しません。CLIで一度認証すると、プラグインはその資格情報を再利用します。

`project`や`url`を含むプロジェクトおよびサーバー構成には、標準的な<.localized_link href="/references/tuist-toml">tuist.tomlリファレンス</.localized_link>を使用してください。

ローカルで使用するには、次を実行します。

```bash
tuist auth login
```

CIの場合、次のいずれかを使用します。

- <.localized_link href="/guides/server/authentication#setting-up-oidc-authentication">OIDC認証</.localized_link>（利用可能な場合は推奨）
- <.localized_link href="/guides/server/authentication#continuous-integration">アカウントトークン認証</.localized_link>（`TUIST_TOKEN`経由）

セルフホスト型Tuistサーバーの場合、`tuist.toml`でサーバーURLを定義し（例：`url = "https://tuist.your-company.com"`）、標準のログインフローを実行します。URLはプラグインで使用される同じ構成ファイルから解決されます。

認証が構成された後、Gradleキャッシュコマンドとタスクを通常どおり実行します。

## アカウントトークン {#account-tokens}

OIDCをサポートしないCI環境の場合、または権限を細かく制御する必要がある場合は、アカウントトークンを使用できます。アカウントトークンを使用すると、トークンがアクセスできるスコープとプロジェクトを正確に指定できます。

### アカウントトークンの作成 {#creating-an-account-token}

アカウントトークンを作成する最も簡単な方法は、ダッシュボードからです。

1. Tuistダッシュボードで組織を開きます。
2. **設定** > **トークン**に移動します。
3. **トークンを生成**を選択します。
4. 名前、オプションの有効期限、プロジェクトアクセス、およびトークンに必要なスコープを選択します。
5. ダイアログを閉じる前に、生成されたトークン値をコピーしてください。トークン値は1回だけ表示されます。

CLIからアカウントトークンを作成することもでき、スクリプトや自動化に役立ちます。

```bash
tuist account tokens create account-handle \
  --scopes account:cache:write project:cache:read project:cache:write \
  --name ci-cache-token \
  --expires 1y
```

> [!IMPORTANT]
> `account-handle`を、トークンにアクセスさせたいプロジェクトを所有するアカウントのハンドルに置き換えてください。これは個人アカウントではなく、組織アカウントでも構いません。

コマンドは次のオプションを受け入れます。

| オプション | 説明 |
| --- | --- |
| `--scopes` | 必須。トークンに付与するスコープのカンマ区切りリスト。 |
| `--name` | 必須。トークンの一意の識別子（1〜32文字、英数字、ハイフン、アンダースコアのみ）。 |
| `--expires` | オプション。トークンの有効期限。`30d`（日）、`6m`（月）、または`1y`（年）などの形式を使用します。指定しない場合、トークンは失効しません。 |
| `--projects` | トークンを特定のプロジェクトハンドルに制限します。指定しない場合、トークンはすべてのプロジェクトにアクセスできます。 |

### 利用可能なスコープ {#available-scopes}

| スコープ | 説明 |
| --- | --- |
| `account:cache:read` | アカウントスコープのキャッシュ済みバイナリをダウンロード |
| `account:cache:write` | アカウントスコープのキャッシュ済みバイナリをアップロード |
| `account:members:read` | アカウントメンバーを読み取る |
| `account:members:write` | アカウントメンバーを管理する |
| `account:registry:read` | Swiftパッケージレジストリから読み取る |
| `account:registry:write` | Swiftパッケージレジストリに公開する |
| `account:runners:read` | ランナーのジョブ、ワークフロー、プロファイル、およびボリュームを読み取る |
| `account:runners:write` | ランナーのプロファイルを管理し、ランナーのボリュームをクリアする |
| `project:previews:read` | プレビューをダウンロード |
| `project:previews:write` | プレビューをアップロード |
| `project:admin:read` | プロジェクトとその設定を読み取る |
| `project:admin:write` | プロジェクトを作成、更新、削除します。プロジェクトを作成するには、すべてのプロジェクトにアクセスできるトークンが必要です |
| `project:cache:read` | キャッシュ済みバイナリをダウンロード |
| `project:cache:write` | キャッシュ済みバイナリをアップロード |
| `project:bundles:read` | バンドルを表示 |
| `project:bundles:write` | バンドルをアップロード |
| `project:tests:read` | テスト結果を読み取る |
| `project:tests:write` | テスト結果をアップロード |
| `project:builds:read` | ビルド分析を読み取る |
| `project:builds:write` | ビルド分析をアップロード |
| `project:runs:read` | コマンド実行を読み取る |
| `project:runs:write` | コマンド実行を作成および更新 |

### スコープグループ {#scope-groups}

スコープグループは、単一の識別子で複数の関連スコープを付与する便利な方法を提供します。スコープグループを使用すると、含まれる個々のスコープすべてが自動的に展開されます。

| スコープグループ | 含まれるスコープ |
| --- | --- |
| `ci` | `account:cache:write`, `project:cache:write`, `project:previews:write`, `project:bundles:write`, `project:tests:write`, `project:builds:write`, `project:runs:write` |
| `mcp` | `project:cache:read`, `project:previews:read`, `project:bundles:read`, `project:tests:read`, `project:builds:read`, `project:runs:read` |

### 継続的インテグレーション {#continuous-integration}

OIDCをサポートしないCI環境の場合、`ci`スコープグループを使用してアカウントトークンを作成し、CIワークフローを認証します。ダッシュボードでは、トークンを生成する際に**CI**プリセットを選択します。

CLIから同じトークンを作成することもできます。

```bash
tuist account tokens create account-handle --scopes ci --name ci
```

これにより、一般的なCI操作（キャッシュ、プレビュー、バンドル、テスト、ビルド、および実行）に必要なすべてのスコープを持つトークンが作成されます。生成されたトークンをCI環境のシークレットとして保存し、`TUIST_TOKEN`環境変数として設定します。

### アカウントトークンの管理 {#managing-account-tokens}

アカウントダッシュボードで**設定** > **トークン**を開き、アカウントトークンを表示し、トークンのスコープとプロジェクトアクセスを確認し、ローテーション中にトークンを取り消します。

アカウントのすべてのトークンを一覧表示するには:

```bash
tuist account tokens list account-handle
```

名前でトークンを取り消すには:

```bash
tuist account tokens revoke account-handle ci-cache-token
```

### アカウントトークンの使用 {#using-account-tokens}

アカウントトークンは環境変数`TUIST_TOKEN`として定義されることが想定されています。

```bash
export TUIST_TOKEN=your-account-token
```

> [!TIP]
> **アカウントトークンを使用するタイミング**
>
> 次の場合にアカウントトークンを使用してください。
> - OIDCをサポートしないCI環境での認証
> - トークンが実行できる操作に関する細かな制御
> - アカウント内の複数のプロジェクトにアクセスできるトークン
> - 自動的に期限切れになる時間制限付きトークン
