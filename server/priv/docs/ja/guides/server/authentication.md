# 認証 {#authentication}

サーバーとやり取りするには、CLI は [ベアラー認証](https://swagger.io/docs/specification/authentication/bearer-authentication/) を使用してリクエストを認証する必要があります。CLI は、ユーザーとして、アカウントとして、または OIDC トークンを使用して認証することをサポートしています。

## ユーザーとして {#as-a-user}

マシン上でローカルに CLI を使用する場合は、ユーザーとして認証することをお勧めします。ユーザーとして認証するには、次のコマンドを実行する必要があります。

```bash
tuist auth login
```

このコマンドを実行すると、Web ベースの認証フローが進みます。認証が完了すると、CLI は長期有効なリフレッシュトークンと短期有効なアクセストークンを `~/.config/tuist/credentials` に保存します。ディレクトリ内の各ファイルは、認証対象のドメインを表しており、デフォルトでは `tuist.dev.json` になります。そのディレクトリに保存される情報は機密性が高いので、**安全に保管してください**。

CLI は、サーバーへのリクエスト時に自動的に資格情報を参照します。アクセストークンの有効期限が切れている場合、CLI はリフレッシュトークンを使用して新しいアクセストークンを取得します。

> [!NOTE]
> 組織でシングルサインオンを使用している場合は、ブラウザでエンタープライズログインオプションを選択し、勤務先のメールアドレスを入力してください。Tuist は、既存の組織メンバーシップまたは <.localized_link href="/guides/integrations/authentication/sso#verify-a-login-email-domain">検証済みのログイン用メールドメイン</.localized_link> からプロバイダーを検出できます。

## OIDC トークン {#oidc-tokens}

OpenID Connect (OIDC) をサポートする CI 環境の場合、Tuist は長期有効なシークレットの管理を必要とせずに自動的に認証できます。サポートされている CI 環境で実行すると、CLI は OIDC トークンプロバイダーを自動的に検出し、CI が提供するトークンを Tuist のアクセストークンと交換します。

### サポートされているプロバイダー {#supported-ci-providers}

Tuist は以下の CI プロバイダーを認識し、リポジトリ接続を通じてそれらのトークンをプロジェクトにマッピングします。

- GitHub Actions
- CircleCI
- Bitrise

[Amp](#amp-orbs) Orb は、Tuist アカウントに接続した Amp ワークスペースを通じて認証され、[Claude Code セッション](#claude-code-sessions) は、Tuist Sandboxes で実行するために接続した Claude Code 環境を通じて認証されます。

OpenID Connect トークンを発行する他のあらゆるアイデンティティプロバイダーは、アカウント内の現在および将来のすべてのプロジェクトに対して一度だけ構成する [ワークロードアイデンティティ信頼ポリシー](#workload-identity-trust-policies) を介して認証できます。例えば [Fly.io Machines](#flyio-machines) などです。

### OIDC 認証の設定 {#setting-up-oidc-authentication}

GitHub Actions、CircleCI、Bitrise の場合：

1. **リポジトリを Tuist に接続**：<.localized_link href="/guides/integrations/gitforge/github">GitHub 統合ガイド</.localized_link> に従って、GitHub リポジトリを Tuist プロジェクトに接続します。

2. **アイデンティティトークンを付与**：GitHub Actions では、ジョブに `permissions: id-token: write` を付与します。CircleCI および Bitrise では、プロジェクトで OIDC を有効にします。Tuist 4.218.0 以降では、CLI がサインインしておらず、`TUIST_TOKEN` も設定されていない場合、CI 環境を検出して初回リクエスト時にアイデンティティトークンを交換するため、ログイン手順は不要です。それ以前のバージョンではまず `tuist auth login` が必要であり、明示的にサインインして、交換が拒否された場合に早期に失敗させるために引き続き実行できます。

プロバイダー固有の設定例については、<.localized_link href="/guides/integrations/continuous-integration">継続的インテグレーションガイド</.localized_link> を参照してください。

### Amp Orb {#amp-orbs}

[Amp](https://ampcode.com) Orb は、Amp ワークスペースを識別する OIDC トークンを発行できます。ワークスペースを Tuist アカウントに一度接続すると、そのワークスペースの任意の Orb 内の Tuist CLI および `tuist_ex` Mix タスクは、保存されたトークンやログイン手順なしで自動的にサインインします。

1. ID の確認：Orb で実行されているワークスペースのスレッドで、`echo $AMP_WORKSPACE_ID $AMP_PROJECT_ID` を実行します。
2. Tuist アカウントで **Settings → Integrations** を開き、Amp カードの **Connect workspace** を選択して、ワークスペース ID を貼り付けます。1 つの Amp プロジェクトの Orb のみを許可するには、そのプロジェクト ID も貼り付けてください。アカウント管理者または所有者である必要があります。
3. ワークスペースの Orb で Tuist を使用します。サインインしていない場合、CLI または Mix タスクは Orb を検出し、`amp orb id-token --audience https://tuist.dev` でトークンを発行して、それを Tuist セッションと交換します。`tuist auth login` および `mix tuist.login` も同じ交換を明示的に行います。

[Amp の OIDC ガイド](https://ampcode.com/manual/orbs/oidc) の信頼構成と同様に、Tuist はすべてのトークンで Amp の署名を検証し、オーディエンスが `https://tuist.dev` であり、`token_use` が `exchanged` であり、`workspace_id` が接続されたワークスペースと一致し、プロジェクトに限定された接続の場合は `project_id` がそのプロジェクトと一致する場合のみ受け入れます。`sub` は、これらのクレームと同じワークスペース（プロジェクト接続の場合は同じプロジェクト）を指す必要があります：`workspace:<workspace-id>:project:<project-id>:…`。これは `amp orb id-token` がデフォルトで発行します。

接続によって許可されたすべての Orb は、キャッシュのアップロードを含め、アカウントが所有する現在および将来のすべてのプロジェクトに対する CI アクセス権限を取得します。また、`account:sandboxes:write` スコープも取得するため、<.localized_link href="/guides/features/sandboxes">サンドボックス</.localized_link> を作成し、アカウントのメンバーのようにその中でコマンドを実行できます。例えば、Linux Orb から macOS サンドボックスでビルドするなどです。そのアクセス権限を信頼できるメンバーを持つワークスペースのみを接続してください。ID を慎重に確認してください。Tuist は、あなたが接続するワークスペースに所属していることを確認できません。ワークスペースが複数の Tuist アカウントに接続されている場合、Orb はサインイン先のアカウントを指定するために `TUIST_OIDC_ACCOUNT` を設定する必要があります。Amp プロジェクトの環境でこれを設定すると、サインインがあなたのアカウントに固定されます。ワークスペース外のスレッドにはワークスペースアイデンティティがなく、接続を使用できません。Amp カードからワークスペースを切断して新しいサインインを停止してください。すでに発行されたセッションは、1 時間後に有効期限が切れるまで有効です。セッションにはリフレッシュトークンは不要です。有効期限が近づくと、Orb 内の CLI が新しい Amp トークンを発行して再度交換するため、ワークスペースが接続されている間、長時間実行される Orb はサインイン状態を維持します。

ワークスペースを接続する前に作成した Amp 発行者用の信頼ポリシーは、`TUIST_OIDC_ACCOUNT` を設定した場合でも機能し続けます。

### Claude Code セッション {#claude-code-sessions}

セルフホスト環境内の各 Claude Code クラウドセッションには、Anthropic が署名したアイデンティティトークン（`CLAUDE_CODE_SESSION_ACCESS_TOKEN`）が含まれています。<.localized_link href="/guides/features/sandboxes/claude#claude-code">Tuist Sandboxes で実行するために接続</.localized_link>した環境では、Tuist はこれを `TUIST_OIDC_TOKEN` としてセッションに渡すため、Tuist CLI および `tuist_ex` Mix タスクは自動的にサインインします。

Tuist は Anthropic の署名を検証し、トークンがセッショントークン（`ccr:role` が `session_worker`）であり、そのオーディエンスで指定された環境が Tuist アカウントに接続されて有効になっている場合にのみ、そのトークンを受け入れます。接続された環境のすべてのセッションは、キャッシュのアップロードを含め、アカウントが所有する現在および将来のすべてのプロジェクトに対する CI アクセス権限を取得するため、Claude 組織が環境の使用を許可した anyone はあなたのキャッシュにパブリッシュできます。セッションの Tuist セッションは、1 時間後またはアイデンティティトークンの有効期限切れのいずれか早い方で失効します。トークンはセッション開始時に使用されたもので、デフォルトでは 4 時間有効です。そのため、より長いセッションでは、次のメッセージが新しいランナーで再開されるまで Tuist アクセスを失います。新しいサインインを停止するには、環境を切断または無効にしてください。

### ワークロードアイデンティティ信頼ポリシー {#workload-identity-trust-policies}

信頼ポリシーを使用すると、デプロイメントプラットフォーム、Kubernetes クラスター、または自己管理型 CI システムなど、別のアイデンティティプロバイダーからのワークロードが、長寿命の Tuist シークレットなしでプロジェクトにアクセスできます。プロバイダーは以下の条件を満たす必要があります。

- パブリックアドレスで HTTPS 経由で到達可能であること。Tuist はリダイレクトを追跡せず、プライベートまたは内部ネットワークアドレスには接続しません。これはセルフホスト型 Tuist サーバーからの接続にも適用されます。
- 非対称鍵（例えば `RS256` や `ES256`）で署名された JWT を発行すること。署名されていないトークンや共有シークレット（`HS256` など）で署名されたトークンは拒否されます。
- 署名鍵を JSON Web Key Set (JWKS) として固定された HTTPS URL で公開すること。レスポンスは最大 64 KiB で、鍵は最大 20 個含まれている必要があります。
- すべてのトークンに有効期限（`exp`）を含めること。

GitHub Actions、CircleCI、および Bitrise の発行者は、前述のリポジトリベースのフロー用に予約されており、信頼ポリシーでは使用できません。

> [!NOTE]
> セルフホスト展開の場合、ワークロードアイデンティティを設定したりジョブを移行したりする前に、データベースマイグレーションを適用し、稼働中のすべての Tuist サーバーレプリカをアップグレードしてください。その後、CLI または Elixir 統合を `TUIST_OIDC_TOKEN` および `TUIST_OIDC_ACCOUNT` をサポートするバージョンにアップグレードしてください。既存の GitHub Actions、CircleCI、および Bitrise ジョブはリポジトリベースの認証を引き続き使用し、アカウントハンドルを必要としません。本番ジョブを切り替える前に、意図したワークロードで短期間のトークン交換とキャッシュ操作を確認してください。新しい交換を停止するには、ポリシーを削除してください。すでに発行された Tuist アクセストークンが失効するまで最大 1 時間かかります。ポリシーを削除しても、これらのトークンは直ちに取り消されません。

#### ポリシーを作成する {#create-a-trust-policy}

Tuist ダッシュボードで、アカウントの **設定** > **認証** を開き、**ワークロードアイデンティティ** セクションを見つけます。あなたはアカウント管理者（または個人アカウントの所有者）である必要があります。各アカウントには最大 20 のポリシーを設定できます。アカウント全体の CI アクセスのためにアイデンティティを一度設定します。プロジェクトの選択は不要です。

**ワークロードアイデンティティ** の横にあるスイッチを使用して、ポリシーフォームを開きます。アカウントに保存されたアイデンティティがある場合、スイッチはオンから始まり、保存後もオンのままになります。アイデンティティがないアカウントの場合、スイッチはオフから始まります。組織の場合、このセクションは **SCIM プロビジョニング** の下に表示されます。フォームを非表示にしても下書きは保存され、ワークロード認証は無効になりません。保存されたアイデンティティカードとセットアップドキュメントへのリンクは表示されたままになります。各カードには、アイデンティティの名前、発行者および JWKS URL、オーディエンス、正確な JSON クレーム、アカウント全体のスコープ、作成時刻が表示されます。カード上のアクションを使用してアイデンティティを削除します。

以下のフィールドを入力するには **カスタムプロバイダー** を選択するか、組織のスラッグおよび数値の組織 ID とアプリケーション ID から生成するには **Fly.io Machines** を選択します。Fly テンプレートは、生成された発行者、JWKS URL、およびクレームを **詳細設定** で編集可能な状態に保ちます。テンプレートまたはヘルパー値を変更しても、手動で編集したフィールドは保持されます。発行者、JWKS URL、またはクレームがテンプレートを上書きする場合、Tuist は **詳細設定** を展開し、警告を表示して、保存されるポリシーを確認できるようにします。**カスタムプロバイダー** に戻って、Fly ヘルパーなしで続行できます。テンプレートは構成を入力するだけであり、Tuist がトークンを検証する方法は変更しません。

| フィールド | 説明 |
| --- | --- |
| 名前 | ポリシーを識別するためのラベル。アカウント内で一意である必要があります。 |
| 発行者 URL | トークンの `iss` クレーム。末尾のスラッシュを含め、完全に一致する必要があります。 |
| JWKS URL | プロバイダーの署名鍵の HTTPS URL。Tuist はこの URL を直接使用し、プロバイダーの OpenID Connect ディスカバリードキュメントを読み取らないため、プロバイダーのドキュメントまたは `<issuer>/.well-known/openid-configuration` から `jwks_uri` をコピーしてください。 |
| オーディエンス | トークンが発行されるべきオーディエンス。デフォルトは `tuist` です。トークンの `aud` はこれと等しいか、`aud` がリストの場合はこれを含んでいる必要があります。他のサービス向けに発行されたトークンがここで再利用されないよう、Tuist だけが受け入れる値を使用してください。 |
| クレーム | トークンに含まれる必要がある 1〜10 個のクレームを持つ JSON オブジェクト。例：`{"sub": "system:serviceaccount:ci:builder"}`。JSON 入力は最大 8 KiB に制限されています。値は文字列、符号付き 64 ビット整数、またはブール値である必要があり、型を含めて完全に一致する必要があります。`"123"` は `123` と一致しません。ネストされたオブジェクト、リスト、および `iss`、`aud`、`exp`、`nbf`、`iat`、`jti` などの時間またはトークン関連のクレームは許可されません。 |

各ポリシーは、個別のプロジェクトを選択することなく、**アカウントが所有する現在および将来のすべてのプロジェクト**に対する CI アクセス権限を付与します。最初のプロジェクトを作成する前にアイデンティティを設定できます。これはアカウント管理権限や他のアカウントへのアクセスを付与するものではありません。

一致するクレームを持つトークンを取得できるすべてのワークロードは、それらのすべてのプロジェクトにアクセスできるため、プロバイダーが保証し、誰も再利用できないクレームを選択してください。削除後に名前変更や再登録が可能な名前よりも、安定した数値 ID を優先してください。

> [!WARNING]
> 共有アイデンティティプロバイダーでは、ポリシーを組織またはテナント **と**、対象のアプリケーション、プロジェクト、またはサービスアカウントにバインドしてください。`main` などのブランチ名、`production` などの環境、または一般的なロールだけではアイデンティティの境界にはなりません。別のテナントが同じ値を持つトークンを取得する可能性があるためです。例えば、GitLab.com のポリシーは、`ref` だけでなく、対象プロジェクトの安定した `project_id` を含める必要があります。一致するトークンはキャッシュへの書き込みを含むアカウント全体の CI アクセス権限を付与するため、無関係なワークロードを信頼するポリシーはキャッシュポイズニングを許容する可能性があります。

Tuist は、発行者、オーディエンス、有効期限、not-before 時刻（最大 60 秒のクロックスキューを許容）、およびすべてのクレームを確認した後、トークンに署名した鍵を独自の JWKS URL が保持しているポリシーに対してのみアクセスを許可します。発行される 1 時間有効の CI トークンはアカウント全体に適用され、プロジェクト ID のスナップショットではありません。発行後にアカウントで作成または転送されたプロジェクトも含まれます。プロジェクトの承認には引き続き現在のアカウント所有権が必要であるため、プロジェクトをアカウント外に転送すると、そのアカウントのトークンによるアクセスは削除されます。

#### ワークロードの認証 {#authenticate-a-workload}

1. プロバイダーから、ポリシーのオーディエンスを指定してアイデンティティトークンをリクエストします。
2. `TUIST_OIDC_TOKEN` をそのトークンに設定し、`TUIST_OIDC_ACCOUNT` をプロジェクトを所有する Tuist アカウントのハンドルに設定します。アカウントはすべてのトラストポリシー交換で必須です。これは検索先を選択するだけであり、それ自体では何も権限を付与しません。
3. Tuist を実行します。`TUIST_TOKEN` または有効な保存済み認証情報が利用できない場合、CLI と Elixir 統合は自動的にトークンを交換します。`tuist auth login` および `mix tuist.login` も同様の交換を明示的に行います。

結果として得られる Tuist アクセストークンは `ci` スコープグループのみを持ち、選択したアカウントが所有する現在および将来のすべてのプロジェクトをカバーします。アカウント内の 20 を超えるポリシーが同じトークンに一致する場合、または 2 つを超える異なる JWKS URL を使用する場合、交換は失敗します。

Tuist はこれらのセッションを更新しません。アクセストークンは 1 時間後に失効し、リフレッシュトークンはありません。プロバイダーのアイデンティティトークンは通常数分間しか有効ではないため、古い `TUIST_OIDC_TOKEN` を保持することは更新戦略にはなりません。1 時間以上実行されるジョブの場合、Tuist セッションが失効する前に新しいアイデンティティトークンをリクエストし、再度ログインしてください。ポリシーを削除すると新しい交換は停止しますが、すでに発行されたアクセストークンは失効するまで有効です。

Tuist は、専用かつサイズ制限のあるキャッシュ内で、取得成功後最大 15 分間プロバイダーの署名鍵をキャッシュします。エントリはより早く削除され、再度取得される場合があります。失敗した取得はキャッシュされません。プロバイダーが鍵をローテーションする場合、その鍵でトークンに署名する少なくとも 15 分前に新しい鍵を JWKS で公開する必要があります。キャッシュされたセットに含まれない鍵で署名されたトークンは、キャッシュが失効するまで拒否されるためです。鍵 ID (`kid`) がないトークンは、JWKS に単一の適格な署名鍵が含まれている場合にのみ受け入れられます。JWKS に鍵 ID が存在する場合、それは最大 256 バイトの文字列でなければなりません。

> [!NOTE]
> `TUIST_OIDC_TOKEN` は汎用的なトークン入力であり、サーバーの信頼を回避する方法ではありません。CI プロバイダーの検出よりも優先されますが、サーバーは組み込みプロバイダーおよび一致するトラストポリシーを持つアイデンティティのみを受け入れます。Tuist 認証情報を想定する `TUIST_TOKEN` にアイデンティティトークンを入れないでください。

交換が失敗した場合、ポリシー内の発行者、オーディエンス、およびすべてのクレームがトークンと完全に一致すること、JWKS URL がトークンに署名した鍵を提供していること、ポリシーが削除されていないこと、そして `TUIST_OIDC_ACCOUNT` がプロジェクトを所有するアカウントを指していることを確認してください。どのアイデンティティが信頼されているかを露呈しないよう、Tuist はこれらのすべてのケースで同じエラーを返します。

### Fly.io Machines {#flyio-machines}

[Fly.io は OIDC ワークロードアイデンティティをサポートしています](https://docs.fly.io/reference/openid-connect/)。Machine は Fly API トークンや長寿命の Tuist シークレットなしで、ローカルの `/.fly/api` Unix ソケットから短命の署名付きアイデンティティトークンをリクエストできます。Fly トークンはソースリポジトリではなく組織とアプリケーションを識別するため、GitHub リポジトリを接続する代わりにトラストポリシーを使用してください。

1. Fly Machine 内で発行されたアイデンティティトークンから、発行者 (`iss`)、組織 ID (`org_id`)、およびアプリケーション ID (`app_id`) を取得します。発行者は `https://oidc.fly.io/<organization-slug>` です。組織名やアプリ名ではなく、数値 ID を使用してください。
2. **Fly.io Machines** テンプレートを使用して [トラストポリシーを作成](#create-a-trust-policy)し、組織スラッグと両方の数値 ID を入力します。これにより以下の値が入力され、ID は文字列として保持されます。**カスタムプロバイダー**を使用して手動で入力することもできます。その場合、クレーム内の ID を囲む引用符を保持してください。

   | フィールド | 値 |
   | --- | --- |
   | 発行者 URL | `https://oidc.fly.io/<organization-slug>` |
   | JWKS URL | `https://oidc.fly.io/<organization-slug>/.well-known/jwks` |
   | オーディエンス | `tuist` |
   | クレーム | `{"org_id": "<organization-id>", "app_id": "<application-id>"}` |

3. Machine 内で、`TUIST_OIDC_ACCOUNT` をプロジェクトを所有する Tuist アカウントのハンドル（Fly 組織スラッグではない）に設定し、オーディエンス `tuist` でトークンをリクエストして、`TUIST_OIDC_TOKEN` を使用して `tuist auth login` に渡します。

```bash
set -euo pipefail
export TUIST_OIDC_ACCOUNT="my-tuist-account"

TUIST_OIDC_TOKEN="$(curl --fail --silent --show-error \
  --unix-socket /.fly/api \
  -X POST http://localhost/v1/tokens/oidc \
  -H 'Content-Type: application/json' \
  --data '{"aud":"tuist"}')"
export TUIST_OIDC_TOKEN

tuist auth login
unset TUIST_OIDC_TOKEN
```

初期設定では、トークンをエクスポートした後、アンセットする前に、ローカルでアイデンティティフィールドのみを検査できます。これにより構成用のクレームをデコードします。Tuist は認証中に署名を個別に検証します。

```bash
python3 - <<'PY'
import base64, json, os
payload = os.environ["TUIST_OIDC_TOKEN"].split(".")[1]
claims = json.loads(base64.urlsafe_b64decode(payload + "=" * (-len(payload) % 4)))
print(json.dumps({key: claims[key] for key in ("iss", "org_id", "app_id")}, indent=2))
PY
```

トークン自体を印刷したりコミットしたりしないでください。許可された Fly アプリ内のすべての Machine は、Tuist アカウント内の現在および将来のすべてのプロジェクトに対して認証できます。追加のアプリごとに個別のポリシーを作成してください。Fly アイデンティティトークンは約 10 分後に失効するため、長時間実行される Machine では、1 時間の Tuist セッションが失効する前に新しいトークンをリクエストし、`tuist auth login` を再度実行してください。

### OIDC トークンスコープ {#oidc-token-scopes}

OIDC トークンには `ci` スコープグループが付与されます。GitHub Actions、CircleCI、Bitrise の場合、これによりリポジトリに接続されたすべてのプロジェクトへのアクセスが可能になります。接続された Amp ワークスペース、接続された Claude Code 環境、およびワークロードアイデンティティトラストポリシーの場合、これにより選択したアカウントが所有する現在および将来のすべてのプロジェクトへのアクセスが可能になりますが、プロジェクト作成、プロジェクト管理、ランナー管理、またはアカウントメンバー管理は付与されません。`ci` スコープに含まれる内容の詳細については、[スコープグループ](#scope-groups)を参照してください。

> [!TIP]
> **セキュリティ上の利点**
>
> OIDC 認証は長寿命トークンよりも安全です。その理由は次のとおりです。
> - シークレットのローテーションや管理が不要
> - トークンの有効期間が短い
> - 認証がリポジトリアイデンティティまたは明示的に許可されたワークロードアイデンティティに紐付けられている


## Gradle プラグインの認証 {#gradle-plugin-authentication}

Gradle プラグインは Tuist CLI の認証状態を使用し、独自のログインフローを定義しません。CLI で一度認証すると、プラグインはその認証情報を再利用します。

`project` や `url` を含むプロジェクトおよびサーバーの設定には、標準の <.localized_link href="/references/tuist-toml">tuist.toml リファレンス</.localized_link> を使用してください。

ローカルで使用するには、次を実行します。

```bash
tuist auth login
```

CI では、次のいずれかを使用します。

- <.localized_link href="/guides/server/authentication#setting-up-oidc-authentication">OIDC 認証</.localized_link>（利用可能な場合は推奨）
- `TUIST_TOKEN` を介した <.localized_link href="/guides/server/authentication#continuous-integration">アカウントトークン認証</.localized_link>

セルフホスト型の Tuist サーバーの場合、`tuist.toml` でサーバー URL を定義し（例：`url = "https://tuist.your-company.com"`）、標準のログインフローを実行してください。URL はプラグインが使用する同じ設定ファイルから解決されます。

認証を設定した後、Gradle のキャッシュコマンドとタスクを通常どおり実行してください。

## アカウントトークン {#account-tokens}

OIDC をサポートしない CI 環境や、権限を細かく制御する必要がある場合は、アカウントトークンを使用できます。アカウントトークンを使用すると、トークンがアクセスできるスコープとプロジェクトを正確に指定できます。

### アカウントトークンの作成 {#creating-an-account-token}

アカウントトークンを作成する最も簡単な方法は、ダッシュボードから行うことです。

1. Tuist ダッシュボードで組織を開きます。
2. **設定** > **トークン** に移動します。
3. **トークンを生成** を選択します。
4. 名前、任意の有効期限、プロジェクトへのアクセス、およびトークンに必要なスコープを選択します。
5. ダイアログを閉じる前に、生成されたトークンの値をコピーしてください。トークンの値は一度しか表示されません。

CLI からアカウントトークンを作成することもでき、スクリプトや自動化に役立ちます。

```bash
tuist account tokens create account-handle \
  --scopes account:cache:write project:cache:read project:cache:write \
  --name ci-cache-token \
  --expires 1y
```

> [!IMPORTANT]
> トークンにアクセスさせたいプロジェクトを所有するアカウントのハンドルで `account-handle` を置き換えてください。これは個人のアカウントではなく、組織のアカウントである可能性があります。

このコマンドは次のオプションを受け付けます。

| オプション | 説明 |
| --- | --- |
| `--scopes` | 必須。トークンに付与するスコープのスペース区切りリスト。 |
| `--name` | 必須。トークンの一意の識別子（1〜32文字、英数字、ハイフン、アンダースコアのみ）。 |
| `--expires` | 任意。トークンの有効期限。`30d`（日）、`6m`（月）、または `1y`（年）などの形式を使用します。指定しない場合、トークンは失効しません。 |
| `--projects` | トークンを特定のプロジェクトハンドルに制限します。指定しない場合、トークンはすべてのプロジェクトにアクセスできます。 |

### 利用可能なスコープ {#available-scopes}

| スコープ | 説明 |
| --- | --- |
| `account:cache:read` | アカウントスコープのキャッシュ済みバイナリをダウンロード |
| `account:cache:write` | アカウントスコープのキャッシュ済みバイナリをアップロード |
| `account:members:read` | アカウントメンバーを読み取り |
| `account:members:write` | アカウントメンバーを管理 |
| `account:registry:read` | Swift パッケージレジストリから読み取り |
| `account:registry:write` | Swift パッケージレジストリに公開 |
| `account:runners:read` | ランナーのジョブ、ワークフロー、プロファイル、およびボリュームを読み取り |
| `account:runners:write` | ランナーのプロファイルを管理し、ランナーのボリュームを削除 |
| `account:sandboxes:write` | アカウントのメンバーと同様に、サンドボックスを作成してその中でコマンドを実行 |
| `project:previews:read` | プレビューをダウンロード |
| `project:previews:write` | プレビューをアップロード |
| `project:admin:read` | プロジェクトとその設定を読み取り |
| `project:admin:write` | プロジェクトの作成、更新、削除。プロジェクトを作成するには、すべてのプロジェクトにアクセスできるトークンが必要です |
| `project:cache:read` | キャッシュ済みバイナリをダウンロード |
| `project:cache:write` | キャッシュ済みバイナリをアップロード |
| `project:bundles:read` | バンドルを表示 |
| `project:bundles:write` | バンドルをアップロード |
| `project:tests:read` | テスト結果を読み取り |
| `project:tests:write` | テスト結果をアップロード |
| `project:builds:read` | ビルド分析を読み取り |
| `project:builds:write` | ビルド分析をアップロード |
| `project:runs:read` | コマンド実行を読み取り |
| `project:runs:write` | コマンド実行を作成および更新 |

### スコープグループ {#scope-groups}

スコープグループは、単一の識別子で複数の関連するスコープを付与する便利な方法を提供します。スコープグループを使用すると、含まれる個々のスコープが自動的に展開されます。

| スコープグループ | 含まれるスコープ |
| --- | --- |
| `ci` | `account:cache:write`, `project:cache:write`, `project:previews:write`, `project:bundles:write`, `project:tests:write`, `project:builds:write`, `project:runs:write` |
| `mcp` | `project:cache:read`, `project:previews:read`, `project:bundles:read`, `project:tests:read`, `project:builds:read`, `project:runs:read` |

### 継続的インテグレーション {#continuous-integration}

OIDC をサポートしない CI 環境では、`ci` スコープグループを使用してアカウントトークンを作成し、CI ワークフローを認証してください。ダッシュボードでトークンを生成する際に、**CI** プリセットを選択します。

CLI から同じトークンを作成することもできます。

```bash
tuist account tokens create account-handle --scopes ci --name ci
```

これにより、一般的な CI 操作（キャッシュ、プレビュー、バンドル、テスト、ビルド、実行）に必要なすべてのスコープを持つトークンが作成されます。生成されたトークンを CI 環境のシークレットとして保存し、`TUIST_TOKEN` 環境変数として設定してください。

### アカウントトークンの管理 {#managing-account-tokens}

アカウントダッシュボードで **設定** > **トークン** を開き、アカウントトークンを表示したり、トークンのスコープとプロジェクトへのアクセスを確認したり、ローテーション中にトークンを取り消したりできます。

アカウントのすべてのトークンを一覧表示するには:

```bash
tuist account tokens list account-handle
```

名前でトークンを取り消すには:

```bash
tuist account tokens revoke account-handle ci-cache-token
```

### アカウントトークンの使用 {#using-account-tokens}

アカウントトークンは、環境変数 `TUIST_TOKEN` として定義されることが想定されています。

```bash
export TUIST_TOKEN=your-account-token
```

> [!TIP]
> **アカウントトークンを使用するタイミング**
>
> 次のような場合にアカウントトークンを使用してください。
> - OIDC をサポートしない CI 環境での認証
> - トークンが実行できる操作に対するきめ細かい制御
> - アカウント内の複数のプロジェクトにアクセスできるトークン
> - 自動的に失効する時間制限付きトークン
