# Gradle コードカバレッジ {#gradle-code-coverage}

コードカバレッジは、テストがコードのどの行を実行したかを示します。Tuist Gradle プラグインは JaCoCo を使用してテストタスクのカバレッジを測定し、各テスト実行ごとにアップロードします。Tuist はコミットの各実行を集約し、プロジェクト全体、各 Gradle プロジェクト、および各ファイルごとの数値として表示します。ダッシュボードの **コードカバレッジ** ページでは、コミットごとの数値と各ブランチのトレンドを確認できます。

> [!IMPORTANT]
> **要件**
>
> - `dev.tuist` Gradle プラグインが適用されていること（詳細は <.localized_link href="/guides/get-started/gradle-project">Gradle プロジェクトで始める</.localized_link> を参照）
> - プロジェクトが Git リポジトリ内にあること：リポジトリ外での実行ではテスト結果はアップロードされますが、カバレッジはアップロードされません

## セットアップ {#setup}

### カバレッジを有効にする {#turn-coverage-on}

`settings.gradle.kts` の `tuist` ブロックでカバレッジを有効にします：

```kotlin
tuist {
    coverage {
        enabled = true
    }
}
```

または、CI ジョブなどの単一の実行に対して環境変数で有効にすることもできます。この場合、環境変数の設定が優先されます：

```sh
TUIST_TEST_COVERAGE=1 ./gradlew test
```

カバレッジの有効・無効によってテストタスクのビルドキャッシュエントリは別々になります（[パフォーマンスへの影響](#performance-impact) を参照）。CI とローカルビルドがビルドキャッシュを共有している場合は、設定による制御を推奨します。CI でのみカバレッジを有効にすると、互いのテスト結果を再利用することを防げます。

カバレッジが有効な場合、プラグインはすべての JVM プロジェクトに Gradle の `jacoco` プラグインを適用します。JaCoCo エージェントは、あなたが手動でプラグインを適用した場合と同様に、プロジェクトのリポジトリから取得されます。すでに JaCoCo を構成しているプロジェクトは既存の設定を維持し、独自のレポートも引き続き機能します。

### Android プロジェクト {#android-projects}

このプラグインは、`testDebugUnitTest` などの Android プロジェクトのローカルユニットテストを測定します。デバイスやエミュレータ上で実行されるインストゥルメント化テストは測定対象ではありません。

ユニットテストで Robolectric を使用している場合は、Robolectric が読み込むクラスを JaCoCo に含めるよう指示してください。Robolectric はアプリのクラスを独自のクラスローダーで定義するため、JaCoCo はデフォルトでこれらのクラスをスキップします。その結果、それらのテストが実行するコードはカバーされていないと表示されてしまいます。Android プロジェクトの `build.gradle.kts` で以下を設定します：

```kotlin
pluginManager.withPlugin("jacoco") {
    tasks.withType<Test>().configureEach {
        extensions.configure<JacocoTaskExtension> {
            isIncludeNoLocationClasses = true
            excludes = listOf("jdk.internal.*")
        }
    }
}
```

このブロックはカバレッジが有効な場合にのみ適用されます。これは、プラグインが `jacoco` を適用するのがその時だからです。

Android のユニットテストはデフォルトで JUnit 4 で実行され、カバレッジは記録されますが、[各テストが実行したコード](#per-test-evidence) は記録されません。これを記録するには、JUnit Vintage を介して JUnit Platform 上で実行してください。

### シャード実行 {#sharded-runs}

<.localized_link href="/guides/features/test-sharding/gradle">テストをシャード分割</.localized_link> する場合、カバレッジを有効にして実行された各シャードは、自身が実行したテストのカバレッジを報告し、Tuist は実行内の各シャードを統合して一つの数値にまとめます。シャードは意図的にスイートの一部を実行するため、コミットのカバレッジが不完全になることはありません。

### CI で各コミットを完了させる {#complete-each-commit}

コミットのカバレッジは、シャードごとのジョブなど、複数のジョブから得られることがよくあります。Tuist は最後に報告されたジョブを自動で検出できないため、明示的に通知する必要があります。コミットに関するすべてのテストジョブが終了したら、それらすべてに依存するジョブで以下を実行してください：

```sh
./gradlew tuistCoverageComplete
```

単一のジョブでコミットのすべてのテストを実行する場合は、テストの失敗時も含め、テスト実行後のステップとしてタスクを実行してください。失敗したテストを含む実行でも、カバレッジは報告されます。

タスクは `GIT_COMMIT` またはチェックアウトの `HEAD` からコミットを読み取ります。別のコミットを指定するには `-Ptuist.coverage.commit=<sha>` を渡してください。コミットが完了するまで、そのカバレッジは **進行中** と表示され、ブランチのトレンドには含まれません。

## 仕組み {#how-it-works}

### Tuist が測定するもの {#what-tuist-measures}

- **プロジェクト。** 各 Gradle プロジェクトはダッシュボード上のモジュールとして扱われ、それぞれ独自のカバレッジを持ちます。
- **プロダクトコードのみ。** テストソースセットからコンパイルされたクラスはテストコードです。Tuist はこれらを保存しますが、あらゆる数値からは除外します。
- **リポジトリ内のファイル。** クラスは、リポジトリ内のパスに基づき、コンパイル元のソースファイルに対応付けられます。生成されたソースや Git が無視するファイルは報告されません。
- **各行の実行有無。** JaCoCo はコードが実行されたかどうかを記録し、実行回数は記録しません。そのため、ダッシュボード上の実行回数は 0 または 1 となります。

### 各テストが実行したコード {#per-test-evidence}

JUnit Platform（JUnit 5、または JUnit Vintage を介した JUnit 4）上で実行されるテストの場合、プラグインは各テストが実行したコードと、`@BeforeAll` などテスト外で各テストクラスが実行した内容を記録します。これにより、Tuist は実行から除外されたテストのカバレッジを過去のデータから引き継ぐことができます（[スキップされたテスト](#skipped-tests) を参照）。テスト側に追加の設定は不要です。

これは、各テスト JVM が一度に一つのテストを実行する場合に機能します。JUnit の並列実行を有効にしない限り、Gradle はこの方法でテストを実行します。`maxParallelForks` を使用して複数の JVM でテストクラスを実行することは問題ありません。同じ JVM 内で同時に実行されるテストもカバレッジには計上されますが、個別のテストごとの記録は行われません。

### ビルドキャッシュ {#build-cache}

ビルドキャッシュから復元されたテストタスク、または最新状態のテストタスクは、テストを実行しません。それでもカバレッジはアップロードされます。JaCoCo のデータはタスクの出力の一つであり、同じ入力に対してテストを実行した実行によって記録されるためです。

### スキップされたテスト {#skipped-tests}

実行からテストが除外された場合、Tuist は実行されたコードに変更がない限り、以前の実行からカバレッジ情報を補完します。補完できない場合、コミットのカバレッジは **不完全** となります。実行から除外されるパターン：

- **プロジェクトのテストタスクを除外**した場合（例: `-x :app:test`）。コードが変更されていない最後のテスト実行の結果が引き継がれます。
- **一部のプロジェクトのテスト**のみを実行する場合（例: `./gradlew :core:test`）、または**一部のテスト**のみを実行する場合（例: `--tests`）。この実行は指定されたもののみをカバーするため、コミット内のすべてのテストを実行する別の実行がない限り、カバレッジは不完全となります。
- **最初の失敗で停止したテストタスク**（`failFast`）。

意図的に除外され、コミットを不完全にしないテストもあります：

- **ビルドスクリプト内のフィルタ**（例：`filter { excludeTestsMatching(...) }`）。これらはスイートが実行するテストを定義します。
- **ビルドスクリプトで無効にしたテストタスク**（`enabled = false` またはそれらをスキップする `onlyIf` を使用）。
- **<.localized_link href="/guides/features/test-insights/flaky-tests/gradle">検疫</.localized_link>によってスキップされたテスト。** これらは削除されたものとして除外されるため、これらのテストのみがカバーしていた行は未カバーとして扱われます。
- **他のシャードのテスト**。[テストをシャード化](#sharded-runs)している場合です。

### 完全および不完全なコミット {#commit-status}

| ステータス | 意味 |
| --- | --- |
| 進行中 | 実行からカバレッジが報告されていますが、コミットに対して `tuistCoverageComplete` がまだ実行されていません。 |
| 完了 | コミットの実行に含まれるすべてのテストが実行されたか、引き継がれたか、意図的に除外されました。 |
| 不完全 | 一部のカバレッジを特定できなかったため、数値は下限となります。 |
| 未測定 | コミットに対してカバレッジを報告した実行がありません。 |

ブランチのトレンドには、完了したコミットのみが含まれます。

## パフォーマンスへの影響 {#performance-impact}

JaCoCo はテスト JVM がクラスをロードする際にインストゥルメントするため、コンパイル済みクラスとコンパイルタスクのビルドキャッシュエントリは、カバレッジの有無にかかわらず同じままです。SBOM ジェネレーターなど、すべての依存関係構成を読み取るタスクも JaCoCo エージェントの影響を受けるため、カバレッジを有効にすると出力が変化します。テストの実行速度はわずかに低下し、プラグインはテストタスクの完了後に JaCoCo のデータを読み取ります。カバレッジ有効時と無効時のテストタスクは別々のビルドキャッシュエントリを持つため、カバレッジ無効時の結果がキャッシュされていても、カバレッジ有効での初回実行ではテストが実行されます。

## 制限事項 {#limitations}

- **分離プロジェクトとオンデマンド設定。** これらのビルドはすべてのプロジェクトを設定しないため、プラグインは実行からどのプロジェクトのテストが除外されたかを判別できず、一部のプロジェクトのテストのみを実行した場合でも完了として扱われます。
- **フォークからのプルリクエストからはカバレッジを取得できません。** カバレッジは Tuist で認証された実行によってのみアップロードされ、CI は通常、フォークから開かれたプルリクエストに対してシークレットや ID トークンを提供しません。

## カバレッジのクエリ {#querying}

ダッシュボードの **コードカバレッジ** ページには、各コミットの数値、モジュール、ファイル、および各実行がカバーした行が表示されます。同じデータは、<.localized_link href="/guides/features/agentic-coding/mcp">Model Context Protocol サーバー</.localized_link> を介してエージェントからも利用可能です。
