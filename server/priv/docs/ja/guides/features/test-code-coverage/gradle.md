# Gradle コードカバレッジ {#gradle-code-coverage}

コードカバレッジは、テストがコードのどの行を実行したかを示します。Tuist Gradle プラグインは JaCoCo を使ってテストタスクのカバレッジを測定し、各テスト実行ごとにアップロードします。Tuist はコミットの各実行を集約して 1 つの数値にまとめ、プロジェクト全体、各 Gradle プロジェクト、および各ファイルごとに表示します。ダッシュボードの **コードカバレッジ** ページでは、コミットごとの結果とブランチごとの推移を確認できます。

> [!IMPORTANT]
> **必要条件**
>
> - `dev.tuist` Gradle プラグインが適用されていること（詳細は <.localized_link href="/guides/get-started/gradle-project">Gradle プロジェクトで始める</.localized_link> を参照）
> - プロジェクトが Git リポジトリ内にあること：リポジトリ外での実行ではテスト結果はアップロードされますが、カバレッジは含まれません

## セットアップ {#setup}

### カバレッジを有効にする {#turn-coverage-on}

`settings.gradle.kts` の `tuist` ブロックでカバレッジを有効にします：

```kotlin
tuist {
    coverage {
        enabled = true
    }
}
```

または、CI ジョブなどの単一の呼び出しに対して環境変数で有効にすることもできます。この設定はどちらの場合でも優先されます：

```sh
TUIST_TEST_COVERAGE=1 ./gradlew test
```

カバレッジを有効にすると、プラグインはすべての JVM プロジェクトに Gradle の `jacoco` プラグインを適用します。JaCoCo エージェントは、自分でプラグインを適用した場合と同様に、プロジェクトのリポジトリから取得されます。すでに JaCoCo を構成しているプロジェクトは既存の設定を維持し、独自のレポートも引き続き機能します。

### シャード化された実行 {#sharded-runs}

<.localized_link href="/guides/features/test-sharding/gradle">テストをシャード化</.localized_link> すると、カバレッジを有効にして実行された各シャードが、実行したテストのカバレッジを報告し、Tuist は 1 回の実行における複数のシャードの結果を 1 つの数値に統合します。シャードは意図的にスイートの一部のみを実行するため、コミットのカバレッジが不完全になることはありません。

### CI で各コミットを完了させる {#complete-each-commit}

コミットのカバレッジ情報は、多くの場合、シャードごとのジョブなど複数のジョブから提供されます。Tuist は最後のジョブが報告を終えたタイミングを自動で検出できないため、明示的に通知する必要があります。コミットに関連するすべてのテストジョブが終了したら、それらすべてに依存するジョブで次のコマンドを実行してください：

```sh
./gradlew tuistCoverageComplete
```

このタスクは `GIT_COMMIT` またはチェックアウトの `HEAD` からコミットを読み取ります。別のコミットを指定するには `-Ptuist.coverage.commit=<sha>` を渡してください。コミットが完了するまで、そのカバレッジは **進行中** と表示され、ブランチの推移には含められません。

## 仕組み {#how-it-works}

### Tuist が測定する内容 {#what-tuist-measures}

- **プロジェクト。** 各 Gradle プロジェクトはダッシュボード上のモジュールとして扱われ、それぞれ独自のカバレッジを持ちます。
- **プロダクトコードのみ。** テストソースセットからコンパイルされたクラスはテストコードです。Tuist はこれらを保存しますが、すべての数値からは除外します。
- **リポジトリ内のファイル。** クラスは、リポジトリ内のパスに基づいてコンパイル元のソースファイルに対応付けられます。生成されたソースや Git が無視するファイルは報告されません。
- **各行の実行有無。** JaCoCo はコードが実行されたかどうかを記録し、実行回数は記録しません。そのため、ダッシュボード上の実行回数は 0 または 1 になります。

### 各テストが実行したコード {#per-test-evidence}

JUnit Platform（JUnit 5、または JUnit Vintage 経由の JUnit 4）上で実行されるテストの場合、プラグインは各テストが実行したコードと、`@BeforeAll` などテスト外の部分で各テストクラスが実行したコードも記録します。これにより、Tuist は実行から除外されたテストのカバレッジを過去のデータから引き継ぐことができます（[スキップされたテスト](#skipped-tests) を参照）。テスト側に追加の設定は不要です。

これは、各テスト用 JVM が一度に 1 つのテストを実行する場合に機能します。JUnit の並列実行を有効にしない限り、Gradle はこの方法でテストを実行します。`maxParallelForks` を使用して複数の JVM でテストクラスを実行しても問題ありません。1 つの JVM 内で同時に実行されるテストもカバレッジには計上されますが、個別には識別されません。

### ビルドキャッシュ {#build-cache}

ビルドキャッシュから復元されたテストタスク、または最新の状態であるテストタスクは、テストを実行しません。しかし、そのカバレッジは依然としてアップロードされます。JaCoCo のデータはタスクの出力の一つであり、同じ入力に対してテストを実行した実行によって記録されます。

### スキップされたテスト {#skipped-tests}

実行からテストが除外された場合、Tuist は実行対象のコードに変更がない限り、以前の実行からカバレッジ情報を補完します。補完できない場合、コミットのカバレッジは **不完全** となります。実行から除外されるパターン：

- **プロジェクトのテストタスクを除外**：`-x :app:test` を使用。これらのテストは、コードに変更がない直近の実行からカバレッジを引き継ぎます。
- **一部のプロジェクトのテスト**：`./gradlew :core:test` を使用、または **一部のテスト**：`--tests` を使用。この実行は指定されたもののみをカバーするため、コミットの別の実行で全体が実行されない限り、コミットは不完全となります。
- **最初の失敗で停止したテストタスク**（`failFast`）。

意図的に除外され、コミットを不完全にしないテストもあります：

- **ビルドスクリプト内のフィルター**：`filter { excludeTestsMatching(...) }` など、スイートの実行対象を定義するもの。
- **ビルドスクリプトで無効化したテストタスク**：`enabled = false` またはそれらをスキップする `onlyIf` を使用。
- **<.localized_link href="/guides/features/test-insights/flaky-tests/gradle">隔離</.localized_link> によってスキップされたテスト。** これらは削除されたものとして扱われるため、これらのテストのみがカバーしていた行は未カバーとして計上されます。
- **他のシャードのテスト**：[テストをシャード化](#sharded-runs) している場合。

### 完了および不完全なコミット {#commit-status}

| ステータス | 意味 |
| --- | --- |
| 進行中 | 実行からカバレッジが報告されていますが、コミットに対して `tuistCoverageComplete` がまだ実行されていません。 |
| 完了 | コミットの実行に含まれるすべてのテストが実行されたか、引き継がれたか、意図的に除外されました。 |
| 不完全 | 一部のカバレッジを特定できなかったため、数値は下限となります。 |
| 未測定 | コミットに対してカバレッジを報告した実行がありません。 |

ブランチのトレンドには、完了したコミットのみが含まれます。

## パフォーマンスへの影響 {#performance-impact}

JaCoCo はテスト JVM がクラスをロードする際にインストルメンテーションを行うため、コンパイル済みクラスやコンパイルタスクのビルドキャッシュエントリは、カバレッジの有無にかかわらず同じままです。SBOM ジェネレーターなど、すべての依存関係設定を読み取るタスクも JaCoCo のエージェントを検出するため、カバレッジを有効にすると出力が変化します。テストの実行はわずかに遅くなり、プラグインはテストタスクの終了後に JaCoCo のデータを読み取ります。カバレッジ有効時と無効時のテストタスクは別々のビルドキャッシュエントリを持つため、カバレッジ無効時の結果がキャッシュされていても、カバレッジ有効での初回実行ではテストが実行されます。

## 制限事項 {#limitations}

- **Isolated Projects とオンデマンド設定。** これらのビルドはすべてのプロジェクトを設定しないため、プラグインは実行からどのプロジェクトのテストが除外されたかを判別できず、一部のプロジェクトのテストのみを実行した場合でも完了として扱われます。
- **フォークからのプルリクエストからはカバレッジを取得できません。** カバレッジは Tuist で認証された実行によってのみアップロードされ、CI は通常、フォークから開かれたプルリクエストに対してシークレットや ID トークンを提供しません。

## カバレッジのクエリ {#querying}

ダッシュボードの **コードカバレッジ** ページには、各コミットの数値、モジュール、ファイル、および各実行でカバーされた行が表示されます。同じデータは、<.localized_link href="/guides/features/agentic-coding/mcp">Model Context Protocol サーバー</.localized_link> を介してエージェントからも利用可能です。
