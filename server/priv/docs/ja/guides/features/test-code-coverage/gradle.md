# Gradleのコードカバレッジ {#gradle-code-coverage}

コードカバレッジは、テストがコードのどの行を実行したかを示します。Tuist GradleプラグインはJaCoCoを使用してテストタスクのカバレッジを測定し、各テスト実行時にアップロードします。Tuistはコミット内の各実行を統合し、プロジェクト全体、各Gradleプロジェクト、および各ファイルごとの数値として集計します。ダッシュボードの**Code Coverage**ページでは、コミットごとの結果とブランチごとの推移を確認できます。

> [!IMPORTANT]
> **要件**
>
> - `dev.tuist` Gradleプラグインが適用されていること（詳細は<.localized_link href="/guides/get-started/gradle-project">Gradleプロジェクトで始める</.localized_link>を参照）
> - プロジェクトがGitリポジトリ内にあること：リポジトリ外での実行ではテスト結果はアップロードされますが、カバレッジはアップロードされません

## セットアップ {#setup}

### カバレッジを有効にする {#turn-coverage-on}

`settings.gradle.kts` の `tuist` ブロックでカバレッジを有効にします：

```kotlin
tuist {
    coverage {
        enabled = true
    }
}
```

または、CIジョブなどの単一の実行に対して環境変数で有効にすることもできます。この設定はブロック内の設定よりも優先されます：

```sh
TUIST_TEST_COVERAGE=1 ./gradlew test
```

カバレッジが有効なテストタスクと無効なテストタスクは別々のビルドキャッシュエントリを持ちます（[パフォーマンスへの影響](#performance-impact)を参照）。CIとローカルビルドでビルドキャッシュを共有している場合は、設定による有効化をお勧めします。CIでのみカバレッジを有効にすると、互いのテスト結果の再利用を防ぐことができます。

カバレッジが有効な場合、プラグインはすべてのJVMプロジェクトにGradleの `jacoco` プラグインを適用します。JaCoCoのエージェントは、あなたが手動でプラグインを適用した場合と同様に、プロジェクトのリポジトリから取得されます。すでにJaCoCoを設定しているプロジェクトは既存の設定を維持し、独自のレポートも引き続き機能します。

### Androidプロジェクト {#android-projects}

このプラグインは、`testDebugUnitTest` などのAndroidプロジェクトのローカルユニットテストを測定します。デバイスやエミュレータ上で実行されるインストゥルメンテーションテストは測定されません。

ユニットテストでRobolectricを使用している場合は、Robolectricが読み込むクラスをJaCoCoに含めるよう指示してください。Robolectricは独自のクラスローダーでアプリのクラスを定義するため、JaCoCoはデフォルトでこれらのクラスをスキップします。その結果、それらのテストが実行するコードは未カバーとして表示されます。Androidプロジェクトの `build.gradle.kts` で以下のように設定します：

```kotlin
pluginManager.withPlugin("jacoco") {
    tasks.withType<Test>().configureEach {
        extensions.configure<JacocoTaskExtension> {
            isIncludeNoLocationClasses = true
            excludes = listOf("jdk.internal.*")
        }
    }
}
```

このブロックはカバレッジが有効な場合にのみ適用されます。これは、プラグインが `jacoco` を適用するのがその時だからです。

AndroidのユニットテストはデフォルトでJUnit 4上で実行され、カバレッジは記録されますが、[各テストが実行したコード](#per-test-evidence)までは記録されません。これを記録するには、JUnit Vintageを介してJUnit Platform上で実行してください。

### シャード化された実行 {#sharded-runs}

<.localized_link href="/guides/features/test-sharding/gradle">テストをシャード化</.localized_link>する場合、カバレッジ有効状態で実行された各シャードは、自身が実行したテストのカバレッジを報告します。Tuistは実行内の各シャードを統合して一つの数値にまとめます。シャードは意図的にスイートの一部のみを実行するため、コミットのカバレッジが不完全になることはありません。

### CIで各コミットを完了させる {#complete-each-commit}

コミットのカバレッジは、シャードごとに1つなど、複数のジョブから報告されることがよくあります。Tuistは最後のジョブが報告を終えたタイミングを自動検出できないため、明示的に通知する必要があります。コミットに関連するすべてのテストジョブが終了したら、それらすべてに依存するジョブで以下を実行してください：

```sh
./gradlew tuistCoverageComplete
```

単一のジョブでコミットのすべてのテストを実行する場合は、代わりにテスト後のステップとしてタスクを実行してください。テストが失敗した場合でも同様です。失敗したテストを含む実行でも、カバレッジは報告されます。

タスクは `GIT_COMMIT` またはチェックアウトの `HEAD` からコミットを読み取ります。別のコミットを指定するには `-Ptuist.coverage.commit=<sha>` を渡してください。コミットが完了するまで、そのカバレッジは **In progress** と表示され、ブランチの推移には含まれません。

## 仕組み {#how-it-works}

### Tuistが測定するもの {#what-tuist-measures}

- **プロジェクト。** 各Gradleプロジェクトはダッシュボード上のモジュールとして扱われ、それぞれ独自のカバレッジを持ちます。
- **プロダクトコードのみ。** テストソースセットからコンパイルされたクラスはテストコードです。Tuistはこれらを保存しますが、すべての数値からは除外します。
- **リポジトリ内のファイル。** クラスは、リポジトリ内のパスに基づいて、コンパイル元のソースファイルに対応します。生成されたソースやGitが無視するファイルは報告されません。
- **各行の実行有無。** JaCoCoはコードが実行されたかどうかを記録し、実行回数は記録しません。そのため、ダッシュボード上の実行回数は0または1になります。

### 各テストが実行したコード {#per-test-evidence}

JUnit Platform（JUnit 5、またはJUnit Vintageを介したJUnit 4）上で実行されるテストの場合、プラグインは各テストが実行したコードと、`@BeforeAll` などテスト外の部分で各テストクラスが実行した内容を記録します。これにより、Tuistは実行から除外されたテストのカバレッジを過去の実行から引き継ぐことができます（[スキップされたテスト](#skipped-tests)を参照）。テストに追加の設定は必要ありません。

これは、各テストJVMが一度に1つのテストを実行する場合に機能します。JUnitの並列実行を有効にしない限り、Gradleはこの方法でテストを実行します。`maxParallelForks` を使用して複数のJVMでテストクラスを実行しても問題ありません。1つのJVM内で同時に実行されるテストもカバレッジには計上されますが、個別には識別されません。

### ビルドキャッシュ {#build-cache}

ビルドキャッシュから復元されたテストタスク、または最新状態のテストタスクは、テストを実行しません。それでもカバレッジはアップロードされます。JaCoCoのデータはタスクの出力の一つであり、同じ入力に対してテストを実行した実行によって記録されたものだからです。

### スキップされたテスト {#skipped-tests}

実行からテストが除外された場合、Tuistは実行対象のコードに変更がない限り、以前の実行でカバーされていた内容を補完します。補完できない場合、コミットのカバレッジは **Incomplete** となります。実行から除外されるパターン：

- **プロジェクトのテストタスクを除外**した場合（`-x :app:test`を使用）。これらのテストは、コードに変更がない最後の実行の結果から引き継がれます。
- **一部のプロジェクトのテスト**（`./gradlew :core:test`を使用）、または **一部のテスト**（`--tests`を使用）。この実行は要求された部分のみをカバーするため、コミットの別の実行で全てが実行されていない限り、コミットは不完全となります。
- **最初の失敗で停止したテストタスク**（`failFast`）。

意図的に除外され、コミットを不完全にしないテストもあります：

- **ビルドスクリプト内のフィルタ**（`filter { excludeTestsMatching(...) }`など）。これはスイートが実行するテストを定義するものです。
- **ビルドスクリプトで無効にしたテストタスク**（`enabled = false` またはそれらをスキップする `onlyIf` を使用）。
- **<.localized_link href="/guides/features/test-insights/flaky-tests/gradle">quarantine</.localized_link> によってスキップされたテスト。** これらは削除されたものとして除外されるため、これらのテストのみがカバーしていた行は未カバーとして扱われます。
- **他のシャードのテスト**（[テストをシャード化](#sharded-runs)した場合）。

### 完全および不完全なコミット {#commit-status}

| ステータス | 意味 |
| --- | --- |
| 進行中 | 実行からカバレッジが報告されていますが、コミットに対して `tuistCoverageComplete` がまだ実行されていません。 |
| 完了 | コミットの実行におけるすべてのテストが実行されたか、引き継がれたか、意図的に除外されました。 |
| 不完全 | 一部のカバレッジを特定できなかったため、数値は下限となります。 |
| 未測定 | コミットに対するカバレッジを報告した実行がありません。 |

ブランチのトレンドには、完全なコミットのみが含まれます。

## パフォーマンスへの影響 {#performance-impact}

JaCoCo はテストJVMがクラスをロードする際にインストルメントするため、コンパイル済みクラスとコンパイルタスクのビルドキャッシュエントリは、カバレッジの有無にかかわらず同じままです。SBOMジェネレータなど、すべての依存関係設定を読み取るタスクもJaCoCoエージェントの影響を受けるため、カバレッジを有効にすると出力が変化します。テストの実行速度はわずかに低下し、プラグインはテストタスクの終了後にJaCoCoのデータを読み取ります。カバレッジ有効時と無効時のテストタスクは別々のビルドキャッシュエントリを持つため、カバレッジ無効時の結果がキャッシュされていても、カバレッジ有効での初回実行ではテストが実行されます。

## 制限事項 {#limitations}

- **Isolated Projects と configuration on demand。** これらのビルドではすべてのプロジェクトを設定しないため、プラグインは実行からどのプロジェクトのテストが除外されたかを判別できず、一部のプロジェクトのテストのみを実行した場合でも完了として扱われます。
- **フォークからのプルリクエストからはカバレッジを取得できません。** カバレッジはTuistで認証された実行によってのみアップロードされ、CIは通常、フォークから開かれたプルリクエストに対してシークレットやIDトークンを提供しません。

## カバレッジのクエリ {#querying}

ダッシュボードの **Code Coverage** ページには、各コミットの数値、そのモジュール、ファイル、および各実行がカバーした行が表示されます。同じデータは、<.localized_link href="/guides/features/agentic-coding/mcp">Model Context Protocol server</.localized_link> を介してエージェントからも利用可能です。
