# Gradleのコードカバレッジ {#gradle-code-coverage}

コードカバレッジは、テストがコードのどの行を実行したかを示します。Tuist GradleプラグインはJaCoCoを使用してテストタスクのカバレッジを測定し、各テスト実行時にそれをアップロードします。Tuistは、プロジェクト全体、各Gradleプロジェクト、および各ファイルについて、コミット内のすべての実行を1つの数値に集約します。ダッシュボードの**コードカバレッジ**ページでは、コミットごとの結果と各ブランチのトレンドを表示します。

> [!IMPORTANT]
> **要件**
>
> - `dev.tuist` Gradleプラグインが適用されていること（詳細は<.localized_link href="/guides/get-started/gradle-project">Gradleプロジェクトで始める</.localized_link>を参照）
> - プロジェクトがGitリポジトリ内にあること：リポジトリ外での実行はテスト結果をアップロードしますが、カバレッジはアップロードしません

## セットアップ {#setup}

### カバレッジを有効にする {#turn-coverage-on}

`settings.gradle.kts` の `tuist` ブロックでカバレッジを有効にします：

```kotlin
tuist {
    coverage {
        enabled = true
    }
}
```

または、CIジョブなどの1回の実行に対してのみ環境変数で有効にすることもできます。この場合、環境変数の設定が優先されます：

```sh
TUIST_TEST_COVERAGE=1 ./gradlew test
```

カバレッジが有効なテストタスクと無効なテストタスクは別々のビルドキャッシュエントリを持ちます（[パフォーマンスへの影響](#performance-impact)を参照）。CIとローカルビルドがビルドキャッシュを共有する場合は、設定による有効化をお勧めします。CIでのみカバレッジを有効にすると、互いのテスト結果を再利用できなくなるのを防げます。

カバレッジが有効な場合、プラグインはすべてのJVMプロジェクトにGradleの `jacoco` プラグインを適用します。JaCoCoのエージェントは、あなたが自分でプラグインを適用した場合と同様に、プロジェクトのリポジトリから取得されます。すでにJaCoCoを設定しているプロジェクトは、その設定を維持し、独自のレポートも引き続き機能します。

### Androidプロジェクト {#android-projects}

このプラグインは、`testDebugUnitTest` などのAndroidプロジェクトのローカル単体テストを測定します。デバイスやエミュレータ上で実行されるインストゥルメント化テストは測定されません。

単体テストでRobolectricを使用している場合は、Robolectricが読み込むクラスをJaCoCoに含めるよう指示してください。Robolectricはアプリのクラスを独自のクラスローダーで定義するため、JaCoCoはデフォルトでそのようなクラスをスキップします。その結果、それらのテストが実行するコードはカバーされていないと表示されてしまいます。Androidプロジェクトの `build.gradle.kts` で以下のように設定します：

```kotlin
pluginManager.withPlugin("jacoco") {
    tasks.withType<Test>().configureEach {
        extensions.configure<JacocoTaskExtension> {
            isIncludeNoLocationClasses = true
            excludes = listOf("jdk.internal.*")
        }
    }
}
```

このブロックは、プラグインが `jacoco` を適用するとき、つまりカバレッジが有効な場合にのみ適用されます。

Androidの単体テストはデフォルトでJUnit 4上で実行され、カバレッジは記録されますが、[各テストが実行したコード](#per-test-evidence)は記録されません。これを記録するには、JUnit Vintageを介してJUnit Platform上で実行してください。

### シャーディングされた実行 {#sharded-runs}

<.localized_link href="/guides/features/test-sharding/gradle">テストをシャーディング</.localized_link>する場合、カバレッジ有効で実行された各シャードは、自身が実行したテストのカバレッジを報告し、Tuistは1回の実行におけるすべてのシャードを1つの数値にマージします。シャードは意図的にスイートの一部のみを実行するため、コミットのカバレッジが不完全になることはありません。

### CIで各コミットを完了させる {#complete-each-commit}

コミットのカバレッジ情報は、しばしば複数のジョブ（例：シャードごと）から得られます。Tuistは最後のジョブが報告を終えたタイミングを自動検出できないため、明示的に通知する必要があります。コミットに対するすべてのテストジョブが終了したら、それらすべてに依存するジョブで以下を実行します：

```sh
./gradlew tuistCoverageComplete
```

単一のジョブでコミットのすべてのテストを実行する場合は、テスト失敗時も含め、テスト実行後のステップとしてこのタスクを実行してください。テストが失敗した実行でも、カバレッジは報告されます。

このタスクは `GIT_COMMIT` またはチェックアウトの `HEAD` からコミットを読み取ります。別のコミットを指定するには `-Ptuist.coverage.commit=<sha>` を渡してください。コミットが完了するまで、そのカバレッジは **進行中** と表示され、ブランチのトレンドには含まれません。

## 仕組み {#how-it-works}

### Tuistが測定するもの {#what-tuist-measures}

- **プロジェクト。** 各Gradleプロジェクトはダッシュボード上のモジュールとして扱われ、それぞれ独自のカバレッジを持ちます。
- **プロダクトコードのみ。** テストソースセットからコンパイルされたクラスはテストコードです。Tuistはこれらを保存しますが、すべての数値計算からは除外します。
- **リポジトリ内のファイル。** クラスは、リポジトリ内のパスに基づき、コンパイル元のソースファイルに対応します。生成されたソースやGitが無視するファイルは報告されません。
- **各行の実行有無。** JaCoCoはコードが実行されたかどうかを記録し、実行回数は記録しません。そのため、ダッシュボード上の実行回数は0または1になります。

### 各テストが実行したコード {#per-test-evidence}

JUnit Platform（JUnit 5、またはJUnit Vintageを介したJUnit 4）上で実行されるテストの場合、プラグインは各テストが実行したコードと、`@BeforeAll` などテスト外の部分で各テストクラスが実行した内容も記録します。これにより、Tuistは実行から除外されたテストのカバレッジを以前のデータから引き継ぐことができます（[スキップされたテスト](#skipped-tests)を参照）。テスト側に追加の設定は不要です。

これは、各テストJVMが一度に1つのテストを実行する場合に機能します。JUnitの並列実行を有効にしない限り、Gradleはこの方法でテストを実行します。`maxParallelForks` を使用して複数のJVMでテストクラスを実行しても問題ありません。1つのJVM内で同時に実行されるテストもカバレッジには計上されますが、個別には識別されません。

### ビルドキャッシュ {#build-cache}

ビルドキャッシュから復元されたテストタスク、または最新の状態にあるテストタスクは、テストを実行しません。しかし、そのカバレッジは依然としてアップロードされます。JaCoCoのデータはタスクの出力の一つであり、同じ入力に対してテストを実行した実行によって記録されるためです。

### スキップされたテスト {#skipped-tests}

実行からテストが除外された場合、Tuistは実行されたコードに変更がない限り、以前の実行からカバレッジ情報を補完します。補完できない場合、コミットのカバレッジは **不完全** となります。実行から除外されるパターン：

- **プロジェクトのテストタスクが除外された場合**（`-x :app:test` を使用）。これらのテストは、コードに変更がない最後の実行からのデータが引き継がれます。
- **一部のプロジェクトのテスト**（`./gradlew :core:test` を使用）、または **一部のテスト**（`--tests` を使用）。この実行は指定されたもののみをカバーするため、コミットの他の実行で全てが実行されない限り、コミットは不完全となります。
- **最初の失敗で停止したテストタスク**（`failFast`）。

意図的に除外され、コミットを不完全にしないテストもあります：

- **ビルドスクリプト内のフィルタ**（例：`filter { excludeTestsMatching(...) }`）。これはスイートが実行するテストを定義します。
- **ビルドスクリプトで無効にしたテストタスク**（`enabled = false` またはそれらをスキップする `onlyIf` を使用）。
- **<.localized_link href="/guides/features/test-insights/flaky-tests/gradle">検疫</.localized_link>によってスキップされたテスト。** これらは削除されたものとして扱われるため、これらのテストのみがカバーしていた行は未カバーとして計上されます。
- **他のシャードのテスト**（[テストをシャード化](#sharded-runs)している場合）。

### 完全なコミットと不完全なコミット {#commit-status}

| ステータス | 意味 |
| --- | --- |
| 進行中 | 実行からカバレッジが報告されていますが、`tuistCoverageComplete` がこのコミットに対してまだ実行されていません。 |
| 完了 | コミットの実行に含まれるすべてのテストが実行されたか、引き継がれたか、意図的に除外されました。 |
| 不完全 | 一部のカバレッジを特定できなかったため、数値は下限となります。 |
| 未測定 | このコミットに対してカバレッジを報告した実行がありません。 |

ブランチのトレンドには、完了したコミットのみが含まれます。

## パフォーマンスへの影響 {#performance-impact}

JaCoCoはテストJVMがクラスをロードする際にインストルメントするため、コンパイル済みクラスおよびコンパイルタスクのビルドキャッシュエントリは、カバレッジの有無にかかわらず同じままです。SBOMジェネレータなど、すべての依存関係設定を読み取るタスクもJaCoCoエージェントの影響を受けるため、カバレッジを有効にすると出力が変化します。テストの実行速度はわずかに低下し、プラグインはテストタスクの完了後にJaCoCoのデータを読み取ります。カバレッジ有効時と無効時のテストタスクは別々のビルドキャッシュエントリを持つため、カバレッジ無効時の結果がキャッシュされていても、カバレッジ有効での初回実行ではテストが実行されます。

## 制限事項 {#limitations}

- **分離プロジェクトとオンデマンド設定。** これらのビルドはすべてのプロジェクトを設定しないため、プラグインは実行からどのプロジェクトのテストが除外されたかを判別できず、一部のプロジェクトのテストのみを実行した場合でも完了として扱われます。
- **フォークからのプルリクエストからはカバレッジを取得できません。** カバレッジはTuistで認証された実行によってのみアップロードされ、CIは通常、フォークから開かれたプルリクエストに対してシークレットやIDトークンを提供しません。

## カバレッジのクエリ {#querying}

ダッシュボードの **コードカバレッジ** ページには、各コミットの数値、モジュール、ファイル、および各実行がカバーした行が表示されます。同じデータは、<.localized_link href="/guides/features/agentic-coding/mcp">Model Context Protocolサーバー</.localized_link> を介してエージェントからも利用可能です。
