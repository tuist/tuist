# Gradle の不安定なテスト {#gradle-flaky-tests}

不安定なテストとは、同じコードで複数回実行したときに結果（合格または不合格）が異なるテストです。これらはテストスイートへの信頼を損ない、誤った失敗の調査に開発者の時間を浪費させます。Tuist は不安定なテストを自動検出し、経時的な追跡をサポートします。

![不安定なテスト ページ](/images/guides/features/test-insights/flaky-tests-page.png)

## 不安定さの検出仕組み {#how-it-works}

Tuist は次の 2 つの方法で不安定なテストを検出します。

### テスト再試行 {#test-retries}

再試行機能を使ってテストを実行すると、Tuist は各試行の結果を分析します。一部の試行で失敗し、他の試行で合格するテストは不安定としてマークされます。

[Test Retry プラグイン](https://github.com/gradle/test-retry-gradle-plugin) や同様の仕組みを使って失敗したテストを再実行できます。Tuist は、一部の試行で合格し他の試行で失敗するテストを検出します。

プラグインを `build.gradle.kts` に追加します。

```kotlin
plugins {
    id("org.gradle.test-retry") version "1.6.2"
}

tasks.test {
    retry {
        maxRetries = 3
        maxFailures = 5
        failOnPassedAfterRetry = false
    }
}
```

![不安定なテストケースの詳細](/images/guides/features/test-insights/flaky-test-case-detail.png)

### クロス実行検出 {#cross-run-detection}

テスト再試行を使わなくても、Tuist は同じコミットと同じ Gradle プロジェクトに対する異なる CI 実行間で結果を比較することで不安定なテストを検出できます。ある CI 実行では合格し、同じコミットとプロジェクトの別の実行では失敗する場合、両方の実行が不安定としてマークされます。

Gradle プロジェクトは比較キーの一部です。同じテストでもプロジェクトによって決定的に異なる振る舞いをする可能性があるためです。たとえば、異なる依存関係でコンパイルされた共有テストクラスや、異なるモジュールフィクスチャで実行される場合などです。異なる Gradle プロジェクト上で同じコミットの 2 回の実行は別の実行バリアントとして扱われ、互いを不安定としてフラグ付けしません。

これは、再試行で捕捉できるほど一貫して失敗しないものの、依然として断続的な CI 失敗を引き起こす不安定なテストを捕捉するのに特に役立ちます。

## 不安定なテストの管理 {#managing-flaky-tests}

### 自動クリア

検出とクリアはプロジェクト上の **自動化アラート** を介して実行されます。すべてのプロジェクトにはデフォルトの「不安定なテスト検出」自動化が用意されており、その *トリガー* がテストを不安定としてマークし、*リカバリー* が、設定されたリカバリー期間（デフォルト **14 日**）中に再トリガーされずに経過するとフラグを解除します。**Settings → Automations** で編集して、リカバリー期間を変更したり、リカバリーアクションを入れ替えたり（例: 隔離も解除）、リカバリーを完全に無効にして手動でクリアするまでテストが不安定としてマークされたままになるように設定できます。

### 手動管理

テストケースの詳細ページから、テストを手動で不安定としてマークしたり、そのマークを解除したりすることもできます。これは以下のような場合に便利です。
- 修正作業中に既知の不安定なテストを認識しておきたい場合
- インフラの問題によりテストが誤ってフラグ付けされた場合

## 不安定なテストの隔離 {#quarantining}

隔離は、修正中に CI をブロックしないよう不安定なテストを分離します。デフォルトでは **手動アクション** です。ダッシュボードのテストケース詳細ページから隔離・隔離解除・モード切り替えを行いますが、**Settings → Automations** 下の **自動化アラート** に組み込んで、不安定さが閾値を超えたときに自動でミュート（またはスキップ）し、回復したら隔離を解除することもできます。手動か自動かを問わず、すべての遷移はテストケースの監査ログに記録されます。

隔離されたテストは次の 2 つのモードのいずれかになります。

- **ミュート**: テストは引き続き実行されますが、プラグインが `ignoreFailures = true` を設定し、隔離されていない失敗のみでビルドを再失敗させます。失敗は依然として不安定テスト検出器に供給されるため、ビルドを壊さずにテストを監視し続けられます。積極的に調査中のテストに選択してください。
- **スキップ**: プラグインが Gradle の `excludeTestsMatching` を介してテストを除外するため、テストは開始されません。新しい結果は生成されず、再度有効にするまで不安定テストダッシュボードから外れます。テストが壊れている、遅い、またはあまりにも持続的に不安定で実行することが CI 時間の無駄である場合に選択してください。

### 隔離されたテストが合格として表示される理由 {#quarantined-passing}

- **ミュートされたテスト** は引き続き実行されます。失敗したミュートテストはテストケース実行上で **failed** として記録され、不安定としてフラグ付けされます。テストごとのステータスは書き換えられません。上書きされるのは **全体のテスト実行** です。実行内のすべての失敗テストケースがミュートされている場合、実行全体は合格として報告されるため、ミュートされた失敗は CI を壊しません。
- **スキップされたテスト** はまったく実行されないため、ダッシュボードにはテストの最後の実際の実行からのステータスが表示され続けます。そのスナップショットは数週間前のものかもしれません。

### 隔離の有効化 {#enabling-quarantine}

隔離は **CI で自動有効**（`CI` 環境変数が設定されている場合）になり、ローカルビルドでは無効になります。プラグインは各テストタスクの前に Tuist サーバーから隔離されたテストのリストを取得します。ミュートされたテストは通常通り実行され、その失敗はマスクされます。スキップされたテストは除外されます。

これを `settings.gradle.kts` で明示的に制御できます。

```kotlin
tuist {
    testQuarantine {
        enabled = true  // or false to disable
    }
}
```

`enabled` が設定されていない場合、デフォルトは自動検出です。CI では有効、ローカルでは無効になります。

## 新しいテストのストレステスト {#stress-testing-new-tests}

ストレスゲートは、ブランチが追加したテストケースをそれぞれ新しいプロセスで複数回再実行し、不安定になったものを報告します。導入したプルリクエスト上で新しい不安定なテストを確認でき、数週間後ではありません。

テストケースは、プロジェクトのデフォルトブランチで過去 90 日間に CI で実行されていない場合、またはそれ以降にそのブランチにマージされたコミットで実行されていない場合に新規とみなされます。マージキューがある場合、キューが実行したテストケースはキューのコミットがマージされると既知となり、キューがそれを削除した場合は新規のままとなります。コミットは、Tuist が CI で収集する <.localized_link href="/guides/features/test-insights/gradle#git-history">Git ヒストリー</.localized_link> を通じて照合されます。

### 有効化

ゲートはデフォルトでオフです。モードを設定します。

- **`report`**: 各不安定なテストケースについて警告します。実行は自身の結果に基づいて終了します。
- **`enforce`**: 不安定なテストケースは実行を失敗させ、失敗したテストと同じ終了コードになります。

数週間 `report` から始めて、`enforce` が何をブロックしていたかを確認してください。

`settings.gradle.kts` で宣言するか、`TUIST_TEST_STRESS_NEW_TESTS` を設定して CI レーンごとにモードを変更します。

```kotlin
tuist {
    stressNewTests {
        mode = "report" // or "enforce"
    }
}
```

隔離とは異なり、このゲートには CI を認識するデフォルト値がありません。`mode` が設定されていない場合、どこでも実行されません。

### 各テストの再実行回数

最初のパスでのテストケースの実行時間によって異なります。

| 最初のパス | 再実行 |
| --- | --- |
| 最大 5 秒 | 10 |
| 最大 10 秒 | 5 |
| 最大 30 秒 | 3 |
| 最大 5 分 | 2 |
| 5 分超 | 再実行なし |

各再実行はその 1 つのテストケースにフィルタリングされたネストされた Gradle ビルドであるため、すべての再実行で新しいテスト JVM が使用されます。このパスは、200 テストケースまたは 10 分のいずれかに先に達した時点で停止し、どの制限に達したかを報告します。

### ゲートが実行されない場合

- 最初のパスですでに失敗しています。まずそれらのテストを修正してください。
- プロジェクトにデフォルトブランチがないか、そのブランチで CI がまだ何も実行されていません。
- プロジェクトのテストケースの 30% 以上が新規のように見えます。これほど多くを再実行するのはコストに見合いません。Tuist へのレポートを始めたばかりのプロジェクトや、一度に多くのテストを移動させるリネーム後のプロジェクトでは、これが予想されます。

## Slack 通知 {#slack-notifications}

Slack 統合で <.localized_link href="/guides/integrations/slack#flaky-test-alerts">不安定なテストのアラート</.localized_link> を設定すると、テストが不安定になった瞬間に通知を受け取れます。

## 不安定および隔離状態のクエリ {#querying}

### CLI

`tuist test case` コマンドツリーは、Tuist がテストケースについて追跡するすべてを公開します。

```sh
tuist test case list --flaky                       # only flaky test cases
tuist test case list --quarantined                 # only muted or skipped test cases
tuist test case show <test_case_id>                # detail: flakiness rate, last status, run counts
tuist test case events <test_case_id>              # audit log: marked_flaky, muted, skipped, ...
tuist test case run list <test_case_id>            # run history with status and duration
tuist test case run show <test_case_run_id>        # single run, including failure breakdown
```

これらはすべてスクリプト用に `--json` を受け入れます。

### REST API

同じデータは HTTP 経由でも利用できます。ルート、フィルター、レスポンスフィールドの完全なリストについては、API リファレンスの [テストケースのエンドポイント](https://tuist.dev/api/docs#tag/test-cases) を参照してください。テストケースの状態（不安定のマーク/解除、ミュート、スキップ）を変更するには、`is_flaky` または `state` を指定して `PATCH /api/projects/{account_handle}/{project_handle}/tests/test-cases/{test_case_id}` を送信します。同じ変更は `tuist test case update` および `update_test_case` Model Context Protocol ツールとしても利用できます。
