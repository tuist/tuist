# Xcodeの不安定なテスト {#xcode-flaky-tests}

> [!WARNING]
> **要件**
>
> - <.localized_link href="/guides/features/test-insights/xcode"></.localized_link>が設定されていること。Tuistは、各テスト実行でアップロードされるテストインサイトイベントから不安定なテストを検出します。

不安定なテストとは、同じコードで複数回実行したときに異なる結果（合格または不合格）を返すテストです。これらはテストスイートへの信頼を損ない、誤った失敗の原因調査に開発者の時間を浪費させます。Tuistは不安定なテストを自動的に検出し、経時的な追跡をサポートします。

![不安定なテストページ](/images/guides/features/test-insights/flaky-tests-page.png)

## 不安定さの検出仕組み {#how-it-works}

Tuistは次の2つの方法で不安定なテストを検出します。

### テストの再試行 {#test-retries}

再試行機能を使ってテストを実行すると、Tuistは各試行の結果を分析します。一部の試行で失敗し、他の試行で成功した場合、そのテストは不安定としてマークされます。

`-retry-tests-on-failure`または`-test-iterations`を`tuist xcodebuild test`経由で渡します。

```sh
tuist xcodebuild test \
  -scheme MyScheme \
  -retry-tests-on-failure \
  -test-iterations 3
```

![不安定なテストケースの詳細](/images/guides/features/test-insights/flaky-test-case-detail.png)

### クロスラン検出 {#cross-run-detection}

テストの再試行を行わなくても、Tuistは同じコミット、スキーム、報告されたデスティネーション（デバイス名、プラットフォーム、OSバージョン）における異なるCI実行間の結果を比較することで、不安定なテストを検出できます。一致するCI実行の片方で合格し、もう片方で失敗した場合、失敗した実行は不安定としてマークされます。これは、どちらの結果が先に到着するかに関係なく動作します。

同じテストでも、スキームやデスティネーションによって一貫して異なる動作をする場合があります。たとえば、iOS 26で合格し、iOS 27で失敗しても、それは不安定さを意味しません。異なるスキーム、デバイス、プラットフォーム、またはOSバージョンからの結果は、互いを不安定としてフラグ付けしません。

帰属可能なデスティネーションを持たない結果は、既知のデスティネーションを持つ結果とは別に、他の帰属不能な結果と比較されます。これには、デスティネーションメタデータが欠落または不完全なレポートや、複数の異なるデスティネーションを含むレポートが含まれます。個々のテスト結果をまだデスティネーションに帰属できないためです。このグループ内の環境間の差異は、依然として誤った不安定分類を生む可能性があります。再試行ベースの検出は引き続き適用されます。既存の過去の不安定分類は変更されません。

これは、再試行で捕捉できるほど一貫して失敗しないものの、依然として断続的なCI失敗を引き起こす不安定なテストを検出するのに特に役立ちます。

## 不安定なテストの管理 {#managing-flaky-tests}

### 自動クリア

検出とクリアは、プロジェクト上の**自動化アラート**を通じて実行されます。すべてのプロジェクトには、デフォルトの「不安定なテスト検出」自動化が付与されます。この自動化の*トリガー*はテストを不安定としてマークし、*リカバリー*は、テストが構成されたリカバリーウィンドウ（デフォルト**14日間**）を再トリガーなしで経過した際にフラグを解除します。**設定 → 自動化**で編集し、リカバリーウィンドウを変更したり、リカバリーアクション（例：隔離解除も行う）を入れ替えたり、リカバリーを完全に無効にして、手動でクリアするまでテストが不安定としてマークされたままになるように設定できます。

### 手動管理

テストケース詳細ページから、テストを手動で不安定としてマークしたり、そのマークを外したりすることもできます。これは以下の場合に便利です。
- 修正作業中に既知の不安定なテストであることを認めたい場合
- インフラストラクチャの問題により、テストが誤ってフラグ付けされた場合

## 不安定なテストの隔離 {#quarantining}

隔離は、不安定なテストを分離し、修正中にCIをブロックしないようにします。デフォルトでは**手動アクション**です。ダッシュボードのテストケース詳細ページから隔離、隔離解除、モードの切り替えを行います。ただし、**設定 → 自動化**下の**自動化アラート**に組み込むこともでき、不安定さが閾値を超えたときにテストを自動的にミュート（またはスキップ）し、回復時に隔離解除できます。手動および自動化のすべての遷移は、テストケースの監査ログに記録されます。

デフォルトでは、リカバリーはトリガー条件が成立しなくなるまで待機するため、テストは古い不安定な実行がトリガーウィンドウから外れるまで隔離されたままになります。より早く回復させるには、**回復条件**を**新しい不安定な実行なし**に設定します。これにより、新しい不安定な実行なしでリカバリーウィンドウ（日数または実行回数）が経過するとテストは回復し、新しい不安定な実行が発生するたびにその待機が再開され、回復後は新しい不安定な実行のみが再び隔離を引き起こします。

隔離されたテストは、次の2つのモードのいずれかになります。

- **ミュート**: テストは引き続き実行されますが、`tuist xcodebuild test`が失敗をマスクします。失敗は依然として不安定テスト検出器に供給されるため、ビルドを壊さずにテストを監視し続けることができます。積極的に調査中のテストにこのモードを選択してください。
- **スキップ**: xcodebuildは`-skip-testing <identifier>`を受け取るため、テストは決して開始されません。新しい結果は生成されず、再度有効にするまで不安定テストダッシュボードから除外されます。テストが壊れている、遅い、またはあまりにも持続的に不安定で実行することがCI時間の無駄である場合にこのモードを選択してください。

### 隔離されたテストが合格として表示される理由 {#quarantined-passing}

- **ミュートされたテスト**は依然として実行されます。失敗したミュートテストは、テストケース実行上で**失敗**として記録され、不安定としてフラグ付けされます。テストごとのステータスは書き換えられません。上書きされるのは**全体のテスト実行**です。実行内のすべての失敗テストケースがミュートされている場合、実行全体は合格として報告されるため、ミュートされた失敗はCIを中断しません。
- **スキップされたテスト**はまったく実行されないため、ダッシュボードにはテストの最後の実際の実行からのステータスが表示され続けます。そのスナップショットは数週間前のものかもしれません。

### テストの実行 {#running-tests}

`tuist xcodebuild test`は両方のモードを自動的に尊重するパススルーラッパーです。xcodebuildを呼び出すのと同じ方法で使用します。

```sh
tuist xcodebuild test -scheme MyScheme
```

スキップされたテストは、xcodebuild呼び出しに`-skip-testing <identifier>`として追加され、決して開始されません。ミュートされたテストは通常通り実行され、失敗した場合、その失敗は結果のビルドステータスでマスクされます。

#### 隔離のバイパス

`tuist xcodebuild test`は`--skip-quarantine`を受け入れ、ミュートおよびスキップされたテストを含め、すべてを実行します。

```sh
tuist xcodebuild test --skip-quarantine -scheme MyScheme
```

#### xcodebuildを直接呼び出す

`tuist xcodebuild test`を経由できない場合は、`tuist test case list`を使用して、隔離されたテストを自分で`-skip-testing`引数に展開します。

```sh
xcodebuild test \
  -scheme MyScheme \
  $(tuist test case list --quarantined --skip-testing)
```

これは`tuist xcodebuild test`以外での安全なデフォルトです。ミュートされたテストの失敗マスキングはそのコマンドを経由した場合のみ発生するため、両方のモードをスキップすることで偽のCI失敗を回避できます。より細かな制御が必要な場合は、代わりに`tuist xcodebuild test`を経由してください。

## 新しいテストのストレステスト {#stress-testing-new-tests}

ストレスゲートは、ブランチが追加したテストケースをそれぞれ新しいプロセスで複数回再実行し、不安定になったものを報告します。数週間後ではなく、それを導入したプルリクエスト上で新しい不安定なテストを確認できます。

テストケースは、プロジェクトのデフォルトブランチまたはそれにマージされたコミット上で過去90日間CIで実行されていない場合に新規とみなされます。マージキューを使用している場合、キューが実行したテストケースはキューのコミットがマージされると認識され、キューがそれを削除した場合は新規のままとなります。コミットは、TuistがCIで収集する<.localized_link href="/guides/features/test-insights/xcode#git-history">Git履歴</.localized_link>を通じて照合されます。

### 有効化

ゲートはデフォルトでオフです。モードを設定してください：

- **`report`**：各不安定なテストケースについて警告します。実行は依然としてその結果に基づいて終了します。
- **`enforce`**：不安定なテストケースは実行を失敗させ、失敗したテストと同じ終了コードを返します。

`report`を数週間使用して、`enforce`が何をブロックしていたかを確認することから始めてください。

パススルー引数の前に渡すか、`TUIST_TEST_STRESS_NEW_TESTS`を設定してCIレーンごとにモードを変更します：

```sh
tuist xcodebuild test --stress-new-tests report -scheme MyScheme
```

### 各テストの再実行回数

最初のパスでテストケースにかかった時間によって異なります：

| 最初のパス | 再実行 |
| --- | --- |
| 最大5秒 | 10 |
| 最大10秒 | 5 |
| 最大30秒 | 3 |
| 最大5分 | 2 |
| 5分以上 | 再実行なし |

再実行は最初のパスでビルドされたものを利用します。パスは200テストケースまたは10分に達すると停止し、どちらの制限に達したかを報告します。

### ゲートが実行されない場合

- 最初のパスがすでに失敗しています。まずそれらのテストを修正してください。
- プロジェクトにデフォルトブランチがないか、まだCIで何も実行されていません。
- プロジェクトのテストケースの30%以上が新規のように見えます。それほど多くを再実行するのは手間に見合いません。これは、Tuistへのレポートを始めたばかりのプロジェクトや、一度に多くのテストを移動させる名前変更後のプロジェクトで予想されます。

## Slack通知 {#slack-notifications}

Slack統合で<.localized_link href="/guides/integrations/slack#flaky-test-alerts">不安定なテストのアラート</.localized_link>を設定することで、テストが不安定になった瞬間に通知を受け取れます。

## 不安定および隔離状態のクエリ {#querying}

### CLI

`tuist test case`コマンドツリーは、Tuistがテストケースについて追跡するすべてを公開します：

```sh
tuist test case list --flaky                       # only flaky test cases
tuist test case list --quarantined                 # only muted or skipped test cases
tuist test case show <test_case_id>                # detail: flakiness rate, last status, run counts
tuist test case events <test_case_id>              # audit log: marked_flaky, muted, skipped, ...
tuist test case run list <test_case_id>            # run history with status and duration
tuist test case run show <test_case_run_id>        # single run, including failure breakdown
```

これらすべてはスクリプト用に`--json`を受け入れます。

### REST API

同じデータはHTTP経由でも利用可能です。ルート、フィルター、レスポンスフィールドの完全なリストについては、APIリファレンスの[テストケースエンドポイント](https://tuist.dev/api/docs#tag/test-cases)を参照してください。テストケースの状態（不安定のマーク/解除、ミュート、スキップ）を変更するには、`is_flaky`または`state`を使用して`PATCH /api/projects/{account_handle}/{project_handle}/tests/test-cases/{test_case_id}`を送信します。同じ変更は`tuist test case update`および`update_test_case` Model Context Protocolツールとしても利用可能です。
