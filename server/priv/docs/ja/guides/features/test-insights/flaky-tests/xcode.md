# Xcode の不安定なテスト {#xcode-flaky-tests}

> [!WARNING]
> **要件**
>
> - <.localized_link href="/guides/features/test-insights/xcode">Xcode テストインサイト</.localized_link> が構成されていること。Tuist は、各テスト実行によってアップロードされるテストインサイトイベントから不安定なテストを検出します。

不安定なテストとは、同じコードで複数回実行した際に異なる結果（成功または失敗）を生み出すテストのことです。これらはテストスイートへの信頼を損ない、誤った失敗の調査に開発者の時間を浪費させます。Tuist は不安定なテストを自動的に検出し、経時的に追跡することを支援します。

![不安定なテストページ](/images/guides/features/test-insights/flaky-tests-page.png)

## 不安定な検出の仕組み {#how-it-works}

Tuist は以下の2つの方法で不安定なテストを検出します：

### テスト再試行 {#test-retries}

再試行機能を使用してテストを実行すると、Tuist は各試行の結果を分析します。ある試行では失敗し、別の試行では成功するテストは、不安定としてマークされます。

`-retry-tests-on-failure` または `-test-iterations` を `tuist xcodebuild test` に渡してください：

```sh
tuist xcodebuild test \
  -scheme MyScheme \
  -retry-tests-on-failure \
  -test-iterations 3
```

![不安定なテストケースの詳細](/images/guides/features/test-insights/flaky-test-case-detail.png)

### クロスラン検出 {#cross-run-detection}

テストの再試行がなくても、Tuist は同じコミット、スキーム、および報告されたデスティネーション（デバイス名、プラットフォーム、OSバージョン）における異なるCI実行間の結果を比較することで、不安定なテストを検出できます。一致するCI実行の1つでテストが成功し、別の実行で失敗した場合、失敗した実行は不安定としてマークされます。これは、どちらの結果が先に到着するかに関係なく動作します。

同じテストでも、スキームやデスティネーションによって一貫して異なる動作をする場合があります。例えば、iOS 26で成功しiOS 27で失敗しても、それは不安定性を示すものではありません。異なるスキーム、デバイス、プラットフォーム、またはOSバージョンからの結果は、互いに不安定としてフラグを立てません。

帰属可能なデスティネーションがない結果は、既知のデスティネーションを持つ結果とは別に、他の帰属されていない結果と比較されます。これには、デスティネーションメタデータが欠落または不完全なレポートや、複数の異なるデスティネーションを含むレポートが含まれます。個々のテスト結果をまだデスティネーションに帰属できないためです。このグループ内の環境間の違いは、依然として誤った不安定分類を生み出す可能性があります。再試行ベースの検出は引き続き適用されます。既存の履歴的な不安定分類は変更されません。

これは、再試行で捕捉できるほど一貫して失敗しないものの、依然として断続的なCI障害を引き起こす不安定なテストを捕捉するのに特に役立ちます。

## 不安定なテストの管理 {#managing-flaky-tests}

### 自動クリア

検出とクリアは、プロジェクト上の **自動化アラート** を介して実行されます。すべてのプロジェクトには、デフォルトの「不安定なテスト検出」自動化が付与されており、その *トリガー* がテストを不安定としてマークし、*リカバリー* が、テストが構成されたリカバリー期間（デフォルト **14日間**）中に再トリガーされずに経過するとフラグをクリアします。**設定 → 自動化** で編集して、リカバリー期間を変更したり、リカバリーアクションを入れ替えたり（例：隔離解除も行う）、リカバリーを完全に無効にして、手動でクリアするまでテストが不安定としてマークされたままになるようにすることができます。

### 手動管理

テストケースの詳細ページから、テストを手動で不安定としてマークしたり、マークを解除したりすることもできます。これは以下の場合に役立ちます：
- 修正作業中に既知の不安定なテストを確認したい場合
- インフラストラクチャの問題によりテストが誤ってフラグ付けされた場合

## 不安定なテストの隔離 {#quarantining}

隔離は、不安定なテストを分離し、修正中にCIをブロックしないようにします。デフォルトでは **手動アクション** です — ダッシュボードのテストケース詳細ページから隔離、隔離解除、モードの切り替えを行います — が、**設定 → 自動化** の下の **自動化アラート** に組み込むこともでき、不安定性の閾値を超えたときにテストが自動的にミュート（またはスキップ）され、回復すると隔離解除されます。手動か自動かを問わず、すべての遷移はテストケースの監査ログに記録されます。

隔離されたテストは、以下の2つのモードのいずれかになります：

- **ミュート**：テストは引き続き実行されますが、`tuist xcodebuild test` が失敗をマスクします。失敗は依然として不安定テスト検出器に供給されるため、ビルドを壊さずにテストを監視し続けることができます。積極的に調査中のテストにこれを選択してください。
- **スキップ**：xcodebuild は `-skip-testing <identifier>` を受け取るため、テストは決して開始されません。新しい結果は生成されず、再度有効にするまで不安定テストダッシュボードから除外されます。テストが壊れている、遅い、またはあまりにも持続的に不安定で実行することが単にCI時間の無駄である場合にこれを選択してください。

### 隔離されたテストが成功として表示される理由 {#quarantined-passing}

- **ミュートされたテスト** は依然として実行されます。失敗したミュートされたテストは、テストケース実行上で **失敗** として記録され、不安定としてフラグ付けされます — テストごとのステータスは書き換えられません。上書きされるのは **全体のテスト実行** です：実行内のすべての失敗したテストケースがミュートされている場合、実行全体は成功として報告されるため、ミュートされた失敗はCIを壊しません。
- **スキップされたテスト** はまったく実行されないため、ダッシュボードはテストの最後の実際の実行からのステータスを表示し続けます — そのスナップショットは数週間前のものである可能性があります。

### テストの実行 {#running-tests}

`tuist xcodebuild test` は、両方のモードを自動的に尊重するパススルーラッパーです。xcodebuild を呼び出すのと同じ方法で使用してください：

```sh
tuist xcodebuild test -scheme MyScheme
```

スキップされたテストは、xcodebuild 呼び出しに `-skip-testing <identifier>` として追加され、決して開始されません。ミュートされたテストは通常通り実行されます。失敗した場合、その失敗は結果のビルドステータスでマスクされます。

#### 隔離のバイパス

`tuist xcodebuild test` は `--skip-quarantine` を受け入れ、ミュートおよびスキップされたテストを含め、すべてを実行します：

```sh
tuist xcodebuild test --skip-quarantine -scheme MyScheme
```

#### xcodebuild を直接呼び出す

`tuist xcodebuild test` を経由できない場合は、`tuist test case list` を使用して、隔離されたテストを自分で `-skip-testing` 引数に展開してください：

```sh
xcodebuild test \
  -scheme MyScheme \
  $(tuist test case list --quarantined --skip-testing)
```

これは `tuist xcodebuild test` の外部での安全なデフォルトです：ミュートされたテストの失敗マスキングは、そのコマンドを経由した場合のみ発生するため、両方のモードをスキップすることで虚偽のCI障害を回避します。より細かい制御が必要な場合は、代わりに `tuist xcodebuild test` を経由してください。

## 新しいテストのストレステスト {#stress-testing-new-tests}

ストレステストゲートは、ブランチが追加したテストケースをそれぞれ新しいプロセスで複数回再実行し、不安定であることが判明したものを報告します。数週間後ではなく、それを導入したプルリクエスト上で新しい不安定なテストを確認できます。

プロジェクトのデフォルトブランチで過去90日間CIで実行されていない場合、またはそれ以降にマージされたコミット上で実行されていない場合、そのテストケースは新規とみなされます。マージキューを使用している場合、キューが実行したテストケースは、キューのコミットがマージされると認識され、キューがそれを削除した場合でも新規のままとなります。コミットは、TuistがCI上で収集する<.localized_link href="/guides/features/test-insights/xcode#git-history">Git履歴</.localized_link>を通じて照合されます。

### 有効にする

ゲートはデフォルトでオフになっています。モードを設定してください：

- **`report`**：各不安定なテストケースについて警告します。実行は依然として自身の結果に基づいて終了します。
- **`enforce`**：不安定なテストケースは実行を失敗させ、失敗したテストと同じ終了コードを返します。

`report` を数週間使用して、`enforce` が何をブロックしていたかを確認することから始めてください。

パススルー引数の前に渡すか、`TUIST_TEST_STRESS_NEW_TESTS` を設定してCIレーンごとにモードを変更します：

```sh
tuist xcodebuild test --stress-new-tests report -scheme MyScheme
```

### 各テストの再実行回数

最初のパスでのテストケースの実行時間によって異なります：

| 最初のパス | 再実行 |
| --- | --- |
| 5秒以内 | 10 |
| 10秒以内 | 5 |
| 30秒以内 | 3 |
| 5分以内 | 2 |
| 5分超 | 再実行なし |

再実行は最初のパスでビルドされたものを利用します。パスは200テストケースまたは10分のいずれか先に到達した時点で停止し、どの制限に達したかを報告します。

### ゲートが実行されない場合

- 最初のパスがすでに失敗しています。まずそれらのテストを修正してください。
- プロジェクトにデフォルトブランチがないか、そのブランチでまだCIが何も実行されていません。
- プロジェクトのテストケースの30%以上が新規に見えます。これほど多くを再実行するのはコストに見合いません。これは、Tuistへのレポートを始めたばかりのプロジェクトや、一度に多くのテストを移動させる名前変更の後などに発生することが予想されます。

Slack統合で<.localized_link href="/guides/integrations/slack#flaky-test-alerts">不安定なテストのアラート</.localized_link>を設定することで、テストが不安定になった際に即座に通知を受け取れます。

## 不安定および隔離状態のクエリ {#querying}

### CLI

`tuist test case` コマンドツリーは、Tuistがテストケースについて追跡するすべての情報を公開します：

```sh
tuist test case list --flaky                       # only flaky test cases
tuist test case list --quarantined                 # only muted or skipped test cases
tuist test case show <test_case_id>                # detail: flakiness rate, last status, run counts
tuist test case events <test_case_id>              # audit log: marked_flaky, muted, skipped, ...
tuist test case run list <test_case_id>            # run history with status and duration
tuist test case run show <test_case_run_id>        # single run, including failure breakdown
```

これらすべてはスクリプト用に `--json` を受け入れます。

### REST API

同じデータはHTTP経由でも利用可能です — ルート、フィルター、レスポンスフィールドの完全なリストについては、APIリファレンスの[テストケースエンドポイント](https://tuist.dev/api/docs#tag/test-cases)を参照してください。テストケースの状態（不安定のマーク/解除、ミュート、スキップ）を変更するには、`is_flaky` または `state` を含めて `PATCH /api/projects/{account_handle}/{project_handle}/tests/test-cases/{test_case_id}` を送信してください。同じ変更は `tuist test case update` としても、また `update_test_case` Model Context Protocolツールとしても利用可能です。
