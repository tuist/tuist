# 生成されたXcodeプロジェクト {#generated-xcode-project-flaky-tests}

> [!WARNING]
> **要件**
>
> - <.localized_link href="/guides/features/test-insights/xcode">Xcodeテストインサイト</.localized_link> が構成されていること（自動生成されたスキームには `tuist inspect test` ポストアクションが含まれています。カスタムスキームではこれを追加する必要があります）。

不安定なテストとは、同じコードで複数回実行したときに異なる結果（合格または不合格）を返すテストのことです。これらはテストスイートへの信頼を損ない、誤った失敗の調査に開発者の時間を浪費させます。Tuistは不安定なテストを自動的に検出し、経時的な追跡を支援します。

![不安定なテストのページ](/images/guides/features/test-insights/flaky-tests-page.png)

## 不安定な検出の仕組み {#how-it-works}

Tuistは以下の2つの方法で不安定なテストを検出します。

### テストの再試行 {#test-retries}

再試行機能を使用してテストを実行すると、Tuistは各試行の結果を分析します。一部の試行で失敗し、他の試行で合格した場合、そのテストは不安定としてマークされます。

`tuist test` を介して `-retry-tests-on-failure` または `-test-iterations` を渡します。

```sh
tuist test --scheme MyScheme -- -retry-tests-on-failure -test-iterations 3
```

![不安定なテストケースの詳細](/images/guides/features/test-insights/flaky-test-case-detail.png)

### クロスラン検出 {#cross-run-detection}

テストの再試行を行わなくても、Tuistは同じコミットと同じスキームに対する異なるCI実行の結果を比較することで、不安定なテストを検出できます。あるCI実行でテストが合格し、同じコミットとスキームの別の実行で失敗した場合、両方の実行が不安定としてマークされます。

同じテストでもスキームによって決定的に異なる動作をする可能性があるため（例えば、特定のシミュレータデスティネーションに対してのみ有効なスナップショットテストや、異なるフラグでコンパイルされるテストターゲットなど）、スキームは比較キーの一部となります。異なるスキームでの同じコミットの2回の実行は別の実行バリアントとして扱われ、互いを不安定としてフラグ付けすることはありません。

これは、再試行で捕捉できるほど一貫して失敗しないものの、依然として断続的なCI障害を引き起こす不安定なテストを検出する際に特に有用です。

## 不安定なテストの管理 {#managing-flaky-tests}

### 自動クリア

検出とクリアは、プロジェクト上の **自動化アラート** を介して実行されます。すべてのプロジェクトには、デフォルトの「不安定なテスト検出」自動化が用意されており、その *トリガー* はテストを不安定としてマークし、*リカバリー* は、テストが構成されたリカバリーウィンドウ（デフォルト **14日**）の間再トリガーされなかった場合にフラグをクリアします。**設定 → 自動化** で編集し、リカバリーウィンドウを変更したり、リカバリーアクション（例：隔離解除も行う）を入れ替えたり、リカバリーを完全に無効にしてテストを手動でクリアするまで不安定としてマークされたままにするように設定できます。

### 手動管理

テストケースの詳細ページから、テストを手動で不安定としてマークしたり、そのマークを解除したりすることもできます。これは以下の場合に便利です。
- 修正作業中に既知の不安定なテストを認識しておきたい場合
- インフラストラクチャの問題によりテストが誤ってフラグ付けされた場合

## 不安定なテストの隔離 {#quarantining}

隔離は、不安定なテストを分離し、修正中にCIをブロックしないようにします。デフォルトでは **手動アクション** です（ダッシュボードのテストケース詳細ページから隔離、隔離解除、モードの切り替えを行います）が、**設定 → 自動化** の下の **自動化アラート** に組み込むこともでき、不安定さが閾値を超えるとテストが自動的にミュート（またはスキップ）され、回復すると隔離が解除されます。手動か自動かを問わず、すべての遷移はテストケースの監査ログに記録されます。

隔離されたテストは、以下の2つのモードのいずれかになります。

- **ミュート**: テストは引き続き実行されますが、`tuist test` が失敗をマスクします。失敗は依然として不安定テスト検出器にフィードされるため、ビルドを壊すことなくテストを監視し続けることができます。積極的に調査中のテストにこのモードを選択してください。
- **スキップ**: xcodebuild は `-skip-testing <identifier>` を受け取るため、テストは開始されません。新しい結果は生成されず、再度有効にするまで不安定テストダッシュボードから除外されます。テストが壊れている、遅い、またはあまりにも持続的に不安定で実行することがCI時間の無駄である場合にこのモードを選択してください。

### 隔離されたテストが合格として表示される理由 {#quarantined-passing}

- **ミュートされたテスト** は引き続き実行されます。失敗したミュートテストは、テストケース実行上で **失敗** として記録され、不安定としてフラグ付けされます（テストごとのステータスは書き換えられません）。上書きされるのは **テスト実行全体** です。実行内のすべての失敗したテストケースがミュートされている場合、実行全体は合格として報告されるため、ミュートされた失敗はCIを中断しません。
- **スキップされたテスト** はまったく実行されないため、ダッシュボードにはテストの最後の実行時のステータスが表示され続けます（そのスナップショットは数週間前のものかもしれません）。

### テストの実行 {#running-tests}

`tuist test` は両方のモードを自動的に尊重します。

```sh
tuist test
```

スキップされたテストは `-skip-testing` としてxcodebuildに渡され、開始されません。ミュートされたテストは通常通り実行され、失敗した場合、その失敗は結果のビルドステータスでマスクされます。

隔離を完全にバイパスし、ミュートおよびスキップされたテストを含めてすべてを実行するには:

```sh
tuist test --skip-quarantine
```

## 新しいテストのストレステスト {#stress-testing-new-tests}

ストレスゲートは、ブランチが追加したテストケースをそれぞれ新しいプロセスで数回再実行し、不安定であることが判明したものを報告します。導入したプルリクエスト上で新しい不安定なテストを確認でき、数週間後になるのを待つ必要はありません。

テストケースは、プロジェクトのデフォルトブランチで過去90日間CIで実行されていない場合、またはそれ以降にデフォルトブランチにマージされたコミットで実行されていない場合に新規とカウントされます。マージキューを使用している場合、キューが実行したテストケースは、キューのコミットがマージされると認識され、キューがそれをドロップした場合は新規のままとなります。コミットは、TuistがCIで収集する <.localized_link href="/guides/features/test-insights/xcode#git-history">Git履歴</.localized_link> を介して照合されます。

### 有効化

ゲートはデフォルトでオフになっています。モードを設定してください。

- **`report`**: 各不安定なテストケースについて警告します。実行はその自身の結果に基づいて終了します。
- **`enforce`**: 不安定なテストケースは実行を失敗させ、失敗したテストと同じ終了コードを返します。

どちらのモードでも、<.localized_link href="/guides/features/selective-testing/generated-xcode-project">選択的テスト</.localized_link> は、次の実行で不安定な新しいテストケースを含むテストターゲットをスキップしません。ターゲットは再度実行され、ゲートはテストケースを再びストレステストし、すべての再実行に合格するまで続けます。

数週間は `report` で開始し、`enforce` が何をブロックしていたかを確認してください。

パススルー引数の前に指定するか、CIレーンごとにモードを変更するために `TUIST_TEST_STRESS_NEW_TESTS` を設定します:

```sh
tuist test --stress-new-tests report
```

### 各テストの再実行回数

最初のパスでのテストケースの実行時間によって異なります:

| 最初のパス | 再実行 |
| --- | --- |
| 5秒以内 | 10 |
| 10秒以内 | 5 |
| 30秒以内 | 3 |
| 5分以内 | 2 |
| 5分超 | 再実行なし |

再実行では、最初のパスでビルドされたものを再利用します。このパスは、200テストケースまたは10分のいずれかに達すると停止し、どの制限に達したかを表示します。

### ゲートが実行されない場合

- 最初のパスがすでに失敗しています。まずそれらのテストを修正してください。
- プロジェクトにデフォルトブランチがないか、そのブランチでCIがまだ何も実行されていません。
- プロジェクトのテストケースの30%以上が新規と見なされます。これほど多くのテストを再実行するのは時間がかかりすぎます。Tuistへのレポートを始めたばかりのプロジェクトや、一度に多くのテストを移動させる名前変更の後には、この状況が予想されます。

## 不安定および隔離状態のクエリ {#querying}

### CLI

`tuist test case` コマンドツリーは、Tuistがテストケースについて追跡するすべての情報を公開します:

```sh
tuist test case list --flaky                       # only flaky test cases
tuist test case list --quarantined                 # only muted or skipped test cases
tuist test case show <test_case_id>                # detail: flakiness rate, last status, run counts
tuist test case events <test_case_id>              # audit log: marked_flaky, muted, skipped, ...
tuist test case run list <test_case_id>            # run history with status and duration
tuist test case run show <test_case_run_id>        # single run, including failure breakdown
```

これらはすべてスクリプト用に `--json` を受け付けます。

### REST API

同じデータはHTTP経由でも利用可能です — ルート、フィルター、レスポンスフィールドの完全なリストについては、APIリファレンスの [テストケースエンドポイント](https://tuist.dev/api/docs#tag/test-cases) を参照してください。テストケースの状態（不安定のマーク/解除、ミュート、スキップ）を変更するには、`is_flaky` または `state` を含めて `PATCH /api/projects/{account_handle}/{project_handle}/tests/test-cases/{test_case_id}` を送信してください。同じ変更は `tuist test case update` および `update_test_case` Model Context Protocolツールとしても利用できます。
