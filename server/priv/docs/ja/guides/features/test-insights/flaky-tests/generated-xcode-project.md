# 生成されたXcodeプロジェクト {#generated-xcode-project-flaky-tests}

> [!WARNING]
> **要件**
>
> - <.localized_link href="/guides/features/test-insights/xcode">Xcodeテストインサイト</.localized_link>が構成されていること（自動生成されたスキームには`tuist inspect test`ポストアクションが含まれています。カスタムスキームにはこれを追加する必要があります）。

不安定なテストとは、同じコードで複数回実行したときに異なる結果（合格または不合格）を生み出すテストのことです。これらはテストスイートへの信頼を損ない、誤った失敗の調査に開発者の時間を浪費させます。Tuistは不安定なテストを自動的に検出し、経時的に追跡するのに役立ちます。

![不安定なテストページ](/images/guides/features/test-insights/flaky-tests-page.png)

## 不安定な検出の仕組み {#how-it-works}

Tuistは以下の2つの方法で不安定なテストを検出します。

### テストの再試行 {#test-retries}

再試行機能を使用してテストを実行すると、Tuistは各試行の結果を分析します。ある試行では失敗し、他の試行では成功するテストは、不安定としてマークされます。

`-retry-tests-on-failure`または`-test-iterations`を`tuist test`経由で渡します。

```sh
tuist test --scheme MyScheme -- -retry-tests-on-failure -test-iterations 3
```

![不安定なテストケースの詳細](/images/guides/features/test-insights/flaky-test-case-detail.png)

### クロスラン検出 {#cross-run-detection}

テストの再試行を行わなくても、Tuistは同じコミットと同じスキームに対する異なるCI実行間の結果を比較することで、不安定なテストを検出できます。あるCI実行ではテストが成功し、同じコミットとスキームの別の実行では失敗する場合、両方の実行は不安定としてマークされます。

スキームは比較キーの一部です。なぜなら、同じテストでもスキームによって決定論的に異なる動作をする可能性があるからです。例えば、特定のシミュレータ宛先に対してのみ有効なスナップショットテストや、異なるフラグでコンパイルされるテストターゲットなどです。異なるスキームでの同じコミットの2回の実行は、別の実行バリアントとして扱われ、互いを不安定としてフラグ付けすることはありません。

これは、再試行で捕捉できるほど一貫して失敗しないものの、依然として断続的なCI失敗を引き起こす不安定なテストを捕捉するのに特に有用です。

## 不安定なテストの管理 {#managing-flaky-tests}

### 自動クリア

検出とクリアは、プロジェクト上の**自動化アラート**を通じて実行されます。すべてのプロジェクトには、デフォルトの「不安定なテスト検出」自動化が用意されており、その*トリガー*はテストを不安定としてマークし、*リカバリ*は、テストが再トリガーされずに設定されたリカバリ期間（デフォルト**14日間**）を経過するとフラグをクリアします。**設定 → 自動化**で編集し、リカバリ期間を変更したり、リカバリアクションを入れ替えたり（例：隔離解除も行う）、リカバリを完全に無効にして、手動でクリアするまでテストが不安定としてマークされたままになるようにすることができます。

### 手動管理

テストケースの詳細ページから、テストを手動で不安定としてマークしたり、そのマークを外したりすることもできます。これは以下の場合に便利です。
- 修正作業中に既知の不安定なテストを認識したい場合
- インフラストラクチャの問題により、テストが誤ってフラグ付けされた場合

## 不安定なテストの隔離 {#quarantining}

隔離は、不安定なテストを分離し、修正中にCIをブロックしないようにします。デフォルトでは**手動アクション**です。ダッシュボードのテストケース詳細ページから隔離、隔離解除、モードの切り替えを行います。ただし、**設定 → 自動化**の下にある**自動化アラート**に組み込むこともでき、不安定性の閾値を超えたときにテストが自動的にミュート（またはスキップ）され、回復すると隔離解除されます。手動か自動かを問わず、すべての遷移はテストケースの監査ログに記録されます。

デフォルトでは、リカバリはトリガー条件が成立しなくなるまで待機するため、古い不安定な実行がトリガーウィンドウから外れるまでテストは隔離されたままになります。より早く回復させるには、**回復時期**を**新しい不安定な実行なし**に設定します。これにより、新しい不安定な実行なしにリカバリ期間（日数または実行回数）が経過するとテストは回復し、新しい不安定な実行ごとにその待機時間が再開され、回復後は新しい不安定な実行のみが再び隔離します。

隔離されたテストは、以下の2つのモードのいずれかになります。

- **ミュート**: テストは引き続き実行されますが、`tuist test`が失敗をマスクします。失敗は依然として不安定テスト検出器に供給されるため、ビルドを壊さずにテストを監視し続けることができます。積極的に調査中のテストにこのモードを選択してください。
- **スキップ**: xcodebuildは`-skip-testing <identifier>`を受け取るため、テストは決して開始されません。新しい結果は生成されず、再度有効にするまで不安定テストダッシュボードから除外されます。テストが壊れている、遅い、またはあまりにも持続的に不安定で実行することが無駄なCI時間となる場合にこのモードを選択してください。

### 隔離されたテストが合格として表示される理由 {#quarantined-passing}

- **ミュートされたテスト**は依然として実行されます。失敗したミュートテストは、テストケース実行上で**失敗**として記録され、不安定としてフラグ付けされます。テストごとのステータスは書き換えられません。上書きされるのは**全体のテスト実行**です。実行内のすべての失敗したテストケースがミュートされている場合、実行全体は合格として報告されるため、ミュートされた失敗はCIを中断しません。
- **スキップされたテスト**はまったく実行されないため、ダッシュボードにはテストの最後の実際の実行からのステータスが引き続き表示されます。そのスナップショットは数週間前のものかもしれません。

### テストの実行 {#running-tests}

`tuist test`は両方のモードを自動的に尊重します。

```sh
tuist test
```

スキップされたテストは`-skip-testing`としてxcodebuildに渡され、決して開始されません。ミュートされたテストは通常通り実行されます。失敗した場合、その失敗は結果のビルドステータスでマスクされます。

隔離を完全にバイパスし、ミュートおよびスキップされたテストを含むすべてを実行するには:

```sh
tuist test --skip-quarantine
```

## 新しいテストの負荷テスト {#stress-testing-new-tests}

ストレージゲートは、ブランチが追加したテストケースをそれぞれ新しいプロセスで複数回再実行し、不安定であることが判明したものを報告します。数週間後ではなく、それを導入したプルリクエスト上で新しい不安定なテストを確認できます。

テストケースは、プロジェクトのデフォルトブランチで過去90日間にCIで実行されていない場合、またはそれ以来そのブランチに着陸したコミットで実行されていない場合、新しいものとみなされます。マージキューを使用する場合、キューが実行したテストケースは、キューのコミットが着陸した時点で認識され、キューがそれをドロップした場合、新しいままとなります。コミットは、TuistがCIで収集する<.localized_link href="/guides/features/test-insights/xcode#git-history">Git履歴</.localized_link>を通じてマッチングされます。

### 有効化

ゲートはデフォルトでオフになっています。モードを設定してください:

- **`report`**: 不安定なテストケースごとに警告を表示します。実行は依然としてその結果に基づいて終了します。
- **`enforce`**: 不安定なテストケースは実行を失敗させ、失敗したテストと同じ終了コードを返します。

どちらのモードでも、<.localized_link href="/guides/features/selective-testing/generated-xcode-project">選択的テスト</.localized_link>は、次の実行で不安定な新しいテストケースを含むテストターゲットをスキップしません。ターゲットは再度実行され、ゲートはテストケースを再び負荷テストし、すべての再実行に合格するまで続けます。

`report`から始めて数週間過ごし、`enforce`が何をブロックしていたかを確認してください。

パススルー引数の前に指定するか、`TUIST_TEST_STRESS_NEW_TESTS`を設定してCIレーンごとにモードを変更します:

```sh
tuist test --stress-new-tests report
```

### 各テストの再実行回数

最初のパスでのテストケースの実行時間によって異なります:

| 最初のパス | 再実行 |
| --- | --- |
| 最大5秒 | 10 |
| 最大10秒 | 5 |
| 最大30秒 | 3 |
| 最大5分 | 2 |
| 5分超 | 再実行なし |

再実行では、最初のパスでビルドされたものを再利用します。パスは200テストケースまたは10分のいずれかに達すると停止し、どの制限に達したかを示します。

### ゲートが実行されない場合

- 最初のパスがすでに失敗しています。まずそれらのテストを修正してください。
- プロジェクトにデフォルトブランチがないか、そのブランチでCIがまだ何も実行されていません。
- プロジェクトのテストケースの30%以上が新しいように見えます。それほど多くを再実行するのは手間に見合いません。Tuistへのレポートを始めたばかりのプロジェクトや、一度に多くのテストを移動させるリネームを行った後には、この状況が予想されます。

## Slack通知 {#slack-notifications}

Slack連携で<.localized_link href="/guides/integrations/slack#flaky-test-alerts">不安定なテストのアラート</.localized_link>を設定することで、テストが不安定になった瞬間に通知を受け取れます。

## 不安定および隔離状態のクエリ {#querying}

### CLI

`tuist test case`コマンドツリーは、Tuistがテストケースについて追跡するすべての情報を公開します:

```sh
tuist test case list --flaky                       # only flaky test cases
tuist test case list --quarantined                 # only muted or skipped test cases
tuist test case show <test_case_id>                # detail: flakiness rate, last status, run counts
tuist test case events <test_case_id>              # audit log: marked_flaky, muted, skipped, ...
tuist test case run list <test_case_id>            # run history with status and duration
tuist test case run show <test_case_run_id>        # single run, including failure breakdown
```

これらすべてはスクリプト用に`--json`を受け入れます。

### REST API

同じデータはHTTP経由でも利用可能です。ルート、フィルター、レスポンスフィールドの完全なリストについては、APIリファレンスの[テストケースエンドポイント](https://tuist.dev/api/docs#tag/test-cases)を参照してください。テストケースの状態（不安定のマーク/解除、ミュート、スキップ）を変更するには、`is_flaky`または`state`を指定して`PATCH /api/projects/{account_handle}/{project_handle}/tests/test-cases/{test_case_id}`を送信してください。同じ変更は`tuist test case update`としても、また`update_test_case` Model Context Protocolツールとしても利用可能です。
