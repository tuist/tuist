# Elixirの不安定なテスト {#elixir-flaky-tests}

不安定なテストとは、同じコードで複数回実行したときに結果（合格または不合格）が異なるテストです。これらはテストスイートへの信頼を損ない、誤った失敗の調査に開発者の時間を浪費させます。Tuistは不安定なテストを自動的に検出し、経時的に追跡するのを支援します。

> [!IMPORTANT] REQUIREMENTS
> - テスト実行を報告するには、<.localized_link href="/guides/get-started/elixir-project">共有Elixirセットアップ</.localized_link>を完了してください

![Phoenixアプリケーションの不安定なテスト](/images/guides/features/elixir/flaky-tests.png)

## 不安定な検出の仕組み {#how-it-works}

Tuistは次の2つの方法で不安定なテストを検出します：

### テストの再試行 {#test-retries}

ExUnitは各テストを1回だけ実行するため、断続的に失敗するテストは壊れたテストと同じように見えます。再試行を有効にすると、Hexパッケージは設定した回数まで失敗したテストを再度実行します。再試行で合格したテストは不安定として報告され、すべての失敗したテストが最終的に合格すれば実行は成功します。

再試行はデフォルトでオフです。有効にするには、`mix.exs`内の既存のTuistオプションに`test_retries`を追加してください：

```elixir
tuist: [project: "account/project", cache: true, test_retries: 2]
```

または、フラグまたは環境変数を使用して単一の実行の場合：

```bash
mix test --retries 2
TUIST_TEST_RETRIES=2 mix test
```

フラグは環境変数より優先され、環境変数は`mix.exs`より優先されます。

失敗したテストのみが`mix test --failed`の実行方法と同様に再度実行され、ダッシュボードには各テストの試行とその所要時間が表示されます。`--max-failures`のためにExUnitが早期に停止した実行は再試行されません。失敗したテストがすべてタイムアウトした実行も再試行されません。各再試行で再びすべてのタイムアウトを待たなければならないためです。再試行はまた、`--warnings-as-errors`ではスキップされ、`mix test`はこれを強制しなくなり、アンブレラプロジェクトのルートからもスキップされます。再試行するには、そのアプリケーションの内部でテストを実行してください。

![不安定なExUnitテストとその履歴](/images/guides/features/elixir/flaky-test-case.png)

### クロスラン検出 {#cross-run-detection}

テストの再試行がなくても、Tuistは同じコミットに対する異なるCI実行間の結果を比較することで不安定なテストを検出できます。あるCI実行でテストが合格し、同じコミットの別の実行で失敗した場合、両方の実行が不安定としてマークされます。

これは、再試行で捕捉されるほど一貫して失敗しないものの、依然として断続的なCI失敗を引き起こす不安定なテストを捕捉するのに特に有用です。

## 不安定なテストの管理 {#managing-flaky-tests}

### 自動クリア

検出とクリアは、プロジェクト上の**自動化アラート**を通じて実行されます。すべてのプロジェクトにはデフォルトの「不安定なテスト検出」自動化があり、その*トリガー*はテストを不安定としてマークし、*リカバリー*はテストが構成されたリカバリーウィンドウ（デフォルト**14日間**）を再トリガーなしで経過するとフラグをクリアします。**設定 → 自動化**で編集して、リカバリーウィンドウを変更するか、リカバリーを完全に無効にして、手動でクリアするまでテストが不安定としてマークされたままになるようにします。

### 手動管理

テストケースの詳細ページから、テストを手動で不安定としてマークまたはマーク解除することもできます。これは以下の場合に便利です：
- 修正作業中に既知の不安定なテストを認識したい場合
- インフラストラクチャの問題によりテストが誤ってフラグ付けされた場合

## 不安定なテストの隔離 {#quarantining}

隔離は、修正中に不安定なテストがCIをブロックしないようにします。ダッシュボードのテストページで、その状態を**ミュート**または**スキップ**に変更するか、**設定 → 自動化**で自動化を設定して、テストが不安定になったときにミュートまたはスキップし、回復したら再度有効にします。テストを実行する前に、`mix test`はプロジェクトのすべての隔離されたテストを読み取り、それらを適用します：

- **ミュート**：テストは実行され、その失敗は依然として報告されますが、失敗がミュートされたテストのみである実行は合格します。再試行は依然として失敗するミュートされたテストを再実行するため、不安定なテストは合格して不安定として報告される可能性があります。
- **スキップ**：テストは実行されません。`mix test`は実行開始前にスキップされたテストを一覧表示します。

```text
Tuist: skipping 1 quarantined test:
  MyApp.CheckoutTest: create_order/2 times out
Tuist: 1 muted test run, and their failures do not fail the run.
```

ミュートされていないテストが失敗した場合、または`--max-failures`のためにExUnitが早期に停止した場合、実行は通常どおり失敗します。

> [!WARNING]
> **制限事項**
>
> - 隔離を適用するのはHexパッケージの最近のバージョンのみです。以前のバージョンはミュートおよびスキップされたテストを他のテストと同様に実行するため、ミュートされたテストの失敗は依然として実行を失敗させます。依存する前に`tuist_ex`を更新してください。
> - ミュートされたテストは、`--warnings-as-errors`またはアンブレラプロジェクトのルートからは適用されません。その場合、それらの失敗は実行を失敗させます。代わりに、アンブレラの各アプリケーション内部でテストを実行してください。
> - スキップはモジュールではなく、describeブロックと名前でテストを一致させます。別のモジュールで同じdescribeブロックと名前を持つテストもスキップされます。[スキップがテストを選択する方法](#how-skipping-selects-tests)を参照してください。
> - スキップされたテストは、`--only`、`--include`、または`path:line`で選択した場合、あるいは`test`で宣言されていない場合（例えばStreamDataの`property`）でも依然として実行されます。
> - `mix test`が隔離されたテストを読み取れない場合、すべてのテストを実行し、すべての失敗をカウントします。
> - 隔離されたテストの読み取りには、パブリックプロジェクトであっても認証情報が必要です。`TUIST_TOKEN`、`mix tuist.login`セッション、または継続的インテグレーション識別トークンなしの実行では隔離は適用されません。これには、通常シークレットなしで実行されるフォークからのプルリクエストも含まれます。
> - `--cover`を使用する場合、スキップされたテストは削除されたものとしてカウントされます：そのテストのみがカバーしていた行は未カバーとして報告されます。
>
> `mix test`は、サマリーの後に、スキップによって誤って除外されたテストと、それでも実行されたスキップされたテストの名前を表示します。

### スキップがテストを選択する方法 {#how-skipping-selects-tests}

スキップされたテストは、フルネームに対するExUnitフィルター（例えば`--exclude "test:test create_order/2 times out"`）によって除外されます。ExUnitフィルターはモジュールも一致させることができないため：

- 別のモジュールで同じdescribeブロックと名前を持つテストも除外されます。`mix test`は実行後にそれらのテストの名前を表示します。
- `--only`、`--include`、または`path:line`で選択したテストは、除外フィルターの後に包含フィルターが適用されるため、スキップされていても実行されます。`test`で宣言されていないテスト（例えばStreamDataの`property`）も同様です。`mix test`は実行後にそれらのテストの名前を表示します。

### 隔離されたテストを再実行する {#running-quarantined-tests-again}

すべてのテストを実行してすべての失敗をカウントするには、`--no-quarantine`を渡してください（修正の確認などに役立ちます）。

```bash
mix test --no-quarantine
```

後続の実行に含めるには、そのテストのページで状態を**有効**に戻してください。スキップされたテストは、再度実行されるまで新しい結果を生成しません。

`mix test`が隔離されたテストを読み取れない場合、警告を表示してそれらを除くすべてのテストを実行します。認証情報や設定済みプロジェクトがない場合は、警告なしですべてのテストを実行します。

Hexパッケージはまだ新しいテストに対する負荷テストを行いません。

## Slack通知 {#slack-notifications}

テストがflakyになった瞬間に通知を受け取るには、Slack連携で<.localized_link href="/guides/integrations/slack#flaky-test-alerts">flaky test alerts</.localized_link>を設定してください。

## 不安定な状態のクエリ {#querying}

データはHTTP経由で利用できます。ルート、フィルター、レスポンスフィールドの完全な一覧については、APIリファレンスの[テストケースエンドポイント](https://tuist.dev/api/docs#tag/test-cases)を参照してください。テストケースを不安定としてマークまたは解除するには、`is_flaky`を含めて`PATCH /api/projects/{account_handle}/{project_handle}/tests/test-cases/{test_case_id}`を送信するか、`update_test_case` Model Context Protocolツールを使用してください。
