# Elixirの不安定なテスト {#elixir-flaky-tests}

不安定なテストとは、同じコードで複数回実行した際に異なる結果（合格または不合格）を返すテストのことです。これらはテストスイートへの信頼を損ない、誤った失敗の原因調査に開発者の時間を浪費させます。Tuistは不安定なテストを自動的に検出し、経時的に追跡することを支援します。

> [!IMPORTANT] REQUIREMENTS
> - テスト実行を報告するには、<.localized_link href="/guides/get-started/elixir-project">共有Elixirセットアップ</.localized_link>を完了してください

![Phoenixアプリケーションの不安定なテスト](/images/guides/features/elixir/flaky-tests.png)

## 不安定な検出の仕組み {#how-it-works}

Tuistは以下の2つの方法で不安定なテストを検出します：

### テストの再試行 {#test-retries}

ExUnitは各テストを1回だけ実行するため、断続的に失敗するテストは壊れているテストと同じように見えます。再試行が有効になっている場合、Hexパッケージは設定した回数まで失敗したテストを再度実行します。再試行で合格したテストは不安定として報告され、すべての失敗したテストが最終的に合格すれば実行は成功します。

再試行はデフォルトで無効です。有効にするには、`mix.exs`内の既存のTuistオプションに`test_retries`を追加してください：

```elixir
tuist: [project: "account/project", cache: true, test_retries: 2]
```

または、フラグまたは環境変数を使用して単一の実行に対して指定します：

```bash
mix test --retries 2
TUIST_TEST_RETRIES=2 mix test
```

フラグは環境変数より優先され、環境変数は`mix.exs`より優先されます。

失敗したテストのみが`mix test --failed`の実行方法と同様に再度実行され、ダッシュボードには各テストの試行回数とその所要時間が表示されます。`--max-failures`のためにExUnitが早期に停止した実行は再試行されません。失敗したテストがすべてタイムアウトした実行も再試行されません。各再試行で再びすべてのタイムアウトを待機するためです。また、`--warnings-as-errors`では再試行もスキップされます。これは`mix test`が強制しなくなるためであり、umbrellaプロジェクトのルートからもスキップされます。再試行するには、そのアプリケーションの内部でテストを実行してください。

![不安定なExUnitテストとその履歴](/images/guides/features/elixir/flaky-test-case.png)

### クロスラン検出 {#cross-run-detection}

テストの再試行なしでも、Tuistは同じコミットに対する異なるCI実行の結果を比較することで不安定なテストを検出できます。あるCI実行でテストが合格し、同じコミットの別の実行で失敗した場合、両方の実行が不安定としてマークされます。

これは、再試行で捕捉できるほど一貫して失敗しないものの、依然として断続的なCI失敗を引き起こす不安定なテストを捕捉するのに特に有用です。

## 不安定なテストの管理 {#managing-flaky-tests}

### 自動クリア

検出とクリアは、プロジェクト上の**自動化アラート**を通じて実行されます。すべてのプロジェクトには、デフォルトの「不安定なテスト検出」自動化が付与されており、その*トリガー*はテストを不安定としてマークし、*リカバリー*は、テストが構成されたリカバリーウィンドウ（デフォルト**14日間**）中に再トリガーされずに経過するとフラグをクリアします。**Settings → Automations**で編集してリカバリーウィンドウを変更するか、リカバリーを完全に無効にして、手動でクリアするまでテストが不安定としてマークされたままになるように設定できます。

### 手動管理

テストケースの詳細ページから、テストを手動で不安定としてマークしたり、マークを解除したりすることもできます。これは以下の場合に便利です：
- 修正作業中に既知の不安定なテストを認識したい場合
- インフラストラクチャの問題によりテストが誤ってフラグ付けされた場合

## 不安定なテストの隔離 {#quarantining}

隔離により、修正中に不安定なテストがCIをブロックするのを防ぎます。ダッシュボードのテストページで、その状態を**Muted**または**Skipped**に変更するか、**Settings → Automations**で自動化を設定して、テストが不安定になったときにミュートまたはスキップし、回復したら再度有効にします。テストを実行する前に、`mix test`はプロジェクトのすべての隔離されたテストを読み取り、それらを適用します：

- **Muted**：テストは実行され、その失敗は報告されますが、失敗がミュートされたテストのみである実行は合格となります。再試行は失敗するミュートされたテストを依然として再実行するため、不安定なテストは合格して不安定として報告される可能性があります。
- **Skipped**：テストは実行されません。`mix test`は実行開始前にスキップされたテストを一覧表示します。

```text
Tuist: skipping 1 quarantined test:
  MyApp.CheckoutTest: create_order/2 times out
Tuist: 1 muted test run, and their failures do not fail the run.
```

ミュートされていないテストが失敗した場合、または`--max-failures`のためにExUnitが早期に停止した場合、実行は通常どおり失敗します。

> [!WARNING]
> **制限事項**
>
> - 隔離を適用するのはHexパッケージの最近のバージョンのみです。以前のバージョンはミュートされたテストやスキップされたテストを他のテストと同様に実行するため、ミュートされたテストの失敗は依然として実行を失敗させます。依存する前に`tuist_ex`を更新してください。
> - ミュートされたテストは、`--warnings-as-errors`を使用する場合やumbrellaプロジェクトのルートからは適用されません。その場合、それらの失敗は実行を失敗させます。代わりにumbrellaの各アプリケーションの内部でテストを実行してください。
> - スキッピングはモジュールではなく、describeブロックと名前でテストを一致させます。別のモジュールに同じdescribeブロックと名前を持つテストがある場合、それもスキップされます。[スキッピングがテストを選択する方法](#how-skipping-selects-tests)を参照してください。
> - スキップされたテストは、`--only`、`--include`、または`path:line`で選択した場合、あるいは`test`で宣言されていない場合（例えばStreamDataの`property`など）は依然として実行されます。
> - `mix test`が隔離されたテストを読み取れない場合、すべてのテストを実行し、すべての失敗をカウントします。
> - 隔離されたテストの読み取りには、パブリックプロジェクトであっても認証情報が必要です。`TUIST_TOKEN`、`mix tuist.login`セッション、または継続的インテグレーション識別トークンがない実行では、隔離は適用されません。これには、通常シークレットなしで実行されるフォークからのプルリクエストも含まれます。
> - `--cover`を使用する場合、スキップされたテストは削除されたものとしてカウントされます。そのテストのみがカバーしていた行は、未カバーとして報告されます。
>
> `mix test`は、スキップによって誤って除外されたテストと、それでも実行されたスキップされたテストの名前を、サマリーの後に表示します。

### スキッピングがテストを選択する方法 {#how-skipping-selects-tests}

スキップされたテストは、完全な名前に対するExUnitフィルター（例：`--exclude "test:test create_order/2 times out"`）によって除外されます。ExUnitフィルターはモジュールも一致させることができないため：

- 別のモジュールに同じdescribeブロックと名前を持つテストも除外されます。`mix test`は実行後にそれらのテストの名前を表示します。
- `--only`、`--include`、または`path:line`で選択したテストは除外フィルターよりも後に包含フィルターが適用されるため、スキップされていても実行されます。`test`で宣言されていないテスト（例えばStreamDataの`property`など）も同様です。`mix test`は実行後にそれらのテストの名前を表示します。

### 隔離されたテストを再度実行する {#running-quarantined-tests-again}

修正を確認する場合など、すべてのテストを実行してすべての失敗をカウントするには、`--no-quarantine`を渡してください：

```bash
mix test --no-quarantine
```

後続の実行に含めるには、そのテストのページで状態を**有効**に戻してください。スキップされたテストは、再度実行されるまで新しい結果を生成しません。

`mix test`が隔離されたテストを読み取れない場合、警告を表示してそれらを除くすべてのテストを実行します。認証情報や設定済みプロジェクトがない場合は、警告なしですべてのテストを実行します。

Hexパッケージはまだ新しいテストに対するストレステストを行いません。

## Slack通知 {#slack-notifications}

Slackインテグレーションで<.localized_link href="/guides/integrations/slack#flaky-test-alerts">フラッキーテストアラート</.localized_link>を設定することで、テストが不安定になった際に即座に通知を受け取れます。

## 不安定な状態のクエリ {#querying}

データはHTTP経由で利用可能です。ルート、フィルター、レスポンスフィールドの完全な一覧については、APIリファレンスの[テストケースエンドポイント](https://tuist.dev/api/docs#tag/test-cases)を参照してください。テストケースを不安定としてマークまたは解除するには、`is_flaky`を含めて`PATCH /api/projects/{account_handle}/{project_handle}/tests/test-cases/{test_case_id}`を送信するか、`update_test_case` Model Context Protocolツールを使用してください。
