# Elixir の不安定なテスト {#elixir-flaky-tests}

不安定なテストとは、同じコードで複数回実行したときに異なる結果（合格または不合格）を返すテストのことです。これらはテストスイートへの信頼を損ない、誤った失敗の調査に開発者の時間を浪費させます。Tuist は不安定なテストを自動的に検出し、経時的に追跡するのに役立ちます。

> [!IMPORTANT] REQUIREMENTS
> - テスト実行を報告するには、<.localized_link href="/guides/get-started/elixir-project">共有 Elixir セットアップ</.localized_link>を完了してください

![Phoenix アプリケーションの不安定なテスト](/images/guides/features/elixir/flaky-tests.png)

## 不安定な検出の仕組み {#how-it-works}

Tuist は以下の 2 つの方法で不安定なテストを検出します。

### テストの再試行 {#test-retries}

ExUnit は各テストを 1 回だけ実行するため、断続的に失敗するテストは壊れているテストと同じように見えます。再試行が有効になっている場合、Hex パッケージは設定した回数まで失敗したテストを再度実行します。再試行で合格したテストは不安定として報告され、すべての失敗したテストが最終的に合格すれば実行は成功します。

再試行はデフォルトで無効になっています。有効にするには、`mix.exs`内の既存の Tuist オプションに `test_retries` を追加してください。

```elixir
tuist: [project: "account/project", cache: true, test_retries: 2]
```

または、フラグまたは環境変数を使用して単一の実行に対して指定します。

```bash
mix test --retries 2
TUIST_TEST_RETRIES=2 mix test
```

フラグは環境変数より優先され、環境変数は `mix.exs` より優先されます。

失敗したテストのみが `mix test --failed` の実行方法と同様に再度実行され、ダッシュボードには各テストの試行回数とその所要時間が表示されます。`--max-failures` のために ExUnit が早期に停止した実行は再試行されません。失敗したテストがすべてタイムアウトした実行も再試行されません。これは、各再試行で再びすべてのタイムアウトを待機するためです。また、`--warnings-as-errors` では再試行もスキップされます。これにより `mix test` は強制されなくなり、アンブレラプロジェクトのルートからもスキップされます。再試行するには、そのアプリケーションのいずれかの中でテストを実行してください。

![不安定な ExUnit テストとその履歴](/images/guides/features/elixir/flaky-test-case.png)

### クロスラン検出 {#cross-run-detection}

テストの再試行なしでも、Tuist は同じコミットに対する異なる CI 実行間の結果を比較することで不安定なテストを検出できます。ある CI 実行でテストが合格し、同じコミットの別の実行で失敗した場合、両方の実行は不安定としてマークされます。

これは、再試行で捕捉されるほど一貫して失敗しないものの、依然として断続的な CI 失敗を引き起こす不安定なテストを捕捉するのに特に有用です。

## 不安定なテストの管理 {#managing-flaky-tests}

### 自動クリア

検出とクリアは、プロジェクト上の **自動化アラート** を介して実行されます。すべてのプロジェクトには、デフォルトの「不安定なテスト検出」自動化が付与されており、その *トリガー* はテストを不安定としてマークし、*回復* はテストが構成された回復期間（デフォルト **14 日**）の間に再トリガーされずに経過するとフラグをクリアします。**設定 → 自動化** で編集して回復期間を変更するか、回復を完全に無効にして、手動でクリアするまでテストが不安定としてマークされたままになるようにすることができます。

### 手動管理

テストケースの詳細ページから、テストを手動で不安定としてマークしたり、マークを解除することもできます。これは以下の場合に便利です。
- 修正作業中に既知の不安定なテストを認識したい場合
- インフラストラクチャの問題によりテストが誤ってフラグ付けされた場合

## 不安定なテストの隔離 {#quarantining}

隔離により、修正中に不安定なテストが CI をブロックすることを防ぎます。ダッシュボードのテストページで、その状態を **ミュート** または **スキップ** に変更するか、**設定 → 自動化** で、テストが不安定になったときにミュートまたはスキップし、回復したら再度有効にする自動化を構成します。テストを実行する前に、`mix test` はプロジェクトのすべての隔離されたテストを読み取り、それらを適用します。

- **ミュート**: テストは実行され、その失敗は引き続き報告されますが、失敗がミュートされたテストのみである実行は合格となります。再試行は失敗したミュートテストを依然として再実行するため、不安定なテストは合格して不安定として報告される可能性があります。
- **スキップ**: テストは実行されません。`mix test` は実行開始前にスキップされたテストを一覧表示します。

```text
Tuist: skipping 1 quarantined test:
  MyApp.CheckoutTest: create_order/2 times out
Tuist: 1 muted test run, and their failures do not fail the run.
```

ミュートされていないテストが失敗した場合、または `--max-failures` のために ExUnit が早期に停止した場合、実行は通常どおり失敗します。

> [!WARNING]
> **制限事項**
>
> - 隔離を適用するのは Hex パッケージの最近のバージョンのみです。以前のバージョンはミュートおよびスキップされたテストを他のテストと同様に実行するため、ミュートされたテストの失敗は依然として実行を失敗させます。依存する前に `tuist_ex` を更新してください。
> - ミュートされたテストは `--warnings-as-errors` とともに、またはアンブレラプロジェクトのルートからは適用されません。それらの失敗はその後実行を失敗させます。代わりに、アンブレラの各アプリケーション内でテストを実行してください。
> - スキッピングはモジュールではなく、describe ブロックと名前でテストを一致させます。別のモジュールで同じ describe ブロックと名前を持つテストもスキップされます。[スキッピングがテストを選択する方法](#how-skipping-selects-tests)を参照してください。
> - スキップされたテストは、`--only`、`--include`、または `path:line` で選択した場合、あるいは `test` で宣言されていない場合（例えば StreamData の `property` など）でも依然として実行されます。
> - `mix test` が隔離されたテストを読み取れない場合、すべてのテストを実行し、すべての失敗をカウントします。
> - 隔離されたテストの読み取りには、パブリックプロジェクトであっても認証情報が必要です。`TUIST_TOKEN`、`mix tuist.login` セッション、または継続的インテグレーション識別トークンがない実行では隔離は適用されません。これには、通常シークレットなしで実行されるフォークからのプルリクエストも含まれます。
> - `--cover` を使用すると、スキップされたテストは削除されたものとしてカウントされます。そのテストのみがカバーしていた行は未カバーとして報告されます。
>
> `mix test` は、まとめの後に、スキップによって誤って除外されたテストと、それでも実行されたスキップされたテストの名前を表示します。

### スキッピングがテストを選択する方法 {#how-skipping-selects-tests}

スキップされたテストは、完全な名前に対する ExUnit フィルター（例: `--exclude "test:test create_order/2 times out"`）によって除外されます。ExUnit フィルターはモジュールも一致させることができないため、次のようになります。

- 別のモジュールで同じ describe ブロックと名前を持つテストも除外されます。`mix test` は実行後にそれらのテストの名前を表示します。
- `--only`、`--include`、または `path:line` で選択したテストは、ExUnit が除外フィルターの後に包含フィルターを適用するため、スキップされていても実行されます。`test` で宣言されていないテスト（例えば StreamData の `property` など）も同様です。`mix test` は実行後にそれらのテストの名前を表示します。

### 隔離されたテストを再度実行する {#running-quarantined-tests-again}

すべてのテストを実行し、すべての失敗をカウントするには `--no-quarantine` を渡します（例えば修正を確認する場合など）。

```bash
mix test --no-quarantine
```

後続の実行に含めるには、そのページでテストを **有効** に戻してください。スキップされたテストは、再度実行されるまで新しい結果を生成しません。

`mix test` が隔離されたテストを読み取れない場合、警告を表示してそれらを除いたすべてのテストを実行します。認証情報や設定済みプロジェクトがない場合は、警告なしですべてのテストを実行します。

Hex パッケージはまだ新しいテストのストレステストを行っていません。

## Slack 通知 {#slack-notifications}

Slack インテグレーションで <.localized_link href="/guides/integrations/slack#flaky-test-alerts">不安定なテストのアラート</.localized_link> を設定することで、テストが不安定になった際に即座に通知を受け取れます。

## 不安定な状態のクエリ {#querying}

データは HTTP 経由で利用可能です。ルート、フィルター、レスポンスフィールドの完全なリストについては、API リファレンスの [テストケースのエンドポイント](https://tuist.dev/api/docs#tag/test-cases) を参照してください。テストケースを不安定としてマークまたはアンマークするには、`is_flaky` を指定して `PATCH /api/projects/{account_handle}/{project_handle}/tests/test-cases/{test_case_id}` を送信するか、`update_test_case` Model Context Protocol ツールを使用してください。
