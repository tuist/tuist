# Grafana 統合 {#grafana}

Tuist データソースを使用すると、ビルド時間、失敗回数、キャッシュによる節約時間など、ビルド、テスト、キャッシュのメトリクスを Grafana で利用できます。チームが重視するプロジェクトやメトリクスを中心にダッシュボードを構築したり、社内既存のダッシュボードで Tuist メトリクスを他のデータソースと組み合わせたりできます。Grafana のアラートルールと通知チャネルを活用し、ビルドが遅くなったり失敗が増加した際にチームに通知しましょう。

## 利用可能なメトリクス {#metric-definitions}

テーブルには読みやすいラベルとそのクエリ識別子が記載されています。ビルド健全性のクエリでは `metric` フィールドの識別子を使用し、ビルドおよびテスト時間のクエリでは `series` フィールドで `average`、`p50`、`p90`、または `p99` を選択します。

### ビルド数と信頼性

| メトリクス | 識別子 | 測定内容 |
| --- | --- | --- |
| ビルド数 | `builds` | 記録されたビルドの数。 |
| 成功したビルド | `successful_builds` | 正常に完了したビルド。 |
| 失敗したビルド | `failed_builds` | 失敗したビルド。 |
| キャンセルされたビルド | `cancelled_builds` | キャンセルとして記録されたビルド。[ビルドシステムの差異](#build-systems)を参照してください。 |
| ビルド成功率 | `success_rate` | 成功 ÷ (成功 + 失敗) をパーセンテージで表示。 |
| 失敗または低速なビルド | `builds_needing_attention` | 失敗または低速なビルドを、ビルドごとに1回カウント。 |

### ビルドおよびテスト時間

| メトリクス | 識別子 | 測定内容 |
| --- | --- | --- |
| 平均時間 | `average` | 選択した実行の平均時間。 |
| 中央値 | `p50` | 実行時間の50パーセンタイル。 |
| 90パーセンタイル時間 | `p90` | 実行の90%がこの時間以下となる値。 |
| 99パーセンタイル時間 | `p99` | 実行の99%がこの時間以下となる値。 |
| 低速ビルドのしきい値 | `slow_build_threshold` | 90パーセンタイル時間、またはミリ秒単位の固定上限値。 |

テスト時間のメトリクスは、Tuist に記録されたテスト実行を使用します。低速ビルドのしきい値はビルドにのみ適用され、ビルド時間がそのしきい値を超えると低速と判定されます。キャンセルされたビルドは別途カウントされ、ビルド成功率からは除外されます。

### キャッシュによる節約

| メトリクス | 識別子 | 測定内容 |
| --- | --- | --- |
| 累積タスク時間の節約（Gradle） | `cache_work_avoided` | キャッシュヒットによって回避された推定タスク実行時間の合計。 |
| 累積タスク時間を報告するビルド | `cache_work_avoided_samples` | 完全な推定値を持つビルド。 |
| 報告されたキャッシュによる時間節約 | `cache_time_saved` | 報告された経過時間の節約の合計。 |
| キャッシュによる時間節約を報告するビルド | `cache_time_saved_samples` | 有効な節約値を持つビルド。 |

Gradle プラグインは、ローカルおよびリモートのタスクキャッシュヒットに対して、回避された作業量を自動的に報告します。各キャッシュされたタスクについて、Gradle が保存した元の実行時間からタスクの復元時間を差し引き、最小値をゼロとします。ビルドの推定値はこれらの値を合計したものです。並列タスクは重複する可能性があるため、これは累積タスク時間であり、節約された経過ビルド時間ではありません。最新の状態のタスクやスキップされたタスクは除外されます。

タスクキャッシュヒットのないビルドはゼロを報告します。キャッシュされたタスクに元の実行時間が欠けている場合、テレメトリが不完全な場合、またはカスタムメタデータマップに空きがない場合、プラグインは推定値を省略します。古いプラグインバージョンや他のビルドシステムはこれを報告しません。カバレッジを確認するには、報告数と総ビルド数を比較してください。

報告された経過時間の節約は `tuist.cache_time_saved_ms` メタデータから取得されます。このメトリクスは自動推定値とは別に扱われます。

報告するビルドがない場合、キャッシュによる節約には値がありません。Struo は現在この測定値を記録していません。キャッシュヒット率とミス率は、このデータソースでは利用できません。

### テーブル

これらの識別子は、クエリの `queryType` フィールドの値です。

| テーブル | クエリタイプ | 内容 |
| --- | --- | --- |
| ワークロード別の健全性 | `buildWorkloads` | ビルド数、成功率、中央値および90パーセンタイル時間。 |
| 失敗カテゴリ | `buildFailureReasons` | 失敗カテゴリ別のすべての失敗とその数。 |
| 最近の失敗したビルド | `buildRecentFailures` | 最新の100件の失敗。Tuist へのリンク付き。 |

最近の失敗には、開始時間、期間、ユーザー、ブランチ、および要求されたタスクが含まれます。失敗カテゴリは `verification`、`infrastructure_tooling`、および `unknown` です。

ワークロードの概要とブランチ/ワークロードの値リストは、最大1000個の値を返します。ビルド健全性の変数クエリは過去90日間を使用します。レガシー Gradle 変数クエリは既存の履歴ウィンドウを維持します。Bazel はツールによって報告されたビルドユーザーを表示します。他の統合は、報告資格情報に関連付けられたアカウントを表示します。記録されたユーザーがない場合、歴史的な Bazel および Struo の実行、ならびにプロジェクト資格情報で報告された Struo の実行は「不明」として表示されます。

ビルド実行の「失敗カテゴリ」フィルターを使用して、一致する失敗を検索します。カテゴリはビルド詳細に表示され、その意味を説明する情報ヒントが付いています。デフォルトの概要とビルド実行テーブルは既存の列を維持します。成功したビルド、キャンセルされたビルド、未完了のビルドには失敗カテゴリがありません。Gradle のキャッシュ分析カードとビルド詳細には「累積タスク時間の節約」が表示され、ツールチップには推定値と並列タスクの影響が説明されています。キャッシュウィジェットは、選択した範囲を同じフィルターを使用した直前の同等の期間と比較します。比較は中立的です。合計値が大きくなるのは、ビルド数が増加したことを反映している可能性があります。以前の推定値がない場合は比較が表示されません。記録されたベースラインがゼロの場合、割合ではなく絶対的な増加が表示されます。

## 標準ダッシュボード {#what-you-can-query}

[ビルド健全性ダッシュボード](https://github.com/tuist/tuist/blob/main/grafana-datasource/src/dashboards/build-health.json)をインポートし、データソースとプロジェクトを選択します。これには、ビルド数、成功率、中央値および90パーセンタイル時間、低速ビルドのしきい値、中立的な失敗または低速ビルドの数、グループ化されたキャッシュ節約と報告カバレッジ、および3つの失敗とワークロードのテーブルが含まれます。必要に応じて、他の利用可能なメトリクスのパネルを追加してください。自動低速しきい値は、選択した期間自体の90パーセンタイルです。それを超えるビルドが必ずしも回帰を示すわけではありません。時間目標のアラートには固定しきい値を設定してください。キャッシュパネルは、Gradle の自動累積タスク時間推定値とそのカバレッジを優先し、次に明示的に報告された経過時間の節約とそのカバレッジを表示します。

## ビルドシステム {#build-systems}

ビルド健全性クエリと標準ダッシュボードは、Bazel、Cargo、Struo、Gradle、および Xcode をサポートしています。Tuist はプロジェクトからビルドシステムを選択します。混合プロジェクトは、現在ビルド健全性クエリまたは標準ダッシュボードではサポートされていません。

| ビルドシステム | ワークロード | キャンセル報告 | キャッシュによる節約 |
| --- | --- | --- | --- |
| Bazel | コマンド | 終了コード 8（`run` を除く） | カスタムメタデータが必要 |
| Cargo | コマンド | 区別されません。カウントはゼロです。 | 経過時間の節約にはカスタムメタデータが必要です。コンパイラの作業回避は経過時間の節約ではありません。 |
| Struo | コマンド種別 | 記録されたキャンセル理由 | 記録されません |
| Gradle | タスクグループ | 報告されたキャンセル | 自動的な作業回避推定値。経過時間の節約にはカスタムメタデータが必要です。 |
| Xcode | スキーム | 区別されません。カウントはゼロです。 | カスタムメタデータが必要 |

処理中のレコードと未完了の実行は除外されます。Bazel には、ビルド、テスト、実行、およびカバレッジのコマンドが含まれます。Struo には、確定したビルド、テスト、および一般的な実行が含まれます。Cargo には、`build`、`check`、`test-build` などのビルドコマンドが含まれます。レガシーなテスト実行レポートはビルド健全性から除外されます。Cargo の最近の失敗は、利用可能な場合は記録された開始時間を使用し、そうでない場合は挿入時間にフォールバックします。欠落している継続時間はゼロではなく、利用不可のままとなります。

Gradle は、優先順位の高い順に、計装テスト、ユニットテスト、リント/チェック、アセンブル/パッケージ、その他としてタスクをグループ化します。各ビルドは1つのワークロードに属します。カスタムメタデータを使用して、Xcode、Bazel、Cargo、および Gradle のワークロードを上書きできます。

### 失敗カテゴリ

| カテゴリ | 意味 | 記録された証拠 |
| --- | --- | --- |
| `verification` | コードのコンパイル、リンク、テスト、またはチェックが失敗しました。 | Gradle の検証またはコンパイル例外および既知の失敗したタスクタイプ。Xcode のコンパイラおよびリンカーの問題。Bazel の構造化された非ゼロのコンパイラ/テストアクション結果。Cargo で記録された失敗した rustc コンパイル。Struo のテスト失敗、またはコンパイル、リンク、テスト、リント、チェックとして明示的に宣言された失敗したアクション。 |
| `infrastructure_tooling` | ツール、依存関係、または環境の失敗により、ビルドを正常に実行できませんでした。 | Gradle の構成、依存関係解決、入出力、またはメモリの失敗。Bazel の構造化されたインフラストラクチャの失敗および [文書化された終了コード](https://bazel.build/run/scripts)。Struo のインフラストラクチャアクションエラー。 |
| `unknown` | レポートには、失敗を分類するための十分な証拠が含まれていません。 | 任意のコマンド、欠落している診断情報、構造化された証拠のない古いレポート。 |

ビルドスクリプトのエラーを含む Gradle の構成フェーズの失敗は、タスクの実行が進められなかったため、インフラストラクチャ/ツール配下にグループ化されます。

明示的なカテゴリメタデータや記録された失敗した rustc コンパイルのない Cargo の失敗は `unknown` のままです。`check` または `test-build` コマンドの失敗だけでは、検証失敗とはみなされません。Cargo のタスク再利用カウンターと推定されたコンパイラ作業回避は、経過キャッシュ節約も Gradle の累積タスク時間メトリックも提供しません。

明示的な `tuist.failure_category` メタデータは自動分類を上書きします。それ以外の場合、ビルド内で両方が発生した場合、インフラストラクチャの証拠が検証よりも優先されます。失敗した任意のスクリプトは、コンパイラまたはテストの失敗とはみなされません。履歴レポートは Tuist がすでに保存している証拠を使用できますが、新しいレポーターフィールドは欠落している情報を後付けしません。自動レポーターメタデータは、既存の20エントリのカスタムメタデータ制限内の利用可能なスペースを使用します。

`buildFailureReasons` レスポンスは互換性のために `all` 行を保持します。標準ダッシュボードは、その合計を「失敗カテゴリ」チャートからフィルタリングし、総失敗数を別に表示します。レガシーな `gradleFailureReasons` クエリは、元の3つのカテゴリ行を保持します。

## クエリオプション {#query-options}

数値クエリはこれらの `queryType` 値を使用します。

| クエリ | クエリタイプ |
| --- | --- |
| ビルド健全性 | `buildHealth` |
| Xcode ビルド時間 | `buildDuration` |
| テスト時間 | `testDuration` |

`resultMode` フィールドは、結果の返し方を制御します。

| 結果 | 値 | 動作 |
| --- | --- | --- |
| 時系列 | `series` | 各間隔の値。 |
| 全期間 | `total` | 範囲内のすべての実行から計算された単一の値。 |

フィルターラベルは、次のクエリフィールドに対応します。

| フィルター | クエリフィールド | 利用可能なクエリ |
| --- | --- | --- |
| 環境 | `environment` | すべてのクエリ |
| ブランチ | `gitBranch` | ビルド健全性クエリとテーブル |
| ワークロード | `workload` | ビルド健全性クエリとテーブル |
| ステータス | `status` | ビルド健全性クエリ、テーブル、および Xcode ビルド時間 |
| スキーム | `scheme` | Xcode ビルド時間とテスト時間 |
| 構成 | `configuration` | Xcode ビルド時間 |
| ビルドタイプ | `category` | Xcode ビルド時間 |

環境の値は `any`、`ci`（自動ビルド）、および `local` です。ステータスの値は `success`、`failure`、およびビルド健全性クエリの場合は `cancelled` です。値を省略すると、すべてのステータスが含まれます。ビルドタイプの値は `clean` と `incremental` です。値を省略すると、両方が含まれます。

空のビルド健全性間隔は、カウントがゼロで、平均時間、時間のパーセンタイル、または成功率の値はありません。低速ビルドのしきい値は、選択された全範囲を引き続き使用します。別個のテスト時間クエリは、空の時系列間隔に対してゼロを返します。全期間のパーセンタイルは、間隔のパーセンタイルではなく、実行から計算されます。ビルド健全性のパーセンタイルは正確な集計を使用します。別個の Xcode およびテスト時間クエリは近似パーセンタイルを使用します。

ビルド健全性の時系列は、選択された範囲の開始時に部分的な最初のバケットを配置し、表示されるようにします。レガシーな Gradle クエリは、元のバケットタイムスタンプを保持します。

すべてのクエリは、最大 366 日の日付範囲を受け入れます。境界とタイムスタンプは異なります。

| クエリ | 使用されるタイムスタンプ | 範囲の境界 |
| --- | --- | --- |
| ビルド健全性: Xcode、Bazel、Cargo、Gradle | 記録挿入時間 | 開始を含み、終了を除外 |
| ビルド健全性: Struo | 実行開始時間 | 開始を含み、終了を除外 |
| Xcode ビルド時間 | 記録挿入時間 | 開始と終了を除外 |
| テスト時間 | 記録された実行時間 | 開始と終了を含む |

### ダッシュボード変数

プロジェクトおよびサポートされているフィルターにダッシュボード変数を使用します。ブランチとワークロードの変数は、次のクエリを使用します。

| 変数 | クエリ |
| --- | --- |
| ブランチ | `buildBranches account/project` |
| ワークロード | `buildWorkloads account/project` |

フィルターは単一の正確な値を受け入れます。ブランチとワークロードの変数については、「すべて」オプションのカスタム値を `__tuist_all__` に設定してください。他のフィルターは、組み込みの「任意」オプションまたは空の値を使用します。複数選択や正規表現はサポートされていません。

## カスタムメタデータの報告 {#custom-metadata}

Xcode、Bazel、Cargo、および Gradle ビルドは、次のオプションのメタデータ値を受け入れます。

| キー | 受け入れられる値 |
| --- | --- |
| `tuist.workload` | デフォルトのグループ化を置き換えるワークロード名。 |
| `tuist.failure_category` | `verification` または `infrastructure_tooling`。 |
| `tuist.cache_work_avoided_ms` | Gradle のみ。自動的に報告される作業回避の推定値（整数ミリ秒、最大365日）。 |
| `tuist.cache_time_saved_ms` | 0 から 31,536,000,000（365日）までの整数ミリ秒。 |

ビルド統合のカスタムメタデータ構成を通じてこれらを指定します。

```json
{
  "custom_metadata": {
    "values": {
      "tuist.workload": "Release verification",
      "tuist.failure_category": "verification",
      "tuist.cache_time_saved_ms": "12000"
    }
  }
}
```

そのビルドの経過時間測定値または文書化された推定値がある場合にのみ、キャッシュの節約を報告してください。タスクが並行して実行される場合、キャッシュヒットと累積タスク時間だけでは経過した節約時間を決定できません。欠落しているキャッシュ節約は不明のままです。欠落している失敗カテゴリのメタデータは、[ビルドシステム](#build-systems) で説明されているように、記録された証拠にフォールバックします。データ保持ポリシーは変更されません。

## アラートと Slack {#alerts-and-slack}

数値メトリクスを使用して Grafana 管理のアラートルールを作成します。例：

| メトリクス | 識別子 | 条件の例 |
| --- | --- | --- |
| ビルド成功率 | `success_rate` | 99% 未満 |
| 失敗したビルド | `failed_builds` | ゼロより大きい |
| 90パーセンタイル時間 | `p90` | チームの時間制限を超える |

評価ウィンドウ内の単一値を取得するには **全期間** を使用するか、時系列を単一値に集約します。全期間モードの時間クエリの場合は、1つのシリーズを選択してください。

- 固定されたプロジェクトとフィルターの値を使用してください。バックグラウンドのアラート評価中はダッシュボード変数を使用できません。
- アラートには数値クエリを使用してください。ワークロードを監視するには、ビルド健全性クエリをそのワークロードにフィルターかけます。
- ビルドや報告されたキャッシュ節約がない間隔に対するルールの「データなし」動作を設定してください。

[Slack コンタクトポイント](https://grafana.com/docs/grafana/latest/alerting/configure-notifications/manage-contact-points/integrations/configure-slack/) を構成し、Grafana の通知ポリシーを通じてルールをそこにルーティングします。Grafana が通知を送信し、Slack 認証情報を保存します。

## 既存のダッシュボードのアップグレード {#upgrading}

既存の時間パネルは、クエリ、フィルター、シリーズ名、および単位を保持します。保存された Gradle 健全性パネルと変数も引き続き機能します。

共有ビルド健全性クエリを使用するには、標準ダッシュボードを個別にインポートしてください。既存のダッシュボードは自動的に移行されません。共有クエリには、ビルド健全性エンドポイントを提供する Tuist サーバーが必要です。既存の時間クエリは、古いサーバーでも引き続き機能します。

## 要件 {#requirements}

- Grafana 10.4 以降。
- チャート化したいプロジェクトとメトリクスを読み取る権限を持つ Tuist トークン。以下の [認証](#authentication) を参照してください。

## 認証 {#authentication}

ダッシュボードとバックグラウンドのアラート評価には <.localized_link href="/guides/server/authentication#account-tokens">アカウントトークン</.localized_link> を使用してください。ビルドメトリクスには `project:builds:read`、テスト時間には `project:tests:read` を付与し、チャート化したいプロジェクトへのアクセスを制限してください。使用するメトリクスのスコープのみが必要です。<.localized_link href="/guides/server/authentication#creating-an-account-token">トークン作成手順</.localized_link> に従って生成してください。

この統合は、既存のプロジェクトトークンをそのプロジェクト向けに受け入れ、またユーザーの読み取り権限を持つ <.localized_link href="/guides/server/authentication#as-a-user">ユーザーアクセストークン</.localized_link> も受け入れます。ユーザーアクセストークンは短寿命です。Grafana は提供されたトークンを保存しますが、更新したりローカルの Tuist ログインを再利用したりしません。有効期限が切れたら交換してください。アカウントトークンを使用すると、ユーザーのログインセッションとは独立して、プロジェクトへのアクセス、権限、および有効期限を制御できます。

## 設定 {#configuration}

データソースを追加し、以下を設定します：

| フィールド | 保存される設定 | 備考 |
| --- | --- | --- |
| サーバー URL | `jsonData.url` | デフォルトは `https://tuist.dev` です。 |
| トークン | `secureJsonData.apiToken` | Tuist ベアラートークン（暗号化されて保存されます）。 |

**保存＆テスト** を選択して接続を確認してください。Grafana はアクセス可能なプロジェクトを一覧表示し、最初のプロジェクトに対してビルドおよびテストの読み取り権限をチェックします。

## インストール {#installation}

### Grafana カタログから {#from-the-grafana-catalog}

公開されると、**Connections → Add new connection → Tuist** から他のデータソースと同様にインストールするか、`grafana-cli plugins install tuist-metrics-datasource` でインストールできます。

### 公開前（セルフホスト型 Grafana） {#before-it-is-published-self-hosted-grafana}

プラグインはカタログで承認されるまで署名されていません。セルフホスト型インスタンスでは、次のいずれかを行います：

- **署名なしで許可** — `allow_loading_unsigned_plugins` に `tuist-metrics-datasource` を追加し（または `GF_PLUGINS_ALLOW_LOADING_UNSIGNED_PLUGINS=tuist-metrics-datasource`）、ビルドされたプラグインを plugins ディレクトリに配置します。
- インスタンス用に **プライベートに署名** する — `npm run sign -- --rootUrls https://grafana.example.com`（URL はインスタンスの `root_url` と一致する必要があります）。その後、zip ファイルを配布します。

[Grafana Cloud ではカタログからのプラグインが必要](https://grafana.com/docs/grafana-cloud/learn-and-build/get-started/learn/find-and-use-plugins/)であり、署名されていないプラグインや手動でアップロードされたプラグインはサポートされません。
