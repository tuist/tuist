# Grafana 統合 {#grafana}

Tuist のデータソースを使用すると、Grafana でビルド、テスト、キャッシュのメトリクス（所要時間、失敗数、キャッシングによって報告された節約時間など）を利用できます。チームが重視するプロジェクトやメトリクスを中心にダッシュボードを構築したり、社内の既存ダッシュボードで Tuist のメトリクスを他のデータソースと組み合わせたりできます。Grafana のアラートルールと通知チャネルを活用し、ビルドの遅延や失敗の増加をチームに通知しましょう。

## 利用可能なメトリクス {#metric-definitions}

表には、読みやすいラベルとそのクエリ識別子が記載されています。ビルド健全性のクエリでは `metric` フィールドの識別子を使用し、ビルドおよびテストの所要時間クエリでは `series` フィールドで `average`、`p50`、`p90`、または `p99` を選択します。

### ビルド数と信頼性

| メトリクス | 識別子 | 測定内容 |
| --- | --- | --- |
| ビルド数 | `builds` | 記録されたビルドの数。 |
| 成功したビルド | `successful_builds` | 正常に完了したビルド。 |
| 失敗したビルド | `failed_builds` | 失敗したビルド。 |
| キャンセルされたビルド | `cancelled_builds` | キャンセルとして記録されたビルド。[ビルドシステムの差異](#build-systems)を参照してください。 |
| ビルド成功率 | `success_rate` | 成功 ÷ (成功 + 失敗) をパーセンテージで表したもの。 |
| 失敗または低速なビルド | `builds_needing_attention` | 失敗または低速なビルドを、ビルドごとに1回カウント。 |

### ビルドおよびテストの所要時間

| メトリクス | 識別子 | 測定内容 |
| --- | --- | --- |
| 平均所要時間 | `average` | 選択した実行の平均所要時間。 |
| 中央値の所要時間 | `p50` | 実行所要時間の50パーセンタイル。 |
| 90パーセンタイルの所要時間 | `p90` | 実行の90%がこの時間以下になる所要時間。 |
| 99パーセンタイルの所要時間 | `p99` | 実行の99%がこの時間以下になる所要時間。 |
| 低速ビルドのしきい値 | `slow_build_threshold` | 90パーセンタイルの所要時間、またはミリ秒単位の固定制限値。 |

テスト所要時間のメトリクスは、Tuist に記録されたテスト実行を使用します。低速ビルドのしきい値はビルドにのみ適用されます。ビルドの所要時間がそのしきい値を超えると、低速と判定されます。キャンセルされたビルドは別途カウントされ、ビルド成功率からは除外されます。

### キャッシュによる節約

| メトリクス | 識別子 | 測定内容 |
| --- | --- | --- |
| 累積タスク時間の節約 (Gradle) | `cache_work_avoided` | キャッシュヒットによって回避された推定タスク実行時間の合計。 |
| 累積タスク時間を報告するビルド | `cache_work_avoided_samples` | 完全な見積もりを持つビルド。 |
| 報告されたキャッシュによる時間節約 | `cache_time_saved` | 報告された経過時間の節約分の合計。 |
| キャッシュによる時間節約を報告するビルド | `cache_time_saved_samples` | 有効な節約値を持つビルド。 |

Gradle プラグインは、ローカルおよびリモートのタスクキャッシュヒットに対して、回避された作業量を自動的に報告します。各キャッシュされたタスクについて、Gradle が保存した元の実行時間からタスクの復元所要時間を差し引き、最小値をゼロとします。ビルドの見積もりはこれらの値を合計したものです。並列タスクは重複する可能性があるため、これは累積タスク時間であり、節約された経過ビルド時間ではありません。最新の状態のタスクやスキップされたタスクは除外されます。

タスクキャッシュヒットのないビルドはゼロを報告します。キャッシュされたタスクのいずれかに元のタイミング情報がない場合、テレメトリが不完全な場合、またはカスタムメタデータマップに空きがない場合、プラグインは見積もりを省略します。古いバージョンのプラグインや他のビルドシステムはこれを報告しません。カバレッジを確認するには、報告数と総ビルド数を比較してください。

報告された経過時間の節約分は `tuist.cache_time_saved_ms` メタデータから取得されます。このメトリクスは自動見積もりとは別に扱われます。

報告するビルドがない場合、キャッシュによる節約には値がありません。Struo は現在この測定値を記録していません。キャッシュヒット率とミス率は、このデータソースでは利用できません。

### テーブル

これらの識別子は、クエリの `queryType` フィールドの値です。

| テーブル | クエリタイプ | 内容 |
| --- | --- | --- |
| ワークロード別の健全性 | `buildWorkloads` | ビルド数、成功率、中央値および90パーセンタイルの所要時間。 |
| 失敗カテゴリ | `buildFailureReasons` | 失敗カテゴリ別のすべての失敗とその数。 |
| 最近の失敗したビルド | `buildRecentFailures` | 最新の100件の失敗。Tuist へのリンク付き。 |

最近の失敗には、開始時間、所要時間、ユーザー、ブランチ、および要求されたタスクが含まれます。失敗カテゴリは `verification`、`infrastructure_tooling`、および `unknown` です。

ワークロードの概要とブランチ/ワークロードの値リストは、最大1000件の値を返します。ビルド健全性の変数クエリは過去90日間を使用します。レガシー Gradle 変数クエリは既存の履歴期間を維持します。Bazel はツールによって報告されたビルドユーザーを表示します。他の統合では、報告資格情報に関連付けられたアカウントを表示します。記録されたユーザーがない場合、過去の Bazel および Struo の実行、ならびにプロジェクト資格情報で報告された Struo の実行は「不明」として表示されます。

ビルド実行の「失敗カテゴリ」フィルターを使用して、一致する失敗を検索してください。カテゴリはビルド詳細に表示され、その意味を説明する情報ヒントが付いています。デフォルトの概要およびビルド実行テーブルは既存の列を維持します。成功、キャンセル、および未完了のビルドには失敗カテゴリがありません。Gradle のキャッシュ分析カードとビルド詳細には「累積タスク時間の節約」が表示され、ツールチップで見積もりと並列タスクの影響について説明しています。キャッシュウィジェットは、同じフィルターを使用して、選択した範囲を直前の同等の期間と比較します。比較は中立的です。合計値が大きくなるのは、ビルド数が増加していることを反映している可能性があります。以前の見積もりがない場合は比較が表示されません。記録されたゼロのベースラインの場合、パーセンテージではなく絶対的な増加量が表示されます。

## 標準ダッシュボード {#what-you-can-query}

[ビルド健全性ダッシュボード](https://github.com/tuist/tuist/blob/main/grafana-datasource/src/dashboards/build-health.json)をインポートし、データソースとプロジェクトを選択してください。ビルド数、成功率、中央値および90パーセンタイルの所要時間、低速ビルドのしきい値、中立的な失敗または低速ビルドの数、グループ化されたキャッシュ節約と報告カバレッジ、および3つの失敗およびワークロードテーブルが含まれています。必要に応じて、他の利用可能なメトリクスのパネルを追加してください。自動低速しきい値は、選択した期間自体の90パーセンタイルです。これを超えるビルドが必ずしも回帰を示すわけではありません。所要時間ターゲットのアラートには固定しきい値を設定してください。キャッシュパネルは、Gradle の自動累積タスク時間見積もりとそのカバレッジを優先し、その後に明示的に報告された経過時間の節約とそのカバレッジを表示します。

## ビルドシステム {#build-systems}

ビルド健全性クエリと標準ダッシュボードは、Bazel、Cargo、Struo、Gradle、および Xcode をサポートしています。Tuist はプロジェクトからビルドシステムを選択します。混合プロジェクトは、現在ビルド健全性クエリまたは標準ダッシュボードではサポートされていません。

| ビルドシステム | ワークロード | キャンセル報告 | キャッシュによる節約 |
| --- | --- | --- | --- |
| Bazel | コマンド | 終了コード 8（`run` を除く） | カスタムメタデータが必要 |
| Cargo | コマンド | 区別されません。カウントはゼロです。 | 経過時間の節約にはカスタムメタデータが必要です。コンパイラの作業回避は経過時間の節約ではありません。 |
| Struo | コマンドの種類 | 記録されたキャンセル理由 | 記録されていません |
| Gradle | タスクグループ | 報告されたキャンセル | 自動的な作業回避見積もり。経過時間の節約にはカスタムメタデータが必要です。 |
| Xcode | スキーム | 区別されません。カウントはゼロです。 | カスタムメタデータが必要 |

処理中のレコードと未完了の実行は除外されます。Bazel はビルド、テスト、実行、およびカバレッジのコマンドを含みます。Struo は最終化されたビルド、テスト、および一般的な実行を含みます。Cargo は `build`、`check`、`test-build` などのビルドコマンドを含みます。レガシーなテスト実行レポートはビルド健全性から除外されます。Cargo の最近の失敗は、利用可能な場合は記録された開始時間を使用し、利用できない場合は挿入時間にフォールバックします。欠落している所要時間はゼロではなく、利用不可のままとなります。

Gradle はタスクを、優先順位の高い順に、計装テスト、ユニットテスト、リント/チェック、アセンブル/パッケージ、その他としてグループ化します。各ビルドは1つのワークロードに属します。カスタムメタデータを使用して、Xcode、Bazel、Cargo、および Gradle のワークロードを上書きできます。

### 失敗のカテゴリ

| カテゴリ | 意味 | 記録された証拠 |
| --- | --- | --- |
| `verification` | コードのコンパイル、リンク、テスト、またはチェックが失敗しました。 | Gradle の検証またはコンパイル例外、既知の失敗したタスクタイプ。Xcode のコンパイラおよびリンカーの問題。Bazel の構造化された非ゼロのコンパイラ/テストアクション結果。Cargo で記録された rustc コンパイルの失敗。Struo のテスト失敗、またはコンパイル、リンク、テスト、リント、チェックとして明示的に宣言された失敗したアクション。 |
| `infrastructure_tooling` | ツール、依存関係、または環境の失敗により、ビルドを正常に実行できませんでした。 | Gradle の設定、依存関係の解決、入出力、またはメモリの失敗。Bazel の構造化されたインフラストラクチャの失敗および [文書化された終了コード](https://bazel.build/run/scripts)。Struo のインフラストラクチャアクションエラー。 |
| `unknown` | レポートには、失敗を分類するのに十分な証拠が含まれていません。 | 任意のコマンド、欠落している診断情報、構造化された証拠のない古いレポート。 |

Gradle の設定フェーズでの失敗（ビルドスクリプトのエラーを含む）は、タスクの実行が進められなかったため、インフラストラクチャ/ツール配下にグループ化されます。

明示的なカテゴリメタデータまたは記録された rustc コンパイルの失敗がない Cargo の失敗は `unknown` のままです。`check` または `test-build` コマンドの失敗だけでは、検証失敗とはみなされません。Cargo のタスク再利用カウンターと推定されるコンパイラ作業回避量は、経過キャッシュ節約量や Gradle の累積タスク時間メトリクスを提供することはありません。

明示的な `tuist.failure_category` メタデータは自動分類を上書きします。それ以外の場合、ビルド内で両方が発生した場合、インフラストラクチャの証拠が検証よりも優先されます。失敗した任意のスクリプトは、コンパイラまたはテストの失敗とはみなされません。履歴レポートは Tuist がすでに保存している証拠を使用できますが、新しいレポーターフィールドは欠落している情報を後付けしません。自動レポーターメタデータは、既存の20エントリのカスタムメタデータ制限内の利用可能なスペースを使用します。

`buildFailureReasons` レスポンスは互換性のために `all` 行を保持します。標準ダッシュボードは、その合計を「失敗のカテゴリ」チャートから除外し、総失敗数を別に表示します。レガシーな `gradleFailureReasons` クエリは、元の3つのカテゴリ行を保持します。

## クエリオプション {#query-options}

数値クエリはこれらの `queryType` 値を使用します。

| クエリ | クエリタイプ |
| --- | --- |
| ビルド健全性 | `buildHealth` |
| Xcode ビルド所要時間 | `buildDuration` |
| テスト所要時間 | `testDuration` |

`resultMode` フィールドは、結果の返却方法を制御します。

| 結果 | 値 | 動作 |
| --- | --- | --- |
| 時系列 | `series` | 各間隔ごとの値。 |
| 全期間 | `total` | 範囲内のすべての実行から計算された単一の値。 |

フィルターラベルは、以下のクエリフィールドに対応します。

| フィルター | クエリフィールド | 適用対象 |
| --- | --- | --- |
| 環境 | `environment` | すべてのクエリ |
| ブランチ | `gitBranch` | ビルド健全性クエリとテーブル |
| ワークロード | `workload` | ビルド健全性クエリとテーブル |
| ステータス | `status` | ビルド健全性クエリ、テーブル、および Xcode 所要時間 |
| スキーム | `scheme` | Xcode ビルドおよびテスト所要時間 |
| 構成 | `configuration` | Xcode ビルド所要時間 |
| ビルドタイプ | `category` | Xcode ビルド所要時間 |

環境の値は `any`、`ci`（自動ビルド）、および `local` です。ステータスの値は `success`、`failure`、およびビルド健全性クエリの場合は `cancelled` です。値を省略すると、すべてのステータスが含まれます。ビルドタイプの値は `clean` と `incremental` です。値を省略すると、両方が含まれます。

空のビルド健全性間隔は、カウントがゼロであり、平均所要時間、所要時間のパーセンタイル、または成功率の値を持ちません。低速ビルドのしきい値は、選択された全範囲を使用します。個別のテスト所要時間クエリは、空の時系列間隔に対してゼロを返します。全期間のパーセンタイルは、間隔のパーセンタイルではなく、実行から計算されます。ビルド健全性のパーセンタイルは正確な集計を使用しますが、個別の Xcode およびテスト所要時間クエリは近似パーセンタイルを使用します。

ビルド健全性の時系列は、選択された範囲の開始位置に部分的な最初のバケットを配置し、可視性を維持します。レガシーな Gradle クエリは、元のバケットタイムスタンプを保持します。

すべてのクエリは最大366日間の日付範囲を受け入れます。境界とタイムスタンプは異なります。

| クエリ | 使用されるタイムスタンプ | 範囲の境界 |
| --- | --- | --- |
| ビルド健全性: Xcode、Bazel、Cargo、Gradle | レコード挿入時間 | 開始を含む、終了を除外 |
| ビルド健全性: Struo | 実行開始時間 | 開始を含む、終了を除外 |
| Xcode ビルド所要時間 | レコード挿入時間 | 開始と終了を除外 |
| テスト所要時間 | 記録された実行時間 | 開始と終了を含む |

### ダッシュボード変数

プロジェクトおよびサポートされているフィルターにはダッシュボード変数を使用します。ブランチとワークロードの変数は、以下のクエリを使用します。

| 変数 | クエリ |
| --- | --- |
| ブランチ | `buildBranches account/project` |
| ワークロード | `buildWorkloads account/project` |

フィルターは1つの正確な値を受け入れます。ブランチおよびワークロード変数の場合、[すべて] オプションのカスタム値を `__tuist_all__` に設定してください。他のフィルターは、組み込みの [任意] オプションまたは空の値を使用します。複数選択や正規表現はサポートされていません。

## カスタムメタデータのレポート {#custom-metadata}

Xcode、Bazel、Cargo、および Gradle のビルドは、以下のオプションのメタデータ値を受け入れます。

| キー | 許可される値 |
| --- | --- |
| `tuist.workload` | デフォルトのグループ化を置き換えるワークロード名。 |
| `tuist.failure_category` | `verification` または `infrastructure_tooling`。 |
| `tuist.cache_work_avoided_ms` | Gradle のみ。自動的にレポートされる作業回避見積もり（整数ミリ秒、最大365日）。 |
| `tuist.cache_time_saved_ms` | 0 から 31,536,000,000（365日）までの整数ミリ秒。 |

ビルド統合のカスタムメタデータ構成を通じてこれらを指定します。

```json
{
  "custom_metadata": {
    "values": {
      "tuist.workload": "Release verification",
      "tuist.failure_category": "verification",
      "tuist.cache_time_saved_ms": "12000"
    }
  }
}
```

経過時間の測定値またはそのビルドの文書化された見積もりがある場合にのみ、キャッシュ節約をレポートしてください。タスクが並行して実行される場合、キャッシュヒットと累積タスク所要時間だけでは経過した節約時間を特定できません。欠落しているキャッシュ節約情報は不明のままです。欠落している失敗カテゴリのメタデータは、[ビルドシステム](#build-systems) で説明されているように、記録された証拠にフォールバックします。データ保持ポリシーは変更されません。

## アラートと Slack {#alerts-and-slack}

数値メトリックを使用して Grafana 管理のアラートルールを作成します。例：

| メトリック | 識別子 | 条件の例 |
| --- | --- | --- |
| ビルド成功率 | `success_rate` | 99% 未満 |
| 失敗したビルド | `failed_builds` | 0 より大きい |
| 90パーセンタイル所要時間 | `p90` | チームの所要時間制限を超える |

評価ウィンドウ内の単一値を取得するには **全期間** を使用するか、時系列を単一値に集約します。全期間モードでの所要時間クエリの場合、1つのシリーズを選択してください。

- 固定されたプロジェクトおよびフィルター値を使用してください。バックグラウンドのアラート評価中はダッシュボード変数を利用できません。
- アラートには数値クエリを使用してください。ワークロードを監視するには、ビルド健全性クエリをそのワークロードにフィルターしてください。
- ビルドや報告されたキャッシュ節約がない間隔に対するルールの「データなし」動作を設定してください。

[Slack 連絡先ポイント](https://grafana.com/docs/grafana/latest/alerting/configure-notifications/manage-contact-points/integrations/configure-slack/) を構成し、Grafana の通知ポリシーを通じてルールをそこにルーティングします。Grafana が通知を送信し、Slack 認証情報を保存します。

## 既存のダッシュボードのアップグレード {#upgrading}

既存の所要時間パネルは、クエリ、フィルター、シリーズ名、および単位を保持します。保存された Gradle 健全性パネルと変数も引き続き機能します。

共有ビルド健全性クエリを使用するには、標準ダッシュボードを個別にインポートしてください。既存のダッシュボードは自動的に移行されません。共有クエリには、ビルド健全性エンドポイントを提供する Tuist サーバーが必要です。既存の所要時間クエリは、古いサーバーでも引き続き機能します。

## 要件 {#requirements}

- Grafana 10.4 以降。
- チャート表示したいプロジェクトとメトリックを読み取る権限を持つ Tuist トークン。以下の [認証](#authentication) を参照してください。

## 認証 {#authentication}

ダッシュボードとバックグラウンドのアラート評価には <.localized_link href="/guides/server/authentication#account-tokens">アカウントトークン</.localized_link> を使用してください。ビルドメトリックには `project:builds:read`、テスト所要時間には `project:tests:read` を付与し、チャート表示したいプロジェクトへのアクセスを制限してください。使用するメトリックに必要なスコープのみが必要です。<.localized_link href="/guides/server/authentication#creating-an-account-token">トークン作成手順</.localized_link> に従って生成してください。

この統合は、既存のプロジェクトトークンをそのプロジェクトに対して、およびユーザーの読み取り権限を持つ <.localized_link href="/guides/server/authentication#as-a-user">ユーザーアクセストークン</.localized_link> も受け入れます。ユーザーアクセストークンは有効期限が短いです。Grafana は提供されたトークンを保存しますが、更新したりローカルの Tuist ログインを再利用したりしません。有効期限が切れたら交換してください。アカウントトークンを使用すると、ユーザーのログインセッションとは独立して、プロジェクトへのアクセス、権限、有効期限を制御できます。

## 設定 {#configuration}

データソースを追加して以下を設定します：

| フィールド | 保存される設定 | 注記 |
| --- | --- | --- |
| サーバー URL | `jsonData.url` | デフォルトは `https://tuist.dev` です。 |
| トークン | `secureJsonData.apiToken` | Tuist ベアラートークン（暗号化されて保存されます）。 |

**Save & test** を選択して接続を確認してください。Grafana はアクセス可能なプロジェクトを一覧表示し、最初のプロジェクトに対してビルドおよびテストの読み取り権限をチェックします。

## インストール {#installation}

### Grafana カタログから {#from-the-grafana-catalog}

公開されると、**Connections → Add new connection → Tuist** から他のデータソースと同様にインストールするか、`grafana-cli plugins install tuist-metrics-datasource` でインストールできます。

### 公開前（セルフホスト型 Grafana） {#before-it-is-published-self-hosted-grafana}

プラグインはカタログで承認されるまで署名されていません。セルフホスト型インスタンスでは、次のいずれかを実行できます：

- **署名なしで許可** — `tuist-metrics-datasource` を `allow_loading_unsigned_plugins` （または `GF_PLUGINS_ALLOW_LOADING_UNSIGNED_PLUGINS=tuist-metrics-datasource`）に追加し、ビルド済みプラグインをプラグインディレクトリに配置します。
- インスタンス用に **プライベート署名** する — `npm run sign -- --rootUrls https://grafana.example.com` （URL はインスタンスの `root_url` と一致する必要があります）、その後 zip を配布します。

[Grafana Cloud ではカタログからのプラグインが必要](https://grafana.com/docs/grafana-cloud/learn-and-build/get-started/learn/find-and-use-plugins/) であり、署名されていないプラグインや手動でアップロードされたプラグインはサポートされません。
