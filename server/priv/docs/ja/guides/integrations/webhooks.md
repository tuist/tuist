# Webhook {#webhooks}

Webhook を使えば、Tuist 内で変更が発生した瞬間にシステムが反応できます。関連するイベント（新しいテストケースの検出、プレビューのアップロード完了、flaky テストの是正など）が発生すると、Tuist はそのイベントタイプを購読しているすべてのエンドポイントに HTTP POST リクエストを送信します。リクエストボディは JSON エンベロープであり、各配信にはエンドポイントの署名シークレットで検証できる署名ヘッダーが付与されます。

宛先 URL を登録し、必要なイベントを選択すれば、署名、再試行、配信監査ログの管理は Tuist が行います。

## Webhook 受信の手順 {#steps}

以下の手順で、アプリでのイベント通知受信を開始できます。

1. [アプリケーションが受信したいイベントを特定](#event-types)します。
2. ローカルサーバー上に HTTP エンドポイント（URL）として [Webhook エンドポイントを作成](#create-an-endpoint)します。
3. [ペイロードを解析](#payload)し、[2xx ステータス](#responding)を返すことで Tuist からのリクエストを処理し、配信を成功としてマークさせます。
4. Tuist からのリクエストであることを証明するため、すべてのリクエストで [署名を検証](#verify-signature)します。
5. 構築中にデバッグを行う際は、Tuist ダッシュボードの [イベントログ](#inspect-deliveries) を活用してください。

## イベントタイプ {#event-types}

Tuist は、イベントが記述するリソースごとにイベントをグループ化します。エンベロープ内の `type` フィールドはドット表記（`{resource}.{action}`）を使用しており、ダッシュボードで購読する値と同じ形式です。

## エンドポイントの作成 {#create-an-endpoint}

エンドポイントはアカウントごとに設定します。アカウント設定から **Webhooks** を開き、**Add endpoint** をクリックして、以下を入力してください。

- **Name** — リスト表示でエンドポイントが表示される名前。
- **Endpoint URL** — `https://` を使用する必要があります。
- **Events to listen for** — 特定のイベントを選択するか、グループレベルで **Select all** を使用します。Tuist は、購読したイベントのいずれかが発生した場合のみ、エンドポイントに POST します。

![それぞれ 2 つのイベントを購読した 2 つの Webhook エンドポイントを含む Endpoints リスト](/images/guides/integrations/webhooks/endpoints.png)

保存すると、Tuist は新しい署名シークレットを生成し、一度だけ表示します。すぐにアプリケーションの設定にコピーしてください。ダッシュボードから再度取得することはできません。シークレットを紛失した場合は、エンドポイントのアクションメニューで **Rotate secret** を使用して新しいシークレットを発行してください。

## ペイロード {#payload}

各配信は単一の JSON オブジェクトです。エンベロープは、配信の重複排除、ルーティング、監査に使用できるメタデータ内に、イベント固有のリソーススナップショットを包みます。

| フィールド     | 説明                                                              |
| --------- | ------------------------------------------------------------------------ |
| `id`      | この配信に固有の UUID。再試行時に重複排除に使用します。 |
| `type`    | ドット表記のイベントタイプ（例: `test_case.updated`）。                         |
| `created` | Tuist が配信をキューに追加した時点の Unix タイムスタンプ（秒）。           |
| `object`  | リソーススナップショット。形状はイベントタイプによって異なります。              |

各イベントタイプの正確なペイロードスキーマは、[Tuist API リファレンス](https://tuist.dev/api/docs#section/Webhook-events) の **Webhook events** セクションに記載されています。すべてのイベントには `components.schemas` 下に一致する `WebhookXxxEvent` スキーマがあり、コードジェネレーターから `$ref` できます。

例えば `test_case.updated` ペイロードには、書き込みを引き起こした標準的な遷移（`marked_flaky`、`muted`、`unskipped` など）をリストする `events` 配列に加え、受信側が手動編集と自動化による変更を区別できるように `actor_id` と `alert_id` も含まれます。

各リクエストには以下の HTTP ヘッダーも含まれます。

| ヘッダー              | 説明                                                                                   |
| ------------------- | --------------------------------------------------------------------------------------------- |
| `Content-Type`      | 常に `application/json`。                                                                    |
| `User-Agent`        | `Tuist-Webhooks/1.0`.                                                                         |
| `Tuist-Event-Id`    | ボディ内の `id` と同じ UUID。ペイロードを解析する前にヘッダーをログ記録する場合に便利です。     |
| `Tuist-Event-Type`  | ボディ内の `type` と同じ文字列。                                                            |
| `Tuist-Signature`   | HMAC-SHA256 署名。`t={timestamp},v1={hex_digest}` 形式でフォーマットされます。詳細は下記参照。          |

## Webhook への応答 {#responding}

配信を確認するには、エンドポイントから任意の `2xx` ステータスコードを返す必要があります。`2xx` 範囲外のステータス、接続失敗、タイムアウトは配信失敗として扱われ、再試行されます。Tuist は `3xx` レスポンスを追従しないため、リダイレクトせず正規の URL で直接応答してください。

ハンドラーは**高速に**保ってください。Tuist はレスポンスを最大 **10 秒** 待ちます。重い処理（別の API の呼び出し、データベースの更新、通知の送信など）がある場合は、リクエストを受け付けて非同期で処理してください。早期にレスポンスを返すことで、ダウンストリームサービスの一時的な遅延に対する耐性も高まります。

## 署名の検証 {#verify-signature}

エンドポイント URL を知っていれば誰でも POST できます。署名シークレットを使用することで、サーバーは Tuist 以外からのリクエストを拒否できます。

各リクエストに対して、Tuist は以下を計算します。

```
signed_payload = "{timestamp}.{raw_request_body}"
signature      = HMAC-SHA256(signing_secret, signed_payload)
header         = "t={timestamp},v1={hex(signature)}"
```

側で検証するには：

1. `Tuist-Signature` ヘッダーを読み取り、`t=`（タイムスタンプ）と `v1=`（16進ダイジェスト）の部分に分割します。
2. タイムスタンプがサーバーの現在時刻から **5 分** 以上離れている場合はリクエストを拒否してください。これにより再生ウィンドウが*制限*されますが、完全に閉じるわけではありません。下記の冪等性と組み合わせて使用してください。
3. `HMAC-SHA256(signing_secret, "{timestamp}.{raw_body}")` を再計算し、ダイジェストと**定数時間**で比較します。
4. ペイロードの `id`（`Tuist-Event-Id` ヘッダーとしても公開されます）に基づいて配信の重複を排除します。これは再試行間で安定しているため、すでに処理した ID を永続化することで、許容ウィンドウ内でのキャプチャされたリクエストの再生を防ぎ、再試行時の二重処理から保護します。

> [!IMPORTANT] USE THE RAW BODY
> 署名は Tuist が送信したバイト列に対して計算されます。検証前に Web フレームワークが JSON を再解析して再シリアライズすると、ダイジェストが一致しません。生のボディ（例: Rack では `request.body.read`、Express では生の `Buffer`）をキャプチャし、検証器に渡してください。

Node.js 用の参照検証器です。受信側の実装言語に合わせて、同じ 4 つの手順（ヘッダーの解析、タイムスタンプのずれの確認、HMAC の再計算、定数時間での比較）に変換してください。

```javascript
import crypto from "node:crypto";

function verifyTuistSignature(rawBody, header, secret, toleranceSeconds = 300) {
  const parts = Object.fromEntries(
    header.split(",").map((kv) => kv.split("=", 2))
  );
  const timestamp = Number(parts.t);
  const signature = parts.v1;
  if (!timestamp || !signature) return false;

  const drift = Math.abs(Math.floor(Date.now() / 1000) - timestamp);
  if (drift > toleranceSeconds) return false;

  const expected = crypto
    .createHmac("sha256", secret)
    .update(`${timestamp}.${rawBody}`)
    .digest("hex");

  const a = Buffer.from(expected, "hex");
  const b = Buffer.from(signature, "hex");
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}
```

## 再試行 {#retries}

Tuist は、非 `2xx` ステータスを返す配信、タイムアウト、接続失敗を再試行します。スケジュールは固定されています。

| 試行回数 | 送信前の待機時間 |
| ------- | ------------------- |
| 1       | （即時）         |
| 2       | 1 分            |
| 3       | 5 分           |
| 4       | 30 分          |
| 5       | 2 時間             |
| 6       | 8 時間             |
| 7       | 24 時間            |

7 回目の試行が失敗すると、配信は永久に失敗としてマークされます。各試行には送信時のタイムスタンプで署名されているため、再生保護ウィンドウは再試行時にも適用され、広げる必要はありません。

## 配信の検査 {#inspect-deliveries}

**Webhooks** ページからエンドポイントを開き、配信履歴を確認します。詳細ページには以下が表示されます。

- 宛先 URL、マスキングされた署名シークレット、購読中のイベント、作成日を含む**サマリーカード**。
- 選択した時間枠に限定された実行合計と失敗数を表示する**配信チャート**。
- ステータス、イベントタイプ、またはイベント ID でフィルター可能な**イベントテーブル**。

![サマリーカードとイベント配信チャートを表示する Webhook エンドポイントの詳細ページ](/images/guides/integrations/webhooks/endpoint-detail.png)

イベントをクリックすると、その試行からの完全なリクエストとレスポンス（Tuist が送信した正確なペイロード、ヘッダー、アップストリームステータスコード、レスポンスボディ）を確認できます。これはサーバーが見たものと同じデータであり、署名検証の不一致や 5xx アップストリームエラーをデバッグする最も迅速な方法です。

![サマリー、リクエストヘッダーとボディ、およびアップストリームレスポンスを表示する Webhook イベントの詳細ページ](/images/guides/integrations/webhooks/event-detail.png)

配信記録は無期限に保持されるため、統合のデバッグ時に遡って確認できます。ダウンストリームシステムで耐久性のあるコピーが必要な場合（例: コンプライアンスのため）、到着時に独自のインフラストラクチャで配信をキャプチャしてください。

## エンドポイントのシークレット回転または削除 {#rotate-or-delete}

どちらの操作も、エンドポイント行のケバブメニューおよびエンドポイントの詳細ページにあります。

- **シークレットを回転** — 新しい署名シークレットを生成し、一度だけ表示します。既存のコンシューマーは更新するまで検証に失敗するため、デプロイに合わせて回転を計画してください。
- **エンドポイントを削除** — エンドポイントを削除し、配信を停止します。すでに記録された配信試行は、標準の保持期間が終了するまで保持されます。

## セキュリティに関する注意事項 {#security}

- エンドポイント URL は HTTPS である必要があります。Tuist はプレーンテキストの宛先への配信を拒否します。
- Tuist は各配信前に宛先ホスト名を解決し、ループバック、RFC1918、リンクローカル、ULA、クラウドメタデータアドレス（`169.254.169.254`、`fd00::/8` など）を拒否します。これにより、誤設定された Webhook が Tuist サーバーを実行しているホストのスキャンや攻撃に使用されるのを防ぎます。
- エンドポイント URL と署名シークレットは保存時に暗号化されます。これらはベアラークレデンシャルとして GDPR/CCPA データエクスポートから除外されます。
- 署名シークレットは一度だけ表示されます。パスワードと同様に扱い、リポジトリではなくシークレットマネージャーに保存してください。
