# Webhook {#webhooks}

Webhookを利用すると、Tuist内部で変更が発生した瞬間にシステムが反応できます。関連するイベント（新しいテストケースの検出、プレビューのアップロード完了、flakyテストの修復など）が発生すると、Tuistはそのイベントタイプをサブスクライブしているすべてのエンドポイントに対してHTTP POSTリクエストを送信します。リクエストボディはJSONエンベロープであり、各配信にはエンドポイントの署名シークレットで検証可能な署名ヘッダーが含まれます。

宛先URLを登録し、必要なイベントを選択すると、Tuistが署名、再試行、配信監査ログの管理を行います。

## Webhookを受信する手順 {#steps}

以下の手順で、アプリでのイベント通知受信を開始できます。

1. [アプリケーションが受信したいイベントを特定](#event-types)します。
2. ローカルサーバー上にHTTPエンドポイント（URL）として[Webhookエンドポイントを作成](#create-an-endpoint)します。
3. [ペイロードを解析](#payload)し、[2xxステータス](#responding)を返すことでTuistからのリクエストを処理し、配信が成功したとマークされるようにします。
4. リクエストごとに[署名を検証](#verify-signature)し、Tuistから送信されたことを証明します。
5. ビルド中にデバッグを行うため、Tuistダッシュボードの[イベントログ](#inspect-deliveries)を使用します。

## イベントタイプ {#event-types}

Tuistは、イベントが記述するリソースごとにイベントをグループ化します。エンベロープ内の`type`フィールドはドット表記（`{resource}.{action}`）を使用しており、これはダッシュボードでサブスクライブする値と同じです。

今後さらに多くのイベントタイプが追加されます。現在発行されていないイベントタイプが必要な場合は、お知らせください。カタログに追加します。

## エンドポイントの作成 {#create-an-endpoint}

エンドポイントはアカウントごとに設定されます。アカウント設定から**Webhooks**を開き、**Add endpoint**をクリックして、以下を入力してください。

- **Name** — リスト内でエンドポイントが表示される名前。
- **Endpoint URL** — `https://`を使用する必要があります。
- **Events to listen for** — 特定のイベントを選択するか、グループレベルで**Select all**を使用します。Tuistは、サブスクライブされたイベントのいずれかが発生した場合のみ、エンドポイントにPOSTリクエストを送信します。

![それぞれ2つのイベントをサブスクライブした2つのWebhookエンドポイントを持つEndpointsリスト](/images/guides/integrations/webhooks/endpoints.png)

保存すると、Tuistは新しい署名シークレットを生成し、一度だけ表示します。すぐにアプリケーションの設定にコピーしてください。ダッシュボードから再度取得することはできません。失った場合は、エンドポイントのアクションメニューで**Rotate secret**を使用して新しいシークレットを発行します。

## ペイロード {#payload}

各配信は単一のJSONオブジェクトです。エンベロープは、配信の重複排除、ルーティング、監査に使用できるメタデータ内にイベント固有のリソーススナップショットを包み込みます。

| フィールド     | 説明                                                              |
| --------- | ------------------------------------------------------------------------ |
| `id`      | この配信に固有のUUID。再試行時に重複排除のために使用します。 |
| `type`    | ドット表記のイベントタイプ（例: `test_case.updated`）。                         |
| `created` | Tuistが配信をキューに追加したUnixタイムスタンプ（秒）。           |
| `object`  | リソーススナップショット。形状はイベントタイプによって異なります。              |

各イベントタイプの正確なペイロードスキーマは、[Tuist APIリファレンス](https://tuist.dev/api/docs#section/Webhook-events)の**Webhook events**セクションに記載されています。すべてのイベントには、`components.schemas`の下に対応する`WebhookXxxEvent`スキーマがあり、コードジェネレーターから`$ref`できます。

例えば、`test_case.updated`ペイロードには、書き込みを引き起こした標準的な遷移（`marked_flaky`、`muted`、`unskipped`、…）をリストする`events`配列に加え、受信者が手動編集と自動化による変更を区別できるように`actor_id`と`alert_id`も含まれます。

各リクエストには以下のHTTPヘッダーも含まれます。

| ヘッダー              | 説明                                                                                   |
| ------------------- | --------------------------------------------------------------------------------------------- |
| `Content-Type`      | 常に`application/json`。                                                                    |
| `User-Agent`        | `Tuist-Webhooks/1.0`.                                                                         |
| `Tuist-Event-Id`    | ボディ内の`id`と同じUUID。ペイロードを解析する前にヘッダーをログ記録する場合に便利です。     |
| `Tuist-Event-Type`  | ボディ内の`type`と同じ文字列。                                                            |
| `Tuist-Signature`   | HMAC-SHA256署名。`t={timestamp},v1={hex_digest}`形式でフォーマットされます。詳細は以下を参照してください。          |

## Webhookへの応答 {#responding}

配信を確認するには、エンドポイントから任意の`2xx`ステータスコードを返す必要があります。`2xx`範囲外のステータスコード、接続失敗、タイムアウトは配信失敗として扱われ、再試行されます。Tuistは`3xx`レスポンスに従わないため、リダイレクトせず、正規のURLで直接応答してください。

ハンドラーは**高速に**処理してください。Tuistはレスポンスを最大**10秒**間待ちます。重い処理（他のAPIの呼び出し、データベースの更新、通知の送信など）がある場合は、リクエストを受け付けて非同期で処理してください。早期にレスポンスを返すことで、下流サービスの一時的な遅延に対する耐性も高まります。

## 署名の検証 {#verify-signature}

エンドポイントURLを知っている anyone はそこにPOSTできます。署名シークレットを使用することで、サーバーはTuist以外からのリクエストを拒否できます。

すべてのリクエストに対して、Tuistは以下を計算します。

```
signed_payload = "{timestamp}.{raw_request_body}"
signature      = HMAC-SHA256(signing_secret, signed_payload)
header         = "t={timestamp},v1={hex(signature)}"
```

側で検証するには:

1. `Tuist-Signature`ヘッダーを読み取り、`t=`（タイムスタンプ）と`v1=`（16進ダイジェスト）の部分に分割します。
2. タイムスタンプがサーバーの現在時刻から**5分**以上離れている場合は、リクエストを拒否してください。これによりリプレイウィンドウが*制限*されますが、完全に閉じるわけではありません。以下の冪等性と組み合わせて使用してください。
3. `HMAC-SHA256(signing_secret, "{timestamp}.{raw_body}")`を再計算し、ダイジェストと**定数時間**で比較します。
4. ペイロードの`id`（`Tuist-Event-Id`ヘッダーとしても公開されています）に基づいて配信の重複を排除します。これは再試行間で安定しているため、すでに処理したIDを永続化することで、許容ウィンドウ内でのキャプチャされたリクエストのリプレイを防ぎ、再試行時の二重処理から保護します。

> [!IMPORTANT] USE THE RAW BODY
> 署名はTuistが送信したバイト列に対して計算されます。検証前にWebフレームワークがJSONを再解析して再シリアル化すると、ダイジェストが一致しません。生のボディ（例: Rackでの`request.body.read`、Expressでの生の`Buffer`）をキャプチャし、検証器に渡してください。

Node.jsでの参照検証器です。受信側の実装言語に合わせて、同じ4つのステップ（ヘッダーの解析、タイムスタンプのずれの確認、HMACの再計算、定数時間での比較）に変換してください。

```javascript
import crypto from "node:crypto";

function verifyTuistSignature(rawBody, header, secret, toleranceSeconds = 300) {
  const parts = Object.fromEntries(
    header.split(",").map((kv) => kv.split("=", 2))
  );
  const timestamp = Number(parts.t);
  const signature = parts.v1;
  if (!timestamp || !signature) return false;

  const drift = Math.abs(Math.floor(Date.now() / 1000) - timestamp);
  if (drift > toleranceSeconds) return false;

  const expected = crypto
    .createHmac("sha256", secret)
    .update(`${timestamp}.${rawBody}`)
    .digest("hex");

  const a = Buffer.from(expected, "hex");
  const b = Buffer.from(signature, "hex");
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}
```

## 再試行 {#retries}

Tuistは、非`2xx`ステータスを返す配信、タイムアウト、または接続失敗した配信を再試行します。スケジュールは固定されています。

| 試行 | 送信前の待機時間 |
| ------- | ------------------- |
| 1       | （即時）         |
| 2       | 1分            |
| 3       | 5分           |
| 4       | 30分          |
| 5       | 2時間             |
| 6       | 8時間             |
| 7       | 24時間            |

7回目の試行が失敗すると、配信は永久に失敗としてマークされます。各試行は送信時のタイムスタンプで署名されているため、再試行時にもリプレイ保護ウィンドウが適用され、広げる必要はありません。

## 配信の検査 {#inspect-deliveries}

**Webhooks**ページからエンドポイントを開き、配信履歴を確認します。詳細ページには以下が表示されます。

- 宛先URL、マスクされた署名シークレット、購読中のイベント、作成日を含む**概要カード**。
- 選択した時間範囲のスコープで、累計と失敗回数を表示する**配信チャート**。
- ステータス、イベントタイプ、またはイベントIDでフィルタリングできる**イベントテーブル**。

![概要カードとイベント配信チャートを表示するWebhookエンドポイントの詳細ページ](/images/guides/integrations/webhooks/endpoint-detail.png)

イベントをクリックすると、その試行からの完全なリクエストとレスポンス（Tuistが送信した正確なペイロード、ヘッダー、上流のステータスコード、レスポンスボディ）を確認できます。これはサーバーが見たものと同じデータであり、署名検証の不一致や5xx上流エラーをデバッグする最速の方法です。

![概要、リクエストヘッダーとボディ、および上流レスポンスを表示するWebhookイベントの詳細ページ](/images/guides/integrations/webhooks/event-detail.png)

配信記録は無期限に保持されるため、統合のデバッグ時に過去を振り返ることができます。下流システムで耐久性のあるコピーが必要な場合（例: コンプライアンスのため）、到着時に独自のインフラストラクチャで配信をキャプチャしてください。

## エンドポイントのシークレット更新または削除 {#rotate-or-delete}

どちらの操作も、エンドポイント行のケバブメニューおよびエンドポイントの詳細ページにあります。

- **シークレットを更新** — 新しい署名シークレットを生成し、一度だけ表示します。既存のコンシューマーは更新するまで検証に失敗するため、デプロイと同時に更新を計画してください。
- **エンドポイントを削除** — エンドポイントを削除し、配信を停止します。すでに記録された配信試行は、標準の保持期間が終了するまで保持されます。

## セキュリティに関する注意事項 {#security}

- エンドポイントURLはHTTPSである必要があります。Tuistはプレーンテキストの宛先への配信を拒否します。
- Tuistは各配信前に宛先ホスト名を解決し、ループバック、RFC1918、リンクローカル、ULA、クラウドメタデータアドレス（`169.254.169.254`、`fd00::/8`、…）を拒否します。これにより、誤って設定されたWebhookがTuistサーバーを実行しているホストのスキャンや攻撃に使用されるのを防ぎます。
- エンドポイントURLと署名シークレットは保存時に暗号化されます。これらはBearerクレデンシャルとしてGDPR/CCPAデータエクスポートから除外されます。
- 署名シークレットは一度だけ表示されます。パスワードと同様に扱い、リポジトリではなくシークレットマネージャーに保存してください。
