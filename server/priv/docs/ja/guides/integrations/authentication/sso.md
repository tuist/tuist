# シングルサインオン {#single-sign-on}

Tuist は、組織のアカウントセキュリティを強化するためのログインオプションとしてシングルサインオンを提供します。

シングルサインオンは、組織設定の **認証** タブから構成します。Google Workspace、Okta、Microsoft Entra ID、およびカスタムの [OAuth 2.0](https://oauth.net/2/) プロバイダーがサポートされています。

Microsoft Entra ID は、ディレクトリ識別子に基づいて Tuist が構成する OpenID Connect プロバイダーです。このガイドでカスタムプロバイダーについて説明している内容（ログイン用メールドメインの検証や登録など）は、すべて Microsoft Entra ID にも適用されます。

> [!NOTE]
> シングルサインオンは、メンバーの認証方法と、認証済みユーザーが自動的に参加できるかどうかを制御します。<.localized_link href="/guides/integrations/authentication/scim">クロスドメインアイデンティティ管理のプロビジョニング</.localized_link> は、アイデンティティプロバイダーが組織メンバーを作成、更新、およびプロビジョニング解除できるかどうかを制御します。Okta では、ほとんどの組織が両方を構成しています。

## アクセスの仕組み {#how-access-works}

プロバイダーのアイデンティティ、ログインの検出、組織への登録は別々の課題です。

- **プロバイダーの発行者:** ユーザーを認証したプロバイダー組織または認可サーバーです。Tuist は、リンクされたアイデンティティを検索する際に、プロバイダー、発行者、および安定したプロバイダーユーザー識別子を組み合わせます。Okta の場合、発行者は Okta ドメインで表されます。Microsoft Entra ID の場合、ディレクトリ（テナント）識別子から派生します。カスタムプロバイダーの場合、プロバイダー URL で表されます。
- **ログイン用メールドメイン:** Tuist が一般的なログインページから Okta またはカスタムプロバイダーを検出するために使用するメールドメインです。検証が完了すると、新しいアカウントのリンクと自動登録で信頼できるメールアドレスも確立されます。
- **登録ポリシー:** 信頼されたドメインのユーザーに招待が必要か、自動的に参加できるかを決定します。
- **プロビジョニング:** ログインフローとは独立して組織メンバーシップを作成および管理します。

プロバイダーの発行者とログイン用メールドメインは異なることがよくあります。たとえば、企業は従業員用のメールに `example.com` を使用し、プロバイダーの発行者は `https://login.vendor.example.net` である場合があります。新しい Okta およびカスタムプロバイダーの構成では、これらの値は個別に保存されます。

### ログイン用メールドメインを検証する {#verify-a-login-email-domain}

Okta およびカスタムプロバイダーの構成では、新しい Tuist アカウントを作成したり、既存のアカウントをメールアドレスでリンクしたりする前に、ログイン用メールドメインの検証が必要です。ドメインが未検証の間でも、メンバーは <.localized_link href="/guides/integrations/authentication/sso#link-an-existing-account">既存のアカウントをリンク</.localized_link> できます。

1. **ログイン用メールドメイン** に、`example.com` などの従業員用メールドメインを入力します。
2. シングルサインオンの構成を保存します。
3. Tuist が表示する TXT レコードを、ドメインの [Domain Name System](https://www.cloudflare.com/learning/dns/dns-records/dns-txt-record/) 構成に追加します。
4. 認証設定に戻り、**ドメインを検証** をクリックします。

検証済みのログイン用メールドメインは、1 つの Tuist 組織のみに関連付けることができます。ドメインを変更すると、その検証はクリアされ、新しい TXT レコードを発行する必要があります。ドメインが検証されるまで、自動登録は一時停止されたままになります。

Tuist は毎日 TXT レコードを再確認します。解決されなくなったレコードがあっても、検証はすぐにクリアされません。ドメインは 14 日間それを保持し、認証設定には **検証の有効期限切れ** と、再度発行すべきレコードが表示されます。レコードを発行して検証を行うと、警告は消えます。14 日後もレコードが見つからないドメインは未検証の状態に戻り、プロバイダーの検出、アイデンティティのリンク、自動登録は、再び検証されるまで停止します。他の理由でルックアップが失敗しても、タイマーはリフレッシュされず、検証自体はクリアされません。每日の再確認が導入される前に検証されたドメインは、再確認の対象ではありません。

Google Workspace は、認証されたアイデンティティの一部として検証済みの Workspace ドメインを Google が提供するため、この個別の Tuist 検証ステップを必要としません。

### 登録ポリシーを選択する {#choose-an-enrollment-policy}

Tuist は 2 つの登録ポリシーをサポートしています。

- **招待のみ:** ユーザーには組織からの招待が必要です。Okta およびカスタムプロバイダーの場合、プロバイダーが新しい Tuist アカウントを作成するには、ログイン用メールドメインの検証が依然として必要です。既存の Tuist アカウントを持つ招待されたユーザーは、まず招待を受け入れ、その後 <.localized_link href="/guides/integrations/authentication/sso#link-an-existing-account">既存の Tuist アカウントをリンク</.localized_link> で説明されているようにプロバイダーのアイデンティティをリンクします。
- **自動:** 認証されたメールが信頼されたドメインと一致するユーザーは、招待なしでアカウントを作成またはリンクし、組織に参加できます。Google の構成では Workspace ドメインを使用します。Okta およびカスタムプロバイダーでは、検証済みのログイン用メールドメインが必要です。

Google の構成はデフォルトで自動登録になります。新しい Okta およびカスタムプロバイダーの構成はデフォルトで招待のみの登録になります。

**シングルサインオンを強制** 設定は登録とは独立しています。組織の保護されたブラウザページへのアクセスには、現在のプロバイダーと発行者（または検証済みの Google Workspace）を通じて認証されたセッションが必要です。過去にリンクされたアイデンティティや、別の組織のプロバイダーを通じた認証では不十分です。Tuist への通常のサインインや他のアカウントへのアクセスは引き続き利用可能であり、強制によって組織メンバーシップが付与されるわけではありません。匿名のパブリックダッシュボードと期間限定のオペレーターサポート権限は、それぞれ独自のアクセスルールを維持します。アプリのプレビューページでは、組織メンバーに対してのみ強制が適用されるため、組織外で共有されたプレビューリンクは、訪問者がすでに開くことができるプレビューに対して機能し続けます。

強制は、メンバーのセッションが組織に到達するすべての場所で適用されます。

- **ダッシュボード**: 組織のページには、組織のプロバイダーでサインインしたセッションが必要です。
- **Tuist CLI、Tuist アプリ、MCP クライアント、および API リファレンス**: これらにサインインすると、すべての組織でメンバーに代わって動作する認証情報が作成されるため、シングルサインオンを強制する組織を通じてサインインしたセッションが必要です。Tuist は、別の方法でサインインしたメンバーをまずプロバイダーに送信し、メールとパスワードまたは Apple によるサインインを拒否します。これらのクライアントが認証情報を更新するたびに、Tuist は再度チェックを行います。組織のシングルサインオンを通じて取得した認証情報は更新され続け、以前に組織のプロバイダーを通じてサインインしたメンバーが別の方法で取得した認証情報も同様に更新され続けます。その他の認証情報（例えば、組織がシングルサインオンを強制する前にメンバーがパスワードで取得したもの）は、強制下での初回更新から 4 週間更新され続けます。その後、クライアントはメンバーに再度サインインするよう求めます。その間にダッシュボードまたは `tuist auth login` を使用してプロバイダーを通じてサインインすると、更新が継続されます。

シングルサインオンを強制する複数の組織のメンバーは、1 つのセッションが 1 つの組織を通じてサインインするため、CLI、アプリ、または MCP クライアントにサインインできません。

### 登録されたメンバーが得るロールを選択する {#choose-the-enrollment-role}

自動参加したメンバーには、**登録されたメンバーのロール** で設定された <.localized_link href="/guides/server/accounts-and-projects#roles">ロール</.localized_link> が付与されます。管理者が変更しない限り、これは `user` です。`viewer` に設定すると、ディレクトリ内の全員にサインインを開放しつつ、全員に変更権限を与えることはありません。

この設定は `admin` に設定できず、<.localized_link href="/guides/integrations/authentication/scim">SCIM</.localized_link> 経由でロールなしでプロビジョニングされたメンバーおよびサインインするメンバーに適用され、管理者が手動で設定したロールを上書きすることはありません。

### 既存の Tuist アカウントをリンクする {#link-an-existing-account}

リンクされたプロバイダーのアイデンティティは、アカウントが属する他のすべての組織を含め、Tuist アカウント全体にサインインします。Okta およびカスタムプロバイダーの場合、Tuist はメールアドレスが検証済みのログイン用メールドメインにある場合、または組織の SCIM プロビジョニングによってアカウントが作成された場合にのみ、既存のアカウントを自動的にリンクします。

資格条件を満たさないアカウントを持つメンバーは、自分でアイデンティティをリンクします:

1. アカウントの通常のサインイン方法を使用して Tuist にログインします。
2. アプリケーションタイルなど、アイデンティティプロバイダーから Tuist を開くか、シングルサインオンを強制している場合は組織のプロジェクトの 1 つを開きます。
3. Tuist が表示する組織とアイデンティティプロバイダーのアカウントを確認し、**アカウントをリンク** をクリックします。

サインアウト状態でシングルサインオンを開始したメンバーは、最初にログインするよう求められ、その後 Tuist は確認画面に戻ります。リンクはドメインの検証に依存しないため、メンバーはドメインが検証される前でもシングルサインオンを使用できます。

### 既存の組織 {#existing-organizations}

すべての Okta およびカスタムプロバイダー組織は、検証済みドメインモデルを使用します。一時的な互換性モードは削除されました。

ログイン用メールドメインが未検証の場合:

- 既存のリンク済みメンバーは引き続きサインインでき、既存の SSO 強制は組織メンバーに引き続き適用されます。
- ログインページは、既存の組織メンバーシップを通じてのみプロバイダーを検出します。
- 自動登録は一時停止されており、プロバイダーは招待があっても新しい Tuist アカウントを作成できません。
- リンクされていないメンバーは、既存の Tuist アカウントにサインインし、上記のようにリンクを確認します。組織の SCIM プロビジョニングによって作成されたアカウントは、最初の SSO サインイン時に依然としてリンクできます。
- 新規サインアップ者は、メールアドレスがあなたのドメインを使用しているという理由だけで、あなたのプロバイダーを使用する必要はありません。

既存の有効な登録および強制設定は保存されたままになり、無効にすることができます。管理者はドメインが未検証の間も構成を編集できます。いずれかの設定を有効にするには検証が必要です。その設定が有効な場合、検証により一致するメールアドレスに対する自動登録が再開されます。Google Workspace の動作は変更されません。

**ログイン用メールドメイン** には、組織のメンバーからの情報が入力されている可能性があります。値を確認し、テキストレコードを発行して、**ドメインを検証** をクリックします。毎日再チェックを行うために、レコードを発行した状態に保ってください。

## Google Workspace {#google}

Google Workspace シングルサインオンは、Workspace ドメインに対してユーザーを認証します。管理者は、一致するユーザーの自動参加を許可するか、招待を必須にすることができます。

> [!NOTE]
> **前提条件**
>
> 検証済みドメインを持つ Google Workspace 組織が必要です。また、設定しようとしているドメインに関連付けられたメールを使用して Google で認証されている必要があります。

### セットアップ {#google-setup}

1. 組織の **認証** 設定タブに移動します。
2. シングルサインオンを有効にします。
3. プロバイダーとして **Google** を選択します。
4. Google Workspace ドメイン（例: `example.com`）を入力します。
5. **自動登録** または招待のみの登録を選択します。Google の場合、自動登録はデフォルトで有効になっています。
6. オプションで、ログインフローをテストした後、**シングルサインオンを強制** を有効にします。
7. **変更を保存** をクリックします。

## Okta {#okta}

Okta は [OpenID Connect](https://openid.net/developers/how-connect-works/) を使用してメンバーを認証します。Okta ドメインはプロバイダーの発行者を識別し、別途検証されたログイン用メールドメインは検出、新しいアカウントのリンク、および登録を制御します。

Okta によるメンバーの自動作成、更新、またはプロビジョニング解除も行う場合は、シングルサインオンが機能してから <.localized_link href="/guides/integrations/authentication/scim#okta">Okta System for Cross-domain Identity Management provisioning</.localized_link> を構成してください。

### ステップ 1: Okta アプリケーションを作成する {#okta-step-1}

1. Okta 管理ダッシュボードで、**Applications > Applications > Create App Integration** に移動します。
2. **OpenID Connect** と **Web Application** を選択します。
3. アプリケーション名（例: `Tuist`）を設定します。オプションで [Tuist ロゴ](https://tuist.dev/images/tuist_dashboard.png) をアップロードできます。
4. **サインインリダイレクト URI** に、認証設定ページに表示される値（例: `https://tuist.dev/users/auth/okta/callback`）を設定します。
5. **Assignments** で、希望するアクセス制御を選択して保存します。
6. アプリケーションの一般設定から **Client ID** と **Client Secret** をコピーします。**Okta ドメイン**（例: `your-company.okta.com`）をメモしてください。
7. オプションで、Okta ダッシュボードからのログインを許可するには、General Settings で **Edit** をクリックし、**Login initiated by** を **Either Okta or App** に変更し、**Display application icon to users** を選択して、**Initiate login URI** に認証設定ページに表示される値を設定します。

### ステップ 2: Tuist を構成する {#okta-step-2}

1. 組織の **認証** 設定タブに移動します。
2. シングルサインオンを有効にします。
3. プロバイダーとして **Okta** を選択します。
4. **Okta ドメイン**、**Client ID**、および **Client Secret** を入力します。
5. **ログイン用メールドメイン** に従業員のメールドメインを入力します。例えば、Okta ドメインが `your-company.okta.com` の場合、ログイン用メールドメインは `example.com` になります。
6. **変更を保存** をクリックします。
7. Tuist が表示するテキストレコードをログイン用メールドメインに追加し、**ドメインを検証** をクリックします。
8. ユーザーに招待が必要か、自動登録を許可するかを選択し、構成を再度保存します。
9. オプションで、ログインフローをテストした後、**シングルサインオンを強制** を有効にします。

### ステップ 3: ユーザーを Okta アプリケーションに割り当てる {#okta-step-3}

Okta アプリケーションを通じて認証を許可すべきユーザーまたはグループを割り当てます。

割り当てによりログインフローへのアクセスが付与されますが、組織メンバーシップは引き続き登録ポリシーに従います。同じユーザーが System for Cross-domain Identity Management 経由でプロビジョニングされている場合、Tuist はユーザーが初めてサインインした際に、SCIM が作成したアカウントに Okta アイデンティティをリンクします。SCIM によって追加される前にアカウントが存在していたメンバーは、メールアドレスが検証済みのログイン用メールドメインに含まれている場合、またはサインイン済みのアカウントからリンクを確認した後にリンクされます。

## Microsoft Entra ID {#microsoft-entra-id}

Microsoft Entra ID は [OpenID Connect](https://openid.net/developers/how-connect-works/) を介してメンバーを認証します。Tuist はディレクトリ（テナント）識別子から承認、トークン、およびユーザー情報エンドポイントを導出するため、アプリケーションの認証情報とともにその値のみを入力する必要があります。

Entra ID によるメンバーの自動作成、更新、またはプロビジョニング解除も行う場合は、シングルサインオンが機能してから <.localized_link href="/guides/integrations/authentication/scim#microsoft-entra-id">Microsoft Entra ID System for Cross-domain Identity Management provisioning</.localized_link> を構成してください。

### ステップ 1: Entra アプリケーションを登録する {#entra-step-1}

1. [Microsoft Entra admin center](https://entra.microsoft.com) で、**Identity > Applications > App registrations > New registration** に移動します。
2. アプリケーション名（例: `Tuist`）を設定します。
3. **Redirect URI** で、**Web** プラットフォームを選択し、認証設定ページに表示される値（例: `https://tuist.dev/users/auth/oauth2/callback`）を入力します。
4. アプリケーションを登録し、概要ページから **Directory (tenant) ID** と **Application (client) ID** をコピーします。
5. **Certificates & secrets > New client secret** に移動し、シークレットを作成してその **Value** をコピーします。Microsoft は値を一度だけ表示し、すべてのクライアントシークレットには有効期限があるため、回転が必要な時期を記録してください。
6. **API permissions** に移動し、委任された Microsoft Graph 権限 `openid`、`profile`、および `email` が付与されていることを確認します。
7. オプションで、メンバーが My Apps ポータルからサインインフローを開始できるようにするには、**Branding & properties** の下の **Home page URL** に、認証設定ページに表示される値を設定します。

### ステップ 2: Tuist を構成する {#entra-step-2}

1. 組織の **認証** 設定タブに移動します。
2. シングルサインオンを有効にします。
3. プロバイダーとして **Microsoft Entra ID** を選択します。
4. **Directory (tenant) ID**、**Client ID**、および **Client Secret** を入力します。
5. **ログイン用メールドメイン** に従業員のメールドメインを入力します。例えば、ユーザーが `first.last@example.com` としてサインインするディレクトリのログイン用メールドメインは `example.com` です。
6. **変更を保存** をクリックします。
7. Tuist が表示するテキストレコードをログイン用メールドメインに追加し、**ドメインを検証** をクリックします。
8. ユーザーに招待が必要か、自動登録を許可するかを選択し、構成を再度保存します。
9. オプションで、ログインフローをテストした後、**シングルサインオンを強制** を有効にします。

### ステップ 3: ユーザーを Entra アプリケーションに割り当てる {#entra-step-3}

認証を許可するユーザーまたはグループを割り当てます。アプリケーションが割り当てを必須とするように構成されている場合、割り当てられたユーザーのみがサインインできます。

割り当てによりログインフローへのアクセスが付与されますが、組織のメンバーシップは引き続き登録ポリシーに従います。同じユーザーが System for Cross-domain Identity Management 経由でプロビジョニングされる場合、Tuist はユーザーが最初にサインインした際に SCIM が作成したアカウントに Entra ID をリンクします。SCIM によって追加される前にアカウントが存在していたメンバーは、そのメールアドレスが検証済みのログイン用メールドメインに含まれている場合、またはサインイン済みのアカウントからリンクを確認した後にリンクされます。

### email クレームの要件 {#entra-email-claim}

Tuist は Microsoft Graph のユーザー情報エンドポイントから認証済みユーザーのプロファイルを読み取ります。このエンドポイントは、ユーザーが利用可能なメールアドレスを持っている場合にのみそれを返します。`mail` 属性が空のディレクトリユーザーは、Tuist がログイン用メールドomain と照合するアドレスを持たないため、サインインできません。

シングルサインオンを展開する前に、割り当てるメンバーのディレクトリにメールアドレスが入力されていることを確認してください。メールボックスのないオンプレミス Active Directory から同期されたユーザーは、この属性が欠落している最も一般的なケースです。

### 条件付きアクセスと多要素認証 {#entra-conditional-access}

条件付きアクセスポリシー、多要素認証、およびサインインリスクポリシーは、承認リクエスト中に評価されるため、他の Entra アプリケーションと同様に Tuist アプリケーションにも適用されます。追加の Tuist 構成は不要です。

## カスタム OAuth 2.0 プロバイダー {#custom-oauth-2-provider}

カスタム OAuth 2.0 プロバイダーを使用すると、組織は Google Workspace や Okta 以外の ID サービスを利用できます。プロバイダーのユーザー情報エンドポイントは、安定したユーザー識別子とメールアドレスを返す必要があります。

1. プロバイダーで OAuth 2.0 ウェブアプリケーションを作成します。
2. **Sign-in redirect URI** およびオプションの **Initiate login URI** を、Tuist の認証設定に表示される値に設定します。
3. Tuist でシングルサインオンを有効にし、**OAuth2** を選択します。
4. プロバイダー URL、承認エンドポイント、トークンエンドポイント、ユーザー情報エンドポイント、クライアント識別子、およびクライアントシークレットを入力します。
5. **ログイン用メールドメイン** を入力して保存します。これは従業員のメールドメインであり、プロバイダー URL ではありません。
6. Tuist が表示するテキストレコードをログイン用メールドメインに追加し、**ドメインを検証** をクリックします。
7. 招待制または自動登録を選択し、構成を保存します。
8. オプションで **シングルサインオンを強制** を有効にする前に、サインインをテストします。

プロバイダー URL は、発行元プロバイダーに対して ID をスコープ限定します。検証済みのログイン用メールドメインは、ユーザーのリンクまたは登録時に Tuist が信頼できるメールアドレスを決定します。

## コマンドライン構成 {#command-line-configuration}

コマンドラインインターフェースを使用して Google Workspace または Okta を構成し、登録ポリシーを選択できます。例:

```bash
tuist organization update sso example \
  --provider okta \
  --organization-id your-company.okta.com \
  --enrollment-policy invitation-only
```

Microsoft Entra ID とカスタムプロバイダーは、コマンドラインではなく組織の認証設定から構成されます。

`--organization-id` の値はプロバイダー組織を識別します。これはログイン用メールドメインではありません。新しい Okta ユーザーを登録する前に、組織の認証設定からログイン用メールドメインを追加して検証してください。

## トラブルシューティング {#troubleshooting}

### 既存のメンバーはサインインできますが、新しいユーザーはできません {#existing-members-can-sign-in-but-new-users-cannot}

Okta およびカスタムプロバイダーの構成では、ログイン用メールドメインが検証済みであることを確認してください。その後、ユーザーを招待するか、自動登録を有効にします。

### シングルサインオンで最初にログインするよう求められます {#single-sign-on-asks-you-to-log-in-first}

Tuist アカウントのメールアドレスが組織の検証済みログイン用メールドメインに含まれていないか、ドメインがまだ検証されていないため、Tuist はプロバイダーの ID を自動的にリンクしません。通常のサインイン方法でログインし、<.localized_link href="/guides/integrations/authentication/sso#link-an-existing-account">既存の Tuist アカウントをリンクする</.localized_link>の説明に従ってリンクを確認してください。
### Tuist がメールアドレスに対応する組織を見つけられません {#tuist-cannot-find-an-organization-for-an-email-address}

ユーザーが想定される従業員のメールアドレスを入力し、そのドメインが検証済みのログイン用メールドメインと完全に一致することを確認してください。既存のメンバーは、現在の組織メンバーシップを通じて発見されることもあります。

### ドメイン検証が保留中です {#domain-verification-remains-pending}

テキストレコードの名前と値が Tuist に表示される値と完全に一致することを確認してください。DNS の変更には反映に時間がかかることがあるため、レコードが公開されてから検証を再試行してください。

### プロバイダーを変更した後、サインインが停止しました {#sign-in-stopped-after-changing-the-provider}

新しいプロバイダーの構成を確認し、ログイン用メールドメインを検証してから、強制を有効にする前にログインフローをテストします。
