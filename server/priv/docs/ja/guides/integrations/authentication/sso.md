# シングルサインオン {#single-sign-on}

Tuist は、組織のアカウント セキュリティを強化するためのログイン オプションとしてシングルサインオンを提供します。

シングルサインオンは、組織設定の **認証** タブから構成します。Google Workspace、Okta、Microsoft Entra ID、およびカスタムの [OAuth 2.0](https://oauth.net/2/) プロバイダーがサポートされています。

Microsoft Entra ID は OpenID Connect プロバイダーであり、Tuist がディレクトリ識別子に基づいて構成します。このガイドでカスタム プロバイダーについて説明している内容（ログイン用メール ドメインの検証や登録など）は、Microsoft Entra ID にも適用されます。

> [!NOTE]
> シングルサインオンは、メンバーの認証方法と、認証済みユーザーが自動的に参加できるかどうかを制御します。<.localized_link href="/guides/integrations/authentication/scim">クロスドメイン ID 管理プロビジョニング</.localized_link>は、ID プロバイダーが組織メンバーを作成、更新、およびプロビジョニング解除できるかどうかを制御します。Okta では、ほとんどの組織が両方を構成しています。

## アクセスの仕組み {#how-access-works}

プロバイダーの ID、ログインの検出、組織への登録は別々の概念です。

- **プロバイダーの発行者:** ユーザーを認証したプロバイダー組織または認可サーバーです。Tuist は、リンクされた ID を検索する際に、プロバイダー、発行者、および安定したプロバイダー ユーザー識別子を組み合わせて使用します。Okta の場合、発行者は Okta ドメインで表されます。Microsoft Entra ID の場合、ディレクトリ (テナント) 識別子から導出されます。カスタム プロバイダーの場合、プロバイダー URL で表されます。
- **ログイン用メール ドメイン:** Tuist が一般的なログイン ページから Okta またはカスタム プロバイダーを検出するために使用するメール ドメインです。検証されると、新しいアカウントのリンクと自動登録において信頼できるメールアドレスも確立されます。
- **登録ポリシー:** 信頼されたドメインのユーザーが招待を必要とするか、自動的に参加できるかを決定します。
- **プロビジョニング:** ログイン フローとは独立して組織メンバーシップを作成および管理します。

プロバイダーの発行者とログイン用メール ドメインは異なることがよくあります。たとえば、企業は従業員メールに `example.com` を使用しながら、プロバイダーの発行者が `https://login.vendor.example.net` である場合があります。新しい Okta およびカスタム プロバイダー構成では、これらの値は別々に保存されます。

### ログイン用メール ドメインを検証する {#verify-a-login-email-domain}

Okta およびカスタム プロバイダー構成では、新しい Tuist アカウントを作成したり、既存のアカウントをメールアドレスでリンクしたりする前に、検証済みのログイン用メール ドメインが必要です。ドメインが未検証の間でも、メンバーは <.localized_link href="/guides/integrations/authentication/sso#link-an-existing-account">既存のアカウントをリンク</.localized_link> できます。

1. **ログイン用メール ドメイン** に、`example.com` などの従業員メール ドメインを入力します。
2. シングルサインオン構成を保存します。
3. Tuist が表示する TXT レコードを、ドメインの [Domain Name System](https://www.cloudflare.com/learning/dns/dns-records/dns-txt-record/) 構成に追加します。
4. 認証設定に戻り、**ドメインを検証** をクリックします。

検証済みのログイン用メール ドメインは、1 つの Tuist 組織にのみ属することができます。ドメインを変更すると検証がクリアされ、新しい TXT レコードの公開が必要になります。ドメインが検証されるまで、自動登録は一時停止されたままです。

Tuist は毎日 TXT レコードを再確認します。解決されなくなったレコードがあっても、検証は直ちにクリアされません。ドメインは 14 日間それを保持し、認証設定には **検証の有効期限切れ** と、再度公開すべきレコードが表示されます。レコードを公開して検証すると、警告はクリアされます。14 日後もレコードが見つからないドメインは未検証の状態に戻り、プロバイダーの検出、ID のリンク、および自動登録は、再度検証されるまで停止します。その他の理由でルックアップが失敗しても、タイマーはリフレッシュされず、検証自体はクリアされません。每日の再確認が導入される前に検証されたドメインは、再確認の対象ではありません。

Google は認証された ID の一部として検証済みの Workspace ドメインを提供するため、Google Workspace ではこの個別の Tuist 検証ステップは不要です。

### 登録ポリシーを選択する {#choose-an-enrollment-policy}

Tuist は 2 つの登録ポリシーをサポートしています。

- **招待のみ:** ユーザーには組織からの招待が必要です。Okta およびカスタム プロバイダーの場合、プロバイダーが新しい Tuist アカウントを作成する前に、ログイン用メール ドメインを検証しておく必要があります。既存の Tuist アカウントを持つ招待されたユーザーは、まず招待を受け入れ、その後 <.localized_link href="/guides/integrations/authentication/sso#link-an-existing-account">既存の Tuist アカウントをリンク</.localized_link> で説明されているようにプロバイダー ID をリンクします。
- **自動:** 認証されたメールが信頼されたドメインと一致するユーザーは、招待なしでアカウントを作成またはリンクし、組織に参加できます。Google 構成では Workspace ドメインを使用します。Okta およびカスタム プロバイダーでは、検証済みのログイン用メール ドメインが必要です。

Google 構成のデフォルトは自動登録です。新しい Okta およびカスタム プロバイダー構成のデフォルトは招待のみの登録です。

**シングルサインオンを強制** 設定は登録とは独立しています。組織の保護されたブラウザ ページへのアクセスには、現在のプロバイダーと発行者 (または検証済みの Google Workspace) を介して認証されたセッションが必要です。過去にリンクされた ID や、別の組織のプロバイダーを介した認証では不十分です。Tuist への通常のサインインや他のアカウントへのアクセスは引き続き利用可能であり、強制によって組織メンバーシップが付与されるわけではありません。匿名の公開ダッシュボードと期間限定のオペレーター サポート付与は、それぞれ独自のアクセス ルールを維持します。アプリ プレビュー ページでは組織メンバーのみに強制が適用されるため、組織外で共有されたプレビュー リンクは、訪問者がすでに開くことができるプレビューに対して機能し続けます。

### 登録メンバーに付与されるロールを選択する {#choose-the-enrollment-role}

自動的に参加するメンバーには、**登録メンバーのロール** で設定された <.localized_link href="/guides/server/accounts-and-projects#roles">ロール</.localized_link> が付与されます。管理者が変更しない限り、これは `user` です。`viewer` に設定すると、ディレクトリ内の全員がサインインできるようになりますが、全員に変更権限が付与されるわけではありません。

この設定を `admin` にすることはできず、<.localized_link href="/guides/integrations/authentication/scim">SCIM</.localized_link> を介してロールなしでプロビジョニングされたメンバーと、サインインするメンバーの両方に適用され、管理者が手動で設定したロールを上書きすることはありません。

### 既存の Tuist アカウントをリンクする {#link-an-existing-account}

リンクされたプロバイダー ID は、アカウントが属する他のすべての組織を含む Tuist アカウント全体にサインインします。Okta およびカスタム プロバイダーの場合、Tuist はメールアドレスが検証済みのログイン メール ドメインにある場合、または組織の SCIM プロビジョニングによってアカウントが作成された場合にのみ、既存のアカウントを自動的にリンクします。

資格のないアカウントを持つメンバーは、自分で ID をリンクする必要があります。

1. アカウントの通常のサインイン方法を使用して Tuist にログインします。
2. ID プロバイダー (アプリケーション タイルなど) から Tuist を開くか、シングル サインオンを強制している場合は組織のプロジェクトの 1 つを開きます。
3. Tuist が表示する組織と ID プロバイダー アカウントを確認し、**アカウントをリンク** をクリックします。

サインアウト中にシングル サインオンを開始したメンバーは、最初にログインするように求められ、その後 Tuist は確認画面に戻ります。リンクはドメインの検証に依存しないため、メンバーはドメインが検証される前にシングル サインオンを使用できます。

### 既存の組織 {#existing-organizations}

すべての Okta およびカスタム プロバイダー組織は、検証済みドメイン モデルを使用します。一時的な互換性モードは削除されました。

ログイン メール ドメインが未検証の場合:

- 既存のリンク済みメンバーは引き続きサインインでき、既存の SSO 強制は組織メンバーに引き続き適用されます。
- ログイン ページは、既存の組織メンバーシップを通じてのみプロバイダーを検出します。
- 自動登録は一時停止され、プロバイダーは招待があっても新しい Tuist アカウントを作成できません。
- リンクされていないメンバーは、既存の Tuist アカウントにサインインし、上記のようにリンクを確認します。組織の SCIM プロビジョニングによって作成されたアカウントは、最初の SSO サインイン時に依然としてリンクできます。
- 新規サインアップ者は、メールアドレスがあなたのドメインを使用しているという理由だけで、あなたのプロバイダーを使用する必要はありません。

既存の有効な登録および強制設定は保存されたままになり、無効にすることができます。管理者はドメインが未検証の間も構成を編集できますが、いずれかの設定を有効にするには検証が必要です。その設定が有効になっている場合、検証により一致するメールアドレスの自動登録が再開されます。Google Workspace の動作は変更されません。

**ログイン メール ドメイン** は、組織のメンバーからすでに入力されている可能性があります。値を確認し、テキスト レコードを発行して、**ドメインを検証** をクリックします。毎日再チェックするためにレコードを発行したままにしてください。

## Google Workspace {#google}

Google Workspace シングル サインオンは、Workspace ドメインに対してユーザーを認証します。管理者は、一致するユーザーが自動的に参加することを許可するか、招待を要求するかを選択できます。

> [!NOTE]
> **前提条件**
>
> 検証済みのドメインを持つ Google Workspace 組織が必要です。また、設定しているドメインに関連付けられたメールアドレスを使用して Google で認証されている必要があります。

### セットアップ {#google-setup}

1. 組織の **認証** 設定タブに移動します。
2. シングル サインオンを有効にします。
3. プロバイダーとして **Google** を選択します。
4. Google Workspace ドメイン (例: `example.com`) を入力します。
5. **自動登録** または招待のみの登録を選択します。Google のデフォルトでは自動登録が有効になっています。
6. オプションで、ログイン フローをテストした後、**シングル サインオンを強制** を有効にします。
7. **変更を保存** をクリックします。

## Okta {#okta}

Okta は [OpenID Connect](https://openid.net/developers/how-connect-works/) を使用してメンバーを認証します。Okta ドメインはプロバイダーの発行者を識別し、別途検証されたログイン メール ドメインは検出、新しいアカウントのリンク、および登録を制御します。

Okta によるメンバーの自動作成、更新、またはプロビジョニング解除も希望する場合は、シングル サインオンが機能した後、<.localized_link href="/guides/integrations/authentication/scim#okta">Okta System for Cross-domain Identity Management provisioning</.localized_link> を構成します。

### 手順 1: Okta アプリケーションを作成する {#okta-step-1}

1. Okta 管理ダッシュボードで、**Applications > Applications > Create App Integration** に移動します。
2. **OpenID Connect** と **Web Application** を選択します。
3. アプリケーション名 (例: `Tuist`) を設定します。オプションで [Tuist ロゴ](https://tuist.dev/images/tuist_dashboard.png) をアップロードします。
4. **Sign-in redirect URI** を認証設定ページに表示されている値 (例: `https://tuist.dev/users/auth/okta/callback`) に設定します。
5. **Assignments** で、必要なアクセス制御を選択して保存します。
6. アプリケーションの一般設定から **Client ID** と **Client Secret** をコピーします。**Okta ドメイン** (例: `your-company.okta.com`) をメモします。
7. オプションで、Okta ダッシュボードからのログインを許可するには、General Settings で **Edit** をクリックし、**Login initiated by** を **Either Okta or App** に変更し、**Display application icon to users** を選択して、**Initiate login URI** を認証設定ページに表示されている値に設定します。

### 手順 2: Tuist を構成する {#okta-step-2}

1. 組織の **Authentication** 設定タブに移動します。
2. シングル サインオンを有効にします。
3. プロバイダーとして **Okta** を選択します。
4. **Okta ドメイン**、**Client ID**、および **Client Secret** を入力します。
5. **Login email domain** に従業員のメール ドメインを入力します。例えば、Okta ドメインが `your-company.okta.com` の場合、ログイン メール ドメインは `example.com` になります。
6. **変更を保存** をクリックします。
7. Tuist が表示する TXT レコードをログイン メール ドメインに追加し、**Verify domain** をクリックします。
8. ユーザーに招待が必要か、自動登録を許可するかを選択し、構成を再度保存します。
9. オプションで、ログイン フローをテストした後、**シングル サインオンを強制** を有効にします。

### 手順 3: ユーザーを Okta アプリケーションに割り当てる {#okta-step-3}

Okta アプリケーションを通じて認証を許可されるユーザーまたはグループを割り当てます。

割り当てによりログイン フローへのアクセス権が付与されますが、組織のメンバーシップは引き続き登録ポリシーに従います。同じユーザーが System for Cross-domain Identity Management によってプロビジョニングされている場合、Tuist はユーザーが最初にサインインした際に SCIM が作成したアカウントに Okta ID をリンクします。SCIM による追加前にアカウントが存在していたメンバーは、そのメールアドレスが検証済みのログイン メール ドメインに含まれている場合、またはサインイン済みのアカウントからリンクを確認した後にリンクされます。

## Microsoft Entra ID {#microsoft-entra-id}

Microsoft Entra ID は [OpenID Connect](https://openid.net/developers/how-connect-works/) を介してメンバーを認証します。Tuist はディレクトリ (テナント) 識別子から承認、トークン、およびユーザー情報エンドポイントを導出するため、アプリケーションの資格情報とともにその値のみを入力すれば済みます。

Entra ID によるメンバーの自動作成、更新、またはプロビジョニング解除も希望する場合は、シングル サインオンが機能した後、<.localized_link href="/guides/integrations/authentication/scim#microsoft-entra-id">Microsoft Entra ID System for Cross-domain Identity Management provisioning</.localized_link> を構成します。

### 手順 1: Entra アプリケーションを登録する {#entra-step-1}

1. [Microsoft Entra admin center](https://entra.microsoft.com) で、**Identity > Applications > App registrations > New registration** に移動します。
2. アプリケーション名 (例: `Tuist`) を設定します。
3. **Redirect URI** で **Web** プラットフォームを選択し、認証設定ページに表示されている値 (例: `https://tuist.dev/users/auth/oauth2/callback`) を入力します。
4. アプリケーションを登録し、概要ページから **Directory (tenant) ID** と **Application (client) ID** をコピーします。
5. **Certificates & secrets > New client secret** に移動し、シークレットを作成してその **Value** をコピーします。Microsoft は値を一度だけ表示し、すべてのクライアント シークレットには有効期限があるため、回転が必要な時期を記録してください。
6. **API permissions** に移動し、委任された Microsoft Graph 権限 `openid`、`profile`、および `email` が付与されていることを確認します。
7. オプションで、メンバーが My Apps ポータルからサインイン フローを開始できるようにするには、**Branding & properties** の下の **Home page URL** を認証設定ページに表示されている値に設定します。

### 手順 2: Tuist を構成する {#entra-step-2}

1. 組織の **Authentication** 設定タブに移動します。
2. シングル サインオンを有効にします。
3. プロバイダーとして **Microsoft Entra ID** を選択します。
4. **Directory (tenant) ID**、**Client ID**、および **Client Secret** を入力します。
5. **Login email domain** に従業員のメール ドメインを入力します。例えば、ユーザーが `first.last@example.com` としてサインインするディレクトリのログイン メール ドメインは `example.com` です。
6. **変更を保存** をクリックします。
7. Tuist が表示する TXT レコードをログイン メール ドメインに追加し、**Verify domain** をクリックします。
8. ユーザーに招待が必要か、自動登録を許可するかを選択し、構成を再度保存します。
9. オプションで、ログイン フローをテストした後、**シングル サインオンを強制** を有効にします。

### 手順 3: ユーザーを Entra アプリケーションに割り当てる {#entra-step-3}

認証を許可されるユーザーまたはグループを割り当てます。アプリケーションが割り当てを必須とするように構成されている場合、割り当てられたユーザーのみがサインインできます。

割り当てによりログイン フローへのアクセス権が付与されますが、組織のメンバーシップは引き続き登録ポリシーに従います。同じユーザーが System for Cross-domain Identity Management によってプロビジョニングされている場合、Tuist はユーザーが最初にサインインした際に SCIM が作成したアカウントに Entra ID をリンクします。SCIM による追加前にアカウントが存在していたメンバーは、そのメールアドレスが検証済みのログイン メール ドメインに含まれている場合、またはサインイン済みのアカウントからリンクを確認した後にリンクされます。

### email クレームの要件 {#entra-email-claim}

Tuist は Microsoft Graph ユーザー情報エンドポイントから認証済みユーザーのプロファイルを読み取ります。このエンドポイントは、ユーザーが利用可能なメールアドレスを持っている場合にのみそれを返します。`mail` 属性が空のディレクトリ ユーザーは、Tuist がログイン メール ドメインと照合するアドレスを持たないため、サインインできません。

シングル サインオンを展開する前に、割り当てたメンバーのディレクトリにメールアドレスが入力されていることを確認してください。この属性が欠落している最も一般的なケースは、メールボックスなしでオンプレミスの Active Directory から同期されたユーザーです。

### 条件付きアクセスと多要素認証 {#entra-conditional-access}

条件付きアクセス ポリシー、多要素認証、およびサインイン リスク ポリシーは、承認リクエスト中に評価されるため、他の Entra アプリケーションと同様に Tuist アプリケーションにも適用されます。追加の Tuist 構成は必要ありません。

## カスタム OAuth 2.0 プロバイダー {#custom-oauth-2-provider}

カスタム OAuth 2.0 プロバイダーを使用すると、組織は Google Workspace や Okta 以外の ID サービスを利用できます。プロバイダーのユーザー情報エンドポイントは、安定したユーザー識別子とメールアドレスを返す必要があります。

1. プロバイダーで OAuth 2.0 ウェブ アプリケーションを作成します。
2. Tuist の認証設定に表示されている値に合わせて、**サインイン リダイレクト URI** およびオプションの **ログイン開始 URI** を設定します。
3. Tuist でシングル サインオンを有効にし、**OAuth2** を選択します。
4. プロバイダー URL、承認エンドポイント、トークン エンドポイント、ユーザー情報エンドポイント、クライアント識別子、およびクライアント シークレットを入力します。
5. **ログイン メール ドメイン** を入力して保存します。これは従業員のメール ドメインであり、プロバイダー URL ではありません。
6. Tuist が表示する TXT レコードをログイン メール ドメインに追加し、**Verify domain** をクリックします。
7. 招待のみまたは自動登録を選択し、構成を保存します。
8. オプションで **シングル サインオンを強制** を有効にする前に、サインインをテストします。

プロバイダー URL は、発行元プロバイダーに対して ID をスコープします。検証済みのログイン メール ドメインは、ユーザーのリンクまたは登録時に Tuist が信頼するメールアドレスを決定します。

## コマンドライン構成 {#command-line-configuration}

コマンドライン インターフェースを使用して Google Workspace または Okta を構成し、登録ポリシーを選択できます。例:

```bash
tuist organization update sso example \
  --provider okta \
  --organization-id your-company.okta.com \
  --enrollment-policy invitation-only
```

Microsoft Entra ID とカスタム プロバイダーは、コマンドラインではなく組織の認証設定から構成されます。

`--organization-id` 値はプロバイダー組織を識別します。これはログイン メール ドメインではありません。新しい Okta ユーザーを登録する前に、組織の認証設定からログイン メール ドメインを追加して検証してください。

## トラブルシューティング {#troubleshooting}

### 既存のメンバーはサインインできますが、新しいユーザーはできません {#existing-members-can-sign-in-but-new-users-cannot}

Okta およびカスタム プロバイダーの構成では、ログイン メール ドメインが検証済みであることを確認してください。その後、ユーザーを招待するか、自動登録を有効にします。

### シングル サインオンで最初にログインするよう求められます {#single-sign-on-asks-you-to-log-in-first}

Tuist アカウントのメールアドレスが組織の検証済みログイン メール ドメインに含まれていないか、ドメインがまだ検証されていないため、Tuist はプロバイダー ID を自動的にリンクしません。通常のサインイン方法でログインし、<.localized_link href="/guides/integrations/authentication/sso#link-an-existing-account">既存の Tuist アカウントをリンク</.localized_link> で説明されているようにリンクを確認してください。
### Tuist がメールアドレスに対応する組織を見つけられません {#tuist-cannot-find-an-organization-for-an-email-address}

ユーザーが想定される従業員のメールアドレスを入力しており、そのドメインが検証済みのログイン メール ドメインと完全に一致していることを確認してください。既存のメンバーは、現在の組織メンバーシップを通じて検出されることもあります。

### ドメイン検証が保留中です {#domain-verification-remains-pending}

TXT レコードの名前と値が Tuist に表示されている値と完全に一致していることを確認してください。DNS の変更には反映に時間がかかることがあるため、レコードが公開された後に検証を再試行してください。

### プロバイダーを変更した後、サインインが停止しました {#sign-in-stopped-after-changing-the-provider}

新しいプロバイダー構成を確認し、ログイン メール ドメインを検証してから、強制を有効にする前にログイン フローをテストします。
