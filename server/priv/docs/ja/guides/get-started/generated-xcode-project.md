# 生成されたXcodeプロジェクト {#generated-xcode-project}

::: code-group

```text [Agent prompt]
Help me get started with Tuist. Follow the setup at:
https://tuist.dev/en/docs/guides/get-started/generated-xcode-project
```

:::

TuistにSwiftマニフェストからXcodeプロジェクトを記述・生成させたい場合は、この手順に従ってください。生成されたプロジェクトは、モジュラーなXcodeプロジェクトの複雑さを、グラフの簡潔で宣言的な記述に圧縮します。また、モジュールキャッシュと選択的テストには必須の要件です。

以下の各セクションでは、まず現状で不足している点を示し、そのギャップを埋める機能について説明します。

## 前提条件

- XcodeがインストールされたmacOS。
- <.localized_link href="/guides/install-tuist">Tuistコマンドラインインターフェース</.localized_link>。

## プロジェクトの作成

動作を確認する最も早い方法は、新しいプロジェクトを作成することです。空のディレクトリで `tuist init` を実行し、**生成されたプロジェクトを作成** を選択して、プラットフォームを選び、名前を確認します。その後、認証を行い、プロジェクトを所有するアカウントを選択してください。

```bash
mkdir MyApp && cd MyApp
tuist init
```

コーディングエージェントやスクリプトから実行する場合は、まず `tuist auth login` を実行してください（ブラウザでのフローではEnterキーを押すまで待機します）。その後、非インタラクティブな形式を使用します。

```bash
tuist init --build-system generated-xcode --name MyApp --platform ios --account <account>
```

initが完了したら、`tuist generate` を実行します。Tuistはマニフェストの隣に `.xcworkspace` を書き込み、Xcodeで開きます。ターゲットをビルドして実行してください。シミュレータでサンプルアプリが起動するはずです。

これが「接続＋生成」の状態です。以下はすべてオプションであり、独立しています。

既存のアプリを移行する場合は、まず [Xcodeプロジェクトの移行ガイド](https://tuist.dev/en/docs/guides/features/projects/adoption/migrate/xcode-project) で接続を行い、その後戻って、あなたの課題に適したセクションを続けてください。

## プロジェクト生成

`.xcodeproj` は、アプリの構造をXMLにバンドルします。ファイル参照、ビルドフェーズ、ターゲット依存関係、スキーム、ビルド設定がすべて同じツリー内に存在し、グラフをグラフとして推論するためのプリミティブがありません。プロジェクトが大きくなるにつれて、その構造を頭の中で把握するのが難しくなり、Xcodeには変更がない場合にハッシュ化して作業をスキップするための安定したハンドルがありません。

生成されたプロジェクトは、グラフを宣言的なSwiftに圧縮します。`Project.swift` はターゲット、依存関係、リソースを直接記述し、Tuistはその背後でグラフの安定したモデルを維持します。このモデルこそが、以下のセクションを可能にするものです。モジュールキャッシングはこれをハッシュ化してバイナリを再利用し、選択的テストは入力に変更がないテストをスキップするためにハッシュ化します。

```swift
import ProjectDescription

let project = Project(
    name: "MyApp",
    targets: [
        .target(
            name: "MyApp",
            destinations: .iOS,
            product: .app,
            bundleId: "dev.tuist.MyApp",
            sources: ["MyApp/Sources/**"],
            dependencies: []
        )
    ]
)
```

各 `tuist generate` は、マニフェストから決定論的なワークスペースを生成します。`.xcodeproj` と `.xcworkspace` を `.gitignore` に追加してください。

## モジュールキャッシュ

モジュラーなXcodeプロジェクトをゼロからコンパイルするには、マシンごとのコストがかかります。チームメンバーそれぞれとCIランナーそれぞれが、同じオブジェクトファイルのコピーを個別に生成します。Xcodeのコンパilationキャッシュは内側ループを短縮しますが、すべてのターゲットのマシンごとのビルドを排除することはできず、フレームワーク全体を事前構築されたバイナリで置き換えることもできません。

モジュールキャッシュはそれを実現します。グラフ内のキャッシュ可能なすべての依存関係（フレームワーク、ライブラリ、バンドル）を一度ビルドし、結果のバイナリをターゲットの入力のハッシュ値に関連付けて保存し、後続の生成ではターゲットをそのバイナリに置き換えます。変更されていないモジュールはコンパイルされなくなります。

```bash
tuist cache
```

初回の実行ではすべてをコンパイルし、バイナリをあなたのアカウントにアップロードします。次の `tuist generate` では、変更されていない依存関係がキャッシュされたバイナリに置き換えられ、Xcodeはソースからコンパイルする代わりに `.xcframework` に対してリンクを行います。

## 選択的テスト

`xcodebuild test` は、変更がどのテストに影響するかを認識しないため、CIはプッシュごとにスイート全体を実行します。スイートが大きくなるにつれて、実際に実行が必要なものと実行されるものの間のギャップが、数分から数十分に広がります。

選択的テストは、最後の成功したテスト実行以降に変更があった影響を受けるテストのみを実行します。これには、プロジェクトグラフとモジュールキャッシュが依存するのと同じハッシュアルゴリズムを使用します。

```bash
tuist test
```

最初の `tuist test` はすべてを実行し、ターゲットごとのハッシュを永続化します。後続の実行では、入力に変更がないターゲットをスキップします。CIで `xcodebuild test` の代わりに `tuist test` を使用するように移行すれば、フィードバックが数分ではなく数秒で得られます。

## パッケージレジストリ

Swift Package Managerは、パッケージがレジストリではなくURLでアドレス指定されるため、各パッケージのgit履歴を深くクローンすることで依存関係を解決します。数十の推移的なパッケージを持つプロジェクトでは、クリーンなチェックアウト時の解決に数分かかり、それがすべてのCIジョブで繰り返されます。

Tuist Package Registryは、Swift Package Indexが追跡している同じパッケージを提供しますが、実際のレジストリとして機能するため、SwiftPMは実際に必要なコミットのみを取得します。`Tuist.swift` で `registryEnabled: true` を設定することで、一度有効にできます。

```swift
let tuist = Tuist(
    project: .tuist(
        generationOptions: .options(
            registryEnabled: true
        )
    )
)
```

再生成してください。パッケージの解決時間が数分から数秒に短縮されます。

## ビルドインサイト

Xcodeは、ログとビルドレポートにターゲットごとのビルド所要時間を記録します。どちらも実行間やマシン間で集計されないため、ビルド時間の劣化は通常、CI全体の低速化としてのみ表面化します。

ビルドインサイトは、生成されたスキームに対するすべてのビルドの所要時間とフェーズのタイミングを自動的に記録します。追加の設定は不要です。次の `tuist generate` ＋ビルドサイクル後に、ダッシュボードの **ビルド** タブを開いてください。

## テストインサイト

Xcodeは、テストごとの結果を1回の実行ごとに報告します。実際に必要なクロスランのシグナル、つまり不安定さの割合、週ごとの所要時間、どのシミュレータバリアントが失敗するかを集計しません。

テストインサイトは、生成されたスキームに対するすべてのテストの結果と所要時間を自動的に記録し、実行間の結果を相関付けます。不安定なテスト、遅いテスト、および失敗は、ダッシュボードの **テスト** タブに表示されます。不安定なテストが蓄積された場合は、ダッシュボードから隔離して、マージをブロックしないようにしてください。

## チームを巻き込む

モジュールキャッシュと選択的テストは、全員が同じ共有 surface にアクセスしているときに最も効果を発揮します。ダッシュボードのアカウント設定からチームメイトを組織に招待し、<.localized_link href="/guides/integrations/authentication/sso">シングルサインオン</.localized_link>（Google、Okta、Microsoft）を設定して、オンボーディングを個人ごとの `tuist auth login` ではなくクリックだけで完了できるようにしてください。
