# 不安定なテストとは何ですか？ {#what-is-a-flaky-test}

不安定なテストは、同じコードに対して実行した際に合格と不合格の両方の結果を生み出す自動テストです。テスト対象のコードやテスト自体に変更はありません。その結果は、テストが制御できない要素（タイミング、テストの実行順序、他のテストが残した状態、実行マシン、ネットワーク経由で呼び出すサービスなど）に依存します。そのため、不安定な失敗はテスト中の変更について信頼できる情報を何も提供せず、これが不安定なテストのコストを高める要因となります。信頼できるようになる前に、すべての赤い結果を調査するか再実行する必要があります。

不安定さはあらゆる規模で一般的です。Google は、すべてのテスト実行の約 1.5% が不安定な結果を生み出し、テストのほぼ 16% が何らかのレベルの不安定さを示していると報告しています（[Flaky Tests at Google and How We Mitigate Them](https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html)、2016年）。

## 不安定なテストの現れ方 {#how-flaky-tests-show-up}

テストが不安定であると判明するのは、同じ入力に対して両方の結果が生じた場合のみです。実際には、その証拠は次の 3 つの場所から得られます。

- **実行内の再試行。** テストが失敗し、ランナーが再試行して、再試行が合格します。これは最もコストの低いシグナルであり、ほとんどのテストランナーで生成できます。
- **同じコミットの不一致する実行。** 同じコミットと構成に対する 2 回の CI 実行で、テストの結果が異なります。例えば、プルリクエストでの実行と、誰かが再試行をクリックした後の再実行などです。
- **意図的な繰り返し。** テストが失敗するかどうかを確認するために、意図的に何度も連続して実行します。これは、疑わしい不安定さを確認したり、マージ前に新しいテストが安定しているかを確認する方法です。

結果が不安定さの証拠としてカウントされるのは、重要なすべてが同一である場合のみです。コミット、ビルド構成、デバイスまたはシミュレータ、OS バージョン、ツールチェーンです。iOS 17 で失敗し iOS 18 で合格するテストは、いずれかに実際の決定論的バグがある可能性があります。

## ビルドシステムごとの不安定なテスト検出の仕組み {#how-it-works-per-build-system}

各ツールチェーンはテストの再試行と繰り返しをサポートしていますが、結果の記録と報告方法は異なります。

### Xcode {#xcode}

`xcodebuild` とテストプランはテストの繰り返しをサポートしています。`-retry-tests-on-failure` は失敗したテストを再実行し、`-test-iterations <n>` は許可される試行回数を設定し、`-run-tests-until-failure` は失敗するまでテストを繰り返します。これは疑わしい不安定さを再現するのに役立ちます。テストプランは、テスト繰り返しモードと同じオプションに加え、テストをランダムな順序で実行するオプションを提供し、隠れた順序依存性を表面化させます。

すべての試行は `.xcresult` バンドルに保存されるため、失敗してから再試行で合格したテストはそこで確認できます。Xcode は実行をまたいで履歴を保持しないため、同じ実行内で再試行されない不安定さを検出するには、同じコミットの異なる実行からの結果バンドルを比較する必要があります。

### Gradle {#gradle}

Gradle の `Test` タスクは単独では失敗したテストを再試行しません。[Test Retry プラグイン](https://github.com/gradle/test-retry-gradle-plugin)（`org.gradle.test-retry`）は `Test` タスクに `retry` ブロックを追加し、`maxRetries` や `failOnPassedAfterRetry` などのオプションを提供します。失敗してから合格したテストは、テストレポートと JUnit XML の両方に両方の試行が表示されます。テストフレームワークは独自の繰り返しツールを追加しており、例えば JUnit 5 の `@RepeatedTest` などがあります。

Gradle のビルドキャッシュも不安定さを隠す可能性があります。入力が変更されていないキャッシュ可能な `Test` タスクは、実行される代わりにキャッシュから復元されるため、一度合格したテストは実行されずに合格し続けます。不安定さを測定する際は、`--rerun-tasks` を使用してテストを強制的に実行するか、ビルドキャッシュを無効にして `Test` タスクを実行してください。

### Bazel {#bazel}

Bazel には組み込みサポートがあります。テストターゲットに `flaky = True` をマークすると、Bazel は最大 3 回実行し、すべての試行が失敗した場合のみ失敗とします。`--flaky_test_attempts` フラグはターゲットを変更せずに試行回数を設定し、失敗した試行の後に合格した場合、ターゲットの結果は `FLAKY` として報告されます。意図的に不安定さを測定するには、`--runs_per_test=<n>` でテストを複数回実行し、`--runs_per_test_detects_flakes` は少なくとも 1 回が合格し 1 回が失敗した場合にシャードを `FLAKY` として報告します。

Bazel はビルド出力をキャッシュするのと同じ方法でテスト結果をキャッシュします。同じ入力で合格したテストは、ローカルおよびリモートキャッシュのどちらからでも、再度実行せずに `(cached) PASSED` として報告されます。新鮮な実行が必要な場合は `--cache_test_results=no`（または `--nocache_test_results`）を使用してください。Bazel のドキュメントは `flaky = True` に依存することを推奨していません。再試行した失敗を永続的に隠してしまうためです。

### その他のテストランナー {#other-test-runners}

同じパターンがほぼ everywhere に存在します。pytest には `pytest-rerunfailures` プラグインがあり、Jest には `jest.retryTimes()` があり、Elixir の ExUnit には `mix test --repeat-until-failure` があり、使用したランダムシードを出力するため、順序依存の失敗を `--seed` で再生できます。

## 不安定なテストの一般的な原因 {#common-causes}

オープンソースプロジェクトにおける不安定なテストの実証研究（[Luo et al., FSE 2014](https://doi.org/10.1145/2635868.2635920)）では、非同期待機、並行性、テスト順序依存性が最も一般的な根本原因であることがわかりました。以下のリストはそれらと、チームが最も頻繁に遭遇する他の原因をカバーしています。

- **非同期待機と固定スリープ。** テストは、`sleep(1)` や短いタイムアウトを持つ期待値など、作業が完了するまで固定時間を待機しますが、特に負荷の高い CI マシンでは作業に時間がかかることがあります。条件そのものを、 generous な上限値付きで待機してください。
- **並行性。** 2 つのスレッドまたはタスクが共有データで競合するか、バックグラウンド操作が完了する前にテストがアサートを行います。これらの失敗は多くの場合 CPU 数と負荷に依存するため、CI では発生しますが高速なラップトップでは発生しません。
- **テスト順序依存性と共有状態。** テストは、別のテストが作成したりクリーンアップを忘れた状態に依存します。シングルトン、データベース行、ディスク上のファイル、`UserDefaults`、環境変数、またはモック化されたグローバルなどです。テストをランダムな順序または並列で実行すると露呈します。
- **時間と日付。** 実時計を使用するテストは、深夜、月末、夏時間の変更時、または別のタイムゾーンで失敗します。代わりにクロックを注入してください。
- **シードなしのランダム性と順序なしコレクション。** 記録されたシードのないランダムデータ、またはハッシュマップやセットの反復順序に依存するアサーション。
- **ネットワークと外部サービス。** 実際の API、パッケージレジストリ、または共有ステージング環境への呼び出しは、それらのサービスが遅い、または利用できない場合に失敗します。境界でスタブ化し、明示的な統合テストを少数に抑えてください。
- **リソースの圧迫と環境状態。** 低速または過負荷のマシン、リセットされていないシミュレーターやエミュレーター、ディスク容量の逼迫、他のジョブが既に使用しているポートなどです。無関係な多くのテストが同時に失敗する場合は、テストよりも環境を疑ってください。
- **UI テスト。** エンドツーエンドおよび UI テストは、上記のほとんどの原因にアニメーション、レンダリングのタイミング、システムダイアログが組み合わさるため、ユニットテストよりも不安定になりがちです。

変更後に一貫して失敗するテストは不安定ではなく、回帰です。不安定というラベルは、同じコードで両方の結果を出したテストにのみ reserved すべきです。

## 修正、再試行、隔離 {#fixing-retrying-and-quarantining}

チームは通常 3 つの対応を組み合わせており、これらを区別することが役立ちます。

- 原因を**修正**する。これがテストの価値を回復させる唯一の対応です。記録された試行回数、失敗メッセージ、各失敗実行時の条件は、原因を示す証拠となります。
- パイプラインを動かすために**再試行**する。再試行は有用な検出シグナルですが、一律の再試行は問題を隠蔽し、失敗するすべての実行にマシンの時間を追加します。再試行で成功した場合でも、黙って破棄せず、不安定な結果として記録すべきです。
- 既知の不安定なテストを**隔離**し、修正中にマージをブロックしないようにします。隔離されたテストは、失敗を無視して実行し続ける（ミュート）ことで証拠を生み出し続けるか、まったく実行しない（スキップ）ことでカバレッジを失います。隔離には責任者と終了条件が必要であり、否则隔離されたテストが蓄積し、カバレッジが静かに縮小します。

## 不安定さを測定する方法 {#how-to-measure-flakiness}

パイプラインごとだけでなく、テストごとに不安定さを追跡してください。

- **不安定率。** テストの実行のうち不安定な結果を出した割合。失敗の後に成功する再試行、または同じコミットと設定の別の実行と一致しない結果などです。
- **影響。** テストがブロックまたは遅延させたパイプライン、プルリクエスト、マージキューのエントリ数、および再試行が消費したマシン時間。不安定率が低くてもすべてのパイプラインで実行されるテストは、非常に不安定だがまれにしか実行されないテストよりもコストがかかる可能性があります。
- **傾向。** 新しい不安定なテストが、古いものが修正されるよりも速く導入されているかどうか。マージ前に新しい、または変更されたテストを複数回繰り返すことで、多くの不安定さを源头で捕捉できます。

テストが安定していることを確認するには、直感よりも多くの実行が必要です。テストが各実行で確率 *p* で失敗する場合、*n* 回の実行で少なくとも 1 回の失敗を見る確率は 1 − (1 − p)ⁿ です。1% の確率で失敗するテストの場合、10 回の実行では約 10% の確率でしか捕捉できず、95% の信頼度で捕捉するには約 300 回の実行が必要です。数回の成功した再実行は、修正が機能したという弱い証拠にすぎません。

## 価値がない場合 {#when-it-isnt-worth-it}

すべての不安定なテストが調査に値するわけではなく、すべてのチームが不安定なテスト用のツールを必要とするわけではありません。

- **低価値なテスト。** 不安定なテストが他のテストがすでに提供しているカバレッジを重複している場合、削除することが適切な修正となり得ます。誰も信頼しないテストは、いずれにせよカバレッジを提供しません。
- **インフラストラクチャの問題。** 失敗が 1 台のマシン、ランナーイメージ、または特定の時間帯に集中する場合、テストを 1 つずつ修正するよりも環境を修正する方が安上がりです。
- **小規模で高速なスイート。** 高速なスイートを持ち、既知の不安定なテストが 1 つある小規模なチームの場合、追跡システムよりも共有ノートと今週の修正の方が優れています。専用検出と隔離は、スイート、貢献者数、またはパイプライン数が多くなり、どの失敗がノイズなのかを誰も覚えられなくなったときに効果を発揮します。
- **クリティカルパス。** 支払い、データ整合性、またはセキュリティを保護するテストに対して隔離は間違ったツールです。これらのテストは、不便であっても修正されるまでブロックすべきです。

## Tuist による不安定なテストの検出 {#flaky-test-detection-with-tuist}

[Tuist](https://tuist.dev) は、Xcode、Gradle、Bazel、Elixir、およびその他のサポートされている統合からのすべてのテスト試行を記録し、再試行全体、およびサポートされている統合については同じコミットの CI 実行全体で、同じコードで失敗と成功が発生した場合にテストを不安定としてマークし、修正中にチームが既知の不安定なテストを手動または自動化によってミュートまたはスキップできるようにします。サポートと要件はツールチェーンによって異なります。

- <.localized_link href="/guides/features/test-insights/flaky-tests">不安定なテスト</.localized_link> では、検出、隔離、新しいテストのストレステストの仕組みについて、ツールチェーンごとのガイドとともに説明しています。
- <.localized_link href="/guides/features/test-insights">テストインサイト</.localized_link> では、まずテスト結果を記録する方法についてカバーしています。
- [私のテストは不安定です](https://tuist.dev/solutions/flaky-tests) は、チームとして不安定なテストを診断し封じ込めるための実践的なガイドです。
