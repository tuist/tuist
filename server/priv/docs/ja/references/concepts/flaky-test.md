# 不安定なテストとは {#what-is-a-flaky-test}

不安定なテストとは、テスト対象のコードやテスト自体に変更がない状態で同じコードに対して実行した際に、成功と失敗の両方の結果を生み出す自動テストです。その結果は、タイミング、テストの実行順序、他のテストが残した状態、実行マシン、ネットワーク経由で呼び出すサービスなど、テストが制御できない要因に依存します。そのため、不安定な失敗はテスト中の変更について信頼できる情報を何も示さず、これが不安定なテストのコストを高める原因となります。赤い結果（失敗）は、信頼できるようになるまでに調査または再実行が必要です。

不安定さはあらゆる規模で一般的です。Google は、すべてのテスト実行の約 1.5% が不安定な結果を生み出し、テストのほぼ 16% が何らかのレベルの不安定さを示していると報告しています（[Flaky Tests at Google and How We Mitigate Them](https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html)、2016年）。

## 不安定なテストの現れ方 {#how-flaky-tests-show-up}

テストが不安定であると判明するのは、同じ入力に対して両方の結果が生じたときだけです。実際には、その証拠は次の 3 つのいずれかから得られます。

- **実行内の再試行。** テストが失敗し、ランナーが再試行して、再試行が成功します。これは最も低コストなシグナルであり、ほとんどのテストランナーで生成できます。
- **同じコミットの不一致する実行。** 同じコミットと構成に対する 2 回の CI 実行が、あるテストに対して異なる結果を報告します。例えば、プルリクエストでの実行と、誰かが再試行をクリックした後の再実行などです。
- **意図的な繰り返し。** テストが失敗するかどうかを確認するために、意図的に何度も連続して実行します。これは、疑わしい不安定さを確認したり、マージ前に新しいテストが安定しているかどうかをチェックする方法です。

結果が不安定さの証拠としてカウントされるのは、コミット、ビルド構成、デバイスまたはシミュレータ、OS バージョン、ツールチェーンなど、重要な要素がすべて同じ場合のみです。iOS 17 で失敗し iOS 18 で成功するテストは、どちらかに実際の決定論的なバグがある可能性があります。

## ビルドシステムごとの不安定なテスト検出の仕組み {#how-it-works-per-build-system}

各ツールチェーンはテストの再試行と繰り返しを行えますが、結果の記録と報告方法は異なります。

### Xcode {#xcode}

`xcodebuild` とテストプランはテストの繰り返しをサポートしています。`-retry-tests-on-failure` は失敗したテストを再実行し、`-test-iterations <n>` は許可される試行回数を設定し、`-run-tests-until-failure` は失敗するまでテストを繰り返します。これは疑わしい不安定さを再現するのに役立ちます。テストプランは、テスト繰り返しモードと同じオプションに加え、テストをランダムな順序で実行するオプションを提供し、隠れた順序依存性を表面化させます。

すべての試行は `.xcresult` バンドルに保存されるため、失敗してから再試行で成功したテストはそこで確認できます。Xcode は実行をまたいだ履歴を保持しないため、同じ実行内で再試行されない不安定さを検出するには、同じコミットの異なる実行からの結果バンドルを比較する必要があります。

### Gradle {#gradle}

Gradle の `Test` タスクは単独では失敗したテストを再試行しません。[Test Retry プラグイン](https://github.com/gradle/test-retry-gradle-plugin)（`org.gradle.test-retry`）は `Test` タスクに `retry` ブロックを追加し、`maxRetries` や `failOnPassedAfterRetry` などのオプションを提供します。失敗してから成功したテストは、テストレポートと JUnit XML の両方に両方の試行が表示されます。テストフレームワークは独自の繰り返しツールを追加しており、例えば JUnit 5 の `@RepeatedTest` などがあります。

Gradle のビルドキャッシュも不安定さを隠す可能性があります。入力に変更のないキャッシュ可能な `Test` タスクは、実行ではなくキャッシュから復元されるため、一度成功したテストは実行されずに成功し続けます。不安定さを測定する際は、`--rerun-tasks` を使用してテストを強制的に実行するか、ビルドキャッシュを無効にして `Test` タスクを実行してください。

### Bazel {#bazel}

Bazel には組み込みサポートがあります。テストターゲットに `flaky = True` をマークすると、Bazel は最大 3 回実行し、すべての試行が失敗した場合のみ失敗と判定します。`--flaky_test_attempts` フラグはターゲットを変更せずに試行回数を設定し、失敗した試行の後に成功した場合、ターゲットの結果は `FLAKY` として報告されます。意図的に不安定さを測定するには、`--runs_per_test=<n>` でテストを何度も実行し、`--runs_per_test_detects_flakes` は少なくとも 1 回成功し 1 回失敗した場合にシャードを `FLAKY` として報告します。

Bazel はビルド出力をキャッシュするのと同じ方法でテスト結果をキャッシュします。同じ入力で成功したテストは、ローカルおよびリモートキャッシュのどちらからも、再実行せずに `(cached) PASSED` として報告されます。新鮮な実行が必要な場合は `--cache_test_results=no`（または `--nocache_test_results`）を使用してください。Bazel のドキュメントでは、再試行した失敗を永続的に隠してしまうため、`flaky = True` に依存しないよう推奨されています。

### その他のテストランナー {#other-test-runners}

同じパターンはほぼ everywhere に存在します。pytest には `pytest-rerunfailures` プラグインがあり、Jest には `jest.retryTimes()` があり、Elixir の ExUnit には `mix test --repeat-until-failure` があり、使用したランダムシードを出力するため、順序依存の失敗を `--seed` で再生できます。

## 不安定なテストの一般的な原因 {#common-causes}

オープンソースプロジェクトにおける不安定なテストの実証研究（[Luo et al., FSE 2014](https://doi.org/10.1145/2635868.2635920)）では、非同期待機、並行性、テスト順序依存性が最も一般的な根本原因であることがわかりました。以下のリストはそれらと、チームが最も頻繁に遭遇する他の原因をカバーしています。

- **非同期待機と固定スリープ。** テストは作業が完了するまで固定時間待機します。例えば `sleep(1)` や短いタイムアウトを持つ期待値などですが、作業は時々、特に負荷の高い CI マシン上でより長くかかることがあります。条件そのものを、余裕のある上限付きで待機してください。
- **並行性。** 2 つのスレッドまたはタスクが共有データで競合するか、バックグラウンド操作が完了する前にテストがアサートを行います。これらの失敗は多くの場合 CPU 数と負荷に依存するため、高速なラップトップではなく CI で発生します。
- **テスト順序依存性と共有状態。** テストは、他のテストが作成したがクリーンアップを忘れた状態に依存します。シングルトン、データベース行、ディスク上のファイル、`UserDefaults`、環境変数、またはモック化されたグローバルなどです。テストをランダムな順序または並列で実行すると、これが表面化します。
- **時刻と日付。** 実時計を使用するテストは、真夜中、月末、夏時間の変更時、または別のタイムゾーンで失敗します。代わりにクロックを注入してください。
- **シードなしのランダム性と順序なしコレクション。** 記録されたシードなしのランダムデータ、またはハッシュマップやセットの反復順序に依存するアサーション。
- **ネットワークと外部サービス。** 実際のAPI、パッケージレジストリ、または共有ステージング環境への呼び出しは、それらのサービスが遅い、または利用できない場合に失敗します。境界でスタブ化し、少数の明示的な統合テストのみを維持してください。
- **リソース圧力と環境状態。** 低速または過負荷のマシン、リセットされていないシミュレーターやエミュレーター、ディスク容量の逼迫、または他のジョブがすでに使用しているポートなど。無関係な多くのテストが一度に失敗する場合、テスト自体よりも環境を疑ってください。
- **UIテスト。** エンドツーエンドテストとUIテストは、上記のほとんどの原因にアニメーション、レンダリングタイミング、およびシステムダイアログを組み合わせているため、ユニットテストよりも頻繁に不安定になります。

変更後に一貫して失敗するテストは不安定ではありません。それは回帰です。不安定というラベルは、同じコードで両方の結果（成功と失敗）を生み出したテストのために予約すべきです。

## Fixing, retrying, and quarantining {#fixing-retrying-and-quarantining}

チームは通常、3つの対応策を組み合わせますが、これらを区別することが役立ちます：

- 原因を**修正**する。これがテストの価値を回復させる唯一の対応策です。記録された試行、失敗メッセージ、および各失敗した実行の条件は、原因を示す証拠となります。
- パイプラインを進めるために**再試行**する。再試行は有用な検出シグナルですが、無差別な再試行は問題を隠蔽し、失敗するすべての実行にマシンの時間を追加します。成功した再試行は、黙って破棄されるのではなく、依然として不安定な結果として記録されるべきです。
- 修正中のマージブロックを停止させるために、既知の不安定なテストを**隔離**します。隔離されたテストは、失敗を無視して実行され続ける（ミュート）ことで証拠を生み出し続けるか、まったく実行されない（スキップ）ことでカバレッジを失います。隔離には所有者と終了条件が必要であり、否则隔離されたテストが蓄積し、カバレッジが静かに縮小します。

## How to measure flakiness {#how-to-measure-flakiness}

パイプラインごとだけでなく、テストごとに不安定性を追跡してください：

- **不安定率。** テストの実行のうち不安定な結果を生み出した割合：失敗の後に成功する再試行、または同じコミットと構成の別の実行と一致しない結果。
- **影響。** テストがブロックまたは遅延させたパイプライン、プルリクエスト、またはマージキューのエントリ数、およびその再試行が消費したマシン時間。低い不安定率でもすべてのパイプラインで実行されるテストは、非常に不安定だがめったに実行されないテストよりもコストがかかる可能性があります。
- **傾向。** 新しい不安定なテストが、古いものが修正されるよりも速く導入されているかどうか。マージ前に新しいテストや変更されたテストを数回繰り返すことで、多くの不安定性を源流で捕捉できます。

テストが安定していることを確認するには、直感よりも多くの実行が必要です。テストが各実行で確率 *p* で失敗する場合、*n* 回の実行で少なくとも1回の失敗を見る確率は 1 − (1 − p)ⁿ です。1%の時間で失敗するテストの場合、10回の実行では約10%の確率でしか捕捉できず、95%の信頼度で捕捉するには約300回の実行が必要です。わずかな成功した再実行は、修正が機能したという弱い証拠にすぎません。

## When it isn't worth it {#when-it-isnt-worth-it}

すべての不安定なテストが調査に値するわけではなく、すべてのチームが不安定なテスト用のツールを必要とするわけではありません：

- **低価値なテスト。** 不安定なテストが他のテストによってすでに提供されているカバレッジを重複している場合、削除することが適切な修正となり得ます。誰も信頼しないテストは、いずれにせよカバレッジを提供しません。
- **インフラストラクチャの問題。** 障害が1台のマシン、ランナーイメージ、または特定の時間帯に集中している場合、テストを1つずつ修正するよりも環境を修正する方が安上がりです。
- **小規模で高速なスイート。** 高速なスイートを持ち、既知の不安定なテストが1つある小規模なチームの場合、追跡システムよりも共有メモと今週中の修正の方が優れています。専用の検出と隔離は、スイートの規模、貢献者の数、またはパイプラインの数が増え、誰にとってもどの障害がノイズであるかを記憶することが不可能になったときに効果を発揮します。
- **クリティカルパス。** 支払い、データの整合性、またはセキュリティを保護するテストにとって、隔離は間違ったツールです。これらのテストは、不便であっても修正されるまでブロックすべきです。

## Flaky test detection with Tuist {#flaky-test-detection-with-tuist}

[Tuist](https://tuist.dev) は、Xcode、Gradle、Bazel、Elixir、およびその他のサポートされているインテグレーションからのすべてのテスト試行を記録し、同じコードに対して失敗と成功の両方が発生した場合（再試行間、およびサポートされているインテグレーションでは同じコミットのCI実行間）にテストを不安定としてマークします。また、修正中に既知の不安定なテストを手動または自動化によってミュートまたはスキップすることをチームに許可します。サポートと要件はツールチェーンによって異なります：

- <.localized_link href="/guides/features/test-insights/flaky-tests">不安定なテスト</.localized_link> では、検出、隔離、および新しいテストの負荷テストがどのように機能するかを、ツールチェーンごとのガイドとともに説明しています。
- <.localized_link href="/guides/features/test-insights">テストインサイト</.localized_link> では、まずテスト結果を記録する方法について説明しています。
- [私のテストは不安定です](https://tuist.dev/solutions/flaky-tests) は、チームとして不安定なテストを診断し封じ込めるための実践的なガイドです。
