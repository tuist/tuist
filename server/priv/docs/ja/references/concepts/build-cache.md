# ビルドキャッシュとは何ですか？ {#what-is-a-build-cache}

ビルドキャッシュは、コンパイルされたオブジェクトファイル、モジュール、ライブラリ、テスト結果など、個々のビルドステップの出力を、それらの生成に関与したすべての要素（ソースファイル、コンパイラフラグ、依存関係、環境、ツールチェーンのバージョン）から計算されたキーの下に保存します。後続のビルドで、同じキーを生成する入力を持つステップが必要になった場合、ビルドシステムはそのステップを再度実行するのではなく、保存された出力を使用します。**ローカルビルドキャッシュ**は1台のマシン上に存在し、そのマシンでの後続のビルドを高速化します。**リモートビルドキャッシュ**は共有サーバーであり、多くのマシンが読み書きを行うため、CIジョブ、チームメンバー、またはコーディングエージェントが他の誰かがすでにビルドした出力を再利用できます。

## ビルドキャッシュ、インクリメンタルビルド、およびCIキャッシュ {#build-cache-incremental-build-and-ci-cache}

「キャッシュ」と呼ばれる3つの概念があり、それぞれ動作が異なります：

- **インクリメンタルビルド**は、独自のビルドディレクトリにすでに存在する出力を再利用し、そのディレクトリでの最後のビルド以降に変更があった部分のみを再ビルドします。通常、ファイルのタイムスタンプやビルド製品とともに保持される依存関係グラフに依存します。ブランチの切り替え、チェックアウトの移動、または新しいマシンからの開始では、その状態は失われます。
- **ビルドキャッシュ**は、同じディレクトリで最後にビルドされたものではなく、入力のコンテンツに基づいて出力を検索します。これにより、入力が一致する限り、ブランチ、チェックアウト、およびマシン間で出力を再利用できます。
- **CIディレクトリキャッシング**（例えばGitHub Actionsでの`actions/cache`）は、ジョブの終了時にディレクトリを保存し、次のジョブの開始時に、ロックファイルのハッシュなど、選択したキーの下でそれを復元します。これはファイル転送であり、ビルドキャッシュではありません。ビルドシステムは何を再ビルドするかを依然として決定し、復元されたディレクトリは部分的または完全に古くなっている可能性があります。

ダウンロードされたパッケージやGradleまたはSwiftパッケージキャッシュなどの依存関係キャッシュはまた異なり、コンパイルではなくネットワークフェッチを保存します。

## ビルドキャッシュの仕組み {#how-a-build-cache-works}

キャッシングをサポートするビルドシステムは、ビルドをステップに分割し（Bazelではアクション、Gradleではタスクと呼びます）、それぞれに対して同じことを行います：

1. **キャッシュキーを計算する。** ビルドシステムは、出力に影響を与える可能性のあるすべての入力（入力ファイルの内容、コマンドラインまたはタスク構成、関連する環境変数、およびツールチェーン）をハッシュ化します。
2. **キーを検索する。** まずローカルキャッシュを確認し、設定されている場合はリモートキャッシュも確認します。
3. **ヒットまたはミス。** ヒットの場合、保存された出力をダウンロードまたはコピーし、ステップをスキップします。ミスの場合、ステップを実行し、許可されていれば、そのキーの下で出力をアップロードします。

ほとんどのキャッシュは出力を**コンテンツアドレサブルストレージ**（CAS）に保存します。ここでは、各ブロブがそのコンテンツ自身のハッシュの下に保存され、さらにキャッシュキーからそれが生成した出力への別々のインデックスが存在します。同一のファイルは一度だけ保存され、クライアントはダウンロードしたものを検証できます。

このモデルには1つの厳格な要件があります。キーは出力を変更するすべての入力を含める必要があります。もしステップがビルドシステムが認識していない入力（宣言されていないファイル、環境変数、現在時刻、またはマシンにインストールされているツールなど）を読み取る場合、キャッシュは現在の入力と一致しない出力を返す可能性があります。ビルドシステムは、宣言された入力にのみ依存するステップを**ハーメティック**と呼びます。反対の問題はより一般的で危険性は低いです。絶対パスやタイムスタンプなど、無関係なものを含むキーは、すべてのマシンで異なるキーを生成するため、キャッシュは決してヒットしません。

## ビルドシステムごとのビルドキャッシュの仕組み {#how-it-works-per-build-system}

### Gradleビルドキャッシュ {#gradle}

[Gradleビルドキャッシュ](https://docs.gradle.org/current/userguide/build_cache.html)は、JavaおよびKotlinのコンパイルやテスト実行など、キャッシュ可能なタスクの出力を、タスクのタイプ、実装、入力プロパティ、および正規化された入力ファイルによってキー付けして保存します。デフォルトではオフになっています。`gradle.properties`内の`org.gradle.caching=true`、または単一のビルド用に`--build-cache`を使用して有効にします。

- **ローカル。** 組み込みのローカルキャッシュは、Gradleユーザーホーム内のディレクトリです（デフォルトでは`~/.gradle`）。ビルドキャッシュがオンになると有効になり、Gradleは最近使用されていないエントリを定期的に削除します。
- **リモート。** リモートキャッシュは`settings.gradle(.kts)`で構成され、例えば`HttpBuildCache`を使用します。Gradleはローカルミス時にリモートキャッシュから出力をダウンロードし、次回のためにローカルに保存します。リモートキャッシュはデフォルトではアップロードを受け入れません。一般的な設定では、CIがプッシュし（CIで実行中は`isPush = true`）、開発者マシンは読み取りのみを行います。

Gradleは、キャッシュから復元されたタスクを`FROM-CACHE`として報告します。これは`UP-TO-DATE`とは異なります。up-to-dateは、Gradleのインクリメンタルビルドがキャッシュを参照せずにタスクの出力がすでに存在することを意味します。構成キャッシュは、タスクの出力ではなく、構成フェーズの結果をキャッシュする第3の独立した機能です。

### Bazelリモートキャッシュ {#bazel}

Bazelはすべてのアクションをキャッシュします。そのアクションキャッシュは、アクションのキー（コマンドライン、環境、および入力ファイルのダイジェスト）をアクションの出力にマップし、出力自体はコンテンツアドレサブルストアに存在します。

- **ローカル。** Bazelはアクションキャッシュとビルド出力をその出力ベースに保持し、1つのワークスペース内で高速なインクリメンタルビルドを提供します。`--disk_cache=<path>`は、同じマシン上のワークスペースとブランチ間で共有されるディスクキャッシュを追加します。
- **リモート。** `--remote_cache=grpcs://…`（または`https://…`）は、[Remote Execution API](https://github.com/bazelbuild/remote-apis)またはプレーンなHTTPキャッシュを実装するリモートキャッシュをBazelに指定します。`--remote_upload_local_results=false`はマシンを読み取り専用にし、多くのチームが開発者マシンから共有キャッシュへの書き込みを防ぐ方法です。`--remote_download_minimal`または`--remote_download_toplevel`（「バイトなしビルド」）は、ローカルビルドが決して必要としない中間出力のダウンロードを回避します。

Bazelはテスト結果もキャッシュします。入力が変更されていないテストは、実行せずに`(cached) PASSED`として報告されます。リモートキャッシュは、アクションもリモートマシンで実行されるリモート実行と同じではありません。キャッシュは結果のみを保存します。

### Xcodeキャッシュとは何ですか？ {#xcode}

Xcodeは混同しやすいいくつかのキャッシュとディレクトリを使用します。ビルド時間に影響を与えるものは以下の通りです：

- **DerivedData**（`~/Library/Developer/Xcode/DerivedData/<Project>-<hash>/`）は、各プロジェクトのビルド成果物、中間ファイル、インデックス、ログ、および解決済みのSwiftパッケージを保持します。これはインクリメンタルビルドが再利用する状態です。削除しても安全ですが、そのプロジェクトの次のビルドはフルリビルドとなり、インデックス作成とパッケージ解決が再度実行されます。
- **Clangモジュールキャッシュ**（`~/Library/Developer/Xcode/DerivedData/ModuleCache.noindex/`）は、インポートされたCおよびObjective-CモジュールとSDKフレームワーク用の事前コンパイル済みClangモジュール（`.pcm`ファイル）を保持し、プロジェクト間で共有されます。明示的にビルドされたモジュールが有効になっている場合、Xcodeは代わりにモジュールを通常のビルドタスクとしてビルドし、各プロジェクトの中間ファイルと一緒に保持します。削除しても安全です。モジュールは必要に応じて再ビルドされます。
- **コンパイルキャッシュ**（Xcode 26以降、デフォルトではDerivedData内の`CompilationCache.noindex`、`COMPILATION_CACHE_CAS_PATH`で設定可能）は、`COMPILATION_CACHE_ENABLE_CACHING = YES`のときにSwift、C、およびObjective-Cのコンテンツアドレサブルなコンパイル出力を保持します。削除しても安全です。再生可能だったコンパイルが再度実行されます。
- **Swift Package Managerキャッシュ**（`~/Library/Caches/org.swift.swiftpm/`）は、プロジェクト間で共有されるダウンロード済みのパッケージリポジトリとマニフェストを保持します。削除しても安全です。パッケージは再度取得されます。

`~/Library/Developer`の下にある他の大きなディレクトリはビルドキャッシュではありませんが、ディスク容量をクリーンアップする際によく話題になります。`Xcode/Archives`はアーカイブされたアプリビルドとそのデバッグシンボルを保持します（クラッシュのシンボライズに必要になる可能性があるものは保持してください）。`Xcode/iOS DeviceSupport`は接続されたデバイスのOSバージョン用のシンボルを保持し、`CoreSimulator/Devices`はシミュレータとそのデータを保持します（`xcrun simctl delete unavailable`はインストールされなくなったランタイム用のシミュレータを削除します）。

DerivedDataはXcodeのインクリメンタルビルド状態であり、コンテンツアドレサブルキャッシュではありません。ディスク上のプロジェクトの場所とファイルのタイムスタンプに関連付けられています。異なるパスでCIキャッシュからDerivedDataを復元したり、フレッシュなチェックアウト後にすべてのファイルの変更時刻が変わったりすると、多くの場合、結局フルリビルドにつながります。

Xcode 26で導入された**コンパイルキャッシュ**は、このページの文脈におけるXcodeのビルドキャッシュです。入力の内容に基づいてコンパイル結果を保存し、ヒット時にそれを再生するため、出力はブランチの切り替えやビルド成果物のクリーニング後も残ります。これはコンパイルをキャッシュしますが、すべてのビルドステップをキャッシュするわけではありません。リンク、リソース処理、スクリプトフェーズは引き続き実行されます。デフォルトでは、ストアは1台のマシンにローカルでDerivedData内に存在するため、DerivedData全体を削除すると失われます。プロジェクトのビルド成果物のみを削除すれば保持されます。Xcodeはプラグイン（`COMPILATION_CACHE_ENABLE_PLUGIN`および`COMPILATION_CACHE_REMOTE_SERVICE_PATH`）を通じてコンパイルキャッシュをリモートキャッシュサービスに接続することもでき、これにより共有リモートキャッシュになります。

コンパイルキャッシュ以前、Xcodeプロジェクトは主に**バイナリキャッシング**によってマシン間で作業を再利用していました。依存関係を事前ビルドされたフレームワークまたはXCFrameworksとしてビルドし、ソースをコンパイルする代わりにそれらをリンクしていました。これはコンパイルではなくモジュールの粒度で機能し、プロジェクトのビルド方法を変更します。

## レイテンシ、ブロブサイズ、およびブロブ数 {#latency-blob-size-and-blob-count}

リモートキャッシュのヒットにはコストがかかります。出力の取得には、前のリクエストを待たなければならない各リクエストに対する固定の遅延と、バイト転送にかかる時間がかかります。

**time ≈ R × L + S / B**

ここで、*R*は重複できないラウンドトリップの数、*L*はキャッシュへのラウンドトリップレイテンシ、*S*は転送されるバイト数、*B*は帯域幅です。どの項が支配的になるかは、ビルドシステムが作業をどのようにブロブに分割するかによります。

- **少数の大きなブロブは帯域幅制限を受けます。** Gradleタスクのパックされた出力やバイナリモジュールキャッシュ内の事前ビルドされたフレームワークなど、粗い出力を保存するキャッシュは、それぞれがメガバイト単位で移動する少数のリクエストを発行します。200 MBの出力セットは、100 Mbit/sで約16秒、1 Gbit/sで2秒未満かかり、数ミリ秒の追加レイテンシはほとんど影響しません。
- **多数の小さなブロブはレイテンシ制限を受けます。** BazelのアクションごとのキャッシュやXcodeのコンパイルキャッシュなどの細粒度キャッシュは、数キロバイトのブロブに対して数千回のリクエストを行い、その多くはキーが存在するかどうかを確認するためだけです。2,000回のルックアップ、同時に8回の実行中、40 msのレイテンシの場合、ブロブの大きさに関係なく、ビルドはラウンドトリップだけで約10秒待機します。レイテンシが2 msの場合、同じルックアップは約0.5秒かかります。ここでは帯域幅を増やしても役に立ちません。より近いキャッシュが役立ちます。
- **ミスもラウンドトリップのコストがかかります。** ミスしたルックアップはすべて、作業を節約せずにレイテンシを追加します。ヒット率の低い遠隔のキャッシュは、リモートキャッシュがない場合よりもビルドを遅くする可能性があります。
- **ボリュームは両方を増幅します。** ブロブの数はプロジェクトの構造とともに増加します。多くの小さなモジュールまたはターゲットのグラフは、少数の大きなものよりも多くの小さな出力を生み出します。プロジェクトを分割すると並列性と無効化が改善されますが、ビルドはキャッシュレイテンシに対してより敏感になります。

出力の取得が再計算よりも高速な場合にのみ、ヒットは価値があります。そして、その比較は距離によって変化します。ローカルで50 msかかるコンパイルは、同じネットワーク上のキャッシュからのヒットであれば良好ですが、別の大陸のキャッシュからのヒットであれば貧弱です。そのため、リモートキャッシュの調整ポイントは、生の帯域幅ではなく、主にレイテンシとリクエスト数に関するものです。

- **キャッシュを実行環境に近い場所に配置する**。CIランナーと同じリージョンまたはネットワーク内、および開発者にとって実用的に近い場所に配置します。
- **リクエストをオーバーラップさせる。** BazelのRemote Execution APIは存在チェック（`FindMissingBlobs`）と小さな読み取りをバッチ処理し、`--remote_max_connections`は同時実行数を制限します。Xcodeの`COMPILATION_CACHE_ENABLE_DETACHED_KEY_QUERIES`は、実行レーン上ではなく、ビルドの残りの部分と同時にコンパイルキャッシュのルックアップを実行します。HTTP/2は1つの接続上で多くのリクエストを多重化します。
- **ダウンロード量を減らす。** Bazelの`--remote_download_minimal`は中間出力をスキップし、Bazelの`--disk_cache`やGradleのローカルビルドキャッシュなどのローカルキャッシュ層は、ネットワークリクエストなしで繰り返しヒットを提供します。
- **大きなブロブを圧縮する。** Bazelの`--remote_cache_compression`は、キャッシュがサポートしている場合にzstdを使用します。これは帯域幅制限のある転送には役立ちますが、レイテンシ制限のある転送にはあまり効果がありません。

## よくある落とし穴 {#common-pitfalls}

- **宣言されていない入力。** ステップが、キーの一部ではないファイル、環境変数、またはツールを読み取ります。その結果、キャッシュは異なる入力からビルドされた出力を返す可能性があります。Gradleでは、カスタムタスクのすべての入力を宣言してください。Bazelでは、アクションを自己完結型に保ち、ホストの`PATH`が漏れないように`--incompatible_strict_action_env`を検討してください。
- **マシン固有のキー。** 絶対パス、ユーザー名、ビルドタイムスタンプが入力または出力に埋め込まれていると、マシン間でキーが異なり、リモートキャッシュがヒットしなくなります。Gradleのパス感度、Bazelの相対実行パス、およびXcodeのClangとSwiftのプレフィックスマッピング設定は、これらの違いを除去するために存在します。
- **グラフのルート付近にある揮発性入力。** すべてが依存するモジュールにビルド番号、コミットハッシュ、または日付をスタンプすると、すべてのビルドでそれより上位のものが無効化されます。揮発性の値は可能な限り遅く注入し、理想的にはリリースビルドのみに注入してください。
- **ツールチェーンの不一致。** コンパイラ、JDK、またはXcodeのバージョンが異なると、異なるキーが生成されます。これは正しい動作ですが、混合バージョンのフリートは実質的にキャッシュを分割します。
- **汚染された、または信頼できない書き込み。** コミットされていない変更がある開発者マシンや、非自己完結型のセットアップにより、他の人が再利用する出力がアップロードされる可能性があります。多くのチームでは、信頼されたブランチ上のCIのみがリモートキャッシュに書き込むことを許可し、他のすべてのマシンを読み取り専用にしています。信頼されていないプルリクエストのビルドは、信頼されたビルドが読み取るキャッシュに書き込まないでください。
- **転送コストの無視。** 実行に50ミリ秒かかるステップでも、遠隔のキャッシュからの取得にはそれ以上の時間がかかる可能性があります。[レイテンシ、ブロブサイズ、およびブロブ数](#latency-blob-size-and-blob-count)を参照してください。
- **隠れたテスト実行。** テストが決定的である場合、テスト結果をキャッシュすることは正しいですが、一度合格したflakyなテストが実行されずに合格し続けることにもなります。<.localized_link href="/references/concepts/flaky-test">flakyなテストとは何ですか？</.localized_link>を参照してください。

## ビルドキャッシュの測定方法 {#how-to-measure-a-build-cache}

キャッシュの価値は、ヒット率だけでなく、エンドツーエンドで節約できる量によって決まります。

- **作業量で重み付けされたヒット率。** ステップごとのヒットとミスをカウントしますが、各ステップの実行時間で重み付けしてください。安価なステップでの95%のヒット率は、最も遅いコンパイルでの50%のヒット率よりも節約効果が低い場合があります。
- **コールド、ウォーム、および典型的なビルド。** 空のキャッシュでのビルド、完全にウォームされたキャッシュでのビルド、そして人々が実際に実行するビルド（例えば、小さな変更後のプルリクエスト上のCI）を比較してください。重要なのは最後の数値です。
- **キャッシュ自体に費やされた時間。** リクエスト数、レイテンシ、バイト数、およびダウンロードとアップロードに費やされた時間を測定してください。その時間の大部分が多くの小さなリクエストを待っている場合、帯域幅を増やすよりもキャッシュを近くに配置する方が効果的です。少数の大きなブロブを移動している場合は、帯域幅と圧縮の方が重要です。
- **ミスが発生する理由。** 2つのマシンで同じステップのキャッシュキーを比較してください。Gradleは`-Dorg.gradle.caching.debug=true`を使用して各キーの背後にある入力を出力でき、Bazelは2つのビルド間でdiffできる実行ログ（`--execution_log_compact_file`）を書き込め、Xcodeは`COMPILATION_CACHE_ENABLE_DIAGNOSTIC_REMARKS = YES`のときにビルドログでコンパイルキャッシュのヒットとミスを報告します。

## 価値がない場合 {#when-it-isnt-worth-it}

ビルドキャッシュはインフラストラクチャ、セキュリティ境界、および新しい種類のバグを追加します。常に適切なツールとは限りません。

- **小規模または高速なビルド。** クリーンビルドに1分しかかからない場合、リモートキャッシュの節約効果は小さく、ネットワークの往復時間がビルドを遅くする可能性があります。
- **設計上ミスするビルド。** ほとんどのビルドがグラフのルート付近の入力を変更する場合、それが修正されるまでキャッシュは役立ちません。まず無効化の問題を修正してください。キャッシュは入力が一致する作業のみをスキップします。
- **永続的なビルドマシン。** 同じブランチ上のジョブ間でビルドディレクトリを保持するCIマシンは、すでに増分ビルドを利用しています。共有キャッシュは、マシンが一時的な場合、多数のブランチがある場合、または開発者とCIが互いの作業を再利用すべき場合に役立ちます。
- **まだ修正できない非自己完結型ビルド。** 時々間違った出力を返すキャッシュは、時間を節約する以上に信頼を損ないます。まずキャッシュするステップを再現可能にし、問題のあるステップはキャッシュしないままにしてください（例えば、Bazelの`no-remote-cache`タグを使用）。
- **低速または遠隔のネットワーク。** キャッシュがビルド実行場所から遠い場合、全員に展開する前に転送時間を測定してください。

## Tuistでのビルドキャッシング {#build-caching-with-tuist}

[Tuist](https://tuist.dev)は、各ビルドシステムの独自のキャッシングに接続するリモートキャッシュを提供し、開発者マシン、CI、およびコーディングエージェントが互いの出力を再利用できるようにします。また、ヒット、ミス、および転送時間を記録するため、効果を測定できます。

- <.localized_link href="/guides/features/cache/xcode-cache">Xcodeキャッシュ</.localized_link>は、Xcode 26以降の任意のXcodeプロジェクト向けに、Xcodeのコンパイルキャッシュを共有リモートキャッシュに接続します。
- <.localized_link href="/guides/features/cache/module-cache">モジュールキャッシュ</.localized_link>は、Tuistで生成されたプロジェクト内のモジュール全体を事前ビルドされたバイナリに置き換えます。
- <.localized_link href="/guides/features/cache/gradle-cache">Gradleキャッシュ</.localized_link>および<.localized_link href="/guides/features/cache/bazel-cache">Bazelキャッシュ</.localized_link>は、GradleのリモートビルドキャッシュおよびBazelのRemote Execution APIキャッシュとして機能します。
- <.localized_link href="/guides/features/cache">キャッシュ</.localized_link>は、ElixirやStruoを含むサポートされているすべてのビルドシステムを一覧表示します。
- [Slow builds](https://tuist.dev/solutions/slow-builds)は、キャッシュを選択する前に削除する価値のある作業を見つけるための実践的なガイドです。
- [The physics of build systems](https://tuist.dev/blog/2026/08/25/the-physics-of-build-systems)および[Kura](https://tuist.dev/blog/2026/09/14/kura)は、Tuistのキャッシュからの測定値を用いて、モジュールキャッシュ、Xcodeのコンパイルキャッシュ、Bazel、およびGradleの間でアーティファクトサイズとリクエストボリュームがどのように異なるかを説明しています。
