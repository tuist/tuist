# 什么是不稳定测试？{#what-is-a-flaky-test}

不稳定测试是一种自动化测试，在针对相同代码运行时，既可能通过也可能失败，而被测代码或测试本身并未发生任何变化。其结果取决于测试无法控制的因素，例如时序、测试运行顺序、其他测试留下的状态、运行所在的机器，或通过网络调用的服务。因此，不稳定失败并不能可靠地反映被测变更的情况，这也正是不稳定测试代价高昂的原因：在任何人能够信任之前，必须对每个红色结果进行调查或重试。

不稳定现象在各种规模下都很常见。Google 报告称，其所有测试运行中约有 1.5% 产生了不稳定结果，且近 16% 的测试表现出某种程度的不稳定性（[Google 的不稳定测试及我们的缓解措施](https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html)，2016 年）。

## 不稳定测试如何显现{#how-flaky-tests-show-up}

只有当测试针对相同输入产生两种不同结果时，才能确定其为不稳定测试。在实践中，这类证据通常来自以下三个来源之一：

- **运行内的重试。** 测试失败后，运行器对其进行重试，且重试通过。这是成本最低的信号，大多数测试运行器都能提供。
- **同一提交的不同运行结果不一致。** 同一提交和配置的两个 CI 运行对某个测试报告了不同的结果，例如拉取请求中的一次运行与有人点击重试后的再次运行。
- **刻意重复执行。** 故意连续多次运行测试，以观察其是否会出现失败。团队借此确认疑似的不稳定问题，或在合并新测试前检查其稳定性。

只有当所有关键因素都相同时，结果才被视为不稳定性的证据：提交、构建配置、设备或模拟器、操作系统版本以及工具链。在 iOS 17 上失败而在 iOS 18 上通过的测试，可能在其中一个系统上存在真实的确定性缺陷。

## 各构建系统如何检测不稳定测试{#how-it-works-per-build-system}

每种工具链都可以重试和重复执行测试，但它们记录和报告结果的方式各不相同。

### Xcode{#xcode}

`xcodebuild`和测试计划支持测试重复执行。`-retry-tests-on-failure`会重新运行失败的测试，`-test-iterations <n>`设置允许的重试次数，而`-run-tests-until-failure`会重复运行测试直到其失败，这对于复现疑似的不稳定问题很有用。测试计划提供了与测试重复模式相同的选项，并增加了随机顺序运行测试的选项，从而暴露隐藏的顺序依赖关系。

每次尝试都会存储在`.xcresult`包中，因此失败后重试通过的测试可以在其中查看。Xcode 不会跨运行保留历史记录，因此要检测从未在同一运行中重试的不稳定测试，需要比较同一提交在不同运行中的结果包。

### Gradle{#gradle}

Gradle 的`Test`任务本身不会重试失败的测试。[Test Retry 插件](https://github.com/gradle/test-retry-gradle-plugin)（`org.gradle.test-retry`）为`Test`任务添加了一个`retry`块，并提供诸如`maxRetries`和`failOnPassedAfterRetry`等选项。失败后重试通过的测试会在测试报告和 JUnit XML 中显示两次尝试。测试框架还添加了各自的重复执行工具，例如 JUnit 5 的`@RepeatedTest`。

Gradle 的构建缓存也可能掩盖不稳定性：输入未变化的可缓存`Test`任务会从缓存中恢复而非实际运行，因此曾经通过的测试会在不执行的情况下持续显示通过。在测量不稳定性时，请使用`--rerun-tasks`强制运行测试，或在禁用构建缓存的情况下运行`Test`任务。

### Bazel{#bazel}

Bazel 内置了支持。将测试目标标记为`flaky = True`会使 Bazel 最多运行该测试三次，仅在所有尝试都失败时才判定为失败。`--flaky_test_attempts`标志可在不更改目标的情况下设置尝试次数，当测试在失败尝试后通过时，其结果会被报告为`FLAKY`。为了刻意测量不稳定性，`--runs_per_test=<n>`会多次运行测试，而当至少有一次运行通过且有一次失败时，`--runs_per_test_detects_flakes`会将分片报告为`FLAKY`。

Bazel 缓存测试结果的方式与其缓存构建产物相同。使用相同输入通过的测试会被报告为`(cached) PASSED`，不再次运行，无论是本地还是从远程缓存。当需要全新执行时，请使用`--cache_test_results=no`（或`--nocache_test_results`）。Bazel 文档也不建议依赖`flaky = True`，因为它会永久隐藏其重试的失败。

### 其他测试运行器{#other-test-runners}

这种模式几乎无处不在：pytest 拥有`pytest-rerunfailures`插件，Jest 拥有`jest.retryTimes()`，而 Elixir 的 ExUnit 拥有`mix test --repeat-until-failure`并打印所使用的随机种子，以便可以使用`--seed`重放依赖顺序的失败。

## 不稳定测试的常见原因{#common-causes}

一项针对开源项目中不稳定测试的实证研究（[Luo 等人，FSE 2014](https://doi.org/10.1145/2635868.2635920)）发现，异步等待、并发性和测试顺序依赖是最常见的根本原因。下表列出了这些原因以及团队最常遇到的其他原因。

- **异步等待和固定休眠。** 测试等待固定的时间以完成工作，例如`sleep(1)`或带有短超时的期望，而工作有时需要更长时间，尤其是在负载较高的 CI 机器上。应直接等待条件满足，并设置宽松的上限。
- **并发性。** 两个线程或任务在共享数据上发生竞争，或者测试在后台操作完成前就进行了断言。这些失败通常取决于 CPU 数量和负载，因此它们出现在 CI 上而不是快速的笔记本电脑上。
- **测试顺序依赖和共享状态。** 测试依赖于另一个测试创建或忘记清理的状态：单例、数据库行、磁盘上的文件、`UserDefaults`、环境变量或模拟的全局变量。以随机顺序或并行运行测试可以暴露这一问题。
- **时间和日期。** 使用真实时钟的测试会在午夜、月末、跨越夏令时变更或在其他时区失败。改为注入一个时钟对象。
- **无种子的随机性和无序集合。** 没有记录种子的随机数据，或依赖于哈希映射或集合迭代顺序的断言。
- **网络和外部服务。** 当这些服务缓慢或不可用时，对真实 API、包注册表或共享预发布环境的调用会失败。在边界处使用桩替代它们，并保留少量明确的集成测试。
- **资源压力和环境状态。** 机器缓慢或过载、未重置的模拟器或仿真器、磁盘已满，或者端口已被其他作业占用。当许多不相关的测试同时失败时，应先怀疑环境问题，而非测试本身。
- **UI 测试。** 端到端测试和 UI 测试将上述大多数原因与动画、渲染时序以及系统对话框结合在一起，因此它们比单元测试更容易出现不稳定。

在代码变更后持续失败的测试并非不稳定测试，而是回归缺陷。“不稳定”标签应仅用于那些在同一代码上既通过又失败的测试。

## 修复、重试和隔离{#fixing-retrying-and-quarantining}

团队通常会结合使用三种应对措施，将它们区分开来会有所帮助：

- **修复**根本原因。这是唯一能恢复测试价值的应对措施。记录的尝试次数、失败消息以及每次失败运行的环境条件是指向根本原因的证据。
- **重试**以保持流水线继续运行。重试是有用的检测信号，但无差别的重试会掩盖问题，并为每次失败运行增加机器时间。通过重试通过的测试仍应记录为不稳定结果，而不应静默丢弃。
- **隔离**已知的不稳定测试，以便在修复期间不再阻塞合并。被隔离的测试要么继续运行但忽略其失败（静音），从而持续产生证据；要么完全不运行（跳过），从而移除其覆盖范围。隔离需要指定负责人和退出条件，否则被隔离的测试会不断累积，导致覆盖范围悄然缩小。

## 如何衡量不稳定性{#how-to-measure-flakiness}

按每个测试跟踪不稳定性，而不仅仅是按流水线：

- **不稳定率。** 产生不稳定结果的测试运行比例：即先失败后重试通过，或者结果与同一提交和配置的另一轮运行不一致。
- **影响。** 一个测试阻塞或拖慢了多少条流水线、拉取请求或合并队列条目，以及其重试消耗了多少机器时间。一个不稳定率低但在每条流水线中都运行的测试，其成本可能高于一个极不稳定但很少运行的测试。
- **趋势。** 新引入的不稳定测试是否比修复的旧测试增长得更快。在合并前多次重复运行新的或已更改的测试，可以从源头捕获许多不稳定因素。

确认测试稳定所需的运行次数比直觉预期的要多。如果测试在每次运行中失败的概率为*p*，那么在*n*次运行中至少看到一次失败的概率是 1 − (1 − p)ⁿ。对于失败率为 1% 的测试，10 次运行只有约 10% 的概率能捕获到它，而需要约 300 次运行才能以 95% 的置信度捕获到它。少数几次绿色的重跑结果是修复有效的弱证据。

## 何时不值得投入{#when-it-isnt-worth-it}

并非每个不稳定测试都值得调查，也并非每个团队都需要不稳定测试工具：

- **低价值测试。** 如果不稳定测试重复了其他测试已提供的覆盖范围，删除它可能是正确的修复方法。无人信任的测试无论如何都不提供覆盖范围。
- **基础设施问题。** 当失败集中在某台机器、运行器镜像或特定时间段时，修复环境比逐个修复测试更划算。
- **小型、快速的测试套件。** 对于拥有快速测试套件且只有一个已知不稳定测试的小团队，共享笔记并在一周内修复比使用跟踪系统更有效。当测试套件规模、贡献者数量或流水线数量使得任何人都无法记住哪些失败是噪音时，专用的检测和隔离措施才会带来回报。
- **关键路径。** 对于保护支付、数据完整性或安全性的测试，隔离是错误的工具。这些测试应一直阻塞直到修复完成，即使这会带来不便。

## 使用 Tuist 进行不稳定测试检测{#flaky-test-detection-with-tuist}

[Tuist](https://tuist.dev)记录来自 Xcode、Gradle、Bazel、Elixir 和其他受支持集成的每次测试尝试，当测试在同一代码上既失败又通过时（无论是在重试中，还是对于受支持的集成，在同一提交的不同 CI 运行中），将其标记为不稳定，并允许团队在修复期间手动或通过自动化静音或跳过已知的不稳定测试。支持和要求因工具链而异：

- <.localized_link href="/guides/features/test-insights/flaky-tests">不稳定测试</.localized_link>解释了检测、隔离和对新测试进行压力测试的工作原理，并提供了每种工具链的指南。
- <.localized_link href="/guides/features/test-insights">测试洞察</.localized_link>涵盖了首先记录测试结果的内容。
- [我的测试不稳定](https://tuist.dev/solutions/flaky-tests)是一份实用指南，介绍如何以团队形式诊断和控制不稳定测试。
