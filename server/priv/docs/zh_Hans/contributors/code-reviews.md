# 代码审查 {#code-reviews}

审查拉取请求是一种常见的贡献方式。尽管持续集成（CI）能确保代码按预期运行，但这还不够。有些贡献特质无法自动化：设计、代码结构与架构、测试质量或拼写错误。以下各节代表代码审查流程的不同方面。

## 可读性 {#readability}

代码是否清晰表达了其意图？**如果你需要花费大量时间才能弄清代码在做什么，就需要改进代码实现。** 建议将代码拆分为更小、更易理解的抽象。作为备选方案，也可以添加注释来解释背后的推理。问问自己：在没有拉取请求描述等上下文的情况下，你是否能在不久后仍然理解这段代码。

## 小型拉取请求 {#small-pull-requests}

大型拉取请求难以审查，也更容易遗漏细节。如果拉取请求变得过大且难以管理，建议作者将其拆分。

> [!NOTE]
> **例外情况**
>
> 在少数情况下无法拆分拉取请求，例如变更紧密耦合且无法分离。在这些情况下，作者应提供清晰的变更说明及其背后的理由。


## 一致性 {#consistency}

确保变更与项目的其余部分保持一致很重要。不一致会增加维护复杂度，因此我们应避免这种情况。如果已有向用户输出消息或报告错误的既定做法，我们就应遵循。如果作者不同意项目标准，建议他们创建一个议题，以便进一步讨论。

## 测试 {#tests}

测试让你能够自信地修改代码。拉取请求中的代码应当经过测试，并且所有测试都应通过。好的测试能够稳定地产出相同结果，并且易于理解和维护。审查者会将大部分时间花在实现代码上，但测试同样重要，因为它们也是代码。

## 破坏性变更 {#breaking-changes}

破坏性变更会给 Tuist 用户带来糟糕的体验。除非绝对必要，否则贡献应避免引入破坏性变更。我们可以利用许多语言特性来演进 Tuist 的接口，而无需引入破坏性变更。一项变更是否具有破坏性可能并不明显。验证变更是否具有破坏性的一种方法是在 fixtures 目录中的示例项目上运行 Tuist。这需要站在用户的角度，设想这些变更会如何影响他们。
