# 代码审查 {#code-reviews}

审查拉取请求是一种常见的贡献方式。尽管持续集成（CI）能确保代码按预期运行，但这还不够。有些贡献特质无法自动化：设计、代码结构与架构、测试质量或拼写错误。以下各节代表代码审查流程的不同方面。

## 可读性 {#readability}

代码是否清晰表达了其意图？**如果你需要花费大量时间才能弄清楚代码在做什么，就需要改进代码实现。** 建议将代码拆分为更小、更易于理解的抽象。作为备选方案，也是最后的手段，可以添加注释来解释背后的理由。问问自己，在没有拉取请求描述等周围上下文的情况下，你是否能在不久的将来理解这段代码。

## 小型拉取请求 {#small-pull-requests}

大型拉取请求难以审查，容易遗漏细节。如果拉取请求变得过于庞大且难以管理，建议作者将其拆分。

> [!NOTE]
> **例外情况**
>
> 在少数情况下，无法拆分拉取请求，例如当变更紧密耦合且无法拆分时。在这些情况下，作者应提供清晰的变更说明及其背后的理由。


## 一致性 {#consistency}

确保变更与项目的其余部分保持一致非常重要。不一致会增加维护的复杂性，因此我们应避免这种情况。如果项目中已有向用户输出消息或报告错误的方式，我们应遵循该方式。如果作者不同意项目标准，建议他们提出一个问题，以便进一步讨论。

## 测试 {#tests}

测试让你能够自信地更改代码。拉取请求中的代码应经过测试，并且所有测试都应通过。好的测试是指能稳定产生相同结果、且易于理解和维护的测试。审查者会将大部分审查时间花在实现代码上，但测试同样重要，因为它们也是代码。

## 破坏性变更 {#breaking-changes}

破坏性变更会给 Tuist 用户带来糟糕的体验。除非绝对必要，否则贡献应避免引入破坏性变更。我们可以利用许多语言特性来演进 Tuist 的接口，而无需诉诸破坏性变更。变更是否具有破坏性可能并不明显。验证变更是否具有破坏性的一种方法是在 fixtures 目录中对 fixture 项目运行 Tuist。这需要设身处地从用户的角度思考，想象这些变更会如何影响他们。
