# 이슈 보고 {#issue-reporting}

Tuist 사용 중 버그나 예상치 못한 동작을 마주할 수 있습니다. 이런 경우 문제를 보고해 주시면 수정하는 데 도움이 됩니다.

## GitHub 이슈는 티켓팅 플랫폼입니다 {#github-issues-is-our-ticketing-platform}

이슈는 Slack이나 다른 플랫폼이 아닌 GitHub의 [GitHub issues](https://github.com/tuist/tuist/issues)로 보고해야 합니다. GitHub는 이슈를 추적하고 관리하기에 적합하며 코드베이스와 가까워 진행 상황을 파악하기 쉽습니다. 또한 장문의 문제 설명을 유도해 보고자가 문제를 깊이 생각하고 더 많은 맥락을 제공하도록 돕습니다.

## 맥락이 중요합니다 {#context-is-crucial}

충분한 맥락이 없는 이슈는 불완전하다고 판단되며 추가 정보를 요청합니다. 정보가 제공되지 않으면 이슈는 종료됩니다. 맥락을 많이 제공할수록 문제를 이해하고 해결하기 쉬워진다고 생각하세요. 이슈가 해결되길 원한다면 가능한 한 많은 맥락을 제공하세요. 다음 질문에 답해 보세요.

- 무엇을 하려고 했나요?
- 그래프 구조는 어떻게 되나요?
- 사용 중인 Tuist 버전은 무엇인가요?
- 이 문제로 작업이 막혔나요?

최소한의 **재현 가능한 프로젝트**도 함께 제공해야 합니다.

## 재현 가능한 프로젝트 {#reproducible-project}

### 재현 가능한 프로젝트란 무엇인가요? {#what-is-a-reproducible-project}

재현 가능한 프로젝트는 문제를 보여주는 작은 Tuist 프로젝트로, 대부분 Tuist의 버그가 원인입니다. 재현 가능한 프로젝트에는 버그를 명확히 보여주기 위해 필요한 최소한의 기능만 포함해야 합니다.

### 왜 재현 가능한 테스트 케이스를 만들어야 하나요? {#why-should-you-create-a-reproducible-test-case}

재현 가능한 프로젝트를 통해 문제의 원인을 격리할 수 있으며, 이는 해결을 위한 첫걸음입니다. 모든 버그 보고서에서 가장 중요한 부분은 버그를 재현하는 정확한 단계를 설명하는 것입니다.

재현 가능한 프로젝트는 버그를 유발하는 특정 환경을 공유하는 좋은 방법입니다. 도움을 주고자 하는 사람들에게 가장 효과적인 지원 수단입니다.

### 재현 가능한 프로젝트 생성 단계 {#steps-to-create-a-reproducible-project}

- 새 Git 리포지토리를 만듭니다.
- 리포지토리 디렉터리에서 `tuist init`를 사용해 프로젝트를 초기화합니다.
- 발생한 오류를 재현하는 데 필요한 코드를 추가합니다.
- 코드를 공개합니다(GitHub 계정이 적합하며), 이슈를 생성할 때 해당 코드로 링크합니다.

### 재현 가능한 프로젝트의 이점 {#benefits-of-reproducible-projects}

- **범위 축소:** 오류 외의 요소를 제거하면 버그를 찾는 데 시간을 낭비하지 않아도 됩니다.
- **비밀 코드 공개 불필요:** 여러 이유로 메인 사이트를 공개하기 어려울 수 있습니다. 일부만 재현 가능한 테스트 케이스로 다시 만들면 비밀 코드를 노출하지 않고도 문제를 공개적으로 시연할 수 있습니다.
- **버그 입증:** 때로는 머신의 설정 조합으로 인해 버그가 발생하기도 합니다. 재현 가능한 테스트 케이스를 사용하면 기여자가 빌드를 내려받아 자신의 머신에서도 테스트할 수 있어 문제 원인을 검증하고 좁히는 데 도움이 됩니다.
- **버그 수정 도움 받기:** 다른 사람이 문제를 재현할 수 있다면 해결 가능성도 높아집니다. 재현이 불가능하면 버그를 수정하는 것은 거의 불가능합니다.
