# 코드 리뷰 {#code-reviews}

풀 리퀘스트 검토는 일반적인 기여 방식입니다. 지속적 통합(CI)이 코드가 의도대로 동작하는지 보장하더라도 충분하지 않습니다. 디자인, 코드 구조 및 아키텍처, 테스트 품질, 오타 등 자동화할 수 없는 기여 특성이 있습니다. 다음 섹션에서는 코드 리뷰 프로세스의 다양한 측면을 다룹니다.

## 가독성 {#readability}

코드가 의도를 명확히 표현하고 있나요? **코드가 무엇을 하는지 이해하는 데 많은 시간이 필요하다면 코드 구현을 개선해야 합니다.** 이해하기 쉬운 작은 추상화로 코드를 분할하도록 제안하세요. 대안으로, 마지막 수단으로 그 배경 이유를 설명하는 주석을 추가할 수 있습니다. 풀 리퀘스트 설명과 같은 주변 맥락 없이도 가까운 미래에 코드를 이해할 수 있을지 자문해 보세요.

## 작은 풀 리퀘스트 {#small-pull-requests}

큰 풀 리퀘스트는 검토하기 어렵고 세부 사항을 놓치기 쉽습니다. 풀 리퀘스트가 너무 크고 관리하기 어려워지면 작성자에게 분할하도록 제안하세요.

> [!NOTE]
> **예외**
>
> 변경 사항이 긴밀하게 결합되어 분할할 수 없는 경우처럼 풀 리퀘스트를 분할할 수 없는 시나리오가 몇 가지 있습니다. 이러한 경우 작성자는 변경 사항과 그 배경 이유를 명확히 설명해야 합니다.


## 일관성 {#consistency}

변경 사항이 프로젝트의 나머지 부분과 일관성을 유지하는 것이 중요합니다. 불일치는 유지보수를 복잡하게 하므로 피해야 합니다. 사용자에게 메시지를 출력하거나 오류를 보고하는 접근 방식이 있다면 이를 준수해야 합니다. 작성자가 프로젝트 표준에 동의하지 않으면 해당 사항을 추가로 논의할 수 있는 이슈를 열도록 제안하세요.

## 테스트 {#tests}

테스트를 통해 자신 있게 코드를 변경할 수 있습니다. 풀 리퀘스트의 코드는 테스트되어야 하며 모든 테스트가 통과해야 합니다. 좋은 테스트는 일관되게 동일한 결과를 생성하며 이해하고 유지보수하기 쉬운 테스트입니다. 리뷰어는 대부분의 리뷰 시간을 구현 코드에 할애하지만, 테스트 역시 코드이므로 마찬가지로 중요합니다.

## Breaking changes {#breaking-changes}

Breaking changes는 Tuist 사용자에게 나쁜 사용자 경험을 제공합니다. 기여 시 엄격히 필요한 경우가 아니면 breaking changes 도입을 피해야 합니다. Breaking change에 의존하지 않고 Tuist 인터페이스를 진화시키기 위해 활용할 수 있는 언어 기능이 많이 있습니다. 변경 사항이 breaking인지 여부는 분명하지 않을 수 있습니다. 변경 사항이 breaking인지 확인하는 한 가지 방법은 fixtures 디렉터리의 fixture 프로젝트에서 Tuist를 실행하는 것입니다. 사용자의 입장에서 생각하여 변경 사항이 사용자에게 어떤 영향을 미칠지 상상해야 합니다.
