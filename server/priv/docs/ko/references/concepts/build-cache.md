# 빌드 캐시란 무엇인가요? {#what-is-a-build-cache}

빌드 캐시는 소스 파일, 컴파일러 플래그, 의존성, 환경 및 툴체인 버전 등 산출물 생성에 관여한 모든 요소로부터 계산된 키를 사용하여 컴파일된 오브젝트 파일, 모듈, 라이브러리 또는 테스트 결과와 같은 개별 빌드 단계의 산출물을 저장합니다. 이후 빌드에서 동일한 키를 생성하는 입력을 가진 단계가 필요할 때, 빌드 시스템은 해당 단계를 다시 실행하는 대신 저장된 산출물을 사용합니다. **로컬 빌드 캐시**는 한 머신에 존재하며 해당 머신의 후속 빌드 속도를 높입니다. **원격 빌드 캐시**는 여러 머신이 읽고 쓸 수 있는 공유 서버로, CI 작업, 팀원 또는 코딩 에이전트가 다른 사람이 이미 빌드한 산출물을 재사용할 수 있게 합니다.

## 빌드 캐시, 증분 빌드 및 CI 캐시 {#build-cache-incremental-build-and-ci-cache}

세 가지 개념이 종종 "캐시"라고 불리며, 각각 동작 방식이 다릅니다:

- **증분 빌드**는 빌드 디렉터리에 이미 있는 산출물을 재사용하고, 해당 디렉터리에서 마지막 빌드 이후 변경된 부분만 다시 빌드합니다. 일반적으로 파일 타임스탬프나 빌드 산출물과 함께 유지되는 의존성 그래프에 의존합니다. 브랜치를 전환하거나 체크아웃 위치를 이동하거나 새 머신에서 시작하면 이 상태가 손실됩니다.
- **빌드 캐시**는 동일한 디렉터리에서 마지막으로 빌드된 내용이 아니라 입력의 콘텐츠 기준으로 산출물을 조회합니다. 따라서 입력이 일치하는 한 브랜치, 체크아웃 및 머신을 넘어 산출물을 재사용할 수 있습니다.
- **CI 디렉터리 캐싱**(예: GitHub Actions의 `actions/cache`)은 잠금 파일 해시와 같이 사용자가 선택한 키를 사용하여 작업 종료 시 디렉터리를 저장하고 다음 작업 시작 시 복원합니다. 이는 파일 전송일 뿐 빌드 캐시가 아닙니다. 빌드 시스템은 여전히 무엇을 다시 빌드할지 결정하며, 복원된 디렉터리는 일부 또는 전체가陈旧할 수 있습니다.

다운로드된 패키지나 Gradle 또는 Swift 패키지 캐시와 같은 의존성 캐시는 또 다릅니다. 이들은 컴파일이 아닌 네트워크 가져오기를 저장합니다.

## 빌드 캐시 작동 방식 {#how-a-build-cache-works}

캐싱을 지원하는 빌드 시스템은 빌드를 단계로 분할합니다(Bazel은 이를 액션이라고 부르고, Gradle은 태스크라고 부름). 각 단계마다 다음과 같은 작업을 수행합니다:

1. **캐시 키 계산.** 빌드 시스템은 산출물에 영향을 줄 수 있는 모든 입력(입력 파일의 내용, 명령줄 또는 태스크 구성, 관련 환경 변수 및 툴체인)을 해싱합니다.
2. **키 조회.** 로컬 캐시를 먼저 확인하고, 구성된 경우 원격 캐시도 확인합니다.
3. **히트 또는 미스.** 히트 시 저장된 산출물을 다운로드하거나 복사하고 단계를 건너뜁니다. 미스 시 단계를 실행하고 허용되는 경우 해당 키로 산출물을 업로드합니다.

대부분의 캐시는 **콘텐츠 주소 지정 스토리지**(CAS)에 산출물을 저장합니다. 여기서 각 블롭은 자체 콘텐츠의 해시 아래에 저장되며, 캐시 키에서 해당 키가 생성한 산출물로 매핑되는 별도의 인덱스가 존재합니다. 동일한 파일은 한 번만 저장되며, 클라이언트는 다운로드한 내용을 검증할 수 있습니다.

이 모델에는 한 가지 엄격한 요구 사항이 있습니다. 키는 산출물을 변경하는 모든 입력을 포함해야 합니다. 만약 단계가 빌드 시스템이 알지 못하는 입력(선언되지 않은 파일, 환경 변수, 현재 시간 또는 머신에 설치된 도구 등)을 읽으면, 캐시는 현재 입력과 일치하지 않는 산출물을 반환할 수 있습니다. 빌드 시스템은 선언된 입력에만 의존하는 단계를 **허메틱(hermetic)** 이라고 부릅니다. 반대 문제는 더 흔하고 덜 위험합니다. 절대 경로나 타임스탬프와 같은 무관한 것을 포함하는 키는 모든 머신에서 서로 다른 키를 생성하므로 캐시가 전혀 히트되지 않습니다.

## 빌드 시스템별 빌드 캐시 작동 방식 {#how-it-works-per-build-system}

### Gradle 빌드 캐시 {#gradle}

[Gradle 빌드 캐시](https://docs.gradle.org/current/userguide/build_cache.html)는 Java 및 Kotlin 컴파일과 테스트 실행과 같은 캐싱 가능 태스크의 산출물을 태스크 유형, 구현, 입력 속성 및 정규화된 입력 파일을 키로 하여 저장합니다. 기본적으로 비활성화되어 있습니다. `gradle.properties`에서 `org.gradle.caching=true`를 사용하거나 단일 빌드의 경우 `--build-cache`를 사용하여 활성화하세요.

- **로컬.** 내장 로컬 캐시는 Gradle 사용자 홈(`~/.gradle`가 기본값)의 디렉터리입니다. 빌드 캐시가 활성화되면 자동으로 사용되며, Gradle은 최근에 사용하지 않은 항목을 주기적으로 제거합니다.
- **원격.** 원격 캐시는 `settings.gradle(.kts)`에서 구성하며, 예를 들어 `HttpBuildCache`를 사용합니다. Gradle은 로컬 미스 시 원격 캐시에서 산출물을 다운로드하고 다음 사용을 위해 로컬에 저장합니다. 원격 캐시는 기본적으로 업로드를 허용하지 않습니다. 일반적인 설정에서는 CI가 푸시하도록 하고(`isPush = true` CI에서 실행 시) 개발자 머신은 읽기 전용으로 제한합니다.

Gradle은 캐시에서 복원된 태스크를 `FROM-CACHE`로 보고하며, 이는 `UP-TO-DATE`와 다릅니다. up-to-date는 Gradle의 증분 빌드가 캐시를 참조하지 않고도 태스크의 산출물이 이미 제자리에 있음을 발견했음을 의미합니다. 구성 캐시는 태스크 산출물이 아닌 구성 단계의 결과를 캐싱하는 세 번째 별도 기능입니다.

### Bazel 원격 캐시 {#bazel}

Bazel은 모든 액션을 캐시합니다. 액션 캐시는 액션의 키(명령줄, 환경 및 입력 파일의 다이제스트)를 액션의 산출물에 매핑하며, 산출물 자체는 콘텐츠 주소 지정 스토어에 저장됩니다.

- **로컬.** Bazel은 출력 베이스에 액션 캐시와 빌드 산출물을 유지하여 한 워크스페이스 내에서 빠른 증분 빌드를 제공합니다. `--disk_cache=<path>`는 동일한 머신의 워크스페이스와 브랜치 간에 공유되는 디스크 캐시를 추가합니다.
- **원격.** `--remote_cache=grpcs://…`(또는 `https://…`)는 [Remote Execution API](https://github.com/bazelbuild/remote-apis) 또는 일반 HTTP 캐시를 구현하는 원격 캐시를 가리킵니다. `--remote_upload_local_results=false`는 머신을 읽기 전용으로 만들어 많은 팀이 개발자 머신이 공유 캐시에 쓰는 것을 방지하는 방법입니다. `--remote_download_minimal` 또는 `--remote_download_toplevel`("바이트 없이 빌드")는 로컬 빌드가 필요로 하지 않는 중간 산출물의 다운로드를 피합니다.

Bazel은 테스트 결과도 캐시합니다. 입력이 변경되지 않은 테스트는 실행 없이 `(cached) PASSED`로 보고됩니다. 원격 캐시는 액션이 원격 머신에서도 실행되는 원격 실행과 동일하지 않으며, 캐시는 결과만 저장합니다.

### Xcode 캐시란 무엇인가요? {#xcode}

Xcode는 혼동하기 쉬운 여러 캐시와 디렉터리를 사용합니다. 빌드 시간에 영향을 미치는 것은 다음과 같습니다:

- **DerivedData**(`~/Library/Developer/Xcode/DerivedData/<Project>-<hash>/`)는 각 프로젝트의 빌드 산출물, 중간 파일, 인덱스, 로그 및 해결된 Swift 패키지를 보관합니다. 이는 증분 빌드가 재사용하는 상태입니다. 이를 삭제해도 안전하지만, 해당 프로젝트의 다음 빌드는 전체 재빌드가 되며 인덱싱과 패키지 해결이 다시 실행됩니다.
- **Clang 모듈 캐시**(`~/Library/Developer/Xcode/DerivedData/ModuleCache.noindex/`)는 가져온 C 및 Objective-C 모듈과 SDK 프레임워크를 위한 사전 컴파일된 Clang 모듈(`.pcm` 파일)을 보관하며, 프로젝트 간에 공유됩니다. 명시적으로 빌드된 모듈이 활성화되면 Xcode는 대신 모듈을 일반 빌드 태스크로 빌드하고 각 프로젝트의 중간 파일과 함께 유지합니다. 이를 삭제해도 안전하며 모듈은 필요에 따라 다시 빌드됩니다.
- **컴파일레이션 캐시**(Xcode 26 이상, 기본적으로 DerivedData 내부의 `CompilationCache.noindex`, `COMPILATION_CACHE_CAS_PATH`로 구성 가능)는 `COMPILATION_CACHE_ENABLE_CACHING = YES`일 때 Swift, C 및 Objective-C용 콘텐츠 주소 지정 컴파일 출력물을 보관합니다. 이를 삭제해도 안전하며, 재실행될 수 있었던 컴파일레이션이 다시 실행됩니다.
- **Swift Package Manager 캐시**(`~/Library/Caches/org.swift.swiftpm/`)는 다운로드된 패키지 리포지토리 및 매니페스트를 보관하며 프로젝트 간에 공유됩니다. 이를 삭제해도 안전하며 패키지는 다시 가져옵니다.

`~/Library/Developer` 아래의 다른 대형 디렉터리는 빌드 캐시가 아니지만 디스크 공간을 정리할 때 자주 언급됩니다. `Xcode/Archives`는 아카이브된 앱 빌드와 디버그 심볼을 보관하며(크래시 심볼화 시 필요한 것을 유지), `Xcode/iOS DeviceSupport`는 연결된 기기의 OS 버전용 심볼을 보관하고, `CoreSimulator/Devices`는 시뮬레이터와 해당 데이터를 보관합니다(`xcrun simctl delete unavailable`는 더 이상 설치되지 않은 런타임용 시뮬레이터를 제거합니다).

DerivedData는 Xcode의 증분 빌드 상태로, 콘텐츠 주소 지정 캐시가 아닙니다. 디스크상의 프로젝트 위치와 파일 타임스탬프에 연결되어 있습니다. CI 캐시에서 다른 경로로 DerivedData를 복원하거나, 새 체크아웃으로 모든 파일의 수정 시간이 변경된 후에는 종종 전체 재빌드가 발생합니다.

Xcode 26에서 도입된 **컴파일레이션 캐시**는 이 페이지에서 의미하는 바의 Xcode 빌드 캐시입니다. 입력물의 콘텐츠를 기준으로 컴파일 결과를 저장하고 히트 시 이를 재실행하므로, 브랜치 전환이나 빌드 산출물 정리 후에도 출력이 유지됩니다. 이는 컴파일레이션만 캐시하며 모든 빌드 단계를 캐시하지는 않습니다. 링킹, 리소스 처리 및 스크립트 단계는 여전히 실행됩니다. 기본적으로 스토어는 한 머신에 로컬이며 DerivedData 내부에 존재하므로 DerivedData 전체를 삭제하면 함께 제거되지만, 프로젝트의 빌드 산출물만 삭제하면 유지됩니다. Xcode는 플러그인(`COMPILATION_CACHE_ENABLE_PLUGIN` 및 `COMPILATION_CACHE_REMOTE_SERVICE_PATH`)을 통해 컴파일레이션 캐시를 원격 캐시 서비스에 연결할 수도 있으며, 이를 공유 원격 캐시로 변환합니다.

컴파일레이션 캐시 이전에는 Xcode 프로젝트가 머신 간 작업을 주로 **바이너리 캐싱**을 통해 전체 모듈 단위로 재사용했습니다. 종속성을 사전 빌드된 프레임워크 또는 XCFrameworks로 빌드하고 소스를 컴파일하는 대신 이를 링크하는 방식입니다. 이는 컴파일레이션이 아닌 모듈 단위로 작동하며 프로젝트 빌드 방식을 변경합니다.

## 지연 시간, 블롭 크기 및 블롭 수 {#latency-blob-size-and-blob-count}

원격 캐시 히트는 무료가 아닙니다. 출력을 가져오는 데에는 이전 요청을 기다려야 하는 모든 요청에 대한 고정 지연 시간과 바이트를 전송하는 시간이 추가로 소요됩니다.

**time ≈ R × L + S / B**

여기서 *R*은 겹칠 수 없는 라운드 트립 수, *L*은 캐시까지의 라운드 트립 지연 시간, *S*는 전송된 바이트 수, *B*는 대역폭입니다. 어떤 항이 지배적인지는 빌드 시스템이 작업을 어떻게 블롭으로 나누는지에 따라 달라집니다.

- **적고 큰 블롭은 대역폭 제한적입니다.** Gradle 태스크의 압축된 출력물이나 바이너리 모듈 캐시의 사전 빌드된 프레임워크와 같이 거친 출력물을 저장하는 캐시는 각각 메가바이트 단위로 이동하는 적은 수의 요청을 생성합니다. 200MB의 출력물 세트는 100Mbit/s에서 약 16초, 1Gbit/s에서 2초 미만이 걸리며, 몇 밀리초의 추가 지연 시간은 거의 영향을 미치지 않습니다.
- **많은 작은 블롭은 지연 시간 제한적입니다.** Bazel의 액션별 캐시나 Xcode의 컴파일레이션 캐시와 같은 세분화된 캐시는 수 킬로바이트 크기의 블롭에 대해 수천 건의 요청을 발생시키며, 그중 많은 것은 키 존재 여부만 확인하기 위한 것입니다. 2,000번 조회, 동시 8개 처리, 40ms 지연 시간 조건에서 빌드는 블롭 크기와 무관하게 라운드 트립만으로 약 10초를 대기합니다. 지연 시간이 2ms라면 동일한 조회는 약 0.5초가 걸립니다. 여기서 대역폭 증가는 도움이 되지 않으며, 캐시의 물리적 근접성이 중요합니다.
- **미스도 라운드 트립 비용이 발생합니다.** 미스되는 모든 조회는 작업을 절약하지 않고 지연 시간만 추가합니다. 히트율이 낮은 원격 캐시는 원격 캐시가 전혀 없는 경우보다 빌드를 더 느리게 만들 수 있습니다.
- **볼륨은 두 요소 모두를 증폭시킵니다.** 블롭 수는 프로젝트 구조에 따라 증가합니다. 많은 소규모 모듈이나 타겟으로 구성된 그래프는 몇 개의 대규모 모듈보다 더 많고 작은 출력물을 생성합니다. 프로젝트를 분할하면 병렬성과 무효화 처리가 개선되지만, 빌드가 캐시 지연 시간에 더 민감해집니다.

출력을 가져오는 것이 다시 계산하는 것보다 빠를 때만 히트가 가치가 있으며, 이 비교 결과는 거리에 따라 달라집니다. 로컬에서 50ms가 걸리는 컴파일레이션은 동일 네트워크 내 캐시에서는 좋은 히트이지만, 다른 대륙의 캐시에서는 효율이 떨어집니다. 따라서 원격 캐시의 주요 조절 레버는 원시 대역폭보다는 지연 시간과 요청 횟수와 관련이 있습니다.

- **캐시를 빌드가 실행되는 위치와 가깝게 배치하세요**. CI 러너와 동일한 지역 또는 네트워크에 두고, 개발자에게도 가능한 한 가깝게 유지합니다.
- **요청을 중복 처리하세요.** Bazel의 Remote Execution API는 존재 확인(`FindMissingBlobs`)과 작은 읽기를 일괄 처리하며, `--remote_max_connections`는 동시성을 제한합니다. Xcode의 `COMPILATION_CACHE_ENABLE_DETACHED_KEY_QUERIES`는 컴파일레이션 캐시 조회를 실행 레인이 아닌 빌드 나머지 과정과 동시에 실행합니다. HTTP/2는 하나의 연결로 여러 요청을 다중화합니다.
- **다운로드량을 줄이세요.** Bazel의 `--remote_download_minimal`는 중간 출력물을 건너뛰며, Bazel의 `--disk_cache`나 Gradle의 로컬 빌드 캐시와 같은 로컬 캐시 계층은 네트워크 요청 없이 반복 히트를 제공합니다.
- **대형 블롭을 압축하세요.** Bazel의 `--remote_cache_compression`는 캐시가 지원할 때 zstd를 사용하며, 이는 대역폭 제한 전송에는 도움이 되지만 지연 시간 제한 전송에는 효과가 미미합니다.

## 일반적인 함정 {#common-pitfalls}

- **선언되지 않은 입력값.** 단계가 키에 포함되지 않은 파일, 환경 변수 또는 도구를 읽습니다. 그러면 캐시가 다른 입력값으로 빌드된 출력을 반환할 수 있습니다. Gradle에서는 커스텀 작업의 모든 입력값을 선언하고, Bazel에서는 작업을 격리 상태로 유지하며 호스트 `PATH`가 누출되지 않도록 `--incompatible_strict_action_env`를 고려하세요.
- **머신별 키.** 입력값이나 출력값에 포함된 절대 경로, 사용자 이름 및 빌드 타임스탬프로 인해 머신 간 키가 달라지므로 원격 캐시에서 히트가 발생하지 않습니다. Gradle의 경로 민감도, Bazel의 상대 실행 경로, Xcode의 Clang 및 Swift 전접 매핑 설정은 이러한 차이를 제거하기 위해 존재합니다.
- **그래프 루트 근처의 휘발성 입력값.** 모든 것이 의존하는 모듈에 빌드 번호, 커밋 해시 또는 날짜를 찍으면 매 빌드마다 그 위의 모든 것이 무효화됩니다. 휘발성 값은 가능한 한 늦게, 이상적으로는 릴리스 빌드에만 주입하세요.
- **툴체인 불일치.** 컴파일러, JDK 또는 Xcode 버전이 다르면 키도 달라집니다. 이는 올바른 동작이지만, 버전이 혼합된 플릿은 효과적으로 캐시를 분할합니다.
- **오염되었거나 신뢰할 수 없는 쓰기.** 커밋되지 않은 변경 사항이 있거나 격리되지 않은 설정을 가진 개발자 머신이 다른 사람이 재사용하는 출력을 업로드할 수 있습니다. 많은 팀은 신뢰할 수 있는 브랜치의 CI만 원격 캐시에 쓰기를 허용하고 다른 모든 머신은 읽기 전용으로 만듭니다. 신뢰할 수 없는 풀 요청의 빌드는 신뢰할 수 있는 빌드가 읽는 캐시에 쓰지 않아야 합니다.
- **전송 비용 무시.** 실행에 50밀리초가 걸리는 단계는 원격 캐시에서 가져오는 데 더 오래 걸릴 수 있습니다. [지연 시간, 블롭 크기 및 블롭 수](#latency-blob-size-and-blob-count)를 참조하세요.
- **숨겨진 테스트 실행.** 테스트가 결정론적일 때 테스트 결과를 캐싱하는 것은 올바르지만, 한 번 통과한 불안정한 테스트가 실행 없이 계속 통과한다는 의미이기도 합니다. <.localized_link href="/references/concepts/flaky-test">불안정한 테스트란 무엇인가요?</.localized_link>를 참조하세요.

## 빌드 캐시 측정 방법 {#how-to-measure-a-build-cache}

캐시의 가치는 히트율 자체가 아니라 종단 간 절약되는 비용으로 결정됩니다.

- **작업량으로 가중치를 적용한 히트율.** 단계별 히트와 미스를 계산하지만, 각 단계 실행 시간에 따라 가중치를 적용하세요. 저렴한 단계에서 95% 히트율은 가장 느린 컴파일레이션에서 50% 히트율보다 적게 절약할 수 있습니다.
- **콜드, 웜 및 일반적인 빌드.** 빈 캐시가 있는 빌드, 완전히 웜업된 캐시가 있는 빌드, 그리고 사람들이 실제로 실행하는 빌드(예: 작은 변경 후 풀 요청에 대한 CI)를 비교하세요. 마지막 것이 중요한 수치입니다.
- **캐시 자체에 소요된 시간.** 요청 수, 지연 시간, 바이트 수, 다운로드 및 업로드에 소요된 시간을 측정하세요. 대부분의 시간이 많은 작은 요청을 기다리는 데 소요된다면 대역폭 증가보다 캐시 위치를 가까이 하는 것이 더 도움이 됩니다. 몇 개의 대형 블롭을 이동하는 데 시간이 소요된다면 대역폭과 압축이 더 중요합니다.
- **미스 발생 원인.** 두 머신에서 동일한 단계의 캐시 키를 비교하세요. Gradle은 `-Dorg.gradle.caching.debug=true`로 각 키 뒤의 입력값을 출력할 수 있고, Bazel은 두 빌드 간 차이 비교가 가능한 실행 로그(`--execution_log_compact_file`)를 작성할 수 있으며, Xcode는 `COMPILATION_CACHE_ENABLE_DIAGNOSTIC_REMARKS = YES`일 때 빌드 로그에 컴파일레이션 캐시 히트와 미스를 보고합니다.

## 가치가 없을 때 {#when-it-isnt-worth-it}

빌드 캐시는 인프라, 보안 경계 및 새로운 종류의 버그를 추가합니다. 항상 올바른 도구는 아닙니다.

- **소규모 또는 빠른 빌드.** 클린 빌드에 1분이 걸린다면 원격 캐시는 거의 절약되지 않으며, 네트워크 라운드 트립으로 인해 더 느려질 수 있습니다.
- **설계상 미스가 발생하는 빌드.** 대부분의 빌드가 그래프 루트 근처의 입력값을 변경하면, 해당 문제가 해결될 때까지 캐시가 도움이 되지 않습니다. 먼저 무효화 문제를 해결하세요. 캐시는 입력값이 일치하는 작업만 건너뜁니다.
- **지속적인 빌드 머신.** 동일 브랜치의 작업 간에 빌드 디렉터리를 유지하는 CI 머신은 이미 증분 빌드를 수행합니다. 공유 캐시는 머신이 일시적일 때, 브랜치가 많을 때, 또는 개발자와 CI가 서로의 작업을 재사용해야 할 때 도움이 됩니다.
- **아직 수정할 수 없는 비격리 빌드.** 가끔 잘못된 출력을 반환하는 캐시는 시간을 절약하는 것보다 신뢰 비용을 더 많이 발생시킵니다. 먼저 캐싱할 단계를 재현 가능하게 만들거나, 문제가 있는 단계는 캐싱하지 않으세요(예: Bazel의 `no-remote-cache` 태그 사용).
- **느리거나 원격 네트워크.** 캐시가 빌드 실행 위치에서 멀리 떨어져 있다면, 모두에게 배포하기 전에 전송 시간을 측정하세요.

## Tuist로 빌드 캐싱하기 {#build-caching-with-tuist}

[Tuist](https://tuist.dev)는 각 빌드 시스템의 자체 캐싱에 연결되는 원격 캐시를 제공하여, 개발자 머신, CI 및 코딩 에이전트가 서로의 출력을 재사용할 수 있게 하며, 히트, 미스 및 전송 시간을 기록하여 효과를 측정할 수 있게 합니다.

- <.localized_link href="/guides/features/cache/xcode-cache">Xcode 캐시</.localized_link>는 Xcode 26 이상의 모든 Xcode 프로젝트에 대해 Xcode의 컴파일레이션 캐시를 공유 원격 캐시에 연결합니다.
- <.localized_link href="/guides/features/cache/module-cache">모듈 캐시</.localized_link>는 Tuist로 생성된 프로젝트에서 전체 모듈을 사전 빌드된 바이너리로 대체합니다.
- <.localized_link href="/guides/features/cache/gradle-cache">Gradle 캐시</.localized_link>와 <.localized_link href="/guides/features/cache/bazel-cache">Bazel 캐시</.localized_link>는 Gradle 원격 빌드 캐시와 Bazel용 Remote Execution API 캐시로 작동합니다.
- <.localized_link href="/guides/features/cache">캐시</.localized_link>는 Elixir와 Once를 포함하여 지원되는 모든 빌드 시스템을 나열합니다.
- [느린 빌드](https://tuist.dev/solutions/slow-builds)는 캐시를 선택하기 전에 제거할 가치가 있는 작업을 찾는 실용적인 가이드입니다.
- [빌드 시스템의 물리학](https://tuist.dev/blog/2026/08/25/the-physics-of-build-systems)과 [Kura](https://tuist.dev/blog/2026/09/14/kura)는 Tuist 캐시의 측정값을 통해 모듈 캐시, Xcode 컴파일레이션 캐시, Bazel 및 Gradle 간 아티팩트 크기와 요청 볼륨이 어떻게 다른지 설명합니다.
