# Bazel 불안정 테스트 {#bazel-flaky-tests}

`tuist bazel test`는 각 호출 전에 Tuist의 격리 정책을 가져와서 기본 `bazel test` 실행에 적용합니다.

## 격리 적용 {#applying-quarantine}

테스트 페이지에서 상태를 **음소거됨**으로 변경한 후 다음을 실행하세요:

```sh
tuist bazel test -- //app:tests
```

`--` 뒤의 인수는 `bazel test`로 전달됩니다. 프로젝트와 작업 디렉터리를 선택하려면 `--path`를 사용하고, `bazelisk`와 같은 다른 실행 파일을 선택하려면 `--bazel`를 사용하세요. 일반 `bazel test`는 여전히 테스트 결과를 보고하지만, Tuist 격리 정책을 가져오거나 적용하지는 않습니다.

격리를 위해 명명된 Bazel 구성이나 재시도가 필요하지 않습니다. **불안정 테스트**, **격리된 테스트** 및 개별 테스트 페이지는 다른 빌드 시스템과 동일한 수동 상태 변경을 지원합니다. **설정 → 자동화**를 사용하여 불안정성 임계값, 격리 작업 및 복구 작업을 구성하세요.

### 음소거 {#mute}

주요 격리 워크플로우로 **음소거**를 사용하세요. 음소거된 케이스는 계속 실행되며, 실패는 그대로 표시되고 정상적인 형제 케이스는 결과에 영향을 미칩니다. 새로운 실행은 대상에서 어떤 케이스도 제외하지 않고 복구를 위한 증거를 제공합니다.

Tuist는 임시 로컬 빌드 이벤트 파일과 참조된 `test.xml` 보고서를 읽습니다. 완전한 보고서가 실패한 대상의 모든 보고된 실패를 음소거된 케이스에 귀속시킬 때만 Bazel의 테스트 실패 종료를 성공으로 변경합니다.

빌드 오류, 시간 초과, 중단된 실행, 누락되거나 잘못된 형식의 보고서, 불완전한 이벤트 스트림, 그리고 음소거 집합 외부의 실패는 Bazel의 실패 상태를 유지합니다. 로컬 이벤트 파일은 64 MiB로 제한되며 개별 보고서는 5 MiB로 제한됩니다. Tuist는 음소거된 실패를 확인하고 오래된 건너뛴 대상에서 복구하기 위해 자체 로컬 빌드 이벤트 파일이 필요하므로, 명시적 `--build_event_json_file`는 활성화된 음소거 또는 건너뛴 케이스와 결합할 수 없습니다. 원격 빌드 이벤트 보고는 `tuist bazel setup`를 통해 계속 구성됩니다.

원본 Bazel 호출과 보고서는 실제 결과를 유지합니다. Tuist 서버는 보고서가 처리되기 전에 상태가 변경되더라도 호출이 시작될 때 케이스가 격리되었는지 여부를 기록합니다.

### 건너뛰기 {#skip}

해당 대상 내의 정상적인 케이스를 포함하여 **전체 Bazel 대상**을 제외하려는 경우에만 **건너뛰기**를 사용하세요. 단일 케이스를 **건너뜀**으로 표시하면 이 대상 전체에 영향을 미칩니다. Bazel의 개별 케이스 필터 구문은 테스트 프레임워크에 따라 다르며 보편적으로 지원되지 않습니다. 따라서 Tuist는 테스트 스위트 확장이 활성화된 네이티브 부정 대상 패턴을 사용합니다. 명시적 대상, 와일드카드 선택 및 `test_suite` 규칙 내부의 테스트는 Bazel의 일반 선택 동작을 유지합니다.

이 명령어는 모든 격리 페이지를 가져오고 대상을 중복 제거합니다. Bazel의 전체 이벤트 로그가 대상 구성 또는 실행 전에 누락된 건너뛴 대상을 식별하면, Tuist는 경고에서 이를 명시하고 해당 오래된 제외 없이 다시 시도합니다. 원래 요청된 패턴과 다른 모든 제외 사항은 보존됩니다. 복구는 최대 5회 재시도로 제한되며, 다른 로드 실패 및 불완전한 증거는 Bazel의 오류를 유지합니다. 오래된 케이스를 **활성화됨**으로 반환하여 정책을 영구적으로 제거하세요. 대상 패턴을 직접 전달하세요. `--target_pattern_file`는 격리 제외와 결합할 수 없습니다. 남은 테스트 대상이 없으면 Bazel은 정상적인 "테스트를 찾을 수 없음" 종료 상태를 유지하며, 이는 실수로 빈 테스트 선택이 된 경우도 포착합니다.

이 명령어는 제외된 모든 대상 라벨을 출력하므로, 빌드 로그를 통해 격리 정책이 어떤 대상(정상적인 케이스 포함)을 제외하는지 확인할 수 있습니다.

### 격리된 테스트 다시 실행 {#running-quarantined-tests-again}

수정을 조사하거나 검증하려면 두 가지 격리 정책을 모두 우회하세요:

```sh
tuist bazel test --no-quarantine -- --nocache_test_results //app:tests
```

케이스를 **활성화됨**으로 반환하여 후속 일반 실행에 해당 대상을 포함시키세요. 건너뛴 케이스는 명시적으로 포함될 때까지 새로운 실행을 생성하지 않으므로, 성공적인 새로운 실행을 기반으로 하는 자동화는 이를 복구하기 전에 검증 실행이 필요합니다.

격리 검색 오류는 테스트 실행 전에 명령어를 중지시킵니다. 또한 명령어는 20,000개 이상의 케이스 또는 제한된 크기 이상의 대상 인수를 가진 정책을 거부하며 부분적인 정책을 적용하지 않습니다. 의도적으로 정책 없이 실행하려면 `--no-quarantine`를 사용하세요.

## 선택적 구성 및 재시도 {#optional-configuration-and-retries}

리포지토리가 `.bazelrc`에 명명된 `ci` 구성을 정의하는 경우, `--config=ci`로 선택할 수 있습니다:

```sh
tuist bazel test -- --config=ci //app:tests
```

이는 리포지토리에서 정의된 구성이며 Tuist의 필수 조건이 아닙니다. 리포지토리에서 이를 정의하지 않는 경우 옵션을 생략하세요.

재시도도 선택 사항이며 격리와 독립적입니다. `--flaky_test_attempts=3`는 테스트당 추가 재시도 3회가 아닌 **최대 3회의 총 Bazel 시도**를 활성화합니다. 팀은 `.bazelrc`에 기존 재시도 구성을 유지하거나 명시적으로 전달할 수 있습니다:

```sh
tuist bazel test -- --flaky_test_attempts=3 //app:tests
```

`ci`을 정의하는 리포지토리의 경우 옵션을 결합할 수 있습니다:

```sh
tuist bazel test -- --config=ci --flaky_test_attempts=3 //app:tests
```

## 불안정성 감지 {#detecting-flakiness}

Tuist는 Bazel의 `test.xml` 보고서에서 개별 케이스를 사용하여 재시도 간 및 지속적 통합에서 동일한 커밋과 대상 선택의 실행 간 일관되지 않은 결과를 감지합니다. 로컬 실행은 계속 표시되지만 테스트 케이스를 자동으로 불안정하다고 플래그 지정하지는 않습니다. 빌드 환경이 이미 메타데이터를 게시하지 않는 경우 커밋 및 브랜치 메타데이터를 제공하세요:

```sh
tuist bazel test -- \
  --build_metadata=CI=true \
  --build_metadata=GIT_COMMIT="$GIT_COMMIT" \
  --build_metadata=GIT_BRANCH="$GIT_BRANCH" //app:tests
```

Tuist가 결과를 관찰하려면 재시도가 실제로 실행되어야 합니다. Bazel 대상의 불안정 요약만으로는 어떤 개별 케이스가 불안정했는지 식별할 수 없습니다. 사용할 수 없거나 파싱할 수 없는 보고서는 케이스 수준의 증거를 제공할 수 없습니다.

케이스는 대상 라벨, 클래스 이름(スイ트 이름으로 대체) 및 테스트 이름으로 식별됩니다. 이로 인해 다른 클래스의 동일한 이름 메서드가 분리됩니다. 다른 enclosing suite 이름을 사용한 이전 보고서는 이전 식별자 하에 기록을 유지하며, 해당 격리 상태는 새 식별자에 적용되어야 합니다. 실패가 현재 클래스 식별자가 아닌 이전 suite 기반 음소거와 일치하는 경우, 명령어는 어떤 정책을 다시 적용해야 하는지 경고하고 실패를 차단 상태로 유지합니다. 여러 클래스가 이전 식별자를 공유할 수 있으므로 정책은 자동으로 전송되지 않습니다.

기본 동작에 대해서는 Bazel의 [테스트 필터](https://bazel.build/docs/user-manual#test-filter), [명령 옵션](https://bazel.build/reference/command-line-reference) 및 [빌드 이벤트 설명](https://bazel.build/remote/bep-glossary)을 참조하세요.
