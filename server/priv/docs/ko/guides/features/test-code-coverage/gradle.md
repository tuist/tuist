# Gradle 코드 커버리지 {#gradle-code-coverage}

코드 커버리지는 테스트가 코드의 어떤 줄을 실행했는지 보여줍니다. Tuist Gradle 플러그인은 JaCoCo를 사용해 테스트 작업의 커버리지를 측정하고 각 테스트 실행마다 업로드하며, Tuist는 커밋의 실행 결과를 프로젝트, 각 Gradle 프로젝트 및 파일별로 하나의 수치로 통합합니다. 대시보드의 **코드 커버리지** 페이지에서는 이를 커밋별 및 브랜치별 추이로 확인할 수 있습니다.

> [!IMPORTANT]
> **요구 사항**
>
> - `dev.tuist` Gradle 플러그인이 적용되어 있어야 합니다. 자세한 내용은 <.localized_link href="/guides/get-started/gradle-project">Gradle 프로젝트 시작하기</.localized_link>를 참조하세요.
> - 프로젝트가 Git 리포지토리에 있어야 합니다. Git 외부에서 실행된 경우 테스트 결과는 업로드되지만 커버리지는 업로드되지 않습니다.

## 설정 {#setup}

### 커버리지 활성화 {#turn-coverage-on}

`settings.gradle.kts`의 `tuist` 블록에서 커버리지를 활성화하세요:

```kotlin
tuist {
    coverage {
        enabled = true
    }
}
```

또는 CI 작업과 같은 단일 호출에 대해 환경 변수를 사용하여 활성화할 수 있으며, 이 설정은 다른 설정보다 우선합니다:

```sh
TUIST_TEST_COVERAGE=1 ./gradlew test
```

커버리지가 활성화되면 플러그인은 모든 JVM 프로젝트에 Gradle의 `jacoco` 플러그인을 적용합니다. JaCoCo 에이전트는 사용자가 직접 플러그인을 적용했을 때와 마찬가지로 프로젝트의 리포지토리에서 가져옵니다. 이미 JaCoCo를 구성한 프로젝트는 기존 설정을 유지하며 자체 보고서는 계속 작동합니다.

### 샤딩된 실행 {#sharded-runs}

<.localized_link href="/guides/features/test-sharding/gradle">테스트를 샤딩</.localized_link>하면 커버리지가 활성화된 상태에서 실행된 각 샤드가 실행한 테스트의 커버리지를 보고하고, Tuist는 한 번의 실행에 대한 샤드 결과를 하나의 수치로 병합합니다. 샤드는 의도적으로 스위트의 일부만 실행하므로 커밋의 커버리지가 불완전해지지 않습니다.

### CI에서 각 커밋 완료하기 {#complete-each-commit}

커밋의 커버리지는 종종 여러 작업(예: 샤드당 하나)에서 생성됩니다. Tuist는 마지막 보고 시점을 알 수 없으므로 직접 알려주어야 합니다. 커밋의 모든 테스트 작업이 완료되면 해당 작업들에 의존하는 작업에서 다음을 실행하세요:

```sh
./gradlew tuistCoverageComplete
```

이 작업은 `GIT_COMMIT` 또는 체크아웃의 `HEAD`에서 커밋을 읽습니다. 다른 커밋을 지정하려면 `-Ptuist.coverage.commit=<sha>`를 전달하세요. 커밋이 완료될 때까지 커버리지는 **진행 중**으로 표시되며 브랜치의 추이에 포함되지 않습니다.

## 작동 방식 {#how-it-works}

### Tuist가 측정하는 항목 {#what-tuist-measures}

- **프로젝트.** 각 Gradle 프로젝트는 대시보드에서 자체 커버리지를 가진 모듈로 표시됩니다.
- **제품 코드만.** 테스트 소스 세트에서 컴파일된 클래스는 테스트 코드로 간주됩니다. Tuist는 이를 저장하지만 모든 수치에서는 제외합니다.
- **리포지토리의 파일.** 클래스는 리포지토리 내 경로에 따라 컴파일된 소스 파일에 속합니다. 생성된 소스와 Git이 무시하는 파일은 보고되지 않습니다.
- **각 줄의 실행 여부.** JaCoCo는 코드가 실행되었는지 여부만 기록하며 실행 횟수는 기록하지 않으므로 대시보드의 실행 횟수는 0 또는 1입니다.

### 각 테스트가 실행한 코드 {#per-test-evidence}

JUnit 플랫폼(JUnit 5 또는 JUnit Vintage를 통한 JUnit 4)에서 실행되는 테스트의 경우, 플러그인은 각 테스트가 실행한 코드와 `@BeforeAll`와 같이 테스트 외부에서 각 테스트 클래스가 실행한 내용도 기록합니다. 이를 통해 Tuist는 실행에서 제외된 테스트의 커버리지를 이전 데이터로부터 이어갈 수 있습니다([스킵된 테스트](#skipped-tests) 참조). 테스트에 추가적인 설정이 필요하지 않습니다.

이는 각 테스트 JVM이 한 번에 하나의 테스트를 실행할 때 작동하며, JUnit의 병렬 실행을 활성화하지 않는 한 Gradle이 테스트를 실행하는 방식입니다. `maxParallelForks`를 사용하여 여러 JVM에서 테스트 클래스를 실행해도 문제가 없습니다. 하나의 JVM에서 동시에 실행되는 테스트도 커버리지에는 포함되지만 개별적으로는 구분되지 않습니다.

### 빌드 캐시 {#build-cache}

Gradle이 빌드 캐시에서 복원하거나 최신 상태인 테스트 작업은 테스트를 실행하지 않습니다. 그러나 해당 커버리지는 여전히 업로드됩니다. JaCoCo 데이터는 작업의 출력 중 하나로, 동일한 입력으로 테스트를 실행한 실행에 의해 기록됩니다.

### 스킵된 테스트 {#skipped-tests}

실행에서 테스트가 제외되면 Tuist는 실행된 코드가 변경되지 않은 한 이전 실행에서 커버된 내용을 채워 넣습니다. 그렇지 않을 경우 커밋의 커버리지는 **불완전**으로 표시됩니다. 실행에서 제외되는 항목:

- **프로젝트의 테스트 태스크가 제외된 경우**, `-x :app:test`를 사용합니다. 해당 테스트의 코드가 변경되지 않은 마지막 실행 결과가 이어집니다.
- `./gradlew :core:test`를 사용한 **일부 프로젝트의 테스트** 또는 `--tests`를 사용한 **일부 테스트**. 실행은 요청한 항목만 커버하므로, 커밋의 다른 실행이 모든 것을 실행하지 않으면 커밋은 불완전합니다.
- **첫 번째 실패에서 중지된 테스트 작업**(`failFast`).

일부 테스트는 의도적으로 제외되며 이로 인해 커밋이 불완전해지지 않습니다:

- **빌드 스크립트의 필터**(예: `filter { excludeTestsMatching(...) }`). 이는 스위트가 실행하는 항목을 정의합니다.
- **빌드 스크립트에서 비활성화된 테스트 작업**(`enabled = false` 또는 이를 스킵하는 `onlyIf` 사용).
- **<.localized_link href="/guides/features/test-insights/flaky-tests/gradle">격리</.localized_link>로 스킵된 테스트**. 제거된 것처럼 제외되므로 해당 테스트만 커버했던 줄은 커버되지 않은 것으로 간주됩니다.
- **다른 샤드의 테스트**([테스트 샤딩](#sharded-runs) 시).

### 완료 및 불완전 커밋 {#commit-status}

| 상태 | 의미 |
| --- | --- |
| 진행 중 | 실행에서 커버리지가 보고되었지만, `tuistCoverageComplete`가 아직 이 커밋에 대해 실행되지 않았습니다. |
| 완료 | 커밋의 모든 테스트 실행이 완료되거나, 이전 결과가 이어졌거나, 의도적으로 제외되었습니다. |
| 불완전 | 일부 커버리지를 확인할 수 없어 수치는 하한선으로 표시됩니다. |
| 측정되지 않음 | 커밋에 대해 커버리지를 보고한 실행이 없습니다. |

브랜치의 추세에는 완료된 커밋만 포함됩니다.

## 성능 영향 {#performance-impact}

JaCoCo는 테스트 JVM이 클래스를 로드할 때 인스트루먼트하므로, 컴파일된 클래스와 컴파일 작업의 빌드 캐시 항목은 커버리지 활성화 여부와 관계없이 동일하게 유지됩니다. SBOM 생성기와 같이 모든 의존성 구성을 읽는 작업도 JaCoCo 에이전트를 감지하므로 커버리지를 켜면 출력이 변경됩니다. 테스트 실행 속도가 약간 느려지며, 플러그인은 테스트 작업이 완료된 후 JaCoCo 데이터를 읽습니다. 커버리지 활성화 및 비활성화 상태의 테스트 작업은 별도의 빌드 캐시 항목을 가지므로, 커버리지 없이 캐시된 결과가 있더라도 커버리지를 켠 첫 번째 실행에서는 테스트가 실제로 실행됩니다.

## 제한 사항 {#limitations}

- **격리된 프로젝트 및 필요 시 구성(Configuration on demand).** 이러한 빌드는 모든 프로젝트를 구성하지 않으므로, 플러그인은 실행에서 어떤 프로젝트의 테스트가 제외되었는지 알 수 없으며 일부 프로젝트의 테스트 실행은 완료된 것으로 간주됩니다.
- **포크된 리포지토리에서의 풀 리퀘스트는 커버리지를 제공하지 않습니다.** 커버리지는 Tuist로 인증된 실행에서만 업로드되며, CI는 일반적으로 포크된 리포지토리에서 열린 풀 리퀘스트에 대해 시크릿과 신원 토큰을 전달하지 않습니다.

## 커버리지 조회 {#querying}

대시보드의 **코드 커버리지** 페이지는 각 커밋의 수치, 모듈, 파일 및 각 실행이 커버한 줄을 보여줍니다. 동일한 데이터는 <.localized_link href="/guides/features/agentic-coding/mcp">Model Context Protocol 서버</.localized_link>를 통해 에이전트에서도 사용할 수 있습니다.
