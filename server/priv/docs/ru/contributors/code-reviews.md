# Проверка кода {#code-reviews}

Ревью пул-реквестов — распространённый вид вклада. Несмотря на то, что непрерывная интеграция (CI) гарантирует, что код делает то, что от него ожидается, этого недостаточно. Есть аспекты вклада, которые нельзя автоматизировать: дизайн, структура и архитектура кода, качество тестов или опечатки. В следующих разделах рассмотрены различные аспекты процесса ревью кода.

## Читаемость {#readability}

Код ясно выражает свои намерения? **Если приходится тратить много времени на то, чтобы разобраться, что делает код, реализацию нужно улучшить.** Предложите разбить код на более мелкие абстракции, которые легче понять. В качестве альтернативы и как крайняя мера можно добавить комментарий, объясняющий логику решения. Спросите себя, сможете ли вы понять этот код в ближайшем будущем без дополнительного контекста, например описания пул-реквеста.

## Небольшие пул-реквесты {#small-pull-requests}

Большие пул-реквесты сложно ревьюить, и в них легче упустить детали. Если пул-реквест становится слишком большим и трудноуправляемым, предложите автору разбить его на части.

> [!NOTE]
> **Исключения**
>
> Есть немного сценариев, когда разделение пул-реквеста невозможно, например, когда изменения тесно связаны и их нельзя разделить. В таких случаях автор должен дать чёткое объяснение изменений и обоснование.


## Согласованность {#consistency}

Важно, чтобы изменения были согласованы с остальной частью проекта. Несогласованность усложняет поддержку, поэтому её следует избегать. Если в проекте уже есть подход к выводу сообщений пользователю или сообщению об ошибках, стоит придерживаться его. Если автор не согласен со стандартами проекта, предложите ему создать задачу, где это можно будет обсудить подробнее.

## Тесты {#tests}

Тесты позволяют менять код уверенно. Код в пул-реквестах должен быть покрыт тестами, и все тесты должны проходить. Хороший тест — это тест, который стабильно даёт один и тот же результат и который легко понимать и поддерживать. Ревьюеры тратят большую часть времени на код реализации, но тесты не менее важны, потому что это тоже код.

## Несовместимые изменения {#breaking-changes}

Несовместимые изменения ухудшают пользовательский опыт для пользователей Tuist. Вклады должны избегать внедрения несовместимых изменений, если это не строго необходимо. Есть множество возможностей языка, которые можно использовать для эволюции интерфейса Tuist без несовместимых изменений. Не всегда очевидно, является ли изменение несовместимым. Один из способов проверить это — запустить Tuist на проектах-примерах из директории fixtures. Это требует поставить себя на место пользователя и представить, как изменения повлияют на него.
