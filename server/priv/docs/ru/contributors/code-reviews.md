# Проверка кода {#code-reviews}

Проверка pull-запросов — распространённый вид вклада. Несмотря на то, что непрерывная интеграция (CI) гарантирует корректность работы кода, этого недостаточно. Есть аспекты вклада, которые нельзя автоматизировать: дизайн, структура и архитектура кода, качество тестов или опечатки. В следующих разделах рассмотрены различные аспекты процесса проверки кода.

## Читаемость {#readability}

Код ясно выражает своё назначение? **Если приходится тратить много времени, чтобы разобраться, что делает код, реализацию нужно улучшить.** Предложите разбить код на более мелкие абстракции, которые проще понять. Как альтернативу и в крайнем случае можно добавить комментарий, объясняющий логику решения. Спросите себя, сможете ли вы понять этот код в ближайшем будущем без дополнительного контекста, например описания pull-запроса.

## Небольшие pull-запросы {#small-pull-requests}

Большие pull-запросы сложно проверять, и в них легче упустить детали. Если pull-запрос становится слишком большим и неудобным для управления, предложите автору разбить его на части.

> [!NOTE]
> **Исключения**
>
> Есть немногие сценарии, когда разделение pull-запроса невозможно, например когда изменения тесно связаны и их нельзя разделить. В таких случаях автор должен чётко объяснить внесённые изменения и причины, по которым они были сделаны.


## Согласованность {#consistency}

Важно, чтобы изменения были согласованы с остальной частью проекта. Несогласованность усложняет поддержку, поэтому её следует избегать. Если в проекте есть единый подход к выводу сообщений пользователю или сообщению об ошибках, стоит его придерживаться. Если автор не согласен со стандартами проекта, предложите ему создать issue, где мы сможем обсудить это подробнее.

## Тесты {#tests}

Тесты позволяют менять код с уверенностью. Код в pull-запросах должен быть покрыт тестами, и все тесты должны проходить. Хороший тест стабильно выдаёт один и тот же результат, а также прост для понимания и поддержки. Рецензенты проводят большую часть времени проверки над кодом реализации, но тесты не менее важны, потому что это тоже код.

## Несовместимые изменения {#breaking-changes}

Несовместимые изменения ухудшают пользовательский опыт для пользователей Tuist. Вклады должны избегать внесения несовместимых изменений, если это не строго необходимо. Есть множество возможностей языка, которые можно использовать для эволюции интерфейса Tuist без несовместимых изменений. Не всегда очевидно, является ли изменение несовместимым. Один из способов проверить это — запустить Tuist на тестовых проектах из директории fixtures. Это требует поставить себя на место пользователя и представить, как изменения повлияют на него.
