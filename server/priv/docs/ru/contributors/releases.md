# Релизы

Tuist автоматически публикует новые версии по мере слияния изменений в основную ветку. CLI, сервер и сервер кэширования Kura поставляются через каналы релизов (canary, release candidate, stable), чтобы рекомендуемая установка оставалась стабильной и медленно обновляемой; выпуск кандидата в релизы и его продвижение до стабильной версии — это осознанные еженедельные шаги. Приложение выпускается непрерывно (iOS-приложение развёртывается только в TestFlight, подробнее [здесь](#app-store-release)).

## Обзор

Мы выпускаем следующие основные компоненты:
- **Tuist CLI** — инструмент командной строки, поставляемый через каналы canary, release candidate и stable [каналы](#release-channels)
- **Tuist Server** — бэкенд-сервисы, поставляемые по той же модели каналов, что и CLI
- **Kura** — сервер кэширования, поставляемый по той же модели каналов, что и CLI
- **Tuist App** — приложения для macOS и iOS, выпускаемые непрерывно (iOS-приложение развёртывается только в TestFlight, подробнее [здесь](#app-store-release))

Каждый пуш в `main` публикует canary-пререлиз для CLI, сервера и Kura. Стабильный релиз каждого из этих компонентов выпускается только тогда, когда мейнтейнер продвигает проверенный кандидат в релизы, а еженедельное расписание синхронно запускает все три потока (см. [Каналы релизов](#release-channels)). Приложение публикует стабильную версию при каждом пуше в `main`.

## Как это работает

### 1. Соглашения о коммитах

Мы используем [Conventional Commits](https://www.conventionalcommits.org/) для структурирования сообщений коммитов. Это позволяет нашим инструментам понимать характер изменений, определять повышение версий и генерировать соответствующие списки изменений.

Формат: `type(scope): description`

#### Типы коммитов и их влияние

| Тип | Описание | Влияние на версию | Пример |
|------|-------------|----------------|---------|
| `feat` | Новая функция или возможность | Повышение минорной версии (x.Y.z) | `feat(cli): add support for Swift 6` |
| `fix` | Исправление ошибки | Повышение патч-версии (x.y.Z) | `fix(app): resolve crash when opening projects` |
| `docs` | Изменения в документации | Без релиза | `docs: update installation guide` |
| `style` | Изменения стиля кода | Без релиза | `style: format code with swiftformat` |
| `refactor` | Рефакторинг кода | Без релиза | `refactor(server): simplify auth logic` |
| `perf` | Улучшения производительности | Повышение патч-версии | `perf(cli): optimize dependency resolution` |
| `test` | Добавление/изменение тестов | Без релиза | `test: add unit tests for cache` |
| `chore` | Задачи по обслуживанию | Без релиза | `chore: update dependencies` |
| `ci` | Изменения CI/CD | Без релиза | `ci: add workflow for releases` |

Для CLI эти повышения определяют canary-версию и группировку в списке изменений. Стабильные версии CLI — это минорные линии (`X.Y.0`), выпускаемые вручную, а стабильные патчи (`X.Y.Z`) поступают только из бэкпортов, поэтому `feat` или `fix` достигает пользователей CLI через поток каналов, описанный ниже, а не как немедленный стабильный релиз.

#### Критические изменения

Критические изменения вызывают повышение мажорной версии (X.0.0) и должны быть указаны в теле коммита:

```
feat(cli): change default cache location

BREAKING CHANGE: The cache is now stored in ~/.tuist/cache instead of .tuist-cache.
Users will need to clear their old cache directory.
```

### 2. Обнаружение изменений

Каждый компонент использует [git cliff](https://git-cliff.org/) для:
- Анализа коммитов с момента последнего релиза
- Фильтрации коммитов по области (cli, app, server)
- Определения наличия изменений, готовых к релизу
- Автоматической генерации списков изменений

### 3. Конвейер релизов

При обнаружении изменений, готовых к релизу:

1. **Расчет версии**: конвейер определяет номер следующей версии
2. **Генерация списка изменений**: git cliff создает список изменений на основе сообщений коммитов
3. **Процесс сборки**: компонент собирается и тестируется
4. **Генерация артефактов**: создаются специфичные для релиза ресурсы, такие как пакеты CLI, контрольные суммы и спецификация CLI `tuist.spec.json`, сгенерированная из `tuist --experimental-dump-help`
5. **Создание релиза**: создается релиз на GitHub с артефактами
6. **Распространение**: обновления отправляются в менеджеры пакетов (например, Homebrew для CLI)

Для приложения это приводит к стабильному релизу при каждом слиянии. Для CLI, сервера и Kura этот же автоматический конвейер создает только предварительный релиз **canary**; кандидаты в релизы и стабильные релизы выпускаются в рамках еженедельного цикла релизов (см. [Каналы релизов](#release-channels)).

### 4. Фильтрация по области

Каждый компонент выпускается только при наличии соответствующих изменений:

- **CLI**: Коммиты с областью `(cli)` или без указания области
- **App**: Коммиты с областью `(app)`
- **Server**: Коммиты с областью `(server)`

## Каналы релизов

CLI, сервер и Kura не переводятся в стабильный релиз при каждом пуше в `main`. Каждый из них поставляется через три канала, чтобы рекомендуемая установка оставалась стабильной и медленно меняющейся, в то время как ранние пользователи получают сборки по каждому коммиту. Пользовательская документация находится по ссылкам <.localized_link href="/cli/release/channels">Каналы релизов CLI</.localized_link> и <.localized_link href="/guides/server/self-host/release/channels">Каналы релизов сервера</.localized_link>; этот раздел предназначен для сопровождающих.

Каждый компонент использует одни и те же три канала:

| Канал | Версия | Кем выпускается |
|---------|---------|--------|
| Canary | `X.Y.0-canary.N` | Автоматически, при каждом пуше в `main`, затрагивающем компонент (`<component>-release.yml`; для Kura вызывается через `server-production-deployment.yml` при изменении `kura/`) |
| Кандидат в релизы | `X.Y.0-rc.N` | Каждый понедельник или вручную, в ветке `releases/<component>-<major>.<minor>.x` (`<component>-rc.yml`) |
| Стабильный | `X.Y.Z` | Каждый понедельник или вручную, путем продвижения проверенного RC (`<component>-promote.yml`); патчи через `<component>-backport.yml` |

Сборки Canary и RC публикуются как предварительные релизы на GitHub (никогда не помечаются как «Latest», никогда не перемещают тег `:latest` в GHCR, никогда не отправляются в Homebrew для CLI), поэтому менеджеры пакетов и резолверы образов получают их только при явном согласии. Canary всегда нацелен на следующую невыпущенную минорную версию: как только линия RC выпущена, canary-версия `main` переходит к следующей минорной.

Хостинговый Tuist не ждет стабильного цикла: сервер развертывается по каждому коммиту, а хостинговые среды canary и production запускают новейшую canary-версию Kura. Каскад развертывания публикует эту canary-версию перед ее развертыванием, поэтому у `kura-release.yml` нет собственного триггера. Изменения только в инструментах релиза Kura (`mise/tasks/kura/**`, воркфлоу `kura-*.yml`) не приводят к выпуску canary.

Вы никогда не выбираете номера версий вручную. Следующая версия каждого канала выводится из существующих git-тегов скриптом `mise/tasks/<component>/release/channel-version.sh`, который вызывают приведенные ниже воркфлоу.

Ветки релизов имеют пространство имен для каждого компонента (`releases/server-X.Y.x`, `releases/kura-X.Y.x`, `releases/X.Y.x` для CLI), чтобы линии трех компонентов никогда не пересекались в одной минорной версии.

### Еженедельное расписание

Каждый понедельник в 06:00 UTC задачи продвижения трех компонентов выполняются синхронно: **CLI Promote to Stable**, **Server Promote to Stable** и **Kura Promote to Stable**. Каждая задача продвигает новейшую линию RC, которая еще не стала стабильной, обычно это линия, выпущенная в предыдущий понедельник. Если такой линии нет, задача ничего не публикует.

Когда продвижение завершается, независимо от результата, соответствующий воркфлоу **Release Candidate** (`cli-rc.yml`, `server-rc.yml`, `kura-rc.yml`) запускается через `workflow_run` и выпускает следующую линию из `main`.

Если какой-либо из запланированных запусков завершается ошибкой или отменяется, в Slack отправляется сообщение. Продвижение завершается ошибкой, если в ветке релиза есть коммиты после последнего RC. Чтобы выпустить эту линию, создайте на ней новый RC и продвиньте его вручную. В противном случае в следующий понедельник будет продвинута более новая линия.

### Выпуск кандидата в релизы

Чтобы выпустить новую линию вне еженедельного расписания (подставьте ниже название воркфлоу компонента):

1. Запустите воркфлоу **\<Component\> Release Candidate** (например, `server-rc.yml`) с пустым входным параметром `branch`.
2. Он публикует `X.Y.0-rc.1` и, после успешного завершения, создает защищенную ветку `releases/<component>-X.Y.x` на собранном коммите.

Чтобы включить критическое исправление или регрессию в тестируемую линию, сделайте cherry-pick в ветку релиза через PR (тот же процесс, что и для бэкпортов; CI никогда не делает cherry-pick самостоятельно), затем создайте новый RC:

1. Создайте ветку от `releases/<component>-X.Y.x`, сделайте cherry-pick исправления, откройте PR обратно в ветку релиза, разрешите любые конфликты и выполните слияние.
2. Снова запустите воркфлоу **Release Candidate** с параметром `branch=releases/<component>-X.Y.x`. Он опубликует `X.Y.0-rc.(N+1)` из HEAD ветки.

Тестируемая линия заморожена по функционалу: в нее попадают только критические исправления и регрессии.

### Продвижение в стабильную версию

Чтобы продвинуть линию вне еженедельного расписания, после того как ее RC успешно прошел тестирование:

1. Запустите воркфлоу **\<Component\> Promote to Stable** (например, `server-promote.yml`) с параметром `branch=releases/<component>-X.Y.x`.
2. Он публикует образ с семантическим тегом с параметром `make_latest=true`, перемещая тег GHCR `:latest` и указатель "Latest" в GitHub. CLI дополнительно обновляет формулу Homebrew.

Продвижение не запускается, если HEAD ветки не совпадает точно с коммитом, на который указывает последний RC. Поэтому, если после последнего RC в линию были внесены исправления, необходимо создать новый RC и дать ему пройти тестирование, прежде чем он сможет быть выпущен как стабильный.

### Бэкпорт исправлений в стабильную линию

Когда линия становится стабильной, выпускайте патчи с помощью воркфлоу **Backport Release**, доступного только для CLI (`cli-backport.yml`): сделайте cherry-pick исправления в `releases/X.Y.x` через PR, затем запустите воркфлоу для этой ветки, чтобы выпустить `X.Y.(Z+1)`. Бэкпорты никогда не перемещают указатель "Latest" и не обновляют формулу Homebrew. Одновременно поддерживаются две линии: текущая линия получает исправления регрессий и безопасности, предыдущая — только критические исправления и исправления безопасности. Другие исправления ошибок не бэкпортятся и выходят со следующей минорной версией.

Для сервера и Kura используйте **Server Backport Release** (`server-backport.yml`) или **Kura Backport Release** (`kura-backport.yml`). Продвижение публикует только `X.Y.0` RC; оно не может применять патчи к уже стабильной линии.

1. Начните с последнего опубликованного стабильного тега компонента в выбранной линии `X.Y` и откройте точечный PR с исправлением в существующую ветку `releases/server-X.Y.x` или `releases/kura-X.Y.x`. Более новая минорная или мажорная версия не препятствует применению патчей к поддерживаемой линии. Не включайте изменения из main, не относящиеся к делу.
2. Проверьте и слейте исходный PR. Получите удаленную ветку релиза и подтвердите ее **финальный слитый коммит**, включая поддерживаемые платформы компонента и положительные/отрицательные контрольные точки TLS. Успешный пре-мердж HEAD не является подтверждением другого squash или merge коммита.
3. С отдельным утверждением публикации запустите соответствующий воркфлоу бэкпорта **из main**, установив `source_sha` в тот самый подтвержденный слитый коммит, а `base_tag` — в текущий стабильный тег, например `server@X.Y.Z` или `kura@X.Y.Z`. Воркфлоу выводит `X.Y.(Z+1)`; операторы не выбирают повышение минорной версии и не продвигают содержимое canary.

Планирование обновляет точную удаленную ветку и базовый тег, требует, чтобы выбранный источник совпадал с концом ветки, отклоняет неизмененный источник или изменения вне компонента, его входные данные политики доверия и валидацию, и фиксирует разрешенный базовый коммит. Контроли, исходящие из main, повторяют эти проверки непосредственно перед публикацией версионированного образа и в GitHub. Если исходная ветка, стабильная база или доступная версия изменяются, остановитесь и повторно подтвердите качество, а не заменяйте источник новым.

Бэкпорты используют существующие мультиплатформенные издатели без перемещения указателя "Latest" в GitHub или GHCR `:latest`. Публикация отделена от развертывания на хостинге: эти воркфлоу не продвигают хостируемый сервер или флот Kura, не обходят приемку canary и не подтверждают качество установленной среды выполнения. Вспомогательные скрипты сборки и Dockerfiles по-прежнему берутся из выбранного стабильного источника. Контроли являются шлюзами публикации, а не задачами сборки без учетных данных; сборки могут загружать нетегированные дайджесты образов до финального шлюза. Публикация образа и в GitHub не является атомарной: если позже шлюз завершается ошибкой после публикации тега образа, проверьте частичный релиз и сохраните его исходный источник и артефакты. Никогда не заменяйте существующий релиз и не используйте другие байты под его тегом.

## Написание хороших сообщений коммитов

Поскольку сообщения коммитов напрямую влияют на примечания к релизу, важно писать четкие и описательные сообщения:

### Делайте:
- Используйте настоящее время: "add feature", а не "added feature"
- Будьте лаконичны, но описательны
- Указывайте область действия, если изменения относятся к конкретному компоненту
- Ссылайтесь на задачи, когда это применимо: `fix(cli): resolve build cache issue (#1234)`

### Не делайте:
- Не используйте расплывчатые сообщения, такие как "fix bug" или "update code"
- Не смешивайте несколько несвязанных изменений в одном коммите
- Не забывайте включать информацию о критических изменениях

### Критические изменения

Для критических изменений включите `BREAKING CHANGE:` в тело коммита:

```
feat(cli): change cache directory structure

BREAKING CHANGE: Cache files are now stored in a new directory structure.
Users need to clear their cache after updating.
```

## Воркфлоу релизов

CLI, сервер и Kura имеют свой собственный набор воркфлоу каналов, следующих одной структуре:

- `<component>-release.yml` — публикует canary при каждом пуше в `main`, затрагивающем компонент (для Kura это переиспользуемый воркфлоу, который вызывает `server-production-deployment.yml` при изменении `kura/`)
- `<component>-rc.yml` — выпускает кандидата в релизы каждый понедельник (через `workflow_run` после продвижения) или вручную выпускает или обновляет его
- `<component>-promote.yml` — продвигает ожидающий RC в стабильную версию каждый понедельник в 06:00 UTC или вручную продвигает протестированный RC
- `<component>-build-publish.yml` — общий конвейер сборки и публикации, который вызывают три вышеупомянутых воркфлоу

CLI, сервер и Kura также имеют `<component>-backport.yml` для выпуска патчей в стабильной линии. Все воркфлоу компонента сериализуются через одну группу параллелизма `<component>-publish`, поэтому разрешение версий и тегирование никогда не конфликтуют. Исключение составляет Kura: ее canary использует `kura-canary-publish`, а RC, продвижение и бэкпорт используют `kura-stable-publish`, поэтому длительная стабильная сборка никогда не задерживает каскад развертывания. Пространства имен тегов не пересекаются, поэтому две группы не могут конфликтовать.

Helm-чарт и инфраструктурные образы (оператор CAPI, контроллер раннеров, образ обработчика xcresult, образ linux-раннера и так далее) по-прежнему выпускаются через `.github/workflows/server-production-deployment.yml`. Он запускается при пушах в `main` и выполняет каскад canary → приемочные тесты → продакшн для хостингового развертывания, а также публикует эти инфраструктурные компоненты по мере их изменения. Приложение, кэш, плагин Gradle, навыки, Noora и автономные инфраструктурные контроллеры имеют выделенный воркфлоу `*-release.yml`. Все они используют общее обнаружение изменений: `mise/tasks/release/components.json` объявляет префикс тега и пути включения для каждого компонента, а git cliff превращает соответствующие коммиты в примечания к релизу.

Сборка CLI (`cli-build-publish.yml`) также создает и публикует артефакт `tuist.spec.json` (генерируется из `tuist --experimental-dump-help`), чтобы сторонние инструменты могли использовать интерфейс командной строки.

## Мониторинг релизов

Вы можете отслеживать релизы через:
- [Страницу релизов GitHub](https://github.com/tuist/tuist/releases)
- Вкладку GitHub Actions для запусков воркфлоу
- Файлы changelog в директории каждого компонента

## Преимущества

Этот подход непрерывного выпуска обеспечивает:

- **Быструю доставку**: изменения попадают к пользователям сразу после слияния
- **Снижение узких мест**: не нужно ждать ручных релизов
- **Четкую коммуникацию**: автоматизированные changelog на основе сообщений коммитов
- **Единый процесс**: одинаковый поток релиза для всех компонентов
- **Гарантию качества**: выпускаются только протестированные изменения

## Устранение неполадок

Если релиз не удался:

1. Проверьте логи GitHub Actions для неудачного воркфлоу
2. Убедитесь, что сообщения ваших коммитов соответствуют общепринятому формату
3. Проверьте, что все тесты проходят
4. Убедитесь, что компонент успешно собирается

Для срочных исправлений, требующих немедленного выпуска:
1. Убедитесь, что ваш коммит имеет четкую область действия
2. После слияния отслеживайте воркфлоу релиза
3. Для сервера или приложения исправление выйдет со следующим пушем; при необходимости запустите ручной релиз
4. Для CLI исправление автоматически попадает в canary. Чтобы доставить его пользователям стабильной версии, сделайте бэкпорт в поддерживаемую стабильную линию (см. [Бэкпорт исправлений в стабильную линию](#backporting-fixes-to-a-stable-line))

## Релиз в App Store

Хотя CLI и сервер следуют описанному выше процессу непрерывного выпуска, **iOS-приложение** является исключением из-за процесса проверки Apple App Store:

- **Ручные релизы**: релизы iOS-приложения требуют ручной отправки в App Store
- **Задержки проверки**: каждый релиз должен пройти процесс проверки Apple, который может занять 1–7 дней
- **Пакетные изменения**: несколько изменений обычно объединяются в каждом релизе iOS
- **TestFlight**: бета-версии могут распространяться через TestFlight перед релизом в App Store
- **Примечания к релизу**: должны быть написаны специально в соответствии с требованиями App Store

iOS-приложение по-прежнему следует тем же соглашениям о коммитах и использует git cliff для генерации changelog, но фактический релиз для пользователей происходит реже и по ручному графику.
