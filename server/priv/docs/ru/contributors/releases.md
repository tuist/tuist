# Релизы

Tuist автоматически публикует новые версии по мере слияния изменений в основную ветку. CLI, сервер и кэш-сервер Kura поставляются через каналы релизов (canary, release candidate, stable), чтобы рекомендуемая установка оставалась стабильной и менялась нечасто; создание release candidate и его продвижение до stable — это осознанные еженедельные шаги. Приложение выпускается непрерывно (приложение для iOS непрерывно разворачивается только в TestFlight, подробнее [здесь](#app-store-release)).

## Обзор

Мы выпускаем следующие основные компоненты:
- **Tuist CLI** — инструмент командной строки, поставляемый через каналы canary, release candidate и stable [каналы](#release-channels)
- **Tuist Server** — бэкенд-сервисы, поставляемые по той же канальной модели, что и CLI
- **Kura** — кэш-сервер, поставляемый по той же канальной модели, что и CLI
- **Tuist App** — приложения для macOS и iOS, выпускаемые непрерывно (приложение для iOS непрерывно разворачивается только в TestFlight, подробнее [здесь](#app-store-release))

Каждый пуш в `main` публикует canary-пререлиз для CLI, сервера и Kura. Стабильный релиз каждого из этих компонентов создаётся только тогда, когда мейнтейнер продвигает проверенный release candidate, а еженедельное расписание запускает все три потока синхронно (см. [Каналы релизов](#release-channels)). Приложение публикует стабильную версию при каждом пуше в `main`.

## Как это работает

### 1. Соглашения о коммитах

Мы используем [Conventional Commits](https://www.conventionalcommits.org/) для структурирования сообщений коммитов. Это позволяет нашим инструментам понимать характер изменений, определять повышение версий и генерировать соответствующие журналы изменений.

Формат: `type(scope): description`

#### Типы коммитов и их влияние

| Тип | Описание | Влияние на версию | Пример |
|------|-------------|----------------|---------|
| `feat` | Новая функция или возможность | Повышение минорной версии (x.Y.z) | `feat(cli): add support for Swift 6` |
| `fix` | Исправление ошибки | Повышение патч-версии (x.y.Z) | `fix(app): resolve crash when opening projects` |
| `docs` | Изменения в документации | Без релиза | `docs: update installation guide` |
| `style` | Изменения стиля кода | Без релиза | `style: format code with swiftformat` |
| `refactor` | Рефакторинг кода | Без релиза | `refactor(server): simplify auth logic` |
| `perf` | Улучшения производительности | Повышение патч-версии | `perf(cli): optimize dependency resolution` |
| `test` | Добавление/изменение тестов | Без релиза | `test: add unit tests for cache` |
| `chore` | Задачи по обслуживанию | Без релиза | `chore: update dependencies` |
| `ci` | Изменения в CI/CD | Без релиза | `ci: add workflow for releases` |

Для CLI эти повышения определяют версию canary и группировку в журнале изменений. Стабильные версии CLI — это минорные линии (`X.Y.0`), создаваемые вручную, а стабильные патчи (`X.Y.Z`) поступают только через бэкпорты, поэтому `feat` или `fix` достигает пользователей CLI через приведённый ниже поток каналов, а не как немедленный стабильный релиз.

#### Критические изменения

Критические изменения вызывают повышение мажорной версии (X.0.0) и должны быть указаны в теле коммита:

```
feat(cli): change default cache location

BREAKING CHANGE: The cache is now stored in ~/.tuist/cache instead of .tuist-cache.
Users will need to clear their old cache directory.
```

### 2. Обнаружение изменений

Каждый компонент использует [git cliff](https://git-cliff.org/) для:
- Анализа коммитов с момента последнего релиза
- Фильтрации коммитов по области (cli, app, server)
- Определения наличия изменений, готовых к релизу
- Автоматической генерации журналов изменений

### 3. Конвейер релизов

При обнаружении изменений, готовых к релизу:

1. **Расчёт версии**: конвейер определяет номер следующей версии
2. **Генерация журнала изменений**: git cliff создаёт журнал изменений на основе сообщений коммитов
3. **Процесс сборки**: компонент собирается и тестируется
4. **Генерация артефактов**: создаются специфичные для релиза ресурсы, такие как архивы CLI, контрольные суммы и спецификация CLI `tuist.spec.json`, генерируемая из `tuist --experimental-dump-help`
5. **Создание релиза**: создаётся релиз на GitHub с прикреплёнными артефактами
6. **Дистрибуция**: обновления публикуются в менеджеры пакетов (например, Homebrew для CLI)

Для приложения это приводит к стабильному релизу при каждом слиянии. Для CLI, сервера и Kura этот же автоматический конвейер создаёт только предварительный релиз **canary**; кандидаты в релизы и стабильные релизы выпускаются в рамках еженедельного цикла (см. [Каналы релизов](#release-channels)).

### 4. Фильтрация по области

Каждый компонент выпускается только при наличии соответствующих изменений:

- **CLI**: коммиты с областью `(cli)` или без указания области
- **App**: коммиты с областью `(app)`
- **Server**: коммиты с областью `(server)`

## Каналы релизов

CLI, сервер и Kura не переводятся в стабильный релиз при каждом пуше в `main`. Каждый из них проходит через три канала, чтобы рекомендуемая установка оставалась стабильной и медленно меняющейся, в то время как ранние пользователи получают сборки для каждого коммита. Пользовательская документация находится по ссылкам <.localized_link href="/cli/release-channels">Каналы релизов CLI</.localized_link> и <.localized_link href="/guides/server/self-host/release-channels">Каналы релизов сервера</.localized_link>; этот раздел представляет собой инструкцию для сопровождающих.

Каждый компонент использует одни и те же три канала:

| Канал | Версия | Кем создаётся |
|---------|---------|--------|
| Canary | `X.Y.0-canary.N` | Автоматически, при каждом пуше в `main`, затрагивающем компонент (`<component>-release.yml`; для Kura вызывается из `server-production-deployment.yml` при изменениях в `kura/`) |
| Кандидат в релизы | `X.Y.0-rc.N` | Каждый понедельник или вручную, на ветке `releases/<component>-<major>.<minor>.x` (`<component>-rc.yml`) |
| Стабильный | `X.Y.Z` | Каждый понедельник или вручную, путём продвижения проверенного кандидата в релизы (`<component>-promote.yml`); патчи через `<component>-backport.yml` |

Сборки Canary и RC публикуются как предварительные релизы на GitHub (никогда не помечаются как «Latest», тег `:latest` на GHCR никогда не перемещается, в Homebrew для CLI не отправляются), поэтому менеджеры пакетов и резолверы образов подбирают их только при явном согласии. Canary всегда нацелен на следующую невыпущенную минорную версию: как только создаётся линия RC, canary в `main` переходит к следующей минорной версии.

Hosted Tuist не ожидает стабильного цикла: сервер развёртывается для каждого коммита, а хостинговые среды canary и production используют новейший canary-релиз Kura. Каскад развёртывания публикует этот canary перед его развёртыванием, поэтому у `kura-release.yml` нет собственного триггера. Изменения только в инструментах релиза Kura (`mise/tasks/kura/**`, рабочие процессы `kura-*.yml`) не приводят к созданию canary-релиза.

Вы никогда не выбираете номера версий вручную. Следующая версия каждого канала выводится из существующих git-тегов с помощью `mise/tasks/<component>/release/channel-version.sh`, который вызывают приведённые ниже рабочие процессы.

Ветки релизов имеют пространство имён для каждого компонента (`releases/server-X.Y.x`, `releases/kura-X.Y.x`, `releases/X.Y.x` для CLI), чтобы линии трёх компонентов никогда не пересекались на одной минорной версии.

### Еженедельное расписание

Каждый понедельник в 06:00 UTC задачи продвижения трёх компонентов выполняются синхронно: **CLI Promote to Stable**, **Server Promote to Stable** и **Kura Promote to Stable**. Каждая задача продвигает новейшую линию RC, которая ещё не стала стабильной, обычно это линия, созданная в предыдущий понедельник. Если такой линии нет, задача ничего не публикует.

По завершении продвижения, независимо от результата, запускается соответствующий рабочий процесс **Release Candidate** (`cli-rc.yml`, `server-rc.yml`, `kura-rc.yml`) через `workflow_run` и создаёт следующую линию из `main`.

Если запланированный запуск завершается ошибкой или отменяется, в Slack отправляется сообщение. Продвижение завершается ошибкой, если в ветке релиза есть коммиты после её последнего кандидата в релизы. Чтобы выпустить эту линию, создайте на ней новый кандидат в релизы и продвиньте его вручную. В противном случае в следующий понедельник будет продвинута более новая линия.

### Создание кандидата в релизы

Чтобы создать новую линию вне еженедельного расписания (замените ниже название рабочего процесса компонента):

1. Запустите рабочий процесс **\<Component\> Release Candidate** (например, `server-rc.yml`) с пустым входным параметром `branch`.
2. Он публикует `X.Y.0-rc.1` и после успешного завершения создаёт защищённую ветку `releases/<component>-X.Y.x` на собранном коммите.

Чтобы включить критическое исправление или регрессию в тестируемую линию, сделайте cherry-pick в ветку релиза через PR (тот же поток, что и для бэкпортов; CI никогда не делает cherry-pick), затем обновите RC:

1. Создайте ветку от `releases/<component>-X.Y.x`, сделайте cherry-pick исправления, откройте PR обратно в ветку релиза, разрешите возможные конфликты и выполните слияние.
2. Снова запустите рабочий процесс **Release Candidate** с параметром `branch=releases/<component>-X.Y.x`. Он опубликует `X.Y.0-rc.(N+1)` из HEAD ветки.

Тестируемая линия заморожена по функционалу: в неё попадают только критические исправления и регрессии.

### Продвижение в стабильную версию

Чтобы продвинуть линию вне еженедельного расписания после чистого тестирования её RC:

1. Запустите рабочий процесс **\<Component\> Promote to Stable** (например, `server-promote.yml`) с параметром `branch=releases/<component>-X.Y.x`.
2. Он публикует образ с семантическим тегом версии с параметром `make_latest=true`, перемещая тег GHCR `:latest` и указатель «Latest» на GitHub. CLI также обновляет формулу Homebrew.

Продвижение не запускается, если HEAD ветки не совпадает точно с коммитом, на который указывает последний RC. Поэтому, если после последнего RC в линию были включены какие-либо исправления, необходимо создать новый RC и дать ему протестироваться перед выпуском в стабильную версию.

### Бэкпорт исправлений в стабильную линию

Когда линия становится стабильной, выпускайте патчи с помощью предназначенного только для CLI рабочего процесса **Backport Release** (`cli-backport.yml`): сделайте cherry-pick исправления в `releases/X.Y.x` через PR, затем запустите рабочий процесс с этой веткой, чтобы создать `X.Y.(Z+1)`. Бэкпорты никогда не перемещают указатель «Latest» и не обновляют формулу Homebrew. Одновременно поддерживаются две линии: текущая линия получает исправления регрессий и уязвимостей безопасности, предыдущая — только критические исправления и исправления уязвимостей безопасности. Другие исправления ошибок не бэкпортятся и выходят со следующей минорной версией.

Для сервера и Kura бэкпорты сейчас создаются путём запуска рабочего процесса продвижения для более старой ветки релиза. В дальнейшем будут добавлены специализированные рабочие процессы для бэкпортов, аналогичные тем, что используются в CLI.

## Написание хороших сообщений коммитов

Поскольку сообщения коммитов напрямую влияют на примечания к выпуску, важно писать понятные и описательные сообщения:

### Рекомендуется:
- Используйте настоящее время: «add feature», а не «added feature»
- Будьте лаконичны, но информативны
- Указывайте область изменений, если они относятся к конкретному компоненту
- Ссылайтесь на задачи, если это применимо: `fix(cli): resolve build cache issue (#1234)`

### Не рекомендуется:
- Использовать расплывчатые сообщения вроде «fix bug» или «update code»
- Объединять несколько несвязанных изменений в одном коммите
- Забывать указывать информацию о ломающих изменениях

### Ломающие изменения

Для ломающих изменений включайте `BREAKING CHANGE:` в тело коммита:

```
feat(cli): change cache directory structure

BREAKING CHANGE: Cache files are now stored in a new directory structure.
Users need to clear their cache after updating.
```

## Рабочие процессы релизов

CLI, сервер и Kura имеют собственные наборы рабочих процессов каналов, следующих одной структуре:

- `<component>-release.yml` — публикует канареечную версию при каждом затрагивающем компонент пуше в `main` (для Kura это переиспользуемый рабочий процесс, который вызывает `server-production-deployment.yml` при изменениях в `kura/`)
- `<component>-rc.yml` — создаёт кандидата в релизы каждый понедельник (через `workflow_run` после продвижения) или вручную создаёт или обновляет его
- `<component>-promote.yml` — продвигает ожидающий RC в стабильную версию каждый понедельник в 06:00 UTC или вручную продвигает протестированный RC
- `<component>-build-publish.yml` — общий конвейер сборки и публикации, вызываемый тремя вышеуказанными процессами

CLI дополнительно имеет `cli-backport.yml` для создания патчей на стабильной линии. Все рабочие процессы компонента сериализуются через одну группу параллелизма `<component>-publish`, чтобы разрешение версий и тегирование никогда не конкурировали. Kura является исключением: её канареечная версия использует `kura-canary-publish`, а RC и продвижение используют `kura-stable-publish`, поэтому длительная сборка RC или продвижения не блокирует каскад развёртывания. Пространства имён тегов не пересекаются, поэтому две группы не могут конфликтовать.

Helm-чарт и инфраструктурные образы (оператор CAPI, контроллер раннеров, образ процессора xcresult, образ linux-раннера и т. д.) по-прежнему выпускаются через `.github/workflows/server-production-deployment.yml`. Он запускается при пушах в `main` и выполняет каскад канареечная версия → приёмочные тесты → продакшн для хостингового развёртывания, публикуя эти инфраструктурные компоненты по мере их изменения. Приложение, кэш, плагин Gradle, навыки, Noora и автономные инфраструктурные контроллеры имеют выделенный рабочий процесс `*-release.yml`. Все они используют общее обнаружение изменений: `mise/tasks/release/components.json` объявляет префикс тега и пути включения для каждого компонента, а git cliff превращает соответствующие коммиты в примечания к выпуску.

Сборка CLI (`cli-build-publish.yml`) также создаёт и публикует артефакт `tuist.spec.json` (сгенерированный из `tuist --experimental-dump-help`), чтобы сторонние инструменты могли использовать интерфейс командной строки.

## Мониторинг релизов

Вы можете отслеживать релизы через:
- [Страницу релизов GitHub](https://github.com/tuist/tuist/releases)
- Вкладку GitHub Actions для запусков рабочих процессов
- Файлы журнала изменений в директории каждого компонента

## Преимущества

Этот подход непрерывного выпуска обеспечивает:

- **Быструю доставку**: изменения попадают к пользователям сразу после слияния
- **Снижение узких мест**: не нужно ждать ручных релизов
- **Чёткую коммуникацию**: автоматическое создание журнала изменений из сообщений коммитов
- **Единый процесс**: одинаковый поток выпуска для всех компонентов
- **Гарантию качества**: выпускаются только протестированные изменения

## Устранение неполадок

Если выпуск завершился неудачей:

1. Проверьте логи GitHub Actions для неудачного рабочего процесса
2. Убедитесь, что сообщения ваших коммитов соответствуют общепринятому формату
3. Убедитесь, что все тесты проходят успешно
4. Проверьте, что компонент собирается без ошибок

Для срочных исправлений, требующих немедленного выпуска:
1. Убедитесь, что у вашего коммита чётко указана область изменений
2. После слияния отслеживайте рабочий процесс выпуска
3. Для сервера или приложения исправление выйдет со следующим пушем; при необходимости запустите ручной выпуск
4. Для CLI исправление автоматически попадает в канареечный канал. Чтобы доставить его пользователям стабильной версии, выполните бэкпорт в поддерживаемую стабильную линию (см. [Бэкпорт исправлений в стабильную линию](#backporting-fixes-to-a-stable-line))

## Выпуск в App Store

Хотя CLI и сервер следуют описанному выше процессу непрерывного выпуска, **iOS-приложение** является исключением из-за процесса проверки Apple в App Store:

- **Ручные выпуски**: выпуски iOS-приложения требуют ручной отправки в App Store
- **Задержки проверки**: каждый выпуск должен пройти проверку Apple, которая может занять 1–7 дней
- **Пакетные изменения**: несколько изменений обычно объединяются в один выпуск iOS-приложения
- **TestFlight**: бета-версии могут распространяться через TestFlight до выпуска в App Store
- **Примечания к выпуску**: должны быть написаны специально в соответствии с требованиями App Store

iOS-приложение по-прежнему следует тем же соглашениям о коммитах и использует git cliff для генерации журнала изменений, но фактический выпуск для пользователей происходит реже и по ручному графику.
