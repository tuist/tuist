# Релизы

Tuist автоматически публикует новые версии по мере слияния изменений в основную ветку. CLI, сервер и кэш-сервер Kura поставляются через каналы релизов (canary, release candidate, stable), чтобы рекомендуемая установка оставалась стабильной и обновлялась нечасто; выпуск кандидата в релиз и его продвижение до стабильной версии — это осознанные еженедельные шаги. Приложение выпускается непрерывно (iOS-приложение разворачивается только в TestFlight, подробнее [здесь](#app-store-release)).

## Обзор

Мы выпускаем следующие основные компоненты:
- **Tuist CLI** — инструмент командной строки, поставляемый через каналы canary, release candidate и stable [каналы](#release-channels)
- **Tuist Server** — бэкенд-сервисы, поставляемые по той же канальной модели, что и CLI
- **Kura** — кэш-сервер, поставляемый по той же канальной модели, что и CLI
- **Tuist App** — приложения для macOS и iOS, выпускаемые непрерывно (iOS-приложение разворачивается только в TestFlight, подробнее [здесь](#app-store-release))

Каждый пуш в `main` публикует предварительный релиз canary для CLI, сервера и Kura. Стабильный релиз для каждого из этих компонентов выпускается только тогда, когда мейнтейнер продвигает проверенный кандидат в релиз, а еженедельное расписание синхронно запускает все три потока (см. [Каналы релизов](#release-channels)). Приложение публикует стабильную версию при каждом пуше в `main`.

## Как это работает

### 1. Соглашения о коммитах

Мы используем [Conventional Commits](https://www.conventionalcommits.org/) для структурирования сообщений коммитов. Это позволяет нашим инструментам понимать характер изменений, определять повышение версий и генерировать соответствующие списки изменений.

Формат: `type(scope): description`

#### Типы коммитов и их влияние

| Тип | Описание | Влияние на версию | Пример |
|------|-------------|----------------|---------|
| `feat` | Новая функция или возможность | Повышение минорной версии (x.Y.z) | `feat(cli): add support for Swift 6` |
| `fix` | Исправление ошибки | Повышение патч-версии (x.y.Z) | `fix(app): resolve crash when opening projects` |
| `docs` | Изменения в документации | Без релиза | `docs: update installation guide` |
| `style` | Изменения стиля кода | Без релиза | `style: format code with swiftformat` |
| `refactor` | Рефакторинг кода | Без релиза | `refactor(server): simplify auth logic` |
| `perf` | Улучшения производительности | Повышение патч-версии | `perf(cli): optimize dependency resolution` |
| `test` | Добавление/изменение тестов | Без релиза | `test: add unit tests for cache` |
| `chore` | Задачи по обслуживанию | Без релиза | `chore: update dependencies` |
| `ci` | Изменения CI/CD | Без релиза | `ci: add workflow for releases` |

Для CLI эти повышения определяют версию canary и группировку в списке изменений. Стабильные версии CLI — это минорные линии (`X.Y.0`), выпускаемые вручную, а стабильные патчи (`X.Y.Z`) поступают только через бэкпорты, поэтому `feat` или `fix` достигает пользователей CLI через описанный ниже поток каналов, а не как немедленный стабильный релиз.

#### Критические изменения

Критические изменения вызывают повышение мажорной версии (X.0.0) и должны быть указаны в теле коммита:

```
feat(cli): change default cache location

BREAKING CHANGE: The cache is now stored in ~/.tuist/cache instead of .tuist-cache.
Users will need to clear their old cache directory.
```

### 2. Обнаружение изменений

Каждый компонент использует [git cliff](https://git-cliff.org/) для:
- Анализа коммитов с момента последнего релиза
- Фильтрации коммитов по области (cli, app, server)
- Определения наличия изменений, готовых к релизу
- Автоматической генерации списков изменений

### 3. Пайплайн релиза

Когда обнаружены изменения, готовые к релизу:

1. **Расчет версии**: пайплайн определяет следующий номер версии
2. **Генерация списка изменений**: git cliff создает список изменений на основе сообщений коммитов
3. **Процесс сборки**: компонент собирается и тестируется
4. **Генерация артефактов**: создаются специфичные для релиза ресурсы, такие как бандлы CLI, контрольные суммы и спецификация CLI `tuist.spec.json`, генерируемая из `tuist --experimental-dump-help`
5. **Создание релиза**: создается релиз на GitHub с артефактами
6. **Дистрибуция**: обновления отправляются в менеджеры пакетов (например, Homebrew для CLI)

Для приложения это приводит к стабильному релизу при каждом слиянии. Для CLI, сервера и Kura этот же автоматический пайплайн выпускает только предварительный релиз **canary**; кандидаты в релизы и стабильные релизы выпускаются еженедельно (см. [Каналы релизов](#release-channels)).

### 4. Фильтрация по области

Каждый компонент выпускается только при наличии соответствующих изменений:

- **CLI**: коммиты с областью `(cli)` или без области
- **App**: коммиты с областью `(app)`
- **Server**: коммиты с областью `(server)`

## Каналы релизов

CLI, сервер и Kura не переводятся в стабильный релиз при каждом пуше в `main`. Каждый из них проходит через три канала, чтобы рекомендуемая установка оставалась стабильной и медленно меняющейся, в то время как ранние пользователи получают сборки для каждого коммита. Пользовательская документация находится по адресам <.localized_link href="/cli/release/channels">Каналы релизов CLI</.localized_link> и <.localized_link href="/guides/server/self-host/release/channels">Каналы релизов сервера</.localized_link>; этот раздел является руководством для мейнтейнеров.

Каждый компонент использует одни и те же три канала:

| Канал | Версия | Выпускается |
|---------|---------|--------|
| Canary | `X.Y.0-canary.N` | Автоматически, при каждом пуше в `main`, затрагивающем компонент (`<component>-release.yml`; для Kura вызывается `server-production-deployment.yml`, когда изменено `kura/`) |
| Кандидат в релизы | `X.Y.0-rc.N` | Каждый понедельник или вручную, в ветке `releases/<component>-<major>.<minor>.x` (`<component>-rc.yml`) |
| Стабильный | `X.Y.Z` | Каждый понедельник или вручную, путем продвижения проверенного RC (`<component>-promote.yml`); патчи через `<component>-backport.yml` |

Сборки Canary и RC публикуются как предварительные релизы на GitHub (никогда не помечаются как «Latest», никогда не перемещают тег `:latest` на GHCR, никогда не отправляются в Homebrew для CLI), поэтому менеджеры пакетов и резолверы образов выбирают их только при явном согласии. Canary всегда нацелен на следующую невыпущенную минорную версию: как только линия RC выпущена, canary `main` переходит к следующей минорной версии.

Хостинг Tuist не ждет стабильного релиза: сервер развертывается для каждого коммита, а хостинг canary и production используют новейший canary Kura. Каскад развертывания публикует этот canary перед его развертыванием, поэтому у `kura-release.yml` нет собственного триггера. Изменения только в инструментах релиза Kura (`mise/tasks/kura/**`, воркфлоу `kura-*.yml`) не приводят к выпуску canary.

Вы никогда не выбираете номера версий вручную. Следующая версия каждого канала выводится из существующих git-тегов скриптом `mise/tasks/<component>/release/channel-version.sh`, который вызывают приведенные ниже воркфлоу.

Ветки релизов изолированы по компонентам (`releases/server-X.Y.x`, `releases/kura-X.Y.x`, `releases/X.Y.x` для CLI), чтобы линии трех компонентов никогда не пересекались на одной минорной версии.

### Еженедельное расписание

Каждый понедельник в 06:00 UTC задачи продвижения трех компонентов выполняются синхронно: **CLI Promote to Stable**, **Server Promote to Stable** и **Kura Promote to Stable**. Каждая из них продвигает новейшую линию RC, которая еще не стала стабильной, обычно это линия, выпущенная в предыдущий понедельник. Если такой линии нет, задача ничего не публикует.

Когда продвижение завершается, независимо от результата, соответствующий воркфлоу **Release Candidate** (`cli-rc.yml`, `server-rc.yml`, `kura-rc.yml`) запускается через `workflow_run` и выпускает следующую линию из `main`.

Если запланированный запуск завершается ошибкой или отменяется, в Slack отправляется сообщение. Продвижение завершается ошибкой, если в ветке релиза есть коммиты после последнего RC. Чтобы выпустить эту линию, создайте на ней новый RC и продвиньте его вручную. В противном случае в следующий понедельник будет продвинута более новая линия.

### Выпуск кандидата в релизы

Чтобы выпустить новую линию вне еженедельного расписания (подставьте ниже имя воркфлоу компонента):

1. Запустите воркфлоу **\<Component\> Release Candidate** (например, `server-rc.yml`) с пустым входным параметром `branch`.
2. Он публикует `X.Y.0-rc.1` и, после успешного завершения, создает защищенную ветку `releases/<component>-X.Y.x` на собранном коммите.

Чтобы включить критическое исправление или регрессию в линию, находящуюся на этапе тестирования, выполните cherry-pick в ветку релиза через PR (тот же процесс, что и для бэкпортов; CI никогда не делает cherry-pick самостоятельно), затем создайте новую версию RC:

1. Создайте ветку от `releases/<component>-X.Y.x`, выполните cherry-pick исправления, откройте PR обратно в ветку релиза, разрешите возможные конфликты и выполните слияние.
2. Снова запустите воркфлоу **Release Candidate** с параметром `branch=releases/<component>-X.Y.x`. Он опубликует `X.Y.0-rc.(N+1)` из HEAD ветки.

Линия на этапе тестирования заморожена по функциям: в нее попадают только критические исправления и регрессии.

### Продвижение в стабильный релиз

Чтобы продвинуть линию вне еженедельного расписания, после того как ее RC успешно прошел этап тестирования:

1. Запустите воркфлоу **\<Component\> Promote to Stable** (например, `server-promote.yml`) с параметром `branch=releases/<component>-X.Y.x`.
2. Он публикует образ с тегом semver, устанавливая `make_latest=true`, что перемещает тег GHCR `:latest` и указатель "Latest" на GitHub. CLI дополнительно обновляет формулу Homebrew.

Продвижение не запустится, если HEAD ветки не совпадает точно с коммитом, на который указывает последний RC. Поэтому, если после последнего RC в линию были включены какие-либо исправления, необходимо создать новый RC и дать ему время на тестирование, прежде чем он сможет быть выпущен как стабильный.

### Бэкпорт исправлений в стабильную линию

Когда линия становится стабильной, выпускайте патчи с помощью воркфлоу **Backport Release**, доступного только для CLI (`cli-backport.yml`): выполните cherry-pick исправления в `releases/X.Y.x` через PR, затем запустите воркфлоу для этой ветки, чтобы выпустить `X.Y.(Z+1)`. Бэкпорты никогда не перемещают указатель "Latest" и не обновляют формулу Homebrew. Одновременно поддерживаются две линии: текущая линия получает исправления регрессий и уязвимостей безопасности, предыдущая линия получает только критические исправления и исправления безопасности. Другие исправления ошибок не бэкпортятся и выходят со следующим минорным релизом.

Для сервера и Kura используйте **Server Backport Release** (`server-backport.yml`) или **Kura Backport Release** (`kura-backport.yml`). Продвижение публикует только `X.Y.0` версии RC; оно не может применять патчи к уже стабильной линии.

1. Начните с последнего опубликованного стабильного тега компонента для выбранной линии `X.Y` и откройте точечный PR с исправлением в существующую ветку `releases/server-X.Y.x` или `releases/kura-X.Y.x`. Более новый минорный или мажорный релиз не препятствует применению патчей к поддерживаемой линии. Не включайте посторонние изменения из main.
2. Проверьте и слейте исходный PR. Получите удаленную ветку релиза и подтвердите ее **финальный слитый коммит**, включая поддерживаемые платформы компонента и положительные/отрицательные контрольные проверки TLS. Успешная проверка головы перед слиянием не является подтверждением другого squash-коммита или коммита слияния.
3. Получив отдельное одобрение на публикацию, запустите соответствующий воркфлоу бэкпорта **из main**, установив `source_sha` в тот самый подтвержденный слитый коммит, а `base_tag` — в текущий стабильный тег, например `server@X.Y.Z` или `kura@X.Y.Z`. Воркфлоу выводит `X.Y.(Z+1)`; операторы не выбирают минорное обновление и не продвигают содержимое canary.

Планирование обновляет точную удаленную ветку и базовый тег, требует, чтобы выбранный источник совпадал с концом ветки, отвергает неизмененный источник или изменения вне компонента, его входные данные политики доверия и валидацию, и фиксирует разрешенный базовый коммит. Контроли, основанные на main, повторяют эти проверки непосредственно перед публикацией версионированного образа и на GitHub. Если исходная ветка, стабильная база или доступная версия изменяются, остановитесь и повторно подтвердите квалификацию, вместо замены источника.

Бэкпорты используют существующие мультиплатформенные издатели, не перемещая указатель "Latest" на GitHub или `:latest` в GHCR. Публикация отделена от развертывания на хостинге: эти воркфлоу не продвигают размещенный сервер или флот Kura, не обходят приемку canary и не квалифицируют установленную среду выполнения. Вспомогательные скрипты сборки и Dockerfile по-прежнему берутся из выбранного стабильного источника. Контроли являются этапами публикации, а не задачами сборки без учетных данных; сборки могут загружать нетегированные дайджесты образов до финального этапа. Публикация образа и на GitHub не является атомарной: если позже этап завершается ошибкой после публикации тега образа, проверьте частичный релиз и сохраните его исходный источник и артефакты. Никогда не заменяйте существующий релиз и не используйте другие байты под его тегом.

## Написание хороших сообщений коммитов

Поскольку сообщения коммитов напрямую влияют на примечания к релизу, важно писать четкие и описательные сообщения:

### Делайте:
- Используйте настоящее время: "add feature", а не "added feature"
- Будьте лаконичны, но описательны
- Указывайте область изменений, если они относятся к конкретному компоненту
- Ссылайтесь на задачи, если применимо: `fix(cli): resolve build cache issue (#1234)`

### Не делайте:
- Не используйте расплывчатые сообщения, такие как "fix bug" или "update code"
- Не смешивайте несколько несвязанных изменений в одном коммите
- Не забывайте включать информацию о критических изменениях

### Критические изменения

Для критических изменений включите `BREAKING CHANGE:` в тело коммита:

```
feat(cli): change cache directory structure

BREAKING CHANGE: Cache files are now stored in a new directory structure.
Users need to clear their cache after updating.
```

## Воркфлоу релизов

CLI, сервер и Kura имеют свой собственный набор воркфлоу каналов, следующих одной структуре:

- `<component>-release.yml` — публикует canary при каждом пуше в `main`, затрагивающем компонент (для Kura это переиспользуемый воркфлоу, который вызывает `server-production-deployment.yml`, когда изменяется `kura/`)
- `<component>-rc.yml` — выпускает кандидата в релизы каждый понедельник (через `workflow_run` после продвижения) или вручную выпускает или обновляет его
- `<component>-promote.yml` — продвигает ожидающий RC в стабильный релиз каждый понедельник в 06:00 UTC или вручную продвигает протестированный RC
- `<component>-build-publish.yml` — общий конвейер сборки и публикации, вызываемый тремя вышеуказанными воркфлоу

CLI, сервер и Kura дополнительно имеют `<component>-backport.yml` для выпуска патчей на стабильной линии. Все воркфлоу компонента сериализуются через одну группу параллелизма `<component>-publish`, чтобы разрешение версий и тегирование никогда не конфликтовали. Kura является исключением: ее canary использует `kura-canary-publish`, а ее RC, продвижение и бэкпорт используют `kura-stable-publish`, поэтому длительная стабильная сборка никогда не задерживает каскад развертывания. Пространства имен тегов не пересекаются, поэтому две группы не могут столкнуться.

Helm-чарт и инфраструктурные образы (CAPI operator, runners controller, xcresult processor image, linux runner image и другие) по-прежнему выпускаются через `.github/workflows/server-production-deployment.yml`. Процесс запускается при пушах в `main` и выполняет каскад canary → приемочные тесты → продакшен для хостингового развертывания, публикуя эти инфраструктурные компоненты по мере их изменения. Приложение, кэш, плагин Gradle, навыки, Noora и автономные инфраструктурные контроллеры имеют выделенный воркфлоу `*-release.yml`. Все они используют общий механизм обнаружения изменений: `mise/tasks/release/components.json` объявляет префикс тега и пути включения для каждого компонента, а git cliff превращает соответствующие коммиты в примечания к релизу.

Сборка CLI (`cli-build-publish.yml`) также создает и публикует артефакт `tuist.spec.json` (сгенерированный из `tuist --experimental-dump-help`), чтобы сторонние инструменты могли использовать интерфейс командной строки.

## Мониторинг релизов

Вы можете отслеживать релизы через:
- [Страницу релизов GitHub](https://github.com/tuist/tuist/releases)
- Вкладку GitHub Actions для запусков воркфлоу
- Файлы changelog в директории каждого компонента

## Преимущества

Этот подход непрерывного релиза обеспечивает:

- **Быструю доставку**: изменения попадают к пользователям сразу после слияния
- **Снижение узких мест**: не нужно ждать ручных релизов
- **Четкую коммуникацию**: автоматизированные changelog на основе сообщений коммитов
- **Единообразный процесс**: одинаковый поток релиза для всех компонентов
- **Гарантию качества**: выпускаются только протестированные изменения

## Устранение неполадок

Если релиз не удался:

1. Проверьте логи GitHub Actions для неудачного воркфлоу
2. Убедитесь, что ваши сообщения коммитов соответствуют общепринятому формату
3. Проверьте, что все тесты проходят успешно
4. Убедитесь, что компонент собирается успешно

Для срочных исправлений, требующих немедленного выпуска:
1. Убедитесь, что ваш коммит имеет четкую область применения
2. После слияния отслеживайте воркфлоу релиза
3. Для сервера или приложения исправление выйдет со следующим пушем; при необходимости запустите ручной релиз
4. Для CLI исправление автоматически попадает в canary. Чтобы доставить его пользователям стабильной версии, сделайте бэкпорт в поддерживаемую стабильную линию (см. [Бэкпорт исправлений в стабильную линию](#backporting-fixes-to-a-stable-line))

## Релиз в App Store

Хотя CLI и сервер следуют описанному выше процессу непрерывного релиза, **iOS-приложение** является исключением из-за процесса проверки Apple App Store:

- **Ручные релизы**: релизы iOS-приложения требуют ручной отправки в App Store
- **Задержки проверки**: каждый релиз должен пройти процесс проверки Apple, который может занять 1–7 дней
- **Пакетные изменения**: несколько изменений обычно объединяются в каждом релизе iOS
- **TestFlight**: бета-версии могут распространяться через TestFlight перед релизом в App Store
- **Примечания к релизу**: должны быть написаны специально в соответствии с требованиями App Store

iOS-приложение по-прежнему следует тем же соглашениям о коммитах и использует git cliff для генерации changelog, но фактический релиз для пользователей происходит реже и по ручному графику.
