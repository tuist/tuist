# Аутентификация {#authentication}

Для взаимодействия с сервером CLI должен аутентифицировать запросы, используя [bearer-аутентификацию](https://swagger.io/docs/specification/authentication/bearer-authentication/). CLI поддерживает аутентификацию как пользователя, как аккаунта или с помощью токена OIDC.

## Как пользователь {#as-a-user}

При локальном использовании CLI на вашем компьютере мы рекомендуем аутентифицироваться как пользователь. Для аутентификации в качестве пользователя выполните следующую команду:

```bash
tuist auth login
```

Команда проведет вас через процесс веб-аутентификации. После успешной аутентификации CLI сохранит долгоживущий токен обновления и короткоживущий токен доступа в директории `~/.config/tuist/credentials`. Каждый файл в этой директории соответствует домену, для которого выполнена аутентификация; по умолчанию это `tuist.dev.json`. Данные в этой директории конфиденциальны, поэтому **обязательно обеспечьте их безопасность**.

CLI автоматически использует учетные данные при отправке запросов к серверу. Если токен доступа истек, CLI использует токен обновления для получения нового токена доступа.

> [!NOTE]
> Если ваша организация использует единый вход (SSO), выберите опцию корпоративного входа в браузере и введите свой рабочий адрес электронной почты. Tuist может найти провайдера на основе вашего существующего членства в организации или <.localized_link href="/guides/integrations/authentication/sso#verify-a-login-email-domain">проверенного домена электронной почты для входа</.localized_link>.

## Токены OIDC {#oidc-tokens}

Для сред CI, поддерживающих OpenID Connect (OIDC), Tuist может выполнять аутентификацию автоматически, не требуя управления долгоживущими секретами. При запуске в поддерживаемой среде CI CLI автоматически определит провайдера токенов OIDC и обменяет предоставленный CI токен на токен доступа Tuist.

### Поддерживаемые провайдеры {#supported-ci-providers}

Tuist распознает следующие провайдеры CI и сопоставляет их токены с проектами через подключение вашего репозитория:

- GitHub Actions
- CircleCI
- Bitrise

Любой другой провайдер удостоверений, выдающий токены OpenID Connect, может пройти аутентификацию через [политику доверия идентификаторам рабочих нагрузок](#workload-identity-trust-policies), которую вы настраиваете один раз для всех текущих и будущих проектов в вашем аккаунте, например [Fly.io Machines](#flyio-machines).

### Настройка аутентификации OIDC {#setting-up-oidc-authentication}

Для GitHub Actions, CircleCI и Bitrise:

1. **Подключите ваш репозиторий к Tuist**: следуйте <.localized_link href="/guides/integrations/gitforge/github">руководству по интеграции с GitHub</.localized_link>, чтобы подключить ваш репозиторий GitHub к проекту Tuist.

2. **Выполните `tuist auth login`**: в вашем CI-воркфлоу выполните `tuist auth login` перед любыми командами, требующими аутентификации. CLI автоматически определит среду CI и выполнит аутентификацию с использованием OIDC.

Смотрите <.localized_link href="/guides/integrations/continuous-integration">руководство по непрерывной интеграции</.localized_link> для примеров конфигурации для конкретных провайдеров.

### Политики доверия идентификаторам рабочих нагрузок {#workload-identity-trust-policies}

Политика доверия позволяет рабочим нагрузкам от другого провайдера удостоверений, таким как платформа развертывания, кластер Kubernetes или самостоятельно управляемая система CI, получать доступ к проекту без долгоживущего секрета Tuist. Провайдер должен:

- Быть доступным по HTTPS по публичному адресу. Tuist не следует за перенаправлениями и не подключается к частным или внутренним сетевым адресам, включая адреса от самостоятельно размещенных серверов Tuist.
- Выдавать JWT, подписанные асимметричным ключом, например `RS256` или `ES256`. Токены без подписи и токены, подписанные общим секретом (`HS256` и аналогичные), отклоняются.
- Публиковать свои ключи подписи в виде набора JSON Web Key Set (JWKS) по фиксированному HTTPS-URL. Ответ должен быть не более 64 КиБ и содержать не более 20 ключей.
- Включать срок действия (`exp`) в каждый токен.

Эмитенты GitHub Actions, CircleCI и Bitrise зарезервированы для описанного выше потока на основе репозитория и не могут использоваться в политике доверия.

> [!NOTE]
> Для самостоятельного развертывания примените миграции базы данных и обновите каждую обслуживающую реплику сервера Tuist перед настройкой идентификаторов рабочих нагрузок или переносом задач на них. Затем обновите CLI или интеграцию Elixir до версии, поддерживающей `TUIST_OIDC_TOKEN` и `TUIST_OIDC_ACCOUNT`. Существующие задачи GitHub Actions, CircleCI и Bitrise продолжают использовать авторизацию на основе репозитория и не требуют хэндла аккаунта. Перед переключением производственных задач проверьте обмен короткоживущим токеном и операцию кэширования с предполагаемой рабочей нагрузкой. Чтобы прекратить новые обмены, удалите политику; подождите до одного часа, чтобы уже выданные токены доступа Tuist истекли. Удаление политики не отзывает эти токены немедленно.

#### Создание политики {#create-a-trust-policy}

В панели управления Tuist откройте раздел **Настройки** > **Аутентификация** вашего аккаунта и найдите раздел **Идентификаторы рабочих нагрузок**. Вы должны быть администратором аккаунта (или владельцем личного аккаунта). Каждый аккаунт может иметь до 20 политик. Настройте идентификатор один раз для доступа CI ко всему аккаунту; выбор отдельных проектов не требуется.

Используйте переключатель рядом с **Идентификаторы рабочих нагрузок**, чтобы открыть форму политики. Переключатель включен, если в аккаунте есть сохраненные идентификаторы, и остается включенным после сохранения. Он выключен для аккаунтов без идентификаторов. Раздел появляется ниже **Предоставление SCIM** для организаций. Скрытие формы сохраняет черновик и не отключает аутентификацию рабочих нагрузок: карточки сохраненных идентификаторов и ссылка на документацию по настройке остаются видимыми. Каждая карточка показывает имя идентификатора, URL эмитента и JWKS, аудиторию, точные JSON-утверждения, область действия на весь аккаунт и время создания. Удалите идентификатор, используя действие на его карточке.

Выберите **Пользовательский провайдер**, чтобы ввести поля ниже, или **Fly.io Machines**, чтобы сгенерировать их из slug вашей организации и числовых идентификаторов организации и приложения. Шаблон Fly позволяет редактировать сгенерированный эмитент, URL JWKS и утверждения в разделе **Расширенная конфигурация**. Изменение шаблонов или вспомогательных значений сохраняет поля, которые вы отредактировали вручную. Если ваш эмитент, URL JWKS или утверждения переопределяют шаблон, Tuist раскрывает **Расширенная конфигурация** и показывает предупреждение, чтобы вы могли проверить сохраняемую политику. Вернитесь к **Пользовательскому провайдеру**, чтобы продолжить без помощников Fly. Шаблоны только заполняют конфигурацию и не меняют способ проверки токенов Tuist.

| Поле | Описание |
| --- | --- |
| Имя | Метка для распознавания политики, уникальная в пределах аккаунта. |
| URL эмитента | Утверждение `iss` токена. Оно должно совпадать точно, включая любой завершающий слэш. |
| URL JWKS | HTTPS-URL ключей подписи провайдера. Tuist использует этот URL напрямую и не читает документ обнаружения OpenID Connect провайдера, поэтому скопируйте `jwks_uri` из документации провайдера или из `<issuer>/.well-known/openid-configuration`. |
| Аудитория | Аудитория, для которой должен быть выпущен токен, по умолчанию `tuist`. Утверждение `aud` токена должно равняться ей или, если `aud` является списком, содержать её. Используйте значение, которое принимает только Tuist, чтобы токены, выпущенные для других сервисов, нельзя было здесь повторно использовать. |
| Утверждения | JSON-объект с 1–10 утверждениями, которые должен содержать токен, например `{"sub": "system:serviceaccount:ci:builder"}`. Входные данные JSON ограничены 8 КиБ. Значения должны быть строками, знаковыми 64-битными целыми числами или булевыми значениями, и они должны совпадать точно, включая их тип: `"123"` не совпадает с `123`. Вложенные объекты, списки и временные или токеновые утверждения, такие как `iss`, `aud`, `exp`, `nbf`, `iat` и `jti`, не разрешены. |

Каждая политика предоставляет CI-доступ ко **всем текущим и будущим проектам, принадлежащим аккаунту**, без выбора отдельных проектов. Вы можете настроить идентичность до создания первого проекта. Это не дает прав администрирования аккаунта или доступа к другому аккаунту.

Любая рабочая нагрузка, которая может получить токен с совпадающими утверждениями, получает доступ ко всем этим проектам, поэтому выбирайте утверждения, которые гарантируются провайдером и которые никто не сможет повторно использовать. Отдавайте предпочтение стабильным числовым идентификаторам вместо имен, которые можно переименовать или зарегистрировать заново после удаления.

> [!WARNING]
> В общем провайдере идентичностей привяжите политику к вашей организации или тенанту **и** к целевому приложению, проекту или сервисному аккаунту. Имя ветки, такое как `main`, среда, такая как `production`, или общая роль сами по себе не являются границей идентичности: другой тенант может получить токен с теми же значениями. Например, политика GitLab.com должна включать стабильный `project_id` целевого проекта, а не только `ref`. Совпадающий токен предоставляет CI-доступ ко всему аккаунту, включая запись в кэш, поэтому политика, доверяющая нерелевантным рабочим нагрузкам, может позволить отравление кэша.

Tuist предоставляет доступ только для политик, чей собственный URL JWKS содержит ключ, которым подписан токен, после проверки эмитента, аудитории, срока действия, времени начала действия (с допустимым расхождением часов до 60 секунд) и каждого утверждения. Выданный часовой CI-токен действует для всего аккаунта, а не является снимком идентификаторов проектов: он включает проекты, созданные или переданные в аккаунт после выдачи. Авторизация проекта по-прежнему требует текущего владения аккаунтом, поэтому передача проекта из аккаунта удаляет его доступ по токену этого аккаунта.

#### Аутентификация рабочей нагрузки {#authenticate-a-workload}

1. Запросите токен идентичности у вашего провайдера с аудиторией политики.
2. Установите `TUIST_OIDC_TOKEN` в этот токен и `TUIST_OIDC_ACCOUNT` в хендл аккаунта Tuist, которому принадлежит проект. Аккаунт требуется для каждого обмена по политике доверия. Он только определяет место поиска и сам по себе ничего не предоставляет.
3. Выполните `tuist auth login`. Для проектов на Elixir вы можете использовать вместо этого `mix tuist.login` или позволить интеграции Elixir автоматически обменять токен, когда нет `TUIST_TOKEN` или действительных сохраненных учетных данных.

Полученный токен доступа Tuist имеет только группу областей видимости `ci` и охватывает все текущие и будущие проекты, принадлежащие выбранному аккаунту. Обмены завершаются ошибкой, если более 20 политик в аккаунте соответствуют одному и тому же токену или если они используют более двух разных URL JWKS.

Tuist не обновляет эти сессии. Токены доступа истекают через один час и не имеют токена обновления. Токены идентичности провайдера часто действительны всего несколько минут, поэтому хранение старого `TUIST_OIDC_TOKEN` не является стратегией обновления: для задач, выполняющихся дольше часа, запросите новый токен идентичности и войдите снова до истечения сессии Tuist. Удаление политики останавливает новые обмены, но уже выданные токены доступа остаются действительными до истечения их срока.

Tuist кэширует ключи подписи провайдера до 15 минут после успешной выборки в выделенном кэше с ограничением размера. Записи могут быть удалены раньше и загружены снова. Неудачные выборки не кэшируются. Если ваш провайдер меняет ключи, он должен опубликовать новый ключ в своем JWKS как минимум за 15 минут до подписания им токенов, потому что токены, подписанные ключом, которого нет в кэшированном наборе, отклоняются до истечения срока кэша. Токены без идентификатора ключа (`kid`) принимаются только тогда, когда JWKS содержит один подходящий ключ подписи. Если в JWKS присутствует идентификатор ключа, он должен быть строкой длиной не более 256 байт.

> [!NOTE]
> `TUIST_OIDC_TOKEN` — это общий ввод токена, а не способ обойти доверие сервера. Он имеет приоритет над обнаружением CI-провайдера, и сервер по-прежнему принимает только встроенные провайдеры и идентичности с соответствующей политикой доверия. Не помещайте токен идентичности в `TUIST_TOKEN`, который ожидает учетные данные Tuist.

Если обмен не удается, проверьте, что эмитент, аудитория и каждое утверждение в политике точно соответствуют токену, что URL JWKS предоставляет ключ, которым подписан токен, что политика не была удалена и что `TUIST_OIDC_ACCOUNT` указывает на аккаунт, которому принадлежит проект. Чтобы не раскрывать, какие идентичности доверены, Tuist возвращает одну и ту же ошибку для всех этих случаев.

### Fly.io Machines {#flyio-machines}

[Fly.io поддерживает OIDC-идентичность рабочих нагрузок](https://docs.fly.io/reference/openid-connect/). Машина может запросить краткосрочный подписанный токен идентичности из своего локального Unix-сокета `/.fly/api` без токена Fly API или долгосрочного секрета Tuist. Токены Fly идентифицируют организацию и приложение, а не исходный репозиторий, поэтому используйте политику доверия вместо подключения репозитория GitHub:

1. Получите эмитент (`iss`), идентификатор организации (`org_id`) и идентификатор приложения (`app_id`) из токена идентичности, выпущенного внутри вашей Fly Machine. Эмитент — `https://oidc.fly.io/<organization-slug>`. Используйте числовые идентификаторы, а не имена организации или приложения.
2. [Создайте политику доверия](#create-a-trust-policy), используя шаблон **Fly.io Machines**, и введите slug организации и оба числовых идентификатора. Он заполняет значения ниже и сохраняет идентификаторы как строки. Вы также можете ввести их вручную, используя **Пользовательский провайдер**; оставьте кавычки вокруг идентификаторов в утверждениях.

   | Поле | Значение |
   | --- | --- |
   | URL эмитента | `https://oidc.fly.io/<organization-slug>` |
   | URL JWKS | `https://oidc.fly.io/<organization-slug>/.well-known/jwks` |
   | Аудитория | `tuist` |
   | Утверждения | `{"org_id": "<organization-id>", "app_id": "<application-id>"}` |

3. Внутри машины установите `TUIST_OIDC_ACCOUNT` в хендл аккаунта Tuist, которому принадлежит проект (не slug организации Fly), запросите токен с аудиторией `tuist` и передайте его в `tuist auth login`, используя `TUIST_OIDC_TOKEN`:

```bash
set -euo pipefail
export TUIST_OIDC_ACCOUNT="my-tuist-account"

TUIST_OIDC_TOKEN="$(curl --fail --silent --show-error \
  --unix-socket /.fly/api \
  -X POST http://localhost/v1/tokens/oidc \
  -H 'Content-Type: application/json' \
  --data '{"aud":"tuist"}')"
export TUIST_OIDC_TOKEN

tuist auth login
unset TUIST_OIDC_TOKEN
```

Для первоначальной настройки вы можете локально проверить только поля идентичности после экспорта токена и до его сброса. Это декодирует утверждения для конфигурации; Tuist отдельно проверяет подпись во время аутентификации:

```bash
python3 - <<'PY'
import base64, json, os
payload = os.environ["TUIST_OIDC_TOKEN"].split(".")[1]
claims = json.loads(base64.urlsafe_b64decode(payload + "=" * (-len(payload) % 4)))
print(json.dumps({key: claims[key] for key in ("iss", "org_id", "app_id")}, indent=2))
PY
```

Не выводите и не фиксируйте сам токен. Каждая машина в авторизованном приложении Fly может аутентифицироваться ко всем текущим и будущим проектам в аккаунте Tuist. Создайте отдельную политику для каждого дополнительного приложения. Токены идентичности Fly истекают примерно через десять минут, поэтому на долго работающих машинах запросите новый токен и снова выполните `tuist auth login` до истечения одночасовой сессии Tuist.

### Области действия OIDC-токенов {#oidc-token-scopes}

OIDC-токенам предоставляется группа областей действия `ci`. Для GitHub Actions, CircleCI и Bitrise это обеспечивает доступ ко всем проектам, подключенным к репозиторию. Для политик доверия идентичности рабочих нагрузок это обеспечивает доступ ко всем текущим и будущим проектам, принадлежащим выбранному аккаунту, без предоставления прав на создание проектов, администрирование проектов, администрирование раннеров или администрирование участников аккаунта. См. [Группы областей действия](#scope-groups) для получения подробной информации о том, что включает область действия `ci`.

> [!TIP]
> **Преимущества безопасности**
>
> Аутентификация OIDC более безопасна, чем долгосрочные токены, потому что:
> - Нет секретов, которые нужно ротировать или управлять ими
> - Токены имеют короткий срок жизни
> - Аутентификация привязана к идентичности вашего репозитория или явно авторизованной идентичности рабочей нагрузки


## Аутентификация плагина Gradle {#gradle-plugin-authentication}

Плагин Gradle использует состояние аутентификации CLI Tuist и не определяет отдельный поток входа. Аутентифицируйтесь один раз через CLI, и плагин повторно использует эти учетные данные.

Для конфигурации проекта и сервера, включая `project` и `url`, используйте каноническую <.localized_link href="/references/tuist-toml">справку по tuist.toml</.localized_link>.

Для локального использования выполните:

```bash
tuist auth login
```

Для CI используйте либо:

- <.localized_link href="/guides/server/authentication#setting-up-oidc-authentication">OIDC-аутентификацию</.localized_link> (рекомендуется, если доступна)
- <.localized_link href="/guides/server/authentication#continuous-integration">Аутентификацию токеном аккаунта</.localized_link> через `TUIST_TOKEN`

Для самостоятельно размещаемых серверов Tuist определите URL сервера в `tuist.toml` (например, `url = "https://tuist.your-company.com"`) и выполните стандартный поток входа. URL разрешается из того же файла конфигурации, который используется плагином.

После настройки аутентификации выполняйте команды и задачи кэширования Gradle как обычно.

## Токены аккаунта {#account-tokens}

Для сред CI, которые не поддерживают OIDC, или когда вам нужен детальный контроль над разрешениями, вы можете использовать токены аккаунта. Токены аккаунта позволяют точно указать, к каким областям действия и проектам токен имеет доступ.

### Создание токена аккаунта {#creating-an-account-token}

Самый простой способ создать токен аккаунта — через дашборд:

1. Откройте организацию в дашборде Tuist.
2. Перейдите в **Настройки** > **Токены**.
3. Выберите **Сгенерировать токен**.
4. Выберите имя, необязательный срок действия, доступ к проектам и необходимые области действия для токена.
5. Скопируйте сгенерированное значение токена перед закрытием диалогового окна. Значения токенов отображаются только один раз.

Вы также можете создавать токены аккаунта из CLI, что полезно для скриптов или автоматизации:

```bash
tuist account tokens create account-handle \
  --scopes account:cache:write project:cache:read project:cache:write \
  --name ci-cache-token \
  --expires 1y
```

> [!IMPORTANT]
> Замените `account-handle` на хендл аккаунта, которому принадлежат проекты, к которым токен должен иметь доступ. Это может быть организационный аккаунт, а не обязательно ваш личный аккаунт.

Команда принимает следующие опции:

| Опция | Описание |
| --- | --- |
| `--scopes` | Обязательно. Список областей действия через запятую, которые нужно предоставить токену. |
| `--name` | Обязательно. Уникальный идентификатор для токена (1–32 символа, только буквенно-цифровые символы, дефисы и подчеркивания). |
| `--expires` | Необязательно. Когда токен должен истечь. Используйте формат, например `30d` (дни), `6m` (месяцы) или `1y` (годы). Если не указано, токен никогда не истекает. |
| `--projects` | Ограничить токен конкретными хендлами проектов. Если не указано, токен имеет доступ ко всем проектам. |

### Доступные области действия {#available-scopes}

| Область действия | Описание |
| --- | --- |
| `account:cache:read` | Скачивание кэшированных бинарных файлов с областью действия аккаунта |
| `account:cache:write` | Загрузка кэшированных бинарных файлов с областью действия аккаунта |
| `account:members:read` | Чтение участников аккаунта |
| `account:members:write` | Управление участниками аккаунта |
| `account:registry:read` | Чтение из реестра пакетов Swift |
| `account:registry:write` | Публикация в реестр пакетов Swift |
| `account:runners:read` | Чтение задач раннеров, рабочих процессов, профилей и томов |
| `account:runners:write` | Управление профилями раннеров и очистка томов раннеров |
| `project:previews:read` | Скачивание превью |
| `project:previews:write` | Загрузка превью |
| `project:admin:read` | Чтение проектов и их настроек |
| `project:admin:write` | Создание, обновление и удаление проектов. Для создания проекта требуется токен с доступом ко всем проектам |
| `project:cache:read` | Скачивание кэшированных бинарных файлов |
| `project:cache:write` | Загрузка кэшированных бинарных файлов |
| `project:bundles:read` | Просмотр бандлов |
| `project:bundles:write` | Загрузка бандлов |
| `project:tests:read` | Чтение результатов тестов |
| `project:tests:write` | Загрузка результатов тестов |
| `project:builds:read` | Чтение аналитики сборок |
| `project:builds:write` | Загрузка аналитики сборок |
| `project:runs:read` | Чтение запусков команд |
| `project:runs:write` | Создание и обновление запусков команд |

### Группы областей действия {#scope-groups}

Группы областей действия предоставляют удобный способ предоставить несколько связанных областей действия с помощью одного идентификатора. При использовании группы областей действия она автоматически раскрывается, включая все отдельные области действия, которые она содержит.

| Группа областей действия | Включенные области действия |
| --- | --- |
| `ci` | `account:cache:write`, `project:cache:write`, `project:previews:write`, `project:bundles:write`, `project:tests:write`, `project:builds:write`, `project:runs:write` |
| `mcp` | `project:cache:read`, `project:previews:read`, `project:bundles:read`, `project:tests:read`, `project:builds:read`, `project:runs:read` |

### Непрерывная интеграция {#continuous-integration}

Для сред CI, которые не поддерживают OIDC, создайте токен аккаунта с группой областей действия `ci`, чтобы аутентифицировать ваши рабочие процессы CI. В дашборде выберите пресет **CI** при генерации токена.

Вы также можете создать такой же токен из CLI:

```bash
tuist account tokens create account-handle --scopes ci --name ci
```

Это создает токен со всеми областями действия, необходимыми для типичных операций CI (кэш, превью, бандлы, тесты, сборки и запуски). Сохраните сгенерированный токен как секрет в вашей среде CI и установите его как переменную окружения `TUIST_TOKEN`.

### Управление токенами аккаунта {#managing-account-tokens}

Откройте **Настройки** > **Токены** в дашборде аккаунта, чтобы просмотреть токены аккаунта, проверить области действия и доступ к проектам токена, а также отозвать токены во время ротации.

Чтобы列出所有 токены для аккаунта:

```bash
tuist account tokens list account-handle
```

Чтобы отозвать токен по имени:

```bash
tuist account tokens revoke account-handle ci-cache-token
```

### Использование токенов аккаунта {#using-account-tokens}

Токены аккаунта должны быть определены как переменная окружения `TUIST_TOKEN`:

```bash
export TUIST_TOKEN=your-account-token
```

> [!TIP]
> **Когда использовать токены аккаунта**
>
> Используйте токены аккаунта, когда вам нужно:
> - Аутентификация в средах CI, которые не поддерживают OIDC
> - Тонкая настройка контроля над тем, какие операции может выполнять токен
> - Токен, который может получать доступ к нескольким проектам в рамках аккаунта
> - Токены с ограниченным сроком действия, которые автоматически истекают
