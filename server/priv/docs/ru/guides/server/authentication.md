# Аутентификация {#authentication}

Для взаимодействия с сервером CLI должен аутентифицировать запросы, используя [bearer-аутентификацию](https://swagger.io/docs/specification/authentication/bearer-authentication/). CLI поддерживает аутентификацию как пользователь, как аккаунт или с помощью токена OIDC.

## Как пользователь {#as-a-user}

При локальном использовании CLI на вашем компьютере мы рекомендуем аутентифицироваться как пользователь. Для аутентификации в качестве пользователя выполните следующую команду:

```bash
tuist auth login
```

Команда проведет вас через веб-процесс аутентификации. После успешной аутентификации CLI сохранит долгоживущий токен обновления и короткоживущий токен доступа в каталоге `~/.config/tuist/credentials`. Каждый файл в этом каталоге соответствует домену, для которого выполнена аутентификация; по умолчанию это `tuist.dev.json`. Данные в этом каталоге конфиденциальны, поэтому **обязательно обеспечьте их безопасность**.

CLI автоматически использует учетные данные при отправке запросов к серверу. Если токен доступа истек, CLI использует токен обновления для получения нового токена доступа.

> [!NOTE]
> Если ваша организация использует единый вход (SSO), выберите вариант корпоративного входа в браузере и введите свой рабочий адрес электронной почты. Tuist может найти провайдера на основе вашего существующего членства в организации или <.localized_link href="/guides/integrations/authentication/sso#verify-a-login-email-domain">подтвержденного домена электронной почты для входа</.localized_link>.

## Токены OIDC {#oidc-tokens}

Для сред непрерывной интеграции (CI), поддерживающих OpenID Connect (OIDC), Tuist может выполнять автоматическую аутентификацию без необходимости управлять долгоживущими секретами. При запуске в поддерживаемой среде CI CLI автоматически обнаруживает провайдера токенов OIDC и обменивает предоставленный CI токен на токен доступа Tuist.

### Поддерживаемые провайдеры {#supported-ci-providers}

Tuist распознает следующие провайдеры CI и сопоставляет их токены с проектами через подключение вашего репозитория:

- GitHub Actions
- CircleCI
- Bitrise

Орбы [Amp](#amp-orbs) аутентифицируются через рабочие пространства Amp, которые вы подключаете к своему аккаунту Tuist, а [сессии Claude Code](#claude-code-sessions) — через среды Claude Code, которые вы подключаете для запуска на Tuist Sandboxes.

Любой другой провайдер удостоверений, выпускающий токены OpenID Connect, может пройти аутентификацию через [политику доверия для рабочих нагрузок](#workload-identity-trust-policies), которую вы настраиваете один раз для всех текущих и будущих проектов в своем аккаунте, например [Fly.io Machines](#flyio-machines).

### Настройка аутентификации OIDC {#setting-up-oidc-authentication}

Для GitHub Actions, CircleCI и Bitrise:

1. **Подключите ваш репозиторий к Tuist**: следуйте <.localized_link href="/guides/integrations/gitforge/github">руководству по интеграции с GitHub</.localized_link>, чтобы подключить ваш репозиторий GitHub к проекту Tuist.

2. **Предоставьте токен удостоверения**: в GitHub Actions задайте для задачи `permissions: id-token: write`; в CircleCI и Bitrise включите OIDC для проекта. Начиная с Tuist 4.218.0, если CLI не выполнен вход и переменная `TUIST_TOKEN` не установлена, он определяет среду CI и обменивает токен удостоверения при первом запросе, поэтому шаг входа не требуется. В более ранних версиях сначала необходимо выполнить `tuist auth login`, и вы все еще можете запустить эту команду для явного входа и раннего завершения в случае отказа в обмене.

Смотрите <.localized_link href="/guides/integrations/continuous-integration">руководство по непрерывной интеграции</.localized_link> для примеров конфигурации для конкретных провайдеров.

### Орбы Amp {#amp-orbs}

Орбы [Amp](https://ampcode.com) могут выпускать токены OIDC, идентифицирующие их рабочее пространство Amp. Подключите рабочее пространство к своему аккаунту Tuist один раз, и CLI Tuist, а также задачи Mix `tuist_ex` в любом орбе этого рабочего пространства будут выполнять вход самостоятельно, без сохраненного токена или шага входа:

1. Найдите идентификаторы: в потоке рабочего пространства, который выполняется в орбе, выполните `echo $AMP_WORKSPACE_ID $AMP_PROJECT_ID`.
2. В своем аккаунте Tuist откройте **Settings → Integrations**, выберите **Connect workspace** на карточке Amp и вставьте идентификатор рабочего пространства. Чтобы разрешить доступ только орбам одного проекта Amp, также вставьте его идентификатор проекта. Вы должны быть администратором аккаунта или владельцем.
3. Используйте Tuist в орбах рабочего пространства. Если вход не выполнен, CLI или задача Mix обнаруживает орб, выпускает токен с помощью `amp orb id-token --audience https://tuist.dev` и обменивает его на сессию Tuist. `tuist auth login` и `mix tuist.login` выполняют тот же обмен явно.

Как и в конфигурациях доверия из [руководства по OIDC для Amp](https://ampcode.com/manual/orbs/oidc), Tuist проверяет подпись Amp на каждом токене и принимает его только если аудитория равна `https://tuist.dev`, параметр `token_use` равен `exchanged`, параметр `workspace_id` соответствует подключенному рабочему пространству, а для подключения, ограниченного проектом, параметр `project_id` соответствует этому проекту. Параметр `sub` должен указывать на то же рабочее пространство, а для подключения к проекту — на тот же проект, что и в этих утверждениях: `workspace:<workspace-id>:project:<project-id>:…`, которые `amp orb id-token` выпускает по умолчанию.

Каждый орб, допущенный подключением, получает доступ CI ко всем текущим и будущим проектам, принадлежащим аккаунту, включая загрузку в кэш. Он также получает область видимости `account:sandboxes:write`, что позволяет ему создавать <.localized_link href="/guides/features/sandboxes">песочницы</.localized_link> и выполнять в них команды как участник аккаунта, например, для сборки в песочнице macOS из орба Linux. Подключайте только те рабочие пространства, участникам которых вы доверяете такой доступ. Тщательно проверяйте идентификатор: Tuist не может подтвердить, что вы принадлежите к подключаемому рабочему пространству. Если рабочее пространство подключено к нескольким аккаунтам Tuist, орбы должны установить `TUIST_OIDC_ACCOUNT` для указания аккаунта, в который нужно войти; установка этой переменной в среде проекта Amp также закрепляет вход за вашим аккаунтом. Потоки вне рабочего пространства не имеют идентичности рабочего пространства и не могут использовать подключение. Отключите рабочее пространство на карточке Amp, чтобы прекратить новые входы; уже выданные сессии остаются действительными до истечения срока их действия через один час. Сессиям не нужен токен обновления: когда срок действия подходит к концу, CLI в орбе выпускает новый токен Amp и снова обменивает его, поэтому долго работающие орбы остаются авторизованными, пока рабочее пространство подключено.

Политики доверия для эмитента Amp, созданные вами до подключения рабочего пространства, продолжают работать, если вы установите `TUIST_OIDC_ACCOUNT`.

### Сессии Claude Code {#claude-code-sessions}

Каждая облачная сессия Claude Code в самохостинговой среде несет токен удостоверения, подписанный Anthropic (`CLAUDE_CODE_SESSION_ACCESS_TOKEN`). В средах, которые вы <.localized_link href="/guides/features/sandboxes/claude#claude-code">подключаете для запуска на Tuist Sandboxes</.localized_link>, Tuist передает его сессии как `TUIST_OIDC_TOKEN`, благодаря чему CLI Tuist и задачи Mix `tuist_ex` выполняют вход самостоятельно.

Tuist проверяет подпись Anthropic и принимает токен только в том случае, если это токен сессии (`ccr:role` равен `session_worker`), среда которого, указанная в аудитории, подключена к аккаунту Tuist и включена. Каждая сессия подключенной среды получает доступ CI ко всем текущим и будущим проектам, принадлежащим аккаунту, включая загрузку в кэш, и может создавать и использовать песочницы аккаунта, как участник аккаунта. Таким образом, любой пользователь вашей организации Claude, которому разрешено использовать среду, может публиковать данные в ваш кэш и запускать песочницы, например macOS-песочницу для сборки. Сессии Tuist для такой сессии истекают через один час или вместе с её токеном удостоверения — в зависимости от того, что наступит раньше; токен — это тот, с которым сессия началась, и по умолчанию он действует четыре часа, поэтому более длительная сессия теряет доступ к Tuist, пока следующее сообщение не возобновит его на новом раннере. Отключите или отключите среду, чтобы прекратить новые входы.

### Политики доверия для удостоверений рабочих нагрузок {#workload-identity-trust-policies}

Политика доверия позволяет рабочим нагрузкам от другого провайдера удостоверений, такого как платформа развертывания, кластер Kubernetes или самостоятельно управляемая система CI, получать доступ к проекту без долгоживущего секрета Tuist. Провайдер должен:

- Быть доступным по HTTPS по публичному адресу. Tuist не следует за перенаправлениями и не подключается к частным или внутренним сетевым адресам, в том числе с самохостинговых серверов Tuist.
- Выпускать JWT, подписанные асимметричным ключом, например `RS256` или `ES256`. Токены без подписи и токены, подписанные общим секретом (`HS256` и аналогичные), отклоняются.
- Публиковать свои ключи подписи в виде набора JSON Web Key Set (JWKS) по фиксированному HTTPS-URL. Ответ должен быть не более 64 КиБ и содержать не более 20 ключей.
- Включать срок действия (`exp`) в каждый токен.

Эмитенты GitHub Actions, CircleCI и Bitrise зарезервированы для описанного выше потока на основе репозитория и не могут использоваться в политике доверия.

> [!NOTE]
> Для развертывания на самохостинге примените миграции базы данных и обновите каждую обслуживающую реплику сервера Tuist перед настройкой удостоверений рабочих нагрузок или переносом на них задач. Затем обновите CLI или интеграцию с Elixir до версии, поддерживающей `TUIST_OIDC_TOKEN` и `TUIST_OIDC_ACCOUNT`. Существующие задачи GitHub Actions, CircleCI и Bitrise продолжают использовать авторизацию на основе репозитория и не требуют хендла аккаунта. Перед переключением продакшен-задач проверьте обмен короткоживущим токеном и операцию с кэшем для предполагаемой рабочей нагрузки. Чтобы остановить новые обмены, удалите политику; подождите до одного часа, чтобы уже выданные токены доступа Tuist истекли. Удаление политики не отзывает эти токены немедленно.

#### Создать политику {#create-a-trust-policy}

В дашборде Tuist откройте **Настройки** вашего аккаунта > **Аутентификация** и найдите раздел **Удостоверения рабочих нагрузок**. Вы должны быть администратором аккаунта (или владельцем личного аккаунта). Каждый аккаунт может иметь до 20 политик. Настройте удостоверение один раз для доступа CI ко всему аккаунту; выбор проекта не требуется.

Используйте переключатель рядом с **Удостоверения рабочих нагрузок**, чтобы открыть форму политики. Переключатель изначально включен, если в аккаунте есть сохраненные удостоверения, и остается включенным после сохранения. Для аккаунтов без удостоверений он изначально выключен. Раздел отображается ниже **Подготовки SCIM** для организаций. Скрытие формы сохраняет ваш черновик и не отключает аутентификацию рабочих нагрузок: карточки сохраненных удостоверений и ссылка на документацию по настройке остаются видимыми. Каждая карточка показывает имя удостоверения, URL эмитента и JWKS, аудиторию, точные JSON-утверждения, область действия на уровне аккаунта и время создания. Удалите удостоверение, используя действие на его карточке.

Выберите **Пользовательский провайдер**, чтобы ввести поля ниже, или **Fly.io Machines**, чтобы сгенерировать их из слага вашей организации и числовых идентификаторов организации и приложения. Шаблон Fly оставляет сгенерированный эмитент, URL JWKS и утверждения редактируемыми в разделе **Расширенная конфигурация**. Изменение шаблонов или вспомогательных значений сохраняет поля, которые вы отредактировали вручную. Если ваш эмитент, URL JWKS или утверждения переопределяют шаблон, Tuist раскрывает **Расширенная конфигурация** и показывает предупреждение, чтобы вы могли проверить политику, которая будет сохранена. Вернитесь к **Пользовательскому провайдеру**, чтобы продолжить без помощников Fly. Шаблоны только заполняют конфигурацию и не меняют способ проверки токенов в Tuist.

| Поле | Описание |
| --- | --- |
| Имя | Метка для распознавания политики, уникальная в пределах аккаунта. |
| URL эмитента | Утверждение `iss` токена. Оно должно совпадать точно, включая любой завершающий слеш. |
| URL JWKS | HTTPS-URL ключей подписи провайдера. Tuist использует этот URL напрямую и не читает документ обнаружения OpenID Connect провайдера, поэтому скопируйте `jwks_uri` из документации провайдера или из `<issuer>/.well-known/openid-configuration`. |
| Аудитория | Аудитория, для которой должен быть выпущен токен, по умолчанию `tuist`. Утверждение `aud` токена должно равняться ей или, если `aud` является списком, содержать её. Используйте значение, которое принимает только Tuist, чтобы токены, выпущенные для других сервисов, нельзя было повторно использовать здесь. |
| Утверждения | JSON-объект с 1–10 утверждениями, которые должен содержать токен, например `{"sub": "system:serviceaccount:ci:builder"}`. Ввод JSON ограничен 8 КиБ. Значения должны быть строками, знаковыми 64-битными целыми числами или булевыми значениями, и они должны совпадать точно, включая их тип: `"123"` не совпадает с `123`. Вложенные объекты, списки и утверждения времени или токена, такие как `iss`, `aud`, `exp`, `nbf`, `iat` и `jti`, не допускаются. |

Каждая политика предоставляет доступ CI к **всем текущим и будущим проектам, принадлежащим аккаунту**, без выбора отдельных проектов. Вы можете настроить удостоверение до создания первого проекта. Это не дает прав администрирования аккаунта или доступа к другому аккаунту.

Любая рабочая нагрузка, которая может получить токен с совпадающими утверждениями, получает доступ ко всем этим проектам, поэтому выбирайте утверждения, которые гарантируются провайдером и которые никто не может повторно использовать. Предпочитайте стабильные числовые идентификаторы именам, которые можно переименовать или зарегистрировать заново после удаления.

> [!WARNING]
> При использовании общего провайдера удостоверений привяжите политику к вашей организации или арендатору **и** к целевому приложению, проекту или сервисному аккаунту. Имя ветки, например `main`, среда, например `production`, или общая роль сами по себе не являются границей удостоверения: другой арендатор может получить токен с теми же значениями. Например, политика GitLab.com должна включать стабильный `project_id` целевого проекта, а не только `ref`. Соответствующий токен предоставляет доступ CI ко всему аккаунту, включая запись в кэш, поэтому политика, доверяющая нерелевантным рабочим нагрузкам, может допустить отравление кэша.

Tuist предоставляет доступ только для тех политик, чей собственный URL JWKS содержит ключ, подписавший токен, после проверки эмитента, аудитории, срока действия, времени начала действия (с допустимым расхождением часов до 60 секунд) и каждого утверждения. Выданный часовой токен CI действует для всего аккаунта, а не является снимком идентификаторов проектов: он включает проекты, созданные или переданные в аккаунт после выдачи. Авторизация проекта по-прежнему требует текущего владения аккаунтом, поэтому передача проекта из аккаунта лишает его доступа по токену этого аккаунта.

#### Аутентификация рабочей нагрузки {#authenticate-a-workload}

1. Запросите токен удостоверения у вашего провайдера с аудиторией политики.
2. Установите `TUIST_OIDC_TOKEN` равным этому токену, а `TUIST_OIDC_ACCOUNT` — хэндлу аккаунта Tuist, которому принадлежит проект. Аккаунт требуется для каждого обмена по политике доверия. Он лишь определяет место поиска и сам по себе ничего не предоставляет.
3. Запустите Tuist. Если отсутствуют `TUIST_TOKEN` или действительные сохраненные учетные данные, CLI и интеграция Elixir автоматически обменивают токен. `tuist auth login` и `mix tuist.login` выполняют тот же обмен явно.

Полученный токен доступа Tuist имеет только группу областей видимости `ci` и охватывает все текущие и будущие проекты, принадлежащие выбранному аккаунту. Обмен завершается ошибкой, если более 20 политик в аккаунте соответствуют одному и тому же токену или если они используют более двух разных URL JWKS.

Tuist не обновляет эти сессии. Токены доступа истекают через один час и не имеют токена обновления. Токены удостоверений провайдера часто действительны всего несколько минут, поэтому хранение старого `TUIST_OIDC_TOKEN` не является стратегией обновления: для задач, выполняющихся дольше часа, запросите новый токен удостоверения и войдите снова до истечения часовой сессии Tuist. Удаление политики прекращает новые обмены, но уже выданные токены доступа остаются действительными до истечения их срока.

Tuist кэширует ключи подписи провайдера на срок до 15 минут после успешной выборки в выделенном кэше с ограничением размера. Записи могут быть удалены раньше и запрошены заново. Неудачные выборки не кэшируются. Если ваш провайдер ротирует ключи, он должен опубликовать новый ключ в своем JWKS как минимум за 15 минут до подписания им токенов, поскольку токены, подписанные ключом, отсутствующим в кэшированном наборе, будут отклоняться до истечения срока кэша. Токены без идентификатора ключа (`kid`) принимаются только тогда, когда JWKS содержит единственный допустимый ключ подписи. Если в JWKS присутствует идентификатор ключа, он должен быть строкой длиной не более 256 байт.

> [!NOTE]
> `TUIST_OIDC_TOKEN` — это общий ввод токена, а не способ обойти доверие сервера. Он имеет приоритет над обнаружением провайдера CI, и сервер по-прежнему принимает только встроенных провайдеров и удостоверения с соответствующей политикой доверия. Не помещайте токен удостоверения в `TUIST_TOKEN`, который ожидает учетные данные Tuist.

Если обмен не удается, проверьте, что эмитент, аудитория и каждое утверждение в политике точно соответствуют токену, что URL JWKS предоставляет ключ, подписавший токен, что политика не была удалена и что `TUIST_OIDC_ACCOUNT` указывает на аккаунт, которому принадлежит проект. Чтобы не раскрывать, какие удостоверения доверены, Tuist возвращает одну и ту же ошибку для всех этих случаев.

### Машины Fly.io {#flyio-machines}

[Fly.io поддерживает удостоверения рабочих нагрузок OIDC](https://docs.fly.io/reference/openid-connect/). Машина может запросить краткосрочный подписанный токен удостоверения через свой локальный Unix-сокет `/.fly/api`, без токена Fly API или долгосрочного секрета Tuist. Токены Fly идентифицируют организацию и приложение, а не исходный репозиторий, поэтому используйте политику доверия вместо подключения репозитория GitHub:

1. Получите эмитента (`iss`), идентификатор организации (`org_id`) и идентификатор приложения (`app_id`) из токена удостоверения, выданного внутри вашей машины Fly. Эмитент — это `https://oidc.fly.io/<organization-slug>`. Используйте числовые идентификаторы, а не имена организации или приложения.
2. [Создайте политику доверия](#create-a-trust-policy), используя шаблон **Fly.io Machines**, и введите slug организации и оба числовых идентификатора. Это заполнит значения ниже и сохранит идентификаторы как строки. Вы также можете ввести их вручную, используя **Custom provider**; оставьте кавычки вокруг идентификаторов в утверждениях.

   | Поле | Значение |
   | --- | --- |
   | URL эмитента | `https://oidc.fly.io/<organization-slug>` |
   | URL JWKS | `https://oidc.fly.io/<organization-slug>/.well-known/jwks` |
   | Аудитория | `tuist` |
   | Утверждения | `{"org_id": "<organization-id>", "app_id": "<application-id>"}` |

3. Внутри машины установите `TUIST_OIDC_ACCOUNT` равным хэндлу аккаунта Tuist, которому принадлежит проект (не slug организации Fly), запросите токен с аудиторией `tuist` и передайте его в `tuist auth login`, используя `TUIST_OIDC_TOKEN`:

```bash
set -euo pipefail
export TUIST_OIDC_ACCOUNT="my-tuist-account"

TUIST_OIDC_TOKEN="$(curl --fail --silent --show-error \
  --unix-socket /.fly/api \
  -X POST http://localhost/v1/tokens/oidc \
  -H 'Content-Type: application/json' \
  --data '{"aud":"tuist"}')"
export TUIST_OIDC_TOKEN

tuist auth login
unset TUIST_OIDC_TOKEN
```

Для первоначальной настройки вы можете локально проверить только поля удостоверения после экспорта токена и до его сброса. Это декодирует утверждения для конфигурации; Tuist отдельно проверяет подпись во время аутентификации:

```bash
python3 - <<'PY'
import base64, json, os
payload = os.environ["TUIST_OIDC_TOKEN"].split(".")[1]
claims = json.loads(base64.urlsafe_b64decode(payload + "=" * (-len(payload) % 4)))
print(json.dumps({key: claims[key] for key in ("iss", "org_id", "app_id")}, indent=2))
PY
```

Не выводите и не фиксируйте в репозитории сам токен. Каждая машина в авторизованном приложении Fly может аутентифицироваться ко всем текущим и будущим проектам в аккаунте Tuist. Создайте отдельную политику для каждого дополнительного приложения. Токены удостоверений Fly истекают примерно через десять минут, поэтому на долго работающих машинах запросите новый токен и снова выполните `tuist auth login` до истечения часовой сессии Tuist.

### Области видимости токенов OIDC {#oidc-token-scopes}

Токенам OIDC предоставляется группа областей видимости `ci`. Для GitHub Actions, CircleCI и Bitrise это обеспечивает доступ ко всем проектам, подключенным к репозиторию. Для подключенных рабочих пространств Amp, подключенных сред Claude Code и политик доверия удостоверений рабочих нагрузок это обеспечивает доступ ко всем текущим и будущим проектам, принадлежащим выбранному аккаунту, без предоставления прав на создание проектов, администрирование проектов, администрирование раннеров или администрирование участников аккаунта. Подробнее о том, что включает область видимости `ci`, см. в разделе [Группы областей видимости](#scope-groups).

> [!TIP]
> **Преимущества безопасности**
>
> Аутентификация OIDC безопаснее долгосрочных токенов, потому что:
> - Нет секретов, которые нужно ротировать или управлять ими
> - Токены краткосрочные
> - Аутентификация привязана к идентичности вашего репозитория или явно авторизованному удостоверению рабочей нагрузки


## Аутентификация плагина Gradle {#gradle-plugin-authentication}

Плагин Gradle использует состояние аутентификации Tuist CLI и не определяет отдельный процесс входа. Выполните аутентификацию один раз через CLI, и плагин будет использовать эти учетные данные.

Для настройки проекта и сервера, включая `project` и `url`, используйте каноническую <.localized_link href="/references/tuist-toml">справку по tuist.toml</.localized_link>.

Для локального использования выполните:

```bash
tuist auth login
```

Для CI используйте один из вариантов:

- <.localized_link href="/guides/server/authentication#setting-up-oidc-authentication">Аутентификация OIDC</.localized_link> (рекомендуется, если доступна)
- <.localized_link href="/guides/server/authentication#continuous-integration">Аутентификация токеном аккаунта</.localized_link> через `TUIST_TOKEN`

Для самостоятельно размещаемых серверов Tuist укажите URL сервера в `tuist.toml` (например, `url = "https://tuist.your-company.com"`) и выполните стандартный процесс входа. URL разрешается из того же файла конфигурации, который используется плагином.

После настройки аутентификации выполняйте команды и задачи кэширования Gradle в обычном режиме.

## Токены аккаунта {#account-tokens}

Для сред CI, которые не поддерживают OIDC, или когда требуется точный контроль над разрешениями, можно использовать токены аккаунта. Токены аккаунта позволяют точно указать, к каким областям видимости и проектам токен имеет доступ.

### Создание токена аккаунта {#creating-an-account-token}

Самый простой способ создать токен аккаунта — через панель управления:

1. Откройте организацию в панели управления Tuist.
2. Перейдите в **Настройки** > **Токены**.
3. Выберите **Сгенерировать токен**.
4. Укажите имя, необязательный срок действия, доступ к проектам и необходимые области видимости для токена.
5. Скопируйте сгенерированное значение токена перед закрытием диалога. Значения токенов отображаются только один раз.

Вы также можете создавать токены аккаунта через CLI, что удобно для скриптов и автоматизации:

```bash
tuist account tokens create account-handle \
  --scopes account:cache:write project:cache:read project:cache:write \
  --name ci-cache-token \
  --expires 1y
```

> [!IMPORTANT]
> Замените `account-handle` на идентификатор аккаунта, которому принадлежат проекты, к которым должен иметь доступ токен. Это может быть аккаунт организации, а не обязательно ваш личный аккаунт.

Команда принимает следующие параметры:

| Параметр | Описание |
| --- | --- |
| `--scopes` | Обязательно. Список областей видимости для токена, разделенный пробелами. |
| `--name` | Обязательно. Уникальный идентификатор токена (1–32 символа, только буквенно-цифровые символы, дефисы и подчеркивания). |
| `--expires` | Необязательно. Срок истечения токена. Используйте формат, например `30d` (дни), `6m` (месяцы) или `1y` (годы). Если не указано, токен не истекает. |
| `--projects` | Ограничивает токен конкретными идентификаторами проектов. Если не указано, токен имеет доступ ко всем проектам. |

### Доступные области видимости {#available-scopes}

| Область видимости | Описание |
| --- | --- |
| `account:cache:read` | Скачивание кэшированных бинарных файлов уровня аккаунта |
| `account:cache:write` | Загрузка кэшированных бинарных файлов уровня аккаунта |
| `account:members:read` | Чтение участников аккаунта |
| `account:members:write` | Управление участниками аккаунта |
| `account:registry:read` | Чтение из реестра пакетов Swift |
| `account:registry:write` | Публикация в реестре пакетов Swift |
| `account:runners:read` | Чтение заданий раннеров, рабочих процессов, профилей и томов |
| `account:runners:write` | Управление профилями раннеров и удаление томов раннеров |
| `account:sandboxes:write` | Создание песочниц и выполнение команд в них, как участник аккаунта |
| `project:previews:read` | Скачивание превью |
| `project:previews:write` | Загрузка превью |
| `project:admin:read` | Чтение проектов и их настроек |
| `project:admin:write` | Создание, обновление и удаление проектов. Для создания проекта требуется токен с доступом ко всем проектам |
| `project:cache:read` | Скачивание кэшированных бинарных файлов |
| `project:cache:write` | Загрузка кэшированных бинарных файлов |
| `project:bundles:read` | Просмотр бандлов |
| `project:bundles:write` | Загрузка бандлов |
| `project:tests:read` | Чтение результатов тестов |
| `project:tests:write` | Загрузка результатов тестов |
| `project:builds:read` | Чтение аналитики сборок |
| `project:builds:write` | Загрузка аналитики сборок |
| `project:runs:read` | Чтение запусков команд |
| `project:runs:write` | Создание и обновление запусков команд |

### Группы областей видимости {#scope-groups}

Группы областей видимости предоставляют удобный способ предоставления нескольких связанных областей одним идентификатором. При использовании группы областей она автоматически раскрывается, включая все отдельные области, которые в неё входят.

| Группа областей видимости | Включенные области видимости |
| --- | --- |
| `ci` | `account:cache:write`, `project:cache:write`, `project:previews:write`, `project:bundles:write`, `project:tests:write`, `project:builds:write`, `project:runs:write` |
| `mcp` | `project:cache:read`, `project:previews:read`, `project:bundles:read`, `project:tests:read`, `project:builds:read`, `project:runs:read` |

### Непрерывная интеграция {#continuous-integration}

Для сред CI, не поддерживающих OIDC, создайте токен аккаунта с группой областей видимости `ci`, чтобы аутентифицировать ваши рабочие процессы CI. В дашборде выберите пресет **CI** при генерации токена.

Вы также можете создать такой же токен через CLI:

```bash
tuist account tokens create account-handle --scopes ci --name ci
```

Это создаст токен со всеми областями видимости, необходимыми для типичных операций CI (кэш, превью, бандлы, тесты, сборки и запуски). Сохраните сгенерированный токен как секрет в вашей среде CI и установите его как переменную окружения `TUIST_TOKEN`.

### Управление токенами аккаунта {#managing-account-tokens}

Откройте **Настройки** > **Токены** в дашборде аккаунта, чтобы просмотреть токены аккаунта, проверить области видимости и доступ к проектам токена, а также отозвать токены при ротации.

Чтобы вывести список всех токенов для аккаунта:

```bash
tuist account tokens list account-handle
```

Чтобы отозвать токен по имени:

```bash
tuist account tokens revoke account-handle ci-cache-token
```

### Использование токенов аккаунта {#using-account-tokens}

Токены аккаунта должны быть определены как переменная окружения `TUIST_TOKEN`:

```bash
export TUIST_TOKEN=your-account-token
```

> [!TIP]
> **Когда использовать токены аккаунта**
>
> Используйте токены аккаунта, когда вам нужно:
> - Аутентификация в средах CI, не поддерживающих OIDC
> - Детальный контроль над операциями, которые может выполнять токен
> - Токен, который может получать доступ к нескольким проектам в рамках аккаунта
> - Ограниченные по времени токены, которые автоматически истекают
