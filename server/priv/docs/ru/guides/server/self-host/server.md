# Сервер {#server}

Мы предлагаем версию сервера Tuist для самостоятельного размещения в организациях, которым требуется больший контроль над инфраструктурой. Эта версия позволяет разместить Tuist на собственной инфраструктуре, обеспечивая безопасность и конфиденциальность ваших данных.

> [!WARNING]
> **Требуется лицензия**
>
> Для самостоятельного размещения Tuist необходима юридически действительная платная лицензия. Версия для локального развертывания доступна только для организаций с планом Enterprise. Если вас интересует эта версия, свяжитесь с нами по адресу [contact@tuist.dev](mailto:contact@tuist.dev).

> [!WARNING]
> **Устаревший сервис кэширования**
>
> Старая технология узлов кэша для самостоятельного размещения устарела для новых установок. Используйте <.localized_link href="/guides/features/cache/self-hosting">руководство по самостоятельному размещению кэша</.localized_link> для актуальной инфраструктуры кэша.
>
> Существующие развертывания могут по-прежнему обращаться к устаревшей исходной документации в просмотрщике Markdown на GitHub: [узлы кэша](https://github.com/tuist/tuist/blob/main/server/priv/docs/en/guides/cache/self-host.md) и [архитектура кэша](https://github.com/tuist/tuist/blob/main/server/priv/docs/en/guides/cache/architecture.md).

## Частота выпусков {#release-cadence}

Сервер Tuist и сервер кэша Kura поставляются через три канала образов GHCR: **canary** (каждый коммит в `main`), **release candidate** (формируется каждый понедельник, тестируется неделю) и **stable** (продвигается в следующий понедельник). Только стабильные релизы обновляют `:latest` и разрешаются по умолчанию; canary и release candidate — это предварительные релизы GitHub, которые вы выбираете, фиксируя их тег. Сервер и Kura следуют одному еженедельному графику, синхронно с <.localized_link href="/cli/release/channels">графиком выпусков CLI Tuist</.localized_link>.

Мы придерживаемся [семантического версионирования](https://semver.org/), чтобы обеспечить предсказуемость версий и совместимость. Старшая версия используется для обозначения критических изменений в сервере Tuist, требующих координации с пользователями самостоятельного размещения; мы не планируем часто её использовать, а в случае необходимости поможем сделать переход максимально плавным.

На странице <.localized_link href="/guides/server/self-host/release/channels">Каналы выпусков</.localized_link> описано, как формируется каждый канал, как зафиксировать его в вашем развертывании и какая стратегия рекомендуется для поддержания продакшена на стабильной ветке, пока стендовое окружение тестирует предстоящий релиз.

## Обновление браузерных сессий {#browser-session-upgrade}

Браузерные сессии истекают через семь дней без аутентифицированных запросов к страницам или взаимодействия с LiveView, но не позднее чем через 30 дней после аутентификации. Функция «Запомнить меня» восстанавливает ту же серверную сессию и не продлевает ни один из сроков. Активность фиксируется раз в минуту, поэтому неактивная сессия может истечь на 59 секунд раньше. Heartbeat WebSocket, автоматические переподключения и фоновые обновления не возобновляют активность. Эти сроки не влияют на учетные данные машин или время жизни API-токенов.

Выполните аддитивную миграцию `users_tokens` перед запуском обновленных процессов приложения. Существующие строки не заполняются обратно: время их создания ограничивает период неактивности и абсолютный срок действия, и перед доступом к организации с принудительным SSO требуется повторная аутентификация. Провайдер обратного вызова, эмитент или проверенное Workspace, а также пользовательское подключение SSO хранятся на стороне сервера и сравниваются с текущими настройками организации. Привязанный аккаунт не является доказательством аутентификации сессии.

Обновите каждую веб-реплику, обслуживающую трафик, прежде чем считать политику примененной. Старые бинарные файлы всё ещё могут принимать прежние 60-дневные сессии и не применяют новые границы LiveView; смешанные версии совместимы по схеме, но не эквивалентны по политике. Ожидайте, что пользователям потребуется войти снова. Откат к старым бинарным файлам ослабляет эти ограничения; если необходим откат схемы, остановите все бинарные файлы, читающие новые поля, перед их удалением. Никогда не продлевайте старые сессии и не делайте выводов об источнике, чтобы избежать повторной аутентификации.

## MFA через приложение-аутентификатор {#authenticator-app-mfa}

Сервер включает встроенную двухфакторную аутентификацию через приложение-аутентификатор (TOTP). В дашборде пока нет ссылки на неё; точка входа в настройки появится в более позднем релизе. Не требуется флаг активации, зависимость от хостингового сервиса или учетные данные провайдера идентификации: нужны только PostgreSQL, миграция ниже, TOTP-аутентификатор и стабильный ключ шифрования, общий для всех обслуживающих реплик (`TUIST_SECRET_KEY_ENCRYPTION`, с резервом на `TUIST_SECRET_KEY_BASE`). Синхронизируйте часы сервера и аутентификатора. Проверка MFA и общий лимит из пяти неверных кодов за пять минут используют блокировки строк PostgreSQL, а не Redis.

Для настройки требуется вход в систему в течение последних пяти минут, ввод ключа настройки в приложение TOTP-аутентификатора и подтверждение сгенерированного приложением кода. Десять одноразовых кодов восстановления показываются один раз; сохраните их в безопасном месте. Для отключения фактора также требуется недавний вход и неиспользованный аутентификатор или код восстановления. Изменение фактора аннулирует другие браузерные сессии. Сброс пароля не удаляет MFA, и эта реализация не предоставляет обхода только по электронной почте или через администратора при потере фактора.

После регистрации каждый новый вход через браузер, включая федеративный вход, требует использования встроенного второго фактора перед получением сессии или завершением авторизации CLI/устройства через браузер. Прямой вход по паролю и через Apple API отказывает зарегистрированным пользователям и предлагает использовать вход через браузер. Новые утверждения почтового агента для зарегистрированных пользователей требуют браузерной сессии, прошедшей проверку MFA; устаревшие утверждения только по почтовому ящику отклоняются. Существующие API-токены, учетные данные машин, идентификаторы рабочих нагрузок и правила их обновления остаются без изменений. Это опциональная поддержка для каждого пользователя, а не обязательное требование MFA для всей организации и не проверка политики MFA самого провайдера идентификации. Для SSO организации по-прежнему требуется правильный настроенный провайдер/эмитент в дополнение к встроенному фактору.

Электронная почта не требуется для регистрации, входа, использования кодов восстановления или отключения MFA. Уведомления об изменении фактора отправляются по возможности; ошибка доставки не отменяет выполненное изменение.

Выполните отдельную аддитивную миграцию `user_mfa`/`users_tokens.mfa_verified_at` перед запуском нового бинарного файла. Секрет TOTP использует существующий ключ шифрования Vault; сохраните этот ключ и его резервные копии. Завершите обновление **всех реплик, обслуживающих аутентификацию, прежде чем разрешать регистрацию MFA**. Старые бинарные файлы могут обходить встроенную MFA, поэтому они не являются совместимой с политикой целью для отката после регистрации. Удаление схемы MFA уничтожает состояние регистрации и восстановления; сначала остановите процессы чтения и сохраните зашифрованную резервную копию. Совместимость схем смешанных версий не является доказательством того, что применяются элементы управления MFA или браузерными сессиями.

## Граница обновления и отката OAuth {#oauth-upgrade-and-rollback-boundary}

Удаление кэша сущностей OAuth требует поэтапного обновления для существующих установок. Перед развертыванием версии, которая прекращает инвалидацию кэша OAuth, сначала разверните релиз совместимости с авторитетным чтением из [#14040](https://github.com/tuist/tuist/pull/14040) на **каждый читатель и писатель OAuth**. Этот этап совместимости впервые появляется в линии релизов **1.355**: `ghcr.io/tuist/tuist:1.355.0-rc.1` содержит его; для производственных развертываний следует использовать стабильный релиз `1.355.x` после его продвижения. Установки версии 1.354 или более ранние должны завершить этот этап перед обновлением до более позднего релиза, содержащего удаление. Сохраняйте линию 1.355 только для совместимости: не портируйте обратно удаление инвалидации в нее.

Оригинальный коммит совместимости также доступен как `ghcr.io/tuist/tuist:sha-c8e54471a425`. Другой образ подходит в качестве этапа совместимости только если он сохраняет авторитетное чтение **и сохраняет устаревшие инвалидации**, пока остаются старые потребители. Выполните обычные миграции базы данных для этого этапа перед обработкой трафика, включая индекс поиска токенов обновления.

Проверьте все веб-реплики, фоновые воркеры, запланированные задачи и отдельно закрепленные образы процессоров в каждой среде. Дождитесь завершения rollout совместимости и убедитесь, что не осталось бинарных файлов, читающих кэш, перед удалением инвалидаций. Не допускайте, чтобы плавающий тег образа пропустил этот этап во время автоматического обновления. Свежие установки без старых потребителей не требуют промежуточного развертывания.

> [!WARNING]
> **Сохраняйте цель отката с авторитетным чтением**
>
> После удаления инвалидаций обычный rolling rollback должен быть направлен на #14040 или другую версию с авторитетным чтением. Сохраненные записи кэша OAuth могут быть устаревшими даже после остановки всех процессов без инвалидации, и перезапущенная реплика, читающая кэш, может импортировать их от пиров.
>
> Дальнейший откат требует остановки и дренажа **всех** потребителей OAuth без инвалидации, затем очистки или замены **каждого** сохраненного участника кэша Boruta перед запуском любого потребителя, читающего кэш. Предотвратите повторное подключение сохраненных участников. Дренаж только входящего трафика или перезапуск только веб-реплик недостаточны; согласуйте это восстановление с вашей контактной службой поддержки Tuist, а не очищайте кэши или автоматически откатывайте миграции базы данных.

## Кластеризация нескольких реплик {#multi-replica-clustering}

Поддерживаемые веб-развертывания с несколькими репликами требуют кластеризации Erlang для межрепликовых уведомлений Phoenix PubSub и Oban PG, а не как органа для аутентификации. Chart отвергает несколько реплик, включая автоскейлер, который может расти beyond одной реплики, когда `server.cluster.enabled` имеет значение false. Ранее принятые некластеризованные развертывания должны планировать это обновление, а не обходить защиту. Завершите <.localized_link href="/guides/server/self-host/server#oauth-upgrade-and-rollback-boundary">последовательность обновления OAuth</.localized_link>, включая удаление инвалидаций, перед изменением членства.

Создайте приватный Secret cookie в namespace релиза, используя ваш менеджер секретов, затем настройте его имя и ключ:

```yaml
server:
  replicaCount: 2
  cluster:
    enabled: true
    distributionPort: 9100
    cookieExistingSecret: tuist-server-cluster
    cookieExistingSecretKey: release-cookie
```

Cookie должно иметь высокую энтропию и использоваться всеми участвующими веб-репликами. Никогда не используйте cookie, встроенный в опубликованный образ: владение cookie распределения предоставляет удаленное выполнение на его узлах. Запуск распределенного релиза теперь отказывает при отсутствии приватного `RELEASE_COOKIE` или неверном порте, включая явно настроенные `RELEASE_DISTRIBUTION=name` или `sname` без обнаружения DNS. Развертывания вне chart также должны последовательно настраивать `TUIST_CLUSTER_DNS_SERVICE`, `TUIST_CLUSTER_APP_NAME` и IP пода/имя узла. Обнаружение в настоящее время использует записи A IPv4.

При обычном `helm upgrade`, подключенном к серверу, оставление `cookieExistingSecret` пустым создает Secret cookie и повторно использует его текущее значение при последующих обновлениях. Офлайн `helm template`, Argo CD и другие рендереры GitOps без поиска live Secret не могут сохранить это сгенерированное значение; они должны использовать `cookieExistingSecret`, поддерживаемый отдельно управляемым, стабильным Secret. Не меняйте ключ cookie для неявного ротации работающего кластера. Ротация cookie требует скоординированной миграции/перезапуска каждого участника; обновление только Secret не обновляет существующие процессы.

Первый rollout из cookie, запеченных в образе, формирует отдельные острова членства старых/новых версий, пока все веб-реплики не начнут использовать приватный Secret. Запланируйте окно миграции для обновлений в реальном времени. Последующие rolling deployments формируют кластеры смешанных версий, поэтому учитывайте уведомления PubSub, Oban и замену пиров across фактических старых/новых версий. Эти уведомления не являются гарантиями надежной доставки. Сохраняйте образ отката с авторитетным чтением и сохраняйте тот же приватный cookie при откате совместимой версии.

Разрешите EPMD (TCP 4369) и настроенный порт распределения только между доверенными пирами сервера, никогда от рабочих нагрузок арендаторов или публичной сети. Проверьте фактическую изоляцию ingress/egress в вашей среде; рендеринг NetworkPolicy не доказывает принудительное применение или доступность бэкенда. Canary с двумя репликами под непрерывной нагрузкой должен пройти присоединение, rolling replacement и сбой/восстановление перед продвижением. DNS используется для обнаружения пиров, а не для отключения здоровых узлов при временном сбое или частичном ответе; реальная потеря узлов и предотвращение разделения OTP все еще применяются. libcluster может все еще логировать успешную операцию "отключено" для callback сохранения без закрытия соединения; устанавливайте фактическое членство по событиям node-up/down или `Node.list()`, а не только по этой строке лога.

## Непрерывное развертывание {#continuous-deployment}

Мы рекомендуем закреплять production-окружение на стабильной минорной ветке (например, `ghcr.io/tuist/tuist:1.351`), чтобы ежедневные обновления включали только исправления, перенесенные из других веток. Стабильные ветки выпускаются каждый понедельник в 06:00 UTC после недельного тестирования в канале release-candidate; staging-окружение на canary или на текущем теге release-candidate позволит выявить регрессии до того, как они достигнут ваших пользователей. См. <.localized_link href="/guides/server/self-host/release/channels">Каналы выпусков</.localized_link> для рекомендуемой стратегии закрепления версий.

Если вы предпочитаете получать новые функции по мере их стабилизации без изменения манифестов, закрепите тег `:latest`. Тег обновляется раз в неделю утром в понедельник, поэтому соответствующим образом планируйте окно развертывания. Вот пример рабочего процесса GitHub Actions, который проверяет и развертывает последний стабильный образ с такой периодичностью:

```yaml
name: Update Tuist Server
on:
  schedule:
    - cron: '0 8 * * 1' # Mondays 08:00 UTC, after the weekly stable promote
  workflow_dispatch: # Allow manual runs

jobs:
  update:
    runs-on: ubuntu-latest
    steps:
      - name: Check and deploy latest version
        run: |
          # Your deployment commands here
          # Example: docker pull ghcr.io/tuist/tuist:latest
          # Deploy to your infrastructure
```

## Доступ с доверием к сети {#network-trusted-access}

Установки self-hosted могут разрешать разработчикам в доверенной сети отправлять аналитику, использовать кэш или делать и то, и другое без входа в систему. Для доступа к панели управления и администрированию по-прежнему требуется аутентификация.

Включайте только те возможности, которые вам нужны:

| Переменная окружения сервера | Разрешено без входа в систему |
| --- | --- |
| `TUIST_NETWORK_TRUSTED_INSIGHTS_ACCESS=true` | Отправка аналитики сборок и тестов |
| `TUIST_NETWORK_TRUSTED_CACHE_ACCESS=true` | Чтение и запись кэшированных результатов сборки |

Обе настройки **по умолчанию отключены**, независимы и применяются ко всему экземпляру для всех аккаунтов и проектов, включая приватные проекты. Они недоступны в hosted Tuist и не заменяют лицензию для self-hosting.

Предыдущее имя `TUIST_NETWORK_TRUSTED_REPORT_PUBLISHING` остается резервным вариантом для совместимости, если `TUIST_NETWORK_TRUSTED_INSIGHTS_ACCESS` не задана.

> [!WARNING]
> Включайте эти настройки только за границей корпоративной сети или VPN с принудительным контролем. Любой, кто может достичь включенной конечной точки, может отправлять отчеты или, при включенном доступе к кэшу, читать и перезаписывать кэшированные результаты. Это допускает подделку телеметрии, отравление кэша и исчерпание ресурсов. Ответы на отчеты также могут раскрывать идентификаторы приватных проектов и системы сборки. Tuist не проверяет членство в VPN и не доверяет перенаправляемым IP-заголовкам как доказательству членства.

### Настройка экземпляра {#network-trusted-instance-configuration}

1. Ограничьте доступ к серверу Tuist, каждому слушателю Kura HTTP/gRPC и любому входящему трафику Bazel BES вашей доверенной сетью, используя брандмауэр или частный ingress.
2. Обновите каждую реплику сервера и Kura перед обновлением клиентов. Оставьте аутентификацию Kura включенной с помощью `KURA_AUTH_TUIST_URL` и ее учетных данных control-plane; отключение этого параметра обходит данные ограничения. Настройте конечную точку кэша, используя <.localized_link href="/guides/features/cache/self-hosting">руководство по кэшу для self-hosting</.localized_link>.
3. Установите желаемые переменные выше на каждой соответствующей реплике сервера Tuist, затем перезапустите или повторно разверните их. Только точное значение `true` включает настройку. В панели управления нет переключателя или отдельного флага Kura.

### Настройка клиентов {#network-trusted-client-configuration}

Настройте окончательный URL-адрес self-hosted сервера и проект на каждом совместимом клиенте. Клиенты автоматически определяют, какие возможности включены, когда учетные данные отсутствуют; участие клиента не требуется. Обнаружение не следует за перенаправлениями. Существующие учетные данные остаются в использовании, а недействительные учетные данные или сбои при их обновлении вызывают ошибку, а не анонимный откат. Войдите в систему снова или явно выйдите, чтобы восстановить работу.

Перед включением доступа к аналитике обновите все инструменты, использующие общие учетные данные, до версий, которые сохраняют поврежденные или отклоненные учетные данные, отвергают нечитаемые каталоги учетных данных и исключают источники Git из неподписанных отчетов. Старые инструменты могут удалять учетные данные и непреднамеренно разрешать анонимный откат; обновление только сервера не исправит это. Если сервер не поддерживает обнаружение или откатывается к более старой версии, клиенты должны проходить аутентификацию. Предыдущая настройка клиента `TUIST_NETWORK_TRUSTED_PUBLISHING` больше не применяется.

- **Аналитика:** Отправляйте только завершенные отчеты Xcode, Gradle, Elixir/Mix и Bazel, без доступа к архивам, вложениям, покрытию кода, планированию шардов или существующим отчетам. Утверждения об акторах не проверяются; неподписанная телеметрия не формирует доверенные доказательства тестов или автоматизацию. См. руководства по <.localized_link href="/guides/features/build-insights/xcode#network-trusted-publishing">Xcode</.localized_link>, <.localized_link href="/guides/features/build-insights/gradle#network-trusted-publishing">Gradle</.localized_link> и <.localized_link href="/guides/features/build-insights/elixir#network-trusted-publishing">Elixir</.localized_link> для настройки клиента и сведений о конфиденциальности.
- **Кэш:** Поддерживается кэширование компиляции/модулей через CLI, кэширование Bazel и кэширование задач Gradle. Очистка кэша и загрузка Remote Asset по-прежнему требуют учетных данных. Клиенты без поддержки должны продолжать проходить аутентификацию.
- **Bazel:** Для отчетности требуется явное указание `TUIST_BAZEL_BES_BACKEND` и совместимая Kura. Параметры кэша и отчетности включаются независимо. Повторно запустите `tuist bazel setup` после изменения учетных данных или любой из настроек; повторно запустите `tuist cache config` для изменений конфигурации кэша компиляции.

Запросы на отправку отчетов ограничены 8 МБ, 60 запросами в минуту и 10 000 в день на проект. Настройте общий Valkey для квот на все развертывание с несколькими репликами; в противном случае лимиты применяются на процесс. Если настроенный общий бэкенд квот недоступен, неподписанная отчетность отклоняется. Также добавьте ограничения на входящие соединения, размер тела запроса и скорость.

### Отключение доступа с доверием к сети {#disable-network-trusted-publishing}

Установите соответствующую переменную в `false`, затем перезапустите **каждую соответствующую реплику сервера**. Старые реплики могут продолжать принимать запросы без учетных данных до их замены. Доступ к кэшу для новых запросов прекращается в течение 60 секунд после переключения последней реплики; текущие передачи не отменяются. Сначала заблокируйте трафик на ingress, если требуется немедленное отзывание доступа. Существующие отчеты сохраняют свою обычную видимость и срок хранения, а аутентифицированные клиенты продолжают работать.

### База данных ClickHouse {#clickhouse-database}

Tuist использует [ClickHouse](https://clickhouse.com/) для хранения и запроса больших объемов аналитических данных. ClickHouse **обязателен** для таких возможностей, как инсайты сборок. Вы можете выбрать, размещать ли ClickHouse самостоятельно или использовать их хостинговый сервис.

> [!NOTE]
> **Миграции**
>
> Точка входа образа Docker автоматически выполняет все ожидающие миграции схемы ClickHouse перед запуском сервиса.

Встроенные конфигурации ClickHouse в комплектах Docker Compose и Helm понижают уровень текстового журнала ClickHouse с значения по умолчанию `trace` до `information`, что является основным источником объема `system.text_log`. Обе конфигурации также могут ограничивать собственные таблицы оперативных журналов `system.*` ClickHouse, которые иначе не имеют ограничений, но по умолчанию эта функция отключена — см. ниже. Во внешних развертываниях ClickHouse следует настраивать эти оперативные журналы непосредственно в сервисе ClickHouse.

#### Топология репликации ClickHouse {#clickhouse-replication-topology}

Многорепликовый ClickHouse за Tuist поддерживается только в ClickHouse Cloud. Самостоятельно управляемый ClickHouse работает с одной репликой.

Миграции приема данных создают движок `MergeTree`. В Cloud он прозрачно становится `SharedMergeTree`, поэтому запись идет в общее объектное хранилище и работает с любым количеством реплик. В самостоятельно управляемом ClickHouse `MergeTree` пишет на локальный диск только одной реплики; многорепликовая настройка либо silently разделит прием данных между репликами, либо отклонит CREATE с ошибкой `UNKNOWN_STORAGE: Only tables with a Replicated engine or tables which do not store data on disk are allowed in a Replicated database.` в зависимости от того, как настроен параметр `database_replicated_allow_only_replicated_engine` у подключающегося пользователя.

Запускайте один шард с одной репликой в самостоятельно управляемом ClickHouse и регулярно делайте резервные копии каталога данных ClickHouse. Если узел будет потерян, второй реплики для восстановления не будет.

#### Ограничение срока хранения оперативных журналов {#capping-operational-log-retention}

Срок хранения можно применить к `system.text_log`, `system.query_log`, `system.query_thread_log`, `system.query_views_log`, `system.trace_log`, `system.metric_log`, `system.asynchronous_metric_log` и `system.part_log`.

Включение этой функции — одноразовое необратимое действие для экземпляра, в котором уже есть данные, поэтому ни один из комплектов не делает этого за вас. Любое окно хранения приводит к тому, что определения этих таблиц перестают соответствовать их конфигурации, поэтому ClickHouse переименовывает каждую из них и создает новую таблицу, как описано в разделе [замещенные таблицы журналов](#superseded-log-tables). Оставленная версия содержит все накопленные на данный момент данные и не имеет собственного срока хранения, поэтому, если вы не освободите место на том же шаге, она останется на диске навсегда, а новое окно будет ограничивать только строки, записанные с этого момента. Включите обе настройки вместе:

```yaml
clickhouse:
  embedded:
    systemLogs:
      ttlDays: 14
      supersededTables: delete
```

Эта одиночная операция `helm upgrade` самодостаточна, потому что изменение `ttlDays` с пустого значения на установленное добавляет монтирование drop-in и перезапускает под ClickHouse: он перезагружается, замещает таблицы, а затем задача после обновления удаляет их. Развертывайте с помощью `helm upgrade --wait`, чтобы под был перезапущен до запуска задачи; в противном случае версии появятся после того, как задача уже проверила их наличие, и следующий `helm upgrade` освободит место вместо нее.

В Docker Compose раскомментируйте том `clickhouse-log-ttl.xml` для сервиса `clickhouse` в файле `docker-compose.yml` и установите обе переменные в `.env`:

```bash
CLICKHOUSE_SYSTEM_LOG_TTL_DAYS=14
CLICKHOUSE_SUPERSEDED_LOG_TABLES=delete
```

После освобождения места вы можете вернуть `supersededTables`/`CLICKHOUSE_SUPERSEDED_LOG_TABLES` к значению `ignore`, чтобы последующее обновление ClickHouse не удаляло историю самостоятельно.

#### Замещенные таблицы журналов {#superseded-log-tables}

При запуске ClickHouse проверяет, соответствует ли каждая системная таблица журналов своей конфигурации. Если нет, он переименовывает существующую таблицу в `system.<name>_0`, затем в `_1`, `_2` и так далее, и создает новую. Это происходит при изменении окна хранения и при любом обновлении ClickHouse, которое изменяет схему системного журнала.

Переименование таблицы не копирует ее данные, поэтому дополнительное место на диске не требуется. Что происходит с замещенной таблицей afterward, зависит от исходной таблицы, так как она сохраняет тот срок хранения, который был у активной таблицы в момент замещения. При первом включении хранения у замещаемой таблицы его нет, поэтому она хранит всю накопленную историю бессрочно. Последующее изменение окна замещает таблицу, которая уже имеет TTL, поэтому такие данные истекают самостоятельно, оставляя пустую таблицу. ClickHouse никогда не удаляет сами таблицы, поэтому на долгоживущем экземпляре они накапливаются в любом случае.

Замещенные таблицы сохраняются по умолчанию, чтобы обновление никогда не удаляло оперативную историю самостоятельно. Установите политику в `delete`, чтобы удалять их, что происходит при `docker compose up` и каждом `helm upgrade`:

```bash
CLICKHOUSE_SUPERSEDED_LOG_TABLES=delete
```

В чарте Helm настройте ту же политику как значение:

```yaml
clickhouse:
  embedded:
    systemLogs:
      supersededTables: delete
```

Удаление замещенной таблицы освобождает занимаемое ею место на диске. Активная таблица никогда не затрагивается, как и строки, записанные после ее замещения.

Чтобы освободить место один раз без изменения политики, удалите таблицы вручную:

```sql
SELECT name FROM system.tables WHERE database = 'system' AND match(name, '_log_[0-9]+$');
DROP TABLE IF EXISTS system.text_log_0 SYNC;
```

База данных `system` использует движок `Atomic`, который откладывает обычное `DROP TABLE` на время, заданное параметром `database_atomic_delay_before_drop_table_sec` (по умолчанию восемь минут). `SYNC` удаляет данные немедленно, что необходимо, когда вы удаляете их из-за заполнения диска.


### Хранилище {#storage}

Вам также понадобится решение для хранения файлов (например, бинарных файлов фреймворков и библиотек). Сервер Tuist поддерживает S3-совместимые хранилища и Azure Blob Storage для артефактов, принадлежащих серверу.

> [!TIP]
> **Оптимизированное кэширование**
>
> Если ваша основная цель — снизить задержку кэша, вам может не потребоваться самостоятельное размещение всего сервера. Вы можете развернуть узлы Kura с самостоятельным размещением близко к вашей сети CI или разработчиков и подключить их к хостинговому серверу Tuist или вашему самостоятельно размещенному серверу.
>
> См. <.localized_link href="/guides/cache/self-host">руководство по самостоятельному размещению кэша</.localized_link>.


### Узлы Kura с самостоятельным размещением {#self-hosted-cache-nodes}

Чтобы использовать узлы Kura с самостоятельным размещением с самостоятельно размещенным сервером Tuist:

1. Настройте `KURA_CONTROL_PLANE_CLIENT_ID` и `KURA_CONTROL_PLANE_CLIENT_SECRET` на сервере Tuist. Идентификатор клиента **должен быть UUID**. Сгенерируйте UUID и случайный секрет с помощью команд из <.localized_link href="/guides/cache/self-host#control-plane-client">руководства по самостоятельному размещению кэша</.localized_link> и сохраните их в секретах вашего развертывания.
2. Разверните узлы Kura, следуя <.localized_link href="/guides/cache/self-host">руководству по самостоятельному размещению кэша</.localized_link>, используя те же учетные данные плоскости управления.
3. Настройте каждый узел Kura с помощью `KURA_REGISTRATION_URL` и `KURA_ADVERTISED_HTTP_URL`. Heartbeat-сигналы регистрации сообщают серверу, какие готовые клиентские конечные точки Kura он может рекламировать CLI.

### Конфигурация базы данных {#database-configuration}

Следующие переменные окружения используются для настройки подключения к базе данных:

| Переменная окружения | Описание | Обязательно | По умолчанию | Пример |
| --- | --- | --- | --- | --- |
| `DATABASE_URL` | URL для доступа к базе данных Postgres. Обратите внимание, что URL должен содержать информацию для аутентификации | Да | | `postgres://username:password@cloud.us-east-2.aws.test.com/production` |
| `TUIST_DATABASE_SCHEMA` | Схема PostgreSQL, используемая таблицами приложения Tuist. Установите это значение, если политика вашей базы данных запрещает использование схемы `public`. Имя схемы должно быть нецитируемым идентификатором PostgreSQL. | Нет | `public` | `tuist` |
| `TUIST_MIGRATION_DATABASE_URL` | Необязательный URL Postgres, используемый только `Tuist.Release.migrate`. | `TUIST_CLICKHOUSE_URL` | URL для доступа к базе данных ClickHouse. Обратите внимание, что URL должен содержать информацию для аутентификации | Нет | | `http://username:password@cloud.us-east-2.aws.test.com/production` |

| `TUIST_DATABASE_QUEUE_TARGET` | Интервал (в миллисекундах) для проверки того, заняли ли все соединения, взятые из пула, больше времени, чем интервал очереди [(Подробнее)](https://hexdocs.pm/db_connection/DBConnection.html#start_link/2-queue-config) | Нет | `300` | `300` |

| `TUIST_CLICKHOUSE_FLUSH_INTERVAL_MS` | Временной интервал в миллисекундах между сбросами буфера ClickHouse. | Нет | `5000` | `5000` |
| `TUIST_CLICKHOUSE_MAX_BUFFER_SIZE` | Максимальный размер буфера ClickHouse в байтах перед принудительным сбросом. | Нет | `1000000` | `1000000` |
| `TUIST_CLICKHOUSE_BUFFER_POOL_SIZE` | Количество процессов буферизации ClickHouse для запуска. | Нет | `5` | `5` |

По умолчанию Tuist шифрует подключение к базе данных, но не проверяет сертификат сервера, поэтому злоумышленник в сетевом пути может выдать себя за базу данных. Установите `TUIST_DATABASE_SSL_VERIFY=1`, чтобы включить проверку. Если ваш провайдер подписывает сертификаты собственным CA, как это делают Amazon RDS и Google Cloud SQL, скачайте его пакет CA, смонтируйте его в контейнере и укажите на него через `TUIST_DATABASE_SSL_CA_CERT_FILE`. Хост в `DATABASE_URL` должен совпадать с именем или IP-адресом в сертификате. При включенной проверке сертификат, не прошедший эти проверки, приведет к сбою каждого подключения к базе данных, поэтому после включения проверьте журналы сервера на наличие `Bad Certificate` или `Unknown CA`.

Когда `TUIST_DATABASE_SCHEMA` не равно `public`, миграции релиза создают схему, если она еще не существует, перед запуском цепочки миграций Ecto. Если роль миграции не может создавать схемы, создайте схему заранее и сделайте роль миграции ее владельцем.

Tuist направляет подключение на пользовательскую схему, устанавливая `search_path` сессии. Некоторые конфигурации Postgres с пулингом или проксированием (например, PgBouncer или управляемые базы данных, ограничивающие параметры запуска) не применяют это, и сессия возвращается к `public`, что проявляется во время миграций как `permission denied for schema public`. При подключении через такую конфигурацию закрепите схему за самой ролью, чтобы каждая сессия начиналась в ней независимо от прокси:

```sql
CREATE SCHEMA IF NOT EXISTS tuist AUTHORIZATION <migration_role>;
ALTER ROLE <migration_role> IN DATABASE <database> SET search_path = tuist;
-- If the web server connects as a separate runtime role (TUIST_DATABASE_RUNTIME_ROLE):
ALTER ROLE <runtime_role> IN DATABASE <database> SET search_path = tuist;
```

### Конфигурация окружения аутентификации {#authentication-environment-configuration}

Мы обеспечиваем аутентификацию через [поставщиков удостоверений (IdP)](https://en.wikipedia.org/wiki/Identity_provider). Чтобы использовать эту возможность, убедитесь, что все необходимые переменные окружения для выбранного провайдера присутствуют в окружении сервера. **Отсутствие переменных** приведет к тому, что Tuist пропустит этого провайдера.

#### Электронная почта и пароль {#email-and-password}

Вход по электронной почте и паролю и самостоятельная регистрация встроены и включены по умолчанию. В экземпляре, где вы хотите требовать использования поставщика удостоверений (например, при принудительном использовании SSO), вы можете полностью отключить их. Это удалит форму ввода электронной почты/пароля, ссылку для регистрации и процесс сброса пароля из процесса входа, а также закроет все соответствующие серверные конечные точки, включая конечную точку электронной почты/пароля, используемую CLI (`tuist auth`).

| Переменная окружения | Описание | Обязательно | По умолчанию | Пример |
| --- | --- | --- | --- | --- |
| `TUIST_EMAIL_AUTH_ENABLED` | Можно ли использовать электронную почту и пароль для входа и регистрации. Установите значение `0`, чтобы удалить форму ввода электронной почты/пароля, ссылку для регистрации и процесс сброса пароля со страницы входа и закрыть соответствующие серверные конечные точки. | Нет | `1` | `0` |

#### Отключение настроенного поставщика удостоверений {#disabling-a-configured-identity-provider}

По умолчанию провайдер отображается как вариант входа всякий раз, когда он настроен. Чтобы оставить провайдер настроенным (его учетные данные остаются установленными), но убрать его со страниц входа и регистрации, установите соответствующий переключатель в `0`. Для GitHub, Google и Apple это также закрывает обратный вызов входа, поэтому метод становится полностью недоступным.

| Переменная окружения | Описание | Обязательно | По умолчанию | Пример |
| --- | --- | --- | --- | --- |
| `TUIST_GITHUB_AUTH_ENABLED` | Можно ли использовать GitHub для входа (см. раздел [GitHub](#github), чтобы узнать, почему приложение разделяет свои учетные данные с входом) | Нет | `1` | `0` |
| `TUIST_GOOGLE_AUTH_ENABLED` | Можно ли использовать Google для входа | Нет | `1` | `0` |
| `TUIST_OKTA_AUTH_ENABLED` | Можно ли использовать настроенный провайдер Okta как вариант входа | Нет | `1` | `0` |
| `TUIST_APPLE_AUTH_ENABLED` | Можно ли использовать Apple для входа | Нет | `1` | `0` |

#### GitHub {#github}

Мы рекомендуем аутентифицироваться через [приложение GitHub](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/about-creating-github-apps), но можно также использовать [OAuth-приложение](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/creating-an-oauth-app). Убедитесь, что все необходимые переменные окружения, указанные GitHub, присутствуют в окружении сервера. Если переменные отсутствуют, Tuist проигнорирует аутентификацию через GitHub. Чтобы правильно настроить приложение GitHub:
- В общих настройках приложения GitHub:
    - Скопируйте `Client ID` и установите его как `TUIST_GITHUB_APP_CLIENT_ID`
    - Создайте и скопируйте новый `client secret` и установите его как `TUIST_GITHUB_APP_CLIENT_SECRET`
    - Установите `Callback URL` как `http://YOUR_APP_URL/users/auth/github/callback`. `YOUR_APP_URL` также может быть IP-адресом вашего сервера.
- Требуются следующие разрешения:
  - Репозитории:
    - Pull requests: чтение и запись
  - Аккаунты:
    - Адреса электронной почты: только чтение

В разделе `Account permissions` настроек `Permissions and events` установите разрешение `Email addresses` в значение `Read-only`.

Затем вам нужно будет выставить следующие переменные окружения в среде, где работает сервер Tuist:

| Переменная окружения | Описание | Обязательно | По умолчанию | Пример |
| --- | --- | --- | --- | --- |
| `TUIST_GITHUB_APP_CLIENT_ID` | Client ID приложения GitHub | Да | | `Iv1.a629723000043722` |
| `TUIST_GITHUB_APP_CLIENT_SECRET` | Client secret приложения | Да | | `232f972951033b89799b0fd24566a04d83f44ccc` |
| `TUIST_GITHUB_AUTH_ENABLED` | Можно ли использовать GitHub для входа. Приложение GitHub, которое вы настраиваете для интеграций с платформой (комментарии к PR и т. д.), разделяет свои клиентские учетные данные с входом, поэтому иначе оно отображается как вариант входа. Установите значение `0`, чтобы оставить приложение, но убрать GitHub со страницы входа | Нет | `1` | `0` |

#### Google {#google}

Вы можете настроить аутентификацию через Google, используя [OAuth 2](https://developers.google.com/identity/protocols/oauth2). Для этого нужно создать новые учетные данные типа «OAuth client ID». При создании учетных данных выберите тип приложения «Web Application», назовите его `Tuist` и установите URI перенаправления в `{base_url}/users/auth/google/callback`, где `base_url` — URL, по которому работает ваш хостинг-сервис. После создания приложения скопируйте client ID и secret и установите их как переменные окружения `GOOGLE_CLIENT_ID` и `GOOGLE_CLIENT_SECRET` соответственно.

> [!NOTE]
> **Области доступа экрана согласия**
>
> Возможно, вам потребуется создать экран согласия. При его создании обязательно добавьте области доступа `userinfo.email` и `openid` и отметьте приложение как внутреннее.


#### Okta {#okta}

Вы можете включить аутентификацию через Okta по протоколу [OAuth 2.0](https://oauth.net/2/). Вам нужно будет [создать приложение](https://developer.okta.com/docs/en/guides/implement-oauth-for-okta/main/#create-an-oauth-2-0-app-in-okta) в Okta, следуя <.localized_link href="/guides/integrations/authentication/sso#okta">этим инструкциям</.localized_link>.

После получения client id и secret при настройке приложения Okta вам нужно будет установить следующие переменные окружения:

| Переменная окружения | Описание | Обязательно | По умолчанию | Пример |
| --- | --- | --- | --- | --- |
| `TUIST_OKTA_1_CLIENT_ID` | Client ID для аутентификации в Okta. Число должно быть идентификатором вашей организации | Да | | |
| `TUIST_OKTA_1_CLIENT_SECRET` | Client secret для аутентификации в Okta | Да | | |

Число `1` нужно заменить на идентификатор вашей организации. Обычно это 1, но проверьте в своей базе данных.

> Если ваш провайдер хранилища — AWS и вы хотите аутентифицироваться с помощью токена веб-идентичности, установите переменную окружения `TUIST_S3_AUTHENTICATION_METHOD` в значение `aws_web_identity_token_from_env_vars`, и Tuist будет использовать этот метод с обычными переменными окружения AWS.


#### Google Cloud Storage {#google-cloud-storage}
Для Google Cloud Storage следуйте [этой документации](https://cloud.google.com/storage/docs/authentication/managing-hmackeys), чтобы получить пару `AWS_ACCESS_KEY_ID` и `AWS_SECRET_ACCESS_KEY`. Значение `AWS_ENDPOINT` должно быть установлено в `https://storage.googleapis.com`. Остальные переменные окружения такие же, как для любого другого S3-совместимого хранилища.

#### Azure Blob Storage {#azure-blob-storage}

Для Azure Blob Storage установите `TUIST_OBJECT_STORAGE_PROVIDER=azure_blob` и настройте учетные данные аккаунта хранения Azure:

| Переменная окружения | Описание | Обязательно | По умолчанию | Пример |
| --- | --- | --- | --- | --- |
| `TUIST_AZURE_STORAGE_ACCOUNT_NAME` | Имя аккаунта Azure Storage | Да | | `tuiststorage` |
| `TUIST_AZURE_STORAGE_ACCOUNT_KEY` | Ключ доступа аккаунта хранения, используемый для подписи REST-запросов Azure Blob и SAS-URL | Да | | `******` |
| `TUIST_AZURE_BLOB_CONTAINER_NAME` | Контейнер, в котором хранятся артефакты сервера | Да | | `tuist-artifacts` |
| `TUIST_AZURE_BLOB_ENDPOINT` | Эндпоинт службы Blob. Опустите, чтобы использовать `https://<account>.blob.core.windows.net` | Нет | Формируется из имени аккаунта | `https://tuiststorage.blob.core.windows.net` |
| `TUIST_AZURE_BLOB_SERVICE_VERSION` | Версия REST API Azure Blob, используемая для подписанных запросов и SAS-URL | Нет | `2020-12-06` | `2020-12-06` |

При использовании Helm-чарта установите `server.storage.provider=azure_blob` и заполните `server.azureBlob.*`. Настройки верхнего уровня `objectStorage` чарта остаются S3-совместимыми, поскольку опциональные воркलोады кэша и зеркала реестра по-прежнему ожидают S3-совместимое хранилище. Если эти ворклоады отключены и сервер использует Azure Blob, установите `objectStorage.mode=external` и оставьте эндпоинт внешнего объектного хранилища и учетные данные пустыми, чтобы избежать развертывания встроенной службы MinIO.

#### Хранение артефактов {#artifact-retention}

Очистка артефактов по умолчанию отключена на самостоятельно размещаемых экземплярах. Для каждого поддерживаемого типа артефактов предусмотрена своя переменная окружения. Установите значение переменной в положительное целое число дней, чтобы включить очистку для этого типа артефактов. Если переменная не задана или пуста, очистка отключается только для соответствующего типа артефактов.

```bash
TUIST_CACHE_ARTIFACT_RETENTION_DAYS=30
TUIST_APP_PREVIEW_RETENTION_DAYS=30
TUIST_BUILD_ARCHIVE_RETENTION_DAYS=60
TUIST_RUN_ARTIFACT_RETENTION_DAYS=30
TUIST_TEST_ATTACHMENT_RETENTION_DAYS=30
TUIST_SHARD_BUNDLE_RETENTION_DAYS=14
```

При использовании Helm-чарта настройте те же периоды в виде карты:

```yaml
server:
  artifactRetentionDays:
    cacheArtifacts: 30
    appPreviews: 30
    buildArchives: 60
    runArtifacts: 30
    testAttachments: 30
    shardBundles: 14
```

Все шесть ключей необязательны. В этом примере включены все поддерживаемые типы артефактов с независимыми периодами хранения. Пропустите ключ или оставьте его значение пустым, чтобы оставить очистку отключенной для этого типа артефактов. Для самостоятельно размещаемых экземпляров нет ограничения в 30 дней на максимальный период хранения. Значения, которые не являются положительными целыми числами, приведут к ошибке запуска сервера.

Перезапустите сервер после изменения переменной хранения. Каждая поставленная в очередь пакетная задача очистки на самостоятельно размещаемом экземпляре проверяет текущую конфигурацию перед удалением файлов, поэтому сброс или очистка переменной, а также увеличение ее периода также защищает файлы от ожидающих задач после перезапуска.

| Переменная окружения | Файлы артефактов, удаляемые из объектного хранилища |
| --- | --- |
| `TUIST_CACHE_ARTIFACT_RETENTION_DAYS` | Кэш Xcode, устаревший кэш с адресацией по содержимому, кэш модулей и файлы кэша Gradle |
| `TUIST_APP_PREVIEW_RETENTION_DAYS` | Сборки предварительного просмотра приложений и иконки |
| `TUIST_BUILD_ARCHIVE_RETENTION_DAYS` | Текущие и устаревшие архивы сборок |
| `TUIST_RUN_ARTIFACT_RETENTION_DAYS` | Все объекты, хранящиеся под префиксом артефактов истекшего запуска, включая пакеты результатов, записи вызовов и архивы сессий |
| `TUIST_TEST_ATTACHMENT_RETENTION_DAYS` | Вложения запусков тестов |
| `TUIST_SHARD_BUNDLE_RETENTION_DAYS` | Пакеты шардов тестов |

Запланированная очистка удаляет только блобы артефактов. Соответствующие строки в PostgreSQL и ClickHouse сохраняются, поэтому метаданные сборок, тестов, запусков, предварительных просмотров и шардов могут оставаться видимыми в дашбордах после истечения срока загрузки. Эта конфигурация не изменяет правила хранения таблиц ClickHouse.

### Настройка электронной почты {#email-configuration}

Tuist требует функциональности электронной почты для аутентификации пользователей и транзакционных уведомлений (например, сброса пароля, уведомлений об аккаунте). В настоящее время **поддерживается только Mailgun** в качестве провайдера электронной почты.

| Переменная окружения | Описание | Обязательно | По умолчанию | Пример |
| --- | --- | --- | --- | --- |
| `TUIST_MAILGUN_API_KEY` | API-ключ для аутентификации в Mailgun | Да* | | `key-1234567890abcdef` |
| `TUIST_MAILING_DOMAIN` | Домен, с которого будут отправляться письма | Да* | | `mg.tuist.io` |
| `TUIST_MAILING_FROM_ADDRESS` | Адрес электронной почты, который будет отображаться в поле «От» | Да* | | `noreply@tuist.io` |
| `TUIST_MAILING_REPLY_TO_ADDRESS` | Необязательный адрес для ответов пользователей | Нет | | `support@tuist.dev` |
| `TUIST_SKIP_EMAIL_CONFIRMATION` | Пропускать подтверждение электронной почты при регистрации новых пользователей. При включении пользователи автоматически подтверждаются и могут войти сразу после регистрации | Нет | `true`, если электронная почта не настроена, `false`, если электронная почта настроена | `true`, `false`, `1`, `0` |

\* Переменные настройки электронной почты требуются только если вы хотите отправлять письма. Если они не настроены, подтверждение электронной почты автоматически пропускается

> [!NOTE]
> **Поддержка SMTP**
>
> Общая поддержка SMTP в настоящее время недоступна. Если вам нужна поддержка SMTP для вашего локального развертывания, пожалуйста, свяжитесь с [contact@tuist.dev](mailto:contact@tuist.dev), чтобы обсудить ваши требования.


> [!NOTE]
> **Развертывания в изолированных сетях**
>
> Для локальных установок без доступа к интернету или настройки провайдера электронной почты подтверждение электронной почты по умолчанию автоматически пропускается. Пользователи могут войти сразу после регистрации. Если у вас настроена электронная почта, но вы все равно хотите пропустить подтверждение, установите `TUIST_SKIP_EMAIL_CONFIRMATION=true`. Чтобы требовать подтверждение электронной почты, когда она настроена, установите `TUIST_SKIP_EMAIL_CONFIRMATION=false`.

> [!NOTE]
> **Квоты электронной почты и ссылки для сброса пароля**
>
> При настроенной электронной почте письма-приглашения (созданные, массовые или повторно отправленные) ограничены одним письмом на получателя каждые пять минут и bursts до 50 писем с восполнением до 50 в час на организацию и на приглашающего. Отмена приглашения не восстанавливает лимит, и API приглашений отвечает на исчерпанный лимит кодом `429` и заголовком `Retry-After`. При наличии нескольких реплик настройте общий Valkey для квот на все развертывание; если он настроен, но недоступен, письма-приглашения отклоняются. Ссылки для сброса пароля истекают через 15 минут.


### Настройка Git-платформы {#git-platform-configuration}

Tuist может <.localized_link href="/guides/server/authentication">интегрироваться с Git-платформами</.localized_link> для предоставления дополнительных возможностей, таких как автоматическая публикация комментариев в ваших pull-запросах.

#### GitHub {#platform-github}

Самостоятельно размещенный сервер Tuist не может установить приложение GitHub, которое работает на `https://tuist.dev`. Приложения GitHub привязаны к серверу, который их зарегистрировал, поэтому вашему развертыванию нужно собственное приложение на github.com.

##### Регистрация приложения {#platform-github-registering-the-app}

[Создайте приложение GitHub](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/about-creating-github-apps), принадлежащее вашей организации GitHub. Вы можете повторно использовать приложение, созданное для аутентификации, если только вы не создали приложение OAuth. Настройте его следующим образом, заменив `YOUR_APP_URL` значением `TUIST_APP_URL`:

| Параметр | Значение |
| --- | --- |
| URL-адреса обратного вызова | `YOUR_APP_URL/users/auth/github/callback` и `YOUR_APP_URL/integrations/github/authorize` |
| URL-адрес настройки | `YOUR_APP_URL/integrations/github/setup` |
| Перенаправление при обновлении | Включено |
| URL-адрес вебхука | `YOUR_APP_URL/webhooks/github` |
| Секрет вебхука | Любая случайная строка. Вы установите ее как `TUIST_GITHUB_APP_WEBHOOK_SECRET` |

Предоставьте следующие разрешения для репозитория:

| Разрешение | Доступ |
| --- | --- |
| Содержимое | Только чтение |
| Метаданные | Только чтение |
| Задачи (Issues) | Чтение и запись |
| Pull-запросы | Чтение и запись |
| Проверки | Чтение и запись |

Также предоставьте разрешение организации **Участники: только чтение**. Во время настройки на github.com Tuist проверяет, что человек, подключающий установку организации, является активным владельцем организации GitHub, а не просто тем, у кого есть доступ к одному из ее репозиториев.

Подпишите приложение на события `Check run`, `Pull request` и `Issue comment`.

Оставьте опцию **Запрашивать авторизацию пользователя (OAuth) во время установки** отключенной, чтобы GitHub отправлял установщиков на URL-адрес настройки. Tuist запускает отдельный шаг авторизации, используя дополнительный обратный вызов `/integrations/github/authorize` для проверки владения установкой. Когда установка начинается на GitHub, установщик затем выбирает организацию Tuist; установки, начатые в Tuist, сохраняют свою организацию.

##### Настройка сервера {#platform-github-configuring-the-server}

Установите следующие переменные окружения, затем перезапустите сервер:

| Переменная окружения | Описание | Обязательно | По умолчанию | Пример |
| --- | --- | --- | --- | --- |
| `TUIST_GITHUB_APP_NAME` | Слаг приложения, который является последним компонентом пути его публичного URL-адреса страницы `https://github.com/apps/<slug>` | Да | | `my-company-tuist` |
| `TUIST_GITHUB_APP_ID` | Числовой идентификатор приложения, используемый для проверки владения установкой | Да | | `123456` |
| `TUIST_GITHUB_APP_CLIENT_ID` | Идентификатор клиента приложения GitHub | Да | | `Iv1.a629723000043722` |
| `TUIST_GITHUB_APP_CLIENT_SECRET` | Секрет клиента приложения | Да | | `232f972951033b89799b0fd24566a04d83f44ccc` |
| `TUIST_GITHUB_APP_PRIVATE_KEY_BASE64` | Закрытый ключ приложения GitHub в кодировке base64. Предпочтительнее, чем `TUIST_GITHUB_APP_PRIVATE_KEY`, так как он чувствителен к тому, как ваша платформа обрабатывает переносы строк | Да | | `LS0tLS1CRUdJTiBSU0EgUFJJVkFUR...` |
| `TUIST_GITHUB_APP_WEBHOOK_SECRET` | Секрет вебхука, настроенный в приложении GitHub | Нет | | `a4c1e0f2b8d6...` |

> [!IMPORTANT]
> **Настройте все необходимые учетные данные приложения**
>
> Кнопка **Установить приложение GitHub** на странице интеграций организации остается неактивной, пока не будут установлены `TUIST_GITHUB_APP_NAME`, `TUIST_GITHUB_APP_CLIENT_ID`, `TUIST_GITHUB_APP_CLIENT_SECRET` и закрытый ключ. Числовой `TUIST_GITHUB_APP_ID` также необходим для проверки владения установкой. URL-адрес установки содержит слаг приложения, поэтому отсутствие `TUIST_GITHUB_APP_NAME` в частности приводит к тому, что GitHub отвечает ошибкой 404.

После перезапуска сервера администраторы организации устанавливают приложение и подключают репозитории к проектам, следуя <.localized_link href="/guides/integrations/gitforge/github">руководству по интеграции с GitHub</.localized_link>.

##### Аутентификация OIDC зависит от этого {#platform-github-oidc}

<.localized_link href="/guides/server/authentication#oidc-tokens">Аутентификация OIDC</.localized_link> сопоставляет утверждение о репозитории в токене CI с репозиториями, подключенными к вашим проектам, и соединение может быть создано только через установленное приложение GitHub. Завершите настройку выше, прежде чем ваши рабочие процессы CI запустят `tuist auth login` без токена.

Вашему серверу Tuist также нужен исходящий доступ к эмитенту OIDC вашего провайдера CI для получения его ключей подписи:

| Провайдер CI | Хост |
| --- | --- |
| GitHub Actions | `token.actions.githubusercontent.com` |
| CircleCI | `oidc.circleci.com` |
| Bitrise | `token.builds.bitrise.io` |

##### GitHub Enterprise Server {#platform-github-enterprise-server}

Переменные окружения выше настраивают только приложение Tuist для github.com. Чтобы интегрировать Tuist с экземпляром GitHub Enterprise Server (GHES), администраторы организации переходят на вкладку **Корпоративный сервер** на странице интеграций и вводят базовый URL-адрес GHES — Tuist проводит их через [процесс регистрации приложения через манифест](https://docs.github.com/en/apps/sharing-github-apps/registering-a-github-app-from-a-manifest) GitHub для регистрации нового приложения Tuist на их экземпляре GHES. Учетные данные нового приложения хранятся в зашифрованном виде для каждой установки; дополнительные переменные окружения `TUIST_GITHUB_APP_*` не требуются.

#### Origin {#platform-origin}

Серверу Tuist, размещенному самостоятельно, требуется собственное приложение Origin, настроенное с URL-адресами вашего развертывания и ключом подписи. Зарегистрируйте отдельное приложение для каждой среды Tuist, чтобы установки и учетные данные оставались независимыми.

##### Регистрация приложения {#platform-origin-registering-the-app}

1. Сгенерируйте пару ключей подписи Ed25519 с помощью OpenSSL с поддержкой Ed25519:

   ```sh
   umask 077
   openssl genpkey -algorithm ED25519 -out origin-app-private.pem
   openssl pkey -in origin-app-private.pem -pubout -out origin-app-public.pem
   ```

2. Создайте приложение в [настройках приложения Origin](https://cursor.com/codebase/settings/apps). Зарегистрируйте содержимое `origin-app-public.pem` в качестве его открытого ключа подписи. Храните `origin-app-private.pem` в секрете; вы предоставите его серверу Tuist, а не загрузите в Cursor.
3. Настройте следующие параметры, заменив `YOUR_APP_URL` на базовый HTTPS-URL вашего развертывания Tuist:

   | Параметр | Значение |
   | --- | --- |
   | URL-адрес главной страницы | `YOUR_APP_URL` |
   | URI перенаправления | `YOUR_APP_URL/integrations/origin/setup` |
   | URL-адрес вебхука | `YOUR_APP_URL/webhooks/origin` |

4. Скопируйте зарегистрированный идентификатор приложения, который начинается с `app_`.

Во время установки Tuist запрашивает следующие разрешения:

| Область действия | Используется для |
| --- | --- |
| `repository:pull_requests:read` | Поиск pull-запросов и их текущего головного коммита. |
| `repository:pull_requests:reviews:write` | Чтение, публикация и обновление комментариев к отчетам. Origin включает соответствующее разрешение на чтение отзывов. |
| `repository:metadata:read` | Обнаружение репозиториев и чтение их веток по умолчанию. Предоставляется автоматически Origin. |

Не выбирайте необязательные события вебхуков репозитория. Уведомлений о жизненном цикле установки достаточно; доступ к исходному коду, разрешения на слияние и разрешения на выполнение проверок не требуются.

##### Настройка сервера {#platform-origin-configuring-the-server}

Установите следующие переменные окружения, затем перезапустите сервер:

| Переменная окружения | Описание | Обязательно | По умолчанию | Пример |
| --- | --- | --- | --- | --- |
| `TUIST_ORIGIN_APP_ID` | Идентификатор приложения, скопированный из настроек приложения Origin. | Да | | `app_...` |
| `TUIST_ORIGIN_APP_PRIVATE_KEY` | Полное содержимое `origin-app-private.pem`, включая строки `BEGIN PRIVATE KEY` и `END PRIVATE KEY` и все разрывы строк. | Да | | `-----BEGIN PRIVATE KEY-----...` |

Храните закрытый ключ в менеджере секретов вашего развертывания. Сохраняйте его многострочный формат PEM; этот параметр не принимает замену в кодировке base64. Никогда не добавляйте ключ в систему контроля версий и не раскрывайте его в журналах. Обе переменные должны принадлежать одному и тому же зарегистрированному приложению.

Вашему серверу Tuist необходим исходящий HTTPS-доступ к `api.cursor.com`. Cursor должен иметь возможность доставлять запросы на URL-адрес вебхука, а администраторы должны иметь возможность возвращаться на URI перенаправления в своем браузере. Оба зарегистрированных URL-адреса должны совпадать с базовым HTTPS-URL вашего развертывания.

##### Установка приложения {#platform-origin-installing-the-app}

После перезапуска сервера администратор открывает **Настройки → Интеграции**, выбирает **Подключить** в разделе Origin и предоставляет приложению доступ к соответствующей учетной записи Origin и репозиториям. Организация Tuist сохраняется на протяжении всего процесса. При установке, инициированной непосредственно из Origin, администратору предлагается войти в систему и выбрать организацию Tuist для подключения. Затем они выбирают **Добавить новое подключение проекта**, чтобы связать проект Tuist с нативным репозиторием.

Следуйте <.localized_link href="/guides/integrations/gitforge/origin">руководству по интеграции с Origin</.localized_link> для настройки подключений проектов и требований к загрузке результатов. Установка приложения не запускает рабочие процессы сборки или тестирования; эти рабочие процессы продолжают отправлять результаты на ваш сервер Tuist.

## Локальное тестирование {#testing-locally}

Мы предоставляем комплексную конфигурацию Docker Compose, которая включает все необходимые зависимости для тестирования сервера Tuist на вашем локальном компьютере перед развертыванием в вашей инфраструктуре:

## Kubernetes с Helm {#kubernetes-with-helm}

Tuist предоставляет официальный Helm-чарт для развертывания в Kubernetes. Чарт включает сервер и службу кэша Tuist, а также встроенные зависимости инфраструктуры, которые при необходимости можно заменить на внешние провайдеры.

### Установка чарта {#installing-the-chart}

```bash
helm install tuist oci://ghcr.io/tuist/charts/tuist \
  --set server.license.key="YOUR_LICENSE_KEY"
```

Чтобы зафиксировать конкретную версию чарта:

```bash
helm install tuist oci://ghcr.io/tuist/charts/tuist \
  --set server.license.key="YOUR_LICENSE_KEY" \
  --version 0.1.0
```

### Лицензия {#helm-license}

Значение `server.license.key` принимает как стандартный ключ лицензии, так и (для установок в изолированных сетях) сертификат лицензии в кодировке Base64; сервер автоматически определяет тип.

Передача лицензии через `--set` подходит для быстрой установки. Если вы храните значения в системе контроля версий, сохраните лицензию в Kubernetes Secret, которым управляете вне Helm (например, через Vault, Sealed Secrets или SOPS), и укажите на него в чарте:

```yaml
# values.yaml
server:
  license:
    existingSecret: tuist-license
    existingSecretKeys:
      key: TUIST_LICENSE
      certificateBase64: ""
```

Запись под `existingSecretKeys.key` указывает поле в вашем Secret, содержащее значение лицензии (ключ лицензии или, для изолированных сетей, сертификат в кодировке Base64). Каждое поле под `existingSecretKeys` по умолчанию совпадает с именем ключа чарта, поэтому поля, отсутствующие в вашем Secret, задайте пустой строкой, как показано выше для `certificateBase64`. Иначе поды будут ссылаться на несуществующие ключи и не смогут запуститься. Создайте Secret в пространстве имен релиза перед установкой или обновлением чарта.

Настраивайте лицензию только из одного источника: `server.license.key` или `server.license.existingSecret`. Чарт не отрендерится, если ни один источник не задан или если источники комбинируются. Лицензия, переданная через `server.extraEnv`, не считается источником, поэтому используйте вместо этого `existingSecret`.

### Зависимости инфраструктуры {#helm-infrastructure-dependencies}

Чарт управляет тремя зависимостями инфраструктуры: `postgresql`, `clickhouse` и `objectStorage`. По умолчанию каждая работает в режиме **embedded**, то есть чарт разворачивает их внутри кластера. Чтобы использовать собственные внешние экземпляры, установите для зависимости `mode` значение `external` и заполните параметры подключения в вашем `values.yaml`. Например, чтобы использовать внешнюю базу данных PostgreSQL:

```yaml
# values.yaml
postgresql:
  mode: external
  external:
    host: your-db-host
    port: 5432
    database: tuist
    username: tuist
    password: your-password
```

Если вы управляете учетными данными PostgreSQL вне Helm, укажите чарту на существующий Kubernetes Secret:

```yaml
# values.yaml
postgresql:
  mode: external
  external:
    port: 5432
    database: tuist
    existingSecret: tuist-postgresql
    existingSecretKeys:
      host: host
      username: username
      password: password
```

Чарт считывает хост, имя пользователя и пароль из Secret и формирует `DATABASE_URL` через подстановку переменных окружения Kubernetes, поэтому пароль не попадает в манифест Helm. Значение пароля в Secret должно быть безопасным для URL, так как оно вставляется в URL базы данных.

Та же схема применяется к `clickhouse` и `objectStorage`. Полный набор настраиваемых полей см. в блоке `external` каждого раздела в `values.yaml` чарта.

### Общие настройки планирования и метки {#helm-shared-scheduling-and-labels}

Чарт предоставляет небольшой набор общих настроек подов через `global`, чтобы операторы могли адаптировать развертывание под свой кластер без повторения одних и тех же значений для каждой рабочей нагрузки:

```yaml
global:
  podLabels:
    environment: production
  imagePullSecrets:
    - name: ghcr-pull-secret
  nodeSelector:
    nodepool: apps
  tolerations:
    - key: dedicated
      operator: Equal
      value: apps
      effect: NoSchedule
```

Используйте эти настройки, когда нужно:

- добавить специфичные для кластера метки ко всем подам
- загружать зеркалированные образы из частного реестра
- нацелить развертывание на выделенный пул узлов
- разрешить подам запускаться на tainted-узлах, зарезервированных для рабочих нагрузок Tuist

### Идентификация рабочих нагрузок и сервисные аккаунты {#helm-workload-identity}

Чарт ограничивает область действия сервисных аккаунтов каждой рабочей нагрузкой приложения, чтобы вы могли предоставлять доступ только там, где это необходимо:

- `server.serviceAccount` применяется к развертыванию сервера Tuist и задаче миграции
- `cache.serviceAccount` применяется к развертыванию кэша

Например, если кэш использует внешний бакет S3 в EKS, вы можете включить IRSA для рабочей нагрузки кэша, не привязывая ту же роль IAM к встроенным базам данных:

```yaml
cache:
  serviceAccount:
    create: true
    annotations:
      eks.amazonaws.com/role-arn: arn:aws:iam::123456789012:role/tuist-cache
```

### Переопределения совместимости {#helm-compatibility-overrides}

Чарт оставляет специфичные для хранилища и сетки настройки опциональными, чтобы значения по умолчанию оставались переносимыми:

```yaml
cache:
  podSecurityContext:
    fsGroup: 990

clickhouse:
  embedded:
    service:
      nativePort: 9100
    systemLogs:
      ttlDays: 7
      supersededTables: delete
      level: warning
```

Используйте эти переопределения только тогда, когда ваш кластер требует их:

- `cache.podSecurityContext` по умолчанию пуст. Установите `fsGroup`, если ваш класс хранения или CSI-драйвер требует общего группового владения для смонтированных томов.
- `clickhouse.embedded.service.nativePort` по умолчанию соответствует стандартному порту нативного сервиса ClickHouse `9000` и может быть изменен, если сетевая mesh-инфраструктура или резервирование платформы конфликтуют с этим портом.
- `clickhouse.embedded.systemLogs.ttlDays` по умолчанию пуст, что оставляет неограниченное хранение во встроенных внутренних таблицах логов ClickHouse, таких как `system.text_log`, `system.query_log`, `system.trace_log`, `system.metric_log` и `system.part_log`. Установка этого параметра один раз заменяет эти таблицы, поэтому используйте его вместе с `supersededTables: delete` — см. <.localized_link href="/guides/server/self-host/server#capping-operational-log-retention">ограничение срока хранения операционных логов</.localized_link>.
- `clickhouse.embedded.systemLogs.level` по умолчанию установлено в `information` для встроенного логгера сервера ClickHouse и `system.text_log`. В отличие от `ttlDays`, этот параметр не является частью определения таблиц, поэтому его изменение никогда не приводит к замене таблиц.
- `clickhouse.embedded.systemLogs.supersededTables` по умолчанию установлено в `ignore` и определяет, что происходит с таблицами `<name>_N`, которые ClickHouse оставляет после замены системной таблицы логов. Установите значение `delete`, чтобы удалять их при каждом `helm upgrade`.
- Изменения `ttlDays` и `level` применяются к поду ClickHouse при следующем перезапуске, так как оба параметра монтируются через `subPath`, и чарт не выполняет роллинг StatefulSet при изменении ConfigMap.

### Наблюдаемость {#helm-observability}

Чарт включает опциональный стек наблюдаемости (OpenTelemetry Collector, Prometheus, Grafana, Loki и Tempo). Он **отключен по умолчанию**. Чтобы включить его в вашем `values.yaml`:

```yaml
# values.yaml
observability:
  enabled: true
```

При включении Grafana доступна с предварительно настроенными детализациями для логов, трассировок и метрик. Для внешней наблюдаемости оставьте эту функцию отключенной и настройте конечные точки через `server.extraEnv`:

```yaml
# values.yaml
server:
  extraEnv:
    - name: TUIST_OTEL_EXPORTER_OTLP_ENDPOINT
      value: "http://your-otel-collector:4317"
    - name: TUIST_LOKI_URL
      value: "http://your-loki:3100"
```

### Справочник значений {#helm-values-reference}

Полный список настраиваемых значений см. в [`values.yaml`](https://github.com/tuist/tuist/blob/main/infra/helm/tuist/values.yaml) чарта.

## Развертывание {#deployment}

Официальный Docker-образ Tuist доступен по адресу:
```
ghcr.io/tuist/tuist
```

Опубликованный образ включает встроенную обработку сборок для Linux архивов `.xcactivitylog`, поэтому саморазвернутые инстансы могут обрабатывать сборки без запуска дополнительных сервисов — задача Oban `ProcessBuildWorker` выполняется внутри процесса каждого пода сервера. Если вы хотите вынести обработку сборок на отдельный набор реплик (например, чтобы масштабировать пропускную способность парсинга независимо от веб-уровня), установите `processor.enabled: true` в Helm-чарте: чарт развернет тот же образ как потребителя только очереди (`TUIST_PROCESSOR_MODE=true`). Полный набор параметров см. в [`values.yaml`](https://github.com/tuist/tuist/blob/main/infra/helm/tuist/values.yaml).

> [!NOTE]
> Парсинг `.xcresult` опирается на `xcresulttool` из Xcode, поэтому он может выполняться только на macOS. CLI прозрачно обрабатывает это для саморазвернутых инстансов: `tuist test` по умолчанию использует режим обработки **local** для любого сервера, кроме `tuist.dev`, выполняя парсинг xcresult на машине разработчика (где уже установлен Xcode для самой сборки) и загружая структурированные результаты. Результаты тестов принимаются без дополнительной инфраструктуры.

### Загрузка Docker-образа {#pulling-the-docker-image}

Вы можете получить образ, выполнив следующую команду:

```bash
docker pull ghcr.io/tuist/tuist:latest
```

Образ опубликован для архитектур `linux/amd64` и `linux/arm64`, поэтому Docker автоматически выбирает нативную Linux-архитектуру для хоста.

Или загрузите конкретную версию:
```bash
docker pull ghcr.io/tuist/tuist:0.1.0
```

### Развертывание Docker-образа {#deploying-the-docker-image}

Процесс развертывания Docker-образа будет отличаться в зависимости от выбранного облачного провайдера и подхода вашей организации к непрерывному развертыванию. Поскольку большинство облачных решений и инструментов, таких как [Kubernetes](https://kubernetes.io/), используют Docker-образы в качестве базовых единиц, примеры в этом разделе должны хорошо согласовываться с вашей текущей конфигурацией.

> [!WARNING]
> Если вашему пайплайну развертывания нужно проверить, что сервер запущен и работает, вы можете отправить HTTP-запрос `GET` на `/ready` и проверить код состояния `200` в ответе.


#### Fly {#fly}

Для развертывания приложения на [Fly](https://fly.io/) вам потребуется файл конфигурации `fly.toml`. Рассмотрите возможность генерации его динамически в вашем пайплайне непрерывного развертывания (CD). Ниже приведен пример для справки:

```toml
app = "tuist"
primary_region = "fra"
kill_signal = "SIGINT"
kill_timeout = "5s"

[experimental]
  auto_rollback = true

[env]
  # Your environment configuration goes here
  # Or exposed through Fly secrets

[processes]
  app = "/usr/local/bin/hivemind /app/Procfile"

[[services]]
  protocol = "tcp"
  internal_port = 8080
  auto_stop_machines = false
  auto_start_machines = false
  processes = ["app"]
  http_options = { h2_backend = true }

  [[services.ports]]
    port = 80
    handlers = ["http"]
    force_https = true

  [[services.ports]]
    port = 443
    handlers = ["tls", "http"]
  [services.concurrency]
    type = "connections"
    hard_limit = 100
    soft_limit = 80

  [[services.http_checks]]
    interval = 10000
    grace_period = "10s"
    method = "get"
    path = "/ready"
    protocol = "http"
    timeout = 2000
    tls_skip_verify = false
    [services.http_checks.headers]

[[statics]]
  guest_path = "/app/public"
  url_prefix = "/"
```

Затем вы можете выполнить `fly launch --local-only --no-deploy` для запуска приложения. При последующих развертываниях вместо `fly launch --local-only` нужно выполнять `fly deploy --local-only`. Fly.io не позволяет загружать частные Docker-образы, поэтому нам нужно использовать флаг `--local-only`.


## Метрики Prometheus {#prometheus-metrics}

Tuist предоставляет метрики Prometheus по адресу `/metrics`, чтобы помочь вам отслеживать работу вашего собственного экземпляра. Эти метрики включают:

### Метрики HTTP-клиента Finch {#finch-metrics}

Tuist использует [Finch](https://github.com/sneako/finch) в качестве HTTP-клиента и предоставляет подробные метрики о HTTP-запросах:

#### Метрики запросов
- `tuist_prom_ex_finch_request_count_total` — общее количество запросов Finch (счетчик)
  - Метки: `finch_name`, `method`, `scheme`, `host`, `port`, `status`
- `tuist_prom_ex_finch_request_duration_milliseconds` — длительность HTTP-запросов (гистограмма)
  - Метки: `finch_name`, `method`, `scheme`, `host`, `port`, `status`
  - Интервалы: 10 мс, 50 мс, 100 мс, 250 мс, 500 мс, 1 с, 2,5 с, 5 с, 10 с
- `tuist_prom_ex_finch_request_exception_count_total` — общее количество исключений запросов Finch (счетчик)
  - Метки: `finch_name`, `method`, `scheme`, `host`, `port`, `kind`, `reason`

#### Метрики очереди пула соединений
- `tuist_prom_ex_finch_queue_duration_milliseconds` — время ожидания в очереди пула соединений (гистограмма)
  - Метки: `finch_name`, `scheme`, `host`, `port`, `pool`
  - Интервалы: 1 мс, 5 мс, 10 мс, 25 мс, 50 мс, 100 мс, 250 мс, 500 мс, 1 с
- `tuist_prom_ex_finch_queue_idle_time_milliseconds` — время простоя соединения перед использованием (гистограмма)
  - Метки: `finch_name`, `scheme`, `host`, `port`, `pool`
  - Интервалы: 10 мс, 50 мс, 100 мс, 250 мс, 500 мс, 1 с, 5 с, 10 с
- `tuist_prom_ex_finch_queue_exception_count_total` — общее количество исключений очереди Finch (счетчик)
  - Метки: `finch_name`, `scheme`, `host`, `port`, `kind`, `reason`

#### Метрики соединений
- `tuist_prom_ex_finch_connect_duration_milliseconds` — время установления соединения (гистограмма)
  - Метки: `finch_name`, `scheme`, `host`, `port`, `error`
  - Интервалы: 10 мс, 50 мс, 100 мс, 250 мс, 500 мс, 1 с, 2,5 с, 5 с
- `tuist_prom_ex_finch_connect_count_total` — общее количество попыток подключения (счетчик)
  - Метки: `finch_name`, `scheme`, `host`, `port`

#### Метрики отправки
- `tuist_prom_ex_finch_send_duration_milliseconds` — время отправки запроса (гистограмма)
  - Метки: `finch_name`, `method`, `scheme`, `host`, `port`, `error`
  - Интервалы: 1 мс, 5 мс, 10 мс, 25 мс, 50 мс, 100 мс, 250 мс, 500 мс, 1 с
- `tuist_prom_ex_finch_send_idle_time_milliseconds` — время простоя соединения перед отправкой (гистограмма)
  - Метки: `finch_name`, `method`, `scheme`, `host`, `port`, `error`
  - Интервалы: 1 мс, 5 мс, 10 мс, 25 мс, 50 мс, 100 мс, 250 мс, 500 мс

Все метрики-гистограммы предоставляют варианты `_bucket`, `_sum` и `_count` для детального анализа.

### Другие метрики

Помимо метрик Finch, Tuist предоставляет метрики для:
- производительности виртуальной машины BEAM
- метрик пользовательской бизнес-логики (хранилище, учетные записи, проекты и т. д.)
- производительности базы данных (при использовании инфраструктуры, размещенной Tuist)

## Операции {#operations}

Tuist предоставляет набор утилит по адресу `/ops/`, которые можно использовать для управления вашим экземпляром.

> [!WARNING]
> **Авторизация**
>
> Доступ к конечным точкам `/ops/` имеют только пользователи, чей домен электронной почты совпадает с `TUIST_OPERATOR_EMAIL_DOMAIN`. Если переменная не задана, доступ закрыт для всех. Установите значение переменной в домен, почтовые ящики которого вы контролируете.
>
> Пользователь также должен подтвердить контроль над своим адресом: перейдя по ссылке из письма с подтверждением или сбросом пароля, войдя через Google, GitHub или Apple, введя одноразовый код или предъявив подтвержденный адрес электронной почты при входе агента. Учетные записи, подтвержденные автоматически (что является настройкой по умолчанию при отсутствии почтового провайдера), не считаются подтвержденными, пока пользователь не выполнит одно из этих действий. После создания учетной записи подтверждение фиксируется только тогда, когда адрес входит в `TUIST_OPERATOR_EMAIL_DOMAIN`, поэтому после установки или изменения переменной операторам, которые еще не подтвердили свой адрес в этом домене, нужно сделать это снова. Учетные записи, созданные через вход одним из указанных провайдеров или через вход агента, сохраняют подтверждение с момента создания. Без почтового провайдера учетная запись, зарегистрированная с паролем, не может быть связана с одним из таких провайдеров, поэтому создавайте учетные записи операторов, входя через Google, GitHub или Apple, либо настройте почтовый провайдер.
>
> Учетные записи, созданные до появления этой проверки, еще не зафиксировали такое подтверждение, поэтому существующий оператор восстановит доступ после сброса пароля или однократного входа через один из указанных провайдеров.
>
> При первом подтверждении адреса таким способом для учетной записи в домене операторов, у которой еще нет такого подтверждения, Tuist удаляет пароль, ключи доступа и ссылки на провайдеры единого входа организации, а также выполняет выход из браузера и CLI, поскольку тот, кто зарегистрировал адрес, может не быть его владельцем. Сброс пароля для такой учетной записи делает то же самое, за исключением установки нового пароля. Приложение-аутентификатор, настроенное для учетной записи, сохраняется; если оно не принадлежит владельцу, удалите его. Подтвержденные учетные записи вне домена операторов сохраняют свои учетные данные. Владелец продолжает входить через провайдера или устанавливает новый пароль через сброс.
>
> Учетные записи, созданные или переименованные при помощи SCIM-провиженинга, не имеют подтверждения, пока владелец не предоставит его.


- **Ошибки (`/ops/errors`):** Вы можете просматривать непредвиденные ошибки, возникшие в приложении. Это полезно для отладки и понимания причин сбоев. При возникновении проблем мы можем попросить вас поделиться этой информацией с нами.
- **Панель управления (`/ops/dashboard`):** Вы можете просматривать панель управления, которая предоставляет информацию о производительности и состоянии приложения (например, потребление памяти, запущенные процессы, количество запросов). Эта панель помогает понять, достаточно ли ресурсов вашего оборудования для обработки нагрузки.
