# Сервер {#server}

Мы предлагаем версию сервера Tuist для самостоятельного размещения организациям, которым требуется больший контроль над своей инфраструктурой. Эта версия позволяет размещать Tuist на собственной инфраструктуре, обеспечивая безопасность и конфиденциальность ваших данных.

> [!WARNING]
> **Требуется лицензия**
>
> Для самостоятельного размещения Tuist требуется юридически действительная платная лицензия. Версия Tuist для локального развертывания доступна только для организаций на тарифе Enterprise. Если вас интересует эта версия, пожалуйста, свяжитесь с нами по адресу [contact@tuist.dev](mailto:contact@tuist.dev).

> [!WARNING]
> **Устаревший сервис кэширования**
>
> Старая технология узлов кэша для самостоятельного размещения устарела для новых установок. Используйте <.localized_link href="/guides/features/cache/self-hosting">руководство по самостоятельному размещению кэша</.localized_link> для актуальной инфраструктуры кэша.
>
> Существующие развертывания могут по-прежнему обращаться к устаревшей исходной документации в просмотрщике Markdown на GitHub: [узлы кэша](https://github.com/tuist/tuist/blob/main/server/priv/docs/en/guides/cache/self-host.md) и [архитектура кэша](https://github.com/tuist/tuist/blob/main/server/priv/docs/en/guides/cache/architecture.md).

## Частота выпусков {#release-cadence}

Сервер Tuist и сервер кэша Kura поставляются через три канала образов GHCR: **canary** (каждый коммит в `main`), **release candidate** (формируется каждый понедельник, тестируется неделю) и **stable** (повышается до стабильного в следующий понедельник). Только стабильные релизы перемещают тег `:latest` и разрешаются по умолчанию; версии canary и release candidate являются предварительными релизами GitHub, которые вы выбираете, закрепляя их тег. Сервер и Kura выходят синхронно еженедельно, в соответствии с <.localized_link href="/cli/release/channels">графиком выпусков CLI Tuist</.localized_link>.

Мы следуем [семантическому версионированию](https://semver.org/), чтобы обеспечить предсказуемость версий и совместимость. Старшая версия используется для обозначения критических изменений в сервере Tuist, которые потребуют координации с пользователями самостоятельного размещения; вам не следует ожидать, что мы будем часто использовать её, а в случае необходимости будьте уверены, что мы поможем вам сделать переход максимально плавным.

Смотрите страницу <.localized_link href="/guides/server/self-host/release/channels">Каналы выпусков</.localized_link>, чтобы узнать, как формируется каждый канал, как закрепить его в вашем развертывании и какая стратегия рекомендуется для поддержания производства на медленно обновляемой стабильной ветке, пока тестовая среда проверяет предстоящий релиз.

## Обновление сеансов браузера {#browser-session-upgrade}

Сеансы браузера истекают через семь дней без аутентифицированных запросов страниц или взаимодействия с LiveView, но не позднее чем через 30 дней после аутентификации. Опция «Запомнить меня» восстанавливает тот же сеанс на стороне сервера и не может продлить ни один из этих сроков. Активность фиксируется раз в минуту, поэтому неактивный сеанс может истечь на 59 секунд раньше. Heartbeat-сигналы WebSocket, автоматические повторные подключения и фоновые обновления не возобновляют активность. Эти сроки не влияют на учетные данные машин или время жизни токенов API.

Выполните аддитивную миграцию `users_tokens` перед запуском обновленных процессов приложения. Существующие строки не заполняются обратно: время их создания ограничивает период неактивности и абсолютный срок действия, и они должны пройти новую аутентификацию перед доступом к организации с обязательным SSO. Провайдер обратного вызова, эмитент или проверенное рабочее пространство, а также пользовательское подключение SSO хранятся на стороне сервера и сравниваются с текущими настройками организации. Связанный аккаунт не является доказательством аутентификации сеанса.

Обновите каждую веб-реплику перед тем, как считать политику примененной. Старые бинарные файлы все еще могут принимать свои прежние 60-дневные сеансы и не применяют новые границы LiveView; смешанные версии совместимы по схеме, но не эквивалентны по политике. Ожидайте, что пользователям придется войти в систему заново. Откат к старым бинарным файлам ослабляет эти элементы управления; если необходим откат схемы, остановите все бинарные файлы, читающие новые поля, перед их удалением. Никогда не продлевайте старые сеансы и не определяйте источник происхождения, чтобы избежать повторной аутентификации.

## MFA через приложение-аутентификатор {#authenticator-app-mfa}

Сервер включает нативную двухфакторную аутентификацию через приложение-аутентификатор (TOTP). В панели управления пока нет ссылки на неё; точка входа в настройки будет добавлена в более позднем релизе. Она не требует флага активации, зависимости от хостингового сервиса или учетных данных провайдера идентификации: нужны только PostgreSQL, миграция ниже, TOTP-аутентификатор и стабильный ключ шифрования, общий для всех обслуживающих реплик (`TUIST_SECRET_KEY_ENCRYPTION`, с резервом на `TUIST_SECRET_KEY_BASE`). Синхронизируйте часы сервера и аутентификатора. Проверка MFA и общий лимит из пяти неудачных кодов за пять минут используют блокировки строк PostgreSQL, а не Redis.

Настройка требует входа в систему в течение последних пяти минут, ввода ключа настройки в приложение TOTP-аутентификатора и подтверждения кода, сгенерированного приложением. Десять одноразовых кодов восстановления показываются один раз; сохраните их надежно. Отключение фактора также требует недавнего входа в систему и неиспользованного аутентификатора или кода восстановления. Изменения фактора отменяют другие сеансы браузера. Сброс пароля не удаляет MFA, и эта реализация не предоставляет обхода только по электронной почте или через администратора для потерянного фактора.

После регистрации каждый новый вход через браузер, включая федеративный вход, требует нативного второго фактора перед получением сеанса или завершением авторизации CLI/устройства через браузер. Прямой вход по паролю и через Apple API отказывает зарегистрированным пользователям и предписывает им использовать вход через браузер. Новые утверждения почтового агента для зарегистрированных пользователей требуют сеанса браузера с подтвержденной MFA; устаревшие утверждения только по почтовому ящику отклоняются. Существующие токены API, учетные данные машин, идентификаторы рабочих нагрузок и правила их обновления остаются неизменными. Это необязательная поддержка для каждого пользователя, а не обязательное требование MFA для всей организации и не проверка собственной политики MFA провайдера идентификации. Организационный SSO по-прежнему требует правильного настроенного провайдера/эмитента в дополнение к нативному фактору.

Электронная почта не требуется для регистрации, входа в систему, использования кодов восстановления или отключения MFA. Уведомления об изменении фактора отправляются по принципу «best-effort»; ошибка доставки не отменяет выполненное изменение.

Выполните отдельную аддитивную миграцию `user_mfa`/`users_tokens.mfa_verified_at` перед запуском нового бинарного файла. Секрет TOTP использует существующий ключ шифрования Vault; сохраните этот ключ и его резервные копии. Завершите обновление **всех реплик, обслуживающих аутентификацию, прежде чем разрешать регистрацию MFA**. Старые бинарные файлы могут обходить нативную MFA, поэтому они не являются совместимой с политикой целью для отката после регистрации. Удаление схемы MFA уничтожает состояние регистрации и восстановления; сначала остановите процессы чтения и сохраните зашифрованную резервную копию. Совместимость схем смешанных версий не является доказательством того, что применяются элементы управления MFA или сеансами браузера.

## Граница обновления и отката OAuth {#oauth-upgrade-and-rollback-boundary}

Удаление кэша сущностей OAuth требует поэтапного обновления для существующих установок. Перед развертыванием версии, которая прекращает инвалидацию кэша OAuth, сначала разверните релиз совместимости с авторитетным чтением из [#14040](https://github.com/tuist/tuist/pull/14040) на **каждый компонент чтения и записи OAuth**. Этот этап совместимости впервые появляется в линейке релизов **1.355**: `ghcr.io/tuist/tuist:1.355.0-rc.1` содержит его; для производственных развертываний следует использовать стабильный релиз `1.355.x` после его продвижения. Установки версии 1.354 или более ранние должны завершить этот этап перед обновлением до более позднего релиза, содержащего удаление. Сохраняйте линейку 1.355 только для совместимости: не портируйте обратно удаление инвалидации в нее.

Оригинальный коммит совместимости также доступен как `ghcr.io/tuist/tuist:sha-c8e54471a425`. Другой образ подходит в качестве этапа совместимости только если он сохраняет авторитетное чтение **и сохраняет устаревшие инвалидации**, пока существуют старые потребители. Выполните обычные миграции базы данных для этого этапа перед обслуживанием трафика, включая индекс поиска токенов обновления.

Проверьте все веб-реплики, фоновые воркеры, запланированные задачи и отдельно закрепленные образы процессоров в каждой среде. Дождитесь завершения развертывания совместимости и убедитесь, что не осталось бинарных файлов, читающих кэш, перед удалением инвалидаций. Не допускайте, чтобы плавающий тег образа пропустил этот этап во время автоматического обновления. Свежие установки без старых потребителей не нуждаются в промежуточном развертывании.

> [!WARNING]
> **Сохраните цель отката с авторитетным чтением**
>
> После удаления инвалидаций обычный пошаговый откат должен быть направлен на #14040 или другую версию с авторитетным чтением. Сохраненные записи кэша OAuth могут быть устаревшими даже после остановки всех процессов без инвалидации, и перезапущенная реплика, читающая кэш, может импортировать их от peers.
>
> Дальнейший откат требует остановки и дренажа **всех** потребителей OAuth без инвалидации, затем очистки или замены **каждого** сохраненного участника кэша Boruta перед запуском любого потребителя, читающего кэш. Предотвратите повторное подключение сохраненных участников. Дренаж только входящего трафика или перезапуск только веб-реплик недостаточны; согласуйте это восстановление с вашей контактной службой поддержки Tuist, а не очищайте кэши или не выполняйте откат миграций базы данных автоматически.

## Кластеризация нескольких реплик {#multi-replica-clustering}

Поддерживаемые веб-развертывания с несколькими репликами требуют кластеризации Erlang для межрепликовых уведомлений Phoenix PubSub и Oban PG, а не как органа для аутентификации. Chart отвергает несколько реплик, включая автомасштабировщик, который может расти beyond одной реплики, когда `server.cluster.enabled` имеет значение false. Ранее принятые некластеризованные развертывания должны спланировать это обновление, а не обходить защиту. Завершите <.localized_link href="/guides/server/self-host/server#oauth-upgrade-and-rollback-boundary">последовательность обновления OAuth</.localized_link>, включая удаление инвалидаций, перед изменением членства.

Создайте приватный Secret cookie в namespace релиза, используя ваш менеджер секретов, затем настройте его имя и ключ:

```yaml
server:
  replicaCount: 2
  cluster:
    enabled: true
    distributionPort: 9100
    cookieExistingSecret: tuist-server-cluster
    cookieExistingSecretKey: release-cookie
```

Cookie должно иметь высокую энтропию и использоваться всеми участвующими веб-репликами. Никогда не используйте cookie, встроенный в опубликованный образ: владение cookie распределения предоставляет удаленное выполнение на его узлах. Запуск распределенного релиза теперь отказывает в отсутствии приватного `RELEASE_COOKIE` или неверном порте, включая явно настроенный `RELEASE_DISTRIBUTION=name` или `sname` без обнаружения DNS. Развертывания вне chart также должны последовательно настроить `TUIST_CLUSTER_DNS_SERVICE`, `TUIST_CLUSTER_APP_NAME` и IP-адрес подa/имя узла. Обнаружение в настоящее время использует записи A IPv4.

При обычном `helm upgrade`, подключенном к серверу, оставление `cookieExistingSecret` пустым создает Secret cookie и повторно использует его текущее значение при последующих обновлениях. Оффлайн `helm template`, Argo CD и другие рендереры GitOps без поиска активных Secrets не могут сохранить это сгенерированное значение; они должны использовать `cookieExistingSecret`, поддерживаемый отдельно управляемым, стабильным Secret. Не меняйте ключ cookie для неявного ротации активного кластера. Ротация cookie требует скоординированной миграции/перезапуска каждого участника; обновление только Secret не обновляет существующие процессы.

Первый rollout из cookie, встроенных в образ, формирует отдельные острова членства старых/новых версий, пока все веб-реплики не начнут использовать приватный Secret. Запланируйте окно миграции для обновлений в реальном времени. Последующие пошаговые развертывания формируют кластеры смешанных версий, поэтому учитывайте PubSub, уведомления Oban и замену peers across фактических старых/новых версий. Эти уведомления не являются гарантиями надежной доставки. Сохраните образ отката с авторитетным чтением и сохраните тот же приватный cookie при откате совместимой версии.

Разрешите EPMD (TCP 4369) и настроенный порт распределения только между доверенными peers сервера, никогда от рабочих нагрузок арендаторов или публичной сети. Проверьте фактическую изоляцию входящего/исходящего трафика в вашей среде; применение NetworkPolicy не доказывает enforcement или доступность backend. Canary с двумя репликами под непрерывной нагрузкой должен пройти присоединение, пошаговую замену и восстановление после сбоя перед продвижением. DNS используется для обнаружения peers, а не для отключения здоровых узлов при временном сбое или частичном ответе; реальная потеря узлов и предотвращение разделения OTP все еще применяются. libcluster может все еще регистрировать успешную операцию "отключено" для callback сохранения без закрытия соединения; устанавливайте фактическое членство на основе событий включения/выключения узлов или `Node.list()`, а не только этой строки лога.

## Непрерывное развертывание {#continuous-deployment}

Рекомендуем закреплять production на стабильной минорной ветке (например, `ghcr.io/tuist/tuist:1.351`), чтобы ежедневные обновления доставляли только исправления, перенесённые из других веток. Стабильные ветки публикуются каждый понедельник в 06:00 UTC после недельного тестирования в канале release-candidate; staging-среда на canary или на текущем теге release-candidate позволит выявить регрессии до того, как они достигнут ваших пользователей. См. <.localized_link href="/guides/server/self-host/release/channels">Каналы релизов</.localized_link> для рекомендуемой стратегии закрепления версий.

Если вы предпочитаете получать новые возможности по мере их стабилизации без изменения манифестов, закрепите тег `:latest`. Тег обновляется раз в неделю утром в понедельник, поэтому запланируйте окно развертывания соответствующим образом. Ниже приведён пример workflow GitHub Actions, который проверяет и развёртывает последний стабильный образ с такой периодичностью:

```yaml
name: Update Tuist Server
on:
  schedule:
    - cron: '0 8 * * 1' # Mondays 08:00 UTC, after the weekly stable promote
  workflow_dispatch: # Allow manual runs

jobs:
  update:
    runs-on: ubuntu-latest
    steps:
      - name: Check and deploy latest version
        run: |
          # Your deployment commands here
          # Example: docker pull ghcr.io/tuist/tuist:latest
          # Deploy to your infrastructure
```

## Доступ из доверенной сети {#network-trusted-access}

В self-hosted установках можно разрешить разработчикам из доверенной сети отправлять аналитику, использовать кэш или делать и то, и другое без входа в систему. Для доступа к панели управления и администрирования аутентификация по-прежнему требуется.

Включайте только те возможности, которые вам нужны:

| Переменная окружения сервера | Разрешено без входа в систему |
| --- | --- |
| `TUIST_NETWORK_TRUSTED_INSIGHTS_ACCESS=true` | Отправка аналитики сборок и тестов |
| `TUIST_NETWORK_TRUSTED_CACHE_ACCESS=true` | Чтение и запись закэшированных результатов сборки |

Обе настройки **по умолчанию отключены**, независимы друг от друга и применяются ко всему экземпляру для всех аккаунтов и проектов, включая приватные проекты. Они недоступны в hosted Tuist и не заменяют лицензию на self-hosting.

Предыдущее имя `TUIST_NETWORK_TRUSTED_REPORT_PUBLISHING` остаётся совместимым резервным вариантом, если `TUIST_NETWORK_TRUSTED_INSIGHTS_ACCESS` не задана.

> [!WARNING]
> Включайте эти настройки только за границей корпоративной сети или VPN с принудительным контролем. Любой, кто может достичь включённой конечной точки, сможет отправлять отчёты или, при включённом доступе к кэшу, читать и перезаписывать закэшированные результаты. Это допускает подделку телеметрии, отравление кэша и исчерпание ресурсов. Ответы на отчёты также могут раскрывать идентификаторы приватных проектов и используемые системы сборки. Tuist не проверяет членство в VPN и не считает перенаправленные IP-заголовки доказательством членства.

### Настройка экземпляра {#network-trusted-instance-configuration}

1. Ограничьте доступ к серверу Tuist, каждому HTTP/gRPC-слушателю Kura и любому входящему трафику Bazel BES вашей доверенной сетью с помощью фаервола или приватного ingress.
2. Обновите каждую реплику сервера и Kura перед обновлением клиентов. Оставьте аутентификацию Kura включённой с помощью `KURA_AUTH_TUIST_URL` и её учётных данных control-plane; отключение этого параметра обойдёт данные ограничения. Настройте конечную точку кэша, используя <.localized_link href="/guides/features/cache/self-hosting">руководство по self-hosted кэшу</.localized_link>.
3. Установите нужные переменные, указанные выше, на каждой соответствующей реплике сервера Tuist, затем перезапустите или повторно разверните их. Настройка включается только при точном значении `true`. В панели управления нет переключателя, а в Kura — отдельного флага.

### Настройка клиентов {#network-trusted-client-configuration}

Настройте финальный URL self-hosted сервера и проект на каждом совместимом клиенте. Клиенты автоматически определяют, какие возможности включены, когда отсутствуют учётные данные; дополнительная настройка на стороне клиента не требуется. При обнаружении не выполняются редиректы. Существующие учётные данные остаются в использовании, а недействительные или не обновившиеся учётные данные вызывают ошибку, а не переход к анонимному режиму. Чтобы восстановить работу, войдите в систему заново или явно выйдите из неё.

Перед включением доступа к аналитике обновите все инструменты, использующие общие учётные данные, до версий, которые сохраняют повреждённые или отклонённые учётные данные, отвергают нечитаемые каталоги с учётными данными и исключают источники Git из неподписанных отчётов. Старые инструменты могут удалять учётные данные и непреднамеренно разрешать анонимный fallback; обновление только сервера это не исправит. Если сервер не поддерживает обнаружение возможностей или откатывается на более старую версию, клиентам потребуется аутентификация. Прежняя клиентская настройка `TUIST_NETWORK_TRUSTED_PUBLISHING` больше не применяется.

- **Аналитика:** Отправляйте только завершённые отчёты Xcode, Gradle, Elixir/Mix и Bazel, без архивов, вложений, данных покрытия, планирования шардов или доступа к существующим отчётам. Заявления об исполнителе не проверяются; неподписанная телеметрия не формирует доверенные доказательства тестов и не управляет автоматизацией. См. руководства по <.localized_link href="/guides/features/build-insights/xcode#network-trusted-publishing">Xcode</.localized_link>, <.localized_link href="/guides/features/build-insights/gradle#network-trusted-publishing">Gradle</.localized_link> и <.localized_link href="/guides/features/build-insights/elixir#network-trusted-publishing">Elixir</.localized_link> для настройки клиента и сведений о конфиденциальности.
- **Кэш:** Поддерживается кэширование компиляции/модулей через CLI, кэширование Bazel и кэширование задач Gradle. Очистка кэша и загрузка Remote Asset по-прежнему требуют учётных данных. Клиенты без поддержки должны продолжать проходить аутентификацию.
- **Bazel:** Для отправки отчётов требуется явное указание `TUIST_BAZEL_BES_BACKEND` и совместимая версия Kura. Параметры кэша и отчётности включаются независимо. После изменения учётных данных или любой из этих настроек повторно выполните `tuist bazel setup`; для изменений конфигурации кэша компиляции повторно выполните `tuist cache config`.

Запросы на отправку отчётов ограничены 8 МБ, 60 запросами в минуту и 10 000 запросами в день на проект. Настройте общий Valkey для квот на всё развертывание с несколькими репликами; в противном случае лимиты применяются на процесс. Если настроенный общий бэкенд квот недоступен, неподписанные отчёты отклоняются. Также добавьте ограничения на входящие соединения, размер тела запроса и частоту запросов.

### Отключение доступа из доверенной сети {#disable-network-trusted-publishing}

Установите соответствующую переменную в значение `false`, затем перезапустите **каждую соответствующую реплику сервера**. Старые реплики могут продолжать принимать запросы без учётных данных до их замены. Доступ к кэшу для новых запросов прекращается в течение 60 секунд после переключения последней реплики; текущие передачи не отменяются. Если требуется немедленное отзывание прав, сначала заблокируйте трафик на ingress. Существующие отчёты сохраняют обычную видимость и срок хранения, а аутентифицированные клиенты продолжают работать.

### База данных ClickHouse {#clickhouse-database}

Tuist использует [ClickHouse](https://clickhouse.com/) для хранения и запросов больших объемов аналитических данных. ClickHouse **обязателен** для таких возможностей, как аналитика сборок. Вы можете выбрать, размещать ли ClickHouse самостоятельно или использовать их хостинговый сервис.

> [!NOTE]
> **Миграции**
>
> Точка входа Docker-образа автоматически выполняет все ожидающие миграции схемы ClickHouse перед запуском сервиса.

Встроенные конфигурации ClickHouse в Docker Compose и Helm понижают уровень текстового журнала ClickHouse с принятого по умолчанию в образе `trace` до `information`, что является основным источником объема `system.text_log`. Оба варианта также могут ограничивать собственные таблицы операционных журналов `system.*` ClickHouse, которые иначе не имеют ограничений, но по умолчанию эта функция отключена — см. ниже. Во внешних развертываниях ClickHouse следует настраивать эти операционные журналы непосредственно в сервисе ClickHouse.

#### Топология репликации ClickHouse {#clickhouse-replication-topology}

Многорепликационный ClickHouse за Tuist поддерживается только в ClickHouse Cloud. Самостоятельно управляемый ClickHouse работает с одной репликой.

Миграции приема данных создают движок `MergeTree`. В Cloud он прозрачно становится `SharedMergeTree`, поэтому запись выполняется в общее объектное хранилище, и любое количество реплик работает корректно. В самостоятельно управляемом ClickHouse `MergeTree` пишет на локальный диск только одной реплики; многорепликационная настройка либо незаметно разделит прием данных между репликами, либо отклонит CREATE с ошибкой `UNKNOWN_STORAGE: Only tables with a Replicated engine or tables which do not store data on disk are allowed in a Replicated database.` в зависимости от того, как у подключенного пользователя настроен параметр `database_replicated_allow_only_replicated_engine`.

Запускайте один шард с одной репликой в самостоятельно управляемом ClickHouse и регулярно создавайте резервные копии каталога данных ClickHouse. Если узел будет потерян, второй реплики для восстановления не будет.

#### Ограничение срока хранения операционных журналов {#capping-operational-log-retention}

Срок хранения можно применить к `system.text_log`, `system.query_log`, `system.query_thread_log`, `system.query_views_log`, `system.trace_log`, `system.metric_log`, `system.asynchronous_metric_log` и `system.part_log`.

Включение этой функции — одноразовое необратимое действие для экземпляра, в котором уже есть данные, поэтому ни один из пакетов не делает этого за вас. Любое окно хранения приводит к тому, что определения этих таблиц перестают соответствовать их конфигурации, поэтому ClickHouse переименовывает каждую из них и создает новую таблицу, как описано в разделе [замещенные таблицы журналов](#superseded-log-tables). Оставленная версия содержит все накопленные на данный момент данные и не имеет собственного срока хранения, поэтому, если вы не освободите место на том же шаге, она останется на диске навсегда, а новое окно будет ограничивать только строки, записанные с этого момента. Включите обе настройки вместе:

```yaml
clickhouse:
  embedded:
    systemLogs:
      ttlDays: 14
      supersededTables: delete
```

Эта единственная операция `helm upgrade` самодостаточна, потому что изменение `ttlDays` с пустого значения на заданное добавляет монтирование drop-in и перезапускает под ClickHouse: он перезагружается, замещает таблицы, а затем задание после обновления удаляет их. Развертывайте с помощью `helm upgrade --wait`, чтобы под был перезапущен до запуска задания; в противном случае версии появятся после того, как задание уже проверило состояние, и следующее `helm upgrade` освободит место вместо него.

В Docker Compose раскомментируйте том `clickhouse-log-ttl.xml` для сервиса `clickhouse` в файле `docker-compose.yml` и установите обе переменные в `.env`:

```bash
CLICKHOUSE_SYSTEM_LOG_TTL_DAYS=14
CLICKHOUSE_SUPERSEDED_LOG_TABLES=delete
```

После освобождения места вы можете вернуть `supersededTables`/`CLICKHOUSE_SUPERSEDED_LOG_TABLES` к значению `ignore`, чтобы последующее обновление ClickHouse не удаляло историю самостоятельно.

#### Замещенные таблицы журналов {#superseded-log-tables}

При запуске ClickHouse проверяет, соответствует ли каждая системная таблица журналов своей конфигурации. Если нет, он переименовывает существующую таблицу в `system.<name>_0`, затем в `_1`, `_2` и так далее, и создает новую. Это происходит при изменении окна хранения и при любом обновлении ClickHouse, которое изменяет схему системного журнала.

Переименование таблицы не копирует ее данные, поэтому дополнительное место на диске не требуется. Что происходит с замещенной таблицей afterward, зависит от исходной таблицы, так как она сохраняет тот срок хранения, который был у активной таблицы в момент замещения. При первом включении хранения у замещаемой таблицы его нет, поэтому она хранит всю накопленную историю бессрочно. Последующее изменение окна замещает таблицу, которая уже имеет TTL, поэтому такие данные истекают сами по себе, оставляя пустую таблицу. ClickHouse никогда не удаляет сами таблицы, поэтому на долгоживущем экземпляре они накапливаются в любом случае.

Замещенные таблицы сохраняются по умолчанию, чтобы обновление никогда не удаляло операционную историю самостоятельно. Установите политику в `delete`, чтобы удалять их, что происходит при `docker compose up` и каждом `helm upgrade`:

```bash
CLICKHOUSE_SUPERSEDED_LOG_TABLES=delete
```

В чарте Helm настройте ту же политику как значение:

```yaml
clickhouse:
  embedded:
    systemLogs:
      supersededTables: delete
```

Удаление замещенной таблицы освобождает занимаемое ею место на диске. Активная таблица не затрагивается, как и строки, записанные после ее замещения.

Чтобы освободить место один раз без изменения политики, удалите таблицы вручную:

```sql
SELECT name FROM system.tables WHERE database = 'system' AND match(name, '_log_[0-9]+$');
DROP TABLE IF EXISTS system.text_log_0 SYNC;
```

База данных `system` использует движок `Atomic`, который откладывает обычное `DROP TABLE` на время, заданное параметром `database_atomic_delay_before_drop_table_sec` (по умолчанию восемь минут). `SYNC` удаляет данные немедленно, что необходимо, когда вы удаляете их из-за заполнения диска.


### Хранилище {#storage}

Вам также понадобится решение для хранения файлов (например, бинарных файлов фреймворков и библиотек). Сервер Tuist поддерживает S3-совместимые хранилища и Azure Blob Storage для артефактов, принадлежащих серверу.

> [!TIP]
> **Оптимизированное кэширование**
>
> Если ваша основная цель — снизить задержку кэша, вам может не потребоваться самостоятельное размещение всего сервера. Вы можете развернуть узлы Kura с самостоятельным размещением близко к вашей сети CI или разработчиков и подключить их к хостинговому серверу Tuist или вашему самостоятельно размещенному серверу.
>
> См. <.localized_link href="/guides/cache/self-host">руководство по самостоятельному размещению кэша</.localized_link>.


### Узлы Kura с самостоятельным размещением {#self-hosted-cache-nodes}

Чтобы использовать узлы Kura с самостоятельным размещением вместе с самостоятельно размещенным сервером Tuist:

1. Настройте `KURA_CONTROL_PLANE_CLIENT_ID` и `KURA_CONTROL_PLANE_CLIENT_SECRET` на сервере Tuist. Идентификатор клиента **должен быть UUID**. Сгенерируйте UUID и случайный секрет с помощью команд из <.localized_link href="/guides/cache/self-host#control-plane-client">руководства по самостоятельному размещению кэша</.localized_link> и сохраните их в секретах вашего развертывания.
2. Разверните узлы Kura, следуя <.localized_link href="/guides/cache/self-host">руководству по самостоятельному размещению кэша</.localized_link>, используя те же учетные данные плоскости управления.
3. Настройте каждый узел Kura с помощью `KURA_REGISTRATION_URL` и `KURA_ADVERTISED_HTTP_URL`. Heartbeat-сигналы регистрации сообщают серверу, какие готовые конечные точки Kura, обращенные к клиенту, он может рекламировать CLI.

## Конфигурация {#configuration}

Конфигурация сервиса выполняется во время выполнения через переменные окружения. Учитывая чувствительный характер этих переменных, мы рекомендуем шифровать их и хранить в защищенных решениях для управления паролями. Будьте уверены, Tuist обращается с этими переменными с особой осторожностью, гарантируя, что они никогда не отображаются в логах.

> [!NOTE]
> **Проверки при запуске**
>
> Необходимые переменные проверяются при запуске. Если какие-либо из них отсутствуют, запуск завершится ошибкой, а сообщение об ошибке укажет на отсутствующие переменные.


### Конфигурация лицензии {#license-configuration}

Как пользователь on-premise решения, вы получите лицензию, которую нужно будет передать в виде переменной окружения. Лицензия используется для проверки развертывания и обеспечения того, что сервис работает в рамках условий соглашения.

| Переменная окружения | Описание | Обязательно | По умолчанию | Пример |
| --- | --- | --- | --- | --- |
| `TUIST_LICENSE` | Лицензия, предоставляемая после подписания соглашения об уровне обслуживания. Принимает либо стандартный ключ лицензии, либо сертификат в кодировке base64, используемый в изолированных средах, где сервер не может обращаться к внешним сервисам. | Да | | `******` |

> [!WARNING]
> **Срок действия**
>
> У лицензий есть срок действия. Пользователи получат предупреждение при использовании команд Tuist, взаимодействующих с сервером, если срок действия лицензии истекает менее чем через 30 дней. Если вы хотите продлить лицензию, пожалуйста, свяжитесь с [contact@tuist.dev](mailto:contact@tuist.dev).

### Конфигурация базы данных {#database-configuration}

Следующие переменные окружения используются для настройки подключения к базе данных:

| Переменная окружения | Описание | Обязательно | По умолчанию | Пример |

| `TUIST_CLICKHOUSE_BUFFER_POOL_SIZE` | Количество процессов буферизации ClickHouse для запуска | Нет | `5` | `5` |

По умолчанию Tuist шифрует подключение к базе данных, но не проверяет сертификат сервера, поэтому злоумышленник в сетевом пути может выдать себя за базу данных. Установите `TUIST_DATABASE_SSL_VERIFY=1`, чтобы включить проверку. Если ваш провайдер подписывает сертификаты собственным CA, как это делают Amazon RDS и Google Cloud SQL, скачайте его пакет CA, смонтируйте его в контейнере и укажите на него в `TUIST_DATABASE_SSL_CA_CERT_FILE`. Хост в `DATABASE_URL` должен совпадать с именем или IP-адресом в сертификате. При включенной проверке сертификат, не прошедший эти проверки, приведет к сбою каждого подключения к базе данных, поэтому после включения проверьте журналы сервера на наличие `Bad Certificate` или `Unknown CA`.

Когда `TUIST_DATABASE_SCHEMA` не равно `public`, миграции релиза создают схему, если она еще не существует, перед запуском цепочки миграций Ecto. Если роль миграции не может создавать схемы, создайте схему заранее и сделайте роль миграции ее владельцем.

Tuist направляет подключение к пользовательской схеме, устанавливая `search_path` сессии. Некоторые конфигурации Postgres с пулингом или проксированием (например, PgBouncer или управляемые базы данных, ограничивающие параметры запуска) не применяют это, и сессия возвращается к `public`, что проявляется во время миграций как `permission denied for schema public`. При подключении через такую конфигурацию закрепите схему за самой ролью, чтобы каждая сессия начиналась в ней независимо от прокси:

```sql
CREATE SCHEMA IF NOT EXISTS tuist AUTHORIZATION <migration_role>;
ALTER ROLE <migration_role> IN DATABASE <database> SET search_path = tuist;
-- If the web server connects as a separate runtime role (TUIST_DATABASE_RUNTIME_ROLE):
ALTER ROLE <runtime_role> IN DATABASE <database> SET search_path = tuist;
```

### Конфигурация окружения аутентификации {#authentication-environment-configuration}

Мы обеспечиваем аутентификацию через [провайдеров удостоверений (IdP)](https://en.wikipedia.org/wiki/Identity_provider). Чтобы использовать это, убедитесь, что все необходимые переменные окружения для выбранного провайдера присутствуют в окружении сервера. **Отсутствие переменных** приведет к тому, что Tuist пропустит этого провайдера.

#### Электронная почта и пароль {#email-and-password}

Вход по электронной почте и паролю и самостоятельная регистрация встроены и включены по умолчанию. В экземпляре, где требуется использование провайдера удостоверений (например, при принудительном использовании SSO), вы можете полностью отключить их. Это удалит форму ввода электронной почты/пароля, ссылку на регистрацию и процесс сброса пароля из процесса входа, а также закроет все соответствующие серверные конечные точки, включая конечную точку электронной почты/пароля, используемую CLI (`tuist auth`).

| Переменная окружения | Описание | Обязательно | По умолчанию | Пример |
| --- | --- | --- | --- | --- |
| `TUIST_EMAIL_AUTH_ENABLED` | Можно ли использовать электронную почту и пароль для входа и регистрации. Установите значение `0`, чтобы удалить форму ввода электронной почты/пароля, ссылку на регистрацию и процесс сброса пароля со страницы входа и закрыть соответствующие серверные конечные точки. | Нет | `1` | `0` |

#### Отключение настроенного провайдера удостоверений {#disabling-a-configured-identity-provider}

По умолчанию провайдер отображается как вариант входа, когда он настроен. Чтобы оставить провайдер настроенным (его учетные данные остаются установленными), но убрать его со страниц входа и регистрации, установите соответствующий переключатель в `0`. Для GitHub, Google и Apple это также закрывает обратный вызов входа, поэтому метод становится полностью недоступным.

| Переменная окружения | Описание | Обязательно | По умолчанию | Пример |
| --- | --- | --- | --- | --- |
| `TUIST_GITHUB_AUTH_ENABLED` | Можно ли использовать GitHub для входа (см. раздел [GitHub](#github), чтобы узнать, почему приложение использует одни и те же учетные данные для входа) | Нет | `1` | `0` |
| `TUIST_GOOGLE_AUTH_ENABLED` | Можно ли использовать Google для входа | Нет | `1` | `0` |
| `TUIST_OKTA_AUTH_ENABLED` | Отображается ли настроенный провайдер Okta как вариант входа | Нет | `1` | `0` |
| `TUIST_APPLE_AUTH_ENABLED` | Можно ли использовать Apple для входа | Нет | `1` | `0` |

#### GitHub {#github}

Мы рекомендуем аутентифицироваться с помощью [приложения GitHub](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/about-creating-github-apps), но вы также можете использовать [приложение OAuth](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/creating-an-oauth-app). Убедитесь, что все необходимые переменные окружения, указанные GitHub, присутствуют в окружении сервера. Отсутствие переменных приведет к тому, что Tuist проигнорирует аутентификацию через GitHub. Чтобы правильно настроить приложение GitHub:
- В общих настройках приложения GitHub:
    - Скопируйте `Client ID` и установите его как `TUIST_GITHUB_APP_CLIENT_ID`
    - Создайте и скопируйте новый `client secret`, затем установите его как `TUIST_GITHUB_APP_CLIENT_SECRET`
    - Установите `Callback URL` как `http://YOUR_APP_URL/users/auth/github/callback`. `YOUR_APP_URL` также может быть IP-адресом вашего сервера.
- Требуются следующие разрешения:
  - Репозитории:
    - Запросы на слияние: чтение и запись
  - Аккаунты:
    - Адреса электронной почты: только чтение

В разделе `Account permissions` настроек `Permissions and events` установите разрешение `Email addresses` на значение `Read-only`.

Затем вам нужно будет сделать доступными следующие переменные окружения в среде, где работает сервер Tuist:

| Переменная окружения | Описание | Обязательно | По умолчанию | Пример |
| --- | --- | --- | --- | --- |
| `TUIST_GITHUB_APP_CLIENT_ID` | Идентификатор клиента приложения GitHub | Да | | `Iv1.a629723000043722` |
| `TUIST_GITHUB_APP_CLIENT_SECRET` | Секрет клиента приложения | Да | | `232f972951033b89799b0fd24566a04d83f44ccc` |
| `TUIST_GITHUB_AUTH_ENABLED` | Можно ли использовать GitHub для входа. Приложение GitHub, которое вы настраиваете для интеграций с платформой (комментарии к PR и т. д.), использует те же клиентские учетные данные для входа, поэтому оно отображается как вариант входа. Установите значение `0`, чтобы сохранить приложение, но убрать GitHub со страницы входа. | Нет | `1` | `0` |

#### Google {#google}

Вы можете настроить аутентификацию через Google, используя [OAuth 2](https://developers.google.com/identity/protocols/oauth2). Для этого вам нужно создать новые учетные данные типа «Идентификатор клиента OAuth». При создании учетных данных выберите «Веб-приложение» в качестве типа приложения, назовите его `Tuist` и установите URI перенаправления в `{base_url}/users/auth/google/callback`, где `base_url` — это URL-адрес, по которому работает ваш размещенный сервис. После создания приложения скопируйте идентификатор клиента и секрет и установите их как переменные окружения `GOOGLE_CLIENT_ID` и `GOOGLE_CLIENT_SECRET` соответственно.

> [!NOTE]
> **Области действия экрана согласия**
>
> Возможно, вам потребуется создать экран согласия. При этом обязательно добавьте области действия `userinfo.email` и `openid` и отметьте приложение как внутреннее.


#### Okta {#okta}

Вы можете включить аутентификацию через Okta с помощью протокола [OAuth 2.0](https://oauth.net/2/). Вам нужно будет [создать приложение](https://developer.okta.com/docs/en/guides/implement-oauth-for-okta/main/#create-an-oauth-2-0-app-in-okta) в Okta, следуя <.localized_link href="/guides/integrations/authentication/sso#okta">этим инструкциям</.localized_link>.

После получения идентификатора клиента и секрета при настройке приложения Okta вам нужно будет установить следующие переменные окружения:

| Переменная окружения | Описание | Обязательно | По умолчанию | Пример |
| --- | --- | --- | --- | --- |
| `TUIST_OKTA_1_CLIENT_ID` | Идентификатор клиента для аутентификации в Okta. Число должно быть вашим идентификатором организации | Да | | |
| `TUIST_OKTA_1_CLIENT_SECRET` | Секрет клиента для аутентификации в Okta | Да | | |

Число `1` нужно заменить на идентификатор вашей организации. Обычно это 1, но проверьте в своей базе данных.

### Конфигурация хранилища {#storage-environment-configuration}

 Tuist требуется хранилище для артефактов, загружаемых через API. Для эффективной работы Tuist **необходимо настроить одно из поддерживаемых решений для хранения**.

| `TUIST_OBJECT_STORAGE_PROVIDER` | Бэкенд для хранения артефактов сервера. Используйте `s3` для хранилища, совместимого с S3, или `azure_blob` для Azure Blob Storage | Нет | `s3` | `azure_blob` |

Вы можете использовать любого провайдера хранилища, совместимого с S3, для хранения артефактов. Для аутентификации и настройки интеграции с провайдером хранилища требуются следующие переменные окружения:

| `TUIST_S3_SECRET_ACCESS_KEY` или `AWS_SECRET_ACCESS_KEY` | Секретный ключ доступа для аутентификации у провайдера хранилища | Да | | `wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY` |

| `TUIST_S3_ENDPOINT` или `AWS_ENDPOINT` | Эндпоинт провайдера хранилища | Да | | `https://s3.us-west-2.amazonaws.com` |

#### Хранение артефактов {#artifact-retention}

Очистка артефактов по умолчанию отключена на самостоятельно размещаемых экземплярах. Для каждого поддерживаемого типа артефактов предусмотрена своя переменная окружения. Установите значение переменной в положительное целое число дней, чтобы включить очистку для этого типа артефактов. Если переменная не задана или пуста, очистка отключается только для соответствующего типа артефактов.

```bash
TUIST_CACHE_ARTIFACT_RETENTION_DAYS=30
TUIST_APP_PREVIEW_RETENTION_DAYS=30
TUIST_BUILD_ARCHIVE_RETENTION_DAYS=60
TUIST_RUN_ARTIFACT_RETENTION_DAYS=30
TUIST_TEST_ATTACHMENT_RETENTION_DAYS=30
TUIST_SHARD_BUNDLE_RETENTION_DAYS=14
```

В Helm-чарте настройте те же периоды в виде карты:

```yaml
server:
  artifactRetentionDays:
    cacheArtifacts: 30
    appPreviews: 30
    buildArchives: 60
    runArtifacts: 30
    testAttachments: 30
    shardBundles: 14
```

Все шесть ключей необязательны. В этом примере включены все поддерживаемые типы артефактов с независимыми периодами хранения. Пропустите ключ или оставьте его значение пустым, чтобы сохранить очистку отключенной для этого типа артефактов. Для самостоятельно размещаемых экземпляров нет ограничения в 30 дней на максимальный период хранения. Значения, которые не являются положительными целыми числами, приведут к ошибке запуска сервера.

Перезапустите сервер после изменения переменной хранения. Каждая поставленная в очередь задача очистки на самостоятельно размещаемом экземпляре проверяет текущую конфигурацию перед удалением файлов, поэтому снятие значения переменной, установка пустого значения или увеличение периода хранения также защищает файлы от ожидающих задач после перезапуска.

| Переменная окружения | Файлы артефактов, удаляемые из объектного хранилища |
| --- | --- |
| `TUIST_CACHE_ARTIFACT_RETENTION_DAYS` | Кэш Xcode, устаревший кэш с адресацией по содержимому, кэш модулей и файлы кэша Gradle |
| `TUIST_APP_PREVIEW_RETENTION_DAYS` | Сборки предварительного просмотра приложений и иконки |
| `TUIST_BUILD_ARCHIVE_RETENTION_DAYS` | Текущие и устаревшие архивы сборок |
| `TUIST_RUN_ARTIFACT_RETENTION_DAYS` | Все объекты, хранящиеся под префиксом артефактов истекшего запуска, включая пакеты результатов, записи вызовов и архивы сессий |
| `TUIST_TEST_ATTACHMENT_RETENTION_DAYS` | Вложения запусков тестов |
| `TUIST_SHARD_BUNDLE_RETENTION_DAYS` | Пакеты шардов тестов |

Запланированная очистка удаляет только блобы артефактов. Она сохраняет соответствующие строки в PostgreSQL и ClickHouse, поэтому метаданные сборок, тестов, запусков, предварительных просмотров и шардов могут оставаться видимыми в дашбордах после истечения срока загрузки. Эта конфигурация не изменяет правила хранения таблиц ClickHouse.

### Настройка электронной почты {#email-configuration}

Tuist требует функциональности электронной почты для аутентификации пользователей и транзакционных уведомлений (например, сброс пароля, уведомления об аккаунте). В настоящее время **поддерживается только Mailgun** в качестве провайдера электронной почты.

| Переменная окружения | Описание | Обязательно | По умолчанию | Пример |
| --- | --- | --- | --- | --- |
| `TUIST_MAILGUN_API_KEY` | API-ключ для аутентификации в Mailgun | Да* | | `key-1234567890abcdef` |
| `TUIST_MAILING_DOMAIN` | Домен, с которого будут отправляться письма | Да* | | `mg.tuist.io` |
| `TUIST_MAILING_FROM_ADDRESS` | Адрес электронной почты, который будет отображаться в поле «От» | Да* | | `noreply@tuist.io` |
| `TUIST_MAILING_REPLY_TO_ADDRESS` | Необязательный адрес для ответов пользователей | Нет | | `support@tuist.dev` |
| `TUIST_SKIP_EMAIL_CONFIRMATION` | Пропускать подтверждение электронной почты при регистрации новых пользователей. При включении пользователи автоматически подтверждаются и могут войти сразу после регистрации | Нет | `true`, если электронная почта не настроена, `false`, если электронная почта настроена | `true`, `false`, `1`, `0` |

\* Переменные настройки электронной почты требуются только если вы хотите отправлять письма. Если они не настроены, подтверждение электронной почты автоматически пропускается

> [!NOTE]
> **Поддержка SMTP**
>
> Общая поддержка SMTP в настоящее время недоступна. Если вам нужна поддержка SMTP для вашего локального развертывания, пожалуйста, свяжитесь с [contact@tuist.dev](mailto:contact@tuist.dev), чтобы обсудить ваши требования.


> [!NOTE]
> **Развертывания в изолированной среде**
>
> Для локальных установок без доступа к интернету или настройки провайдера электронной почты подтверждение по электронной почте автоматически пропускается. Пользователи могут войти сразу после регистрации. Если электронная почта настроена, но вы всё равно хотите пропустить подтверждение, установите `TUIST_SKIP_EMAIL_CONFIRMATION=true`. Чтобы требовать подтверждение по электронной почте при её настройке, установите `TUIST_SKIP_EMAIL_CONFIRMATION=false`.

> [!NOTE]
> **Квоты на электронную почту и ссылки для сброса пароля**
>
> При настройке электронной почты приглашения (созданные, массовые или отправленные повторно) ограничены одним письмом на получателя каждые пять минут и пакетами по 50 писем с пополнением до 50 в час на организацию и на отправителя приглашений. Отмена приглашения не восстанавливает лимит, а API приглашений отвечает на исчерпанный лимит кодом `429` и заголовком `Retry-After`. При наличии нескольких реплик настройте общий Valkey для квот в рамках всего развертывания; если он настроен, но недоступен, письма с приглашениями отклоняются. Ссылки для сброса пароля истекают через 15 минут.


### Настройка Git-платформы {#git-platform-configuration}

Tuist может <.localized_link href="/guides/server/authentication">интегрироваться с Git-платформами</.localized_link>, чтобы предоставлять дополнительные возможности, такие как автоматическое добавление комментариев в ваши pull-запросы.

#### GitHub {#platform-github}

Самостоятельно размещаемый сервер Tuist не может установить GitHub App, работающий на `https://tuist.dev`. GitHub Apps привязаны к серверу, который их зарегистрировал, поэтому вашему развертыванию нужно собственное приложение на github.com.

##### Регистрация приложения {#platform-github-registering-the-app}

[Создайте GitHub App](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/about-creating-github-apps), принадлежащий вашей организации на GitHub. Вы можете повторно использовать приложение, созданное для аутентификации, если только это не было OAuth-приложение. Настройте его следующим образом, заменив `YOUR_APP_URL` значением `TUIST_APP_URL`:

| Параметр | Значение |
| --- | --- |
| URL-адреса обратного вызова | `YOUR_APP_URL/users/auth/github/callback` и `YOUR_APP_URL/integrations/github/authorize` |
| URL-адрес настройки | `YOUR_APP_URL/integrations/github/setup` |
| Перенаправление при обновлении | Включено |
| URL-адрес вебхука | `YOUR_APP_URL/webhooks/github` |
| Секрет вебхука | Любая случайная строка. Вы установите её как `TUIST_GITHUB_APP_WEBHOOK_SECRET` |

Предоставьте следующие разрешения для репозиториев:

| Разрешение | Доступ |
| --- | --- |
| Содержимое | Только чтение |
| Метаданные | Только чтение |
| Задачи (Issues) | Чтение и запись |
| Pull-запросы | Чтение и запись |
| Проверки (Checks) | Чтение и запись |

Также предоставьте разрешение организации **Участники: только чтение**. Во время настройки на github.com Tuist проверяет, что человек, подключающий установку для организации, является активным владельцем организации на GitHub, а не просто пользователем с доступом к одному из её репозиториев.

Подпишите приложение на события `Check run`, `Pull request` и `Issue comment`.

Оставьте опцию **Запрашивать авторизацию пользователя (OAuth) во время установки** отключенной, чтобы GitHub отправлял установщиков на URL-адрес настройки. Tuist запускает отдельный шаг авторизации, используя дополнительный обратный вызов `/integrations/github/authorize` для проверки владения установкой. Когда установка начинается на GitHub, установщик затем выбирает организацию Tuist. Установки в организации на GitHub всегда показывают этот выбор; установки, начатые в Tuist, сохраняют свою организацию.

##### Настройка сервера {#platform-github-configuring-the-server}

Установите следующие переменные окружения, затем перезапустите сервер:

| Переменная окружения | Описание | Обязательно | По умолчанию | Пример |
| --- | --- | --- | --- | --- |
| `TUIST_GITHUB_APP_NAME` | Слаг приложения, который является последним компонентом пути его публичного URL-адреса `https://github.com/apps/<slug>` | Да | | `my-company-tuist` |
| `TUIST_GITHUB_APP_ID` | Числовой идентификатор приложения, используемый для проверки владения установкой | Да | | `123456` |
| `TUIST_GITHUB_APP_CLIENT_ID` | Client ID приложения GitHub | Да | | `Iv1.a629723000043722` |
| `TUIST_GITHUB_APP_CLIENT_SECRET` | Client Secret приложения | Да | | `232f972951033b89799b0fd24566a04d83f44ccc` |
| `TUIST_GITHUB_APP_PRIVATE_KEY_BASE64` | Закрытый ключ приложения GitHub в кодировке base64. Предпочтительнее, чем `TUIST_GITHUB_APP_PRIVATE_KEY`, так как он чувствителен к тому, как ваша платформа обрабатывает переносы строк | Да | | `LS0tLS1CRUdJTiBSU0EgUFJJVkFUR...` |
| `TUIST_GITHUB_APP_WEBHOOK_SECRET` | Секрет вебхука, настроенный в приложении GitHub | Нет | | `a4c1e0f2b8d6...` |

> [!IMPORTANT]
> **Настройте все необходимые учетные данные приложения**
>
> Кнопка **Установить приложение GitHub** на странице интеграций организации остается неактивной, пока не будут установлены `TUIST_GITHUB_APP_NAME`, `TUIST_GITHUB_APP_CLIENT_ID`, `TUIST_GITHUB_APP_CLIENT_SECRET` и закрытый ключ. Числовой `TUIST_GITHUB_APP_ID` также необходим для проверки владения установкой. URL-адрес установки содержит слаг приложения, поэтому отсутствие `TUIST_GITHUB_APP_NAME` в частности приводит к тому, что GitHub отвечает ошибкой 404.

После перезапуска сервера администраторы организации устанавливают приложение и подключают репозитории к проектам, следуя <.localized_link href="/guides/integrations/gitforge/github">руководству по интеграции с GitHub</.localized_link>.

##### Аутентификация OIDC зависит от этого {#platform-github-oidc}

<.localized_link href="/guides/server/authentication#oidc-tokens">Аутентификация OIDC</.localized_link> сопоставляет утверждение о репозитории в токене CI с репозиториями, подключенными к вашим проектам, и соединение может быть создано только через установленное приложение GitHub. Завершите настройку выше, прежде чем ваши рабочие процессы CI начнут аутентифицироваться с помощью OIDC.

Вашему серверу Tuist также необходим исходящий доступ к эмитенту OIDC вашего провайдера CI для получения его ключей подписи:

| Провайдер CI | Хост |
| --- | --- |
| GitHub Actions | `token.actions.githubusercontent.com` |
| CircleCI | `oidc.circleci.com` |
| Bitrise | `token.builds.bitrise.io` |

##### GitHub Enterprise Server {#platform-github-enterprise-server}

Переменные окружения выше настраивают только приложение Tuist для github.com. Чтобы интегрировать Tuist вместо этого с экземпляром GitHub Enterprise Server (GHES), администраторы организации переходят на вкладку **Корпоративный сервер** на странице интеграций и вводят базовый URL-адрес GHES — Tuist проводит их через [процесс регистрации приложения через манифест](https://docs.github.com/en/apps/sharing-github-apps/registering-a-github-app-from-a-manifest) GitHub для регистрации нового приложения Tuist на их экземпляре GHES. Учетные данные нового приложения хранятся в зашифрованном виде для каждой установки; дополнительные переменные окружения `TUIST_GITHUB_APP_*` не требуются.

#### Origin {#platform-origin}

Самостоятельно размещаемому серверу Tuist требуется собственное приложение Origin, настроенное с URL-адресами вашего развертывания и ключом подписи. Зарегистрируйте отдельное приложение для каждой среды Tuist, чтобы установки и учетные данные оставались независимыми.

##### Регистрация приложения {#platform-origin-registering-the-app}

1. Сгенерируйте пару ключей подписи Ed25519 с помощью OpenSSL с поддержкой Ed25519:

   ```sh
   umask 077
   openssl genpkey -algorithm ED25519 -out origin-app-private.pem
   openssl pkey -in origin-app-private.pem -pubout -out origin-app-public.pem
   ```

2. Создайте приложение в [настройках приложения Origin](https://cursor.com/codebase/settings/apps). Зарегистрируйте содержимое `origin-app-public.pem` в качестве его открытого ключа подписи. Храните `origin-app-private.pem` в секрете; вы предоставите его серверу Tuist, а не загрузите в Cursor.
3. Настройте следующие параметры, заменив `YOUR_APP_URL` базовым HTTPS-URL-адресом вашего развертывания Tuist:

   | Параметр | Значение |
   | --- | --- |
   | URL-адрес главной страницы | `YOUR_APP_URL` |
   | URI перенаправления | `YOUR_APP_URL/integrations/origin/setup` |
   | URL-адрес вебхука | `YOUR_APP_URL/webhooks/origin` |

4. Скопируйте зарегистрированный идентификатор приложения, который начинается с `app_`.

Во время установки Tuist запрашивает следующие разрешения:

| Область действия | Используется для |
| --- | --- |
| `repository:pull_requests:read` | Поиск pull-запросов и их текущего head-коммита. |
| `repository:pull_requests:reviews:write` | Чтение, публикация и обновление комментариев к отчетам. Origin включает соответствующее разрешение на чтение ревью. |
| `repository:metadata:read` | Обнаружение репозиториев и чтение их веток по умолчанию. Предоставляется автоматически Origin. |

Не выбирайте необязательные события вебхуков репозитория. Уведомлений о жизненном цикле установки достаточно; доступ к исходному коду, разрешения на слияние и разрешения на запуск проверок не требуются.

##### Настройка сервера {#platform-origin-configuring-the-server}

Задайте следующие переменные окружения, затем перезапустите сервер:

| Переменная окружения | Описание | Обязательно | По умолчанию | Пример |
| --- | --- | --- | --- | --- |
| `TUIST_ORIGIN_APP_ID` | Идентификатор приложения, скопированный из настроек приложения Origin. | Да | | `app_...` |
| `TUIST_ORIGIN_APP_PRIVATE_KEY` | Полное содержимое `origin-app-private.pem`, включая строки `BEGIN PRIVATE KEY` и `END PRIVATE KEY` и все переносы строк. | Да | | `-----BEGIN PRIVATE KEY-----...` |

Храните закрытый ключ в менеджере секретов вашего развертывания. Сохраняйте его многострочный формат PEM; этот параметр не принимает замену в кодировке base64. Никогда не фиксируйте ключ в системе контроля версий и не раскрывайте его в логах. Обе переменные должны принадлежать одному и тому же зарегистрированному приложению.

Вашему серверу Tuist необходим исходящий HTTPS-доступ к `api.cursor.com`. Cursor должен иметь возможность доставлять запросы на URL-адрес вебхука, а администраторы — возвращаться на URI перенаправления в своем браузере. Оба зарегистрированных URL-адреса должны совпадать с базовым HTTPS-URL-адресом вашего развертывания.

##### Установка приложения {#platform-origin-installing-the-app}

После перезапуска сервера администратор открывает **Настройки → Интеграции**, выбирает **Подключить** в разделе Origin и предоставляет приложению доступ к соответствующей учетной записи Origin и репозиториям. Организация Tuist сохраняется на протяжении всего процесса. При установке, инициированной непосредственно из Origin, администратору предлагается войти в систему и выбрать организацию Tuist для подключения. Затем он выбирает **Добавить новое подключение проекта**, чтобы связать проект Tuist с нативным репозиторием.

Следуйте <.localized_link href="/guides/integrations/gitforge/origin">руководству по интеграции Origin</.localized_link> для настройки подключений проектов и требований к загрузке результатов. Установка приложения не запускает рабочие процессы сборки или тестирования; эти процессы продолжают отправлять результаты на ваш сервер Tuist.

#### Entire {#platform-entire}

Самостоятельно размещаемому серверу Tuist требуется собственный плагин Entire, настроенный с URL-адресами вашего развертывания и ключом подписи. Плагины Entire требуют регистрации партнера, поэтому свяжитесь с Entire перед началом работы. Зарегистрируйте отдельный плагин или, как минимум, отдельный ключ подписи для каждой среды Tuist, чтобы установки и учетные данные оставались независимыми.

##### Регистрация плагина {#platform-entire-registering-the-plugin}

1. Сгенерируйте пару ключей подписи Ed25519 с помощью OpenSSL с поддержкой Ed25519:

   ```sh
   umask 077
   openssl genpkey -algorithm ED25519 -out entire-plugin-private.pem
   openssl pkey -in entire-plugin-private.pem -pubout -out entire-plugin-public.pem
   ```

2. Зарегистрируйте плагин, следуя [руководству по регистрации плагинов](https://docs.entire.com/guides/api/plugins/register) Entire. Предоставьте содержимое `entire-plugin-public.pem` или URL-адрес JWKS, который его публикует, в качестве ключа подписи плагина. Храните `entire-plugin-private.pem` в секрете; вы предоставите его серверу Tuist, а не Entire.
3. Настройте следующие URL-адреса, заменив `YOUR_APP_URL` базовым HTTPS-URL-адресом вашего развертывания Tuist:

   | Параметр | Значение |
   | --- | --- |
   | URL-адрес после установки | `YOUR_APP_URL/integrations/entire/callback` |
   | URL-адрес вебхука | `YOUR_APP_URL/webhooks/entire` |

4. Запишите slug плагина, подтвержденный Entire, и предоставленный им URL-адрес ключа подписи вебхука.

Запросите следующие разрешения:

| Разрешение | Используется для |
| --- | --- |
| `contents:read` | Получение событий Trail и поиск открытых и черновых Trails с их head-коммитами. |
| `checks:write` | Публикация гейта Tuist. |
| `findings:write` | Публикация и устранение находок неудачных и нестабильных тестов. |
| `discussions:write` | Публикация и обновление сводного комментария. Установки, которые не предоставили это разрешение, все равно получают гейт и находки. |

Запись в репозиторий не требуется. Если вы добавляете разрешения к существующей регистрации, попросите Entire обновить её и подтвердите, что установки предоставляют новые разрешения. См. контракты Entire: [Checks](https://docs.entire.com/guides/api/plugins/report-checks), [Findings](https://docs.entire.com/guides/api/plugins/trail-findings) и [Trail comments](https://docs.entire.com/guides/api/plugins/trail-comments.md).

##### Настройка сервера {#platform-entire-configuring-the-server}

Установите следующие переменные окружения, затем перезапустите сервер:

| Переменная окружения | Описание | Обязательно | По умолчанию | Пример |
| --- | --- | --- | --- | --- |
| `TUIST_ENTIRE_PLUGIN_SLUG` | Slug плагина, подтвержденный Entire. | Да | | `tuist` |
| `TUIST_ENTIRE_PLUGIN_PRIVATE_KEY` | Полное содержимое `entire-plugin-private.pem`, включая строки `BEGIN PRIVATE KEY` и `END PRIVATE KEY` и все переносы строк. | Да | | `-----BEGIN PRIVATE KEY-----...` |
| `TUIST_ENTIRE_DELIVERY_JWKS_URL` | URL-адрес ключа подписи вебхука, предоставленный Entire при регистрации. | Да | | |
| `TUIST_ENTIRE_PLUGIN_KEY_ID` | Идентификатор ключа, если вы зарегистрировали ключ подписи через JWKS. | Нет | | |
| `TUIST_ENTIRE_CORE_URL` | URL-адрес Entire Core, используемый для запросов на установку. | Нет | `https://eu.auth.entire.io` | |

Сохраните закрытый ключ в менеджере секретов вашего развертывания и сохраните его многострочный формат PEM. Никогда не фиксируйте ключ в системе контроля версий и не раскрывайте его в логах. При использовании Helm-чарта Tuist вы можете вместо этого сохранить PEM в хранилище 1Password как `ENTIRE_PLUGIN/private_key` и включить `server.config.entirePluginKey.enabled` вместе с `server.config.managedSecrets`; имена элемента и поля настраиваются через `server.config.entirePluginKey.item` и `.field`. Это сопоставление не устанавливает slug или URL-адрес ключа подписи вебхука.

Вашему серверу Tuist требуется исходящий HTTPS-доступ к Entire Core и региональным хостам API Entire, обслуживающим ваши репозитории, все они находятся в доменах `entire.io` или `entire.com`. Tuist проверяет квитанции об установке и подписи вебхуков, выпускает краткосрочные токены с областью действия репозитория и никогда не встраивает токены в ссылки на отчеты.

##### Включение интеграции {#platform-entire-enabling-the-integration}

Примените миграции сервера перед развертыванием приложения, затем включите флаг функции `entire_trails` глобально, чтобы предложить интеграцию всем аккаунтам, или только выбранным аккаунтам. Включение флага не меняет тех, кто может установить плагин в Entire; чтобы предложить его вне проекта Entire, владеющего плагином, попросите вашего контактного лица в Entire разрешить это. Интеграция не зависит от конфигурации выполнения CI в Tuist.

Если вы откатываете приложение, сохраните таблицу `entire_trail_reports`, чтобы последующее обновление могло восстановить публикации, которые были в процессе.

Затем администраторы устанавливают плагин и подключают репозитории к проектам, следуя <.localized_link href="/guides/integrations/gitforge/entire">руководству по интеграции с Entire</.localized_link>. Установка плагина не запускает рабочие процессы сборки или тестирования; эти рабочие процессы продолжают отправлять результаты на ваш сервер Tuist.

## Локальное тестирование {#testing-locally}

Мы предоставляем комплексную конфигурацию Docker Compose, которая включает все необходимые зависимости для тестирования сервера Tuist на вашем локальном компьютере перед развертыванием в вашей инфраструктуре:

- PostgreSQL 15
- ClickHouse 26.5 для аналитики
- ClickHouse Keeper для координации
- MinIO для хранилища, совместимого с S3
- Kura для локального тестирования самостоятельно размещаемого кэша
- pgweb для администрирования базы данных

> [!CAUTION]
> **Требуется лицензия**
>
> Для запуска сервера Tuist, включая локальные экземпляры разработки, юридически требуется действительная переменная окружения `TUIST_LICENSE`. Если вам нужна лицензия, пожалуйста, свяжитесь с нами по адресу [contact@tuist.dev](mailto:contact@tuist.dev).


**Быстрый старт:**

1. Скачайте файлы конфигурации:
   ```bash
   curl -O https://tuist.dev/server/self-host/docker-compose.yml
   curl -O https://tuist.dev/server/self-host/clickhouse-config.xml
   curl -O https://tuist.dev/server/self-host/clickhouse-log-level.xml
   curl -O https://tuist.dev/server/self-host/clickhouse-log-ttl.xml
   curl -O https://tuist.dev/server/self-host/clickhouse-keeper-config.xml
   curl -O https://tuist.dev/server/self-host/.env.example
   ```

2. Настройте переменные окружения:
   ```bash
   cp .env.example .env
   # Edit .env and add your TUIST_LICENSE, TUIST_SECRET_KEY_BASE, and authentication credentials
   ```

   Встроенный сервис ClickHouse принимает следующие необязательные параметры управления операционными логами:

   | Переменная окружения | Описание | По умолчанию | Пример |
   | --- | --- | --- | --- |
   | `CLICKHOUSE_SYSTEM_LOG_TTL_DAYS` | Окно хранения в днях для системных логов ClickHouse `system.*`, таких как `text_log`, `query_log`, `trace_log`, `metric_log` и `part_log` | `14` | `7` |
   | `CLICKHOUSE_TEXT_LOG_LEVEL` | Уровень логирования сервера ClickHouse и `system.text_log` | `information` | `warning` |
   | `CLICKHOUSE_SUPERSEDED_LOG_TABLES` | Что делать с таблицами `<name>_N`, которые ClickHouse оставляет при замене системной таблицы логов. `ignore` сохраняет их, `delete` удаляет | `ignore` | `delete` |

3. Запустите все сервисы:
   ```bash
   docker compose up -d
   # or with podman:
   podman compose up -d
   ```

   На Apple Silicon Docker Desktop автоматически загружает образы `linux/arm64` для Tuist и зависимостей. Чтобы принудительно использовать эмуляцию amd64 для отладки, запустите Compose с переменной `DOCKER_DEFAULT_PLATFORM=linux/amd64`.

   Встроенный файл compose использует именованные тома Docker для постоянных данных. Если вы замените их на привязки к хосту, сначала создайте директории на хосте и сделайте их доступными для записи пользователям контейнера, особенно директории данных ClickHouse и ClickHouse Keeper.

4. Откройте сервер по адресу http://localhost:8080

**Эндпоинты сервисов:**
- Сервер Tuist: http://localhost:8080
- Кэш Kura (HTTP + REAPI gRPC на одном порту): http://localhost:4000
- Консоль MinIO: http://localhost:9003 (учетные данные: `tuist` / `tuist_dev_password`)
- API MinIO: http://localhost:9002
- pgweb (UI для PostgreSQL): http://localhost:8081
- Метрики Prometheus: http://localhost:9091/metrics
- ClickHouse HTTP: http://localhost:8124

**Основные команды:**

Проверить статус сервисов:
```bash
docker compose ps

```

Просмотреть логи:
```bash
docker compose logs -f tuist
```

Остановить сервисы:


Сбросить всё (удаляет все данные):

## Kubernetes с Helm {#kubernetes-with-helm}

Tuist предоставляет официальный Helm-чарт для развертывания в Kubernetes. Чарт включает сервер и кэш-сервис Tuist, а также встроенные инфраструктурные зависимости, которые при необходимости можно заменить на внешние провайдеры.

### Установка чарта {#installing-the-chart}

```bash
helm install tuist oci://ghcr.io/tuist/charts/tuist \
  --set server.license.key="YOUR_LICENSE_KEY"
```

Чтобы закрепить конкретную версию чарта:

```bash
helm install tuist oci://ghcr.io/tuist/charts/tuist \
  --set server.license.key="YOUR_LICENSE_KEY" \
  --version 0.1.0
```

### Лицензия {#helm-license}

Значение `server.license.key` принимает как стандартный ключ лицензии, так и Base64-кодированный сертификат лицензии для изолированных установок; сервер автоматически определяет тип.

Передача лицензии через `--set` подходит для быстрой установки. Если вы храните значения в системе контроля версий, сохраните лицензию в Kubernetes Secret, которым управляете вне Helm (например, через Vault, Sealed Secrets или SOPS), и укажите его в чарте:

```yaml
# values.yaml
server:
  license:
    existingSecret: tuist-license
    existingSecretKeys:
      key: TUIST_LICENSE
      certificateBase64: ""
```

Запись в `existingSecretKeys.key` задает имя поля в вашем Secret, содержащего значение лицензии (ключ лицензии или Base64-кодированный сертификат для изолированных установок). Каждое поле в `existingSecretKeys` по умолчанию совпадает с именем ключа в чарте, поэтому для отсутствующих в Secret полей указывайте пустую строку, как показано для `certificateBase64`. В противном случае поды будут ссылаться на несуществующие ключи и не смогут запуститься. Создайте Secret в неймспейсе релиза перед установкой или обновлением чарта.

Настройте лицензию только из одного источника: `server.license.key` или `server.license.existingSecret`. Рендеринг чарта завершится ошибкой, если источник не указан или источники объединены. Лицензия, переданная через `server.extraEnv`, не считается источником, поэтому используйте `existingSecret`.

### Инфраструктурные зависимости {#helm-infrastructure-dependencies}

Чарт управляет тремя инфраструктурными зависимостями: `postgresql`, `clickhouse` и `objectStorage`. По умолчанию каждая работает в режиме **embedded**, то есть разворачивается внутри кластера. Чтобы использовать свои внешние экземпляры, установите для зависимости параметр `mode` в значение `external` и заполните данные подключения в файле `values.yaml`. Например, чтобы использовать внешнюю базу данных PostgreSQL:

```yaml
# values.yaml
postgresql:
  mode: external
  external:
    host: your-db-host
    port: 5432
    database: tuist
    username: tuist
    password: your-password
```

Если вы управляете учетными данными PostgreSQL вне Helm, укажите в чарте существующий Kubernetes Secret:

```yaml
# values.yaml
postgresql:
  mode: external
  external:
    port: 5432
    database: tuist
    existingSecret: tuist-postgresql
    existingSecretKeys:
      host: host
      username: username
      password: password
```

Чарт считывает хост, имя пользователя и пароль из Secret и формирует `DATABASE_URL` через подстановку переменных окружения Kubernetes, поэтому пароль не попадает в манифест Helm. Значение пароля в Secret должно быть безопасным для URL, так как оно встраивается в строку подключения к базе данных.

Та же схема применяется к `clickhouse` и `objectStorage`. Полный список настраиваемых полей см. в блоке `external` каждого раздела файла `values.yaml` чарта.

### Общие настройки планирования и метки {#helm-shared-scheduling-and-labels}

Чарт предоставляет небольшой набор общих настроек подов через `global`, чтобы операторы могли адаптировать развертывание под свой кластер, не повторяя одни и те же значения для каждой рабочей нагрузки:

```yaml
global:
  podLabels:
    environment: production
  imagePullSecrets:
    - name: ghcr-pull-secret
  nodeSelector:
    nodepool: apps
  tolerations:
    - key: dedicated
      operator: Equal
      value: apps
      effect: NoSchedule
```

Используйте эти настройки, если вам нужно:

- добавить специфичные для кластера метки ко всем подам
- загружать зеркалированные образы из приватного реестра
- нацеливаться на выделенный пул узлов
- разрешать размещение подов на tainted-узлах, зарезервированных для рабочих нагрузок Tuist

### Идентификация рабочих нагрузок и сервисные аккаунты {#helm-workload-identity}

Чарт ограничивает область действия сервисных аккаунтов отдельными рабочими нагрузками приложения, чтобы предоставлять идентификатор только там, где это необходимо:

- `server.serviceAccount` применяется к развертыванию сервера Tuist и задаче миграции
- `cache.serviceAccount` применяется к развертыванию кэша

Например, когда кэш использует внешний бакет S3 в EKS, вы можете включить IRSA для рабочей нагрузки кэша, не привязывая ту же IAM-роль к встроенным базам данных:

```yaml
cache:
  serviceAccount:
    create: true
    annotations:
      eks.amazonaws.com/role-arn: arn:aws:iam::123456789012:role/tuist-cache
```

### Переопределения совместимости {#helm-compatibility-overrides}

Чарт оставляет специфичные для хранилищ и service mesh настройки опциональными, чтобы значения по умолчанию оставались переносимыми:

```yaml
cache:
  podSecurityContext:
    fsGroup: 990

clickhouse:
  embedded:
    service:
      nativePort: 9100
    systemLogs:
      ttlDays: 7
      supersededTables: delete
      level: warning
```

Используйте эти переопределения только при необходимости в вашем кластере:

- `cache.podSecurityContext` по умолчанию пуст. Укажите `fsGroup`, если ваш StorageClass или CSI-драйвер требует общего группового владения для монтируемых томов.
- `clickhouse.embedded.service.nativePort` по умолчанию соответствует стандартному порту нативного сервиса ClickHouse `9000` и может быть изменен, если этот порт конфликтует с service mesh или резервированием платформы.
- `clickhouse.embedded.systemLogs.ttlDays` по умолчанию пуст, что сохраняет неограниченное хранение во встроенных внутренних таблицах логов ClickHouse, таких как `system.text_log`, `system.query_log`, `system.trace_log`, `system.metric_log` и `system.part_log`. Установка этого параметра один раз заменяет эти таблицы, поэтому применяйте его вместе с `supersededTables: delete` — см. <.localized_link href="/guides/server/self-host/server#capping-operational-log-retention">ограничение срока хранения операционных логов</.localized_link>.
- `clickhouse.embedded.systemLogs.level` по умолчанию имеет значение `information` для встроенного логгера сервера ClickHouse и `system.text_log`. В отличие от `ttlDays`, он не входит в определение таблиц, поэтому его изменение никогда не приводит к замене таблиц.
- `clickhouse.embedded.systemLogs.supersededTables` по умолчанию имеет значение `ignore` и определяет, что происходит с таблицами `<name>_N`, которые ClickHouse оставляет после замены системной таблицы логов. Установите значение `delete`, чтобы удалять их при каждом `helm upgrade`.
- Изменения `ttlDays` и `level` применяются к поду ClickHouse при следующем перезапуске, так как оба параметра монтируются через `subPath`, а чарт не выполняет rolling update StatefulSet при изменении ConfigMap.

### Наблюдаемость {#helm-observability}

Чарт включает опциональный стек наблюдаемости (OpenTelemetry Collector, Prometheus, Grafana, Loki и Tempo). Он **отключен по умолчанию**. Чтобы включить его в файле `values.yaml`:

```yaml
# values.yaml
observability:
  enabled: true
```

При включении Grafana доступна с предварительно настроенными детализациями по логам, трейсам и метрикам. Для внешней наблюдаемости оставьте эту функцию отключенной и настройте эндпоинты через `server.extraEnv`:

```yaml
# values.yaml
server:
  extraEnv:
    - name: TUIST_OTEL_EXPORTER_OTLP_ENDPOINT
      value: "http://your-otel-collector:4317"
    - name: TUIST_LOKI_URL
      value: "http://your-loki:3100"
```

### Справочник значений {#helm-values-reference}

Полный список настраиваемых значений см. в файле чарта [`values.yaml`](https://github.com/tuist/tuist/blob/main/infra/helm/tuist/values.yaml).

## Развертывание {#deployment}

Официальный Docker-образ Tuist доступен по адресу:
```
ghcr.io/tuist/tuist
```

Опубликованный образ включает встроенную обработку сборок для Linux архивов `.xcactivitylog`, поэтому развертывания на собственных серверах могут обрабатывать сборки без запуска дополнительных сервисов — задача Oban `ProcessBuildWorker` выполняется внутри процесса на каждом поде сервера. Если вы хотите вынести обработку сборок на выделенный набор реплик (например, чтобы масштабировать пропускную способность парсинга независимо от веб-уровня), установите `processor.enabled: true` в Helm-чарте: чарт развернет тот же образ как потребителя только очереди (`TUIST_PROCESSOR_MODE=true`). См. [`values.yaml`](https://github.com/tuist/tuist/blob/main/infra/helm/tuist/values.yaml) для полного списка параметров.

> [!NOTE]
> Парсинг `.xcresult` опирается на `xcresulttool` из Xcode, поэтому может выполняться только на macOS. CLI обрабатывает это прозрачно для развертываний на собственных серверах: `tuist test` по умолчанию использует режим обработки **local** для любого сервера, кроме `tuist.dev`, парсит xcresult на машине разработчика (где уже установлен Xcode для самой сборки) и загружает структурированные результаты. Результаты тестов принимаются без дополнительной инфраструктуры.

### Загрузка Docker-образа {#pulling-the-docker-image}

Вы можете получить образ, выполнив следующую команду:

```bash
docker pull ghcr.io/tuist/tuist:latest
```

Образ опубликован для архитектур `linux/amd64` и `linux/arm64`, поэтому Docker автоматически выбирает нативную Linux-архитектуру для хоста.

Или загрузите конкретную версию:
```bash
docker pull ghcr.io/tuist/tuist:0.1.0
```

### Развертывание Docker-образа {#deploying-the-docker-image}

Процесс развертывания Docker-образа будет отличаться в зависимости от выбранного облачного провайдера и подхода вашей организации к непрерывному развертыванию. Поскольку большинство облачных решений и инструментов, таких как [Kubernetes](https://kubernetes.io/), используют Docker-образы в качестве базовых единиц, примеры в этом разделе должны хорошо соответствовать вашей текущей конфигурации.

> [!WARNING]
> Если вашему конвейеру развертывания нужно проверить, что сервер запущен и работает, вы можете отправить HTTP-запрос `GET` на `/ready` и проверить код состояния `200` в ответе.


#### Fly {#fly}

Чтобы развернуть приложение на [Fly](https://fly.io/), вам потребуется файл конфигурации `fly.toml`. Рассмотрите возможность его динамической генерации в конвейере непрерывного развертывания (CD). Ниже приведен справочный пример для использования:

```toml
app = "tuist"
primary_region = "fra"
kill_signal = "SIGINT"
kill_timeout = "5s"

[experimental]
  auto_rollback = true

[env]
  # Your environment configuration goes here
  # Or exposed through Fly secrets

[processes]
  app = "/usr/local/bin/hivemind /app/Procfile"

[[services]]
  protocol = "tcp"
  internal_port = 8080
  auto_stop_machines = false
  auto_start_machines = false
  processes = ["app"]
  http_options = { h2_backend = true }

  [[services.ports]]
    port = 80
    handlers = ["http"]
    force_https = true

  [[services.ports]]
    port = 443
    handlers = ["tls", "http"]
  [services.concurrency]
    type = "connections"
    hard_limit = 100
    soft_limit = 80

  [[services.http_checks]]
    interval = 10000
    grace_period = "10s"
    method = "get"
    path = "/ready"
    protocol = "http"
    timeout = 2000
    tls_skip_verify = false
    [services.http_checks.headers]

[[statics]]
  guest_path = "/app/public"
  url_prefix = "/"
```

Затем вы можете выполнить `fly launch --local-only --no-deploy`, чтобы запустить приложение. При последующих развертываниях вместо выполнения `fly launch --local-only` необходимо запускать `fly deploy --local-only`. Fly.io не позволяет загружать приватные Docker-образы, поэтому нам нужно использовать флаг `--local-only`.


## Метрики Prometheus {#prometheus-metrics}

Tuist предоставляет метрики Prometheus по адресу `/metrics`, чтобы помочь вам отслеживать работу вашего собственного экземпляра. Эти метрики включают:

### Метрики HTTP-клиента Finch {#finch-metrics}

Tuist использует [Finch](https://github.com/sneako/finch) в качестве HTTP-клиента и предоставляет подробные метрики о HTTP-запросах:

#### Метрики запросов
- `tuist_prom_ex_finch_request_count_total` — общее количество запросов Finch (счетчик)
  - Метки: `finch_name`, `method`, `scheme`, `host`, `port`, `status`
- `tuist_prom_ex_finch_request_duration_milliseconds` — длительность HTTP-запросов (гистограмма)
  - Метки: `finch_name`, `method`, `scheme`, `host`, `port`, `status`
  - Интервалы: 10 мс, 50 мс, 100 мс, 250 мс, 500 мс, 1 с, 2,5 с, 5 с, 10 с
- `tuist_prom_ex_finch_request_exception_count_total` — общее количество исключений при запросах Finch (счетчик)
  - Метки: `finch_name`, `method`, `scheme`, `host`, `port`, `kind`, `reason`

#### Метрики очереди пула соединений
- `tuist_prom_ex_finch_queue_duration_milliseconds` — время ожидания в очереди пула соединений (гистограмма)
  - Метки: `finch_name`, `scheme`, `host`, `port`, `pool`
  - Интервалы: 1 мс, 5 мс, 10 мс, 25 мс, 50 мс, 100 мс, 250 мс, 500 мс, 1 с
- `tuist_prom_ex_finch_queue_idle_time_milliseconds` — время простоя соединения перед использованием (гистограмма)
  - Метки: `finch_name`, `scheme`, `host`, `port`, `pool`
  - Интервалы: 10 мс, 50 мс, 100 мс, 250 мс, 500 мс, 1 с, 5 с, 10 с
- `tuist_prom_ex_finch_queue_exception_count_total` — общее количество исключений очереди Finch (счетчик)
  - Метки: `finch_name`, `scheme`, `host`, `port`, `kind`, `reason`

#### Метрики соединений
- `tuist_prom_ex_finch_connect_duration_milliseconds` — время, затраченное на установление соединения (гистограмма)
  - Метки: `finch_name`, `scheme`, `host`, `port`, `error`
  - Интервалы: 10 мс, 50 мс, 100 мс, 250 мс, 500 мс, 1 с, 2,5 с, 5 с
- `tuist_prom_ex_finch_connect_count_total` — общее количество попыток соединения (счетчик)
  - Метки: `finch_name`, `scheme`, `host`, `port`

#### Метрики отправки
- `tuist_prom_ex_finch_send_duration_milliseconds` — время, затраченное на отправку запроса (гистограмма)
  - Метки: `finch_name`, `method`, `scheme`, `host`, `port`, `error`
  - Интервалы: 1 мс, 5 мс, 10 мс, 25 мс, 50 мс, 100 мс, 250 мс, 500 мс, 1 с
- `tuist_prom_ex_finch_send_idle_time_milliseconds` — время простоя соединения перед отправкой (гистограмма)
  - Метки: `finch_name`, `method`, `scheme`, `host`, `port`, `error`
  - Интервалы: 1 мс, 5 мс, 10 мс, 25 мс, 50 мс, 100 мс, 250 мс, 500 мс

Все гистограммные метрики предоставляют варианты `_bucket`, `_sum` и `_count` для детального анализа.

### Другие метрики

Помимо метрик Finch, Tuist предоставляет метрики для:
- производительности виртуальной машины BEAM
- Метрики пользовательской бизнес-логики (хранилище, учетные записи, проекты и т. д.)
- Производительность базы данных (при использовании инфраструктуры, размещенной Tuist)

## Операции {#operations}

Tuist предоставляет набор утилит по адресу `/ops/`, которые можно использовать для управления вашим экземпляром.

> [!WARNING]
> **Авторизация**
>
> Доступ к конечным точкам `/ops/` имеют только пользователи, чей домен электронной почты совпадает с `TUIST_OPERATOR_EMAIL_DOMAIN`. Если переменная не задана, доступ закрыт для всех. Установите значение переменной в домен, почтовые ящики которого вы контролируете.
>
> Пользователь также должен подтвердить контроль над своим адресом: перейдя по ссылке из письма с подтверждением или сбросом пароля, войдя через Google, GitHub или Apple, введя одноразовый код или предоставив проверенный адрес электронной почты при входе через агента. Учетные записи, подтвержденные автоматически (что является значением по умолчанию при отсутствии почтового провайдера), не считаются подтвержденными, пока это не будет сделано. После создания учетной записи подтверждение фиксируется только тогда, когда адрес находится в `TUIST_OPERATOR_EMAIL_DOMAIN`, поэтому после установки или изменения переменной операторам, которые еще не подтвердили свой адрес в этом домене, необходимо сделать это снова. Учетные записи, созданные путем входа через одного из этих провайдеров или через вход агента, сохраняют подтверждение с момента создания. Без почтового провайдера учетная запись, зарегистрированная с паролем, не может быть связана с одним из этих провайдеров, поэтому создавайте учетные записи операторов, входя через Google, GitHub или Apple, либо настройте почтовый провайдер.
>
> Учетные записи, созданные до появления этой проверки, еще не зафиксировали такое подтверждение, поэтому существующий оператор восстановит доступ после сброса пароля или однократного входа через одного из этих провайдеров.
>
> Когда учетная запись в домене операторов без такого подтверждения впервые подтверждает свой адрес таким образом, Tuist удаляет ее пароль, ключи доступа и ссылки на провайдеры единого входа организации, а также выполняет выход из браузера и CLI, поскольку лицо, зарегистрировавшее адрес, может не быть его владельцем. Сброс пароля для такой учетной записи приводит к тем же действиям, за исключением установки нового пароля. Приложение-аутентификатор, настроенное для учетной записи, сохраняется; если оно не принадлежит владельцу, удалите его. Подтвержденные учетные записи вне домена операторов сохраняют свои учетные данные. Владелец продолжает входить через провайдера или устанавливает новый пароль через сброс.
>
> Учетные записи, созданные или переименованные при помощи SCIM-провижининга, не имеют подтверждения, пока владелец не предоставит его.


- **Ошибки (`/ops/errors`):** Здесь можно просмотреть непредвиденные ошибки, возникшие в приложении. Это полезно для отладки и понимания причин сбоев; мы можем попросить вас поделиться этой информацией, если вы столкнетесь с проблемами.
- **Панель управления (`/ops/dashboard`):** Здесь доступна панель управления, которая предоставляет информацию о производительности и состоянии приложения (например, потребление памяти, запущенные процессы, количество запросов). Эта панель помогает понять, достаточно ли мощности используемого оборудования для обработки нагрузки.
