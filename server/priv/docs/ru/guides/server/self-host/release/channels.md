# Каналы релизов {#release-channels}

Сервер Tuist и сервер кэша Kura поставляются через три канала образов GHCR с разными гарантиями стабильности. Рекомендуемая установка — **stable**, которая обновляется раз в неделю: она не продвигается при каждом слиянии новой возможности в `main`, поэтому обновление больше не означает поглощение пакета несвязанных изменений. Ранние пользователи по-прежнему могут запускать сборки для каждого коммита на канале **canary**, а канал **release candidate** позволяет предварительно протестировать будущую ветку до её перевода в статус stable.

Сервер и Kura следуют одному еженедельному графику и синхронизированы с <.localized_link href="/cli/release/channels">графиком релизов CLI Tuist</.localized_link>.

## Каналы {#the-channels}

| Канал | Формат версии | Частота | Обновляет `:latest`? |
| --- | --- | --- | --- |
| Canary | `X.Y.0-canary.N` (например, `1.351.0-canary.5`) | Каждый коммит в `main` | Нет, явное подключение |
| Release candidate | `X.Y.0-rc.N` (например, `1.351.0-rc.1`) | Отсекается от `main` каждый понедельник, тестируется ~1 неделю | Нет, явное подключение |
| Stable | `X.Y.Z` (например, `1.350.2`, `1.351.0`) | Повышается каждый понедельник после успешного тестирования | **Да** |

Сборки Canary и Release Candidate публикуются как предварительные релизы GitHub. Любой инструмент, исключающий предварительные релизы при разрешении `:latest`, будет их пропускать, поэтому вы попадёте на один из них только при явном запросе.

### Canary {#canary}

Каждый коммит в `main` публикует образ canary. Canary всегда представляет **следующую невыпущенную минорную версию**: как только ветка отсекается для релиза, `main` переходит к следующей минорной версии (например, с `1.350.0-canary.42` на `1.351.0-canary.1`). Canary — правильный канал для staging-среды, которая зеркально отражает production и даёт самый ранний сигнал о регрессиях, или для проверки того, что исправление, которое вы сообщили, работает должным образом до попадания в stable.

```
ghcr.io/tuist/tuist:1.351.0-canary.5
ghcr.io/tuist/kura:0.55.0-canary.5
```

### Release candidate {#release-candidate}

Когда минорная версия готова к выпуску, её ветка замораживается в защищённой ветке `releases/server-<major>.<minor>.x` (или `releases/kura-<major>.<minor>.x`) и публикуется как `X.Y.0-rc.1`. Ветка заморожена по функциональности; в неё принимаются только критические исправления и исправления регрессий, и каждое принятое исправление увеличивает номер кандидата в релизы (`-rc.2`, `-rc.3` и так далее). После успешного завершения периода тестирования ветка повышается до stable в следующий понедельник.

```
ghcr.io/tuist/tuist:1.351.0-rc.1
ghcr.io/tuist/kura:0.55.0-rc.1
```

### Stable {#stable}

Stable — рекомендуемый канал, на который ссылается вся документация. Стабильная минорная версия (`X.Y.0`) публикуется только после успешного тестирования кандидата в релизы и **не** продвигается при слиянии новых возможностей в `main`. Патчи (`X.Y.1`, `X.Y.2` и так далее) в стабильной ветке содержат только бэкпортированные исправления, никогда — новые возможности. `:latest` перемещается только при повышении до stable.

```
ghcr.io/tuist/tuist:1.351.0
ghcr.io/tuist/kura:0.55.0
ghcr.io/tuist/tuist:latest
ghcr.io/tuist/kura:latest
```

## Понедельничный поезд {#the-monday-train}

Каждый понедельник в 06:00 UTC процессы релиза трёх компонентов запускаются синхронно:

1. **06:00 UTC** — запускаются задачи повышения. Каждая повышает новейшую ветку кандидата в релизы, которая ещё не является stable (обычно это ветка, отсечённая в предыдущий понедельник), и ничего не делает, если таких нет.
2. **После завершения каждого повышения** — задача release-candidate отсекает следующую ветку от `main`, поэтому свежеотсечённая ветка никогда не повышается в том же запуске.

Неудачное повышение блокирует отсечение: выбирается только самая старшая ветка кандидата в релизы выше последней stable, поэтому отсечение следующей ветки поверх неудачи оставило бы непоставленную ветку без внимания. В следующий понедельник удержанная ветка автоматически повторяется.

## Закрепление канала {#pinning-a-channel}

Закрепите нужный тег в манифесте развёртывания, значениях Helm или файле Docker Compose. Пример с использованием чарта Helm:

```yaml
server:
  image:
    repository: ghcr.io/tuist/tuist
    tag: "1.350.2"          # Pinned to a stable patch
    # tag: "1.351.0-rc.1"   # Or opt into a release candidate to soak it
    # tag: "1.351.0-canary.5" # Or opt into a specific canary build

kuraRuntime:
  image:
    repository: ghcr.io/tuist/kura
    tag: "0.54.0"           # Same three channels apply to Kura
```

`:latest` для обоих `ghcr.io/tuist/tuist` и `ghcr.io/tuist/kura` отслеживает новейшую stable, перемещаемую только при понедельничном повышении. Закрепление `:latest` даёт вам еженедельный стабильный ритм без необходимости обновлять тег; закрепление конкретной версии даёт полный контроль над моментом обновления.

## Рекомендуемая стратегия {#recommended-strategy}

Каналы существуют для того, чтобы разделить «получение новейших исправлений» и «получение новейших возможностей». Безопасный вариант с минимальными усилиями по умолчанию:

1. **Закрепите production на стабильной минорной ветке**, например `ghcr.io/tuist/tuist:1.351`. Эта ветка получает только бэкпортированные исправления, никогда — новые возможности, поэтому ежедневные обновления остаются низкорисковыми. Обновляйте закрепление, когда будете готовы перейти на следующую минорную версию.
2. **Запустите staging-окружение на canary или на конкретном теге кандидата в релизы.** Staging выявляет регрессии, которые иначе достигли бы ваших пользователей, и чем ближе staging отслеживает `main`, тем раньше вы их обнаружите. Staging-окружение на текущей ветке кандидата в релизы — хороший компромисс: оно проверяет именно те байты, которые станут stable в следующий понедельник.
3. **Следите за [журналом изменений сервера](/changelog), чтобы знать, что действительно было выпущено.** Каждое повышение до stable анонсируется там со списком попавших в выпуск pull request-ов.

Если вы предпочитаете, чтобы новые возможности автоматически попадали в production по мере стабилизации, оставьте production на `:latest`. Учтите, что тег обновляется еженедельно утром в понедельник, поэтому планируйте окно развёртывания соответствующим образом.

## Бэкпорты {#backports}

В любой момент активно поддерживаются две стабильные ветки сервера (и Kura): текущая ветка получает регрессии и исправления безопасности через бэкпорт-запросы, а предыдущая — только критические исправления и исправления безопасности. Более старые ветки не получают бэкпортов; перейдите на поддерживаемую ветку, чтобы получать исправления. Когда новая ветка повышается до stable, текущая становится «предыдущей», а та, что была «предыдущей», перестаёт получать бэкпорты.

Бэкпорты выпускаются по запросу как патч-релизы `X.Y.(Z+1)`. Они никогда не перемещают `:latest`.
