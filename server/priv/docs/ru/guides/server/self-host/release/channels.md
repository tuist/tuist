# Каналы релизов {#release-channels}

Сервер Tuist и сервер кэширования Kura поставляются через три канала образов GHCR с разными гарантиями стабильности. Рекомендуемая установка — **stable**, обновления выходят раз в неделю: канал не продвигается при каждом слиянии функции в `main`, поэтому обновление больше не означает поглощение пакета несвязанных изменений. Ранние пользователи по-прежнему могут запускать сборки для каждого коммита на канале **canary**, а канал **release candidate** позволяет протестировать предстоящую ветку до её перевода в статус stable.

И сервер, и Kura следуют одному еженедельному графику и синхронизированы с <.localized_link href="/cli/release/channels">графиком релизов CLI Tuist</.localized_link>.

## Каналы {#the-channels}

| Канал | Формат версии | Частота | Обновляет `:latest`? |
| --- | --- | --- | --- |
| Canary | `X.Y.0-canary.N` (например, `1.351.0-canary.5`) | Каждый коммит в `main` | Нет, требуется явное согласие |
| Release candidate | `X.Y.0-rc.N` (например, `1.351.0-rc.1`) | Отсекается от `main` каждый понедельник, тестируется ~1 неделю | Нет, требуется явное согласие |
| Stable | `X.Y.Z` (например, `1.350.2`, `1.351.0`) | Продвигается каждый понедельник после успешного тестирования | **Да** |

Сборки Canary и Release Candidate публикуются как предварительные релизы GitHub. Любой инструмент, исключающий предварительные релизы при разрешении `:latest`, будет их пропускать, поэтому вы попадёте на них только при явном запросе.

### Canary {#canary}

Каждый коммит в `main` публикует образ canary. Canary всегда представляет **следующую невыпущенную минорную версию**: как только ветка отсекается для релиза, `main` переходит к следующей минорной версии (например, с `1.350.0-canary.42` на `1.351.0-canary.1`). Canary — правильный канал для стендовой среды, которая зеркально отражает продакшен и даёт максимально ранний сигнал о регрессиях, или для проверки того, что исправление, которое вы сообщили, работает так, как ожидается, до попадания в stable.

```
ghcr.io/tuist/tuist:1.351.0-canary.5
ghcr.io/tuist/kura:0.55.0-canary.5
```

### Release candidate {#release-candidate}

Когда минорная версия готова к выпуску, её ветка замораживается на защищённой ветке `releases/server-<major>.<minor>.x` (или `releases/kura-<major>.<minor>.x`) и публикуется как `X.Y.0-rc.1`. Ветка заморожена по функциональности; в неё попадают только критические исправления и исправления регрессий, и каждое принятое исправление увеличивает номер кандидата в релизы (`-rc.2`, `-rc.3` и так далее). После успешного завершения периода тестирования ветка переводится в статус stable в следующий понедельник.

```
ghcr.io/tuist/tuist:1.351.0-rc.1
ghcr.io/tuist/kura:0.55.0-rc.1
```

### Stable {#stable}

Stable — рекомендуемый канал, на который ссылается вся документация. Стабильная минорная версия (`X.Y.0`) публикуется только после успешного тестирования кандидата в релизы и **не** продвигается при слиянии новых функций в `main`. Патчи (`X.Y.1`, `X.Y.2` и так далее) в стабильной ветке содержат только бэкпортированные исправления, никогда — новые функции. `:latest` обновляется только при продвижении стабильной версии.

```
ghcr.io/tuist/tuist:1.351.0
ghcr.io/tuist/kura:0.55.0
ghcr.io/tuist/tuist:latest
ghcr.io/tuist/kura:latest
```

## Понедельничный поезд {#the-monday-train}

Каждый понедельник в 06:00 UTC релизные поезда трёх компонентов запускаются синхронно:

1. **06:00 UTC** — выполняются задачи продвижения. Каждая задача продвигает новейшую ветку кандидата в релизы, которая ещё не стала стабильной (обычно это ветка, отсечённая в предыдущий понедельник), и ничего не делает, если таких веток нет.
2. **После завершения каждого продвижения** — задача release-candidate отсекает следующую ветку от `main`, поэтому свежеотсечённая ветка никогда не продвигается в том же запуске.

Неудачное продвижение задерживает отсечение: выбирается только самая старшая ветка кандидата в релизы выше последней стабильной, поэтому отсечение следующей ветки поверх неудачи оставило бы непоставленную ветку без поддержки. В следующий понедельник задержанная ветка автоматически повторяется.

## Закрепление канала {#pinning-a-channel}

Закрепите нужный тег в манифесте развёртывания, значениях Helm или файле Docker Compose. Пример с использованием чарта Helm:

```yaml
server:
  image:
    repository: ghcr.io/tuist/tuist
    tag: "1.350.2"          # Pinned to a stable patch
    # tag: "1.351.0-rc.1"   # Or opt into a release candidate to soak it
    # tag: "1.351.0-canary.5" # Or opt into a specific canary build

kuraRuntime:
  image:
    repository: ghcr.io/tuist/kura
    tag: "0.54.0"           # Same three channels apply to Kura
```

`:latest` в обоих `ghcr.io/tuist/tuist` и `ghcr.io/tuist/kura` отслеживает новейшую стабильную версию, обновляемую только при понедельничном продвижении. Закрепление `:latest` даёт еженедельный стабильный ритм без необходимости обновлять тег; закрепление конкретной версии даёт полный контроль над моментом обновления.

## Рекомендуемая стратегия {#recommended-strategy}

Каналы существуют, чтобы разделить «получение новейших исправлений» и «получение новейших функций». Безопасный вариант с минимальными усилиями:

1. **Закрепите продакшен на стабильной минорной ветке**, например `ghcr.io/tuist/tuist:1.351`. Эта ветка получает только бэкпортированные исправления, никогда — новые функции, поэтому повседневные обновления остаются низко рискованными. Обновляйте закрепление, когда будете готовы перейти на следующую минорную версию.
2. **Запустите промежуточную среду на канале canary или с конкретным тегом кандидата в релизы.** Промежуточная среда выявляет регрессии, которые иначе дошли бы до ваших пользователей, и чем ближе она отслеживает `main`, тем раньше вы их обнаружите. Промежуточная среда на текущей ветке кандидата в релизы — хороший компромисс: она проверяет именно те данные, которые станут стабильными в следующий понедельник.
3. **Следите за [журналом изменений сервера](/changelog), чтобы знать, что действительно выпущено.** Каждое стабильное продвижение анонсируется там со списком включённых pull-запросов.

Если вы предпочитаете, чтобы новые функции автоматически попадали в продакшен по мере стабилизации, оставьте продакшен на `:latest`. Имейте в виду, что тег обновляется еженедельно утром в понедельник, поэтому планируйте окно развёртывания соответствующим образом.

## Бэкпорты {#backports}

Две стабильные ветки сервера (и Kura) активно поддерживаются в любой момент времени: текущая ветка получает регрессии и исправления безопасности в виде бэкпорт-запросов, а предыдущая ветка — только критические исправления и исправления безопасности. Более старые ветки не бэкпортируются; обновитесь до поддерживаемой ветки, чтобы получать исправления. Когда новая ветка продвигается в стабильную, текущая ветка становится «предыдущей», а ветка, которая была «предыдущей», перестаёт получать бэкпорты.

Бэкпорты выпускаются по требованию как патч-релизы `X.Y.(Z+1)`. Они никогда не перемещают `:latest`.
