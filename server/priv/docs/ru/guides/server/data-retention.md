# Хранение данных {#data-retention}

Tuist применяет отдельные политики хранения к загруженным файлам артефактов и записям, используемым для панелей мониторинга и аналитики. Удаление устаревшего файла артефакта не удаляет связанные с ним записи аналитики.

Для файлов артефактов хостинговый сервер Tuist использует окна хранения, зависящие от тарифного плана и ограниченные 30 днями. Очистка артефактов по умолчанию отключена на самостоятельно размещаемых экземплярах, где операторы могут включить её и настроить отдельное окно для каждого поддерживаемого типа артефактов.

## Файлы артефактов {#artifact-files}

### Хостинговый сервер Tuist {#hosted-artifact-files}

Эти окна определяют, как долго файлы артефактов остаются доступными на хостинговом сервере Tuist.

| Артефакт | Air и Open Source | Pro | Enterprise |
| --- | --- | --- | --- |
| Артефакты кэша, включая кэш Xcode, кэш модулей, кэш Gradle, файлы удалённого кэша Bazel и архивы кэша GitLab CI от Tuist Runners | 14 дней | 30 дней | 30 дней |
| Сборки предварительного просмотра приложений и иконки | 30 дней | 30 дней | 30 дней |
| Архивы сборок | 7 дней | 30 дней | 30 дней |
| Артефакты запуска, включая пакеты результатов, архивы сессий и журналы удалённых действий Bazel | 7 дней | 30 дней | 30 дней |
| Вложения запусков тестов | 30 дней | 30 дней | 30 дней |
| Пакеты шардов | 7 дней | 14 дней | 30 дней |

Активный тарифный план аккаунта определяет окно хранения на хостинге. Если у аккаунта нет активной подписки, Tuist использует окно хранения Air. Для некоторых типов артефактов используются более короткие окна, поскольку ожидается их повторная генерация.

Вложения тестов, созданные до того, как Tuist зафиксировал идентификатор запуска тестов, исключаются из автоматического удаления. Их файлы остаются доступными, пока Tuist избегает неограниченного поиска исторических данных о владении во время очистки хранения.

### Самостоятельно размещаемые экземпляры {#self-hosted-artifact-files}

Очистка артефактов на самостоятельно размещаемых экземплярах включается опционально, настраивается отдельно для каждого типа артефактов и не ограничена 30 днями. См. <.localized_link href="/guides/server/self-host/server#artifact-retention">конфигурацию хранения артефактов для самостоятельного размещения</.localized_link>, чтобы узнать о поддерживаемых типах артефактов и вариантах развёртывания.

## Данные панели мониторинга и активности {#dashboard-and-activity-data}

Записи панели мониторинга и активности имеют политики хранения, независимые от очистки файлов артефактов. Окна ниже не зависят от хостингового тарифного плана, включая Enterprise.

### Инсайты сборки и тестирования Xcode {#xcode-build-and-test-insights}

Основные записи сборки и тестирования Xcode в настоящее время не имеют фиксированного расписания удаления по времени. Другие данные отчётов, такие как шаги временной шкалы и метрики машин, истекают отдельно:

| Данные | Хранение |
| --- | --- |
| Сводки сборок, записи сборки по файлам и целям, а также проблемы сборки | Нет фиксированного расписания удаления по времени |
| Запуски тестов, результаты модулей и наборов, а также индивидуальные результаты тестов | Нет фиксированного расписания удаления по времени |
| Шаги временной шкалы сборки и их сохранённые журналы | 90 дней |
| Метрики машин сборки | 90 дней |
| Записи графа проекта Xcode | 30 дней |

Эти записи отделены от загружаемых архивов сборок, пакетов результатов и вложений тестов, на которые распространяются [окна хранения файлов артефактов](#hosted-artifact-files). На тарифе Enterprise эти файлы хранятся 30 дней; связанные записи сборки и тестирования остаются доступными после истечения срока хранения файлов. Отсутствие фиксированного расписания удаления по времени не гарантирует постоянного доступа.

### Другие данные панели мониторинга и активности {#other-dashboard-and-activity-data}

Индексированные шаги профиля Bazel включают необязательные времена удалённой очереди, выборки входных данных, выполнения и выгрузки результатов для каждого действия, когда их можно безопасно связать с действием. Они используют тот же 90-дневный срок хранения профиля, независимо от кэшированных артефактов и записей биллинга.

| Данные | Хранение |
| --- | --- |
| Записи сборки Gradle, записи задач и сообщения об ошибках неудавшихся задач и шагов конфигурации, записи событий кэша, записи сборки Mix, записи компилированных файлов, записи и диагностика шагов сборки, записи сборки Cargo (включая агрегированные измерения кэша компиляции) и наблюдения компилятора, вызовы Bazel, профили трассировки Bazel, индексированные шаги профиля и диагностика действий, ожидающие записи импорта профилей и тестов Bazel, журналы вызовов Bazel, наблюдения кэша удалённых действий Bazel и записи удалённо выполненных действий (команда, окружение, платформа, код выхода и начало их вывода) | 90 дней |
| Начало вызовов Bazel, которые отображаются как выполняющиеся до завершения | 2 дня |
| История компиляции модулей Xcode и кэша на постоянных страницах деталей модулей | 30 дней |
| Наблюдения за задачами, объявленными действиями Struo, действиями Bazel BEP, компилированными файлами и модулями на постоянных страницах деталей | 90 дней, кроме модулей Xcode выше |
| Постоянные метаданные идентичности задач/действий/модулей/файлов | 365 дней без наблюдений |
| Журналы заданий раннеров, архивные журналы раннеров и метрики машин заданий раннеров | 90 дней |
| Детализация покрытия кода по строкам (покрытие каждой строки и функции для каждого запуска тестов, отображаемое на странице покрытия файла) | 31 день |
| Общие показатели покрытия кода для каждого запуска тестов | 365 дней |
| Покрытие кода коммита (его общие показатели, цели и показатели по файлам) | 3 года; 90 дней для коммитов, добавленных только pull request |
| История доставки вебхуков | Нет фиксированного расписания удаления |

Постоянные URL-адреса деталей не зависят от доступности конкретной сборки. Их метаданные идентичности могут существовать дольше отдельных наблюдений, поэтому на странице деталей может отсутствовать история за выбранный период. Новая история индексируется из отчётов, полученных после развёртывания функции; существующая история на уровне запусков не копируется ретроспективно.

Внутренние таблицы журналов операций ClickHouse `system.*` настраиваются на уровне ClickHouse, а не политикой хранения данных продукта Tuist. По умолчанию они не ограничены; конфигурации Docker Compose для самостоятельного размещения и встроенные конфигурации Helm ClickHouse могут устанавливать для них лимиты, как описано в разделе <.localized_link href="/guides/server/self-host/server#capping-operational-log-retention">ограничение срока хранения журналов операций</.localized_link>.
