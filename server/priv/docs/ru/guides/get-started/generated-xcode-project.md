# Сгенерированный Xcode-проект {#generated-xcode-project}

::: code-group

```text [Agent prompt]
Help me get started with Tuist. Follow the setup at:
https://tuist.dev/en/docs/guides/get-started/generated-xcode-project
```

:::

Выбирайте этот путь, когда хотите, чтобы Tuist описывал и генерировал ваш Xcode-проект из Swift-манифестов. Сгенерированный проект сжимает сложность модульного Xcode-проекта в лаконичное декларативное описание графа. Это также строгое требование для кэша модулей и выборочного тестирования.

Каждый раздел ниже начинается с того, чего сейчас не хватает, а затем проводит вас через функцию, которая закрывает этот пробел.

## Предварительные требования

- macOS с установленным Xcode.
- <.localized_link href="/guides/install-tuist">Интерфейс командной строки Tuist</.localized_link>.

## Создание проекта

Самый быстрый способ увидеть всё в работе — начать с чистого проекта. В пустой директории выполните `tuist init`, выберите **Создать сгенерированный проект**, укажите платформу, подтвердите имя, затем пройдите аутентификацию и выберите аккаунт, которому должен принадлежать проект.

```bash
mkdir MyApp && cd MyApp
tuist init
```

Если вы управляете этим процессом из агента для написания кода или скрипта, сначала выполните `tuist auth login` (браузерный поток ждёт, пока вы нажмёте Enter), затем используйте неинтерактивную форму:

```bash
tuist init --build-system generated-xcode --name MyApp --platform ios --account <account>
```

Когда init завершится, выполните `tuist generate`. Tuist создаст файл `.xcworkspace` рядом с вашими манифестами и откроет его в Xcode. Соберите и запустите таргет. Вы должны увидеть запуск примера приложения в симуляторе.

Это состояние «подключено + генерируется». Всё ниже по тексту опционально и независимо.

Если вы переносите существующее приложение, сначала подключите его, следуя [руководству по миграции Xcode-проекта](https://tuist.dev/en/docs/guides/features/projects/adoption/migrate/xcode-project), затем вернитесь сюда и продолжайте с разделами, которые подходят для вашей задачи.

## Генерация проекта

Файл `.xcodeproj` упаковывает структуру вашего приложения в XML: ссылки на файлы, этапы сборки, зависимости таргетов, схемы и настройки сборки находятся в одном дереве, без примитива для анализа графа как графа. По мере роста проекта эту структуру всё сложнее удерживать в голове, а у Xcode нет стабильного идентификатора, который позволил бы инструментам хешировать её и пропускать работу, если ничего не изменилось.

Сгенерированные проекты сжимают граф в декларативный Swift. Файл `Project.swift` напрямую описывает таргеты, зависимости и ресурсы, а Tuist поддерживает за ним стабильную модель графа. Именно эта модель открывает возможности, описанные ниже: кэш модулей хеширует её для повторного использования бинарных файлов, а выборочное тестирование хеширует её, чтобы пропускать тесты, входные данные которых не изменились.

```swift
import ProjectDescription

let project = Project(
    name: "MyApp",
    targets: [
        .target(
            name: "MyApp",
            destinations: .iOS,
            product: .app,
            bundleId: "dev.tuist.MyApp",
            sources: ["MyApp/Sources/**"],
            dependencies: []
        )
    ]
)
```

Каждый вызов `tuist generate` создаёт детерминированное рабочее пространство из манифестов. Добавьте `.xcodeproj` и `.xcworkspace` в `.gitignore`.

## Кэш модулей

Компиляция модульного Xcode-проекта с нуля — это затраты на каждой машине. Каждый участник команды и каждый CI-раннер создаёт свою копию одних и тех же объектных файлов. Кэш компиляции Xcode сокращает внутренний цикл разработки, но не устраняет необходимость сборки каждого таргета на каждой машине и не может заменить целый фреймворк предварительно собранным бинарным файлом.

Кэш модулей делает именно это. Он один раз собирает каждую кешируемую зависимость в вашем графе (фреймворки, библиотеки, бандлы), сохраняет полученные бинарные файлы, привязывая их к хешу входных данных таргета, и при последующих генерациях подменяет таргет его бинарным файлом. Неизменённые модули перестают компилироваться:

```bash
tuist cache
```

Первый запуск компилирует всё и загружает бинарные файлы в ваш аккаунт. При следующем вызове `tuist generate` неизменённые зависимости заменяются их кешированными бинарными файлами, и Xcode линкуется с `.xcframework` вместо компиляции из исходного кода.

## Выборочное тестирование

`xcodebuild test` не знает, каких тестов касается изменение, поэтому CI запускает весь набор при каждом пуше. По мере роста набора разрыв между тем, что действительно нужно запустить, и тем, что запускается, увеличивается от минут до десятков минут.

Выборочное тестирование запускает только те тесты, на которые повлияли изменения с момента последнего успешного запуска тестов, используя граф проекта и тот же алгоритм хеширования, на который опирается кэш модулей:

```bash
tuist test
```

Первый вызов `tuist test` запускает всё и сохраняет хеши для каждого таргета. Последующие запуски пропускают таргеты, входные данные которых не изменились. Перенесите `tuist test` в CI вместо `xcodebuild test`, и обратная связь будет поступать за секунды, а не за минуты.

## Реестр пакетов

Swift Package Manager разрешает зависимости, выполняя глубокое клонирование git-истории каждого пакета, потому что пакеты адресуются по URL, а не через реестр. В проекте с десятками транзитивных пакетов разрешение зависимостей на чистой checkout-версии занимает минуты и повторяется в каждой задаче CI.

Реестр пакетов Tuist обслуживает те же пакеты, которые отслеживает Swift Package Index, но как настоящий реестр, поэтому SwiftPM загружает только нужный вам коммит. Включите его один раз, установив `registryEnabled: true` в вашем `Tuist.swift`:

```swift
let tuist = Tuist(
    project: .tuist(
        generationOptions: .options(
            registryEnabled: true
        )
    )
)
```

Выполните повторную генерацию. Разрешение зависимостей сокращается с минут до секунд.

## Аналитика сборок

Xcode записывает длительность сборки для каждого таргета в лог и в отчёт о сборке. Эти данные не агрегируются по запускам или по машинам, поэтому регрессия времени сборки обычно проявляется лишь как общее замедление CI.

Аналитика сборок автоматически записывает длительность каждой сборки и время выполнения этапов для сгенерированных схем. Дополнительная настройка не требуется. Откройте вкладку **Сборки** в дашборде после следующего цикла `tuist generate` + сборки.

## Аналитика тестов

Xcode сообщает результаты по каждому тесту по одному запуску за раз. Он не агрегирует межзапусковые сигналы, которые вам действительно нужны: уровень нестабильности, изменение длительности от недели к неделе, какие варианты симуляторов дают сбои.

Аналитика тестов автоматически записывает результат и длительность каждого теста для сгенерированных схем и коррелирует результаты между запусками. Нестабильные тесты, медленные тесты и сбои отображаются на вкладке **Тесты** в дашборде. Когда количество нестабильных тестов накапливается, помещайте их в карантин из дашборда, чтобы они перестали блокировать слияния.

## Подключите команду

Кэш модулей и выборочное тестирование дают наибольший эффект, когда вся команда работает с одной общей поверхностью. Пригласите коллег в организацию из настроек аккаунта в дашборде и настройте <.localized_link href="/guides/integrations/authentication/sso">Единый вход (SSO)</.localized_link> (Google, Okta, Microsoft), чтобы онбординг занимал один клик, а не требовал индивидуального `tuist auth login` для каждого человека.
