# Сгенерированный Xcode-проект {#generated-xcode-project}

::: code-group

```text [Agent prompt]
Help me get started with Tuist. Follow the setup at:
https://tuist.dev/en/docs/guides/get-started/generated-xcode-project
```

:::

Выбирайте этот путь, если хотите, чтобы Tuist описывал и генерировал ваш Xcode-проект из Swift-манифестов. Сгенерированный проект сжимает сложность модульного Xcode-проекта в лаконичное декларативное описание графа. Это также строгое требование для кэша модулей и выборочного тестирования.

Каждый раздел ниже начинается с того, чего сейчас не хватает, а затем проводит вас через функцию, которая закрывает этот пробел.

## Предварительные требования

- macOS с установленным Xcode.
- <.localized_link href="/guides/install-tuist">Интерфейс командной строки Tuist</.localized_link>.

## Создайте проект

Самый быстрый способ увидеть работу — начать с нового проекта. В пустой директории выполните `tuist init` и выберите **Создать сгенерированный проект**, укажите платформу, подтвердите имя, затем выполните аутентификацию и выберите аккаунт, которому должен принадлежать проект.

```bash
mkdir MyApp && cd MyApp
tuist init
```

Если вы управляете этим процессом через агент написания кода или скрипт, сначала выполните `tuist auth login` (браузерный поток ожидает нажатия Enter), затем используйте неинтерактивную форму:

```bash
tuist init --build-system generated-xcode --name MyApp --platform ios --account <account>
```

Когда инициализация завершится, выполните `tuist generate`. Tuist создаст файл `.xcworkspace` рядом с вашими манифестами и откроет его в Xcode. Соберите и запустите таргет. Вы должны увидеть запуск примера приложения в симуляторе.

Это состояние «подключено + генерируется». Всё ниже по тексту является опциональным и независимым.

Если вы переносите существующее приложение, сначала подключите его, следуя [руководству по миграции Xcode-проекта](https://tuist.dev/en/docs/guides/features/projects/adoption/migrate/xcode-project), затем вернитесь сюда и продолжайте с разделами, которые подходят для вашей задачи.

## Генерация проекта

Файл `.xcodeproj` упаковывает структуру вашего приложения в XML: ссылки на файлы, этапы сборки, зависимости таргетов, схемы и настройки сборки находятся в одном дереве, без примитива для рассуждения о графе как о графе. По мере роста проекта эту структуру всё сложнее удерживать в голове, а у Xcode нет стабильного идентификатора, позволяющего инструментам хешировать её и пропускать работу, когда ничего не изменилось.

Сгенерированные проекты сжимают граф в декларативный Swift. Файл `Project.swift` напрямую описывает таргеты, зависимости и ресурсы, а Tuist поддерживает стабильную модель графа за ним. Именно эта модель открывает доступ к разделам ниже: кэш модулей хеширует её для повторного использования бинарных файлов, а выборочное тестирование хеширует её, чтобы пропускать тесты, чьи входные данные не изменились.

```swift
import ProjectDescription

let project = Project(
    name: "MyApp",
    targets: [
        .target(
            name: "MyApp",
            destinations: .iOS,
            product: .app,
            bundleId: "dev.tuist.MyApp",
            sources: ["MyApp/Sources/**"],
            dependencies: []
        )
    ]
)
```

Каждый вызов `tuist generate` создаёт детерминированное рабочее пространство из манифестов. Добавьте `.xcodeproj` и `.xcworkspace` в `.gitignore`.

## Кэш модулей

Компиляция модульного Xcode-проекта с нуля обходится дорого для каждой машины. Каждый участник команды и каждый CI-раннер создаёт свою копию одних и тех же объектных файлов. Кэш компиляции Xcode сокращает внутренний цикл разработки, но не устраняет необходимость сборки каждого таргета на каждой машине и не может заменить целый фреймворк предварительно собранным бинарным файлом.

Кэш модулей делает это. Он собирает каждую кешируемую зависимость в вашем графе один раз (фреймворки, библиотеки, бандлы), сохраняет полученные бинарные файлы, привязывая их к хешу входных данных таргета, и заменяет таргет его бинарным файлом при последующих генерациях. Неизменённые модули перестают компилироваться:

```bash
tuist cache
```

Первый запуск компилирует всё и загружает бинарные файлы в ваш аккаунт. При следующем вызове `tuist generate` неизменённые зависимости заменяются их закэшированными бинарными файлами, и Xcode линкуется с `.xcframework` вместо компиляции из исходного кода.

## Выборочное тестирование

Команда `xcodebuild test` не знает, каких тестов касается изменение, поэтому CI запускает весь набор при каждом пуше. По мере роста набора разрыв между тем, что действительно нужно запустить, и тем, что запускается, увеличивается от минут до десятков минут.

Выборочное тестирование запускает только те тесты, на которые повлияли изменения с момента последнего успешного запуска тестов, используя граф проекта и тот же алгоритм хеширования, на который опирается кэш модулей:

```bash
tuist test
```

Первый вызов `tuist test` запускает всё и сохраняет хеши для каждого таргета. Последующие запуски пропускают таргеты, чьи входные данные не изменились. Перенесите `tuist test` в CI вместо `xcodebuild test`, и обратная связь будет поступать за секунды, а не за минуты.

## Реестр пакетов

Swift Package Manager разрешает зависимости, глубоко клонируя git-историю каждого пакета, потому что пакеты адресуются по URL, а не через реестр. В проекте с десятками транзитивных пакетов разрешение занимает минуты при чистой выгрузке и повторяется в каждой задаче CI.

Реестр пакетов Tuist предоставляет те же пакеты, которые отслеживает Swift Package Index, но как настоящий реестр, поэтому SwiftPM загружает только нужный вам коммит. Включите его один раз, установив `registryEnabled: true` в вашем файле `Tuist.swift`:

```swift
let tuist = Tuist(
    project: .tuist(
        generationOptions: .options(
            registryEnabled: true
        )
    )
)
```

Выполните повторную генерацию. Разрешение пакетов сократится с минут до секунд.

## Аналитика сборок

Xcode записывает длительность сборки для каждого таргета в лог и в отчёт о сборке. Ни то, ни другое не агрегируется по запускам или машинам, поэтому регрессия времени сборки обычно проявляется лишь как общее замедление CI.

Аналитика сборок автоматически записывает длительность каждой сборки и время выполнения этапов для сгенерированных схем. Ничего дополнительно настраивать не нужно. Откройте вкладку **Сборки** в панели управления после следующего цикла `tuist generate` + сборки.

## Аналитика тестов

Xcode сообщает результаты по каждому тесту для одного запуска за раз. Он не агрегирует межзапусковые сигналы, которые вам действительно нужны: уровень нестабильности, изменение длительности от недели к неделе, какие варианты симуляторов дают сбои.

Аналитика тестов автоматически записывает результат и длительность каждого теста для сгенерированных схем и сопоставляет результаты между запусками. Нестабильные тесты, медленные тесты и сбои отображаются на вкладке **Тесты** в панели управления. Когда количество нестабильных тестов накапливается, поместите их в карантин через панель управления, чтобы они перестали блокировать слияния.

## Подключите команду

Кэш модулей и выборочное тестирование дают наибольший эффект, когда вся команда работает с одной общей поверхностью. Пригласите участников команды в организацию через настройки аккаунта в панели управления и настройте <.localized_link href="/guides/integrations/authentication/sso">Единый вход (SSO)</.localized_link> (Google, Okta, Microsoft), чтобы онбординг занимал один клик, а не требовал индивидуального `tuist auth login` для каждого человека.
