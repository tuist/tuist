::: code-group

Следуйте этому пути, чтобы подключить существующий проект Gradle к Tuist. Плагин Gradle `dev.tuist` связывает локальный кэш сборок Gradle с удалённым кэшем Tuist и загружает данные о сборках и тестах в панель управления, не изменяя ни одной команды `./gradlew`.

Каждый раздел ниже начинается с описания того, чего сейчас не хватает, а затем показывает функцию, которая заполняет этот пробел.

## Предварительные требования

- Проект Gradle с файлом `settings.gradle.kts` (или `settings.gradle`).
- <.localized_link href="/guides/install-tuist">Интерфейс командной строки Tuist</.localized_link>.

## Подключение проекта

В корневом каталоге проекта Gradle выполните команду `tuist init`. Выберите **Интеграция проекта Gradle**, затем пройдите аутентификацию в браузере и выберите аккаунт, которому должен принадлежать проект.

```bash
tuist init
```

Если вы выполняете это действие через агента для написания кода или скрипт, сначала выполните команду `tuist auth login` (браузерный поток ожидает нажатия Enter), затем используйте неинтерактивную форму:

```bash
tuist init --build-system gradle --name <project-handle> --account <account>
```

Tuist создаёт файл `tuist.toml` в корне репозитория с идентификатором проекта и выводит блок `plugins { ... }`. Вставьте его в начало файла `settings.gradle.kts`:

```kotlin
plugins {
    id("dev.tuist") version "0.10.0"
}
```

Выполните проверку с помощью `./gradlew help`. Gradle должен загрузиться без ошибок. Если он не может найти плагин, убедитесь, что блок находится в `settings.gradle.kts`, а не в `build.gradle.kts`.

Все пункты ниже являются необязательными и независимыми.

## Удалённый кэш сборок

Локальный кэш сборок Gradle хранит результаты задач на машине, которая их создала. Два разработчика на одной ветке обращаются к кэшу в своих собственных каталогах `~/.gradle`, а не друг друга, а CI каждый раз использует новый пустой кэш.

Удалённый кэш Tuist расширяет тот же протокол ключ/значение, который Gradle уже использует между машинами. Результаты задачи загружаются на машине, которая первой её выполнила, и скачиваются всеми остальными, кто сталкивается с теми же входными данными. Включите его в файле `gradle.properties`:

```properties
org.gradle.caching=true
```

Затем выполните сборку в двух средах:

```bash
./gradlew clean build --build-cache --info
```

Задачи, поддерживающие кэширование, отчитываются как `FROM-CACHE` при втором запуске. Откройте раздел **Кэш** на панели управления, чтобы увидеть динамику попаданий в кэш.

## Аналитика сборок

Gradle выводит время выполнения задач в конце сборки, а с флагом `--profile` создаёт HTML-отчёт для каждой сборки. Ни то, ни другое не агрегирует данные между запусками. Задача, которая замедлилась за серию коммитов, выглядит в отчёте любой отдельной сборки так же, как и всегда.

Плагин `dev.tuist` автоматически загружает время выполнения задач для каждой сборки на панель управления после применения плагина. Дополнительная настройка не требуется. Откройте раздел **Сборки** на панели управления после следующего выполнения `./gradlew build`, чтобы увидеть тенденцию.

## Аналитика тестов

Отчёты о тестах Gradle сохраняются для каждой сборки в каталоге `build/reports/tests/`. Тест, который периодически падает в десяти запусках CI, в любом отдельном отчёте выглядит как стабильный тест, который однажды случайно упал.

Аналитика тестов записывает результат и длительность каждой задачи для каждого запуска `./gradlew test` и сопоставляет результаты между запусками. Нестабильные тесты, медленные тесты и сбои отображаются на вкладке **Тесты** панели управления. Когда количество нестабильных тестов накапливается, изолируйте их через панель управления, чтобы они перестали блокировать слияния.

Плагин также поддерживает **режим стресс-тестирования**, который повторно запускает тесты, добавленные сборкой, и помечает те из них, которые оказываются нестабильными, до их попадания в основную ветку. Добавьте это в расширение `tuist` в файле `settings.gradle.kts`:

```kotlin
tuist {
    stressNewTests {
        mode = "report" // or "enforce"
    }
}
```

## Аналитика бандлов

Android Gradle Plugin сообщает размер созданного файла `.aab` в выводе сборки. Это число исчезает вместе с веткой, а сравнение размеров между релизами становится ручной учётной задачей. Play Console сообщает те же числа, но только после загрузки артефакта.

Аналитика бандлов записывает размеры установки и скачивания для каждого файла `.aab` (рекомендуется) или `.apk` и может завершать проверку PR ошибкой, если превышен порог для ветки. Добавьте это в ваш CI сразу после шага сборки:

```bash
tuist inspect bundle App.aab
```

Откройте раздел **Аналитика бандлов → Android** на панели управления, чтобы увидеть тенденцию и настроить пороги.

## Превью

Внутренний тестовый трек Play Console добавляет задержку на проверку и распространение при каждом обмене. Отправка сырого файла `.apk` через Slack или электронную почту быстрее, но теряется связь между конкретным сообщением и соответствующей сборкой.

Превью превращает сборку в ссылку для общего доступа, которую получатели устанавливают одной командой:

```bash
tuist share App.apk
```

## Подключение команды

Попадания в кэш, аналитика и стресс-тестирование становятся тем эффективнее, чем больше людей подключено к проекту. Пригласите своих коллег в организацию через настройки аккаунта на панели управления и настройте <.localized_link href="/guides/integrations/authentication/sso">Единый вход (SSO)</.localized_link> (Google, Okta, Microsoft), чтобы процесс адаптации занимал один клик, а не требовал индивидуального выполнения `tuist auth login` для каждого человека.

Для CI не используйте личный логин. Установите `TUIST_TOKEN` с областью действия вашего проекта (создайте его в настройках проекта на панели управления).
