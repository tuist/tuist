Следуйте этому пути, чтобы подключить существующий проект Gradle к Tuist. Плагин Gradle `dev.tuist` связывает локальный кэш сборок Gradle с удаленным кэшем Tuist и загружает данные о сборках и тестах в панель управления, не изменяя ни одной команды `./gradlew`.

Каждый раздел ниже начинается с описания того, чего сейчас не хватает, а затем показывает функцию, которая заполняет этот пробел.

## Предварительные требования

- Проект Gradle с файлом `settings.gradle.kts` (или `settings.gradle`).
- <.localized_link href="/guides/install-tuist">Интерфейс командной строки Tuist</.localized_link>.

## Подключение проекта

В корневой директории проекта Gradle выполните `tuist init`. Выберите **Интегрировать проект Gradle**, затем пройдите аутентификацию в браузере и выберите аккаунт, которому должен принадлежать проект.

```bash
tuist init
```

Если вы выполняете это через агента кодирования или скрипт, сначала запустите `tuist auth login` (браузерный поток ждет, пока вы нажмете Enter), затем используйте неинтерактивную форму:

```bash
tuist init --build-system gradle --name <project-handle> --account <account>
```

Tuist создает файл `tuist.toml` в корне репозитория с идентификатором проекта и выводит блок `plugins { ... }`. Вставьте его в начало файла `settings.gradle.kts`:

<!-- @snippet: ../_gradle-plugin-block -->

Выполните проверку с помощью `./gradlew help`. Gradle должен загрузиться без ошибок. Если плагин не найден, убедитесь, что блок находится в `settings.gradle.kts`, а не в `build.gradle.kts`.

Все нижеперечисленное является необязательным и независимым.

## Удаленный кэш сборок

Локальный кэш сборок Gradle хранит результаты задач на машине, которая их создала. Два разработчика, работающие над одной веткой, используют кэш в своих собственных директориях `~/.gradle`, но не друг друга, а CI каждый раз обращается к новому, пустому кэшу.

Удаленный кэш Tuist расширяет тот же протокол ключ/значение, который Gradle уже использует между машинами. Результаты задачи загружаются на машине, которая первой ее выполнила, и скачиваются всеми остальными, кто сталкивается с теми же входными данными. Включите его в `gradle.properties`:

```properties
org.gradle.caching=true
```

Затем выполните сборку в двух средах:

```bash
./gradlew clean build --build-cache --info
```

Задачи, поддерживающие кэширование, сообщают `FROM-CACHE` при втором запуске. Откройте раздел **Кэш** на панели управления, чтобы увидеть процент попаданий в кэш со временем.

## Аналитика сборок

Gradle выводит время выполнения задач в конце сборки и с помощью `--profile` создает HTML-отчет для каждой сборки. Ни один из этих методов не агрегирует данные по нескольким запускам. Задача, которая замедлилась в серии коммитов, выглядит в отчете любой отдельной сборки так же, как и всегда.

Плагин `dev.tuist` автоматически загружает время выполнения задач для каждой сборки на панель управления после применения плагина. Дополнительная настройка не требуется. Откройте раздел **Сборки** на панели управления после следующего `./gradlew build`, чтобы увидеть тенденцию.

## Аналитика тестов

Отчеты о тестах Gradle создаются для каждой сборки в директории `build/reports/tests/`. Тест, который периодически падает в десяти запусках CI, в любом конкретном отчете выглядит как стабильный тест, который просто однажды упал.

Аналитика тестов записывает результат и длительность каждой задачи для каждого запуска `./gradlew test` и коррелирует результаты между запусками. Нестабильные тесты, медленные тесты и сбои отображаются на вкладке **Тесты** панели управления. Когда количество нестабильных тестов накапливается, изолируйте их через панель управления, чтобы они перестали блокировать слияния.

Плагин также поддерживает **режим стресс-тестирования**, который повторно запускает тесты, добавленные сборкой, и помечает те, которые оказываются нестабильными, до их попадания в основную ветку. Добавьте его в расширение `tuist` в файле `settings.gradle.kts`:

```kotlin
tuist {
    stressNewTests {
        mode = "report" // or "enforce"
    }
}
```

## Покрытие кода

JaCoCo создает отчет о покрытии для каждой тестовой задачи и для каждой машины. Ничто не объединяет отчеты задач CI одного коммита и не показывает, увеличилось или уменьшилось покрытие ветки.

Плагин может измерять покрытие ваших модульных тестов JVM и Android с помощью JaCoCo и загружать данные о покрытии при каждом запуске тестов. Tuist объединяет запуски одного коммита, включая шарды, в одну цифру. Включите это в расширении `tuist` в файле `settings.gradle.kts`:

```kotlin
tuist {
    coverage {
        enabled = true
    }
}
```

Откройте раздел **Покрытие кода** на панели управления, чтобы видеть данные по коммитам и файлам. См. <.localized_link href="/guides/features/test-code-coverage/gradle">Покрытие кода Gradle</.localized_link> для настройки завершения коммита в CI и Robolectric.

## Аналитика бандлов

Android Gradle Plugin сообщает размер созданного `.aab` в выводе сборки. Это число исчезает вместе с веткой, а сравнение размеров между релизами требует ручной работы. Play Console сообщает те же числа, но только после загрузки артефакта.

Аналитика бандлов записывает размеры установки и скачивания для каждого `.aab` (рекомендуется) или `.apk` и может отклонить проверку PR, если превышен порог для ветки. Добавьте это в ваш CI сразу после шага сборки:

```bash
tuist inspect bundle App.aab
```

Откройте раздел **Аналитика бандлов → Android** на панели управления, чтобы увидеть тенденцию и настроить пороги.

## Превью

Внутренний тестовый трек Play Console добавляет задержку на проверку и распространение при каждом обмене. Отправка сырого `.apk` через Slack или электронную почту быстрее, но теряется связь с тем, к какой сборке относится конкретное сообщение.

Плагин может собирать и публиковать вариант приложения напрямую, без отдельной загрузки через CLI:

```bash
./gradlew :app:tuistShareDebug --track nightly
```

Запрос задачи `tuistShare<Variant>` включает эту сборку в публикацию; обычные сборки никогда не загружают превью. См. <.localized_link href="/guides/features/previews/gradle">Превью Gradle</.localized_link> для информации о поддерживаемых APK, подписи и установке.

## Подключите команду

Попадания в кэш, аналитика и стресс-тестирование становятся эффективнее с увеличением числа людей, подключенных к проекту. Пригласите коллег в организацию через настройки аккаунта на панели управления и настройте <.localized_link href="/guides/integrations/authentication/sso">Единый вход (SSO)</.localized_link> (Google, Okta, Microsoft), чтобы онбординг занимал один клик, а не требовал индивидуального `tuist auth login` для каждого человека.

Для CI не используйте личный логин. Аутентифицируйтесь через OIDC-идентификатор вашего провайдера CI или создайте токен аккаунта с пресетом **CI** на панели управления и установите его как `TUIST_TOKEN`. См. <.localized_link href="/guides/server/authentication#gradle-plugin-authentication">Аутентификация плагина Gradle</.localized_link>.
