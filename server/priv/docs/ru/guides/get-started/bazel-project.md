# Проект Bazel {#bazel-project}

::: code-group

```text [Agent prompt]
Help me get started with Tuist. Follow the setup at:
https://tuist.dev/en/docs/guides/get-started/bazel-project
```

:::

Следуйте этому пути, чтобы подключить существующее рабочее пространство Bazel к Tuist. Tuist предоставляет кэш [Remote Execution API](https://github.com/bazelbuild/remote-apis), к которому Bazel подключается как к удалённому кэшу, а также поток Build Event Service, который превращает каждую сборку и тест в видимые данные на панели управления.

Каждый раздел ниже начинается с описания того, чего не хватает сегодня, а затем проводит вас через функцию, которая заполняет этот пробел.

## Предварительные требования

- Рабочее пространство Bazel (файл `WORKSPACE` или `MODULE.bazel` в его корне) и Bazel, доступный в вашем `PATH`.
- <.localized_link href="/guides/install-tuist">Интерфейс командной строки Tuist</.localized_link>.

## Подключение рабочего пространства

> [!NOTE]
> Рабочий процесс Bazel внутри `tuist init` требует версии CLI Tuist, которая поставляется вместе с ним. В более ранних версиях `tuist init` не будет предлагать «Integrate a Bazel workspace» в качестве опции. В качестве альтернативы выполните `tuist auth login`, а затем `tuist bazel setup` из корня рабочего пространства, что проведёт вас через те же шаги, что и ниже.

Из корня рабочего пространства Bazel выполните `tuist init`. Tuist обнаруживает `WORKSPACE` / `MODULE.bazel` и предлагает **Integrate a Bazel workspace**. Пройдите аутентификацию в браузере и выберите учётную запись, которой должен принадлежать проект.

```bash
tuist init
```

Если вы управляете этим процессом через агента кодирования или скрипт, сначала выполните `tuist auth login` (браузерный поток ожидает нажатия Enter), затем используйте неинтерактивную форму:

```bash
tuist init --build-system bazel --name <project-handle> --account <account>
```

Когда init завершится, Tuist:

1. Записывает `tuist.toml` в корне рабочего пространства с идентификатором проекта.
2. Записывает `.bazelrc.tuist` рядом с вашим `.bazelrc`, настроенный на ближайший регион кэша Tuist и аутентифицированный через вспомогательный инструмент учётных данных для каждого рабочего пространства.
3. Добавляет строку `try-import %workspace%/.bazelrc.tuist` в ваш `.bazelrc`.

Зафиксируйте строку `try-import` в системе контроля версий. Она идентична на каждой машине. Добавьте `.bazelrc.tuist` в ваш `.gitignore`. Путь к вспомогательному инструменту учётных данных зависит от пользователя, а регион кэша — от местоположения, поэтому их не следует передавать другим.

Всё перечисленное ниже включается автоматически после подключения рабочего пространства.

## Удалённый кэш

Собственный локальный дисковый кэш Bazel находится в `~/.cache/bazel` (или там, куда указывает `--disk_cache`). Попадание в кэш на машине одного разработчика не доступно другим, а контейнеры заданий CI каждый раз запускаются с пустым кэшем.

[Remote Execution API](https://github.com/bazelbuild/remote-apis) от Bazel — это протокол для расширения этого же кэша до общей конечной точки. Tuist поддерживает его. Как только `.bazelrc.tuist` настроен, Bazel пропускает действия, результаты которых уже есть в общем кэше, и загружает их вместо выполнения. Работа одной машины приносит пользу всем остальным машинам, собирающим ту же ревизию.

Проверьте с помощью двух чистых сборок для одной и той же ревизии (локально или одна локальная + одна в CI):

```bash
bazel clean
bazel build //...
```

Сводка второго запуска должна сообщать о попаданиях в кэш. Откройте раздел **Cache** на панели управления, чтобы увидеть коэффициент попаданий со временем.

## Аналитика сборок и тестов

Поток событий сборки Bazel и XML-отчёты по каждому тесту генерируются при каждом вызове. Сравнение длительностей на уровне целей в течение недели или выявление теста, ставшего нестабильным за несколько запусков в CI, означает сбор и агрегацию этих событий где-либо.

Протокол Build Event Service, который уже генерирует Bazel, предназначен именно для этого. `.bazelrc.tuist`, созданный `tuist init`, настраивает поток BES против Tuist, поэтому аналитика сборок и тестов начинает поступать при следующем `bazel build` и `bazel test`. Ничего дополнительно настраивать не нужно. Откройте разделы **Builds** и **Tests** на панели управления, чтобы увидеть данные.

## Подключите команду

Попадания в кэш и аналитика накапливаются с увеличением числа людей, подключённых к проекту. Пригласите своих коллег в организацию через настройки учётной записи на панели управления и настройте <.localized_link href="/guides/integrations/authentication/sso">Single Sign-On</.localized_link> (Google, Okta, Microsoft), чтобы онбординг занимал один клик, а не требовал индивидуального `tuist auth login` для каждого человека.
