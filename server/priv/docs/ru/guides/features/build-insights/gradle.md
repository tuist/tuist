# Аналитика сборок Gradle {#gradle-build-insights}

Плагин Gradle от Tuist может отправлять аналитику сборок в Tuist, предоставляя информацию о выполнении задач и производительности сборки.

## Настройка поведения загрузки {#configure-upload-behavior}

По умолчанию:
- Аналитика сборок загружается в фоновом режиме для локальных сборок.
- Аналитика сборок загружается в активном режиме при запусках в CI, чтобы избежать потери телеметрии на кратковременных агентах.

Вы можете управлять этим поведением, используя `uploadInBackground` внутри расширения `tuist`:

```kotlin
tuist {
    uploadInBackground = false // always upload in the foreground
}
```

## Справочник конфигурации {#configuration-reference}

Опция `uploadInBackground` доступна в блоке расширения `tuist` в файле `settings.gradle.kts`:

| Опция | Тип | По умолчанию | Описание |
| --- | --- | --- | --- |
| `uploadInBackground` | `Boolean?` | `null` (в фоне локально, в активном режиме в CI) | Загружать ли аналитику сборок в фоновом режиме для локальных сборок. |

Эта настройка не влияет на параметры удалённого кэша в блоке `buildCache`.

## Указание актора в отчётах {#report-actor-claim}

Запросы на отправку отчётов о сборках и тестах включают необязательный заголовок `x-tuist-actor-id` только если вы явно установили `TUIST_ACTOR_ID` в метку уровня организации или настроили `buildInsights.actorId` в своих параметрах. По умолчанию метка не отправляется, и плагин не определяет имена пользователей операционной системы. Переопределение через переменные окружения имеет приоритет. Установите любое из переопределений в пустую строку, чтобы исключить идентификатор из отчёта; это не удаляет личность, установленную индивидуальными учётными данными. Недействительные переопределения исключают указание актора вместо возврата к значению по умолчанию. Если пользовательский прокси отклоняет неизвестные заголовки, откажитесь от отправки, задав `TUIST_ACTOR_ID=""`.

```kotlin
tuist {
    buildInsights {
        actorId = providers.environmentVariable("CORPORATE_ACTOR_ID").getOrElse("")
    }
}
```

Идентификаторы акторов состоят из 1–128 байт печатных символов ASCII, кроме пробела. Они видны всем, кто может просматривать отчёты проекта, включая публичных зрителей, если проект общедоступен, и экспортируются вместе с отчётами. Не включайте секреты или личную информацию, которую вы не хотите публиковать. В панели управления приоритет имеет проверенная индивидуальная учётная запись; идентификаторы, отправляемые клиентами, иначе явно помечаются как **Непроверенные**. Они никогда не предоставляют права доступа и не связываются автоматически с пользователем Tuist. Старые серверы игнорируют заголовок атрибуции, а новые серверы продолжают принимать старые клиенты без него. Новые отчёты с общим токеном без идентификатора показывают **Неизвестно**, а не публикующую организацию; исторические отчёты сохраняют прежнюю атрибуцию. В списках сборок и тестов фильтры по проверенным пользователям отделены от фильтров по непроверенным идентификаторам акторов.

## Публикация с доверием к сети {#network-trusted-publishing}

Развёртывания на собственных серверах могут явно разрешать отчёты о сборках и тестах Gradle из доверенной сети без учётных данных разработчиков. Оператор должен сначала настроить `TUIST_NETWORK_TRUSTED_INSIGHTS_ACCESS=true` на экземпляре и перезапустить его. Это применяется ко всем поддерживаемым проектам; настройки в панели управления нет. См. <.localized_link href="/guides/server/self-host/server#network-trusted-access">руководство по самостоятельному размещению</.localized_link>.

Настройте назначение один раз в репозитории:

```kotlin
tuist {
    project = "organization/project"
    url = "https://tuist.internal.example"
    buildCache { enabled = false }
}
```

Отправка отчётов о сборках и тестах не требует аутентифицированного обнаружения конечных точек кэша. Отключите кэш, если экземпляр отдельно не включает доступ к кэшу с доверием к сети или разработчики не предоставляют токены. Неподписанные отчёты о тестах опускают ссылки на шарды и существующие сборки и не запускают автоматизацию карантина или определения нестабильности. Поиск карантина пропускается, когда учётные данные действительно отсутствуют; при наличии действительных учётных данных сохраняется существующее поведение с аутентификацией. Если учётные данные присутствуют, они всё равно используются, а недействительные учётные данные приводят к ошибке вместо перехода к публикации без учётных данных. Когда учётные данные отсутствуют, плагин автоматически определяет, разрешает ли самостоятельно размещённый сервер отправку отчётов без учётных данных. Флаги клиента или настройка `buildInsights` не требуются. Обновите каждую реплику сервера до версии с поддержкой обнаружения перед обновлением клиентов, работающих без учётных данных. Более старые серверы без обнаружения, отключённые экземпляры и ошибки обнаружения по-прежнему требуют аутентификации; аутентифицированная публикация остаётся совместимой. Явно пустое значение `TUIST_TOKEN` приводит к отказу в публикации, а не к включению публикации без учётных данных. Для задач форков или Dependabot без секретов удалите эту переменную вместо того, чтобы определять её как пустую строку.

Сервер назначает идентификаторы отчётов без учётных данных. Повторная отправка может создать второй отчёт; этот режим не гарантирует идемпотентность повторных попыток или корреляцию с аутентифицированными отчётами о тестах. Такие отчёты не могут вызывать комментарии в системе контроля версий или автоматические события агентов сбоев. Доступ к сети является границей доверия для публикации, а не доказательством личности указанного актора.

## Пользовательские метаданные {#custom-metadata}

Добавляйте теги и данные в формате «ключ-значение» к сборкам Gradle, чтобы сравнивать запуски разных команд, оборудования или рабочих процессов. Теги доступны как фильтры в панели управления, а значения отображаются на странице деталей каждой сборки, а также в интерфейсе прикладного программирования и инструментах Model Context Protocol.

Задайте метаданные через переменные окружения:

```sh
export TUIST_BUILD_TAGS="nightly,android"
export TUIST_BUILD_VALUE_TICKET="TUIST-123"
export TUIST_BUILD_VALUE_RUNNER="macos-14"
```

Вы также можете настроить метаданные в файле `settings.gradle.kts`:

```kotlin
tuist {
    buildInsights {
        tag("nightly")
        tag("android")
        value("ticket", "TUIST-123")
        value("runner", "macos-14")
    }
}
```

Если одно и то же значение настроено в обоих местах, приоритет имеет значение в файле `settings.gradle.kts`.

Теги должны содержать только буквы, цифры, дефисы и подчёркивания. Сборка может иметь до 50 тегов, каждый тег — до 50 символов. Сборка может иметь до 20 записей «ключ-значение», каждый ключ — до 50 символов, каждое значение — до 500 символов. Это те же ограничения на стороне сервера, что и для метаданных сборок Xcode. Плагин пропускает недопустимые теги и слишком большие или пустые записи метаданных перед отправкой отчёта, поэтому неверная конфигурация не препятствует сохранению остальной части отчёта аналитики сборки. Используйте метаданные «ключ-значение» для значений, не соответствующих ограничениям тегов.

Пользовательские метаданные видны участникам проекта в панели управления, а также через интерфейс прикладного программирования и инструменты Model Context Protocol. Не используйте их для учётных данных, токенов доступа или других конфиденциальных данных. Tuist хранит данные сборок Gradle, включая эти метаданные, в течение 90 дней. Подробнее см. в <.localized_link href="/guides/server/data-retention">политике хранения данных</.localized_link>.

## Подробности о сбоях {#failure-details}

При сбое сборки плагин сообщает причину сбоя каждой неудачной задачи или шага конфигурации: сообщение об исключении и цепочку причин, как они выводятся в консоли Gradle, например ошибки компилятора при неудачном выполнении задачи `compileJava` или ошибку в скрипте сборки. Стек-трейсы и вывод задач не собираются. Перед отправкой отчёта плагин преобразует пути внутри проекта в относительные, а Tuist удаляет учётные данные и другие распознаваемые локальные пути. Каждое сообщение ограничено 16 КиБ, и сборка хранит сообщения не более чем для 32 неудачных шагов.

Сообщения о сбоях доступны участникам проекта через интерфейс прикладного программирования, инструменты Model Context Protocol (`get_gradle_build`, `list_gradle_build_tasks` и `get_gradle_build_step`) и CLI:

```bash
tuist build gradle failure list <build-id>
```

Сообщения могут содержать фрагменты исходного кода и сведения о проекте. Отчёты, опубликованные без учётных данных через [публикацию с доверием к сети](#network-trusted-publishing), не включают их. Tuist хранит их вместе с остальными данными сборок Gradle в течение 90 дней.
