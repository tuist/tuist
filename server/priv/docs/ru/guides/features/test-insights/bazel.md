# Аналитика тестов Bazel {#bazel-test-insights}

Запускайте тесты Bazel через Tuist, чтобы использовать те же панели мониторинга тестов, что и для любой другой системы сборки:

```bash
tuist bazel test -- //app:tests
```

Аргументы после `--` передаются в `bazel test`. Используйте `--path` для выбора проекта и рабочего каталога, а `--bazel` — для выбора другого исполняемого файла, например `bazelisk`. Обычный `bazel test` по-прежнему выводит результаты тестов, но не получает и не применяет политики карантина Tuist.

> [!NOTE]
> Обёртка `tuist bazel test` требуется только для <.localized_link href="/guides/features/test-insights/flaky-tests/bazel">тестов в карантине</.localized_link>. Отчётность по отдельным случаям для обычных запусков тестов настраивается с помощью `tuist bazel setup` в `.bazelrc.tuist`, поэтому обычный `bazel test` также выводит данные по отдельным случаям.

## Что отслеживается {#what-is-tracked}

Tuist анализирует отчёты `test.xml` и собирает вывод `test.log`, который Bazel генерирует для каждой цели теста, а затем агрегирует их в общей модели запусков тестов. Каждый запуск фиксирует:

- Статус прохождения, сбоя или пропуска каждого отдельного тестового случая вместе с длительностью.
- Цель теста, класс и структуру набора тестов.
- Попытки повторного запуска, если Bazel настроен на повтор нестабильных тестов.
- Вывод ошибок, полученный из `test.log` цели.

Страницы **Запуски тестов**, **Тестовые случаи** и отдельных тестов работают для Bazel так же, как и для других систем сборки.

## Генерация отчётов JUnit по отдельным случаям {#per-case-junit-reports}

Строки по отдельным случаям зависят от того, записывает ли цель теста JUnit-файл `test.xml` по пути `$XML_OUTPUT_FILE`, предоставленному Bazel. Если исполнитель не создаёт такой файл, Bazel использует синтетический отчёт с одним случаем, названный по имени цели, и Tuist показывает одну строку на цель (помеченную как **Цель Bazel** в списке тестовых случаев), при этом исходный `test.log` остаётся доступным на странице запуска.

Большинство правил тестирования Bazel уже создают настоящий `test.xml`:

- `java_test` и `kt_jvm_test`: JUnit встроен.
- `cc_test` с GoogleTest: исполнитель записывает JUnit при компиляции против свежей версии gtest; в старых конфигурациях требуется `--gtest_output=xml:$XML_OUTPUT_FILE`.
- `py_test`: используйте pytest с `--junitxml=$XML_OUTPUT_FILE` или исполнитель pytest из `rules_python`.
- `go_test`: передайте вывод `go test -json` через `gotestsum --junitfile=$XML_OUTPUT_FILE` или оберните вспомогательным скриптом, генерирующим JUnit.

`rust_test` из `rules_rust` и `rules_rs` использует стандартный механизм `libtest`, который не создаёт JUnit в стабильной версии Rust. Оберните цель теста скриптом, который разбирает вывод `libtest` и записывает JUnit в `$XML_OUTPUT_FILE`; так вы сохраните строки по отдельным случаям в Tuist, а запуск останется одной целью теста Bazel.

## Идентификация тестов {#test-identity}

Случаи идентифицируются по метке цели, имени класса (с резервным вариантом имени набора) и имени теста. Это позволяет разделять методы с одинаковыми именами в разных классах. Старые отчёты, использовавшие другое имя охватывающего набора, сохраняют историю под старой идентификацией; изменения состояния, применённые к старой идентификации, необходимо повторно применить к новой, а команда предупреждает вас, когда сбой соответствует старой идентификации, чтобы вы знали, какую политику перенести.

## Предоставление контекста CI {#providing-ci-context}

Tuist считывает информацию о коммите и ветке Git из метаданных сборки Bazel, чтобы можно было сравнивать запуски на одном и том же коммите в разных окружениях. Большинство систем непрерывной интеграции уже устанавливают эти значения; если ваша система этого не делает, передайте их явно:

```bash
tuist bazel test -- \
  --build_metadata=CI=true \
  --build_metadata=GIT_COMMIT="$GIT_COMMIT" \
  --build_metadata=GIT_BRANCH="$GIT_BRANCH" //app:tests
```

Тот же флаг `--build_metadata` описан на странице <.localized_link href="/guides/features/build-insights/bazel#custom-metadata">Аналитика сборок Bazel</.localized_link> для маркировки запусков, поэтому один набор флагов покрывает обе функции.

## Нестабильные тесты и карантин {#flaky-tests-and-quarantine}

Повторные запуски, обнаружение нестабильности между запусками и карантин отдельных тестов (Отключить и Пропустить) работают через `tuist bazel test`. Полный рабочий процесс описан в разделе <.localized_link href="/guides/features/test-insights/flaky-tests/bazel">Нестабильные тесты в Bazel</.localized_link>.

## Хранение данных {#data-retention}

Tuist хранит команду вызова Bazel, которая запустила тест, её логи и ожидающие обработки записи о тестах в течение 90 дней. Тест-кейсы и история их запусков используют ту же модель, что и другие системы сборки, и не подпадают под это ограничение сроков. Полную политику см. в разделе <.localized_link href="/guides/server/data-retention">Хранение данных</.localized_link>.
