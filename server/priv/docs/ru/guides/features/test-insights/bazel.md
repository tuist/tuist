# Аналитика тестов Bazel {#bazel-test-insights}

Запускайте тесты Bazel через Tuist, чтобы данные попадали на те же панели мониторинга тестов, что и для других систем сборки:

```bash
tuist bazel test -- //app:tests
```

Аргументы после `--` передаются в `bazel test`. Используйте `--path`, чтобы выбрать проект и рабочий каталог, и `--bazel`, чтобы указать другой исполняемый файл, например `bazelisk`. Обычный вызов `bazel test` по-прежнему выводит результаты тестов, но не получает и не применяет политики карантина Tuist.

> [!NOTE]
> Обёртка `tuist bazel test` требуется только для <.localized_link href="/guides/features/test-insights/flaky-tests/bazel">тестов в карантине</.localized_link>. Отчёты по отдельным тест-кейсам для обычных запусков тестов настраиваются командой `tuist bazel setup` в файле `.bazelrc.tuist`, поэтому обычный вызов `bazel test` также отображает отдельные кейсы.

## Что отслеживается {#what-is-tracked}

Tuist разбирает отчёты `test.xml` и собирает вывод `test.log`, который Bazel генерирует для каждой цели теста, а затем агрегирует их в общую модель запусков тестов. Каждый запуск фиксирует:

- Статус прохождения, сбоя или пропуска каждого отдельного тест-кейса, а также длительность выполнения.
- Цель теста, класс и структуру набора тестов.
- Попытки повторного запуска, если Bazel настроен на повтор нестабильных тестов.
- Вывод ошибок, полученный из файла `test.log` цели.

Страницы **Запуски тестов**, **Тест-кейсы** и страницы отдельных тестов работают для Bazel так же, как и для других систем сборки.

## Формирование JUnit-отчётов по каждому кейсу {#per-case-junit-reports}

Строки с детализацией по кейсам появляются, когда цель теста записывает JUnit-файл `test.xml` по пути `$XML_OUTPUT_FILE`, который предоставляет Bazel. Если раннер не создаёт такой файл, Bazel формирует синтетический отчёт с одним кейсом, названный по имени цели, и Tuist показывает одну строку на цель (с меткой **Цель Bazel** в списке тест-кейсов), при этом исходный файл `test.log` остаётся доступен на странице запуска.

Большинство правил тестирования Bazel уже создают полноценный файл `test.xml`:

- `java_test` и `kt_jvm_test`: поддержка JUnit встроена.
- `cc_test` с GoogleTest: раннер записывает JUnit, если сборка выполнена против свежей версии gtest; в старых конфигурациях нужно добавить флаг `--gtest_output=xml:$XML_OUTPUT_FILE`.
- `py_test`: используйте pytest с флагом `--junitxml=$XML_OUTPUT_FILE` или раннер pytest из `rules_python`.
- `go_test`: передайте вывод `go test -json` через `gotestsum --junitfile=$XML_OUTPUT_FILE` или оберните вызов вспомогательной утилитой, которая генерирует JUnit.

`rust_test` из `rules_rust` и `rules_rs` использует стандартный harness `libtest`, который не создаёт JUnit-отчёты в стабильной версии Rust. Оберните цель теста скриптом, который разбирает вывод `libtest` и записывает JUnit в `$XML_OUTPUT_FILE`; так вы сохраните детализацию по кейсам в Tuist, а запуск останется одной целью теста Bazel.

## Идентификация тестов {#test-identity}

Кейсы идентифицируются по метке цели, имени класса (с откатом к имени набора тестов) и имени теста. Это позволяет разделять методы с одинаковыми именами из разных классов. Старые отчёты, использовавшие другое имя охватывающего набора тестов, сохраняют историю под прежней идентичностью; изменения состояния, применённые к старой идентичности, нужно повторно применить к новой, а команда предупреждает, если сбой совпадает со старой идентичностью, чтобы вы знали, какую политику перенести.

## Передача контекста CI {#providing-ci-context}

Tuist считывает информацию о коммите и ветке Git из метаданных сборки Bazel, чтобы запуски на одном и том же коммите можно было сравнивать между окружениями. Большинство систем непрерывной интеграции уже устанавливают эти значения; если ваша система этого не делает, передайте их явно:

```bash
tuist bazel test -- \
  --build_metadata=CI=true \
  --build_metadata=GIT_COMMIT="$GIT_COMMIT" \
  --build_metadata=GIT_BRANCH="$GIT_BRANCH" //app:tests
```

Тот же флаг `--build_metadata` используется для пометки вызовов, как описано на странице <.localized_link href="/guides/features/build-insights/bazel#custom-metadata">Инсайты сборки Bazel</.localized_link>, поэтому один набор флагов покрывает обе области.

## Нестабильные тесты и карантин {#flaky-tests-and-quarantine}

Повторные запуски, обнаружение нестабильности между запусками и карантин отдельных тест-кейсов (игнорирование и пропуск) работают через `tuist bazel test`. Полный рабочий процесс описан в разделе <.localized_link href="/guides/features/test-insights/flaky-tests/bazel">Нестабильные тесты в Bazel</.localized_link>.

## Хранение данных {#data-retention}

Tuist хранит в течение 90 дней вызов Bazel, который создал запуск тестов, его логи и ожидающие обработки записи импорта тестов. Тест-кейсы и история их запусков используют ту же модель, что и для других систем сборки, и не подпадают под этот срок. Полную политику см. в разделе <.localized_link href="/guides/server/data-retention">хранение данных</.localized_link>.
