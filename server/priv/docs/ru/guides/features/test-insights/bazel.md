# Аналитика тестов Bazel {#bazel-test-insights}

> [!IMPORTANT]
> **Требования**
>
> - Рабочее пространство Bazel, подключенное через `tuist bazel setup`, как описано в <.localized_link href="/guides/get-started/bazel-project">Начало работы с проектом Bazel</.localized_link>.

`tuist bazel setup` настраивает отчётность по каждому тест-кейсу в `.bazelrc.tuist`, поэтому обычный `bazel test` отправляет отдельные тест-кейсы на те же дашборды, что и любая другая система сборки:

```bash
bazel test //app:tests
```

Чтобы также применить <.localized_link href="/guides/features/test-insights/flaky-tests/bazel">карантин</.localized_link>, запускайте тесты через обёртку Tuist. Аргументы после `--` передаются в `bazel test`:

```bash
tuist bazel test -- //app:tests
```

## Что отслеживается {#what-is-tracked}

Tuist разбирает отчёты `test.xml` и фиксирует вывод `test.log`, который Bazel генерирует для каждой цели теста, а затем агрегирует их в общую модель запусков тестов. Каждый запуск записывает:

- Статус прохождения, сбоя или пропуска отдельного тест-кейса вместе с длительностью.
- Структуру целей теста, классов и наборов.
- Попытки повторного запуска, если Bazel настроен на повтор нестабильных тестов.
- Вывод ошибок, полученный из `test.log` цели.

Страницы **Запуски тестов**, **Тест-кейсы** и отдельных тестов работают для Bazel так же, как и для других систем сборки.

## Генерация JUnit-отчётов по каждому тест-кейсу {#per-case-junit-reports}

Строки по каждому тест-кейсу зависят от того, записывает ли цель теста JUnit-файл `test.xml` по пути `$XML_OUTPUT_FILE`, который предоставляет Bazel. Если раннер не создаёт такой файл, Bazel использует синтетический отчёт с одним тест-кейсом, названный по имени цели, и Tuist показывает одну строку на цель (помеченную как **Цель Bazel** в списке тест-кейсов), при этом исходный `test.log` остаётся доступен на странице запуска.

Большинство правил тестирования Bazel уже создают настоящий `test.xml`:

- `java_test` и `kt_jvm_test`: JUnit встроен.
- `cc_test` с GoogleTest: раннер записывает JUnit при компиляции с недавней версией gtest; в старых конфигурациях требуется `--gtest_output=xml:$XML_OUTPUT_FILE`.
- `py_test`: используйте pytest с `--junitxml=$XML_OUTPUT_FILE` или раннер pytest из `rules_python`.
- `go_test`: передайте вывод `go test -json` через `gotestsum --junitfile=$XML_OUTPUT_FILE` или оберните вспомогательным скриптом, который генерирует JUnit.

`rust_test` из `rules_rust` и `rules_rs` использует стандартный механизм `libtest`, который не записывает JUnit в стабильной версии Rust. Оберните цель теста скриптом, который разбирает вывод `libtest` и записывает JUnit в `$XML_OUTPUT_FILE`; так вы сохраните строки по каждому тест-кейсу в Tuist, а тот же запуск останется одной целью теста Bazel.

## Идентификация тестов {#test-identity}

Тест-кейсы идентифицируются по метке цели, имени класса (с резервным вариантом — имя набора) и имени теста. Это позволяет разделять методы с одинаковыми именами в разных классах. Более старые отчёты, использовавшие другое имя охватывающего набора, сохраняют историю под старой идентичностью; изменения состояния, применённые к старой идентичности, нужно повторно применить к новой, и команда предупреждает вас, когда сбой соответствует старой идентичности, чтобы вы знали, какую политику перенести.

## Предоставление контекста CI {#providing-ci-context}

Tuist считывает информацию о коммите и ветке git из метаданных сборки Bazel, чтобы можно было сравнивать запуски на одном и том же коммите между средами. Большинство систем непрерывной интеграции уже устанавливают эти значения; если ваша этого не делает, передайте их явно:

```bash
tuist bazel test -- \
  --build_metadata=CI=true \
  --build_metadata=GIT_COMMIT="$GIT_COMMIT" \
  --build_metadata=GIT_BRANCH="$GIT_BRANCH" //app:tests
```

Тот же флаг `--build_metadata` описан на странице <.localized_link href="/guides/features/build-insights/bazel#custom-metadata">Аналитика сборок Bazel</.localized_link> для маркировки вызовов, поэтому один набор флагов покрывает обе области.

## Нестабильные тесты и карантин {#flaky-tests-and-quarantine}

Повторные запуски, обнаружение нестабильности между запусками и карантин по каждому тест-кейсу (Игнорировать и Пропустить) работают через `tuist bazel test`. Полное описание рабочего процесса см. в разделе <.localized_link href="/guides/features/test-insights/flaky-tests/bazel">Нестабильные тесты Bazel</.localized_link>.

## Хранение данных {#data-retention}

Tuist хранит вызов Bazel, который породил запуск теста, его логи и ожидающие обработки записи импорта тестов в течение 90 дней. Тест-кейсы и история их запусков используют ту же модель, что и любая другая система сборки, и не попадают под этот срок. Полную политику см. в разделе <.localized_link href="/guides/server/data-retention">хранение данных</.localized_link>.
