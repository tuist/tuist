# Аналитика тестов Rust {#rust-test-insights}

Tuist отчитывается об отдельных результатах тестов из `cargo test`, включая модульные тесты, интеграционные тесты и doctests. Зависимости Rust или дополнительный запускальщик тестов не требуются.

> [!IMPORTANT]
> **Требования**
>
> - Следуйте инструкциям по <.localized_link href="/guides/get-started/rust-project">настройке проекта Rust</.localized_link>.

## Отчетность о запусках тестов {#report-your-test-runs}

```sh
tuist cargo test --workspace
```

При настроенной обертке mise для Cargo вы можете продолжать вводить `cargo test`. Cargo по-прежнему компилирует и запускает ваши тесты со своими обычными аргументами, выводом и кодом выхода. Ошибки отчетности не влияют на результат ваших тестов.

Вы можете выбрать пакет или отфильтровать тесты как обычно:

```sh
tuist cargo test -p store
tuist cargo test authentication
```

## Что отслеживает Tuist {#what-is-tracked}

- Пройденные, проваленные и проигнорированные тесты из завершенных наборов тестов.
- Модульные тесты, интеграционные тесты и doctests.
- Длительность выполнения всего набора тестов.
- Доступные метаданные ветки, коммита, CI и раннера.

Отфильтрованные тесты и тесты, не выполненные после сбоя, никогда не отмечаются как пройденные. Результаты отображаются в разделе **Тесты** на панели управления.

## Непрерывная интеграция {#continuous-integration}

Tuist распознает GitHub Actions, GitLab CI, Bitrise, CircleCI, Buildkite и Codemagic и связывает каждый запуск с его задачей CI. В любой другой системе CI запуск считается запуском CI, если установлена переменная окружения `CI`. Большинство систем CI устанавливают её самостоятельно; установите её вручную там, где это не делается, например, на Fly.io Machines. Обнаружение нестабильных тестов сравнивает только запуски CI.

Задача, которая получает коммит вместо ветки, оставляет Git без имени ветки, поэтому у её запусков нет ветки. В системах CI, которые распознает Tuist, ветка берется от провайдера. В остальных случаях задайте её через `TUIST_GIT_BRANCH`:

```sh
CI=true TUIST_GIT_BRANCH=main tuist cargo test --workspace
```

## Пакеты, модули и тестовые случаи {#test-hierarchy}

Tuist группирует результаты по пакету и цели Cargo. Пути модулей Rust группируют отдельные тесты внутри цели:

| Метка на панели управления | Значение в Rust | Пример |
| --- | --- | --- |
| Модули | Пакет и цель Cargo | `store::api` |
| Наборы тестов | Пути модулей Rust | `api::authentication` |
| Тестовые случаи | Отдельные тесты | `rejects_invalid_token` |

Doctests используют отдельный модуль, например `store::doctest/store`. Их имена включают расположение в исходном коде, поэтому перемещение примера может изменить его идентификатор.

## Doctests и длительность {#cargo-test}

Doctests запускаются с вашей обычной командой тестирования, включая примеры `compile_fail`, `should_panic` и `no_run`. Чтобы запустить только doctests:

```sh
tuist cargo test --doc
```

Стабильный libtest сообщает время выполнения всего набора, но не длительность отдельных тестов. Недоступные временные метки исключаются из истории длительности по случаям и аналитики длительности, при этом результаты тестов по-прежнему влияют на надежность и количество запусков.

## Ограничения отчетности {#reporting-limits}

Отдельные результаты собираются из стандартного вывода Cargo/libtest. Команды, использующие `--no-run`, `--list`, тихий или подробный вывод Cargo, альтернативные форматы или неперехваченный вывод тестов, выполняются нормально без отчетности по отдельным тестам. Пользовательские harnesses, неполные сводки, неоднозначное определение цели и отчеты чрезмерного размера не загружаются.

Если пакеты рабочего пространства имеют интеграционные цели с одинаковыми именами, выберите одну из них с помощью `-p <package>`. Отчетность поддерживает точные имена пакетов рабочего пространства; пакеты зависимостей, селекторы с указанием версии и глобальные шаблоны выполняются нормально, но не отчитываются. Абсолютные пути doctest опускаются, чтобы пути checkout не попадали в идентификаторы тестов.

Tuist потоково передает вывод во время сбора результатов. Это может повлиять на автоматическое определение цвета. Фоновые процессы, которые оставляют каналы вывода открытыми после завершения Cargo, могут привести к пропуску отчета, но не изменяют код выхода Cargo.

## Надежность и выборка {#reliability-and-selection}

Используйте <.localized_link href="/guides/features/test-insights/flaky-tests/rust">обнаружение нестабильных тестов и карантин</.localized_link> для исследования нестабильных тестов и их игнорирования или пропуска. <.localized_link href="/guides/features/test-sharding/rust">Разделение тестов</.localized_link> распределяет целые цели Cargo между работниками CI. Включите <.localized_link href="/guides/features/test-code-coverage/rust">покрытие кода</.localized_link>, чтобы отслеживать покрытие строк в ваших запусках тестов. Выборка тестов на основе покрытия и распределение с однократной сборкой недоступны для обычных запусков тестов Cargo.

## Устранение неполадок {#troubleshooting}

Если запуск теста не отображается на панели управления, включите отладочный вывод, чтобы увидеть, почему отчет не был отправлен:

```sh
TUIST_DEBUG=1 tuist cargo test --workspace
```
