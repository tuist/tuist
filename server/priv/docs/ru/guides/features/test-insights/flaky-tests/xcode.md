# Нестабильные тесты Xcode {#xcode-flaky-tests}

> [!WARNING]
> **Требования**
>
> - <.localized_link href="/guides/features/test-insights/xcode">Xcode test insights</.localized_link> настроены. Tuist обнаруживает нестабильные тесты по событиям аналитики тестов, которые загружаются при каждом запуске тестов.

Нестабильные тесты — это тесты, которые дают разные результаты (проходят или падают) при многократном запуске с одним и тем же кодом. Они подрывают доверие к набору тестов и отнимают время разработчиков на расследование ложных сбоев. Tuist автоматически обнаруживает нестабильные тесты и помогает отслеживать их со временем.

![Страница нестабильных тестов](/images/guides/features/test-insights/flaky-tests-page.png)

## Как работает обнаружение нестабильности {#how-it-works}

Tuist обнаруживает нестабильные тесты двумя способами:

### Повторные запуски тестов {#test-retries}

Когда вы запускаете тесты с функцией повторных попыток, Tuist анализирует результаты каждой попытки. Если тест падает в одних попытках, но проходит в других, он помечается как нестабильный.

Передайте `-retry-tests-on-failure` или `-test-iterations` через `tuist xcodebuild test`:

```sh
tuist xcodebuild test \
  -scheme MyScheme \
  -retry-tests-on-failure \
  -test-iterations 3
```

![Детали нестабильного тест-кейса](/images/guides/features/test-insights/flaky-test-case-detail.png)

### Обнаружение между запусками {#cross-run-detection}

Даже без повторных запусков тестов Tuist может обнаруживать нестабильные тесты, сравнивая результаты разных запусков CI для одного и того же коммита, схемы и указанного назначения (имя устройства, платформа и версия ОС). Если тест проходит в одном подходящем запуске CI, но падает в другом, неудачное выполнение помечается как нестабильное. Это работает независимо от того, какой результат приходит первым.

Один и тот же тест может вести себя по-разному в зависимости от схемы или назначения. Например, прохождение на iOS 26 и падение на iOS 27 не свидетельствует о нестабильности. Результаты из разных схем, устройств, платформ или версий ОС не помечают друг друга как нестабильные.

Результаты без привязанного назначения сравниваются с другими непривязанными результатами отдельно от результатов с известным назначением. Сюда входят отчёты с отсутствующими или неполными метаданными назначения и отчёты, содержащие несколько различных назначений, поскольку отдельные результаты тестов пока нельзя отнести к конкретному назначению. Различия между средами в этой группе всё ещё могут приводить к ложной классификации нестабильности. Обнаружение на основе повторных запусков продолжает работать. Существующие исторические классификации нестабильности остаются неизменными.

Это особенно полезно для выявления нестабильных тестов, которые не падают достаточно последовательно, чтобы быть пойманными повторными запусками, но всё равно вызывают периодические сбои в CI.

## Управление нестабильными тестами {#managing-flaky-tests}

### Автоматическая очистка

Обнаружение и очистка выполняются через **автоматизацию с оповещением** в проекте. Каждый проект получает автоматизацию «Обнаружение нестабильных тестов» по умолчанию, чей *триггер* помечает тест как нестабильный, а *восстановление* снимает флаг, когда тест проходит настроенное окно восстановления (по умолчанию **14 дней**) без повторного срабатывания. Отредактируйте её в разделе **Settings → Automations**, чтобы изменить окно восстановления, заменить действия восстановления (например, также снять карантин) или полностью отключить восстановление, чтобы тесты оставались помеченными как нестабильные, пока вы не снимете метку вручную.

### Ручное управление

Вы также можете вручную помечать или снимать пометку нестабильности с тестов на странице деталей тест-кейса. Это полезно, когда:
- Вы хотите подтвердить известный нестабильный тест, работая над исправлением
- Тест был ошибочно помечен из-за проблем с инфраструктурой

## Карантин нестабильных тестов {#quarantining}

Карантин изолирует нестабильный тест, чтобы он не блокировал CI, пока вы его исправляете. По умолчанию это **ручное действие** — вы помещаете в карантин, снимаете карантин и переключаете режимы на странице деталей тест-кейса в панели управления, — но вы также можете настроить это через **автоматизацию с оповещением** в разделе **Settings → Automations**, чтобы тест автоматически игнорировался (или пропускался) при превышении порога нестабильности и снимался с карантина при восстановлении. Каждое изменение, ручное или автоматическое, записывается в журнал аудита тест-кейса.

Тест в карантине находится в одном из двух режимов:

- **Игнорирование сбоев**: тест всё ещё выполняется, но `tuist xcodebuild test` маскирует сбой. Сбои всё ещё поступают в детектор нестабильных тестов, поэтому вы можете продолжать наблюдать за тестом, не ломая сборку. Выбирайте этот режим для теста, который вы активно исследуете.
- **Пропуск**: xcodebuild получает `-skip-testing <identifier>`, поэтому тест никогда не запускается. Он не создаёт новых результатов и исчезает из панели нестабильных тестов, пока вы не включите его снова. Выбирайте этот режим, когда тест сломан, медленный или настолько постоянно нестабилен, что его запуск просто тратит минуты CI впустую.

### Почему тесты в карантине могут отображаться как прошедшие {#quarantined-passing}

- **Тесты с игнорированием сбоев** всё ещё выполняются. Тест с игнорированием сбоев, который упал, записывается как **упавший** в запуске тест-кейса и помечается как нестабильный — статус отдельного теста не перезаписывается. Переопределяется **общий результат запуска тестов**: если каждый упавший тест-кейс в запуске имеет игнорирование сбоев, весь запуск сообщается как пройденный, поэтому такие сбои не ломают CI.
- **Пропущенные тесты** вообще не запускаются, поэтому панель управления продолжает показывать статус последнего фактического выполнения теста — этот снимок может быть недельной давности.

### Запуск тестов {#running-tests}

`tuist xcodebuild test` — это прозрачная обёртка, которая автоматически учитывает оба режима. Используйте её так же, как вызывали бы xcodebuild:

```sh
tuist xcodebuild test -scheme MyScheme
```

Пропущенные тесты добавляются к вашему вызову xcodebuild как `-skip-testing <identifier>` и никогда не запускаются. Тесты с игнорированием сбоев выполняются нормально; если они падают, сбой маскируется в итоговом статусе сборки.

#### Обход карантина

`tuist xcodebuild test` принимает `--skip-quarantine`, чтобы запустить всё, включая тесты с игнорированием сбоев и пропущенные тесты:

```sh
tuist xcodebuild test --skip-quarantine -scheme MyScheme
```

#### Прямой вызов xcodebuild

Если вы не можете использовать `tuist xcodebuild test`, самостоятельно разверните тесты в карантине в аргументы `-skip-testing` с помощью `tuist test case list`:

```sh
xcodebuild test \
  -scheme MyScheme \
  $(tuist test case list --quarantined --skip-testing)
```

Это безопасный вариант по умолчанию вне `tuist xcodebuild test`: маскировка сбоев для тестов с игнорированием происходит только при использовании этой команды, поэтому пропуск обоих режимов позволяет избежать ложных сбоев CI. Если вам нужен более тонкий контроль, используйте вместо этого `tuist xcodebuild test`.

## Стресс-тестирование новых тестов {#stress-testing-new-tests}

Шлюз стресс-тестирования повторно запускает тест-кейсы, добавленные вашей веткой, несколько раз каждый в отдельном процессе и сообщает о тех, которые оказываются нестабильными. Вы увидите новый нестабильный тест в пул-реквесте, который его добавил, а не спустя недели.

Тест-кейс считается новым, если он не запускался в CI за последние 90 дней на ветке проекта по умолчанию или на коммите, который впоследствии был включён в неё. При использовании очереди слияния тест-кейс, запущенный очередью, становится известным после включения коммита очереди, и остаётся новым, если очередь его отбрасывает. Коммиты сопоставляются через <.localized_link href="/guides/features/test-insights/xcode#git-history">историю Git</.localized_link>, которую Tuist собирает в CI.

### Включение

Шлюз по умолчанию отключён. Выберите режим:

- **`report`**: предупреждает о каждом нестабильном тест-кейсе. Завершение процесса зависит от его собственного результата.
- **`enforce`**: нестабильный тест-кейс приводит к сбою запуска с тем же кодом выхода, что и упавший тест.

Начните с `report` на пару недель, чтобы увидеть, что бы заблокировал `enforce`.

Передайте его перед сквозными аргументами или установите `TUIST_TEST_STRESS_NEW_TESTS`, чтобы менять режим для каждого этапа CI:

```sh
tuist xcodebuild test --stress-new-tests report -scheme MyScheme
```

### Сколько раз каждый тест перезапускается

Это зависит от того, сколько времени занял тест-кейс при первом проходе:

| Первый проход | Повторные запуски |
| --- | --- |
| До 5 с | 10 |
| До 10 с | 5 |
| До 30 с | 3 |
| До 5 мин | 2 |
| Более 5 мин | Не перезапускается |

Повторные запуски используют артефакты, собранные при первом проходе. Проход останавливается после 200 тест-кейсов или 10 минут — в зависимости от того, что наступит раньше, — и указывает, какой лимит был достигнут.

### Когда шлюз не запускается

- Первый проход уже завершился с ошибкой. Сначала исправьте эти тесты.
- У проекта нет основной ветки, или в CI на ней ещё ничего не запускалось.
- Более 30% тест-кейсов проекта выглядят новыми. Повторный запуск такого количества займёт слишком много времени. Это ожидаемо для проекта, который только начал отправлять данные в Tuist, или после переименования, которое перемещает сразу много тестов.

## Запрос состояния нестабильности и карантина {#querying}

### CLI

Дерево команд `tuist test case` предоставляет всю информацию, которую Tuist отслеживает о тест-кейсе:

```sh
tuist test case list --flaky                       # only flaky test cases
tuist test case list --quarantined                 # only muted or skipped test cases
tuist test case show <test_case_id>                # detail: flakiness rate, last status, run counts
tuist test case events <test_case_id>              # audit log: marked_flaky, muted, skipped, ...
tuist test case run list <test_case_id>            # run history with status and duration
tuist test case run show <test_case_run_id>        # single run, including failure breakdown
```

Все они поддерживают `--json` для скриптов.

### REST API

Те же данные доступны по HTTP — см. [эндпоинты тест-кейсов](https://tuist.dev/api/docs#tag/test-cases) в справочнике API для полного списка маршрутов, фильтров и полей ответа. Чтобы изменить состояние тест-кейса (отметить или снять отметку нестабильности, включить игнорирование сбоев, пропустить), отправьте `PATCH /api/projects/{account_handle}/{project_handle}/tests/test-cases/{test_case_id}` с параметром `is_flaky` или `state`. То же изменение доступно через `tuist test case update` и инструмент Model Context Protocol `update_test_case`.
