# Нестабильные тесты в Rust {#rust-flaky-tests}

Tuist может обнаруживать противоречивые результаты тестов Cargo и помогать вам исследовать их в разделе **Tests → Flaky Tests**.

> [!IMPORTANT] Requirements
> - Настройте <.localized_link href="/guides/features/test-insights/rust">Rust Test Insights</.localized_link>.

## Как работает обнаружение нестабильности {#how-it-works}

Tuist сравнивает запуски CI для одного и того же коммита. Тест, который проходит в одном запуске и падает в другом, может быть помечен как нестабильный.

Отправляйте данные каждого запуска с помощью обычной команды:

```sh
tuist cargo test --workspace
```

Cargo не повторяет упавшие тесты автоматически. Повторный запуск задания CI для того же коммита предоставляет еще один результат для межзапускового обнаружения.

## Управление нестабильными тестами {#managing-flaky-tests}

### Автоматическая очистка

Обнаружение и восстановление выполняются через автоматизацию проекта «Flaky test detection». По умолчанию флаг нестабильности снимается через 14 дней без повторного срабатывания. Измените окно восстановления и действия в разделе **Settings → Automations**.

### Ручное управление

Откройте **Tests → Flaky Tests**, чтобы просмотреть историю теста. Вы можете вручную пометить или снять пометку о нестабильности на странице деталей теста.

## Карантин и стресс-тестирование {#quarantine}

Отключите уведомления или пропустите тест на странице его деталей либо настройте карантин в разделе **Settings → Automations**. Следующий вызов `tuist cargo test` получит текущее состояние карантина проекта:

- **Muted** (отключенные) тесты все равно выполняются и сообщают свои фактические результаты, но их падения не приводят к ошибке команды. Другие падения тестов, ошибки компиляции, сбои и неполные результаты по-прежнему приводят к ошибке.
- **Skipped** (пропущенные) тесты исключаются из выполнения и отчеты показывают их как пропущенные из-за карантина. Сопоставление включает пакет, цель, путь модуля Rust и имя теста, поэтому тесты с похожими именами остаются независимыми.

Отключение уведомлений сохраняет выбранные пакеты рабочего пространства и функции, а также запускает все выбранные цели, даже если отключенная цель падает. Пропуск карантина требует выбора одного пакета: используйте `tuist cargo test -p store` вместо команды для рабочего пространства с несколькими пакетами. Tuist отклоняет пропуск нескольких пакетов, поскольку сужение команды может изменить унифицированные зависимости функций Cargo.

Карантин также применяется к <.localized_link href="/guides/features/test-sharding/rust">шардированным запускам Cargo</.localized_link>. Если Tuist не может получить состояние, он выводит предупреждение и выполняет запуск без карантина; падения не подавляются. Чтобы намеренно выполнить запуск без карантина:

```sh
TUIST_TEST_SKIP_QUARANTINE=1 tuist cargo test --workspace
```

Применение требует стандартных harness-ов libtest и захвата вывода по умолчанию. Команды с тихим, подробным, альтернативным форматом или незахваченным выводом завершаются ошибкой, когда необходимо применить карантин. Выберите точный пакет рабочего пространства с помощью `-p <package>`, если атрибуция цели неоднозначна. Пользовательские harness-ы, глобы имен пакетов/целей и неразрешенные выборы пакетов не поддерживаются. Doctests также можно отключать или пропускать, но фильтрация тестов Rustdoc не может различить каждую возможную пару имен примеров. Если пропуск примера также пропустит включенный пример или частичное исключение doctest использует `--exact`, Tuist завершается с диагностикой, а не выполняет пропущенный пример или молча пропускает включенные тесты; используйте вышеуказанное переопределение во время расследования.

Tuist не проводит стресс-тестирование новых тестов Cargo. Используйте фильтр тестов Cargo, чтобы повторить падающий тест во время его исследования:

```sh
tuist cargo test -p store rejects_invalid_token
```
