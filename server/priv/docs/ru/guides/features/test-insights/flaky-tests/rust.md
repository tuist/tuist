# Нестабильные тесты в Rust {#rust-flaky-tests}

Tuist может обнаруживать несогласованные результаты тестов Cargo и помогать исследовать их в разделе **Тесты → Нестабильные тесты**.

> [!IMPORTANT]
> **Требования**
>
> - Настройте <.localized_link href="/guides/features/test-insights/rust">Rust Test Insights</.localized_link>.

## Как работает обнаружение нестабильных тестов {#how-it-works}

Tuist сравнивает запуски CI на одном и том же коммите. Тест, который проходит в одном запуске и падает в другом, может быть помечен как нестабильный. В системе CI, которую Tuist не распознаёт, установите `CI=true`, чтобы её запуски учитывались как запуски CI: см. <.localized_link href="/guides/features/test-insights/rust#continuous-integration">непрерывную интеграцию</.localized_link>.

Отправляйте каждый запуск через обычную команду:

```sh
tuist cargo test --workspace
```

Cargo не повторяет упавшие тесты автоматически. Повторный запуск задачи CI на том же коммите даёт ещё один результат для межзапускового обнаружения.

## Карантин нестабильных тестов {#quarantining}

Игнорируйте или пропускайте тест со страницы его деталей либо настройте карантин в разделе **Настройки → Автоматизации**. Следующий вызов `tuist cargo test` получит текущее состояние карантина проекта:

- **Игнорируемые** тесты всё равно запускаются и сообщают свои фактические результаты, но их сбои не приводят к падению команды. Другие сбои тестов, ошибки компиляции, падения и неполные результаты по-прежнему приводят к ошибке.
- **Пропущенные** тесты исключаются из выполнения и отчитываются как пропуски из-за карантина. Сопоставление включает пакет, цель, путь модуля Rust и имя теста, поэтому тесты с похожими именами остаются независимыми.

Игнорирование сохраняет выбранные пакеты рабочего пространства и возможности, а также запускает все выбранные цели, даже если игнорируемая цель упала. Пропуск по карантину требует выбора одного пакета: используйте `tuist cargo test -p store` вместо команды для многопакетного рабочего пространства. Tuist отклоняет пропуск нескольких пакетов, потому что сужение команды может изменить унифицированные возможности зависимостей Cargo.

Карантин также применяется к <.localized_link href="/guides/features/test-sharding/rust">разделённым запускам Cargo</.localized_link>. Если Tuist не может получить состояние, он выводит предупреждение и запускает тесты без карантина; сбои не подавляются. Чтобы намеренно запустить без карантина:

```sh
TUIST_TEST_SKIP_QUARANTINE=1 tuist cargo test --workspace
```

### Ограничения {#limitations}

- Применение требует стандартных обвязок libtest и захвата вывода по умолчанию. Команды с тихим, подробным, альтернативным форматом или без захвата вывода завершаются ошибкой, когда нужно применить карантин.
- Выбирайте точный пакет рабочего пространства с помощью `-p <package>`, если атрибуция цели неоднозначна. Пользовательские обвязки, шаблоны имён пакетов/целей и неразрешённые выборы пакетов не поддерживаются.
- Доктесты тоже можно игнорировать или пропускать, но фильтрация тестов Rustdoc не может различить каждую возможную пару имён примеров. Если пропуск примера привёл бы также к пропуску включённого примера или частичное исключение доктеста использует `--exact`, Tuist завершается с диагностикой вместо выполнения пропущенного примера или молчаливого пропуска включённых тестов. Используйте указанное выше переопределение во время исследования.

## Стресс-тестирование новых тестов {#stress-testing-new-tests}

Tuist не выполняет стресс-тестирование новых тестов Cargo. Используйте фильтр тестов Cargo, чтобы повторить падающий тест во время его исследования:

```sh
tuist cargo test -p store rejects_invalid_token
```
