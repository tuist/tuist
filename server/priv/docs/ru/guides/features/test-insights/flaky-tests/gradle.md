# Нестабильные тесты Gradle {#gradle-flaky-tests}

> **Требования**
>
> - Настроены <.localized_link href="/guides/features/test-insights/gradle">инсайты тестов Gradle</.localized_link>.

<!-- @snippet: ./_intro -->

![Страница нестабильных тестов](/images/guides/features/test-insights/flaky-tests-page.png)

## Как работает обнаружение нестабильности {#how-it-works}

Tuist обнаруживает нестабильные тесты двумя способами:

### Повторные запуски тестов {#test-retries}

Когда вы запускаете тесты с функцией повторных попыток, Tuist анализирует результаты каждой попытки. Если тест падает в некоторых попытках, но проходит в других, он помечается как нестабильный.

Вы можете использовать [плагин Test Retry](https://github.com/gradle/test-retry-gradle-plugin) или аналогичный механизм для повторного запуска упавших тестов. Tuist обнаружит тесты, которые проходят в одних попытках, но падают в других.

Добавьте плагин в ваш `build.gradle.kts`:

```kotlin
plugins {
    id("org.gradle.test-retry") version "1.6.2"
}

tasks.test {
    retry {
        maxRetries = 3
        maxFailures = 5
        failOnPassedAfterRetry = false
    }
}
```

![Детали нестабильного тест-кейса](/images/guides/features/test-insights/flaky-test-case-detail.png)

### Обнаружение между запусками {#cross-run-detection}

Даже без повторных запусков тестов Tuist может обнаруживать нестабильные тесты, сравнивая результаты разных запусков CI на одном и том же коммите и в одном и том же проекте Gradle. Если тест проходит в одном запуске CI, но падает в другом запуске для того же коммита и проекта, упавшее выполнение помечается как нестабильное.

Проект Gradle является частью ключа сравнения, потому что один и тот же тест может детерминированно вести себя по-разному в разных проектах — например, общий тестовый класс, скомпилированный с разными зависимостями или запущенный на другом фикстуре модуля. Два запуска одного и того же коммита на разных проектах Gradle рассматриваются как отдельные варианты выполнения и не будут помечать друг друга как нестабильные.

Это особенно полезно для выявления нестабильных тестов, которые падают недостаточно регулярно, чтобы их поймали повторные запуски, но всё ещё вызывают периодические сбои в CI.

## Карантин нестабильных тестов {#quarantining}

<!-- @snippet: ./_quarantine-intro -->

Тест в карантине находится в одном из двух режимов:

- **Игнорирование сбоев**: тест всё ещё выполняется, но плагин устанавливает `ignoreFailures = true` и повторно прерывает сборку только при сбоях тестов вне карантина. Сбои всё ещё поступают в детектор нестабильных тестов, поэтому вы можете продолжать наблюдать за тестом, не ломая сборку. Выбирайте этот режим для теста, который вы активно исследуете.
- **Пропуск**: плагин фильтрует тест через Gradle’s `excludeTestsMatching`, поэтому он никогда не запускается. Он не создаёт новых результатов и исчезает с дашборда нестабильных тестов, пока вы не включите его снова. Выбирайте этот режим, когда тест сломан, медленный или настолько постоянно нестабилен, что его запуск просто тратит минуты CI впустую.

<!-- @snippet: ./_quarantined-passing -->

### Включение карантина {#enabling-quarantine}

Карантин **автоматически включается в CI** (когда установлена переменная окружения `CI`) и отключается для локальных сборок. Плагин получает список тестов в карантине с сервера Tuist перед каждой задачей тестирования; тесты с игнорированием сбоев выполняются нормально, и их сбои маскируются, пропущенные тесты фильтруются.

Вы можете явно управлять этим в вашем `settings.gradle.kts`:

```kotlin
tuist {
    testQuarantine {
        enabled = true  // or false to disable
    }
}
```

Когда `enabled` не установлен, по умолчанию используется автоопределение: включено в CI, отключено локально.

## Стресс-тестирование новых тестов {#stress-testing-new-tests}

<!-- @snippet: ./_stress-intro -->

Тест-кейс считается новым, если он не запускался в CI за последние 90 дней на основной ветке проекта или на коммите, который уже был в неё вмержен. При использовании очереди слияния тест-кейс, запущенный очередью, становится известным, когда коммит очереди попадает в ветку, и остаётся новым, если очередь его отбрасывает. Коммиты сопоставляются через <.localized_link href="/guides/features/test-insights/gradle#git-history">историю Git</.localized_link>, которую Tuist собирает в CI.

<!-- @snippet: ./_stress-modes -->

Объявите это в `settings.gradle.kts` или установите `TUIST_TEST_STRESS_NEW_TESTS`, чтобы варьировать режим для каждого канала CI:

```kotlin
tuist {
    stressNewTests {
        mode = "report" // or "enforce"
    }
}
```

В отличие от карантина, у гейта нет значения по умолчанию, учитывающего CI. Без установленного `mode` он нигде не запускается.

<!-- @snippet: ./_stress-reruns -->

Каждый повторный запуск — это вложенная сборка Gradle, отфильтрованная до одного конкретного тест-кейса, поэтому каждый повторный запуск получает свежую JVM для тестов.
