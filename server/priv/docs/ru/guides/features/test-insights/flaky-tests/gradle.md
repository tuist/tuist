# Нестабильные тесты Gradle {#gradle-flaky-tests}

Нестабильные тесты — это тесты, которые дают разные результаты (проходят или падают) при многократном запуске с одним и тем же кодом. Они подрывают доверие к вашему набору тестов и отнимают время разработчиков на расследование ложных сбоев. Tuist автоматически обнаруживает нестабильные тесты и помогает отслеживать их со временем.

![Страница нестабильных тестов](/images/guides/features/test-insights/flaky-tests-page.png)

## Как работает обнаружение нестабильности {#how-it-works}

Tuist обнаруживает нестабильные тесты двумя способами:

### Повторные запуски тестов {#test-retries}

Когда вы запускаете тесты с функцией повторных попыток, Tuist анализирует результаты каждой попытки. Если тест падает в некоторых попытках, но проходит в других, он помечается как нестабильный.

Вы можете использовать [плагин Test Retry](https://github.com/gradle/test-retry-gradle-plugin) или аналогичный механизм для повторного запуска упавших тестов. Tuist обнаружит тесты, которые проходят в некоторых попытках, но падают в других.

Добавьте плагин в ваш `build.gradle.kts`:

```kotlin
plugins {
    id("org.gradle.test-retry") version "1.6.2"
}

tasks.test {
    retry {
        maxRetries = 3
        maxFailures = 5
        failOnPassedAfterRetry = false
    }
}
```

![Детали случая нестабильного теста](/images/guides/features/test-insights/flaky-test-case-detail.png)

### Обнаружение между запусками {#cross-run-detection}

Даже без повторных запусков тестов Tuist может обнаруживать нестабильные тесты, сравнивая результаты разных запусков CI для одного и того же коммита и одного и того же проекта Gradle. Если тест проходит в одном запуске CI, но падает в другом запуске для того же коммита и проекта, оба запуска помечаются как нестабильные.

Проект Gradle является частью ключа сравнения, потому что один и тот же тест может детерминированно вести себя по-разному в разных проектах — например, общий тестовый класс, скомпилированный с разными зависимостями или запущенный на другом фикстуре модуля. Два запуска одного и того же коммита на разных проектах Gradle рассматриваются как отдельные варианты выполнения и не будут помечать друг друга как нестабильные.

Это особенно полезно для выявления нестабильных тестов, которые не падают достаточно последовательно, чтобы быть пойманными повторными попытками, но всё ещё вызывают периодические сбои CI.

## Управление нестабильными тестами {#managing-flaky-tests}

### Автоматическая очистка

Обнаружение и очистка выполняются через **автоматическое оповещение** в проекте. Каждый проект получает автоматизацию «Обнаружение нестабильных тестов» по умолчанию, чей *триггер* помечает тест как нестабильный, а *восстановление* снимает флаг, как только тест пройдет настроенное окно восстановления (по умолчанию **14 дней**) без повторного срабатывания. Отредактируйте его в разделе **Настройки → Автоматизации**, чтобы изменить окно восстановления, заменить действия восстановления (например, также снять карантин) или полностью отключить восстановление, чтобы тесты оставались помеченными как нестабильные, пока вы не очистите их вручную.

### Ручное управление

Вы также можете вручную помечать или снимать пометку нестабильности с тестов на странице деталей тестового случая. Это полезно, когда:
- Вы хотите отметить известный нестабильный тест во время работы над исправлением
- Тест был ошибочно помечен из-за проблем с инфраструктурой

## Карантин нестабильных тестов {#quarantining}

Карантин изолирует нестабильный тест, чтобы он не блокировал CI, пока вы его исправляете. По умолчанию это **ручное действие** — вы помещаете в карантин, снимаете с карантина и переключаете режимы на странице деталей тестового случая в панели управления — но вы также можете настроить это через **автоматическое оповещение** в разделе **Настройки → Автоматизации**, чтобы тест автоматически заглушался (или пропускался) при превышении порога нестабильности и снимался с карантина при восстановлении. Каждый переход, ручной или автоматический, записывается в журнал аудита тестового случая.

Тест в карантине находится в одном из двух режимов:

- **Заглушен**: тест всё ещё выполняется, но плагин устанавливает `ignoreFailures = true` и вызывает сбой сборки только при сбоях, не находящихся в карантине. Сбои всё ещё поступают в детектор нестабильных тестов, поэтому вы можете продолжать наблюдать за тестом, не ломая сборку. Выберите этот режим для теста, который вы активно исследуете.
- **Пропущен**: плагин фильтрует тест через Gradle's `excludeTestsMatching`, поэтому он никогда не запускается. Он не produces новых результатов и исчезает из панели нестабильных тестов, пока вы не включите его снова. Выберите этот режим, когда тест сломан, медленный или настолько постоянно нестабилен, что его запуск просто тратит минуты CI впустую.

### Почему тесты в карантине могут отображаться как прошедшие {#quarantined-passing}

- **Заглушенные тесты** всё ещё выполняются. Заглушенный тест, который падает, записывается как **упавший** в запуске тестового случая и помечается как нестабильный — статус отдельного теста не перезаписывается. Переопределяется **общий результат запуска теста**: если каждый упавший тестовый случай в запуске заглушен, весь запуск сообщается как пройденный, поэтому заглушенные сбои не ломают CI.
- **Пропущенные тесты** вообще не запускаются, поэтому панель управления продолжает показывать статус последнего фактического выполнения теста — этот снимок может быть недельной давности.

### Включение карантина {#enabling-quarantine}

Карантин **автоматически включается в CI** (когда установлена переменная окружения `CI`) и отключается для локальных сборок. Плагин получает список тестов в карантине с сервера Tuist перед каждой задачей тестирования; заглушенные тесты выполняются нормально, и их сбои маскируются, пропущенные тесты фильтруются.

Вы можете явно управлять этим в вашем `settings.gradle.kts`:

```kotlin
tuist {
    testQuarantine {
        enabled = true  // or false to disable
    }
}
```

Когда `enabled` не установлен, по умолчанию используется автоопределение: включено в CI, отключено локально.

## Стресс-тестирование новых тестов {#stress-testing-new-tests}

Шлюз стресс-тестирования повторно запускает тестовые случаи, добавленные вашей веткой, несколько раз каждый в новом процессе, и сообщает о тех, которые оказываются нестабильными. Вы увидите новый нестабильный тест в pull request, который его добавил, а не спустя недели.

Тестовый случай считается новым, если он не запускался в CI за последние 90 дней на основной ветке проекта или на коммите, который впоследствии был в неё включён. При использовании очереди слияния тестовый случай, запущенный очередью, становится известным, как только коммит очереди попадает в основную ветку, и остаётся новым, если очередь его отбрасывает. Коммиты сопоставляются через <.localized_link href="/guides/features/test-insights/gradle#git-history">историю Git</.localized_link>, которую Tuist собирает в CI.

### Включение

Шлюз по умолчанию отключен. Установите режим:

- **`report`**: предупреждает о каждом нестабильном тестовом случае. Запуск всё ещё завершается со своим собственным результатом.
- **`enforce`**: нестабильный тестовый случай приводит к сбою запуска с тем же кодом выхода, что и упавший тест.

Начните с `report` на пару недель, чтобы увидеть, что бы заблокировал `enforce`.

Объявите это в `settings.gradle.kts`, или установите `TUIST_TEST_STRESS_NEW_TESTS`, чтобы менять режим для каждого CI-конвейера:

```kotlin
tuist {
    stressNewTests {
        mode = "report" // or "enforce"
    }
}
```

В отличие от карантина, у шлюза нет настройки по умолчанию с учетом CI. Если `mode` не установлен, он нигде не запускается.

### Сколько раз каждый тест перезапускается

Это зависит от того, сколько времени занял тестовый случай при первом проходе:

| Первый проход | Повторные запуски |
| --- | --- |
| До 5 с | 10 |
| До 10 с | 5 |
| До 30 с | 3 |
| До 5 мин | 2 |
| Более 5 мин | Не перезапускается |

Каждый повторный запуск — это вложенная сборка Gradle, отфильтрованная по одному тестовому случаю, поэтому каждый повторный запуск получает свежую JVM для тестов. Проход останавливается на 200 тестовых случаях или через 10 минут, в зависимости от того, что наступит раньше, и указывает, какой лимит был достигнут.

### Когда шлюз не запускается

- Первый проход уже завершился неудачей. Сначала исправьте эти тесты.
- У проекта нет основной ветки, или в ней еще ничего не запускалось в CI.
- Более 30% тестовых случаев проекта выглядят как новые. Повторный запуск такого количества займет больше времени, чем того стоит. Ожидайте этого на проекте, который только начал отправлять отчеты в Tuist, или после переименования, которое перемещает много тестов сразу.

## Запрос состояния нестабильных и карантинных тестов {#querying}

### CLI

Дерево команд `tuist test case` предоставляет всю информацию, которую Tuist отслеживает о тестовом случае:

```sh
tuist test case list --flaky                       # only flaky test cases
tuist test case list --quarantined                 # only muted or skipped test cases
tuist test case show <test_case_id>                # detail: flakiness rate, last status, run counts
tuist test case events <test_case_id>              # audit log: marked_flaky, muted, skipped, ...
tuist test case run list <test_case_id>            # run history with status and duration
tuist test case run show <test_case_run_id>        # single run, including failure breakdown
```

Все они принимают `--json` для скриптов.

### REST API

Те же данные доступны по HTTP — см. [эндпоинты тестовых случаев](https://tuist.dev/api/docs#tag/test-cases) в справочнике API для полного списка маршрутов, фильтров и полей ответа. Чтобы изменить состояние тестового случая (отметить или снять отметку нестабильности, заглушить, пропустить), отправьте `PATCH /api/projects/{account_handle}/{project_handle}/tests/test-cases/{test_case_id}` с `is_flaky` или `state`. То же изменение доступно как `tuist test case update` и как инструмент Model Context Protocol `update_test_case`.
