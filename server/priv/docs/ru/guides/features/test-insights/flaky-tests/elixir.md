# Нестабильные тесты в Elixir {#elixir-flaky-tests}

Нестабильные тесты — это тесты, которые дают разные результаты (проходят или падают) при многократном запуске с одним и тем же кодом. Они подрывают доверие к набору тестов и отнимают время разработчиков на расследование ложных сбоев. Tuist автоматически обнаруживает нестабильные тесты и помогает отслеживать их со временем.

> [!IMPORTANT] REQUIREMENTS
> - Выполните <.localized_link href="/guides/get-started/elixir-project">общую настройку Elixir</.localized_link>, чтобы отправлять данные о прогонах тестов

![Нестабильные тесты приложения Phoenix](/images/guides/features/elixir/flaky-tests.png)

## Как работает обнаружение нестабильных тестов {#how-it-works}

Tuist обнаруживает нестабильные тесты двумя способами:

### Повторные запуски тестов {#test-retries}

ExUnit запускает каждый тест один раз, поэтому тест, который падает периодически, выглядит так же, как сломанный. При включенных повторных запусках Hex-пакет повторно выполняет упавшие тесты столько раз, сколько вы указали. Тест, который проходит при повторном запуске, помечается как нестабильный, а прогон считается успешным, если все упавшие тесты в итоге проходят.

По умолчанию повторные запуски отключены. Добавьте `test_retries` в существующие настройки Tuist в `mix.exs`, чтобы включить их:

```elixir
tuist: [project: "account/project", cache: true, test_retries: 2]
```

Или для одного прогона используйте флаг или переменную окружения:

```bash
mix test --retries 2
TUIST_TEST_RETRIES=2 mix test
```

Флаг имеет приоритет над переменной окружения, а переменная окружения — над `mix.exs`.

Повторно запускаются только упавшие тесты, как это делает `mix test --failed`, а в дашборде отображается каждая попытка выполнения теста и её длительность. Прогон, который ExUnit остановил досрочно из-за `--max-failures`, не повторяется. Прогон, у которого все упавшие тесты превысили таймаут, также не повторяется, поскольку каждый повторный запуск снова ждал бы истечения всех таймаутов. Повторные запуски также пропускаются при использовании `--warnings-as-errors`, которое `mix test` больше не применяет, и при запуске из корня umbrella-проекта; чтобы выполнить повторные запуски, запускайте тесты внутри одного из его приложений.

![Нестабильный тест ExUnit и его история](/images/guides/features/elixir/flaky-test-case.png)

### Обнаружение между прогонами {#cross-run-detection}

Даже без повторных запусков тестов Tuist может обнаруживать нестабильные тесты, сравнивая результаты разных CI-прогонов для одного коммита. Если тест проходит в одном CI-прогоне, но падает в другом прогоне для того же коммита, оба прогона помечаются как нестабильные.

Это особенно полезно для выявления нестабильных тестов, которые падают недостаточно регулярно, чтобы их поймали повторные запуски, но всё равно вызывают периодические сбои в CI.

## Управление нестабильными тестами {#managing-flaky-tests}

### Автоматическая очистка

Обнаружение и очистка выполняются через **автоматизированное оповещение** в проекте. Каждый проект получает автоматизацию «Обнаружение нестабильных тестов» по умолчанию, чей *триггер* помечает тест как нестабильный, а *восстановление* снимает этот флаг, когда тест проходит настроенный период восстановления (по умолчанию **14 дней**) без повторного срабатывания. Отредактируйте её в разделе **Settings → Automations**, чтобы изменить период восстановления или полностью отключить восстановление, чтобы тесты оставались помеченными как нестабильные, пока вы не снимете отметку вручную.

### Ручное управление

Вы также можете вручную помечать или снимать пометку нестабильности с тестов на странице деталей тест-кейса. Это полезно, когда:
- Вы хотите отметить известный нестабильный тест, работая над исправлением
- Тест был ошибочно помечен из-за проблем с инфраструктурой

## Карантин нестабильных тестов {#quarantining}

Карантин не даёт нестабильному тесту блокировать CI, пока вы его исправляете. На странице теста в дашборде измените его состояние на **Muted** или **Skipped**, либо настройте автоматизацию в разделе **Settings → Automations**, которая игнорирует или пропускает тест, когда он становится нестабильным, и снова включает его после восстановления. Перед запуском тестов `mix test` считывает все помещённые в карантин тесты проекта и применяет их:

- **Muted**: тест запускается, и его сбой всё ещё фиксируется, но прогон считается успешным, если единственные сбои — от игнорируемых тестов. Повторные запуски всё равно перезапускают падающий игнорируемый тест, поэтому нестабильный тест может пройти и быть отмечен как нестабильный.
- **Skipped**: тест не запускается. `mix test` перечисляет пропущенные тесты перед началом прогона.

```text
Tuist: skipping 1 quarantined test:
  MyApp.CheckoutTest: create_order/2 times out
Tuist: 1 muted test run, and their failures do not fail the run.
```

Прогон завершается неудачей, как обычно, если падает любой тест, который не игнорируется, или если ExUnit останавливается досрочно из-за `--max-failures`.

> [!WARNING]
> **Ограничения**
>
> - Только последние версии Hex-пакета применяют карантин. Более ранние версии запускают игнорируемые и пропущенные тесты как обычные, поэтому сбой игнорируемого теста всё равно приводит к неудаче прогона. Обновите `tuist_ex` перед тем, как полагаться на эту функцию.
> - Игнорируемые тесты не применяются при использовании `--warnings-as-errors` или при запуске из корня umbrella-проекта. Их сбои тогда приводят к неудаче прогона. Вместо этого запускайте тесты внутри каждого приложения umbrella.
> - Пропуск сопоставляет тест по блоку describe и имени, а не по модулю. Тест с таким же блоком describe и именем в другом модуле также будет пропущен. См. [как пропуск выбирает тесты](#how-skipping-selects-tests).
> - Пропущенный тест всё равно запускается, если вы выбрали его с помощью `--only`, `--include` или `path:line`, или если он не объявлен через `test`, например StreamData `property`.
> - Если `mix test` не может прочитать помещённые в карантин тесты, он запускает все тесты и учитывает каждый сбой.
> - Чтение помещённых в карантин тестов требует учётных данных, даже для публичного проекта. Прогон без `TUIST_TOKEN`, сессии `mix tuist.login` или токена идентификации непрерывной интеграции не применяет карантин. Это включает пул-реквесты из форков, которые обычно запускаются без секретов.
> - При использовании `--cover` пропущенный тест считается удалённым: строки, которые покрывал только он, reported as uncovered.
>
> `mix test` перечисляет тесты, которые были случайно исключены пропуском, и пропущенные тесты, которые всё равно запустились, после сводки.

### Как пропуск выбирает тесты {#how-skipping-selects-tests}

Пропущенный тест исключается фильтром ExUnit по полному имени, например `--exclude "test:test create_order/2 times out"`. Фильтры ExUnit не могут дополнительно сопоставлять модуль, поэтому:

- Тест с таким же блоком describe и именем в другом модуле также исключается. `mix test` перечисляет эти тесты после прогона.
- Тест, который вы выбрали с помощью `--only`, `--include` или `path:line`, запускается даже если он пропущен, потому что ExUnit применяет фильтры включения после фильтров исключения. То же самое происходит с тестом, который не объявлен через `test`, например StreamData `property`. `mix test` перечисляет эти тесты после прогона.

### Повторный запуск помещённых в карантин тестов {#running-quarantined-tests-again}

Передайте `--no-quarantine`, чтобы запустить все тесты и учесть каждый сбой, например для проверки исправления:

```bash
mix test --no-quarantine
```

Верните тесту состояние **Включено** на его странице, чтобы включить его в последующие прогоны. Пропущенный тест не даёт новых результатов, пока не будет запущен снова.

Если `mix test` не может прочитать помещённые в карантин тесты, он выводит предупреждение и запускает все тесты без них. Без учётных данных или настроенного проекта он запускает все тесты без предупреждения.

Пакет Hex пока не проводит стресс-тестирование новых тестов.

## Уведомления в Slack {#slack-notifications}

Получайте мгновенные уведомления, когда тест становится нестабильным, настроив <.localized_link href="/guides/integrations/slack#flaky-test-alerts">оповещения о нестабильных тестах</.localized_link> в вашей интеграции со Slack.

## Запрос состояния нестабильности {#querying}

Данные доступны по HTTP. См. [эндпоинты тест-кейсов](https://tuist.dev/api/docs#tag/test-cases) в справочнике API для полного списка маршрутов, фильтров и полей ответа. Чтобы отметить или снять отметку о нестабильности тест-кейса, отправьте `PATCH /api/projects/{account_handle}/{project_handle}/tests/test-cases/{test_case_id}` с `is_flaky` или используйте инструмент Model Context Protocol `update_test_case`.
