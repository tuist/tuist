## Как работает обнаружение нестабильных тестов {#how-it-works}

Tuist обнаруживает нестабильные тесты двумя способами:

### Повторные запуски тестов {#test-retries}

ExUnit запускает каждый тест один раз, поэтому тест, который периодически падает, выглядит так же, как сломанный. При включённых повторных запусках Hex-пакет повторно выполняет упавшие тесты до заданного числа попыток. Тест, который проходит при повторном запуске, помечается как нестабильный, а прогон считается успешным, если все ранее упавшие тесты в итоге проходят.

По умолчанию повторные запуски отключены. Добавьте `test_retries` к существующим параметрам Tuist в `mix.exs`, чтобы включить их:

```elixir
tuist: [project: "account/project", cache: true, test_retries: 2]
```

Или для одного прогона используйте флаг или переменную окружения:

```bash
mix test --retries 2
TUIST_TEST_RETRIES=2 mix test
```

Флаг имеет приоритет над переменной окружения, а переменная окружения — над `mix.exs`.

Повторно запускаются только упавшие тесты, как это делает `mix test --failed`, а на панели отображается каждая попытка теста и её длительность. Прогон, который ExUnit остановил досрочно из‑за `--max-failures`, не повторяется. Прогон, у которого все упавшие тесты завершились по таймауту, также не повторяется, поскольку каждый повторный запуск снова ждал бы истечения всех таймаутов. Повторные запуски также пропускаются с `--warnings-as-errors`, который `mix test` больше не применяет, и из корня umbrella‑проекта; чтобы повторить тесты, запускайте их внутри одного из приложений.

![Нестабильный тест ExUnit и его история](/images/guides/features/elixir/flaky-test-case.png)

### Обнаружение между прогонаами {#cross-run-detection}

Даже без повторных запусков тестов Tuist может обнаруживать нестабильные тесты, сравнивая результаты разных прогонов CI для одного коммита. Если тест проходит в одном прогоне CI, но падает в другом прогоне для того же коммита и метки схемы (`--scheme`), неудачное выполнение помечается как нестабильное.

Это особенно полезно для выявления нестабильных тестов, которые падают недостаточно стабильно, чтобы их поймали повторные запуски, но всё равно вызывают периодические сбои в CI.

## Карантин нестабильных тестов {#quarantining}

Карантин не даёт нестабильному тесту блокировать CI, пока вы его исправляете. На странице теста в панели измените его состояние на **Игнорировать сбои** или **Пропущен**, либо настройте автоматизацию в разделе **Настройки → Автоматизации**, которая игнорирует или пропускает тест при появлении нестабильности и снова включает его после восстановления. Перед запуском тестов `mix test` считывает все помещённые в карантин тесты проекта и применяет их:

- **Игнорировать сбои**: тест выполняется, и его сбой по‑прежнему фиксируется, но прогон считается успешным, если единственные сбои — у тестов с игнорированием сбоев. Повторные запуски всё равно перезапускают такой тест при сбое, поэтому нестабильный тест может пройти и быть отмечен как нестабильный.
- **Пропущен**: тест не выполняется. `mix test` перечисляет пропущенные тесты перед началом прогона.

```text
Tuist: skipping 1 quarantined test:
  MyApp.CheckoutTest: create_order/2 times out
Tuist: 1 muted test run, and their failures do not fail the run.
```

Прогон завершается ошибкой, как обычно, если падает любой тест без игнорирования сбоев или если ExUnit останавливается досрочно из‑за `--max-failures`.

> [!WARNING]
> **Ограничения**
>
> - Карантин применяют только свежие версии Hex‑пакета. Более ранние версии запускают тесты с игнорированием сбоев и пропущенные тесты как обычные, поэтому сбой такого теста всё равно приводит к ошибке прогона. Обновите `tuist_ex` перед тем, как полагаться на эту функцию.
> - Тесты с игнорированием сбоев не применяются с `--warnings-as-errors` и из корня umbrella‑проекта. Их сбои тогда приводят к ошибке прогона. Вместо этого запускайте тесты внутри каждого приложения umbrella.
> - Пропуск сопоставляет тест по блоку describe и имени, а не по модулю. Тест с тем же блоком describe и именем в другом модуле тоже будет пропущен. См. [как пропуск выбирает тесты](#how-skipping-selects-tests).
> - Пропущенный тест всё равно выполняется, если вы выбрали его с помощью `--only`, `--include` или `path:line`, либо если он не объявлен через `test`, например свойство StreamData `property`.
> - Если `mix test` не может прочитать помещённые в карантин тесты, он запускает все тесты и учитывает каждый сбой.
> - Чтение помещённых в карантин тестов требует учётных данных, даже для публичного проекта. Прогон без `TUIST_TOKEN`, сессии `mix tuist.login` или токена идентификации непрерывной интеграции не применяет карантин. Это включает pull‑запросы из форков, которые обычно выполняются без секретов.
> - С `--cover` пропущенный тест считается удалённым: строки, которые покрывал только он, отображаются как непокрытые.
>
> `mix test` перечисляет тесты, которые пропуск случайно исключил, и пропущенные тесты, которые всё равно выполнились, после сводки.

### Как пропуск выбирает тесты {#how-skipping-selects-tests}

Пропущенный тест исключается фильтром ExUnit по полному имени, например `--exclude "test:test create_order/2 times out"`. Фильтры ExUnit не могут дополнительно сопоставлять модуль, поэтому:

- Тест с тем же блоком describe и именем в другом модуле тоже исключается. `mix test` перечисляет такие тесты после прогона.
- Тест, выбранный с помощью `--only`, `--include` или `path:line`, выполняется, даже если он пропущен, потому что ExUnit применяет фильтры включения после фильтров исключения. То же самое происходит с тестом, который не объявлен через `test`, например свойством StreamData `property`. `mix test` перечисляет такие тесты после прогона.

### Повторный запуск помещённых в карантин тестов {#running-quarantined-tests-again}

Передайте `--no-quarantine`, чтобы запустить все тесты и учесть каждый сбой, например для проверки исправления:

```bash
mix test --no-quarantine
```

Верните тест в состояние **Включён** на его странице, чтобы включать его в последующие прогоны. Пропущенный тест не даёт новых результатов, пока не будет запущен снова.

Если `mix test` не может прочитать помещённые в карантин тесты, он выводит предупреждение и запускает все тесты без них. Без учётных данных или настроенного проекта он запускает все тесты без предупреждения.

Hex‑пакет пока не проводит стресс‑тестирование новых тестов.

## Запрос состояния нестабильности {#querying}

Данные доступны по HTTP. Полный список маршрутов, фильтров и полей ответа см. в [эндпоинтах тест-кейсов](https://tuist.dev/api/docs#tag/test-cases) справочника API. Чтобы отметить или снять отметку о нестабильности тест-кейса, отправьте запрос `PATCH /api/projects/{account_handle}/{project_handle}/tests/test-cases/{test_case_id}` с параметром `is_flaky` или используйте инструмент протокола Model Context Protocol `update_test_case`.
