# Нестабильные тесты Bazel {#bazel-flaky-tests}

> [!IMPORTANT]
> **Требования**
>
> - <.localized_link href="/guides/features/test-insights/bazel">Аналитика тестов Bazel</.localized_link>, настроенная через `tuist bazel setup`.

<!-- @snippet: ./_intro -->

## Как работает обнаружение нестабильных тестов {#how-it-works}

Tuist использует отдельные тест-кейсы из отчетов `test.xml` Bazel для выявления несогласованных результатов при повторных запусках и при сравнении прогонов одного и того же коммита и выбора целей в непрерывной интеграции. Локальные запуски остаются видимыми, но не помечают тест-кейсы как нестабильные автоматически.

### Повторные запуски тестов {#test-retries}

Повторные запуски необязательны и не зависят от карантина. Флаг `--flaky_test_attempts=3` позволяет выполнить до **трех попыток Bazel всего** на один тест, а не три дополнительных повтора. Сохраните существующую конфигурацию повторов в `.bazelrc` или передайте её явно:

```sh
tuist bazel test -- --flaky_test_attempts=3 //app:tests
```

Чтобы Tuist мог наблюдать результаты, повторные запуски должны действительно выполняться. Одного сводного отчета о нестабильности цели Bazel недостаточно, чтобы определить, какой именно тест-кейс был нестабильным.

### Обнаружение между запусками {#cross-run-detection}

Для сравнения запусков нужны метаданные коммита и ветки. Передавайте их, если ваша сборочная среда не публикует их автоматически:

```sh
tuist bazel test -- \
  --build_metadata=CI=true \
  --build_metadata=GIT_COMMIT="$GIT_COMMIT" \
  --build_metadata=GIT_BRANCH="$GIT_BRANCH" //app:tests
```

Тест-кейсы идентифицируются по метке цели, имени класса (с откатом к имени набора тестов) и имени теста, как описано в <.localized_link href="/guides/features/test-insights/bazel">аналитике тестов Bazel</.localized_link>.

## Карантин нестабильных тестов {#quarantining}

<!-- @snippet: ./_quarantine-intro -->

`tuist bazel test` получает политику карантина перед каждым вызовом и применяет её к базовому запуску `bazel test`. Обычный `bazel test` по-прежнему сообщает результаты тестов, но не применяет карантин:

```sh
tuist bazel test -- //app:tests
```

Аргументы после `--` передаются в `bazel test`. Используйте `--path`, чтобы выбрать проект и рабочий каталог, и `--bazel`, чтобы выбрать другой исполняемый файл, например `bazelisk`. Именованная конфигурация Bazel, такая как `--config=ci`, необязательна и работает аналогично.

### Игнорировать {#mute}

Используйте **Игнорировать** как основной сценарий карантина. Игнорируемые тест-кейсы продолжают выполняться, их сбои остаются видимыми, а исправные кейсы из той же группы по-прежнему влияют на результат. Tuist преобразует код выхода Bazel при сбое теста в успешный только тогда, когда отчеты относят каждый сбой в каждой неудавшейся цели к игнорируемому кейсу. Ошибки сборки, таймауты, прерванные запуски, отсутствующие или неполные отчеты, а также сбои вне множества игнорируемых кейсов сохраняют статус сбоя Bazel.

### Пропустить {#skip}

Пропуск работает на уровне цели Bazel: пропуск одного кейса исключает всю его цель, включая исправные кейсы, потому что Bazel не может фильтровать отдельные кейсы для каждого фреймворка тестирования. Отдавайте предпочтение **Игнорированию**, если вы не намерены исключать всю цель целиком. Команда выводит все исключаемые метки целей, чтобы в логах сборки было видно, что именно политика карантина исключила.

Если пропускаемая цель больше не существует, Tuist указывает её в предупреждении и выполняет запуск без этого исключения. Верните устаревшие кейсы в состояние **Включено**, чтобы навсегда удалить их политики. Если не осталось ни одной тестовой цели, Bazel сохраняет свой обычный статус выхода «тесты не найдены».

### Повторный запуск тестов из карантина {#running-quarantined-tests-again}

Чтобы исследовать проблему или проверить исправление, обойдите политику карантина:

```sh
tuist bazel test --no-quarantine -- --nocache_test_results //app:tests
```

Верните кейс в состояние **Включено**, чтобы его цель участвовала в последующих обычных запусках. Пропущенные кейсы не создают новых выполнений, пока их явно не включат, поэтому автоматизация, основанная на успешных новых запусках, требует проверочного запуска, прежде чем сможет восстановить такие кейсы.

### Ограничения {#limitations}

- Явные флаги `--build_event_json_file` или `--target_pattern_file` нельзя использовать вместе с активным карантином. Передавайте шаблоны целей напрямую.
- Если Tuist не может получить политику карантина, команда останавливается до запуска тестов. Частичное применение политики никогда не выполняется. Используйте `--no-quarantine`, если вы намеренно хотите запустить тесты без карантина.
- Сбой, совпадающий с правилом игнорирования, записанным под старой идентификацией на основе набора тестов, остается блокирующим, и команда указывает политику, которую нужно применить повторно.

Смотрите документацию Bazel: [фильтры тестов](https://bazel.build/docs/user-manual#test-filter), [параметры командной строки](https://bazel.build/reference/command-line-reference) и [описания событий сборки](https://bazel.build/remote/bep-glossary) для понимания базового поведения.
