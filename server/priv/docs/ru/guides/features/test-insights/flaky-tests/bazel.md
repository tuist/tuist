# Нестабильные тесты Bazel {#bazel-flaky-tests}

`tuist bazel test` получает политику карантина Tuist перед каждым запуском и применяет её к выполняемому запуску `bazel test`.

## Применение карантина {#applying-quarantine}

На странице теста измените его состояние на **Игнорировать сбои**, затем выполните:

```sh
tuist bazel test -- //app:tests
```

Аргументы после `--` передаются в `bazel test`. Используйте `--path`, чтобы выбрать проект и рабочий каталог, и `--bazel`, чтобы выбрать другой исполняемый файл, например `bazelisk`. Обычный `bazel test` по-прежнему выводит результаты тестов, но не получает и не применяет политики карантина Tuist.

Для карантина не требуется ни именованная конфигурация Bazel, ни повторные попытки. Страницы **Нестабильные тесты**, **Тесты в карантине** и отдельных тестов поддерживают те же ручные изменения состояний, что и другие системы сборки. Используйте **Настройки → Автоматизации**, чтобы настроить пороги нестабильности, действия карантина и действия восстановления.

### Игнорировать сбои {#mute}

Используйте **Игнорировать сбои** как основной рабочий процесс карантина. Тест-кейсы с игнорированием сбоев продолжают выполняться, их ошибки остаются видимыми, а работоспособные кейсы из того же таргета по-прежнему влияют на результат. Новые запуски предоставляют данные для восстановления без исключения каких-либо кейсов из таргета.

Tuist читает временный локальный файл событий сборки и указанные отчёты `test.xml`. Он меняет код выхода при ошибке теста Bazel на успешный только тогда, когда полные отчёты относят каждую зафиксированную ошибку в каждом неудачном таргете к кейсу с игнорированием сбоев.

Ошибки сборки, таймауты, прерванные запуски, отсутствующие или некорректные отчёты, неполные потоки событий и ошибки вне набора с игнорированием сохраняют статус ошибки Bazel. Размер локального файла событий ограничен 64 МиБ, а отдельных отчётов — 5 МиБ. Tuist нуждается в собственном локальном файле событий сборки, чтобы проверять ошибки с игнорированием и восстанавливаться после устаревших пропущенных таргетов, поэтому явный параметр `--build_event_json_file` нельзя использовать вместе с активными кейсами с игнорированием или пропуском. Удалённая отправка событий сборки остаётся настроенной через `tuist bazel setup`.

Исходный запуск Bazel и его отчёты сохраняют фактические результаты. Сервер Tuist фиксирует, был ли кейс помещён в карантин на момент начала запуска, даже если его состояние изменилось до обработки отчёта.

### Пропустить {#skip}

Используйте **Пропустить** только если вы намерены исключить **весь таргет Bazel**, включая работоспособные кейсы внутри этого таргета. Пометка одного кейса как **Пропущен** имеет такой эффект для всего таргета. Синтаксис фильтрации отдельных кейсов в Bazel зависит от тестового фреймворка и поддерживается не везде. Поэтому Tuist использует нативные шаблоны исключения таргетов с включённым развёртыванием наборов тестов. Явные таргеты, выбор по маске и тесты внутри правил `test_suite` сохраняют обычное поведение выбора Bazel.

Команда получает все страницы карантина и удаляет дубликаты таргетов. Если полный журнал событий Bazel обнаруживает отсутствующий пропущенный таргет до этапа конфигурации или выполнения, Tuist указывает его в предупреждении и повторяет попытку без этого устаревшего исключения. Исходные запрошенные шаблоны и все остальные исключения сохраняются. Восстановление ограничено пятью повторами; другие ошибки загрузки и неполные доказательства сохраняют ошибку Bazel. Верните устаревшие кейсы в состояние **Включено**, чтобы навсегда удалить их политики. Передавайте шаблоны таргетов напрямую; `--target_pattern_file` нельзя использовать вместе с исключениями карантина. Если не осталось тестовых таргетов, Bazel сохраняет свой обычный код выхода «тесты не найдены», который также ловит случайно пустой выбор тестов.

Команда выводит метки всех исключённых таргетов, чтобы в логах сборки было видно, какие таргеты, включая их работоспособные кейсы, исключает политика карантина.

### Повторный запуск тестов в карантине {#running-quarantined-tests-again}

Чтобы исследовать проблему или проверить исправление, обойдите обе политики карантина:

```sh
tuist bazel test --no-quarantine -- --nocache_test_results //app:tests
```

Верните кейс в состояние **Включено**, чтобы его таргет участвовал в последующих обычных запусках. Пропущенные кейсы не создают новых запусков, пока их явно не включат, поэтому автоматизация, основанная на успешных новых запусках, требует проверочного запуска перед их восстановлением.

Ошибки получения политик карантина останавливают команду до запуска тестов. Команда также отклоняет политики свыше 20 000 кейсов или аргументы таргетов сверх установленного предела; она никогда не применяет политику частично. Используйте `--no-quarantine`, если вы намеренно хотите запустить тесты без политики.

## Необязательная конфигурация и повторные попытки {#optional-configuration-and-retries}

Если ваш репозиторий определяет именованную конфигурацию `ci` в `.bazelrc`, вы можете выбрать её с помощью `--config=ci`:

```sh
tuist bazel test -- --config=ci //app:tests
```

Это конфигурация, определённая в репозитории, а не обязательное требование Tuist. Не указывайте этот параметр, если ваш репозиторий её не определяет.

Повторные попытки также необязательны и не зависят от карантина. Параметр `--flaky_test_attempts=3` включает до **трёх общих попыток Bazel** на тест, а не три дополнительные повторные попытки. Команды могут оставить существующую конфигурацию повторных попыток в `.bazelrc` или передать её явно:

```sh
tuist bazel test -- --flaky_test_attempts=3 //app:tests
```

Для репозиториев, определяющих `ci`, параметры можно комбинировать:

```sh
tuist bazel test -- --config=ci --flaky_test_attempts=3 //app:tests
```

## Обнаружение нестабильности {#detecting-flakiness}

Tuist использует отдельные кейсы из отчётов `test.xml` Bazel, чтобы обнаружить несогласованные результаты между повторными попытками и между запусками одного и того же коммита и выбора таргетов в непрерывной интеграции. Локальные запуски остаются видимыми, но автоматически не помечают тест-кейсы как нестабильные. Предоставьте метаданные коммита и ветки, если ваша среда сборки ещё не публикует их:

```sh
tuist bazel test -- \
  --build_metadata=CI=true \
  --build_metadata=GIT_COMMIT="$GIT_COMMIT" \
  --build_metadata=GIT_BRANCH="$GIT_BRANCH" //app:tests
```

Повторные попытки должны действительно выполняться, чтобы Tuist мог наблюдать их результаты. Одного сводного отчёта о нестабильности таргета Bazel недостаточно, чтобы определить, какой именно отдельный кейс был нестабилен. Отчёты, которые недоступны или не могут быть распарсены, не могут предоставить доказательства на уровне кейсов.

Кейсы идентифицируются по метке таргета, имени класса (с откатом к имени набора) и имени теста. Это позволяет разделять методы с одинаковыми именами в разных классах. Более старые отчёты, использовавшие другое имя охватывающего набора, сохраняют историю под старой идентичностью; их состояние карантина необходимо применить к новой идентичности. Когда ошибка соответствует старому правилу игнорирования на основе набора вместо текущей идентичности класса, команда предупреждает, какую политику нужно применить повторно, и оставляет ошибку блокирующей. Политики не переносятся автоматически, потому что одну и ту же старую идентичность могли использовать несколько классов.
