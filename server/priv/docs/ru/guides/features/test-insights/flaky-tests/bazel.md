# Нестабильные тесты Bazel {#bazel-flaky-tests}

`tuist bazel test` получает политику карантина Tuist перед каждым запуском и применяет её к выполняемому процессу `bazel test`.

## Применение карантина {#applying-quarantine}

На странице теста измените его состояние на **Отключено**, затем выполните:

```sh
tuist bazel test -- //app:tests
```

Аргументы после `--` передаются в `bazel test`. Используйте `--path`, чтобы выбрать проект и рабочий каталог, и `--bazel`, чтобы выбрать другой исполняемый файл, например `bazelisk`. Обычный `bazel test` по-прежнему отображает результаты тестов, но не получает и не применяет политики карантина Tuist.

Для карантина не требуется ни именованная конфигурация Bazel, ни повторные попытки. Страницы **Нестабильные тесты**, **Тесты на карантине** и отдельных тестов поддерживают те же ручные изменения состояния, что и другие системы сборки. Используйте **Настройки → Автоматизации**, чтобы настроить пороги нестабильности, действия по карантину и действия по восстановлению.

### Отключение {#mute}

Используйте **Отключение** как основной рабочий процесс карантина. Отключенные случаи продолжают выполняться, их сбои остаются видимыми, а исправные родственные случаи по-прежнему влияют на результат. Новые запуски предоставляют доказательства для восстановления без исключения каких-либо случаев из цели.

Tuist считывает временный локальный файл событий сборки и связанные отчеты `test.xml`. Он изменяет код выхода при сбое теста Bazel на успех только тогда, когда полные отчеты относят каждый зафиксированный сбой в каждой неудачной цели к отключенному случаю.

Ошибки сборки, тайм-ауты, прерванные запуски, отсутствующие или неправильно сформированные отчеты, неполные потоки событий и сбои вне набора отключенных случаев сохраняют статус сбоя Bazel. Размер локального файла событий ограничен 64 мебибайтами, а отдельных отчетов — 5 мебибайтами. Tuist нуждается в собственном локальном файле событий сборки для проверки отключенных сбоев и восстановления после устаревших пропущенных целей, поэтому явное указание `--build_event_json_file` нельзя сочетать с активными отключенными или пропущенными случаями. Удаленная отчетность о событиях сборки остается настроенной через `tuist bazel setup`.

Исходный вызов Bazel и отчеты сохраняют свои фактические результаты. Сервер Tuist записывает, был ли случай помещен на карантин в момент начала вызова, даже если его состояние изменилось до обработки отчета.

### Пропуск {#skip}

Используйте **Пропуск** только тогда, когда вы намерены исключить **всю цель Bazel**, включая исправные случаи внутри этой цели. Пометка одного случая как **Пропущенный** имеет такой эффект для всей цели. Синтаксис фильтрации отдельных случаев в Bazel зависит от фреймворка тестирования и поддерживается не везде. Поэтому Tuist использует собственные отрицательные шаблоны целей с включенным расширением наборов тестов. Явные цели, выбор по маске и тесты внутри правил `test_suite` сохраняют обычное поведение выбора Bazel.

Команда получает все страницы карантина и удаляет дубликаты целей. Если полный журнал событий Bazel определяет отсутствующую пропущенную цель до настройки или выполнения цели, Tuist указывает её в предупреждении и повторяет попытку без этого устаревшего исключения. Исходные запрошенные шаблоны и все остальные исключения сохраняются. Восстановление ограничено пятью повторными попытками; другие ошибки загрузки и неполные доказательства сохраняют ошибку Bazel. Верните устаревшие случаи в состояние **Включено**, чтобы навсегда удалить их политики. Передавайте шаблоны целей напрямую; `--target_pattern_file` нельзя сочетать с исключениями карантина. Если не осталось целей для тестирования, Bazel сохраняет свой обычный статус выхода «тесты не найдены», что также перехватывает случайно пустой выбор тестов.

Команда выводит метку каждой исключенной цели, чтобы в журналах сборки было видно, какие цели, включая их исправные случаи, исключает политика карантина.

### Повторный запуск тестов на карантине {#running-quarantined-tests-again}

Чтобы исследовать проблему или проверить исправление, обойдите обе политики карантина:

```sh
tuist bazel test --no-quarantine -- --nocache_test_results //app:tests
```

Верните случай в состояние **Включено**, чтобы включить его цель в последующие обычные запуски. Пропущенные случаи не создают новых запусков, пока не будут явно включены, поэтому автоматизация, основанная на успешных новых запусках, требует проверочного запуска, прежде чем сможет их восстановить.

Ошибки получения карантина останавливают команду до запуска тестов. Команда также отклоняет политики свыше 20 000 случаев или аргументы целей, превышающие её ограниченный размер; она никогда не применяет частичную политику. Используйте `--no-quarantine`, если вы намеренно хотите запустить тесты без политики.

## Дополнительная конфигурация и повторные попытки {#optional-configuration-and-retries}

Если ваш репозиторий определяет именованную конфигурацию `ci` в `.bazelrc`, вы можете выбрать её с помощью `--config=ci`:

```sh
tuist bazel test -- --config=ci //app:tests
```

Это конфигурация, определяемая репозиторием, а не обязательное требование Tuist. Не указывайте эту опцию, если ваш репозиторий её не определяет.

Повторные попытки также являются необязательными и не зависят от карантина. `--flaky_test_attempts=3` включает до **трех общих попыток Bazel** на тест, а не три дополнительные повторные попытки. Команды могут сохранить свою существующую конфигурацию повторных попыток в `.bazelrc` или передать её явно:

```sh
tuist bazel test -- --flaky_test_attempts=3 //app:tests
```

Для репозиториев, определяющих `ci`, эти опции можно комбинировать:

```sh
tuist bazel test -- --config=ci --flaky_test_attempts=3 //app:tests
```

## Обнаружение нестабильности {#detecting-flakiness}

Tuist использует отдельные случаи из отчетов `test.xml` Bazel для обнаружения несогласованных результатов при повторных попытках и при запусках одного и того же коммита и выбора целей в непрерывной интеграции. Локальные запуски остаются видимыми, но автоматически не помечают тестовые случаи как нестабильные. Предоставляйте метаданные коммита и ветки, если ваша среда сборки уже не публикует их:

```sh
tuist bazel test -- \
  --build_metadata=CI=true \
  --build_metadata=GIT_COMMIT="$GIT_COMMIT" \
  --build_metadata=GIT_BRANCH="$GIT_BRANCH" //app:tests
```

Для того чтобы Tuist мог наблюдать результаты, повторные попытки должны реально выполняться. Одного сводного отчета о нестабильности цели Bazel недостаточно, чтобы определить, какой именно отдельный случай был нестабильным. Отчеты, которые недоступны или не могут быть разобраны, не могут предоставить доказательства на уровне случаев.

Случаи идентифицируются по метке цели, имени класса (с возвратом к имени набора) и имени теста. Это позволяет разделять методы с одинаковыми именами в разных классах. Более старые отчеты, использовавшие другое имя охватывающего набора, сохраняют свою историю под старой идентичностью; их состояние карантина должно быть применено к новой идентичности. Когда сбой соответствует старому отключению на основе набора вместо текущей идентичности класса, команда предупреждает, какую политику нужно применить повторно, и оставляет сбой блокирующим. Политики не переносятся автоматически, поскольку несколько классов могли использовать общую старую идентичность.

Смотрите [фильтры тестов](https://bazel.build/docs/user-manual#test-filter), [опции командной строки](https://bazel.build/reference/command-line-reference) и [описания событий сборки](https://bazel.build/remote/bep-glossary) Bazel для понимания основного поведения.
