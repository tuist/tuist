# Нестабильные тесты Bazel {#bazel-flaky-tests}

> [!IMPORTANT]
> **Требования**
>
> - <.localized_link href="/guides/features/test-insights/bazel">Аналитика тестов Bazel</.localized_link>, настроенная через `tuist bazel setup`.

<!-- @snippet: ./_intro -->

## Как работает обнаружение нестабильности {#how-it-works}

Tuist использует отдельные тест-кейсы из отчетов Bazel `test.xml`, чтобы выявлять несогласованные результаты при повторных запусках и при сравнении прогонов с тем же коммитом и выбором целей в непрерывной интеграции. Локальные запуски остаются видимыми, но не помечают тест-кейсы как нестабильные автоматически.

### Повторные запуски тестов {#test-retries}

Повторные запуски необязательны и не зависят от карантина. Флаг `--flaky_test_attempts=3` разрешает до **трех попыток выполнения теста в Bazel** всего, а не три дополнительных повтора. Сохраните существующую конфигуграфию повторов в `.bazelrc` или передайте её явно:

```sh
tuist bazel test -- --flaky_test_attempts=3 //app:tests
```

Чтобы Tuist мог зафиксировать результаты, повторные запуски должны действительно выполняться. Сводка нестабильности цели Bazel сама по себе не определяет, какой именно тест-кейс был нестабильным.

### Обнаружение между запусками {#cross-run-detection}

Для сравнения запусков нужны метаданные коммита и ветки. Передавайте их, если ваша сборочная среда не публикует их автоматически:

```sh
tuist bazel test -- \
  --build_metadata=CI=true \
  --build_metadata=GIT_COMMIT="$GIT_COMMIT" \
  --build_metadata=GIT_BRANCH="$GIT_BRANCH" //app:tests
```

Тест-кейсы определяются по метке цели, имени класса (с откатом к имени набора) и имени теста, как описано в разделе <.localized_link href="/guides/features/test-insights/bazel">Аналитика тестов Bazel</.localized_link>.

## Карантин нестабильных тестов {#quarantining}

<!-- @snippet: ./_quarantine-intro -->

Команда `tuist bazel test` получает политику карантина перед каждым вызовом и применяет её к базовому запуску `bazel test`. Обычный запуск `bazel test` по‑прежнему сообщает результаты тестов, но не применяет карантин:

```sh
tuist bazel test -- //app:tests
```

Аргументы после `--` передаются в `bazel test`. Используйте `--path`, чтобы выбрать проект и рабочий каталог, и `--bazel`, чтобы выбрать другой исполняемый файл, например `bazelisk`. Именованная конфигурация Bazel, такая как `--config=ci`, необязательна и работает аналогично.

### Игнорировать сбои {#mute}

Используйте **Игнорировать сбои** как основной сценарий карантина. Игнорируемые кейсы продолжают выполняться, их сбои остаются видимыми, а работоспособные кейсы из того же набора всё ещё влияют на результат. Tuist преобразует код выхода Bazel при сбое теста в успешный только тогда, когда отчеты относят каждый сбой в каждой неуспешной цели к игнорируемому кейсу. Ошибки сборки, таймауты, прерванные запуски, отсутствующие или неполные отчеты, а также сбои вне множества игнорируемых кейсов сохраняют статус сбоя Bazel.

### Пропустить {#skip}

Пропуск работает на уровне цели Bazel: пропуск одного кейса исключает всю его цель, включая работоспособные кейсы, потому что Bazel не может фильтровать отдельные кейсы для каждого тестового фреймворка. Отдавайте предпочтение режиму **Игнорировать сбои**, если вы не хотите исключать цель целиком. Команда выводит метки всех исключенных целей, чтобы в логах сборки было видно, что осталось за рамками политики карантина.

Если пропущенная цель больше не существует, Tuist указывает её в предупреждении и выполняет запуск без этого исключения. Верните устаревшие кейсы в состояние **Включено**, чтобы навсегда удалить их политики. Если не осталось ни одной тестовой цели, Bazel сохраняет свой обычный статус выхода «тесты не найдены».

### Повторный запуск тестов из карантина {#running-quarantined-tests-again}

Чтобы исследовать проблему или проверить исправление, обойдите политику карантина:

```sh
tuist bazel test --no-quarantine -- --nocache_test_results //app:tests
```

Верните кейс в состояние **Включено**, чтобы его цель участвовала в последующих обычных запусках. Пропущенные кейсы не создают новых выполнений, пока их явно не включат, поэтому автоматизация, основанная на успешных новых запусках, требует проверочного запуска, прежде чем сможет восстановить такие кейсы.

### Ограничения {#limitations}

- Явные флаги `--build_event_json_file` и `--target_pattern_file` нельзя использовать вместе с активным карантином. Передавайте шаблоны целей напрямую.
- Если Tuist не может получить политику карантина, команда останавливается до запуска тестов. Частичное применение политики никогда не выполняется. Используйте `--no-quarantine`, если вы намеренно хотите запустить тесты без карантина.
- Сбой, совпадающий с правилом игнорирования, записанным под старым идентификатором на основе набора, остаётся блокирующим, и команда указывает политику, которую нужно применить повторно.

Подробнее о базовом поведении см. в документации Bazel: [фильтры тестов](https://bazel.build/docs/user-manual#test-filter), [параметры командной строки](https://bazel.build/reference/command-line-reference) и [описания событий сборки](https://bazel.build/remote/bep-glossary).
