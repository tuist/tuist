# Нестабильные тесты Bazel {#bazel-flaky-tests}

`tuist bazel test` получает политику карантина Tuist перед каждым вызовом и применяет её к запуску `bazel test`.

## Применение карантина {#applying-quarantine}

На странице теста измените его состояние на **Игнорировать сбои**, затем выполните:

```sh
tuist bazel test -- //app:tests
```

Аргументы после `--` передаются в `bazel test`. Используйте `--path`, чтобы выбрать проект и рабочий каталог, и `--bazel`, чтобы выбрать другой исполняемый файл, например `bazelisk`. Обычный `bazel test` по-прежнему выводит результаты тестов, но не получает и не применяет политики карантина Tuist.

Для карантина не требуются ни именованная конфигурация Bazel, ни повторные попытки. Страницы **Нестабильные тесты**, **Тесты в карантине** и отдельных тестов поддерживают те же ручные изменения состояния, что и другие системы сборки. Используйте **Настройки → Автоматизации**, чтобы настроить пороги нестабильности, действия карантина и действия восстановления.

### Игнорировать сбои {#mute}

Используйте **Игнорировать сбои** как основной рабочий процесс карантина. Игнорируемые случаи продолжают выполняться, их сбои остаются видимыми, а исправные соседние случаи по-прежнему влияют на результат. Новые запуски предоставляют данные для восстановления без исключения каких-либо случаев из цели.

Tuist считывает временный локальный файл событий сборки и указанные отчёты `test.xml`. Он изменяет код завершения при сбое теста в Bazel на успешный только тогда, когда полные отчёты относят каждый зафиксированный сбой в каждой неуспешной цели к игнорируемому случаю.

Ошибки сборки, тайм-ауты, прерванные запуски, отсутствующие или некорректные отчёты, неполные потоки событий и сбои вне множества игнорируемых случаев сохраняют статус ошибки Bazel. Локальный файл событий ограничен 64 мебибайтами, а отдельные отчёты — 5 мебибайтами. Tuist нужен собственный локальный файл событий сборки для проверки игнорируемых сбоев и восстановления после устаревших пропущенных целей, поэтому явный параметр `--build_event_json_file` нельзя использовать вместе с активными игнорируемыми или пропущенными случаями. Удалённая отправка событий сборки остаётся настроенной через `tuist bazel setup`.

Исходный вызов Bazel и отчёты сохраняют фактические результаты. Сервер Tuist фиксирует, был ли случай помещён в карантин на момент начала вызова, даже если его состояние изменилось до обработки отчёта.

### Пропустить {#skip}

Используйте **Пропустить** только если вы намерены исключить **цель Bazel целиком**, включая исправные случаи внутри этой цели. Пометка одного случая как **Пропущенный** имеет эффект для всей цели. Синтаксис фильтрации отдельных случаев в Bazel зависит от тестового фреймворка и поддерживается не везде. Поэтому Tuist использует нативные шаблоны отрицания целей с включённым раскрытием наборов тестов. Явные цели, выбор по маске и тесты внутри правил `test_suite` сохраняют обычное поведение выбора Bazel.

Команда загружает каждую страницу карантина и удаляет дубликаты целей. Если полный журнал событий Bazel определяет отсутствующую пропущенную цель до конфигурации или выполнения цели, Tuist указывает её в предупреждении и повторяет попытку без этого устаревшего исключения. Исходные запрошенные шаблоны и все остальные исключения сохраняются. Восстановление ограничено пятью повторами; другие ошибки загрузки и неполные доказательства сохраняют ошибку Bazel. Верните устаревшие случаи в состояние **Включено**, чтобы навсегда удалить их политики. Передавайте шаблоны целей напрямую; `--target_pattern_file` нельзя использовать вместе с исключениями карантина. Если не осталось тестовых целей, Bazel сохраняет свой обычный статус выхода «тесты не найдены», который также перехватывает случайно пустой выбор тестов.

Команда выводит метки всех исключённых целей, чтобы в логах сборки было видно, какие цели, включая их исправные случаи, исключает политика карантина.

### Повторный запуск тестов в карантине {#running-quarantined-tests-again}

Чтобы исследовать проблему или проверить исправление, обойдите обе политики карантина:

```sh
tuist bazel test --no-quarantine -- --nocache_test_results //app:tests
```

Верните случай в состояние **Включено**, чтобы его цель участвовала в последующих обычных запусках. Пропущенные случаи не создают новых запусков, пока их явно не включат, поэтому автоматизация, основанная на успешных новых запусках, требует проверочного запуска перед их восстановлением.

Ошибки получения политик карантина останавливают команду до запуска тестов. Команда также отклоняет политики свыше 20 000 случаев или аргументы целей, превышающие установленный предел размера; она никогда не применяет политику частично. Используйте `--no-quarantine`, если вы намеренно хотите запустить тесты без политики.

## Необязательная конфигурация и повторные попытки {#optional-configuration-and-retries}

Если ваш репозиторий определяет именованную конфигурацию `ci` в `.bazelrc`, вы можете выбрать её с помощью `--config=ci`:

```sh
tuist bazel test -- --config=ci //app:tests
```

Это конфигурация, определённая в репозитории, а не обязательное требование Tuist. Не указывайте этот параметр, если ваш репозиторий его не определяет.

Повторные попытки также необязательны и не зависят от карантина. `--flaky_test_attempts=3` включает до **трёх общих попыток Bazel** на тест, а не три дополнительных повтора. Команды могут хранить существующую конфигурацию повторов в `.bazelrc` или передавать её явно:

```sh
tuist bazel test -- --flaky_test_attempts=3 //app:tests
```

Для репозиториев, определяющих `ci`, параметры можно комбинировать:

```sh
tuist bazel test -- --config=ci --flaky_test_attempts=3 //app:tests
```

## Обнаружение нестабильности {#detecting-flakiness}

Tuist использует отдельные случаи из отчётов `test.xml` Bazel для обнаружения несогласованных результатов при повторных попытках и при запусках одного и того же коммита и выбора целей в непрерывной интеграции. Локальные запуски остаются видимыми, но автоматически не помечают тестовые случаи как нестабильные. Предоставьте метаданные коммита и ветки, если ваша среда сборки ещё не публикует их:

```sh
tuist bazel test -- \
  --build_metadata=CI=true \
  --build_metadata=GIT_COMMIT="$GIT_COMMIT" \
  --build_metadata=GIT_BRANCH="$GIT_BRANCH" //app:tests
```

Повторные попытки должны фактически выполняться, чтобы Tuist мог наблюдать их результаты. Одного сводного отчёта о нестабильности цели Bazel недостаточно для определения того, какой именно случай был нестабильным. Отчёты, которые недоступны или не могут быть разобраны, не могут предоставить доказательства на уровне случаев.

Случаи идентифицируются по метке цели, имени класса (с откатом к имени набора) и имени теста. Это позволяет разделять методы с одинаковыми именами в разных классах. Более старые отчёты, использовавшие другое имя охватывающего набора, сохраняют свою историю под старой идентичностью; их состояние карантина необходимо применить к новой идентичности. Когда сбой соответствует старому игнорированию на основе набора вместо текущей идентичности класса, команда предупреждает, какую политику нужно применить повторно, и оставляет сбой блокирующим. Политики не переносятся автоматически, потому что несколько классов могли разделять старую идентичность.

См. [фильтры тестов](https://bazel.build/docs/user-manual#test-filter), [параметры командной строки](https://bazel.build/reference/command-line-reference) и [описания событий сборки](https://bazel.build/remote/bep-glossary) Bazel для понимания базового поведения.
