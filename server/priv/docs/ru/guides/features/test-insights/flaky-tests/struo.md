# Нестабильные тесты Struo {#struo-flaky-tests}

<a id="once-flaky-tests"></a>

> [!IMPORTANT]
> **Требования**
>
> - Настройте <.localized_link href="/guides/features/test-insights/struo">аналитику тестов Struo</.localized_link> со структурированными результатами отдельных тестов.

<!-- @snippet: ./_intro -->

## Как работает обнаружение нестабильности {#how-it-works}

### Повторные запуски тестов {#test-retries}

Когда раннер сообщает несколько попыток для одного и того же теста, Tuist сохраняет их. Тест, который сначала падает, а затем проходит, помечается как нестабильный; тот, что продолжает падать, остаётся ошибкой. Включите повторные запуски в базовом раннере, если он это поддерживает. Подключение Struo к Tuist не добавляет автоматически повторные запуски ко всем целям тестирования.

### Обнаружение между запусками {#cross-run-detection}

Общая история тестов также позволяет Tuist сравнивать успешные и неуспешные результаты для одного и того же теста и коммита в CI. Struo должен сообщать контекст коммита и CI для этого сравнения; локальные запуски остаются видимыми, но не становятся автоматическим доказательством нестабильности между запусками.

Тест-кейсы идентифицируются по нативной цели, набору и имени кейса. Сохраняйте эти идентификаторы стабильными, чтобы сохранить историю, и используйте полные отчёты по каждому кейсу вместо вывода надёжности из общего результата цели.

## Исследование нестабильных тестов {#investigate-flaky-tests}

Откройте историю тест-кейса в Tuist, чтобы сравнить его попытки, сбои и затронутые коммиты CI. Общие запросы к тестам также доступны через <.localized_link href="/guides/features/agentic-coding/mcp">инструменты Model Context Protocol</.localized_link>, поэтому агент написания кода может исследовать те же самые reported результаты.

## Управление нестабильными тестами {#managing-flaky-tests}

Вы можете пометить или снять пометку теста как нестабильного на странице деталей во время расследования сбоя. Автоматизация обнаружения нестабильных тестов по умолчанию также снимает флаг после окна восстановления, обычно 14 дней без другого триггера.

Проекты Struo сейчас не показывают вкладку настроек **Автоматизации**. Обнаружение и сохранённое состояние тестов доступны, но рабочий процесс настроек, документированный для систем сборки с принудительным карантином, пока не доступен для Struo.

## Карантин {#quarantining}

Tuist может сопоставлять сообщаемые кейсы с их сохранённым состоянием карантина, но нативный клиент Struo сейчас не получает и не применяет политики Tuist **Игнорирование** или **Пропуск**. Изменение этого состояния в Tuist не останавливает выполнение теста в Struo и не делает его сбой прекращающим блокировку CI.

Используйте собственную политику фильтрации или обработки сбоев вашего раннера, когда вам нужен карантин во время выполнения. Не полагайтесь только на состояние дашборда для изменения кода выхода команды.
