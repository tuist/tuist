# Нестабильные тесты Struo {#struo-flaky-tests}

<a id="once-flaky-tests"></a>

> [!IMPORTANT]
> **Требования**
>
> - Настройте <.localized_link href="/guides/features/test-insights/struo">аналитику тестов Struo</.localized_link> со структурированными результатами отдельных тестов.

<!-- @snippet: ./_intro -->

## Как работает обнаружение нестабильности {#how-it-works}

### Повторные запуски тестов {#test-retries}

Когда раннер сообщает несколько попыток для одного и того же теста, Tuist сохраняет их. Тест, который сначала завершился с ошибкой, а затем прошел успешно, помечается как нестабильный; тот, что продолжает завершаться с ошибкой, остается ошибочным. Включите повторные запуски в используемом раннере, если это поддерживается. Подключение Struo к Tuist не добавляет автоматически повторные запуски ко всем целям тестирования.

### Обнаружение между запусками {#cross-run-detection}

Общая история тестов также позволяет Tuist сравнивать успешные и ошибочные результаты для одного и того же теста и коммита в CI. Struo должен передавать контекст коммита и CI для этого сравнения; локальные запуски остаются видимыми, но не становятся автоматическими доказательствами нестабильности между запусками.

Тест-кейсы идентифицируются по нативной цели, набору тестов и имени кейса. Сохраняйте эти идентификаторы неизменными, чтобы поддерживать историю, и используйте полные отчеты по каждому кейсу вместо вывода о надежности из общего результата цели.

## Исследование нестабильных тестов {#investigate-flaky-tests}

Откройте историю тест-кейса в Tuist, чтобы сравнить его попытки, ошибки и затронутые коммиты в CI. Общие запросы к тестам также доступны через <.localized_link href="/guides/features/agentic-coding/mcp">инструменты Model Context Protocol</.localized_link>, поэтому агент написания кода может исследовать те же сообщенные результаты.

## Управление нестабильными тестами {#managing-flaky-tests}

Вы можете пометить или снять пометку теста как нестабильного на странице его деталей во время расследования ошибки. Автоматизация обнаружения нестабильных тестов по умолчанию также снимает флаг после окна восстановления, обычно 14 дней без другого триггера.

Проекты Struo сейчас не предоставляют вкладку настроек **Автоматизации**. Обнаружение и сохраненное состояние тестов доступны, но рабочий процесс настроек, документированный для систем сборки с принудительным карантином, пока не доступен для Struo.

## Карантин {#quarantining}

Tuist может сопоставлять сообщенные кейсы с их сохраненным состоянием карантина, но нативный клиент Struo сейчас не получает и не применяет политики Tuist **Игнорировать сбои** или **Пропущено**. Изменение этого состояния в Tuist не останавливает выполнение теста в Struo и не делает так, чтобы его ошибка перестала блокировать CI.

Используйте собственную политику фильтрации или обработки ошибок вашего раннера, когда нужен карантин во время выполнения. Не полагайтесь только на состояние в панели управления для изменения кода завершения команды.
