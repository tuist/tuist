## Как работает обнаружение нестабильности {#how-it-works}

Tuist определяет нестабильные тесты двумя способами:

### Повторные запуски тестов {#test-retries}

Когда вы запускаете тесты с включённым повтором, Tuist анализирует результаты каждой попытки. Если тест падает на одних попытках, но проходит на других, он помечается как нестабильный.

Передайте `-retry-tests-on-failure` или `-test-iterations` через `tuist test`:

```sh
tuist test MyScheme -- -retry-tests-on-failure -test-iterations 3
```

## Карантин для нестабильных тестов {#quarantining}

<!-- @snippet: ./_quarantine-intro -->

Тест в карантине может находиться в одном из двух режимов:

- **Игнорирование сбоев**: тест всё равно запускается, но `tuist test` скрывает его сбой. Сбои по-прежнему поступают в детектор нестабильных тестов, поэтому вы можете продолжать наблюдать за тестом, не ломая сборку. Выбирайте этот режим, если активно исследуете проблему.
- **Пропуск**: xcodebuild получает `-skip-testing <identifier>`, поэтому тест никогда не запускается. Он не генерирует новых результатов и исчезает с дашборда нестабильных тестов, пока вы не включите его снова. Выбирайте этот режим, если тест сломан, медленный или настолько постоянно нестабилен, что его запуск просто тратит минуты CI впустую.

<!-- @snippet: ./_quarantined-passing -->

### Запуск тестов {#running-tests}

`tuist test` автоматически учитывает оба режима:

```sh
tuist test
```

Пропущенные тесты передаются в xcodebuild как `-skip-testing` и никогда не запускаются. Тесты с игнорированием сбоев запускаются как обычно; если они падают, сбой маскируется в итоговом статусе сборки.

Чтобы полностью обойти карантин и запустить всё, включая тесты с игнорированием сбоев и пропущенные тесты:

```sh
tuist test --skip-quarantine
```

## Стресс-тестирование новых тестов {#stress-testing-new-tests}

<!-- @snippet: ./_stress-intro -->

Тест-кейс считается новым, если он не запускался в CI за последние 90 дней на ветке по умолчанию проекта или на коммите, который уже попал в эту ветку. При использовании очереди слияния тест-кейс, запущенный очередью, становится известным после того, как коммит очереди попадёт в ветку, и остаётся новым, если очередь его отбросит. Коммиты сопоставляются через <.localized_link href="/guides/features/test-insights/xcode#git-history">историю Git</.localized_link>, которую Tuist собирает в CI.

<!-- @snippet: ./_stress-modes -->

В обоих режимах <.localized_link href="/guides/features/selective-testing/generated-xcode-project">выборочное тестирование</.localized_link> не пропускает таргет с нестабильным новым тест-кейсом при следующем запуске. Таргет запускается снова, и гейт повторно проводит стресс-тестирование этого тест-кейса, пока он не пройдёт все повторные запуски.

Передайте параметр перед сквозными аргументами или установите `TUIST_TEST_STRESS_NEW_TESTS`, чтобы менять режим для каждого шага CI:

```sh
tuist test --stress-new-tests report
```

<!-- @snippet: ./_stress-reruns -->

Повторные запуски переиспользуют артефакты, собранные первым проходом.
