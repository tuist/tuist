# GitLab CI {#gitlab-ci}

> [!IMPORTANT]
> **Только по приглашению**
>
> Tuist Runners сейчас доступны только по приглашению. [Свяжитесь с нами](mailto:contact@tuist.dev), чтобы запросить доступ для вашего аккаунта.

Ваши пайплайны остаются в GitLab. Tuist предоставляет изолированную машину на Linux или macOS для каждой задачи и отправляет её логи и результат в GitLab и на панель управления Tuist. Требуется GitLab версии 19.3 или новее. Поддерживаются GitLab.com и самостоятельно размещённые экземпляры, доступные через публичный HTTPS.

1. **Создайте раннер GitLab.** В разделе проекта **Settings → CI/CD → Runners** создайте проектный раннер. Также можно использовать групповой раннер. Добавьте все метки профилей Tuist, которые хотите использовать как теги раннера, например `tuist-linux` и `tuist-macos`, и отключите опцию **Run untagged jobs**. Сохраните токен аутентификации, который покажет GitLab; он начинается с `glrt-`. Устанавливать раннер на свою машину не нужно.
2. **Подключитесь один раз в Tuist.** В разделе **Settings → Integrations** выберите **Connect** на карточке GitLab CI. Введите URL вашего GitLab и токен аутентификации раннера. Это подключение может обслуживать задачи с разными профилями. Токены хранятся в зашифрованном виде и больше не отображаются. При желании добавьте токен доступа к API, чтобы пайплайны merge request могли сохранять тома кэша; см. [Пайплайны merge request](#merge-request-pipelines).
3. **Выберите машину для каждой задачи.** Укажите ровно одну <.localized_link href="/guides/features/runners/profiles">метку профиля Tuist</.localized_link> в поле `tags` задачи. Другие теги допустимы, если они также есть у зарегистрированного раннера GitLab:

   ```yaml
   # .gitlab-ci.yml
   linux-check:
     tags: [tuist-linux]
     script:
       - uname -a

   test:
     tags: [tuist-macos]
     script:
       - tuist test
     retry:
       max: 2
       when: runner_system_failure
   ```

4. **Отправьте код и наблюдайте.** Tuist начнёт опрос в течение минуты. Задачи появятся в разделе **Runners** со ссылкой на задачу в GitLab, логами и метриками машины. GitLab получает логи во время выполнения задачи; Tuist получает замаскированный лог после её завершения.

Tuist считывает `CI_JOB_TAGS` из каждого назначения и определяет профиль в рамках подключённого аккаунта Tuist. Машина не выводится из `CI_RUNNER_TAGS` и профиль по умолчанию не используется. Отсутствие, неизвестность или наличие нескольких меток профиля Tuist приводят к сбою назначенной задачи с пояснением в её логе GitLab. Не переопределяйте `CI_JOB_TAGS` в переменных пайплайна.

## Среда выполнения {#execution-environment}

Задачи используют **shell executor** GitLab внутри изолированной машины. Клонирование репозитория, переменные CI, `before_script`, `script`, `after_script`, артефакты и отмена обрабатываются GitLab Runner. Настройки пайплайна `image:` и `services:` не конфигурируют эту оболочку; используйте инструменты, установленные в <.localized_link href="/guides/features/runners/profiles">образе раннера</.localized_link>, или устанавливайте их в своём скрипте.

Многоразовый токен аутентификации раннера остаётся на сервере Tuist. Машины получают учётные данные только для назначенной им задачи. Разрешения на подпись кэша сейчас не выдаются для задач GitLab. Пользовательские тома кэша на Linux проверяют идентичность задачи и права на сохранение через API GitLab; перезаписываемые переменные CI не обеспечивают доверия.

GitLab помечает задачу как выполняющуюся и запускает её тайм-аут сразу после того, как Tuist её захватит. Пока задачи, уже захваченные Tuist, занимают лимит параллельности вашего аккаунта, остальные задачи остаются в состоянии ожидания в GitLab. Захваченная задача ожидает машину вплоть до своего тайм-аута, но не более 12 часов. Если к этому времени машина не станет доступна, Tuist завершит назначение с ошибкой `runner_system_failure`, и политика повторных попыток, описанная выше, позволит GitLab повторить её. Эта же политика применяется при потере машины раннера.

## Ротация токенов и отключение {#rotating-tokens-and-disconnecting}

Обновите токены подключения и выберите **Save changes**, чтобы выполнить их ротацию. Если оставить поле токена пустым, существующие учётные данные сохранятся.

**Disconnect** останавливает захват задач и приводит к сбою ожидающих назначений. Выполняющиеся задачи продолжают работу со своими учётными данными. Если GitLab недоступен, Tuist сохраняет отключённое подключение, повторяя попытки отмены ожидающих назначений. Подключение удаляется после завершения этих назначений.

## Тома кэша {#cache-volumes}

Сохраняйте кэши Xcode, модулей и Gradle, а также другие директории между задачами с помощью <.localized_link href="/guides/features/runners/cache-volumes">томов кэша</.localized_link>. Добавляйте их после клонирования репозитория и перед командами, которые их используют.

### Пайплайны merge request {#merge-request-pipelines}

Пайплайны push, schedule и web проекта сохраняют свои изменения в тома кэша. Пайплайны merge request используют кэш и сохраняют изменения только если у подключения есть токен доступа к API:

1. В GitLab создайте токен доступа проекта или группы с ролью **Reporter** и областью действия `read_api`. Групповой токен покрывает все проекты группы, которые выполняются на раннерах Tuist.
2. В разделе **Settings → Integrations** вставьте его в поле **API access token** на карточке GitLab CI и выберите **Save changes**.

Затем Tuist считывает merge request каждого пайплайна merge request. Пайплайны merge request, открытые из ветки самого проекта, сохраняют изменения под исходной веткой merge request, поэтому <.localized_link href="/guides/features/runners/cache-volumes#choose-which-branches-save">настройки веток</.localized_link> профиля раннера применяются к этой ветке. Merge request из форков никогда не сохраняют изменения. Если Tuist не может прочитать merge request, задача всё равно выполняется и использует кэш, но её изменения отбрасываются.
