# GitLab CI {#gitlab-ci}

Ваши пайплайны остаются в GitLab. Tuist предоставляет изолированную машину на Linux или macOS для каждой задачи и отправляет её логи и результат в GitLab и на панель управления Tuist. Требуется GitLab версии 19.3 или новее. Поддерживаются GitLab.com и самостоятельно развернутые экземпляры, доступные через публичный HTTPS.

1. **Создайте раннер GitLab.** В разделе **Settings → CI/CD → Runners** вашего проекта создайте проектный раннер. Вы также можете использовать групповой раннер. Добавьте все метки профилей Tuist, которые хотите использовать, в качестве тегов раннера, например `tuist-linux` и `tuist-macos`, и отключите опцию **Run untagged jobs**. Сохраните токен аутентификации, который показывает GitLab; он начинается с `glrt-`. Вам не нужно устанавливать раннер на свою собственную машину.
2. **Подключитесь один раз в Tuist.** В разделе **Settings → Integrations** выберите **Connect** на карточке GitLab CI. Введите URL-адрес вашего GitLab и токен аутентификации раннера. Это подключение может обслуживать задачи, использующие разные профили. Токены хранятся в зашифрованном виде и больше никогда не отображаются. При желании добавьте токен доступа к API, чтобы пайплайны merge request могли сохранять тома кэша; см. [Merge request pipelines](#merge-request-pipelines).
3. **Выберите машину для каждой задачи.** Укажите ровно одну <.localized_link href="/guides/features/runners/profiles">метку профиля Tuist</.localized_link> в поле `tags` задачи. Другие теги допустимы, при условии что зарегистрированный раннер GitLab также имеет их:

   ```yaml
   # .gitlab-ci.yml
   linux-check:
     tags: [tuist-linux]
     script:
       - uname -a

   test:
     tags: [tuist-macos]
     script:
       - tuist test
     retry:
       max: 2
       when: runner_system_failure
   ```

4. **Отправьте код и наблюдайте.** Tuist начинает опрос в течение минуты. Задачи появляются в разделе **Runners** со ссылкой на задачу в GitLab, логами и метриками машины. GitLab получает логи во время выполнения задачи; Tuist получает замаскированный лог после её завершения.

Tuist считывает `CI_JOB_TAGS` из каждого назначения и определяет профиль в рамках подключенной учетной записи Tuist. Он не выводит тип машины из `CI_RUNNER_TAGS` и не использует профиль по умолчанию. Отсутствие, неизвестность или наличие нескольких меток профиля Tuist приводят к сбою полученной задачи с пояснением в её логе GitLab. Не переопределяйте `CI_JOB_TAGS` в переменных вашего пайплайна.

## Среда выполнения {#execution-environment}

Задачи используют **shell executor** GitLab внутри изолированной машины. Checkout, переменные CI, `before_script`, `script`, `after_script`, артефакты и отмена обрабатываются GitLab Runner. Настройки пайплайна `image:` и `services:` не конфигурируют эту shell-среду; используйте инструменты, установленные в <.localized_link href="/guides/features/runners/profiles">образе раннера</.localized_link>, или устанавливайте их в своем скрипте.

Многоразовый токен аутентификации раннера остается на сервере Tuist. Машины получают учетные данные только для назначенной им задачи. Права на подпись кэша в настоящее время не предоставляются для задач GitLab. Пользовательские тома кэша Linux проверяют идентичность задачи и разрешение на сохранение через API GitLab; перезаписываемые переменные CI не обеспечивают доверия.

GitLab помечает задачу как выполняющуюся и запускает её тайм-аут сразу после того, как Tuist получает её. Пока задачи, уже полученные Tuist, исчерпывают лимит параллельности вашей учетной записи, остальные задачи остаются в состоянии ожидания в GitLab. Полученная задача ожидает машину вплоть до своего тайм-аута, но не более 12 часов. Если к этому времени машина не станет доступна, Tuist завершает назначение с ошибкой `runner_system_failure`, и политика повторных попыток, описанная выше, позволяет GitLab повторить её. Эта же политика применяется при потере машины раннера.

## Ротация токенов и отключение {#rotating-tokens-and-disconnecting}

Обновите токены подключения и выберите **Save changes**, чтобы выполнить их ротацию. Если оставить поле токена пустым, существующие учетные данные сохранятся.

**Disconnect** останавливает получение новых задач и приводит к сбою ожидающих назначений. Выполняющиеся задачи продолжают работу со своими собственными учетными данными. Если GitLab недоступен, Tuist сохраняет отключенное подключение, повторно пытаясь отменить ожидающие назначения. Подключение удаляется после завершения этих назначений.

## Тома кэша {#cache-volumes}

Сохраняйте кэши Xcode, модулей и Gradle, а также другие директории между задачами с помощью <.localized_link href="/guides/features/runners/cache-volumes">томов кэша</.localized_link>. Добавляйте их после checkout и перед командами, которые их используют.

### Пайплайны merge request {#merge-request-pipelines}

Пайплайны push, schedule и web проекта сохраняют свои изменения в тома кэша. Пайплайны merge request используют кэш и сохраняют свои изменения только если у подключения есть токен доступа к API:

1. В GitLab создайте токен доступа проекта или группы с ролью **Reporter** и областью действия `read_api`. Групповой токен распространяется на все проекты в группе, использующие раннеры Tuist.
2. В разделе **Settings → Integrations** вставьте его в поле **API access token** на карточке GitLab CI и выберите **Save changes**.

Затем Tuist считывает информацию о каждом merge request из соответствующего пайплайна. Пайплайны merge request, открытые из ветки самого проекта, сохраняют свои изменения под исходной веткой merge request, поэтому к этой ветке применяются <.localized_link href="/guides/features/runners/cache-volumes#choose-which-branches-save">настройки веток</.localized_link> профиля раннера. Merge request из форков никогда не сохраняют изменения. Если Tuist не может прочитать merge request, задача всё равно выполняется и использует кэш, но её изменения отбрасываются.
