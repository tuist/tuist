# API {#api}

<!-- @snippet: ./_invite-only -->

Git-форжи, очереди слияния и оркестраторы агентов, у которых нет собственного протокола раннеров, могут запускать задачи напрямую на Tuist Runners. Вы создаёте задачу одним запросом, машина Tuist выбранного вами <.localized_link href="/guides/features/runners/profiles">профиля</.localized_link> клонирует коммит и запускает ваш скрипт, а Tuist отправляет результат на вашу вебхук-эндпоинт.

## Запуск задачи {#run-a-job}

1. **Создайте токен аккаунта** со скоупом `account:runners:write`:

   ```bash
   tuist account tokens create my-org --scopes account:runners:write --name forge
   ```

2. **Создайте задачу.** Обычно вызывающая сторона делает это из своего push-хука, используя короткоживущий токен, который позволяет машине клонировать репозиторий:

   ```bash
   curl -X POST https://tuist.dev/api/accounts/my-org/runners/jobs \
     -H "Authorization: Bearer $TUIST_TOKEN" \
     -H "Content-Type: application/json" \
     -d '{
       "profile": "tuist-macos",
       "repository_url": "https://git.example.com/acme/app.git",
       "clone_token": "<short-lived token>",
       "commit_sha": "4f1c2d0e9b8a7c6d5e4f3a2b1c0d9e8f7a6b5c4d",
       "ref": "refs/heads/main",
       "name": "test",
       "script": "mise install\nmise run test",
       "secrets": { "SIGNING_KEY": "..." },
       "timeout_minutes": 30,
       "idempotency_key": "acme/app:4f1c2d0e:test"
     }'
   ```

   Ответ содержит задачу с её `workflow_job_id`. Она сразу появляется в разделе **Runners** вашего дашборда Tuist и начинается, как только освободится машина выбранного профиля. Разогретые машины обычно запускают её за считанные секунды.

3. **Отслеживайте задачу.** Подпишите <.localized_link href="/guides/integrations/webhooks">вебхук-эндпоинт</.localized_link> на события `runner_job.started` и `runner_job.completed`. Событие завершения содержит `conclusion` задачи: `success`, `failure` или `cancelled`. Также можно опрашивать `GET /api/accounts/my-org/runners/jobs/{workflow_job_id}` и читать лог через `GET /api/accounts/my-org/runners/jobs/{workflow_job_id}/logs`.

## Интеграция с git-форжей {#integrate-a-git-forge}

Форжа без протокола раннеров подключается через небольшой мост, который может быть сервисом самой форжи или функцией, вызываемой из её хуков:

1. **При пуше** push-хук форжи попадает в мост. Мост проверяет хук, определяет, какие проверки нужны коммиту, и выпускает токен для клонирования репозитория только на чтение, срок действия которого истекает после таймаута задачи.
2. **Для каждой проверки** мост создаёт задачу с установленным `idempotency_key` в значение `<repository>:<commit>:<check>`, поэтому повторная доставка хука не создаст ничего нового. Он сохраняет возвращённый `workflow_job_id` и может пометить проверку как ожидающую в форже.
3. **При событиях `runner_job.started` и `runner_job.completed`** мост проверяет заголовок `Tuist-Signature` с секретом эндпоинта, находит проверку по `workflow_job_id` или `idempotency_key` и обновляет статус коммита в форже, указывая `conclusion`. Статус можно связать со страницей задачи в дашборде Tuist.
4. **Когда пуш заменяет коммит**, мост отменяет задачи, созданные для старого коммита.

## Как выполняется задача {#how-the-job-runs}

Машина загружает `commit_sha` из `repository_url` по HTTPS. Если сервер не отдаёт коммит по его SHA, она загружает вместо него `ref`, который должен содержать этот коммит. `clone_token`, если вы его указали, отправляется только хосту репозитория в виде `Authorization: Bearer <token>`. Он никогда не попадает в ваш скрипт или лог задачи.

Ваш скрипт выполняется в Bash в login-оболочке с параметром `set -eo pipefail`, начиная с корня клонированного репозитория. Задача завершается с ошибкой, если скрипт завершается с ненулевым кодом или превышает `timeout_minutes` (по умолчанию 60 минут, максимум 360). Помимо ваших `env` и `secrets`, скрипт видит переменные `CI=true`, `TUIST_JOB_ID`, `TUIST_JOB_NAME`, `TUIST_JOB_REPOSITORY_URL`, `TUIST_JOB_REF` и `TUIST_JOB_COMMIT_SHA`. Значения `secrets` маскируются в логе задачи.

## Повторные попытки и идемпотентность {#idempotency}

Укажите для каждой задачи `idempotency_key`, описывающий её назначение, например `<repository>:<commit>:<check>`. Запрос с ключом, уже использованным в вашем аккаунте, вернёт существующую задачу со статусом 200 вместо 201 и ничего не создаст. Это позволяет вашему push-хуку передавать запрос в очередь повторных попыток без риска создания дубликатов задач.

Доставки вебхуков повторяются, пока ваш эндпоинт не ответит статусом 2xx, поэтому событие может прийти несколько раз. Для устранения дубликатов используйте `id` конверта или `workflow_job_id` задачи вместе с типом события.

## Отмена задачи {#cancel-a-job}

```bash
curl -X POST https://tuist.dev/api/accounts/my-org/runners/jobs/{workflow_job_id}/cancel \
  -H "Authorization: Bearer $TUIST_TOKEN"
```

Задача, которую ни одна машина ещё не начала, отменяется немедленно. Выполняющаяся задача останавливается в течение нескольких секунд, а её событие завершения сообщает `cancelled`. Задача, которую ни одна машина не начала в течение 24 часов, отменяется автоматически.

## Кэширование и доверие {#trust}

Любой, кто может делать пуш в репозиторий, может изменить то, что выполняет задача, поэтому задачи API считаются ненадёжными: они не получают доступ к общим <.localized_link href="/guides/features/runners/cache-volumes">томам кэша</.localized_link> вашего аккаунта или к разрешению на подпись кэша. Секреты, скрипт и токен клонирования задачи хранятся в зашифрованном виде и удаляются после завершения задачи.
