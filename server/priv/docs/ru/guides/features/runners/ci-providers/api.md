# API {#api}

Git-форджи, очереди слияний и оркестраторы агентов, у которых нет собственного протокола раннеров, могут напрямую запускать задачи на Tuist Runners. Вы создаёте задачу одним запросом, машина Tuist выбранного вами <.localized_link href="/guides/features/runners/profiles">профиля</.localized_link> клонирует коммит и выполняет ваш скрипт, а Tuist отправляет результат на ваш вебхук.

## Запуск задачи {#run-a-job}

1. **Создайте токен аккаунта** со скоупом `account:runners:write`:

   ```bash
   tuist account tokens create my-org --scopes account:runners:write --name forge
   ```

2. **Создайте задачу.** Обычно вызывающая сторона делает это из хука push, используя короткоживущий токен, который позволяет машине клонировать репозиторий:

   ```bash
   curl -X POST https://tuist.dev/api/accounts/my-org/runners/jobs \
     -H "Authorization: Bearer $TUIST_TOKEN" \
     -H "Content-Type: application/json" \
     -d '{
       "profile": "tuist-macos",
       "repository_url": "https://git.example.com/acme/app.git",
       "clone_token": "<short-lived token>",
       "commit_sha": "4f1c2d0e9b8a7c6d5e4f3a2b1c0d9e8f7a6b5c4d",
       "ref": "refs/heads/main",
       "name": "test",
       "script": "mise install\nmise run test",
       "secrets": { "SIGNING_KEY": "..." },
       "timeout_minutes": 30,
       "idempotency_key": "acme/app:4f1c2d0e:test"
     }'
   ```

   В ответе возвращается задача с её `workflow_job_id`. Она сразу появляется в разделе **Runners** вашей панели управления Tuist и запускается, как только освободится машина указанного профиля. Прогретые машины обычно запускают её за считанные секунды.

3. **Отслеживайте выполнение задачи.** Подпишите <.localized_link href="/guides/integrations/webhooks">вебхук</.localized_link> на события `runner_job.started` и `runner_job.completed`. В событии завершения передаётся `conclusion` задачи: `success`, `failure` или `cancelled`. Также можно опрашивать `GET /api/accounts/my-org/runners/jobs/{workflow_job_id}` и читать лог через `GET /api/accounts/my-org/runners/jobs/{workflow_job_id}/logs`.

## Интеграция с Git-форджем {#integrate-a-git-forge}

Фордж без собственного протокола раннеров подключается через небольшой мост, который может быть сервисом самого форджа или функцией, вызываемой из его хуков:

1. **При пуше** хук push форджа обращается к мосту. Мост проверяет хук, определяет, какие проверки нужны для коммита, и выпускает токен только для чтения для клонирования репозитория, срок действия которого истекает после таймаута задачи.
2. **Для каждой проверки** мост создаёт задачу с установленным `idempotency_key` в значение `<repository>:<commit>:<check>`, поэтому повторная доставка хука не создаст ничего нового. Он сохраняет полученный `workflow_job_id` и может пометить проверку как ожидающую в фордже.
3. **При событиях `runner_job.started` и `runner_job.completed`** мост проверяет заголовок `Tuist-Signature` с помощью секрета эндпоинта, находит проверку по `workflow_job_id` или `idempotency_key` и обновляет статус коммита в фордже, указывая `conclusion`. Он может добавить ссылку на страницу задачи в панели управления Tuist.
4. **Когда пуш заменяет коммит**, мост отменяет задачи, созданные для старого коммита.

## Как выполняется задача {#how-the-job-runs}

Машина получает `commit_sha` из `repository_url` по HTTPS. Если сервер не отдаёт коммит по его SHA, вместо этого запрашивается `ref`, который должен содержать этот коммит. `clone_token`, если он указан, отправляется только хосту репозитория в виде `Authorization: Bearer <token>`. Он никогда не попадает в ваш скрипт или лог задачи.

Ваш скрипт выполняется в Bash в login-оболочке с параметром `set -eo pipefail` из корня клонированного репозитория. Задача завершается с ошибкой, если скрипт возвращает ненулевой код выхода или превышает время выполнения `timeout_minutes` (по умолчанию 60 минут, максимум 360). Помимо ваших `env` и `secrets`, скрипт видит переменные `CI=true`, `TUIST_JOB_ID`, `TUIST_JOB_NAME`, `TUIST_JOB_REPOSITORY_URL`, `TUIST_JOB_REF` и `TUIST_JOB_COMMIT_SHA`. Значения `secrets` маскируются в логе задачи.

## Повторные попытки и идемпотентность {#idempotency}

Укажите для каждой задачи `idempotency_key`, описывающий её назначение, например `<repository>:<commit>:<check>`. Запрос с ключом, уже использованным в вашем аккаунте, вернёт существующую задачу со статусом 200 вместо 201 и ничего не создаст заново. Это позволяет вашему хуку push передавать запрос в очередь повторных попыток без риска создания дубликатов задач.

Доставки вебхуков повторяются до тех пор, пока ваш эндпоинт не ответит статусом 2xx, поэтому событие может прийти несколько раз. Для устранения дубликатов используйте `id` конверта или `workflow_job_id` задачи вместе с типом события.

## Отмена задачи {#cancel-a-job}

```bash
curl -X POST https://tuist.dev/api/accounts/my-org/runners/jobs/{workflow_job_id}/cancel \
  -H "Authorization: Bearer $TUIST_TOKEN"
```

Задача, которую ни одна машина ещё не начала выполнять, отменяется немедленно. Выполняющаяся задача останавливается в течение нескольких секунд, а в событии завершения указывается `cancelled`. Задача, которую ни одна машина не начала в течение 24 часов, отменяется автоматически.

## Кэширование и доверие {#trust}

Любой, кто может делать пуш в репозиторий, может изменить то, что выполняет задача, поэтому задачи API считаются недоверенными: они не получают доступ к общим <.localized_link href="/guides/features/runners/cache-volumes">томам кэша</.localized_link> вашего аккаунта и к правам на подпись кэша. Секреты, скрипт и токен клонирования задачи хранятся в зашифрованном виде и удаляются после её завершения.
