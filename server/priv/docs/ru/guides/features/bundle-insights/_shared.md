## Теги {#tags}

Добавляйте теги при загрузке бандла, чтобы различать варианты сборки, окружения или каналы релизов. Теги бандлов следуют тем же правилам, что и теги Build Insights:

```bash
tuist inspect bundle App.ipa --tags paid production
```

В CI вы также можете задать теги через запятую с помощью `TUIST_BUNDLE_TAGS`:

```bash
TUIST_BUNDLE_TAGS="paid,production" tuist inspect bundle App.ipa
```

Явные `--tags` заменяют теги из переменной окружения. Теги могут содержать буквы, цифры, дефисы и подчеркивания, до 10 тегов на бандл и до 50 символов в одном теге. Эти же параметры работают для Android-бандлов. `--json` остаётся локальным и не загружает ни теги, ни сам бандл.

Теги отображаются рядом с названиями бандлов и в деталях бандла. Используйте фильтр **Tags** в панели управления и введите тег, чтобы включить или исключить его из списка бандлов. Совпадение точное и чувствительное к регистру, даже если операторы фильтра названы **contains** и **does not contain**: `paid` не совпадает с `paid-extra`. Для фильтрации из CLI:

```bash
tuist bundle list --tags paid production
```

CLI, API (`?tags=paid,production`) и инструмент MCP `list_bundles` (`tags: ["paid", "production"]`) возвращают бандлы, содержащие **все** указанные теги. При загрузке через API принимается параметр `bundle.custom_metadata.tags`; ответы списков и деталей возвращают `custom_metadata.tags`. Существующие бандлы без тегов остаются доступными как раньше. Теги фильтруют список бандлов, но не влияют на графики размеров или автоматические сравнения и базовые линии порогов.

Существующие клиенты могут продолжать загружать и читать бандлы без тегов. Обновлённые клиенты также могут читать ответы от старых серверов, которые опускают `custom_metadata`. Хранение и фильтрация тегов требуют версии сервера с поддержкой тегов бандлов: старые серверы игнорируют метаданные загрузки и отклоняют фильтры по тегам. Обновлённые клиенты не отправляют метаданные загрузки и параметры запроса тегов, если теги не указаны.

## Понимание размеров бандлов {#understanding-sizes}

Для каждого проанализированного бандла Tuist сообщает два значения:

- **Install size**: место, которое приложение занимает после установки на устройство.
- **Download size**: сжатый размер, который пользователи скачивают. Для Apple-бандлов это значение доступно только для `.ipa` (размер архива); для входных данных `.xcarchive` или `.app` оно недоступно.

Размеры хранятся в байтах и отображаются по десятичной системе, где 1 МБ равен 1 000 000 байт, а 1 ГБ — 1 000 000 000 байт, — той же системе, которую Apple использует для отчётов о хранилище и размерах приложений (см. [How storage capacity is measured on Apple devices](https://support.apple.com/en-us/102119)). Размер установки 733 446 863 байт отображается как 733,4 МБ.

## Непрерывная интеграция {#continuous-integration}

Чтобы отслеживать размер бандла со временем, анализируйте бандл в CI. Сначала убедитесь, что ваш CI <.localized_link href="/guides/server/authentication#continuous-integration">аутентифицирован</.localized_link>.

Tuist также должен знать, к какому проекту относить бандл. Если вы ещё не подключили проект, выполните `tuist init` или укажите handle вручную:

::: code-group
```swift [Tuist.swift]
let tuist = Tuist(fullHandle: "my-account/my-project")
```
```toml [tuist.toml]
project = "my-account/my-project"
```
<!-- -->
:::

Используйте <.localized_link href="/references/tuist-toml">`tuist.toml`</.localized_link> для проектов без Swift-манифеста, например Gradle-проектов. Если присутствуют оба файла, приоритет имеет `Tuist.swift`.

Пример рабочего процесса GitHub Actions:

::: code-group
```yaml [Apple]
name: Build

jobs:
  build:
    steps:
      - # Build your app
      - name: Analyze bundle
        run: tuist inspect bundle App.ipa
        env:
          TUIST_TOKEN: ${{ secrets.TUIST_TOKEN }}
```
```yaml [Android]
name: Build

jobs:
  build:
    steps:
      - # Build your app
      - name: Analyze bundle
        # .aab is recommended over .apk for more accurate size analysis
        run: tuist inspect bundle App.aab
        env:
          TUIST_TOKEN: ${{ secrets.TUIST_TOKEN }}
```
<!-- -->
:::

## Пороги размера {#size-thresholds}

> [!WARNING]
> **Требуется интеграция с Git-форжем**
>
> Чтобы использовать пороги размера, подключите [Tuist GitHub App](https://github.com/apps/tuist) к вашему проекту. Это можно сделать на странице интеграций проекта.

Пороги размера позволяют блокировать pull request, если размер бандла превышает заданный процент или абсолютное значение по сравнению с базовой веткой. При нарушении порога Tuist создаёт GitHub Check Run для коммита PR, блокируя слияние до устранения увеличения размера:

![Проверка статуса PR, показывающая превышение порога размера бандла](/images/guides/features/bundle-size/github-pr-check-status.png)

Check run показывает базовый размер, текущий размер и изменение в выбранной единице измерения. Если увеличение преднамеренное, вы можете принять его прямо в интерфейсе GitHub, нажав кнопку **Accept**:

![Check run GitHub, показывающий нарушение порога](/images/guides/features/bundle-size/github-check-run-threshold.png)

### Настройка {#size-thresholds-configuration}

Чтобы настроить пороги, перейдите на вкладку **Settings > Bundles** вашего проекта:

![Настройки порогов размера бандла](/images/guides/features/bundle-size/bundle-size-thresholds.png)

Выберите **Install size** или **Download size**, затем выберите **Threshold type**:

- **Percentage (%)**: ограничивает рост относительно базового размера. Поддерживаются дробные проценты, например `0.47`. Существующие процентные пороги сохраняют свои настроенные значения и поведение.
- **Absolute size (MB)**: ограничивает рост фиксированным значением, независимо от базового размера. Введите `1.5`, чтобы разрешить рост до 1,5 МБ. MB использует десятичные единицы: 1 МБ = 1 000 000 байт. Значения должны приводиться к положительному целому числу байт.

![Настройка порога абсолютного роста размера бандла](/images/guides/features/bundle-size/absolute-size-threshold.png)

Оба типа сравнивают с последним бандлом на настроенной **Baseline branch** с тем же именем, тем же типом бандла (например, `.app` или `.ipa`) и хотя бы одной общей платформой, поэтому симуляторный `.app` сравнивается только с загрузками симуляторного `.app`. Необязательное поле **Bundle name** ограничивает правило этим бандлом. Проверка завершается ошибкой только если рост **more than** лимита; равный рост, неизменные размеры и уменьшение проходят проверку. При отсутствии подходящей базы или записанного размера для выбранной метрики правило пропускается. Нулевой размер базы поддерживается для абсолютных лимитов; процентные лимиты продолжают пропускать её, так как процентный рост не определён.

### Ограничение круга лиц, которые могут принять {#size-thresholds-approvals}

По умолчанию любой пользователь с правами на запись в репозиторий может принять увеличение размера, поскольку именно ему GitHub показывает кнопку. Чтобы сузить круг, настройте параметр **Who can accept** в разделе **Settings > Bundles**:

- **Anyone**: по умолчанию. Любой пользователь с правами на запись в репозиторий.
- **Selected GitHub users**: только указанные вами пользователи GitHub.

Если пользователя нет в списке, проверка остаётся неудачной с пояснением, а кнопка остаётся доступной для тех, кто может ею воспользоваться.
