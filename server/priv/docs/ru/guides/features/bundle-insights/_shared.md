## Теги {#tags}

Прикрепляйте теги при загрузке бандла, чтобы различать варианты сборки, окружения или каналы выпуска. Теги бандлов следуют тем же правилам, что и теги Build Insights:

```bash
tuist inspect bundle App.ipa --tags paid production
```

В CI вы также можете задать теги через запятую с помощью `TUIST_BUNDLE_TAGS`:

```bash
TUIST_BUNDLE_TAGS="paid,production" tuist inspect bundle App.ipa
```

Явные `--tags` заменяют теги из переменной окружения. Теги могут содержать буквы, цифры, дефисы и подчёркивания; допускается до 10 тегов на бандл и до 50 символов в одном теге. Те же параметры работают для Android-бандлов. `--json` остаётся локальным и не загружает ни теги, ни сам бандл.

Теги отображаются рядом с именами бандлов и в деталях бандла. Используйте фильтр **Теги** в дашборде и введите тег, чтобы включить его в список бандлов или исключить из него. Сопоставление точное и чувствительное к регистру, даже если операторы фильтра называются **содержит** и **не содержит**: `paid` не совпадает с `paid-extra`. Чтобы отфильтровать из CLI:

```bash
tuist bundle list --tags paid production
```

CLI, API (`?tags=paid,production`) и инструмент MCP `list_bundles` (`tags: ["paid", "production"]`) возвращают бандлы, содержащие **все** указанные теги. При загрузке через API принимается `bundle.custom_metadata.tags`; ответы списков и деталей возвращают `custom_metadata.tags`. Существующие бандлы без тегов остаются доступными как раньше. Теги фильтруют список бандлов; они не изменяют графики размеров или базовые линии автоматического сравнения и порогов.

Существующие клиенты могут продолжать загружать и читать бандлы без тегов. Обновлённые клиенты также могут читать ответы от старых серверов, которые опускают `custom_metadata`. Хранение и фильтрация тегов требуют версии сервера с поддержкой тегов бандлов: старые серверы игнорируют метаданные загрузки и отклоняют фильтры по тегам. Обновлённые клиенты не отправляют метаданные загрузки и параметры запроса тегов, если теги не указаны.

## Понимание размеров бандлов {#understanding-sizes}

Для каждого проанализированного бандла Tuist сообщает два значения:

- **Размер установки**: место, которое приложение занимает после установки на устройство.
- **Размер загрузки**: сжатый размер, который скачивают пользователи. Для Apple-бандлов это сообщается только для `.ipa` (размер архива); для входных данных `.xcarchive` или `.app` оно недоступно.

Размеры хранятся в байтах и отображаются по десятичной системе, где 1 МБ = 1 000 000 байт, а 1 ГБ = 1 000 000 000 байт — та же система, которую Apple использует для отчётов о хранилище и размерах приложений (см. [Как измеряется ёмкость хранилища на устройствах Apple](https://support.apple.com/en-us/102119)). Размер установки 733 446 863 байт отображается как 733,4 МБ.

## Непрерывная интеграция {#continuous-integration}

Чтобы отслеживать размер бандла со временем, анализируйте бандл в CI. Сначала убедитесь, что ваш CI <.localized_link href="/guides/integrations/continuous-integration#authentication">аутентифицирован</.localized_link>.

Tuist также должен знать, в какой проект сообщать о бандле. Если вы ещё не подключили проект, выполните `tuist init` или укажите handle самостоятельно:

::: code-group
```swift [Tuist.swift]
let tuist = Tuist(fullHandle: "my-account/my-project")
```
```toml [tuist.toml]
project = "my-account/my-project"
```
<!-- -->
:::

Используйте <.localized_link href="/references/tuist-toml">`tuist.toml`</.localized_link> для проектов без Swift-манифеста, например Gradle-проектов. Когда присутствуют оба файла, приоритет имеет `Tuist.swift`.

Пример рабочего процесса GitHub Actions:

::: code-group
```yaml [Apple]
name: Build

jobs:
  build:
    steps:
      - # Build your app
      - name: Analyze bundle
        run: tuist inspect bundle App.ipa
        env:
          TUIST_TOKEN: ${{ secrets.TUIST_TOKEN }}
```
```yaml [Android]
name: Build

jobs:
  build:
    steps:
      - # Build your app
      - name: Analyze bundle
        # .aab is recommended over .apk for more accurate size analysis
        run: tuist inspect bundle App.aab
        env:
          TUIST_TOKEN: ${{ secrets.TUIST_TOKEN }}
```
<!-- -->
:::

## Пороги размера {#size-thresholds}

> [!WARNING]
> **Требуется интеграция с Git-форжем**
>
> Чтобы использовать пороги размера, подключите [Tuist GitHub App](https://github.com/apps/tuist) к своему проекту. Это можно сделать на странице интеграций проекта.

Пороги размера позволяют блокировать pull request, когда размер бандла превышает настроенный процент или абсолютное значение по сравнению с базовой веткой. При нарушении порога Tuist создаёт GitHub Check Run для коммита PR, блокируя слияние до устранения увеличения размера:

![Проверка статуса PR показывает превышение порога размера бандла](/images/guides/features/bundle-size/github-pr-check-status.png)

Check run показывает базовый размер, текущий размер и изменение в выбранной единице измерения. Если увеличение преднамеренное, вы можете принять его прямо в интерфейсе GitHub, нажав кнопку **Принять**:

![GitHub check run показывает нарушение порога](/images/guides/features/bundle-size/github-check-run-threshold.png)

### Настройка {#size-thresholds-configuration}

Чтобы настроить пороги, перейдите на вкладку **Настройки > Бандлы** вашего проекта:

![Настройки порогов размера бандлов](/images/guides/features/bundle-size/bundle-size-thresholds.png)

Выберите **Размер установки** или **Размер загрузки**, затем выберите **Тип порога**:

- **Процент (%)**: ограничивает рост относительно базового размера. Поддерживаются дробные проценты, например `0.47`. Существующие процентные пороги сохраняют свои настроенные значения и поведение.
- **Абсолютный размер (МБ)**: ограничивает рост на фиксированную величину, независимо от базового размера. Введите `1.5`, чтобы разрешить рост до 1,5 МБ. МБ использует десятичные единицы: 1 МБ = 1 000 000 байт. Значения должны приводиться к положительному целому числу байт.

![Настройка порога абсолютного роста размера бандла](/images/guides/features/bundle-size/absolute-size-threshold.png)

Оба типа сравнивают с последним бандлом на настроенной **базовой ветке** с тем же именем, тем же типом бандла (например, `.app` или `.ipa`) и хотя бы одной общей платформой, поэтому симуляторный `.app` сравнивается только с загрузками симуляторных `.app`. Необязательное поле **Имя бандла** ограничивает правило этим бандлом. Проверка завершается неудачей только если рост **превышает** лимит; равный рост, неизменные размеры и уменьшение проходят проверку. Без подходящей базы или записанного размера для выбранной метрики правило пропускается. Базовый размер нуля поддерживается для абсолютных лимитов; процентные лимиты продолжают пропускать его, так как процентный рост не определён.

### Ограничение круга лиц, которые могут принять {#size-thresholds-approvals}

По умолчанию любой пользователь с правами на запись в репозиторий может принять увеличение размера, потому что именно ему GitHub показывает кнопку. Чтобы сузить круг, настройте параметр **Кто может принять** в разделе **Настройки > Бандлы**:

- **Все**: значение по умолчанию. Любой пользователь с правами на запись в репозиторий.
- **Выбранные пользователи GitHub**: только указанные вами имена пользователей GitHub.

Если пользователя нет в списке, проверка остаётся неуспешной с пояснением, а кнопка остаётся доступной для тех, кто может ею воспользоваться.
