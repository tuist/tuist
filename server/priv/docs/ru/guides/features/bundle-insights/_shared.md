## Теги {#tags}

Добавляйте теги при загрузке бандла, чтобы различать варианты сборки, окружения или каналы релизов. Теги бандлов следуют тем же правилам, что и теги Build Insights:

```bash
tuist inspect bundle App.ipa --tags paid production
```

В CI вы также можете задать теги через запятую с помощью `TUIST_BUNDLE_TAGS`:

```bash
TUIST_BUNDLE_TAGS="paid,production" tuist inspect bundle App.ipa
```

Явное указание `--tags` заменяет теги из переменной окружения. Теги могут содержать буквы, цифры, дефисы и подчеркивания; не более 10 тегов на бандл и до 50 символов в каждом теге. Эти же параметры работают для Android-бандлов. `--json` работает только локально и не загружает ни теги, ни сам бандл.

Теги отображаются рядом с названиями бандлов и в деталях бандла. Используйте фильтр **Tags** в дашборде и введите тег, чтобы включить его в список бандлов или исключить из него. Сравнение выполняется точно и с учетом регистра, даже если операторы фильтра помечены как **contains** и **does not contain**: `paid` не совпадает с `paid-extra`. Чтобы отфильтровать через CLI:

```bash
tuist bundle list --tags paid production
```

CLI, API (`?tags=paid,production`) и инструмент MCP `list_bundles` (`tags: ["paid", "production"]`) возвращают бандлы, содержащие **все** указанные теги. При загрузке через API принимаются значения `bundle.custom_metadata.tags`; ответы списков и детализации возвращают `custom_metadata.tags`. Существующие бандлы без тегов остаются доступными, как и раньше. Теги фильтруют список бандлов; они не влияют на графики размеров или автоматические сравнения и базовые линии порогов.

Существующие клиенты могут продолжать загружать и читать бандлы без тегов. Обновленные клиенты также могут читать ответы от старых серверов, которые опускают `custom_metadata`. Хранение и фильтрация по тегам требуют версии сервера с поддержкой тегов бандлов: старые серверы игнорируют метаданные загрузки и отклоняют фильтры по тегам. Обновленные клиенты не отправляют метаданные загрузки и параметры запроса по тегам, если теги не указаны.

## Понимание размеров бандлов {#understanding-sizes}

Для каждого проанализированного бандла Tuist сообщает два значения:

- **Install size**: место, которое приложение занимает после установки на устройство.
- **Download size**: сжатый размер, который скачивают пользователи. Для Apple-бандлов это значение доступно только для `.ipa` (размер архива); для входных данных `.xcarchive` или `.app` оно недоступно.

Размеры хранятся в байтах и отображаются в десятичной системе, где 1 МБ = 1 000 000 байт, а 1 ГБ = 1 000 000 000 байт — та же система, которую Apple использует для отчетов о хранилище и размерах приложений (см. [How storage capacity is measured on Apple devices](https://support.apple.com/en-us/102119)). Размер установки 733 446 863 байт отображается как 733,4 МБ.

## Непрерывная интеграция {#continuous-integration}

Чтобы отслеживать размер бандла со временем, анализируйте его в CI. Сначала убедитесь, что ваш CI <.localized_link href="/guides/server/authentication#continuous-integration">аутентифицирован</.localized_link>.

Tuist также должен знать, к какому проекту относить бандл. Если проект еще не подключен, выполните `tuist init` или укажите handle вручную:

::: code-group
```swift [Tuist.swift]
let tuist = Tuist(fullHandle: "my-account/my-project")
```
```toml [tuist.toml]
project = "my-account/my-project"
```
<!-- -->
:::

Используйте <.localized_link href="/references/tuist-toml">`tuist.toml`</.localized_link> для проектов без Swift-манифеста, например Gradle-проектов. Если присутствуют оба файла, приоритет имеет `Tuist.swift`.

Пример рабочего процесса GitHub Actions:

::: code-group
```yaml [Apple]
name: Build

jobs:
  build:
    steps:
      - # Build your app
      - name: Analyze bundle
        run: tuist inspect bundle App.ipa
        env:
          TUIST_TOKEN: ${{ secrets.TUIST_TOKEN }}
```
```yaml [Android]
name: Build

jobs:
  build:
    steps:
      - # Build your app
      - name: Analyze bundle
        # .aab is recommended over .apk for more accurate size analysis
        run: tuist inspect bundle App.aab
        env:
          TUIST_TOKEN: ${{ secrets.TUIST_TOKEN }}
```
<!-- -->
:::

## Пороги размера {#size-thresholds}

> [!WARNING]
> **Требуется интеграция с Git-форжем**
>
> Чтобы использовать пороги размера, подключите [Tuist GitHub App](https://github.com/apps/tuist) к своему проекту. Это можно сделать на странице интеграций проекта.

Пороги размера позволяют блокировать pull request, когда размер бандла превышает настроенный процент или абсолютное значение по сравнению с базовой веткой. При нарушении порога Tuist создает GitHub Check Run для коммита PR, блокируя слияние до устранения увеличения размера:

![Проверка статуса PR, показывающая превышение порога размера бандла](/images/guides/features/bundle-size/github-pr-check-status.png)

Check run показывает базовый размер, текущий размер и изменение в выбранной единице измерения. Если увеличение преднамеренное, вы можете принять его прямо в интерфейсе GitHub, нажав кнопку **Accept**:

![GitHub check run, показывающий нарушение порога](/images/guides/features/bundle-size/github-check-run-threshold.png)

### Настройка {#size-thresholds-configuration}

Чтобы настроить пороги, перейдите на вкладку **Settings > Bundles** вашего проекта:

![Настройки порогов размера бандла](/images/guides/features/bundle-size/bundle-size-thresholds.png)

Выберите **Install size** или **Download size**, затем выберите **Threshold type**:

- **Percentage (%)**: ограничивает рост относительно базового размера. Поддерживаются дробные проценты, например `0.47`. Существующие процентные пороги сохраняют свои настроенные значения и поведение.
- **Absolute size (MB)**: ограничивает рост на фиксированную величину, независимо от базового размера. Введите `1.5`, чтобы разрешить рост до 1,5 МБ. MB использует десятичные единицы: 1 МБ = 1 000 000 байт. Значения должны приводиться к положительному целому числу байт.

![Настройка порога абсолютного роста размера бандла](/images/guides/features/bundle-size/absolute-size-threshold.png)

Оба типа сравнивают с последним бандлом на настроенной **Baseline branch** с тем же именем, тем же типом бандла (например, `.app` или `.ipa`) и хотя бы одной общей платформой, поэтому симуляторный `.app` сравнивается только с загрузками симуляторных `.app`. Необязательное поле **Bundle name** ограничивает правило этим бандлом. Проверка не проходит только тогда, когда рост **more than** лимита; равный рост, неизменные размеры и уменьшение проходят. При отсутствии подходящей базовой линии или записанного размера для выбранной метрики правило пропускается. Базовая линия нулевого размера поддерживается для абсолютных лимитов; процентные лимиты продолжают пропускать её, так как процентный рост не определен.

### Ограничение круга лиц, которые могут принять {#size-thresholds-approvals}

По умолчанию любой пользователь с правами на запись в репозиторий может принять увеличение размера, потому что именно ему GitHub показывает кнопку. Чтобы сузить круг, настройте **Who can accept** в разделе **Settings > Bundles**:

- **Anyone**: по умолчанию. Любой пользователь с правами на запись в репозиторий.
- **Selected GitHub users**: только указанные вами имена пользователей GitHub.

Если пользователя нет в списке, проверка остается неуспешной с пояснением, а кнопка остается доступной для тех, кто может ею воспользоваться.
