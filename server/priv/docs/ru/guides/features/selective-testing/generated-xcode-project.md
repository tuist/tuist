# Сгенерированный проект Xcode {#generated-xcode-project}

По мере роста проекта увеличивается и количество тестов. Долгое время запуск всех тестов при каждом PR или пуше в `main` занимал десятки секунд. Но такое решение не масштабируется на тысячи тестов, которые могут быть у вашей команды.

При каждом запуске тестов в CI вы, скорее всего, заново прогоняете все тесты, независимо от изменений. Выборочное тестирование Tuist помогает значительно ускорить выполнение самих тестов, запуская только те из них, которые изменились с момента последнего успешного запуска, на основе нашего <.localized_link href="/guides/features/projects/hashing">алгоритма хеширования</.localized_link>.

Чтобы выборочно запускать тесты для вашего <.localized_link href="/guides/features/projects">сгенерированного проекта</.localized_link>, используйте команду `tuist test`. Команда <.localized_link href="/guides/features/projects/hashing">хеширует</.localized_link> ваш проект так же, как и для <.localized_link href="/guides/features/cache/module-cache">кеша модулей</.localized_link>, а при успешном выполнении сохраняет хеши, чтобы определить изменения в будущих запусках. В следующих запусках `tuist test` прозрачно использует хеши для фильтрации тестов и запускает только те, которые изменились с момента последнего успешного прогона.

`tuist test` напрямую интегрируется с <.localized_link href="/guides/features/cache/module-cache">кешем модулей</.localized_link>, используя бинарные файлы из локального или удаленного хранилища для сокращения времени сборки при запуске набора тестов. Сочетание выборочного тестирования с кешированием модулей может существенно сократить время выполнения тестов в CI.

Если ваши тесты предназначены только для симуляторов, передайте флаг `--destination simulator`, чтобы `tuist test` использовал и загружал только части кэшированных бинарных файлов для симулятора. См. раздел <.localized_link href="/guides/features/cache/module-cache#destination-selection">выбора целевого устройства</.localized_link>. Хеши для выборочного тестирования одинаковы для любого значения `--destination`.

## Раздельные задачи сборки и тестирования {#separate-build-and-test-jobs}

Выборочное тестирование поддерживает раздельные задачи сборки и тестирования. Выполните `tuist test --build-only` в задаче сборки, чтобы Tuist мог сохранить файл `selective-testing-graph.json` рядом с артефактами сборки. Этот граф содержит хеши, необходимые для выборочного тестирования, поэтому задаче тестирования не нужно заново генерировать проект или разрешать зависимости Swift Package, чтобы определить, какие цели запускать.

Во время `--build-only` Tuist записывает граф в два места:

- Внутри бандла `.xctestproducts`, если передан параметр `-testProductsPath`.
- Рядом с каждым файлом `.xctestrun` в директории `Build/Products/` производных данных.

Кешируйте любой из этих результатов вместе со сборками и передавайте тот же путь в `--without-building` в задаче тестирования. Работают оба варианта:

```sh
# Build job — writes an .xctestproducts bundle with the graph inside it.
tuist test MyScheme \
  --build-only \
  -- \
  -testProductsPath artifacts/MyScheme.xctestproducts \
  -destination 'platform=iOS Simulator,id=SIMULATOR_IDENTIFIER'

# Test job — restores the same bundle.
tuist test MyScheme \
  --without-building \
  -- \
  -testProductsPath artifacts/MyScheme.xctestproducts \
  -destination 'platform=iOS Simulator,id=SIMULATOR_IDENTIFIER'
```

```sh
# Build job — writes the graph as a sibling of each xctestrun in derived data.
tuist test MyScheme \
  --build-only \
  --derived-data-path artifacts/derived-data

# Test job — points --without-building at any of those xctestrun files.
tuist test MyScheme \
  --without-building \
  --derived-data-path artifacts/derived-data \
  -- \
  -destination 'platform=iOS Simulator,id=SIMULATOR_IDENTIFIER' \
  -xctestrun artifacts/derived-data/Build/Products/MyScheme_iphonesimulator.xctestrun
```

Если Tuist не находит этот граф рядом с входными данными (например, когда задача сборки использовала обычный `xcodebuild build-for-testing` вместо `tuist test --build-only`), он возвращается к повторной генерации проекта, чтобы всё ещё вычислить затронутые цели. Для этого fallback-режима требуется разрешение зависимостей Swift Package в задаче тестирования, поэтому сначала выполните `tuist install` или кешируйте `Tuist/.build` между задачами.

Граф отражает дерево исходного кода таким, каким оно было во время сборки. Запускайте задачу тестирования на том же коммите, что и задачу сборки — если исходный код изменится между ними, хеши устареют, и выборочное тестирование может пропустить тесты, которые на самом деле упадут на новом коде.

### Какой флаг использовать? {#which-flag-should-i-use}

`.xctestrun` и `.xctestproducts` — это два разных формата вывода Xcode, представляющие компромисс между портативностью и удобством в пайплайне:

- **`-testProductsPath` (`.xctestproducts`) — рекомендуется для новых пайплайнов.** Это самодостаточная директория: собранные бинарные файлы `.xctest` и их файлы `.xctestrun` находятся внутри неё, а пути сделаны относительными корня бандла, поэтому она остаётся работоспособной в любом месте. Это также формат, который дольше всего поддерживал быстрый путь выборочного тестирования, поэтому он наиболее отработан.
- **`-xctestrun` (сырой `.xctestrun`) — используйте, если у вас уже есть пайплайн, построенный вокруг производных данных.** `xcodebuild build-for-testing` по умолчанию записывает `.xctestrun` в начало `<derivedData>/Build/Products/` и указывает на тестовые бандлы, расположенные elsewhere в этом дереве. Повторное использование в другой задаче означает сохранение путей в `Build/Products/` неизменными.

Если вы начинаете с нуля, предпочтите `-testProductsPath`. Если вы интегрируете Tuist в существующий пайплайн, который уже кеширует производные данные, `-xctestrun` теперь получит тот же быстрый путь, при условии, что задача сборки выполняется через `tuist test --build-only`.

Любой из режимов ввода взаимно исключает `-workspace`/`-project`/`-scheme`, поэтому Tuist пропускает эти флаги, если сквозные аргументы включают `-xctestrun` или `-testProductsPath`, и передает выбранные цели через `-only-testing`.

> [!WARNING]
> **Гранулярность на уровне модулей против уровня файлов**
>
> Из-за невозможности обнаружения зависимостей в коде между тестами и исходниками максимальная гранулярность выборочного тестирования находится на уровне целей. Поэтому мы рекомендуем делать ваши цели небольшими и сфокусированными, чтобы максимизировать преимущества выборочного тестирования.


> [!NOTE]
> **Покрытие кода тестами**
>
> Инструменты покрытия кода, читающие отчет одного запуска (включая Xcode), предполагают, что был выполнен весь набор тестов, поэтому отчет выборочного запуска не включает пропущенные тесты. <.localized_link href="/guides/features/test-code-coverage/generated-xcode-project">Покрытие кода</.localized_link> Tuist вместо этого переносит данные о покрытии пропущенных целей тестов из предыдущего запуска, используя <.localized_link href="/guides/features/test-code-coverage/generated-xcode-project#target-level-coverage">покрытие на уровне целей</.localized_link>, которое записывается при каждом запуске.


## Комментарии к pull/merge request {#pullmerge-request-comments}

> [!WARNING]
> **Требуется интеграция с Git-платформой**
>
> Чтобы получать автоматические комментарии к pull/merge-запросам, интегрируйте ваш <.localized_link href="/guides/server/accounts-and-projects">проект Tuist</.localized_link> с <.localized_link href="/guides/server/authentication">Git-платформой</.localized_link>.


Как только ваш проект Tuist будет подключен к Git-платформе, такой как [GitHub](https://github.com), и вы начнете использовать `tuist test` в рамках своего CI-воркфлоу, Tuist опубликует комментарий непосредственно в ваших pull/merge requests, указав, какие тесты были запущены, а какие пропущены: ![Комментарий приложения GitHub со ссылкой на Tuist Preview](/images/guides/features/selective-testing/github-app-comment.png)


## Исследование промахов на дашборде {#investigating-misses-on-the-dashboard}

Когда ранее закэшированная тестовая цель отображается как промах, вкладка **Выборочное тестирование** на странице запуска тестов позволяет детально изучить входные данные, сформировавшие хеш. Развертывание строки показывает подхеши по компонентам — исходники, зависимости, переменные окружения, настройки проекта и целей, Info.plist, entitlements, заголовки и т. д., — что позволяет точно определить входные данные, которые изменились между запусками.

Используйте кнопку **Копировать как JSON** в верхней части карточки «Выборочное тестирование», чтобы экспортировать каждую цель выборочного тестирования с её хешем и подхешами. Сравнение JSON между двумя запусками — самый быстрый способ подтвердить, какие входные данные изменились, когда хеш тестовой цели изменился.
