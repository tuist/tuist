# Сгенерированный проект Xcode {#generated-xcode-project}

По мере роста проекта запуск всех тестов при каждом пуше перестаёт масштабироваться. Выборочное тестирование Tuist запускает только те тесты, чьи таргеты изменились с момента последнего успешного запуска тестов, на основе <.localized_link href="/guides/features/projects/hashing">алгоритма хеширования</.localized_link> Tuist.

Чтобы выборочно запускать тесты в вашем <.localized_link href="/guides/features/projects">сгенерированном проекте</.localized_link>, используйте команду `tuist test`. Команда <.localized_link href="/guides/features/projects/hashing">хеширует</.localized_link> ваш проект так же, как для <.localized_link href="/guides/features/cache/module-cache">кэша модулей</.localized_link>, и при успехе сохраняет хеши, чтобы определить, что изменилось в будущих запусках. В последующих запусках `tuist test` прозрачно использует хеши для фильтрации тестов и запускает только те, которые изменились с момента последнего успешного запуска.

`tuist test` напрямую интегрируется с <.localized_link href="/guides/features/cache/module-cache">кэшем модулей</.localized_link>, чтобы использовать как можно больше бинарных файлов из вашего локального или удалённого хранилища и сократить время сборки при запуске набора тестов. Сочетание выборочного тестирования с кэшированием модулей может значительно сократить время выполнения тестов в вашем CI.

Если ваши тесты предназначены только для симуляторов, передайте `--destination simulator`, чтобы `tuist test` использовал и загружал только срезы симулятора из кэшированных бинарных файлов. См. <.localized_link href="/guides/features/cache/module-cache#destination-selection">выбор назначения</.localized_link>. Хеши выборочного тестирования одинаковы для любого значения `--destination`.

## Раздельные задачи сборки и тестирования {#separate-build-and-test-jobs}

Выборочное тестирование поддерживает раздельные задачи сборки и тестирования. Запустите `tuist test --build-only` в задаче сборки, чтобы Tuist мог сохранить файл `selective-testing-graph.json` рядом с продуктами, создаваемыми сборкой. Этот граф содержит хеши, необходимые для выборочного тестирования, поэтому задаче тестирования не нужно заново генерировать проект или разрешать зависимости Swift Package, чтобы определить, какие таргеты запускать.

Во время `--build-only` Tuist записывает граф в два места:

- Внутри бандла `.xctestproducts`, если вы передали `-testProductsPath`.
- Рядом с каждым файлом `.xctestrun` в директории `Build/Products/` производных данных.

Кэшируйте любой из этих результатов вместе со собранными продуктами и передайте тот же путь в `--without-building` в задаче тестирования. Оба варианта работают:

```sh
# Build job — writes an .xctestproducts bundle with the graph inside it.
tuist test MyScheme \
  --build-only \
  -- \
  -testProductsPath artifacts/MyScheme.xctestproducts \
  -destination 'platform=iOS Simulator,id=SIMULATOR_IDENTIFIER'

# Test job — restores the same bundle.
tuist test MyScheme \
  --without-building \
  -- \
  -testProductsPath artifacts/MyScheme.xctestproducts \
  -destination 'platform=iOS Simulator,id=SIMULATOR_IDENTIFIER'
```

```sh
# Build job — writes the graph as a sibling of each xctestrun in derived data.
tuist test MyScheme \
  --build-only \
  -- \
  -derivedDataPath artifacts/derived-data

# Test job — points --without-building at any of those xctestrun files.
tuist test MyScheme \
  --without-building \
  -- \
  -derivedDataPath artifacts/derived-data \
  -destination 'platform=iOS Simulator,id=SIMULATOR_IDENTIFIER' \
  -xctestrun artifacts/derived-data/Build/Products/MyScheme_iphonesimulator.xctestrun
```

Когда Tuist не может найти этот граф рядом с входными данными (например, когда задача сборки использовала обычный `xcodebuild build-for-testing` вместо `tuist test --build-only`), он возвращается к повторной генерации проекта, чтобы всё ещё вычислить затронутые таргеты. Для этого отката требуется разрешение зависимостей Swift Package в задаче тестирования, поэтому сначала запустите `tuist install` или кэшируйте `Tuist/.build` между задачами.

Граф отражает дерево исходного кода таким, каким оно было во время сборки. Запускайте задачу тестирования для того же коммита, что и задача сборки — если исходный код изменится между ними, хеши перестанут соответствовать источнику, и выборочное тестирование может пропустить тесты, которые на самом деле упадут на новом исходном коде.

### Какой флаг использовать? {#which-flag-should-i-use}

`.xctestrun` и `.xctestproducts` — это два разных формата вывода Xcode, и они представляют собой компромисс между портативностью и удобством в конвейере:

- **`-testProductsPath` (`.xctestproducts`) — рекомендуется для новых конвейеров.** Это самодостаточная директория: собранные бинарные файлы `.xctest` и их файлы `.xctestrun` находятся внутри неё с путями, относительными к корню бандла, поэтому она остаётся действительной независимо от того, куда её поместят.
- **`-xctestrun` (сырой `.xctestrun`) — используйте, если у вас уже есть конвейер, построенный вокруг производных данных.** `xcodebuild build-for-testing` по умолчанию записывает `.xctestrun` в начало `<derivedData>/Build/Products/` и указывает на тестовые бандлы, расположенные в других местах этого дерева. Повторное использование в другой задаче означает сохранение путей в `Build/Products/` без изменений.

Если вы начинаете с нуля, предпочтите `-testProductsPath`. Если вы подключаете Tuist к существующему конвейеру, который уже кэширует производные данные, `-xctestrun` обеспечит тот же быстрый путь, пока задача сборки выполняется через `tuist test --build-only`.

Любой режим ввода взаимно исключает `-workspace`/`-project`/`-scheme`, поэтому Tuist пропускает эти флаги, когда аргументы сквозной передачи включают `-xctestrun` или `-testProductsPath`, и передаёт выбранные таргеты через `-only-testing`.

> [!WARNING]
> **Гранулярность на уровне модуля против уровня файла**
>
> Из-за невозможности обнаружения зависимостей в коде между тестами и исходниками максимальная гранулярность стандартного выборочного тестирования находится на уровне таргета. [Стратегия покрытия](#coverage-based-test-selection) сужает её до отдельных тестов XCTest. Поэтому мы рекомендуем держать ваши таргеты небольшими и сфокусированными, чтобы максимизировать преимущества выборочного тестирования.


## Выбор тестов на основе покрытия {#coverage-based-test-selection}

> [!NOTE]
> **Ранний доступ**
>
> Выбор тестов на основе покрытия находится в раннем доступе. Свяжитесь с нами, чтобы включить его для вашего аккаунта. Пока он не включён, стратегия ведёт себя как стандартное выборочное тестирование.

По умолчанию выборочное тестирование пропускает целые тестовые таргеты, хеш которых уже прошёл проверку. Стратегия `.coverage()` идёт дальше: в оставшихся тестовых таргетах она также пропускает тесты XCTest и XCUITest, покрытие кода которых в предыдущем запуске не включает ни одного файла, затронутого вашим изменением. Включите её в `Tuist.swift`:

```swift
import ProjectDescription

let tuist = Tuist(
    fullHandle: "{account-handle}/{project-handle}",
    testInsights: .testInsights(
        coverage: .coverage(upload: true),
        selectiveTesting: .selectiveTesting(strategy: .coverage())
    ),
    project: .tuist()
)
```

Стратегия требует:

- **Загрузка данных покрытия.** Tuist выбирает тесты на основе покрытия, загруженного предыдущими запусками, поэтому `tuist test` не сможет загрузить манифест, в котором `.coverage()` установлено с `upload: false`.
- **[TestCoverageAttribution](https://github.com/tuist/TestCoverageAttribution) версии 0.3.0 или новее**, подключённый к вашим тестовым таргетам. Он записывает, какие файлы выполняет каждый тест, и пропускает тесты, которые Tuist не выбрал. Таргет без него всегда пропускается целиком, как в стандартном режиме.
- **Запуски тестов на вашей основной ветке без выбора.** Запускайте там `tuist test --no-selective-testing`, а также на любой другой ветке, где тесты не должны пропускаться. Эти запуски выполняют каждый тест и становятся базовыми линиями, с которыми сравниваются последующие запуски.

При включённой стратегии `tuist test` пропускает таргеты, хеш которых уже прошёл проверку, затем запрашивает у Tuist, какие тесты из оставшихся таргетов могут быть затронуты вашим изменением. Таргеты без затронутых тестов не собираются. Новые тесты, тесты, упавшие в последний раз, тесты в изменённом тестовом файле и тесты без записанного покрытия всегда запускаются. Тесты Swift Testing запускаются всякий раз, когда запускается их таргет.

Когда покрытие не может принять решение, вывод объясняет причину. Без недавней базовой линии на той же платформе или когда изменение затрагивает более 5000 файлов, запускается каждый тест, чтобы коммит мог стать базовой линией. Когда изменился файл, который может повлиять на любой тест, например `Package.resolved`, `Project.swift` или `.xcconfig`, запуск использует стандартное выборочное тестирование. Чтобы запустить каждый тест, передайте `--no-selective-testing`.

> [!NOTE]
> **Покрытие тестов**
>
> Инструменты покрытия, читающие отчёт одного запуска (включая Xcode), предполагают, что был выполнен весь набор тестов, поэтому отчёт выборочного запуска не включает пропущенные тесты. <.localized_link href="/guides/features/test-code-coverage/generated-xcode-project">Покрытие кода</.localized_link> в Tuist вместо этого переносит покрытие пропущенных тестовых таргетов из предыдущего запуска, используя <.localized_link href="/guides/features/test-code-coverage/generated-xcode-project#target-level-coverage">покрытие на уровне таргета</.localized_link>, которое записывается при каждом запуске.


## Комментарии к pull/merge request {#pullmerge-request-comments}

> [!WARNING]
> **Требуется интеграция с Git-платформой**
>
> Чтобы получать автоматические комментарии к pull/merge request, интегрируйте ваш <.localized_link href="/guides/server/accounts-and-projects">проект Tuist</.localized_link> с <.localized_link href="/guides/server/authentication">Git-платформой</.localized_link>.


Как только ваш проект Tuist будет подключён к вашей Git-платформе, например [GitHub](https://github.com), и вы начнёте использовать `tuist test` в рамках вашего CI-процесса, Tuist оставит комментарий непосредственно в ваших pull/merge request, указав, какие тесты были запущены, а какие пропущены: ![Комментарий приложения GitHub со ссылкой на Tuist Preview](/images/guides/features/selective-testing/github-app-comment.png)


## Анализ промахов на дашборде {#investigating-misses-on-the-dashboard}

Когда ранее закэшированный тестовый таргет отображается как промах, вкладка **Выборочное тестирование** на странице запуска тестов позволяет изучить входные данные, сформировавшие хеш. Развернув строку, вы увидите субхеши по компонентам — исходный код, зависимости, переменные окружения, настройки проекта и таргета, Info.plist, entitlements, заголовки и так далее, — чтобы точно определить входные данные, которые изменились между запусками.

Используйте кнопку **Копировать как JSON** в верхней части карточки «Выборочное тестирование», чтобы экспортировать каждый таргет выборочного тестирования с его хешем и субхешами. Сравнение JSON между двумя запусками — самый быстрый способ подтвердить, какие входные данные изменились, когда хеш тестового таргета изменился.
