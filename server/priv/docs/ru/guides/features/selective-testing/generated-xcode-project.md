# Сгенерированный проект Xcode {#generated-xcode-project}

По мере роста проекта увеличивается и количество тестов. Долгое время запуск всех тестов при каждом PR или пуше в `main` занимал десятки секунд. Но такое решение не масштабируется на тысячи тестов, которые могут быть в вашей команде.

При каждом запуске тестов в CI вы, скорее всего, повторно запускаете все тесты, независимо от изменений. Выборочное тестирование Tuist помогает значительно ускорить выполнение самих тестов, запуская только те из них, которые изменились с момента последнего успешного прогона на основе нашего <.localized_link href="/guides/features/projects/hashing">алгоритма хеширования</.localized_link>.

Чтобы выборочно запускать тесты для вашего <.localized_link href="/guides/features/projects">сгенерированного проекта</.localized_link>, используйте команду `tuist test`. Эта команда <.localized_link href="/guides/features/projects/hashing">хеширует</.localized_link> ваш проект так же, как и для <.localized_link href="/guides/features/cache/module-cache">кеша модулей</.localized_link>, и при успешном выполнении сохраняет хеши, чтобы определить, что изменилось в будущих запусках. В последующих запусках `tuist test` прозрачно использует хеши для фильтрации тестов и запускает только те, которые изменились с момента последнего успешного прогона.

`tuist test` напрямую интегрируется с <.localized_link href="/guides/features/cache/module-cache">кешем модулей</.localized_link>, чтобы использовать как можно больше бинарных файлов из вашего локального или удаленного хранилища для сокращения времени сборки при запуске набора тестов. Сочетание выборочного тестирования с кешированием модулей может существенно сократить время выполнения тестов в вашем CI.

## Раздельные задачи сборки и тестирования {#separate-build-and-test-jobs}

Выборочное тестирование поддерживает раздельные задачи сборки и тестирования. Выполните `tuist test --build-only` в задаче сборки, чтобы Tuist мог сохранить файл `selective-testing-graph.json` рядом с артефактами, создаваемыми сборкой. Этот граф содержит хеши, необходимые для выборочного тестирования, поэтому задаче тестирования не нужно заново генерировать проект или разрешать зависимости Swift Package, чтобы определить, какие цели запускать.

Во время `--build-only` Tuist записывает граф в два места:

- Внутри бандла `.xctestproducts`, если передан параметр `-testProductsPath`.
- Рядом с каждым файлом `.xctestrun` в директории `Build/Products/` производных данных.

Кэшируйте любой из этих результатов вместе со собранными продуктами и передайте тот же путь в `--without-building` в задаче тестирования. Оба варианта работают:

```sh
# Build job — writes an .xctestproducts bundle with the graph inside it.
tuist test MyScheme \
  --build-only \
  -- \
  -testProductsPath artifacts/MyScheme.xctestproducts \
  -destination 'platform=iOS Simulator,id=SIMULATOR_IDENTIFIER'

# Test job — restores the same bundle.
tuist test MyScheme \
  --without-building \
  -- \
  -testProductsPath artifacts/MyScheme.xctestproducts \
  -destination 'platform=iOS Simulator,id=SIMULATOR_IDENTIFIER'
```

```sh
# Build job — writes the graph as a sibling of each xctestrun in derived data.
tuist test MyScheme \
  --build-only \
  --derived-data-path artifacts/derived-data

# Test job — points --without-building at any of those xctestrun files.
tuist test MyScheme \
  --without-building \
  --derived-data-path artifacts/derived-data \
  -- \
  -destination 'platform=iOS Simulator,id=SIMULATOR_IDENTIFIER' \
  -xctestrun artifacts/derived-data/Build/Products/MyScheme_iphonesimulator.xctestrun
```

Если Tuist не может найти этот граф рядом с входными данными (например, когда задача сборки использовала обычный `xcodebuild build-for-testing` вместо `tuist test --build-only`), он возвращается к повторной генерации проекта, чтобы всё ещё вычислить затронутые цели. Для такого отката требуется разрешение зависимостей Swift Package в задаче тестирования, поэтому сначала выполните `tuist install` или кэшируйте `Tuist/.build` между задачами.

Граф отражает дерево исходного кода таким, каким оно было во время сборки. Запускайте задачу тестирования на том же коммите, что и задачу сборки — если исходный код изменится между ними, хеши устареют, и выборочное тестирование может пропустить тесты, которые на самом деле упадут на новой версии кода.

### Какой флаг использовать? {#which-flag-should-i-use}

`.xctestrun` и `.xctestproducts` — это два разных формата вывода Xcode, и они представляют компромисс между портативностью и удобством конвейера:

- **`-testProductsPath` (`.xctestproducts`) — рекомендуется для новых конвейеров.** Это самодостаточная директория: собранные бинарные файлы `.xctest` и их файлы `.xctestrun` находятся внутри неё с путями, относительными к корню бандла, поэтому она остаётся рабочей независимо от того, куда её поместят. Это также формат, который дольше всего поддерживал быстрый путь выборочного тестирования, поэтому он наиболее отработан.
- **`-xctestrun` (сырой `.xctestrun`) — используйте, если у вас уже есть конвейер, построенный вокруг производных данных.** `xcodebuild build-for-testing` по умолчанию записывает `.xctestrun` в верхнюю часть `<derivedData>/Build/Products/` и указывает на тестовые бандлы, расположенные в других местах этого дерева. Повторное использование в другой задаче означает сохранение путей в `Build/Products/` без изменений.

Если вы начинаете с нуля, предпочтите `-testProductsPath`. Если вы интегрируете Tuist в существующий конвейер, который уже кэширует производные данные, `-xctestrun` теперь получит тот же быстрый путь, при условии что задача сборки выполняется через `tuist test --build-only`.

Любой из режимов ввода взаимно исключаем с `-workspace`/`-project`/`-scheme`, поэтому Tuist пропускает эти флаги, если аргументы сквозной передачи включают `-xctestrun` или `-testProductsPath`, и передаёт выбранные цели через `-only-testing`.

> [!WARNING]
> **Гранулярность на уровне модуля против уровня файла**
>
> Из-за невозможности обнаружения зависимостей в коде между тестами и исходниками максимальная гранулярность выборочного тестирования находится на уровне цели. Поэтому мы рекомендуем делать ваши цели небольшими и сфокусированными, чтобы максимизировать преимущества выборочного тестирования.


> [!WARNING]
> **Покрытие тестами**
>
> Инструменты анализа покрытия тестами предполагают, что весь набор тестов запускается одновременно, что делает их несовместимыми с выборочными запусками — это означает, что данные о покрытии могут не отражать реальность при использовании выбора тестов. Это известное ограничение, и оно не означает, что вы делаете что-то неправильно. Мы призываем команды задуматься, приносит ли покрытие по-прежнему значимые инсайты в этом контексте, и если да, будьте уверены: мы уже думаем о том, как правильно интегрировать покрытие с выборочными запусками в будущем.

Как только ваш проект Tuist будет подключён к Git-платформе, такой как [GitHub](https://github.com), и вы начнёте использовать `tuist test` в рамках своего CI-конвейера, Tuist опубликует комментарий прямо в ваших pull/merge-запросах, указав, какие тесты были запущены, а какие пропущены: ![Комментарий приложения GitHub со ссылкой на Tuist Preview](/images/guides/features/selective-testing/github-app-comment.png)


## Исследование промахов на дашборде {#investigating-misses-on-the-dashboard}

Когда ранее закэшированная цель тестирования отображается как промах, вкладка **Выборочное тестирование** на странице запуска тестов позволяет детально изучить входные данные, сформировавшие хеш. Развёртывание строки показывает подхеши по компонентам — исходники, зависимости, переменные окружения, настройки проекта и цели, Info.plist, entitlements, заголовки и т. д., — что позволяет точно определить входные данные, которые изменились между запусками.

Используйте кнопку **Копировать как JSON** в верхней части карточки выборочного тестирования, чтобы экспортировать каждую цель выборочного тестирования с её хешем и подхешами. Сравнение JSON между двумя запусками — самый быстрый способ подтвердить, какие входные данные изменились, когда хеш цели тестирования устарел.
