# Сгенерированный проект Xcode {#generated-xcode-project}

По мере роста проекта увеличивается и количество тестов. Долгое время запуск всех тестов при каждом PR или пуше в `main` занимал десятки секунд. Но такое решение не масштабируется на тысячи тестов, которые могут быть в вашей команде.

При каждом запуске тестов в CI вы, скорее всего, повторно запускаете все тесты, независимо от внесённых изменений. Выборочное тестирование Tuist помогает значительно ускорить выполнение тестов, запуская только те из них, которые изменились с момента последнего успешного <.localized_link href="/guides/features/projects/hashing">запуска тестов</.localized_link> на основе нашего алгоритма хеширования.

Чтобы выборочно запускать тесты в <.localized_link href="/guides/features/projects">сгенерированном проекте</.localized_link>, используйте команду `tuist test`. Команда <.localized_link href="/guides/features/projects/hashing">хеширует</.localized_link> ваш проект так же, как для <.localized_link href="/guides/features/cache/module-cache">кэша модулей</.localized_link>, и при успешном выполнении сохраняет хеши, чтобы определить изменения в будущих запусках. В следующих запусках `tuist test` прозрачно использует хеши для фильтрации тестов и запускает только те, которые изменились с момента последнего успешного прогона.

`tuist test` напрямую интегрируется с <.localized_link href="/guides/features/cache/module-cache">кэшем модулей</.localized_link>, чтобы использовать как можно больше бинарных файлов из вашего локального или удалённого хранилища и сократить время сборки при запуске набора тестов. Сочетание выборочного тестирования с кэшированием модулей может значительно уменьшить время выполнения тестов в вашем CI.

Если ваши тесты предназначены только для симуляторов, передайте `--destination simulator`, чтобы `tuist test` использовал и загружал только компоненты симулятора из закэшированных бинарных файлов. См. <.localized_link href="/guides/features/cache/module-cache#destination-selection">выбор целевой платформы</.localized_link>. Хэши для выборочного тестирования одинаковы для любого значения `--destination`.

## Раздельные задачи сборки и тестирования {#separate-build-and-test-jobs}

Выборочное тестирование поддерживает раздельные задачи сборки и тестирования. Запустите `tuist test --build-only` в задаче сборки, чтобы Tuist мог сохранить файл `selective-testing-graph.json` рядом с продуктами, создаваемыми сборкой. Этот граф содержит хеши, необходимые для выборочного тестирования, поэтому задаче тестирования не нужно заново генерировать проект или разрешать зависимости Swift Package, чтобы определить, какие цели запускать.

Во время `--build-only` Tuist записывает граф в два места:

- Внутри пакета `.xctestproducts`, если вы передаете `-testProductsPath`.
- Рядом с каждым файлом `.xctestrun` в директории `Build/Products/` производных данных.

Кэшируйте любой из этих результатов вместе со собранными продуктами и передайте тот же путь в `--without-building` в задаче тестирования. Оба варианта работают:

```sh
# Build job — writes an .xctestproducts bundle with the graph inside it.
tuist test MyScheme \
  --build-only \
  -- \
  -testProductsPath artifacts/MyScheme.xctestproducts \
  -destination 'platform=iOS Simulator,id=SIMULATOR_IDENTIFIER'

# Test job — restores the same bundle.
tuist test MyScheme \
  --without-building \
  -- \
  -testProductsPath artifacts/MyScheme.xctestproducts \
  -destination 'platform=iOS Simulator,id=SIMULATOR_IDENTIFIER'
```

```sh
# Build job — writes the graph as a sibling of each xctestrun in derived data.
tuist test MyScheme \
  --build-only \
  --derived-data-path artifacts/derived-data

# Test job — points --without-building at any of those xctestrun files.
tuist test MyScheme \
  --without-building \
  --derived-data-path artifacts/derived-data \
  -- \
  -destination 'platform=iOS Simulator,id=SIMULATOR_IDENTIFIER' \
  -xctestrun artifacts/derived-data/Build/Products/MyScheme_iphonesimulator.xctestrun
```

Когда Tuist не может найти этот граф рядом с входными данными (например, когда задача сборки использовала обычный `xcodebuild build-for-testing` вместо `tuist test --build-only`), он возвращается к повторной генерации проекта, чтобы все еще иметь возможность вычислить затронутые цели. Для этого резервного варианта требуется разрешение зависимостей Swift Package в задаче тестирования, поэтому сначала выполните `tuist install` или кэшируйте `Tuist/.build` между задачами.

Граф отражает дерево исходного кода таким, каким оно было во время сборки. Запускайте задачу тестирования на том же коммите, что и задачу сборки — если исходный код изменится между ними, хеши устареют, и выборочное тестирование может пропустить тесты, которые на самом деле упадут на более новой версии кода.

### Какой флаг использовать? {#which-flag-should-i-use}

`.xctestrun` и `.xctestproducts` — это два разных формата вывода Xcode, и они представляют компромисс между портативностью и удобством в конвейере:

- **`-testProductsPath` (`.xctestproducts`) — рекомендуется для новых конвейеров.** Это самодостаточная директория: собранные бинарные файлы `.xctest` и их файлы `.xctestrun` находятся внутри нее с путями, относительными к корню пакета, поэтому она остается работоспособной wherever it ends up. Это также формат, который дольше всего поддерживал быстрый путь для выборочного тестирования, поэтому он наиболее отtested.
- **`-xctestrun` (сырой `.xctestrun`) — используйте его, если у вас уже есть конвейер, построенный вокруг производных данных.** `xcodebuild build-for-testing` по умолчанию записывает `.xctestrun` в верхнюю часть `<derivedData>/Build/Products/` и указывает на тестовые пакеты, расположенные в других местах этого дерева. Повторное использование в другой задаче означает сохранение путей в `Build/Products/` нетронутыми.

Если вы начинаете с нуля, предпочтите `-testProductsPath`. Если вы внедряете Tuist в существующий конвейер, который уже кэширует производные данные, `-xctestrun` теперь получит тот же быстрый путь, пока задача сборки выполняется через `tuist test --build-only`.

Любой режим ввода взаимно исключает `-workspace`/`-project`/`-scheme`, поэтому Tuist пропускает эти флаги, когда аргументы сквозной передачи включают `-xctestrun` или `-testProductsPath`, и передает выбранные цели через `-only-testing`.

> [!WARNING]
> **Гранулярность на уровне модулей против уровня файлов**
>
> Из-за невозможности обнаружения зависимостей в коде между тестами и исходниками максимальная гранулярность выборочного тестирования находится на уровне целей. Поэтому мы рекомендуем держать ваши цели небольшими и сфокусированными, чтобы максимизировать преимущества выборочного тестирования.


> [!WARNING]
> **Покрытие тестами**
>
> Инструменты покрытия тестами предполагают, что весь набор тестов запускается сразу, что делает их несовместимыми с выборочными запусками тестов — это означает, что данные о покрытии могут не отражать реальность при использовании выбора тестов. Это известное ограничение, и оно не означает, что вы делаете что-то неправильно. Мы призываем команды задуматься о том, приносит ли покрытие значимые инсайты в этом контексте, и если да, будьте уверены, что мы уже думаем о том, как сделать работу покрытия корректной с выборочными запусками в будущем.

Как только ваш проект Tuist будет подключен к вашей Git-платформе, такой как [GitHub](https://github.com), и вы начнете использовать `tuist test` как часть вашего CI-воркфлоу, Tuist опубликует комментарий прямо в ваших pull/merge запросах, включая информацию о том, какие тесты были запущены, а какие пропущены: ![Комментарий приложения GitHub со ссылкой на Tuist Preview](/images/guides/features/selective-testing/github-app-comment.png)


## Исследование промахов на дашборде {#investigating-misses-on-the-dashboard}

Когда ранее закэшированная цель теста отображается как промах, вкладка **Выборочное тестирование** на странице запуска тестов позволяет углубиться во входные данные, которые сформировали хеш. Развертывание строки показывает подхеши по компонентам — исходники, зависимости, переменные окружения, настройки проекта и цели, Info.plist, entitlements, заголовки и т. д. — чтобы вы могли точно определить входные данные, которые изменились между запусками.

Используйте кнопку **Копировать как JSON** в верхней части карточки Selective Testing, чтобы экспортировать каждую цель выборочного тестирования с ее хешем и подхешами. Сравнение JSON между двумя запусками — самый быстрый способ подтвердить, какие входные данные изменились, когда хеш цели теста изменился.
