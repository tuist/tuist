# Поддерживаемые типы превью

Тип превью определяет, что именно вы упаковываете и где это может выполняться, независимо от системы сборки, которая его создала. Каждый рабочий процесс публикации имеет собственные требования к подписи и условиям допуска.

## Мобильные приложения {#mobile-apps}

- **Android:** подписанный APK-файл приложения. Получателям требуется совместимое Android-устройство или эмулятор. Пакеты Android App Bundles (`.aab`) не являются пакетами для установки превью.
- **Apple:** пакет приложения для симулятора или экспортированный IPA-файл для физических устройств. Для сборок под устройства нужен профиль обеспечения, разрешающий установку на устройство получателя.

Руководства по <.localized_link href="/guides/features/previews/xcode">Xcode</.localized_link>, <.localized_link href="/guides/features/previews/gradle">Gradle</.localized_link> и <.localized_link href="/guides/features/previews/bazel">Bazel</.localized_link> описывают, какие артефакты может публиковать каждый рабочий процесс. Например, публикация через Bazel и Once поддерживает допустимые приложения для симуляторов Apple и macOS, но не сборки для физических устройств.

## Настольные приложения {#desktop-apps}

Поделитесь собранным пакетом приложения macOS:

```bash
tuist share path/to/MyApp.app
```

Требования к подписи и нотариализации по-прежнему применяются. Пакет настольного приложения отличается от приложения Tuist для macOS, которое получатели могут использовать для запуска превью.

## Инструменты командной строки {#command-line-tools}

Поделитесь автономным исполняемым файлом на macOS или Linux:

```bash
tuist share path/to/my-tool
```

Если CLI требует пакеты ресурсов, динамические библиотеки или вспомогательные исполняемые файлы, соберите директорию дистрибутива и укажите точку входа относительно этой директории:

```bash
tuist share path/to/distribution --executable bin/my-tool
```

Загружается вся директория дистрибутива. Включите библиотеки, ресурсы и вспомогательные файлы, необходимые вашему инструменту, и убедитесь, что он может работать вне директории сборки. Скриптам требуются shebang и интерпретатор, установленные в системе получателя.

Исполняемые файлы не имеют собственного значка. Передайте PNG-файл через `--icon`, чтобы показать значок в превью, например, для настольного приложения Linux:

```bash
tuist share path/to/distribution --executable bin/my-app --icon path/to/icon.png
```

## Несколько целей CLI {#multiple-cli-targets}

Превью группирует сборки одного и того же CLI для одного коммита; каждая сборка содержит дистрибутив для одной операционной системы и одной или нескольких архитектур CPU. Например, одно превью может содержать дистрибутивы для macOS arm64, macOS x86_64 и Linux x86_64. Универсальный исполняемый файл macOS покрывает обе архитектуры Mac в одной сборке.

Соберите каждую цель отдельно, затем публикуйте дистрибутивы последовательно из одного и того же рабочего каталога Git, используя одно и то же базовое имя точки входа и трек:

```bash
tuist share dist/macos-arm64 --executable bin/tuist --track pr
tuist share dist/macos-x86_64 --executable bin/tuist --track pr
tuist share dist/linux-x86_64 --executable bin/tuist --track pr
```

Эти загрузки добавляют сборки к одной и той же ссылке превью. Сохраняйте проект, коммит, учетную запись публикации, имя CLI и трек одинаковыми во всех загрузках. Tuist выбирает сборку, соответствующую операционной системе и архитектуре CPU получателя.

## Совместимость клиента и сервера {#client-and-server-compatibility}

Используйте актуальную версию Tuist CLI для запуска превью настольных приложений и инструментов командной строки. Если вы размещаете Tuist самостоятельно, обновите сервер перед публикацией этих типов. Мобильные превью продолжают работать со старыми версиями клиентов.

Собирайте приложение для операционных систем и архитектур CPU ваших получателей. Tuist не выполняет кросс-компиляцию вашего приложения и не устанавливает его зависимости; инструментам для Linux также требуются совместимые системные библиотеки.

Превью выполняются с правами вашей пользовательской учетной записи, а не в песочнице. Запускайте только сборки от авторов и pull request'ов, которым вы доверяете.
