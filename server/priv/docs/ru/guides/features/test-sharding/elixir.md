# Шардирование тестов Elixir {#elixir-test-sharding}

Пакет Tuist Hex включает встроенную поддержку шардирования тестов проекта на Elixir. Он использует сервер Tuist для создания сбалансированных планов шардов на основе исторических данных о времени выполнения и компилирует ваш проект один раз, чтобы каждый раннер мог сразу перейти к запуску тестов.

> [!IMPORTANT] REQUIREMENTS
> - Выполните <.localized_link href="/guides/get-started/elixir-project">общую настройку Elixir</.localized_link>, прежде чем настраивать задания шардирования в CI

## Как это работает {#how-it-works}

Шардирование тестов следует двухэтапному рабочему процессу:

1. **Этап сборки:** Tuist компилирует ваш проект для тестирования, перечисляет файлы тестов и создает **план шардов** на сервере. Сервер использует исторические данные о времени выполнения тестов за последние 30 дней, чтобы распределить тесты по шардам так, чтобы каждый шард занимал примерно одинаковое время. Этап сборки загружает сборку и выводит **матрицу шардов**, которую ваша система CI использует для запуска параллельных раннеров.
2. **Этап тестирования:** Каждый раннер CI получает **индекс шарда**, скачивает сборку и выполняет только те тесты, которые назначены этому шарду.

Тесты распределяются по файлам: все тесты в одном файле выполняются на одном шарде. Для тестов, которые Tuist еще не видел, используется оценка, поэтому первые планы проекта менее сбалансированы, чем последующие.

## Этап сборки {#build-phase}

Подготовьте шарды тестов с помощью задачи `tuist.test.build`:

```sh
MIX_ENV=test mix compile --warnings-as-errors
MIX_ENV=test mix tuist.test.build --shard-max 5
```

Компилируйте через алиас, установленный общей настройкой, перед вызовом задачи шардирования. При чистой выгрузке кода Mix может компилировать зависимости во время обнаружения `tuist.test.build`, до того как кэш зависимостей Tuist успеет их восстановить. Явная компиляция выполняется в той же тестовой среде, что и задача шардирования.

Эта задача:
1. Компилирует проект в тестовой среде
2. Создает план шардов на сервере Tuist, используя исторические данные о времени выполнения
3. Загружает сборку, чтобы шардам не приходилось компилировать ее снова
4. Выводит матрицу шардов для вашей системы CI

### Параметры сборки {#build-options}

| Параметр | Описание |
|--------|-------------|
| `--shard-max <N>` | Максимальное количество шардов (по умолчанию: 2) |
| `--shard-min <N>` | Минимальное количество шардов |
| `--shard-total <N>` | Точное количество шардов вместо диапазона |
| `--shard-max-duration <MS>` | Целевая максимальная длительность одного шарда в миллисекундах |
| `--shard-reference <REF>` | Имя, по которому шарды находят план |
| `--no-upload` | Спланировать шарды без загрузки сборки; каждый шард затем компилирует самостоятельно |

Все остальные аргументы передаются в `mix compile`.

Ссылка на шард автоматически определяется из переменных среды CI (`GITHUB_RUN_ID`, `CI_PIPELINE_ID`, `CIRCLE_WORKFLOW_ID`, `BUILDKITE_BUILD_ID`) или может быть задана явно через переменную среды `TUIST_SHARD_REFERENCE`. Вне этих провайдеров вы должны задать ее значение, общее для этапа сборки и всех шардов одного запуска пайплайна. В GitHub Actions ссылки также включают попытку запуска: при повторном запуске только неудавшихся задач передавайте ссылку исходной задачи сборки, а не создавайте новую в задачах шардов.

## Этап тестирования {#test-phase}

Когда установлена переменная `TUIST_SHARD_INDEX`, пакет получает назначение шарда с сервера, скачивает сборку и запускает только назначенные файлы тестов без компиляции. На чистом раннере инициализируйте SDK и загрузите его пути перед вызовом задачи:

```sh
MIX_ENV=test TUIST_SHARD_INDEX=0 mix do deps.compile tuist_ex --include-children + deps.loadpaths --no-compile --no-deps-check + tuist.test
```

Компиляция SDK в рабочих процессах Mix не загружает его в родительский процесс. Явный шаг `deps.loadpaths` предотвращает компиляцию оставшихся зависимостей при обнаружении задач до скачивания сборки. Эта форма одной команды сохраняет алиас подготовки тестов вашего проекта. Если его команды настройки вызывают компиляцию, используйте отдельную последовательность настройки ниже.

Любые переданные файлы или директории тестов дополнительно сужают шард: выполняются только файлы, которые находятся и в шарде, и в вашем выборе. Шард, в котором не осталось тестов, завершается успешно.

Результаты всех шардов поступают на панель управления как один запуск тестов, а в разделе **Шарды** показано, сколько времени занял каждый из них.

Если настройка должна выполняться перед тестами, сначала скачайте сборку без запуска приложения:

```sh
MIX_ENV=test TUIST_SHARD_INDEX=0 mix do deps.compile tuist_ex --include-children + deps.loadpaths --no-compile --no-deps-check + tuist.test --prepare-only
```

Запустите настройку в отдельном процессе с отключенной компиляцией. Например, проект Ecto может создать и мигрировать свои базы данных с помощью:

```sh
MIX_ENV=test mix run --no-start --no-compile --no-deps-check -e 'Mix.Tasks.Ecto.Create.run([]); Mix.Tasks.Ecto.Migrate.run([])'
```

Оставьте любую другую подготовку, специфичную для проекта, на этом этапе. Ваш алиас компиляции также должен учитывать `--no-compile` перед выполнением начальной настройки: Mix передает флаги только последней задаче в списке алиасов, поэтому более ранний безусловный `deps.compile` все равно выполняется. См. защищенный алиас в разделе <.localized_link href="/guides/features/cache/elixir-advanced#manual-compile-integration">ручная интеграция компиляции</.localized_link>.

Затем загрузите восстановленный SDK без компиляции перед выполнением шарда. Это также предотвращает компиляцию path-зависимости при обнаружении задач, если ее исходники новее скачанной сборки:

```sh
MIX_ENV=test TUIST_SHARD_INDEX=0 mix do deps.loadpaths --no-compile --no-deps-check + tuist.test --no-download
```

Обе команды требуют одну и ту же ссылку на шард. `--prepare-only` требует загруженную сборку, а `--no-download` завершается ошибкой, если отсутствует подготовленный артефакт приложения. `--no-download` явно пропускает алиас подготовки тестов вашего проекта, включая повторы, и выводит уведомление при пропуске шагов настройки. Обычные запуски сохраняют свои алиасы, даже если вы передаете `--no-compile --no-deps-check`. Разделение миграций базы данных в отдельный процесс также позволяет избежать предупреждений о переопределении модулей, когда регрессионные тесты миграций загружают эти модули самостоятельно.

При тестировании разных сред передавайте стабильную метку `--scheme`, например `--scheme clickhouse-current` или `--scheme clickhouse-floor`. Результаты с разными метками не рассматриваются как нестабильные повторные запуски одной и той же конфигурации.

### Что нужно шардам {#what-the-shards-need}

Загруженная сборка — это директория `_build/test`. Каждому раннеру шарда по-прежнему требуется:
- Та же самая копия репозитория, что и на этапе сборки
- Те же версии Elixir и Erlang/OTP
- Исходные коды зависимостей, полученные через `mix deps.get`

Шардирование из корня umbrella-проекта пока не поддерживается. Запускайте оба этапа внутри одного из его приложений.

## Непрерывная интеграция {#continuous-integration}

### GitHub Actions {#github-actions}

В GitHub Actions этап сборки записывает индексы шардов в вывод шага `matrix`. Используйте матричную стратегию для параллельного запуска шардов:

```yaml
name: Tests
on: [pull_request]

env:
  MIX_ENV: test
  TUIST_TOKEN: ${{ secrets.TUIST_TOKEN }}

jobs:
  build:
    name: Build test shards
    runs-on: ubuntu-latest
    outputs:
      matrix: ${{ steps.build.outputs.matrix }}
    steps:
      - uses: actions/checkout@v4
      - uses: erlef/setup-beam@v1
        with:
          elixir-version: '1.18'
          otp-version: '27'
      - run: mix deps.get
      - run: mix compile --warnings-as-errors
      - id: build
        run: mix tuist.test.build --shard-max 5

  test:
    name: "Shard #${{ matrix.shard }}"
    needs: build
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        shard: ${{ fromJson(needs.build.outputs.matrix).shard }}
    env:
      TUIST_SHARD_INDEX: ${{ matrix.shard }}
    steps:
      - uses: actions/checkout@v4
      - uses: erlef/setup-beam@v1
        with:
          elixir-version: '1.18'
          otp-version: '27'
      - run: mix deps.get
      - run: mix do deps.compile tuist_ex --include-children + deps.loadpaths --no-compile --no-deps-check + tuist.test --prepare-only
      # Ecto example: keep all project-specific test preparation here.
      # The project's compile alias must honor --no-compile (see above).
      - run: mix run --no-start --no-compile --no-deps-check -e 'Mix.Tasks.Ecto.Create.run([]); Mix.Tasks.Ecto.Migrate.run([])'
      - run: mix do deps.loadpaths --no-compile --no-deps-check + tuist.test --no-download
```

### Другие провайдеры {#other-providers}

За пределами GitHub Actions этап сборки записывает план в файл `.tuist-shard-matrix.json`:

```json
{
  "reference": "gitlab-1234",
  "shard_count": 2,
  "shards": [
    {
      "index": 0,
      "test_targets": ["MyApp.AccountsTest", "MyApp.CheckoutTest"],
      "estimated_duration_ms": 41000
    },
    {
      "index": 1,
      "test_targets": ["MyAppWeb.PageControllerTest"],
      "estimated_duration_ms": 39500
    }
  ]
}
```

Используйте `shard_count` для настройки параллельных задач и передавайте каждой задаче её `TUIST_SHARD_INDEX` от `0` до `shard_count - 1`. На провайдере, откуда Tuist не выводит ссылку автоматически, также задайте всем задачам одинаковый `TUIST_SHARD_REFERENCE`.
