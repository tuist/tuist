# Сегментирование тестов Rust {#rust-test-sharding}

Tuist распределяет цели тестирования Cargo между воркерами CI, используя исторические данные о длительности выполнения целей. Цели модульных тестов, интеграционных тестов и документационные тесты каждой библиотеки являются отдельными модулями. Тесты в рамках одной цели выполняются вместе.

> [!IMPORTANT] Requirements
> - Настройте <.localized_link href="/guides/features/test-insights/rust">Rust Test Insights</.localized_link> и выполните аутентификацию CLI в задаче планирования и на воркерах.
> - Выберите один пакет, используя `-p <package>` в рабочем пространстве. Сегментирование нескольких пакетов не поддерживается.
> - Используйте одинаковую ревизию, инструментарий Rust, выбор пакета, возможности и фильтры тестов в каждой задаче.

## Создание плана {#create-a-plan}

Добавьте количество сегментов к `--no-run`, чтобы скомпилировать и перечислить цели без выполнения тестов:

```sh
TUIST_SHARD_REFERENCE=my-ci-run tuist cargo test -p store --no-run --shard-max 4
```

Команда выводит JSON, содержащий `shard_plan_id` и массив `shards` с нулевой индексацией. В GitHub Actions она также записывает `shard-plan-id` и `shards` в `GITHUB_OUTPUT`. Если явная ссылка не указана, Tuist формирует её на основе поддерживаемой среды CI.

| Опция | Описание |
| --- | --- |
| `--shard-max N` | Максимальное количество сегментов |
| `--shard-min N` | Минимальное количество сегментов |
| `--shard-total N` | Точное количество, вплоть до доступных целей |
| `--shard-max-duration N` | Целевая максимальная длительность сегмента в миллисекундах |

Используйте только `--shard-total` или комбинируйте `--shard-min` и `--shard-max`. Без исторических данных о длительности планировщик использует оценки целей по умолчанию. Обычная команда `--no-run` без опций сегментирования остаётся командой только для сборки.

## Выполнение каждого сегмента {#execute-each-shard}

Установите ID плана и индекс сегмента на каждом воркере, затем используйте те же аргументы теста Cargo:

```sh
TUIST_SHARD_PLAN_ID=<plan-id> TUIST_SHARD_INDEX=0 tuist cargo test -p store
```

В качестве альтернативы установите `TUIST_SHARD_REFERENCE` равным ссылке задачи планирования вместо передачи ID плана. Tuist получает назначение и просит Cargo выполнить только соответствующие цели. Недействительные или несовместимые назначения приводят к ошибке команды, а не к запуску всех тестов. Пустые назначения не выполняют тесты. Результаты с воркеров связываются с планом в Test Insights, и <.localized_link href="/guides/features/test-insights/flaky-tests/rust#quarantine">карантин</.localized_link> применяется в пределах каждого сегмента.

## Ограничения {#limits}

Это сегментирование на уровне целей, а не распределение с однократной сборкой. Каждому воркеру требуется клон исходного кода, и он собирает свои собственные цели; <.localized_link href="/guides/features/cache/rust">кэш компиляции Cargo</.localized_link> может повторно использовать подходящие результаты компиляции. Tuist не загружает исполняемые файлы тестов и не требует другого запускающего механизма для тестов Rust.

Для сегментирования требуется выбрать один пакет. Сужение команды для нескольких пакетов может изменить объединённые возможности зависимостей Cargo, поэтому Tuist отклоняет такой запрос вместо запуска тестов с другим графом возможностей. Планируйте каждый пакет отдельно, пока не будет добавлена поддержка сегментирования нескольких пакетов.

Сегментирование требует стандартных harness-механизмов libtest и захвата вывода по умолчанию. Команды с тихим режимом, подробным выводом, альтернативным форматом, без захвата вывода и с пользовательскими harness-механизмами отклоняются. Если Cargo не может однозначно идентифицировать цель, выберите точный пакет рабочего пространства с помощью `-p <package>`. Пакеты зависимостей, селекторы с указанием версии, шаблоны имён пакетов/целей и ночная опция Cargo `-C` не поддерживаются для сегментирования. Сохраняйте идентичный выбор тестов при планировании и выполнении.
