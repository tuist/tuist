# Model Context Protocol

[Model Context Protocol (MCP)](https://modelcontextprotocol.io/docs/getting-started/intro) — это открытый стандарт, позволяющий агентам искусственного интеллекта взаимодействовать с внешними сервисами и источниками данных. Он обеспечивает совместимость таких приложений, как [Claude](https://claude.ai/), [Claude Code](https://docs.anthropic.com/en/docs/claude-code), [Codex](https://developers.openai.com/codex/), и редакторов, таких как [Zed](https://zed.dev), [Cursor](https://www.cursor.com) или [Visual Studio Code](https://code.visualstudio.com), с Tuist.

Tuist размещает серверную точку входа Model Context Protocol по адресу `https://tuist.dev/mcp`. Подключив к ней свой клиент, агенты смогут получать доступ к данным вашего проекта Tuist, включая аналитику тестов, анализ нестабильных тестов и многое другое. Большинство инструментов работают только в режиме чтения и ограничены данными проектов Tuist, прошедших аутентификацию. Инструменты настройки аккаунта могут перечислять аккаунты, создавать организации, создавать проекты и добавлять существующих пользователей в организации, если у аутентифицированного пользователя есть необходимые разрешения. Каждый инструмент предоставляет аннотации, указывающие, работает ли он только в режиме чтения, может ли он вызвать трудно обратимые изменения и может ли он изменять состояние публичного интернета. Инструменты настройки аккаунта требуют аутентификации пользователя. Они недоступны для токенов проектов или обычных токенов аккаунтов. Когда пользователь авторизует клиент в браузере или подтверждает регистрацию `auth.md`, Tuist связывает эти учетные данные с пользователем только на точке входа Model Context Protocol, чтобы инструменты настройки могли завершить запрошенный рабочий процесс.

Tuist реализует [протокол 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http). Запросы не сохраняют состояние: клиенты отправляют метаданные протокола с каждым запросом и могут вызывать инструменты напрямую без инициализации. `server/discover` возвращает идентификатор сервера, возможности, поддерживаемые версии и инструкции. Идентификаторы сеансов или независимые потоки событий отсутствуют. Клиенты, использующие поток инициализации 2025-06-18 или 2025-03-26, по-прежнему поддерживаются; они также работают без серверных сеансов.

## Model Context Protocol против навыков

Функциональность инструментов Model Context Protocol и <.localized_link href="/guides/features/agentic-coding/skills">навыков</.localized_link> может пересекаться. Учитывая текущее перекрытие между ними, выбирайте один подход для каждого рабочего процесса и используйте его последовательно, вместо того чтобы смешивать оба в одном потоке.

Для клиентов, поддерживающих установку плагинов, используйте <.localized_link href="/guides/features/agentic-coding/plugins">плагины Tuist</.localized_link>, чтобы установить их вместе.

## Конфигурация

Добавьте `https://tuist.dev/mcp` как удаленный сервер Model Context Protocol в вашем клиенте. Инструкции по инициализации сервера и публичная карточка сервера описывают OAuth 2.0 с динамической регистрацией клиента и стандартный поток авторизации в браузере встроенными средствами, не требуя от агентов загружать или следовать внешним документам аутентификации. Эти общесерверные инструкции делают рекомендации по рабочему процессу универсальными: аутентификация инструментов не аутентифицирует локальные инструменты командной строки или интеграции с системами сборки, и агенты должны проверять запрашиваемые изменения через соответствующие инструменты Tuist. Настройка и проверки аутентификации, специфичные для системы сборки, документированы в руководствах по интеграции и подсказках. Tuist по-прежнему предоставляет метаданные обнаружения [Open Authorization](https://oauth.net/2/) и текущий [протокол auth.md](https://workos.com/auth-md) по адресу `https://tuist.dev/auth.md` отдельно.

Если одна из ваших организаций требует единого входа (SSO), авторизация клиента в браузере требует сеанса, выполненного через эту организацию, и Tuist при необходимости сначала направляет вас к провайдеру. См. <.localized_link href="/guides/integrations/authentication/sso#choose-an-enrollment-policy">единый вход</.localized_link>.

Точка входа принимает не сохраняющий состояние жизненный цикл запросов Model Context Protocol `2026-07-28`, включая `server/discover`, наряду со старым жизненным циклом на основе сеансов. Существующие клиенты могут продолжать использовать свой текущий метод подключения.

Клиенты, поддерживающие события Model Context Protocol, могут подписываться на события проекта. См. раздел [События](#events) для получения информации о доступных событиях и требованиях к доставке.

Клиенты, которые уже поддерживают удаленную аутентификацию в браузере, могут продолжать аутентификацию в браузере. Клиенты и агенты, поддерживающие `auth.md`, могут регистрироваться анонимно, предоставлять доверенное утверждение идентичности провайдера или начинать запрос на подтверждение электронной почты с аутентификацией службы. Регистрация возвращает подписанное Tuist утверждение идентичности, которое агент обменивает на стандартной конечной точке токена на токен доступа сроком на один час. Tuist публикует свой открытый ключ подписи и поддерживает стандартное отзывание токенов и доставку событий безопасности от провайдера.

Неаутентифицированный агент должен прочитать заголовок `WWW-Authenticate`, возвращаемый точкой входа Model Context Protocol, получить метаданные защищенного ресурса, получить метаданные сервера авторизации и перейти по его URL-адресу `agent_auth.skill`. Tuist также возвращает тот же локальный URL-адрес `auth_md` в теле ответа об отказе в доступе, чтобы клиенты, управляемые языковыми моделями, могли обнаружить этот поток без reliance на нативную интеграцию клиента. Локальный для развертывания документ является источником истины для имен конечных точек, тел запросов, опроса заявок и обмена утверждениями.

Прежде чем агент начнет запрос на подтверждение электронной почты, он должен попросить пользователя подтвердить адрес электронной почты для его аккаунта Tuist. Он не должен выводить этот адрес из профиля провайдера, конфигурации Git, переменной окружения или метаданных сеанса.

Точка входа использует группу областей видимости `mcp`. Анонимные учетные данные до подтверждения заявки могут обнаруживать возможности и читать публичные руководства по интеграции, но они не рассматриваются как вошедшие в систему пользователи. После авторизации в браузере или подтверждения заявки учетные данные получают область видимости пользователя, и каждый инструмент применяет те же проверки авторизации, что и панель управления. Подробнее см. в <.localized_link href="/guides/server/authentication#scope-groups">документации по группам областей видимости</.localized_link>.

Инструменты разрешаются к проектам, которые аутентифицированный пользователь уже может читать. Инструменты сборки Xcode и Gradle принимают UUID сборки или URL-адрес панели управления. UUID должен идентифицировать ровно один проект; если он встречается в нескольких проектах, инструмент возвращает «не найдено» вместо выбора отчета другого проекта. Чтения панели управления и API в области проекта остаются доступными. Сообщаемые идентификаторы акторов являются непроверенными метками, а не учетными данными или дополнительными правами доступа.

Инструменты списка сборок и деталей предоставляют дополнительные метаданные `tuist_version`: CLI Tuist для Xcode и Cargo, плагин Tuist Gradle для Gradle и библиотеку `tuist_ex` для Mix. Xcode также предоставляет `tuist_generation_version` из связанного события генерации проекта, которое может отличаться от загружающего CLI. Отсутствующие значения равны null и не выводятся из данных сервера или другого отчета. Bazel использует свой существующий `bazel_version`; детали запуска Once предоставляют `once_version`. Эти поля описывают сообщаемые версии, а не проверенную идентификацию или версии протокола взаимодействия. Конечные точки REST API для сборок предоставляют те же метаданные. Существующие интеграции и навыки работы с нестабильными тестами не зависят от полей версий и не требуют изменений в рабочих процессах.

Операторы Tuist, исследующие аккаунт клиента, делают это через внутренние операционные инструменты Tuist, которые записывают каждый вызов; прямое подключение к этой конечной точке не дает доступа сверх членства самого пользователя.

Безголовый агент сможет прочитать возвращенный URL-адрес `auth_md` и следовать рабочему процессу регистрации Tuist, обмена утверждениями идентичности и опроса заявок. Если вы предпочитаете аутентификацию через браузер, установите `auth` в значение `"oauth"`. Для этого потока держите один процесс активным с помощью [remote procedure call mode](https://pi.dev/docs/latest/rpc) Pi, пока аутентификация не завершится:

```bash
pi --mode rpc
```

Не разделяйте ожидающую аутентификацию в браузере между отдельными вызовами `pi --print`, так как процесс, владеющий состоянием обратного вызова, уже завершился.

## Интеграции систем сборки используют два набора учетных данных

Учетные данные, используемые для инструментов Model Context Protocol, не аутентифицируют плагин Gradle или удаленные сервисы Bazel. Перед тем как агент изменит или проверит интеграцию Gradle или Bazel, он должен выполнить:

```bash
tuist auth whoami --url https://tuist.dev
```

Если эта команда не аутентифицирована, агент должен остановиться и попросить пользователя выполнить:

```bash
tuist auth login --url https://tuist.dev
```

Для локального или самостоятельно размещенного развертывания замените URL-адрес в обеих командах и в `tuist.toml`. Сохраняйте одинаковое написание имени хоста везде. Например, `localhost` и `127.0.0.1` используют отдельные сохраненные учетные данные.


## Возможности

### Инструменты

Следующие инструменты доступны через сервер Tuist Model Context Protocol:

Каждый инструмент предоставляет понятное описание вместе с явными схемами ввода и вывода. Успешные вызовы возвращают структурированный контент, соответствующий заявленной схеме вывода, а также тот же результат в виде текста для клиентов, которые еще не поддерживают структурированный контент.

Инструменты, принимающие идентификатор одной записи, такой как `build_run_id`, `test_run_id`, `test_case_id`, `bundle_id`, `run_id`, `generation_id` или `cache_run_id`, также принимают URL-адрес этой записи в панели управления Tuist. Вставьте URL-адрес прямо из браузера вместо того, чтобы извлекать из него идентификатор.

#### Поиск по документации и сообществу

Этот инструмент только для чтения выполняет поиск по документации Tuist, справочнику [application programming interface](https://en.wikipedia.org/wiki/API), релизам на GitHub, форуму сообщества и задачам на GitHub через тот же поисковый движок, который используется на сайте документации. Результаты поиска по релизам включают продукт, версию, дату публикации и статус предварительного выпуска. По умолчанию выполняется поиск по стабильным релизам, предварительные релизы можно включить с помощью `include_prereleases`. Инструмент доступен только на сервере, размещенном Tuist, по адресу `https://tuist.dev/mcp`.

| Инструмент | Описание | Обязательные параметры |
|------|-------------|---------------------|
| `search_tuist` | Поиск по публичной документации Tuist, справочнику application programming interface, релизам на GitHub, обсуждениям в сообществе и задачам на GitHub. При необходимости можно ограничить поиск одним `source` (`docs`, `api_reference`, `releases`, `forum`, `issues`). | `query` |

#### Обратная связь

Агенты могут сообщить команде Tuist, если инструмент или подсказка Tuist работали не так, как ожидалось, например, выдали непонятный результат, ошибку, отсутствующие данные или недостающую возможность. Агенту предлагается подготовить отчет и отправить его только после вашего согласия. Каждый отчет открывает диалог со службой поддержки Tuist, которая может ответить вам по электронной почте. Отчет включает ожидаемое агентом поведение, фактический результат, необязательное предложение, ваш идентификатор пользователя Tuist, имя пользователя и электронную почту, а также организации, к которым вы принадлежите. Агенты также могут указать аккаунт и проект, в которых возникла проблема, чтобы команда знала, с какой организацией связаться; принимаются только аккаунты, к которым вы имеете доступ. Отчеты могут отправлять только агенты, вошедшие в систему как пользователь Tuist, и каждый пользователь может создавать до 10 отчетов в час. Инструмент доступен только на сервере, размещенном Tuist, по адресу `https://tuist.dev/mcp`.

| Инструмент | Описание | Обязательные параметры |
|------|-------------|---------------------|
| `report_feedback` | Сообщить о проблеме с инструментом или подсказкой Tuist. При необходимости укажите `tool_name`, `account_handle` и `project_handle`, в которых возникла проблема, и добавьте `suggestion`. | `category`, `expected`, `actual` |

#### Ответы на основе исходного кода

Эти инструменты только для чтения позволяют агентам использовать точную публичную ревизию исходного кода Tuist, развернутую вместе с размещенным сервером, в качестве источника истины для ответов, зависящих от текущего поведения. Они доступны только по адресу `https://tuist.dev/mcp`.

Совместимые клиенты получают фактические описания ревизии исходного кода инструментов, ссылки и ограничения результатов во время инициализации вместе с информацией для встроенной аутентификации OAuth. Эти описания не предписывают стиль ответа или процесс проверки. Пользователи могут задать вопрос напрямую, не вызывая сначала подсказку `ask_tuist`; подсказка остается доступной для явного рабочего процесса с опорой на исходный код.

#### Сборки Xcode

Инструменты детализации сборок для Xcode, Gradle, Bazel, Mix и Cargo предоставляют данные в существующем формате `custom_metadata: {tags, values}`, включая наблюдения за инфраструктурой, если они доступны. Значения остаются строками, а неизвестные ключи сохраняются. Например, `tuist.cpu.available_processors` описывает логические процессоры, доступные во время выполнения, тогда как `tuist.gradle.max_workers` — это ограничение на количество рабочих процессов Gradle, а `tuist.jvm.max_heap_bytes` — ограничение кучи JVM, а не память хоста. Это ненадежные наблюдения клиента, а не проверенные идентификаторы раннеров. Отсутствующие наблюдения остаются отсутствующими; импортированные логи и старые клиенты могут не иметь метаданных инфраструктуры. В настоящее время обновление метаданных ожидает согласованного обновления клиента/протокола.

| Инструмент | Описание | Обязательные параметры |
|------|-------------|---------------------|

| `get_xcode_build` | Получить подробную информацию о конкретном запуске сборки Xcode, включая временный URL-адрес для скачивания архива с исходным файлом `.xcactivitylog`. | `build_run_id` |
| `list_xcode_build_targets` | Список целей сборки для конкретного запуска сборки Xcode. | `build_run_id` |
| `list_xcode_build_files` | Список скомпилированных файлов для конкретного запуска сборки Xcode. | `build_run_id` |
| `list_xcode_build_steps` | Список записанных шагов сборки с указанием времени и результатов, без текста логов. | `build_run_id` |

`list_xcode_build_steps` по умолчанию возвращает страницы по 20 шагов (максимум 100 через `page_size`), с параметрами `page` и `pagination_metadata` для навигации. Используйте `search` для поиска по названиям, проектам или целям, либо фильтруйте по точным значениям `project`, `target`, `category` (например, `swiftCompilation`) и `status` (`success` или `failure`). Сортируйте по `duration_ms`, чтобы сначала показать самые медленные (по умолчанию), или по `start_ms` для хронологического порядка. ID шагов используются для разрешения неоднозначностей и возвращаются в виде десятичных строк для сохранения полной 64-битной точности. ID привязаны к конкретной сборке и не должны сопоставляться между разными сборками.

Необязательные параметры `start_ms` и `end_ms` выбирают шаги, пересекающиеся с диапазоном времени в миллисекундах от начала сборки; конец диапазона исключается. Оба инструмента принимают UUID сборки или URL панели управления в качестве `build_run_id`. Передайте полученный ID шага `id` без изменений в качестве `step_id` для получения его лога. Логи хранят до 64 КиБ на шаг, при этом `log_truncated` указывает на усеченный вывод.

Шаги собираются по умолчанию при обработке сборок Xcode. Записанные данные шагов хранятся в течение 90 дней. Ответ списка включает поле `availability`: `available`, если записанные шаги существуют, даже если фильтры ничего не находят; `processing`, если сборка все еще обрабатывается и шагов пока нет; или `unavailable`, если шаги не были записаны или срок их хранения истек.

Те же операции доступны через HTTP API по адресам `GET /api/projects/{account_handle}/{project_handle}/xcode/builds/{build_id}/steps` и `GET /api/projects/{account_handle}/{project_handle}/xcode/builds/{build_id}/steps/{step_id}`, с теми же фильтрами и пагинацией. Для обоих требуется доступ на чтение к проекту сборки.

ID шагов Bazel, возвращаемые из сохраненных сводок, остаются читаемыми, если полный профиль поступает между получением списка и запросом шага. Индексированный профиль, данные шагов которого истекли, сообщает о недоступности. Списки шагов Gradle включают кэшированные и пропущенные операции с нулевой длительностью.

#### Задачи, действия, модули и файлы

Эти инструменты, работающие в контексте проекта, анализируют постоянные идентификаторы сборок across запусков. Начните с `list_build_entities`, затем передайте полученный стабильный `id` с тем же `kind` в `get_build_entity` или `list_build_entity_history`, вместе с `account_handle` и `project_handle`. Идентификатор сборки или вызова не требуется.

| Инструмент | Описание | Обязательные параметры |
| --- | --- | --- |
| `list_build_entities` | Список задач, модулей, действий или файлов одного типа, обнаруженных в сборках проекта. | `account_handle`, `project_handle`, `kind` |
| `get_build_entity` | Получение данных об одной сущности сборки с её нативным идентификатором и аналитикой за выбранный период. | `account_handle`, `project_handle`, `kind`, `id` |
| `list_build_entity_history` | Список записанных выполнений, компиляций или событий кэша для одной сущности сборки, от новых к старым. | `account_handle`, `project_handle`, `kind`, `id` |

| `kind` | Инструментарий | Списки истории |
| --- | --- | --- |
| `bazel_actions` | Действия Bazel | Выполнения действий, сообщенные через BEP |
| `gradle_tasks` | Задачи Gradle | Выполнения задач |
| `xcode_modules` | Модули Xcode | Компиляции и события кэша модулей |
| `once_actions` | Действия Once | Выполнения |
| `mix_files` | Скомпилированные файлы Mix | Компиляции |
| `mix_modules` | Скомпилированные модули Mix | Компиляции |
| `cargo_crates` | Крейты Cargo | Записанные вызовы rustc |

Эти инструменты внедряются постепенно и возвращают данные только для проектов, где они включены; для остальных проектов возвращается ошибка вместо пустого результата. Тип доступен только для проектов, использующих соответствующий инструментарий сборки. Инструменты принимают ограниченные фильтры `start_at`/`end_at`, `environment` (`any`, `ci` или `local`) и точное значение `branch`. `list_build_entities` принимает `q`; `list_build_entity_history` поддерживает непрозрачные курсоры `after`/`before`. Неизвестные данные о времени или наблюдения кэша остаются недоступными, а не превращаются в нули или промахи. История ссылается на записанного родителя и нативное выполнение для детализации с использованием существующих инструментов запусков.

Метрики `get_build_entity` включают `duration_samples` — количество наблюдений с записанным временем: подлинные нулевые длительности учитываются, отсутствующие данные о времени — нет. Это количество может быть меньше общего числа наблюдений; недоступная статистика длительности остается null.

Длительности модулей Xcode берутся из измеренных компиляций целей в логах сборки. Разрешения кэша модулей и цели без работы по компиляции не вносят вклад в выборку длительностей. Наблюдения компиляции ссылается на сборку Xcode; события кэша — на команду генерации или кэширования.

Действия Bazel идентифицируются по метке цели, мнемонике и настроенному основному выходному файлу, что позволяет разделять действия и конфигурации без опоры на зависящие от входных данных дайджесты кэша. История записывает выполнения, сообщенные через BEP, а не поиски в кэше или этапы профилирования трассировки. Полное покрытие выполнения требует `--build_event_publish_all_actions`; доставка артефактов выполняется по возможности, поэтому отсутствие наблюдений не является доказательством того, что работа не выполнялась. Старые payloads Kura без стабильного идентификатора или начала выполнения по-прежнему принимаются, но не индексируются. Отсутствие измерений времени окончания остается недоступным, а подлинные нулевые длительности учитываются.

Длительности модулей Mix измеряют компиляцию содержащего файла, а не независимо измеренную работу модуля. Действия Once используют объявленные слоты target/capability/index, когда клиент сообщал сопоставления целей; одни лишь диагностические метки не являются стабильными идентификаторами. Существующие клиенты и инструменты уровня запуска по-прежнему поддерживаются без изменений.

Крейты Cargo группируются по точно записанному корню крейта, имени и типу. Изменения пути checkout могут разделять истории, а профили сборки, возможности и тройки целей не различаются. История измеряет вызовы rustc, а не работу по отдельным файлам или попадания в кэш; отсутствующие задания не свидетельствуют об удалениях или полной инвентаризации рабочего пространства.

Чтение аналитики имеет ограничения по памяти и времени выполнения. Если запрос превышает эти лимиты, инструмент возвращает ошибку вместо создания пустого результата.

Новые наблюдения индексируются после развертывания; эта функция не заполняет ретроспективно существующую телеметрию запусков. Метаданные идентификаторов хранятся дольше отдельных наблюдений в соответствии с <.localized_link href="/guides/server/data-retention">политикой хранения данных</.localized_link>.

### События

Клиенты, использующие жизненный цикл Model Context Protocol без сохранения состояния `2026-07-28`, могут вызывать `events/list` для обнаружения событий и их схем полезной нагрузки:

| Событие | Когда отправляется | Фильтр подписки |
|-------|-----------------|---------------------|
| `test_case.marked_flaky` | Тест-кейс меняется с нестабильного на стабильный или наоборот (становится нестабильным). | `account_handle`, `project_handle` |
| `build.failed` | Локальная сборка или сборка в системе непрерывной интеграции Xcode, Gradle или Bazel завершается с ошибкой. | `account_handle`, `project_handle` |
| `test_run.failed` | Локальный запуск тестов или запуск тестов в системе непрерывной интеграции завершается с ошибкой, включая объединенный шардированный запуск или прерванный запуск. | `account_handle`, `project_handle` |
| `ci_job.failed` | Задача раннера Tuist завершается с ошибкой. | `account_handle` |

Для подписки клиент вызывает `events/subscribe` с именем события, идентификаторами, перечисленными выше в `arguments`, и доставкой `webhook`, содержащей URL обратного вызова `https://` и секрет подписи `whsec_`. События проекта требуют членства в аккаунте и права на чтение соответствующих данных тестов или сборок; события задач раннера требуют членства в аккаунте и права на чтение данных раннера. Заявленные токены доступа [`auth.md`](https://workos.com/auth-md), заявленные токены аккаунта и гранты авторизации браузера могут создавать подписки; доставка останавливается, когда связанные учетные данные становятся неактивными. Каждый пользователь может иметь до 25 активных подписок. Tuist отправляет проверочный запрос на обратный вызов перед сохранением подписки. Обратный вызов должен вернуть объект, содержащий то же значение `challenge`. Подписка действует семь дней по умолчанию, может быть обновлена путем повторной подписки и прекращает доставку при удалении доступа или учетных данных пользователя. Необязательный параметр `ttlMs` ограничен диапазоном от одного часа до 30 дней. Tuist повторяет попытки вызова тайм-аута и отменяет подписку после как минимум трех последовательных тайм-аутов в течение пяти минут; подпишитесь снова после восстановления обратного вызова.

При возникновении события Tuist отправляет его идентификатор ресурса и URL панели управления на обратный вызов. Ошибки сборок и запусков тестов также включают `is_ci` и `git_branch`, поэтому клиенты могут игнорировать локальные ошибки или фильтровать по ветке. События сборки включают `build_system`; события задач раннера включают как `workflow_job_id`, так и `workflow_run_id`. Запрос включает идентификатор подписки и заголовки подписи [Standard Webhooks](https://www.standardwebhooks.com/), чтобы клиент мог проверить источник. Tuist повторяет неудачные доставки, поэтому клиентам следует использовать стабильный `eventId` для отброса дубликатов. Полезная нагрузка не содержит имен тестов, логов и сообщений об ошибках; клиент может получить эти детали через инструменты выше и решить, уведомлять ли команду или начинать отладку. Клиенты могут остановить доставку с помощью `events/unsubscribe`.

### Подсказки

| Подсказка | Описание |
|--------|-------------|
| `fix_flaky_test` | Направляет вас через процесс исправления нестабильного теста, анализируя шаблоны ошибок, выявляя первопричину и применяя целевое исправление. |
| `compare_builds` | Направляет вас через сравнение сборок для выявления регрессий производительности, изменений кэша и проблем сборки. Использует нативные инструменты для проектов Xcode, Gradle, Bazel и Cargo. Сравнения Cargo сохраняют частичное покрытие компилятора и различают оцененную работу компилятора от сэкономленного времени. |
| `compare_test_runs` | Направляет вас через сравнение двух запусков тестов для выявления регрессий, новых ошибок и нестабильных тестов. |
| `compare_bundles` | Направляет вас через сравнение двух пакетов для выявления изменений размера во всем дереве артефактов. |
| `compare_test_case` | Направляет вас через сравнение поведения тест-кейса в двух ветках или временных периодах. |
| `compare_generations` | Направляет вас через сравнение двух запусков генераций для выявления регрессий производительности и изменений кэша модулей. |
| `compare_cache_runs` | Направляет вас через сравнение двух запусков кэша для выявления изменений эффективности кэша и регрессий на уровне целей. |
| `integrate_gradle_project` | Направляет вас через интеграцию Tuist в существующий проект Gradle. Включает отдельную аутентификацию инструмента и Gradle, обнаружение аккаунта, создание проекта, политику удаленного кэша, аналитику сборок и проверку чтения. |
| `integrate_bazel_project` | Направляет вас через создание или выбор проекта Bazel, аутентификацию командной строки, настройку удаленного кэша и аналитики сборок, а также проверку интеграции через данные сборок Tuist. |
| `integrate_xcode_project` | Направляет вас через интеграцию Tuist в существующий проект Xcode. Поддерживает кэш Xcode, аналитику сборок, аналитику тестов и шардирование тестов. |
| `ask_tuist` | Отвечает на вопрос о Tuist, используя общедоступные материалы для контекста и сфокусированные доказательства реализации и тестирования как источник истины для текущего поведения. Требуется `question` и цитируются доказательства, привязанные к ревизии. |

Подсказки с данными проекта принимают `account_handle` и `project_handle` для ограничения исследования конкретным проектом. Подсказки сравнения также принимают аргументы `base` и `head` для указания двух сравниваемых элементов (по ID, URL панели управления или имени ветки). `ask_tuist` принимает `question` вместо параметров проекта. `integrate_gradle_project` также принимает `features`, список интеграций Gradle через запятую: `remote_cache`, `build_insights`, `test_insights`, `flaky_tests` и `test_sharding`. `integrate_bazel_project` принимает необязательный `server_url` для самостоятельных или локальных установок. `integrate_xcode_project` принимает `features` с `xcode_cache`, `build_insights`, `test_insights` и `test_sharding`.

#### Возможности подсказки интеграции Gradle

Подсказка `integrate_gradle_project` и инструмент `get_gradle_integration_guide` документируют полный рабочий процесс настройки. Инструмент также упоминается в инструкциях инициализации сервера, что делает его обнаруживаемым агентами, которые не перечисляют подсказки.

| Возможность | Что настраивает агент |
|---------|---------------------------|
| `remote_cache` | Включает кэш сборок Gradle, настраивает политику загрузки удаленного кэша Tuist и рекомендует загружать только с раннеров непрерывной интеграции с локальным доступом только для чтения. |
| `build_insights` | Применяет плагин Tuist Gradle и настраивает поведение загрузки аналитики сборок при необходимости. |
| `test_insights` | Применяет плагин Tuist Gradle, чтобы результаты задач Gradle `Test` загружались автоматически. |
| `flaky_tests` | Руководит настройкой обнаружения нестабильных тестов, опциональным использованием плагина Gradle Test Retry и конфигурацией карантина тестов. |
| `test_sharding` | Добавляет рабочий процесс непрерывной интеграции для `tuistPrepareTestShards`, генерации матрицы шардов и выполнения тестов на основе `TUIST_SHARD_INDEX`. |

Если `features` не указан, подсказка просит агента уточнить, какие интеграции нужны пользователю, или вывести минимальный полезный набор из запроса перед редактированием проекта Gradle.

#### Возможности подсказки интеграции Xcode

Подсказка `integrate_xcode_project` документирует все интеграции с Xcode, которые поддерживает Tuist:

| Возможность | Что настраивает агент |
|---------|---------------------------|
| `xcode_cache` | Настраивает `tuist setup cache`, параметры кэша сгенерированного проекта, ручные настройки сборки кэша Xcode и политику загрузки, ограниченную раннерами непрерывной интеграции. |
| `build_insights` | Настраивает `tuist inspect build`, `tuist xcodebuild`, `-resultBundlePath` и опциональные метрики машины через `tuist setup insights`. |
| `test_insights` | Настраивает `tuist inspect test`, пост-действия тестирования схемы и генерацию bundle результатов для запусков тестов в непрерывной интеграции. |
| `test_sharding` | Добавляет планирование шардов для Xcode или сгенерированного проекта и рабочий процесс выполнения шардов с `TUIST_SHARD_INDEX`. |

Если `features` не указан, подсказка просит агента уточнить, какие интеграции нужны пользователю, или вывести минимальный полезный набор из запроса перед редактированием проекта Xcode.
