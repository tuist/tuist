# Протокол Model Context Protocol

[Model Context Protocol (MCP)](https://modelcontextprotocol.io/docs/getting-started/intro) — это открытый стандарт, позволяющий агентам искусственного интеллекта взаимодействовать с внешними сервисами и источниками данных. Он обеспечивает совместимость таких приложений, как [Claude](https://claude.ai/), [Claude Code](https://docs.anthropic.com/en/docs/claude-code), [Codex](https://developers.openai.com/codex/), и редакторов, таких как [Zed](https://zed.dev), [Cursor](https://www.cursor.com) или [Visual Studio Code](https://code.visualstudio.com), с Tuist.

Tuist размещает серверную точку входа Model Context Protocol по адресу `https://tuist.dev/mcp`. Подключив к ней свой клиент, агенты смогут получать доступ к данным вашего проекта в Tuist, включая аналитику тестов, анализ нестабильных тестов и многое другое. Большинство инструментов работают только на чтение и ограничены данными аутентифицированного проекта Tuist. Инструменты настройки аккаунта могут перечислять аккаунты, создавать организации, создавать проекты и добавлять существующих пользователей в организации, если у аутентифицированного пользователя есть необходимые разрешения. Каждый инструмент предоставляет аннотации, указывающие, работает ли он только на чтение, может ли он вызвать изменения, которые трудно отменить, и может ли он изменить состояние в публичном интернете. Инструменты настройки аккаунта требуют аутентификации пользователя. Они недоступны для токенов проектов или обычных токенов аккаунтов. Когда пользователь авторизует клиент в браузере или подтверждает регистрацию через `auth.md`, Tuist связывает эти учетные данные с пользователем только в точке входа Model Context Protocol, чтобы инструменты настройки могли завершить запрошенный рабочий процесс.

Tuist реализует [протокол версии 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http). Запросы являются stateless: клиенты отправляют метаданные протокола с каждым запросом и могут вызывать инструменты напрямую без инициализации. `server/discover` возвращает идентификатор сервера, его возможности, поддерживаемые версии и инструкции. Идентификаторы сессий или независимые потоки событий отсутствуют. Клиенты, использующие поток инициализации 2025-06-18 или 2025-03-26, по-прежнему поддерживаются; они также работают без серверных сессий.

## Model Context Protocol против навыков (skills)

Инструменты Model Context Protocol и <.localized_link href="/guides/features/agentic-coding/skills">навыки</.localized_link> могут пересекаться по функциональности. Учитывая текущее перекрытие между ними, выбирайте один подход для каждого рабочего процесса и используйте его последовательно, вместо того чтобы смешивать оба подхода в одном потоке.

Для клиентов, поддерживающих установку плагинов, используйте <.localized_link href="/guides/features/agentic-coding/plugins">плагины Tuist</.localized_link>, чтобы установить их вместе.

## Конфигурация

Добавьте `https://tuist.dev/mcp` в качестве удаленного сервера Model Context Protocol в вашем клиенте. Инструкции по инициализации сервера и публичная карточка сервера описывают OAuth 2.0 с динамической регистрацией клиента и стандартный поток авторизации через браузер непосредственно в тексте, не требуя от агентов загружать или следовать внешним документам аутентификации. Эти общие для всего сервера инструкции сохраняют рекомендации по рабочему процессу универсальными: аутентификация инструментов не аутентифицирует локальные инструменты командной строки или интеграции с системами сборки, и агенты должны проверять запрашиваемые изменения через соответствующие инструменты Tuist. Настройка и проверки аутентификации, специфичные для системы сборки, документированы в руководствах по интеграции и подсказках. Tuist по-прежнему предоставляет метаданные обнаружения [Open Authorization](https://oauth.net/2/) и текущий [протокол auth.md](https://workos.com/auth-md) отдельно по адресу `https://tuist.dev/auth.md`.

Точка входа принимает stateless жизненный цикл запросов Model Context Protocol версии `2026-07-28`, включая `server/discover`, наряду со старым жизненным циклом на основе сессий. Существующие клиенты могут продолжать использовать свой текущий метод подключения.

Клиенты, поддерживающие события Model Context Protocol, могут подписываться на события проекта. См. раздел [События](#events) для получения информации о доступных событиях и требованиях к доставке.

Клиенты, которые уже поддерживают удаленную аутентификацию через браузер, могут продолжать аутентификацию в браузере. Клиенты и агенты, поддерживающие `auth.md`, могут регистрироваться анонимно, представлять доверенное утверждение идентичности провайдера или начинать запрос на подтверждение электронной почты с аутентификацией сервиса. Регистрация возвращает подписанное Tuist утверждение идентичности, которое агент обменивает на стандартной конечной точке токенов на токен доступа сроком на один час. Tuist публикует свой открытый ключ подписи и поддерживает стандартное отзывание токенов и доставку событий безопасности от провайдера.

Неаутентифицированный агент должен прочитать заголовок `WWW-Authenticate`, возвращаемый точкой входа Model Context Protocol, получить метаданные защищенного ресурса, получить метаданные сервера авторизации и перейти по URL `agent_auth.skill`. Tuist также возвращает тот же локальный URL `auth_md` в теле ответа об отказе в доступе, чтобы клиенты, управляемые языковыми моделями, могли обнаружить этот поток без reliance на нативную интеграцию клиента. Локальный для развертывания документ является источником истины для имен конечных точек, тел запросов, опроса подтверждения и обмена утверждениями.

Прежде чем агент начнет запрос на подтверждение электронной почты, он должен попросить пользователя подтвердить адрес электронной почты для его аккаунта Tuist. Он не должен выводить этот адрес из профиля провайдера, конфигурации Git, переменной окружения или метаданных сессии.

Точка входа использует группу областей видимости `mcp`. Анонимные учетные данные до подтверждения могут обнаруживать возможности и читать публичные руководства по интеграции, но они не рассматриваются как учетные данные вошедшего в систему пользователя. После авторизации в браузере или подтверждения, учетные данные получают область видимости пользователя, и каждый инструмент применяет те же проверки авторизации, что и панель управления. Подробнее см. в <.localized_link href="/guides/server/authentication#scope-groups">документации по группам областей видимости</.localized_link>.

Инструменты работают с проектами, к которым у аутентифицированного пользователя уже есть доступ. Инструменты сборки Xcode и Gradle принимают UUID сборки или URL-адрес дашборда. UUID должен однозначно идентифицировать один проект; если он встречается в нескольких проектах, инструмент возвращает ошибку «не найдено», вместо того чтобы выбирать отчёт из другого проекта. Чтение данных через дашборд и API в рамках проекта остаётся доступным. Идентификаторы акторов — это непроверенные метки, а не учётные данные или дополнительные права доступа.

Инструменты списка сборок и деталей предоставляют дополнительные метаданные `tuist_version`: версию CLI Tuist для Xcode и Cargo, плагин Tuist Gradle для Gradle и библиотеку `tuist_ex` для Mix. Xcode также предоставляет `tuist_generation_version` из связанного события генерации проекта, которое может отличаться от версии загружающего CLI. Отсутствующие значения равны null, они не выводятся из данных сервера или другого отчёта. Bazel использует существующий `bazel_version`; детали запуска Once предоставляют `once_version`. Эти поля описывают сообщаемые версии, а не проверенную идентичность или версии сетевого контракта. REST-эндпоинты сборок предоставляют те же метаданные. Существующие навыки интеграции и работы с нестабильными тестами не зависят от полей версий и не требуют изменений в рабочем процессе.

Операторы Tuist, исследующие аккаунт клиента, делают это через внутренние инструменты операций Tuist, которые записывают каждый вызов; прямое подключение к этой точке входа не даёт доступа beyond членства самого пользователя.

<summary>Claude Code</summary>

Выполните:

```bash
claude mcp add --transport http tuist https://tuist.dev/mcp
```

Если безголовый клиент Claude Code не передаёт модели информацию об ошибке подключения к нативному серверу, потребуйте от агента проверить неаутентифицированный ответ [протокола передачи гипертекста](https://developer.mozilla.org/en-US/docs/Web/HTTP) настроенной точки входа перед поиском в размещённой документации или редактированием проекта. Ответ направляет модель к локальному документу `auth.md`, даже если аутентификация в браузере недоступна.

</details>


<details>
<summary>Codex</summary>

Выполните:

```bash
codex mcp add tuist --url https://tuist.dev/mcp

```

Завершите вход через браузер перед началом нового запуска `codex exec`. Codex считывает инструкции сервера Tuist во время инициализации, поэтому запросы на оптимизацию Gradle автоматически получают рабочий процесс аутентификации и проверки.

</details>

<details>
<summary>Pi</summary>

Pi не включает клиент Model Context Protocol. Вы можете установить стороннее расширение [`pi-mcp-adapter`](https://pi.dev/packages/pi-mcp-adapter) после изучения его исходного кода и последствий для безопасности:

```bash
pi install npm:pi-mcp-adapter
```

Добавьте файл `.mcp.json` на уровне проекта:

```json
{
  "mcpServers": {
    "tuist": {
      "url": "https://tuist.dev/mcp",
      "auth": false
    }
  }
}
```

Установка `auth` в значение `false` предотвращает скрытие неавторизованного ответа Tuist обработчиком аутентификации браузера адаптера. После этого безголовый агент может прочитать возвращённый URL `auth_md` и следовать процессу регистрации Tuist, обмена утверждением идентичности и опроса подтверждения. Настройте полученный токен доступа как bearer-токен или позвольте агенту выполнять аутентифицированные вызовы Model Context Protocol напрямую.

Если вы предпочитаете аутентификацию через браузер, установите `auth` в значение `"oauth"`. Для этого потока держите один процесс активным с использованием [режима удалённого вызова процедур](https://pi.dev/docs/latest/rpc) Pi, пока аутентификация не завершится:

```bash
pi --mode rpc
```

Не разделяйте ожидающую аутентификацию в браузере между отдельными вызовами `pi --print`, так как процесс, владеющий состоянием обратного вызова, уже завершился.

</details>

Если ваш агент поддерживает `auth.md`, он может начать работу анонимно, не открывая браузер. Доверенная идентичность провайдера также может завершить процесс без браузера, если идентичность провайдера уже связана. Для электронной почты с аутентификацией службы, анонимного подтверждения или первой связи с провайдером агент показывает вам ссылку на проверку Tuist и шестизначный код. Откройте ссылку, войдите в систему и введите код агента на странице Tuist. Никогда не отправляйте код обратно агенту. Метаданные сервера авторизации Tuist указывают непосредственно на собственный `/auth.md` развёртывания, который содержит точные форматы запросов и опроса.

## Интеграции систем сборки используют два набора учётных данных

Учётные данные, используемые для инструментов Model Context Protocol, не аутентифицируют плагин Gradle или удалённые сервисы Bazel. Перед тем как агент изменит или проверит интеграцию Gradle или Bazel, он должен выполнить:

```bash
tuist auth whoami --url https://tuist.dev
```

Если эта команда не аутентифицирована, агент должен остановиться и попросить пользователя выполнить:

```bash
tuist auth login --url https://tuist.dev
```

Для локального или самостоятельно размещённого развёртывания замените URL в обеих командах и в `tuist.toml`. Сохраняйте одинаковое написание хоста везде. Например, `localhost` и `127.0.0.1` используют отдельные сохранённые учётные данные.


## Возможности

### Инструменты

Следующие инструменты доступны через сервер Tuist Model Context Protocol:

Каждый инструмент публикует понятное человеку описание вместе с явными схемами ввода и вывода. Успешные вызовы возвращают структурированный контент, соответствующий заявленной схеме вывода, а также тот же результат, сериализованный в виде текста для клиентов, которые ещё не потребляют структурированный контент.

Инструменты, принимающие идентификатор одной записи, такие как `build_run_id`, `test_run_id`, `test_case_id`, `bundle_id`, `run_id`, `generation_id` или `cache_run_id`, также принимают URL-адрес этой записи в панели управления Tuist. Вставьте URL прямо из браузера вместо того, чтобы извлекать из него идентификатор.

#### Поиск по документации и сообществу

Этот инструмент только для чтения выполняет поиск по документации Tuist, справочнику [application programming interface](https://en.wikipedia.org/wiki/API), релизам на GitHub, форуму сообщества и задачам на GitHub через тот же поисковый движок, который работает на сайте документации. Результаты поиска по релизам включают продукт, версию, дату публикации и статус предварительного релиза. По умолчанию выполняется поиск по стабильным релизам, предварительные релизы можно включить с помощью `include_prereleases`. Инструмент доступен только на сервере, размещённом Tuist, по адресу `https://tuist.dev/mcp`.

| Инструмент | Описание | Обязательные параметры |
|------|-------------|---------------------|
| `search_tuist` | Поиск по публичной документации Tuist, справочнику application programming interface, релизам на GitHub, обсуждениям в сообществе и задачам на GitHub. При необходимости ограничьте поиск одним `source` (`docs`, `api_reference`, `releases`, `forum`, `issues`). | `query` |

#### Ответы на основе исходного кода

Эти инструменты только для чтения позволяют агентам использовать точную общедоступную ревизию исходного кода Tuist, развёрнутую вместе с размещённым сервером, в качестве источника истины для ответов, зависящих от текущего поведения. Они доступны только по адресу `https://tuist.dev/mcp`.

Совместимые клиенты получают фактические описания ревизии исходного кода инструментов, ссылки и ограничения результатов во время инициализации вместе со встроенной информацией об аутентификации OAuth. Эти описания не предписывают стиль ответа или рабочий процесс проверки. Пользователи могут задать вопрос напрямую, не вызывая сначала подсказку `ask_tuist`; подсказка остаётся доступной для явного рабочего процесса на основе исходного кода.

Каждая операция имеет фиксированные ограничения на параллелизм, длительность, обход, количество прочитанных байтов и размер ответа. Результаты поиска и списков включают поля `truncated` и `truncation_reason`. Когда результат усечён, сузьте путь, шаблон файла или поисковый запрос вместо того, чтобы считать результат исчерпывающим.

| Инструмент | Описание | Обязательные параметры |
|------|-------------|---------------------|
| `search_tuist_code` | Отвечайте на вопросы о текущем поведении, значениях по умолчанию, конфигурации, флагах функций, обработке ошибок или недокументированных деталях, выполняя поиск по исходным файлам. Результаты включают окружающие строки, ссылки на исходный код, привязанные к ревизии, и статистику сканирования. | `pattern` |
| `list_tuist_files` | Найдите подсистему исходного кода или близлежащие тесты, когда соответствующий путь неизвестен. Списки имеют ограниченную глубину и количество результатов. | Нет |
| `read_tuist_file` | Изучите определённый диапазон строк в файле реализации, месте вызова или тесте после нахождения соответствующего пути. Усечённые ответы предоставляют `next_start_line` для продолжения. | `path` |

#### Сборки Xcode

Инструменты детализации сборок для Xcode, Gradle, Bazel, Mix и Cargo предоставляют данные в существующем формате `custom_metadata: {tags, values}`, включая наблюдения за инфраструктурой, если они были переданы. Значения остаются строками, а неизвестные ключи сохраняются. Например, `tuist.cpu.available_processors` описывает доступные во время выполнения логические процессоры, тогда как `tuist.gradle.max_workers` — это ограничение на количество рабочих процессов Gradle, а `tuist.jvm.max_heap_bytes` — ограничение кучи JVM, а не память хоста. Это ненадёжные наблюдения клиента, а не проверенные идентификаторы раннеров. Отсутствующие наблюдения остаются отсутствующими; импортированные логи и старые клиенты могут не содержать метаданных инфраструктуры. Обновление метаданных Once ожидает согласованного обновления клиента/протокола.

| Инструмент | Описание | Обязательные параметры |
|------|-------------|---------------------|
| `list_xcode_builds` | Перечислите запуски сборок Xcode для проекта. | `account_handle`, `project_handle` |
| `get_xcode_build` | Получите подробную информацию о конкретном запуске сборки Xcode, включая временный URL-адрес для скачивания архива с исходным файлом `.xcactivitylog`. | `build_run_id` |
| `list_xcode_build_targets` | Перечислите цели сборки для конкретного запуска сборки Xcode. | `build_run_id` |
| `list_xcode_build_files` | Перечислите скомпилированные файлы для конкретного запуска сборки Xcode. | `build_run_id` |
| `list_xcode_build_steps` | Перечислите записанные шаги сборки с указанием времени и результатов, без текста логов. | `build_run_id` |

| `list_xcode_build_cas_outputs` | Перечислите выходные данные [хранилища с адресацией по содержимому](https://en.wikipedia.org/wiki/Content-addressable_storage) для конкретного запуска сборки Xcode. | `build_run_id` |

`list_xcode_build_steps` по умолчанию возвращает страницы по 20 шагов (максимум 100 через `page_size`), с параметрами `page` и `pagination_metadata` для навигации. Используйте `search` для поиска по названиям, проектам или целям, либо фильтруйте по точному совпадению `project`, `target`, `category` (например, `swiftCompilation`) и `status` (`success` или `failure`). Сортируйте по `duration_ms`, чтобы сначала показывать самые медленные (по умолчанию), или по `start_ms` для хронологического порядка. Идентификаторы шагов используются для разрешения ничьих и возвращаются в виде десятичных строк для сохранения полной 64-битной точности. Идентификаторы привязаны к сборке и не должны сопоставляться между разными сборками.

Необязательные параметры `start_ms` и `end_ms` выбирают шаги, пересекающиеся с диапазоном времени в миллисекундах от начала сборки; конец диапазона не включается. Оба инструмента принимают UUID сборки или URL панели управления в качестве `build_run_id`. Передайте полученный идентификатор шага `id` без изменений в качестве `step_id` для получения его лога. Логи хранят до 64 КиБ на шаг, при этом `log_truncated` указывает на усечённый вывод.

Шаги собираются по умолчанию при обработке сборок Xcode. Записанные данные шагов хранятся 90 дней. Ответ списка включает поле `availability`: `available`, если записанные шаги существуют, даже если фильтры ничего не находят; `processing`, если сборка ещё обрабатывается и шагов пока нет; или `unavailable`, если шаги не были записаны или срок их хранения истёк.

Те же операции доступны через HTTP API по адресам `GET /api/projects/{account_handle}/{project_handle}/xcode/builds/{build_id}/steps` и `GET /api/projects/{account_handle}/{project_handle}/xcode/builds/{build_id}/steps/{step_id}`, с теми же фильтрами и пагинацией. Для обоих требуется доступ на чтение к проекту сборки.

Списки шагов Gradle и Bazel по умолчанию возвращают 20 результатов (максимум 100), поддерживают `search`, точное совпадение по `project`, `target`, `category` и `status`, фильтры по пересекающимся интервалам `start_ms` / `end_ms` (конец не включается) и сортировку по `duration_ms` или `start_ms`. Старые отчёты Gradle используют `first_recorded_timestamp`, так как время начала сборки не было загружено. Профили Bazel предоставляют все записанные интервалы с покрытием `trace_profile` и `profile_start` в качестве начала отсчёта времени. Для старых сборок используются сохранённые сводки BEP. Исходные записи истекают через 90 дней. Детали Bazel включают очищенные логи действий, если они опубликованы; поле `log` деталей Gradle равно null. Подсказка `compare_builds` использует это покрытие, чтобы отличать полные трассировки Bazel от сохранённых сводок, и направляет агентов к деталям шагов для получения результатов действий и логов перед проверкой общего вывода вызова.

Идентификаторы шагов Bazel, возвращаемые из сохранённых сводок, остаются читаемыми, если полный профиль поступает между моментом составления списка и запросом шага. Индексированный профиль, данные шагов которого истекли, сообщает о недоступности. Списки шагов Gradle включают кэшированные и пропущенные операции с нулевой длительностью.

#### Задачи, действия, модули и файлы

Эти инструменты, работающие в контексте проекта, анализируют постоянные идентификаторы сборок across запусков. Начните с `list_build_entities`, затем передайте полученный стабильный `id` с тем же `kind` в `get_build_entity` или `list_build_entity_history` вместе с `account_handle` и `project_handle`. Идентификатор сборки или вызова не требуется.

| Инструмент | Описание | Обязательные параметры |
| --- | --- | --- |
| `list_build_entities` | Перечислите задачи, модули, действия или файлы одного типа, обнаруженные в сборках проекта. | `account_handle`, `project_handle`, `kind` |
| `get_build_entity` | Получите одну сущность сборки с её нативным идентификатором и аналитикой за выбранный период. | `account_handle`, `project_handle`, `kind`, `id` |
| `list_build_entity_history` | Перечислите записанные выполнения, компиляции или события кэша одной сущности сборки, начиная с самых новых. | `account_handle`, `project_handle`, `kind`, `id` |

| `kind` | Инструментарий | Списки истории |
| --- | --- | --- |
| `bazel_actions` | Действия Bazel | Выполнения действий, сообщённые через BEP |
| `gradle_tasks` | Задачи Gradle | Выполнения задач |
| `xcode_modules` | Модули Xcode | Компиляции и события кэша модулей |
| `once_actions` | Действия Once | Выполнения |
| `mix_files` | Скомпилированные файлы Mix | Компиляции |
| `mix_modules` | Скомпилированные модули Mix | Компиляции |

Эти инструменты внедряются постепенно и возвращают данные только для проектов, где они включены; для остальных проектов возвращается ошибка вместо пустого результата. Тип доступен только для проектов, использующих соответствующий инструментарий сборки. Инструменты принимают ограниченные фильтры `start_at`/`end_at`, `environment` (`any`, `ci` или `local`) и точное значение `branch`. `list_build_entities` принимает `q`; `list_build_entity_history` поддерживает непрозрачные курсоры `after`/`before`. Неизвестные измерения времени или наблюдения кэша остаются недоступными, а не превращаются в нули или промахи. История ссылается на записанного родителя и нативное выполнение для детализации с помощью существующих инструментов запусков.

Метрики `get_build_entity` включают `duration_samples` — количество наблюдений с записанным временем: подлинные нулевые длительности учитываются, отсутствующие измерения времени — нет. Это число может быть меньше количества наблюдений; недоступная статистика длительности остаётся null.

Длительности модулей Xcode берутся из измеренных компиляций целей в журналах сборки. Разрешения кэша модулей и цели без работы по компиляции не вносят вклад в выборки длительности. Наблюдения компиляции ссылаются на сборку Xcode; события кэша ссылаются на команду генерации или кэширования.

Действия Bazel идентифицируются по метке цели, мнемонике и настроенному основному выходному файлу, что позволяет разделять действия и конфигурации без опоры на зависящие от входных данных дайджесты кэша. История записывает выполнения, сообщённые через BEP, а не поиски в кэше или этапы профилирования трассировки. Полное покрытие выполнения требует `--build_event_publish_all_actions`; доставка артефактов выполняется по принципу best effort, поэтому отсутствие наблюдений не является доказательством того, что работа не выполнялась. Старые полезные нагрузки Kura без стабильной идентичности или начала выполнения по-прежнему принимаются, но не индексируются. Отсутствующие измерения времени окончания остаются недоступными, а подлинные нулевые длительности учитываются.

Длительности модулей Mix измеряют компиляцию содержащего файла, а не независимо измеренную работу модуля. Действия Once используют объявленные слоты target/capability/index, когда клиент сообщил сопоставления целей; одни лишь диагностические метки не являются стабильными идентификаторами. Существующие клиенты и инструменты уровня запуска поддерживаются без изменений.

Чтения аналитики имеют ограниченное потребление памяти и времени выполнения. Если запрос превышает эти лимиты, инструмент возвращает ошибку вместо создания пустого результата.

Новые наблюдения индексируются после развертывания; эта функция не заполняет ретроспективно существующую телеметрию запусков. Метаданные идентичности хранятся дольше отдельных наблюдений в соответствии с <.localized_link href="/guides/server/data-retention">политикой хранения данных</.localized_link>.

### События

Клиенты, использующие жизненный цикл Model Context Protocol без сохранения состояния `2026-07-28`, могут вызывать `events/list` для обнаружения событий и их схем полезной нагрузки:

| Событие | Когда отправляется | Фильтр подписки |
|-------|-----------------|---------------------|
| `test_case.marked_flaky` | Тест-кейс меняется с нестабильного на стабильный. | `account_handle`, `project_handle` |
| `build.failed` | Локальная сборка или сборка в непрерывной интеграции Xcode, Gradle или Bazel завершается с ошибкой. | `account_handle`, `project_handle` |
| `test_run.failed` | Локальный запуск тестов или запуск в непрерывной интеграции завершается с ошибкой, включая объединённый шардированный запуск или прерванный запуск. | `account_handle`, `project_handle` |
| `ci_job.failed` | Задача раннера Tuist завершается с ошибкой. | `account_handle` |

Для подписки клиент вызывает `events/subscribe` с именем события, идентификаторами, указанными выше в `arguments`, и доставкой `webhook`, содержащей URL-адрес обратного вызова `https://` и секрет подписи `whsec_`. Для событий проекта требуется членство в аккаунте и доступ на чтение к соответствующим данным тестов или сборок; для событий задач раннера требуется членство в аккаунте и доступ на чтение к раннеру. Заявленные токены доступа [`auth.md`](https://workos.com/auth-md), заявленные токены аккаунта и разрешения авторизации браузера могут создавать подписки; доставка останавливается, когда связанные учетные данные больше не активны. Каждый пользователь может иметь до 25 активных подписок. Tuist отправляет проверочный запрос на обратный вызов перед сохранением подписки. Обратный вызов должен вернуть объект, содержащий то же значение `challenge`. Подписка действует семь дней по умолчанию, может быть обновлена путем повторной подписки и прекращает доставку, когда доступ пользователя или учетные данные удаляются. Необязательный параметр `ttlMs` ограничен диапазоном от одного часа до 30 дней. Tuist повторяет попытку вызова обратного вызова при тайм-ауте и отменяет подписку после как минимум трех последовательных тайм-аутов в течение пяти минут; подпишитесь снова после восстановления обратного вызова.

При возникновении события Tuist отправляет его идентификатор ресурса и URL-адрес панели управления на обратный вызов. Ошибки сборок и запусков тестов также включают `is_ci` и `git_branch`, поэтому клиенты могут игнорировать локальные ошибки или фильтровать по ветке. События сборки включают `build_system`; события задач раннера включают как `workflow_job_id`, так и `workflow_run_id`. Запрос включает идентификатор подписки и заголовки подписи [Standard Webhooks](https://www.standardwebhooks.com/), чтобы клиент мог проверить источник. Tuist повторяет неудачные доставки, поэтому клиентам следует использовать стабильный `eventId` для отбрасывания дубликатов. Полезная нагрузка не содержит имен тестов, логов и сообщений об ошибках; клиент может получить эти детали через инструменты выше и решить, уведомлять ли команду или начать отладку. Клиенты могут остановить доставку с помощью `events/unsubscribe`.

| `build_insights` | Применяет плагин Tuist Gradle и при необходимости настраивает поведение загрузки аналитики сборки. |
| `test_insights` | Применяет плагин Tuist Gradle, чтобы результаты задач Gradle `Test` автоматически загружались. |
| `flaky_tests` | Помогает настроить обнаружение нестабильных тестов, опциональное использование плагина Gradle Test Retry и конфигурацию карантина тестов. |
| `test_sharding` | Добавляет рабочий процесс непрерывной интеграции для `tuistPrepareTestShards`, генерации матрицы шардов и выполнения тестов на основе `TUIST_SHARD_INDEX`. |

Если `features` отсутствует, подсказка просит агента уточнить, какие интеграции нужны пользователю, или вывести минимально полезный набор из запроса перед редактированием проекта Gradle.

#### Возможности подсказки интеграции Xcode

Подсказка `integrate_xcode_project` документирует каждую интеграцию Xcode, которую поддерживает Tuist:

| Возможность | Что настраивает агент |
|---------|---------------------------|
| `xcode_cache` | Настраивает `tuist setup cache`, параметры кэша сгенерированного проекта, ручные настройки сборки кэша Xcode и политику загрузки, ограниченную раннерами непрерывной интеграции. |
| `build_insights` | Настраивает `tuist inspect build`, `tuist xcodebuild`, `-resultBundlePath` и опциональные метрики машины через `tuist setup insights`. |
| `test_insights` | Настраивает `tuist inspect test`, пост-действия тестирования схем и генерацию бандлов результатов для запусков тестов в непрерывной интеграции. |
| `test_sharding` | Добавляет планирование шардов для Xcode или сгенерированного проекта и рабочий процесс выполнения шардов с `TUIST_SHARD_INDEX`. |

Если `features` отсутствует, подсказка просит агента уточнить, какие интеграции нужны пользователю, или вывести минимально полезный набор из запроса перед редактированием проекта Xcode.
