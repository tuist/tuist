# Протокол Model Context Protocol

[Model Context Protocol (MCP)](https://modelcontextprotocol.io/docs/getting-started/intro) — это открытый стандарт, позволяющий агентам искусственного интеллекта взаимодействовать с внешними сервисами и источниками данных. Он обеспечивает совместимость таких приложений, как [Claude](https://claude.ai/), [Claude Code](https://docs.anthropic.com/en/docs/claude-code), [Codex](https://developers.openai.com/codex/), и редакторов, таких как [Zed](https://zed.dev), [Cursor](https://www.cursor.com) или [Visual Studio Code](https://code.visualstudio.com), с Tuist.

Tuist размещает серверную точку входа Model Context Protocol по адресу `https://tuist.dev/mcp`. Подключив к ней свой клиент, вы позволяете агентам получать доступ к данным ваших проектов Tuist, включая аналитику тестов, анализ нестабильных тестов и многое другое. Большинство инструментов работают только в режиме чтения и имеют доступ исключительно к данным проектов Tuist, прошедших аутентификацию. Инструменты настройки аккаунта могут перечислять аккаунты, создавать организации, создавать проекты и добавлять существующих пользователей в организации, если у аутентифицированного пользователя есть необходимые разрешения. Каждый инструмент предоставляет аннотации, указывающие, работает ли он только в режиме чтения, может ли он вызвать изменения, которые трудно отменить, и может ли он изменить состояние в публичном интернете. `update_runner_profile`, `update_notification_rule` и `connect_claude_subscription` помечены как `destructiveHint: true`, поскольку они могут заменять существующие конфигурации или учетные данные. Инструменты настройки аккаунта требуют аутентификации пользователя. Они недоступны для токенов проектов или обычных токенов аккаунтов. Когда пользователь авторизует клиент в браузере или подтверждает регистрацию через `auth.md`, Tuist связывает эти учетные данные с пользователем только в точке входа Model Context Protocol, чтобы инструменты настройки могли завершить запрошенный рабочий процесс.

Tuist реализует [протокол версии 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http). Запросы не сохраняют состояние: клиенты отправляют метаданные протокола с каждым запросом и могут вызывать инструменты напрямую без инициализации. `server/discover` возвращает идентификатор сервера, его возможности, поддерживаемые версии и инструкции. Идентификаторы сессий или независимые потоки событий отсутствуют. Клиенты, использующие поток инициализации версий 2025-06-18 или 2025-03-26, по-прежнему поддерживаются; они также работают без серверных сессий.

## Model Context Protocol против навыков

Инструменты Model Context Protocol и <.localized_link href="/guides/features/agentic-coding/skills">навыки</.localized_link> могут частично дублировать функциональность друг друга. Учитывая текущее перекрытие возможностей, выбирайте один подход для каждого рабочего процесса и используйте его последовательно, вместо того чтобы смешивать оба подхода в одном процессе.

Для клиентов, поддерживающих установку плагинов, используйте <.localized_link href="/guides/features/agentic-coding/plugins">плагины Tuist</.localized_link> для одновременной установки обоих компонентов.

## Конфигурация

Добавьте `https://tuist.dev/mcp` в качестве удаленного сервера Model Context Protocol в вашем клиенте. Инструкции по инициализации сервера и публичная карточка сервера описывают OAuth 2.0 с динамической регистрацией клиента и стандартный поток авторизации через браузер непосредственно в интерфейсе, не требуя от агентов загружать или следовать внешним документам по аутентификации. Эти общие для всего сервера инструкции сохраняют рекомендации по рабочему процессу универсальными: аутентификация инструментов не аутентифицирует локальные инструменты командной строки или интеграции с системами сборки, и агенты должны проверять запрашиваемые изменения через соответствующие инструменты Tuist. Настройка и проверки аутентификации, специфичные для системы сборки, документированы в руководствах по интеграции и подсказках. Tuist по-прежнему отдельно предоставляет метаданные обнаружения [Open Authorization](https://oauth.net/2/) и текущий [протокол auth.md](https://workos.com/auth-md) по адресу `https://tuist.dev/auth.md`.

Если одна из ваших организаций требует единого входа (SSO), авторизация клиента в браузере требует сессии, выполненной через эту организацию, и при необходимости Tuist сначала перенаправляет вас к провайдеру. См. <.localized_link href="/guides/integrations/authentication/sso#choose-an-enrollment-policy">единый вход</.localized_link>.

Точка входа принимает жизненный цикл запросов Model Context Protocol без сохранения состояния `2026-07-28`, включая `server/discover`, наряду со старым жизненным циклом на основе сессий. Существующие клиенты могут продолжать использовать свой текущий метод подключения.

Клиенты, поддерживающие события Model Context Protocol, могут подписываться на события проекта. См. раздел [События](#events) для получения информации о доступных событиях и требованиях к доставке.

Клиенты, уже поддерживающие удаленную аутентификацию через браузер, могут продолжать аутентификацию в браузере. Клиенты и агенты, поддерживающие `auth.md`, могут регистрироваться анонимно, предъявлять доверенное утверждение идентичности провайдера или начинать процесс подтверждения адреса электронной почты с аутентификацией сервиса. Регистрация возвращает утверждение идентичности, подписанное Tuist, которое агент обменивает на стандартной конечной точке токенов на токен доступа сроком на один час. Tuist публикует свой открытый ключ подписи и поддерживает стандартное отзывание токенов и доставку событий безопасности от провайдера.

Неаутентифицированный агент должен прочитать заголовок `WWW-Authenticate`, возвращаемый точкой входа Model Context Protocol, получить метаданные защищенного ресурса, получить метаданные сервера авторизации и перейти по его URL `agent_auth.skill`. Tuist также возвращает тот же локальный URL `auth_md` в теле ответа об отказе в доступе, чтобы клиенты, управляемые языковыми моделями, могли обнаружить этот поток без reliance на нативную интеграцию клиента. Локальный для развертывания документ является источником истины для имен конечных точек, тел запросов, опроса подтверждений и обмена утверждениями.

Перед тем как агент начнет процесс подтверждения адреса электронной почты, он должен попросить пользователя подтвердить адрес электронной почты своего аккаунта Tuist. Агент не должен определять этот адрес из профиля провайдера, конфигурации Git, переменных окружения или метаданных сессии.

Точка входа использует группу областей видимости `mcp`. Анонимные учетные данные до подтверждения могут обнаруживать возможности и читать публичные руководства по интеграции, но они не рассматриваются как учетные данные вошедшего пользователя. После авторизации в браузере или подтверждения учетные данные привязываются к пользователю, и каждый инструмент применяет те же проверки авторизации, что и панель управления. Подробнее см. в <.localized_link href="/guides/server/authentication#scope-groups">документации по группам областей видимости</.localized_link>.

Инструменты разрешаются к проектам, которые аутентифицированный пользователь уже может читать. Инструменты сборки Xcode и Gradle принимают UUID сборки или URL панели управления. UUID должен идентифицировать ровно один проект; если он встречается в нескольких проектах, инструмент возвращает ошибку «не найдено» вместо выбора отчета другого проекта. Чтение данных панели управления и API в рамках проекта остается доступным. Сообщаемые идентификаторы субъектов являются непроверенными метками, а не учетными данными или дополнительными правами доступа.

Инструменты списка сборок и деталей предоставляют дополнительные метаданные `tuist_version`: версию CLI Tuist для Xcode и Cargo, плагин Tuist Gradle для Gradle и библиотеку `tuist_ex` для Mix. Xcode также предоставляет `tuist_generation_version` из связанного события генерации проекта, которое может отличаться от версии загружающего CLI. Отсутствующие значения равны null, а не выводятся из сервера или другого отчета. Bazel использует свой существующий `bazel_version`; детали запуска Once предоставляют `once_version`. Эти поля описывают сообщаемые версии, а не проверенную идентификацию или версии контракта передачи данных. Конечные точки REST API для сборок предоставляют те же метаданные. Существующие интеграции и навыки работы с нестабильными тестами не зависят от полей версий и не требуют изменений в рабочем процессе.

Операторы Tuist, исследующие аккаунт клиента, делают это через внутренние инструменты операций Tuist, которые записывают каждый вызов; прямое подключение к этой конечной точке не дает доступа, выходящего за рамки членства самого пользователя.

### Pulse

Pulse предоставляет два инструмента только для чтения, оба адресуются через `account_handle`:

| Инструмент | REST-эквивалент под `/api/accounts/:account_handle/pulse` |
| --- | --- |
| `query_pulse` | `GET /:signal` |
| `get_pulse_analytics` | `GET /:signal/analytics` |

Доступ к Pulse ограничен текущими участниками организации, настроенной на сервере, даже если аккаунт или проект является публичным. Требуется аутентификация пользователя или учетные данные `mcp`, связанные с пользователем, а также разрешение на чтение аккаунта. Токены проектов, обычные токены аккаунтов, анонимные регистрации и доступ операторов без членства в организации не предоставляют доступ к Pulse. Учетные данные не могут выбирать другой бэкенд или арендатора телеметрии. Браузерные агенты получают эти инструменты только на страницах Pulse, в рамках области видимости аккаунта этой страницы.

REST требует учетных данных пользователя. Ассоциации пользователей OAuth и `auth.md` доступны только на конечной точке `/mcp`; учетные данные аккаунта без текущего пользователя отклоняются, независимо от членства или видимости связанного аккаунта.

`query_pulse` принимает `signal` (`metrics`, `logs` или `traces`), необязательный `query` и `range` (`15m`, `1h`, `6h` или `24h`, по умолчанию `1h`). Метрики принимают выражения PromQL. Логи и трассировки принимают буквальный текст без учета регистра, сопоставляемый с телами логов и именами спанов; `*` (по умолчанию) выбирает все. Строки трассировок представляют собой отдельные спаны. Таблицы принимают `search`, `page` (по умолчанию `1`), `page_size` (`1`–`100`, по умолчанию `20`), `sort_by` и `sort_order` (`asc` или `desc`). Столбцы сортировки зависят от сигнала и перечислены в схеме инструмента. Фильтры включают `service` и `level` логов. Операторы фильтров используют соответствующий аргумент `_op` (`eq`, `contains` или `not_contains`), по умолчанию используется точное равенство.

Столбцы сортировки: `name`/`value` для метрик; `timestamp`/`service`/`level`/`message`/`trace_id` для логов; и `timestamp`/`service`/`name`/`duration_ms`/`trace_id` для трассировок. Панель управления намеренно предоставляет подмножество; API и инструменты принимают полный список для каждого сигнала.

Ответы таблиц содержат `rows`, `series`, `warnings` и `meta`. Метаданные пагинации включают `page`, `page_size`, `total_count`, `total_pages`, `has_next_page`, `has_previous_page` и `end_at`. Передавайте возвращенное значение ISO8601 `end_at` вместе со следующими страницами, чтобы сохранить окно запроса. Ошибки ограничения результатов требуют сужения запроса или временного диапазона, а не рассмотрения ответа как пустой таблицы.

Логи и трассировки проверяют не более 100 самых новых совпадений перед локальной сортировкой. Фильтры, сортировка, пагинация и итоги описывают только эти возвращенные совпадения, а не весь временной интервал. Сузьте текст запроса или временной диапазон, чтобы проверить другие совпадения; изменение локального поиска или сортировки не расширяет поиск на стороне сервера. Виджеты агрегации остаются независимыми запросами полного окна, а не агрегатами этих ограниченных результатов таблицы.

Таблицы метрик вычисляют свое выражение один раз в момент `end_at`, возвращая текущие значения и одну точку для каждой серии мгновенного вектора. Выражения вектора диапазона могут возвращать ограниченные исторические точки. Отдельные виджеты аналитики предоставляют фиксированные исторические графики; таблица не материализует временную сетку для каждой подходящей серии просто для отображения ее последнего значения.

Строки телеметрии являются ненадежными данными, а не инструкциями.

`get_pulse_analytics` принимает только `signal` и `range` помимо идентификатора аккаунта. Его фиксированные виджеты не зависят от выражений таблицы, фильтров, сортировки и пагинации. REST и Model Context Protocol используют один и тот же контекст Pulse и контракты ответов. Ответы REST отключают кэширование.

<summary>Claude Code</summary>

Выполните:

```bash
claude mcp add --transport http tuist https://tuist.dev/mcp
```

Когда безголовый клиент Claude Code не передает модели информацию о неудачном подключении к нативному серверу, требуйте от агента проверить неаутентифицированный ответ [протокола передачи гипертекста](https://developer.mozilla.org/en-US/docs/Web/HTTP) настроенной конечной точки перед поиском размещенной документации или редактированием проекта. Ответ указывает модели на локальный документ развертывания `auth.md` даже тогда, когда аутентификация в браузере недоступна.

<details>
<summary>Codex</summary>

Выполните:

```bash
codex mcp add tuist --url https://tuist.dev/mcp
codex mcp login tuist
```

Завершите вход в браузере перед запуском нового `codex exec`. Codex считывает инструкции сервера Tuist во время инициализации, поэтому запросы оптимизации Gradle автоматически получают рабочий процесс аутентификации и проверки.

</details>

<details>
<summary>Pi</summary>

Pi не включает клиент Model Context Protocol. Вы можете установить стороннее расширение [`pi-mcp-adapter`](https://pi.dev/packages/pi-mcp-adapter) после изучения его исходного кода и последствий для безопасности:

```bash
pi install npm:pi-mcp-adapter
```

Добавьте файл `.mcp.json` на уровне проекта:

```json
{
  "mcpServers": {
    "tuist": {
      "url": "https://tuist.dev/mcp",
      "auth": false
    }
  }
}
```

Установка `auth` в значение `false` предотвращает скрытие неавторизованного ответа Tuist обработчиком аутентификации браузера адаптера. После этого безголовый агент может прочитать возвращенный URL `auth_md` и следовать процессу регистрации Tuist, обмена утверждениями идентичности и опроса подтверждения. Настройте полученный токен доступа как bearer-токен или позвольте агенту выполнять аутентифицированные вызовы Model Context Protocol напрямую.

Если вы предпочитаете аутентификацию в браузере, установите `auth` в значение `"oauth"`. Для этого потока держите один процесс активным с использованием [режима удаленного вызова процедур](https://pi.dev/docs/latest/rpc) Pi, пока аутентификация не завершится:

```bash
pi --mode rpc
```

Не разделяйте ожидающую аутентификацию в браузере между отдельными вызовами `pi --print`, так как процесс, владеющий состоянием обратного вызова, уже завершился.

</details>

Если ваш агент поддерживает `auth.md`, он может запуститься анонимно, не открывая браузер. Доверенная идентичность провайдера также может завершить процесс без браузера, если она уже связана. Для аутентифицированной сервисом электронной почты, анонимного подтверждения или первой ссылки на провайдера агент покажет вам ссылку для проверки Tuist и шестизначный код. Откройте ссылку, войдите в систему и введите код агента на странице Tuist. Никогда не отправляйте код обратно агенту. Метаданные сервера авторизации Tuist указывают непосредственно на собственный файл `/auth.md` развертывания, который содержит точные форматы запросов и опроса.

## Агенты в Amp orbs и облачных сессиях Claude Code

Агенты для написания кода, работающие в песочницах, подключенных к аккаунту Tuist, могут аутентифицироваться на конечной точке с помощью собственного токена идентичности, без браузера или сохраненных учетных данных Tuist:

- **Amp orbs** рабочего пространства Amp или проекта, которые аккаунт подключил через **Settings → Integrations → Amp**, отправляют токен ID орба. В Amp установите заголовок `Authorization` сервера в значение `Bearer ${amp:id-token}`. Amp выпускает токен для источника URL сервера, поэтому URL должен быть адресом этого экземпляра Tuist, и обновляет его до истечения срока действия. Токены, выпущенные для другого источника, отклоняются.
- **Облачные сессии Claude Code** подключенной среды Claude Code отправляют токен сессии, который Tuist передает им как `TUIST_OIDC_TOKEN`. Установите заголовок в значение `Bearer ${TUIST_OIDC_TOKEN}`.

Песочницы Linux в Tuist поставляются с этой конфигурацией: сервер `tuist` в пользовательских настройках Amp и в пользовательской конфигурации Claude Code, оба указывают на `${TUIST_URL}/mcp`, вместе с CLI Tuist и навыком, который сообщает агенту, когда проверять его результаты по истории проекта. В других местах добавьте сервер с указанным выше заголовком самостоятельно.

Эти токены предоставляют доступ только для чтения ко всем проектам подключенного аккаунта: они несут права на чтение группы `mcp` и не имеют прав на создание, изменение или удаление данных, таких как игнорирование или пропуск тестов. Отключение рабочего пространства или среды прекращает доступ при следующем запросе, и доступ никогда не длится дольше самого токена. Рабочее пространство Amp, подключенное к нескольким аккаунтам Tuist, отклоняется, потому что его токен не указывает один из них. Когда подключение отсутствует, об этом говорится в поле `error_description` ответа об отсутствии авторизации.

Этот доступ только для чтения применяется только к конечной точке Model Context Protocol. Инструмент командной строки и интеграции систем сборки в той же песочнице по-прежнему обменивают токен на CI-доступ подключения.

## WebMCP

В браузерах, поддерживающих [WebMCP](https://webmachinelearning.github.io/webmcp), страницы Tuist регистрируют инструменты через `document.modelContext`, поэтому агенты, встроенные в браузер, могут вызывать их без дополнительной настройки. Вызовы выполняются на сервере Tuist.

- **Страницы веб-сайта и документации** регистрируют инструменты документации и исходного кода (`search_tuist`, `search_tuist_code`, `list_tuist_files` и `read_tuist_file`). Им не требуется вход в систему.
- **Страницы панели управления аккаунта**, когда вы вошли в систему, регистрируют инструменты Tuist только для чтения для этого аккаунта. Каждая страница регистрирует только инструменты для того, что она отображает, для системы сборки проекта: страница сборок проекта Gradle получает инструменты сборки Gradle, страницы тестов — инструменты тестирования и покрытия, страницы раннеров — инструменты раннеров, а страницы песочниц — инструменты песочниц. Раздел «Подписки» на странице настроек ИИ вашего личного аккаунта получает `list_ai_subscriptions`, который отвечает только для вашего собственного аккаунта. Каждая страница также получает инструменты документации, `list_projects` и `get_project`. Инструменты выполняются от имени вошедшего пользователя, поэтому они получают доступ только к данным, которые вы можете читать в панели управления, и только к аккаунту, который вы просматриваете. При переходе на другую страницу или аккаунт инструменты заменяются инструментами этой страницы.

Инструменты, которые создают, изменяют или удаляют данные, недоступны через WebMCP, поскольку браузерный агент получает инструменты без вашего добавления и читает контент, создаваемый сборками и тестами. Подключите клиент MCP к конечной точке `/mcp`, чтобы использовать эти инструменты.

Если организация требует единый вход (SSO), войдите в панель управления через ее провайдера, чтобы использовать ее инструменты.

## Интеграции систем сборки используют два набора учетных данных

Учетные данные, используемые для инструментов Model Context Protocol, не аутентифицируют плагин Gradle или удаленные службы Bazel. Прежде чем агент редактирует или проверяет интеграцию Gradle или Bazel, он должен выполнить:

```bash
tuist auth whoami --url https://tuist.dev
```

Если эта команда не аутентифицирована, агент должен остановиться и попросить пользователя выполнить:

```bash
tuist auth login --url https://tuist.dev
```

Для локального или самостоятельного развертывания замените URL в обеих командах и в `tuist.toml`. Сохраняйте одинаковое написание хоста везде. Например, `localhost` и `127.0.0.1` используют отдельные сохраненные учетные данные.


## Возможности

### Инструменты

Следующие инструменты доступны через сервер Tuist Model Context Protocol:

Каждый инструмент публикует понятное человеку описание вместе с явными схемами ввода и вывода. Успешные вызовы возвращают структурированный контент, соответствующий заявленной схеме вывода, а также тот же результат, сериализованный в виде текста для клиентов, которые еще не потребляют структурированный контент.

Инструменты, принимающие идентификатор отдельной записи, такой как `build_run_id`, `test_run_id`, `test_case_id`, `bundle_id`, `run_id`, `generation_id` или `cache_run_id`, также принимают URL панели управления Tuist для этой записи. Вставьте URL прямо из браузера вместо извлечения из него идентификатора.

`get_xcode_build`, `get_test_run`, `get_gradle_build` и `get_project` могут включать `side_quests`: возможности Tuist, которые проект не использует, но которые, согласно записи, были бы полезны. Каждый имеет `id`, `tip`, указывающий на доказательства, на которых он основан, и ссылку `docs`. Агентам предлагается сначала выполнить запрос пользователя, упомянуть применимые побочные задачи и действовать по одной из них только с согласия пользователя. Они возвращаются только участникам аккаунта проекта, независимо от того, подключаются ли они через пользовательскую сессию, токен MCP или идентичность агента:

| ID | Инструмент | Рекомендуется, когда |
|----|------|----------------|
| `xcode_compilation_cache` | `get_xcode_build` | Обработанная чистая сборка с Xcode 26 или новее не выполнила ни одной кэшируемой задачи компиляции. |
| `gradle_build_cache` | `get_gradle_build` | Сборка выполнила кэшируемые задачи, но кэш сборок Gradle не вычислил ключ ни для одной из них, что означает, что кэш сборок был отключен. |
| `flaky_test_quarantine` | `get_test_run` | В запуске были нестабильные тесты, и в проекте не включена автоматизация, которая игнорирует или пропускает их. Не рекомендуется для проектов Once. |
| `test_sharding` | `get_test_run` | Запуск CI без шардирования занял 10 минут или больше в системе сборки, которую Tuist может шардировать. Подсказка указывает, сколько тестов уже было пропущено выборочным тестированием, когда оно сработало. |
| `tuist_runners` | `get_xcode_build`, `get_test_run` | Запуск CI использовал машины GitHub Actions, Bitrise, GitLab CI или Buildkite, а аккаунт никогда не запускал задачи на Tuist Runners. Доступно только на tuist.dev. |
| `pull_request_comments` | `get_xcode_build`, `get_test_run` | Запуск GitHub Actions относится к проекту, который не подключен к своему репозиторию GitHub. |
| `other_build_systems` | `get_project` | Аккаунт не использует Tuist со всеми поддерживаемыми системами сборки. В подсказке перечислены файлы, идентифицирующие другие системы, чтобы агент мог проверить репозиторий. |

#### Поиск по документации и сообществу

Этот инструмент только для чтения выполняет поиск по документации Tuist, справочнику [прикладного программного интерфейса](https://en.wikipedia.org/wiki/API), релизам на GitHub, форуму сообщества и задачам на GitHub через тот же поисковый движок, что работает на сайте документации. Результаты поиска по релизам включают продукт, версию, дату публикации и статус предварительного релиза. По умолчанию ищутся стабильные релизы, предварительные релизы можно включить с помощью `include_prereleases`. Инструмент доступен только на сервере, размещенном Tuist, по адресу `https://tuist.dev/mcp`.

| Инструмент | Описание | Обязательные параметры |
|------|-------------|---------------------|
| `search_tuist` | Поиск по публичной документации Tuist, справочнику прикладного программного интерфейса, релизам на GitHub, обсуждениям в сообществе и задачам на GitHub. При необходимости можно ограничить поиск одним `source` (`docs`, `api_reference`, `releases`, `forum`, `issues`). | `query` |

#### Обратная связь

Агенты могут сообщить команде Tuist, если инструмент или подсказка Tuist сработали не так, как ожидалось: например, выдали непонятный результат, ошибку, недостающие данные или отсутствующую возможность. Агентам предлагается предложить отчет и отправить его только после вашего согласия. Каждый отчет открывает диалог с поддержкой Tuist, которая может ответить вам по электронной почте. Отчет включает ожидаемое агентом поведение, фактический результат, необязательное предложение, ваш идентификатор пользователя Tuist, хэндл и электронную почту, а также организации, к которым вы принадлежите. Агенты также могут указать аккаунт и проект, в которых возникла проблема, чтобы команда знала, с какой организацией связаться; принимаются только аккаунты, к которым вы имеете доступ. Отчеты могут отправлять только агенты, вошедшие в систему как пользователь Tuist, и каждый пользователь может создавать до 10 отчетов в час. Инструмент доступен только на сервере, размещенном Tuist, по адресу `https://tuist.dev/mcp`.

| Инструмент | Описание | Обязательные параметры |
|------|-------------|---------------------|
| `report_feedback` | Сообщить о проблеме с инструментом или подсказкой Tuist. При необходимости укажите `tool_name`, `account_handle` и `project_handle`, в которых она возникла, и добавьте `suggestion`. | `category`, `expected`, `actual` |

#### Ответы на основе исходного кода

Эти инструменты только для чтения позволяют агентам использовать точную публичную ревизию исходного кода Tuist, развернутую вместе с размещенным сервером, как источник истины для ответов, зависящих от текущего поведения. Они доступны только по адресу `https://tuist.dev/mcp`.

Совместимые клиенты получают фактические описания ревизии исходного кода инструментов, ссылки и ограничения результатов во время инициализации вместе с информацией для встроенной OAuth-аутентификации. Эти описания не предписывают стиль ответа или процесс верификации. Пользователи могут задать вопрос напрямую, не вызывая сначала подсказку `ask_tuist`; подсказка остается доступной для явного рабочего процесса с опорой на исходный код.

Каждая операция имеет фиксированные ограничения на параллелизм, длительность, обход, количество прочитанных байт и размер ответа. Результаты поиска и списков включают поля `truncated` и `truncation_reason`. Если результат усечен, сузьте путь, шаблон файла или поисковый запрос вместо того, чтобы считать результат исчерпывающим.

| Инструмент | Описание | Обязательные параметры |
|------|-------------|---------------------|
| `search_tuist_code` | Отвечайте на вопросы о текущем поведении, значениях по умолчанию, конфигурации, флагах возможностей, обработке ошибок или недокументированных деталях, выполняя поиск по исходным файлам. Результаты включают окружающие строки, ссылки на исходный код, привязанные к ревизии, и статистику сканирования. | `pattern` |
| `list_tuist_files` | Обнаруживайте подсистему исходного кода или близлежащие тесты, когда соответствующий путь неизвестен. Списки имеют ограниченную глубину и количество результатов. | Нет |
| `read_tuist_file` | Просматривайте определенный диапазон строк в файле реализации, месте вызова или тесте после нахождения соответствующего пути. Усеченные ответы предоставляют `next_start_line` для продолжения. | `path` |

Без правил вы не получаете уведомлений. Они требуют аутентификации пользователя, действуют только над вашими собственными правилами и принимают только проекты аккаунтов, к которым вы принадлежите. Они не предлагаются на страницах панели управления, так как правила охватывают все ваши аккаунты.

#### Сборки Xcode

Инструменты детализации сборок для Xcode, Gradle, Bazel, Mix и Cargo предоставляют существующую структуру `custom_metadata: {tags, values}`, включая наблюдения за инфраструктурой, если они сообщаются. Значения остаются строками, а неизвестные ключи сохраняются. Например, `tuist.cpu.available_processors` описывает логические процессоры, доступные во время выполнения, тогда как `tuist.gradle.max_workers` — это ограничение на количество воркеров Gradle, а `tuist.jvm.max_heap_bytes` — ограничение кучи JVM, а не памяти хоста. Это ненадежные наблюдения клиента, а не проверенные идентификаторы раннеров. Отсутствующие наблюдения остаются отсутствующими; импортированные логи и старые клиенты могут не иметь метаданных инфраструктуры. Метаданные ожидают согласованного обновления клиента/протокола.

| Инструмент | Описание | Обязательные параметры |
|------|-------------|---------------------|
| `list_xcode_builds` | Выводит список запусков сборок Xcode для проекта. | `account_handle`, `project_handle` |
| `get_xcode_build` | Получает подробную информацию о конкретном запуске сборки Xcode, включая временный URL-адрес для скачивания архива, содержащего исходный `.xcactivitylog`. | `build_run_id` |
| `list_xcode_build_targets` | Выводит список целей сборки для конкретного запуска сборки Xcode. | `build_run_id` |
| `list_xcode_build_files` | Выводит список скомпилированных файлов для конкретного запуска сборки Xcode. | `build_run_id` |
| `list_xcode_build_steps` | Выводит список записанных шагов сборки с указанием времени и результатов, без текста логов. | `build_run_id` |
| `get_xcode_build_step` | Получает один записанный шаг сборки, включая его лог и флаг усечения. | `build_run_id`, `step_id` |
| `list_xcode_build_issues` | Выводит список проблем сборки (предупреждения и ошибки) для конкретного запуска сборки. | `build_run_id` |
| `list_xcode_build_cache_tasks` | Выводит список задач, поддающихся кэшированию (попадания/промахи кэша), для конкретного запуска сборки Xcode. | `build_run_id` |
| `list_xcode_build_cas_outputs` | Выводит выходные данные [хранилища с адресацией по содержимому](https://en.wikipedia.org/wiki/Content-addressable_storage) для конкретного запуска сборки Xcode. | `build_run_id` |

`list_xcode_build_steps` по умолчанию возвращает страницы по 20 шагов (максимум 100 через `page_size`), с `page` и `pagination_metadata` для навигации. Используйте `search` для поиска по названиям, проектам или целям, либо фильтруйте по точным значениям `project`, `target`, `category` (например, `swiftCompilation`) и `status` (`success` или `failure`). Сортируйте по `duration_ms` для отображения самых медленных сначала (по умолчанию) или по `start_ms` для хронологического порядка. ID шагов разрывают связи и возвращаются в виде десятичных строк для сохранения полной 64-битной точности. ID привязаны к сборке и не должны сопоставляться между разными сборками.

Необязательные параметры `start_ms` и `end_ms` выбирают шаги, пересекающиеся с временным диапазоном в миллисекундах от начала сборки; конец диапазона исключается. Оба инструмента принимают UUID сборки или URL панели управления в качестве `build_run_id`. Передавайте полученный `id` шага без изменений в качестве `step_id` для получения его лога. Логи хранят до 64 КиБ на шаг, при этом `log_truncated` указывает на пропущенный вывод.

Шаги собираются по умолчанию при обработке сборок Xcode. Записанные данные шагов хранятся в течение 90 дней. Ответ списка включает `availability`: `available`, если записанные шаги существуют, даже если фильтры ничего не находят; `processing`, если сборка все еще обрабатывается и шагов пока нет; или `unavailable`, если шаги не были записаны или срок их хранения истек.

Те же операции доступны через HTTP API по адресам `GET /api/projects/{account_handle}/{project_handle}/xcode/builds/{build_id}/steps` и `GET /api/projects/{account_handle}/{project_handle}/xcode/builds/{build_id}/steps/{step_id}`, с теми же фильтрами и пагинацией. Для обоих требуется доступ на чтение к проекту сборки.

| `get_gradle_build` | Получение метаданных сборки, количества задач/кэша и `failures`: сообщения об ошибке для каждой неудачной задачи и шага конфигурации. | `build_run_id` |
| `list_gradle_build_tasks` | Список результатов задач, идентификатора составной сборки, возможности кэширования, статуса инкрементальности и сообщений об ошибках. | `build_run_id` |

Списки шагов Gradle и Bazel по умолчанию возвращают 20 результатов (максимум 100), поддерживают `search`, точное совпадение `project`, `target`, `category` и `status`, фильтры по пересекающимся диапазонам `start_ms` / `end_ms` (конец исключается) и сортировку по `duration_ms` или `start_ms`. Передавайте полученные ID без изменений; они привязаны к своей сборке. Списки предоставляют `time_origin` и `coverage`. Старые отчеты Gradle используют `first_recorded_timestamp`, так как время начала сборки не загружалось. Профили Bazel предоставляют все записанные интервалы с покрытием `trace_profile` и `profile_start` в качестве временной точки отсчета. Для старых сборок используются сохраненные сводки BEP. Записи исходных данных истекают через 90 дней. Детали Bazel включают очищенные логи действий, если они опубликованы. Детали Gradle для неудачной задачи или шага конфигурации включают сообщение об ошибке, которое плагин Tuist Gradle сообщил как `log`: сообщение исключения и цепочку причин, как их выводит консоль Gradle, без трассировки стека или вывода задачи, с путями внутри проекта, сделанными относительными, и скрытыми учетными данными и другими локальными путями, не более 16 КиБ на шаг и 32 неудачных шага на сборку. Другие шаги Gradle, сборки, сообщаемые старыми версиями плагина, и отчеты без учетных данных имеют нулевое значение `log`. Шаги конфигурации сообщают `failure` при неудаче и `unknown` в противном случае. Подсказка `compare_builds` использует это покрытие, чтобы отличать полные трассировки Bazel от сохраненных сводок и направляет агентов к деталям шагов для получения результатов действий и логов перед проверкой общего вывода вызова.

Инструменты для одного шага `get_gradle_build_step` и `get_bazel_build_step` получают шаг по ID и не принимают временные фильтры; используйте соответствующие инструменты списков для фильтрации шагов по временному диапазону.

ID шагов Bazel, возвращаемые из сохраненных сводок, остаются читаемыми, если полный профиль поступает между получением списка и запросом шага. Индексированный профиль, данные шагов которого истекли, сообщает о недоступности. Списки шагов Gradle включают кэшированные и пропущенные операции с нулевой длительностью.

Логи тестов содержат `target_label` и статус попытки `status` результата теста, из которого они получены, поэтому `target_label: "//foo:bar_test"` возвращает только логи тестов этой цели. `errors: true` возвращает логи тестов неудачных попыток и фрагменты прогресса stderr, содержащие строку, которую репортер Bazel начинает с `ERROR:`, `FAIL:` или `TIMEOUT:`. Неудачные действия и их собственный вывод доступны по целям через `list_bazel_build_steps`, а сбои по каждому тест-кейсу — через инструменты запуска тестов.

#### Задачи, действия, модули и файлы

Эти инструменты уровня проекта анализируют постоянные идентификаторы сборок across запусков. Начните с `list_build_entities`, затем передайте возвращенный стабильный `id` с тем же `kind` в `get_build_entity` или `list_build_entity_history` вместе с `account_handle` и `project_handle`. Идентификатор сборки или вызова не требуется.

| Инструмент | Описание | Обязательные параметры |
| --- | --- | --- |
| `list_build_entities` | Список задач, модулей, действий или файлов одного типа, обнаруженных в сборках проекта. | `account_handle`, `project_handle`, `kind` |
| `get_build_entity` | Получение одной сущности сборки с её нативным идентификатором и аналитикой за выбранный период. | `account_handle`, `project_handle`, `kind`, `id` |
| `list_build_entity_history` | Список записанных выполнений, компиляций или событий кэша для одной сущности сборки, начиная с самых новых. | `account_handle`, `project_handle`, `kind`, `id` |

| `kind` | Инструментарий | Списки истории |
| --- | --- | --- |
| `bazel_actions` | Действия Bazel | Выполнения действий, сообщенные через BEP |
| `gradle_tasks` | Задачи Gradle | Выполнения задач |
| `xcode_modules` | Модули Xcode | Компиляции и события кэша модулей |
| `once_actions` | Действия Once | Выполнения |
| `mix_files` | Компилированные файлы Mix | Компиляции |
| `mix_modules` | Компилированные модули Mix | Компиляции |
| `cargo_crates` | Крейты Cargo | Записанные вызовы rustc |

Эти инструменты внедряются постепенно и возвращают данные только для проектов, в которых они включены; для остальных проектов возвращается ошибка вместо пустого результата. Тип доступен только для проектов, использующих соответствующий инструментарий сборки. Инструменты принимают ограниченные фильтры `start_at`/`end_at`, `environment` (`any`, `ci` или `local`) и точное значение `branch`. `list_build_entities` принимает `q`; `list_build_entity_history` поддерживает непрозрачные курсоры `after`/`before`. Неизвестные наблюдения времени выполнения или кэша остаются недоступными, а не превращаются в нули или промахи. История ссылается на записанные родительские и нативные выполнения для детализации с помощью существующих инструментов запусков.

Метрики `get_build_entity` включают `duration_samples` — количество наблюдений с записанным временем: подлинные нулевые длительности учитываются, отсутствующее время — нет. Это количество может быть меньше общего числа наблюдений; недоступная статистика длительности остаётся null.

Длительности модулей Xcode берутся из измеренных компиляций целей в логах сборки. Разрешения кэша модулей и цели без работы по компиляции не вносят вклад в выборки длительности. Наблюдения компиляций относятся к сборке Xcode; события кэша относятся к команде генерации или кэширования.

Действия Bazel идентифицируются по метке цели, мнемонике и настроенному первичному выходному файлу, что позволяет разделять действия и конфигурации без опоры на зависящие от входных данных дайджесты кэша. История записывает выполнения, сообщенные через BEP, а не поиски в кэше или этапы трассировки. Полное покрытие выполнения требует `--build_event_publish_all_actions`; доставка артефактов выполняется по принципу best effort, поэтому отсутствие наблюдений не является доказательством того, что работа не выполнялась. Старые полезные нагрузки Kura без стабильного идентификатора или начала выполнения по-прежнему принимаются, но не индексируются. Отсутствующие измерения времени окончания остаются недоступными, а подлинные нулевые длительности учитываются.

Длительности модулей Mix измеряют компиляцию содержащего файла, а не независимо измеренную работу модуля. Действия Once используют объявленные слоты цель/возможность/индекс, когда клиент сообщил сопоставления целей; одни лишь диагностические метки не являются стабильными идентификаторами. Существующие клиенты и инструменты уровня запуска поддерживаются без изменений.

Крейты Cargo группируются по точно записанному корню крейта, имени и типу. Изменения пути checkout могут разделять истории, а профили сборки, возможности и тройки целей не различаются. История измеряет вызовы rustc, а не работу по отдельным файлам или попадания в кэш; отсутствующие задачи не свидетельствуют об удалениях или полной инвентаризации рабочего пространства.

Чтения аналитики имеют ограниченное потребление памяти и времени выполнения. Если запрос превышает эти лимиты, инструмент возвращает ошибку вместо создания пустого результата.

Новые наблюдения индексируются после развертывания; эта функция не заполняет ретроспективно существующую телеметрию запусков. Метаданные идентичности хранятся дольше отдельных наблюдений согласно <.localized_link href="/guides/server/data-retention">политике хранения данных</.localized_link>.

### События

Клиенты, использующие жизненный цикл Model Context Protocol без сохранения состояния `2026-07-28`, могут вызывать `events/list` для обнаружения событий и их схем полезной нагрузки:

| Событие | Когда отправляется | Фильтр подписки |
|-------|-----------------|---------------------|
| `test_case.marked_flaky` | Тест-кейс меняется с нестабильного на стабильный. | `account_handle`, `project_handle` |
| `build.failed` | Локальная сборка Xcode, Gradle или Bazel или сборка в системе непрерывной интеграции завершается с ошибкой. | `account_handle`, `project_handle` |
| `test_run.failed` | Локальный запуск тестов или запуск тестов в системе непрерывной интеграции завершается с ошибкой, включая объединенный шардированный запуск или прерванный запуск. | `account_handle`, `project_handle` |
| `ci_job.failed` | Задача раннера Tuist завершается с ошибкой. | `account_handle` |

Для подписки клиент вызывает `events/subscribe` с именем события, идентификаторами, указанными выше в `arguments`, и доставкой `webhook`, содержащей URL-адрес обратного вызова `https://` и секрет подписи `whsec_`. События проекта требуют членства в аккаунте и права на чтение соответствующих данных тестов или сборок; события задач раннера требуют членства в аккаунте и права на чтение данных раннера. Заявленные токены доступа [`auth.md`](https://workos.com/auth-md), заявленные токены аккаунта и разрешения авторизации браузера могут создавать подписки; доставка останавливается, когда связанные учетные данные больше не активны. Каждый пользователь может иметь до 25 активных подписок. Tuist отправляет проверочный запрос на обратный вызов перед сохранением подписки. Обратный вызов должен вернуть объект, содержащий то же значение `challenge`. Подписка действует семь дней по умолчанию, может быть обновлена путем повторной подписки и прекращает доставку при удалении доступа или учетных данных пользователя. Необязательный параметр `ttlMs` ограничен от одного часа до 30 дней. Tuist повторяет попытку вызова обратного вызова при тайм-ауте и отменяет подписку после как минимум трех последовательных тайм-аутов в течение пяти минут; подпишитесь снова после восстановления обратного вызова.

При возникновении события Tuist отправляет его идентификатор ресурса и URL-адрес панели управления на обратный вызов. Ошибки сборки и запуска тестов также включают `is_ci` и `git_branch`, поэтому клиенты могут игнорировать локальные ошибки или фильтровать по ветке. События сборки включают `build_system`; события задач раннера включают как `workflow_job_id`, так и `workflow_run_id`. Запрос включает идентификатор подписки и заголовки подписи [Standard Webhooks](https://www.standardwebhooks.com/), чтобы клиент мог проверить его источник. Tuist повторяет неудачные доставки, поэтому клиентам следует использовать стабильный `eventId` для отклонения дубликатов. Полезная нагрузка не содержит имен тестов, логов и сообщений об ошибках; клиент может получить эти детали через инструменты выше и решить, уведомлять ли команду или начинать отладку. Клиенты могут остановить доставку с помощью `events/unsubscribe`.

### Подсказки

| Подсказка | Описание |
|--------|-------------|
| `fix_flaky_test` | Помогает исправить нестабильный тест, анализируя паттерны сбоев, выявляя корневую причину и применяя целенаправленное исправление. |
| `compare_builds` | Помогает сравнивать сборки для выявления регрессий производительности, изменений в кэше и проблем со сборкой. Использует нативные инструменты для проектов Xcode, Gradle, Bazel и Cargo. При сравнении Cargo сохраняется частичное покрытие компилятора, а оценочная работа компилятора отделяется от фактической экономии времени. |
| `compare_test_runs` | Помогает сравнивать два запуска тестов для выявления регрессий, новых сбоев и нестабильных тестов. |
| `compare_bundles` | Помогает сравнивать два бандла для выявления изменений размера в дереве артефактов. |
| `compare_test_case` | Помогает сравнивать поведение тест-кейса между двумя ветками или временными периодами. |
| `compare_generations` | Помогает сравнивать два запуска генерации для выявления регрессий производительности и изменений в кэше модулей. |
| `compare_cache_runs` | Помогает сравнивать два запуска кэширования для выявления изменений эффективности кэша и регрессий на уровне таргетов. |
| `integrate_gradle_project` | Помогает интегрировать Tuist в существующий проект Gradle. Включает отдельную аутентификацию инструментов и Gradle, обнаружение аккаунта, создание проекта, политику удаленного кэша, аналитику сборок и проверку чтения данных. |
| `integrate_bazel_project` | Помогает создать или выбрать проект Bazel, выполнить аутентификацию командной строки, настроить удаленный кэш и аналитику сборок, а также проверить интеграцию через данные сборок Tuist. |
| `integrate_xcode_project` | Помогает интегрировать Tuist в существующий проект Xcode. Поддерживает кэш Xcode, аналитику сборок, аналитику тестов и шардирование тестов. |
| `ask_tuist` | Отвечает на вопросы по Tuist, используя общедоступные материалы для контекста и сфокусированные доказательства реализации и тестирования как источник истины для текущего поведения. Требуется `question`, и приводятся доказательства, привязанные к ревизии. |

Подсказки с данными проекта принимают `account_handle` и `project_handle` для ограничения исследования конкретным проектом. Подсказки сравнения также принимают аргументы `base` и `head` для указания двух сравниваемых элементов (по ID, URL панели управления или имени ветки). `ask_tuist` принимает `question` вместо параметров проекта. `integrate_gradle_project` также принимает `features` — список интеграций Gradle через запятую: `remote_cache`, `build_insights`, `test_insights`, `flaky_tests` и `test_sharding`. `integrate_bazel_project` принимает необязательный `server_url` для самодостаточных или локальных установок. `integrate_xcode_project` принимает `features` со значениями `xcode_cache`, `build_insights`, `test_insights` и `test_sharding`.

#### Возможности подсказки интеграции Gradle

Подсказка `integrate_gradle_project` и инструмент `get_gradle_integration_guide` документируют полный рабочий процесс настройки. Инструмент также упоминается в инструкциях инициализации сервера, что делает его обнаруживаемым для агентов, которые не перечисляют подсказки.

| Возможность | Что настраивает агент |
|---------|---------------------------|
| `remote_cache` | Включает кэш сборок Gradle, настраивает политику загрузки в удаленный кэш Tuist и рекомендует загружать данные только с раннеров непрерывной интеграции с локальным доступом только для чтения. |
| `build_insights` | Применяет плагин Tuist для Gradle и при необходимости настраивает поведение загрузки аналитики сборок. |
| `test_insights` | Применяет плагин Tuist для Gradle, чтобы результаты задач Gradle `Test` автоматически загружались. |
| `flaky_tests` | Помогает настроить обнаружение нестабильных тестов, опциональное использование плагина Gradle Test Retry и конфигурацию карантина тестов. |
| `test_sharding` | Добавляет рабочий процесс непрерывной интеграции для `tuistPrepareTestShards`, генерации матрицы шардов и выполнения тестов на основе `TUIST_SHARD_INDEX`. |

Если `features` опущен, подсказка просит агента уточнить, какие интеграции нужны пользователю, или вывести минимальный полезный набор из запроса перед редактированием проекта Gradle.

#### Возможности подсказки интеграции Xcode

Подсказка `integrate_xcode_project` документирует каждую интеграцию Xcode, которую поддерживает Tuist:

| Возможность | Что настраивает агент |
|---------|---------------------------|
| `xcode_cache` | Настраивает `tuist setup cache`, параметры кэша сгенерированного проекта, ручные настройки сборки кэша Xcode и политику загрузки, ограниченную раннерами непрерывной интеграции. |
| `build_insights` | Настраивает `tuist inspect build`, `tuist xcodebuild`, `-resultBundlePath` и опциональные метрики машины через `tuist setup insights`. |
| `test_insights` | Настраивает `tuist inspect test`, пост-действия тестирования схем и генерацию бандлов результатов для запусков тестов в непрерывной интеграции. |
| `test_sharding` | Добавляет планирование шардов для Xcode или сгенерированного проекта и рабочий процесс выполнения шардов с `TUIST_SHARD_INDEX`. |

Если `features` опущен, подсказка просит агента уточнить, какие интеграции нужны пользователю, или вывести минимальный полезный набор из запроса перед редактированием проекта Xcode.
