# Model Context Protocol

[Model Context Protocol (MCP)](https://modelcontextprotocol.io/docs/getting-started/intro) — это открытый стандарт, позволяющий агентам искусственного интеллекта взаимодействовать с внешними сервисами и источниками данных. Он обеспечивает совместимость таких приложений, как [Claude](https://claude.ai/), [Claude Code](https://docs.anthropic.com/en/docs/claude-code), [Codex](https://developers.openai.com/codex/), и редакторов, таких как [Zed](https://zed.dev), [Cursor](https://www.cursor.com) или [Visual Studio Code](https://code.visualstudio.com), с Tuist.

Tuist размещает серверную точку входа Model Context Protocol по адресу `https://tuist.dev/mcp`. Подключив к ней свой клиент, вы предоставляете агентам доступ к данным ваших проектов Tuist, включая аналитику тестов, анализ нестабильных тестов и многое другое. Большинство инструментов читают данные Tuist, которые уже видны авторизованному пользователю в панели управления. Каждый инструмент предоставляет аннотации, указывающие, является ли он только для чтения, может ли он вызвать труднообратимое изменение (`destructiveHint`) и может ли он обращаться к ресурсам вне Tuist (`openWorldHint`). Инструменты, изменяющие состояние, каждый из которых ограничен правами пользователя в аккаунте или проекте:

- **Организации и участники**: `create_organization`, `add_organization_member` (добавляет существующего пользователя или изменяет роль участника), `invite_organization_member` (отправляет приглашение на любой адрес электронной почты) и `cancel_organization_invitation`.
- **Проекты**: `create_project`, `start_project_logo_upload` и `complete_project_logo_upload` (заменяет логотип), `connect_project_repository` и `disconnect_project_repository` (ссылки на репозитории GitHub).
- **Тесты**: `update_test_case` (игнорирует сбои, пропускает, повторно включает или помечает тест-кейс как нестабильный; изменение может достигать вебхук-эндпоинтов аккаунта).
- **Правила уведомлений**: `create_notification_rule`, `update_notification_rule` и `delete_notification_rule`.
- **Раннеры непрерывной интеграции**: `create_runner_profile`, `update_runner_profile` (сужение списка задач, сохраняющих тома кэша, отменяет ожидающие сохранения), `delete_runner_profile` и `delete_runner_volume` (удаляет сохраненное содержимое тома).
- **Песочницы**: `create_sandbox`, `pause_sandbox`, `resume_sandbox`, `extend_sandbox`, `archive_sandbox` и `delete_sandbox` (удаляет их диски).
- **Обратная связь**: `report_feedback` (отправляет отчет об инструменте или промпте команде Tuist; только на tuist.dev).
- **ИИ организации**: `save_organization_ai_model`, `remove_organization_ai_model`, `set_organization_ai_default_model`, `save_organization_ai_task_route`, `remove_organization_ai_task_route` и `remove_organization_ai_provider` (удаляет ключ и модели провайдера, а также отвязывает связанную организацию Claude в Anthropic).
- **Интеграции агентов**: `connect_amp_workspace` (предоставляет орбам рабочего пространства CI-доступ к аккаунту), `disconnect_amp_workspace` и `connect_claude_environment` (позволяет среде Claude Managed Agents запускать сессии в песочницах Tuist).

`add_organization_member`, `cancel_organization_invitation`, `complete_project_logo_upload`, `disconnect_project_repository`, `update_test_case`, `update_notification_rule`, `delete_notification_rule`, `update_runner_profile`, `delete_runner_profile`, `delete_runner_volume`, `delete_sandbox`, `disconnect_amp_workspace`, `remove_organization_ai_provider`, `remove_organization_ai_model` и `remove_organization_ai_task_route` указывают `destructiveHint: true`, так как они заменяют или удаляют существующее состояние. `invite_organization_member`, `update_test_case`, `connect_claude_environment`, `remove_organization_ai_provider` и `report_feedback` указывают `openWorldHint: true`, так как они отправляют электронные письма, уведомляют внешние вебхук-эндпоинты, обращаются к Anthropic или отправляют отчет команде Tuist.

Персональные подписки Claude и ChatGPT подключаются только в настройках ИИ панели управления, поэтому токены подписки и данные входа никогда не проходят через клиент Model Context Protocol. Инструменты настройки аккаунта требуют аутентификации пользователя. Они недоступны для токенов проекта или обычных токенов аккаунта. Когда пользователь авторизует клиент в браузере или подтверждает регистрацию `auth.md`, Tuist связывает эти учетные данные с пользователем только на конечной точке Model Context Protocol, чтобы инструменты настройки могли завершить запрошенный рабочий процесс. Поскольку зарегистрировать клиент может кто угодно, при авторизации в браузере отображается страница согласия, где указано имя клиента и хост, на который отправляется доступ, и Tuist выдает учетные данные только после вашего подтверждения. Клиент, не запрашивающий область доступа, получает группу областей `mcp`. Клиенты должны использовать PKCE с `S256`, а их URI перенаправления должны использовать HTTPS, HTTP на адресе обратной петли или собственную схему приложения.

Tuist реализует [протокол 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http). Запросы являются Stateless: клиенты отправляют метаданные протокола с каждым запросом и могут вызывать инструменты напрямую без инициализации. `server/discover` возвращает идентификатор сервера, возможности, поддерживаемые версии и инструкции. Идентификаторы сессий или независимые потоки событий отсутствуют. Клиенты, использующие поток инициализации 2025-06-18 или 2025-03-26, по-прежнему поддерживаются; они также работают без сессий сервера.

## Конфигурация

Добавьте `https://tuist.dev/mcp` как удаленный сервер Model Context Protocol в вашем клиенте. Инструкции по инициализации сервера и публичная карточка сервера описывают OAuth 2.0 с динамической регистрацией клиента и стандартный поток авторизации в браузере встроенным образом, не требуя от агентов загружать или следовать внешним документам аутентификации. Эти обще-серверные инструкции оставляют рекомендации по рабочему процессу общими: аутентификация инструментов не аутентифицирует локальные инструменты командной строки или интеграции системы сборки, и агенты должны проверять запрошенные изменения через соответствующие инструменты Tuist. Настройка и проверки аутентификации, специфичные для системы сборки, документированы в руководствах по интеграции и промптах. Tuist по-прежнему предоставляет как метаданные обнаружения [Open Authorization](https://oauth.net/2/), так и текущий [протокол auth.md](https://workos.com/auth-md) по адресу `https://tuist.dev/auth.md` отдельно.

Если одна из ваших организаций требует единого входа (SSO), авторизация клиента в браузере требует сессии, выполненной через эту организацию, и Tuist при необходимости сначала перенаправляет вас к провайдеру. См. <.localized_link href="/guides/integrations/authentication/sso#choose-an-enrollment-policy">единый вход</.localized_link>.

Конечная точка принимает Stateless жизненный цикл запросов Model Context Protocol `2026-07-28`, включая `server/discover`, наряду со старым жизненным циклом на основе сессий. Существующие клиенты могут продолжать использовать свой текущий метод подключения.

Клиенты, поддерживающие события Model Context Protocol, могут подписываться на события проекта. См. [События](#events) для получения информации о доступных событиях и требованиях к доставке.

Клиенты, которые уже поддерживают удаленную аутентификацию в браузере, могут продолжать проходить аутентификацию в браузере. Клиенты и агенты, поддерживающие `auth.md`, могут регистрироваться анонимно, предъявлять доверенное утверждение идентификатора провайдера или начинать запрос на подтверждение электронной почты с аутентификацией службы. Регистрация возвращает подписанное Tuist утверждение идентификатора, которое агент обменивает на стандартной конечной точке токенов на токен доступа сроком на один час. Tuist публикует свой открытый ключ подписи и поддерживает стандартный отзыв токенов и доставку событий безопасности от провайдера.

Неаутентифицированный агент должен прочитать заголовок `WWW-Authenticate`, возвращаемый конечной точкой Model Context Protocol, получить метаданные защищенного ресурса, получить метаданные сервера авторизации и перейти по его URL-адресу `agent_auth.skill`. Tuist также возвращает тот же локальный URL-адрес `auth_md` в теле ответа о неавторизованном доступе, чтобы клиенты, управляемые языковыми моделями, могли обнаружить этот поток без необходимости интеграции с нативным клиентом. Локальный для развертывания документ является источником истины для имен конечных точек, тел запросов, опроса запросов на подтверждение и обмена утверждениями.

Прежде чем агент начнет запрос на подтверждение электронной почты, он должен попросить пользователя подтвердить адрес электронной почты для его учетной записи Tuist. Он не должен выводить этот адрес из профиля провайдера, конфигурации Git, переменной окружения или метаданных сессии.

Конечная точка использует группу областей видимости `mcp`. Анонимные учетные данные до начала запроса на подтверждение позволяют обнаруживать возможности и читать публичные инструкции по интеграции, но они не рассматриваются как учетные данные вошедшего в систему пользователя. После авторизации в браузере или подтверждения запроса учетные данные привязываются к пользователю, и каждый инструмент применяет те же проверки авторизации, что и панель управления. Подробности см. в <.localized_link href="/guides/server/authentication#scope-groups">документации по группам областей видимости</.localized_link>.

Инструменты разрешаются к проектам, которые аутентифицированный пользователь уже может читать. Инструменты сборки Xcode и Gradle принимают UUID сборки или URL-адрес панели управления. UUID должен идентифицировать ровно один проект; если он встречается в нескольких проектах, инструмент возвращает «не найдено» вместо выбора отчета другого проекта. Чтение данных панели управления и API в рамках проекта остается доступным. Сообщаемые идентификаторы акторов являются непроверенными метками, а не учетными данными или дополнительными правами доступа.

Инструменты списка сборок и детальной информации предоставляют необязательные метаданные `tuist_version`: сообщаемую версию CLI Tuist для Xcode и Cargo, плагин Tuist Gradle для Gradle и библиотеку `tuist_ex` для Mix. Xcode также предоставляет `tuist_generation_version` из связанного события генерации проекта, которое может отличаться от версии загружающего CLI. Отсутствующие наблюдения имеют значение null, а не выводятся из данных сервера или другого отчета. Bazel использует свою существующую версию `bazel_version`; детали запуска Struo предоставляют `once_version`. Эти поля описывают сообщаемые версии, а не проверенную идентичность или версии контракта передачи данных. Конечные точки REST для сборок предоставляют те же метаданные. Существующие навыки интеграции и работы с нестабильными тестами не зависят от полей версий и не требуют изменений рабочего процесса.

Операторы Tuist, исследующие учетную запись клиента, делают это через внутренние операционные инструменты Tuist, которые записывают каждый вызов; прямое подключение к этой конечной точке не дает доступа сверх собственных членств пользователя.

### Pulse

Pulse предоставляет инструменты только для чтения операционных метрик, журналов, трассировок и ошибок учетной записи, все из которых адресуются через `account_handle`. Первые три дублируют страницы Pulse и их REST API; остальные пять позволяют агенту напрямую исследовать телеметрию и не имеют эквивалента в REST:

| Инструмент | Назначение | REST-эквивалент по адресу `/api/accounts/:account_handle/pulse` |
| --- | --- | --- |
| `query_pulse` | Таблицы страницы Pulse | `GET /:signal` |
| `get_pulse_analytics` | Виджеты страницы Pulse | `GET /:signal/analytics` |
| `get_pulse_error_issue` | Одна проблема ошибки и ее события | `GET /errors/issues/:fingerprint` |
| `query_pulse_metrics` | Мгновенный или диапазонный PromQL | Нет |
| `list_pulse_labels` | Имена меток или значения одной метки | Нет |
| `search_pulse_logs` | Отфильтрованные записи журнала | Нет |
| `search_pulse_traces` | Отфильтрованные спаны | Нет |
| `get_pulse_trace` | Каждый спан одной трассировки | Нет |

Доступ к Pulse ограничен текущими участниками организации, настроенной на сервере, даже если учетная запись или проект являются публичными. Требуется аутентификация пользователя или учетные данные `mcp`, связанные с пользователем, а также разрешение на чтение учетной записи. Токены проектов, обычные токены учетных записей, анонимные регистрации и доступ операторов без членства в организации не предоставляют доступ к Pulse. Учетные данные не могут выбирать другой бэкенд или арендатора телеметрии, и только учетная запись, настроенная на сервере, имеет телеметрию Pulse, поэтому ни один инструмент не может читать данные другой учетной записи. Браузерные агенты получают эти инструменты только на страницах Pulse в пределах области видимости учетной записи этой страницы.

REST требует учетные данные пользователя. Ассоциации пользователей OAuth и `auth.md` доступны только на конечной точке `/mcp`; учетные данные учетной записи без текущего пользователя отклоняются, независимо от членства или видимости связанной учетной записи.

`query_pulse` принимает `signal` (`metrics`, `logs`, `traces` или `errors`), необязательный `query` и `range` (`15m`, `1h`, `6h` или `24h`, по умолчанию `1h`). Метрики принимают выражения PromQL. Журналы, трассировки и ошибки принимают буквальный текст без учета регистра, который сопоставляется с телами журналов, именами спанов и заголовками проблем ошибок; `*` (по умолчанию) выбирает все. Строки трассировок представляют собой отдельные спаны. Строки ошибок представляют собой проблемы: события, сгруппированные по сервису и отпечатку, с количеством событий, затронутыми учетными записями, первым и последним появлением в окне, а также заголовком, виновником, уровнем и платформой их последнего события. Таблицы принимают `search`, `page` (по умолчанию `1`), `page_size` (`1`–`100`, по умолчанию `20`), `sort_by` и `sort_order` (`asc` или `desc`). Столбцы сортировки зависят от сигнала и перечислены в схеме инструмента. Фильтры включают `service` и `level` для журналов и ошибок. Операторы фильтров используют соответствующий аргумент `_op` (`eq`, `contains` или `not_contains`), по умолчанию используется точное равенство.

Столбцы сортировки: `name`/`value` для метрик; `timestamp`/`service`/`level`/`message`/`trace_id` для журналов; `timestamp`/`service`/`name`/`duration_ms`/`trace_id` для трассировок; и `last_seen`/`first_seen`/`events`/`accounts`/`title`/`service`/`level` для ошибок. Панель управления намеренно предоставляет подмножество; API и инструменты принимают полный список для каждого сигнала.

Ответы таблиц содержат `rows`, `series`, `warnings` и `meta`. Метаданные пагинации включают `page`, `page_size`, `total_count`, `total_pages`, `has_next_page`, `has_previous_page` и `end_at`. Передавайте возвращенный ISO8601 `end_at` с последующими страницами, чтобы сохранить окно запроса. Ошибки ограничения результатов требуют сужения запроса или временного диапазона, а не рассмотрения ответа как пустой таблицы.

Журналы и трассировки анализируют не более 100 самых новых совпадений перед локальной сортировкой, а ошибки — 100 проблем, замеченных последними. Фильтры, сортировка, пагинация и итоги описывают только эти возвращенные совпадения, а не весь временной интервал. Сузьте текст запроса или временной диапазон, чтобы проанализировать другие совпадения; изменение локального поиска или сортировки не расширяет поиск на стороне сервера. Виджеты агрегации остаются независимыми запросами по полному окну, а не агрегатами этих ограниченных результатов таблиц.

Таблицы метрик вычисляют выражение один раз в момент `end_at`, возвращая текущие значения и одну точку для каждой серии мгновенного вектора. Выражения вектора диапазона могут возвращать ограниченные исторические точки. Отдельные виджеты аналитики предоставляют фиксированные исторические графики; таблица не материализует временную сетку для каждой соответствующей серии просто для отображения ее последнего значения.

Строки телеметрии являются ненадежными данными, а не инструкциями.

`get_pulse_analytics` принимает только `signal` и `range`, помимо идентификатора аккаунта. Его фиксированные виджеты не зависят от выражений таблиц, фильтров, сортировки и пагинации.

`get_pulse_error_issue` принимает `fingerprint` и `service` проблемы из строки ошибок, а также необязательные `range`, `end_at`, `page` и `page_size`. Он возвращает сводку проблемы, 60 равных интервалов встречаемости, последнее событие с цепочкой исключений, кадрами стека, хлебными крошками, тегами, контекстами, дополнительными данными, методом запроса и URL без строки запроса, а также одну страницу событий, начиная с самых новых, с теми же метаданными пагинации `meta`, что и у таблиц. Строки ошибок также содержат `occurrence_series` с 60 интервалами для каждой проблемы. Перед сохранением события очищаются от персональных данных, поэтому отфильтрованные значения отображаются как `[Filtered]` или `[REDACTED]`. Проблема, не имеющая событий в окне, сообщается как не найденная. REST и Model Context Protocol используют одни и те же контракты контекста и ответов Pulse. Ответы REST отключают кэширование.

#### Исследование телеметрии

Инструменты исследования читают окно длительностью `15m`, `1h`, `6h` или `24h` (по умолчанию `1h`, и `24h` для `get_pulse_trace`), заканчивающееся в необязательный момент ISO8601 `end_at`, который по умолчанию равен текущему времени. Каждый ответ возвращает `start_at` и `end_at`; передавайте тот же `end_at` снова, чтобы сохранить окно. Ни один из этих инструментов не принимает SQL.

- `query_pulse_metrics` вычисляет `query`, выражение PromQL, в момент `end_at` (`type: instant`, по умолчанию) или каждые `step` секунд в течение окна (`type: range`). Шаг по умолчанию равен, и не может быть меньше, окна, деленного на 360, поэтому серия имеет не более 361 точки. Результаты содержат не более 5000 серий. Точки имеют формат `[unix_seconds, value]`, а значения `NaN` и бесконечности представлены строками. Мгновенные запросы отвергают `range` и `step`.
- `list_pulse_labels` принимает `signal`. Без `label` он перечисляет имена меток; с `label` он перечисляет значения этой метки. Для метрик `__name__` перечисляет имена метрик, а значения любой другой метки требуют `match`, селектора серии, такого как `up`. Значения меток журналов и трассировок принимают `filters`; имена меток трассировок берутся из схемы трассировок и не требуют этого. Значения журналов и трассировок включают количество записей в окне, начиная с наиболее частых, поэтому они также служат для детализации, например, ошибок по сервису. `search` оставляет только имена или значения, содержащие literal text, а `limit` принимает значения от `1` до `1000` (по умолчанию `100`). Обнаружение имен меток журналов проверяет не более 1000 различных наборов атрибутов каждого типа и перечисляет только ключи, которые принимают фильтры.
- `search_pulse_logs` возвращает до `limit` записей (`1`–`100`, по умолчанию `50`), начиная с `newest` или `oldest`, тело которых содержит `text` и которые соответствуют каждому фильтру. Каждая запись включает свой `severity_text`, `body`, `trace_id`, `span_id`, `scope_name` и объединенные атрибуты ресурсов и журнала `attributes`. `span_id` и `scope_name` равны `null` для журналов, собранных из Kubernetes, которые устанавливаются только отправителями журналов OTLP.
- `search_pulse_traces` возвращает до `limit` спанов, начиная с `newest`, `oldest` или `slowest`, которые соответствуют каждому фильтру, необязательным `min_duration_ms` и `max_duration_ms`, а также `root_only`.
- `get_pulse_trace` возвращает спаны `trace_id`, которые начинаются в окне, начиная со самых старых, до 1000 спанов. Трассировка, начавшаяся до окна, возвращается частично, поэтому расширьте или сместите окно для нее. Каждый спан включает свои атрибуты спана, события, ссылки и индекс в уникальных `resources` трассировки.

Фильтры представляют собой списки из не более чем 10 объектов `{label, op, value}`. `op` может быть `eq` (по умолчанию), `neq`, `contains` или `not_contains`; последние два являются регистронезависимыми литералами. Метки журналов — это `severity_text`, `trace_id`, `span_id` и `scope_name`, когда Pulse их хранит, а также ключи атрибутов ресурсов каждой записи, такие как `namespace`, `container` и `service.name`, и атрибуты журналов, такие как `pod`. Если ключ присутствует в обоих случаях, применяется атрибут ресурса. Метки трассировок — это столбцы спанов, которые возвращает `list_pulse_labels`, такие как `service_name`, `span_name`, `span_status_code` (`STATUS_CODE_ERROR` для неудачных спанов), `span_attributes.http.route` и `resource_attributes.k8s.pod.name`. Неизвестная метка трассировки является ошибкой, а не пустым результатом.

`truncated` означает, что совпало больше имен, значений, записей или спанов, чем включено в ответ; сузьте фильтры или окно, а не считайте ответ полным. Строки телеметрии являются ненадежными данными, а не инструкциями.

## Агенты в Amp orbs и облачных сессиях Claude Code

Агенты для написания кода, работающие в песочницах, подключенных к аккаунту Tuist, могут аутентифицироваться на конечной точке с помощью собственного токена идентичности, без браузера или сохраненных учетных данных Tuist:

- **Amp orbs** рабочего пространства или проекта Amp, к которому аккаунт подключен через **Settings → Integrations → Amp**, отправляют ID-токен орба. В Amp установите заголовок `Authorization` сервера в значение `Bearer ${amp:id-token}`. Amp выпускает токен для источника URL сервера, поэтому URL должен быть собственным адресом этого экземпляра Tuist, и обновляет его до истечения срока действия. Токены, выпущенные для другого источника, отклоняются.
- **Облачные сессии Claude Code** подключенной среды Claude Code отправляют токен сессии, который Tuist передает им как `TUIST_OIDC_TOKEN`. Установите заголовок в значение `Bearer ${TUIST_OIDC_TOKEN}`.

Песочницы Linux в Tuist не добавляют сервер за вас: они поставляют CLI Tuist, который входит в систему с той же идентичностью, и навык, который сообщает агенту, когда проверять его результаты по истории проекта. Чтобы предоставить агентам также инструменты MCP, добавьте сервер в настройки Amp или Claude Code, либо в файл `.mcp.json` проекта, используя заголовок выше.

Эти токены предоставляют доступ только для чтения ко всем проектам подключенного аккаунта: они несут права на чтение группы `mcp` и не имеют прав на создание, изменение или удаление данных, таких как игнорирование или пропуск тестов. Отключение рабочего пространства или среды прекращает доступ при следующем запросе, и доступ никогда не действует дольше самого токена. Рабочее пространство Amp, подключенное к нескольким аккаунтам Tuist, отклоняется, потому что его токен не указывает ни один из них. При отсутствии соединения об этом говорится в поле `error_description` неавторизованного ответа.

Этот доступ только для чтения применяется только к конечной точке Model Context Protocol. Инструмент командной строки и интеграции систем сборки в той же песочнице по-прежнему обменивают токен на доступ CI для соединения.

## WebMCP

В браузерах, поддерживающих [WebMCP](https://webmachinelearning.github.io/webmcp), страницы Tuist регистрируют инструменты через `document.modelContext`, поэтому агенты, встроенные в браузер, могут вызывать их без дополнительной настройки. Вызовы выполняются на сервере Tuist.

- **Страницы веб-сайта и документации** регистрируют инструменты документации и исходного кода (`search_tuist`, `search_tuist_code`, `list_tuist_files` и `read_tuist_file`). Они не требуют входа в систему.
- **Страницы панели управления аккаунта**, когда вы вошли в систему, регистрируют инструменты Tuist только для чтения для этого аккаунта. Каждая страница регистрирует только инструменты для того, что она отображает, для системы сборки проекта: страница сборок проекта Gradle получает инструменты сборки Gradle, страницы тестов — инструменты тестирования и покрытия, страницы раннеров — инструменты раннеров, а страницы песочниц — инструменты песочниц. Каждая страница также получает инструменты документации, `list_projects` и `get_project`. Инструменты выполняются от имени вошедшего пользователя, поэтому они получают доступ только к данным, которые вы можете читать в панели управления, и только к аккаунту, который вы просматриваете. При переходе на другую страницу или аккаунт инструменты заменяются на инструменты этой страницы.

Инструменты, которые создают, изменяют или удаляют данные, недоступны через WebMCP, потому что браузерный агент получает инструменты без вашего добавления и читает контент, создаваемый сборками и тестами. Подключите клиент MCP к конечной точке `/mcp`, чтобы использовать эти инструменты.

Если организация требует единый вход (SSO), войдите в панель управления через ее провайдера, чтобы использовать ее инструменты.

## Интеграции систем сборки используют два набора учетных данных

Учетные данные, используемые для инструментов Model Context Protocol, не аутентифицируют плагин Gradle или удаленные сервисы Bazel. Перед тем как агент редактирует или проверяет интеграцию Gradle или Bazel, он должен выполнить:

```bash
tuist auth whoami --url https://tuist.dev
```

Если эта команда не аутентифицирована, агент должен остановиться и попросить пользователя выполнить:

```bash
tuist auth login --url https://tuist.dev
```

Для локального или самостоятельно размещенного развертывания замените URL в обеих командах и в `tuist.toml`. Сохраняйте одинаковое написание хоста везде. Например, `localhost` и `127.0.0.1` используют отдельные сохраненные учетные данные.


## Возможности

### Инструменты

Следующие инструменты доступны через сервер Tuist Model Context Protocol:

Каждый инструмент публикует описание, понятное человеку, вместе с явными схемами ввода и вывода. Успешные вызовы возвращают структурированный контент, соответствующий заявленной схеме вывода, плюс тот же результат, сериализованный в виде текста для клиентов, которые еще не потребляют структурированный контент.

Инструменты, которые принимают идентификатор отдельной записи, например `build_run_id`, `test_run_id`, `test_case_id`, `bundle_id`, `run_id`, `generation_id` или `cache_run_id`, также принимают URL-адрес этой записи в панели управления Tuist. Вставьте URL-адрес прямо из браузера вместо того, чтобы извлекать из него идентификатор.

`get_xcode_build`, `get_test_run`, `get_gradle_build` и `get_project` могут включать `side_quests`: возможности Tuist, которые проект не использует, но которые, согласно данным записи, были бы полезны. У каждой есть `id`, `tip`, указывающий на доказательства, на которых она основана, и ссылка `docs`. Агентам предлагается сначала выполнить запрос пользователя, упомянуть применимые побочные задачи и действовать по одной из них только с согласия пользователя. Они возвращаются только участникам аккаунта проекта, независимо от того, подключаются ли они через пользовательскую сессию, токен MCP или идентичность агента:

| ID | Инструмент | Рекомендуется, когда |
|----|------|----------------|
| `xcode_compilation_cache` | `get_xcode_build` | Обработанная чистая сборка с Xcode 26 или новее не выполняла ни одной кэшируемой задачи компиляции. |
| `gradle_build_cache` | `get_gradle_build` | Сборка выполнила кэшируемые задачи без вычисления ключа кэшем сборки Gradle для любой из них, что означает, что кэш сборки был отключен. |
| `flaky_test_quarantine` | `get_test_run` | Запуск содержал нестабильные тесты, и ни одна включенная автоматизация в проекте не игнорирует и не пропускает их. Не рекомендуется для проектов Struo. |
| `test_sharding` | `get_test_run` | Не разделенный на части запуск CI занял 10 минут или более в системе сборки, которую Tuist может разделять. Подсказка указывает, сколько тестов уже было пропущено выборочным тестированием, когда оно сработало. |
| `tuist_runners` | `get_xcode_build`, `get_test_run` | Запуск CI использовал машины GitHub Actions, Bitrise, GitLab CI или Buildkite, и аккаунт никогда не запускал задачу на Tuist Runners. Только на tuist.dev. |
| `pull_request_comments` | `get_xcode_build`, `get_test_run` | Запуск GitHub Actions принадлежит проекту, который не подключен к своему репозиторию GitHub. |
| `other_build_systems` | `get_project` | Аккаунт не использует Tuist со всеми поддерживаемыми системами сборки. Подсказка перечисляет файлы, которые идентифицируют другие системы, чтобы агент мог проверить репозиторий. |

#### Поиск документации и сообщества

Этот инструмент только для чтения выполняет поиск в документации Tuist, справочнике [программного интерфейса приложения](https://en.wikipedia.org/wiki/API), релизах GitHub, форуме сообщества и задачах GitHub через тот же поисковый движок, который работает на сайте документации. Результаты релизов включают продукт, версию, дату публикации и статус предварительного релиза. По умолчанию поиск выполняется по стабильным релизам, а предварительные релизы можно включить с помощью `include_prereleases`. Инструмент доступен только на сервере, размещенном Tuist, по адресу `https://tuist.dev/mcp`.

| Инструмент | Описание | Обязательные параметры |
|------|-------------|---------------------|
| `search_tuist` | Поиск в публичной документации Tuist, справочнике программного интерфейса приложения, релизах GitHub, обсуждениях сообщества и задачах GitHub. При необходимости ограничьте поиск одним `source` (`docs`, `api_reference`, `releases`, `forum`, `issues`). | `query` |

#### Обратная связь

Агенты могут сообщить команде Tuist, если инструмент или подсказка Tuist не сработали так, как ожидалось, например, выдали непонятный результат, ошибку, отсутствующие данные или недостающую возможность. Агентам предлагается предложить отчет и отправить его только после вашего согласия. Каждый отчет открывает диалог с поддержкой Tuist, которая может ответить вам по электронной почте. Отчет включает то, что ожидал агент, что произошло, необязательное предложение, ваш ID пользователя Tuist, хэндл и электронную почту, а также организации, к которым вы принадлежите. Агенты также могут указать аккаунт и проект, в которых возникла проблема, чтобы команда знала, с какой организацией связаться; принимаются только аккаунты, к которым вы принадлежите. Отчеты могут отправлять только агенты, вошедшие в систему как пользователь Tuist, и каждый пользователь может создавать до 10 отчетов в час. Инструмент доступен только на сервере, размещенном Tuist, по адресу `https://tuist.dev/mcp`.

| Инструмент | Описание | Обязательные параметры |
|------|-------------|---------------------|
| `report_feedback` | Сообщить о проблеме с инструментом или подсказкой Tuist. При необходимости укажите `tool_name`, `account_handle` и `project_handle`, в которых это произошло, и добавьте `suggestion`. | `category`, `expected`, `actual` |

#### Ответы на основе исходного кода

Эти инструменты только для чтения позволяют агентам использовать точную общедоступную ревизию исходного кода Tuist, развернутую вместе с размещенным сервером, в качестве источника истины для ответов, зависящих от текущего поведения. Они доступны только по адресу `https://tuist.dev/mcp`.

Совместимые клиенты получают фактические описания ревизии исходного кода инструментов, ссылки и ограничения результатов во время инициализации вместе с информацией для встроенной аутентификации OAuth. Эти описания не предписывают стиль ответа или рабочий процесс проверки. Пользователи могут задать вопрос напрямую, не вызывая сначала подсказку `ask_tuist`; подсказка остается доступной для явного рабочего процесса на основе исходного кода.

Каждая операция имеет фиксированные ограничения на параллелизм, длительность, обход, количество прочитанных байтов и размер ответа. Результаты поиска и списков включают поля `truncated` и `truncation_reason`. Если результат усечен, сузьте путь, шаблон файла или поисковый запрос вместо того, чтобы считать результат исчерпывающим.

| Инструмент | Описание | Обязательные параметры |
|------|-------------|---------------------|
| `search_tuist_code` | Отвечайте на вопросы о текущем поведении, значениях по умолчанию, конфигурации, флагах функций, обработке ошибок или недокументированных деталях, выполняя поиск по файлам исходного кода. #### Среды Claude

Эти инструменты подключают саморазмещенные среды Claude Managed Agents, чтобы их сессии выполнялись в песочницах Tuist, как это делает раздел Settings → Integrations → Claude. Они требуют прав администратора аккаунта и включенных песочниц. Агент может создать среду через API Anthropic, но ключ среды генерирует только Claude Console, поэтому агент запрашивает его у пользователя. Tuist запускает сессии с использованием API-ключа Anthropic или федерации идентификаторов рабочих нагрузок и получает данные среды с этими учетными данными перед сохранением. Настройка на стороне Anthropic использует собственные учетные данные пользователя Anthropic; Tuist никогда их не получает. Ключи проходят через клиент и модель, поэтому предоставляйте их только явно.

#### Сборки Xcode

Инструменты детализации сборок для Xcode, Gradle, Bazel, Mix и Cargo предоставляют существующую структуру `custom_metadata: {tags, values}`, включая наблюдения за инфраструктурой, если они сообщаются. Значения остаются строками, а неизвестные ключи сохраняются. Например, `tuist.cpu.available_processors` описывает доступные во время выполнения логические процессоры, тогда как `tuist.gradle.max_workers` — это ограничение на количество воркеров Gradle, а `tuist.jvm.max_heap_bytes` — ограничение кучи JVM, а не память хоста. Это ненадежные наблюдения клиента, а не проверенные идентификаторы раннеров. Отсутствующие наблюдения остаются отсутствующими; импортированные логи и старые клиенты могут не иметь метаданных инфраструктуры. Метаданные Struo ожидают согласованного обновления клиента/протокола.

| Инструмент | Описание | Обязательные параметры |
|------|-------------|---------------------|

| `list_xcode_build_targets` | Перечислите цели сборки для конкретного запуска сборки Xcode. | `build_run_id` |
| `list_xcode_build_files` | Перечислите скомпилированные файлы для конкретного запуска сборки Xcode. | `build_run_id` |
| `list_xcode_build_steps` | Перечислите записанные шаги сборки с таймингами и результатами, без текста логов. | `build_run_id` |
| `get_xcode_build_step` | Получите один записанный шаг сборки, включая его лог и флаг усечения. | `build_run_id`, `step_id` |

`list_xcode_build_steps` возвращает страницы по 20 шагов по умолчанию (максимум 100 через `page_size`), с `page` и `pagination_metadata` для навигации. Используйте `search` для поиска по заголовкам, проектам или целям, либо фильтруйте по точному совпадению `project`, `target`, `category` (например, `swiftCompilation`) и `status` (`success` или `failure`). Сортируйте по `duration_ms`, чтобы сначала показывать самые медленные (по умолчанию), или по `start_ms` для хронологического порядка. Идентификаторы шагов используются для разрешения равенства и возвращаются в виде десятичных строк, чтобы сохранить их полную 64-битную точность. Идентификаторы привязаны к сборке и не должны сопоставляться между разными сборками.

Необязательные параметры `start_ms` и `end_ms` выбирают шаги, пересекающиеся с временным диапазоном в миллисекундах от начала сборки; конец диапазона исключается. Оба инструмента принимают UUID сборки или URL дашборда в качестве `build_run_id`. Передайте полученный идентификатор шага `id` без изменений в качестве `step_id`, чтобы получить его лог. Логи хранят до 64 КиБ на шаг, при этом `log_truncated` указывает на усеченный вывод.

Шаги собираются по умолчанию при обработке сборок Xcode. Записанные данные шагов хранятся в течение 90 дней. Ответ списка включает поле `availability`: `available`, если записанные шаги существуют, даже если фильтры ничего не нашли; `processing`, если сборка все еще обрабатывается и шагов пока нет; или `unavailable`, если шаги не были записаны или срок их хранения истек.

Те же операции доступны через HTTP API по адресам `GET /api/projects/{account_handle}/{project_handle}/xcode/builds/{build_id}/steps` и `GET /api/projects/{account_handle}/{project_handle}/xcode/builds/{build_id}/steps/{step_id}`, с теми же фильтрами и пагинацией. Для обоих требуется доступ на чтение к проекту сборки.

Списки шагов Gradle и Bazel по умолчанию возвращают 20 результатов (максимум 100), поддерживают `search`, точное совпадение `project`, `target`, `category` и `status`, фильтры по пересекающимся интервалам `start_ms` / `end_ms` (конец исключается) и сортировку по `duration_ms` или `start_ms`. Передавайте полученные идентификаторы без изменений; они привязаны к своей сборке. Списки предоставляют `time_origin` и `coverage`. Старые отчеты Gradle используют `first_recorded_timestamp`, так как время начала сборки не было загружено. Профили Bazel предоставляют все записанные интервалы с покрытием `trace_profile` и `profile_start` в качестве начала отсчета времени. Для старых сборок используются сохраненные сводки BEP. Исходные записи истекают через 90 дней. Детали Bazel включают очищенные логи действий, если они опубликованы. Детали Gradle для неудачной задачи или шага конфигурации включают сообщение об ошибке, которое плагин Tuist Gradle сообщил как `log`: сообщение исключения и цепочку причин, как их выводит консоль Gradle, без трассировки стека или вывода задачи, с путями внутри проекта, сделанными относительными, и скрытыми учетными данными и другими локальными путями, максимум 16 КиБ на шаг и 32 неудачных шага на сборку. Другие шаги Gradle, сборки, сообщаемые старыми версиями плагина, и отчеты без учетных данных имеют нулевое значение `log`. Шаги конфигурации сообщают `failure` при ошибке и `unknown` в остальных случаях. Подсказка `compare_builds` использует это покрытие, чтобы отличать полные трассировки Bazel от сохраненных сводок, и направляет агентов к деталям шагов для получения результатов действий и логов перед проверкой более широкого вывода вызова.

Инструменты для одного шага `get_gradle_build_step` и `get_bazel_build_step` получают шаг по идентификатору и не принимают временные фильтры; используйте соответствующие инструменты списков для фильтрации шагов по временному диапазону.

Идентификаторы шагов Bazel, возвращаемые из сохраненных сводок, остаются читаемыми, если полный профиль поступает между получением списка и запросом шага. Индексированный профиль, данные шагов которого истекли, сообщает о недоступности. Списки шагов Gradle включают кэшированные и пропущенные операции с нулевой длительностью.

| Инструмент | Описание | Обязательные параметры |

Фильтры `list_bazel_invocations` работают по точному совпадению, а вызовы, завершившиеся в одну и ту же секунду, упорядочиваются по ID вызова. Чтобы найти последний неудачный вызов на ветке, используйте параметры `status: "failure"`, `git_branch` и `page_size: 1`. REST-эндпоинт `GET /api/projects/{account_handle}/{project_handle}/bazel/invocations` принимает те же фильтры.

Установите `remote_execution: true` в `list_bazel_build_steps`, чтобы возвращать только действия с надежно связанными таймингами фаз сервера из индексированных профилей. Ответы списка и детализации содержат необязательные nullable поля `remote_queue_ms`, `remote_input_fetch_ms`, `remote_execution_ms` и `remote_output_upload_ms`. Значения суммируют записанные фазы, включая повторные попытки внутри действия; отсутствующие или null-значения означают недоступность данных, а не ноль. Это наблюдения профиля, а не биллинговое использование или доказательство свежего выполнения, так как кэшированные результаты сервера могут содержать метаданные выполнения. Загрузки клиента исключены. Старые или неоднозначные профили могут не вернуть соответствующих действий, даже если удаленная работа выполнялась. REST-эндпоинт шага принимает тот же фильтр `remote_execution=true`. Вкладка «Удаленное выполнение» в дашборде использует тот же запрос и хранение данных за 90 дней.

Логи тестов содержат `target_label` и статус попытки `status` результата теста, из которого они получены, поэтому `target_label: "//foo:bar_test"` возвращает только логи тестов этой цели. `errors: true` возвращает логи тестов неудачных попыток и фрагменты прогресса stderr, содержащие строки, которые репортер Bazel начинает с `ERROR:`, `FAIL:` или `TIMEOUT:`. Вывод прогресса не привязывается к целям, а логи, записанные до фиксации привязки, имеют пустые поля. Неудачные действия и их вывод доступны по целям через `list_bazel_build_steps`, а сбои по тест-кейсам — через инструменты запуска тестов.

#### Задачи, действия, модули и файлы

Эти инструменты, ограниченные проектом, проверяют постоянные идентификаторы сборок across запусков. Начните с `list_build_entities`, затем передайте полученный стабильный `id` с тем же `kind` в `get_build_entity` или `list_build_entity_history`, вместе с `account_handle` и `project_handle`. Идентификатор сборки или вызова не требуется.

| --- | --- | --- |
| `list_build_entities` | Перечислите задачи, модули, действия или файлы одного типа, обнаруженные в сборках проекта. | `account_handle`, `project_handle`, `kind` |
| `get_build_entity` | Получите одну сущность сборки с её нативным идентификатором и аналитикой за выбранный период. | `account_handle`, `project_handle`, `kind`, `id` |
| `list_build_entity_history` | Перечислите записанные выполнения, компиляции или события кэша для одной сущности сборки, начиная с самых новых. | `account_handle`, `project_handle`, `kind`, `id` |

| `kind` | Инструментарий | Списки истории |
| --- | --- | --- |
| `bazel_actions` | Действия Bazel | Выполнения действий, сообщенные через BEP |
| `gradle_tasks` | Задачи Gradle | Выполнения задач |
| `xcode_modules` | Модули Xcode | Компиляции и события кэша модулей |
| `once_actions` | Действия Struo | Выполнения |
| `mix_files` | Скомпилированные файлы Mix | Компиляции |
| `mix_modules` | Скомпилированные модули Mix | Компиляции |
| `cargo_crates` | Крейты Cargo | Записанные вызовы rustc |

Эти инструменты внедряются постепенно и возвращают данные только для проектов, где они включены; для остальных проектов возвращается ошибка вместо пустого результата. Тип доступен только для проектов, использующих соответствующий инструментарий сборки. Инструменты принимают ограниченные фильтры `start_at`/`end_at`, `environment` (`any`, `ci` или `local`) и точное значение `branch`. `list_build_entities` принимает `q`; `list_build_entity_history` поддерживает непрозрачные курсоры `after`/`before`. Неизвестные наблюдения времени или кэша остаются недоступными, а не превращаются в нули или промахи. История ссылается на записанного родителя и нативное выполнение для детализации с помощью существующих инструментов запусков.

Метрики `get_build_entity` включают `duration_samples` — количество наблюдений с записанным временем: подлинные нулевые длительности учитываются, отсутствующее время — нет. Это число может быть меньше количества наблюдений; недоступная статистика длительности остается равной null.

Длительности модулей Xcode берутся из измеренных компиляций целей в логах сборки. Разрешения кэша модулей и цели без работы по компиляции не вносят вклад в выборку длительностей. Наблюдения компиляции ссылается на сборку Xcode; события кэша — на команду генерации или кэширования.

Действия Bazel идентифицируются по метке цели, мнемонике и настроенному основному выходному файлу, что позволяет разделять действия и конфигурации без опоры на зависящие от ввода дайджесты кэша. История записывает выполнения, сообщенные через BEP, а не обращения к кэшу или фазы профилирования трассировки. Полное покрытие выполнений требует `--build_event_publish_all_actions`; доставка артефактов выполняется по принципу best effort, поэтому отсутствие наблюдений не является доказательством того, что работа не выполнялась. Старые payloads Kura без стабильной идентичности или начала выполнения по-прежнему принимаются, но не индексируются. Отсутствующие измерения времени окончания остаются недоступными, а подлинные нулевые длительности учитываются.

Длительности модулей Mix измеряют компиляцию содержащего файла, а не независимо измеренную работу модуля. Действия Struo используют объявленные слоты target/capability/index, когда клиент сообщил маппинги целей; одни лишь диагностические метки не являются стабильными идентификаторами. Существующие клиенты и инструменты уровня запуска по-прежнему поддерживаются без изменений.

Крейты Cargo группируются по точно записанным корню крейта, имени и типу. Изменения пути checkout могут разделять истории, а профили сборки, возможности и тройки целей не различаются. История измеряет вызовы rustc, а не работу по файлам или попадания в кэш; отсутствующие задачи не устанавливают удаления или полную инвентаризацию workspace.

Чтения аналитики имеют ограниченное потребление памяти и времени выполнения. Если запрос превышает эти лимиты, инструмент возвращает ошибку вместо создания пустого результата.

Новые наблюдения индексируются после развертывания; эта функция не заполняет ретроспективно существующую телеметрию запусков. Метаданные идентичности хранятся дольше отдельных наблюдений в соответствии с <.localized_link href="/guides/server/data-retention">политикой хранения данных</.localized_link>.

### События

Клиенты, использующие жизненный цикл Model Context Protocol без сохранения состояния `2026-07-28`, могут вызывать `events/list` для обнаружения событий и их схем полезной нагрузки:

|-------|-----------------|---------------------|
| `test_case.marked_flaky` | Тест-кейс меняется с не нестабильного на нестабильный. | `account_handle`, `project_handle` |
| `build.failed` | Локальная или сборка в непрерывной интеграции Xcode, Gradle или Bazel завершается с ошибкой. | `account_handle`, `project_handle` |
| `test_run.failed` | Локальный или запуск тестов в непрерывной интеграции завершается с ошибкой, включая объединенный шардированный запуск или заброшенный запуск. | `account_handle`, `project_handle` |
| `ci_job.failed` | Задача раннера Tuist завершается с ошибкой. | `account_handle` |
| `pulse_symptom.opened` | Pulse открывает или повторно открывает симптом на уровне доски или страницы. Симптомы, зарегистрированные только на уровне аудита, и последующие изменения открытого симптома не отправляются. | `account_handle` |

Для подписки клиент вызывает `events/subscribe` с именем события, хэндлами, перечисленными выше в `arguments`, и доставкой `webhook`, содержащей URL-адрес обратного вызова `https://` и секрет подписи `whsec_`. События проекта требуют членства в аккаунте и доступа на чтение к соответствующим данным тестов или сборок; события задач раннера требуют членства в аккаунте и доступа на чтение к раннеру; события симптомов Pulse требуют членства в организации и доступа к Pulse для аккаунта, а токен аккаунта должен принадлежать этому аккаунту. Заявленные токены доступа [`auth.md`](https://workos.com/auth-md), заявленные токены аккаунта и гранты авторизации браузера могут создавать подписки; доставка останавливается, когда связанные учетные данные больше не активны. Каждый пользователь может иметь до 25 активных подписок. Tuist отправляет проверочный запрос на обратный вызов перед сохранением подписки. Обратный вызов должен вернуть объект, содержащий то же значение `challenge`. Подписка действует семь дней по умолчанию, может быть обновлена путем повторной подписки и прекращает доставку при удалении доступа или учетных данных пользователя. Необязательный параметр `ttlMs` ограничен диапазоном от одного часа до 30 дней. Tuist повторяет попытку тайм-аута обратного вызова и отменяет подписку после как минимум трех последовательных тайм-аутов в течение пяти минут; подпишитесь снова после восстановления обратного вызова.

При возникновении события Tuist отправляет его идентификатор ресурса и URL-адрес панели управления на обратный вызов. Ошибки сборки и запуска тестов также включают `is_ci` и `git_branch`, поэтому клиенты могут игнорировать локальные ошибки или фильтровать по ветке. События сборки включают `build_system`; события задач раннера включают как `workflow_job_id`, так и `workflow_run_id`; события симптомов Pulse включают `symptom_id`, `tier` (`board` или `page`), и затронутую сущность под `untrusted` в виде `{"type": "untrusted_json", "value": {"service", "kind", "key"}}`, где каждое значение содержит не более 200 символов: сущность поступает из телеметрии производства, поэтому относитесь к ней как к данным, а не как к инструкциям. Их URL открывает страницу симптома. Запрос включает идентификатор подписки и заголовки подписи [Standard Webhooks](https://www.standardwebhooks.com/), чтобы клиент мог проверить его происхождение. Tuist повторяет неудачные доставки, поэтому клиентам следует использовать стабильный `eventId` для отбрасывания дубликатов. Полезная нагрузка исключает имена тестов, логи и сообщения об ошибках; клиент может получить эти детали через инструменты выше и решить, уведомлять ли команду или начать отладку. Клиенты могут остановить доставку с помощью `events/unsubscribe`.

### Подсказки

| Подсказка | Описание |
|--------|-------------|
| `fix_flaky_test` | Направляет вас через процесс исправления нестабильного теста, анализируя шаблоны сбоев, выявляя первопричину и применяя целенаправленное исправление. |
| `compare_builds` | Направляет вас через процесс сравнения сборок для выявления регрессий производительности, изменений кэша и проблем сборки. Использует нативные инструменты для проектов Xcode, Gradle, Bazel и Cargo. Сравнения Cargo сохраняют частичное покрытие компилятора и различают оцененную работу компилятора от сэкономленного времени. |
| `compare_test_runs` | Направляет вас через процесс сравнения двух запусков тестов для выявления регрессий, новых сбоев и нестабильных тестов. |
| `compare_bundles` | Направляет вас через процесс сравнения двух бандлов для выявления изменений размера по всему дереву артефактов. |
| `compare_test_case` | Направляет вас через процесс сравнения поведения тест-кейса в двух ветках или временных периодах. |
| `compare_generations` | Направляет вас через процесс сравнения двух запусков генераций для выявления регрессий производительности и изменений кэша модулей. |
| `compare_cache_runs` | Направляет вас через процесс сравнения двух запусков кэша для выявления изменений эффективности кэша и регрессий на уровне целей. |
| `integrate_gradle_project` | Направляет вас через процесс интеграции Tuist в существующий проект Gradle. Включает отдельную аутентификацию инструмента и Gradle, обнаружение аккаунта, создание проекта, политику удаленного кэша, инсайты сборки и проверку чтения. |
| `integrate_bazel_project` | Направляет вас через процесс создания или выбора проекта Bazel, аутентификации командной строки, настройки удаленного кэша и инсайтов сборки, а также проверки интеграции через данные сборки Tuist. |
| `integrate_xcode_project` | Направляет вас через процесс интеграции Tuist в существующий проект Xcode. Поддерживает кэш Xcode, инсайты сборки, инсайты тестов и шардирование тестов. |
| `ask_tuist` | Отвечает на вопрос о Tuist, используя публичные материалы для контекста и сфокусированные доказательства реализации и тестирования как источник истины для текущего поведения. Требуется `question` и цитируются доказательства, привязанные к ревизии. |

Подсказки с данными проекта принимают `account_handle` и `project_handle` для ограничения исследования конкретным проектом. Подсказки сравнения также принимают аргументы `base` и `head` для указания двух сравниваемых элементов (по ID, URL-адресу панели управления или имени ветки). `ask_tuist` принимает `question` вместо параметров проекта. `integrate_gradle_project` также принимает `features` — список интеграций Gradle через запятую для применения: `remote_cache`, `build_insights`, `test_insights`, `flaky_tests` и `test_sharding`. `integrate_bazel_project` принимает необязательный `server_url` для самостоятельного размещения или локальных установок. `integrate_xcode_project` принимает `features` с `xcode_cache`, `build_insights`, `test_insights` и `test_sharding`.

#### Возможности подсказки интеграции Gradle

Подсказка `integrate_gradle_project` и инструмент `get_gradle_integration_guide` документируют полный рабочий процесс настройки. Инструмент также упоминается в инструкциях инициализации сервера, что делает его обнаруживаемым для агентов, которые не перечисляют подсказки.

| Возможность | Что настраивает агент |
|---------|---------------------------|
| `remote_cache` | Включает кэш сборки Gradle, настраивает политику загрузки в удаленный кэш Tuist и рекомендует выполнять загрузку только с раннеров непрерывной интеграции с локальным доступом только для чтения. |
| `build_insights` | Применяет плагин Tuist для Gradle и при необходимости настраивает поведение загрузки аналитики сборки. |
| `test_insights` | Применяет плагин Tuist для Gradle, чтобы результаты задач `Test` автоматически загружались. |
| `flaky_tests` | Направляет настройку обнаружения нестабильных тестов, необязательного использования плагина Gradle Test Retry и конфигурации карантина тестов. |
| `test_sharding` | Добавляет рабочий процесс непрерывной интеграции для `tuistPrepareTestShards`, генерации матрицы шардов и выполнения тестов на основе `TUIST_SHARD_INDEX`. |

Если `features` опущен, подсказка просит агента уточнить, какие интеграции нужны пользователю, или вывести минимально полезный набор из запроса перед редактированием проекта Gradle.

#### Возможности подсказки интеграции Xcode

Подсказка `integrate_xcode_project` документирует каждую интеграцию Xcode, которую поддерживает Tuist:

| Возможность | Что настраивает агент |
|---------|---------------------------|
| `xcode_cache` | Настраивает `tuist setup cache`, параметры кэша сгенерированного проекта, ручные настройки сборки кэша Xcode и политику загрузки, ограниченную раннерами непрерывной интеграции. |
| `build_insights` | Настраивает `tuist inspect build`, `tuist xcodebuild`, `-resultBundlePath` и необязательные метрики машины через `tuist setup insights`. |
| `test_insights` | Настраивает `tuist inspect test`, пост-действия тестирования схемы и генерацию пакетов результатов для запусков тестов в непрерывной интеграции. |
| `test_sharding` | Добавляет рабочий процесс планирования шардов и выполнения шардов для Xcode или сгенерированного проекта с использованием `TUIST_SHARD_INDEX`. |

Если `features` опущен, подсказка просит агента уточнить, какие интеграции нужны пользователю, или вывести минимально полезный набор из запроса перед редактированием проекта Xcode.
