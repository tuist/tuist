# Model Context Protocol

[Model Context Protocol (MCP)](https://modelcontextprotocol.io/docs/getting-started/intro) — это открытый стандарт, позволяющий агентам искусственного интеллекта взаимодействовать с внешними сервисами и источниками данных. Он обеспечивает совместимость таких приложений, как [Claude](https://claude.ai/), [Claude Code](https://docs.anthropic.com/en/docs/claude-code), [Codex](https://developers.openai.com/codex/), и редакторов, таких как [Zed](https://zed.dev), [Cursor](https://www.cursor.com) или [Visual Studio Code](https://code.visualstudio.com), с Tuist.

Tuist размещает серверную точку доступа Model Context Protocol по адресу `https://tuist.dev/mcp`. Подключив к ней свой клиент, агенты смогут получать доступ к данным вашего проекта Tuist, включая аналитику тестов, анализ нестабильных тестов и многое другое. Большинство инструментов работают только в режиме чтения и ограничены данными проектов Tuist, требующими аутентификации. Инструменты настройки аккаунта позволяют просматривать список аккаунтов, создавать организации, создавать проекты и добавлять существующих пользователей в организации, если у аутентифицированного пользователя есть необходимые разрешения. Каждый инструмент содержит аннотации, указывающие, работает ли он только в режиме чтения, может ли он вызвать изменения, которые трудно отменить, и может ли он изменить состояние в публичном интернете. `update_runner_profile`, `update_notification_rule` и `connect_claude_subscription` помечены как `destructiveHint: true`, поскольку они могут заменять существующую конфигурацию или учетные данные. Инструменты настройки аккаунта требуют аутентификации пользователя. Они недоступны для токенов проектов или обычных токенов аккаунтов. Когда пользователь авторизует клиент в браузере или подтверждает регистрацию через `auth.md`, Tuist связывает эти учетные данные с пользователем только на точке доступа Model Context Protocol, чтобы инструменты настройки могли завершить запрошенный рабочий процесс.

Tuist реализует [протокол версии 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http). Запросы являются Stateless: клиенты отправляют метаданные протокола с каждым запросом и могут вызывать инструменты напрямую без инициализации. `server/discover` возвращает идентификатор сервера, его возможности, поддерживаемые версии и инструкции. Идентификаторы сессий или независимые потоки событий отсутствуют. Клиенты, использующие поток инициализации версий 2025-06-18 или 2025-03-26, по-прежнему поддерживаются; они также работают без серверных сессий.

## Model Context Protocol против навыков (skills)

Функциональность инструментов Model Context Protocol и <.localized_link href="/guides/features/agentic-coding/skills">навыков (skills)</.localized_link> может пересекаться. Учитывая текущее перекрытие между ними, выбирайте один подход для каждого рабочего процесса и используйте его последовательно, вместо того чтобы смешивать оба подхода в одном потоке.

Для клиентов, поддерживающих установку плагинов, используйте <.localized_link href="/guides/features/agentic-coding/plugins">плагины Tuist</.localized_link>, чтобы установить их вместе.

## Конфигурация

Добавьте `https://tuist.dev/mcp` в качестве удаленного сервера Model Context Protocol в вашем клиенте. Инструкции по инициализации сервера и публичная карточка сервера описывают OAuth 2.0 с динамической регистрацией клиента и стандартный поток авторизации в браузере непосредственно в интерфейсе, не требуя от агентов загружать или следовать внешним документам аутентификации. Эти общие для всего сервера инструкции сохраняют рекомендации по рабочему процессу универсальными: аутентификация инструментов не аутентифицирует локальные инструменты командной строки или интеграции со системами сборки, и агенты должны проверять запрашиваемые изменения через соответствующие инструменты Tuist. Настройка, специфичная для системы сборки, и проверки аутентификации документированы в руководствах по интеграции и промптах. Tuist по-прежнему отдельно предоставляет метаданные обнаружения [Open Authorization](https://oauth.net/2/) и текущий [протокол auth.md](https://workos.com/auth-md) по адресу `https://tuist.dev/auth.md`.

Если одна из ваших организаций требует единого входа (SSO), авторизация клиента в браузере требует сессии, выполненной через эту организацию, и Tuist при необходимости сначала перенаправляет вас к провайдеру. См. <.localized_link href="/guides/integrations/authentication/sso#choose-an-enrollment-policy">единый вход (SSO)</.localized_link>.

Точка доступа поддерживает Stateless жизненный цикл запросов Model Context Protocol версии `2026-07-28`, включая `server/discover`, наряду со старым жизненным циклом на основе сессий. Существующие клиенты могут продолжать использовать свой текущий метод подключения.

Клиенты, поддерживающие события Model Context Protocol, могут подписываться на события проекта. См. раздел [События](#events) для получения информации о доступных событиях и требованиях к доставке.

Клиенты, которые уже поддерживают удаленную аутентификацию в браузере, могут продолжать аутентифицироваться в браузере. Клиенты и агенты, поддерживающие `auth.md`, могут регистрироваться анонимно, предоставлять доверенное утверждение идентичности провайдера или начинать запрос подтверждения электронной почты с аутентификацией сервиса. Регистрация возвращает утверждение идентичности, подписанное Tuist, которое агент обменивает на стандартной точке доступа токенов на часовой токен доступа. Tuist публикует свой открытый ключ подписи и поддерживает стандартное аннулирование токенов и доставку событий безопасности от провайдера.

Неаутентифицированный агент должен прочитать заголовок `WWW-Authenticate`, возвращаемый точкой доступа Model Context Protocol, получить метаданные защищенного ресурса, получить метаданные сервера авторизации и перейти по его URL `agent_auth.skill`. Tuist также возвращает тот же локальный URL `auth_md` в теле ответа об отказе в доступе, чтобы клиенты, управляемые языковыми моделями, могли обнаружить этот поток без reliance на нативную интеграцию клиента. Локальный для развертывания документ является источником истины для имен точек доступа, тел запросов, опроса подтверждений и обмена утверждениями.

Прежде чем агент начнет запрос подтверждения электронной почты, он должен попросить пользователя подтвердить адрес электронной почты для его аккаунта Tuist. Он не должен определять этот адрес из профиля провайдера, конфигурации Git, переменной окружения или метаданных сессии.

Точка доступа использует группу областей видимости `mcp`. Анонимные учетные данные до подтверждения могут обнаруживать возможности и читать публичные руководства по интеграции, но они не рассматриваются как вошедший в систему пользователь. После авторизации в браузере или подтверждения, учетные данные привязываются к пользователю, и каждый инструмент применяет те же проверки авторизации, что и панель управления. Подробности см. в <.localized_link href="/guides/server/authentication#scope-groups">документации по группам областей видимости</.localized_link>.

Инструменты разрешаются к проектам, которые аутентифицированный пользователь уже может читать. Инструменты сборки Xcode и Gradle принимают UUID сборки или URL панели управления. UUID должен идентифицировать ровно один проект; если он встречается в нескольких проектах, инструмент возвращает ошибку «не найдено» вместо выбора отчета другого проекта. Чтение данных панели управления и API в scope проекта остается доступным. Сообщаемые идентификаторы акторов являются непроверенными метками, а не учетными данными или дополнительными правами доступа.

Инструменты списка сборок и деталей сборки предоставляют необязательные метаданные `tuist_version`: CLI Tuist для Xcode и Cargo, плагин Tuist Gradle для Gradle и библиотека `tuist_ex` для Mix. Xcode также предоставляет `tuist_generation_version` из связанного события генерации проекта, которое может отличаться от версии загружающего CLI. Отсутствующие значения равны null, а не выводятся из сервера или другого отчета. Bazel использует существующий `bazel_version`; детали запуска Once предоставляют `once_version`. Эти поля описывают сообщаемые версии, а не проверенную идентификацию или версии контракта взаимодействия. REST-эндпоинты сборок предоставляют те же метаданные. Существующие интеграции и навыки работы с нестабильными тестами не зависят от полей версий и не требуют изменений в рабочих процессах.

Операторы Tuist, исследующие аккаунт клиента, делают это через внутренние инструменты операций Tuist, которые записывают каждый вызов; прямое подключение к этому эндпоинту не дает доступа сверх членства самого пользователя.

### Pulse

Pulse предоставляет четыре инструмента только для чтения, все они адресуются через `account_handle`:

| Инструмент | REST-эквивалент под `/api/accounts/:account_handle/pulse` |
| --- | --- |
| `query_pulse` | `GET /:signal` |
| `get_pulse_analytics` | `GET /:signal/analytics` |
| `get_pulse_error_issue` | `GET /errors/issues/:issue_id` |
| `get_pulse_error_event` | `GET /errors/issues/:issue_id/events/:event_id` |

Доступ к Pulse ограничен текущими участниками организации, настроенной на сервере, даже если аккаунт или проект являются публичными. Требуется аутентификация пользователя или учетные данные `mcp`, связанные с пользователем, и разрешение на чтение аккаунта. Токены проектов, обычные токены аккаунтов, анонимные регистрации и доступ операторов без членства в организации не предоставляют доступ к Pulse. Учетные данные не могут выбирать другой бэкенд или арендатора телеметрии. Браузерные агенты получают эти четыре инструмента только на страницах Pulse, в рамках области видимости аккаунта этой страницы.

REST требует учетные данные пользователя. Ассоциации пользователей OAuth и `auth.md` доступны только на эндпоинте `/mcp`; учетные данные аккаунта без текущего пользователя отклоняются, независимо от членства или видимости связанного аккаунта.

`query_pulse` принимает `signal` (`metrics`, `logs`, `traces` или `errors`), необязательный `query` и `range` (`15m`, `1h`, `6h` или `24h`, по умолчанию `1h`). Метрики, логи и трассировки принимают нативные выражения PromQL, LogQL и TraceQL. Ошибки возвращают сгруппированные инциденты; их `query` является буквальным поиском по заголовку, а не нативным выражением. Таблицы принимают `search`, `page` (по умолчанию `1`), `page_size` (`1`–`100`, по умолчанию `20`), `sort_by` и `sort_order` (`asc` или `desc`). Столбцы сортировки зависят от сигнала и перечислены в схеме инструмента. Фильтры включают `service`, `level` логов и `project`, `environment` и `release` ошибок. Операторы фильтров используют соответствующий аргумент `_op` (`eq`, `contains` или `not_contains`), по умолчанию используется точное равенство.

Столбцы сортировки: `name`/`value` для метрик; `timestamp`/`service`/`level`/`message`/`trace_id` для логов; `timestamp`/`service`/`name`/`duration_ms`/`trace_id` для трассировок; и `last_seen_ns`/`first_seen_ns`/`count`/`title`/`service`/`project`/`issue_id` для ошибок. Панель управления намеренно предоставляет подмножество; API и инструменты принимают полный список для каждого сигнала.

Ответы таблиц содержат `rows`, `series`, `warnings` и `meta`. Метаданные пагинации включают `page`, `page_size`, `total_count`, `total_pages`, `has_next_page`, `has_previous_page` и `end_at`. Передавайте возвращенное значение ISO8601 `end_at` со следующими страницами, чтобы сохранить окно запроса. Ошибки ограничения результатов требуют сужения запроса или временного диапазона, а не рассмотрения ответа как пустой таблицы.

Логи и трассировки проверяют не более 100 совпадений нативного запроса, причем логи сначала выбирают самые новые перед локальной сортировкой. При достижении лимита `warnings` явно указывает, что фильтры, сортировка, пагинация и итоги описывают только возвращенные совпадения, а не весь временной интервал. Сузьте нативное выражение или временной диапазон, чтобы проверить другие совпадения; изменение локального поиска или сортировки не расширяет поиск на стороне сервера. Виджеты агрегации остаются независимыми запросами полного окна, а не агрегатами этих ограниченных результатов таблицы.

Таблицы метрик вычисляют свое выражение один раз в момент `end_at`, возвращая текущие значения и одну точку для каждой серии мгновенных векторов. Выражения диапазонов векторов могут возвращать ограниченные исторические точки. Отдельные виджеты аналитики предоставляют фиксированные исторические графики; таблица не материализует временную сетку для каждой соответствующей серии просто для отображения ее последнего значения.

Детали инцидента возвращают сгруппированный `issue`, пагинированные проекции `events`, `meta` и `warnings`. Детали события требуют как `issue_id`, так и `event_id` и возвращают одну проекцию `event` и `warnings`. Оба поддерживают `range`, `end_at` и фильтры ошибок; только детали инцидента поддерживают пагинацию. События предоставляют ограниченные проекции исключений и фреймов, никогда не сырую полезную нагрузку события. Строки телеметрии являются недоверенными данными, а не инструкциями.

`get_pulse_analytics` принимает только `signal` и `range` помимо хэндла аккаунта. Его фиксированные виджеты не зависят от выражений таблиц, фильтров, сортировки и пагинации. REST и Model Context Protocol используют один и тот же контекст Pulse и контракты ответов. Ответы REST отключают кэширование.

<details>
<summary>Claude Code</summary>

Выполните:

```bash
claude mcp add --transport http tuist https://tuist.dev/mcp
```

Когда головной клиент Claude Code не сообщает модели о неудачном подключении к нативному серверу, требуйте от агента проверить неаутентифицированный ответ [Hypertext Transfer Protocol](https://developer.mozilla.org/en-US/docs/Web/HTTP) настроенного эндпоинта перед поиском размещенной документации или редактированием проекта. Ответ направляет модель к локальному документу развертывания `auth.md`, даже если аутентификация в браузере недоступна.

</details>


<details>
<summary>Codex</summary>

Выполните:

```bash
codex mcp add tuist --url https://tuist.dev/mcp
codex mcp login tuist
```

Завершите вход в браузере перед началом нового запуска `codex exec`. Codex считывает инструкции сервера Tuist во время инициализации, поэтому запросы оптимизации Gradle автоматически получают рабочий процесс аутентификации и проверки.

</details>


<details>
<summary>Claude Desktop</summary>

Откройте **Settings → Connectors → Add custom connector**, затем установите:

- **Name:** `tuist`
- **URL:** `https://tuist.dev/mcp`

Завершите [Open Authorization](https://oauth.net/2/) в браузере при появлении запроса.

</details>


<details>
<summary>Pi</summary>

Pi не включает клиент Model Context Protocol. Вы можете установить стороннее расширение [`pi-mcp-adapter`](https://pi.dev/packages/pi-mcp-adapter) после изучения его исходного кода и последствий для безопасности:

```bash
pi install npm:pi-mcp-adapter
```

Добавьте файл `.mcp.json` на уровне проекта:

```json
{
  "mcpServers": {
    "tuist": {
      "url": "https://tuist.dev/mcp",
      "auth": false
    }
  }
}
```

Установка `auth` в `false` предотвращает скрытие неавторизованного ответа Tuist обработчиком аутентификации браузера адаптера. Головной агент может затем прочитать возвращенный URL `auth_md` и следовать процессу регистрации Tuist, обмена утверждениями идентичности и опроса подтверждения. Настройте полученный токен доступа как bearer-токен или позвольте агенту выполнять аутентифицированные вызовы Model Context Protocol напрямую.

Если вы предпочитаете аутентификацию через браузер, установите `auth` в `"oauth"`. Для этого процесса оставьте один процесс активным с использованием [режима удаленного вызова процедур](https://pi.dev/docs/latest/rpc) Pi до завершения аутентификации:

```bash
pi --mode rpc
```

Не разделяйте ожидающую аутентификацию в браузере между отдельными вызовами `pi --print`, так как процесс, владеющий состоянием обратного вызова, уже завершился.

</details>


<details>
<summary>OpenCode</summary>

Добавьте сервер Tuist Model Context Protocol в `opencode.json`:

```json
{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "tuist": {
      "type": "remote",
      "url": "https://tuist.dev/mcp"
    }
  }
}
```

Затем выполните аутентификацию сервера:

```bash
opencode mcp auth tuist
```

</details>

Если ваш агент поддерживает `auth.md`, он может запуститься анонимно без открытия браузера. Доверенная идентичность провайдера также может завершить процесс без браузера, если она уже связана. Для электронной почты с аутентификацией службы, анонимного подтверждения или первой ссылки на провайдера агент покажет вам ссылку для проверки Tuist и шестизначный код. Откройте ссылку, войдите в систему и введите код агента на странице Tuist. Никогда не отправляйте код обратно агенту. Метаданные сервера авторизации Tuist указывают непосредственно на локальный `/auth.md` развертывания, который содержит точные формы запроса и опроса.

## Агенты в Amp orbs и облачных сессиях Claude Code

Агенты для написания кода, работающие в песочницах, подключенных к аккаунту Tuist, могут аутентифицироваться на эндпоинте с помощью собственного токена идентичности, без браузера или сохраненных учетных данных Tuist:

- **Amp orbs** рабочего пространства или проекта Amp, к которому аккаунт подключен через **Settings → Integrations → Amp**, отправляют ID-токен орба. В Amp установите заголовок `Authorization` сервера в значение `Bearer ${amp:id-token}`. Amp выпускает токен для источника URL сервера, поэтому URL должен быть адресом именно этого экземпляра Tuist, и обновляет его до истечения срока действия. Токены, выпущенные для другого источника, отклоняются.
- **Облачные сессии Claude Code** подключенной среды Claude Code отправляют токен сессии, который Tuist передает им как `TUIST_OIDC_TOKEN`. Установите заголовок в значение `Bearer ${TUIST_OIDC_TOKEN}`.

Песочницы Linux в Tuist поставляются с этой конфигурацией: сервер `tuist` в пользовательских настройках Amp и в пользовательской конфигурации Claude Code, оба направлены на `${TUIST_URL}/mcp`, вместе с CLI Tuist и навыком, который сообщает агенту, когда проверять его результаты по истории проекта. В других местах добавьте сервер с указанным выше заголовком самостоятельно.

Эти токены предоставляют доступ только для чтения ко всем проектам подключенного аккаунта: они несут права чтения группы `mcp` и не имеют прав на создание, изменение или удаление данных, таких как игнорирование или пропуск тестов. Отключение рабочего пространства или среды прекращает доступ при следующем запросе, и доступ никогда не длится дольше самого токена. Рабочее пространство Amp, подключенное к нескольким аккаунтам Tuist, отклоняется, потому что его токен не указывает на один конкретный аккаунт. Когда подключение отсутствует, об этом говорится в поле `error_description` ответа об отсутствии авторизации.

Этот доступ только для чтения применяется только к эндпоинту Model Context Protocol. Инструмент командной строки и интеграции системы сборки в той же песочнице по-прежнему обменивают токен на CI-доступ подключения.

## WebMCP

В браузерах, поддерживающих [WebMCP](https://webmachinelearning.github.io/webmcp), страницы Tuist регистрируют инструменты через `document.modelContext`, поэтому встроенные в браузер агенты могут вызывать их без дополнительной настройки. Вызовы выполняются на сервере Tuist.

- **Страницы веб-сайта и документации** регистрируют инструменты документации и исходного кода (`search_tuist`, `search_tuist_code`, `list_tuist_files` и `read_tuist_file`). Им не требуется вход в систему.
- **Страницы панели управления аккаунта**, когда вы вошли в систему, регистрируют инструменты Tuist только для чтения для этого аккаунта. Каждая страница регистрирует только инструменты для того, что она отображает, для системы сборки проекта: страница сборок проекта Gradle получает инструменты сборки Gradle, ее страницы тестов — инструменты тестирования и покрытия, страницы раннеров — инструменты раннеров, а страницы песочниц — инструменты песочниц. Раздел «Подписки» на странице настроек ИИ вашего личного аккаунта получает `list_ai_subscriptions`, который отвечает только для вашего собственного аккаунта. Каждая страница также получает инструменты документации, `list_projects` и `get_project`. Инструменты выполняются от имени вошедшего пользователя, поэтому они получают доступ только к данным, которые вы можете читать в панели управления, и только к аккаунту, который вы просматриваете. При переходе на другую страницу или аккаунт инструменты заменяются на инструменты этой страницы.

Инструменты, которые создают, изменяют или удаляют данные, недоступны через WebMCP, потому что браузерный агент получает инструменты без вашего добавления и читает контент, создаваемый сборками и тестами. Подключите клиент MCP к эндпоинту `/mcp`, чтобы использовать эти инструменты.

Если организация требует единый вход (SSO), войдите в панель управления через ее провайдера, чтобы использовать ее инструменты.

## Интеграции системы сборки используют два набора учетных данных

Учетные данные, используемые для инструментов Model Context Protocol, не аутентифицируют плагин Gradle или удаленные сервисы Bazel. Перед тем как агент редактирует или проверяет интеграцию Gradle или Bazel, он должен выполнить:

```bash
tuist auth whoami --url https://tuist.dev
```

Если эта команда не аутентифицирована, агент должен остановиться и попросить пользователя выполнить:

```bash
tuist auth login --url https://tuist.dev
```

Для локального или самостоятельно размещенного развертывания замените URL в обеих командах и в `tuist.toml`. Сохраняйте одинаковое написание хоста везде. Например, `localhost` и `127.0.0.1` используют отдельные сохраненные учетные данные.


## Возможности

### Инструменты

Следующие инструменты доступны через сервер Tuist Model Context Protocol:

Каждый инструмент публикует описание, понятное человеку, вместе с явными схемами ввода и вывода. Успешные вызовы возвращают структурированный контент, соответствующий заявленной схеме вывода, а также тот же результат, сериализованный в виде текста для клиентов, которые еще не потребляют структурированный контент.

Инструменты, которые принимают идентификатор одной записи, такой как `build_run_id`, `test_run_id`, `test_case_id`, `bundle_id`, `run_id`, `generation_id` или `cache_run_id`, также принимают URL панели управления Tuist для этой записи. Вставьте URL прямо из браузера вместо извлечения из него идентификатора.

#### Поиск по документации и сообществу

Этот инструмент только для чтения выполняет поиск в документации Tuist, справочнике [программного интерфейса приложения](https://en.wikipedia.org/wiki/API), релизах GitHub, на форуме сообщества и в задачах GitHub через тот же поисковый движок, что используется на сайте документации. Результаты поиска по релизам включают продукт, версию, дату публикации и статус предварительной версии. По умолчанию выполняется поиск по стабильным релизам; предварительные релизы можно включить с помощью `include_prereleases`. Инструмент доступен только на сервере, размещенном Tuist, по адресу `https://tuist.dev/mcp`.

| Инструмент | Описание | Обязательные параметры |
|------|-------------|---------------------|
| `search_tuist` | Поиск в публичной документации Tuist, справочнике программного интерфейса приложения, релизах GitHub, обсуждениях сообщества и задачах GitHub. При необходимости можно ограничить поиск одним `source` (`docs`, `api_reference`, `releases`, `forum`, `issues`). | `query` |

#### Обратная связь

Агенты могут сообщить команде Tuist, если инструмент или подсказка Tuist не сработали так, как ожидалось: например, выдали непонятный результат, ошибку, отсутствующие данные или не предоставили нужную возможность. Агентам предлагается составить отчет и отправить его только после вашего согласия. Каждый отчет открывает диалог со службой поддержки Tuist, которая может ответить вам по электронной почте. Отчет включает ожидаемое агентом поведение, фактический результат, необязательное предложение, ваш идентификатор пользователя Tuist, имя пользователя и адрес электронной почты, а также организации, к которым вы принадлежите. Агенты также могут указать аккаунт и проект, в которых возникла проблема, чтобы команда знала, с какой организацией связаться; принимаются только аккаунты, к которым у вас есть доступ. Отчеты могут отправлять только агенты, вошедшие в систему как пользователь Tuist, и каждый пользователь может создавать до 10 отчетов в час. Инструмент доступен только на сервере, размещенном Tuist, по адресу `https://tuist.dev/mcp`.

| Инструмент | Описание | Обязательные параметры |
|------|-------------|---------------------|
| `report_feedback` | Сообщить о проблеме с инструментом или подсказкой Tuist. При необходимости укажите `tool_name`, `account_handle` и `project_handle`, в которых произошла проблема, и добавьте `suggestion`. | `category`, `expected`, `actual` |

#### Ответы на основе исходного кода

Эти инструменты только для чтения позволяют агентам использовать точную публичную ревизию исходного кода Tuist, развернутую вместе с хостинговым сервером, как источник истины для ответов, зависящих от текущего поведения. Они доступны только по адресу `https://tuist.dev/mcp`.

Совместимые клиенты получают фактические описания ревизии исходного кода инструментов, ссылки и ограничения результатов во время инициализации вместе с информацией для встроенной аутентификации OAuth. Эти описания не предписывают стиль ответа или порядок проверки. Пользователи могут задать вопрос напрямую, не вызывая сначала подсказку `ask_tuist`; подсказка остается доступной для явного рабочего процесса с опорой на исходный код.

Каждая операция имеет фиксированные ограничения на параллельность, длительность, обход, объем прочитанных байтов и размер ответа. Результаты поиска и списков включают поля `truncated` и `truncation_reason`. Если результат усечен, сузьте путь, шаблон файла или поисковый запрос вместо того, чтобы считать результат исчерпывающим.

| Инструмент | Описание | Обязательные параметры |
|------|-------------|---------------------|
| `search_tuist_code` | Отвечайте на вопросы о текущем поведении, значениях по умолчанию, конфигурации, флагах функций, обработке ошибок или недокументированных деталях, выполняя поиск по файлам исходного кода. Результаты включают окружающие строки, ссылки на исходный код, привязанные к ревизии, и статистику сканирования. | `pattern` |
| `list_tuist_files` | Обнаруживайте подсистему исходного кода или близлежащие тесты, когда соответствующий путь неизвестен. Списки имеют ограниченную глубину и количество результатов. | Нет |
| `read_tuist_file` | Просматривайте определенный диапазон строк в файле реализации, месте вызова или тесте после нахождения соответствующего пути. Усеченные ответы предоставляют `next_start_line` для продолжения. | `path` |

#### Сборки Xcode

Инструменты детализации сборок для Xcode, Gradle, Bazel, Mix и Cargo предоставляют существующую структуру `custom_metadata: {tags, values}`, включая наблюдения за инфраструктурой, если они сообщаются. Значения остаются строками, а неизвестные ключи сохраняются. Например, `tuist.cpu.available_processors` описывает логические процессоры, доступные во время выполнения, тогда как `tuist.gradle.max_workers` — это ограничение на количество воркеров Gradle, а `tuist.jvm.max_heap_bytes` — ограничение кучи JVM, а не память хоста. Это ненадежные наблюдения клиента, а не проверенные идентификаторы раннеров. Отсутствующие наблюдения остаются отсутствующими; импортированные логи и старые клиенты могут не иметь метаданных инфраструктуры. В будущем метаданные потребуют согласованного обновления клиента/протокола.

| Инструмент | Описание | Обязательные параметры |
|------|-------------|---------------------|
| `list_xcode_builds` | Получить список запусков сборок Xcode для проекта. | `account_handle`, `project_handle` |
| `get_xcode_build` | Получить подробную информацию о конкретном запуске сборки Xcode, включая временный URL для скачивания архива, содержащего исходный `.xcactivitylog`. | `build_run_id` |
| `list_xcode_build_targets` | Получить список целей сборки для конкретного запуска сборки Xcode. | `build_run_id` |
| `list_xcode_build_files` | Получить список скомпилированных файлов для конкретного запуска сборки Xcode. | `build_run_id` |
| `list_xcode_build_steps` | Получить список записанных шагов сборки с временными затратами и результатами, без текста логов. | `build_run_id` |
| `get_xcode_build_step` | Получить один записанный шаг сборки, включая его лог и флаг усечения. | `build_run_id`, `step_id` |
| `list_xcode_build_issues` | Получить список проблем сборки (предупреждения и ошибки) для конкретного запуска сборки. | `build_run_id` |
| `list_xcode_build_cache_tasks` | Получить список задач, подлежащих кэшированию (попадания/промахи кэша), для конкретного запуска сборки Xcode. | `build_run_id` |
| `list_xcode_build_cas_outputs` | Получить список выходов [хранилища с контентной адресацией](https://en.wikipedia.org/wiki/Content-addressable_storage) для конкретного запуска сборки Xcode. | `build_run_id` |

`list_xcode_build_steps` по умолчанию возвращает страницы по 20 шагов (максимум 100 через `page_size`), с `page` и `pagination_metadata` для навигации. Используйте `search` для поиска по названиям, проектам или целям, либо фильтруйте по точным значениям `project`, `target`, `category` (например, `swiftCompilation`) и `status` (`success` или `failure`). Сортируйте по `duration_ms` для отображения самых медленных сначала (по умолчанию) или по `start_ms` для хронологического порядка. ID шагов используются для разрешения ничьих и возвращаются в виде десятичных строк для сохранения полной 64-битной точности. ID привязаны к сборке и не должны сопоставляться между разными сборками.

Необязательные параметры `start_ms` и `end_ms` выбирают шаги, попадающие в диапазон времени в миллисекундах от начала сборки; конец диапазона исключается. Оба инструмента принимают UUID сборки или URL панели управления в качестве `build_run_id`. Передавайте полученный `id` шага без изменений в качестве `step_id` для получения его лога. Логи хранят до 64 КиБ на шаг, при этом `log_truncated` указывает на усеченный вывод.

Шаги собираются по умолчанию при обработке сборок Xcode. Записанные данные шагов хранятся 90 дней. Ответ списка включает `availability`: `available`, если записанные шаги существуют, даже если фильтры ничего не нашли; `processing`, если сборка еще обрабатывается и шагов пока нет; или `unavailable`, если шаги не были записаны или срок их хранения истек.

Те же операции доступны через HTTP API по адресам `GET /api/projects/{account_handle}/{project_handle}/xcode/builds/{build_id}/steps` и `GET /api/projects/{account_handle}/{project_handle}/xcode/builds/{build_id}/steps/{step_id}`, с теми же фильтрами и пагинацией. Для обоих требуется доступ на чтение к проекту сборки.

Списки шагов Gradle и Bazel по умолчанию возвращают 20 результатов (максимум 100), поддерживают `search`, точное совпадение `project`, `target`, `category` и `status`, фильтры по пересекающимся интервалам `start_ms` / `end_ms` (конец исключается) и сортировку по `duration_ms` или `start_ms`. Передавайте полученные ID без изменений; они привязаны к своей сборке. Списки предоставляют `time_origin` и `coverage`. Старые отчеты Gradle используют `first_recorded_timestamp`, так как время начала сборки не было загружено. Профили Bazel показывают все записанные интервалы с покрытием `trace_profile` и `profile_start` в качестве начала отсчета времени. Для старых сборок используются сохраненные сводки BEP. Исходные записи истекают через 90 дней. Детали Bazel включают очищенные логи действий, если они опубликованы. Детали Gradle для неудачной задачи или шага конфигурации включают сообщение об ошибке, которое плагин Tuist Gradle сообщил как `log`: сообщение исключения и цепочку причин, как их выводит консоль Gradle, без трассировки стека или вывода задачи, с путями внутри проекта, сделанными относительными, и скрытыми учетными данными и другими локальными путями, не более 16 КиБ на шаг и 32 неудачных шага на сборку. Другие шаги Gradle, сборки, сообщаемые старыми версиями плагина, и отчеты без учетных данных имеют null в поле `log`. Шаги конфигурации сообщают `failure` при ошибке и `unknown` в остальных случаях. Подсказка `compare_builds` использует это покрытие, чтобы отличать полные трассировки Bazel от сохраненных сводок, и направляет агентов к деталям шагов для получения результатов действий и логов перед проверкой общего вывода вызова.

Инструменты для одного шага `get_gradle_build_step` и `get_bazel_build_step` получают шаг по ID и не принимают временные фильтры; используйте соответствующие инструменты списка для фильтрации шагов по временному диапазону.

ID шагов Bazel, возвращаемые из сохраненных сводок, остаются читаемыми, если полный профиль поступает между получением списка и запросом шага. Индексированный профиль, данные шагов которого истекли, сообщает о недоступности. Списки шагов Gradle включают кэшированные и пропущенные операции с нулевой длительностью.

Фильтры `list_bazel_invocations` работают по точному совпадению, а вызовы, завершившиеся в одну и ту же секунду, упорядочиваются по ID вызова. Чтобы найти последний неудачный вызов на ветке, вызовите его с `status: "failure"`, `git_branch` и `page_size: 1`. REST-эндпоинт `GET /api/projects/{account_handle}/{project_handle}/bazel/invocations` принимает те же фильтры.

Логи тестов содержат `target_label` и статус попытки `status` результата теста, из которого они получены, поэтому `target_label: "//foo:bar_test"` возвращает только логи тестов этой цели. `errors: true` возвращает логи тестов неудачных попыток и фрагменты прогресса stderr, содержащие строки, которые репортер Bazel начинает с `ERROR:`, `FAIL:` или `TIMEOUT:`. Вывод прогресса не привязывается к целям, а логи, записанные до фиксации привязки, имеют пустые поля. Неудачные действия и их собственный вывод доступны по целям через `list_bazel_build_steps`, а сбои по тест-кейсам — через инструменты запуска тестов.

#### Задачи, действия, модули и файлы

Эти инструменты уровня проекта анализируют постоянные идентификаторы сборок across запусков. Начните с `list_build_entities`, затем передайте полученный стабильный `id` с тем же `kind` в `get_build_entity` или `list_build_entity_history` вместе с `account_handle` и `project_handle`. Идентификатор сборки или вызова не требуется.

| Инструмент | Описание | Обязательные параметры |
| --- | --- | --- |
| `list_build_entities` | Список задач, модулей, действий или файлов одного типа, обнаруженных в сборках проекта. | `account_handle`, `project_handle`, `kind` |
| `get_build_entity` | Получение одной сущности сборки с её нативным идентификатором и аналитикой за выбранный период. | `account_handle`, `project_handle`, `kind`, `id` |
| `list_build_entity_history` | Список записанных выполнений, компиляций или событий кэша для одной сущности сборки в порядке убывания новизны. | `account_handle`, `project_handle`, `kind`, `id` |

| `kind` | Инструментарий | Списки истории |
| --- | --- | --- |
| `bazel_actions` | Действия Bazel | Выполнения действий, сообщенные через BEP |
| `gradle_tasks` | Задачи Gradle | Выполнения задач |
| `xcode_modules` | Модули Xcode | Компиляции и события кэша модулей |
| `once_actions` | Действия Once | Выполнения |
| `mix_files` | Компилируемые файлы Mix | Компиляции |
| `mix_modules` | Компилируемые модули Mix | Компиляции |
| `cargo_crates` | Крейты Cargo | Записанные вызовы rustc |

Эти инструменты внедряются постепенно и возвращают данные только для проектов, где они включены; для других проектов они возвращают ошибку вместо пустого результата. Тип доступен только для проектов, использующих соответствующий инструментарий сборки. Инструменты принимают ограниченные фильтры `start_at`/`end_at`, `environment` (`any`, `ci` или `local`) и точное значение `branch`. `list_build_entities` принимает `q`; `list_build_entity_history` поддерживает непрозрачные курсоры `after`/`before`. Неизвестные данные о времени или наблюдения кэша остаются недоступными, а не превращаются в нули или промахи. История ссылается на записанного родителя и нативное выполнение для детализации с использованием существующих инструментов запусков.

Метрики `get_build_entity` включают `duration_samples` — количество наблюдений с записанным временем: реальные нулевые длительности учитываются, отсутствующие данные о времени — нет. Это количество может быть меньше количества наблюдений; недоступная статистика длительности остается равной null.

Длительности модулей Xcode берутся из измеренных компиляций целей в логах сборки. Разрешения кэша модулей и цели без работы по компиляции не вносят вклад в выборку длительностей. Наблюдения компиляции ссылается на сборку Xcode; события кэша — на команду генерации или кэширования.

Действия Bazel идентифицируются по метке цели, мнемонике и настроенному первичному выходному файлу, что позволяет разделять действия и конфигурации без опоры на зависящие от ввода дайджесты кэша. История записывает выполнения, сообщенные через BEP, а не поиски в кэше или фазы профиля трассировки. Полное покрытие выполнений требует `--build_event_publish_all_actions`; доставка артефактов осуществляется по принципу best effort, поэтому отсутствие наблюдений не является доказательством того, что работа не выполнялась. Старые payloads Kura без стабильного идентификатора или начала выполнения по-прежнему принимаются, но не индексируются. Отсутствующие измерения времени окончания остаются недоступными, а реальные нулевые длительности учитываются.

Длительности модулей Mix измеряют компиляцию содержащего файла, а не независимо измеренную работу модуля. Действия Once используют объявленные слоты цель/возможность/индекс, когда клиент сообщал сопоставления целей; одни лишь диагностические метки не являются стабильными идентификаторами. Существующие клиенты и инструменты уровня запуска остаются поддерживаемыми без изменений.

Крейты Cargo группируются по точно записанному корню крейта, имени и типу. Изменения пути checkout могут разделять истории, а профили сборки, функции и тройки целей не различаются. История измеряет вызовы rustc, а не работу по отдельным файлам или попадания в кэш; отсутствующие задачи не свидетельствуют об удалениях или полной инвентаризации рабочего пространства.

Чтение аналитики ограничено по памяти и времени выполнения. Если запрос превышает эти лимиты, инструмент возвращает ошибку вместо создания пустого результата.

Новые наблюдения индексируются после развертывания; эта функция не заполняет ретроспективно существующую телеметрию запусков. Метаданные идентификаторов хранятся дольше отдельных наблюдений в соответствии с <.localized_link href="/guides/server/data-retention">политикой хранения данных</.localized_link>.

|-------|-----------------|---------------------|
| `test_case.marked_flaky` | Тест-кейс изменяет статус с стабильного на нестабильный. | `account_handle`, `project_handle` |
| `build.failed` | Локальная сборка или сборка в непрерывной интеграции Xcode, Gradle или Bazel завершается с ошибкой. | `account_handle`, `project_handle` |
| `test_run.failed` | Локальный запуск тестов или запуск тестов в непрерывной интеграции завершается с ошибкой, включая объединенный шардированный запуск или отмененный запуск. | `account_handle`, `project_handle` |
| `ci_job.failed` | Задача раннера Tuist завершается с ошибкой. | `account_handle` |

Для подписки клиент вызывает `events/subscribe` с именем события, идентификаторами, указанными выше в `arguments`, и доставкой `webhook`, содержащей URL-адрес обратного вызова `https://` и секрет подписи `whsec_`. События проекта требуют членства в аккаунте и права на чтение соответствующих данных тестов или сборок; события задач раннера требуют членства в аккаунте и права на чтение данных раннера. Заявленные токены доступа [`auth.md`](https://workos.com/auth-md), заявленные токены аккаунта и гранты авторизации браузера могут создавать подписки; доставка прекращается, когда связанные учетные данные больше не активны. Каждый пользователь может иметь до 25 активных подписок. Tuist отправляет проверочный запрос на обратный вызов перед сохранением подписки. Обратный вызов должен вернуть объект, содержащий то же значение `challenge`. Подписка действует семь дней по умолчанию, может быть обновлена путем повторной подписки и прекращает доставку при удалении доступа пользователя или учетных данных. Необязательный параметр `ttlMs` ограничен диапазоном от одного часа до 30 дней. Tuist повторяет попытку вызова обратного вызова при тайм-ауте и отменяет подписку после как минимум трех последовательных тайм-аутов в течение пяти минут; подпишитесь снова после восстановления обратного вызова.

При возникновении события Tuist отправляет его идентификатор ресурса и URL-адрес панели управления на обратный вызов. Ошибки сборки и запуска тестов также включают `is_ci` и `git_branch`, поэтому клиенты могут игнорировать локальные ошибки или фильтровать по ветке. События сборки включают `build_system`; события задач раннера включают как `workflow_job_id`, так и `workflow_run_id`. Запрос включает идентификатор подписки и заголовки подписи [Standard Webhooks](https://www.standardwebhooks.com/), чтобы клиент мог проверить источник. Tuist повторяет неудачные доставки, поэтому клиентам следует использовать стабильный `eventId` для отклонения дубликатов. Полезная нагрузка не содержит имен тестов, журналов и сообщений об ошибках; клиент может получить эти детали через указанные выше инструменты и решить, уведомлять ли команду или начать отладку. Клиенты могут остановить доставку с помощью `events/unsubscribe`.

### Подсказки

| Подсказка | Описание |
|--------|-------------|
| `fix_flaky_test` | Помогает исправить нестабильный тест, анализируя шаблоны сбоев, выявляя первопричину и применяя целенаправленное исправление. |
| `compare_builds` | Помогает сравнить сборки для выявления регрессий производительности, изменений кэша и проблем сборки. Использует нативные инструменты для проектов Xcode, Gradle, Bazel и Cargo. Сравнения Cargo сохраняют частичное покрытие компилятора и различают оценочную работу компилятора и фактическую экономию времени. |
| `compare_test_runs` | Помогает сравнить два запуска тестов для выявления регрессий, новых сбоев и нестабильных тестов. |
| `compare_bundles` | Помогает сравнить два бандла для выявления изменений размера во всем дереве артефактов. |
| `compare_test_case` | Помогает сравнить поведение тест-кейса в двух ветках или временных периодах. |
| `compare_generations` | Помогает сравнить два запуска генерации для выявления регрессий производительности и изменений модульного кэша. |
| `compare_cache_runs` | Помогает сравнить два запуска кэша для выявления изменений эффективности кэша и регрессий на уровне таргетов. |
| `integrate_gradle_project` | Помогает интегрировать Tuist в существующий проект Gradle. Включает отдельную аутентификацию инструмента и Gradle, поиск аккаунта, создание проекта, политику удаленного кэша, аналитику сборки и проверку считыванием. |
| `integrate_bazel_project` | Помогает создать или выбрать проект Bazel, выполнить аутентификацию командной строки, настроить удаленный кэш и аналитику сборки, а также проверить интеграцию через данные сборки Tuist. |
| `integrate_xcode_project` | Помогает интегрировать Tuist в существующий проект Xcode. Поддерживает кэш Xcode, аналитику сборки, аналитику тестов и шардирование тестов. |
| `ask_tuist` | Отвечает на вопрос о Tuist, используя публичные материалы для контекста и сфокусированные доказательства реализации и тестирования как источник истины для текущего поведения. Требует `question` и ссылается на доказательства, привязанные к ревизии. |

Подсказки с данными проекта принимают `account_handle` и `project_handle` для ограничения исследования конкретным проектом. Подсказки сравнения также принимают аргументы `base` и `head` для указания двух сравниваемых элементов (по ID, URL дашборда или имени ветки). `ask_tuist` принимает `question` вместо параметров проекта. `integrate_gradle_project` также принимает `features` — список интеграций Gradle через запятую: `remote_cache`, `build_insights`, `test_insights`, `flaky_tests` и `test_sharding`. `integrate_bazel_project` принимает необязательный `server_url` для самостоятельного хостинга или локальных установок. `integrate_xcode_project` принимает `features` с `xcode_cache`, `build_insights`, `test_insights` и `test_sharding`.

#### Возможности подсказки интеграции Gradle

Подсказка `integrate_gradle_project` и инструмент `get_gradle_integration_guide` документируют полный рабочий процесс настройки. Инструмент также упоминается в инструкциях инициализации сервера, что делает его обнаруживаемым для агентов, которые не перечисляют подсказки.

| Возможность | Что настраивает агент |
|---------|---------------------------|
| `remote_cache` | Включает кэш сборки Gradle, настраивает политику загрузки удаленного кэша Tuist и рекомендует загрузку только с раннеров непрерывной интеграции с локальным доступом только для чтения. |
| `build_insights` | Применяет плагин Tuist Gradle и при необходимости настраивает поведение загрузки аналитики сборки. |
| `test_insights` | Применяет плагин Tuist Gradle, чтобы результаты задач Gradle `Test` загружались автоматически. |
| `flaky_tests` | Помогает настроить обнаружение нестабильных тестов, опциональное использование плагина Gradle Test Retry и конфигурацию карантина тестов. |
| `test_sharding` | Добавляет рабочий процесс непрерывной интеграции для `tuistPrepareTestShards`, генерации матрицы шардов и выполнения тестов на основе `TUIST_SHARD_INDEX`. |

Если `features` пропущен, подсказка просит агента уточнить, какие интеграции нужны пользователю, или вывести минимально полезный набор из запроса перед редактированием проекта Gradle.

#### Возможности подсказки интеграции Xcode

Подсказка `integrate_xcode_project` документирует каждую интеграцию Xcode, которую поддерживает Tuist:

| Возможность | Что настраивает агент |
|---------|---------------------------|
| `xcode_cache` | Настраивает `tuist setup cache`, параметры кэша сгенерированного проекта, ручные настройки сборки кэша Xcode и политику загрузки, ограниченную раннерами непрерывной интеграции. |
| `build_insights` | Настраивает `tuist inspect build`, `tuist xcodebuild`, `-resultBundlePath` и опциональные метрики машины через `tuist setup insights`. |
| `test_insights` | Настраивает `tuist inspect test`, пост-действия тестирования схем и генерацию бандла результатов для запусков тестов непрерывной интеграции. |
| `test_sharding` | Добавляет планирование шардов для Xcode или сгенерированного проекта и рабочий процесс выполнения шардов с `TUIST_SHARD_INDEX`. |

Если `features` пропущен, подсказка просит агента уточнить, какие интеграции нужны пользователю, или вывести минимально полезный набор из запроса перед редактированием проекта Xcode.
