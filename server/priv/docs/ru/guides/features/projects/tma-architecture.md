# Модульная архитектура (TMA) {#the-modular-architecture-tma}

TMA — это архитектурный подход к структурированию приложений, который обеспечивает масштабируемость, оптимизирует циклы сборки и тестирования и помогает внедрять лучшие практики в вашей команде. Основная идея заключается в создании приложений из независимых возможностей, связанных между собой через чёткие и лаконичные API.

Эти рекомендации описывают принципы архитектуры, помогая выявлять и организовывать возможности вашего приложения по разным слоям. Здесь также приведены советы, инструменты и рекомендации на случай, если вы решите использовать эту архитектуру.

> [!NOTE]
> **µFeatures**
>
> Ранее эта архитектура была известна как µFeatures. Мы переименовали её в «Модульная архитектура (TMA)», чтобы точнее отразить её назначение и лежащие в основе принципы.


## Основной принцип {#core-principle}

Разработчики должны иметь возможность **быстро собирать, тестировать и проверять** свои возможности независимо от основного приложения, при этом обеспечивая надёжную работу функций Xcode, таких как предварительный просмотр интерфейса, автодополнение кода и отладка.

## Что такое модуль {#what-is-a-module}

Модуль представляет собой возможность приложения и состоит из следующих пяти таргетов (здесь «таргет» означает таргет Xcode):

- **Source:** Содержит исходный код возможности (Swift, Objective-C, C++, JavaScript...) и её ресурсы (изображения, шрифты, storyboard-файлы, xib-файлы).
- **Interface:** Это сопутствующий таргет, содержащий публичный интерфейс и модели возможности.
- **Tests:** Содержит модульные и интеграционные тесты возможности.
- **Testing:** Предоставляет тестовые данные, которые можно использовать в тестах и примере приложения. Также он предоставляет моки для классов и протоколов модуля, которые могут использоваться другими возможностями, как мы увидим далее.
- **Example:** Содержит пример приложения, который разработчики могут использовать для проверки возможности в определённых условиях (разные языки, размеры экранов, настройки).

Мы рекомендуем соблюдать соглашение об именах для таргетов, которое можно обеспечить в проекте благодаря DSL Tuist.

| Таргет | Зависимости | Содержимое |
| ---- | ---- | ---- |
| `Feature` | `FeatureInterface` | Исходный код и ресурсы |
| `FeatureInterface` | - | Публичный интерфейс и модели |
| `FeatureTests` | `Feature`, `FeatureTesting` | Модульные и интеграционные тесты |
| `FeatureTesting` | `FeatureInterface` | Тестовые данные и моки |
| `FeatureExample` | `FeatureTesting`, `Feature` | Пример приложения |

> [!TIP]
> **Предварительный просмотр интерфейса**
>
> `Feature` может использовать `FeatureTesting` в качестве ресурса разработки, чтобы включить предварительный просмотр интерфейса


> [!WARNING]
> **Директивы компилятора вместо тестовых таргетов**
>
> В качестве альтернативы можно использовать директивы компилятора, чтобы включать тестовые данные и моки в таргеты `Feature` или `FeatureInterface` при компиляции для `Debug`. Это упрощает граф зависимостей, но приводит к компиляции кода, который не нужен для запуска приложения.


## Зачем нужен модуль {#why-a-module}

### Чёткие и лаконичные API {#clear-and-concise-apis}

Когда весь исходный код приложения находится в одном таргете, легко создать неявные зависимости в коде и получить так называемый «спагетти-код». Всё сильно связано, состояние иногда непредсказуемо, а внесение новых изменений превращается в кошмар. Когда мы определяем возможности в независимых таргетах, нам нужно проектировать публичные API как часть реализации возможности. Необходимо решить, что должно быть публичным, как должна использоваться наша возможность и что должно оставаться приватным. Мы получаем больше контроля над тем, как клиенты нашей возможности будут её использовать, и можем внедрять лучшие практики, проектируя безопасные API.

### Небольшие модули {#small-modules}

[Разделяй и властвуй](https://en.wikipedia.org/wiki/Divide_and_conquer). Работа с небольшими модулями позволяет лучше сфокусироваться и тестировать и проверять возможность изолированно. Кроме того, циклы разработки становятся значительно быстрее, поскольку компиляция более избирательна: компилируются только компоненты, необходимые для работы нашей возможности. Компиляция всего приложения требуется лишь в самом конце работы, когда нужно интегрировать возможность в приложение.

### Повторное использование {#reusability}

Повторное использование кода между приложениями и другими продуктами, такими как расширения, поощряется с помощью фреймворков или библиотек. При использовании модулей их повторное применение становится довольно простым. Мы можем создать расширение iMessage, виджет Today или приложение для watchOS, просто комбинируя существующие модули и добавляя _(при необходимости)_ специфичные для платформы слои интерфейса.

## Зависимости {#dependencies}

Когда один модуль зависит от другого, он объявляет зависимость от его таргета интерфейса. Это даёт двойную выгоду. Оно предотвращает связывание реализации одного модуля с реализацией другого и ускоряет чистые сборки, поскольку компилируется только реализация нашей возможности и интерфейсы прямых и транзитивных зависимостей. Этот подход вдохновлён идеей SwiftRock о [сокращении времени сборки iOS за счёт использования интерфейсных модулей](https://swiftrocks.com/reducing-ios-build-times-by-using-interface-targets).

Зависимость от интерфейсов требует, чтобы приложения строили граф реализаций во время выполнения и внедряли его через инъекцию зависимостей в модули, которым он нужен. Хотя TMA не навязывает конкретный способ решения этой задачи, мы рекомендуем использовать решения или паттерны инъекции зависимостей, которые не добавляют косвенных вызовов во время сборки и не используют платформенные API, не предназначенные для этой цели.

## Типы продуктов {#product-types}

При сборке модуля вы можете выбрать между **библиотеками и фреймворками**, а также между **статической и динамической линковкой** для таргетов. Без Tuist принятие этого решения немного сложнее, поскольку нужно вручную настраивать граф зависимостей. Однако благодаря Tuist Projects эта проблема больше не актуальна.

Мы рекомендуем использовать динамические библиотеки или фреймворки во время разработки, применяя <.localized_link href="/guides/features/projects/synthesized-files#bundle-accessors">аксессоры бандлов</.localized_link>, чтобы отделить логику доступа к бандлу от типа таргета (библиотека или фреймворк). Это ключевой момент для быстрого времени компиляции и обеспечения надёжной работы [предварительного просмотра SwiftUI](https://developer.apple.com/documentation/swiftui/previews-in-xcode). Для релизных сборок используйте статические библиотеки или фреймворки, чтобы обеспечить быстрый запуск приложения. Вы можете воспользоваться <.localized_link href="/guides/features/projects/dynamic-configuration#configuration-through-environment-variables">динамической конфигурацией</.localized_link>, чтобы изменить тип продукта на этапе генерации:

```bash
# You'll have to read the value of the variable from the manifest
# and use it to change the linking type
TUIST_PRODUCT_TYPE=static-library tuist generate
```

```swift
// You can place this in your manifest files or helpers
// and use the returned value when instantiating targets.
func productType() -> Product {
    if case let .string(productType) = Environment.productType {
        return productType == "static-library" ? .staticLibrary : .framework
    } else {
        return .framework
    }
}
```


> [!WARNING]
> **Объединяемые библиотеки**
>
> Apple попыталась упростить переключение между статическими и динамическими библиотеками, представив [объединяемые библиотеки](https://developer.apple.com/documentation/xcode/configuring-your-project-to-use-mergeable-libraries). Однако это вносит недетерминированность во время сборки, из-за чего сборка становится невоспроизводимой и сложнее поддаётся оптимизации, поэтому мы не рекомендуем их использовать.


## Код {#code}

TMA не навязывает конкретную архитектуру кода и паттерны для ваших модулей. Тем не менее, мы хотим поделиться несколькими советами, основанными на нашем опыте:

- **Использование возможностей компилятора — это хорошо.** Чрезмерное reliance на компилятор может снизить продуктивность и привести к нестабильной работе некоторых функций Xcode, таких как предварительный просмотр. Мы рекомендуем использовать компилятор для внедрения лучших практик и раннего выявления ошибок, но не до такой степени, чтобы код становился сложнее читать и поддерживать.
- **Используйте макросы Swift умеренно.** Они могут быть очень мощными, но также усложняют чтение и поддержку кода.
- **Принимайте платформу и язык такими, какие они есть, не абстрагируйте их.** Попытки создать сложные уровни абстракции могут оказаться контрпродуктивными. Платформа и язык достаточно мощны, чтобы создавать отличные приложения без необходимости в дополнительных уровнях абстракции. Используйте хорошие практики программирования и паттерны проектирования как ориентир при разработке своих возможностей.
