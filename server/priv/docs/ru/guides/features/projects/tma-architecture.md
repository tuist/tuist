# Модульная архитектура (TMA) {#the-modular-architecture-tma}

TMA — это архитектурный подход к структурированию приложений, который обеспечивает масштабируемость, оптимизирует циклы сборки и тестирования и помогает внедрять лучшие практики в вашей команде. Его основная идея заключается в создании приложений из независимых возможностей, связанных между собой с помощью чётких и лаконичных API.

Эти рекомендации описывают принципы архитектуры, помогая выявлять и организовывать возможности вашего приложения по разным слоям. Также здесь приведены советы, инструменты и рекомендации на случай, если вы решите использовать эту архитектуру.

> [!NOTE]
> **µFeatures**
>
> Ранее эта архитектура была известна как µFeatures. Мы переименовали её в Модульную архитектуру (TMA), чтобы лучше отразить её назначение и лежащие в её основе принципы.


## Основной принцип {#core-principle}

Разработчики должны иметь возможность **быстро собирать, тестировать и проверять** свои возможности независимо от основного приложения, при этом гарантируя надёжную работу функций Xcode, таких как предпросмотр интерфейса, автодополнение кода и отладка.

## Что такое модуль {#what-is-a-module}

Модуль представляет собой возможность приложения и состоит из следующих пяти таргетов (здесь «таргет» означает таргет Xcode):

- **Исходный код:** Содержит исходный код возможности (Swift, Objective-C, C++, JavaScript…) и её ресурсы (изображения, шрифты, storyboard-файлы, xib-файлы).
- **Интерфейс:** Это сопутствующий таргет, содержащий публичный интерфейс и модели возможности.
- **Тесты:** Содержит модульные и интеграционные тесты возможности.
- **Тестирование:** Предоставляет тестовые данные, которые можно использовать в тестах и примерном приложении. Также он предоставляет моки для классов и протоколов модуля, которые могут использоваться другими возможностями, как мы увидим далее.
- **Пример:** Содержит пример приложения, которое разработчики могут использовать для проверки возможности в определённых условиях (разные языки, размеры экранов, настройки).

Мы рекомендуем соблюдать соглашение об именах для таргетов, что можно обеспечить в вашем проекте благодаря DSL Tuist.

| Таргет | Зависимости | Содержимое |
| ---- | ---- | ---- |
| `Feature` | `FeatureInterface` | Исходный код и ресурсы |
| `FeatureInterface` | - | Публичный интерфейс и модели |
| `FeatureTests` | `Feature`, `FeatureTesting` | Модульные и интеграционные тесты |
| `FeatureTesting` | `FeatureInterface` | Тестовые данные и моки |
| `FeatureExample` | `FeatureTesting`, `Feature` | Пример приложения |

> [!TIP]
> **Предпросмотр интерфейса**
>
> `Feature` может использовать `FeatureTesting` в качестве ресурса разработки, чтобы включить предпросмотр интерфейса


> [!WARNING]
> **Директивы компилятора вместо тестовых таргетов**
>
> В качестве альтернативы вы можете использовать директивы компилятора, чтобы включать тестовые данные и моки в таргеты `Feature` или `FeatureInterface` при компиляции для `Debug`. Это упрощает граф зависимостей, но приводит к компиляции кода, который не понадобится для запуска приложения.


## Зачем нужен модуль {#why-a-module}

### Чёткие и лаконичные API {#clear-and-concise-apis}

Когда весь исходный код приложения находится в одном таргете, очень легко создать неявные зависимости в коде и получить так называемый «спагетти-код». Всё сильно связано, состояние иногда непредсказуемо, а внесение новых изменений становится кошмаром. Когда мы определяем возможности в независимых таргетах, нам нужно проектировать публичные API как часть реализации возможности. Нам необходимо решить, что должно быть публичным, как должна использоваться наша возможность и что должно оставаться приватным. У нас больше контроля над тем, как клиенты нашей возможности будут её использовать, и мы можем обеспечивать лучшие практики, проектируя безопасные API.

### Небольшие модули {#small-modules}

[Разделяй и властвуй](https://en.wikipedia.org/wiki/Divide_and_conquer). Работа с небольшими модулями позволяет сосредоточиться и тестировать возможность изолированно. Кроме того, циклы разработки становятся намного быстрее, поскольку компиляция более избирательна: компилируются только компоненты, необходимые для работы нашей возможности. Компиляция всего приложения требуется лишь в самом конце работы, когда нужно интегрировать возможность в приложение.

### Переиспользование {#reusability}

Повторное использование кода между приложениями и другими продуктами, такими как расширения, поощряется с помощью фреймворков или библиотек. Благодаря модульной структуре их повторное использование становится довольно простым. Мы можем создать расширение iMessage, виджет Today или приложение watchOS, просто комбинируя существующие модули и добавляя _(при необходимости)_ специфичные для платформы слои пользовательского интерфейса.

## Зависимости {#dependencies}

Когда один модуль зависит от другого, он объявляет зависимость от его таргета интерфейса. Преимущество такого подхода двоякое. Он предотвращает связывание реализации одного модуля с реализацией другого и ускоряет чистые сборки, поскольку компилируется только реализация нашей возможности и интерфейсы прямых и транзитивных зависимостей. Этот подход вдохновлён идеей SwiftRock о [сокращении времени сборки iOS за счёт использования интерфейсных модулей](https://swiftrocks.com/reducing-ios-build-times-by-using-interface-targets).

Зависимость от интерфейсов требует, чтобы приложения строили граф реализаций во время выполнения и внедряли зависимости в модули, которым они нужны. Хотя TMA не навязывает конкретный способ решения этой задачи, мы рекомендуем использовать решения или паттерны внедрения зависимостей, которые не добавляют косвенности на этапе сборки и не используют платформенные API, не предназначенные для этой цели.

## Типы продуктов {#product-types}

При сборке модуля вы можете выбрать между **библиотеками и фреймворками**, а также между **статической и динамической линковкой** для таргетов. Без Tuist принятие этого решения немного сложнее, поскольку нужно вручную настраивать граф зависимостей. Однако благодаря Tuist Projects эта проблема исчезает.

Мы рекомендуем использовать динамические библиотеки или фреймворки во время разработки, применяя <.localized_link href="/guides/features/projects/synthesized-files#bundle-accessors">аксессоры бандлов</.localized_link>, чтобы отделить логику доступа к бандлу от типа таргета (библиотека или фреймворк). Это ключевой момент для быстрого времени компиляции и обеспечения надёжной работы [предпросмотра SwiftUI](https://developer.apple.com/documentation/swiftui/previews-in-xcode). Для релизных сборок используйте статические библиотеки или фреймворки, чтобы обеспечить быструю загрузку приложения. Вы можете использовать <.localized_link href="/guides/features/projects/dynamic-configuration#configuration-through-environment-variables">динамическую конфигурацию</.localized_link>, чтобы изменять тип продукта на этапе генерации:

```bash
# You'll have to read the value of the variable from the manifest
# and use it to change the linking type
TUIST_PRODUCT_TYPE=static-library tuist generate
```

```swift
// You can place this in your manifest files or helpers
// and use the returned value when instantiating targets.
func productType() -> Product {
    if case let .string(productType) = Environment.productType {
        return productType == "static-library" ? .staticLibrary : .framework
    } else {
        return .framework
    }
}
```


> [!WARNING]
> **Объединяемые библиотеки**
>
> Apple попыталась упростить переключение между статическими и динамическими библиотеками, представив [объединяемые библиотеки](https://developer.apple.com/documentation/xcode/configuring-your-project-to-use-mergeable-libraries). Однако это вносит недетерминированность на этапе сборки, из-за чего сборка становится невоспроизводимой и её сложнее оптимизировать, поэтому мы не рекомендуем использовать этот подход.


## Код {#code}

TMA не навязывает конкретную архитектуру кода и паттерны для ваших модулей. Тем не менее, мы хотели бы поделиться несколькими советами, основанными на нашем опыте:

- **Использование возможностей компилятора — это хорошо.** Чрезмерное reliance на компилятор может снизить продуктивность и привести к нестабильной работе некоторых функций Xcode, таких как предпросмотр. Мы рекомендуем использовать компилятор для внедрения хороших практик и раннего выявления ошибок, но не до такой степени, чтобы код становился сложным для чтения и поддержки.
- **Используйте макросы Swift умеренно.** Они могут быть очень мощными, но также усложняют чтение и поддержку кода.
- **Принимайте платформу и язык такими, какие они есть, не абстрагируйте их.** Попытки создать сложные уровни абстракции могут оказаться контрпродуктивными. Платформа и язык достаточно мощны, чтобы создавать отличные приложения без необходимости в дополнительных уровнях абстракции. Используйте хорошие практики программирования и паттерны проектирования как ориентир при разработке ваших функций.
