# Рекомендации {#best-practices}

За годы работы с разными командами и проектами мы выявили набор рекомендаций, которых советуем придерживаться при работе с Tuist и проектами Xcode. Эти практики не являются обязательными, но они помогут структурировать проекты так, чтобы их было проще поддерживать и масштабировать.

## Xcode {#xcode}

### Нежелательные подходы {#discouraged-patterns}

#### Конфигурации для моделирования удалённых сред {#configurations-to-model-remote-environments}

Многие организации используют конфигурации сборки для моделирования разных удалённых сред (например, `Debug-Production` или `Release-Canary`), но у такого подхода есть недостатки:

- **Несогласованность:** Если в графе зависимостей встречаются несогласованные конфигурации, система сборки может использовать неверную конфигурацию для некоторых целей.
- **Сложность:** В проекте может накопиться длинный список локальных конфигураций и удалённых сред, которые трудно анализировать и поддерживать.

Конфигурации сборки предназначены для разных настроек сборки, и проектам редко требуется больше, чем просто `Debug` и `Release`. Потребность в моделировании разных сред можно решить иначе:

- **В сборках Debug:** Вы можете включить в приложение все конфигурации, доступные при разработке (например, эндпоинты), и переключать их во время выполнения. Переключение можно реализовать через переменные среды запуска схемы или через интерфейс внутри приложения.
- **В сборках Release:** Для релиза можно включить только ту конфигурацию, к которой привязана сборка release, и исключить логику переключения конфигураций во время выполнения с помощью директив компилятора.

> [!NOTE]
> **Нестандартные конфигурации**
>
> Хотя Tuist поддерживает нестандартные конфигурации и упрощает их управление по сравнению с обычными проектами Xcode, вы получите предупреждения, если конфигурации не согласованы в графе зависимостей. Это помогает обеспечить надёжность сборки и предотвращает проблемы, связанные с конфигурациями.


## Генерируемые проекты

### Сборочные папки

В Tuist 4.62.0 добавлена поддержка **сборочных папок** (синхронизированных групп Xcode) — функции, появившейся в Xcode 16 для уменьшения конфликтов слияния.

Хотя шаблоны с подстановочными знаками в Tuist (например, `Sources/**/*.swift`) уже устраняют конфликты слияния в генерируемых проектах, сборочные папки дают дополнительные преимущества:

- **Автоматическая синхронизация**: структура проекта остаётся синхронизированной с файловой системой — при добавлении или удалении файлов не нужно перегенерировать проект
- **Рабочие процессы, удобные для ИИ**: ассистенты и агенты могут изменять кодовую базу без триггера перегенерации проекта
- **Более простая конфигурация**: задавайте пути к папкам вместо управления явными списками файлов

Мы рекомендуем перейти на сборочные папки вместо традиционных атрибутов `Target.sources` и `Target.resources` для более эффективного процесса разработки.

::: code-group

```swift [With buildable folders]
let target: Target = .target(
  name: "App",
  destinations: .iOS,
  product: .app,
  bundleId: "dev.tuist.App",
  buildableFolders: ["App/Sources", "App/Resources"]
)
```

```swift [Without buildable folders]
let target: Target = .target(
  name: "App",
  destinations: .iOS,
  product: .app,
  bundleId: "dev.tuist.App",
  sources: ["App/Sources/**"],
  resources: ["App/Resources/**"]
)
```

:::

### Зависимости

#### Фиксация разрешённых версий на CI

При установке зависимостей Swift Package Manager на CI мы рекомендуем использовать флаг `--force-resolved-versions` для обеспечения детерминированных сборок:

```bash
tuist install --force-resolved-versions
```

Этот флаг гарантирует, что зависимости разрешаются с точными версиями, зафиксированными в `Package.resolved`, устраняя проблемы, вызванные недетерминированностью разрешения зависимостей. Это особенно важно на CI, где критична воспроизводимость сборок.

#### Кэшированная установка зависимостей на GitHub Actions {#dependency-cache-volumes}

Для генерируемых проектов используйте [tuist/install](https://github.com/tuist/install), чтобы установить зависимости, зафиксированные в `Package.resolved`, и кэшировать их между запусками. Действие автоматически использует <.localized_link href="/guides/features/runners/cache-volumes">тома кэша</.localized_link> на Tuist Runners и кэш GitHub на других раннерах.

```yaml
name: Generate project
on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read

jobs:
  generate:
    runs-on: tuist-macos
    steps:
      - uses: actions/checkout@v4
      - uses: jdx/mise-action@v4
      - uses: tuist/install@v1
      - run: tuist generate --no-open
```

Для проекта в подкаталоге укажите его путь относительно 체크아웃a:

```yaml
- uses: tuist/install@v1
  with:
    path: apps/ios
```

Дополнительные параметры см. в [справке по действию](https://github.com/tuist/install#usage).

### Агентная разработка и рабочие деревья {#agentic-coding-and-worktrees}

Агенты кодирования и люди всё чаще работают параллельно: разработчик держит открытым рабочее дерево для ревьюируемой функции, пока один или несколько агентов итерируют по своим веткам в соседних рабочих деревьях. Несколько решений по проекту делают этот процесс гораздо удобнее.

#### Используйте сборочные папки для изменений, вносимых агентом {#worktrees-buildable-folders}

Когда агент добавляет или удаляет файлы, всё, что зависит от списка файлов в `Project.swift`, требует `tuist generate` перед повторной сборкой проекта. [Сборочные папки](#buildable-folders) переносят эту ответственность на синхронизированные группы Xcode, поэтому изменения в дереве файлов больше не вызывают перегенерацию.

Совместите это с `generated-projects` <.localized_link href="/guides/features/agentic-coding/skills">скиллом</.localized_link>, который обучает агентов повседневному рабочему процессу проекта Tuist.

#### Не изолируйте кэш для каждого рабочего дерева {#worktrees-shared-cache}

Tuist следует <.localized_link href="/cli/directories">спецификации базовых директорий XDG</.localized_link>, поэтому по умолчанию все рабочие деревья на одной машине разделяют `~/.cache/tuist` и `~/.local/state/tuist`. Это именно то, что нужно: хелперы, скомпилированные в одном рабочем дереве, плагины, скачанные в другом, и бинарные файлы из кэша модулей, полученные третьим, — все они пригодны для повторного использования.

Параллельные вызовы `tuist` в разных рабочих деревьях безопасно выполнять одновременно. Не направляйте `TUIST_XDG_CACHE_HOME` на путь внутри рабочего дерева, если вам не нужна изоляция: это заставит каждое рабочее дерево заново прогревать хелперы, плагины и бинарные файлы.

#### Храните временные данные SwiftPM отдельно для каждого рабочего дерева {#worktrees-swiftpm-scratch}

Swift Package Manager управляет путями самостоятельно. `--scratch-path` — это изменяемое рабочее состояние, по умолчанию равное `.build`, а `--cache-path` — общая директория кэша. Эти два пути не следует считать одинаковыми, когда активно несколько рабочих деревьев.

Поведение `tuist install` по умолчанию в Tuist уже хранит временные данные SwiftPM в директории пакета, поэтому каждое рабочее дерево получает свой собственный `.build`. Сохраняйте эту изоляцию. Общая директория временных данных SwiftPM может смешивать клоны, промежуточные файлы сборки, плагины, макросы и файлы блокировок из несвязанных веток.

Если вы передаете аргументы SwiftPM через `tuist install -- ...` или через `installOptions` в `Tuist.swift`, используйте общий `--cache-path` для ускорения загрузки зависимостей, но оставьте `--scratch-path` незаданным или укажите путь внутри рабочего дерева:

```swift
import ProjectDescription

let tuist = Tuist(
    project: .tuist(
        installOptions: .options(
            passthroughSwiftPackageManagerArguments: [
                "--cache-path",
                "/Users/Shared/swiftpm/cache/xcode-16-macos",
            ]
        )
    )
)
```

Используйте обертку или переменную окружения CI для пути к кэшу, если он должен различаться в зависимости от Xcode, инструментария Swift или платформы. Не коммитьте общий `--scratch-path` в репозиторий.

Если состояние зависимостей выглядит поврежденным только в одном рабочем дереве, удалите директорию `.build` этого рабочего дерева и снова запустите `tuist install`. Если общий кэш SwiftPM вызывает подозрения во всех рабочих деревьях, используйте `swift package purge-cache` перед повторной установкой зависимостей.

#### Опирайтесь на кэш модулей {#worktrees-module-cache}

<.localized_link href="/guides/features/cache/module-cache">Кэш модулей</.localized_link> делает параллельную работу с рабочими деревьями управляемой. Поскольку Tuist вычисляет детерминированный <.localized_link href="/guides/features/projects/hashing">хеш</.localized_link> для каждой цели, два рабочих дерева, указывающие на ветки с общей историей, будут использовать одни и те же бинарные файлы. Запускайте `tuist cache` при каждом коммите в `main` из CI; локально `tuist generate` в каждом рабочем дереве забирает из кэша всё возможное и собирает только то, что действительно изменилось в вашей ветке.

Если рабочее дерево переходит к сборке из исходного кода, хотя вы ожидали попадания в кэш, следуйте <.localized_link href="/guides/features/projects/hashing#debugging">шагам отладки хеширования</.localized_link>; недетерминированные хеши (обычно вызванные абсолютными путями в проекте) являются наиболее частой причиной и явно проявляются при сравнении двух рабочих деревьев.

#### Ускорьте разрешение Swift-пакетов с помощью реестра {#worktrees-registry}

Каждое рабочее дерево разрешает Swift-пакеты независимо. В проекте с большим графом зависимостей это быстро накапливается. Переход на <.localized_link href="/guides/features/package-registries/swift">Tuist Registry</.localized_link> позволяет избежать повторного клонирования git-историй и сокращает время разрешения с минут до секунд.

#### Предоставьте агентам доступ к аналитике проекта {#worktrees-mcp}

Когда сборки и тесты запускаются во многих рабочих деревьях, самое полезное, что может сделать агент, — это определить, *какие* из этих запусков регрессировали, какие тесты нестабильны или как изменился размер бандла. Tuist предоставляет эти данные через <.localized_link href="/guides/features/agentic-coding/mcp">MCP-сервер</.localized_link> и пакет <.localized_link href="/guides/features/agentic-coding/skills">Skills</.localized_link>. Выберите один вариант для каждого рабочего процесса и придерживайтесь его; смешивание обоих для одной задачи часто приводит к непоследовательному поведению агента.
