# Лучшие практики {#best-practices}

За годы работы с разными командами и проектами мы выявили набор лучших практик, которые рекомендуем соблюдать при работе с Tuist и проектами Xcode. Эти практики не являются обязательными, но они помогут вам структурировать проекты так, чтобы их было легче поддерживать и масштабировать.

## Xcode {#xcode}

### Нежелательные паттерны {#discouraged-patterns}

#### Конфигурации для моделирования удаленных сред {#configurations-to-model-remote-environments}

Многие организации используют конфигурации сборки для моделирования различных удаленных сред (например, `Debug-Production` или `Release-Canary`), но у этого подхода есть недостатки:

- **Несогласованность:** Если в графе зависимостей есть несогласованности конфигураций, система сборки может использовать неправильную конфигурацию для некоторых целей.
- **Сложность:** В проектах может появиться длинный список локальных конфигураций и удаленных сред, которые трудно анализировать и поддерживать.

Конфигурации сборки предназначены для хранения различных настроек сборки, и проектам редко требуется больше, чем просто `Debug` и `Release`. Потребность в моделировании различных сред можно решить иначе:

- **В сборках Debug:** Вы можете включить в приложение все конфигурации, которые должны быть доступны в разработке (например, эндпоинты), и переключать их во время выполнения. Переключение может происходить либо с помощью переменных среды запуска схемы, либо через пользовательский интерфейс внутри приложения.
- **В сборках Release:** В случае релиза вы можете включить только ту конфигурацию, к которой привязана релизная сборка, и не включать логику переключения конфигураций во время выполнения, используя директивы компилятора.

> [!NOTE]
> **Нестандартные конфигурации**
>
> Хотя Tuist поддерживает нестандартные конфигурации и упрощает их управление по сравнению с обычными проектами Xcode, вы получите предупреждения, если конфигурации не согласованы во всем графе зависимостей. Это помогает обеспечить надежность сборки и предотвращает проблемы, связанные с конфигурацией.


## Сгенерированные проекты

### Папки, доступные для сборки

Tuist 4.62.0 добавил поддержку **папок, доступных для сборки** (синхронизированных групп Xcode) — функции, представленной в Xcode 16 для уменьшения конфликтов слияния.

Хотя шаблоны с подстановочными знаками Tuist (например, `Sources/**/*.swift`) уже устраняют конфликты слияния в сгенерированных проектах, папки, доступные для сборки, предлагают дополнительные преимущества:

- **Автоматическая синхронизация**: структура вашего проекта остается синхронизированной с файловой системой — не нужно перегенерировать проект при добавлении или удалении файлов
- **Рабочие процессы, дружественные к ИИ**: помощники по кодированию и агенты могут изменять вашу кодовую базу, не запуская перегенерацию проекта
- **Более простая конфигурация**: определяйте пути к папкам вместо управления явными списками файлов

Мы рекомендуем использовать папки, доступные для сборки, вместо традиционных атрибутов `Target.sources` и `Target.resources` для более эффективного процесса разработки.

::: code-group

```swift [With buildable folders]
let target = Target(
  name: "App",
  buildableFolders: ["App/Sources", "App/Resources"]
)
```

```swift [Without buildable folders]
let target = Target(
  name: "App",
  sources: ["App/Sources/**"],
  resources: ["App/Resources/**"]
)
```
<!-- -->
:::

### Зависимости

#### Принудительное использование разрешенных версий на CI

При установке зависимостей Swift Package Manager на CI мы рекомендуем использовать флаг `--force-resolved-versions`, чтобы обеспечить детерминированные сборки:

```bash
tuist install --force-resolved-versions
```

Этот флаг гарантирует, что зависимости разрешаются с использованием точных версий, закрепленных в `Package.resolved`, что устраняет проблемы, вызванные недетерминизмом при разрешении зависимостей. Это особенно важно на CI, где воспроизводимость сборок имеет решающее значение.

#### Кэшированная установка зависимостей на GitHub Actions {#dependency-cache-volumes}

Для сгенерированных проектов используйте [tuist/install](https://github.com/tuist/install) для установки зависимостей, закрепленных в `Package.resolved`, и их кэширования между запусками. Он автоматически использует <.localized_link href="/guides/features/runners/cache-volumes">тома кэша</.localized_link> на Tuist Runners и кэш GitHub на других раннерах.

```yaml
name: Generate project
on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read

jobs:
  generate:
    runs-on: tuist-macos
    steps:
      - uses: actions/checkout@v4
      - uses: jdx/mise-action@v4
      - uses: tuist/install@v1
      - run: tuist generate --no-open
```

Для проекта в подкаталоге передайте его путь относительно 체크아웃нутого репозитория:

```yaml
- uses: tuist/install@v1
  with:
    path: apps/ios
```

Смотрите [справочник по действию](https://github.com/tuist/install#usage) для дополнительных опций.

### Агентное программирование и рабочие деревья {#agentic-coding-and-worktrees}

Агенты по кодированию и люди-разработчики все чаще работают параллельно: разработчик держит открытым рабочее дерево для функции, которую он проверяет, в то время как один или несколько агентов итерируют свои собственные ветки в соседних рабочих деревьях. Несколько решений по проекту делают этот процесс гораздо более гладким.

#### Используйте папки, доступные для сборки, для изменений, вносимых агентом {#worktrees-buildable-folders}

Когда агент добавляет или удаляет файлы, все, что зависит от списка файлов в `Project.swift`, требует `tuist generate` перед повторной сборкой проекта. [Папки, доступные для сборки](#buildable-folders) перекладывают эту ответственность на синхронизированные группы Xcode, поэтому изменения в дереве файлов больше не вызывают перегенерацию.

Сочетайте это с `generated-projects` <.localized_link href="/guides/features/agentic-coding/skills">навыком</.localized_link>, который обучает агентов повседневному рабочему процессу проекта Tuist.

#### Не изолируйте кэш для каждого рабочего дерева {#worktrees-shared-cache}

Tuist следует <.localized_link href="/cli/directories">спецификации базовых директорий XDG</.localized_link>, поэтому по умолчанию каждое рабочее дерево на одной машине разделяет `~/.cache/tuist` и `~/.local/state/tuist`. Это именно то, что нужно: хелперы, скомпилированные в одном рабочем дереве, плагины, загруженные в другом, и бинарные файлы кэша модулей, полученные третьим, — все они пригодны для повторного использования.

Параллельные вызовы `tuist` across рабочих деревьев безопасны для одновременного выполнения. Не указывайте `TUIST_XDG_CACHE_HOME` на путь, локальный для рабочего дерева, если вам специально не нужна изоляция; в противном случае каждое рабочее дерево будет вынуждено повторно прогревать хелперы, плагины и бинарные файлы.

#### Сохраняйте временные файлы SwiftPM отдельными для каждого рабочего дерева {#worktrees-swiftpm-scratch}

Swift Package Manager имеет собственные элементы управления путями. `--scratch-path` — это изменяемое рабочее состояние, по умолчанию равное `.build`, а `--cache-path` — это общая директория кэша. Эти два пути не следует обрабатывать одинаково, когда активно несколько рабочих деревьев.

Поведение `tuist install` по умолчанию в Tuist уже хранит временные файлы SwiftPM в директории пакета, поэтому каждое рабочее дерево получает свою собственную директорию `.build`. Сохраняйте эту изоляцию. Одна общая директория временных файлов SwiftPM может смешивать клоны, промежуточные файлы сборки, плагины, макросы и файлы блокировок из несвязанных веток.

Если вы передаете аргументы SwiftPM через `tuist install -- ...` или через `installOptions` в `Tuist.swift`, используйте общий `--cache-path` для ускорения загрузки зависимостей, но оставьте `--scratch-path` незаданным или укажите путь, локальный для рабочего дерева:

```swift
import ProjectDescription

let tuist = Tuist(
    project: .tuist(
        installOptions: .options(
            passthroughSwiftPackageManagerArguments: [
                "--cache-path",
                "/Users/Shared/swiftpm/cache/xcode-16-macos",
            ]
        )
    )
)
```

Используйте обертку или переменную окружения CI для пути к кэшу, если он должен различаться в зависимости от Xcode, инструментария Swift или платформы. Не добавляйте в репозиторий общий `--scratch-path`.

Если состояние зависимостей выглядит поврежденным только в одном рабочем дереве, удалите директорию `.build` этого рабочего дерева и снова запустите `tuist install`. Если общий кэш SwiftPM вызывает подозрения во всех рабочих деревьях, используйте `swift package purge-cache` перед повторной установкой зависимостей.

#### Опирайтесь на кэш модулей {#worktrees-module-cache}

<.localized_link href="/guides/features/cache/module-cache">Кэш модулей</.localized_link> делает параллельную работу с рабочими деревьями управляемой. Поскольку Tuist вычисляет детерминированный <.localized_link href="/guides/features/projects/hashing">хеш</.localized_link> для каждой цели, два рабочих дерева, указывающие на ветки с общей историей, будут использовать одни и те же бинарные файлы. Запускайте `tuist cache` при каждом коммите в `main` из CI; локально `tuist generate` в каждом рабочем дереве загружает из кэша всё возможное и собирает только то, что действительно изменилось в вашей ветке.

Если рабочее дерево переключается на сборку из исходного кода, когда вы ожидали попадания в кэш, следуйте <.localized_link href="/guides/features/projects/hashing#debugging">шагам отладки хеширования</.localized_link>; недетерминированные хеши (обычно вызванные абсолютными путями в проекте) являются наиболее частой причиной, и они явно проявляются при сравнении двух рабочих деревьев.

#### Ускорьте разрешение пакетов Swift с помощью реестра {#worktrees-registry}

Каждое рабочее дерево разрешает Swift-пакеты независимо. В проекте с большим графом зависимостей это быстро накапливается. Переход на <.localized_link href="/guides/features/package-registries/swift">Tuist Registry</.localized_link> позволяет избежать повторного клонирования git-историй и сокращает время разрешения зависимостей с минут до секунд.

#### Предоставьте агентам доступ к аналитике проекта {#worktrees-mcp}

Когда сборки и тесты выполняются во многих рабочих деревьях, самое полезное, что может сделать агент, — это определить, *какие* из этих запусков привели к регрессии, какие тесты нестабильны или как изменился размер пакета. Tuist предоставляет эти данные через <.localized_link href="/guides/features/agentic-coding/mcp">MCP-сервер</.localized_link> и пакет <.localized_link href="/guides/features/agentic-coding/skills">Skills</.localized_link>. Выберите один вариант для каждого рабочего процесса и придерживайтесь его; использование обоих для одной задачи часто приводит к непоследовательному поведению агента.
