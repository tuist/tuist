# Покрытие кода Gradle {#gradle-code-coverage}

Покрытие кода показывает, какие строки вашего кода выполнили тесты. Плагин Tuist для Gradle измеряет покрытие ваших задач тестирования с помощью JaCoCo и загружает его при каждом запуске тестов, а Tuist объединяет результаты всех запусков одного коммита в единую метрику для проекта, каждого проекта Gradle и каждого файла. На странице **Покрытие кода** панели управления эти данные отображаются по каждому коммиту и в виде тренда для каждой ветки.

> [!IMPORTANT]
> **Требования**
>
> - Подключен плагин Gradle `dev.tuist`, как описано в разделе <.localized_link href="/guides/get-started/gradle-project">Начало работы с проектом Gradle</.localized_link>
> - Ваш проект находится в репозитории Git: запуск вне репозитория загружает результаты тестов, но не данные покрытия

## Настройка {#setup}

### Включение покрытия {#turn-coverage-on}

Включите покрытие в блоке `tuist` файла `settings.gradle.kts`:

```kotlin
tuist {
    coverage {
        enabled = true
    }
}
```

Или включите его для одного запуска, например задания CI, с помощью переменной окружения, которая имеет приоритет над настройкой в любом случае:

```sh
TUIST_TEST_COVERAGE=1 ./gradlew test
```

Задачи тестирования с включенным и выключенным покрытием имеют разные записи в кэше сборки (см. [Влияние на производительность](#performance-impact)), поэтому предпочтительнее использовать настройку, когда сборки CI и локальные сборки используют общий кэш: включение покрытия только в CI предотвращает повторное использование результатов тестов друг друга.

При включенном покрытии плагин применяет плагин Gradle `jacoco` ко всем JVM-проектам. Агент JaCoCo берется из репозиториев вашего проекта, как если бы вы подключили плагин самостоятельно. Проект, который уже настроил JaCoCo, сохраняет свои настройки, и его собственные отчеты продолжают работать.

### Проекты Android {#android-projects}

Плагин измеряет локальные модульные тесты проектов Android, такие как `testDebugUnitTest`. Инструментированные тесты, выполняемые на устройстве или эмуляторе, не измеряются.

Если ваши модульные тесты используют Robolectric, укажите JaCoCo включать классы, которые загружает Robolectric. Robolectric определяет классы вашего приложения в своем собственном загрузчике классов, а JaCoCo по умолчанию пропускает такие классы, поэтому код, выполняемый этими тестами, будет отображаться как непокрытый. В файле `build.gradle.kts` проекта Android:

```kotlin
pluginManager.withPlugin("jacoco") {
    tasks.withType<Test>().configureEach {
        extensions.configure<JacocoTaskExtension> {
            isIncludeNoLocationClasses = true
            excludes = listOf("jdk.internal.*")
        }
    }
}
```

Блок применяется только тогда, когда покрытие включено, потому что именно в этот момент плагин применяет `jacoco`.

Модульные тесты Android по умолчанию выполняются на JUnit 4, который записывает покрытие, но не [какой код выполнил каждый тест](#per-test-evidence). Чтобы записать это, запускайте их на платформе JUnit через JUnit Vintage.

### Шардированные запуски {#sharded-runs}

Когда вы <.localized_link href="/guides/features/test-sharding/gradle">шардируете свои тесты</.localized_link>, каждый шард, выполняемый с включенным покрытием, сообщает о покрытии запущенных им тестов, а Tuist объединяет шарды одного запуска в единую метрику. Шард намеренно выполняет часть набора тестов, поэтому это не делает покрытие коммита неполным.

### Завершение каждого коммита в CI {#complete-each-commit}

Покрытие коммита часто формируется из нескольких заданий, например, по одному на каждый шард. Tuist не может определить, когда последнее из них отчиталось, поэтому сообщите ему об этом. Как только все задания тестирования для коммита завершатся, выполните эту команду в задании, которое зависит от всех них:

```sh
./gradlew tuistCoverageComplete
```

Когда одно задание выполняет все тесты коммита, запускайте задачу как шаг после тестов, в том числе при сбоях тестов: запуск с неудавшимися тестами все равно сообщает свое покрытие.

Задача считывает коммит из `GIT_COMMIT` или `HEAD` checkout; передайте `-Ptuist.coverage.commit=<sha>`, чтобы указать другой. Пока коммит не завершен, его покрытие отображается как **В процессе** и не учитывается в тренде ветки.

## Как это работает {#how-it-works}

### Что измеряет Tuist {#what-tuist-measures}

- **Проекты.** Каждый проект Gradle является модулем на панели управления со своим собственным покрытием.
- **Только продуктивный код.** Классы, скомпилированные из исходных наборов тестов, являются тестовым кодом. Tuist хранит их, но исключает из всех метрик.
- **Файлы вашего репозитория.** Класс учитывается для исходного файла, из которого он был скомпилирован, по его пути в вашем репозитории. Сгенерированные исходные файлы и файлы, игнорируемые Git, не отчетятся.
- **Выполнение каждой строки.** JaCoCo записывает факт выполнения кода, а не количество раз, поэтому счетчики executions на панели управления равны 0 или 1.

### Какой код выполнил каждый тест {#per-test-evidence}

Для тестов, выполняемых на платформе JUnit (JUnit 5 или JUnit 4 через JUnit Vintage), плагин также записывает, какой код выполнил каждый тест, и что выполнил каждый тестовый класс вне своих тестов, например, в `@BeforeAll`. Это позволяет Tuist переносить покрытие тестов, которые были пропущены в запуске (см. [Пропущенные тесты](#skipped-tests)). Ничего добавлять в ваши тесты не нужно.

Это работает, когда каждая JVM тестов выполняет один тест за раз, что является способом запуска тестов в Gradle, если вы не включили параллельное выполнение JUnit. Запуск тестовых классов в нескольких JVM с помощью `maxParallelForks` допустим. Тесты, выполняющиеся одновременно в одной JVM, все еще учитываются в покрытии, но не по отдельности.

### Кэш сборки {#build-cache}

Задача тестирования, восстановленная Gradle из кэша сборки или актуальная, не запускает тесты. Ее покрытие все равно загружается: данные JaCoCo являются одним из выходных данных задачи, записанных запуском, который выполнил ее тесты на тех же входных данных.

### Пропущенные тесты {#skipped-tests}

Когда запуск пропускает тесты, Tuist заполняет данные об их покрытии из предыдущего запуска, если код, который они выполняли, не изменился. Если это невозможно, покрытие коммита помечается как **Неполное**. Что пропускает запуск:

- **Задача тестирования проекта исключена** с помощью `-x :app:test`. Ее тесты переносятся из последнего запуска, код которого не изменился.
- **Тесты некоторых проектов** с помощью `./gradlew :core:test` или **некоторые тесты** с помощью `--tests`. Запуск покрывает только то, что вы запросили, поэтому коммит считается неполным, если другой запуск этого коммита не выполнил все тесты.
- **Задача тестирования, остановившаяся при первом сбое** (`failFast`).

Некоторые тесты пропускаются намеренно и не делают коммит неполным:

- **Фильтры в вашем скрипте сборки**, такие как `filter { excludeTestsMatching(...) }`, которые определяют, что выполняет ваш набор тестов.
- **Задачи тестирования, отключенные вашим скриптом сборки** с помощью `enabled = false` или условия `onlyIf`, которое их пропускает.
- **Тесты, которые пропускает <.localized_link href="/guides/features/test-insights/flaky-tests/gradle">карантин</.localized_link>.** Они исключаются так, как если бы были удалены, поэтому строки, покрытые только ими, считаются непокрытыми.
- **Тесты других шардов**, когда вы [разделяете свои тесты на шарды](#sharded-runs).

### Полные и неполные коммиты {#commit-status}

| Статус | Значение |
| --- | --- |
| В процессе | Запуски сообщили о покрытии, но `tuistCoverageComplete` еще не выполнен для этого коммита. |
| Полный | Все тесты запусков коммита выполнены, перенесены из предыдущих запусков или пропущены намеренно. |
| Неполный | Некоторое покрытие не удалось определить, поэтому показатель является нижней границей. |
| Не измерялось | Ни один запуск не сообщил о покрытии для этого коммита. |

Тренд ветки включает только полные коммиты.

## Влияние на производительность {#performance-impact}

JaCoCo инструментализирует классы по мере их загрузки JVM тестов, поэтому ваши скомпилированные классы и записи кэша сборки задач компиляции остаются неизменными независимо от того, включено покрытие или нет. Задачи, читающие все конфигурации зависимостей, такие как генераторы SBOM, также видят агент JaCoCo, поэтому их выходные данные меняются при включении покрытия. Тесты выполняются немного медленнее, и плагин считывает данные JaCoCo после завершения задач тестирования. Задачи тестирования с включенным и выключенным покрытием имеют разные записи в кэше сборки, поэтому первый запуск с включенным покрытием выполнит тесты, даже если их результаты без покрытия уже закэшированы.

## Ограничения {#limitations}

- **Изолированные проекты и конфигурация по требованию.** Такие сборки не настраивают каждый проект, поэтому плагин не может определить, тесты каких проектов пропустил запуск, и запуск тестов некоторых проектов считается полным.
- **Нет покрытия из pull-запросов из форков.** Покрытие загружается только запусками, прошедшими аутентификацию в Tuist, а CI обычно скрывает секреты и токены идентификации от pull-запросов, открытых из форков.

## Запрос данных о покрытии {#querying}

На странице **Покрытие кода** дашборда показан показатель каждого коммита, его модули и файлы с указанием строк, покрытых каждым запуском. Те же данные доступны агентам через <.localized_link href="/guides/features/agentic-coding/mcp">сервер Model Context Protocol</.localized_link>.
