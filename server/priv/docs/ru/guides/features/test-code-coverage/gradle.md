# Покрытие кода в Gradle {#gradle-code-coverage}

Покрытие кода показывает, какие строки вашего кода были выполнены тестами. Плагин Tuist для Gradle измеряет покрытие ваших задач тестирования с помощью JaCoCo и загружает его при каждом запуске тестов. Tuist объединяет результаты всех запусков коммита в одну метрику для всего проекта, каждого проекта Gradle и каждого файла. На странице **Покрытие кода** панели управления эти данные отображаются по каждому коммиту и в виде тренда для каждой ветки.

> [!IMPORTANT]
> **Требования**
>
> - Подключен плагин Gradle `dev.tuist`, как описано в разделе <.localized_link href="/guides/get-started/gradle-project">Начало работы с проектом Gradle</.localized_link>
> - Ваш проект находится в репозитории Git: запуск вне репозитория загружает результаты тестов, но не данные покрытия

## Настройка {#setup}

### Включение покрытия {#turn-coverage-on}

Включите покрытие в блоке `tuist` файла `settings.gradle.kts`:

```kotlin
tuist {
    coverage {
        enabled = true
    }
}
```

Или включите его для одного запуска, например задачи CI, с помощью переменной окружения, которая имеет приоритет над настройкой в любом случае:

```sh
TUIST_TEST_COVERAGE=1 ./gradlew test
```

Задачи тестирования с включенным и выключенным покрытием имеют отдельные записи в кэше сборки (см. [Влияние на производительность](#performance-impact)), поэтому предпочтительнее использовать настройку, когда ваши сборки CI и локальные сборки используют общий кэш: включение покрытия только в CI предотвращает повторное использование результатов тестов друг друга.

При включенном покрытии плагин применяет плагин Gradle `jacoco` к каждому JVM-проекту. Агент JaCoCo загружается из репозиториев вашего проекта, так же как если бы вы подключили плагин самостоятельно. Проект, который уже настроил JaCoCo, сохраняет свои настройки, и его собственные отчеты продолжают работать.

### Проекты Android {#android-projects}

Плагин измеряет локальные модульные тесты проектов Android, такие как `testDebugUnitTest`. Инструментированные тесты, выполняемые на устройстве или эмуляторе, не измеряются.

Если ваши модульные тесты используют Robolectric, укажите JaCoCo включать классы, которые загружает Robolectric. Robolectric определяет классы вашего приложения в собственном загрузчике классов, а JaCoCo по умолчанию пропускает такие классы, поэтому код, выполняемый этими тестами, будет показан как непокрытый. В файле `build.gradle.kts` проекта Android:

```kotlin
pluginManager.withPlugin("jacoco") {
    tasks.withType<Test>().configureEach {
        extensions.configure<JacocoTaskExtension> {
            isIncludeNoLocationClasses = true
            excludes = listOf("jdk.internal.*")
        }
    }
}
```

Блок применяется только при включенном покрытии, так как именно тогда плагин применяет `jacoco`.

Модульные тесты Android по умолчанию выполняются на JUnit 4, который записывает покрытие, но не [какой код выполнил каждый тест](#per-test-evidence). Чтобы записать это, запускайте их на платформе JUnit через JUnit Vintage.

### Разделенные запуски {#sharded-runs}

Когда вы <.localized_link href="/guides/features/test-sharding/gradle">разделяете свои тесты</.localized_link>, каждый шард, выполняющийся с включенным покрытием, сообщает о покрытии запущенных им тестов, и Tuist объединяет шарды одного запуска в одну метрику. Шард намеренно выполняет часть набора тестов, поэтому это не делает покрытие коммита неполным.

### Завершение каждого коммита в CI {#complete-each-commit}

Покрытие коммита часто формируется из нескольких задач, например по одной на каждый шард. Tuist не может определить, когда последняя из них завершила отчет, поэтому сообщите ему об этом. Как только все задачи тестирования для коммита завершатся, выполните эту команду в задаче, зависящей от всех них:

```sh
./gradlew tuistCoverageComplete
```

Если одна задача выполняет все тесты коммита, запускайте эту задачу как шаг после тестов, включая случаи сбоя тестов: запуск с упавшими тестами все равно отправляет данные покрытия.

Задача считывает коммит из `GIT_COMMIT` или `HEAD` 체크아웃нутого репозитория; передайте `-Ptuist.coverage.commit=<sha>`, чтобы указать другой. Пока коммит не завершен, его покрытие отображается как **В процессе** и не учитывается в тренде ветки.

## Как это работает {#how-it-works}

### Что измеряет Tuist {#what-tuist-measures}

- **Проекты.** Каждый проект Gradle является модулем на панели управления со своим собственным покрытием.
- **Только продуктивный код.** Классы, скомпилированные из исходных наборов тестов, являются тестовым кодом. Tuist хранит их, но исключает из всех метрик.
- **Файлы вашего репозитория.** Класс учитывается для исходного файла, из которого он был скомпилирован, по его пути в вашем репозитории. Сгенерированные исходники и файлы, игнорируемые Git, не отчетятся.
- **Выполнение каждой строки.** JaCoCo записывает факт выполнения кода, а не количество раз, поэтому счетчики выполнения на панели управления равны 0 или 1.

### Какой код выполнил каждый тест {#per-test-evidence}

Для тестов, выполняющихся на платформе JUnit (JUnit 5 или JUnit 4 через JUnit Vintage), плагин также записывает, какой код выполнил каждый тест, и что выполнил каждый тестовый класс вне своих тестов, например в `@BeforeAll`. Это позволяет Tuist переносить покрытие тестов, которые были пропущены в запуске (см. [Пропущенные тесты](#skipped-tests)). Ничего добавлять в ваши тесты не нужно.

Это работает, когда каждая JVM для тестов выполняет один тест за раз, что является стандартным поведением Gradle, если вы не включили параллельное выполнение JUnit. Запуск тестовых классов в нескольких JVM с помощью `maxParallelForks` допустим. Тесты, выполняющиеся одновременно в одной JVM, все еще учитываются в покрытии, но не по отдельности.

### Кэш сборки {#build-cache}

Задача тестирования, восстановленная Gradle из кэша сборки или актуальная, не запускает тесты. Ее покрытие все равно загружается: данные JaCoCo являются одним из выводов задачи, записанным запуском, который выполнил ее тесты с теми же входными данными.

### Пропущенные тесты {#skipped-tests}

Когда запуск пропускает тесты, Tuist заполняет данные об их покрытии из предыдущего запуска, если код, который они выполняли, не изменился. Если это невозможно, покрытие коммита помечается как **Неполное**. Что пропускает запуск:

- **Задача тестирования проекта исключена** с помощью `-x :app:test`. Ее тесты переносятся из последнего запуска, где их код не изменился.
- **Тесты некоторых проектов** с `./gradlew :core:test`, или **некоторые тесты** с `--tests`. Запуск покрывает только запрошенное, поэтому коммит считается неполным, если другой запуск этого коммита не выполнил все тесты.
- **Задача тестирования, остановившаяся при первом сбое** (`failFast`).

Некоторые тесты пропускаются намеренно и не делают коммит неполным:

- **Фильтры в вашем скрипте сборки**, такие как `filter { excludeTestsMatching(...) }`, которые определяют, что выполняет ваш набор тестов.
- **Задачи тестирования, отключенные в скрипте сборки**, с помощью `enabled = false` или условия `onlyIf`, которое их пропускает.
- **Тесты, которые пропускает <.localized_link href="/guides/features/test-insights/flaky-tests/gradle">карантин</.localized_link>.** Они исключаются так, как если бы были удалены, поэтому строки, покрытые только ими, считаются непокрытыми.
- **Тесты других шардов**, когда вы [разделяете тесты на шарды](#sharded-runs).

### Полные и неполные коммиты {#commit-status}

| Статус | Значение |
| --- | --- |
| В процессе | Запуски сообщили о покрытии, но `tuistCoverageComplete` еще не выполнилась для этого коммита. |
| Завершено | Все тесты запусков коммита были выполнены, перенесены из предыдущих запусков или намеренно пропущены. |
| Неполное | Некоторое покрытие не удалось определить, поэтому показатель является нижней границей. |
| Не измерялось | Ни один запуск не сообщил о покрытии для этого коммита. |

Тренд ветки включает только полные коммиты.

## Влияние на производительность {#performance-impact}

JaCoCo инструментирует классы по мере их загрузки JVM для тестов, поэтому ваши скомпилированные классы и записи кэша сборки для задач компиляции остаются неизменными независимо от того, включено покрытие или нет. Задачи, читающие все конфигурации зависимостей, такие как генераторы SBOM, также видят агент JaCoCo, поэтому их выходные данные меняются при включении покрытия. Тесты выполняются немного медленнее, и плагин считывает данные JaCoCo после завершения задач тестирования. Задачи тестирования с включенным и выключенным покрытием имеют отдельные записи в кэше сборки, поэтому первый запуск с включенным покрытием выполнит тесты, даже если их результаты без покрытия уже закэшированы.

## Ограничения {#limitations}

- **Изолированные проекты и конфигурация по требованию.** Такие сборки не конфигурируют каждый проект, поэтому плагин не может определить, тесты каких проектов были пропущены запуском, и запуск тестов некоторых проектов считается полным.
- **Отсутствие покрытия из pull-реквестов из форков.** Покрытие загружается только запусками, прошедшими аутентификацию в Tuist, а CI-системы обычно не передают секреты и токены идентификации в pull-реквесты, открытые из форков.

## Запрос данных о покрытии {#querying}

Страница **Покрытие кода** в дашборде показывает показатель каждого коммита, его модули и файлы с указанием строк, покрытых каждым запуском. Те же данные доступны агентам через <.localized_link href="/guides/features/agentic-coding/mcp">сервер Model Context Protocol</.localized_link>.
