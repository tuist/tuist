# Покрытие кода Gradle {#gradle-code-coverage}

Покрытие кода показывает, какие строки вашего кода выполнялись тестами. Плагин Tuist для Gradle измеряет покрытие ваших задач тестирования с помощью JaCoCo и загружает его при каждом запуске тестов, а Tuist объединяет результаты всех запусков одного коммита в единый показатель для проекта, каждого проекта Gradle и каждого файла. На странице **Code Coverage** панели управления эти данные отображаются по каждому коммиту и в виде тренда для каждой ветки.

> [!IMPORTANT]
> **Требования**
>
> - Применён плагин Gradle `dev.tuist`, как описано в разделе <.localized_link href="/guides/get-started/gradle-project">Начало работы с проектом Gradle</.localized_link>
> - Ваш проект находится в репозитории Git: запуск вне репозитория загружает результаты тестов, но не данные покрытия

## Настройка {#setup}

### Включение покрытия {#turn-coverage-on}

Включите покрытие в блоке `tuist` вашего файла `settings.gradle.kts`:

```kotlin
tuist {
    coverage {
        enabled = true
    }
}
```

Или включите его для одного запуска, например задания CI, с помощью переменной окружения, которая имеет приоритет над настройкой в любом случае:

```sh
TUIST_TEST_COVERAGE=1 ./gradlew test
```

Задачи тестирования с включённым и выключенным покрытием имеют отдельные записи в кэше сборки (см. [Влияние на производительность](#performance-impact)), поэтому предпочтительнее использовать настройку, когда ваши сборки CI и локальные сборки используют общий кэш: включение покрытия только в CI предотвращает повторное использование результатов тестов друг друга.

При включённом покрытии плагин применяет плагин Gradle `jacoco` ко всем JVM-проектам. Агент JaCoCo загружается из репозиториев вашего проекта, как если бы вы применили плагин самостоятельно. Проект, который уже настроил JaCoCo, сохраняет свои настройки, и его собственные отчёты продолжают работать.

Плагин сообщает только о покрытии кода вашего репозитория, поэтому он ограничивает JaCoCo им: если задача тестирования сама не устанавливает `includes` JaCoCo, агент инструментирует только пакеты классов, которые компилирует ваш репозиторий. В пакете, где зависимости также имеют классы, например тестовая заглушка для `android.util.Log`, инструментируются только классы этого пакета из вашего репозитория. Зависимости, фреймворк Android и ваши тестовые фреймворки выполняются без инструментации, что позволяет сохранять небольшой объём данных JaCoCo и записей кэша сборки для задач тестирования.

Когда покрытие запуска частичное, плагин регистрирует предупреждение с указанием причины, например, проекты, тесты которых не были запущены сборкой. Проекты без модульных тестов, такие как JVM-библиотека, у которой задача `test` не имеет исходных файлов тестов, или Android-библиотека только с инструментированными тестами, никогда не считаются пропущенными.

### Проекты Android {#android-projects}

Плагин измеряет локальные модульные тесты проектов Android, такие как `testDebugUnitTest`. Инструментированные тесты, запускаемые на устройстве или эмуляторе, не измеряются.

Если ваши модульные тесты используют Robolectric, укажите JaCoCo включать классы, которые загружает Robolectric. Robolectric определяет классы вашего приложения в своём собственном загрузчике классов, а JaCoCo по умолчанию пропускает такие классы, поэтому код, выполняемый этими тестами, будет отображаться как непокрытый. В файле `build.gradle.kts` проекта Android:

```kotlin
pluginManager.withPlugin("jacoco") {
    tasks.withType<Test>().configureEach {
        extensions.configure<JacocoTaskExtension> {
            isIncludeNoLocationClasses = true
            excludes = listOf("jdk.internal.*")
        }
    }
}
```

Блок применяется только при включённом покрытии, потому что именно тогда плагин применяет `jacoco`.

Модульные тесты Android по умолчанию запускаются на JUnit 4, который записывает покрытие, но не [какой код выполнял каждый тест](#per-test-evidence). Чтобы записать это, запускайте их на платформе JUnit через JUnit Vintage.

### Разделённые запуски {#sharded-runs}

Когда вы <.localized_link href="/guides/features/test-sharding/gradle">разделяете свои тесты</.localized_link>, каждый шард, запускаемый с включённым покрытием, сообщает о покрытии выполненных им тестов, а Tuist объединяет шарды одного запуска в единый показатель. Шард намеренно выполняет часть набора тестов, поэтому это не делает покрытие коммита неполным.

### Завершение каждого коммита в CI {#complete-each-commit}

Покрытие коммита часто формируется из нескольких заданий, например по одному на каждый шард. Tuist не может определить, когда последнее из них завершило отчёт, поэтому сообщите ему об этом. Как только все тестовые задания для коммита завершатся, выполните эту команду в задании, которое зависит от всех них:

```sh
./gradlew tuistCoverageComplete
```

Если одно задание запускает все тесты коммита, выполняйте задачу как шаг после тестов, в том числе при сбоях тестов: запуск с неудачными тестами всё равно отправляет данные покрытия.

Задача считывает коммит из `HEAD` рабочей копии, то есть коммит, на котором выполнялись ваши тесты; передайте `-Ptuist.coverage.commit=<sha>`, чтобы указать другой. Пока коммит не завершён, его покрытие отображается как **В процессе** и не учитывается в тренде ветки.

## Как это работает {#how-it-works}

### Что измеряет Tuist {#what-tuist-measures}

- **Проекты.** Каждый проект Gradle является модулем на панели управления со своим собственным показателем покрытия.
- **Только продуктивный код.** Классы, скомпилированные из наборов исходных файлов тестов, являются тестовым кодом. Tuist хранит их, но исключает из всех показателей.
- **Файлы вашего репозитория.** Класс учитывается для исходного файла, из которого он был скомпилирован, по его пути в вашем репозитории. Сгенерированные исходные файлы и файлы, игнорируемые Git, не отчитываются.
- **Выполнялась ли каждая строка.** JaCoCo записывает, выполнялся ли код, а не сколько раз, поэтому счётчики выполнения на панели управления равны 0 или 1.

### Какой код выполнял каждый тест {#per-test-evidence}

Для тестов, запускаемых на платформе JUnit (JUnit 5 или JUnit 4 через JUnit Vintage), плагин также записывает, какой код выполнял каждый тест, и что выполнял каждый тестовый класс вне своих тестов, например в `@BeforeAll`. Это позволяет Tuist переносить покрытие тестов, которые были пропущены в запуске (см. [Пропущенные тесты](#skipped-tests)). Ничего добавлять в ваши тесты не нужно.

Это работает, когда каждая JVM для тестов выполняет один тест за раз, что является стандартным поведением Gradle, если вы не включили параллельное выполнение JUnit. Запуск тестовых классов в нескольких JVM с помощью `maxParallelForks` допустим. Тесты, выполняющиеся одновременно в одной JVM, всё ещё учитываются в покрытии, но не по отдельности.

### Кэш сборки {#build-cache}

Задача тестирования, которую Gradle восстанавливает из кэша сборки или которая актуальна, не запускает тесты. Её покрытие всё равно загружается: данные JaCoCo являются одним из выходных данных задачи, записанных запуском, который выполнил её тесты с теми же входными данными.

### Пропущенные тесты {#skipped-tests}

Когда запуск пропускает тесты, Tuist заполняет данные об их покрытии из предыдущего запуска, если код, который они выполняли, не изменился. Если это невозможно, покрытие коммита помечается как **Неполное**. Что может пропустить запуск:

- **Задача тестирования проекта исключена** с помощью `-x :app:test`. Её тесты переносятся из последнего запуска, код которого не изменился.
- **Тесты некоторых проектов** с помощью `./gradlew :core:test` или **некоторые тесты** с помощью `--tests`. Запуск покрывает только то, что вы запросили, поэтому коммит считается неполным, если другой запуск этого коммита не выполнил всё.
- **Задача тестирования, остановившаяся при первом сбое** (`failFast`).

Некоторые тесты намеренно исключаются и не делают коммит неполным:

- **Фильтры в вашем скрипте сборки**, например `filter { excludeTestsMatching(...) }`, которые определяют, какие тесты запускаются.
- **Задачи тестирования, отключенные вашим скриптом сборки**, с помощью `enabled = false` или условия `onlyIf`, которое их пропускает.
- **Тесты, которые пропускает <.localized_link href="/guides/features/test-insights/flaky-tests/gradle">карантин</.localized_link>.** Они исключаются так, как если бы были удалены, поэтому строки, покрытые только ими, считаются непокрытыми.
- **Тесты других шардов**, когда вы [разделяете тесты на шарды](#sharded-runs).

### Полные и неполные коммиты {#commit-status}

| Статус | Значение |
| --- | --- |
| В процессе | Запуски сообщили о покрытии, но `tuistCoverageComplete` ещё не выполнена для этого коммита. |
| Полный | Все тесты запусков коммита выполнились, были перенесены из предыдущих запусков или намеренно пропущены. |
| Неполный | Некоторое покрытие не удалось определить, поэтому показатель является нижней границей. |
| Не измерялось | Ни один запуск не сообщил о покрытии для этого коммита. |

Тренд ветки включает только полные коммиты.

## Влияние на производительность {#performance-impact}

JaCoCo инструментирует классы по мере их загрузки JVM для тестов, поэтому ваши скомпилированные классы и записи кэша сборки задач компиляции остаются неизменными независимо от того, включено покрытие или нет. Задачи, которые читают все конфигурации зависимостей, такие как генераторы SBOM, также видят агент JaCoCo, поэтому их выходные данные изменяются при включении покрытия. Тесты выполняются немного медленнее, и плагин считывает данные JaCoCo после завершения задач тестирования. Задачи тестирования с включенным и отключенным покрытием имеют разные записи в кэше сборки, поэтому первый запуск с включенным покрытием выполнит тесты, даже если их результаты без покрытия уже закэшированы.

## Ограничения {#limitations}

- **Изолированные проекты и конфигурация по требованию.** Такие сборки не конфигурируют каждый проект, поэтому плагин не может определить, тесты каких проектов были пропущены запуском, и запуск тестов некоторых проектов считается полным.
- **Нет покрытия из pull-запросов из форков.** Покрытие загружается только запусками, прошедшими аутентификацию в Tuist, а CI обычно не передает секреты и токены идентификаторов в pull-запросы, открытые из форков.

## Запрос данных о покрытии {#querying}

На странице **Покрытие кода** дашборда отображается показатель каждого коммита, его модули и файлы с указанием строк, покрытых каждым запуском. Те же данные доступны агентам через <.localized_link href="/guides/features/agentic-coding/mcp">сервер Model Context Protocol</.localized_link>.
