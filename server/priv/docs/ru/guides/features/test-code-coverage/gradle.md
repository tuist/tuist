# Покрытие кода Gradle {#gradle-code-coverage}

Покрытие кода показывает, какие строки вашего кода выполнили тесты. Плагин Tuist для Gradle измеряет покрытие ваших задач тестирования с помощью JaCoCo и загружает его при каждом запуске тестов, а Tuist объединяет запуски одного коммита в одну метрику для проекта, каждого проекта Gradle и каждого файла. На странице **Code Coverage** дашборда эти данные отображаются по коммитам и в виде тренда для каждой ветки.

> [!IMPORTANT]
> **Требования**
>
> - Применён плагин Gradle `dev.tuist`, как описано в разделе <.localized_link href="/guides/get-started/gradle-project">Начало работы с проектом Gradle</.localized_link>
> - Ваш проект находится в репозитории Git: запуск вне такого репозитория загрузит результаты тестов, но не данные покрытия

## Настройка {#setup}

### Включение покрытия {#turn-coverage-on}

Включите покрытие в блоке `tuist` файла `settings.gradle.kts`:

```kotlin
tuist {
    coverage {
        enabled = true
    }
}
```

Или включите его для одного вызова, например задачи CI, с помощью переменной окружения, которая имеет приоритет над настройкой в любом случае:

```sh
TUIST_TEST_COVERAGE=1 ./gradlew test
```

Задачи тестирования с включённым и выключенным покрытием имеют отдельные записи в кэше сборки (см. [Влияние на производительность](#performance-impact)), поэтому предпочтительнее использовать настройку, когда ваши CI- и локальные сборки используют общий кэш сборки: включение покрытия только в CI предотвратит повторное использование результатов тестов друг друга.

При включённом покрытии плагин применяет плагин Gradle `jacoco` ко всем JVM-проектам. Агент JaCoCo берётся из репозиториев вашего проекта, как если бы вы сами применили этот плагин. Проект, который уже настроил JaCoCo, сохраняет свои настройки, и его собственные отчёты продолжают работать.

### Проекты Android {#android-projects}

Плагин измеряет локальные модульные тесты проектов Android, такие как `testDebugUnitTest`. Инструментированные тесты, выполняемые на устройстве или эмуляторе, не измеряются.

Если ваши модульные тесты используют Robolectric, укажите JaCoCo включать классы, которые загружает Robolectric. Robolectric определяет классы вашего приложения в своём собственном загрузчике классов, а JaCoCo по умолчанию пропускает такие классы, поэтому код, выполняемый этими тестами, будет отображаться как непокрытый. В файле `build.gradle.kts` проекта Android:

```kotlin
pluginManager.withPlugin("jacoco") {
    tasks.withType<Test>().configureEach {
        extensions.configure<JacocoTaskExtension> {
            isIncludeNoLocationClasses = true
            excludes = listOf("jdk.internal.*")
        }
    }
}
```

Блок применяется только при включённом покрытии, поскольку именно тогда плагин применяет `jacoco`.

Модульные тесты Android по умолчанию выполняются на JUnit 4, который записывает покрытие, но не [какой код выполнил каждый тест](#per-test-evidence). Чтобы записать эти данные, запускайте их на платформе JUnit через JUnit Vintage.

### Шардированные запуски {#sharded-runs}

Когда вы <.localized_link href="/guides/features/test-sharding/gradle">шардируете свои тесты</.localized_link>, каждый шард, выполняющийся с включённым покрытием, сообщает о покрытии запущенных им тестов, а Tuist объединяет шарды одного запуска в одну метрику. Шард намеренно выполняет часть набора тестов, поэтому это не делает покрытие коммита неполным.

### Завершение каждого коммита в CI {#complete-each-commit}

Покрытие коммита часто формируется из нескольких задач, например по одной на каждый шард. Tuist не может определить, когда последняя из них завершила отчёт, поэтому сообщите ему об этом. После завершения всех задач тестирования для коммита выполните эту команду в задаче, зависящей от всех них:

```sh
./gradlew tuistCoverageComplete
```

Если одна задача выполняет все тесты коммита, запускайте эту задачу как шаг после тестов, в том числе при сбоях тестов: запуск с неудачными тестами всё равно отправляет данные покрытия.

Задача считывает коммит из `HEAD` 체크아웃-а, то есть коммит, на котором выполнялись ваши тесты; передайте `-Ptuist.coverage.commit=<sha>`, чтобы указать другой коммит. Пока коммит не завершён, его покрытие отображается как **В процессе** и не учитывается в тренде ветки.

## Как это работает {#how-it-works}

### Что измеряет Tuist {#what-tuist-measures}

- **Проекты.** Каждый проект Gradle является модулем на дашборде со своим собственным покрытием.
- **Только продуктивный код.** Классы, скомпилированные из наборов исходников тестов, являются тестовым кодом. Tuist хранит их, но исключает из всех метрик.
- **Файлы вашего репозитория.** Класс учитывается для исходного файла, из которого он был скомпилирован, согласно его пути в вашем репозитории. Сгенерированные исходники и файлы, игнорируемые Git, не отчитываются.
- **Выполнение каждой строки.** JaCoCo записывает факт выполнения кода, а не количество выполнений, поэтому счётчики выполнения на дашборде равны 0 или 1.

### Какой код выполнил каждый тест {#per-test-evidence}

Для тестов, выполняющихся на платформе JUnit (JUnit 5 или JUnit 4 через JUnit Vintage), плагин также записывает, какой код выполнил каждый тест, и что выполнил каждый тестовый класс вне своих тестов, например в `@BeforeAll`. Это позволяет Tuist переносить покрытие тестов, которые были пропущены в запуске (см. [Пропущенные тесты](#skipped-tests)). Ничего добавлять в ваши тесты не нужно.

Это работает, когда каждая JVM для тестов выполняет один тест за раз, что является стандартным поведением Gradle, если вы не включили параллельное выполнение JUnit. Запуск тестовых классов в нескольких JVM с помощью `maxParallelForks` допустим. Тесты, выполняющиеся одновременно в одной JVM, всё ещё учитываются в покрытии, но не по отдельности.

### Кэш сборки {#build-cache}

Задача тестирования, восстановленная Gradle из кэша сборки или актуальная, не выполняет тесты. Её покрытие всё равно загружается: данные JaCoCo являются одним из выходных артефактов задачи, записанным запуском, который выполнил её тесты на тех же входных данных.

### Пропущенные тесты {#skipped-tests}

Когда запуск пропускает тесты, Tuist заполняет данные об их покрытии из предыдущего запуска, если код, который они выполняли, не изменился. Если это невозможно, покрытие коммита помечается как **Неполное**. Что может пропустить запуск:

- **Задача тестирования проекта исключена** с помощью `-x :app:test`. Её тесты переносятся из последнего запуска, где их код не изменился.
- **Тесты некоторых проектов** с помощью `./gradlew :core:test` или **некоторые тесты** с помощью `--tests`. Запуск покрывает только запрошенное, поэтому коммит считается неполным, если другой запуск этого коммита не выполнил всё.
- **Задача тестирования, остановившаяся при первом сбое** (`failFast`).

Некоторые тесты пропускаются намеренно и не делают коммит неполным:

- **Фильтры в скрипте сборки**, такие как `filter { excludeTestsMatching(...) }`, которые определяют, что выполняется в вашем наборе тестов.
- **Задачи тестирования, отключённые в скрипте сборки** с помощью `enabled = false` или условия `onlyIf`, которое их пропускает.
- **Тесты, которые пропускает <.localized_link href="/guides/features/test-insights/flaky-tests/gradle">карантин</.localized_link>.** Они исключаются так, как если бы были удалены, поэтому строки, покрытые только ими, считаются непокрытыми.
- **Тесты других шардов**, когда вы [разделяете тесты на шарды](#sharded-runs).

### Полные и неполные коммиты {#commit-status}

| Статус | Значение |
| --- | --- |
| В процессе | Запуски сообщили о покрытии, но `tuistCoverageComplete` ещё не выполнена для этого коммита. |
| Полный | Все тесты запусков коммита выполнены, перенесены из предыдущих запусков или намеренно пропущены. |
| Неполный | Некоторое покрытие не удалось определить, поэтому значение является нижней границей. |
| Не измерялось | Ни один запуск не сообщил о покрытии для этого коммита. |

Тренд ветки включает только полные коммиты.

## Влияние на производительность {#performance-impact}

JaCoCo инструментирует классы по мере их загрузки JVM для тестов, поэтому ваши скомпилированные классы и записи кэша сборки для задач компиляции остаются неизменными независимо от того, включено покрытие или нет. Задачи, читающие все конфигурации зависимостей, такие как генераторы SBOM, также видят агент JaCoCo, поэтому их выходные данные изменяются при включении покрытия. Тесты выполняются немного медленнее, и плагин считывает данные JaCoCo после завершения задач тестирования. Задачи тестирования с включённым и выключенным покрытием имеют отдельные записи в кэше сборки, поэтому первый запуск с включённым покрытием выполнит тесты, даже если их результаты без покрытия уже закэшированы.

## Ограничения {#limitations}

- **Изолированные проекты и конфигурация по требованию.** Такие сборки не конфигурируют каждый проект, поэтому плагин не может определить, тесты каких проектов были пропущены запуском, и запуск тестов некоторых проектов считается полным.
- **Нет покрытия из pull-запросов из форков.** Покрытие загружается только запусками, прошедшими аутентификацию в Tuist, а CI обычно скрывает секреты и токены идентичности от pull-запросов, открытых из форков.

## Запрос данных о покрытии {#querying}

На странице **Покрытие кода** панели управления отображается показатель каждого коммита, его модулей и файлов с указанием строк, покрытых каждым запуском. Те же данные доступны агентам через <.localized_link href="/guides/features/agentic-coding/mcp">сервер Model Context Protocol</.localized_link>.
