# Покрытие кода Gradle {#gradle-code-coverage}

Покрытие кода показывает, какие строки вашего кода выполнили тесты. Плагин Tuist для Gradle измеряет покрытие ваших задач тестирования с помощью JaCoCo и загружает его при каждом запуске тестов, а Tuist объединяет запуски коммита в одну метрику для проекта, каждого проекта Gradle и каждого файла. На странице **Покрытие кода** дашборда оно отображается по коммитам и в виде тренда для каждой ветки.

> [!IMPORTANT]
> **Требования**
>
> - Применён плагин Gradle `dev.tuist`, как описано в <.localized_link href="/guides/get-started/gradle-project">Начало работы с проектом Gradle</.localized_link>
> - Ваш проект находится в репозитории Git: запуск вне репозитория загружает результаты тестов, но не покрытие

## Настройка {#setup}

### Включить покрытие {#turn-coverage-on}

Включите покрытие в блоке `tuist` вашего файла `settings.gradle.kts`:

```kotlin
tuist {
    coverage {
        enabled = true
    }
}
```

Или включите его для одного вызова, например задачи CI, с помощью переменной окружения, которая имеет приоритет над настройкой в любом случае:

```sh
TUIST_TEST_COVERAGE=1 ./gradlew test
```

При включённом покрытии плагин применяет плагин Gradle `jacoco` ко всем JVM-проектам. Агент JaCoCo берётся из репозиториев вашего проекта, как если бы вы сами применили этот плагин. Проект, который уже настраивает JaCoCo, сохраняет свои настройки, и его собственные отчёты продолжают работать.

### Запуски шардов {#sharded-runs}

Когда вы <.localized_link href="/guides/features/test-sharding/gradle">разделяете тесты на шарды</.localized_link>, каждый шард, запущенный с включённым покрытием, сообщает о покрытии выполненных им тестов, а Tuist объединяет шарды одного запуска в одну метрику. Шард намеренно выполняет часть набора тестов, поэтому это не делает покрытие коммита неполным.

### Завершать каждый коммит в CI {#complete-each-commit}

Покрытие коммита часто формируется из нескольких задач, например по одной на шард. Tuist не может определить, когда последняя из них завершила отчёт, поэтому сообщите ему об этом. Как только все задачи тестирования для коммита завершатся, выполните эту команду в задаче, зависящей от всех них:

```sh
./gradlew tuistCoverageComplete
```

Задача считывает коммит из `GIT_COMMIT` или `HEAD` 체크아웃нутого репозитория; передайте `-Ptuist.coverage.commit=<sha>`, чтобы указать другой. Пока коммит не завершён, его покрытие отображается как **В процессе** и не учитывается в тренде ветки.

## Как это работает {#how-it-works}

### Что измеряет Tuist {#what-tuist-measures}

- **Проекты.** Каждый проект Gradle является модулем на дашборде со своим собственным покрытием.
- **Только продуктивный код.** Классы, скомпилированные из исходных наборов тестов, являются тестовым кодом. Tuist хранит их, но исключает из всех метрик.
- **Файлы вашего репозитория.** Класс учитывается для исходного файла, из которого он был скомпилирован, по его пути в вашем репозитории. Сгенерированные исходные файлы и файлы, игнорируемые Git, не отчитываются.
- **Выполнение каждой строки.** JaCoCo записывает, выполнялся ли код, а не сколько раз, поэтому счётчики выполнения на дашборде равны 0 или 1.

### Какой код выполнил каждый тест {#per-test-evidence}

Для тестов, запускаемых на платформе JUnit (JUnit 5 или JUnit 4 через JUnit Vintage), плагин также записывает, какой код выполнил каждый тест, и что выполнил каждый тестовый класс вне своих тестов, например в `@BeforeAll`. Это позволяет Tuist переносить покрытие тестов, которые были пропущены в запуске (см. [Пропущенные тесты](#skipped-tests)). В ваши тесты ничего добавлять не нужно.

Это работает, когда каждая JVM для тестов выполняет один тест за раз, что является стандартным поведением Gradle, если вы не включили параллельное выполнение JUnit. Запуск тестовых классов в нескольких JVM с помощью `maxParallelForks` допустим. Тесты, выполняющиеся одновременно в одной JVM, всё ещё учитываются в покрытии, но не по отдельности.

### Кэш сборки {#build-cache}

Задача тестирования, восстановленная Gradle из кэша сборки или актуальная, не выполняет тесты. Её покрытие всё равно загружается: данные JaCoCo являются одним из выходных данных задачи, записанных запуском, который выполнил её тесты с теми же входными данными.

### Пропущенные тесты {#skipped-tests}

Когда запуск пропускает тесты, Tuist заполняет их покрытие данными из предыдущего запуска, если код, который они выполняли, не изменился. Если это невозможно, покрытие коммита помечается как **Неполное**. Что пропускает запуск:

- **Исключена задача тестирования проекта** с помощью `-x :app:test`. Её тесты переносятся из последнего запуска, где их код не изменился.
- **Тесты некоторых проектов** с помощью `./gradlew :core:test`, или **некоторые тесты** с помощью `--tests`. Запуск покрывает только запрошенное, поэтому коммит считается неполным, если другой запуск этого коммита не выполнил всё.
- **Задача тестирования, остановившаяся при первой ошибке** (`failFast`).

Некоторые тесты пропускаются намеренно и не делают коммит неполным:

- **Фильтры в скрипте сборки**, такие как `filter { excludeTestsMatching(...) }`, которые определяют, что выполняет ваш набор тестов.
- **Задачи тестирования, отключённые скриптом сборки**, с помощью `enabled = false` или условия `onlyIf`, которое их пропускает.
- **Тесты, которые пропускает <.localized_link href="/guides/features/test-insights/flaky-tests/gradle">карантин</.localized_link>.** Они исключаются так, как если бы были удалены, поэтому строки, покрытые только ими, считаются непокрытыми.
- **Тесты других шардов**, когда вы [разделяете тесты на шарды](#sharded-runs).

### Завершённые и незавершённые коммиты {#commit-status}

| Статус | Значение |
| --- | --- |
| В процессе | Запуски сообщили о покрытии, но `tuistCoverageComplete` ещё не выполнен для этого коммита. |
| Завершено | Все тесты запусков коммита выполнились, были перенесены или намеренно пропущены. |
| Неполное | Некоторое покрытие не удалось определить, поэтому значение является нижней границей. |
| Не измерялось | Ни один запуск не сообщил о покрытии для этого коммита. |

Тренд ветки включает только завершённые коммиты.

## Влияние на производительность {#performance-impact}

JaCoCo инструментирует классы по мере их загрузки JVM тестов, поэтому скомпилированные классы и записи кэша сборки задач компиляции остаются неизменными независимо от того, включено покрытие или нет. Задачи, читающие все конфигурации зависимостей, такие как генераторы SBOM, также видят агент JaCoCo, поэтому их выходные данные меняются при включении покрытия. Тесты выполняются немного медленнее, и плагин считывает данные JaCoCo после завершения задач тестирования. Задачи тестирования с включённым и выключенным покрытием имеют отдельные записи в кэше сборки, поэтому первый запуск с включённым покрытием выполнит тесты, даже если их результаты без покрытия уже закэшированы.

## Ограничения {#limitations}

- **Изолированные проекты и конфигурация по требованию.** Такие сборки не конфигурируют каждый проект, поэтому плагин не может определить, тесты каких проектов пропустил запуск, и запуск тестов некоторых проектов считается завершённым.
- **Нет покрытия из пул-реквестов из форков.** Покрытие загружается только запусками, прошедшими аутентификацию в Tuist, а CI обычно скрывает секреты и токены идентификации от пул-реквестов, открытых из форков.

## Получение данных о покрытии {#querying}

Страница **Покрытие кода** в дашборде показывает значение для каждого коммита, его модули и файлы с указанием строк, покрытых каждым запуском. Те же данные доступны агентам через <.localized_link href="/guides/features/agentic-coding/mcp">сервер Model Context Protocol</.localized_link>.
