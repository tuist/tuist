# Сгенерированный проект Xcode {#generated-xcode-project-code-coverage}

Покрытие кода показывает, какие строки вашего кода выполнили тесты. Tuist загружает покрытие по строкам каждого запуска `tuist test` и объединяет результаты всех запусков коммита в одну метрику для проекта, каждой цели и каждого файла. На странице **Покрытие кода** в дашборде эти данные отображаются для каждого коммита и в виде тренда для каждой ветки.

<!-- @snippet: ./_xcode-requirements -->

Метрика остаётся точной, даже когда Tuist пропускает работу. Ваши цели из <.localized_link href="/guides/features/cache/module-cache">бинарного кэша</.localized_link> собираются со счётчиками покрытия, поэтому их код измеряется так же, как код, собранный из исходников. А когда <.localized_link href="/guides/features/selective-testing/generated-xcode-project">выборочное тестирование</.localized_link> пропускает тестовую цель, эта цель сохраняет покрытие, полученное в предыдущем запуске, благодаря [покрытию на уровне целей](#target-level-coverage), которое Tuist записывает при каждом запуске.

## Настройка {#setup}

### Включите покрытие {#turn-coverage-on}

Включите покрытие в параметрах генерации вашего `Tuist.swift` и активируйте загрузку данных о покрытии, которая по умолчанию отключена:

```swift
import ProjectDescription

let tuist = Tuist(
    testInsights: .testInsights(coverage: .coverage(upload: true)),
    project: .tuist(
        generationOptions: .options(
            coverage: .coverage(enabled: true)
        )
    )
)
```

При включённом параметре генерации:

- Действие тестирования каждой схемы, которую генерирует Tuist, собирает данные о покрытии, как и действие тестирования любой схемы, которую вы определяете самостоятельно и оставляете `coverage` незаданным. Схема с `.options(coverage: false)` или `.options(coverage: true)` сохраняет своё значение. Тест-планы сами определяют настройку покрытия: для тест-планов, которые генерирует Tuist, передайте `coverage: true` в `.testPlans(_:coverage:)`.
- Собственные цели вашего проекта считываются и прогревают бинарный кэш со счётчиками покрытия в конфигурациях Debug. См. [Как это работает](#instrumented-binaries).

Переменные окружения `TUIST_COVERAGE_ENABLED` и `TUIST_COVERAGE_UPLOAD` (`1` или `0`) имеют приоритет над `enabled` и `upload`. Устанавливайте их для всего окружения, например для CI-воркфлоу, а не для отдельной команды, чтобы команды, которые прогревают кэш, и команды, которые его читают, использовали одинаковые настройки.

> [!IMPORTANT] KEEP THE VALUE THE SAME EVERYWHERE
> Параметр генерации меняет ключи кэша для целей вашего проекта и хеши выборочного тестирования для его тестовых целей. Используйте одно и то же значение на всех машинах, которые используют общий кэш, и не выводите его из окружения (например, из `Environment.isCI`). Запуск с отключённым покрытием не переиспользует бинарные файлы или результаты выборочного тестирования из запусков с включённым покрытием.

### Исключите схемы {#leave-schemes-out}

Некоторые тестовые наборы не должны входить в отчёт о покрытии. Например, приёмочные или сквозные тесты, которые управляют вашим приложением или CLI из другого процесса, выполняют код, который инструменты покрытия не видят, а сбор этих данных лишь замедляет их работу. Отключите покрытие в действии тестирования их схемы:

```swift
.scheme(
    name: "AcceptanceTests",
    testAction: .targets(
        ["AcceptanceTests"],
        options: .options(coverage: false)
    )
)
```

Схема сохраняет покрытие выключенным независимо от того, что указано в опции `Tuist.swift` или `TUIST_COVERAGE_ENABLED`, и её запуски не учитываются в покрытии коммита. Покрытие собирается по схемам, поэтому, чтобы исключить одну тестовую цель, перенесите её в отдельную схему.

### Запустите тесты {#run-your-tests}

Запустите тесты с помощью `tuist test`, как обычно:

```sh
tuist test
```

Tuist загружает покрытие, собранное во время запуска, вместе с результатами тестов. Это включает <.localized_link href="/guides/features/test-sharding/generated-xcode-project">разделённые запуски</.localized_link> и запуски, которые тестируют продукты, собранные в другой задаче с помощью `--without-building`. Чтобы исключить покрытие запуска из Tuist, например в задачах, которые обрабатывают пул-реквесты из форков, установите `TUIST_COVERAGE_UPLOAD=0`.

### Завершайте каждый коммит в CI {#complete-each-commit}

Покрытие коммита часто формируется из нескольких задач: по одной на схему, шард или платформу. Tuist не может определить, когда последняя из них завершила отчёт, поэтому сообщите ему об этом. Когда все тестовые задачи для коммита завершены, выполните эту команду в задаче, которая зависит от всех них:

```sh
tuist coverage complete
```

Команда считывает коммит из рабочей копии или от вашего CI-провайдера; передайте `--commit <sha>`, чтобы указать другой коммит. Пока коммит не завершён, его покрытие отображается как **В процессе** и не включается в тренд ветки.

### Запускайте полный набор тестов в основной ветке {#full-runs}

> [!IMPORTANT] SET UP A FULL RUN
> Выборочное тестирование поддерживает полноту покрытия коммита только если есть предыдущий запуск, из которого можно взять данные по пропущенным целям. Запланируйте запуск всех тестов без выборочного тестирования в вашей основной ветке:
>
> ```sh
> tuist test --no-selective-testing
> ```
>
> Идеально — запускать при каждом слиянии. Для репозиториев с небольшим количеством изменений может быть достаточно ежедневного или еженедельного запуска. Записанное покрытие истекает через 90 дней, поэтому запускайте его чаще.

Переносимое покрытие опирается на полные запуски. Они обновляют записанное покрытие каждой цели до истечения срока и предоставляют Tuist актуальное состояние файлов, которые не собирает выборочный запуск. Чем больше изменений в репозитории между полными запусками, тем чаще выборочный запуск обнаруживает изменившиеся файлы, и покрытие такого коммита становится **Неполным**.

## Покрытие на уровне целей {#target-level-coverage}

Покрытие запуска показывает, что выполнил весь запуск целиком, а не что выполнила каждая тестовая цель. Когда выборочное тестирование пропускает цель, Tuist должен знать, что эта цель выполняла в предыдущем запуске, чтобы перенести её покрытие.

Поэтому при каждом запуске Tuist также записывает, какие файлы и строки выполнила каждая тестовая цель. Он считывает их из отчёта о покрытии, который Xcode формирует для каждого тестового процесса, поэтому ничего дополнительно настраивать не нужно. Данные записываются на macOS и в симуляторе iOS, но не на устройствах. UI-тесты не записывают данные о приложении, которым они управляют, потому что код приложения выполняется в отдельном процессе.

## Как это работает {#how-it-works}

### Инструментированные бинарные файлы {#instrumented-binaries}

Цель из бинарного кэша — это предварительно собранный бинарный файл, и тестовый запуск может измерить его код только если бинарный файл был собран со счётчиками покрытия. При включённом покрытии бинарный кэш хранит инструментированный вариант собственных целей вашего проекта, и каждая команда считывает и прогревает этот вариант:

- **Конфигурации Debug** используют инструментированный вариант: `tuist cache` прогревает его, а `tuist generate` и `tuist test` считывают его.
- **Конфигурации Release** всегда используют обычный вариант, поэтому то, что вы выпускаете, никогда не содержит счётчиков покрытия.
- **Внешние пакеты** всегда используют обычный вариант. Tuist измеряет только код вашего репозитория.

Прогревайте кэш с включённым покрытием в том же окружении, что и ваши тестовые задачи, чтобы `tuist test` находил инструментированные бинарные файлы. Если запуск собирает покрытие, но получает ваши цели из кэша как обычные бинарные файлы, Tuist выдаст предупреждение, и их код не будет измерен. <.localized_link href="/guides/features/cache/module-cache#code-coverage">Кэш модулей</.localized_link> подробно описывает варианты.

### Пути на разных машинах {#paths-across-machines}

Инструментированные бинарные файлы записывают пути к исходникам относительно рабочей копии, в которой они были собраны, поэтому бинарный файл, прогретый в CI, корректно измеряет нужные файлы на машине любого разработчика.

<.localized_link href="/guides/features/cache/xcode-cache">Кэш Xcode</.localized_link> работает аналогично благодаря сопоставлению префиксов, которое Tuist по умолчанию отключает в сборках, собирающих покрытие, поскольку собственный отчёт о покрытии Xcode не может разрешить сопоставленные пути. В Xcode 27 и новее при включённом `enableCaching` параметр `prefixMapping: true` сохраняет это включённым, поэтому сборки с покрытием также совместно используют результаты компиляции между рабочими копиями:

```swift
.options(coverage: .coverage(enabled: true, prefixMapping: true))
```

Загрузка Tuist разрешает сопоставленные пути, но отчёт о покрытии Xcode и `xccov` могут исключать эти файлы. См. <.localized_link href="/guides/features/cache/xcode-cache#coverage-with-prefix-mapping">Покрытие с сопоставлением префиксов</.localized_link>.

### Пропущенные тесты {#skipped-tests}

Выборочное тестирование пропускает тестовую цель, если предыдущий успешный запуск уже протестировал её с тем же хешем. Хеш охватывает исходники цели, её тесты и все зависимости, поэтому одинаковый хеш означает одни и те же тесты над одним и тем же кодом. Tuist повторно использует [покрытие на уровне цели](#target-level-coverage), записанное для этой цели в предыдущем запуске. Если ничего не было записано, например потому что покрытие было отключено или запуск старше 90 дней, переносить нечего, и коммит помечается как **Неполный**.

Выборочный запуск также не собирает каждый файл. Для файлов, которые он не компилировал, Tuist берёт строки из ближайшего предыдущего полного запуска, если файлы не изменились с тех пор. Вот почему важны [полные запуски](#full-runs) на вашей ветке по умолчанию.

Тесты, которые вы пропускаете вручную с помощью `--skip-test-targets` или `-skip-testing`, не переносятся: коммит, запуски которого их пропустили, будет **Неполным**, если только другой запуск этого коммита не выполнил их. Тесты, пропущенные карантином, вообще не входят в покрытие: Tuist ни переносит их, ни помечает коммит **Неполным** из-за них.

### Полные и неполные коммиты {#commit-status}

Каждый коммит на панели управления имеет статус:

| Статус | Значение |
| --- | --- |
| В процессе | Запуски сообщили о покрытии, но `tuist coverage complete` ещё не выполнен для этого коммита. |
| Завершён | Все тесты схем коммита были выполнены или перенесены. |
| Неполный | Некоторое покрытие не удалось определить, поэтому значение является нижней границей. |
| Не измерено | Ни один запуск не сообщил о покрытии для этого коммита. |

Тренд ветки включает только завершённые коммиты. Коммит считается неполным, например, когда:

- Выборочное тестирование пропустило цель, которую нельзя было перенести: предыдущий запуск не записал для неё покрытие, файл, который выборочный запуск не собирал, изменился с последнего полного запуска, или коммит изменил файлы, влияющие на каждую цель, такие как `Package.resolved`, `Project.swift` или `.xcconfig`.
- Запуск пропустил тесты с помощью `--skip-test-targets` или `-skip-testing`, и никакой другой запуск этого коммита их не выполнял.
- Запуск получил ваши цели из бинарного кэша как обычные бинарные файлы.
- Каждый запуск схемы был ограничен с помощью `-only-testing`.
- Покрытие схемы получено только из запусков CI на рабочей копии с незафиксированными изменениями.

## Влияние на производительность {#performance-impact}

Сбор покрытия добавляет накладные расходы, в основном после завершения тестов, пока Xcode записывает свой отчёт о покрытии, а Tuist экспортирует данные. Сборка и выполнение тестов занимают примерно столько же времени, сколько и без покрытия. Инструментированные сборки также занимают больше места на диске — в DerivedData и в бинарном кэше Debug. Сборки Release и архивы не затрагиваются.

## Ограничения {#limitations}

### Сборки Release схем, собирающих покрытие {#release-builds}

Когда тестовое действие схемы собирает покрытие, Xcode также инструментирует цели, которые `xcodebuild build` компилирует из исходников для этой схемы в любой конфигурации, включая Release. `xcodebuild archive` игнорирует эту настройку, поэтому архивы никогда не инструментируются. Распространяйте архивы или собирайте продукты Release из схемы с `.options(coverage: false)`.

### Другие инструменты покрытия {#other-coverage-tools}

`-enableCodeCoverage YES` только определяет, собирает ли запуск покрытие, как в Xcode. Это не заставляет Tuist читать инструментированные бинарные файлы из кэша, поэтому используйте вместо этого опцию `Tuist.swift` или `TUIST_COVERAGE_ENABLED`.

Чтобы передать данные другому инструменту покрытия, настройте `tuist test` на запись покрытия каждого запуска в формате LCOV. Это то же покрытие, которое загружает Tuist, с путями относительно репозитория и кодом из бинарного кэша:

```sh
tuist test --coverage-output-path coverage
```

Каждый запуск записывает `coverage/<result bundle name>.lcov`. Объедините файлы шардированного запуска с помощью `lcov -a`. Для этой опции требуется включённая загрузка покрытия.

Собственный отчёт о покрытии Xcode и инструменты, читающие его, включают только цели, собранные Xcode в этом запуске, и никогда не включают код из бинарного кэша. Загрузка Tuist измеряет и то, и другое. Если вы хотите видеть покрытие цели в отчёте Xcode, сгенерируйте проект так, чтобы эта цель собиралась из исходников: `tuist generate MyTarget` оставляет `MyTarget` в виде исходников и берёт остальное из кэша.

## Запрос покрытия {#querying}

Команды `tuist coverage` считывают данные, отображаемые на панели управления. Без `--commit` они читают последний завершённый коммит из `--branch` или из вашей ветки по умолчанию:

```sh
tuist coverage show                          # the project's coverage and its targets
tuist coverage files --commit <sha>          # files, least covered first
tuist coverage file Sources/Cart.swift --lines  # a file's functions, with per-line counts
```

Все они принимают `--json` для скриптов. Те же данные доступны агентам через <.localized_link href="/guides/features/agentic-coding/mcp">сервер Model Context Protocol</.localized_link>.
