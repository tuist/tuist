# Сгенерированный проект Xcode {#generated-xcode-project-code-coverage}

Покрытие кода показывает, какие строки вашего кода выполнили тесты. Tuist загружает покрытие по строкам каждого запуска `tuist test` и объединяет запуски одного коммита в одну метрику для проекта, каждой цели и каждого файла. На странице \*\*Покрытие кода\*\* **Code Coverage** панели управления оно отображается по коммитам и как тренд для каждой ветки.

<!-- @snippet: ./_xcode-requirements -->

Метрика остаётся точной, когда Tuist пропускает работу. Ваши цели из <.localized_link href="/guides/features/cache/module-cache">бинарного кэша</.localized_link> собираются со счётчиками покрытия, поэтому их код измеряется так же, как код, собранный из исходников. А когда <.localized_link href="/guides/features/selective-testing/generated-xcode-project">выборочное тестирование</.localized_link> пропускает тестовую цель, эта цель сохраняет покрытие, которое у неё было в предыдущем запуске, благодаря [покрытию на уровне целей](#target-level-coverage), которое Tuist записывает при каждом запуске.

## Настройка {#setup}

### Включить покрытие {#turn-coverage-on}

Включите покрытие в параметрах генерации вашего `Tuist.swift`, а также включите загрузку покрытия, которая по умолчанию отключена:

```swift
import ProjectDescription

let tuist = Tuist(
    testInsights: .testInsights(coverage: .coverage(upload: true)),
    project: .tuist(
        generationOptions: .options(
            coverage: .coverage(enabled: true)
        )
    )
)
```

При включённом параметре генерации:

- Действие тестирования каждой схемы, которую генерирует Tuist, собирает покрытие, как и действие тестирования каждой схемы, которую вы определяете и оставляете `coverage` неустановленным. Схема с `.options(coverage: false)` или `.options(coverage: true)` сохраняет своё значение. Тестовые планы сами определяют покрытие: для тестовых планов, которые генерирует Tuist, передайте `coverage: true` в `.testPlans(_:coverage:)`.
- Собственные цели вашего проекта считываются из бинарного кэша и прогреваются в нём со счётчиками покрытия в конфигурациях Debug. См. [Как это работает](#instrumented-binaries).

Переменные окружения `TUIST_COVERAGE_ENABLED` и `TUIST_COVERAGE_UPLOAD` (`1` или `0`) имеют приоритет над `enabled` и `upload`. Устанавливайте их для всего окружения, например для рабочего процесса CI, а не для отдельной команды, чтобы команды, которые прогревают кэш, и команды, которые его читают, использовали одинаковые значения.

> [!IMPORTANT] KEEP THE VALUE THE SAME EVERYWHERE
> Параметр генерации изменяет ключи кэша целей вашего проекта и хэши выборочного тестирования его тестовых целей. Используйте одно и то же значение на всех машинах, которые используют общий кэш, и не выводите его из окружения (например, из `Environment.isCI`). Запуск с отключённым покрытием не переиспользует бинарные файлы или результаты выборочного тестирования запусков с включённым покрытием.

### Исключить схемы {#leave-schemes-out}

Некоторые тестовые наборы не должны входить в ваше покрытие. Например, приёмочные или сквозные тесты, которые управляют вашим приложением или CLI из другого процесса, выполняют код, который покрытие не видит, а сбор данных только замедляет их. Отключите покрытие в действии тестирования их схемы:

```swift
.scheme(
    name: "AcceptanceTests",
    testAction: .targets(
        ["AcceptanceTests"],
        options: .options(coverage: false)
    )
)
```

Схема сохраняет покрытие отключённым независимо от того, что указано в опции `Tuist.swift` или `TUIST_COVERAGE_ENABLED`, и её запуски не учитываются в покрытии коммита. Покрытие собирается по схемам, поэтому, чтобы исключить одну тестовую цель, перенесите её в отдельную схему.

### Запустить тесты {#run-your-tests}

Запустите тесты с помощью `tuist test`, как обычно:

```sh
tuist test
```

Tuist загружает покрытие, собранное запуском, вместе с результатами тестов. Это включает <.localized_link href="/guides/features/test-sharding/generated-xcode-project">разделённые запуски</.localized_link> и запуски, которые тестируют продукты, собранные в другой задаче с помощью `--without-building`. Чтобы исключить покрытие запуска из Tuist, например в задачах, которые запускают пул-реквесты из форков, установите `TUIST_COVERAGE_UPLOAD=0`.

### Завершать каждый коммит в CI {#complete-each-commit}

Покрытие коммита часто формируется из нескольких задач: по одной на схему, шард или платформу. Tuist не может определить, когда последняя из них отчиталась, поэтому сообщите ему об этом. Когда все тестовые задачи для коммита завершатся, выполните эту команду в задаче, которая зависит от всех них:

```sh
tuist coverage complete
```

Команда считывает коммит из `HEAD` 체크아웃a — коммит, на котором выполнялись ваши тесты; передайте `--commit <sha>`, чтобы указать другой. Пока коммит не завершён, его покрытие отображается как **В процессе** и не попадает в тренд ветки.

### Запускать весь набор на основной ветке {#full-runs}

> [!IMPORTANT] SET UP A FULL RUN
> Выборочное тестирование поддерживает полноту покрытия коммита только если есть более ранний запуск, из которого можно взять пропущенные цели. Запланируйте запуск всех тестов без выборочного тестирования на вашей основной ветке:
>
> ```sh
> tuist test --no-selective-testing
> ```
>
> Идеально — один раз при каждом слиянии. Для репозиториев с небольшим количеством изменений может быть достаточно ежедневного или еженедельного запуска. Записанное покрытие истекает через 31 день, поэтому запускайте его чаще.

Переносимое покрытие опирается на полные запуски. Они обновляют записанное покрытие каждой цели до истечения срока и предоставляют Tuist актуальное состояние файлов, которые не собирает выборочный запуск. Чем больше изменений в репозитории между полными запусками, тем чаще выборочный запуск обнаруживает изменившиеся файлы, и покрытие его коммита становится **Неполным**.

## Покрытие на уровне целей {#target-level-coverage}

Покрытие запуска показывает, что выполнил весь запуск целиком, а не что выполнила каждая тестовая цель. Когда выборочное тестирование пропускает цель, Tuist должен знать, что эта цель выполнила в предыдущем запуске, чтобы перенести её покрытие.

Поэтому при каждом запуске Tuist также записывает, какие файлы и строки выполнила каждая тестовая цель. Он считывает их из отчёта о покрытии, который Xcode формирует для каждого тестового процесса, поэтому ничего дополнительно настраивать не нужно. Данные записываются на macOS и в симуляторе iOS, но не на устройствах. UI-тесты не записывают данные о приложении, которым они управляют, потому что код приложения выполняется в отдельном процессе.

## Как это работает {#how-it-works}

### Инструментированные бинарные файлы {#instrumented-binaries}

Цель из бинарного кэша — это предварительно собранный бинарный файл, и тестовый запуск может измерить его код только если бинарный файл был собран со счётчиками покрытия. При включённом покрытии бинарный кэш хранит инструментированный вариант собственных целей вашего проекта, и каждая команда читает и прогревает именно этот вариант:

- **Конфигурации Debug** используют инструментированный вариант: `tuist cache` прогревает его, а `tuist generate` и `tuist test` читают его.
- **Конфигурации Release** всегда используют обычный вариант, поэтому то, что вы выпускаете, никогда не содержит счётчиков покрытия.
- **Внешние пакеты** всегда используют обычный вариант. Tuist измеряет только код вашего репозитория.

Прогревайте кэш с включённым покрытием в том же окружении, что и ваши тестовые задачи, чтобы `tuist test` находил инструментированные бинарные файлы. Если запуск собирает покрытие, но получает ваши цели из кэша как обычные бинарные файлы, Tuist выдаст предупреждение, и их код не будет измерен. В <.localized_link href="/guides/features/cache/module-cache#code-coverage">кэше модулей</.localized_link> варианты подробно описаны.

### Пути на разных машинах {#paths-across-machines}

Инструментированные бинарные файлы записывают пути к исходникам относительно 체크아웃a, в котором они были собраны, поэтому бинарный файл, прогретый в CI, корректно измеряет нужные файлы на машине любого разработчика.

<.localized_link href="/guides/features/cache/xcode-cache">Кэш Xcode</.localized_link> работает аналогично через маппинг префиксов, который Tuist по умолчанию отключает в сборках, собирающих покрытие, поскольку собственный отчёт о покрытии Xcode не может разрешить замапленные пути. В Xcode 27 и новее, при включённом `enableCaching`, параметр `prefixMapping: true` сохраняет его включённым, поэтому сборки с покрытием также разделяют результаты компиляции между 체크아웃ами:

```swift
.options(coverage: .coverage(enabled: true, prefixMapping: true))
```

Загрузка Tuist разрешает замапленные пути, но отчёт о покрытии Xcode и `xccov` могут исключать эти файлы. См. <.localized_link href="/guides/features/cache/xcode-cache#coverage-with-prefix-mapping">Покрытие с маппингом префиксов</.localized_link>.

### Пропущенные тесты {#skipped-tests}

Выборочное тестирование пропускает тестовую цель, если более ранний успешный запуск уже протестировал её с тем же хэшем. Хэш охватывает исходники цели, её тесты и все зависимости, поэтому одинаковый хэш означает одни и те же тесты над одним и тем же кодом. Tuist повторно использует [покрытие на уровне целей](#target-level-coverage), которое тот запуск записал для цели. Если ничего не было записано, например потому что покрытие тогда было выключено или запуск старше 31 дня, переносить нечего, и коммит помечается как **Неполный**.

Выборочный запуск также не собирает каждый файл. Для файлов, которые он не компилировал, Tuist берёт строки из ближайшего предыдущего полного запуска, если файлы с тех пор не изменились. Вот почему важны [полные запуски](#full-runs) на вашей ветке по умолчанию.

Тесты, которые вы пропускаете самостоятельно, с помощью `--skip-test-targets` или `-skip-testing`, не переносятся: коммит, чьи запуски их исключили, будет **Неполным**, если только другой запуск этого коммита их не выполнил. Тесты, пропущенные карантином, вообще не входят в покрытие: Tuist ни переносит их, ни помечает из-за них коммит как **Неполный**.

### Полные и неполные коммиты {#commit-status}

Каждый коммит на панели имеет статус:

| Статус | Значение |
| --- | --- |
| В процессе | Запуски сообщили о покрытии, но `tuist coverage complete` ещё не выполнен для этого коммита. |
| Полный | Все тесты схем коммита были выполнены или перенесены. |
| Неполный | Некоторое покрытие не удалось определить, поэтому показатель является нижней границей. |
| Не измерено | Ни один запуск не сообщил о покрытии для этого коммита. |

Тренд ветки включает только полные коммиты. Коммит считается неполным, например, когда:

- Выборочное тестирование пропустило цель, которую нельзя было перенести: предыдущий запуск не записал для неё покрытие, файл, который выборочный запуск не собирал, изменился с последнего полного запуска, или коммит изменил файлы, влияющие на все цели, такие как `Package.resolved`, `Project.swift` или `.xcconfig`.
- Запуск пропустил тесты с помощью `--skip-test-targets` или `-skip-testing`, и ни один другой запуск этого коммита их не выполнил.
- Запуск получил ваши цели из бинарного кэша как обычные бинарные файлы.
- Каждый запуск схемы был ограничен с помощью `-only-testing`.
- Покрытие схемы поступило только из запусков CI в 체크아웃е с незакоммиченными изменениями.

## Влияние на производительность {#performance-impact}

Сбор покрытия добавляет накладные расходы, преимущественно после завершения тестов, пока Xcode записывает свой отчёт о покрытии, а Tuist экспортирует данные. Сборка и выполнение тестов занимают примерно столько же времени, сколько и без него. Инструментированные сборки также требуют больше дискового пространства в DerivedData и в бинарном кэше Debug. Сборки Release и архивы не затрагиваются.

## Ограничения {#limitations}

### Сборки Release схем, собирающих покрытие {#release-builds}

Когда тестовое действие схемы собирает покрытие, Xcode также инструментирует цели, которые `xcodebuild build` компилирует из исходников для этой схемы в любой конфигурации, включая Release. `xcodebuild archive` игнорирует эту настройку, поэтому архивы никогда не инструментруются. Распространяйте архивы или собирайте продукты Release из схемы с `.options(coverage: false)`.

### Другие инструменты покрытия {#other-coverage-tools}

`-enableCodeCoverage YES` только определяет, собирает ли запуск покрытие, как в Xcode. Это не заставляет Tuist читать инструментированные бинарные файлы из кэша, поэтому вместо этого используйте опцию `Tuist.swift` или `TUIST_COVERAGE_ENABLED`.

Чтобы передать данные другому инструменту покрытия, настройте `tuist test` на запись покрытия каждого запуска в формате LCOV. Это то же самое покрытие, которое загружает Tuist, с путями относительно репозитория и включением кода из бинарного кэша:

```sh
tuist test --coverage-output-path coverage
```

Каждый запуск записывает `coverage/<result bundle name>.lcov`. Объедините файлы шардированного запуска с помощью `lcov -a`. Эта опция требует включения загрузки покрытия.

Собственный отчёт о покрытии Xcode и инструменты, которые его читают, включают только цели, собранные Xcode в этом запуске, и никогда не включают код из бинарного кэша. Загрузка Tuist измеряет и то, и другое. Если вы хотите видеть покрытие цели в отчёте Xcode, сгенерируйте проект так, чтобы эта цель собиралась из исходников: `tuist generate MyTarget` оставляет `MyTarget` как исходный код и берёт остальное из кэша.

## Запрос покрытия {#querying}

Команды `tuist coverage` читают данные, отображаемые на панели. Без `--commit` они читают последний полный коммит `--branch` или вашей ветки по умолчанию:

```sh
tuist coverage show                          # the project's coverage and its targets
tuist coverage files --commit <sha>          # files, least covered first
tuist coverage file Sources/Cart.swift --lines  # a file's functions, with per-line counts
tuist coverage targets                       # targets, least covered first, then those taken from the binary cache without coverage
tuist coverage commits --branch main         # a branch's commits with their status and change, newest first
tuist coverage runs --commit <sha>           # the test runs behind a commit, marked full, partial or discarded
tuist coverage branches                      # the branches with coverage
```

Покрытие самого тестового запуска отображается в `tuist test show <test-run-id>`.

Все они поддерживают `--json` для скриптинга. Те же данные доступны агентам через <.localized_link href="/guides/features/agentic-coding/mcp">сервер Model Context Protocol</.localized_link>.
