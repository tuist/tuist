# Сгенерированный проект Xcode {#generated-xcode-project-code-coverage}

<!-- @snippet: ./_xcode-early-access -->

Покрытие кода показывает, какие строки вашего кода выполнили тесты. Tuist загружает покрытие по строкам каждого запуска `tuist test` и объединяет результаты запусков одного коммита в единую метрику для проекта, каждой цели и каждого файла. На странице **Покрытие кода** в дашборде эти данные отображаются для каждого коммита и в виде тренда для каждой ветки.

Метрика остается точной, даже когда Tuist пропускает работу. Ваши цели из <.localized_link href="/guides/features/cache/module-cache">бинарного кэша</.localized_link> собираются со счетчиками покрытия, поэтому их код измеряется так же, как код, собранный из исходников. А когда <.localized_link href="/guides/features/selective-testing/generated-xcode-project">выборочное тестирование</.localized_link> пропускает цель с тестами, эта цель сохраняет покрытие, полученное в предыдущем запуске, благодаря [покрытию на уровне целей](#target-level-coverage), которое Tuist записывает при каждом запуске.

## Настройка {#setup}

### Включите покрытие {#turn-coverage-on}

Включите покрытие в параметрах генерации вашего `Tuist.swift`, а также включите загрузку данных о покрытии, которая по умолчанию отключена:

```swift
import ProjectDescription

let tuist = Tuist(
    testInsights: .testInsights(coverage: .coverage(upload: true)),
    project: .tuist(
        generationOptions: .options(
            coverage: .coverage(enabled: true)
        )
    )
)
```

Когда параметр генерации включен:

- Действие тестирования каждой схемы, которую генерирует Tuist, собирает данные о покрытии, как и действие тестирования любой схемы, определенной вами, где параметр `coverage` не задан. Схема со значением `.options(coverage: false)` или `.options(coverage: true)` сохраняет свое значение. Тестовые планы сами определяют настройку покрытия: для тестовых планов, которые генерирует Tuist, передайте `coverage: true` в `.testPlans(_:coverage:)`.
- Собственные цели вашего проекта считываются из бинарного кэша и прогревают его со счетчиками покрытия в конфигурациях Debug. См. [Как это работает](#instrumented-binaries).

Переменные окружения `TUIST_COVERAGE_ENABLED` и `TUIST_COVERAGE_UPLOAD` (`1` или `0`) имеют приоритет над параметрами `enabled` и `upload`. Устанавливайте их для всей среды, например для CI-воркфлоу, а не для отдельной команды, чтобы команды, прогревающие кэш, и команды, читающие его, работали согласованно.

> [!IMPORTANT] KEEP THE VALUE THE SAME EVERYWHERE
> Параметр генерации изменяет ключи кэша целей вашего проекта и хеши выборочного тестирования его тестовых целей. Используйте одно и то же значение на всех машинах, использующих общий кэш, и не выводите его из переменных окружения (например, из `Environment.isCI`). Запуск с отключенным покрытием не переиспользует бинарные файлы или результаты выборочного тестирования из запусков с включенным покрытием.

### Исключение схем {#leave-schemes-out}

Некоторые наборы тестов не должны учитываться в покрытии. Например, приемочные или сквозные тесты, которые управляют вашим приложением или CLI из другого процесса, выполняют код, который инструменты покрытия не видят, а сбор этих данных лишь замедляет их выполнение. Отключите покрытие в действии тестирования их схемы:

```swift
.scheme(
    name: "AcceptanceTests",
    testAction: .targets(
        ["AcceptanceTests"],
        options: .options(coverage: false)
    )
)
```

Схема останется с отключенным покрытием независимо от того, что указано в параметре `Tuist.swift` или переменной `TUIST_COVERAGE_ENABLED`, и ее запуски не будут учитываться в покрытии коммита. Покрытие собирается по схемам, поэтому, чтобы исключить одну тестовую цель, перенесите ее в отдельную схему.

### Запустите тесты {#run-your-tests}

Запустите тесты с помощью `tuist test`, как обычно:

```sh
tuist test
```

Tuist загружает данные о покрытии, собранные во время запуска, вместе с результатами тестов. Это включает <.localized_link href="/guides/features/test-sharding/generated-xcode-project">разделенные запуски</.localized_link> и запуски, которые тестируют продукты, собранные в другой задаче с помощью `--without-building`. Чтобы исключить покрытие запуска из Tuist, например в задачах, выполняющих pull request’ы из форков, установите `TUIST_COVERAGE_UPLOAD=0`.

### Завершайте каждый коммит в CI {#complete-each-commit}

Покрытие коммита часто формируется из нескольких задач: по одной на схему, шард или платформу. Tuist не может самостоятельно определить, когда последняя из них отчиталась, поэтому сообщите ему об этом. Когда все тестовые задачи для коммита завершены, выполните эту команду в задаче, зависящей от всех них:

```sh
tuist coverage complete
```

Команда считывает коммит из рабочей копии или от вашего CI-провайдера; используйте `--commit <sha>`, чтобы указать другой коммит. Пока коммит не завершен, его покрытие отображается как **В процессе** и не учитывается в тренде ветки.

### Запускайте весь набор тестов на основной ветке {#full-runs}

> [!IMPORTANT] SET UP A FULL RUN
> Выборочное тестирование поддерживает полноту покрытия коммита только если есть предыдущий запуск, откуда можно взять данные по пропущенным целям. Запланируйте запуск всех тестов без выборочного тестирования на вашей основной ветке:
>
> ```sh
> tuist test --no-selective-testing
> ```
>
> Идеально — один раз при каждом слиянии. Для репозиториев с небольшим количеством изменений может быть достаточно ежедневного или еженедельного запуска. Записанное покрытие истекает через 90 дней, поэтому запускайте его чаще.

Переносимое покрытие опирается на полные запуски. Они обновляют записанное покрытие каждой цели до истечения срока действия и предоставляют Tuist актуальное состояние файлов, которые не собираются при выборочном запуске. Чем больше изменений в репозитории между полными запусками, тем чаще выборочный запуск обнаруживает измененные файлы, и покрытие такого коммита становится **Неполным**.

## Покрытие на уровне целей {#target-level-coverage}

Покрытие запуска показывает, что выполнил весь запуск целиком, а не что выполнила каждая тестовая цель. Когда выборочное тестирование пропускает цель, Tuist должен знать, что эта цель выполнила в предыдущем запуске, чтобы перенести ее покрытие.

Поэтому при каждом запуске Tuist также записывает, какие файлы и строки выполнила каждая тестовая цель. Он считывает эти данные из отчетов о покрытии, которые Xcode формирует для каждого тестового процесса, поэтому ничего дополнительно подключать или настраивать не нужно. Данные записываются на macOS и в симуляторе iOS, но не на устройствах. UI-тесты не записывают ничего о приложении, которым они управляют, потому что код приложения выполняется в отдельном процессе.

## Как это работает {#how-it-works}

### Инструментированные бинарные файлы {#instrumented-binaries}

Цель из бинарного кэша — это предварительно собранный бинарный файл, и тестовый запуск может измерить его код только если бинарный файл был собран со счетчиками покрытия. При включенном покрытии бинарный кэш хранит инструментированный вариант собственных целей вашего проекта, и каждая команда считывает и прогревает именно этот вариант:

- **Конфигурации Debug** используют инструментированный вариант: `tuist cache` прогревает его, а `tuist generate` и `tuist test` считывают его.
- **Конфигурации Release** всегда используют обычный вариант, поэтому то, что вы выпускаете, никогда не содержит счетчиков покрытия.
- **Внешние пакеты** всегда используют обычный вариант. Tuist измеряет только код вашего репозитория.

Прогревайте кэш с включенным покрытием в той же среде, что и ваши тестовые задачи, чтобы `tuist test` находил инструментированные бинарные файлы. Если запуск собирает покрытие, но получает ваши цели из кэша как обычные бинарные файлы, Tuist выдаст предупреждение, и их код не будет измерен. <.localized_link href="/guides/features/cache/module-cache#code-coverage">Кэш модулей</.localized_link> подробно описывает варианты.

### Пути на разных машинах {#paths-across-machines}

Инструментированные бинарные файлы записывают пути к исходникам относительно рабочей копии, в которой они были собраны, поэтому бинарный файл, прогретый в CI, корректно измеряет нужные файлы на машине любого разработчика.

<.localized_link href="/guides/features/cache/xcode-cache">Кэш Xcode</.localized_link> работает аналогично благодаря маппингу префиксов, который Tuist по умолчанию отключает в сборках, собирающих покрытие, поскольку собственный отчет о покрытии Xcode не может разрешить сопоставленные пути. В Xcode 27 и новее при включенном `enableCaching` параметр `prefixMapping: true` сохраняет его активным, поэтому сборки с покрытием также разделяют результаты компиляции между рабочими копиями:

```swift
.options(coverage: .coverage(enabled: true, prefixMapping: true))
```

Загрузка Tuist разрешает сопоставленные пути, но отчет о покрытии Xcode и `xccov` могут исключать эти файлы. См. <.localized_link href="/guides/features/cache/xcode-cache#coverage-with-prefix-mapping">Покрытие с маппингом префиксов</.localized_link>.

### Пропущенные тесты {#skipped-tests}

Выборочное тестирование пропускает тестовую цель, если предыдущий успешный запуск уже протестировал её с тем же хэшем. Хэш охватывает исходники цели, её тесты и все зависимости, поэтому одинаковый хэш означает одни и те же тесты для одного и того же кода. Tuist повторно использует [покрытие на уровне целей](#target-level-coverage), записанное для этой цели в предыдущем запуске. Если ничего не было записано, например, потому что покрытие было отключено или запуск старше 90 дней, перенести нечего, и коммит помечается как **Неполный**.

Выборочный запуск также не компилирует каждый файл. Для файлов, которые он не компилировал, Tuist берет данные из ближайшего предыдущего полного запуска, при условии, что файлы не изменились. Вот почему важны [полные запуски](#full-runs) в вашей основной ветке.

Тесты, которые вы пропускаете вручную с помощью `--skip-test-targets` или `-skip-testing`, не переносятся: коммит, запуски которого их пропустили, помечается как **Неполный**, если только другой запуск этого коммита не выполнил их. Тесты, пропущенные карантином, вообще не учитываются в покрытии: Tuist не переносит их и не помечает коммит как **Неполный** из-за них.

### Полные и неполные коммиты {#commit-status}

Каждый коммит на панели управления имеет статус:

| Статус | Значение |
| --- | --- |
| В процессе | Запуски сообщили о покрытии, но `tuist coverage complete` еще не выполнен для этого коммита. |
| Завершен | Все тесты схем коммита были выполнены или перенесены. |
| Неполный | Некоторое покрытие не удалось определить, поэтому значение является нижней границей. |
| Не измерено | Ни один запуск не сообщил о покрытии для этого коммита. |

Тренд ветки включает только завершенные коммиты. Коммит считается неполным, например, когда:

- Выборочное тестирование пропустило цель, которую нельзя было перенести: предыдущий запуск не записал для неё покрытие, файл, который выборочный запуск не собирал, изменился после последнего полного запуска, или коммит изменил файлы, влияющие на каждую цель, такие как `Package.resolved`, `Project.swift` или `.xcconfig`.
- Запуск пропустил тесты с помощью `--skip-test-targets` или `-skip-testing`, и ни один другой запуск этого коммита их не выполнил.
- Запуск получил ваши цели из бинарного кэша как обычные бинарные файлы.
- Каждый запуск схемы был ограничен с помощью `-only-testing`.
- Покрытие схемы получено только из запусков CI в рабочей копии с незафиксированными изменениями.

## Влияние на производительность {#performance-impact}

Сбор покрытия добавляет накладные расходы, преимущественно после завершения тестов, пока Xcode записывает свой отчет о покрытии, а Tuist экспортирует данные. Сборка и выполнение тестов занимают примерно столько же времени, сколько и без покрытия. Инструментированные сборки также занимают больше места на диске в DerivedData и в бинарном кэше Debug. Сборки Release и архивы не затрагиваются.

## Ограничения {#limitations}

### Сборки Release схем, собирающих покрытие {#release-builds}

Когда действие тестирования схемы собирает покрытие, Xcode также инструментирует цели, которые `xcodebuild build` компилирует из исходников для этой схемы в любой конфигурации, включая Release. `xcodebuild archive` игнорирует эту настройку, поэтому архивы никогда не инструментруются. Распространяйте архивы или собирайте продукты Release из схемы с `.options(coverage: false)`.

### Другие инструменты покрытия {#other-coverage-tools}

`-enableCodeCoverage YES` только определяет, собирает ли запуск покрытие, как в Xcode. Это не заставляет Tuist читать инструментированные бинарные файлы из кэша, поэтому используйте вместо этого опцию `Tuist.swift` или `TUIST_COVERAGE_ENABLED`.

Чтобы передать данные другому инструменту покрытия, настройте `tuist test` на запись покрытия каждого запуска в формате LCOV. Это то же покрытие, которое загружает Tuist, с путями относительно репозитория и включением кода из бинарного кэша:

```sh
tuist test --coverage-output-path coverage
```

Каждый запуск записывает `coverage/<result bundle name>.lcov`. Объедините файлы шардированного запуска с помощью `lcov -a`. Для этой опции необходима включенная загрузка покрытия.

Собственный отчет о покрытии Xcode и инструменты, читающие его, включают только цели, собранные Xcode в этом запуске, и никогда не включают код из бинарного кэша. Загрузка Tuist измеряет и то, и другое. Если вам нужно покрытие цели в отчете Xcode, сгенерируйте проект так, чтобы эта цель собиралась из исходников: `tuist generate MyTarget` оставляет `MyTarget` как исходный код и берет остальное из кэша.

## Запрос покрытия {#querying}

Команды `tuist coverage` считывают данные, отображаемые на панели управления. Без `--commit` они считывают последний завершенный коммит из `--branch` или из вашей основной ветки:

```sh
tuist coverage show                          # the project's coverage and its targets
tuist coverage files --commit <sha>          # files, least covered first
tuist coverage file Sources/Cart.swift --lines  # a file's functions, with per-line counts
```

Все они поддерживают `--json` для скриптов. Те же данные доступны агентам через <.localized_link href="/guides/features/agentic-coding/mcp">сервер Model Context Protocol</.localized_link>.
