# Покрытие кода Elixir {#elixir-code-coverage}

Покрытие кода показывает, какие строки вашего кода выполнили тесты. Пакет Hex загружает покрытие по строкам каждого запуска `mix test --cover`, а Tuist объединяет запуски коммита в одну цифру для проекта, каждого OTP-приложения и каждого файла. На странице **Code Coverage** панели управления эти данные отображаются по коммитам и в виде тренда для каждой ветки.

> [!IMPORTANT]
> **Требования**
>
> - Выполните <.localized_link href="/guides/get-started/elixir-project">общую настройку Elixir</.localized_link>, которая направляет `mix test` через пакет

## Настройка {#setup}

### Запуск тестов с покрытием {#run-your-tests}

Передайте `--cover`, как вы бы это сделали для `mix test` без Tuist:

```sh
mix test --cover
```

Пакет загружает покрытие вместе с результатами тестов запуска. Когда набор тестов завершается, он также выполняет действия инструмента покрытия Mix, настроенного с теми же опциями `test_coverage`:

- **Сводка.** Выводится покрытие каждого модуля и общее покрытие. `summary: false` отключает эту функцию.
- **Порог.** Запуск завершается с ошибкой (код выхода 3), если общее покрытие падает ниже порога, который по умолчанию составляет 90%, если вы не задали другое значение:

```elixir
def project do
  [
    test_coverage: [summary: [threshold: 80]]
  ]
end
```

Как и в Mix, порог относится к сводке, поэтому `summary: false` отключает обе функции. Чтобы вывести сводку без завершения запуска с ошибкой, установите `threshold: 0`. Модули, перечисленные в `test_coverage: [ignore_modules: [...]]`, исключаются из сводки и загрузки.

Tuist отслеживает покрытие по коммитам, поэтому ваш проект должен находиться в Git-репозитории: запуск вне репозитория загрузит результаты тестов, но не покрытие.

Покрытие опирается на <.localized_link href="/guides/features/test-insights/elixir#git-history">историю Git</.localized_link>, которую загружает пакет и которая размещает коммит в его ветке. Запуски в непрерывной интеграции всегда загружают её, а запуски `--cover` загружают её на любой машине. С помощью `--cover` пакет также определяет точку ответвления пул-реквеста: он получает базовую ветку и углубляет поверхностный клон настолько, насколько это необходимо. В непрерывной интеграции поверхностная проверка также углубляется, без содержимого файлов, пока не достигнет коммитов, которые уже есть у Tuist, поэтому коммит никогда не загружается без родительского коммита, на котором он основан. Установите `TUIST_GIT_UNSHALLOW_ENABLED=false`, чтобы предотвратить обращение к удалённому репозиторию.

### Шардированные запуски {#sharded-runs}

Когда вы <.localized_link href="/guides/features/test-sharding/elixir">шардируете свои тесты</.localized_link>, запускайте каждый шард с `--cover`:

```sh
MIX_ENV=test TUIST_SHARD_INDEX=0 mix tuist.test --cover
```

На новом раннере используйте команду bootstrap из раздела <.localized_link href="/guides/features/test-sharding/elixir#test-phase">фаза тестирования</.localized_link> руководства по шардированию, которая предотвращает компиляцию всех зависимостей Mix до того, как шард загрузит свою сборку, и добавьте к ней `--cover`.

Шард сообщает только своё собственное покрытие и не проверяет порог, так как он выполняет часть набора тестов. Tuist объединяет шарды одного запуска в одну цифру.

Каждый шард добавляет счётчики покрытия к сборке, которую он загружает. Чтобы сделать это один раз вместо этого, передайте `--cover` также в фазу сборки:

```sh
MIX_ENV=test mix tuist.test.build --shard-max 5 --cover
```

Отключите эту опцию, если вы сохраняете директорию сборки между запусками конвейера и повторно используете её в запусках, которые не собирают покрытие, чтобы эта сборка оставалась без счётчиков.

### Завершение каждого коммита в CI {#complete-each-commit}

Покрытие коммита часто формируется из нескольких задач: по одной на шард, версию базы данных или приложение. Tuist не может определить, когда последняя из них завершила отчёт, поэтому сообщите ему об этом. Как только все задачи тестирования для коммита завершатся, выполните следующую команду в задаче, зависящей от всех них:

```sh
MIX_ENV=test mix tuist.coverage.complete
```

Задача считывает коммит из `GIT_COMMIT` или `HEAD` 체크아웃; передайте `--commit <sha>`, чтобы указать другой коммит. Пока коммит не завершён, его покрытие отображается как **В процессе** и не включается в тренд ветки.

## Как это работает {#how-it-works}

### Нативные счётчики строк {#native-line-counters}

Инструмент покрытия Mix перекомпилирует каждый модуль для Erlang `cover` в начале каждого запуска, что замедляет работу на больших проектах. Вместо этого пакет использует нативные счётчики строк среды выполнения. Он перекомпилирует только те модули, которые были изменены с момента последнего запуска, переключает среду выполнения на эти счётчики и считывает их по завершении набора тестов. Инструмент покрытия Mix не используется, но его сводка и порог сохраняются.

Пакет возвращается к инструменту покрытия Mix с той же загрузкой для:

- Корня umbrella-проекта. Запускайте тесты внутри каждого приложения для нативного подсчёта.
- Проекта, который устанавливает свой собственный `test_coverage: [tool: ...]`.
- Среды выполнения без JIT, которая не может выполнять нативный подсчёт.

### Что измеряет Tuist {#what-tuist-measures}

- **Приложения.** Каждое OTP-приложение является целью на панели управления со своим собственным покрытием.
- **Только продуктивный код.** Файлы в ваших тестовых путях являются тестовым кодом. Tuist хранит их, но исключает из всех показателей.
- **Строки на файл.** Строка учитывается один раз для файла, независимо от того, скольким модулям она принадлежит.
- **Функции.** Каждая строка принадлежит функции, чья клауза начинается ближе всего выше неё. Функции, генерируемые компилятором или макросом, такие как `__info__/1` или `__schema__/1`, не перечисляются, но их строки всё равно учитываются для файла.

Таким образом, показатели Tuist отличаются от собственного отчёта о покрытии Mix несколькими способами: они исключают тестовый код и считают строки по файлам, а не по модулям. Нативный подсчёт также видит код, выполняемый при запуске приложения, и исключает строки, которые, как доказывает компилятор, никогда не могут быть выполнены, тогда как инструмент Mix сообщает о них как о непокрытых.

### Пропущенные тесты {#skipped-tests}

Tuist не может перенести покрытие тестов, которые пропущены запуском: пакет записывает то, что выполнил весь запуск, а не то, что выполнил каждый тест. Поэтому, когда аргументы самого запуска исключают тесты с помощью `--only`, `--exclude`, `--failed`, `--stale`, `--name-pattern`, `--max-failures` или тестовых файлов или строк, покрытие коммита становится **Неполным**, если только не был выполнен запуск того же варианта, который ничего не исключал. Два запуска, каждый из которых исключает тесты, например `--exclude slow` и `--only slow`, всё равно делают коммит неполным, даже если вместе они выполнили все тесты.

Некоторые тесты исключаются намеренно и не делают коммит неполным:

- **Исключения вашего тестового помощника.** Тесты, которые `ExUnit.start(exclude: [...])` исключает по умолчанию, представляют собой выбор вашего проекта относительно того, что выполняется в наборе по умолчанию, поэтому Tuist не считает их отсутствующими. Запустите их в другой задаче с помощью `--include` или `--only`, чтобы добавить их покрытие к коммиту.
- **Тесты, пропущенные в коде** с помощью `@tag :skip`.
- **Тесты, которые пропускает <.localized_link href="/guides/features/test-insights/flaky-tests/elixir#quarantining">карантин</.localized_link>.** Они исключаются так, как если бы были удалены, поэтому строки, покрытые только ими, считаются непокрытыми.

### Полные и неполные коммиты {#commit-status}

Каждый коммит на панели управления имеет статус:

| Статус | Значение |
| --- | --- |
| В процессе | Запуски сообщили о покрытии, но `mix tuist.coverage.complete` ещё не выполнен для этого коммита. |
| Завершён | Все тесты запусков коммита выполнены или намеренно пропущены. |
| Неполный | Некоторое покрытие не удалось определить, поэтому показатель является нижней границей. |
| Не измерялось | Ни один запуск не сообщил о покрытии для коммита. |

Тренд ветки включает только завершённые коммиты. Коммит считается неполным, например, когда:

- Каждый запуск варианта исключал тесты своими аргументами.
- В каждом запуске варианта отсутствовали некоторые шарды.
- Покрытие варианта получено только из запусков CI в рабочей копии с незафиксированными изменениями.

Вариант — это метка, передаваемая через `--scheme`, например версия базы данных. Запуски без метки относятся к одному варианту. Показатель коммита объединяет все запуски, но Tuist проверяет полноту каждого варианта отдельно, поэтому для каждого варианта нужен запуск, ничего не исключающий.

## Влияние на производительность {#performance-impact}

Сбор покрытия добавляет накладные расходы, поэтому запуски с `--cover` занимают больше времени, чем запуски без него. Первый запуск перекомпилирует ваши модули со счётчиками строк; последующие запуски перекомпилируют только изменившееся, поэтому их стоимость значительно ниже. На больших проектах нативный подсчёт также намного быстрее инструмента покрытия Mix.

## Ограничения {#limitations}

- **Нет HTML-отчёта.** Нативный подсчёт не записывает отчёт в директорию `test_coverage: [output: ...]`, и запуск выводит предупреждение, если она указана. Вместо этого страницы файлов на панели управления показывают покрытые строки.
- **Повторные попытки не добавляют покрытие.** При использовании <.localized_link href="/guides/features/test-insights/flaky-tests/elixir#test-retries">повторных попыток тестов</.localized_link> покрытием считается результат первой попытки. Эта попытка уже выполнила упавшие тесты, поэтому отсутствуют только те строки, которые нестабильный тест достигает при повторной попытке, но не при первой.
- **Нет покрытия из pull request'ов из форков.** Покрытие загружается только запусками, прошедшими аутентификацию в Tuist, а CI обычно не передаёт секреты и токены идентификации в pull request'ы, открытые из форков, поэтому такие запуски не сообщают о покрытии. После слияния коммит выполняется в вашей ветке с учётными данными и сообщает о своём покрытии как обычно.

## Запрос покрытия {#querying}

Страница **Покрытие кода** на панели управления показывает показатель каждого коммита, его приложения и файлы со строками, покрытыми каждым запуском. Те же данные доступны агентам через <.localized_link href="/guides/features/agentic-coding/mcp">сервер Model Context Protocol</.localized_link>.
