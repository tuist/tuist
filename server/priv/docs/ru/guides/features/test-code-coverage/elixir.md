# Покрытие кода Elixir {#elixir-code-coverage}

Покрытие кода показывает, какие строки вашего кода выполнялись тестами. Пакет Hex загружает покрытие строк каждого запуска `mix test --cover`, а Tuist объединяет запуски одного коммита в одну метрику для проекта, каждого OTP-приложения и каждого файла. На странице **Code Coverage** дашборда эти данные отображаются по коммитам и в виде тренда для каждой ветки.

> [!IMPORTANT] REQUIREMENTS
> - Выполните <.localized_link href="/guides/get-started/elixir-project">общую настройку Elixir</.localized_link>, которая направляет `mix test` через пакет

## Настройка {#setup}

### Запуск тестов с покрытием {#run-your-tests}

Передайте `--cover`, как вы бы сделали это для `mix test` без Tuist:

```sh
mix test --cover
```

Пакет загружает покрытие вместе с результатами тестов запуска. Когда набор тестов завершается, он также выполняет действия инструмента покрытия Mix, настроенного с теми же опциями `test_coverage`:

- **Сводка.** Выводит покрытие каждого модуля и общее покрытие. `summary: false` отключает эту функцию.
- **Порог.** Запуск завершается с ошибкой (код выхода 3), если общее покрытие падает ниже порога, который по умолчанию составляет 90%, если вы не задали иное:

```elixir
def project do
  [
    test_coverage: [summary: [threshold: 80]]
  ]
end
```

Как и в Mix, порог относится к сводке, поэтому `summary: false` отключает обе функции. Чтобы вывести сводку, не прерывая запуск, установите `threshold: 0`. Модули, перечисленные в `test_coverage: [ignore_modules: [...]]`, исключаются из сводки и загрузки.

Tuist отслеживает покрытие по коммитам, поэтому ваш проект должен находиться в репозитории Git: запуск вне репозитория загрузит результаты тестов, но не покрытие.

Покрытие опирается на <.localized_link href="/guides/features/test-insights/elixir#git-history">историю Git</.localized_link>, которую загружает пакет, что позволяет привязать коммит к его ветке. Запуски в непрерывной интеграции всегда загружают её, а запуски с `--cover` загружают её на любой машине. С `--cover` пакет также определяет, от какой ветки ответвился пул-реквест: он получает базовую ветку и углубляет поверхностный клон настолько, насколько это необходимо. Установите `TUIST_GIT_UNSHALLOW_ENABLED=false`, чтобы предотвратить обращение к удалённому репозиторию.

### Разделённые запуски {#sharded-runs}

Когда вы <.localized_link href="/guides/features/test-sharding/elixir">разделяете свои тесты</.localized_link>, запускайте каждый шард с `--cover`:

```sh
MIX_ENV=test TUIST_SHARD_INDEX=0 mix tuist.test --cover
```

На новом раннере используйте команду бутстрапа из раздела <.localized_link href="/guides/features/test-sharding/elixir#test-phase">фазы тестирования</.localized_link> руководства по разделению, которая предотвращает компиляцию всех зависимостей Mix до того, как шард загрузит свою сборку, и добавьте к ней `--cover`.

Шард сообщает только своё собственное покрытие и не проверяет порог, так как он выполняет часть набора тестов. Tuist объединяет шарды одного запуска в одну метрику.

Каждый шард добавляет счётчики покрытия к сборке, которую он загружает. Чтобы сделать это один раз, передайте `--cover` также в фазу сборки:

```sh
MIX_ENV=test mix tuist.test.build --shard-max 5 --cover
```

Не используйте эту опцию, если вы сохраняете директорию сборки между запусками конвейера и повторно используете её в запусках, которые не собирают покрытие, чтобы эта сборка оставалась без счётчиков.

### Завершение каждого коммита в CI {#complete-each-commit}

Покрытие коммита часто формируется из нескольких задач: по одной на шард, версию базы данных или приложение. Tuist не может определить, когда последняя из них завершила отчёт, поэтому сообщите ему об этом. Как только все тестовые задачи для коммита завершатся, выполните следующую команду в задаче, зависящей от всех них:

```sh
MIX_ENV=test mix tuist.coverage.complete
```

Задача считывает коммит из `GIT_COMMIT` или `HEAD` 체크아웃a; передайте `--commit <sha>`, чтобы указать другой коммит. Пока коммит не завершён, его покрытие отображается как **In progress** и не включается в тренд ветки.

## Как это работает {#how-it-works}

### Нативные счётчики строк {#native-line-counters}

Инструмент покрытия Mix перекомпилирует каждый модуль для Erlang `cover` в начале каждого запуска, что замедляет работу на больших проектах. Вместо этого пакет использует нативные счётчики строк среды выполнения. Он перекомпилирует только те модули, которые были изменены с последнего запуска, переключает среду выполнения на эти счётчики и считывает их значения после завершения набора тестов. Инструмент покрытия Mix не используется, но его сводка и порог сохраняются.

Пакет возвращается к инструменту покрытия Mix с той же загрузкой в следующих случаях:

- Корень umbrella-проекта. Запускайте тесты внутри каждого приложения для нативного подсчёта.
- Проект, который устанавливает свой собственный `test_coverage: [tool: ...]`.
- Среда выполнения без JIT, которая не поддерживает нативный подсчёт.

### Что измеряет Tuist {#what-tuist-measures}

- **Приложения.** Каждое OTP-приложение является целью на дашборде со своим собственным покрытием.
- **Только продуктивный код.** Файлы в путях тестов считаются тестовым кодом. Tuist хранит их, но исключает из всех метрик.
- **Строки на файл.** Строка учитывается один раз для файла, независимо от того, скольким модулям она принадлежит.
- **Функции.** Каждая строка относится к функции, чья клауза начинается ближе всего выше неё. Функции, генерируемые компилятором или макросом, такие как `__info__/1` или `__schema__/1`, не перечисляются, но их строки всё равно учитываются для файла.

Таким образом, метрики Tuist отличаются от отчёта о покрытии Mix несколькими способами: они исключают тестовый код и считают строки по файлам, а не по модулям. Нативный подсчёт также видит код, выполняемый при запуске приложения, и исключает строки, которые компилятор доказывает как недостижимые, тогда как инструмент Mix сообщает о них как о непокрытых.

### Пропущенные тесты {#skipped-tests}

Tuist не может перенести покрытие тестов, которые запуск пропустил: пакет записывает, что выполнил весь запуск целиком, а не что выполнил каждый тест. Поэтому, когда аргументы самого запуска пропускают тесты с помощью `--only`, `--exclude`, `--failed`, `--stale`, `--name-pattern`, `--max-failures` или файлов и строк тестов, покрытие коммита становится **Incomplete**, если только не был выполнен запуск той же вариации, который ничего не пропустил. Два запуска, каждый из которых пропускает тесты, например `--exclude slow` и `--only slow`, всё равно делают коммит неполным, даже если вместе они выполнили все тесты.

Некоторые тесты пропускаются намеренно и не делают коммит неполным:

- **Исключения вашего тестового хелпера.** Тесты, которые `ExUnit.start(exclude: [...])` пропускает по умолчанию, представляют собой выбор вашего проекта относительно того, что выполняется в наборе по умолчанию, поэтому Tuist не считает их отсутствующими. Запустите их в другой задаче с `--include` или `--only`, чтобы добавить их покрытие к коммиту.
- **Тесты, пропущенные в коде** с помощью `@tag :skip`.
- **Тесты, которые пропускает <.localized_link href="/guides/features/test-insights/flaky-tests/elixir#quarantining">карантин</.localized_link>.** Они исключаются так, как если бы были удалены, поэтому строки, покрытые только ими, считаются непокрытыми.

### Полные и неполные коммиты {#commit-status}

Каждый коммит на панели управления имеет статус:

| Статус | Значение |
| --- | --- |
| В процессе | Запуски сообщили о покрытии, но `mix tuist.coverage.complete` ещё не выполнился для этого коммита. |
| Полный | Все тесты запусков коммита были выполнены или пропущены намеренно. |
| Неполный | Некоторые данные покрытия не удалось определить, поэтому показатель является нижней границей. |
| Не измерялось | Ни один запуск не сообщил о покрытии для этого коммита. |

Тренд ветки включает только полные коммиты. Коммит считается неполным, например, когда:

- Каждый запуск вариации пропустил тесты из-за своих аргументов.
- В каждом запуске вариации отсутствовали некоторые шарды.
- Покрытие вариации поступило только от запусков CI на checkout с незакомиченными изменениями.

Вариация — это метка, которую вы передаёте через `--scheme`, например версия базы данных. Запуски без метки относятся к одной вариации. Показатель коммита объединяет все запуски, но Tuist проверяет полноту каждой вариации отдельно, поэтому для каждой вариации нужен запуск, который ничего не пропускает.

## Влияние на производительность {#performance-impact}

Сбор покрытия добавляет накладные расходы, поэтому запуски с `--cover` занимают больше времени, чем запуски без него. Первый запуск перекомпилирует ваши модули со счётчиками строк; последующие запуски перекомпилируют только изменённое, поэтому их стоимость значительно ниже. На больших проектах нативный подсчёт также намного быстрее инструмента покрытия Mix.

## Ограничения {#limitations}

- **Нет HTML-отчёта.** Нативный подсчёт не записывает отчёт в директорию `test_coverage: [output: ...]`, и запуск выдаёт предупреждение, если она указана. Вместо этого страницы файлов на панели управления показывают покрытые строки.
- **Повторные попытки не добавляют покрытие.** При использовании <.localized_link href="/guides/features/test-insights/flaky-tests/elixir#test-retries">повторных попыток тестов</.localized_link> покрытием считается результат первой попытки. Эта попытка уже выполнила упавшие тесты, поэтому отсутствуют только те строки, которые нестабильный тест достигает при повторной попытке, но не при первой.
- **Нет покрытия от pull request'ов из форков.** Покрытие загружается только запусками, которые проходят аутентификацию в Tuist, а CI обычно скрывает секреты и токены идентификации от pull request'ов, открытых из форков, поэтому такие запуски не сообщают о покрытии. После слияния коммит выполняется в вашей ветке с учётными данными и сообщает о своём покрытии как обычно.

## Запрос данных о покрытии {#querying}

На странице **Code Coverage** панели управления отображается показатель каждого коммита, его приложения и файлы с указанием строк, покрытых каждым запуском. Те же данные доступны агентам через <.localized_link href="/guides/features/agentic-coding/mcp">сервер Model Context Protocol</.localized_link>.
