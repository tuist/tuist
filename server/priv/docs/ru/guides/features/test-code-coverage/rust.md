# Покрытие кода Rust {#rust-code-coverage}

Покрытие кода показывает, какие строки вашего кода выполнили тесты. Tuist измеряет покрытие строк каждого запуска `cargo test` с помощью инструментария LLVM на основе исходного кода и объединяет результаты всех запусков коммита в одну цифру для проекта, каждого пакета и каждого файла. На странице **Code Coverage** дашборда эти данные отображаются по каждому коммиту и в виде тренда для каждой ветки.

> [!IMPORTANT]
> **Требования**
>
> - Следуйте инструкциям по <.localized_link href="/guides/get-started/rust-project">настройке проекта Rust</.localized_link>
> - Инструменты LLVM из вашего тулчейна Rust (`llvm-tools`). Tuist устанавливает их в тулчейн, управляемый rustup.
> - Ваш проект находится в Git-репозитории

## Настройка {#setup}

### Включите покрытие {#turn-coverage-on}

Добавьте это в корневой файл `Cargo.toml` воркспейса:

```toml
[workspace.metadata.tuist.test_insights.coverage]
upload = true
```

Если вы настраиваете Tuist через `tuist.toml`, добавьте туда раздел `[test_insights.coverage]` с параметром `upload = true`.

Затем запустите тесты как обычно:

```sh
tuist cargo test --workspace
```

Tuist собирает крейты вашего репозитория с флагом `-C instrument-coverage`, запускает тесты и загружает данные покрытия вместе с результатами тестового запуска. Вывод и код выхода ваших тестов не меняются. Чтобы переопределить настройку для одного запуска, установите `TUIST_COVERAGE_UPLOAD=1` или `TUIST_COVERAGE_UPLOAD=0`.

Покрытие опирается на историю Git, которую Tuist загружает с каждым запуском, собирающим эти данные, что позволяет привязать коммит к его ветке. Запуск вне Git-репозитория загружает результаты тестов, но не данные покрытия.

### Разделенные запуски {#sharded-runs}

Когда вы <.localized_link href="/guides/features/test-sharding/rust">разделяете свои тесты</.localized_link>, каждый шард, выполняющийся с включенным покрытием, сообщает покрытие своих целей, а Tuist объединяет данные всех шардов одного запуска в одну цифру. Шард намеренно выполняет только часть набора тестов, поэтому это не делает покрытие коммита неполным.

### Завершайте каждый коммит в CI {#complete-each-commit}

Покрытие коммита часто формируется из нескольких задач: по одной на каждый шард или набор функций. Tuist не может определить, когда отчиталась последняя из них, поэтому сообщите ему об этом явно. Когда все тестовые задачи для коммита завершены, выполните эту команду в задаче, зависящей от всех них:

```sh
tuist cargo coverage-complete
```

Команда считывает коммит из `HEAD` 체크아웃нутого репозитория — тот самый коммит, на котором запускались ваши тесты; передайте `--commit <sha>`, чтобы указать другой коммит. Пока коммит не помечен как завершенный, его покрытие отображается как **In progress** и не учитывается в тренде ветки.

## Как это работает {#how-it-works}

### Что измеряет Tuist {#what-tuist-measures}

- **Пакеты.** Каждый пакет Cargo является целью на дашборде со своим собственным покрытием.
- **Только продуктовый код.** Интеграционные тесты, бенчмарки и примеры (директории `tests/`, `benches/` и `examples/`, а также цели этих типов) считаются тестовым кодом. Tuist сохраняет их, но исключает из всех расчетных показателей. Юнит-тесты в модуле `#[cfg(test)]` являются частью своего исходного файла, поэтому их строки учитываются вместе с ним, как в `cargo llvm-cov`.
- **Функции.** Каждая строка относится к функции, начало которой расположено ближе всего выше неё. Обобщённая функция учитывается один раз, независимо от количества типов, с которыми она была инстанцирована.
- **Doctests** запускаются как обычно, но не измеряются.

Tuist также записывает, какой код выполнил каждый тестовый бинарный файл, для последующего выбора тестов на основе покрытия. `cargo test` запускает тесты бинарного файла в одном процессе, поэтому эта запись относится ко всему бинарному файлу в целом, а не к отдельным тестам внутри него.

### Пропущенные тесты {#skipped-tests}

Если аргументы самого запуска исключают некоторые тесты, например, фильтр по имени теста, `--skip`, `--ignored`, `-p`, `--exclude`, `--lib` или `--test`, то покрытие коммита считается **Incomplete**, если только не был выполнен другой запуск этого же коммита, который ничего не исключал. Сбой, останавливающий `cargo test` до запуска всех тестовых бинарных файлов, имеет тот же эффект. Добавьте `--no-fail-fast`, чтобы продолжить выполнение оставшихся бинарных файлов.

Некоторые тесты исключаются намеренно и не делают покрытие коммита неполным:

- **Тесты, которые пропускает <.localized_link href="/guides/features/test-insights/flaky-tests/rust">карантин</.localized_link>.** Они исключаются так, как если бы были удалены, поэтому строки, покрытые только ими, считаются непокрытыми.
- **Цели других шардов**, когда вы разделяете свои тесты.
- **Игнорируемые тесты** (`#[ignore]`), которые по умолчанию не запускаются.

### Завершенные и незавершенные коммиты {#commit-status}

Каждый коммит на дашборде имеет статус:

| Статус | Значение |
| --- | --- |
| В процессе | Запуски сообщили данные покрытия, но `tuist cargo coverage-complete` ещё не выполнялась для этого коммита. |
| Завершен | Все тесты запусков коммита выполнились или были намеренно пропущены. |
| Незавершен | Некоторые данные покрытия не удалось определить, поэтому показатель является нижней границей. |
| Не измерялось | Ни один запуск не отправил данные покрытия для этого коммита. |

Тренд ветки включает только завершенные коммиты.

## Влияние на производительность {#performance-impact}

Инструментированный код выполняется немного медленнее. Tuist инструментирует только крейты вашего репозитория: зависимости собираются точно так же, как в обычных сборках, и продолжают браться из кэша. Tuist хранит оба варианта ваших собственных крейтов в директории target, поэтому переключение между запусками с покрытием и без него не вызывает их пересборки, если их код не изменился.

## Ограничения {#limitations}

- **Пользовательский `rustc-wrapper` со специфичными для таргета `rustflags`.** Если ваш проект задает собственный `rustc-wrapper`, Tuist вместо этого добавляет `-C instrument-coverage` в `build.rustflags` Cargo. Запись `target.<triple>.rustflags` в файле конфигурации Cargo заменяет их, поэтому добавьте флаг туда самостоятельно. Запуск, тесты которого не записали данные покрытия, сообщает об этом.
- **Настроенные раннеры для таргетов.** Tuist запускает тестовые бинарные файлы через собственный раннер. Запись `target.<triple>.runner` в файле конфигурации Cargo заменяет его: данные покрытия запуска все равно отправляются, но Tuist не может определить, какой именно тестовый бинарный файл что выполнил. Раннер, заданный через переменную окружения `CARGO_TARGET_<TRIPLE>_RUNNER`, продолжает работать.
- **Нет данных покрытия из пул-реквестов из форков.** Данные покрытия отправляются только запусками, прошедшими аутентификацию в Tuist, а CI обычно не передает секреты и токены идентичности в пул-реквесты, открытые из форков.

## Запрос данных покрытия {#querying}

Страница **Code Coverage** на дашборде показывает показатель каждого коммита, его пакеты и файлы с функциями, которые содержит каждый файл. Те же данные доступны агентам через <.localized_link href="/guides/features/agentic-coding/mcp">сервер Model Context Protocol</.localized_link>.
