# Покрытие кода Rust {#rust-code-coverage}

Покрытие кода показывает, какие строки вашего кода выполнялись тестами. Tuist измеряет покрытие строк каждого запуска `cargo test` с помощью инструментария LLVM на основе исходного кода и объединяет результаты всех запусков коммита в одну метрику для проекта, каждого пакета и каждого файла. На странице **Code Coverage** дашборда эти данные отображаются по коммитам и в виде тренда для каждой ветки.

> [!IMPORTANT]
> **Требования**
>
> - Следуйте <.localized_link href="/guides/get-started/rust-project">инструкциям по настройке Rust-проекта</.localized_link>
> - Инструменты LLVM из вашего Rust toolchain (`llvm-tools`). Tuist устанавливает их в тулчейн, управляемый rustup.
> - Ваш проект находится в Git-репозитории

## Настройка {#setup}

### Включите покрытие {#turn-coverage-on}

Добавьте это в корневой файл `Cargo.toml` рабочего пространства:

```toml
[workspace.metadata.tuist.test_insights.coverage]
upload = true
```

Если вы настраиваете Tuist через `tuist.toml`, добавьте туда раздел `[test_insights.coverage]` с параметром `upload = true`.

Затем запустите тесты как обычно:

```sh
tuist cargo test --workspace
```

Tuist собирает крейты вашего репозитория с флагом `-C instrument-coverage`, запускает тесты и загружает данные о покрытии вместе с результатами прогона. Вывод тестов и код завершения не меняются. Чтобы переопределить настройку для одного запуска, установите `TUIST_COVERAGE_UPLOAD=1` или `TUIST_COVERAGE_UPLOAD=0`.

Покрытие опирается на историю Git, которую Tuist загружает при каждом сборе данных, привязывая коммит к его ветке. Запуск вне Git-репозитория загружает результаты тестов, но не данные о покрытии.

### Шардированные запуски {#sharded-runs}

Когда вы <.localized_link href="/guides/features/test-sharding/rust">шардируете свои тесты</.localized_link>, каждый шард, запущенный с включённым покрытием, отчитывается о покрытии своих целей, а Tuist объединяет данные всех шардов одного запуска в единую метрику. Шард намеренно выполняет только часть набора тестов, поэтому это не делает покрытие коммита неполным.

### Завершайте каждый коммит в CI {#complete-each-commit}

Покрытие коммита часто формируется несколькими задачами: по одной на шард или набор функций. Tuist не может самостоятельно определить, когда отчиталась последняя из них, поэтому сообщите ему об этом. Когда все тестовые задачи для коммита завершатся, выполните следующую команду в задаче, зависящей от всех них:

```sh
tuist cargo coverage-complete
```

Команда считывает коммит из `HEAD` текущего чекаута — тот самый коммит, на котором выполнялись ваши тесты; передайте `--commit <sha>`, чтобы указать другой. Пока коммит не помечен как завершённый, его покрытие отображается как **In progress** и не учитывается в тренде ветки.

## Как это работает {#how-it-works}

### Что измеряет Tuist {#what-tuist-measures}

- **Пакеты.** Каждый Cargo-пакет является отдельной целью на дашборде со своим собственным покрытием.
- **Только продакшен-код.** Интеграционные тесты, бенчмарки и примеры (каталоги `tests/`, `benches/` и `examples/`, а также цели соответствующих типов) считаются тестовым кодом. Tuist сохраняет их, но исключает из всех метрик. Юнит-тесты внутри модуля `#[cfg(test)]` являются частью своего исходного файла, поэтому их строки учитываются вместе с ним, как в `cargo llvm-cov`.
- **Функции.** Каждая строка относится к функции, начало которой расположено выше всего. Универсальная функция учитывается один раз, независимо от количества типов, с которыми она была инстанцирована.
- **Doctests** выполняются как обычно, но не измеряются.

Tuist также записывает, какой код выполнял каждый тестовый бинарный файл, для последующего выбора тестов на основе покрытия. `cargo test` запускает тесты бинарного файла в одном процессе, поэтому эта запись относится ко всему бинарному файлу в целом, а не к отдельным тестам.

### Пропущенные тесты {#skipped-tests}

Если аргументы самого запуска исключают некоторые тесты, например фильтр по имени теста, `--skip`, `--ignored`, `-p`, `--exclude`, `--lib` или `--test`, то покрытие коммита считается **Incomplete**, если только не был выполнен другой запуск этого же коммита без исключений. Сбой, который останавливает `cargo test` до выполнения всех тестовых бинарных файлов, приводит к тому же эффекту. Добавьте `--no-fail-fast`, чтобы продолжить выполнение оставшихся бинарных файлов.

Некоторые тесты исключаются намеренно и не делают покрытие коммита неполным:

- **Тесты, которые пропускает <.localized_link href="/guides/features/test-insights/flaky-tests/rust">карантин</.localized_link>.** Они исключаются так, будто были удалены, поэтому строки, покрытые только ими, считаются непокрытыми.
- **Цели других шардов**, если вы используете шардирование тестов.
- **Игнорируемые тесты** (`#[ignore]`), которые не запускаются по умолчанию.

### Завершённые и незавершённые коммиты {#commit-status}

Каждый коммит на дашборде имеет статус:

| Статус | Значение |
| --- | --- |
| В процессе | Запуски отчитались о покрытии, но `tuist cargo coverage-complete` ещё не выполнялась для этого коммита. |
| Завершён | Все тесты запусков коммита выполнились или были намеренно исключены. |
| Неполный | Некоторые данные о покрытии не удалось определить, поэтому показатель является нижней границей. |
| Не измерялось | Ни один запуск не сообщил данные о покрытии для этого коммита. |

В тренд ветки входят только завершённые коммиты.

## Влияние на производительность {#performance-impact}

Инструментированный код выполняется немного медленнее. Tuist инструментирует только крейты вашего репозитория: зависимости собираются точно так же, как при обычных сборках, и берутся из кэша. Tuist хранит оба варианта ваших собственных крейтов в целевой директории, поэтому переключение между запусками с покрытием и без него не вызывает их пересборку, если их код не изменился.

## Ограничения {#limitations}

- **Пользовательский `rustc-wrapper` со специфичными для таргета `rustflags`.** Если ваш проект задаёт собственный `rustc-wrapper`, Tuist вместо этого добавляет `-C instrument-coverage` в `build.rustflags` Cargo. Запись `target.<triple>.rustflags` в конфигурационном файле Cargo заменяет их, поэтому добавьте этот флаг туда самостоятельно. Запуск, тесты которого не записали данные о покрытии, сообщает об этом.
- **Настроенные раннеры для таргетов.** Tuist запускает тестовые бинарные файлы через собственный раннер. Запись `target.<triple>.runner` в конфигурационном файле Cargo заменяет его: покрытие запуска всё равно загружается, но Tuist не может определить, какой именно тестовый бинарный файл что выполнял. Раннер, заданный через переменную окружения `CARGO_TARGET_<TRIPLE>_RUNNER`, продолжает работать.
- **Нет данных о покрытии из пул-реквестов из форков.** Покрытие загружается только запусками, которые проходят аутентификацию в Tuist, а CI обычно не передаёт секреты и токены идентификации пул-реквестам, открытым из форков.

## Запрос данных о покрытии {#querying}

Страница **Code Coverage** на дашборде показывает показатель для каждого коммита, его пакеты и файлы с функциями, которые содержит каждый файл. Те же данные доступны агентам через <.localized_link href="/guides/features/agentic-coding/mcp">Model Context Protocol server</.localized_link>.
