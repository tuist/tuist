# Покрытие кода Rust {#rust-code-coverage}

Покрытие кода показывает, какие строки вашего кода выполнили тесты. Tuist измеряет покрытие строк каждого запуска `cargo test` с помощью основанного на исходном коде покрытия LLVM и объединяет запуски одного коммита в одну метрику для проекта, каждого пакета и каждого файла. Страница **Покрытие кода** на панели управления показывает её по коммитам и в виде тренда для каждой ветки.

> [!IMPORTANT]
> **Требования**
>
> - Выполните <.localized_link href="/guides/get-started/rust-project">настройку Rust-проекта</.localized_link>
> - Инструменты LLVM из вашего Rust-тулчейна (`llvm-tools`). Tuist устанавливает их в тулчейн, управляемый rustup.
> - Ваш проект в Git-репозитории

## Настройка {#setup}

### Включить покрытие {#turn-coverage-on}

Добавьте это в корневой `Cargo.toml` воркспейса:

```toml
[workspace.metadata.tuist.test_insights.coverage]
upload = true
```

Если вы настраиваете Tuist через `tuist.toml`, добавьте туда `[test_insights.coverage]` с `upload = true`.

Затем запустите тесты как обычно:

```sh
tuist cargo test --workspace
```

Tuist собирает крейты вашего репозитория с `-C instrument-coverage`, запускает тесты и загружает их покрытие вместе с результатами тестового запуска. Вывод и код выхода ваших тестов не меняются. Чтобы переопределить настройку для одного запуска, установите `TUIST_COVERAGE_UPLOAD=1` или `TUIST_COVERAGE_UPLOAD=0`.

Покрытие опирается на историю Git, которую Tuist загружает с каждым запуском, собирающим её, что размещает коммит в его ветке. Запуск вне Git-репозитория загружает результаты тестов, но не покрытие. Запуск из 체크아웃 коммита, а не ветки, не имеет ветки и не размещает свой коммит в какой-либо ветке; в системе CI, которую Tuist не распознаёт, назовите ветку через `TUIST_GIT_BRANCH`, как описано в разделе <.localized_link href="/guides/features/test-insights/rust#continuous-integration">непрерывная интеграция</.localized_link>.

### Шардированные запуски {#sharded-runs}

Когда вы <.localized_link href="/guides/features/test-sharding/rust">шардируете свои тесты</.localized_link>, каждый шард, запущенный с включённым покрытием, сообщает покрытие своих целей, а Tuist объединяет шарды одного запуска в одну метрику. Шард намеренно выполняет часть набора тестов, поэтому он не делает покрытие коммита неполным.

### Завершайте каждый коммит в CI {#complete-each-commit}

Покрытие коммита часто формируется из нескольких задач: по одной на шард или на набор функций. Tuist не может определить, когда последняя из них отчиталась, поэтому сообщите ему об этом. Когда все тестовые задачи для коммита завершены, выполните это в задаче, зависящей от всех них:

```sh
tuist coverage complete
```

Команда считывает коммит из `HEAD` 체크아웃, то есть коммит, на котором выполнялись ваши тесты; передайте `--commit <sha>`, чтобы указать другой. Пока коммит не завершён, его покрытие отображается как **В процессе** и не учитывается в тренде ветки.

## Как это работает {#how-it-works}

### Что измеряет Tuist {#what-tuist-measures}

- **Пакеты.** Каждый пакет Cargo является целью на панели управления со своим собственным покрытием.
- **Только код продукта.** Интеграционные тесты, бенчмарки и примеры (каталоги `tests/`, `benches/` и `examples/`, а также цели таких типов) являются тестовым кодом. Tuist хранит их, но исключает из всех метрик. Модульные тесты в модуле `#[cfg(test)]` являются частью их исходного файла, поэтому их строки учитываются вместе с ним, как в `cargo llvm-cov`.
- **Функции.** Каждая строка относится к функции, начинающейся ближе всего выше неё. Универсальная функция учитывается один раз, независимо от количества типов, с которыми она была инстанцирована.
- **Doctests** выполняются как обычно, но не измеряются.

Tuist также записывает, какой код выполнил каждый тестовый бинарный файл, для последующего выбора тестов на основе покрытия. `cargo test` запускает тесты бинарного файла в одном процессе, поэтому эта запись относится ко всему бинарному файлу, а не к отдельным тестам.

### Пропущенные тесты {#skipped-tests}

Когда аргументы самого запуска исключают тесты, такие как фильтр по имени теста, `--skip`, `--ignored`, `-p`, `--exclude`, `--lib` или `--test`, покрытие коммита становится **Неполным**, если только не был выполнен ещё один запуск этого коммита, ничего не исключающий. Сбой, останавливающий `cargo test` до выполнения всех тестовых бинарных файлов, имеет тот же эффект. Добавьте `--no-fail-fast`, чтобы продолжить выполнение оставшихся бинарных файлов.

Некоторые тесты намеренно исключаются и не делают коммит неполным:

- **Тесты, которые пропускает <.localized_link href="/guides/features/test-insights/flaky-tests/rust">карантин</.localized_link>.** Они исключаются так, как если бы были удалены, поэтому строки, покрытые только ими, считаются непокрытыми.
- **Цели других шардов**, когда вы шардируете свои тесты.
- **Игнорируемые тесты** (`#[ignore]`), которые не выполняются по умолчанию.

### Незафиксированные изменения {#uncommitted-changes}

Запуск из 체크아웃, где отслеживаемые файлы имеют незафиксированные изменения, измерял код, не относящийся к коммиту, поэтому его покрытие не учитывается для коммита. Запуск выдаёт предупреждение и перечисляет изменённые файлы. Файлы, которые ваша задача CI записывает рядом с исходниками, такие как выходные данные сборки или отчёты о покрытии, не считаются изменениями, пока Git их не отслеживает. Если только такие запуски измеряли коммит, его покрытие будет **Неполным**, и `tuist coverage complete` объяснит причину.

### Завершённые и незавершённые коммиты {#commit-status}

Каждый коммит на панели управления имеет статус:

| Статус | Значение |
| --- | --- |
| В процессе | Запуски сообщили о покрытии, но `tuist coverage complete` ещё не выполнялся для этого коммита. |
| Завершён | Все тесты запусков коммита выполнились или были намеренно исключены. |
| Неполный | Некоторое покрытие не удалось определить, поэтому показатель является нижней границей. |
| Не измерялось | Ни один запуск не сообщил о покрытии для коммита. |

Тренд ветки включает только завершённые коммиты.

## Влияние на производительность {#performance-impact}

Инструментированный код выполняется немного медленнее. Tuist инструментирует только крейты вашего репозитория: зависимости собираются точно так же, как в обычных сборках, и берутся из кэша. Tuist хранит оба варианта ваших собственных крейтов в целевой директории, поэтому переключение между запусками с покрытием и без него не вызывает их пересборки, если их код не изменился.

## Ограничения {#limitations}

- **Пользовательский `rustc-wrapper` с флагами `rustflags` для конкретной цели.** Если ваш проект задаёт собственный `rustc-wrapper`, Tuist вместо этого добавляет `-C instrument-coverage` в `build.rustflags` Cargo. Запись `target.<triple>.rustflags` в файле конфигурации Cargo заменяет их, поэтому добавьте флаг туда самостоятельно. Запуск, тесты которого не записали покрытие, сообщит об этом.
- **Настроенные раннеры целей.** Tuist запускает тестовые бинарные файлы через собственный раннер. Запись `target.<triple>.runner` в файле конфигурации Cargo заменяет его: покрытие запуска всё равно загружается, но Tuist не может определить, какой тестовый бинарный файл что выполнял. Раннер, заданный через переменную окружения `CARGO_TARGET_<TRIPLE>_RUNNER`, продолжает работать.
- **Нет покрытия от пул-реквестов из форков.** Покрытие загружается только запусками, которые аутентифицируются в Tuist, а CI обычно не передаёт секреты и токены идентификации пул-реквестам, открытым из форков.

## Запрос данных о покрытии {#querying}

Страница **Покрытие кода** на панели управления показывает показатель каждого коммита, его пакеты и файлы с функциями, которые содержит каждый файл. Те же данные доступны агентам через <.localized_link href="/guides/features/agentic-coding/mcp">сервер Model Context Protocol</.localized_link>.
