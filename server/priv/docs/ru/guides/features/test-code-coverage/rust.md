# Покрытие кода Rust {#rust-code-coverage}

Покрытие кода показывает, какие строки вашего кода выполнили тесты. Tuist измеряет покрытие строк каждого запуска `cargo test` с помощью основанного на источниках покрытия LLVM и объединяет запуски коммита в одну метрику для проекта, каждого пакета и каждого файла. На странице **Code Coverage** панели управления эти данные отображаются по коммитам и в виде тренда для каждой ветки.

> [!IMPORTANT]
> **Требования**
>
> - Следуйте инструкциям по <.localized_link href="/guides/get-started/rust-project">настройке проекта Rust</.localized_link>
> - Инструменты LLVM из вашего инструментария Rust (`llvm-tools`). Tuist устанавливает их в инструментарий, управляемый rustup.
> - Ваш проект находится в репозитории Git

## Настройка {#setup}

### Включение покрытия {#turn-coverage-on}

Добавьте это в файл `tuist.toml` в корне вашего репозитория:

```toml
[test_insights.coverage]
upload = true
```

Затем запустите тесты как обычно:

```sh
tuist cargo test --workspace
```

Tuist собирает крейты вашего репозитория с флагом `-C instrument-coverage`, запускает тесты и загружает их покрытие вместе с результатами тестового запуска. Вывод тестов и код выхода не меняются. Чтобы переопределить настройку для одного запуска, установите `TUIST_COVERAGE_UPLOAD=1` или `TUIST_COVERAGE_UPLOAD=0`.

Покрытие опирается на историю Git, которую Tuist загружает с каждым запуском, собирающим эти данные, что привязывает коммит к его ветке. Запуск вне репозитория Git загружает результаты тестов, но не покрытие.

### Шардированные запуски {#sharded-runs}

Когда вы <.localized_link href="/guides/features/test-sharding/rust">шардируете свои тесты</.localized_link>, каждый шард, запущенный с включенным покрытием, сообщает о покрытии своих собственных целей, а Tuist объединяет шарды одного запуска в одну метрику. Шард намеренно выполняет часть набора тестов, поэтому он не делает покрытие коммита неполным.

### Завершение каждого коммита в CI {#complete-each-commit}

Покрытие коммита часто формируется из нескольких задач: по одной на шард или набор функций. Tuist не может определить, когда последняя из них отчиталась, поэтому сообщите ему об этом. Как только все тестовые задачи для коммита завершатся, выполните эту команду в задаче, зависящей от всех них:

```sh
tuist cargo coverage-complete
```

Команда считывает коммит из 체크아웃-версии или тот, который ваш CI-провайдер сообщает для пул-реквеста; передайте `--commit <sha>`, чтобы указать другой. Пока коммит не завершён, его покрытие отображается как **In progress** и не учитывается в тренде ветки.

## Как это работает {#how-it-works}

### Что измеряет Tuist {#what-tuist-measures}

- **Пакеты.** Каждый пакет Cargo является целью на панели управления со своим собственным покрытием.
- **Только код продукта.** Интеграционные тесты, бенчмарки и примеры (каталоги `tests/`, `benches/` и `examples/`, а также цели таких типов) являются тестовым кодом. Tuist сохраняет их, но исключает из всех метрик. Юнит-тесты в модуле `#[cfg(test)]` являются частью их исходного файла, поэтому их строки учитываются вместе с ним, как в `cargo llvm-cov`.
- **Функции.** Каждая строка относится к функции, которая начинается ближе всего выше неё. Обобщённая функция учитывается один раз, независимо от того, с каким количеством типов она была инстанцирована.
- **Doctests** выполняются как обычно, но не измеряются.

Tuist также записывает, какой код выполнил каждый тестовый бинарный файл, для последующего выбора тестов на основе покрытия. `cargo test` запускает тесты бинарного файла в одном процессе, поэтому эта запись относится ко всему бинарному файлу в целом, а не к его отдельным тестам.

### Пропущенные тесты {#skipped-tests}

Если аргументы самого запуска исключают тесты, такие как фильтр по имени теста, `--skip`, `--ignored`, `-p`, `--exclude`, `--lib` или `--test`, покрытие коммита считается **Incomplete**, если не был выполнен другой запуск этого коммита, ничего не исключающий. Сбой, останавливающий `cargo test` до запуска всех тестовых бинарных файлов, имеет тот же эффект. Добавьте `--no-fail-fast`, чтобы продолжить выполнение оставшихся бинарных файлов.

Некоторые тесты намеренно исключаются и не делают коммит неполным:

- **Тесты, которые пропускает <.localized_link href="/guides/features/test-insights/flaky-tests/rust">карантин</.localized_link>.** Они исключаются так, как если бы были удалены, поэтому строки, покрытые только ими, считаются непокрытыми.
- **Цели других шардов**, когда вы шардируете свои тесты.
- **Игнорируемые тесты** (`#[ignore]`), которые по умолчанию не запускаются.

### Завершённые и незавершённые коммиты {#commit-status}

Каждый коммит на панели управления имеет статус:

| Статус | Значение |
| --- | --- |
| В процессе | Запуски сообщили о покрытии, но `tuist cargo coverage-complete` ещё не выполнялась для этого коммита. |
| Завершён | Все тесты запусков коммита выполнились или были намеренно исключены. |
| Незавершён | Некоторое покрытие не удалось определить, поэтому метрика является нижней границей. |
| Не измерялось | Ни один запуск не сообщил о покрытии для этого коммита. |

В тренд ветки входят только завершённые коммиты.

## Влияние на производительность {#performance-impact}

Инструментированный код работает немного медленнее. Tuist инструментирует только крейты вашего репозитория: зависимости собираются так же, как в обычных сборках, и берутся из кэша. Tuist хранит оба варианта ваших собственных крейтов в целевой директории, поэтому переключение между запусками с покрытием и без него не приводит к их пересборке, если их код не изменился.

## Ограничения {#limitations}

- **Пользовательский `rustc-wrapper` с флагами `rustflags` для конкретной цели.** Если ваш проект задаёт собственный `rustc-wrapper`, Tuist вместо этого добавляет `-C instrument-coverage` в `build.rustflags` Cargo. Запись `target.<triple>.rustflags` в файле конфигурации Cargo заменяет их, поэтому добавьте флаг туда самостоятельно. Запуск, тесты которого не записали покрытие, сообщает об этом.
- **Настроенные исполнители целей.** Tuist запускает тестовые бинарные файлы через собственный исполнитель. Запись `target.<triple>.runner` в файле конфигурации Cargo заменяет его: покрытие запуска всё равно загружается, но Tuist не может определить, какой тестовый бинарный файл что выполнил. Исполнитель, заданный через переменную окружения `CARGO_TARGET_<TRIPLE>_RUNNER`, продолжает работать.
- **Нет покрытия из pull-запросов из форков.** Покрытие загружается только запусками, которые аутентифицируются в Tuist, а CI обычно скрывает секреты и токены идентификации от pull-запросов, открытых из форков.

## Запрос покрытия {#querying}

Страница **Code Coverage** на панели управления показывает метрику каждого коммита, его пакеты и файлы с функциями, которые содержит каждый файл. Те же данные доступны агентам через <.localized_link href="/guides/features/agentic-coding/mcp">сервер Model Context Protocol</.localized_link>.
