# Покрытие кода Rust {#rust-code-coverage}

Покрытие кода показывает, какие строки вашего кода выполнили тесты. Tuist измеряет покрытие строк каждого запуска `cargo test` с помощью основанного на источниках покрытия LLVM и объединяет результаты запусков коммита в одну цифру для проекта, каждого пакета и каждого файла. На странице **Code Coverage** панели управления оно отображается по коммитам и как тренд для каждой ветки.

> [!IMPORTANT]
> **Требования**
>
> - Следуйте инструкциям по <.localized_link href="/guides/get-started/rust-project">настройке проекта Rust</.localized_link>
> - Инструменты LLVM из вашего инструментария Rust (`llvm-tools`). Tuist устанавливает их в инструментарий, управляемый rustup.
> - Ваш проект в репозитории Git

## Настройка {#setup}

### Включение покрытия {#turn-coverage-on}

Добавьте это в корневой файл `Cargo.toml` рабочего пространства:

```toml
[workspace.metadata.tuist.test_insights.coverage]
upload = true
```

Если вы настраиваете Tuist через `tuist.toml`, добавьте туда `[test_insights.coverage]` с параметром `upload = true`.

Затем запустите тесты как обычно:

```sh
tuist cargo test --workspace
```

Tuist собирает крейты вашего репозитория с флагом `-C instrument-coverage`, запускает тесты и загружает данные о покрытии вместе с результатами тестового запуска. Вывод и код выхода ваших тестов не меняются. Чтобы переопределить настройку для одного запуска, установите `TUIST_COVERAGE_UPLOAD=1` или `TUIST_COVERAGE_UPLOAD=0`.

Покрытие опирается на историю Git, которую Tuist загружает с каждым запуском, собирающим эти данные, что позволяет привязать коммит к его ветке. Запуск вне репозитория Git загружает результаты тестов, но не данные о покрытии.

### Разделенные запуски {#sharded-runs}

Когда вы <.localized_link href="/guides/features/test-sharding/rust">разделяете свои тесты</.localized_link>, каждый шард, выполняющийся с включенным покрытием, сообщает о покрытии своих целей, а Tuist объединяет данные всех шардов одного запуска в одну цифру. Шард намеренно выполняет только часть набора тестов, поэтому это не делает покрытие коммита неполным.

### Завершение каждого коммита в CI {#complete-each-commit}

Покрытие коммита часто формируется из нескольких заданий: по одному на шард или набор функций. Tuist не может определить, когда последнее из них завершило отчет, поэтому сообщите ему об этом. Как только все тестовые задания для коммита завершатся, выполните эту команду в задании, зависящем от всех них:

```sh
tuist coverage complete
```

Команда считывает коммит из `HEAD` checkout’а, то есть тот коммит, на котором выполнялись ваши тесты; передайте `--commit <sha>`, чтобы указать другой. Пока коммит не будет завершен, его покрытие отображается как **In progress** и не учитывается в тренде ветки.

## Как это работает {#how-it-works}

### Что измеряет Tuist {#what-tuist-measures}

- **Пакеты.** Каждый пакет Cargo является целью на панели управления со своим собственным покрытием.
- **Только код продукта.** Интеграционные тесты, бенчмарки и примеры (каталоги `tests/`, `benches/` и `examples/`, а также цели таких типов) считаются тестовым кодом. Tuist хранит их, но исключает из всех расчетных показателей. Юнит-тесты в модуле `#[cfg(test)]` являются частью их исходного файла, поэтому их строки учитываются вместе с ним, как в `cargo llvm-cov`.
- **Функции.** Каждая строка относится к функции, начало которой находится ближе всего выше нее. Обобщенная функция учитывается один раз, независимо от количества типов, с которыми она была инстанцирована.
- **Doctests** выполняются как обычно, но не измеряются.

Tuist также записывает, какой код выполнил каждый тестовый бинарный файл, для последующего выбора тестов на основе покрытия. `cargo test` запускает тесты бинарного файла в одном процессе, поэтому эта запись относится к бинарному файлу в целом, а не к его отдельным тестам.

### Пропущенные тесты {#skipped-tests}

Если аргументы самого запуска исключают тесты, например, фильтр по имени теста, `--skip`, `--ignored`, `-p`, `--exclude`, `--lib` или `--test`, покрытие коммита считается **Incomplete**, если только не был выполнен другой запуск этого коммита, который ничего не исключал. Сбой, останавливающий `cargo test` до того, как будут выполнены все тестовые бинарные файлы, имеет тот же эффект. Добавьте `--no-fail-fast`, чтобы продолжить выполнение оставшихся бинарных файлов.

Некоторые тесты исключаются намеренно и не делают коммит неполным:

- **Тесты, которые пропускает <.localized_link href="/guides/features/test-insights/flaky-tests/rust">карантин</.localized_link>.** Они исключаются так, как если бы были удалены, поэтому строки, покрытые только ими, считаются непокрытыми.
- **Цели других шардов**, когда вы разделяете свои тесты.
- **Игнорируемые тесты** (`#[ignore]`), которые не выполняются по умолчанию.

### Незафиксированные изменения {#uncommitted-changes}

Запуск из checkout’а, где отслеживаемые файлы имеют незафиксированные изменения, измерял код, не относящийся к коммиту, поэтому его покрытие не засчитывается для коммита. Запуск выдает предупреждение и перечисляет измененные файлы. Файлы, которые ваше CI-задание записывает рядом с исходниками, такие как выходные данные сборки или отчеты о покрытии, не считаются изменениями, пока Git их не отслеживает. Если коммит измерялся только такими запусками, его покрытие будет **Incomplete**, а `tuist coverage complete` объяснит причину.

### Завершенные и незавершенные коммиты {#commit-status}

Каждый коммит на панели управления имеет статус:

| Статус | Значение |
| --- | --- |
| В процессе | Запуски сообщили о покрытии, но `tuist coverage complete` еще не выполнялась для этого коммита. |
| Завершен | Все тесты запусков коммита выполнились или были намеренно исключены. |
| Неполный | Некоторые данные о покрытии не удалось определить, поэтому показатель является нижней границей. |
| Не измерялось | Ни один запуск не сообщил данные о покрытии для этого коммита. |

Тренд ветки включает только завершенные коммиты.

## Влияние на производительность {#performance-impact}

Инструментированный код выполняется немного медленнее. Tuist инструментирует только крейты вашего репозитория: зависимости собираются точно так же, как и при обычных сборках, и продолжают браться из кэша. Tuist хранит оба варианта ваших собственных крейтов в директории target, поэтому переключение между запусками с покрытием и без него не приводит к их пересборке, если их код не изменился.

## Ограничения {#limitations}

- **Пользовательский `rustc-wrapper` с флагами `rustflags` для конкретной цели.** Если ваш проект задает собственный `rustc-wrapper`, Tuist вместо этого добавляет `-C instrument-coverage` в `build.rustflags` Cargo. Запись `target.<triple>.rustflags` в файле конфигурации Cargo заменяет их, поэтому добавьте флаг туда самостоятельно. Запуск, тесты которого не записали данные о покрытии, сообщает об этом.
- **Настроенные раннеры целей.** Tuist запускает тестовые бинарные файлы через собственный раннер. Запись `target.<triple>.runner` в файле конфигурации Cargo занимает его место: данные о покрытии запуска все равно загружаются, но Tuist не может определить, какой именно тестовый бинарный файл что выполнял. Раннер, заданный через переменную окружения `CARGO_TARGET_<TRIPLE>_RUNNER`, продолжает работать.
- **Нет данных о покрытии из pull request’ов из форков.** Данные о покрытии загружаются только запусками, которые аутентифицируются в Tuist, а CI-системы обычно не передают секреты и токены идентификации в pull request’ы, открытые из форков.

## Запрос данных о покрытии {#querying}

Страница **Code Coverage** на панели управления показывает показатель каждого коммита, его пакеты и файлы с функциями, которые содержит каждый файл. Эти же данные доступны агентам через <.localized_link href="/guides/features/agentic-coding/mcp">сервер Model Context Protocol</.localized_link>.
