# Покрытие кода Rust {#rust-code-coverage}

Покрытие кода показывает, какие строки вашего кода выполнили тесты. Tuist измеряет покрытие по строкам каждого запуска `cargo test` с помощью инструмента LLVM на основе исходного кода и объединяет результаты запусков одного коммита в единую метрику для проекта, каждого пакета и каждого файла. Страница **Покрытие кода** на панели управления отображает эти данные для каждого коммита и в виде тренда для каждой ветки.

> [!IMPORTANT]
> **Требования**
>
> - Следуйте инструкциям по <.localized_link href="/guides/get-started/rust-project">настройке проекта Rust</.localized_link>
> - Инструменты LLVM из вашего инструментария Rust (`llvm-tools`). Tuist устанавливает их в тулчейн, управляемый rustup.
> - Ваш проект находится в репозитории Git

## Настройка {#setup}

### Включение покрытия {#turn-coverage-on}

Добавьте это в корневой файл `Cargo.toml` рабочего пространства:

```toml
[workspace.metadata.tuist.test_insights.coverage]
upload = true
```

Если вы настраиваете Tuist через `tuist.toml`, добавьте туда раздел `[test_insights.coverage]` с параметром `upload = true`.

Затем запустите тесты как обычно:

```sh
tuist cargo test --workspace
```

Tuist собирает крейты вашего репозитория с флагом `-C instrument-coverage`, запускает тесты и загружает данные о покрытии вместе с результатами тестового запуска. Вывод и код выхода ваших тестов не изменяются. Чтобы переопределить настройку для отдельного запуска, установите `TUIST_COVERAGE_UPLOAD=1` или `TUIST_COVERAGE_UPLOAD=0`.

Покрытие опирается на историю Git, которую Tuist загружает с каждым запуском, собирающим эти данные, что позволяет привязать коммит к его ветке. Запуск вне репозитория Git загружает результаты тестов, но не данные о покрытии.

### Шардированные запуски {#sharded-runs}

Когда вы <.localized_link href="/guides/features/test-sharding/rust">шардируете свои тесты</.localized_link>, каждый шард, выполняющийся с включенным покрытием, сообщает о покрытии своих собственных целей, а Tuist объединяет данные всех шардов одного запуска в единую метрику. Шард преднамеренно выполняет только часть набора тестов, поэтому это не делает покрытие коммита неполным.

### Завершение обработки каждого коммита в CI {#complete-each-commit}

Покрытие коммита часто формируется из нескольких задач: по одной на каждый шард или набор функций. Tuist не может самостоятельно определить, когда отчиталась последняя из них, поэтому сообщите ему об этом. Как только все тестовые задачи для коммита завершатся, выполните эту команду в задаче, зависящей от всех них:

```sh
tuist cargo coverage-complete
```

Команда считывает коммит из `HEAD` рабочей копии — тот самый коммит, на котором выполнялись ваши тесты; передайте `--commit <sha>`, чтобы указать другой коммит. Пока коммит не будет помечен как завершенный, его покрытие отображается как **В процессе** и не учитывается в тренде ветки.

## Как это работает {#how-it-works}

### Что измеряет Tuist {#what-tuist-measures}

- **Пакеты.** Каждый пакет Cargo является целью на панели управления со своим собственным показателем покрытия.
- **Только код продукта.** Интеграционные тесты, бенчмарки и примеры (каталоги `tests/`, `benches/` и `examples/`, а также цели таких типов) считаются тестовым кодом. Tuist сохраняет их, но исключает из всех метрик. Юнит-тесты в модуле `#[cfg(test)]` являются частью своего исходного файла, поэтому их строки учитываются вместе с ним, как в `cargo llvm-cov`.
- **Функции.** Каждая строка относится к функции, начало которой расположено ближе всего выше неё. Обобщённая функция учитывается один раз, независимо от количества типов, с которыми она была инстанцирована.
- **Doctests** выполняются как обычно, но не измеряются.

Tuist также записывает, какой код выполнял каждый тестовый бинарный файл, для последующего выбора тестов на основе покрытия. `cargo test` запускает тесты бинарного файла в одном процессе, поэтому эта запись относится ко всему бинарному файлу в целом, а не к его отдельным тестам.

### Пропущенные тесты {#skipped-tests}

Если аргументы самого запуска исключают некоторые тесты, например, фильтр по имени теста, `--skip`, `--ignored`, `-p`, `--exclude`, `--lib` или `--test`, покрытие коммита считается **Неполным**, если только не был выполнен другой запуск этого же коммита, который ничего не исключал. Сбой, останавливающий `cargo test` до выполнения всех тестовых бинарных файлов, имеет тот же эффект. Добавьте `--no-fail-fast`, чтобы продолжить выполнение оставшихся бинарных файлов.

Некоторые тесты исключаются преднамеренно и не делают покрытие коммита неполным:

- **Тесты, которые пропускает <.localized_link href="/guides/features/test-insights/flaky-tests/rust">карантин</.localized_link>.** Они исключаются так, будто были удалены, поэтому строки, покрытые только ими, считаются непокрытыми.
- **Цели других шардов**, когда вы шардируете свои тесты.
- **Игнорируемые тесты** (`#[ignore]`), которые не запускаются по умолчанию.

### Незафиксированные изменения {#uncommitted-changes}

Запуск из рабочей копии, где отслеживаемые файлы имеют незафиксированные изменения, измерял код, не относящийся к данному коммиту, поэтому его покрытие не учитывается для этого коммита. Запуск выдаёт предупреждение и список изменённых файлов. Файлы, которые ваша задача CI создаёт рядом с исходниками, такие как артефакты сборки или отчёты о покрытии, не считаются изменениями, пока Git их не отслеживает. Если коммит измерялся только такими запусками, его покрытие будет **Неполным**, а `tuist cargo coverage-complete` объяснит причину.

### Завершённые и незавершённые коммиты {#commit-status}

Каждый коммит на панели управления имеет статус:

| Статус | Значение |
| --- | --- |
| В процессе | Запуски сообщили о покрытии, но `tuist cargo coverage-complete` ещё не выполнялась для этого коммита. |
| Завершён | Все тесты запусков коммита выполнились или были исключены преднамеренно. |
| Неполное | Часть покрытия не удалось определить, поэтому значение является нижней границей. |
| Не измерялось | Ни один запуск не сообщил о покрытии для этого коммита. |

Тренд ветки включает только завершённые коммиты.

## Влияние на производительность {#performance-impact}

Инструментированный код выполняется немного медленнее. Туист инструментирует только крейты вашего репозитория: зависимости собираются точно так же, как в обычных сборках, и берутся из кэша. Туист хранит оба варианта ваших собственных крейтов в целевой директории, поэтому переключение между запусками с покрытием и без него не приводит к их пересборке, если их код не изменился.

## Ограничения {#limitations}

- **Пользовательский `rustc-wrapper` со специфичными для цели `rustflags`.** Когда ваш проект задаёт собственный `rustc-wrapper`, Туист вместо этого добавляет `-C instrument-coverage` в `build.rustflags` Cargo. Запись `target.<triple>.rustflags` в файле конфигурации Cargo заменяет их, поэтому добавьте флаг туда самостоятельно. Запуск, чьи тесты не записали покрытие, сообщает об этом.
- **Настроенные раннеры целей.** Туист запускает тестовые бинарные файлы через собственный раннер. Запись `target.<triple>.runner` в файле конфигурации Cargo заменяет его: покрытие запуска всё равно загружается, но Туист не может определить, какой тестовый бинарный файл что выполнял. Раннер, заданный через переменную окружения `CARGO_TARGET_<TRIPLE>_RUNNER`, продолжает работать.
- **Нет покрытия от пул-реквестов из форков.** Покрытие загружается только запусками, которые аутентифицируются в Туист, а CI обычно не передаёт секреты и токены идентичности пул-реквестам, открытым из форков.

## Запрос покрытия {#querying}

Страница **Покрытие кода** на панели управления показывает значение для каждого коммита, его пакеты и файлы с функциями, которые содержит каждый файл. Те же данные доступны агентам через <.localized_link href="/guides/features/agentic-coding/mcp">сервер Model Context Protocol</.localized_link>.
