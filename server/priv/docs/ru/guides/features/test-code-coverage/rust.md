# Покрытие кода Rust {#rust-code-coverage}

Покрытие кода показывает, какие строки вашего кода были выполнены тестами. Tuist измеряет покрытие по строкам каждого запуска `cargo test` с помощью инструментария LLVM на основе исходного кода и объединяет результаты всех запусков коммита в единую метрику для проекта, каждого пакета и каждого файла. На странице **Покрытие кода** в дашборде эти данные отображаются для каждого коммита и в виде тренда для каждой ветки.

> [!IMPORTANT]
> **Требования**
>
> - Следуйте инструкциям по <.localized_link href="/guides/get-started/rust-project">настройке Rust-проекта</.localized_link>
> - Инструменты LLVM из вашего Rust-тулчейна (`llvm-tools`). Tuist устанавливает их в тулчейн, управляемый rustup.
> - Ваш проект находится в Git-репозитории

## Настройка {#setup}

### Включение покрытия {#turn-coverage-on}

Добавьте следующее в корневой файл `Cargo.toml` рабочего пространства:

```toml
[workspace.metadata.tuist.test_insights.coverage]
upload = true
```

Если вы настраиваете Tuist через файл `tuist.toml`, добавьте туда раздел `[test_insights.coverage]` с параметром `upload = true`.

Затем запустите тесты как обычно:

```sh
tuist cargo test --workspace
```

Tuist собирает крейты вашего репозитория с флагом `-C instrument-coverage`, запускает тесты и загружает данные о покрытии вместе с результатами тестового запуска. Вывод и код выхода ваших тестов не изменяются. Чтобы переопределить настройку для одного запуска, установите `TUIST_COVERAGE_UPLOAD=1` или `TUIST_COVERAGE_UPLOAD=0`.

Покрытие опирается на историю Git, которую Tuist загружает при каждом сборе данных, что позволяет привязать коммит к его ветке. Запуск вне Git-репозитория загружает результаты тестов, но не данные о покрытии.

### Шардированные запуски {#sharded-runs}

Когда вы <.localized_link href="/guides/features/test-sharding/rust">шардируете свои тесты</.localized_link>, каждый шард, запущенный с включенным покрытием, отчитывается о покрытии своих целевых модулей, а Tuist объединяет данные всех шардов одного запуска в единую метрику. Шард преднамеренно выполняет только часть набора тестов, поэтому это не делает покрытие коммита неполным.

### Завершение каждого коммита в CI {#complete-each-commit}

Покрытие коммита часто формируется из нескольких задач: по одной на каждый шард или набор функций. Tuist не может самостоятельно определить, когда отчиталась последняя из них, поэтому сообщите ему об этом. Когда все тестовые задачи для коммита завершены, выполните следующую команду в задаче, зависящей от всех них:

```sh
tuist cargo coverage-complete
```

Команда считывает коммит из рабочей копии или тот, о котором ваш CI-провайдер сообщает в пул-реквесте; передайте `--commit <sha>`, чтобы указать другой коммит. Пока коммит не помечен как завершенный, его покрытие отображается как **В процессе** и не учитывается в тренде ветки.

## Как это работает {#how-it-works}

### Что измеряет Tuist {#what-tuist-measures}

- **Пакеты.** Каждый пакет Cargo является отдельной целью в дашборде со своим собственным покрытием.
- **Только продуктивный код.** Интеграционные тесты, бенчмарки и примеры (каталоги `tests/`, `benches/` и `examples/`, а также цели таких типов) считаются тестовым кодом. Tuist сохраняет их, но исключает из всех метрик. Юнит-тесты в модуле `#[cfg(test)]` являются частью своего исходного файла, поэтому их строки учитываются вместе с ним, как в `cargo llvm-cov`.
- **Функции.** Каждая строка относится к функции, начало которой расположено ближе всего выше неё. Обобщённая функция учитывается один раз, независимо от количества типов, с которыми она была инстанцирована.
- **Doctests** выполняются как обычно, но не измеряются.

Tuist также записывает, какой код выполнял каждый тестовый бинарный файл, для последующего выбора тестов на основе покрытия. `cargo test` запускает тесты бинарного файла в одном процессе, поэтому эта запись относится ко всему бинарному файлу в целом, а не к его отдельным тестам.

### Пропущенные тесты {#skipped-tests}

Если аргументы самого запуска исключают некоторые тесты, например, фильтр по имени теста, `--skip`, `--ignored`, `-p`, `--exclude`, `--lib` или `--test`, то покрытие коммита считается **Неполным**, если не был выполнен другой запуск этого же коммита, который ничего не исключал. Сбой, останавливающий `cargo test` до запуска всех тестовых бинарных файлов, имеет тот же эффект. Добавьте `--no-fail-fast`, чтобы продолжить выполнение оставшихся бинарных файлов.

Некоторые тесты исключаются преднамеренно и не делают коммит неполным:

- **Тесты, которые пропускает <.localized_link href="/guides/features/test-insights/flaky-tests/rust">карантин</.localized_link>.** Они исключаются так, как если бы были удалены, поэтому строки, покрытые только ими, считаются непокрытыми.
- **Целевые модули других шардов**, когда вы шардируете свои тесты.
- **Игнорируемые тесты** (`#[ignore]`), которые не запускаются по умолчанию.

### Завершенные и незавершенные коммиты {#commit-status}

Каждый коммит в дашборде имеет статус:

| Статус | Значение |
| --- | --- |
| В процессе | Запуски отчитались о покрытии, но `tuist cargo coverage-complete` ещё не был выполнен для этого коммита. |
| Завершен | Все тесты запусков коммита были выполнены или исключены преднамеренно. |
| Неполный | Некоторые данные покрытия не удалось определить, поэтому показатель является нижней границей. |
| Не измерялось | Ни один запуск не сообщил о покрытии для этого коммита. |

Тренд ветки включает только завершенные коммиты.

## Влияние на производительность {#performance-impact}

Инструментированный код выполняется немного медленнее. Tuist инструментирует только крейты вашего репозитория: зависимости собираются точно так же, как и при обычных сборках, и по-прежнему берутся из кэша. Tuist хранит оба варианта ваших собственных крейтов в целевой директории, поэтому переключение между запусками с покрытием и без него не вызывает их пересборку, если только их код не изменился.

## Ограничения {#limitations}

- **Пользовательский `rustc-wrapper` со специфичными для таргета `rustflags`.** Если ваш проект устанавливает собственный `rustc-wrapper`, Tuist вместо этого добавляет `-C instrument-coverage` в `build.rustflags` Cargo. Запись `target.<triple>.rustflags` в конфигурационном файле Cargo заменяет их, поэтому добавьте флаг туда самостоятельно. Запуск, тесты которого не записали покрытие, сообщает об этом.
- **Настроенные раннеры таргетов.** Tuist запускает тестовые бинарные файлы через собственный раннер. Запись `target.<triple>.runner` в конфигурационном файле Cargo занимает его место: покрытие запуска всё равно загружается, но Tuist не может определить, какой тестовый бинарный файл что выполнял. Раннер, установленный через переменную окружения `CARGO_TARGET_<TRIPLE>_RUNNER`, продолжает работать.
- **Нет покрытия от пул-реквестов из форков.** Покрытие загружается только запусками, которые аутентифицируются в Tuist, а CI обычно не передает секреты и токены идентификации пул-реквестам, открытым из форков.

## Запрос данных о покрытии {#querying}

Страница **Покрытие кода** в дашборде показывает показатель каждого коммита, его пакеты и файлы с функциями, которые содержит каждый файл. Те же данные доступны агентам через <.localized_link href="/guides/features/agentic-coding/mcp">сервер Model Context Protocol</.localized_link>.
