# Покрытие кода Rust {#rust-code-coverage}

Покрытие кода показывает, какие строки вашего кода были выполнены тестами. Tuist измеряет покрытие по строкам каждого запуска `cargo test`, используя основанное на исходном коде покрытие LLVM, и объединяет результаты всех запусков коммита в одну метрику для проекта, каждого пакета и каждого файла. На странице **Code Coverage** дашборда эти данные отображаются для каждого коммита и в виде тренда для каждой ветки.

> [!IMPORTANT]
> **Требования**
>
> - Следуйте инструкциям по <.localized_link href="/guides/get-started/rust-project">настройке проекта Rust</.localized_link>
> - Инструменты LLVM из вашего инструментария Rust (`llvm-tools`). Tuist устанавливает их в тулчейн, управляемый rustup.
> - Ваш проект находится в репозитории Git

## Настройка {#setup}

### Включение покрытия {#turn-coverage-on}

Добавьте это в корневой файл `Cargo.toml` воркспейса:

```toml
[workspace.metadata.tuist.test_insights.coverage]
upload = true
```

Если вы настраиваете Tuist через `tuist.toml`, добавьте туда раздел `[test_insights.coverage]` с параметром `upload = true`.

Затем запустите тесты как обычно:

```sh
tuist cargo test --workspace
```

Tuist собирает крейты вашего репозитория с флагом `-C instrument-coverage`, запускает тесты и загружает данные о покрытии вместе с результатами запуска. Вывод и код выхода ваших тестов не изменяются. Чтобы переопределить настройку для одного запуска, установите `TUIST_COVERAGE_UPLOAD=1` или `TUIST_COVERAGE_UPLOAD=0`.

Покрытие опирается на историю Git, которую Tuist загружает при каждом сборе данных, что позволяет привязать коммит к его ветке. Запуск вне репозитория Git загружает результаты тестов, но не данные о покрытии.

### Запуски с шардированием {#sharded-runs}

Когда вы <.localized_link href="/guides/features/test-sharding/rust">шардируете свои тесты</.localized_link>, каждый шард, запущенный с включенным покрытием, сообщает о покрытии своих целей, а Tuist объединяет данные всех шардов одного запуска в единую метрику. Шард преднамеренно выполняет только часть набора тестов, поэтому это не делает покрытие коммита неполным.

### Завершение обработки каждого коммита в CI {#complete-each-commit}

Покрытие коммита часто формируется из нескольких задач: по одной на шард или набор функций. Tuist не может определить, когда отчиталась последняя из них, поэтому сообщите ему об этом. Как только все тестовые задачи для коммита завершатся, выполните эту команду в задаче, зависящей от всех них:

```sh
tuist cargo coverage-complete
```

Команда считывает коммит из 체크아웃нутой версии или тот, о котором ваш CI-провайдер сообщает в пул-реквесте; передайте `--commit <sha>`, чтобы указать другой коммит. Пока коммит не будет помечен как завершенный, его покрытие отображается как **In progress** и не учитывается в тренде ветки.

## Как это работает {#how-it-works}

### Что измеряет Tuist {#what-tuist-measures}

- **Пакеты.** Каждый пакет Cargo является отдельной целью на дашборде со своим собственным покрытием.
- **Только код продукта.** Интеграционные тесты, бенчмарки и примеры (директории `tests/`, `benches/` и `examples/`, а также цели этих типов) считаются тестовым кодом. Tuist сохраняет их, но исключает из всех метрик. Юнит-тесты в модуле `#[cfg(test)]` являются частью их исходного файла, поэтому их строки учитываются вместе с ним, как в `cargo llvm-cov`.
- **Функции.** Каждая строка относится к функции, начало которой расположено ближе всего выше неё. Обобщённая функция учитывается один раз, независимо от количества типов, с которыми она была инстанцирована.
- **Doctests** выполняются как обычно, но не измеряются.

Tuist также записывает, какой код выполнял каждый тестовый бинарный файл, для последующего выбора тестов на основе покрытия. `cargo test` запускает тесты бинарного файла в одном процессе, поэтому эта запись относится ко всему бинарному файлу в целом, а не к отдельным тестам.

### Пропущенные тесты {#skipped-tests}

Если аргументы самого запуска исключают некоторые тесты, например фильтр по имени теста, `--skip`, `--ignored`, `-p`, `--exclude`, `--lib` или `--test`, то покрытие коммита считается **Incomplete**, если только не был выполнен другой запуск этого же коммита, который ничего не исключал. Сбой, останавливающий `cargo test` до того, как будут запущены все тестовые бинарные файлы, имеет тот же эффект. Добавьте `--no-fail-fast`, чтобы продолжить выполнение оставшихся бинарных файлов.

Некоторые тесты исключаются преднамеренно и не делают покрытие коммита неполным:

- **Тесты, которые пропускает <.localized_link href="/guides/features/test-insights/flaky-tests/rust">карантин</.localized_link>.** Они исключаются так, будто были удалены, поэтому строки, покрытые только ими, считаются непокрытыми.
- **Цели других шардов**, если вы используете шардирование тестов.
- **Игнорируемые тесты** (`#[ignore]`), которые не запускаются по умолчанию.

### Завершенные и незавершенные коммиты {#commit-status}

Каждый коммит на дашборде имеет статус:

| Статус | Значение |
| --- | --- |
| В процессе | Запуски сообщили данные о покрытии, но команда `tuist cargo coverage-complete` ещё не была выполнена для этого коммита. |
| Завершен | Все тесты запусков коммита были выполнены или исключены преднамеренно. |
| Неполный | Некоторые данные о покрытии не удалось определить, поэтому показатель является нижней границей. |
| Не измерялось | Ни один запуск не сообщил данные о покрытии для этого коммита. |

Тренд ветки включает только завершенные коммиты.

## Влияние на производительность {#performance-impact}

Инструментированный код выполняется немного медленнее. Tuist инструментирует только крейты вашего репозитория: зависимости собираются точно так же, как и при обычных сборках, и по-прежнему берутся из кэша. Tuist хранит оба варианта ваших собственных крейтов в целевой директории, поэтому переключение между запусками с покрытием и без него не приводит к их пересборке, если только не изменился их код.

## Ограничения {#limitations}

- **Пользовательский `rustc-wrapper` со специфичными для цели `rustflags`.** Если ваш проект задает собственный `rustc-wrapper`, Tuist вместо этого добавляет `-C instrument-coverage` в `build.rustflags` Cargo. Запись `target.<triple>.rustflags` в файле конфигурации Cargo заменяет их, поэтому добавьте этот флаг туда самостоятельно. Запуск, тесты которого не записали данные о покрытии, сообщает об этом.
- **Настроенные исполнители целей.** Tuist запускает тестовые бинарные файлы через собственный исполнитель. Запись `target.<triple>.runner` в файле конфигурации Cargo занимает его место: данные о покрытии запуска все равно загружаются, но Tuist не может определить, какой именно тестовый бинарный файл что выполнял. Исполнитель, заданный через переменную окружения `CARGO_TARGET_<TRIPLE>_RUNNER`, продолжает работать.
- **Нет данных о покрытии из пул-реквестов из форков.** Покрытие загружается только запусками, которые проходят аутентификацию в Tuist, а CI обычно не передает секреты и токены идентификаторности пул-реквестам, открытым из форков.

## Запрос данных о покрытии {#querying}

Страница **Code Coverage** на дашборде показывает показатель каждого коммита, его пакеты и файлы с функциями, содержащимися в каждом файле. Те же данные доступны агентам через <.localized_link href="/guides/features/agentic-coding/mcp">сервер Model Context Protocol</.localized_link>.
