# Вебхуки {#webhooks}

Вебхуки позволяют вашим системам реагировать на изменения в Tuist в момент их возникновения. При наступлении соответствующего события — обнаружении нового тест-кейса, завершении загрузки превью или устранении нестабильного теста — Tuist выполняет HTTP POST-запрос ко всем конечным точкам, которые вы подписали на этот тип события. Тело запроса представляет собой JSON-обертку, а каждая доставка содержит заголовок с подписью, которую можно проверить с помощью секрета подписи конечной точки.

Вы регистрируете URL назначения, выбираете нужные события, а Tuist берет на себя подписание, повторные попытки и ведение журнала аудита доставок.

## Шаги для получения вебхуков {#steps}

Вы можете начать получать уведомления о событиях в вашем приложении, выполнив следующие шаги:

1. [Определите события](#event-types), которые должно получать ваше приложение.
2. [Создайте конечную точку вебхука](#create-an-endpoint) как HTTP-эндпоинт (URL) на вашем локальном сервере.
3. Обрабатывайте запросы от Tuist, [разбирая полезную нагрузку](#payload) и возвращая [статус 2xx](#responding), чтобы Tuist пометил доставку как успешную.
4. [Проверяйте подпись](#verify-signature) в каждом запросе, чтобы убедиться, что он пришел от Tuist.
5. Используйте [журнал событий](#inspect-deliveries) в панели управления Tuist для отладки во время разработки.

## Типы событий {#event-types}

Tuist группирует события по ресурсу, который они описывают. Поле `type` в обертке использует точечную нотацию (`{resource}.{action}`) — то же значение, которое вы бы выбрали при подписке в панели управления.

## Создание конечной точки {#create-an-endpoint}

Конечные точки настраиваются для каждого аккаунта. Откройте раздел **Webhooks** в настройках аккаунта, нажмите **Add endpoint** и укажите:

- **Name** — как конечная точка отображается в списке.
- **Endpoint URL** — должен использовать `https://`.
- **Events to listen for** — выберите конкретные события или используйте **Select all** на уровне группы. Tuist отправляет POST-запросы на конечную точку только при срабатывании одного из подписанных событий.

![Список конечных точек с двумя вебхук-эндпоинтами, каждый из которых подписан на два события](/images/guides/integrations/webhooks/endpoints.png)

При сохранении Tuist генерирует новый секрет подписи и показывает его один раз. Немедленно скопируйте его в конфигурацию вашего приложения — вы не сможете получить его снова из панели управления. Если вы потеряете его, используйте пункт **Rotate secret** в меню действий конечной точки, чтобы выпустить новый.

## Полезная нагрузка {#payload}

Каждая доставка представляет собой один JSON-объект. Обертка содержит снимок ресурса, специфичный для события, в метаданных, которые можно использовать для дедупликации, маршрутизации и аудита доставок:

| Поле     | Описание                                                              |
| --------- | ------------------------------------------------------------------------ |
| `id`      | UUID, уникальный для этой доставки. Используйте его для дедупликации при повторных попытках. |
| `type`    | Тип события в точечной нотации, например `test_case.updated`.                         |
| `created` | Unix-временная метка (в секундах), когда Tuist поставил доставку в очередь.           |
| `object`  | Снимок ресурса. Структура зависит от типа события.              |

Точная схема полезной нагрузки для каждого типа события документирована в [справочнике API Tuist](https://tuist.dev/api/docs#section/Webhook-events) в разделе **Webhook events** — каждое событие имеет соответствующую схему `WebhookXxxEvent` в разделе `components.schemas`, на которую можно сослаться через `$ref` из генератора кода.

Полезная нагрузка `test_case.updated`, например, также содержит массив `events` со списком канонических переходов, вызвавших запись (`marked_flaky`, `muted`, `unskipped`, …), а также `actor_id` и `alert_id`, чтобы получатели могли отличить ручные правки от изменений, инициированных автоматизацией.

Каждый запрос также содержит следующие HTTP-заголовки:

| Заголовок              | Описание                                                                                   |
| ------------------- | --------------------------------------------------------------------------------------------- |
| `Content-Type`      | Всегда `application/json`.                                                                    |
| `User-Agent`        | `Tuist-Webhooks/1.0`.                                                                         |
| `Tuist-Event-Id`    | Такой же UUID, как `id` в теле запроса — удобно, если вы логируете заголовки до разбора полезной нагрузки.     |
| `Tuist-Event-Type`  | Та же строка, что и `type` в теле запроса.                                                            |
| `Tuist-Signature`   | Подпись HMAC-SHA256 в формате `t={timestamp},v1={hex_digest}` — см. ниже.          |

## Ответ на вебхук {#responding}

Для подтверждения доставки ваша конечная точка должна вернуть любой код статуса `2xx`. Все, что выходит за пределы диапазона `2xx`, а также ошибки соединения и таймауты, считаются неудачной доставкой и повторяются. Tuist не следует за ответами `3xx`, поэтому отвечайте напрямую по каноническому URL, а не через перенаправление.

Сделайте ваш обработчик **быстрым**: Tuist ожидает ответа до **10 секунд**. Если вам нужно выполнить ресурсоемкие задачи (вызов другого API, обновление базы данных, отправка уведомлений), примите запрос и обработайте его асинхронно. Быстрый возврат ответа также повышает устойчивость к временным задержкам в ваших downstream-сервисах.

## Проверка подписи {#verify-signature}

Любой, кто узнает URL вашей конечной точки, может отправить на нее POST-запрос. Секрет подписи позволяет вашему серверу отклонять все запросы, которые не поступили от Tuist.

Для каждого запроса Tuist вычисляет:

```
signed_payload = "{timestamp}.{raw_request_body}"
signature      = HMAC-SHA256(signing_secret, signed_payload)
header         = "t={timestamp},v1={hex(signature)}"
```

Чтобы проверить подпись на своей стороне:

1. Прочитайте заголовок `Tuist-Signature` и разделите его на части `t=` (временная метка) и `v1=` (hex-дайджест).
2. Отклоните запрос, если временная метка отличается от текущего времени вашего сервера более чем на **5 минут**. Это *ограничивает* окно повторного воспроизведения, но не закрывает его полностью — используйте это вместе с идемпотентностью, описанной ниже.
3. Повторно вычислите `HMAC-SHA256(signing_secret, "{timestamp}.{raw_body}")` и сравните результат с дайджестом за **константное время**.
4. Выполняйте дедупликацию доставок по идентификатору полезной нагрузки `id` (также доступен в заголовке `Tuist-Event-Id`). Он остается неизменным при повторных попытках, поэтому сохранение уже обработанных ID предотвращает повторное выполнение перехваченного запроса в пределах допустимого окна и защищает от двойной обработки при повторе.

> [!IMPORTANT] USE THE RAW BODY
> Подпись вычисляется по байтам, отправленным Tuist. Если ваш веб-фреймворк повторно парсит и сериализует JSON перед проверкой, дайджест не совпадет. Получайте «сырое» тело запроса (например, `request.body.read` в Rack, необработанный `Buffer` в Express) и передавайте его верификатору.

Эталонный верификатор на Node.js — адаптируйте те же четыре шага (разбор заголовка, проверка смещения временной метки, повторное вычисление HMAC, сравнение за константное время) под любой язык, на котором написан ваш получатель:

```javascript
import crypto from "node:crypto";

function verifyTuistSignature(rawBody, header, secret, toleranceSeconds = 300) {
  const parts = Object.fromEntries(
    header.split(",").map((kv) => kv.split("=", 2))
  );
  const timestamp = Number(parts.t);
  const signature = parts.v1;
  if (!timestamp || !signature) return false;

  const drift = Math.abs(Math.floor(Date.now() / 1000) - timestamp);
  if (drift > toleranceSeconds) return false;

  const expected = crypto
    .createHmac("sha256", secret)
    .update(`${timestamp}.${rawBody}`)
    .digest("hex");

  const a = Buffer.from(expected, "hex");
  const b = Buffer.from(signature, "hex");
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}
```

## Повторные попытки {#retries}

Tuist повторяет любую доставку, которая возвращает статус, отличный от `2xx`, истекает по таймауту или не может установить соединение. Расписание фиксировано:

| Попытка | Ожидание перед отправкой |
| ------- | ------------------- |
| 1       | (немедленно)         |
| 2       | 1 минута            |
| 3       | 5 минут           |
| 4       | 30 минут          |
| 5       | 2 часа             |
| 6       | 8 часов             |
| 7       | 24 часа            |

После седьмой неудачной попытки доставка навсегда помечается как неудачная. Поскольку каждая попытка подписывается временной меткой момента отправки, ваше окно защиты от повторного воспроизведения действует и для повторных попыток — расширять его не нужно.

## Просмотр доставок {#inspect-deliveries}

Откройте конечную точку на странице **Webhooks**, чтобы увидеть историю ее доставок. На странице деталей отображаются:

- **Карточка сводки** с URL назначения, замаскированным секретом подписи, подписанными событиями и датой создания.
- **Диаграмма доставок** с накопительными итогами и количеством ошибок в выбранном временном окне.
- **Таблица событий**, которую можно фильтровать по статусу, типу события или ID события.

Нажмите на событие, чтобы увидеть полный запрос и ответ этой попытки — точную полезную нагрузку, отправленную Tuist, заголовки, код статуса upstream-сервера и тело ответа. Это те же данные, которые видел ваш сервер, что делает этот способ самым быстрым для отладки несоответствия при проверке подписи или ошибки 5xx на стороне upstream.

Записи о доставках хранятся бессрочно, чтобы вы могли обращаться к ним при отладке интеграции. Если вашей downstream-системе нужны надежные копии (например, для соблюдения нормативных требований), сохраняйте доставки на своей инфраструктуре по мере их поступления.

## Ротация или удаление конечной точки {#rotate-or-delete}

Оба действия доступны в меню с тремя точками в строке конечной точки и на странице ее деталей:

- **Ротировать секрет** — генерирует новый секрет подписи и показывает его один раз. Существующие потребители не пройдут проверку, пока вы их не обновите, поэтому планируйте ротацию вместе с развертыванием.
- **Удалить конечную точку** — удаляет конечную точку и останавливает доставку. Уже записанные попытки доставки сохраняются до истечения стандартного срока хранения.

## Заметки по безопасности {#security}

- URL-адреса конечных точек должны использовать HTTPS. Tuist отказывается доставлять данные на адреса без шифрования.
- Tuist разрешает имя хоста назначения перед каждой доставкой и отклоняет loopback-адреса, адреса RFC1918, link-local, ULA и адреса облачных метаданных (`169.254.169.254`, `fd00::/8`, …). Это предотвращает использование неправильно настроенного вебхука для сканирования или атаки на хост, на котором работает ваш сервер Tuist.
- URL конечной точки и секрет подписи шифруются при хранении. Они исключаются из экспортов данных GDPR/CCPA как учетные данные bearer.
- Секрет подписи показывается ровно один раз. Относитесь к нему как к паролю: храните его в менеджере секретов, а не в репозитории.
