# Вебхуки {#webhooks}

Вебхуки позволяют вашим системам реагировать на изменения в Tuist в момент их возникновения. При возникновении соответствующего события — обнаружении нового тест-кейса, завершении загрузки превью или исправлении нестабильного теста — Tuist отправляет HTTP POST-запрос на каждый конечный пункт, подписанный на этот тип события. Тело запроса представляет собой JSON-обёртку, а каждая доставка содержит заголовок с подписью, которую можно проверить с помощью секрета подписи конечного пункта.

Вы регистрируете URL назначения, выбираете нужные события, а Tuist берёт на себя подписание, повторные попытки и журнал аудита доставок.

## Шаги для получения вебхуков {#steps}

Вы можете начать получать уведомления о событиях в своём приложении, выполнив следующие шаги:

1. [Определите события](#event-types), которые должно получать ваше приложение.
2. [Создайте конечный пункт вебхука](#create-an-endpoint) в виде HTTP-эндпоинта (URL) на вашем локальном сервере.
3. Обрабатывайте запросы от Tuist, [разбирая полезную нагрузку](#payload) и возвращая [статус 2xx](#responding), чтобы Tuist пометил доставку как успешную.
4. [Проверяйте подпись](#verify-signature) каждого запроса, чтобы убедиться, что он пришёл от Tuist.
5. Используйте [журнал событий](#inspect-deliveries) в панели управления Tuist для отладки во время разработки.

## Типы событий {#event-types}

Tuist группирует события по ресурсу, который они описывают. Поле `type` в обёртке использует точечную нотацию (`{resource}.{action}`) — так же, как значение, на которое вы подписываетесь в панели управления.

## Создание конечного пункта {#create-an-endpoint}

Конечные пункты настраиваются для каждой учётной записи. Откройте **Вебхуки** в настройках аккаунта, нажмите **Добавить конечный пункт** и укажите:

- **Имя** — как конечный пункт отображается в списке.
- **URL конечного пункта** — должен использовать `https://`.
- **События для прослушивания** — выберите конкретные события или используйте **Выбрать все** на уровне группы. Tuist отправляет POST-запросы на конечный пункт только при срабатывании одного из подписанных событий.

![Список конечных пунктов с двумя вебхук-эндпоинтами, каждый из которых подписан на два события](/images/guides/integrations/webhooks/endpoints.png)

При сохранении Tuist генерирует новый секрет подписи и показывает его один раз. Немедленно скопируйте его в конфигурацию вашего приложения — вы не сможете получить его снова из панели управления. Если вы потеряете его, используйте **Обновить секрет** в меню действий конечного пункта, чтобы выпустить новый.

## Полезная нагрузка {#payload}

Каждая доставка представляет собой единый JSON-объект. Обёртка содержит снимок ресурса, специфичный для события, в метаданных, которые можно использовать для дедупликации, маршрутизации и аудита доставок:

| Поле     | Описание                                                              |
| --------- | ------------------------------------------------------------------------ |
| `id`      | UUID, уникальный для этой доставки. Используйте его для дедупликации при повторных попытках. |
| `type`    | Точечный тип события, например `test_case.updated`.                         |
| `created` | Unix-временная метка (в секундах), когда Tuist поставил доставку в очередь.           |
| `object`  | Снимок ресурса. Структура зависит от типа события.              |

Точная схема полезной нагрузки для каждого типа события документирована в [справочнике API Tuist](https://tuist.dev/api/docs#section/Webhook-events) в разделе **События вебхуков** — каждое событие имеет соответствующую схему `WebhookXxxEvent` в разделе `components.schemas`, на которую можно сослаться через `$ref` из генератора кода.

Например, полезная нагрузка `test_case.updated` также содержит массив `events`, перечисляющий канонические переходы, вызвавшие запись (`marked_flaky`, `muted`, `unskipped`, …), а также `actor_id` и `alert_id`, чтобы получатели могли отличить ручные правки от изменений, инициированных автоматизацией.

Каждый запрос также содержит следующие HTTP-заголовки:

| Заголовок              | Описание                                                                                   |
| ------------------- | --------------------------------------------------------------------------------------------- |
| `Content-Type`      | Всегда `application/json`.                                                                    |
| `User-Agent`        | `Tuist-Webhooks/1.0`.                                                                         |
| `Tuist-Event-Id`    | Тот же UUID, что и `id` в теле запроса — удобно, если вы логируете заголовки до разбора полезной нагрузки.     |
| `Tuist-Event-Type`  | Та же строка, что и `type` в теле запроса.                                                            |
| `Tuist-Signature`   | Подпись HMAC-SHA256, отформатированная как `t={timestamp},v1={hex_digest}` — см. ниже.          |

## Ответ на вебхук {#responding}

Чтобы подтвердить получение доставки, ваш конечный пункт должен вернуть любой код статуса `2xx`. Всё, что выходит за пределы диапазона `2xx`, а также сбои соединения и таймауты, рассматриваются как ошибка доставки и повторяются. Tuist не следует за ответами `3xx`, поэтому отвечайте напрямую по каноническому URL, а не перенаправляйте.

Делайте обработчик **быстрым**: Tuist ожидает ответа до **10 секунд**. Если вам нужно выполнить ресурсоемкие задачи (вызов другого API, обновление базы данных, отправка уведомлений), примите запрос и обработайте его асинхронно. Быстрый ответ также повышает устойчивость к временным задержкам в ваших downstream-сервисах.

## Проверка подписи {#verify-signature}

Любой, кто узнает URL вашего конечного пункта, может отправить на него POST-запрос. Секрет подписи позволяет вашему серверу отклонять все запросы, которые не поступили от Tuist.

Для каждого запроса Tuist вычисляет:

```
signed_payload = "{timestamp}.{raw_request_body}"
signature      = HMAC-SHA256(signing_secret, signed_payload)
header         = "t={timestamp},v1={hex(signature)}"
```

Чтобы проверить подпись на вашей стороне:

1. Прочитайте заголовок `Tuist-Signature` и разделите его на части `t=` (временная метка) и `v1=` (hex-дайджест).
2. Отклоняйте запрос, если временная метка отличается от текущего времени вашего сервера более чем на **5 минут**. Это *ограничивает* окно повторного воспроизведения, но не закрывает его полностью — используйте вместе с идемпотентностью, описанной ниже.
3. Пересчитайте `HMAC-SHA256(signing_secret, "{timestamp}.{raw_body}")` и сравните результат с дайджестом за **постоянное время**.
4. Выполняйте дедупликацию доставок по `id` полезной нагрузки (также доступен как заголовок `Tuist-Event-Id`). Этот идентификатор остается неизменным при повторных попытках, поэтому сохранение уже обработанных ID предотвращает повторное выполнение перехваченного запроса в пределах допустимого окна и защищает от двойной обработки при повторе.

> [!IMPORTANT] USE THE RAW BODY
> Подпись вычисляется по байтам, отправленным Tuist. Если ваш веб-фреймворк повторно парсит и сериализует JSON перед проверкой, дайджест не совпадет. Захватывайте исходное тело запроса (например, `request.body.read` в Rack, необработанный `Buffer` в Express) и передавайте его в верификатор.

Эталонный верификатор на Node.js — адаптируйте те же четыре шага (разбор заголовка, проверка смещения временной метки, пересчет HMAC, сравнение за постоянное время) под язык, на котором написан ваш получатель:

```javascript
import crypto from "node:crypto";

function verifyTuistSignature(rawBody, header, secret, toleranceSeconds = 300) {
  const parts = Object.fromEntries(
    header.split(",").map((kv) => kv.split("=", 2))
  );
  const timestamp = Number(parts.t);
  const signature = parts.v1;
  if (!timestamp || !signature) return false;

  const drift = Math.abs(Math.floor(Date.now() / 1000) - timestamp);
  if (drift > toleranceSeconds) return false;

  const expected = crypto
    .createHmac("sha256", secret)
    .update(`${timestamp}.${rawBody}`)
    .digest("hex");

  const a = Buffer.from(expected, "hex");
  const b = Buffer.from(signature, "hex");
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}
```

## Повторные попытки {#retries}

Tuist повторяет любую доставку, которая возвращает статус, отличный от `2xx`, завершается таймаутом или не может установить соединение. Расписание фиксировано:

| Попытка | Ожидание перед отправкой |
| ------- | ------------------- |
| 1       | (немедленно)         |
| 2       | 1 минута            |
| 3       | 5 минут           |
| 4       | 30 минут          |
| 5       | 2 часа             |
| 6       | 8 часов             |
| 7       | 24 часа            |

После неудачи седьмой попытки доставка окончательно помечается как неуспешная. Поскольку каждая попытка подписывается временной меткой момента отправки, ваше окно защиты от повторного воспроизведения продолжает действовать при повторах — расширять его не нужно.

## Ротация или удаление конечного пункта {#rotate-or-delete}

Оба действия доступны в меню с тремя точками в строке конечного пункта и на странице его деталей:

- **Ротировать секрет** — генерирует новый секрет подписи и показывает его один раз. Существующие потребители не пройдут проверку, пока вы их не обновите, поэтому планируйте ротацию совместно с развертыванием.
- **Удалить конечный пункт** — удаляет конечный пункт и останавливает доставку. Уже записанные попытки доставки сохраняются до истечения стандартного срока хранения.

## Заметки по безопасности {#security}

- URL конечных пунктов должны использовать HTTPS. Tuist отказывается доставлять данные на адреса без шифрования.
- Tuist разрешает имя хоста назначения перед каждой доставкой и отклоняет loopback-адреса, адреса RFC1918, link-local, ULA и адреса облачных метаданных (`169.254.169.254`, `fd00::/8`, …). Это предотвращает использование неправильно настроенного вебхука для сканирования или атаки на хост, где работает ваш сервер Tuist.
- URL конечного пункта и секрет подписи шифруются при хранении. Они исключаются из экспортов данных GDPR/CCPA как учетные данные bearer.
- Секрет подписи показывается ровно один раз. Относитесь к нему как к паролю: храните его в менеджере секретов, а не в репозитории.
