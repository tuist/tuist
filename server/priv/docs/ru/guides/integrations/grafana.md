# Интеграция с Grafana {#grafana}

Источник данных Tuist позволяет использовать в Grafana метрики сборок, тестов и кэша, включая длительность, количество сбоев и сообщаемое время, сэкономленное благодаря кэшированию. Создавайте дашборды вокруг проектов и метрик, важных для вашей команды, или объединяйте метрики Tuist с другими источниками данных в существующих дашбордах вашей компании. Используйте правила оповещений и каналы уведомлений Grafana, чтобы информировать команду о замедлении сборок или росте числа сбоев.

## Доступные метрики {#metric-definitions}

В таблицах перечислены понятные названия и их идентификаторы для запросов. Запросы состояния сборки используют идентификатор в поле `metric`; запросы длительности сборок и тестов выбирают `average`, `p50`, `p90` или `p99` в поле `series`.

### Количество сборок и надежность

| Метрика | Идентификатор | Что измеряет |
| --- | --- | --- |
| Количество сборок | `builds` | Количество записанных сборок. |
| Успешные сборки | `successful_builds` | Сборки, завершившиеся успешно. |
| Неудачные сборки | `failed_builds` | Сборки, завершившиеся с ошибкой. |
| Отмененные сборки | `cancelled_builds` | Сборки, записанные как отмененные. См. [различия между системами сборки](#build-systems). |
| Процент успешных сборок | `success_rate` | Успешные ÷ (успешные + неудачные), в процентах. |
| Неудачные или медленные сборки | `builds_needing_attention` | Неудачные или медленные сборки, учитываемые один раз на сборку. |

### Длительность сборок и тестов

| Метрика | Идентификатор | Что измеряет |
| --- | --- | --- |
| Средняя длительность | `average` | Средняя длительность выбранных запусков. |
| Медианная длительность | `p50` | 50-й перцентиль длительности запусков. |
| Длительность на уровне 90-го процентиля | `p90` | Длительность, ниже или равной которой находятся 90% запусков. |
| Длительность на уровне 99-го процентиля | `p99` | Длительность, ниже или равной которой находятся 99% запусков. |
| Порог медленной сборки | `slow_build_threshold` | Длительность на уровне 90-го процентиля или ваш фиксированный лимит в миллисекундах. |

Метрики длительности тестов используют запуски тестов, записанные в Tuist. Порог медленной сборки применяется только к сборкам: сборка считается медленной, если ее длительность превышает этот порог. Отмененные сборки учитываются отдельно и исключаются из расчета процента успешных сборок.

### Экономия кэша

| Метрика | Идентификатор | Что измеряет |
| --- | --- | --- |
| Суммарное сэкономленное время задач (Gradle) | `cache_work_avoided` | Сумма оценочного времени выполнения задач, сэкономленного благодаря попаданиям в кэш. |
| Сборки с отчётом о суммарном времени задач | `cache_work_avoided_samples` | Сборки с полной оценкой. |
| Отчётное сэкономленное время кэша | `cache_time_saved` | Сумма отчётной экономии elapsed-времени. |
| Сборки с отчётом об экономии времени кэша | `cache_time_saved_samples` | Сборки с корректным значением экономии. |

Плагин Gradle автоматически сообщает оценочную работу, избегаемую при попаданиях в кэш задач локально и удалённо. Для каждой закэшированной задачи он вычитает длительность восстановления задачи из исходного времени выполнения, сохранённого Gradle, с минимумом ноль. Оценка сборки складывает эти значения. Параллельные задачи могут перекрываться, поэтому это суммарное время задач, а не сэкономленное elapsed-время сборки. Актуальные и пропущенные задачи исключаются.

Сборка без попаданий в кэш задач сообщает ноль. Если у какой-либо закэшированной задачи отсутствует исходное время, телеметрия неполная или в карте пользовательских метаданных нет места, плагин опускает оценку. Старые версии плагина и другие системы сборки её не сообщают. Сравните количество отчётов с общим числом сборок, чтобы проверить покрытие.

Отчётная экономия elapsed-времени берётся из метаданных `tuist.cache_time_saved_ms`. Эта метрика остаётся отдельной от автоматической оценки.

Экономия кэша не имеет значения, если ни одна сборка её не сообщает. Once сейчас не записывает это измерение. Процент попаданий и промахов кэша недоступен через этот источник данных.

### Таблицы

Эти идентификаторы являются значениями поля запроса `queryType` .

| Таблица | Тип запроса | Содержимое |
| --- | --- | --- |
| Здоровье по рабочей нагрузке | `buildWorkloads` | Количество сборок, процент успешных, медианная длительность и длительность на уровне 90-го процентиля. |
| Категории сбоев | `buildFailureReasons` | Все сбои и их количество по категориям сбоев. |
| Недавние неудачные сборки | `buildRecentFailures` | Последние 100 сбоев со ссылками на Tuist. |

Недавние сбои включают время начала, длительность, пользователя, ветку и запрошенные задачи. Категории сбоев: `verification`, `infrastructure_tooling` и `unknown` .

Сводки по рабочей нагрузке и списки значений веток/нагрузок возвращают до 1000 значений. Запросы переменных здоровья сборок используют последние 90 дней; устаревшие запросы переменных Gradle сохраняют своё существующее окно истории. Bazel показывает пользователя сборки, сообщаемого инструментом. Другие интеграции показывают аккаунт, связанный с учётными данными отчёта. Исторические запуски Bazel и Once, а также запуски Once, сообщённые с учётными данными проекта, отображаются как Unknown, если пользователь не был записан.

Используйте фильтр «Категория сбоя» на странице Build Runs, чтобы найти соответствующие сбои. Категория отображается в деталях сборки с информационной подсказкой, объясняющей её значение; таблицы обзорной панели по умолчанию и Build Runs сохраняют свои существующие столбцы. Успешные, отменённые и незавершённые сборки не имеют категории сбоя. Карточка Cache Analytics Gradle и детали сборки показывают «Суммарное сэкономленное время задач»; всплывающая подсказка объясняет оценку и влияние параллельных задач. Виджет кэша сравнивает выбранный диапазон с непосредственно предшествующим периодом той же длины, используя те же фильтры. Сравнения нейтральны: большее общее значение может отражать больше сборок. При отсутствии предыдущих оценок сравнение не показывается; записанная нулевая базовая линия показывает абсолютный прирост, а не процент.

## Стандартная панель мониторинга {#what-you-can-query}

Импортируйте [панель мониторинга здоровья сборок](https://github.com/tuist/tuist/blob/main/grafana-datasource/src/dashboards/build-health.json), затем выберите источник данных и проект. Она включает количество сборок, процент успешных, медианную длительность и длительность на уровне 90-го процентиля, порог медленной сборки, нейтральное количество неудачных или медленных сборок, сгруппированную экономию кэша и покрытие отчётами, а также три таблицы сбоев и рабочих нагрузок. Добавьте панели для других доступных метрик по мере необходимости. Автоматический порог медленности — это собственный 90-й перцентиль выбранного периода; сборки выше него не обязательно указывают на регрессию. Установите фиксированный порог для оповещений по целевой длительности. Панели кэша в приоритете показывают автоматическую оценку суммарного времени задач Gradle рядом с её покрытием, затем явно сообщённую экономию elapsed-времени рядом с её собственным покрытием.

## Системы сборки {#build-systems}

Запросы здоровья сборок и стандартная панель мониторинга поддерживают Bazel, Once, Gradle и Xcode. Tuist выбирает систему сборки из вашего проекта. Смешанные проекты сейчас не поддерживаются запросами здоровья сборок или стандартной панелью мониторинга.

| Система сборки | Рабочая нагрузка | Отчётность об отменах | Экономия кэша |
| --- | --- | --- | --- |
| Bazel | Команда | Код выхода 8, кроме `run` | Требует пользовательских метаданных |
| Once | Вид команды | Записанная причина отмены | Не записано |
| Gradle | Группа задач | Сообщённые отмены | Автоматическая оценка сэкономленной работы; экономия elapsed-времени требует пользовательских метаданных |
| Xcode | Схема | Не различается; количество равно нулю | Требует пользовательских метаданных |

Записи обработки и незавершённые запуски исключаются. Bazel включает команды сборки, тестирования, запуска и покрытия кода. Once включает завершённые сборки, тесты и общие запуски.

Gradle группирует задачи как инструментированные тесты, модульные тесты, линтинг/проверки, сборка/пакетирование или Другие, в порядке приоритета. Каждая сборка относится к одной рабочей нагрузке. Пользовательские метаданные могут переопределять рабочие нагрузки для Xcode, Bazel и Gradle.

### Категории сбоев

| Категория | Значение | Записанные доказательства |
| --- | --- | --- |
| `verification` | Код не прошёл компиляцию, линковку, тесты или проверки. | Исключения верификации или компиляции Gradle и известные типы неудачных задач; проблемы компилятора и линковщика Xcode; структурированные ненулевые результаты действий компилятора/тестов Bazel; сбои тестов Once или неудачные действия, явно объявленные как компиляция, линковка, тест, линтинг или проверка. |
| `infrastructure_tooling` | Сборка не могла выполняться нормально из-за сбоя инструментов, зависимостей или окружения. | Сбои конфигурации, разрешения зависимостей, ввода/вывода или памяти в Gradle; структурированные сбои инфраструктуры Bazel и [документированные коды выхода](https://bazel.build/run/scripts); ошибки действий инфраструктуры Once. |
| `unknown` | Отчёт не содержит достаточных доказательств для классификации сбоя. | Произвольные команды, отсутствующая диагностика и старые отчёты без структурированных доказательств. |

Сбои фазы конфигурации Gradle, включая ошибки в скриптах сборки, группируются под инфраструктурой/инструментами, поскольку выполнение задач не могло продолжаться.

Явные метаданные `tuist.failure_category` переопределяют автоматическую классификацию. В противном случае доказательства инфраструктуры имеют приоритет над верификацией, если оба присутствуют в сборке. Сбой произвольного скрипта не считается сбоем компилятора или теста. Исторические отчёты могут использовать доказательства, которые Tuist уже хранит, но новые поля репортёра не заполняют недостающую информацию ретроспективно. Автоматические метаданные репортёра используют доступное пространство в рамках существующего лимита из 20 записей пользовательских метаданных.

Ответ `buildFailureReasons` сохраняет строку `all` для совместимости. Стандартная панель мониторинга исключает эту сумму из диаграммы категорий сбоев и показывает общее количество сбоев отдельно. Устаревший запрос `gradleFailureReasons` сохраняет свои исходные три строки категорий.

## Параметры запроса {#query-options}

Числовые запросы используют следующие значения `queryType`:

| Запрос | Тип запроса |
| --- | --- |
| Здоровье сборки | `buildHealth` |
| Длительность сборок Xcode | `buildDuration` |
| Длительность тестов | `testDuration` |

Поле `resultMode` управляет способом возврата результатов:

| Результат | Значение | Поведение |
| --- | --- | --- |
| Временной ряд | `series` | Значение для каждого интервала. |
| Весь период | `total` | Одно значение, рассчитанное по всем запускам в диапазоне. |

Метки фильтров соответствуют следующим полям запроса:

| Фильтр | Поле запроса | Доступно для |
| --- | --- | --- |
| Окружение | `environment` | Все запросы |
| Ветка | `gitBranch` | Запросы и таблицы здоровья сборки |
| Рабочая нагрузка | `workload` | Запросы и таблицы здоровья сборки |
| Статус | `status` | Запросы здоровья сборки, таблицы и длительность сборок Xcode |
| Схема | `scheme` | Длительность сборок и тестов Xcode |
| Конфигурация | `configuration` | Длительность сборок Xcode |
| Тип сборки | `category` | Длительность сборок Xcode |

Значения окружения: `any`, `ci` (автоматизированные сборки) и `local`. Значения статуса: `success`, `failure` и, для запросов здоровья сборки, `cancelled`; не указывайте значение, чтобы включить все статусы. Значения типа сборки: `clean` и `incremental`; не указывайте значение, чтобы включить оба.

Пустые интервалы здоровья сборки имеют нулевые счётчики и не содержат значений средней длительности, процентиля длительности или коэффициента успешности. Порог медленной сборки всё равно использует весь выбранный диапазон. Отдельный запрос длительности тестов возвращает ноль для пустых интервалов временного ряда. Процентили за весь период рассчитываются по запускам, а не по процентилям интервалов. Процентили здоровья сборки используют точную агрегацию; отдельные запросы длительности сборок Xcode и тестов используют приблизительные процентили.

Временные ряды здоровья сборки размещают частичный первый бакет в начале выбранного диапазона, чтобы он оставался видимым. Устаревшие запросы Gradle сохраняют свои исходные метки времени бакетов.

Все запросы принимают диапазоны дат до 366 дней. Их границы и метки времени различаются:

| Запрос | Используемая метка времени | Границы диапазона |
| --- | --- | --- |
| Здоровье сборки: Xcode, Bazel, Gradle | Время вставки записи | Включает начало, исключает конец |
| Здоровье сборки: Once | Время начала запуска | Включает начало, исключает конец |
| Длительность сборок Xcode | Время вставки записи | Исключает начало и конец |
| Длительность тестов | Зафиксированное время запуска | Включает начало и конец |

### Переменные панели мониторинга

Используйте переменные панели мониторинга для проектов и поддерживаемых фильтров. Переменные ветки и рабочей нагрузки используют следующие запросы:

| Переменная | Запрос |
| --- | --- |
| Ветка | `buildBranches account/project` |
| Рабочая нагрузка | `buildWorkloads account/project` |

Фильтры принимают одно точное значение. Для переменных ветки и рабочей нагрузки установите пользовательское значение опции «Все» в `__tuist_all__`. Остальные фильтры используют встроенную опцию «Любое» или пустое значение. Множественный выбор и регулярные выражения не поддерживаются.

## Передача пользовательских метаданных {#custom-metadata}

Сборки Xcode, Bazel и Gradle принимают следующие необязательные значения метаданных:

| Ключ | Допустимое значение |
| --- | --- |
| `tuist.workload` | Название рабочей нагрузки, заменяющее группировку по умолчанию. |
| `tuist.failure_category` | `verification` или `infrastructure_tooling`. |
| `tuist.cache_work_avoided_ms` | Только для Gradle. Автоматически передаваемая оценка сэкономленной работы в целых миллисекундах (до 365 дней). |
| `tuist.cache_time_saved_ms` | Целые миллисекунды от 0 до 31 536 000 000 (365 дней). |

Передавайте их через конфигурацию пользовательских метаданных вашей интеграции сборки:

```json
{
  "custom_metadata": {
    "values": {
      "tuist.workload": "Release verification",
      "tuist.failure_category": "verification",
      "tuist.cache_time_saved_ms": "12000"
    }
  }
}
```

Сообщайте об экономии кэша только при наличии замера прошедшего времени или документально подтверждённой оценки для этой сборки. Одних лишь попаданий в кэш и суммарной длительности задач недостаточно для определения сэкономленного времени при параллельном выполнении задач. Данные об экономии кэша остаются неизвестными, если они отсутствуют. При отсутствии метаданных категории сбоя система использует зафиксированные доказательства, как описано в разделе [Системы сборки](#build-systems). Политика хранения данных не меняется.

## Оповещения и Slack {#alerts-and-slack}

Создайте правило оповещения, управляемое Grafana, с числовой метрикой. Например:

| Метрика | Идентификатор | Пример условия |
| --- | --- | --- |
| Коэффициент успешности сборок | `success_rate` | Ниже 99% |
| Неудавшиеся сборки | `failed_builds` | Выше нуля |
| Длительность на уровне 90-го процентиля | `p90` | Выше лимита длительности вашей команды |

Используйте **Весь период** для получения одного значения за окно оценки или сведите временной ряд к одному значению. Для запросов длительности в режиме «Весь период» выберите один ряд.

- Используйте фиксированные значения проекта и фильтров. Переменные панели мониторинга недоступны при фоновой оценке оповещений.
- Для оповещений используйте числовые запросы. Чтобы отслеживать рабочую нагрузку, отфильтруйте запрос здоровья сборки по этой рабочей нагрузке.
- Настройте поведение правила при отсутствии данных для интервалов без сборок или переданной экономии кэша.

Настройте [точку контакта Slack](https://grafana.com/docs/grafana/latest/alerting/configure-notifications/manage-contact-points/integrations/configure-slack/) и направьте правило к ней через политику уведомлений Grafana. Grafana отправляет уведомления и хранит учётные данные Slack.

## Обновление существующих панелей мониторинга {#upgrading}

Существующие панели длительности сохраняют свои запросы, фильтры, названия рядов и единицы измерения. Сохранённые панели здоровья Gradle и переменные также продолжают работать.

Импортируйте стандартную панель мониторинга отдельно, чтобы использовать общие запросы здоровья сборки. Существующие панели мониторинга не мигрируют автоматически. Общие запросы требуют сервера Tuist, предоставляющего конечные точки здоровья сборки; существующие запросы длительности продолжают работать со старыми версиями сервера.

## Требования {#requirements}

- Grafana 10.4 или новее.
- Токен Tuist с разрешением на чтение проектов и метрик, которые вы хотите отображать на графиках. См. раздел [Аутентификация](#authentication) ниже.

## Аутентификация {#authentication}

Используйте <.localized_link href="/guides/server/authentication#account-tokens">токен аккаунта</.localized_link> для панелей мониторинга и фоновой оценки оповещений. Предоставьте `project:builds:read` для метрик сборок и `project:tests:read` для длительности тестов, а также ограничьте доступ только теми проектами, которые вы хотите отображать на графиках. Требуются только те области доступа, которые соответствуют используемым вами метрикам. Следуйте <.localized_link href="/guides/server/authentication#creating-an-account-token">инструкциям по созданию токена</.localized_link>, чтобы сгенерировать его.

Интеграция также принимает существующие токены проектов для их собственного проекта и <.localized_link href="/guides/server/authentication#as-a-user">токены доступа пользователя</.localized_link> с правами чтения пользователя. Токены доступа пользователя имеют короткий срок действия. Grafana хранит предоставленный вами токен и не обновляет его и не использует ваш локальный вход в Tuist; замените его по истечении срока действия. Токены аккаунта позволяют управлять доступом к проектам, разрешениями и сроком действия независимо от сеанса входа пользователя.

## Конфигурация {#configuration}

Добавьте источник данных и укажите:

| Поле | Сохранённая настройка | Примечания |
| --- | --- | --- |
| URL сервера | `jsonData.url` | По умолчанию `https://tuist.dev`. |
| Токен | `secureJsonData.apiToken` | Bearer-токен Tuist, хранится в зашифрованном виде. |

Выберите **Save & test**, чтобы проверить подключение. Grafana перечислит доступные проекты, а затем проверит права на чтение метрик сборок и тестов для первого проекта.

## Установка {#installation}

### Из каталога Grafana {#from-the-grafana-catalog}

После публикации установите его как любой другой источник данных через **Connections → Add new connection → Tuist** или с помощью `grafana-cli plugins install tuist-metrics-datasource`.

### До публикации (самостоятельно размещённая Grafana) {#before-it-is-published-self-hosted-grafana}

Плагин не подписан, пока не будет одобрен для каталога. На самостоятельно размещённом экземпляре вы можете:

- **Разрешить неподписанный плагин** — добавьте `tuist-metrics-datasource` в `allow_loading_unsigned_plugins` (или `GF_PLUGINS_ALLOW_LOADING_UNSIGNED_PLUGINS=tuist-metrics-datasource`) и поместите собранный плагин в каталог плагинов.
- **Подписать его privately** для ваших экземпляров — `npm run sign -- --rootUrls https://grafana.example.com` (URL должен совпадать с `root_url` экземпляра), затем распространите zip-архив.

[Grafana Cloud требует плагины из каталога](https://grafana.com/docs/grafana-cloud/learn-and-build/get-started/learn/find-and-use-plugins/) и не поддерживает неподписанные или вручную загруженные плагины.
