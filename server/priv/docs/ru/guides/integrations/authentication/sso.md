# Единый вход {#single-sign-on}

Tuist предлагает единый вход как вариант аутентификации для повышения безопасности аккаунтов вашей организации.

Единый вход настраивается на вкладке **Аутентификация** в настройках организации. Поддерживаются Google Workspace, Okta, Microsoft Entra ID и пользовательские провайдеры [OAuth 2.0](https://oauth.net/2/).

Microsoft Entra ID — это провайдер OpenID Connect, который Tuist настраивает автоматически по идентификатору вашего каталога. Всё, что описано в этом руководстве для пользовательских провайдеров, включая проверку домена электронной почты для входа и политику подключения, применимо и к нему.

> [!NOTE]
> Единый вход управляет тем, как участники проходят аутентификацию и могут ли авторизованные пользователи присоединяться автоматически. <.localized_link href="/guides/integrations/authentication/scim">Предоставление доступа через System for Cross-domain Identity Management</.localized_link> определяет, может ли провайдер удостоверений создавать, обновлять и отключать участников организации. Для Okta большинство организаций настраивают оба механизма.

## Как работает доступ {#how-access-works}

Идентификатор провайдера, обнаружение при входе и подключение к организации — это отдельные аспекты:

- **Издатель провайдера:** Организация-провайдер или сервер авторизации, выполнивший аутентификацию пользователя. При поиске связанной учётной записи Tuist объединяет провайдера, издателя и стабильный идентификатор пользователя провайдера. Для Okta издатель задаётся доменом Okta. Для Microsoft Entra ID он выводится из идентификатора каталога (тенанта). Для пользовательского провайдера издателем выступает URL провайдера.
- **Домен электронной почты для входа:** Домен электронной почты, который Tuist использует для обнаружения провайдера Okta или пользовательского провайдера на общей странице входа. После проверки этот домен также определяет, какие адреса электронной почты можно доверять при привязке новых учётных записей и автоматическом подключении.
- **Политика подключения:** Определяет, нужен ли пользователю из доверенного домена приглашение или он может присоединиться автоматически.
- **Предоставление доступа:** Создаёт и управляет членством в организации независимо от процесса входа.

Издатель провайдера и домен электронной почты для входа часто различаются. Например, компания может использовать `example.com` для корпоративной почты, тогда как издателем провайдера будет `https://login.vendor.example.net`. В новых конфигурациях Okta и пользовательских провайдеров эти значения хранятся раздельно.

### Проверка домена электронной почты для входа {#verify-a-login-email-domain}

Конфигурации Okta и пользовательских провайдеров требуют проверенный домен электронной почты для входа, прежде чем они смогут создать новую учётную запись Tuist или связать существующую по адресу электронной почты. Участники всё ещё могут <.localized_link href="/guides/integrations/authentication/sso#link-an-existing-account">связать свою существующую учётную запись</.localized_link>, пока домен не проверен.

1. Введите домен электронной почты сотрудников, например `example.com`, в поле **Домен электронной почты для входа**.
2. Сохраните конфигурацию единого входа.
3. Добавьте текстовую запись, показанную Tuist, в конфигурацию [Domain Name System](https://www.cloudflare.com/learning/dns/dns-records/dns-txt-record/) вашего домена.
4. Вернитесь в настройки аутентификации и нажмите **Проверить домен**.

Проверенный домен электронной почты для входа может принадлежать только одной организации Tuist. Изменение домена сбрасывает его проверку и требует публикации новой текстовой записи. Автоматическое подключение остаётся приостановленным, пока домен не будет проверен.

Tuist ежедневно перепроверяет текстовую запись. Если запись перестаёт разрешаться, проверка не сбрасывается сразу: домен сохраняет статус ещё 14 дней, а в настройках аутентификации отображается **Срок проверки истекает** вместе с записью, которую нужно опубликовать заново. Публикация записи и повторная проверка снимают предупреждение. Если запись отсутствует более 14 дней, домен возвращается в непроверенное состояние, и обнаружение провайдера, связывание идентичностей и автоматическое подключение прекращаются до повторной проверки. Ошибка поиска по другим причинам не обновляет таймер и не сбрасывает проверку самостоятельно. Домены, проверенные до внедрения ежедневных повторных проверок, не перепроверяются.

Google Workspace не требует этого отдельного шага проверки в Tuist, поскольку Google передаёт проверенный домен Workspace как часть аутентифицированной идентичности.

### Выбор политики подключения {#choose-an-enrollment-policy}

Tuist поддерживает две политики подключения:

- **Только по приглашению:** Пользователю требуется приглашение в организацию. Для Okta и пользовательских провайдеров домен электронной почты для входа всё равно должен быть проверен, прежде чем провайдер сможет создать совершенно новую учётную запись Tuist. Приглашённый пользователь с существующей учётной записью Tuist сначала принимает приглашение, а затем связывает идентичность провайдера, как описано в разделе <.localized_link href="/guides/integrations/authentication/sso#link-an-existing-account">Связать существующую учётную запись Tuist</.localized_link>.
- **Автоматически:** Пользователь, чья аутентифицированная электронная почта совпадает с доверенным доменом, может создать или связать учётную запись и присоединиться к организации без приглашения. Конфигурации Google используют домен Workspace. Okta и пользовательские провайдеры требуют проверенный домен электронной почты для входа.

В конфигурациях Google по умолчанию включено автоматическое подключение. В новых конфигурациях Okta и пользовательских провайдеров по умолчанию используется подключение только по приглашению.

Настройка **Принудительный единый вход** не зависит от политики подключения. Доступ к защищённым страницам организации в браузере требует сессии, аутентифицированной через текущий провайдер и издателя организации (или через проверенный Google Workspace). Ранее связанная идентичность или аутентификация через провайдер другой организации недостаточна. Обычный вход в Tuist и доступ к другим аккаунтам остаются доступными; принудительный вход не предоставляет членство в организации. Анонимные публичные дашборды и временные гранты поддержки операторов сохраняют свои отдельные правила доступа. Страницы предварительного просмотра приложений применяют принудительный вход только к участникам организации, поэтому ссылки на превью, которыми поделились за пределами организации, продолжают работать для посетителей, которые уже могли их открывать.

Принудительный вход применяется везде, где сессия участника обращается к организации:

- **Дашборд**: страницы организации и инструменты, которые они предоставляют браузерным агентам через <.localized_link href="/guides/features/agentic-coding/mcp#webmcp">WebMCP</.localized_link>, требуют сессии, выполненной через провайдер организации.
- **Туист CLI, приложение Туист, клиенты MCP и справка по API**: вход в них создаёт учётные данные, которые действуют от имени участника во всех организациях, поэтому требуется сессия, выполненная через организацию, которая применяет принудительный единый вход. Туист сначала перенаправляет участника, вошедшего другим способом, к провайдеру и отказывает во входе с помощью электронной почты и пароля или через Apple. Каждый раз, когда один из этих клиентов обновляет свои учётные данные, Туист выполняет повторную проверку. Учётные данные, полученные через единый вход организации, продолжают обновляться; то же самое происходит с учётными данными, полученными другим способом участником, который ранее входил через провайдер организации. Любые другие учётные данные, например полученные с паролем до того, как организация включила принудительный единый вход, продолжают обновляться в течение четырёх недель с момента первого обновления в режиме принуждения; после этого клиент попросит участника войти снова. Вход через провайдера в этот период, на дашборде или с помощью `tuist auth login`, позволяет продолжить обновление.

Участник нескольких организаций, применяющих принудительный единый вход, не может войти в CLI, приложение или клиенты MCP, потому что одна сессия выполняется через одну организацию.

### Выберите роль для подключаемых участников {#choose-the-enrollment-role}

Участники, подключающиеся автоматически, получают <.localized_link href="/guides/server/accounts-and-projects#roles">роль</.localized_link>, указанную в настройке **Роль для подключаемых участников**; по умолчанию это `user`, если администратор не изменит её. Установка значения `viewer` открывает вход всем пользователям из каталога, не давая им возможности вносить изменения.

Эту настройку нельзя установить в значение `admin`; она применяется как к участникам, созданным через <.localized_link href="/guides/integrations/authentication/scim">SCIM</.localized_link> без назначенной роли, так и к тем, кто входит в систему, и никогда не перезаписывает роль, заданную администратором вручную.

### Связать существующий аккаунт Туист {#link-an-existing-account}

Связанная идентичность провайдера обеспечивает вход во весь аккаунт Туист, включая все другие организации, к которым принадлежит аккаунт. Для Okta и пользовательских провайдеров Туист автоматически связывает существующий аккаунт только если его адрес электронной почты находится в проверенном домене входа или если аккаунт был создан через SCIM-подключение организации.

Участники, чьи аккаунты не соответствуют условиям, связывают идентичность самостоятельно:

1. Войдите в Туист обычным для этого аккаунта способом.
2. Откройте Туист из провайдера идентичности, например через плитку приложения, или откройте один из проектов организации, если в ней включён принудительный единый вход.
3. Подтвердите организацию и аккаунт провайдера идентичности, которые показывает Туист, затем нажмите **Связать аккаунт**.

Если участник начинает процесс с единого входа, будучи неавторизованным, ему сначала предлагается войти, а затем Туист возвращается к подтверждению. Связывание не зависит от проверки домена, поэтому участники могут использовать единый вход до проверки домена.

### Существующие организации {#existing-organizations}

Все организации с Okta и пользовательскими провайдерами используют модель с проверенным доменом. Временный режим совместимости удалён.

Если ваш домен электронной почты для входа не проверен:

- Существующие связанные участники могут продолжать вход, и действующее принуждение к SSO по-прежнему применяется к участникам организации.
- Страница входа обнаруживает вашего провайдера только через существующее членство в организации.
- Автоматическое подключение приостановлено, и провайдер не может создавать новые аккаунты Туист, даже по приглашению.
- Несвязанные участники входят в свой существующий аккаунт Туист и подтверждают связь, как описано выше. Аккаунты, созданные через SCIM-подключение организации, всё ещё можно связать при первом входе через SSO.
- Новым зарегистрированным пользователям не обязательно использовать вашего провайдера только потому, что их адрес электронной почты использует ваш домен.

Существующие включённые настройки подключения и принуждения остаются сохранёнными и могут быть отключены. Администраторы могут редактировать конфигурацию, пока домен не проверен; включение любой из этих настроек требует проверки. Проверка возобновляет автоматическое подключение для совпадающих адресов электронной почты, когда эта настройка включена. Поведение Google Workspace не меняется.

Поле **Домен электронной почты для входа** может уже быть заполнено на основе участников вашей организации. Подтвердите значение, опубликуйте текстовую запись и нажмите **Проверить домен**. Оставьте запись опубликованной для ежедневных повторных проверок.

## Google Workspace {#google}

Единый вход Google Workspace аутентифицирует пользователей по домену Workspace. Администраторы могут разрешить подходящим пользователям подключаться автоматически или требовать приглашение.

> [!NOTE]
> **Предварительные требования**
>
> Вам нужна организация Google Workspace с проверенным доменом. Вы также должны быть аутентифицированы в Google, используя электронную почту, привязанную к настраиваемому домену.

### Настройка {#google-setup}

1. Перейдите на вкладку настроек **Аутентификация** вашей организации.
2. Включите единый вход.
3. Выберите **Google** в качестве провайдера.
4. Введите ваш домен Google Workspace, например `example.com`.
5. Выберите **Автоматическое подключение** или подключение только по приглашению. Для Google автоматическое подключение включено по умолчанию.
6. При необходимости включите **Принудительный единый вход** после тестирования процесса входа.
7. Нажмите **Сохранить изменения**.

## Okta {#okta}

Okta использует [OpenID Connect](https://openid.net/developers/how-connect-works/) для аутентификации участников. Домен Okta определяет издателя провайдера; отдельно проверенный домен электронной почты для входа управляет обнаружением, связыванием новых аккаунтов и подключением.

Если вы также хотите, чтобы Okta автоматически создавал, обновлял или удалял участников, настройте <.localized_link href="/guides/integrations/authentication/scim#okta">подключение Okta System for Cross-domain Identity Management</.localized_link> после того, как единый вход начнёт работать.

### Шаг 1: Создайте приложение Okta {#okta-step-1}

1. В панели администратора Okta перейдите в раздел **Applications > Applications > Create App Integration**.
2. Выберите **OpenID Connect** и **Web Application**.
3. Задайте имя приложения, например `Tuist`. При желании загрузите [логотип Tuist](https://tuist.dev/images/tuist_dashboard.png).
4. Установите **URI перенаправления при входе** равным значению, указанному на странице настроек аутентификации, например `https://tuist.dev/users/auth/okta/callback`.
5. В разделе **Assignments** выберите нужный контроль доступа и сохраните изменения.
6. Скопируйте **Client ID** и **Client Secret** из общих настроек приложения. Запишите ваш **домен Okta**, например `your-company.okta.com`.
7. При желании, чтобы разрешить вход из панели управления Okta, нажмите **Edit** в разделе General Settings, измените **Login initiated by** на **Either Okta or App**, выберите **Display application icon to users** и установите **Initiate login URI** равным значению, указанному на странице настроек аутентификации.

### Шаг 2: Настройте Tuist {#okta-step-2}

1. Перейдите на вкладку настроек **Аутентификация** вашей организации.
2. Включите единый вход.
3. Выберите **Okta** в качестве провайдера.
4. Введите **домен Okta**, **Client ID** и **Client Secret**.
5. Введите домен электронной почты сотрудников в поле **Домен электронной почты для входа**. Например, домену Okta `your-company.okta.com` может соответствовать домен электронной почты для входа `example.com`.
6. Нажмите **Сохранить изменения**.
7. Добавьте текстовую запись, показанную Tuist, к домену электронной почты для входа, затем нажмите **Проверить домен**.
8. Выберите, нужно ли пользователям приглашение или они могут подключаться автоматически, затем снова сохраните конфигурацию.
9. При необходимости включите **Принудительный единый вход** после тестирования процесса входа.

### Шаг 3: Назначьте пользователей приложению Okta {#okta-step-3}

Назначьте пользователей или группы, которым должно быть разрешено проходить аутентификацию через приложение Okta.

Назначение предоставляет доступ к процессу входа, но членство в организации по-прежнему определяется политикой подключения. Если те же пользователи предоставляются через System for Cross-domain Identity Management, Tuist связывает идентификатор Okta с аккаунтом, созданным SCIM, при первом входе пользователя. Участник, чей аккаунт существовал до добавления его через SCIM, связывается, когда его адрес электронной почты находится в проверенном домене электронной почты для входа, или после подтверждения связи из своего вошедшего в систему аккаунта.

## Microsoft Entra ID {#microsoft-entra-id}

Microsoft Entra ID аутентифицирует участников через [OpenID Connect](https://openid.net/developers/how-connect-works/). Tuist получает конечные точки авторизации, токенов и информации о пользователе из идентификатора вашего каталога (арендатора), поэтому вы вводите только это значение вместе с учетными данными приложения.

Если вы также хотите, чтобы Entra ID автоматически создавал, обновлял или удалял участников, настройте <.localized_link href="/guides/integrations/authentication/scim#microsoft-entra-id">подключение Microsoft Entra ID System for Cross-domain Identity Management</.localized_link> после того, как единый вход начнёт работать.

### Шаг 1: Зарегистрируйте приложение Entra {#entra-step-1}

1. В [центре администрирования Microsoft Entra](https://entra.microsoft.com) перейдите в раздел **Identity > Applications > App registrations > New registration**.
2. Задайте имя приложения, например `Tuist`.
3. В разделе **Redirect URI** выберите платформу **Web** и введите значение, указанное на странице настроек аутентификации, например `https://tuist.dev/users/auth/oauth2/callback`.
4. Зарегистрируйте приложение, затем скопируйте **Directory (tenant) ID** и **Application (client) ID** с его обзорной страницы.
5. Перейдите в раздел **Certificates & secrets > New client secret**, создайте секрет и скопируйте его **Value**. Microsoft показывает значение только один раз, и у каждого клиентского секрета есть срок действия, поэтому запишите, когда его нужно будет обновить.
6. Перейдите в раздел **API permissions** и убедитесь, что делегированные разрешения Microsoft Graph `openid`, `profile` и `email` предоставлены.
7. При желании, чтобы позволить участникам начинать процесс входа с портала My Apps, установите **Home page URL** в разделе **Branding & properties** равным значению, указанному на странице настроек аутентификации.

### Шаг 2: Настройте Tuist {#entra-step-2}

1. Перейдите на вкладку настроек **Аутентификация** вашей организации.
2. Включите единый вход.
3. Выберите **Microsoft Entra ID** в качестве провайдера.
4. Введите **Directory (tenant) ID**, **Client ID** и **Client Secret**.
5. Введите домен электронной почты сотрудников в поле **Домен электронной почты для входа**. Например, каталогу, пользователи которого входят в систему как `first.last@example.com`, соответствует домен электронной почты для входа `example.com`.
6. Нажмите **Сохранить изменения**.
7. Добавьте текстовую запись, показанную Tuist, к домену электронной почты для входа, затем нажмите **Проверить домен**.
8. Выберите, нужно ли пользователям приглашение или они могут подключаться автоматически, затем снова сохраните конфигурацию.
9. При необходимости включите **Принудительный единый вход** после тестирования процесса входа.

### Шаг 3: Назначьте пользователей приложению Entra {#entra-step-3}

Назначьте пользователей или группы, которым разрешена аутентификация. Если приложение настроено на требование назначения, войти могут только назначенные пользователи.

Назначение предоставляет доступ к процессу входа, но членство в организации по-прежнему регулируется политикой подключения. Если те же пользователи предоставляются через System for Cross-domain Identity Management, Tuist связывает идентификатор Entra с учетной записью, созданной SCIM при первом входе пользователя. Учетная запись участника, существовавшая до добавления его через SCIM, связывается, когда его адрес электронной почты находится в проверенном домене электронной почты для входа, или после того, как он подтвердит связь из своей активной учетной записи.

### Требования к утверждению email {#entra-email-claim}

Tuist считывает профиль аутентифицированного пользователя из конечной точки пользовательской информации Microsoft Graph, которая возвращает адрес электронной почты только если он доступен. Пользователь каталога, у которого атрибут `mail` пуст, не может войти в систему, потому что у Tuist нет адреса для сопоставления с доменом электронной почты для входа.

Убедитесь, что у назначаемых участников в каталоге заполнен адрес электронной почты, прежде чем внедрять единый вход. Наиболее частый случай отсутствия этого атрибута — пользователи, синхронизированные из локального Active Directory без почтового ящика.

### Условный доступ и многофакторная аутентификация {#entra-conditional-access}

Политики условного доступа, многофакторная аутентификация и политики риска входа применяются к приложению Tuist так же, как и к любому другому приложению Entra, поскольку они оцениваются во время запроса авторизации. Дополнительная настройка Tuist не требуется.

## Пользовательский провайдер OAuth 2.0 {#custom-oauth-2-provider}

Пользовательский провайдер OAuth 2.0 позволяет организации использовать службу идентификации, отличную от Google Workspace или Okta. Конечная точка пользовательской информации провайдера должна возвращать стабильный идентификатор пользователя и адрес электронной почты.

1. В провайдере создайте веб-приложение OAuth 2.0.
2. Установите **Sign-in redirect URI** и необязательный **Initiate login URI** равными значениям, указанным в настройках аутентификации Tuist.
3. В Tuist включите единый вход и выберите **OAuth2**.
4. Введите URL провайдера, конечную точку авторизации, конечную точку токена, конечную точку пользовательской информации, идентификатор клиента и секрет клиента.
5. Введите и сохраните **Домен электронной почты для входа**. Это домен электронной почты сотрудников, а не URL провайдера.
6. Добавьте текстовую запись, показанную Tuist, к домену электронной почты для входа, затем нажмите **Проверить домен**.
7. Выберите подключение только по приглашению или автоматическое подключение и сохраните конфигурацию.
8. Протестируйте вход перед необязательным включением **Принудительного единого входа**.

URL провайдера ограничивает идентификаторы выдающим провайдером. Проверенный домен электронной почты для входа определяет, каким адресам электронной почты Tuist может доверять при связывании или подключении пользователей.

## Конфигурация командной строки {#command-line-configuration}

Интерфейс командной строки может настроить Google Workspace или Okta и выбрать политику подключения. Например:

```bash
tuist organization update sso example \
  --provider okta \
  --organization-id your-company.okta.com \
  --enrollment-policy invitation-only
```

Microsoft Entra ID и пользовательские провайдеры настраиваются через настройки аутентификации организации, а не через командную строку.

Значение `--organization-id` идентифицирует организацию провайдера. Это не домен электронной почты для входа. Добавьте и проверьте домен электронной почты для входа в настройках аутентификации организации, прежде чем подключать новых пользователей Okta.

## Устранение неполадок {#troubleshooting}

### Существующие участники могут войти, но новые пользователи не могут {#existing-members-can-sign-in-but-new-users-cannot}

Для конфигураций Okta и пользовательских провайдеров убедитесь, что домен электронной почты для входа проверен. Затем либо пригласите пользователя, либо включите автоматическое подключение.

### Единый вход требует сначала войти в систему {#single-sign-on-asks-you-to-log-in-first}

Адрес электронной почты вашей учетной записи Tuist не входит в проверенный домен электронной почты для входа организации, или домен еще не проверен, поэтому Tuist не связывает идентификатор провайдера автоматически. Войдите в систему обычным способом и подтвердите связь, как описано в разделе <.localized_link href="/guides/integrations/authentication/sso#link-an-existing-account">Связать существующую учетную запись Tuist</.localized_link>.
### Tuist не может найти организацию для адреса электронной почты {#tuist-cannot-find-an-organization-for-an-email-address}

Убедитесь, что пользователь ввел ожидаемый адрес электронной почты сотрудника и что его домен точно совпадает с проверенным доменом электронной почты для входа. Существующих участников также можно обнаружить через их текущее членство в организации.

### Проверка домена все еще ожидает выполнения {#domain-verification-remains-pending}

Убедитесь, что имя и значение текстовой записи точно совпадают со значениями, показанными в Tuist. Изменения в системе доменных имен (DNS) могут распространяться некоторое время, поэтому повторите проверку после того, как запись станет общедоступной.

### Вход прекратился после смены провайдера {#sign-in-stopped-after-changing-the-provider}

Подтвердите новую конфигурацию провайдера, проверьте домен электронной почты для входа и протестируйте процесс входа перед включением принудительного режима.
