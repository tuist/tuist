# რა არის ბილდის ქეში? {#what-is-a-build-cache}

ბილდის ქეში ინახავს ცალკეული ბილდის ეტაპების შედეგებს, როგორიცაა კომპილირებული ობიექტური ფაილები, მოდულები, ბიბლიოთეკები ან ტესტების შედეგები, გასაღებზე, რომელიც გამოითვლება ყველაფრის მიხედვით, რაც მათ წარმოქმნაში მონაწილეობდა: საწყისი ფაილები, კომპილატორის დროშები, დამოკიდებულებები, გარემო და ხელსაწყოების ვერსია. როდესაც მოგვიანებით ბილდს სჭირდება ეტაპი, რომლის შემავალი მონაცემები იმავე გასაღებს წარმოქმნიან, ბილდის სისტემა იყენებს შენახულ შედეგს ეტაპის ხელახლა გაშვების ნაცვლად. **ლოკალური ბილდის ქეში** ერთ მანქანაზეა განთავსებული და აჩქარებს ამ მანქანის მომდევნო ბილდებს. **დაშორებული ბილდის ქეში** არის საერთო სერვერი, საიდანაც ბევრი მანქანა კითხულობს და სადაც წერს, რათა CI-ის სამუშაომ, თანამშრომელმა ან კოდირების აგენტმა შეძლოს უკვე აგებული შედეგების ხელახლა გამოყენება.

## ბილდის ქეში, ინკრემენტული ბილდი და CI ქეში {#build-cache-incremental-build-and-ci-cache}

სამ იდეას ხშირად „ქეშს“ უწოდებენ და ისინი განსხვავებულად მუშაობენ:

- **ინკრემენტული ბილდები** ხელახლა იყენებენ შედეგებს, რომლებიც უკვე არის თქვენს ბილდის დირექტორიაში და ხელახლა აგებენ მხოლოდ იმას, რაც ბოლო ბილდის შემდეგ შეიცვალა ამ დირექტორიაში. ისინი ჩვეულებრივ ეყრდნობიან ფაილების დროის შტამპებს ან დამოკიდებულებების გრაფს, რომელიც ბილდის პროდუქტებთან ერთად ინახება. განშტოების შეცვლა, ჩეკაუტის გადატანა ან ახალი მანქანიდან დაწყება ამ მდგომარეობას კარგავს.
- **ბილდის ქეში** ეძებს შედეგებს მათი შემავალი მონაცემების შინაარსის მიხედვით და არა იმის მიხედვით, რა აიგო ბოლოს იმავე დირექტორიაში. ეს საშუალებას აძლევს შედეგები ხელახლა გამოყენებულ იქნას განშტოებებს, ჩეკაუტებსა და მანქანებს შორის, სანამ შემავალი მონაცემები ემთხვევა.
- **CI დირექტორიის ქეშირება** (მაგალითად, `actions/cache` GitHub Actions-ზე) ინახავს დირექტორიას სამუშაოს ბოლოს და აღადგენს მას მომდევნოს დასაწყისში, თქვენს მიერ შერჩეული გასაღებით, როგორიცაა lockfile-ის ჰეში. ეს არის ფაილების გადაცემა და არა ბილდის ქეში: ბილდის სისტემა კვლავ თავად წყვეტს, რა ააგოს ხელახლა, და აღდგენილი დირექტორია შეიძლება ნაწილობრივ ან მთლიანად მოძველებული იყოს.

დამოკიდებულებების ქეშები, როგორიცაა ჩამოტვირთული პაკეტები ან Gradle ან Swift პაკეტის ქეში, განსხვავებულია: ისინი ინახავენ ქსელური მოთხოვნის შედეგს და არა კომპილაციას.

## როგორ მუშაობს ბილდის ქეში {#how-a-build-cache-works}

ბილდის სისტემები, რომლებიც მხარს უჭერენ ქეშირებას, ბილდს ყოფენ ეტაპებად (Bazel მათ actions-ს უწოდებს, Gradle კი tasks-ს) და თითოეულისთვის ერთსა და იმავეს აკეთებს:

1. **გამოთვალეთ ქეშის გასაღები.** ბილდის სისტემა აკეთებს ჰეშირებას ყველა შემავალი მონაცემისა, რომელსაც შეუძლია შედეგზე გავლენა მოახდინოს: შემავალი ფაილების შინაარსი, ბრძანების სტრიქონი ან ამოცანის კონფიგურაცია, შესაბამისი გარემოს ცვლადები და ხელსაწყოები.
2. **მოძებნეთ გასაღები.** ის ჯერ ამოწმებს ლოკალურ ქეშს და, თუ კონფიგურირებულია, დაშორებულ ქეშსაც.
3. **მოხვედრა ან აცდენა.** მოხვედრის შემთხვევაში, ის ჩამოტვირთავს ან აკოპირებს შენახულ შედეგებს და ტოვებს ეტაპს. აცდენის შემთხვევაში, ის ასრულებს ეტაპს და, თუ ნებადართულია, ტვირთავს შედეგებს ამ გასაღებით.

ქეშების უმრავლესობა ინახავს შედეგებს **შინაარსით მიმართვად საცავში** (CAS), სადაც თითოეული ბლობი ინახება მისი საკუთარი შინაარსის ჰეშის ქვეშ, პლუს ცალკე ინდექსი ქეშის გასაღებიდან მათ მიერ წარმოქმნილ შედეგებამდე. იდენტური ფაილები ინახება ერთხელ და კლიენტს შეუძლია დაადასტუროს ჩამოტვირთული.

მოდელს აქვს ერთი მკაცრი მოთხოვნა: გასაღებმა უნდა მოიცვას ყველა შემავალი მონაცემი, რომელიც ცვლის შედეგს. თუ ეტაპი კითხულობს შემავალ მონაცემს, რომლის შესახებაც ბილდის სისტემამ არ იცის, როგორიცაა გამოუცხადებელი ფაილი, გარემოს ცვლადი, მიმდინარე დრო ან მანქანაზე დაყენებული ხელსაწყო, ქეშმა შეიძლება დააბრუნოს შედეგი, რომელიც არ ემთხვევა მიმდინარე შემავალ მონაცემებს. ბილდის სისტემები ეტაპებს, რომლებიც მხოლოდ გამოცხადებულ შემავალ მონაცემებზეა დამოკიდებული, **ჰერმეტულს** უწოდებენ. საპირისპირო პრობლემა უფრო ხშირია და ნაკლებად საშიში: გასაღები, რომელიც შეიცავს რაიმე არარელევანტურს, როგორიცაა აბსოლუტური გზა ან დროის შტამპი, ყოველ მანქანაზე განსხვავებულ გასაღებს წარმოქმნის, ამიტომ ქეში ვერასდროს ხვდება.

## როგორ მუშაობს ბილდის ქეშები ბილდის სისტემების მიხედვით {#how-it-works-per-build-system}

### Gradle ბილდის ქეში {#gradle}

[Gradle ბილდის ქეში](https://docs.gradle.org/current/userguide/build_cache.html) ინახავს ქეშირებადი ამოცანების შედეგებს, როგორიცაა Java და Kotlin კომპილაცია და ტესტების შესრულება, გასაღებული ამოცანის ტიპით, იმპლემენტაციით, შემავალი თვისებებით და ნორმალიზებული შემავალი ფაილებით. ის გამორთულია ნაგულისხმევად. ჩართეთ იგი `org.gradle.caching=true`-ით `gradle.properties`-ში ან `--build-cache`-ით ერთი ბილდისთვის.

- **ლოკალური.** ჩაშენებული ლოკალური ქეში არის დირექტორია Gradle-ის მომხმარებლის საწყისში (`~/.gradle` ნაგულისხმევად). ის ჩართულია, როგორც კი ბილდის ქეში ჩართულია და Gradle პერიოდულად შლის ჩანაწერებს, რომლებიც ბოლო დროს არ გამოუყენებიათ.
- **დაშორებული.** დაშორებული ქეში კონფიგურირებულია `settings.gradle(.kts)`-ში, მაგალითად, `HttpBuildCache`-ით. Gradle ჩამოტვირთავს შედეგებს დაშორებული ქეშიდან ლოკალური აცდენის შემთხვევაში და ინახავს მათ ლოკალურად მომდევნოსთვის. დაშორებული ქეში ნაგულისხმევად არ იღებს ატვირთვებს; გავრცელებული კონფიგურაცია საშუალებას აძლევს CI-ს ატვირთვას (`isPush = true`, როდესაც CI-ში მუშაობს) და დეველოპერის მანქანებს მხოლოდ კითხვას.

Gradle ქეშიდან აღდგენილ ამოცანას ანგარიშგებს როგორც `FROM-CACHE`, რაც განსხვავდება `UP-TO-DATE`-ისგან: up-to-date ნიშნავს, რომ Gradle-ის ინკრემენტულმა ბილდმა ამოცანის შედეგები უკვე ადგილზე იპოვა, ქეშთან მიმართვის გარეშე. კონფიგურაციის ქეში არის მესამე, ცალკე ფუნქცია, რომელიც ქეშირებს კონფიგურაციის ფაზის შედეგს და არა ამოცანის შედეგებს.

### Bazel დაშორებული ქეში {#bazel}

Bazel ქეშირებს ყოველ action-ს. მისი action ქეში ასახავს action-ის გასაღებს, მისი ბრძანების სტრიქონის, გარემოს და შემავალი ფაილების დაიჯესტს, action-ის შედეგებზე, ხოლო თავად შედეგები შინაარსით მიმართვად საცავში ინახება.

- **ლოკალური.** Bazel ინახავს action ქეშს და ბილდის შედეგებს მის output base-ში, რაც სწრაფ ინკრემენტულ ბილდებს გაძლევთ ერთ workspace-ში. `--disk_cache=<path>` ამატებს დისკის ქეშს, რომელიც გაზიარებულია workspace-ებსა და განშტოებებს შორის იმავე მანქანაზე.
- **დაშორებული.** `--remote_cache=grpcs://…` (ან `https://…`) მიმართავს Bazel-ს დაშორებულ ქეშზე, რომელიც ახორციელებს [Remote Execution API](https://github.com/bazelbuild/remote-apis)-ს ან ჩვეულებრივ HTTP ქეშს. `--remote_upload_local_results=false` ხდის მანქანას მხოლოდ წასაკითხად, რითიც ბევრი გუნდი იცავს დეველოპერის მანქანებს საერთო ქეშში ჩაწერისგან. `--remote_download_minimal` ან `--remote_download_toplevel` („build without the bytes“) თავს არიდებს შუალედური შედეგების ჩამოტვირთვას, რომლებიც ლოკალურ ბილდს არასდროს სჭირდება.

Bazel ასევე ქეშირებს ტესტების შედეგებს: ტესტი, რომლის შემავალი მონაცემები არ შეცვლილა, ანგარიშგდება როგორც `(cached) PASSED` გაშვების გარეშე. დაშორებული ქეში არ არის იგივე, რაც დაშორებული შესრულება, სადაც action-ები ასევე მუშაობენ დაშორებულ მანქანებზე; ქეში მხოლოდ შედეგებს ინახავს.

### რა არის Xcode ქეშები? {#xcode}

Xcode იყენებს რამდენიმე ქეშსა და დირექტორიას, რომელთა ერთმანეთში არევა ადვილია. ისინი, რომლებიც გავლენას ახდენენ ბილდის დროზე, არის:

- **DerivedData** (`~/Library/Developer/Xcode/DerivedData/<Project>-<hash>/`) ინახავს თითოეული პროექტის ბილდის პროდუქტებს, შუალედურ ფაილებს, ინდექსს, ლოგებს და გაწყობილ Swift პაკეტებს. ეს არის მდგომარეობა, რომელსაც ინკრემენტული ბილდები ხელახლა იყენებენ. მისი წაშლა უსაფრთხოა, მაგრამ ამ პროექტის შემდეგი ბილდი სრულად თავიდან აშენდება და ინდექსაცია და პაკეტების გარჩევა კვლავ ჩატარდება.
- **Clang-ის მოდულის ქეში** (`~/Library/Developer/Xcode/DerivedData/ModuleCache.noindex/`) ინახავს წინასწარ კომპილირებულ Clang მოდულებს (`.pcm` ფაილები) იმპორტირებული C და Objective-C მოდულებისა და SDK ჩარჩოებისთვის, რომლებიც გაზიარებულია პროექტებს შორის. ცალსახად აშენებული მოდულების ჩართვისას, Xcode ამის ნაცვლად მოდულებს აშენებს როგორც ჩვეულებრივ ბილდის ამოცანებს და ინახავს მათ თითოეული პროექტის შუალედურ ფაილებთან ერთად. მისი წაშლა უსაფრთხოა; მოდულები საჭიროებისამებრ თავიდან აშენდება.
- **კომპილაციის ქეში** (Xcode 26 და ზემოთ, `CompilationCache.noindex` DerivedData-ში ნაგულისხმევად, კონფიგურირებადი `COMPILATION_CACHE_CAS_PATH`-ით) ინახავს შინაარსზე დაფუძნებულ კომპილაციის შედეგებს Swift, C და Objective-C-ისთვის, როდესაც `COMPILATION_CACHE_ENABLE_CACHING = YES`. მისი წაშლა უსაფრთხოა; კომპილაციები, რომლებიც შესაძლებელი იყო განმეორებით შესრულება, კვლავ შესრულდება.
- **Swift Package Manager-ის ქეში** (`~/Library/Caches/org.swift.swiftpm/`) ინახავს ჩამოტვირთულ პაკეტების რეპოზიტორიებს და მანიფესტებს, რომლებიც გაზიარებულია პროექტებს შორის. მისი წაშლა უსაფრთხოა; პაკეტები კვლავ ჩამოიტვირთება.

სხვა დიდი დირექტორიები `~/Library/Developer`-ის ქვეშ არ არის ბილდის ქეშები, მაგრამ ხშირად ჩნდებიან დისკის სივრცის გასუფთავებისას: `Xcode/Archives` ინახავს დაარქივებულ აპლიკაციის ბილდებს და მათ დებაგის სიმბოლოებს (შეინახეთ ისინი, რომლებიც შეიძლება დაგჭირდეთ კრეშების სიმბოლიზაციისთვის), `Xcode/iOS DeviceSupport` ინახავს სიმბოლოებს მიერთებული მოწყობილობების OS ვერსიებისთვის და `CoreSimulator/Devices` ინახავს სიმულატორებს და მათ მონაცემებს (`xcrun simctl delete unavailable` შლის სიმულატორებს იმ runtime-ებისთვის, რომლებიც აღარ არის დაინსტალირებული).

DerivedData არის Xcode-ის ინკრემენტული ბილდის მდგომარეობა და არა შინაარსზე დაფუძნებული ქეში: ის მიბმულია პროექტის მდებარეობასთან დისკზე და ფაილის დროის შტამპებთან. DerivedData-ის აღდგენა CI ქეშიდან სხვა გზაზე, ან ახალი checkout-ის შემდეგ, როდესაც ყველა ფაილის ცვლილების დრო იცვლება, ხშირად მაინც სრულ გადააშენებამდე მიდის.

**კომპილაციის ქეში**, რომელიც Xcode 26-ში შემოვიდა, არის Xcode-ის ბილდის ქეში ამ გვერდის გაგებით. ის ინახავს კომპილაციის შედეგებს მათი შემავალი მონაცემების შინაარსის მიხედვით და ანახლებს მათ ქეშში მოხვედრისას, რითიც შედეგები ნარჩუნდება განშტოების შეცვლისას და ბილდის პროდუქტების გასუფთავებისას. ის ქეშირებს კომპილაციას და არა ყველა ბილდის ეტაპს: დაკავშირება, რესურსების დამუშავება და სკრიპტის ფაზები კვლავ სრულდება. ნაგულისხმევად საცავი ლოკალურია ერთ მანქანაზე და მდებარეობს DerivedData-ში, ამიტომ DerivedData-ის სრულად წაშლა ასევე შლის მას; მხოლოდ პროექტის ბილდის პროდუქტების წაშლა ინარჩუნებს მას. Xcode-ს ასევე შეუძლია კომპილაციის ქეშის დაკავშირება დაშორებულ ქეშის სერვისთან პლაგინის მეშვეობით (`COMPILATION_CACHE_ENABLE_PLUGIN` და `COMPILATION_CACHE_REMOTE_SERVICE_PATH`), რაც მას საერთო დაშორებულ ქეშად აქცევს.

კომპილაციის ქეშამდე, Xcode პროექტები მუშაობას მანქანებს შორის ძირითადად ხელახლა იყენებდნენ **ბინარული ქეშირებით** მთლიანი მოდულების: დამოკიდებულებების აშენებით როგორც წინასწარ აშენებული ჩარჩოების ან XCFramework-ების და მათი დაკავშირებით წყაროების კომპილაციის ნაცვლად. ეს მუშაობს მოდულის დონეზე და არა კომპილაციის, და ცვლის პროექტის აშენების წესს.

## ლატენტობა, ბლობის ზომა და ბლობების რაოდენობა {#latency-blob-size-and-blob-count}

დაშორებული ქეშის მოხვედრა უფასო არ არის. შედეგის გამოტანა ჯდება ფიქსირებულ დაყოვნებას ყოველი მოთხოვნისთვის, რომელიც უნდა დაელოდოს წინა ერთს, პლუს ბაიტების გადატანის დრო:

**დრო ≈ R × L + S / B**

სადაც *R* არის იმ round trip-ების რაოდენობა, რომლებიც არ შეიძლება გადაფარვას, *L* არის round-trip ლატენტობა ქეშამდე, *S* არის გადატანილი ბაიტების რაოდენობა და *B* არის გამტარუნარიანობა. რომელი ტერმინი დომინირებს, დამოკიდებულია იმაზე, თუ როგორ ყოფს ბილდის სისტემა მუშაობას ბლობებად:

- **ცოტა, დიდი ბლობები შეზღუდულია გამტარუნარიანობით.** ქეშები, რომლებიც ინახავენ უხეშ შედეგებს, როგორიცაა Gradle ამოცანის შეკუმშული შედეგები ან წინასწარ აშენებული ჩარჩო ბინარული მოდულის ქეშში, აკეთებენ ნაკლებ მოთხოვნას, რომელთაგან თითოეული მეგაბაიტებს გადააადგილებს. 200 MB შედეგების ნაკრები იღებს დაახლოებით 16 წამს 100 Mbit/s-ზე და 2 წამზე ნაკლებს 1 Gbit/s-ზე, ხოლო რამდენიმე დამატებითი მილიწამი ლატენტობისა თითქმის არაფერს ცვლის.
- **ბევრი პატარა ბლობი შეზღუდულია ლატენტობით.** წვრილმარცვლოვანი ქეშები, როგორიცაა Bazel-ის თითოეული action-ის ქეში და Xcode-ის კომპილაციის ქეში, აკეთებენ ათასობით მოთხოვნას რამდენიმე კილობაიტიანი ბლობებისთვის, ბევრი მათგანი მხოლოდ იმის შესამოწმებლად, არსებობს თუ არა გასაღები. 2,000 ძიებით, 8 ერთდროულად ფრენაში და 40 ms ლატენტობით, ბილდი ელოდება დაახლოებით 10 წამს მხოლოდ round trip-ებზე, ბლობების სიდიდის მიუხედავად. 2 ms ლატენტობით, იგივე ძიებები იღებენ დაახლოებით ნახევარ წამს. მეტი გამტარუნარიანობა აქ არ ეხმარება; უფრო ახლოს მყოფი ქეში კი ეხმარება.
- **გამოტოვებებიც ჯდება round trip-ს.** ყოველი გამოტოვებული ძიება ამატებს ლატენტობას მუშაობის დაზოგვის გარეშე. დაშორებულ ქეშს დაბალი მოხვედრის მაჩვენებლით შეუძლია ბილდი უფრო ნელი გახადოს, ვიდრე საერთოდ არ ქონდეს დაშორებული ქეში.
- **მოცულობა ორივეს ამრავლებს.** ბლობების რაოდენობა იზრდება პროექტის სტრუქტურასთან ერთად: ბევრი პატარა მოდულის ან target-ის გრაფი წარმოქმნის უფრო მეტ, უფრო პატარა შედეგს, ვიდრე რამდენიმე დიდი. პროექტის გაყოფა აუმჯობესებს პარალელიზმს და გაუქმებას, მაგრამ ბილდს უფრო მგრძნობიარეს ხდის ქეშის ლატენტობის მიმართ.

მოხვედრა მხოლოდ მაშინ ღირს, როდესაც შედეგის გამოტანა უფრო სწრაფია, ვიდრე მისი ხელახლა გამოთვლა, და ეს შედარება იცვლება მანძილთან ერთად. კომპილაცია, რომელიც ლოკალურად 50 ms-ს იღებს, არის კარგი მოხვედრა იმავე ქსელში მყოფი ქეშიდან და ცუდი მოხვედრა სხვა კონტინენტზე მყოფი ქეშიდან. ამიტომ, დაშორებული ქეშების ბერკეტები ძირითადად ეხება ლატენტობას და მოთხოვნების რაოდენობას და არა უბრალოდ გამტარუნარიანობას:

- **მოათავსეთ ქეში ახლოს იქ, სადაც ბილდები სრულდება**, იმავე რეგიონში ან ქსელში, სადაც CI runner-ები, და რაც შეიძლება ახლოს დეველოპერებთან.
- **გადაფარეთ მოთხოვნები.** Bazel-ის Remote Execution API აჯგუფებს არსებობის შემოწმებებს (`FindMissingBlobs`) და პატარა წაკითხვებს, და `--remote_max_connections` ზღუდავს კონკურენტულობას. Xcode-ის `COMPILATION_CACHE_ENABLE_DETACHED_KEY_QUERIES` აწარმოებს კომპილაციის ქეშის ძიებებს ბილდის დანარჩენ ნაწილთან ერთად და არა მის შესრულების ზოლებზე. HTTP/2 ახდენს ბევრი მოთხოვნის მულტიპლექსირებას ერთი კავშირის მეშვეობით.
- **ჩამოტვირთეთ ნაკლები.** Bazel-ის `--remote_download_minimal` ტოვებს შუალედურ შედეგებს, და ლოკალური ქეშის ფენა, როგორიცაა Bazel-ის `--disk_cache` ან Gradle-ის ლოკალური ბილდის ქეში, ემსახურება განმეორებით მოხვედრებს ქსელის მოთხოვნის გარეშე.
- **შეკუმშეთ დიდი ბლობები.** Bazel-ის `--remote_cache_compression` იყენებს zstd-ს, როდესაც ქეში მას მხარდაჭერს, რაც ეხმარება გამტარუნარიანობით შეზღუდულ გადაცემებს და ცოტას აკეთებს ლატენტობით შეზღუდულებისთვის.

## ხშირი შეცდომები {#common-pitfalls}

- **გამოუცხადებელი შეყვანები.** ნაბიჯი კითხულობს ფაილს, გარემოს ცვლადს ან ინსტრუმენტს, რომელიც არ არის მისი გასაღების ნაწილი. ქეშმა შესაძლოა დააბრუნოს სხვადასხვა შეყვანებით აგებული შედეგები. Gradle-ში გამოაცხადეთ ყველა custom task-ის შეყვანა; Bazel-ში შეინარჩუნეთ actions-ების ჰერმეტულობა და განიხილეთ `--incompatible_strict_action_env`, რათა host-ის `PATH` არ გაჟონოს.
- **მანქანაზე დამოკიდებული გასაღებები.** აბსოლუტური ბილიკები, მომხმარებლის სახელები და ბილდის დროის შტამპები, ჩაშენებული შეყვანებსა ან შედეგებში, იწვევს გასაღებების განსხვავებას მანქანებს შორის, ამიტომ remote cache ვერასდროს ხვდება. Gradle-ის ბილიკის მგრძნობელობა, Bazel-ის ფარდობითი შესრულების ბილიკები და Xcode-ში Clang და Swift პრეფიქსის ასახვის პარამეტრები სწორედ ამ განსხვავებების აღმოსაფხვრელად არსებობს.
- **ცვალებადი შეყვანები გრაფის ფესვთან.** ბილდის ნომრის, commit hash-ის ან თარიღის ჩაშტამპვა მოდულში, რომელზეც ყველაფერია დამოკიდებული, ყოველ ბილდზე აუქმებს მასზე ზემოთ მყოფ ყველაფერს. ჩაამატეთ ცვალებადი მნიშვნელობები რაც შეიძლება გვიან, იდეალურ შემთხვევაში მხოლოდ release ბილდებში.
- **ინსტრუმენტების ჯაჭვის შეუსაბამობა.** კომპილატორის, JDK-ის ან Xcode-ის სხვადასხვა ვერსიები წარმოქმნიან განსხვავებულ გასაღებებს. ეს სწორი ქცევაა, მაგრამ შერეული ვერსიების მქონე ფლოტი ეფექტურად ყოფს ქეშს.
- **მოწამლული ან არასანდო ჩაწერები.** დეველოპერის მანქანა, რომელსაც აქვს დაუკომიტებული ცვლილებები ან არაჰერმეტული კონფიგურაცია, შესაძლოა ატვირთოს შედეგები, რომლებსაც სხვები შემდეგ ხელახლა იყენებენ. ბევრი გუნდი remote cache-ში ჩაწერას მხოლოდ სანდო branch-ებზე CI-ს აძლევს და ყველა სხვა მანქანას მხოლოდ წაკითხვის უფლებას ანიჭებს. არასანდო pull request-ების ბილდებმა არ უნდა ჩაწერონ ქეშში, რომელსაც სანდო ბილდები კითხულობენ.
- **გადაცემის ღირებულების იგნორირება.** ნაბიჯს, რომლის შესრულებას 50 მილიწამი სჭირდება, შესაძლოა მეტი დრო დასჭირდეს დაშორებული ქეშიდან მისაღებად. იხილეთ [ლატენტობა, ბლობის ზომა და ბლობების რაოდენობა](#latency-blob-size-and-blob-count).
- **დამალული ტესტის გაშვებები.** ტესტის შედეგების ქეშირება სწორია, როცა ტესტები დეტერმინისტულია, მაგრამ ეს ასევე ნიშნავს, რომ flaky ტესტი, რომელიც ერთხელ წარმატებით ჩაიარა, გაშვების გარეშეც წარმატებით ჩაივლის. იხილეთ <.localized_link href="/references/concepts/flaky-test">რა არის flaky ტესტი?</.localized_link>.

## როგორ გავზომოთ ბილდის ქეში {#how-to-measure-a-build-cache}

ქეში ღირს იმას, რასაც ის ბოლომდე ზოგავს, და არა მხოლოდ მისი მოხვედრის მაჩვენებელი:

- **მოხვედრის მაჩვენებელი, სამუშაოს მიხედვით დაწონილი.** დაითვალეთ მოხვედრები და აცილებები თითოეული ნაბიჯისთვის, მაგრამ დააწონეთ ისინი იმის მიხედვით, თუ რამდენ ხანს სჭირდება თითოეული ნაბიჯის შესრულება. 95%-იანი მოხვედრის მაჩვენებელი იაფ ნაბიჯებზე შესაძლოა ნაკლებს ზოგავდეს, ვიდრე 50%-იანი მოხვედრის მაჩვენებელი ყველაზე ნელ კომპილაციებზე.
- **ცივი, თბილი და ტიპური ბილდები.** შეადარეთ ბილდი ცარიელი ქეშით, ბილდი სრულად გამთბარი ქეშით და ბილდები, რომლებსაც ადამიანები რეალურად ასრულებენ, მაგალითად, CI მცირე ცვლილების შემდეგ pull request-ზე. ბოლო არის ის რიცხვი, რომელსაც მნიშვნელობა აქვს.
- **დრო, დახარჯული თავად ქეშზე.** გაზომეთ მოთხოვნების რაოდენობა, ლატენტობა, ბაიტები და ჩამოტვირთვასა და ატვირთვაზე დახარჯული დრო. თუ ამ დროის უმეტესი ნაწილი ბევრ მცირე მოთხოვნაზე ლოდინია, ახლომდებარე ქეში უფრო მეტს ეხმარება, ვიდრე მეტი გამტარუნარიანობა; თუ ეს რამდენიმე დიდი ბლობის გადაადგილებაა, გამტარუნარიანობა და შეკუმშვა უფრო მნიშვნელოვანია.
- **რატომ ხდება აცილებები.** შეადარეთ ქეშის გასაღებები ერთი და იგივე ნაბიჯისთვის ორ მანქანაზე. Gradle-ს შეუძლია დაბეჭდოს თითოეული გასაღების უკან მყოფი შეყვანები `-Dorg.gradle.caching.debug=true`-ით, Bazel-ს შეუძლია ჩაწეროს შესრულების ლოგები (`--execution_log_compact_file`), რომელთა diff-ის გაკეთებაც შეგიძლიათ ორ ბილდს შორის, და Xcode აცნობებს კომპილაციის ქეშის მოხვედრებსა და აცილებებს ბილდის ლოგში, როცა `COMPILATION_CACHE_ENABLE_DIAGNOSTIC_REMARKS = YES`.

## როდის არ ღირს {#when-it-isnt-worth-it}

ბილდის ქეში ამატებს ინფრასტრუქტურას, უსაფრთხოების საზღვარს და ბაგების ახალ კლასს. ის არ არის ყოველთვის სწორი ინსტრუმენტი:

- **მცირე ან სწრაფი ბილდები.** თუ სუფთა ბილდს ერთი წუთი სჭირდება, remote cache ცოტას ზოგავს, და ქსელის round trip-ებმა შესაძლოა ის უფრო ნელი გახადოს.
- **ბილდები, რომლებიც დიზაინით აცილებენ.** თუ ბილდების უმეტესობა ცვლის შეყვანას გრაფის ფესვთან, ქეში ვერ დაეხმარება, სანამ ეს არ გამოსწორდება. ჯერ გაასწორეთ ინვალიდაცია; ქეში მხოლოდ ისეთ სამუშაოს ტოვებს, რომლის შეყვანები ემთხვევა.
- **მუდმივი ბილდის მანქანები.** CI მანქანა, რომელიც ინარჩუნებს ბილდის დირექტორიას იმავე branch-ზე ჯობებს შორის, უკვე იღებს ინკრემენტულ ბილდებს. გაზიარებული ქეში ეხმარება, როცა მანქანები ეფემერულია, როცა ბევრი branch არსებობს, ან როცა დეველოპერებმა და CI-მ ერთმანეთის სამუშაო უნდა ხელახლა გამოიყენონ.
- **არაჰერმეტული ბილდები, რომელთა გამოსწორებაც ჯერ არ შეგიძლიათ.** ქეში, რომელიც დროდადრო არასწორ შედეგებს აბრუნებს, უფრო მეტ ნდობას ღირს, ვიდრე დროს ზოგავს. ჯერ გახადეთ რეპროდუცირებადი ის ნაბიჯები, რომლებსაც ქეშავთ, ან დატოვეთ პრობლემური ნაბიჯები ქეშის გარეშე (მაგალითად, Bazel-ის `no-remote-cache` ტეგით).
- **ნელი ან დაშორებული ქსელები.** თუ ქეში შორს არის იქიდან, სადაც ბილდები სრულდება, გაზომეთ გადაცემის დრო ყველასთვის მის დანერგვამდე.

## ბილდის ქეშირება Tuist-ით {#build-caching-with-tuist}

[Tuist](https://tuist.dev) უზრუნველყოფს remote cache-ს, რომელიც ერწყმის თითოეული ბილდის სისტემის საკუთარ ქეშირებას, რათა დეველოპერის მანქანებმა, CI-მ და კოდირების აგენტებმა ხელახლა გამოიყენონ ერთმანეთის შედეგები, და ის იწერს მოხვედრებს, აცილებებსა და გადაცემის დროებს, რათა შეძლოთ ეფექტის გაზომვა:

- <.localized_link href="/guides/features/cache/xcode-cache">Xcode cache</.localized_link> აკავშირებს Xcode-ის კომპილაციის ქეშს გაზიარებულ remote cache-თან, ნებისმიერი Xcode პროექტისთვის Xcode 26 ან უფრო გვიან ვერსიაზე.
- <.localized_link href="/guides/features/cache/module-cache">Module cache</.localized_link> ცვლის მთელ მოდულებს წინასწარ აგებული ბინარებით Tuist-ით გენერირებულ პროექტებში.
- <.localized_link href="/guides/features/cache/gradle-cache">Gradle cache</.localized_link> და <.localized_link href="/guides/features/cache/bazel-cache">Bazel cache</.localized_link> ემსახურებიან როგორც Gradle-ის remote build cache და Remote Execution API cache Bazel-ისთვის.
- <.localized_link href="/guides/features/cache">Cache</.localized_link> ჩამოთვლის ყველა მხარდაჭერილ ბილდის სისტემას, Elixir-ის და Once-ის ჩათვლით.
- [Slow builds](https://tuist.dev/solutions/slow-builds) არის პრაქტიკული სახელმძღვანელო იმ სამუშაოს პოვნისთვის, რომლის ამოღებაც ღირს ქეშის არჩევამდე.
- [The physics of build systems](https://tuist.dev/blog/2026/08/25/the-physics-of-build-systems) და [Kura](https://tuist.dev/blog/2026/09/14/kura) ხსნიან, Tuist-ის ქეშის გაზომვებით, თუ როგორ განსხვავდება არტეფაქტის ზომა და მოთხოვნების მოცულობა module cache-ს, Xcode-ის კომპილაციის ქეშს, Bazel-სა და Gradle-ს შორის.
