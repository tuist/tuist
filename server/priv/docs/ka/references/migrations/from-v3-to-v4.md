# Tuist v3-დან v4-ზე {#from-tuist-v3-to-v4}

[Tuist 4](https://github.com/tuist/tuist/releases/tag/4.0.0)-ის გამოშვებასთან ერთად, ჩვენ გამოვიყენეთ შესაძლებლობა და პროექტში შევიტანეთ რიგი უკუთავსებადი ცვლილებები, რომლებიც, ჩვენი აზრით, პროექტის გამოყენებასა და მხარდაჭერას გრძელვადიან პერსპექტივაში გაამარტივებდა. ეს დოკუმენტი აღწერს ცვლილებებს, რომლებიც თქვენს პროექტში უნდა განახორციელოთ Tuist 3-დან Tuist 4-ზე გადასვლისთვის.

## ვერსიების მართვა `tuistenv`-ით აღარ არის ხელმისაწვდომი {#dropped-version-management-through-tuistenv}

Tuist 4-მდე, ინსტალაციის სკრიპტი აყენებდა ინსტრუმენტს `tuistenv`, რომელიც ინსტალაციის დროს სახელს იცვლიდა `tuist`-ზე. ეს ინსტრუმენტი ზრუნავდა Tuist-ის ვერსიების ინსტალაციასა და აქტივაციაზე, რაც უზრუნველყოფდა დეტერმინიზმს სხვადასხვა გარემოში. Tuist-ის ფუნქციონალის შემცირების მიზნით, ჩვენ გადავწყვიტეთ `tuistenv`-ის მოშორება [Mise](https://mise.jdx.dev/)-ის სასარგებლოდ — ინსტრუმენტის, რომელიც იმავე სამუშაოს ასრულებს, მაგრამ უფრო მოქნილია და სხვადასხვა ინსტრუმენტთან ერთად შეიძლება მისი გამოყენება. თუ იყენებდით `tuistenv`, მოგიწევთ Tuist-ის მიმდინარე ვერსიის წაშლა `curl -Ls https://uninstall.tuist.io | bash` ბრძანების გაშვებით და შემდეგ მისი ინსტალაცია თქვენთვის სასურველი მეთოდით. ჩვენ ძლიერ გირჩევთ Mise-ის გამოყენებას, რადგან ის ვერსიების დეტერმინისტულ ინსტალაციასა და აქტივაციას უზრუნველყოფს სხვადასხვა გარემოში.

```bash [Uninstall tuistenv]
curl -Ls https://uninstall.tuist.io | bash
```

## `init` კონსტრუქტორები ამოღებულია `ProjectDescription` მოდელებიდან {#dropped-init-constructors-from-projectdescription-models}

API-ების წაკითხვადობისა და გამომსახველობის გაუმჯობესების მიზნით, გადავწყვიტეთ `init` კონსტრუქტორების ამოღება ყველა `ProjectDescription` მოდელიდან. ყოველ მოდელს ახლა აქვს სტატიკური კონსტრუქტორი, რომლის გამოყენებაც შეგიძლიათ მოდელების ეგზემპლარების შესაქმნელად. თუ იყენებდით `init` კონსტრუქტორებს, მოგიწევთ პროექტის განახლება სტატიკური კონსტრუქტორების გამოსაყენებლად.

> [!TIP]
> **სახელდების კონვენცია**
>
> ჩვენ მიერ დაცული სახელდების კონვენცია გულისხმობს მოდელის სახელის გამოყენებას სტატიკური კონსტრუქტორის სახელად. მაგალითად, `Target` მოდელის სტატიკური კონსტრუქტორია `Target.target`.


## `--no-cache` გადაერქვა `--no-binary-cache` {#renamed-nocache-to-nobinarycache}

რადგან `--no-cache` ფლაგი ორაზროვანი იყო, გადავწყვიტეთ მისი `--no-binary-cache`-ზე გადასახელება, რათა ცხადი ყოფილიყო, რომ ის ბინარულ ქეშს ეხება. თუ იყენებდით `--no-cache` ფლაგს, მოგიწევთ პროექტის განახლება `--no-binary-cache` ფლაგის გამოსაყენებლად.

## `tuist fetch` გადაერქვა `tuist install` {#renamed-tuist-fetch-to-tuist-install}

`tuist fetch` ბრძანება გადავარქვით `tuist install`-ად, რათა დარგის კონვენციას შევუსაბამოთ. თუ იყენებდით `tuist fetch` ბრძანებას, მოგიწევთ პროექტის განახლება `tuist install` ბრძანების გამოსაყენებლად.

## [`Package.swift`-ის მიღება დამოკიდებულობების DSL-ად](https://github.com/tuist/tuist/pull/5862) {#adopt-packageswift-as-the-dsl-for-dependencieshttpsgithubcomtuisttuistpull5862}

Tuist 4-მდე, დამოკიდებულობების განსაზღვრა შეგიძლიათ `Dependencies.swift` ფაილში. ამ საკუთრებულმა ფორმატმა დაარღვია ისეთი ინსტრუმენტების მხარდაჭერა, როგორიცაა [Dependabot](https://github.com/dependabot) ან [Renovatebot](https://github.com/renovatebot/renovate), დამოკიდებულობების ავტომატური განახლებისთვის. გარდა ამისა, მან მომხმარებლებისთვის არასაჭირო შუალედური ნაბიჯები შემოიტანა. ამიტომ, გადავწყვიტეთ `Package.swift`-ის მიღება, როგორც Tuist-ში დამოკიდებულობების განსაზღვრის ერთადერთი გზა. თუ იყენებდით `Dependencies.swift` ფაილს, მოგიწევთ თქვენი `Tuist/Dependencies.swift` შიგთავსის გადატანა ფესვის დონეზე მდებარე `Package.swift` ფაილში და ინტეგრაციის კონფიგურაციისთვის `#if TUIST` დირექტივის გამოყენება. Swift Package დამოკიდებულობების ინტეგრაციის შესახებ მეტის წაკითხვა შეგიძლიათ <.localized_link href="/guides/features/projects/dependencies#swift-packages">აქ</.localized_link>

## `tuist cache warm` გადაერქვა `tuist cache` {#renamed-tuist-cache-warm-to-tuist-cache}

მოკლედ რომ ვთქვათ, გადავწყვიტეთ `tuist cache warm` ბრძანების `tuist cache`-ად გადასახელება. თუ იყენებდით `tuist cache warm` ბრძანებას, მოგიწევთ პროექტის განახლება `tuist cache` ბრძანების გამოსაყენებლად.


## `tuist cache print-hashes` გადაერქვა `tuist cache --print-hashes` {#renamed-tuist-cache-printhashes-to-tuist-cache-printhashes}

გადავწყვიტეთ `tuist cache print-hashes` ბრძანების `tuist cache --print-hashes`-ად გადასახელება, რათა ცხადი ყოფილიყო, რომ ეს `tuist cache` ბრძანების ფლაგია. თუ იყენებდით `tuist cache print-hashes` ბრძანებას, მოგიწევთ პროექტის განახლება `tuist cache --print-hashes` ფლაგის გამოსაყენებლად.

## ქეშირების პროფილები ამოღებულია {#removed-caching-profiles}

Tuist 4-მდე, ქეშირების პროფილების განსაზღვრა შეგიძლიათ `Tuist/Config.swift`-ში, რომელიც შეიცავდა ქეშის კონფიგურაციას. ეს ფუნქცია ამოვიღეთ, რადგან მისი გამოყენება პროექტის გენერაციის პროცესში იმ პროფილით, რომელიც არ ემთხვეოდა პროექტის გენერაციისას გამოყენებულ პროფილს, შეცდომაში შეჰყავდა მომხმარებელს. გარდა ამისა, შესაძლებელი იყო, მომხმარებლებს debug პროფილი გამოეყენებინათ აპლიკაციის release ვერსიის ასაგებად, რაც მოულოდნელ შედეგებს იწვევდა. მის ნაცვლად, შემოვიტანეთ `--configuration` ოფცია, რომლის გამოყენებაც შეგიძლიათ პროექტის გენერაციისას სასურველი კონფიგურაციის მითითებისთვის. თუ იყენებდით ქეშირების პროფილებს, მოგიწევთ პროექტის განახლება `--configuration` ოფციის გამოსაყენებლად.

## `--skip-cache` ამოღებულია არგუმენტების სასარგებლოდ {#removed-skipcache-in-favor-of-arguments}

`generate` ბრძანებიდან ამოვიღეთ ფლაგი `--skip-cache` და ბინარული ქეშის გამოტოვება სამიზნეების მიხედვით არგუმენტების გამოყენებით ვაკონტროლებთ. თუ იყენებდით `--skip-cache` ფლაგს, მოგიწევთ პროექტის განახლება არგუმენტების გამოსაყენებლად.

```bash [Before]
tuist generate --skip-cache Foo
```


## [ხელმოწერის შესაძლებლობები ამოღებულია](https://github.com/tuist/tuist/pull/5716) {#dropped-signing-capabilitieshttpsgithubcomtuisttuistpull5716}

ხელმოწერა უკვე გადაწყვეტილია საზოგადოების ინსტრუმენტებით, როგორიცაა [Fastlane](https://fastlane.tools/) და თავად Xcode, რომლებიც ამას ბევრად უკეთესად აკეთებენ. ჩვენ ვთვლიდით, რომ ხელმოწერა Tuist-ისთვის ზედმეტი ამბიცია იყო და უკეთესი იქნებოდა, პროექტის ძირითად ფუნქციებზე გაგვემახვილებინა ყურადღება. თუ იყენებდით Tuist-ის ხელმოწერის შესაძლებლობებს, რომელიც გულისხმობდა სერტიფიკატებისა და პროფილების დაშიფვრას რეპოზიტორიში და მათ სწორ ადგილებზე ინსტალაციას გენერაციის დროს, შეგიძლიათ ეს ლოგიკა გაიმეოროთ თქვენს საკუთარ სკრიპტებში, რომლებიც პროექტის გენერაციამდე სრულდება. კერძოდ:
  - სკრიპტი, რომელიც შლის სერტიფიკატებისა და პროფილების დაშიფვრას გასაღებით, რომელიც ან ფაილურ სისტემაშია შენახული, ან გარემოს ცვლადშია, და აყენებს სერტიფიკატებს keychain-ში, ხოლო პროვიზიონირების პროფილებს — `~/Library/MobileDevice/Provisioning\ Profiles` დირექტორიაში.
  - სკრიპტი, რომელსაც შეუძლია არსებული პროფილებისა და სერტიფიკატების აღება და მათი დაშიფვრა.

> [!TIP]
> **ხელმოწერის მოთხოვნები**
>
> ხელმოწერისთვის საჭიროა, რომ საჭირო სერტიფიკატები იყოს keychain-ში, ხოლო პროვიზიონირების პროფილები — `~/Library/MobileDevice/Provisioning\ Profiles` დირექტორიაში. სერტიფიკატების keychain-ში დასაყენებლად შეგიძლიათ გამოიყენოთ `security` ბრძანების ხაზის ინსტრუმენტი, ხოლო პროვიზიონირების პროფილების სწორ დირექტორიაში გადასატანად — `cp` ბრძანება.


## Carthage-ის ინტეგრაცია `Dependencies.swift`-ის მეშვეობით ამოღებულია {#dropped-carthage-integration-via-dependenciesswift}

Tuist 4-მდე Carthage-ის დამოკიდებულებების განსაზღვრა შეიძლებოდა `Dependencies.swift` ფაილში, რომლის მიღებაც მომხმარებლებს შეეძლოთ `tuist fetch` ბრძანების გაშვებით. ჩვენ ასევე მივიჩნიეთ, რომ ეს Tuist-ისთვის ზედმეტად ამბიციური ამოცანა იყო, განსაკუთრებით იმ პერსპექტივის გათვალისწინებით, სადაც Swift Package Manager იქნება დამოკიდებულებების მართვის სასურველი გზა. თუ Carthage-ის დამოკიდებულებებს იყენებდით, მოგიწევთ `Carthage`-ის პირდაპირ გამოყენება წინასწარ კომპილირებული frameworks-ებისა და XCFrameworks-ების Carthage-ის სტანდარტულ დირექტორიაში გადასატანად, შემდეგ კი ამ ბინარების თქვენს target-ებში მითითება `TargetDependency.xcframework` და `TargetDependency.framework` ვარიანტების გამოყენებით.

> [!NOTE]
> **Carthage კვლავ მხარდაჭერილია**
>
> ზოგიერთმა მომხმარებელმა გაიგო, რომ Carthage-ის მხარდაჭერა შევწყვიტეთ. არ შეგვიწყვეტია. Tuist-სა და Carthage-ის გამოსავალს შორის ხელშეკრულება ეხება სისტემაში შენახულ frameworks-ებსა და XCFrameworks-ებს. ერთადერთი რაც შეიცვალა, არის ის, თუ ვინ არის პასუხისმგებელი დამოკიდებულებების მიღებაზე. ადრე ეს იყო Tuist Carthage-ის მეშვეობით, ახლა კი — Carthage.


## `TargetDependency.packagePlugin` API ამოღებულია {#dropped-the-targetdependencypackageplugin-api}

Tuist 4-მდე package plugin-ის დამოკიდებულების განსაზღვრა შეიძლებოდა `TargetDependency.packagePlugin` ვარიანტის გამოყენებით. Swift Package Manager-ის მიერ ახალი package ტიპების დანერგვის ნახვის შემდეგ, ჩვენ გადავწყვიტეთ API-ს განვითარება უფრო მოქნილი და მომავლისთვის მზად მყოფი რამისკენ. თუ `TargetDependency.packagePlugin`-ს იყენებდით, მოგიწევთ `TargetDependency.package`-ის გამოყენება და სასურველი package ტიპის არგუმენტად გადაცემა.
