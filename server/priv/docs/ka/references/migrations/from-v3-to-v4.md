# Tuist v3-დან v4-მდე {#from-tuist-v3-to-v4}

[Tuist 4](https://github.com/tuist/tuist/releases/tag/4.0.0)-ის გამოშვებასთან ერთად, ჩვენ ვისარგებლეთ შესაძლებლობით და პროექტში რამდენიმე უკუთავსებადი ცვლილება შევიტანეთ, რაც, ჩვენი აზრით, პროექტის გამოყენებასა და მოვლას გრძელვადიან პერსპექტივაში გაამარტივებდა. ეს დოკუმენტი აღწერს იმ ცვლილებებს, რომლებიც თქვენს პროექტში უნდა განახორციელოთ Tuist 3-დან Tuist 4-ზე გადასასვლელად.

### ვერსიების მართვა `tuistenv`-ის საშუალებით ამოღებულია {#dropped-version-management-through-tuistenv}

Tuist 4-მდე, ინსტალაციის სკრიპტი აინსტალირებდა ხელსაწყოს `tuistenv`, რომელიც ინსტალაციის დროს `tuist`-ად გადაერქმეოდა. ხელსაწყო ზრუნავდა Tuist-ის ვერსიების ინსტალაციასა და გააქტიურებაზე, რითაც უზრუნველყოფდა დეტერმინიზმს გარემოებებს შორის. Tuist-ის ფუნქციონალის შემცირების მიზნით, ჩვენ გადავწყვიტეთ `tuistenv`-ის ამოღება [Mise](https://mise.jdx.dev/)-ის სასარგებლოდ — ეს არის ხელსაწყო, რომელიც იგივე სამუშაოს ასრულებს, მაგრამ უფრო მოქნილია და სხვადასხვა ხელსაწყოსთან ერთად შეიძლება მისი გამოყენება. თუ `tuistenv`-ს იყენებდით, Tuist-ის მიმდინარე ვერსია უნდა წაშალოთ `curl -Ls https://uninstall.tuist.io | bash`-ის გაშვებით და შემდეგ დააინსტალიროთ თქვენთვის სასურველი ინსტალაციის მეთოდით. ჩვენ მკაცრად გირჩევთ Mise-ის გამოყენებას, რადგან ის ვერსიების დეტერმინისტულ ინსტალაციასა და გააქტიურებას უზრუნველყოფს გარემოებებს შორის.

```bash [Uninstall tuistenv]
curl -Ls https://uninstall.tuist.io | bash
```

### `init` კონსტრუქტორები ამოღებულია `ProjectDescription` მოდელებიდან {#dropped-init-constructors-from-projectdescription-models}

API-ების წაკითხვადობისა და გამომსახველობის გაუმჯობესების მიზნით, ჩვენ გადავწყვიტეთ `init` კონსტრუქტორების ამოღება ყველა `ProjectDescription` მოდელიდან. ახლა თითოეული მოდელი უზრუნველყოფს სტატიკურ კონსტრუქტორს, რომლის გამოყენებაც შეგიძლიათ მოდელების ეგზემპლარების შესაქმნელად. თუ `init` კონსტრუქტორებს იყენებდით, თქვენი პროექტი უნდა განაახლოთ, რათა სტატიკური კონსტრუქტორები გამოიყენოთ.

> [!TIP]
> **სახელდების კონვენცია**
>
> ჩვენ მიერ დაცული სახელდების კონვენცია გულისხმობს მოდელის სახელის გამოყენებას სტატიკური კონსტრუქტორის სახელად. მაგალითად, `Target` მოდელის სტატიკური კონსტრუქტორია `Target.target`.


### `--no-cache` გადაერქვა `--no-binary-cache`-ად {#renamed-nocache-to-nobinarycache}

რადგან `--no-cache` ფლაგი ორაზროვანი იყო, ჩვენ გადავწყვიტეთ მისი `--no-binary-cache`-ად გადარქმევა, რათა ცხადი ყოფილიყო, რომ ის ბინარულ ქეშს ეხება. თუ `--no-cache` ფლაგს იყენებდით, თქვენი პროექტი უნდა განაახლოთ, რათა `--no-binary-cache` ფლაგი გამოიყენოთ.

### `tuist fetch` გადაერქვა `tuist install`-ად {#renamed-tuist-fetch-to-tuist-install}

`tuist fetch` ბრძანება `tuist install`-ად გადავარქვით, რათა ინდუსტრიულ კონვენციას შევუსაბამოთ. თუ `tuist fetch` ბრძანებას იყენებდით, თქვენი პროექტი უნდა განაახლოთ, რათა `tuist install` ბრძანება გამოიყენოთ.

### [`Package.swift`-ის მიღება დამოკიდებულობების DSL-ად](https://github.com/tuist/tuist/pull/5862) {#adopt-packageswift-as-the-dsl-for-dependencieshttpsgithubcomtuisttuistpull5862}

Tuist 4-მდე, დამოკიდებულობების განსაზღვრა `Dependencies.swift` ფაილში შეგეძლოთ. ამ საკუთრებულმა ფორმატმა დაარღვია ისეთი ხელსაწყოების მხარდაჭერა, როგორიცაა [Dependabot](https://github.com/dependabot) ან [Renovatebot](https://github.com/renovatebot/renovate), რომლებიც დამოკიდებულობებს ავტომატურად ანახლებდნენ. გარდა ამისა, ის მომხმარებლებისთვის არასაჭირო შუალედურ ნაბიჯებს ქმნიდა. ამიტომ, ჩვენ გადავწყვიტეთ `Package.swift`-ის მიღება, როგორც Tuist-ში დამოკიდებულობების განსაზღვრის ერთადერთი გზა. თუ `Dependencies.swift` ფაილს იყენებდით, თქვენი `Tuist/Dependencies.swift` შიგთავსი უნდა გადაიტანოთ ძირეულ დონეზე მდებარე `Package.swift` ფაილში და ინტეგრაციის კონფიგურაციისთვის გამოიყენოთ `#if TUIST` დირექტივა. Swift Package დამოკიდებულობების ინტეგრაციის შესახებ მეტის წაკითხვა შეგიძლიათ <.localized_link href="/guides/features/projects/dependencies#swift-packages">აქ</.localized_link>.

### `tuist cache warm` გადაერქვა `tuist cache`-ად {#renamed-tuist-cache-warm-to-tuist-cache}

მოკლე ფორმისთვის, ჩვენ გადავწყვიტეთ `tuist cache warm` ბრძანების `tuist cache`-ად გადარქმევა. თუ `tuist cache warm` ბრძანებას იყენებდით, თქვენი პროექტი უნდა განაახლოთ, რათა `tuist cache` ბრძანება გამოიყენოთ.


### `tuist cache print-hashes` გადაერქვა `tuist cache --print-hashes`-ად {#renamed-tuist-cache-printhashes-to-tuist-cache-printhashes}

ჩვენ გადავწყვიტეთ `tuist cache print-hashes` ბრძანების `tuist cache --print-hashes`-ად გადარქმევა, რათა ცხადი ყოფილიყო, რომ ის `tuist cache` ბრძანების ფლაგია. თუ `tuist cache print-hashes` ბრძანებას იყენებდით, თქვენი პროექტი უნდა განაახლოთ, რათა `tuist cache --print-hashes` ფლაგი გამოიყენოთ.

### ქეშირების პროფილები ამოღებულია {#removed-caching-profiles}

Tuist 4-მდე, ქეშირების პროფილების განსაზღვრა `Tuist/Config.swift`-ში შეგეძლოთ, რომელიც ქეშის კონფიგურაციას შეიცავდა. ჩვენ გადავწყვიტეთ ამ ფუნქციის ამოღება, რადგან მისი გამოყენება გენერაციის პროცესში პროფილით, რომელიც განსხვავდებოდა პროექტის გენერაციისთვის გამოყენებული პროფილისგან, შეცდომაში შეჰყავდა მომხმარებელი. გარდა ამისა, ეს შეიძლება გამოეწვია მომხმარებლებისთვის debug პროფილის გამოყენება აპლიკაციის release ვერსიის აგებისას, რაც მოულოდნელ შედეგებს გამოიწვევდა. მის ნაცვლად, ჩვენ შემოვიტანეთ `--configuration` პარამეტრი, რომლის გამოყენებაც შეგიძლიათ პროექტის გენერაციისას სასურველი კონფიგურაციის მითითებისთვის. თუ ქეშირების პროფილებს იყენებდით, თქვენი პროექტი უნდა განაახლოთ, რათა `--configuration` პარამეტრი გამოიყენოთ.

### `--skip-cache` ამოღებულია არგუმენტების სასარგებლოდ {#removed-skipcache-in-favor-of-arguments}

ბრძანებიდან `generate` ამოვიღეთ ფლაგი `--skip-cache` და მის ნაცვლად არგუმენტების გამოყენებით ვაკონტროლებთ, რომელი მიზნებისთვის (targets) უნდა გამოიტოვოს ბინარული ქეში. თუ `--skip-cache` ფლაგს იყენებდით, თქვენი პროექტი უნდა განაახლოთ, რათა არგუმენტები გამოიყენოთ.

::: code-group

```bash [Before]
tuist generate --skip-cache Foo
```

```bash [After]
tuist generate Foo
```

### [ხელმოწერის შესაძლებლობები ამოღებულია](https://github.com/tuist/tuist/pull/5716) {#dropped-signing-capabilitieshttpsgithubcomtuisttuistpull5716}

ხელმოწერა უკვე გადაწყვეტილია ისეთი საზოგადოებრივი ხელსაწყოებით, როგორიცაა [Fastlane](https://fastlane.tools/) და თავად Xcode, რომლებიც ამას ბევრად უკეთესად აკეთებენ. ჩვენ მივიჩნიეთ, რომ ხელმოწერა Tuist-ისთვის ზედმეტი მიზანი იყო და უკეთესი იქნებოდა, თუ პროექტის ძირითად ფუნქციებზე გავამახვილებდით ყურადღებას. თუ Tuist-ის ხელმოწერის შესაძლებლობებს იყენებდით, რაც გულისხმობდა სერტიფიკატებისა და პროფილების დაშიფვრას რეპოზიტორიში და მათ სწორ ადგილებზე ინსტალაციას გენერაციის დროს, შეიძლება მოგინდეთ ამ ლოგიკის გამეორება თქვენს საკუთარ სკრიპტებში, რომლებიც პროექტის გენერაციამდე ეშვება. კერძოდ:
  - სკრიპტი, რომელიც შლის სერტიფიკატებისა და პროფილების დაშიფვრას გასაღებით, რომელიც ან ფაილურ სისტემაშია შენახული, ან გარემოს ცვლადში, აინსტალირებს სერტიფიკატებს keychain-ში, ხოლო პროვიზიონირების პროფილებს — დირექტორიაში `~/Library/MobileDevice/Provisioning\ Profiles`.
  - სკრიპტი, რომელსაც შეუძლია არსებული პროფილებისა და სერტიფიკატების აღება და მათი დაშიფვრა.

> [!TIP]
> **ხელმოწერის მოთხოვნები**
>
> ხელმოწერა მოითხოვს, რომ საჭირო სერტიფიკატები იყოს keychain-ში, ხოლო პროვიზიონირების პროფილები — დირექტორიაში `~/Library/MobileDevice/Provisioning\ Profiles`. სერტიფიკატების keychain-ში ინსტალაციისთვის შეგიძლიათ გამოიყენოთ `security` ბრძანების ხაზის ხელსაწყო, ხოლო პროვიზიონირების პროფილების საჭირო დირექტორიაში დასაკოპირებლად — `cp` ბრძანება.


### Carthage-ის ინტეგრაცია `Dependencies.swift`-ის საშუალებით ამოღებულია {#dropped-carthage-integration-via-dependenciesswift}

Tuist 4-მდე Carthage-ის დამოკიდებულებები შეიძლება განისაზღვროს `Dependencies.swift` ფაილში, რომლის წამოღებაც მომხმარებლებს `tuist fetch` ბრძანების გაშვებით შეეძლოთ. ასევე მიგვაჩნდა, რომ ეს Tuist-ისთვის ზედმეტად ამბიციური მიზანი იყო, განსაკუთრებით იმ პერსპექტივის გათვალისწინებით, სადაც Swift Package Manager იქნება დამოკიდებულებების მართვის სასურველი გზა. თუ Carthage-ის დამოკიდებულებებს იყენებდით, პირდაპირ `Carthage` უნდა გამოიყენოთ წინასწარ კომპილირებული ჩარჩოებისა და XCFramework-ების Carthage-ის სტანდარტულ დირექტორიაში ჩამოსატვირთად, შემდეგ კი ეს ბინარული ფაილები თქვენს სამიზნეებში `TargetDependency.xcframework` და `TargetDependency.framework` ვარიანტების გამოყენებით მიუთითეთ.

> [!NOTE]
> **Carthage კვლავ მხარდაჭერილია**
>
> ზოგიერთმა მომხმარებელმა იფიქრა, რომ Carthage-ის მხარდაჭერა შევწყვიტეთ. არა. Tuist-სა და Carthage-ის გამოსავალს შორის ხელშეკრულება ეხება სისტემაში შენახულ ჩარჩოებსა და XCFramework-ებს. ერთადერთი რაც შეიცვალა, არის ის, ვინ არის პასუხისმგებელი დამოკიდებულებების წამოღებაზე. ადრე ეს იყო Tuist Carthage-ის მეშვეობით, ახლა კი — Carthage.


### ამოღებულია `TargetDependency.packagePlugin` API {#dropped-the-targetdependencypackageplugin-api}

Tuist 4-მდე პაკეტის პლაგინის დამოკიდებულების განსაზღვრა შეიძლებოდა `TargetDependency.packagePlugin` ვარიანტის გამოყენებით. Swift Package Manager-ის მიერ ახალი პაკეტის ტიპების შემოღების ნახვის შემდეგ, გადავწყვიტეთ API-ის იტერაცია უფრო მოქნილი და მომავლისთვის მზად მყოფი რამისკენ. თუ `TargetDependency.packagePlugin`-ს იყენებდით, ნაცვლად ამისა `TargetDependency.package` უნდა გამოიყენოთ და სასურველი პაკეტის ტიპი არგუმენტად გადასცეთ.

ჩვენ წავშალეთ APIs, რომლებიც Tuist 3-ში მოძველებულად იყო მონიშნული. თუ რომელიმე მოძველებულ API-ს იყენებდით, პროექტი უნდა განაახლოთ ახალი APIs-ის გამოყენებისთვის.
