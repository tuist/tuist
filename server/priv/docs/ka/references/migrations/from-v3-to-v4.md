# Tuist v3-დან v4-ზე {#from-tuist-v3-to-v4}

[Tuist 4](https://github.com/tuist/tuist/releases/tag/4.0.0)-ის გამოშვებასთან ერთად, ჩვენ გამოვიყენეთ შესაძლებლობა და პროექტში შევიტანეთ რიგი უკუთავსებადი ცვლილებები, რომლებიც, ჩვენი აზრით, პროექტის გამოყენებასა და მხარდაჭერას გრძელვადიან პერსპექტივაში გაამარტივებდა. ეს დოკუმენტი აღწერს ცვლილებებს, რომლებიც თქვენს პროექტში უნდა განახორციელოთ Tuist 3-დან Tuist 4-ზე გადასასვლელად.

## ვერსიების მართვა `tuistenv`-ის საშუალებით ამოღებულია {#dropped-version-management-through-tuistenv}

Tuist 4-მდე, ინსტალაციის სკრიპტი აინსტალირებდა ხელსაწყოს `tuistenv`, რომელიც ინსტალაციის დროს გადაერქმეოდა `tuist`-ად. ეს ხელსაწყო ზრუნავდა Tuist-ის ვერსიების ინსტალაციაზე და აქტივაციაზე, რაც უზრუნველყოფდა დეტერმინიზმს სხვადასხვა გარემოში. Tuist-ის ფუნქციონალის შემცირების მიზნით, ჩვენ გადავწყვიტეთ `tuistenv`-ის ამოღება [Mise](https://mise.jdx.dev/)-ის სასარგებლოდ — ხელსაწყოს, რომელიც იმავე სამუშაოს ასრულებს, მაგრამ უფრო მოქნილია და სხვადასხვა ხელსაწყოსთან ერთად შეიძლება მისი გამოყენება. თუ იყენებდით `tuistenv`, მოგიწევთ Tuist-ის მიმდინარე ვერსიის წაშლა `curl -Ls https://uninstall.tuist.io | bash`-ის გაშვებით და შემდეგ მისი ინსტალაცია თქვენთვის სასურველი მეთოდით. ჩვენ მკაცრად გირჩევთ Mise-ის გამოყენებას, რადგან ის ვერსიების დეტერმინისტულად ინსტალაციასა და აქტივაციას უზრუნველყოფს სხვადასხვა გარემოში.

## `init` კონსტრუქტორები ამოღებულია `ProjectDescription` მოდელებიდან {#dropped-init-constructors-from-projectdescription-models}

API-ების წაკითხვადობისა და გამომსახველობითობის გაუმჯობესების მიზნით, გადავწყვიტეთ `init` კონსტრუქტორების ამოღება ყველა `ProjectDescription` მოდელიდან. ახლა თითოეული მოდელი გთავაზობთ სტატიკურ კონსტრუქტორს, რომლის გამოყენებაც შეგიძლიათ მოდელების ეგზემპლარების შესაქმნელად. თუ იყენებდით `init` კონსტრუქტორებს, მოგიწევთ თქვენი პროექტის განახლება სტატიკური კონსტრუქტორების გამოსაყენებლად.

> [!TIP]
> **სახელდების კონვენცია**
>
> ჩვენ მიერ დაცული სახელდების კონვენცია გულისხმობს მოდელის სახელის გამოყენებას სტატიკური კონსტრუქტორის სახელად. მაგალითად, `Target` მოდელის სტატიკური კონსტრუქტორია `Target.target`.


## `--no-cache` გადაერქვა `--no-binary-cache`-ად {#renamed-nocache-to-nobinarycache}

რადგან `--no-cache` ფლაგი ორაზროვანი იყო, გადავწყვიტეთ მისი `--no-binary-cache`-ად გადაერქმევა, რათა ცხადი ყოფილიყო, რომ ის ბინარულ ქეშს ეხება. თუ იყენებდით `--no-cache` ფლაგს, მოგიწევთ თქვენი პროექტის განახლება `--no-binary-cache` ფლაგის გამოსაყენებლად.

## `tuist fetch` გადაერქვა `tuist install`-ად {#renamed-tuist-fetch-to-tuist-install}

`tuist fetch` ბრძანება გადავარქვით `tuist install`-ად, რათა შესაბამისობაში მოგვეყვანა ის ინდუსტრიულ კონვენციასთან. თუ იყენებდით `tuist fetch` ბრძანებას, მოგიწევთ თქვენი პროექტის განახლება `tuist install` ბრძანების გამოსაყენებლად.

## [`Package.swift`-ის აპრობირება დამოკიდებულებების DSL-ად](https://github.com/tuist/tuist/pull/5862) {#adopt-packageswift-as-the-dsl-for-dependencieshttpsgithubcomtuisttuistpull5862}

Tuist 4-მდე, დამოკიდებულებების განსაზღვრა შეგიძლიათ `Dependencies.swift` ფაილში. ამ საკუთრებულმა ფორმატმა დაარღვია ისეთი ხელსაწყოების მხარდაჭერა, როგორიცაა [Dependabot](https://github.com/dependabot) ან [Renovatebot](https://github.com/renovatebot/renovate), რათა დამოკიდებულებები ავტომატურად განახლებულიყო. გარდა ამისა, მან შემოიტანა არასაჭირო შუალედური ნაბიჯები მომხმარებლებისთვის. ამიტომ, გადავწყვიტეთ `Package.swift`-ის აპრობირება Tuist-ში დამოკიდებულებების განსაზღვრის ერთადერთ გზად. თუ იყენებდით `Dependencies.swift` ფაილს, მოგიწევთ თქვენი `Tuist/Dependencies.swift` შიგთავსის გადატანა ძირითად დირექტორიაში მდებარე `Package.swift` ფაილში და `#if TUIST` დირექტივის გამოყენება ინტეგრაციის კონფიგურაციისთვის. Swift Package დამოკიდებულებების ინტეგრაციის შესახებ მეტის წაკითხვა შეგიძლიათ <.localized_link href="/guides/features/projects/dependencies#swift-packages">აქ</.localized_link>

## `tuist cache warm` გადაერქვა `tuist cache`-ად {#renamed-tuist-cache-warm-to-tuist-cache}

მოკლე ფორმისთვის, გადავწყვიტეთ `tuist cache warm` ბრძანების `tuist cache`-ად გადაერქმევა. თუ იყენებდით `tuist cache warm` ბრძანებას, მოგიწევთ თქვენი პროექტის განახლება `tuist cache` ბრძანების გამოსაყენებლად.


## `tuist cache print-hashes` გადაერქვა `tuist cache --print-hashes`-ად {#renamed-tuist-cache-printhashes-to-tuist-cache-printhashes}

გადავწყვიტეთ `tuist cache print-hashes` ბრძანების `tuist cache --print-hashes`-ად გადაერქმევა, რათა ცხადი ყოფილიყო, რომ ეს `tuist cache` ბრძანების ფლაგია. თუ იყენებდით `tuist cache print-hashes` ბრძანებას, მოგიწევთ თქვენი პროექტის განახლება `tuist cache --print-hashes` ფლაგის გამოსაყენებლად.

## ქეშირების პროფილები ამოღებულია {#removed-caching-profiles}

Tuist 4-მდე, ქეშირების პროფილების განსაზღვრა შეგიძლიათ `Tuist/Config.swift`-ში, რომელიც შეიცავდა ქეშის კონფიგურაციას. ჩვენ გადავწყვიტეთ ამ ფუნქციის ამოღება, რადგან მისი გამოყენება გენერაციის პროცესში პროექტის გენერაციისთვის გამოყენებული პროფილისგან განსხვავებული პროფილით შეიძლება დაბნეულობას იწვევდეს. გარდა ამისა, ეს შეიძლება გამოეწვია მომხმარებლებს debug პროფილის გამოყენება აპის release ვერსიის აგებისთვის, რაც მოულოდნელ შედეგებს გამოიწვევდა. მის ნაცვლად, ჩვენ შემოვიტანეთ `--configuration` ოფცია, რომლის გამოყენებაც შეგიძლიათ პროექტის გენერაციისას სასურველი კონფიგურაციის მითითებისთვის. თუ იყენებდით ქეშირების პროფილებს, მოგიწევთ თქვენი პროექტის განახლება `--configuration` ოფციის გამოსაყენებლად.

## `--skip-cache` ამოღებულია არგუმენტების სასარგებლოდ {#removed-skipcache-in-favor-of-arguments}

`generate` ბრძანებიდან ამოვიღეთ ფლაგი `--skip-cache` და ბინარული ქეშის გამოტოვება იმ სამიზნეებისთვის, რომელთათვისაც ეს სასურველია, არგუმენტების გამოყენებით ვაკონტროლებთ. თუ იყენებდით `--skip-cache` ფლაგს, მოგიწევთ თქვენი პროექტის განახლება არგუმენტების გამოსაყენებლად.

```bash [Before]
tuist generate --skip-cache Foo
```

```bash [After]
tuist generate Foo
```

## [ხელმოწერის შესაძლებლობები ამოღებულია](https://github.com/tuist/tuist/pull/5716) {#dropped-signing-capabilitieshttpsgithubcomtuisttuistpull5716}

ხელმოწერა უკვე გადაწყვეტილია საზოგადოების ხელსაწყოებით, როგორიცაა [Fastlane](https://fastlane.tools/) და თავად Xcode, რომლებიც ამ საქმეს ბევრად უკეთ ასრულებენ. ჩვენ ვთვლიდით, რომ ხელმოწერა Tuist-ისთვის ზედმეტი მიზანი იყო და უკეთესი იქნებოდა პროექტის ძირითად ფუნქციებზე ფოკუსირება. თუ იყენებდით Tuist-ის ხელმოწერის შესაძლებლობებს, რომლებიც გულისხმობდა სერტიფიკატებისა და პროფილების დაშიფვრას რეპოზიტორიში და მათ სწორ ადგილებზე ინსტალაციას გენერაციის დროს, შეგიძლიათ ეს ლოგიკა გაიმეოროთ თქვენს საკუთარ სკრიპტებში, რომლებიც პროექტის გენერაციამდე გაეშვება. კერძოდ:
  - სკრიპტი, რომელიც შლის სერტიფიკატებსა და პროფილებს გასაღებით, რომელიც ან ფაილურ სისტემაშია შენახული, ან გარემოს ცვლადში, და აინსტალირებს სერტიფიკატებს keychain-ში, ხოლო პროვიზიონირების პროფილებს დირექტორიაში `~/Library/MobileDevice/Provisioning\ Profiles`.
  - სკრიპტი, რომელსაც შეუძლია არსებული პროფილებისა და სერტიფიკატების აღება და მათი დაშიფვრა.

> [!TIP]
> **ხელმოწერის მოთხოვნები**
>
> ხელმოწერა მოითხოვს, რომ საჭირო სერტიფიკატები იყოს keychain-ში, ხოლო პროვიზიონირების პროფილები — დირექტორიაში `~/Library/MobileDevice/Provisioning\ Profiles`. შეგიძლიათ გამოიყენოთ `security` ბრძანების ხაზის ხელსაწყო სერტიფიკატების keychain-ში ინსტალაციისთვის და `cp` ბრძანება პროვიზიონირების პროფილების სწორ დირექტორიაში კოპირებისთვის.


## Carthage-ის ინტეგრაცია `Dependencies.swift`-ის მეშვეობით ამოღებულია {#dropped-carthage-integration-via-dependenciesswift}

Tuist 4-მდე Carthage-ის დამოკიდებულებები შეიძლება განსაზღვრულიყო `Dependencies.swift` ფაილში, რომლის ჩამოტვირთვაც მომხმარებლებს `tuist fetch`-ის გაშვებით შეეძლოთ. ასევე მივიჩნიეთ, რომ ეს Tuist-ისთვის ზედმეტად ამბიციური ამოცანა იყო, განსაკუთრებით იმ მომავლის გათვალისწინებით, სადაც Swift Package Manager იქნება დამოკიდებულებების მართვის სასურველი გზა. თუ Carthage-ის დამოკიდებულებებს იყენებდით, პირდაპირ `Carthage` უნდა გამოიყენოთ წინასწარ კომპილირებული ფრეიმვორკებისა და XCFramework-ების Carthage-ის სტანდარტულ დირექტორიაში ჩამოსატვირთად, შემდეგ კი თქვენს სამიზნეებში (targets) ეს ბინარები `TargetDependency.xcframework` და `TargetDependency.framework` ვარიანტების მეშვეობით მიუთითოთ.

> [!NOTE]
> **Carthage კვლავ მხარდაჭერილია**
>
> ზოგიერთმა მომხმარებელმა იფიქრა, რომ Carthage-ის მხარდაჭერა გავაუქმეთ. არ გაგვიუქმებია. Tuist-სა და Carthage-ის გამომავალ ფაილებს შორის ხელშეკრულება ეხება სისტემაში შენახულ ფრეიმვორკებსა და XCFramework-ებს. ერთადერთი რაც შეიცვალა, არის ის, ვინ არის პასუხისმგებელი დამოკიდებულებების ჩამოტვირთვაზე. ადრე ეს იყო Tuist Carthage-ის მეშვეობით, ახლა კი — Carthage.


## `TargetDependency.packagePlugin` API ამოღებულია {#dropped-the-targetdependencypackageplugin-api}

Tuist 4-მდე პაკეტის პლაგინის დამოკიდებულების განსაზღვრა `TargetDependency.packagePlugin` ვარიანტის გამოყენებით შეგეძლოთ. Swift Package Manager-ის მიერ ახალი ტიპის პაკეტების წარმოდგენის შემდეგ, გადავწყვიტეთ API-ს განვითარება უფრო მოქნილი და მომავალზე ორიენტირებული მიმართულებით. თუ `TargetDependency.packagePlugin`-ს იყენებდით, მის ნაცვლად `TargetDependency.package` უნდა გამოიყენოთ და სასურველი პაკეტის ტიპი არგუმენტად გადასცეთ.

## [მოძველებული API-ები ამოღებულია](https://github.com/tuist/tuist/pull/5560) {#dropped-deprecated-apishttpsgithubcomtuisttuistpull5560}

ამოვიღეთ API-ები, რომლებიც Tuist 3-ში მოძველებულად იყო მონიშნული. თუ რომელიმე მოძველებულ API-ს იყენებდით, პროექტი უნდა განაახლოთ ახალი API-ების გამოყენებისთვის.
