# Tuist v3-დან v4-ზე {#from-tuist-v3-to-v4}

[Tuist 4](https://github.com/tuist/tuist/releases/tag/4.0.0)-ის გამოშვებასთან ერთად, ჩვენ გამოვიყენეთ შესაძლებლობა და პროექტში შევიტანეთ რიგი უთავსებელი ცვლილებები, რომლებიც, ჩვენი აზრით, პროექტის გამოყენებასა და მოვლას გაამარტივებდა გრძელვადიან პერსპექტივაში. ეს დოკუმენტი აღწერს იმ ცვლილებებს, რომლებიც თქვენს პროექტში უნდა განახორციელოთ Tuist 3-დან Tuist 4-ზე გადასასვლელად.

### ვერსიების მართვა `tuistenv`-ით შეწყდა {#dropped-version-management-through-tuistenv}

Tuist 4-მდე ინსტალაციის სკრიპტი აინსტალირებდა ხელსაწყოს `tuistenv`, რომელიც ინსტალაციის დროს გადაერქმეოდა სახელი `tuist`-ზე. ეს ხელსაწყო ზრუნავდა Tuist-ის ვერსიების ინსტალაციასა და აქტივაციაზე, რაც უზრუნველყოფდა დეტერმინიზმს სხვადასხვა გარემოში. Tuist-ის ფუნქციონალის შემცირების მიზნით, ჩვენ გადავწყვიტეთ `tuistenv`-ის შეწყვეტა [Mise](https://mise.jdx.dev/)-ის სასარგებლოდ — ეს არის ხელსაწყო, რომელიც იგივე სამუშაოს ასრულებს, მაგრამ უფრო მოქნილია და შეიძლება გამოყენებული იქნას სხვადასხვა ხელსაწყოსთან. თუ იყენებდით `tuistenv`, მოგიწევთ Tuist-ის მიმდინარე ვერსიის წაშლა `curl -Ls https://uninstall.tuist.io | bash` ბრძანების გაშვებით და შემდეგ მისი ინსტალაცია თქვენთვის სასურველი მეთოდით. ჩვენ ძლიერ გირჩევთ Mise-ის გამოყენებას, რადგან ის შეუძლია ვერსიების დეტერმინისტულად ინსტალაცია და აქტივაცია სხვადასხვა გარემოში.

### `init` კონსტრუქტორები ამოღებულია `ProjectDescription` მოდელებიდან {#dropped-init-constructors-from-projectdescription-models}

API-ების წაკითხვადობისა და გამომსახველობის გაუმჯობესების მიზნით, გადავწყვიტეთ `init` კონსტრუქტორების ამოღება ყველა `ProjectDescription` მოდელიდან. ახლა თითოეული მოდელი უზრუნველყოფს სტატიკურ კონსტრუქტორს, რომლის გამოყენებაც შეგიძლიათ მოდელების ეგზემპლარების შესაქმნელად. თუ იყენებდით `init` კონსტრუქტორებს, მოგიწევთ თქვენი პროექტის განახლება სტატიკური კონსტრუქტორების გამოსაყენებლად.

> [!TIP]
> **სახელდების კონვენცია**
>
> ჩვენ მიერ დაცული სახელდების კონვენცია გულისხმობს მოდელის სახელის გამოყენებას სტატიკური კონსტრუქტორის სახელად. მაგალითად, `Target` მოდელის სტატიკური კონსტრუქტორია `Target.target`.


### `--no-cache` გადაერქვა სახელი `--no-binary-cache`-ზე {#renamed-nocache-to-nobinarycache}

რადგან `--no-cache` ფლაგი ორაზროვანი იყო, გადავწყვიტეთ მისი სახელის შეცვლა `--no-binary-cache`-ზე, რათა ნათლად ყოფილიყო, რომ ის ბინარულ ქეშს ეხება. თუ იყენებდით `--no-cache` ფლაგს, მოგიწევთ თქვენი პროექტის განახლება `--no-binary-cache` ფლაგის გამოსაყენებლად.

### `tuist fetch` გადაერქვა სახელი `tuist install`-ზე {#renamed-tuist-fetch-to-tuist-install}

ბრძანება `tuist fetch` გადავარქვით `tuist install`-ზე ინდუსტრიულ კონვენციასთან შესაბამისობაში. თუ იყენებდით `tuist fetch` ბრძანებას, მოგიწევთ თქვენი პროექტის განახლება `tuist install` ბრძანების გამოსაყენებლად.

### [`Package.swift`-ის მიღება დამოკიდებულებების DSL-ად](https://github.com/tuist/tuist/pull/5862) {#adopt-packageswift-as-the-dsl-for-dependencieshttpsgithubcomtuisttuistpull5862}

Tuist 4-მდე დამოკიდებულებების განსაზღვრა შეგიძლიათ `Dependencies.swift` ფაილში. ამ საკუთრებულმა ფორმატმა დაარღვია მხარდაჭერა ისეთ ხელსაწყოებში, როგორიცაა [Dependabot](https://github.com/dependabot) ან [Renovatebot](https://github.com/renovatebot/renovate), რათა დამოკიდებულებები ავტომატურად განახლდეს. გარდა ამისა, მან შემოიტანა არასაჭირო შუალედური ნაბიჯები მომხმარებლებისთვის. ამიტომ, გადავწყვიტეთ `Package.swift`-ის მიღება Tuist-ში დამოკიდებულებების განსაზღვრის ერთადერთ გზად. თუ იყენებდით `Dependencies.swift` ფაილს, მოგიწევთ თქვენი `Tuist/Dependencies.swift` შიგთავსის გადატანა `Package.swift` ფაილში პროექტის ფესვში და `#if TUIST` დირექტივის გამოყენება ინტეგრაციის კონფიგურაციისთვის. Swift Package დამოკიდებულებების ინტეგრაციის შესახებ მეტის წაკითხვა შეგიძლიათ <.localized_link href="/guides/features/projects/dependencies#swift-packages">აქ</.localized_link>.

### `tuist cache warm` გადაერქვა სახელი `tuist cache`-ზე {#renamed-tuist-cache-warm-to-tuist-cache}

მოკლედ რომ ვთქვათ, გადავწყვიტეთ `tuist cache warm` ბრძანების სახელის შეცვლა `tuist cache`-ზე. თუ იყენებდით `tuist cache warm` ბრძანებას, მოგიწევთ თქვენი პროექტის განახლება `tuist cache` ბრძანების გამოსაყენებლად.


### `tuist cache print-hashes` გადაერქვა სახელი `tuist cache --print-hashes`-ზე {#renamed-tuist-cache-printhashes-to-tuist-cache-printhashes}

გადავწყვიტეთ `tuist cache print-hashes` ბრძანების სახელის შეცვლა `tuist cache --print-hashes`-ზე, რათა ნათლად ყოფილიყო, რომ ის `tuist cache` ბრძანების ფლაგია. თუ იყენებდით `tuist cache print-hashes` ბრძანებას, მოგიწევთ თქვენი პროექტის განახლება `tuist cache --print-hashes` ფლაგის გამოსაყენებლად.

### ქეშირების პროფილები ამოღებულია {#removed-caching-profiles}

Tuist 4-მდე ქეშირების პროფილების განსაზღვრა შეგიძლიათ `Tuist/Config.swift`-ში, რომელიც შეიცავდა ქეშის კონფიგურაციას. გადავწყვიტეთ ამ ფუნქციის ამოღება, რადგან მისი გამოყენება პროექტის გენერაციის პროცესში იმ პროფილით, რომელიც არ ემთხვევა პროექტის გენერაციისას გამოყენებულ პროფილს, შეიძლება გამოიწვიოს დაბნეულობა. გარდა ამისა, ეს შეიძლება გამოიწვიოს მომხმარებლების მიერ debug პროფილის გამოყენება აპლიკაციის release ვერსიის აგებისას, რაც შეიძლება გამოიწვიოს მოულოდნელი შედეგები. მის ნაცვლად, ჩვენ შემოვიტანეთ `--configuration` ოფცია, რომლის გამოყენებაც შეგიძლიათ პროექტის გენერაციისას სასურველი კონფიგურაციის მითითებისთვის. თუ იყენებდით ქეშირების პროფილებს, მოგიწევთ თქვენი პროექტის განახლება `--configuration` ოფციის გამოსაყენებლად.

### `--skip-cache` ამოღებულია არგუმენტების სასარგებლოდ {#removed-skipcache-in-favor-of-arguments}

ბრძანებიდან `generate` ამოვიღეთ ფლაგი `--skip-cache` იმის სასარგებლოდ, რომ ბინარული ქეშის გამოტოვება კონტროლდებოდეს არგუმენტების გამოყენებით იმ სამიზნეებისთვის, რომლებისთვისაც ის უნდა გამოიტოვოს. თუ იყენებდით `--skip-cache` ფლაგს, მოგიწევთ თქვენი პროექტის განახლება არგუმენტების გამოსაყენებლად.

```bash [Before]
tuist generate --skip-cache Foo
```

### [ხელმოწერის შესაძლებლობები ამოღებულია](https://github.com/tuist/tuist/pull/5716) {#dropped-signing-capabilitieshttpsgithubcomtuisttuistpull5716}

ხელმოწერა უკვე გადაწყვეტილია საზოგადოების ხელსაწყოებით, როგორიცაა [Fastlane](https://fastlane.tools/) და თავად Xcode, რომლებიც ამას ბევრად უკეთესად აკეთებენ. ჩვენ ვთვლიდით, რომ ხელმოწერა Tuist-ისთვის ზედმეტი ამოცანა იყო და უკეთესი იქნებოდა პროექტის ძირითად ფუნქციებზე ფოკუსირება. თუ იყენებდით Tuist-ის ხელმოწერის შესაძლებლობებს, რომელიც შედგებოდა რეპოზიტორიაში სერთიფიკატებისა და პროფილების დაშიფვრისა და გენერაციის დროს მათ შესაბამის ადგილებში ინსტალაციისგან, შეიძლება მოგინდეთ ამ ლოგიკის რეპლიკაცია თქვენს საკუთარ სკრიპტებში, რომლებიც პროექტის გენერაციამდე გაეშვება. კერძოდ:
  - სკრიპტი, რომელიც შლის სერთიფიკატებსა და პროფილებს გასაღებით, რომელიც ან ფაილურ სისტემაშია შენახული, ან გარემოს ცვლადში, და აინსტალირებს სერთიფიკატებს keychain-ში, ხოლო პროვიზიონირების პროფილებს დირექტორიაში `~/Library/MobileDevice/Provisioning\ Profiles`.
  - სკრიპტი, რომელსაც შეუძლია არსებული პროფილებისა და სერთიფიკატების აღება და მათი დაშიფვრა.

> [!TIP]
> **ხელმოწერის მოთხოვნები**
>
> ხელმოწერა მოითხოვს, რომ საჭირო სერთიფიკატები იყოს keychain-ში, ხოლო პროვიზიონირების პროფილები — დირექტორიაში `~/Library/MobileDevice/Provisioning\ Profiles`. სერთიფიკატების keychain-ში ინსტალაციისთვის შეგიძლიათ გამოიყენოთ `security` ბრძანების ხაზის ხელსაწყო, ხოლო პროვიზიონირების პროფილების შესაბამის დირექტორიაში კოპირებისთვის — `cp` ბრძანება.


### Carthage-ის ინტეგრაცია `Dependencies.swift`-ით შეწყდა {#dropped-carthage-integration-via-dependenciesswift}

Tuist 4-მდე Carthage-ის დამოკიდებულებები შეიძლება განისაზღვროს `Dependencies.swift` ფაილში, რომლის ჩამოტვირთვაც მომხმარებლებს `tuist fetch` ბრძანების გაშვებით შეეძლოთ. ასევე მივიჩნიეთ, რომ ეს Tuist-ისთვის ზედმეტი ამბიცია იყო, განსაკუთრებით იმ პერსპექტივის გათვალისწინებით, სადაც Swift Package Manager დამოკიდებულებების მართვის სასურველ გზად იქნება მიჩნეული. თუ Carthage-ის დამოკიდებულებებს იყენებდით, მოგიწევთ `Carthage` პირდაპირ გამოიყენოთ წინასწარ კომპილირებული ფრეიმვორკებისა და XCFramework-ების Carthage-ის სტანდარტულ დირექტორიაში ჩამოსატვირთად, შემდეგ კი თქვენს სამიზნეებში (targets) ამ ბინარების მითითება `TargetDependency.xcframework` და `TargetDependency.framework` ვარიანტების გამოყენებით.

> [!NOTE]
> **Carthage კვლავ მხარდაჭერილია**
>
> ზოგიერთმა მომხმარებელმა გაიგო, რომ Carthage-ის მხარდაჭერა შევწყვიტეთ. არა. Tuist-სა და Carthage-ის გამომავალ პროდუქტს შორის კონტრაქტი სისტემაში შენახულ ფრეიმვორკებთან და XCFramework-ებთან არის დაკავშირებული. ერთადერთი რაც შეიცვალა, ის არის, თუ ვინ არის პასუხისმგებელი დამოკიდებულებების ჩამოტვირთვაზე. ადრე ეს Tuist იყო Carthage-ის მეშვეობით, ახლა კი — Carthage.


### შეწყდა `TargetDependency.packagePlugin` API {#dropped-the-targetdependencypackageplugin-api}

Tuist 4-მდე პაკეტის პლაგინის დამოკიდებულების განსაზღვრა `TargetDependency.packagePlugin` ვარიანტის გამოყენებით შეიძლებოდა. Swift Package Manager-ის მიერ ახალი ტიპის პაკეტების წარმოჩენის შემდეგ, გადავწყვიტეთ API-ს განვითარება უფრო მოქნილი და მომავალზე ორიენტირებული მიდგომისკენ. თუ `TargetDependency.packagePlugin`-ს იყენებდით, მის ნაცვლად `TargetDependency.package` უნდა გამოიყენოთ და სასურველი პაკეტის ტიპი არგუმენტად გადასცეთ.
