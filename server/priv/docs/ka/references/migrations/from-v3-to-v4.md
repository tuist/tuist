# Tuist v3-დან v4-ზე {#from-tuist-v3-to-v4}

[Tuist 4](https://github.com/tuist/tuist/releases/tag/4.0.0)-ის გამოშვებასთან ერთად, ჩვენ გამოვიყენეთ შესაძლებლობა და პროექტში შევიტანეთ რიგი უთავსებელი ცვლილებები, რომლებიც, ჩვენი აზრით, პროექტის გამოყენებასა და მოვლას გრძელვადიან პერსპექტივაში გაამარტივებდა. ეს დოკუმენტი აღწერს იმ ცვლილებებს, რომლებიც თქვენს პროექტში უნდა განახორციელოთ Tuist 3-დან Tuist 4-ზე გადასვლისთვის.

## ვერსიების მართვა `tuistenv`-ის საშუალებით ამოღებულია {#dropped-version-management-through-tuistenv}

Tuist 4-მდე ინსტალაციის სკრიპტი აინსტალირებდა ინსტრუმენტს `tuistenv`, რომელიც ინსტალაციის დროს გადაერქმეოდა `tuist`-ად. ეს ინსტრუმენტი ზრუნავდა Tuist-ის ვერსიების ინსტალაციასა და აქტივაციაზე, რაც უზრუნველყოფდა დეტერმინიზმს სხვადასხვა გარემოში. Tuist-ის ფუნქციონალის შემცირების მიზნით, ჩვენ გადავწყვიტეთ `tuistenv`-ის ამოღება [Mise](https://mise.jdx.dev/)-ის სასარგებლოდ — ინსტრუმენტის, რომელიც იგივე სამუშაოს ასრულებს, მაგრამ უფრო მოქნილია და სხვადასხვა ინსტრუმენტთან ერთად შეიძლება მისი გამოყენება. თუ იყენებდით `tuistenv`, მოგიწევთ Tuist-ის მიმდინარე ვერსიის წაშლა `curl -Ls https://uninstall.tuist.io | bash`-ის გაშვებით და შემდეგ მისი ინსტალაცია თქვენთვის სასურველი მეთოდით. ჩვენ მკაცრად გირჩევთ Mise-ის გამოყენებას, რადგან ის სხვადასხვა გარემოში ვერსიების დეტერმინისტულად ინსტალაციასა და აქტივაციას უზრუნველყოფს.

```bash [Uninstall tuistenv]
curl -Ls https://uninstall.tuist.io | bash
```

## `init` კონსტრუქტორები ამოღებულია `ProjectDescription` მოდელებიდან {#dropped-init-constructors-from-projectdescription-models}

API-ების კითხვადობისა და გამომსახველობითობის გაუმჯობესების მიზნით, გადავწყვიტეთ `init` კონსტრუქტორების ამოღება ყველა `ProjectDescription` მოდელიდან. ახლა თითოეული მოდელი უზრუნველყოფს სტატიკურ კონსტრუქტორს, რომლის გამოყენებითაც შეგიძლიათ შექმნათ მოდელების ეგზემპლარები. თუ იყენებდით `init` კონსტრუქტორებს, მოგიწევთ თქვენი პროექტის განახლება სტატიკური კონსტრუქტორების გამოყენებისთვის.

> [!TIP]
> **სახელდების კონვენცია**
>
> ჩვენი მიმდევარი სახელდების კონვენცია გულისხმობს მოდელის სახელის გამოყენებას სტატიკური კონსტრუქტორის სახელად. მაგალითად, `Target` მოდელის სტატიკური კონსტრუქტორია `Target.target`.


## `--no-cache` გადაერქვა `--no-binary-cache`-ად {#renamed-nocache-to-nobinarycache}

რადგან `--no-cache` ფლაგი ორაზროვანი იყო, გადავწყვიტეთ მისი `--no-binary-cache`-ად გადაქცევა, რათა ცხადი ყოფილიყო, რომ ის ბინარულ ქეშს ეხება. თუ იყენებდით `--no-cache` ფლაგს, მოგიწევთ თქვენი პროექტის განახლება `--no-binary-cache` ფლაგის გამოყენებისთვის.

## `tuist fetch` გადაერქვა `tuist install`-ად {#renamed-tuist-fetch-to-tuist-install}

ბრძანება `tuist fetch` გადავარქვით `tuist install`-ად, რათა შესაბამისობაში მოგვეყვანა ის ინდუსტრიულ კონვენციასთან. თუ იყენებდით `tuist fetch` ბრძანებას, მოგიწევთ თქვენი პროექტის განახლება `tuist install` ბრძანების გამოყენებისთვის.

## [`Package.swift`-ის მიღება დამოკიდებულებების DSL-ად](https://github.com/tuist/tuist/pull/5862) {#adopt-packageswift-as-the-dsl-for-dependencieshttpsgithubcomtuisttuistpull5862}

Tuist 4-მდე დამოკიდებულებების განსაზღვრა შეგიძლიათ `Dependencies.swift` ფაილში. ამ პროპრიეტარულმა ფორმატმა დაარღვია მხარდაჭერა ისეთ ინსტრუმენტებში, როგორიცაა [Dependabot](https://github.com/dependabot) ან [Renovatebot](https://github.com/renovatebot/renovate), რათა დამოკიდებულებები ავტომატურად განახლებულიყო. ამასთან, მან შემოიტანა არასაჭირო შუამავლობები მომხმარებლებისთვის. ამიტომ, გადავწყვიტეთ `Package.swift`-ის მიღება Tuist-ში დამოკიდებულებების განსაზღვრის ერთადერთ გზად. თუ იყენებდით `Dependencies.swift` ფაილს, მოგიწევთ თქვენი `Tuist/Dependencies.swift`-ის შინაარსის გადატანა ძირში მდებარე `Package.swift`-ში და `#if TUIST` დირექტივის გამოყენება ინტეგრაციის კონფიგურაციისთვის. Swift Package დამოკიდებულებების ინტეგრაციის შესახებ მეტის წაკითხვა შეგიძლიათ <.localized_link href="/guides/features/projects/dependencies#swift-packages">აქ</.localized_link>

## `tuist cache warm` გადაერქვა `tuist cache`-ად {#renamed-tuist-cache-warm-to-tuist-cache}

მოკლე ფორმისთვის, გადავწყვიტეთ `tuist cache warm` ბრძანების `tuist cache`-ად გადაქცევა. თუ იყენებდით `tuist cache warm` ბრძანებას, მოგიწევთ თქვენი პროექტის განახლება `tuist cache` ბრძანების გამოყენებისთვის.


## `tuist cache print-hashes` გადაერქვა `tuist cache --print-hashes`-ად {#renamed-tuist-cache-printhashes-to-tuist-cache-printhashes}

გადავწყვიტეთ `tuist cache print-hashes` ბრძანების `tuist cache --print-hashes`-ად გადაქცევა, რათა ცხადი ყოფილიყო, რომ ის `tuist cache` ბრძანების ფლაგია. თუ იყენებდით `tuist cache print-hashes` ბრძანებას, მოგიწევთ თქვენი პროექტის განახლება `tuist cache --print-hashes` ფლაგის გამოყენებისთვის.

## ქეშირების პროფილები ამოღებულია {#removed-caching-profiles}

Tuist 4-მდე ქეშირების პროფილების განსაზღვრა შეგიძლიათ `Tuist/Config.swift`-ში, რომელიც შეიცავდა ქეშის კონფიგურაციას. გადავწყვიტეთ ამ ფუნქციის ამოღება, რადგან მისი გამოყენება გენერაციის პროცესში პროექტის გენერაციისთვის გამოყენებული პროფილისგან განსხვავებული პროფილით შეიძლება დაბნეულობას იწვევდეს. ამასთან, შეიძლება მომხმარებლები debug პროფილს იყენებდნენ აპლიკაციის release ვერსიის აგებისთვის, რაც მოულოდნელ შედეგებს გამოიწვევდა. მის ნაცვლად, ჩვენ შემოვიტანეთ `--configuration` ოფცია, რომლის გამოყენებითაც შეგიძლიათ მიუთითოთ კონფიგურაცია, რომელიც გსურთ პროექტის გენერაციისას. თუ იყენებდით ქეშირების პროფილებს, მოგიწევთ თქვენი პროექტის განახლება `--configuration` ოფციის გამოყენებისთვის.

## `--skip-cache` ამოღებულია არგუმენტების სასარგებლოდ {#removed-skipcache-in-favor-of-arguments}

ბრძანებიდან `generate` ამოღებულია ფლაგი `--skip-cache` იმის სასარგებლოდ, რომ არგუმენტების გამოყენებით კონტროლი განხორციელდეს, თუ რომელი target-ებისთვის უნდა გამოიტოვოს ბინარული ქეში. თუ იყენებდით `--skip-cache` ფლაგს, მოგიწევთ თქვენი პროექტის განახლება არგუმენტების გამოყენებისთვის.

```bash [Before]
tuist generate --skip-cache Foo
```

## [ხელმოწერის შესაძლებლობები ამოღებულია](https://github.com/tuist/tuist/pull/5716) {#dropped-signing-capabilitieshttpsgithubcomtuisttuistpull5716}

ხელმოწერა უკვე გადაწყვეტილია საზოგადოების ინსტრუმენტებით, როგორიცაა [Fastlane](https://fastlane.tools/) და თავად Xcode, რომლებიც ამას ბევრად უკეთესად აკეთებენ. ჩვენ ვგრძნობდით, რომ ხელმოწერა Tuist-ისთვის ზედმეტი ამბიცია იყო და უკეთესი იქნებოდა პროექტის ძირითად ფუნქციებზე ფოკუსირება. თუ იყენებდით Tuist-ის ხელმოწერის შესაძლებლობებს, რომელიც გულისხმობდა რეპოზიტორიაში სერტიფიკატებისა და პროფილების დაშიფვრას და გენერაციის დროს მათ სწორ ადგილებზე ინსტალაციას, შეიძლება მოგინდეთ ამ ლოგიკის გამეორება თქვენს საკუთარ სკრიპტებში, რომლებიც პროექტის გენერაციამდე გაეშვება. კერძოდ:
  - სკრიპტი, რომელიც შლის სერტიფიკატებსა და პროფილებს გასაღებით, რომელიც ან ფაილურ სისტემაშია შენახული, ან გარემოს ცვლადში, და აინსტალირებს სერტიფიკატებს keychain-ში, ხოლო პროვიზიონირების პროფილებს დირექტორიაში `~/Library/MobileDevice/Provisioning\ Profiles`.
  - სკრიპტი, რომელსაც შეუძლია არსებული პროფილებისა და სერტიფიკატების აღება და მათი დაშიფვრა.

> [!TIP]
> **ხელმოწერის მოთხოვნები**
>
> ხელმოწერას სჭირდება, რომ საჭირო სერტიფიკატები იყოს keychain-ში, ხოლო პროვიზიონირების პროფილები — დირექტორიაში `~/Library/MobileDevice/Provisioning\ Profiles`. სერტიფიკატების keychain-ში ინსტალაციისთვის შეგიძლიათ გამოიყენოთ `security` ბრძანების ხაზის ინსტრუმენტი, ხოლო პროვიზიონირების პროფილების სწორ დირექტორიაში დასაკოპირებლად — `cp` ბრძანება.


## Carthage-ის ინტეგრაცია `Dependencies.swift`-ის საშუალებით ამოღებულია {#dropped-carthage-integration-via-dependenciesswift}

Tuist 4-მდე Carthage-ის დამოკიდებულებების განსაზღვრა შესაძლებელი იყო `Dependencies.swift` ფაილში, რომლის მიღებაც მომხმარებლებს შეეძლოთ `tuist fetch` ბრძანების გაშვებით. ჩვენ ასევე ვფიქრობდით, რომ ეს Tuist-ისთვის ზედმეტად ამბიციური ამოცანა იყო, განსაკუთრებით იმ პერსპექტივის გათვალისწინებით, სადაც Swift Package Manager იქნება დამოკიდებულებების მართვის სასურველი გზა. თუ Carthage-ის დამოკიდებულებებს იყენებდით, მოგიწევთ `Carthage`-ის პირდაპირ გამოყენება წინასწარ კომპილირებული ფრეიმვორკებისა და XCFrameworks-ის Carthage-ის სტანდარტულ დირექტორიაში ჩამოსატვირთად, შემდეგ კი ამ ბინარული ფაილების თქვენს სამიზნეებზე (`TargetDependency.xcframework` და `TargetDependency.framework` კეისების საშუალებით) მითითება.

> [!NOTE]
> **Carthage კვლავ მხარდაჭერილია**
>
> ზოგიერთმა მომხმარებელმა იფიქრა, რომ Carthage-ის მხარდაჭერა შევწყვიტეთ. არ შეგვიწყვეტია. Tuist-სა და Carthage-ის გამომავალს შორის კონტრაქტი გულისხმობს სისტემაში შენახულ ფრეიმვორკებსა და XCFrameworks-ს. ერთადერთი რაც შეიცვალა, არის ის, თუ ვინ არის პასუხისმგებელი დამოკიდებულებების ჩამოტვირთვაზე. ადრე ეს იყო Tuist Carthage-ის საშუალებით, ახლა კი — Carthage.


## ამოღებულია `TargetDependency.packagePlugin` API {#dropped-the-targetdependencypackageplugin-api}

Tuist 4-მდე პაკეტის პლაგინის დამოკიდებულების განსაზღვრა შესაძლებელი იყო `TargetDependency.packagePlugin` კეისის გამოყენებით. Swift Package Manager-ის მიერ ახალი პაკეტის ტიპების შემოღების ნახვის შემდეგ, გადავწყვიტეთ API-ს იტერაციულად განვითარება უფრო მოქნილი და მომავლისთვის მზად მყოფი რამისკენ. თუ `TargetDependency.packagePlugin`-ს იყენებდით, მოგიწევთ `TargetDependency.package`-ის გამოყენება და სასურველი პაკეტის ტიპის არგუმენტად გადაცემა.

## [მოძველებული API-ები ამოღებულია](https://github.com/tuist/tuist/pull/5560) {#dropped-deprecated-apishttpsgithubcomtuisttuistpull5560}

ჩვენ ამოვიღეთ API-ები, რომლებიც Tuist 3-ში მოძველებულად იყო მონიშნული. თუ რომელიმე მოძველებულ API-ს იყენებდით, მოგიწევთ თქვენი პროექტის განახლება ახალი API-ების გამოყენებისთვის.
