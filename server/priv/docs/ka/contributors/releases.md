# რელიზები

Tuist ახალ ვერსიებს ავტომატურად აქვეყნებს, როდესაც ცვლილებები ერწყმის main შტოს. CLI, სერვერი და Kura ქეშ-სერვერი ყველა გამოიცემა რელიზის არხებით (canary, release candidate, stable), რათა რეკომენდებული ინსტალაცია დარჩეს სტაბილური და ნელა მოძრავი; release candidate-ის შექმნა და მისი stable-ში გადაყვანა განზრახული, ყოველკვირეული ნაბიჯებია. აპლიკაცია გამოიცემა უწყვეტად (iOS აპლიკაცია მხოლოდ უწყვეტად ნერგდება TestFlight-ზე, მეტი იხილეთ [აქ](#app-store-release)).

## მიმოხილვა

ჩვენ ვუშვებთ ამ ძირითად კომპონენტებს:
- **Tuist CLI** - ბრძანების ხაზის ინსტრუმენტი, რომელიც ვრცელდება canary, release candidate და stable [არხებით](#release-channels)
- **Tuist Server** - backend სერვისები, რომლებიც ვრცელდება CLI-ის იგივე არხის მოდელით
- **Kura** - ქეშ-სერვერი, რომელიც ვრცელდება CLI-ის იგივე არხის მოდელით
- **Tuist App** - macOS და iOS აპლიკაციები, რომლებიც გამოიცემა უწყვეტად (iOS აპლიკაცია მხოლოდ უწყვეტად ნერგდება TestFlight-ზე, მეტი იხილეთ [აქ](#app-store-release))

ყოველი push `main`-ზე აქვეყნებს canary პრერელიზს CLI-ისთვის, სერვერისთვის და Kura-სთვის. თითოეული ამ კომპონენტის stable რელიზი იქმნება მხოლოდ მაშინ, როდესაც მემარჩენელი წინასწარ გატესტილ release candidate-ს გადაჰყავს stable-ში, ხოლო ყოველკვირეული გრაფიკი სამივე „მატარებელს“ ერთდროულად აქტიურებს (იხილეთ [რელიზის არხები](#release-channels)). აპლიკაცია აქვეყნებს stable ვერსიას ყოველი push-ისას `main`-ზე.

## როგორ მუშაობს

### 1. კომიტების კონვენციები

ჩვენ ვიყენებთ [Conventional Commits](https://www.conventionalcommits.org/)-ს ჩვენი კომიტების შეტყობინებების სტრუქტურირებისთვის. ეს საშუალებას აძლევს ჩვენს ინსტრუმენტებს გაიგონ ცვლილებების ბუნება, განსაზღვრონ ვერსიის ზრდა და შექმნან შესაბამისი ცვლილებათა ჟურნალები.

ფორმატი: `type(scope): description`

#### კომიტის ტიპები და მათი გავლენა

| ტიპი | აღწერა | ვერსიის გავლენა | მაგალითი |
|------|-------------|----------------|---------|
| `feat` | ახალი ფუნქცია ან შესაძლებლობა | მცირე ვერსიის ზრდა (x.Y.z) | `feat(cli): add support for Swift 6` |
| `fix` | შეცდომის გამოსწორება | პატჩ ვერსიის ზრდა (x.y.Z) | `fix(app): resolve crash when opening projects` |
| `docs` | დოკუმენტაციის ცვლილებები | რელიზის გარეშე | `docs: update installation guide` |
| `style` | კოდის სტილის ცვლილებები | რელიზის გარეშე | `style: format code with swiftformat` |
| `refactor` | კოდის რეფაქტორინგი | რელიზის გარეშე | `refactor(server): simplify auth logic` |
| `perf` | წარმადობის გაუმჯობესება | პატჩ ვერსიის ზრდა | `perf(cli): optimize dependency resolution` |
| `test` | ტესტების დამატება/ცვლილება | რელიზის გარეშე | `test: add unit tests for cache` |
| `chore` | მოვლის ამოცანები | რელიზის გარეშე | `chore: update dependencies` |
| `ci` | CI/CD ცვლილებები | რელიზის გარეშე | `ci: add workflow for releases` |

CLI-ისთვის ეს ზრდები განსაზღვრავენ canary ვერსიას და ცვლილებათა ჟურნალის დაჯგუფებას. Stable CLI ვერსიები არის მცირე ხაზები (`X.Y.0`), რომლებიც ხელით იქმნება, ხოლო stable პატჩები (`X.Y.Z`) მოდის მხოლოდ backport-ებიდან, ამიტომ `feat` ან `fix` აღწევს CLI მომხმარებლებს ქვემოთ მოცემული არხის ნაკადით და არა როგორც უშუალო stable რელიზი.

#### დამრღვევი ცვლილებები

დამრღვევი ცვლილებები იწვევს ძირითადი ვერსიის ზრდას (X.0.0) და უნდა მიეთითოს კომიტის ტექსტში:

```
feat(cli): change default cache location

BREAKING CHANGE: The cache is now stored in ~/.tuist/cache instead of .tuist-cache.
Users will need to clear their old cache directory.
```

### 2. ცვლილებების აღმოჩენა

თითოეული კომპონენტი იყენებს [git cliff](https://git-cliff.org/)-ს:
- კომიტების ანალიზი ბოლო რელიზის შემდეგ
- კომიტების ფილტრაცია სკოპის მიხედვით (cli, app, server)
- განსაზღვრა, არის თუ არა რელიზისთვის ვარგისი ცვლილებები
- ცვლილებათა ჟურნალის ავტომატური გენერირება

### 3. რელიზის პაიპლაინი

როდესაც აღმოჩენილია რელიზისთვის ვარგისი ცვლილებები:

1. **ვერსიის გამოთვლა**: პაიპლაინი განსაზღვრავს მომდევნო ვერსიის ნომერს
2. **ცვლილებათა ჟურნალის გენერირება**: git cliff ქმნის ცვლილებათა ჟურნალს კომიტების შეტყობინებებიდან
3. **აგების პროცესი**: კომპონენტი იგება და იტესტება
4. **არტეფაქტების გენერირება**: იქმნება რელიზისთვის სპეციფიკური რესურსები, როგორიცაა CLI ბანდლები, საკონტროლო ჯამები და `tuist.spec.json` CLI სპეციფიკაცია, რომელიც გენერირდება `tuist --experimental-dump-help`-დან
5. **რელიზის შექმნა**: GitHub-ზე იქმნება რელიზი არტეფაქტებით
6. **გავრცელება**: განახლებები იგზავნება პაკეტების მენეჯერებში (მაგ., Homebrew CLI-ისთვის)

აპისთვის ეს წარმოქმნის stable რელიზს ყოველ შერწყმაზე. CLI-ის, სერვერისა და Kura-სთვის, იგივე ავტომატური პაიპლაინი წარმოქმნის მხოლოდ **canary** პრერელიზს; რელიზის კანდიდატები და stable რელიზები იქმნება ყოველკვირეულ რელიზის „მატარებელზე“ (იხ. [რელიზის არხები](#release-channels)).

### 4. სკოპის ფილტრაცია

თითოეული კომპონენტი აქვეყნებს რელიზს მხოლოდ მაშინ, როცა აქვს შესაბამისი ცვლილებები:

- **CLI**: კომიტები `(cli)` სკოპით ან სკოპის გარეშე
- **App**: კომიტები `(app)` სკოპით
- **Server**: კომიტები `(server)` სკოპით

## რელიზის არხები

CLI, სერვერი და Kura არ გადადიან stable რელიზზე `main`-ში ყოველი push-ის დროს. თითოეული გადის სამი არხის მეშვეობით, რათა რეკომენდებული ინსტალაცია დარჩეს stable და ნელი, ხოლო ადრეულმა მომხმარებლებმა შეინარჩუნონ კომიტზე დაფუძნებული აგებები. მომხმარებლისთვის ხელმისაწვდომი დოკუმენტაცია განთავსებულია <.localized_link href="/cli/release-channels">CLI რელიზის არხები</.localized_link> და <.localized_link href="/guides/server/self-host/release-channels">სერვერის რელიზის არხები</.localized_link>-ზე; ეს სექცია არის შემნახველის ინსტრუქცია.

თითოეული კომპონენტი იყენებს ერთსა და იმავე სამ არხს:

| არხი | ვერსია | შემქმნელი |
|---------|---------|--------|
| Canary | `X.Y.0-canary.N` | ავტომატურად, კომპონენტის შემხებელი ყოველი push-ის დროს `main`-ში (`<component>-release.yml`; Kura-სთვის, გამოძახებულია `server-production-deployment.yml`-ით, როცა `kura/` იცვლება) |
| რელიზის კანდიდატი | `X.Y.0-rc.N` | ყოველ ორშაბათს, ან ხელით, `releases/<component>-<major>.<minor>.x` ბრენჩზე (`<component>-rc.yml`) |
| Stable | `X.Y.Z` | ყოველ ორშაბათს, ან ხელით, გაჟღენთილი RC-ის პრომოუშენით (`<component>-promote.yml`); პატჩები `<component>-backport.yml`-ის მეშვეობით |

Canary და RC აგებები ქვეყნდება როგორც GitHub პრერელიზები (არასდროს მონიშნულია „Latest“-ად, არასდროს გადაადგილებს `:latest`-ს GHCR-ზე, არასდროს იგზავნება Homebrew-ში CLI-ისთვის), ამიტომ პაკეტების მენეჯერები და გამოსახულების რეზოლვერები მათ იღებენ მხოლოდ ცალსახა opt-in-ის დროს. Canary ყოველთვის ისახავს მიზნად შემდეგ გამოუქვეყნებელ მცირე ვერსიას: როგორც კი RC ხაზი შეიქმნება, `main`-ის canary გადადის შემდეგ მცირე ვერსიაზე.

Hosted Tuist არ ელოდება stable „მატარებელს“: სერვერი დეპლოიდება კომიტზე, ხოლო hosted canary და production უშვებენ Kura-ს უახლეს canary-ს. დეპლოის კასკადი აქვეყნებს ამ canary-ს თავად მის დეპლოიმდე, ამიტომ `kura-release.yml`-ს არ აქვს საკუთარი ტრიგერი. ცვლილებები მხოლოდ Kura-ს რელიზის ინსტრუმენტებში (`mise/tasks/kura/**`, `kura-*.yml` workflows) არ ქმნიან canary-ს.

თქვენ არასდროს ირჩევთ ვერსიის ნომრებს ხელით. თითოეული არხის მომდევნო ვერსია მიღებულია არსებული git ტეგებიდან `mise/tasks/<component>/release/channel-version.sh`-ით, რომელსაც ქვემოთ მოცემული workflows იძახებენ.

რელიზის ბრენჩები დაყოფილია კომპონენტების მიხედვით (`releases/server-X.Y.x`, `releases/kura-X.Y.x`, `releases/X.Y.x` CLI-ისთვის), რათა სამი კომპონენტის ხაზები არასდროს შეეჯახოს ერთსა და იმავე მცირე ვერსიაზე.

### ყოველკვირეული განრიგი

ყოველ ორშაბათს 06:00 UTC-ზე, სამი კომპონენტის promote სამუშაოები ერთდროულად გადის: **CLI Promote to Stable**, **Server Promote to Stable** და **Kura Promote to Stable**. თითოეული აკეთებს პრომოუშენს უახლესი RC ხაზის, რომელიც ჯერ არ არის stable, ჩვეულებრივ ეს არის წინა ორშაბათს შექმნილი ხაზი. თუ ასეთი ხაზი არ არსებობს, ეს სამუშაო არაფერს აქვეყნებს.

როდესაც promote სრულდება, შედეგის მიუხედავად, მისი შესაბამისი **რელიზის კანდიდატი** workflow (`cli-rc.yml`, `server-rc.yml`, `kura-rc.yml`) იწყება `workflow_run`-ის მეშვეობით და ქმნის შემდეგ ხაზს `main`-დან.

თუ რომელიმე დაგეგმილი გაშვება ვერ ხერხდება ან გაუქმდება, Slack-ზე იგზავნება შეტყობინება. პრომოუშენი ვერ ხერხდება, როცა რელიზის ბრენჩს აქვს კომიტები მისი უახლესი RC-ის შემდეგ. ამ ხაზის გასაშვებად, შექმენით მასზე ახალი RC და გააკეთეთ მისი პრომოუშენი ხელით. წინააღმდეგ შემთხვევაში, შემდეგ ორშაბათს პრომოუშენს გაუკეთებს უფრო ახალ ხაზს.

### რელიზის კანდიდატის შექმნა

ახალი ხაზის შესაქმნელად ყოველკვირეული განრიგის გარეთ (ჩაანაცვლეთ კომპონენტის workflow-ის სახელი ქვემოთ):

1. გაუშვით **\<Component\> Release Candidate** workflow (მაგალითად, `server-rc.yml`) ცარიელი `branch` შეყვანით.
2. ის აქვეყნებს `X.Y.0-rc.1` და, წარმატების შემდეგ, ქმნის დაცულ `releases/<component>-X.Y.x` ბრენჩს აწყობილ კომიტზე.

კრიტიკული ფიქსის ან რეგრესიის „დასალბად“ ხაზში ჩასართავად, cherry-pick გააკეთეთ მისი რელიზის ბრენჩზე PR-ის მეშვეობით (იგივე ნაკადი, რაც backport-ებისთვის; CI არასდროს აკეთებს cherry-pick-ს), შემდეგ კი გაიმეორეთ RC:

1. გადახტით `releases/<component>-X.Y.x`-დან, გააკეთეთ ფიქსის cherry-pick, გახსენით PR უკან რელიზის ბრენჩში, მოაგვარეთ ნებისმიერი კონფლიქტი და გააერთიანეთ.
2. გაუშვით **Release Candidate** workflow კვლავ `branch=releases/<component>-X.Y.x`-ით. ის აქვეყნებს `X.Y.0-rc.(N+1)`-ს ბრენჩის HEAD-დან.

„დასალბადი“ ხაზი არის ფუნქციებით გაყინული: მასზე მხოლოდ კრიტიკული ფიქსები და რეგრესიები ხვდება.

### Stable-ზე გადაყვანა

ხაზის stable-ზე გადასაყვანად ყოველკვირეული განრიგის გარეთ, მისი RC-ის სუფთად „დასალბვის“ შემდეგ:

1. გაუშვით **\<Component\> Promote to Stable** workflow (მაგალითად, `server-promote.yml`) `branch=releases/<component>-X.Y.x`-ით.
2. ის აქვეყნებს semver-ით მონიშნულ image-ს `make_latest=true`-ით, გადააქვს GHCR `:latest` ტეგი და GitHub-ის „Latest“ მაჩვენებელი. CLI ასევე ანახლებს Homebrew ფორმულას.

პრომოუშენი არ გაეშვება, თუ ბრენჩის HEAD ზუსტად არ ემთხვევა კომიტს, რომელზეც უახლესი RC მიუთითებს. ამიტომ, თუ ბოლო RC-ის შემდეგ ხაზზე რაიმე ფიქსი გაერთიანდა, უნდა შექმნათ ახალი RC და მისცეთ მას „დასალბვის“ დრო, სანამ ის stable-ად გამოიცემა.

### ფიქსების backport-ი stable ხაზზე

როგორც კი ხაზი stable ხდება, პატჩები გამოიცემა მხოლოდ CLI-ისთვის განკუთვნილი **Backport Release** workflow-ით (`cli-backport.yml`): გააკეთეთ ფიქსის cherry-pick `releases/X.Y.x`-ზე PR-ის მეშვეობით, შემდეგ გაუშვით workflow ამ ბრენჩით, რათა შეიქმნას `X.Y.(Z+1)`. Backport-ები არასდროს გადააადგილებენ „Latest“ მაჩვენებელს ან Homebrew ფორმულას. ერთდროულად ორი ხაზი ინახება: მიმდინარე ხაზი იღებს რეგრესიებს და უსაფრთხოების ფიქსებს, წინა ხაზი კი — მხოლოდ კრიტიკულ და უსაფრთხოების ფიქსებს. სხვა ბაგ-ფიქსები არ backport-დება და გამოიცემა შემდეგ მცირე ვერსიასთან ერთად.

სერვერისა და Kura-სთვის გამოიყენეთ **Server Backport Release** (`server-backport.yml`) ან **Kura Backport Release** (`kura-backport.yml`). პრომოუშენი აქვეყნებს მხოლოდ RC-ის `X.Y.0`-ს; მას არ შეუძლია უკვე stable ხაზის პატჩირება.

1. დაიწყეთ შერჩეული `X.Y` ხაზის უახლესი გამოქვეყნებული stable კომპონენტის ტეგიდან და გახსენით ქირურგიული ფიქსის PR მის არსებულ `releases/server-X.Y.x` ან `releases/kura-X.Y.x` ბრენჩში. უფრო ახალი მცირე ან ძირითადი რელიზი არ ხელს უშლის შენარჩუნებული ხაზის პატჩირებას. თავი შეიკავეთ main-ის არარელევანტური ცვლილებებისგან.
2. გადაამოწმეთ და გააერთიანეთ წყაროს PR. ჩამოტვირთეთ დისტანციური რელიზის ბრენჩი და დააკვალიფიცირეთ მისი **საბოლოო გაერთიანებული tip**, კომპონენტის მხარდაჭერილი პლატფორმებისა და TLS დადებითი/უარყოფითი კონტროლების ჩათვლით. წინა-გაერთიანების წარმატებული head არ არის სხვა squash ან merge კომიტის კვალიფიკაცია.
3. ცალკეული გამოქვეყნების დამტკიცებით, გაუშვით შესაბამისი backport workflow **main-დან**, `source_sha`-ის მითითებით ზუსტად იმ კვალიფიცირებულ გაერთიანებულ tip-ზე და `base_tag`-ის მითითებით მიმდინარე stable ტეგზე, როგორიცაა `server@X.Y.Z` ან `kura@X.Y.Z`. workflow გამოიყვანს `X.Y.(Z+1)`-ს; ოპერატორები არ ირჩევენ მცირე ვერსიის აწევას ან canary შიგთავსის პრომოუშენს.

დაგეგმვა ანახლებს ზუსტ დისტანციურ ბრენჩსა და საბაზო ტეგს, მოითხოვს, რომ შერჩეული წყარო ემთხვეოდეს ბრენჩის tip-ს, უარყოფს შეუცვლელ წყაროს ან კომპონენტის გარეთ ცვლილებებს, მის trust-policy შეყვანებსა და ვალიდაციას, და აფიქსირებს გადაწყვეტილ საბაზო კომიტს. Main-დან მიღებული კონტროლები იმეორებენ ამ შემოწმებებს ვერსიირებული image-ისა და GitHub-ზე გამოქვეყნებამდე. თუ წყაროს ბრენჩი, stable საბაზო ან ხელმისაწვდომი ვერსია შეიცვლება, შეწყვიტეთ და ხელახლა დააკვალიფიცირეთ, ნაცვლად ახალი წყაროს ჩანაცვლებისა.

Backport-ები იყენებენ არსებულ მრავალპლატფორმიან გამომქვეყნებლებს GitHub-ის „Latest“ მაჩვენებლის ან GHCR `:latest`-ის გადაადგილების გარეშე. გამოქვეყნება გამოყოფილია hosted განლაგებისგან: ეს workflow-ები არ აკეთებენ hosted სერვერის ან Kura ფლოტის პრომოუშენს, არ უვლიან გვერდს canary მიღებას ან არ აკვალიფიცირებენ ინსტალირებულ runtime-ს. Build-ის დამხმარე საშუალებები და Dockerfiles კვლავ მოდის შერჩეული stable წყაროდან. კონტროლები არის გამოქვეყნების კარიბჭეები და არა credential-free build სამუშაოები; builds-ებს შეუძლიათ ატვირთონ untagged image digests საბოლოო კარიბჭემდე. Image-ისა და GitHub-ის გამოქვეყნება არ არის ატომური: თუ გვიანდელი კარიბჭე ვერ ხერხდება image ტეგის გამოქვეყნების შემდეგ, შეამოწმეთ ნაწილობრივი რელიზი და შეინარჩუნეთ მისი საწყისი წყარო და არტეფაქტები. არასდროს ჩაანაცვლოთ არსებული რელიზი ან არ გამოიყენოთ სხვა ბაიტები მისი ტეგის ქვეშ.

## კარგი კომიტის შეტყობინებების წერა

ვინაიდან კომიტის შეტყობინებები პირდაპირ მოქმედებს რელიზის შენიშვნებზე, მნიშვნელოვანია ნათელი, აღმწერი შეტყობინებების წერა:

### გააკეთეთ:
- გამოიყენეთ აწმყო დრო: „add feature“ და არა „added feature“
- იყავით მოკლე, მაგრამ აღმწერი
- ჩართეთ სფერო, როცა ცვლილებები კომპონენტზეა დამოკიდებული
- მიუთითეთ საკითხები, როცა შესაბამისია: `fix(cli): resolve build cache issue (#1234)`

### არ გააკეთოთ:
- არ გამოიყენოთ ბუნდოვანი შეტყობინებები, როგორიცაა „fix bug“ ან „update code“
- არ აურიოთ რამდენიმე არარელევანტური ცვლილება ერთ კომიტში
- არ დაგავიწყდეთ breaking change ინფორმაციის ჩართვა

### Breaking changes

Breaking changes-ისთვის, ჩართეთ `BREAKING CHANGE:` კომიტის სხეულში:

```
feat(cli): change cache directory structure

BREAKING CHANGE: Cache files are now stored in a new directory structure.
Users need to clear their cache after updating.
```

## რელიზის workflow-ები

CLI-ს, სერვერსა და Kura-ს თითოეულს აქვს საკუთარი არხის workflow-ების ნაკრები, იგივე სტრუქტურის მიხედვით:

- `<component>-release.yml` - აქვეყნებს canary-ს `main`-ზე ყოველი კომპონენტის შეხების push-ზე (Kura-ს არის ხელახლა გამოყენებადი workflow, რომელსაც `server-production-deployment.yml` იძახებს, როცა `kura/` შეიცვლება)
- `<component>-rc.yml` - ქმნის რელიზის კანდიდატს ყოველ ორშაბათს (`workflow_run`-ის მეშვეობით promote-ის შემდეგ), ან ხელით ქმნის ან აუმჯობესებს ერთ-ერთს
- `<component>-promote.yml` - აკეთებს პრომოუშენს მოლოდინში მყოფი RC-ის stable-ზე ყოველ ორშაბათს 06:00 UTC-ზე, ან ხელით აკეთებს პრომოუშენს „დასალბულ“ RC-ზე
- `<component>-build-publish.yml` - საერთო build და publish pipeline, რომელსაც ზემოთ ჩამოთვლილი სამი იძახებს

CLI-ს, სერვერსა და Kura-ს ასევე აქვთ `<component>-backport.yml` stable ხაზზე პატჩების შესაქმნელად. კომპონენტის ყველა workflow სერიალიზდება ერთი `<component>-publish` concurrency ჯგუფის მეშვეობით, რათა ვერსიის გადაწყვეტა და ტეგირება არასდროს შეჯახდეს. Kura არის გამონაკლისი: მისი canary იყენებს `kura-canary-publish`-ს, ხოლო მისი RC, promote და backport იყენებენ `kura-stable-publish`-ს, რათა ხანგრძლივმა stable build-მა არ შეაფერხოს განლაგების კასკადი. ტეგის სივრცეები დისიუნქტურია, ამიტომ ორი ჯგუფი ვერ შეეჯახება.

Helm-ის ჩარტი და ინფრასტრუქტურის გამოსახულებები (CAPI ოპერატორი, runners კონტროლერი, xcresult პროცესორის გამოსახულება, linux runner-ის გამოსახულება და ა.შ.) კვლავ გამოიცემა `.github/workflows/server-production-deployment.yml`-ის მეშვეობით. ის მუშაობს `main`-ზე push-ების დროს და უზრუნველყოფს canary → მიღების ტესტები → production კასკადს hosted განლაგებისთვის, ასევე აქვეყნებს ამ ინფრასტრუქტურულ კომპონენტებს მათი ცვლილების შესაბამისად. აპლიკაციას, cache-ს, Gradle პლაგინს, skills-ს, Noora-ს და დამოუკიდებელ ინფრასტრუქტურის კონტროლერებს თითოეულს აქვს საკუთარი `*-release.yml` workflow. ყველა მათგანი იყენებს საერთო ცვლილებების აღმოჩენას: `mise/tasks/release/components.json` განსაზღვრავს თითოეული კომპონენტის ტეგის პრეფიქსს და include ბილიკებს, ხოლო git cliff გარდაქმნის შესაბამის კომიტებს რელიზის შენიშვნებად.

CLI-ის build (`cli-build-publish.yml`) ასევე ქმნის და აქვეყნებს `tuist.spec.json` არტეფაქტს (გენერირებულია `tuist --experimental-dump-help`-დან), რათა downstream ინსტრუმენტებმა შეძლონ ბრძანების ინტერფეისის გამოყენება.

## პრობლემების გადაჭრა

თუ რელიზი ვერ მოხერხდა:

1. შეამოწმეთ GitHub Actions ლოგები წარუმატებელი workflow-სთვის
2. დარწმუნდით, რომ თქვენი კომიტის შეტყობინებები მიჰყვებიან კონვენციურ ფორმატს
3. დაადასტურეთ, რომ ყველა ტესტი გადის
4. შეამოწმეთ, რომ კომპონენტი წარმატებით აშენდება

სასწრაფო შესწორებებისთვის, რომლებსაც სჭირდებათ დაუყოვნებელი რელიზი:
1. დარწმუნდით, რომ თქვენს კომიტს აქვს ნათელი სკოუპი
2. შერწყმის შემდეგ, აკვირდით რელიზის workflow-ს
3. სერვერის ან აპლიკაციისთვის, შესწორება გამოიცემა შემდეგ push-ზე; საჭიროების შემთხვევაში, გაუშვით ხელით რელიზი
4. CLI-სთვის, შესწორება ავტომატურად ხვდება canary-ზე. stable მომხმარებლებისთვის მისაღებად, გააკეთეთ backport შენარჩუნებულ stable ხაზ(ებ)ზე (იხილეთ [Backporting fixes to a stable line](#backporting-fixes-to-a-stable-line))

## App Store რელიზი

მიუხედავად იმისა, რომ CLI და სერვერი მიჰყვებიან ზემოთ აღწერილ უწყვეტ რელიზის პროცესს, **iOS აპლიკაცია** არის გამონაკლისი Apple-ის App Store განხილვის პროცესის გამო:

- **ხელით რელიზები**: iOS აპლიკაციის რელიზები მოითხოვს ხელით წარდგენას App Store-ში
- **განხილვის დაყოვნებები**: თითოეული რელიზი უნდა გაიაროს Apple-ის განხილვის პროცესი, რასაც შეიძლება 1-7 დღე დასჭირდეს
- **ჯგუფური ცვლილებები**: მრავალი ცვლილება ჩვეულებრივ ერთად იკვრება თითოეულ iOS რელიზში
- **TestFlight**: ბეტა ვერსიები შეიძლება გავრცელდეს TestFlight-ის მეშვეობით App Store რელიზამდე
- **რელიზის შენიშვნები**: უნდა დაიწეროს სპეციფიკურად App Store-ის სახელმძღვანელო მითითებებისთვის

iOS აპლიკაცია კვლავ მიჰყვება იგივე კომიტის კონვენციებს და იყენებს git cliff-ს changelog-ის გენერირებისთვის, მაგრამ რეალური რელიზი მომხმარებლებისთვის ხდება ნაკლებად ხშირ, ხელით გრაფიკზე.
