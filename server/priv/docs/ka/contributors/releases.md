# გამოშვებები

Tuist ახალ ვერსიებს ავტომატურად აქვეყნებს, როდესაც ცვლილებები main შტოს უერთდება. CLI, სერვერი და Kura ქეშ-სერვერი ყველა გამოშვების არხებით (canary, release candidate, stable) ვრცელდება, რათა რეკომენდებული ინსტალაცია სტაბილური და ნელი იყოს; release candidate-ის მომზადება და მისი stable-ში გადაყვანა განზრახული, კვირითი ნაბიჯებია. აპლიკაცია უწყვეტად გამოიცემა (iOS აპლიკაცია მხოლოდ TestFlight-ზე განთავსდება უწყვეტად, მეტი იხილეთ [აქ](#app-store-release)).

## მიმოხილვა

ჩვენ ვუშვებთ ამ ძირითად კომპონენტებს:
- **Tuist CLI** - ბრძანების ხაზის ინსტრუმენტი, რომელიც ვრცელდება canary, release candidate და stable [არხებით](#release-channels)
- **Tuist Server** - backend სერვისები, რომლებიც ვრცელდება CLI-ის მსგავსი არხების მოდელით
- **Kura** - ქეშ-სერვერი, რომელიც ვრცელდება CLI-ის მსგავსი არხების მოდელით
- **Tuist App** - macOS და iOS აპლიკაციები, რომლებიც უწყვეტად გამოიცემა (iOS აპლიკაცია მხოლოდ TestFlight-ზე განთავსდება უწყვეტად, მეტი იხილეთ [აქ](#app-store-release))

ყოველი push `main`-ზე აქვეყნებს canary წინასწარ გამოშვებას CLI-ისთვის, სერვერისთვის და Kura-სთვის. თითოეული ამ კომპონენტის სტაბილური გამოშვება მზადდება მხოლოდ მაშინ, როდესაც შენარჩუნების პასუხისმგებელი პირი soaked release candidate-ს stable-ში გადაჰყავს, და კვირითი გრაფიკი სამივე „მატარებელს“ ერთდროულად აშვებს (იხილეთ [გამოშვების არხები](#release-channels)). აპლიკაცია stable-ს აქვეყნებს ყოველ push-ზე `main`-ზე.

## როგორ მუშაობს

### 1. კომიტის კონვენციები

ჩვენ ვიყენებთ [Conventional Commits](https://www.conventionalcommits.org/)-ს ჩვენი კომიტების შეტყობინებების სტრუქტურირებისთვის. ეს საშუალებას აძლევს ჩვენს ინსტრუმენტებს გაიგონ ცვლილებების ბუნება, განსაზღვრონ ვერსიის ზრდა და შექმნან შესაბამისი ცვლილებების ჟურნალები.

ფორმატი: `type(scope): description`

#### კომიტის ტიპები და მათი გავლენა

| ტიპი | აღწერა | ვერსიის გავლენა | მაგალითი |
|------|-------------|----------------|---------|
| `feat` | ახალი ფუნქცია ან შესაძლებლობა | მცირე ვერსიის ზრდა (x.Y.z) | `feat(cli): add support for Swift 6` |
| `fix` | შეცდომის გამოსწორება | patch ვერსიის ზრდა (x.y.Z) | `fix(app): resolve crash when opening projects` |
| `docs` | დოკუმენტაციის ცვლილებები | გამოშვება არ ხდება | `docs: update installation guide` |
| `style` | კოდის სტილის ცვლილებები | გამოშვება არ ხდება | `style: format code with swiftformat` |
| `refactor` | კოდის რეფაქტორინგი | გამოშვება არ ხდება | `refactor(server): simplify auth logic` |
| `perf` | წარმადობის გაუმჯობესება | patch ვერსიის ზრდა | `perf(cli): optimize dependency resolution` |
| `test` | ტესტების დამატება/ცვლილება | გამოშვება არ ხდება | `test: add unit tests for cache` |
| `chore` | მომსახურების ამოცანები | გამოშვება არ ხდება | `chore: update dependencies` |
| `ci` | CI/CD ცვლილებები | გამოშვება არ ხდება | `ci: add workflow for releases` |

CLI-ისთვის, ეს ზრდები განსაზღვრავენ canary ვერსიას და ცვლილებების ჟურნალის დაჯგუფებას. სტაბილური CLI ვერსიები არის მცირე ხაზები (`X.Y.0`), რომლებიც ხელით მზადდება, და სტაბილური patches (`X.Y.Z`) მოდის მხოლოდ backport-ებიდან, ასე რომ `feat` ან `fix` აღწევს CLI მომხმარებლებს ქვემოთ მოცემული არხების ნაკადით და არა როგორც დაუყოვნებელი სტაბილური გამოშვება.

#### დამრღვევი ცვლილებები

დამრღვევი ცვლილებები იწვევს ძირითადი ვერსიის ზრდას (X.0.0) და უნდა იყოს მითითებული კომიტის ძირითად ნაწილში:

```
feat(cli): change default cache location

BREAKING CHANGE: The cache is now stored in ~/.tuist/cache instead of .tuist-cache.
Users will need to clear their old cache directory.
```

თითოეული კომპონენტი იყენებს [git cliff](https://git-cliff.org/)-ს, რათა:
- გაანალიზოს კომიტები ბოლო გამოშვების შემდეგ
- გაფილტროს კომიტები სკოპის მიხედვით (cli, app, server)
- დაადგინოს, არის თუ არა გამოსაქვეყნებელი ცვლილებები
- ავტომატურად შექმნას ცვლილებების ჟურნალები

### 3. გამოშვების პაიპლაინი

როდესაც აღმოჩნდება გამოსაქვეყნებელი ცვლილებები:

1. **ვერსიის გამოთვლა**: პაიპლაინი განსაზღვრავს შემდეგი ვერსიის ნომერს
2. **ცვლილებების ჟურნალის გენერირება**: git cliff ქმნის ცვლილებების ჟურნალს კომიტების შეტყობინებებიდან
3. **აგების პროცესი**: კომპონენტი აგებული და ტესტირებულია
4. **არტეფაქტების გენერირება**: მზადდება გამოშვებისთვის სპეციფიკური რესურსები, როგორიცაა CLI ბანდლები, საკონტროლო ჯამები და `tuist.spec.json` CLI სპეციფიკაცია, რომელიც გენერირდება `tuist --experimental-dump-help`-დან
5. **გამოშვების შექმნა**: იქმნება GitHub გამოშვება არტეფაქტებით
6. **გავრცელება**: განახლებები იგზავნება პაკეტების მენეჯერებში (მაგ., Homebrew CLI-ისთვის)

აპისთვის ეს წარმოქმნის სტაბილურ გამოშვებას ყოველ შერწყმაზე. CLI-ის, სერვერისა და Kura-სთვის, იგივე ავტომატური პაიპლაინი ქმნის მხოლოდ **canary** წინასწარ გამოშვებას; რელიზის კანდიდატები და სტაბილური გამოშვებები მზადდება ყოველკვირეული რელიზის მატარებელზე (იხ. [გამოშვების არხები](#release-channels)).

### 4. სკოპის ფილტრაცია

თითოეული კომპონენტი გამოიცემა მხოლოდ მაშინ, როდესაც მას აქვს შესაბამისი ცვლილებები:

- **CLI**: კომიტები `(cli)` სკოპით ან სკოპის გარეშე
- **App**: კომიტები `(app)` სკოპით
- **Server**: კომიტები `(server)` სკოპით

## გამოშვების არხები

CLI, სერვერი და Kura არ გადადიან სტაბილურ გამოშვებაზე `main`-ში ყოველი push-ის შემდეგ. თითოეული გადის სამი არხის მეშვეობით, რათა რეკომენდებული ინსტალაცია დარჩეს სტაბილური და ნელა მოძრავი, ხოლო ადრეულმა მომხმარებლებმა შეინარჩუნონ კომიტზე დაფუძნებული აგებები. მომხმარებლისთვის განკუთვნილი დოკუმენტაცია განთავსებულია <.localized_link href="/cli/release/channels">CLI გამოშვების არხებზე</.localized_link> და <.localized_link href="/guides/server/self-host/release/channels">სერვერის გამოშვების არხებზე</.localized_link>; ეს სექცია არის შემნახველის ინსტრუქცია.

თითოეული კომპონენტი იყენებს ერთსა და იმავე სამ არხს:

| არხი | ვერსია | მზადდება |
|---------|---------|--------|
| Canary | `X.Y.0-canary.N` | ავტომატურად, კომპონენტის შემხებელი ყოველი push-ისას `main`-ში (`<component>-release.yml`; Kura-სთვის, გამოძახებულია `server-production-deployment.yml`-ით, როდესაც `kura/` იცვლება) |
| რელიზის კანდიდატი | `X.Y.0-rc.N` | ყოველ ორშაბათს, ან ხელით, `releases/<component>-<major>.<minor>.x` ბრენჩზე (`<component>-rc.yml`) |
| სტაბილური | `X.Y.Z` | ყოველ ორშაბათს, ან ხელით, გაჟღენთილი RC-ის პრომოუშენით (`<component>-promote.yml`); patches `<component>-backport.yml`-ის მეშვეობით |

Canary და RC აგებები ქვეყნდება როგორც GitHub წინასწარ გამოშვებები (არასდროს მონიშნულია როგორც "Latest", არასდროს გადაადგილებს `:latest`-ს GHCR-ზე, არასდროს იგზავნება Homebrew-ში CLI-ისთვის), ამიტომ პაკეტების მენეჯერები და image resolver-ები მათ იღებენ მხოლოდ ცალსახა opt-in-ის შემთხვევაში. Canary ყოველთვის ისახავს მიზნად შემდეგ გამოუქვეყნებელ minor-ს: როგორც კი RC ხაზი მზადდება, `main`-ის canary გადადის შემდეგ minor-ზე.

Hosted Tuist არ ელოდება სტაბილურ მატარებელს: სერვერი განთავსდება კომიტზე, ხოლო hosted canary და production აწარმოებს უახლეს Kura canary-ს. განთავსების კასკადი აქვეყნებს ამ canary-ს თავად მის განთავსებამდე, ამიტომ `kura-release.yml`-ს არ აქვს საკუთარი ტრიგერი. ცვლილებები მხოლოდ Kura-ს გამოშვების ინსტრუმენტებში (`mise/tasks/kura/**`, `kura-*.yml` workflows) არ ქმნის canary-ს.

თქვენ არასდროს ირჩევთ ვერსიის ნომრებს ხელით. თითოეული არხის შემდეგი ვერსია მიღებულია არსებული git ტეგებიდან `mise/tasks/<component>/release/channel-version.sh`-ის მეშვეობით, რომელსაც ქვემოთ მოცემული workflows იყენებენ.

გამოშვების ბრენჩები დაყოფილია კომპონენტების მიხედვით (`releases/server-X.Y.x`, `releases/kura-X.Y.x`, `releases/X.Y.x` CLI-ისთვის), რათა სამი კომპონენტის ხაზები არასდროს ემთხვეოდეს ერთსა და იმავე minor-ზე.

### ყოველკვირეული გრაფიკი

ყოველ ორშაბათს 06:00 UTC-ზე, სამი კომპონენტის promote სამუშაოები მუშაობენ სინქრონულად: **CLI Promote to Stable**, **Server Promote to Stable** და **Kura Promote to Stable**. თითოეული აწინაურებს უახლეს RC ხაზს, რომელიც ჯერ არ არის სტაბილური, რაც ჩვეულებრივ არის წინა ორშაბათს შექმნილი ხაზი. თუ ასეთი ხაზი არ არსებობს, ეს სამუშაო არაფერს აქვეყნებს.

როდესაც promote სრულდება, შედეგის მიუხედავად, მისი შესაბამისი **Release Candidate** workflow (`cli-rc.yml`, `server-rc.yml`, `kura-rc.yml`) იწყება `workflow_run`-ის მეშვეობით და ქმნის შემდეგ ხაზს `main`-დან.

თუ რომელიმე დაგეგმილი გაშვება ვერ ხერხდება ან გაუქმებულია, Slack-ზე იგზავნება შეტყობინება. პრომოუშენი ვერ ხერხდება, როდესაც გამოშვების ბრენჩს აქვს კომიტები მისი უახლესი RC-ის შემდეგ. ამ ხაზის გამოსაქვეყნებლად, შექმენით მასზე ახალი RC და ხელით გააკეთეთ მისი პრომოუშენი. წინააღმდეგ შემთხვევაში, შემდეგ ორშაბათს უფრო ახალი ხაზი აწინაურდება.

### რელიზის კანდიდატის შექმნა

ახალი ხაზის შესაქმნელად ყოველკვირეული გრაფიკის მიღმა (ჩაანაცვლეთ კომპონენტის workflow-ს სახელი ქვემოთ):

1. გაუშვით **\<Component\> Release Candidate** workflow (მაგალითად, `server-rc.yml`) ცარიელი `branch` შეყვანით.
2. ის აქვეყნებს `X.Y.0-rc.1` და, წარმატების შემდეგ, ქმნის დაცულ `releases/<component>-X.Y.x` ბრენჩს აგებულ კომიტზე.

კრიტიკული გამოსწორების ან რეგრესიის „ soaking“ ხაზში ჩასართავად, გააკეთეთ მისი cherry-pick გამოშვების ბრენჩზე PR-ის მეშვეობით (იგივე ნაკადი, რაც backport-ებისთვის; CI არასდროს აკეთებს cherry-pick-ს), შემდეგ კი განაახლეთ RC:

1. გადაერთეთ `releases/<component>-X.Y.x`-დან, გააკეთეთ გამოსწორების cherry-pick, გახსენით PR უკან გამოშვების ბრენჩში, გადაწყვიტეთ ნებისმიერი კონფლიქტი და გააერთიანეთ.
2. კვლავ გაუშვით **Release Candidate** workflow `branch=releases/<component>-X.Y.x`-ით. ის აქვეყნებს `X.Y.0-rc.(N+1)`-ს ბრენჩის HEAD-დან.

„Soaking“ ხაზი არის ფუნქციურად გაყინული: მასზე მხოლოდ კრიტიკული გამოსწორებები და რეგრესიები ხვდება.

### სტაბილურ ვერსიაზე გადაყვანა

ხაზის სტაბილურად გადასაყვანად ყოველკვირეული გრაფიკის მიღმა, მისი RC-ის წარმატებული „soaking“-ის შემდეგ:

1. გაუშვით **\<Component\> Promote to Stable** workflow (მაგალითად, `server-promote.yml`) `branch=releases/<component>-X.Y.x`-ით.
2. ის აქვეყნებს semver-ით მონიშნულ იმიჯს `make_latest=true`-ით, გადააქვს GHCR `:latest` ტეგი და GitHub-ის „Latest“ მაჩვენებელი. CLI ასევე ანახლებს Homebrew ფორმულას.

პრომოუშენი არ გაეშვება, თუ ბრენჩის HEAD ზუსტად არ ემთხვევა კომიტს, რომელზეც უახლესი RC მიუთითებს. ამიტომ, თუ ბოლო RC-ის შემდეგ ხაზზე რაიმე გამოსწორება გაერთიანდა, უნდა შექმნათ ახალი RC და დაუშვათ მისი „soaking“, სანამ ის სტაბილურად გამოქვეყნდება.

### გამოსწორებების backport-ი სტაბილურ ხაზზე

როდესაც ხაზი სტაბილური ხდება, პატჩები გამოაქვეყნეთ მხოლოდ CLI-ისთვის განკუთვნილი **Backport Release** workflow-ით (`cli-backport.yml`): გააკეთეთ გამოსწორების cherry-pick `releases/X.Y.x`-ზე PR-ის მეშვეობით, შემდეგ კი გაუშვით workflow ამ ბრენჩით `X.Y.(Z+1)`-ის შესაქმნელად. Backport-ები არასდროს გადააქვთ „Latest“ მაჩვენებელს ან Homebrew ფორმულას. ერთდროულად ორი ხაზი ნარჩუნდება: მიმდინარე ხაზი იღებს რეგრესიებსა და უსაფრთხოების გამოსწორებებს, წინა ხაზი კი — მხოლოდ კრიტიკულ და უსაფრთხოების გამოსწორებებს. სხვა შეცდომების გამოსწორებები არ გადააქვთ და ისინი შემდეგ minor ვერსიასთან ერთად გამოიცემა.

სერვერისა და Kura-სთვის გამოიყენეთ **Server Backport Release** (`server-backport.yml`) ან **Kura Backport Release** (`kura-backport.yml`). პრომოუშენი აქვეყნებს მხოლოდ RC-ის `X.Y.0`-ს; მას არ შეუძლია უკვე სტაბილური ხაზის პატჩირება.

1. დაიწყეთ არჩეული `X.Y` ხაზის უახლესი გამოქვეყნებული სტაბილური კომპონენტის ტეგიდან და გახსენით ზუსტი გამოსწორების PR მის არსებულ `releases/server-X.Y.x` ან `releases/kura-X.Y.x` ბრენჩში. უფრო ახალი minor ან major გამოშვება არ ხელს უშლის შენარჩუნებული ხაზის პატჩირებას. თავი შეიკავეთ main-ის არარელევანტური ცვლილებებისგან.
2. გადაამოწმეთ და გააერთიანეთ წყაროს PR. ჩამოტვირთეთ დისტანციური გამოშვების ბრენჩი და დაადასტურეთ მისი **საბოლოო გაერთიანებული tip**, კომპონენტის მხარდაჭერილი პლატფორმებისა და TLS დადებითი/უარყოფითი კონტროლების ჩათვლით. წარმატებული pre-merge head არ არის სხვა squash ან merge კომიტის დადასტურება.
3. ცალკეული გამოქვეყნების დადასტურებით, გაუშვით შესაბამისი backport workflow **main-დან**, `source_sha`-ის მითითებით ზუსტად იმ დადასტურებულ გაერთიანებულ tip-ზე და `base_tag`-ის მითითებით მიმდინარე სტაბილურ ტეგზე, როგორიცაა `server@X.Y.Z` ან `kura@X.Y.Z`. workflow გამოიყვანს `X.Y.(Z+1)`-ს; ოპერატორები არ ირჩევენ minor-ის აწევას ან canary შიგთავსის პრომოუშენს.

დაგეგმვა ანახლებს ზუსტ დისტანციურ ბრენჩსა და საბაზისო ტეგს, მოითხოვს, რომ არჩეული წყარო ემთხვეოდეს ბრენჩის tip-ს, უარყოფს შეუცვლელ წყაროს ან კომპონენტის გარეთ ცვლილებებს, მის trust-policy შეყვანებსა და ვალიდაციას და აფიქსირებს გადაწყვეტილ საბაზისო კომიტს. Main-დან აღებული კონტროლები იმეორებს ამ შემოწმებებს ვერსიირებული იმიჯისა და GitHub-ზე გამოქვეყნებამდე. თუ წყაროს ბრენჩი, სტაბილური საბაზო ან ხელმისაწვდომი ვერსია იცვლება, შეწყვიტეთ და ხელახლა დაადასტურეთ, ნაცვლად ახალი წყაროს ჩანაცვლებისა.

Backport-ები იყენებენ არსებულ მულტიპლატფორმიან გამომქვეყნებლებს GitHub-ის „Latest“ მაჩვენებლის ან GHCR `:latest`-ის გადატანის გარეშე. გამოქვეყნება გამოყოფილია hosted განთავსებისგან: ეს workflow-ები არ ახდენენ hosted სერვერის ან Kura ფლოტის პრომოუშენს, არ უვლიან გვერდს canary-ის მიღებას ან არ ადასტურებენ ინსტალირებულ runtime-ს. Build-ის დამხმარე საშუალებები და Dockerfiles კვლავ მოდის არჩეული სტაბილური წყაროდან. კონტროლები არის გამოქვეყნების კარიბჭეები და არა უკრედენტო build სამუშაოები; build-ებს შეუძლიათ ატვირთონ უტეგო იმიჯის digest-ები საბოლოო კარიბჭემდე. იმიჯისა და GitHub-ზე გამოქვეყნება არ არის ატომური: თუ გვიანდელი კარიბჭე ვერ ხერხდება იმიჯის ტეგის გამოქვეყნების შემდეგ, შეამოწმეთ ნაწილობრივი გამოშვება და შეინახეთ მისი საწყისი წყარო და არტიფაქტები. არასდროს ჩაანაცვლოთ არსებული გამოშვება ან არ გამოიყენოთ სხვა ბაიტები მისი ტეგის ქვეშ.

## კარგი კომიტის შეტყობინებების წერა

ვინაიდან კომიტის შეტყობინებები პირდაპირ გავლენას ახდენენ გამოშვების შენიშვნებზე, მნიშვნელოვანია ნათელი, აღმწერი შეტყობინებების წერა:

### გაკეთეთ:
- გამოიყენეთ აწმყო დრო: „add feature“ და არა „added feature“
- იყავით ლაკონიური, მაგრამ აღმწერი
- მიუთითეთ სფერო, როდესაც ცვლილებები კომპონენტისთვისაა დამახასიათებელი
- მიუთითეთ issues, როდესაც შესაბამისია: `fix(cli): resolve build cache issue (#1234)`

### არ გააკეთოთ:
- არ გამოიყენოთ ბუნდოვანი შეტყობინებები, როგორიცაა „fix bug“ ან „update code“
- არ აურიოთ რამდენიმე არარელევანტური ცვლილება ერთ კომიტში
- არ დაგავიწყდეთ breaking change ინფორმაციის ჩართვა

### Breaking changes

Breaking changes-ისთვის, ჩართეთ `BREAKING CHANGE:` კომიტის ძირითად ნაწილში:

```
feat(cli): change cache directory structure

BREAKING CHANGE: Cache files are now stored in a new directory structure.
Users need to clear their cache after updating.
```

## გამოშვების workflow-ები

CLI-ს, სერვერსა და Kura-ს თითოეულს აქვს საკუთარი არხის workflow-ების ნაკრები, ერთი და იგივე სტრუქტურის მიხედვით:

- `<component>-release.yml` - აქვეყნებს canary-ს `main`-ზე ყოველი კომპონენტის შეხების push-ზე (Kura-ს არის ხელახლა გამოსაყენებელი workflow, რომელსაც `server-production-deployment.yml` უწოდებს, როდესაც `kura/` იცვლება)
- `<component>-rc.yml` - ქმნის რელიზის კანდიდატს ყოველ ორშაბათს (`workflow_run`-ის მეშვეობით promote-ის შემდეგ) ან ხელით ქმნის ან განაახლებს ერთ-ერთს
- `<component>-promote.yml` - აწინაურებს მოლოდინში მყოფ RC-ს სტაბილურად ყოველ ორშაბათს 06:00 UTC-ზე ან ხელით აწინაურებს „soaked“ RC-ს
- `<component>-build-publish.yml` - საერთო build და გამოქვეყნების მილსადენი, რომელსაც ზემოთ ჩამოთვლილი სამი იყენებს

CLI-ს, სერვერსა და Kura-ს ასევე აქვთ `<component>-backport.yml` სტაბილურ ხაზზე პატჩების შესაქმნელად. კომპონენტის ყველა workflow სერიალიზდება ერთი `<component>-publish` concurrency ჯგუფის მეშვეობით, რათა ვერსიის გადაწყვეტა და ტეგირება არასდროს შეეჯახოს ერთმანეთს. Kura არის გამონაკლისი: მისი canary იყენებს `kura-canary-publish`-ს, ხოლო მისი RC, promote და backport იყენებენ `kura-stable-publish`-ს, რათა ხანგრძლივმა სტაბილურმა build-მა არ შეაფერხოს განთავსების კასკადი. ტეგების სივრცეები განცალკევებულია, ამიტომ ორი ჯგუფი არ შეეჯახება.

Helm-ის ჩარტი და ინფრასტრუქტურის სახეები (CAPI ოპერატორი, runners კონტროლერი, xcresult პროცესორის სახე, linux runner-ის სახე და ა.შ.) კვლავ გამოიცემა `.github/workflows/server-production-deployment.yml`-ის მეშვეობით. ის მუშაობს `main`-ზე push-ების დროს და იყენებს კასკადს canary → მიღების ტესტები → production ჰოსტინგის განთავსებისთვის, ასევე აქვეყნებს ამ ინფრასტრუქტურულ კომპონენტებს მათი ცვლილებისას. აპლიკაციას, ქეშს, Gradle პლაგინს, skills-ს, Noora-ს და დამოუკიდებელ ინფრასტრუქტურულ კონტროლერებს თითოეულს აქვს საკუთარი `*-release.yml` workflow. ყველა მათგანი იზიარებს ცვლილებების აღმოჩენას: `mise/tasks/release/components.json` განსაზღვრავს თითოეული კომპონენტის ტეგის პრეფიქსს და include ბილიკებს, ხოლო git cliff შესაბამის კომიტებს რელიზის შენიშვნებად აქცევს.

CLI-ის build (`cli-build-publish.yml`) ასევე ქმნის და აქვეყნებს `tuist.spec.json` არტეფაქტს (გენერირებული `tuist --experimental-dump-help`-დან), რათა downstream ინსტრუმენტებმა შეძლონ ბრძანების ინტერფეისის გამოყენება.

- **შეფერხებების შემცირება**: არ არის საჭირო ხელით გამოშვებების ლოდინი
- **ნათელი კომუნიკაცია**: ავტომატური changelog-ები კომიტების შეტყობინებებიდან
- **თანმიმდევრული პროცესი**: იგივე გამოშვების ნაკადი ყველა კომპონენტისთვის
- **ხარისხის უზრუნველყოფა**: გამოიცემა მხოლოდ ტესტირებული ცვლილებები

## პრობლემების გადაჭრა

თუ გამოშვება ვერ მოხერხდა:

1. შეამოწმეთ GitHub Actions ლოგები წარუმატებელი workflow-სთვის
2. დარწმუნდით, რომ თქვენი კომიტების შეტყობინებები ემორჩილება კონვენციურ ფორმატს
3. დაადასტურეთ, რომ ყველა ტესტი გადის
4. შეამოწმეთ, რომ კომპონენტი წარმატებით იკრიბება

სასწრაფო შესწორებებისთვის, რომლებსაც დაუყოვნებელი გამოშვება სჭირდებათ:
1. დარწმუნდით, რომ თქვენს კომიტს აქვს ნათელი სკოუპი
2. შერწყმის შემდეგ, აკონტროლეთ გამოშვების workflow
3. სერვერის ან აპლიკაციისთვის, შესწორება გამოიცემა შემდეგ push-ზე; საჭიროების შემთხვევაში, გაუშვით ხელით გამოშვება
4. CLI-სთვის, შესწორება ავტომატურად ხვდება canary-ზე. სტაბილურ მომხმარებლებამდე მისაყვანად, გააკეთეთ მისი backport შენარჩუნებულ სტაბილურ ხაზ(ებ)ზე (იხილეთ [Backporting fixes to a stable line](#backporting-fixes-to-a-stable-line))

## App Store-ის გამოშვება

მიუხედავად იმისა, რომ CLI და სერვერი მიჰყვებიან ზემოთ აღწერილ უწყვეტ გამოშვების პროცესს, **iOS აპლიკაცია** არის გამონაკლისი Apple-ის App Store-ის განხილვის პროცესის გამო:

- **ხელით გამოშვებები**: iOS აპლიკაციის გამოშვებები მოითხოვს ხელით წარდგენას App Store-ში
- **განხილვის დაყოვნებები**: თითოეულმა გამოშვებამ უნდა გაიაროს Apple-ის განხილვის პროცესი, რასაც 1-7 დღე შეიძლება დასჭირდეს
- **ჯგუფური ცვლილებები**: მრავალი ცვლილება ჩვეულებრივ ერთად იკრიბება თითოეულ iOS გამოშვებაში
- **TestFlight**: ბეტა ვერსიები შეიძლება გავრცელდეს TestFlight-ის მეშვეობით App Store-ში გამოშვებამდე
- **გამოშვების შენიშვნები**: უნდა დაიწეროს სპეციფიკურად App Store-ის სახელმძღვანელო პრინციპებისთვის

iOS აპლიკაცია კვლავ მიჰყვება იგივე კომიტის კონვენციებს და იყენებს git cliff-ს changelog-ის გენერაციისთვის, მაგრამ რეალური გამოშვება მომხმარებლებისთვის ხდება ნაკლებად ხშირი, ხელით განრიგით.
