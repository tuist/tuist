# გამოშვებები

Tuist ახალ ვერსიებს ავტომატურად აქვეყნებს, როდესაც ცვლილებები main შტოს ერწყმის. CLI, სერვერი და Kura ქეშ-სერვერი ყველა გამოშვების არხებით (canary, release candidate, stable) ნაწილდება, რათა რეკომენდებული ინსტალაცია სტაბილური და ნელი იყოს; release candidate-ის მომზადება და მისი stable-ში გადაყვანა განზრახული, კვირითი ნაბიჯებია. აპლიკაცია უწყვეტად გამოიცემა (iOS აპლიკაცია მხოლოდ TestFlight-ზე განთავსდება უწყვეტად, მეტი ინფორმაცია [აქ](#app-store-release)).

## მიმოხილვა

ჩვენ ვუშვებთ ამ ძირითად კომპონენტებს:
- **Tuist CLI** - ბრძანების ხაზის ინსტრუმენტი, რომელიც ნაწილდება canary, release candidate და stable [არხებით](#release-channels)
- **Tuist Server** - ბექენდ სერვისები, რომლებიც ნაწილდება CLI-ის იგივე არხების მოდელით
- **Kura** - ქეშ-სერვერი, რომელიც ნაწილდება CLI-ის იგივე არხების მოდელით
- **Tuist App** - macOS და iOS აპლიკაციები, რომლებიც უწყვეტად გამოიცემა (iOS აპლიკაცია მხოლოდ TestFlight-ზე განთავსდება უწყვეტად, მეტი ინფორმაცია [აქ](#app-store-release))

`main`-ზე ყოველი push აქვეყნებს canary წინასწარ გამოშვებას CLI-ისთვის, სერვერისთვის და Kura-სთვის. თითოეული ამ კომპონენტის stable გამოშვება მზადდება მხოლოდ მაშინ, როდესაც შემნარჩუნებელი „დაყოვნებულ“ release candidate-ს აწინაურებს, ხოლო კვირითი გრაფიკი სამივე „მატარებელს“ ერთდროულად აწარმოებს (იხილეთ [გამოშვების არხები](#release-channels)). აპლიკაცია stable-ს აქვეყნებს `main`-ზე ყოველი push-ისას.

## როგორ მუშაობს

### 1. კომიტების შეთანხმებები

ჩვენ ვიყენებთ [Conventional Commits](https://www.conventionalcommits.org/)-ს ჩვენი კომიტების შეტყობინებების სტრუქტურირებისთვის. ეს საშუალებას აძლევს ჩვენს ინსტრუმენტებს გაიგონ ცვლილებების ბუნება, განსაზღვრონ ვერსიის ზრდა და შექმნან შესაბამისი changelog-ები.

ფორმატი: `type(scope): description`

#### კომიტების ტიპები და მათი გავლენა

| ტიპი | აღწერა | ვერსიის გავლენა | მაგალითი |
|------|-------------|----------------|---------|
| `feat` | ახალი ფუნქცია ან შესაძლებლობა | მინორული ვერსიის ზრდა (x.Y.z) | `feat(cli): add support for Swift 6` |
| `fix` | შეცდომის გამოსწორება | პატჩ-ვერსიის ზრდა (x.y.Z) | `fix(app): resolve crash when opening projects` |
| `docs` | დოკუმენტაციის ცვლილებები | გამოშვება არ ხდება | `docs: update installation guide` |
| `style` | კოდის სტილის ცვლილებები | გამოშვება არ ხდება | `style: format code with swiftformat` |
| `refactor` | კოდის რეფაქტორინგი | გამოშვება არ ხდება | `refactor(server): simplify auth logic` |
| `perf` | წარმადობის გაუმჯობესება | პატჩ-ვერსიის ზრდა | `perf(cli): optimize dependency resolution` |
| `test` | ტესტების დამატება/ცვლილება | გამოშვება არ ხდება | `test: add unit tests for cache` |
| `chore` | ტექნიკური მოვლა | გამოშვება არ ხდება | `chore: update dependencies` |
| `ci` | CI/CD ცვლილებები | გამოშვება არ ხდება | `ci: add workflow for releases` |

CLI-ისთვის ეს ზრდები განსაზღვრავენ canary ვერსიას და changelog-ის დაჯგუფებას. Stable CLI ვერსიები არის მინორული ხაზები (`X.Y.0`), რომლებიც ხელით მზადდება, ხოლო stable პატჩები (`X.Y.Z`) მხოლოდ backport-ებიდან მოდის, ამიტომ `feat` ან `fix` CLI მომხმარებლებს აღწევს ქვემოთ მოცემული არხების ნაკადით და არა როგორც დაუყოვნებელი stable გამოშვება.

#### დამრღვევი ცვლილებები

დამრღვევი ცვლილებები იწვევს მაჟორული ვერსიის ზრდას (X.0.0) და უნდა იყოს მითითებული კომიტის ძირითად ნაწილში:

```
feat(cli): change default cache location

BREAKING CHANGE: The cache is now stored in ~/.tuist/cache instead of .tuist-cache.
Users will need to clear their old cache directory.
```

### 2. ცვლილებების აღმოჩენა

თითოეული კომპონენტი იყენებს [git cliff](https://git-cliff.org/)-ს, რათა:
- გაანალიზოს კომიტები ბოლო გამოშვების შემდეგ
- გაფილტროს კომიტები სკოპის მიხედვით (cli, app, server)
- დაადგინოს, არის თუ არა გამოსაშვები ცვლილებები
- ავტომატურად შექმნას changelog-ები

### 3. გამოშვების პაიპლაინი

როდესაც აღმოჩენილია გამოსაშვები ცვლილებები:

1. **ვერსიის გამოთვლა**: პაიპლაინი განსაზღვრავს მომდევნო ვერსიის ნომერს
2. **Changelog-ის გენერაცია**: git cliff ქმნის changelog-ს კომიტების შეტყობინებებიდან
3. **აწყობის პროცესი**: კომპონენტი აიწყობა და იტესტება
4. **არტეფაქტების გენერაცია**: მზადდება გამოშვებისთვის სპეციფიკური რესურსები, როგორიცაა CLI ბანდლები, საკონტროლო ჯამები და `tuist.spec.json` CLI სპეციფიკაცია, რომელიც გენერირდება `tuist --experimental-dump-help`-დან
5. **გამოშვების შექმნა**: იქმნება GitHub გამოშვება არტეფაქტებით
6. **გავრცელება**: განახლებები იგზავნება პაკეტების მენეჯერებში (მაგ., Homebrew CLI-ისთვის)

აპისთვის ეს წარმოქმნის stable გამოშვებას ყოველ შერწყმაზე. CLI-ის, სერვერისა და Kura-სთვის, ეს იგივე ავტომატური პაიპლაინი წარმოქმნის მხოლოდ **canary** პრერელიზს; რელიზ კანდიდატები და stable გამოშვებები მზადდება ყოველკვირეულ რელიზ ტრენზე (იხ. [გამოშვების არხები](#release-channels)).

- **CLI**: კომიტები `(cli)` სკოპით ან სკოპის გარეშე
- **App**: კომიტები `(app)` სკოპით
- **Server**: კომიტები `(server)` სკოპით

## გამოშვების არხები

CLI, სერვერი და Kura არ გადაჰყავთ stable გამოშვებაში `main`-ზე ყოველი push-ის დროს. თითოეული გადის სამი არხის მეშვეობით, რათა რეკომენდებული ინსტალაცია დარჩეს სტაბილური და ნელი, ხოლო ადრეულმა მომხმარებლებმა შეინარჩუნონ კომიტზე დაფუძნებული აწყობები. მომხმარებლისთვის ხელმისაწვდომი დოკუმენტაცია განთავსებულია <.localized_link href="/cli/release-channels">CLI გამოშვების არხებზე</.localized_link> და <.localized_link href="/guides/server/self-host/release-channels">სერვერის გამოშვების არხებზე</.localized_link>; ეს სექცია არის შენარჩუნების ინსტრუქცია.

თითოეული კომპონენტი იყენებს ერთსა და იმავე სამ არხს:

| არხი | ვერსია | მზადდება |
|---------|---------|--------|
| Canary | `X.Y.0-canary.N` | ავტომატურად, კომპონენტთან დაკავშირებული ყოველი push-ის დროს `main`-ზე (`<component>-release.yml`; Kura-სთვის, გამოძახებულია `server-production-deployment.yml`-ით, როცა `kura/` იცვლება) |
| რელიზ კანდიდატი | `X.Y.0-rc.N` | ყოველ ორშაბათს, ან ხელით, `releases/<component>-<major>.<minor>.x` ბრენჩზე (`<component>-rc.yml`) |
| Stable | `X.Y.Z` | ყოველ ორშაბათს, ან ხელით, გაჟღენთილი RC-ის პრომოციით (`<component>-promote.yml`); პატჩები `<component>-backport.yml`-ის მეშვეობით |

Canary და RC აწყობები ქვეყნდება როგორც GitHub პრერელიზები (არასდროს აღინიშნება როგორც "Latest", არასდროს გადაადგილებს `:latest`-ს GHCR-ზე, არასდროს იგზავნება Homebrew-ში CLI-ისთვის), ამიტომ პაკეტების მენეჯერები და image რეზოლვერები მათ მხოლოდ ცალსახა opt-in-ის შემთხვევაში იღებენ. Canary ყოველთვის ისახავს მიზნად შემდეგ გამოუშვებელ მინორულ ვერსიას: როგორც კი RC ხაზი მზადდება, `main`-ის canary გადადის შემდეგ მინორულ ვერსიაზე.

Hosted Tuist არ ელოდება stable ტრენს: სერვერი დეპლოიდება კომიტის მიხედვით, ხოლო hosted canary და production უშვებენ Kura-ს უახლეს canary-ს. დეპლოიმენტის კასკადი აქვეყნებს ამ canary-ს მის დეპლოიმენტამდე, ამიტომ `kura-release.yml`-ს არ აქვს საკუთარი ტრიგერი. ცვლილებები მხოლოდ Kura-ს გამოშვების ინსტრუმენტებში (`mise/tasks/kura/**`, `kura-*.yml` workflows) არ ქმნიან canary-ს.

თქვენ არასდროს ირჩევთ ვერსიის ნომრებს ხელით. ყოველი არხის მომდევნო ვერსია მიღებულია არსებული git ტეგებიდან `mise/tasks/<component>/release/channel-version.sh`-ის მიერ, რომელსაც ქვემოთ მოცემული workflows იძახებენ.

გამოშვების ბრენჩები დაყოფილია კომპონენტების მიხედვით (`releases/server-X.Y.x`, `releases/kura-X.Y.x`, `releases/X.Y.x` CLI-ისთვის), რათა სამი კომპონენტის ხაზები არასდროს შეეჯახოს ერთსა და იმავე მინორულ ვერსიაზე.

### ყოველკვირეული განრიგი

ყოველ ორშაბათს 06:00 UTC-ზე, სამი კომპონენტის პრომოციის სამუშაოები ერთდროულად მუშაობს: **CLI Promote to Stable**, **Server Promote to Stable** და **Kura Promote to Stable**. თითოეული ახდენს უახლესი RC ხაზის პრომოციას, რომელიც ჯერ არ არის stable, რაც ჩვეულებრივ წინა ორშაბათს მომზადებული ხაზია. თუ ასეთი ხაზი არ არსებობს, ეს სამუშაო არაფერს აქვეყნებს.

როდესაც პრომოცია სრულდება, შედეგის მიუხედავად, მისი შესაბამისი **რელიზ კანდიდატი** workflow (`cli-rc.yml`, `server-rc.yml`, `kura-rc.yml`) იწყება `workflow_run`-ის მეშვეობით და ქმნის შემდეგ ხაზს `main`-დან.

თუ რომელიმე დაგეგმილი გაშვება ვერ ხერხდება ან გაუქმებულია, Slack-ზე იგზავნება შეტყობინება. პრომოცია ვერ ხერხდება, როცა გამოშვების ბრენჩს აქვს კომიტები მისი უახლესი RC-ის შემდეგ. ამ ხაზის გამოსაშვებად, მასზე უნდა შეიქმნას ახალი RC და ხელით მოხდეს მისი პრომოცია. წინააღმდეგ შემთხვევაში, შემდეგ ორშაბათს პრომოცია გაუკეთდება უფრო ახალ ხაზს.

### რელიზ კანდიდატის მომზადება

ახალი ხაზის მოსამზადებლად ყოველკვირეული განრიგის გარეთ (ჩაანაცვლეთ ქვემოთ კომპონენტის workflow-ის სახელი):

1. გაუშვით **\<Component\> Release Candidate** workflow (მაგალითად, `server-rc.yml`) ცარიელი `branch` შეყვანით.
2. ის აქვეყნებს `X.Y.0-rc.1` და, წარმატების შემდეგ, ქმნის დაცულ `releases/<component>-X.Y.x` ბრენჩს აწყობილ კომიტზე.

კრიტიკული შესწორების ან რეგრესიის „soaking“ ხაზში ჩასართავად, გადაიტანეთ ის გამოშვების ბრენჩზე PR-ის მეშვეობით (იგივე ნაკადი, რაც backport-ებისთვის; CI არასდროს აკეთებს cherry-pick-ს), შემდეგ გაიმეორეთ RC:

1. გადადით `releases/<component>-X.Y.x`-დან, გააკეთეთ cherry-pick შესწორების, გახსენით PR უკან გამოშვების ბრენჩში, გადაწყვიტეთ ნებისმიერი კონფლიქტი და გააერთიანეთ.
2. კიდევ ერთხელ გაუშვით **Release Candidate** workflow `branch=releases/<component>-X.Y.x`-ით. ის აქვეყნებს `X.Y.0-rc.(N+1)`-ს ბრენჩის HEAD-იდან.

„Soaking“ ხაზი არის ფუნქციებით გაყინული: მასზე მხოლოდ კრიტიკული შესწორებები და რეგრესიები თავსდება.

### Stable-ზე პრომოცია

ხაზის stable-ზე პრომოციისთვის ყოველკვირეული განრიგის გარეთ, მისი RC-ის სუფთა „soaking“-ის შემდეგ:

1. გაუშვით **\<Component\> Promote to Stable** workflow (მაგალითად, `server-promote.yml`) `branch=releases/<component>-X.Y.x`-ით.
2. ის აქვეყნებს semver-ით მონიშნულ იმიჯს `make_latest=true`-ით, გადააქვს GHCR `:latest` ტეგი და GitHub-ის „Latest“ მაჩვენებელი. CLI ასევე აახლებს Homebrew ფორმულას.

პრომოცია არ მუშაობს, თუ ბრენჩის HEAD ზუსტად არ ემთხვევა კომიტს, რომელზეც მიუთითებს უახლესი RC. ამიტომ, თუ ბოლო RC-ის შემდეგ ხაზზე რაიმე შესწორება გაერთიანდა, უნდა შექმნათ ახალი RC და მისცეთ მას „soak“-ის დრო, სანამ stable-ად გამოიცემა.

### შესწორებების backport-ing stable ხაზზე

როდესაც ხაზი stable-ია, პატჩები გამოიცემა მხოლოდ CLI-ისთვის განკუთვნილი **Backport Release** workflow-ით (`cli-backport.yml`): გადაიტანეთ შესწორება `releases/X.Y.x`-ზე PR-ის მეშვეობით, შემდეგ გაუშვით workflow ამ ბრენჩით `X.Y.(Z+1)`-ის მოსამზადებლად. Backport-ები არასდროს გადააადგილებენ „Latest“ მაჩვენებელს ან Homebrew ფორმულას. ერთდროულად ორი ხაზი ნარჩუნდება: მიმდინარე ხაზი იღებს რეგრესიებს და უსაფრთხოების შესწორებებს, წინა ხაზი კი მხოლოდ კრიტიკულ და უსაფრთხოების შესწორებებს. სხვა ბაგების შესწორებები არ გადაიტანება და გამოიცემა შემდეგ მინორულ ვერსიაში.

სერვერისა და Kura-სთვის გამოიყენეთ **Server Backport Release** (`server-backport.yml`) ან **Kura Backport Release** (`kura-backport.yml`). პრომოცია აქვეყნებს მხოლოდ RC-ის `X.Y.0`-ს; მას არ შეუძლია უკვე stable ხაზის პატჩირება.

1. დაიწყეთ შერჩეული `X.Y` ხაზის უახლესი გამოქვეყნებული stable კომპონენტის ტეგიდან და გახსენით ქირურგიული შესწორების PR მის არსებულ `releases/server-X.Y.x` ან `releases/kura-X.Y.x` ბრენჩში. უფრო ახალი მინორული ან მაჟორული გამოშვება არ ხელს უშლის შენარჩუნებული ხაზის პატჩირებას. თავი შეიკავეთ main-თან დაკავშირებული არარელევანტური ცვლილებებისგან.
2. გადახედეთ და გააერთიანეთ წყაროს PR. ჩამოტვირთეთ დისტანციური გამოშვების ბრენჩი და დააკვალიფიცირეთ მისი **საბოლოო გაერთიანებული tip**, კომპონენტის მხარდაჭერილი პლატფორმებისა და TLS დადებითი/უარყოფითი კონტროლების ჩათვლით. წარმატებული pre-merge head არ არის სხვა squash ან merge კომიტის კვალიფიკაცია.
3. ცალკეული გამოქვეყნების დამტკიცებით, გაუშვით შესაბამისი backport workflow **main-დან**, `source_sha`-ის დაყენებით ზუსტად იმ კვალიფიცირებულ გაერთიანებულ tip-ზე და `base_tag`-ის — მიმდინარე stable ტეგზე, როგორიცაა `server@X.Y.Z` ან `kura@X.Y.Z`. workflow გამოიყვანს `X.Y.(Z+1)`-ს; ოპერატორები არ ირჩევენ მინორულ გაზრდას ან canary შიგთავსის პრომოციას.

დაგეგმვა აახლებს ზუსტ დისტანციურ ბრენჩსა და საბაზისო ტეგს, მოითხოვს, რომ შერჩეული წყარო ემთხვეოდეს ბრენჩის tip-ს, უარყოფს შეუცვლელ წყაროს ან კომპონენტის გარეთ ცვლილებებს, მის trust-policy შეყვანებსა და ვალიდაციას და ამაგრებს გადაწყვეტილ საბაზისო კომიტს. Main-ზე დაფუძნებული კონტროლები იმეორებენ ამ შემოწმებებს ვერსიირებული იმიჯისა და GitHub-ზე გამოქვეყნებამდე. თუ წყაროს ბრენჩი, stable საბაზო ან ხელმისაწვდომი ვერსია იცვლება, შეაჩერეთ და ხელახლა დააკვალიფიცირეთ, ნაცვლად ახალი წყაროს ჩანაცვლებისა.

Backport-ები იყენებენ არსებულ მრავალპლატფორმიან გამომქვეყნებლებს GitHub-ის „Latest“ მაჩვენებლის ან GHCR `:latest`-ის გადაადგილების გარეშე. გამოქვეყნება გამოყოფილია hosted განლაგებისგან: ეს workflow-ები არ ახდენენ hosted სერვერის ან Kura ფლოტის პრომოციას, არ ავლიან canary მიღებას ან არ აკვალიფიცირებენ ინსტალირებულ runtime-ს. აწყობის დამხმარე საშუალებები და Dockerfiles კვლავ მოდიან შერჩეული stable წყაროდან. კონტროლები არის გამოქვეყნების კარიბჭეები და არა უკრედენტიანო აწყობის სამუშაოები; აწყობებს შეუძლიათ ატვირთონ უტეგო იმიჯის digest-ები საბოლოო კარიბჭემდე. იმიჯისა და GitHub-ზე გამოქვეყნება არ არის ატომური: თუ გვიანი კარიბჭე ვერ ხერხდება იმიჯის ტეგის გამოქვეყნების შემდეგ, შეამოწმეთ ნაწილობრივი გამოშვება და შეინახეთ მისი საწყისი წყარო და არტეფაქტები. არასდროს ჩაანაცვლოთ არსებული გამოშვება ან არ გამოიყენოთ სხვა ბაიტები მისი ტეგის ქვეშ.

## კარგი კომიტის შეტყობინებების წერა

ვინაიდან კომიტის შეტყობინებები პირდაპირ გავლენას ახდენენ გამოშვების შენიშვნებზე, მნიშვნელოვანია მკაფიო, აღმწერი შეტყობინებების წერა:

### გააკეთეთ:
- გამოიყენეთ აწმყო დრო: „add feature“ და არა „added feature“
- იყავით მოკლე, მაგრამ აღმწერი
- მიუთითეთ სკოპი, როცა ცვლილებები კომპონენტზეა დამოკიდებული
- მიუთითეთ issues, როცა შესაბამისია: `fix(cli): resolve build cache issue (#1234)`

### არ გააკეთოთ:
- არ გამოიყენოთ ბუნდოვანი შეტყობინებები, როგორიცაა „fix bug“ ან „update code“
- არ შეურიოთ რამდენიმე დაუკავშირებელი ცვლილება ერთ კომიტში
- არ დაგავიწყდეთ breaking change ინფორმაციის ჩართვა

### Breaking changes

Breaking changes-ისთვის, ჩართეთ `BREAKING CHANGE:` კომიტის სხეულში:

```
feat(cli): change cache directory structure

BREAKING CHANGE: Cache files are now stored in a new directory structure.
Users need to clear their cache after updating.
```

## გამოშვების workflow-ები

CLI-ს, სერვერს და Kura-ს თითოეულს აქვს საკუთარი არხის workflow-ების ნაკრები, ერთი და იგივე სტრუქტურის მიხედვით:

- `<component>-release.yml` - აქვეყნებს canary-ს `main`-ზე ყოველი კომპონენტის შეხების push-ზე (Kura-ს არის ხელახლა გამოყენებადი workflow, რომელსაც `server-production-deployment.yml` იძახებს, როცა `kura/` იცვლება)
- `<component>-rc.yml` - ქმნის რელიზ კანდიდატს ყოველ ორშაბათს (`workflow_run`-ის მეშვეობით პრომოციის შემდეგ), ან ხელით ქმნის ან აუმჯობესებს ერთ-ერთს
- `<component>-promote.yml` - ახდენს მოლოდინში მყოფი RC-ის პრომოციას stable-ზე ყოველ ორშაბათს 06:00 UTC-ზე, ან ხელით ახდენს „soaked“ RC-ის პრომოციას
- `<component>-build-publish.yml` - საერთო აწყობისა და გამოქვეყნების პაიპლაინი, რომელსაც ზემოთ ჩამოთვლილი სამი იძახებს

CLI-ს, სერვერს და Kura-ს ასევე აქვთ `<component>-backport.yml` stable ხაზზე პატჩების მოსამზადებლად. კომპონენტის ყველა workflow სერიალიზდება ერთი `<component>-publish` concurrency ჯგუფის მეშვეობით, რათა ვერსიის გადაწყვეტა და ტეგირება არასდროს შეეჯახოს. Kura არის გამონაკლისი: მისი canary იყენებს `kura-canary-publish`-ს, ხოლო მისი RC, პრომოცია და backport იყენებენ `kura-stable-publish`-ს, რათა ხანგრძლივმა stable აწყობამ არ შეაფერხოს განლაგების კასკადი. ტეგების სივრცეები განცალკევებულია, ამიტომ ორი ჯგუფი არ შეეჯახება.

Helm chart და ინფრასტრუქტურის სახეები (CAPI operator, runners controller, xcresult processor image, linux runner image და სხვა) კვლავ გამოიცემა `.github/workflows/server-production-deployment.yml`-ის მეშვეობით. ის მუშაობს `main`-ზე push-ების დროს და ახდენს canary → მიღების ტესტები → პროდაქშენი კასკადს ჰოსტინგის განლაგებისთვის, ასევე აქვეყნებს ამ ინფრასტრუქტურულ კომპონენტებს ცვლილებების შესაბამისად. აპლიკაციას, cache-ს, Gradle plugin-ს, skills-ს, Noora-ს და დამოუკიდებელ ინფრასტრუქტურულ კონტროლერებს თითოეულს აქვს dedicated `*-release.yml` workflow. ყველა მათგანი იზიარებს ცვლილებების აღმოჩენას: `mise/tasks/release/components.json` აცხადებს თითოეული კომპონენტის ტეგის პრეფიქსს და include paths-ს, ხოლო git cliff გარდაქმნის შესაბამის კომიტებს რელიზის შენიშვნებად.

CLI აწყობა (`cli-build-publish.yml`) ასევე ქმნის და აქვეყნებს `tuist.spec.json` არტიფაქტს (გენერირებული `tuist --experimental-dump-help`-დან), რათა downstream ინსტრუმენტებმა შეძლონ ბრძანების ინტერფეისის მოხმარება.

- **თანმიმდევრული პროცესი**: ერთი და იგივე გამოშვების ნაკადი ყველა კომპონენტისთვის
- **ხარისხის უზრუნველყოფა**: გამოიცემა მხოლოდ ტესტირებული ცვლილებები

## პრობლემების გადაჭრა

თუ რელიზი ვერ ხერხდება:

1. შეამოწმეთ GitHub Actions ლოგები ვერ მოხერხებული workflow-სთვის
2. დარწმუნდით, რომ თქვენი კომიტის შეტყობინებები ემორჩილება conventional ფორმატს
3. დაადასტურეთ, რომ ყველა ტესტი გადის
4. შეამოწმეთ, რომ კომპონენტი წარმატებით აიწყობა

სასწრაფო გამოსწორებებისთვის, რომლებსაც სჭირდებათ დაუყოვნებელი გამოშვება:
1. დარწმუნდით, რომ თქვენს კომიტს აქვს ნათელი scope
2. merge-ის შემდეგ, აკვირდით რელიზის workflow-ს
3. სერვერის ან აპლიკაციისთვის, გამოსწორება გამოიცემა შემდეგ push-ზე; საჭიროების შემთხვევაში, გაუშვით ხელით რელიზი
4. CLI-სთვის, გამოსწორება ავტომატურად ხვდება canary-ზე. stable მომხმარებლებისთვის მისაღწევად, გააკეთეთ backport შენარჩუნებულ stable ხაზ(ებ)ზე (იხილეთ [Backporting fixes to a stable line](#backporting-fixes-to-a-stable-line))

## App Store გამოშვება

მიუხედავად იმისა, რომ CLI და Server მიჰყვებიან ზემოთ აღწერილ უწყვეტ გამოშვების პროცესს, **iOS აპლიკაცია** არის გამონაკლისი Apple-ის App Store განხილვის პროცესის გამო:

- **ხელით გამოშვებები**: iOS აპლიკაციის გამოშვებები მოითხოვს ხელით წარდგენას App Store-ში
- **განხილვის დაყოვნებები**: თითოეულმა გამოშვებამ უნდა გაიაროს Apple-ის განხილვის პროცესი, რასაც 1-7 დღე შეიძლება დასჭირდეს
- **ჯგუფური ცვლილებები**: მრავალი ცვლილება ჩვეულებრივ ერთად იკვრება თითოეულ iOS გამოშვებაში
- **TestFlight**: Beta ვერსიები შეიძლება გავრცელდეს TestFlight-ის მეშვეობით App Store გამოშვებამდე
- **გამოშვების შენიშვნები**: უნდა დაიწეროს სპეციფიკურად App Store guidelines-ის შესაბამისად

iOS აპლიკაცია კვლავ მიჰყვება იგივე კომიტის კონვენციებს და იყენებს git cliff-ს changelog-ის გენერაციისთვის, მაგრამ რეალური გამოშვება მომხმარებლებისთვის ხდება ნაკლებად ხშირი, ხელით გრაფიკით.
