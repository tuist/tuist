# რელიზები

Tuist ავტომატურად აქვეყნებს ახალ ვერსიებს, როდესაც ცვლილებები ერწყმის main შტოს. CLI, სერვერი და Kura ქეშ-სერვერი ყველა გამოიცემა რელიზის არხების საშუალებით (canary, release candidate, stable), რათა რეკომენდებული ინსტალაცია დარჩეს სტაბილური და ნელა მოძრავი; რელიზის კანდიდატის შექმნა და მისი სტაბილურზე გადაყვანა განზრახული, ყოველკვირეული ნაბიჯებია. აპლიკაცია გამოიცემა უწყვეტად (iOS აპლიკაცია მხოლოდ უწყვეტად ნერგდება TestFlight-ში, მეტი იხილეთ [აქ](#app-store-release)).

## მიმოხილვა

ჩვენ ვუშვებთ ამ ძირითად კომპონენტებს:
- **Tuist CLI** - ბრძანებათა ხაზის ინსტრუმენტი, რომელიც გამოიცემა canary, release candidate და სტაბილური [არხების](#release-channels) საშუალებით
- **Tuist Server** - ბექენდის სერვისები, რომლებიც გამოიცემა იგივე არხის მოდელით, როგორც CLI
- **Kura** - ქეშ-სერვერი, რომელიც გამოიცემა იგივე არხის მოდელით, როგორც CLI
- **Tuist App** - macOS და iOS აპლიკაციები, რომლებიც გამოიცემა უწყვეტად (iOS აპლიკაცია მხოლოდ უწყვეტად ნერგდება TestFlight-ში, მეტი იხილეთ [აქ](#app-store-release))

ყოველი push `main`-ზე აქვეყნებს canary წინასწარ რელიზს CLI-სთვის, სერვერისთვის და Kura-სთვის. თითოეული ამ კომპონენტის სტაბილური რელიზი იჭრება მხოლოდ მაშინ, როდესაც შემნარჩუნებელი აწვდის გაჟღენთილ რელიზის კანდიდატს, და ყოველკვირეული გრაფიკი ერთდროულად აწარმოებს სამივე მატარებელს (იხილეთ [რელიზის არხები](#release-channels)). აპლიკაცია აქვეყნებს სტაბილურ ვერსიას ყოველ push-ზე `main`-ზე.

## როგორ მუშაობს

### 1. კომიტის კონვენციები

ჩვენ ვიყენებთ [Conventional Commits](https://www.conventionalcommits.org/)-ს ჩვენი კომიტის შეტყობინებების სტრუქტურირებისთვის. ეს საშუალებას აძლევს ჩვენს ინსტრუმენტებს გაიგონ ცვლილებების ბუნება, განსაზღვრონ ვერსიის ზრდა და შექმნან შესაბამისი ცვლილებების ჟურნალები.

ფორმატი: `type(scope): description`

#### კომიტის ტიპები და მათი გავლენა

| ტიპი | აღწერა | ვერსიის გავლენა | მაგალითი |
|------|-------------|----------------|---------|
| `feat` | ახალი ფუნქცია ან შესაძლებლობა | მინორული ვერსიის ზრდა (x.Y.z) | `feat(cli): add support for Swift 6` |
| `fix` | შეცდომის გამოსწორება | პეტჩის ვერსიის ზრდა (x.y.Z) | `fix(app): resolve crash when opening projects` |
| `docs` | დოკუმენტაციის ცვლილებები | არ არის რელიზი | `docs: update installation guide` |
| `style` | კოდის სტილის ცვლილებები | არ არის რელიზი | `style: format code with swiftformat` |
| `refactor` | კოდის რეფაქტორინგი | არ არის რელიზი | `refactor(server): simplify auth logic` |
| `perf` | წარმადობის გაუმჯობესება | პეტჩის ვერსიის ზრდა | `perf(cli): optimize dependency resolution` |
| `test` | ტესტების დამატება/ცვლილებები | არ არის რელიზი | `test: add unit tests for cache` |
| `chore` | მომსახურების ამოცანები | არ არის რელიზი | `chore: update dependencies` |
| `ci` | CI/CD ცვლილებები | არ არის რელიზი | `ci: add workflow for releases` |

CLI-სთვის, ეს ზრდები განსაზღვრავენ canary ვერსიას და ცვლილებების ჟურნალის დაჯგუფებას. სტაბილური CLI ვერსიები არის მინორული ხაზები (`X.Y.0`), რომლებიც ხელით იჭრება, და სტაბილური პეტჩები (`X.Y.Z`) მოდის მხოლოდ backport-ებიდან, ასე რომ `feat` ან `fix` აღწევს CLI მომხმარებლებს ქვემოთ მოცემული არხის ნაკადის საშუალებით და არა როგორც უშუალო სტაბილური რელიზი.

#### დამრღვევი ცვლილებები

დამრღვევი ცვლილებები იწვევს მაჟორული ვერსიის ზრდას (X.0.0) და უნდა იყოს მითითებული კომიტის ტექსტში:

```
feat(cli): change default cache location

BREAKING CHANGE: The cache is now stored in ~/.tuist/cache instead of .tuist-cache.
Users will need to clear their old cache directory.
```

### 2. ცვლილებების აღმოჩენა

თითოეული კომპონენტი იყენებს [git cliff](https://git-cliff.org/)-ს, რათა:
- გაანალიზოს კომიტები ბოლო რელიზის შემდეგ
- ფილტრაცია მოახდინოს კომიტების სკოპის მიხედვით (cli, app, server)
- დაადგინოს, არის თუ არა რელიზისთვის მზა ცვლილებები
- ავტომატურად შექმნას ცვლილებების ჟურნალები

### 3. რელიზის პაიპლაინი

როდესაც აღმოჩენილია რელიზისთვის მზა ცვლილებები:

1. **ვერსიის გამოთვლა**: პაიპლაინი განსაზღვრავს შემდეგი ვერსიის ნომერს
2. **ცვლილებების ჟურნალის გენერაცია**: git cliff ქმნის ცვლილებების ჟურნალს კომიტების შეტყობინებებიდან
3. **აწყობის პროცესი**: კომპონენტი აიწყობა და იტესტება
4. **არტეფაქტების გენერაცია**: წარმოიქმნება რელიზისთვის სპეციფიკური რესურსები, როგორიცაა CLI ბუნდლები, საკონტროლო ჯამები და `tuist.spec.json` CLI სპეციფიკაცია, რომელიც გენერირდება `tuist --experimental-dump-help`-დან
5. **რელიზის შექმნა**: GitHub-ზე იქმნება რელიზი არტეფაქტებით
6. **გავრცელება**: განახლებები იგზავნება პაკეტების მენეჯერებში (მაგ., Homebrew CLI-სთვის)

აპისთვის ეს წარმოქმნის სტაბილურ რელიზს ყოველ შერწყმაზე. CLI-სთვის, სერვერისთვის და Kura-სთვის, ეს იგივე ავტომატური პაიპლაინი წარმოქმნის მხოლოდ **canary** პრერელიზს; რელიზის კანდიდატები და სტაბილური რელიზები იჭრება ყოველკვირეულ რელიზის ტრეინზე (იხ. [რელიზის არხები](#release-channels)).

### 4. სკოპის ფილტრაცია

თითოეული კომპონენტი აკეთებს რელიზს მხოლოდ მაშინ, როცა აქვს შესაბამისი ცვლილებები:

- **CLI**: კომიტები `(cli)` სკოპით ან სკოპის გარეშე
- **App**: კომიტები `(app)` სკოპით
- **Server**: კომიტები `(server)` სკოპით

## რელიზის არხები

CLI, სერვერი და Kura არ გადაჰყავთ სტაბილურ რელიზზე `main`-ში ყოველი push-ისას. თითოეული გადის სამი არხის მეშვეობით, რათა რეკომენდებული ინსტალაცია დარჩეს სტაბილური და ნელა მოძრავი, ხოლო ადრეულმა მომხმარებლებმა შეინარჩუნონ კომიტზე დაფუძნებული აწყობები. მომხმარებლისთვის განკუთვნილი დოკუმენტაცია განთავსებულია <.localized_link href="/cli/release-channels">CLI რელიზის არხები</.localized_link> და <.localized_link href="/guides/server/self-host/release-channels">სერვერის რელიზის არხები</.localized_link>-ზე; ეს სექცია არის მემaintenance-ის სახელმძღვანელო.

თითოეული კომპონენტი იყენებს ერთსა და იმავე სამ არხს:

| არხი | ვერსია | ჭრა |
|---------|---------|--------|
| Canary | `X.Y.0-canary.N` | ავტომატურად, კომპონენტის შემხები ყოველი push-ისას `main`-ში (`<component>-release.yml`; Kura-სთვის, გამოძახებულია `server-production-deployment.yml`-ით, როცა `kura/` შეიცვალა) |
| რელიზის კანდიდატი | `X.Y.0-rc.N` | ყოველ ორშაბათს, ან ხელით, `releases/<component>-<major>.<minor>.x` ბრენჩზე (`<component>-rc.yml`) |
| სტაბილური | `X.Y.Z` | ყოველ ორშაბათს, ან ხელით, გამწიფებული RC-ის პრომოციით (`<component>-promote.yml`); პეტჩები `<component>-backport.yml`-ის მეშვეობით |

Canary და RC აწყობები ქვეყნდება როგორც GitHub პრერელიზები (არასდროს მონიშნულია "Latest"-ად, არასდროს გადაადგილებს `:latest`-ს GHCR-ზე, არასდროს იგზავნება Homebrew-ში CLI-სთვის), ასე რომ პაკეტების მენეჯერები და image resolver-ები მათ იღებენ მხოლოდ ცალსახა opt-in-ისას. Canary ყოველთვის ისახავს მიზნად შემდეგ გამოუშვებელ მინორულს: როგორც კი RC ხაზი მოიჭრება, `main`-ის canary გადადის შემდეგ მინორულზე.

Hosted Tuist არ ელოდება სტაბილურ ტრეინს: სერვერი დეპლოიმენტს აკეთებს კომიტზე, ხოლო hosted canary და production უშვებენ Kura-ს უახლეს canary-ს. დეპლოიმენტის კასკადი აქვეყნებს ამ canary-ს თავად მის დეპლოიმენტამდე, ასე რომ `kura-release.yml`-ს არ აქვს საკუთარი ტრიგერი. ცვლილებები მხოლოდ Kura-ს რელიზის ინსტრუმენტებში (`mise/tasks/kura/**`, `kura-*.yml` workflow-ები) არ ჭრის canary-ს.

თქვენ არასდროს ირჩევთ ვერსიის ნომრებს ხელით. თითოეული არხის შემდეგი ვერსია მიღებულია არსებული git ტეგებიდან `mise/tasks/<component>/release/channel-version.sh`-ის მიერ, რომელსაც ქვემოთ მოცემული workflow-ები იძახებენ.

რელიზის ბრენჩები დაყოფილია კომპონენტების მიხედვით (`releases/server-X.Y.x`, `releases/kura-X.Y.x`, `releases/X.Y.x` CLI-სთვის), რათა სამი კომპონენტის ხაზები არასდროს შეეჯახონ ერთსა და იმავე მინორულზე.

### ყოველკვირეული განრიგი

ყოველ ორშაბათს 06:00 UTC-ზე, სამი კომპონენტის პრომოციის სამუშაოები ერთდროულად ეშვება: **CLI Promote to Stable**, **Server Promote to Stable** და **Kura Promote to Stable**. თითოეული ახდენს უახლესი RC ხაზის პრომოციას, რომელიც ჯერ არ არის სტაბილური, რაც ჩვეულებრივ არის წინა ორშაბათს მოჭრილი ხაზი. თუ ასეთი ხაზი არ არსებობს, ეს სამუშაო არაფერს აქვეყნებს.

როდესაც პრომოცია სრულდება, შედეგის მიუხედავად, მისი შესაბამისი **რელიზის კანდიდატის** workflow (`cli-rc.yml`, `server-rc.yml`, `kura-rc.yml`) ეშვება `workflow_run`-ის მეშვეობით და ჭრის შემდეგ ხაზს `main`-დან.

თუ რომელიმე დაგეგმილი გაშვება ვერ ხერხდება ან გაუქმებულია, Slack-ზე იგზავნება შეტყობინება. პრომოცია ვერ ხერხდება, როდესაც რელიზის ბრენჩს აქვს კომიტები მისი უახლესი RC-ის შემდეგ. იმ ხაზის გასაშვებად, მოჭერით მასზე ახალი RC და გააკეთეთ მისი პრომოცია ხელით. წინააღმდეგ შემთხვევაში, შემდეგ ორშაბათს პრომოციას გაუკეთებს უფრო ახალ ხაზს.

### რელიზის კანდიდატის მოჭრა

ახალი ხაზის მოსაჭრელად ყოველკვირეული განრიგის გარეთ (ჩაანაცვლეთ ქვემოთ კომპონენტის workflow-ის სახელი):

1. გაუშვით **\<Component\> Release Candidate** workflow (მაგალითად, `server-rc.yml`) ცარიელი `branch` შეყვანით.
2. ის აქვეყნებს `X.Y.0-rc.1` და, წარმატების შემდეგ, ქმნის დაცულ `releases/<component>-X.Y.x` ბრენჩს აწყობილ კომიტზე.

კრიტიკული შესწორების ან რეგრესიის soaking ხაზში ჩასართავად, გადაიტანეთ ის რელიზის ბრენჩზე PR-ის მეშვეობით (იგივე ნაკადი, რაც backport-ებისთვის; CI არასდროს აკეთებს cherry-pick-ს), შემდეგ გაიმეორეთ RC:

1. გადადით `releases/<component>-X.Y.x`-დან, გააკეთეთ fix-ის cherry-pick, გახსენით PR უკან რელიზის ბრენჩში, მოაგვარეთ ნებისმიერი კონფლიქტი და გააერთიანეთ.
2. კიდევ ერთხელ გაუშვით **Release Candidate** workflow `branch=releases/<component>-X.Y.x`-ით. ის აქვეყნებს `X.Y.0-rc.(N+1)`-ს ბრენჩის HEAD-იდან.

Soaking ხაზი არის ფუნქციებით გაყინული: მასზე მხოლოდ კრიტიკული შესწორებები და რეგრესიები თავსდება.

### სტაბილურზე პრომოცია

ხაზის სტაბილურზე პრომოციისთვის ყოველკვირეული განრიგის გარეთ, მისი RC-ის სუფთად soaking-ის შემდეგ:

1. გაუშვით **\<Component\> Promote to Stable** workflow (მაგალითად, `server-promote.yml`) `branch=releases/<component>-X.Y.x`-ით.
2. ის აქვეყნებს semver-ით მონიშნულ იმიჯს `make_latest=true`-ით, გადააქვს GHCR `:latest` ტეგი და GitHub-ის „Latest“ მაჩვენებელი. CLI ასევე ანახლებს Homebrew ფორმულას.

პრომოცია არ ეშვება, თუ ბრენჩის HEAD ზუსტად არ ემთხვევა კომიტს, რომელზეც მიუთითებს უახლესი RC. ამიტომ, თუ ბოლო RC-ის შემდეგ ხაზზე რაიმე შესწორება გაერთიანდა, უნდა მოჭრათ ახალი RC და დაუშვათ მისი soaking, სანამ ის სტაბილურად გაიშვება.

### შესწორებების backport-ირება სტაბილურ ხაზზე

როდესაც ხაზი სტაბილურია, პატჩები გაუშვით მხოლოდ CLI-სთვის განკუთვნილი **Backport Release** workflow-ით (`cli-backport.yml`): გადაიტანეთ შესწორება `releases/X.Y.x`-ზე PR-ის მეშვეობით, შემდეგ გაუშვით workflow ამ ბრენჩით `X.Y.(Z+1)`-ის მოსაჭრელად. Backport-ები არასდროს გადააადგილებენ „Latest“ მაჩვენებელს ან Homebrew ფორმულას. ერთდროულად ორი ხაზი ნარჩუნდება: მიმდინარე ხაზი იღებს რეგრესიებს და უსაფრთხოების შესწორებებს, წინა ხაზი — მხოლოდ კრიტიკულ და უსაფრთხოების შესწორებებს. სხვა bug fix-ები არ backport-ირდება და შემდეგ მინორულთან ერთად გამოიცემა.

სერვერისა და Kura-სთვის გამოიყენეთ **Server Backport Release** (`server-backport.yml`) ან **Kura Backport Release** (`kura-backport.yml`). პრომოცია აქვეყნებს მხოლოდ RC-ის `X.Y.0`-ს; მას არ შეუძლია უკვე სტაბილური ხაზის პატჩირება.

1. დაიწყეთ შერჩეული `X.Y` ხაზის უახლესი გამოქვეყნებული სტაბილური კომპონენტის ტეგიდან და გახსენით ქირურგიული შესწორების PR მის არსებულ `releases/server-X.Y.x` ან `releases/kura-X.Y.x` ბრენჩში. უფრო ახალი მინორული ან მაჟორული რელიზი არ ხელს უშლის შენარჩუნებული ხაზის პატჩირებას. არ ჩართოთ main-ის არარელევანტური ცვლილებები.
2. გადახედეთ და გააერთიანეთ წყაროს PR. ჩამოიტანეთ დისტანციური რელიზის ბრენჩი და დააკვალიფიცირეთ მისი **საბოლოო გაერთიანებული tip**, კომპონენტის მხარდაჭერილი პლატფორმებისა და TLS დადებითი/უარყოფითი კონტროლების ჩათვლით. წარმატებული pre-merge head არ არის სხვა squash ან merge კომიტის კვალიფიკაცია.
3. ცალკეული გამოქვეყნების დამტკიცებით, გაუშვით შესაბამისი backport workflow **main-დან**, `source_sha`-ის მითითებით ზუსტად იმ კვალიფიცირებულ გაერთიანებულ tip-ზე და `base_tag`-ის — მიმდინარე სტაბილურ ტეგზე, როგორიცაა `server@X.Y.Z` ან `kura@X.Y.Z`. workflow გამოიყვანს `X.Y.(Z+1)`-ს; ოპერატორები არ ირჩევენ მინორულ bump-ს ან არ აკეთებენ canary შიგთავსის პრომოციას.

დაგეგმვა ანახლებს ზუსტ დისტანციურ ბრენჩსა და საბაზო ტეგს, მოითხოვს, რომ შერჩეული წყარო ემთხვეოდეს ბრენჩის tip-ს, უარყოფს შეუცვლელ წყაროს ან კომპონენტის გარეთ ცვლილებებს, მის trust-policy შეყვანებსა და ვალიდაციას და ამაგრებს ამოხსნილ საბაზო კომიტს. Main-ზე დაფუძნებული კონტროლები იმეორებენ ამ შემოწმებებს ვერსიით მონიშნული იმიჯისა და GitHub-ზე გამოქვეყნებამდე. თუ წყაროს ბრენჩი, სტაბილური საბაზო ან ხელმისაწვდომი ვერსია იცვლება, შეწყვიტეთ და ხელახლა დააკვალიფიცირეთ, ნაცვლად ახალი წყაროს ჩანაცვლებისა.

Backport-ები იყენებენ არსებულ მულტიპლატფორმიან გამომქვეყნებლებს GitHub-ის „Latest“ მაჩვენებლის ან GHCR `:latest`-ის გადაადგილების გარეშე. გამოქვეყნება გამოყოფილია hosted განთავსებისგან: ეს workflows არ აკეთებენ hosted სერვერის ან Kura ფლოტის პრომოციას, არ აუქმებენ canary მიღებას ან არ აკვალიფიცირებენ ინსტალირებულ runtime-ს. Build-ის დამხმარე საშუალებები და Dockerfiles კვლავ მოდის შერჩეული სტაბილური წყაროდან. კონტროლები არის გამოქვეყნების კარიბჭეები, არა credential-free build სამუშაოები; builds-ებს შეუძლიათ ატვირთონ untagged იმიჯის digests საბოლოო კარიბჭემდე. იმიჯისა და GitHub-ზე გამოქვეყნება არ არის ატომური: თუ გვიანდელი კარიბჭე ვერ ხერხდება იმიჯის ტეგის გამოქვეყნების შემდეგ, შეამოწმეთ ნაწილობრივი რელიზი და შეინარჩუნეთ მისი საწყისი წყარო და არტეფაქტები. არასდროს ჩაანაცვლოთ არსებული რელიზი ან არ გამოიყენოთ სხვა байты მისი ტეგის ქვეშ.

## კარგი კომიტის შეტყობინებების წერა

ვინაიდან კომიტის შეტყობინებები პირდაპირ მოქმედებენ რელიზის შენიშვნებზე, მნიშვნელოვანია წეროთ ნათელი, აღწერითი შეტყობინებები:

### გაკეთეთ:
- გამოიყენეთ present tense: „add feature“ და არა „added feature“
- იყავით მოკლე, მაგრამ აღწერითი
- ჩართეთ scope, როდესაც ცვლილებები კომპონენტის სპეციფიკურია
- მიუთითეთ issues, როდესაც შესაბამისია: `fix(cli): resolve build cache issue (#1234)`

### არ გააკეთოთ:
- არ გამოიყენოთ ბუნდოვანი შეტყობინებები, როგორიცაა „fix bug“ ან „update code“
- არ აურიოთ რამდენიმე არარელევანტური ცვლილება ერთ კომიტში
- არ დაგავიწყდეთ breaking change ინფორმაციის ჩართვა

### Breaking changes

Breaking changes-ისთვის, ჩართეთ `BREAKING CHANGE:` კომიტის ძირითად ნაწილში:

```
feat(cli): change cache directory structure

BREAKING CHANGE: Cache files are now stored in a new directory structure.
Users need to clear their cache after updating.
```

## რელიზის workflows

CLI-ს, სერვერსა და Kura-ს თითოეულს აქვს არხების workflows-ის საკუთარი ნაკრები, იგივე სტრუქტურის მიხედვით:

- `<component>-release.yml` - აქვეყნებს canary-ს ყოველ კომპონენტის შემხებ push-ზე `main`-ზე (Kura-ს არის ხელახლა გამოყენებადი workflow, რომელსაც `server-production-deployment.yml` უწოდებს, როდესაც `kura/` იცვლება)
- `<component>-rc.yml` - ჭრის რელიზის კანდიდატს ყოველ ორშაბათს (`workflow_run`-ის მეშვეობით პრომოციის შემდეგ), ან ხელით ჭრის ან აუმჯობესებს ერთ-ერთს
- `<component>-promote.yml` - აკეთებს მოლოდინში მყოფი RC-ის პრომოციას სტაბილურზე ყოველ ორშაბათს 06:00 UTC-ზე, ან ხელით აკეთებს soaked RC-ის პრომოციას
- `<component>-build-publish.yml` - საერთო build და გამოქვეყნების pipeline, რომელსაც ზემოთ ჩამოთვლილი სამი უწოდებს

CLI-ს, სერვერსა და Kura-ს ასევე აქვთ `<component>-backport.yml` სტაბილურ ხაზზე პატჩების მოსაჭრელად. კომპონენტის ყველა workflow სერიალიზდება ერთი `<component>-publish` concurrency ჯგუფის მეშვეობით, რათა ვერსიის ამოხსნა და ტეგირება არასდროს შეეჯახოს. Kura არის გამონაკლისი: მისი canary იყენებს `kura-canary-publish`-ს, ხოლო მისი RC, promote და backport იყენებენ `kura-stable-publish`-ს, რათა ხანგრძლივმა სტაბილურმა build-მა არ შეაფერხოს განთავსების კასკადი. ტეგების სივრცეები დისჯუნქტურია, ამიტომ ორი ჯგუფი არ შეეჯახება.

Helm chart და ინფრასტრუქტურის image-ები (CAPI operator, runners controller, xcresult processor image, linux runner image და სხვა) კვლავ გამოიცემა `.github/workflows/server-production-deployment.yml`-ის მეშვეობით. ის ეშვება push-ებზე `main`-ზე და ახორციელებს canary → acceptance tests → production კასკადს hosted განთავსებისთვის, ასევე აქვეყნებს ამ ინფრასტრუქტურის კომპონენტებს მათი ცვლილებისას. აპლიკაციას, cache-ს, Gradle plugin-ს, skills-ს, Noora-ს და დამოუკიდებელ infra controllers-ს თითოეულს აქვს საკუთარი `*-release.yml` workflow. ყველა მათგანი იზიარებს ცვლილებების აღმოჩენას: `mise/tasks/release/components.json` აცხადებს თითოეული კომპონენტის ტეგის პრეფიქსს და include ბილიკებს, ხოლო git cliff შესაბამის კომიტებს გარდაქმნის რელიზის შენიშვნებად.

CLI build (`cli-build-publish.yml`) ასევე ქმნის და აქვეყნებს `tuist.spec.json` არტიფაქტს (გენერირებული `tuist --experimental-dump-help`-დან), რათა downstream tooling-მა შეძლოს command interface-ის მოხმარება.

## პრობლემების გადაჭრა

თუ რელიზი ვერ ხერხდება:

1. შეამოწმეთ GitHub Actions ლოგები ვერ მოხერხებული workflow-სთვის
2. დარწმუნდით, რომ თქვენი კომიტის შეტყობინებები ემორჩილება კონვენციურ ფორმატს
3. დაადასტურეთ, რომ ყველა ტესტი წარმატებით გადის
4. შეამოწმეთ, რომ კომპონენტი წარმატებით ბილდება

სასწრაფო გამოსწორებებისთვის, რომლებსაც საჭიროებს დაუყოვნებელი რელიზი:
1. დარწმუნდით, რომ თქვენს კომიტს აქვს ნათელი სკოუპი
2. შერწყმის შემდეგ, აკონტროლეთ რელიზის workflow
3. სერვერის ან აპლიკაციისთვის, გამოსწორება გამოიცემა შემდეგ push-ზე; საჭიროების შემთხვევაში, გაუშვით ხელით რელიზი
4. CLI-სთვის, გამოსწორება ავტომატურად ხვდება canary-ზე. სტაბილურ მომხმარებლებთან მისაღწევად, გააკეთეთ მისი backport შენარჩუნებულ სტაბილურ ხაზ(ებ)ზე (იხილეთ [გამოსწორებების backport-ი სტაბილურ ხაზზე](#backporting-fixes-to-a-stable-line))

## App Store რელიზი

მიუხედავად იმისა, რომ CLI და Server მიჰყვებიან ზემოთ აღწერილ უწყვეტ რელიზის პროცესს, **iOS აპლიკაცია** არის გამონაკლისი Apple-ის App Store განხილვის პროცესის გამო:

- **ხელით რელიზები**: iOS აპლიკაციის რელიზები მოითხოვს ხელით წარდგენას App Store-ში
- **განხილვის დაყოვნებები**: თითოეულ რელიზს უნდა გაიაროს Apple-ის განხილვის პროცესი, რასაც 1-7 დღე შეიძლება დასჭირდეს
- **ჯგუფური ცვლილებები**: მრავალი ცვლილება ჩვეულებრივ ერთად იკრიბება თითოეულ iOS რელიზში
- **TestFlight**: Beta ვერსიები შეიძლება გავრცელდეს TestFlight-ის მეშვეობით App Store რელიზამდე
- **რელიზის შენიშვნები**: უნდა დაიწეროს სპეციფიკურად App Store-ის სახელმძღვანელოებისთვის

iOS აპლიკაცია კვლავ მიჰყვება იგივე კომიტის კონვენციებს და იყენებს git cliff-ს changelog-ის გენერირებისთვის, მაგრამ მომხმარებლებისთვის ფაქტობრივი რელიზი ხდება ნაკლებად ხშირი, ხელით გრაფიკის მიხედვით.
