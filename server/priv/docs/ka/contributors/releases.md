# გამოშვებები

Tuist ახალ ვერსიებს ავტომატურად აქვეყნებს, როდესაც ცვლილებები main შტოში ერწყმის. CLI, სერვერი და Kura ქეშ-სერვერი ყველა გამოშვების არხებით (canary, release candidate, stable) ნაწილდება, რათა რეკომენდებული ინსტალაცია სტაბილური და ნელი დარჩეს; release candidate-ის მოჭრა და მისი stable-ზე გადაყვანა განზრახული, კვირეული ნაბიჯებია. აპლიკაცია უწყვეტად გამოიცემა (iOS აპლიკაცია მხოლოდ TestFlight-ზე ნაწილდება უწყვეტად, იხილეთ მეტი [აქ](#app-store-release)).

## მიმოხილვა

ჩვენ ვუშვებთ ამ ძირითად კომპონენტებს:
- **Tuist CLI** - ბრძანებათა ხაზის ინსტრუმენტი, რომელიც canary, release candidate და stable [არხებით](#release-channels) ნაწილდება
- **Tuist Server** - ბექენდის სერვისები, რომლებიც CLI-ის იგივე არხის მოდელით ნაწილდება
- **Kura** - ქეშ-სერვერი, რომელიც CLI-ის იგივე არხის მოდელით ნაწილდება
- **Tuist App** - macOS და iOS აპლიკაციები, რომლებიც უწყვეტად გამოიცემა (iOS აპლიკაცია მხოლოდ TestFlight-ზე ნაწილდება უწყვეტად, იხილეთ მეტი [აქ](#app-store-release))

`main`-ზე ყოველი პუში CLI-ის, სერვერისა და Kura-სთვის canary წინასწარ გამოშვებას აქვეყნებს. თითოეული ამ კომპონენტისთვის stable გამოშვება მხოლოდ მაშინ იჭრება, როდესაც შენარჩუნების პასუხისმგებელი „დაჟენებულ“ release candidate-ს აწინაურებს, ხოლო კვირეული გრაფიკი სამივე „მატარებელს“ ერთდროულად ააქტიურებს (იხილეთ [გამოშვების არხები](#release-channels)). აპლიკაცია `main`-ზე ყოველ პუშზე stable-ს აქვეყნებს.

## როგორ მუშაობს

### 1. კომიტების კონვენციები

ჩვენ ვიყენებთ [Conventional Commits](https://www.conventionalcommits.org/)-ს ჩვენი კომიტების შეტყობინებების სტრუქტურირებისთვის. ეს საშუალებას აძლევს ჩვენს ინსტრუმენტებს გაიგონ ცვლილებების ბუნება, განსაზღვრონ ვერსიის მატება და შექმნან შესაბამისი ცვლილებათა ჟურნალები.

ფორმატი: `type(scope): description`

#### კომიტის ტიპები და მათი გავლენა

| ტიპი | აღწერა | ვერსიის გავლენა | მაგალითი |
|------|-------------|----------------|---------|
| `feat` | ახალი ფუნქცია ან შესაძლებლობა | მინორული ვერსიის მატება (x.Y.z) | `feat(cli): add support for Swift 6` |
| `fix` | შეცდომის გამოსწორება | პეტჩის ვერსიის მატება (x.y.Z) | `fix(app): resolve crash when opening projects` |
| `docs` | დოკუმენტაციის ცვლილებები | გამოშვება არ ხდება | `docs: update installation guide` |
| `style` | კოდის სტილის ცვლილებები | გამოშვება არ ხდება | `style: format code with swiftformat` |
| `refactor` | კოდის რეფაქტორინგი | გამოშვება არ ხდება | `refactor(server): simplify auth logic` |
| `perf` | წარმადობის გაუმჯობესება | პეტჩის ვერსიის მატება | `perf(cli): optimize dependency resolution` |
| `test` | ტესტების დამატება/ცვლილება | გამოშვება არ ხდება | `test: add unit tests for cache` |
| `chore` | ტექნიკური მოვლა | გამოშვება არ ხდება | `chore: update dependencies` |
| `ci` | CI/CD ცვლილებები | გამოშვება არ ხდება | `ci: add workflow for releases` |

CLI-ისთვის ეს მატებები განსაზღვრავენ canary ვერსიას და ცვლილებათა ჟურნალის დაჯგუფებას. Stable CLI ვერსიები არის ხელით მოჭრილი მინორული ხაზები (`X.Y.0`), ხოლო stable პეტჩები (`X.Y.Z`) მხოლოდ backport-ებიდან მოდის, ამიტომ `feat` ან `fix` CLI-ის მომხმარებლებამდე ქვემოთ მოცემული არხის ნაკადით აღწევს და არა როგორც უშუალო stable გამოშვება.

#### დამრღვევი ცვლილებები

დამრღვევი ცვლილებები იწვევს მაჟორული ვერსიის მატებას (X.0.0) და უნდა იყოს მითითებული კომიტის ძირითად ნაწილში:

```
feat(cli): change default cache location

BREAKING CHANGE: The cache is now stored in ~/.tuist/cache instead of .tuist-cache.
Users will need to clear their old cache directory.
```

### 2. ცვლილებების აღმოჩენა

თითოეული კომპონენტი იყენებს [git cliff](https://git-cliff.org/)-ს, რათა:
- გაანალიზოს კომიტები ბოლო გამოშვების შემდეგ
- გაფილტროს კომიტები სკოპის მიხედვით (cli, app, server)
- დაადგინოს, არის თუ არა გამოსაქვეყნებელი ცვლილებები
- ავტომატურად შექმნას ცვლილებათა ჟურნალები

### 3. გამოშვების პაიპლაინი

როდესაც აღმოჩენილია გამოსაქვეყნებელი ცვლილებები:

1. **ვერსიის გამოთვლა**: პაიპლაინი განსაზღვრავს შემდეგი ვერსიის ნომერს
2. **ცვლილებათა ჟურნალის გენერაცია**: git cliff ქმნის ცვლილებათა ჟურნალს კომიტების შეტყობინებებიდან
3. **აგების პროცესი**: კომპონენტი აგებული და ტესტირებულია
4. **არტეფაქტების გენერაცია**: იქმნება გამოშვებისთვის სპეციფიკური რესურსები, როგორიცაა CLI ბუნდლები, საკონტროლო ჯამები და `tuist --experimental-dump-help`-დან გენერირებული `tuist.spec.json` CLI სპეციფიკაცია
5. **გამოშვების შექმნა**: იქმნება GitHub გამოშვება არტეფაქტებით
6. **გავრცელება**: განახლებები იგზავნება პაკეტების მენეჯერებში (მაგ., Homebrew CLI-ისთვის)

აპისთვის ეს ყოველ შერწყმაზე stable გამოშვებას წარმოქმნის. CLI-ის, სერვერისა და Kura-სთვის, ეს same ავტომატური პაიპლაინი მხოლოდ **canary** პრერელიზს ქმნის; რელიზ კანდიდატები და stable გამოშვებები იჭრება ყოველკვირეულ რელიზ ტრეინზე (იხ. [გამოშვების არხები](#release-channels)).

### 4. სკოპის ფილტრაცია

თითოეული კომპონენტი გამოიცემა მხოლოდ მაშინ, როცა მას აქვს შესაბამისი ცვლილებები:

- **CLI**: კომიტები `(cli)` სკოპით ან სკოპის გარეშე
- **App**: კომიტები `(app)` სკოპით
- **Server**: კომიტები `(server)` სკოპით

## გამოშვების არხები

CLI, სერვერი და Kura არ გადადიან stable გამოშვებაზე `main`-ზე ყოველი push-ისას. თითოეული სამი არხით გამოიცემა, რათა რეკომენდებული ინსტალაცია დარჩეს stable და ნელა მოძრავი, ხოლო ადრეულმა მომხმარებლებმა შეინარჩუნონ კომიტზე დაფუძნებული აგებები. მომხმარებლისთვის განკუთვნილი დოკუმენტაცია განთავსებულია <.localized_link href="/cli/release-channels">CLI გამოშვების არხები</.localized_link> და <.localized_link href="/guides/server/self-host/release-channels">სერვერის გამოშვების არხები</.localized_link>-ზე; ეს სექცია არის მეინტეინერის სახელმძღვანელო.

თითოეული კომპონენტი იყენებს ერთსა და იმავე სამ არხს:

| არხი | ვერსია | მოჭრა |
|---------|---------|--------|
| Canary | `X.Y.0-canary.N` | ავტომატურად, `main`-ზე ყოველი კომპონენტის შემხები push-ისას (`<component>-release.yml`; Kura-სთვის, გამოძახებულია `server-production-deployment.yml`-ით, როცა `kura/` შეიცვალა) |
| რელიზ კანდიდატი | `X.Y.0-rc.N` | ყოველ ორშაბათს, ან ხელით, `releases/<component>-<major>.<minor>.x` ბრენჩზე (`<component>-rc.yml`) |
| Stable | `X.Y.Z` | ყოველ ორშაბათს, ან ხელით, გაჟღენთილი RC-ის პრომოუშენით (`<component>-promote.yml`); პეტჩები `<component>-backport.yml`-ით |

Canary და RC აგებები ქვეყნდება როგორც GitHub პრერელიზები (არასდროს მონიშნული როგორც "Latest", არასდროს გადაადგილებს `:latest`-ს GHCR-ზე, არასდროს იგზავნება Homebrew-ში CLI-ისთვის), ამიტომ პაკეტების მენეჯერები და სურათების რეზოლვერები მათ მხოლოდ ცხადი opt-in-ისას იღებენ. Canary ყოველთვის მიემართება შემდეგ გამოუქვეყნებელ მინორულ ვერსიაზე: როგორც კი RC ხაზი მოიჭრება, `main`-ის canary გადადის შემდეგ მინორულზე.

Hosted Tuist არ ელოდება stable ტრეინს: სერვერი დეპლოიდება კომიტზე, ხოლო hosted canary და production უშვებენ უახლეს Kura canary-ს. დეპლოიმენტის კასკადი აქვეყნებს ამ canary-ს მის დეპლოიმენტამდე, ამიტომ `kura-release.yml`-ს არ აქვს საკუთარი ტრიგერი. ცვლილებები მხოლოდ Kura-ს გამოშვების ინსტრუმენტებში (`mise/tasks/kura/**`, `kura-*.yml` workflow-ები) არ ჭრის canary-ს.

თქვენ არასდროს ირჩევთ ვერსიის ნომრებს ხელით. თითოეული არხის შემდეგი ვერსია მიღებულია არსებული git ტეგებიდან `mise/tasks/<component>/release/channel-version.sh`-ით, რომელსაც ქვემოთ მოცემული workflow-ები იძახებენ.

გამოშვების ბრენჩები დაყოფილია კომპონენტების მიხედვით (`releases/server-X.Y.x`, `releases/kura-X.Y.x`, `releases/X.Y.x` CLI-ისთვის), რათა სამი კომპონენტის ხაზები არასდროს შეეჯახოს ერთსა და იმავე მინორულზე.

### ყოველკვირეული განრიგი

ყოველ ორშაბათს 06:00 UTC-ზე, სამი კომპონენტის promote სამუშაოები ერთდროულად მუშაობენ: **CLI Promote to Stable**, **Server Promote to Stable** და **Kura Promote to Stable**. თითოეული აწინაურებს უახლეს RC ხაზს, რომელიც ჯერ არ არის stable, რაც ჩვეულებრივ წინა ორშაბათს მოჭრილი ხაზია. თუ ასეთი ხაზი არ არსებობს, ეს სამუშაო არაფერს აქვეყნებს.

როდესაც promote სრულდება, შედეგის მიუხედავად, მისი შესაბამისი **რელიზ კანდიდატი** workflow (`cli-rc.yml`, `server-rc.yml`, `kura-rc.yml`) იწყება `workflow_run`-ით და ჭრის შემდეგ ხაზს `main`-დან.

თუ რომელიმე დაგეგმილი გაშვება ვერ მოხერხდა ან გაუქმდა, Slack-ზე იგზავნება შეტყობინება. პრომოუშენი ვერ ხერხდება, როცა გამოშვების ბრენჩს აქვს კომიტები მისი უახლესი RC-ის შემდეგ. ამ ხაზის გამოსაშვებად, მასზე უნდა მოიჭრას ახალი RC და ხელით უნდა მოხდეს მისი პრომოუშენი. წინააღმდეგ შემთხვევაში, შემდეგ ორშაბათს უფრო ახალი ხაზი აწინაურდება.

### რელიზ კანდიდატის მოჭრა

ახალი ხაზის მოსაჭრელად ყოველკვირეული განრიგის გარეთ (ქვემოთ ჩაანაცვლეთ კომპონენტის workflow-ის სახელი):

1. გაუშვით **\<Component\> Release Candidate** workflow (მაგალითად, `server-rc.yml`) ცარიელი `branch` შეყვანით.
2. ის აქვეყნებს `X.Y.0-rc.1` და, წარმატების შემდეგ, ქმნის დაცულ `releases/<component>-X.Y.x` ბრენჩს აწყობილ კომიტზე.

კრიტიკული ფიქსის ან რეგრესიის soaking ხაზში შესატანად, გადაიტანეთ ის PR-ით გამოშვების ბრენჩზე (იგივე ნაკადი, რაც backport-ებისთვის; CI არასდროს აკეთებს cherry-pick-ს), შემდეგ გაიმეორეთ RC:

1. გადადით `releases/<component>-X.Y.x`-დან, გააკეთეთ fix-ის cherry-pick, გახსენით PR უკან გამოშვების ბრენჩში, გადაწყვიტეთ ნებისმიერი კონფლიქტი და გააერთიანეთ.
2. გაუშვით **Release Candidate** workflow კიდევ ერთხელ `branch=releases/<component>-X.Y.x`-ით. ის აქვეყნებს `X.Y.0-rc.(N+1)` ბრენჩის HEAD-დან.

Soaking ხაზი არის feature-frozen: მასზე მხოლოდ კრიტიკული ფიქსები და რეგრესიები თავსდება.

### Stable-ზე პრომოუშენი

ხაზის stable-ზე ასაწევად ყოველკვირეული განრიგის გარეთ, მისი RC-ის სუფთად soaking-ის შემდეგ:

1. გაუშვით **\<Component\> Promote to Stable** workflow (მაგალითად, `server-promote.yml`) `branch=releases/<component>-X.Y.x`-ით.
2. ის აქვეყნებს semver-ტეგირებულ image-ს `make_latest=true`-ით, გადააქვს GHCR `:latest` ტეგი და GitHub „Latest“ მაჩვენებელი. CLI ასევე ანახლებს Homebrew ფორმულას.

პრომოუშენი არ იწყება, თუ ბრენჩის HEAD ზუსტად არ ემთხვევა კომიტს, რომელზეც უახლესი RC მიუთითებს. ამიტომ, თუ ბოლო RC-ის შემდეგ ხაზზე რაიმე ფიქსი გაერთიანდა, უნდა მოჭრა ახალი RC და დატოვოთ ის soaking-ზე, სანამ stable-ად გამოიცემა.

### ფიქსების backport-ing stable ხაზზე

როგორც კი ხაზი stable ხდება, პაჩების გამოსაცემად გამოიყენეთ მხოლოდ CLI-სთვის განკუთვნილი **Backport Release** workflow (`cli-backport.yml`): გადაიტანეთ fix `releases/X.Y.x`-ზე PR-ით, შემდეგ გაუშვით workflow ამ ბრენჩით, რათა მოიჭრას `X.Y.(Z+1)`. Backport-ები არასდროს გადააადგილებენ „Latest“ მაჩვენებელს ან Homebrew ფორმულას. ერთდროულად ორი ხაზი ინახება: მიმდინარე ხაზი იღებს რეგრესიებს და უსაფრთხოების ფიქსებს, წინა ხაზი — მხოლოდ კრიტიკულ და უსაფრთხოების ფიქსებს. სხვა bug fix-ები არ backport-დება და გამოიცემა შემდეგ მინორულთან ერთად.

სერვერისა და Kura-სთვის, backport-ები დღეს იჭრება promote workflow-ის გაშვებით ძველ გამოშვების ბრენჩზე. მომავალში დაემატება სპეციალური backport workflow-ები, რომლებიც CLI-ს მსგავსი იქნება.

## კარგი კომიტის შეტყობინებების წერა

რადგან კომიტის შეტყობინებები პირდაპირ მოქმედებენ გამოშვების შენიშვნებზე, მნიშვნელოვანია წეროთ ნათელი, აღწერითი შეტყობინებები:

### გააკეთეთ:
- გამოიყენეთ present tense: „add feature“ და არა „added feature“
- იყავით მოკლე, მაგრამ აღწერითი
- მიუთითეთ scope, როცა ცვლილებები კომპონენტის სპეციფიკურია
- მიუთითეთ issues, როცა შესაბამისია: `fix(cli): resolve build cache issue (#1234)`

### არ გააკეთოთ:
- არ გამოიყენოთ ბუნდოვანი შეტყობინებები, როგორიცაა „fix bug“ ან „update code“
- არ აურიოთ ერთ კომიტში რამდენიმე დაუკავშირებელი ცვლილება
- არ დაგავიწყდეთ breaking change ინფორმაციის ჩართვა

### Breaking changes

Breaking changes-ისთვის, ჩართეთ `BREAKING CHANGE:` კომიტის ტექსტში:

```
feat(cli): change cache directory structure

BREAKING CHANGE: Cache files are now stored in a new directory structure.
Users need to clear their cache after updating.
```

## გამოშვების workflow-ები

CLI-ს, სერვერს და Kura-ს თითოეულს აქვს საკუთარი channel workflow-ების ნაკრები, იგივე სტრუქტურით:

- `<component>-release.yml` - აქვეყნებს canary-ს ყოველ კომპონენტის შემხებ push-ზე `main`-ზე (Kura-ს არის ხელახლა გამოყენებადი workflow, რომელსაც `server-production-deployment.yml` უწოდებს, როცა `kura/` იცვლება)
- `<component>-rc.yml` - ჭრის release candidate-ს ყოველ ორშაბათს (`workflow_run`-ით promote-ის შემდეგ), ან ხელით ჭრის ან აუმჯობესებს ერთს
- `<component>-promote.yml` - აწინაურებს მოლოდინში მყოფ RC-ს stable-ზე ყოველ ორშაბათს 06:00 UTC-ზე, ან ხელით აწინაურებს soaked RC-ს
- `<component>-build-publish.yml` - საერთო აწყობისა და გამოქვეყნების pipeline, რომელსაც ზემოთ ჩამოთვლილი სამი იყენებს

CLI-ს ასევე აქვს `cli-backport.yml` stable ხაზზე პაჩების მოსაჭრელად. კომპონენტის ყველა workflow სერიალიზდება ერთი `<component>-publish` concurrency ჯგუფის მეშვეობით, რათა ვერსიის განსაზღვრა და ტეგირება არასდროს შეეჯახოს. Kura არის გამონაკლისი: მისი canary იყენებს `kura-canary-publish`-ს, ხოლო მისი RC და promote იყენებენ `kura-stable-publish`-ს, რათა ხანგრძლივი RC ან promote აწყობა არ შეაფერხოს deploy cascade. ტეგების namespace-ები განცალკევებულია, ამიტომ ორი ჯგუფი არ შეეჯახება.

Helm chart და ინფრასტრუქტურის images (CAPI operator, runners controller, xcresult processor image, linux runner image და ა.შ.) კვლავ გამოიცემა `.github/workflows/server-production-deployment.yml`-ით. ის მუშაობს `main`-ზე push-ებისას და ავრცელებს canary → acceptance tests → production hosted deploy-ისთვის, და აქვეყნებს ამ ინფრასტრუქტურის კომპონენტებს მათი ცვლილებისას. აპს, cache-ს, Gradle plugin-ს, skills-ს, Noora-ს და დამოუკიდებელ infra controllers-ს თითოეულს აქვს სპეციალური `*-release.yml` workflow. ყველა მათგანი იზიარებს ცვლილებების აღმოჩენას: `mise/tasks/release/components.json` აცხადებს თითოეული კომპონენტის ტეგის პრეფიქსს და include paths-ს, ხოლო git cliff შესაბამის კომიტებს გამოშვების შენიშვნებად აქცევს.

CLI აწყობა (`cli-build-publish.yml`) ასევე ქმნის და აქვეყნებს `tuist.spec.json` artifact-ს (გენერირებული `tuist --experimental-dump-help`-დან), რათა downstream tooling-მა შეძლოს command interface-ის გამოყენება.

უწყვეტი გამოშვების მიდგომა უზრუნველყოფს:

- **სწრაფი მიწოდება**: ცვლილებები მომხმარებლებამდე მყისიერად აღწევს შერწყმის შემდეგ
- **შეფერხებების შემცირება**: არ არის საჭირო ხელით გამოშვებების ლოდინი
- **ნათელი კომუნიკაცია**: ავტომატური changelog-ები კომიტების შეტყობინებებიდან
- **თანმიმდევრული პროცესი**: იგივე გამოშვების ნაკადი ყველა კომპონენტისთვის
- **ხარისხის უზრუნველყოფა**: გამოიცემა მხოლოდ დატესტილი ცვლილებები

## პრობლემების გადაჭრა

თუ გამოშვება ვერ მოხერხდა:

1. შეამოწმეთ GitHub Actions ლოგები წარუმატებელი workflow-სთვის
2. დარწმუნდით, რომ თქვენი კომიტების შეტყობინებები ემორჩილება conventional ფორმატს
3. დაადასტურეთ, რომ ყველა ტესტი გადის
4. შეამოწმეთ, რომ კომპონენტი წარმატებით აიწყობა

სასწრაფო შესწორებებისთვის, რომლებსაც დაუყოვნებელი გამოშვება სჭირდებათ:
1. დარწმუნდით, რომ თქვენს კომიტს აქვს ნათელი scope
2. შერწყმის შემდეგ, აკონტროლეთ გამოშვების workflow
3. სერვერის ან აპისთვის, შესწორება გამოიცემა შემდეგ push-ზე; საჭიროების შემთხვევაში, გაუშვით ხელით გამოშვება
4. CLI-სთვის, შესწორება ავტომატურად ხვდება canary-ზე. stable მომხმარებლებისთვის მისაღწევად, გააკეთეთ backport შენარჩუნებულ stable ხაზ(ებ)ზე (იხილეთ [შესწორებების backport-ing stable ხაზზე](#backporting-fixes-to-a-stable-line))

## App Store-ის გამოშვება

მიუხედავად იმისა, რომ CLI და Server მიჰყვებიან ზემოთ აღწერილ უწყვეტ გამოშვების პროცესს, **iOS აპი** არის გამონაკლისი Apple-ის App Store-ის განხილვის პროცესის გამო:

- **ხელით გამოშვებები**: iOS აპის გამოშვებები მოითხოვს App Store-ში ხელით წარდგენას
- **განხილვის დაყოვნებები**: თითოეული გამოშვება უნდა გაიაროს Apple-ის განხილვის პროცესს, რასაც 1-7 დღე შეიძლება დასჭირდეს
- **ჯგუფური ცვლილებები**: მრავალი ცვლილება ჩვეულებრივ ერთად იკრიბება თითოეულ iOS გამოშვებაში
- **TestFlight**: Beta ვერსიები შეიძლება გავრცელდეს TestFlight-ის მეშვეობით App Store-ში გამოშვებამდე
- **გამოშვების შენიშვნები**: უნდა დაიწეროს სპეციფიკურად App Store-ის სახელმძღვანელოებისთვის

iOS აპი კვლავ მიჰყვება იგივე კომიტების კონვენციებს და იყენებს git cliff-ს changelog-ების გენერაციისთვის, მაგრამ რეალური გამოშვება მომხმარებლებისთვის ხდება ნაკლებად ხშირი, ხელით გრაფიკით.
