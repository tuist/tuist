# გამოშვებები

Tuist ავტომატურად აქვეყნებს ახალ ვერსიებს, როდესაც ცვლილებები ერწყმის main შტოს. CLI, სერვერი და Kura ქეშის სერვერი ყველა გამოიცემა რელიზის არხების მეშვეობით (canary, რელიზის კანდიდატი, სტაბილური), რათა რეკომენდებული ინსტალაცია დარჩეს სტაბილური და ნელა მოძრავი; რელიზის კანდიდატის შექმნა და მისი სტაბილურად წარდგენა განზრახული, ყოველკვირეული ნაბიჯებია. აპლიკაცია გამოიცემა უწყვეტად (iOS აპლიკაცია მხოლოდ უწყვეტად ნაწილდება TestFlight-ზე, იხილეთ მეტი [აქ](#app-store-release)).

## მიმოხილვა

ჩვენ ვუშვებთ ამ ძირითად კომპონენტებს:
- **Tuist CLI** - ბრძანების ხაზის ინსტრუმენტი, რომელიც გამოიცემა canary, რელიზის კანდიდატისა და სტაბილური [არხების](#release-channels) მეშვეობით
- **Tuist Server** - უკანა ბოლოს სერვისები, რომლებიც გამოიცემა CLI-ის მსგავსი არხის მოდელით
- **Kura** - ქეშის სერვერი, რომელიც გამოიცემა CLI-ის მსგავსი არხის მოდელით
- **Tuist App** - macOS და iOS აპლიკაციები, რომლებიც გამოიცემა უწყვეტად (iOS აპლიკაცია მხოლოდ უწყვეტად ნაწილდება TestFlight-ზე, იხილეთ მეტი [აქ](#app-store-release))

ყოველი push-ი `main`-ში აქვეყნებს canary პრერელიზს CLI-ისთვის, სერვერისთვის და Kura-სთვის. თითოეული ამ კომპონენტის სტაბილური რელიზი იჭრება მხოლოდ მაშინ, როდესაც შემნარჩუნებელი წარადგენს გაჟღენთილ რელიზის კანდიდატს, ხოლო ყოველკვირეული განრიგი სამივე „მატარებელს“ ერთდროულად ამუშავებს (იხილეთ [რელიზის არხები](#release-channels)). აპლიკაცია აქვეყნებს სტაბილურ ვერსიას `main`-ში ყოველი push-ისას.

## როგორ მუშაობს

### 1. კომიტის კონვენციები

ჩვენ ვიყენებთ [Conventional Commits](https://www.conventionalcommits.org/)-ს ჩვენი კომიტის შეტყობინებების სტრუქტურირებისთვის. ეს საშუალებას აძლევს ჩვენს ინსტრუმენტებს გაიგონ ცვლილებების ბუნება, განსაზღვრონ ვერსიის ამაღლება და შექმნან შესაბამისი ცვლილებათა ჟურნალები.

ფორმატი: `type(scope): description`

#### კომიტის ტიპები და მათი გავლენა

| ტიპი | აღწერა | ვერსიის გავლენა | მაგალითი |
|------|-------------|----------------|---------|
| `feat` | ახალი ფუნქცია ან შესაძლებლობა | მცირე ვერსიის ამაღლება (x.Y.z) | `feat(cli): add support for Swift 6` |
| `fix` | ბაგის გამოსწორება | პატჩის ვერსიის ამაღლება (x.y.Z) | `fix(app): resolve crash when opening projects` |
| `docs` | დოკუმენტაციის ცვლილებები | რელიზი არ არის | `docs: update installation guide` |
| `style` | კოდის სტილის ცვლილებები | რელიზი არ არის | `style: format code with swiftformat` |
| `refactor` | კოდის რეფაქტორინგი | რელიზი არ არის | `refactor(server): simplify auth logic` |
| `perf` | წარმადობის გაუმჯობესება | პატჩის ვერსიის ამაღლება | `perf(cli): optimize dependency resolution` |
| `test` | ტესტების დამატება/ცვლილებები | რელიზი არ არის | `test: add unit tests for cache` |
| `chore` | ტექნიკური მოვლის ამოცანები | რელიზი არ არის | `chore: update dependencies` |
| `ci` | CI/CD ცვლილებები | რელიზი არ არის | `ci: add workflow for releases` |

CLI-ისთვის ეს ამაღლებები განსაზღვრავენ canary ვერსიას და ცვლილებათა ჟურნალის დაჯგუფებას. სტაბილური CLI ვერსიები არის მცირე ხაზები (`X.Y.0`), რომლებიც ხელით იჭრება, ხოლო სტაბილური პატჩები (`X.Y.Z`) მოდის მხოლოდ backport-ებიდან, ამიტომ `feat` ან `fix` აღწევს CLI მომხმარებლებს ქვემოთ მოცემული არხის ნაკადის მეშვეობით და არა როგორც უშუალო სტაბილური რელიზი.

#### დამრღვევი ცვლილებები

დამრღვევი ცვლილებები იწვევს მთავარი ვერსიის ამაღლებას (X.0.0) და უნდა იყოს მითითებული კომიტის ტანში:

```
feat(cli): change default cache location

BREAKING CHANGE: The cache is now stored in ~/.tuist/cache instead of .tuist-cache.
Users will need to clear their old cache directory.
```

### 2. ცვლილებების აღმოჩენა

თითოეული კომპონენტი იყენებს [git cliff](https://git-cliff.org/)-ს:
- კომიტების ანალიზი ბოლო რელიზის შემდეგ
- კომიტების ფილტრაცია სკოპის მიხედვით (cli, app, server)
- რელიზისთვის შესაბამისი ცვლილებების არსებობის დადგენა
- ცვლილებათა ჟურნალის ავტომატური გენერაცია

### 3. რელიზის პაიპლაინი

როდესაც აღმოჩენილია რელიზისთვის შესაბამისი ცვლილებები:

1. **ვერსიის გამოთვლა**: პაიპლაინი განსაზღვრავს მომდევნო ვერსიის ნომერს
2. **ცვლილებათა ჟურნალის გენერაცია**: git cliff ქმნის ცვლილებათა ჟურნალს კომიტების შეტყობინებებიდან
3. **აწყობის პროცესი**: კომპონენტი აიწყობა და ტესტირდება
4. **არტეფაქტების გენერაცია**: წარმოიქმნება რელიზისთვის სპეციფიკური რესურსები, როგორიცაა CLI ბანდლები, საკონტროლო ჯამები და `tuist.spec.json` CLI სპეციფიკაცია, რომელიც გენერირდება `tuist --experimental-dump-help`-დან
5. **რელიზის შექმნა**: იქმნება GitHub რელიზი არტეფაქტებით
6. **გავრცელება**: განახლებები იგზავნება პაკეტების მენეჯერებში (მაგ., Homebrew CLI-ისთვის)

აპისთვის ეს ყოველ შერწყმაზე ქმნის სტაბილურ რელიზს. CLI-ის, სერვერისა და Kura-სთვის, იგივე ავტომატური პაიპლაინი ქმნის მხოლოდ **canary** წინარელიზს; რელიზის კანდიდატები და სტაბილური რელიზები იჭრება ყოველკვირეულ რელიზის მატარებელზე (იხ. [რელიზის არხები](#release-channels)).

### 4. სკოპის ფილტრაცია

თითოეული კომპონენტი აქვეყნებს რელიზს მხოლოდ მაშინ, როცა მას აქვს შესაბამისი ცვლილებები:

- **CLI**: კომიტები `(cli)` სკოპით ან სკოპის გარეშე
- **App**: კომიტები `(app)` სკოპით
- **Server**: კომიტები `(server)` სკოპით

## რელიზის არხები

CLI, სერვერი და Kura არ გადაჰყავთ სტაბილურ რელიზზე `main`-ში ყოველი პუშისას. თითოეული გადის სამი არხის მეშვეობით, რათა რეკომენდებული ინსტალაცია დარჩეს სტაბილური და ნელა მოძრავი, ხოლო ადრეულმა მომხმარებლებმა შეინარჩუნონ კომიტზე დაფუძნებული აწყობები. მომხმარებლისთვის განკუთვნილი დოკუმენტაცია განთავსებულია <.localized_link href="/cli/release/channels">CLI რელიზის არხებზე</.localized_link> და <.localized_link href="/guides/server/self-host/release/channels">სერვერის რელიზის არხებზე</.localized_link>; ეს სექცია არის მემaintenance-ის ინსტრუქცია.

თითოეული კომპონენტი იყენებს ერთსა და იმავე სამ არხს:

| არხი | ვერსია | მოჭრა |
|---------|---------|--------|
| Canary | `X.Y.0-canary.N` | ავტომატურად, კომპონენტის შემხებელი ყოველი პუშისას `main`-ში (`<component>-release.yml`; Kura-სთვის, გამოძახებულია `server-production-deployment.yml`-ით, როცა `kura/` შეიცვალა) |
| რელიზის კანდიდატი | `X.Y.0-rc.N` | ყოველ ორშაბათს, ან ხელით, `releases/<component>-<major>.<minor>.x` ბრენჩზე (`<component>-rc.yml`) |
| სტაბილური | `X.Y.Z` | ყოველ ორშაბათს, ან ხელით, გამწიფებული RC-ის გადაყვანით (`<component>-promote.yml`); პატჩები `<component>-backport.yml`-ის მეშვეობით |

Canary და RC აწყობები ქვეყნდება როგორც GitHub წინარელიზები (არასდროს მონიშნულია "Latest"-ად, არასდროს გადაადგილებს `:latest`-ს GHCR-ზე, არასდროს იგზავნება Homebrew-ში CLI-ისთვის), ამიტომ პაკეტების მენეჯერები და გამოსახულების რეზოლვერები მათ იღებენ მხოლოდ ცალსახა opt-in-ის შემთხვევაში. Canary ყოველთვის ისახავს მიზნად შემდეგ გამოუშვებელ მცირე ვერსიას: როგორც კი RC ხაზი მოიჭრება, `main`-ის canary გადადის შემდეგ მცირე ვერსიაზე.

Hosted Tuist არ ელოდება სტაბილურ მატარებელს: სერვერი დეპლოიდება კომიტზე, ხოლო hosted canary და production უშვებენ უახლეს Kura canary-ს. დეპლოიმენტის კასკადი აქვეყნებს ამ canary-ს თავად მის დეპლოიმენტამდე, ამიტომ `kura-release.yml`-ს არ აქვს საკუთარი ტრიგერი. ცვლილებები მხოლოდ Kura-ს რელიზის ინსტრუმენტებში (`mise/tasks/kura/**`, `kura-*.yml` workflow-ები) არ ჭრის canary-ს.

თქვენ არასდროს ირჩევთ ვერსიის ნომრებს ხელით. თითოეული არხის მომდევნო ვერსია გამოყვანილია არსებული git ტეგებიდან `mise/tasks/<component>/release/channel-version.sh`-ის მიერ, რომელსაც ქვემოთ მოცემული workflow-ები იძახებენ.

რელიზის ბრენჩები დაყოფილია კომპონენტების მიხედვით (`releases/server-X.Y.x`, `releases/kura-X.Y.x`, `releases/X.Y.x` CLI-ისთვის), რათა სამი კომპონენტის ხაზები არასდროს შეეჯახონ ერთსა და იმავე მცირე ვერსიაზე.

### ყოველკვირეული განრიგი

ყოველ ორშაბათს 06:00 UTC-ზე, სამი კომპონენტის promote სამუშაოები ერთდროულად მუშაობენ: **CLI Promote to Stable**, **Server Promote to Stable** და **Kura Promote to Stable**. თითოეული გადაჰყავს უახლეს RC ხაზს, რომელიც ჯერ არ არის სტაბილური, ჩვეულებრივ ეს არის წინა ორშაბათს მოჭრილი ხაზი. თუ ასეთი ხაზი არ არსებობს, ეს სამუშაო არაფერს აქვეყნებს.

როდესაც promote დასრულდება, შედეგის მიუხედავად, მისი შესაბამისი **რელიზის კანდიდატი** workflow (`cli-rc.yml`, `server-rc.yml`, `kura-rc.yml`) იწყება `workflow_run`-ის მეშვეობით და ჭრის შემდეგ ხაზს `main`-დან.

თუ რომელიმე დაგეგმილი გაშვება ვერ მოხერხდება ან გაუქმდება, Slack-ზე იგზავნება შეტყობინება. promotion ვერ ხერხდება, როდესაც რელიზის ბრენჩს აქვს კომიტები მისი უახლესი RC-ის შემდეგ. ამ ხაზის გასაშვებად, მოჭერით ახალი RC მასზე და გადაიყვანეთ ხელით. წინააღმდეგ შემთხვევაში, შემდეგ ორშაბათს გადაიყვანება უფრო ახალი ხაზი.

### რელიზის კანდიდატის მოჭრა

ახალი ხაზის მოსაჭრელად ყოველკვირეული განრიგის გარეთ (ჩაანაცვლეთ კომპონენტის workflow-ის სახელი ქვემოთ):

1. გაუშვით **\<Component\> Release Candidate** workflow (მაგალითად, `server-rc.yml`) ცარიელი `branch` შეყვანით.
2. ის აქვეყნებს `X.Y.0-rc.1` და, წარმატების შემდეგ, ქმნის დაცულ `releases/<component>-X.Y.x` ბრენჩს აგებულ კომიტზე.

კრიტიკული გამოსწორების ან რეგრესიის შესატანად soaking ხაზში, cherry-pick გააკეთეთ მასზე რელიზის ბრენჩში PR-ის მეშვეობით (იგივე ნაკადი, რაც backport-ებისთვის; CI არასდროს აკეთებს cherry-pick-ს), შემდეგ გაიმეორეთ RC:

1. გადაიხარეთ `releases/<component>-X.Y.x`-დან, გააკეთეთ fix-ის cherry-pick, გახსენით PR უკან რელიზის ბრენჩში, გადაწყვიტეთ ნებისმიერი კონფლიქტი და გააერთიანეთ.
2. კვლავ გაუშვით **Release Candidate** workflow `branch=releases/<component>-X.Y.x`-ით. ის აქვეყნებს `X.Y.0-rc.(N+1)`-ს ბრენჩის HEAD-დან.

Soaking ხაზი არის ფუნქციებით გაყინული: მასზე მხოლოდ კრიტიკული გამოსწორებები და რეგრესიები ხვდება.

### სტაბილურზე გადაყვანა

ხაზის სტაბილურზე გადასაყვანად ყოველკვირეული განრიგის გარეთ, მისი RC-ის სუფთა soaking-ის შემდეგ:

1. გაუშვით **\<Component\> Promote to Stable** workflow (მაგალითად, `server-promote.yml`) `branch=releases/<component>-X.Y.x`-ით.
2. ის აქვეყნებს semver-ით მონიშნულ იმიჯს `make_latest=true`-ით, გადააქვს GHCR `:latest` ტეგი და GitHub-ის „Latest“ მაჩვენებელი. CLI ასევე ანახლებს Homebrew ფორმულას.

Promotion არ მუშაობს, თუ ბრენჩის HEAD ზუსტად არ ემთხვევა კომიტს, რომელზეც უახლესი RC მიუთითებს. ამიტომ, თუ ბოლო RC-ის შემდეგ ხაზზე რაიმე გამოსწორება გაერთიანდა, უნდა მოჭრათ ახალი RC და მისცეთ მას soaking-ის დრო, სანამ ის სტაბილურად გაიშვება.

### გამოსწორებების backport-ing სტაბილურ ხაზზე

როდესაც ხაზი სტაბილურია, პატჩები გააშვით მხოლოდ CLI-ისთვის განკუთვნილი **Backport Release** workflow-ით (`cli-backport.yml`): გააკეთეთ fix-ის cherry-pick `releases/X.Y.x`-ზე PR-ის მეშვეობით, შემდეგ გაუშვით workflow ამ ბრენჩით `X.Y.(Z+1)`-ის მოსაჭრელად. Backport-ები არასდროს გადააქვთ „Latest“ მაჩვენებელს ან Homebrew ფორმულას. ერთდროულად ორი ხაზი ინახება: მიმდინარე ხაზი იღებს რეგრესიებსა და უსაფრთხოების გამოსწორებებს, წინა ხაზი — მხოლოდ კრიტიკულ და უსაფრთხოების გამოსწორებებს. სხვა bug fix-ები არ გადაიტანება backport-ით და გაიშვება შემდეგ მცირე ვერსიასთან ერთად.

სერვერისა და Kura-სთვის გამოიყენეთ **Server Backport Release** (`server-backport.yml`) ან **Kura Backport Release** (`kura-backport.yml`). Promotion აქვეყნებს მხოლოდ RC-ის `X.Y.0`-ს; მას არ შეუძლია უკვე სტაბილური ხაზის პატჩინგი.

1. დაიწყეთ შერჩეული `X.Y` ხაზის უახლესი გამოქვეყნებული სტაბილური კომპონენტის ტეგიდან და გახსენით ქირურგიული fix PR მის არსებულ `releases/server-X.Y.x` ან `releases/kura-X.Y.x` ბრენჩში. უფრო ახალი მცირე ან ძირითადი რელიზი არ ხელს უშლის შენარჩუნებული ხაზის პატჩინგს. თავი შეიკავეთ main-ის არარელევანტური ცვლილებებისგან.
2. გადაამოწმეთ და გააერთიანეთ source PR. ჩამოტვირთეთ remote რელიზის ბრენჩი და დააკვალიფიცირეთ მისი **საბოლოო გაერთიანებული tip**, კომპონენტის მხარდაჭერილი პლატფორმებისა და TLS დადებითი/უარყოფითი კონტროლების ჩათვლით. წარმატებული pre-merge head არ არის სხვა squash ან merge კომიტის კვალიფიკაცია.
3. ცალკეული გამოქვეყნების დამტკიცებით, გაუშვით შესაბამისი backport workflow **main-დან**, `source_sha`-ის დაყენებით ზუსტად იმ კვალიფიცირებულ გაერთიანებულ tip-ზე და `base_tag`-ის — მიმდინარე სტაბილურ ტეგზე, როგორიცაა `server@X.Y.Z` ან `kura@X.Y.Z`. workflow გამოიყვანს `X.Y.(Z+1)`-ს; ოპერატორები არ ირჩევენ მცირე ვერსიის აწევას ან canary შიგთავსის გადაყვანას.

Planning აახლებს ზუსტ remote ბრენჩსა და base ტეგს, მოითხოვს, რომ შერჩეული source ემთხვეოდეს ბრენჩის tip-ს, უარყოფს შეუცვლელ source-ს ან კომპონენტის გარეთ ცვლილებებს, მის trust-policy შეყვანებსა და ვალიდაციას, და ამაგრებს გადაწყვეტილ base კომიტს. Main-ზე დაფუძნებული კონტროლები იმეორებენ ამ შემოწმებებს ვერსიიანი იმიჯისა და GitHub-ზე გამოქვეყნებამდე უშუალოდ. თუ source ბრენჩი, სტაბილური base ან ხელმისაწვდომი ვერსია შეიცვლება, შეაჩერეთ და ხელახლა დააკვალიფიცირეთ, ნაცვლად ახალი source-ის ჩანაცვლებისა.

Backport-ები იყენებენ არსებულ მულტიპლატფორმიან გამომქვეყნებლებს GitHub-ის „Latest“ მაჩვენებლის ან GHCR `:latest`-ის გადატანის გარეშე. გამოქვეყნება გამოყოფილია hosted განთავსებისგან: ეს workflows არ გადაჰყავთ hosted სერვერს ან Kura ფლოტს, არ ავლიან canary მიღებას ან არ აკვალიფიცირებენ ინსტალირებულ runtime-ს. Build-ის დამხმარე საშუალებები და Dockerfiles კვლავ მოდის შერჩეული სტაბილური source-დან. კონტროლები არის გამოქვეყნების კარიბჭეები, არა credential-free build სამუშაოები; builds-ებს შეუძლიათ ატვირთონ untagged იმიჯის digests საბოლოო კარიბჭემდე. იმიჯისა და GitHub-ზე გამოქვეყნება არ არის ატომური: თუ მოგვიანებით კარიბჭე ვერ მოხერხდება იმიჯის ტეგის გამოქვეყნების შემდეგ, შეამოწმეთ ნაწილობრივი რელიზი და შეინარჩუნეთ მისი საწყისი source და არტეფაქტები. არასდროს ჩაანაცვლოთ არსებული რელიზი ან გამოიყენოთ სხვა bytes მისი ტეგის ქვეშ.

## კარგი კომიტის შეტყობინებების წერა

რადგან კომიტის შეტყობინებები პირდაპირ გავლენას ახდენენ რელიზის შენიშვნებზე, მნიშვნელოვანია ნათელი, აღმწერი შეტყობინებების წერა:

### გაკეთება:
- გამოიყენეთ present tense: „add feature“ და არა „added feature“
- იყავით მოკლე, მაგრამ აღმწერი
- ჩართეთ scope, როდესაც ცვლილებები კომპონენტზეა დამოკიდებული
- მიუთითეთ issues, როდესაც ეს შესაბამისია: `fix(cli): resolve build cache issue (#1234)`

### არ გააკეთოთ:
- არ გამოიყენოთ ბუნდოვანი შეტყობინებები, როგორიცაა „fix bug“ ან „update code“
- არ აურიოთ რამდენიმე არარელევანტური ცვლილება ერთ კომიტში
- არ დაგავიწყდეთ breaking change ინფორმაციის ჩართვა

### Breaking changes

Breaking changes-ისთვის, ჩართეთ `BREAKING CHANGE:` კომიტის სხეულში:

```
feat(cli): change cache directory structure

BREAKING CHANGE: Cache files are now stored in a new directory structure.
Users need to clear their cache after updating.
```

## რელიზის workflows

CLI-ს, სერვერსა და Kura-ს თითოეულს აქვს საკუთარი channel workflows-ების ნაკრები, ერთი და იგივე სტრუქტურის მიხედვით:

- `<component>-release.yml` - აქვეყნებს canary-ს `main`-ზე ყოველი კომპონენტის შემხები push-ისას (Kura-ს არის ხელახლა გამოყენებადი workflow, რომელსაც `server-production-deployment.yml` იძახებს, როდესაც `kura/` შეიცვლება)
- `<component>-rc.yml` - ჭრის რელიზის კანდიდატს ყოველ ორშაბათს (`workflow_run`-ის მეშვეობით promote-ის შემდეგ), ან ხელით ჭრის ან აუმჯობესებს ერთ-ერთს
- `<component>-promote.yml` - გადაჰყავს მოლოდინში მყოფ RC-ს სტაბილურზე ყოველ ორშაბათს 06:00 UTC-ზე, ან ხელით გადაჰყავს soaked RC
- `<component>-build-publish.yml` - საერთო build და publish pipeline, რომელსაც ზემოთ ჩამოთვლილი სამი იძახებს

CLI-ს, სერვერსა და Kura-ს ასევე აქვთ `<component>-backport.yml` სტაბილურ ხაზზე პატჩების მოსაჭრელად. კომპონენტის ყველა workflow სერიალიზდება ერთი `<component>-publish` concurrency ჯგუფის მეშვეობით, რათა ვერსიის გადაწყვეტა და ტეგირება არასდროს შეჯახდეს. Kura არის გამონაკლისი: მისი canary იყენებს `kura-canary-publish`-ს, ხოლო მისი RC, promote და backport იყენებენ `kura-stable-publish`-ს, რათა ხანგრძლივმა სტაბილურმა build-მა არ შეაფერხოს deploy cascade. ტეგის სივრცეები განცალკევებულია, ამიტომ ორი ჯგუფი არ შეეჯახება.

Helm chart და ინფრასტრუქტურის სახეები (CAPI operator, runners controller, xcresult processor image, linux runner image და სხვა) კვლავ რელიზდება `.github/workflows/server-production-deployment.yml`-ის მეშვეობით. ის ეშვება `main`-ზე push-ებისას და აკეთებს cascade-ს canary → acceptance tests → production hosted deploy-ისთვის, ასევე აქვეყნებს ამ ინფრასტრუქტურის კომპონენტებს მათი ცვლილებისას. აპლიკაციას, cache-ს, Gradle plugin-ს, skills-ს, Noora-ს და დამოუკიდებელ infra controllers-ს თითოეულს აქვს საკუთარი `*-release.yml` workflow. ყველა მათგანი იზიარებს ცვლილებების აღმოჩენას: `mise/tasks/release/components.json` განსაზღვრავს თითოეული კომპონენტის ტეგის პრეფიქსს და include paths-ს, ხოლო git cliff გარდაქმნის შესაბამის კომიტებს release notes-ად.

CLI build (`cli-build-publish.yml`) ასევე ქმნის და აქვეყნებს `tuist.spec.json` არტიფაქტს (გენერირებული `tuist --experimental-dump-help`-დან), რათა downstream tooling-მა შეძლოს ბრძანების ინტერფეისის მოხმარება.

- **მკაფიო კომუნიკაცია**: ავტომატური changelogs კომიტის შეტყობინებებიდან

- **ხარისხის უზრუნველყოფა**: რელიზდება მხოლოდ ტესტირებული ცვლილებები

3. დაადასტურეთ, რომ ყველა ტესტი გადის
4. შეამოწმეთ, რომ კომპონენტი წარმატებით ბილდება

სასწრაფო შესწორებებისთვის, რომლებსაც საჭიროებს დაუყოვნებელი რელიზი:
1. დარწმუნდით, რომ თქვენს კომიტს აქვს მკაფიო scope
2. merging-ის შემდეგ, აკონტროლეთ რელიზის workflow
3. სერვერის ან აპლიკაციისთვის, შესწორება გამოიცემა შემდეგ push-ზე; საჭიროების შემთხვევაში, გამოიწვიეთ ხელით რელიზი
4. CLI-სთვის, შესწორება ავტომატურად ხვდება canary-ზე. სტაბილურ მომხმარებლებამდე მისატანად, გააკეთეთ მისი backport შენარჩუნებულ სტაბილურ ხაზ(ებ)ზე (იხილეთ [შესწორებების backport-ing სტაბილურ ხაზზე](#backporting-fixes-to-a-stable-line))

## App Store რელიზი

მიუხედავად იმისა, რომ CLI და Server მიჰყვებიან ზემოთ აღწერილ უწყვეტ რელიზის პროცესს, **iOS აპლიკაცია** არის გამონაკლისი Apple-ის App Store განხილვის პროცესის გამო:

- **ხელით რელიზები**: iOS აპლიკაციის რელიზები მოითხოვს ხელით წარდგენას App Store-ში
- **განხილვის დაყოვნებები**: თითოეულ რელიზს უნდა გაიაროს Apple-ის განხილვის პროცესი, რასაც 1-7 დღე შეიძლება დასჭირდეს
- **ჯგუფური ცვლილებები**: მრავალი ცვლილება ჩვეულებრივ ერთად იკვრება თითოეულ iOS რელიზში
- **TestFlight**: Beta ვერსიები შეიძლება გავრცელდეს TestFlight-ის მეშვეობით App Store რელიზამდე
- **Release notes**: უნდა დაიწეროს სპეციფიკურად App Store guidelines-ისთვის

iOS აპლიკაცია კვლავ მიჰყვება იგივე კომიტის კონვენციებს და იყენებს git cliff-ს changelog-ის გენერირებისთვის, მაგრამ რეალური რელიზი მომხმარებლებისთვის ხდება ნაკლებად ხშირად, ხელით განრიგით.
