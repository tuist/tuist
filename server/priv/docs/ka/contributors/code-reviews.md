# კოდის რევიუები {#code-reviews}

პულ-რეკვესტების რევიუ კონტრიბუციის გავრცელებული ფორმაა. მიუხედავად იმისა, რომ უწყვეტი ინტეგრაცია (CI) უზრუნველყოფს, რომ კოდი ასრულებს საჭირო ფუნქციებს, ეს არ არის საკმარისი. არსებობს კონტრიბუციის ისეთი ასპექტები, რომელთა ავტომატიზება შეუძლებელია: დიზაინი, კოდის სტრუქტურა და არქიტექტურა, ტესტების ხარისხი ან ბეჭდური შეცდომები. ქვემოთ მოცემული განყოფილებები წარმოადგენს კოდის რევიუს პროცესის სხვადასხვა ასპექტს.

## წაკითხვადობა {#readability}

გამოხატავს თუ არა კოდი თავის ჩანაფიქრს ცალსახად? **თუ კოდის მუშაობის გასაგებად ბევრი დროის დახარჯვა გიწევთ, კოდის იმპლემენტაცია საჭიროებს გაუმჯობესებას.** შესთავაზეთ კოდის დაყოფა უფრო მცირე, გასაგებ აბსტრაქციებად. ალტერნატიულად, როგორც ბოლო საშუალება, შეგიძლიათ დაამატოთ კომენტარი, რომელიც ახსნის მსჯელობას. ჰკითხეთ საკუთარ თავს, შეძლებდით თუ არა კოდის გაგებას მომავალში, პულ-რეკვესტის აღწერის ან სხვა კონტექსტის გარეშე.

## მცირე პულ-რეკვესტები {#small-pull-requests}

დიდი პულ-რეკვესტების რევიუ რთულია და დეტალების გამოტოვება უფრო ადვილია. თუ პულ-რეკვესტი ზედმეტად დიდი და სამართავი ხდება, შესთავაზეთ ავტორს მისი ნაწილებად დაყოფა.

> [!NOTE]
> **გამონაკლისები**
>
> არსებობს იშვიათი შემთხვევები, როდესაც პულ-რეკვესტის დაყოფა შეუძლებელია, მაგალითად, როცა ცვლილებები მჭიდროდ არის გადაჯაჭვული და ვერ იყოფა. ასეთ შემთხვევებში, ავტორმა უნდა წარმოადგინოს ცვლილებების ნათელი ახსნა და მათი მსჯელობა.


## თანმიმდევრულობა {#consistency}

მნიშვნელოვანია, რომ ცვლილებები თანმიმდევრული იყოს პროექტის დანარჩენ ნაწილთან. შეუსაბამობები ართულებს მხარდაჭერას, ამიტომ უნდა ავირიდოთ ისინი. თუ არსებობს მიდგომა მომხმარებლისთვის შეტყობინებების გამოტანის ან შეცდომების შეტყობინებისთვის, უნდა დავიცვათ ის. თუ ავტორი არ ეთანხმება პროექტის სტანდარტებს, შესთავაზეთ მას საკითხის (issue) გახსნა, სადაც შევძლებთ მათ განხილვას.

## ტესტები {#tests}

ტესტები საშუალებას გვაძლევს კოდის ცვლილებისას ვიმოქმედოთ დარწმუნებულობით. პულ-რეკვესტებში არსებული კოდი უნდა იყოს დატესტული და ყველა ტესტმა უნდა გაიაროს. კარგი ტესტი არის ის, რომელიც თანმიმდევრულად იძლევა ერთსა და იმავე შედეგს და რომლის გაგება და მხარდაჭერა ადვილია. რევიუერები რევიუს დროის უმეტეს ნაწილს იმპლემენტაციის კოდს უთმობენ, მაგრამ ტესტებიც ისეთივე მნიშვნელოვანია, რადგან ისინიც კოდია.

## დამრღვევი ცვლილებები {#breaking-changes}

დამრღვევი ცვლილებები Tuist-ის მომხმარებლებისთვის ცუდ გამოცდილებას ქმნის. კონტრიბუციებმა უნდა აიცილონ დამრღვევი ცვლილებების შეტანა, თუ ეს მკაცრად აუცილებელი არ არის. არსებობს ენის მრავალი ფუნქცია, რომლის გამოყენებითაც შეგვიძლია Tuist-ის ინტერფეისის განვითარება დამრღვევი ცვლილებების გარეშე. არ არის ყოველთვის ცხადი, არის თუ არა ცვლილება დამრღვევი. ერთ-ერთი მეთოდი ამის შესამოწმებლად არის Tuist-ის გაშვება fixtures დირექტორიაში არსებული სატესტო პროექტებზე. ეს მოითხოვს, თავი მომხმარებლის ადგილას ჩავაყენოთ და წარმოვიდგინოთ, თუ როგორ იმოქმედებენ ცვლილებები მათზე.
