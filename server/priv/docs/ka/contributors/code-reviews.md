# კოდის რევიუ {#code-reviews}

პულ-რეკვესტების განხილვა წვლილის შეტანის გავრცელებული ფორმაა. მიუხედავად იმისა, რომ უწყვეტი ინტეგრაცია (CI) უზრუნველყოფს კოდის სათანადო ფუნქციონირებას, ეს არ არის საკმარისი. არსებობს წვლილის ისეთი ასპექტები, რომელთა ავტომატიზაცია შეუძლებელია: დიზაინი, კოდის სტრუქტურა და არქიტექტურა, ტესტების ხარისხი ან ბეჭდვითი შეცდომები. შემდეგი სექციები ასახავს კოდის რევიუს პროცესის სხვადასხვა ასპექტს.

## წაკითხვადობა {#readability}

გამოსახავს თუ არა კოდი თავის განზრახვას ცალსახად? **თუ კოდის დანიშნულების გასარკვევად ბევრი დროის დახარჯვა გიწევთ, კოდის იმპლემენტაცია საჭიროებს გაუმჯობესებას.** შესთავაზეთ კოდის დაყოფა უფრო მცირე, გასაგებ აბსტრაქციებად. ალტერნატივის სახით და ბოლო რესურსად, შესაძლებელია კომენტარის დამატება, რომელიც ახსნის მსჯელობას. ჰკითხეთ საკუთარ თავს, შეძლებდით თუ არა კოდის გაგებას მომავალში ნებისმიერი კონტექსტის (მაგალითად, პულ-რეკვესტის აღწერის) გარეშე.

## მცირე ზომის პულ-რეკვესტები {#small-pull-requests}

დიდი ზომის პულ-რეკვესტების განხილვა რთულია და დეტალების გამოტოვების ალბათობა მაღალია. თუ პულ-რეკვესტი ზედმეტად დიდი და სამართავად რთული ხდება, შესთავაზეთ ავტორს მისი დაშლა.

> [!NOTE]
> **გამონაკლისები**
>
> არსებობს იშვიათი სცენარები, როდესაც პულ-რეკვესტის დაშლა შეუძლებელია, მაგალითად, როცა ცვლილებები მჭიდროდ არის გადაჯაჭვული და ვერ ნაწილდება. ასეთ შემთხვევებში ავტორმა უნდა წარმოადგინოს ცვლილებების ნათელი ახსნა და მათი მსჯელობა.


## თანმიმდევრულობა {#consistency}

მნიშვნელოვანია, რომ ცვლილებები იყოს თანმიმდევრული პროექტის დანარჩენ ნაწილთან. შეუსაბამობა ართულებს მხარდაჭერას, ამიტომ მათი თავიდან აცილება უნდა მოვახდინოთ. თუ არსებობს მომხმარებლისთვის შეტყობინებების გამოტანის ან შეცდომების რეპორტირების მიდგომა, უნდა მივყვეთ მას. თუ ავტორი არ ეთანხმება პროექტის სტანდარტებს, შესთავაზეთ მას საკითხის (issue) გახსნა, სადაც შეგვიძლია დეტალურად განვიხილოთ ისინი.

## ტესტები {#tests}

ტესტები საშუალებას გვაძლევს კოდში ცვლილებები დარწმუნებით შევიტანოთ. პულ-რეკვესტებში წარმოდგენილი კოდი უნდა იყოს დატესტილი და ყველა ტესტი უნდა გაიაროს. კარგი ტესტი არის ის, რომელიც თანმიმდევრულად იძლევა ერთსა და იმავე შედეგს და ადვილად გასაგები და მხარდასაჭერია. რევიუერები რევიუს დროის უმეტეს ნაწილს იმპლემენტაციის კოდს უთმობენ, მაგრამ ტესტებიც ისეთივე მნიშვნელოვანია, რადგან ისინიც კოდია.

## დამრღვევი ცვლილებები {#breaking-changes}

დამრღვევი ცვლილებები Tuist-ის მომხმარებლებისთვის ცუდ გამოცდილებას ქმნის. წვლილის შეტანისას უნდა ავიცილოთ დამრღვევი ცვლილებების შემოტანა, თუ ეს აბსოლუტურად აუცილებელი არ არის. არსებობს ენის მრავალი ფუნქცია, რომლის გამოყენებითაც Tuist-ის ინტერფეისის ევოლუცია დამრღვევი ცვლილებების გარეშეა შესაძლებელი. არ არის ყოველთვის ცხადი, არის თუ არა ცვლილება დამრღვევი. ერთ-ერთი მეთოდი დამრღვევი ცვლილების დასადასტურებლად არის Tuist-ის გაშვება fixtures დირექტორიაში არსებული სატესტო პროექტების წინააღმდეგ. ეს მოითხოვს თავი მომხმარებლის ადგილას ჩავდგათ და წარმოვიდგინოთ, თუ როგორ იმოქმედებენ ცვლილებები მათზე.
