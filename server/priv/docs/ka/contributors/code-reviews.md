# კოდის რევიუ {#code-reviews}

Pull request-ების რევიუ წვლილის შეტანის გავრცელებული ფორმაა. მიუხედავად იმისა, რომ უწყვეტი ინტეგრაცია (CI) უზრუნველყოფს კოდის სწორად მუშაობას, ეს საკმარისი არ არის. არსებობს წვლილის ისეთი ასპექტები, რომელთა ავტომატიზაცია შეუძლებელია: დიზაინი, კოდის სტრუქტურა და არქიტექტურა, ტესტების ხარისხი ან ბეჭდვითი შეცდომები. შემდეგი სექციები აღწერენ კოდის რევიუს პროცესის სხვადასხვა ასპექტს.

## მკითხველობადობა {#readability}

გამოსახავს თუ არა კოდი თავის განზრახვას ცალსახად? **თუ კოდის დანიშნულების გაგებას ბევრი დრო სჭირდება, კოდის იმპლემენტაცია უნდა გაუმჯობესდეს.** შესთავაზეთ კოდის დაყოფა უფრო მცირე აბსტრაქციებად, რომლებიც უფრო ადვილად გასაგებია. ალტერნატიულად, ბოლო საშუალების სახით, შეიძლება დაემატოს კომენტარი, რომელიც ხსნის მის ლოგიკას. ჰკითხეთ საკუთარ თავს, შეძლებდით თუ არა მომავალში კოდის გაგებას ნებისმიერი გარე კონტექსტის (მაგალითად, pull request-ის აღწერის) გარეშე.

## მცირე pull request-ები {#small-pull-requests}

დიდი pull request-ების რევიუ რთულია და დეტალების გამოტოვება ადვილია. თუ pull request ზედმეტად დიდი და სამართავად რთული ხდება, შესთავაზეთ ავტორს მისი დაშლა.

> [!NOTE]
> **გამონაკლისები**
>
> არსებობს მცირე რაოდენობით სცენარები, სადაც pull request-ის დაშლა შეუძლებელია, მაგალითად, როცა ცვლილებები მჭიდროდ არიან გადაჯაჭვული და ვერ იყოფა. ასეთ შემთხვევებში ავტორმა უნდა წარმოადგინოს ცვლილებების ცალსახა ახსნა და მათი ლოგიკა.


## თანმიმდევრულობა {#consistency}

მნიშვნელოვანია, რომ ცვლილებები თანმიმდევრული იყოს პროექტის დანარჩენ ნაწილთან. შეუსაბამობა ართულებს მხარდაჭერას, ამიტომ უნდა ავიცილოთ ისინი. თუ არსებობს მიდგომა მომხმარებლისთვის შეტყობინებების გამოტანის ან შეცდომების რეპორტინგისთვის, უნდა დავიცვათ ის. თუ ავტორი არ ეთანხმება პროექტის სტანდარტებს, შესთავაზეთ მას საკითხის (issue) გახსნა, სადაც შევძლებთ მათზე დეტალურად განხილვას.

## ტესტები {#tests}

ტესტები საშუალებას გვაძლევს კოდის ცვლილებისას ვიმოქმედოთ დარწმუნებით. Pull request-ში არსებული კოდი უნდა იყოს დატესტილი და ყველა ტესტი უნდა გადიოდეს. კარგი ტესტი არის ის, რომელიც თანმიმდევრულად იძლევა ერთსა და იმავე შედეგს და ადვილად გასაგები და მხარდასაჭერია. რევიუერები რევიუზე დროის უმეტეს ნაწილს იმპლემენტაციის კოდს უთმობენ, მაგრამ ტესტებიც იგივე მნიშვნელობისაა, რადგან ისინიც კოდია.

## დამრღვევი ცვლილებები {#breaking-changes}

დამრღვევი ცვლილებები Tuist-ის მომხმარებლებისთვის ცუდ გამოცდილებას ქმნის. წვლილმა უნდა აიცილოს დამრღვევი ცვლილებების შეტანა, თუ ეს აბსოლუტურად აუცილებელი არ არის. არსებობს ენის მრავალი ფუნქცია, რომლის გამოყენებითაც შეგვიძლია Tuist-ის ინტერფეისის განვითარება დამრღვევი ცვლილებების გარეშე. ცვლილების დამრღვევობა ყოველთვის ცალსახა არ არის. მეთოდი იმის შესამოწმებლად, არის თუ არა ცვლილება დამრღვევი, არის Tuist-ის გაშვება fixtures დირექტორიაში არსებული სატესტო პროექტებზე. ეს მოითხოვს თავის მომხმარებლის ადგილას ჩასმას და წარმოდგენას, თუ როგორ იმოქმედებს ცვლილებები მათზე.
