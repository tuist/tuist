# პრობლემების შეტყობინება {#issue-reporting}

Tuist-ის მომხმარებელმა შეიძლება წააწყდეთ ბაგებს ან არასაჭირო ქცევებს. თუ ასე მოხდა, გირჩევთ შეატყობინოთ ისინი, რათა ჩვენ შევძლოთ მათი გამოსწორება.

## GitHub Issues არის ჩვენი სატიკეტო პლატფორმა {#github-issues-is-our-ticketing-platform}

პრობლემები უნდა იქნას შეტყობინებული GitHub-ზე, როგორც [GitHub issues](https://github.com/tuist/tuist/issues), და არა Slack-ში ან სხვა პლატფორმებზე. GitHub უკეთესია პრობლემების კვალის გასადევნად და სამართავად, უფრო ახლოსაა კოდთან და საშუალებას გვაძლევს დავაკვირდეთ პრობლემის პროგრესს. ამასთან, ის ხელს უწყობს პრობლემის დეტალურ აღწერას, რაც აიძულებს შემტყობინებელს იფიქროს პრობლემაზე და წარმოადგინოს მეტი კონტექსტი.

## კონტექსტი გადამწყვეტია {#context-is-crucial}

პრობლემა საკმარისი კონტექსტის გარეშე ჩაითვლება არასრულყოფილად და ავტორს სთხოვენ დამატებით კონტექსტს. თუ ის არ იქნება წარმოდგენილი, პრობლემა დაიხურება. იფიქრეთ ასე: რაც უფრო მეტ კონტექსტს წარმოადგენთ, მით უფრო ადვილია ჩვენთვის პრობლემის გაგება და მისი გამოსწორება. ასე რომ, თუ გსურთ თქვენი პრობლემის გამოსწორება, წარმოადგინეთ მაქსიმალურად ბევრი კონტექსტი. ეცადეთ უპასუხოთ შემდეგ კითხვებს:

- რა ცდილობდით გაგეკეთებინათ?
- როგორ გამოიყურება თქვენი გრაფი?
- Tuist-ის რომელ ვერსიას იყენებთ?
- გთიშავთ ეს პრობლემა?

ასევე მოვითხოვთ წარმოადგინოთ მინიმალური **reproducible project**.

## Reproducible project {#reproducible-project}

### რა არის reproducible project? {#what-is-a-reproducible-project}

Reproducible project არის მცირე Tuist-ის პროექტი პრობლემის სადემონსტრაციოდ - ხშირად ეს პრობლემა გამოწვეულია Tuist-ში არსებული ბაგით. თქვენს reproducible project-ში უნდა იყოს მხოლოდ ის მინიმალური ფუნქციები, რომლებიც საჭიროა ბაგის ცხადად სადემონსტრაციოდ.

### რატომ უნდა შექმნათ reproducible test case? {#why-should-you-create-a-reproducible-test-case}

Reproducible projects საშუალებას გვაძლევს გამოვყოთ პრობლემის მიზეზი, რაც პირველი ნაბიჯია მისი გამოსწორებისკენ! ნებისმიერი ბაგის შეტყობინების ყველაზე მნიშვნელოვანი ნაწილია ზუსტად აღწეროთ ნაბიჯები, რომლებიც საჭიროა ბაგის გასამეორებლად.

Reproducible project შესანიშნავი გზაა იმ კონკრეტული გარემოს გაზიარებისთვის, რომელიც იწვევს ბაგს. თქვენი reproducible project არის საუკეთესო გზა დაეხმაროთ იმ ადამიანებს, რომლებიც გინდათ დაგეხმარონ.

### ნაბიჯები reproducible project-ის შესაქმნელად {#steps-to-create-a-reproducible-project}

- შექმენით ახალი git რეპოზიტორია.
- ინიციალიზაცია გაუკეთეთ პროექტს `tuist init`-ის გამოყენებით რეპოზიტორიის დირექტორიაში.
- დაამატეთ კოდი, რომელიც საჭიროა თქვენს მიერ ნანახი შეცდომის გასამეორებლად.
- გამოაქვეყნეთ კოდი (თქვენი GitHub ანგარიში კარგი ადგილია ამისთვის) და შემდეგ მიუთითეთ ბმული მასზე პრობლემის შექმნისას.

### Reproducible projects-ის სარგებელი {#benefits-of-reproducible-projects}

- **უფრო მცირე ზედაპირი:** ყველაფრის წაშლით, გარდა შეცდომისა, არ გჭირდებათ ბაგის საპოვნელად ძიება.
- **საჭირო არ არის საიდუმლო კოდის გამოქვეყნება:** შეიძლება ვერ შეძლოთ თქვენი მთავარი საიტის გამოქვეყნება (მრავალი მიზეზის გამო). მისი მცირე ნაწილის ხელახლა შექმნა, როგორც reproducible test case, საშუალებას გაძლევთ საჯაროდ აჩვენოთ პრობლემა საიდუმლო კოდის გაუშიფვრად.
- **ბაგის დადასტურება:** ზოგჯერ ბაგი გამოწვეულია თქვენს მანქანაზე პარამეტრების გარკვეული კომბინაციით. Reproducible test case საშუალებას აძლევს კონტრიბუტორებს ჩამოტვირთონ თქვენი ბილდი და შეამოწმონ ის თავიანთ მანქანებზეც. ეს ეხმარება პრობლემის მიზეზის დადასტურებასა და შევიწროებას.
- **დახმარება ბაგის გამოსწორებაში:** თუ ვინმე სხვას შეუძლია გაიმეოროს თქვენი პრობლემა, მათ ხშირად აქვთ კარგი შანსი პრობლემის გამოსწორების. თითქმის შეუძლებელია ბაგის გამოსწორება მისი გასამეორებლად შესაძლებლობის გარეშე.
