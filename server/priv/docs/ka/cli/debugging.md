# დაგება {#debugging}

Tuist გთავაზობთ რამდენიმე ინსტრუმენტს, რომელიც დაგეხმარებათ პრობლემების დიაგნოსტიკაში, როდესაც ბრძანებები არ მუშაობენ მოსალოდნელად.

> [!WARNING]
> სესიის მონაცემები შეიძლება შეიცავდეს კონფიდენციალურ ინფორმაციას, როგორიცაა ფაილის გზები, პროექტის სახელები და მოთხოვნა/პასუხის სხეულები. მიუხედავად იმისა, რომ მგრძნობიარე ჰედერები (მაგალითად, Authorization) ინიღბება, იყავით ყურადღებიანი სესიის მონაცემების სხვებთან გაზიარებისას.


## სესიის მონაცემები {#session-data}

თუ ბრძანების გამოძახება არ იძლევა სასურველ შედეგებს, პრობლემის დიაგნოსტიკა შეგიძლიათ სესიის მონაცემების შესწავლით. CLI აგზავნის ლოგებს [OSLog](https://developer.apple.com/documentation/os/oslog)-ში და ფაილურ სისტემაში.

ყოველ გაშვებაზე ის ქმნის სესიის საქაღალდეს მისამართზე `$XDG_STATE_HOME/tuist/sessions/{uuid}/`, სადაც `$XDG_STATE_HOME` იღებს მნიშვნელობას `~/.local/state`, თუ გარემოს ცვლადი არ არის დაყენებული. ასევე შეგიძლიათ გამოიყენოთ `$TUIST_XDG_STATE_HOME` Tuist-ისთვის სპეციფიური მდგომარეობის საქაღალდის დასაყენებლად, რომელსაც უპირატესობა ენიჭება `$XDG_STATE_HOME`-თან შედარებით.

ყოველი სესიის საქაღალდე შეიცავს:
- **`logs.txt`** - ტექსტური ლოგები CLI სესიიდან
- **`network.har`** - [HTTP Archive (HAR)](https://w3c.github.io/web-performance/specs/HAR/Overview.html) ფაილი, რომელიც შეიცავს სესიის განმავლობაში შესრულებულ ყველა ქსელურ მოთხოვნას და პასუხს

### HAR ფაილების ვიზუალიზაცია {#visualizing-har-files}

HAR ფაილი აღრიცხავს სესიის განმავლობაში შესრულებულ ყველა HTTP მოთხოვნას და პასუხს, რაც სასარგებლოა სერვერთან კომუნიკაციის პრობლემების დასადგენად. HAR ფაილების გახსნა რამდენიმე ინსტრუმენტით შეგიძლიათ:

- **[Proxyman](https://proxyman.io/)**: macOS-ის ნატიური აპლიკაცია HTTP ტრაფიკის სანახავად და ანალიზისთვის. HAR ფაილის შემოტანა File > Import მენიუს მეშვეობით.
- **ბრაუზერის დეველოპერის ინსტრუმენტები**: Chrome, Firefox და Safari მხარს უჭერენ HAR ფაილების შემოტანას მათ Network ჩანართში.
- **[HAR Viewer](http://www.softwareishard.com/har/viewer/)**: ვებზე დაფუძნებული HAR ფაილების ნახვის ინსტრუმენტი.

> [!TIP]
> შეიტყვეთ მეტი Tuist-ის საქაღალდეების ორგანიზაციისა და მორგებული საქაღალდეების კონფიგურაციის შესახებ <.localized_link href="/cli/directories">საქაღალდეების დოკუმენტაციაში</.localized_link>.


ნაგულისხმევად, CLI ასახავს სესიის გზას, როდესაც შესრულება მოულოდნელად სრულდება. თუ ეს არ ხდება, სესიის მონაცემები შეგიძლიათ იპოვოთ ზემოთ ნახსენებ გზაზე (ანუ, უახლეს სესიის საქაღალდეში).

5 დღეზე ძველი სესიის საქაღალდეები ავტომატურად იშლება. Tuist ასევე ნაგულისხმევად ინახავს არაუმეტეს 50 არააქტიური სესიის საქაღალდეს, თანამედროვედ ინახავს იმ სესიებს, რომლებიც ეკუთვნის ამჟამად გაშვებულ Tuist პროცესებს. CI გარემოებში, სადაც ერთი და იგივე მდგომარეობის საქაღალდით მრავალი Tuist ბრძანება სრულდება, შეგიძლიათ გაზარდოთ არააქტიური სესიების ლიმიტი `TUIST_SESSION_MAX_SESSIONS`-ით, მაგალითად `TUIST_SESSION_MAX_SESSIONS=200`. არასწორი მნიშვნელობები, ნული და უარყოფითი მნიშვნელობები იგნორირდება და Tuist ბრუნდება ნაგულისხმევ მნიშვნელობაზე 50.

### უწყვეტი ინტეგრაცია {#diagnose-issues-using-logs-ci}

CI-ში, სადაც გარემოებები დროებითია, შეიძლება დაგჭირდეთ თქვენი CI მილსადენის კონფიგურაცია Tuist სესიის მონაცემების ექსპორტისთვის. არტიფაქტების ექსპორტი CI სერვისებში გავრცელებული შესაძლებლობაა და კონფიგურაცია დამოკიდებულია თქვენს მიერ გამოყენებულ სერვისზე. მაგალითად, GitHub Actions-ში შეგიძლიათ გამოიყენოთ `actions/upload-artifact` action სესიის მონაცემების არტიფაქტად ასატვირთად:

```yaml
name: Node CI

on: [push]

env:
  TUIST_XDG_STATE_HOME: /tmp

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout repository
        uses: actions/checkout@v4
      # ... other steps
      - run: tuist generate
      # ... do something with the project
      - name: Export Tuist session data
        if: failure()
        uses: actions/upload-artifact@v4
        with:
          name: tuist-sessions
          path: /tmp/tuist/sessions/
```

### Xcode ქეშის დაგება {#cache-daemon-debugging}

Xcode ქეშის პრობლემების დასადგენად, დააყენეთ `TUIST_CAS_LOG` ფაილის გზაზე როგორც `tuist setup cache`-ის გაშვებისას, ასევე ბილდის დროს. Tuist ამ ფაილს ამატებს ქეშის სტატისტიკასა და შეცდომებს:

```bash
export TUIST_CAS_LOG=$HOME/.local/state/tuist/cas.log
tuist setup cache
xcodebuild build -scheme YourScheme
```

CI-ზე, Tuist წერს ამ ლოგს `~/.local/state/tuist/cas.log`-ში ყოველგვარი კონფიგურაციის გარეშე.

## ქსელური ტაიმაუთებისა და ხელახლა ცდების მორგება {#tuning-network-timeouts}

Tuist-ის მთელი [Hypertext Transfer Protocol (HTTP)](https://developer.mozilla.org/en-US/docs/Web/HTTP) ტრაფიკი, მათ შორის სერვერის გამოძახებები, რეესტრი, პრევიუები და ქეშის არტიფაქტების გადაცემა, გადის საერთო `URLSession`-ში გონივრული ნაგულისხმევი პარამეტრებით. ნელი ან გადატვირთული ქსელური გზებზე (მაგალითად, თვითმასპინძლებელი კონფიგურაცია, რომელიც ობიექტების საცავს კორპორატიული პროქსის მეშვეობით უკავშირდება), ინდივიდუალურმა მოთხოვნამ შეიძლება ვერ მიიღოს რესურსი და შეეჯახოს რესურსის ტაიმაუთს სანამ დასრულდება. განსაკუთრებით ქეშის ჩამოტვირთვისას, ტაიმაუთის მიღწევა აიძულებს Tuist-ს დაუბრუნდეს მოდულის წყაროდან აგებას, რაც გაცილებით ძვირია, ვიდრე ოდნავ მეტი ლოდინი ქეშში არსებული ბინარული ფაილისთვის. ქვედა პარამეტრების მორგება შეგიძლიათ გარემოს ცვლადების მეშვეობით, სადაც ნაგულისხმევი მნიშვნელობები მოქმედებს, როდესაც ისინი არ არის დაყენებული ან დაყენებულია არასწორ მნიშვნელობაზე:

```bash
# Maximum time (in seconds) a single resource transfer can take before it's cancelled
# (default: 90, or 600 for whole-file transfers such as test-product shard artifacts)
export TUIST_HTTP_TIMEOUT_INTERVAL_FOR_RESOURCE=600

# Maximum time (in seconds) to wait for new data on an existing request (default: 120)
export TUIST_HTTP_TIMEOUT_INTERVAL_FOR_REQUEST=300

# Maximum number of simultaneous connections per host (default: 20)
export TUIST_HTTP_MAXIMUM_CONNECTIONS_PER_HOST=40

# Maximum retries after the initial attempt (default: 3, maximum: 10)
export TUIST_HTTP_MAXIMUM_RETRY_COUNT=1

# Initial exponential backoff delay in milliseconds (default: 100, maximum: 30000)
export TUIST_HTTP_RETRY_BASE_DELAY_IN_MILLISECONDS=250
```

რესურსის ტაიმაუთი არის მთლიანი გადაცემის საათისმიერი ზღვარი, არა გაჩერების დაცვა, ამიტომ ის უნდა იყოს საკმარისად დიდი იმ უდიდესი არტიფაქტისთვის, რომელსაც გადააადგილებთ. მთლიანი ფაილის გადაცემები, როგორიცაა ტესტის პროდუქტები, რომლებსაც shard ჩამოტვირთავს, ნაგულისხმევად 10 წუთია 90 წამის ნაცვლად, და გაჩერებული გადაცემა მაინც ვერდება `TUIST_HTTP_TIMEOUT_INTERVAL_FOR_REQUEST`-ის შემდეგ ახალი მონაცემების გარეშე. ეს გადაცემები კითხულობენ `TUIST_HTTP_TIMEOUT_INTERVAL_FOR_RESOURCE`-ს მხოლოდ მათი ზღვრის გასაზრდელად, არასდროს ამცირებენ მას 10 წუთზე ნაკლებად, ამიტომ მნიშვნელობა, რომელიც არჩეულია ქეშის მოთხოვნების სწრაფად ვერებისთვის, არ აუქმებს shard-ის მიერ ტესტის პროდუქტების ჩამოტვირთვას. `TUIST_HTTP_TIMEOUT_INTERVAL_FOR_RESOURCE`-ის გაზრდა საშუალებას აძლევს აღდგენად, მაგრამ ნელ ჩამოტვირთვას დასრულდეს ტაიმაუთის ნაცვლად. ქეშის ჩამოტვირთვისთვის ეს ნიშნავს ქეშში მოხვედრას წყაროდან აგებაზე დაბრუნების ნაცვლად, ამიტომ გაზარდეთ იგი განზრახ: იგივე მნიშვნელობა, რომელიც ინარჩუნებს ნელ ქეშის ჩამოტვირთვას, ასევე აყოვნებს დაბრუნებას წყაროდან აგებაზე. `TUIST_HTTP_MAXIMUM_RETRY_COUNT`-ის შემცირებამ შეიძლება ხელი შეუშალოს უფრო ხანგრძლივ ტაიმაუთს გაამრავლოს უარესი შემთხვევის ლოდინი რამდენიმე ცდაზე. ხელახლა ცდის დაყოვნებები ორმაგდება ყოველი ვერების შემდეგ, შეიცავს ერთ ბაზისურ დაყოვნებას შემთხვევითი jitter-ით და არასდროს აღემატება 30 წამს.

## მორგებული CA სერტიფიკატის ნდობა {#trusting-a-custom-ca-certificate}

ნაგულისხმევად, Tuist ამოწმებს TLS სერტიფიკატებს ოპერაციული სისტემის root store-ის მიმართ. როდესაც აწარმოებთ თვითმასპინძელ Tuist ან Kura სერვერს, რომელიც იყენებს პირად სერტიფიკატების გამცემს (CA), Tuist-საც უნდა ენდოს ამ CA-ს. root-ის System keychain-ში დაყენება (და SSL-ისთვის ნდობის მონიშვნა) არის სტანდარტული მიდგომა, მაგრამ ეს ხშირად პრაქტიკული არ არის headless CI ჰოსტებზე, სადაც არ არის GUI სესია ან მობილური მოწყობილობების მართვა (MDM) ნდობის ბიტის დასაყენებლად.

ამ შემთხვევებში შეგიძლიათ პირდაპირ მიუთითოთ Tuist-ს CA სერტიფიკატების bundle. bundle შეიძლება იყოს PEM (ერთი ან მეტი შეერთებული `-----BEGIN CERTIFICATE-----` ბლოკი) ან ერთი DER ფაილი. სისტემის root store რჩება სანდო მასთან ერთად, ამიტომ საჯარო სერტიფიკატები ჩვეულებრივად ამოწმდება და სერტიფიკატების შეფასება არასდროს არის გვერდის ავლილი.

```bash
# Path to a PEM/DER CA bundle to trust on top of the system root store (default: unset)
export TUIST_CA_CERTIFICATE=/etc/ssl/certs/self-hosted-ca.pem
```

ასევე შეგიძლიათ განაცხადოთ იგი თქვენს <.localized_link href="/references/tuist-toml">კონფიგურაციის ფაილში</.localized_link>:

```toml
[network]
ca_certificate = "/etc/ssl/certs/self-hosted-ca.pem"
```

`TUIST_CA_CERTIFICATE` გარემოს ცვლადს უპირატესობა ენიჭება კონფიგურაციის ფაილთან შედარებით, რაც მოსახერხებელია CI საიდუმლოდ მიწოდებისთვის კომიტირებული მანიფესტის შეცვლის გარეშე.
