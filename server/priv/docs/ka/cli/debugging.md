# გამართვა {#debugging}

Tuist გთავაზობთ რამდენიმე ინსტრუმენტს, რომელიც დაგეხმარებათ პრობლემების დიაგნოსტიკაში, როდესაც ბრძანებები მოულოდნელად იქცევიან.

> [!WARNING]
> სესიის მონაცემები შეიძლება შეიცავდეს კონფიდენციალურ ინფორმაციას, როგორიცაა ფაილების გზები, პროექტების სახელები და მოთხოვნა/პასუხის სხეულები. მიუხედავად იმისა, რომ მგრძნობიარე ჰედერები (მაგალითად, Authorization) არის დაფარული, იყავით ყურადღებიანი სესიის მონაცემების სხვებთან გაზიარებისას.


## სესიის მონაცემები {#session-data}

თუ ბრძანების გამოძახება არ იძლევა სასურველ შედეგებს, პრობლემის დიაგნოსტიკა შეგიძლიათ სესიის მონაცემების შესწავლით. CLI გადასცემს ლოგებს [OSLog](https://developer.apple.com/documentation/os/oslog)-სა და ფაილურ სისტემას.

ყოველ გაშვებაზე ის ქმნის სესიის დირექტორიას `$XDG_STATE_HOME/tuist/sessions/{uuid}/`-ში, სადაც `$XDG_STATE_HOME` იღებს მნიშვნელობას `~/.local/state`, თუ გარემოს ცვლადი არ არის დაყენებული. ასევე შეგიძლიათ გამოიყენოთ `$TUIST_XDG_STATE_HOME` Tuist-ისთვის სპეციფიკური მდგომარეობის დირექტორიის დასაყენებლად, რომელიც უპირატესობას ანიჭებს `$XDG_STATE_HOME`-ს.

თითოეული სესიის დირექტორია შეიცავს:
- **`logs.txt`** - ტექსტური ლოგები CLI სესიიდან
- **`network.har`** - [HTTP Archive (HAR)](https://w3c.github.io/web-performance/specs/HAR/Overview.html) ფაილი, რომელიც შეიცავს სესიის განმავლობაში შესრულებულ ყველა ქსელურ მოთხოვნას და პასუხს

### HAR ფაილების ვიზუალიზაცია {#visualizing-har-files}

HAR ფაილი აღრიცხავს სესიის განმავლობაში შესრულებულ ყველა HTTP მოთხოვნას და პასუხს, რაც სასარგებლოა სერვერთან კომუნიკაციის პრობლემების გამოსასწორებლად. HAR ფაილების გახსნა რამდენიმე ინსტრუმენტით შეგიძლიათ:

- **[Proxyman](https://proxyman.io/)**: macOS-ის ნატიური აპლიკაცია HTTP ტრაფიკის ნახვისა და ანალიზისთვის. HAR ფაილის იმპორტი ფაილი > იმპორტი გზით.
- **ბრაუზერის დეველოპერის ინსტრუმენტები**: Chrome, Firefox და Safari ყველა მხარდაჭერს HAR ფაილების იმპორტს მათ Network ჩანართში.
- **[HAR Viewer](http://www.softwareishard.com/har/viewer/)**: ვებზე დაფუძნებული HAR ფაილის ნახვის ინსტრუმენტი.

> [!TIP]
> შეიტყვეთ მეტი Tuist-ის დირექტორიების ორგანიზაციისა და მორგებული დირექტორიების კონფიგურაციის შესახებ <.localized_link href="/cli/directories">დირექტორიების დოკუმენტაციაში</.localized_link>.


> [!TIP]
> **xcodebuild-ის დაუმუშავებელი გამომავალი მონაცემები**
>
> ბრძანებები, რომლებიც ასრულებენ `xcodebuild`-ს, აფორმატებენ მის გამომავალ მონაცემებს xcbeautify-ით. გადაეცით `--verbose` დაუმუშავებელი გამომავალი მონაცემების სანახავად. იხილეთ <.localized_link href="/guides/integrations/continuous-integration#xcodebuild-output-formatting">xcodebuild გამომავალი მონაცემების ფორმატირება</.localized_link>.

ნაგულისხმევად, CLI ასახავს სესიის გზას, როდესაც შესრულება მოულოდნელად წყდება. თუ ეს არ ხდება, სესიის მონაცემები შეგიძლიათ იპოვოთ ზემოთ ნახსენებ გზაზე (ე.ი. უახლეს სესიის დირექტორიაში).

5 დღეზე ძველი სესიის დირექტორიები ავტომატურად იშლება. Tuist ასევე ნაგულისხმევად ინახავს მაქსიმუმ 50 არააქტიურ სესიის დირექტორიას, თან ამავდროულად ინარჩუნებს მიმდინარე Tuist პროცესების კუთვნილ სესიებს. CI გარემოებში, სადაც ერთი და იგივე მდგომარეობის დირექტორიით ბევრი Tuist ბრძანება სრულდება, შეგიძლიათ გაზარდოთ არააქტიური სესიების ზღვარი `TUIST_SESSION_MAX_SESSIONS`-ით, მაგალითად `TUIST_SESSION_MAX_SESSIONS=200`. არასწორი მნიშვნელობები, ნული და უარყოფითი მნიშვნელობები იგნორირდება და Tuist ბრუნდება ნაგულისხმევ 50-ზე.

### უწყვეტი ინტეგრაცია {#diagnose-issues-using-logs-ci}

CI-ში, სადაც გარემოებები დროებითია, შეიძლება მოგინდეთ თქვენი CI პაიპლაინის კონფიგურაცია Tuist სესიის მონაცემების ექსპორტისთვის. არტეფაქტების ექსპორტი ჩვეულებრივი შესაძლებლობაა CI სერვისებში და კონფიგურაცია დამოკიდებულია თქვენს მიერ გამოყენებულ სერვისზე. მაგალითად, GitHub Actions-ში შეგიძლიათ გამოიყენოთ `actions/upload-artifact` action სესიის მონაცემების არტეფაქტად ატვირთვისთვის:

```yaml
name: Node CI

on: [push]

env:
  TUIST_XDG_STATE_HOME: /tmp

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout repository
        uses: actions/checkout@v4
      # ... other steps
      - run: tuist generate
      # ... do something with the project
      - name: Export Tuist session data
        if: failure()
        uses: actions/upload-artifact@v4
        with:
          name: tuist-sessions
          path: /tmp/tuist/sessions/
```

### Xcode ქეშის გამართვა {#cache-daemon-debugging}

Xcode ქეშის პრობლემების გამოსასწორებლად, დააყენეთ `TUIST_CAS_LOG` ფაილის გზაზე როგორც `tuist setup cache`-ის გაშვებისას, ასევე აგებისას. Tuist ამ ფაილს ამატებს ქეშის სტატისტიკასა და შეცდომებს:

```bash
export TUIST_CAS_LOG=$HOME/.local/state/tuist/cas.log
tuist setup cache
xcodebuild build -scheme YourScheme
```

CI-ზე, Tuist წერს ამ ლოგს `~/.local/state/tuist/cas.log`-ში ნებისმიერი კონფიგურაციის გარეშე.

## ქსელური დროის ლიმიტებისა და ხელახალი ცდების მორგება {#tuning-network-timeouts}

Tuist-ის მთელი [Hypertext Transfer Protocol (HTTP)](https://developer.mozilla.org/en-US/docs/Web/HTTP) ტრაფიკი, მათ შორის სერვერის ზარები, რეესტრი, პრევიუები და ქეშის არტეფაქტების გადაცემა, გადის საერთო `URLSession`-ში გონივრული ნაგულისხმევი მნიშვნელობებით. ნელ ან გადატვირთულ ქსელურ გზებზე (მაგალითად, თვითმასპინძელი განლაგება, რომელიც ობიექტების საცავს კორპორატიული პროქსის მეშვეობით აღწევს), ინდივიდუალურმა მოთხოვნამ შეიძლება ვერ მიიღოს რესურსები და დროის ლიმიტს მიაღწიოს სანამ დასრულდება. ქეშის ჩამოტვირთვების შემთხვევაში, დროის ლიმიტის მიღწევა აიძულებს Tuist-ს დაუბრუნდეს მოდულის აგებას წყაროდან, რაც გაცილებით ძვირია, ვიდრე ოდნავ მეტი ლოდინი ქეშში არსებული ბინარისთვის. შეგიძლიათ მორგოთ საბაზისო პარამეტრები გარემოს ცვლადების მეშვეობით, ნაგულისხმევი მნიშვნელობები გამოიყენება, როდესაც ისინი არ არის დაყენებული ან დაყენებულია არასწორ მნიშვნელობაზე:

```bash
# Maximum time (in seconds) a single resource transfer can take before it's cancelled
# (default: 90, or 600 for whole-file transfers such as test-product shard artifacts)
export TUIST_HTTP_TIMEOUT_INTERVAL_FOR_RESOURCE=600

# Maximum time (in seconds) to wait for new data on an existing request (default: 120)
export TUIST_HTTP_TIMEOUT_INTERVAL_FOR_REQUEST=300

# Maximum number of simultaneous connections per host (default: 20)
export TUIST_HTTP_MAXIMUM_CONNECTIONS_PER_HOST=40

# Maximum retries after the initial attempt (default: 3, maximum: 10)
export TUIST_HTTP_MAXIMUM_RETRY_COUNT=1

# Initial exponential backoff delay in milliseconds (default: 100, maximum: 30000)
export TUIST_HTTP_RETRY_BASE_DELAY_IN_MILLISECONDS=250
```

რესურსის დროის ლიმიტი არის მთლიანი გადაცემის საათისმიერი ზღვარი, არა გაჩერების დამცავი, ამიტომ ის საკმარისად დიდი უნდა იყოს თქვენს მიერ გადაადგილებული უდიდესი არტეფაქტისთვის. მთლიანი ფაილის გადაცემები, როგორიცაა ტესტის პროდუქტები, რომლებსაც shard ჩამოტვირთავს, ნაგულისხმევად 10 წუთია 90 წამის ნაცვლად, და გაჩერებული გადაცემა მაინც მარცხდება `TUIST_HTTP_TIMEOUT_INTERVAL_FOR_REQUEST`-ის შემდეგ ახალი მონაცემების გარეშე. ეს გადაცემები კითხულობენ `TUIST_HTTP_TIMEOUT_INTERVAL_FOR_RESOURCE`-ს მხოლოდ მათი ზღვრის გასაზრდელად, არასდროს 10 წუთზე დასაწევად, ამიტომ მნიშვნელობა, რომელიც არჩეულია ქეშის მოთხოვნების სწრაფად შესაწყვეტად, არ აუქმებს shard-ის მიერ ტესტის პროდუქტების ჩამოტვირთვას. `TUIST_HTTP_TIMEOUT_INTERVAL_FOR_RESOURCE`-ის გაზრდა საშუალებას აძლევს აღდგენად, მაგრამ ნელ ჩამოტვირთვას დასრულდეს დროის ლიმიტის ამოწურვის ნაცვლად. ქეშის ჩამოტვირთვებისთვის, ეს ნიშნავს ქეშში მოხვედრას წყაროდან აგებაზე დაბრუნების ნაცვლად, ამიტომ გაზარდეთ იგი გონივრულად: იგივე მნიშვნელობა, რომელიც ინარჩუნებს ნელ ქეშის ჩამოტვირთვას, ასევე აყოვნებს წყაროდან აგებაზე დაბრუნებას. `TUIST_HTTP_MAXIMUM_RETRY_COUNT`-ის შემცირება შეიძლება ხელი შეუშალოს უფრო ხანგრძლივ დროის ლიმიტს გაამრავლოს უარესი შემთხვევის ლოდინი რამდენიმე ცდაზე. ხელახალი ცდის დაყოვნებები ორმაგდება ყოველი მარცხის შემდეგ, შეიცავს შემთხვევითი jitter-ის ერთ საბაზისო დაყოვნებას და არასდროს აღემატება 30 წამს.

## მორგებული CA სერთიფიკატის სანდოობა {#trusting-a-custom-ca-certificate}

ნაგულისხმევად, Tuist ამოწმებს TLS სერთიფიკატებს ოპერაციული სისტემის ფესვურ საცავთან. როდესაც თქვენ აწარმოებთ თვითმასპინძელ Tuist ან Kura სერვერს, რომელიც იყენებს კერძო სერთიფიკატების ორგანოს, Tuist-საც სჭირდება ამ CA-ს სანდოობა. ფესვის დაყენება System keychain-ში (და SSL-ისთვის სანდოდ მონიშვნა) არის სტანდარტული მიდგომა, მაგრამ ეს ხშირად არაპრაქტიკულია headless CI ჰოსტებზე, სადაც არ არის GUI სესია ან მობილური მოწყობილობების მართვა (MDM) სანდოობის ბიტის დასაყენებლად.

ამ შემთხვევებში შეგიძლიათ მიუთითოთ Tuist-ს პირდაპირ CA სერთიფიკატების კონაზე. კონა შეიძლება იყოს PEM (ერთი ან მეტი შეერთებული `-----BEGIN CERTIFICATE-----` ბლოკი) ან ერთი DER ფაილი. სისტემის ფესვური საცავი რჩება სანდოდ მის გვერდით, ამიტომ საჯარო სერთიფიკატები ჩვეულებრივად მოწმდება და სერთიფიკატების შეფასება არასდროს არის გვერდის ავლილი.

```bash
# Path to a PEM/DER CA bundle to trust on top of the system root store (default: unset)
export TUIST_CA_CERTIFICATE=/etc/ssl/certs/self-hosted-ca.pem
```
