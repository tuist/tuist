# დაგება {#debugging}

Tuist გთავაზობთ რამდენიმე ინსტრუმენტს, რომელიც დაგეხმარებათ პრობლემების დიაგნოსტიკაში, როდესაც ბრძანებები მოულოდნელად იქცევიან.

> [!WARNING]
> სესიის მონაცემები შეიძლება შეიცავდეს კონფიდენციალურ ინფორმაციას, როგორიცაა ფაილების გზები, პროექტების სახელები და მოთხოვნა/პასუხის სხეულები. მიუხედავად იმისა, რომ მგრძნობიარე ჰედერები (მაგალითად, Authorization) ინიღბება, იყავით ყურადღებიანი სესიის მონაცემების სხვებთან გაზიარებისას.


## სესიის მონაცემები {#session-data}

თუ ბრძანების გამოძახება არ იძლევა სასურველ შედეგებს, შეგიძლიათ პრობლემა დიაგნოსტიკოთ სესიის მონაცემების შესწავლით. CLI გადასცემს ლოგებს [OSLog](https://developer.apple.com/documentation/os/oslog)-სა და ფაილურ სისტემას.

ყოველ გაშვებაზე ის ქმნის სესიის დირექტორიას `$XDG_STATE_HOME/tuist/sessions/{uuid}/`-ში, სადაც `$XDG_STATE_HOME` იღებს მნიშვნელობას `~/.local/state`, თუ გარემოს ცვლადი არ არის დაყენებული. ასევე შეგიძლიათ გამოიყენოთ `$TUIST_XDG_STATE_HOME` Tuist-ისთვის სპეციფიკური მდგომარეობის დირექტორიის დასაყენებლად, რომელსაც აქვს უპირატესობა `$XDG_STATE_HOME`-თან მიმართებაში.

ყოველი სესიის დირექტორია შეიცავს:
- **`logs.txt`** - ტექსტური ლოგები CLI სესიიდან
- **`network.har`** - [HTTP Archive (HAR)](https://w3c.github.io/web-performance/specs/HAR/Overview.html) ფაილი, რომელიც შეიცავს სესიის განმავლობაში შესრულებულ ყველა ქსელურ მოთხოვნას და პასუხს

### HAR ფაილების ვიზუალიზაცია {#visualizing-har-files}

HAR ფაილი აღრიცხავს სესიის განმავლობაში შესრულებულ ყველა HTTP მოთხოვნას და პასუხს, რაც სასარგებლოა სერვერთან კომუნიკაციის პრობლემების დასადგენად. HAR ფაილების გახსნა რამდენიმე ინსტრუმენტით შეგიძლიათ:

- **[Proxyman](https://proxyman.io/)**: macOS-ის ნატიური აპლიკაცია HTTP ტრაფიკის ნახვისა და ანალიზისთვის. HAR ფაილის იმპორტი ხდება File > Import-ის მეშვეობით.
- **ბრაუზერის დეველოპერული ინსტრუმენტები**: Chrome, Firefox და Safari მხარს უჭერენ HAR ფაილების იმპორტს თავიანთ Network ჩანართში.
- **[HAR Viewer](http://www.softwareishard.com/har/viewer/)**: ვებზე დაფუძნებული HAR ფაილების ნახვის ინსტრუმენტი.

> [!TIP]
> შეიტყვეთ მეტი Tuist-ის დირექტორიების ორგანიზაციისა და მორგებული დირექტორიების კონფიგურაციის შესახებ <.localized_link href="/cli/directories">Directories documentation</.localized_link>-ში.


ნაგულისხმევად, CLI ასახავს სესიის გზას, როდესაც შესრულება მოულოდნელად წყდება. თუ ეს არ ხდება, სესიის მონაცემები შეგიძლიათ იპოვოთ ზემოთ ნახსენებ გზაზე (ანუ, უახლეს სესიის დირექტორიაში).

5 დღეზე ძველი სესიის დირექტორიები ავტომატურად იშლება. Tuist ასევე ნაგულისხმევად ინახავს მაქსიმუმ 50 არააქტიურ სესიის დირექტორიას, თანამედროვედ ინარჩუნებს ამჟამად მოქმედი Tuist პროცესების მიერ კუთვნილ სესიებს. CI გარემოებში, სადაც ერთი და იგივე მდგომარეობის დირექტორიით ბევრი Tuist ბრძანება სრულდება, შეგიძლიათ გაზარდოთ არააქტიური სესიების ზღვარი `TUIST_SESSION_MAX_SESSIONS`-ით, მაგალითად `TUIST_SESSION_MAX_SESSIONS=200`. არასწორი მნიშვნელობები, ნული და უარყოფითი მნიშვნელობები იგნორირდება და Tuist ბრუნდება ნაგულისხმევ მნიშვნელობაზე 50.

### უწყვეტი ინტეგრაცია {#diagnose-issues-using-logs-ci}

CI-ში, სადაც გარემოებები დროებითია, შეიძლება გსურთ დააკონფიგურიროთ თქვენი CI პაიპლაინი Tuist სესიის მონაცემების ექსპორტისთვის. არტიფაქტების ექსპორტი CI სერვისებში ჩვეულებრივი შესაძლებლობაა და კონფიგურაცია დამოკიდებულია თქვენს მიერ გამოყენებულ სერვისზე. მაგალითად, GitHub Actions-ში შეგიძლიათ გამოიყენოთ `actions/upload-artifact` action სესიის მონაცემების არტიფაქტად ასატვირთად:

```yaml
name: Node CI

on: [push]

env:
  TUIST_XDG_STATE_HOME: /tmp

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout repository
        uses: actions/checkout@v4
      # ... other steps
      - run: tuist generate
      # ... do something with the project
      - name: Export Tuist session data
        if: failure()
        uses: actions/upload-artifact@v4
        with:
          name: tuist-sessions
          path: /tmp/tuist/sessions/
```

### Xcode ქეშის დაგება {#cache-daemon-debugging}

Xcode ქეშის პრობლემების დასადგენად, დააყენეთ `TUIST_CAS_LOG` ფაილის გზაზე როგორც `tuist setup cache`-ის გაშვებისას, ასევე აგებისას. Tuist ამ ფაილს ამატებს ქეშის სტატისტიკასა და შეცდომებს:

```bash
export TUIST_CAS_LOG=$HOME/.local/state/tuist/cas.log
tuist setup cache
xcodebuild build -scheme YourScheme
```

CI-ზე Tuist წერს ამ ლოგს `~/.local/state/tuist/cas.log`-ში ნებისმიერი კონფიგურაციის გარეშე.

## ქსელური ტაიმაუთებისა და ხელახალი ცდების რეგულირება {#tuning-network-timeouts}

Tuist-ის მთელი [Hypertext Transfer Protocol (HTTP)](https://developer.mozilla.org/en-US/docs/Web/HTTP) ტრაფიკი, სერვერის გამოძახებების, რეესტრის, პრევიუებისა და ქეშის არტიფაქტების გადაცემის ჩათვლით, გადის საერთო `URLSession`-ზე გონივრული ნაგულისხმევი პარამეტრებით. ნელი ან გადატვირთული ქსელური გზებზე (მაგალითად, თვითმასპინძელი დაყენება, რომელიც ობიექტურ საცავს კორპორატიული პროქსის მეშვეობით უკავშირდება), ინდივიდუალურმა მოთხოვნამ შეიძლება ვერ მიიღოს რესურსები და მიაღწიოს რესურსის ტაიმაუთს სანამ დასრულდება. კერძოდ, ქეშის ჩამოტვირთვისას, ტაიმაუთის მიღწევა აიძულებს Tuist-ს დაუბრუნდეს მოდულის აგებას წყაროდან, რაც გაცილებით ძვირია, ვიდრე ქეშში არსებული ბინარისთვის ოდნავ მეტი ლოდინი. ქვედა დონის პარამეტრების რეგულირება შეგიძლიათ გარემოს ცვლადების მეშვეობით, სადაც ნაგულისხმევი მნიშვნელობები გამოიყენება, როდესაც ისინი არ არის დაყენებული ან დაყენებულია არასწორ მნიშვნელობაზე:

```bash
# Maximum time (in seconds) a single resource transfer can take before it's cancelled
# (default: 90, or 600 for whole-file transfers such as test-product shard artifacts)
export TUIST_HTTP_TIMEOUT_INTERVAL_FOR_RESOURCE=600

# Maximum time (in seconds) to wait for new data on an existing request (default: 120)
export TUIST_HTTP_TIMEOUT_INTERVAL_FOR_REQUEST=300

# Maximum number of simultaneous connections per host (default: 20)
export TUIST_HTTP_MAXIMUM_CONNECTIONS_PER_HOST=40

# Maximum retries after the initial attempt (default: 3, maximum: 10)
export TUIST_HTTP_MAXIMUM_RETRY_COUNT=1

# Initial exponential backoff delay in milliseconds (default: 100, maximum: 30000)
export TUIST_HTTP_RETRY_BASE_DELAY_IN_MILLISECONDS=250
```

რესურსის დროული ლიმიტი არის მთლიანი გადაცემის საათისმხრივი ზედა ზღვარი და არა გაჩერების დაცვა, ამიტომ ის უნდა იყოს საკმარისად დიდი თქვენს მიერ გადატანილი ყველაზე დიდი არტიფაქტისთვის. მთელი ფაილის გადაცემები, როგორიცაა შარდის მიერ ჩამოტვირთული ტესტური პროდუქტები, ნაგულისხმევად 10 წუთია და არა 90 წამი, ხოლო გაჩერებული გადაცემა მაინც ვერ მოხერხდება `TUIST_HTTP_TIMEOUT_INTERVAL_FOR_REQUEST`-ის შემდეგ ახალი მონაცემების გარეშე. ასეთი გადაცემები კითხულობენ `TUIST_HTTP_TIMEOUT_INTERVAL_FOR_RESOURCE`-ს მხოლოდ ზედა ზღვრის გასაზრდელად და არასდროს ამცირებენ მას 10 წუთზე ნაკლებად, ამიტომ ქეშის მოთხოვნების სწრაფად ჩავარდნისთვის არჩეული მნიშვნელობა არ გააუქმებს შარდის მიერ ტესტური პროდუქტების ჩამოტვირთვას. `TUIST_HTTP_TIMEOUT_INTERVAL_FOR_RESOURCE`-ის გაზრდა საშუალებას აძლევს აღდგენად, მაგრამ ნელ ჩამოტვირთვას დასრულდეს დროული ლიმიტის ამოწურვის ნაცვლად. ქეშის ჩამოტვირთვებისთვის ეს ნიშნავს ქეშში მოხვედრას წყაროდან აგებაზე გადასვლის ნაცვლად, ამიტომ გაზარდეთ ის განზრახ: იგივე მნიშვნელობა, რომელიც ინარჩუნებს ნელ ქეშის ჩამოტვირთვას, ასევე აყოვნებს წყაროდან აგებაზე გადასვლას. `TUIST_HTTP_MAXIMUM_RETRY_COUNT`-ის შემცირებამ შეიძლება თავიდან აიცილოს უფრო ხანგრძლივი დროული ლიმიტის გამო ყველაზე ცუდი შემთხვევის ლოდინის გამრავლება რამდენიმე ცდის განმავლობაში. ხელახალი ცდის დაყოვნებები ორმაგდება ყოველი ჩავარდნის შემდეგ, შეიცავს შემთხვევითი ჯიტერის ერთ ბაზურ დაყოვნებას და არასდროს აღემატება 30 წამს.

## მორგებული CA სერტიფიკატის სანდოობა {#trusting-a-custom-ca-certificate}

ნაგულისხმევად, Tuist ამოწმებს TLS სერტიფიკატებს ოპერაციული სისტემის ფესვურ საცავთან მიმართებაში. როდესაც აწარმოებთ თვითმასპინძელ Tuist ან Kura სერვერს, რომელიც იყენებს პირად სერტიფიკატების გამომცემელს, Tuist-საც უნდა ენდოს ამ CA-ს. ფესვის System keychain-ში დაყენება (და SSL-ისთვის სანდოდ მონიშვნა) არის სტანდარტული მიდგომა, მაგრამ ეს ხშირად პრაქტიკული არ არის headless CI ჰოსტებზე, სადაც არ არის GUI სესია ან მობილური მოწყობილობების მართვა (MDM) სანდოობის ბიტის დასაყენებლად.

ამ შემთხვევებში შეგიძლიათ პირდაპირ მიუთითოთ Tuist-ს CA სერტიფიკატების კრებული. კრებული შეიძლება იყოს PEM (ერთი ან მეტი შეერთებული `-----BEGIN CERTIFICATE-----` ბლოკი) ან ერთი DER ფაილი. სისტემური ფესვური საცავი რჩება სანდოდ მასთან ერთად, ამიტომ საჯარო სერტიფიკატები ჩვეულებრივად მოწმდება და სერტიფიკატების შეფასება არასდროს არის გაუქმებული.

```bash
# Path to a PEM/DER CA bundle to trust on top of the system root store (default: unset)
export TUIST_CA_CERTIFICATE=/etc/ssl/certs/self-hosted-ca.pem
```

ასევე შეგიძლიათ განაცხადოთ იგი თქვენს <.localized_link href="/references/tuist-toml">კონფიგურაციის ფაილში</.localized_link>:

```toml
[network]
ca_certificate = "/etc/ssl/certs/self-hosted-ca.pem"
```
