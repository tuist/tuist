# Webhooks {#webhooks}

Webhooks-ები საშუალებას აძლევს თქვენს სისტემებს რეაგირება მოახდინონ Tuist-ში მომხდარ ცვლილებებზე მათი განხორციელების მომენტში. როდესაც შესაბამისი მოვლენა ხდება — ახალი სატესტო შემთხვევა ფიქსირდება, პრევიუს ატვირთვა სრულდება, არასტაბილური ტესტი ისწორება — Tuist აკეთებს HTTP POST-ს ყოველ იმ endpoint-ზე, რომელიც გამოწერილი გაქვთ ამ ტიპის მოვლენებისთვის. მოთხოვნის სხეული არის JSON კონვერტი, ხოლო თითოეული მიწოდება შეიცავს ხელმოწერის ჰედერს, რომლის ვერიფიკაციაც შესაძლებელია endpoint-ის ხელმოწერის საიდუმლო კოდით.

თქვენ ა регистриრებთ დანიშნულების URL-ს, ირჩევთ სასურველ მოვლენებს და Tuist იღებს თავის თავზე ხელმოწერას, ხელახლა ცდებსა და მიწოდების აუდიტის ჟურნალს.

## ნაბიჯები Webhooks-ების მიღებისთვის {#steps}

თქვენს აპლიკაციაში მოვლენების შეტყობინებების მიღება შეგიძლიათ ამ ნაბიჯებით დაიწყოთ:

1. [განსაზღვრეთ მოვლენები](#event-types), რომელთა მიღებაც სურს თქვენს აპლიკაციას.
2. [შექმენით webhook endpoint](#create-an-endpoint) როგორც HTTP endpoint (URL) თქვენს ლოკალურ სერვერზე.
3. დაამუშავეთ Tuist-ის მოთხოვნები [payload-ის პარსინგით](#payload) და [2xx სტატუსის დაბრუნებით](#responding), რათა Tuist-მა მიწოდება წარმატებულად აღნიშნოს.
4. [დაავერიფიცირეთ ხელმოწერა](#verify-signature) ყოველ მოთხოვნაზე, რათა დაადასტუროთ, რომ ის Tuist-დან მოდის.
5. გამოიყენეთ [მოვლენების ჟურნალი](#inspect-deliveries) Tuist-ის დაფაზე, რათა შეცდომები გამართოთ პროექტის აწყობის დროს.

## მოვლენების ტიპები {#event-types}

Tuist აჯგუფებს მოვლენებს იმ რესურსის მიხედვით, რომელსაც ისინი აღწერენ. კონვერტში `type` ველი იყენებს წერტილოვან ნოტაციას (`{resource}.{action}`) — იგივე მნიშვნელობას, რომელსაც გამოიწერდით დაფაზე.

## endpoint-ის შექმნა {#create-an-endpoint}

Endpoint-ები კონფიგურირდება ანგარიშის მიხედვით. გახსენით **Webhooks** თქვენი ანგარიშის პარამეტრებიდან, დააჭირეთ **Add endpoint** და მიუთითეთ:

- **სახელი** — როგორ ჩანს endpoint სიაში.
- **Endpoint URL** — უნდა იყენებდეს `https://`-ს.
- **მოსასმენი მოვლენები** — აირჩიეთ კონკრეტული მოვლენები ან გამოიყენეთ **Select all** ჯგუფის დონეზე. Tuist აკეთებს POST-ს endpoint-ზე მხოლოდ მაშინ, როდესაც ერთ-ერთი გამოწერილი მოვლენა ხდება.

## Payload {#payload}

ყოველი მიწოდება არის ერთი JSON ობიექტი. კონვერტი აერთიანებს მოვლენის სპეციფიკურ რესურსის სნეპშოტს მეტამონაცემებში, რომლის გამოყენებაც შეგიძლიათ მიწოდებების დედუპლიკაციის, მარშრუტიზაციისა და აუდიტისთვის:

| ველი     | აღწერა                                                              |
| --------- | ------------------------------------------------------------------------ |
| `id`      | ამ მიწოდებისთვის უნიკალური UUID. გამოიყენეთ ის დედუპლიკაციისთვის, როდესაც ხელახლა ცდები ხდება. |
| `type`    | წერტილოვანი მოვლენის ტიპი, მაგ. `test_case.updated`.                         |
| `created` | Unix დროის შტამპი (წამებში), როდესაც Tuist-მა მიწოდება რიგში ჩააყენა.           |
| `object`  | რესურსის სნეპშოტი. სტრუქტურა დამოკიდებულია მოვლენის ტიპზე.              |

ყოველი მოვლენის ტიპის ზუსტი payload სქემა დოკუმენტირებულია [Tuist API reference](https://tuist.dev/api/docs#section/Webhook-events)-ში **Webhook events** ქვეშ — ყოველ მოვლენას აქვს შესაბამისი `WebhookXxxEvent` სქემა `components.schemas` ქვეშ, რომლის `$ref`-იც შესაძლებელია კოდის გენერატორიდან.

`test_case.updated` payload, მაგალითად, ასევე შეიცავს `events` მასივს, რომელიც ჩამოთვლის კანონიკურ გადასვლებს, რამაც გამოიწვია ჩაწერა (`marked_flaky`, `muted`, `unskipped`, …), ასევე `actor_id` და `alert_id`, რათა მიმღებებმა განასხვავონ ხელით შეტანილი ცვლილებები ავტომატიზაციით გამოწვეული ცვლილებებისგან.

ყოველი მოთხოვნა ასევე შეიცავს ამ HTTP ჰედერებს:

| ჰედერი              | აღწერა                                                                                   |
| ------------------- | --------------------------------------------------------------------------------------------- |
| `Content-Type`      | ყოველთვის `application/json`.                                                                    |
| `User-Agent`        | `Tuist-Webhooks/1.0`.                                                                         |
| `Tuist-Event-Id`    | იგივე UUID, რაც `id` სხეულში — მოსახერხებელია, თუ ჰედერებს payload-ის პარსინგამდე ალოგებთ.     |
| `Tuist-Event-Type`  | იგივე სტრიנגი, რაც `type` სხეულში.                                                            |
| `Tuist-Signature`   | HMAC-SHA256 ხელმოწერა, ფორმატირებული როგორც `t={timestamp},v1={hex_digest}` — იხილეთ ქვემოთ.          |

## webhook-ზე პასუხის გაცემა {#responding}

მიწოდების დასადასტურებლად, თქვენმა endpoint-მა უნდა დააბრუნოს ნებისმიერი `2xx` სტატუსის კოდი. ნებისმიერი რამ `2xx` დიაპაზონის გარეთ — კავშირის შეცდომებთან და ტაიმაუტებთან ერთად — განიხილება როგორც მიწოდების შეცდომა და ხელახლა ცდება. Tuist არ მიჰყვება `3xx` პასუხებს, ამიტომ პასუხი გასცეთ პირდაპირ კანონიკურ URL-ზე გადაგზავნის ნაცვლად.

დატოვეთ თქვენი handler **სწრაფი**: Tuist ელოდება პასუხს მაქსიმუმ **10 წამის** განმავლობაში. თუ გექნებათ მძიმე სამუშაო შესასრულებლად (სხვა API-ზე დარეკვა, მონაცემთა ბაზის განახლება, შეტყობინებების გაგზავნა), მიიღეთ მოთხოვნა და დაამუშავეთ ის ასინქრონულად. ადრეული პასუხის გაცემა ასევე ზრდის თქვენს გამძლეობას ქვემოთ არსებული სერვისების დროებითი შენელების მიმართ.

## ხელმოწერის ვერიფიკაცია {#verify-signature}

ნებისმიერს, ვინც გაიგებს თქვენს endpoint URL-ს, შეუძლია POST მოთხოვნის გაგზავნა. ხელმოწერის საიდუმლო კოდი საშუალებას აძლევს თქვენს სერვერს უარყოს ყველაფერი, რაც არ მოდის Tuist-ისგან.

ყოველი მოთხოვნისთვის Tuist ითვლის:

```
signed_payload = "{timestamp}.{raw_request_body}"
signature      = HMAC-SHA256(signing_secret, signed_payload)
header         = "t={timestamp},v1={hex(signature)}"
```

ვერიფიკაციისთვის თქვენს მხარეს:

1. წაიკითხეთ `Tuist-Signature` ჰედერი და დაყავით ის `t=` (დროის ნიშანი) და `v1=` (hex digest) ნაწილებად.
2. უარყავით მოთხოვნა, თუ დროის ნიშანი თქვენი სერვერის ამჟამინდელი დროიდან მეტია **5 წუთით**. ეს *ზღუდავს* განმეორებითი გაშვების ფანჯარას, მაგრამ არ კეტავს მას — შეუთავსეთ ის ქვემოთ აღწერილ იდემპოტენტობასთან.
3. გადაითვალეთ `HMAC-SHA256(signing_secret, "{timestamp}.{raw_body}")` და შეადარეთ ის digest-ს **მუდმივ დროში**.
4. გააკეთეთ მიწოდებების დედუპლიკაცია payload `id`-ის მიხედვით (ასევე ჩანს როგორც `Tuist-Event-Id` ჰედერი). ის სტაბილურია ხელახალი ცდების დროს, ამიტომ უკვე დამუშავებული ID-ების შენახვა ხელს უშლის перехваченный მოთხოვნის განმეორებით გაშვებას დაშვებულ ფანჯარაში და იცავს თქვენს ორმაგი დამუშავებისგან ხელახალი ცდის დროს.

> [!IMPORTANT] USE THE RAW BODY
> ხელმოწერა ითვლება Tuist-ის მიერ გაგზავნილ ბაიტებზე. თუ თქვენი web framework ხელახლა პარსავს და სერიალიზაციას უკეთებს JSON-ს ვერიფიკაციამდე, digest არ ემთხვევა. დაიჭირეთ raw body (მაგ., `request.body.read` Rack-ში, raw `Buffer` Express-ში) და გადაეცით ის თქვენს verifier-ს.

საწყისი verifier Node.js-ში — გადაიტანეთ იგივე ოთხი ნაბიჯი (ჰედერის პარსინგი, დროის ნიშნის გადახრის შემოწმება, HMAC-ის გადათვლა, შედარება მუდმივ დროში) იმ ენაზე, რომელზეც დაწერილია თქვენი მიმღები:

```javascript
import crypto from "node:crypto";

function verifyTuistSignature(rawBody, header, secret, toleranceSeconds = 300) {
  const parts = Object.fromEntries(
    header.split(",").map((kv) => kv.split("=", 2))
  );
  const timestamp = Number(parts.t);
  const signature = parts.v1;
  if (!timestamp || !signature) return false;

  const drift = Math.abs(Math.floor(Date.now() / 1000) - timestamp);
  if (drift > toleranceSeconds) return false;

  const expected = crypto
    .createHmac("sha256", secret)
    .update(`${timestamp}.${rawBody}`)
    .digest("hex");

  const a = Buffer.from(expected, "hex");
  const b = Buffer.from(signature, "hex");
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}
```

## ხელახალი ცდები {#retries}

Tuist ხელახლა ცდის ნებისმიერ მიწოდებას, რომელიც აბრუნებს არა-`2xx` სტატუსს, ან ტაიმაუტდება, ან კავშირის დამყარება ვერ ხერხდება. გრაფიკი ფიქსირებულია:

| ცდა | ლოდინა გაგზავნამდე |
| ------- | ------------------- |
| 1       | (მყისიერად)         |
| 2       | 1 წუთი            |
| 3       | 5 წუთი           |
| 4       | 30 წუთი          |
| 5       | 2 საათი             |
| 6       | 8 საათი             |
| 7       | 24 საათი            |

მეშვიდე ცდის ჩავარდნის შემდეგ, მიწოდება სამუდამოდ მონიშნულია როგორც ჩავარდნილი. რადგან ყოველი ცდა ხელმოწერილია იმ დროის ნიშნით, როდესაც ის გაიგზავნა, თქვენი განმეორებითი გაშვების დაცვის ფანჯარა კვლავ მოქმედებს ხელახალი ცდების დროს — არ გჭირდებათ მისი გაფართოება.

## მიწოდებების ინსპექტირება {#inspect-deliveries}

გახსენით endpoint **Webhooks** გვერდიდან, რათა ნახოთ მისი მიწოდების ისტორია. დეტალური გვერდი აჩვენებს:

- **შეჯამების ბარათს** დანიშნულების URL-ით, დაფარული ხელმოწერის საიდუმლო კოდით, გამოწერილი მოვლენებით და შექმნის თარიღით.
- **მიწოდების დიაგრამას** მიმდინარე ჯამებით და ჩავარდნების რაოდენობით, შერჩეული დროის ფანჯრის ფარგლებში.
- **მოვლენების ცხრილს**, რომლის ფილტრაცია შესაძლებელია სტატუსის, მოვლენის ტიპის ან მოვლენის ID-ის მიხედვით.

![webhook endpoint-ის დეტალური გვერდი, რომელიც აჩვენებს შეჯამების ბარათს და მოვლენების მიწოდების დიაგრამას](/images/guides/integrations/webhooks/endpoint-detail.png)

დააჭირეთ მოვლენას, რათა ნახოთ სრული მოთხოვნა და პასუხი ამ ცდიდან — ზუსტი payload, რომელიც Tuist-მა გაგზავნა, ჰედერები, upstream სტატუსის კოდი და პასუხის სხეული. ეს იგივე მონაცემებია, რაც თქვენმა სერვერმა ნახა, რაც ხდის მას ყველაზე სწრაფ გზას ხელმოწერის ვერიფიკაციის შეუსაბამობის ან 5xx upstream შეცდომის დიაგნოსტიკისთვის.

![webhook მოვლენის დეტალური გვერდი, რომელიც აჩვენებს შეჯამებას, მოთხოვნის ჰედერებს და სხეულს, და upstream პასუხს](/images/guides/integrations/webhooks/event-detail.png)

მიწოდების ჩანაწერები ინახება უვადოდ, რათა შეძლოთ უკან დაბრუნება ინტეგრაციის დიაგნოსტიკის დროს. თუ თქვენს ქვემოთ არსებულ სისტემას სჭირდება მდგრადი ასლები (მაგ., შესაბამისობისთვის), დაიჭირეთ მიწოდებები თქვენს ინფრასტრუქტურაზე მათი მიღებისას.

## endpoint-ის საიდუმლო კოდის როტაცია ან წაშლა {#rotate-or-delete}

ორივე ქმედება ხელმისაწვდომია kebab მენიუში endpoint-ის რიგზე და endpoint-ის დეტალურ გვერდზე:

- **საიდუმლო კოდის როტაცია** — ქმნის ახალ ხელმოწერის საიდუმლო კოდს და აჩვენებს მას ერთხელ. არსებული მომხმარებლები ვერ გაივლიან ვერიფიკაციას, სანამ არ განაახლებთ მათ, ამიტომ დაგეგმეთ როტაცია დეპლოიმენტთან ერთად.
- **endpoint-ის წაშლა** — აშორებს endpoint-ს და აჩერებს მიწოდებას. უკვე ჩაწერილი მიწოდების ცდები ინახება სტანდარტული შენახვის ფანჯრის ამოწურვამდე.

## უსაფრთხოების შენიშვნები {#security}

- Endpoint URL-ები უნდა იყოს HTTPS. Tuist უარს ამბობს plaintext დანიშნულებებზე მიწოდებაზე.
- Tuist ახდენს დანიშნულების hostname-ის რეზოლუციას ყოველი მიწოდებამდე და უარყოფს loopback, RFC1918, link-local, ULA და cloud-metadata მისამართებს (`169.254.169.254`, `fd00::/8`, …). ეს ხელს უშლის არასწორად კონფიგურირებული webhook-ის გამოყენებას თქვენი Tuist სერვერის მასპინძლის სკანირების ან შეტევისთვის.
- endpoint URL და ხელმოწერის საიდუმლო კოდი დაშიფრულია უმოქმედო მდგომარეობაში. ისინი გამორიცხულია GDPR/CCPA მონაცემთა ექსპორტიდან როგორც bearer credentials.
- ხელმოწერის საიდუმლო კოდი ნაჩვენებია ზუსტად ერთხელ. მოეპყარით მას როგორც პაროლს: შეინახეთ ის თქვენს საიდუმლოების მენეჯერში, არა რეპოზიტორიაში.
