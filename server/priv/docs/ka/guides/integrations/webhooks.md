# Webhooks {#webhooks}

Webhooks საშუალებას აძლევს თქვენს სისტემებს, რეაგირება მოახდინონ Tuist-ში მომხდარ ცვლილებებზე მათი წარმოქმნისთანავე. როდესაც შესაბამისი მოვლენა ხდება — ახალი სატესტო შემთხვევა ფიქსირდება, პრივიუსის ატვირთვა სრულდება, არასტაბილური ტესტი ისწორება — Tuist აკეთებს HTTP POST-ს ყოველ იმ endpoint-ზე, რომელიც გამოწერილი გაქვთ ამ ტიპის მოვლენისთვის. მოთხოვნის სხეული არის JSON გარსი, ხოლო თითოეული მიწოდება შეიცავს ხელმოწერის ჰედერს, რომლის ვერიფიცირებაც შესაძლებელია endpoint-ის ხელმოწერის საიდუმლო კოდით.

თქვენ რეგისტრირებთ დანიშნულების URL-ს, ირჩევთ სასურველ მოვლენებს, ხოლო Tuist იღებს პასუხისმგებლობას ხელმოწერაზე, განმეორებით ცდებზე და მიწოდების აუდიტის ჟურნალზე.

## ნაბიჯები Webhooks-ის მიღებისთვის {#steps}

თქვენს აპლიკაციაში მოვლენების შეტყობინებების მიღება შეგიძლიათ შემდეგი ნაბიჯებით:

1. [განსაზღვრეთ მოვლენები](#event-types), რომელთა მიღებაც სურს თქვენს აპლიკაციას.
2. [შექმენით webhook endpoint](#create-an-endpoint) როგორც HTTP endpoint (URL) თქვენს ლოკალურ სერვერზე.
3. დაამუშავეთ Tuist-ის მოთხოვნები [payload-ის პარსინგით](#payload) და [2xx სტატუსის](#responding) დაბრუნებით, რათა Tuist-მა მიწოდება წარმატებულად მონიშნოს.
4. [დაადასტურეთ ხელმოწერა](#verify-signature) ყოველ მოთხოვნაზე, რათა დაამტკიცოთ, რომ ის Tuist-დან მოდის.
5. გამოიყენეთ [მოვლენების ჟურნალი](#inspect-deliveries) Tuist-ის დაშბორდზე, რათა შეცდომები აღმოაჩინოთ პროექტის აწყობისას.

## მოვლენის ტიპები {#event-types}

Tuist აჯგუფებს მოვლენებს იმ რესურსის მიხედვით, რომელსაც ისინი აღწერენ. გარსში მყოფი `type` ველი იყენებს წერტილოვან ნოტაციას (`{resource}.{action}`) — იგივე მნიშვნელობაა, რასაც დაშბორდზე გამოიწერთ.

მომავალში მეტი ტიპის მოვლენა დაემატება. თუ გჭირდებათ ისეთი, რომელსაც ჩვენ ჯერ არ ვაგზავნით, შეგვატყობინეთ და მას კატალოგში დავამატებთ.

## Endpoint-ის შექმნა {#create-an-endpoint}

Endpoint-ები კონფიგურირდება ანგარიშის მიხედვით. გახსენით **Webhooks** თქვენი ანგარიშის პარამეტრებიდან, დააჭირეთ **Add endpoint** და მიუთითეთ:

- **სახელი** — როგორ ჩანს endpoint სიაში.
- **Endpoint URL** — უნდა იყენებდეს `https://`-ს.
- **მოსასმენი მოვლენები** — აირჩიეთ კონკრეტული მოვლენები ან გამოიყენეთ **Select all** ჯგუფის დონეზე. Tuist აკეთებს POST-ს endpoint-ზე მხოლოდ მაშინ, როდესაც ერთ-ერთი გამოწერილი მოვლენა აქტიურდება.

## Payload {#payload}

ყოველი მიწოდება არის ერთი JSON ობიექტი. გარსი აერთიანებს მოვლენისთვის სპეციფიკურ რესურსის სნეპშოტს მეტამონაცემებში, რომელთა გამოყენებაც შეგიძლიათ მიწოდებების დედუპლიკაციისთვის, მარშრუტიზაციისთვის და აუდიტისთვის:

| ველი     | აღწერა                                                              |
| --------- | ------------------------------------------------------------------------ |
| `id`      | ამ მიწოდებისთვის უნიკალური UUID. გამოიყენეთ ის დედუპლიკაციისთვის, როდესაც განმეორებითი ცდები ხდება. |
| `type`    | წერტილოვანი მოვლენის ტიპი, მაგ. `test_case.updated`.                         |
| `created` | Unix დროის შტამპი (წამებში), როდესაც Tuist-მა მიწოდება რიგში ჩააყენა.           |
| `object`  | რესურსის სნეპშოტი. სტრუქტურა დამოკიდებულია მოვლენის ტიპზე.              |

ყოველი მოვლენის ტიპის ზუსტი payload სქემა დოკუმენტირებულია [Tuist API reference](https://tuist.dev/api/docs#section/Webhook-events)-ში **Webhook events** განყოფილებაში — ყოველ მოვლენას აქვს შესაბამისი `WebhookXxxEvent` სქემა `components.schemas`-ში, რომლის `$ref`-იც შესაძლებელია კოდის გენერატორიდან.

`test_case.updated` payload, მაგალითად, ასევე შეიცავს `events` მასივს, რომელიც ჩამოთვლის კანონიკურ გადასვლებს, რამაც გამოიწვია ჩაწერა (`marked_flaky`, `muted`, `unskipped`, …), ასევე `actor_id` და `alert_id`, რათა მიმღებებმა განასხვავონ ხელით შესრულებული ცვლილებები ავტომატიზაციით გამოწვეული ცვლილებებისგან.

ყოველი მოთხოვნა ასევე შეიცავს შემდეგ HTTP ჰედერებს:

| ჰედერი              | აღწერა                                                                                   |
| ------------------- | --------------------------------------------------------------------------------------------- |
| `Content-Type`      | ყოველთვის `application/json`.                                                                    |
| `User-Agent`        | `Tuist-Webhooks/1.0`.                                                                         |
| `Tuist-Event-Id`    | იგივე UUID, რაც `id` სხეულში — მოსახერხებელია, თუ ჰედერებს payload-ის პარსინგამდე აფიქსირებთ.     |
| `Tuist-Event-Type`  | იგივე სტრიנגი, რაც `type` სხეულში.                                                            |
| `Tuist-Signature`   | HMAC-SHA256 ხელმოწერა, ფორმატირებული როგორც `t={timestamp},v1={hex_digest}` — იხილეთ ქვემოთ.          |

## პასუხის გაცემა webhook-ზე {#responding}

მიწოდების დასადასტურებლად, თქვენმა endpoint-მა უნდა დააბრუნოს ნებისმიერი `2xx` სტატუსის კოდი. ნებისმიერი რამ `2xx` დიაპაზონის გარეთ — კავშირის შეცდომებთან და დროის ამოწურვასთან ერთად — მიიჩნევა მიწოდების შეცდომად და განმეორდება. Tuist არ მიჰყვება `3xx` პასუხებს, ამიტომ პირდაპირ კანონიკურ URL-ზე გაეცით პასუხი და არა გადამისამართებით.

შეინახეთ თქვენი ჰენდლერი **სწრაფი**: Tuist ელოდება პასუხს მაქსიმუმ **10 წამის** განმავლობაში. თუ მძიმე სამუშაო გაქვთ შესასრულებელი (სხვა API-ზე ზარი, მონაცემთა ბაზის განახლება, შეტყობინებების გაგზავნა), მიიღეთ მოთხოვნა და დაამუშავეთ ის ასინქრონულად. ადრეული დაბრუნება ასევე ზრდის თქვენს გამძლეობას ქვედა დონის სერვისებში დროებითი შენელების მიმართ.

## ხელმოწერის ვერიფიკაცია {#verify-signature}

ნებისმიერს, ვინც იცის თქვენი endpoint URL, შეუძლია მასზე POST მოთხოვნის გაგზავნა. ხელმოწერის საიდუმლო საშუალებას აძლევს თქვენს სერვერს უარყოს ყველაფერი, რაც არ მოდის Tuist-დან.

ყოველი მოთხოვნისთვის Tuist ითვლის:

```
signed_payload = "{timestamp}.{raw_request_body}"
signature      = HMAC-SHA256(signing_secret, signed_payload)
header         = "t={timestamp},v1={hex(signature)}"
```

თქვენს მხარეს ვერიფიკაციისთვის:

1. წაიკითხეთ `Tuist-Signature` ჰედერი და დაყავით ის `t=` (დროის შტამპი) და `v1=` (hex digest) ნაწილებად.
2. უარყავით მოთხოვნა, თუ დროის შტამპი თქვენი სერვერის მიმდინარე დროზე **5 წუთით** მეტად განსხვავდება. ეს *ზღუდავს* განმეორებითი გაშვების ფანჯარას, მაგრამ არ კეტავს მას — შეუთავსეთ ის ქვემოთ აღწერილ იდემპოტენტობასთან.
3. გადაითვალეთ `HMAC-SHA256(signing_secret, "{timestamp}.{raw_body}")` და შეადარეთ ის digest-ს **მუდმივ დროში**.
4. გაატარეთ დუბლიკატები payload `id`-ის მიხედვით (ასევე ჩანს როგორც `Tuist-Event-Id` ჰედერი). ის სტაბილურია განმეორებებზე, ამიტომ უკვე დამუშავებული ID-ების შენახვა ხელს უშლის დაჭერილი მოთხოვნის განმეორებით გაშვებას დაშვებულ ფანჯარაში და გიცავთ განმეორებითი დამუშავებისგან.

> [!IMPORTANT] USE THE RAW BODY
> ხელმოწერა გამოითვლება Tuist-ის მიერ გაგზავნილ ბაიტებზე. თუ თქვენი ვებ-ჩარჩო JSON-ს ხელახლა პარსავს და სერიალიზებს ვერიფიკაციამდე, digest არ ემთხვევა. დაიჭირეთ raw body (მაგ., `request.body.read` Rack-ში, raw `Buffer` Express-ში) და გადაეცით ის თქვენს ვერიფიკატორს.

სანიმუშო ვერიფიკატორი Node.js-ში — გადაიტანეთ იგივე ოთხი ნაბიჯი (ჰედერის პარსინგი, დროის შტამპის ცდომილების შემოწმება, HMAC-ის გადათვლა, შედარება მუდმივ დროში) იმ ენაზე, რომელზეც დაწერილია თქვენი მიმღები:

```javascript
import crypto from "node:crypto";

function verifyTuistSignature(rawBody, header, secret, toleranceSeconds = 300) {
  const parts = Object.fromEntries(
    header.split(",").map((kv) => kv.split("=", 2))
  );
  const timestamp = Number(parts.t);
  const signature = parts.v1;
  if (!timestamp || !signature) return false;

  const drift = Math.abs(Math.floor(Date.now() / 1000) - timestamp);
  if (drift > toleranceSeconds) return false;

  const expected = crypto
    .createHmac("sha256", secret)
    .update(`${timestamp}.${rawBody}`)
    .digest("hex");

  const a = Buffer.from(expected, "hex");
  const b = Buffer.from(signature, "hex");
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}
```

## განმეორებები {#retries}

Tuist ახდენს ნებისმიერი მიწოდების განმეორებას, რომელიც აბრუნებს არა-`2xx` სტატუსს, ამოიწურება დრო ან ვერ უკავშირდება. გრაფიკი ფიქსირებულია:

| მცდელობა | ლოდინა გაგზავნამდე |
| ------- | ------------------- |
| 1       | (მყისიერი)         |
| 2       | 1 წუთი            |
| 3       | 5 წუთი           |
| 4       | 30 წუთი          |
| 5       | 2 საათი             |
| 6       | 8 საათი             |
| 7       | 24 საათი            |

მეშვიდე მცდელობის ჩავარდნის შემდეგ, მიწოდება სამუდამოდ მონიშნულია როგორც ჩავარდნილი. ვინაიდან ყოველი მცდელობა ხელმოწერილია გაგზავნის დროის შტამპით, თქვენი replay-protection ფანჯარა კვლავ მოქმედებს განმეორებებზე — მისი გაფართოება არ არის საჭირო.

## მიწოდებების ინსპექტირება {#inspect-deliveries}

გახსენით endpoint **Webhooks** გვერდიდან მისი მიწოდების ისტორიის სანახავად. დეტალური გვერდი აჩვენებს:

- **შეჯამების ბარათს** დანიშნულების URL-ით, დამალული ხელმოწერის საიდუმლოთი, გამოწერილი მოვლენებით და შექმნის თარიღით.
- **მიწოდების დიაგრამას** მიმდინარე ჯამებით და ჩავარდნების რაოდენობით, არჩეული დროის ფანჯრის ფარგლებში.
- **მოვლენების ცხრილს**, რომლის ფილტრაციაც შესაძლებელია სტატუსის, მოვლენის ტიპის ან მოვლენის ID-ის მიხედვით.

![webhook endpoint-ის დეტალური გვერდი, რომელიც აჩვენებს შეჯამების ბარათს და მოვლენების მიწოდების დიაგრამას](/images/guides/integrations/webhooks/endpoint-detail.png)

დააჭირეთ მოვლენას, რათა ნახოთ სრული მოთხოვნა და პასუხი ამ მცდელობიდან — ზუსტი payload, რომელიც Tuist-მა გაგზავნა, ჰედერები, upstream სტატუსის კოდი და პასუხის სხეული. ეს იგივე მონაცემებია, რაც თქვენმა სერვერმა ნახა, რაც ხდის მას ყველაზე სწრაფ გზას ხელმოწერის ვერიფიკაციის შეუსაბამობის ან 5xx upstream პრობლემის დიაგნოსტიკისთვის.

![webhook მოვლენის დეტალური გვერდი, რომელიც აჩვენებს შეჯამებას, მოთხოვნის ჰედერებს და სხეულს, ასევე upstream პასუხს](/images/guides/integrations/webhooks/event-detail.png)

მიწოდების ჩანაწერები ინახება უვადოდ, რათა შეძლოთ ინტეგრაციის დიაგნოსტიკისას უკან გადახედვა. თუ თქვენს ქვედა დონის სისტემას სჭირდება მყარი ასლები (მაგ., შესაბამისობისთვის), დაიჭირეთ მიწოდებები თქვენს ინფრასტრუქტურაზე მათი მიღებისას.

## endpoint-ის საიდუმლოს როტაცია ან წაშლა {#rotate-or-delete}

ორივე ქმედება ხელმისაწვდომია kebab მენიუში endpoint-ის სტრიქონზე და endpoint-ის დეტალურ გვერდზე:

- **საიდუმლოს როტაცია** — ქმნის ახალ ხელმოწერის საიდუმლოს და აჩვენებს მას ერთხელ. არსებული მომხმარებლები ვერიფიკაციას ვერ გაივლიან მანამ, სანამ არ განაახლებთ მათ, ამიტომ დაგეგმეთ როტაცია დეპლოიმენტთან ერთად.
- **endpoint-ის წაშლა** — შლის endpoint-ს და აჩერებს მიწოდებას. უკვე ჩაწერილი მიწოდების მცდელობები ინახება სტანდარტული შენახვის ფანჯრის ამოწურვამდე.

## უსაფრთხოების შენიშვნები {#security}

- Endpoint URL-ები უნდა იყოს HTTPS. Tuist უარს ამბობს plaintext დანიშნულებებზე მიწოდებაზე.
- Tuist ახდენს დანიშნულების ჰოსტნეიმის რეზოლუციას ყოველი მიწოდებამდე და უარყოფს loopback, RFC1918, link-local, ULA და cloud-metadata მისამართებს (`169.254.169.254`, `fd00::/8`, …). ეს ხელს უშლის არასწორად კონფიგურირებული webhook-ის გამოყენებას თქვენი Tuist სერვერის მასპინძლის სკანირების ან შეტევისთვის.
- Endpoint URL და ხელმოწერის საიდუმლო დაშიფრულია უძრაობისას. ისინი გამორიცხულია GDPR/CCPA მონაცემთა ექსპორტიდან როგორც bearer credentials.
- ხელმოწერის საიდუმლო ნაჩვენებია ზუსტად ერთხელ. მოეპყარით მას როგორც პაროლს: შეინახეთ თქვენს საიდუმლოების მენეჯერში, არა რეპოზიტორიაში.
