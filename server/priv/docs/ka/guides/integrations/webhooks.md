# ვებჰუკები {#webhooks}

ვებჰუკები საშუალებას აძლევს თქვენს სისტემებს რეაგირება მოახდინონ Tuist-ში მიმდინარე ცვლილებებზე მათი წარმოქმნისთანავე. როდესაც შესაბამისი მოვლენა ხდება — ახალი სატესტო შემთხვევა ფიქსირდება, პრივიუსის ატვირთვა სრულდება, არასტაბილური ტესტი კორექტირდება — Tuist აგზავნის HTTP POST მოთხოვნას ყველა იმ ენდპოინტზე, რომელიც გამოწერილი გაქვთ ამ ტიპის მოვლენისთვის. მოთხოვნის სხეული არის JSON კონვერტი, ხოლო თითოეული მიწოდება შეიცავს ხელმოწერის ჰედერს, რომლის ვერიფიკაციაც შესაძლებელია ენდპოინტის ხელმოწერის საიდუმლო კოდით.

თქვენ რეგისტრირებთ დანიშნულების URL-ს, ირჩევთ სასურველ მოვლენებს და Tuist იღებს თავის თავზე ხელმოწერას, ხელახლა ცდებსა და მიწოდების აუდიტის ჟურნალს.

## ნაბიჯები ვებჰუკების მიღებისთვის {#steps}

შეგიძლიათ დაიწყოთ მოვლენების შეტყობინებების მიღება თქვენს აპლიკაციაში შემდეგი ნაბიჯებით:

1. [განსაზღვრეთ მოვლენები](#event-types), რომელთა მიღებაც სურს თქვენს აპლიკაციას.
2. [შექმენით ვებჰუკის ენდპოინტი](#create-an-endpoint) როგორც HTTP ენდპოინტი (URL) თქვენს ლოკალურ სერვერზე.
3. დაამუშავეთ Tuist-ის მოთხოვნები [პეილოუდის პარსინგით](#payload) და [2xx სტატუსის დაბრუნებით](#responding), რათა Tuist-მა მიწოდება წარმატებულად აღნიშნოს.
4. [დაადასტურეთ ხელმოწერა](#verify-signature) ყოველ მოთხოვნაზე, რათა დარწმუნდეთ, რომ ის Tuist-დან მოდის.
5. გამოიყენეთ [მოვლენების ჟურნალი](#inspect-deliveries) Tuist-ის დაშბორდზე შეცდომების გამოსასწორებლად ბილდის პროცესში.

## მოვლენების ტიპები {#event-types}

Tuist აჯგუფებს მოვლენებს იმ რესურსის მიხედვით, რომელსაც ისინი აღწერენ. კონვერტში `type` ველი იყენებს წერტილოვან ნოტაციას (`{resource}.{action}`) — იგივე მნიშვნელობას, რომელსაც გამოიწერთ დაშბორდზე.

მოგვიანებით დაემატება მეტი მოვლენის ტიპი. თუ გჭირდებათ ისეთი, რომელსაც ჩვენ ჯერ არ ვაგზავნით, შეგვატყობინეთ და მას კატალოგში დავამატებთ.

## ენდპოინტის შექმნა {#create-an-endpoint}

ენდპოინტები კონფიგურირდება ანგარიშის მიხედვით. გახსენით **ვებჰუკები** თქვენი ანგარიშის პარამეტრებიდან, დააჭირეთ **ენდპოინტის დამატებას** და მიუთითეთ:

- **სახელი** — როგორ გამოჩნდება ენდპოინტი სიაში.
- **ენდპოინტის URL** — უნდა იყენებდეს `https://`-ს.
- **მოსასმენი მოვლენები** — აირჩიეთ კონკრეტული მოვლენები ან გამოიყენეთ **ყველას არჩევა** ჯგუფის დონეზე. Tuist აგზავნის POST მოთხოვნას ენდპოინტზე მხოლოდ მაშინ, როდესაც ერთ-ერთი გამოწერილი მოვლენა ხდება.

## პეილოუდი {#payload}

ყოველი მიწოდება არის ერთი JSON ობიექტი. კონვერტი აერთიანებს მოვლენისთვის დამახასიათებელ რესურსის სნეპშოტს მეტამონაცემებში, რომელთა გამოყენებაც შეგიძლიათ დუბლიკატების აღმოსაფხვრელად, მარშრუტიზაციისთვის და მიწოდებების აუდიტისთვის:

| ველი     | აღწერა                                                              |
| --------- | ------------------------------------------------------------------------ |
| `id`      | ამ მიწოდებისთვის უნიკალური UUID. გამოიყენეთ ის დუბლიკატების აღმოსაფხვრელად, როდესაც ხელახლა ცდები ხდება. |
| `type`    | წერტილოვანი მოვლენის ტიპი, მაგ. `test_case.updated`.                         |
| `created` | Unix დროის შტამპი (წამებში), როდესაც Tuist-მა მიწოდება რიგში ჩააყენა.           |
| `object`  | რესურსის სნეპშოტი. სტრუქტურა დამოკიდებულია მოვლენის ტიპზე.              |

თითოეული მოვლენის ტიპის ზუსტი პეილოუდის სქემა დოკუმენტირებულია [Tuist API ცნობარში](https://tuist.dev/api/docs#section/Webhook-events) **ვებჰუკის მოვლენები** ქვეშ — ყოველ მოვლენას აქვს შესაბამისი `WebhookXxxEvent` სქემა `components.schemas` ქვეშ, რომლის `$ref`-ც შესაძლებელია კოდის გენერატორიდან.

`test_case.updated` პეილოუდი, მაგალითად, ასევე შეიცავს `events` მასივს, რომელიც ჩამოთვლის კანონიკურ გადასვლებს, რამაც გამოიწვია ჩაწერა (`marked_flaky`, `muted`, `unskipped`, …), ასევე `actor_id` და `alert_id`, რათა მიმღებებმა განასხვავონ ხელით შესრულებული ცვლილებები ავტომატიზაციით გამოწვეული ცვლილებებისგან.

ყოველი მოთხოვნა ასევე შეიცავს შემდეგ HTTP ჰედერებს:

| ჰედერი              | აღწერა                                                                                   |
| ------------------- | --------------------------------------------------------------------------------------------- |
| `Content-Type`      | ყოველთვის `application/json`.                                                                    |
| `User-Agent`        | `Tuist-Webhooks/1.0`.                                                                         |
| `Tuist-Event-Id`    | იგივე UUID, რაც `id` სხეულში — მოსახერხებელია, თუ ჰედერებს იწერთ პეილოუდის პარსინგამდე.     |
| `Tuist-Event-Type`  | იგივე სტრიנגი, რაც `type` სხეულში.                                                            |
| `Tuist-Signature`   | HMAC-SHA256 ხელმოწერა, ფორმატირებული როგორც `t={timestamp},v1={hex_digest}` — იხილეთ ქვემოთ.          |

## პასუხის გაგზავნა ვებჰუკზე {#responding}

მიწოდების დასადასტურებლად, თქვენმა ენდპოინტმა უნდა დააბრუნოს ნებისმიერი `2xx` სტატუსის კოდი. ყველაფერი, რაც `2xx` დიაპაზონს გარეთაა — კავშირის შეცდომებთან და ტაიმაუტებთან ერთად — განიხილება როგორც მიწოდების შეცდომა და ხელახლა ცდება. Tuist არ მიჰყვება `3xx` პასუხებს, ამიტომ პირდაპირ უპასუხეთ კანონიკურ URL-ზე გადამისამართების ნაცვლად.

შეინარჩუნეთ თქვენი ჰენდლერი **სწრაფი**: Tuist პასუხის მოლოდინშია მაქსიმუმ **10 წამის** განმავლობაში. თუ გრძელვადიანი ოპერაციების შესრულება გჭირდებათ (სხვა API-ზე დარეკვა, მონაცემთა ბაზის განახლება, შეტყობინებების გაგზავნა), მიიღეთ მოთხოვნა და დაამუშავეთ ის ასინქრონულად. ადრეული პასუხის გაგზავნა ასევე ზრდის თქვენს გამძლეობას ქვედა ნაკადის სერვისებში დროებითი შენელებების მიმართ.

## ხელმოწერის ვერიფიკაცია {#verify-signature}

ნებისმიერმა, ვინც შეიტყობს თქვენს ენდპოინტის URL-ს, შეუძლია მასზე POST-ით მიმართვა. ხელმოწერის საიდუმლო კოდი საშუალებას აძლევს თქვენს სერვერს უარყოს ყველაფერი, რაც Tuist-დან არ მოდის.

ყოველი მოთხოვნისთვის Tuist ითვლის:

```
signed_payload = "{timestamp}.{raw_request_body}"
signature      = HMAC-SHA256(signing_secret, signed_payload)
header         = "t={timestamp},v1={hex(signature)}"
```

თქვენს მხარეს ვერიფიკაციისთვის:

1. წაიკითხეთ `Tuist-Signature` ჰედერი და დაყავით ის `t=` (დროის შტამპი) და `v1=` (hex digest) ნაწილებად.
2. უარყავით მოთხოვნა, თუ დროის შტამპი თქვენი სერვერის მიმდინარე დროზე მეტად **5 წუთით** განსხვავდება. ეს *ზღუდავს* ხელახალი გაგზავნის ფანჯარას, მაგრამ არ კეტავს მას — შეუთავსეთ ის ქვემოთ აღწერილ იდემპოტენტობასთან.
3. გადაითვალეთ `HMAC-SHA256(signing_secret, "{timestamp}.{raw_body}")` და შეადარეთ ის digest-ს **მუდმივი დროის** განმავლობაში.
4. გააერთიანეთ მიწოდებები პეილოუდის `id`-ის მიხედვით (ასევე ხელმისაწვდომია როგორც `Tuist-Event-Id` ჰედერი). ის სტაბილურია ხელახალი ცდების განმავლობაში, ამიტომ უკვე დამუშავებული ID-ების შენახვა ხელს უშლის ჩაჭერილი მოთხოვნის ხელახალ გაგზავნას დაშვებულ ფანჯარაში და გიცავთ ხელახალი ცდის დროს ორმაგი დამუშავებისგან.

> [!IMPORTANT] USE THE RAW BODY
> ხელმოწერა გამოითვლება Tuist-ის მიერ გაგზავნილ ბაიტებზე. თუ თქვენი ვებ-ჩარჩო JSON-ს ხელახლა პარსავს და სერიალიზებს ვერიფიკაციამდე, digest არ ემთხვევა. დაიჭირეთ raw სხეული (მაგ., `request.body.read` Rack-ში, raw `Buffer` Express-ში) და გადაეცით ის თქვენს ვერიფიკატორს.

საცნობარი ვერიფიკატორი Node.js-ში — გადაიტანეთ იგივე ოთხი ნაბიჯი (ჰედერის პარსინგი, დროის შტამპის გადახრის შემოწმება, HMAC-ის გადათვლა, შედარება მუდმივ დროში) იმ ენაზე, რომელზეც დაწერილია თქვენი მიმღები:

```javascript
import crypto from "node:crypto";

function verifyTuistSignature(rawBody, header, secret, toleranceSeconds = 300) {
  const parts = Object.fromEntries(
    header.split(",").map((kv) => kv.split("=", 2))
  );
  const timestamp = Number(parts.t);
  const signature = parts.v1;
  if (!timestamp || !signature) return false;

  const drift = Math.abs(Math.floor(Date.now() / 1000) - timestamp);
  if (drift > toleranceSeconds) return false;

  const expected = crypto
    .createHmac("sha256", secret)
    .update(`${timestamp}.${rawBody}`)
    .digest("hex");

  const a = Buffer.from(expected, "hex");
  const b = Buffer.from(signature, "hex");
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}
```

## ხელახალი ცდები {#retries}

Tuist ხელახლა ცდის ნებისმიერ მიწოდებას, რომელიც აბრუნებს არა-`2xx` სტატუსს, ვერ აკეთებს კავშირს ან ტაიმაუტდება. განრიგი ფიქსირებულია:

| ცდა | ლოდინა გაგზავნამდე |
| ------- | ------------------- |
| 1       | (უყოვნებლივ)         |

## მიწოდებების ინსპექტირება {#inspect-deliveries}

- **შეჯამების ბარათს** დანიშნულების URL-ით, დაფარული ხელმოწერის საიდუმლო კოდით, გამოწერილი მოვლენებით და შექმნის თარიღით.
- **მიწოდების დიაგრამას** მიმდინარე ჯამებით და ჩავარდნების რაოდენობით, არჩეული დროის ფანჯრის ფარგლებში.

## ენდპოინტის საიდუმლო კოდის განახლება ან წაშლა {#rotate-or-delete}

ორივე ქმედება ხელმისაწვდომია kebab მენიუში ენდპოინტის სტრიქონზე და ენდპოინტის დეტალურ გვერდზე:

- **საიდუმლო კოდის განახლება** — ქმნის ახალ ხელმოწერის საიდუმლო კოდს და აჩვენებს მას ერთხელ. არსებული მომხმარებლები ვერ გაივლიან ვერიფიკაციას მანამ, სანამ არ განაახლებთ მათ, ამიტომ დაგეგმეთ განახლება განლაგებასთან ერთად.
- **ენდპოინტის წაშლა** — აშორებს ენდპოინტს და აჩერებს მიწოდებას. უკვე ჩაწერილი მიწოდების ცდები ინახება სტანდარტული შენახვის ფანჯრის ამოწურვამდე.

## უსაფრთხოების შენიშვნები {#security}

- ენდპოინტის URL-ები უნდა იყოს HTTPS. Tuist უარს ამბობს plaintext დანიშნულების ადგილებზე მიწოდებაზე.
- Tuist აგვარებს დანიშნულების ჰოსტნეიმს ყოველი მიწოდებამდე და უარყოფს loopback, RFC1918, link-local, ULA და cloud-metadata მისამართებს (`169.254.169.254`, `fd00::/8`, …). ეს ხელს უშლის არასწორად კონფიგურირებული ვებჰუკის გამოყენებას თქვენი Tuist სერვერის მასპინძლის სკანირების ან შეტევისთვის.
- ენდპოინტის URL და ხელმოწერის საიდუმლო კოდი დაშიფრულია უძრაობის მდგომარეობაში. ისინი გამორიცხულია GDPR/CCPA მონაცემთა ექსპორტიდან, როგორც bearer კრედენციალები.
- ხელმოწერის საიდუმლო კოდი ნაჩვენებია ზუსტად ერთხელ. მოეპყარით მას როგორც პაროლს: შეინახეთ ის თქვენს საიდუმლოების მენეჯერში და არა რეპოზიტორიაში.
