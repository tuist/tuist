# ვებჰუკები {#webhooks}

ვებჰუკები საშუალებას აძლევს თქვენს სისტემებს რეაგირება მოახდინონ Tuist-ში მიმდინარე ცვლილებებზე მათი წარმოქმნისთანავე. როდესაც შესაბამისი მოვლენა ხდება — ახალი სატესტო შემთხვევა ფიქსირდება, პრევიუს ატვირთვა სრულდება, არასტაბილური ტესტი კორექტირდება — Tuist აგზავნის HTTP POST-მოთხოვნას ყველა იმ ენდპოინტზე, რომელიც გამოწერილი გაქვთ ამ ტიპის მოვლენისთვის. მოთხოვნის სხეული არის JSON-კონვერტი, ხოლო თითოეული მიწოდება შეიცავს ხელმოწერის ჰედერს, რომლის ვერიფიკაციაც შესაძლებელია ენდპოინტის ხელმოწერის საიდუმლო კოდით.

თქვენ რეგისტრირებთ დანიშნულების URL-ს, ირჩევთ სასურველ მოვლენებს და Tuist იღებს თავზე ხელმოწერას, ხელახლა ცდებსა და მიწოდების აუდიტის ჟურნალს.

## ნაბიჯები ვებჰუკების მიღებისთვის {#steps}

შეგიძლიათ დაიწყოთ მოვლენების შეტყობინებების მიღება თქვენს აპლიკაციაში შემდეგი ნაბიჯებით:

1. [განსაზღვრეთ მოვლენები](#event-types), რომელთა მიღებაც სურს თქვენს აპლიკაციას.
2. [შექმენით ვებჰუკის ენდპოინტი](#create-an-endpoint) როგორც HTTP ენდპოინტი (URL) თქვენს ლოკალურ სერვერზე.
3. დაამუშავეთ Tuist-ის მოთხოვნები [პეილოადის პარსინგით](#payload) და [2xx სტატუსის დაბრუნებით](#responding), რათა Tuist-მა მიწოდება წარმატებულად აღნიშნოს.
4. [დაადასტურეთ ხელმოწერა](#verify-signature) ყოველ მოთხოვნაზე, რათა დაამტკიცოთ, რომ ის Tuist-დან მოდის.
5. გამოიყენეთ [მოვლენების ჟურნალი](#inspect-deliveries) Tuist-ის დაშბორდზე შეცდომების გამოსასწორებლად პროექტის აწყობის დროს.

## მოვლენების ტიპები {#event-types}

Tuist აჯგუფებს მოვლენებს იმ რესურსის მიხედვით, რომელსაც ისინი აღწერენ. კონვერტის `type` ველი იყენებს წერტილოვან ნოტაციას (`{resource}.{action}`) — იგივე მნიშვნელობას, რომელსაც გამოიწერდით დაშბორდზე.

## ენდპოინტის შექმნა {#create-an-endpoint}

ენდპოინტები კონფიგურირდება ანგარიშის მიხედვით. გახსენით **Webhooks** თქვენი ანგარიშის პარამეტრებიდან, დააჭირეთ **Add endpoint** და მიუთითეთ:

- **სახელი** — როგორ გამოჩნდება ენდპოინტი სიაში.
- **ენდპოინტის URL** — უნდა იყენებდეს `https://`-ს.
- **მოსასმენი მოვლენები** — აირჩიეთ კონკრეტული მოვლენები ან გამოიყენეთ **Select all** ჯგუფის დონეზე. Tuist აგზავნის POST-მოთხოვნას ენდპოინტზე მხოლოდ მაშინ, როდესაც გამოწერილი მოვლენებიდან ერთ-ერთი აქტიურდება.

## პეილოადი {#payload}

ყოველი მიწოდება არის ერთი JSON-ობიექტი. კონვერტი მოიცავს მოვლენის სპეციფიკურ რესურსის სნეპშოტს მეტამონაცემებით, რომლის გამოყენებაც შეგიძლიათ მიწოდებების დედუპლიკაციის, მარშრუტიზაციისა და აუდიტისთვის:

| ველი     | აღწერა                                                              |
| --------- | ------------------------------------------------------------------------ |
| `id`      | UUID, რომელიც უნიკალურია ამ მიწოდებისთვის. გამოიყენეთ ის დედუპლიკაციისთვის, როდესაც ხელახლა ცდები ხორციელდება. |
| `type`    | წერტილოვანი მოვლენის ტიპი, მაგ. `test_case.updated`.                         |
| `created` | Unix დროის შტამპი (წამებში), როდესაც Tuist-მა მიწოდება რიგში ჩააყენა.           |
| `object`  | რესურსის სნეპშოტი. სტრუქტურა დამოკიდებულია მოვლენის ტიპზე.              |

თითოეული მოვლენის ტიპის ზუსტი პეილოადის სქემა დოკუმენტირებულია [Tuist API reference](https://tuist.dev/api/docs#section/Webhook-events)-ში **Webhook events** განყოფილებაში — ყოველ მოვლენას აქვს შესაბამისი `WebhookXxxEvent` სქემა `components.schemas`-ში, რომლის `$ref`-იც შესაძლებელია კოდის გენერატორიდან.

`test_case.updated` პეილოადი, მაგალითად, ასევე შეიცავს `events` მასივს, რომელიც ჩამოთვლის კანონიკურ გადასვლებს, რამაც გამოიწვია ჩაწერა (`marked_flaky`, `muted`, `unskipped`, …), ასევე `actor_id` და `alert_id`, რათა მიმღებებმა განასხვავონ ხელით შესრულებული ცვლილებები ავტომატიზაციით გამოწვეული ცვლილებებისგან.

ყოველი მოთხოვნა ასევე შეიცავს შემდეგ HTTP ჰედერებს:

| ჰედერი              | აღწერა                                                                                   |
| ------------------- | --------------------------------------------------------------------------------------------- |
| `Content-Type`      | ყოველთვის `application/json`.                                                                    |
| `User-Agent`        | `Tuist-Webhooks/1.0`.                                                                         |
| `Tuist-Event-Id`    | იგივე UUID, რაც სხეულში `id` — მოსახერხებელია, თუ ჰედერებს აფიქსირებთ პეილოადის პარსინგამდე.     |
| `Tuist-Event-Type`  | იგივე სტრიქონი, რაც სხეულში `type`.                                                            |
| `Tuist-Signature`   | HMAC-SHA256 ხელმოწერა, ფორმატით `t={timestamp},v1={hex_digest}` — იხილეთ ქვემოთ.          |

## ვებჰუკზე პასუხის გაცემა {#responding}

მიწოდების დასადასტურებლად, თქვენმა ენდპოინტმა უნდა დააბრუნოს ნებისმიერი `2xx` სტატუსის კოდი. ყველაფერი `2xx` დიაპაზონის გარეთ — კავშირის შეცდომებთან და დროის ამოწურვასთან ერთად — განიხილება როგორც მიწოდების შეცდომა და ხორციელდება ხელახლა. Tuist არ მიჰყვება `3xx` პასუხებს, ამიტომ პირდაპირ უპასუხეთ კანონიკურ URL-ზე გადამისამართების ნაცვლად.

შეინარჩუნეთ თქვენი ჰენდლერი **სწრაფი**: Tuist პასუხისთვის ელოდება მაქსიმუმ **10 წამს**. თუ გაქვთ რთული სამუშაო შესასრულებელი (სხვა API-ზე დაძახება, მონაცემთა ბაზის განახლება, შეტყობინებების გაგზავნა), მიიღეთ მოთხოვნა და დაამუშავეთ ის ასინქრონულად. ადრეული პასუხის გაცემა ასევე გაგიმყარებთ მდგრადობას ქვედა დონის სერვისებში დროებითი შენელების მიმართ.

## ხელმოწერის ვერიფიცირება {#verify-signature}

ნებისმიერს, ვინც გაიგებს თქვენს ენდპოინტის URL-ს, შეუძლია მასზე POST მოთხოვნის გაგზავნა. ხელმოწერის საიდუმლო კოდი საშუალებას აძლევს თქვენს სერვერს უარყოს ყველაფერი, რაც არ მოდის Tuist-დან.

ყოველი მოთხოვნისთვის Tuist ითვლის:

```
signed_payload = "{timestamp}.{raw_request_body}"
signature      = HMAC-SHA256(signing_secret, signed_payload)
header         = "t={timestamp},v1={hex(signature)}"
```

თქვენს მხარეს ვერიფიცირებისთვის:

1. წაიკითხეთ `Tuist-Signature` ჰედერი და დაყავით ის `t=` (დროის შტამპი) და `v1=` (hex digest) ნაწილებად.
2. უარყავით მოთხოვნა, თუ დროის შტამპი თქვენი სერვერის მიმდინარე დროსთან შედარებით **5 წუთზე** მეტად განსხვავდება. ეს *ზღუდავს* განმეორებითი გამოყენების ფანჯარას, მაგრამ არ კეტავს მას — შეუთავსეთ ის ქვემოთ მოცემულ იდემპოტენტობასთან.
3. გადაანგარიშეთ `HMAC-SHA256(signing_secret, "{timestamp}.{raw_body}")` და შეადარეთ ის digest-ს **მუდმივ დროში**.
4. გააკეთეთ მიწოდებების დედუპლიკაცია პეილოადის `id`-ით (ასევე ჩანს როგორც `Tuist-Event-Id` ჰედერი). ის სტაბილურია ხელახალი ცდების განმავლობაში, ამიტომ უკვე დამუშავებული ID-ების შენახვა ხელს უშლის перехваченный მოთხოვნის განმეორებით გამოყენებას დაშვებულ ფანჯარაში და გიცავთ ხელახალი ცდის დროს ორჯერ დამუშავებისგან.

> [!IMPORTANT] USE THE RAW BODY
> ხელმოწერა ითვლება Tuist-ის მიერ გაგზავნილ ბაიტებზე. თუ თქვენი ვებ-ფრეიმვორკი JSON-ს ხელახლა პარსავს და სერიალიზაციას აკეთებს ვერიფიცირებამდე, digest არ ემთხვევა. დაიჭირეთ raw სხეული (მაგ., `request.body.read` Rack-ში, raw `Buffer` Express-ში) და გადაეცით ის თქვენს ვერიფიკატორს.

საცნობარო ვერიფიკატორი Node.js-ში — გადაიტანეთ იგივე ოთხი ნაბიჯი (ჰედერის პარსინგი, დროის შტამპის გადახრის შემოწმება, HMAC-ის გადაანგარიშება, შედარება მუდმივ დროში) იმ ენაზე, რომელზეც დაწერილია თქვენი მიმღები:

```javascript
import crypto from "node:crypto";

function verifyTuistSignature(rawBody, header, secret, toleranceSeconds = 300) {
  const parts = Object.fromEntries(
    header.split(",").map((kv) => kv.split("=", 2))
  );
  const timestamp = Number(parts.t);
  const signature = parts.v1;
  if (!timestamp || !signature) return false;

  const drift = Math.abs(Math.floor(Date.now() / 1000) - timestamp);
  if (drift > toleranceSeconds) return false;

  const expected = crypto
    .createHmac("sha256", secret)
    .update(`${timestamp}.${rawBody}`)
    .digest("hex");

  const a = Buffer.from(expected, "hex");
  const b = Buffer.from(signature, "hex");
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}
```

## ხელახალი ცდები {#retries}

Tuist აკეთებს ხელახალ ცდას ნებისმიერი მიწოდებისთვის, რომელიც აბრუნებს არა-`2xx` სტატუსს, ამოიწურება დრო ან ვერ უკავშირდება. გრაფიკი ფიქსირებულია:

| ცდა | ლოდინა გაგზავნამდე |
| ------- | ------------------- |
| 1       | (მყისიერი)         |
| 2       | 1 წუთი            |
| 3       | 5 წუთი           |
| 4       | 30 წუთი          |
| 5       | 2 საათი             |
| 6       | 8 საათი             |
| 7       | 24 საათი            |

მეშვიდე ცდის ჩავარდნის შემდეგ, მიწოდება სამუდამოდ მონიშნება როგორც ჩავარდნილი. ვინაიდან ყოველი ცდა ხელმოწერილია იმ დროის შტამპით, როდესაც ის გაიგზავნა, თქვენი განმეორებითი გამოყენების დაცვის ფანჯარა კვლავ მოქმედებს ხელახალი ცდების დროს — არ გჭირდებათ მისი გაფართოება.

## მიწოდებების ინსპექტირება {#inspect-deliveries}

გახსენით ენდპოინტი **Webhooks** გვერდიდან, რათან ნახოთ მისი მიწოდების ისტორია. დეტალური გვერდი აჩვენებს:

- **შეჯამების ბარათს** დანიშნულების URL-ით, დამალული ხელმოწერის საიდუმლო კოდით, გამოწერილი მოვლენებით და შექმნის თარიღით.
- **მიწოდების დიაგრამას** მიმდინარე ჯამებით და შეცდომების რაოდენობით, არჩეული დროის ფანჯრის მიხედვით.
- **მოვლენების ცხრილს**, რომლის ფილტრაციაც შესაძლებელია სტატუსით, მოვლენის ტიპით ან მოვლენის ID-ით.

## ენდპოინტის საიდუმლო კოდის როტაცია ან წაშლა {#rotate-or-delete}

ორივე ქმედება ხელმისაწვდომია kebab მენიუში ენდპოინტის სტრიქონზე და ენდპოინტის დეტალურ გვერდზე:

- **საიდუმლო კოდის როტაცია** — ქმნის ახალ ხელმოწერის საიდუმლო კოდს და აჩვენებს მას ერთხელ. არსებული მომხმარებლები ვერ ახდენენ ვერიფიცირებას მანამ, სანამ არ განაახლებთ მათ, ამიტომ დაგეგმეთ როტაცია დეპლოიმენტთან ერთად.
- **ენდპოინტის წაშლა** — შლის ენდპოინტს და აჩერებს მიწოდებას. უკვე ჩაწერილი მიწოდების ცდები ინახება სტანდარტული შენახვის ფანჯრის ამოწურვამდე.

## უსაფრთხოების შენიშვნები {#security}

- ენდპოინტის URL-ები უნდა იყოს HTTPS. Tuist უარს ამბობს plaintext დანიშნულებებზე მიწოდებაზე.
- Tuist აგვარებს დანიშნულების ჰოსტის სახელს ყოველი მიწოდებამდე და უარყოფს loopback, RFC1918, link-local, ULA და cloud-metadata მისამართებს (`169.254.169.254`, `fd00::/8`, …). ეს ხელს უშლის არასწორად კონფიგურირებული ვებჰუკის გამოყენებას თქვენი Tuist სერვერის მასპინძელი ჰოსტის სკანირების ან შეტევისთვის.
- ენდპოინტის URL და ხელმოწერის საიდუმლო კოდი დაშიფრულია უძრაობისას. ისინი გამორიცხულია GDPR/CCPA მონაცემთა ექსპორტიდან როგორც bearer credentials.
- ხელმოწერის საიდუმლო კოდი ნაჩვენებია მხოლოდ ერთხელ. მოეპყარით მას როგორც პაროლს: შეინახეთ ის თქვენს საიდუმლოების მენეჯერში და არა რეპოზიტორიში.
