# ვებჰუკები {#webhooks}

ვებჰუკები საშუალებას აძლევს თქვენს სისტემებს რეაგირება მოახდინონ Tuist-ში მიმდინარე ცვლილებებზე მათი წარმოქმნისთანავე. როდესაც შესაბამისი მოვლენა ხდება — ახალი სატესტო შემთხვევა ფიქსირდება, პრივიუსის ატვირთვა სრულდება, არასტაბილური ტესტი ისწორება — Tuist აგზავნის HTTP POST მოთხოვნას ყველა იმ ენდპოინტზე, რომელიც გამოწერილი გაქვთ ამ ტიპის მოვლენებისთვის. მოთხოვნის სხეული არის JSON კონვერტი და ყოველი მიწოდება შეიცავს ხელმოწერის ჰედერს, რომლის ვერიფიკაციაც შესაძლებელია ენდპოინტის ხელმოწერის საიდუმლო კოდით.

თქვენ აირჩევთ დანიშნულების URL-ს, მონიშნავთ სასურველ მოვლენებს და Tuist უზრუნველყოფს ხელმოწერას, განმეორებით ცდებსა და მიწოდების აუდიტის ჟურნალს.

## ნაბიჯები ვებჰუკების მიღებისთვის {#steps}

შეგიძლიათ დაიწყოთ მოვლენების შეტყობინებების მიღება თქვენს აპლიკაციაში შემდეგი ნაბიჯებით:

1. [განსაზღვრეთ მოვლენები](#event-types), რომელთა მიღებაც სურთ თქვენს აპლიკაციას.
2. [შექმენით ვებჰუკის ენდპოინტი](#create-an-endpoint) როგორც HTTP ენდპოინტი (URL) თქვენს ლოკალურ სერვერზე.
3. დაამუშავეთ Tuist-ის მოთხოვნები [პეილოდის პარსინგით](#payload) და [2xx სტატუსის](#responding) დაბრუნებით, რათა Tuist-მა მიწოდება წარმატებულად აღნიშნოს.
4. [დაავერიფიცირეთ ხელმოწერა](#verify-signature) ყოველ მოთხოვნაზე, რათა დაამტკიცოთ, რომ ის Tuist-დან მოდის.
5. გამოიყენეთ [მოვლენების ჟურნალი](#inspect-deliveries) Tuist-ის დაშბორდზე შეცდომების გამოსასწორებლად პროექტის აწყობის დროს.

## მოვლენების ტიპები {#event-types}

Tuist აჯგუფებს მოვლენებს იმ რესურსის მიხედვით, რომელსაც ისინი აღწერენ. კონვერტში `type` ველი იყენებს წერტილოვან ნოტაციას (`{resource}.{action}`) — იგივე მნიშვნელობას, რომელსაც გამოიწერდით დაშბორდზე.

## ენდპოინტის შექმნა {#create-an-endpoint}

ენდპოინტები კონფიგურირდება ანგარიშის მიხედვით. გახსენით **ვებჰუკები** თქვენი ანგარიშის პარამეტრებიდან, დააჭირეთ **ენდპოინტის დამატება** და მიუთითეთ:

- **სახელი** — როგორ გამოჩნდება ენდპოინტი სიაში.
- **ენდპოინტის URL** — უნდა იყენებდეს `https://`-ს.
- **მოსასმენი მოვლენები** — აირჩიეთ კონკრეტული მოვლენები ან გამოიყენეთ **ყველას მონიშვნა** ჯგუფის დონეზე. Tuist აგზავნის POST-ს ენდპოინტზე მხოლოდ მაშინ, როდესაც ერთ-ერთი გამოწერილი მოვლენა აქტიურდება.

## პეილოდი {#payload}

ყოველი მიწოდება არის ერთი JSON ობიექტი. კონვერტი აერთიანებს მოვლენისთვის სპეციფიკურ რესურსის სნეპშოტს მეტამონაცემებში, რომელთა გამოყენებაც შესაძლებელია მიწოდებების დედუპლიკაციის, მარშრუტიზაციისა და აუდიტისთვის:

| ველი     | აღწერა                                                              |
| --------- | ------------------------------------------------------------------------ |
| `id`      | UUID, უნიკალური ამ მიწოდებისთვის. გამოიყენეთ იგი დედუპლიკაციისთვის განმეორებითი ცდების დროს. |
| `type`    | წერტილოვანი მოვლენის ტიპი, მაგ. `test_case.updated`.                         |
| `created` | Unix დროის შტამპი (წამებში), როდესაც Tuist-მა მიწოდება რიგში ჩააყენა.           |
| `object`  | რესურსის სნეპშოტი. სტრუქტურა დამოკიდებულია მოვლენის ტიპზე.              |

ყოველი მოვლენის ტიპის ზუსტი პეილოდის სქემა დოკუმენტირებულია [Tuist API-ის ცნობარში](https://tuist.dev/api/docs#section/Webhook-events) **ვებჰუკის მოვლენები** განყოფილებაში — ყოველ მოვლენას აქვს შესაბამისი `WebhookXxxEvent` სქემა `components.schemas`-ის ქვეშ, რომლის `$ref`-იც შესაძლებელია კოდის გენერატორიდან.

`test_case.updated` პეილოდი, მაგალითად, ასევე შეიცავს `events` მასივს, რომელიც ჩამოთვლის კანონიკურ გადასვლებს, რომლებმაც გამოიწვიეს ჩაწერა (`marked_flaky`, `muted`, `unskipped`, …), ასევე `actor_id` და `alert_id`, რათა მიმღებებმა განასხვავონ ხელით შესრულებული ცვლილებები ავტომატიზაციით გამოწვეული ცვლილებებისგან.

ყოველი მოთხოვნა ასევე შეიცავს შემდეგ HTTP ჰედერებს:

| ჰედერი              | აღწერა                                                                                   |
| ------------------- | --------------------------------------------------------------------------------------------- |
| `Content-Type`      | ყოველთვის `application/json`.                                                                    |
| `User-Agent`        | `Tuist-Webhooks/1.0`.                                                                         |
| `Tuist-Event-Id`    | იგივე UUID, რაც სხეულში `id` — მოსახერხებელია, თუ ჰედერებს იწერთ პეილოდის პარსინგამდე.     |
| `Tuist-Event-Type`  | იგივე სტრიנגი, რაც სხეულში `type`.                                                            |
| `Tuist-Signature`   | HMAC-SHA256 ხელმოწერა, ფორმატირებული როგორც `t={timestamp},v1={hex_digest}` — იხილეთ ქვემოთ.          |

## პასუხის გაცემა ვებჰუკზე {#responding}

მიწოდების დასადასტურებლად, თქვენმა ენდპოინტმა უნდა დააბრუნოს ნებისმიერი `2xx` სტატუსის კოდი. ყველაფერი, რაც `2xx` დიაპაზონს გარეთაა — კავშირის შეცდომებთან და დროის ამოწურვასთან ერთად — განიხილება როგორც მიწოდების შეცდომა და განმეორდება. Tuist არ მიჰყვება `3xx` პასუხებს, ამიტომ პასუხი გაეცით პირდაპირ კანონიკურ URL-ზე გადამისამართების ნაცვლად.

შეინარჩუნეთ თქვენი ჰენდლერი **სწრაფი**: Tuist პასუხისთვის ელოდება მაქსიმუმ **10 წამს**. თუ გაქვთ რთული სამუშაო შესასრულებელი (სხვა API-ის გამოძახება, მონაცემთა ბაზის განახლება, შეტყობინებების გაგზავნა), მიიღეთ მოთხოვნა და დაამუშავეთ ის ასინქრონულად. ადრეული პასუხის გაცემა ასევე ზრდის თქვენს გამძლეობას ქვედა დონის სერვისებში დროებითი შენელების მიმართ.

## ხელმოწერის ვერიფიკაცია {#verify-signature}

ნებისმიერს, ვინც გაიგებს თქვენს ენდპოინტის URL-ს, შეუძლია მასზე POST მოთხოვნის გაგზავნა. ხელმოწერის საიდუმლო კოდი საშუალებას აძლევს თქვენს სერვერს უარყოს ყველაფერი, რაც არ მოდის Tuist-დან.

ყოველი მოთხოვნისთვის Tuist ითვლის:

```
signed_payload = "{timestamp}.{raw_request_body}"
signature      = HMAC-SHA256(signing_secret, signed_payload)
header         = "t={timestamp},v1={hex(signature)}"
```

ვერიფიკაციისთვის თქვენს მხარეს:

1. წაიკითხეთ `Tuist-Signature` ჰედერი და დაყავით ის `t=` (დროის შტამპი) და `v1=` (hex digest) ნაწილებად.
2. უარყავით მოთხოვნა, თუ დროის შტამპი თქვენი სერვერის მიმდინარე დროსთან შედარებით **5 წუთზე** მეტად განსხვავდება. ეს *ზღუდავს* განმეორებითი გაშვების ფანჯარას, მაგრამ არ კეტავს მას — შეუთავსეთ ის ქვემოთ აღწერილ იდემპოტენტობასთან.
3. გადაითვალეთ `HMAC-SHA256(signing_secret, "{timestamp}.{raw_body}")` და შეადარეთ ის digest-ს **მუდმივ დროში**.
4. გააერთიანეთ მიწოდებები პეილოდის `id` მიხედვით (ასევე ჩანს როგორც `Tuist-Event-Id` ჰედერი). ის სტაბილურია განმეორებითი ცდების დროს, ამიტომ უკვე დამუშავებული ID-ების შენახვა ხელს უშლის перехваченный მოთხოვნის განმეორებით გაშვებას დაშვებულ ფანჯარაში და იცავს თქვენს სისტემას განმეორებითი ცდის დროს ორმაგი დამუშავებისგან.

> [!IMPORTANT] USE THE RAW BODY
> ხელმოწერა ითვლება Tuist-ის მიერ გაგზავნილ ბაიტებზე. თუ თქვენი ვებ-ჩარჩო ხელახლა პარსავს და ახდენს JSON-ის რესერიალიზაციას ვერიფიკაციამდე, digest არ ემთხვევა. დაიჭირეთ raw body (მაგ., `request.body.read` Rack-ში, raw `Buffer` Express-ში) და გადაეცით ის თქვენს ვერიფიკატორს.

საწყისი ვერიფიკატორი Node.js-ში — გადაიტანეთ იგივე ოთხი ნაბიჯი (ჰედერის პარსინგი, დროის შტამპის გადახრის შემოწმება, HMAC-ის გადათვლა, შედარება მუდმივ დროში) იმ ენაზე, რომელზეც დაწერილია თქვენი მიმღები:

```javascript
import crypto from "node:crypto";

function verifyTuistSignature(rawBody, header, secret, toleranceSeconds = 300) {
  const parts = Object.fromEntries(
    header.split(",").map((kv) => kv.split("=", 2))
  );
  const timestamp = Number(parts.t);
  const signature = parts.v1;
  if (!timestamp || !signature) return false;

  const drift = Math.abs(Math.floor(Date.now() / 1000) - timestamp);
  if (drift > toleranceSeconds) return false;

  const expected = crypto
    .createHmac("sha256", secret)
    .update(`${timestamp}.${rawBody}`)
    .digest("hex");

  const a = Buffer.from(expected, "hex");
  const b = Buffer.from(signature, "hex");
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}
```

## განმეორებითი ცდები {#retries}

Tuist ახდენს ნებისმიერი მიწოდების განმეორებით ცდას, რომელიც აბრუნებს არა-`2xx` სტატუსს, იწურება დრო ან ვერ უკავშირდება. გრაფიკი ფიქსირებულია:

| ცდა | ლოდინა გაგზავნამდე |
| ------- | ------------------- |
| 1       | (მყისიერად)         |
| 2       | 1 წუთი            |
| 3       | 5 წუთი           |

## მიწოდებების ინსპექტირება {#inspect-deliveries}

გახსენით ენდპოინტი **Webhooks** გვერდიდან, რათან ნახოთ მისი მიწოდების ისტორია. დეტალური გვერდი აჩვენებს:

- **შეჯამების ბარათს** დანიშნულების URL-ით, დაფარული ხელმოწერის საიდუმლო კოდით, გამოწერილი მოვლენებით და შექმნის თარიღით.
- **მიწოდების დიაგრამას** მიმდინარე ჯამებით და ჩავარდნების რაოდენობით, შერჩეული დროის ფანჯრის ფარგლებში.
- **მოვლენების ცხრილს**, რომლის ფილტრაციაც შესაძლებელია სტატუსის, მოვლენის ტიპის ან მოვლენის ID-ის მიხედვით.

## ენდპოინტის საიდუმლო კოდის როტაცია ან წაშლა {#rotate-or-delete}

ორივე ქმედება ხელმისაწვდომია kebab მენიუში ენდპოინტის სტრიქონზე და ენდპოინტის დეტალურ გვერდზე:

- **საიდუმლო კოდის როტაცია** — ქმნის ახალ ხელმოწერის საიდუმლო კოდს და აჩვენებს მას ერთხელ. არსებული მომხმარებლები ვერ გაივლიან ვერიფიკაციას მანამ, სანამ არ განაახლებთ მათ, ამიტომ დაგეგმეთ როტაცია დეპლოის პარალელურად.
- **ენდპოინტის წაშლა** — შლის ენდპოინტს და აჩერებს მიწოდებას. უკვე ჩაწერილი მიწოდების ცდები ინახება სტანდარტული შენახვის ვადის ამოწურვამდე.

## უსაფრთხოების შენიშვნები {#security}

- ენდპოინტის URL-ები უნდა იყოს HTTPS. Tuist უარს ამბობს მიწოდებაზე plaintext დანიშნულების ადგილებზე.
- Tuist ახდენს დანიშნულების ჰოსტნეიმის გარჩევას ყოველი მიწოდებამდე და უარყოფს loopback, RFC1918, link-local, ULA და cloud-metadata მისამართებს (`169.254.169.254`, `fd00::/8`, …). ეს ხელს უშლის არასწორად კონფიგურირებული ვებჰუკის გამოყენებას იმ ჰოსტის სკანირების ან შეტევისთვის, რომელიც აწარმოებს თქვენს Tuist სერვერს.
- ენდპოინტის URL და ხელმოწერის საიდუმლო კოდი დაშიფრულია უძრაობის მდგომარეობაში. ისინი გამორიცხულია GDPR/CCPA მონაცემთა ექსპორტიდან, როგორც bearer credentials.
- ხელმოწერის საიდუმლო კოდი ჩანახდება ზუსტად ერთხელ. მოეპყარით მას როგორც პაროლს: შეინახეთ ის თქვენს საიდუმლოების მენეჯერში, არა რეპოზიტორიაში.
