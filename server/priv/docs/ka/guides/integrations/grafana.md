# Grafana-ის ინტეგრაცია {#grafana}

Tuist-ის მონაცემთა წყარო საშუალებას გაძლევთ გამოიყენოთ ბილდების, ტესტების და ქეშის მეტრიკები Grafana-ში, მათ შორის ხანგრძლივობები, შეცდომების რაოდენობა და ქეშირებით დაზოგილი დრო. ააწყვეთ დაშბორდები თქვენი გუნდისთვის მნიშვნელოვანი პროექტებისა და მეტრიკების მიხედვით, ან გააერთიანეთ Tuist-ის მეტრიკები სხვა მონაცემთა წყაროებთან თქვენი კომპანიის არსებულ დაშბორდებში. გამოიყენეთ Grafana-ის გაფრთხილების წესები და შეტყობინების არხები, რათა თქვენმა გუნდმა იცოდეს, როდის ნელდება ბილდები ან იზრდება შეცდომების რაოდენობა.

## ხელმისაწვდომი მეტრიკები {#metric-definitions}

ცხრილებში ჩამოთვლილია წასაკითხი სახელები და მათი მოთხოვნის იდენტიფიკატორები. ბილდის ჯანმრთელობის მოთხოვნები იყენებენ იდენტიფიკატორს ველში `metric`; ბილდისა და ტესტის ხანგრძლივობის მოთხოვნები ირჩევენ `average`, `p50`, `p90`, ან `p99` ველში `series`.

### ბილდების რაოდენობა და საიმედოობა

| მეტრიკა | იდენტიფიკატორი | რა ზომავს |
| --- | --- | --- |
| ბილდების რაოდენობა | `builds` | ჩაწერილი ბილდების რაოდენობა. |
| წარმატებული ბილდები | `successful_builds` | ბილდები, რომლებიც წარმატებით დასრულდა. |
| შეცდომით დასრულებული ბილდები | `failed_builds` | ბილდები, რომლებიც შეცდომით დასრულდა. |
| გაუქმებული ბილდები | `cancelled_builds` | ბილდები, რომლებიც ჩაიწერა როგორც გაუქმებული. იხილეთ [განსხვავებები ბილდის სისტემებს შორის](#build-systems). |
| ბილდის წარმატების მაჩვენებელი | `success_rate` | წარმატებული ÷ (წარმატებული + შეცდომით დასრულებული), პროცენტულად. |
| შეცდომით ან ნელა შესრულებული ბილდები | `builds_needing_attention` | შეცდომით ან ნელა შესრულებული ბილდები, თითოეული ბილდი ერთხელ ითვლება. |

### ბილდისა და ტესტის ხანგრძლივობა

| მეტრიკა | იდენტიფიკატორი | რა ზომავს |
| --- | --- | --- |
| საშუალო ხანგრძლივობა | `average` | არჩეული გაშვებების საშუალო ხანგრძლივობა. |
| მედიანური ხანგრძლივობა | `p50` | გაშვებების ხანგრძლივობის 50-ე პერცენტილი. |
| 90-ე პერცენტილის ხანგრძლივობა | `p90` | ხანგრძლივობა, რომელიც არ აღემატება გაშვებების 90%-ს. |
| 99-ე პერცენტილის ხანგრძლივობა | `p99` | ხანგრძლივობა, რომელიც არ აღემატება გაშვებების 99%-ს. |
| ნელი ბილდის ზღვარი | `slow_build_threshold` | 90-ე პერცენტილის ხანგრძლივობა, ან თქვენი ფიქსირებული ლიმიტი მილიწამებში. |

ტესტის ხანგრძლივობის მეტრიკები იყენებენ Tuist-ში ჩაწერილ ტესტის გაშვებებს. ნელი ბილდის ზღვარი ვრცელდება მხოლოდ ბილდებზე: ბილდი ნელია, როცა მისი ხანგრძლივობა აღემატება ამ ზღვარს. გაუქმებული ბილდები ითვლება ცალკე და არ შედის ბილდის წარმატების მაჩვენებელში.

### ქეშის დაზოგვა

| მეტრიკა | იდენტიფიკატორი | რა ზომავს |
| --- | --- | --- |
| დაზოგილი ჯამური ამოცანის დრო (Gradle) | `cache_work_avoided` | ქეშში მოხვედრით თავიდან აცილებული ამოცანის შესრულების სავარაუდო დროის ჯამი. |
| ბილდები, რომლებიც იუწყებიან ჯამურ ამოცანის დროს | `cache_work_avoided_samples` | ბილდები სრული შეფასებით. |
| მოხსენებული ქეშის დაზოგილი დრო | `cache_time_saved` | მოხსენებული გასული დროის დაზოგვის ჯამი. |
| ბილდები, რომლებიც იუწყებიან ქეშის დაზოგილ დროს | `cache_time_saved_samples` | ბილდები ვალიდური დაზოგვის მნიშვნელობით. |

Gradle-ის პლაგინი ავტომატურად იუწყება ლოკალური და დისტანციური ამოცანების ქეშში მოხვედრით თავიდან აცილებულ სამუშაოს. თითოეული ქეშირებული ამოცანისთვის ის Gradle-ის მიერ შენახულ საწყის შესრულების დროს აკლებს ამოცანის აღდგენის ხანგრძლივობას, მინიმუმ ნულის გათვალისწინებით. ბილდის შეფასება ამ მნიშვნელობებს კრებს. პარალელური ამოცანები შეიძლება ერთმანეთს ემთხვეოდეს, ამიტომ ეს არის ჯამური ამოცანის დრო და არა დაზოგილი ბილდის გასული დრო. განახლებული და გამოტოვებული ამოცანები გამორიცხულია.

ბილდი ამოცანების ქეშში მოხვედრის გარეშე ნულს იუწყება. თუ რაიმე ქეშირებულ ამოცანას აკლია საწყისი ტაიმინგი, ტელემეტრია არასრულია, ან მორგებული მეტამონაცემების რუკას არ აქვს ადგილი, პლაგინი გამოტოვებს შეფასებას. პლაგინის უფრო ძველი ვერსიები და სხვა ბილდის სისტემები არ იუწყებიან მას. დაფარვის შესამოწმებლად შეადარეთ მოხსენებების რაოდენობა ბილდების საერთო რაოდენობას.

მოხსენებული გასული დროის დაზოგვა მოდის `tuist.cache_time_saved_ms` მეტამონაცემებიდან. ეს მეტრიკა რჩება ცალკე ავტომატური შეფასებისგან.

ქეშის დაზოგვას არ აქვს მნიშვნელობა, როცა არცერთი ბილდი არ იუწყება მას. Once ამჟამად არ იწერს ამ გაზომვას. ქეშში მოხვედრის და გამოტოვების მაჩვენებლები არ არის ხელმისაწვდომი ამ მონაცემთა წყაროს მეშვეობით.

### ცხრილები

ეს იდენტიფიკატორები არის მოთხოვნის `queryType` ველის მნიშვნელობები.

| ცხრილი | მოთხოვნის ტიპი | შემცველობა |
| --- | --- | --- |
| ჯანმრთელობა დატვირთვის მიხედვით | `buildWorkloads` | ბილდების რაოდენობა, წარმატების მაჩვენებელი, მედიანური და 90-ე პერცენტილის ხანგრძლივობა. |
| შეცდომის კატეგორიები | `buildFailureReasons` | ყველა შეცდომა და რაოდენობა შეცდომის კატეგორიის მიხედვით. |
| ბოლო დროის შეცდომით დასრულებული ბილდები | `buildRecentFailures` | ბოლო 100 შეცდომა, Tuist-ზე ბმულებით. |

ბოლო დროის შეცდომები მოიცავს დაწყების დროს, ხანგრძლივობას, მომხმარებელს, ბრენჩს და მოთხოვნილ ამოცანებს. შეცდომის კატეგორიებია `verification`, `infrastructure_tooling` და `unknown`.

დატვირვის შეჯამებები და ბრენჩის/დატვირვის მნიშვნელობების სიები აბრუნებენ 1000-მდე მნიშვნელობას. ბილდის ჯანმრთელობის ცვლადების მოთხოვნები იყენებენ ბოლო 90 დღეს; Gradle-ის მემკვიდრე ცვლადების მოთხოვნები ინარჩუნებენ არსებულ ისტორიულ ფანჯარას. Bazel აჩვენებს ინსტრუმენტის მიერ მოხსენებულ ბილდის მომხმარებელს. სხვა ინტეგრაციები აჩვენებენ ანგარიშს, რომელიც დაკავშირებულია მოხსენების სერთიფიკატთან. ისტორიული Bazel-ის და Once-ის გაშვებები, ასევე Once-ის გაშვებები, რომლებიც მოხსენებულია პროექტის სერთიფიკატებით, ჩანს როგორც უცნობი, თუ მომხმარებელი არ ჩაიწერა.

გამოიყენეთ შეცდომის კატეგორიის ფილტრი ბილდის გაშვებებზე შესაბამისი შეცდომების საპოვნელად. კატეგორია ჩანს ბილდის დეტალებში, ინფორმაციის მითითებით, რომელიც ხსნის მის მნიშვნელობას; ნაგულისხმევი მიმოხილვის და ბილდის გაშვებების ცხრილები ინარჩუნებენ არსებულ სვეტებს. წარმატებულ, გაუქმებულ და დაუსრულებელ ბილდებს არ აქვთ შეცდომის კატეგორია. Gradle-ის ქეშის ანალიტიკის ბარათი და ბილდის დეტალები აჩვენებენ ჯამურ ამოცანის დაზოგილ დროს; ინსტრუმენტის მინიშნება ხსნის შეფასებას და პარალელური ამოცანების ეფექტს. ქეშის ვიჯეტი შედარებს შერჩეულ დიაპაზონს უშუალოდ წინამდებარე იგივე ხანგრძლივობის პერიოდთან იგივე ფილტრების გამოყენებით. შედარებები ნეიტრალურია: უფრო დიდი ჯამი შეიძლება ასახავდეს მეტ ბილდს. წინა შეფასებების არარსებობა არ აჩვენებს შედარებას; ჩაწერილი ნულოვანი საბაზისო მაჩვენებელი აჩვენებს აბსოლუტურ ზრდას პროცენტის ნაცვლად.

## სტანდარტული დაფა {#what-you-can-query}

შემოიტანეთ [ბილდის ჯანმრთელობის დაფა](https://github.com/tuist/tuist/blob/main/grafana-datasource/src/dashboards/build-health.json), შემდეგ აირჩიეთ თქვენი მონაცემთა წყარო და პროექტი. ის მოიცავს ბილდების რაოდენობას, წარმატების მაჩვენებელს, მედიანურ და 90-ე პერცენტილის ხანგრძლივობას, ნელი ბილდის ზღვარს, ნეიტრალურ შეცდომით ან ნელა შესრულებული ბილდების რაოდენობას, დაჯგუფებულ ქეშის დაზოგვას და მოხსენების დაფარვას, ასევე სამ შეცდომისა და დატვირვის ცხრილს. საჭიროების შემთხვევაში დაამატეთ პანელები სხვა ხელმისაწვდომი მეტრიკებისთვის. ავტომატური ნელი ზღვარი არის შერჩეული პერიოდის საკუთარი 90-ე პერცენტილი; მასზე მაღალი ბილდები არ აუცილებლად მიუთითებენ რეგრესიაზე. დააყენეთ ფიქსირებული ზღვარი ხანგრძლივობის სამიზნე გაფრთხილებებისთვის. ქეშის პანელები პრიორიტეტს ანიჭებენ Gradle-ის ავტომატურ ჯამურ ამოცანის დროის შეფასებას მის დაფარვასთან ერთად, რასაც მოსდევს აშკარად მოხსენებული გასული დროის დაზოგვა მათი საკუთარი დაფარვასთან ერთად.

## ბილდის სისტემები {#build-systems}

ბილდის ჯანმრთელობის მოთხოვნები და სტანდარტული დაფა მხარდაჭერენ Bazel-ს, Cargo-ს, Once-ს, Gradle-ს და Xcode-ს. Tuist ირჩევს ბილდის სისტემას თქვენი პროექტიდან. შერეული პროექტები ამჟამად არ არის მხარდაჭერილი ბილდის ჯანმრთელობის მოთხოვნების ან სტანდარტული დაფის მიერ.

| ბილდის სისტემა | დატვირვა | გაუქმების მოხსენება | ქეშის დაზოგვა |
| --- | --- | --- | --- |
| Bazel | ბრძანება | გასვლის კოდი 8, `run`-ის გარდა | მოითხოვს მორგებულ მეტამონაცემებს |
| Cargo | ბრძანება | არ განსხვავდება; რაოდენობა ნულია | გავლილი დროის დაზოგვა მოითხოვს მორგებულ მეტამონაცემებს; კომპილატორის თავიდან არიდებული სამუშაო არ არის გავლილი დროის დაზოგვა |
| Once | ბრძანების ტიპი | ჩაწერილი გაუქმების მიზეზი | არ არის ჩაწერილი |
| Gradle | ამოცანების ჯგუფი | მოხსენებული გაუქმებები | ავტომატური თავიდან არიდებული სამუშაოს შეფასება; გავლილი დროის დაზოგვა მოითხოვს მორგებულ მეტამონაცემებს |
| Xcode | სქემა | არ განსხვავდება; რაოდენობა ნულია | მოითხოვს მორგებულ მეტამონაცემებს |

დამუშავების ჩანაწერები და დაუსრულებელი გაშვებები გამოირიცხება. Bazel მოიცავს ბილდის, ტესტირების, გაშვების და დაფარვის ბრძანებებს. Once მოიცავს დასრულებულ ბილდებს, ტესტებს და ზოგად გაშვებებს. Cargo მოიცავს ბილდის ბრძანებებს, როგორიცაა `build`, `check` და `test-build`; ტესტების შესრულების ძველი ანგარიშები გამოირიცხება ბილდის ჯანმრთელობიდან. Cargo-ს ბოლოდროინდელი შეცდომები იყენებენ ჩაწერილ დაწყების დროს, თუ ის ხელმისაწვდომია, წინააღმდეგ შემთხვევაში გადადიან ჩასმის დროზე; არარსებული ხანგრძლივობები რჩება მიუწვდომლად, ნულის ნაცვლად.

Gradle ამოცანებს აჯგუფებს ინსტრუმენტული ტესტების, ერთეულოვანი ტესტების, lint/checks, assemble/package ან სხვა კატეგორიებში, პრიორიტეტის ამ თანმიმდევრობით. თითოეული ბილდი ეკუთვნის ერთ დატვირვას. მორგებული მეტამონაცემები შეუძლიათ გადაწერონ დატვირვები Xcode-ის, Bazel-ის, Cargo-ს და Gradle-ისთვის.

### შეცდომების კატეგორიები

| კატეგორია | მნიშვნელობა | ჩაწერილი მტკიცებულება |
| --- | --- | --- |
| `verification` | კოდმა ვერ გაიარა კომპილაცია, ლინკინგი, ტესტები ან შემოწმებები. | Gradle-ის ვერიფიკაციის ან კომპილაციის გამონაკლისები და ცნობილი შეცდომიანი ამოცანების ტიპები; Xcode-ის კომპილატორის და ლინკერის პრობლემები; Bazel-ის სტრუქტურირებული არანულოვანი კომპილატორის/ტესტის მოქმედების შედეგები; Cargo-ს ჩაწერილი ვერგამოსული rustc კომპილაციები; Once-ის ტესტის შეცდომები ან მოქმედებები, რომლებიც აშკარად არის განსაზღვრული როგორც კომპილაცია, ლინკინგი, ტესტი, lint ან check. |
| `infrastructure_tooling` | ბილდმა ვერ შეძლო ნორმალურად გაშვება, რადგან მისმა ინსტრუმენტებმა, დამოკიდებულებებმა ან გარემომ ვერ იმუშავა. | Gradle-ის კონფიგურაციის, დამოკიდებულებების გადაჭრის, შეყვანა/გამოყვანის ან მეხსიერების შეცდომები; Bazel-ის სტრუქტურირებული ინფრასტრუქტურის შეცდომები და [დოკუმენტირებული გასვლის კოდები](https://bazel.build/run/scripts); Once-ის ინფრასტრუქტურის მოქმედების შეცდომები. |
| `unknown` | ანგარიში არ შეიცავს საკმარის მტკიცებულებას შეცდომის კლასიფიცირებისთვის. | ნებისმიერი ბრძანებები, არარსებული დიაგნოსტიკა და ძველი ანგარიშები სტრუქტურირებული მტკიცებულების გარეშე. |

Gradle-ის კონფიგურაციის ფაზის შეცდომები, მათ შორის ბილდის სკრიპტებში არსებული შეცდომები, დაჯგუფებულია ინფრასტრუქტურა/ინსტრუმენტების ქვეშ, რადგან ამოცანის შესრულება ვერ გაგრძელდა.

Cargo-ს შეცდომები აშკარა კატეგორიის მეტამონაცემების ან ჩაწერილი ვერგამოსული rustc კომპილაციის გარეშე რჩება `unknown`; მხოლოდ ვერგამოსული `check` ან `test-build` ბრძანება არ ამყარებს ვერიფიკაციის შეცდომას. Cargo-ს ამოცანის ხელახალი გამოყენების მრიცხველები და შეფასებული კომპილატორის თავიდან არიდებული სამუშაო არასდროს უზრუნველყოფენ ვერც გავლილი დროის ქეშის დაზოგვას და ვერც Gradle-ის კუმულაციური ამოცანის დროის მეტრიკას.

აშკარა `tuist.failure_category` მეტამონაცემები გადაწერენ ავტომატურ კლასიფიკაციას. წინააღმდეგ შემთხვევაში, ინფრასტრუქტურის მტკიცებულებას აქვს უპირატესობა ვერიფიკაციაზე, როდესაც ორივე გვხვდება ბილდში. ვერგამოსული ნებისმიერი სკრიპტი არ ითვლება კომპილატორის ან ტესტის შეცდომად. ისტორიულ ანგარიშებს შეუძლიათ გამოიყენონ Tuist-ის მიერ უკვე შენახული მტკიცებულება, მაგრამ ახალი მომხსენებლის ველები არ ავსებენ არარსებულ ინფორმაციას. ავტომატური მომხსენებლის მეტამონაცემები იყენებენ თავისუფალ ადგილს არსებული 20-ჩანაწერიანი მორგებული მეტამონაცემების ლიმიტის ფარგლებში.

`buildFailureReasons` პასუხი ინარჩუნებს თავის `all` სტრიქონს თავსებადობისთვის. სტანდარტული დაფა ფილტრავს ამ ჯამს შეცდომების კატეგორიების დიაგრამიდან და აჩვენებს ჯამურ შეცდომებს ცალკე. ძველ `gradleFailureReasons` მოთხოვნას რჩება თავისი საწყისი სამი კატეგორიის სტრიქონი.

| მოთხოვნა | მოთხოვნის ტიპი |
| --- | --- |
| ბილდის ჯანმრთელობა | `buildHealth` |
| Xcode ბილდის ხანგრძლივობები | `buildDuration` |

`resultMode` ველი აკონტროლებს შედეგების დაბრუნების წესს:

| შედეგი | მნიშვნელობა | ქცევა |
| --- | --- | --- |
| დროის სერია | `series` | მნიშვნელობა თითოეული ინტერვალისთვის. |
| მთელი პერიოდი | `total` | ერთი მნიშვნელობა, გამოთვლილი დიაპაზონში არსებული ყველა გაშვებიდან. |

| ფილტრი | მოთხოვნის ველი | ხელმისაწვდომია |
| --- | --- | --- |
| გარემო | `environment` | ყველა მოთხოვნა |
| ბრენჩი | `gitBranch` | ბილდის ჯანმრთელობის მოთხოვნები და ცხრილები |
| დატვირთვა | `workload` | ბილდის ჯანმრთელობის მოთხოვნები და ცხრილები |
| სტატუსი | `status` | ბილდის ჯანმრთელობის მოთხოვნები, ცხრილები და Xcode ხანგრძლივობები |

| ბილდის ტიპი | `category` | Xcode ბილდის ხანგრძლივობები |

გარემოს მნიშვნელობებია `any`, `ci` (ავტომატური ბილდები) და `local`. სტატუსის მნიშვნელობებია `success`, `failure` და, ბილდის ჯანმრთელობის მოთხოვნებისთვის, `cancelled`; გამოტოვეთ მნიშვნელობა ყველა სტატუსის ჩასართავად. ბილდის ტიპის მნიშვნელობებია `clean` და `incremental`; გამოტოვეთ მნიშვნელობა ორივეს ჩასართავად.

ცარიელ ბილდის ჯანმრთელობის ინტერვალებს აქვთ ნულოვანი რაოდენობა და არ აქვთ საშუალო ხანგრძლივობის, ხანგრძლივობის პერცენტილის ან წარმატების მაჩვენებლის მნიშვნელობა. ნელი ბილდის ზღვარი კვლავ იყენებს შერჩეულ სრულ დიაპაზონს. ცალკეული ტესტის ხანგრძლივობის მოთხოვნა აბრუნებს ნულს ცარიელი დროის სერიის ინტერვალებისთვის. მთელი პერიოდის პერცენტილები გამოითვლება გაშვებებიდან, და არა ინტერვალის პერცენტილებიდან. ბილდის ჯანმრთელობის პერცენტილები იყენებენ ზუსტ აგრეგაციას; ცალკეული Xcode-ისა და ტესტის ხანგრძლივობის მოთხოვნები იყენებენ მიახლოებით პერცენტილებს.

ბილდის ჯანმრთელობის დროის სერიები ათავსებენ ნაწილობრივ პირველ ბაკეტს შერჩეული დიაპაზონის დასაწყისში, რათა ის ხილული დარჩეს. ძველ Gradle მოთხოვნებს რჩებათ თავიანთი საწყისი ბაკეტის დროის ნიშნულები.

ყველა მოთხოვნა იღებს თარიღის დიაპაზონებს 366 დღემდე. მათი საზღვრები და დროის ნიშნულები განსხვავდება:

| მოთხოვნა | გამოყენებული დროის ნიშნული | დიაპაზონის საზღვრები |
| --- | --- | --- |
| ბილდის ჯანმრთელობა: Xcode, Bazel, Cargo, Gradle | ჩანაწერის ჩასმის დრო | მოიცავს დასაწყისს, გამორიცხავს დასასრულს |
| ბილდის ჯანმრთელობა: Once | გაშვების დაწყების დრო | მოიცავს დასაწყისს, გამორიცხავს დასასრულს |
| Xcode ბილდის ხანგრძლივობები | ჩანაწერის ჩასმის დრო | გამორიცხავს დასაწყისსა და დასასრულს |
| ტესტის ხანგრძლივობები | ჩაწერილი გაშვების დრო | მოიცავს დასაწყისსა და დასასრულს |

### დაფის ცვლადები

გამოიყენეთ დაფის ცვლადები პროექტებისა და მხარდაჭერილი ფილტრებისთვის. ბრენჩისა და სამუშაო დატვირთვის ცვლადები იყენებენ შემდეგ მოთხოვნებს:

| ცვლადი | მოთხოვნა |
| --- | --- |
| ბრენჩი | `buildBranches account/project` |
| სამუშაო დატვირთვა | `buildWorkloads account/project` |

ფილტრები იღებენ ერთ ზუსტ მნიშვნელობას. ბრენჩისა და სამუშაო დატვირთვის ცვლადებისთვის, დააყენეთ „ყველა“ ვარიანტის მორგებული მნიშვნელობა `__tuist_all__`-ზე. სხვა ფილტრები იყენებენ ჩაშენებულ „ნებისმიერი“ ვარიანტს ან ცარიელ მნიშვნელობას. მრავალჯერადი არჩევანი და რეგულარული გამოსახულებები არ არის მხარდაჭერილი.

## მორგებული მეტამონაცემების შეტყობინება {#custom-metadata}

Xcode, Bazel, Cargo და Gradle ბილდები იღებენ ამ არჩევით მეტამონაცემთა მნიშვნელობებს:

| გასაღები | დასაშვები მნიშვნელობა |
| --- | --- |
| `tuist.workload` | სამუშაო დატვირთვის სახელი, რომელიც ცვლის ნაგულისხმევ დაჯგუფებას. |
| `tuist.failure_category` | `verification` ან `infrastructure_tooling`. |
| `tuist.cache_work_avoided_ms` | მხოლოდ Gradle. ავტომატურად შეტყობინებული თავიდან აცილებული სამუშაოს შეფასება, მთელ მილიწამებში 365 დღემდე. |
| `tuist.cache_time_saved_ms` | მთელი მილიწამები 0-დან 31,536,000,000-მდე (365 დღე). |

მიეწოდეთ ისინი თქვენი ბილდის ინტეგრაციის მორგებული მეტამონაცემების კონფიგურაციის მეშვეობით:

```json
{
  "custom_metadata": {
    "values": {
      "tuist.workload": "Release verification",
      "tuist.failure_category": "verification",
      "tuist.cache_time_saved_ms": "12000"
    }
  }
}
```

კეშის ეკონომიის შესახებ შეატყობინეთ მხოლოდ მაშინ, როცა გაქვთ გასული დროის გაზომვა ან დოკუმენტური შეფასება იმ ბილდისთვის. კეშის მოხმარებები და ამოცანების კუმულაციური ხანგრძლივობები მხოლოდ ვერ განსაზღვრავენ გასულ ეკონომიას, როცა ამოცანები პარალელურად მუშაობენ. არარსებული კეშის ეკონომია უცნობი რჩება. არარსებული წარუმატებლობის კატეგორიის მეტამონაცემები ეყრდნობა ჩაწერილ მტკიცებულებას, როგორც აღწერილია [აგების სისტემებში](#build-systems). მონაცემთა შენახვა უცვლელია.

## გაფრთხილებები და Slack {#alerts-and-slack}

შექმენით Grafana-ს მიერ მართული გაფრთხილების წესი რიცხვითი მეტრიკით. მაგალითად:

| მეტრიკა | იდენტიფიკატორი | მაგალითის პირობა |
| --- | --- | --- |
| ბილდის წარმატების მაჩვენებელი | `success_rate` | 99%-ზე ქვემოთ |
| წარუმატებელი ბილდები | `failed_builds` | ნულზე ზემოთ |
| 90-ე პროცენტილის ხანგრძლივობა | `p90` | თქვენი გუნდის ხანგრძლივობის ლიმიტზე ზემოთ |

გამოიყენეთ **მთელი პერიოდი** შეფასების ფანჯარაში ერთი მნიშვნელობისთვის, ან შეამცირეთ დროის სერია ერთ მნიშვნელობამდე. ხანგრძლივობის მოთხოვნებისთვის „მთელი პერიოდის“ რეჟიმში, აირჩიეთ ერთი სერია.

- გამოიყენეთ ფიქსირებული პროექტისა და ფილტრის მნიშვნელობები. დაფის ცვლადები ხელმიუწვდომელია ფონური გაფრთხილებების შეფასების დროს.
- გაფრთხილებებისთვის გამოიყენეთ რიცხვითი მოთხოვნები. სამუშაო დატვირვის მონიტორინგისთვის, გაფილტრეთ ბილდის ჯანმრთელობის მოთხოვნა იმ სამუშაო დატვირთვაზე.
- დააყენეთ წესის „მონაცემების არარსებობის“ ქცევა ინტერვალებისთვის, სადაც არ არის ბილდები ან შეტყობინებული კეშის ეკონომია.

დააკონფიგურირეთ [Slack საკონტაქტო წერტილი](https://grafana.com/docs/grafana/latest/alerting/configure-notifications/manage-contact-points/integrations/configure-slack/) და მიმართეთ წესი მისკენ Grafana-ს შეტყობინებების პოლიტიკის მეშვეობით. Grafana აგზავნის შეტყობინებებს და ინახავს Slack-ის სერთიფიკატებს.

## არსებული დაფების განახლება {#upgrading}

არსებული ხანგრძლივობის პანელები ინარჩუნებენ თავიანთ მოთხოვნებს, ფილტრებს, სერიების სახელებსა და ერთეულებს. შენახული Gradle ჯანმრთელობის პანელები და ცვლადები ასევე აგრძელებენ მუშაობას.

შეიტანეთ სტანდარტული დაფა ცალკე, რათა გამოიყენოთ გაზიარებული ბილდის ჯანმრთელობის მოთხოვნები. არსებული დაფები ავტომატურად არ გადაიტანება. გაზიარებული მოთხოვნები საჭიროებენ Tuist სერვერს, რომელიც უზრუნველყოფს ბილდის ჯანმრთელობის ბოლოწერტილებს; არსებული ხანგრძლივობის მოთხოვნები კვლავ მუშაობენ ძველ სერვერებთან.

## მოთხოვნები {#requirements}

- Grafana 10.4 ან უფრო ახალი.
- Tuist ტოკენი ნებართვით, წაიკითხოთ პროექტები და მეტრიკები, რომელთა დიაგრამებზე გამოსახვაც გსურთ. იხილეთ [ავთენტიკაცია](#authentication) ქვემოთ.

## ავთენტიკაცია {#authentication}

გამოიყენეთ <.localized_link href="/guides/server/authentication#account-tokens">ანგარიშის ტოკენი</.localized_link> დაფებისა და ფონური შეტყობინებების შეფასებისთვის. მიანიჭეთ `project:builds:read` ბილდის მეტრიკებისთვის და `project:tests:read` ტესტების ხანგრძლივობისთვის, შემოიფარგლოთ წვდომა იმ პროექტებზე, რომელთა დიაგრამებზე გამოსახვაც გსურთ. საჭიროა მხოლოდ თქვენს მიერ გამოყენებული მეტრიკების სკოპები. ტოკენის გენერირებისთვის მიჰყევით <.localized_link href="/guides/server/authentication#creating-an-account-token">ტოკენის შექმნის ინსტრუქციებს</.localized_link>.

ინტეგრაცია ასევე იღებს არსებულ პროექტის ტოკენებს საკუთარი პროექტისთვის და <.localized_link href="/guides/server/authentication#as-a-user">მომხმარებლის წვდომის ტოკენებს</.localized_link> მომხმარებლის წაკითხვის ნებართვებით. მომხმარებლის წვდომის ტოკენები მოკლევადიანია. Grafana ინახავს თქვენს მიერ მიწოდებულ ტოკენს და არ ანახლებს მას ან არ იყენებს ხელახლა თქვენს ლოკალურ Tuist შესვლას; შეცვალეთ ის ვადის გასვლის შემდეგ. ანგარიშის ტოკენები საშუალებას გაძლევთ აკონტროლოთ პროექტზე წვდომა, ნებართვები და ვადა მომხმარებლის შესვლის სესიისგან დამოუკიდებლად.

## კონფიგურაცია {#configuration}

დაამატეთ მონაცემთა წყარო და დააყენეთ:

## ინსტალაცია {#installation}

### Grafana-ს კატალოგიდან {#from-the-grafana-catalog}

გამოქვეყნების შემდეგ, დააინსტალირეთ ის ნებისმიერი სხვა მონაცემთა წყაროს მსგავსად **Connections → Add new connection → Tuist**-დან, ან `grafana-cli plugins install tuist-metrics-datasource`-ის გამოყენებით.

### გამოქვეყნებამდე (თვითმასპინძელი Grafana) {#before-it-is-published-self-hosted-grafana}

პლაგინი ხელმოუწერელია, სანამ კატალოგისთვის არ დამტკიცდება. თვითმასპინძელ ეგზემპლარზე შეგიძლიათ:

- **დაუშვათ ხელმოუწერლად** — დაამატეთ `tuist-metrics-datasource` `allow_loading_unsigned_plugins`-ში (ან `GF_PLUGINS_ALLOW_LOADING_UNSIGNED_PLUGINS=tuist-metrics-datasource`) და ჩააგდეთ აწყობილი პლაგინი თქვენს პლაგინების დირექტორიაში.
- **პირადად მოაწერეთ ხელი** თქვენი ეგზემპლარებისთვის — `npm run sign -- --rootUrls https://grafana.example.com` (URL უნდა ემთხვეოდეს ეგზემპლარის `root_url`-ს), შემდეგ გაავრცელეთ zip.

[Grafana Cloud მოითხოვს პლაგინებს კატალოგიდან](https://grafana.com/docs/grafana-cloud/learn-and-build/get-started/learn/find-and-use-plugins/) და არ უჭერს მხარს ხელმოუწერელ ან ხელით ატვირთულ პლაგინებს.
