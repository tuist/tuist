# Grafana-ს ინტეგრაცია {#grafana}

Tuist-ის მონაცემთა წყარო საშუალებას გაძლევთ გამოიყენოთ ბილდების, ტესტების და ქეშის მეტრიკები Grafana-ში, მათ შორის ხანგრძლივობები, შეცდომების რაოდენობა და ქეშირებით დაზოგილი დრო. ააწყვეთ დაშბორდები თქვენი გუნდისთვის მნიშვნელოვანი პროექტებისა და მეტრიკების მიხედვით, ან გააერთიანეთ Tuist-ის მეტრიკები სხვა მონაცემთა წყაროებთან თქვენი კომპანიის არსებულ დაშბორდებში. გამოიყენეთ Grafana-ს გაფრთხილების წესები და შეტყობინების არხები, რათა თქვენმა გუნდმა იცოდეს, როდესაც ბილდები ნელდება ან შეცდომების რაოდენობა იზრდება.

## ხელმისაწვდომი მეტრიკები {#metric-definitions}

ცხრილებში ჩამოთვლილია წასაკითხი ლეიბლები და მათი მოთხოვნის იდენტიფიკატორები. ბილდის ჯანმრთელობის მოთხოვნები იყენებენ იდენტიფიკატორს `metric` ველში; ბილდისა და ტესტის ხანგრძლივობის მოთხოვნები ირჩევენ `average`, `p50`, `p90` ან `p99`-ს `series` ველში.

### ბილდების რაოდენობა და საიმედოობა

| მეტრიკა | იდენტიფიკატორი | რას ზომავს |
| --- | --- | --- |
| ბილდების რაოდენობა | `builds` | ჩაწერილი ბილდების რაოდენობა. |
| წარმატებული ბილდები | `successful_builds` | ბილდები, რომლებიც წარმატებით დასრულდა. |
| შეცდომიანი ბილდები | `failed_builds` | ბილდები, რომლებიც ვერ შესრულდა. |
| გაუქმებული ბილდები | `cancelled_builds` | ბილდები, რომლებიც ჩაიწერა როგორც გაუქმებული. იხილეთ [ბილდის სისტემებს შორის განსხვავებები](#build-systems). |
| ბილდის წარმატების მაჩვენებელი | `success_rate` | წარმატებული ÷ (წარმატებული + შეცდომიანი), პროცენტულად. |
| შეცდომიანი ან ნელი ბილდები | `builds_needing_attention` | შეცდომიანი ან ნელი ბილდები, დათვლილი ერთხელ თითოეული ბილდისთვის. |

### ბილდისა და ტესტის ხანგრძლივობები

| მეტრიკა | იდენტიფიკატორი | რას ზომავს |
| --- | --- | --- |
| საშუალო ხანგრძლივობა | `average` | შერჩეული გაშვებების საშუალო ხანგრძლივობა. |
| მედიანური ხანგრძლივობა | `p50` | გაშვებების ხანგრძლივობის 50-ე პერცენტილი. |
| 90-ე პერცენტილის ხანგრძლივობა | `p90` | ხანგრძლივობა, რომლის ქვემოთ ან ტოლია გაშვებების 90%. |
| 99-ე პერცენტილის ხანგრძლივობა | `p99` | ხანგრძლივობა, რომლის ქვემოთ ან ტოლია გაშვებების 99%. |
| ნელი ბილდის ზღვარი | `slow_build_threshold` | 90-ე პერცენტილის ხანგრძლივობა, ან თქვენი ფიქსირებული ზღვარი მილიწამებში. |

ტესტის ხანგრძლივობის მეტრიკები იყენებენ Tuist-ში ჩაწერილ ტესტის გაშვებებს. ნელი ბილდის ზღვარი ვრცელდება მხოლოდ ბილდებზე: ბილდი არის ნელი, როდესაც მისი ხანგრძლივობა აღემატება ამ ზღვარს. გაუქმებული ბილდები ითვლება ცალკე და გამორიცხულია ბილდის წარმატების მაჩვენებლიდან.

### ქეშის დაზოგვა

| მეტრიკა | იდენტიფიკატორი | რას ზომავს |
| --- | --- | --- |
| დაზოგილი ჯამური დავალების დრო (Gradle) | `cache_work_avoided` | ქეშში მოხვედრით თავიდან აცილებული დავალების შესრულების სავარაუდო დროის ჯამი. |
| ბილდები, რომლებიც იტყობინებენ ჯამურ დავალების დროს | `cache_work_avoided_samples` | ბილდები სრული შეფასებით. |
| შეტყობინებული ქეშის დაზოგილი დრო | `cache_time_saved` | შეტყობინებული გასული დროის დაზოგვის ჯამი. |
| ბილდები, რომლებიც იტყობინებენ ქეშის დაზოგილ დროს | `cache_time_saved_samples` | ბილდები ვალიდური დაზოგვის მნიშვნელობით. |

Gradle-ის პლაგინი ავტომატურად იტყობინება სავარაუდო თავიდან აცილებულ სამუშაოს ლოკალური და დისტანციური დავალების ქეშში მოხვედრებისთვის. თითოეული ქეშირებული დავალებისთვის ის აკლებს დავალების აღდგენის ხანგრძლივობას Gradle-ის მიერ შენახულ საწყის შესრულების დროს, მინიმუმ ნულით. ბილდის შეფასება კრებს ამ მნიშვნელობებს ერთად. პარალელურ დავალებებს შეუძლიათ გადაფარვა, ამიტომ ეს არის ჯამური დავალების დრო და არა გასული ბილდის დაზოგილი დრო. განახლებული და გამოტოვებული დავალებები გამორიცხულია.

ბილდი დავალების ქეშში მოხვედრების გარეშე იტყობინება ნულს. თუ რომელიმე ქეშირებულ დავალებას აკლია საწყისი დრო, ტელემეტრია არასრულია, ან მორგებული მეტამონაცემების რუკას არ აქვს ადგილი, პლაგინი ტოვებს შეფასებას. პლაგინის უფრო ძველი ვერსიები და სხვა ბილდის სისტემები არ იტყობინებენ მას. შეადარეთ შეტყობინებების რაოდენობა ბილდების საერთო რაოდენობას დაფარვის შესამოწმებლად.

შეტყობინებული გასული დროის დაზოგვა მოდის `tuist.cache_time_saved_ms` მეტამონაცემებიდან. ეს მეტრიკა რჩება ცალკე ავტომატური შეფასებისგან.

ქეშის დაზოგვას არ აქვს მნიშვნელობა, როდესაც არცერთი ბილდი არ იტყობინებს მას. Once ამჟამად არ იწერს ამ გაზომვას. ქეშში მოხვედრისა და გამოტოვების მაჩვენებლები არ არის ხელმისაწვდომი ამ მონაცემთა წყაროს მეშვეობით.

### ცხრილები

ეს იდენტიფიკატორები არის მოთხოვნის `queryType` ველის მნიშვნელობები.

| ცხრილი | მოთხოვნის ტიპი | შემცველობა |
| --- | --- | --- |
| ჯანმრთელობა დატვირთვით | `buildWorkloads` | ბილდების რაოდენობა, წარმატების მაჩვენებელი, მედიანური და 90-ე პერცენტილის ხანგრძლივობა. |
| შეცდომის კატეგორიები | `buildFailureReasons` | ყველა შეცდომა და რაოდენობა შეცდომის კატეგორიის მიხედვით. |
| ბოლო დროის შეცდომიანი ბილდები | `buildRecentFailures` | ბოლო 100 შეცდომა, ბმულებით Tuist-ზე. |

ბოლო დროის შეცდომები მოიცავს დაწყების დროს, ხანგრძლივობას, მომხმარებელს, შტოს და მოთხოვნილ დავალებებს. შეცდომის კატეგორიებია `verification`, `infrastructure_tooling` და `unknown`.

დატვირთვის შეჯამებები და შტო/დატვირთვის მნიშვნელობების სიები აბრუნებენ 1000-მდე მნიშვნელობას. ბილდის ჯანმრთელობის ცვლადის მოთხოვნები იყენებენ ბოლო 90 დღეს; მემკვიდრე Gradle-ის ცვლადის მოთხოვნები ინარჩუნებენ არსებულ ისტორიის ფანჯარას. Bazel აჩვენებს ბილდის მომხმარებელს, რომელიც შეიტყობინა ინსტრუმენტმა. სხვა ინტეგრაციები აჩვენებენ ანგარიშს, რომელიც დაკავშირებულია შეტყობინების სერთიფიკატთან. ისტორიული Bazel-ისა და Once-ის გაშვებები, და Once-ის გაშვებები, რომლებიც შეიტყობინეს პროექტის სერთიფიკატებით, ჩანს როგორც უცნობი, როდესაც მომხმარებელი არ ჩაიწერა.

გამოიყენეთ შეცდომის კატეგორიის ფილტრი ბილდის გაშვებებზე შესაბამი შეცდომების საპოვნელად. კატეგორია ჩანს ბილდის დეტალებში, ინფორმაციის მინიშნებით, რომელიც ხსნის მის მნიშვნელობას; ნაგულისხმევი გადახედვა და ბილდის გაშვებების ცხრილები ინარჩუნებენ არსებულ სვეტებს. წარმატებულ, გაუქმებულ და დაუსრულებელ ბილდებს არ აქვთ შეცდომის კატეგორია. Gradle-ის ქეშის ანალიტიკის ბარათი და ბილდის დეტალები აჩვენებენ ჯამურ დავალების დაზოგილ დროს; ხელსაწყოების მინიშნება ხსნის შეფასებას და პარალელური დავალებების ეფექტს. ქეშის ვიჯეტი ადარებს შერჩეულ დიაპაზონს უშუალოდ წინამდებარე იგივე ხანგრძლივობის პერიოდს იგივე ფილტრების გამოყენებით. შედარებები ნეიტრალურია: უფრო დიდი ჯამი შეიძლება ასახავდეს მეტ ბილდს. წინა შეფასებების არარსებობა არ აჩვენებს შედარებას; ჩაწერილი ნულოვანი საწყისი წერტილი აჩვენებს აბსოლუტურ ზრდას პროცენტის ნაცვლად.

## სტანდარტული დაფა {#what-you-can-query}

შემოიტანეთ [ბილდის ჯანმრთელობის დაფა](https://github.com/tuist/tuist/blob/main/grafana-datasource/src/dashboards/build-health.json), შემდეგ აირჩიეთ თქვენი მონაცემთა წყარო და პროექტი. ის მოიცავს ბილდების რაოდენობას, წარმატების მაჩვენებელს, მედიანურ და 90-ე პერცენტილის ხანგრძლივობებს, ნელი ბილდის ზღვარს, ნეიტრალურ შეცდომიანი ან ნელი ბილდების რაოდენობას, დაჯგუფებულ ქეშის დაზოგვასა და შეტყობინების დაფარვას, და სამ შეცდომისა და დატვირთვის ცხრილს. დაამატეთ პანელები სხვა ხელმისაწვდომი მეტრიკებისთვის საჭიროების შემთხვევაში. ავტომატური ნელი ზღვარი არის შერჩეული პერიოდის საკუთარი 90-ე პერცენტილი; მასზე მაღალი ბილდები არ მიუთითებს აუცილებლად რეგრესიაზე. დააყენეთ ფიქსირებული ზღვარი ხანგრძლივობის სამიზნე გაფრთხილებებისთვის. ქეშის პანელები პრიორიტეტს ანიჭებენ Gradle-ის ავტომატურ ჯამურ დავალების დროის შეფასებას მის დაფარვასთან ერთად, რასაც მოჰყვება აშკარად შეტყობინებული გასული დროის დაზოგვა მათი საკუთარი დაფარვით.

## ბილდის სისტემები {#build-systems}

ბილდის ჯანმრთელობის მოთხოვნები და სტანდარტული დაფა მხარდაჭერას უწევს Bazel-ს, Cargo-ს, Once-ს, Gradle-ს და Xcode-ს. Tuist ირჩევს ბილდის სისტემას თქვენი პროექტიდან. შერეული პროექტები ამჟამად არ არის მხარდაჭერილი ბილდის ჯანმრთელობის მოთხოვნების ან სტანდარტული დაფის მიერ.

| ბილდის სისტემა | დატვირთვა | გაუქმების შეტყობინება | ქეშის დაზოგვა |
| --- | --- | --- | --- |
| Bazel | ბრძანება | გასვლის კოდი 8, გარდა `run` | საჭიროებს მორგებულ მეტამონაცემებს |
| Cargo | ბრძანება | არ არის განსხვავებული; რაოდენობა არის ნული | დროში გაზომილი დაზოგვა საჭიროებს მორგებულ მეტამონაცემებს; კომპილატორის თავიდან არიდებული სამუშაო არ არის დროში გაზომილი დაზოგვა |
| Once | ბრძანების ტიპი | ჩაწერილი გაუქმების მიზეზი | არ არის ჩაწერილი |
| Gradle | დავალებათა ჯგუფი | შეტყობინებული გაუქმებები | ავტომატური თავიდან არიდებული სამუშაოს შეფასება; დროში გაზომილი დაზოგვა საჭიროებს მორგებულ მეტამონაცემებს |
| Xcode | სქემა | არ არის განსხვავებული; რაოდენობა არის ნული | საჭიროებს მორგებულ მეტამონაცემებს |

დამუშავების ჩანაწერები და დაუსრულებელი გაშვებები გამორიცხულია. Bazel მოიცავს ბილდის, ტესტის, გაშვების და დაფარვის ბრძანებებს. Once მოიცავს დასრულებულ ბილდებს, ტესტებს და ზოგად გაშვებებს. Cargo მოიცავს ისეთ ბილდის ბრძანებებს, როგორიცაა `build`, `check` და `test-build`; ძველი ტესტის შესრულების ანგარიშები გამორიცხულია ბილდის ჯანმრთელობიდან. Cargo-ს ბოლოდროინდელი შეცდომები იყენებენ ჩაწერილ დაწყების დროს, თუ ხელმისაწვდომია, წინააღმდეგ შემთხვევაში გადადიან ჩასმის დროზე; არარსებული ხანგრძლივობები რჩება მიუწვდომლად და არ ითვლება ნულად.

Gradle აჯგუფებს დავალებებს როგორც ინსტრუმენტულ ტესტებს, ერთეულურ ტესტებს, ლინტინგს/შემოწმებებს, აწყობას/პაკეტირებას ან სხვას, ამ პრიორიტეტული თანმიმდევრობით. თითოეული ბილდი ეკუთვნის ერთ დატვირთვას. მორგებული მეტამონაცემები შეუძლია ჩაანაცვლოს დატვირთვები Xcode-ის, Bazel-ის, Cargo-ს და Gradle-ისთვის.

### შეცდომის კატეგორიები

| კატეგორია | მნიშვნელობა | ჩაწერილი მტკიცებულება |
| --- | --- | --- |
| `verification` | კოდის კომპილაციის, ლინკინგის, ტესტების ან შემოწმებების შეცდომა. | Gradle-ის ვერიფიკაციის ან კომპილაციის გამონაკლისები და ცნობილი შეცდომიანი დავალებების ტიპები; Xcode-ის კომპილატორის და ლინკერის პრობლემები; Bazel-ის სტრუქტურირებული არანულოვანი კომპილატორის/ტესტის ქმედებების შედეგები; Cargo-ს ჩაწერილი შეცდომიანი rustc კომპილაციები; Once-ის ტესტის შეცდომები ან ქმედებები, რომლებიც ცალსახად არის განსაზღვრული როგორც კომპილაცია, ლინკინგი, ტესტი, ლინტინგი ან შემოწმება. |
| `infrastructure_tooling` | ბილდი ვერ შესრულდა ჩვეულებრივად, რადგან მისი ინსტრუმენტები, დამოკიდებულებები ან გარემო ვერ მუშაობდა. | Gradle-ის კონფიგურაციის, დამოკიდებულებების გადაწყვეტის, შეყვანა/გამოყვანის ან მეხსიერების შეცდომები; Bazel-ის სტრუქტურირებული ინფრასტრუქტურის შეცდომები და [დოკუმენტირებული გასვლის კოდები](https://bazel.build/run/scripts); Once-ის ინფრასტრუქტურის ქმედებების შეცდომები. |
| `unknown` | ანგარიში არ შეიცავს საკმარის მტკიცებულებას შეცდომის კლასიფიცირებისთვის. | ნებისმიერი ბრძანებები, არარსებული დიაგნოსტიკა და ძველი ანგარიშები სტრუქტურირებული მტკიცებულებების გარეშე. |

Gradle-ის კონფიგურაციის ფაზის შეცდომები, მათ შორის შეცდომები ბილდის სკრიპტებში, დაჯგუფებულია ინფრასტრუქტურა/ინსტრუმენტების ქვეშ, რადგან დავალების შესრულება ვერ გაგრძელდა.

Cargo-ს შეცდომები ცალსახა კატეგორიის მეტამონაცემების ან ჩაწერილი შეცდომიანი rustc კომპილაციის გარეშე რჩება `unknown`; მხოლოდ შეცდომიანი `check` ან `test-build` ბრძანება არ ქმნის ვერიფიკაციის შეცდომას. Cargo-ს დავალების ხელახლა გამოყენების მრიცხველები და კომპილატორის თავიდან არიდებული სამუშაოს შეფასება არასდროს იძლევა დროში გაზომილ ქეშის დაზოგვას ან Gradle-ის კუმულაციური დავალების დროის მეტრიკას.

ცალსახა `tuist.failure_category` მეტამონაცემები ანაცვლებს ავტომატურ კლასიფიკაციას. წინააღმდეგ შემთხვევაში, ინფრასტრუქტურის მტკიცებულებას აქვს უპირატესობა ვერიფიკაციაზე, როდესაც ორივე გვხვდება ბილდში. შეცდომიანი ნებისმიერი სკრიპტი არ ითვლება კომპილატორის ან ტესტის შეცდომად. ისტორიულ ანგარიშებს შეუძლიათ გამოიყენონ Tuist-ის მიერ უკვე შენახული მტკიცებულება, მაგრამ ახალი შემტყობინებლის ველები არ ავსებენ არარსებულ ინფორმაციას. ავტომატური შემტყობინებლის მეტამონაცემები იყენებს თავისუფალ ადგილს არსებული 20-ჩანაწერიანი მორგებული მეტამონაცემების ლიმიტის ფარგლებში.

`buildFailureReasons` პასუხი ინარჩუნებს თავის `all` სტრიქონს თავსებადობისთვის. სტანდარტული დაფა ფილტრავს ამ ჯამს შეცდომის კატეგორიების დიაგრამიდან და ცალკე აჩვენებს ჯამურ შეცდომებს. ძველი `gradleFailureReasons` მოთხოვნა ინარჩუნებს თავის საწყის სამ კატეგორიულ სტრიქონს.

## მოთხოვნის პარამეტრები {#query-options}

რიცხვითი მოთხოვნები იყენებენ ამ `queryType` მნიშვნელობებს:

| მოთხოვნა | მოთხოვნის ტიპი |
| --- | --- |
| ბილდის ჯანმრთელობა | `buildHealth` |
| Xcode ბილდის ხანგრძლივობა | `buildDuration` |
| ტესტის ხანგრძლივობა | `testDuration` |

`resultMode` ველი აკონტროლებს შედეგების დაბრუნების წესს:

| შედეგი | მნიშვნელობა | ქცევა |
| --- | --- | --- |
| დროის სერია | `series` | მნიშვნელობა თითოეული ინტერვალისთვის. |
| მთელი პერიოდი | `total` | ერთი მნიშვნელობა, გამოთვლილი დიაპაზონში არსებული ყველა გაშვებიდან. |

ფილტრის ლეიბლები შეესაბამება ამ მოთხოვნის ველებს:

| ფილტრი | მოთხოვნის ველი | ხელმისაწვდომია |
| --- | --- | --- |
| გარემო | `environment` | ყველა მოთხოვნა |
| ბრენჩი | `gitBranch` | ბილდის ჯანმრთელობის მოთხოვნები და ცხრილები |
| სამუშაო დატვირთვა | `workload` | ბილდის ჯანმრთელობის მოთხოვნები და ცხრილები |
| სტატუსი | `status` | ბილდის ჯანმრთელობის მოთხოვნები, ცხრილები და Xcode ხანგრძლივობა |

| ბილდის ტიპი | `category` | Xcode ბილდის ხანგრძლივობა |

გარემოს მნიშვნელობებია `any`, `ci` (ავტომატიზებული ბილდები) და `local`. სტატუსის მნიშვნელობებია `success`, `failure` და, ბილდის ჯანმრთელობის მოთხოვნებისთვის, `cancelled`; გამორიცხეთ მნიშვნელობა ყველა სტატუსის ჩასართავად. ბილდის ტიპის მნიშვნელობებია `clean` და `incremental`; გამორიცხეთ მნიშვნელობა ორივეს ჩასართავად.

ცარიელ ბილდის ჯანმრთელობის ინტერვალებს აქვთ ნულოვანი რაოდენობა და არ აქვთ საშუალო ხანგრძლივობის, ხანგრძლივობის პერცენტილის ან წარმატების მაჩვენებლის მნიშვნელობა. ნელი ბილდის ზღვარი კვლავ იყენებს სრულად შერჩეულ დიაპაზონს. ცალკეული ტესტის ხანგრძლივობის მოთხოვნა აბრუნებს ნულს ცარიელი დროის სერიის ინტერვალებისთვის. მთელი პერიოდის პერცენტილები გამოითვლება გაშვებებიდან, და არა ინტერვალის პერცენტილებიდან. ბილდის ჯანმრთელობის პერცენტილები იყენებენ ზუსტ აგრეგაციას; ცალკეული Xcode და ტესტის ხანგრძლივობის მოთხოვნები იყენებენ მიახლოებით პერცენტილებს.

ბილდის ჯანმრთელობის დროის სერიები ათავსებენ ნაწილობრივ პირველ ბაკეტს შერჩეული დიაპაზონის დასაწყისში, რათა ის ხილული დარჩეს. ძველი Gradle მოთხოვნები ინარჩუნებენ თავიანთ საწყის ბაკეტის დროის შტამპებს.

ყველა მოთხოვნა იღებს თარიღის დიაპაზონებს 366 დღემდე. მათი საზღვრები და დროის შტამპები განსხვავდება:

| მოთხოვნა | გამოყენებული დროის შტამპი | დიაპაზონის საზღვრები |
| --- | --- | --- |
| ბილდის ჯანმრთელობა: Xcode, Bazel, Cargo, Gradle | ჩანაწერის ჩასმის დრო | მოიცავს დასაწყისს, გამორიცხავს დასასრულს |
| ბილდის ჯანმრთელობა: Once | გაშვების დაწყების დრო | მოიცავს დასაწყისს, გამორიცხავს დასასრულს |
| Xcode ბილდის ხანგრძლივობა | ჩანაწერის ჩასმის დრო | გამორიცხავს დასაწყისსა და დასასრულს |
| ტესტის ხანგრძლივობა | ჩაწერილი გაშვების დრო | მოიცავს დასაწყისსა და დასასრულს |

### დაფის ცვლადები

გამოიყენეთ დაფის ცვლადები პროექტებისა და მხარდაჭერილი ფილტრებისთვის. ტოტისა და სამუშაო დატვირთვის ცვლადები იყენებენ შემდეგ მოთხოვნებს:

| ცვლადი | მოთხოვნა |
| --- | --- |
| ტოტი | `buildBranches account/project` |
| სამუშაო დატვირთვა | `buildWorkloads account/project` |

ფილტრები იღებენ ერთ ზუსტ მნიშვნელობას. ტოტისა და სამუშაო დატვირთვის ცვლადებისთვის, ყველას პარამეტრის მორგებული მნიშვნელობა დააყენეთ `__tuist_all__`-ზე. სხვა ფილტრები იყენებენ ჩაშენებულ ნებისმიერ პარამეტრს ან ცარიელ მნიშვნელობას. მრავალჯერადი შერჩევა და რეგულარული გამოსახულებები არ არის მხარდაჭერილი.

## მორგებული მეტამონაცემების გაგზავნა {#custom-metadata}

Xcode, Bazel, Cargo და Gradle ბილდები იღებენ ამ არჩევით მეტამონაცემთა მნიშვნელობებს:

| გასაღები | დასაშვები მნიშვნელობა |
| --- | --- |
| `tuist.workload` | სამუშაო დატვირთვის სახელი, რომელიც ცვლის ნაგულისხმევ დაჯგუფებას. |
| `tuist.failure_category` | `verification` ან `infrastructure_tooling`. |
| `tuist.cache_work_avoided_ms` | მხოლოდ Gradle. ავტომატურად გაგზავნილი თავიდან აცილებული სამუშაოს შეფასება, მთელ მილიწამებში 365 დღემდე. |
| `tuist.cache_time_saved_ms` | მთელი მილიწამები 0-დან 31,536,000,000-მდე (365 დღე). |

მიეწოდეთ ისინი თქვენი ბილდის ინტეგრაციის მორგებული მეტამონაცემების კონფიგურაციით:

```json
{
  "custom_metadata": {
    "values": {
      "tuist.workload": "Release verification",
      "tuist.failure_category": "verification",
      "tuist.cache_time_saved_ms": "12000"
    }
  }
}
```

კეშის დაზოგვის შესახებ მოახსენეთ მხოლოდ მაშინ, როცა გაქვთ გასული დროის გაზომვა ან დოკუმენტური შეფასება ამ ბილდისთვის. კეშის მოხვედრები და დაგროვებითი ამოცანების ხანგრძლივობა მარტო ვერ განსაზღვრავენ გასულ დაზოგვას, როცა ამოცანები პარალელურად მუშაობენ. გამოტოვებული კეშის დაზოგვა უცნობი რჩება. გამოტოვებული შეცდომის კატეგორიის მეტამონაცემები ეყრდნობა ჩაწერილ მტკიცებულებას, როგორც აღწერილია [ბილდის სისტემებში](#build-systems). მონაცემთა შენახვა უცვლელია.

## გაფრთხილებები და Slack {#alerts-and-slack}

შექმენით Grafana-ს მიერ მართული გაფრთხილების წესი რიცხვითი მეტრიკით. მაგალითად:

| მეტრიკა | იდენტიფიკატორი | მაგალითის პირობა |
| --- | --- | --- |
| ბილდის წარმატების მაჩვენებელი | `success_rate` | 99%-ზე ნაკლები |
| შეცდომიანი ბილდები | `failed_builds` | ნულზე მეტი |
| 90-ე პერცენტილის ხანგრძლივობა | `p90` | თქვენი გუნდის ხანგრძლივობის ლიმიტზე მეტი |

გამოიყენეთ **მთელი პერიოდი** შეფასების ფანჯარაში ერთი მნიშვნელობისთვის, ან შეამცირეთ დროის სერია ერთ მნიშვნელობამდე. ხანგრძლივობის მოთხოვნებისთვის მთელი პერიოდის რეჟიმში, აირჩიეთ ერთი სერია.

- გამოიყენეთ ფიქსირებული პროექტისა და ფილტრის მნიშვნელობები. დაფის ცვლადები მიუწვდომელია ფონური გაფრთხილების შეფასების დროს.
- გაფრთხილებებისთვის გამოიყენეთ რიცხვითი მოთხოვნები. სამუშაო დატვირთვის მონიტორინგისთვის, ფილტრეთ ბილდის ჯანმრთელობის მოთხოვნა იმ სამუშაო დატვირთვაზე.
- დააყენეთ წესის ქცევა მონაცემების არარსებობისას იმ ინტერვალებისთვის, სადაც არ არის ბილდები ან გაგზავნილი კეშის დაზოგვა.

კონფიგურაცია გაუკეთეთ [Slack საკონტაქტო წერტილს](https://grafana.com/docs/grafana/latest/alerting/configure-notifications/manage-contact-points/integrations/configure-slack/) და მიმართეთ წესი მისკენ Grafana-ს შეტყობინებების პოლიტიკის მეშვეობით. Grafana აგზავნის შეტყობინებებს და ინახავს Slack-ის სერთიფიკატებს.

## არსებული დაფების განახლება {#upgrading}

არსებული ხანგრძლივობის პანელები ინარჩუნებენ თავიანთ მოთხოვნებს, ფილტრებს, სერიების სახელებსა და ერთეულებს. შენახული Gradle ჯანმრთელობის პანელები და ცვლადები ასევე განაგრძობენ მუშაობას.

შეიტანეთ სტანდარტული დაფა ცალკე, რათა გამოიყენოთ გაზიარებული ბილდის ჯანმრთელობის მოთხოვნები. არსებული დაფები არ მიგრირდება ავტომატურად. გაზიარებულ მოთხოვნებს სჭირდებათ Tuist სერვერი, რომელიც უზრუნველყოფს ბილდის ჯანმრთელობის ბოლოწერტილებს; არსებული ხანგრძლივობის მოთხოვნები კვლავ მუშაობენ ძველ სერვერებთან.

## მოთხოვნები {#requirements}

- Grafana 10.4 ან უფრო ახალი.
- Tuist ტოკენი ნებართვით, წაიკითხოთ პროექტები და მეტრიკები, რომლებიც გსურთ დახატოთ. იხილეთ [ავტორიზაცია](#authentication) ქვემოთ.

## ავტორიზაცია {#authentication}

გამოიყენეთ <.localized_link href="/guides/server/authentication#account-tokens">ანგარიშის ტოკენი</.localized_link> დაფებისა და ფონური გაფრთხილებების შეფასებისთვის. მიანიჭეთ `project:builds:read` ბილდის მეტრიკებისთვის და `project:tests:read` ტესტების ხანგრძლივობისთვის, და შეზღუდეთ წვდომა იმ პროექტებზე, რომელთა მონაცემთა ვიზუალიზაციაც გსურთ. საჭიროა მხოლოდ იმ სკოპების ნებართვა, რომელთა მეტრიკებსაც იყენებთ. ერთის შესაქმნელად მიჰყევით <.localized_link href="/guides/server/authentication#creating-an-account-token">ტოკენის შექმნის ინსტრუქციებს</.localized_link>.

ინტეგრაცია ასევე იღებს არსებულ პროექტის ტოკენებს მათი საკუთარი პროექტისთვის და <.localized_link href="/guides/server/authentication#as-a-user">მომხმარებლის წვდომის ტოკენებს</.localized_link> მომხმარებლის წაკითხვის ნებართვებით. მომხმარებლის წვდომის ტოკენები მოკლე ვადით მოქმედებს. Grafana ინახავს თქვენს მიერ მოწოდებულ ტოკენს და არ ანახლებს მას ან არ იყენებს ხელახლა თქვენს ადგილობრივ Tuist-ში შესვლას; შეცვალეთ ის, როდესაც ვადა ამოეწურება. ანგარიშის ტოკენები გაძლევთ საშუალებას, დამოუკიდებლად მომხმარებლის შესვლის სესიისგან, მართოთ პროექტზე წვდომა, ნებართვები და ვადის გასვლა.

## კონფიგურაცია {#configuration}

დაამატეთ მონაცემთა წყარო და დააყენეთ:

| ველი | შენახული პარამეტრი | შენიშვნები |
| --- | --- | --- |
| სერვერის URL | `jsonData.url` | ნაგულისხმევად არის `https://tuist.dev`. |
| ტოკენი | `secureJsonData.apiToken` | Tuist bearer ტოკენი, ინახება დაშიფრული. |

აირჩიეთ **შენახვა და ტესტირება** კავშირის შესამოწმებლად. Grafana ჩამოთვლის ხელმისაწვდომ პროექტებს, შემდეგ კი შეამოწმებს ბილდისა და ტესტების წაკითხვის ნებართვებს პირველი პროექტის მიმართ.

## ინსტალაცია {#installation}

### Grafana-ს კატალოგიდან {#from-the-grafana-catalog}

გამოქვეყნების შემდეგ, დააინსტალირეთ ის, როგორც ნებისმიერი სხვა მონაცემთა წყარო **კავშირები → ახალი კავშირის დამატება → Tuist**-დან, ან `grafana-cli plugins install tuist-metrics-datasource`-ით.

### გამოქვეყნებამდე (თვითმასპინძელი Grafana) {#before-it-is-published-self-hosted-grafana}

პლაგინი ხელმოუწერელია, სანამ კატალოგისთვის არ დამტკიცდება. თვითმასპინძელ ინსტანციაზე შეგიძლიათ:

- **დაუშვათ ხელმოუწერლად** — დაამატეთ `tuist-metrics-datasource` `allow_loading_unsigned_plugins`-ში (ან `GF_PLUGINS_ALLOW_LOADING_UNSIGNED_PLUGINS=tuist-metrics-datasource`) და ჩაყარეთ აწყობილი პლაგინი თქვენს პლაგინების დირექტორიაში.
- **პირადად მოაწერეთ ხელი** თქვენი ინსტანციებისთვის — `npm run sign -- --rootUrls https://grafana.example.com` (URL უნდა ემთხვეოდეს ინსტანციის `root_url`-ს), შემდეგ კი გაავრცელეთ zip ფაილი.

[Grafana Cloud მოითხოვს პლაგინებს კატალოგიდან](https://grafana.com/docs/grafana-cloud/learn-and-build/get-started/learn/find-and-use-plugins/) და არ უჭერს მხარს ხელმოუწერელ ან ხელით ატვირთულ პლაგინებს.
