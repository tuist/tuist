# Grafana-სთან ინტეგრაცია {#grafana}

Tuist-ის მონაცემთა წყარო საშუალებას გაძლევთ გამოიყენოთ ბილდების, ტესტების და ქეშის მეტრიკები Grafana-ში, მათ შორის ხანგრძლივობა, შეცდომების რაოდენობა და ქეშირებით მიღებული დროის დაზოგვა. ააწყვეთ დაშბორდები თქვენი გუნდისთვის მნიშვნელოვანი პროექტებისა და მეტრიკების გარშემო, ან გააერთიანეთ Tuist-ის მეტრიკები სხვა მონაცემთა წყაროებთან თქვენი კომპანიის არსებულ დაშბორდებში. გამოიყენეთ Grafana-ს შეტყობინებების წესები და არხები, რათა თქვენმა გუნდმა იცოდეს, როდესაც ბილდები ნელდება ან შეცდომების რაოდენობა იზრდება.

## ხელმისაწვდომი მეტრიკები {#metric-definitions}

ცხრილებში ჩამოთვლილია წასაკითხი სახელები და მათი მოთხოვნის იდენტიფიკატორები. ბილდის ჯანმრთელობის მოთხოვნები იყენებენ იდენტიფიკატორს `metric` ველში; ბილდისა და ტესტის ხანგრძლივობის მოთხოვნები ირჩევენ `average`, `p50`, `p90` ან `p99`-ს `series` ველში.

### ბილდების რაოდენობა და საიმედოობა

| მეტრიკა | იდენტიფიკატორი | რა ზომავს |
| --- | --- | --- |
| ბილდების რაოდენობა | `builds` | ჩაწერილი ბილდების რაოდენობა. |
| წარმატებული ბილდები | `successful_builds` | ბილდები, რომლებიც წარმატებით დასრულდა. |
| შეცდომით დასრულებული ბილდები | `failed_builds` | ბილდები, რომლებიც შეცდომით დასრულდა. |
| გაუქმებული ბილდები | `cancelled_builds` | ბილდები, რომლებიც ჩაიწერა როგორც გაუქმებული. იხილეთ [განსხვავებები ბილდის სისტემებს შორის](#build-systems). |
| ბილდის წარმატების მაჩვენებელი | `success_rate` | წარმატებული ÷ (წარმატებული + შეცდომით დასრულებული), პროცენტულად. |
| შეცდომით ან ნელა შესრულებული ბილდები | `builds_needing_attention` | შეცდომით ან ნელა შესრულებული ბილდები, თითოეული ბილდი ერთხელ ითვლება. |

### ბილდისა და ტესტის ხანგრძლივობა

| მეტრიკა | იდენტიფიკატორი | რა ზომავს |
| --- | --- | --- |
| საშუალო ხანგრძლივობა | `average` | შერჩეული გაშვებების საშუალო ხანგრძლივობა. |
| მედიანური ხანგრძლივობა | `p50` | გაშვებების ხანგრძლივობის 50-ე პერცენტილი. |
| 90-ე პერცენტილის ხანგრძლივობა | `p90` | ხანგრძლივობა, რომლის ქვემოთ ან ტოლია გაშვებების 90%. |
| 99-ე პერცენტილის ხანგრძლივობა | `p99` | ხანგრძლივობა, რომლის ქვემოთ ან ტოლია გაშვებების 99%. |
| ნელი ბილდის ზღვარი | `slow_build_threshold` | 90-ე პერცენტილის ხანგრძლივობა, ან თქვენი ფიქსირებული ლიმიტი მილიწამებში. |

ტესტის ხანგრძლივობის მეტრიკები იყენებენ Tuist-ში ჩაწერილ ტესტის გაშვებებს. ნელი ბილდის ზღვარი ვრცელდება მხოლოდ ბილდებზე: ბილდი ნელია, როდესაც მისი ხანგრძლივობა აღემატება ამ ზღვარს. გაუქმებული ბილდები ითვლება ცალკე და არ შედის ბილდის წარმატების მაჩვენებელში.

### ქეშის დაზოგვა

| მეტრიკა | იდენტიფიკატორი | რა ზომავს |
| --- | --- | --- |
| ჯამური დავალების დროის დაზოგვა (Gradle) | `cache_work_avoided` | ქეშში მოხვედრის შედეგად თავიდან აცილებული დავალების შესრულების სავარაუდო დროის ჯამი. |
| ბილდები, რომლებიც იუწყებიან ჯამურ დავალების დროს | `cache_work_avoided_samples` | ბილდები სრული შეფასებით. |
| მოხსენებული ქეშის დროის დაზოგვა | `cache_time_saved` | მოხსენებული გასული დროის დაზოგვის ჯამი. |
| ბილდები, რომლებიც იუწყებიან ქეშის დროის დაზოგვას | `cache_time_saved_samples` | ბილდები ვალიდური დაზოგვის მნიშვნელობით. |

Gradle პლაგინი ავტომატურად იუწყება სავარაუდოდ თავიდან აცილებულ სამუშაოს ლოკალური და დისტანციური დავალების ქეშში მოხვედრისთვის. თითოეული ქეშირებული დავალებისთვის, ის აკლებს დავალების აღდგენის ხანგრძლივობას Gradle-ის მიერ შენახულ საწყის შესრულების დროს, ნულის მინიმუმით. ბილდის შეფასება კრებს ამ მნიშვნელობებს ერთად. პარალელურმა დავალებებმა შეიძლება გადაფარონ ერთმანეთი, ამიტომ ეს არის ჯამური დავალების დრო, არა დაზოგილი ბილდის გასული დრო. აქტუალური და გამოტოვებული დავალებები გამორიცხულია.

ბილდი დავალების ქეშში მოხვედრის გარეშე იუწყება ნულს. თუ რაიმე ქეშირებულ დავალებას აკლია საწყისი ტაიმინგი, ტელემეტრია არასრულია, ან მორგებული მეტამონაცემების რუკას არ აქვს ადგილი, პლაგინი ტოვებს შეფასებას. პლაგინის ძველი ვერსიები და სხვა ბილდის სისტემები არ იუწყებიან მას. შეადარეთ მოხსენების რაოდენობა ბილდების საერთო რაოდენობას დაფარვის შესამოწმებლად.

მოხსენებული გასული დროის დაზოგვა მოდის `tuist.cache_time_saved_ms` მეტამონაცემებიდან. ეს მეტრიკა რჩება ცალკე ავტომატური შეფასებისგან.

ქეშის დაზოგვას არ აქვს მნიშვნელობა, როდესაც არცერთი ბილდი არ იუწყება მას. Once ამჟამად არ იწერს ამ გაზომვას. ქეშში მოხვედრისა და გამოტოვების მაჩვენებლები არ არის ხელმისაწვდომი ამ მონაცემთა წყაროს მეშვეობით.

### ცხრილები

ეს იდენტიფიკატორები არის მოთხოვნის `queryType` ველის მნიშვნელობები.

| ცხრილი | მოთხოვნის ტიპი | შემცველობა |
| --- | --- | --- |
| ჯანმრთელობა დატვირთვით | `buildWorkloads` | ბილდების რაოდენობა, წარმატების მაჩვენებელი, მედიანური და 90-ე პერცენტილის ხანგრძლივობა. |
| შეცდომების კატეგორიები | `buildFailureReasons` | ყველა შეცდომა და რაოდენობა შეცდომის კატეგორიის მიხედვით. |
| ბოლოდროინდელი შეცდომით დასრულებული ბილდები | `buildRecentFailures` | ბოლო 100 შეცდომა, Tuist-ზე ბმულებით. |

ბოლოდროინდელი შეცდომები მოიცავს დაწყების დროს, ხანგრძლივობას, მომხმარებელს, შტოს და მოთხოვნილ დავალებებს. შეცდომების კატეგორიებია `verification`, `infrastructure_tooling` და `unknown`.

დატვირთვის შეჯამებები და შტო/დატვირთვის მნიშვნელობების სიები აბრუნებენ 1000-მდე მნიშვნელობას. ბილდის ჯანმრთელობის ცვლადის მოთხოვნები იყენებენ ბოლო 90 დღეს; legacy Gradle ცვლადის მოთხოვნები ინარჩუნებენ არსებულ ისტორიის ფანჯარას. Bazel აჩვენებს ბილდის მომხმარებელს, რომელიც მოხსენებულია ინსტრუმენტის მიერ. სხვა ინტეგრაციები აჩვენებენ ანგარიშს, რომელიც დაკავშირებულია მომხსენებელ სერთიფიკატთან. ისტორიული Bazel და Once გაშვებები, და Once გაშვებები, რომლებიც მოხსენებულია პროექტის სერთიფიკატებით, ჩნდება როგორც უცნობი, როდესაც მომხმარებელი არ ჩაწერილა.

გამოიყენეთ შეცდომის კატეგორიის ფილტრი ბილდის გაშვებებზე შესაბამისი შეცდომების საპოვნელად. კატეგორია ჩნდება ბილდის დეტალებში, ინფორმაციის მინიშნებით, რომელიც ხსნის მის მნიშვნელობას; ნაგულისხმევი მიმოხილვისა და ბილდის გაშვებების ცხრილები ინარჩუნებენ არსებულ სვეტებს. წარმატებულ, გაუქმებულ და დაუსრულებელ ბილდებს არ აქვთ შეცდომის კატეგორია. Gradle-ის ქეშის ანალიტიკის ბარათი და ბილდის დეტალები აჩვენებენ ჯამურ დავალების დროის დაზოგვას; tooltip ხსნის შეფასებას და პარალელური დავალებების ეფექტს. ქეშის ვიჯეტი ადარებს შერჩეულ დიაპაზონს უშუალოდ წინამდებარე თანაბრძენ პერიოდს იგივე ფილტრების გამოყენებით. შედარებები ნეიტრალურია: უფრო დიდი ჯამი შეიძლება ასახავდეს მეტ ბილდს. წინა შეფასებების არარსებობა არ აჩვენებს შედარებას; ჩაწერილი ნულოვანი საბაზისო მაჩვენებელი აჩვენებს აბსოლუტურ ზრდას პროცენტის ნაცვლად.

## სტანდარტული დაფა {#what-you-can-query}

შემოიტანეთ [ბილდის ჯანმრთელობის დაფა](https://github.com/tuist/tuist/blob/main/grafana-datasource/src/dashboards/build-health.json), შემდეგ აირჩიეთ თქვენი მონაცემთა წყარო და პროექტი. ის მოიცავს ბილდების რაოდენობას, წარმატების მაჩვენებელს, მედიანურ და 90-ე პერცენტილის ხანგრძლივობებს, ნელი ბილდის ზღვარს, ნეიტრალურ შეცდომით ან ნელა შესრულებული ბილდების რაოდენობას, დაჯგუფებულ ქეშის დაზოგვასა და მოხსენების დაფარვას, და სამ შეცდომისა და დატვირთვის ცხრილს. დაამატეთ პანელები სხვა ხელმისაწვდომი მეტრიკებისთვის საჭიროებისამებრ. ავტომატური ნელი ზღვარი არის შერჩეული პერიოდის საკუთარი 90-ე პერცენტილი; მასზე მაღალი ბილდები არ მიუთითებს აუცილებლად რეგრესიაზე. დააყენეთ ფიქსირებული ზღვარი ხანგრძლივობის სამიზნე გაფრთხილებებისთვის. ქეშის პანელები პრიორიტეტს ანიჭებენ Gradle-ის ავტომატურ ჯამურ დავალების დროის შეფასებას მისი დაფარვის გვერდით, რასაც მოსდევს აშკარად მოხსენებული გასული დროის დაზოგვა მათი საკუთარი დაფარვის გვერდით.

## ბილდის სისტემები {#build-systems}

ბილდის ჯანმრთელობის მოთხოვნები და სტანდარტული დაფა მხარს უჭერს Bazel-ს, Cargo-ს, Once-ს, Gradle-ს და Xcode-ს. Tuist ირჩევს ბილდის სისტემას თქვენი პროექტიდან. შერეული პროექტები ამჟამად არ არის მხარდაჭერილი ბილდის ჯანმრთელობის მოთხოვნების ან სტანდარტული დაფის მიერ.

| ბილდის სისტემა | დატვირთვა | გაუქმების მოხსენება | ქეშის დაზოგვა |
| --- | --- | --- | --- |
| Bazel | ბრძანება | გასვლის კოდი 8, `run`-ის გარდა | მოითხოვს მორგებულ მეტამონაცემებს |
| Cargo | ბრძანება | არ განირჩევა; რაოდენობა ნულია | გავლილი დროის დაზოგვა მოითხოვს მორგებულ მეტამონაცემებს; კომპილატორის თავიდან არიდებული სამუშაო არ არის გავლილი დროის დაზოგვა |
| Once | ბრძანების ტიპი | ჩაწერილი გაუქმების მიზეზი | არ არის ჩაწერილი |
| Gradle | ამოცანების ჯგუფი | მოხსენებული გაუქმებები | თავიდან არიდებული სამუშაოს ავტომატური შეფასება; გავლილი დროის დაზოგვა მოითხოვს მორგებულ მეტამონაცემებს |
| Xcode | სქემა | არ განირჩევა; რაოდენობა ნულია | მოითხოვს მორგებულ მეტამონაცემებს |

დამუშავების ჩანაწერები და დაუსრულებელი გაშვებები გამორიცხულია. Bazel მოიცავს ბილდის, ტესტის, გაშვების და დაფარვის ბრძანებებს. Once მოიცავს დასრულებულ ბილდებს, ტესტებს და ზოგად გაშვებებს. Cargo მოიცავს ისეთ ბილდის ბრძანებებს, როგორიცაა `build`, `check` და `test-build`; ტესტების შესრულების ძველი მოხსენებები გამორიცხულია ბილდის ჯანმრთელობიდან. Cargo-ს ბოლოდროინდელი შეცდომები იყენებენ ჩაწერილ დაწყების დროს, თუ ის ხელმისაწვდომია, წინააღმდეგ შემთხვევაში გადადიან ჩასმის დროზე; არარსებული ხანგრძლივობები რჩება მიუწვდომლად და არა ნულად.

Gradle ამოცანებს აჯგუფებს ინსტრუმენტული ტესტების, ერთეულოვანი ტესტების, lint/checks-ის, assemble/package-ის ან სხვა კატეგორიებში, პრიორიტეტის ამ თანმიმდევრობით. თითოეული ბილდი ეკუთვნის ერთ დატვირთვას. მორგებული მეტამონაცემებით შესაძლებელია დატვირთვების გადაფარვა Xcode-ის, Bazel-ის, Cargo-სა და Gradle-ისთვის.

### შეცდომების კატეგორიები

| კატეგორია | მნიშვნელობა | ჩაწერილი მტკიცებულება |
| --- | --- | --- |
| `verification` | კოდის კომპილაციის, დაკავშირების, ტესტების ან შემოწმებების შეცდომა. | Gradle-ის ვერიფიკაციის ან კომპილაციის გამონაკლისები და ცნობილი შეცდომიანი ამოცანის ტიპები; Xcode-ის კომპილატორის და ლინკერის პრობლემები; Bazel-ის სტრუქტურირებული არანულოვანი კომპილატორის/ტესტის ქმედების შედეგები; Cargo-ს ჩაწერილი შეცდომიანი rustc კომპილაციები; Once-ის ტესტის შეცდომები ან ქმედებები, რომლებიც აშკარად არის გამოცხადებული როგორც კომპილაცია, დაკავშირება, ტესტი, lint ან შემოწმება. |
| `infrastructure_tooling` | ბილდი ვერ შესრულდა ჩვეულებრივად, რადგან მისმა ინსტრუმენტებმა, დამოკიდებულებებმა ან გარემომ ვერ იმუშავა. | Gradle-ის კონფიგურაციის, დამოკიდებულებების ამოხსნის, შეყვანა/გამოტანის ან მეხსიერების შეცდომები; Bazel-ის სტრუქტურირებული ინფრასტრუქტურის შეცდომები და [დოკუმენტირებული გასვლის კოდები](https://bazel.build/run/scripts); Once-ის ინფრასტრუქტურის ქმედების შეცდომები. |
| `unknown` | მოხსენება არ შეიცავს საკმარის მტკიცებულებას შეცდომის კლასიფიცირებისთვის. | ნებისმიერი ბრძანებები, არარსებული დიაგნოსტიკა და ძველი მოხსენებები სტრუქტურირებული მტკიცებულებების გარეშე. |

Gradle-ის კონფიგურაციის ფაზის შეცდომები, მათ შორის შეცდომები ბილდის სკრიპტებში, დაჯგუფებულია ინფრასტრუქტურის/ინსტრუმენტების ქვეშ, რადგან ამოცანის შესრულება ვერ გაგრძელდა.

Cargo-ს შეცდომები აშკარა კატეგორიის მეტამონაცემების ან ჩაწერილი შეცდომიანი rustc კომპილაციის გარეშე რჩება `unknown`; მხოლოდ შეცდომიანი `check` ან `test-build` ბრძანება არ ადგენს ვერიფიკაციის შეცდომას. Cargo-ს ამოცანის ხელახლა გამოყენების მრიცხველები და კომპილატორის თავიდან არიდებული სამუშაოს შეფასება არასდროს იძლევა არც გავლილი დროის ქეშის დაზოგვას და არც Gradle-ის დაგროვებითი ამოცანის დროის მეტრიკას.

აშკარა `tuist.failure_category` მეტამონაცემები გადაფარავს ავტომატურ კლასიფიკაციას. წინააღმდეგ შემთხვევაში, ინფრასტრუქტურის მტკიცებულებას აქვს უპირატესობა ვერიფიკაციაზე, როდესაც ორივე გვხვდება ბილდში. შეცდომიანი ნებისმიერი სკრიპტი არ ითვლება კომპილატორის ან ტესტის შეცდომად. ისტორიულ მოხსენებებს შეუძლიათ გამოიყენონ Tuist-ის მიერ უკვე შენახული მტკიცებულებები, მაგრამ ახალი მომხსენებლის ველები არ ავსებენ არარსებულ ინფორმაციას. ავტომატური მომხსენებლის მეტამონაცემები იყენებს ხელმისაწვდომ ადგილს არსებული 20-ჩანაწერიანი მორგებული მეტამონაცემების ლიმიტის ფარგლებში.

`buildFailureReasons` პასუხი ინარჩუნებს თავის `all` სტრიქონს თავსებადობისთვის. სტანდარტული დაფა ფილტრავს ამ ჯამს შეცდომების კატეგორიების დიაგრამიდან და ცალკე აჩვენებს ჯამურ შეცდომებს. ძველი `gradleFailureReasons` მოთხოვნა ინარჩუნებს თავის საწყის სამ კატეგორიულ სტრიქონს.

| ბილდის ტიპი | `category` | Xcode ბილდის ხანგრძლივობა |

გარემოს მნიშვნელობებია `any`, `ci` (ავტომატური ბილდები) და `local`. სტატუსის მნიშვნელობებია `success`, `failure` და, ბილდის ჯანმრთელობის მოთხოვნებისთვის, `cancelled`; გამოტოვეთ მნიშვნელობა ყველა სტატუსის ჩასართავად. ბილდის ტიპის მნიშვნელობებია `clean` და `incremental`; გამოტოვეთ მნიშვნელობა ორივეს ჩასართავად.

ცარიელ ბილდის ჯანმრთელობის ინტერვალებს აქვთ ნულოვანი რაოდენობა და არ აქვთ საშუალო ხანგრძლივობა, ხანგრძლივობის პერცენტილი ან წარმატების მაჩვენებლის მნიშვნელობა. ნელი ბილდის ზღვარი კვლავ იყენებს სრულად შერჩეულ დიაპაზონს. ცალკეული ტესტის ხანგრძლივობის მოთხოვნა აბრუნებს ნულს ცარიელი დროის სერიის ინტერვალებისთვის. მთლიანი პერიოდის პერცენტილები გამოითვლება გაშვებებიდან, არა ინტერვალის პერცენტილებიდან. ბილდის ჯანმრთელობის პერცენტილები იყენებენ ზუსტ აგრეგაციას; ცალკეული Xcode-ისა და ტესტის ხანგრძლივობის მოთხოვნები იყენებენ მიახლოებით პერცენტილებს.

ბილდის ჯანმრთელობის დროის სერიები ათავსებენ ნაწილობრივ პირველ ბაკეტს შერჩეული დიაპაზონის დასაწყისში, რათა ის ხილული დარჩეს. ძველი Gradle-ის მოთხოვნები ინარჩუნებენ თავიანთ საწყის ბაკეტის დროის შტამპებს.

ყველა მოთხოვნა იღებს თარიღის დიაპაზონებს 366 დღემდე. მათი საზღვრები და დროის შტამპები განსხვავდება:

| მოთხოვნა | გამოყენებული დროის შტამპი | დიაპაზონის საზღვრები |
| --- | --- | --- |
| ბილდის ჯანმრთელობა: Xcode, Bazel, Cargo, Gradle | ჩანაწერის ჩასმის დრო | მოიცავს დასაწყისს, გამორიცხავს დასასრულს |
| ბილდის ჯანმრთელობა: Once | გაშვების დაწყების დრო | მოიცავს დასაწყისს, გამორიცხავს დასასრულს |
| Xcode ბილდის ხანგრძლივობა | ჩანაწერის ჩასმის დრო | გამორიცხავს დასაწყისსა და დასასრულს |
| ტესტის ხანგრძლივობა | ჩაწერილი გაშვების დრო | მოიცავს დასაწყისსა და დასასრულს |

### დაფის ცვლადები

გამოიყენეთ დაფის ცვლადები პროექტებისა და მხარდაჭერილი ფილტრებისთვის. განშტოებისა და სამუშაო დატვირთვის ცვლადები იყენებენ შემდეგ მოთხოვნებს:

| ცვლადი | მოთხოვნა |
| --- | --- |
| განშტოება | `buildBranches account/project` |
| სამუშაო დატვირთვა | `buildWorkloads account/project` |

ფილტრები იღებენ ერთ ზუსტ მნიშვნელობას. განშტოებისა და სამუშაო დატვირთვის ცვლადებისთვის, დააყენეთ „ყველა“ პარამეტრის მორგებული მნიშვნელობა `__tuist_all__`-ზე. სხვა ფილტრები იყენებენ ჩაშენებულ „ნებისმიერ“ პარამეტრს ან ცარიელ მნიშვნელობას. მრავალჯერადი შერჩევა და რეგულარული გამოსახულებები არ არის მხარდაჭერილი.

## მორგებული მეტამონაცემების შეტყობინება {#custom-metadata}

Xcode, Bazel, Cargo და Gradle ბილდები იღებენ ამ არასავალდებულო მეტამონაცემთა მნიშვნელობებს:

| გასაღები | მიღებული მნიშვნელობა |
| --- | --- |
| `tuist.workload` | სამუშაო დატვირთვის სახელი, რომელიც ცვლის ნაგულისხმევ დაჯგუფებას. |
| `tuist.failure_category` | `verification` ან `infrastructure_tooling`. |
| `tuist.cache_work_avoided_ms` | მხოლოდ Gradle. ავტომატურად შეტყობინებული თავიდან აცილებული სამუშაოს შეფასება, მთელ მილიწამებში 365 დღემდე. |
| `tuist.cache_time_saved_ms` | მთელი მილიწამები 0-დან 31,536,000,000-მდე (365 დღე). |

მიეწოდეთ ისინი თქვენი ბილდის ინტეგრაციის მორგებული მეტამონაცემების კონფიგურაციის მეშვეობით:

```json
{
  "custom_metadata": {
    "values": {
      "tuist.workload": "Release verification",
      "tuist.failure_category": "verification",
      "tuist.cache_time_saved_ms": "12000"
    }
  }
}
```

შეატყობინეთ ქეშის ეკონომია მხოლოდ მაშინ, როცა გაქვთ გასული დროის გაზომვა ან დოკუმენტური შეფასება იმ ბილდისთვის. ქეშის მოხვედრები და დაგროვებითი ამოცანების ხანგრძლივობა ერთად ვერ განსაზღვრავენ გასულ ეკონომიას, როცა ამოცანები პარალელურად მუშაობენ. დაკარგული ქეშის ეკონომია უცნობი რჩება. დაკარგული წარუმატებლობის კატეგორიის მეტამონაცემები გადადის ჩაწერილ მტკიცებულებაზე, როგორც აღწერილია [ბილდის სისტემებში](#build-systems). მონაცემთა შენახვა უცვლელია.

## გაფრთხილებები და Slack {#alerts-and-slack}

შექმენით Grafana-ს მიერ მართული გაფრთხილების წესი რიცხვითი მეტრიკით. მაგალითად:

| მეტრიკა | იდენტიფიკატორი | მაგალითის პირობა |
| --- | --- | --- |
| ბილდის წარმატების მაჩვენებელი | `success_rate` | 99%-ზე ნაკლები |
| წარუმატებელი ბილდები | `failed_builds` | ნულზე მეტი |
| 90-ე პროცენტილის ხანგრძლივობა | `p90` | თქვენი გუნდის ხანგრძლივობის ლიმიტზე მეტი |

გამოიყენეთ **მთელი პერიოდი** ერთი მნიშვნელობისთვის შეფასების ფანჯარაში, ან შეამცირეთ დროის სერია ერთ მნიშვნელობამდე. ხანგრძლივობის მოთხოვნებისთვის „მთელი პერიოდის“ რეჟიმში, აირჩიეთ ერთი სერია.

- გამოიყენეთ ფიქსირებული პროექტისა და ფილტრის მნიშვნელობები. დაფის ცვლადები ხელმიუწვდომელია ფონური გაფრთხილებების შეფასების დროს.
- გაფრთხილებებისთვის გამოიყენეთ რიცხვითი მოთხოვნები. სამუშაო დატვირვის მონიტორინგისთვის, გაფილტრეთ ბილდის ჯანმრთელობის მოთხოვნა იმ სამუშაო დატვირთვაზე.
- დააყენეთ წესის „მონაცემების არარსებობის“ ქცევა ინტერვალებისთვის, სადაც არ არის ბილდები ან შეტყობინებული ქეშის ეკონომია.

კონფიგურაცია გაუკეთეთ [Slack საკონტაქტო წერტილს](https://grafana.com/docs/grafana/latest/alerting/configure-notifications/manage-contact-points/integrations/configure-slack/) და მიმართეთ წესი მასთან Grafana-ს შეტყობინებების პოლიტიკის მეშვეობით. Grafana აგზავნის შეტყობინებებს და ინახავს Slack-ის სერთიფიკატებს.

## არსებული დაფების განახლება {#upgrading}

არსებული ხანგრძლივობის პანელები ინარჩუნებენ თავიანთ მოთხოვნებს, ფილტრებს, სერიების სახელებსა და ერთეულებს. შენახული Gradle ჯანმრთელობის პანელები და ცვლადები ასევე აგრძელებენ მუშაობას.

სტანდარტული დაფა ცალკე შემოიტანეთ საერთო ბილდის ჯანმრთელობის მოთხოვნების გამოსაყენებლად. არსებული დაფები ავტომატურად არ მიგრირდება. საერთო მოთხოვნებს სჭირდებათ Tuist სერვერი, რომელიც უზრუნველყოფს ბილდის ჯანმრთელობის ბოლოწერტილებს; არსებული ხანგრძლივობის მოთხოვნები კვლავ მუშაობენ ძველ სერვერებთან.

## მოთხოვნები {#requirements}

- Grafana 10.4 ან უფრო ახალი.
- Tuist ტოკენი, რომელსაც აქვს ნებართვა წაიკითხოს პროექტები და მეტრიკები, რომელთა გრაფიკულად გამოსახვაც გსურთ. იხილეთ [ავტორიზაცია](#authentication) ქვემოთ.

## ავტორიზაცია {#authentication}

დაფებისა და ფონური გაფრთხილებების შეფასებისთვის გამოიყენეთ <.localized_link href="/guides/server/authentication#account-tokens">ანგარიშის ტოკენი</.localized_link>. მიანიჭეთ `project:builds:read` ბილდის მეტრიკებისთვის და `project:tests:read` ტესტების ხანგრძლივობისთვის, და შეზღუდეთ წვდომა იმ პროექტებზე, რომელთა გრაფიკულად გამოსახვაც გსურთ. საჭიროა მხოლოდ იმ სკოპების მინიჭება, რომელთა მეტრიკებსაც იყენებთ. ერთ-ერთის შესაქმნელად მიჰყევით <.localized_link href="/guides/server/authentication#creating-an-account-token">ტოკენის შექმნის ინსტრუქციას</.localized_link>.

ინტეგრაცია ასევე იღებს არსებულ პროექტის ტოკენებს მათივე პროექტისთვის და <.localized_link href="/guides/server/authentication#as-a-user">მომხმარებლის წვდომის ტოკენებს</.localized_link> მომხმარებლის წაკითხვის ნებართვებით. მომხმარებლის წვდომის ტოკენები მოკლევადიანია. Grafana ინახავს თქვენს მიერ მოწოდებულ ტოკენს და არ ანახლებს მას ან არ იყენებს ხელახლა თქვენს ადგილობრივ Tuist შესვლას; შეცვალეთ ის ვადის ამოწურვისას. ანგარიშის ტოკენები საშუალებას გაძლევთ დამოუკიდებლად მართოთ პროექტზე წვდომა, ნებართვები და ვადა მომხმარებლის შესვლის სესიისგან.

## კონფიგურაცია {#configuration}

დაამატეთ მონაცემთა წყარო და დააყენეთ:

| ველი | შენახული პარამეტრი | შენიშვნები |
| --- | --- | --- |
| სერვერის URL | `jsonData.url` | ნაგულისხმევად არის `https://tuist.dev`. |
| ტოკენი | `secureJsonData.apiToken` | Tuist bearer ტოკენი, შენახულია დაშიფრული. |

აირჩიეთ **Save & test** კავშირის შესამოწმებლად. Grafana ჩამოთვლის ხელმისაწვდომ პროექტებს, შემდეგ კი შეამოწმებს ბილდისა და ტესტების წაკითხვის ნებართვებს პირველი პროექტის მიმართ.

## ინსტალაცია {#installation}

### Grafana-ს კატალოგიდან {#from-the-grafana-catalog}

გამოქვეყნების შემდეგ, დააინსტალირეთ ის ნებისმიერი სხვა მონაცემთა წყაროს მსგავსად **Connections → Add new connection → Tuist**-დან, ან `grafana-cli plugins install tuist-metrics-datasource`-ით.

### გამოქვეყნებამდე (თვითმასპინძელი Grafana) {#before-it-is-published-self-hosted-grafana}

პლაგინი ხელმოუწერელია, სანამ კატალოგისთვის არ დამტკიცდება. თვითმასპინძელ ინსტანციაზე შეგიძლიათ:

- **დაუშვათ ხელმოუწერლად** — დაამატეთ `tuist-metrics-datasource` `allow_loading_unsigned_plugins`-ში (ან `GF_PLUGINS_ALLOW_LOADING_UNSIGNED_PLUGINS=tuist-metrics-datasource`) და ჩააგდეთ აწყობილი პლაგინი თქვენს პლაგინების დირექტორიაში.
- **პირადად მოაწერეთ ხელი** თქვენი ინსტანციებისთვის — `npm run sign -- --rootUrls https://grafana.example.com` (URL უნდა ემთხვეოდეს ინსტანციის `root_url`-ს), შემდეგ კი გაავრცელეთ zip.

[Grafana Cloud მოითხოვს პლაგინებს კატალოგიდან](https://grafana.com/docs/grafana-cloud/learn-and-build/get-started/learn/find-and-use-plugins/) და არ უჭერს მხარს ხელმოუწერელ ან ხელით ატვირთულ პლაგინებს.
