# Grafana-ის ინტეგრაცია {#grafana}

Tuist-ის მონაცემთა წყარო საშუალებას გაძლევთ გამოიყენოთ ბილდის, ტესტირებისა და ქეშირების მეტრიკები Grafana-ში, მათ შორის ხანგრძლივობები, შეცდომების რაოდენობა და ქეშირებით მიღებული დროის დაზოგვა. ააწყვეთ დაშბორდები თქვენი გუნდისთვის მნიშვნელოვანი პროექტებისა და მეტრიკების გარშემო, ან გააერთიანეთ Tuist-ის მეტრიკები სხვა მონაცემთა წყაროებთან თქვენი კომპანიის არსებულ დაშბორდებში. გამოიყენეთ Grafana-ის გაფრთხილების წესები და შეტყობინების არხები, რათა შეატყობინოთ თქვენს გუნდს, როდესაც ბილდები ნელდება ან შეცდომების რაოდენობა იზრდება.

## ხელმისაწვდომი მეტრიკები {#metric-definitions}

ცხრილებში ჩამოთვლილია წაკითხვადი სახელები და მათი მოთხოვნის იდენტიფიკატორები. ბილდის ჯანმრთელობის მოთხოვნები იყენებენ იდენტიფიკატორს `metric` ველში; ბილდისა და ტესტის ხანგრძლივობის მოთხოვნები ირჩევენ `average`, `p50`, `p90` ან `p99`-ს `series` ველში.

### ბილდების რაოდენობა და სანდოობა

| მეტრიკა | იდენტიფიკატორი | რას ზომავს |
| --- | --- | --- |
| ბილდების რაოდენობა | `builds` | ჩაწერილი ბილდების რაოდენობა. |
| წარმატებული ბილდები | `successful_builds` | ბილდები, რომლებიც წარმატებით დასრულდა. |
| შეცდომიანი ბილდები | `failed_builds` | ბილდები, რომლებიც ვერ შესრულდა. |
| გაუქმებული ბილდები | `cancelled_builds` | ბილდები, რომლებიც ჩაიწერა როგორც გაუქმებული. იხილეთ [განსხვავებები ბილდის სისტემებს შორის](#build-systems). |
| ბილდის წარმატების მაჩვენებელი | `success_rate` | წარმატებული ÷ (წარმატებული + შეცდომიანი), პროცენტულად. |
| შეცდომიანი ან ნელი ბილდები | `builds_needing_attention` | შეცდომიანი ან ნელი ბილდები, დათვლილი ერთხელ თითოეული ბილდისთვის. |

### ბილდისა და ტესტის ხანგრძლივობები

| მეტრიკა | იდენტიფიკატორი | რას ზომავს |
| --- | --- | --- |
| საშუალო ხანგრძლივობა | `average` | შერჩეული გაშვებების საშუალო ხანგრძლივობა. |
| მედიანური ხანგრძლივობა | `p50` | გაშვებების ხანგრძლივობის 50-ე პერცენტილი. |
| 90-ე პერცენტილის ხანგრძლივობა | `p90` | ხანგრძლივობა, რომლის ქვემოთაც ან ტოლია გაშვებების 90%. |
| 99-ე პერცენტილის ხანგრძლივობა | `p99` | ხანგრძლივობა, რომლის ქვემოთაც ან ტოლია გაშვებების 99%. |
| ნელი ბილდის ზღვარი | `slow_build_threshold` | 90-ე პერცენტილის ხანგრძლივობა, ან თქვენი ფიქსირებული ლიმიტი მილიწამებში. |

ტესტის ხანგრძლივობის მეტრიკები იყენებენ Tuist-ში ჩაწერილ ტესტის გაშვებებს. ნელი ბილდის ზღვარი ვრცელდება მხოლოდ ბილდებზე: ბილდი ნელია, როდესაც მისი ხანგრძლივობა აღემატება ამ ზღვარს. გაუქმებული ბილდები ითვლება ცალკე და არ შედის ბილდის წარმატების მაჩვენებელში.

### ქეშირებით მიღებული დაზოგვა

| მეტრიკა | იდენტიფიკატორი | რას ზომავს |
| --- | --- | --- |
| ჯამური დროის დაზოგვა ამოცანებზე (Gradle) | `cache_work_avoided` | ქეშში მოხვედრით თავიდან აცილებული ამოცანის შესრულების სავარაუდო დროის ჯამი. |
| ბილდები, რომლებიც იტყობინებიან ჯამურ დროს ამოცანებზე | `cache_work_avoided_samples` | ბილდები სრული შეფასებით. |
| შეტყობინებული ქეშის დროის დაზოგვა | `cache_time_saved` | შეტყობინებული გასული დროის დაზოგვის ჯამი. |
| ბილდები, რომლებიც იტყობინებიან ქეშის დროის დაზოგვას | `cache_time_saved_samples` | ბილდები ვალიდური დაზოგვის მნიშვნელობით. |

Gradle-ის პლაგინი ავტომატურად იტყობინება სავარაუდოდ თავიდან აცილებულ სამუშაოს ლოკალური და დისტანციური ამოცანების ქეშში მოხვედრისთვის. თითოეული ქეშირებული ამოცანისთვის ის აკლებს ამოცანის აღდგენის ხანგრძლივობას Gradle-ის მიერ შენახულ საწყის შესრულების დროს, მინიმუმ ნულით. ბილდის შეფასება კრებს ამ მნიშვნელობებს ერთად. პარალელურმა ამოცანებმა შეიძლება გადაიფაროს ერთმანეთი, ამიტომ ეს არის ჯამური ამოცანის დრო, არა გასული ბილდის დროის დაზოგვა. განახლებული და გამოტოვებული ამოცანები გამორიცხულია.

ბილდი ამოცანის ქეშში მოხვედრის გარეშე იტყობინება ნულს. თუ რაიმე ქეშირებულ ამოცანას აკლია საწყისი ტაიმინგი, ტელემეტრია არასრულია, ან მორგებული მეტამონაცემების რუკას არ აქვს ადგილი, პლაგინი ტოვებს შეფასებას. პლაგინის უფრო ძველი ვერსიები და სხვა ბილდის სისტემები არ იტყობინებენ მას. შეადარეთ შეტყობინებების რაოდენობა ბილდების საერთო რაოდენობას ფარვის შესამოწმებლად.

შეტყობინებული გასული დროის დაზოგვა მოდის `tuist.cache_time_saved_ms` მეტამონაცემებიდან. ეს მეტრიკა რჩება ცალკე ავტომატური შეფასებისგან.

ქეშის დაზოგვას არ აქვს მნიშვნელობა, როდესაც არცერთი ბილდი არ იტყობინება მას. Struo ამჟამად არ იწერს ამ გაზომვას. ქეშში მოხვედრისა და გამოტოვების მაჩვენებლები არ არის ხელმისაწვდომი ამ მონაცემთა წყაროს მეშვეობით.

### ცხრილები

ეს იდენტიფიკატორები არის მოთხოვნის `queryType` ველის მნიშვნელობები.

| ცხრილი | მოთხოვნის ტიპი | შემცველობა |
| --- | --- | --- |
| ჯანმრთელობა დატვირთვით | `buildWorkloads` | ბილდების რაოდენობა, წარმატების მაჩვენებელი, მედიანური და 90-ე პერცენტილის ხანგრძლივობა. |
| შეცდომების კატეგორიები | `buildFailureReasons` | ყველა შეცდომა და რაოდენობა შეცდომის კატეგორიის მიხედვით. |
| ბოლო დროის შეცდომიანი ბილდები | `buildRecentFailures` | უახლესი 100 შეცდომა, Tuist-ზე ბმულებით. |

ბოლო დროის შეცდომები მოიცავს დაწყების დროს, ხანგრძლივობას, მომხმარებელს, შტოს და მოთხოვნილ ამოცანებს. შეცდომების კატეგორიებია `verification`, `infrastructure_tooling` და `unknown`.

დატვირთვის შეჯამებები და შტო/დატვირთვის მნიშვნელობების სიები აბრუნებენ 1000-მდე მნიშვნელობას. ბილდის ჯანმრთელობის ცვლადის მოთხოვნები იყენებენ ბოლო 90 დღეს; Gradle-ის ძველი ცვლადის მოთხოვნები ინარჩუნებენ არსებულ ისტორიის ფანჯარას. Bazel აჩვენებს ბილდის მომხმარებელს, რომელიც შეიტყობინა ინსტრუმენტმა. სხვა ინტეგრაციები აჩვენებენ ანგარიშს, რომელიც დაკავშირებულია შეტყობინების სერთიფიკატთან. Bazel-ისა და Struo-ს ისტორიული გაშვებები, ასევე Struo-ს გაშვებები, რომლებიც შეიტყობინეს პროექტის სერთიფიკატებით, ჩანს როგორც Unknown, როდესაც მომხმარებელი არ ჩაწერილა.

გამოიყენეთ შეცდომის კატეგორიის ფილტრი ბილდის გაშვებებზე შესაბამისი შეცდომების საპოვნელად. კატეგორია ჩანს ბილდის დეტალებში, ინფორმაციის მინიშნებით, რომელიც ხსნის მის მნიშვნელობას; ნაგულისხმევი გადახედვა და ბილდის გაშვებების ცხრილები ინარჩუნებენ არსებულ სვეტებს. წარმატებულ, გაუქმებულ და დაუსრულებელ ბილდებს არ აქვთ შეცდომის კატეგორია. Gradle-ის Cache Analytics ბარათი და ბილდის დეტალები აჩვენებენ ჯამურ დროის დაზოგვას ამოცანებზე; ინსტრუმენტის მინიშნება ხსნის შეფასებას და პარალელური ამოცანების ეფექტს. ქეშის ვიჯეტი ადარებს შერჩეულ დიაპაზონს უშუალოდ წინამდებარე თანაბრძან სიგრძის პერიოდს იგივე ფილტრების გამოყენებით. შედარებები ნეიტრალურია: უფრო დიდმა ჯამმა შეიძლება ასახოს მეტი ბილდი. წინა შეფასებების არარსებობა არ აჩვენებს შედარებას; ჩაწერილი ნულოვანი საწყისი წერტილი აჩვენებს აბსოლუტურ ზრდას პროცენტის ნაცვლად.

## სტანდარტული დაფა {#what-you-can-query}

შემოიტანეთ [ბილდის ჯანმრთელობის დაფა](https://github.com/tuist/tuist/blob/main/grafana-datasource/src/dashboards/build-health.json), შემდეგ აირჩიეთ თქვენი მონაცემთა წყარო და პროექტი. ის მოიცავს ბილდების რაოდენობას, წარმატების მაჩვენებელს, მედიანურ და 90-ე პერცენტილის ხანგრძლივობებს, ნელი ბილდის ზღვარს, ნეიტრალურ შეცდომიანი ან ნელი ბილდების რაოდენობას, დაჯგუფებულ ქეშის დაზოგვასა და შეტყობინების ფარვას, და სამ შეცდომისა და დატვირთვის ცხრილს. დაამატეთ პანელები სხვა ხელმისაწვდომი მეტრიკებისთვის საჭიროებისამებრ. ავტომატური ნელი ზღვარი არის შერჩეული პერიოდის საკუთარი 90-ე პერცენტილი; მასზე მაღალი ბილდები არ მიუთითებს აუცილებლად რეგრესიაზე. დააყენეთ ფიქსირებული ზღვარი ხანგრძლივობის სამიზნე გაფრთხილებებისთვის. ქეშის პანელები პრიორიტეტს ანიჭებენ Gradle-ის ავტომატურ ჯამურ ამოცანის დროის შეფასებას მისი ფარვის გვერდით, რასაც მოსდევს ცალსახად შეტყობინებული გასული დროის დაზოგვა მათი საკუთარი ფარვის გვერდით.

## ბილდის სისტემები {#build-systems}

ბილდის ჯანმრთელობის მოთხოვნები და სტანდარტული დაფა მხარდაჭერენ Bazel-ს, Cargo-ს, Struo-ს, Gradle-ს და Xcode-ს. Tuist ირჩევს ბილდის სისტემას თქვენი პროექტიდან. შერეული პროექტები ამჟამად არ არის მხარდაჭერილი ბილდის ჯანმრთელობის მოთხოვნების ან სტანდარტული დაფის მიერ.

| ბილდის სისტემა | დატვირთვა | გაუქმების შეტყობინება | ქეშირებით მიღებული დაზოგვა |
| --- | --- | --- | --- |
| Bazel | ბრძანება | გასვლის კოდი 8, გარდა `run` | საჭიროებს მორგებულ მეტამონაცემებს |
| Cargo | ბრძანება | არ განირჩევა; რაოდენობა ნულია | გავლის დროის დაზოგვა საჭიროებს მორგებულ მეტამონაცემებს; კომპილატორის თავიდან აცილებული სამუშაო არ არის გავლის დროის დაზოგვა |
| Struo | ბრძანების ტიპი | ჩაწერილი გაუქმების მიზეზი | არ არის ჩაწერილი |
| Gradle | ამოცანების ჯგუფი | შეტყობინებული გაუქმებები | თავიდან აცილებული სამუშაოს ავტომატური შეფასება; გავლის დროის დაზოგვა საჭიროებს მორგებულ მეტამონაცემებს |
| Xcode | სქემა | არ განირჩევა; რაოდენობა ნულია | საჭიროებს მორგებულ მეტამონაცემებს |

დამუშავების ჩანაწერები და დაუსრულებელი გაშვებები გამოკლებულია. Bazel მოიცავს ბილდის, ტესტირების, გაშვების და კოდის დაფარვის ბრძანებებს. Struo მოიცავს დასრულებულ ბილდებს, ტესტებს და ზოგად გაშვებებს. Cargo მოიცავს ბილდის ბრძანებებს, როგორიცაა `build`, `check` და `test-build`; ტესტების შესრულების ძველი ანგარიშები გამოკლებულია ბილდის ჯანმრთელობიდან. Cargo-ს ბოლოდროინდელი შეცდომები იყენებენ ჩაწერილ დაწყების დროს, თუ ის ხელმისაწვდომია, წინააღმდეგ შემთხვევაში გადადიან ჩასმის დროზე; არარსებული ხანგრძლივობები რჩება მიუწვდომლად და არ განიხილება როგორც ნული.

Gradle ამოცანებს აჯგუფებს ინსტრუმენტული ტესტების, ერთეულოვანი ტესტების, ლინტინგის/შემოწმებების, ასემბლირების/პაკეტირების ან სხვა კატეგორიებად, ამ უპირატესობის თანმიმდევრობით. თითოეული ბილდი ეკუთვნის ერთ დატვირთვას. მორგებული მეტამონაცემებით შესაძლებელია Xcode-ის, Bazel-ის, Cargo-ს და Gradle-ის დატვირთვების გადაფარვა.

### შეცდომების კატეგორიები

| კატეგორია | მნიშვნელობა | ჩაწერილი მტკიცებულება |
| --- | --- | --- |
| `verification` | კოდის კომპილაციის, ლინკინგის, ტესტების ან შემოწმებების შეცდომა. | Gradle-ის ვერიფიკაციის ან კომპილაციის გამონაკლისები და ცნობილი შეცდომიანი ამოცანების ტიპები; Xcode-ის კომპილატორისა და ლინკერის პრობლემები; Bazel-ის სტრუქტურირებული არანულოვანი კომპილატორის/ტესტის ქმედებების შედეგები; Cargo-ს ჩაწერილი შეცდომიანი rustc კომპილაციები; Struo-ს ტესტების შეცდომები ან ქმედებები, რომლებიც აშკარად არის განსაზღვრული როგორც კომპილაცია, ლინკინგი, ტესტი, ლინტინგი ან შემოწმება. |
| `infrastructure_tooling` | ბილდი ვერ შესრულდა ჩვეულებრივად, რადგან მისმა ინსტრუმენტებმა, დამოკიდებულებებმა ან გარემომ დააფიქსირა შეცდომა. | Gradle-ის კონფიგურაციის, დამოკიდებულებების გადაწყვეტის, შეყვანა/გამოყვანის ან მეხსიერების შეცდომები; Bazel-ის სტრუქტურირებული ინფრასტრუქტურის შეცდომები და [დოკუმენტირებული გასვლის კოდები](https://bazel.build/run/scripts); Struo-ს ინფრასტრუქტურის ქმედებების შეცდომები. |
| `unknown` | ანგარიში არ შეიცავს საკმარის მტკიცებულებას შეცდომის კლასიფიცირებისთვის. | ნებისმიერი ბრძანებები, დიაგნოსტიკის არარსებობა და ძველი ანგარიშები სტრუქტურირებული მტკიცებულების გარეშე. |

Gradle-ის კონფიგურაციის ფაზის შეცდომები, მათ შორის ბილდის სკრიპტებში არსებული შეცდომები, ჯგუფდება ინფრასტრუქტურის/ინსტრუმენტების კატეგორიაში, რადგან ამოცანის შესრულება ვერ გაგრძელდა.

Cargo-ს შეცდომები, რომლებსაც არ აქვთ აშკარა კატეგორიის მეტამონაცემები ან ჩაწერილი შეცდომიანი rustc კომპილაცია, რჩებიან `unknown`; მხოლოდ შეცდომიანი `check` ან `test-build` ბრძანება არ ადასტურებს ვერიფიკაციის შეცდომას. Cargo-ს ამოცანების ხელახალი გამოყენების მრიცხველები და კომპილატორის თავიდან აცილებული სამუშაოს შეფასება არასდროს იძლევა არც გავლის დროის ქეშირებით მიღებულ დაზოგვას და არც Gradle-ის კუმულაციურ ამოცანის დროის მეტრიკას.

აშკარა `tuist.failure_category` მეტამონაცემები გადაფარავს ავტომატურ კლასიფიკაციას. წინააღმდეგ შემთხვევაში, თუ ბილდში ორივე გვხვდება, ინფრასტრუქტურის მტკიცებულებას აქვს უპირატესობა ვერიფიკაციაზე. შეცდომიანი ნებისმიერი სკრიპტი არ განიხილება როგორც კომპილატორის ან ტესტის შეცდომა. ისტორიულ ანგარიშებს შეუძლიათ გამოიყენონ Tuist-ის მიერ უკვე შენახული მტკიცებულება, მაგრამ ახალი შემტყობინებლის ველები არ ავსებენ არარსებულ ინფორმაციას. ავტომატური შემტყობინებლის მეტამონაცემები იყენებს თავისუფალ ადგილს არსებული 20-ჩანაწერიანი მორგებული მეტამონაცემების ლიმიტის ფარგლებში.

`buildFailureReasons` პასუხი ინარჩუნებს თავის `all` სტრიქონს თავსებადობისთვის. სტანდარტული დაფა ფილტრავს ამ ჯამს შეცდომების კატეგორიების დიაგრამიდან და ცალკე აჩვენებს ჯამურ შეცდომებს. ძველ `gradleFailureReasons` მოთხოვნას ინარჩუნებს თავის საწყის სამ კატეგორიულ სტრიქონს.

| კონფიგურაცია | `configuration` | Xcode ბილდის ხანგრძლივობები |
| ბილდის ტიპი | `category` | Xcode ბილდის ხანგრძლივობები |

გარემოს მნიშვნელობებია `any`, `ci` (ავტომატიზებული ბილდები) და `local`. სტატუსის მნიშვნელობებია `success`, `failure` და, ბილდის ჯანმრთელობის მოთხოვნებისთვის, `cancelled`; მნიშვნელობის გამოტოვება მოიცავს ყველა სტატუსს. ბილდის ტიპის მნიშვნელობებია `clean` და `incremental`; მნიშვნელობის გამოტოვება მოიცავს ორივეს.

ცარიელ ბილდის ჯანმრთელობის ინტერვალებს აქვთ ნულოვანი რაოდენობა და არ აქვთ საშუალო ხანგრძლივობის, ხანგრძლივობის პერცენტილის ან წარმატების მაჩვენებლის მნიშვნელობა. ნელი ბილდის ზღვარი კვლავ იყენებს სრულად შერჩეულ დიაპაზონს. ცალკეული ტესტის ხანგრძლივობის მოთხოვნა აბრუნებს ნულს ცარიელი დროითი მწკრივის ინტერვალებისთვის. მთლიანი პერიოდის პერცენტილები გამოითვლება გაშვებებიდან და არა ინტერვალის პერცენტილებიდან. ბილდის ჯანმრთელობის პერცენტილები იყენებენ ზუსტ აგრეგაციას; ცალკეული Xcode-ისა და ტესტის ხანგრძლივობის მოთხოვნები იყენებენ მიახლოებით პერცენტილებს.

ბილდის ჯანმრთელობის დროითი მწკრივები განათავსებენ ნაწილობრივ პირველ ბაკეტს შერჩეული დიაპაზონის დასაწყისში, რათა ის ხილული დარჩეს. ძველ Gradle-ის მოთხოვნებს ინარჩუნებენ თავიანთ საწყის ბაკეტის დროის შტამპებს.

ყველა მოთხოვნა იღებს თარიღის დიაპაზონებს 366 დღემდე. მათი საზღვრები და დროის შტამპები განსხვავდება:

| მოთხოვნა | გამოყენებული დროის შტამპი | დიაპაზონის საზღვრები |
| --- | --- | --- |
| ბილდის ჯანმრთელობა: Xcode, Bazel, Cargo, Gradle | ჩანაწერის ჩასმის დრო | მოიცავს დასაწყისს, გამორიცხავს დასასრულს |
| ბილდის ჯანმრთელობა: Struo | გაშვების დაწყების დრო | მოიცავს დასაწყისს, გამორიცხავს დასასრულს |
| Xcode ბილდის ხანგრძლივობები | ჩანაწერის ჩასმის დრო | გამორიცხავს დასაწყისსა და დასასრულს |
| ტესტების ხანგრძლივობები | ჩაწერილი გაშვების დრო | მოიცავს დასაწყისსა და დასასრულს |

### დაფის ცვლადები

გამოიყენეთ დაფის ცვლადები პროექტებისა და მხარდაჭერილი ფილტრებისთვის. ტოტისა და სამუშაო დატვირთვის ცვლადები იყენებენ შემდეგ მოთხოვნებს:

| ცვლადი | მოთხოვნა |
| --- | --- |
| ტოტი | `buildBranches account/project` |
| სამუშაო დატვირთვა | `buildWorkloads account/project` |

ფილტრები იღებენ ერთ ზუსტ მნიშვნელობას. ტოტისა და სამუშაო დატვირთვის ცვლადებისთვის, დააყენეთ ყველას პარამეტრის მორგებული მნიშვნელობა `__tuist_all__`-ზე. სხვა ფილტრები იყენებენ ჩაშენებულ ნებისმიერ პარამეტრს ან ცარიელ მნიშვნელობას. მრავალჯერადი შერჩევა და რეგულარული გამოსახულებები არ არის მხარდაჭერილი.

## მორგებული მეტამონაცემების შეტყობინება {#custom-metadata}

Xcode, Bazel, Cargo და Gradle ბილდები იღებენ ამ არასავალდებულო მეტამონაცემების მნიშვნელობებს:

| გასაღები | მიღებული მნიშვნელობა |
| --- | --- |
| `tuist.workload` | სამუშაო დატვირთვის სახელი, რომელიც ცვლის ნაგულისხმევ დაჯგუფებას. |
| `tuist.failure_category` | `verification` ან `infrastructure_tooling`. |
| `tuist.cache_work_avoided_ms` | მხოლოდ Gradle. ავტომატურად შეტყობინებული თავიდან არიდებული სამუშაოს შეფასება, მთელ მილიწამებში 365 დღემდე. |
| `tuist.cache_time_saved_ms` | მთელი მილიწამები 0-დან 31,536,000,000-მდე (365 დღე). |

მიეწოდეთ ისინი თქვენი ბილდის ინტეგრაციის მორგებული მეტამონაცემების კონფიგურაციით:

```json
{
  "custom_metadata": {
    "values": {
      "tuist.workload": "Release verification",
      "tuist.failure_category": "verification",
      "tuist.cache_time_saved_ms": "12000"
    }
  }
}
```

შეატყობინეთ ქეშის დაზოგვა მხოლოდ მაშინ, როცა გაქვთ გასული დროის გაზომვა ან დოკუმენტური შეფასება იმ ბილდისთვის. ქეშის მოხვედრები და დაგროვებითი ამოცანების ხანგრძლივობები ერთად ვერ განსაზღვრავენ გასულ დაზოგვას, როცა ამოცანები პარალელურად მუშაობენ. დაკარგული ქეშის დაზოგვა უცნობი რჩება. დაკარგული შეცდომის კატეგორიის მეტამონაცემები ეყრდნობა ჩაწერილ მტკიცებულებას, როგორც აღწერილია [ბილდის სისტემებში](#build-systems). მონაცემთა შენახვა უცვლელია.

## გაფრთხილებები და Slack {#alerts-and-slack}

შექმენით Grafana-ს მიერ მართული გაფრთხილების წესი რიცხვითი მეტრიკით. მაგალითად:

| მეტრიკა | იდენტიფიკატორი | მაგალითის პირობა |
| --- | --- | --- |
| ბილდის წარმატების მაჩვენებელი | `success_rate` | 99%-ზე ნაკლები |
| ვერ მოხერხებული ბილდები | `failed_builds` | ნულზე მეტი |
| 90-ე პროცენტილის ხანგრძლივობა | `p90` | თქვენი გუნდის ხანგრძლივობის ლიმიტზე მეტი |

გამოიყენეთ **მთელი პერიოდი** ერთი მნიშვნელობისთვის შეფასების ფანჯარაში, ან შეამცირეთ დროითი მწკრივი ერთ მნიშვნელობამდე. ხანგრძლივობის მოთხოვნებისთვის მთელი პერიოდის რეჟიმში, აირჩიეთ ერთი მწკრივი.

- გამოიყენეთ ფიქსირებული პროექტისა და ფილტრის მნიშვნელობები. დაფის ცვლადები ხელმიუწვდომელია ფონური გაფრთხილების შეფასების დროს.
- გამოიყენეთ რიცხვითი მოთხოვნები გაფრთხილებებისთვის. სამუშაო დატვირვის მონიტორინგისთვის, გაფილტრეთ ბილდის ჯანმრთელობის მოთხოვნა იმ სამუშაო დატვირთვაზე.
- დააყენეთ წესის ქცევა მონაცემების არარსებობის შემთხვევაში იმ ინტერვალებისთვის, სადაც არ არის ბილდები ან შეტყობინებული ქეშის დაზოგვა.

კონფიგურირება [Slack საკონტაქტო წერტილი](https://grafana.com/docs/grafana/latest/alerting/configure-notifications/manage-contact-points/integrations/configure-slack/) და მიმართეთ წესი მასთან Grafana-ს შეტყობინებების პოლიტიკის მეშვეობით. Grafana აგზავნის შეტყობინებებს და ინახავს Slack-ის სერთიფიკატებს.

## არსებული დაფების განახლება {#upgrading}

არსებული ხანგრძლივობის პანელები ინარჩუნებენ თავიანთ მოთხოვნებს, ფილტრებს, მწკრივების სახელებსა და ერთეულებს. შენახული Gradle ჯანმრთელობის პანელები და ცვლადები ასევე აგრძელებენ მუშაობას.

შეიტანეთ სტანდარტული დაფა ცალკე, რათა გამოიყენოთ გაზიარებული ბილდის ჯანმრთელობის მოთხოვნები. არსებული დაფები არ მიგრირდება ავტომატურად. გაზიარებული მოთხოვნები საჭიროებენ Tuist სერვერს, რომელიც უზრუნველყოფს ბილდის ჯანმრთელობის ბოლო წერტილებს; არსებული ხანგრძლივობის მოთხოვნები კვლავ მუშაობენ ძველ სერვერებთან.

## მოთხოვნები {#requirements}

- Grafana 10.4 ან უფრო ახალი.
- Tuist ტოკენი, რომელსაც აქვს ნებართვა წაიკითხოს პროექტები და მეტრიკები, რომლებიც გსურთ დახაზოთ. იხილეთ [ავტორიზაცია](#authentication) ქვემოთ.

## ავტორიზაცია {#authentication}

გამოიყენეთ <.localized_link href="/guides/server/authentication#account-tokens">ანგარიშის ტოკენი</.localized_link> დაფებისა და ფონური გაფრთხილებების შეფასებისთვის. მიანიჭეთ `project:builds:read` ბილდის მეტრიკებისთვის და `project:tests:read` ტესტების ხანგრძლივობისთვის, და შემოიფარგლეთ წვდომა იმ პროექტებზე, რომელთა ვიზუალიზაციაც გსურთ. საჭიროა მხოლოდ იმ სკოპების მინიჭება, რომლებიც გამოყენებულ მეტრიკებს ეხება. მიჰყევით <.localized_link href="/guides/server/authentication#creating-an-account-token">ტოკენის შექმნის ინსტრუქციებს</.localized_link> ერთის გენერირებისთვის.

ინტეგრაცია ასევე იღებს არსებულ პროექტის ტოკენებს მათი საკუთარი პროექტისთვის და <.localized_link href="/guides/server/authentication#as-a-user">მომხმარებლის წვდომის ტოკენებს</.localized_link> მომხმარებლის წაკითხვის ნებართვებით. მომხმარებლის წვდომის ტოკენები მოკლე ვადიანია. Grafana ინახავს თქვენს მიერ მოწოდებულ ტოკენს და არ ანახლებს მას ან არ იყენებს ხელახლა თქვენს ადგილობრივ Tuist შესვლას; შეცვალეთ ის, როდესაც ვადა გაუვა. ანგარიშის ტოკენები გაძლევთ საშუალებას მართოთ პროექტზე წვდომა, ნებართვები და ვადა დამოუკიდებლად მომხმარებლის შესვლის სესიისგან.

## კონფიგურაცია {#configuration}

დაამატეთ მონაცემთა წყარო და დააყენეთ:

| ველი | შენახული პარამეტრი | შენიშვნები |
| --- | --- | --- |
| სერვერის URL | `jsonData.url` | ნაგულისხმევად არის `https://tuist.dev`. |

## ინსტალაცია {#installation}

### Grafana-ს კატალოგიდან {#from-the-grafana-catalog}

გამოქვეყნების შემდეგ, დააინსტალირეთ ის, როგორც ნებისმიერი სხვა მონაცემთა წყარო **კავშირები → ახალი კავშირის დამატება → Tuist**-დან, ან `grafana-cli plugins install tuist-metrics-datasource`-ის გამოყენებით.

### გამოქვეყნებამდე (თვითმასპინძელი Grafana) {#before-it-is-published-self-hosted-grafana}

პლაგინი არის ხელმოუწერილი, სანამ ის კატალოგისთვის არ დამტკიცდება. თვითმასპინძელ ინსტანციაზე შეგიძლიათ:

- **დაუშვათ ის ხელმოუწერლად** — დაამატეთ `tuist-metrics-datasource` `allow_loading_unsigned_plugins`-ში (ან `GF_PLUGINS_ALLOW_LOADING_UNSIGNED_PLUGINS=tuist-metrics-datasource`) და ჩააგდეთ აწყობილი პლაგინი თქვენს პლაგინების დირექტორიაში.
- **პირადად მოაწერეთ ხელი** თქვენი ინსტანციებისთვის — `npm run sign -- --rootUrls https://grafana.example.com` (URL უნდა ემთხვეოდეს ინსტანციის `root_url`-ს), შემდეგ გაავრცელეთ zip ფაილი.

[Grafana Cloud მოითხოვს პლაგინებს კატალოგიდან](https://grafana.com/docs/grafana-cloud/learn-and-build/get-started/learn/find-and-use-plugins/) და არ უჭერს მხარს ხელმოუწერელ ან ხელით ატვირთულ პლაგინებს.
