# SCIM პროვიზირება {#scim-provisioning}

Tuist მხარდაჭერს SCIM 2.0 პროვიზირებას, რათა იდენტობის პროვაიდერმა შეძლოს ორგანიზაციის წევრების ავტომატურად შექმნა, განახლება და პროვიზიის გაუქმება.

SCIM კონფიგურირდება თქვენი ორგანიზაციის პარამეტრებში **Authentication** ჩანართიდან. SCIM ტოკენი არის ორგანიზაციის საკუთრებაში არსებული ანგარიშის ტოკენი, რომელიც შეზღუდულია SCIM წვდომით და გამოჩნდება მხოლოდ ერთხელ გენერაციისას.

> [!NOTE]
> SCIM აკონტროლებს წევრობას და სიცოცხლის ციკლს. ის არ ცვლის <.localized_link href="/guides/integrations/authentication/sso">Single Sign-On</.localized_link>-ს. ცალ-ცალკე დააკონფიგურეთ SSO, თუ პროვიზირებულ მომხმარებლებს ასევე უნდა შესვლა თქვენი იდენტობის პროვაიდერის მეშვეობით.

პროვიზირებული მომხმარებლები უკვე ორგანიზაციის წევრები არიან. როდესაც ისინი შედიან იმავე ელფოსტის მისამართით, ეს წევრობა შეიძლება გამოყენებულ იქნას ნდობის დასამყარებლად მათი პროვაიდერის იდენტობასთან დასაკავშირებლად. <.localized_link href="/guides/integrations/authentication/sso#verify-a-login-email-domain">დადასტურებული შესვლის ელფოსტის დომენი</.localized_link> და <.localized_link href="/guides/integrations/authentication/sso#choose-an-enrollment-policy">რეგისტრაციის პოლიტიკა</.localized_link> აკონტროლებს მომხმარებლებს, რომლებიც ჯერ არ არიან პროვიზირებული ან დამატებული ორგანიზაციაში.

## Okta {#okta}

Okta Tuist-ისთვის იყენებს ორ ცალკე აპლიკაციას:

- **OIDC ვებ აპლიკაცია** Tuist-ში შესასვლელად.
- **SCIM 2.0 Test App (Header Auth)** აპლიკაცია Tuist-ში მომხმარებლებისა და ჯგუფების პროვიზირებისთვის.

ჯერ დააკონფიგურეთ <.localized_link href="/guides/integrations/authentication/sso#okta">Okta SSO</.localized_link>, თუ მომხმარებლებმა Okta-ს მეშვეობით უნდა შეძლონ შესვლა, შემდეგ კი დააკონფიგურეთ SCIM პროვიზირება ქვემოთ მოცემული ნაბიჯებით.

### ნაბიჯი 1: Tuist SCIM ტოკენის გენერაცია {#okta-step-1}

1. Tuist-ში გადადით თქვენი ორგანიზაციის **Authentication** პარამეტრების ჩანართზე.
2. **SCIM provisioning** სექციაში დააკოპირეთ **SCIM endpoint URL**. ის უნდა მთავრდებოდეს `/scim/v2`-ით.
3. დააწკაპუნეთ **Generate token**.
4. მიანიჭეთ ტოკენს სახელი (მაგალითად, `Okta`).
5. დააკოპირეთ გენერირებული ტოკენი. Tuist ტოკენს მხოლოდ ერთხელ აჩვენებს.

### ნაბიჯი 2: Okta SCIM აპლიკაციის დამატება {#okta-step-2}

1. თქვენს Okta ადმინისტრატორის დაფაზე გადადით **Applications > Applications > Browse App Catalog**.
2. მოძებნეთ და დაამატეთ **SCIM 2.0 Test App (Header Auth)**.
3. მიანიჭეთ მას რაიმე ამოსაცნობი სახელი, მაგალითად `Tuist SCIM`.
4. შეავსეთ შესვლის პარამეტრები SCIM სატესტო აპლიკაციისთვის. Tuist ამ აპლიკაციას შესვლისთვის არ იყენებს; შესვლას ამუშავებს OIDC აპლიკაცია SSO სახელმძღვანელოდან.

### ნაბიჯი 3: API ინტეგრაციის კონფიგურაცია {#okta-step-3}

1. გახსენით SCIM აპლიკაციის **Provisioning** ჩანართი.
2. **Settings > Integration** ქვეშ დააწკაპუნეთ **Configure API Integration** ან **Edit**.
3. აირჩიეთ **Enable API integration**.
4. ჩასვით Tuist-ის **SCIM endpoint URL** Okta-ს **Base URL** ველში.
5. ჩასვით Tuist SCIM ტოკენი **API Token**-ში `Bearer ` პრეფიქსით. მაგალითად, `Bearer tuist_scim_...`. Okta ამ ველს აგზავნის როგორც `Authorization` ჰედერს, ხოლო Tuist ელოდება bearer ტოკენს.
6. ჩართეთ **Import Groups**, თუ გსურთ, რომ Okta-მ წაიკითხოს Tuist-ის SCIM ჯგუფები.
7. დააწკაპუნეთ **Test API Credentials**. Okta უნდა აცნობოს, რომ ინტეგრაცია წარმატებით დადასტურდა.
8. დააწკაპუნეთ **Save**.

### ნაბიჯი 4: პროვიზირების მოქმედებების ჩართვა {#okta-step-4}

1. SCIM აპლიკაციის **Provisioning** ჩანართში გახსენით **Settings > To App**.
2. დააწკაპუნეთ **Edit**.
3. ჩართეთ:
   - **Create Users**
   - **Update User Attributes**
   - **Deactivate Users**
4. დააწკაპუნეთ **Save**.

### ნაბიჯი 5: მომხმარებლების ან ჯგუფების მინიჭება {#okta-step-5}

1. გახსენით SCIM აპლიკაციის **Assignments** ჩანართი.
2. მიანიჭეთ ის მომხმარებლები ან ჯგუფები, რომლებიც Tuist-ში უნდა პროვიზირდეს.
3. მიანიჭეთ იგივე მომხმარებლები ან ჯგუფები Okta OIDC აპლიკაციას, თუ მათ ასევე SSO-ით შესვლა უნდა შეეძლოთ.
4. შეამოწმეთ Tuist-ის **Members** ჩანართი, რათა დარწმუნდეთ, რომ მინიჭებული მომხმარებლები ორგანიზაციაში ჩანან.

დეპროვიზირების შესამოწმებლად, გააუქმეთ ან გააუქციეთ მომხმარებელი Okta-ში და დარწმუნდით, რომ ის ქრება Tuist ორგანიზაციის **Members** ჩანართიდან.

### როლების მინიჭება {#okta-assigning-roles}

Tuist-ს აქვს სამი <.localized_link href="/guides/server/accounts-and-projects#roles">როლი</.localized_link>: `admin`, `user` და `viewer`. Tuist თითოეული როლისთვის ერთ SCIM ჯგუფს წარმოადგენს: `Tuist Admins`, `Tuist Users` და `Tuist Viewers`. მიამაგრეთ Okta ჯგუფები მათზე **Group Push**-ის საშუალებით:

1. აირჩიეთ ან შექმენით Okta ჯგუფი თითოეული მინიჭებადი როლისთვის და მიანიჭეთ ეს ჯგუფები SCIM აპლიკაციის **Assignments** ჩანართზე.
2. დარწმუნდით, რომ API ინტეგრაციაში ჩართულია **Import Groups**, შემდეგ გახსენით SCIM აპლიკაციის **Import** ჩანართი და დააწკაპუნეთ **Import Now**, რათა Okta-მ იცოდეს Tuist-ის ჯგუფების შესახებ.
3. გახსენით SCIM აპლიკაციის **Push Groups** ჩანართი და დააწკაპუნეთ **Push Groups > Find groups by name**.
4. აირჩიეთ Okta ჯგუფი, აირჩიეთ **Link Group** როგორც push მოქმედება და აირჩიეთ შესაბამისი Tuist ჯგუფი. Tuist არ უჭერს მხარს ჯგუფების შექმნას SCIM-ის საშუალებით, ამიტომ ახლის შექმნის ნაცვლად არსებულ ჯგუფს მიამაგრეთ.
5. დააწკაპუნეთ **Save** და გაიმეორეთ დარჩენილი როლებისთვის.

მომხმარებლის დამატება მიმაგრებულ ჯგუფში ანიჭებს მას ამ როლს. ჯგუფიდან მისი ამოღება აბრუნებს მას იმ როლზე, რომელზეც ორგანიზაცია აერთიანებს single sign-on წევრებს, რაც არის `user`, თუ ადმინისტრატორმა არ შეცვალა ეს **Settings > Authentication** ქვეშ. მომხმარებლები, რომლებიც არ არიან არცერთ მიმაგრებულ ჯგუფში, ასევე იღებენ ამ როლს. მომხმარებლის ჯგუფიდან ამოღება არ შლის მას ორგანიზაციიდან; ამისთვის გააუქმეთ ან გააუქციეთ ის Okta-ში.

## Microsoft Entra ID {#microsoft-entra-id}

Entra ID ახორციელებს Tuist-ის პროვიზირებას არა-გალერიის საწარმო აპლიკაციის საშუალებით. ჯერ კონფიგურაცია გაუკეთეთ <.localized_link href="/guides/integrations/authentication/sso#microsoft-entra-id">Microsoft Entra ID SSO</.localized_link>-ს, თუ მომხმარებლებს ასევე Entra ID-ით შესვლა უნდა შეეძლოთ.

აპლიკაცია, რომელსაც single sign-on-ისთვის აირეგისტრირებთ და საწარმო აპლიკაცია, რომელსაც პროვიზირებისთვის გამოიყენებთ, შეიძლება ერთი და იგივე იყოს. პროვიზირება კონფიგურირდება საწარმო აპლიკაციის ჩანაწერზე.

### ნაბიჯი 1: Tuist SCIM ტოკენის გენერირება {#entra-step-1}

1. Tuist-ში გადადით თქვენი ორგანიზაციის **Authentication** პარამეტრების ჩანართზე.
2. **SCIM provisioning** სექციაში დააკოპირეთ **SCIM endpoint URL**. ის უნდა მთავრდებოდეს `/scim/v2`-ით.
3. დააწკაპუნეთ **Generate token**.
4. მიანიჭეთ სახელი ტოკენს (მაგალითად, `Entra ID`).
5. დააკოპირეთ გენერირებული ტოკენი. Tuist ტოკენს მხოლოდ ერთხელ აჩვენებს.

### ნაბიჯი 2: პროვიზირების კონფიგურაცია {#entra-step-2}

1. Microsoft Entra admin center-ში გადადით **Identity > Applications > Enterprise applications**-ზე და გახსენით Tuist აპლიკაცია.
2. გახსენით **Provisioning** და დააყენეთ **Provisioning Mode** მნიშვნელობაზე **Automatic**.
3. დააყენეთ **Tenant URL** Tuist SCIM endpoint URL-ზე.
4. დააყენეთ **Secret Token** Tuist SCIM ტოკენზე. შეიყვანეთ ტოკენი ცალკე, `Bearer ` პრეფიქსის გარეშე; Entra ID სქემას თავად ამატებს.
5. დააწკაპუნეთ **Test Connection**. Entra ID უნდა აცნობოს, რომ მიწოდებული მონაცემები ავტორიზებულია.
6. შეინახეთ კონფიგურაცია.

### ნაბიჯი 3: შესაბამისი ატრიბუტის დაყენება {#entra-step-3}

1. **Mappings** ქვეშ გახსენით **Provision Microsoft Entra ID Users**.
2. დარწმუნდით, რომ `userPrincipalName` ან `mail` ასახავს SCIM `userName` ატრიბუტზე და რომ ეს ატრიბუტი გამოიყენება **Matching precedence 1**-ისთვის.
3. ამოიღეთ `externalId` შესაბამისი ატრიბუტებიდან, თუ ის არსებობს.

Tuist პროვიზირებულ მომხმარებლებს `userName`-ით აიდენტიფიცირებს. ის არ ინახავს დირექტორიის ობიექტის იდენტიფიკატორს, რომელსაც Entra ID აგზავნის როგორც `externalId`, ამიტომ ამ ატრიბუტზე ფილტრი არსებულ წევრს ვერ პოულობს და პროვიზირების ციკლებმა შეიძლება არაპროგნოზირებადად იმოქმედონ.

### ნაბიჯი 4: ჯგუფის პროვიზირების გათიშვა {#entra-step-4}

**Mappings** ქვეშ დააყენეთ **Provision Microsoft Entra ID Groups** გათიშულ მდგომარეობაში.

Tuist-ის SCIM ჯგუფები არის ფიქსირებული ჯგუფი თითოეული ორგანიზაციის როლისთვის და არა დირექტორიის ჯგუფები, რომელთა შექმნაც შეგიძლიათ, ამიტომ დირექტორიის ჯგუფის პროვიზირების მცდელობა მარცხდება. ამის ნაცვლად მიანიჭეთ როლები ქვემოთ აღწერილი გზით.

### ნაბიჯი 5: მომხმარებლების მინიჭება და პროვიზირების დაწყება {#entra-step-5}

1. გახსენით აპლიკაციის **Users and groups** ჩანართი და მიანიჭეთ მომხმარებლები ან ჯგუფები, რომლებიც Tuist-ში უნდა პროვიზირდეს.
2. დაბრუნდით **Provisioning**-ზე და დაიწყეთ ის.
3. შეამოწმეთ Tuist-ის **Members** ჩანართი, რათა დარწმუნდეთ, რომ მინიჭებული მომხმარებლები ორგანიზაციაში ჩანან.

Entra ID პროვიზირებას საკუთარი განრიგით ასრულებს, რაც ჩვეულებრივ ყოველ 40 წუთში ხდება, ამიტომ წევრები მყისიერად არ ჩანან. ერთი მომხმარებლის დაუყოვნებლივ შესამოწმებლად გამოიყენეთ **Provision on demand**.

პროვიზირების გაუქმების შესამოწმებლად, Entra ID-ში გააუქმეთ ან გამორთეთ მომხმარებელი და დარწმუნდით, რომ ის Tuist ორგანიზაციის **Members** ჩანართიდან გაქრა.

თუ მოგვიანებით შეცვლით პროვიზირების სფეროს, მაგალითად **Sync all users and groups**-დან **Sync only assigned users and groups**-ზე, შემდეგ დააჭირეთ **Restart provisioning**. Entra ID ახალ სფეროს, მათ შორის იმ მომხმარებლების პროვიზირების გაუქმებას, ვინც მასში აღარ არიან, მხოლოდ გადატვირთვის შემდეგ გამოიყენებს.

### როლების მინიჭება {#entra-assigning-administrators}

Tuist-ს აქვს სამი <.localized_link href="/guides/server/accounts-and-projects#roles">როლი</.localized_link>: `admin`, `user` და `viewer`. მათი Entra ID-დან დასაყენებლად:

1. **App registrations**-ში გახსენით Tuist აპლიკაცია და დაამატეთ აპლიკაციის როლი თითოეული Tuist როლისთვის, რომლის მინიჭებაც გსურთ. დააყენეთ **Allowed member types** მნიშვნელობად **Users/Groups** და **Value** — `admin`, `user` ან `viewer`.
2. საწარმო აპლიკაციის **Users and groups** ჩანართზე მიანიჭეთ თითოეულ მომხმარებელს ან ჯგუფს ერთ-ერთი ეს აპლიკაციის როლი. მომხმარებელს შეიძლება ჰქონდეს რამდენიმე აპლიკაციის როლი. Tuist იყენებს ყველაზე მაღალი პრივილეგიის მქონე როლს, სადაც `admin` უფრო მაღალია ვიდრე `user` და `user` უფრო მაღალია ვიდრე `viewer`, ამიტომ მომხმარებელი, რომელიც სხვადასხვა როლზე ასახულ ჯგუფებს ეკუთვნის, იღებს მათ შორის უმაღლესს.
3. **Provisioning > Mappings** ქვეშ, გახსენით **Advanced Options** ჩამოსაშლელი მენიუ და აირჩიეთ **Edit target User attributes**. დაამატეთ ატრიბუტი სახელით `roles`, სადაც **Type** დაყენებულია `String`-ზე და **Multi-Value** მონიშნულია.
4. **Provisioning > Mappings > Provision Microsoft Entra ID Users** ქვეშ, დააჭირეთ **Add New Mapping**. დააყენეთ **Mapping type** მნიშვნელობად **Expression**, **Expression** — `AssertiveAppRoleAssignmentsComplex([appRoleAssignments])`, ხოლო **Target attribute** — თქვენს მიერ დამატებულ `roles` ატრიბუტზე.
5. პროვიზირების სფერო დატოვეთ დაყენებული **Sync only assigned users and groups**-ზე. `AssertiveAppRoleAssignmentsComplex` არ არის თავსებადი **Sync all users and groups**-თან.

`AssertiveAppRoleAssignmentsComplex` აგზავნის ყველა აპლიკაციის როლს, რომელიც მომხმარებელს აქვს, და ასევე აგზავნის წაშლებს, ამიტომ როლის ჩამორთმევა Entra ID-ში ამცირებს მომხმარებლის პრივილეგიებს იმ ყველაზე მაღალ როლამდე, რომელიც მას კვლავ აქვს. `SingleAppRoleAssignment([appRoleAssignments])` ასახული `roles[primary eq "True"].value`-ზე ასევე მუშაობს, მაგრამ ის ყოველთვის მხოლოდ ერთ როლს აგზავნის და Entra ID არ იძლევა გარანტიას, თუ რომელს აირჩევს, როდესაც მომხმარებელს რამდენიმე როლი აქვს.

მომხმარებლის აპლიკაციის როლების შეცვლა Entra ID-ში ანახლებს მის Tuist როლს შემდეგი პროვიზირების ციკლის დროს. მომხმარებელი, რომელიც პროვიზირებულია აპლიკაციის როლის გარეშე ან `admin`, `user` ან `viewer`-ისგან განსხვავებული მნიშვნელობებით, იღებს იმ როლს, რომლითაც ორგანიზაცია აერთიანებს ერთჯერადი შესვლის (SSO) წევრებს, რაც არის `user`, თუ ადმინისტრატორმა არ შეცვალა ის **Settings > Authentication** ქვეშ.

## სიცოცხლის ციკლის ქცევა {#lifecycle-behavior}

როდესაც თქვენი იდენტობის პროვაიდერი მომხმარებელს პროვიზირების აპლიკაციას ანიჭებს, Tuist ქმნის მომხმარებელს, თუ ელფოსტა Tuist-ისთვის უცნობია, შემდეგ კი ამატებს მას ორგანიზაციაში. თუ ელფოსტა უკვე ეკუთვნის ორგანიზაციის გარეთ არსებულ Tuist მომხმარებელს, Tuist ამატებს ამ მომხმარებელს და აგზავნის შეტყობინებას, თუკი ანგარიში სხვა ორგანიზაციის SCIM ინტეგრაციით არ არის შექმნილი. ამ შემთხვევაში Tuist უარყოფს მოთხოვნას `409`-ით, რათა იდენტობის პროვაიდერმა ვერ მოითხოვოს ანგარიში, რომელსაც სხვა ორგანიზაცია მართავს.

თქვენს იდენტობის პროვაიდერს შეუძლია შეცვალოს მომხმარებლის ელფოსტა (`userName`) მხოლოდ მაშინ, როცა თქვენი ორგანიზაცია ანგარიშს დამოუკიდებლად მართავს. ეს ნიშნავს, რომ Tuist-მა შექმნა ანგარიში თქვენი SCIM ინტეგრაციის მეშვეობით და ამის შემდეგ მომხმარებელმა არ დააყენა პაროლი, არ შესულა თქვენი ორგანიზაციის ერთჯერადი შესვლის (SSO) გარდა სხვა პროვაიდერით, არ მოითხოვა აგენტის რეგისტრაცია ან არ შეუერთდა სხვა ორგანიზაციას. ნებისმიერი სხვა მომხმარებლისთვის Tuist უარყოფს ცვლილებას `400`-ით და `mutability` SCIM შეცდომის ტიპით. ის მაინც გამოიყენებს იმავე მოთხოვნაში გაგზავნილ დეაქტივაციას. Tuist ასევე უარს ამბობს შექმნას მომხმარებლები ან გადაარქვას სახელი მომხმარებლებს შესვლის დომენში, რომელიც სხვა ორგანიზაციამ დაადასტურა, და tuist.dev-ზე, Tuist-ის საკუთარ დომენში. სახელის გადარქმევა შლის ჩანაწერს, რომ მომხმარებელმა დაადასტურა ძველი მისამართის კონტროლი.

როდესაც თქვენი იდენტობის პროვაიდერი აუქმებს ან დეაქტივირებს მომხმარებელს, Tuist აშორებს მის ორგანიზაციულ როლს, ინარჩუნებს მომხმარებლის ჩანაწერს და მის მიერ შესრულებულ ნამუშევარს. პროვიზირების გაუქმება არ თიშავს მომხმარებელს გლობალურად, რადგან ერთი და იგივე Tuist მომხმარებელი შეიძლება სხვა ორგანიზაციებსაც ეკუთვნოდეს.

Tuist აჩვენებს სამ სინთეზურ SCIM ჯგუფს: `Tuist Admins`, `Tuist Users` და `Tuist Viewers`. ჯგუფში წევრის დამატება აყენებს მის ორგანიზაციულ როლს. წევრის წაშლა ჯგუფიდან, რომელიც ემთხვევა მის მიმდინარე როლს, აბრუნებს მას რეგისტრაციის როლზე, ხოლო წევრობა მთავრდება მხოლოდ მაშინ, როცა მომხმარებელი გაუქმებულია ან დეაქტივირებული. იდენტობის პროვაიდერებს ასევე შეუძლიათ დააყენონ როლი SCIM `roles` ატრიბუტის მეშვეობით მომხმარებელზე, მნიშვნელობებით `admin`, `user` ან `viewer`. იდენტობის პროვაიდერი, რომელიც რამდენიმე მნიშვნელობას აგზავნის, იღებს მათ შორის ყველაზე მაღალი პრივილეგიის მქონეს, სადაც `admin` უფრო მაღალია ვიდრე `user` და `user` უფრო მაღალია ვიდრე `viewer`.

## მხარდაჭერილი SCIM ფუნქციები {#supported-scim-features}

Tuist მხარს უჭერს SCIM 2.0 ბოლოწერტილებს, რომლებიც იდენტობის პროვაიდერებს სჭირდებათ სიცოცხლის ციკლის მართვისთვის:

- `POST`, `GET`, `PUT`, `PATCH` და `DELETE` `/Users`-ისთვის.
- `GET` და `PATCH` `/Groups`-ისთვის.
- SCIM აღმოჩენის ბოლოწერტილები `/ServiceProviderConfig`, `/ResourceTypes` და `/Schemas`-ისთვის.
