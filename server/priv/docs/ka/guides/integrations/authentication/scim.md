# SCIM პროვიზინგი {#scim-provisioning}

Tuist მხარდაჭერს SCIM 2.0 პროვიზინგს, რათა იდენტობის პროვაიდერმა შეძლოს ორგანიზაციის წევრების ავტომატური შექმნა, განახლება და დეპროვიზინგი.

SCIM კონფიგურირდება თქვენი ორგანიზაციის პარამეტრებში **Authentication** ჩანართიდან. SCIM ტოკენი არის ორგანიზაციის საკუთრებაში არსებული ანგარიშის ტოკენი, რომელიც შეზღუდულია SCIM წვდომით და გამოჩნდება მხოლოდ ერთხელ გენერაციისას.

> [!NOTE]
> SCIM აკონტროლებს წევრობას და სიცოცხლის ციკლს. ის არ ცვლის <.localized_link href="/guides/integrations/authentication/sso">Single Sign-On</.localized_link>. კონფიგურირეთ SSO ცალკე, თუ პროვიზირებულ მომხმარებლებს ასევე უნდა შეეძლოთ შესვლა თქვენი იდენტობის პროვაიდერის მეშვეობით.

პროვიზირებული მომხმარებლები უკვე არიან ორგანიზაციის წევრები. როდესაც ისინი შედიან იმავე ელფოსტის მისამართით, ეს წევრობა შეუძლია დაამყაროს ნდობა მათი პროვაიდერის იდენტობის დასაკავშირებლად. <.localized_link href="/guides/integrations/authentication/sso#verify-a-login-email-domain">verified login email domain</.localized_link> და <.localized_link href="/guides/integrations/authentication/sso#choose-an-enrollment-policy">enrollment policy</.localized_link> აკონტროლებენ მომხმარებლებს, რომლებიც ჯერ არ არიან პროვიზირებული ან დამატებული ორგანიზაციაში.

## Okta {#okta}

Okta Tuist-ისთვის იყენებს ორ ცალკეულ აპლიკაციას:

- **OIDC Web Application** Tuist-ში შესასვლელად.
- **SCIM 2.0 Test App (Header Auth)** აპლიკაცია მომხმარებლებისა და ჯგუფების Tuist-ში პროვიზინგისთვის.

კონფიგურირეთ <.localized_link href="/guides/integrations/authentication/sso#okta">Okta SSO</.localized_link> ჯერ, თუ მომხმარებლებმა უნდა შეძლონ Okta-ს მეშვეობით შესვლა, შემდეგ კი კონფიგურირეთ SCIM პროვიზინგი ქვემოთ მოცემული ნაბიჯებით.

### ნაბიჯი 1: Tuist SCIM ტოკენის გენერაცია {#okta-step-1}

1. Tuist-ში გადადით თქვენი ორგანიზაციის **Authentication** პარამეტრების ჩანართზე.
2. **SCIM provisioning** სექციაში დააკოპირეთ **SCIM endpoint URL**. ის უნდა მთავრდებოდეს `/scim/v2`-ით.
3. დააწკაპუნეთ **Generate token**.
4. მიანიჭეთ ტოკენს სახელი (მაგალითად, `Okta`).
5. დააკოპირეთ გენერირებული ტოკენი. Tuist ტოკენს აჩვენებს მხოლოდ ერთხელ.

### ნაბიჯი 2: Okta SCIM აპლიკაციის დამატება {#okta-step-2}

1. თქვენს Okta ადმინისტრატორის დაფაზე გადადით **Applications > Applications > Browse App Catalog**.
2. მოძებნეთ და დაამატეთ **SCIM 2.0 Test App (Header Auth)**.
3. მიანიჭეთ მას რაიმე ამოსაცნობი სახელი, მაგალითად `Tuist SCIM`.
4. შეავსეთ შესვლის პარამეტრები SCIM სატესტო აპლიკაციისთვის. Tuist არ იყენებს ამ აპლიკაციას შესასვლელად; შესვლას ამუშავებს OIDC აპლიკაცია SSO სახელმძღვანელოდან.

### ნაბიჯი 3: API ინტეგრაციის კონფიგურაცია {#okta-step-3}

1. გახსენით SCIM აპლიკაციის **Provisioning** ჩანართი.
2. **Settings > Integration** ქვეშ დააწკაპუნეთ **Configure API Integration** ან **Edit**.
3. აირჩიეთ **Enable API integration**.
4. ჩასვით Tuist-ის **SCIM endpoint URL** Okta-ს **Base URL** ველში.
5. ჩასვით Tuist SCIM ტოკენი **API Token**-ში, პრეფიქსით `Bearer `. მაგალითად, `Bearer tuist_scim_...`. Okta ამ ველს აგზავნის როგორც `Authorization` ჰედერს, ხოლო Tuist ელის bearer ტოკენს.
6. ჩართეთ **Import Groups**, თუ გსურთ, რომ Okta-მ წაიკითხოს Tuist-ის SCIM ჯგუფები.
7. დააწკაპუნეთ **Test API Credentials**. Okta უნდა აჩვენოს, რომ ინტეგრაცია წარმატებით დადასტურდა.
8. დააწკაპუნეთ **Save**.

### ნაბიჯი 4: პროვიზინგის მოქმედებების ჩართვა {#okta-step-4}

1. SCIM აპლიკაციის **Provisioning** ჩანართში გახსენით **Settings > To App**.
2. დააწკაპუნეთ **Edit**.
3. ჩართეთ:
   - **Create Users**
   - **Update User Attributes**
   - **Deactivate Users**
4. დააწკაპუნეთ **Save**.

### ნაბიჯი 5: მომხმარებლების ან ჯგუფების მინიჭება {#okta-step-5}

1. გახსენით SCIM აპლიკაციის **Assignments** ჩანართი.
2. მიანიჭეთ ის მომხმარებლები ან ჯგუფები, რომლებიც Tuist-ში უნდა დაპროვიზირდეს.
3. მიანიჭეთ იგივე მომხმარებლები ან ჯგუფები Okta OIDC აპლიკაციას, თუ მათ ასევე SSO-ით შესვლა უნდა შეეძლოთ.
4. შეამოწმეთ Tuist-ის **Members** ჩანართი, რათა დარწმუნდეთ, რომ მინიჭებული მომხმარებლები ორგანიზაციაში ჩანს.

დეპროვიზინგის შესამოწმებლად, გააუქმეთ ან გაააქტიურეთ მომხმარებელი Okta-ში და დარწმუნდით, რომ ის ქრება Tuist ორგანიზაციის **Members** ჩანართიდან.

### როლების მინიჭება {#okta-assigning-roles}

Tuist-ს აქვს სამი <.localized_link href="/guides/server/accounts-and-projects#roles">როლი</.localized_link>: `admin`, `user` და `viewer`. Tuist თითოეული როლისთვის ერთ SCIM ჯგუფს აჩენს: `Tuist Admins`, `Tuist Users` და `Tuist Viewers`. მიამაგრეთ Okta ჯგუფები მათთან **Group Push**-ის საშუალებით:

1. აირჩიეთ ან შექმენით Okta ჯგუფი თითოეული მინიჭებადი როლისთვის და მიანიჭეთ ეს ჯგუფები SCIM აპლიკაციის **Assignments** ჩანართში.
2. დარწმუნდით, რომ API ინტეგრაციაში ჩართულია **Import Groups**, შემდეგ გახსენით SCIM აპლიკაციის **Import** ჩანართი და დააწკაპუნეთ **Import Now**, რათა Okta-მ იცოდეს Tuist-ის ჯგუფების შესახებ.
3. გახსენით SCIM აპლიკაციის **Push Groups** ჩანართი და დააწკაპუნეთ **Push Groups > Find groups by name**.
4. აირჩიეთ Okta ჯგუფი, აირჩიეთ **Link Group** როგორც push მოქმედება და აირჩიეთ შესაბამისი Tuist ჯგუფი. Tuist არ უჭერს მხარს ჯგუფების შექმნას SCIM-ის საშუალებით, ამიტომ დააკავშირეთ არსებულ ჯგუფთან ახლის შექმნის ნაცვლად.
5. დააწკაპუნეთ **Save** და გაიმეორეთ დარჩენილი როლებისთვის.

მომხმარებლის დამატება დაკავშირებულ ჯგუფში ანიჭებს მას ამ როლს. მისი ჯგუფიდან წაშლა აბრუნებს მას იმ როლზე, რომელზეც ორგანიზაცია აერთიანებს single sign-on მომხმარებლებს, რაც არის `user`, თუ ადმინისტრატორმა არ შეცვალა ის **Settings > Authentication** პარამეტრებში. მომხმარებლები, რომლებიც არცერთ დაკავშირებულ ჯგუფში არ არიან, ასევე იღებენ ამ როლს. მომხმარებლის ჯგუფიდან წაშლა არ შლის მას ორგანიზაციიდან; ამისთვის გააუქმეთ ან გაააქტიურეთ ის Okta-ში.

## Microsoft Entra ID {#microsoft-entra-id}

Entra ID ახდენს Tuist-ის პროვიზინგს არა-გალერეის საწარმო აპლიკაციის საშუალებით. კონფიგურაცია <.localized_link href="/guides/integrations/authentication/sso#microsoft-entra-id">Microsoft Entra ID SSO</.localized_link> ჯერ, თუ მომხმარებლებს ასევე Entra ID-ით შესვლა უნდა შეეძლოთ.

აპლიკაცია, რომელსაც single sign-on-ისთვის აირეგისტრირებთ და საწარმო აპლიკაცია, რომელსაც პროვიზინგისთვის იყენებთ, შეიძლება იყოს ერთი და იგივე. პროვიზინგი კონფიგურირდება საწარმო აპლიკაციის ჩანაწერზე.

### ნაბიჯი 1: Tuist SCIM ტოკენის გენერირება {#entra-step-1}

1. Tuist-ში გადადით თქვენი ორგანიზაციის **Authentication** პარამეტრების ჩანართზე.
2. **SCIM provisioning** სექციაში დააკოპირეთ **SCIM endpoint URL**. ის უნდა მთავრდებოდეს `/scim/v2`-ით.
3. დააწკაპუნეთ **Generate token**.
4. მიანიჭეთ ტოკენს სახელი (მაგალითად, `Entra ID`).
5. დააკოპირეთ გენერირებული ტოკენი. Tuist ტოკენს მხოლოდ ერთხელ აჩვენებს.

### ნაბიჯი 2: პროვიზინგის კონფიგურაცია {#entra-step-2}

1. Microsoft Entra admin center-ში გადადით **Identity > Applications > Enterprise applications** და გახსენით Tuist აპლიკაცია.
2. გახსენით **Provisioning** და დააყენეთ **Provisioning Mode** მნიშვნელობაზე **Automatic**.
3. დააყენეთ **Tenant URL** Tuist SCIM endpoint URL-ზე.
4. დააყენეთ **Secret Token** Tuist SCIM ტოკენზე. შეიყვანეთ ტოკენი ცალკე, `Bearer ` პრეფიქსის გარეშე; Entra ID თავად ამატებს სქემას.
5. დააწკაპუნეთ **Test Connection**. Entra ID უნდა აჩვენოს, რომ მიწოდებული სერთიფიკატები ავტორიზებულია.
6. შეინახეთ კონფიგურაცია.

### ნაბიჯი 3: შესაბამისობის ატრიბუტის დაყენება {#entra-step-3}

1. **Mappings** ქვეშ გახსენით **Provision Microsoft Entra ID Users**.
2. დაადასტურეთ, რომ `userPrincipalName` ან `mail` შეესაბამება SCIM `userName` ატრიბუტს და რომ ეს ატრიბუტი გამოიყენება **Matching precedence 1**-ისთვის.
3. წაშალეთ `externalId` შესაბამისობის ატრიბუტებიდან, თუ ის არსებობს.

Tuist ახდენს დაპროვიზირებული მომხმარებლების შესაბამისობას `userName`-ით. ის არ ინახავს დირექტორიის ობიექტის იდენტიფიკატორს, რომელსაც Entra ID აგზავნის როგორც `externalId`, ამიტომ ფილტრი ამ ატრიბუტზე ვერ პოულობს არსებულ წევრს და პროვიზინგის ციკლებმა შეიძლება არაპროგნოზირებადად იმოქმედონ.

### ნაბიჯი 4: ჯგუფის პროვიზინგის გამორთვა {#entra-step-4}

**Mappings** ქვეშ დააყენეთ **Provision Microsoft Entra ID Groups** გამორთულ მდგომარეობაზე.

Tuist-ის SCIM ჯგუფები არის ფიქსირებული ჯგუფი თითოეული ორგანიზაციის როლისთვის და არა დირექტორიის ჯგუფები, რომელთა შექმნაც შეგიძლიათ, ამიტომ დირექტორიის ჯგუფის პროვიზინგის მცდელობა ვერ ხერხდება. ნაცვლად ამისა, მიანიჭეთ როლები ქვემოთ აღწერილი წესით.

### ნაბიჯი 5: მომხმარებლების მინიჭება და პროვიზინგის დაწყება {#entra-step-5}

1. გახსენით აპლიკაციის **Users and groups** ჩანართი და მიანიჭეთ მომხმარებლები ან ჯგუფები, რომლებიც Tuist-ში უნდა დაპროვიზირდეს.
2. დაბრუნდით **Provisioning**-ზე და დაიწყეთ ის.
3. შეამოწმეთ Tuist-ის **Members** ჩანართი, რათა დარწმუნდეთ, რომ მინიჭებული მომხმარებლები ორგანიზაციაში ჩანს.

Entra ID ახდენს პროვიზინგს საკუთარი გრაფიკით, რაც ჩვეულებრივ ყოველ 40 წუთში ხდება, ამიტომ წევრები მყისიერად არ ჩნდებიან. ერთი მომხმარებლის დაუყოვნებლივ შესამოწმებლად გამოიყენეთ **Provision on demand**.

დეპროვიზინგის შესამოწმებლად, გააუქმეთ ან გამორთეთ მომხმარებელი Entra ID-ში და დარწმუნდით, რომ ის ქრება Tuist ორგანიზაციის **Members** ჩანართიდან.

თუ მოგვიანებით შეცვლით პროვიზინგის სფეროს, მაგალითად, **Sync all users and groups**-დან **Sync only assigned users and groups**-ზე, შემდეგ დააჭირეთ **Restart provisioning**. Entra ID ახალ სფეროს, მათ შორის იმ მომხმარებლების დეპროვიზინგს, რომლებიც აღარ არიან მასში, მხოლოდ გადატვირთვის შემდეგ გამოიყენებს.

### როლების მინიჭება {#entra-assigning-administrators}

Tuist-ს აქვს სამი <.localized_link href="/guides/server/accounts-and-projects#roles">როლი</.localized_link>: `admin`, `user` და `viewer`. მათი Entra ID-დან დასაყენებლად:

1. **App registrations**-ში გახსენით Tuist აპლიკაცია და დაამატეთ აპლიკაციის როლი თითოეული Tuist როლისთვის, რომლის მინიჭებაც გსურთ. დააყენეთ **Allowed member types** მნიშვნელობაზე **Users/Groups** და **Value** — `admin`, `user` ან `viewer`.
2. საწარმო აპლიკაციის **Users and groups** ჩანართზე მიანიჭეთ თითოეულ მომხმარებელს ან ჯგუფს ერთ-ერთი ამ აპლიკაციის როლი. მომხმარებელს შეიძლება ჰქონდეს რამდენიმე აპლიკაციის როლი. Tuist იყენებს ყველაზე მაღალი პრივილეგიის მქონე როლს, სადაც `admin` უპირატესია `user`-ზე და `user` უპირატესია `viewer`-ზე, ამიტომ მომხმარებელი, რომელიც სხვადასხვა როლზე ასახულ ჯგუფებს ეკუთვნის, იღებს მათ შორის უმაღლესს.
3. **Provisioning > Mappings** ქვეშ გახსენით **Advanced Options** ჩამოსაშლელი მენიუ და აირჩიეთ **Edit target User attributes**. დაამატეთ ატრიბუტი სახელით `roles`, სადაც **Type** დაყენებულია `String`-ზე და **Multi-Value** მონიშნულია.
4. **Provisioning > Mappings > Provision Microsoft Entra ID Users** ქვეშ დააჭირეთ **Add New Mapping**. დააყენეთ **Mapping type** მნიშვნელობაზე **Expression**, **Expression** — `AssertiveAppRoleAssignmentsComplex([appRoleAssignments])`-ზე და **Target attribute** — თქვენს მიერ დამატებულ `roles` ატრიბუტზე.
5. დატოვეთ პროვიზინგის სფერო დაყენებული **Sync only assigned users and groups**-ზე. `AssertiveAppRoleAssignmentsComplex` არ არის თავსებადი **Sync all users and groups**-თან.

`AssertiveAppRoleAssignmentsComplex` აგზავნის ყველა აპლიკაციის როლს, რომელიც მომხმარებელს აქვს, ასევე აგზავნის წაშლებს, ამიტომ როლის წართმევა Entra ID-ში ამცირებს მომხმარებლის პრივილეგიებს მათ შორის დარჩენილ ყველაზე მაღალ როლამდე. `SingleAppRoleAssignment([appRoleAssignments])`, ასახული `roles[primary eq "True"].value`-ზე, ასევე მუშაობს, მაგრამ ის ყოველთვის მხოლოდ ერთ როლს აგზავნის და Entra ID არ იძლევა გარანტიას, თუ რომელს აირჩევს, როდესაც მომხმარებელს რამდენიმე როლი აქვს.

მომხმარებლის აპლიკაციის როლების შეცვლა Entra ID-ში ანახლებს მათ Tuist როლს შემდეგი პროვიზინგის ციკლზე. მომხმარებელი, რომელიც დაპროვიზირდა აპლიკაციის როლის გარეშე ან `admin`, `user` ან `viewer`-ისგან განსხვავებული მნიშვნელობებით, იღებს როლს, რომლითაც ორგანიზაცია აფორმებს ერთჯერადი შესვლის (SSO) წევრებს, რაც არის `user`, თუ ადმინისტრატორმა არ შეცვალა ეს **Settings > Authentication**-ში.

## სიცოცხლის ციკლის ქცევა {#lifecycle-behavior}

როდესაც თქვენი იდენტობის პროვაიდერი (IdP) ანიჭებს მომხმარებელს პროვიზინგის აპლიკაციას, Tuist ქმნის მომხმარებელს, თუ ელფოსტა ჯერ არ არის ცნობილი Tuist-ისთვის, შემდეგ კი ამატებს მას ორგანიზაციაში. თუ ელფოსტა უკვე ეკუთვნის არსებულ Tuist მომხმარებელს ორგანიზაციის გარეთ, Tuist უარყოფს მოთხოვნას, რათა ხელი შეუშალოს IdP-ს მოითხოვოს მომხმარებელი, რომელსაც ის ამ ორგანიზაციაში ჯერ არ მართავს.

როდესაც თქვენი იდენტობის პროვაიდერი აუქმებს ან თიშავს მომხმარებელს, Tuist აშორებს მათ ორგანიზაციის როლს, ინარჩუნებს მომხმარებლის ჩანაწერს და ნებისმიერ მათ მიერ შესრულებულ სამუშაოს. დეპროვიზინგი არ თიშავს მომხმარებელს გლობალურად, რადგან იგივე Tuist მომხმარებელი შეიძლება ეკუთვნოდეს სხვა ორგანიზაციებს.

Tuist წარმოადგენს სამ სინთეზურ SCIM ჯგუფს: `Tuist Admins`, `Tuist Users` და `Tuist Viewers`. ჯგუფში წევრის დამატება აყენებს მათ ორგანიზაციის როლს. წევრის წაშლა ჯგუფიდან, რომელიც შეესაბამება მათ მიმდინარე როლს, აბრუნებს მათ დარეგისტრირების როლზე, ხოლო წევრობა მთავრდება მხოლოდ მაშინ, როდესაც მომხმარებელი გაუქმებულია ან გამორთული. იდენტობის პროვაიდერებს ასევე შეუძლიათ დააყენონ როლი SCIM `roles` ატრიბუტის მეშვეობით მომხმარებელზე, მნიშვნელობით `admin`, `user` ან `viewer`. იდენტობის პროვაიდერი, რომელიც აგზავნის რამდენიმე მნიშვნელობას, იღებს მათ შორის ყველაზე მაღალი პრივილეგიის მქონეს, სადაც `admin` უპირატესია `user`-ზე და `user` უპირატესია `viewer`-ზე.

## მხარდაჭერილი SCIM ფუნქციები {#supported-scim-features}

Tuist მხარს უჭერს SCIM 2.0 ბოლოწერტილებს, რომლებიც იდენტობის პროვაიდერებს სჭირდებათ სიცოცხლის ციკლის მართვისთვის:

- `POST`, `GET`, `PUT`, `PATCH` და `DELETE` `/Users`-ისთვის.
- `GET` და `PATCH` `/Groups`-ისთვის.
- SCIM აღმოჩენის ბოლოწერტილები `/ServiceProviderConfig`, `/ResourceTypes` და `/Schemas`-ისთვის.
