# SCIM პროვიზირება {#scim-provisioning}

Tuist მხარდაჭერას უწევს SCIM 2.0 პროვიზირებას, რათა იდენტობის პროვაიდერმა ავტომატურად შექმნას, განაახლოს და გააუქმოს ორგანიზაციის წევრები.

SCIM კონფიგურირდება თქვენი ორგანიზაციის პარამეტრებში **Authentication** ჩანართიდან. SCIM ტოკენი არის ორგანიზაციის საკუთრებაში არსებული ანგარიშის ტოკენი, რომელიც შეზღუდულია SCIM წვდომით და გამოჩნდება მხოლოდ ერთხელ გენერაციისას.

> [!NOTE]
> SCIM აკონტროლებს წევრობას და სიცოცხლის ციკლს. ის არ ცვლის <.localized_link href="/guides/integrations/authentication/sso">Single Sign-On</.localized_link>-ს. კონფიგურაცია SSO-სთვის ცალკე გააკეთეთ, თუ პროვიზირებულ მომხმარებლებს ასევე უნდა შესძლებოდეთ შესვლა თქვენი იდენტობის პროვაიდერის მეშვეობით.

პროვიზირებული მომხმარებლები უკვე ორგანიზაციის წევრები არიან. როდესაც ისინი შედიან იგივე ელფოსტის მისამართით, ეს წევრობა შეიძლება გამოყენებულ იქნას ნდობის დასამყარებლად მათი პროვაიდერის იდენტობის დასაკავშირებლად. <.localized_link href="/guides/integrations/authentication/sso#verify-a-login-email-domain">verified login email domain</.localized_link> და <.localized_link href="/guides/integrations/authentication/sso#choose-an-enrollment-policy">enrollment policy</.localized_link> აკონტროლებენ მომხმარებლებს, რომლებიც ჯერ არ არიან პროვიზირებული ან დამატებული ორგანიზაციაში.

## Okta {#okta}

Okta Tuist-ისთვის იყენებს ორ ცალკეულ აპლიკაციას:

- **OIDC Web Application** Tuist-ში შესასვლელად.
- **SCIM 2.0 Test App (Header Auth)** აპლიკაცია მომხმარებლებისა და ჯგუფების Tuist-ში პროვიზირებისთვის.

ჯერ კონფიგურაცია გააკეთეთ <.localized_link href="/guides/integrations/authentication/sso#okta">Okta SSO</.localized_link>-სთვის, თუ მომხმარებლებმა Okta-ს მეშვეობით უნდა შეძლონ შესვლა, შემდეგ კი ქვემოთ მოცემული ნაბიჯებით დააკონფიგურიროთ SCIM პროვიზირება.

### ნაბიჯი 1: Tuist SCIM ტოკენის გენერირება {#okta-step-1}

1. Tuist-ში გადადით თქვენი ორგანიზაციის **Authentication** პარამეტრების ჩანართზე.
2. **SCIM provisioning** სექციაში დააკოპირეთ **SCIM endpoint URL**. ის უნდა მთავრდებოდეს `/scim/v2`-ით.
3. დააჭირეთ **Generate token**-ს.
4. მიანიჭეთ სახელი ტოკენს (მაგალითად, `Okta`).
5. დააკოპირეთ გენერირებული ტოკენი. Tuist ტოკენს აჩვენებს მხოლოდ ერთხელ.

### ნაბიჯი 2: Okta SCIM აპლიკაციის დამატება {#okta-step-2}

1. თქვენს Okta ადმინისტრატორის დაფაზე გადადით **Applications > Applications > Browse App Catalog**-ზე.
2. მოძებნეთ და დაამატეთ **SCIM 2.0 Test App (Header Auth)**.
3. მიანიჭეთ მას რაიმე ამოსაცნობი სახელი, მაგალითად `Tuist SCIM`.
4. შეავსეთ შესვლის პარამეტრები SCIM სატესტო აპლიკაციისთვის. Tuist ამ აპლიკაციას შესვლისთვის არ იყენებს; შესვლას მართავს OIDC აპლიკაცია SSO სახელმძღვანელოდან.

### ნაბიჯი 3: API ინტეგრაციის კონფიგურაცია {#okta-step-3}

1. გახსენით SCIM აპლიკაციის **Provisioning** ჩანართი.
2. **Settings > Integration** ქვეშ დააჭირეთ **Configure API Integration** ან **Edit**.
3. მონიშნეთ **Enable API integration**.
4. ჩასვით Tuist-ის **SCIM endpoint URL** Okta-ს **Base URL** ველში.
5. ჩასვით Tuist SCIM ტოკენი **API Token**-ში, პრეფიქსით `Bearer `. მაგალითად, `Bearer tuist_scim_...`. Okta ამ ველს გზავნის როგორც `Authorization` ჰედერს, ხოლო Tuist ელოდება bearer ტოკენს.
6. ჩართეთ **Import Groups**, თუ გსურთ, რომ Okta-მ წაიკითხოს Tuist-ის SCIM ჯგუფები.
7. დააჭირეთ **Test API Credentials**-ს. Okta უნდა აჩვენოს, რომ ინტეგრაცია წარმატებით დადასტურდა.
8. დააჭირეთ **Save**-ს.

### ნაბიჯი 4: პროვიზირების მოქმედებების ჩართვა {#okta-step-4}

1. SCIM აპლიკაციის **Provisioning** ჩანართში გახსენით **Settings > To App**.
2. დააჭირეთ **Edit**-ს.
3. ჩართეთ:
   - **Create Users**
   - **Update User Attributes**
   - **Deactivate Users**
4. დააჭირეთ **Save**-ს.

### ნაბიჯი 5: მომხმარებლების ან ჯგუფების მინიჭება {#okta-step-5}

1. გახსენით SCIM აპლიკაციის **Assignments** ჩანართი.
2. მინიჭეთ ის მომხმარებლები ან ჯგუფები, რომლებიც Tuist-ში უნდა პროვიზირდეს.
3. მიანიჭეთ იგივე მომხმარებლები ან ჯგუფები Okta OIDC აპლიკაციას, თუ მათ ასევე SSO-ით შესვლა უნდა შეეძლოთ.
4. შეამოწმეთ Tuist-ის **Members** ჩანართი, რათა დარწმუნდეთ, რომ მინიჭებული მომხმარებლები ორგანიზაციაში ჩანან.

დეპროვიზირების შესამოწმებლად, გააუქმეთ ან გააუქციეთ მომხმარებელი Okta-ში და დარწმუნდით, რომ ის ქრება Tuist ორგანიზაციის **Members** ჩანართიდან.

### როლების მინიჭება {#okta-assigning-roles}

Tuist-ს აქვს სამი <.localized_link href="/guides/server/accounts-and-projects#roles">როლი</.localized_link>: `admin`, `user` და `viewer`. Tuist თითოეული როლისთვის ერთ SCIM ჯგუფს წარმოადგენს: `Tuist Admins`, `Tuist Users` და `Tuist Viewers`. მიამაგრეთ Okta ჯგუფები მათ **Group Push**-ის საშუალებით:

1. აირჩიეთ ან შექმენით Okta ჯგუფი თითოეული მინიჭებადი როლისთვის და მიანიჭეთ ეს ჯგუფები SCIM აპლიკაციის **Assignments** ჩანართზე.
2. დარწმუნდით, რომ API ინტეგრაციაში ჩართულია **Import Groups**, შემდეგ გახსენით SCIM აპლიკაციის **Import** ჩანართი და დააჭირეთ **Import Now**-ს, რათა Okta-მ იცოდეს Tuist-ის ჯგუფების შესახებ.
3. გახსენით SCIM აპლიკაციის **Push Groups** ჩანართი და დააჭირეთ **Push Groups > Find groups by name**-ს.
4. აირჩიეთ Okta ჯგუფი, აირჩიეთ **Link Group** როგორც push-მოქმედება და აირჩიეთ შესაბამისი Tuist ჯგუფი. Tuist არ უჭერს მხარს ჯგუფების შექმნას SCIM-ის საშუალებით, ამიტომ ახლის შექმნის ნაცვლად დააკავშირეთ არსებულ ჯგუფთან.
5. დააჭირეთ **Save**-ს და გაიმეორეთ დარჩენილი როლებისთვის.

მომხმარებლის დაკავშირებულ ჯგუფში დამატება ანიჭებს მას ამ როლს. ჯგუფიდან მისი ამოღება აბრუნებს მას იმ როლზე, რომლითაც ორგანიზაცია აერთიანებს ერთჯერადი შესვლის (SSO) წევრებს, რაც არის `user`, თუ ადმინისტრატორმა არ შეცვალა ის **Settings > Authentication**-ში. მომხმარებლები, რომლებიც არცერთ დაკავშირებულ ჯგუფში არ არიან, ასევე იღებენ ამ როლს. მომხმარებლის ჯგუფიდან ამოღება არ შლის მას ორგანიზაციიდან; ამისთვის გააუქმეთ ან გააუქციეთ ის Okta-ში.

## Microsoft Entra ID {#microsoft-entra-id}

Entra ID ახორციელებს Tuist-ის პროვიზირებას არა-გალერეის საწარმო აპლიკაციის საშუალებით. ჯერ კონფიგურირეთ <.localized_link href="/guides/integrations/authentication/sso#microsoft-entra-id">Microsoft Entra ID SSO</.localized_link>, თუ მომხმარებლებს ასევე Entra ID-ით შესვლა უნდა შეეძლოთ.

აპლიკაცია, რომელსაც ერთჯერადი შესვლისთვის ადრეგისტრირებთ და საწარმო აპლიკაცია, რომელსაც პროვიზირებისთვის იყენებთ, შეიძლება ერთი და იგივე იყოს. პროვიზირება კონფიგურირდება საწარმო აპლიკაციის ჩანაწერზე.

### ნაბიჯი 1: Tuist SCIM ტოკენის გენერირება {#entra-step-1}

1. Tuist-ში გადადით თქვენი ორგანიზაციის **Authentication** პარამეტრების ჩანართზე.
2. **SCIM provisioning** სექციაში დააკოპირეთ **SCIM endpoint URL**. ის უნდა მთავრდებოდეს `/scim/v2`-ით.
3. დააჭირეთ **Generate token**-ს.
4. მიანიჭეთ სახელი ტოკენს (მაგალითად, `Entra ID`).
5. დააკოპირეთ გენერირებული ტოკენი. Tuist ტოკენს მხოლოდ ერთხელ აჩვენებს.

### ნაბიჯი 2: პროვიზირების კონფიგურაცია {#entra-step-2}

1. Microsoft Entra admin center-ში გადადით **Identity > Applications > Enterprise applications**-ზე და გახსენით Tuist აპლიკაცია.
2. გახსენით **Provisioning** და დააყენეთ **Provisioning Mode** მნიშვნელობაზე **Automatic**.
3. დააყენეთ **Tenant URL** Tuist SCIM ბოლოწერტილის URL-ზე.
4. დააყენეთ **Secret Token** Tuist SCIM ტოკენზე. შეიყვანეთ ტოკენი ცალკე, `Bearer ` პრეფიქსის გარეშე; Entra ID სქემას თავად დაამატებს.
5. დააჭირეთ **Test Connection**-ს. Entra ID უნდა აჩვენოს, რომ მიწოდებული სერთიფიკატები ავტორიზებულია.
6. შეინახეთ კონფიგურაცია.

### ნაბიჯი 3: შესაბამისობის ატრიბუტის დაყენება {#entra-step-3}

1. **Mappings**-ის ქვეშ გახსენით **Provision Microsoft Entra ID Users**.
2. დარწმუნდით, რომ `userPrincipalName` ან `mail` ასახავს SCIM `userName` ატრიბუტს და რომ ეს ატრიბუტი გამოიყენება **Matching precedence 1**-ისთვის.
3. ამოიღეთ `externalId` შესაბამისობის ატრიბუტებიდან, თუ ის არსებობს.

Tuist პროვიზირებულ მომხმარებლებს `userName`-ით ადარებს. ის არ ინახავს დირექტორიის ობიექტის იდენტიფიკატორს, რომელსაც Entra ID გზავნის როგორც `externalId`, ამიტომ ამ ატრიბუტზე ფილტრი არსებულ წევრს ვერ პოულობს და პროვიზირების ციკლებმა შეიძლება არაპროგნოზირებადად იმოქმედონ.

### ნაბიჯი 4: ჯგუფების პროვიზირების გამორთვა {#entra-step-4}

**Mappings**-ის ქვეშ, დააყენეთ **Provision Microsoft Entra ID Groups** გამორთულ მდგომარეობაზე.

Tuist-ის SCIM ჯგუფები არის ფიქსირებული ჯგუფი თითოეული ორგანიზაციის როლისთვის და არა დირექტორიის ჯგუფები, რომელთა შექმნაც შეგიძლიათ, ამიტომ დირექტორიის ჯგუფის პროვიზირების მცდელობა ვერ ხერხდება. ამის ნაცვლად მიანიჭეთ როლები ქვემოთ აღწერილი წესით.

### ნაბიჯი 5: მომხმარებლების მინიჭება და პროვიზირების დაწყება {#entra-step-5}

1. გახსენით აპლიკაციის **Users and groups** ჩანართი და მიანიჭეთ მომხმარებლები ან ჯგუფები, რომლებიც Tuist-ში უნდა პროვიზირდეს.
2. დაუბრუნდით **Provisioning**-ს და დაიწყეთ ის.
3. შეამოწმეთ Tuist-ის **Members** ჩანართი, რათა დარწმუნდეთ, რომ მინიჭებული მომხმარებლები ორგანიზაციაში ჩანან.

Entra ID პროვიზირებას ახორციელებს საკუთარი განრიგით, რაც ჩვეულებრივ ყოველ 40 წუთში ხდება, ამიტომ წევრები მყისიერად არ ჩანან. ერთი მომხმარებლის დაუყოვნებლივ შესამოწმებლად გამოიყენეთ **Provision on demand**.

პროვიზირების გაუქმების შესამოწმებლად, Entra ID-ში გააუქმეთ ან გამორთეთ მომხმარებელი და დარწმუნდით, რომ ის გაქრა Tuist ორგანიზაციის **Members** ჩანართიდან.

თუ მოგვიანებით შეცვლით პროვიზირების ფარგლებს, მაგალითად **Sync all users and groups**-დან **Sync only assigned users and groups**-ზე, შემდეგ დააჭირეთ **Restart provisioning**. Entra ID ახალ ფარგლებს, მათ შორის იმ მომხმარებლების პროვიზირების გაუქმებას, ვინც აღარ შედის მასში, მხოლოდ გადატვირთვის შემდეგ გამოიყენებს.

### როლების მინიჭება {#entra-assigning-administrators}

Tuist-ს აქვს სამი <.localized_link href="/guides/server/accounts-and-projects#roles">როლი</.localized_link>: `admin`, `user` და `viewer`. მათი Entra ID-დან დასაყენებლად:

1. **App registrations**-ში გახსენით Tuist აპლიკაცია და დაამატეთ აპლიკაციის როლი თითოეული Tuist როლისთვის, რომლის მინიჭებაც გსურთ. დააყენეთ **Allowed member types** მნიშვნელობაზე **Users/Groups** და **Value** — `admin`, `user` ან `viewer`.
2. საწარმო აპლიკაციის **Users and groups** ჩანართზე მიანიჭეთ თითოეულ მომხმარებელს ან ჯგუფს ერთ-ერთი ამ აპლიკაციის როლი. მომხმარებელს შეიძლება ჰქონდეს რამდენიმე აპლიკაციის როლი. Tuist იყენებს ყველაზე მაღალი პრივილეგიის მქონე როლს, სადაც `admin` უფრო მაღალია ვიდრე `user` და `user` უფრო მაღალია ვიდრე `viewer`, ამიტომ მომხმარებელი, რომელიც სხვადასხვა როლზე ასახულ ჯგუფებს ეკუთვნის, იღებს მათ შორის უმაღლესს.
3. **Provisioning > Mappings**-ის ქვეშ, გახსენით **Advanced Options** ჩამოსაშლელი მენიუ და აირჩიეთ **Edit target User attributes**. დაამატეთ ატრიბუტი სახელით `roles`, სადაც **Type** დაყენებულია `String`-ზე და **Multi-Value** მონიშნულია.
4. **Provisioning > Mappings > Provision Microsoft Entra ID Users**-ის ქვეშ, დააჭირეთ **Add New Mapping**. დააყენეთ **Mapping type** მნიშვნელობაზე **Expression**, **Expression** — `AssertiveAppRoleAssignmentsComplex([appRoleAssignments])`-ზე, ხოლო **Target attribute** — თქვენს მიერ დამატებულ `roles` ატრიბუტზე.
5. პროვიზირების ფარგლები დატოვეთ დაყენებული **Sync only assigned users and groups**-ზე. `AssertiveAppRoleAssignmentsComplex` არ არის თავსებადი **Sync all users and groups**-თან.

`AssertiveAppRoleAssignmentsComplex` გზავნის ყველა აპლიკაციის როლს, რომელიც მომხმარებელს აქვს, ასევე გზავნის წაშლებს, ამიტომ როლის წართმევა Entra ID-ში ამცირებს მომხმარებლის უფლებებს იმ ყველაზე მაღალ პრივილეგიურ როლამდე, რომელიც მას კვლავ აქვს. `SingleAppRoleAssignment([appRoleAssignments])`, რომელიც ასახულია `roles[primary eq "True"].value`-ზე, ასევე მუშაობს, მაგრამ ის ყოველთვის მხოლოდ ერთ როლს გზავნის და Entra ID არ იძლევა გარანტიას, თუ რომელს აირჩევს, როცა მომხმარებელს რამდენიმე როლი აქვს.

მომხმარებლის აპლიკაციის როლების შეცვლა Entra ID-ში აახლებს მათ Tuist როლს შემდეგი პროვიზირების ციკლის დროს. მომხმარებელი, რომელიც პროვიზირებულია აპლიკაციის როლის გარეშე ან `admin`, `user` ან `viewer`-ისგან განსხვავებული მნიშვნელობებით, იღებს იმ როლს, რომლითაც ორგანიზაცია აფორმებს ერთჯერადი შესვლის (SSO) წევრებს, რაც არის `user`, თუ ადმინისტრატორმა არ შეცვალა ეს **Settings > Authentication**-ში.

## სიცოცხლის ციკლის ქცევა {#lifecycle-behavior}

როდესაც თქვენი იდენტობის პროვაიდერი მომხმარებელს პროვიზირების აპლიკაციას მიაკუთვნებს, Tuist ქმნის მომხმარებელს, თუ ელფოსტა Tuist-ისთვის ჯერ არ არის ცნობილი, შემდეგ კი მას ორგანიზაციას უმატებს. თუ ელფოსტა უკვე ეკუთვნის არსებულ Tuist მომხმარებელს ორგანიზაციის გარეთ, Tuist ამ მომხმარებელს უმატებს და აგზავნის შეტყობინებას ამის შესახებ, თუ არა სხვა ორგანიზაციის SCIM ინტეგრაციამ შექმნა ანგარიში. ამ შემთხვევაში Tuist უარყოფს მოთხოვნას `409`-ით, რათა იდენტობის პროვაიდერმა ვერ მიისაკუთროს ანგარიში, რომელსაც სხვა ორგანიზაცია მართავს.

თქვენს იდენტობის პროვაიდერს შეუძლია შეცვალოს მომხმარებლის ელფოსტა (`userName`) მხოლოდ მაშინ, როცა თქვენი ორგანიზაცია ანგარიშს დამოუკიდებლად მართავს. ეს ნიშნავს, რომ Tuist-მა შექმნა ანგარიში თქვენი SCIM ინტეგრაციის მეშვეობით და ამის შემდეგ მომხმარებელს არ დაუყენებია პაროლი, არ შესულა პროვაიდერით, რომელიც განსხვავდება თქვენი ორგანიზაციის ერთჯერადი შესვლისგან, არ მოითხოვა აგენტის რეგისტრაცია ან არ შეუერთდა სხვა ორგანიზაციას. ნებისმიერი სხვა მომხმარებლისთვის Tuist უარყოფს ცვლილებას `400`-ით და `mutability` SCIM შეცდომის ტიპით. ის მაინც გამოიყენებს იმავე მოთხოვნაში გაგზავნილ დეაქტივაციას. Tuist ასევე უარს ამბობს მომხმარებლების შექმნაზე ან გადასახელებაზე შესვლის დომენში, რომელიც სხვა ორგანიზაციამ დაადასტურა, და tuist.dev-ზე, Tuist-ის საკუთარ დომენში. გადასახელება ასუფთავებს ჩანაწერს იმის შესახებ, რომ მომხმარებელმა დაადასტურა ძველი მისამართის კონტროლი.

როდესაც თქვენი იდენტობის პროვაიდერი მომხმარებელს აუქმებს ან დეაქტივირებს, Tuist აშორებს მათ ორგანიზაციის როლს, თუმცა ინარჩუნებს მომხმარებლის ჩანაწერს და მათ მიერ შესრულებულ ნამუშევარს. პროვიზირების გაუქმება არ თიშავს მომხმარებელს გლობალურად, რადგან იგივე Tuist მომხმარებელი შეიძლება ეკუთვნოდეს სხვა ორგანიზაციებს.

Tuist წარმოადგენს სამ სინთეზურ SCIM ჯგუფს: `Tuist Admins`, `Tuist Users` და `Tuist Viewers`. ჯგუფში წევრის დამატება აყენებს მათ ორგანიზაციის როლს. წევრის იმ ჯგუფიდან წაშლა, რომელიც შეესაბამება მათ ამჟამინდელ როლს, აბრუნებს მათ დარეგისტრირების როლზე, ხოლო წევრობა თავად მხოლოდ მაშინ სრულდება, როცა მომხმარებელი გაუქმებულია ან დეაქტივირებული. იდენტობის პროვაიდერებს ასევე შეუძლიათ დააყენონ როლი SCIM `roles` ატრიბუტის მეშვეობით მომხმარებელზე, მნიშვნელობით `admin`, `user` ან `viewer`. იდენტობის პროვაიდერი, რომელიც რამდენიმე მნიშვნელობას გზავნის, იღებს მათ შორის ყველაზე მაღალი პრივილეგიის მქონეს, სადაც `admin` უფრო მაღალია ვიდრე `user` და `user` უფრო მაღალია ვიდრე `viewer`.

## მხარდაჭერილი SCIM ფუნქციები {#supported-scim-features}

Tuist მხარს უჭერს SCIM 2.0 ბოლოწერტილებს, რომლებიც იდენტობის პროვაიდერებს სჭირდებათ სიცოცხლის ციკლის მართვისთვის:

- `POST`, `GET`, `PUT`, `PATCH` და `DELETE` `/Users`-ისთვის.
- `GET` და `PATCH` `/Groups`-ისთვის.
- SCIM აღმოჩენის ბოლოწერტილები `/ServiceProviderConfig`, `/ResourceTypes` და `/Schemas`-ისთვის.
