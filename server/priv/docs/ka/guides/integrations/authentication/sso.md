# ერთიანი შესვლა {#single-sign-on}

Tuist გთავაზობთ ერთიან შესვლას, როგორც შესვლის ვარიანტს, რათა უზრუნველყოს თქვენი ორგანიზაციის ანგარიშების დამატებითი უსაფრთხოება.

ერთიანი შესვლა კონფიგურირდება თქვენი ორგანიზაციის პარამეტრებში, **Authentication** ჩანართზე. მხარდაჭერილია Google Workspace, Okta, Microsoft Entra ID და მომხმარებლის მიერ მითითებული [OAuth 2.0](https://oauth.net/2/) პროვაიდერები.

Microsoft Entra ID არის OpenID Connect პროვაიდერი, რომელსაც Tuist აკონფიგურირებს თქვენი დირექტორიის იდენტიფიკატორის საფუძველზე. ამ სახელმძღვანელოში მომხმარებლისთვის მითითებული პროვაიდერებისთვის აღწერილი ყველა ნაბიჯი, მათ შორის ელფოსტის დომენის ვერიფიკაცია და რეგისტრაცია, მასზეც ვრცელდება.

> [!NOTE]
> ერთიანი შესვლა განსაზღვრავს, თუ როგორ ახდენენ წევრები ავთენტიფიკაციას და შეუძლიათ თუ არა ავთენტიფიცირებულ მომხმარებლებს ავტომატურად შეერთება. <.localized_link href="/guides/integrations/authentication/scim">System for Cross-domain Identity Management provisioning</.localized_link> განსაზღვრავს, შეუძლია თუ არა იდენტობის პროვაიდერს შექმნას, განაახლოს ან გააუქმოს ორგანიზაციის წევრობა. Okta-ს შემთხვევაში, უმეტესი ორგანიზაცია ორივეს აკონფიგურირებს.

## როგორ მუშაობს წვდომა {#how-access-works}

პროვაიდერის იდენტობა, შესვლის აღმოჩენა და ორგანიზაციაში რეგისტრაცია ცალ-ცალკე საკითხებია:

- **პროვაიდერის გამომცემელი:** პროვაიდერის ორგანიზაცია ან ავტორიზაციის სერვერი, რომელმაც მომხმარებელი დააავთენტურა. დაკავშირებული იდენტობის ძიებისას Tuist აერთიანებს პროვაიდერს, გამომცემელს და პროვაიდერის სტაბილურ მომხმარებლის იდენტიფიკატორს. Okta-სთვის გამომცემელი წარმოდგენილია Okta-ს დომენით. Microsoft Entra ID-სთვის ის გამოყვანილია დირექტორიის (არენდატორის) იდენტიფიკატორიდან. მომხმარებლისთვის მითითებული პროვაიდერისთვის ის წარმოდგენილია პროვაიდერის URL-ით.
- **შესვლის ელფოსტის დომენი:** ელფოსტის დომენი, რომელსაც Tuist იყენებს Okta-ს ან მომხმარებლისთვის მითითებული პროვაიდერის აღმოსაჩენად ზოგადი შესვლის გვერდიდან. ვერიფიკაციის შემდეგ, ის ასევე განსაზღვრავს, რომელი ელფოსტის მისამართების მიმართ იქნება ნდობა ახალი ანგარიშების დაკავშირებისა და ავტომატური რეგისტრაციისთვის.
- **რეგისტრაციის პოლიტიკა:** განსაზღვრავს, სჭირდება თუ არა ნდობის დომენიდან მომხმარებელს მიწვევა, ან შეუძლია თუ არა მას ავტომატურად შეერთება.
- **Provisioning:** ქმნის და მართავს ორგანიზაციის წევრობას შესვლის პროცესისგან დამოუკიდებლად.

პროვაიდერის გამომცემელი და შესვლის ელფოსტის დომენი ხშირად განსხვავდება. მაგალითად, კომპანიამ შეიძლება გამოიყენოს `example.com` თანამშრომლების ელფოსტისთვის, ხოლო მისი პროვაიდერის გამომცემელი იყოს `https://login.vendor.example.net`. ახალი Okta-ს და მომხმარებლისთვის მითითებული პროვაიდერის კონფიგურაციები ამ მნიშვნელობებს ცალ-ცალკე ინახავს.

### შესვლის ელფოსტის დომენის ვერიფიკაცია {#verify-a-login-email-domain}

Okta-ს და მომხმარებლისთვის მითითებული პროვაიდერის კონფიგურაციებს სჭირდებათ ვერიფიცირებული შესვლის ელფოსტის დომენი, სანამ შეძლებენ ახალი Tuist ანგარიშის შექმნას ან არსებული ანგარიშის დაკავშირებას მისი ელფოსტის მისამართით. წევრებს მაინც შეუძლიათ <.localized_link href="/guides/integrations/authentication/sso#link-an-existing-account">დააკავშირონ არსებული ანგარიში</.localized_link>, მაშინაც კი, თუ დომენი ჯერ ვერიფიცირებული არ არის.

1. შეიყვანეთ თანამშრომლების ელფოსტის დომენი, მაგალითად `example.com`, ველში **Login email domain**.
2. შეინახეთ ერთიანი შესვლის კონფიგურაცია.
3. დაამატეთ Tuist-ის მიერ ნაჩვენები ტექსტური ჩანაწერი დომენის [Domain Name System](https://www.cloudflare.com/learning/dns/dns-records/dns-txt-record/) კონფიგურაციაში.
4. დაუბრუნდით Authentication პარამეტრებს და დააჭირეთ **Verify domain**.

ვერიფიცირებული შესვლის ელფოსტის დომენი შეიძლება ეკუთვნოდეს მხოლოდ ერთ Tuist ორგანიზაციას. დომენის შეცვლა ასუფთავებს მის ვერიფიკაციას და მოითხოვს ახალი ტექსტური ჩანაწერის გამოქვეყნებას. ავტომატური რეგისტრაცია დარჩება შეჩერებული, სანამ დომენი არ ვერიფიცირდება.

Tuist ყოველდღიურად ამოწმებს ტექსტურ ჩანაწერს. ჩანაწერი, რომლის გარჩევაც შეწყდა, არ ასუფთავებს ვერიფიკაციას მაშინვე: დომენი ინარჩუნებს მას 14 დღის განმავლობაში, ხოლო Authentication პარამეტრები აჩვენებს **Verification expiring**-ს იმ ჩანაწერთან ერთად, რომელიც ხელახლა უნდა გამოქვეყნდეს. ჩანაწერის გამოქვეყნება და ვერიფიკაცია ასუფთავებს გაფრთხილებას. დომენი, რომლის ჩანაწერიც 14 დღის შემდეგაც კი არ არის, ბრუნდება არავერიფიცირებულ მდგომარეობაში და პროვაიდერის აღმოჩენა, იდენტობის დაკავშირება და ავტომატური რეგისტრაცია ჩერდება, სანამ ის ხელახლა არ ვერიფიცირდება. სხვა მიზეზით ვერ მოხერხებული ძიება არ ანახლებს ტაიმერს და არ ასუფთავებს ვერიფიკაციას თავისთავად. დომენები, რომლებიც ვერიფიცირდა ყოველდღიური ხელახალი შემოწმებების შემოღებამდე, არ მოწმდება ხელახლა.

Google Workspace-ს არ სჭირდება ეს ცალკეული Tuist ვერიფიკაციის ნაბიჯი, რადგან Google აწვდის ვერიფიცირებულ Workspace დომენს ავთენტიფიცირებული იდენტობის ნაწილად.

### აირჩიეთ რეგისტრაციის პოლიტიკა {#choose-an-enrollment-policy}

Tuist მხარდაჭერს რეგისტრაციის ორ პოლიტიკას:

- **მხოლოდ მიწვევით:** მომხმარებელს სჭირდება ორგანიზაციის მიწვევა. Okta-ს და მომხმარებლისთვის მითითებული პროვაიდერებისთვის, შესვლის ელფოსტის დომენი მაინც უნდა იყოს ვერიფიცირებული, სანამ პროვაიდერი შეძლებს სრულიად ახალი Tuist ანგარიშის შექმნას. მიწვეულ მომხმარებელს, რომელსაც უკვე აქვს Tuist ანგარიში, ჯერ უნდა მიიღოს მიწვევა, შემდეგ კი დააკავშიროს პროვაიდერის იდენტობა, როგორც ეს აღწერილია <.localized_link href="/guides/integrations/authentication/sso#link-an-existing-account">Link an existing Tuist account</.localized_link>-ში.
- **ავტომატური:** მომხმარებელს, რომლის ავთენტიფიცირებული ელფოსტაც ემთხვევა ნდობის დომენს, შეუძლია შექმნას ან დააკავშიროს ანგარიში და შეუერთდეს ორგანიზაციას მიწვევის გარეშე. Google კონფიგურაციები იყენებენ Workspace დომენს. Okta-ს და მომხმარებლისთვის მითითებული პროვაიდერები მოითხოვენ ვერიფიცირებულ შესვლის ელფოსტის დომენს.

Google კონფიგურაციების ნაგულისხმევი რეჟიმია ავტომატური რეგისტრაცია. ახალი Okta-ს და მომხმარებლისთვის მითითებული პროვაიდერის კონფიგურაციების ნაგულისხმევი რეჟიმია მხოლოდ მიწვევით რეგისტრაცია.

**Enforce single sign-on** პარამეტრი დამოუკიდებელია რეგისტრაციისგან. ორგანიზაციის დაცულ ბრაუზერის გვერდებზე წვდომა მოითხოვს სესიას, რომელიც ავთენტიფიცირებულია მისი მიმდინარე პროვაიდერისა და გამომცემლის მეშვეობით (ან ვერიფიცირებული Google Workspace-ის). ისტორიულად დაკავშირებული იდენტობა ან სხვა ორგანიზაციის პროვაიდერით ავთენტიფიკაცია არასაკმარისია. Tuist-ში ჩვეულებრივი შესვლა და სხვა ანგარიშებზე წვდომა რჩება ხელმისაწვდომი; აღსრულება არ ანიჭებს ორგანიზაციის წევრობას. ანონიმურ საჯარო დაფებსა და დროში შეზღუდულ ოპერატორის მხარდაჭერის გრანტებს რჩებათ თავიანთი ცალკეული წვდომის წესები. აპლიკაციის გადახედვის გვერდები აღსრულებას ავრცელებენ მხოლოდ ორგანიზაციის წევრებზე, ამიტომ ორგანიზაციის გარეთ გაზიარებული გადახედვის ბმულები კვლავ მუშაობენ იმ ვიზიტორებისთვის, ვისაც უკვე შეეძლო მათი გახსნა.

აღსრულება ვრცელდება ყველგან, სადაც წევრის სესია ეხება ორგანიზაციას:

- **Dashboard**: ორგანიზაციის გვერდები და ინსტრუმენტები, რომლებსაც ისინი სთავაზობენ ბრაუზერის აგენტებს <.localized_link href="/guides/features/agentic-coding/mcp#webmcp">WebMCP</.localized_link>-ის მეშვეობით, მოითხოვენ სესიას, რომელიც შესულია ორგანიზაციის პროვაიდერით.
- **Tuist CLI, Tuist აპლიკაცია, MCP კლიენტები და API ცნობარი**: მათში შესვლა ქმნის სერთიფიკატს, რომელიც წევრის სახელით მოქმედებს ყველა ორგანიზაციაში, ამიტომ ის მოითხოვს სესიას, რომელიც შესულია იმ ორგანიზაციის მეშვეობით, რომელიც აღასრულებს ერთჯერად შესვლას. Tuist პირველ რიგში პროვაიდერზე გადამისამართებს წევრს, რომელიც სხვა გზით შევიდა, და უარყოფს შესვლას ელფოსტითა და პაროლით ან Apple-ით. ყოველ ჯერზე, როდესაც ამ კლიენტებიდან ერთ-ერთი აახლებს თავის სერთიფიკატს, Tuist ხელახლა ამოწმებს. ორგანიზაციის ერთჯერადი შესვლის მეშვეობით მიღებული სერთიფიკატი განაგრძობს განახლებას; ასევე განაგრძობს განახლებას სხვა გზით მიღებული სერთიფიკატიც, თუ წევრი ადრე შესული იყო ორგანიზაციის პროვაიდერით. ნებისმიერი სხვა სერთიფიკატი, მაგალითად, წევრის მიერ პაროლით მიღებული სერთიფიკატი ორგანიზაციის ერთჯერადი შესვლის აღსრულებამდე, განაგრძობს განახლებას აღსრულების პირობებში პირველი განახლებიდან ოთხი კვირის განმავლობაში; ამის შემდეგ კლიენტი სთხოვს წევრს ხელახლა შესვლას. ამ დროის განმავლობაში პროვაიდერით შესვლა, დაფაზე ან `tuist auth login`-ის გამოყენებით, ინარჩუნებს მის განახლებას.

რამდენიმე ორგანიზაციის წევრი, რომლებიც აღასრულებენ ერთჯერად შესვლას, ვერ შევლენ CLI-ში, აპლიკაციაში ან MCP კლიენტებში, რადგან ერთი სესია ერთი ორგანიზაციის მეშვეობით შედის.

### აირჩიეთ როლი, რომელსაც მიიღებენ რეგისტრირებული წევრები {#choose-the-enrollment-role}

წევრები, რომლებიც ავტომატურად უერთდებიან, იღებენ <.localized_link href="/guides/server/accounts-and-projects#roles">როლს</.localized_link>, რომელიც დაყენებულია **Role for enrolled members** პარამეტრში, ეს არის `user`, თუ ადმინისტრატორი არ შეცვლის მას. მისი `viewer`-ზე დაყენება ხსნის შესვლას დირექტორიაში ყველასთვის, ყველასთვის ცვლილებების შეტანის შესაძლებლობის მიცემის გარეშე.

პარამეტრი ვერ დაყენდება `admin`-ზე, ვრცელდება <.localized_link href="/guides/integrations/authentication/scim">SCIM</.localized_link>-ის მეშვეობით როლის გარეშე მიწოდებულ წევრებზე, ასევე მათზე, ვინც შედის, და არასდროს გადაწერს ადმინისტრატორის მიერ ხელით დაყენებულ როლს.

### დააკავშირეთ არსებული Tuist ანგარიში {#link-an-existing-account}

დაკავშირებული პროვაიდერის იდენტობა შედის მთლიან Tuist ანგარიშში, მათ შორის ყველა სხვა ორგანიზაციაში, რომელსაც ანგარიში ეკუთვნის. Okta-სა და მორგებული პროვაიდერებისთვის, Tuist ავტომატურად აკავშირებს არსებულ ანგარიშს მხოლოდ მაშინ, როდესაც მისი ელფოსტის მისამართი ეკუთვნის ვერიფიცირებულ შესვლის ელფოსტის დომენს, ან როდესაც ორგანიზაციის SCIM მიწოდებამ შექმნა ანგარიში.

წევრები, რომელთა ანგარიში არ აკმაყოფილებს პირობებს, თავად აკავშირებენ იდენტობას:

1. შედით Tuist-ში ანგარიშის ჩვეულებრივი შესვლის მეთოდით.
2. გახსენით Tuist იდენტობის პროვაიდერიდან, მაგალითად, მისი აპლიკაციის ფილიდან, ან გახსენით ორგანიზაციის ერთ-ერთი პროექტი, თუ ის აღასრულებს ერთჯერად შესვლას.
3. დაადასტურეთ ორგანიზაცია და იდენტობის პროვაიდერის ანგარიში, რომელსაც Tuist აჩვენებს, შემდეგ დააჭირეთ **Link account**.

წევრს, რომელიც იწყებს ერთჯერად შესვლას გასვლის მდგომარეობაში, სთხოვენ ჯერ შესვლას, და Tuist შემდეგ ბრუნდება დადასტურებაზე. დაკავშირება არ არის დამოკიდებული დომენის ვერიფიკაციაზე, ამიტომ წევრებს შეუძლიათ გამოიყენონ ერთჯერადი შესვლა დომენის ვერიფიკაციამდე.

### არსებული ორგანიზაციები {#existing-organizations}

ყველა Okta და მორგებული პროვაიდერის ორგანიზაცია იყენებს ვერიფიცირებული დომენის მოდელს. დროებითი თავსებადობის რეჟიმი წაშლილია.

თუ თქვენი შესვლის ელფოსტის დომენი არ არის ვერიფიცირებული:

- არსებულმა დაკავშირებულმა წევრებმა შეიძლება განაგრძონ შესვლა, და არსებული SSO აღსრულება კვლავ ვრცელდება ორგანიზაციის წევრებზე.
- შესვლის გვერდი აღმოაჩენს თქვენს პროვაიდერს მხოლოდ არსებული ორგანიზაციის წევრობის მეშვეობით.
- ავტომატური რეგისტრაცია შეჩერებულია, და პროვაიდერს არ შეუძლია შექმნას ახალი Tuist ანგარიშები, მაშინაც კი, თუ მოწვევა არსებობს.
- დაუკავშირებელი წევრები შედიან თავიანთ არსებულ Tuist ანგარიშში და ადასტურებენ ბმულს ზემოთ აღწერილი წესით. ორგანიზაციის SCIM მიწოდებით შექმნილ ანგარიშებს კვლავ შეუძლიათ დაკავშირება პირველი SSO შესვლისას.
- ახალი რეგისტრაციები არ არიან ვალდებულნი გამოიყენონ თქვენი პროვაიდერი მხოლოდ იმიტომ, რომ მათი ელფოსტის მისამართი იყენებს თქვენს დომენს.

არსებული ჩართული რეგისტრაციისა და აღსრულების პარამეტრები რჩება შენახული და შეიძლება გაითიშოს. ადმინისტრატორებს შეუძლიათ შეცვალონ კონფიგურაცია, როდესაც დომენი არ არის ვერიფიცირებული; ნებისმიერი პარამეტრის ჩართვა მოითხოვს ვერიფიკაციას. ვერიფიკაცია აღადგენს ავტომატურ რეგისტრაციას შესაბამისი ელფოსტის მისამართებისთვის, როდესაც ეს პარამეტრი ჩართულია. Google Workspace-ის ქცევა უცვლელია.

თქვენი **Login email domain** შეიძლება უკვე იყოს შევსებული თქვენი ორგანიზაციის წევრების მონაცემებით. დაადასტურეთ მნიშვნელობა, გამოაქვეყნეთ ტექსტური ჩანაწერი და დააჭირეთ **Verify domain**. შეინარჩუნეთ ჩანაწერის გამოქვეყნება ყოველდღიური ხელახალი შემოწმებებისთვის.

## Google Workspace {#google}

Google Workspace ერთჯერადი შესვლა ავთენტიფიცირებს მომხმარებლებს Workspace დომენის მიმართ. ადმინისტრატორებს შეუძლიათ ნება დართონ შესაბამის მომხმარებლებს ავტომატურად შეერთება ან მოითხოვონ მოწვევა.

> [!NOTE]
> **Prerequisites**
>
> გჭირდებათ Google Workspace ორგანიზაცია ვერიფიცირებული დომენით. ასევე უნდა იყოთ ავთენტიფიცირებული Google-ით იმ ელფოსტით, რომელიც დაკავშირებულია იმ დომენთან, რომელსაც აყენებთ.

### მოწყობა {#google-setup}

1. გადადით თქვენი ორგანიზაციის **Authentication** პარამეტრების ჩანართზე.
2. ჩართეთ ერთჯერადი შესვლა.
3. აირჩიეთ **Google**, როგორც პროვაიდერი.
4. შეიყვანეთ თქვენი Google Workspace დომენი, მაგალითად `example.com`.
5. აირჩიეთ **Automatic enrollment** ან მხოლოდ მოწვევით რეგისტრაცია. Google-ისთვის ავტომატური რეგისტრაცია ნაგულისხმევად ჩართულია.
6. სურვილისამებრ ჩართეთ **Enforce single sign-on** შესვლის ნაკადის ტესტირების შემდეგ.
7. დააჭირეთ **Save changes**.

## Okta {#okta}

Okta იყენებს [OpenID Connect](https://openid.net/developers/how-connect-works/)-ს წევრების ავთენტიფიკაციისთვის. Okta დომენი განსაზღვრავს პროვაიდერის გამომცემელს; ცალკე ვერიფიცირებული შესვლის ელფოსტის დომენი აკონტროლებს აღმოჩენას, ახალი ანგარიშის დაკავშირებას და რეგისტრაციას.

თუ ასევე გსურთ, რომ Okta-მ ავტომატურად შექმნას, განაახლოს ან გააუქმოს წევრები, დააკონფიგურირეთ <.localized_link href="/guides/integrations/authentication/scim#okta">Okta System for Cross-domain Identity Management provisioning</.localized_link> ერთჯერადი შესვლის მუშაობის შემდეგ.

### ნაბიჯი 1: შექმენით Okta აპლიკაცია {#okta-step-1}

1. თქვენს Okta ადმინისტრატორის დაფაზე, გადადით **Applications > Applications > Create App Integration**.
2. აირჩიეთ **OpenID Connect** და **Web Application**.
3. დააყენეთ აპლიკაციის სახელი, მაგალითად `Tuist`. სურვილისამებრ ატვირთეთ [Tuist ლოგო](https://tuist.dev/images/tuist_dashboard.png).
4. დააყენეთ **Sign-in redirect URI** Authentication პარამეტრების გვერდზე ნაჩვენებ მნიშვნელობაზე, მაგალითად `https://tuist.dev/users/auth/okta/callback`.
5. **Assignments**-ის ქვეშ, აირჩიეთ სასურველი წვდომის კონტროლი და შეინახეთ.
6. დააკოპირეთ **Client ID** და **Client Secret** აპლიკაციის ზოგადი პარამეტრებიდან. ჩაინიშნეთ თქვენი **Okta domain**, მაგალითად `your-company.okta.com`.
7. სურვილისამებრ, Okta დაფიდან შესვლის დასაშვებად, დააჭირეთ **Edit** ზოგად პარამეტრებში, შეცვალეთ **Login initiated by** მნიშვნელობა **Either Okta or App**-ზე, აირჩიეთ **Display application icon to users** და დააყენეთ **Initiate login URI** Authentication პარამეტრების გვერდზე ნაჩვენებ მნიშვნელობაზე.

### ნაბიჯი 2: დააკონფიგურირეთ Tuist {#okta-step-2}

1. გადადით თქვენი ორგანიზაციის **Authentication** პარამეტრების ჩანართზე.
2. ჩართეთ ერთჯერადი შესვლა.
3. აირჩიეთ **Okta**, როგორც პროვაიდერი.
4. შეიყვანეთ **Okta domain**, **Client ID** და **Client Secret**.
5. შეიყვანეთ თანამშრომლების ელფოსტის დომენი **Login email domain**-ის ქვეშ. მაგალითად, Okta დომენმა `your-company.okta.com` შეიძლება ჰქონდეს შესვლის ელფოსტის დომენი `example.com`.
6. დააჭირეთ **Save changes**.
7. დაამატეთ Tuist-ის მიერ ნაჩვენები ტექსტური ჩანაწერი შესვლის ელფოსტის დომენში, შემდეგ დააჭირეთ **Verify domain**.
8. აირჩიეთ, სჭირდებათ თუ არა მომხმარებლებს მოწვევა, ან შეუძლიათ თუ არა ავტომატური რეგისტრაცია, შემდეგ კვლავ შეინახეთ კონფიგურაცია.
9. სურვილისამებრ ჩართეთ **Enforce single sign-on** შესვლის ნაკადის ტესტირების შემდეგ.

### ნაბიჯი 3: მიანიჭეთ მომხმარებლები Okta აპლიკაციას {#okta-step-3}

მიანიჭეთ მომხმარებლები ან ჯგუფები, რომლებსაც უნდა ჰქონდეთ Okta აპლიკაციის მეშვეობით ავთენტიფიკაციის უფლება.

მინიჭება იძლევა წვდომას შესვლის ნაკადზე, მაგრამ ორგანიზაციის წევრობა კვლავ ემორჩილება რეგისტრაციის პოლიტიკას. თუ იგივე მომხმარებლები პროვიზირებულია System for Cross-domain Identity Management-ის მეშვეობით, Tuist აკავშირებს Okta იდენტობას SCIM-ის მიერ შექმნილ ანგარიშთან მომხმარებლის პირველი შესვლისას. წევრი, რომლის ანგარიში არსებობდა SCIM-ის მიერ დამატებამდე, დაკავშირდება, როდესაც მისი ელფოსტის მისამართი იქნება ვერიფიცირებულ შესვლის ელფოსტის დომენში, ან მას შემდეგ, რაც ის დაადასტურებს ბმულს შესული ანგარიშიდან.

## Microsoft Entra ID {#microsoft-entra-id}

Microsoft Entra ID ავთენტიფიცირებს წევრებს [OpenID Connect](https://openid.net/developers/how-connect-works/)-ის მეშვეობით. Tuist იღებს ავტორიზაციის, ტოკენისა და მომხმარებლის ინფორმაციის ბოლოწერტილებს თქვენი დირექტორიის (არენდატორის) იდენტიფიკატორიდან, ამიტომ თქვენ მხოლოდ ამ მნიშვნელობას შეიყვანთ აპლიკაციის სერთიფიკატებთან ერთად.

თუ ასევე გსურთ, რომ Entra ID-მ ავტომატურად შექმნას, განაახლოს ან გააუქმოს წევრები, დააკონფიგურირეთ <.localized_link href="/guides/integrations/authentication/scim#microsoft-entra-id">Microsoft Entra ID System for Cross-domain Identity Management provisioning</.localized_link> ერთჯერადი შესვლის მუშაობის შემდეგ.

### ნაბიჯი 1: დაარეგისტრირეთ Entra აპლიკაცია {#entra-step-1}

1. [Microsoft Entra admin center](https://entra.microsoft.com)-ში, გადადით **Identity > Applications > App registrations > New registration**.
2. დააყენეთ აპლიკაციის სახელი, მაგალითად `Tuist`.
3. **Redirect URI**-ის ქვეშ, აირჩიეთ **Web** პლატფორმა და შეიყვანეთ Authentication პარამეტრების გვერდზე ნაჩვენები მნიშვნელობა, მაგალითად `https://tuist.dev/users/auth/oauth2/callback`.
4. დაარეგისტრირეთ აპლიკაცია, შემდეგ დააკოპირეთ **Directory (tenant) ID** და **Application (client) ID** მისი მიმოხილვის გვერდიდან.
5. გადადით **Certificates & secrets > New client secret**, შექმენით სექრეტი და დააკოპირეთ მისი **Value**. Microsoft აჩვენებს მნიშვნელობას მხოლოდ ერთხელ და ყოველ კლიენტის სექრეტს აქვს ვადის გასვლის თარიღი, ამიტომ ჩაინიშნეთ, როდის უნდა მოხდეს მისი როტაცია.
6. გადადით **API permissions**-ზე და დაადასტურეთ, რომ დელეგირებული Microsoft Graph ნებართვები `openid`, `profile` და `email` მინიჭებულია.
7. სურვილისამებრ, წევრებისთვის My Apps პორტალიდან შესვლის ნაკადის დაწყების დასაშვებად, დააყენეთ **Home page URL** **Branding & properties**-ის ქვეშ Authentication პარამეტრების გვერდზე ნაჩვენებ მნიშვნელობაზე.

### ნაბიჯი 2: დააკონფიგურირეთ Tuist {#entra-step-2}

1. გადადით თქვენი ორგანიზაციის **Authentication** პარამეტრების ჩანართზე.
2. ჩართეთ ერთჯერადი შესვლა.
3. აირჩიეთ **Microsoft Entra ID**, როგორც პროვაიდერი.
4. შეიყვანეთ **Directory (tenant) ID**, **Client ID** და **Client Secret**.
5. შეიყვანეთ თანამშრომლების ელფოსტის დომენი **Login email domain**-ის ქვეშ. მაგალითად, დირექტორიას, რომლის მომხმარებლებიც შედიან როგორც `first.last@example.com`, აქვს შესვლის ელფოსტის დომენი `example.com`.
6. დააჭირეთ **Save changes**.
7. დაამატეთ Tuist-ის მიერ ნაჩვენები ტექსტური ჩანაწერი შესვლის ელფოსტის დომენში, შემდეგ დააჭირეთ **Verify domain**.
8. აირჩიეთ, სჭირდებათ თუ არა მომხმარებლებს მოწვევა, ან შეუძლიათ თუ არა ავტომატური რეგისტრაცია, შემდეგ კვლავ შეინახეთ კონფიგურაცია.
9. სურვილისამებრ ჩართეთ **Enforce single sign-on** შესვლის ნაკადის ტესტირების შემდეგ.

### ნაბიჯი 3: მიანიჭეთ მომხმარებლები Entra აპლიკაციას {#entra-step-3}

მიანიჭეთ მომხმარებლები ან ჯგუფები, რომლებსაც უნდა ჰქონდეთ ავტორიზაციის უფლება. თუ აპლიკაცია კონფიგურირებულია ისე, რომ მოითხოვს მინიჭებას, შესვლა შეუძლიათ მხოლოდ მინიჭებულ მომხმარებლებს.

მინიჭება იძლევა წვდომას შესვლის ნაკადზე, მაგრამ ორგანიზაციის წევრობა კვლავ ემორჩილება რეგისტრაციის პოლიტიკას. თუ იგივე მომხმარებლები პროვიზირდება System for Cross-domain Identity Management-ის საშუალებით, Tuist აკავშირებს Entra იდენტობას იმ ანგარიშთან, რომელიც SCIM-მა შექმნა მომხმარებლის პირველი შესვლისას. წევრი, რომლის ანგარიში არსებობდა SCIM-ის მიერ დამატებამდე, დაკავშირდება მაშინ, როდესაც მისი ელფოსტის მისამართი ეკუთვნის ვერიფიცირებულ შესვლის ელფოსტის დომენს, ან მას შემდეგ, რაც ის დაადასტურებს ბმულს თავისი შესული ანგარიშიდან.

### მოთხოვნები ელფოსტის მონაცემისთვის {#entra-email-claim}

Tuist კითხულობს ავტორიზებული მომხმარებლის პროფილს Microsoft Graph-ის მომხმარებლის ინფორმაციის endpoint-იდან, რომელიც აბრუნებს ელფოსტის მისამართს მხოლოდ მაშინ, როდესაც მომხმარებელს აქვს ხელმისაწვდომი ერთი ასეთი. დირექტორიის მომხმარებელი, რომლის `mail` ატრიბუტი ცარიელია, ვერ შეძლებს შესვლას, რადგან Tuist-ს არ აქვს მისამართი შესვლის ელფოსტის დომენთან შესადარებლად.

ერთჯერადი შესვლის ამოქმედებამდე დარწმუნდით, რომ თქვენს მიერ მინიჭებულ წევრებს აქვთ ელფოსტის მისამართი შეყვანილი დირექტორიაში. ყველაზე ხშირი შემთხვევა, როდესაც ეს ატრიბუტი აკლია, არის მომხმარებლები, რომლებიც სინქრონიზებულია ადგილობრივი Active Directory-დან ფოსტის ყუთის გარეშე.

### Conditional Access და მრავალფაქტორიანი ავთენტიკაცია {#entra-conditional-access}

Conditional Access-ის პოლიტიკები, მრავალფაქტორიანი ავთენტიკაცია და შესვლის რისკის პოლიტიკები ვრცელდება Tuist აპლიკაციაზე იმავე წესით, როგორც ნებისმიერ სხვა Entra აპლიკაციაზე, რადგან ისინა ფასდება ავტორიზაციის მოთხოვნის დროს. Tuist-ის დამატებითი კონფიგურაცია არ არის საჭირო.

## მორგებული OAuth 2.0 პროვაიდერი {#custom-oauth-2-provider}

მორგებული OAuth 2.0 პროვაიდერი საშუალებას აძლევს ორგანიზაციას გამოიყენოს იდენტობის სერვისი Google Workspace-ის ან Okta-ს ნაცვლად. პროვაიდერის მომხმარებლის ინფორმაციის endpoint-მა უნდა დააბრუნოს სტაბილური მომხმარებლის იდენტიფიკატორი და ელფოსტის მისამართი.

1. პროვაიდერში შექმენით OAuth 2.0 ვებ აპლიკაცია.
2. დააყენეთ **Sign-in redirect URI** და სურვილისამებრ **Initiate login URI** Tuist-ის Authentication პარამეტრებში ნაჩვენებ მნიშვნელობებზე.
3. Tuist-ში ჩართეთ ერთჯერადი შესვლა და აირჩიეთ **OAuth2**.
4. შეიყვანეთ პროვაიდერის URL, ავტორიზაციის endpoint, ტოკენის endpoint, მომხმარებლის ინფორმაციის endpoint, კლიენტის იდენტიფიკატორი და კლიენტის საიდუმლო.
5. შეიყვანეთ და შეინახეთ **Login email domain**. ეს არის თანამშრომლების ელფოსტის დომენი და არა პროვაიდერის URL.
6. დაამატეთ Tuist-ის მიერ ნაჩვენები ტექსტური ჩანაწერი შესვლის ელფოსტის დომენში, შემდეგ დააჭირეთ **Verify domain**.
7. აირჩიეთ მხოლოდ მოწვევით ან ავტომატური რეგისტრაცია და შეინახეთ კონფიგურაცია.
8. შეამოწმეთ შესვლა **Enforce single sign-on**-ის სურვილისამებრ ჩართვამდე.

პროვაიდერის URL აიდენტიფიცირებს იდენტობებს გამცემ პროვაიდერთან. ვერიფიცირებული შესვლის ელფოსტის დომენი განსაზღვრავს, რომელ ელფოსტის მისამართებს შეუძლია Tuist-ს ენდოს მომხმარებლების დაკავშირების ან რეგისტრაციის დროს.

## კონფიგურაცია ბრძანების სტრიქონიდან {#command-line-configuration}

ბრძანების სტრიქონის ინტერფეისს შეუძლია დააკონფიგურიროს Google Workspace ან Okta და აირჩიოს რეგისტრაციის პოლიტიკა. მაგალითად:

```bash
tuist organization update sso example \
  --provider okta \
  --organization-id your-company.okta.com \
  --enrollment-policy invitation-only
```

Microsoft Entra ID და მორგებული პროვაიდერები კონფიგურირდება ორგანიზაციის Authentication პარამეტრებიდან და არა ბრძანების სტრიქონიდან.

`--organization-id` მნიშვნელობა აიდენტიფიცირებს პროვაიდერის ორგანიზაციას. ეს არ არის შესვლის ელფოსტის დომენი. ახალი Okta მომხმარებლების რეგისტრაციამდე დაამატეთ და დაავერიფიცირეთ შესვლის ელფოსტის დომენი ორგანიზაციის Authentication პარამეტრებიდან.

## პრობლემების აღმოფხვრა {#troubleshooting}

### არსებულ წევრებს შეუძლიათ შესვლა, მაგრამ ახალ მომხმარებლებს არა {#existing-members-can-sign-in-but-new-users-cannot}

Okta-ს და მორგებული პროვაიდერის კონფიგურაციებისთვის დარწმუნდით, რომ შესვლის ელფოსტის დომენი ვერიფიცირებულია. შემდეგ ან მოიწვიეთ მომხმარებელი, ან ჩართეთ ავტომატური რეგისტრაცია.

### ერთჯერადი შესვლა გთხოვთ ჯერ შესვლას {#single-sign-on-asks-you-to-log-in-first}

თქვენი Tuist ანგარიშის ელფოსტის მისამართი არ არის ორგანიზაციის ვერიფიცირებულ შესვლის ელფოსტის დომენზე, ან დომენი ჯერ არ არის ვერიფიცირებული, ამიტომ Tuist ავტომატურად არ აკავშირებს პროვაიდერის იდენტობას. შედით ჩვეულებრივი შესვლის მეთოდით და დაადასტურეთ ბმული, როგორც აღწერილია <.localized_link href="/guides/integrations/authentication/sso#link-an-existing-account">Link an existing Tuist account</.localized_link>-ში.
### Tuist ვერ პოულობს ორგანიზაციას ელფოსტის მისამართისთვის {#tuist-cannot-find-an-organization-for-an-email-address}

დარწმუნდით, რომ მომხმარებელმა შეიყვანა მოსალოდნელი თანამშრომლის ელფოსტის მისამართი და რომ მისი დომენი ზუსტად ემთხვევა ვერიფიცირებულ შესვლის ელფოსტის დომენს. არსებული წევრების პოვნა ასევე შესაძლებელია მათი მიმდინარე ორგანიზაციის წევრობის საშუალებით.

### დომენის ვერიფიკაცია ჯერ კიდევ მოლოდინის რეჟიმშია {#domain-verification-remains-pending}

დარწმუნდით, რომ ტექსტური ჩანაწერის სახელი და მნიშვნელობა ზუსტად ემთხვევა Tuist-ში ნაჩვენებ მნიშვნელობებს. Domain Name System-ის ცვლილებებს შეიძლება დასჭირდეთ გავრცელების დრო, ამიტომ ხელახლა სცადეთ ვერიფიკაცია ჩანაწერის საჯაროდ ხელმისაწვდომობის შემდეგ.

### შესვლა შეწყდა პროვაიდერის შეცვლის შემდეგ {#sign-in-stopped-after-changing-the-provider}

დაადასტურეთ ახალი პროვაიდერის კონფიგურაცია, დაავერიფიცირეთ შესვლის ელფოსტის დომენი და შეამოწმეთ შესვლის ნაკადი აღსრულების ჩართვამდე.
