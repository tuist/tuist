# ერთიანი შესვლა {#single-sign-on}

Tuist გთავაზობთ ერთიან შესვლას, როგორც შესვლის ვარიანტს, რათა უზრუნველყოს თქვენი ორგანიზაციის ანგარიშების დამატებითი უსაფრთხოება.

ერთიანი შესვლა კონფიგურირდება თქვენი ორგანიზაციის პარამეტრებში არსებული **Authentication** ჩანართიდან. მხარდაჭერილია Google Workspace, Okta, Microsoft Entra ID და მორგებული [OAuth 2.0](https://oauth.net/2/) პროვაიდერები.

Microsoft Entra ID არის OpenID Connect პროვაიდერი, რომელსაც Tuist აკონფიგურირებს თქვენი დირექტორიის იდენტიფიკატორის მიხედვით. ყველაფერი, რაც ამ სახელმძღვანელოში აღწერილია მორგებული პროვაიდერებისთვის, მათ შორის შესვლის ელფოსტის დომენის ვერიფიკაცია და რეგისტრაცია, მასზეც ვრცელდება.

> [!NOTE]
> ერთიანი შესვლა აკონტროლებს, თუ როგორ ახდენენ წევრები ავტორიზაციას და შეუძლიათ თუ არა ავტორიზებულ მომხმარებლებს ავტომატურად შემოერთება. <.localized_link href="/guides/integrations/authentication/scim">System for Cross-domain Identity Management provisioning</.localized_link> აკონტროლებს, შეუძლია თუ არა იდენტობის პროვაიდერს ორგანიზაციის წევრების შექმნა, განახლება და გაუქმება. Okta-ს შემთხვევაში, უმეტესი ორგანიზაცია ორივეს აკონფიგურირებს.

## როგორ მუშაობს წვდომა {#how-access-works}

პროვაიდერის იდენტობა, შესვლის აღმოჩენა და ორგანიზაციაში რეგისტრაცია ცალ-ცალკე საკითხებია:

- **პროვაიდერის გამომცემელი:** პროვაიდერი ორგანიზაცია ან ავტორიზაციის სერვერი, რომელმაც მომხმარებელი დაამოწმა. Tuist აერთიანებს პროვაიდერს, გამომცემელს და პროვაიდერის სტაბილურ მომხმარებლის იდენტიფიკატორს დაკავშირებული იდენტობის ძიებისას. Okta-სთვის გამომცემელი წარმოდგენილია Okta-ს დომენით. Microsoft Entra ID-სთვის ის მიღებულია დირექტორიის (არენდატორის) იდენტიფიკატორიდან. მორგებული პროვაიდერისთვის ის წარმოდგენილია პროვაიდერის URL-ით.
- **შესვლის ელფოსტის დომენი:** ელფოსტის დომენი, რომელსაც Tuist იყენებს ზოგადი შესვლის გვერდიდან Okta-ს ან მორგებული პროვაიდერის აღმოსაჩენად. ვერიფიკაციის შემდეგ, ის ასევე განსაზღვრავს, რომელი ელფოსტის მისამართები შეიძლება იყოს სანდო ახალი ანგარიშის დაკავშირებისა და ავტომატური რეგისტრაციისთვის.
- **რეგისტრაციის პოლიტიკა:** განსაზღვრავს, სჭირდება თუ არა სანდო დომენიდან მომხმარებელს მოწვევა, ან შეუძლია თუ არა მას ავტომატურად შემოერთება.
- **მოწოდება (Provisioning):** ქმნის და მართავს ორგანიზაციის წევრობას შესვლის პროცესისგან დამოუკიდებლად.

პროვაიდერის გამომცემელი და შესვლის ელფოსტის დომენი ხშირად განსხვავდება. მაგალითად, კომპანიამ შეიძლება გამოიყენოს `example.com` თანამშრომლების ელფოსტისთვის, ხოლო მისი პროვაიდერის გამომცემელი იყოს `https://login.vendor.example.net`. ახალი Okta-ს და მორგებული პროვაიდერის კონფიგურაციები ინახავს ამ მნიშვნელობებს ცალ-ცალკე.

### შესვლის ელფოსტის დომენის ვერიფიკაცია {#verify-a-login-email-domain}

Okta-ს და მორგებული პროვაიდერის კონფიგურაციებს სჭირდებათ ვერიფიცირებული შესვლის ელფოსტის დომენი, სანამ შეძლებენ ახალი Tuist ანგარიშის შექმნას ან არსებული ანგარიშის მისი ელფოსტის მისამართით დაკავშირებას. წევრებს მაინც შეუძლიათ <.localized_link href="/guides/integrations/authentication/sso#link-an-existing-account">არსებული ანგარიშის დაკავშირება</.localized_link>, მაშინაც კი, როცა დომენი ვერიფიცირებული არ არის.

1. შეიყვანეთ თანამშრომლების ელფოსტის დომენი, მაგალითად `example.com`, ველში **Login email domain**.
2. შეინახეთ ერთიანი შესვლის კონფიგურაცია.
3. დაამატეთ Tuist-ის მიერ ნაჩვენები ტექსტური ჩანაწერი დომენის [Domain Name System](https://www.cloudflare.com/learning/dns/dns-records/dns-txt-record/) კონფიგურაციაში.
4. დაბრუნდით Authentication პარამეტრებში და დააჭირეთ **Verify domain**.

ვერიფიცირებული შესვლის ელფოსტის დომენი შეიძლება ეკუთვნოდეს მხოლოდ ერთ Tuist ორგანიზაციას. დომენის შეცვლა ასუფთავებს მის ვერიფიკაციას და მოითხოვს ახალი ტექსტური ჩანაწერის გამოქვეყნებას. ავტომატური რეგისტრაცია რჩება შეჩერებული, სანამ დომენი არ დამოწმდება.

Tuist ყოველდღიურად ამოწმებს ტექსტურ ჩანაწერს. ჩანაწერი, რომლის გარჩევაც შეწყდა, არ ასუფთავებს ვერიფიკაციას მაშინვე: დომენი ინარჩუნებს მას 14 დღის განმავლობაში, ხოლო Authentication პარამეტრებში ჩანს **Verification expiring** თავიდან გამოსაქვეყნებელ ჩანაწერთან ერთად. ჩანაწერის გამოქვეყნება და ვერიფიკაცია ასუფთავებს გაფრთხილებას. დომენი, რომლის ჩანაწერიც 14 დღის შემდეგაც არ არის, ბრუნდება ვერიფიცირებულ მდგომარეობაში და პროვაიდერის აღმოჩენა, იდენტობის დაკავშირება და ავტომატური რეგისტრაცია ჩერდება, სანამ ის ხელახლა არ დამოწმდება. ძიება, რომელიც ნებისმიერი სხვა მიზეზით ვერ ხერხდება, არ ანახლებს ტაიმერს და არ ასუფთავებს ვერიფიკაციას თავისთავად. დომენები, რომლებიც ვერიფიცირდა ყოველდღიური ხელახალი შემოწმებების შემოღებამდე, არ მოწმდება ხელახლა.

Google Workspace-ს არ სჭირდება ეს ცალკეული Tuist ვერიფიკაციის ნაბიჯი, რადგან Google ამოწმებულ Workspace დომენს აწვდის ავტორიზებული იდენტობის ნაწილად.

### რეგისტრაციის პოლიტიკის არჩევა {#choose-an-enrollment-policy}

Tuist მხარდაჭერს ორ რეგისტრაციის პოლიტიკას:

- **მხოლოდ მოწვევით:** მომხმარებელს სჭირდება ორგანიზაციის მოწვევა. Okta-ს და მორგებული პროვაიდერებისთვის, შესვლის ელფოსტის დომენი მაინც უნდა იყოს ვერიფიცირებული, სანამ პროვაიდერი შეძლებს ახალი Tuist ანგარიშის შექმნას. მოწვეულ მომხმარებელს, რომელსაც უკვე აქვს Tuist ანგარიში, ჯერ უნდა მიიღოს მოწვევა, შემდეგ კი დააკავშიროს პროვაიდერის იდენტობა, როგორც აღწერილია <.localized_link href="/guides/integrations/authentication/sso#link-an-existing-account">Link an existing Tuist account</.localized_link>-ში.
- **ავტომატური:** მომხმარებელს, რომლის ავტორიზებული ელფოსტა ემთხვევა სანდო დომენს, შეუძლია შექმნას ან დააკავშიროს ანგარიში და შემოუერთდეს ორგანიზაციას მოწვევის გარეშე. Google კონფიგურაციები იყენებენ Workspace დომენს. Okta-ს და მორგებული პროვაიდერებისთვის საჭიროა ვერიფიცირებული შესვლის ელფოსტის დომენი.

Google კონფიგურაციები ნაგულისხმევად იყენებენ ავტომატურ რეგისტრაციას. ახალი Okta-ს და მორგებული პროვაიდერის კონფიგურაციები ნაგულისხმევად იყენებენ მხოლოდ მოწვევით რეგისტრაციას.

პარამეტრი **Enforce single sign-on** დამოუკიდებელია რეგისტრაციისგან. ორგანიზაციის დაცულ ბრაუზერის გვერდებზე წვდომა მოითხოვს სესიას, რომელიც ავტორიზებულია მისი მიმდინარე პროვაიდერისა და გამომცემლის მეშვეობით (ან ვერიფიცირებული Google Workspace-ის). ისტორიულად დაკავშირებული იდენტობა ან სხვა ორგანიზაციის პროვაიდერით ავტორიზაცია არასაკმარისია. ჩვეულებრივი შესვლა Tuist-ში და სხვა ანგარიშებზე წვდომა რჩება ხელმისაწვდომი; აღსრულება არ ანიჭებს ორგანიზაციის წევრობას. ანონიმურ საჯარო დაფებს და დროში შეზღუდულ ოპერატორის მხარდაჭერის გრანტებს რჩებათ ცალკეული წვდომის წესები. აპლიკაციის პრევიუს გვერდები აღსრულებას ავრცელებენ მხოლოდ ორგანიზაციის წევრებზე, ამიტომ ორგანიზაციის გარეთ გაზიარებული პრევიუს ბმულები განაგრძობენ მუშაობას იმ ვიზიტორებისთვის, ვისაც პრევიუს გახსნა უკვე შეეძლო.

აღსრულება ვრცელდება ყველგან, სადაც წევრის სესია აღწევს ორგანიზაციამდე:

- **Dashboard**: ორგანიზაციის გვერდები და ინსტრუმენტები, რომლებსაც ისინი სთავაზობენ ბრაუზერის აგენტებს <.localized_link href="/guides/features/agentic-coding/mcp#webmcp">WebMCP</.localized_link>-ის მეშვეობით, მოითხოვენ სესიას, რომელიც შესულია ორგანიზაციის პროვაიდერით.
- **Tuist CLI, Tuist-ის აპლიკაცია, MCP კლიენტები და API-ს ცნობარი**: მათში შესვლა ქმნის სერთიფიკატს, რომელიც წევრის სახელით მოქმედებს ყველა ორგანიზაციაში, ამიტომ ის მოითხოვს სესიას, რომელიც შესულია იმ ორგანიზაციის მეშვეობით, რომელიც აღასრულებს ერთჯერად შესვლას. Tuist ჯერ პროვაიდერზე გადაჰყავს წევრს, რომელიც სხვა გზით შევიდა, და უარს ამბობს შესვლაზე ელფოსტითა და პაროლით ან Apple-ით. ყოველ ჯერზე, როდესაც ასეთი კლიენტი აახლებს თავის სერთიფიკატს, Tuist ხელახლა ამოწმებს მას. ორგანიზაციის ერთჯერადი შესვლით მიღებული სერთიფიკატი განაგრძობს განახლებას; ასევე იქცევა სხვა გზით მიღებული სერთიფიკატიც, თუ წევრი ადრე შევიდა ორგანიზაციის პროვაიდერით. ნებისმიერი სხვა სერთიფიკატი, მაგალითად, ის, რომელიც წევრმა მიიღო პაროლით ორგანიზაციის ერთჯერადი შესვლის აღსრულებამდე, განაგრძობს განახლებას აღსრულების პირობებში პირველი განახლებიდან ოთხი კვირის განმავლობაში; ამის შემდეგ კლიენტი სთხოვს წევრს ხელახლა შესვლას. ამ დროის განმავლობაში პროვაიდერით შესვლა, დაფაზე ან `tuist auth login`-ის გამოყენებით, აგრძელებს მის განახლებას.

რამდენიმე ორგანიზაციის წევრი, რომლებიც აღასრულებენ ერთჯერად შესვლას, ვერ შევლენ CLI-ში, აპლიკაციაში ან MCP კლიენტებში, რადგან ერთი სესია შედის მხოლოდ ერთი ორგანიზაციის მეშვეობით.

### აირჩიეთ როლი, რომელსაც მიიღებენ რეგისტრირებული წევრები {#choose-the-enrollment-role}

ავტომატურად შემოერთებულ წევრებს ენიჭებათ <.localized_link href="/guides/server/accounts-and-projects#roles">როლი</.localized_link>, რომელიც მითითებულია **Role for enrolled members** პარამეტრში, ეს არის `user`, თუ ადმინისტრატორი არ შეცვლის მას. მისი `viewer`-ზე დაყენება ხსნის შესვლას დირექტორიის ყველა მომხმარებლისთვის, ყველასთვის ცვლილებების შეტანის შესაძლებლობის მიცემის გარეშე.

პარამეტრი ვერ დაყენდება `admin`-ზე, ვრცელდება <.localized_link href="/guides/integrations/authentication/scim">SCIM</.localized_link>-ის მეშვეობით როლის გარეშე მიწოდებულ წევრებზე, ისევე როგორც შესვლის მცდელობებზე, და არასდროს გადაწერს ადმინისტრატორის მიერ ხელით დაყენებულ როლს.

### დააკავშირეთ არსებული Tuist-ის ანგარიში {#link-an-existing-account}

დაკავშირებული პროვაიდერის იდენტობით შესვლა ხდება მთელ Tuist-ის ანგარიშზე, მათ შორის ყველა სხვა ორგანიზაციაზე, რომელსაც ანგარიში ეკუთვნის. Okta-სა და მორგებული პროვაიდერებისთვის, Tuist ავტომატურად აკავშირებს არსებულ ანგარიშს მხოლოდ მაშინ, როდესაც მისი ელფოსტის მისამართი ეკუთვნის ვერიფიცირებულ შესვლის ელფოსტის დომენს, ან როდესაც ორგანიზაციის SCIM მიწოდებამ შექმნა ანგარიში.

წევრები, რომელთა ანგარიში არ აკმაყოფილებს პირობებს, თავად აკავშირებენ იდენტობას:

1. შედით Tuist-ში ანგარიშის ჩვეულებრივი შესვლის მეთოდით.
2. გახსენით Tuist იდენტობის პროვაიდერიდან, მაგალითად, მისი აპლიკაციის ფილიალიდან, ან გახსენით ორგანიზაციის ერთ-ერთი პროექტი, თუ ის აღასრულებს ერთჯერად შესვლას.
3. დაადასტურეთ ორგანიზაცია და იდენტობის პროვაიდერის ანგარიში, რომელსაც Tuist აჩვენებს, შემდეგ დააჭირეთ **Link account**.

წევრს, რომელიც იწყებს ერთჯერად შესვლას გასვლის მდგომარეობაში, ჯერ სთხოვენ შესვლას, და Tuist შემდეგ ბრუნდება დადასტურებაზე. დაკავშირება არ არის დამოკიდებული დომენის ვერიფიკაციაზე, ამიტომ წევრებს შეუძლიათ გამოიყენონ ერთჯერადი შესვლა დომენის ვერიფიკაციამდე.

### არსებული ორგანიზაციები {#existing-organizations}

ყველა Okta-ს და მორგებული პროვაიდერის ორგანიზაცია იყენებს ვერიფიცირებული დომენის მოდელს. დროებითი თავსებადობის რეჟიმი წაშლილია.

თუ თქვენი შესვლის ელფოსტის დომენი არ არის ვერიფიცირებული:

- არსებულ დაკავშირებულ წევრებს შეუძლიათ განაგრძონ შესვლა, და არსებული SSO აღსრულება კვლავ ვრცელდება ორგანიზაციის წევრებზე.
- შესვლის გვერდი აღმოაჩენს თქვენს პროვაიდერს მხოლოდ არსებული ორგანიზაციის წევრობის მეშვეობით.
- ავტომატური რეგისტრაცია შეჩერებულია, და პროვაიდერს არ შეუძლია შექმნას ახალი Tuist-ის ანგარიშები, მოწვევის არსებობის შემთხვევაშიც კი.
- დაუკავშირებელი წევრები შედიან თავიანთ არსებულ Tuist-ის ანგარიშზე და ადასტურებენ დაკავშირებას ზემოთ აღწერილი გზით. ორგანიზაციის SCIM მიწოდებით შექმნილ ანგარიშებს კვლავ შეუძლიათ დაკავშირება პირველი SSO შესვლისას.
- ახალ რეგისტრაციებს არ ევალებათ თქვენი პროვაიდერის გამოყენება მხოლოდ იმის გამო, რომ მათი ელფოსტის მისამართი იყენებს თქვენს დომენს.

არსებული ჩართული რეგისტრაციისა და აღსრულების პარამეტრები რჩება შენახული და შეიძლება გამორთვა. ადმინისტრატორებს შეუძლიათ შეცვალონ კონფიგურაცია დომენის ვერიფიცირების გარეშე; ნებისმიერი პარამეტრის ჩართვა მოითხოვს ვერიფიკაციას. ვერიფიკაცია აღადგენს ავტომატურ რეგისტრაციას შესაბამისი ელფოსტის მისამართებისთვის, როდესაც ეს პარამეტრი ჩართულია. Google Workspace-ის ქცევა უცვლელია.

თქვენი **Login email domain** შესაძლოა უკვე შევსებული იყოს თქვენი ორგანიზაციის წევრების მონაცემებით. დაადასტურეთ მნიშვნელობა, გამოაქვეყნეთ ტექსტური ჩანაწერი და დააჭირეთ **Verify domain**. შეინარჩუნეთ ჩანაწერის გამოქვეყნება ყოველდღიური ხელახალი შემოწმებებისთვის.

## Google Workspace {#google}

Google Workspace-ის ერთჯერადი შესვლა ავტორიზებს მომხმარებლებს Workspace დომენის მიმართ. ადმინისტრატორებს შეუძლიათ ნება დართონ შესაბამის მომხმარებლებს ავტომატურად შეერთება ან მოითხოვონ მოწვევა.

> [!NOTE]
> **Prerequisites**
>
> გჭირდებათ Google Workspace ორგანიზაცია ვერიფიცირებული დომენით. ასევე უნდა იყოთ ავტორიზებული Google-ში იმ ელფოსტით, რომელიც დაკავშირებულია იმ დომენთან, რომელსაც აყენებთ.

### მოწყობა {#google-setup}

1. გადადით თქვენი ორგანიზაციის **Authentication** პარამეტრების ჩანართზე.
2. ჩართეთ ერთჯერადი შესვლა.
3. აირჩიეთ **Google**, როგორც პროვაიდერი.
4. შეიყვანეთ თქვენი Google Workspace დომენი, მაგალითად, `example.com`.
5. აირჩიეთ **Automatic enrollment** ან მხოლოდ მოწვევით რეგისტრაცია. ავტომატური რეგისტრაცია ნაგულისხმევად ჩართულია Google-ისთვის.
6. სურვილისამებრ ჩართეთ **Enforce single sign-on** შესვლის ნაკადის ტესტირების შემდეგ.
7. დააჭირეთ **Save changes**.

## Okta {#okta}

Okta იყენებს [OpenID Connect](https://openid.net/developers/how-connect-works/)-ს წევრების ავტორიზაციისთვის. Okta-ს დომენი განსაზღვრავს პროვაიდერის გამომცემელს; ცალკე ვერიფიცირებული შესვლის ელფოსტის დომენი აკონტროლებს აღმოჩენას, ახალი ანგარიშის დაკავშირებას და რეგისტრაციას.

თუ ასევე გსურთ, რომ Okta-მ ავტომატურად შექმნას, განაახლოს ან გააუქმოს წევრები, მოაწყვეთ <.localized_link href="/guides/integrations/authentication/scim#okta">Okta System for Cross-domain Identity Management provisioning</.localized_link> ერთჯერადი შესვლის მუშაობის შემდეგ.

### ნაბიჯი 1: შექმენით Okta აპლიკაცია {#okta-step-1}

1. თქვენს Okta ადმინისტრატორის დაფაზე, გადადით **Applications > Applications > Create App Integration**.
2. აირჩიეთ **OpenID Connect** და **Web Application**.
3. დააყენეთ აპლიკაციის სახელი, მაგალითად, `Tuist`. სურვილისამებრ ატვირთეთ [Tuist-ის ლოგო](https://tuist.dev/images/tuist_dashboard.png).
4. დააყენეთ **Sign-in redirect URI** იმ მნიშვნელობაზე, რომელიც ნაჩვენებია Authentication პარამეტრების გვერდზე, მაგალითად, `https://tuist.dev/users/auth/okta/callback`.
5. **Assignments**-ის ქვეშ, აირჩიეთ სასურველი წვდომის კონტროლი და შეინახეთ.
6. დააკოპირეთ **Client ID** და **Client Secret** აპლიკაციის ზოგადი პარამეტრებიდან. ჩაინიშნეთ თქვენი **Okta domain**, მაგალითად, `your-company.okta.com`.
7. სურვილისამებრ, Okta-ს დაფიდან შესვლის დასაშვებად, დააჭირეთ **Edit** ზოგად პარამეტრებში, შეცვალეთ **Login initiated by** მნიშვნელობაზე **Either Okta or App**, აირჩიეთ **Display application icon to users** და დააყენეთ **Initiate login URI** იმ მნიშვნელობაზე, რომელიც ნაჩვენებია Authentication პარამეტრების გვერდზე.

### ნაბიჯი 2: მოაწყვეთ Tuist {#okta-step-2}

1. გადადით თქვენი ორგანიზაციის **Authentication** პარამეტრების ჩანართზე.
2. ჩართეთ ერთჯერადი შესვლა.
3. აირჩიეთ **Okta**, როგორც პროვაიდერი.
4. შეიყვანეთ **Okta domain**, **Client ID** და **Client Secret**.
5. შეიყვანეთ თანამშრომლების ელფოსტის დომენი **Login email domain**-ის ქვეშ. მაგალითად, Okta-ს დომენმა `your-company.okta.com` შეიძლება ჰქონდეს შესვლის ელფოსტის დომენი `example.com`.
6. დააჭირეთ **Save changes**.
7. დაამატეთ Tuist-ის მიერ ნაჩვენები ტექსტური ჩანაწერი შესვლის ელფოსტის დომენში, შემდეგ დააჭირეთ **Verify domain**.
8. აირჩიეთ, სჭირდებათ თუ არა მომხმარებლებს მოწვევა ან შეუძლიათ თუ არა ავტომატური რეგისტრაცია, შემდეგ კვლავ შეინახეთ კონფიგურაცია.
9. სურვილისამებრ ჩართეთ **Enforce single sign-on** შესვლის ნაკადის ტესტირების შემდეგ.

### ნაბიჯი 3: მიანიჭეთ მომხმარებლები Okta აპლიკაციას {#okta-step-3}

მიანიჭეთ ის მომხმარებლები ან ჯგუფები, რომლებსაც უნდა ჰქონდეთ Okta აპლიკაციის მეშვეობით ავტორიზაციის უფლება.

მინიჭება იძლევა წვდომას შესვლის ნაკადთან, მაგრამ ორგანიზაციის წევრობა კვლავ ემორჩილება რეგისტრაციის პოლიტიკას. თუ იგივე მომხმარებლები მომარაგებულია System for Cross-domain Identity Management-ის მეშვეობით, Tuist აკავშირებს Okta-ს იდენტობას იმ ანგარიშთან, რომელიც SCIM-მა შექმნა მომხმარებლის პირველი შესვლისას. წევრი, რომლის ანგარიში არსებობდა SCIM-ის მიერ დამატებამდე, დაკავშირდება, როდესაც მისი ელფოსტის მისამართი იქნება ვერიფიცირებულ შესვლის ელფოსტის დომენში, ან მას შემდეგ, რაც ის დაადასტურებს ბმულს თავისი შესული ანგარიშიდან.

## Microsoft Entra ID {#microsoft-entra-id}

Microsoft Entra ID ავტორიზებს წევრებს [OpenID Connect](https://openid.net/developers/how-connect-works/)-ის მეშვეობით. Tuist იღებს ავტორიზაციის, ტოკენის და მომხმარებლის ინფორმაციის ბოლოწერტილებს თქვენი დირექტორიის (არენდატორის) იდენტიფიკატორიდან, ამიტომ თქვენ მხოლოდ ამ მნიშვნელობას შეიყვანთ აპლიკაციის სარწმუნოებებთან ერთად.

თუ ასევე გსურთ, რომ Entra ID-მ ავტომატურად შექმნას, განაახლოს ან გააუქმოს წევრები, მოაწყვეთ <.localized_link href="/guides/integrations/authentication/scim#microsoft-entra-id">Microsoft Entra ID System for Cross-domain Identity Management provisioning</.localized_link> ერთჯერადი შესვლის მუშაობის შემდეგ.

### ნაბიჯი 1: დაარეგისტრირეთ Entra აპლიკაცია {#entra-step-1}

1. [Microsoft Entra admin center](https://entra.microsoft.com)-ში, გადადით **Identity > Applications > App registrations > New registration**.
2. დააყენეთ აპლიკაციის სახელი, მაგალითად, `Tuist`.
3. **Redirect URI**-ის ქვეშ, აირჩიეთ **Web** პლატფორმა და შეიყვანეთ იმ მნიშვნელობა, რომელიც ნაჩვენებია Authentication პარამეტრების გვერდზე, მაგალითად, `https://tuist.dev/users/auth/oauth2/callback`.
4. დაარეგისტრირეთ აპლიკაცია, შემდეგ დააკოპირეთ **Directory (tenant) ID** და **Application (client) ID** მისი გადახედვის გვერდიდან.
5. გადადით **Certificates & secrets > New client secret**-ზე, შექმენით საიდუმლო და დააკოპირეთ მისი **Value**. Microsoft აჩვენებს მნიშვნელობას მხოლოდ ერთხელ და ყოველ საიდუმლოს აქვს ვადის გასვლის თარიღი, ამიტომ ჩაინიშნეთ, როდის უნდა განახლდეს ის.
6. გადადით **API permissions**-ზე და დაადასტურეთ, რომ დელეგირებული Microsoft Graph ნებართვები `openid`, `profile` და `email` მინიჭებულია.
7. სურვილისამებრ, წევრებისთვის My Apps პორტალიდან შესვლის ნაკადის დაწყების დასაშვებად, დააყენეთ **Home page URL** **Branding & properties**-ის ქვეშ იმ მნიშვნელობაზე, რომელიც ნაჩვენებია Authentication პარამეტრების გვერდზე.

### ნაბიჯი 2: მოაწყვეთ Tuist {#entra-step-2}

1. გადადით თქვენი ორგანიზაციის **Authentication** პარამეტრების ჩანართზე.
2. ჩართეთ ერთჯერადი შესვლა.
3. აირჩიეთ **Microsoft Entra ID**, როგორც პროვაიდერი.
4. შეიყვანეთ **Directory (tenant) ID**, **Client ID** და **Client Secret**.
5. შეიყვანეთ თანამშრომლების ელფოსტის დომენი **Login email domain**-ის ქვეშ. მაგალითად, დირექტორიას, რომლის მომხმარებლებიც შედიან როგორც `first.last@example.com`, აქვს შესვლის ელფოსტის დომენი `example.com`.
6. დააჭირეთ **Save changes**.
7. დაამატეთ Tuist-ის მიერ ნაჩვენები ტექსტური ჩანაწერი შესვლის ელფოსტის დომენში, შემდეგ დააჭირეთ **Verify domain**.
8. აირჩიეთ, სჭირდებათ თუ არა მომხმარებლებს მოწვევა ან შეუძლიათ თუ არა ავტომატური რეგისტრაცია, შემდეგ კვლავ შეინახეთ კონფიგურაცია.
9. სურვილისამებრ ჩართეთ **Enforce single sign-on** შესვლის ნაკადის ტესტირების შემდეგ.

### ნაბიჯი 3: მიანიჭეთ მომხმარებლები Entra აპლიკაციას {#entra-step-3}

მიანიჭეთ მომხმარებლები ან ჯგუფები, რომლებსაც უნდა ჰქონდეთ ავთენტიკაციის უფლება. თუ აპლიკაცია ისეა კონფიგურირებული, რომ მოითხოვს მინიჭებას, შესვლა შეუძლიათ მხოლოდ მინიჭებულ მომხმარებლებს.

მინიჭება იძლევა წვდომას შესვლის ნაკადზე, მაგრამ ორგანიზაციაში წევრობა კვლავ ემორჩილება რეგისტრაციის პოლიტიკას. თუ იგივე მომხმარებლები პროვიზირებულია System for Cross-domain Identity Management-ის მეშვეობით, Tuist აკავშირებს Entra იდენტობას იმ ანგარიშთან, რომელიც SCIM-მა შექმნა მომხმარებლის პირველი შესვლისას. წევრი, რომლის ანგარიში არსებობდა SCIM-ის მიერ დამატებამდე, დაკავშირდება მაშინ, როცა მისი ელფოსტის მისამართი შემოწმებულ შესვლის ელფოსტის დომენშია, ან მას შემდეგ, რაც ის დაადასტურებს ბმულს თავისი შესული ანგარიშიდან.

### მოთხოვნები ელფოსტის პრეტენზიისთვის {#entra-email-claim}

Tuist კითხულობს ავთენტიფიცირებული მომხმარებლის პროფილს Microsoft Graph-ის მომხმარებლის ინფორმაციის endpoint-იდან, რომელიც აბრუნებს ელფოსტის მისამართს მხოლოდ მაშინ, როცა მომხმარებელს აქვს ხელმისაწვდომი მისამართი. დირექტორიის მომხმარებელი, რომლის `mail` ატრიბუტი ცარიელია, ვერ შევა სისტემაში, რადგან Tuist-ს არ აქვს მისამართი შესვლის ელფოსტის დომენთან შესადარებლად.

დაადასტურეთ, რომ თქვენს მიერ მინიჭებულ წევრებს დირექტორიაში შევსებული აქვთ ელფოსტის მისამართი ერთჯერადი შესვლის გავრცელებამდე. ყველაზე ხშირი შემთხვევა, როცა ეს ატრიბუტი აკლია, არის მომხმარებლები, რომლებიც სინქრონიზებულია ადგილობრივი Active Directory-დან საფოსტო ყუთის გარეშე.

### პირობითი წვდომა და მრავალფაქტორიანი ავთენტიკაცია {#entra-conditional-access}

პირობითი წვდომის პოლიტიკები, მრავალფაქტორიანი ავთენტიკაცია და შესვლის რისკის პოლიტიკები ვრცელდება Tuist აპლიკაციაზე იმავე გზით, როგორც ნებისმიერ სხვა Entra აპლიკაციაზე, რადგან ისინი ფასდება ავტორიზაციის მოთხოვნის დროს. Tuist-ის დამატებითი კონფიგურაცია არ არის საჭირო.

## მორგებული OAuth 2.0 პროვაიდერი {#custom-oauth-2-provider}

მორგებული OAuth 2.0 პროვაიდერი საშუალებას აძლევს ორგანიზაციას გამოიყენოს იდენტობის სერვისი Google Workspace-ის ან Okta-ს გარდა. პროვაიდერის მომხმარებლის ინფორმაციის endpoint-მა უნდა დააბრუნოს სტაბილური მომხმარებლის იდენტიფიკატორი და ელფოსტის მისამართი.

1. პროვაიდერში შექმენით OAuth 2.0 ვებ აპლიკაცია.
2. დააყენეთ **Sign-in redirect URI** და არასავალდებულო **Initiate login URI** Tuist-ის Authentication პარამეტრებში ნაჩვენებ მნიშვნელობებზე.
3. Tuist-ში ჩართეთ ერთჯერადი შესვლა და აირჩიეთ **OAuth2**.
4. შეიყვანეთ პროვაიდერის URL, ავტორიზაციის endpoint, ტოკენის endpoint, მომხმარებლის ინფორმაციის endpoint, კლიენტის იდენტიფიკატორი და კლიენტის საიდუმლო.
5. შეიყვანეთ და შეინახეთ **Login email domain**. ეს არის თანამშრომლების ელფოსტის დომენი, არა პროვაიდერის URL.
6. დაამატეთ Tuist-ის მიერ ნაჩვენები ტექსტური ჩანაწერი შესვლის ელფოსტის დომენში, შემდეგ დააჭირეთ **Verify domain**.
7. აირჩიეთ მხოლოდ მოწვევით ან ავტომატური რეგისტრაცია და შეინახეთ კონფიგურაცია.
8. შეამოწმეთ შესვლა **Enforce single sign-on**-ის სურვილისამებრ ჩართვამდე.

პროვაიდერის URL განსაზღვრავს იდენტობებს გამცემი პროვაიდერის მიხედვით. შემოწმებული შესვლის ელფოსტის დომენი განსაზღვრავს, რომელ ელფოსტის მისამართებს ენდობა Tuist მომხმარებლების დაკავშირების ან რეგისტრაციის დროს.

## კონფიგურაცია ბრძანების სტრიქონიდან {#command-line-configuration}

ბრძანების სტრიქონის ინტერფეისს შეუძლია დააკონფიგურიროს Google Workspace ან Okta და აირჩიოს რეგისტრაციის პოლიტიკა. მაგალითად:

```bash
tuist organization update sso example \
  --provider okta \
  --organization-id your-company.okta.com \
  --enrollment-policy invitation-only
```

Microsoft Entra ID და მორგებული პროვაიდერები კონფიგურირდება ორგანიზაციის Authentication პარამეტრებიდან და არა ბრძანების სტრიქონიდან.

`--organization-id` მნიშვნელობა აიდენტიფიცირებს პროვაიდერის ორგანიზაციას. ეს არ არის შესვლის ელფოსტის დომენი. დაამატეთ და შეამოწმეთ შესვლის ელფოსტის დომენი ორგანიზაციის Authentication პარამეტრებიდან ახალი Okta მომხმარებლების რეგისტრაციამდე.

## პრობლემების აღმოფხვრა {#troubleshooting}

### არსებულ წევრებს შეუძლიათ შესვლა, მაგრამ ახალ მომხმარებლებს არა {#existing-members-can-sign-in-but-new-users-cannot}

Okta-სა და მორგებული პროვაიდერის კონფიგურაციებისთვის დაადასტურეთ, რომ შესვლის ელფოსტის დომენი შემოწმებულია. შემდეგ ან მოიწვიეთ მომხმარებელი, ან ჩართეთ ავტომატური რეგისტრაცია.

### ერთჯერადი შესვლა გთხოვთ ჯერ შესვლას {#single-sign-on-asks-you-to-log-in-first}

თქვენი Tuist ანგარიშის ელფოსტის მისამართი არ არის ორგანიზაციის შემოწმებულ შესვლის ელფოსტის დომენში, ან დომენი ჯერ არ არის შემოწმებული, ამიტომ Tuist არ აკავშირებს პროვაიდერის იდენტობას ავტომატურად. შედით თქვენი ჩვეული შესვლის მეთოდით და დაადასტურეთ ბმული, როგორც აღწერილია <.localized_link href="/guides/integrations/authentication/sso#link-an-existing-account">Link an existing Tuist account</.localized_link>-ში.
### Tuist ვერ პოულობს ორგანიზაციას ელფოსტის მისამართისთვის {#tuist-cannot-find-an-organization-for-an-email-address}

დაადასტურეთ, რომ მომხმარებელმა შეიყვანა მოსალოდნელი თანამშრომლის ელფოსტის მისამართი და რომ მისი დომენი ზუსტად ემთხვევა შემოწმებულ შესვლის ელფოსტის დომენს. არსებული წევრები ასევე შეიძლება აღმოჩენილი იყოს მათი მიმდინარე ორგანიზაციული წევრობის მეშვეობით.

### დომენის შემოწმება ჯერ კიდევ მოლოდინის რეჟიმშია {#domain-verification-remains-pending}

დაადასტურეთ, რომ ტექსტური ჩანაწერის სახელი და მნიშვნელობა ზუსტად ემთხვევა Tuist-ში ნაჩვენებ მნიშვნელობებს. Domain Name System-ის ცვლილებებს შეიძლება დასჭირდეს გავრცელების დრო, ამიტომ ხელახლა სცადეთ შემოწმება ჩანაწერის საჯაროდ ხელმისაწვდომობის შემდეგ.

### შესვლა შეწყდა პროვაიდერის შეცვლის შემდეგ {#sign-in-stopped-after-changing-the-provider}

დაადასტურეთ ახალი პროვაიდერის კონფიგურაცია, შეამოწმეთ შესვლის ელფოსტის დომენი და შეამოწმეთ შესვლის ნაკადი აღსრულების ჩართვამდე.
