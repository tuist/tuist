# გენერირებული Xcode პროექტი {#generated-xcode-project-code-coverage}

<!-- @snippet: ./_xcode-early-access -->

კოდის დაფარვა გაჩვენებთ, თუ კოდის რომელი ხაზები შეასრულეს თქვენმა ტესტებმა. Tuist ატვირთავს ყოველი `tuist test` გაშვების ხაზოვან დაფარვას და კომიტის გაშვებებს აერთიანებს ერთ მაჩვენებლად — პროექტის, თითოეული მიზნისა და თითოეული ფაილისთვის. ინფორმაციის პანელის გვერდი **Code Coverage** აჩვენებს მას კომიტების მიხედვით და როგორც ტრენდს თითოეული შტოსთვის.

მაჩვენებელი ზუსტი რჩება მაშინაც, როცა Tuist გამოტოვებს სამუშაოს. <.localized_link href="/guides/features/cache/module-cache">ბინარული ქეშიდან</.localized_link> აღებული თქვენი მიზნები აგებულია დაფარვის მრიცხველებით, ამიტომ მათი კოდი იზომება ისევე, როგორც წყაროდან აგებული კოდი. როცა <.localized_link href="/guides/features/selective-testing/generated-xcode-project">შერჩევითი ტესტირება</.localized_link> გამოტოვებს ტესტის მიზანს, ეს მიზანი ინარჩუნებს ადრეულ გაშვებაში მიღებულ დაფარვას [მიზნის დონის დაფარვის](#target-level-coverage) საშუალებით, რომელსაც Tuist იწერს ყოველ გაშვებაზე.

## მოწყობა {#setup}

### დაფარვის ჩართვა {#turn-coverage-on}

ჩართეთ დაფარვა თქვენი `Tuist.swift` გენერაციის პარამეტრებში და ჩართეთ დაფარვის ატვირთვა, რომელიც ნაგულისხმევად გამორთულია:

```swift
import ProjectDescription

let tuist = Tuist(
    testInsights: .testInsights(coverage: .coverage(upload: true)),
    project: .tuist(
        generationOptions: .options(
            coverage: .coverage(enabled: true)
        )
    )
)
```

როცა გენერაციის პარამეტრი ჩართულია:

- Tuist-ის მიერ გენერირებული ყოველი სქემის ტესტის მოქმედება აგროვებს დაფარვას; ასევე აგროვებს თქვენს მიერ განსაზღვრული ყოველი ისეთი სქემის ტესტის მოქმედება, რომელშიც `coverage` არ არის მითითებული. სქემა `.options(coverage: false)` ან `.options(coverage: true)` მნიშვნელობით ინარჩუნებს თავის მნიშვნელობას. ტესტის გეგმები თავად განსაზღვრავენ დაფარვას: Tuist-ის მიერ გენერირებული ტესტის გეგმებისთვის გადაეცით `coverage: true` პარამეტრს `.testPlans(_:coverage:)` .
- თქვენი პროექტის საკუთარი მიზნები იკითხება ბინარული ქეშიდან და მასში ცხელდება დაფარვის მრიცხველებით Debug კონფიგურაციებში. იხილეთ [როგორ მუშაობს](#instrumented-binaries).

გარემოს ცვლადები `TUIST_COVERAGE_ENABLED` და `TUIST_COVERAGE_UPLOAD` (`1` ან `0`) უპირატესობას იღებენ `enabled` და `upload` პარამეტრებთან შედარებით. დააყენეთ ისინი მთლიანი გარემოსთვის, მაგალითად CI სამუშაო ნაკადისთვის, და არა ერთი ბრძანებისთვის, რათა ქეშის გამთბობ და წამკითხ ბრძანებებს შორის შეთანხმება იყოს.

> [!IMPORTANT] KEEP THE VALUE THE SAME EVERYWHERE
> გენერაციის პარამეტრი ცვლის თქვენი პროექტის მიზნების ქეშის გასაღებებს და მისი ტესტის მიზნების შერჩევითი ტესტირების ჰეშებს. გამოიყენეთ ერთი და იგივე მნიშვნელობა ყოველ იმ მანქანაზე, რომელიც იზიარებს ქეშს, და არ მიიღოთ ის გარემოდან (მაგალითად, `Environment.isCI`-დან). გაშვება გამორთული დაფარვით არ იყენებს ხელახლა ბინარებს ან შერჩევითი ტესტირების შედეგებს ჩართული დაფარვის მქონე გაშვებებიდან.

### სქემების გამოტოვება {#leave-schemes-out}

ზოგიერთი ტესტის ნაკრები არ ეკუთვნის თქვენს დაფარვას. მაგალითად, მიღების ან end-to-end ტესტები, რომლებიც მართავენ თქვენს აპლიკაციას ან CLI-ს სხვა პროცესიდან, ასრულებენ კოდს, რომლის დაფარვასაც ვერ ხედავთ, და მისი შეგროვება მხოლოდ ანელებს მათ. გამორთეთ დაფარვა მათი სქემის ტესტის მოქმედებაში:

```swift
.scheme(
    name: "AcceptanceTests",
    testAction: .targets(
        ["AcceptanceTests"],
        options: .options(coverage: false)
    )
)
```

სქემა ინარჩუნებს დაფარვას გამორთულ მდგომარეობაში, მიუხედავად იმისა, რასაც ამბობს `Tuist.swift` პარამეტრი ან `TUIST_COVERAGE_ENABLED`, და მისი გაშვებები არ შედის კომიტის დაფარვაში. დაფარვა გროვდება სქემების მიხედვით, ამიტომ ერთი ტესტის მიზნის გამოსარიცხად გადაიტანეთ ის საკუთარ სქემაში.

### ტესტების გაშვება {#run-your-tests}

გაუშვით თქვენი ტესტები `tuist test`-ით, როგორც ჩვეულებრივ:

```sh
tuist test
```

Tuist ატვირთავს გაშვების მიერ შეგროვებულ დაფარვას ტესტის შედეგებთან ერთად. ეს მოიცავს <.localized_link href="/guides/features/test-sharding/generated-xcode-project">დაყოფილ გაშვებებს</.localized_link> და გაშვებებს, რომლებიც ამოწმებენ სხვა სამუშაოში `--without-building`-ით აგებულ პროდუქტებს. Tuist-ში გაშვების დაფარვის გამოსარიცხად, მაგალითად fork-ებიდან შემოსული pull request-ების გამშვებ სამუშაოებში, დააყენეთ `TUIST_COVERAGE_UPLOAD=0`.

### CI-ზე თითოეული კომიტის დასრულება {#complete-each-commit}

კომიტის დაფარვა ხშირად რამდენიმე სამუშაოდან მოდის: ერთი სქემის, ერთი ნაწილის ან ერთი პლატფორმის მიხედვით. Tuist-ს არ შეუძლია გაიგოს, როდის მოახსენა ბოლომ მათგან, ამიტომ მიანიშნეთ მას. როცა კომიტის ყოველი ტესტის სამუშაო დასრულდება, გაუშვით ეს ბრძანება სამუშაოში, რომელიც დამოკიდებულია მათ ყველაზე:

```sh
tuist coverage complete
```

ბრძანება კითხულობს კომიტს checkout-იდან ან თქვენი CI პროვაიდერიდან; სხვის მითითებისთვის გადაეცით `--commit <sha>`. სანამ კომიტი არ დასრულდება, მისი დაფარვა ჩანს როგორც **In progress** და არ შედის მისი შტოს ტრენდში.

### მთლიანი ნაკრების გაშვება თქვენს ნაგულისხმევ შტოზე {#full-runs}

> [!IMPORTANT] SET UP A FULL RUN
> შერჩევითი ტესტირება კომიტის დაფარვას სრულს მხოლოდ მაშინ ინარჩუნებს, თუ არსებობს ადრეული გაშვება, საიდანაც გამოტოვებული მიზნები გადააქვს. დაგეგმეთ ყოველი ტესტის გაშვება შერჩევითი ტესტირების გარეშე თქვენს ნაგულისხმევ შტოზე:
>
> ```sh
> tuist test --no-selective-testing
> ```
>
> იდეალურია ერთხელ ყოველ merge-ზე. ყოველდღიური ან ყოველკვირეული გაშვება შეიძლება საკმარისი იყოს იმ რეპოზიტორიისთვის, სადაც ცვლილებები ცოტაა. ჩაწერილი დაფარვა იწურება 90 დღის შემდეგ, ამიტომ გაუშვით უფრო ხშირად.

გადატანილი დაფარვა ეყრდნობა სრულ გაშვებებს. ისინი ანახლებენ თითოეული მიზნის ჩაწერილ დაფარვას მის ამოწურვამდე და Tuist-ს აწვდიან ფაილების ახალ მდგომარეობას, რომელსაც შერჩევითი გაშვება არ აგებს. რაც უფრო მეტად იცვლება რეპოზიტორია სრულ გაშვებებს შორის, მით უფრო ხშირად პოულობს შერჩევითი გაშვება ფაილს, რომელიც მას შემდეგ შეიცვალა, და მისი კომიტის დაფარვა ხდება **Incomplete**.

## მიზნის დონის დაფარვა {#target-level-coverage}

გაშვების დაფარვა გვიჩვენებს, რა შეასრულა მთლიანმა გაშვებამ და არა ის, რა შეასრულა თითოეულმა ტესტის მიზანმა. როცა შერჩევითი ტესტირება გამოტოვებს მიზანს, Tuist-ს სჭირდება იცოდეს, რა შეასრულა ამ მიზანმა ადრეულ გაშვებაში, რათა მისი დაფარვა გადაიტანოს წინ.

ამიტომ ყოველ გაშვებაზე Tuist ასევე იწერს, თუ რომელი ფაილები და ხაზები შეასრულა თითოეულმა ტესტის მიზანმა. ის კითხულობს მათ Xcode-ის მიერ თითოეული ტესტის პროცესისთვის ჩაწერილი დაფარვიდან, ამიტომ არაფერია შესაბამისად დასაკავშირებელი ან დასაკონფიგურირებელი. ეს იწერება macOS-ზე და iOS სიმულატორზე, არა მოწყობილობებზე. UI ტესტები არაფერს იწერენ იმ აპლიკაციაზე, რომელსაც ისინი მართავენ, რადგან აპლიკაციის კოდი საკუთარ პროცესში მუშაობს.

## როგორ მუშაობს {#how-it-works}

### ინსტრუმენტირებული ბინარები {#instrumented-binaries}

ბინარული ქეშიდან აღებული მიზანი არის წინასწარ აგებული ბინარი და ტესტის გაშვებას შეუძლია მისი კოდის გაზომვა მხოლოდ მაშინ, თუ ბინარი აგებულია დაფარვის მრიცხველებით. ჩართული დაფარვის პირობებში ბინარული ქეში ინახავს თქვენი პროექტის საკუთარი მიზნების ინსტრუმენტირებულ ვარიანტს და ყოველი ბრძანება კითხულობს და ათბობს ამ ვარიანტს:

- **Debug კონფიგურაციები** იყენებენ ინსტრუმენტირებულ ვარიანტს: `tuist cache` ათბობს მას, ხოლო `tuist generate` და `tuist test` კითხულობენ.
- **Release კონფიგურაციები** ყოველთვის იყენებენ ჩვეულებრივ ვარიანტს, ამიტომ თქვენს მიერ გაგზავნილ პროდუქტს არასდროს აქვს დაფარვის მრიცხველები.
- **გარე პაკეტები** ყოველთვის იყენებენ ჩვეულებრივ ვარიანტს. Tuist ზომავს მხოლოდ თქვენი რეპოზიტორიის კოდს.

გაათბეთ ქეში ჩართული დაფარვით, იმავე გარემოში, რაშიც თქვენი ტესტის სამუშაოებია, რათა `tuist test` იპოვოს ინსტრუმენტირებული ბინარები. როცა გაშვება აგროვებს დაფარვას, მაგრამ თქვენს მიზნებს იღებს ქეშიდან ჩვეულებრივი ბინარების სახით, Tuist გაფრთხილებთ და მათი კოდი არ იზომება. <.localized_link href="/guides/features/cache/module-cache#code-coverage">მოდულის ქეში</.localized_link> დეტალურად აღწერს ვარიანტებს.

### გზები მანქანებს შორის {#paths-across-machines}

ინსტრუმენტირებული ბინარები იწერენ თავიანთ წყაროს გზებს იმ checkout-ის მიმართ, სადაც ისინი აიგო, ამიტომ CI-ზე გათბილი ბინარი ზომავს სწორ ფაილებს ნებისმიერი დეველოპერის მანქანაზე.

<.localized_link href="/guides/features/cache/xcode-cache">Xcode ქეში</.localized_link> მუშაობს იგივე პრინციპით პრეფიქსების მეპინგის საშუალებით, რასაც Tuist ნაგულისხმევად თიშავს იმ ბილდებში, რომლებიც აგროვებენ დაფარვას, რადგან Xcode-ის საკუთარი დაფარვის ანგარიში ვერ ხსნის მეპირებულ გზებს. Xcode 27-ზე და უფრო ახალ ვერსიებზე, როცა `enableCaching` ჩართულია, `prefixMapping: true` ტოვებს მას ჩართულს, რათა დაფარვის ბილდებმა კომპილაციის შედეგები გაუზიარონ checkout-ებს შორისაც:

```swift
.options(coverage: .coverage(enabled: true, prefixMapping: true))
```

Tuist-ის ატვირთვა ხსნის მეპირებულ გზებს, მაგრამ Xcode-ის დაფარვის ანგარიში და `xccov` შეიძლება გამოტოვონ ეს ფაილები. იხილეთ <.localized_link href="/guides/features/cache/xcode-cache#coverage-with-prefix-mapping">დაფარვა პრეფიქსების მეპინგით</.localized_link>.

### გამოტოვებული ტესტები {#skipped-tests}

შერჩევითი ტესტირება ტოვებს ტესტის მიზანს, თუ წინა წარმატებულმა გაშვებამ ის უკვე შეამოწმა იგივე ჰეშით. ჰეში მოიცავს მიზნის წყაროებს, მის ტესტებს და ყველა დამოკიდებულებას, ამიტომ იგივე ჰეში ნიშნავს იგივე ტესტებს იგივე კოდზე. Tuist იყენებს ხელახლა [მიზნის დონის დაფარვას](#target-level-coverage), რომელიც იმ წინა გაშვებამ ჩაიწერა მიზნისთვის. თუ არაფერი ჩაიწერა, მაგალითად, იმიტომ რომ დაფარვა მაშინ გამორთული იყო ან გაშვება 90 დღეზე ძველია, გადასატანი არაფერია და კომიტი არის **არასრული**.

შერჩევითი გაშვება ასევე არ აგებს ყველა ფაილს. იმ ფაილებისთვის, რომლებიც მან არ დააკომპილირა, Tuist იღებს სტრიქონებს უახლოესი წინა სრული გაშვებიდან, იმ პირობით, რომ ფაილები მას შემდეგ არ შეცვლილა. სწორედ ამიტომ არის მნიშვნელოვანი თქვენს ძირითად ბრენჩზე შესრულებული [სრული გაშვებები](#full-runs).

ტესტები, რომლებსაც თქვენ თვითონ ტოვებთ `--skip-test-targets` ან `-skip-testing`-ის საშუალებით, არ გადააქვთ: კომიტი, რომლის გაშვებებმაც ისინი გამოტოვეს, არის **არასრული**, თუ კომიტზე სხვა გაშვებამ ისინი არ გაუშვა. ტესტები, რომლებსაც კარანტინი ტოვებს, საერთოდ არ შედიან დაფარვაში: Tuist არც გადააქვს მათ და არც მონიშნავს კომიტს მათ გამო **არასრულად**.

### სრული და არასრული კომიტები {#commit-status}

დაფარდაზე თითოეულ კომიტს აქვს სტატუსი:

| სტატუსი | მნიშვნელობა |
| --- | --- |
| მიმდინარეობს | გაშვებებმა მოახსენეს დაფარვა, მაგრამ `tuist coverage complete` ჯერ არ გაშვებულა კომიტისთვის. |
| სრული | კომიტის სქემების ყველა ტესტი გაშვებული იყო ან გადატანილი წინა გაშვებიდან. |
| არასრული | ზოგიერთი დაფარვის დადგენა ვერ მოხერხდა, ამიტომ მაჩვენებელი ქვედა ზღვარია. |
| არ გაზომილა | არც ერთმა გაშვებამ არ მოახსენა დაფარვა კომიტისთვის. |

ბრენჩის ტრენდი მოიცავს მხოლოდ სრულ კომიტებს. კომიტი არასრულია, მაგალითად, როცა:

- შერჩევითმა ტესტირებამ გამოტოვა მიზანი, რომლის გადატანაც შეუძლებელი იყო: წინა გაშვებამ მისთვის არ ჩაიწერა დაფარვა, ფაილი, რომელიც შერჩევითმა გაშვებამ არ ააგო, შეიცვალა ბოლო სრული გაშვების შემდეგ, ან კომიტმა შეცვალა ფაილები, რომლებიც ყველა მიზანზე მოქმედებენ, როგორიცაა `Package.resolved`, `Project.swift` ან `.xcconfig`.
- გაშვებამ გამოტოვა ტესტები `--skip-test-targets` ან `-skip-testing`-ის საშუალებით და კომიტზე სხვა გაშვებამ ისინი არ გაუშვა.
- გაშვებამ თქვენი მიზნები აიღო ბინარული ქეშიდან ჩვეულებრივი ბინარების სახით.
- სქემის ყველა გაშვება შევიწროვდა `-only-testing`-ით.
- სქემის დაფარვა მოვიდა მხოლოდ CI გაშვებებიდან checkout-ზე, სადაც იყო არაკომიტირებული ცვლილებები.

## წარმადობაზე გავლენა {#performance-impact}

დაფარვის შეგროვება მატებს დამატებით დატვირთვას, ძირითადად ტესტების დასრულების შემდეგ, როცა Xcode წერს თავის დაფარვის ანგარიშს და Tuist აექსპორტებს დაფარვას. ტესტების აგება და გაშვება დაახლოებით იმდენსვე ხანს გრძელდება, რამდენსაც მის გარეშე. ინსტრუმენტირებული ბილდები ასევე იკავებენ მეტ ადგილს დისკზე, DerivedData-ში და Debug ბინარულ ქეშში. Release ბილდებსა და არქივებზე ეს არ მოქმედებს.

## შეზღუდვები {#limitations}

### Release ბილდები სქემებისთვის, რომლებიც აგროვებენ დაფარვას {#release-builds}

როცა სქემის ტესტის მოქმედება აგროვებს დაფარვას, Xcode ასევე აინსტრუმენტებს მიზნებს, რომლებსაც `xcodebuild build` აწყობს წყაროდან ამ სქემისთვის, ნებისმიერ კონფიგურაციაში, Release-ის ჩათვლით. `xcodebuild archive` იგნორირებს ამ პარამეტრს, ამიტომ არქივები არასდროს არის ინსტრუმენტირებული. გაავრცელეთ არქივები, ან ააგეთ Release პროდუქტები სქემიდან `.options(coverage: false)`-ით.

### სხვა დაფარვის ინსტრუმენტები {#other-coverage-tools}

`-enableCodeCoverage YES` მხოლოდ განსაზღვრავს, აგროვებს თუ არა გაშვება დაფარვას, როგორც Xcode-ში. ის არ აიძულებს Tuist-ს წაიკითხოს ინსტრუმენტირებული ბინარები ქეშიდან, ამიტომ გამოიყენეთ `Tuist.swift` პარამეტრი ან `TUIST_COVERAGE_ENABLED`.

სხვა დაფარვის ინსტრუმენტისთვის მონაცემების გადასაცემად, მიეცით `tuist test`-ს თითოეული გაშვების დაფარვის LCOV ფორმატში ჩაწერის ბრძანება. ეს არის იგივე დაფარვა, რასაც Tuist ატვირთავს, რეპოზიტორიის მიმართ ფარდობითი გზებით და ბინარული ქეშიდან აღებული კოდის ჩათვლით:

```sh
tuist test --coverage-output-path coverage
```

თითოეული გაშვება წერს `coverage/<result bundle name>.lcov`. გააერთიანეთ დაშლილი (sharded) გაშვების ფაილები `lcov -a`-ით. პარამეტრს სჭირდება ჩართული დაფარვის ატვირთვა.

Xcode-ის საკუთარი დაფარვის ანგარიში და მისი წამკითხავი ინსტრუმენტები მოიცავენ მხოლოდ იმ მიზნებს, რომლებიც Xcode-მა ააგო ამ გაშვებაში, არასდროს კოდს, რომელიც ბინარული ქეშიდან მოვიდა. Tuist-ის ატვირთვა ზომავს ორივეს. თუ გსურთ მიზნის დაფარვა Xcode-ის ანგარიშში, დააგენერირეთ პროექტი ისე, რომ ეს მიზანი აიგოს წყაროდან: `tuist generate MyTarget` ტოვებს `MyTarget`-ს წყაროდ და დანარჩენს იღებს ქეშიდან.

## დაფარვის მოთხოვნა {#querying}

`tuist coverage` ბრძანებები კითხულობენ იმას, რასაც დაფარდა აჩვენებს. `--commit`-ის გარეშე, ისინი კითხულობენ `--branch`-ის ან თქვენი ძირითადი ბრენჩის უახლეს სრულ კომიტს:

```sh
tuist coverage show                          # the project's coverage and its targets
tuist coverage files --commit <sha>          # files, least covered first
tuist coverage file Sources/Cart.swift --lines  # a file's functions, with per-line counts
```

ყველა მათგანი იღებს `--json`-ს სკრიპტინგისთვის. იგივე მონაცემები ხელმისაწვდომია აგენტებისთვის <.localized_link href="/guides/features/agentic-coding/mcp">Model Context Protocol სერვერის</.localized_link> საშუალებით.
