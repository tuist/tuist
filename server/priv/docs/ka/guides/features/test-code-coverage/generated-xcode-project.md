# გენერირებული Xcode პროექტი {#generated-xcode-project-code-coverage}

კოდის დაფარვა გიჩვენებს, თუ კოდის რომელი ხაზები შესრულდა ტესტების მიერ. Tuist ატვირთავს ხაზოვან დაფარვას ყოველი `tuist test` გაშვებისთვის და აერთიანებს კომიტის გაშვებებს ერთ მაჩვენებლად — პროექტის, თითოეული სამიზნისა და თითოეული ფაილის დონეზე. დაშბორდის **კოდის დაფარვის** გვერდი აჩვენებს მას კომიტების მიხედვით და როგორც ტრენდს თითოეული ბრენჩისთვის.

<!-- @snippet: ./_xcode-requirements -->

მაჩვენებელი ზუსტი რჩება მაშინაც, როცა Tuist გამოტოვებს სამუშაოს. თქვენი სამიზნეები <.localized_link href="/guides/features/cache/module-cache">ბინარული ქეშიდან</.localized_link> აგებულია დაფარვის მრიცხველებით, ამიტომ მათი კოდი იზომება ისევე, როგორც წყაროდან აგებული კოდი. ხოლო როცა <.localized_link href="/guides/features/selective-testing/generated-xcode-project">შერჩევითი ტესტირება</.localized_link> გამოტოვებს სატესტო სამიზნეს, სამიზნე ინარჩუნებს იმ დაფარვას, რაც მას ჰქონდა წინა გაშვებაში, [სამიზნის დონის დაფარვის](#target-level-coverage) მეშვეობით, რომელსაც Tuist იწერს ყოველ გაშვებაზე.

## მოწყობა {#setup}

### დაფარვის ჩართვა {#turn-coverage-on}

ჩართეთ დაფარვა თქვენი `Tuist.swift` გენერაციის პარამეტრებში და ჩართეთ დაფარვის ატვირთვა, რომელიც ნაგულისხმევად გამორთულია:

```swift
import ProjectDescription

let tuist = Tuist(
    testInsights: .testInsights(coverage: .coverage(upload: true)),
    project: .tuist(
        generationOptions: .options(
            coverage: .coverage(enabled: true)
        )
    )
)
```

როცა გენერაციის პარამეტრი ჩართულია:

- Tuist-ის მიერ გენერირებული ყოველი სქემის სატესტო მოქმედება აგროვებს დაფარვას, ასევე აგროვებს თქვენს მიერ განსაზღვრული ყოველი სქემის სატესტო მოქმედება, თუ `coverage` არ არის მითითებული. სქემა `.options(coverage: false)`-ით ან `.options(coverage: true)`-ით ინარჩუნებს თავის მნიშვნელობას. სატესტო გეგმები თავად განსაზღვრავენ დაფარვას: Tuist-ის მიერ გენერირებული სატესტო გეგმებისთვის გადაეცით `coverage: true` პარამეტრს `.testPlans(_:coverage:)`.
- თქვენი პროექტის საკუთარი სამიზნეები იკითხება და ცხელდება ბინარულ ქეშში დაფარვის მრიცხველებით Debug კონფიგურაციებში. იხილეთ [როგორ მუშაობს](#instrumented-binaries).

გარემოს ცვლადები `TUIST_COVERAGE_ENABLED` და `TUIST_COVERAGE_UPLOAD` (`1` ან `0`) ანიჭებენ უპირატესობას `enabled` და `upload` პარამეტრებს. დააყენეთ ისინი მთლიანი გარემოსთვის, მაგალითად CI ნაკადისთვის, და არა ერთი ბრძანებისთვის, რათა ქეშის გამაცხელებელ და მკითხავ ბრძანებებს შორის შეთანხმება იყოს.

> [!IMPORTANT] KEEP THE VALUE THE SAME EVERYWHERE
> გენერაციის პარამეტრი ცვლის თქვენი პროექტის სამიზნეების ქეშის გასაღებებს და მათი სატესტო სამიზნეების შერჩევითი ტესტირების ჰეშებს. გამოიყენეთ ერთი და იგივე მნიშვნელობა ყოველ მანქანაზე, რომელიც იზიარებს ქეშს, და არ მიიღოთ ის გარემოდან (მაგალითად, `Environment.isCI`-დან). გაშვება გამორთული დაფარვით არ იყენებს ხელახლა ბინარებს ან შერჩევითი ტესტირების შედეგებს ჩართული დაფარვის მქონე გაშვებებიდან.

### სქემების გამოტოვება {#leave-schemes-out}

ზოგიერთი სატესტო ნაკრები არ ეკუთვნის თქვენს დაფარვას. მაგალითად, მიღების ან end-to-end ტესტები, რომლებიც მართავენ თქვენს აპს ან CLI-ს სხვა პროცესიდან, ასრულებენ კოდს, რომლის დაფარვის დანახვაც შეუძლებელია, და მისი შეგროვება მხოლოდ ანელებს მათ. გამორთეთ დაფარვა მათი სქემის სატესტო მოქმედებაში:

```swift
.scheme(
    name: "AcceptanceTests",
    testAction: .targets(
        ["AcceptanceTests"],
        options: .options(coverage: false)
    )
)
```

სქემა ინარჩუნებს დაფარვას გამორთულს, მიუხედავად იმისა, რასაც `Tuist.swift` პარამეტრი ან `TUIST_COVERAGE_ENABLED` ამბობს, და მისი გაშვებები არ შედის კომიტის დაფარვაში. დაფარვა გროვდება სქემის მიხედვით, ამიტომ ერთი სატესტო სამიზნის გამოსატოვებლად გადაიტანეთ ის საკუთარ სქემაში.

### ტესტების გაშვება {#run-your-tests}

გაუშვით ტესტები `tuist test`-ით, როგორც ჩვეულებრივ:

```sh
tuist test
```

Tuist ატვირთავს გაშვების მიერ შეგროვებულ დაფარვას ტესტების შედეგებთან ერთად. ეს მოიცავს <.localized_link href="/guides/features/test-sharding/generated-xcode-project">დაყოფილ გაშვებებს</.localized_link> და გაშვებებს, რომლებიც ტესტავენ სხვა ჯობში აგებულ პროდუქტებს `--without-building`-ით. რომ გაშვების დაფარვა არ მოხვდეს Tuist-ში, მაგალითად ჯობებში, რომლებიც ასრულებენ pull request-ებს fork-ებიდან, დააყენეთ `TUIST_COVERAGE_UPLOAD=0`.

### ყოველი კომიტის დასრულება CI-ზე {#complete-each-commit}

კომიტის დაფარვა ხშირად მოდის რამდენიმე ჯობიდან: ერთი სქემის, ერთი ნაწილის ან ერთი პლატფორმის მიხედვით. Tuist ვერ ხვდება, როდის ანგარიშგება ბოლო მათგანი, ამიტომ შეატყობინეთ მას. როგორც კი კომიტის ყოველი სატესტო ჯობი დასრულდება, გაუშვით ეს ჯობში, რომელიც დამოკიდებულია ყველა მათგანზე:

```sh
tuist coverage complete
```

ბრძანება კითხულობს კომიტს checkout-იდან ან თქვენი CI პროვაიდერიდან; გადაეცით `--commit <sha>` სხვის დასახელებლად. სანამ კომიტი არ დასრულდება, მისი დაფარვა ჩანს როგორც **მიმდინარე** და არ შედის მისი ბრენჩის ტრენდში.

### მთლიანი ნაკრების გაშვება ნაგულისხმევ ბრენჩზე {#full-runs}

> [!IMPORTANT] SET UP A FULL RUN
> შერჩევითი ტესტირება მხოლოდ მაშინ ინარჩუნებს კომიტის დაფარვას სრულად, თუ არსებობს ადრეული გაშვება, საიდანაც გამოტოვებული სამიზნეების გადატანაა შესაძლებელი. დაგეგმეთ ყოველი ტესტის გაშვება, შერჩევითი ტესტირების გარეშე, თქვენს ნაგულისხმევ ბრენჩზე:
>
> ```sh
> tuist test --no-selective-testing
> ```
>
> იდეალურია ერთხელ ყოველ merge-ზე. ყოველდღიური ან ყოველკვირეული შეიძლება საკმარისი იყოს რეპოზიტორიისთვის, სადაც ცვლილებები ცოტაა. ჩაწერილი დაფარვა იწურება 31 დღის შემდეგ, ამიტომ გაუშვით ის უფრო ხშირად.

გადატანილი დაფარვა ეყრდნობა სრულ გაშვებებს. ისინი აახლებენ ყოველი სამიზნის ჩაწერილ დაფარვას მის ამოწურვამდე და აძლევენ Tuist-ს ფაილების ბოლო მდგომარეობას, რომელსაც შერჩევითი გაშვება არ აგებს. რაც უფრო მეტად იცვლება რეპოზიტორია სრულ გაშვებებს შორის, მით უფრო ხშირად პოულობს შერჩევითი გაშვება ფაილს, რომელიც შეიცვალა მას შემდეგ, და მისი კომიტის დაფარვა არის **არასრული**.

## სამიზნის დონის დაფარვა {#target-level-coverage}

გაშვების დაფარვა გვიჩვენებს, რა შეასრულა მთლიანმა გაშვებამ, და არა ის, რა შეასრულა თითოეულმა სატესტო სამიზნემ. როცა შერჩევითი ტესტირება გამოტოვებს სამიზნეს, Tuist-ს სჭირდება იცოდეს, რა შეასრულა ამ სამიზნემ ადრეულ გაშვებაში, რათა გადაიტანოს მისი დაფარვა.

ამიტომ ყოველ გაშვებაზე Tuist ასევე იწერს, თუ რომელი ფაილები და ხაზები შეასრულა თითოეულმა სატესტო სამიზნემ. ის კითხულობს მათ დაფარვიდან, რომელსაც Xcode წერს თითოეული სატესტო პროცესისთვის, ამიტომ არაფერია დასაკავშირებელი ან დასაკონფიგურირებელი. ის იწერება macOS-ზე და iOS სიმულატორზე, არა მოწყობილობებზე. UI ტესტები არაფერს იწერენ აპის შესახებ, რომელსაც ისინი მართავენ, რადგან აპის კოდი მუშაობს საკუთარ პროცესში.

## როგორ მუშაობს {#how-it-works}

### ინსტრუმენტირებული ბინარები {#instrumented-binaries}

ბინარული ქეშიდან აღებული სამიზნე არის წინასწარ აგებული ბინარი, და სატესტო გაშვებას შეუძლია მისი კოდის გაზომვა მხოლოდ მაშინ, თუ ბინარი აგებულია დაფარვის მრიცხველებით. ჩართული დაფარვის პირობებში, ბინარული ქეში ინახავს თქვენი პროექტის საკუთარი სამიზნეების ინსტრუმენტირებულ ვარიანტს, და ყოველი ბრძანება კითხულობს და აცხელებს ამ ვარიანტს:

- **Debug კონფიგურაციები** იყენებენ ინსტრუმენტირებულ ვარიანტს: `tuist cache` აცხელებს მას, ხოლო `tuist generate` და `tuist test` კითხულობენ.
- **Release კონფიგურაციები** ყოველთვის იყენებენ ჩვეულებრივ ვარიანტს, ამიტომ ის, რასაც აგზავნით, არასდროს შეიცავს დაფარვის მრიცხველებს.
- **გარე პაკეტები** ყოველთვის იყენებენ ჩვეულებრივ ვარიანტს. Tuist ზომავს მხოლოდ თქვენი რეპოზიტორიის კოდს.

გააცხელეთ ქეში ჩართული დაფარვით, იმავე გარემოში, რაშიც თქვენი სატესტო ჯობები მუშაობენ, რათა `tuist test` იპოვოს ინსტრუმენტირებული ბინარები. როცა გაშვება აგროვებს დაფარვას, მაგრამ იღებს თქვენს სამიზნეებს ქეშიდან ჩვეულებრივი ბინარების სახით, Tuist გაფრთხილებთ და მათი კოდი არ იზომება. <.localized_link href="/guides/features/cache/module-cache#code-coverage">მოდულის ქეში</.localized_link> დეტალურად აღწერს ვარიანტებს.

### გზები მანქანებს შორის {#paths-across-machines}

ინსტრუმენტირებული ბინარები იწერენ თავიანთ წყაროს გზებს იმ checkout-ის მიმართებაში, სადაც ისინი აიგნენ, ამიტომ CI-ზე გაცხელებული ბინარი ზომავს სწორ ფაილებს ნებისმიერი დეველოპერის მანქანაზე.

<.localized_link href="/guides/features/cache/xcode-cache">Xcode ქეში</.localized_link> იგივენაირად მუშაობს პრეფიქსების მაპინგის საშუალებით, რომელსაც Tuist ნაგულისხმევად თიშავს იმ აგებებში, რომლებიც აგროვებენ დაფარვას, რადგან Xcode-ის საკუთარი დაფარვის ანგარიში ვერ ხსნის მაპირებულ გზებს. Xcode 27-ზე და უფრო ახალ ვერსიებზე, `enableCaching` ჩართული რომ იყოს, `prefixMapping: true` ტოვებს მას ჩართულს, რათა დაფარვის აგებებმა ასევე გაიზიარონ კომპილაციის შედეგები checkout-ებს შორის:

```swift
.options(coverage: .coverage(enabled: true, prefixMapping: true))
```

Tuist-ის ატვირთვა ხსნის მაპირებულ გზებს, მაგრამ Xcode-ის დაფარვის ანგარიშმა და `xccov`-მა შესაძლოა გამოტოვონ ეს ფაილები. იხილეთ <.localized_link href="/guides/features/cache/xcode-cache#coverage-with-prefix-mapping">დაფარვა პრეფიქსების მაპინგით</.localized_link>.

### გამოტოვებული ტესტები {#skipped-tests}

შერჩევითი ტესტირება ტოვებს სატესტო სამიზნეს, თუ წინა წარმატებულმა გაშვებამ ის უკვე შეამოწმა იგივე ჰეშით. ჰეში მოიცავს სამიზნის წყაროებს, მის ტესტებს და ყველა დამოკიდებულებას, ამიტომ იგივე ჰეში ნიშნავს იგივე ტესტებს იგივე კოდზე. Tuist ხელახლა იყენებს [სამიზნის დონის დაფარვას](#target-level-coverage), რომელიც იმ წინა გაშვებამ ჩაიწერა ამ სამიზნისთვის. თუ არაფერი ჩაიწერა, მაგალითად, იმიტომ რომ დაფარვა მაშინ გამორთული იყო ან გაშვება 31 დღეზე ძველია, გადასატანი მონაცემები არ არსებობს და კომიტი არის **არასრული**.

შერჩევითი გაშვება ასევე არ აგებს ყველა ფაილს. იმ ფაილებისთვის, რომლებიც მან არ დააკომპილირა, Tuist იღებს სტრიქონებს უახლოესი წინა სრული გაშვებიდან, იმ პირობით, რომ ფაილები მას შემდეგ არ შეცვლილა. სწორედ ამიტომ არის მნიშვნელოვანი თქვენს ძირითად ბრენჩზე არსებული [სრული გაშვებები](#full-runs).

ტესტები, რომლებსაც თქვენ თავად ტოვებთ `--skip-test-targets`-ით ან `-skip-testing`-ით, არ გადააქვთ წინ: კომიტი, რომლის გაშვებებმაც ისინი გამოტოვეს, არის **არასრული**, თუ კომიტზე სხვა გაშვებამ არ გაუშვა ისინი. ტესტები, რომლებსაც კარანტინი ტოვებს, საერთოდ არ არის დაფარვის ნაწილი: Tuist არ გადააქვს ისინი და არ აღნიშნავს კომიტს **არასრულად** მათი გამოტოვების გამო.

### სრული და არასრული კომიტები {#commit-status}

დაფარდის თითოეულ კომიტს აქვს სტატუსი:

| სტატუსი | მნიშვნელობა |
| --- | --- |
| მიმდინარე | გაშვებებმა მოახსენეს დაფარვა, მაგრამ `tuist coverage complete` ჯერ არ გაუშვია კომიტისთვის. |
| სრული | კომიტის სქემების ყველა ტესტი გაუშვეს ან გადაიტანეს წინ. |
| არასრული | ზოგიერთი დაფარვის განსაზღვრა ვერ მოხერხდა, ამიტომ მაჩვენებელი არის ქვედა ზღვარი. |
| არ არის გაზომილი | არცერთმა გაშვებამ არ მოახსენა დაფარვა კომიტისთვის. |

ბრენჩის ტრენდი მოიცავს მხოლოდ სრულ კომიტებს. კომიტი არის არასრული, მაგალითად, როცა:

- შერჩევითმა ტესტირებამ გამოტოვა სამიზნე, რომლის გადატანაც ვერ მოხერხდა: წინა გაშვებამ მისთვის არ ჩაიწერა დაფარვა, ფაილი, რომელიც შერჩევითმა გაშვებამ არ ააგო, შეიცვალა ბოლო სრული გაშვების შემდეგ, ან კომიტმა შეცვალა ფაილები, რომლებიც ყველა სამიზნეს ეხება, როგორიცაა `Package.resolved`, `Project.swift` ან `.xcconfig`.
- გაშვებამ გამოტოვა ტესტები `--skip-test-targets`-ით ან `-skip-testing`-ით და კომიტზე სხვა გაშვებამ არ გაუშვა ისინი.
- გაშვებამ აიღო თქვენი სამიზნეები ბინარული ქეშიდან ჩვეულებრივი ბინარების სახით.
- სქემის ყველა გაშვება შევიწროვდა `-only-testing`-ით.
- სქემის დაფარვა მიღებული იყო მხოლოდ CI გაშვებებიდან checkout-ზე, რომელსაც ჰქონდა დაუფიქსირებელი ცვლილებები.

## გავლენა წარმადობაზე {#performance-impact}

დაფარვის შეგროვება ზრდის დატვირთვას, ძირითადად ტესტების დასრულების შემდეგ, როცა Xcode წერს თავის დაფარვის ანგარიშს და Tuist აგდებს დაფარვას. ტესტების აგება და გაშვება დაახლოებით იმდენივე დროს იკავებს, რამდენიც მის გარეშე. ინსტრუმენტირებული აგებები ასევე იკავებენ მეტ ადგილს დისკზე, DerivedData-ში და Debug ბინარულ ქეშში. Release აგებებზე და არქივებზე ეს გავლენას არ ახდენს.

## შეზღუდვები {#limitations}

### Release აგებები სქემებისთვის, რომლებიც აგროვებენ დაფარვას {#release-builds}

როცა სქემის სატესტო მოქმედება აგროვებს დაფარვას, Xcode ასევე აინსტრუმენტებს სამიზნეებს, რომლებსაც `xcodebuild build` აკომპილირებს წყაროდან ამ სქემისთვის, ნებისმიერ კონფიგურაციაში, Release-ის ჩათვლით. `xcodebuild archive` იგნორირებს ამ პარამეტრს, ამიტომ არქივები არასდროს არის ინსტრუმენტირებული. გაავრცელეთ არქივები, ან ააგეთ Release პროდუქტები სქემიდან `.options(coverage: false)`-ით.

### სხვა დაფარვის ინსტრუმენტები {#other-coverage-tools}

`-enableCodeCoverage YES` მხოლოდ განსაზღვრავს, აგროვებს თუ არა გაშვება დაფარვას, როგორც Xcode-ში. ეს არ აიძულებს Tuist-ს წაიკითხოს ინსტრუმენტირებული ბინარები ქეშიდან, ამიტომ ნაცვლად გამოიყენეთ `Tuist.swift` პარამეტრი ან `TUIST_COVERAGE_ENABLED`.

იმისთვის, რომ მიაწოდოთ მონაცემები სხვა დაფარვის ინსტრუმენტს, აიძულეთ `tuist test`-მა ჩაწეროს თითოეული გაშვების დაფარვა LCOV ფორმატში. ეს არის იგივე დაფარვა, რომელსაც Tuist ტვირთავს, რეპოზიტორიის მიმართებითი გზებით და ბინარული ქეშიდან აღებული კოდის ჩათვლით:

```sh
tuist test --coverage-output-path coverage
```

თითოეული გაშვება წერს `coverage/<result bundle name>.lcov`. გააერთიანეთ შარდირებული გაშვების ფაილები `lcov -a`-ით. ამ პარამეტრს სჭირდება დაფარვის ატვირთვის ჩართვა.

Xcode-ის საკუთარი დაფარვის ანგარიში და ინსტრუმენტები, რომლებიც მას კითხულობენ, მოიცავს მხოლოდ იმ სამიზნეებს, რომლებიც Xcode-მა ააგო ამ გაშვებაში, არასდროს კოდს, რომელიც ბინარული ქეშიდან მოვიდა. Tuist-ის ატვირთვა ზომავს ორივეს. თუ გსურთ სამიზნის დაფარვა Xcode-ის ანგარიშში, დააგენერირეთ პროექტი ისე, რომ ეს სამიზნე აგებული იყოს წყაროდან: `tuist generate MyTarget` ტოვებს `MyTarget`-ს წყაროდ და დანარჩენს იღებს ქეშიდან.

## დაფარვის მოთხოვნა {#querying}

`tuist coverage` ბრძანებები კითხულობენ იმას, რასაც დაფარდა აჩვენებს. `--commit`-ს გარეშე, ისინი კითხულობენ `--branch`-ის ან თქვენი ძირითადი ბრენჩის უახლეს სრულ კომიტს:

```sh
tuist coverage show                          # the project's coverage and its targets
tuist coverage files --commit <sha>          # files, least covered first
tuist coverage file Sources/Cart.swift --lines  # a file's functions, with per-line counts
tuist coverage targets                       # targets, least covered first, then those taken from the binary cache without coverage
tuist coverage commits --branch main         # a branch's commits with their status and change, newest first
tuist coverage runs --commit <sha>           # the test runs behind a commit, marked full, partial or discarded
tuist coverage branches                      # the branches with coverage
```

სატესტო გაშვების საკუთარი დაფარვა ჩანს `tuist test show <test-run-id>`-ში.

ყველა მათგანი იღებს `--json`-ს სკრიპტინგისთვის. იგივე მონაცემები ხელმისაწვდომია აგენტებისთვის <.localized_link href="/guides/features/agentic-coding/mcp">Model Context Protocol სერვერის</.localized_link> საშუალებით.
