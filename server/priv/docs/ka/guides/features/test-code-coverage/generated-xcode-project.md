# გენერირებული Xcode პროექტი {#generated-xcode-project-code-coverage}

კოდის დაფარვა გაჩვენებთ, თქვენი ტესტები კოდის რომელ ხაზებს ასრულებდნენ. Tuist ატვირთავს ყოველი `tuist test` გაშვების ხაზოვან დაფარვას და აერთიანებს კომიტის გაშვებებს ერთ მაჩვენებლად — პროექტის, თითოეული მიზნისა და თითოეული ფაილისთვის. ინფორმაციული პანელის გვერდი **Code Coverage** აჩვენებს მას კომიტების მიხედვით და როგორც ტრენდს თითოეული ბრენჩისთვის.

<!-- @snippet: ./_xcode-requirements -->

მაჩვენებელი ზუსტი რჩება, როცა Tuist გამოტოვებს სამუშაოს. თქვენი მიზნები <.localized_link href="/guides/features/cache/module-cache">binary cache</.localized_link>-დან აგებულია დაფარვის მრიცხველებით, ამიტომ მათი კოდი იზომება ისევე, როგორც წყაროდან აგებული კოდი. ხოლო როცა <.localized_link href="/guides/features/selective-testing/generated-xcode-project">selective testing</.localized_link> გამოტოვებს სატესტო მიზანს, მიზანი ინარჩუნებს ადრეულ გაშვებაში ქონილ დაფარვას [target-level coverage](#target-level-coverage)-ის მეშვეობით, რომელსაც Tuist ყოველ გაშვებაზე აღრიცხავს.

## მოწყობა {#setup}

### დაფარვის ჩართვა {#turn-coverage-on}

ჩართეთ დაფარვა თქვენი `Tuist.swift`-ის გენერაციის პარამეტრებში და ჩართეთ დაფარვის ატვირთვა, რომელიც ნაგულისხმევად გამორთულია:

```swift
import ProjectDescription

let tuist = Tuist(
    testInsights: .testInsights(coverage: .coverage(upload: true)),
    project: .tuist(
        generationOptions: .options(
            coverage: .coverage(enabled: true)
        )
    )
)
```

გენერაციის პარამეტრის ჩართვისას:

- Tuist-ის მიერ გენერირებული ყოველი სქემის სატესტო მოქმედება აგროვებს დაფარვას, ასევე აგროვებს თქვენს მიერ განსაზღვრული ყოველი სქემის სატესტო მოქმედება, თუ `coverage` არ არის მითითებული. სქემა `.options(coverage: false)`-ით ან `.options(coverage: true)`-ით ინარჩუნებს თავის მნიშვნელობას. სატესტო გეგმები თავად განსაზღვრავენ დაფარვას: Tuist-ის მიერ გენერირებული სატესტო გეგმებისთვის გადაეცით `coverage: true` პარამეტრად `.testPlans(_:coverage:)`-ში.
- თქვენი პროექტის საკუთარი მიზნები იკითხება და ცხელდება binary cache-ში დაფარვის მრიცხველებით Debug კონფიგურაციებში. იხილეთ [How it works](#instrumented-binaries).

გარემოს ცვლადები `TUIST_COVERAGE_ENABLED` და `TUIST_COVERAGE_UPLOAD` (`1` ან `0`) უპირატესობას იღებენ `enabled` და `upload` პარამეტრებზე. დააყენეთ ისინი მთლიანი გარემოსთვის, მაგალითად CI ნაკადისთვის, და არა ერთი ბრძანებისთვის, რათა cache-ის გამთბობმა და წამკითხავმა ბრძანებებმა შეთანხმებულად იმუშაონ.

> [!IMPORTANT] KEEP THE VALUE THE SAME EVERYWHERE
> გენერაციის პარამეტრი ცვლის თქვენი პროექტის მიზნების cache-ის გასაღებებს და მისი სატესტო მიზნების selective-testing ჰეშებს. გამოიყენეთ ერთი და იგივე მნიშვნელობა ყველა იმ მანქანაზე, რომელიც იზიარებს cache-ს, და არ მიიღოთ ის გარემოდან (მაგალითად `Environment.isCI`-დან). გაშვება გამორთული დაფარვით არ იყენებს ხელახლა ბინარებს ან selective-testing შედეგებს ჩართული დაფარვის გაშვებებიდან.

### სქემების გამოტოვება {#leave-schemes-out}

ზოგიერთი სატესტო ნაკრები არ ეკუთვნის თქვენს დაფარვას. მაგალითად, მიღების ან end-to-end ტესტები, რომლებიც მართავენ თქვენს აპლიკაციას ან CLI-ს სხვა პროცესიდან, ასრულებენ კოდს, რომლის დაფარვასაც ვერ ხედავთ, და მისი შეგროვება მხოლოდ ანელებს მათ. გამორთეთ დაფარვა მათი სქემის სატესტო მოქმედებაში:

```swift
.scheme(
    name: "AcceptanceTests",
    testAction: .targets(
        ["AcceptanceTests"],
        options: .options(coverage: false)
    )
)
```

სქემა ინარჩუნებს დაფარვას გამორთულს, მიუხედავად იმისა, რასაც `Tuist.swift` პარამეტრი ან `TUIST_COVERAGE_ENABLED` ამბობს, და მისი გაშვებები არ ითვლება კომიტის დაფარვაში. დაფარვა გროვდება სქემების მიხედვით, ამიტომ ერთი სატესტო მიზნის გამოსატოვებლად გადაიტანეთ ის საკუთარ სქემაში.

### ტესტების გაშვება {#run-your-tests}

გაუშვით თქვენი ტესტები `tuist test`-ით, როგორც ჩვეულებრივ:

```sh
tuist test
```

Tuist ატვირთავს გაშვების მიერ შეგროვებულ დაფარვას მის სატესტო შედეგებთან ერთად. ეს მოიცავს <.localized_link href="/guides/features/test-sharding/generated-xcode-project">sharded runs</.localized_link>-ებს და გაშვებებს, რომლებიც ამოწმებენ სხვა სამუშაოში `--without-building`-ით აგებულ პროდუქტებს. Tuist-ში გაშვების დაფარვის შესატანად, მაგალითად fork-ებიდან pull request-ების შემსრულებელ სამუშაოებში, დააყენეთ `TUIST_COVERAGE_UPLOAD=0`.

### ყოველი კომიტის დასრულება CI-ზე {#complete-each-commit}

კომიტის დაფარვა ხშირად რამდენიმე სამუშაოდან მოდის: ერთი სქემის, shard-ის ან პლატფორმის მიხედვით. Tuist-ს არ შეუძლია გაიგოს, როდის ანგარიშობს ბოლო მათგანი, ამიტომ შეატყობინეთ მას. როგორც კი კომიტის ყველა სატესტო სამუშაო დასრულდება, გაუშვით ეს ბრძანება სამუშაოში, რომელიც დამოკიდებულია მათ ყველაზე:

```sh
tuist coverage complete
```

ბრძანება კითხულობს კომიტს checkout-ის `HEAD`-დან, ანუ იმ კომიტს, რომელზეც თქვენი ტესტები გაუშვით; გადაეცით `--commit <sha>` სხვის დასახელებლად. სანამ კომიტი არ დასრულდება, მისი დაფარვა ჩანს როგორც **In progress** და არ შედის მისი ბრენჩის ტრენდში.

### მთლიანი ნაკრების გაშვება ნაგულისხმევ ბრენჩზე {#full-runs}

> [!IMPORTANT] SET UP A FULL RUN
> Selective testing მხოლოდ მაშინ ინარჩუნებს კომიტის დაფარვას სრულად, თუ არსებობს ადრეული გაშვება, საიდანაც გამოტოვებული მიზნები გადაიტანება. დაგეგმეთ ყოველი ტესტის გაშვება, selective testing-ის გარეშე, თქვენს ნაგულისხმევ ბრენჩზე:
>
> ```sh
> tuist test --no-selective-testing
> ```
>
> იდეალურია ერთხელ ყოველ merge-ზე. ყოველდღიური ან ყოველკვირეული გაშვება შეიძლება საკმარისი იყოს იმ რეპოზიტორიებისთვის, სადაც ცვლილებები ცოტაა. ჩაწერილი დაფარვა იწურება 31 დღის შემდეგ, ამიტომ გაუშვით უფრო ხშირად.

გადატანილი დაფარვა ეყრდნობა სრულ გაშვებებს. ისინი აახლებენ ყოველი მიზნის ჩაწერილ დაფარვას მის ამოწურვამდე და აძლევენ Tuist-ს ფაილების ახალ მდგომარეობას, რომელთა აგებასაც selective გაშვება არ აკეთებს. რაც უფრო მეტად იცვლება რეპოზიტორია სრულ გაშვებებს შორის, მით უფრო ხშირად პოულობს selective გაშვება ფაილს, რომელიც მას შემდეგ შეიცვალა, და მისი კომიტის დაფარვა არის **Incomplete**.

## მიზნის დონის დაფარვა {#target-level-coverage}

გაშვების დაფარვა გვიჩვენებს, რა შეასრულა მთლიანმა გაშვებამ, და არა ის, რა შეასრულა თითოეულმა სატესტო მიზანმა. როცა selective testing გამოტოვებს მიზანს, Tuist-ს სჭირდება იცოდეს, რა შეასრულა ამ მიზანმა ადრეულ გაშვებაში, რათა გადაიტანოს მისი დაფარვა.

ამიტომ ყოველ გაშვებაზე Tuist ასევე აღრიცხავს, რომელი ფაილები და ხაზები შეასრულა თითოეულმა სატესტო მიზანმა. ის კითხულობს მათ იმ დაფარვიდან, რომელსაც Xcode წერს თითოეული სატესტო პროცესისთვის, ამიტომ არაფრის დაკავშირება ან კონფიგურირება არ არის საჭირო. ის იწერება macOS-ზე და iOS სიმულატორზე, არა მოწყობილობებზე. UI ტესტები არაფერს აღრიცხავენ აპლიკაციის შესახებ, რომელსაც ისინი მართავენ, რადგან აპლიკაციის კოდი საკუთარ პროცესში მუშაობს.

## როგორ მუშაობს {#how-it-works}

### ინსტრუმენტირებული ბინარები {#instrumented-binaries}

binary cache-დან მიზანი არის წინასწარ აგებული ბინარი და სატესტო გაშვებას მისი კოდის გაზომვა მხოლოდ მაშინ შეუძლია, თუ ბინარი აგებული იყო დაფარვის მრიცხველებით. ჩართული დაფარვისას binary cache ინახავს თქვენი პროექტის საკუთარი მიზნების ინსტრუმენტირებულ ვარიანტს და ყოველი ბრძანება კითხულობს და ათბობს ამ ვარიანტს:

- **Debug configurations** იყენებენ ინსტრუმენტირებულ ვარიანტს: `tuist cache` ათბობს მას, ხოლო `tuist generate` და `tuist test` კითხულობენ.
- **Release configurations** ყოველთვის იყენებენ ჩვეულებრივ ვარიანტს, ამიტომ თქვენს მიერ მიწოდებულ პროდუქტს არასდროს აქვს დაფარვის მრიცხველები.
- **External packages** ყოველთვის იყენებენ ჩვეულებრივ ვარიანტს. Tuist ზომავს მხოლოდ თქვენი რეპოზიტორიის კოდს.

გაათბეთ cache ჩართული დაფარვით, იმავე გარემოში, რაშიც თქვენი სატესტო სამუშაოები მუშაობენ, რათა `tuist test` იპოვოს ინსტრუმენტირებული ბინარები. როცა გაშვება აგროვებს დაფარვას, მაგრამ თქვენს მიზნებს cache-დან იღებს როგორც ჩვეულებრივ ბინარებს, Tuist გაფრთხილებთ და მათი კოდი არ იზომება. <.localized_link href="/guides/features/cache/module-cache#code-coverage">module cache</.localized_link> დეტალურად აღწერს ვარიანტებს.

### გზები მანქანებს შორის {#paths-across-machines}

ინსტრუმენტირებული ბინარები აღრიცხავენ თავიანთ წყაროს გზებს იმ checkout-ის მიმართ, სადაც ისინი აიგო, ამიტომ CI-ზე გამთბარი ბინარი ზომავს სწორ ფაილებს ნებისმიერი დეველოპერის მანქანაზე.

<.localized_link href="/guides/features/cache/xcode-cache">Xcode cache</.localized_link> იგივენაირად მუშაობს პრეფიქსის მაპინგის საშუალებით, რომელსაც Tuist ნაგულისხმევად თიშავს იმ აგებებში, რომლებიც აგროვებენ დაფარვას, რადგან Xcode-ის საკუთარი დაფარვის ანგარიში ვერ ხსნის მაპირებულ გზებს. Xcode 27-ზე და ზემოთ, `enableCaching` ჩართული მდგომარეობით, `prefixMapping: true` ტოვებს მას ჩართულს, ამიტომ დაფარვის აგებები ასევე იზიარებენ კომპილაციის შედეგებს checkout-ებს შორის:

```swift
.options(coverage: .coverage(enabled: true, prefixMapping: true))
```

Tuist-ის ატვირთვა ხსნის მაპირებულ გზებს, მაგრამ Xcode-ის დაფარვის ანგარიშმა და `xccov`-მა შეიძლება გამოტოვონ ეს ფაილები. იხილეთ <.localized_link href="/guides/features/cache/xcode-cache#coverage-with-prefix-mapping">დაფარვა პრეფიქსის მაპინგით</.localized_link>.

### გამოტოვებული ტესტები {#skipped-tests}

შერჩევითი ტესტირება ტოვებს სატესტო მიზანს, თუ უწინდელმა წარმატებულმა გაშვებამ ის უკვე შეამოწმა იგივე ჰეშით. ჰეში მოიცავს მიზნის წყაროებს, მის ტესტებს და ყველა დამოკიდებულებას, ამიტომ იგივე ჰეში ნიშნავს იგივე ტესტებს იგივე კოდზე. Tuist ხელახლა იყენებს [მიზნის დონის დაფარვას](#target-level-coverage), რომელიც უწინდელმა გაშვებამ ჩაწერა ამ მიზნისთვის. თუ არაფერი ჩაიწერა, მაგალითად იმიტომ, რომ დაფარვა მაშინ გამორთული იყო ან გაშვება 31 დღეზე ძველია, გადასატანი არაფერია და კომიტი არის **არასრული**.

შერჩევითი გაშვება ასევე არ აგებს ყველა ფაილს. იმ ფაილებისთვის, რომლებიც მან არ დააკომპილირა, Tuist იღებს სტრიქონებს უახლოესი უწინდელი სრული გაშვებიდან, იმ პირობით, რომ ფაილები მას შემდეგ არ შეცვლილა. სწორედ ამიტომ არის მნიშვნელოვანი თქვენს ძირითად შტოზე შესრულებული [სრული გაშვებები](#full-runs).

ტესტები, რომლებსაც თქვენ თავად ტოვებთ `--skip-test-targets`-ით ან `-skip-testing`-ით, არ გადააქვთ წინ: კომიტი, რომლის გაშვებებმაც ისინი გამოტოვეს, არის **არასრული**, თუ კომიტზე სხვა გაშვებამ არ გაუშვა ისინი. ტესტები, რომლებსაც quarantine ტოვებს, საერთოდ არ შედიან დაფარვაში: Tuist არც გადააქვს მათ და არც აღნიშნავს კომიტს **არასრულად** მათ გამო.

### სრული და არასრული კომიტები {#commit-status}

დაფარვის თითოეულ კომიტს აქვს სტატუსი:

| სტატუსი | მნიშვნელობა |
| --- | --- |
| მიმდინარე | გაშვებებმა მოახსენეს დაფარვა, მაგრამ `tuist coverage complete` ჯერ არ გაშვებულა ამ კომიტისთვის. |
| სრული | კომიტის სქემების ყველა ტესტი გაშვებული იყო ან გადატანილი წინ. |
| არასრული | ზოგიერთი დაფარვის დადგენა ვერ მოხერხდა, ამიტომ მაჩვენებელი ქვედა ზღვარია. |
| არ გაზომილა | არც ერთმა გაშვებამ არ მოახსენა დაფარვა ამ კომიტისთვის. |

შტოს ტრენდი მოიცავს მხოლოდ სრულ კომიტებს. კომიტი არასრულია, მაგალითად, როცა:

- შერჩევითმა ტესტირებამ გამოტოვა მიზანი, რომლის გადატანაც შეუძლებელი იყო: უწინდელმა გაშვებამ მისთვის დაფარვა არ ჩაწერა, ფაილი, რომელიც შერჩევითმა გაშვებამ არ ააგო, შეიცვალა ბოლო სრული გაშვების შემდეგ, ან კომიტმა შეცვალა ფაილები, რომლებიც ყველა მიზანს ეხება, როგორიცაა `Package.resolved`, `Project.swift` ან `.xcconfig`.
- გაშვებამ გამოტოვა ტესტები `--skip-test-targets`-ით ან `-skip-testing`-ით და კომიტზე სხვა გაშვებამ არ გაუშვა ისინი.
- გაშვებამ თქვენი მიზნები binary cache-დან აიღო როგორც ჩვეულებრივი ბინარები.
- სქემის ყველა გაშვება შევიწროვდა `-only-testing`-ით.
- სქემის დაფარვა მოვიდა მხოლოდ CI გაშვებებიდან checkout-ზე, სადაც იყო არაკომიტირებული ცვლილებები.

## წარმადობაზე გავლენა {#performance-impact}

დაფარვის შეგროვება მატებს დამატებით დატვირთვას, ძირითადად ტესტების დასრულების შემდეგ, როცა Xcode წერს თავის დაფარვის ანგარიშს და Tuist აგზავნის დაფარვას. ტესტების აგება და გაშვება დაახლოებით იმდენს ხანს გრძელდება, რამდენსაც მის გარეშე. ინსტრუმენტირებული აგებები ასევე იკავებენ მეტ დისკურ სივრცეს, DerivedData-ში და Debug binary cache-ში. Release აგებები და არქივები არ ზარალდება.

## შეზღუდვები {#limitations}

### Release აგებები სქემებისთვის, რომლებიც აგროვებენ დაფარვას {#release-builds}

როცა სქემის სატესტო ქმედება აგროვებს დაფარვას, Xcode ასევე ინსტრუმენტირებს მიზნებს, რომლებსაც `xcodebuild build` აკომპილირებს წყაროდან ამ სქემისთვის, ნებისმიერ კონფიგურაციაში, Release-ის ჩათვლით. `xcodebuild archive` იგნორირებს ამ პარამეტრს, ამიტომ არქივები არასდროს არის ინსტრუმენტირებული. გაავრცელეთ არქივები, ან ააგეთ Release პროდუქტები სქემით `.options(coverage: false)`.

### სხვა დაფარვის ინსტრუმენტები {#other-coverage-tools}

`-enableCodeCoverage YES` მხოლოდ განსაზღვრავს, აგროვებს თუ არა გაშვება დაფარვას, როგორც Xcode-ში. ეს არ აიძულებს Tuist-ს წაიკითხოს ინსტრუმენტირებული ბინარები cache-დან, ამიტომ გამოიყენეთ `Tuist.swift` პარამეტრი ან `TUIST_COVERAGE_ENABLED`.

იმისთვის, რომ მივაწოდოთ მონაცემები სხვა დაფარვის ინსტრუმენტს, `tuist test`-მა ჩაწეროს თითოეული გაშვების დაფარვა LCOV ფორმატში. ეს არის იგივე დაფარვა, რომელსაც Tuist ატვირთავს, რეპოზიტორიის მიმართებითი გზებით და binary cache-დან აღებული კოდის ჩათვლით:

```sh
tuist test --coverage-output-path coverage
```

თითოეული გაშვება წერს `coverage/<result bundle name>.lcov`. გააერთიანეთ sharded გაშვების ფაილები `lcov -a`-ით. პარამეტრს სჭირდება დაფარვის ატვირთვა ჩართული.

Xcode-ის საკუთარი დაფარვის ანგარიში და მისი წამკითხავი ინსტრუმენტები მოიცავენ მხოლოდ იმ მიზნებს, რომლებიც Xcode-მა ააგო ამ გაშვებაში, არასდროს კოდს, რომელიც მოვიდა binary cache-დან. Tuist-ის ატვირთვა ზომავს ორივეს. თუ გსურთ მიზნის დაფარვა Xcode-ის ანგარიშში, გააგენერირეთ პროექტი ისე, რომ ეს მიზანი აგებული იყოს წყაროდან: `tuist generate MyTarget` ტოვებს `MyTarget`-ს როგორც წყაროს და დანარჩენს იღებს cache-დან.

## დაფარვის მოთხოვნა {#querying}

`tuist coverage` ბრძანებები კითხულობენ იმას, რასაც დაფარვის დაფა აჩვენებს. `--commit`-ის გარეშე, ისინი კითხულობენ `--branch`-ის უახლეს სრულ კომიტს, ან თქვენი ძირითადი შტოს:

```sh
tuist coverage show                          # the project's coverage and its targets
tuist coverage files --commit <sha>          # files, least covered first
tuist coverage file Sources/Cart.swift --lines  # a file's functions, with per-line counts
tuist coverage targets                       # targets, least covered first, then those taken from the binary cache without coverage
tuist coverage commits --branch main         # a branch's commits with their status and change, newest first
tuist coverage runs --commit <sha>           # the test runs behind a commit, marked full, partial or discarded
tuist coverage branches                      # the branches with coverage
```

სატესტო გაშვების საკუთარი დაფარვა ჩანს `tuist test show <test-run-id>`-ში.

ყველა მათგანი იღებს `--json`-ს სკრიპტინგისთვის. იგივე მონაცემები ხელმისაწვდომია აგენტებისთვის <.localized_link href="/guides/features/agentic-coding/mcp">Model Context Protocol server</.localized_link>-ის საშუალებით.
