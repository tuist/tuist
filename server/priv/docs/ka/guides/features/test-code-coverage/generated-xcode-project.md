# გენერირებული Xcode პროექტი {#generated-xcode-project-code-coverage}

კოდის დაფარვა გეუბნებათ, თქვენი ტესტების მიერ შესრულებული კოდის რომელი ხაზებია. Tuist ატვირთავს ყოველი `tuist test` გაშვების ხაზოვან დაფარვას და კომიტის გაშვებებს ერთ რიცხვად აერთიანებს — პროექტისთვის, თითოეული სამიზნისა და ფაილისთვის. დაფის **კოდის დაფარვის** გვერდი მას აჩვენებს კომიტის მიხედვით და როგორც ტენდენციას თითოეული შტოსთვის.

<!-- @snippet: ./_xcode-requirements -->

რიცხვი ზუსტი რჩება მაშინაც, როცა Tuist საქმეს გამოტოვებს. თქვენი სამიზნეები <.localized_link href="/guides/features/cache/module-cache">ბინარული ქეშიდან</.localized_link> აგებულია დაფარვის მრიცხველებით, ამიტომ მათი კოდი ისევე იზომება, როგორც წყაროდან აგებული კოდი. და როცა <.localized_link href="/guides/features/selective-testing/generated-xcode-project">შერჩევითი ტესტირება</.localized_link> გამოტოვებს ტესტის სამიზნეს, სამიზნე ინარჩუნებს ადრეულ გაშვებაში არსებულ დაფარვას [სამიზნის დონის დაფარვის](#target-level-coverage) მეშვეობით, რომელსაც Tuist ყოველ გაშვებაზე აღრიცხავს.

## მოწყობა {#setup}

### დაფარვის ჩართვა {#turn-coverage-on}

ჩართეთ დაფარვა თქვენი `Tuist.swift`-ის გენერაციის პარამეტრებში და ჩართეთ დაფარვის ატვირთვა, რომელიც ნაგულისხმევად გამორთულია:

```swift
import ProjectDescription

let tuist = Tuist(
    testInsights: .testInsights(coverage: .coverage(upload: true)),
    project: .tuist(
        generationOptions: .options(
            coverage: .coverage(enabled: true)
        )
    )
)
```

როცა გენერაციის პარამეტრი ჩართულია:

- ყოველი სქემის ტესტის მოქმედება, რომელსაც Tuist აგენერირებს, აგროვებს დაფარვას; ასევე აგროვებს ყოველი თქვენს მიერ განსაზღვრული სქემის ტესტის მოქმედება, თუ `coverage` არ არის მითითებული. სქემა `.options(coverage: false)`-ით ან `.options(coverage: true)`-ით ინარჩუნებს თავის მნიშვნელობას. ტესტ-პლანები თვითონ განსაზღვრავენ დაფარვას: Tuist-ის მიერ გენერირებული ტესტ-პლანებისთვის გადაეცით `coverage: true` `.testPlans(_:coverage:)`-ში.
- თქვენი პროექტის საკუთარი სამიზნეები იკითხება და თბება ბინარულ ქეშში Debug კონფიგურაციებში დაფარვის მრიცხველებით. იხილეთ [როგორ მუშაობს](#instrumented-binaries).

`TUIST_COVERAGE_ENABLED` და `TUIST_COVERAGE_UPLOAD` გარემოს ცვლადები (`1` ან `0`) უპირატესობას იღებენ `enabled` და `upload`-ზე. დააყენეთ ისინი მთელი გარემოსთვის, მაგალითად CI ნაკადისთვის, და არა ერთი ბრძანებისთვის, რათა ქეშის გამთბობ და მკითხავი ბრძანებები შეთანხმდნენ.

> [!IMPORTANT] KEEP THE VALUE THE SAME EVERYWHERE
> გენერაციის პარამეტრი ცვლის თქვენი პროექტის სამიზნეების ქეშის გასაღებებს და მათი ტესტის სამიზნეების შერჩევითი ტესტირების ჰეშებს. გამოიყენეთ ერთი და იგივე მნიშვნელობა ყოველ მანქანაზე, რომელიც იზიარებს ქეშს, და არ მიიღოთ ის გარემოდან (მაგალითად `Environment.isCI`-დან). გაშვება გამორთული დაფარვით არ იყენებს ხელახლა ბინარებს ან შერჩევითი ტესტირების შედეგებს ჩართული დაფარვის გაშვებებიდან.

### სქემების გამოტოვება {#leave-schemes-out}

ზოგიერთი ტესტ-სიუტი არ ეკუთვნის თქვენს დაფარვას. მიღების ან end-to-end ტესტები, რომლებიც მართავენ თქვენს აპს ან CLI-ს სხვა პროცესიდან, მაგალითად, ასრულებენ კოდს, რომლის დაფარვის დანახვაც შეუძლებელია, და მისი შეგროვება მხოლოდ ანელებს მათ. გამორთეთ დაფარვა მათი სქემის ტესტის მოქმედებაში:

```swift
.scheme(
    name: "AcceptanceTests",
    testAction: .targets(
        ["AcceptanceTests"],
        options: .options(coverage: false)
    )
)
```

სქემა ინარჩუნებს დაფარვას გამორთულს, მიუხედავად იმისა, რასაც `Tuist.swift` პარამეტრი ან `TUIST_COVERAGE_ENABLED` ამბობს, და მისი გაშვებები არ ითვლება კომიტის დაფარვაში. დაფარვა გროვდება სქემის მიხედვით, ამიტომ ერთი ტესტის სამიზნის გამოსატოვებლად გადაიტანეთ ის საკუთარ სქემაში.

### ტესტების გაშვება {#run-your-tests}

გაუშვით თქვენი ტესტები `tuist test`-ით, როგორც ჩვეულებრივ:

```sh
tuist test
```

Tuist ატვირთავს გაშვების მიერ შეგროვებულ დაფარვას ტესტის შედეგებთან ერთად. ეს მოიცავს <.localized_link href="/guides/features/test-sharding/generated-xcode-project">დაყოფილ გაშვებებს</.localized_link> და გაშვებებს, რომლებიც ტესტავენ სხვა ჯობში `--without-building`-ით აგებულ პროდუქტებს. Tuist-ში გაშვების დაფარვის შესატანად, მაგალითად ჯობებში, რომლებიც ასრულებენ პულ-რეკვესტებს ფორკებიდან, დააყენეთ `TUIST_COVERAGE_UPLOAD=0`.

### ყოველი კომიტის დასრულება CI-ზე {#complete-each-commit}

კომიტის დაფარვა ხშირად რამდენიმე ჯობიდან მოდის: ერთი სქემის, ნაწილის ან პლატფორმის მიხედვით. Tuist ვერ ხვდება, როდის ანგარიშგა აქვს ბოლო მათგანი, ამიტომ აცნობეთ მას. როგორც კი კომიტის ყოველი ტესტის ჯობი დასრულდება, გაუშვით ეს ჯობში, რომელიც დამოკიდებულია ყველა მათგანზე:

```sh
tuist coverage complete
```

ბრძანება კითხულობს კომიტს ჩექაუთიდან ან თქვენი CI პროვაიდერიდან; სხვის დასახელებისთვის გადაეცით `--commit <sha>`. სანამ კომიტი არ დასრულდება, მისი დაფარვა ჩანს როგორც **მიმდინარე** და არ შედის მისი შტოს ტენდენციაში.

### მთლიანი სიუტის გაშვება თქვენს ნაგულისხმევ შტოზე {#full-runs}

> [!IMPORTANT] SET UP A FULL RUN
> შერჩევითი ტესტირება მხოლოდ მაშინ ინარჩუნებს კომიტის დაფარვას სრულად, თუ არსებობს ადრეული გაშვება, რომლიდანაც გამოტოვებული სამიზნეების გადატანაა შესაძლებელი. დაგეგმეთ ყოველი ტესტის გაშვება, შერჩევითი ტესტირების გარეშე, თქვენს ნაგულისხმევ შტოზე:
>
> ```sh
> tuist test --no-selective-testing
> ```
>
> იდეალურია ერთხელ ყოველ შერწყმაზე. ყოველდღიური ან ყოველკვირეული შეიძლება საკმარისი იყოს რეპოზიტორიისთვის, სადაც ცვლილებები ცოტაა. ჩაწერილი დაფარვა იწურება 90 დღის შემდეგ, ამიტომ გაუშვით იმაზე ხშირად.

გადატანილი დაფარვა ეყრდნობა სრულ გაშვებებს. ისინი ანახლებენ ყოველი სამიზნის ჩაწერილ დაფარვას მის ამოწურვამდე და აძლევენ Tuist-ს ფაილების ბოლო მდგომარეობას, რომელსაც შერჩევითი გაშვება არ აგებს. რაც უფრო მეტად იცვლება რეპოზიტორია სრულ გაშვებებს შორის, მით უფრო ხშირად პოულობს შერჩევითი გაშვება ფაილს, რომელიც მას შემდეგ შეიცვალა, და მისი კომიტის დაფარვა არის **არასრული**.

## სამიზნის დონის დაფარვა {#target-level-coverage}

გაშვების დაფარვა გვეუბნება, რა შეასრულა მთლიანმა გაშვებამ, და არა რა შეასრულა თითოეულმა ტესტის სამიზნემ. როცა შერჩევითი ტესტირება გამოტოვებს სამიზნეს, Tuist-ს სჭირდება იცოდეს, რა შეასრულა ამ სამიზნემ ადრეულ გაშვებაში, რათა გადაიტანოს მისი დაფარვა.

ამიტომ ყოველ გაშვებაზე Tuist ასევე აღრიცხავს, რომელი ფაილები და ხაზები შეასრულა თითოეულმა ტესტის სამიზნემ. ის კითხულობს მათ დაფარვიდან, რომელსაც Xcode წერს თითოეული ტესტის პროცესისთვის, ამიტომ არაფერია დასაკავშირებელი ან დასაკონფიგურირებელი. ის იწერება macOS-ზე და iOS სიმულატორზე, არა მოწყობილობებზე. UI ტესტები არაფერს აღრიცხავენ აპის შესახებ, რომელსაც ისინი მართავენ, რადგან აპის კოდი საკუთარ პროცესში მუშაობს.

## როგორ მუშაობს {#how-it-works}

### ინსტრუმენტული ბინარები {#instrumented-binaries}

ბინარული ქეშიდან სამიზნე არის წინასწარ აგებული ბინარი, და ტესტის გაშვებას მისი კოდის გაზომვა მხოლოდ მაშინ შეუძლია, თუ ბინარი აგებულია დაფარვის მრიცხველებით. ჩართული დაფარვით, ბინარული ქეში ინახავს თქვენი პროექტის საკუთარი სამიზნეების ინსტრუმენტულ ვარიანტს, და ყოველი ბრძანება კითხულობს და ათბობს ამ ვარიანტს:

- **Debug კონფიგურაციები** იყენებენ ინსტრუმენტულ ვარიანტს: `tuist cache` ათბობს მას, ხოლო `tuist generate` და `tuist test` კითხულობენ.
- **Release კონფიგურაციები** ყოველთვის იყენებენ ჩვეულებრივ ვარიანტს, ამიტომ რასაც აწვდით, არასდროს შეიცავს დაფარვის მრიცხველებს.
- **გარე პაკეტები** ყოველთვის იყენებენ ჩვეულებრივ ვარიანტს. Tuist ზომავს მხოლოდ თქვენი რეპოზიტორიის კოდს.

გაათბეთ ქეში ჩართული დაფარვით, იმავე გარემოში, რაშიც თქვენი ტესტის ჯობებია, რათა `tuist test` იპოვოს ინსტრუმენტული ბინარები. როცა გაშვება აგროვებს დაფარვას, მაგრამ იღებს თქვენს სამიზნეებს ქეშიდან ჩვეულებრივი ბინარების სახით, Tuist გაფრთხილებთ და მათი კოდი არ იზომება. <.localized_link href="/guides/features/cache/module-cache#code-coverage">მოდულის ქეში</.localized_link> დეტალურად აღწერს ვარიანტებს.

### გზები მანქანებს შორის {#paths-across-machines}

ინსტრუმენტული ბინარები აღრიცხავენ თავიანთ წყაროს გზებს იმ ჩექაუთის მიმართ, რომელშიც ისინი აგებულნი იყვნენ, ამიტომ CI-ზე გამთბარი ბინარი ზომავს სწორ ფაილებს ნებისმიერი დეველოპერის მანქანაზე.

<.localized_link href="/guides/features/cache/xcode-cache">Xcode ქეში</.localized_link> მუშაობს იგივე პრინციპით პრეფიქსების მიბმის საშუალებით, რასაც Tuist ნაგულისხმევად თიშავს იმ აგებებში, რომლებიც აგროვებენ დაფარვას, რადგან Xcode-ის საკუთარი დაფარვის ანგარიში ვერ ხსნის მიბმულ გზებს. Xcode 27-ზე და უფრო ახალ ვერსიებზე, როცა `enableCaching` ჩართულია, `prefixMapping: true` ტოვებს მას ჩართულს, ამიტომ დაფარვის აგებები ასევე იზიარებენ კომპილაციის შედეგებს ჩექაუთებს შორის:

```swift
.options(coverage: .coverage(enabled: true, prefixMapping: true))
```

Tuist-ის ატვირთვა ხსნის მიბმულ გზებს, მაგრამ Xcode-ის დაფარვის ანგარიშმა და `xccov`-მა შესაძლოა გამოტოვონ ეს ფაილები. იხილეთ <.localized_link href="/guides/features/cache/xcode-cache#coverage-with-prefix-mapping">დაფარვა პრეფიქსების მიბმით</.localized_link>.

### გამოტოვებული ტესტები {#skipped-tests}

შერჩევითი ტესტირება ტოვებს ტესტის სამიზნეს, თუ წინა წარმატებულმა გაშვებამ ის უკვე შეამოწმა იგივე ჰეშით. ჰეში მოიცავს სამიზნის წყაროებს, მის ტესტებს და ყველა დამოკიდებულებას, ამიტომ იგივე ჰეში ნიშნავს იგივე ტესტებს იგივე კოდზე. Tuist ხელახლა იყენებს [სამიზნის დონის დაფარვას](#target-level-coverage), რომელიც იმ წინა გაშვებამ აღრიცხა ამ სამიზნისთვის. თუ არაფერი აღირიცხა, მაგალითად, იმიტომ რომ დაფარვა მაშინ გამორთული იყო ან გაშვება 90 დღეზე ძველია, გადასატანი არაფერია და კომიტი არის **არასრული**.

შერჩევითი გაშვება ასევე არ აგებს ყველა ფაილს. იმ ფაილებისთვის, რომლებიც მან არ ააგო, Tuist იღებს სტრიქონებს უახლოესი წინა სრული გაშვებიდან, იმ პირობით, რომ ფაილები მას შემდეგ არ შეცვლილა. სწორედ ამიტომ არის მნიშვნელოვანი [სრული გაშვებები](#full-runs) თქვენს ძირითად ბრენჩზე.

ტესტები, რომლებსაც თქვენ თავად ტოვებთ `--skip-test-targets`-ის ან `-skip-testing`-ის საშუალებით, არ გადაიტანება: კომიტი, რომლის გაშვებებმაც ისინი გამოტოვეს, არის **არასრული**, თუ კომიტზე სხვა გაშვებამ ისინი არ გაუშვა. ტესტები, რომლებსაც კარანტინი ტოვებს, საერთოდ არ შედიან დაფარვაში: Tuist არც გადააქვს ისინი და არც აღნიშნავს კომიტს **არასრულად** მათი გამოტოვების გამო.

### სრული და არასრული კომიტები {#commit-status}

დაფის თითოეულ კომიტს აქვს სტატუსი:

| სტატუსი | მნიშვნელობა |
| --- | --- |
| მიმდინარეობს | გაშვებებმა მოახსენეს დაფარვა, მაგრამ `tuist coverage complete` ჯერ არ გაშვებულა ამ კომიტისთვის. |
| სრული | კომიტის სქემების ყველა ტესტი გაშვებული იყო ან გადატანილი. |
| არასრული | ზოგიერთი დაფარვის განსაზღვრა ვერ მოხერხდა, ამიტომ მაჩვენებელი ქვედა ზღვარია. |
| არ გაზომილა | არცერთმა გაშვებამ არ მოახსენა დაფარვა ამ კომიტისთვის. |

ბრენჩის ტრენდი მოიცავს მხოლოდ სრულ კომიტებს. კომიტი არასრულია, მაგალითად, როცა:

- შერჩევითმა ტესტირებამ გამოტოვა სამიზნე, რომლის გადატანა შეუძლებელი იყო: წინა გაშვებამ მისთვის არ აღრიცხა დაფარვა, ფაილი, რომელიც შერჩევითმა გაშვებამ არ ააგო, შეიცვალა ბოლო სრული გაშვების შემდეგ, ან კომიტმა შეცვალა ფაილები, რომლებიც ყველა სამიზნეს ეხება, როგორიცაა `Package.resolved`, `Project.swift` ან `.xcconfig`.
- გაშვებამ გამოტოვა ტესტები `--skip-test-targets`-ის ან `-skip-testing`-ის საშუალებით და კომიტზე სხვა გაშვებამ ისინი არ გაუშვა.
- გაშვებამ აიღო თქვენი სამიზნეები ბინარული ქეშიდან ჩვეულებრივი ბინარების სახით.
- სქემის ყველა გაშვება შევიწროვდა `-only-testing`-ით.
- სქემის დაფარვა მოვიდა მხოლოდ CI გაშვებებიდან ჩექაუთზე, რომელსაც ჰქონდა დაუკომიტებელი ცვლილებები.

## წარმადობაზე გავლენა {#performance-impact}

დაფარვის შეგროვება ზრდის დამატებით დატვირთვას, ძირითადად ტესტების დასრულების შემდეგ, როცა Xcode წერს თავის დაფარვის ანგარიშს და Tuist აექსპორტებს დაფარვას. ტესტების აგება და გაშვება დაახლოებით იმავე დროს იღებს, რაც მის გარეშე. ინსტრუმენტულ აგებებს ასევე სჭირდებათ მეტი დისკური სივრცე DerivedData-ში და Debug ბინარულ ქეშში. Release აგებებზე და არქივებზე ეს გავლენას არ ახდენს.

## შეზღუდვები {#limitations}

### Release აგებები სქემებისთვის, რომლებიც აგროვებენ დაფარვას {#release-builds}

როცა სქემის ტესტის მოქმედება აგროვებს დაფარვას, Xcode ასევე აინსტრუმენტებს სამიზნეებს, რომლებსაც `xcodebuild build` აგებს წყაროდან ამ სქემისთვის, ნებისმიერ კონფიგურაციაში, Release-ის ჩათვლით. `xcodebuild archive` იგნორირებს ამ პარამეტრს, ამიტომ არქივები არასდროს არის ინსტრუმენტული. გაავრცელეთ არქივები, ან ააგეთ Release პროდუქტები სქემიდან `.options(coverage: false)`-ით.

### სხვა დაფარვის ინსტრუმენტები {#other-coverage-tools}

`-enableCodeCoverage YES` მხოლოდ განსაზღვრავს, აგროვებს თუ არა გაშვება დაფარვას, როგორც Xcode-ში. ის არ აიძულებს Tuist-ს წაიკითხოს ინსტრუმენტული ბინარები ქეშიდან, ამიტომ გამოიყენეთ `Tuist.swift` პარამეტრი ან `TUIST_COVERAGE_ENABLED`.

სხვა დაფარვის ინსტრუმენტისთვის მონაცემების გადასაცემად, მიეცით `tuist test`-ს თითოეული გაშვების დაფარვის LCOV ფორმატში ჩაწერის შესაძლებლობა. ეს არის იგივე დაფარვა, რასაც Tuist ატვირთავს, რეპოზიტორიის მიმართებითი გზებით და ბინარული ქეშიდან აღებული კოდის ჩათვლით:

```sh
tuist test --coverage-output-path coverage
```

თითოეული გაშვება წერს `coverage/<result bundle name>.lcov`. შარდირებული გაშვების ფაილები გააერთიანეთ `lcov -a`-ით. პარამეტრს სჭირდება ჩართული დაფარვის ატვირთვა.

Xcode-ის საკუთარი დაფარვის ანგარიში და ინსტრუმენტები, რომლებიც მას კითხულობენ, მოიცავენ მხოლოდ იმ სამიზნეებს, რომლებიც Xcode-მა ააგო ამ გაშვებაში, არასდროს კოდს, რომელიც ბინარული ქეშიდან მოვიდა. Tuist-ის ატვირთვა ზომავს ორივეს. თუ გსურთ სამიზნის დაფარვა Xcode-ის ანგარიშში, აგენერირეთ პროექტი ისე, რომ ეს სამიზნე აგებული იყოს წყაროდან: `tuist generate MyTarget` ტოვებს `MyTarget`-ს წყაროდ და დანარჩენს იღებს ქეშიდან.

## დაფარვის მოთხოვნა {#querying}

`tuist coverage` ბრძანებები კითხულობენ იმას, რასაც დაფა აჩვენებს. `--commit`-ის გარეშე, ისინი კითხულობენ `--branch`-ის ან თქვენი ძირითადი ბრენჩის უახლეს სრულ კომიტს:

```sh
tuist coverage show                          # the project's coverage and its targets
tuist coverage files --commit <sha>          # files, least covered first
tuist coverage file Sources/Cart.swift --lines  # a file's functions, with per-line counts
```

ყველა მათგანი იღებს `--json`-ს სკრიპტინგისთვის. იგივე მონაცემები ხელმისაწვდომია აგენტებისთვის <.localized_link href="/guides/features/agentic-coding/mcp">Model Context Protocol სერვერის</.localized_link> საშუალებით.
