# გენერირებული Xcode პროექტი {#generated-xcode-project-code-coverage}

> [!NOTE] EARLY ACCESS
> Xcode პროექტების კოდის დაფარვა ადრეულ წვდომაშია. [დაგვიკავშირდით](mailto:contact@tuist.dev), რათა ის თქვენს ანგარიშზე ჩართოთ. მანამდე Tuist არ ინახავს თქვენი გაშვებების მიერ ატვირთულ დაფარვას.

კოდის დაფარვა გიჩვენებთ, თუ რომელი ხაზები შესრულდა თქვენი ტესტების მიერ. Tuist ტვირთავს ყოველი `tuist test` გაშვების ხაზოვან დაფარვას და აერთებს ერთი კომიტის გაშვებებს ერთ მაჩვენებლად — პროექტის, თითოეული სამიზნისა და თითოეული ფაილისთვის. დაფის **კოდის დაფარვის** გვერდი აჩვენებს მას კომიტის მიხედვით და როგორც ტრენდს თითოეული შტოსთვის.

მაჩვენებელი ზუსტი რჩება მაშინაც, როცა Tuist გამოტოვებს სამუშაოს. თქვენი სამიზნეები <.localized_link href="/guides/features/cache/module-cache">ბინარული ქეშიდან</.localized_link> აგებულია დაფარვის მრიცხველებით, ამიტომ მათი კოდი იზომება ისევე, როგორც წყაროდან აგებული კოდი. და როცა <.localized_link href="/guides/features/selective-testing/generated-xcode-project">შერჩევითი ტესტირება</.localized_link> გამოტოვებს ტესტის სამიზნეს, სამიზნე ინარჩუნებს იმ დაფარვას, რაც მას ჰქონდა წინა გაშვებაში, [სამიზნის დონის დაფარვის](#target-level-coverage) მეშვეობით, რომელსაც Tuist აღრიცხავს ყოველ გაშვებაზე.

## მოწყობა {#setup}

### დაფარვის ჩართვა {#turn-coverage-on}

ჩართეთ დაფარვა თქვენი `Tuist.swift` გენერაციის პარამეტრებში და ჩართეთ დაფარვის ატვირთვა, რომელიც ნაგულისხმევად გამორთულია:

```swift
import ProjectDescription

let tuist = Tuist(
    testInsights: .testInsights(coverage: .coverage(upload: true)),
    project: .tuist(
        generationOptions: .options(
            coverage: .coverage(enabled: true)
        )
    )
)
```

გენერაციის პარამეტრის ჩართვისას:

- Tuist-ის მიერ გენერირებული ყოველი სქემის ტესტის მოქმედება აგროვებს დაფარვას, ასევე აგროვებს თქვენს მიერ განსაზღვრული ყოველი სქემის ტესტის მოქმედება, თუ `coverage` დატოვებულია დაყენებულად. სქემა `.options(coverage: false)`-ით ან `.options(coverage: true)`-ით ინარჩუნებს თავის მნიშვნელობას. ტესტის გეგმები თავად განსაზღვრავენ დაფარვას: Tuist-ის მიერ გენერირებული ტესტის გეგმებისთვის გადაეცით `coverage: true` `.testPlans(_:coverage:)`-ში.
- თქვენი პროექტის საკუთარი სამიზნეები იკითხება და შედის ბინარულ ქეშში დაფარვის მრიცხველებით Debug კონფიგურაციებში. იხილეთ [როგორ მუშაობს](#instrumented-binaries).

`TUIST_COVERAGE_ENABLED` და `TUIST_COVERAGE_UPLOAD` გარემოს ცვლადები (`1` ან `0`) უპირატესობას იღებენ `enabled` და `upload`-ზე. დააყენეთ ისინი მთლიანი გარემოსთვის, მაგალითად CI სამუშაო ნაკადისთვის, და არა ერთი ბრძანებისთვის, რათა ქეშის შემავსებელმა და მწკვრის წამკითხავმა ბრძანებებმა ერთმანეთთან შეთანხმებით იმუშაონ.

> [!IMPORTANT] KEEP THE VALUE THE SAME EVERYWHERE
> გენერაციის პარამეტრი ცვლის თქვენი პროექტის სამიზნეების ქეშის გასაღებებს და მისი ტესტის სამიზნეების შერჩევითი ტესტირების ჰეშებს. გამოიყენეთ ერთი და იგივე მნიშვნელობა ყოველ მანქანაზე, რომელიც იზიარებს ქეშს, და არ მიიღოთ ის გარემოდან (მაგალითად `Environment.isCI`-დან). გაშვება გამორთული დაფარვით არ იყენებს ხელახლა ბინარებს ან შერჩევითი ტესტირების შედეგებს ჩართული დაფარვის გაშვებებიდან.

### სქემების გამოტოვება {#leave-schemes-out}

ზოგიერთი ტესტის ნაკრები არ ეკუთვნის თქვენს დაფარვას. მაგალითად, მიღების ან end-to-end ტესტები, რომლებიც მართავენ თქვენს აპს ან CLI-ს სხვა პროცესიდან, ასრულებენ კოდს, რომლის დაფარვის დანახვაც შეუძლებელია, და მისი შეგროვება მხოლოდ ანელებს მათ. გამორთეთ დაფარვა მათი სქემის ტესტის მოქმედებაში:

```swift
.scheme(
    name: "AcceptanceTests",
    testAction: .targets(
        ["AcceptanceTests"],
        options: .options(coverage: false)
    )
)
```

სქემა ინარჩუნებს დაფარვას გამორთულად, მიუხედავად იმისა, რასაც ამბობს `Tuist.swift` პარამეტრი ან `TUIST_COVERAGE_ENABLED`, და მისი გაშვებები არ შედის კომიტის დაფარვაში. დაფარვა გროვდება სქემის მიხედვით, ამიტომ ერთი ტესტის სამიზნის გამოსატოვებლად გადაიტანეთ ის საკუთარ სქემაში.

### ტესტების გაშვება {#run-your-tests}

გაუშვით თქვენი ტესტები `tuist test`-ით, როგორც ჩვეულებრივ:

```sh
tuist test
```

Tuist ტვირთავს გაშვების მიერ შეგროვებულ დაფარვას მის ტესტის შედეგებთან ერთად. ეს მოიცავს <.localized_link href="/guides/features/test-sharding/generated-xcode-project">დაყოფილ გაშვებებს</.localized_link> და გაშვებებს, რომლებიც ამოწმებენ სხვა სამუშაოში აგებულ პროდუქტებს `--without-building`-ით. რომ გაშვების დაფარვა არ შევიდეს Tuist-ში, მაგალითად fork-ებიდან pull request-ების გამშვებ სამუშაოებში, დააყენეთ `TUIST_COVERAGE_UPLOAD=0`.

### CI-ზე თითოეული კომიტის დასრულება {#complete-each-commit}

კომიტის დაფარვა ხშირად რამდენიმე სამუშაოდან მოდის: ერთი სქემის, ერთი ნაწილის ან ერთი პლატფორმის მიხედვით. Tuist ვერ ხვდება, როდის მოახსენა ბოლომ მათგან, ამიტომ უთხარით მას. როგორც კი კომიტის ყველა ტესტის სამუშაო დასრულდება, გაუშვით ეს სამუშაოში, რომელიც დამოკიდებულია მათ ყველაზე:

```sh
tuist coverage complete
```

ბრძანება კითხულობს კომიტს checkout-იდან ან თქვენი CI პროვაიდერიდან; გადაეცით `--commit <sha>` სხვის დასახელებლად. სანამ კომიტი არ დასრულდება, მისი დაფარვა ჩანს როგორც **მიმდინარე** და არ შედის მისი შტოს ტრენდში.

### მთლიანი ნაკრების გაშვება თქვენს ნაგულისხმევ შტოზე {#full-runs}

> [!IMPORTANT] SET UP A FULL RUN
> შერჩევითი ტესტირება მხოლოდ მაშინ ინარჩუნებს კომიტის დაფარვას სრულად, თუ არსებობს წინა გაშვება, საიდანაც გამოტოვებული სამიზნეების გადატანაა შესაძლებელი. დაგეგმეთ ყოველი ტესტის გაშვება, შერჩევითი ტესტირების გარეშე, თქვენს ნაგულისხმევ შტოზე:
>
> ```sh
> tuist test --no-selective-testing
> ```
>
> იდეალურია ერთხელ ყოველ merge-ზე. ყოველდღიური ან ყოველკვირეული შეიძლება საკმარისი იყოს რეპოზიტორიისთვის, სადაც ცვლილებები ცოტაა. ჩაწერილი დაფარვა იწურება 90 დღის შემდეგ, ამიტომ გაუშვით ის უფრო ხშირად.

გადატანილი დაფარვა ეყრდნობა სრულ გაშვებებს. ისინი ანახლებენ თითოეული სამიზნის ჩაწერილ დაფარვას მის ამოწურვამდე და აძლევენ Tuist-ს ფაილების ბოლო მდგომარეობას, რომლებსაც შერჩევითი გაშვება არ აგებს. რაც უფრო მეტად იცვლება რეპოზიტორია სრულ გაშვებებს შორის, მით უფრო ხშირად პოულობს შერჩევითი გაშვება ფაილს, რომელიც მას შემდეგ შეიცვალა და მისი კომიტის დაფარვა არის **არასრული**.

## სამიზნის დონის დაფარვა {#target-level-coverage}

გაშვების დაფარვა გვიჩვენებს, რა შეასრულა მთლიანმა გაშვებამ და არა ის, რა შეასრულა თითოეულმა ტესტის სამიზნემ. როცა შერჩევითი ტესტირება გამოტოვებს სამიზნეს, Tuist-მა უნდა იცოდეს, რა შეასრულა იმ სამიზნემ წინა გაშვებაში, რათა მისი დაფარვა გადაიტანოს.

ამიტომ ყოველ გაშვებაზე Tuist ასევე აღრიცხავს, რომელი ფაილები და ხაზები შეასრულა თითოეულმა ტესტის სამიზნემ. ის კითხულობს მათ იმ დაფარვიდან, რომელსაც Xcode წერს თითოეული ტესტის პროცესისთვის, ამიტომ არაფერია დასაკავშირებელი ან დასაკონფიგურირებელი. ის იწერება macOS-ზე და iOS სიმულატორზე, არა მოწყობილობებზე. UI ტესტები არაფერს აღრიცხავენ აპის შესახებ, რომელსაც ისინი მართავენ, რადგან აპის კოდი საკუთარ პროცესში მუშაობს.

## როგორ მუშაობს {#how-it-works}

### ინსტრუმენტირებული ბინარები {#instrumented-binaries}

ბინარული ქეშიდან აღებული სამიზნე არის წინასწარ აგებული ბინარი და ტესტის გაშვება მის კოდს მხოლოდ მაშინ ზომავს, თუ ბინარი აგებული იყო დაფარვის მრიცხველებით. ჩართული დაფარვისას ბინარული ქეში ინახავს თქვენი პროექტის საკუთარი სამიზნეების ინსტრუმენტირებულ ვარიანტს და ყოველი ბრძანება კითხულობს და ავსებს ამ ვარიანტს:

- **Debug კონფიგურაციები** იყენებენ ინსტრუმენტირებულ ვარიანტს: `tuist cache` ავსებს მას, ხოლო `tuist generate` და `tuist test` კითხულობენ მას.
- **Release კონფიგურაციები** ყოველთვის იყენებენ ჩვეულებრივ ვარიანტს, ამიტომ რასაც თქვენ აგზავნით, არასდროს შეიცავს დაფარვის მრიცხველებს.
- **გარე პაკეტები** ყოველთვის იყენებენ ჩვეულებრივ ვარიანტს. Tuist ზომავს მხოლოდ თქვენი რეპოზიტორიის კოდს.

შეავსეთ ქეში ჩართული დაფარვით, იმავე გარემოში, რაშიც თქვენი ტესტის სამუშაოები მუშაობენ, რათა `tuist test` იპოვოს ინსტრუმენტირებული ბინარები. როცა გაშვება აგროვებს დაფარვას, მაგრამ იღებს თქვენს სამიზნეებს ქეშიდან ჩვეულებრივი ბინარების სახით, Tuist გაფრთხილებთ და მათი კოდი არ იზომება. <.localized_link href="/guides/features/cache/module-cache#code-coverage">მოდულის ქეში</.localized_link> დეტალურად აღწერს ვარიანტებს.

### გზები მანქანებს შორის {#paths-across-machines}

ინსტრუმენტირებული ბინარები აღრიცხავენ თავიანთ წყაროს გზებს იმ checkout-ის მიმართ, სადაც ისინი აიგნენ, ამიტომ CI-ზე შევსებული ბინარი ზომავს სწორ ფაილებს ნებისმიერი დეველოპერის მანქანაზე.

<.localized_link href="/guides/features/cache/xcode-cache">Xcode ქეში</.localized_link> მუშაობს იმავე პრინციპით პრეფიქსების მაპინგის მეშვეობით, რასაც Tuist ნაგულისხმევად თიშავს იმ აგებებში, რომლებიც აგროვებენ დაფარვას, რადგან Xcode-ის საკუთარი დაფარვის ანგარიში ვერ ხსნის მაპირებულ გზებს. Xcode 27-ზე და უფრო ახალ ვერსიებზე, როცა `enableCaching` ჩართულია, `prefixMapping: true` ტოვებს მას ჩართულს, რათა დაფარვის აგებები გაუზიარონ კომპილაციის შედეგები checkout-ებს შორისაც:

```swift
.options(coverage: .coverage(enabled: true, prefixMapping: true))
```

Tuist-ის ატვირთვა ხსნის მაპირებულ გზებს, მაგრამ Xcode-ის დაფარვის ანგარიშმა და `xccov`-მა შეიძლება გამოტოვონ ეს ფაილები. იხილეთ <.localized_link href="/guides/features/cache/xcode-cache#coverage-with-prefix-mapping">დაფარვა პრეფიქსების მაპინგით</.localized_link>.

### გამოტოვებული ტესტები {#skipped-tests}

შერჩევითი ტესტირება ტოვებს ტესტის სამიზნეს, თუ წინა წარმატებულმა გაშვებამ უკვე შეამოწმა ის იგივე ჰეშით. ჰეში მოიცავს სამიზნის წყაროებს, მის ტესტებს და ყველა დამოკიდებულებას, ამიტომ იგივე ჰეში ნიშნავს იგივე ტესტებს იგივე კოდზე. Tuist იყენებს ხელახლა [სამიზნის დონის დაფარვას](#target-level-coverage), რომელიც იმ ადრეულმა გაშვებამ აღრიცხა ამ სამიზნისთვის. თუ არაფერი აღურიცხავს, მაგალითად, იმიტომ რომ დაფარვა მაშინ გამორთული იყო ან გაშვება 90 დღეზე ძველია, გადასატანი არაფერია და კომიტი არის **არასრული**.

შერჩევითი გაშვება ასევე არ აგებს ყველა ფაილს. იმ ფაილებისთვის, რომლებიც მან არ დააკომპილირა, Tuist იღებს სტრიქონებს უახლოესი წინა სრული გაშვებიდან, იმ პირობით, რომ ფაილები მას შემდეგ არ შეცვლილა. სწორედ ამიტომ არის მნიშვნელოვანი [სრული გაშვებები](#full-runs) თქვენს ძირითად ბრენჩზე.

ტესტები, რომლებსაც თქვენ თავად ტოვებთ `--skip-test-targets`-ის ან `-skip-testing`-ის მეშვეობით, არ გადააქვთ წინ: კომიტი, რომლის გაშვებებმაც ისინი გამოტოვეს, არის **არასრული**, თუ კომიტზე სხვა გაშვებამ არ გაუშვა ისინი. ტესტები, რომლებსაც კარანტინი ტოვებს, საერთოდ არ არის დაფარვის ნაწილი: Tuist არც გადააქვს ისინი და არც მონიშნავს კომიტს **არასრულად** მათ გამო.

### სრული და არასრული კომიტები {#commit-status}

დაფარდაშის თითოეულ კომიტს აქვს სტატუსი:

| სტატუსი | მნიშვნელობა |
| --- | --- |
| მიმდინარეობს | გაშვებებმა მოახსენეს დაფარვა, მაგრამ `tuist coverage complete` ჯერ არ გაუშვია კომიტისთვის. |
| სრული | კომიტის სქემების ყველა ტესტი გაშვებულია ან გადატანილია წინ. |
| არასრული | ზოგიერთი დაფარვის განსაზღვრა ვერ მოხერხდა, ამიტომ მაჩვენებელი არის ქვედა ზღვარი. |
| არ არის გაზომილი | არცერთ გაშვებას არ მოუხსენებია დაფარვა კომიტისთვის. |

ბრენჩის ტრენდი მოიცავს მხოლოდ სრულ კომიტებს. კომიტი არასრულია, მაგალითად, როცა:

- შერჩევითმა ტესტირებამ გამოტოვა სამიზნე, რომლის გადატანაც შეუძლებელი იყო: ადრეულმა გაშვებამ მისთვის არ აღრიცხა დაფარვა, ფაილი, რომელიც შერჩევითმა გაშვებამ არ ააგო, შეიცვალა ბოლო სრული გაშვების შემდეგ, ან კომიტმა შეცვალა ფაილები, რომლებიც ყველა სამიზნეს ეხება, როგორიცაა `Package.resolved`, `Project.swift` ან `.xcconfig`.
- გაშვებამ გამოტოვა ტესტები `--skip-test-targets`-ის ან `-skip-testing`-ის მეშვეობით და კომიტზე სხვა გაშვებამ არ გაუშვა ისინი.
- გაშვებამ აიღო თქვენი სამიზნეები ბინარული ქეშიდან ჩვეულებრივი ბინარების სახით.
- სქემის ყველა გაშვება შევიწროვდა `-only-testing`-ით.
- სქემის დაფარვა მიიღეს მხოლოდ CI გაშვებებიდან checkout-ზე, სადაც იყო დაუფიქსირებელი ცვლილებები.

## წარმადობაზე გავლენა {#performance-impact}

დაფარვის შეგროვება მატებს დამატებით დატვირთვას, ძირითადად ტესტების დასრულების შემდეგ, როცა Xcode წერს თავის დაფარვის ანგარიშს და Tuist აგდებს დაფარვას. ტესტების აგება და გაშვება დაახლოებით იმდენსვე დროს მოითხოვს, რამდენსაც მის გარეშე. ინსტრუმენტირებული აგებები ასევე იკავებენ მეტ დისკის სივრცეს, DerivedData-ში და Debug ბინარულ ქეშში. Release აგებებსა და არქივებზე ეს არ მოქმედებს.

## შეზღუდვები {#limitations}

### Release აგებები სქემებისთვის, რომლებიც აგროვებენ დაფარვას {#release-builds}

როცა სქემის ტესტის მოქმედება აგროვებს დაფარვას, Xcode ასევე აინსტრუმენტებს სამიზნეებს, რომლებსაც `xcodebuild build` აკომპილირებს წყაროდან ამ სქემისთვის, ნებისმიერ კონფიგურაციაში, Release-ის ჩათვლით. `xcodebuild archive` იგნორირებს ამ პარამეტრს, ამიტომ არქივები არასდროს არის ინსტრუმენტირებული. გაავრცელეთ არქივები ან ააგეთ Release პროდუქტები სქემიდან `.options(coverage: false)`-ით.

### სხვა დაფარვის ინსტრუმენტები {#other-coverage-tools}

`-enableCodeCoverage YES` მხოლოდ გადაწყვეტს, აგროვებს თუ არა გაშვება დაფარვას, როგორც Xcode-ში. ის არ აიძულებს Tuist-ს წაიკითხოს ინსტრუმენტირებული ბინარები ქეშიდან, ამიტომ გამოიყენეთ `Tuist.swift` პარამეტრი ან `TUIST_COVERAGE_ENABLED`.

იმისთვის, რომ მიაწოდოთ სხვა დაფარვის ინსტრუმენტს, აიძულეთ `tuist test`-მა ჩაწეროს თითოეული გაშვების დაფარვა LCOV ფორმატში. ეს არის იგივე დაფარვა, რასაც Tuist ტვირთავს, რეპოზიტორიის მიმართებითი გზებით და ბინარული ქეშიდან მიღებული კოდის ჩათვლით:

```sh
tuist test --coverage-output-path coverage
```

თითოეული გაშვება წერს `coverage/<result bundle name>.lcov`. გააერთიანეთ შარდირებული გაშვების ფაილები `lcov -a`-ით. პარამეტრი მოითხოვს დაფარვის ატვირთვის ჩართვას.

Xcode-ის საკუთარი დაფარვის ანგარიში და მისი წამკითხავი ინსტრუმენტები მოიცავენ მხოლოდ იმ სამიზნეებს, რომლებიც Xcode-მა ააგო ამ გაშვებაში, არასდროს კოდს, რომელიც ბინარული ქეშიდან მოვიდა. Tuist-ის ატვირთვა ზომავს ორივეს. თუ გსურთ სამიზნის დაფარვა Xcode-ის ანგარიშში, აგენერირეთ პროექტი ისე, რომ ეს სამიზნე აიგოს წყაროდან: `tuist generate MyTarget` ტოვებს `MyTarget`-ს წყაროდ და დანარჩენს იღებს ქეშიდან.

## დაფარვის მოთხოვნა {#querying}

`tuist coverage` ბრძანებები კითხულობენ იმას, რასაც დაფარდაში აჩვენებს. `--commit`-ის გარეშე, ისინი კითხულობენ `--branch`-ის ან თქვენი ძირითადი ბრენჩის უახლეს სრულ კომიტს:

```sh
tuist coverage show                          # the project's coverage and its targets
tuist coverage files --commit <sha>          # files, least covered first
tuist coverage file Sources/Cart.swift --lines  # a file's functions, with per-line counts
```

ყველა მათგანი იღებს `--json`-ს სკრიპტინგისთვის. იგივე მონაცემები ხელმისაწვდომია აგენტებისთვის <.localized_link href="/guides/features/agentic-coding/mcp">Model Context Protocol სერვერის</.localized_link> მეშვეობით.
