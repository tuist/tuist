# გენერირებული Xcode პროექტი {#generated-xcode-project-code-coverage}

კოდის დაფარვა გიჩვენებს, თუ კოდის რომელი ხაზები შეასრულეს თქვენმა ტესტებმა. Tuist ატვირთავს ხაზოვან დაფარვას ყოველი `tuist test` გაშვებისთვის და აჯამებს კომიტის გაშვებებს ერთ რიცხვად — პროექტის, თითოეული სამიზნისა და თითოეული ფაილის მიხედვით. დაფის **Code Coverage** გვერდი აჩვენებს მას კომიტების მიხედვით და როგორც ტრენდს თითოეული შტოსთვის.

<!-- @snippet: ./_xcode-requirements -->

რიცხვი ზუსტი რჩება მაშინაც, როცა Tuist გამოტოვებს სამუშაოს. თქვენი სამიზნეები <.localized_link href="/guides/features/cache/module-cache">ბინარული ქეშიდან</.localized_link> აგებულია დაფარვის მრიცხველებით, ამიტომ მათი კოდი იზომება ისევე, როგორც წყაროდან აგებული კოდი. ხოლო როცა <.localized_link href="/guides/features/selective-testing/generated-xcode-project">შერჩევითი ტესტირება</.localized_link> გამოტოვებს ტესტის სამიზნეს, სამიზნე ინარჩუნებს ადრეულ გაშვებაში მიღებულ დაფარვას [სამიზნის დონის დაფარვის](#target-level-coverage) მეშვეობით, რომელსაც Tuist აღრიცხავს ყოველ გაშვებაზე.

## მოწყობა {#setup}

### დაფარვის ჩართვა {#turn-coverage-on}

ჩართეთ დაფარვა თქვენი `Tuist.swift`-ის გენერაციის პარამეტრებში და ჩართეთ დაფარვის ატვირთვა, რომელიც ნაგულისხმევად გამორთულია:

```swift
import ProjectDescription

let tuist = Tuist(
    testInsights: .testInsights(coverage: .coverage(upload: true)),
    project: .tuist(
        generationOptions: .options(
            coverage: .coverage(enabled: true)
        )
    )
)
```

როცა გენერაციის პარამეტრი ჩართულია:

- ყოველი სქემის ტესტის მოქმედება, რომელსაც Tuist აგენერირებს, აგროვებს დაფარვას; ასევე აგროვებს ყოველი თქვენს მიერ განსაზღვრული სქემის ტესტის მოქმედება, თუ `coverage` არ არის მითითებული. სქემა `.options(coverage: false)`-ით ან `.options(coverage: true)`-ით ინარჩუნებს თავის მნიშვნელობას. ტესტ-პლანები თავად განსაზღვრავენ დაფარვას: Tuist-ის მიერ გენერირებული ტესტ-პლანებისთვის გადაეცით `coverage: true` პარამეტრად `.testPlans(_:coverage:)`-ში.
- თქვენი პროექტის საკუთარი სამიზნეები იკითხება და თბება ბინარულ ქეშში Debug კონფიგურაციებში დაფარვის მრიცხველებით. იხილეთ [როგორ მუშაობს](#instrumented-binaries).

გარემოს ცვლადები `TUIST_COVERAGE_ENABLED` და `TUIST_COVERAGE_UPLOAD` (`1` ან `0`) აქვთ უპირატესობა `enabled` და `upload` პარამეტრებთან მიმართებაში. დააყენეთ ისინი მთლიანი გარემოსთვის, მაგალითად CI სამუშაო ნაკადისთვის, და არა ერთი ბრძანებისთვის, რათა ქეშის გამთბობმა და მკითხავმა ბრძანებებმა შეთანხმებულად იმუშაონ.

> [!IMPORTANT] KEEP THE VALUE THE SAME EVERYWHERE
> გენერაციის პარამეტრი ცვლის თქვენი პროექტის სამიზნეების ქეშის გასაღებებს და მათი ტესტის სამიზნეების შერჩევითი ტესტირების ჰეშებს. გამოიყენეთ ერთი და იგივე მნიშვნელობა ყველა იმ მანქანაზე, რომელიც იზიარებს ქეშს, და არ მიიღოთ ის გარემოდან (მაგალითად, `Environment.isCI`-დან). გაშვება გამორთული დაფარვით არ იყენებს ხელახლა ბინარებს ან შერჩევითი ტესტირების შედეგებს ჩართული დაფარვის გაშვებებიდან.

### სქემების გამოტოვება {#leave-schemes-out}

ზოგიერთი ტესტ-სიუტი არ ეკუთვნის თქვენს დაფარვას. მაგალითად, მიღების ან end-to-end ტესტები, რომლებიც მართავენ თქვენს აპს ან CLI-ს სხვა პროცესიდან, ასრულებენ კოდს, რომლის დაფარვასაც ვერ ხედავთ, და მისი შეგროვება მხოლოდ ანელებს მათ. გამორთეთ დაფარვა მათი სქემის ტესტის მოქმედებაში:

```swift
.scheme(
    name: "AcceptanceTests",
    testAction: .targets(
        ["AcceptanceTests"],
        options: .options(coverage: false)
    )
)
```

სქემა ინარჩუნებს დაფარვას გამორთულს, მიუხედავად იმისა, რასაც `Tuist.swift` პარამეტრი ან `TUIST_COVERAGE_ENABLED` ამბობს, და მისი გაშვებები არ შედიან კომიტის დაფარვაში. დაფარვა გროვდება სქემის მიხედვით, ამიტომ ერთი ტესტის სამიზნის გამოსატოვებლად გადაიტანეთ ის საკუთარ სქემაში.

### ტესტების გაშვება {#run-your-tests}

გაუშვით თქვენი ტესტები `tuist test`-ით, როგორც ჩვეულებრივ:

```sh
tuist test
```

Tuist ატვირთავს გაშვების მიერ შეგროვებულ დაფარვას ტესტის შედეგებთან ერთად. ეს მოიცავს <.localized_link href="/guides/features/test-sharding/generated-xcode-project">დაყოფილ გაშვებებს</.localized_link> და გაშვებებს, რომლებიც ტესტავენ სხვა სამუშაოში `--without-building`-ით აგებულ პროდუქტებს. Tuist-ში გაშვების დაფარვის გამოსატოვებლად, მაგალითად fork-ებიდან მოსული pull request-ების გამშვებ სამუშაოებში, დააყენეთ `TUIST_COVERAGE_UPLOAD=0`.

### ყოველი კომიტის დასრულება CI-ზე {#complete-each-commit}

კომიტის დაფარვა ხშირად მოდის რამდენიმე სამუშაოდან: ერთი სქემის, ერთი ნაწილის ან ერთი პლატფორმის მიხედვით. Tuist ვერ ხვდება, როდის ანგარიშგაუწია ბოლომ, ამიტომ შეატყობინეთ. როგორც კი კომიტის ყველა ტესტის სამუშაო დასრულდება, გაუშვით ეს ბრძანება სამუშაოში, რომელიც დამოკიდებულია მათ ყველაზე:

```sh
tuist coverage complete
```

ბრძანება კითხულობს კომიტს checkout-იდან ან თქვენი CI პროვაიდერიდან; სხვის მისათითებლად გადაეცით `--commit <sha>`. სანამ კომიტი არ დასრულდება, მისი დაფარვა ჩანს როგორც **In progress** და არ შედის შტოს ტრენდში.

### მთლიანი სიუტის გაშვება ნაგულისხმევ შტოზე {#full-runs}

> [!IMPORTANT] SET UP A FULL RUN
> შერჩევითი ტესტირება მხოლოდ მაშინ ინარჩუნებს კომიტის დაფარვას სრულად, თუ არსებობს ადრეული გაშვება, საიდანაც გამოტოვებული სამიზნეების გადატანაა შესაძლებელი. დაგეგმეთ ყოველი ტესტის გაშვება შერჩევითი ტესტირების გარეშე თქვენს ნაგულისხმევ შტოზე:
>
> ```sh
> tuist test --no-selective-testing
> ```
>
> იდეალურია ერთხელ ყოველ merge-ზე. დღიური ან კვირეული შეიძლება საკმარისი იყოს რეპოზიტორიისთვის, სადაც ცვლილებები ცოტაა. ჩაწერილი დაფარვა იწურება 31 დღის შემდეგ, ამიტომ გაუშვით უფრო ხშირად.

გადატანილი დაფარვა ეყრდნობა სრულ გაშვებებს. ისინი ანახლებენ ყოველი სამიზნის ჩაწერილ დაფარვას მის ამოწურვამდე და აწვდიან Tuist-ს ფაილების ბოლო მდგომარეობას, რომელსაც შერჩევითი გაშვება არ აგებს. რაც უფრო მეტად იცვლება რეპოზიტორია სრულ გაშვებებს შორის, მით უფრო ხშირად პოულობს შერჩევითი გაშვება ფაილს, რომელიც მას შემდეგ შეიცვალა, და კომიტის დაფარვა ხდება **Incomplete**.

## სამიზნის დონის დაფარვა {#target-level-coverage}

გაშვების დაფარვა გვიჩვენებს, რა შეასრულა მთლიანმა გაშვებამ და არა ის, რა შეასრულა თითოეულმა ტესტის სამიზნემ. როცა შერჩევითი ტესტირება გამოტოვებს სამიზნეს, Tuist-ს სჭირდება იცოდეს, რა შეასრულა ამ სამიზნემ ადრეულ გაშვებაში, რათა გადაიტანოს მისი დაფარვა.

ამიტომ ყოველ გაშვებაზე Tuist ასევე აღრიცხავს, თუ რომელი ფაილები და ხაზები შეასრულა თითოეულმა ტესტის სამიზნემ. ის კითხულობს მათ Xcode-ის მიერ თითოეული ტესტის პროცესისთვის ჩაწერილი დაფარვიდან, ამიტომ არაფრის დაკავშირება ან კონფიგურირება არ არის საჭირო. ის იწერება macOS-ზე და iOS სიმულატორზე, არა მოწყობილობებზე. UI ტესტები არაფერს აღრიცხავენ აპის შესახებ, რომელსაც მართავენ, რადგან აპის კოდი საკუთარ პროცესში მუშაობს.

## როგორ მუშაობს {#how-it-works}

### ინსტრუმენტირებული ბინარები {#instrumented-binaries}

ბინარული ქეშიდან აღებული სამიზნე არის წინასწარ აგებული ბინარი, და ტესტის გაშვებას შეუძლია მისი კოდის გაზომვა მხოლოდ მაშინ, თუ ბინარი აგებულია დაფარვის მრიცხველებით. ჩართული დაფარვის პირობებში, ბინარული ქეში ინახავს თქვენი პროექტის საკუთარი სამიზნეების ინსტრუმენტირებულ ვარიანტს, და ყოველი ბრძანება კითხულობს და ათბობს ამ ვარიანტს:

- **Debug კონფიგურაციები** იყენებენ ინსტრუმენტირებულ ვარიანტს: `tuist cache` ათბობს მას, ხოლო `tuist generate` და `tuist test` კითხულობენ.
- **Release კონფიგურაციები** ყოველთვის იყენებენ ჩვეულებრივ ვარიანტს, ამიტომ თქვენს მიერ მიწოდებულ პროდუქტს არასდროს აქვს დაფარვის მრიცხველები.
- **გარე პაკეტები** ყოველთვის იყენებენ ჩვეულებრივ ვარიანტს. Tuist ზომავს მხოლოდ თქვენი რეპოზიტორიის კოდს.

გაათბეთ ქეში ჩართული დაფარვით, იმავე გარემოში, სადაც თქვენი ტესტის სამუშაოები მუშაობენ, რათა `tuist test` იპოვოს ინსტრუმენტირებული ბინარები. როცა გაშვება აგროვებს დაფარვას, მაგრამ იღებს თქვენს სამიზნეებს ქეშიდან ჩვეულებრივი ბინარების სახით, Tuist გაფრთხილებთ და მათი კოდი არ იზომება. <.localized_link href="/guides/features/cache/module-cache#code-coverage">მოდულის ქეში</.localized_link> დეტალურად აღწერს ვარიანტებს.

### გზები მანქანებს შორის {#paths-across-machines}

ინსტრუმენტირებული ბინარები აღრიცხავენ წყაროს გზებს იმ checkout-ის მიმართ, სადაც ისინი აიგნენ, ამიტომ CI-ზე გამთბარი ბინარი ზომავს სწორ ფაილებს ნებისმიერი დეველოპერის მანქანაზე.

<.localized_link href="/guides/features/cache/xcode-cache">Xcode-ის ქეში</.localized_link> მუშაობს იმავე პრინციპით პრეფიქსების მიბმის საშუალებით, რასაც Tuist ნაგულისხმევად თიშავს დაფარვის შეგროვებისას აგებულ ბილდებში, რადგან Xcode-ის საკუთარი დაფარვის ანგარიში ვერ ხსნის მიბმულ გზებს. Xcode 27-სა და უფრო ახალ ვერსიებში, როცა `enableCaching` ჩართულია, `prefixMapping: true` ტოვებს მას ჩართულს, ამიტომ დაფარვის ბილდები ასევე იზიარებენ კომპილაციის შედეგებს checkout-ებს შორის:

```swift
.options(coverage: .coverage(enabled: true, prefixMapping: true))
```

Tuist-ის ატვირთვა ხსნის მიბმულ გზებს, მაგრამ Xcode-ის დაფარვის ანგარიშმა და `xccov`-მა შეიძლება გამოტოვონ ეს ფაილები. იხილეთ <.localized_link href="/guides/features/cache/xcode-cache#coverage-with-prefix-mapping">დაფარვა პრეფიქსების მიბმით</.localized_link>.

### გამოტოვებული ტესტები {#skipped-tests}

შერჩევითი ტესტირება ტოვებს ტესტის სამიზნეს, თუ წინა წარმატებულმა გაშვებამ ის უკვე შეამოწმა იგივე ჰეშით. ჰეში მოიცავს სამიზნის წყაროებს, მის ტესტებსა და ყველა დამოკიდებულებას, ამიტომ იგივე ჰეში ნიშნავს იგივე ტესტებს იგივე კოდზე. Tuist იყენებს ხელახლა [სამიზნის დონის დაფარვას](#target-level-coverage), რომელიც წინა გაშვებამ ჩაწერა ამ სამიზნისთვის. თუ არაფერი ჩაწერილა, მაგალითად იმიტომ, რომ მაშინ დაფარვა გამორთული იყო ან გაშვება 31 დღეზე მეტი ხნისაა, გადასატანი არაფერია და კომიტი არის **არასრული**.

შერჩევითი გაშვება ასევე არ აგებს ყველა ფაილს. ფაილებისთვის, რომლებიც მან არ ააგო, Tuist იღებს სტრიქონებს უახლოესი წინა სრული გაშვებიდან, იმ პირობით, რომ ფაილები მას შემდეგ არ შეცვლილა. სწორედ ამიტომ არის მნიშვნელოვანი თქვენს ძირითად შტოზე შესრულებული [სრული გაშვებები](#full-runs).

ტესტები, რომლებსაც თქვენ თვითონ ტოვებთ `--skip-test-targets`-ით ან `-skip-testing`-ით, არ გადაიტანება: კომიტი, რომლის გაშვებებმაც ისინი გამოტოვა, არის **არასრული**, თუ კომიტზე სხვა გაშვებამ არ გაუშვა ისინი. ტესტები, რომლებსაც კარანტინი ტოვებს, საერთოდ არ შედიან დაფარვაში: Tuist არც გადააქვს ისინი და არც აღნიშნავს კომიტს **არასრულად** მათ გამო.

### სრული და არასრული კომიტები {#commit-status}

დაფარვის დაფაზე თითოეულ კომიტს აქვს სტატუსი:

| სტატუსი | მნიშვნელობა |
| --- | --- |
| მიმდინარე | გაშვებებმა შეატყობინეს დაფარვა, მაგრამ `tuist coverage complete` ჯერ არ შესრულებულა ამ კომიტისთვის. |
| სრული | კომიტის სქემების ყველა ტესტი გაშვებული იყო ან გადატანილი. |
| არასრული | ზოგიერთი დაფარვის განსაზღვრა ვერ მოხერხდა, ამიტომ მაჩვენებელი ქვედა ზღვარია. |
| არ გაზომილა | არცერთ გაშვებას არ შეუტყობინებია დაფარვა ამ კომიტისთვის. |

შტოს ტრენდი მოიცავს მხოლოდ სრულ კომიტებს. კომიტი არასრულია, მაგალითად, როცა:

- შერჩევითმა ტესტირებამ გამოტოვა სამიზნე, რომლის გადატანაც შეუძლებელი იყო: წინა გაშვებამ მისთვის არ ჩაწერა დაფარვა, ფაილი, რომელიც შერჩევითმა გაშვებამ არ ააგო, შეიცვალა ბოლო სრული გაშვების შემდეგ, ან კომიტმა შეცვალა ფაილები, რომლებიც ყველა სამიზნეს ეხება, როგორიცაა `Package.resolved`, `Project.swift` ან `.xcconfig`.
- გაშვებამ გამოტოვა ტესტები `--skip-test-targets`-ით ან `-skip-testing`-ით და კომიტზე სხვა გაშვებამ არ გაუშვა ისინი.
- გაშვებამ აიღო თქვენი სამიზნეები ბინარული ქეშიდან ჩვეულებრივი ბინარების სახით.
- სქემის ყველა გაშვება შევიწროვდა `-only-testing`-ით.
- სქემის დაფარვა მიღებული იყო მხოლოდ CI-ის გაშვებებიდან checkout-ზე, სადაც იყო დაუფიქსირებელი ცვლილებები.

## წარმადობაზე გავლენა {#performance-impact}

დაფარვის შეგროვება ზრდის დამატებით დატვირთვას, ძირითადად ტესტების დასრულების შემდეგ, როცა Xcode წერს თავის დაფარვის ანგარიშს და Tuist აექსპორტებს დაფარვას. ტესტების აგება და გაშვება დაახლოებით იმავე დროს იკავებს, რაც მის გარეშე. ინსტრუმენტირებული ბილდები ასევე იკავებენ მეტ ადგილს დისკზე, DerivedData-ში და Debug ბინარულ ქეშში. Release ბილდებსა და არქივებზე ეს გავლენას არ ახდენს.

## შეზღუდვები {#limitations}

### Release ბილდები სქემებისთვის, რომლებიც აგროვებენ დაფარვას {#release-builds}

როცა სქემის ტესტის მოქმედება აგროვებს დაფარვას, Xcode ასევე აინსტრუმენტებს სამიზნეებს, რომლებსაც `xcodebuild build` აგებს წყაროდან ამ სქემისთვის, ნებისმიერ კონფიგურაციაში, Release-ის ჩათვლით. `xcodebuild archive` იგნორირებს ამ პარამეტრს, ამიტომ არქივები არასდროს არის ინსტრუმენტირებული. გაავრცელეთ არქივები, ან ააგეთ Release პროდუქტები სქემიდან `.options(coverage: false)`-ით.

### სხვა დაფარვის ინსტრუმენტები {#other-coverage-tools}

`-enableCodeCoverage YES` მხოლოდ განსაზღვრავს, აგროვებს თუ არა გაშვება დაფარვას, როგორც Xcode-ში. ის არ აიძულებს Tuist-ს წაიკითხოს ინსტრუმენტირებული ბინარები ქეშიდან, ამიტომ გამოიყენეთ `Tuist.swift` პარამეტრი ან `TUIST_COVERAGE_ENABLED`.

სხვა დაფარვის ინსტრუმენტისთვის მონაცემების გადასაცემად, აიძულეთ `tuist test`-მ ჩაწეროს თითოეული გაშვების დაფარვა LCOV ფორმატში. ეს არის იგივე დაფარვა, რასაც Tuist ატვირთავს, რეპოზიტორიის მიმართ ფარდობითი გზებით და ბინარული ქეშიდან მიღებული კოდის ჩათვლით:

```sh
tuist test --coverage-output-path coverage
```

თითოეული გაშვება წერს `coverage/<result bundle name>.lcov`. გააერთიანეთ დაშლილი გაშვების ფაილები `lcov -a`-ით. პარამეტრი მოითხოვს დაფარვის ატვირთვის ჩართვას.

Xcode-ის საკუთარი დაფარვის ანგარიში და მისი წამკითხავი ინსტრუმენტები მოიცავენ მხოლოდ იმ სამიზნეებს, რომლებიც Xcode-მ ააგო ამ გაშვებაში, არასდროს კოდს, რომელიც ბინარული ქეშიდან მოვიდა. Tuist-ის ატვირთვა ზომავს ორივეს. თუ გსურთ სამიზნის დაფარვა Xcode-ის ანგარიშში, დააგენერირეთ პროექტი ისე, რომ ეს სამიზნე აგებული იყოს წყაროდან: `tuist generate MyTarget` ტოვებს `MyTarget`-ს წყაროდ და დანარჩენს იღებს ქეშიდან.

## დაფარვის მოთხოვნა {#querying}

`tuist coverage` ბრძანებები კითხულობენ იმას, რასაც დაფა აჩვენებს. `--commit`-ს გარეშე, ისინი კითხულობენ `--branch`-ის ან თქვენი ძირითადი შტოს უახლეს სრულ კომიტს:

```sh
tuist coverage show                          # the project's coverage and its targets
tuist coverage files --commit <sha>          # files, least covered first
tuist coverage file Sources/Cart.swift --lines  # a file's functions, with per-line counts
tuist coverage targets                       # targets, least covered first, then those taken from the binary cache without coverage
tuist coverage commits --branch main         # a branch's commits with their status and change, newest first
tuist coverage runs --commit <sha>           # the test runs behind a commit, marked full, partial or discarded
tuist coverage branches                      # the branches with coverage
```

ტესტის გაშვების საკუთარი დაფარვა ჩანს `tuist test show <test-run-id>`-ში.

ყველა მათგანი იღებს `--json`-ს სკრიპტინგისთვის. იგივე მონაცემები ხელმისაწვდომია აგენტებისთვის <.localized_link href="/guides/features/agentic-coding/mcp">Model Context Protocol სერვერის</.localized_link> საშუალებით.
