# Gradle-ის კოდის დაფარვა {#gradle-code-coverage}

კოდის დაფარვა გიჩვენებს, თუ რომელი ხაზები შესრულდა თქვენი ტესტების მიერ. Tuist-ის Gradle პლაგინი ზომავს თქვენი ტესტების ამოცანების დაფარვას JaCoCo-თი და ატვირთავს მას ყოველი ტესტების გაშვებისას, ხოლო Tuist აერთიანებს კომიტის გაშვებებს ერთ მაჩვენებლად — პროექტისთვის, თითოეული Gradle პროექტისთვის და თითოეული ფაილისთვის. დაფის **კოდის დაფარვის** გვერდი აჩვენებს მას კომიტის მიხედვით და როგორც ტენდენციას თითოეული შტოსთვის.

> [!IMPORTANT]
> **მოთხოვნები**
>
> - გამოყენებულია `dev.tuist` Gradle პლაგინი, როგორც აღწერილია <.localized_link href="/guides/get-started/gradle-project">დაიწყეთ Gradle პროექტით</.localized_link>
> - თქვენი პროექტი Git რეპოზიტორიაში: გაშვება რეპოზიტორიის გარეთ ატვირთავს ტესტების შედეგებს, მაგრამ არა დაფარვას

## მორგება {#setup}

### ჩართეთ დაფარვა {#turn-coverage-on}

ჩართეთ დაფარვა თქვენი `settings.gradle.kts`-ის `tuist` ბლოკში:

```kotlin
tuist {
    coverage {
        enabled = true
    }
}
```

ან ჩართეთ ის ერთი გამოძახებისთვის, მაგალითად CI სამუშაოსთვის, გარემოს ცვლადის მეშვეობით, რომელსაც აქვს უპირატესობა ნებისმიერ შემთხვევაში:

```sh
TUIST_TEST_COVERAGE=1 ./gradlew test
```

როცა დაფარვა ჩართულია, პლაგინი აკეთებს Gradle-ის `jacoco` პლაგინს ყველა JVM პროექტზე. JaCoCo-ს აგენტი მოდის თქვენი პროექტის რეპოზიტორიებიდან, ისევე როგორც თავად პლაგინის დამატების შემთხვევაში. პროექტი, რომელიც უკვე აკონფიგურირებს JaCoCo-ს, ინარჩუნებს თავის პარამეტრებს და მისი საკუთარი ანგარიშები განაგრძობენ მუშაობას.

### დაყოფილი გაშვებები {#sharded-runs}

როცა თქვენ <.localized_link href="/guides/features/test-sharding/gradle">ყოფთ თქვენს ტესტებს</.localized_link>, ყოველი ნაწილი, რომელიც გაშვებულია ჩართული დაფარვით, ანგარიშდება იმ ტესტების დაფარვას, რომლებიც მან გაუშვა, და Tuist აერთიანებს გაშვების ნაწილებს ერთ მაჩვენებლად. ნაწილი განზრახ ასრულებს სუიტის ნაწილს, ამიტომ ის არ ხდის კომიტის დაფარვას არასრულყოფილს.

### დაასრულეთ ყოველი კომიტი CI-ზე {#complete-each-commit}

კომიტის დაფარვა ხშირად მოდის რამდენიმე სამუშაოდან, მაგალითად, ერთი თითოეული ნაწილისთვის. Tuist-ს არ შეუძლია გაიგოს, როდის მოახსენა ბოლომ, ამიტომ უთხარით მას. როცა კომიტის ყველა ტესტის სამუშაო დასრულდება, გაუშვით ეს სამუშაოში, რომელიც დამოკიდებულია მათ ყველაზე:

```sh
./gradlew tuistCoverageComplete
```

ამოცანა კითხულობს კომიტს `GIT_COMMIT`-დან ან checkout-ის `HEAD`-დან; გადაეცით `-Ptuist.coverage.commit=<sha>` სხვის დასახელებლად. სანამ კომიტი არ დასრულდება, მისი დაფარვა ჩანს როგორც **მიმდინარე** და არ შედის მისი შტოს ტენდენციაში.

## როგორ მუშაობს {#how-it-works}

### რას ზომავს Tuist {#what-tuist-measures}

- **პროექტები.** თითოეული Gradle პროექტი არის მოდული დაფაზე, თავისი საკუთარი დაფარვით.
- **მხოლოდ პროდუქციის კოდი.** კლასები, რომლებიც კომპილირებულია ტესტის წყაროების სიმრავლეებიდან, არის ტესტის კოდი. Tuist ინახავს მათ, მაგრამ ტოვებს მათ ყველა მაჩვენებლის გარეთ.
- **თქვენი რეპოზიტორიის ფაილები.** კლასი ითვლება იმ საწყისი ფაილისთვის, საიდანაც ის კომპილირდა, მისი გზის მიხედვით თქვენს რეპოზიტორიაში. გენერირებული წყაროები და ფაილები, რომლებსაც Git იგნორირებს, არ არის მოხსენებული.
- **შესრულდა თუ არა თითოეული ხაზი.** JaCoCo აღრიცხავს, შესრულდა თუ არა კოდი, არა თუ რამდენჯერ, ამიტომ დაფის შესრულების რაოდენობა არის 0 ან 1.

### რომელი კოდი გაუშვა თითოეულმა ტესტმა {#per-test-evidence}

JUnit Platform-ზე (JUnit 5, ან JUnit 4 JUnit Vintage-ის მეშვეობით) გაშვებული ტესტებისთვის, პლაგინი ასევე აღრიცხავს, თუ რომელი კოდი გაუშვა თითოეულმა ტესტმა და რა გაუშვა თითოეულმა ტესტის კლასმა ტესტების გარეთ, მაგალითად `@BeforeAll`-ში. ეს არის ის, რაც საშუალებას აძლევს Tuist-ს გადაიტანოს იმ ტესტების დაფარვა, რომლებიც გაშვებამ გამოტოვა (იხილეთ [გამოტოვებული ტესტები](#skipped-tests)). თქვენს ტესტებს არაფერი უნდა დაემატოს.

ეს მუშაობს, როცა თითოეული ტესტის JVM ასრულებს ერთ ტესტს ერთდროულად, რაც არის Gradle-ის ტესტების გაშვების გზა, თუ არ ჩართავთ JUnit-ის პარალელურ შესრულებას. ტესტის კლასების გაშვება რამდენიმე JVM-ში `maxParallelForks`-ით არის დასაშვები. ტესტები, რომლებიც ერთდროულად გაშვებულია ერთ JVM-ში, ასევე ითვლება დაფარვაში, მაგრამ არა ცალ-ცალკე.

### აგების ქეში {#build-cache}

ტესტის ამოცანა, რომელიც Gradle აღადგინა აგების ქეშიდან, ან რომელიც განახლებულია, არ ასრულებს ტესტებს. მისი დაფარვა მაინც აიტვირთება: JaCoCo-ს მონაცემები არის ამოცანის ერთ-ერთი გამომავალი, რომელიც ჩაიწერა გაშვების მიერ, რომელმაც შეასრულა მისი ტესტები იმავე შეყვანებზე.

### გამოტოვებული ტესტები {#skipped-tests}

როცა გაშვება ტოვებს ტესტებს გარეთ, Tuist ავსებს იმას, რაც მათ დაფარეს ადრეული გაშვებიდან, იმ პირობით, რომ კოდი, რომელიც მათ გაუშვეს, უცვლელია. როცა ეს შეუძლებელია, კომიტის დაფარვა არის **არასრული**. რას ტოვებს გაშვება გარეთ:

- **პროექტის ტესტის ამოცანა გამორიცხულია** `-x :app:test`-ით. მისი ტესტები გადააქვს ბოლო გაშვებიდან, რომლის კოდიც უცვლელია.
- **ზოგიერთი პროექტის ტესტები** `./gradlew :core:test`-ით, ან **ზოგიერთი ტესტი** `--tests`-ით. გაშვება ფარავს მხოლოდ იმას, რაც მოითხოვეთ, ამიტომ კომიტი არასრულია, თუ კომიტის სხვა გაშვებამ არ გაუშვა ყველაფერი.
- **ტესტის ამოცანა, რომელიც შეჩერდა პირველ შეცდომაზე** (`failFast`).

ზოგიერთი ტესტი განზრახ არის გამოტოვებული და არ ხდის კომიტს არასრულს:

- **ფილტრები თქვენს აგების სკრიპტში**, მაგალითად `filter { excludeTestsMatching(...) }`, რომლებიც განსაზღვრავენ, რას ასრულებს თქვენი სუიტა.
- **ტესტის ამოცანები, რომლებსაც თქვენი აგების სკრიპტი თიშავს**, `enabled = false`-ით ან `onlyIf`-ით, რომელიც ტოვებს მათ.
- **ტესტები, რომლებსაც <.localized_link href="/guides/features/test-insights/flaky-tests/gradle">კარანტინი</.localized_link> ტოვებს.** ისინი გამოტოვებულია, თითქოს წაშლილი იყვნენ, ამიტომ ხაზები, რომლებიც მხოლოდ მათ დაფარეს, ითვლება დაუფარავად.
- **სხვა ნაწილების ტესტები**, როცა თქვენ [ყოფთ თქვენს ტესტებს](#sharded-runs).

## წარმადობაზე გავლენა {#performance-impact}

JaCoCo ინსტრუმენტაციას უკეთებს კლასებს მაშინ, როცა სატესტო JVM ტვირთავს მათ, ამიტომ თქვენი კომპილირებული კლასები და კომპილაციის ამოცანების ბილდ-ქეშის ჩანაწერები იგივე რჩება, მიუხედავად იმისა, ჩართულია თუ არა დაფარვა. ამოცანები, რომლებიც კითხულობენ ყველა დამოკიდებულების კონფიგურაციას, მაგალითად SBOM გენერატორები, ასევე ხედავენ JaCoCo-ს აგენტს, ამიტომ მათი გამოსავალი იცვლება, როცა ჩართავთ დაფარვას. ტესტები ოდნავ ნელა სრულდება და პლაგინი კითხულობს JaCoCo-ს მონაცემებს სატესტო ამოცანების დასრულების შემდეგ. სატესტო ამოცანებს ჩართული და გამორთული დაფარვით აქვთ ცალკე ბილდ-ქეშის ჩანაწერები, ამიტომ პირველი გაშვება ჩართული დაფარვით ასრულებს ტესტებს მაშინაც კი, თუ მათი შედეგები დაფარვის გარეშე ქეშირებულია.

## შეზღუდვები {#limitations}

- **იზოლირებული პროექტები და კონფიგურაცია მოთხოვნისას.** ასეთი აგებები არ აკონფიგურირებენ ყველა პროექტს, ამიტომ პლაგინს არ შეუძლია განსაზღვროს, რომელი პროექტების ტესტები გამოტოვა გაშვებამ და ზოგიერთი პროექტის ტესტების გაშვება სრულად ითვლება.
- **დაფარვა არ არის ფორკებიდან გაგზავნილი პულ-რეკვესტებიდან.** დაფარვა იტვირთება მხოლოდ იმ გაშვებების მიერ, რომლებიც ავტორიზაციას გადიან Tuist-თან, ხოლო CI ჩვეულებრივ ფარავს საიდუმლოებს და იდენტობის ტოკენებს ფორკებიდან გახსნილი პულ-რეკვესტებისთვის.

## დაფარვის მოთხოვნა {#querying}

დაშბორდის **კოდის დაფარვა** გვერდი აჩვენებს თითოეული კომიტის მაჩვენებელს, მის მოდულებს და ფაილებს, იმ ხაზებით, რომლებიც თითოეულმა გაშვებამ დაფარა. იგივე მონაცემები ხელმისაწვდომია აგენტებისთვის <.localized_link href="/guides/features/agentic-coding/mcp">Model Context Protocol სერვერის</.localized_link> მეშვეობით.
