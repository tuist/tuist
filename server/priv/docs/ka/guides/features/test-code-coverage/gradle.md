# Gradle-ის კოდის დაფარვა {#gradle-code-coverage}

კოდის დაფარვა გაჩვენებთ, თქვენი ტესტების მიერ შესრულებულ კოდის სტრიქონებს. Tuist-ის Gradle პლაგინი ზომავს თქვენი ტესტების ამოცანების დაფარვას JaCoCo-ს საშუალებით და ატვირთავს მას ყოველი ტესტების გაშვებისას, ხოლო Tuist აჯამებს კომიტის გაშვებებს ერთ მაჩვენებლად — პროექტისთვის, თითოეული Gradle პროექტისთვის და თითოეული ფაილისთვის. დაფის **კოდის დაფარვა** გვერდი აჩვენებს მას კომიტების მიხედვით და როგორც ტრენდს თითოეული შტოსთვის.

> [!IMPORTANT]
> **მოთხოვნები**
>
> - გამოყენებულია `dev.tuist` Gradle პლაგინი, როგორც აღწერილია <.localized_link href="/guides/get-started/gradle-project">დაიწყეთ Gradle პროექტით</.localized_link>
> - თქვენი პროექტი Git რეპოზიტორიაში: რეპოზიტორიის გარეთ გაშვება ატვირთავს ტესტების შედეგებს, მაგრამ არა დაფარვას

## მორგება {#setup}

### ჩართეთ დაფარვა {#turn-coverage-on}

ჩართეთ დაფარვა თქვენი `settings.gradle.kts`-ის `tuist` ბლოკში:

```kotlin
tuist {
    coverage {
        enabled = true
    }
}
```

ან ჩართეთ ის ერთი გამოძახებისთვის, მაგალითად CI სამუშაოსთვის, გარემოს ცვლადის მეშვეობით, რომელიც ნებისმიერ შემთხვევაში უპირატესობას ანიჭებს ამ პარამეტრს:

```sh
TUIST_TEST_COVERAGE=1 ./gradlew test
```

ტესტების ამოცანებს ჩართული და გამორთული დაფარვით აქვთ ცალკე ბილდის ქეშის ჩანაწერები (იხილეთ [წარმადობაზე გავლენა](#performance-impact)), ამიტომ უპირატესობა მიანიჭეთ პარამეტრს, როდესაც თქვენი CI და ადგილობრივი ბილდები იზიარებენ ბილდის ქეშს: დაფარვის მხოლოდ CI-ში ჩართვა ხელს უშლის მათ ერთმანეთის ტესტების შედეგების ხელახლა გამოყენებას.

ჩართული დაფარვის შემთხვევაში, პლაგინი ამატებს Gradle-ის `jacoco` პლაგინს ყოველ JVM პროექტს. JaCoCo-ს აგენტი მოდის თქვენი პროექტის რეპოზიტორიებიდან, ისევე როგორც ეს იქნებოდა, თქვენ რომ თავად დაამატოთ პლაგინი. პროექტი, რომელიც უკვე აკონფიგურირებს JaCoCo-ს, ინარჩუნებს თავის პარამეტრებს და მისი საკუთარი ანგარიშები განაგრძობენ მუშაობას.

პლაგინი ანგარიშგებას აწარმოებს მხოლოდ თქვენი რეპოზიტორიის კოდის დაფარვაზე, ამიტომ ის ზღუდავს JaCoCo-ს მისთვის: თუ ტესტების ამოცანა თავად არ აყენებს JaCoCo-ს `includes`-ს, აგენტი ინსტრუმენტაციას უკეთებს მხოლოდ იმ პაკეტებს, რომელთა კლასებსაც თქვენი რეპოზიტორია აკომპილირებს. პაკეტში, სადაც დამოკიდებულებასაც აქვს კლასები, მაგალითად `android.util.Log`-ის ტესტის ჩანაცვლება, ის ინსტრუმენტაციას უკეთებს მხოლოდ თქვენი რეპოზიტორიის იმ პაკეტის კლასებს. დამოკიდებულებები, Android ჩარჩო და თქვენი ტესტების ჩარჩოები მუშაობენ ინსტრუმენტაციის გარეშე, რაც JaCoCo-ს მონაცემებს და ტესტების ამოცანების ბილდის ქეშის ჩანაწერებს მცირეს ტოვებს.

როდესაც გაშვების დაფარვა ნაწილობრივია, პლაგინი იწერს გაფრთხილებას, რომელიც ხსნის მიზეზს, მაგალითად, პროექტებს, რომელთა ტესტებიც ბილდმა არ გაუშვა. პროექტები ერთეულოვანი ტესტების გარეშე, როგორიცაა JVM ბიბლიოთეკა, რომლის `test` ამოცანას არ აქვს ტესტის წყაროები, ან Android ბიბლიოთეკა მხოლოდ ინსტრუმენტირებული ტესტებით, არასდროს ითვლება გამოტოვებულად.

### Android პროექტები {#android-projects}

პლაგინი ზომავს Android პროექტების ადგილობრივ ერთეულოვან ტესტებს, როგორიცაა `testDebugUnitTest`. მოწყობილობაზე ან ემულატორზე გაშვებული ინსტრუმენტირებული ტესტები არ იზომება.

თუ თქვენი ერთეულოვანი ტესტები იყენებენ Robolectric-ს, უთხარით JaCoCo-ს, რომ ჩართოს კლასები, რომლებსაც Robolectric ტვირთავს. Robolectric განსაზღვრავს თქვენი აპლიკაციის კლასებს თავის კლასის ჩამტვირთავში, და JaCoCo ნაგულისხმევად ტოვებს ასეთ კლასებს, ამიტომ კოდი, რომელსაც ეს ტესტები ასრულებენ, გამოჩნდება როგორც არადაფარული. Android პროექტის `build.gradle.kts`-ში:

```kotlin
pluginManager.withPlugin("jacoco") {
    tasks.withType<Test>().configureEach {
        extensions.configure<JacocoTaskExtension> {
            isIncludeNoLocationClasses = true
            excludes = listOf("jdk.internal.*")
        }
    }
}
```

ბლოკი მოქმედებს მხოლოდ მაშინ, როდესაც დაფარვა ჩართულია, რადგან სწორედ მაშინ ამატებს პლაგინი `jacoco`-ს.

Android-ის ერთეულოვანი ტესტები ნაგულისხმევად მუშაობენ JUnit 4-ზე, რომელიც იწერს დაფარვას, მაგრამ არა [რომელი კოდი შეასრულა თითოეულმა ტესტმა](#per-test-evidence). მის ჩასაწერად, გაუშვით ისინი JUnit Platform-ზე JUnit Vintage-ის მეშვეობით.

### დაშლილი გაშვებები {#sharded-runs}

როდესაც თქვენ <.localized_link href="/guides/features/test-sharding/gradle">ყოფთ თქვენს ტესტებს</.localized_link>, ყოველი ნაწილი, რომელიც მუშაობს ჩართული დაფარვით, ანგარიშგებას აწარმოებს მის მიერ გაშვებული ტესტების დაფარვაზე, და Tuist აერთიანებს ერთი გაშვების ნაწილებს ერთ მაჩვენებლად. ნაწილი განზრახ ასრულებს სუიტის ნაწილს, ამიტომ ის არ ხდის კომიტის დაფარვას არასრულს.

### დაასრულეთ ყოველი კომიტი CI-ზე {#complete-each-commit}

კომიტის დაფარვა ხშირად მოდის რამდენიმე სამუშაოდან, მაგალითად, ერთი თითოეული ნაწილისთვის. Tuist-ს არ შეუძლია გაიგოს, როდის ანგარიშგებას აწარმოებს ბოლო მათგანი, ამიტომ უთხარით მას. როდესაც კომიტის ყოველი ტესტის სამუშაო დასრულდება, გაუშვით ეს სამუშაოში, რომელიც დამოკიდებულია ყველა მათგანზე:

```sh
./gradlew tuistCoverageComplete
```

როდესაც ერთი სამუშაო ასრულებს კომიტის ყველა ტესტს, გაუშვით ამოცანა როგორც ნაბიჯი ტესტების შემდეგ, მათ შორის მაშინაც, როდესაც ტესტები ვერხერხდება: ვერხერხებული ტესტების მქონე გაშვებაც ანგარიშგებას აწარმოებს თავის დაფარვაზე.

ამოცანა კითხულობს კომიტს checkout-ის `HEAD`-დან, კომიტიდან, რომელზეც თქვენი ტესტები მუშაობდნენ; გადაეცით `-Ptuist.coverage.commit=<sha>` სხვის დასახელებლად. სანამ კომიტი არ დასრულდება, მისი დაფარვა ჩანს როგორც **მიმდინარე** და არ შედის მისი შტოს ტრენდში.

## როგორ მუშაობს {#how-it-works}

### რას ზომავს Tuist {#what-tuist-measures}

- **პროექტები.** თითოეული Gradle პროექტი არის მოდული დაფაზე, თავისი საკუთარი დაფარვით.
- **მხოლოდ პროდუქტის კოდი.** კლასები, რომლებიც აკომპილირებულია ტესტის წყაროების ნაკრებიდან, არის ტესტის კოდი. Tuist ინახავს მათ, მაგრამ ტოვებს მათ ყოველი მაჩვენებლის გარეთ.
- **თქვენი რეპოზიტორიის ფაილები.** კლასი ითვლება იმ საწყისი ფაილისთვის, საიდანაც ის აკომპილირდა, თქვენს რეპოზიტორიაში მისი გზის მიხედვით. გენერირებული წყაროები და ფაილები, რომლებსაც Git იგნორირებს, არ ანგარიშგება.
- **შესრულდა თუ არა თითოეული სტრიქონი.** JaCoCo იწერს, შესრულდა თუ არა კოდი, არა თუ რამდენჯერ, ამიტომ დაფის შესრულების რაოდენობა არის 0 ან 1.

### რომელი კოდი შეასრულა თითოეულმა ტესტმა {#per-test-evidence}

JUnit Platform-ზე მომუშავე ტესტებისთვის (JUnit 5, ან JUnit 4 JUnit Vintage-ის მეშვეობით), პლაგინი ასევე იწერს, რომელი კოდი შეასრულა თითოეულმა ტესტმა და რა შეასრულა თითოეულმა ტესტის კლასმა ტესტების გარეთ, მაგალითად `@BeforeAll`-ში. ეს არის ის, რაც საშუალებას აძლევს Tuist-ს გადაიტანოს იმ ტესტების დაფარვა, რომლებიც გაშვებამ გამოტოვა (იხილეთ [გამოტოვებული ტესტები](#skipped-tests)). თქვენს ტესტებში არაფრის დამატება არ არის საჭირო.

ეს მუშაობს, როდესაც თითოეული ტესტის JVM ასრულებს ერთ ტესტს ერთდროულად, რაც არის Gradle-ის ტესტების გაშვების გზა, თუ არ ჩართავთ JUnit-ის პარალელურ შესრულებას. ტესტის კლასების გაშვება რამდენიმე JVM-ში `maxParallelForks`-ით არის დასაშვები. ტესტები, რომლებიც ერთდროულად მუშაობენ ერთ JVM-ში, ასევე ითვლებიან დაფარვაში, მაგრამ არა ერთი-ერთზე.

### ბილდის ქეში {#build-cache}

ტესტის ამოცანა, რომელსაც Gradle აღადგენს ბილდის ქეშიდან, ან რომელიც აქტუალურია, არ ასრულებს ტესტებს. მისი დაფარვა მაინც აიტვირთება: JaCoCo-ს მონაცემები არის ამოცანის ერთ-ერთი გამომავალი, ჩაწერილი იმ გაშვების მიერ, რომელმაც შეასრულა მისი ტესტები იმავე შეყვანებზე.

### გამოტოვებული ტესტები {#skipped-tests}

როდესაც გაშვება ტოვებს ტესტებს გარეთ, Tuist ავსებს იმას, რაც მათ დაფარეს წინა გაშვებიდან, იმ პირობით, რომ კოდი, რომელიც მათ შეასრულეს, უცვლელია. როდესაც ეს შეუძლებელია, კომიტის დაფარვა არის **არასრული**. რას ტოვებს გაშვება გარეთ:

- **პროექტის ტესტის ამოცანა გამოირიცხა** `-x :app:test`-ით. მისი ტესტები გადაიტანება მათი ბოლო გაშვებიდან, რომლის კოდიც უცვლელია.
- **ზოგიერთი პროექტის ტესტები** `./gradlew :core:test`-ით, ან **ზოგიერთი ტესტი** `--tests`-ით. გაშვება ფარავს მხოლოდ იმას, რაც მოითხოვეთ, ამიტომ კომიტი არასრულია, თუ კომიტის სხვა გაშვებამ არ შეასრულა ყველაფერი.
- **ტესტის ამოცანა, რომელიც შეჩერდა პირველ შეცდომაზე** (`failFast`).

ზოგიერთი ტესტი განზრახ არის გამოტოვებული და კომიტს არასრულად არ აქცევს:

- **ფილტრები თქვენს ბილდის სკრიპტში**, მაგალითად `filter { excludeTestsMatching(...) }`, რომლებიც განსაზღვრავენ, რას ასრულებს თქვენი ტესტების ნაკრები.
- **ტესტის ამოცანები, რომლებიც თქვენმა ბილდის სკრიპტმა გამორთო**, `enabled = false`-ით ან `onlyIf`-ით, რომელიც მათ გამოტოვებს.
- **ტესტები, რომლებსაც <.localized_link href="/guides/features/test-insights/flaky-tests/gradle">კარანტინი</.localized_link> ტოვებს გარეთ.** ისინი გამოტოვებულია ისე, თითქოს წაშლილი იყვნენ, ამიტომ ხაზები, რომლებსაც მხოლოდ ისინი ფარავდნენ, დაუფარავად ითვლება.
- **სხვა შარდების ტესტები**, როდესაც თქვენ [ყოფთ ტესტებს შარდებად](#sharded-runs).

## წარმადობაზე გავლენა {#performance-impact}

JaCoCo აკვირდება კლასებს, როდესაც სატესტო JVM ტვირთავს მათ, ამიტომ თქვენი კომპილირებული კლასები და კომპილაციის ამოცანების ბილდის ქეშის ჩანაწერები უცვლელი რჩება, დაფარვა ჩართული იქნება თუ გამორთული. ამოცანები, რომლებიც კითხულობენ ყველა დამოკიდებულების კონფიგურაციას, მაგალითად SBOM-ის გენერატორები, ასევე ხედავენ JaCoCo-ს აგენტს, ამიტომ მათი გამომავალი მონაცემები იცვლება, როდესაც დაფარვას ჩართავთ. ტესტები ოდნავ უფრო ნელა მუშაობს და პლაგინი კითხულობს JaCoCo-ს მონაცემებს ტესტის ამოცანების დასრულების შემდეგ. ტესტის ამოცანებს ჩართული და გამორთული დაფარვით აქვთ ცალკეული ბილდის ქეშის ჩანაწერები, ამიტომ პირველი გაშვება ჩართული დაფარვით ასრულებს ტესტებს მაშინაც კი, თუ მათი შედეგები დაფარვის გარეშე ქეშირებულია.

## შეზღუდვები {#limitations}

- **იზოლირებული პროექტები და კონფიგურაცია მოთხოვნისას.** ეს ბილდები არ აკონფიგურირებენ ყველა პროექტს, ამიტომ პლაგინს არ შეუძლია დაადგინოს, რომელი პროექტების ტესტები გამოტოვა გაშვებამ, და ზოგიერთი პროექტის ტესტების გაშვება სრულად ითვლება.
- **არ არის დაფარვა ფორკებიდან გახსნილი პულ-რეკვესტებიდან.** დაფარვა აიტვირთება მხოლოდ იმ გაშვებების მიერ, რომლებიც ავთენტიკაციას გადიან Tuist-თან, და CI ჩვეულებრივ ფარავს საიდუმლოებს და იდენტობის ტოკენებს ფორკებიდან გახსნილი პულ-რეკვესტებისგან.

## დაფარვის მოთხოვნა {#querying}

დაშბორდის **კოდის დაფარვა** გვერდი აჩვენებს თითოეული კომიტის მაჩვენებელს, მის მოდულებს და ფაილებს, იმ ხაზებით, რომლებიც თითოეულმა გაშვებამ დაფარა. იგივე მონაცემები ხელმისაწვდომია აგენტებისთვის <.localized_link href="/guides/features/agentic-coding/mcp">Model Context Protocol სერვერის</.localized_link> მეშვეობით.
