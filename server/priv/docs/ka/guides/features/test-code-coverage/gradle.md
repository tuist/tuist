# Gradle-ის კოდის დაფარვა {#gradle-code-coverage}

კოდის დაფარვა გიჩვენებს, თუ რომელი ხაზები შესრულდა თქვენი ტესტების მიერ. Tuist-ის Gradle პლაგინი ზომავს თქვენი ტესტების ამოცანების დაფარვას JaCoCo-ს საშუალებით და ატვირთავს მას ყოველი ტესტების გაშვებისას, ხოლო Tuist აერთიანებს კომიტის გაშვებებს ერთ მაჩვენებლად — პროექტისთვის, თითოეული Gradle პროექტისთვის და თითოეული ფაილისთვის. დაფის **კოდის დაფარვის** გვერდი აჩვენებს მას კომიტების მიხედვით და როგორც ტენდენციას თითოეული შტოსთვის.

> [!IMPORTANT]
> **მოთხოვნები**
>
> - გამოყენებულია `dev.tuist` Gradle პლაგინი, როგორც აღწერილია <.localized_link href="/guides/get-started/gradle-project">დაიწყეთ Gradle პროექტით</.localized_link>
> - თქვენი პროექტი Git რეპოზიტორიაში: მის გარეთ გაშვება ატვირთავს ტესტების შედეგებს, მაგრამ არა დაფარვას

## მოწყობა {#setup}

### ჩართეთ დაფარვა {#turn-coverage-on}

ჩართეთ დაფარვა თქვენი `settings.gradle.kts`-ის `tuist` ბლოკში:

```kotlin
tuist {
    coverage {
        enabled = true
    }
}
```

ან ჩართეთ ის ერთი გამოძახებისთვის, მაგალითად CI სამუშაოსთვის, გარემოს ცვლადის საშუალებით, რომელსაც აქვს უპირატესობა ნებისმიერი პარამეტრის მიმართ:

```sh
TUIST_TEST_COVERAGE=1 ./gradlew test
```

ტესტების ამოცანებს ჩართული და გამორთული დაფარვით აქვთ ცალკეული ბილდის ქეშის ჩანაწერები (იხილეთ [წარმადობაზე გავლენა](#performance-impact)), ამიტომ უპირატესობა მიანიჭეთ პარამეტრს, როდესაც თქვენი CI და ლოკალური ბილდები იზიარებენ ბილდის ქეშს: დაფარვის მხოლოდ CI-ში ჩართვა ხელს უშლის მათ ერთმანეთის ტესტების შედეგების ხელახლა გამოყენებას.

ჩართული დაფარვის შემთხვევაში, პლაგინი ამატებს Gradle-ის `jacoco` პლაგინს ყოველ JVM პროექტს. JaCoCo-ს აგენტი მოდის თქვენი პროექტის რეპოზიტორიებიდან, ისევე როგორც ეს იქნებოდა, თუ თქვენ თავად დაამატებდით პლაგინს. პროექტი, რომელიც უკვე აკონფიგურირებს JaCoCo-ს, ინარჩუნებს თავის პარამეტრებს და მისი საკუთარი ანგარიშები განაგრძობენ მუშაობას.

### Android პროექტები {#android-projects}

პლაგინი ზომავს Android პროექტების ლოკალურ ერთეულოვან ტესტებს, როგორიცაა `testDebugUnitTest`. ინსტრუმენტული ტესტები, რომლებიც ეწყობა მოწყობილობაზე ან ემულატორზე, არ იზომება.

თუ თქვენი ერთეულოვანი ტესტები იყენებენ Robolectric-ს, უთხარით JaCoCo-ს, რომ ჩართოს კლასები, რომლებსაც Robolectric ტვირთავს. Robolectric განსაზღვრავს თქვენი აპლიკაციის კლასებს თავის კლასების ჩამტვირთავში, და JaCoCo ნაგულისხმევად ტოვებს ასეთ კლასებს, ამიტომ კოდი, რომელსაც ეს ტესტები ასრულებენ, გამოჩნდება როგორც დაუფარავი. Android პროექტის `build.gradle.kts`-ში:

```kotlin
pluginManager.withPlugin("jacoco") {
    tasks.withType<Test>().configureEach {
        extensions.configure<JacocoTaskExtension> {
            isIncludeNoLocationClasses = true
            excludes = listOf("jdk.internal.*")
        }
    }
}
```

ბლოკი მოქმედებს მხოლოდ მაშინ, როდესაც დაფარვა ჩართულია, რადგან სწორედ მაშინ ამატებს პლაგინი `jacoco`-ს.

Android-ის ერთეულოვანი ტესტები ნაგულისხმევად ეწყობა JUnit 4-ზე, რომელიც იწერს დაფარვას, მაგრამ არა [რომელი კოდი შეასრულა თითოეულმა ტესტმა](#per-test-evidence). მის ჩასაწერად, გაუშვით ისინი JUnit Platform-ზე JUnit Vintage-ის საშუალებით.

### დაყოფილი გაშვებები {#sharded-runs}

როდესაც თქვენ <.localized_link href="/guides/features/test-sharding/gradle">ყოფთ თქვენს ტესტებს</.localized_link>, ყოველი შარდი, რომელიც ეწყობა ჩართული დაფარვით, ანგარიშგებს იმ ტესტების დაფარვას, რომლებიც მან შეასრულა, და Tuist აერთიანებს გაშვების შარდებს ერთ მაჩვენებლად. შარდი განზრახ ასრულებს სუიტის ნაწილს, ამიტომ ის არ ხდის კომიტის დაფარვას არასრულყოფილს.

### დაასრულეთ ყოველი კომიტი CI-ზე {#complete-each-commit}

კომიტის დაფარვა ხშირად მოდის რამდენიმე სამუშაოდან, მაგალითად, ერთი შარდისთვის. Tuist-ს არ შეუძლია გაიგოს, როდის ანგარიშგებოდა ბოლო მათგანი, ამიტომ უთხარით მას. როდესაც კომიტის ყოველი ტესტის სამუშაო დასრულდება, გაუშვით ეს სამუშაოში, რომელიც დამოკიდებულია მათ ყველაზე:

```sh
./gradlew tuistCoverageComplete
```

როდესაც ერთი სამუშაო ასრულებს კომიტის ყველა ტესტს, გაუშვით ამოცანა როგორც ნაბიჯი ტესტების შემდეგ, მათ შორის მაშინაც, როდესაც ტესტები ვერ ხერხდება: გაშვება ვერშესრულებული ტესტებით მაინც ანგარიშგებდა თავის დაფარვას.

ამოცანა კითხულობს კომიტს `GIT_COMMIT`-დან ან checkout-ის `HEAD`-დან; გადაეცით `-Ptuist.coverage.commit=<sha>` სხვის დასახელებლად. სანამ კომიტი არ დასრულდება, მისი დაფარვა ჩანს როგორც **მიმდინარეობს** და არ შედის მისი შტოს ტენდენციაში.

## როგორ მუშაობს {#how-it-works}

### რას ზომავს Tuist {#what-tuist-measures}

- **პროექტები.** ყოველი Gradle პროექტი არის მოდული დაფზე, თავისი საკუთარი დაფარვით.
- **მხოლოდ პროდუქციის კოდი.** კლასები, რომლებიც კომპილირდება ტესტების წყაროების სიმრავლეებიდან, არის ტესტების კოდი. Tuist ინახავს მათ, მაგრამ ტოვებს მათ ყოველი მაჩვენებლის გარეთ.
- **თქვენი რეპოზიტორიის ფაილები.** კლასი ითვლება იმ საწყისი ფაილისთვის, საიდანაც ის კომპილირდა, მისი გზის მიხედვით თქვენს რეპოზიტორიაში. გენერირებული წყაროები და ფაილები, რომლებსაც Git იგნორირებს, არ ანგარიშგდება.
- **შესრულდა თუ არა თითოეული ხაზი.** JaCoCo იწერს, შესრულდა თუ არა კოდი, არა თუ რამდენჯერ, ამიტომ დაფის შესრულების რაოდენობა არის 0 ან 1.

### რომელი კოდი შეასრულა თითოეულმა ტესტმა {#per-test-evidence}

JUnit Platform-ზე მომუშავე ტესტებისთვის (JUnit 5, ან JUnit 4 JUnit Vintage-ის საშუალებით), პლაგინი ასევე იწერს, თუ რომელი კოდი შეასრულა თითოეულმა ტესტმა და რა შეასრულა თითოეულმა ტესტის კლასმა თავისი ტესტების გარეთ, მაგალითად `@BeforeAll`-ში. ეს არის ის, რაც საშუალებას აძლევს Tuist-ს გადაიტანოს იმ ტესტების დაფარვა, რომლებიც გაშვებამ გამოტოვა (იხილეთ [გამოტოვებული ტესტები](#skipped-tests)). თქვენს ტესტებში არაფრის დამატება არ არის საჭირო.

ეს მუშაობს, როდესაც თითოეული ტესტის JVM ასრულებს ერთ ტესტს ერთდროულად, რაც არის ის, თუ როგორ ასრულებს Gradle ტესტებს, თუ არ ჩართავთ JUnit-ის პარალელურ შესრულებას. ტესტის კლასების რამდენიმე JVM-ში გაშვება `maxParallelForks`-ით არის დასაშვები. ტესტები, რომლებიც ერთდროულად ეწყობა ერთ JVM-ში, მაინც ითვლება დაფარვაში, მაგრამ არა ერთ-ერთად.

### ბილდის ქეში {#build-cache}

ტესტის ამოცანა, რომელსაც Gradle აღადგენს ბილდის ქეშიდან, ან რომელიც განახლებულია, არ ასრულებს ტესტებს. მისი დაფარვა მაინც აიტვირთება: JaCoCo-ს მონაცემები არის ამოცანის ერთ-ერთი შედეგი, რომელიც ჩაიწერა გაშვების მიერ, რომელმაც შეასრულა მისი ტესტები იმავე შეყვანებზე.

### გამოტოვებული ტესტები {#skipped-tests}

როდესაც გაშვება ტოვებს ტესტებს გარეთ, Tuist ავსებს იმას, რაც მათ დაფარეს ადრეული გაშვებიდან, იმ პირობით, რომ კოდი, რომელიც მათ შეასრულეს, უცვლელია. როდესაც ეს შეუძლებელია, კომიტის დაფარვა არის **არასრული**. რას ტოვებს გაშვება გარეთ:

- **პროექტის ტესტის ამოცანა გამოირიცხა** `-x :app:test`-ით. მისი ტესტები გადაიტანება მათი ბოლო გაშვებიდან, რომლის კოდი უცვლელია.
- **ზოგიერთი პროექტის ტესტები** `./gradlew :core:test`-ით, ან **ზოგიერთი ტესტი** `--tests`-ით. გაშვება ფარავს მხოლოდ იმას, რაც მოითხოვეთ, ამიტომ კომიტი არის არასრული, თუ კომიტის სხვა გაშვებამ არ შეასრულა ყველაფერი.
- **ტესტის ამოცანა, რომელიც შეჩერდა პირველი შეცდომისას** (`failFast`).

ზოგიერთი ტესტი განზრახ არის გამოტოვებული და არ ხდის კომიტს არასრულს:

- **ფილტრები თქვენს ბილდის სკრიპტში**, როგორიცაა `filter { excludeTestsMatching(...) }`, რომლებიც განსაზღვრავენ, რას ასრულებს თქვენი სუიტა.
- **ტესტის ამოცანები, რომლებსაც თქვენი ბილდის სკრიპტი თიშავს**, `enabled = false`-ით ან `onlyIf`-ით, რომელიც მათ გამოტოვებს.
- **ტესტები, რომლებსაც <.localized_link href="/guides/features/test-insights/flaky-tests/gradle">კარანტინი</.localized_link> ტოვებს გარეთ.** ისინი გამოტოვებულია ისე, თითქოს წაშლილი იყოს, ამიტომ ხაზები, რომლებიც მხოლოდ მათ დაფარეს, ჩაითვლება დაუფარავად.
- **სხვა შარდების ტესტები**, როდესაც თქვენ [ყოფთ თქვენს ტესტებს შარდებად](#sharded-runs).

## წარმადობაზე გავლენა {#performance-impact}

JaCoCo ინსტრუმენტებს კლასებს მაშინ, როდესაც სატესტო JVM ტვირთავს მათ, ამიტომ თქვენი კომპილირებული კლასები და კომპილაციის ამოცანების ბილდის ქეშის ჩანაწერები უცვლელი რჩება დაფარვის ჩართვის ან გამორთვის შემთხვევაში. ამოცანები, რომლებიც კითხულობენ ყოველ დამოკიდებულების კონფიგურაციას, როგორიცაა SBOM გენერატორები, ასევე ხედავენ JaCoCo-ს აგენტს, ამიტომ მათი შედეგები იცვლება, როდესაც თქვენ ჩართავთ დაფარვას. ტესტები ოდნავ ნელა სრულდება და პლაგინი კითხულობს JaCoCo-ს მონაცემებს მას შემდეგ, რაც ტესტის ამოცანები დასრულდება. ტესტის ამოცანებს ჩართული და გამორთული დაფარვით აქვთ ცალკეული ბილდის ქეშის ჩანაწერები, ამიტომ პირველი გაშვება ჩართული დაფარვით ასრულებს ტესტებს მაშინაც კი, როდესაც მათი შედეგები დაფარვის გარეშე არის ქეშში.

## შეზღუდვები {#limitations}

- **იზოლირებული პროექტები და კონფიგურაცია მოთხოვნისას.** ეს ბილდები არ აკონფიგურირებენ ყოველ პროექტს, ამიტომ პლაგინს არ შეუძლია განსაზღვროს, რომელი პროექტების ტესტები გამოტოვა გაშვებამ, და ზოგიერთი პროექტის ტესტების გაშვება ითვლება სრულად.
- **არ არის დაფარვა ფორკებიდან გახსნილი პულ-რეკვესტებიდან.** დაფარვა აიტვირთება მხოლოდ იმ გაშვებების მიერ, რომლებიც ავთენტიკაციას გადიან Tuist-თან, და CI ჩვეულებრივ ფარავს საიდუმლოებს და იდენტობის ტოკენებს ფორკებიდან გახსნილი პულ-რეკვესტებისთვის.

## დაფარვის მოთხოვნა {#querying}

დაშბორდის **კოდის დაფარვა** გვერდი აჩვენებს თითოეული კომიტის მაჩვენებელს, მის მოდულებს და ფაილებს, იმ ხაზებით, რომლებიც თითოეულმა გაშვებამ დაფარა. იგივე მონაცემები ხელმისაწვდომია აგენტებისთვის <.localized_link href="/guides/features/agentic-coding/mcp">Model Context Protocol სერვერის</.localized_link> მეშვეობით.
