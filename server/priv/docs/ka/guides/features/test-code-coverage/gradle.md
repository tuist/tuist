# Gradle-ის კოდის დაფარვა {#gradle-code-coverage}

კოდის დაფარვა გაჩვენებთ, თქვენი ტესტები კოდის რომელი ხაზები შეასრულეს. Tuist-ის Gradle პლაგინი ზომავს თქვენი ტესტების ამოცანების დაფარვას JaCoCo-ს საშუალებით და ატვირთავს მას ყოველი ტესტების გაშვებისას, ხოლო Tuist აერთიანებს კომიტის გაშვებებს ერთ მაჩვენებლად პროექტისთვის, თითოეული Gradle პროექტისთვის და თითოეული ფაილისთვის. დაშბორდის **კოდის დაფარვის** გვერდი აჩვენებს მას კომიტების მიხედვით და როგორც ტრენდს თითოეული ბრენჩისთვის.

> [!IMPORTANT]
> **მოთხოვნები**
>
> - გამოყენებულია `dev.tuist` Gradle პლაგინი, როგორც აღწერილია <.localized_link href="/guides/get-started/gradle-project">დაიწყეთ Gradle პროექტით</.localized_link>
> - თქვენი პროექტი Git რეპოზიტორიაში: გაშვება მის გარეთ ატვირთავს ტესტების შედეგებს, მაგრამ არა დაფარვას

## მორგება {#setup}

### ჩართეთ დაფარვა {#turn-coverage-on}

ჩართეთ დაფარვა თქვენი `settings.gradle.kts`-ის `tuist` ბლოკში:

```kotlin
tuist {
    coverage {
        enabled = true
    }
}
```

ან ჩართეთ ის ერთი გამოძახებისთვის, მაგალითად CI სამუშაოსთვის, გარემოს ცვლადის საშუალებით, რომელსაც ნებისმიერ შემთხვევაში უპირატესობა აქვს პარამეტრთან მიმართებაში:

```sh
TUIST_TEST_COVERAGE=1 ./gradlew test
```

ტესტების ამოცანებს ჩართული და გამორთული დაფარვით აქვთ ცალკე ბილდის ქეშის ჩანაწერები (იხილეთ [წარმადობაზე გავლენა](#performance-impact)), ამიტომ უპირატესობა მიანიჭეთ პარამეტრს, როდესაც თქვენი CI და ადგილობრივი ბილდები იზიარებენ ბილდის ქეშს: დაფარვის მხოლოდ CI-ში ჩართვა ხელს უშლის მათ ერთმანეთის ტესტების შედეგების ხელახლა გამოყენებას.

ჩართული დაფარვისას, პლაგინი იყენებს Gradle-ის `jacoco` პლაგინს ყოველი JVM პროექტისთვის. JaCoCo-ს აგენტი მოდის თქვენი პროექტის რეპოზიტორიებიდან, ისევე როგორც ეს იქნებოდა, თქვენ რომ თავად გამოგეყენებინათ პლაგინი. პროექტი, რომელიც უკვე აკონფიგურირებს JaCoCo-ს, ინარჩუნებს თავის პარამეტრებს და მისი საკუთარი ანგარიშები განაგრძობენ მუშაობას.

### Android პროექტები {#android-projects}

პლაგინი ზომავს Android პროექტების ადგილობრივ ერთეულურ ტესტებს, როგორიცაა `testDebugUnitTest`. ინსტრუმენტული ტესტები, რომლებიც ეშვებიან მოწყობილობაზე ან ემულატორზე, არ იზომება.

თუ თქვენი ერთეულური ტესტები იყენებენ Robolectric-ს, უთხარით JaCoCo-ს, რომ მოიცვას კლასები, რომლებსაც Robolectric ტვირთავს. Robolectric განსაზღვრავს თქვენი აპლიკაციის კლასებს საკუთარ კლასის ჩამტვირთავში, და JaCoCo ნაგულისხმევად ტოვებს ასეთ კლასებს, ამიტომ კოდი, რომელსაც ეს ტესტები ასრულებენ, გამოჩნდება როგორც დაუფარავი. Android პროექტის `build.gradle.kts`-ში:

```kotlin
pluginManager.withPlugin("jacoco") {
    tasks.withType<Test>().configureEach {
        extensions.configure<JacocoTaskExtension> {
            isIncludeNoLocationClasses = true
            excludes = listOf("jdk.internal.*")
        }
    }
}
```

ბლოკი მოქმედებს მხოლოდ მაშინ, როდესაც დაფარვა ჩართულია, რადგან სწორედ მაშინ იყენებს პლაგინი `jacoco`-ს.

Android-ის ერთეულური ტესტები ნაგულისხმევად ეშვებიან JUnit 4-ზე, რომელიც აღრიცხავს დაფარვას, მაგრამ არა [რომელი კოდი შეასრულა თითოეულმა ტესტმა](#per-test-evidence). მის აღსარიცხად, გაუშვით ისინი JUnit Platform-ზე JUnit Vintage-ის საშუალებით.

### დაშლილი გაშვებები {#sharded-runs}

როდესაც თქვენ <.localized_link href="/guides/features/test-sharding/gradle">ყოფთ თქვენს ტესტებს</.localized_link>, ყოველი შარდი, რომელიც ეშვება ჩართული დაფარვით, ანგარიშგებს იმ ტესტების დაფარვას, რომლებიც მან შეასრულა, და Tuist აერთიანებს გაშვების შარდებს ერთ მაჩვენებლად. შარდი მიზანმიმართულად ასრულებს სუიტის ნაწილს, ამიტომ ის არ ხდის კომიტის დაფარვას არასრულს.

### დაასრულეთ ყოველი კომიტი CI-ზე {#complete-each-commit}

კომიტის დაფარვა ხშირად მოდის რამდენიმე სამუშაოდან, მაგალითად ერთი შარდისთვის. Tuist-ს არ შეუძლია განსაზღვროს, როდის მოახსენა ბოლომ მათგან, ამიტომ უთხარით მას. მას შემდეგ, რაც კომიტის ყოველი ტესტის სამუშაო დასრულდება, გაუშვით ეს იმ სამუშაოში, რომელიც დამოკიდებულია მათ ყველაზე:

```sh
./gradlew tuistCoverageComplete
```

როდესაც ერთი სამუშაო ასრულებს კომიტის ყველა ტესტს, გაუშვით ამოცანა როგორც ნაბიჯი ტესტების შემდეგ, მათ შორის მაშინაც, როდესაც ტესტები ვერ ხერხდება: ვერშესრულებული ტესტების მქონე გაშვებაც კი ანგარიშგებს თავის დაფარვას.

ამოცანა კითხულობს კომიტს `GIT_COMMIT`-დან ან ჩექაუთის `HEAD`-დან; გადაეცით `-Ptuist.coverage.commit=<sha>` სხვის დასახელებლად. სანამ კომიტი არ დასრულდება, მისი დაფარვა ჩანს როგორც **მიმდინარეობს** და რჩება მისი ბრენჩის ტრენდის გარეთ.

## როგორ მუშაობს {#how-it-works}

### რას ზომავს Tuist {#what-tuist-measures}

- **პროექტები.** ყოველი Gradle პროექტი არის მოდული დაშბორდზე, საკუთარი დაფარვით.
- **მხოლოდ პროდუქტის კოდი.** კლასები, რომლებიც კომპილირებულია ტესტების წყაროს ნაკრებებიდან, არის ტესტის კოდი. Tuist ინახავს მათ, მაგრამ ტოვებს მათ ყოველი მაჩვენებლის გარეთ.
- **თქვენი რეპოზიტორიის ფაილები.** კლასი ითვლება იმ საწყისი ფაილისთვის, საიდანაც ის კომპილირდა, მისი გზის მიხედვით თქვენს რეპოზიტორიაში. გენერირებული წყაროები და ფაილები, რომლებსაც Git იგნორირებს, არ არის მოხსენებული.
- **შეასრულა თუ არა თითოეულმა ხაზმა.** JaCoCo აღრიცხავს, შესრულდა თუ არა კოდი, არა თუ რამდენჯერ, ამიტომ დაშბორდის შესრულების რაოდენობა არის 0 ან 1.

### რომელი კოდი შეასრულა თითოეულმა ტესტმა {#per-test-evidence}

JUnit Platform-ზე მომუშავე ტესტებისთვის (JUnit 5, ან JUnit 4 JUnit Vintage-ის საშუალებით), პლაგინი ასევე აღრიცხავს, რომელი კოდი შეასრულა თითოეულმა ტესტმა და რა შეასრულა თითოეულმა ტესტის კლასმა თავისი ტესტების გარეთ, მაგალითად `@BeforeAll`-ში. ეს არის ის, რაც საშუალებას აძლევს Tuist-ს გადაიტანოს იმ ტესტების დაფარვა, რომლებიც გაშვებამ გამოტოვა (იხილეთ [გამოტოვებული ტესტები](#skipped-tests)). თქვენს ტესტებში არაფრის დამატება არ არის საჭირო.

ეს მუშაობს, როდესაც თითოეული ტესტის JVM ასრულებს ერთ ტესტს ერთდროულად, რაც არის ის, თუ როგორ ასრულებს Gradle ტესტებს, თუ არ ჩართავთ JUnit-ის პარალელურ შესრულებას. ტესტის კლასების გაშვება რამდენიმე JVM-ში `maxParallelForks`-ის საშუალებით დასაშვებია. ტესტები, რომლებიც ერთდროულად ეშვებიან ერთ JVM-ში, ასევე ითვლება დაფარვაში, მაგრამ არა ცალ-ცალკე.

### ბილდის ქეში {#build-cache}

ტესტის ამოცანა, რომელსაც Gradle აღადგენს ბილდის ქეშიდან, ან რომელიც აქტუალურია, არ ასრულებს ტესტებს. მისი დაფარვა მაინც აიტვირთება: JaCoCo-ს მონაცემები არის ამოცანის ერთ-ერთი შედეგი, რომელიც ჩაიწერა გაშვების მიერ, რომელმაც შეასრულა მისი ტესტები იმავე შეყვანებზე.

### გამოტოვებული ტესტები {#skipped-tests}

როდესაც გაშვება ტოვებს ტესტებს გარეთ, Tuist ავსებს იმას, რაც მათ დაფარეს ადრეული გაშვებიდან, იმ პირობით, რომ კოდი, რომელიც მათ შეასრულეს, უცვლელია. როდესაც ეს შეუძლებელია, კომიტის დაფარვა არის **არასრული**. რას ტოვებს გაშვება გარეთ:

- **პროექტის ტესტის ამოცანა გამორიცხულია** `-x :app:test`-ით. მისი ტესტები გადააქვს ბოლო გაშვებიდან, რომლის კოდიც უცვლელია.
- **ზოგიერთი პროექტის ტესტები** `./gradlew :core:test`-ით, ან **ზოგიერთი ტესტი** `--tests`-ით. გაშვება ფარავს მხოლოდ იმას, რაც მოითხოვეთ, ამიტომ კომიტი არასრულია, თუ კომიტის სხვა გაშვებამ არ შეასრულა ყველაფერი.
- **ტესტის ამოცანა, რომელიც შეჩერდა პირველი ვერშესრულებისას** (`failFast`).

ზოგიერთი ტესტი მიზანმიმართულად არის გამოტოვებული და არ ხდის კომიტს არასრულს:

- **ფილტრები თქვენს ბილდის სკრიპტში**, როგორიცაა `filter { excludeTestsMatching(...) }`, რომლებიც განსაზღვრავენ, რას ასრულებს თქვენი სუიტა.
- **ტესტის ამოცანები, რომლებსაც თქვენი ბილდის სკრიპტი თიშავს**, `enabled = false`-ით ან `onlyIf`-ით, რომელიც მათ ტოვებს.
- **ტესტები, რომლებსაც <.localized_link href="/guides/features/test-insights/flaky-tests/gradle">კარანტინი</.localized_link> ტოვებს.** ისინი გამოტოვებულია ისე, თითქოს წაშლილი იყოს, ამიტომ ხაზები, რომლებიც მხოლოდ მათ დაფარეს, არადაფარულად ითვლება.
- **სხვა შარდების ტესტები**, როდესაც თქვენ [ტესტებს შარდებათ](#sharded-runs).

## წარმადობაზე გავლენა {#performance-impact}

JaCoCo ინსტრუმენტებს კლასებს, როგორც ტესტის JVM ტვირთავს მათ, ამიტომ თქვენი კომპილირებული კლასები და კომპილაციის ამოცანების ბილდის ქეშის ჩანაწერები უცვლელი რჩება დაფარვის ჩართვის ან გამორთვისას. ამოცანები, რომლებიც კითხულობენ ყველა დამოკიდებულების კონფიგურაციას, როგორიცაა SBOM გენერატორები, ასევე ხედავენ JaCoCo-ს აგენტს, ამიტომ მათი შედეგები იცვლება, როდესაც დაფარვას ჩართავთ. ტესტები ოდნავ ნელა სრულდება და პლაგინი კითხულობს JaCoCo-ს მონაცემებს ტესტის ამოცანების დასრულების შემდეგ. ტესტის ამოცანებს ჩართული და გამორთული დაფარვით აქვთ ცალკეული ბილდის ქეშის ჩანაწერები, ამიტომ პირველი გაშვება ჩართული დაფარვით ასრულებს ტესტებს მაშინაც, როცა მათი შედეგები დაფარვის გარეშე ქეშირებულია.

## შეზღუდვები {#limitations}

- **იზოლირებული პროექტები და კონფიგურაცია მოთხოვნისას.** ეს ბილდები არ აკონფიგურირებენ ყველა პროექტს, ამიტომ პლაგინს არ შეუძლია განსაზღვროს, რომელი პროექტების ტესტები გამოტოვა გაშვებამ და ზოგიერთი პროექტის ტესტების გაშვება სრულად ითვლება.
- **არ არის დაფარვა ფორკებიდან გახსნილი პულ-რეკვესტებიდან.** დაფარვა აიტვირთება მხოლოდ იმ გაშვებების მიერ, რომლებიც ავტორიზაციას გადიან Tuist-თან, და CI ჩვეულებრივ ფარავს საიდუმლოებსა და იდენტობის ტოკენებს ფორკებიდან გახსნილი პულ-რეკვესტებისგან.

## დაფარვის მოთხოვნა {#querying}

დაშბორდის **კოდის დაფარვა** გვერდი აჩვენებს თითოეული კომიტის მაჩვენებელს, მის მოდულებს და ფაილებს, იმ ხაზებით, რომლებიც თითოეულმა გაშვებამ დაფარა. იგივე მონაცემები ხელმისაწვდომია აგენტებისთვის <.localized_link href="/guides/features/agentic-coding/mcp">Model Context Protocol სერვერის</.localized_link> მეშვეობით.
