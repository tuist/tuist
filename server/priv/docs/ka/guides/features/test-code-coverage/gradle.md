# Gradle-ის კოდის დაფარვა {#gradle-code-coverage}

კოდის დაფარვა გაჩვენებთ, თქვენი ტესტების მიერ შესრულებულ კოდის ხაზებს. Tuist-ის Gradle პლაგინი ზომავს თქვენი ტესტების ამოცანების დაფარვას JaCoCo-ს საშუალებით და ატვირთავს მას ყოველ ტესტების გაშვებაზე, ხოლო Tuist აერთიანებს კომიტის გაშვებებს ერთ მაჩვენებლად — პროექტისთვის, თითოეული Gradle პროექტისთვის და თითოეული ფაილისთვის. დაშბორდის **კოდის დაფარვის** გვერდი აჩვენებს მას კომიტების მიხედვით და როგორც ტრენდს თითოეული ბრენჩისთვის.

> [!IMPORTANT]
> **მოთხოვნები**
>
> - გამოყენებულია `dev.tuist` Gradle პლაგინი, როგორც აღწერილია <.localized_link href="/guides/get-started/gradle-project">დაწყება Gradle პროექტით</.localized_link>-ში
> - თქვენი პროექტი Git რეპოზიტორიაში: გაშვება რეპოზიტორიის გარეთ ატვირთავს ტესტების შედეგებს, მაგრამ არა დაფარვას

## მორგება {#setup}

### დაფარვის ჩართვა {#turn-coverage-on}

ჩართეთ დაფარვა თქვენი `settings.gradle.kts`-ის `tuist` ბლოკში:

```kotlin
tuist {
    coverage {
        enabled = true
    }
}
```

ან ჩართეთ ის ერთი გამოძახებისთვის, მაგალითად CI სამუშაოსთვის, გარემოს ცვლადის საშუალებით, რომელიც ნებისმიერ შემთხვევაში უპირატესობას იღებს პარამეტრზე:

```sh
TUIST_TEST_COVERAGE=1 ./gradlew test
```

ტესტების ამოცანებს ჩართული და გამორთული დაფარვით აქვთ ცალკე ბილდის ქეშის ჩანაწერები (იხილეთ [წარმადობაზე გავლენა](#performance-impact)), ამიტომ უპირატესობა მიანიჭეთ პარამეტრს, როდესაც თქვენი CI და ლოკალური ბილდები იზიარებენ ბილდის ქეშს: დაფარვის მხოლოდ CI-ში ჩართვა ხელს უშლის მათ ერთმანეთის ტესტების შედეგების ხელახლა გამოყენებას.

ჩართული დაფარვის შემთხვევაში, პლაგინი ამატებს Gradle-ის `jacoco` პლაგინს ყოველ JVM პროექტს. JaCoCo-ს აგენტი მოდის თქვენი პროექტის რეპოზიტორიებიდან, ისევე როგორც ეს იქნებოდა, თქვენ რომ თავად დაამატოთ პლაგინი. პროექტი, რომელიც უკვე აკონფიგურირებს JaCoCo-ს, ინარჩუნებს თავის პარამეტრებს და მისი საკუთარი ანგარიშები განაგრძობენ მუშაობას.

### Android პროექტები {#android-projects}

პლაგინი ზომავს Android პროექტების ლოკალურ ერთეულურ ტესტებს, როგორიცაა `testDebugUnitTest`. ინსტრუმენტული ტესტები, რომლებიც გაშვებულია მოწყობილობაზე ან ემულატორზე, არ იზომება.

თუ თქვენი ერთეულური ტესტები იყენებენ Robolectric-ს, უთხარით JaCoCo-ს, რომ ჩართოს კლასები, რომლებსაც Robolectric ტვირთავს. Robolectric განსაზღვრავს თქვენი აპლიკაციის კლასებს საკუთარ კლასის ჩამტვირთავში, ხოლო JaCoCo ნაგულისხმევად ტოვებს ასეთ კლასებს, ამიტომ კოდი, რომელსაც ეს ტესტები ასრულებენ, გამოჩნდება როგორც არადაფარული. Android პროექტის `build.gradle.kts`-ში:

```kotlin
pluginManager.withPlugin("jacoco") {
    tasks.withType<Test>().configureEach {
        extensions.configure<JacocoTaskExtension> {
            isIncludeNoLocationClasses = true
            excludes = listOf("jdk.internal.*")
        }
    }
}
```

ბლოკი მოქმედებს მხოლოდ მაშინ, როდესაც დაფარვა ჩართულია, რადგან სწორედ მაშინ ამატებს პლაგინი `jacoco`-ს.

Android-ის ერთეულური ტესტები ნაგულისხმევად გაშვებულია JUnit 4-ზე, რომელიც აღრიცხავს დაფარვას, მაგრამ არა [რომელი კოდი შეასრულა თითოეულმა ტესტმა](#per-test-evidence). მის აღრიცხვისთვის, გაუშვით ისინი JUnit Platform-ზე JUnit Vintage-ის საშუალებით.

### დაყოფილი გაშვებები {#sharded-runs}

როდესაც თქვენ <.localized_link href="/guides/features/test-sharding/gradle">ყოფთ თქვენს ტესტებს</.localized_link>, ყოველი შარდი, რომელიც გაშვებულია ჩართული დაფარვით, ანგარიშგებს იმ ტესტების დაფარვას, რომლებიც მან შეასრულა, და Tuist აერთიანებს გაშვების შარდებს ერთ მაჩვენებლად. შარდი მიზანმიმართულად ასრულებს სუიტის ნაწილს, ამიტომ ის არ ხდის კომიტის დაფარვას არასრულყოფილს.

### ყოველი კომიტის დასრულება CI-ზე {#complete-each-commit}

კომიტის დაფარვა ხშირად მოდის რამდენიმე სამუშაოდან, მაგალითად, ერთი შარდისთვის. Tuist-ს არ შეუძლია გაიგოს, როდის ანგარიშგებს ბოლო მათგანი, ამიტომ უთხარით მას. მას შემდეგ, რაც კომიტის ყოველი ტესტის სამუშაო დასრულდება, გაუშვით ეს სამუშაოში, რომელიც დამოკიდებულია მათ ყველაზე:

```sh
./gradlew tuistCoverageComplete
```

როდესაც ერთი სამუშაო ასრულებს კომიტის ყველა ტესტს, გაუშვით ამოცანა როგორც ნაბიჯი ტესტების შემდეგ, მათ შორის მაშინაც, როდესაც ტესტები ვერ ხერხდება: ვერშეუსრულებელი ტესტების მქონე გაშვებაც ანგარიშგებს თავის დაფარვას.

ამოცანა კითხულობს კომიტს `GIT_COMMIT`-დან ან checkout-ის `HEAD`-დან; გადაეცით `-Ptuist.coverage.commit=<sha>` სხვის დასახელებლად. სანამ კომიტი არ დასრულდება, მისი დაფარვა ჩანს როგორც **მიმდინარე** და არ შედის მისი ბრენჩის ტრენდში.

## როგორ მუშაობს {#how-it-works}

### რას ზომავს Tuist {#what-tuist-measures}

- **პროექტები.** ყოველი Gradle პროექტი არის მოდული დაშბორდზე, საკუთარი დაფარვით.
- **მხოლოდ პროდუქციის კოდი.** კლასები, რომლებიც კომპილირებულია ტესტების წყაროების ნაკრებებიდან, არის ტესტების კოდი. Tuist ინახავს მათ, მაგრამ ტოვებს მათ ყოველი მაჩვენებლის გარეთ.
- **თქვენი რეპოზიტორიის ფაილები.** კლასი ითვლება იმ საწყისი ფაილისთვის, რომლიდანაც ის იყო კომპილირებული, მისი გზის მიხედვით თქვენს რეპოზიტორიაში. გენერირებული წყაროები და ფაილები, რომლებსაც Git იგნორირებს, არ არის მოხსენებული.
- **შესრულდა თუ არა თითოეული ხაზი.** JaCoCo აღრიცხავს, შესრულდა თუ არა კოდი, არა თუ რამდენჯერ, ამიტომ დაშბორდის შესრულების რაოდენობა არის 0 ან 1.

### რომელი კოდი შეასრულა თითოეულმა ტესტმა {#per-test-evidence}

JUnit Platform-ზე გაშვებული ტესტებისთვის (JUnit 5, ან JUnit 4 JUnit Vintage-ის საშუალებით), პლაგინი ასევე აღრიცხავს, რომელი კოდი შეასრულა თითოეულმა ტესტმა და რა შეასრულა თითოეულმა ტესტის კლასმა ტესტების გარეთ, მაგალითად `@BeforeAll`-ში. ეს არის ის, რაც საშუალებას აძლევს Tuist-ს გადაიტანოს იმ ტესტების დაფარვა, რომლებიც გაშვებამ გამოტოვა (იხილეთ [გამოტოვებული ტესტები](#skipped-tests)). თქვენს ტესტებს არაფერი უნდა დაემატოს.

ეს მუშაობს, როდესაც თითოეული ტესტის JVM ასრულებს ერთ ტესტს ერთდროულად, რაც არის ის, თუ როგორ ასრულებს Gradle ტესტებს, თუ არ ჩართავთ JUnit-ის პარალელურ შესრულებას. ტესტის კლასების გაშვება რამდენიმე JVM-ში `maxParallelForks`-ით არის დასაშვები. ტესტები, რომლებიც ერთდროულად გაშვებულია ერთ JVM-ში, ასევე ითვლება დაფარვაში, მაგრამ არა ცალ-ცალკე.

### ბილდის ქეში {#build-cache}

ტესტის ამოცანა, რომელსაც Gradle აღადგენს ბილდის ქეშიდან, ან რომელიც აქტუალურია, არ ასრულებს ტესტებს. მისი დაფარვა მაინც აიტვირთება: JaCoCo-ს მონაცემები არის ამოცანის ერთ-ერთი გამომავალი, რომელიც ჩაიწერა გაშვების მიერ, რომელმაც შეასრულა მისი ტესტები იმავე შეყვანებზე.

### გამოტოვებული ტესტები {#skipped-tests}

როდესაც გაშვება ტოვებს ტესტებს გარეთ, Tuist ავსებს იმას, რაც მათ დაფარეს ადრეული გაშვებიდან, იმ პირობით, რომ კოდი, რომელიც მათ შეასრულეს, უცვლელია. როდესაც ეს შეუძლებელია, კომიტის დაფარვა არის **არასრული**. რას ტოვებს გაშვება გარეთ:

- **პროექტის ტესტის ამოცანის გამორიცხვა** `-x :app:test`-ით. მისი ტესტები გადააქვს ბოლო გაშვებიდან, რომლის კოდი უცვლელია.
- **ზოგიერთი პროექტის ტესტები** `./gradlew :core:test`-ით, ან **ზოგიერთი ტესტი** `--tests`-ით. გაშვება ფარავს მხოლოდ იმას, რაც მოითხოვეთ, ამიტომ კომიტი არასრულია, თუ კომიტის სხვა გაშვებამ არ შეასრულა ყველაფერი.
- **ტესტის ამოცანა, რომელიც შეჩერდა პირველ ვერშეუსრულებლობაზე** (`failFast`).

ზოგიერთი ტესტი მიზანმიმართულად არის გამოტოვებული და არ ხდის კომიტს არასრულს:

- **ფილტრები თქვენს ბილდის სკრიპტში**, როგორიცაა `filter { excludeTestsMatching(...) }`, რომლებიც განსაზღვრავენ, რას ასრულებს თქვენი სუიტა.
- **ტესტის ამოცანები, რომლებსაც თქვენი ბილდის სკრიპტი თიშავს**, `enabled = false`-ით ან `onlyIf`-ით, რომელიც ტოვებს მათ გარეთ.
- **ტესტები, რომლებსაც <.localized_link href="/guides/features/test-insights/flaky-tests/gradle">კარანტინი</.localized_link> ტოვებს გარეთ.** ისინი გამოტოვებულია ისე, თითქოს წაშლილი იყვნენ, ამიტომ ხაზები, რომლებიც მხოლოდ მათ დაფარეს, ჩაითვლება დაუფარავად.
- **სხვა შარდების ტესტები**, როდესაც თქვენ [ყოფთ ტესტებს შარდებად](#sharded-runs).

## წარმადობაზე გავლენა {#performance-impact}

JaCoCo ინსტრუმენტებს კლასებს, როგორც ტესტის JVM ტვირთავს მათ, ამიტომ თქვენი კომპილირებული კლასები და კომპილაციის ამოცანების ბილდის ქეშის ჩანაწერები უცვლელი რჩება დაფარვის ჩართვით ან გამორთვით. ამოცანები, რომლებიც კითხულობენ ყველა დამოკიდებულების კონფიგურაციას, როგორიცაა SBOM გენერატორები, ასევე ხედავენ JaCoCo-ს აგენტს, ამიტომ მათი გამომავალი იცვლება, როდესაც ჩართავთ დაფარვას. ტესტები ოდნავ ნელა სრულდება და პლაგინი კითხულობს JaCoCo-ს მონაცემებს ტესტის ამოცანების დასრულების შემდეგ. ტესტის ამოცანებს ჩართული და გამორთული დაფარვით აქვთ ცალკეული ბილდის ქეშის ჩანაწერები, ამიტომ პირველი გაშვება ჩართული დაფარვით ასრულებს ტესტებს მაშინაც კი, თუ მათი შედეგები დაფარვის გარეშე არის ქეშირებული.

## შეზღუდვები {#limitations}

- **იზოლირებული პროექტები და კონფიგურაცია მოთხოვნისას.** ეს ბილდები არ აკონფიგურირებენ ყველა პროექტს, ამიტომ პლაგინს არ შეუძლია განსაზღვროს, რომელი პროექტების ტესტები დატოვა გაშვებამ გარეთ, და ზოგიერთი პროექტის ტესტების გაშვება ითვლება სრულად.
- **არ არის დაფარვა ფორკებიდან გახსნილი პულ-რეკვესტებიდან.** დაფარვა აიტვირთება მხოლოდ იმ გაშვებების მიერ, რომლებიც ავთენტიკაციას გადიან Tuist-თან, და CI ჩვეულებრივ უკავებს საიდუმლოებს და იდენტობის ტოკენებს ფორკებიდან გახსნილ პულ-რეკვესტებს.

## დაფარვის მოთხოვნა {#querying}

დაშბორდის **კოდის დაფარვა** გვერდი აჩვენებს თითოეული კომიტის მაჩვენებელს, მის მოდულებს და ფაილებს, იმ ხაზებით, რომლებიც თითოეულმა გაშვებამ დაფარა. იგივე მონაცემები ხელმისაწვდომია აგენტებისთვის <.localized_link href="/guides/features/agentic-coding/mcp">Model Context Protocol სერვერის</.localized_link> მეშვეობით.
