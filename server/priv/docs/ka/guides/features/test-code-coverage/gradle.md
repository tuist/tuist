# Gradle-ის კოდის დაფარვა {#gradle-code-coverage}

კოდის დაფარვა გაჩვენებთ, თქვენი ტესტების მიერ შესრულებული კოდის რომელი ხაზებია. Tuist-ის Gradle პლაგინი JaCoCo-ს საშუალებით ზომავს თქვენი ტესტების ამოცანების დაფარვას და ატვირთავს მას ყოველი ტესტების გაშვებისას, ხოლო Tuist აერთიანებს კომიტის გაშვებებს ერთ მაჩვენებლად — პროექტისთვის, თითოეული Gradle პროექტისთვის და თითოეული ფაილისთვის. დაფის **კოდის დაფარვის** გვერდი აჩვენებს მას კომიტების მიხედვით და როგორც ტენდენციას თითოეული შტოსთვის.

> [!IMPORTANT]
> **მოთხოვნები**
>
> - გამოყენებულია `dev.tuist` Gradle პლაგინი, როგორც აღწერილია <.localized_link href="/guides/get-started/gradle-project">დაწყება Gradle პროექტთან</.localized_link>
> - თქვენი პროექტი Git რეპოზიტორიაში: მის გარეთ გაშვება ატვირთავს ტესტების შედეგებს, მაგრამ არა დაფარვას

## მორგება {#setup}

### დაფარვის ჩართვა {#turn-coverage-on}

ჩართეთ დაფარვა თქვენი `settings.gradle.kts`-ის `tuist` ბლოკში:

```kotlin
tuist {
    coverage {
        enabled = true
    }
}
```

ან ჩართეთ იგი ერთი გამოძახებისთვის, მაგალითად CI სამუშაოსთვის, გარემოს ცვლადის მეშვეობით, რომელსაც ნებისმიერ შემთხვევაში უპირატესობა ენიჭება პარამეტრთან მიმართებაში:

```sh
TUIST_TEST_COVERAGE=1 ./gradlew test
```

ტესტების ამოცანებს ჩართული და გამორთული დაფარვით აქვთ ცალკეული აგების ქეშის ჩანაწერები (იხილეთ [წარმადობაზე გავლენა](#performance-impact)), ამიტომ უპირატესობა მიანიჭეთ პარამეტრს, როდესაც თქვენი CI და ადგილობრივი აგებები იზიარებენ აგების ქეშს: დაფარვის მხოლოდ CI-ში ჩართვა ხელს უშლის მათ ერთმანეთის ტესტების შედეგების ხელახლა გამოყენებას.

ჩართული დაფარვის პირობებში, პლაგინი თითოეულ JVM პროექტზე ავრცელებს Gradle-ის `jacoco` პლაგინს. JaCoCo-ს აგენტი მოდის თქვენი პროექტის რეპოზიტორიებიდან, ისევე როგორც ეს იქნებოდა, თქვენ რომ თავად გამოგეყენებინათ პლაგინი. პროექტი, რომელიც უკვე აკონფიგურირებს JaCoCo-ს, ინარჩუნებს თავის პარამეტრებს და მისი საკუთარი ანგარიშები განაგრძობენ მუშაობას.

### Android პროექტები {#android-projects}

პლაგინი ზომავს Android პროექტების ადგილობრივ ერთეულურ ტესტებს, მაგალითად `testDebugUnitTest`. ინსტრუმენტული ტესტები, რომლებიც მოწყობილობაზე ან ემულატორზე გადის, არ იზომება.

თუ თქვენი ერთეულური ტესტები იყენებენ Robolectric-ს, მიუთითეთ JaCoCo-ს, რომ ჩართოს Robolectric-ის მიერ ჩატვირთული კლასები. Robolectric განსაზღვრავს თქვენი აპლიკაციის კლასებს საკუთარ კლასების ჩამტვირთავში, ხოლო JaCoCo ნაგულისხმევად ტოვებს ასეთ კლასებს, ამიტომ კოდი, რომელსაც ეს ტესტები ასრულებენ, გამოჩნდება როგორც დაუფარავი. Android პროექტის `build.gradle.kts`-ში:

```kotlin
pluginManager.withPlugin("jacoco") {
    tasks.withType<Test>().configureEach {
        extensions.configure<JacocoTaskExtension> {
            isIncludeNoLocationClasses = true
            excludes = listOf("jdk.internal.*")
        }
    }
}
```

ბლოკი ვრცელდება მხოლოდ მაშინ, როდესაც დაფარვა ჩართულია, რადგან სწორედ მაშინ ავრცელებს პლაგინი `jacoco`-ს.

Android-ის ერთეულური ტესტები ნაგულისხმევად გადის JUnit 4-ზე, რომელიც აღრიცხავს დაფარვას, მაგრამ არა [იმ კოდს, რომელიც თითოეულმა ტესტმა შეასრულა](#per-test-evidence). მის აღრიცხვისთვის, გაუშვით ისინი JUnit Platform-ზე JUnit Vintage-ის მეშვეობით.

### დაშლილი გაშვებები {#sharded-runs}

როდესაც თქვენ <.localized_link href="/guides/features/test-sharding/gradle">ყოფთ თქვენს ტესტებს</.localized_link>, ყოველი დაშლა, რომელიც ჩართული დაფარვით გადის, ანგარიშგებს მის მიერ შესრულებული ტესტების დაფარვას და Tuist აერთიანებს გაშვების დაშლებს ერთ მაჩვენებლად. დაშლა განზრახ ასრულებს სუიტის ნაწილს, ამიტომ ის არ ხდის კომიტის დაფარვას არასრულყოფილს.

### CI-ზე თითოეული კომიტის დასრულება {#complete-each-commit}

კომიტის დაფარვა ხშირად მოდის რამდენიმე სამუშაოდან, მაგალითად, ერთი დაშლისთვის. Tuist-ს არ შეუძლია გაიგოს, როდის ანგარიშგებოდა ბოლო მათგანი, ამიტომ მიუთითეთ მას. მას შემდეგ, რაც კომიტის ყოველი ტესტის სამუშაო დასრულდება, გაუშვით ეს იმ სამუშაოში, რომელიც დამოკიდებულია მათ ყველაზე:

```sh
./gradlew tuistCoverageComplete
```

როდესაც ერთი სამუშაო ასრულებს კომიტის ყველა ტესტს, გაუშვით ამოცანა როგორც ნაბიჯი ტესტების შემდეგ, მათ შორის მაშინაც, როდესაც ტესტები ვერ ხერხდება: ვერშესრულებული ტესტების მქონე გაშვებაც ანგარიშგებს თავის დაფარვას.

ამოცანა კითხულობს კომიტს checkout-ის `HEAD`-დან, კომიტს, რომელზეც თქვენი ტესტები გადიოდა; გადაეცით `-Ptuist.coverage.commit=<sha>` სხვის დასახელებისთვის. სანამ კომიტი არ დასრულდება, მისი დაფარვა ჩანს როგორც **მიმდინარე** და რჩება მისი შტოს ტენდენციის გარეთ.

## როგორ მუშაობს {#how-it-works}

### რას ზომავს Tuist {#what-tuist-measures}

- **პროექტები.** თითოეული Gradle პროექტი არის მოდული დაფაზე, საკუთარი დაფარვით.
- **მხოლოდ პროდუქტის კოდი.** ტესტების წყაროების სიმრავლეებიდან კომპილირებული კლასები არის ტესტების კოდი. Tuist ინახავს მათ, მაგრამ ტოვებს მათ ყოველი მაჩვენებლის გარეთ.
- **თქვენი რეპოზიტორიის ფაილები.** კლასი ითვლება იმ საწყისი ფაილისთვის, საიდანაც ის იყო კომპილირებული, მისი გზის მიხედვით თქვენს რეპოზიტორიაში. გენერირებული წყაროები და Git-ის მიერ იგნორირებული ფაილები არ ანგარიშგდება.
- **შესრულდა თუ არა თითოეული ხაზი.** JaCoCo აღრიცხავს, შესრულდა თუ არა კოდი, არა თუ რამდენჯერ, ამიტომ დაფის შესრულების რაოდენობა არის 0 ან 1.

### რომელი კოდი შეასრულა თითოეულმა ტესტმა {#per-test-evidence}

JUnit Platform-ზე (JUnit 5, ან JUnit 4 JUnit Vintage-ის მეშვეობით) მომუშავე ტესტებისთვის, პლაგინი ასევე აღრიცხავს, თუ რომელი კოდი შეასრულა თითოეულმა ტესტმა და რა შეასრულა თითოეულმა ტესტის კლასმა ტესტების გარეთ, მაგალითად `@BeforeAll`-ში. ეს არის ის, რაც საშუალებას აძლევს Tuist-ს გადაიტანოს იმ ტესტების დაფარვა, რომლებიც გაშვებამ გამოტოვა (იხილეთ [გამოტოვებული ტესტები](#skipped-tests)). თქვენს ტესტებში არაფრის დამატება არ არის საჭირო.

ეს მუშაობს, როდესაც თითოეული ტესტის JVM ასრულებს ერთ ტესტს ერთდროულად, რაც არის Gradle-ის ტესტების გაშვების წესი, თუ არ ჩართავთ JUnit-ის პარალელურ შესრულებას. ტესტების კლასების გაშვება რამდენიმე JVM-ში `maxParallelForks`-ის მეშვეობით დასაშვებია. ერთსა და იმავე JVM-ში ერთდროულად მომუშავე ტესტები მაინც ითვლება დაფარვაში, მაგრამ არა ცალ-ცალკე.

### აგების ქეში {#build-cache}

ტესტების ამოცანა, რომელსაც Gradle აღადგენს აგების ქეშიდან, ან რომელიც აქტუალურია, არ ასრულებს ტესტებს. მისი დაფარვა მაინც აიტვირთება: JaCoCo-ს მონაცემები არის ამოცანის ერთ-ერთი გამომავალი, ჩაწერილი იმ გაშვების მიერ, რომელმაც შეასრულა მისი ტესტები იმავე შეყვანებზე.

### გამოტოვებული ტესტები {#skipped-tests}

როდესაც გაშვება ტოვებს ტესტებს გარეთ, Tuist ავსებს იმას, რაც მათ დაფარეს ადრეული გაშვებიდან, იმ პირობით, რომ მათ მიერ შესრულებული კოდი უცვლელია. როდესაც ეს შეუძლებელია, კომიტის დაფარვა არის **არასრული**. რას ტოვებს გაშვება გარეთ:

- **პროექტის ტესტის ამოცანის გამორიცხვა** `-x :app:test`-ით. მისი ტესტები გადააქვთ მათი ბოლო გაშვებიდან, რომლის კოდი უცვლელია.
- **ზოგიერთი პროექტის ტესტები** `./gradlew :core:test`-ით, ან **ზოგიერთი ტესტი** `--tests`-ით. გაშვება ფარავს მხოლოდ იმას, რაც მოითხოვეთ, ამიტომ კომიტი არის არასრული, თუ კომიტის სხვა გაშვებამ არ შეასრულა ყველაფერი.
- **ტესტის ამოცანა, რომელიც შეჩერდა პირველი შეცდომისას** (`failFast`).

ზოგიერთი ტესტი განზრახ არის გამოტოვებული და არ ხდის კომიტს არასრულს:

- **ფილტრები თქვენს აგების სკრიპტში**, მაგალითად `filter { excludeTestsMatching(...) }`, რომლებიც განსაზღვრავენ, რას ასრულებს თქვენი სუიტა.
- **ტესტის ამოცანები, რომლებსაც თქვენი აგების სკრიპტი თიშავს**, `enabled = false`-ით ან `onlyIf`-ით, რომელიც გამოტოვებს მათ.
- **ტესტები, რომლებსაც <.localized_link href="/guides/features/test-insights/flaky-tests/gradle">კარანტინი</.localized_link> ტოვებს გარეთ.** ისინი გამოტოვებულია ისე, თითქოს წაშლილი იყოს, ამიტომ ხაზები, რომლებიც მხოლოდ მათ დაფარეს, ჩაითვლება დაუფარავად.
- **სხვა შარდების ტესტები**, როდესაც თქვენ [ყოფთ ტესტებს შარდებად](#sharded-runs).

## წარმადობაზე გავლენა {#performance-impact}

JaCoCo ინსტრუმენტაციას უკეთებს კლასებს, როდესაც სატესტო JVM ტვირთავს მათ, ამიტომ თქვენი კომპილირებული კლასები და კომპილაციის ამოცანების აგების ქეშის ჩანაწერები უცვლელი რჩება, მიუხედავად იმისა, ჩართულია დაფარვა თუ არა. ამოცანები, რომლებიც კითხულობენ ყველა დამოკიდებულების კონფიგურაციას, მაგალითად SBOM გენერატორები, ასევე ხედავენ JaCoCo-ს აგენტს, ამიტომ მათი გამომავალი იცვლება, როდესაც ჩართავთ დაფარვას. ტესტები ოდნავ ნელა სრულდება და პლაგინი კითხულობს JaCoCo-ს მონაცემებს ტესტის ამოცანების დასრულების შემდეგ. ტესტის ამოცანებს ჩართული და გამორთული დაფარვით აქვთ ცალკე აგების ქეშის ჩანაწერები, ამიტომ პირველი გაშვება ჩართული დაფარვით ასრულებს ტესტებს მაშინაც კი, როდესაც მათი შედეგები დაფარვის გარეშე არის ქეშირებული.

## შეზღუდვები {#limitations}

- **იზოლირებული პროექტები და კონფიგურაცია მოთხოვნისას.** ეს აგებები არ აკონფიგურირებენ ყველა პროექტს, ამიტომ პლაგინს არ შეუძლია განსაზღვროს, რომელი პროექტების ტესტები გამოტოვა გაშვებამ, და ზოგიერთი პროექტის ტესტების გაშვება ითვლება სრულად.
- **დაფარვა არ არის ხელმისაწვდომი ფორკებიდან გახსნილი პულ-რეკვესტებიდან.** დაფარვა აიტვირთება მხოლოდ იმ გაშვებების მიერ, რომლებიც ავთენტიკაციას გადიან Tuist-თან, და CI ჩვეულებრივ ფარავს საიდუმლოებებს და იდენტობის ტოკენებს ფორკებიდან გახსნილი პულ-რეკვესტებისგან.

## დაფარვის მოთხოვნა {#querying}

დაშბორდის **კოდის დაფარვა** გვერდი აჩვენებს თითოეული კომიტის მაჩვენებელს, მის მოდულებს და ფაილებს, იმ ხაზებით, რომლებიც თითოეულმა გაშვებამ დაფარა. იგივე მონაცემები ხელმისაწვდომია აგენტებისთვის <.localized_link href="/guides/features/agentic-coding/mcp">Model Context Protocol სერვერის</.localized_link> მეშვეობით.
