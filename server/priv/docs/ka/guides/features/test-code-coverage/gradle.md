# Gradle-ის კოდის დაფარვა {#gradle-code-coverage}

კოდის დაფარვა გიჩვენებთ, თქვენი ტესტების მიერ შესრულებულ კოდის ხაზებს. Tuist-ის Gradle პლაგინი ზომავს თქვენი ტესტების ამოცანების დაფარვას JaCoCo-ს საშუალებით და ატვირთავს მას ყოველი ტესტების გაშვებისას, ხოლო Tuist აერთიანებს კომიტის გაშვებებს ერთ მაჩვენებლად — პროექტისთვის, თითოეული Gradle პროექტისთვის და თითოეული ფაილისთვის. დაშბორდის **კოდის დაფარვის** გვერდი აჩვენებს მას კომიტების მიხედვით და როგორც ტენდენციას თითოეული ბრენჩისთვის.

> [!IMPORTANT]
> **მოთხოვნები**
>
> - გამოყენებულია `dev.tuist` Gradle პლაგინი, როგორც აღწერილია <.localized_link href="/guides/get-started/gradle-project">დაიწყეთ Gradle პროექტით</.localized_link>
> - თქვენი პროექტი Git რეპოზიტორიაში: რეპოზიტორიის გარეთ გაშვება ატვირთავს ტესტების შედეგებს, მაგრამ არა დაფარვას

## მორგება {#setup}

### ჩართეთ დაფარვა {#turn-coverage-on}

ჩართეთ დაფარვა თქვენი `settings.gradle.kts`-ის `tuist` ბლოკში:

```kotlin
tuist {
    coverage {
        enabled = true
    }
}
```

ან ჩართეთ ის ერთი გამოძახებისთვის, მაგალითად CI სამუშაოსთვის, გარემოს ცვლადის საშუალებით, რომელსაც აქვს უპირატესობა ნებისმიერი პარამეტრის მიმართ:

```sh
TUIST_TEST_COVERAGE=1 ./gradlew test
```

ტესტების ამოცანებს ჩართული და გამორთული დაფარვით აქვთ ცალკეული ბილდის ქეშის ჩანაწერები (იხილეთ [წარმადობაზე გავლენა](#performance-impact)), ამიტომ უპირატესობა მიანიჭეთ პარამეტრს, როდესაც თქვენი CI და ადგილობრივი ბილდები იზიარებენ ბილდის ქეშს: დაფარვის მხოლოდ CI-ში ჩართვა ხელს უშლის მათ ერთმანეთის ტესტების შედეგების ხელახლა გამოყენებას.

ჩართული დაფარვის შემთხვევაში, პლაგინი აკავშირებს Gradle-ის `jacoco` პლაგინს ყოველ JVM პროექტთან. JaCoCo-ს აგენტი მოდის თქვენი პროექტის რეპოზიტორებიდან, ისევე როგორც ეს იქნებოდა, თქვენ რომ თავად დააკავშიროთ პლაგინი. პროექტი, რომელიც უკვე აკონფიგურირებს JaCoCo-ს, ინარჩუნებს თავის პარამეტრებს და მისი საკუთარი ანგარიშები განაგრძობენ მუშაობას.

პლაგინი ანგარიშგებს მხოლოდ თქვენი რეპოზიტორიის კოდის დაფარვას, ამიტომ ის ზღუდავს JaCoCo-ს მისთვის: თუ ტესტების ამოცანა თავად არ აყენებს JaCoCo-ს `includes`-ს, აგენტი ინსტრუმენტაციას უკეთებს მხოლოდ იმ პაკეტებს, რომელთა კლასებსაც თქვენი რეპოზიტორია აკომპილირებს. დამოკიდებულებები, Android ჩარჩო და თქვენი ტესტების ჩარჩოები მუშაობენ ინსტრუმენტაციის გარეშე, რაც JaCoCo-ს მონაცემებს და ტესტების ამოცანების ბილდის ქეშის ჩანაწერებს მცირეს ტოვებს.

### Android პროექტები {#android-projects}

პლაგინი ზომავს Android პროექტების ადგილობრივ ერთეულოვან ტესტებს, როგორიცაა `testDebugUnitTest`. ინსტრუმენტირებული ტესტები, რომლებიც მუშაობენ მოწყობილობაზე ან ემულატორზე, არ იზომება.

თუ თქვენი ერთეულოვანი ტესტები იყენებენ Robolectric-ს, უთხარით JaCoCo-ს, რომ ჩართოს კლასები, რომლებსაც Robolectric ტვირთავს. Robolectric განსაზღვრავს თქვენი აპლიკაციის კლასებს თავის კლასების ჩამტვირთავში, და JaCoCo ნაგულისხმევად ტოვებს ასეთ კლასებს, ამიტომ იმ კოდს, რომელსაც ეს ტესტები ასრულებენ, დაფარული არ ექნება. Android პროექტის `build.gradle.kts`-ში:

```kotlin
pluginManager.withPlugin("jacoco") {
    tasks.withType<Test>().configureEach {
        extensions.configure<JacocoTaskExtension> {
            isIncludeNoLocationClasses = true
            excludes = listOf("jdk.internal.*")
        }
    }
}
```

ბლოკი მოქმედებს მხოლოდ მაშინ, როდესაც დაფარვა ჩართულია, რადგან სწორედ მაშინ აკავშირებს პლაგინი `jacoco`-ს.

Android-ის ერთეულოვანი ტესტები ნაგულისხმევად მუშაობენ JUnit 4-ზე, რომელიც აღრიცხავს დაფარვას, მაგრამ არა [იმ კოდს, რომელიც თითოეულმა ტესტმა შეასრულა](#per-test-evidence). მის აღრიცხვისთვის, გაუშვით ისინი JUnit Platform-ზე JUnit Vintage-ის საშუალებით.

### დაშლილი გაშვებები {#sharded-runs}

როდესაც თქვენ <.localized_link href="/guides/features/test-sharding/gradle">ყოფთ თქვენს ტესტებს</.localized_link>, ყოველი შარდი, რომელიც მუშაობს ჩართული დაფარვით, ანგარიშგებს მის მიერ შესრულებული ტესტების დაფარვას და Tuist აერთიანებს გაშვების შარდებს ერთ მაჩვენებლად. შარდი განზრახ ასრულებს სუიტის ნაწილს, ამიტომ ის არ ხდის კომიტის დაფარვას არასრულყოფილს.

### დაასრულეთ ყოველი კომიტი CI-ზე {#complete-each-commit}

კომიტის დაფარვა ხშირად მოდის რამდენიმე სამუშაოდან, მაგალითად, ერთი შარდისთვის. Tuist-ს არ შეუძლია გაიგოს, როდის ანგარიშგებოდა ბოლო მათგანი, ამიტომ მიუთითეთ ეს მას. როდესაც კომიტის ყოველი ტესტის სამუშაო დასრულდება, გაუშვით ეს სამუშაოში, რომელიც დამოკიდებულია მათ ყველაზე:

```sh
./gradlew tuistCoverageComplete
```

როდესაც ერთი სამუშაო ასრულებს კომიტის ყველა ტესტს, გაუშვით ამოცანა როგორც ნაბიჯი ტესტების შემდეგ, მათ შორის მაშინაც, როდესაც ტესტები ვერ ხერხდება: ვერშესრულებული ტესტების მქონე გაშვებაც ანგარიშგებდა თავის დაფარვას.

ამოცანა კითხულობს კომიტს ჩექაუთის `HEAD`-დან, კომიტს, რომელზეც თქვენი ტესტები მუშაობდნენ; გადაეცით `-Ptuist.coverage.commit=<sha>` სხვის დასახელებლად. სანამ კომიტი არ დასრულდება, მისი დაფარვა ჩანს როგორც **მიმდინარე** და არ შედის მისი ბრენჩის ტენდენციაში.

## როგორ მუშაობს {#how-it-works}

### რას ზომავს Tuist {#what-tuist-measures}

- **პროექტები.** ყოველი Gradle პროექტი არის მოდული დაშბორდზე, საკუთარი დაფარვით.
- **მხოლოდ პროდუქტის კოდი.** კლასები, რომლებიც აკომპილირებულია ტესტების წყაროების სიმრავლეებიდან, არის ტესტების კოდი. Tuist ინახავს მათ, მაგრამ ტოვებს მათ ყოველი მაჩვენებლის გარეთ.
- **თქვენი რეპოზიტორიის ფაილები.** კლასი ითვლება იმ საწყისი ფაილისთვის, რომლიდანაც ის აკომპილირდა, მისი გზის მიხედვით თქვენს რეპოზიტორიაში. გენერირებული წყაროები და ფაილები, რომლებსაც Git იგნორირებს, არ ანგარიშგდება.
- **შესრულდა თუ არა თითოეული ხაზი.** JaCoCo აღრიცხავს, შესრულდა თუ არა კოდი, არა თუ რამდენჯერ, ამიტომ დაშბორდის შესრულების რაოდენობა არის 0 ან 1.

### რომელი კოდი შეასრულა თითოეულმა ტესტმა {#per-test-evidence}

JUnit Platform-ზე მომუშავე ტესტებისთვის (JUnit 5, ან JUnit 4 JUnit Vintage-ის საშუალებით), პლაგინი ასევე აღრიცხავს, რომელი კოდი შეასრულა თითოეულმა ტესტმა და რა შეასრულა თითოეულმა ტესტების კლასმა თავისი ტესტების გარეთ, მაგალითად `@BeforeAll`-ში. ეს არის ის, რაც Tuist-ს საშუალებას აძლევს გადაიტანოს იმ ტესტების დაფარვა, რომლებიც გაშვებამ გამოტოვა (იხილეთ [გამოტოვებული ტესტები](#skipped-tests)). თქვენს ტესტებში არაფრის დამატება არ არის საჭირო.

ეს მუშაობს, როდესაც თითოეული ტესტის JVM ასრულებს ერთ ტესტს ერთდროულად, რაც არის ის, როგორც Gradle ასრულებს ტესტებს, თუ არ ჩართავთ JUnit-ის პარალელურ შესრულებას. ტესტების კლასების რამდენიმე JVM-ში გაშვება `maxParallelForks`-ით არის დასაშვები. ტესტები, რომლებიც მუშაობენ ერთდროულად ერთ JVM-ში, ასევე ითვლებიან დაფარვაში, მაგრამ არა ერთი-ერთზე.

### ბილდის ქეში {#build-cache}

ტესტების ამოცანა, რომელსაც Gradle აღადგენს ბილდის ქეშიდან, ან რომელიც აქტუალურია, არ ასრულებს ტესტებს. მისი დაფარვა მაინც აიტვირთება: JaCoCo-ს მონაცემები არის ამოცანის ერთ-ერთი გამომავალი, ჩაწერილი იმ გაშვების მიერ, რომელმაც შეასრულა მისი ტესტები იმავე შეყვანებზე.

### გამოტოვებული ტესტები {#skipped-tests}

როდესაც გაშვება ტოვებს ტესტებს გარეთ, Tuist ავსებს იმას, რაც მათ დაფარეს ადრეული გაშვებიდან, სანამ მათ მიერ შესრულებული კოდი უცვლელია. როდესაც ეს შეუძლებელია, კომიტის დაფარვა არის **არასრული**. რას ტოვებს გაშვება გარეთ:

- **პროექტის ტესტების ამოცანა გამორიცხულია** `-x :app:test`-ით. მისი ტესტები გადააქვს ბოლო გაშვებიდან, რომლის კოდიც უცვლელია.
- **ზოგიერთი პროექტის ტესტები** `./gradlew :core:test`-ით, ან **ზოგიერთი ტესტი** `--tests`-ით. გაშვება ფარავს მხოლოდ იმას, რაც მოითხოვეთ, ამიტომ კომიტი არასრულია, თუ კომიტის სხვა გაშვებამ არ შეასრულა ყველაფერი.
- **ტესტების ამოცანა, რომელიც გაჩერდა პირველ ვერშესრულებაზე** (`failFast`).

ზოგიერთი ტესტი განზრახ არის გამოტოვებული და არ ხდის კომიტს არასრულს:

- **ფილტრები თქვენს ბილდის სკრიპტში**, მაგალითად `filter { excludeTestsMatching(...) }`, რომლებიც განსაზღვრავენ, რას ასრულებს თქვენი ტესტების ნაკრები.
- **ტესტების ამოცანები, რომლებსაც თქვენი ბილდის სკრიპტი თიშავს**, `enabled = false`-ით ან `onlyIf`-ით, რომელიც გამოტოვებს მათ.
- **ტესტები, რომლებსაც <.localized_link href="/guides/features/test-insights/flaky-tests/gradle">კარანტინი</.localized_link> ტოვებს გარეთ.** ისინი გამოტოვებულია ისე, თითქოს წაშლილი იყვნენ, ამიტომ ხაზები, რომლებსაც მხოლოდ ისინი ფარავდნენ, ითვლება დაუფარავად.
- **სხვა შარდების ტესტები**, როდესაც თქვენ [ყოფთ ტესტებს შარდებად](#sharded-runs).

## წარმადობაზე გავლენა {#performance-impact}

JaCoCo ინსტრუმენტებს კლასებს მაშინ, როდესაც სატესტო JVM ტვირთავს მათ, ამიტომ თქვენი კომპილირებული კლასები და კომპილაციის ამოცანების ბილდის ქეშის ჩანაწერები უცვლელი რჩება, მიუხედავად იმისა, ჩართულია დაფარვა თუ არა. ამოცანები, რომლებიც კითხულობენ ყველა დამოკიდებულების კონფიგურაციას, მაგალითად SBOM გენერატორები, ასევე ხედავენ JaCoCo-ს აგენტს, ამიტომ მათი გამომავალი მონაცემები იცვლება, როდესაც ჩართავთ დაფარვას. ტესტები ოდნავ ნელა სრულდება და პლაგინი კითხულობს JaCoCo-ს მონაცემებს ტესტების ამოცანების დასრულების შემდეგ. ტესტების ამოცანებს ჩართული და გამორთული დაფარვით აქვთ ცალკეული ბილდის ქეშის ჩანაწერები, ამიტომ პირველი გაშვება ჩართული დაფარვით ასრულებს ტესტებს მაშინაც კი, თუ მათი შედეგები დაფარვის გარეშე ქეშირებულია.

## შეზღუდვები {#limitations}

- **იზოლირებული პროექტები და კონფიგურაცია მოთხოვნისას.** ასეთი ბილდები არ აკონფიგურირებენ ყველა პროექტს, ამიტომ პლაგინს არ შეუძლია დაადგინოს, რომელი პროექტების ტესტები დატოვა გაშვებამ გარეთ, და ზოგიერთი პროექტის ტესტების გაშვება ითვლება სრულად.
- **არ არის დაფარვა ფორკებიდან გახსნილი პულ-რეკვესტებიდან.** დაფარვა აიტვირთება მხოლოდ იმ გაშვებების მიერ, რომლებიც ავთენტიკაციას გადიან Tuist-თან, და CI ჩვეულებრივ ფარავს საიდუმლოებებს და იდენტობის ტოკენებს ფორკებიდან გახსნილი პულ-რეკვესტებისგან.

## დაფარვის მოთხოვნა {#querying}

დაშბორდის **კოდის დაფარვა** გვერდი აჩვენებს თითოეული კომიტის მაჩვენებელს, მის მოდულებს და ფაილებს, იმ ხაზებით, რომლებიც თითოეულმა გაშვებამ დაფარა. იგივე მონაცემები ხელმისაწვდომია აგენტებისთვის <.localized_link href="/guides/features/agentic-coding/mcp">Model Context Protocol სერვერის</.localized_link> მეშვეობით.
