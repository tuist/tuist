# Rust-ის კოდის დაფარვა {#rust-code-coverage}

კოდის დაფარვა გაჩვენებთ, თქვენი ტესტების მიერ შესრულებულ კოდის ხაზებს. Tuist ზომავს ხაზოვან დაფარვას ყოველი `cargo test` გაშვებისთვის LLVM-ის წყაროზე დაფუძნებული დაფარვის გამოყენებით და აერთიანებს კომიტის გაშვებებს ერთ რიცხვად პროექტის, თითოეული პაკეტისა და ფაილისთვის. დაშბორდის **კოდის დაფარვის** გვერდი აჩვენებს მას კომიტის მიხედვით და როგორც ტენდენციას თითოეული ბრენჩისთვის.

> [!IMPORTANT]
> **მოთხოვნები**
>
> - მიჰყევით <.localized_link href="/guides/get-started/rust-project">Rust-ის პროექტის დაყენებას</.localized_link>
> - თქვენი Rust-ის ინსტრუმენტების ჯაჭვის LLVM-ის ინსტრუმენტები (`llvm-tools`). Tuist აყენებს მათ rustup-ის მიერ მართულ ინსტრუმენტების ჯაჭვში.
> - თქვენი პროექტი Git-ის რეპოზიტორიაში

## დაყენება {#setup}

### ჩართეთ დაფარვა {#turn-coverage-on}

დაამატეთ ეს სამუშაო სივრცის ძირეულ `Cargo.toml`-ში:

```toml
[workspace.metadata.tuist.test_insights.coverage]
upload = true
```

თუ Tuist-ს აკონფიგურირებთ `tuist.toml`-ში, დაამატეთ იქ `[test_insights.coverage]` პარამეტრით `upload = true`.

შემდეგ გაუშვით ტესტები ჩვეულებრივად:

```sh
tuist cargo test --workspace
```

Tuist აწყობს თქვენი რეპოზიტორიის კრეიტებს `-C instrument-coverage` ფლაგით, ასრულებს ტესტებს და ატვირთავს მათ დაფარვას გაშვების ტესტების შედეგებთან ერთად. თქვენი ტესტების გამოსავალი და გასვლის კოდი არ იცვლება. ერთი გაშვებისთვის პარამეტრის გადასაწერად, დააყენეთ `TUIST_COVERAGE_UPLOAD=1` ან `TUIST_COVERAGE_UPLOAD=0`.

დაფარვა ეყრდნობა Git-ის ისტორიას, რომელსაც Tuist ტვირთავს ყოველ გაშვებასთან ერთად, რაც განათავსებს კომიტს მის ბრენჩზე. Git-ის რეპოზიტორიის გარეთ გაშვება ტვირთავს ტესტების შედეგებს, მაგრამ არა დაფარვას.

### დაშლილი გაშვებები {#sharded-runs}

როდესაც <.localized_link href="/guides/features/test-sharding/rust">ყოფთ თქვენს ტესტებს</.localized_link>, ყოველი შარდი, რომელიც გაშვებულია ჩართული დაფარვით, აცხობს თავისი სამიზნეების დაფარვას და Tuist აერთიანებს გაშვების შარდებს ერთ რიცხვად. შარდი მიზანმიმართულად ასრულებს საიტის ნაწილს, ამიტომ ის არ ხდის კომიტის დაფარვას არასრულყოფილს.

### დაასრულეთ ყოველი კომიტი CI-ზე {#complete-each-commit}

კომიტის დაფარვა ხშირად მოდის რამდენიმე სამუშაოდან: ერთი შარდის ან ფუნქციების ნაკრების მიხედვით. Tuist-მა არ იცის, როდის აღმოაჩინა ბოლომ მათგანმა, ამიტომ უთხარით მას. როდესაც კომიტის ყოველი ტესტის სამუშაო დასრულდება, გაუშვით ეს სამუშაოში, რომელიც დამოკიდებულია მათ ყველაზე:

```sh
tuist cargo coverage-complete
```

ბრძანება კითხულობს კომიტს ჩეკაუტიდან, ან იმას, რომელსაც თქვენი CI პროვაიდერი აცხობს pull request-ზე; გადაეცით `--commit <sha>` სხვის დასახელებლად. სანამ კომიტი არ დასრულდება, მისი დაფარვა ჩანს როგორც **მიმდინარე** და არ შედის მისი ბრენჩის ტენდენციაში.

## როგორ მუშაობს {#how-it-works}

### რას ზომავს Tuist {#what-tuist-measures}

- **პაკეტები.** ყოველი Cargo პაკეტი არის სამიზნე დაშბორდზე, თავისი დაფარვით.
- **მხოლოდ პროდუქტის კოდი.** ინტეგრაციის ტესტები, ბენჩმარკები და მაგალითები (დირექტორიები `tests/`, `benches/` და `examples/`, და ამ ტიპის სამიზნეები) არის ტესტის კოდი. Tuist ინახავს მათ, მაგრამ ტოვებს მათ ყოველი რიცხვის გარეთ. ერთეულოვანი ტესტები `#[cfg(test)]` მოდულში არის მათი წყაროს ფაილის ნაწილი, ამიტომ მათი ხაზები ითვლება მასთან ერთად, როგორც `cargo llvm-cov`-ში.
- **ფუნქციები.** ყოველი ხაზი ეკუთვნის ფუნქციას, რომელიც იწყება მასთან ყველაზე ახლოს ზემოთ. ზოგადი ფუნქცია ითვლება ერთხელ, რამდენივე ტიპითაც არ უნდა იყოს ის ინსტანცირებული.
- **Doctests** გაშვებულია ჩვეულებრივად, მაგრამ არ იზომება.

Tuist ასევე იწერს, თუ რომელი კოდი შეასრულა ყოველმა ტესტის ბინარულმა ფაილმა, მოგვიანებით დაფარვაზე დაფუძნებული ტესტის შერჩევისთვის. `cargo test` ასრულებს ბინარული ფაილის ტესტებს ერთ პროცესში, ამიტომ ეს ჩანაწერი ეკუთვნის ბინარულ ფაილს მთლიანად, არა მის ინდივიდუალურ ტესტებს.

### გამოტოვებული ტესტები {#skipped-tests}

როდესაც გაშვების საკუთარი არგუმენტები ტოვებს ტესტებს გარეთ, როგორიცაა ტესტის სახელის ფილტრი, `--skip`, `--ignored`, `-p`, `--exclude`, `--lib` ან `--test`, კომიტის დაფარვა არის **არასრული**, თუ არ გაშვებულა კომიტის სხვა გაშვება, რომელმაც არაფერი დატოვა გარეთ. შეცდომა, რომელიც აჩერებს `cargo test`-ს სანამ ყოველი ტესტის ბინარული ფაილი გაშვებული იქნება, აქვს იგივე ეფექტი. დაამატეთ `--no-fail-fast` დარჩენილი ბინარული ფაილების გასაგრძელებლად.

ზოგიერთი ტესტი მიზანმიმართულად არის გამოტოვებული და არ ხდის კომიტს არასრულს:

- **ტესტები, რომლებსაც <.localized_link href="/guides/features/test-insights/flaky-tests/rust">კარანტინი</.localized_link> ტოვებს.** ისინი გამოტოვებულია, როგორც თუ ისინი წაშლილი იყვნენ, ამიტომ ხაზები, რომლებიც მხოლოდ მათ დაფარეს, ითვლება დაუფარავად.
- **სხვა შარდების სამიზნეები**, როდესაც ყოფთ თქვენს ტესტებს.
- **იგნორირებული ტესტები** (`#[ignore]`), რომლებიც არ გაშვებულია ნაგულისხმევად.

### სრული და არასრული კომიტები {#commit-status}

ყოველ კომიტს დაშბორდზე აქვს სტატუსი:

| სტატუსი | მნიშვნელობა |
| --- | --- |
| მიმდინარე | გაშვებებმა აღმოაჩინეს დაფარვა, მაგრამ `tuist cargo coverage-complete` არ გაშვებულა კომიტისთვის ჯერ. |
| სრული | კომიტის გაშვებების ყოველი ტესტი გაშვებული იყო, ან მიზანმიმართულად იყო გამოტოვებული. |
| არასრული | ზოგიერთი დაფარვის განსაზღვრა ვერ მოხერხდა, ამიტომ მაჩვენებელი წარმოადგენს ქვედა ზღვარს. |
| არ გაზომილა | არცერთმა გაშვებამ არ აღმოაჩინა დაფარვა კომიტისთვის. |

ტრენდი შეტყოს მხოლოდ სრულ კომიტებს.

## წარმადობაზე გავლენა {#performance-impact}

ინსტრუმენტული კოდი ოდნავ ნელა მუშაობს. Tuist ინსტრუმენტებს მხოლოდ თქვენი რეპოზიტორიის კრეიტებს: დამოკიდებულებები იწყება ზუსტად ისე, როგორც ჩვეულებრივ ბილდებში და გრძელდება ქეშიდან მიღება. Tuist ინახავს თქვენი საკუთარი კრეიტების ორივე ვარიანტს სამიზნე დირექტორიაში, ამიტომ გაშვებებს შორის გადასვლა დაფარვით და მის გარეშე არ ახდენს მათ ხელახლა აწყობას, თუ მათი კოდი არ შეიცვალა.

## შეზღუდვები {#limitations}

- **მორგებული `rustc-wrapper` სამიზნე-სპეციფიკური `rustflags`-ით.** როდესაც თქვენი პროექტი აყენებს საკუთარ `rustc-wrapper`-ს, Tuist უმატებს `-C instrument-coverage`-ს Cargo-ს `build.rustflags`-ს ნაცვლად. `target.<triple>.rustflags` ჩანაწერი Cargo-ს კონფიგურაციის ფაილში ცვლის მათ, ამიტომ დაამატეთ დროშა იქ თავად. გაშვება, რომლის ტესტებმაც არ დაწერეს დაფარვა, ამბობს ასე.
- **კონფიგურირებული სამიზნე გამშვებები.** Tuist აწყებს ტესტის ბინარულ ფაილებს საკუთარი გამშვებლით. `target.<triple>.runner` Cargo-ს კონფიგურაციის ფაილში იკავებს მის ადგილს: გაშვების დაფარვა მაინც აიტვირთება, მაგრამ Tuist-ს არ შეუძლია თქვას, რომელმა ტესტის ბინარულმა ფაილმა რა შეასრულა. გამშვებელი, რომელიც დაყენებულია `CARGO_TARGET_<TRIPLE>_RUNNER` გარემოს ცვლადით, განაგრძობს მუშაობას.
- **არ არის დაფარვა პულ-რეკვესტებიდან ფორკებიდან.** დაფარვა აიტვირთება მხოლოდ იმ გაშვებების მიერ, რომლებიც ავთენტიკაციას ავლებენ Tuist-თან, და CI ჩვეულებრივ უკავებს საიდუმლოებს და იდენტობის ტოკენებს პულ-რეკვესტებს, რომლებიც გაიხსნა ფორკებიდან.

## დაფარვის მოთხოვნა {#querying}

დაშბორდის **კოდის დაფარვა** გვერდი აჩვენებს თითოეული კომიტის მაჩვენებელს, მის პაკეტებს და ფაილებს, თითოეული ფაილის ფუნქციებით. იგივე მონაცემები ხელმისაწვდომია აგენტებისთვის <.localized_link href="/guides/features/agentic-coding/mcp">Model Context Protocol სერვერის</.localized_link> მეშვეობით.
