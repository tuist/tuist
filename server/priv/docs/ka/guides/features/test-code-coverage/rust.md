# Rust-ის კოდის დაფარვა {#rust-code-coverage}

კოდის დაფარვა გაჩვენებთ, თქვენი ტესტების მიერ შესრულებულ კოდის ხაზებს. Tuist ზომავს თითოეული `cargo test` გაშვების ხაზოვან დაფარვას LLVM-ის წყაროზე დაფუძნებული ინსტრუმენტებით და აერთიანებს კომიტის ყველა გაშვებას ერთ მაჩვენებლად — პროექტის, თითოეული პაკეტისა და ფაილისთვის. დაშბორდის **Code Coverage** გვერდი აჩვენებს მას კომიტების მიხედვით და როგორც ტენდენციას თითოეული ბრენჩისთვის.

> [!IMPORTANT]
> **მოთხოვნები**
>
> - მიჰყევით <.localized_link href="/guides/get-started/rust-project">Rust-ის პროექტის კონფიგურაციას</.localized_link>
> - თქვენი Rust-ის ინსტრუმენტების ნაკრების LLVM-ის ინსტრუმენტები (`llvm-tools`). Tuist ამონტაჟებს მათ rustup-ის მიერ მართულ ინსტრუმენტების ნაკრებში.
> - თქვენი პროექტი Git-ის რეპოზიტორიაში

## კონფიგურაცია {#setup}

### დაფარვის ჩართვა {#turn-coverage-on}

დაამატეთ ეს სამუშაო სივრცის ძირითად `Cargo.toml`-ში:

```toml
[workspace.metadata.tuist.test_insights.coverage]
upload = true
```

თუ Tuist-ს `tuist.toml`-ში აკონფიგურებთ, იქ დაამატეთ `[test_insights.coverage]` პარამეტრით `upload = true`.

შემდეგ გაუშვით თქვენი ტესტები ჩვეულებრივად:

```sh
tuist cargo test --workspace
```

Tuist აგებს თქვენი რეპოზიტორიის კრეიტებს `-C instrument-coverage` ფლაგით, ასრულებს ტესტებს და ატვირთავს მათ დაფარვას გაშვების ტესტების შედეგებთან ერთად. თქვენი ტესტების გამოტანა და გამოსვლის კოდი არ იცვლება. ერთი გაშვებისთვის პარამეტრის გადასაწერად, დააყენეთ `TUIST_COVERAGE_UPLOAD=1` ან `TUIST_COVERAGE_UPLOAD=0`.

დაფარვა ეყრდნობა Git-ის ისტორიას, რომელსაც Tuist ტვირთავს ყოველი გაშვებისას, რაც კომიტს მის ბრენჩზე ათავსებს. Git-ის რეპოზიტორიის გარეთ გაშვება ტვირთავს ტესტების შედეგებს, მაგრამ არა დაფარვას.

### დაშლილი გაშვებები {#sharded-runs}

როდესაც <.localized_link href="/guides/features/test-sharding/rust">ტესტებს ნაწილებად ყოფთ</.localized_link>, ყოველი ნაწილი, რომელიც ჩართული დაფარვით მუშაობს, აგზავნის საკუთარი სამიზნეების დაფარვას და Tuist აერთიანებს გაშვების ნაწილებს ერთ მაჩვენებლად. ნაწილი განზრახ ასრულებს ტესტების ნაკრების ნაწილს, ამიტომ ის არ ხდის კომიტის დაფარვას არასრულყოფილს.

### CI-ზე ყოველი კომიტის დასრულება {#complete-each-commit}

კომიტის დაფარვა ხშირად რამდენიმე სამუშაოსგან მოდის: ერთი ნაწილის ან ფუნქციების ნაკრებისთვის. Tuist ვერ განსაზღვრავს, როდის აგზავნის ბოლო მათგან მონაცემებს, ამიტომ უნდა მიუთითოთ. როდესაც კომიტის ყველა ტესტის სამუშაო დასრულდება, გაუშვით ეს სამუშაოში, რომელიც დამოკიდებულია მათ ყველაზე:

```sh
tuist cargo coverage-complete
```

ბრძანება კითხულობს კომიტს შემოწმების `HEAD`-დან, ანუ იმ კომიტს, რომელზეც თქვენი ტესტები გაშვებული იყო; სხვა კომიტის მითითებისთვის გადაეცით `--commit <sha>`. სანამ კომიტი არ დასრულდება, მისი დაფარვა ჩანს როგორც **მიმდინარე** და არ შედის ბრენჩის ტენდენციაში.

## როგორ მუშაობს {#how-it-works}

### რას ზომავს Tuist {#what-tuist-measures}

- **პაკეტები.** ყოველი Cargo პაკეტი არის სამიზნე დაშბორდზე, საკუთარი დაფარვით.
- **მხოლოდ პროდუქციის კოდი.** ინტეგრაციის ტესტები, ბენჩმარკები და მაგალითები (`tests/`, `benches/` და `examples/` დირექტორიები და ამ ტიპის სამიზნეები) არის სატესტო კოდი. Tuist ინახავს მათ, მაგრამ არ შეჰყავს მაჩვენებლებში. `#[cfg(test)]` მოდულში არსებული ერთეულოვანი ტესტები მათი წყაროს ფაილის ნაწილია, ამიტომ მათი ხაზები ითვლება მასთან ერთად, როგორც `cargo llvm-cov`-ში.
- **ფუნქციები.** ყოველი ხაზი ეკუთვნის ფუნქციას, რომელიც მასზე უახლოეს ზემოთ იწყება. ზოგადი ფუნქცია ერთხელ ითვლება, მიუხედავად იმისა, თუ რამდენი ტიპით იქნა ის ინსტანცირებული.
- **Doctests** ჩვეულებრივად მუშაობენ, მაგრამ არ იზომებიან.

Tuist ასევე აღრიცხავს, თუ რომელი კოდი შეასრულა თითოეულმა სატესტო ბინარმა, მოგვიანებით დაფარვაზე დაფუძნებული ტესტების შერჩევისთვის. `cargo test` ასრულებს ბინარის ტესტებს ერთ პროცესში, ამიტომ ეს ჩანაწერი ეკუთვნის ბინარს მთლიანად და არა მის ცალკეულ ტესტებს.

### გამოტოვებული ტესტები {#skipped-tests}

როდესაც გაშვების არგუმენტები ტოვებენ ტესტებს გარეთ, მაგალითად, ტესტის სახელის ფილტრი, `--skip`, `--ignored`, `-p`, `--exclude`, `--lib` ან `--test`, კომიტის დაფარვა არის **არასრული**, თუ არ გაშვებულა კომიტის სხვა გაშვება, რომელმაც არაფერი გამოტოვა. შეცდომა, რომელიც აჩერებს `cargo test`-ს სანამ ყველა სატესტო ბინარი გაშვებული იქნება, იგივე ეფექტს იწვევს. დაამატეთ `--no-fail-fast` დარჩენილი ბინარების გასაგრძელებლად.

ზოგიერთი ტესტი განზრახ არის გამოტოვებული და არ ხდის კომიტს არასრულს:

- **ტესტები, რომლებსაც <.localized_link href="/guides/features/test-insights/flaky-tests/rust">კარანტინი</.localized_link> ტოვებს.** ისინი გამოტოვებულია, თითქოს წაშლილი იყოს, ამიტომ ხაზები, რომლებიც მხოლოდ მათ ფარავდა, ითვლება დაუფარავად.
- **სხვა ნაწილების სამიზნეები**, როდესაც ტესტებს ნაწილებად ყოფთ.
- **იგნორირებული ტესტები** (`#[ignore]`), რომლებიც ნაგულისხმევად არ მუშაობენ.

### სრული და არასრული კომიტები {#commit-status}

დაშბორდზე ყოველ კომიტს აქვს სტატუსი:

| სტატუსი | მნიშვნელობა |
| --- | --- |
| მიმდინარე | გაშვებებმა ანგარიში გაუგზავნეს დაფარვას, მაგრამ `tuist cargo coverage-complete` ჯერ არ გაშვებულა კომიტისთვის. |
| სრული | კომიტის გაშვებების ყოველი ტესტი შესრულდა ან განზრახ იქნა გამოტოვებული. |
| არასრული | ზოგიერთი დაფარვა ვერ განისაზღვრა, ამიტომ მაჩვენებელი წარმოადგენს ქვედა ზღვარს. |
| არ არის გაზომილი | არცერთმა გაშვებამ არ ანგარიში კომიტის დაფარვის შესახებ. |

ბრენჩის ტრენდი მოიცავს მხოლოდ სრულ კომიტებს.

## წარმადობაზე გავლენა {#performance-impact}

ინსტრუმენტული კოდი ოდნავ ნელა მუშაობს. Tuist ინსტრუმენტებს მხოლოდ თქვენი რეპოზიტორიის კრეიტებს: დამოკიდებულებები იგივენაირად აშენდება, როგორც ჩვეულებრივი ბილდების დროს და კეშიდან მოდის. Tuist ინახავს თქვენი საკუთარი კრეიტების ორივე ვარიანტს target დირექტორიაში, ამიტომ დაფარვით და უდაფარვოდ გაშვებებს შორის გადართვა არ იწვევს მათ ხელახლა აწყობას, თუ კოდი არ შეცვლილა.

## შეზღუდვები {#limitations}

- **მორგებული `rustc-wrapper` სამიზნე-სპეციფიკური `rustflags`-ით.** როდესაც თქვენი პროექტი აყენებს საკუთარ `rustc-wrapper`-ს, Tuist ნაცვლად ამისა Cargo-ს `build.rustflags`-ში ამატებს `-C instrument-coverage`-ს. Cargo-ს კონფიგურაციის ფაილში `target.<triple>.rustflags` ჩანაწერი ცვლის მათ, ამიტომ დაამატეთ ეს ფლაგი თავად. გაშვება, რომლის ტესტებმაც დაფარვა არ ჩაწერეს, ამას აღნიშნავს.
- **კონფიგურირებული სამიზნე რანერები.** Tuist სატესტო ბინარებს საკუთარი რანერის მეშვეობით იწყებს. Cargo-ს კონფიგურაციის ფაილში `target.<triple>.runner` იკავებს მის ადგილს: გაშვების დაფარვა ისევ იტვირთება, მაგრამ Tuist ვერ განსაზღვრავს, რომელმა სატესტო ბინარმა რა შეასრულა. რანერი, რომელიც დაყენებულია `CARGO_TARGET_<TRIPLE>_RUNNER` გარემოს ცვლადის მეშვეობით, განაგრძობს მუშაობას.
- **დაფარვა არ არის ხელმისაწვდომი fork-ებიდან გახსნილი pull request-ებისთვის.** დაფარვა იტვირთება მხოლოდ იმ გაშვებების მიერ, რომლებიც ავთენტიკაციას გადიან Tuist-თან, ხოლო CI ჩვეულებრივ კრძალავს საიდუმლოებებსა და იდენტობის ტოკენებს fork-ებიდან გახსნილი pull request-ებისთვის.

## დაფარვის მოთხოვნა {#querying}

დაშბორდის **კოდის დაფარვა** გვერდი აჩვენებს თითოეული კომიტის მაჩვენებელს, მის პაკეტებსა და ფაილებს, თითოეული ფაილის ფუნქციებით. იგივე მონაცემები ხელმისაწვდომია აგენტებისთვის <.localized_link href="/guides/features/agentic-coding/mcp">Model Context Protocol სერვერის</.localized_link> მეშვეობით.
