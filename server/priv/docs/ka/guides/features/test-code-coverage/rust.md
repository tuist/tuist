# Rust-ის კოდის დაფარვა {#rust-code-coverage}

კოდის დაფარვა გიჩვენებთ, თქვენი ტესტების მიერ შესრულებულ კოდის სტრიქონებს. Tuist ზომავს ხაზოვან დაფარვას ყოველი `cargo test` გაშვებისას LLVM-ის წყაროზე დაფუძნებული დაფარვის გამოყენებით და აერთიანებს კომიტის გაშვებებს ერთ მაჩვენებლად პროექტის, თითოეული პაკეტისა და ფაილისთვის. დაფის **Code Coverage** გვერდი აჩვენებს მას კომიტის მიხედვით და როგორც ტრენდს თითოეული ბრენჩისთვის.

> [!IMPORTANT]
> **მოთხოვნები**
>
> - მიჰყევით <.localized_link href="/guides/get-started/rust-project">Rust-ის პროექტის კონფიგურაციას</.localized_link>
> - თქვენი Rust-ის ინსტრუმენტების ჯაჭვის LLVM ინსტრუმენტები (`llvm-tools`). Tuist ამონტაჟებს მათ rustup-ის მიერ მართულ ინსტრუმენტების ჯაჭვში.
> - თქვენი პროექტი Git რეპოზიტორიაში

## კონფიგურაცია {#setup}

### დაფარვის ჩართვა {#turn-coverage-on}

დაამატეთ ეს სამუშაო სივრცის ძირითად `Cargo.toml` ფაილში:

```toml
[workspace.metadata.tuist.test_insights.coverage]
upload = true
```

თუ Tuist-ს კონფიგურაციას `tuist.toml`-ში აკეთებთ, იქ დაამატეთ `[test_insights.coverage]` პარამეტრით `upload = true`.

შემდეგ გაუშვით ტესტები ჩვეულებრივად:

```sh
tuist cargo test --workspace
```

Tuist აწყობს თქვენი რეპოზიტორიის კრეიტებს `-C instrument-coverage` ფლაგით, უშვებს ტესტებს და ატვირთავს მათ დაფარვას გაშვების ტესტის შედეგებთან ერთად. თქვენი ტესტების გამომავალი მონაცემები და გასვლის კოდი არ იცვლება. ერთი გაშვებისთვის პარამეტრის გადასაწერად, დააყენეთ `TUIST_COVERAGE_UPLOAD=1` ან `TUIST_COVERAGE_UPLOAD=0`.

დაფარვა ეყრდნობა Git ისტორიას, რომელსაც Tuist ტვირთავს ყოველი გაშვებისას, რომელიც აგროვებს მას, რაც კომიტს ათავსებს მის ბრენჩზე. Git რეპოზიტორიის გარეთ გაშვება ტვირთავს ტესტის შედეგებს, მაგრამ არა დაფარვას.

### დაყოფილი გაშვებები {#sharded-runs}

როდესაც <.localized_link href="/guides/features/test-sharding/rust">ტესტებს ყოფთ ნაწილებად</.localized_link>, ყოველი ნაწილი, რომელიც გაშვებულია ჩართული დაფარვით, ანგარიშდება საკუთარი სამიზნეების დაფარვას და Tuist აერთიანებს გაშვების ნაწილებს ერთ მაჩვენებლად. ნაწილი განზრახ უშვებს ტესტების ნაკრების ნაწილს, ამიტომ ის არ ხდის კომიტის დაფარვას არასრულყოფილს.

### CI-ზე ყოველი კომიტის დასრულება {#complete-each-commit}

კომიტის დაფარვა ხშირად მოდის რამდენიმე სამუშაოდან: ერთი ნაწილის ან ფუნქციების ნაკრების მიხედვით. Tuist-მა არ იცის, როდის ანგარიშდება ბოლო მათგანი, ამიტომ უნდა აცნობოთ მას. როდესაც კომიტის ყოველი ტესტის სამუშაო დასრულდება, გაუშვით ეს სამუშაოში, რომელიც დამოკიდებულია ყველა მათგანზე:

```sh
tuist cargo coverage-complete
```

ბრძანება კითხულობს კომიტს ჩეკაუტის `HEAD`-დან, კომიტს, რომელზეც თქვენი ტესტები გაშვებული იყო; გამოიყენეთ `--commit <sha>` სხვა კომიტის მითითებისთვის. სანამ კომიტი არ დასრულდება, მისი დაფარვა ჩანს როგორც **In progress** და არ შედის ბრენჩის ტრენდში.

## როგორ მუშაობს {#how-it-works}

### რას ზომავს Tuist {#what-tuist-measures}

- **პაკეტები.** ყოველი Cargo პაკეტი არის სამიზნე დაფაზე, საკუთარი დაფარვით.
- **მხოლოდ პროდუქციის კოდი.** ინტეგრაციის ტესტები, ბენჩმარკები და მაგალითები (დირექტორიები `tests/`, `benches/` და `examples/`, და ასეთი ტიპის სამიზნეები) არის ტესტის კოდი. Tuist ინახავს მათ, მაგრამ არ შეაქვს მაჩვენებლებში. ერთეულოვანი ტესტები `#[cfg(test)]` მოდულში არის მათი წყაროს ფაილის ნაწილი, ამიტომ მათი სტრიქონები ითვლება მასთან ერთად, როგორც `cargo llvm-cov`-ში.
- **ფუნქციები.** ყოველი სტრიქონი ეკუთვნის ფუნქციას, რომელიც მასზე ზემოთ იწყება. ზოგადი ფუნქცია ითვლება ერთხელ, რამდენივე ტიპითაც არ უნდა იყოს ის ინსტანცირებული.
- **Doctests** გაშვებულია ჩვეულებრივად, მაგრამ არ იზომება.

Tuist ასევე აღრიცხავს, თუ რომელი კოდი შეასრულა ყოველმა ტესტის ბინარულმა ფაილმა, მოგვიანებით დაფარვაზე დაფუძნებული ტესტის შერჩევისთვის. `cargo test` უშვებს ბინარული ფაილის ტესტებს ერთ პროცესში, ამიტომ ეს ჩანაწერი ეკუთვნის ბინარულ ფაილს მთლიანად, არა მის ცალკეულ ტესტებს.

### გამოტოვებული ტესტები {#skipped-tests}

როდესაც გაშვების საკუთარი არგუმენტები ტოვებს ტესტებს გარეთ, როგორიცაა ტესტის სახელის ფილტრი, `--skip`, `--ignored`, `-p`, `--exclude`, `--lib` ან `--test`, კომიტის დაფარვა არის **Incomplete**, თუ არ გაშვებულა კომიტის სხვა გაშვებაც, რომელმაც არაფერი გამოტოვა. შეცდომას, რომელიც აჩერებს `cargo test`-ს სანამ ყოველი ტესტის ბინარული ფაილი გაშვებული იქნება, აქვს იგივე ეფექტი. დაამატეთ `--no-fail-fast` დარჩენილი ბინარული ფაილების გაშვების გასაგრძელებლად.

ზოგიერთი ტესტი განზრახ არის გამოტოვებული და არ ხდის კომიტს არასრულყოფილს:

- **ტესტები, რომლებსაც <.localized_link href="/guides/features/test-insights/flaky-tests/rust">კარანტინი</.localized_link> ტოვებს.** ისინი გამოტოვებულია ისე, თითქოს წაშლილი იყოს, ამიტომ სტრიქონები, რომლებსაც მხოლოდ ისინი ფარავდნენ, ითვლება დაუფარავად.
- **სხვა ნაწილების სამიზნეები**, როდესაც ტესტებს ყოფთ ნაწილებად.
- **იგნორირებული ტესტები** (`#[ignore]`), რომლებიც ნაგულისხმევად არ გაშვებულია.

### სრული და არასრული კომიტები {#commit-status}

ყოველ კომიტს დაფაზე აქვს სტატუსი:

| სტატუსი | მნიშვნელობა |
| --- | --- |
| მიმდინარე | გაშვებებმა ანგარიშდა დაფარვა, მაგრამ `tuist cargo coverage-complete` ჯერ არ გაშვებულა კომიტისთვის. |
| სრული | კომიტის გაშვებების ყოველი ტესტი გაშვებული იყო, ან განზრახ იყო გამოტოვებული. |
| არასრული | ზოგიერთი დაფარვა ვერ განისაზღვრა, ამიტომ მაჩვენებელი წარმოადგენს ქვედა ზღვარს. |
| არ გაზომილა | არც ერთმა გაშვებამ არ აანგარიშა კომიტის დაფარვა. |

ბრენჩის ტრენდი მოიცავს მხოლოდ სრულ კომიტებს.

## წარმადობაზე გავლენა {#performance-impact}

ინსტრუმენტირებული კოდი ოდნავ უფრო ნელა მუშაობს. Tuist ინსტრუმენტაციას უკეთებს მხოლოდ თქვენი რეპოზიტორიის კრეიტებს: დამოკიდებულებები იბილდება ზუსტად ისე, როგორც ჩვეულებრივი ბილდების დროს და კეშიდან აღებულია. Tuist ინახავს თქვენი საკუთარი კრეიტების ორივე ვარიანტს target დირექტორიაში, ამიტომ გადახვევა დაფარვის ჩართვით და გამორთვით გაშვებებს შორის არ იწვევს მათ ხელახლა აწყობას, თუ მათი კოდი არ შეცვლილა.

## შეზღუდვები {#limitations}

- **საკუთარი `rustc-wrapper` სამიზნე-სპეციფიკური `rustflags`-ით.** როდესაც თქვენი პროექტი აყენებს საკუთარ `rustc-wrapper`-ს, Tuist ნაცვლად ამისა Cargo-ს `build.rustflags`-ში ამატებს `-C instrument-coverage`-ს. Cargo-ს კონფიგურაციის ფაილში `target.<triple>.rustflags` ჩანაწერი ცვლის მათ, ამიტომ თავად დაამატეთ ეს ფლაგი იქ. გაშვება, რომლის ტესტებმაც არ ჩაწერეს დაფარვა, ამას აღნიშნავს.
- **კონფიგურირებული სამიზნე გამშვებები.** Tuist ტესტის ბინარულ ფაილებს აშვებს საკუთარი გამშვებლის მეშვეობით. Cargo-ს კონფიგურაციის ფაილში `target.<triple>.runner` იკავებს მის ადგილს: გაშვების დაფარვა მაინც აიტვირთება, მაგრამ Tuist ვერ განსაზღვრავს, რომელმა ტესტის ბინარულმა ფაილმა რა შეასრულა. გარემოს ცვლადის `CARGO_TARGET_<TRIPLE>_RUNNER` მეშვეობით დაყენებული გამშვებელი განაგრძობს მუშაობას.
- **დაფარვა არ არის ხელმისაწვდომი fork-ებიდან გაგზავნილი pull request-ებიდან.** დაფარვა აიტვირთება მხოლოდ იმ გაშვებების მიერ, რომლებიც ავთენტიფიცირდებიან Tuist-თან, ხოლო CI ჩვეულებრივ ფარავს საიდუმლოებებსა და იდენტობის ტოკენებს fork-ებიდან გახსნილი pull request-ებისთვის.

## დაფარვის მოთხოვნა {#querying}

დაფის **Code Coverage** გვერდი აჩვენებს თითოეული კომიტის მაჩვენებელს, მის პაკეტებსა და ფაილებს, თითოეული ფაილის შემცველი ფუნქციებით. იგივე მონაცემები ხელმისაწვდომია აგენტებისთვის <.localized_link href="/guides/features/agentic-coding/mcp">Model Context Protocol server</.localized_link>-ის მეშვეობით.
