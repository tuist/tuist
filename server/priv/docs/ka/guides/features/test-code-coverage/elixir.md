# Elixir-ის კოდის დაფარვა {#elixir-code-coverage}

კოდის დაფარვა გაჩვენებთ, თქვენი ტესტების მიერ შესრულებულ კოდის ხაზებს. Hex პაკეტი ატვირთავს ხაზოვანი დაფარვის მონაცემებს ყოველი `mix test --cover` გაშვებისთვის, ხოლო Tuist აჯამებს კომიტის გაშვებებს ერთ მაჩვენებლად პროექტის, თითოეული OTP აპლიკაციისა და თითოეული ფაილის მიხედვით. დაშბორდის **კოდის დაფარვა** გვერდი აჩვენებს მას კომიტების მიხედვით და როგორც ტრენდს თითოეული ბრენჩისთვის.

> [!IMPORTANT] REQUIREMENTS
> - დაასრულეთ <.localized_link href="/guides/get-started/elixir-project">Elixir-ის საერთო კონფიგურაცია</.localized_link>, რომელიც `mix test`-ს პაკეტის მეშვეობით ატარებს

## კონფიგურაცია {#setup}

### ტესტების გაშვება დაფარვით {#run-your-tests}

გადაეცით `--cover`, ისევე როგორც `mix test`-ს Tuist-ის გარეშე:

```sh
mix test --cover
```

პაკეტი ატვირთავს დაფარვას გაშვების ტესტის შედეგებთან ერთად. სუიტის დასრულებისას, ის ასევე ასრულებს იმას, რასაც Mix-ის დაფარვის ინსტრუმენტი აკეთებს, იმავე `test_coverage` პარამეტრებით კონფიგურირებული:

- **შეჯამება.** ის ბეჭდავს თითოეული მოდულის და ჯამურ დაფარვას. `summary: false` თიშავს მას.
- **ზღვარი.** ის აწყვეტინებს გაშვებას გამოსვლის სტატუსით 3, როდესაც ჯამური მაჩვენებელი ეცემა ზღვარზე ქვემოთ, რომელიც არის 90%, თუ სხვას არ მიუთითებთ:

```elixir
def project do
  [
    test_coverage: [summary: [threshold: 80]]
  ]
end
```

როგორც Mix-ში, ზღვარი ეკუთვნის შეჯამებას, ამიტომ `summary: false` თიშავს ორივეს. შეჯამების დაბეჭდვისთვის გაშვების შეწყვეტის გარეშე, დააყენეთ `threshold: 0`. მოდულები, რომლებიც ჩამოთვლილია `test_coverage: [ignore_modules: [...]]`-ში, გამოტოვებულია შეჯამებიდან და ატვირთვიდან.

Tuist აკონტროლებს დაფარვას კომიტების მიხედვით, ამიტომ მას სჭირდება თქვენი პროექტი Git რეპოზიტორიაში: გაშვება რეპოზიტორიის გარეთ ატვირთავს ტესტის შედეგებს, მაგრამ არა დაფარვას.

დაფარვა ეყრდნობა <.localized_link href="/guides/features/test-insights/elixir#git-history">Git-ის ისტორიას</.localized_link>, რომელსაც პაკეტი ატვირთავს და რომელიც ათავსებს კომიტს მის ბრენჩზე. უწყვეტი ინტეგრაციის გაშვებები ყოველთვის ატვირთავენ მას, ხოლო `--cover` გაშვებები ატვირთავენ მას ნებისმიერ მანქანაზე. `--cover`-ით, პაკეტი ასევე პოულობს, საიდანაც გადაიღო pull request-მა ბრენჩი: ის იღებს საბაზო ბრენჩს და აძლიერებს ზედაპირულ კლონს იმდენად, რამდენადაც საჭიროა. დააყენეთ `TUIST_GIT_UNSHALLOW_ENABLED=false`, რათა თავიდან აიცილოთ დაშორებულ რეპოზიტორიასთან დაკავშირება.

### დაყოფილი გაშვებები {#sharded-runs}

როდესაც <.localized_link href="/guides/features/test-sharding/elixir">ყოფთ თქვენს ტესტებს</.localized_link>, გაუშვით თითოეული ნაწილი `--cover`-ით:

```sh
MIX_ENV=test TUIST_SHARD_INDEX=0 mix tuist.test --cover
```

ახალ გამშვებზე, გამოიყენეთ bootstrap ბრძანება დაყოფის სახელმძღვანელოს <.localized_link href="/guides/features/test-sharding/elixir#test-phase">ტესტის ფაზიდან</.localized_link>, რომელიც ხელს უშლის Mix-ს ყველა დამოკიდებულების კომპილაციას მანამ, სანამ ნაწილი ჩამოტვირთავს მის ბილდს, და დაუმატეთ მას `--cover`.

ნაწილი ანგარიშგებს მხოლოდ საკუთარ დაფარვას და არ ამოწმებს ზღვარს, ვინაიდან ის ასრულებს სუიტის ნაწილს. Tuist აერთიანებს გაშვების ნაწილებს ერთ მაჩვენებლად.

თითოეული ნაწილი ამატებს დაფარვის მრიცხველებს ბილდს, რომელსაც ჩამოტვირთავს. ამის ერთხელ გასაკეთებლად, გადაეცით `--cover` ასევე ბილდის ფაზას:

```sh
MIX_ENV=test mix tuist.test.build --shard-max 5 --cover
```

გამორთეთ ის, როდესაც ინარჩუნებთ ბილდის დირექტორიას პაიპლაინის გაშვებებს შორის და ხელახლა იყენებთ მას გაშვებებში, რომლებიც არ აგროვებენ დაფარვას, რათა ეს ბილდი დარჩეს მრიცხველების გარეშე.

### დაასრულეთ თითოეული კომიტი CI-ზე {#complete-each-commit}

კომიტის დაფარვა ხშირად მოდის რამდენიმე სამუშაოდან: ერთი თითოეული ნაწილისთვის, მონაცემთა ბაზის ვერსიისთვის ან აპლიკაციისთვის. Tuist-ს არ შეუძლია განსაზღვროს, როდის მოახსენა ბოლომ მათგან, ამიტომ უთხარით მას. მას შემდეგ, რაც კომიტის ყველა ტესტის სამუშაო დასრულდება, გაუშვით ეს სამუშაოში, რომელიც დამოკიდებულია მათ ყველაზე:

```sh
MIX_ENV=test mix tuist.coverage.complete
```

ამოცანა კითხულობს კომიტს `GIT_COMMIT`-დან ან checkout-ის `HEAD`-დან; გადაეცით `--commit <sha>` სხვის დასახელებლად. სანამ კომიტი არ დასრულდება, მისი დაფარვა ჩანს როგორც **მიმდინარეობს** და რჩება მისი ბრენჩის ტრენდის გარეთ.

## როგორ მუშაობს {#how-it-works}

### ნატიური ხაზების მრიცხველები {#native-line-counters}

Mix-ის დაფარვის ინსტრუმენტი აკომპილირებს ყოველ მოდულს ხელახლა Erlang-ის `cover`-თვის ყოველი გაშვების დასაწყისში, რაც დიდ პროექტებზე ნელდება. პაკეტი ითვლის რანთაიმის ნატიური ხაზების მრიცხველებით. ის ხელახლა აკომპილირებს მხოლოდ იმ მოდულებს, რომლებიც კომპილაციამ დაწერა ბოლო გაშვების შემდეგ, გადაჰყავს რანთაიმი ამ მრიცხველებზე და კითხულობს მათ სუიტის დასრულებისას. Mix-ის დაფარვის ინსტრუმენტი გამოტოვებულია, მაგრამ მისი შეჯამება და ზღვარი შენარჩუნებულია.

პაკეტი გადადის Mix-ის დაფარვის ინსტრუმენტზე, იმავე ატვირთვით, შემდეგი შემთხვევებისთვის:

- umbrella პროექტის ფესვი. გაუშვით ტესტები თითოეული აპლიკაციის შიგნით ნატიურად დათვლისთვის.
- პროექტი, რომელიც აყენებს საკუთარ `test_coverage: [tool: ...]`-ს.
- რანთაიმი JIT-ის გარეშე, რომელსაც არ შეუძლია ნატიურად დათვლა.

### რას ზომავს Tuist {#what-tuist-measures}

- **აპლიკაციები.** თითოეული OTP აპლიკაცია არის სამიზნე დაშბორდზე, საკუთარი დაფარვით.
- **მხოლოდ პროდუქციის კოდი.** ფაილები თქვენი ტესტის გზებზე არის ტესტის კოდი. Tuist ინახავს მათ, მაგრამ გამოტოვებს ყოველი მაჩვენებლიდან.
- **ხაზები ფაილის მიხედვით.** ხაზი ითვლება ერთხელ ფაილის მიხედვით, მიუხედავად იმისა, თუ რამდენ მოდულს ეკუთვნის.
- **ფუნქციები.** თითოეული ხაზი ეკუთვნის ფუნქციას, რომლის წინადადებაც იწყება მასთან ყველაზე ახლოს ზემოთ. ფუნქციები, რომლებსაც კომპილატორი ან მაკრო ქმნის, როგორიცაა `__info__/1` ან `__schema__/1`, არ არის ჩამოთვლილი, მაგრამ მათი ხაზები მაინც ითვლება მათი ფაილისთვის.

ასე რომ, Tuist-ის მაჩვენებლები განსხვავდება Mix-ის საკუთარი დაფარვის ანგარიშისგან რამდენიმე გზით: ისინი გამოტოვებენ ტესტის კოდს და ითვლიან ხაზებს ფაილის მიხედვით და არა მოდულის მიხედვით. ნატიური დათვლა ასევე ხედავს კოდს, რომელიც მუშაობს თქვენი აპლიკაციის გაშვებისას, და გამოტოვებს ხაზებს, რომლებიც კომპილატორმა დაამტკიცა, რომ ვერასდროს შესრულდება, რასაც Mix-ის ინსტრუმენტი ანგარიშგებს როგორც არასდროს დაფარულს.

### გამოტოვებული ტესტები {#skipped-tests}

Tuist-ს არ შეუძლია გადაიტანოს იმ ტესტების დაფარვა, რომლებიც გაშვებამ გამოტოვა: პაკეტი აღრიცხავს, რა შეასრულა მთელმა გაშვებამ და არა ის, რა შეასრულა თითოეულმა ტესტმა. ასე რომ, როდესაც გაშვების საკუთარი არგუმენტები ტოვებენ ტესტებს გარეთ, `--only`-ით, `--exclude`-ით, `--failed`-ით, `--stale`-ით, `--name-pattern`-ით, `--max-failures`-ით, ან ტესტის ფაილებით ან ხაზებით, კომიტის დაფარვა არის **არასრული**, თუ არ გაშვებულა იმავე ვარიანტის გაშვება, რომელმაც არაფერი გამოტოვა. ორი გაშვება, რომლებიც თითო ტოვებენ ტესტებს გარეთ, როგორიცაა `--exclude slow` და `--only slow`, მაინც ხდიან კომიტს არასრულს, მიუხედავად იმისა, რომ ერთად მათ ყველა ტესტი გაუშვეს.

ზოგიერთი ტესტი განზრახ არის გამოტოვებული და არ ხდის კომიტს არასრულს:

- **თქვენი ტესტის დამხმარის გამონაკლისები.** ტესტები, რომლებსაც `ExUnit.start(exclude: [...])` ტოვებს გარეთ ნაგულისხმევად, არის თქვენი პროექტის არჩევანი, თუ რას ასრულებს მისი სუიტა ნაგულისხმევად, ამიტომ Tuist არ თვლის მათ დაკარგულად. გაუშვით ისინი სხვა სამუშაოში, `--include`-ით ან `--only`-ით, რათა დაუმატოთ მათი დაფარვა კომიტს.
- **კოდში გამოტოვებული ტესტები** `@tag :skip`-ით.
- **ტესტები, რომლებსაც <.localized_link href="/guides/features/test-insights/flaky-tests/elixir#quarantining">კარანტინი</.localized_link> ტოვებს.** ისინი გამოტოვებულია ისე, თითქოს წაშლილი იყვნენ, ამიტომ ხაზები, რომლებიც მხოლოდ მათ დაფარეს, ითვლება დაუფარავად.

| სტატუსი | მნიშვნელობა |

ბრენჩის ტრენდი მხოლოდ სრულ კომიტებს მოიცავს. კომიტი არასრულია, მაგალითად, როდესაც:

- ვარიანტის ყველა გაშვებამ საკუთარი არგუმენტებით ტესტები გამოტოვა.
- ვარიანტის ყველა გაშვებას აკლდა ზოგიერთი შარდი.
- ვარიანტის დაფარვა მიღებული იყო მხოლოდ CI გაშვებებიდან, სადაც ჩეკაუთს ჰქონდა დაუკომიტებილი ცვლილებები.

ვარიანტი არის ეტიკეტი, რომელსაც `--scheme`-ით გადასცემთ, მაგალითად, მონაცემთა ბაზის ვერსია. ეტიკეტის გარეშე გაშვებები ერთ ვარიანტად ითვლება. კომიტის მაჩვენებელი აერთიანებს ყველა გაშვებას, მაგრამ Tuist თითოეულ ვარიანტს სისრულისთვის ცალ-ცალკე ამოწმებს, ამიტომ თითოეულ ვარიანტს სჭირდება გაშვება, რომელიც არაფერს ტოვებს გარეთ.

## წარმადობაზე გავლენა {#performance-impact}

დაფარვის შეგროვება დამატებით ხარჯს ქმნის, ამიტომ `--cover`-ით გაშვებები უფრო მეტ დროს იღებს, ვიდრე მის გარეშე. პირველი გაშვება ხაზების მრიცხველებით თავიდან კომპილირებს თქვენს მოდულებს; შემდგომი გაშვებები მხოლოდ შეცვლილს აკომპილირებენ, ამიტომ მათი ღირებულება ბევრად ნაკლებია. დიდ პროექტებში ნატიური თვლა ასევე ბევრად უფრო სწრაფია, ვიდრე Mix-ის დაფარვის ინსტრუმენტი.

## შეზღუდვები {#limitations}

- **HTML ანგარიში არ არსებობს.** ნატიური თვლა არ წერს ანგარიშს `test_coverage: [output: ...]` დირექტორიაში და გაშვება აფრთხილებს, როდესაც ის მითითებულია. დაფის ფაილების გვერდები ნაცვლად ამისა აჩვენებს დაფარულ ხაზებს.
- **განმეორებითი გაშვებები არ ზრდიან დაფარვას.** <.localized_link href="/guides/features/test-insights/flaky-tests/elixir#test-retries">ტესტების განმეორებითი გაშვების</.localized_link> შემთხვევაში, დაფარვა პირველი მცდელობისაა. ამ მცდელობამ უკვე გაუშვა ჩავარდნილი ტესტები, ამიტომ დაკარგული ხაზები მხოლოდ ისინია, რომლებსაც არამდგრადი ტესტი აღწევს განმეორებით გაშვებაზე, მაგრამ არა პირველ მცდელობაზე.
- **ფორკებიდან გაგზავნილი პულ-რეკვესტებიდან დაფარვა არ მიიღება.** დაფარვა იტვირთება მხოლოდ იმ გაშვებების მიერ, რომლებიც Tuist-თან ავტორიზდებიან, ხოლო CI ჩვეულებრივ ფარავს საიდუმლოებსა და იდენტობის ტოკენებს ფორკებიდან გახსნილი პულ-რეკვესტებისთვის, ამიტომ ეს გაშვებები არ ატყობინებენ დაფარვას. შერწყმის შემდეგ, კომიტი თქვენს ბრენჩზე რბის კრედენციალებით და ჩვეულებრივად ატყობინებს თავის დაფარვას.

## დაფარვის მოთხოვნა {#querying}

დაფის **კოდის დაფარვის** გვერდი აჩვენებს თითოეული კომიტის მაჩვენებელს, მის აპლიკაციებსა და ფაილებს, იმ ხაზებით, რომლებიც თითოეულმა გაშვებამ დაფარა. იგივე მონაცემები ხელმისაწვდომია აგენტებისთვის <.localized_link href="/guides/features/agentic-coding/mcp">Model Context Protocol სერვერის</.localized_link> მეშვეობით.
