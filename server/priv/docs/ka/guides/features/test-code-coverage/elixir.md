# Elixir-ის კოდის დაფარვა {#elixir-code-coverage}

კოდის დაფარვა გაჩვენებთ, თქვენი ტესტების მიერ შესრულებულ კოდის ხაზებს. Hex პაკეტი ატვირთავს ხაზოვან დაფარვას ყოველი `mix test --cover` გაშვებისთვის, ხოლო Tuist აერთიანებს კომიტის გაშვებებს ერთ მაჩვენებლად პროექტის, თითოეული OTP აპლიკაციისა და თითოეული ფაილის მიხედვით. დაშბორდის **კოდის დაფარვის** გვერდი აჩვენებს მას კომიტების მიხედვით და როგორც ტენდენციას თითოეული ბრენჩისთვის.

> [!IMPORTANT]
> **მოთხოვნები**
>
> - დაასრულეთ <.localized_link href="/guides/get-started/elixir-project">Elixir-ის საერთო კონფიგურაცია</.localized_link>, რომელიც `mix test`-ს ატარებს პაკეტის მეშვეობით

## კონფიგურაცია {#setup}

### ტესტების გაშვება დაფარვით {#run-your-tests}

გადაეცით `--cover`, როგორც ეს `mix test`-ში კეთდება Tuist-ის გარეშე:

```sh
mix test --cover
```

პაკეტი ატვირთავს დაფარვას გაშვების ტესტების შედეგებთან ერთად. როდესაც ტესტების ნაკრები სრულდება, ის ასევე ასრულებს იმას, რასაც Mix-ის დაფარვის ინსტრუმენტი აკეთებს, იმავე `test_coverage` პარამეტრებით კონფიგურირებული:

- **შეჯამება.** ის ბეჭდავს თითოეული მოდულის და ჯამურ დაფარვას. `summary: false` თიშავს მას.
- **ზღვარი.** ის აფრუშებს გაშვებას გამოსვლის სტატუსით 3, როდესაც ჯამური მაჩვენებელი ეცემა ზღვარზე დაბლა, რომელიც არის 90%, თუ სხვა რამ არ არის მითითებული:

```elixir
def project do
  [
    test_coverage: [summary: [threshold: 80]]
  ]
end
```

როგორც Mix-ში, ზღვარი ეკუთვნის შეჯამებას, ამიტომ `summary: false` თიშავს ორივეს. შეჯამების დაბეჭდვისთვის გაშვების შეცდომის გარეშე, დააყენეთ `threshold: 0`. მოდულები, რომლებიც ჩამოთვლილია `test_coverage: [ignore_modules: [...]]`-ში, გამოტოვებულია შეჯამებიდან და ატვირთვიდან.

Tuist თვალყურს ადევნებს დაფარვას კომიტების მიხედვით, ამიტომ მას სჭირდება თქვენი პროექტი Git რეპოზიტორიაში: გაშვება მის გარეშე ატვირთავს ტესტების შედეგებს, მაგრამ არა დაფარვას.

დაფარვა ეყრდნობა <.localized_link href="/guides/features/test-insights/elixir#git-history">Git-ის ისტორიას</.localized_link>, რომელსაც პაკეტი ატვირთავს და რომელიც ათავსებს კომიტს მის ბრენჩზე. უწყვეტი ინტეგრაციის გაშვებები ყოველთვის ატვირთავენ მას, ხოლო `--cover` გაშვებები ატვირთავენ მას ნებისმიერ მანქანაზე. `--cover`-ით, პაკეტი ასევე პოულობს, საიდანაც გაიყო პულ-რეკვესტი: ის იღებს საბაზისო ბრენჩს და აფართოებს ზედაპირულ კლონს საჭირო მანძილზე. უწყვეტ ინტეგრაციაზე, ზედაპირული ჩექაუთიც ფართოვდება, ფაილების შინაარსის გარეშე, სანამ არ მიაღწევს იმ კომიტებს, რომლებიც Tuist-ს უკვე აქვს, ამიტომ კომიტი არასდროს აიტვირთება მისი მშობლის გარეშე. დააყენეთ `TUIST_GIT_UNSHALLOW_ENABLED=false`, რათა თავიდან აიცილოთ დაშორებულ რეპოზიტორიასთან დაკავშირება.

### ნაწილობრივი გაშვებები {#sharded-runs}

როდესაც <.localized_link href="/guides/features/test-sharding/elixir">ყოფთ ტესტებს</.localized_link>, გაუშვით თითოეული ნაწილი `--cover`-ით:

```sh
MIX_ENV=test TUIST_SHARD_INDEX=0 mix tuist.test --cover
```

ახალ გამშვებზე, გამოიყენეთ ბუტსტრაპის ბრძანება ნაწილობრივი გაშვების სახელმძღვanelodan <.localized_link href="/guides/features/test-sharding/elixir#test-phase">ტესტის ფაზა</.localized_link>, რომელიც ხელს უშლის Mix-ს ყოველი დამოკიდებულების კომპილაციას მანამ, სანამ ნაწილი ჩამოტვირთავს მის ბილდს, და დაამატეთ მას `--cover`.

ნაწილი ანგარიშგებს მხოლოდ საკუთარ დაფარვას და არ ამოწმებს ზღვარს, რადგან ის ასრულებს ნაკრების ნაწილს. Tuist აერთიანებს გაშვების ნაწილებს ერთ მაჩვენებლად.

თითოეული ნაწილი ამატებს დაფარვის მრიცხველებს ჩამოტვირთულ ბილდს. ამის ერთხელ გასაკეთებლად, გადაეცით `--cover` ასევე ბილდის ფაზას:

```sh
MIX_ENV=test mix tuist.test.build --shard-max 5 --cover
```

გამორთეთ ის, როდესაც ინარჩუნებთ ბილდის დირექტორიას პაიპლაინის გაშვებებს შორის და იყენებთ მას ისეთ გაშვებებში, რომლებიც არ აგროვებენ დაფარვას, რათა ბილდი დარჩეს მრიცხველების გარეშე.

### დაასრულეთ თითოეული კომიტი CI-ზე {#complete-each-commit}

კომიტის დაფარვა ხშირად მოდის რამდენიმე სამუშაოდან: ერთი ნაწილის, მონაცემთა ბაზის ვერსიის ან აპლიკაციის მიხედვით. Tuist-ს არ შეუძლია განსაზღვროს, როდის ანგარიშგებოდა ბოლო მათგანი, ამიტომ უთხარით მას. როდესაც კომიტის ყველა ტესტის სამუშაო დასრულდება, გაუშვით ეს სამუშაოში, რომელიც დამოკიდებულია ყველა მათგანზე:

```sh
MIX_ENV=test mix tuist.coverage.complete
```

ამოცანა კითხულობს კომიტს `GIT_COMMIT`-დან ან ჩექაუთის `HEAD`-დან; გადაეცით `--commit <sha>` სხვის დასახელებლად. სანამ კომიტი არ დასრულდება, მისი დაფარვა ჩანს, როგორც **მიმდინარე** და არ შედის მისი ბრენჩის ტენდენციაში.

## როგორ მუშაობს {#how-it-works}

### ნატიური ხაზოვანი მრიცხველები {#native-line-counters}

Mix-ის დაფარვის ინსტრუმენტი ხელახლა აკომპილირებს ყოველ მოდულს Erlang-ის `cover`-სთვის ყოველი გაშვების დასაწყისში, რაც დიდ პროექტებზე ნელდება. პაკეტი ითვლის რანთაიმის ნატიური ხაზოვანი მრიცხველებით. ის ხელახლა აკომპილირებს მხოლოდ იმ მოდულებს, რომლებიც ბოლო გაშვების შემდეგ დაიწერა, გადაჰყავს რანთაიმს ამ მრიცხველებზე და კითხულობს მათ, როდესაც ნაკრები სრულდება. Mix-ის დაფარვის ინსტრუმენტი გამოტოვებულია, მაგრამ მისი შეჯამება და ზღვარი შენარჩუნებულია.

პაკეტი გადადის Mix-ის დაფარვის ინსტრუმენტზე, იმავე ატვირთვით, შემდეგი შემთხვევებისთვის:

- umbrella პროექტის ფესვი. გაუშვით ტესტები თითოეულ აპლიკაციაში ნატიურად დათვლისთვის.
- პროექტი, რომელიც აყენებს საკუთარ `test_coverage: [tool: ...]`-ს.
- რანთაიმი JIT-ის გარეშე, რომელსაც არ შეუძლია ნატიურად დათვლა.

### რას ზომავს Tuist {#what-tuist-measures}

- **აპლიკაციები.** თითოეული OTP აპლიკაცია არის მიზანი დაშბორდზე, საკუთარი დაფარვით.
- **მხოლოდ პროდუქციის კოდი.** თქვენი ტესტების გზებზე მყოფი ფაილები არის ტესტის კოდი. Tuist ინახავს მათ, მაგრამ გამოტოვებს ყოველ მაჩვენებელში.
- **ხაზები ფაილის მიხედვით.** ხაზი ითვლება ერთხელ ფაილის მიხედვით, მიუხედავად იმისა, თუ რამდენ მოდულს ეკუთვნის.
- **ფუნქციები.** თითოეული ხაზი ეკუთვნის ფუნქციას, რომლის წინადადებაც ყველაზე ახლოს იწყება მის ზემოთ. ფუნქციები, რომლებსაც კომპილატორი ან მაკრო ქმნის, როგორიცაა `__info__/1` ან `__schema__/1`, არ არის ჩამოთვლილი, მაგრამ მათი ხაზები მაინც ითვლება მათი ფაილისთვის.

ამიტომ, Tuist-ის მაჩვენებლები განსხვავდება Mix-ის საკუთარი დაფარვის ანგარიშისგან რამდენიმე გზით: ისინი გამოტოვებენ ტესტის კოდს და ითვლიან ხაზებს ფაილის მიხედვით და არა მოდულის მიხედვით. ნატიური დათვლა ასევე ხედავს კოდს, რომელიც სრულდება თქვენი აპლიკაციის გაშვებისას, და გამოტოვებს ხაზებს, რომლებიც კომპილატორმა დაამტკიცა, რომ ვერასდროს შესრულდება, რასაც Mix-ის ინსტრუმენტი აღწერს, როგორც არასდროს დაფარულს.

### გამოტოვებული ტესტები {#skipped-tests}

Tuist-ს არ შეუძლია გადაიტანოს იმ ტესტების დაფარვა, რომლებიც გაშვებამ გამოტოვა: პაკეტი აღრიცხავს, რა შეასრულა მთლიანმა გაშვებამ და არა ის, რა შეასრულა თითოეულმა ტესტმა. ამიტომ, როდესაც გაშვების არგუმენტები ტოვებენ ტესტებს გარეთ, `--only`, `--exclude`, `--failed`, `--stale`, `--name-pattern`, `--max-failures`-ით, ან ტესტის ფაილებით ან ხაზებით, კომიტის დაფარვა არის **არასრული**, თუ არ გაშვებულა იმავე ვარიანტის გაშვება, რომელმაც არაფერი გამოტოვა. ორი გაშვება, რომლებიც თითოეული ტოვებს ტესტებს გარეთ, როგორიცაა `--exclude slow` და `--only slow`, მაინც ხდის კომიტს არასრულს, მიუხედავად იმისა, რომ ერთად მათ ყველა ტესტი გაუშვეს.

ზოგიერთი ტესტი განზრახ არის გამოტოვებული და არ ხდის კომიტს არასრულს:

- **თქვენი ტესტის დამხმარის გამონაკლისები.** ტესტები, რომლებსაც `ExUnit.start(exclude: [...])` ტოვებს გარეთ ნაგულისხმევად, არის თქვენი პროექტის არჩევანი, თუ რას ასრულებს მისი ნაკრები ნაგულისხმევად, ამიტომ Tuist არ თვლის მათ დაკარგულად. გაუშვით ისინი სხვა სამუშაოში, `--include` ან `--only`-ით, რათა დაამატოთ მათი დაფარვა კომიტს.
- **კოდში გამოტოვებული ტესტები** `@tag :skip`-ით.
- **ტესტები, რომლებსაც <.localized_link href="/guides/features/test-insights/flaky-tests/elixir#quarantining">კარანტინი</.localized_link> ტოვებს გარეთ.** ისინი გამოტოვებულია ისე, თითქოს წაშლილი იყოს, ამიტომ ხაზები, რომლებსაც მხოლოდ ისინი ფარავდნენ, დაფარულად არ ითვლება.

### სრული და არასრული კომიტები {#commit-status}

დაფის თითოეულ კომიტს აქვს სტატუსი:

| სტატუსი | მნიშვნელობა |
| --- | --- |
| მიმდინარეობს | გაშვებებმა მოახსენეს დაფარვა, მაგრამ `mix tuist.coverage.complete` ჯერ არ გაშვებულა ამ კომიტისთვის. |
| სრული | კომიტის ყველა გაშვების ყველა ტესტი შესრულდა ან განზრახ იქნა გამოტოვებული. |
| არასრული | ზოგიერთი დაფარვის დადგენა ვერ მოხერხდა, ამიტომ მაჩვენებელი ქვედა ზღვარია. |
| არ არის გაზომილი | არცერთ გაშვებას არ მოუხსენებია დაფარვა ამ კომიტისთვის. |

ბრენჩის ტრენდი მხოლოდ სრულ კომიტებს შეიცავს. კომიტი არასრულია, მაგალითად, როდესაც:

- ვარიანტის ყველა გაშვებამ თავისი არგუმენტებით ტესტები გამოტოვა.
- ვარიანტის ყველა გაშვებას აკლდა ზოგიერთი შარდი.
- ვარიანტის დაფარვა მიღებული იყო მხოლოდ CI-ს გაშვებებიდან, სადაც ჩექაუთში იყო დაუკომიტები ცვლილებები.

ვარიანტი არის ეტიკეტი, რომელსაც `--scheme`-ით გადასცემთ, მაგალითად, მონაცემთა ბაზის ვერსია. ეტიკეტის გარეშე გაშვებები ერთ ვარიანტად ითვლება. კომიტის მაჩვენებელი აერთიანებს ყველა გაშვებას, მაგრამ Tuist თითოეულ ვარიანტს სისრულეს ცალ-ცალკე ამოწმებს, ამიტომ თითოეულ ვარიანტს სჭირდება გაშვება, რომელიც არაფერს ტოვებს გარეთ.

## წარმადობაზე გავლენა {#performance-impact}

დაფარვის შეგროვება დამატებით ხარჯებს ქმნის, ამიტომ `--cover`-იანი გაშვებები უფრო მეტ დროს მოითხოვს, ვიდრე მის გარეშე გაშვებები. პირველი გაშვება ხაზების მრიცხველებით ხელახლა აკომპილირებს თქვენს მოდულებს; შემდგომი გაშვებები მხოლოდ ცვლილებებს აკომპილირებენ ხელახლა, ამიტომ მათი ღირებულება ბევრად ნაკლებია. დიდ პროექტებზე ნატიური თვლა ასევე ბევრად უფრო სწრაფია, ვიდრე Mix-ის დაფარვის ინსტრუმენტი.

## შეზღუდვები {#limitations}

- **HTML ანგარიში არ არის.** ნატიური თვლა არ წერს ანგარიშს `test_coverage: [output: ...]` დირექტორიაში და გაშვება აფრთხილებს, როდესაც ის მითითებულია. დაფის ფაილის გვერდები კი დაფარულ ხაზებს აჩვენებს.
- **განმეორებითი გაშვებები დაფარვას არ ამატებს.** <.localized_link href="/guides/features/test-insights/flaky-tests/elixir#test-retries">ტესტების განმეორებითი გაშვების</.localized_link> დროს დაფარვა პირველი მცდელობისაა. ამ მცდელობამ უკვე გაუშვა წარუმატებელი ტესტები, ამიტომ აკლია მხოლოდ ის ხაზები, რომლებსაც არამდგრადი ტესტი განმეორებით გაშვებაზე აღწევს, მაგრამ პირველ მცდელობაზე — არა.
- **დაფარვა არ არის ფორკებიდან გახსნილი პულ-რეკვესტებიდან.** დაფარვა იტვირთება მხოლოდ იმ გაშვებების მიერ, რომლებიც Tuist-თან ავთენტიკაციას გადიან, ხოლო CI ჩვეულებრივ ფარავს საიდუმლოებებსა და იდენტობის ტოკენებს ფორკებიდან გახსნილი პულ-რეკვესტებისთვის, ამიტომ ასეთი გაშვებები დაფარვას არ მოახსენებენ. შერწყმის შემდეგ კომიტი თქვენს ბრენჩზე რბის კრედენციალებით და ჩვეულებრივად მოახსენებს თავის დაფარვას.

## დაფარვის მოთხოვნა {#querying}

დაფის **კოდის დაფარვის** გვერდი აჩვენებს თითოეული კომიტის მაჩვენებელს, მის აპლიკაციებსა და ფაილებს, იმ ხაზებთან ერთად, რომლებიც თითოეულმა გაშვებამ დაფარა. იგივე მონაცემები ხელმისაწვდომია აგენტებისთვის <.localized_link href="/guides/features/agentic-coding/mcp">Model Context Protocol სერვერის</.localized_link> საშუალებით.
