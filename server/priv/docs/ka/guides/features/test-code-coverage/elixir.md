# Elixir-ის კოდის დაფარვა {#elixir-code-coverage}

კოდის დაფარვა გიჩვენებს, თუ კოდის რომელი სტრიქონები შეასრულეს თქვენმა ტესტებმა. Hex პაკეტი ატვირთავს სტრიქონების დაფარვას ყოველი `mix test --cover` გაშვებისთვის, ხოლო Tuist აერთიანებს კომიტის გაშვებებს ერთ რიცხვში — პროექტის, თითოეული OTP აპლიკაციისა და თითოეული ფაილის მიხედვით. დაფის **კოდის დაფარვა** გვერდი აჩვენებს მას კომიტის მიხედვით და როგორც ტენდენციას თითოეული ბრენჩისთვის.

> [!IMPORTANT]
> **მოთხოვნები**
>
> - დაასრულეთ <.localized_link href="/guides/get-started/elixir-project">ზოგადი Elixir-ის კონფიგურაცია</.localized_link>, რომელიც `mix test`-ს პაკეტის მეშვეობით ატარებს

## კონფიგურაცია {#setup}

### გაუშვით ტესტები დაფარვით {#run-your-tests}

გადაეცით `--cover`, ისევე როგორც `mix test`-ს Tuist-ის გარეშე:

```sh
mix test --cover
```

პაკეტი ატვირთავს დაფარვას გაშვების ტესტის შედეგებთან ერთად. როდესაც საიტი დასრულდება, ის ასევე ასრულებს იმას, რასაც Mix-ის დაფარვის ინსტრუმენტი აკეთებს, იგივე `test_coverage` პარამეტრებით კონფიგურირებული:

- **შეჯამება.** ის ბეჭდავს თითოეული მოდულის და ჯამურ დაფარვას. `summary: false` თიშავს მას.
- **ზღვარი.** ის აწყვეტს გაშვებას გამოსვლის სტატუსით 3, როდესაც ჯამური მაჩვენებელი ეცემა ზღვარზე ქვემოთ, რომელიც არის 90%, თუ სხვა რამ არ დააყენეთ:

```elixir
def project do
  [
    test_coverage: [summary: [threshold: 80]]
  ]
end
```

როგორც Mix-ში, ზღვარი ეკუთვნის შეჯამებას, ამიტომ `summary: false` თიშავს ორივეს. შეჯამების დაბეჭდვისთვის გაშვების შეწყვეტის გარეშე, დააყენეთ `threshold: 0`. მოდულები, ჩამოთვლილი `test_coverage: [ignore_modules: [...]]`-ში, გამოტოვებულია შეჯამებიდან და ატვირთვიდან.

Tuist აკონტროლებს დაფარვას კომიტის მიხედვით, ამიტომ მას სჭირდება თქვენი პროექტი Git რეპოზიტორიაში: გაშვება მის გარეშე ატვირთავს ტესტის შედეგებს, მაგრამ არა დაფარვას.

დაფარვა ეყრდნობა <.localized_link href="/guides/features/test-insights/elixir#git-history">Git-ის ისტორიას</.localized_link>, რომელსაც პაკეტი ატვირთავს, რაც კომიტს ათავსებს მის ბრენჩზე. უწყვეტი ინტეგრაციის გაშვებები ყოველთვის ატვირთავენ მას, ხოლო `--cover` გაშვებები ატვირთავენ მას ნებისმიერ მანქანაზე. `--cover`-ით, პაკეტი ასევე პოულობს, საიდანაც გადაიღო pull request-მა ბრენჩი: ის იღებს საბაზისო ბრენჩს და აძლიერებს ზედაპირულ კლონს იმდენად, რამდენადაც საჭიროა. უწყვეტ ინტეგრაციაზე, ზედაპირული checkout-იც ძლიერდება, ფაილების შინაარსის გარეშე, სანამ არ მიაღწევს კომიტებს, რომლებიც Tuist-ს უკვე აქვს, ამიტომ კომიტი არასდროს აიტვირთება მშობლის გარეშე, რომელზეც ის დგას. დააყენეთ `TUIST_GIT_UNSHALLOW_ENABLED=false`, რათა თავიდან აიცილოთ დაშორებულ რეპოზიტორიასთან დაკავშირება.

### დაყოფილი გაშვებები {#sharded-runs}

როდესაც <.localized_link href="/guides/features/test-sharding/elixir">ყოფთ ტესტებს</.localized_link>, გაუშვით თითოეული ნაწილი `--cover`-ით:

```sh
MIX_ENV=test TUIST_SHARD_INDEX=0 mix tuist.test --cover
```

ახალ გამშვებზე, გამოიყენეთ bootstrap ბრძანება დაყოფის სახელმძღვანელოს <.localized_link href="/guides/features/test-sharding/elixir#test-phase">ტესტის ფაზიდან</.localized_link>, რომელიც ხელს უშლის Mix-ს ყოველი დამოკიდებულების კომპილაციას სანამ ნაწილი ჩამოტვირთავს მის ბილდს, და დაამატეთ მას `--cover`.

ნაწილი ანგარიშგებს მხოლოდ საკუთარ დაფარვას და არ ამოწმებს ზღვარს, ვინაიდან ის ასრულებს საიტის ნაწილს. Tuist აერთიანებს გაშვების ნაწილებს ერთ რიცხვად.

თითოეული ნაწილი ამატებს დაფარვის მრიცხველებს ბილდს, რომელსაც ის ჩამოტვირთავს. ამის ერთხელ გასაკეთებლად, გადაეცით `--cover` ბილდის ფაზასაც:

```sh
MIX_ENV=test mix tuist.test.build --shard-max 5 --cover
```

გამორთეთ ის, როდესაც ინარჩუნებთ ბილდის დირექტორიას პაიპლაინის გაშვებებს შორის და ხელახლა იყენებთ მას გაშვებებში, რომლებიც არ აგროვებენ დაფარვას, რათა ეს ბილდი დარჩეს მრიცხველების გარეშე.

### დაასრულეთ თითოეული კომიტი CI-ზე {#complete-each-commit}

კომიტის დაფარვა ხშირად მოდის რამდენიმე სამუშაოდან: ერთი თითოეული ნაწილისთვის, თითოეული მონაცემთა ბაზის ვერსიისთვის ან თითოეული აპლიკაციისთვის. Tuist-ს არ შეუძლია განსაზღვროს, როდის მოახსენა ბოლომ მათგან, ამიტომ უთხარით მას. როდესაც კომიტის ყოველი ტესტის სამუშაო დასრულდება, გაუშვით ეს სამუშაოში, რომელიც დამოკიდებულია ყველა მათგანზე:

```sh
MIX_ENV=test mix tuist.coverage.complete
```

ამოცანა კითხულობს კომიტს `GIT_COMMIT`-დან ან checkout-ის `HEAD`-დან; გადაეცით `--commit <sha>` სხვის დასახელებლად. სანამ კომიტი არ იქნება დასრულებული, მისი დაფარვა ჩანს როგორც **მიმდინარე** და რჩება მისი ბრენჩის ტენდენციის გარეთ.

## როგორ მუშაობს {#how-it-works}

### ნატიური სტრიქონების მრიცხველები {#native-line-counters}

Mix-ის დაფარვის ინსტრუმენტი ხელახლა აკომპილირებს ყოველ მოდულს Erlang-ის `cover`-თვის ყოველი გაშვების დასაწყისში, რაც დიდ პროექტებზე ნელდება. პაკეტი ითვლის რანთაიმის ნატიური სტრიქონების მრიცხველებით. ის ხელახლა აკომპილირებს მხოლოდ იმ მოდულებს, რომლებიც კომპილაციამ დაწერა ბოლო გაშვების შემდეგ, გადააქვს რანთაიმი ამ მრიცხველებზე და კითხულობს მათ, როდესაც საიტი დასრულდება. Mix-ის დაფარვის ინსტრუმენტი გამოტოვებულია, მაგრამ მისი შეჯამება და ზღვარი რჩება.

პაკეტი ბრუნდება Mix-ის დაფარვის ინსტრუმენტზე, იგივე ატვირთვით, შემდეგი შემთხვევებისთვის:

- umbrella პროექტის ფესვი. გაუშვით ტესტები თითოეული აპლიკაციის შიგნით ნატიურად დასათვლელად.
- პროექტი, რომელიც აყენებს საკუთარ `test_coverage: [tool: ...]`-ს.
- რანთაიმი JIT-ის გარეშე, რომელსაც არ შეუძლია ნატიურად დათვლა.

### რას ზომავს Tuist {#what-tuist-measures}

- **აპლიკაციები.** თითოეული OTP აპლიკაცია არის მიზანი დაფაზე, საკუთარი დაფარვით.
- **მხოლოდ პროდუქტის კოდი.** ფაილები თქვენს ტესტის გზებქვეშ არის ტესტის კოდი. Tuist ინახავს მათ, მაგრამ ტოვებს მათ ყოველი რიცხვის გარეთ.
- **სტრიქონები ფაილის მიხედვით.** სტრიქონი ითვლება ერთხელ ფაილში, მიუხედავად იმისა, თუ რამდენ მოდულს ეკუთვნის ის.
- **ფუნქციები.** თითოეული სტრიქონი ეკუთვნის ფუნქციას, რომლის წინადადებაც ყველაზე ახლოს იწყება მის ზემოთ. ფუნქციები, რომლებსაც კომპილატორი ან მაკრო ქმნის, როგორიცაა `__info__/1` ან `__schema__/1`, არ არის ჩამოთვლილი, მაგრამ მათი სტრიქონები მაინც ითვლება მათი ფაილისთვის.

ამიტომ Tuist-ის რიცხვები განსხვავდება Mix-ის საკუთარი დაფარვის ანგარიშისგან რამდენიმე გზით: ისინი ტოვებენ ტესტის კოდს გარეთ და თვლიან სტრიქონებს ფაილის მიხედვით და არა მოდულის მიხედვით. ნატიური დათვლა ასევე ხედავს კოდს, რომელიც მუშაობს თქვენი აპლიკაციის გაშვებისას, და ტოვებს გარეთ სტრიქონებს, რომლებიც კომპილატორმა დაამტკიცა, რომ ვერასდროს იმუშავებს, რასაც Mix-ის ინსტრუმენტი ანგარიშგებს როგორც არასდროს დაფარულს.

### გამოტოვებული ტესტები {#skipped-tests}

Tuist-ს არ შეუძლია გადაიტანოს იმ ტესტების დაფარვა, რომლებსაც გაშვება ტოვებს გარეთ: პაკეტი აღრიცხავს, რა შეასრულა მთელმა გაშვებამ, და არა ის, რა შეასრულა თითოეულმა ტესტმა. ამიტომ, როდესაც გაშვების საკუთარი არგუმენტები ტოვებენ ტესტებს გარეთ, `--only`-ით, `--exclude`-ით, `--failed`-ით, `--stale`-ით, `--name-pattern`-ით, `--max-failures`-ით, ან ტესტის ფაილებით ან სტრიქონებით, კომიტის დაფარვა არის **არასრული**, თუ არ გაშვებულა იმავე ვარიანტის გაშვებაც, რომელმაც არაფერი დატოვა გარეთ. ორი გაშვება, რომლებიც თითოეული ტოვებს ტესტებს გარეთ, როგორიცაა `--exclude slow` და `--only slow`, მაინც ხდის კომიტს არასრულს, მიუხედავად იმისა, რომ ერთად მათ ყოველი ტესტი გაუშვეს.

ზოგიერთი ტესტი განზრახ არის გამოტოვებული და არ ხდის კომიტს არასრულს:

- **თქვენი ტესტის დამხმარის გამონაკლისები.** ტესტები, რომლებსაც `ExUnit.start(exclude: [...])` ტოვებს გარეთ ნაგულისხმევად, არის თქვენი პროექტის არჩევანი, თუ რას ასრულებს მისი საიტი ნაგულისხმევად, ამიტომ Tuist არ თვლის მათ როგორც დაკარგულს. გაუშვით ისინი სხვა სამუშაოში, `--include`-ით ან `--only`-ით, რათა დაამატოთ მათი დაფარვა კომიტს.
- **კოდში გამოტოვებული ტესტები** `@tag :skip`-ით.
- **ტესტები, რომლებსაც <.localized_link href="/guides/features/test-insights/flaky-tests/elixir#quarantining">კარანტინი</.localized_link> ტოვებს გარეთ.** ისინი გამოტოვებულია ისე, თითქოს წაშლილი იყოს, ამიტომ სტრიქონები, რომლებიც მხოლოდ მათ დაფარეს, ჩაითვლება დაუფარავად.

### სრული და არასრული კომიტები {#commit-status}

დაფის თითოეულ კომიტს აქვს სტატუსი:

| სტატუსი | მნიშვნელობა |
| --- | --- |
| მიმდინარეობს | გაშვებებმა ანგარიში გაუწია დაფარვას, მაგრამ `mix tuist.coverage.complete` ჯერ არ გაშვებულა კომიტისთვის. |
| სრული | კომიტის ყოველი გაშვების ყოველი ტესტი შესრულდა ან განზრახ იქნა გამოტოვებული. |
| არასრული | ზოგიერთი დაფარვის დადგენა ვერ მოხერხდა, ამიტომ მაჩვენებელი წარმოადგენს ქვედა ზღვარს. |
| არ არის გაზომილი | არც ერთმა გაშვებამ არ ანგარიში გაუწია კომიტის დაფარვას. |

ბრენჩის ტრენდი მოიცავს მხოლოდ სრულ კომიტებს. კომიტი არასრულია, მაგალითად, როდესაც:

- ვარიანტის ყოველმა გაშვებამ საკუთარი არგუმენტებით დატოვა ტესტები გარეთ.
- ვარიანტის ყოველ გაშვებას აკლდა ზოგიერთი შარდი.
- ვარიანტის დაფარვა მიღებული იყო მხოლოდ CI-ის გაშვებებიდან შეცვლილი ფაილების შემცველ ჩექაუთზე.

ვარიანტი არის ლეიბლი, რომელსაც გადასცემთ `--scheme`-ით, მაგალითად, მონაცემთა ბაზის ვერსია. ლეიბლის გარეშე გაშვებები ერთ ვარიანტს წარმოადგენს. კომიტის მაჩვენებელი აერთიანებს ყოველ გაშვებას, მაგრამ Tuist თითოეულ ვარიანტს სიმპლეტისთვის ცალ-ცალკე ამოწმებს, ამიტომ თითოეულ ვარიანტს სჭირდება გაშვება, რომელიც არაფერს ტოვებს გარეთ.

## წარმადობაზე გავლენა {#performance-impact}

დაფარვის შეგროვება ზრდის დამატებით დატვირთვას, ამიტომ `--cover`-ით გაშვებები უფრო ხანგრძლივია, ვიდრე მის გარეშე. პირველი გაშვება ხელახლა აკომპილირებს თქვენს მოდულებს სტრიქონების მთვლელებით; შემდგომი გაშვებები ხელახლა აკომპილირებს მხოლოდ იმას, რაც შეიცვალა, ამიტომ მათი ღირებულება ბევრად ნაკლებია. დიდ პროექტებზე, ნატიური თვლა ასევე ბევრად სწრაფია, ვიდრე Mix-ის დაფარვის ინსტრუმენტი.

## შეზღუდვები {#limitations}

- **HTML ანგარიში არ არის.** ნატიური თვლა არ წერს ანგარიშს `test_coverage: [output: ...]` დირექტორიაში და გაშვება აფრთხილებს, როდესაც ის მითითებულია. დაფის ფაილების გვერდები კი ნაცვლად აჩვენებს დაფარულ სტრიქონებს.
- **განმეორებითი ცდები არ ზრდის დაფარვას.** <.localized_link href="/guides/features/test-insights/flaky-tests/elixir#test-retries">ტესტების განმეორებითი ცდების</.localized_link> დროს, დაფარვა პირველი ცდისაა. ეს ცდა უკვე გაუშვა ჩავარდნილი ტესტები, ამიტომ ერთადერთი დაკარგული სტრიქონებია ისინი, რომლებსაც არამყარი ტესტი აღწევს განმეორებით ცდაზე, მაგრამ არა პირველ ცდაზე.
- **დაფარვა არ არის fork-ებიდან გახსნილი pull request-ებიდან.** დაფარვა იტვირთება მხოლოდ იმ გაშვებების მიერ, რომლებიც ავთენტიფიცირდებიან Tuist-თან, და CI ჩვეულებრივ ფარავს საიდუმლოებსა და იდენტობის ტოკენებს fork-ებიდან გახსნილი pull request-ებისთვის, ამიტომ ეს გაშვებები არ ანგარიშობენ დაფარვას. შერწყმის შემდეგ, კომიტი გაეშვება თქვენს ბრენჩზე კრედენციალებით და ანგარიშობს თავის დაფარვას ჩვეულებრივად.

## დაფარვის მოთხოვნა {#querying}

დაფის **კოდის დაფარვის** გვერდი აჩვენებს თითოეული კომიტის მაჩვენებელს, მის აპლიკაციებსა და ფაილებს, თითოეული გაშვების მიერ დაფარული სტრიქონებით. იგივე მონაცემები ხელმისაწვდომია აგენტებისთვის <.localized_link href="/guides/features/agentic-coding/mcp">Model Context Protocol სერვერის</.localized_link> მეშვეობით.
