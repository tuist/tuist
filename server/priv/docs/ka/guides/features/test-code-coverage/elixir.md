# Elixir-ის კოდის დაფარვა {#elixir-code-coverage}

კოდის დაფარვა გაჩვენებთ, თქვენი ტესტები კოდის რომელ ხაზებს ასრულებდნენ. Hex-ის პაკეტი ატვირთავს ხაზოვან დაფარვას ყოველი `mix test --cover` გაშვებისთვის, ხოლო Tuist აჯამებს კომიტის გაშვებებს ერთ რიცხვად — პროექტის, თითოეული OTP აპლიკაციისა და თითოეული ფაილის მიხედვით. დაფის **კოდის დაფარვის** გვერდი აჩვენებს მას კომიტების მიხედვით და როგორც ტრენდს თითოეულ ბრენჩზე.

> [!IMPORTANT] REQUIREMENTS
> - დაასრულეთ <.localized_link href="/guides/get-started/elixir-project">Elixir-ის საერთო მოწყობა</.localized_link>, რომელიც `mix test`-ს პაკეტის მეშვეობით ატარებს

## მოწყობა {#setup}

### ტესტების დაფარვით გაშვება {#run-your-tests}

გადაეცით `--cover`, ისევე როგორც `mix test`-ს Tuist-ის გარეშე:

```sh
mix test --cover
```

პაკეტი ატვირთავს დაფარვას გაშვების ტესტების შედეგებთან ერთად. სუიტის დასრულებისას ის ასრულებს იმავეს, რასაც Mix-ის დაფარვის ინსტრუმენტი, იმავე `test_coverage` პარამეტრებით კონფიგურირებული:

- **შეჯამება.** ის ბეჭდავს თითოეული მოდულის და ჯამურ დაფარვას. `summary: false` თიშავს მას.
- **ზღვარი.** ის აფერხებს გაშვებას გასვლის სტატუსით 3, როცა ჯამური მაჩვენებელი ზღვარზე ნაკლებია, რომელიც არის 90%, თუ სხვას არ დააყენებთ:

```elixir
def project do
  [
    test_coverage: [summary: [threshold: 80]]
  ]
end
```

როგორც Mix-ში, ზღვარი ეკუთვნის შეჯამებას, ამიტომ `summary: false` ორივეს თიშავს. შეჯამების დაბეჭდვისთვის გაშვების შეცდომის გარეშე, დააყენეთ `threshold: 0`. მოდულები, ჩამოთვლილი `test_coverage: [ignore_modules: [...]]`-ში, გამოტოვებულია შეჯამებიდან და ატვირთვიდან.

Tuist აკონტროლებს დაფარვას კომიტების მიხედვით, ამიტომ მას სჭირდება თქვენი პროექტი Git-ის რეპოზიტორიაში: მის გარეთ გაშვება ატვირთავს ტესტების შედეგებს, მაგრამ არა დაფარვას.

დაფარვა ეყრდნობა <.localized_link href="/guides/features/test-insights/elixir#git-history">Git-ის ისტორიას</.localized_link>, რომელსაც პაკეტი ატვირთავს და რომელიც კომიტს თავის ბრენჩზე ათავსებს. უწყვეტი ინტეგრაციის გაშვებები ყოველთვის ატვირთავენ მას, ხოლო `--cover` გაშვებები ატვირთავენ მას ნებისმიერ მანქანაზე. `--cover`-ით პაკეტი ასევე პოულობს, საიდანაც გადახრილი იყო pull request: ის იღებს საბაზისო ბრენჩს და აფართოებს ზედაპირულ კლონს საჭირო სიღრმემდე. დააყენეთ `TUIST_GIT_UNSHALLOW_ENABLED=false`, რათა თავიდან აიცილოთ დაშორებულ რეპოზიტორიასთან დაკავშირება.

### გაყოფილი გაშვებები {#sharded-runs}

როცა <.localized_link href="/guides/features/test-sharding/elixir">ყოფთ თქვენს ტესტებს</.localized_link>, გაუშვით თითოეული შარდი `--cover`-ით:

```sh
MIX_ENV=test TUIST_SHARD_INDEX=0 mix tuist.test --cover
```

ახალ გამშვებზე გამოიყენეთ გაყოფის სახელმძღვანელოს <.localized_link href="/guides/features/test-sharding/elixir#test-phase">ტესტის ფაზის</.localized_link> ბუტსტრაპის ბრძანება, რომელიც ხელს უშლის Mix-ს ყოველი დამოკიდებულების კომპილაციას შარდის ბილდის ჩამოტვირთვამდე, და დაამატეთ მას `--cover`.

შარდი ანგარიშგებს მხოლოდ საკუთარ დაფარვას და არ ამოწმებს ზღვარს, რადგან ის ასრულებს სუიტის ნაწილს. Tuist აერთიანებს გაშვების შარდებს ერთ რიცხვად.

თითოეული შარდი ამატებს დაფარვის მრიცხველებს ბილდში, რომელსაც ის ჩამოტვირთავს. ამის ერთხელ გასაკეთებლად, გადაეცით `--cover` ასევე ბილდის ფაზას:

```sh
MIX_ENV=test mix tuist.test.build --shard-max 5 --cover
```

გამორთეთ ის, როცა ინახავთ ბილდის დირექტორიას პაიპლაინის გაშვებებს შორის და ხელახლა იყენებთ მას გაშვებებში, რომლებიც არ აგროვებენ დაფარვას, რათა ეს ბილდი დარჩეს მრიცხველების გარეშე.

### დაასრულეთ თითოეული კომიტი CI-ზე {#complete-each-commit}

კომიტის დაფარვა ხშირად მოდის რამდენიმე სამუშაოდან: ერთი თითოეული შარდის, მონაცემთა ბაზის ვერსიის ან აპლიკაციისთვის. Tuist-ს არ შეუძლია განსაზღვროს, როდის მოახსენა ბოლომ მათგან, ამიტომ მიუთითეთ მას. როგორც კი კომიტის ყოველი ტესტის სამუშაო დასრულდება, გაუშვით ეს სამუშაოში, რომელიც დამოკიდებულია ყველა მათგანზე:

```sh
MIX_ENV=test mix tuist.coverage.complete
```

ამოცანა კითხულობს კომიტს `GIT_COMMIT`-დან ან checkout-ის `HEAD`-დან; გადაეცით `--commit <sha>`, რათა მიუთითოთ სხვა. სანამ კომიტი არ დასრულდება, მისი დაფარვა ჩანს როგორც **მიმდინარე** და არ შედის მისი ბრენჩის ტრენდში.

## როგორ მუშაობს {#how-it-works}

### ნატიური ხაზოვანი მრიცხველები {#native-line-counters}

Mix-ის დაფარვის ინსტრუმენტი ხელახლა აკომპილირებს ყოველ მოდულს Erlang-ის `cover`-სთვის ყოველი გაშვების დასაწყისში, რაც დიდ პროექტებზე ნელდება. პაკეტი ითვლის რანთაიმის ნატიური ხაზოვანი მრიცხველებით. ის ხელახლა აკომპილირებს მხოლოდ იმ მოდულებს, რომლებიც კომპილაციამ დაწერა ბოლო გაშვების შემდეგ, გადართავს რანთაიმს ამ მრიცხველებზე და კითხულობს მათ სუიტის დასრულებისას. Mix-ის დაფარვის ინსტრუმენტი გამოტოვებულია, მაგრამ მისი შეჯამება და ზღვარი შენარჩუნებულია.

პაკეტი გადადის Mix-ის დაფარვის ინსტრუმენტზე, იმავე ატვირთვით, შემდეგი შემთხვევებისთვის:

- umbrella პროექტის ფესვი. გაუშვით ტესტები თითოეულ აპლიკაციაში ნატიურად დათვლისთვის.
- პროექტი, რომელიც აყენებს საკუთარ `test_coverage: [tool: ...]`-ს.
- რანთაიმი JIT-ის გარეშე, რომელსაც არ შეუძლია ნატიურად დათვლა.

### რას ზომავს Tuist {#what-tuist-measures}

- **აპლიკაციები.** თითოეული OTP აპლიკაცია არის სამიზნე დაფაზე, საკუთარი დაფარვით.
- **მხოლოდ პროდუქტის კოდი.** ფაილები თქვენი ტესტების გზებზე არის ტესტის კოდი. Tuist ინახავს მათ, მაგრამ ტოვებს მათ ყოველი რიცხვის გარეთ.
- **ხაზები ფაილის მიხედვით.** ხაზი ითვლება ერთხელ ფაილის მიხედვით, მიუხედავად იმისა, თუ რამდენ მოდულს ეკუთვნის.
- **ფუნქციები.** თითოეული ხაზი ეკუთვნის ფუნქციას, რომლის წინადადებაც ყველაზე ახლოს იწყება მის ზემოთ. ფუნქციები, რომლებსაც კომპილატორი ან მაკრო ქმნის, როგორიცაა `__info__/1` ან `__schema__/1`, არ არის ჩამოთვლილი, მაგრამ მათი ხაზები მაინც ითვლება მათი ფაილისთვის.

ასე რომ, Tuist-ის რიცხვები განსხვავდება Mix-ის საკუთარი დაფარვის ანგარიშისგან რამდენიმე გზით: ისინი ტოვებენ ტესტის კოდს გარეთ და ითვლიან ხაზებს ფაილის მიხედვით და არა მოდულის მიხედვით. ნატიური დათვლა ასევე ხედავს კოდს, რომელიც სრულდება თქვენი აპლიკაციის გაშვებისას, და ტოვებს გარეთ ხაზებს, რომლებიც კომპილატორმა დაამტკიცა, რომ ვერასდროს შესრულდება, რასაც Mix-ის ინსტრუმენტი ანგარიშგებს როგორც არასდროს დაფარულს.

### გამოტოვებული ტესტები {#skipped-tests}

Tuist-ს არ შეუძლია გადაიტანოს იმ ტესტების დაფარვა, რომლებსაც გაშვება ტოვებს გარეთ: პაკეტი აღრიცხავს, რა შეასრულა მთელმა გაშვებამ, და არა ის, რა შეასრულა თითოეულმა ტესტმა. ასე რომ, როცა გაშვების საკუთარი არგუმენტები ტოვებენ ტესტებს გარეთ, `--only`-ით, `--exclude`-ით, `--failed`-ით, `--stale`-ით, `--name-pattern`-ით, `--max-failures`-ით, ან ტესტის ფაილებით ან ხაზებით, კომიტის დაფარვა არის **არასრული**, თუ არ გაშვებულა იმავე ვარიანტის გაშვებაც, რომელმაც არაფერი დატოვა გარეთ. ორი გაშვება, რომელთაგან თითოეული ტოვებს ტესტებს გარეთ, როგორიცაა `--exclude slow` და `--only slow`, მაინც ხდის კომიტს არასრულს, მიუხედავად იმისა, რომ ერთად მათ ყოველი ტესტი გაუშვეს.

ზოგიერთი ტესტი განზრახ არის გამოტოვებული და არ ხდის კომიტს არასრულს:

- **თქვენი ტესტის დამხმარის გამორიცხვები.** ტესტები, რომლებსაც `ExUnit.start(exclude: [...])` ტოვებს გარეთ ნაგულისხმევად, არის თქვენი პროექტის არჩევანი, თუ რას ასრულებს მისი სუიტა ნაგულისხმევად, ამიტომ Tuist არ თვლის მათ დაკარგულად. გაუშვით ისინი სხვა სამუშაოში, `--include`-ით ან `--only`-ით, რათა დაამატოთ მათი დაფარვა კომიტს.
- **კოდში გამოტოვებული ტესტები** `@tag :skip`-ით.
- **ტესტები, რომლებსაც <.localized_link href="/guides/features/test-insights/flaky-tests/elixir#quarantining">კარანტინი</.localized_link> ტოვებს.** ისინი გამოტოვებულია, თითქოს წაშლილი იყვნენ, ამიტომ ხაზები, რომლებიც მხოლოდ მათ ფარავდა, ითვლება დაუფარავად.

| --- | --- |
| მიმდინარეობს | გაშვებებმა ანგარიში წარადგინეს დაფარვის შესახებ, მაგრამ `mix tuist.coverage.complete` ჯერ არ გაუშვია ამ კომიტისთვის. |
| სრული | კომიტის ყველა გაშვების ყოველი ტესტი შესრულდა ან განზრახ იყო გამოტოვებული. |
| არასრული | ზოგიერთი დაფარვის დადგენა ვერ მოხერხდა, ამიტომ მაჩვენებელი წარმოადგენს ქვედა ზღვარს. |
| არ გაზომილა | არცერთმა გაშვებამ არ წარადგინა ანგარიში ამ კომიტის დაფარვის შესახებ. |

ბრენჩის ტრენდი მხოლოდ სრულ კომიტებს შეიცავს. კომიტი არასრულია, მაგალითად, როცა:

- ვარიანტის ყოველმა გაშვებამ საკუთარი არგუმენტებით ტესტები დატოვა გარეთ.
- ვარიანტის ყოველ გაშვებას აკლდა რამდენიმე შარდი.
- ვარიანტის დაფარვა მიღებული იყო მხოლოდ CI-ს გაშვებებიდან ისეთ ჩექაუთზე, სადაც იყო დაუკომიტებელი ცვლილებები.

ვარიანტი არის ლეიბლი, რომელსაც გადასცემთ `--scheme`-ით, მაგალითად, მონაცემთა ბაზის ვერსია. ლეიბლის გარეშე გაშვებები ერთ ვარიანტად ითვლება. კომიტის მაჩვენებელი აერთიანებს ყოველ გაშვებას, მაგრამ Tuist თითოეულ ვარიანტს სრულყოფილებისთვის ცალ-ცალკე ამოწმებს, ამიტომ თითოეულ ვარიანტს სჭირდება გაშვება, რომელიც არაფერს ტოვებს გარეთ.

## წარმადობაზე გავლენა {#performance-impact}

დაფარვის შეგროვება დამატებით ხარჯებს ქმნის, ამიტომ `--cover`-ით გაშვებები უფრო დიდხანს გრძელდება, ვიდრე მის გარეშე. პირველი გაშვება ხაზების მრიცხველებით თავიდან აკომპილირებს თქვენს მოდულებს; შემდგომი გაშვებები მხოლოდ იმას აკომპილირებენ ხელახლა, რაც შეიცვალა, ამიტომ მათი ღირებულება ბევრად ნაკლებია. დიდ პროექტებზე ნატიური აღრიცხვა ასევე ბევრად სწრაფია, ვიდრე Mix-ის დაფარვის ინსტრუმენტი.

## შეზღუდვები {#limitations}

- **HTML-ანგარიში არ არის.** ნატიური აღრიცხვა არ წერს ანგარიშს `test_coverage: [output: ...]` დირექტორიაში და გაშვება აფრთხილებს, როცა ის მითითებულია. დაფის ფაილის გვერდები ამის ნაცვლად აჩვენებს დაფარულ ხაზებს.
- **განმეორებითი გაშვებები არ ზრდის დაფარვას.** <.localized_link href="/guides/features/test-insights/flaky-tests/elixir#test-retries">ტესტების განმეორებითი გაშვების</.localized_link> დროს, დაფარვა პირველი მცდელობისაა. ეს მცდელობა უკვე გაუშვა წარუმატებელი ტესტები, ამიტომ დაკარგული ხაზები მხოლოდ ისინია, რომლებსაც არამდგრადი ტესტი აღწევს განმეორებითი გაშვებისას, მაგრამ არა პირველ მცდელობაზე.
- **დაფარვა არ არის fork-ებიდან გახსნილი pull request-ებიდან.** დაფარვა იტვირთება მხოლოდ იმ გაშვებების მიერ, რომლებიც ავთენტიკაციას გადიან Tuist-თან, ხოლო CI ჩვეულებრივ ფარავს საიდუმლოებებსა და იდენტობის ტოკენებს fork-ებიდან გახსნილი pull request-ებისთვის, ამიტომ ასეთი გაშვებები არ ანგარიშობენ დაფარვას. შერწყმის შემდეგ, კომიტი თქვენს ბრენჩზე რბის სერთიფიკატებით და ჩვეულებრივად ანგარიშობს თავის დაფარვას.

## დაფარვის მოთხოვნა {#querying}

დაფის **კოდის დაფარვის** გვერდი აჩვენებს თითოეული კომიტის მაჩვენებელს, მის აპლიკაციებსა და ფაილებს, იმ ხაზებთან ერთად, რომლებიც თითოეულმა გაშვებამ დაფარა. იგივე მონაცემები ხელმისაწვდომია აგენტებისთვის <.localized_link href="/guides/features/agentic-coding/mcp">Model Context Protocol სერვერის</.localized_link> მეშვეობით.
