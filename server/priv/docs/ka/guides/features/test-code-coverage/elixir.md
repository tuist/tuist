# Elixir-ის კოდის დაფარვა {#elixir-code-coverage}

კოდის დაფარვა გაჩვენებთ, თუ რომელი სტრიქონები შესრულდა თქვენი ტესტების მიერ. Hex-პაკეტი ატვირთავს სტრიქონების დაფარვას ყოველი `mix test --cover` გაშვებისთვის, ხოლო Tuist აერთიანებს კომიტის გაშვებებს ერთ მაჩვენებლად პროექტის, თითოეული OTP აპლიკაციისა და თითოეული ფაილისთვის. ინფორმაციის პანელის **კოდის დაფარვის** გვერდი აჩვენებს მას კომიტების მიხედვით და როგორც ტენდენციას თითოეული ბრენჩისთვის.

> [!IMPORTANT]
> **მოთხოვნები**
>
> - დაასრულეთ <.localized_link href="/guides/get-started/elixir-project">Elixir-ის საერთო კონფიგურაცია</.localized_link>, რომელიც `mix test`-ს გაატარებს პაკეტის მეშვეობით

## კონფიგურაცია {#setup}

### ტესტების გაშვება დაფარვით {#run-your-tests}

გადაეცით `--cover`, ისევე როგორც `mix test`-ს Tuist-ის გარეშე:

```sh
mix test --cover
```

პაკეტი ატვირთავს დაფარვას გაშვების ტესტის შედეგებთან ერთად. როდესაც ტესტების ნაკრები დასრულდება, ის ასევე ასრულებს იმავეს, რასაც Mix-ის დაფარვის ხელსაწყო, კონფიგურირებული იგივე `test_coverage` პარამეტრებით:

- **შეჯამება.** ბეჭდავს თითოეული მოდულის და ჯამურ დაფარვას. `summary: false` თიშავს მას.
- **ზღვარი.** გაშვება ვერდება გამოსვლის სტატუსით 3, როდესაც ჯამური მაჩვენებელი ეცემა ზღვარზე ქვემოთ, რომელიც არის 90%, თუ სხვა რამ არ არის მითითებული:

```elixir
def project do
  [
    test_coverage: [summary: [threshold: 80]]
  ]
end
```

Mix-ის მსგავსად, ზღვარი ეკუთვნის შეჯამებას, ამიტომ `summary: false` თიშავს ორივეს. შეჯამების დაბეჭდვისთვის გაშვების ჩავარდნის გარეშე, დააყენეთ `threshold: 0`. მოდულები, რომლებიც ჩამოთვლილია `test_coverage: [ignore_modules: [...]]`-ში, გამოტოვებულია შეჯამებიდან და ატვირთვიდან.

Tuist თვალყურს ადევნებს დაფარვას კომიტების მიხედვით, ამიტომ მას სჭირდება თქვენი პროექტი Git რეპოზიტორიაში: გაშვება რეპოზიტორიის გარეშე ატვირთავს ტესტის შედეგებს, მაგრამ არა დაფარვას.

დაფარვა ეყრდნობა <.localized_link href="/guides/features/test-insights/elixir#git-history">Git-ის ისტორიას</.localized_link>, რომელსაც პაკეტი ატვირთავს და რომელიც ათავსებს კომიტს მის ბრენჩზე. უწყვეტი ინტეგრაციის (CI) გაშვებები ყოველთვის ატვირთავენ მას, ხოლო `--cover` გაშვებები ატვირთავენ მას ნებისმიერ მანქანაზე. `--cover`-ით, პაკეტი ასევე პოულობს, საიდანაც გაიყო პულ-რეკვესტი: ის იღებს საბაზო ბრენჩს და აფართოებს ზედაპირულ კლონს საჭირო მანძილზე. უწყვეტ ინტეგრაციაზე, ზედაპირული ჩექაუთი ასევე ფართოვდება, ფაილების შინაარსის გარეშე, სანამ არ მიაღწევს იმ კომიტებს, რომლებიც Tuist-ს უკვე აქვს, ამიტომ კომიტი არასდროს აიტვირთება მშობელი კომიტის გარეშე. დააყენეთ `TUIST_GIT_UNSHALLOW_ENABLED=false`, რათა თავიდან აიცილოთ დისტანციურ რეპოზიტორიასთან დაკავშირება.

### დაშლილი გაშვებები {#sharded-runs}

როდესაც <.localized_link href="/guides/features/test-sharding/elixir">ყოფთ თქვენს ტესტებს</.localized_link>, გაუშვით თითოეული ნაწილი `--cover`-ით:

```sh
MIX_ENV=test TUIST_SHARD_INDEX=0 mix tuist.test --cover
```

ახალ გამშვებზე, გამოიყენეთ ბუტსტრაპის ბრძანება დაშლის სახელმძღვანელოს <.localized_link href="/guides/features/test-sharding/elixir#test-phase">ტესტის ფაზიდან</.localized_link>, რაც ხელს უშლის Mix-ს ყოველი დამოკიდებულების კომპილაციას სანამ ნაწილი ჩამოტვირთავს თავის ბილდს, და დაუმატეთ მას `--cover`.

ნაწილი ანგარიშგებს მხოლოდ საკუთარ დაფარვას და არ ამოწმებს ზღვარს, რადგან ის ასრულებს ნაკრების ნაწილს. Tuist აერთიანებს გაშვების ნაწილებს ერთ მაჩვენებლად.

თითოეული ნაწილი ამატებს დაფარვის მრიცხველებს ბილდს, რომელსაც ის ჩამოტვირთავს. ამის ერთხელ გასაკეთებლად, გადაეცით `--cover` ასევე ბილდის ფაზას:

```sh
MIX_ENV=test mix tuist.test.build --shard-max 5 --cover
```

გამორთეთ ის, როდესაც ინახავთ ბილდის დირექტორიას პაიპლაინის გაშვებებს შორის და იყენებთ მას ხელახლა გაშვებებში, რომლებიც არ აგროვებენ დაფარვას, რათა ეს ბილდი დარჩეს მრიცხველების გარეშე.

### ყოველი კომიტის დასრულება CI-ზე {#complete-each-commit}

კომიტის დაფარვა ხშირად მოდის რამდენიმე სამუშაოდან: ერთი თითოეული ნაწილისთვის, მონაცემთა ბაზის ვერსიისთვის ან აპლიკაციისთვის. Tuist-ს არ შეუძლია განსაზღვროს, როდის ანგარიშგებს ბოლო მათგანი, ამიტომ მიუთითეთ მას. როდესაც კომიტის ყოველი ტესტის სამუშაო დასრულდება, გაუშვით ეს სამუშაოში, რომელიც დამოკიდებულია ყველა მათგანზე:

```sh
MIX_ENV=test mix tuist.coverage.complete
```

ამოცანა კითხულობს კომიტს `GIT_COMMIT`-დან ან ჩექაუთის `HEAD`-დან; გადაეცით `--commit <sha>`, რათა მიუთითოთ სხვა. სანამ კომიტი არ დასრულდება, მისი დაფარვა ჩანს როგორც **მიმდინარე** და არ შედის მისი ბრენჩის ტენდენციაში.

## როგორ მუშაობს {#how-it-works}

### ნატიური სტრიქონების მრიცხველები {#native-line-counters}

Mix-ის დაფარვის ხელსაწყო აკომპილირებს ყოველ მოდულს ხელახლა Erlang-ის `cover`-სთვის ყოველი გაშვების დასაწყისში, რაც ნელდება დიდ პროექტებზე. პაკეტი იყენებს რანთაიმის ნატიურ სტრიქონების მრიცხველებს. ის აკომპილირებს ხელახლა მხოლოდ იმ მოდულებს, რომლებიც დაიწერა ბოლო გაშვების შემდეგ, გადართავს რანთაიმს ამ მრიცხველებზე და კითხულობს მათ, როდესაც ნაკრები დასრულდება. Mix-ის დაფარვის ხელსაწყო გამოტოვებულია, მაგრამ მისი შეჯამება და ზღვარი შენარჩუნებულია.

პაკეტი გადადის Mix-ის დაფარვის ხელსაწყოზე, იგივე ატვირთვით, შემდეგი შემთხვევებისთვის:

- umbrella პროექტის ფესვი. გაუშვით ტესტები თითოეული აპლიკაციის შიგნით, რათა დათვალოთ ნატიურად.
- პროექტი, რომელიც აყენებს საკუთარ `test_coverage: [tool: ...]`-ს.
- რანთაიმი JIT-ის გარეშე, რომელსაც არ შეუძლია ნატიურად დათვლა.

### რას ზომავს Tuist {#what-tuist-measures}

- **აპლიკაციები.** თითოეული OTP აპლიკაცია არის მიზანი ინფორმაციის პანელზე, საკუთარი დაფარვით.
- **მხოლოდ პროდუქტის კოდი.** ფაილები თქვენს ტესტის გზებზე არის ტესტის კოდი. Tuist ინახავს მათ, მაგრამ ტოვებს მათ ყოველი მაჩვენებლის გარეთ.
- **სტრიქონები ფაილის მიხედვით.** სტრიქონი ითვლება ერთხელ ფაილის მიხედვით, მიუხედავად იმისა, თუ რამდენ მოდულს ეკუთვნის.
- **ფუნქციები.** თითოეული სტრიქონი ეკუთვნის ფუნქციას, რომლის წინადადებაც იწყება მასზე ყველაზე ახლოს ზემოთ. ფუნქციები, რომლებსაც კომპილატორი ან მაკრო ქმნის, როგორიცაა `__info__/1` ან `__schema__/1`, არ არის ჩამოთვლილი, მაგრამ მათი სტრიქონები მაინც ითვლება მათი ფაილისთვის.

ამიტომ, Tuist-ის მაჩვენებლები განსხვავდება Mix-ის საკუთარი დაფარვის ანგარიშისგან რამდენიმე გზით: ისინი ტოვებენ ტესტის კოდს გარეთ და თვლიან სტრიქონებს ფაილის მიხედვით და არა მოდულის მიხედვით. ნატიური დათვლა ასევე ხედავს კოდს, რომელიც მუშაობს თქვენი აპლიკაციის გაშვებისას, და ტოვებს გარეთ სტრიქონებს, რომლებიც კომპილატორმა დაამტკიცა, რომ ვერასდროს შესრულდება, რასაც Mix-ის ხელსაწყო ანგარიშგებს როგორც არასდროს დაფარულს.

### გამოტოვებული ტესტები {#skipped-tests}

Tuist-ს არ შეუძლია გადაიტანოს იმ ტესტების დაფარვა, რომლებიც გაშვებამ გამოტოვა: პაკეტი აღრიცხავს, რა შესრულდა მთლიანი გაშვების მიერ, და არა რა შესრულდა თითოეული ტესტის მიერ. ამიტომ, როდესაც გაშვების არგუმენტები ტოვებენ ტესტებს გარეთ, `--only`, `--exclude`, `--failed`, `--stale`, `--name-pattern`, `--max-failures`-ით, ან ტესტის ფაილებით ან სტრიქონებით, კომიტის დაფარვა არის **არასრული**, თუ არ გაშვებულა იგივე ვარიანტის გაშვება, რომელმაც არაფერი გამოტოვა. ორი გაშვება, რომელთაგან თითოეული ტოვებს ტესტებს გარეთ, როგორიცაა `--exclude slow` და `--only slow`, მაინც ხდის კომიტს არასრულს, მიუხედავად იმისა, რომ ერთად მათ ყოველი ტესტი გაუშვეს.

ზოგიერთი ტესტი განზრახ არის გამოტოვებული და არ ხდის კომიტს არასრულს:

- **თქვენი ტესტის დამხმარის გამონაკლისები.** ტესტები, რომლებსაც `ExUnit.start(exclude: [...])` ტოვებს გარეთ ნაგულისხმევად, არის თქვენი პროექტის არჩევანი, თუ რას ასრულებს მისი ნაკრები ნაგულისხმევად, ამიტომ Tuist არ თვლის მათ დაკარგულად. გაუშვით ისინი სხვა სამუშაოში, `--include` ან `--only`-ით, რათა დაუმატოთ მათი დაფარვა კომიტს.
- **კოდში გამოტოვებული ტესტები** `@tag :skip`-ით.
- **ტესტები, რომლებსაც <.localized_link href="/guides/features/test-insights/flaky-tests/elixir#quarantining">კარანტინი</.localized_link> ტოვებს გარეთ.** ისინი გამოტოვებულია ისე, თითქოს წაშლილი იყოს, ამიტომ სტრიქონები, რომლებიც მხოლოდ მათ დაფარეს, ჩაითვლება დაუფარავად.

### სრული და არასრული კომიტები {#commit-status}

დაფის თითოეულ კომიტს აქვს სტატუსი:

| სტატუსი | მნიშვნელობა |
| --- | --- |
| მიმდინარეობს | გაშვებებმა მოახსენეს დაფარვა, მაგრამ `mix tuist.coverage.complete` ჯერ არ გაშვებულა კომიტისთვის. |
| სრული | კომიტის ყველა გაშვების ყოველი ტესტი შესრულდა ან განზრახ იქნა გამოტოვებული. |
| არასრული | ზოგიერთი დაფარვის დადგენა ვერ მოხერხდა, ამიტომ მაჩვენებელი ქვედა ზღვარია. |
| არ არის გაზომილი | არცერთ გაშვებას არ მოუხსენებია დაფარვა კომიტისთვის. |

ბრენჩის ტრენდი მოიცავს მხოლოდ სრულ კომიტებს. კომიტი არასრულია, მაგალითად, როდესაც:

- ვარიანტის ყოველმა გაშვებამ თავისი არგუმენტებით ტესტები დატოვა გარეთ.
- ვარიანტის ყოველ გაშვებას აკლდა ზოგიერთი შარდი.
- ვარიანტის დაფარვა მიღებული იყო მხოლოდ CI-ის გაშვებებიდან შეუმოწმებელი ცვლილებების შემცველ checkout-ზე.

ვარიანტი არის ლეიბლი, რომელსაც გადასცემთ `--scheme`-ით, მაგალითად, მონაცემთა ბაზის ვერსია. ლეიბლის გარეშე გაშვებები ერთ ვარიანტს წარმოადგენს. კომიტის მაჩვენებელი აერთიანებს ყოველ გაშვებას, მაგრამ Tuist თითოეულ ვარიანტს ცალ-ცალკე ამოწმებს სისრულისთვის, ამიტომ თითოეულ ვარიანტს სჭირდება გაშვება, რომელიც არაფერს ტოვებს გარეთ.

## წარმადობაზე გავლენა {#performance-impact}

დაფარვის შეგროვება ზრდის დამატებით ხარჯს, ამიტომ `--cover`-ით გაშვებები უფრო დიდხანს გრძელდება, ვიდრე მის გარეშე. პირველი გაშვება ხელახლა აკომპილირებს თქვენს მოდულებს სტრიქონების მთვლელებით; მომდევნო გაშვებები ხელახლა აკომპილირებენ მხოლოდ იმას, რაც შეიცვალა, ამიტომ მათი ხარჯი ბევრად ნაკლებია. დიდ პროექტებზე ნატიური დათვლა ასევე ბევრად უფრო სწრაფია, ვიდრე Mix-ის დაფარვის ინსტრუმენტი.

## შეზღუდვები {#limitations}

- **HTML ანგარიში არ არის.** ნატიური დათვლა არ წერს ანგარიშს `test_coverage: [output: ...]` დირექტორიაში და გაშვება აფრთხილებს, როდესაც ის მითითებულია. დაფის ფაილის გვერდები ნაცვლად ამისა აჩვენებენ დაფარულ სტრიქონებს.
- **გადაცდები არ ზრდის დაფარვას.** <.localized_link href="/guides/features/test-insights/flaky-tests/elixir#test-retries">ტესტების გადაცდების</.localized_link> დროს დაფარვა ეკუთვნის პირველ მცდელობას. ეს მცდელობა უკვე გაუშვა წარუმატებელი ტესტები, ამიტომ დაკარგულია მხოლოდ ის სტრიქონები, რომლებსაც არამდგრადი ტესტი აღწევს გადაცდისას, მაგრამ არა პირველ მცდელობაზე.
- **დაფარვა არ არის fork-ებიდან გახსნილი pull request-ებიდან.** დაფარვა იტვირთება მხოლოდ იმ გაშვებების მიერ, რომლებიც ავთენტიკაციას გადიან Tuist-თან, ხოლო CI ჩვეულებრივ ფარავს საიდუმლოებს და იდენტობის ტოკენებს fork-ებიდან გახსნილი pull request-ებისგან, ამიტომ ეს გაშვებები არ მოახსენებენ დაფარვას. შერწყმის შემდეგ კომიტი თქვენს ბრენჩზე გაშვებული იქნება სერთიფიკატებით და მოახსენებს თავის დაფარვას ჩვეულებრივად.

## დაფარვის მოთხოვნა {#querying}

დაფის **კოდის დაფარვა** გვერდი აჩვენებს თითოეული კომიტის მაჩვენებელს, მის აპლიკაციებს და ფაილებს, იმ სტრიქონებით, რომლებიც თითოეულმა გაშვებამ დაფარა. იგივე მონაცემები ხელმისაწვდომია აგენტებისთვის <.localized_link href="/guides/features/agentic-coding/mcp">Model Context Protocol სერვერის</.localized_link> მეშვეობით.
