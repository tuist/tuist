# Elixir-ის კოდის დაფარვა {#elixir-code-coverage}

კოდის დაფარვა გაჩვენებთ, თქვენი ტესტები კოდის რომელი ხაზები შეასრულეს. Hex-ის პაკეტი ატვირთავს ხაზების დაფარვას ყოველი `mix test --cover` გაშვებისთვის, ხოლო Tuist კომიტის გაშვებებს ერთ მაჩვენებლად აერთიანებს პროექტის, თითოეული OTP აპლიკაციისა და თითოეული ფაილის მიხედვით. დაფარვის გვერდი **კოდის დაფარვა** აჩვენებს მას კომიტების მიხედვით და როგორც ტენდენციას თითოეული ბრენჩისთვის.

> [!IMPORTANT]
> **მოთხოვნები**
>
> - დაასრულეთ <.localized_link href="/guides/get-started/elixir-project">Elixir-ის საერთო კონფიგურაცია</.localized_link>, რომელიც `mix test`-ს პაკეტის მეშვეობით ატარებს

## კონფიგურაცია {#setup}

### გაუშვით ტესტები დაფარვით {#run-your-tests}

გადაეცით `--cover`, ისევე როგორც `mix test`-ს Tuist-ის გარეშე:

```sh
mix test --cover
```

პაკეტი ატვირთავს დაფარვას გაშვების ტესტის შედეგებთან ერთად. როდესაც სუიტა დასრულდება, ის ასევე ასრულებს იმას, რასაც Mix-ის დაფარვის ინსტრუმენტი აკეთებს, იგივე `test_coverage` პარამეტრებით კონფიგურირებული:

- **შეჯამება.** ის ბეჭდავს თითოეული მოდულის და საერთო დაფარვას. `summary: false` თიშავს მას.
- **ზღვარი.** ის აცდენს გაშვებას exit status 3-ით, როდესაც საერთო მაჩვენებელი ზღვარზე ქვემოთ ეცემა, რაც არის 90%, თუ სხვას არ დააყენებთ:

```elixir
def project do
  [
    test_coverage: [summary: [threshold: 80]]
  ]
end
```

როგორც Mix-ში, ზღვარი შეჯამებას ეკუთვნის, ამიტომ `summary: false` ორივეს თიშავს. შეჯამების დაბეჭდვისთვის გაშვების აცდენის გარეშე, დააყენეთ `threshold: 0`. მოდულები, რომლებიც ჩამოთვლილია `test_coverage: [ignore_modules: [...]]`-ში, გამოტოვებულია შეჯამებიდან და ატვირთვიდან.

Tuist თვალყურს ადევნებს დაფარვას კომიტების მიხედვით, ამიტომ მას სჭირდება თქვენი პროექტი Git რეპოზიტორიაში: გაშვება მის გარეშე ატვირთავს ტესტის შედეგებს, მაგრამ არა დაფარვას.

დაფარვა ეყრდნობა <.localized_link href="/guides/features/test-insights/elixir#git-history">Git-ის ისტორიას</.localized_link>, რომელსაც პაკეტი ატვირთავს და რომელიც კომიტს თავის ბრენჩზე ათავსებს. უწყვეტი ინტეგრაციის გაშვებები ყოველთვის ატვირთავენ მას, ხოლო `--cover` გაშვებები ატვირთავენ მას ნებისმიერ მანქანაზე. `--cover`-ით პაკეტი ასევე პოულობს, საიდანაც გაიყო pull request: ის იღებს საბაზისო ბრენჩს და აღრმავებს ზედაპირულ კლონს საჭირო რაოდენობამდე. უწყვეტ ინტეგრაციაზე ზედაპირული checkout-იც აღრმავდება, ფაილების შინაარსის გარეშე, სანამ Tuist-ისთვის უკვე არსებულ კომიტებს არ მიაღწევს, ამიტომ კომიტი არასდროს აიტვირთება მშობლის გარეშე, რომელზეც ის ეყრდნობა. დააყენეთ `TUIST_GIT_UNSHALLOW_ENABLED=false`, რათა თავიდან აიცილოთ დისტანციურ რეპოზიტორიასთან დაკავშირება.

### დაშლილი გაშვებები {#sharded-runs}

როდესაც <.localized_link href="/guides/features/test-sharding/elixir">ტესტებს შარდებად ყოფთ</.localized_link>, გაუშვით თითოეული შარდი `--cover`-ით:

```sh
MIX_ENV=test TUIST_SHARD_INDEX=0 mix tuist.test --cover
```

ახალ გამშვებზე გამოიყენეთ შარდინგის სახელმძღვანელოს <.localized_link href="/guides/features/test-sharding/elixir#test-phase">ტესტის ფაზიდან</.localized_link> bootstrap ბრძანება, რომელიც ხელს უშლის Mix-ს ყველა დამოკიდებულების კომპილაციას მანამ, სანამ შარდი ჩამოტვირთავს თავის ბილდს, და დაამატეთ მას `--cover`.

შარდი ანგარიშგებს მხოლოდ საკუთარ დაფარვას და არ ამოწმებს ზღვარს, ვინაიდან ის სუიტის ნაწილს ასრულებს. Tuist გაშვების შარდებს ერთ მაჩვენებლად აერთიანებს.

თითოეული შარდი ამატებს დაფარვის მრიცხველებს ბილდს, რომელსაც ჩამოტვირთავს. ამის ერთხელ გასაკეთებლად, გადაეცით `--cover` ბილდის ფაზასაც:

```sh
MIX_ENV=test mix tuist.test.build --shard-max 5 --cover
```

გამორთეთ ის, როდესაც პაიპლაინის გაშვებებს შორის ინახავთ ბილდის დირექტორიას და ხელახლა იყენებთ მას გაშვებებში, რომლებიც არ აგროვებენ დაფარვას, რათა ეს ბილდი დარჩეს მრიცხველების გარეშე.

### დაასრულეთ თითოეული კომიტი CI-ზე {#complete-each-commit}

კომიტის დაფარვა ხშირად რამდენიმე სამუშაოსგან მოდის: ერთი შარდის, მონაცემთა ბაზის ვერსიის ან აპლიკაციის მიხედვით. Tuist-ს არ შეუძლია განსაზღვროს, როდის მოახსენა ბოლომ მათგან, ამიტომ შეატყობინეთ მას. როდესაც კომიტის ყველა ტესტის სამუშაო დასრულდება, გაუშვით ეს სამუშაოში, რომელიც ყველა მათგანზეა დამოკიდებული:

```sh
MIX_ENV=test mix tuist.coverage.complete
```

ამოცანა კითხულობს კომიტს `GIT_COMMIT`-დან ან checkout-ის `HEAD`-დან; გადაეცით `--commit <sha>` სხვის დასახელებლად. სანამ კომიტი არ დასრულდება, მისი დაფარვა ჩანს როგორც **მიმდინარე** და არ შედის ბრენჩის ტენდენციაში.

## როგორ მუშაობს {#how-it-works}

### ნატიური ხაზების მრიცხველები {#native-line-counters}

Mix-ის დაფარვის ინსტრუმენტი თითოეულ გაშვების დასაწყისში ხელახლა აკომპილირებს ყველა მოდულს Erlang-ის `cover`-თვის, რაც დიდ პროექტებზე ნელდება. პაკეტი ნაცვლად იყენებს runtime-ის ნატიურ ხაზების მრიცხველებს. ის ხელახლა აკომპილირებს მხოლოდ იმ მოდულებს, რომლებიც ბოლო გაშვების შემდეგ დაიწერა, გადართავს runtime-ს ამ მრიცხველებზე და კითხულობს მათ, როდესაც სუიტა დასრულდება. Mix-ის დაფარვის ინსტრუმენტი გამოტოვებულია, მაგრამ მისი შეჯამება და ზღვარი ინახება.

პაკეტი ბრუნდება Mix-ის დაფარვის ინსტრუმენტზე, იგივე ატვირთვით, შემდეგი შემთხვევებისთვის:

- umbrella პროექტის ფესვი. გაუშვით ტესტები თითოეულ აპლიკაციაში ნატიურად დათვლისთვის.
- პროექტი, რომელიც აყენებს საკუთარ `test_coverage: [tool: ...]`.
- runtime JIT-ის გარეშე, რომელსაც არ შეუძლია ნატიურად დათვლა.

### რას ზომავს Tuist {#what-tuist-measures}

- **აპლიკაციები.** თითოეული OTP აპლიკაცია არის სამიზნე დაფარვის გვერდზე, საკუთარი დაფარვით.
- **მხოლოდ პროდუქციის კოდი.** თქვენი ტესტის გზებქვეშ მყოფი ფაილები არის ტესტის კოდი. Tuist ინახავს მათ, მაგრამ გამოტოვებს ყველა მაჩვენებლიდან.
- **ხაზები ფაილის მიხედვით.** ხაზი ითვლება ერთხელ ფაილის მიხედვით, მიუხედავად იმისა, რამდენ მოდულს ეკუთვნის.
- **ფუნქციები.** თითოეული ხაზი ეკუთვნის ფუნქციას, რომლის წინადადებაც მასზე ყველაზე ახლოს იწყება. ფუნქციები, რომლებსაც კომპილატორი ან მაკრო ქმნის, როგორიცაა `__info__/1` ან `__schema__/1`, არ არის ჩამოთვლილი, მაგრამ მათი ხაზები მაინც ითვლება მათი ფაილისთვის.
- **შაბლონები.** ნატიური დათვლით, შაბლონი, რომელიც აკომპილირებულია მოდულში, როგორიცაა LiveView-ის `.html.heex`, `embed_templates` ან `EEx.function_from_file`, იზომება როგორც საკუთარი ფაილი, საკუთარი ხაზებით და ფუნქციების გარეშე. Mix-ის დაფარვის ინსტრუმენტი არ ზომავს შაბლონებს, ამიტომ შეჯამება და ზღვარი მათ გამოტოვებს.

ამიტომ Tuist-ის მაჩვენებლები რამდენიმე გზით განსხვავდება Mix-ის საკუთარი დაფარვის ანგარიშისგან: ისინი გამოტოვებენ ტესტის კოდს და ითვლიან ხაზებს ფაილის მიხედვით და არა მოდულის მიხედვით. ნატიური დათვლა ასევე ხედავს კოდს, რომელიც მუშაობს თქვენი აპლიკაციის გაშვებისას, და გამოტოვებს ხაზებს, რომლებიც კომპილატორმა დაამტკიცა, რომ არასდროს შესრულდება, რასაც Mix-ის ინსტრუმენტი ანგარიშგებს როგორც არასდროს დაფარულს.

### გამოტოვებული ტესტები {#skipped-tests}

Tuist-ს არ შეუძლია გადაიტანოს იმ ტესტების დაფარვა, რომლებსაც გაშვება გამოტოვებს: პაკეტი აღრიცხავს, რა შეასრულა მთლიანმა გაშვებამ და არა ის, რა შეასრულა თითოეულმა ტესტმა. ამიტომ, როდესაც გაშვების საკუთარი არგუმენტები გამოტოვებენ ტესტებს, `--only`, `--exclude`, `--failed`, `--stale`, `--name-pattern`, `--max-failures` ან ტესტის ფაილების ან ხაზების მეშვეობით, კომიტის დაფარვა არის **არასრული**, თუ არ გაშვებულა იგივე ვარიანტის გაშვება, რომელმაც არაფერი გამოტოვა. ორი გაშვება, რომლებიც თითოეული გამოტოვებს ტესტებს, როგორიცაა `--exclude slow` და `--only slow`, მაინც ხდის კომიტს არასრულს, მიუხედავად იმისა, რომ ერთად მათ ყველა ტესტი გაუშვეს.

ზოგიერთი ტესტი განზრახ არის გამოტოვებული და არ ხდის კომიტს არასრულს:

- **თქვენი ტესტის დამხმარის გამორიცხვები.** ტესტები, რომლებსაც `ExUnit.start(exclude: [...])` ნაგულისხმევად გამოტოვებს, არის თქვენი პროექტის არჩევანი, თუ რას ასრულებს მისი სუიტა ნაგულისხმევად, ამიტომ Tuist მათ არ თვლის დაკარგულად. გაუშვით ისინი სხვა სამუშაოში, `--include` ან `--only`-ით, რათა დაამატოთ მათი დაფარვა კომიტს.
- **კოდში გამოტოვებული ტესტები** `@tag :skip`-ით.
- **ტესტები, რომლებსაც <.localized_link href="/guides/features/test-insights/flaky-tests/elixir#quarantining">კარანტინი</.localized_link> ტოვებს.** ისინი გამოტოვებულია ისე, თითქოს წაშლილი იყვნენ, ამიტომ ხაზები, რომლებიც მხოლოდ მათ ფარავდა, დაფარულად არ ითვლება.

### სრული და არასრული კომიტები {#commit-status}

დაფის თითოეულ კომიტს აქვს სტატუსი:

| სტატუსი | მნიშვნელობა |
| --- | --- |
| მიმდინარეობს | გაშვებებმა შეატყობინეს დაფარვა, მაგრამ `mix tuist.coverage.complete` ჯერ არ გაშვებულა კომიტისთვის. |
| სრული | კომიტის ყველა გაშვების ყველა ტესტი შესრულდა ან განზრახ იქნა გამოტოვებული. |
| არასრული | ზოგიერთი დაფარვის დადგენა ვერ მოხერხდა, ამიტომ მაჩვენებელი ქვედა ზღვარია. |
| არ არის გაზომილი | არცერთ გაშვებას არ შეუტყობინებია დაფარვა ამ კომიტისთვის. |

ბრენჩის ტრენდი მხოლოდ სრულ კომიტებს შეიცავს. კომიტი არასრულია, მაგალითად, როდესაც:

- ვარიანტის ყველა გაშვებამ საკუთარი არგუმენტებით გამოტოვა ტესტები.
- ვარიანტის ყველა გაშვებას აკლდა ზოგიერთი შარდი.
- ვარიანტის დაფარვა მიღებული იყო მხოლოდ CI გაშვებებიდან, სადაც იყო დაკომიტების გარეშე ცვლილებები.

ვარიანტი არის ლეიბლი, რომელსაც გადასცემთ `--scheme`-ით, მაგალითად, მონაცემთა ბაზის ვერსია. ლეიბლის გარეშე გაშვებები ერთ ვარიანტად ითვლება. კომიტის მაჩვენებელი აერთიანებს ყველა გაშვებას, მაგრამ Tuist თითოეულ ვარიანტს სიმწირისთვის ცალ-ცალკე ამოწმებს, ამიტომ თითოეულ ვარიანტს სჭირდება გაშვება, რომელიც არაფერს გამოტოვებს.

## შესრულებაზე გავლენა {#performance-impact}

დაფარვის შეგროვება ზრდის დამატებით დატვირთვას, ამიტომ `--cover`-ით გაშვებები უფრო გრძელდება, ვიდრე მის გარეშე. პირველი გაშვება ხაზების მრიცხველებით თავიდან აკომპილირებს თქვენს მოდულებს; შემდგომი გაშვებები მხოლოდ ცვლილებებს აკომპილირებენ, ამიტომ მათი ღირებულება ბევრად ნაკლებია. დიდ პროექტებზე ნატიური აღრიცხვა ასევე ბევრად სწრაფია, ვიდრე Mix-ის დაფარვის ინსტრუმენტი.

## შეზღუდვები {#limitations}

- **HTML ანგარიში არ არის.** ნატიური აღრიცხვა არ წერს ანგარიშს `test_coverage: [output: ...]` დირექტორიაში და გაშვება აფრთხილებს, როდესაც ის მითითებულია. დაფის ფაილების გვერდები კი დაფარულ ხაზებს აჩვენებს.
- **განმეორებითი გაშვებები არ ზრდის დაფარვას.** <.localized_link href="/guides/features/test-insights/flaky-tests/elixir#test-retries">ტესტების განმეორებითი გაშვების</.localized_link> შემთხვევაში, დაფარვა პირველი მცდელობისაა. ამ მცდელობამ უკვე გაუშვა ჩავარდნილი ტესტები, ამიტომ დაკარგული ხაზები მხოლოდ ისინია, რომლებსაც არასტაბილური ტესტი აღწევს განმეორებითი გაშვებისას, მაგრამ არა პირველ მცდელობაზე.
- **ფორკებიდან გახსნილი pull request-ებიდან დაფარვა არ არის.** დაფარვა იტვირთება მხოლოდ იმ გაშვებების მიერ, რომლებიც Tuist-თან ავტორიზაციას გადიან, ხოლო CI ჩვეულებრივ ფარავს საიდუმლოებს და იდენტობის ტოკენებს ფორკებიდან გახსნილი pull request-ებისთვის, ამიტომ ეს გაშვებები დაფარვას არ ატყობინებენ. შერწყმის შემდეგ, კომიტი თქვენს ბრენჩზე რბის კრედენციალებით და ატყობინებს თავის დაფარვას ჩვეულებრივად.

## დაფარვის მოთხოვნა {#querying}

დაფის **კოდის დაფარვის** გვერდი აჩვენებს თითოეული კომიტის მაჩვენებელს, მის აპლიკაციებს და ფაილებს, თითოეული გაშვების დაფარული ხაზებით. იგივე მონაცემები ხელმისაწვდომია აგენტებისთვის <.localized_link href="/guides/features/agentic-coding/mcp">Model Context Protocol სერვერის</.localized_link> მეშვეობით.
