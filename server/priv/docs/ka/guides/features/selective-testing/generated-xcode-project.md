# გენერირებული Xcode-პროექტი {#generated-xcode-project}

როგორც იზრდება თქვენი პროექტი, ისე იზრდება ტესტების რაოდენობაც. დიდი ხნის განმავლობაში ყოველ PR-ზე ან `main`-ში push-ისას ყველა ტესტის გაშვებას ათეულობით წამი სჭირდებოდა. მაგრამ ეს მიდგომა არ მასშტაბირდება ათასობით ტესტზე, რომელიც შეიძლება ჰქონდეს თქვენს გუნდს.

CI-ზე ტესტების ყოველი გაშვებისას, ცვლილებების მიუხედავად, სავარაუდოდ, ყველა ტესტს ხელახლა აკეთებთ. Tuist-ის შერჩევითი ტესტირება გეხმარებათ ტესტების შესრულების დრო მნიშვნელოვნად შეამციროთ, რადგან ის მხოლოდ იმ ტესტებს ასრულებს, რომლებიც ბოლო წარმატებული ტესტების გაშვების შემდეგ შეიცვალა ჩვენი <.localized_link href="/guides/features/projects/hashing">ჰეშირების ალგორითმის</.localized_link> საფუძველზე.

ტესტების შერჩევითად გასაშვებად თქვენს <.localized_link href="/guides/features/projects">გენერირებულ პროექტთან</.localized_link> ერთად, გამოიყენეთ ბრძანება `tuist test`. ეს ბრძანება თქვენს პროექტს <.localized_link href="/guides/features/projects/hashing">ჰეშირებს</.localized_link> იმავე გზით, როგორც ამას <.localized_link href="/guides/features/cache/module-cache">მოდულის ქეშისთვის</.localized_link> აკეთებს და წარმატების შემთხვევაში ინახავს ჰეშებს, რათა მომავალ გაშვებებში განსაზღვროს, რა შეიცვალა. მომავალ გაშვებებში `tuist test` გამჭვირვალედ იყენებს ჰეშებს ტესტების ფილტრაციისთვის და ასრულებს მხოლოდ მათ, რომლებიც ბოლო წარმატებული ტესტების გაშვების შემდეგ შეიცვალა.

`tuist test` პირდაპირ ინტეგრირდება <.localized_link href="/guides/features/cache/module-cache">მოდულის ქეშთან</.localized_link>, რათა გამოიყენოს მაქსიმალური რაოდენობის ბინარები თქვენი ლოკალური ან დისტანციური საცავიდან და გააუმჯობესოს აწყობის დრო თქვენი ტესტების ნაკრების გაშვებისას. შერჩევითი ტესტირებისა და მოდულის ქეშირების კომბინაციამ შეიძლება მნიშვნელოვნად შეამციროს დრო, რომელიც სჭირდება ტესტების გაშვებას თქვენს CI-ზე.

თუ თქვენი ტესტები მხოლოდ სიმულატორებს ისახავენ სამიზნედ, გადაეცით `--destination simulator`, რათა `tuist test` იყენებდეს და ჩამოტვირთავდეს მხოლოდ ქეშირებული ბინარების სიმულატორის ნაწილებს. იხილეთ <.localized_link href="/guides/features/cache/module-cache#destination-selection">დანიშნულების არჩევა</.localized_link>. შერჩევითი ტესტირების ჰეშები ერთნაირია `--destination`-ის ყოველი მნიშვნელობისთვის.

## ბილდისა და ტესტების ცალკეული ჯობები {#separate-build-and-test-jobs}

შერჩევითი ტესტირება უჭერს მხარს ბილდისა და ტესტების ცალკეულ ჯობებს. ბილდის ჯობაში გაუშვით `tuist test --build-only`, რათა Tuist-მა შეინახოს `selective-testing-graph.json` ფაილი ბილდის მიერ გამოცემული პროდუქტების გვერდით. ეს გრაფი შეიცავს ჰეშებს, რომლებიც საჭიროა შერჩევითი ტესტირებისთვის, ამიტომ ტესტების ჯობას არ სჭირდება პროექტის ხელახლა გენერირება ან Swift Package დამოკიდებულებების გადაწყვეტა იმის დასადგენად, თუ რომელი სამიზნეები უნდა გაუშვას.

Tuist წერს გრაფს ორ ადგილას `--build-only`-ის დროს:

- `.xctestproducts` ბანდლის შიგნით, როდესაც გადასცემთ `-testProductsPath`.
- ყოველი `.xctestrun` ფაილის გვერდით derived data-ს `Build/Products/` დირექტორიაში.

ქეშირეთ ნებისმიერი გამომავალი ბილდის პროდუქტების გვერდით და გადაეცით იგივე გზა `--without-building`-ს ტესტების ჯობაში. ორივე ფორმა მუშაობს:

```sh
# Build job — writes an .xctestproducts bundle with the graph inside it.
tuist test MyScheme \
  --build-only \
  -- \
  -testProductsPath artifacts/MyScheme.xctestproducts \
  -destination 'platform=iOS Simulator,id=SIMULATOR_IDENTIFIER'

# Test job — restores the same bundle.
tuist test MyScheme \
  --without-building \
  -- \
  -testProductsPath artifacts/MyScheme.xctestproducts \
  -destination 'platform=iOS Simulator,id=SIMULATOR_IDENTIFIER'
```

```sh
# Build job — writes the graph as a sibling of each xctestrun in derived data.
tuist test MyScheme \
  --build-only \
  --derived-data-path artifacts/derived-data

# Test job — points --without-building at any of those xctestrun files.
tuist test MyScheme \
  --without-building \
  --derived-data-path artifacts/derived-data \
  -- \
  -destination 'platform=iOS Simulator,id=SIMULATOR_IDENTIFIER' \
  -xctestrun artifacts/derived-data/Build/Products/MyScheme_iphonesimulator.xctestrun
```

როდესაც Tuist ვერ პოულობს იმ გრაფს შეყვანის გვერდით (მაგალითად, როდესაც ბილდის ჯობამ გამოიყენა ჩვეულებრივი `xcodebuild build-for-testing` ნაცვლად `tuist test --build-only`-ის), ის ბრუნდება პროექტის ხელახლა გენერირებაზე, რათა მაინც გამოთვალოს დაზარალებული სამიზნეები. ამ ალტერნატიულ მიდგომას სჭირდება Swift Package დამოკიდებულებების გადაწყვეტა ტესტების ჯობაზე, ამიტომ ჯერ გაუშვით `tuist install` ან დააკეშირეთ `Tuist/.build` ჯობებს შორის.

გრაფი ასახავს წყაროს ხეს ისე, როგორც ის იყო ბილდის დროს. ტესტების ჯობა გაუშვით იმავე კომიტზე, რაზეც ბილდის ჯობა — თუ წყარო გადაიხარა ამ ორს შორის, ჰეშები მოძველდება და შერჩევითმა ტესტირებამ შეიძლება გამოტოვოს ტესტები, რომლებიც რეალურად ჩავარდებოდნენ უფრო ახალ წყაროსთან.

### რომელი ფლაგი უნდა გამოვიყენო? {#which-flag-should-i-use}

`.xctestrun` და `.xctestproducts` არის Xcode-ის ორი განსხვავებული გამომავალი ფორმატი და ისინი აბალანსებენ პორტაბელურობას პაიპლაინის მოხერხებულობის წინააღმდეგ:

- **`-testProductsPath` (`.xctestproducts`) — რეკომენდებულია ახალი პაიპლაინებისთვის.** ეს არის თვითშემცველი დირექტორია: აგებული `.xctest` ბინარები და მათი `.xctestrun` ფაილები ცხოვრობენ მის შიგნით ისე, რომ ბილიკები შეფარდებითია ბანდლის ფესვთან, ამიტომ ის რჩება ვალიდური ნებისმიერ ადგილას. ეს ასევე არის ფორმატი, რომელსაც ყველაზე დიდი ხანია აქვს შერჩევითი ტესტირების სწრაფი გზა, ამიტომ ის არის ყველაზე მეტად გამოცდილი გზა.
- **`-xctestrun` (ნედლი `.xctestrun`) — გამოიყენეთ, თუ უკვე გაქვთ პაიპლაინი, აგებული derived data-ს გარშემო.** `xcodebuild build-for-testing` წერს `.xctestrun`-ს `<derivedData>/Build/Products/`-ის თავში ნაგულისხმევად და მიუთითებს ტესტების ბანდლებზე, რომლებიც ცხოვრობენ ამ ხის სხვა ადგილას. მისი ხელახლა გამოყენება სხვა ჯობაში ნიშნავს ბილიკების შენარჩუნებას `Build/Products/`-ში.

თუ ახალს იწყებთ, არჩიეთ `-testProductsPath`. თუ Tuist-ს აკავშირებთ არსებულ პაიპლაინთან, რომელიც უკვე აკეშირებს derived data-ს, `-xctestrun` ახლა მიიღებს იმავე სწრაფ გზას, იმ პირობით, რომ ბილდის ჯობა გადის `tuist test --build-only`-ით.

ნებისმიერი შეყვანის რეჟიმი ურთიერთგამომრიცხავია `-workspace`/`-project`/`-scheme`-თან, ამიტომ Tuist ტოვებს ამ ფლაგებს, როდესაც პასსრაუთ არგუმენტები შეიცავს `-xctestrun` ან `-testProductsPath`-ს, და გადასცემს შერჩეულ სამიზნეებს `-only-testing`-ით.

> [!WARNING]
> **მოდულის versus ფაილის დონის გრანულარობა**
>
> კოდში ტესტებსა და წყაროებს შორის დამოკიდებულებების აღმოჩენის შეუძლებლობის გამო, შერჩევითი ტესტირების მაქსიმალური გრანულარობა არის სამიზნის დონეზე. ამიტომ, ჩვენ გირჩევთ, თქვენი სამიზნეები იყოს მცირე და ფოკუსირებული, რათა მაქსიმალურად გაზარდოთ შერჩევითი ტესტირების სარგებელი.


> [!NOTE]
> **ტესტების დაფარვა**
>
> კოდის დაფარვის (coverage) ხელსაწყოები, რომლებიც კითხულობენ ერთი გაშვების ანგარიშს, Xcode-ის ჩათვლით, ვარაუდობენ, რომ მთლიანი ტესტების ნაკრები შესრულდა, ამიტომ შერჩევითი გაშვების ანგარიში ტოვებს გამოტოვებულ ტესტებს. Tuist-ის <.localized_link href="/guides/features/test-code-coverage/generated-xcode-project">კოდის დაფარვა</.localized_link> კი გადააქვს გამოტოვებული ტესტის სამიზნეების დაფარვა წინა გაშვებიდან, იყენებს რა <.localized_link href="/guides/features/test-code-coverage/generated-xcode-project#target-level-coverage">სამიზნე-დონის დაფარვას</.localized_link>, რომელსაც ის ყოველ გაშვებაზე იწერს.

## გამოტოვებების კვლევა დაშბორდზე {#investigating-misses-on-the-dashboard}

როდესაც ადრე ქეშირებული ტესტის სამიზნე გამოჩნდება როგორც გამოტოვებული (miss), ტესტების გაშვების გვერდზე არსებული **შერჩევითი ტესტირება** ჩანართი საშუალებას გაძლევთ ჩაუღრმავდეთ იმ შეყვანებს, რომლებმაც წარმოქმნეს ჰეში. სტრიქონის გაშლა აჩვენებს კომპონენტურ ქვეჰეშებს — წყაროებს, დამოკიდებულებებს, გარემოს ცვლადებს, პროექტისა და სამიზნის პარამეტრებს, Info.plist-ს, უფლებებს, ჰედერებს და ა.შ., რათა ზუსტად განსაზღვროთ შეყვანა, რომელიც შეიცვალა გაშვებებს შორის.

გამოიყენეთ ღილაკი **JSON-ად კოპირება** შერჩევითი ტესტირების ბარათის თავში, რათა ექსპორტირდეს ყოველი შერჩევითი ტესტირების სამიზნე თავისი ჰეშითა და სუბჰეშებით. JSON-ის შედარება ორ გაშვებას შორის არის ყველაზე სწრაფი გზა იმის დასადასტურებლად, თუ რომელი შეყვანა შეიცვალა, როდესაც ტესტების სამიზნის ჰეში გადაიხარა.
