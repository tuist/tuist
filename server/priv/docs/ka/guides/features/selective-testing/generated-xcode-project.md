# გენერირებული Xcode-პროექტი {#generated-xcode-project}

როგორც იზრდება თქვენი პროექტი, ისევე იზრდება ტესტების რაოდენობაც. დიდი ხნის განმავლობაში ყველა ტესტის გაშვება ყოველ PR-ზე ან `main`-ში push-ზე ათეულობით წამს იღებდა. მაგრამ ეს მიდგომა არ მასშტაბირდება თქვენი გუნდის შესაძლო ათასობით ტესტზე.

CI-ზე ყოველი ტესტების გაშვებისას, ცვლილებების მიუხედავად, სავარაუდოდ, ყველა ტესტს ხელახლა აკეთებთ. Tuist-ის შერჩევითი ტესტირება გეხმარებათ ტესტების შესრულების დრო მნიშვნელოვნად შეამციროთ, რადგან ის მხოლოდ იმ ტესტებს ასრულებს, რომლებიც ბოლო წარმატებული <.localized_link href="/guides/features/projects/hashing">ჰეშირების ალგორითმის</.localized_link> საფუძველზე შეიცვალა.

ტესტების შერჩევითად გასაშვებად თქვენს <.localized_link href="/guides/features/projects">გენერირებულ პროექტთან</.localized_link>, გამოიყენეთ ბრძანება `tuist test`. ბრძანება <.localized_link href="/guides/features/projects/hashing">ჰეშავს</.localized_link> თქვენს პროექტს იმავე გზით, როგორც <.localized_link href="/guides/features/cache/module-cache">მოდულის ქეშისთვის</.localized_link>, და წარმატების შემთხვევაში ინახავს ჰეშებს, რათა მომავალ გაშვებებში დაადგინოს, რა შეიცვალა. მომავალ გაშვებებში, `tuist test` გამჭვირვალედ იყენებს ჰეშებს ტესტების ფილტრაციისთვის და უშვებს მხოლოდ იმას, რაც შეიცვალა ბოლო წარმატებული ტესტების გაშვებიდან.

`tuist test` პირდაპირ ინტეგრირდება <.localized_link href="/guides/features/cache/module-cache">მოდულის ქეშთან</.localized_link>, რათა გამოიყენოს რაც შეიძლება მეტი ბინარი თქვენი ადგილობრივი ან დაშორებული საცავიდან და გააუმჯობესოს ბილდის დრო თქვენი ტესტების ნაკრების გაშვებისას. შერჩევითი ტესტირებისა და მოდულების ქეშირების კომბინაციამ შეიძლება მკვეთრად შეამციროს დრო, რომელიც სჭირდება ტესტების გაშვებას თქვენს CI-ზე.

## ბილდისა და ტესტების ცალკეული სამუშაოები {#separate-build-and-test-jobs}

შერჩევითი ტესტირება მხარს უჭერს ბილდისა და ტესტების ცალკეულ სამუშაოებს. გაუშვით `tuist test --build-only` ბილდის სამუშაოში, რათა Tuist-მა შეინახოს ფაილი `selective-testing-graph.json` ბილდის მიერ გამოშვებულ პროდუქტებთან ერთად. ეს გრაფი შეიცავს ჰეშებს, რომლებიც საჭიროა შერჩევითი ტესტირებისთვის, ამიტომ ტესტების სამუშაოს არ სჭირდება პროექტის ხელახლა გენერირება ან Swift Package-ის დამოკიდებულებების გადაწყვეტა იმის დასადგენად, თუ რომელი სამიზნეები უნდა გაეშვას.

Tuist წერს გრაფს ორ ადგილას `--build-only`-ის დროს:

- `.xctestproducts` ბანდლის შიგნით, როდესაც გადასცემთ `-testProductsPath`.
- ყოველი `.xctestrun` ფაილის გვერდით derived data-ს `Build/Products/` დირექტორიაში.

შეინახეთ ნებისმიერი გამომავალი მონაცემი აგებულ პროდუქტებთან ერთად და გადაეცით იგივე გზა `--without-building`-ს ტესტების სამუშაოში. ორივე ფორმა მუშაობს:

```sh
# Build job — writes an .xctestproducts bundle with the graph inside it.
tuist test MyScheme \
  --build-only \
  -- \
  -testProductsPath artifacts/MyScheme.xctestproducts \
  -destination 'platform=iOS Simulator,id=SIMULATOR_IDENTIFIER'

# Test job — restores the same bundle.
tuist test MyScheme \
  --without-building \
  -- \
  -testProductsPath artifacts/MyScheme.xctestproducts \
  -destination 'platform=iOS Simulator,id=SIMULATOR_IDENTIFIER'
```

```sh
# Build job — writes the graph as a sibling of each xctestrun in derived data.
tuist test MyScheme \
  --build-only \
  --derived-data-path artifacts/derived-data

# Test job — points --without-building at any of those xctestrun files.
tuist test MyScheme \
  --without-building \
  --derived-data-path artifacts/derived-data \
  -- \
  -destination 'platform=iOS Simulator,id=SIMULATOR_IDENTIFIER' \
  -xctestrun artifacts/derived-data/Build/Products/MyScheme_iphonesimulator.xctestrun
```

როდესაც Tuist ვერ პოულობს ამ გრაფს შეყვანასთან (მაგალითად, როდესაც ბილდის სამუშაომ გამოიყენა ჩვეულებრივი `xcodebuild build-for-testing` ნაცვლად `tuist test --build-only`-ის), ის ბრუნდება პროექტის ხელახლა გენერირებაზე, რათა მაინც გამოთვალოს დაზარალებული სამიზნეები. ამ ალტერნატიულ გზას სჭირდება Swift Package-ის დამოკიდებულებების გადაწყვეტა ტესტების სამუშაოზე, ამიტომ ჯერ გაუშვით `tuist install` ან შეინახეთ ქეშში `Tuist/.build` სამუშაოებს შორის.

გრაფი ასახავს წყაროს ხეს ისე, როგორიც იყო ბილდის დროს. გაუშვით ტესტების სამუშაო იმავე კომიტზე, რაც ბილდის სამუშაო — თუ წყარო განსხვავდება ამ ორს შორის, ჰეშები მოძველდება და შერჩევითი ტესტირება შეიძლება გამოტოვოს ტესტები, რომლებიც რეალურად ჩავარდებოდა ახალ წყაროზე.

### რომელი ფლაგი უნდა გამოვიყენო? {#which-flag-should-i-use}

`.xctestrun` და `.xctestproducts` არის Xcode-ის ორი განსხვავებული გამომავალი ფორმატი და ისინი წონასწორობას აკეთებენ პორტატულობასა და პაიპლაინის მოხერხებულობას შორის:

- **`-testProductsPath` (`.xctestproducts`) — რეკომენდებულია ახალი პაიპლაინებისთვის.** ეს არის თვითშემცველი დირექტორია: აგებული `.xctest` ბინარები და მათი `.xctestrun` ფაილები ცხოვრობენ მის შიგნით გზებით, რომლებიც შედარებითია ბანდლის ფესტთან, ამიტომ ის რჩება ვალიდური ნებისმიერ ადგილას, სადაც აღმოჩნდება. ეს ასევე არის ფორმატი, რომელსაც ყველაზე დიდი ხანია აქვს შერჩევითი ტესტირების სწრაფი გზა, ამიტომ ის არის ყველაზე მეტად გამოცდილი გზა.
- **`-xctestrun` (ნედლი `.xctestrun`) — გამოიყენეთ, თუ უკვე გაქვთ პაიპლაინი, აგებული derived data-ს გარშემო.** `xcodebuild build-for-testing` წერს `.xctestrun`-ს `<derivedData>/Build/Products/`-ის თავში ნაგულისხმევად და მიმართავს მას ტესტების ბანდლებზე, რომლებიც ცხოვრობენ ამ ხის სხვა ადგილას. მისი ხელახლა გამოყენება სხვა სამუშაოში ნიშნავს გზების შენარჩუნებას `Build/Products/`-ში ხელშეუხებლად.

თუ ახალს იწყებთ, უპირატესობა მიანიჭეთ `-testProductsPath`-ს. თუ Tuist-ს აერთებთ არსებულ პაიპლაინში, რომელიც უკვე აქეშებს derived data-ს, `-xctestrun` ახლა მიიღებს იმავე სწრაფ გზას, სანამ ბილდის სამუშაო გაივლის `tuist test --build-only`-ს.

ნებისმიერი შეყვანის რეჟიმია ურთიერთგამომრიცხავი `-workspace`/`-project`/`-scheme`-თან, ამიტომ Tuist ტოვებს ამ ფლაგებს, როდესაც passthrough არგუმენტები შეიცავს `-xctestrun`-ს ან `-testProductsPath`-ს, და გადასცემს შერჩეულ სამიზნეებს `-only-testing`-ის საშუალებით.

> [!WARNING]
> **მოდულის vs ფაილის დონის გრანულარობა**
>
> ტესტებსა და წყაროებს შორის კოდში არსებული დამოკიდებულებების აღმოჩენის შეუძლებლობის გამო, შერჩევითი ტესტირების მაქსიმალური გრანულარობა არის სამიზნის დონეზე. ამიტომ, ჩვენ გირჩევთ, რომ თქვენი სამიზნეები იყოს მცირე და ფოკუსირებული, რათა მაქსიმალურად გაზარდოთ შერჩევითი ტესტირების სარგებელი.


> [!WARNING]
> **ტესტების დაფარვა**
>
> ტესტების დაფარვის ინსტრუმენტები ვარაუდობენ, რომ მთლიანი ტესტების ნაკრები ერთდროულად ეშვება, რაც მათ შეუთავსებელს ხდის შერჩევით ტესტების გაშვებებთან — ეს ნიშნავს, რომ დაფარვის მონაცემები შეიძლება არ ასახავდეს რეალობას ტესტების შერჩევის გამოყენებისას. ეს არის ცნობილი შეზღუდვა და არ ნიშნავს, რომ რაიმეს არასწორად აკეთებთ. ჩვენ ვურჩევთ გუნდებს, დაფიქრდნენ, თუ რამდენად მოაქვს დაფარვას კვლავ მნიშვნელოვანი insights ამ კონტექსტში, და თუ მოაქვს, დარწმუნებულნი იყავით, რომ ჩვენ უკვე ვფიქრობთ იმაზე, თუ როგორ გავხადოთ დაფარვა სწორად მომუშავე შერჩევით გაშვებებთან მომავალში.

## გამოტოვებების კვლევა დაშბორდზე {#investigating-misses-on-the-dashboard}

როდესაც ადრე ქეშირებული ტესტის სამიზნე ჩანს, როგორც გამოტოვება, ტესტების გაშვების გვერდზე \*\***შერჩევითი ტესტირება**\*\* ჩანართი საშუალებას გაძლევთ ჩაუღრმავდეთ იმ შეყვანებს, რომლებმაც წარმოქმნეს ჰეში. რიგის გაფართოება აჩენს კომპონენტურ სუბჰეშებს — წყაროებს, დამოკიდებულებებს, გარემოს ცვლადებს, პროექტისა და სამიზნის პარამეტრებს, Info.plist-ს, entitlements-ებს, ჰედერებს და ა.შ. — რათა ზუსტად დაადგინოთ შეყვანა, რომელიც შეიცვალა გაშვებებს შორის.

გამოიყენეთ ღილაკი **JSON-ად კოპირება** შერჩევითი ტესტირების ბარათის ზედა ნაწილში, რათა ექსპორტიროთ ყოველი შერჩევითი ტესტირების სამიზნე მისი ჰეშითა და სუბჰეშებით.
