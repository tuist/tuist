# გენერირებული Xcode პროექტი {#generated-xcode-project}

როგორც იზრდება თქვენი პროექტი, ისევე იზრდება ტესტების რაოდენობაც. დიდი ხნის განმავლობაში ყველა ტესტის გაშვება ყოველ PR-ზე ან `main`-ში push-ისას ათეულობით წამს იღებდა. მაგრამ ეს გადაწყვეტა ვერ მასშტაბდება თქვენი გუნდის შესაძლო ათასობით ტესტზე.

CI-ზე ყოველი ტესტების გაშვებისას, ცვლილებების მიუხედავად, სავარაუდოდ, ყველა ტესტს ხელახლა აკეთებთ. Tuist-ის შერჩევითი ტესტირება გეხმარებათ ტესტების შესრულების დრო მნიშვნელოვნად შეამციროთ იმ ტესტების გაშვებით, რომლებიც ბოლო წარმატებული ტესტების გაშვების შემდეგ შეიცვალა ჩვენი <.localized_link href="/guides/features/projects/hashing">ჰეშირების ალგორითმის</.localized_link> საფუძველზე.

ტესტების შერჩევითად გასაშვებად თქვენს <.localized_link href="/guides/features/projects">გენერირებულ პროექტთან</.localized_link> ერთად, გამოიყენეთ `tuist test` ბრძანება. ბრძანება თქვენს პროექტს <.localized_link href="/guides/features/projects/hashing">ჰეშავებს</.localized_link> ისევე, როგორც <.localized_link href="/guides/features/cache/module-cache">მოდულის ქეშისთვის</.localized_link>, და წარმატების შემთხვევაში ინახავს ჰეშებს, რათა მომავალ გაშვებებში განსაზღვროს, რა შეიცვალა. მომავალ გაშვებებში, `tuist test` გამჭვირვალედ იყენებს ჰეშებს ტესტების ფილტრაციისთვის და მხოლოდ იმ ტესტებს აკეთებს, რომლებიც ბოლო წარმატებული ტესტების გაშვების შემდეგ შეიცვალა.

`tuist test` პირდაპირ ინტეგრირდება <.localized_link href="/guides/features/cache/module-cache">მოდულის ქეშთან</.localized_link>, რათა გამოიყენოს მაქსიმალურად ბინარები თქვენი ადგილობრივი ან დისტანციური საცავიდან და გააუმჯობესოს აწყობის დრო თქვენი ტესტების ნაკრების გაშვებისას. შერჩევითი ტესტირებისა და მოდულის ქეშირების კომბინაციამ შეიძლება მნიშვნელოვნად შეამციროს დრო, რომელიც სჭირდება ტესტების გაშვებას თქვენს CI-ზე.

## აგებისა და ტესტირების ცალკეული სამუშაოები {#separate-build-and-test-jobs}

შერჩევითი ტესტირება მხარდაჭერილია აგებისა და ტესტირების ცალკეული სამუშაოებით. აგების სამუშაოში გაუშვით `tuist test --build-only`, რათა Tuist-მა შეინახოს ფაილი `selective-testing-graph.json` აგების მიერ გამოშვებულ პროდუქტებთან ერთად. ეს გრაფი შეიცავს ჰეშებს, რომლებიც საჭიროა შერჩევითი ტესტირებისთვის, ამიტომ ტესტირების სამუშაოს არ სჭირდება პროექტის ხელახლა გენერირება ან Swift Package დამოკიდებულებების გადაწყვეტა იმის დასადგენად, თუ რომელი სამიზნეები უნდა გაეშვას.

Tuist წერს გრაფს ორ ადგილას `--build-only`-ის დროს:

- `.xctestproducts` ბანდლის შიგნით, როდესაც გადასცემთ `-testProductsPath`.
- ყოველი `.xctestrun` ფაილის გვერდით წარმოებული მონაცემების `Build/Products/` დირექტორიაში.

დააქეშეთ ნებისმიერი გამომავალი აგებულ პროდუქტებთან ერთად და გადასცით იგივე გზა `--without-building`-ს ტესტირების სამუშაოში. ორივე ფორმა მუშაობს:

```sh
# Build job — writes an .xctestproducts bundle with the graph inside it.
tuist test MyScheme \
  --build-only \
  -- \
  -testProductsPath artifacts/MyScheme.xctestproducts \
  -destination 'platform=iOS Simulator,id=SIMULATOR_IDENTIFIER'

# Test job — restores the same bundle.
tuist test MyScheme \
  --without-building \
  -- \
  -testProductsPath artifacts/MyScheme.xctestproducts \
  -destination 'platform=iOS Simulator,id=SIMULATOR_IDENTIFIER'
```

```sh
# Build job — writes the graph as a sibling of each xctestrun in derived data.
tuist test MyScheme \
  --build-only \
  --derived-data-path artifacts/derived-data

# Test job — points --without-building at any of those xctestrun files.
tuist test MyScheme \
  --without-building \
  --derived-data-path artifacts/derived-data \
  -- \
  -destination 'platform=iOS Simulator,id=SIMULATOR_IDENTIFIER' \
  -xctestrun artifacts/derived-data/Build/Products/MyScheme_iphonesimulator.xctestrun
```

როდესაც Tuist ვერ პოულობს ამ გრაფს შეყვანასთან (მაგალითად, როდესაც აგების სამუშაომ გამოიყენა ჩვეულებრივი `xcodebuild build-for-testing` ნაცვლად `tuist test --build-only`-ის), ის ბრუნდება პროექტის ხელახლა გენერირებაზე, რათა მაინც გამოთვალოს დაზარალებული სამიზნეები. ამ ალტერნატივას სჭირდება Swift Package დამოკიდებულებების გადაწყვეტა ტესტირების სამუშაოზე, ამიტომ ჯერ გაუშვით `tuist install` ან დააქეშეთ `Tuist/.build` სამუშაოებს შორის.

გრაფი ასახავს წყაროს ხეს ისე, როგორიც ის იყო აგების დროს. გაუშვით ტესტირების სამუშაო იმავე კომიტზე, რაზეც აგების სამუშაო — თუ წყარო გადაიხრება ორს შორის, ჰეშები მოძველდება და შერჩევითმა ტესტირებამ შეიძლება გამოტოვოს ტესტები, რომლებიც რეალურად ჩავარდებოდა უფრო ახალ წყაროსთან.

### რომელი ფლაგი უნდა გამოვიყენო? {#which-flag-should-i-use}

`.xctestrun` და `.xctestproducts` არის Xcode-ის ორი განსხვავებული გამომავალი ფორმატი და ისინი წონასწორობას ქმნიან პორტატულობასა და პაიპლაინის მოხერხებულობას შორის:

- **`-testProductsPath` (`.xctestproducts`) — რეკომენდებულია ახალი პაიპლაინებისთვის.** ეს არის თვითკმარი დირექტორია: აგებული `.xctest` ბინარები და მათი `.xctestrun` ფაილები ცხოვრობენ მის შიგნით გზებით, რომლებიც შეფარდებულია ბანდლის ფესვთან, ამიტომ ის რჩება ვალიდური, სადაცაც არ უნდა აღმოჩნდეს. ეს ასევე არის ფორმატი, რომელსაც ყველაზე დიდი ხანია აქვს შერჩევითი ტესტირების სწრაფი გზა, ამიტომ ის არის ყველაზე მეტად გამოცდილი გზა.
- **`-xctestrun` (ნედლი `.xctestrun`) — გამოიყენეთ, თუ უკვე გაქვთ პაიპლაინი, აგებული წარმოებული მონაცემების გარშემო.** `xcodebuild build-for-testing` წერს `.xctestrun`-ს `<derivedData>/Build/Products/`-ის თავში ნაგულისხმევად და მიუთითებს სატესტო ბანდლებზე, რომლებიც ცხოვრობენ ამ ხის სხვა ადგილას. მისი ხელახლა გამოყენება სხვა სამუშაოში ნიშნავს გზების შენარჩუნებას `Build/Products/`-ში უცვლელად.

თუ ახალს იწყებთ, უპირატესობა მიანიჭეთ `-testProductsPath`-ს. თუ Tuist-ს აერთებთ არსებულ პაიპლაინში, რომელიც უკვე აქეშებს წარმოებულ მონაცემებს, `-xctestrun` ახლა მიიღებს იმავე სწრაფ გზას, სანამ აგების სამუშაო გადის `tuist test --build-only`-ით.

ნებისმიერი შეყვანის რეჟიმია ურთიერთგამომრიცხავი `-workspace`/`-project`/`-scheme`-თან, ამიტომ Tuist ტოვებს ამ ფლაგებს, როდესაც გადაცემული არგუმენტები შეიცავს `-xctestrun`-ს ან `-testProductsPath`-ს, და გადასცემს შერჩეულ სამიზნეებს `-only-testing`-ით.

> [!WARNING]
> **მოდულის Vs ფაილის დონის გრანულარობა**
>
> ტესტებსა და წყაროებს შორის კოდში არსებული დამოკიდებულებების აღმოჩენის შეუძლებლობის გამო, შერჩევითი ტესტირების მაქსიმალური გრანულარობა არის სამიზნის დონეზე. ამიტომ, ჩვენ გირჩევთ, თქვენი სამიზნეები იყოს მცირე და ფოკუსირებული, რათა მაქსიმალურად გაიზარდოს შერჩევითი ტესტირების სარგებელი.


> [!WARNING]
> **ტესტების დაფარვა**
>
> ტესტების დაფარვის ინსტრუმენტები ვარაუდობენ, რომ მთელი სატესტო ნაკრები ერთდროულად ეშვება, რაც მათ შეუთავსებელს ხდის შერჩევით ტესტებთან—ეს ნიშნავს, რომ დაფარვის მონაცემები შეიძლება არ ასახავდეს რეალობას ტესტების შერჩევის გამოყენებისას. ეს არის ცნობილი შეზღუდვა და არ ნიშნავს, რომ რაიმე არასწორად აკეთებთ. ჩვენ ვურჩევთ გუნდებს, დაფიქრდნენ, არის თუ არა დაფარვა კვლავ მნიშვნელოვანი ინსაიტების მომტანი ამ კონტექსტში, და თუ არის, დარწმუნდით, რომ ჩვენ უკვე ვფიქრობთ იმაზე, თუ როგორ გავაკეთოთ დაფარვა სწორად შერჩევით გაშვებებთან მომავალში.

## გამოტოვებების კვლევა დაშბორდზე {#investigating-misses-on-the-dashboard}

როდესაც ადრე დაქეშებული სატესტო სამიზნე ჩანს როგორც გამოტოვება, ტესტების გაშვების გვერდზე **შერჩევითი ტესტირების** ჩანართი საშუალებას გაძლევთ ჩაუღრმავდეთ შეყვანებს, რომლებმაც წარმოქმნეს ჰეში. რიგის გაფართოება აჩვენებს კომპონენტების მიხედვით სუბჰეშებს — წყაროები, დამოკიდებულებები, გარემოს ცვლადები, პროექტისა და სამიზნის პარამეტრები, Info.plist, უფლებები, ჰედერები და ა.შ. — რათა შეძლოთ იმ შეყვანის ზუსტად დადგენა, რომელიც გადაიხარა გაშვებებს შორის.

გამოიყენეთ **კოპირება JSON-ად** ღილაკი შერჩევითი ტესტირების ბარათის ზედა ნაწილში, რათა გაიტანოთ ყოველი შერჩევითი ტესტირების სამიზნე მისი ჰეშითა და სუბჰეშებით.
