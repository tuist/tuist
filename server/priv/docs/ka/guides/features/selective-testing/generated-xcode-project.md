# გენერირებული Xcode პროექტი {#generated-xcode-project}

როდესაც პროექტი იზრდება, ყოველ პუშზე ყველა ტესტის გაშვება აღარ მასშტაბირდება. Tuist-ის შერჩევითი ტესტირება აწარმოებს მხოლოდ იმ ტესტებს, რომელთა სამიზნეებიც შეიცვალა ბოლო წარმატებული ტესტების გაშვების შემდეგ, Tuist-ის <.localized_link href="/guides/features/projects/hashing">ჰეშირების ალგორითმის</.localized_link> საფუძველზე.

შერჩევითად ტესტების გასაშვებად თქვენს <.localized_link href="/guides/features/projects">გენერირებულ პროექტთან</.localized_link> ერთად, გამოიყენეთ `tuist test` ბრძანება. ეს ბრძანება თქვენს პროექტს <.localized_link href="/guides/features/projects/hashing">აჰეშირებს</.localized_link> ისევე, როგორც <.localized_link href="/guides/features/cache/module-cache">მოდულის ქეშისთვის</.localized_link>, და წარმატების შემთხვევაში ინახავს ჰეშებს, რათა მომავალ გაშვებებში განსაზღვროს, რა შეიცვალა. მომავალ გაშვებებში, `tuist test` გამჭვირვალედ იყენებს ჰეშებს ტესტების ფილტრაციისთვის და აწარმოებს მხოლოდ მათ, რომლებიც შეიცვალა ბოლო წარმატებული ტესტების გაშვების შემდეგ.

`tuist test` პირდაპირ ინტეგრირდება <.localized_link href="/guides/features/cache/module-cache">მოდულის ქეშთან</.localized_link>, რათა გამოიყენოს მაქსიმალური რაოდენობის ბინარული ფაილები თქვენი ადგილობრივი ან დისტანციური საცავიდან და გააუმჯობესოს აგების დრო თქვენი ტესტების სუიტის გაშვებისას. შერჩევითი ტესტირებისა და მოდულების ქეშირების კომბინაციამ შეიძლება მნიშვნელოვნად შეამციროს დრო, რომელიც სჭირდება ტესტების გაშვებას თქვენს CI-ზე.

თუ თქვენი ტესტები მხოლოდ სიმულატორის სამიზნეებს ეხება, გადაეცით `--destination simulator`, რათა `tuist test` გამოიყენოს და ჩამოტვირთოს მხოლოდ ქეშირებული ბინარული ფაილების სიმულატორის ნაწილები. იხილეთ <.localized_link href="/guides/features/cache/module-cache#destination-selection">დანიშნულების არჩევა</.localized_link>. შერჩევითი ტესტირების ჰეშები ერთნაირია ნებისმიერი `--destination` მნიშვნელობისთვის.

## აგებისა და ტესტირების ცალკეული სამუშაოები {#separate-build-and-test-jobs}

შერჩევითი ტესტირება მხარდაჭერს აგებისა და ტესტირების ცალკეულ სამუშაოებს. გაუშვით `tuist test --build-only` აგების სამუშაოში, რათა Tuist-მა შეინახოს `selective-testing-graph.json` ფაილი აგების მიერ გენერირებული პროდუქტების გვერდით. ეს გრაფი შეიცავს ჰეშებს, რომლებიც საჭიროა შერჩევითი ტესტირებისთვის, რათა ტესტირების სამუშაოს არ დასჭირდეს პროექტის ხელახლა გენერირება ან Swift Package დამოკიდებულებების ამოხსნა იმის დასადგენად, თუ რომელი სამიზნეები უნდა გაეშვას.

Tuist წერს გრაფს ორ ადგილას `--build-only`-ის დროს:

- `.xctestproducts` ბანდლის შიგნით, როდესაც გადასცემთ `-testProductsPath`-ს.
- ყოველი `.xctestrun` ფაილის გვერდით წარმოებული მონაცემების `Build/Products/` დირექტორიაში.

შეინახეთ ნებისმიერი გამომავალი მონაცემი აგებულ პროდუქტებთან ერთად და გადაეცით იგივე გზა `--without-building`-ს ტესტირების სამუშაოში. ორივე ფორმა მუშაობს:

```sh
# Build job — writes an .xctestproducts bundle with the graph inside it.
tuist test MyScheme \
  --build-only \
  -- \
  -testProductsPath artifacts/MyScheme.xctestproducts \
  -destination 'platform=iOS Simulator,id=SIMULATOR_IDENTIFIER'

# Test job — restores the same bundle.
tuist test MyScheme \
  --without-building \
  -- \
  -testProductsPath artifacts/MyScheme.xctestproducts \
  -destination 'platform=iOS Simulator,id=SIMULATOR_IDENTIFIER'
```

```sh
# Build job — writes the graph as a sibling of each xctestrun in derived data.
tuist test MyScheme \
  --build-only \
  -- \
  -derivedDataPath artifacts/derived-data

# Test job — points --without-building at any of those xctestrun files.
tuist test MyScheme \
  --without-building \
  -- \
  -derivedDataPath artifacts/derived-data \
  -destination 'platform=iOS Simulator,id=SIMULATOR_IDENTIFIER' \
  -xctestrun artifacts/derived-data/Build/Products/MyScheme_iphonesimulator.xctestrun
```

როდესაც Tuist ვერ პოულობს ამ გრაფს შეყვანის გვერდით (მაგალითად, როდესაც აგების სამუშაომ გამოიყენა ჩვეულებრივი `xcodebuild build-for-testing` ნაცვლად `tuist test --build-only`-ის), ის ბრუნდება პროექტის ხელახლა გენერირებაზე, რათა მაინც გამოთვალოს დაზარალებული სამიზნეები. ამ ალტერნატიულ ვარიანტს სჭირდება Swift Package დამოკიდებულებების ამოხსნა ტესტირების სამუშაოზე, ამიტომ ჯერ გაუშვით `tuist install` ან შეინახეთ `Tuist/.build` ქეშში სამუშაოებს შორის.

გრაფი ასახავს წყაროს ხეს ისე, როგორიც ის იყო აგების დროს. გაუშვით ტესტირების სამუშაო იმავე კომიტზე, რაზეც აგების სამუშაო — თუ წყარო იცვლება ამ ორს შორის, ჰეშები აღარ ემთხვევა წყაროს და შერჩევითმა ტესტირებამ შეიძლება გამოტოვოს ტესტები, რომლებიც რეალურად ჩავარდებოდა ახალ წყაროსთან.

### რომელი ფლაგი უნდა გამოვიყენო? {#which-flag-should-i-use}

`.xctestrun` და `.xctestproducts` არის Xcode-ის ორი განსხვავებული გამომავალი ფორმატი და ისინი აბალანსებენ პორტაბელურობას პაიპლაინის მოხერხებულობასთან:

- **`-testProductsPath` (`.xctestproducts`) — რეკომენდებულია ახალი პაიპლაინებისთვის.** ეს არის თვითშემცველი დირექტორია: აგებული `.xctest` ბინარული ფაილები და მათი `.xctestrun` ფაილები მდებარეობენ მის შიგნით ისეთი გზებით, რომლებიც შედარებითია ბანდლის ფესვთან, რის გამოც ის ძალაში რჩება ნებისმიერ ადგილას.
- **`-xctestrun` (ნედლი `.xctestrun`) — გამოიყენეთ, თუ უკვე გაქვთ პაიპლაინი, აგებული წარმოებულ მონაცემებზე.** `xcodebuild build-for-testing` წერს `.xctestrun`-ს `<derivedData>/Build/Products/`-ის თავში ნაგულისხმევად და მიუთითებს ტესტების ბანდლებზე, რომლებიც მდებარეობენ ამ ხის სხვა ადგილას. მისი ხელახლა გამოყენება სხვა სამუშაოში ნიშნავს გზების შენარჩუნებას `Build/Products/`-ში უცვლელად.

თუ ახალი იწყებთ, უპირატესობა მიანიჭეთ `-testProductsPath`-ს. თუ Tuist-ს აკავშირებთ არსებულ პაიპლაინთან, რომელიც უკვე ინახავს წარმოებულ მონაცემებს ქეშში, `-xctestrun` იღებს იმავე სწრაფ გზას, სანამ აგების სამუშაო გადის `tuist test --build-only`-ის მეშვეობით.

ნებისმიერი შეყვანის რეჟიმი ურთიერთგამომრიცხავია `-workspace`/`-project`/`-scheme`-თან, ამიტომ Tuist ტოვებს ამ ფლაგებს, როდესაც გადამავალი არგუმენტები შეიცავს `-xctestrun`-ს ან `-testProductsPath`-ს, და გადასცემს შერჩეულ სამიზნეებს `-only-testing`-ის მეშვეობით.

> [!WARNING]
> **მოდულის vs ფაილის დონის გრანულარობა**
>
> კოდში ტესტებსა და წყაროებს შორის დამოკიდებულებების აღმოჩენის შეუძლებლობის გამო, ნაგულისხმევი შერჩევითი ტესტირების მაქსიმალური გრანულარობა არის სამიზნის დონეზე. [დაფარვის სტრატეგია](#coverage-based-test-selection) ამცირებს მას ცალკეულ XCTest ტესტებამდე. ამიტომ, ჩვენ გირჩევთ, შეინარჩუნოთ თქვენი სამიზნეები მცირე და ფოკუსირებული, რათა მაქსიმალურად გამოიყენოთ შერჩევითი ტესტირების უპირატესობები.


## დაფარვაზე დაფუძნებული ტესტების შერჩევა {#coverage-based-test-selection}

> [!NOTE]
> **ადრეული წვდომა**
>
> დაფარვაზე დაფუძნებული ტესტების შერჩევა არის ადრეული წვდომის ეტაპზე. დაგვიკავშირდით, რათა ჩავრთოთ ის თქვენს ანგარიშზე. სანამ ის ჩართული არ იქნება, სტრატეგია იქცევა როგორც ნაგულისხმევი შერჩევითი ტესტირება.

ნაგულისხმევად, შერჩევითი ტესტირება ტოვებს მთლიან ტესტების სამიზნეებს, რომელთა ჰეშიც უკვე გაიარა. `.coverage()` სტრატეგია მიდის უფრო შორს: დარჩენილ ტესტების სამიზნეებში, ის ასევე ტოვებს XCTest და XCUITest ტესტებს, რომელთა კოდის დაფარვაც წინა გაშვებაზე არ მოიცავდა არცერთ ფაილს, რომელსაც თქვენი ცვლილება შეეხო. ჩართეთ ის `Tuist.swift`-ში:

```swift
import ProjectDescription

let tuist = Tuist(
    fullHandle: "{account-handle}/{project-handle}",
    testInsights: .testInsights(
        coverage: .coverage(upload: true),
        selectiveTesting: .selectiveTesting(strategy: .coverage())
    ),
    project: .tuist()
)
```

სტრატეგია მოითხოვს:

- **დაფარვის ატვირთვებს.** Tuist ირჩევს ტესტებს იმ დაფარვის მიხედვით, რომელიც წინა გაშვებებმა ატვირთეს, ამიტომ `tuist test` ვერ ტვირთავს მანიფესტს, რომელიც აყენებს `.coverage()`-ს `upload: false`-ით.
- **[TestCoverageAttribution](https://github.com/tuist/TestCoverageAttribution) 0.3.0 ან უფრო ახალი** დაკავშირებული თქვენი ტესტების სამიზნეების მიერ. ის იწერს, თუ რომელ ფაილებს ასრულებს თითოეული ტესტი და ტოვებს ტესტებს, რომლებიც Tuist-მა არ შეარჩია. სამიზნე მის გარეშე ყოველთვის ტოვდება მთლიანად, როგორც ნაგულისხმევი.
- **ტესტების გაშვება თქვენს ნაგულისხმევ შტოზე შერჩევის გარეშე.** გაუშვით `tuist test --no-selective-testing` იქ და ნებისმიერ სხვა შტოზე, სადაც ტესტები არ უნდა გამოტოვდეს. ეს გაშვებები ასრულებენ ყველა ტესტს და ხდებიან ბაზისური ხაზები, რომლებსაც მომავალი გაშვებები ადარებენ.

სტრატეგიის ჩართვისას, `tuist test` ტოვებს სამიზნეებს, რომელთა ჰეშიც უკვე გაიარა, შემდეგ კი ეკითხება Tuist-ს, თუ რომელ ტესტებზე შეიძლება იმოქმედოს თქვენმა ცვლილებამ დარჩენილ სამიზნეებში. სამიზნეები, რომლებსაც არ აქვთ დაზარალებული ტესტი, არ აგებენ. ახალი ტესტები, ტესტები, რომლებიც ბოლოჯერ ჩავარდა, ტესტები შეცვლილ ტესტის ფაილში და ტესტები ჩაწერილი დაფარვის გარეშე ყოველთვის სრულდება. Swift Testing ტესტები სრულდება მაშინ, როდესაც მათი სამიზნე სრულდება.

## გამოტოვებების შესწავლა დაფაზე {#investigating-misses-on-the-dashboard}

როდესაც ადრე კეშირებული ტესტის სამიზნე ჩანს როგორც გამოტოვება (miss), ტესტების გაშვების გვერდზე არსებული **შერჩევითი ტესტირება** ჩანართი საშუალებას გაძლევთ ჩაუღრმავდეთ იმ შემავალ მონაცემებს, რომლებმაც ჰეში წარმოქმნეს. სტრიქონის გაშლა აჩვენებს კომპონენტების მიხედვით ქვეჰეშებს — წყაროები, დამოკიდებულებები, გარემოს ცვლადები, პროექტისა და სამიზნის პარამეტრები, Info.plist, უფლებები, ჰედერები და ა.შ. — რათა ზუსტად განსაზღვროთ შემავალი მონაცემი, რომელიც შეიცვალა გაშვებებს შორის.

გამოიყენეთ **JSON-ად კოპირება** ღილაკი შერჩევითი ტესტირების ბარათის თავში, რათა გაიტანოთ ყველა შერჩევითი ტესტირების სამიზნე მისი ჰეშითა და ქვეჰეშებით. JSON-ის შედარება ორ გაშვებას შორის არის ყველაზე სწრაფი გზა იმის დასადასტურებლად, თუ რომელი შემავალი მონაცემი შეიცვალა, როდესაც ტესტის სამიზნის ჰეში შეიცვალა.
