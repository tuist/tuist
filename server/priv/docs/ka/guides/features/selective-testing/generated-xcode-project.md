# გენერირებული Xcode პროექტი {#generated-xcode-project}

როგორც კი პროექტი იზრდება, ყოველ push-ზე ყველა ტესტის გაშვება მასშტაბურობას კარგავს. Tuist-ის შერჩევითი ტესტირება აწარმოებს მხოლოდ იმ ტესტებს, რომელთა სამიზნეები (targets) შეიცვალა ბოლო წარმატებული ტესტების გაშვების შემდეგ, Tuist-ის <.localized_link href="/guides/features/projects/hashing">ჰეშირების ალგორითმის</.localized_link> საფუძველზე.

შერჩევითი ტესტების გასაშვებად თქვენს <.localized_link href="/guides/features/projects">გენერირებულ პროექტთან</.localized_link> ერთად, გამოიყენეთ `tuist test` ბრძანება. ბრძანება <.localized_link href="/guides/features/projects/hashing">ჰეშირებს</.localized_link> თქვენს პროექტს ისევე, როგორც ამას აკეთებს <.localized_link href="/guides/features/cache/module-cache">მოდულის ქეშისთვის</.localized_link>, და წარმატების შემთხვევაში ინახავს ჰეშებს, რათა მომავალ გაშვებებში დაადგინოს, რა შეიცვალა. მომავალ გაშვებებში, `tuist test` გამჭვირვალედ იყენებს ჰეშებს ტესტების ფილტრაციისთვის და აწარმოებს მხოლოდ მათ, რომლებიც შეიცვალა ბოლო წარმატებული ტესტების გაშვების შემდეგ.

`tuist test` პირდაპირ ინტეგრირდება <.localized_link href="/guides/features/cache/module-cache">მოდულის ქეშთან</.localized_link>, რათა გამოიყენოს მაქსიმალური რაოდენობის ბინარული ფაილები თქვენი ლოკალური ან დისტანციური საცავიდან და გააუმჯობესოს აგების დრო ტესტების სუიტის გაშვებისას. შერჩევითი ტესტირებისა და მოდულის ქეშირების კომბინაციამ შეიძლება მნიშვნელოვნად შეამციროს დრო, რომელიც სჭირდება ტესტების გაშვებას თქვენს CI-ზე.

თუ თქვენი ტესტები მხოლოდ სიმულატორის სამიზნეებს ეხება, გადაეცით `--destination simulator`, რათა `tuist test` გამოიყენოს და ჩამოტვირთოს მხოლოდ ქეშირებული ბინარული ფაილების სიმულატორის ნაწილები. იხილეთ <.localized_link href="/guides/features/cache/module-cache#destination-selection">დანიშნულების ადგილის შერჩევა</.localized_link>. შერჩევითი ტესტირების ჰეშები ერთნაირია ნებისმიერი `--destination` მნიშვნელობისთვის.

## აგებისა და ტესტირების ცალკეული ჯობები {#separate-build-and-test-jobs}

შერჩევითი ტესტირება უჭერს მხარს აგებისა და ტესტირების ცალკეულ ჯობებს. გაუშვით `tuist test --build-only` აგების ჯობში, რათა Tuist-მა შეინახოს `selective-testing-graph.json` ფაილი იმ პროდუქტებთან ერთად, რომლებსაც აგება გამოიმუშავებს. ეს გრაფი შეიცავს ჰეშებს, რომლებიც საჭიროა შერჩევითი ტესტირებისთვის, რათა ტესტირების ჯობას არ დასჭირდეს პროექტის ხელახლა გენერირება ან Swift Package დამოკიდებულებების გადაწყვეტა იმის დასადგენად, თუ რომელი სამიზნეები უნდა გაეშვას.

Tuist წერს გრაფს ორ ადგილას `--build-only`-ის დროს:

- `.xctestproducts` ბანდლის შიგნით, როდესაც გადასცემთ `-testProductsPath`-ს.
- ყოველი `.xctestrun` ფაილის გვერდით derived data-ს `Build/Products/` დირექტორიაში.

შეინახეთ ნებისმიერი გამომავალი მონაცემი აგებულ პროდუქტებთან ერთად და გადაეცით იგივე გზა `--without-building`-ს ტესტირების ჯობში. ორივე ფორმა მუშაობს:

```sh
# Build job — writes an .xctestproducts bundle with the graph inside it.
tuist test MyScheme \
  --build-only \
  -- \
  -testProductsPath artifacts/MyScheme.xctestproducts \
  -destination 'platform=iOS Simulator,id=SIMULATOR_IDENTIFIER'

# Test job — restores the same bundle.
tuist test MyScheme \
  --without-building \
  -- \
  -testProductsPath artifacts/MyScheme.xctestproducts \
  -destination 'platform=iOS Simulator,id=SIMULATOR_IDENTIFIER'
```

```sh
# Build job — writes the graph as a sibling of each xctestrun in derived data.
tuist test MyScheme \
  --build-only \
  -- \
  -derivedDataPath artifacts/derived-data

# Test job — points --without-building at any of those xctestrun files.
tuist test MyScheme \
  --without-building \
  -- \
  -derivedDataPath artifacts/derived-data \
  -destination 'platform=iOS Simulator,id=SIMULATOR_IDENTIFIER' \
  -xctestrun artifacts/derived-data/Build/Products/MyScheme_iphonesimulator.xctestrun
```

როდესაც Tuist ვერ პოულობს ამ გრაფს შეყვანის მონაცემებთან ერთად (მაგალითად, როდესაც აგების ჯობამ გამოიყენა ჩვეულებრივი `xcodebuild build-for-testing` `tuist test --build-only`-ის ნაცვლად), ის ბრუნდება პროექტის ხელახლა გენერირებაზე, რათა მაინც გამოთვალოს დაზარალებული სამიზნეები. ამ ალტერნატიულ ვარიანტს სჭირდება Swift Package დამოკიდებულებების გადაწყვეტა ტესტირების ჯობზე, ამიტომ ჯერ გაუშვით `tuist install` ან შეინახეთ `Tuist/.build` ჯობებს შორის.

გრაფი ასახავს წყაროს ხეს ისეთს, როგორიც ის იყო აგების დროს. გაუშვით ტესტირების ჯობა იმავე კომიტზე, რაზეც აგების ჯობა — თუ წყარო განსხვავდება ამ ორს შორის, ჰეშები აღარ ემთხვევა წყაროს და შერჩევითი ტესტირებამ შეიძლება გამოტოვოს ტესტები, რომლებიც რეალურად ჩავარდებოდა ახალ წყაროსთან მიმართებაში.

### რომელი ფლაგი უნდა გამოვიყენო? {#which-flag-should-i-use}

`.xctestrun` და `.xctestproducts` არის Xcode-ის ორი განსხვავებული გამომავალი ფორმატი, და ისინი აბალანსებენ პორტაბელურობასა და პაიპლაინის მოხერხებულობას:

- **`-testProductsPath` (`.xctestproducts`) — რეკომენდებულია ახალი პაიპლაინებისთვის.** ეს არის თვითკმარი დირექტორია: აგებული `.xctest` ბინარული ფაილები და მათი `.xctestrun` ფაილები ინახება მის შიგნით ისეთი გზებით, რომლებიც ფარდობითია ბანდლის ფესვთან მიმართებაში, ამიტომ ის ვალიდური რჩება ნებისმიერ ადგილას.
- **`-xctestrun` (ნედლი `.xctestrun`) — გამოიყენეთ, თუ უკვე გაქვთ პაიპლაინი, აგებული derived data-ს გარშემო.** `xcodebuild build-for-testing` წერს `.xctestrun`-ს `<derivedData>/Build/Products/`-ის თავში ნაგულისხმევად და მიუთითებს ტესტ ბანდლებზე, რომლებიც ინახება ამ ხის სხვა ადგილას. მისი ხელახლა გამოყენება სხვა ჯობაში ნიშნავს გზების შენარჩუნებას `Build/Products/`-ში უცვლელად.

თუ ახალს იწყებთ, უპირატესობა მიანიჭეთ `-testProductsPath`-ს. თუ Tuist-ს აკავშირებთ არსებულ პაიპლაინთან, რომელიც უკვე აკეთებს derived data-ს ქეშირებას, `-xctestrun` იღებს იმავე სწრაფ გზას, სანამ აგების ჯობა გადის `tuist test --build-only`-ის მეშვეობით.

ნებისმიერი შეყვანის რეჟიმი ურთიერთგამომრიცხავია `-workspace`/`-project`/`-scheme`-თან, ამიტომ Tuist ტოვებს ამ ფლაგებს, როდესაც გადაცემული არგუმენტები შეიცავს `-xctestrun`-ს ან `-testProductsPath`-ს, და აწვდის შერჩეულ სამიზნეებს `-only-testing`-ის მეშვეობით.

> [!WARNING]
> **მოდულის vs ფაილის დონის გრანულარობა**
>
> ტესტებსა და წყაროებს შორის კოდში არსებული დამოკიდებულებების აღმოჩენის შეუძლებლობის გამო, ნაგულისხმევი შერჩევითი ტესტირების მაქსიმალური გრანულარობა სამიზნის დონეზეა. [დაფარვის სტრატეგია](#coverage-based-test-selection) ამცირებს მას ცალკეულ XCTest ტესტებამდე. ამიტომ, ჩვენ გირჩევთ, თქვენი სამიზნეები იყოს მცირე და ფოკუსირებული, რათა მაქსიმალურად გაზარდოთ შერჩევითი ტესტირების სარგებელი.


## დაფარვაზე დაფუძნებული ტესტების შერჩევა {#coverage-based-test-selection}

> [!NOTE]
> **ადრეული წვდომა**
>
> დაფარვაზე დაფუძნებული ტესტების შერჩევა ადრეულ წვდომაშია. დაგვიკავშირდით, რათა ჩავრთოთ ის თქვენს ანგარიშზე. სანამ ის ჩართული არ იქნება, სტრატეგია იქცევა როგორც ნაგულისხმევი შერჩევითი ტესტირება.

ნაგულისხმევად, შერჩევითი ტესტირება ტოვებს მთლიან ტესტ სამიზნეებს, რომელთა ჰეშიც უკვე გაიარა. `.coverage()` სტრატეგია მიდის უფრო შორს: დარჩენილ ტესტ სამიზნეებში, ის ასევე ტოვებს XCTest და XCUITest ტესტებს, რომელთა კოდის დაფარვაც ადრეულ გაშვებაში არ შეიცავს არცერთ ფაილს, რომელსაც თქვენმა ცვლილებამ შეეხო. ჩართეთ ის `Tuist.swift`-ში:

```swift
import ProjectDescription

let tuist = Tuist(
    fullHandle: "{account-handle}/{project-handle}",
    testInsights: .testInsights(
        coverage: .coverage(upload: true),
        selectiveTesting: .selectiveTesting(strategy: .coverage())
    ),
    project: .tuist()
)
```

სტრატეგია მოითხოვს:

- **დაფარვის ატვირთვები.** Tuist ირჩევს ტესტებს იმ დაფარვის მიხედვით, რომელიც ადრეულმა გაშვებებმა ატვირთეს, ამიტომ `tuist test` ვერ ტვირთავს მანიფესტს, რომელიც აყენებს `.coverage()`-ს `upload: false`-ით.
- **[TestCoverageAttribution](https://github.com/tuist/TestCoverageAttribution) 0.3.0 ან უფრო ახალი**, დაკავშირებული თქვენი ტესტ სამიზნეების მიერ. ის იწერს, თუ რომელ ფაილებს ასრულებს თითოეული ტესტი და ტოვებს იმ ტესტებს, რომლებიც Tuist-მა არ შეარჩია. სამიზნე მის გარეშე მხოლოდ მთლიანად შეიძლება გამოიტოვოს, როგორც ნაგულისხმევ შემთხვევაში.
- **ტესტების გაშვება თქვენს ნაგულისხმევ ბრენჩზე შერჩევის გარეშე.** გაუშვით `tuist test --no-selective-testing` იქ და ნებისმიერ სხვა ბრენჩზე, სადაც ტესტები არ უნდა გამოიტოვოს. ეს გაშვებები ასრულებენ ყველა ტესტს და ხდებიან ბაზისური ხაზები, რომლებსაც მომავალი გაშვებები შეადარებენ.

სტრატეგიის ჩართვისას, `tuist test` ტოვებს სამიზნეებს, რომელთა ჰეშიც უკვე გაიარა, შემდეგ კი ეკითხება Tuist-ს, თუ რომელ ტესტებს შეუძლია თქვენს ცვლილებას შეეხოს დარჩენილ სამიზნეებში. სამიზნეები, რომლებსაც არ აქვთ დაზარალებული ტესტი, არ აგდება. ახალი ტესტები, ტესტები, რომლებიც ბოლოს ჩავარდა, ტესტები შეცვლილ ტესტ ფაილში და ტესტები ჩაწერილი დაფარვის გარეშე ყოველთვის გაეშვება. Swift Testing ტესტები გაეშვება ნებისმიერ დროს, როდესაც მათი სამიზნე გაეშვება.

როდესაც დაფარვა ვერ იღებს გადაწყვეტილებას, გამომავალი მონაცემები ამბობენ, რატომ. იმავე პლატფორმაზე ბოლოდროინდელი ბაზისური ხაზის გარეშე, ან როდესაც ცვლილება ეხება 5,000-ზე მეტ ფაილს, ყველა ტესტი გაეშვება, რათა კომიტმა შეძლოს ბაზისურ ხაზად ქცევა. როდესაც შეიცვალა ფაილი, რომელსაც შეუძლია ნებისმიერი ტესტის შეხება, როგორიცაა `Package.resolved`, `Project.swift`, ან `.xcconfig`, გაშვება იყენებს ნაგულისხმევ შერჩევით ტესტირებას. ყველა ტესტის გასაშვებად, გადაეცით `--no-selective-testing`.

## გამოტოვებების შესწავლა დაშბორდზე {#investigating-misses-on-the-dashboard}

როდესაც ადრე cached ტესტის სამიზნე გამოჩნდება როგორც გამოტოვება, ტესტების გაშვების გვერდზე არსებული **შერჩევითი ტესტირება** ჩანართი საშუალებას გაძლევთ ჩაუღრმავდეთ იმ შემავალ მონაცემებს, რომლებმაც წარმოქმნეს ჰეში. სტრიქონის გაფართოება აჩვენებს კომპონენტების მიხედვით ქვეჰეშებს — წყაროები, დამოკიდებულებები, გარემოს ცვლადები, პროექტისა და სამიზნის პარამეტრები, Info.plist, უფლებები, ჰედერები და ა.შ. — რათა ზუსტად განსაზღვროთ შემავალი მონაცემი, რომელიც შეიცვალა გაშვებებს შორის.

გამოიყენეთ **Copy as JSON** ღილაკი შერჩევითი ტესტირების ბარათის თავში, რათა ექსპორტირება მოახდინოთ ყველა შერჩევითი ტესტირების სამიზნისთვის მისი ჰეშითა და ქვეჰეშებით. ორ გაშვებას შორის JSON-ის შედარება არის ყველაზე სწრაფი გზა იმის დასადასტურებლად, თუ რომელი შემავალი მონაცემი შეიცვალა, როდესაც ტესტის სამიზნის ჰეში შეიცვალა.
