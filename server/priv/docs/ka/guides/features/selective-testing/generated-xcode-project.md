# გენერირებული Xcode პროექტი {#generated-xcode-project}

როდესაც პროექტი იზრდება, ყოველ push-ზე ყველა ტესტის გაშვება აღარ მასშტაბირდება. Tuist-ის შერჩევითი ტესტირება ასრულებს მხოლოდ იმ ტესტებს, რომელთა სამიზნეებიც შეიცვალა ბოლო წარმატებული ტესტების გაშვების შემდეგ, Tuist-ის <.localized_link href="/guides/features/projects/hashing">ჰეშირების ალგორითმის</.localized_link> საფუძველზე.

ტესტების შერჩევითად გასაშვებად თქვენს <.localized_link href="/guides/features/projects">გენერირებულ პროექტთან</.localized_link>, გამოიყენეთ `tuist test` ბრძანება. ბრძანება <.localized_link href="/guides/features/projects/hashing">აჰეშირებს</.localized_link> თქვენს პროექტს ისევე, როგორც <.localized_link href="/guides/features/cache/module-cache">მოდილის ქეშისთვის</.localized_link>, და წარმატების შემთხვევაში ინახავს ჰეშებს, რათა მომავალ გაშვებებში განსაზღვროს, რა შეიცვალა. მომავალ გაშვებებში `tuist test` გამჭვირვალედ იყენებს ჰეშებს ტესტების ფილტრაციისთვის და ასრულებს მხოლოდ იმას, რაც შეიცვალა ბოლო წარმატებული ტესტების გაშვების შემდეგ.

`tuist test` პირდაპირ ინტეგრირდება <.localized_link href="/guides/features/cache/module-cache">მოდილის ქეშთან</.localized_link>, რათა გამოიყენოს მაქსიმალური რაოდენობის ბინარები თქვენი ადგილობრივი ან დისტანციური საცავიდან და შეამციროს ბილდის დრო თქვენი ტესტების ნაკრების გაშვებისას. შერჩევითი ტესტირებისა და მოდილის ქეშირების კომბინაციამ შეიძლება მნიშვნელოვნად შეამციროს დრო, რომელიც სჭირდება ტესტების გაშვებას თქვენს CI-ზე.

თუ თქვენი ტესტების გაშვება მხოლოდ სიმულატორების სამიზნეებს ეხება, გადაეცით `--destination simulator`, რათა `tuist test` გამოიყენოს და ჩამოტვირთოს მხოლოდ ქეშირებული ბინარების სიმულატორის ნაწილები. იხილეთ <.localized_link href="/guides/features/cache/module-cache#destination-selection">დანიშნულების არჩევა</.localized_link>. შერჩევითი ტესტირების ჰეშები ერთნაირია `--destination` ნებისმიერი მნიშვნელობისთვის.

## ბილდისა და ტესტების ცალკეული ჯობები {#separate-build-and-test-jobs}

შერჩევითი ტესტირება მხარს უჭერს ბილდისა და ტესტების ცალკეულ ჯობებს. გაუშვით `tuist test --build-only` ბილდის ჯობაში, რათა Tuist-მა შეინახოს `selective-testing-graph.json` ფაილი ბილდის მიერ გამოცემული პროდუქტების გვერდით. ეს გრაფი შეიცავს ჰეშებს, რომლებიც საჭიროა შერჩევითი ტესტირებისთვის, ამიტომ ტესტების ჯობას არ სჭირდება პროექტის ხელახლა გენერირება ან Swift Package დამოკიდებულებების გადაწყვეტა იმის დასადგენად, თუ რომელი სამიზნეები უნდა გაეშვას.

Tuist წერს გრაფს ორ ადგილას `--build-only`-ის დროს:

- `.xctestproducts` ბანდლის შიგნით, როდესაც გადასცემთ `-testProductsPath`.
- ყოველი `.xctestrun` ფაილის გვერდით წარმოებული მონაცემების `Build/Products/` დირექტორიაში.

შეინახეთ ნებისმიერი გამომავალი მონაცემი აგებული პროდუქტების გვერდით და გადაეცით იგივე გზა `--without-building`-ს ტესტების ჯობაში. ორივე ფორმა მუშაობს:

```sh
# Build job — writes an .xctestproducts bundle with the graph inside it.
tuist test MyScheme \
  --build-only \
  -- \
  -testProductsPath artifacts/MyScheme.xctestproducts \
  -destination 'platform=iOS Simulator,id=SIMULATOR_IDENTIFIER'

# Test job — restores the same bundle.
tuist test MyScheme \
  --without-building \
  -- \
  -testProductsPath artifacts/MyScheme.xctestproducts \
  -destination 'platform=iOS Simulator,id=SIMULATOR_IDENTIFIER'
```

```sh
# Build job — writes the graph as a sibling of each xctestrun in derived data.
tuist test MyScheme \
  --build-only \
  -- \
  -derivedDataPath artifacts/derived-data

# Test job — points --without-building at any of those xctestrun files.
tuist test MyScheme \
  --without-building \
  -- \
  -derivedDataPath artifacts/derived-data \
  -destination 'platform=iOS Simulator,id=SIMULATOR_IDENTIFIER' \
  -xctestrun artifacts/derived-data/Build/Products/MyScheme_iphonesimulator.xctestrun
```

როდესაც Tuist ვერ პოულობს ამ გრაფს შეყვანის გვერდით (მაგალითად, როდესაც ბილდის ჯობამ გამოიყენა ჩვეულებრივი `xcodebuild build-for-testing` `tuist test --build-only`-ის ნაცვლად), ის ბრუნდება პროექტის ხელახლა გენერირებაზე, რათა მაინც გამოთვალოს დაზარალებული სამიზნეები. ამ ალტერნატიულ ვარიანტს სჭირდება Swift Package დამოკიდებულებების გადაწყვეტა ტესტების ჯობაზე, ამიტომ ჯერ გაუშვით `tuist install` ან შეინახეთ `Tuist/.build` ჯობებს შორის.

გრაფი ასახავს წყაროს ხეს ისე, როგორც ის იყო ბილდის დროს. გაუშვით ტესტების ჯობა იმავე კომიტზე, რაზეც ბილდის ჯობა — თუ წყარო განსხვავდება ამ ორს შორის, ჰეშები აღარ ემთხვევა წყაროს და შერჩევითმა ტესტირებამ შეიძლება გამოტოვოს ტესტები, რომლებიც რეალურად ჩავარდებოდა ახალ წყაროზე.

### რომელი ფლაგი უნდა გამოვიყენო? {#which-flag-should-i-use}

`.xctestrun` და `.xctestproducts` არის Xcode-ის ორი განსხვავებული გამომავალი ფორმატი და ისინი აბალანსებენ პორტაბელურობასა და პაიპლაინის მოხერხებულობას:

- **`-testProductsPath` (`.xctestproducts`) — რეკომენდებულია ახალი პაიპლაინებისთვის.** ეს არის თვითკმარი დირექტორია: აგებული `.xctest` ბინარები და მათი `.xctestrun` ფაილები მდებარეობენ მის შიგნით ისე, რომ გზები ფარდობითია ბანდლის ფესვთან, ამიტომ ის რჩება ვალიდური ნებისმიერ ადგილას.
- **`-xctestrun` (ნედლი `.xctestrun`) — გამოიყენეთ, თუ უკვე გაქვთ პაიპლაინი, აგებული წარმოებულ მონაცემებზე.** `xcodebuild build-for-testing` წერს `.xctestrun`-ს `<derivedData>/Build/Products/`-ის თავში ნაგულისხმევად და მიუთითებს ტესტ ბანდლებზე, რომლებიც მდებარეობენ ამ ხის სხვა ადგილას. მისი ხელახლა გამოყენება სხვა ჯობაში ნიშნავს გზების შენარჩუნებას `Build/Products/`-ში უცვლელად.

თუ ახალს იწყებთ, უპირატესობა მიანიჭეთ `-testProductsPath`-ს. თუ Tuist-ს აერთიანებთ არსებულ პაიპლაინში, რომელიც უკვე აქეშირებს წარმოებულ მონაცემებს, `-xctestrun` იღებს იმავე სწრაფ გზას, სანამ ბილდის ჯობა გადის `tuist test --build-only`-ის მეშვეობით.

ნებისმიერი შეყვანის რეჟიმი ურთიერთგამომრიცხავია `-workspace`/`-project`/`-scheme`-თან, ამიტომ Tuist ტოვებს ამ ფლაგებს, როდესაც პასტროუ არგუმენტები შეიცავს `-xctestrun`-ს ან `-testProductsPath`-ს, და გადასცემს შერჩეულ სამიზნეებს `-only-testing`-ის მეშვეობით.

> [!WARNING]
> **მოდიული vs ფაილის დონის გრანულარობა**
>
> კოდში ტესტებსა და წყაროებს შორის დამოკიდებულებების აღმოჩენის შეუძლებლობის გამო, ნაგულისხმევი შერჩევითი ტესტირების მაქსიმალური გრანულარობა სამიზნის დონეზეა. [დაფარვის სტრატეგია](#coverage-based-test-selection) ამცირებს მას ცალკეულ XCTest ტესტებამდე. ამიტომ, რეკომენდებულია სამიზნეების მცირე და ფოკუსირებულად შენარჩუნება შერჩევითი ტესტირების სარგებლის მაქსიმიზაციისთვის.


## დაფარვაზე დაფუძნებული ტესტების შერჩევა {#coverage-based-test-selection}

> [!NOTE]
> **ადრეული წვდომა**
>
> დაფარვაზე დაფუძნებული ტესტების შერჩევა ადრეული წვდომის რეჟიმშია. დაგვიკავშირდით მისი თქვენი ანგარიშისთვის ჩართვის მიზნით. სანამ ის ჩართული არ იქნება, სტრატეგია იქცევა როგორც ნაგულისხმევი შერჩევითი ტესტირება.

ნაგულისხმევად, შერჩევითი ტესტირება ტოვებს მთლიან ტესტ სამიზნეებს, რომელთა ჰეშიც უკვე გაიარა. `.coverage()` სტრატეგია მიდის უფრო შორს: დარჩენილ ტესტ სამიზნეებში, ის ასევე ტოვებს XCTest და XCUITest ტესტებს, რომელთა კოდის დაფარვაც ადრეულ გაშვებაზე არ მოიცავს თქვენი ცვლილების მიერ შეხებულ ფაილებს. ჩართეთ ის `Tuist.swift`-ში:

```swift
import ProjectDescription

let tuist = Tuist(
    fullHandle: "{account-handle}/{project-handle}",
    testInsights: .testInsights(
        coverage: .coverage(upload: true),
        selectiveTesting: .selectiveTesting(strategy: .coverage())
    ),
    project: .tuist()
)
```

სტრატეგია მოითხოვს:

- **დაფარვის ატვირთვები.** Tuist ირჩევს ტესტებს ადრეული გაშვებების მიერ ატვირთული დაფარვის მიხედვით, ამიტომ `tuist test` ვერ ტვირთავს მანიფესტს, რომელიც აყენებს `.coverage()`-ს `upload: false`-ით.
- **[TestCoverageAttribution](https://github.com/tuist/TestCoverageAttribution) 0.3.0 ან უფრო გვიანი**, დაკავშირებული თქვენი ტესტ სამიზნეების მიერ. ის იწერს, თუ რომელ ფაილებს ასრულებს თითოეული ტესტი და ტოვებს ტესტებს, რომლებიც Tuist-მა არ შეარჩია. სამიზნე მის გარეშე ყოველთვის ტოვდება მთლიანად, როგორც ნაგულისხმევ შემთხვევაში.
- **ტესტების გაშვება თქვენს ნაგულისხმევ ბრენჩზე შერჩევის გარეშე.** გაუშვით `tuist test --no-selective-testing` იქ და ნებისმიერ სხვა ბრენჩზე, სადაც ტესტები არ უნდა გამოტოვდეს. ეს გაშვებები ასრულებენ ყველა ტესტს და ხდებიან ბაზისური ხაზები, რომლებსაც მომავალი გაშვებები შეადარებენ.

სტრატეგიის ჩართვისას, `tuist test` ტოვებს სამიზნეებს, რომელთა ჰეშიც უკვე გაიარა, შემდეგ კი ეკითხება Tuist-ს, თუ რომელ ტესტებს შეუძლია თქვენი ცვლილების გავლენა დარჩენილ სამიზნეებში. სამიზნეები, რომლებსაც არ აქვთ დაზარალებული ტესტი, არ აგებენ. ახალი ტესტები, ტესტები, რომლებიც ბოლოს ჩავარდნენ, ტესტები შეცვლილ ტესტ ფაილში და ტესტები ჩაწერილი დაფარვის გარეშე ყოველთვის სრულდება. Swift Testing ტესტები სრულდება მაშინ, როდესაც მათი სამიზნე სრულდება.

## გამოტოვებების გამოკვლევა დაფბორდზე {#investigating-misses-on-the-dashboard}

როდესაც ადრე კეშირებული ტესტის სამიზნე გამოჩნდება როგორც გამოტოვებული (miss), ტესტების გაშვების გვერდზე არსებული **შერჩევითი ტესტირება** ჩანართი საშუალებას გაძლევთ შეისწავლოთ ის შემავალი მონაცემები, რომლებმაც ჰეში წარმოქმნეს. სტრიქონის გაშლა აჩვენებს კომპონენტების მიხედვით ქვეჰეშებს — წყაროები, დამოკიდებულებები, გარემოს ცვლადები, პროექტისა და სამიზნის პარამეტრები, Info.plist, უფლებები, ჰედერები და ა.შ. — რათა ზუსტად განსაზღვროთ შემავალი მონაცემი, რომელიც შეიცვალა გაშვებებს შორის.

გამოიყენეთ **Copy as JSON** ღილაკი შერჩევითი ტესტირების ბარათის ზედა ნაწილში, რათა ექსპორტირება მოახდინოთ ყველა შერჩევითი ტესტირების სამიზნის თავის ჰეშებითა და ქვეჰეშებით. JSON-ის შედარება ორ გაშვებას შორის არის ყველაზე სწრაფი გზა იმის დასადასტურებლად, თუ რომელი შემავალი მონაცემი შეიცვალა, როდესაც ტესტის სამიზნის ჰეში შეიცვალა.
