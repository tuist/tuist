# გენერირებული Xcode პროექტი {#generated-xcode-project}

როგორც იზრდება თქვენი პროექტი, ისევე იზრდება ტესტების რაოდენობაც. დიდი ხნის განმავლობაში ყველა ტესტის გაშვება ყოველ PR-ზე ან `main`-ზე push-ისას ათეულობით წამს მოითხოვს. მაგრამ ეს მიდგომა არ მასშტაბდება თქვენი გუნდის შესაძლო ათასობით ტესტზე.

CI-ზე ყოველი ტესტების გაშვებისას, ცვლილებების მიუხედავად, სავარაუდოდ, ყველა ტესტს ხელახლა აშვებთ. Tuist-ის შერჩევითი ტესტირება გეხმარებათ ტესტების შესრულების დრო მნიშვნელოვნად შეამციროთ იმ ტესტების გაშვებით, რომლებიც ბოლო წარმატებული ტესტების გაშვების შემდეგ შეიცვალა ჩვენი <.localized_link href="/guides/features/projects/hashing">ჰეშირების ალგორითმის</.localized_link> საფუძველზე.

შერჩევითი ტესტების გასაშვებად თქვენს <.localized_link href="/guides/features/projects">გენერირებულ პროექტთან</.localized_link> ერთად, გამოიყენეთ `tuist test` ბრძანება. ბრძანება <.localized_link href="/guides/features/projects/hashing">ჰეშირებს</.localized_link> თქვენს პროექტს ისევე, როგორც <.localized_link href="/guides/features/cache/module-cache">მოდიულის ქეშისთვის</.localized_link>, და წარმატების შემთხვევაში ინახავს ჰეშებს, რათა მომავალ გაშვებებში დაადგინოს, რა შეიცვალა. მომავალ გაშვებებში, `tuist test` გამჭვირვალედ იყენებს ჰეშებს ტესტების ფილტრაციისთვის და აშვებს მხოლოდ იმ ტესტებს, რომლებიც ბოლო წარმატებული ტესტების გაშვების შემდეგ შეიცვალა.

`tuist test` პირდაპირ ინტეგრირდება <.localized_link href="/guides/features/cache/module-cache">მოდიულის ქეშთან</.localized_link>, რათა გამოიყენოს მაქსიმალურად მეტი ბინარი თქვენი ლოკალური ან დისტანციური საცავიდან და გააუმჯობესოს აწყობის დრო თქვენი ტესტების ნაკრების გაშვებისას. შერჩევითი ტესტირებისა და მოდიულის ქეშირების კომბინაციამ შეიძლება მნიშვნელოვნად შეამციროს დრო, რომელიც სჭირდება ტესტების გაშვებას თქვენს CI-ზე.

თუ თქვენი ტესტები მხოლოდ სიმულატორებს ემიზნება, გადაეცით `--destination simulator`, რათა `tuist test` იყენებდეს და ჩამოტვირთავდეს მხოლოდ ქეშირებული ბინარების სიმულატორის სლაისებს. იხილეთ <.localized_link href="/guides/features/cache/module-cache#destination-selection">დანიშნულების არჩევა</.localized_link>. შერჩევითი ტესტირების ჰეშები ერთნაირია ყოველი `--destination` მნიშვნელობისთვის.

## ბილდისა და ტესტების ცალკეული სამუშაოები {#separate-build-and-test-jobs}

შერჩევითი ტესტირება მხარდაჭერილია ბილდისა და ტესტების ცალკეული სამუშაოებით. ბილდის სამუშაოში გაუშვით `tuist test --build-only`, რათა Tuist-მა შეინახოს `selective-testing-graph.json` ფაილი ბილდის მიერ გამოშვებული პროდუქტების გვერდით. ეს გრაფი შეიცავს ჰეშებს, რომლებიც შერჩევით ტესტირებას სჭირდება, ამიტომ ტესტების სამუშაოს არ უწევს პროექტის ხელახლა გენერირება ან Swift Package დამოკიდებულებების გარკვევა, რათა დაადგინოს, რომელი target-ები უნდა გაუშვას.

Tuist წერს გრაფს ორ ადგილას `--build-only`-ის დროს:

- `.xctestproducts` ბანდლის შიგნით, როდესაც გადასცემთ `-testProductsPath`-ს.
- ყოველი `.xctestrun` ფაილის გვერდით derived data-ს `Build/Products/` დირექტორიაში.

ქეშირეთ ნებისმიერი გამომავალი ბილდის პროდუქტების გვერდით და გადაეცით იგივე გზა `--without-building`-ს ტესტების სამუშაოში. ორივე ფორმა მუშაობს:

```sh
# Build job — writes an .xctestproducts bundle with the graph inside it.
tuist test MyScheme \
  --build-only \
  -- \
  -testProductsPath artifacts/MyScheme.xctestproducts \
  -destination 'platform=iOS Simulator,id=SIMULATOR_IDENTIFIER'

# Test job — restores the same bundle.
tuist test MyScheme \
  --without-building \
  -- \
  -testProductsPath artifacts/MyScheme.xctestproducts \
  -destination 'platform=iOS Simulator,id=SIMULATOR_IDENTIFIER'
```

```sh
# Build job — writes the graph as a sibling of each xctestrun in derived data.
tuist test MyScheme \
  --build-only \
  --derived-data-path artifacts/derived-data

# Test job — points --without-building at any of those xctestrun files.
tuist test MyScheme \
  --without-building \
  --derived-data-path artifacts/derived-data \
  -- \
  -destination 'platform=iOS Simulator,id=SIMULATOR_IDENTIFIER' \
  -xctestrun artifacts/derived-data/Build/Products/MyScheme_iphonesimulator.xctestrun
```

როდესაც Tuist ვერ პოულობს ამ გრაფს შეყვანის გვერდით (მაგალითად, როდესაც ბილდის სამუშაომ გამოიყენა ჩვეულებრივი `xcodebuild build-for-testing` `tuist test --build-only`-ის ნაცვლად), ის გადადის პროექტის ხელახლა გენერირებაზე, რათა მაინც გამოთვალოს დაზარალებული target-ები. ამ ალტერნატიულ მიდგომას სჭირდება Swift Package დამოკიდებულებების გარკვევა ტესტების სამუშაოზე, ამიტომ ჯერ გაუშვით `tuist install` ან ქეშირეთ `Tuist/.build` სამუშაოებს შორის.

გრაფი ასახავს წყაროს ხეს ისე, როგორიც ის ბილდის დროს იყო. გაუშვით ტესტების სამუშაო იმავე commit-ზე, რაზეც ბილდის სამუშაო — თუ წყარო ორს შორის იცვლება, ჰეშები ძველდება და შერჩევითმა ტესტირებამ შეიძლება გამოტოვოს ტესტები, რომლებიც რეალურად ჩავარდებოდა ახალ წყაროზე.

### რომელი ფლაგი გამოვიყენო? {#which-flag-should-i-use}

`.xctestrun` და `.xctestproducts` არის Xcode-ის ორი განსხვავებული გამომავალი ფორმატი, და ისინი აწონასწორებენ პორტაბელურობას პაიპლაინის მოხერხებულობის წინააღმდეგ:

- **`-testProductsPath` (`.xctestproducts`) — რეკომენდებულია ახალი პაიპლაინებისთვის.** ეს არის თვითკმარი დირექტორია: აგებული `.xctest` ბინარები და მათი `.xctestrun` ფაილები მდებარეობს მის შიგნით გზებით, რომლებიც ბანდლის ფესტვის მიმართებითაა, ამიტომ ის ძალაში რჩება ნებისმიერ ადგილას. ეს ასევე არის ფორმატი, რომელსაც ყველაზე დიდი ხანია აქვს შერჩევითი ტესტირების სწრაფი გზა, ამიტომ ის არის ყველაზე მეტად გამოცდილი გზა.
- **`-xctestrun` (ნედლი `.xctestrun`) — გამოიყენეთ, თუ უკვე გაქვთ პაიპლაინი, აგებული derived data-ს გარშემო.** `xcodebuild build-for-testing` წერს `.xctestrun`-ს `<derivedData>/Build/Products/`-ის თავში ნაგულისხმევად და მიუთითებს ტესტ ბანდლებზე, რომლებიც ამ ხის სხვა ადგილას მდებარეობს. მისი ხელახლა გამოყენება სხვა სამუშაოში ნიშნავს `Build/Products/`-ში გზების უცვლელად შენარჩუნებას.

თუ ახალს იწყებთ, უპირატესობა მიანიჭეთ `-testProductsPath`-ს. თუ Tuist-ს აერთებთ არსებულ პაიპლაინში, რომელიც უკვე ქეშირებს derived data-ს, `-xctestrun` ახლა მიიღებს იმავე სწრაფ გზას, იმ პირობით, რომ ბილდის სამუშაო გადის `tuist test --build-only`-ით.

ნებისმიერი შეყვანის რეჟიმი ურთიერთგამომრიცხავია `-workspace`/`-project`/`-scheme`-თან, ამიტომ Tuist ტოვებს ამ ფლაგებს, როდესაც პასთრუ არგუმენტები შეიცავს `-xctestrun`-ს ან `-testProductsPath`-ს, და გადასცემს შერჩეულ target-ებს `-only-testing`-ით.

> [!WARNING]
> **მოდულის versus ფაილის დონის გრანულარობა**
>
> ტესტებსა და წყაროებს შორის კოდში არსებული დამოკიდებულებების აღმოჩენის შეუძლებლობის გამო, შერჩევითი ტესტირების მაქსიმალური გრანულარობა target-ის დონეზეა. ამიტომ, რეკომენდებულია თქვენი target-ები მცირე და ფოკუსირებული შეინარჩუნოთ, რათა მაქსიმალურად გამოიყენოთ შერჩევითი ტესტირების სარგებელი.


> [!WARNING]
> **ტესტების დაფარვა**
>
> ტესტების დაფარვის ხელსაწყოები ვარაუდობენ, რომ მთელი ტესტების ნაკრები ერთდროულად გაშვებულია, რაც მათ შეუთავსებელს ხდის შერჩევით ტესტების გაშვებებთან — ეს ნიშნავს, რომ დაფარვის მონაცემები შეიძლება არ ასახავდეს რეალობას ტესტების შერჩევის გამოყენებისას. ეს არის ცნობილი შეზღუდვა და არ ნიშნავს, რომ რაიმე არასწორად აკეთებთ. ჩვენ ვურჩევთ გუნდებს, დაფიქრდნენ, აგრძელებს თუ არა დაფარვა მნიშვნელოვანი insights-ის მოტანას ამ კონტექსტში, და თუ ასეა, იყავით დარწმუნებულები, რომ ჩვენ უკვე ვფიქრობთ იმაზე, თუ როგორ გავხადოთ დაფარვა სწორად მომუშავე შერჩევით გაშვებებთან მომავალში.

## გამოტოვებების გამოკვლევა dashboard-ზე {#investigating-misses-on-the-dashboard}

როდესაც ადრე ქეშირებული ტესტის სამიზნე გამოჩნდება როგორც გამოტოვებული (miss), ტესტების გაშვების გვერდზე არსებული **შერჩევითი ტესტირება** ჩანართი საშუალებას გაძლევთ ჩაუღრმავდეთ იმ შეყვანებს, რომლებმაც ჰეში წარმოქმნეს. სტრიქონის გაშლა აჩვენებს კომპონენტების მიხედვით სუბჰეშებს — წყაროებს, დამოკიდებულებებს, გარემოს ცვლადებს, პროექტისა და სამიზნის პარამეტრებს, Info.plist-ს, უფლებებს, ჰედერებს და ა.შ., რათა ზუსტად განსაზღვროთ შეყვანა, რომელიც შეიცვალა გაშვებებს შორის.

გამოიყენეთ **JSON-ად კოპირება** ღილაკი შერჩევითი ტესტირების ბარათის თავში, რათა გაიტანოთ ყოველი შერჩევითი ტესტირების target მისი ჰეშითა და სუბჰეშებით. JSON-ის შედარება ორ გაშვებას შორის არის ყველაზე სწრაფი გზა იმის დასადასტურებლად, თუ რომელი შეყვანა შეიცვალა, როდესაც ტესტის target-ის ჰეში შეიცვალა.
