# მოდულური არქიტექტურა (TMA) {#the-modular-architecture-tma}

TMA არის არქიტექტურული მიდგომა აპლიკაციების სტრუქტურირებისთვის, რაც უზრუნველყოფს მასშტაბირებადობას, აოპტიმიზებს კომპილაციისა და ტესტირების ციკლებს და გუნდში კარგი პრაქტიკების დამკვიდრებას. მისი ძირითადი იდეაა აპლიკაციების აწყობა დამოუკიდებელი ფუნქციებისგან, რომლებიც ერთმანეთთან დაკავშირებულია ნათელი და ლაკონური API-ებით.

ეს სახელმძღვანელო წესები გაგაცნობთ არქიტექტურის პრინციპებს, გეხმარებათ გამოავლინოთ და დაალაგოთ თქვენი აპლიკაციის ფუნქციები სხვადასხვა შრეებში. ასევე მოგაწვდით რჩევებს, ინსტრუმენტებსა და შეთავაზებებს, თუ ამ არქიტექტურის გამოყენებას გადაწყვეტთ.

> [!NOTE]
> **µFeatures**
>
> ეს არქიტექტურა ადრე ცნობილი იყო როგორც µFeatures. ჩვენ გადავარქვით სახელი The Modular Architecture (TMA), რათა უკეთესად ასახავდეს მის დანიშნულებასა და მის საფუძველში მდებარე პრინციპებს.


## ძირითადი პრინციპი {#core-principle}

დეველოპერებს უნდა შეეძლოთ **სწრაფად ააწყონ, დატესტონ და გამოსცადონ** თავიანთი ფუნქციები, მთავარი აპლიკაციისგან დამოუკიდებლად, ისე, რომ Xcode-ის ისეთი ფუნქციები, როგორიცაა UI-ის პრივიუები, კოდის ავტოშევსება და დებაგინგი, საიმედოდ მუშაობდეს.

## რა არის მოდული {#what-is-a-module}

მოდული წარმოადგენს აპლიკაციის ფუნქციას და შედგება შემდეგი ხუთი ტარგეტისგან (სადაც ტარგეტი ეხება Xcode-ის ტარგეტს):

- **Source:** შეიცავს ფუნქციის საწყის კოდს (Swift, Objective-C, C++, JavaScript...) და მის რესურსებს (სურათები, შრიფტები, storyboards, xibs).
- **Interface:** ეს არის დამხმარე ტარგეტი, რომელიც შეიცავს ფუნქციის საჯარო ინტერფეისსა და მოდელებს.
- **Tests:** შეიცავს ფუნქციის unit და ინტეგრაციულ ტესტებს.
- **Testing:** უზრუნველყოფს სატესტო მონაცემებს, რომლებიც შეიძლება გამოყენებულ იქნას ტესტებში და მაგალითის აპლიკაციაში. ასევე უზრუნველყოფს mock-ებს მოდულის კლასებისა და პროტოკოლებისთვის, რომლებიც სხვა ფუნქციებმა შეიძლება გამოიყენონ, როგორც მოგვიანებით ვნახავთ.
- **Example:** შეიცავს მაგალითის აპლიკაციას, რომლის გამოყენებაც დეველოპერებს შეუძლიათ ფუნქციის გამოსაცდელად გარკვეულ პირობებში (სხვადასხვა ენები, ეკრანის ზომები, პარამეტრები).

ჩვენ გირჩევთ დაიცვათ ტარგეტების სახელდების კონვენცია, რისი იმპლემენტაციაც თქვენს პროექტში შესაძლებელია Tuist-ის DSL-ის მეშვეობით.

| ტარგეტი | დამოკიდებულებები | შემცველობა |
| ---- | ---- | ---- |
| `Feature` | `FeatureInterface` | საწყისი კოდი და რესურსები |
| `FeatureInterface` | - | საჯარო ინტერფეისი და მოდელები |
| `FeatureTests` | `Feature`, `FeatureTesting` | Unit და ინტეგრაციული ტესტები |
| `FeatureTesting` | `FeatureInterface` | სატესტო მონაცემები და mock-ები |
| `FeatureExample` | `FeatureTesting`, `Feature` | მაგალითის აპლიკაცია |

> [!TIP]
> **UI პრივიუები**
>
> `Feature` შეუძლია გამოიყენოს `FeatureTesting` როგორც Development Asset UI პრივიუების უზრუნველსაყოფად


> [!WARNING]
> **კომპილატორის დირექტივები სატესტო ტარგეტების ნაცვლად**
>
> ალტერნატიულად, შეგიძლიათ გამოიყენოთ კომპილატორის დირექტივები სატესტო მონაცემებისა და mock-ების ჩასართავად `Feature` ან `FeatureInterface` ტარგეტებში `Debug`-ისთვის კომპილაციისას. თქვენ ამარტივებთ გრაფს, მაგრამ საბოლოოდ დააკომპილირებთ კოდს, რომელიც აპლიკაციის გასაშვებად არ დაგჭირდებათ.


## რატომ მოდული {#why-a-module}

### ნათელი და ლაკონური API-ები {#clear-and-concise-apis}

როდესაც აპლიკაციის მთელი საწყისი კოდი ერთსა და იმავე ტარგეტშია, ძალიან მარტივია კოდში არაცხადი დამოკიდებულებების აწყობა და საბოლოოდ ცნობილი „სპაგეტის კოდის“ მიღება. ყველაფერი მჭიდროდ არის დაკავშირებული, მდგომარეობა ზოგჯერ არაპროგნოზირებადია და ახალი ცვლილებების შეტანა кошмарად იქცევა. როდესაც ფუნქციებს დამოუკიდებელ ტარგეტებში განვსაზღვრავთ, ფუნქციის იმპლემენტაციის ნაწილად საჯარო API-ების დაპროექტება გვიწევს. უნდა გადავწყვიტოთ, რა უნდა იყოს საჯარო, როგორ უნდა მოხმარდეს ჩვენი ფუნქცია, რა უნდა დარჩეს პრივატული. უფრო მეტი კონტროლი გვაქვს იმაზე, თუ როგორ გვინდა, რომ ფუნქციის მომხმარებლებმა გამოიყენონ ის და შეგვიძლია დავამკვიდროთ კარგი პრაქტიკები უსაფრთხო API-ების დაპროექტებით.

### მცირე მოდულები {#small-modules}

[დაყავი და იბატონე](https://en.wikipedia.org/wiki/Divide_and_conquer). მცირე მოდულებზე მუშაობა საშუალებას გაძლევთ უფრო მეტად ფოკუსირდეთ და ფუნქცია იზოლირებულად დატესტოთ და გამოსცადოთ. გარდა ამისა, განვითარების ციკლები ბევრად უფრო სწრაფია, რადგან გვაქვს უფრო სელექციური კომპილაცია — ვაკომპილირებთ მხოლოდ იმ კომპონენტებს, რომლებიც აუცილებელია ჩვენი ფუნქციის სამუშაოდ. მთლიანი აპლიკაციის კომპილაცია მხოლოდ ჩვენი სამუშაოს ბოლოსაა საჭირო, როდესაც ფუნქციის აპლიკაციაში ინტეგრირება გვჭირდება.

### გამოყენებადობა {#reusability}

კოდის ხელახლა გამოყენება აპლიკაციებსა და სხვა პროდუქტებში, მაგალითად გაფართოებებში, წახალისებულია ფრეიმვორკების ან ბიბლიოთეკების გამოყენებით. მოდულების აწყობით მათი ხელახლა გამოყენება საკმაოდ მარტივია. შეგვიძლია ავაწყოთ iMessage გაფართოება, Today Extension ან watchOS აპლიკაცია უბრალოდ არსებული მოდულების გაერთიანებით და _(საჭიროების შემთხვევაში)_ პლატფორმისთვის სპეციფიკური UI შრეების დამატებით.

## დამოკიდებულებები {#dependencies}

როდესაც ერთი მოდული მეორეზეა დამოკიდებული, ის აცხადებს დამოკიდებულებას მისი ინტერფეისის ტარგეტზე. ამის უპირატესობა ორმაგია. ის ხელს უშლის ერთი მოდულის იმპლემენტაციის მეორე მოდულის იმპლემენტაციასთან დაკავშირებას და აჩქარებს სუფთა აწყობებს, რადგან მხოლოდ ჩვენი ფუნქციის იმპლემენტაციისა და პირდაპირი და ტრანზიტული დამოკიდებულებების ინტერფეისების კომპილაციაა საჭირო. ეს მიდგომა შთაგონებულია SwiftRock-ის იდეით [iOS Build Times-ის შემცირება ინტერფეისის მოდულების გამოყენებით](https://swiftrocks.com/reducing-ios-build-times-by-using-interface-targets).

ინტერფეისებზე დამოკიდებულება მოითხოვს, რომ აპლიკაციებმა runtime-ზე ააწყონ იმპლემენტაციების გრაფი და dependency-inject გაუკეთონ იმ მოდულებს, რომლებსაც ეს სჭირდებათ. მიუხედავად იმისა, რომ TMA არ აწესებს კონკრეტულ წესებს ამის გაკეთებისთვის, ჩვენ გირჩევთ გამოიყენოთ dependency-injection-ის გადაწყვეტილებები ან შაბლონები, რომლებიც არ ამატებენ build-time-ის არაპირდაპირობას ან არ იყენებენ პლატფორმის API-ებს, რომლებიც ამ მიზნისთვის არ არის განკუთვნილი.

## პროდუქტის ტიპები {#product-types}

მოდულის აწყობისას შეგიძლიათ აირჩიოთ **ბიბლიოთეკები და ფრეიმვორკები**, ასევე ტარგეტებისთვის **სტატიკური და დინამიური ლინკინგი**. Tuist-ის გარეშე ამ გადაწყვეტილების მიღება ოდნავ უფრო რთულია, რადგან დამოკიდებულებების გრაფის ხელით კონფიგურირება გჭირდებათ. თუმცა, Tuist Projects-ის მეშვეობით ეს პრობლემა აღარ არსებობს.

განვითარების ეტაპზე გირჩევთ გამოიყენოთ დინამიური ბიბლიოთეკები ან ფრეიმვორკები <.localized_link href="/guides/features/projects/synthesized-files#bundle-accessors">bundle accessors</.localized_link>-ის გამოყენებით, რათა bundle-ზე წვდომის ლოგიკა გამოყოთ ტარგეტის ბიბლიოთეკის ან ფრეიმვორკის ბუნებიდან. ეს გადამწყვეტია სწრაფი კომპილაციისთვის და იმის უზრუნველსაყოფად, რომ [SwiftUI Previews](https://developer.apple.com/documentation/swiftui/previews-in-xcode) საიმედოდ მუშაობდეს. ხოლო release აწყობებისთვის — სტატიკური ბიბლიოთეკები ან ფრეიმვორკები, რათა აპლიკაცია სწრაფად ჩაირთოს. შეგიძლიათ გამოიყენოთ <.localized_link href="/guides/features/projects/dynamic-configuration#configuration-through-environment-variables">dynamic configuration</.localized_link> პროდუქტის ტიპის გენერაციის დროს შეცვლისთვის:

```bash
# You'll have to read the value of the variable from the manifest {#youll-have-to-read-the-value-of-the-variable-from-the-manifest}
# and use it to change the linking type {#and-use-it-to-change-the-linking-type}
TUIST_PRODUCT_TYPE=static-library tuist generate
```

```swift
// You can place this in your manifest files or helpers
// and use the returned value when instantiating targets.
func productType() -> Product {
    if case let .string(productType) = Environment.productType {
        return productType == "static-library" ? .staticLibrary : .framework
    } else {
        return .framework
    }
}
```


> [!WARNING]
> **შეერთებადი ბიბლიოთეკები**
>
> Apple-მა სცადა შეემსუბუქებინა სტატიკურ და დინამიურ ბიბლიოთეკებს შორის გადართვის სირთულე [შეერთებადი ბიბლიოთეკების](https://developer.apple.com/documentation/xcode/configuring-your-project-to-use-mergeable-libraries) წარმოდგენით. თუმცა, ეს შემოაქვს აწყობის დროის არადეტერმინიზმს, რაც თქვენს აწყობას არაწარმოებადს ხდის და ოპტიმიზაციას ურთულებს, ამიტომ მის გამოყენებას არ გირჩევთ.


## კოდი {#code}

TMA არ აწესებს კონკრეტულ მოთხოვნებს თქვენი მოდულების კოდის არქიტექტურისა და პატერნების მიმართ. თუმცა, გვინდა გაგიზიაროთ რჩევები ჩვენი გამოცდილებიდან:

- **კომპილატორის გამოყენება შესანიშნავია.** კომპილატორზე ზედმეტად დაყრდნობამ შეიძლება არაეფექტური აღმოჩნდეს და გამოიწვიოს ის, რომ Xcode-ის ზოგიერთი ფუნქცია, მაგალითად previews, არასაიმედოდ მუშაობდეს. გირჩევთ გამოიყენოთ კომპილატორი კარგი პრაქტიკების დასაცავად და შეცდომების ადრეული აღმოსაჩენად, მაგრამ არა იმ დონემდე, რომ კოდის წაკითხვა და შენარჩუნება გაძნელდეს.
- **Swift Macros ზომიერად გამოიყენეთ.** ისინი შეიძლება ძალიან ძლიერი იყოს, მაგრამ ასევე შეუძლიათ კოდის წაკითხვა და შენარჩუნება გაართულონ.
- **მიიღეთ პლატფორმა და ენა, ნუ გააკეთებთ მათ აბსტრაქციას.** რთული აბსტრაქციის შრეების შექმნის მცდელობამ შეიძლება საპირისპირო ეფექტი მოახდინოს. პლატფორმა და ენა საკმარისად ძლიერია შესანიშნავი აპლიკაციების შესაქმნელად დამატებითი აბსტრაქციის შრეების გარეშე. გამოიყენეთ კარგი პროგრამირებისა და დიზაინის პატერნები როგორც სახელმძღვანელო თქვენი ფუნქციების ასაგებად.
