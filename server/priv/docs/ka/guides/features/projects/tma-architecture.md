# მოდულური არქიტექტურა (TMA) {#the-modular-architecture-tma}

TMA არის არქიტექტურული მიდგომა აპლიკაციების სტრუქტურირებისთვის, რაც უზრუნველყოფს მასშტაბირებადობას, ოპტიმიზაციას ბილდისა და ტესტების ციკლებისთვის და კარგი პრაქტიკების დაცვას თქვენს გუნდში. მისი ძირითადი იდეაა აპლიკაციების აგება დამოუკიდებელი ფუნქციების საშუალებით, რომლებიც ერთმანეთთან დაკავშირებულია ნათელი და ლაკონური API-ებით.

ეს სახელმძღვანელო წარმოადგენს არქიტექტურის პრინციპებს, გეხმარებათ იდენტიფიცირებასა და თქვენი აპლიკაციის ფუნქციების ორგანიზებაში სხვადასხვა შრეებში. ის ასევე გთავაზობთ რჩევებს, ინსტრუმენტებსა და რეკომენდაციებს, თუ გადაწყვეტთ ამ არქიტექტურის გამოყენებას.

> [!NOTE]
> **µFeatures**
>
> ეს არქიტექტურა ადრე ცნობილი იყო როგორც µFeatures. ჩვენ შევუცვალეთ სახელი მოდულურ არქიტექტურად (TMA), რათა უკეთესად ასახოს მისი დანიშნულება და მის უკან მდგარი პრინციპები.


## ძირითადი პრინციპი {#core-principle}

დეველოპერებს უნდა შეეძლოთ **ააგონ, შეამოწმონ და გამოსცადონ** თავიანთი ფუნქციები სწრაფად, მთავარი აპლიკაციისგან დამოუკიდებლად, იმის უზრუნველყოფით, რომ Xcode-ის ისეთი ფუნქციები, როგორიცაა UI-ის პრივიუები, კოდის ავტოშევსება და დებაგინგი, საიმედოდ მუშაობდეს.

## რა არის მოდული {#what-is-a-module}

მოდული წარმოადგენს აპლიკაციის ფუნქციას და შედგება შემდეგი ხუთი ტარგეტისგან (სადაც ტარგეტი ეხება Xcode-ის ტარგეტს):

- **Source:** შეიცავს ფუნქციის საწყის კოდს (Swift, Objective-C, C++, JavaScript...) და მის რესურსებს (სურათები, შრიფტები, storyboards, xibs).
- **Interface:** ეს არის თანმხლები ტარგეტი, რომელიც შეიცავს ფუნქციის საჯარო ინტერფეისსა და მოდელებს.
- **Tests:** შეიცავს ფუნქციის unit და ინტეგრაციულ ტესტებს.
- **Testing:** უზრუნველყოფს სატესტო მონაცემებს, რომლებიც შეიძლება გამოყენებულ იქნას ტესტებში და მაგალითის აპლიკაციაში. ის ასევე უზრუნველყოფს mock-ებს მოდულის კლასებისა და პროტოკოლებისთვის, რომლებიც შეიძლება გამოიყენონ სხვა ფუნქციებმა, როგორც მოგვიანებით ვნახავთ.
- **Example:** შეიცავს მაგალითის აპლიკაციას, რომლის გამოყენებაც დეველოპერებს შეუძლიათ ფუნქციის გამოსაცდელად გარკვეულ პირობებში (სხვადასხვა ენები, ეკრანის ზომები, პარამეტრები).

ჩვენ გირჩევთ დაიცვათ ტარგეტების სახელდების კონვენცია, რისი გატარებაც თქვენს პროექტში შესაძლებელია Tuist-ის DSL-ის საშუალებით.

| ტარგეტი | დამოკიდებულებები | შემცველობა |
| ---- | ---- | ---- |
| `Feature` | `FeatureInterface` | საწყისი კოდი და რესურსები |
| `FeatureInterface` | - | საჯარო ინტერფეისი და მოდელები |
| `FeatureTests` | `Feature`, `FeatureTesting` | Unit და ინტეგრაციული ტესტები |
| `FeatureTesting` | `FeatureInterface` | სატესტო მონაცემები და mock-ები |
| `FeatureExample` | `FeatureTesting`, `Feature` | მაგალითის აპლიკაცია |

> [!TIP]
> **UI პრივიუები**
>
> `Feature`-ს შეუძლია გამოიყენოს `FeatureTesting` როგორც Development Asset UI პრივიუების უზრუნველსაყოფად


> [!WARNING]
> **კომპილატორის დირექტივები სატესტო ტარგეტების ნაცვლად**
>
> ალტერნატიულად, შეგიძლიათ გამოიყენოთ კომპილატორის დირექტივები სატესტო მონაცემებისა და mock-ების ჩასართავად `Feature` ან `FeatureInterface` ტარგეტებში `Debug`-თვის კომპილაციისას. ეს ამარტივებს გრაფს, მაგრამ საბოლოოდ დააკომპილირებთ კოდს, რომელიც აპლიკაციის გასაშვებად არ დაგჭირდებათ.


## რატომ მოდული {#why-a-module}

### ნათელი და ლაკონური API-ები {#clear-and-concise-apis}

როდესაც აპლიკაციის მთელი საწყისი კოდი ერთსა და იმავე ტარგეტშია, ძალიან მარტივია კოდში არაცხადი დამოკიდებულებების აგება და საბოლოოდ ცნობილი „სპაგეტის კოდის“ მიღება. ყველაფერი მჭიდროდ არის დაკავშირებული, მდგომარეობა ზოგჯერ არაპროგნოზირებადია და ახალი ცვლილებების შეტანა კოშმარად იქცევა. როდესაც ფუნქციებს დამოუკიდებელ ტარგეტებში განვსაზღვრავთ, საჭირო ხდება საჯარო API-ების დაპროექტება ჩვენი ფუნქციის იმპლემენტაციის ნაწილად. უნდა გადავწყვიტოთ, რა უნდა იყოს საჯარო, როგორ უნდა მოხმარდებოდეს ჩვენი ფუნქცია, რა უნდა დარჩეს პრივატული. გვაქვს მეტი კონტროლი იმაზე, თუ როგორ გვინდა, რომ ფუნქციის მომხმარებლებმა გამოიყენონ ის და შეგვიძლია დავაცდოთ კარგი პრაქტიკები უსაფრთხო API-ების დაპროექტებით.

### მცირე მოდულები {#small-modules}

[დაყავი და იბატონე](https://en.wikipedia.org/wiki/Divide_and_conquer). მცირე მოდულებში მუშაობა საშუალებას გაძლევთ იყოთ უფრო ფოკუსირებული და შეამოწმოთ და გამოსცადოთ ფუნქცია იზოლირებულად. გარდა ამისა, განვითარების ციკლები ბევრად უფრო სწრაფია, რადგან გვაქვს უფრო სელექციური კომპილაცია, რომელიც აკომპილირებს მხოლოდ იმ კომპონენტებს, რომლებიც აუცილებელია ჩვენი ფუნქციის სამუშაოდ. მთლიანი აპლიკაციის კომპილაცია საჭიროა მხოლოდ ჩვენი სამუშაოს ბოლოს, როდესაც ფუნქციის აპლიკაციაში ინტეგრირება გვჭირდება.

### გამოყენებადობა {#reusability}

კოდის ხელახლა გამოყენება აპლიკაციებსა და სხვა პროდუქტებში, როგორიცაა გაფართოებები, წახალისებულია ფრეიმვორკების ან ბიბლიოთეკების გამოყენებით. მოდულების აგებით მათი ხელახლა გამოყენება საკმაოდ მარტივია. შეგვიძლია ავაგოთ iMessage გაფართოება, Today Extension ან watchOS აპლიკაცია არსებული მოდულების გაერთიანებით და _(საჭიროების შემთხვევაში)_ პლატფორმისთვის სპეციფიკური UI შრეების დამატებით.

## დამოკიდებულებები {#dependencies}

როდესაც ერთი მოდული მეორეზეა დამოკიდებული, ის აცხადებს დამოკიდებულებას მისი ინტერფეისის ტარგეტზე. ამის უპირატესობა ორმაგია. ის ხელს უშლის ერთი მოდულის იმპლემენტაციის მეორე მოდულის იმპლემენტაციასთან დაკავშირებას და აჩქარებს სუფთა ბილდებს, რადგან მათ მხოლოდ ჩვენი ფუნქციის იმპლემენტაციისა და პირდაპირი და ტრანზიტული დამოკიდებულებების ინტერფეისების კომპილაცია სჭირდებათ. ეს მიდგომა შთაგონებულია SwiftRock-ის იდეით [iOS ბილდის დროის შემცირება ინტერფეისის მოდულების გამოყენებით](https://swiftrocks.com/reducing-ios-build-times-by-using-interface-targets).

ინტერფეისებზე დამოკიდებულება მოითხოვს, რომ აპლიკაციებმა ააგონ იმპლემენტაციების გრაფი runtime-ში და შეიტანონ დამოკიდებულება იმ მოდულებში, რომლებსაც ეს სჭირდებათ. მიუხედავად იმისა, რომ TMA არ აწესებს კონკრეტულ წესებს ამის გაკეთებისთვის, ჩვენ გირჩევთ გამოიყენოთ დამოკიდებულების ინექციის გადაწყვეტილებები ან შაბლონები, ან ისეთი გადაწყვეტილებები, რომლებიც არ ამატებენ build-time ირიბობებს ან არ იყენებენ პლატფორმის API-ებს, რომლებიც ამ მიზნისთვის არ არის განკუთვნილი.

## პროდუქტის ტიპები {#product-types}

მოდულის აგებისას შეგიძლიათ აირჩიოთ **ბიბლიოთეკები და ფრეიმვორკები**, ასევე **სტატიკური და დინამიკური ბმები** ტარგეტებისთვის. Tuist-ის გარეშე ამ გადაწყვეტილების მიღება ოდნავ უფრო რთულია, რადგან დამოკიდებულების გრაფის ხელით კონფიგურირება გჭირდებათ. თუმცა, Tuist Projects-ის საშუალებით, ეს აღარ არის პრობლემა.

ჩვენ გირჩევთ განვითარების დროს გამოიყენოთ დინამიკური ბიბლიოთეკები ან ფრეიმვორკები <.localized_link href="/guides/features/projects/synthesized-files#bundle-accessors">bundle accessors</.localized_link>-ის გამოყენებით, რათა bundle-ზე წვდომის ლოგიკა გამოყოთ ტარგეტის ბიბლიოთეკის ან ფრეიმვორკის ბუნებიდან. ეს გადამწყვეტია სწრაფი კომპილაციის დროისთვის და იმის უზრუნველსაყოფად, რომ [SwiftUI Previews](https://developer.apple.com/documentation/swiftui/previews-in-xcode) საიმედოდ მუშაობდეს. ხოლო release ბილდებისთვის — სტატიკური ბიბლიოთეკები ან ფრეიმვორკები, რათა აპლიკაცია სწრაფად ჩაირთოს. შეგიძლიათ გამოიყენოთ <.localized_link href="/guides/features/projects/dynamic-configuration#configuration-through-environment-variables">დინამიკური კონფიგურაცია</.localized_link> პროდუქტის ტიპის შესაცვლელად გენერაციის დროს:

```bash
# You'll have to read the value of the variable from the manifest
# and use it to change the linking type
TUIST_PRODUCT_TYPE=static-library tuist generate
```

```swift
// You can place this in your manifest files or helpers
// and use the returned value when instantiating targets.
func productType() -> Product {
    if case let .string(productType) = Environment.productType {
        return productType == "static-library" ? .staticLibrary : .framework
    } else {
        return .framework
    }
}
```

> **შეერთებადი ბიბლიოთეკები**
>
> Apple-მა სცადა შეემსუბუქებინა სტატიკურ და დინამიკურ ბიბლიოთეკებს შორის გადართვის სირთულე [შეერთებადი ბიბლიოთეკების](https://developer.apple.com/documentation/xcode/configuring-your-project-to-use-mergeable-libraries) წარმოდგენით. თუმცა, ეს შემოაქვს აგების დროს არადეტერმინიზმს, რაც თქვენს ბილდს არაწარმოებადს ხდის და ოპტიმიზაციას ურთულებს, ამიტომ მის გამოყენებას არ ვუწევთ რეკომენდაციას.


## კოდი {#code}

TMA არ აწესებს კონკრეტულ მიდგომას თქვენი მოდულების კოდის არქიტექტურისა და პატერნების მიმართ. თუმცა, გვინდა გაგიზიაროთ რჩევები ჩვენი გამოცდილებიდან:

- **კომპილატორის გამოყენება შესანიშნავია.** კომპილატორზე ზედმეტად დამოკიდებულება შეიძლება არაეფექტური აღმოჩნდეს და გამოიწვიოს ის, რომ ზოგიერთი Xcode-ის ფუნქცია, როგორიცაა previews, არასტაბილურად იმუშაოს. ჩვენ გირჩევთ გამოიყენოთ კომპილატორი კარგი პრაქტიკების დასამკვიდრებლად და შეცდომების ადრეულ ეტაპზე აღმოსაჩენად, მაგრამ არა იმ დონემდე, რომ კოდი წაკითხვასა და მხარდაჭერაში გაართულოთ.
- **Swift Macros ზომიერად გამოიყენეთ.** ისინი შეიძლება ძალიან ძლიერი იყოს, მაგრამ ასევე შეუძლიათ კოდი წაკითხვასა და მხარდაჭერაში გაართულონ.
- **მიჰყევით პლატფორმას და ენას, ნუ შექმნით მათ აბსტრაქციას.** რთული აბსტრაქციის შრეების შექმნის ცდა შეიძლება საპირისპირო შედეგი მოგცეთ. პლატფორმა და ენა საკმარისად ძლიერია შესანიშნავი აპლიკაციების შესაქმნელად დამატებითი აბსტრაქციის შრეების საჭიროების გარეშე. გამოიყენეთ კარგი პროგრამირებისა და დიზაინის პატერნები, როგორც სახელმძღვანელო თქვენი ფუნქციების ასაგებად.
