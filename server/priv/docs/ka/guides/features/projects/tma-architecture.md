# მოდულური არქიტექტურა (TMA) {#the-modular-architecture-tma}

TMA არის არქიტექტურული მიდგომა აპლიკაციების სტრუქტურირებისთვის, რაც უზრუნველყოფს მასშტაბირებადობას, აოპტიმიზებს ბილდისა და ტესტირების ციკლებს და გუნდში კარგი პრაქტიკების დაცვას. მისი ძირითადი იდეაა აპლიკაციების აწყობა დამოუკიდებელი ფუნქციებისგან, რომლებიც ერთმანეთთან დაკავშირებულია ნათელი და ლაკონური API-ებით.

ეს სახელმძღვანელო გაგაცნობთ არქიტექტურის პრინციპებს და დაგეხმარებათ აპლიკაციის ფუნქციების იდენტიფიცირებასა და ორგანიზებაში სხვადასხვა შრეებში. ასევე მოგაწვდით რჩევებს, ინსტრუმენტებსა და რეკომენდაციებს, თუ გადაწყვეტთ ამ არქიტექტურის გამოყენებას.

> [!NOTE]
> **µFeatures**
>
> ამ არქიტექტურას ადრე µFeatures ეწოდებოდა. ჩვენ გადავარქვით სახელი The Modular Architecture (TMA), რათა უკეთ ასახოს მისი დანიშნულება და მის საფუძვლად მდებარე პრინციპები.


## ძირითადი პრინციპი {#core-principle}

დეველოპერებს უნდა შეეძლოთ **ააწყონ, გაატესტონ და გამოსცადონ** თავიანთი ფუნქციები სწრაფად, მთავარი აპლიკაციისგან დამოუკიდებლად, ისე, რომ Xcode-ის ისეთი ფუნქციები, როგორიცაა UI-ის პრევიუები, კოდის ავტოშევსება და დებაგინგი, საიმედოდ მუშაობდეს.

## რა არის მოდული {#what-is-a-module}

მოდული წარმოადგენს აპლიკაციის ფუნქციას და შედგება შემდეგი ხუთი ტარგეტისგან (სადაც ტარგეტი ეხება Xcode-ის ტარგეტს):

- **Source:** შეიცავს ფუნქციის საწყის კოდს (Swift, Objective-C, C++, JavaScript...) და მის რესურსებს (სურათები, შრიფტები, storyboard-ები, xib-ები).
- **Interface:** ეს არის თანმხლები ტარგეტი, რომელიც შეიცავს ფუნქციის საჯარო ინტერფეისსა და მოდელებს.
- **Tests:** შეიცავს ფუნქციის unit და ინტეგრაციულ ტესტებს.
- **Testing:** უზრუნველყოფს სატესტო მონაცემებს, რომლებიც შეიძლება გამოყენებულ იქნას ტესტებში და მაგალითის აპლიკაციაში. ასევე უზრუნველყოფს მოკებს მოდულის კლასებისა და პროტოკოლებისთვის, რომლებიც სხვა ფუნქციებმა შეიძლება გამოიყენონ, როგორც ქვემოთ ვნახავთ.
- **Example:** შეიცავს მაგალითის აპლიკაციას, რომლის გამოყენებაც დეველოპერებს შეუძლიათ ფუნქციის გარკვეულ პირობებში გამოსაცდელად (სხვადასხვა ენები, ეკრანის ზომები, პარამეტრები).

ჩვენ გირჩევთ დაიცვათ ტარგეტების სახელდების კონვენცია, რისი განხორციელებაც Tuist-ის DSL-ის მეშვეობით შეგიძლიათ თქვენს პროექტში.

| ტარგეტი | დამოკიდებულებები | შემცველობა |
| ---- | ---- | ---- |
| `Feature` | `FeatureInterface` | საწყისი კოდი და რესურსები |
| `FeatureInterface` | - | საჯარო ინტერფეისი და მოდელები |
| `FeatureTests` | `Feature`, `FeatureTesting` | Unit და ინტეგრაციული ტესტები |
| `FeatureTesting` | `FeatureInterface` | სატესტო მონაცემები და მოკები |
| `FeatureExample` | `FeatureTesting`, `Feature` | მაგალითის აპლიკაცია |

> [!TIP]
> **UI პრევიუები**
>
> `Feature`-ს შეუძლია გამოიყენოს `FeatureTesting` როგორც Development Asset UI პრევიუების შესაძლებლობისთვის


> [!WARNING]
> **კომპილატორის დირექტივები სატესტო ტარგეტების ნაცვლად**
>
> ალტერნატიულად, შეგიძლიათ გამოიყენოთ კომპილატორის დირექტივები სატესტო მონაცემებისა და მოკების ჩასართავად `Feature` ან `FeatureInterface` ტარგეტებში `Debug`-თვის კომპილაციისას. თქვენ ამარტივებთ გრაფს, მაგრამ საბოლოოდ დააკომპილირებთ კოდს, რომელიც აპლიკაციის გასაშვებად არ დაგჭირდებათ.


## რატომ მოდული {#why-a-module}

### ნათელი და ლაკონური API-ები {#clear-and-concise-apis}

როდესაც აპლიკაციის მთელი საწყისი კოდი ერთსა და იმავე ტარგეტშია, ძალიან მარტივია კოდში იმპლიციტური დამოკიდებულებების აწყობა და საბოლოოდ მივიღოთ ე.წ. სპაგეტის კოდი. ყველაფერი მჭიდროდ არის დაკავშირებული, მდგომარეობა ზოგჯერ არაპროგნოზირებადია, ხოლო ახალი ცვლილებების შეტანა кошმარად იქცევა. როდესაც ფუნქციებს დამოუკიდებელ ტარგეტებში ვაწერთ, საჯარო API-ების დაპროექტება ფუნქციის იმპლემენტაციის ნაწილად უნდა გავხადოთ. უნდა გადავწყვიტოთ, რა უნდა იყოს საჯარო, როგორ უნდა მოხმარდეს ჩვენი ფუნქცია და რა უნდა დარჩეს პრივატული. ჩვენ გვაქვს მეტი კონტროლი იმაზე, თუ როგორ გვინდა, რომ ფუნქციის მომხმარებლებმა გამოიყენონ ის და შეგვიძლია დავაცვათ კარგი პრაქტიკები უსაფრთხო API-ების დაპროექტებით.

### მცირე მოდულები {#small-modules}

[დაყავი და იბატონე](https://en.wikipedia.org/wiki/Divide_and_conquer). მცირე მოდულებზე მუშაობა საშუალებას გაძლევთ უფრო მეტად ფოკუსირდეთ და ფუნქცია იზოლირებულად გაატესტოთ და გამოსცადოთ. უფრო მეტიც, განვითარების ციკლები გაცილებით სწრაფია, რადგან გვაქვს უფრო სელექციური კომპილაცია — ვაკომპილირებთ მხოლოდ იმ კომპონენტებს, რომლებიც ფუნქციის მუშაობისთვისაა აუცილებელი. მთლიანი აპლიკაციის კომპილაცია მხოლოდ ჩვენი სამუშაოს ბოლოსაა საჭირო, როდესაც ფუნქციის აპლიკაციაში ინტეგრირება გვჭირდება.

### გამოყენებადობა {#reusability}

კოდის ხელახლა გამოყენება აპლიკაციებსა და სხვა პროდუქტებში, როგორიცაა გაფართოებები, წახალისებულია ფრეიმვორკების ან ბიბლიოთეკების გამოყენებით. მოდულების აწყობით მათი ხელახლა გამოყენება საკმაოდ მარტივია. შეგვიძლია ავაწყოთ iMessage გაფართოება, Today Extension ან watchOS აპლიკაცია უბრალოდ არსებული მოდულების გაერთიანებით და _(საჭიროების შემთხვევაში)_ პლატფორმისთვის სპეციფიკური UI შრეების დამატებით.

## დამოკიდებულებები {#dependencies}

როდესაც ერთი მოდული მეორეზეა დამოკიდებული, ის აცხადებს დამოკიდებულებას მისი ინტერფეისის ტარგეტზე. ამის სარგებელი ორმაგია. ის ხელს უშლის ერთი მოდულის იმპლემენტაციის მეორე მოდულის იმპლემენტაციასთან დაკავშირებას და აჩქარებს clean ბილდებს, რადგან მათ მხოლოდ ჩვენი ფუნქციის იმპლემენტაციისა და პირდაპირი და ტრანზიტული დამოკიდებულებების ინტერფეისების კომპილაცია სჭირდებათ. ეს მიდგომა შთაგონებულია SwiftRock-ის იდეით [iOS Build Times-ის შემცირება ინტერფეისის მოდულების გამოყენებით](https://swiftrocks.com/reducing-ios-build-times-by-using-interface-targets).

ინტერფეისებზე დამოკიდებულება მოითხოვს, რომ აპლიკაციებმა runtime-ზე ააწყონ იმპლემენტაციების გრაფი და dependency-inject გაუკეთონ იმ მოდულებს, რომლებსაც ეს სჭირდებათ. მიუხედავად იმისა, რომ TMA არ აწესებს კონკრეტულ წესებს ამის გაკეთებისთვის, ჩვენ გირჩევთ გამოიყენოთ dependency-injection-ის გადაწყვეტილებები ან შაბლონები, რომლებიც არ ამატებენ build-time ინდირექციებს ან არ იყენებენ პლატფორმის API-ებს, რომლებიც ამ მიზნისთვის არ არის შექმნილი.

## პროდუქტის ტიპები {#product-types}

მოდულის აწყობისას შეგიძლიათ აირჩიოთ **ბიბლიოთეკები და ფრეიმვორკები**, ასევე **სტატიკური და დინამიკური ბმვა** ტარგეტებისთვის. Tuist-ის გარეშე ამ გადაწყვეტილების მიღება ოდნავ რთულია, რადგან დამოკიდებულებების გრაფის ხელით კონფიგურირება გჭირდებათ. თუმცა, Tuist Projects-ის წყალობით, ეს აღარ არის პრობლემა.

ჩვენ გირჩევთ განვითარების დროს გამოიყენოთ დინამიკური ბიბლიოთეკები ან ფრეიმვორკები <.localized_link href="/guides/features/projects/synthesized-files#bundle-accessors">bundle accessors</.localized_link>-ის გამოყენებით, რათა bundle-ზე წვდომის ლოგიკა გამოყოთ ტარგეტის ბიბლიოთეკის ან ფრეიმვორკის ბუნებიდან. ეს გადამწყვეტია სწრაფი კომპილაციის დროისთვის და იმის უზრუნველსაყოფად, რომ [SwiftUI Previews](https://developer.apple.com/documentation/swiftui/previews-in-xcode) საიმედოდ მუშაობდეს. ხოლო release ბილდებისთვის — სტატიკური ბიბლიოთეკები ან ფრეიმვორკები, რათა აპლიკაცია სწრაფად ჩაიტვირთოს. შეგიძლიათ გამოიყენოთ <.localized_link href="/guides/features/projects/dynamic-configuration#configuration-through-environment-variables">დინამიკური კონფიგურაცია</.localized_link> პროდუქტის ტიპის გენერაციის დროს შეცვლისთვის:

```bash
# You'll have to read the value of the variable from the manifest
# and use it to change the linking type
TUIST_PRODUCT_TYPE=static-library tuist generate
```

```swift
// You can place this in your manifest files or helpers
// and use the returned value when instantiating targets.
func productType() -> Product {
    if case let .string(productType) = Environment.productType {
        return productType == "static-library" ? .staticLibrary : .framework
    } else {
        return .framework
    }
}
```


> [!WARNING]
> **შეერთებადი ბიბლიოთეკები**
>
> Apple-მა სცადა სტატიკურ და დინამიკურ ბიბლიოთეკებს შორის გადართვის სირთულის შემსუბუქება [შეერთებადი ბიბლიოთეკების](https://developer.apple.com/documentation/xcode/configuring-your-project-to-use-mergeable-libraries) წარმოდგენით. თუმცა, ეს ამატებს აწყობის დროის არადეტერმინიზმს, რაც ბილდს არაწარმოებადს ხდის და ოპტიმიზაციას ურთულებს, ამიტომ ჩვენ მის გამოყენებას არ გირჩევთ.


## კოდი {#code}

TMA არ აწესებს კონკრეტულ მოთხოვნებს თქვენი მოდულების კოდის არქიტექტურისა და შაბლონების მიმართ. თუმცა, გვსურს გაგიზიაროთ რჩევები ჩვენი გამოცდილებიდან:

- **კომპილატორის გამოყენება შესანიშნავია.** კომპილატორზე ზედმეტი დაყრდნობა შეიძლება არაეფექტური აღმოჩნდეს და გამოიწვიოს ისეთი Xcode ფუნქციების, როგორიცაა previews, არასაიმედო მუშაობა. ჩვენ გირჩევთ კომპილატორის გამოყენებას კარგი პრაქტიკების დასაცავად და შეცდომების ადრეულ ეტაპზე აღმოსაჩენად, მაგრამ არა იმ დონემდე, რომ კოდის წაკითხვა და შენარჩუნება გაუჭირდეთ.
- **Swift Macros ზომიერად გამოიყენეთ.** ისინი შეიძლება ძალიან ძლიერი იყოს, მაგრამ ასევე შეუძლიათ კოდის წაკითხვა და შენარჩუნება გაუძნელონ.
- **მიიღეთ პლატფორმა და ენა, ნუ გააკეთებთ მათ აბსტრაქციას.** რთული აბსტრაქციის ფენების შექმნის მცდელობა შეიძლება საპირისპირო ეფექტი მოახდინოს. პლატფორმა და ენა საკმარისად ძლიერია შესანიშნავი აპლიკაციების აწყობისთვის დამატებითი აბსტრაქციის ფენების გარეშე. გამოიყენეთ კარგი პროგრამირებისა და დიზაინის შაბლონები, როგორც მინიშნება თქვენი ფუნქციების აწყობისას.
