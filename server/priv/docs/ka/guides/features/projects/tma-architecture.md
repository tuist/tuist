# მოდულური არქიტექტურა (TMA) {#the-modular-architecture-tma}

TMA არის არქიტექტურული მიდგომა აპლიკაციების სტრუქტურირებისთვის, რაც უზრუნველყოფს მასშტაბირებადობას, აოპტიმიზებს ბილდისა და ტესტირების ციკლებს და გუნდში კარგი პრაქტიკების დაცვას. მისი ძირითადი იდეაა აპლიკაციების აწყობა დამოუკიდებელი ფუნქციებისგან, რომლებიც ერთმანეთთან დაკავშირებულია ნათელი და ლაკონიური API-ებით.

ეს სახელმძღვანელო გაგაცნობთ არქიტექტურის პრინციპებს, რაც დაგეხმარებათ აპლიკაციის ფუნქციების იდენტიფიცირებასა და ორგანიზებაში სხვადასხვა შრეებში. ასევე მოგაწვდით რჩევებს, ინსტრუმენტებსა და რეკომენდაციებს, თუ გადაწყვეტთ ამ არქიტექტურის გამოყენებას.

> [!NOTE]
> **Μfeatures**
>
> ამ არქიტექტურას წარსულში µFeatures ეწოდებოდა. ჩვენ გადავარქვით სახელი The Modular Architecture (TMA), რათა უკეთესად ასახოს მისი დანიშნულება და მის უკან მდგარი პრინციპები.


## ძირითადი პრინციპი {#core-principle}

დეველოპერებს უნდა შეეძლოთ **ააწყონ, შეამოწმონ და გამოსცადონ** თავიანთი ფუნქციები სწრაფად, მთავარი აპლიკაციისგან დამოუკიდებლად, ისე, რომ Xcode-ის ისეთი ფუნქციები, როგორიცაა UI-ის პრევიუები, კოდის ავტოშევსება და დებაგინგი, საიმედოდ მუშაობდეს.

## რა არის მოდული {#what-is-a-module}

მოდული წარმოადგენს აპლიკაციის ფუნქციას და შედგება შემდეგი ხუთი ტარგეტისგან (სადაც ტარგეტი ეხება Xcode-ის ტარგეტს):

- **Source:** შეიცავს ფუნქციის საწყის კოდს (Swift, Objective-C, C++, JavaScript...) და მის რესურსებს (სურათები, შრიფტები, storyboard-ები, xib-ები).
- **Interface:** ეს არის თანმხლები ტარგეტი, რომელიც შეიცავს ფუნქციის საჯარო ინტერფეისსა და მოდელებს.
- **Tests:** შეიცავს ფუნქციის ერთეულოვან (unit) და ინტეგრაციულ ტესტებს.
- **Testing:** უზრუნველყოფს სატესტო მონაცემებს, რომლებიც შეიძლება გამოყენებულ იქნას ტესტებში და სადემო აპლიკაციაში. ასევე უზრუნველყოფს მოკებს მოდულის კლასებისა და პროტოკოლებისთვის, რომლებიც სხვა ფუნქციებმა შეიძლება გამოიყენონ, როგორც ქვემოთ ვნახავთ.
- **Example:** შეიცავს სადემო აპლიკაციას, რომლის გამოყენებაც დეველოპერებს შეუძლიათ ფუნქციის გამოსაცდელად გარკვეულ პირობებში (სხვადასხვა ენები, ეკრანის ზომები, პარამეტრები).

ჩვენ გირჩევთ დაიცვათ სახელდების კონვენცია ტარგეტებისთვის, რისი დაცვაც პროექტში შეგიძლიათ Tuist-ის DSL-ის მეშვეობით.

| ტარგეტი | დამოკიდებულებები | შემცველობა |
| ---- | ---- | ---- |
| `Feature` | `FeatureInterface` | საწყისი კოდი და რესურსები |
| `FeatureInterface` | - | საჯარო ინტერფეისი და მოდელები |
| `FeatureTests` | `Feature`, `FeatureTesting` | ერთეულოვანი და ინტეგრაციული ტესტები |
| `FeatureTesting` | `FeatureInterface` | სატესტო მონაცემები და მოკები |
| `FeatureExample` | `FeatureTesting`, `Feature` | სადემო აპლიკაცია |

> [!TIP]
> **UI პრევიუები**
>
> `Feature`-ს შეუძლია გამოიყენოს `FeatureTesting` როგორც Development Asset UI პრევიუებისთვის


> [!WARNING]
> **კომპილატორის დირექტივები სატესტო ტარგეტების ნაცვლად**
>
> ალტერნატიულად, შეგიძლიათ გამოიყენოთ კომპილატორის დირექტივები სატესტო მონაცემებისა და მოკების ჩასართავად `Feature` ან `FeatureInterface` ტარგეტებში `Debug`-ზე კომპილაციისას. ეს ამარტივებს გრაფს, მაგრამ საბოლოოდ დააკომპილირებთ კოდს, რომელიც აპლიკაციის გასაშვებად არ დაგჭირდებათ.


## რატომ მოდული {#why-a-module}

### ნათელი და ლაკონიური API-ები {#clear-and-concise-apis}

როდესაც აპლიკაციის მთელი საწყისი კოდი ერთსა და იმავე ტარგეტშია, ძალიან მარტივია კოდში იმპლიციტური დამოკიდებულებების აწყობა და საბოლოოდ ცნობილი „სპაგეტის კოდის“ მიღება. ყველაფერი მჭიდროდ არის დაკავშირებული, მდგომარეობა ზოგჯერ არაპროგნოზირებადია და ახალი ცვლილებების შეტანა კოშმარად იქცევა. როდესაც ფუნქციებს დამოუკიდებელ ტარგეტებში ვგანსაზღვრავთ, საჯარო API-ების დაპროექტება ფუნქციის იმპლემენტაციის ნაწილი ხდება. უნდა გადავწყვიტოთ, რა უნდა იყოს საჯარო, როგორ უნდა მოხდეს ჩვენი ფუნქციის გამოყენება და რა უნდა დარჩეს პრივატული. უფრო მეტი კონტროლი გვაქვს იმაზე, თუ როგორ გვინდა, რომ ფუნქციის კლიენტებმა გამოიყენონ ის და შეგვიძლია დავაცვათ კარგი პრაქტიკები უსაფრთხო API-ების დაპროექტებით.

### მცირე მოდულები {#small-modules}

[დაყავი და იბატონე](https://en.wikipedia.org/wiki/Divide_and_conquer). მცირე მოდულებზე მუშაობა საშუალებას გაძლევთ იყოთ უფრო ფოკუსირებული და ფუნქცია იზოლირებულად შეამოწმოთ და გამოსცადოთ. უფრო მეტიც, განვითარების ციკლები ბევრად უფრო სწრაფია, რადგან გვაქვს უფრო სელექციური კომპილაცია — კომპილირდება მხოლოდ ის კომპონენტები, რომლებიც ფუნქციის სამუშაოდ არის აუცილებელი. მთლიანი აპლიკაციის კომპილაცია მხოლოდ ჩვენი მუშაობის ბოლოს არის საჭირო, როდესაც ფუნქციის აპლიკაციაში ინტეგრირება გვჭირდება.

### გამოყენებადობა {#reusability}

კოდის ხელახლა გამოყენება აპლიკაციებსა და სხვა პროდუქტებში, მაგალითად გაფართოებებში, წახალისებულია ფრეიმვორკების ან ბიბლიოთეკების გამოყენებით. მოდულების აწყობით მათი ხელახლა გამოყენება საკმაოდ მარტივია. შეგვიძლია ავაწყოთ iMessage გაფართოება, Today Extension ან watchOS აპლიკაცია არსებული მოდულების კომბინირებით და _(საჭიროების შემთხვევაში)_ პლატფორმისთვის სპეციფიკური UI შრეების დამატებით.

## დამოკიდებულებები {#dependencies}

როდესაც ერთი მოდული მეორეზეა დამოკიდებული, ის აცხადებს დამოკიდებულებას მისი ინტერფეისის ტარგეტზე. ამის უპირატესობა ორმაგია. ეს ხელს უშლის ერთი მოდულის იმპლემენტაციის მეორესთან დაკავშირებას და აჩქარებს სუფთა ბილდებს, რადგან მათ მხოლოდ ჩვენი ფუნქციის იმპლემენტაციისა და პირდაპირი და ტრანზიტული დამოკიდებულებების ინტერფეისების კომპილაცია სჭირდებათ. ეს მიდგომა შთაგონებულია SwiftRock-ის იდეით [iOS ბილდის დროების შემცირება ინტერფეისის მოდულების გამოყენებით](https://swiftrocks.com/reducing-ios-build-times-by-using-interface-targets).

ინტერფეისებზე დამოკიდებულება მოითხოვს, რომ აპლიკაციებმა რანთაიმზე ააწყონ იმპლემენტაციების გრაფი და შეიტანონ დამოკიდებულება იმ მოდულებში, რომლებსაც ეს სჭირდებათ. მიუხედავად იმისა, რომ TMA არ არის მიკერძოებული იმის მიმართ, თუ როგორ უნდა გაკეთდეს ეს, ჩვენ გირჩევთ გამოიყენოთ დამოკიდებულების ინჟექციის გადაწყვეტილებები ან შაბლონები, რომლებიც არ ამატებენ ბილდის დროის ინდირექციებს ან არ იყენებენ პლატფორმის API-ებს, რომლებიც ამ მიზნისთვის არ არის განკუთვნილი.

## პროდუქტის ტიპები {#product-types}

მოდულის აწყობისას შეგიძლიათ აირჩიოთ **ბიბლიოთეკები და ფრეიმვორკები**, ასევე **სტატიკური და დინამიური ლინკინგი** ტარგეტებისთვის. Tuist-ის გარეშე ამ გადაწყვეტილების მიღება ოდნავ უფრო რთულია, რადგან დამოკიდებულების გრაფის ხელით კონფიგურირებაა საჭირო. თუმცა, Tuist Projects-ის წყალობით, ეს აღარ არის პრობლემა.

ჩვენ გირჩევთ განვითარების დროს გამოიყენოთ დინამიური ბიბლიოთეკები ან ფრეიმვორკები <.localized_link href="/guides/features/projects/synthesized-files#bundle-accessors">ბანდლის აქსესორების</.localized_link> გამოყენებით, რათა ბანდლზე წვდომის ლოგიკა გამოყოთ ტარგეტის ბიბლიოთეკის ან ფრეიმვორკის ბუნებიდან. ეს გადამწყვეტია სწრაფი კომპილაციის დროებისთვის და იმის უზრუნველსაყოფად, რომ [SwiftUI პრევიუები](https://developer.apple.com/documentation/swiftui/previews-in-xcode) საიმედოდ მუშაობდეს. ხოლო რელიზის ბილდებისთვის — სტატიკური ბიბლიოთეკები ან ფრეიმვორკები, რათა აპლიკაცია სწრაფად ჩაირთოს. შეგიძლიათ გამოიყენოთ <.localized_link href="/guides/features/projects/dynamic-configuration#configuration-through-environment-variables">დინამიური კონფიგურაცია</.localized_link> პროდუქტის ტიპის გენერაციის დროს შესაცვლელად:

```bash
# You'll have to read the value of the variable from the manifest {#youll-have-to-read-the-value-of-the-variable-from-the-manifest}
# and use it to change the linking type {#and-use-it-to-change-the-linking-type}
TUIST_PRODUCT_TYPE=static-library tuist generate
```

```swift
// You can place this in your manifest files or helpers
// and use the returned value when instantiating targets.
func productType() -> Product {
    if case let .string(productType) = Environment.productType {
        return productType == "static-library" ? .staticLibrary : .framework
    } else {
        return .framework
    }
}
```

> **შეთავსებადი ბიბლიოთეკები**
>
> Apple-მა სცადა შეემსუბუქებინა სტატიკურ და დინამიურ ბიბლიოთეკებს შორის გადართვის სირთულე [შეთავსებადი ბიბლიოთეკების](https://developer.apple.com/documentation/xcode/configuring-your-project-to-use-mergeable-libraries) შემოღებით. თუმცა, ეს ამატებს აწყობის დროს არადეტერმინიზმს, რაც ბილდს არარეპროდუცირებადს ხდის და ოპტიმიზაციას ურთულებს, ამიტომ მის გამოყენებას არ გირჩევთ.


## კოდი {#code}

TMA არ აწესებს კონკრეტულ მოთხოვნებს თქვენი მოდულების კოდის არქიტექტურისა და პატერნების მიმართ. თუმცა, ჩვენ გვსურს გაგიზიაროთ რამდენიმე რჩევა ჩვენი გამოცდილებიდან:

- **კომპილატორის გამოყენება სასარგებლოა.** კომპილატორზე ზედმეტი დაყრდნობა შეიძლება არაეფექტური აღმოჩნდეს და გამოიწვიოს ის, რომ Xcode-ის ზოგიერთი ფუნქცია, მაგალითად პრევიუები, არასაიმედოდ იმუშაოს. ჩვენ გირჩევთ გამოიყენოთ კომპილატორი კარგი პრაქტიკების დასაცავად და შეცდომების ადრეულ ეტაპზე აღმოსაჩენად, მაგრამ არა იმ დონემდე, რომ კოდის წაკითხვა და შენარჩუნება გაუჭირდეს.
- **Swift Macros გონივრულად გამოიყენეთ.** ისინი ძალიან ძლიერი ინსტრუმენტებია, მაგრამ ასევე შეუძლიათ კოდის წაკითხვა და შენარჩუნება გაართულონ.
- **მიჰყევით პლატფორმას და ენას, ნუ შექმნით მათ აბსტრაქციებს.** რთული აბსტრაქციის შრეების შექმნა შეიძლება საპირისპირო ეფექტი მოახდინოს. პლატფორმა და ენა საკმარისად ძლიერია შესანიშნავი აპლიკაციების ასაწყობად დამატებითი აბსტრაქციის შრეების საჭიროების გარეშე. თქვენი ფუნქციების ასაწყობად გამოიყენეთ კარგი პროგრამირებისა და დიზაინის პატერნები როგორც სახელმძღვანელო.
