# ჰეშინგი {#hashing}

<.localized_link href="/guides/features/cache">ქეშირების</.localized_link> ან შერჩევითი ტესტების შესრულების მსგავს ფუნქციებს სჭირდებათ გზა იმის დასადგენად, შეიცვალა თუ არა სამიზნე. Tuist დამოკიდებულებათა გრაფში თითოეული სამიზნისთვის ჰეშს ითვლის, რათა დაადგინოს, შეიცვალა თუ არა სამიზნე. ჰეში გამოითვლება შემდეგი ატრიბუტების საფუძველზე:

- სამიზნის ატრიბუტები (მაგ., სახელი, პლატფორმა, პროდუქტი და ა.შ.)
- სამიზნის ფაილები
- სამიზნის დამოკიდებულებების ჰეში

## ქეშის ატრიბუტები {#cache-attributes}

დამატებით, <.localized_link href="/guides/features/cache">ქეშირებისთვის</.localized_link> ჰეშის გამოთვლისას ჩვენ ასევე ვაჰეშავთ შემდეგ ატრიბუტებს.

### Swift-ის ვერსია {#swift-version}

ჩვენ ვაჰეშავთ Swift-ის ვერსიას, რომელიც მიღებულია `/usr/bin/xcrun swift --version` ბრძანების გაშვებით, რათა თავიდან ავიცილოთ კომპილაციის შეცდომები სამიზნეებსა და ბინარებს შორის Swift-ის ვერსიების შეუსაბამობის გამო.

> [!NOTE]
> **მოდულის სტაბილურობა**
>
> ბინარული ქეშირების წინა ვერსიები ეყრდნობოდნენ `BUILD_LIBRARY_FOR_DISTRIBUTION` აგების პარამეტრს, რათა ჩართულიყო [მოდულის სტაბილურობა](https://www.swift.org/blog/library-evolution#enabling-library-evolution-support) და შესაძლებელი ყოფილიყო ბინარების გამოყენება ნებისმიერი კომპილატორის ვერსიით. თუმცა, ეს იწვევდა კომპილაციის პრობლემებს ისეთ პროექტებში, რომლებსაც ჰქონდათ სამიზნეები მოდულის სტაბილურობის მხარდაჭერის გარეშე. გენერირებული ბინარები მიბმულია მათი კომპილაციისთვის გამოყენებულ Swift-ის ვერსიაზე და Swift-ის ვერსია უნდა ემთხვეოდეს პროექტის კომპილაციისთვის გამოყენებულ ვერსიას.


### კონფიგურაცია {#configuration}

ქეშის ჰეშების გამოთვლისას Tuist თითოეული პროექტისა და სამიზნის პარამეტრებს ანიჭებს გადაწყვეტილ აგების კონფიგურაციას. ეს არის ის, რომელსაც სახელი ენიჭება `--configuration`-ით, წინააღმდეგ შემთხვევაში პროექტის `defaultConfiguration`, წინააღმდეგ შემთხვევაში — პირველი debug კონფიგურაცია. Tuist აჰეშავს ამ კონფიგურაციის სახელს, ვარიანტს, აგების პარამეტრებს და კონფიგურაციის ფაილის შინაარსს მასზე მოქმედ საერთო საბაზისო პარამეტრებთან ერთად. სხვა კონფიგურაციის დამატება, წაშლა ან შეცვლა არ მოქმედებს გადაწყვეტილი კონფიგურაციის ქეშის ჰეშებზე. რადგან მხოლოდ გადაწყვეტილ კონფიგურაციას აქვს მნიშვნელობა, ცხადად მითითებული `--configuration`-ით შევსებული ქეში წაკითხვადია ბრძანებისთვის, რომელიც იმავე კონფიგურაციას წყვეტს ფლაგის გადაცემის გარეშე.

## გამართვა {#debugging}

თუ შენიშნავთ არადეტერმინისტულ ქცევას ქეშირების გამოყენებისას სხვადასხვა გარემოში ან გამოძახებისას, ეს შეიძლება იყოს დაკავშირებული გარემოებს შორის განსხვავებებთან ან ჰეშინგის ლოგიკაში არსებულ ბაგთან. ჩვენ გირჩევთ, პრობლემის გამოსასწორებლად მიჰყვეთ შემდეგ ნაბიჯებს:

1. გაუშვით `tuist hash cache` ან `tuist hash selective-testing` (<.localized_link href="/guides/features/cache">ბინარული ქეშირების</.localized_link> ან <.localized_link href="/guides/features/selective-testing">შერჩევითი ტესტირების</.localized_link> ჰეშები), დააკოპირეთ ჰეშები, შეუცვალეთ სახელი პროექტის საქაღალდეს და ხელახლა გაუშვით ბრძანება. ჰეშები უნდა ემთხვეოდეს.
2. თუ ჰეშები არ ემთხვევა, სავარაუდოდ, გენერირებული პროექტი დამოკიდებულია გარემოზე. ორივე შემთხვევაში გაუშვით `tuist graph --format json` და შეადარეთ გრაფები. ალტერნატიულად, შექმენით პროექტები და შეადარეთ მათი `project.pbxproj` ფაილები diff ინსტრუმენტით, მაგალითად, [Diffchecker](https://www.diffchecker.com).
3. თუ ჰეშები იდენტურია, მაგრამ განსხვავდება სხვადასხვა გარემოში (მაგალითად, CI და ლოკალური), დარწმუნდით, რომ ყველგან გამოიყენება ერთი და იგივე [კონფიგურაცია](#configuration) და [Swift-ის ვერსია](#swift-version). Swift-ის ვერსია დაკავშირებულია Xcode-ის ვერსიასთან, ამიტომ დაადასტურეთ, რომ Xcode-ის ვერსიები ემთხვევა.

თუ ჰეშები კვლავ არადეტერმინისტულია, შეგვატყობინეთ და ჩვენ დაგეხმარებით გამართვაში.


> [!NOTE]
> **გამართვის გაუმჯობესებული გამოცდილება დაგეგმილია**
>
> ჩვენი გამართვის გამოცდილების გაუმჯობესება შედის ჩვენს სამუშაო გეგმაში. print-hashes ბრძანება, რომელსაც აკლია კონტექსტი განსხვავებების გასაგებად, ჩანაცვლდება უფრო მოსახერხებელი ბრძანებით, რომელიც ხისებრი სტრუქტურის გამოყენებით აჩვენებს ჰეშებს შორის განსხვავებებს.
