# ჰეშინგი {#hashing}

<.localized_link href="/guides/features/cache">კეშირების</.localized_link> ან შერჩევითი ტესტების შესრულების მსგავს ფუნქციებს სჭირდებათ გზა იმის დასადგენად, შეიცვალა თუ არა სამიზნე. Tuist ითვლის ჰეშს დამოკიდებულებების გრაფში არსებული თითოეული სამიზნისთვის, რათა დაადგინოს, შეიცვალა თუ არა ის. ჰეში გამოითვლება შემდეგი ატრიბუტების მიხედვით:

- სამიზნის ატრიბუტები (მაგ., სახელი, პლატფორმა, პროდუქტი და ა.შ.)
- სამიზნის ფაილები
- სამიზნის დამოკიდებულებების ჰეში

## კეშის ატრიბუტები {#cache-attributes}

დამატებით, <.localized_link href="/guides/features/cache">კეშირებისთვის</.localized_link> ჰეშის გამოთვლისას, ჩვენ ასევე ვაჰეშავთ შემდეგ ატრიბუტებს.

### Swift-ის ვერსია {#swift-version}

ჩვენ ვაჰეშავთ Swift-ის ვერსიას, რომელიც მიღებულია `/usr/bin/xcrun swift --version` ბრძანების გაშვებით, რათა თავიდან ავიცილოთ კომპილაციის შეცდომები სამიზნეებსა და ბინარულ ფაილებს შორის Swift-ის ვერსიების შეუსაბამობის გამო.

> [!NOTE]
> **მოდილის სტაბილურობა**
>
> ბინარული კეშირების წინა ვერსიები ეყრდნობოდნენ `BUILD_LIBRARY_FOR_DISTRIBUTION` აგების პარამეტრს, რათა ჩართულიყო [მოდილის სტაბილურობა](https://www.swift.org/blog/library-evolution#enabling-library-evolution-support) და შესაძლებელი გამხდარიყო ბინარული ფაილების გამოყენება ნებისმიერი კომპილატორის ვერსიით. თუმცა, ეს იწვევდა კომპილაციის პრობლემებს პროექტებში, რომლებსაც ჰქონდათ სამიზნეები მოდილის სტაბილურობის მხარდაჭერის გარეშე. გენერირებული ბინარული ფაილები მიბმულია მათი კომპილაციისთვის გამოყენებულ Swift-ის ვერსიაზე და Swift-ის ვერსია უნდა ემთხვეოდეს პროექტის კომპილაციისთვის გამოყენებულ ვერსიას.


### კონფიგურაცია {#configuration}

კეშის ჰეშების გამოთვლისას, Tuist ანიჭებს თითოეული პროექტისა და სამიზნის პარამეტრებს განსაზღვრულ აგების კონფიგურაციას. ეს არის ის, რომელიც მითითებულია `--configuration`-ით, წინააღმდეგ შემთხვევაში პროექტის `defaultConfiguration`, წინააღმდეგ შემთხვევაში პირველი debug კონფიგურაცია. Tuist აჰეშავს ამ კონფიგურაციის სახელს, ვარიანტს, აგების პარამეტრებსა და კონფიგურაციის ფაილის შინაარსს მასზე მოქმედ საერთო საბაზისო პარამეტრებთან ერთად. სხვა კონფიგურაციის დამატება, წაშლა ან ცვლილება არ მოქმედებს განსაზღვრული კონფიგურაციის კეშის ჰეშებზე. რადგან მხოლოდ განსაზღვრული კონფიგურაციაა მნიშვნელოვანი, ცხადად მითითებული `--configuration`-ით შევსებული კეში წაკითხვადია ბრძანებისთვის, რომელიც იგივე კონფიგურაციას ანსაზღვრავს ფლაგის გადაცემის გარეშე.

## გამართვა {#debugging}

თუ შეამჩნევთ არადეტერმინისტულ ქცევას კეშირების გამოყენებისას სხვადასხვა გარემოში ან გამოძახებისას, ეს შეიძლება დაკავშირებული იყოს გარემოებს შორის განსხვავებებთან ან ჰეშინგის ლოგიკაში არსებულ ბაგთან. ჩვენ გირჩევთ, პრობლემის გამოსასწორებლად მიჰყვეთ შემდეგ ნაბიჯებს:

1. გაუშვით `tuist hash cache` ან `tuist hash selective-testing` (<.localized_link href="/guides/features/cache">ბინარული კეშირების</.localized_link> ან <.localized_link href="/guides/features/selective-testing">შერჩევითი ტესტირების</.localized_link> ჰეშები), დააკოპირეთ ჰეშები, გადაარქვით სახელი პროექტის დირექტორიას და ხელახლა გაუშვით ბრძანება. ჰეშები უნდა ემთხვეოდეს.
2. თუ ჰეშები არ ემთხვევა, სავარაუდოდ, გენერირებული პროექტი დამოკიდებულია გარემოზე. ორივე შემთხვევაში გაუშვით `tuist graph --format json` და შეადარეთ გრაფები. ალტერნატიულად, შექმენით პროექტები და შეადარეთ მათი `project.pbxproj` ფაილები diff-ის ინსტრუმენტით, როგორიცაა [Diffchecker](https://www.diffchecker.com).
3. თუ ჰეშები ერთნაირია, მაგრამ განსხვავდება სხვადასხვა გარემოში (მაგალითად, CI და ადგილობრივ), დარწმუნდით, რომ ყველგან გამოიყენება ერთი და იგივე [კონფიგურაცია](#configuration) და [Swift-ის ვერსია](#swift-version). Swift-ის ვერსია დაკავშირებულია Xcode-ის ვერსიასთან, ამიტომ დარწმუნდით, რომ Xcode-ის ვერსიები ემთხვევა.

თუ ჰეშები კვლავ არადეტერმინისტულია, გვაცნობეთ და ჩვენ დაგეხმარებით გამართვაში.


> [!NOTE]
> **გამართვის გაუმჯობესებული გამოცდილება დაგეგმილია**
>
> ჩვენი გამართვის გამოცდილების გაუმჯობესება შედის ჩვენს სამოქმედო გეგმაში. print-hashes ბრძანება, რომელსაც აკლია კონტექსტი განსხვავებების გასაგებად, ჩანაცვლდება უფრო მოსახერხებელი ბრძანებით, რომელიც ხის მსგავს სტრუქტურას იყენებს ჰეშებს შორის განსხვავებების საჩვენებლად.
