# ჰეშინგი {#hashing}

<.localized_link href="/guides/features/cache">ქეშირების</.localized_link> ან შერჩევითი ტესტების შესრულების მსგავს ფუნქციებს სჭირდებათ გზა, რათა დაადგინონ, შეიცვალა თუ არა სამიზნე. Tuist ითვლის ჰეშს დამოკიდებულებების გრაფის თითოეული სამიზნისთვის, რათა დაადგინოს, შეიცვალა თუ არა სამიზნე. ჰეში გამოითვლება შემდეგი ატრიბუტების საფუძველზე:

- სამიზნის ატრიბუტები (მაგ., სახელი, პლატფორმა, პროდუქტი და ა.შ.)
- სამიზნის ფაილები
- სამიზნის დამოკიდებულებების ჰეში

### ქეშის ატრიბუტები {#cache-attributes}

დამატებით, <.localized_link href="/guides/features/cache">ქეშირების</.localized_link> ჰეშის გამოთვლისას, ჩვენ ასევე ვაჰეშავთ შემდეგ ატრიბუტებს.

#### Swift-ის ვერსია {#swift-version}

ჩვენ ვაჰეშავთ Swift-ის ვერსიას, რომელიც მიღებულია `/usr/bin/xcrun swift --version` ბრძანების გაშვებით, რათა თავიდან ავიცილოთ კომპილაციის შეცდომები სამიზნეებსა და ბინარებს შორის Swift-ის ვერსიების შეუსაბამობის გამო.

> [!NOTE]
> **მოდულის სტაბილურობა**
>
> ბინარული ქეშირების წინა ვერსიები ეყრდნობოდა `BUILD_LIBRARY_FOR_DISTRIBUTION` აგების პარამეტრს [მოდულის სტაბილურობის](https://www.swift.org/blog/library-evolution#enabling-library-evolution-support) ჩასართავად და ნებისმიერი კომპილატორის ვერსიით ბინარების გამოყენების შესაძლებლობის უზრუნველსაყოფად. თუმცა, ეს იწვევდა კომპილაციის პრობლემებს პროექტებში ისეთი სამიზნეებით, რომლებიც არ უჭერენ მხარს მოდულის სტაბილურობას. გენერირებული ბინარები მიბმულია მათი კომპილაციისთვის გამოყენებულ Swift-ის ვერსიაზე და Swift-ის ვერსია უნდა ემთხვეოდეს პროექტის კომპილაციისთვის გამოყენებულ ვერსიას.


#### კონფიგურაცია {#configuration}

ქეშის ჰეშების გამოთვლისას, Tuist თითოეული პროექტისა და სამიზნის პარამეტრებს ანიჭებს განსაზღვრულ აგების კონფიგურაციას. ეს არის ის, რომელიც მითითებულია `--configuration`-ით, წინააღმდეგ შემთხვევაში პროექტის `defaultConfiguration`, წინააღმდეგ შემთხვევაში პირველი debug კონფიგურაცია. Tuist აჰეშავს ამ კონფიგურაციის სახელს, ვარიანტს, აგების პარამეტრებსა და კონფიგურაციის ფაილის შინაარსს მასზე გამოყენებად საერთო საბაზისო პარამეტრებთან ერთად. სხვა კონფიგურაციის დამატება, წაშლა ან შეცვლა არ მოქმედებს განსაზღვრული კონფიგურაციის ქეშის ჰეშებზე. ვინაიდან მხოლოდ განსაზღვრული კონფიგურაციაა მნიშვნელოვანი, ცხადად მითითებული `--configuration`-ით შევსებული ქეში წაკითხვადია ბრძანების მიერ, რომელიც იმავე კონფიგურაციას ადგენს ფლაგის გადაცემის გარეშე.

## დაგვისკა {#debugging}

თუ შეამჩნევთ არადეტერმინისტულ ქცევას ქეშირების გამოყენებისას სხვადასხვა გარემოში ან გამოძახებისას, ეს შეიძლება იყოს დაკავშირებული გარემოებს შორის განსხვავებებთან ან ჰეშინგის ლოგიკაში არსებულ ბაგთან. პრობლემის დასადგენად გირჩევთ მიჰყვეთ შემდეგ ნაბიჯებს:

1. გაუშვით `tuist hash cache` ან `tuist hash selective-testing` (<.localized_link href="/guides/features/cache">ბინარული ქეშირების</.localized_link> ან <.localized_link href="/guides/features/selective-testing">შერჩევითი ტესტირების</.localized_link> ჰეშები), დააკოპირეთ ჰეშები, შეუცვალეთ სახელი პროექტის დირექტორიას და ხელახლა გაუშვით ბრძანება. ჰეშები უნდა ემთხვეოდეს.
2. თუ ჰეშები არ ემთხვევა, სავარაუდოდ, გენერირებული პროექტი დამოკიდებულია გარემოზე. ორივე შემთხვევაში გაუშვით `tuist graph --format json` და შეადარეთ გრაფები. ალტერნატიულად, გენერირეთ პროექტები და შეადარეთ მათი `project.pbxproj` ფაილები diff-ის ინსტრუმენტით, როგორიცაა [Diffchecker](https://www.diffchecker.com).
3. თუ ჰეშები იდენტურია, მაგრამ განსხვავდება სხვადასხვა გარემოში (მაგალითად, CI და ლოკალური), დარწმუნდით, რომ ყველგან გამოყენებულია ერთი და იგივე [კონფიგურაცია](#configuration) და [Swift-ის ვერსია](#swift-version). Swift-ის ვერსია დაკავშირებულია Xcode-ის ვერსიასთან, ამიტომ დარწმუნდით, რომ Xcode-ის ვერსიები ემთხვევა.

თუ ჰეშები კვლავ არადეტერმინისტულია, შეგვატყობინეთ და დაგეხმარებით დაგვისკაში.


> [!NOTE]
> **დაგვისკის გაუმჯობესებული გამოცდილება დაგეგმილია**
>
> ჩვენი დაგვისკის გამოცდილების გაუმჯობესება შედის ჩვენს სამოქმედო გეგმაში. print-hashes ბრძანება, რომელსაც აკლია კონტექსტი განსხვავებების გასაგებად, შეიცვლება უფრო მოსახერხებელი ბრძანებით, რომელიც ხის მსგავს სტრუქტურას იყენებს ჰეშებს შორის განსხვავებების საჩვენებლად.
