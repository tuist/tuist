# ჰეშინგი {#hashing}

<.localized_link href="/guides/features/cache">ქეშირების</.localized_link> ან შერჩევითი ტესტების შესრულების მსგავს ფუნქციებს სჭირდებათ გზა იმის დასადგენად, შეიცვალა თუ არა სამიზნე. Tuist ითვლის ჰეშს დამოკიდებულებათა გრაფში ყოველი სამიზნისთვის, რათა დაადგინოს, შეიცვალა თუ არა სამიზნე. ჰეში გამოითვლება შემდეგი ატრიბუტების მიხედვით:

- სამიზნის ატრიბუტები (მაგ., სახელი, პლატფორმა, პროდუქტი და ა.შ.)
- სამიზნის ფაილები
- სამიზნის დამოკიდებულებების ჰეში

## ქეშის ატრიბუტები {#cache-attributes}

დამატებით, <.localized_link href="/guides/features/cache">ქეშირებისთვის</.localized_link> ჰეშის გამოთვლისას, ჩვენ ასევე ვაჰეშავთ შემდეგ ატრიბუტებს.

### Swift-ის ვერსია {#swift-version}

ჩვენ ვაჰეშავთ Swift-ის ვერსიას, რომელიც მიღებულია `/usr/bin/xcrun swift --version` ბრძანების გაშვებით, რათა თავიდან ავიცილოთ კომპილაციის შეცდომები Swift-ის ვერსიების შეუსაბამობის გამო სამიზნეებსა და ბინარებს შორის.

> [!NOTE]
> **მოდიულის სტაბილურობა**
>
> ბინარული ქეშირების წინა ვერსიები ეყრდნობოდნენ `BUILD_LIBRARY_FOR_DISTRIBUTION` აგების პარამეტრს [მოდიულის სტაბილურობის](https://www.swift.org/blog/library-evolution#enabling-library-evolution-support) ჩასართავად და ნებისმიერი კომპილატორის ვერსიით ბინარების გამოყენების შესაძლებლობის მისაცემად. თუმცა, ეს იწვევდა კომპილაციის პრობლემებს პროექტებში, რომლებიც შეიცავდნენ სამიზნეებს მოდიულის სტაბილურობის მხარდაჭერის გარეშე. გენერირებული ბინარები მიბმულია მათი კომპილაციისთვის გამოყენებულ Swift-ის ვერსიაზე და Swift-ის ვერსია უნდა ემთხვეოდეს პროექტის კომპილაციისთვის გამოყენებულ ვერსიას.


### კონფიგურაცია {#configuration}

ქეშის ჰეშების გამოთვლისას, Tuist ანიჭებს თითოეული პროექტისა და სამიზნის პარამეტრებს განსაზღვრულ აგების კონფიგურაციას. ეს არის ის, რომელიც მითითებულია `--configuration`-ით, წინააღმდეგ შემთხვევაში პროექტის `defaultConfiguration`, წინააღმდეგ შემთხვევაში — პირველი debug კონფიგურაცია. Tuist აჰეშავს ამ კონფიგურაციის სახელს, ვარიანტს, აგების პარამეტრებსა და კონფიგურაციის ფაილის შინაარსს იმ საერთო საბაზისო პარამეტრებთან ერთად, რომლებიც მასზე ვრცელდება. სხვა კონფიგურაციის დამატება, წაშლა ან ცვლილება არ ახდენს გავლენას განსაზღვრული კონფიგურაციის ქეშის ჰეშებზე. რადგან მხოლოდ განსაზღვრული კონფიგურაციაა მნიშვნელოვანი, ქეში, რომელიც შევსებულია ცალსახა `--configuration`-ით, ხელმისაწვდომია ბრძანებისთვის, რომელიც იგივე კონფიგურაციას განსაზღვრავს ფლაგის გადაცემის გარეშე.

## დებაგინგი {#debugging}

თუ შეამჩნევთ არადეტერმინისტულ ქცევას ქეშირების გამოყენებისას სხვადასხვა გარემოში ან გამოძახებისას, ეს შეიძლება იყოს დაკავშირებული გარემოებს შორის განსხვავებებთან ან ჰეშინგის ლოგიკაში არსებულ შეცდომასთან. ჩვენ გირჩევთ, მიჰყვეთ ამ ნაბიჯებს პრობლემის დებაგინგისთვის:

1. გაუშვით `tuist hash cache` ან `tuist hash selective-testing` (<.localized_link href="/guides/features/cache">ბინარული ქეშირების</.localized_link> ან <.localized_link href="/guides/features/selective-testing">შერჩევითი ტესტირების</.localized_link> ჰეშები), დააკოპირეთ ჰეშები, შეუცვალეთ სახელი პროექტის საქაღალდეს და კიდევ ერთხელ გაუშვით ბრძანება. ჰეშები უნდა ემთხვეოდეს.
2. თუ ჰეშები არ ემთხვევა, სავარაუდოა, რომ გენერირებული პროექტი დამოკიდებულია გარემოზე. ორივე შემთხვევაში გაუშვით `tuist graph --format json` და შეადარეთ გრაფები. ალტერნატიულად, დააგენერირეთ პროექტები და შეადარეთ მათი `project.pbxproj` ფაილები diff ინსტრუმენტით, როგორიცაა [Diffchecker](https://www.diffchecker.com).
3. თუ ჰეშები ერთნაირია, მაგრამ განსხვავდება სხვადასხვა გარემოში (მაგალითად, CI და ადგილობრივი), დარწმუნდით, რომ ყველგან გამოიყენება იგივე [კონფიგურაცია](#configuration) და [Swift-ის ვერსია](#swift-version). Swift-ის ვერსია დაკავშირებულია Xcode-ის ვერსიასთან, ამიტომ დარწმუნდით, რომ Xcode-ის ვერსიები ემთხვევა.

თუ ჰეშები კვლავ არადეტერმინისტულია, შეგვატყობინეთ და ჩვენ დაგეხმარებით დებაგინგში.


> [!NOTE]
> **დაგეგმილია დებაგინგის გაუმჯობესებული გამოცდილება**
>
> ჩვენი დებაგინგის გამოცდილების გაუმჯობესება შედის ჩვენს სამოქმედო გეგმაში. print-hashes ბრძანება, რომელსაც აკლია კონტექსტი განსხვავებების გასაგებად, შეიცვლება უფრო მოსახერხებელი ბრძანებით, რომელიც ხის მსგავსი სტრუქტურის გამოყენებით აჩვენებს ჰეშებს შორის განსხვავებებს.
