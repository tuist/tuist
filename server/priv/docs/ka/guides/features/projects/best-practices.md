# საუკეთესო პრაქტიკები {#best-practices}

სხვადასხვა გუნდებთან და პროექტებთან მუშაობის წლების განმავლობაში, ჩვენ გამოვყავით საუკეთესო პრაქტიკების ნაკრები, რომელთა დაცვასაც ვურჩევთ Tuist-ისა და Xcode-ის პროექტებთან მუშაობისას. ეს პრაქტიკები არ არის სავალდებულო, მაგრამ ისინი დაგეხმარებათ პროექტების ისეთი სტრუქტურირებით, რაც მათ შენარჩუნებასა და მასშტაბირებას გაუმარტივებს.

## Xcode {#xcode}

### არასასურველი შაბლონები {#discouraged-patterns}

#### კონფიგურაციები დაშორებული გარემოების მოდელირებისთვის {#configurations-to-model-remote-environments}

ბევრი ორგანიზაცია იყენებს აგების კონფიგურაციებს სხვადასხვა დაშორებული გარემოს მოდელირებისთვის (მაგ., `Debug-Production` ან `Release-Canary`), მაგრამ ამ მიდგომას აქვს გარკვეული უარყოფითი მხარეები:

- **შეუსაბამობები:** თუ გრაფში არსებობს კონფიგურაციის შეუსაბამობები, აგების სისტემამ შეიძლება ზოგიერთი სამიზნისთვის არასწორი კონფიგურაცია გამოიყენოს.
- **სირთულე:** პროექტებში შეიძლება აღმოჩნდეს ადგილობრივი კონფიგურაციებისა და დაშორებული გარემოების გრძელი სია, რომლის გააზრებაც და შენარჩუნებაც რთულია.

აგების კონფიგურაციები შექმნილია სხვადასხვა აგების პარამეტრების წარმოსადგენად და პროექტებს იშვიათად სჭირდებათ მეტი, ვიდრე უბრალოდ `Debug` და `Release`. სხვადასხვა გარემოს მოდელირების საჭიროება შეიძლება სხვაგვარად მიღწეულ იქნას:

- **Debug აგებებში:** შეგიძლიათ ჩართოთ ყველა კონფიგურაცია, რომელიც განვითარების ეტაპზე უნდა იყოს ხელმისაწვდომი აპში (მაგ., ბოლოწერტილები) და გადაერთოთ მათ შორის შესრულების დროს. გადართვა შეიძლება მოხდეს ან სქემის გაშვების გარემოს ცვლადების გამოყენებით, ან აპის შიგნით არსებული UI-ით.
- **Release აგებებში:** გამოშვების შემთხვევაში, შეგიძლიათ ჩართოთ მხოლოდ ის კონფიგურაცია, რომელთანაც release აგებაა დაკავშირებული, და არ ჩართოთ კონფიგურაციების გადასართავი შესრულების დროის ლოგიკა კომპილატორის დირექტივების გამოყენებით.

> [!NOTE]
> **არასტანდარტული კონფიგურაციები**
>
> მიუხედავად იმისა, რომ Tuist მხარს უჭერს არასტანდარტულ კონფიგურაციებს და მათ მართვას ამარტივებს ჩვეულებრივ Xcode-ის პროექტებთან შედარებით, თქვენ მიიღებთ გაფრთხილებებს, თუ კონფიგურაციები არ არის თანმიმდევრული დამოკიდებულების გრაფში. ეს ეხმარება აგების საიმედოობის უზრუნველყოფას და კონფიგურაციასთან დაკავშირებული პრობლემების თავიდან აცილებას.


## გენერირებული პროექტები

### აგებადი საქაღალდეები

Tuist 4.62.0-მა დაამატა მხარდაჭერა **აგებადი საქაღალდეებისთვის** (Xcode-ის სინქრონიზებული ჯგუფები), ფუნქცია, რომელიც წარმოდგენილი იყო Xcode 16-ში შერწყმის კონფლიქტების შესამცირებლად.

მიუხედავად იმისა, რომ Tuist-ის ვაილდკარდის შაბლონები (მაგ., `Sources/**/*.swift`) უკვე აღმოფხვრის შერწყმის კონფლიქტებს გენერირებულ პროექტებში, აგებად საქაღალდეებს აქვს დამატებითი უპირატესობები:

- **ავტომატური სინქრონიზაცია**: თქვენი პროექტის სტრუქტურა რჩება სინქრონიზებული ფაილურ სისტემასთან — ფაილების დამატების ან წაშლისას ხელახალი გენერაცია არ არის საჭირო
- **AI-ზე მორგებული სამუშაო ნაკადები**: კოდირების ასისტენტებსა და აგენტებს შეუძლიათ შეცვალონ თქვენი კოდის ბაზა პროექტის ხელახალი გენერაციის გამოწვევის გარეშე
- **უფრო მარტივი კონფიგურაცია**: განსაზღვრეთ საქაღალდეების გზები ცალსახა ფაილების სიების მართვის ნაცვლად

ჩვენ ვურჩევთ აგებადი საქაღალდეების დანერგვას ტრადიციული `Target.sources` და `Target.resources` ატრიბუტების ნაცვლად უფრო გამარტივებული განვითარების გამოცდილებისთვის.

::: code-group

```swift [With buildable folders]
let target: Target = .target(
  name: "App",
  destinations: .iOS,
  product: .app,
  bundleId: "dev.tuist.App",
  buildableFolders: ["App/Sources", "App/Resources"]
)
```

```swift [Without buildable folders]
let target: Target = .target(
  name: "App",
  destinations: .iOS,
  product: .app,
  bundleId: "dev.tuist.App",
  sources: ["App/Sources/**"],
  resources: ["App/Resources/**"]
)
```

### დამოკიდებულებები

#### CI-ზე ვერსიების იძულებითი გარჩევა

Swift Package Manager-ის დამოკიდებულებების CI-ზე ინსტალაციისას, ჩვენ ვურჩევთ `--force-resolved-versions` ფლაგის გამოყენებას დეტერმინისტული აგებების უზრუნველსაყოფად:

```bash
tuist install --force-resolved-versions
```

ეს ფლაგი უზრუნველყოფს, რომ დამოკიდებულებები გარჩეული იქნას `Package.resolved`-ში ჩამაგრებული ზუსტი ვერსიების გამოყენებით, რაც აღმოფხვრის დამოკიდებულებების გარჩევის არადეტერმინიზმით გამოწვეულ პრობლემებს. ეს განსაკუთრებით მნიშვნელოვანია CI-ზე, სადაც აღწარმოებადი აგებები კრიტიკულია.

#### დამოკიდებულებების ინსტალაციის ქეშირება GitHub Actions-ზე {#dependency-cache-volumes}

გენერირებული პროექტებისთვის, გამოიყენეთ [tuist/install](https://github.com/tuist/install) `Package.resolved`-ში ჩამაგრებული დამოკიდებულებების ინსტალაციისა და გაშვებებს შორის მათი ქეშირებისთვის. ის ავტომატურად იყენებს <.localized_link href="/guides/features/runners/cache-volumes">ქეშის ტომებს</.localized_link> Tuist Runners-ზე და GitHub-ის ქეშს სხვა გამშვებებზე.

```yaml
name: Generate project
on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read

jobs:
  generate:
    runs-on: tuist-macos
    steps:
      - uses: actions/checkout@v4
      - uses: jdx/mise-action@v4
      - uses: tuist/install@v1
      - run: tuist generate --no-open
```

ქვესაქაღალდეში მყოფი პროექტისთვის, გადაეცით მისი გზა checkout-თან მიმართებაში:

```yaml
- uses: tuist/install@v1
  with:
    path: apps/ios
```

დამატებითი პარამეტრებისთვის იხილეთ [action-ის ცნობარი](https://github.com/tuist/install#usage).

### აგენტური კოდირება და worktree-ები {#agentic-coding-and-worktrees}

კოდირების აგენტები და ადამიანი კონტრიბუტორები სულ უფრო ხშირად მუშაობენ პარალელურად: დეველოპერი ტოვებს worktree-ს გახსნილ იმ ფუნქციისთვის, რომელსაც ის აკვირდება, ხოლო ერთი ან მეტი აგენტი იტერაციებს აკეთებს საკუთარ ბრენჩებზე დაქვემდებარებულ worktree-ებში. რამდენიმე პროექტის არჩევანი ამ პროცესს ბევრად უფრო გლუვს ხდის.

#### გამოიყენეთ აგებადი საქაღალდეები აგენტის მიერ შესრულებული ცვლილებებისთვის {#worktrees-buildable-folders}

როდესაც აგენტი ამატებს ან შლის ფაილებს, ყველაფერი, რაც დამოკიდებულია `Project.swift`-ში ფაილების სიაზე, მოითხოვს `tuist generate`-ს, სანამ პროექტი ხელახლა აიგება. [აგებადი საქაღალდეები](#buildable-folders) ამ პასუხისმგებლობას გადააქვთ Xcode-ის სინქრონიზებულ ჯგუფებზე, ასე რომ ფაილების ხის ცვლილებები აღარ იწვევს ხელახალ გენერაციას.

შეუთავსეთ ეს `generated-projects` <.localized_link href="/guides/features/agentic-coding/skills">უნარს</.localized_link>, რომელიც ასწავლის აგენტებს Tuist პროექტის ყოველდღიურ სამუშაო ნაკადს.

#### არ გამოყოთ ქეში თითოეული worktree-სთვის {#worktrees-shared-cache}

Tuist მიჰყვება <.localized_link href="/cli/directories">XDG Base Directory Specification</.localized_link>-ს, ამიტომ ნაგულისხმევად ერთსა და იმავე მანქანაზე ყოველი worktree იზიარებს `~/.cache/tuist`-ს და `~/.local/state/tuist`-ს. ეს არის ის, რაც გსურთ: ერთ worktree-ში კომპილირებული დამხმარე პროგრამები, მეორეში ჩამოტვირთული პლაგინები და მესამის მიერ ამოღებული module-cache ბინარები ყველა ხელახლა გამოყენებადია.

worktree-ებში პარალელური `tuist` გამოძახებების გაშვება უსაფრთხოა. აიცილეთ `TUIST_XDG_CACHE_HOME`-ის მიმართვა worktree-ის ლოკალურ გზაზე, თუ კონკრეტულად იზოლაცია არ გჭირდებათ; წინააღმდეგ შემთხვევაში, ეს აიძულებს ყოველ worktree-ს ხელახლა „გააცხელოს“ დამხმარე პროგრამები, პლაგინები და ბინარები.

#### შეინახეთ SwiftPM-ის დროებითი ფაილები თითოეული worktree-სთვის {#worktrees-swiftpm-scratch}

Swift Package Manager-ს აქვს საკუთარი გზის კონტროლი. `--scratch-path` არის ცვალებადი სამუშაო მდგომარეობა და ნაგულისხმევად არის `.build`, ხოლო `--cache-path` არის საერთო ქეშის დირექტორია. ეს ორი გზა არ უნდა განიხილებოდეს ერთნაირად, როდესაც რამდენიმე worktree არის აქტიური.

Tuist-ის ნაგულისხმევი `tuist install` ქცევა უკვე ინახავს SwiftPM-ის დროებით ფაილებს პაკეტის დირექტორიაში, ამიტომ თითოეულ worktree-ს აქვს საკუთარი `.build`. შეინარჩუნეთ ეს იზოლაცია. ერთი საერთო SwiftPM-ის დროებითი დირექტორია შეიძლება აურიოს გადმოწერები, ბილდის შუალედური ფაილები, პლაგინები, მაკროები და ლოკის ფაილები არადაკავშირებული ბრენჩებიდან.

თუ SwiftPM-ის არგუმენტებს გადასცემთ `tuist install -- ...`-ის მეშვეობით ან `installOptions`-ის მეშვეობით `Tuist.swift`-ში, გააზიარეთ `--cache-path`, როცა დამოკიდებულებების უფრო სწრაფად მიღება გსურთ, ხოლო `--scratch-path` დატოვეთ დაყენების გარეშე ან მიმართეთ ის worktree-ის ლოკალურ დირექტორიაზე:

```swift
import ProjectDescription

let tuist = Tuist(
    project: .tuist(
        installOptions: .options(
            passthroughSwiftPackageManagerArguments: [
                "--cache-path",
                "/Users/Shared/swiftpm/cache/xcode-16-macos",
            ]
        )
    )
)
```

გამოიყენეთ რაპერი ან CI-ის გარემოს ცვლადი ქეშის გზისთვის, თუ ის უნდა განსხვავდებოდეს Xcode-ის, Swift-ის ინსტრუმენტების ჯაჭვის ან პლატფორმის მიხედვით. აიცილეთ საერთო `--scratch-path`-ის კომიტის გაკეთება რეპოზიტორიაში.

თუ დამოკიდებულების მდგომარეობა დაზიანებულად ჩანს მხოლოდ ერთ worktree-ში, წაშალეთ ამ worktree-ის `.build` დირექტორია და ხელახლა გაუშვით `tuist install`. თუ საერთო SwiftPM ქეში ეჭვმიტანილი ჩანს worktree-ებში, გამოიყენეთ `swift package purge-cache` დამოკიდებულებების ხელახლა ინსტალაციამდე.

#### დაეყრდენით მოდულის ქეშს {#worktrees-module-cache}

<.localized_link href="/guides/features/cache/module-cache">მოდულის ქეში</.localized_link> არის ის, რაც პარალელურ worktree-ებს მართვადს ხდის. ვინაიდან Tuist თითოეული სამიზნისთვის ითვლის დეტერმინისტულ <.localized_link href="/guides/features/projects/hashing">ჰეშს</.localized_link>, ორი worktree, რომელიც მიმართულია ბრენჩებზე, რომლებიც თავიანთი ისტორიის უმეტეს ნაწილს იზიარებენ, ერთსა და იმავე ბინარებს გამოიყენებენ. გაუშვით `tuist cache` ყოველ კომიტზე `main`-ზე CI-დან; ლოკალურად, `tuist generate` თითოეულ worktree-ში იღებს ყველაფერს, რაც შესაძლებელია ქეშიდან და აწყობს მხოლოდ იმას, რაც თქვენმა ბრენჩმა რეალურად შეცვალა.

თუ worktree ბრუნდება წყაროს ბილდებზე, როცა ქეშში მოხვედრას ელოდით, მიჰყევით <.localized_link href="/guides/features/projects/hashing#debugging">ჰეშინგის გამართვის ნაბიჯებს</.localized_link>; არადეტერმინისტული ჰეშები (ჩვეულებრივ გამოწვეული პროექტში აბსოლუტური გზებით) არის ყველაზე ხშირი მიზეზი და ისინი მკაფიოდ ჩანან ორი worktree-ის შედარებისას.

#### Swift Package-ის რეზოლუციის დაჩქარება რეესტრის მეშვეობით {#worktrees-registry}

თითოეული worktree დამოუკიდებლად ახდენს Swift პაკეტების რეზოლუციას. დიდი დამოკიდებულების გრაფის მქონე პროექტებზე ეს სწრაფად იკრიბება. <.localized_link href="/guides/features/package-registries/swift">Tuist Registry</.localized_link>-ზე გადასვლა თავს არიდებს git ისტორიების ხელახლა კლონირებას და რეზოლუციის დროს წუთებიდან წამებამდე ამცირებს.

#### აგენტებისთვის პროექტის ინსაიტებზე წვდომის მიცემა {#worktrees-mcp}

როდესაც ბილდები და ტესტები მრავალ worktree-ში გადის, ყველაზე სასარგებლო რამ, რასაც აგენტი გააკეთებს, არის იმის ანალიზი, *რომელი* გაშვება გაუარესდა, რომელი ტესტებია არასტაბილური, ან როგორ შეიცვალა ბანდლის ზომა. Tuist ამ მონაცემებს ავლენს <.localized_link href="/guides/features/agentic-coding/mcp">MCP სერვერის</.localized_link> და <.localized_link href="/guides/features/agentic-coding/skills">Skills</.localized_link> პაკეტის მეშვეობით. აირჩიეთ ერთი თითოეული სამუშაო ნაკადისთვის და დაჰყევით მას; ორივეს ერთდროულად გამოყენება ერთი და იგივე ამოცანისთვის ჩვეულებრივ არათანმიმდევრულ აგენტის ქცევას იწვევს.
