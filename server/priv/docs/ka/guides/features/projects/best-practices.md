# საუკეთესო პრაქტიკები {#best-practices}

სხვადასხვა გუნდებთან და პროექტებთან მუშაობის წლების განმავლობაში, ჩვენ გამოვავლინეთ საუკეთესო პრაქტიკების ნაკრები, რომელთა დაცვასაც ვურჩევთ Tuist-ისა და Xcode-ის პროექტებთან მუშაობისას. ეს პრაქტიკები არ არის სავალდებულო, მაგრამ ისინი დაგეხმარებათ პროექტების ისეთი სტრუქტურირებით, რაც მათ შენარჩუნებასა და მასშტაბირებას გაუმარტივებს.

## Xcode {#xcode}

### არარეკომენდებული შაბლონები {#discouraged-patterns}

#### კონფიგურაციები დაშორებული გარემოების მოდელირებისთვის {#configurations-to-model-remote-environments}

ბევრი ორგანიზაცია იყენებს ბილდის კონფიგურაციებს სხვადასხვა დაშორებული გარემოს მოდელირებისთვის (მაგ., `Debug-Production` ან `Release-Canary`), მაგრამ ამ მიდგომას აქვს გარკვეული უარყოფითი მხარეები:

- **შეუსაბამობები:** თუ გრაფში არსებობს კონფიგურაციის შეუსაბამობები, ბილდის სისტემამ ზოგიერთი სამიზნისთვის შესაძლოა არასწორი კონფიგურაცია გამოიყენოს.
- **სირთულე:** პროექტებში შესაძლოა გაჩნდეს ადგილობრივი კონფიგურაციებისა და დაშორებული გარემოების გრძელი სია, რომლის გააზრება და შენარჩუნება რთულია.

ბილდის კონფიგურაციები შექმნილია სხვადასხვა ბილდის პარამეტრების ასახვისთვის და პროექტებს იშვიათად სჭირდებათ მეტი, ვიდრე უბრალოდ `Debug` და `Release`. სხვადასხვა გარემოს მოდელირების საჭიროება შეიძლება სხვაგვარად მიღწეული იყოს:

- **Debug ბილდებში:** შეგიძლიათ აპლიკაციაში ჩართოთ ყველა კონფიგურაცია, რომელიც დეველოპმენტის დროს უნდა იყოს ხელმისაწვდომი (მაგ., endpoint-ები) და ისინი runtime-ში გადართოთ. გადართვა შეიძლება მოხდეს ან scheme-ის launch environment ცვლადების გამოყენებით, ან აპლიკაციის შიგნით არსებული UI-ით.
- **Release ბილდებში:** release-ის შემთხვევაში, შეგიძლიათ ჩართოთ მხოლოდ ის კონფიგურაცია, რომელზეც release ბილდი არის მიბმული და არ ჩართოთ კონფიგურაციების გადართვის runtime ლოგიკა კომპილატორის დირექტივების გამოყენებით.

> [!NOTE]
> **არასტანდარტული კონფიგურაციები**
>
> მიუხედავად იმისა, რომ Tuist უჭერს მხარს არასტანდარტულ კონფიგურაციებს და მათი მართვა უფრო მარტივია ჩვეულებრივ Xcode პროექტებთან შედარებით, თქვენ მიიღებთ გაფრთხილებებს, თუ კონფიგურაციები თანმიმდევრული არ არის დამოკიდებულობების გრაფში. ეს ეხმარება ბილდის საიმედოობის უზრუნველყოფას და კონფიგურაციასთან დაკავშირებული პრობლემების თავიდან აცილებას.


## გენერირებული პროექტები

### ბილდირებადი საქაღალდეები

Tuist 4.62.0-მა დაამატა მხარდაჭერა **ბილდირებადი საქაღალდეებისთვის** (Xcode-ის სინქრონიზებული ჯგუფები), ფუნქცია, რომელიც Xcode 16-ში შემოვიდა merge კონფლიქტების შესამცირებლად.

მიუხედავად იმისა, რომ Tuist-ის wildcard შაბლონები (მაგ., `Sources/**/*.swift`) უკვე აღმოფხვრის merge კონფლიქტებს გენერირებულ პროექტებში, ბილდირებადი საქაღალდეები დამატებით სარგებელს სთავაზობს:

- **ავტომატური სინქრონიზაცია**: თქვენი პროექტის სტრუქტურა სინქრონიზებული რჩება ფაილურ სისტემასთან — ფაილების დამატების ან წაშლისას ხელახალი გენერაცია არ არის საჭირო
- **AI-ზე მორგებული სამუშაო ნაკადები**: კოდირების ასისტენტებსა და აგენტებს შეუძლიათ შეცვალონ თქვენი კოდბაზა პროექტის ხელახალი გენერაციის გამოწვევის გარეშე
- **უფრო მარტივი კონფიგურაცია**: განსაზღვრეთ საქაღალდეების გზები აშკარა ფაილების სიების მართვის ნაცვლად

ჩვენ ვურჩევთ ბილდირებადი საქაღალდეების გამოყენებას ტრადიციული `Target.sources` და `Target.resources` ატრიბუტების ნაცვლად განვითარების უფრო გამარტივებული გამოცდილებისთვის.

::: code-group

```swift [With buildable folders]
let target = Target(
  name: "App",
  buildableFolders: ["App/Sources", "App/Resources"]
)
```

```swift [Without buildable folders]
let target = Target(
  name: "App",
  sources: ["App/Sources/**"],
  resources: ["App/Resources/**"]
)
```

:::

### დამოკიდებულობები

#### CI-ზე ვერსიების იძულებითი რეზოლუცია

CI-ზე Swift Package Manager დამოკიდებულობების ინსტალაციისას, ჩვენ ვურჩევთ `--force-resolved-versions` ფლაგის გამოყენებას დეტერმინისტული ბილდების უზრუნველსაყოფად:

```bash
tuist install --force-resolved-versions
```

ეს ფლაგი უზრუნველყოფს, რომ დამოკიდებულობები რეზოლვირდეს `Package.resolved`-ში მიმაგრებული ზუსტი ვერსიების გამოყენებით, რაც აღმოფხვრის დამოკიდებულობების რეზოლუციის არადეტერმინიზმით გამოწვეულ პრობლემებს. ეს განსაკუთრებით მნიშვნელოვანია CI-ზე, სადაც რეპროდუცირებადი ბილდები კრიტიკულია.

#### დამოკიდებულობების cached ინსტალაცია GitHub Actions-ზე {#dependency-cache-volumes}

გენერირებული პროექტებისთვის, გამოიყენეთ [tuist/install](https://github.com/tuist/install) `Package.resolved`-ში მიმაგრებული დამოკიდებულობების ინსტალაციისა და გაშვებებს შორის მათი cache-ში შენახვისთვის. ის ავტომატურად იყენებს <.localized_link href="/guides/features/runners/cache-volumes">cache volumes</.localized_link>-ს Tuist Runners-ზე და GitHub-ის cache-ს სხვა runners-ზე.

```yaml
name: Generate project
on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read

jobs:
  generate:
    runs-on: tuist-macos
    steps:
      - uses: actions/checkout@v4
      - uses: jdx/mise-action@v4
      - uses: tuist/install@v1
      - run: tuist generate --no-open
```

ქვედირექტორიაში მყოფი პროექტისთვის, გადაეცით მისი გზა checkout-თან მიმართებაში:

```yaml
- uses: tuist/install@v1
  with:
    path: apps/ios
```

დამატებითი პარამეტრებისთვის იხილეთ [action reference](https://github.com/tuist/install#usage).

### აგენტური კოდირება და worktrees {#agentic-coding-and-worktrees}

კოდირების აგენტები და ადამიანი კონტრიბუტორები სულ უფრო ხშირად მუშაობენ პარალელურად: დეველოპერი ინარჩუნებს open worktree-ს იმ ფიჩერისთვის, რომელსაც ის აკვირდება, ხოლო ერთი ან რამდენიმე აგენტი იტერაციას აკეთებს საკუთარ branch-ებზე sibling worktree-ებში. რამდენიმე პროექტის არჩევანი ამას ბევრად უფრო გლუვს ხდის.

#### გამოიყენეთ ბილდირებადი საქაღალდეები აგენტის მიერ შესრულებული ცვლილებებისთვის {#worktrees-buildable-folders}

როდესაც აგენტი ამატებს ან შლის ფაილებს, ყველაფერი, რაც დამოკიდებულია `Project.swift`-ში არსებულ ფაილების სიაზე, მოითხოვს `tuist generate`-ს, სანამ პროექტი ხელახლა აიწყობს. [ბილდირებადი საქაღალდეები](#buildable-folders) ამ პასუხისმგებლობას Xcode-ის სინქრონიზებულ ჯგუფებზე გადაიტანს, ამიტომ ფაილური ხის ცვლილებები აღარ იწვევს ხელახალ გენერაციას.

შეუთავსეთ ეს `generated-projects` <.localized_link href="/guides/features/agentic-coding/skills">skill</.localized_link>-თან, რომელიც ასწავლის აგენტებს Tuist პროექტის ყოველდღიურ სამუშაო ნაკადს.

#### არ გამოყოთ cache თითოეული worktree-ისთვის {#worktrees-shared-cache}

Tuist მიჰყვება <.localized_link href="/cli/directories">XDG Base Directory Specification</.localized_link>-ს, ამიტომ ნაგულისხმევად ერთსა და იმავე მანქანაზე ყოველი worktree იზიარებს `~/.cache/tuist` და `~/.local/state/tuist`-ს. ეს არის ის, რაც გსურთ: ერთ worktree-ში კომპილირებული helpers, მეორეში ჩამოტვირთული plugins და მესამის მიერ გამოყენებული module-cache ბინარები ყველა ხელახლა გამოყენებადია.

პარალელური `tuist` გამოძახებები worktree-ებში უსაფრთხოა პარალელურად გასაშვებად. თავი აარიდეთ `TUIST_XDG_CACHE_HOME`-ის worktree-ლოკალურ გზაზე მიმართვას, თუ კონკრეტულად იზოლაცია არ გჭირდებათ; ასეთი ქმედება აიძულებს ყოველ worktree-ს ხელახლა „გაათბოს“ helpers, plugins და ბინარები.

#### შეინახეთ SwiftPM scratch თითოეული worktree-ისთვის {#worktrees-swiftpm-scratch}

Swift Package Manager-ს აქვს საკუთარი გზის კონტროლი. `--scratch-path` არის ცვლადი სამუშაო მდგომარეობა და ნაგულისხმევად არის `.build`, ხოლო `--cache-path` არის საერთო cache დირექტორია. ეს ორი გზა არ უნდა განიხილებოდეს ერთნაირად, როდესაც რამდენიმე worktree არის აქტიური.

Tuist-ის ნაგულისხმევი `tuist install` ქცევა უკვე ინახავს SwiftPM scratch-ს პაკეტის დირექტორიაში, ამიტომ თითოეულ worktree-ს აქვს საკუთარი `.build`. შეინარჩუნეთ ეს იზოლაცია. ერთი საერთო SwiftPM scratch დირექტორია შეიძლება აურიოს checkouts, ბილდის შუალედური ფაილები, plugins, macros და lock ფაილები სხვადასხვა branch-ებიდან.

თუ SwiftPM არგუმენტებს გადასცემთ `tuist install -- ...`-ით ან `installOptions`-ით `Tuist.swift`-ში, გააზიარეთ `--cache-path`, როცა დამოკიდებულებების უფრო სწრაფად ჩამოტვირთვა გსურთ, მაგრამ `--scratch-path` დატოვეთ დაყენებული ან მიუთითეთ worktree-ლოკალური დირექტორია:

```swift
import ProjectDescription

let tuist = Tuist(
    project: .tuist(
        installOptions: .options(
            passthroughSwiftPackageManagerArguments: [
                "--cache-path",
                "/Users/Shared/swiftpm/cache/xcode-16-macos",
            ]
        )
    )
)
```

გამოიყენეთ wrapper ან CI გარემოს ცვლადი cache გზისთვის, თუ ის უნდა განსხვავდებოდეს Xcode-ის, Swift toolchain-ის ან პლატფორმის მიხედვით. თავი აარიდეთ საერთო `--scratch-path`-ის რეპოზიტორიაში commit-ებას.

თუ დამოკიდებულებების მდგომარეობა დაზიანებულად ჩანს მხოლოდ ერთ worktree-ში, წაშალეთ ამ worktree-ის `.build` დირექტორია და ხელახლა გაუშვით `tuist install`. თუ საერთო SwiftPM cache ეჭვმიტანილი ჩანს worktree-ებში, გამოიყენეთ `swift package purge-cache` დამოკიდებულებების ხელახლა ინსტალაციამდე.

#### მოეყრდენით module cache-ს {#worktrees-module-cache}

<.localized_link href="/guides/features/cache/module-cache">module cache</.localized_link> არის ის, რაც პარალელურ worktree-ებს მართვადს ხდის. ვინაიდან Tuist თითოეული target-ისთვის ითვლის დეტერმინისტულ <.localized_link href="/guides/features/projects/hashing">hash</.localized_link>-ს, ორი worktree, რომელიც მიუთითებს branch-ებზე, რომლებიც იზიარებენ ისტორიის უმეტეს ნაწილს, მოხვდება იმავე ბინარებში. გაუშვით `tuist cache` ყოველ `main`-ზე commit-ზე CI-დან; ლოკალურად, `tuist generate` თითოეულ worktree-ში იღებს ყველაფერს, რაც შეუძლია cache-დან და კომპილირებს მხოლოდ იმას, რაც თქვენმა branch-მა რეალურად შეცვალა.

თუ worktree ბრუნდება source builds-ზე, როცა cache hit-ს ელოდით, მიჰყევით <.localized_link href="/guides/features/projects/hashing#debugging">hashing debugging steps</.localized_link>-ს; არადეტერმინისტული hashes (ჩვეულებრივ გამოწვეული პროექტში აბსოლუტური გზებით) არის ყველაზე ხშირი მიზეზი და ისინი მკაფიოდ ჩანან ორი worktree-ის შედარებისას.

#### დააჩქარეთ Swift Package resolution registry-ით {#worktrees-registry}

თითოეული worktree დამოუკიდებლად ახდენს Swift პაკეტების resolution-ს. დიდი დამოკიდებულების გრაფის მქონე პროექტზე ეს სწრაფად იკრიბება. <.localized_link href="/guides/features/package-registries/swift">Tuist Registry</.localized_link>-ზე გადასვლა თავიდან აცილებს git ისტორიების ხელახლა კლონირებას და ამცირებს resolution-ს წუთებიდან წამებამდე.

#### მიეცით აგენტებს წვდომა პროექტის insights-ზე {#worktrees-mcp}

როცა builds და tests მიმდინარეობს მრავალ worktree-ში, ყველაზე სასარგებლო რამ, რაც აგენტს შეუძლია გააკეთოს, არის იმის ანალიზი, *რომელი* გაშვება გაუარესდა, რომელი ტესტებია flaky ან როგორ შეიცვალა bundle ზომა. Tuist ამ მონაცემებს ავლენს <.localized_link href="/guides/features/agentic-coding/mcp">MCP server</.localized_link>-ისა და <.localized_link href="/guides/features/agentic-coding/skills">Skills</.localized_link> პაკეტის მეშვეობით. აირჩიეთ ერთი სამუშაო ნაკადისთვის და დარჩით მასზე; ორივეს ერთდროულად გამოყენება იგივე ამოცანისთვის ჩვეულებრივ იწვევს აგენტის არათანმიმდევრულ ქცევას.
