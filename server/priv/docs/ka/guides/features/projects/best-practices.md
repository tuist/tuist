# საუკეთესო პრაქტიკები {#best-practices}

სხვადასხვა გუნდებთან და პროექტებთან მუშაობის წლების განმავლობაში, ჩვენ გამოვყავით საუკეთესო პრაქტიკების ნაკრები, რომლის დაცვასაც ვურჩევთ Tuist-ისა და Xcode-ის პროექტებთან მუშაობისას. ეს პრაქტიკები არ არის სავალდებულო, მაგრამ ისინი დაგეხმარებათ პროექტების ისეთი სტრუქტურირებით, რაც მათ შენარჩუნებასა და მასშტაბირებას გაუმარტივებს.

## Xcode {#xcode}

### არასასურველი შაბლონები {#discouraged-patterns}

#### კონფიგურაციები დაშორებული გარემოების მოდელირებისთვის {#configurations-to-model-remote-environments}

ბევრი ორგანიზაცია იყენებს აგების კონფიგურაციებს სხვადასხვა დაშორებული გარემოს მოდელირებისთვის (მაგ., `Debug-Production` ან `Release-Canary`), მაგრამ ამ მიდგომას აქვს გარკვეული უარყოფითი მხარეები:

- **შეუსაბამობები:** თუ გრაფში არსებობს კონფიგურაციის შეუსაბამობები, აგების სისტემამ შეიძლება ზოგიერთი მიზნისთვის არასწორი კონფიგურაცია გამოიყენოს.
- **სირთულე:** პროექტებში შეიძლება აღმოჩნდეს ადგილობრივი კონფიგურაციებისა და დაშორებული გარემოების გრძელი სია, რომელთა გააზრება და შენარჩუნება რთულია.

აგების კონფიგურაციები შეიქმნა სხვადასხვა აგების პარამეტრების განსახიერებისთვის და პროექტებს იშვიათად სჭირდებათ მეტი, ვიდრე უბრალოდ `Debug` და `Release`. სხვადასხვა გარემოს მოდელირების საჭიროება შესაძლებელია სხვაგვარად მიღწეულ იქნას:

- **Debug აგებებში:** შეგიძლიათ ჩართოთ ყველა კონფიგურაცია, რომელიც განვითარების ეტაპზე უნდა იყოს ხელმისაწვდომი აპში (მაგ., ბოლოწერტილები) და გადაართოთ ისინი runtime-ში. გადართვა შესაძლებელია ან სქემის გაშვების გარემოს ცვლადების გამოყენებით, ან აპში არსებული UI-ს საშუალებით.
- **Release აგებებში:** რელიზის შემთხვევაში, შეგიძლიათ ჩართოთ მხოლოდ ის კონფიგურაცია, რომელთანაც release აგებაა დაკავშირებული და არ ჩართოთ კონფიგურაციების გადართვის runtime ლოგიკა კომპილატორის დირექტივების გამოყენებით.

> [!NOTE]
> **არასტანდარტული კონფიგურაციები**
>
> მიუხედავად იმისა, რომ Tuist მხარს უჭერს არასტანდარტულ კონფიგურაციებს და მათ მართვას უფრო ამარტივებს სტანდარტულ Xcode-ის პროექტებთან შედარებით, თქვენ მიიღებთ გაფრთხილებებს, თუ კონფიგურაციები არ არის თანმიმდევრული დამოკიდებულების გრაფში. ეს ეხმარება აგების საიმედოობის უზრუნველყოფას და კონფიგურაციასთან დაკავშირებული პრობლემების თავიდან აცილებას.


## გენერირებული პროექტები

### აგებადი საქაღალდეები

Tuist 4.62.0-მა დაამატა მხარდაჭერა **აგებადი საქაღალდეებისთვის** (Xcode-ის სინქრონიზებული ჯგუფები), ფუნქცია, რომელიც წარმოდგენილი იქნა Xcode 16-ში merge კონფლიქტების შესამცირებლად.

მიუხედავად იმისა, რომ Tuist-ის ვაილდქარდ შაბლონები (მაგ., `Sources/**/*.swift`) უკვე აღმოფხვრის merge კონფლიქტებს გენერირებულ პროექტებში, აგებადი საქაღალდეები დამატებით სარგებელს სთავაზობს:

- **ავტომატური სინქრონიზაცია**: თქვენი პროექტის სტრუქტურა რჩება სინქრონიზებული ფაილურ სისტემასთან — ფაილების დამატების ან წაშლისას ხელახალი გენერაცია არ არის საჭირო
- **AI-ზე მორგებული სამუშაო პროცესები**: კოდირების ასისტენტებსა და აგენტებს შეუძლიათ შეცვალონ თქვენი კოდის ბაზა პროექტის ხელახალი გენერაციის გამოწვევის გარეშე
- **უფრო მარტივი კონფიგურაცია**: განსაზღვრეთ საქაღალდეების გზები ფაილების ცხადი სიების მართვის ნაცვლად

ჩვენ ვურჩევთ აგებადი საქაღალდეების დანერგვას ტრადიციული `Target.sources` და `Target.resources` ატრიბუტების ნაცვლად უფრო გამარტივებული განვითარების გამოცდილებისთვის.

::: code-group

```swift [With buildable folders]
let target = Target(
  name: "App",
  buildableFolders: ["App/Sources", "App/Resources"]
)
```

```swift [Without buildable folders]
let target = Target(
  name: "App",
  sources: ["App/Sources/**"],
  resources: ["App/Resources/**"]
)
```

### დამოკიდებულებები

#### CI-ზე ვერსიების იძულებითი რეზოლუცია

Swift Package Manager-ის დამოკიდებულებების CI-ზე ინსტალაციისას, ჩვენ ვურჩევთ `--force-resolved-versions` ფლაგის გამოყენებას დეტერმინისტული აგებების უზრუნველსაყოფად:

```bash
tuist install --force-resolved-versions
```

ეს ფლაგი უზრუნველყოფს, რომ დამოკიდებულებები გადაწყდეს `Package.resolved`-ში ჩამაგრებული ზუსტი ვერსიების გამოყენებით, რაც აღმოფხვრის დამოკიდებულების რეზოლუციაში არადეტერმინიზმით გამოწვეულ პრობლემებს. ეს განსაკუთრებით მნიშვნელოვანია CI-ზე, სადაც რეპროდუცირებადი აგებები კრიტიკულია.

#### დამოკიდებულებების cached ინსტალაცია GitHub Actions-ზე {#dependency-cache-volumes}

გენერირებული პროექტებისთვის, გამოიყენეთ [tuist/install](https://github.com/tuist/install) `Package.resolved`-ში ჩამაგრებული დამოკიდებულებების ინსტალაციისა და გაშვებებს შორის მათი cache-ში შენახვისთვის. ის ავტომატურად იყენებს <.localized_link href="/guides/features/runners/cache-volumes">cache volumes</.localized_link> Tuist Runners-ზე და GitHub-ის cache-ს სხვა runners-ზე.

```yaml
name: Generate project
on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read

jobs:
  generate:
    runs-on: tuist-macos
    steps:
      - uses: actions/checkout@v4
      - uses: jdx/mise-action@v4
      - uses: tuist/install@v1
      - run: tuist generate --no-open
```

ქვედირექტორიაში მყოფი პროექტისთვის, გადაეცით მისი გზა checkout-ის მიმართ:

```yaml
- uses: tuist/install@v1
  with:
    path: apps/ios
```

დამატებითი პარამეტრებისთვის იხილეთ [action reference](https://github.com/tuist/install#usage).

### Agentic კოდირება და worktrees {#agentic-coding-and-worktrees}

კოდირების აგენტები და ადამიანი კონტრიბუტორები სულ უფრო მეტად მუშაობენ პარალელურად: დეველოპერი ტოვებს worktree-ს გახსნილ იმ ფუნქციისთვის, რომელსაც ის აკვირდება, ხოლო ერთი ან მეტი აგენტი იტერაციას აკეთებს საკუთარ branches-ზე sibling worktrees-ში. რამდენიმე პროექტული არჩევანი ამ პროცესს ბევრად უფრო გლუვს ხდის.

#### გამოიყენეთ აგებადი საქაღალდეები აგენტის მიერ მართული ცვლილებებისთვის {#worktrees-buildable-folders}

როდესაც აგენტი ამატებს ან შლის ფაილებს, ნებისმიერი რამ, რაც დამოკიდებულია `Project.swift`-ში ფაილების სიაზე, მოითხოვს `tuist generate`-ს, სანამ პროექტი ხელახლა აიგება. [აგებადი საქაღალდეები](#buildable-folders) ამ პასუხისმგებლობას Xcode-ის სინქრონიზებულ ჯგუფებს გადასცემს, ასე რომ ფაილების ხის ცვლილებები აღარ იწვევს ხელახალ გენერაციას.

შეუთავსეთ ეს `generated-projects` <.localized_link href="/guides/features/agentic-coding/skills">skill</.localized_link>-თან, რომელიც ასწავლის აგენტებს Tuist პროექტის ყოველდღიურ სამუშაო პროცესს.

#### არ გამოყოთ cache თითოეული worktree-სთვის {#worktrees-shared-cache}

Tuist მიჰყვება <.localized_link href="/cli/directories">XDG Base Directory Specification</.localized_link>-ს, ასე რომ, ნაგულისხმევად, ერთსა და იმავე მანქანაზე ყოველი worktree იზიარებს `~/.cache/tuist`-ს და `~/.local/state/tuist`-ს. ეს არის ის, რაც გსურთ: ერთ worktree-ში კომპილირებული helpers, მეორეში ჩამოტვირთული plugins და მესამეში გამოყვანილი module-cache binaries ყველა ხელახლა გამოყენებადია.

პარალელური `tuist` გამოძახებები worktrees-ში უსაფრთხოა პარალელურად გასაშვებად. თავი აარიდეთ `TUIST_XDG_CACHE_HOME`-ის მიმართვას worktree-ის ლოკალურ გზაზე, თუ კონკრეტულად იზოლაცია არ გჭირდებათ; ამის გაკეთება აიძულებს ყოველ worktree-ს ხელახლა "გაათბოს" helpers, plugins და binaries.

#### შეინარჩუნეთ SwiftPM scratch თითოეული worktree-სთვის {#worktrees-swiftpm-scratch}

Swift Package Manager-ს აქვს საკუთარი გზის კონტროლი. `--scratch-path` არის ცვლადი სამუშაო მდგომარეობა და ნაგულისხმევად არის `.build`, ხოლო `--cache-path` არის გაზიარებული cache დირექტორია. ეს ორი გზა არ უნდა განიხილებოდეს ერთნაირად, როდესაც რამდენიმე worktree არის აქტიური.

Tuist-ის ნაგულისხმევი `tuist install` ქცევა უკვე ინახავს SwiftPM scratch-ს პაკეტის დირექტორიაში, ასე რომ, თითოეულ worktree-ს აქვს საკუთარი `.build`. შეინარჩუნეთ ეს იზოლაცია. ერთ გაზიარებულ SwiftPM scratch დირექტორიას შეუძლია აურიოს checkouts, ბილდის შუალედური ფაილები, plugins, macros და lock files არადაკავშირებული branches-დან.

თუ SwiftPM არგუმენტებს გადასცემთ `tuist install -- ...`-ის მეშვეობით ან `Tuist.swift`-ში მყოფი `installOptions`-ის მეშვეობით, გააზიარეთ `--cache-path`, როდესაც გსურთ დამოკიდებულებების უფრო სწრაფად მიღება, მაგრამ `--scratch-path` დატოვეთ დაყენების გარეშე ან მიმართეთ ის worktree-ის ლოკალურ დირექტორიაზე:

```swift
import ProjectDescription

let tuist = Tuist(
    project: .tuist(
        installOptions: .options(
            passthroughSwiftPackageManagerArguments: [
                "--cache-path",
                "/Users/Shared/swiftpm/cache/xcode-16-macos",
            ]
        )
    )
)
```

გამოიყენეთ wrapper ან CI გარემოს ცვლადი cache გზისთვის, თუ ის უნდა იცვლებოდეს Xcode-ის, Swift toolchain-ის ან პლატფორმის მიხედვით. თავი აარიდეთ გაზიარებული `--scratch-path`-ის რეპოზიტორიაში ჩაწერას.

თუ დამოკიდებულების მდგომარეობა დაზიანებულად ჩანს მხოლოდ ერთ worktree-ში, წაშალეთ ამ worktree-ის `.build` დირექტორია და ხელახლა გაუშვით `tuist install`. თუ გაზიარებული SwiftPM cache საეჭვოდ ჩანს worktrees-ში, გამოიყენეთ `swift package purge-cache` დამოკიდებულებების ხელახლა ინსტალაციამდე.

#### მოეყრდენით module cache-ს {#worktrees-module-cache}

<.localized_link href="/guides/features/cache/module-cache">module cache</.localized_link> არის ის, რაც პარალელურ worktrees-ს მართვადს ხდის. ვინაიდან Tuist ითვლის დეტერმინისტულ <.localized_link href="/guides/features/projects/hashing">hash</.localized_link>-ს თითოეული target-ისთვის, ორი worktree, რომელიც მიმართულია branches-ზე, რომლებიც იზიარებენ ისტორიის უმეტეს ნაწილს, მიიღებენ იგივე binaries-ს. გაუშვით `tuist cache` ყოველ commit-ზე `main`-ზე CI-დან; ლოკალურად, `tuist generate` თითოეულ worktree-ში იღებს ყველაფერს, რაც შეუძლია cache-დან და აგებს მხოლოდ იმას, რაც თქვენმა branch-მა რეალურად შეცვალა.

თუ worktree ბრუნდება source builds-ზე, როდესაც ელოდით cache hit-ს, მიჰყევით <.localized_link href="/guides/features/projects/hashing#debugging">hashing debugging steps</.localized_link>-ს; არადეტერმინისტული hashes (ჩვეულებრივ გამოწვეული პროექტში აბსოლუტური გზებით) არის ყველაზე გავრცელებული მიზეზი და ისინი მკაფიოდ ჩანან ორი worktree-ის შედარებისას.

#### Swift Package resolution-ის დაჩქარება registry-ს მეშვეობით {#worktrees-registry}

თითოეული worktree დამოუკიდებლად აგვარებს Swift packages-ს. დიდი დამოკიდებულების გრაფის მქონე პროექტზე ეს სწრაფად იკრიბება. <.localized_link href="/guides/features/package-registries/swift">Tuist Registry</.localized_link>-ზე გადასვლა თავიდან აცილებს git ისტორიების ხელახლა კლონირებას და ამცირებს resolution-ის დროს წუთებიდან წამებამდე.

#### აგენტებისთვის პროექტის ინსაიტების მიწოდება {#worktrees-mcp}

როდესაც builds და tests მუშაობენ მრავალ worktree-ში, ყველაზე სასარგებლო რამ, რასაც აგენტი გააკეთებს, არის იმის ანალიზი, *რომელი* გაშვება დაუბრუნდა უკან, რომელი ტესტებია არასტაბილური ან როგორ შეიცვალა bundle ზომა. Tuist ამ მონაცემებს ავლენს <.localized_link href="/guides/features/agentic-coding/mcp">MCP server</.localized_link>-ის და <.localized_link href="/guides/features/agentic-coding/skills">Skills</.localized_link> პაკეტის მეშვეობით. აირჩიეთ ერთი სამუშაო პროცესისთვის და დარჩით მასზე; ორივეს ერთი და იგივე ამოცანისთვის შერევა ჩვეულებრივ იწვევს აგენტის არათანმიმდევრულ ქცევას.
