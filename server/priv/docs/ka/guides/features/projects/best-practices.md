# საუკეთესო პრაქტიკები {#best-practices}

სხვადასხვა გუნდებთან და პროექტებთან მუშაობის წლების განმავლობაში ჩვენ გამოვყავით საუკეთესო პრაქტიკების ნაკრები, რომლის დაცვასაც ვუწევთ რეკომენდაციას Tuist-ისა და Xcode-ის პროექტებზე მუშაობისას. ეს პრაქტიკები არ არის სავალდებულო, მაგრამ ისინი დაგეხმარებათ პროექტების ისეთი სტრუქტურირებით, რომ მათი შენარჩუნება და მასშტაბირება უფრო ადვილი იყოს.

## Xcode {#xcode}

### არასასურველი შაბლონები {#discouraged-patterns}

#### კონფიგურაციები დაშორებული გარემოების მოდელირებისთვის {#configurations-to-model-remote-environments}

ბევრი ორგანიზაცია იყენებს ბილდის კონფიგურაციებს სხვადასხვა დაშორებული გარემოს მოდელირებისთვის (მაგ., `Debug-Production` ან `Release-Canary`), თუმცა ამ მიდგომას აქვს გარკვეული ნაკლოვანებები:

- **შეუსაბამობები:** თუ გრაფში არსებობს კონფიგურაციული შეუსაბამობები, ბილდის სისტემამ შეიძლება ზოგიერთი სამიზნისთვის არასწორი კონფიგურაცია გამოიყენოს.
- **სირთულე:** პროექტებში შეიძლება გაჩნდეს ადგილობრივი კონფიგურაციებისა და დაშორებული გარემოების გრძელი სია, რომლის გააზრება და შენარჩუნება რთულია.

ბილდის კონფიგურაციები შექმნილია სხვადასხვა ბილდის პარამეტრის ასახვისთვის და პროექტებს იშვიათად სჭირდება მეტი, ვიდრე უბრალოდ `Debug` და `Release`. სხვადასხვა გარემოს მოდელირების საჭიროება შესაძლებელია სხვაგვარად მიღწეული იყოს:

- **Debug ბილდებში:** შეგიძლიათ აპლიკაციაში ჩართოთ ყველა კონფიგურაცია, რომელიც განვითარების ეტაპზე ხელმისაწვდომი უნდა იყოს (მაგ., endpoint-ები) და გადაართოთ ისინი runtime-ში. გადართვა შესაძლებელია სქემის გაშვების გარემოს ცვლადების გამოყენებით ან აპლიკაციის შიგნით არსებული UI-ით.
- **Release ბილდებში:** რელიზის შემთხვევაში შეგიძლიათ ჩართოთ მხოლოდ ის კონფიგურაცია, რომელთანაც ბილდი არის დაკავშირებული, და არ ჩართოთ კონფიგურაციების გადართვის runtime-ლოგიკა კომპილატორის დირექტივების გამოყენებით.

> [!NOTE]
> **არასტანდარტული კონფიგურაციები**
>
> მიუხედავად იმისა, რომ Tuist მხარს უჭერს არასტანდარტულ კონფიგურაციებს და მათი მართვა უფრო ადვილია, ვიდრე ჩვეულებრივ Xcode-ის პროექტებში, თქვენ მიიღებთ გაფრთხილებებს, თუ კონფიგურაციები არ არის თანმიმდევრული დამოკიდებულებების გრაფში. ეს ეხმარება ბილდის საიმედოობის უზრუნველყოფას და კონფიგურაციასთან დაკავშირებული პრობლემების თავიდან აცილებას.


## გენერირებული პროექტები

### აგებადი საქაღალდეები

Tuist 4.62.0-მა დაამატა მხარდაჭერა **აგებადი საქაღალდეებისთვის** (Xcode-ის სინქრონიზებული ჯგუფები), ფუნქცია, რომელიც Xcode 16-ში შემოიტანეს merge-კონფლიქტების შესამცირებლად.

მიუხედავად იმისა, რომ Tuist-ის wildcard-შაბლონები (მაგ., `Sources/**/*.swift`) უკვე აღმოფხვრის merge-კონფლიქტებს გენერირებულ პროექტებში, აგებად საქაღალდეებს აქვს დამატებითი უპირატესობები:

- **ავტომატური სინქრონიზაცია**: თქვენი პროექტის სტრუქტურა რჩება სინქრონიზებული ფაილურ სისტემასთან — ფაილების დამატების ან წაშლისას ხელახალი გენერაცია არ არის საჭირო
- **AI-ზე მორგებული სამუშაო პროცესები**: კოდირების ასისტენტებსა და აგენტებს შეუძლიათ შეცვალონ თქვენი კოდბაზა პროექტის ხელახალი გენერაციის გამოწვევის გარეშე
- **უფრო მარტივი კონფიგურაცია**: განსაზღვრეთ საქაღალდეების გზები ცალსახა ფაილების სიების მართვის ნაცვლად

ჩვენ ვუწევთ რეკომენდაციას აგებადი საქაღალდეების გამოყენებას ტრადიციული `Target.sources` და `Target.resources` ატრიბუტების ნაცვლად უფრო გამარტივებული განვითარების გამოცდილებისთვის.

::: code-group

```swift [With buildable folders]
let target: Target = .target(
  name: "App",
  destinations: .iOS,
  product: .app,
  bundleId: "dev.tuist.App",
  buildableFolders: ["App/Sources", "App/Resources"]
)
```

```swift [Without buildable folders]
let target: Target = .target(
  name: "App",
  destinations: .iOS,
  product: .app,
  bundleId: "dev.tuist.App",
  sources: ["App/Sources/**"],
  resources: ["App/Resources/**"]
)
```

### დამოკიდებულებები

#### CI-ზე ვერსიების იძულებითი რეზოლუცია

Swift Package Manager-ის დამოკიდებულებების CI-ზე ინსტალაციისას, ჩვენ ვუწევთ რეკომენდაციას `--force-resolved-versions` ფლაგის გამოყენებას დეტერმინისტული ბილდების უზრუნველსაყოფად:

```bash
tuist install --force-resolved-versions
```

ეს ფლაგი უზრუნველყოფს, რომ დამოკიდებულებები რეზოლუცირდეს `Package.resolved`-ში მიმაგრებული ზუსტი ვერსიების გამოყენებით, რითაც აღმოიფხვრება დამოკიდებულებების რეზოლუციის არადეტერმინიზმით გამოწვეული პრობლემები. ეს განსაკუთრებით მნიშვნელოვანია CI-ზე, სადაც რეპროდუცირებადი ბილდები კრიტიკულია.

#### დამოკიდებულებების ინსტალაციის ქეშირება GitHub Actions-ზე {#dependency-cache-volumes}

გენერირებული პროექტებისთვის გამოიყენეთ [tuist/install](https://github.com/tuist/install) `Package.resolved`-ში მიმაგრებული დამოკიდებულებების ინსტალაციისა და გაშვებებს შორის მათი ქეშირებისთვის. ის ავტომატურად იყენებს <.localized_link href="/guides/features/runners/cache-volumes">cache volumes</.localized_link>-ს Tuist Runners-ზე და GitHub-ის ქეშს სხვა runners-ზე.

```yaml
name: Generate project
on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read

jobs:
  generate:
    runs-on: tuist-macos
    steps:
      - uses: actions/checkout@v4
      - uses: jdx/mise-action@v4
      - uses: tuist/install@v1
      - run: tuist generate --no-open
```

ქვესაქაღალდეში მყოფი პროექტისთვის გადაეცით მისი გზა checkout-ის მიმართებით:

```yaml
- uses: tuist/install@v1
  with:
    path: apps/ios
```

დამატებითი პარამეტრებისთვის იხილეთ [action reference](https://github.com/tuist/install#usage).

### აგენტური კოდირება და worktree-ები {#agentic-coding-and-worktrees}

კოდირების აგენტები და ადამიანი კონტრიბუტორები სულ უფრო ხშირად მუშაობენ პარალელურად: დეველოპერი ტოვებს open worktree-ს იმ ფუნქციისთვის, რომელსაც ის აკვირდება, ხოლო ერთი ან მეტი აგენტი იტერაციას აკეთებს საკუთარ ბრენჩებზე დაძმობილებულ worktree-ებში. პროექტის რამდენიმე არჩევანი ამ პროცესს ბევრად უფრო გლუვს ხდის.

#### აგენტის მიერ შესრულებული ცვლილებებისთვის გამოიყენეთ აგებადი საქაღალდეები {#worktrees-buildable-folders}

როდესაც აგენტი ამატებს ან შლის ფაილებს, ყველაფერი, რაც დამოკიდებულია `Project.swift`-ში ფაილების სიაზე, მოითხოვს `tuist generate`-ს, სანამ პროექტი ხელახლა აიწყობა. [აგებადი საქაღალდეები](#buildable-folders) ამ პასუხისმგებლობას Xcode-ის სინქრონიზებულ ჯგუფებზე გადაიტანს, ასე რომ ფაილური ხის ცვლილებები აღარ იწვევს ხელახალ გენერაციას.

შეუთავსეთ ეს `generated-projects` <.localized_link href="/guides/features/agentic-coding/skills">skill</.localized_link>-თან, რომელიც ასწავლის აგენტებს Tuist პროექტის ყოველდღიურ სამუშაო პროცესს.

#### არ გამოყოთ ქეში თითოეული worktree-ისთვის {#worktrees-shared-cache}

Tuist მიჰყვება <.localized_link href="/cli/directories">XDG Base Directory Specification</.localized_link>-ს, ამიტომ ნაგულისხმევად ერთსა და იმავე მანქანაზე ყოველი worktree იზიარებს `~/.cache/tuist`-ს და `~/.local/state/tuist`-ს. ეს არის ის, რაც გჭირდებათ: ერთ worktree-ში კომპილირებული helpers, მეორეში ჩამოტვირთული plugins და მესამეში ამოღებული module-cache ბინარები ყველა ხელახლა გამოყენებადია.

პარალელური `tuist` გამოძახებები worktree-ებს შორის უსაფრთხოა პარალელურად გასაშვებად. თავი აარიდეთ `TUIST_XDG_CACHE_HOME`-ის worktree-ლოკალურ გზაზე მიმართვას, თუ კონკრეტულად იზოლაცია არ გჭირდებათ; ასეთი ქმედება აიძულებს ყოველ worktree-ს ხელახლა „გაათბოს“ helpers, plugins და ბინარები.

#### შეინახეთ SwiftPM-ის scratch თითოეული worktree-ისთვის {#worktrees-swiftpm-scratch}

Swift Package Manager-ს აქვს საკუთარი გზების კონტროლი. `--scratch-path` არის ცვალებადი სამუშაო მდგომარეობა და ნაგულისხმევად არის `.build`, ხოლო `--cache-path` არის საერთო ქეშის დირექტორია. ეს ორი გზა არ უნდა იყოს ერთნაირად განხილული, როდესაც რამდენიმე worktree არის აქტიური.

Tuist-ის ნაგულისხმევი `tuist install` ქცევა უკვე ინახავს SwiftPM-ის scratch-ს პაკეტის დირექტორიაში, ამიტომ თითოეულ worktree-ს აქვს საკუთარი `.build`. შეინარჩუნეთ ეს იზოლაცია. ერთი საერთო SwiftPM scratch დირექტორია შეიძლება აურიოს checkouts, ბილდის შუალედური ფაილები, plugins, macros და lock ფაილები არადაკავშირებული ბრენჩებიდან.

თუ SwiftPM-ის არგუმენტებს გადასცემთ `tuist install -- ...`-ის მეშვეობით ან `Tuist.swift`-ში მყოფი `installOptions`-ის მეშვეობით, გააზიარეთ `--cache-path`, როდესაც გსურთ დამოკიდებულებების უფრო სწრაფად მიღება, მაგრამ `--scratch-path` დატოვეთ დაყენების გარეშე ან მიმართეთ ის worktree-ლოკალურ დირექტორიაზე:

```swift
import ProjectDescription

let tuist = Tuist(
    project: .tuist(
        installOptions: .options(
            passthroughSwiftPackageManagerArguments: [
                "--cache-path",
                "/Users/Shared/swiftpm/cache/xcode-16-macos",
            ]
        )
    )
)
```

გამოიყენეთ wrapper ან CI-ის გარემოს ცვლადი ქეშის გზისთვის, თუ ის უნდა იცვლებოდეს Xcode-ის, Swift toolchain-ის ან პლატფორმის მიხედვით. თავი აარიდეთ საერთო `--scratch-path`-ის რეპოზიტორიაში შეტანას.

თუ დამოკიდებულების მდგომარეობა დაზიანებულად ჩანს მხოლოდ ერთ worktree-ში, წაშალეთ ამ worktree-ის `.build` დირექტორია და ხელახლა გაუშვით `tuist install`. თუ საერთო SwiftPM ქეში ეჭვმიტანილად ჩანს worktree-ებს შორის, გამოიყენეთ `swift package purge-cache` დამოკიდებულებების ხელახლა ინსტალაციამდე.

#### მოეყრდენით module cache-ს {#worktrees-module-cache}

<.localized_link href="/guides/features/cache/module-cache">module cache</.localized_link> არის ის, რაც პარალელურ worktree-ებს მოქნილს ხდის. ვინაიდან Tuist ითვლის დეტერმინისტულ <.localized_link href="/guides/features/projects/hashing">hash</.localized_link>-ს თითოეული target-ისთვის, ორი worktree, რომელიც მიმართულია ბრენჩებზე, რომლებიც იზიარებენ ისტორიის უმეტეს ნაწილს, მიიღებს იგივე ბინარებს. გაუშვით `tuist cache` ყოველ commit-ზე `main`-ზე CI-დან; ლოკალურად, `tuist generate` თითოეულ worktree-ში იღებს ყველაფერს, რაც შესაძლებელია ქეშიდან და კომპილირებს მხოლოდ იმას, რაც თქვენმა ბრენჩმა რეალურად შეცვალა.

თუ worktree ბრუნდება source ბილდებზე, როდესაც ქეშში მოხვედრას ელოდით, მიჰყევით <.localized_link href="/guides/features/projects/hashing#debugging">hashing debugging steps</.localized_link>-ს; არადეტერმინისტული hashes (ჩვეულებრივ გამოწვეული პროექტში აბსოლუტური გზებით) არის ყველაზე ხშირი მიზეზი და ისინი მკაფიოდ ჩანან ორი worktree-ის შედარებისას.

#### Swift Package-ის რეზოლუციის დაჩქარება registry-ით {#worktrees-registry}

თითოეული worktree დამოუკიდებლად ახდენს Swift პაკეტების რეზოლუციას. დიდ დამოკიდებულების გრაფიან პროექტებზე ეს სწრაფად იკრიბება. <.localized_link href="/guides/features/package-registries/swift">Tuist Registry</.localized_link>-ზე გადასვლა თავიდან აცილებს git ისტორიების ხელახლა კლონირებას და ამცირებს რეზოლუციის დროს წუთებიდან წამებამდე.

#### მიაწოდეთ აგენტებს წვდომა პროექტის ინსაიტებზე {#worktrees-mcp}

როდესაც ბილდები და ტესტები მრავალ worktree-ში გადის, ყველაზე სასარგებლო, რაც აგენტს შეუძლია გააკეთოს, არის იმის განსაზღვრა, *რომელი* გაშვებებში მოხდა რეგრესია, რომელი ტესტებია არასტაბილური ან როგორ შეიცვალა bundle-ის ზომა. Tuist ამ მონაცემებს აწვდის <.localized_link href="/guides/features/agentic-coding/mcp">MCP server</.localized_link>-ის და <.localized_link href="/guides/features/agentic-coding/skills">Skills</.localized_link> პაკეტის მეშვეობით. აირჩიეთ ერთი სამუშაო პროცესისთვის და დარჩით მასზე; ორივეს ერთდროულად გამოყენება ერთი და იგივე ამოცანისთვის ხშირად იწვევს აგენტის არათანმიმდევრულ ქცევას.
