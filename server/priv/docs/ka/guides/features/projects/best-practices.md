# საუკეთესო პრაქტიკები {#best-practices}

სხვადასხვა გუნდებთან და პროექტებთან მუშაობის წლების განმავლობაში, ჩვენ გამოვყავით საუკეთესო პრაქტიკების ნაკრები, რომელთა დაცვასაც ვურჩევთ Tuist-თან და Xcode-ის პროექტებთან მუშაობისას. ეს პრაქტიკები არ არის სავალდებულო, მაგრამ ისინი დაგეხმარებათ პროექტების ისეთი სტრუქტურირებით, რაც მათ შენარჩუნებასა და მასშტაბირებას გაამარტივებს.

## Xcode {#xcode}

### არასასურველი შაბლონები {#discouraged-patterns}

#### კონფიგურაციები დაშორებული გარემოების მოდელირებისთვის {#configurations-to-model-remote-environments}

ბევრი ორგანიზაცია იყენებს ბილდის კონფიგურაციებს სხვადასხვა დაშორებული გარემოს მოდელირებისთვის (მაგ., `Debug-Production` ან `Release-Canary`), თუმცა ამ მიდგომას აქვს გარკვეული უარყოფითი მხარეები:

- **შეუსაბამობები:** თუ გრაფში არსებობს კონფიგურაციის შეუსაბამობები, ბილდის სისტემამ ზოგიერთი სამიზნისთვის შეიძლება არასწორი კონფიგურაცია გამოიყენოს.
- **სირთულე:** პროექტებში შეიძლება აღმოჩნდეს ადგილობრივი კონფიგურაციებისა და დაშორებული გარემოების გრძელი სია, რომელთა გააზრება და შენარჩუნება რთულია.

ბილდის კონფიგურაციები შექმნილია სხვადასხვა ბილდის პარამეტრების ასახვისთვის და პროექტებს იშვიათად სჭირდებათ მეტი, ვიდრე უბრალოდ `Debug` და `Release`. სხვადასხვა გარემოს მოდელირების საჭიროება შესაძლებელია სხვაგვარად მიღწეული იქნას:

- **Debug ბილდებში:** შეგიძლიათ აპლიკაციაში ჩართოთ ყველა კონფიგურაცია, რომელიც განვითარების ეტაპზე უნდა იყოს ხელმისაწვდომი (მაგ., endpoint-ები) და გადაერთოთ მათ შორის runtime-ში. გადართვა შესაძლებელია ან scheme-ის launch environment ცვლადების გამოყენებით, ან აპლიკაციაში არსებული UI-ით.
- **Release ბილდებში:** გამოშვების შემთხვევაში, შეგიძლიათ ჩართოთ მხოლოდ ის კონფიგურაცია, რომელზეც release ბილდი არის მიბმული და არ ჩართოთ კონფიგურაციების გადართვის runtime ლოგიკა კომპილატორის დირექტივების გამოყენებით.

> [!NOTE]
> **არასტანდარტული კონფიგურაციები**
>
> მიუხედავად იმისა, რომ Tuist მხარს უჭერს არასტანდარტულ კონფიგურაციებს და მათ მართვას აადვილებს ჩვეულებრივ Xcode-ის პროექტებთან შედარებით, თქვენ მიიღებთ გაფრთხილებებს, თუ კონფიგურაციები არ არის თანმიმდევრული დამოკიდებულობების გრაფში. ეს ეხმარება ბილდის საიმედოობის უზრუნველყოფას და კონფიგურაციასთან დაკავშირებული პრობლემების თავიდან აცილებას.


## გენერირებული პროექტები

### აგებადი საქაღალდეები

Tuist 4.62.0-მა დაამატა მხარდაჭერა **აგებადი საქაღალდეებისთვის** (Xcode-ის სინქრონიზებული ჯგუფები), ფუნქცია, რომელიც წარმოდგენილი იყო Xcode 16-ში merge კონფლიქტების შესამცირებლად.

მიუხედავად იმისა, რომ Tuist-ის wildcard შაბლონები (მაგ., `Sources/**/*.swift`) უკვე აღმოფხვრის merge კონფლიქტებს გენერირებულ პროექტებში, აგებად საქაღალდეებს აქვთ დამატებითი უპირატესობები:

- **ავტომატური სინქრონიზაცია**: თქვენი პროექტის სტრუქტურა რჩება სინქრონიზებული ფაილურ სისტემასთან — ფაილების დამატების ან წაშლისას ხელახლა გენერაცია არ არის საჭირო
- **AI-ზე მორგებული სამუშაო ნაკადები**: კოდირების ასისტენტებსა და აგენტებს შეუძლიათ შეცვალონ თქვენი კოდის ბაზა პროექტის ხელახალი გენერაციის გამოწვევის გარეშე
- **უფრო მარტივი კონფიგურაცია**: განსაზღვრეთ საქაღალდეების გზები ცალსახა ფაილების სიების მართვის ნაცვლად

ჩვენ ვურჩევთ აგებადი საქაღალდეების გამოყენებას ტრადიციული `Target.sources` და `Target.resources` ატრიბუტების ნაცვლად განვითარების უფრო გამარტივებული გამოცდილებისთვის.

::: code-group

```swift [With buildable folders]
let target: Target = .target(
  name: "App",
  destinations: .iOS,
  product: .app,
  bundleId: "dev.tuist.App",
  buildableFolders: ["App/Sources", "App/Resources"]
)
```

```swift [Without buildable folders]
let target: Target = .target(
  name: "App",
  destinations: .iOS,
  product: .app,
  bundleId: "dev.tuist.App",
  sources: ["App/Sources/**"],
  resources: ["App/Resources/**"]
)
```

### დამოკიდებულობები

#### CI-ზე ვერსიების იძულებითი რეზოლუცია

Swift Package Manager-ის დამოკიდებულობების CI-ზე ინსტალაციისას, ჩვენ ვურჩევთ `--force-resolved-versions` ფლაგის გამოყენებას დეტერმინისტული ბილდების უზრუნველსაყოფად:

```bash
tuist install --force-resolved-versions
```

ეს ფლაგი უზრუნველყოფს, რომ დამოკიდებულობები რეზოლუცირდება `Package.resolved`-ში მიმაგრებული ზუსტი ვერსიების გამოყენებით, რაც აღმოფხვრის დამოკიდებულობების რეზოლუციის არადეტერმინიზმით გამოწვეულ პრობლემებს. ეს განსაკუთრებით მნიშვნელოვანია CI-ზე, სადაც რეპროდუცირებადი ბილდები კრიტიკულია.

#### დამოკიდებულობების cached ინსტალაცია GitHub Actions-ზე {#dependency-cache-volumes}

გენერირებული პროექტებისთვის, გამოიყენეთ [tuist/install](https://github.com/tuist/install) `Package.resolved`-ში მიმაგრებული დამოკიდებულობების ინსტალაციისა და გაშვებებს შორის მათი cache-ში შენახვისთვის. ის ავტომატურად იყენებს <.localized_link href="/guides/features/runners/cache-volumes">cache volumes</.localized_link>-ს Tuist Runners-ზე და GitHub-ის cache-ს სხვა runners-ზე.

```yaml
name: Generate project
on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read

jobs:
  generate:
    runs-on: tuist-macos
    steps:
      - uses: actions/checkout@v4
      - uses: jdx/mise-action@v4
      - uses: tuist/install@v1
      - run: tuist generate --no-open
```

ქვესაქაღალდეში მყოფი პროექტისთვის, გადაეცით მისი გზა checkout-თან მიმართებაში:

```yaml
- uses: tuist/install@v1
  with:
    path: apps/ios
```

დამატებითი პარამეტრებისთვის იხილეთ [action reference](https://github.com/tuist/install#usage).

### აგენტური კოდირება და worktrees {#agentic-coding-and-worktrees}

კოდირების აგენტები და ადამიანი კონტრიბუტორები სულ უფრო მეტად მუშაობენ პარალელურად: დეველოპერი ტოვებს worktree-ს გახსნილს იმ ფუნქციისთვის, რომელსაც ის აკვირდება, ხოლო ერთი ან მეტი აგენტი იტერაციას აკეთებს საკუთარ ბრენჩებზე დაძმობილებულ worktree-ებში. რამდენიმე პროექტული არჩევანი ამ პროცესს ბევრად უფრო გლუვს ხდის.

#### გამოიყენეთ აგებადი საქაღალდეები აგენტის მიერ განხორციელებული ცვლილებებისთვის {#worktrees-buildable-folders}

როდესაც აგენტი ამატებს ან შლის ფაილებს, ყველაფერი, რაც დამოკიდებულია `Project.swift`-ში არსებულ ფაილების სიაზე, საჭიროებს `tuist generate`-ს, სანამ პროექტი ხელახლა აიწყობა. [აგებადი საქაღალდეები](#buildable-folders) ამ პასუხისმგებლობას გადააქვთ Xcode-ის სინქრონიზებულ ჯგუფებზე, ასე რომ ფაილური ხის ცვლილებები აღარ იწვევენ ხელახლა გენერაციას.

შეუთავსეთ ეს `generated-projects` <.localized_link href="/guides/features/agentic-coding/skills">skill</.localized_link>-თან, რომელიც ასწავლის აგენტებს Tuist პროექტის ყოველდღიურ სამუშაო ნაკადს.

#### არ გამოყოთ cache თითოეული worktree-სთვის {#worktrees-shared-cache}

Tuist მიჰყვება <.localized_link href="/cli/directories">XDG Base Directory Specification</.localized_link>-ს, ასე რომ, ნაგულისხმევად, ერთსა და იმავე მანქანაზე ყოველი worktree იზიარებს `~/.cache/tuist`-ს და `~/.local/state/tuist`-ს. ეს არის ის, რაც გჭირდებათ: ერთ worktree-ში კომპილირებული helpers, მეორეში ჩამოტვირთული plugins და მესამის მიერ ამოღებული module-cache ბინარები ყველა ხელახლა გამოყენებადია.

პარალელურად უსაფრთხოა worktree-ებში `tuist`-ის ერთდროული გამოძახებების გაშვება. თავი აარიდეთ `TUIST_XDG_CACHE_HOME`-ის worktree-ის ლოკალურ გზაზე მიმართვას, თუ კონკრეტულად იზოლაცია არ გჭირდებათ; ასეთი ქმედება აიძულებს ყოველ worktree-ს ხელახლა „გაათბოს“ helpers, plugins და ბინარები.

#### შეინახეთ SwiftPM scratch თითოეული worktree-სთვის {#worktrees-swiftpm-scratch}

Swift Package Manager-ს აქვს საკუთარი გზის კონტროლი. `--scratch-path` არის ცვლადი სამუშაო მდგომარეობა და ნაგულისხმევად არის `.build`, ხოლო `--cache-path` არის გაზიარებული cache დირექტორია. ეს ორი გზა არ უნდა განიხილებოდეს ერთნაირად, როდესაც რამდენიმე worktree არის აქტიური.

Tuist-ის ნაგულისხმევი `tuist install` ქცევა უკვე ინახავს SwiftPM scratch-ს პაკეტის დირექტორიაში, ასე რომ, თითოეულ worktree-ს აქვს საკუთარი `.build`. შეინარჩუნეთ ეს იზოლაცია. ერთი გაზიარებული SwiftPM scratch დირექტორია შეიძლება აურიოს checkouts, ბილდის შუალედური ფაილები, plugins, macros და lock files არადაკავშირებული branch-ებიდან.

თუ SwiftPM არგუმენტებს გადასცემთ `tuist install -- ...`-ით ან `installOptions`-ით `Tuist.swift`-ში, გააზიარეთ `--cache-path`, როცა გსურთ დამოკიდებულებების უფრო სწრაფად მიღება, მაგრამ `--scratch-path` დატოვეთ დაყენებელი ან მიმართეთ ის worktree-ის ლოკალურ დირექტორიაზე:

```swift
import ProjectDescription

let tuist = Tuist(
    project: .tuist(
        installOptions: .options(
            passthroughSwiftPackageManagerArguments: [
                "--cache-path",
                "/Users/Shared/swiftpm/cache/xcode-16-macos",
            ]
        )
    )
)
```

გამოიყენეთ wrapper ან CI გარემოს ცვლადი cache გზისთვის, თუ ის უნდა განსხვავდებოდეს Xcode-ის, Swift toolchain-ის ან პლატფორმის მიხედვით. თავი აარიდეთ გაზიარებული `--scratch-path`-ის რეპოზიტორიაში კომიტს.

თუ დამოკიდებულების მდგომარეობა დაზიანებული ჩანს მხოლოდ ერთ worktree-ში, წაშალეთ ამ worktree-ის `.build` დირექტორია და ხელახლა გაუშვით `tuist install`. თუ გაზიარებული SwiftPM cache ეჭვისმომგვრელი ჩანს worktree-ებში, გამოიყენეთ `swift package purge-cache` დამოკიდებულებების ხელახლა ინსტალაციამდე.

#### დაეყრდენით module cache-ს {#worktrees-module-cache}

<.localized_link href="/guides/features/cache/module-cache">module cache</.localized_link> არის ის, რაც პარალელურ worktree-ებს მართვადს ხდის. ვინაიდან Tuist თითოეული target-ისთვის ითვლის დეტერმინისტულ <.localized_link href="/guides/features/projects/hashing">hash</.localized_link>-ს, ორი worktree, რომელიც მიუთითებს branch-ებზე, რომლებიც იზიარებენ ისტორიის უმეტეს ნაწილს, ერთსა და იმავე ბინარებს მოხვდება. გაუშვით `tuist cache` ყოველ კომიტზე `main`-ზე CI-დან; ლოკალურად, `tuist generate` თითოეულ worktree-ში იღებს ყველაფერს, რაც შეუძლია cache-დან და აწყობს მხოლოდ იმას, რაც თქვენმა branch-მა რეალურად შეცვალა.

თუ worktree ბრუნდება source builds-ზე, როცა ქეშში მოხვედრას ელოდით, მიჰყევით <.localized_link href="/guides/features/projects/hashing#debugging">hashing debugging steps</.localized_link>-ს; არადეტერმინისტული hashes (ჩვეულებრივ გამოწვეული პროექტში აბსოლუტური გზებით) არის ყველაზე ხშირი მიზეზი და ისინი მკაფიოდ ჩანან ორი worktree-ის შედარებისას.

#### Swift Package resolution-ის დაჩქარება registry-ით {#worktrees-registry}

თითოეული worktree დამოუკიდებლად ახდენს Swift პაკეტების რეზოლუციას. დიდი დამოკიდებულების გრაფის მქონე პროექტზე ეს სწრაფად იკრიბება. <.localized_link href="/guides/features/package-registries/swift">Tuist Registry</.localized_link>-ზე გადასვლა თავიდან აიცილებს git ისტორიების ხელახლა კლონირებას და რეზოლუციას წუთებიდან წამებამდე ამცირებს.

#### აგენტებისთვის პროექტის insights-ზე წვდომის მიცემა {#worktrees-mcp}

როდესაც builds და tests ბევრ worktree-ში გაშვებულია, ყველაზე სასარგებლო რამ, რაც აგენტს შეუძლია გააკეთოს, არის იმის გააზრება, *რომელი* გაშვებები გაუარესდა, რომელი ტესტებია flaky, ან როგორ შეიცვალა bundle-ის ზომა. Tuist ამ მონაცემებს ავლენს <.localized_link href="/guides/features/agentic-coding/mcp">MCP server</.localized_link>-ისა და <.localized_link href="/guides/features/agentic-coding/skills">Skills</.localized_link> პაკეტის მეშვეობით. აირჩიეთ ერთი სამუშაო ნაკადისთვის და დარჩით მასზე; ორივეს ერთი და იგივე ამოცანისთვის შერევა ჩვეულებრივ არათანმიმდევრულ აგენტის ქცევას იწვევს.
