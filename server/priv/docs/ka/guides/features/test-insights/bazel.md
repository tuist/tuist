# Bazel-ის ტესტების ანალიტიკა {#bazel-test-insights}

გაუშვით Bazel-ის ტესტები Tuist-ის მეშვეობით, რათა გამოიყენოთ იგივე სატესტო დაფები, რომლებსაც ყველა სხვა ბილდ-სისტემა იყენებს:

```bash
tuist bazel test -- //app:tests
```

არგუმენტები `--`-ის შემდეგ გადაეცემა `bazel test`-ს. გამოიყენეთ `--path` პროექტისა და სამუშაო დირექტორიის არჩევასთვის და `--bazel` სხვა შესრულებადი ფაილის, მაგალითად `bazelisk`-ის, არჩევასთვის. ჩვეულებრივი `bazel test` ასევე აჩვენებს ტესტების შედეგებს, მაგრამ არ იღებს და არ აწესებს Tuist-ის კარანტინის პოლიტიკებს.

> [!NOTE]
> `tuist bazel test` გარსაცმის გამოყენება საჭიროა მხოლოდ <.localized_link href="/guides/features/test-insights/flaky-tests/bazel">კარანტინში მოთავსებული ტესტებისთვის</.localized_link>. ცალკეული შემთხვევების ანგარიშგება ჩვეულებრივი ტესტების გაშვებისთვის კონფიგურირდება `tuist bazel setup`-ით `.bazelrc.tuist`-ში, ამიტომ ჩვეულებრივი `bazel test` ასევე აჩვენებს ინდივიდუალურ შემთხვევებს.

## რა თვალყურს ედევნება {#what-is-tracked}

Tuist პარსავს `test.xml` ანგარიშებს და იღებს `test.log` გამოტანას, რომელსაც Bazel ქმნის თითოეული სატესტო მიზნისთვის, შემდეგ კი აერთიანებს მათ საერთო ტესტების გაშვების მოდელში. თითოეული გაშვება იწერს:

- ინდივიდუალური სატესტო შემთხვევის წარმატების, წარუმატებლობისა და გამოტოვების სტატუსს ხანგრძლივობასთან ერთად.
- სატესტო მიზანს, კლასსა და სატესტო ნაკრების სტრუქტურას.
- განმეორებითი ცდები, როდესაც Bazel კონფიგურირებულია არასტაბილური ტესტების განმეორებითი გაშვებისთვის.
- შეცდომის გამოტანა, აღებული მიზნის `test.log`-დან.

**ტესტების გაშვებები**, **სატესტო შემთხვევები** და ინდივიდუალური ტესტების გვერდები Bazel-ისთვის ისევე მუშაობს, როგორც სხვა ბილდ-სისტემებისთვის.

## JUnit-ის ანგარიშების გენერირება ცალკეული შემთხვევებისთვის {#per-case-junit-reports}

ცალკეული შემთხვევების სტრიქონები დამოკიდებულია იმაზე, რომ სატესტო მიზანი წერდეს JUnit `test.xml`-ს `$XML_OUTPUT_FILE` ბილიკზე, რომელსაც Bazel უზრუნველყოფს. როდესაც გამშვები არ წერს მას, Bazel იყენებს სინთეზურ ერთ-შემთხვევიან ანგარიშს, რომელიც სახელდებულია მიზნის მიხედვით, და Tuist აჩვენებს ერთ სტრიქონს თითოეული მიზნისთვის (მონიშნული როგორც **Bazel-ის მიზანი** სატესტო შემთხვევების სიაში), სადაც ნედლი `test.log` კვლავ ხელმისაწვდომია გაშვების გვერდზე.

Bazel-ის ტესტების უმეტესი წესი უკვე ქმნის რეალურ `test.xml`-ს:

- `java_test` და `kt_jvm_test`: JUnit ჩაშენებულია.
- `cc_test` GoogleTest-ით: გამშვები წერს JUnit-ს, როდესაც კომპილირებულია ბოლო gtest-ის წინააღმდეგ; ძველი კონფიგურაციები საჭიროებენ `--gtest_output=xml:$XML_OUTPUT_FILE`-ს.
- `py_test`: გამოიყენეთ pytest `--junitxml=$XML_OUTPUT_FILE`-ით, ან `rules_python` pytest გამშვები.
- `go_test`: გადაუშვით `go test -json` `gotestsum --junitfile=$XML_OUTPUT_FILE`-ის მეშვეობით, ან შეფუთეთ დამხმარე სკრიპტით, რომელიც ქმნის JUnit-ს.

`rust_test` `rules_rust`-დან და `rules_rs`-დან აწარმოებს სტანდარტულ `libtest` ჰარნესს, რომელიც არ წერს JUnit-ს სტაბილურ Rust-ზე. შეფუთეთ სატესტო მიზანი სკრიპტით, რომელიც პარსავს `libtest` გამოტანას და წერს JUnit-ს `$XML_OUTPUT_FILE`-ში; თქვენ ინარჩუნებთ ცალკეული შემთხვევების სტრიქონებს Tuist-ში და იგივე გაშვება რჩება ერთ Bazel-ის სატესტო მიზნად.

## ტესტის იდენტურობა {#test-identity}

შემთხვევები იდენტიფიცირდება მიზნის ლეიბლით, კლასის სახელით (საწყისი მნიშვნელობა — სატესტო ნაკრების სახელი) და ტესტის სახელით. ეს ცალკე ინარჩუნებს იდენტური სახელის მქონე მეთოდებს სხვადასხვა კლასში. ძველი ანგარიშები, რომლებიც იყენებდნენ განსხვავებულ შემომსაზღვრელ სატესტო ნაკრების სახელს, ინარჩუნებენ თავიანთ ისტორიას ძველი იდენტურობის ქვეშ; ძველ იდენტურობაზე გამოყენებული სტატუსის ცვლილებები უნდა გადატანილ იქნას ახალზე, და ბრძანება გაფრთხილებთ, როდესაც შეცდომა ემთხვევა ძველ იდენტურობას, რათა იცოდეთ, რომელი პოლიტიკა გადაიტანოთ.

## CI კონტექსტის მიწოდება {#providing-ci-context}

Tuist კითხულობს git კომიტისა და შტოს ინფორმაციას Bazel-ის ბილდის მეტამონაცემებიდან, რათა ერთსა და იმავე კომიტზე შესრულებული გაშვებები შედარდეს სხვადასხვა გარემოში. უმეტესი უწყვეტი ინტეგრაციის სისტემები უკვე აწესებს ამას; როდესაც თქვენი არ აკეთებს, გადაეცით ისინი ცალსახად:

```bash
tuist bazel test -- \
  --build_metadata=CI=true \
  --build_metadata=GIT_COMMIT="$GIT_COMMIT" \
  --build_metadata=GIT_BRANCH="$GIT_BRANCH" //app:tests
```

იგივე `--build_metadata` ფლაგია, რასაც <.localized_link href="/guides/features/build-insights/bazel#custom-metadata">Bazel-ის ბილდის ანალიტიკის</.localized_link> გვერდი აღწერს გამოძახებების მონიშვნისთვის, ამიტომ ფლაგების ერთი ნაკრები ფარავს ორივე ზედაპირს.

## არასტაბილური ტესტები და კარანტინი {#flaky-tests-and-quarantine}

განმეორებითი ცდები, გაშვებებს შორის არასტაბილურობის აღმოჩენა და ცალკეული შემთხვევების კარანტინი (Mute და Skip) ყველა მუშაობს `tuist bazel test`-ის მეშვეობით. სრული სამუშაო პროცესისთვის იხილეთ <.localized_link href="/guides/features/test-insights/flaky-tests/bazel">Bazel-ის არასტაბილური ტესტები</.localized_link>.

## მონაცემთა შენახვა {#data-retention}

Tuist ინარჩუნებს Bazel-ის გამოძახებას, რომელმაც წარმოქმნა ტესტების გაშვება, მის ჟურნალებსა და მოლოდინში მყოფ ტესტების მიღების ჩანაწერებს 90 დღის განმავლობაში. სატესტო შემთხვევები და მათი გაშვების ისტორია იყენებენ იგივე მოდელს, რასაც ყველა სხვა ბილდ-სისტემა, და არ ექვემდებარებიან ამ ვადას. სრული პოლიტიკისთვის იხილეთ <.localized_link href="/guides/server/data-retention">მონაცემთა შენახვა</.localized_link>.
