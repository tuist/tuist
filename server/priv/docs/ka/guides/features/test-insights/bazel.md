# Bazel ტესტების ანალიტიკა {#bazel-test-insights}

გაუშვით Bazel ტესტები Tuist-ის საშუალებით, რათა მიიღოთ იგივე სატესტო დაფები, რომლებსაც ყველა სხვა ბილდ-სისტემა იყენებს:

```bash
tuist bazel test -- //app:tests
```

არგუმენტები `--`-ის შემდეგ გადაეცემა `bazel test`-ს. გამოიყენეთ `--path` პროექტისა და სამუშაო დირექტორიის არჩევასთვის და `--bazel` სხვა შესრულებადი ფაილის, მაგალითად `bazelisk`-ის, არჩევასთვის. ჩვეულებრივი `bazel test` კვლავ აწვდის ტესტის შედეგებს, მაგრამ არ იღებს და არ აღასრულებს Tuist-ის კარანტინის პოლიტიკებს.

> [!NOTE]
> `tuist bazel test` გარსაცმი საჭიროა მხოლოდ <.localized_link href="/guides/features/test-insights/flaky-tests/bazel">კარანტინში მოქცეული ტესტებისთვის</.localized_link>. რეგულარული ტესტების გაშვებისას საქმეზე ანგარიშგება ნაწყობია `tuist bazel setup`-ით `.bazelrc.tuist`-ში, ამიტომ ჩვეულებრივი `bazel test` ასევე აწვდის ინდივიდუალურ საქმეებს.

## რა ფიქსირდება {#what-is-tracked}

Tuist აანალიზებს `test.xml` ანგარიშებს და იჭერს `test.log` გამოტანას, რომელსაც Bazel ქმნის თითოეული სატესტო მიზნისთვის, შემდეგ კი აერთიანებს მათ საერთო ტესტების გაშვების მოდელში. თითოეული გაშვება იწერს:

- ინდივიდუალური სატესტო საქმის წარმატების, წარუმატებლობისა და გამოტოვების სტატუსს ხანგრძლივობასთან ერთად.
- სატესტო მიზანს, კლასსა და სუიტის სტრუქტურას.
- გამეორების ცდებს, როდესაც Bazel ნაწყობია არასტაბილური ტესტების გამეორებისთვის.
- შეცდომის გამოტანას, რომელიც ამოღებულია მიზნის `test.log`-დან.

**ტესტების გაშვებები**, **სატესტო საქმეები** და ინდივიდუალური ტესტების გვერდები Bazel-ისთვის ისევე მუშაობს, როგორც სხვა ბილდ-სისტემებისთვის.

## საქმეზე JUnit ანგარიშების გენერირება {#per-case-junit-reports}

საქმეზე სტრიქონები დამოკიდებულია იმაზე, რომ სატესტო მიზანი წერს JUnit `test.xml`-ს `$XML_OUTPUT_FILE` გზაზე, რომელსაც Bazel უზრუნველყოფს. როდესაც გამშვები არ წერს მას, Bazel ბრუნდება სინთეზირებულ ერთ-საქმიან ანგარიშზე, რომელიც სახელდება მიზნის მიხედვით, და Tuist აჩვენებს ერთ სტრიქონს თითოეული მიზნისთვის (მონიშნული როგორც **Bazel მიზანი** სატესტო საქმეების სიაში), სადაც უცვლელი `test.log` კვლავ ხელმისაწვდომია გაშვების გვერდზე.

Bazel-ის უმეტესი სატესტო წესები უკვე ქმნიან რეალურ `test.xml`-ს:

- `java_test` და `kt_jvm_test`: JUnit ჩაშენებულია.
- `cc_test` GoogleTest-ით: გამშვები წერს JUnit-ს, როდესაც კომპილირებულია ბოლო gtest-ის წინააღმდეგ; ძველი კონფიგურაციები საჭიროებენ `--gtest_output=xml:$XML_OUTPUT_FILE`-ს.
- `py_test`: გამოიყენეთ pytest `--junitxml=$XML_OUTPUT_FILE`-ით ან `rules_python` pytest გამშვებით.
- `go_test`: გადაუშვით `go test -json` `gotestsum --junitfile=$XML_OUTPUT_FILE`-ში ან შეფუთეთ დამხმარე სკრიპტით, რომელიც გამოიმუშავებს JUnit-ს.

`rust_test` `rules_rust`-დან და `rules_rs`-დან აწარმოებს სტანდარტულ `libtest` ჰარნესს, რომელიც არ წერს JUnit-ს სტაბილურ Rust-ზე. შეფუთეთ სატესტო მიზანი სკრიპტით, რომელიც აანალიზებს `libtest` გამოტანას და წერს JUnit-ს `$XML_OUTPUT_FILE`-ში; თქვენ ინარჩუნებთ საქმეზე სტრიქონებს Tuist-ში და იგივე გაშვება რჩება ერთ Bazel სატესტო მიზნად.

## ტესტის იდენტურობა {#test-identity}

საქმეები იდენტიფიცირდება მიზნის ლეიბლით, კლასის სახელით (სუიტის სახელზე დაბრუნებით) და ტესტის სახელით. ეს უზრუნველყოფს იდენტური სახელის მქონე მეთოდების განცალკევებას სხვადასხვა კლასებში. ძველ ანგარიშებს, რომლებიც იყენებდნენ განსხვავებულ შემომსაზღვრელ სუიტის სახელს, აქვთ თავიანთი ისტორია ძველი იდენტურობის ქვეშ; ძველ იდენტურობაზე გამოყენებული სტატუსის ცვლილებები უნდა გადაიტანოთ ახალზე, და ბრძანება გაფრთხილებთ, როდესაც შეცდომა ემთხვევა ძველ იდენტურობას, რათა იცოდეთ, რომელი პოლიტიკა გადაიტანოთ.

## CI კონტექსტის მიწოდება {#providing-ci-context}

Tuist კითხულობს git კომიტისა და შტოს ინფორმაციას Bazel-ის ბილდის მეტამონაცემებიდან, რათა იგივე კომიტზე გაშვებები შედარდეს გარემოებს შორის. უმეტესი უწყვეტი ინტეგრაციის სისტემები უკვე აყენებს მათ; როდესაც თქვენი არ აკეთებს, გადაეცით ისინი ცალსახად:

```bash
tuist bazel test -- \
  --build_metadata=CI=true \
  --build_metadata=GIT_COMMIT="$GIT_COMMIT" \
  --build_metadata=GIT_BRANCH="$GIT_BRANCH" //app:tests
```

იგივე `--build_metadata` ფლაგია, რასაც <.localized_link href="/guides/features/build-insights/bazel#custom-metadata">Bazel ბილდის ანალიტიკა</.localized_link> გვერდი აღწერს გამოძახებების მონიშვნისთვის, ამიტომ ერთი ნაკრები ფლაგებისა ფარავს ორივე ზედაპირს.

## არასტაბილური ტესტები და კარანტინი {#flaky-tests-and-quarantine}

გამეორებები, გაშვებებს შორის არასტაბილურობის აღმოჩენა და საქმეზე კარანტინი (Mute და Skip) ყველა მუშაობს `tuist bazel test`-ის საშუალებით. სრული სამუშაო პროცესისთვის იხილეთ <.localized_link href="/guides/features/test-insights/flaky-tests/bazel">Bazel არასტაბილური ტესტები</.localized_link>.

## მონაცემთა შენახვა {#data-retention}

Tuist ინარჩუნებს Bazel-ის გამოძახებას, რომელმაც წარმოქმნა ტესტის გაშვება, მის ჟურნალებსა და მოლოდინში მყოფ ტესტის შეტანის ჩანაწერებს 90 დღის განმავლობაში. სატესტო საქმეები და მათი გაშვების ისტორია იყენებენ იგივე მოდელს, როგორც ყველა სხვა ბილდ-სისტემა და არ ექვემდებარებიან ამ ვადას. სრული პოლიტიკისთვის იხილეთ <.localized_link href="/guides/server/data-retention">მონაცემთა შენახვა</.localized_link>.
