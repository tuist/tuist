# Bazel-ის ტესტების ანალიტიკა {#bazel-test-insights}

> [!IMPORTANT]
> **მოთხოვნები**
>
> - Bazel-ის სამუშაო სივრცე, დაკავშირებული `tuist bazel setup`-ით, როგორც აღწერილია <.localized_link href="/guides/get-started/bazel-project">Bazel-ის პროექტის დაწყება</.localized_link>-ში.

`tuist bazel setup` აკონფიგურირებს თითოეული სატესტო შემთხვევის შესახებ ანგარიშგებას `.bazelrc.tuist`-ში, რის შედეგადაც ჩვეულებრივი `bazel test` ინდივიდუალურ სატესტო შემთხვევებს იმავე დაფებზე აგზავნის, რომლებსაც ყველა სხვა ბილდის სისტემა იყენებს:

```bash
bazel test //app:tests
```

<.localized_link href="/guides/features/test-insights/flaky-tests/bazel">კარანტინის</.localized_link> გამოყენებისთვის, ტესტები Tuist-ის გარსაცმის მეშვეობით გაუშვით. არგუმენტები `--`-ის შემდეგ გადაეცემა `bazel test`-ს:

```bash
tuist bazel test -- //app:tests
```

## რა ფიქსირდება {#what-is-tracked}

Tuist პარსავს `test.xml` ანგარიშებს და იღებს `test.log` გამომავალ მონაცემებს, რომელსაც Bazel ქმნის თითოეული სატესტო მიზნისთვის, შემდეგ კი აერთიანებს მათ საერთო ტესტების გაშვების მოდელში. თითოეული გაშვება იწერს:

- ინდივიდუალური სატესტო შემთხვევის წარმატებული, წარუმატებელი და გამოტოვებული სტატუსი ხანგრძლივობასთან ერთად.
- სატესტო მიზანი, კლასი და სატესტო ნაკრების სტრუქტურა.
- გამეორების ცდები, როდესაც Bazel კონფიგურირებულია არასტაბილური ტესტების გამეორებისთვის.
- შეცდომის გამომავალი მონაცემები, ამოღებული მიზნის `test.log`-დან.

**ტესტების გაშვებები**, **სატესტო შემთხვევები** და ინდივიდუალური ტესტების გვერდები Bazel-ისთვის იგივენაირად მუშაობს, როგორც სხვა ბილდის სისტემებისთვის.

## თითოეული შემთხვევისთვის JUnit ანგარიშების გენერირება {#per-case-junit-reports}

თითოეული შემთხვევის სტრიქონები დამოკიდებულია იმაზე, რომ სატესტო მიზანი წერდეს JUnit `test.xml`-ს `$XML_OUTPUT_FILE` გზაზე, რომელსაც Bazel უზრუნველყოფს. როდესაც გამშვები ასეთს არ წერს, Bazel გადადის სინთეზირებულ ერთ-შემთხვევიან ანგარიშზე, სახელდართულ მიზნის მიხედვით, და Tuist აჩვენებს ერთ სტრიქონს თითოეული მიზნისთვის (მონიშნული როგორც **Bazel-ის მიზანი** სატესტო შემთხვევების სიაში), სადაც უმიზნო `test.log` კვლავ ხელმისაწვდომია გაშვების გვერდზე.

Bazel-ის ტესტების უმეტესი წესი უკვე ქმნის რეალურ `test.xml`-ს:

- `java_test` და `kt_jvm_test`: JUnit ჩაშენებულია.
- `cc_test` GoogleTest-ით: გამშვები წერს JUnit-ს, როდესაც კომპილირებულია ბოლო gtest-ის წინააღმდეგ; ძველი კონფიგურაციები საჭიროებენ `--gtest_output=xml:$XML_OUTPUT_FILE`-ს.
- `py_test`: გამოიყენეთ pytest `--junitxml=$XML_OUTPUT_FILE`-ით, ან `rules_python` pytest გამშვები.
- `go_test`: გადაუშვით `go test -json` `gotestsum --junitfile=$XML_OUTPUT_FILE`-ში, ან გააფორმათ დამხმარე საშუალებით, რომელიც გამოიმუშავებს JUnit-ს.

`rust_test` `rules_rust`-დან და `rules_rs`-დან აწარმოებს სტანდარტულ `libtest` ჰარნესს, რომელიც არ წერს JUnit-ს სტაბილურ Rust-ზე. გააფორმათ სატესტო მიზანი სკრიპტით, რომელიც პარსავს `libtest` გამომავალ მონაცემებს და წერს JUnit-ს `$XML_OUTPUT_FILE`-ში; თქვენ ინარჩუნებთ თითოეული შემთხვევის სტრიქონებს Tuist-ში და იგივე გაშვება რჩება ერთ Bazel სატესტო მიზნად.

## ტესტის იდენტურობა {#test-identity}

შემთხვევები იდენტიფიცირდება მიზნის ლეიბლით, კლასის სახელით (სატესტო ნაკრების სახელზე გადასვლით) და ტესტის სახელით. ეს ცალ-ცალკე ინარჩუნებს იდენტური სახელების მქონე მეთოდებს სხვადასხვა კლასებში. უფრო ძველი ანგარიშები, რომლებიც იყენებდნენ განსხვავებულ შემომსაზღვრელ სატესტო ნაკრების სახელს, ინარჩუნებენ ისტორიას ძველი იდენტურობის ქვეშ; ძველ იდენტურობაზე გამოყენებული სტატუსის ცვლილებები უნდა გადაიტანოთ ახალზე, და ბრძანება გაფრთხილებთ, როდესაც შეცდომა ემთხვევა ძველ იდენტურობას, რათა იცოდეთ, რომელი პოლიტიკა გადაიტანოთ.

## CI კონტექსტის მიწოდება {#providing-ci-context}

Tuist კითხულობს git კომიტისა და შტოს ინფორმაციას Bazel-ის ბილდის მეტამონაცემებიდან, რათა იგივე კომიტზე შესრულებული გაშვებები შედარდეს სხვადასხვა გარემოში. უმეტესი უწყვეტი ინტეგრაციის სისტემები უკვე აყენებს ამას; როდესაც თქვენი არ აკეთებს, გადაეცით ისინი ცხადად:

```bash
tuist bazel test -- \
  --build_metadata=CI=true \
  --build_metadata=GIT_COMMIT="$GIT_COMMIT" \
  --build_metadata=GIT_BRANCH="$GIT_BRANCH" //app:tests
```

იგივე `--build_metadata` ფლაგია, რასაც <.localized_link href="/guides/features/build-insights/bazel#custom-metadata">Bazel-ის ბილდის ანალიტიკა</.localized_link> გვერდი აღწერს გამოძახებების მონიშვნისთვის, ასე რომ ერთი ფლაგების ნაკრები ორივე ზედაპირს ფარავს.

## არასტაბილური ტესტები და კარანტინი {#flaky-tests-and-quarantine}

გამეორებები, გაშვებებს შორის არასტაბილურობის აღმოჩენა და თითოეული შემთხვევის კარანტინი (ჩუმად და გამოტოვება) ყველა მუშაობს `tuist bazel test`-ის მეშვეობით. სრული სამუშაო პროცესისთვის იხილეთ <.localized_link href="/guides/features/test-insights/flaky-tests/bazel">Bazel-ის არასტაბილური ტესტები</.localized_link>.

## მონაცემთა შენახვა {#data-retention}

Tuist ინარჩუნებს Bazel-ის გამოძახებას, რომელმაც წარმოქმნა ტესტების გაშვება, მის ჟურნალებს და მოლოდინში მყოფ ტესტების მიღების ჩანაწერებს 90 დღის განმავლობაში. სატესტო შემთხვევები და მათი გაშვების ისტორია იყენებენ იგივე მოდელს, რასაც ყველა სხვა ბილდის სისტემა, და არ ექვემდებარებიან ამ ვადას. სრული პოლიტიკისთვის იხილეთ <.localized_link href="/guides/server/data-retention">მონაცემთა შენახვა</.localized_link>.
