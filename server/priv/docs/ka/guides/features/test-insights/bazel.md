# Bazel ტესტების ანალიტიკა {#bazel-test-insights}

გაუშვით Bazel ტესტები Tuist-ის საშუალებით, რათა შეავსოთ იგივე სატესტო დაფები, რომლებსაც სხვა ყველა ბილდის სისტემა იყენებს:

```bash
tuist bazel test -- //app:tests
```

არგუმენტები `--`-ის შემდეგ გადაეცემა `bazel test`-ს. გამოიყენეთ `--path` პროექტისა და სამუშაო დირექტორიის არჩევასთვის და `--bazel` სხვა შესრულებადი ფაილის, მაგალითად `bazelisk`-ის, არჩევასთვის. ჩვეულებრივი `bazel test` კვლავ აჩვენებს ტესტების შედეგებს, მაგრამ არ იღებს და არ აღასრულებს Tuist-ის კარანტინის პოლიტიკებს.

> [!NOTE]
> `tuist bazel test` გარსაცმი მხოლოდ <.localized_link href="/guides/features/test-insights/flaky-tests/bazel">კარანტინში მოქცეული ტესტებისთვის</.localized_link>აა საჭირო. ცალკეულ სატესტო შემთხვევებზე ანგარიშგება ჩვეულებრივი ტესტების გაშვებისთვის კონფიგურირებულია `tuist bazel setup`-ით `.bazelrc.tuist`-ში, ამიტომ ჩვეულებრივი `bazel test` ასევე აჩვენებს ინდივიდუალურ შემთხვევებს.

## რა ფიქსირდება {#what-is-tracked}

Tuist ამუშავებს `test.xml` ანგარიშებს და იღებს `test.log` გამოტანას, რომელსაც Bazel ქმნის თითოეული სატესტო მიზნისთვის, შემდეგ კი აერთიანებს მათ საერთო ტესტების გაშვების მოდელში. თითოეული გაშვება იწერს:

- ინდივიდუალური სატესტო შემთხვევის წარმატების, შეცდომის და გამოტოვების სტატუსს ხანგრძლივობასთან ერთად.
- სატესტო მიზნის, კლასისა და საიტის სტრუქტურას.
- განმეორებითი ცდები, როდესაც Bazel კონფიგურირებულია არასტაბილური ტესტების განმეორებითი გაშვებისთვის.
- შეცდომის გამოტანა, აღებული მიზნის `test.log`-დან.

**ტესტების გაშვებები**, **სატესტო შემთხვევები** და ინდივიდუალური ტესტების გვერდები Bazel-ისთვის ისევე მუშაობს, როგორც სხვა ბილდის სისტემებისთვის.

## ცალკეულ შემთხვევებზე JUnit ანგარიშების გენერირება {#per-case-junit-reports}

ცალკეულ შემთხვევებზე სტრიქონები დამოკიდებულია იმაზე, რომ სატესტო მიზანი წერდეს JUnit `test.xml`-ს `$XML_OUTPUT_FILE` გზაზე, რომელსაც Bazel უზრუნველყოფს. როდესაც გამშვები არ წერს მას, Bazel გადადის სინთეზურ ერთ-შემთხვევიან ანგარიშზე, რომელიც სახელდება მიზნის მიხედვით, და Tuist აჩვენებს ერთ სტრიქონს თითოეული მიზნისთვის (მონიშნული როგორც **Bazel მიზანი** სატესტო შემთხვევების სიაში), სადაც ნედლი `test.log` კვლავ ხელმისაწვდომია გაშვების გვერდზე.

Bazel-ის უმეტესი სატესტო წესები უკვე ქმნიან რეალურ `test.xml`-ს:

- `java_test` და `kt_jvm_test`: JUnit ჩაშენებულია.
- `cc_test` GoogleTest-ით: გამშვები წერს JUnit-ს, როდესაც კომპილირებულია ბოლო gtest-ის წინააღმდეგ; ძველი კონფიგურაციები საჭიროებენ `--gtest_output=xml:$XML_OUTPUT_FILE`-ს.
- `py_test`: გამოიყენეთ pytest `--junitxml=$XML_OUTPUT_FILE`-ით, ან `rules_python` pytest გამშვები.
- `go_test`: გაატარეთ `go test -json` `gotestsum --junitfile=$XML_OUTPUT_FILE`-ში, ან შეფუთეთ დამხმარე საშუალებით, რომელიც გამოიმუშავებს JUnit-ს.

`rust_test` `rules_rust`-დან და `rules_rs`-დან აწარმოებს სტანდარტულ `libtest` harness-ს, რომელიც არ წერს JUnit-ს სტაბილურ Rust-ზე. შეფუთეთ სატესტო მიზანი სკრიპტით, რომელიც ამუშავებს `libtest` გამოტანას და წერს JUnit-ს `$XML_OUTPUT_FILE`-ში; თქვენ ინარჩუნებთ ცალკეულ შემთხვევებზე სტრიქონებს Tuist-ში და იგივე გაშვება რჩება ერთ Bazel სატესტო მიზნად.

## ტესტის იდენტურობა {#test-identity}

შემთხვევები იდენტიფიცირდება მიზნის ლეიბლით, კლასის სახელით (საიტის სახელზე დაბრუნებით) და ტესტის სახელით. ეს ინარჩუნებს იდენტური სახელის მქონე მეთოდებს სხვადასხვა კლასებში ცალკე. ძველ ანგარიშებს, რომლებიც იყენებდნენ განსხვავებულ შემომსაზღვრელ საიტის სახელს, აქვთ ისტორია ძველი იდენტურობის ქვეშ; ძველ იდენტურობაზე გამოყენებული სტატუსის ცვლილებები უნდა განახლდეს ახალზე, და ბრძანება გაფრთხილებთ, როდესაც შეცდომა ემთხვევა ძველ იდენტურობას, რათა იცოდეთ, რომელი პოლიტიკა გადაიტანოთ.

## CI კონტექსტის მიწოდება {#providing-ci-context}

Tuist კითხულობს git კომიტისა და შტოს ინფორმაციას Bazel-ის ბილდის მეტამონაცემებიდან, რათა იგივე კომიტზე გაშვებები შედარდეს გარემოებს შორის. უმეტესი უწყვეტი ინტეგრაციის სისტემები უკვე აყენებს ამას; როდესაც თქვენი არ აკეთებს, გადაეცით ისინი ცალსახად:

```bash
tuist bazel test -- \
  --build_metadata=CI=true \
  --build_metadata=GIT_COMMIT="$GIT_COMMIT" \
  --build_metadata=GIT_BRANCH="$GIT_BRANCH" //app:tests
```

იგივე `--build_metadata` ფლაგია, რასაც <.localized_link href="/guides/features/build-insights/bazel#custom-metadata">Bazel ბილდის ანალიტიკის</.localized_link> გვერდი აღწერს გამოძახებების მონიშვნისთვის, ამიტომ ფლაგების ერთი ნაკრები ფარავს ორივე ზედაპირს.

## არასტაბილური ტესტები და კარანტინი {#flaky-tests-and-quarantine}

განმეორებითი ცდები, გაშვებებს შორის არასტაბილურობის აღმოჩენა და ცალკეულ შემთხვევებზე კარანტინი (Mute და Skip) ყველა მუშაობს `tuist bazel test`-ის საშუალებით. სრული სამუშაო პროცესისთვის იხილეთ <.localized_link href="/guides/features/test-insights/flaky-tests/bazel">Bazel არასტაბილური ტესტები</.localized_link>.

## მონაცემთა შენახვა {#data-retention}

Tuist ინარჩუნებს Bazel-ის გამოძახებას, რომელმაც წარმოქმნა ტესტების გაშვება, მის ჟურნალებს და მოლოდინში მყოფ ტესტების მიღების ჩანაწერებს 90 დღის განმავლობაში. სატესტო შემთხვევები და მათი გაშვების ისტორია იყენებენ იგივე მოდელს, რასაც სხვა ყველა ბილდის სისტემა და არ ექვემდებარებიან ამ ვადას. სრული პოლიტიკისთვის იხილეთ <.localized_link href="/guides/server/data-retention">მონაცემთა შენახვა</.localized_link>.
