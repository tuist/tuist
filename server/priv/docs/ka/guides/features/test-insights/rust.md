# Rust-ის ტესტების ანალიტიკა {#rust-test-insights}

Tuist იუწყება ინდივიდუალურ ტესტების შედეგებს `cargo test`-დან, მათ შორის ერთეულოვანი ტესტები, ინტეგრაციული ტესტები და doctests. არ არის საჭირო Rust-ის დამატებითი დამოკიდებულება ან სხვა ტესტების გამშვები.

> [!IMPORTANT]
> **მოთხოვნები**
>
> - მიჰყევით <.localized_link href="/guides/get-started/rust-project">Rust პროექტის კონფიგურაციას</.localized_link>.

## შეიტანეთ თქვენი ტესტების გაშვების შესახებ ინფორმაცია {#report-your-test-runs}

```sh
tuist cargo test --workspace
```

mise Cargo wrapper-ის კონფიგურაციის შემთხვევაში, შეგიძლიათ განაგრძოთ `cargo test`-ის აკრეფა. Cargo კვლავ ახდენს თქვენი ტესტების კომპილაციას და გაშვებას ჩვეული არგუმენტებით, გამოტანით და გასვლის კოდით. შეტყობინებების წარუმატებლობა არ ცვლის თქვენი ტესტების შედეგს.

შეგიძლიათ აირჩიოთ პაკეტი ან გაფილტროთ ტესტები ჩვეულებრივად:

```sh
tuist cargo test -p store
tuist cargo test authentication
```

## რა აღრიცხავს Tuist {#what-is-tracked}

- წარმატებული, წარუმატებელი და იგნორირებული ტესტები დასრულებული ტესტების ნაკრებიდან.
- ერთეულოვანი ტესტები, ინტეგრაციული ტესტები და doctests.
- მთლიანი ნაკრების ხანგრძლივობა.
- ხელმისაწვდომი მეტამონაცემები ბრენჩის, კომიტის, CI-ის და გამშვების შესახებ.

გაფილტრული ტესტები და ტესტები, რომლებიც არ შესრულდა წარუმატებლობის შემდეგ, არასდროს იუწყება როგორც წარმატებული. შედეგები ჩანს დაფაზე \*\***Tests**\*\* განყოფილებაში.

## უწყვეტი ინტეგრაცია {#continuous-integration}

Tuist ცნობს GitHub Actions-ს, GitLab CI-ს, Bitrise-ს, CircleCI-ს, Buildkite-ს და Codemagic-ს, და აკავშირებს თითოეულ გაშვებას მის CI სამუშაოსთან. ნებისმიერ სხვა CI სისტემაში, გაშვება ითვლება CI გაშვებად, როდესაც `CI` გარემოს ცვლადი დაყენებულია. უმეტესი CI სისტემები აყენებენ მას; თავად დააყენეთ ის იქ, სადაც ისინი არ აყენებენ, მაგალითად Fly.io Machines-ზე. არასტაბილური ტესტების აღმოჩენა მხოლოდ CI გაშვებებს ადარებს ერთმანეთს.

სამუშაო, რომელიც ამოწმებს კომიტს ბრენჩის ნაცვლად, ტოვებს Git-ს ბრენჩის სახელის გარეშე, ამიტომ მის გაშვებებს არ აქვთ ბრენჩი. Tuist-ის მიერ ცნობილ CI სისტემებში, ბრენჩი მოდის პროვაიდერისგან. სხვაგან, მიანიჭეთ მას სახელი `TUIST_GIT_BRANCH`-ით:

```sh
CI=true TUIST_GIT_BRANCH=main tuist cargo test --workspace
```

## პაკეტები, მოდულები და ტესტების შემთხვევები {#test-hierarchy}

Tuist აჯგუფებს შედეგებს Cargo პაკეტისა და სამიზნის მიხედვით. Rust-ის მოდულის გზები აჯგუფებენ ინდივიდუალურ ტესტებს სამიზნის ფარგლებში:

| დაფის ეტიკეტი | Rust-ის მნიშვნელობა | მაგალითი |
| --- | --- | --- |
| მოდულები | Cargo პაკეტი და სამიზნე | `store::api` |
| ტესტების ნაკრებები | Rust-ის მოდულის გზები | `api::authentication` |
| ტესტების შემთხვევები | ინდივიდუალური ტესტები | `rejects_invalid_token` |

Doctests იყენებენ ცალკეულ მოდულს, როგორიცაა `store::doctest/store`. მათი სახელები შეიცავს წყაროს მდებარეობას, ამიტომ მაგალითის გადატანამ შეიძლება შეცვალოს მისი იდენტურობა.

## Doctests და ხანგრძლივობა {#cargo-test}

Doctests იშვება თქვენი ჩვეულებრივი ტესტების ბრძანებით, მათ შორის `compile_fail`, `should_panic` და `no_run` მაგალითებით. მხოლოდ doctests-ის გასაშვებად:

```sh
tuist cargo test --doc
```

Stable libtest იუწყება მთლიანი ნაკრების დროს, მაგრამ არა ინდივიდუალური ტესტების ხანგრძლივობას. მიუწვდომელი დროის ნიშნულები გამორიცხულია თითოეული შემთხვევის ხანგრძლივობის ისტორიიდან და ანალიტიკიდან, ხოლო ტესტების შედეგები კვლავ მონაწილეობენ საიმედოობისა და გაშვებების რაოდენობის აღრიცხვაში.

## შეტყობინებების ლიმიტები {#reporting-limits}

ინდივიდუალური შედეგები იკრიბება Cargo/libtest-ის ნაგულისხმევი გამოტანიდან. ბრძანებები, რომლებიც იყენებენ `--no-run`, `--list`, ჩუმ ან Cargo-verbose გამოტანას, ალტერნატიულ ფორმატებს ან დაუჭერელ ტესტების გამოტანას, ჩვეულებრივად იშვებიან ინდივიდუალური ტესტების შეტყობინების გარეშე. მორგებული harness-ები, არასრული შეჯამებები, ორაზროვანი სამიზნის მიკუთვნება და ზედმეტად დიდი ანგარიშები არ იტვირთება.

თუ workspace პაკეტებს აქვთ იდენტურად სახელდარქმეული ინტეგრაციული სამიზნეები, აირჩიეთ ერთ-ერთი `-p <package>`-ით. შეტყობინებები მხარდაჭერილია ზუსტი workspace პაკეტის სახელებისთვის; დამოკიდებულების პაკეტები, ვერსიით კვალიფიცირებული სელექტორები და globs ჩვეულებრივად სრულდება, მაგრამ არ იუწყება. აბსოლუტური doctest გზები გამოტოვებულია, რათა checkout გზები არ მოხვდეს ტესტების იდენტურობაში.

Tuist აწვდის გამოტანას შედეგების შეგროვებისას. ეს შეიძლება გავლენა იქონიოს ავტომატურ ფერების აღმოჩენაზე. ფონური პროცესები, რომლებიც ტოვებენ გამოტანის მილებს გახსნილს Cargo-ს გასვლის შემდეგ, შეიძლება გამოიწვიონ ანგარიშის გამოტოვება, მაგრამ არ ცვლიან Cargo-ს გასვლის სტატუსს.

## საიმედოობა და შერჩევა {#reliability-and-selection}

გამოიყენეთ <.localized_link href="/guides/features/test-insights/flaky-tests/rust">არასტაბილური ტესტების აღმოჩენა და კარანტინი</.localized_link> არასტაბილური ტესტების შესასწავლად და მათ დასაჩუმებლად ან გამოტოვებისთვის. <.localized_link href="/guides/features/test-sharding/rust">ტესტების დაშლა</.localized_link> ანაწილებს მთლიან Cargo სამიზნეებს CI მუშაკებზე. ჩართეთ <.localized_link href="/guides/features/test-code-coverage/rust">კოდის დაფარვა</.localized_link>, რათა მიჰყვეთ თქვენი ტესტების გაშვებების ხაზოვან დაფარვას. დაფარვაზე დაფუძნებული ტესტების შერჩევა და ერთხელ აგებული განაწილება არ არის ხელმისაწვდომი ჩვეულებრივი Cargo ტესტების გაშვებებისთვის.

## პრობლემების მოგვარება {#troubleshooting}

თუ ტესტების გაშვება არ ჩანს დაფაზე, ჩართეთ debug გამოტანა, რათა ნახოთ, რატომ არ გაიგზავნა მისი ანგარიში:

```sh
TUIST_DEBUG=1 tuist cargo test --workspace
```
