# Gradle-ის ტესტების ანალიტიკა {#gradle-test-insights}

> [!IMPORTANT]
> **მოთხოვნები**
>
> - გამოყენებულია `dev.tuist` Gradle პლაგინი, როგორც აღწერილია <.localized_link href="/guides/get-started/gradle-project">დაიწყეთ Gradle პროექტით</.localized_link>.

Tuist-ის Gradle პლაგინი ავტომატურად ატვირთავს ტესტების შედეგებს ყოველი სატესტო ამოცანის შესრულების შემდეგ, რაც საშუალებას გაძლევთ პირდაპირ Tuist დაფზე ნახოთ ტესტების წარმადობა და არასტაბილური ტესტები.

ტესტების ანალიტიკა ავტომატურად იკრიბება პლაგინის გამოყენებისთანავე. დამატებითი კონფიგურაცია არ არის საჭირო.

შეგიძლიათ მიუწვდეთ თქვენს ტესტების ანალიტიკას Tuist დაფზე და ნახოთ, როგორ იცვლება ის დროთა განმავლობაში:

![დაფა ტესტების ანალიტიკით](/images/guides/features/build-insights/tests-dashboard.png)

## რა ფიქსირდება {#what-is-tracked}

პლაგინი აგროვებს შედეგებს ყველა Gradle `Test` ამოცანიდან, მათ შორის:
- ცალკეული სატესტო შემთხვევის წარმატების/შეცდომის სტატუსი და ხანგრძლივობა
- სატესტო ნაკრებისა და კლასის სტრუქტურა
- არასტაბილური ტესტების აღმოჩენა გაშვებებს შორის

ჩართეთ <.localized_link href="/guides/features/test-code-coverage/gradle">კოდის დაფარვა</.localized_link>, რათა ასევე აიტვირთოს ინფორმაცია იმ კოდის შესახებ, რომელიც თქვენმა ტესტებმა შეასრულეს.

## ატვირთვის ქცევის კონფიგურაცია {#configure-upload-behavior}

ნაგულისხმევად:
- ტესტების შედეგები აიტვირთება ფონურ რეჟიმში ლოკალური ბილდებისთვის.
- ტესტების შედეგები აიტვირთება წინა პლანზე CI გაშვებებისთვის, რათა თავიდან აიცილოთ ტელემეტრიის დაკარგვა მოკლე სიცოცხლის მქონე აგენტებზე.

შეგიძლიათ გადაწეროთ ეს ქცევა `uploadInBackground`-ის გამოყენებით `tuist` ბლოკში თქვენს `settings.gradle.kts`-ში:

```kotlin
tuist {
    uploadInBackground = false // always upload in the foreground
}
```

### Git-ის ისტორია {#git-history}

CI-ზე პლაგინი ასევე ატვირთავს checkout-ის კომიტების ისტორიას, როდესაც იტყობინება ტესტების გაშვების შესახებ: კომიტების SHA-ები, მათი მშობლები, კომიტების თარიღები და დარტყმა, რომელზეც იყო გაშვება და მისი pull request-ის საბაზო დარტყმა. არ აიტვირთება ფაილების შინაარსი, კომიტების შეტყობინებები ან ავტორები. ეს არის ის, რაც ეუბნება Tuist-ს, რომელი კომიტები მოხვდა თქვენს საბაზო დარტყმაზე, მაგალითად ისინი, რომლებიც merge queue-მ შეამოწმა. პლაგინი კითხულობს ისტორიას, რომელიც checkout-ს უკვე აქვს, და როდესაც checkout-ს არ აქვს საბაზო დარტყმა, ითხოვს remote-დან მის უახლეს კომიტს (`git ls-remote`). კოდის დაფარვის გარეშე ის არ იღებს ისტორიას. კოდის დაფარვისას shallow checkout ღრმავდება, ფაილების შინაარსის გარეშე, რათა იპოვოს, საიდან გაიყო pull request და მიაღწიოს კომიტებს, რომლებიც Tuist-ს უკვე აქვს, ისე, რომ კომიტი არასდროს აიტვირთება მშობლის გარეშე, რომელზეც ის ეყრდნობა.

| ცვლადი | ეფექტი |
| --- | --- |
| `TUIST_GIT_UPLOAD_ENABLED=false` | არ კითხულობს და არ ატვირთავს Git-ის რაიმე ისტორიას. |
| `TUIST_GIT_UNSHALLOW_ENABLED=false` | კითხულობს მხოლოდ checkout-ს, remote-თან დაკავშირების გარეშე. |
