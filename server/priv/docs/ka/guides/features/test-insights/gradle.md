# Gradle ტესტების ანალიტიკა {#gradle-test-insights}

> [!IMPORTANT]
> **მოთხოვნები**
>
> - გამოყენებულია `dev.tuist` Gradle პლაგინი, როგორც აღწერილია <.localized_link href="/guides/get-started/gradle-project">დაწყება Gradle პროექტით</.localized_link>.

Tuist-ის Gradle პლაგინი ავტომატურად ატვირთავს ტესტების შედეგებს ყოველი ტესტის ამოცანის შესრულების შემდეგ, რაც საშუალებას გაძლევთ პირდაპირ Tuist დაფზე ნახოთ ტესტების წარმადობა და არასტაბილური ტესტები.

ტესტების ანალიტიკა ავტომატურად იკრიბება პლაგინის გამოყენების შემდეგ. დამატებითი კონფიგურაცია არ არის საჭირო.

შეგიძლიათ მიუწვდეთ თქვენს ტესტების ანალიტიკას Tuist დაფზე და ნახოთ, როგორ იცვლება ის დროთა განმავლობაში:

![დაფა ტესტების ანალიტიკით](/images/guides/features/build-insights/tests-dashboard.png)

## რა ფიქსირდება {#what-is-tracked}

პლაგინი აგროვებს შედეგებს ყველა Gradle `Test` ამოცანიდან, მათ შორის:
- ინდივიდუალური სატესტო შემთხვევის წარმატებული/ჩავარდნილი სტატუსი და ხანგრძლივობა
- ტესტების ნაკრებისა და კლასის სტრუქტურა
- არასტაბილური ტესტების გამოვლენა გაშვებების მიხედვით

ჩართეთ <.localized_link href="/guides/features/test-code-coverage/gradle">კოდის დაფარვა</.localized_link>, რათა ასევე აიტვირთოს, რომელი კოდი შეასრულეს თქვენმა ტესტებმა.

## ატვირთვის ქცევის კონფიგურაცია {#configure-upload-behavior}

ნაგულისხმევად:
- ტესტების შედეგები აიტვირთება ფონურად ლოკალური ბილდებისთვის.
- ტესტების შედეგები აიტვირთება წინა პლანზე CI გაშვებებისთვის, რათა თავიდან აიცილოთ ტელემეტრიის დაკარგვა მოკლე სიცოცხლის მქონე აგენტებზე.

შეგიძლიათ გადაწეროთ ეს ქცევა `uploadInBackground`-ის გამოყენებით `tuist` ბლოკში თქვენს `settings.gradle.kts`-ში:

```kotlin
tuist {
    uploadInBackground = false // always upload in the foreground
}
```

### Git ისტორია {#git-history}

CI-ზე პლაგინი ასევე ატვირთავს ჩექაუთის კომიტების ისტორიას, როდესაც აცნობებს ტესტების გაშვების შესახებ: კომიტების SHA-ები, მათი მშობლები, კომიტების თარიღები და შტო, რომელზეც იყო გაშვება და მისი pull request-ის საბაზო შტო. არ აიტვირთება ფაილების შინაარსი, კომიტების შეტყობინებები ან ავტორები. ეს არის ის, რაც ეუბნება Tuist-ს, რომელი კომიტები მოხვდა თქვენს საბაზო შტოზე, მაგალითად, ისინი, რომლებიც merge queue-მ შეამოწმა. პლაგინი კითხულობს ისტორიას, რომელიც უკვე აქვს ჩექაუთს, და როდესაც ჩექაუთს არ აქვს საბაზო შტო, ითხოვს remote-დან მის უახლეს კომიტს (`git ls-remote`). კოდის დაფარვის გარეშე ისტორიას არ იღებს. კოდის დაფარვისას ზედაპირული ჩექაუთი ღრმავდება, ფაილების შინაარსის გარეშე, რათა იპოვოს, სად განშტოვდა pull request და მიაღწიოს იმ კომიტებს, რომლებიც Tuist-ს უკვე აქვს, ასე რომ კომიტი არასდროს აიტვირთება მშობლის გარეშე, რომელზეც დგას.

| ცვლადი | ეფექტი |
| --- | --- |
| `TUIST_GIT_UPLOAD_ENABLED=false` | არ კითხულობს და არ ატვირთავს Git-ის რაიმე ისტორიას. |
| `TUIST_GIT_UNSHALLOW_ENABLED=false` | კითხულობს მხოლოდ ჩექაუთს, remote-თან დაკავშირების გარეშე. |
| `TUIST_GIT_BRANCH=<branch>` | არქმევს გაშვების შტოს სახელს, CI პროვაიდერისა და ჩექაუთის წინ. დააყენეთ ის CI სისტემებზე, რომლებსაც Tuist არ ცნობს და რომლებიც შტოს ნაცვლად კომიტს იღებენ, რის გამოც მათ გაშვებებს ჩვეულებრივ შტო არ აქვთ. |
