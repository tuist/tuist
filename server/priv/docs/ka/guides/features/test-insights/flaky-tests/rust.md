# Rust-ის არასტაბილური ტესტები {#rust-flaky-tests}

Tuist-ს შეუძლია აღმოაჩინოს Cargo-ს ტესტების შეუსაბამო შედეგები და დაგეხმაროთ მათ გამოკვლევაში **Tests → Flaky Tests**-ში.

> [!IMPORTANT] Requirements
> - კონფიგურაცია <.localized_link href="/guides/features/test-insights/rust">Rust Test Insights</.localized_link>.

## როგორ მუშაობს არასტაბილურობის აღმოჩენა {#how-it-works}

Tuist ადარებს CI გაშვებებს ერთსა და იმავე კომიტზე. ტესტი, რომელიც ერთ გაშვებაში წარმატებულია, ხოლო მეორეში — მარცხდება, შეიძლება მონიშნულ იქნას როგორც არასტაბილური.

ყველა გაშვება ანგარიშდება ჩვეულებრივი ბრძანებით:

```sh
tuist cargo test --workspace
```

Cargo ავტომატურად არ ცდის თავიდან მარცხებულ ტესტებს. CI სამუშაოს ხელახლა გაშვება იმავე კომიტზე უზრუნველყოფს დამატებით შედეგს გაშვებებს შორის აღმოჩენისთვის.

## არასტაბილური ტესტების მართვა {#managing-flaky-tests}

### ავტომატური გასუფთავება

აღმოჩენა და აღდგენა მიმდინარეობს პროექტის „Flaky test detection“ ავტომატიზაციის საშუალებით. ნაგულისხმევად, არასტაბილურობის ნიშანი იხსნება 14 დღის შემდეგ ხელახალი გამოწვევის გარეშე. შეცვალეთ აღდგენის პერიოდი და ქმედებები **Settings → Automations**-ში.

### ხელით მართვა

გახსენით **Tests → Flaky Tests** ტესტის ისტორიის შესასწავლად. შეგიძლიათ ხელით მონიშნოთ ან მოხსნათ მონიშვნა როგორც არასტაბილური მისი დეტალური გვერდიდან.

## კარანტინი და სტრეს-ტესტირება {#quarantine}

დააყუჩეთ ან გამოტოვეთ ტესტი მისი დეტალური გვერდიდან, ან კონფიგურაცია გააკეთეთ კარანტინისთვის **Settings → Automations**-ში. შემდეგი `tuist cargo test` იღებს პროექტის მიმდინარე კარანტინის მდგომარეობას:

- **დაყუჩებული** ტესტები მაინც გაეშვება და ანგარიშდება მათი რეალური შედეგები, მაგრამ მათი მარცხები არ აფერხებენ ბრძანებას. სხვა ტესტების მარცხები, კომპილაციის შეცდომები, კრახები და არასრული შედეგები მაინც იწვევენ ჩვეულებრივ მარცხს.
- **გამოტოვებული** ტესტები გამორიცხულია შესრულებიდან და ანგარიშდება როგორც კარანტინში მოქცეული გამოტოვებები. შესაბამისობა მოიცავს პაკეტს, სამიზნეს, Rust-ის მოდულის გზას და ტესტის სახელს, ამიტომ მსგავსად სახელდარქმეული ტესტები რჩებიან დამოუკიდებლები.

დაყუჩება ინარჩუნებს შერჩეულ workspace პაკეტებსა და ფუნქციებს და აწარმოებს ყველა შერჩეულ სამიზნეს მაშინაც კი, თუ დაყუჩებული სამიზნე მარცხდება. გამოტოვების კარანტინი მოითხოვს ერთ შერჩეულ პაკეტს: გამოიყენეთ `tuist cargo test -p store` მრავალპაკეტიანი workspace ბრძანების ნაცვლად. Tuist უარყოფს მრავალპაკეტიან გამოტოვებას, რადგან ბრძანების შევიწროვებამ შეიძლება შეცვალოს Cargo-ს გაერთიანებული დამოკიდებულების ფუნქციები.

კარანტინი ასევე ვრცელდება <.localized_link href="/guides/features/test-sharding/rust">sharded Cargo runs</.localized_link>-ზე. თუ Tuist ვერ იღებს მდგომარეობას, ის აფრთხილებს და აწარმოებს კარანტინის გარეშე; მარცხები არ ითრგუნება. განზრახ გასაშვებად კარანტინის გარეშე:

```sh
TUIST_TEST_SKIP_QUARANTINE=1 tuist cargo test --workspace
```

აღსრულება მოითხოვს სტანდარტულ libtest harness-ებს და დაჭერილ ნაგულისხმევ გამომავალ მონაცემებს. ბრძანებები ჩუმი, verbose, ალტერნატიული ფორმატის ან დაუჭერი გამომავალი მონაცემებით მარცხდება, როდესაც კარანტინის გამოყენებაა საჭირო. აირჩიეთ ზუსტი workspace პაკეტი `-p <package>`-ით, თუ სამიზნის მიკუთვნება ორაზროვანია. მორგებული harness-ები, პაკეტის/სამიზნის სახელის glob-ები და გადაუწყვეტელი პაკეტის შერჩევები მხარდაჭერილი არ არის. Doctest-ებიც შეიძლება დაყუჩდეს ან გამოიტოვოს, მაგრამ Rustdoc-ის ტესტის ფილტრაციას არ შეუძლია განასხვავოს ყოველი შესაძლო წყვილი მაგალითის სახელებისა. თუ მაგალითის გამოტოვება ასევე გამოტოვებდა ჩართულ მაგალითს, ან ნაწილობრივი doctest-ის გამორიცხვა იყენებს `--exact`, Tuist მარცხდება დიაგნოსტიკით ნაცვლად გამოტოვებული მაგალითის შესრულებისა ან ჩართული ტესტების ჩუმად გამოტოვებისა; გამოიყენეთ ზემოთ მოცემული გადაფარვა გამოკვლევისას.

Tuist არ აკეთებს სტრეს-ტესტირებას ახალი Cargo ტესტებისთვის. გამოიყენეთ Cargo ტესტის ფილტრი მარცხებული ტესტის გასამეორებლად მისი გამოკვლევისას:

```sh
tuist cargo test -p store rejects_invalid_token
```
