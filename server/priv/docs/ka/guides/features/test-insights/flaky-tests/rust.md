# Rust-ის არასტაბილური ტესტები {#rust-flaky-tests}

Tuist-ს შეუძლია აღმოაჩინოს Cargo-ს ტესტების შეუსაბამო შედეგები და დაგეხმაროთ მათ შესწავლაში **Tests → Flaky Tests**-ში.

> [!IMPORTANT] Requirements
> - დააკონფიგურირეთ <.localized_link href="/guides/features/test-insights/rust">Rust Test Insights</.localized_link>.

## როგორ მუშაობს არასტაბილურობის აღმოჩენა {#how-it-works}

Tuist ადარებს CI-ის გაშვებებს ერთსა და იმავე კომიტზე. ტესტი, რომელიც ერთ გაშვებაში გადის და მეორეში ვერ გადის, შეიძლება მონიშნულ იქნას როგორც არასტაბილური.

ყველა გაშვება დააფიქსირეთ ჩვეული ბრძანებით:

```sh
tuist cargo test --workspace
```

Cargo ავტომატურად არ ცდის თავიდან ჩავარდნილ ტესტებს. CI-ის სამუშაოს ხელახლა გაშვება იმავე კომიტზე იძლევა დამატებით შედეგს გაშვებებს შორის აღმოჩენისთვის.

## არასტაბილური ტესტების მართვა {#managing-flaky-tests}

### ავტომატური გასუფთავება

აღმოჩენა და აღდგენა მიმდინარეობს პროექტის „Flaky test detection“ ავტომატიზაციის მეშვეობით. ნაგულისხმევად, არასტაბილურობის ნიშანი იხსნება 14 დღის შემდეგ, თუ ხელახლა არ გამოვლინდა. შეცვალეთ აღდგენის პერიოდი და მოქმედებები **Settings → Automations**-ში.

### ხელით მართვა

გახსენით **Tests → Flaky Tests** ტესტის ისტორიის შესასწავლად. დეტალურ გვერდზე შეგიძლიათ ხელით მონიშნოთ ან მოხსნათ მონიშვნა როგორც არასტაბილური.

## კარანტინში გადაყვანა და სტრეს-ტესტირება {#quarantine}

დააყუჩეთ ან გამოტოვეთ ტესტი მისი დეტალური გვერდიდან, ან დააკონფიგურირეთ კარანტინი **Settings → Automations**-ში. შემდეგი `tuist cargo test` იღებს პროექტის მიმდინარე კარანტინის მდგომარეობას:

- **დაყუჩებული** ტესტები მაინც გაეშვება და აჩვენებს რეალურ შედეგებს, მაგრამ მათი ჩავარდნა არ აჩერებს ბრძანებას. სხვა ტესტების ჩავარდნები, კომპილაციის შეცდომები, კრახები და არასრული შედეგები კვლავ იწვევენ ჩავარდნას ჩვეულებრივად.
- **გამოტოვებული** ტესტები გამორიცხულია შესრულებიდან და მოხსენებულია როგორც კარანტინში გადაყვანილი გამოტოვებები. შესაბამისობა მოიცავს პაკეტს, target-ს, Rust-ის მოდულის გზას და ტესტის სახელს, ამიტომ მსგავსად სახელდარქმეული ტესტები დამოუკიდებელი რჩება.

დაყუჩება ინარჩუნებს შერჩეულ workspace-ის პაკეტებსა და ფუნქციებს და აწარმოებს ყველა შერჩეულ target-ს მაშინაც კი, თუ დაყუჩებული target ჩავარდება. გამოტოვების კარანტინი მოითხოვს ერთ შერჩეულ პაკეტს: გამოიყენეთ `tuist cargo test -p store` multi-package workspace-ის ბრძანების ნაცვლად. Tuist უარყოფს multi-package გამოტოვებას, რადგან ბრძანების შევიწროვებამ შეიძლება შეცვალოს Cargo-ს გაერთიანებული დამოკიდებულების ფუნქციები.

კარანტინი ასევე ვრცელდება <.localized_link href="/guides/features/test-sharding/rust">sharded Cargo runs</.localized_link>-ზე. თუ Tuist-ს არ შეუძლია მდგომარეობის მიღება, ის გასცემს გაფრთხილებას და აწარმოებს კარანტინის გარეშე; ჩავარდნები არ ითრგუნება. განზრახ გასაშვებად კარანტინის გარეშე:

```sh
TUIST_TEST_SKIP_QUARANTINE=1 tuist cargo test --workspace
```

აღსრულება მოითხოვს სტანდარტულ libtest harness-ებს და ჩაჭერილ ნაგულისხმევ output-ს. ბრძანებები quiet, verbose, ალტერნატიული ფორმატით ან არაჩაჭერილი output-ით ჩავარდება, როცა კარანტინის გამოყენებაა საჭირო. აირჩიეთ ზუსტი workspace პაკეტი `-p <package>`-ით, თუ target-ის მიკუთვნება ბუნდოვანია. მორგებული harness-ები, პაკეტის/target-ის სახელის glob-ები და გადაუწყვეტელი პაკეტის შერჩევები არ არის მხარდაჭერილი. Doctest-ების დაყუჩება ან გამოტოვებაც შესაძლებელია, მაგრამ Rustdoc-ის ტესტების ფილტრაციას არ შეუძლია ყველა შესაძლო წყვილის განსხვავება მაგალითების სახელებში. თუ მაგალითის გამოტოვება ასევე გამოტოვებდა ჩართულ მაგალითს, ან doctest-ის ნაწილობრივი გამორიცხვა იყენებს `--exact`, Tuist ჩავარდება დიაგნოსტიკით ჩართული მაგალითის ჩუმად გამოტოვების ან გამოტოვებული მაგალითის შესრულების ნაცვლად; გამოიყენეთ ზემოთ მოცემული გადაფარვა შესწავლისას.

Tuist არ ატარებს სტრეს-ტესტირებას ახალ Cargo ტესტებზე. გამოიყენეთ Cargo ტესტის ფილტრი ჩავარდნილი ტესტის გასამეორებლად მისი შესწავლისას:

```sh
tuist cargo test -p store rejects_invalid_token
```
