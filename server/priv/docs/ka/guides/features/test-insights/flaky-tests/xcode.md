# Xcode-ის არასტაბილური ტესტები {#xcode-flaky-tests}

> [!WARNING]
> **მოთხოვნები**
>
> - <.localized_link href="/guides/features/test-insights/xcode">Xcode-ის ტესტების ინსაიტები</.localized_link> კონფიგურირებული. Tuist ავლენს არასტაბილურ ტესტებს ყოველი ტესტების გაშვების მიერ ატვირთული ტესტ-ინსაიტის მოვლენებიდან.

არასტაბილური ტესტებია ისეთი ტესტები, რომლებიც ერთი და იმავე კოდით მრავალჯერადი გაშვებისას სხვადასხვა შედეგს (წარმატებას ან შეცდომას) იძლევიან. ისინი ასუსტებენ ნდობას თქვენი ტესტების ნაკრების მიმართ და ფლანგავენ დეველოპერების დროს ცრუ შეცდომების გამოკვლევაში. Tuist ავტომატურად ავლენს არასტაბილურ ტესტებს და გეხმარებათ მათ თვალყურის დევნაში დროთა განმავლობაში.

![არასტაბილური ტესტების გვერდი](/images/guides/features/test-insights/flaky-tests-page.png)

## როგორ მუშაობს არასტაბილურობის აღმოჩენა {#how-it-works}

Tuist ორი გზით ავლენს არასტაბილურ ტესტებს:

### ტესტების ხელახალი გაშვება {#test-retries}

როდესაც ტესტებს ხელახალი გაშვების ფუნქციონალით აშვებთ, Tuist აანალიზებს თითოეული მცდელობის შედეგებს. თუ ტესტი ზოგიერთ მცდელობაზე ვერდება, მაგრამ სხვებზე წარმატებით სრულდება, ის არასტაბილურად მონიშნება.

გაატარეთ `-retry-tests-on-failure` ან `-test-iterations` `tuist xcodebuild test`-ის საშუალებით:

```sh
tuist xcodebuild test \
  -scheme MyScheme \
  -retry-tests-on-failure \
  -test-iterations 3
```

![არასტაბილური სატესტო შემთხვევის დეტალები](/images/guides/features/test-insights/flaky-test-case-detail.png)

### გაშვებებს შორის აღმოჩენა {#cross-run-detection}

ტესტების ხელახალი გაშვების გარეშეც, Tuist-ს შეუძლია არასტაბილური ტესტების აღმოჩენა სხვადასხვა CI გაშვების შედეგების შედარებით ერთსა და იმავე კომიტზე, სქემაზე და მოხსენებულ დანიშნულებაზე (მოწყობილობის სახელი, პლატფორმა და OS ვერსია). თუ ტესტი ერთ შესაბამის CI გაშვებაში წარმატებით სრულდება, მაგრამ მეორეში ვერდება, ვერებული შესრულება არასტაბილურად მონიშნება. ეს მუშაობს მიუხედავად იმისა, რომელი შედეგი მოვა პირველად.

იგივე ტესტს შეიძლება თანმიმდევრულად განსხვავებულად მოიქცეს სხვადასხვა სქემასა თუ დანიშნულებაში. მაგალითად, iOS 26-ზე წარმატება და iOS 27-ზე ვერდება არ ამყარებს არასტაბილურობას. სხვადასხვა სქემებიდან, მოწყობილობებიდან, პლატფორმებიდან ან OS ვერსიებიდან მიღებული შედეგები ერთმანეთს არასტაბილურად არ მონიშნავენ.

შედეგები, რომლებსაც არ აქვთ მიკუთვნებადი დანიშნულება, შედარებულია სხვა მიუკუთვნებელ შედეგებთან, ცალკე ცნობილი დანიშნულების მქონე შედეგებისგან. ეს მოიცავს ანგარიშებს, რომლებშიც აკლია ან არასრულია დანიშნულების მეტამონაცემები, და ანგარიშებს, რომლებიც შეიცავს მრავალ განსხვავებულ დანიშნულებას, რადგან ინდივიდუალური ტესტის შედეგები ჯერ კიდევ ვერ მიეკუთვნება დანიშნულებას. ამ ჯგუფში გარემოებს შორის განსხვავებებმა შეიძლება მაინც გამოიწვიოს ცრუ არასტაბილურობის კლასიფიკაციები. ხელახალი გაშვებაზე დაფუძნებული აღმოჩენა მაინც მოქმედებს. არსებული ისტორიული არასტაბილურობის კლასიფიკაციები უცვლელია.

ეს განსაკუთრებით სასარგებლოა ისეთი არასტაბილური ტესტების დასაჭერად, რომლებიც არ ვერდებიან საკმარისად თანმიმდევრულად, რომ ხელახალი გაშვებით დაიჭირონ, მაგრამ მაინც იწვევენ პერიოდულ CI შეცდომებს.

## არასტაბილური ტესტების მართვა {#managing-flaky-tests}

### ავტომატური გასუფთავება

აღმოჩენა და გასუფთავება ხდება პროექტზე **ავტომატიზაციის გაფრთხილების** საშუალებით. ყოველ პროექტს აქვს ნაგულისხმევი „არასტაბილური ტესტის აღმოჩენის“ ავტომატიზაცია, რომლის *ტრიგერი* ტესტს არასტაბილურად მონიშნავს, ხოლო *აღდგენა* აშორებს ნიშანს, როდესაც ტესტი გაივლის კონფიგურირებულ აღდგენის ფანჯარას (ნაგულისხმევი **14 დღე**) ხელახალი ტრიგერის გარეშე. ჩაასწორეთ ის **პარამეტრები → ავტომატიზაციები**-ის ქვეშ, რათა შეცვალოთ აღდგენის ფანჯარა, შეცვალოთ აღდგენის მოქმედებები (მაგ., ასევე მოხსნა კარანტინიდან), ან სრულად გამორთოთ აღდგენა, რათა ტესტები დარჩნენ არასტაბილურად მონიშნული, სანამ ხელით არ გაასუფთავებთ.

### ხელით მართვა

ასევე შეგიძლიათ ხელით მონიშნოთ ან მოხსნათ ტესტები არასტაბილურად სატესტო შემთხვევის დეტალების გვერდიდან. ეს სასარგებლოა, როდესაც:
- გსურთ აღიაროთ ცნობილი არასტაბილური ტესტი შესწორებაზე მუშაობისას
- ტესტი არასწორად იყო მონიშნული ინფრასტრუქტურის პრობლემების გამო

## არასტაბილური ტესტების კარანტინში მოქცევა {#quarantining}

კარანტინი იზოლირებს არასტაბილურ ტესტს, რათა მან არ დაბლოკოს CI, სანამ მას შეასწორებთ. ნაგულისხმევად ეს არის **ხელით მოქმედება** — თქვენ ათავსებთ კარანტინში, ხსნით კარანტინიდან და ცვლით რეჟიმებს სატესტო შემთხვევის დეტალების გვერდიდან დაშბორდზე — მაგრამ ასევე შეგიძლიათ ჩართოთ ის **ავტომატიზაციის გაფრთხილებაში** **პარამეტრები → ავტომატიზაციები**-ის ქვეშ, რათა ტესტი ავტომატურად დადუმდეს (ან გამოიტოვოს), როდესაც გადალახავს არასტაბილურობის ზღვარს, და მოხსნილი იქნას კარანტინიდან, როდესაც აღდგება. ყოველი გადასვლა, ხელით თუ ავტომატური, იწერება სატესტო შემთხვევის აუდიტის ჟურნალში.

კარანტინში მოქცეული ტესტი არის ერთ-ერთ ორ რეჟიმში:

- **დადუმებული**: ტესტი მაინც ეშვება, მაგრამ `tuist xcodebuild test` ფარავს შეცდომას. შეცდომები მაინც კვებავს არასტაბილური ტესტების დეტექტორს, ასე რომ, შეგიძლიათ აკვირდეთ ტესტს ბილდის გაუფუჭებლად. აირჩიეთ ეს იმ ტესტისთვის, რომელსაც აქტიურად იკვლევთ.
- **გამოტოვებული**: xcodebuild იღებს `-skip-testing <identifier>`, ასე რომ, ტესტი საერთოდ არ იწყება. ის არ წარმოქმნის ახალ შედეგებს და ქრება არასტაბილური ტესტების დაშბორდიდან, სანამ ხელახლა არ ჩართავთ. აირჩიეთ ეს, როდესაც ტესტი გაფუჭებულია, ნელია, ან იმდენად მუდმივად არასტაბილური, რომ მისი გაშვება უბრალოდ ფლანგავს CI წუთებს.

### რატომ შეიძლება კარანტინში მოქცეული ტესტები გამოჩნდნენ როგორც წარმატებული {#quarantined-passing}

- **დადუმებული ტესტები** მაინც სრულდება. დადუმებული ტესტი, რომელიც ვერდება, იწერება როგორც **ვერებული** სატესტო შემთხვევის გაშვებაზე და მონიშნულია როგორც არასტაბილური — თითოეული ტესტის სტატუსი არ გადაიწერება. რაც გადაიფარება, არის **მთლიანი ტესტების გაშვება**: თუ გაშვებაში ყოველი ვერებული სატესტო შემთხვევა დადუმებულია, გაშვება მთლიანად ითვლება წარმატებულად, ასე რომ, დადუმებული შეცდომები არ ფუჭავენ CI-ს.
- **გამოტოვებული ტესტები** საერთოდ არ ეშვება, ასე რომ, დაშბორდი აჩვენებს სტატუსს ტესტის ბოლო რეალური შესრულებიდან — ეს სნეპშოტი შეიძლება კვირების ძველი იყოს.

### ტესტების გაშვება {#running-tests}

`tuist xcodebuild test` არის პასსრაუთ რაპი, რომელიც ავტომატურად ითვალისწინებს ორივე რეჟიმს. გამოიყენეთ ის ისევე, როგორც xcodebuild-ს გამოიძახებდით:

```sh
tuist xcodebuild test -scheme MyScheme
```

გამოტოვებული ტესტები ემატება თქვენს xcodebuild-ის გამოძახებას როგორც `-skip-testing <identifier>` და საერთოდ არ იწყება. დადუმებული ტესტები ჩვეულებრივად ეშვება; თუ ისინი ვერდებიან, შეცდომა ფარულია მიღებულ ბილდის სტატუსში.

#### კარანტინის გვერდის ავლა

`tuist xcodebuild test` იღებს `--skip-quarantine` ყველაფრის გასაშვებად, დადუმებული და გამოტოვებული ტესტების ჩათვლით:

```sh
tuist xcodebuild test --skip-quarantine -scheme MyScheme
```

#### xcodebuild-ის პირდაპირ გამოძახება

თუ ვერ გადიხართ `tuist xcodebuild test`-ის საშუალებით, თავად გააფართოვეთ კარანტინში მოქცეული ტესტები `-skip-testing` არგუმენტებად `tuist test case list`-ის საშუალებით:

```sh
xcodebuild test \
  -scheme MyScheme \
  $(tuist test case list --quarantined --skip-testing)
```

ეს არის უსაფრთხო ნაგულისხმევი `tuist xcodebuild test`-ის გარეთ: დადუმებული ტესტებისთვის შეცდომის დამალვა ხდება მხოლოდ მაშინ, როდესაც გადიხართ ამ ბრძანების საშუალებით, ასე რომ, ორივე რეჟიმის გამოტოვება თავიდან აიცილებს ცრუ CI შეცდომებს. თუ საჭიროებთ უფრო ზუსტ კონტროლს, გადით `tuist xcodebuild test`-ის საშუალებით.

## ახალი ტესტების სტრეს-ტესტირება {#stress-testing-new-tests}

სტრეს-გეიტი ხელახლა აშვებს სატესტო შემთხვევებს, რომლებიც თქვენმა ბრენჩმა დაამატა, თითოეულს რამდენჯერმე ახალ პროცესში, და აფიქსირებს იმას, რაც არასტაბილური აღმოჩნდება. ახალ არასტაბილურ ტესტს ხედავთ pull request-ზე, რომელმაც ის შემოიტანა, და არა კვირების შემდეგ.

სატესტო შემთხვევა ითვლება ახლად, თუ ის ბოლო 90 დღის განმავლობაში არ გაშვებულა CI-ში პროექტის ნაგულისხმევ ბრენჩზე, ან კომიტზე, რომელიც მას შემდეგ შევიდა ამ ბრენჩში. შერწყმის რიგის (merge queue) არსებობისას, რიგის მიერ გაშვებული სატესტო შემთხვევა ცნობილი ხდება მაშინ, როდესაც რიგის კომიტი შედის ბრენჩში, და რჩება ახლად, თუ რიგი მას გამოტოვებს. კომიტები ემთხვევა <.localized_link href="/guides/features/test-insights/xcode#git-history">Git-ის ისტორიის</.localized_link> საშუალებით, რომელსაც Tuist აგროვებს CI-ში.

### მისი ჩართვა

გეიტი ნაგულისხმევად გამორთულია. აირჩიეთ რეჟიმი:

- **`report`**: აფრთხილებს თითოეული არასტაბილური სატესტო შემთხვევის შესახებ. გაშვება მაინც სრულდება თავისი შედეგის მიხედვით.
- **`enforce`**: არასტაბილური სატესტო შემთხვევა აკრეხს გაშვებას, იმავე გასვლის კოდით, რაც ვერშესრულებულ ტესტს აქვს.

დაიწყეთ `report`-ით რამდენიმე კვირის განმავლობაში, რომ ნახოთ, რას დაბლოკავდა `enforce`.

გადაეცით ის პასსრაუთ არგუმენტებამდე, ან დააყენეთ `TUIST_TEST_STRESS_NEW_TESTS` რეჟიმის CI ლეინის მიხედვით შესაცვლელად:

```sh
tuist xcodebuild test --stress-new-tests report -scheme MyScheme
```

### რამდენჯერ მეორდება თითოეული ტესტი

ეს დამოკიდებულია იმაზე, თუ რამდენი დრო დასჭირდა სატესტო შემთხვევას პირველ გაშვებაზე:

| პირველი გაშვება | განმეორებითი გაშვებები |
| --- | --- |
| 5 წმ-მდე | 10 |
| 10 წმ-მდე | 5 |
| 30 წმ-მდე | 3 |
| 5 წთ-მდე | 2 |
| 5 წთ-ზე მეტი | არ მეორდება |

განმეორებითი გაშვებები იყენებენ იმას, რაც პირველმა გაშვებამ ააგო. გაშვება ჩერდება 200 სატესტო შემთხვევაზე ან 10 წუთზე, იმის მიხედვით, რომელიც უფრო ადრე დადგება, და მიუთითებს, რომელ ზღვარს მიაღწია.

### როდესაც გეიტი არ მუშაობს

- პირველი გაშვება უკვე ვერშესრულდა. ჯერ ეს ტესტები გაასწორეთ.
- პროექტს არ აქვს ნაგულისხმევი ბრენჩი, ან მასზე ჯერ არაფერი გაშვებულა CI-ში.
- პროექტის სატესტო შემთხვევების 30%-ზე მეტი ახლად ჩანს. ამდენის განმეორებითი გაშვება უფრო მეტ დროს წაიღებდა, ვიდრე ღირს. ეს მოსალოდნელია პროექტზე, რომელიც ახლახანს დაიწყო Tuist-თან რეპორტირება, ან გადასახელების შემდეგ, რამაც ბევრი ტესტი ერთდროულად გადაიტანა.

## არასტაბილური და კარანტინში მოქცეული მდგომარეობის კითხვა {#querying}

### CLI

`tuist test case` ბრძანებების ხე ხელმისაწვდომს ხდის ყველაფერს, რასაც Tuist აკონტროლებს სატესტო შემთხვევის შესახებ:

```sh
tuist test case list --flaky                       # only flaky test cases
tuist test case list --quarantined                 # only muted or skipped test cases
tuist test case show <test_case_id>                # detail: flakiness rate, last status, run counts
tuist test case events <test_case_id>              # audit log: marked_flaky, muted, skipped, ...
tuist test case run list <test_case_id>            # run history with status and duration
tuist test case run show <test_case_run_id>        # single run, including failure breakdown
```

ყველა ეს იღებს `--json`-ს სკრიპტინგისთვის.

### REST API

იგივე მონაცემები ხელმისაწვდომია HTTP-ით — იხილეთ [სატესტო შემთხვევების endpoint-ები](https://tuist.dev/api/docs#tag/test-cases) API ცნობარში მარშრუტების, ფილტრების და პასუხის ველების სრული სიისთვის. სატესტო შემთხვევის მდგომარეობის შესაცვლელად (არასტაბილურად მონიშვნა ან მოხსნა, დადუმება, გამოტოვება), გაგზავნეთ `PATCH /api/projects/{account_handle}/{project_handle}/tests/test-cases/{test_case_id}` `is_flaky` ან `state`-ით. იგივე ცვლილება ხელმისაწვდომია როგორც `tuist test case update` და როგორც `update_test_case` Model Context Protocol ინსტრუმენტი.
