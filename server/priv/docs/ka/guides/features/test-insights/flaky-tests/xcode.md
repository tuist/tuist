# Xcode-ის არასტაბილური ტესტები {#xcode-flaky-tests}

> [!WARNING]
> **მოთხოვნები**
>
> - <.localized_link href="/guides/features/test-insights/xcode">Xcode-ის ტესტების ანალიზი</.localized_link> კონფიგურირებული. Tuist აღმოაჩენს არასტაბილურ ტესტებს ყოველი ტესტების გაშვების მიერ ატვირთული ტესტის ინსაიტების მოვლენებიდან.

არასტაბილური ტესტები არის ტესტები, რომლებიც ერთი და იგივე კოდით რამდენჯერმე გაშვებისას სხვადასხვა შედეგს (წარმატება ან ჩავარდნა) იძლევიან. ისინი ასუსტებენ ნდობას თქვენს სატესტო ნაკრებში და კარგავენ დეველოპერის დროს ცრუ ჩავარდნების გამოკვლევაში. Tuist ავტომატურად აღმოაჩენს არასტაბილურ ტესტებს და გეხმარებათ მათ თვალყურის დევნაში დროთა განმავლობაში.

![არასტაბილური ტესტების გვერდი](/images/guides/features/test-insights/flaky-tests-page.png)

## როგორ მუშაობს არასტაბილურობის აღმოჩენა {#how-it-works}

Tuist აღმოაჩენს არასტაბილურ ტესტებს ორი გზით:

### ტესტების ხელახლა გაშვება {#test-retries}

როდესაც ტესტებს ხელახლა გაშვების ფუნქციით აწარმოებთ, Tuist აანალიზებს თითოეული მცდელობის შედეგებს. თუ ტესტი ზოგიერთ მცდელობაზე ჩავარდება, მაგრამ სხვებზე წარმატებით შესრულდება, ის არასტაბილურად ინიშნება.

გაატარეთ `-retry-tests-on-failure` ან `-test-iterations` `tuist xcodebuild test`-ის მეშვეობით:

```sh
tuist xcodebuild test \
  -scheme MyScheme \
  -retry-tests-on-failure \
  -test-iterations 3
```

![არასტაბილური სატესტო შემთხვევის დეტალები](/images/guides/features/test-insights/flaky-test-case-detail.png)

### ჯვარედინი გაშვებების აღმოჩენა {#cross-run-detection}

ტესტების ხელახლა გაშვების გარეშეც, Tuist-ს შეუძლია აღმოაჩინოს არასტაბილური ტესტები სხვადასხვა CI გაშვების შედეგების შედარებით ერთსა და იმავე კომიტზე, სქემაზე და მითითებულ დანიშნულებაზე (მოწყობილობის სახელი, პლატფორმა და OS ვერსია). თუ ტესტი ერთ შესაბამის CI გაშვებაში წარმატებით სრულდება, მაგრამ მეორეში ჩავარდება, ჩავარდნილი შესრულება არასტაბილურად ინიშნება. ეს მუშაობს მიუხედავად იმისა, რომელი შედეგი მოვა პირველი.

იგივე ტესტს შეუძლია თანმიმდევრულად განსხვავებულად მოიქცეს სხვადასხვა სქემასა თუ დანიშნულებაზე. მაგალითად, iOS 26-ზე წარმატება და iOS 27-ზე ჩავარდნა არასტაბილურობას არ ამტკიცებს. სხვადასხვა სქემებიდან, მოწყობილობებიდან, პლატფორმებიდან ან OS ვერსიებიდან მიღებული შედეგები ერთმანეთს არასტაბილურად არ ნიშნავენ.

შედეგები მიკუთვნებადი დანიშნულების გარეშე შედარდება სხვა მიუკუთვნებელ შედეგებთან, ცალკე ცნობილი დანიშნულების მქონე შედეგებისგან. ეს მოიცავს ანგარიშებს დაკარგული ან არასრული დანიშნულების მეტამონაცემებით და ანგარიშებს რამდენიმე განსხვავებული დანიშნულებით, რადგან ინდივიდუალური ტესტის შედეგები ჯერ კიდევ ვერ მიეკუთვნება კონკრეტულ დანიშნულებას. ამ ჯგუფში გარემოებს შორის განსხვავებებმა შეიძლება მაინც გამოიწვიოს ცრუ არასტაბილური კლასიფიკაციები. ხელახლა გაშვებაზე დაფუძნებული აღმოჩენა კვლავ მოქმედებს. არსებული ისტორიული არასტაბილური კლასიფიკაციები უცვლელი რჩება.

ეს განსაკუთრებით სასარგებლოა ისეთი არასტაბილური ტესტების დასაჭერად, რომლებიც საკმარისად თანმიმდევრულად არ ჩავარდებიან, რომ ხელახლა გაშვებამ დაიჭიროს, მაგრამ მაინც იწვევენ პერიოდულ CI ჩავარდნებს.

## არასტაბილური ტესტების მართვა {#managing-flaky-tests}

### ავტომატური გასუფთავება

აღმოჩენა და გასუფთავება მუშაობს პროექტზე **ავტომატიზაციის გაფრთხილების** მეშვეობით. ყოველ პროექტს აქვს ნაგულისხმევი „არასტაბილური ტესტების აღმოჩენის“ ავტომატიზაცია, რომლის *ტრიგერი* ტესტს არასტაბილურად ნიშნავს, ხოლო *აღდგენა* ასუფთავებს ნიშანს, როდესაც ტესტი გაივლის კონფიგურირებულ აღდგენის ფანჯარას (ნაგულისხმევი **14 დღე**) ხელახლა ტრიგერის გარეშე. შეცვალეთ ის **პარამეტრები → ავტომატიზაციები**-ში, რათა შეცვალოთ აღდგენის ფანჯარა, შეცვალოთ აღდგენის ქმედებები (მაგ., ასევე მოხსნათ კარანტინი) ან სრულად გამორთოთ აღდგენა, რათა ტესტები დარჩნენ არასტაბილურად მონიშნული, სანამ ხელით არ გაასუფთავებთ.

### ხელით მართვა

ასევე შეგიძლიათ ხელით მონიშნოთ ან მოხსნათ ტესტები არასტაბილურად სატესტო შემთხვევის დეტალების გვერდიდან. ეს სასარგებლოა, როდესაც:
- გსურთ აღიაროთ ცნობილი არასტაბილური ტესტი, სანამ მუშაობთ შესწორებაზე
- ტესტი არასწორად იყო მონიშნული ინფრასტრუქტურის პრობლემების გამო

## არასტაბილური ტესტების კარანტინში მოქცევა {#quarantining}

კარანტინი იზოლირებს არასტაბილურ ტესტს, რათა მან არ დაბლოკოს CI, სანამ მას შეასწორებთ. ნაგულისხმევად ეს არის **ხელით ქმედება** — თქვენ ათავსებთ კარანტინში, ხსნით კარანტინს და ცვლით რეჟიმებს დაფის სატესტო შემთხვევის დეტალების გვერდიდან — მაგრამ ასევე შეგიძლიათ მიუბრუნოთ ის **ავტომატიზაციის გაფრთხილებას** **პარამეტრები → ავტომატიზაციები**-ში, რათა ტესტი ავტომატურად დადუმდეს (ან გამოიტოვოს), როდესაც გადალახავს არასტაბილურობის ზღვარს, და ამოღებულ იქნას კარანტინიდან, როდესაც აღდგება. ყოველი გადასვლა, ხელით თუ ავტომატური, იწერება სატესტო შემთხვევის აუდიტის ჟურნალში.

კარანტინში მყოფი ტესტი არის ერთ-ერთ ორ რეჟიმში:

- **დადუმებული**: ტესტი მაინც სრულდება, მაგრამ `tuist xcodebuild test` ფარავს ჩავარდნას. ჩავარდნები მაინც კვებავენ არასტაბილური ტესტების დეტექტორს, ასე რომ შეგიძლიათ აკვირდეთ ტესტს ბილდის გატეხვის გარეშე. აირჩიეთ ეს იმ ტესტისთვის, რომელსაც აქტიურად იკვლევთ.
- **გამოტოვებული**: xcodebuild იღებს `-skip-testing <identifier>`, ასე რომ ტესტი საერთოდ არ იწყება. ის არ წარმოქმნის ახალ შედეგებს და ქრება არასტაბილური ტესტების დაფიდან, სანამ ხელახლა არ ჩართავთ. აირჩიეთ ეს, როდესაც ტესტი გაფუჭებულია, ნელია ან იმდენად მუდმივად არასტაბილური, რომ მისი გაშვება უბრალოდ კარგავს CI წუთებს.

### რატომ შეიძლება კარანტინში მყოფი ტესტები გამოჩნდნენ როგორც წარმატებული {#quarantined-passing}

- **დადუმებული ტესტები** მაინც სრულდება. დადუმებული ტესტი, რომელიც ჩავარდება, იწერება როგორც **ჩავარდნილი** სატესტო შემთხვევის გაშვებაზე და მონიშნულია როგორც არასტაბილური — თითოეული ტესტის სტატუსი არ გადაიწერება. რაც გადაიწერება არის **მთლიანი ტესტების გაშვება**: თუ გაშვებაში ყოველი ჩავარდნილი სატესტო შემთხვევა დადუმებულია, გაშვება მთლიანად იტყობინება როგორც წარმატებული, ასე რომ დადუმებული ჩავარდნები არ ტეხენ CI-ს.
- **გამოტოვებული ტესტები** საერთოდ არ სრულდება, ასე რომ დაფა აჩვენებს სტატუსს ტესტის ბოლო რეალური შესრულებიდან — ეს სნაპშოტი შეიძლება კვირების ძველი იყოს.

### ტესტების გაშვება {#running-tests}

`tuist xcodebuild test` არის passthrough wrapper, რომელიც ავტომატურად ითვალისწინებს ორივე რეჟიმს. გამოიყენეთ ის ისე, როგორც xcodebuild-ს გამოიძახებდით:

```sh
tuist xcodebuild test -scheme MyScheme
```

გამოტოვებული ტესტები ემატება თქვენს xcodebuild-ის გამოძახებას როგორც `-skip-testing <identifier>` და საერთოდ არ იწყება. დადუმებული ტესტები სრულდება ჩვეულებრივად; თუ ისინი ჩავარდებიან, ჩავარდნა ფარულია მიღებულ ბილდის სტატუსში.

#### კარანტინის გვერდის ავლა

`tuist xcodebuild test` იღებს `--skip-quarantine` ყველაფრის გასაშვებად, დადუმებული და გამოტოვებული ტესტების ჩათვლით:

```sh
tuist xcodebuild test --skip-quarantine -scheme MyScheme
```

#### xcodebuild-ის პირდაპირი გამოძახება

თუ ვერ გაივლით `tuist xcodebuild test`-ს მეშვეობით, გააფართოვეთ კარანტინში მყოფი ტესტები `-skip-testing` არგუმენტებად თავად `tuist test case list`-ის მეშვეობით:

```sh
xcodebuild test \
  -scheme MyScheme \
  $(tuist test case list --quarantined --skip-testing)
```

ეს არის უსაფრთხო ნაგულისხმევი `tuist xcodebuild test`-ს გარეთ: ჩავარდნის დამალვა დადუმებული ტესტებისთვის ხდება მხოლოდ მაშინ, როდესაც ამ ბრძანებას გაივლით, ასე რომ ორივე რეჟიმის გამოტოვება თავიდან აიცილებს ცრუ CI ჩავარდნებს. თუ საჭიროებთ უფრო ზუსტ კონტროლს, გაიარეთ `tuist xcodebuild test`-ის მეშვეობით.

## ახალი ტესტების სტრეს-ტესტირება {#stress-testing-new-tests}

სტრეს-გეიტი ხელახლა აშვებს თქვენი ბრენჩის მიერ დამატებულ სატესტო შემთხვევებს, თითოეულს რამდენჯერმე ახალ პროცესში და აფიქსირებს იმას, რაც არასტაბილური აღმოჩნდება. ახალ არასტაბილურ ტესტს ხედავთ pull request-ზე, რომელმაც ის შემოიტანა, და არა კვირების შემდეგ.

სატესტო შემთხვევა ახლად ითვლება, თუ ის ბოლო 90 დღის განმავლობაში არ გაშვებულა CI-ზე პროექტის ნაგულისხმევ ბრენჩზე, ან კომიტზე, რომელიც მას შემდეგ შევიდა ამ ბრენჩში. შერწყმის რიგის (merge queue) გამოყენებისას, სატესტო შემთხვევა, რომელიც რიგმა გაუშვა, ცნობილი ხდება მაშინ, როდესაც რიგის კომიტი შედის ბრენჩში და რჩება ახლად, თუ რიგი მას გამოტოვებს. კომიტები ემთხვევა <.localized_link href="/guides/features/test-insights/xcode#git-history">Git-ის ისტორიის</.localized_link> მეშვეობით, რომელსაც Tuist აგროვებს CI-ზე.

### მისი ჩართვა

გეიტი ნაგულისხმევად გამორთულია. დააყენეთ რეჟიმი:

- **`report`**: აფრთხილებს თითოეული არასტაბილური სატესტო შემთხვევის შესახებ. გაშვება მაინც სრულდება თავისი შედეგის მიხედვით.
- **`enforce`**: არასტაბილური სატესტო შემთხვევა აკრეხს გაშვებას, იმავე exit code-ით, რაც ჩავარდნილ ტესტს აქვს.

დაიწყეთ `report`-ით რამდენიმე კვირის განმავლობაში, რათა ნახოთ, რას დაბლოკავდა `enforce`.

გადაეცით ის passthrough არგუმენტებამდე, ან დააყენეთ `TUIST_TEST_STRESS_NEW_TESTS` რეჟიმის CI ლეინის მიხედვით ვარიაციისთვის:

```sh
tuist xcodebuild test --stress-new-tests report -scheme MyScheme
```

### რამდენჯერ უშვებს ხელახლა თითოეულ ტესტს

დამოკიდებულია იმაზე, თუ რამდენი დრო დასჭირდა სატესტო შემთხვევას პირველ გაშვებაზე:

| პირველი გაშვება | ხელახალი გაშვებები |
| --- | --- |
| 5 წმ-მდე | 10 |
| 10 წმ-მდე | 5 |
| 30 წმ-მდე | 3 |
| 5 წთ-მდე | 2 |
| 5 წთ-ზე მეტი | არ ხდება ხელახალი გაშვება |

ხელახალი გაშვებები იყენებენ პირველი გაშვების მიერ აგებულს. გაშვება ჩერდება 200 სატესტო შემთხვევაზე ან 10 წუთზე, რაც ადრე მოხდება, და მიუთითებს, რომელ ზღვარს მიაღწია.

### როდესაც გეიტი არ მუშაობს

- პირველი გაშვება უკვე ჩავარდა. ჯერ ეს ტესტები გაასწორეთ.
- პროექტს არ აქვს ნაგულისხმევი ბრენჩი, ან მასზე CI-ზე ჯერ არაფერი გაშვებულა.
- პროექტის სატესტო შემთხვევების 30%-ზე მეტი ახლად ჩანს. ამდენის ხელახლა გაშვება მეტ დროს წაიღებდა, ვიდრე სასარგებლო იქნებოდა. ეს მოსალოდნელია პროექტზე, რომელიც ახლახანს დაიწყო Tuist-თან ანგარიშგება, ან სახელის გადაქარების შემდეგ, რომელიც ერთდროულად ბევრ ტესტს გადაადგილებს.

## არასტაბილური და კარანტინში მყოფი მდგომარეობის კითხვა {#querying}

### CLI

`tuist test case` ბრძანებების ხე აჩვენებს ყველაფერს, რასაც Tuist აკონტროლებს სატესტო შემთხვევის შესახებ:

```sh
tuist test case list --flaky                       # only flaky test cases
tuist test case list --quarantined                 # only muted or skipped test cases
tuist test case show <test_case_id>                # detail: flakiness rate, last status, run counts
tuist test case events <test_case_id>              # audit log: marked_flaky, muted, skipped, ...
tuist test case run list <test_case_id>            # run history with status and duration
tuist test case run show <test_case_run_id>        # single run, including failure breakdown
```

ყველა ეს იღებს `--json`-ს სკრიპტინგისთვის.

### REST API

იგივე მონაცემები ხელმისაწვდომია HTTP-ის მეშვეობით — იხილეთ [სატესტო შემთხვევების endpoint-ები](https://tuist.dev/api/docs#tag/test-cases) API-ის ცნობარში მარშრუტების, ფილტრების და პასუხის ველების სრული სიისთვის. სატესტო შემთხვევის მდგომარეობის შესაცვლელად (არასტაბილურად მონიშვნა/გაუქმება, დადუმება, გამოტოვება), გაგზავნეთ `PATCH /api/projects/{account_handle}/{project_handle}/tests/test-cases/{test_case_id}` `is_flaky`-ით ან `state`-ით. იგივე ცვლილება ხელმისაწვდომია როგორც `tuist test case update`, ასევე `update_test_case` Model Context Protocol ინსტრუმენტის სახით.
