# Xcode-ის არასტაბილური ტესტები {#xcode-flaky-tests}

> [!WARNING]
> **მოთხოვნები**
>
> - <.localized_link href="/guides/features/test-insights/xcode">Xcode-ის ტესტების ინსაიტები</.localized_link> კონფიგურირებული. Tuist აღმოაჩენს არასტაბილურ ტესტებს ყოველი ტესტების გაშვების მიერ ატვირთული ტესტ-ინსაიტის მოვლენებიდან.

არასტაბილური ტესტებია ისეთი ტესტები, რომლებიც ერთი და იგივე კოდით რამდენჯერმე გაშვებისას სხვადასხვა შედეგს (წარმატებას ან ჩავარდნას) იძლევიან. ისინი ამცირებენ ნდობას თქვენს ტესტების ნაკრებში და ფლანგავენ დეველოპერების დროს ცრუ ჩავარდნების გამოკვლევაზე. Tuist ავტომატურად აღმოაჩენს არასტაბილურ ტესტებს და გეხმარებათ მათ თვალყურის დევნაში დროთა განმავლობაში.

![არასტაბილური ტესტების გვერდი](/images/guides/features/test-insights/flaky-tests-page.png)

## როგორ მუშაობს არასტაბილურობის აღმოჩენა {#how-it-works}

Tuist ორი გზით აღმოაჩენს არასტაბილურ ტესტებს:

### ტესტების ხელახალი გაშვება {#test-retries}

როდესაც ტესტებს ხელახალი გაშვების ფუნქციით უშვებთ, Tuist აანალიზებს თითოეული მცდელობის შედეგებს. თუ ტესტი ზოგიერთ მცდელობაზე ვარდება, მაგრამ სხვებზე წარმატებით სრულდება, ის არასტაბილურად მონიშნება.

გაატარეთ `-retry-tests-on-failure` ან `-test-iterations` ბრძანების მეშვეობით `tuist xcodebuild test`:

```sh
tuist xcodebuild test \
  -scheme MyScheme \
  -retry-tests-on-failure \
  -test-iterations 3
```

![არასტაბილური სატესტო შემთხვევის დეტალები](/images/guides/features/test-insights/flaky-test-case-detail.png)

### ჯვარედინი გაშვებების აღმოჩენა {#cross-run-detection}

ტესტების ხელახალი გაშვების გარეშეც, Tuist-ს შეუძლია აღმოაჩინოს არასტაბილური ტესტები სხვადასხვა CI გაშვებების შედეგების შედარებით ერთსა და იმავე კომიტზე, სქემაზე და მითითებულ დანიშნულებაზე (მოწყობილობის სახელი, პლატფორმა და OS ვერსია). თუ ტესტი ერთ შესაბამის CI გაშვებაში წარმატებით სრულდება, მაგრამ მეორეში ვარდება, ჩავარდნილი გაშვება არასტაბილურად მონიშნება. ეს მუშაობს მიუხედავად იმისა, რომელი შედეგი მოვა პირველი.

ერთი და იგივე ტესტი შეიძლება თანმიმდევრულად განსხვავებულად იქცეოდეს სხვადასხვა სქემასა თუ დანიშნულებაზე. მაგალითად, iOS 26-ზე წარმატება და iOS 27-ზე ჩავარდნა არასტაბილურობას არ ადგენს. სხვადასხვა სქემებიდან, მოწყობილობებიდან, პლატფორმებიდან ან OS ვერსიებიდან მიღებული შედეგები ერთმანეთს არასტაბილურად არ მონიშნავენ.

შედეგები მიკუთვნებადი დანიშნულების გარეშე შედარებულია სხვა მიუკუთვნებელ შედეგებთან, ცალკე ცნობილი დანიშნულების მქონე შედეგებისგან. ეს მოიცავს ანგარიშებს დაკარგული ან არასრული დანიშნულების მეტამონაცემებით და ანგარიშებს მრავალი განსხვავებული დანიშნულებით, რადგან ინდივიდუალური ტესტების შედეგები ჯერ კიდევ ვერ მიეკუთვნება კონკრეტულ დანიშნულებას. ამ ჯგუფში გარემოებს შორის განსხვავებებმა შეიძლება მაინც გამოიწვიოს ცრუ არასტაბილური კლასიფიკაციები. ხელახალი გაშვებაზე დაფუძნებული აღმოჩენა კვლავ მოქმედებს. არსებული ისტორიული არასტაბილური კლასიფიკაციები უცვლელია.

ეს განსაკუთრებით სასარგებლოა იმ არასტაბილური ტესტების დასაჭერად, რომლებიც საკმარისად თანმიმდევრულად არ ვარდებიან, რომ ხელახალი გაშვებით დაფიქსირდნენ, მაგრამ მაინც იწვევენ პერიოდულ CI ჩავარდნებს.

## არასტაბილური ტესტების მართვა {#managing-flaky-tests}

### ავტომატური გასუფთავება

აღმოჩენა და გასუფთავება მიმდინარეობს პროექტზე **ავტომატიზაციის შეტყობინების** მეშვეობით. ყოველ პროექტს აქვს ნაგულისხმევი „არასტაბილური ტესტების აღმოჩენის“ ავტომატიზაცია, რომლის *ტრიგერი* ტესტს არასტაბილურად მონიშნავს, ხოლო *აღდგენა* ასუფთავებს ნიშანს, როდესაც ტესტი გაივლის კონფიგურირებულ აღდგენის ფანჯარას (ნაგულისხმევი **14 დღე**) ხელახალი ტრიგერის გარეშე. ჩაასწორეთ ის **პარამეტრები → ავტომატიზაციები**-ის ქვეშ, რათა შეცვალოთ აღდგენის ფანჯარა, შეცვალოთ აღდგენის მოქმედებები (მაგ., ასევე მოხსნა კარანტინიდან) ან სრულად გათიშოთ აღდგენა, რათა ტესტები არასტაბილურად მონიშნული დარჩეს, სანამ ხელით არ გაასუფთავებთ.

### ხელით მართვა

ასევე შეგიძლიათ ხელით მონიშნოთ ან მოხსნათ ტესტები არასტაბილურად სატესტო შემთხვევის დეტალების გვერდიდან. ეს სასარგებლოა, როდესაც:
- გსურთ აღიაროთ ცნობილი არასტაბილური ტესტი მის გამოსწორებაზე მუშაობისას
- ტესტი არასწორად მონიშნული იყო ინფრასტრუქტურის პრობლემების გამო

## არასტაბილური ტესტების კარანტინში მოთავსება {#quarantining}

კარანტინი იზოლირებს არასტაბილურ ტესტს, რათა მან არ დაბლოკოს CI, სანამ მას ასწორებთ. ნაგულისხმევად ეს არის **ხელით შესრულებადი მოქმედება** — თქვენ ათავსებთ კარანტინში, ხსნით კარანტინს და ცვლით რეჟიმებს დაფის სატესტო შემთხვევის დეტალების გვერდიდან — მაგრამ ასევე შეგიძლიათ ჩართოთ ის **ავტომატიზაციის შეტყობინებაში** **პარამეტრები → ავტომატიზაციები**-ის ქვეშ, რათა ტესტი ავტომატურად დადუმდეს (ან გამოტოვებულ იქნას), როდესაც გადალახავს არასტაბილურობის ზღვარს, და ამოღებულ იქნას კარანტინიდან, როდესაც აღდგება. ყოველი გადასვლა, ხელით თუ ავტომატურად, ფიქსირდება სატესტო შემთხვევის აუდიტის ჟურნალში.

ნაგულისხმევად, აღდგენა ელოდება, სანამ ტრიგერის პირობა აღარ შესრულდება, ამიტომ ტესტი რჩება კარანტინში, სანამ მისი ძველი არასტაბილური გაშვებები არ დატოვებენ ტრიგერის ფანჯარას. უფრო სწრაფი აღდგენისთვის, დააყენეთ **აღდგენა, როდესაც** მნიშვნელობაზე **არ არის ახალი არასტაბილური გაშვებები**: ტესტი აღდგება, როდესაც აღდგენის ფანჯარა (დღეები ან გაშვებები) გაივლის ახალი არასტაბილური გაშვების გარეშე, ყოველი ახალი არასტაბილური გაშვება ხელახლა იწყებს ამ ლოდინს და აღდგენის შემდეგ მხოლოდ ახალი არასტაბილური გაშვება ათავსებს მას ხელახლა კარანტინში.

კარანტინში მოთავსებული ტესტი ერთ-ერთ ორ რეჟიმშია:

- **დადუმებული**: ტესტი მაინც გადის, მაგრამ `tuist xcodebuild test` ფარავს ჩავარდნას. ჩავარდნები მაინც კვებავს არასტაბილური ტესტების დეტექტორს, ასე რომ შეგიძლიათ აკვირდეთ ტესტს ბილდის გატეხვის გარეშე. აირჩიეთ ეს ტესტისთვის, რომელსაც აქტიურად იკვლევთ.
- **გამოტოვებული**: xcodebuild იღებს `-skip-testing <identifier>`, ამიტომ ტესტი არასდროს იწყება. ის არ წარმოქმნის ახალ შედეგებს და ქრება არასტაბილური ტესტების დაფიდან, სანამ ხელახლა არ ჩართავთ. აირჩიეთ ეს, როდესაც ტესტი გატეხილია, ნელია ან იმდენად მუდმივად არასტაბილური, რომ მისი გაშვება უბრალოდ ფლანგავს CI წუთებს.

### რატომ შეიძლება კარანტინში მოთავსებული ტესტები წარმატებულად ჩანდეს {#quarantined-passing}

- **დადუმებული ტესტები** მაინც სრულდება. ჩავარდნილი დადუმებული ტესტი ფიქსირდება როგორც **ჩავარდნილი** სატესტო შემთხვევის გაშვებაზე და მონიშნულია როგორც არასტაბილური — ტესტის სტატუსი არ გადაიწერება. რაც იცვლება, არის **მთლიანი ტესტების გაშვება**: თუ გაშვებაში ყოველი ჩავარდნილი სატესტო შემთხვევა დადუმებულია, გაშვება მთლიანად მოხსენებულია როგორც წარმატებული, ასე რომ დადუმებული ჩავარდნები არ ტეხენ CI-ს.
- **გამოტოვებული ტესტები** საერთოდ არ გადის, ამიტომ დაფა აგრძელებს ტესტის ბოლო რეალური გაშვების სტატუსის ჩვენებას — ეს სნაპშოტი შეიძლება კვირების წინანდელი იყოს.

### ტესტების გაშვება {#running-tests}

`tuist xcodebuild test` არის passthrough გარსი, რომელიც ავტომატურად ითვალისწინებს ორივე რეჟიმს. გამოიყენეთ ის ისევე, როგორც xcodebuild-ს გამოიძახებდით:

```sh
tuist xcodebuild test -scheme MyScheme
```

გამოტოვებული ტესტები ემატება თქვენს xcodebuild-ის გამოძახებას როგორც `-skip-testing <identifier>` და არასდროს იწყება. დადუმებული ტესტები ჩვეულებრივად გადის; თუ ისინი ვარდებიან, ჩავარდნა ფარულია მიღებულ ბილდის სტატუსში.

#### კარანტინის გვერდის ავლა

`tuist xcodebuild test` იღებს `--skip-quarantine` ყველაფრის გასაშვებად, დადუმებული და გამოტოვებული ტესტების ჩათვლით:

```sh
tuist xcodebuild test --skip-quarantine -scheme MyScheme
```

#### xcodebuild-ის პირდაპირი გამოძახება

თუ არ შეგიძლიათ `tuist xcodebuild test`-ის მეშვეობით გასვლა, თავად გააფართოვეთ კარანტინში მოთავსებული ტესტები `-skip-testing` არგუმენტებად `tuist test case list`-ის მეშვეობით:

```sh
xcodebuild test \
  -scheme MyScheme \
  $(tuist test case list --quarantined --skip-testing)
```

ეს არის უსაფრთხო ნაგულისხმევი `tuist xcodebuild test`-ის გარეთ: დადუმებული ტესტებისთვის ჩავარდნის დამალვა ხდება მხოლოდ მაშინ, როდესაც ამ ბრძანების მეშვეობით გადიხართ, ამიტომ ორივე რეჟიმის გამოტოვება თავს არიდებს ცრუ CI ჩავარდნებს. თუ უფრო ზუსტი კონტროლი გჭირდებათ, წადით `tuist xcodebuild test`-ის მეშვეობით.

## ახალი ტესტების სტრეს-ტესტირება {#stress-testing-new-tests}

სტრესის კარიბჭე ხელახლა აშვებს თქვენი ბრენჩის მიერ დამატებულ სატესტო შემთხვევებს, თითოეულს რამდენჯერმე ახალ პროცესში, და აფიქსირებს მათ, რომლებიც არასტაბილური აღმოჩნდება. ახალ არასტაბილურ ტესტს ხედავთ იმ pull request-ზე, რომელმაც ის შემოიტანა, და არა კვირების შემდეგ.

სატესტო შემთხვევა ახლად ითვლება, თუ ის ბოლო 90 დღის განმავლობაში არ გაშვებულა CI-ში პროექტის ნაგულისხმევ ბრენჩზე, ან კომიტზე, რომელიც მას შემდეგ ამ ბრენჩზე მოხვდა. შერწყმის რიგის (merge queue) გამოყენებისას, რიგის მიერ გაშვებული სატესტო შემთხვევა ცნობილი ხდება მას შემდეგ, რაც რიგის კომიტი მოხვდება ბრენჩზე, და რჩება ახლად, თუ რიგი მას გამოტოვებს. კომიტები შეესაბამება <.localized_link href="/guides/features/test-insights/xcode#git-history">Git-ის ისტორიას</.localized_link>, რომელსაც Tuist აგროვებს CI-ში.

### მისი ჩართვა

კარიბჭე ნაგულისხმევად გამორთულია. აირჩიეთ რეჟიმი:

- **`report`**: აფრთხილებს თითოეული არასტაბილური სატესტო შემთხვევის შესახებ. გაშვება მაინც სრულდება თავისი შედეგის მიხედვით.
- **`enforce`**: არასტაბილური სატესტო შემთხვევა ავარებს გაშვებას, იმავე exit code-ით, როგორც ჩავარდნილი ტესტი.

დაიწყეთ `report`-ით რამდენიმე კვირის განმავლობაში, რათა ნახოთ, რას დაბლოკავდა `enforce`.

გადაეცით ის passthrough არგუმენტებამდე, ან დააყენეთ `TUIST_TEST_STRESS_NEW_TESTS` რეჟიმის CI ლეინის მიხედვით ვარიაციისთვის:

```sh
tuist xcodebuild test --stress-new-tests report -scheme MyScheme
```

### რამდენჯერ გადის თითოეული ტესტი ხელახლა

ეს დამოკიდებულია იმაზე, თუ რამდენი დრო დასჭირდა სატესტო შემთხვევას პირველ გაშვებაზე:

| პირველი გაშვება | ხელახალი გაშვებები |
| --- | --- |
| 5 წმ-მდე | 10 |
| 10 წმ-მდე | 5 |
| 30 წმ-მდე | 3 |
| 5 წთ-მდე | 2 |
| 5 წთ-ზე მეტი | არ განმეორდება |

ხელახალი გაშვებები იყენებენ პირველი გაშვების მიერ აგებულს. გაშვება ჩერდება 200 სატესტო შემთხვევაზე ან 10 წუთზე, იმის მიხედვით, თუ რომელი მოხდება პირველი, და მიუთითებს, რომელ ლიმიტს მიაღწია.

### როდესაც კარიბჭე არ გადის

- პირველი გაშვება უკვე ჩავარდა. ჯერ შეასწორეთ ეს ტესტები.
- პროექტს არ აქვს ნაგულისხმევი ბრენჩი, ან მასზე CI-ში ჯერ არაფერი გაშვებულა.
- პროექტის სატესტო შემთხვევების 30%-ზე მეტი ახლად ჩანს. ამდენის ხელახლა გაშვებას მეტი დრო დასჭირდება, ვიდრე ღირს. ეს მოსალოდნელია პროექტზე, რომელიც ახლახან დაიწყო Tuist-ისთვის მონაცემების გაგზავნა, ან სახელის შეცვლის შემდეგ, რამაც ერთდროულად ბევრი ტესტი გადაიტანა.

## არასტაბილური და კარანტინში მყოფი მდგომარეობის გამოკითხვა {#querying}

### CLI

`tuist test case` ბრძანებების ხე აჩვენებს ყველაფერს, რასაც Tuist აკვირდება სატესტო შემთხვევის შესახებ:

```sh
tuist test case list --flaky                       # only flaky test cases
tuist test case list --quarantined                 # only muted or skipped test cases
tuist test case show <test_case_id>                # detail: flakiness rate, last status, run counts
tuist test case events <test_case_id>              # audit log: marked_flaky, muted, skipped, ...
tuist test case run list <test_case_id>            # run history with status and duration
tuist test case run show <test_case_run_id>        # single run, including failure breakdown
```

ყველა ეს იღებს `--json`-ს სკრიპტინგისთვის.

### REST API

იგივე მონაცემები ხელმისაწვდომია HTTP-ით — იხილეთ [სატესტო შემთხვევების endpoint-ები](https://tuist.dev/api/docs#tag/test-cases) API ცნობარში სრული სიისთვის მარშრუტების, ფილტრების და პასუხის ველების შესახებ. სატესტო შემთხვევის მდგომარეობის შესაცვლელად (არასტაბილურად მონიშვნა ან მონიშვნის მოხსნა, დადუმება, გამოტოვება), გაგზავნეთ `PATCH /api/projects/{account_handle}/{project_handle}/tests/test-cases/{test_case_id}` `is_flaky`-ით ან `state`-ით. იგივე ცვლილება ხელმისაწვდომია როგორც `tuist test case update`, ასევე როგორც `update_test_case` Model Context Protocol ინსტრუმენტი.
