# Xcode-ის არასტაბილური ტესტები {#xcode-flaky-tests}

> [!WARNING]
> **მოთხოვნები**
>
> - <.localized_link href="/guides/features/test-insights/xcode">Xcode-ის ტესტების ინსაიტები</.localized_link> კონფიგურირებული. Tuist ავტომატურად აღმოაჩენს არასტაბილურ ტესტებს ყოველი ტესტის გაშვებისას ატვირთული ტესტ-ინსაიტის მოვლენებიდან.

არასტაბილური ტესტები არის ტესტები, რომლებიც ერთი და იგივე კოდით რამდენჯერმე გაშვებისას სხვადასხვა შედეგს (წარმატება ან ჩავარდნა) იძლევა. ისინი ამცირებენ ნდობას თქვენს ტესტების ნაკრებში და ფუჭად ხარჯავენ დეველოპერების დროს ცრუ ჩავარდნების გამოკვლევაში. Tuist ავტომატურად აღმოაჩენს არასტაბილურ ტესტებს და გეხმარებათ მათ თვალყურის დევნაში დროთა განმავლობაში.

![არასტაბილური ტესტების გვერდი](/images/guides/features/test-insights/flaky-tests-page.png)

## როგორ მუშაობს არასტაბილურობის აღმოჩენა {#how-it-works}

Tuist ორი გზით აღმოაჩენს არასტაბილურ ტესტებს:

### ტესტების ხელახლა გაშვება {#test-retries}

როდესაც ტესტებს ხელახლა გაშვების ფუნქციით აშვებთ, Tuist აანალიზებს თითოეული მცდელობის შედეგებს. თუ ტესტი ზოგიერთ მცდელობაზე ვარდება, მაგრამ სხვებზე გადის, ის მონიშნულია როგორც არასტაბილური.

გაატარეთ `-retry-tests-on-failure` ან `-test-iterations` `tuist xcodebuild test`-ის საშუალებით:

```sh
tuist xcodebuild test \
  -scheme MyScheme \
  -retry-tests-on-failure \
  -test-iterations 3
```

![არასტაბილური ტესტის საქმის დეტალები](/images/guides/features/test-insights/flaky-test-case-detail.png)

### ჯვარედინი გაშვებების აღმოჩენა {#cross-run-detection}

ტესტების ხელახლა გაშვების გარეშეც, Tuist-ს შეუძლია აღმოაჩინოს არასტაბილური ტესტები სხვადასხვა CI გაშვებების შედეგების შედარებით იმავე კომიტზე, სქემაზე და მითითებულ დანიშნულებაზე (მოწყობილობის სახელი, პლატფორმა და OS-ის ვერსია). თუ ტესტი გადის ერთ შესაბამის CI გაშვებაში, მაგრამ ვარდება მეორეში, ჩავარდნილი შესრულება მონიშნულია როგორც არასტაბილური. ეს მუშაობს მიუხედავად იმისა, რომელი შედეგი მოვა პირველი.

იგივე ტესტს შეიძლება თანმიმდევრულად განსხვავებულად იქცეოდეს სხვადასხვა სქემასა თუ დანიშნულებაზე. მაგალითად, iOS 26-ზე წარმატება და iOS 27-ზე ჩავარდნა არ ქმნის არასტაბილურობას. სხვადასხვა სქემებიდან, მოწყობილობებიდან, პლატფორმებიდან ან OS-ის ვერსიებიდან მიღებული შედეგები ერთმანეთს არასტაბილურად არ მონიშნავენ.

შედეგები, რომლებსაც არ აქვთ მიკუთვნებადი დანიშნულება, შედარებულია სხვა მიუკუთვნებელ შედეგებთან, ცალკე ცნობილი დანიშნულების მქონე შედეგებისგან. ეს მოიცავს ანგარიშებს ნაკლები ან არასრული დანიშნულების მეტამონაცემებით და ანგარიშებს, რომლებიც შეიცავს მრავალ განსხვავებულ დანიშნულებას, რადგან ინდივიდუალური ტესტის შედეგები ჯერ კიდევ ვერ მიეკუთვნება კონკრეტულ დანიშნულებას. ამ ჯგუფში გარემოებს შორის განსხვავებებმა შეიძლება მაინც გამოიწვიოს ცრუ არასტაბილურობის კლასიფიკაციები. ხელახლა გაშვებაზე დაფუძნებული აღმოჩენა კვლავ მოქმედებს. არსებული ისტორიული არასტაბილურობის კლასიფიკაციები უცვლელია.

ეს განსაკუთრებით სასარგებლოა იმ არასტაბილური ტესტების დასაჭერად, რომლებიც საკმარისად თანმიმდევრულად არ ვარდებიან, რათა ხელახლა გაშვებამ დაიჭიროს, მაგრამ მაინც იწვევენ პერიოდულ CI ჩავარდნებს.

## არასტაბილური ტესტების მართვა {#managing-flaky-tests}

### ავტომატური გასუფთავება

აღმოჩენა და გასუფთავება ხდება პროექტზე **ავტომატიზაციის გაფრთხილების** საშუალებით. ყოველ პროექტს აქვს ნაგულისხმევი „არასტაბილური ტესტის აღმოჩენის“ ავტომატიზაცია, რომლის *ტრიგერი* მონიშნავს ტესტს როგორც არასტაბილურს, ხოლო *აღდგენა* ხსნის ნიშანს, როდესაც ტესტი გაივლის კონფიგურირებულ აღდგენის ფანჯარას (ნაგულისხმევი **14 დღე**) ხელახლა ტრიგერის გარეშე. შეასწორეთ ის **პარამეტრები → ავტომატიზაციები**-ის ქვეშ, რათა შეცვალოთ აღდგენის ფანჯარა, შეცვალოთ აღდგენის ქმედებები (მაგ., ასევე მოხსნა კარანტინიდან) ან სრულიად გათიშოთ აღდგენა, რათა ტესტები დარჩეს მონიშნული როგორც არასტაბილური, სანამ ხელით არ გაასუფთავებთ.

### ხელით მართვა

ასევე შეგიძლიათ ხელით მონიშნოთ ან მოხსნათ ტესტები როგორც არასტაბილური ტესტის საქმის დეტალების გვერდიდან. ეს სასარგებლოა, როდესაც:
- გსურთ აღიაროთ ცნობილი არასტაბილური ტესტი, სანამ მუშაობთ გამოსწორებაზე
- ტესტი არასწორად იყო მონიშნული ინფრასტრუქტურის პრობლემების გამო

## არასტაბილური ტესტების კარანტინში მოთავსება {#quarantining}

კარანტინი იზოლირებს არასტაბილურ ტესტს, რათა მან არ დაბლოკოს CI, სანამ მას ასწორებთ. ნაგულისხმევად ეს არის **ხელით ქმედება** — თქვენ ათავსებთ კარანტინში, ხსნით კარანტინიდან და ცვლით რეჟიმებს დაფის ტესტის საქმის დეტალების გვერდიდან — მაგრამ ასევე შეგიძლიათ მიუერთოთ ის **ავტომატიზაციის გაფრთხილებას** **პარამეტრები → ავტომატიზაციები**-ის ქვეშ, რათა ტესტი ავტომატურად დადუმდეს (ან გამოტოვებულ იქნას), როდესაც გადალახავს არასტაბილურობის ზღვარს, და ამოღებულ იქნას კარანტინიდან, როდესაც აღდგება. ყოველი გადასვლა, ხელით თუ ავტომატური, იწერება ტესტის საქმის აუდიტის ჟურნალში.

კარანტინში მოთავსებული ტესტი არის ერთ-ერთ ორ რეჟიმში:

- **დადუმებული**: ტესტი მაინც გადის, მაგრამ `tuist xcodebuild test` ფარავს ჩავარდნას. ჩავარდნები მაინც კვებავენ არასტაბილური ტესტების დეტექტორს, ასე რომ შეგიძლიათ აკვირდეთ ტესტს ბილდის გატეხვის გარეშე. აირჩიეთ ეს იმ ტესტისთვის, რომელსაც აქტიურად იკვლევთ.
- **გამოტოვებული**: xcodebuild იღებს `-skip-testing <identifier>`, ასე რომ ტესტი არასდროს იწყება. ის არ ქმნის ახალ შედეგებს და ქრება არასტაბილური ტესტების დაფიდან, სანამ ხელახლა არ ჩართავთ. აირჩიეთ ეს, როდესაც ტესტი გაფუჭებულია, ნელია, ან იმდენად მუდმივად არასტაბილურია, რომ მისი გაშვება უბრალოდ ფუჭად ხარჯავს CI წუთებს.

### რატომ შეიძლება კარანტინში მოთავსებული ტესტები გამოჩნდნენ როგორც წარმატებული {#quarantined-passing}

- **დადუმებული ტესტები** მაინც სრულდება. დადუმებული ტესტი, რომელიც ვარდება, იწერება როგორც **ჩავარდნილი** ტესტის საქმის გაშვებაზე და მონიშნულია როგორც არასტაბილური — ტესტის სტატუსი არ გადაიწერება. რაც იცვლება, არის **მთლიანი ტესტის გაშვება**: თუ გაშვებაში ყოველი ჩავარდნილი ტესტის საქმე დადუმებულია, გაშვება მთლიანად ითვლება წარმატებულად, ასე რომ დადუმებული ჩავარდნები არ ტეხენ CI-ს.
- **გამოტოვებული ტესტები** საერთოდ არ გადის, ასე რომ დაფა აჩვენებს სტატუსს ტესტის ბოლო რეალური შესრულებიდან — ეს სნაპშოტი შეიძლება იყოს კვირების წინანდელი.

### ტესტების გაშვება {#running-tests}

`tuist xcodebuild test` არის passthrough wrapper, რომელიც ავტომატურად ითვალისწინებს ორივე რეჟიმს. გამოიყენეთ ის ისე, როგორც xcodebuild-ს გამოიძახებდით:

```sh
tuist xcodebuild test -scheme MyScheme
```

გამოტოვებული ტესტები ემატება თქვენს xcodebuild-ის გამოძახებას როგორც `-skip-testing <identifier>` და არასდროს იწყება. დადუმებული ტესტები ჩვეულებრივად გადის; თუ ისინი ვარდებიან, ჩავარდნა ფარულია მიღებულ ბილდის სტატუსში.

#### კარანტინის გვერდის ავლა

`tuist xcodebuild test` იღებს `--skip-quarantine`-ს, რათა გაუშვას ყველაფერი, დადუმებული და გამოტოვებული ტესტების ჩათვლით:

```sh
tuist xcodebuild test --skip-quarantine -scheme MyScheme
```

#### xcodebuild-ის პირდაპირ გამოძახება

თუ არ შეგიძლიათ `tuist xcodebuild test`-ის გამოყენება, თავად გაშალეთ კარანტინში მოთავსებული ტესტები `-skip-testing` არგუმენტებად `tuist test case list`-ის საშუალებით:

```sh
xcodebuild test \
  -scheme MyScheme \
  $(tuist test case list --quarantined --skip-testing)
```

ეს არის უსაფრთხო ნაგულისხმევი `tuist xcodebuild test`-ის გარეთ: დადუმებული ტესტების ჩავარდნის დაფარვა ხდება მხოლოდ მაშინ, როდესაც ამ ბრძანებას გადიხართ, ასე რომ ორივე რეჟიმის გამოტოვება თავიდან აიცილებს ცრუ CI ჩავარდნებს. თუ გჭირდებათ უფრო ზუსტი კონტროლი, გამოიყენეთ `tuist xcodebuild test`.

## ახალი ტესტების სტრეს-ტესტირება {#stress-testing-new-tests}

სტრეს-გეიტი ხელახლა უშვებს ტესტების იმ შემთხვევებს, რომლებსაც თქვენი ბრენჩი ამატებს, თითოეულს რამდენჯერმე ახალ პროცესში და აცნობებს იმას, ვინც არაიმედურად აღმოჩნდება. ახალ არაიმედურ ტესტს ნახავთ pull request-ზე, რომელმაც ის შემოიტანა, და არა კვირების შემდეგ.

ტესტის შემთხვევა ახლად ითვლება, თუ ის ბოლო 90 დღის განმავლობაში არ გაშვებულა CI-ზე პროექტის ნაგულისხმევ ბრენჩზე, ან კომიტზე, რომელიც მას შემდეგ მასში შევიდა. შერწყმის რიგთან ერთად, ტესტის შემთხვევა, რომელიც რიგმა გაუშვა, ცნობილი ხდება მაშინ, როდესაც რიგის კომიტი შევა, და რჩება ახალი, თუ რიგი მას გამოტოვებს. კომიტები შეესაბამება <.localized_link href="/guides/features/test-insights/xcode#git-history">Git-ის ისტორიას</.localized_link>, რომელსაც Tuist აგროვებს CI-ზე.

### მისი ჩართვა

გეიტი ნაგულისხმევად გამორთულია. დააყენეთ რეჟიმი:

- **`report`**: აფრთხილებს თითოეული არაიმედური ტესტის შემთხვევის შესახებ. გაშვება მაინც სრულდება საკუთარი შედეგით.
- **`enforce`**: არაიმედური ტესტის შემთხვევა აცდენს გაშვებას, იმავე გასვლის კოდით, რაც ჩავარდნილ ტესტს აქვს.

დაიწყეთ `report`-ით რამდენიმე კვირის განმავლობაში, რათა ნახოთ, რას დაბლოკავდა `enforce`.

გადაეცით ის passthrough არგუმენტებამდე, ან დააყენეთ `TUIST_TEST_STRESS_NEW_TESTS`, რათა შეცვალოთ რეჟიმი თითოეული CI ზოლისთვის:

```sh
tuist xcodebuild test --stress-new-tests report -scheme MyScheme
```

### რამდენჯერ გადაუშვებს თითოეულ ტესტს

ეს დამოკიდებულია იმაზე, თუ რამდენი დრო დასჭირდა ტესტის შემთხვევას პირველ გაშვებაზე:

| პირველი გაშვება | განმეორებითი გაშვებები |
| --- | --- |
| 5 წმ-მდე | 10 |
| 10 წმ-მდე | 5 |
| 30 წმ-მდე | 3 |
| 5 წთ-მდე | 2 |
| 5 წთ-ზე მეტი | არ განმეორდება |

განმეორებითი გაშვებები იყენებენ იმას, რაც პირველმა გაშვებამ ააგო. გაშვება ჩერდება 200 ტესტის შემთხვევაზე ან 10 წუთზე, რაც უფრო ადრე მოხდება, და ამბობს, რომელი ლიმიტი შეეხო.

### როდესაც გეიტი არ გადის

- პირველი გაშვება უკვე ჩავარდა. ჯერ ეს ტესტები გაასწორეთ.
- პროექტს არ აქვს ნაგულისხმევი ბრენჩი, ან მასზე ჯერ არაფერი გაშვებულა CI-ზე.
- პროექტის ტესტების შემთხვევების 30%-ზე მეტი ახლად ჩანს. იმდენის განმეორებითი გაშვება უფრო მეტ დროს წაიღებდა, ვიდრე ღირს. ეს მოსალოდნელია პროექტზე, რომელიც ახლახან დაიწყო Tuist-ისთვის ანგარიშგება, ან სახელის შეცვლის შემდეგ, რომელიც ბევრ ტესტს ერთდროულად გადაადგილებს.

## არაიმედური და კარანტინის მდგომარეობის მოთხოვნა {#querying}

### CLI

`tuist test case` ბრძანებების ხე აჩვენებს ყველაფერს, რასაც Tuist აკონტროლებს ტესტის შემთხვევის შესახებ:

```sh
tuist test case list --flaky                       # only flaky test cases
tuist test case list --quarantined                 # only muted or skipped test cases
tuist test case show <test_case_id>                # detail: flakiness rate, last status, run counts
tuist test case events <test_case_id>              # audit log: marked_flaky, muted, skipped, ...
tuist test case run list <test_case_id>            # run history with status and duration
tuist test case run show <test_case_run_id>        # single run, including failure breakdown
```

ყველა ეს იღებს `--json`-ს სკრიპტინგისთვის.

### REST API

იგივე მონაცემები ხელმისაწვდომია HTTP-ის საშუალებით — იხილეთ [ტესტების შემთხვევების ბოლოწერტილები](https://tuist.dev/api/docs#tag/test-cases) API-ის ცნობარში მარშრუტების, ფილტრების და პასუხის ველების სრული სიისთვის. ტესტის შემთხვევის მდგომარეობის შესაცვლელად (არაიმედურად მონიშვნა ან მოხსნა, დადუმება, გამოტოვება), გაგზავნეთ `PATCH /api/projects/{account_handle}/{project_handle}/tests/test-cases/{test_case_id}` `is_flaky`-ით ან `state`-ით. იგივე ცვლილება ხელმისაწვდომია როგორც `tuist test case update` და როგორც `update_test_case` Model Context Protocol ინსტრუმენტი.
