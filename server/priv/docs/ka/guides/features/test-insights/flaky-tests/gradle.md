## როგორ მუშაობს არასტაბილურობის აღმოჩენა {#how-it-works}

Tuist არასტაბილურ ტესტებს ორი გზით აღმოაჩენს:

### ტესტების ხელახლა გაშვება {#test-retries}

როდესაც ტესტებს ხელახლა გაშვების ფუნქციით ასრულებთ, Tuist თითოეული ცდის შედეგებს აანალიზებს. თუ ტესტი ზოგიერთ ცდაზე ვერდება, მაგრამ სხვებზე გადის, ის არასტაბილურად მონიშნავს.

შეგიძლიათ გამოიყენოთ [Test Retry პლაგინი](https://github.com/gradle/test-retry-gradle-plugin) ან მსგავსი მექანიზმი ვერებული ტესტების ხელახლა გასაშვებად. Tuist აღმოაჩენს ტესტებს, რომლებიც ზოგიერთ ცდაზე გადის, მაგრამ სხვებზე ვერდება.

დაამატეთ პლაგინი თქვენს `build.gradle.kts`-ში:

```kotlin
plugins {
    id("org.gradle.test-retry") version "1.6.2"
}

tasks.test {
    retry {
        maxRetries = 3
        maxFailures = 5
        failOnPassedAfterRetry = false
    }
}
```

![არასტაბილური სატესტო შემთხვევის დეტალები](/images/guides/features/test-insights/flaky-test-case-detail.png)

### ჯვარედინი გაშვებების აღმოჩენა {#cross-run-detection}

ტესტების ხელახლა გაშვების გარეშეც, Tuist-ს შეუძლია არასტაბილური ტესტების აღმოჩენა იმავე კომიტზე და იმავე Gradle პროექტზე სხვადასხვა CI გაშვებების შედეგების შედარებით. თუ ტესტი ერთ CI გაშვებაზე გადის, მაგრამ იმავე კომიტისა და პროექტისთვის სხვა გაშვებაზე ვერდება, ვერებული შესრულება არასტაბილურად მონიშნავს.

Gradle პროექტი შედარების გასაღების ნაწილია, რადგან ერთი და იგივე ტესტი შეიძლება განსხვავებულად მოიქცეს სხვადასხვა პროექტში — მაგალითად, საერთო სატესტო კლასი, რომელიც სხვადასხვა დამოკიდებულებით კომპილირდება ან სხვა მოდულის ფიქსტურაზე გაშვებულია. ერთი და იგივე კომიტის ორი გაშვება სხვადასხვა Gradle პროექტებზე განიხილება როგორც ცალკე შესრულების ვარიანტები და ერთმანეთს არასტაბილურად არ მონიშნავს.

ეს განსაკუთრებით სასარგებლოა ისეთი არასტაბილური ტესტების აღმოსაჩენად, რომლებიც არ ვერდება საკმარისად თანმიმდევრულად, რომ ხელახლა გაშვებამ დაიჭიროს, მაგრამ მაინც იწვევს პერიოდულ CI ვერებებს.

## არასტაბილური ტესტების კარანტინში გადაყვანა {#quarantining}

<!-- @snippet: ./_quarantine-intro -->

კარანტინში მყოფი ტესტი ერთ-ერთ ორ რეჟიმშია:

- **ჩუმად**: ტესტი მაინც გაშვებულია, მაგრამ პლაგინი აყენებს `ignoreFailures = true` და ბილდს ხელახლა აგდებს მხოლოდ არა-კარანტინული ვერებების შემთხვევაში. ვერებები მაინც კვებავს არასტაბილური ტესტების დეტექტორს, ასე რომ შეგიძლიათ ტესტს აკვირდეთ ბილდის გაწყვეტის გარეშე. აირჩიეთ ეს იმ ტესტისთვის, რომელსაც აქტიურად იკვლევთ.
- **გამოტოვებული**: პლაგინი ფილტრავს ტესტს Gradle-ის `excludeTestsMatching`-ის მეშვეობით, ასე რომ ის საერთოდ არ იწყება. ის არ წარმოქმნის ახალ შედეგებს და ქრება არასტაბილური ტესტების დაშბორდიდან, სანამ ხელახლა არ ჩართავთ. აირჩიეთ ეს, როდესაც ტესტი გატეხილია, ნელია, ან იმდენად მუდმივად არასტაბილურია, რომ მისი გაშვება უბრალოდ CI წუთების ფლანგვაა.

<!-- @snippet: ./_quarantined-passing -->

### კარანტინის ჩართვა {#enabling-quarantine}

კარანტინი **ავტომატურად ჩართულია CI-ზე** (როდესაც `CI` გარემოს ცვლადი დაყენებულია) და გამორთულია ლოკალური ბილდებისთვის. პლაგინი თითოეული სატესტო ამოცანის წინ Tuist სერვერიდან იღებს კარანტინში მყოფი ტესტების სიას; ჩუმად მყოფი ტესტები ჩვეულებრივად გაშვებულია და მათი ვერებები დამალულია, გამოტოვებული ტესტები ფილტრდება.

შეგიძლიათ ეს აშკარად მართოთ თქვენს `settings.gradle.kts`-ში:

```kotlin
tuist {
    testQuarantine {
        enabled = true  // or false to disable
    }
}
```

როდესაც `enabled` არ არის დაყენებული, ის ავტო-აღმოჩენაზე გადადის: ჩართულია CI-ზე, გამორთულია ლოკალურად.

## ახალი ტესტების სტრეს-ტესტირება {#stress-testing-new-tests}

<!-- @snippet: ./_stress-intro -->

სატესტო შემთხვევა ახლად ითვლება, თუ ის ბოლო 90 დღის განმავლობაში არ გაშვებულა CI-ზე პროექტის ძირითად შტოზე, ან კომიტზე, რომელიც მას შემდეგ მასზე მოხვდა. შერწყმის რიგით, ტესტის შემთხვევა, რომელიც რიგმა გაუშვა, ცნობილი ხდება მას შემდეგ, რაც რიგის კომიტი მოხვდება, და რჩება ახალი, თუ რიგი მას ჩამოაგდებს. კომიტები შეესაბამება <.localized_link href="/guides/features/test-insights/gradle#git-history">Git ისტორიის</.localized_link> მეშვეობით, რომელსაც Tuist აგროვებს CI-ზე.

<!-- @snippet: ./_stress-modes -->

განაცხადეთ ის `settings.gradle.kts`-ში, ან დააყენეთ `TUIST_TEST_STRESS_NEW_TESTS` რეჟიმის შესაცვლელად თითოეული CI არხისთვის:

```kotlin
tuist {
    stressNewTests {
        mode = "report" // or "enforce"
    }
}
```

კარანტინისგან განსხვავებით, კარიბჭეს არ აქვს CI-ის ცოდნის მქონე ნაგულისხმები. `mode`-ის დაყენების გარეშე ის არსად გაშვებულია.

<!-- @snippet: ./_stress-reruns -->

თითოეული ხელახლა გაშვება არის ჩადგმული Gradle ბილდი, რომელიც ფილტრულია იმ ერთ სატესტო შემთხვევაზე, ასე რომ ყოველ ხელახლა გაშვებას ახალი სატესტო JVM ეძლევა.
