## როგორ მუშაობს არასტაბილურობის აღმოჩენა {#how-it-works}

Tuist არასტაბილურ ტესტებს ორი გზით ავლენს:

### ტესტების ხელახლა გაშვება {#test-retries}

როდესაც ტესტებს ხელახლა გაშვების ფუნქციით ასრულებთ, Tuist თითოეული მცდელობის შედეგებს აანალიზებს. თუ ტესტი ზოგიერთ მცდელობაზე ვერდება, მაგრამ სხვებზე გადის, ის არასტაბილურად მონიშნება.

შეგიძლიათ გამოიყენოთ [Test Retry პლაგინი](https://github.com/gradle/test-retry-gradle-plugin) ან მსგავსი მექანიზმი ჩავარდნილი ტესტების ხელახლა გასაშვებად. Tuist აღმოაჩენს ტესტებს, რომლებიც ზოგიერთ მცდელობაზე გადის, მაგრამ სხვებზე ვერდება.

დაამატეთ პლაგინი თქვენს `build.gradle.kts`-ში:

```kotlin
plugins {
    id("org.gradle.test-retry") version "1.6.2"
}

tasks.test {
    retry {
        maxRetries = 3
        maxFailures = 5
        failOnPassedAfterRetry = false
    }
}
```

![არასტაბილური სატესტო შემთხვევის დეტალები](/images/guides/features/test-insights/flaky-test-case-detail.png)

### ჯვარედინი გაშვებების აღმოჩენა {#cross-run-detection}

ტესტების ხელახლა გაშვების გარეშეც, Tuist-ს შეუძლია არასტაბილური ტესტების აღმოჩენა იმავე კომიტისა და იმავე Gradle პროექტის სხვადასხვა CI გაშვებების შედეგების შედარებით. თუ ტესტი ერთ CI გაშვებაზე გადის, მაგრამ იმავე კომიტისა და პროექტის მეორე გაშვებაზე ვერდება, ჩავარდნილი შესრულება არასტაბილურად მონიშნება.

Gradle პროექტი შედარების გასაღების ნაწილია, რადგან ერთი და იგივე ტესტი შეიძლება განსხვავებულად მოიქცეს სხვადასხვა პროექტში — მაგალითად, გაზიარებული სატესტო კლასი, რომელიც სხვადასხვა დამოკიდებულებებით კომპილირდება ან სხვა მოდულის ფიქსტურაზე გაშვებულია. ერთი და იგივე კომიტის ორი გაშვება სხვადასხვა Gradle პროექტებზე ცალკე შესრულების ვარიანტებად მიიჩნევა და ერთმანეთს არასტაბილურად არ მონიშნავს.

ეს განსაკუთრებით სასარგებლოა ისეთი არასტაბილური ტესტების დასაჭერად, რომლებიც საკმარისად თანმიმდევრულად არ ვერდება ხელახლა გაშვებით დასაჭერად, მაგრამ მაინც იწვევს პერიოდულ CI ჩავარდნებს.

## არასტაბილური ტესტების კარანტინში მოქცევა {#quarantining}

<!-- @snippet: ./_quarantine-intro -->

კარანტინში მოქცეული ტესტი ერთ-ერთ რეჟიმშია:

- **ჩუმად**: ტესტი მაინც გაშვებულია, მაგრამ პლაგინი აყენებს `ignoreFailures = true`-ს და ბილდს ხელახლა აგდებს მხოლოდ არაკარანტინული ჩავარდნებისას. ჩავარდნები მაინც კვებავს არასტაბილური ტესტების დეტექტორს, ამიტომ შეგიძლიათ აკვირდეთ ტესტს ბილდის გაწყვეტის გარეშე. აირჩიეთ ეს იმ ტესტისთვის, რომელსაც აქტიურად იკვლევთ.
- **გამოტოვებული**: პლაგინი ფილტრავს ტესტს Gradle-ის `excludeTestsMatching`-ით, ამიტომ ის არასდროს იწყება. ის არ წარმოქმნის ახალ შედეგებს და ქრება არასტაბილური ტესტების დაშბორდიდან მის ხელახლა ჩართვამდე. აირჩიეთ ეს, როცა ტესტი გატეხილია, ნელია, ან იმდენად მუდმივად არასტაბილურია, რომ მისი გაშვება უბრალოდ wasted CI წუთებია.

<!-- @snippet: ./_quarantined-passing -->

### კარანტინის ჩართვა {#enabling-quarantine}

კარანტინი **ავტომატურად ჩართულია CI-ზე** (როცა `CI` გარემოს ცვლადი დაყენებულია) და გამორთულია ლოკალური ბილდებისთვის. პლაგინი თითოეული ტესტის ამოცანამდე იღებს კარანტინში მოქცეული ტესტების სიას Tuist სერვერიდან; ჩუმად მყოფი ტესტები ჩვეულებრივად გაშვებულია და მათი ჩავარდნები დამალულია, გამოტოვებული ტესტები ფილტრდება.

შეგიძლიათ ეს აშკარად აკონტროლოთ თქვენს `settings.gradle.kts`-ში:

```kotlin
tuist {
    testQuarantine {
        enabled = true  // or false to disable
    }
}
```

როცა `enabled` არ არის დაყენებული, ის ავტო-აღმოჩენაზე გადადის: ჩართულია CI-ზე, გამორთულია ლოკალურად.

## ახალი ტესტების სტრეს-ტესტირება {#stress-testing-new-tests}

<!-- @snippet: ./_stress-intro -->

სატესტო შემთხვევა ახლად ითვლება, თუ ის ბოლო 90 დღის განმავლობაში არ გაშვებულა CI-ზე პროექტის ძირითად შტოზე, ან კომიტზე, რომელიც მასზე უკვე მოხვდა. მერჯის რიგით, რიგის მიერ გაშვებული სატესტო შემთხვევა ცნობილი ხდება რიგის კომიტის მოხვედრისას და რჩება ახალი, თუ რიგი მას აგდებს. კომიტები შეესაბამება <.localized_link href="/guides/features/test-insights/gradle#git-history">Git ისტორიას</.localized_link>, რომელსაც Tuist აგროვებს CI-ზე.

<!-- @snippet: ./_stress-modes -->

განაცხადეთ ის `settings.gradle.kts`-ში, ან დააყენეთ `TUIST_TEST_STRESS_NEW_TESTS` რეჟიმის შესაცვლელად თითოეული CI ზოლისთვის:

```kotlin
tuist {
    stressNewTests {
        mode = "report" // or "enforce"
    }
}
```

კარანტინისგან განსხვავებით, გეიტს არ აქვს CI-ის გათვალისწინებული ნაგულისხმები. `mode`-ის დაყენების გარეშე ის არსად გაშვებულია.

<!-- @snippet: ./_stress-reruns -->

თითოეული ხელახლა გაშვება არის ჩაბუდებული Gradle ბილდი, ფილტრული იმ ერთ სატესტო შემთხვევაზე, ამიტომ ყოველი ხელახლა გაშვება იღებს ახალ ტესტის JVM-ს.
