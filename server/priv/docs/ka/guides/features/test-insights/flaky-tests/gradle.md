## როგორ მუშაობს არასტაბილურობის აღმოჩენა {#how-it-works}

Tuist ორი გზით აღმოაჩენს არასტაბილურ ტესტებს:

### ტესტების ხელახლა გაშვება {#test-retries}

როდესაც ტესტებს ხელახლა გაშვების ფუნქციით ასრულებთ, Tuist აანალიზებს თითოეული ცდის შედეგებს. თუ ტესტი ზოგიერთ ცდაზე ვერდება, მაგრამ სხვებზე გადის, ის არასტაბილურად მონიშნება.

შეგიძლიათ გამოიყენოთ [Test Retry პლაგინი](https://github.com/gradle/test-retry-gradle-plugin) ან მსგავსი მექანიზმი ჩავარდნილი ტესტების ხელახლა გასაშვებად. Tuist აღმოაჩენს ტესტებს, რომლებიც ზოგიერთ ცდაზე გადის, მაგრამ სხვებზე ვერდება.

დაამატეთ პლაგინი თქვენს `build.gradle.kts`-ში:

```kotlin
plugins {
    id("org.gradle.test-retry") version "1.6.2"
}

tasks.test {
    retry {
        maxRetries = 3
        maxFailures = 5
        failOnPassedAfterRetry = false
    }
}
```

![არასტაბილური სატესტო შემთხვევის დეტალები](/images/guides/features/test-insights/flaky-test-case-detail.png)

### ჯვარედინი გაშვებების აღმოჩენა {#cross-run-detection}

ტესტების ხელახლა გაშვების გარეშეც, Tuist-ს შეუძლია არასტაბილური ტესტების აღმოჩენა იმავე კომიტზე და იმავე Gradle პროექტზე სხვადასხვა CI გაშვების შედეგების შედარებით. თუ ტესტი ერთ CI გაშვებაზე გადის, მაგრამ იმავე კომიტისა და პროექტისთვის სხვა გაშვებაზე ვერდება, ჩავარდნილი შესრულება არასტაბილურად მონიშნება.

Gradle პროექტი შედარების გასაღების ნაწილია, რადგან ერთი და იგივე ტესტი შეიძლება განსხვავებულად მოიქცეს სხვადასხვა პროექტში — მაგალითად, საერთო სატესტო კლასი, რომელიც სხვადასხვა დამოკიდებულებებით კომპილირდება ან სხვა მოდულის ფიქსტურაზე გადის. ერთი და იმავე კომიტის ორი გაშვება სხვადასხვა Gradle პროექტებზე განიხილება როგორც ცალკე შესრულების ვარიანტები და ერთმანეთს არასტაბილურად არ მონიშნავენ.

ეს განსაკუთრებით სასარგებლოა იმ არასტაბილური ტესტების დასაჭერად, რომლებიც საკმარისად თანმიმდევრულად არ ვერდებიან, რომ ხელახლა გაშვებამ დაიჭიროს, მაგრამ მაინც იწვევენ პერიოდულ CI ჩავარდნებს.

## არასტაბილური ტესტების კარანტინში მოქცევა {#quarantining}

<!-- @snippet: ./_quarantine-intro -->

კარანტინში მოქცეული ტესტი ერთ-ერთ ორ რეჟიმშია:

- **ჩუმად**: ტესტი მაინც გადის, მაგრამ პლაგინი აყენებს `ignoreFailures = true` და ბილდს ხელახლა აგდებს მხოლოდ არა-კარანტინული ჩავარდნებისას. ჩავარდნები მაინც კვებავს არასტაბილური ტესტების დეტექტორს, ამიტომ შეგიძლიათ აკვირდეთ ტესტს ბილდის გაწყვეტის გარეშე. აირჩიეთ ეს იმ ტესტისთვის, რომელსაც აქტიურად იკვლევთ.
- **გამოტოვებული**: პლაგინი ფილტრავს ტესტს Gradle-ის `excludeTestsMatching`-ის მეშვეობით, ამიტომ ის არასდროს იწყება. ის არ წარმოქმნის ახალ შედეგებს და ქრება არასტაბილური ტესტების დაფიდან, სანამ ხელახლა არ ჩართავთ. აირჩიეთ ეს, როცა ტესტი გაფუჭებულია, ნელია ან იმდენად მუდმივად არასტაბილური, რომ მისი გაშვება უბრალოდ CI წუთების ფლანგვაა.

<!-- @snippet: ./_quarantined-passing -->

### კარანტინის ჩართვა {#enabling-quarantine}

კარანტინი **ავტომატურად ჩართულია CI-ზე** (როდესაც `CI` გარემოს ცვლადია დაყენებული) და გამორთულია ლოკალური ბილდებისთვის. პლაგინი იღებს კარანტინში მოქცეული ტესტების სიას Tuist სერვერიდან ყოველი სატესტო ამოცანის წინ; ჩუმად მყოფი ტესტები ჩვეულებრივად გადის და მათი ჩავარდნები ინიღბება, გამოტოვებული ტესტები ფილტრდება.

შეგიძლიათ აშკარად აკონტროლოთ ეს თქვენს `settings.gradle.kts`-ში:

```kotlin
tuist {
    testQuarantine {
        enabled = true  // or false to disable
    }
}
```

როდესაც `enabled` არ არის დაყენებული, ნაგულისხმევად არის ავტო-აღმოჩენა: ჩართულია CI-ზე, გამორთულია ლოკალურად.

## ახალი ტესტების სტრეს-ტესტირება {#stress-testing-new-tests}

<!-- @snippet: ./_stress-intro -->

სატესტო შემთხვევა ახლად ითვლება, თუ ის ბოლო 90 დღის განმავლობაში არ გაშვებულა CI-ზე პროექტის ნაგულისხმევ შტოზე, ან კომიტზე, რომელიც შემდეგ მასზე მოხვდა. მერჯის რიგით, რიგის მიერ გაშვებული სატესტო შემთხვევა ცნობილი ხდება მას შემდეგ, რაც რიგის კომიტი მოხვდება, და რჩება ახალი, თუ რიგი მას გამოტოვებს. კომიტები შეესაბამება <.localized_link href="/guides/features/test-insights/gradle#git-history">Git ისტორიის</.localized_link> მეშვეობით, რომელსაც Tuist აგროვებს CI-ზე.

<!-- @snippet: ./_stress-modes -->

განაცხადეთ ეს `settings.gradle.kts`-ში, ან დააყენეთ `TUIST_TEST_STRESS_NEW_TESTS` რეჟიმის CI არხის მიხედვით შესაცვლელად:

```kotlin
tuist {
    stressNewTests {
        mode = "report" // or "enforce"
    }
}
```

კარანტინისგან განსხვავებით, კარიბჭეს არ აქვს CI-ის გათვალისწინებით ნაგულისხმევი. `mode`-ის დაყენების გარეშე ის არსად გადის.

<!-- @snippet: ./_stress-reruns -->

ყოველი ხელახლა გაშვება არის ჩაშენებული Gradle ბილდი, რომელიც ფილტრულია მხოლოდ იმ ერთ სატესტო შემთხვევაზე, ამიტომ ყოველ ხელახლა გაშვებას აქვს ახალი სატესტო JVM.
