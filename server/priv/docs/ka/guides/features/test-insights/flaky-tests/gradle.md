# Gradle-ის არასტაბილური ტესტები {#gradle-flaky-tests}

არასტაბილური ტესტებია ისეთი ტესტები, რომლებიც ერთი და იმავე კოდზე რამდენჯერმე გაშვებისას სხვადასხვა შედეგს (წარმატება ან ჩავარდნა) იძლევიან. ისინი ამცირებენ ნდობას თქვენი ტესტების ნაკრების მიმართ და ფუჭად ხარჯავენ დეველოპერების დროს ცრუ ჩავარდნების გამოკვლევაში. Tuist ავტომატურად აღმოაჩენს არასტაბილურ ტესტებს და გეხმარებათ მათ თვალყურის დევნაში.

![არასტაბილური ტესტების გვერდი](/images/guides/features/test-insights/flaky-tests-page.png)

## როგორ მუშაობს არასტაბილურობის აღმოჩენა {#how-it-works}

Tuist არასტაბილურ ტესტებს ორი გზით აღმოაჩენს:

### ტესტების ხელახალი გაშვება {#test-retries}

როდესაც ტესტებს ხელახალი გაშვების ფუნქციით აწარმოებთ, Tuist აანალიზებს თითოეული მცდელობის შედეგებს. თუ ტესტი ზოგიერთ მცდელობაზე ვარდება, მაგრამ სხვებზე წარმატებით სრულდება, ის არასტაბილურად მონიშნება.

შეგიძლიათ გამოიყენოთ [Test Retry პლაგინი](https://github.com/gradle/test-retry-gradle-plugin) ან მსგავსი მექანიზმი ჩავარდნილი ტესტების ხელახლა გასაშვებად. Tuist აღმოაჩენს ტესტებს, რომლებიც ზოგიერთ მცდელობაზე წარმატებულია, მაგრამ სხვებზე ვარდება.

დაამატეთ პლაგინი თქვენს `build.gradle.kts`-ში:

```kotlin
plugins {
    id("org.gradle.test-retry") version "1.6.2"
}

tasks.test {
    retry {
        maxRetries = 3
        maxFailures = 5
        failOnPassedAfterRetry = false
    }
}
```

### გაშვებებს შორის აღმოჩენა {#cross-run-detection}

ტესტების ხელახალი გაშვების გარეშეც, Tuist-ს შეუძლია აღმოაჩინოს არასტაბილური ტესტები იმავე კომიტზე და იმავე Gradle პროექტზე სხვადასხვა CI გაშვებების შედეგების შედარებით. თუ ტესტი ერთ CI გაშვებაზე წარმატებულია, მაგრამ იმავე კომიტისა და პროექტისთვის სხვა გაშვებაზე ვარდება, ორივე გაშვება არასტაბილურად მონიშნება.

Gradle პროექტი შედარების გასაღების ნაწილია, რადგან ერთი და იგივე ტესტი შეიძლება განსხვავებულად იქცეოდეს სხვადასხვა პროექტში — მაგალითად, საერთო სატესტო კლასი, რომელიც სხვადასხვა დამოკიდებულებებით კომპილირდება ან სხვა მოდულის ფიქსტურაზე გადის. ერთი და იმავე კომიტის ორი გაშვება სხვადასხვა Gradle პროექტებზე განიხილება როგორც ცალკე შესრულების ვარიანტები და ერთმანეთს არასტაბილურად არ მონიშნავენ.

ეს განსაკუთრებით სასარგებლოა იმ არასტაბილური ტესტების დასაჭერად, რომლებიც საკმარისად თანმიმდევრულად არ ვარდებიან, რათა ხელახალი გაშვებით აღმოჩენილიყვნენ, მაგრამ მაინც იწვევენ პერიოდულ CI ჩავარდნებს.

## არასტაბილური ტესტების მართვა {#managing-flaky-tests}

### ავტომატური გასუფთავება

აღმოჩენა და გასუფთავება ხდება პროექტზე **ავტომატიზაციის შეტყობინების** მეშვეობით. ყოველ პროექტს აქვს ნაგულისხმევი „არასტაბილური ტესტების აღმოჩენის“ ავტომატიზაცია, რომლის *ტრიგერი* ტესტს არასტაბილურად მონიშნავს, ხოლო *აღდგენა* ხსნის ნიშანს, როდესაც ტესტი გადალახავს მითითებულ აღდგენის ფანჯარას (ნაგულისხმევი **14 დღე**) ხელახალი ტრიგერის გარეშე. შეცვალეთ ის **პარამეტრები → ავტომატიზაციები**-ში, რათა შეცვალოთ აღდგენის ფანჯარა, შეცვალოთ აღდგენის ქმედებები (მაგ., ასევე მოხსნათ კარანტინი) ან სრულად გათიშოთ აღდგენა, რათა ტესტები არასტაბილურად დარჩეს მონიშნული, სანამ ხელით არ გაასუფთავებთ.

### ხელით მართვა

შეგიძლიათ ხელით მონიშნოთ ან მოხსნათ ტესტების არასტაბილურობა სატესტო შემთხვევის დეტალების გვერდიდან. ეს სასარგებლოა, როდესაც:
- გსურთ აღიაროთ ცნობილი არასტაბილური ტესტი, სანამ მის გამოსწორებაზე მუშაობთ
- ტესტი არასწორად იყო მონიშნული ინფრასტრუქტურის პრობლემების გამო

## არასტაბილური ტესტების კარანტინში მოქცევა {#quarantining}

კარანტინი იზოლირებს არასტაბილურ ტესტს, რათა მან არ დაბლოკოს CI, სანამ მას ასწორებთ. ნაგულისხმევად ეს არის **ხელით შესრულებადი ქმედება** — თქვენ ათავსებთ კარანტინში, ხსნით კარანტინს და ცვლით რეჟიმებს დაფის სატესტო შემთხვევის დეტალების გვერდიდან — მაგრამ ასევე შეგიძლიათ ჩართოთ ის **ავტომატიზაციის შეტყობინებაში** **პარამეტრები → ავტომატიზაციები**-ში, რათა ტესტი ავტომატურად იყოს დახშობილი (ან გამოტოვებული), როდესაც ის გადალახავს არასტაბილურობის ზღვარს, და მოხსნილი იყოს კარანტინიდან, როდესაც აღდგება. ყოველი გადასვლა, ხელით თუ ავტომატურად, ფიქსირდება სატესტო შემთხვევის აუდიტის ჟურნალში.

კარანტინში მყოფი ტესტი ერთ-ერთ ორ რეჟიმშია:

- **დახშობილი**: ტესტი მაინც გადის, მაგრამ პლაგინი აყენებს `ignoreFailures = true` და ბილდს ხელახლა აგდებს მხოლოდ არაკარანტინირებული ჩავარდნების შემთხვევაში. ჩავარდნები მაინც კვებავს არასტაბილური ტესტების დეტექტორს, ასე რომ, შეგიძლიათ აკვირდეთ ტესტს ბილდის გაწყვეტის გარეშე. აირჩიეთ ეს იმ ტესტისთვის, რომელსაც აქტიურად იკვლევთ.
- **გამოტოვებული**: პლაგინი ფილტრავს ტესტს Gradle-ის `excludeTestsMatching`-ის მეშვეობით, ასე რომ, ის საერთოდ არ იწყება. ის არ იძლევა ახალ შედეგებს და ქრება არასტაბილური ტესტების დაფიდან, სანამ ხელახლა არ ჩართავთ. აირჩიეთ ეს, როდესაც ტესტი გაფუჭებულია, ნელია, ან იმდენად მუდმივად არასტაბილურია, რომ მისი გაშვება უბრალოდ ფუჭად ხარჯავს CI წუთებს.

### რატომ შეიძლება კარანტინში მყოფი ტესტები წარმატებულად გამოჩნდნენ {#quarantined-passing}

- **დახშობილი ტესტები** მაინც სრულდება. დახშობილი ტესტი, რომელიც ვარდება, ფიქსირდება როგორც **ჩავარდნილი** სატესტო შემთხვევის გაშვებაზე და მონიშნულია როგორც არასტაბილური — ტესტის სტატუსი არ გადაიწერება. რაც გადაიწერება, არის **საერთო ტესტების გაშვება**: თუ გაშვებაში ყოველი ჩავარდნილი სატესტო შემთხვევა დახშობილია, გაშვება მთლიანად მოიხსენიება როგორც წარმატებული, ასე რომ, დახშობილი ჩავარდნები არ წყვეტენ CI-ს.
- **გამოტოვებული ტესტები** საერთოდ არ გადის, ასე რომ, დაფა აჩვენებს ტესტის ბოლო რეალური შესრულების სტატუსს — ეს სნეპშოტი შეიძლება კვირების ძველი იყოს.

### კარანტინის ჩართვა {#enabling-quarantine}

კარანტინი **ავტომატურად ჩართულია CI-ზე** (როდესაც `CI` გარემოს ცვლადი დაყენებულია) და გათიშულია ლოკალური ბილდებისთვის. პლაგინი იღებს კარანტინში მყოფი ტესტების სიას Tuist სერვერიდან ყოველი სატესტო ამოცანის წინ; დახშობილი ტესტები ჩვეულებრივად გადის და მათი ჩავარდნები იფარება, გამოტოვებული ტესტები ფილტრდება.

შეგიძლიათ აშკარად მართოთ ეს თქვენს `settings.gradle.kts`-ში:

```kotlin
tuist {
    testQuarantine {
        enabled = true  // or false to disable
    }
}
```

როდესაც `enabled` არ არის დაყენებული, ნაგულისხმევად არის ავტო-აღმოჩენა: ჩართულია CI-ზე, გათიშულია ლოკალურად.

## ახალი ტესტების სტრეს-ტესტირება {#stress-testing-new-tests}

სტრესის კარიბჭე ხელახლა აწარმოებს თქვენი ბრენჩის მიერ დამატებულ სატესტო შემთხვევებს, თითოეულს რამდენჯერმე ახალ პროცესში, და აცნობებს იმას, რაც არასტაბილური აღმოჩნდება. თქვენ ხედავთ ახალ არასტაბილურ ტესტს იმ pull request-ზე, რომელმაც ის შემოიტანა, არა კვირების შემდეგ.

სატესტო შემთხვევა ახლად ითვლება, თუ ის ბოლო 90 დღის განმავლობაში არ გაშვებულა CI-ზე პროექტის ნაგულისხმევ ბრენჩზე, ან კომიტზე, რომელიც მას შემდეგ მასში ჩაერთო. შერწყმის რიგით, რიგის მიერ გაშვებული სატესტო შემთხვევა ცნობილი ხდება, როდესაც რიგის კომიტი ჩაერთვება, და რჩება ახლად, თუ რიგი მას ტოვებს. კომიტები შეესაბამება <.localized_link href="/guides/features/test-insights/gradle#git-history">Git ისტორიას</.localized_link>, რომელსაც Tuist აგროვებს CI-ზე.

### მისი ჩართვა

კარიბჭე ნაგულისხმევად გამორთულია. დააყენეთ რეჟიმი:

- **`report`**: აფრთხილებს ყოველ არასტაბილურ სატესტო შემთხვევაზე. გაშვება მაინც სრულდება თავისი შედეგით.
- **`enforce`**: არასტაბილური სატესტო შემთხვევა აგდებს გაშვებას, იმავე exit code-ით, რაც ჩავარდნილ ტესტს.

დაიწყეთ `report`-ით რამდენიმე კვირის განმავლობაში, რომ ნახოთ, რას დაბლოკავდა `enforce`.

განაცხადეთ ის `settings.gradle.kts`-ში, ან დააყენეთ `TUIST_TEST_STRESS_NEW_TESTS`, რათა შეცვალოთ რეჟიმი თითოეული CI არხისთვის:

```kotlin
tuist {
    stressNewTests {
        mode = "report" // or "enforce"
    }
}
```

კარანტინისგან განსხვავებით, კარიბჭეს არ აქვს CI-ზე მორგებული ნაგულისხმევი პარამეტრი. `mode`-ის დაყენების გარეშე ის არსად გაეშვება.

### რამდენჯერ მეორდება თითოეული ტესტი

ეს დამოკიდებულია იმაზე, თუ რამდენ ხანს გაგრძელდა სატესტო შემთხვევა პირველ გაშვებაზე:

| პირველი გაშვება | განმეორებები |
| --- | --- |
| 5 წმ-მდე | 10 |
| 10 წმ-მდე | 5 |
| 30 წმ-მდე | 3 |
| 5 წთ-მდე | 2 |
| 5 წთ-ზე მეტი | არ მეორდება |

ყოველი განმეორება არის ჩაშენებული Gradle ბილდი, რომელიც ფილტრავს მხოლოდ ამ ერთ სატესტო შემთხვევას, ამიტომ ყოველ განმეორებას ენიჭება ახალი სატესტო JVM. გაშვება ჩერდება 200 სატესტო შემთხვევის ან 10 წუთის შემდეგ, იმის მიხედვით, რომელი ლიმიტი დადგება პირველი, და მიუთითებს, რომელ ლიმიტს მიაღწია.

### როდესაც კარიბჭე არ ეშვება

- პირველი გაშვება უკვე ჩავარდა. ჯერ შეასწორეთ ეს ტესტები.
- პროექტს არ აქვს ნაგულისხმევი ბრენჩი, ან მასზე ჯერ არაფერი გაშვებულა CI-ში.
- პროექტის სატესტო შემთხვევების 30%-ზე მეტი ახლად გამოიყურება. ამდენის განმეორებით გაშვება უფრო დიდ დროს წაართმევდა, ვიდრე ღირს. მოელით ამას პროექტზე, რომელიც ახლახანს დაიწყო Tuist-თან მონაცემების გაზიარება, ან სახელის ცვლილების შემდეგ, რამაც ბევრი ტესტი ერთდროულად გადაიტანა.

## არასტაბილური და კარანტინში მყოფი მდგომარეობის მოთხოვნა {#querying}

### CLI

`tuist test case` ბრძანებების ხე აჩვენებს ყველაფერს, რასაც Tuist აკვირდება სატესტო შემთხვევის შესახებ:

```sh
tuist test case list --flaky                       # only flaky test cases
tuist test case list --quarantined                 # only muted or skipped test cases
tuist test case show <test_case_id>                # detail: flakiness rate, last status, run counts
tuist test case events <test_case_id>              # audit log: marked_flaky, muted, skipped, ...
tuist test case run list <test_case_id>            # run history with status and duration
tuist test case run show <test_case_run_id>        # single run, including failure breakdown
```

ყველა მათგანი იღებს `--json`-ს სკრიპტებისთვის.

### REST API

იგივე მონაცემები ხელმისაწვდომია HTTP-ით — იხილეთ [სატესტო შემთხვევების endpoint-ები](https://tuist.dev/api/docs#tag/test-cases) API ცნობარში მარშრუტების, ფილტრების და პასუხის ველების სრული სიისთვის. სატესტო შემთხვევის მდგომარეობის შესაცვლელად (არასტაბილურად მონიშვნა ან მონიშვნის მოხსნა, ჩუმად გაშვება, გამოტოვება), გაგზავნეთ `PATCH /api/projects/{account_handle}/{project_handle}/tests/test-cases/{test_case_id}` `is_flaky`-ით ან `state`-ით. იგივე ცვლილება ხელმისაწვდომია როგორც `tuist test case update`, ასევე `update_test_case` Model Context Protocol ინსტრუმენტის სახით.
