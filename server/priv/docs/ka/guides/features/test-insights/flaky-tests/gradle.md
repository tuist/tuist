# Gradle-ის არასტაბილური ტესტები {#gradle-flaky-tests}

არასტაბილური ტესტებია ისეთი ტესტები, რომლებიც ერთი და იმავე კოდით რამდენჯერმე გაშვებისას სხვადასხვა შედეგს (წარმატება ან ჩავარდნა) იძლევიან. ისინი არღვევენ ნდობას თქვენი ტესტების ნაკრადის მიმართ და ფუჭად ხარჯავენ დეველოპერების დროს ცრუ ჩავარდნების გამოკვლევაზე. Tuist ავტომატურად აღმოაჩენს არასტაბილურ ტესტებს და გეხმარებათ მათ თვალყურის დევნაში.

![არასტაბილური ტესტების გვერდი](/images/guides/features/test-insights/flaky-tests-page.png)

## როგორ მუშაობს არასტაბილურობის აღმოჩენა {#how-it-works}

Tuist არასტაბილურ ტესტებს ორი გზით აღმოაჩენს:

### ტესტების ხელახალი გაშვება {#test-retries}

როცა ტესტებს ხელახალი გაშვების ფუნქციით ასრულებთ, Tuist ანალიზს უკეთებს თითოეული მცდელობის შედეგებს. თუ ტესტი ზოგიერთ მცდელობაზე ვარდება, მაგრამ სხვებზე გადის, ის მონიშნულია როგორც არასტაბილური.

შეგიძლიათ გამოიყენოთ [Test Retry პლაგინი](https://github.com/gradle/test-retry-gradle-plugin) ან მსგავსი მექანიზმი ჩავარდნილი ტესტების ხელახლა გასაშვებად. Tuist აღმოაჩენს ტესტებს, რომლებიც ზოგიერთ მცდელობაზე გადის, მაგრამ სხვებზე ვარდება.

დაამატეთ პლაგინი თქვენს `build.gradle.kts`-ში:

```kotlin
plugins {
    id("org.gradle.test-retry") version "1.6.2"
}

tasks.test {
    retry {
        maxRetries = 3
        maxFailures = 5
        failOnPassedAfterRetry = false
    }
}
```

![არასტაბილური სატესტო შემთხვევის დეტალები](/images/guides/features/test-insights/flaky-test-case-detail.png)

### გაშვებებს შორის აღმოჩენა {#cross-run-detection}

ტესტების ხელახალი გაშვების გარეშეც, Tuist-ს შეუძლია აღმოაჩინოს არასტაბილური ტესტები იმავე კომიტზე და იმავე Gradle პროექტზე სხვადასხვა CI გაშვების შედეგების შედარებით. თუ ტესტი ერთ CI გაშვებაზე გადის, მაგრამ იმავე კომიტისა და პროექტისთვის სხვა გაშვებაზე ვარდება, ორივე გაშვება მონიშნულია როგორც არასტაბილური.

Gradle პროექტი შედარების გასაღების ნაწილია, რადგან ერთი და იმავე ტესტი შეიძლება განსხვავებულად იქცეოდეს სხვადასხვა პროექტში — მაგალითად, საერთო სატესტო კლასი, რომელიც კომპილირებულია სხვადასხვა დამოკიდებულებით ან გაშვებულია სხვა მოდულის ფიქსტურაზე. ერთი და იმავე კომიტის ორი გაშვება სხვადასხვა Gradle პროექტებზე განიხილება როგორც შესრულების ცალკე ვარიანტები და ერთმანეთს არასტაბილურად არ მონიშნავენ.

ეს განსაკუთრებით სასარგებლოა იმ არასტაბილური ტესტების დასაფიქსირებლად, რომლებიც არ ვარდებიან საკმარისად თანმიმდევრულად, რათა ხელახალი გაშვებით დაფიქსირდნენ, მაგრამ მაინც იწვევენ პერიოდულ CI ჩავარდნებს.

## არასტაბილური ტესტების მართვა {#managing-flaky-tests}

### ავტომატური გასუფთავება

აღმოჩენა და გასუფთავება ხდება პროექტზე **ავტომატიზაციის შეტყობინების** მეშვეობით. ყოველ პროექტს აქვს ნაგულისხმევი „არასტაბილური ტესტების აღმოჩენის“ ავტომატიზაცია, რომლის *ტრიგერი* ტესტს არასტაბილურად მონიშნავს, ხოლო *აღდგენა* ხსნის ნიშანს, როცა ტესტი გაივლის კონფიგურირებულ აღდგენის ფანჯარას (ნაგულისხმევი **14 დღე**) ხელახალი ტრიგერის გარეშე. შეასწორეთ ის **პარამეტრები → ავტომატიზაციები**-ში, რათა შეცვალოთ აღდგენის ფანჯარა, შეცვალოთ აღდგენის ქმედებები (მაგ., ასევე მოხსნა კარანტინიდან) ან სრულიად გათიშოთ აღდგენა, რათა ტესტები დარჩნენ არასტაბილურად მონიშნული, სანამ ხელით არ გაასუფთავებთ.

### ხელით მართვა

ასევე შეგიძლიათ ხელით მონიშნოთ ან მოხსნათ ტესტები როგორც არასტაბილური სატესტო შემთხვევის დეტალურ გვერდიდან. ეს სასარგებლოა, როცა:
- გსურთ აღიაროთ ცნობილი არასტაბილური ტესტი, სანამ მის გამოსწორებაზე მუშაობთ
- ტესტი არასწორად იყო მონიშნული ინფრასტრუქტურის პრობლემების გამო

## არასტაბილური ტესტების კარანტინში მოთავსება {#quarantining}

კარანტინი იზოლირებს არასტაბილურ ტესტს, რათა მან არ დაბლოკოს CI, სანამ მას შეასწორებთ. ნაგულისხმევად ეს არის **ხელით შესრულებადი ქმედება** — თქვენ ათავსებთ კარანტინში, ხსნით კარანტინიდან და ცვლით რეჟიმებს დაფის სატესტო შემთხვევის დეტალურ გვერდიდან — მაგრამ ასევე შეგიძლიათ მიუერთოთ ის **ავტომატიზაციის შეტყობინებას** **პარამეტრები → ავტომატიზაციები**-ში, რათა ტესტი ავტომატურად დადუმდეს (ან გამოტოვებულ იქნას), როცა გადალახავს არასტაბილურობის ზღვარს, და ამოღებულ იქნას კარანტინიდან, როცა აღდგება. ყოველი გადასვლა, ხელით თუ ავტომატური, იწერება სატესტო შემთხვევის აუდიტის ჟურნალში.

ნაგულისხმევად, აღდგენა ელოდება, სანამ ტრიგერის პირობა აღარ შესრულდება, ამიტომ ტესტი რჩება კარანტინში, სანამ მისი ძველი არასტაბილური გაშვებები არ დატოვებენ ტრიგერის ფანჯარას. უფრო სწრაფი აღდგენისთვის, დააყენეთ **აღდგენა, როცა** მნიშვნელობაზე **ახალი არასტაბილური გაშვებები არ არის**: ტესტი აღდგება, როცა აღდგენის ფანჯარა (დღეები ან გაშვებები) გაივლის ახალი არასტაბილური გაშვების გარეშე, ყოველი ახალი არასტაბილური გაშვება ხელახლა იწყებს ამ ლოდინს და აღდგენის შემდეგ მხოლოდ ახალი არასტაბილური გაშვება თავსდება მას კარანტინში.

კარანტინში მოთავსებული ტესტი არის ერთ-ერთ ორ რეჟიმში:

- **დადუმებული**: ტესტი მაინც გადის, მაგრამ პლაგინი აყენებს `ignoreFailures = true` და ბილდი ხელახლა ვარდება მხოლოდ არა-კარანტინული ჩავარდნების გამო. ჩავარდნები მაინც კვებავს არასტაბილური ტესტების დეტექტორს, ამიტომ შეგიძლიათ აკვირდეთ ტესტს ბილდის გატეხვის გარეშე. აირჩიეთ ეს იმ ტესტისთვის, რომელსაც აქტიურად იკვლევთ.
- **გამოტოვებული**: პლაგინი ფილტრავს ტესტს Gradle-ის `excludeTestsMatching`-ის მეშვეობით, ამიტომ ის საერთოდ არ იწყება. ის არ წარმოქმნის ახალ შედეგებს და ქრება არასტაბილური ტესტების დაფიდან, სანამ ხელახლა არ ჩართავთ. აირჩიეთ ეს, როცა ტესტი გატეხილია, ნელია ან იმდენად მუდმივად არასტაბილურია, რომ მისი გაშვება უბრალოდ ფუჭად ხარჯავს CI წუთებს.

### რატომ შეიძლება კარანტინში მოთავსებული ტესტები გამოჩნდნენ როგორც წარმატებული {#quarantined-passing}

- **დადუმებული ტესტები** მაინც სრულდება. დადუმებული ტესტი, რომელიც ვარდება, იწერება როგორც **ჩავარდნილი** სატესტო შემთხვევის გაშვებაზე და მონიშნულია როგორც არასტაბილური — თითოეული ტესტის სტატუსი არ იცვლება. რაც იცვლება, არის **მთლიანი ტესტების გაშვება**: თუ გაშვებაში ყოველი ჩავარდნილი სატესტო შემთხვევა დადუმებულია, გაშვება მთლიანად ითვლება წარმატებულად, ამიტომ დადუმებული ჩავარდნები არ ტეხენ CI-ს.
- **გამოტოვებული ტესტები** საერთოდ არ გადის, ამიტომ დაფა აჩვენებს სტატუსს ტესტის ბოლო რეალური შესრულებიდან — ეს სნაპშოტი შეიძლება კვირების წინანდელი იყოს.

### კარანტინის ჩართვა {#enabling-quarantine}

კარანტინი **ავტომატურად ჩართულია CI-ზე** (როცა `CI` გარემოს ცვლადი დაყენებულია) და გამორთულია ადგილობრივი ბილდებისთვის. პლაგინი იღებს კარანტინში მოთავსებული ტესტების სიას Tuist სერვერიდან ყოველი სატესტო ამოცანის წინ; დადუმებული ტესტები ჩვეულებრივად გადის და მათი ჩავარდნები იფარება, გამოტოვებული ტესტები ფილტრდება.

შეგიძლიათ აშკარად მართოთ ეს თქვენს `settings.gradle.kts`-ში:

```kotlin
tuist {
    testQuarantine {
        enabled = true  // or false to disable
    }
}
```

როცა `enabled` არ არის დაყენებული, ნაგულისხმევია ავტო-აღმოჩენა: ჩართულია CI-ზე, გამორთულია ადგილობრივად.

## ახალი ტესტების სტრეს-ტესტირება {#stress-testing-new-tests}

სტრესის კარიბჭე ხელახლა ასრულებს სატესტო შემთხვევებს, რომლებსაც თქვენი ბრანჩი ამატებს, რამდენჯერმე თითოეულს ახალ პროცესში და აცნობებს იმას, რომელიც არასტაბილური აღმოჩნდება. ახალ არასტაბილურ ტესტს ხედავთ pull request-ზე, რომელმაც ის შემოიტანა, არა კვირების შემდეგ.

სატესტო შემთხვევა ითვლება ახლად, თუ ის ბოლო 90 დღის განმავლობაში არ გაშვებულა CI-ზე პროექტის ნაგულისხმევ ბრანჩზე ან კომიტზე, რომელიც მას შემდეგ მოხვდა იქ. შერწყმის რიგით, სატესტო შემთხვევა, რომელიც რიგმა გაუშვა, ცნობილია, როცა რიგის კომიტი მოხვდება, და რჩება ახალი, თუ რიგი მას ტოვებს. კომიტები შეესაბამება <.localized_link href="/guides/features/test-insights/gradle#git-history">Git ისტორიის</.localized_link> მეშვეობით, რომელსაც Tuist აგროვებს CI-ზე.

### მისი ჩართვა

კარიბჭე ნაგულისხმევად გამორთულია. დააყენეთ რეჟიმი:

- **`report`**: აფრთხილებს ყოველი არასტაბილური სატესტო შემთხვევის შესახებ. გაშვება მაინც სრულდება საკუთარი შედეგით.
- **`enforce`**: არასტაბილური სატესტო შემთხვევა აფერხებს გაშვებას, იგივე გამოსვლის კოდით, რაც ჩავარდნილ ტესტს.

დაიწყეთ `report`-ით რამდენიმე კვირის განმავლობაში, რათა ნახოთ, რას დაბლოკავდა `enforce`.

განაცხადეთ ის `settings.gradle.kts`-ში, ან დააყენეთ `TUIST_TEST_STRESS_NEW_TESTS`, რათა შეცვალოთ რეჟიმი თითოეული CI არხისთვის:

```kotlin
tuist {
    stressNewTests {
        mode = "report" // or "enforce"
    }
}
```

კარანტინისგან განსხვავებით, კარიბჭეს არ აქვს CI-ზე მორგებული ნაგულისხმევი პარამეტრი. თუ `mode` არ არის დაყენებული, ის არცერთ ადგილას არ მუშაობს.

### რამდენჯერ მეორდება თითოეული ტესტი

ეს დამოკიდებულია იმაზე, თუ რამდენი ხანი დასჭირდა სატესტო შემთხვევას პირველ გაშვებაზე:

| პირველი გაშვება | განმეორებები |
| --- | --- |
| 5 წმ-მდე | 10 |
| 10 წმ-მდე | 5 |
| 30 წმ-მდე | 3 |
| 5 წთ-მდე | 2 |
| 5 წთ-ზე მეტი | არ მეორდება |

ყოველი განმეორება არის ჩაშენებული Gradle ბილდი, რომელიც ფილტრავს მხოლოდ ამ ერთ სატესტო შემთხვევას, ამიტომ ყოველ განმეორებას აქვს ახალი ტესტის JVM. გაშვება ჩერდება 200 სატესტო შემთხვევის ან 10 წუთის შემდეგ, იმის მიხედვით, თუ რომელი ზღვარი მიიღწევა პირველად, და მიუთითებს, თუ რომელ ზღვარს მიაღწია.

### როდესაც კარიბჭე არ მუშაობს

- პირველი გაშვება უკვე ჩავარდა. ჯერ შეასწორეთ ეს ტესტები.
- პროექტს არ აქვს ნაგულისხმევი ბრანჩი, ან მასზე ჯერ არაფერი გაშვებულა CI-ზე.
- პროექტის სატესტო შემთხვევების 30%-ზე მეტი ახალი ჩანს. ამდენის განმეორებით გაშვებას მეტი დრო დასჭირდება, ვიდრე სასარგებლოა. ელოდეთ ამას პროექტზე, რომელიც ახლახანს დაიწყო Tuist-თან ანგარიშგება, ან გადასახელების შემდეგ, როცა ბევრი ტესტი ერთდროულად გადაადგილდა.

## არასტაბილური და კარანტინში მყოფი მდგომარეობის მოთხოვნა {#querying}

### CLI

`tuist test case` ბრძანებების ხე აჩვენებს ყველაფერს, რასაც Tuist აკონტროლებს სატესტო შემთხვევის შესახებ:

```sh
tuist test case list --flaky                       # only flaky test cases
tuist test case list --quarantined                 # only muted or skipped test cases
tuist test case show <test_case_id>                # detail: flakiness rate, last status, run counts
tuist test case events <test_case_id>              # audit log: marked_flaky, muted, skipped, ...
tuist test case run list <test_case_id>            # run history with status and duration
tuist test case run show <test_case_run_id>        # single run, including failure breakdown
```

ყველა ეს იღებს `--json`-ს სკრიპტინგისთვის.

### REST API

იგივე მონაცემები ხელმისაწვდომია HTTP-ის მეშვეობით — იხილეთ [სატესტო შემთხვევების ბოლოწერტილები](https://tuist.dev/api/docs#tag/test-cases) API ცნობარში სრული სიისთვის მარშრუტების, ფილტრების და პასუხის ველების შესახებ. სატესტო შემთხვევის მდგომარეობის შესაცვლელად (არასტაბილურად მონიშვნა ან მოხსნა, დაყუჩება, გამოტოვება), გაგზავნეთ `PATCH /api/projects/{account_handle}/{project_handle}/tests/test-cases/{test_case_id}` `is_flaky` ან `state` პარამეტრებით. იგივე ცვლილება ხელმისაწვდომია როგორც `tuist test case update`, ასევე `update_test_case` Model Context Protocol ინსტრუმენტის სახით.
