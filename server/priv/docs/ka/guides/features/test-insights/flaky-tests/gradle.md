# Gradle-ის არასტაბილური ტესტები {#gradle-flaky-tests}

არასტაბილური ტესტებია ისეთი ტესტები, რომლებიც ერთი და იმავე კოდით მრავალჯერ გაშვებისას სხვადასხვა შედეგს (წარმატება ან ჩავარდნა) აჩვენებენ. ისინი ამცირებენ ნდობას თქვენი ტესტების ნაკრადში და ფუჭად ხარჯავენ დეველოპერების დროს ყალბი ჩავარდნების გამოკვლევაზე. Tuist ავტომატურად აღმოაჩენს არასტაბილურ ტესტებს და გეხმარებათ მათ თვალყურის დევნაში დროთა განმავლობაში.

![არასტაბილური ტესტების გვერდი](/images/guides/features/test-insights/flaky-tests-page.png)

## როგორ მუშაობს არასტაბილურობის აღმოჩენა {#how-it-works}

Tuist არასტაბილურ ტესტებს ორი გზით აღმოაჩენს:

### ტესტების ხელახლა გაშვება {#test-retries}

როდესაც ტესტებს ხელახლა გაშვების ფუნქციონალით აშვებთ, Tuist აანალიზებს თითოეული მცდელობის შედეგებს. თუ ტესტი ზოგიერთ მცდელობაზე ვარდება, მაგრამ სხვებზე გადის, ის მონიშნულია როგორც არასტაბილური.

შეგიძლიათ გამოიყენოთ [Test Retry პლაგინი](https://github.com/gradle/test-retry-gradle-plugin) ან მსგავსი მექანიზმი ჩავარდნილი ტესტების ხელახლა გასაშვებად. Tuist აღმოაჩენს ტესტებს, რომლებიც ზოგიერთ მცდელობაზე გადის, მაგრამ სხვებზე ვარდება.

დაამატეთ პლაგინი თქვენს `build.gradle.kts`-ში:

```kotlin
plugins {
    id("org.gradle.test-retry") version "1.6.2"
}

tasks.test {
    retry {
        maxRetries = 3
        maxFailures = 5
        failOnPassedAfterRetry = false
    }
}
```

![არასტაბილური სატესტო შემთხვევის დეტალები](/images/guides/features/test-insights/flaky-test-case-detail.png)

### ჯვარედინი გაშვებების აღმოჩენა {#cross-run-detection}

ტესტების ხელახლა გაშვების გარეშეც, Tuist-ს შეუძლია აღმოაჩინოს არასტაბილური ტესტები სხვადასხვა CI გაშვებების შედეგების შედარებით ერთსა და იმავე კომიტზე და ერთსა და იმავე Gradle პროექტზე. თუ ტესტი ერთ CI გაშვებაზე გადის, მაგრამ იმავე კომიტისა და პროექტისთვის სხვა გაშვებაზე ვარდება, ორივე გაშვება მონიშნულია როგორც არასტაბილური.

Gradle პროექტი შედარების გასაღების ნაწილია, რადგან ერთი და იგივე ტესტი შეიძლება განსხვავებულად მოიქცეს სხვადასხვა პროექტში — მაგალითად, საერთო სატესტო კლასი, რომელიც კომპილირებულია სხვადასხვა დამოკიდებულებებით ან გაშვებულია სხვა მოდულის ფიქსტურაზე. ერთი და იმავე კომიტის ორი გაშვება სხვადასხვა Gradle პროექტებზე განიხილება როგორც ცალკე შესრულების ვარიანტები და ერთმანეთს არასტაბილურად არ მონიშნავენ.

ეს განსაკუთრებით სასარგებლოა იმ არასტაბილური ტესტების დასაფიქსირებლად, რომლებიც არ ვარდებიან საკმარისად თანმიმდევრულად, რომ ხელახლა გაშვებამ დაიჭიროს, მაგრამ მაინც იწვევენ პერიოდულ CI ჩავარდნებს.

## არასტაბილური ტესტების მართვა {#managing-flaky-tests}

### ავტომატური გასუფთავება

აღმოჩენა და გასუფთავება ხდება პროექტზე **ავტომატიზაციის შეტყობინების** მეშვეობით. თითოეულ პროექტს აქვს ნაგულისხმები „არასტაბილური ტესტების აღმოჩენის“ ავტომატიზაცია, რომლის *ტრიგერი* ტესტს არასტაბილურად მონიშნავს, ხოლო *აღდგენა* ასუფთავებს ნიშანს, როდესაც ტესტი გაივლის კონფიგურირებულ აღდგენის ფანჯარას (ნაგულისხმები **14 დღე**) ხელახალი ტრიგერის გარეშე. შეასწორეთ ის **პარამეტრები → ავტომატიზაციები**-ში, რათა შეცვალოთ აღდგენის ფანჯარა, შეცვალოთ აღდგენის ქმედებები (მაგ., ასევე კარანტინიდან ამოღება) ან სრულად გათიშოთ აღდგენა, რათა ტესტები დარჩნენ არასტაბილურად მონიშნული, სანამ ხელით არ გაასუფთავებთ.

### ხელით მართვა

ასევე შეგიძლიათ ხელით მონიშნოთ ან მოხსნათ ტესტები არასტაბილურად სატესტო შემთხვევის დეტალურ გვერდიდან. ეს სასარგებლოა, როდესაც:
- გსურთ აღიაროთ ცნობილი არასტაბილური ტესტი მისი გამოსწორების დროს
- ტესტი არასწორად იყო მონიშნული ინფრასტრუქტურის პრობლემების გამო

## არასტაბილური ტესტების კარანტინში მოქცევა {#quarantining}

კარანტინი იზოლირებს არასტაბილურ ტესტს, რათა მან არ დაბლოკოს CI, სანამ მას შეასწორებთ. ნაგულისხმევად ეს არის **ხელით შესრულებადი ქმედება** — თქვენ ათავსებთ კარანტინში, ამოღებთ კარანტინიდან და ცვლით რეჟიმებს დაფის სატესტო შემთხვევის დეტალურ გვერდიდან — მაგრამ ასევე შეგიძლიათ მიუბათ იგი **ავტომატიზაციის შეტყობინებას** **პარამეტრები → ავტომატიზაციები**-ში, რათა ტესტი ავტომატურად იყოს დახშული (ან გამოტოვებული), როდესაც გადალახავს არასტაბილურობის ზღვარს, და ამოღებული იქნას კარანტინიდან, როდესაც აღდგება. ყოველი გადასვლა, ხელით თუ ავტომატური, იწერება სატესტო შემთხვევის აუდიტის ჟურნალში.

კარანტინში მყოფი ტესტი არის ერთ-ერთ ორ რეჟიმში:

- **დახშული**: ტესტი მაინც გადის, მაგრამ პლაგინი აყენებს `ignoreFailures = true` და ბილდი ხელახლა ვარდება მხოლოდ არაკარანტინული ჩავარდნებისას. ჩავარდნები მაინც კვებავს არასტაბილური ტესტების დეტექტორს, ასე რომ შეგიძლიათ აკვირდებოდეთ ტესტს ბილდის გაფუჭების გარეშე. აირჩიეთ ეს იმ ტესტისთვის, რომელსაც აქტიურად იკვლევთ.
- **გამოტოვებული**: პლაგინი ფილტრავს ტესტს Gradle-ის `excludeTestsMatching`-ის მეშვეობით, ასე რომ ის საერთოდ არ იწყება. ის არ წარმოქმნის ახალ შედეგებს და ქრება არასტაბილური ტესტების დაფიდან, სანამ ხელახლა არ ჩართავთ. აირჩიეთ ეს, როდესაც ტესტი გაფუჭებულია, ნელია ან იმდენად მუდმივად არასტაბილური, რომ მისი გაშვება უბრალოდ ფუჭად ხარჯავს CI წუთებს.

### რატომ შეიძლება კარანტინში მყოფი ტესტები გამოჩნდნენ როგორც წარმატებული {#quarantined-passing}

- **დახშული ტესტები** მაინც სრულდება. დახშული ტესტი, რომელიც ვარდება, იწერება როგორც **ჩავარდნილი** სატესტო შემთხვევის გაშვებაზე და მონიშნულია როგორც არასტაბილური — ტესტის ინდივიდუალური სტატუსი არ გადაიწერება. რაც იცვლება, არის **მთლიანი ტესტების გაშვება**: თუ გაშვებაში ყოველი ჩავარდნილი სატესტო შემთხვევა დახშულია, მთლიანი გაშვება ითვლება წარმატებულად, ასე რომ დახშული ჩავარდნები არ აფუჭებენ CI-ს.
- **გამოტოვებული ტესტები** საერთოდ არ გადის, ასე რომ დაფა აგრძელებს ტესტის ბოლო რეალური შესრულების სტატუსის ჩვენებას — ეს სნაპშოტი შეიძლება კვირების წინანდელი იყოს.

### კარანტინის ჩართვა {#enabling-quarantine}

კარანტინი **ავტომატურად ჩართულია CI-ზე** (როდესაც `CI` გარემოს ცვლადი დაყენებულია) და გამორთულია ლოკალური ბილდებისთვის. პლაგინი იღებს კარანტინში მყოფი ტესტების სიას Tuist სერვერიდან ყოველი სატესტო ამოცანის წინ; დახშული ტესტები ჩვეულებრივად გადის და მათი ჩავარდნები ინიღბება, გამოტოვებული ტესტები ფილტრდება.

შეგიძლიათ აშკარად აკონტროლოთ ეს თქვენს `settings.gradle.kts`-ში:

```kotlin
tuist {
    testQuarantine {
        enabled = true  // or false to disable
    }
}
```

როდესაც `enabled` არ არის დაყენებული, ნაგულისხმევად არის ავტო-აღმოჩენა: ჩართულია CI-ზე, გამორთულია ლოკალურად.

## ახალი ტესტების სტრეს-ტესტირება {#stress-testing-new-tests}

სტრესის კარიბჭე ხელახლა აშვებს თქვენი ბრენჩის მიერ დამატებულ სატესტო შემთხვევებს, თითოეულს რამდენჯერმე ახალ პროცესში, და აცხობს იმას, რომლებიც არასტაბილური აღმოჩნდება. თქვენ ხედავთ ახალ არასტაბილურ ტესტს pull request-ზე, რომელმაც ის შემოიტანა, არა კვირების შემდეგ.

სატესტო შემთხვევა ითვლება ახლად, თუ ის ბოლო 90 დღის განმავლობაში არ გაშვებულა CI-ზე პროექტის ნაგულისხმევ ბრენჩზე, ან კომიტზე, რომელიც მას შემდეგ მოხვდა იქ. შერწყმის რიგით, რიგის მიერ გაშვებული სატესტო შემთხვევა ცნობილი ხდება, როდესაც რიგის კომიტი მოხვდება, და რჩება ახალი, თუ რიგი მას ტოვებს. კომიტები შეესაბამება <.localized_link href="/guides/features/test-insights/gradle#git-history">Git ისტორიის</.localized_link> მეშვეობით, რომელსაც Tuist აგროვებს CI-ზე.

### მისი ჩართვა

კარიბჭე ნაგულისხმევად გამორთულია. დააყენეთ რეჟიმი:

- **`report`**: აფრთხილებს ყოველ არასტაბილურ სატესტო შემთხვევაზე. გაშვება მაინც გადის თავისი შედეგის მიხედვით.
- **`enforce`**: არასტაბილური სატესტო შემთხვევა აფუჭებს გაშვებას, იმავე exit code-ით, რაც ჩავარდნილ ტესტს.

დაიწყეთ `report` რამდენიმე კვირით, რომ ნახოთ, რას დაბლოკავდა `enforce`.

განაცხადეთ ეს `settings.gradle.kts`-ში, ან დააყენეთ `TUIST_TEST_STRESS_NEW_TESTS`, რათა შეცვალოთ რეჟიმი თითოეული CI არხისთვის:

```kotlin
tuist {
    stressNewTests {
        mode = "report" // or "enforce"
    }
}
```

კარანტინისგან განსხვავებით, კარიბჭეს არ აქვს CI-ზე მორგებული ნაგულისხმევი პარამეტრი. `mode`-ის დაყენების გარეშე ის არცერთ ადგილას არ გაეშვება.

### რამდენჯერ ხდება თითოეული ტესტის ხელახლა გაშვება

ეს დამოკიდებულია იმაზე, თუ რამდენი დრო დასჭირდა სატესტო შემთხვევას პირველი გაშვებისას:

| პირველი გაშვება | ხელახალი გაშვებები |
| --- | --- |
| 5 წმ-მდე | 10 |
| 10 წმ-მდე | 5 |
| 30 წმ-მდე | 3 |
| 5 წთ-მდე | 2 |
| 5 წთ-ზე მეტი | არ ხდება ხელახლა გაშვება |

ყოველი ხელახალი გაშვება არის ჩაშენებული Gradle ბილდი, რომელიც ფილტრავს მხოლოდ ამ ერთ სატესტო შემთხვევას, ასე რომ ყოველ ხელახალ გაშვებას აქვს ახალი სატესტო JVM. გაშვება ჩერდება 200 სატესტო შემთხვევის ან 10 წუთის ზღვარზე, იმის მიხედვით, თუ რომელი დადგება პირველი, და მიუთითებს, რომელი ლიმიტი მიიღწია.

### როდესაც კარიბჭე არ ეშვება

- პირველი გაშვება უკვე ჩავარდა. ჯერ შეასწორეთ ეს ტესტები.
- პროექტს არ აქვს ნაგულისხმევი ბრენჩი, ან მასზე CI-ზე ჯერ არაფერი გაშვებულა.
- პროექტის სატესტო შემთხვევების 30%-ზე მეტი ახლად გამოიყურება. ამდენის ხელახლა გაშვებას მეტი დრო დასჭირდება, ვიდრე ღირს. ეს მოსალოდნელია პროექტზე, რომელიც ახლახანს დაიწყო Tuist-თან ანგარიშგება, ან სახელის ცვლილების შემდეგ, როდესაც ბევრი ტესტი ერთდროულად გადაადგილდება.

## არასტაბილური და კარანტინში მყოფი მდგომარეობის მოთხოვნა {#querying}

### CLI

`tuist test case` ბრძანებების ხე აჩვენებს ყველაფერს, რასაც Tuist აკონტროლებს სატესტო შემთხვევის შესახებ:

```sh
tuist test case list --flaky                       # only flaky test cases
tuist test case list --quarantined                 # only muted or skipped test cases
tuist test case show <test_case_id>                # detail: flakiness rate, last status, run counts
tuist test case events <test_case_id>              # audit log: marked_flaky, muted, skipped, ...
tuist test case run list <test_case_id>            # run history with status and duration
tuist test case run show <test_case_run_id>        # single run, including failure breakdown
```

ყველა მათგანი იღებს `--json` სკრიპტინგისთვის.

### REST API

იგივე მონაცემები ხელმისაწვდომია HTTP-ის მეშვეობით — იხილეთ [სატესტო შემთხვევების ბოლოწერტილები](https://tuist.dev/api/docs#tag/test-cases) API ცნობარში მარშრუტების, ფილტრების და პასუხის ველების სრული სიისთვის. სატესტო შემთხვევის მდგომარეობის შესაცვლელად (არასტაბილურად მონიშვნა ან მონიშვნის მოხსნა, დახშობა, გამოტოვება), გაგზავნეთ `PATCH /api/projects/{account_handle}/{project_handle}/tests/test-cases/{test_case_id}` `is_flaky` ან `state` პარამეტრებით. იგივე ცვლილება ხელმისაწვდომია როგორც `tuist test case update`, ასევე `update_test_case` Model Context Protocol ინსტრუმენტის სახით.
