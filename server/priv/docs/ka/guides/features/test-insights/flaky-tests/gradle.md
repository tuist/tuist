# Gradle-ის რხევადი ტესტები {#gradle-flaky-tests}

რხევადი ტესტები არის ტესტები, რომლებიც ერთი და იმავე კოდის რამდენჯერმე გაშვებისას სხვადასხვა შედეგს (წარმატება ან ჩავარდნა) აჩვენებენ. ისინი ამცირებენ ნდობას თქვენს ტესტების ნაკრებში და ფუჭად ხარჯავენ დეველოპერების დროს ცრუ ჩავარდნების გამოძიებაზე. Tuist ავტომატურად აღმოაჩენს რხევად ტესტებს და გეხმარებათ მათი თვალყურის დევნაში დროთა განმავლობაში.

![რხევადი ტესტების გვერდი](/images/guides/features/test-insights/flaky-tests-page.png)

## როგორ მუშაობს რხევადობის აღმოჩენა {#how-it-works}

Tuist რხევად ტესტებს ორი გზით აღმოაჩენს:

### ტესტების ხელახალი გაშვება {#test-retries}

როდესაც ტესტებს ხელახალი გაშვების ფუნქციით ასრულებთ, Tuist აანალიზებს თითოეული მცდელობის შედეგებს. თუ ტესტი ზოგიერთ მცდელობაზე ვარდება, მაგრამ სხვებზე გადის, ის რხევადად მონიშნება.

შეგიძლიათ გამოიყენოთ [Test Retry პლაგინი](https://github.com/gradle/test-retry-gradle-plugin) ან მსგავსი მექანიზმი ჩავარდნილი ტესტების ხელახლა გასაშვებად. Tuist აღმოაჩენს ტესტებს, რომლებიც ზოგიერთ მცდელობაზე გადის, მაგრამ სხვებზე ვარდება.

დაამატეთ პლაგინი თქვენს `build.gradle.kts`-ში:

```kotlin
plugins {
    id("org.gradle.test-retry") version "1.6.2"
}

tasks.test {
    retry {
        maxRetries = 3
        maxFailures = 5
        failOnPassedAfterRetry = false
    }
}
```

### ჯვარედინი გაშვებების აღმოჩენა {#cross-run-detection}

ტესტების ხელახალი გაშვების გარეშეც, Tuist-ს შეუძლია რხევადი ტესტების აღმოჩენა იმავე კომიტზე და იმავე Gradle პროექტზე სხვადასხვა CI გაშვებების შედეგების შედარებით. თუ ტესტი ერთ CI გაშვებაზე გადის, მაგრამ იმავე კომიტისა და პროექტისთვის სხვა გაშვებაზე ვარდება, ორივე გაშვება რხევადად მონიშნება.

Gradle პროექტი შედარების გასაღების ნაწილია, რადგან ერთი და იგივე ტესტი შეიძლება პროექტებს შორის დეტერმინისტულად განსხვავებულად იქცეოდეს — მაგალითად, საერთო ტესტის კლასი, რომელიც კომპილირებულია სხვადასხვა დამოკიდებულებებით ან გაშვებულია სხვა მოდულის ფიქსტურაზე. ერთი და იმავე კომიტის ორი გაშვება სხვადასხვა Gradle პროექტებზე განიხილება როგორც შესრულების ცალკეული ვარიანტები და ერთმანეთს რხევადად არ მონიშნავენ.

ეს განსაკუთრებით სასარგებლოა იმ რხევადი ტესტების დასაჭერად, რომლებიც საკმარისად თანმიმდევრულად არ ვარდებიან, რათა ხელახალი გაშვებებით დაფიქსირდნენ, მაგრამ მაინც იწვევენ პერიოდულ CI ჩავარდნებს.

## რხევადი ტესტების მართვა {#managing-flaky-tests}

### ავტომატური გასუფთავება

აღმოჩენა და გასუფთავება მიმდინარეობს პროექტზე **ავტომატიზაციის გაფრთხილების** მეშვეობით. ყოველ პროექტს აქვს ნაგულისხმევი „რხევადი ტესტის აღმოჩენის“ ავტომატიზაცია, რომლის *ტრიგერი* ტესტს რხევადად მონიშნავს, ხოლო *აღდგენა* აშორებს ნიშანს, როდესაც ტესტი ხელახალი ტრიგერის გარეშე გაივლის კონფიგურირებულ აღდგენის ფანჯარას (ნაგულისხმევი **14 დღე**). შეცვალეთ ის **Settings → Automations**-ში, რათა შეცვალოთ აღდგენის ფანჯარა, შეცვალოთ აღდგენის ქმედებები (მაგ., ასევე კარანტინის მოხსნა) ან სრულიად გამორთოთ აღდგენა, რათა ტესტები რხევადად დარჩეს მონიშნული, სანამ ხელით არ გაასუფთავებთ.

### ხელით მართვა

ასევე შეგიძლიათ ხელით მონიშნოთ ან მოხსნათ ტესტები რხევადად ტესტის შემთხვევის დეტალების გვერდიდან. ეს სასარგებლოა, როდესაც:
- გსურთ აღიაროთ ცნობილი რხევადი ტესტი მისი გამოსწორების სამუშაოს დროს
- ტესტი არასწორად მონიშნა ინფრასტრუქტურის პრობლემების გამო

## რხევადი ტესტების კარანტინში მოქცევა {#quarantining}

კარანტინში მოქცევა იზოლირებს რხევად ტესტს, რათა მან არ დაბლოკოს CI, სანამ მას შეასწორებთ. ნაგულისხმევად ეს არის **ხელით შესრულებადი ქმედება** — თქვენ ათავსებთ კარანტინში, ხსნით კარანტინს და ცვლით რეჟიმებს დაფის ტესტის შემთხვევის დეტალების გვერდიდან — მაგრამ ასევე შეგიძლიათ ჩართოთ ის **Settings → Automations**-ში **ავტომატიზაციის გაფრთხილებად**, რათა ტესტი ავტომატურად დადუმდეს (ან გამოტოვებულ იქნას), როდესაც გადალახავს რხევადობის ზღვარს, და კარანტინი მოეხსნას, როდესაც აღდგება. ყოველი გადასვლა, ხელით თუ ავტომატური, იწერება ტესტის შემთხვევის აუდიტის ჟურნალში.

კარანტინში მყოფი ტესტი ერთ-ერთ ორ რეჟიმშია:

- **დადუმებული**: ტესტი მაინც ეშვება, მაგრამ პლაგინი აყენებს `ignoreFailures = true` და ბილდს ხელახლა ავარდენს მხოლოდ არა-კარანტინული ჩავარდნების შემთხვევაში. ჩავარდნები მაინც კვებავს რხევადი ტესტების დეტექტორს, ასე რომ შეგიძლიათ აკვირდეთ ტესტს ბილდის გატეხვის გარეშე. აირჩიეთ ეს იმ ტესტისთვის, რომელსაც აქტიურად იკვლევთ.
- **გამოტოვებული**: პლაგინი ფილტრავს ტესტს Gradle-ის `excludeTestsMatching`-ის მეშვეობით, ასე რომ ის საერთოდ არ იწყება. ის არ წარმოქმნის ახალ შედეგებს და ქრება რხევადი ტესტების დაფიდან, სანამ ხელახლა არ ჩართავთ. აირჩიეთ ეს, როდესაც ტესტი გაფუჭებულია, ნელია ან იმდენად მუდმივად რხევადი, რომ მისი გაშვება უბრალოდ ფუჭად ხარჯავს CI წუთებს.

### რატომ შეიძლება კარანტინში მყოფი ტესტები გამოჩნდნენ როგორც წარმატებული {#quarantined-passing}

- **დადუმებული ტესტები** მაინც სრულდება. დადუმებული ტესტი, რომელიც ვარდება, ჩაიწერება როგორც **ჩავარდნილი** ტესტის შემთხვევის გაშვებაზე და მონიშნული იქნება როგორც რხევადი — თითოეული ტესტის სტატუსი არ გადაიწერება. რაც გადაიწერება, არის **მთლიანი ტესტის გაშვება**: თუ გაშვებაში ყოველი ჩავარდნილი ტესტის შემთხვევა დადუმებულია, გაშვება მთლიანად იტყობინება როგორც წარმატებული, ასე რომ დადუმებული ჩავარდნები არ ტეხენ CI-ს.
- **გამოტოვებული ტესტები** საერთოდ არ ეშვება, ასე რომ დაფა აგრძელებს ტესტის ბოლო რეალური შესრულების სტატუსის ჩვენებას — ეს სნეპშოტი შეიძლება კვირების ძველი იყოს.

### კარანტინის ჩართვა {#enabling-quarantine}

კარანტინი **ავტომატურად ჩართულია CI-ზე** (როდესაც `CI` გარემოს ცვლადი დაყენებულია) და გამორთულია ლოკალური ბილდებისთვის. პლაგინი იღებს კარანტინში მყოფი ტესტების სიას Tuist სერვერიდან ყოველი ტესტის ამოცანის წინ; დადუმებული ტესტები ჩვეულებრივად ეშვება და მათი ჩავარდნები ინიღბება, გამოტოვებული ტესტები ფილტრდება.

შეგიძლიათ აშკარად აკონტროლოთ ეს თქვენს `settings.gradle.kts`-ში:

```kotlin
tuist {
    testQuarantine {
        enabled = true  // or false to disable
    }
}
```

როდესაც `enabled` არ არის დაყენებული, ნაგულისხმევად არის ავტო-აღმოჩენა: ჩართულია CI-ზე, გამორთულია ლოკალურად.

## ახალი ტესტების სტრეს-ტესტირება {#stress-testing-new-tests}

სტრესის კარიბჭე ხელახლა უშვებს თქვენი ბრენჩის მიერ დამატებულ ტესტის შემთხვევებს, თითოეულს რამდენჯერმე ახალ პროცესში, და ატყობინებს იმას, რომელიც რხევადი აღმოჩნდება. თქვენ ხედავთ ახალ რხევად ტესტს იმ pull request-ზე, რომელმაც ის შემოიტანა, არა კვირების შემდეგ.

ტესტის შემთხვევა ახლად ითვლება, თუ ის ბოლო 90 დღის განმავლობაში არ გაშვებულა CI-ზე პროექტის ნაგულისხმევ ბრენჩზე, ან კომიტზე, რომელიც მას შემდეგ მოხვდა იქ. შერწყმის რიგით, ტესტის შემთხვევა, რომელიც რიგმა გაუშვა, ცნობილი ხდება, როდესაც რიგის კომიტი მოხვდება, და რჩება ახალი, თუ რიგი მას ტოვებს. კომიტები შეესაბამება <.localized_link href="/guides/features/test-insights/gradle#git-history">Git history</.localized_link>-ს მეშვეობით, რომელსაც Tuist აგროვებს CI-ზე.

### მისი ჩართვა

კარიბჭე ნაგულისხმევად გამორთულია. დააყენეთ რეჟიმი:

- **`report`**: აფრთხილებს ყოველი რხევადი ტესტის შემთხვევის შესახებ. გაშვება მაინც გადის თავისი შედეგის მიხედვით.
- **`enforce`**: რხევადი ტესტის შემთხვევა ავარდენს გაშვებას, იმავე exit code-ით, როგორც ჩავარდნილი ტესტი.

დაიწყეთ `report`-ით რამდენიმე კვირის განმავლობაში, რომ ნახოთ, რას დაბლოკავდა `enforce`.

განაცხადეთ ის `settings.gradle.kts`-ში, ან დააყენეთ `TUIST_TEST_STRESS_NEW_TESTS`, რათა შეცვალოთ რეჟიმი CI ლეინის მიხედვით:

```kotlin
tuist {
    stressNewTests {
        mode = "report" // or "enforce"
    }
}
```

კარანტინისგან განსხვავებით, კარიბჭეს არ აქვს CI-ის გათვალისწინებული ნაგულისხმევი პარამეტრი. თუ `mode` არ არის დაყენებული, ის არსად გაშვდება.

### რამდენჯერ ხელახლა უშვებს თითოეულ ტესტს

ეს დამოკიდებულია იმაზე, თუ რამდენი ხანი დასჭირდა ტესტის შემთხვევას პირველ გაშვებაზე:

## რხევადი და კარანტინში მყოფი მდგომარეობის გამოკითხვა {#querying}

### CLI

`tuist test case` ბრძანებების ხე აჩვენებს ყველაფერს, რასაც Tuist აკონტროლებს ტესტის შემთხვევის შესახებ:

```sh
tuist test case list --flaky                       # only flaky test cases
tuist test case list --quarantined                 # only muted or skipped test cases
tuist test case show <test_case_id>                # detail: flakiness rate, last status, run counts
tuist test case events <test_case_id>              # audit log: marked_flaky, muted, skipped, ...
tuist test case run list <test_case_id>            # run history with status and duration
tuist test case run show <test_case_run_id>        # single run, including failure breakdown
```

ყველა ეს იღებს `--json`-ს სკრიპტინგისთვის.

### REST API

იგივე მონაცემები ხელმისაწვდომია HTTP-ის მეშვეობით — იხილეთ [ტესტის შემთხვევების endpoint-ები](https://tuist.dev/api/docs#tag/test-cases) API ცნობარში სრული სიისთვის მარშრუტების, ფილტრების და პასუხის ველების შესახებ. ტესტის შემთხვევის მდგომარეობის შესაცვლელად (რხევადის მონიშვნა ან მოხსნა, დადუმება, გამოტოვება), გაგზავნეთ `PATCH /api/projects/{account_handle}/{project_handle}/tests/test-cases/{test_case_id}` `is_flaky`-ით ან `state`-ით. იგივე ცვლილება ხელმისაწვდომია როგორც `tuist test case update`, ასევე `update_test_case` Model Context Protocol ინსტრუმენტის სახით.
