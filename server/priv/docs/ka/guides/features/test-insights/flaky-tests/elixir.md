# Elixir-ის არასტაბილური ტესტები {#elixir-flaky-tests}

არასტაბილური ტესტებია ისეთი ტესტები, რომლებიც ერთი და იმავე კოდის რამდენიმეჯერ გაშვებისას სხვადასხვა შედეგს (წარმატება ან შეცდომა) აჩვენებენ. ისინი ამცირებენ ნდობას თქვენი ტესტების ნაკრების მიმართ და ფუჭად ხარჯავს დეველოპერების დროს ყალბი შეცდომების გამოკვლევაში. Tuist ავტომატურად აღმოაჩენს არასტაბილურ ტესტებს და გეხმარებათ მათ თვალყურის დევნაში დროთა განმავლობაში.

> [!IMPORTANT] REQUIREMENTS
> - დაასრულეთ <.localized_link href="/guides/get-started/elixir-project">Elixir-ის საერთო კონფიგურაცია</.localized_link>, რათა შეიტანოთ თქვენი ტესტების გაშვებები

![Phoenix-ის აპლიკაციის არასტაბილური ტესტები](/images/guides/features/elixir/flaky-tests.png)

## როგორ მუშაობს არასტაბილურობის აღმოჩენა {#how-it-works}

Tuist არასტაბილურ ტესტებს ორი გზით აღმოაჩენს:

### ტესტების გამეორება {#test-retries}

ExUnit თითოეულ ტესტს ერთხელ უშვებს, ამიტომ პერიოდულად მწყვარი ტესტი იგივენაირად ჩანს, როგორც გაფუჭებული. გამეორებების ჩართვისას Hex-ის პაკეტი თავიდან უშვებს შეცდომიან ტესტებს, თქვენს მიერ დაყენებული რაოდენობის ჯერამდე. ტესტი, რომელიც გამეორებისას წარმატებით სრულდება, მოინიშნება როგორც არასტაბილური, ხოლო გაშვება წარმატებულად ითვლება, თუ ყველა შეცდომიანი ტესტი საბოლოოდ წარმატებით დასრულდება.

გამეორებები ნაგულისხმევად გამორთულია. მათ ჩასართავად დაამატეთ `test_retries` თქვენს არსებულ Tuist-ის პარამეტრებში `mix.exs`-ში:

```elixir
tuist: [project: "account/project", cache: true, test_retries: 2]
```

ან ერთი გაშვებისთვის, ფლაგით ან გარემოს ცვლადით:

```bash
mix test --retries 2
TUIST_TEST_RETRIES=2 mix test
```

ფლაგს აქვს უპირატესობა გარემოს ცვლადთან შედარებით, ხოლო გარემოს ცვლადს — `mix.exs`-თან შედარებით.

თავიდან უშვებს მხოლოდ ის ტესტები, რომლებმაც შეცდომა დააფიქსირეს, ისევე როგორც `mix test --failed` უშვებს მათ, და დაშბორდი აჩვენებს თითოეული ტესტის მცდელობას და მის ხანგრძლივობას. გაშვება, რომელიც ExUnit-მა ადრე შეწყვიტა `--max-failures`-ის გამო, არ მეორდება. ასევე არ მეორდება გაშვება, რომლის ყველა შეცდომიანი ტესტი დროის ამოწურვამდე მივიდა, რადგან თითოეული გამეორება თავიდან დაელოდება ყველა დროის ამოწურვას. გამეორებები ასევე გამოიტოვება `--warnings-as-errors`-ით, რასაც `mix test` ვეღარ აიძულებს, და umbrella პროექტის ფესვიდან; ტესტების გამეორებისთვის გაუშვით ისინი მისი ერთ-ერთი აპლიკაციის შიგნით.

![არასტაბილური ExUnit ტესტი და მისი ისტორია](/images/guides/features/elixir/flaky-test-case.png)

### ჯვარედინი გაშვებების აღმოჩენა {#cross-run-detection}

ტესტების გამეორებების გარეშეც, Tuist-ს შეუძლია არასტაბილური ტესტების აღმოჩენა იმავე კომიტზე სხვადასხვა CI გაშვებების შედეგების შედარებით. თუ ტესტი ერთ CI გაშვებაში წარმატებულია, მაგრამ იმავე კომიტის სხვა გაშვებაში მწყვარია, ორივე გაშვება მოინიშნება როგორც არასტაბილური.

ეს განსაკუთრებით სასარგებლოა იმ არასტაბილური ტესტების დასაჭერად, რომლებიც საკმარისად თანმიმდევრულად არ მწყვარია, რომ გამეორებებმა დაიჭიროს, მაგრამ მაინც იწვევს პერიოდულ CI შეცდომებს.

## არასტაბილური ტესტების მართვა {#managing-flaky-tests}

### ავტომატური გასუფთავება

აღმოჩენა და გასუფთავება ხდება პროექტზე **ავტომატიზაციის შეტყობინების** მეშვეობით. ყოველ პროექტს აქვს ნაგულისხმევი „არასტაბილური ტესტების აღმოჩენის“ ავტომატიზაცია, რომლის *ტრიგერი* ტესტს არასტაბილურად ნიშნავს, ხოლო *აღდგენა* ხსნის ნიშანს, როდესაც ტესტი გაივლის კონფიგურირებულ აღდგენის ფანჯარას (ნაგულისხმევი **14 დღე**) ხელახალი ტრიგერის გარეშე. ჩაასწორეთ ის **პარამეტრები → ავტომატიზაციები**-ში, რათა შეცვალოთ აღდგენის ფანჯარა ან სრულად გათიშოთ აღდგენა, რათა ტესტები დარჩეს არასტაბილურად მონიშნული, სანამ ხელით არ გაასუფთავებთ მათ.

### ხელით მართვა

ასევე შეგიძლიათ ხელით მონიშნოთ ან მოხსნათ ტესტები როგორც არასტაბილური სატესტო შემთხვევის დეტალური გვერდიდან. ეს სასარგებლოა, როდესაც:
- გსურთ აღიაროთ ცნობილი არასტაბილური ტესტი მისი გამოსწორების დროს
- ტესტი არასწორად მოინიშნა ინფრასტრუქტურის პრობლემების გამო

## არასტაბილური ტესტების კარანტინში მოთავსება {#quarantining}

კარანტინი ხელს უშლის არასტაბილურ ტესტს CI-ის ბლოკირებაში, სანამ მას ასწორებთ. დაშბორდზე ტესტის გვერდზე შეცვალეთ მისი მდგომარეობა **ჩახშობილზე** ან **გამოტოვებულზე**, ან კონფიგურირეთ ავტომატიზაცია **პარამეტრები → ავტომატიზაციები**-ში, რომელიც ჩახშობს ან გამოტოვებს ტესტს, როდესაც ის არასტაბილური ხდება და თავიდან ჩართავს მას, როდესაც აღდგება. ტესტების გაშვებამდე `mix test` კითხულობს პროექტის ყველა კარანტინში მოთავსებულ ტესტს და ავრცელებს მათ:

- **ჩახშობილი**: ტესტი გაშვებულია და მისი შეცდომა მაინც იქნება მოხსენებული, მაგრამ გაშვება, რომლის ერთადერთი შეცდომები ჩახშობილი ტესტებია, წარმატებულია. გამეორებები მაინც თავიდან უშვებს მწყვარ ჩახშობილ ტესტს, ამიტომ არასტაბილურმა შეიძლება წარმატებით გაიაროს და არასტაბილურად იქნას მოხსენებული.
- **გამოტოვებული**: ტესტი არ გაშვებულა. `mix test` აჩვენებს გამოტოვებულ ტესტებს გაშვების დაწყებამდე.

```text
Tuist: skipping 1 quarantined test:
  MyApp.CheckoutTest: create_order/2 times out
Tuist: 1 muted test run, and their failures do not fail the run.
```

გაშვება ჩვეულებრივად მწყვარია, როდესაც ნებისმიერი ტესტი, რომელიც არ არის ჩახშობილი, მწყვარია, ან როდესაც ExUnit ადრე წყვეტს `--max-failures`-ის გამო.

> [!WARNING]
> **შეზღუდვები**
>
> - კარანტინს მხოლოდ Hex-ის პაკეტის ახალი ვერსიები ავრცელებენ. ადრეული ვერსიები ჩახშობილ და გამოტოვებულ ტესტებს სხვების მსგავსად უშვებენ, ამიტომ ჩახშობილი ტესტის შეცდომა მაინც აფუჭებს გაშვებას. განაახლეთ `tuist_ex`, სანამ მას დაეყრდნობით.
> - ჩახშობილი ტესტები არ ვრცელდება `--warnings-as-errors`-ით, ან umbrella პროექტის ფესვიდან. მათი შეცდომები მაშინ აფუჭებენ გაშვებას. ნაცვლად ამისა, გაუშვით ტესტები umbrella-ის თითოეული აპლიკაციის შიგნით.
> - გამოტოვება ემთხვევა ტესტს მისი describe ბლოკისა და სახელის მიხედვით, არა მოდულის მიხედვით. ტესტი იმავე describe ბლოკითა და სახელით სხვა მოდულში ასევე გამოტოვებულია. იხილეთ [როგორ ირჩევს გამოტოვება ტესტებს](#how-skipping-selects-tests).
> - გამოტოვებული ტესტი მაინც გაშვებულია, როდესაც მას ირჩევთ `--only`-ით, `--include`-ით ან `path:line`-ით, ან როდესაც ის არ არის განცხადებული `test`-ით, როგორიცაა StreamData `property`.
> - თუ `mix test` ვერ კითხულობს კარანტინში მოთავსებულ ტესტებს, ის უშვებს ყველა ტესტს და ითვლის ყველა შეცდომას.
> - კარანტინში მოთავსებული ტესტების წაკითხვა მოითხოვს სერთიფიკატებს, საჯარო პროექტისთვისაც კი. გაშვება `TUIST_TOKEN`-ის, `mix tuist.login` სესიის ან უწყვეტი ინტეგრაციის იდენტობის ტოკენის გარეშე არ ავრცელებს კარანტინს. ეს მოიცავს fork-ებიდან შემოსულ pull request-ებს, რომლებიც ჩვეულებრივ საიდუმლოებების გარეშე გაშვებულია.
> - `--cover`-ით, გამოტოვებული ტესტი ითვლება როგორც ამოღებული: ხაზები, რომლებსაც მხოლოდ ის ფარავდა, მოხსენებულია როგორც დაუფარავი.
>
> `mix test` ასახელებს ტესტებს, რომლებიც გამოტოვებამ შეცდომით დატოვა, და გამოტოვებულ ტესტებს, რომლებიც მაინც გაშვებულია, მისი შეჯამების შემდეგ.

### როგორ ირჩევს გამოტოვება ტესტებს {#how-skipping-selects-tests}

გამოტოვებული ტესტი გამოტოვებულია ExUnit-ის ფილტრით მისი სრული სახელის მიხედვით, მაგალითად `--exclude "test:test create_order/2 times out"`. ExUnit-ის ფილტრებს ასევე არ შეუძლიათ მოდულის დამთხვევა, ამიტომ:

- ტესტი იმავე describe ბლოკითა და სახელით სხვა მოდულში ასევე გამოტოვებულია. `mix test` ასახელებს იმ ტესტებს გაშვების შემდეგ.
- ტესტი, რომელსაც ირჩევთ `--only`-ით, `--include`-ით ან `path:line`-ით, გაშვებულია მაშინაც კი, თუ ის გამოტოვებულია, რადგან ExUnit include ფილტრებს exclude ფილტრების შემდეგ ავრცელებს. ასევე ხდება ტესტის შემთხვევაში, რომელიც არ არის განცხადებული `test`-ით, როგორიცაა StreamData `property`. `mix test` ასახელებს ამ ტესტებს გაშვების შემდეგ.

### კარანტინში მოთავსებული ტესტების ხელახლა გაშვება {#running-quarantined-tests-again}

გადაეცით `--no-quarantine` ყველა ტესტის გასაშვებად და ყველა შეცდომის დასათვლელად, მაგალითად, გამოსწორების შესამოწმებლად:

```bash
mix test --no-quarantine
```

დააბრუნეთ ტესტი მის გვერდზე მდგომარეობაში **Enabled**, რათა ის ჩართოთ მომდევნო გაშვებებში. გამოტოვებული ტესტი ახალ შედეგებს არ გამოიმუშავებს, სანამ ის ხელახლა არ გაშვდება.

თუ `mix test` ვერ კითხულობს კარანტინში მოთავსებულ ტესტებს, ის ბეჭდავს გაფრთხილებას და უშვებს ყველა ტესტს მათ გარეშე. სერთიფიკატების ან კონფიგურირებული პროექტის გარეშე, ის უშვებს ყველა ტესტს გაფრთხილების გარეშე.

Hex პაკეტი ჯერჯერობით არ ატარებს ახალი ტესტების სტრეს-ტესტირებას.

## არასტაბილური მდგომარეობის მოთხოვნა {#querying}

მონაცემები ხელმისაწვდომია HTTP-ით. სრული სიისთვის მარშრუტების, ფილტრების და პასუხის ველების შესახებ, იხილეთ API ცნობარში [ტესტის შემთხვევების ბოლოწერტილები](https://tuist.dev/api/docs#tag/test-cases). სატესტო შემთხვევის არასტაბილურად აღსანიშნავად ან ნიშნის მოსახსნელად, გააგზავნეთ `PATCH /api/projects/{account_handle}/{project_handle}/tests/test-cases/{test_case_id}` `is_flaky`-ით, ან გამოიყენეთ `update_test_case` Model Context Protocol ინსტრუმენტი.
