## როგორ მუშაობს არასტაბილურობის აღმოჩენა {#how-it-works}

Tuist არასტაბილურ ტესტებს ორი გზით აღმოაჩენს:

### ტესტების ხელახალი გაშვება {#test-retries}

ExUnit თითოეულ ტესტს ერთხელ ასრულებს, ამიტომ დროდადრო ჩავარდნილი ტესტი იგივენაირად გამოიყურება, როგორც გაუმართავი. ხელახალი გაშვებების ჩართვისას Hex-პაკეტი ხელახლა ასრულებს ჩავარდნილ ტესტებს თქვენ მიერ დაყენებული რაოდენობის ჯერამდე. ტესტი, რომელიც ხელახალ გაშვებაზე წარმატებით სრულდება, აღინიშნება როგორც არასტაბილური, ხოლო გაშვება წარმატებით სრულდება, თუ ყველა ჩავარდნილი ტესტი საბოლოოდ წარმატებით შესრულდება.

ხელახალი გაშვებები ნაგულისხმევად გამორთულია. მათ ჩასართავად დაამატეთ `test_retries` თქვენს არსებულ Tuist პარამეტრებში `mix.exs` ფაილში:

```elixir
tuist: [project: "account/project", cache: true, test_retries: 2]
```

ან ერთჯერადი გაშვებისთვის, ფლაგით ან გარემოს ცვლადით:

```bash
mix test --retries 2
TUIST_TEST_RETRIES=2 mix test
```

ფლაგი უპირატესობას ანიჭებს გარემოს ცვლადს, ხოლო გარემოს ცვლადი — `mix.exs`-ს.

ხელახლა მხოლოდ ჩავარდნილი ტესტები სრულდება, ისევე, როგორც `mix test --failed`-ს შემთხვევაში, ხოლო დაშბორდი აჩვენებს ტესტის თითოეულ მცდელობას და მის ხანგრძლივობას. გაშვება, რომელიც ExUnit-მა ადრე შეწყვიტა `--max-failures`-ის გამო, ხელახლა არ სრულდება. გაშვება, რომლის ყველა ჩავარდნილი ტესტიც დროის ამოწურვამდე მივიდა, ასევე არ მეორდება, რადგან თითოეული ხელახალი გაშვება ყველა დროის ამოწურვას თავიდან ელოდება. ხელახალი გაშვებები ასევე გამოიტოვება `--warnings-as-errors`-თან ერთად, რასაც `mix test` აღარ აღასრულებს, და umbrella პროექტის ფესვიდან; ტესტების ხელახლა გასაშვებად შეასრულეთ ისინი მისი ერთ-ერთი აპლიკაციის შიგნით.

![არასტაბილური ExUnit ტესტი და მისი ისტორია](/images/guides/features/elixir/flaky-test-case.png)

### გაშვებებს შორის აღმოჩენა {#cross-run-detection}

ტესტების ხელახალი გაშვებების გარეშეც, Tuist-ს შეუძლია არასტაბილური ტესტების აღმოჩენა იმავე კომიტზე სხვადასხვა CI გაშვებების შედეგების შედარებით. თუ ტესტი ერთ CI გაშვებაზე წარმატებით სრულდება, მაგრამ მეორე გაშვებაზე იმავე კომიტისა და სქემის ლეიბლისთვის (`--scheme`) ვერდება, ეს ჩავარდნილი შესრულება აღინიშნება როგორც არასტაბილური.

ეს განსაკუთრებით სასარგებლოა ისეთი არასტაბილური ტესტების აღმოსაჩენად, რომლებიც საკმარისად თანმიმდევრულად არ ვერდება ხელახალი გაშვებებით აღმოსაჩენად, მაგრამ მაინც იწვევს დროდადრო CI ჩავარდნებს.

## არასტაბილური ტესტების კარანტინში მოთავსება {#quarantining}

კარანტინი ხელს უშლის არასტაბილურ ტესტს CI-ს ბლოკირებაში მის გამოსწორებამდე. დაშბორდზე ტესტის გვერდზე შეცვალეთ მისი მდგომარეობა **ჩუმად**-ზე ან **გამოტოვებულ**-ზე, ან დააკონფიგურირეთ ავტომატიზაცია **პარამეტრები → ავტომატიზაციები** განყოფილებაში, რომელიც ტესტს ჩააჩუმებს ან გამოტოვებს, როცა ის არასტაბილური ხდება და ხელახლა ჩართავს მას, როცა ის აღდგება. ტესტების გაშვებამდე `mix test` კითხულობს პროექტის ყველა კარანტინში მყოფ ტესტს და იყენებს მათ:

- **ჩუმად**: ტესტი სრულდება და მისი ჩავარდნა კვლავ შეიტყობინება, მაგრამ გაშვება წარმატებით სრულდება, თუ მისი ერთადერთი ჩავარდნები ჩუმად მყოფი ტესტებია. ხელახალი გაშვებები კვლავ ახდენენ ჩავარდნილი ჩუმი ტესტის ხელახალ გაშვებას, ამიტომ არასტაბილურს შეუძლია წარმატებით შესრულება და არასტაბილურად აღნიშვნა.
- **გამოტოვებული**: ტესტი არ სრულდება. `mix test` ჩამოთვლის გამოტოვებულ ტესტებს გაშვების დაწყებამდე.

```text
Tuist: skipping 1 quarantined test:
  MyApp.CheckoutTest: create_order/2 times out
Tuist: 1 muted test run, and their failures do not fail the run.
```

გაშვება ჩვეულებრივად ვერდება, როცა ნებისმიერი ტესტი, რომელიც ჩუმად არ არის, ვერდება, ან როცა ExUnit ადრე წყვეტს `--max-failures`-ის გამო.

> [!WARNING]
> **შეზღუდვები**
>
> - კარანტინს მხოლოდ Hex-პაკეტის ბოლო ვერსიები იყენებენ. ადრეული ვერსიები ჩუმ და გამოტოვებულ ტესტებს სხვების მსგავსად ასრულებენ, ამიტომ ჩუმი ტესტის ჩავარდნა მაინც აგდებს გაშვებას. სანამ მას დაეყრდნობით, განაახლეთ `tuist_ex`.
> - ჩუმი ტესტები არ გამოიყენება `--warnings-as-errors`-თან ერთად, ან umbrella პროექტის ფესვიდან. მათი ჩავარდნები მაშინ აგდებენ გაშვებას. ამის ნაცვლად, შეასრულეთ ტესტები umbrella-ს თითოეული აპლიკაციის შიგნით.
> - გამოტოვება ემთხვევა ტესტს მისი describe ბლოკისა და სახელის მიხედვით, არა მოდულის მიხედვით. ტესტი იმავე describe ბლოკითა და სახელით სხვა მოდულში ასევე გამოიტოვება. იხილეთ [როგორ ირჩევს გამოტოვება ტესტებს](#how-skipping-selects-tests).
> - გამოტოვებული ტესტი მაინც სრულდება, როცა მას ირჩევთ `--only`-ით, `--include`-ით ან `path:line`-ით, ან როცა ის არ არის გამოცხადებული `test`-ით, მაგალითად StreamData `property`.
> - თუ `mix test` ვერ კითხულობს კარანტინში მყოფ ტესტებს, ის ასრულებს ყველა ტესტს და თვლის ყველა ჩავარდნას.
> - კარანტინში მყოფი ტესტების წაკითხვას სჭირდება მონაცემები, მაშინაც კი, თუ პროექტი საჯაროა. გაშვება `TUIST_TOKEN`-ის, `mix tuist.login` სესიის ან უწყვეტი ინტეგრაციის იდენტობის ტოკენის გარეშე არ იყენებს კარანტინს. ეს მოიცავს fork-ებიდან შემოსულ pull request-ებს, რომლებიც ჩვეულებრივ საიდუმლოების გარეშე სრულდება.
> - `--cover`-თან ერთად, გამოტოვებული ტესტი ითვლება როგორც ამოღებული: ხაზები, რომლებსაც მხოლოდ ის ფარავდა, შეიტყობინება როგორც დაუფარავი.
>
> `mix test` ასახელებს ტესტებს, რომლებიც გამოტოვებამ შეცდომით გამოტოვა, და გამოტოვებულ ტესტებს, რომლებიც მაინც შესრულდა, მისი შეჯამების შემდეგ.

### როგორ ირჩევს გამოტოვება ტესტებს {#how-skipping-selects-tests}

გამოტოვებული ტესტი გამოიტოვება ExUnit ფილტრით მისი სრული სახელის მიხედვით, მაგალითად `--exclude "test:test create_order/2 times out"`. ExUnit ფილტრებს ასევე არ შეუძლიათ მოდულის დამთხვევა, ამიტომ:

- ტესტი იმავე describe ბლოკითა და სახელით სხვა მოდულში ასევე გამოიტოვება. `mix test` ასახელებს იმ ტესტებს გაშვების შემდეგ.
- ტესტი, რომელსაც ირჩევთ `--only`-ით, `--include`-ით ან `path:line`-ით, სრულდება მაშინაც, როცა ის გამოტოვებულია, რადგან ExUnit include ფილტრებს exclude ფილტრების შემდეგ იყენებს. იგივე ეხება ტესტს, რომელიც არ არის გამოცხადებული `test`-ით, მაგალითად StreamData `property`. `mix test` ასახელებს იმ ტესტებს გაშვების შემდეგ.

### კარანტინში მყოფი ტესტების ხელახლა გაშვება {#running-quarantined-tests-again}

გადაეცით `--no-quarantine` ყველა ტესტის გასაშვებად და ყველა ჩავარდნის დასათვლელად, მაგალითად, შესწორების შესამოწმებლად:

```bash
mix test --no-quarantine
```

დააბრუნეთ ტესტი **ჩართულ** მდგომარეობაში მის გვერდზე, რათა ის მომავალ გაშვებებში შევიდეს. გამოტოვებული ტესტი ახალ შედეგებს არ ქმნის, სანამ ის ხელახლა არ შესრულდება.

თუ `mix test` ვერ კითხულობს კარანტინში მყოფ ტესტებს, ის ბეჭდავს გაფრთხილებას და ასრულებს ყველა ტესტს მათ გარეშე. მონაცემების ან კონფიგურირებული პროექტის გარეშე, ის ასრულებს ყველა ტესტს გაფრთხილების გარეშე.

Hex-პაკეტი ახალ ტესტებს ჯერ არ ატარებს დატვირთვის ტესტირებას.

## არასტაბილური მდგომარეობის მოთხოვნა {#querying}

მონაცემები ხელმისაწვდომია HTTP-ით. სრული სიისთვის, რომელიც მოიცავს მარშრუტებს, ფილტრებს და პასუხის ველებს, იხილეთ [სატესტო შემთხვევების ბოლოწერტილები](https://tuist.dev/api/docs#tag/test-cases) API-ის ცნობარში. სატესტო შემთხვევის არასტაბილურად ან არაარასტაბილურად მონიშვნისთვის, გაგზავნეთ `PATCH /api/projects/{account_handle}/{project_handle}/tests/test-cases/{test_case_id}` პარამეტრით `is_flaky`, ან გამოიყენეთ `update_test_case` Model Context Protocol ინსტრუმენტი.
