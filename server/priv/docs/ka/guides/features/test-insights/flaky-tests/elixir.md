## როგორ მუშაობს არასტაბილურობის აღმოჩენა {#how-it-works}

Tuist არასტაბილურ ტესტებს ორი გზით აღმოაჩენს:

### ტესტების ხელახლა გაშვება {#test-retries}

ExUnit თითოეულ ტესტს ერთხელ უშვებს, ამიტომ დროდადრო მწყავარე ტესტი იგივენაირად გამოიყურება, როგორც გაუმართავი. ხელახლა გაშვების ჩართვისას Hex-პაკეტი თავიდან უშვებს წარუმატებელ ტესტებს იმ რაოდენობამდე, რამდენჯერაც მიუთითებთ. ტესტი, რომელიც ხელახლა გაშვებისას გადის, მონიშნულია როგორც არასტაბილური, ხოლო გაშვება წარმატებით სრულდება, თუ ყველა წარუმატებელი ტესტი საბოლოოდ გაივლის.

ხელახლა გაშვება ნაგულისხმევად გამორთულია. მათ ჩასართავად დაამატეთ `test_retries` თქვენს არსებულ Tuist პარამეტრებში `mix.exs` ფაილში:

```elixir
tuist: [project: "account/project", cache: true, test_retries: 2]
```

ან ერთი გაშვებისთვის, დროშის ან გარემოს ცვლადის გამოყენებით:

```bash
mix test --retries 2
TUIST_TEST_RETRIES=2 mix test
```

დროშას აქვს უპირატესობა გარემოს ცვლადთან შედარებით, ხოლო გარემოს ცვლადს — `mix.exs`-თან შედარებით.

მხოლოდ წარუმატებელი ტესტები გაშვებულია ხელახლა, ისევე როგორც `mix test --failed` უშვებს მათ, ხოლო დაფაზე ნაჩვენებია ტესტის თითოეული მცდელობა და მისი ხანგრძლივობა. გაშვება, რომელიც ExUnit-მა ადრე შეწყვიტა `--max-failures`-ის გამო, არ განმეორდება. ასევე არ განმეორდება გაშვება, რომლის ყველა წარუმატებელი ტესტი დროის ამოწურვით დასრულდა, რადგან თითოეული ხელახლა გაშვება ყველა დროის ამოწურვას თავიდან ელოდება. ხელახლა გაშვება ასევე გამოტოვებულია `--warnings-as-errors`-ით, რასაც `mix test` ვეღარ აღასრულებს, და umbrella პროექტის ფესვიდან; ტესტების ხელახლა გასაშვებად გაუშვით ისინი მისი ერთ-ერთი აპლიკაციის შიგნით.

![არასტაბილური ExUnit ტესტი და მისი ისტორია](/images/guides/features/elixir/flaky-test-case.png)

### გაშვებებს შორის აღმოჩენა {#cross-run-detection}

ტესტების ხელახლა გაშვების გარეშეც, Tuist-ს შეუძლია არასტაბილური ტესტების აღმოჩენა ერთსა და იმავე კომიტზე სხვადასხვა CI გაშვებების შედეგების შედარებით. თუ ტესტი ერთ CI გაშვებაში გადის, მაგრამ მეორეში იმავე კომიტისა და სქემის იარლიყისთვის (`--scheme`) მწყავარეა, წარუმატებელი გაშვება მონიშნულია როგორც არასტაბილური.

ეს განსაკუთრებით სასარგებლოა იმ არასტაბილური ტესტების აღმოჩენისთვის, რომლებიც არ მწყავარე enough თანმიმდევრულად, რათა ხელახლა გაშვებამ დაიჭიროს, მაგრამ მაინც იწვევს დროდადრო CI წარუმატებლობებს.

## არასტაბილური ტესტების კარანტინში მოქცევა {#quarantining}

კარანტინი არასტაბილურ ტესტს არ აძლევს CI-ის ბლოკირების საშუალებას, სანამ მას შეასწორებთ. დაფაზე ტესტის გვერდზე შეცვალეთ მისი მდგომარეობა **ჩუმად** ან **გამოტოვებულად**, ან დააკონფიგურირეთ ავტომატიზაცია **პარამეტრები → ავტომატიზაციები** ქვეშ, რომელიც ტესტს ჩააჩუმებს ან გამოტოვებს, როცა ის არასტაბილური გახდება და თავიდან ჩართავს, როცა აღდგება. ტესტების გაშვებამდე `mix test` კითხულობს პროექტის ყველა კარანტინში მყოფ ტესტს და ავრცელებს მათ:

- **ჩუმად**: ტესტი გაშვებულია და მისი წარუმატებლობა კვლავ მოხსენებულია, მაგრამ გაშვება, რომლის ერთადერთი წარუმატებლობები ჩუმად მყოფი ტესტებია, წარმატებით სრულდება. ხელახლა გაშვება კვლავ თავიდან უშვებს მწყავარე ჩუმ ტესტს, ამიტომ არასტაბილურს შეუძლია გაიაროს და მონიშნულ იქნას როგორც არასტაბილური.
- **გამოტოვებული**: ტესტი არ გაშვებულა. `mix test` სიას აკეთებს გამოტოვებული ტესტებისა გაშვების დაწყებამდე.

```text
Tuist: skipping 1 quarantined test:
  MyApp.CheckoutTest: create_order/2 times out
Tuist: 1 muted test run, and their failures do not fail the run.
```

გაშვება ჩვეულებრივ მწყავარეა, როცა ნებისმიერი ტესტი, რომელიც ჩუმად არ არის, მწყავარეა, ან როცა ExUnit ადრე წყვეტს `--max-failures`-ის გამო.

> [!WARNING]
> **შეზღუდვები**
>
> - მხოლოდ Hex პაკეტის ბოლო ვერსიები ავრცელებენ კარანტინს. ადრეული ვერსიები ჩუმ და გამოტოვებულ ტესტებს სხვების მსგავსად უშვებენ, ამიტომ ჩუმი ტესტის წარუმატებლობა კვლავ აწყვეტს გაშვებას. განაახლეთ `tuist_ex` სანამ მას დაეყრდნობით.
> - ჩუმი ტესტები არ ვრცელდება `--warnings-as-errors`-ით, ან umbrella პროექტის ფესვიდან. მათი წარუმატებლობები მაშინ აწყვეტენ გაშვებას. ამის ნაცვლად გაუშვით ტესტები umbrella-ს თითოეული აპლიკაციის შიგნით.
> - გამოტოვება ემთხვევა ტესტს მისი describe ბლოკისა და სახელის მიხედვით, არა მოდულის. სხვა მოდულში იმავე describe ბლოკისა და სახელის მქონე ტესტი ასევე გამოტოვებულია. იხილეთ [როგორ ირჩევს გამოტოვება ტესტებს](#how-skipping-selects-tests).
> - გამოტოვებული ტესტი კვლავ გაშვებულია, როცა მას ირჩევთ `--only`, `--include`, ან `path:line`-ით, ან როცა ის არ არის განცხადებული `test`-ით, მაგალითად StreamData `property`.
> - თუ `mix test` ვერ კითხულობს კარანტინში მყოფ ტესტებს, ის უშვებს ყველა ტესტს და ითვლის ყველა წარუმატებლობას.
> - კარანტინში მყოფი ტესტების წაკითხვა საჭიროებს მონაცემებს, საჯარო პროექტისთვისაც კი. გაშვება `TUIST_TOKEN`-ის, `mix tuist.login` სესიის, ან უწყვეტი ინტეგრაციის იდენტობის ტოკენის გარეშე არ ავრცელებს კარანტინს. ეს მოიცავს fork-ებიდან შემოსულ pull request-ებს, რომლებიც ჩვეულებრივ საიდუმლოების გარეშე გაშვებულია.
> - `--cover`-ით, გამოტოვებული ტესტი ითვლება როგორც ამოღებული: ხაზები, რომლებსაც მხოლოდ ის ფარავდა, მოხსენებულია როგორც დაუფარავი.
>
> `mix test` ასახელებს ტესტებს, რომლებიც გამოტოვებამ შეცდომით დატოვა, და გამოტოვებულ ტესტებს, რომლებიც მაინც გაშვებულია, მისი შეჯამების შემდეგ.

### როგორ ირჩევს გამოტოვება ტესტებს {#how-skipping-selects-tests}

გამოტოვებული ტესტი გამოტოვებულია ExUnit ფილტრით მისი სრული სახელის მიხედვით, მაგალითად `--exclude "test:test create_order/2 times out"`. ExUnit ფილტრებს ასევე არ შეუძლიათ მოდულის დამთხვევა, ამიტომ:

- სხვა მოდულში იმავე describe ბლოკისა და სახელის მქონე ტესტი ასევე გამოტოვებულია. `mix test` ასახელებს იმ ტესტებს გაშვების შემდეგ.
- ტესტი, რომელსაც ირჩევთ `--only`, `--include`, ან `path:line`-ით, გაშვებულია მაშინაც, როცა ის გამოტოვებულია, რადგან ExUnit include ფილტრებს exclude ფილტრების შემდეგ ავრცელებს. ასევე ტესტი, რომელიც არ არის განცხადებული `test`-ით, მაგალითად StreamData `property`. `mix test` ასახელებს იმ ტესტებს გაშვების შემდეგ.

### კარანტინში მყოფი ტესტების ხელახლა გაშვება {#running-quarantined-tests-again}

გადაეცით `--no-quarantine` ყველა ტესტის გასაშვებად და ყველა წარუმატებლობის დასათვლელად, მაგალითად შესწორების შესამოწმებლად:

```bash
mix test --no-quarantine
```

დააბრუნეთ ტესტი **ჩართულ** მდგომარეობაში მის გვერდზე, რათა ის შემდგომ გაშვებებში ჩაერთოს. გამოტოვებული ტესტი ახალ შედეგებს არ ქმნის, სანამ ის ხელახლა არ გაშვდება.

თუ `mix test` ვერ კითხულობს კარანტინში მყოფ ტესტებს, ის ბეჭდავს გაფრთხილებას და უშვებს ყველა ტესტს მათ გარეშე. მონაცემების ან კონფიგურირებული პროექტის გარეშე, ის უშვებს ყველა ტესტს გაფრთხილების გარეშე.

Hex პაკეტი ჯერ არ აკეთებს ახალი ტესტების სტრეს-ტესტირებას.

## არასტაბილური მდგომარეობის მოთხოვნა {#querying}

მონაცემები ხელმისაწვდომია HTTP-ით. სრული სიისთვის, მარშრუტების, ფილტრების და პასუხის ველების ნახვა შეგიძლიათ [სატესტო შემთხვევების ბოლოწერტილებში](https://tuist.dev/api/docs#tag/test-cases) API ცნობარში. სატესტო შემთხვევის არასტაბილურად აღსანიშნავად ან ამ ნიშნის მოსახსნელად, გაგზავნეთ `PATCH /api/projects/{account_handle}/{project_handle}/tests/test-cases/{test_case_id}` პარამეტრით `is_flaky`, ან გამოიყენეთ `update_test_case` Model Context Protocol ინსტრუმენტი.
