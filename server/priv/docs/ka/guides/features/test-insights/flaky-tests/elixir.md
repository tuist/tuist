# Elixir-ის არასტაბილური ტესტები {#elixir-flaky-tests}

არასტაბილური ტესტები არის ტესტები, რომლებიც ერთი და იგივე კოდის რამდენჯერმე გაშვებისას სხვადასხვა შედეგს (წარმატება ან ჩავარდნა) აჩვენებენ. ისინი ამცირებენ ნდობას თქვენი ტესტების ნაკრადის მიმართ და ფუჭად ხარჯავენ დეველოპერების დროს ცრუ ჩავარდნების გამოკვლევაში. Tuist ავტომატურად აღმოაჩენს არასტაბილურ ტესტებს და გეხმარებათ მათ თვალყურის დევნაში დროთა განმავლობაში.

> [!IMPORTANT] REQUIREMENTS
> - დაასრულეთ <.localized_link href="/guides/get-started/elixir-project">Elixir-ის საერთო კონფიგურაცია</.localized_link>, რათა შეატყობინოთ თქვენი ტესტების გაშვებები

![Phoenix აპლიკაციის არასტაბილური ტესტები](/images/guides/features/elixir/flaky-tests.png)

## როგორ მუშაობს არასტაბილურობის აღმოჩენა {#how-it-works}

Tuist არასტაბილურ ტესტებს ორი გზით აღმოაჩენს:

### ტესტების ხელახლა გაშვება {#test-retries}

ExUnit თითოეულ ტესტს ერთხელ უშვებს, ამიტომ პერიოდულად მწყარი ტესტი იგივენაირად ჩანს, როგორც გაუმართავი. ხელახლა გაშვების ჩართვისას Hex-ის პაკეტი ხელახლა უშვებს ჩავარდნილ ტესტებს, თქვენს მიერ მითითებული რაოდენობის ჯერამდე. ტესტი, რომელიც ხელახლა გაშვებისას წარმატებით სრულდება, მოიხსენიება როგორც არასტაბილური, ხოლო გაშვება წარმატებით სრულდება, თუ ყველა ჩავარდნილი ტესტი საბოლოოდ წარმატებით შესრულდება.

ხელახლა გაშვება ნაგულისხმევად გამორთულია. მათ ჩასართავად დაამატეთ `test_retries` თქვენს არსებულ Tuist-ის პარამეტრებში `mix.exs`-ში:

```elixir
tuist: [project: "account/project", cache: true, test_retries: 2]
```

ან ერთი გაშვებისთვის, ფლაგის ან გარემოს ცვლადის გამოყენებით:

```bash
mix test --retries 2
TUIST_TEST_RETRIES=2 mix test
```

ფლაგს აქვს უპირატესობა გარემოს ცვლადზე, ხოლო გარემოს ცვლადს — `mix.exs`-ზე.

ხელახლა მხოლოდ ჩავარდნილი ტესტები ეშვება, ისევე როგორც `mix test --failed` უშვებს მათ, და დაფაზე ჩანს ტესტის თითოეული მცდელობა და მისი ხანგრძლივობა. გაშვება, რომელიც ExUnit-მა ადრე შეწყვიტა `--max-failures`-ის გამო, ხელახლა არ ეშვება. გაშვება, რომლის ჩავარდნილი ტესტებიც ყველა ვადაგასულმა, ასევე არ ეშვება ხელახლა, რადგან თითოეული ხელახალი გაშვება კვლავ დაელოდება ყველა ვადაგასულობას. ხელახალი გაშვებები ასევე გამოიტოვება `--warnings-as-errors`-თან ერთად, რასაც `mix test` აღარ აიძულებს, და umbrella პროექტის ფესვიდან; ტესტების ხელახლა გასაშვებად გაუშვით ისინი მისი ერთ-ერთი აპლიკაციის შიგნით.

![არასტაბილური ExUnit ტესტი და მისი ისტორია](/images/guides/features/elixir/flaky-test-case.png)

### ჯვარედინი გაშვებების აღმოჩენა {#cross-run-detection}

ტესტების ხელახალი გაშვების გარეშეც, Tuist-ს შეუძლია არასტაბილური ტესტების აღმოჩენა იმავე კომიტზე სხვადასხვა CI გაშვებების შედეგების შედარებით. თუ ტესტი ერთ CI გაშვებაში წარმატებით სრულდება, მაგრამ იმავე კომიტის სხვა გაშვებაში მწყარია, ორივე გაშვება მონიშნულია როგორც არასტაბილური.

ეს განსაკუთრებით სასარგებლოა იმ არასტაბილური ტესტების დასაჭერად, რომლებიც საკმარისად თანმიმდევრულად არ მწყარიან, რათა ხელახალი გაშვებებით დაიჭირონ, მაგრამ მაინც იწვევენ პერიოდულ CI ჩავარდნებს.

## არასტაბილური ტესტების მართვა {#managing-flaky-tests}

### ავტომატური გასუფთავება

აღმოჩენა და გასუფთავება ხდება პროექტზე **ავტომატიზაციის გაფრთხილების** მეშვეობით. ყოველ პროექტს აქვს ნაგულისხმევი „არასტაბილური ტესტის აღმოჩენის“ ავტომატიზაცია, რომლის *ტრიგერი* ტესტს არასტაბილურად მონიშნავს, ხოლო *აღდგენა* აშორებს ნიშანს, როდესაც ტესტი გადის კონფიგურირებულ აღდგენის ფანჯარას (ნაგულისხმევი **14 დღე**) ხელახალი ტრიგერის გარეშე. შეასწორეთ ის **Settings → Automations**-ში, რათა შეცვალოთ აღდგენის ფანჯარა ან სრულად გათიშოთ აღდგენა, რათა ტესტები არასტაბილურად დარჩნენ მონიშნული, სანამ ხელით არ გაასუფთავებთ მათ.

### ხელით მართვა

ასევე შეგიძლიათ ხელით მონიშნოთ ან მოხსნათ ტესტები როგორც არასტაბილური ტესტის შემთხვევის დეტალურ გვერდზე. ეს სასარგებლოა, როდესაც:
- გსურთ აღიაროთ ცნობილი არასტაბილური ტესტი, სანამ მუშაობთ მის გამოსწორებაზე
- ტესტი არასწორად იყო მონიშნული ინფრასტრუქტურის პრობლემების გამო

## არასტაბილური ტესტების კარანტინში მოთავსება {#quarantining}

კარანტინში მოთავსება ხელს უშლის არასტაბილურ ტესტს CI-ის ბლოკირებაში, სანამ მას შეასწორებთ. ტესტის გვერდზე დაფაში, შეცვალეთ მისი მდგომარეობა **Muted**-ად ან **Skipped**-ად, ან კონფიგურაცია გაუკეთეთ ავტომატიზაციას **Settings → Automations**-ში, რომელიც აჩუმებს ან გამოტოვებს ტესტს, როდესაც ის არასტაბილური ხდება და კვლავ ააქტიურებს მას, როდესაც აღდგება. ტესტების გაშვებამდე, `mix test` კითხულობს პროექტის ყველა კარანტინში მოთავსებულ ტესტს და ავრცელებს მათ:

- **Muted**: ტესტი ეშვება და მისი ჩავარდნა კვლავ იქნება მოხსენიებული, მაგრამ გაშვება, რომლის ერთადერთი ჩავარდნებიც აჩუმებული ტესტებია, წარმატებით სრულდება. ხელახალი გაშვებები კვლავ ხელახლა უშვებენ მწყარ აჩუმებულ ტესტს, ამიტომ არასტაბილურს შეუძლია წარმატებით შესრულდეს და მოიხსენიებოდეს როგორც არასტაბილური.
- **Skipped**: ტესტი არ ეშვება. `mix test` ჩამოთვლის გამოტოვებულ ტესტებს გაშვების დაწყებამდე.

```text
Tuist: skipping 1 quarantined test:
  MyApp.CheckoutTest: create_order/2 times out
Tuist: 1 muted test run, and their failures do not fail the run.
```

გაშვება ჩვეულებრივად მწყარია, როდესაც ნებისმიერი ტესტი, რომელიც არ არის აჩუმებული, მწყარია, ან როდესაც ExUnit ადრე ჩერდება `--max-failures`-ის გამო.

> [!WARNING]
> **შეზღუდვები**
>
> - მხოლოდ Hex-ის პაკეტის ახალ ვერსიებს აქვთ კარანტინის გამოყენება. ადრეული ვერსიები აჩუმებულ და გამოტოვებულ ტესტებს სხვების მსგავსად უშვებენ, ამიტომ აჩუმებული ტესტის ჩავარდნა კვლავ აფუჭებს გაშვებას. განაახლეთ `tuist_ex`, სანამ მას დაეყრდნობით.
> - აჩუმებული ტესტები არ გამოიყენება `--warnings-as-errors`-თან ერთად, ან umbrella პროექტის ფესვიდან. მათი ჩავარდნები მაშინ აფუჭებენ გაშვებას. ნაცვლად ამისა, გაუშვით ტესტები umbrella-ს თითოეული აპლიკაციის შიგნით.
> - გამოტოვება ემთხვევა ტესტს მისი describe ბლოკისა და სახელის მიხედვით, არა მისი მოდულის მიხედვით. ტესტი იმავე describe ბლოკითა და სახელით სხვა მოდულში ასევე გამოიტოვება. იხილეთ [როგორ ირჩევს გამოტოვება ტესტებს](#how-skipping-selects-tests).
> - გამოტოვებული ტესტი კვლავ ეშვება, როდესაც მას ირჩევთ `--only`-ით, `--include`-ით, ან `path:line`-ით, ან როდესაც ის არ არის გამოცხადებული `test`-ით, როგორიცაა StreamData `property`.
> - თუ `mix test` ვერ კითხულობს კარანტინში მოთავსებულ ტესტებს, ის უშვებს ყველა ტესტს და ითვლის ყველა ჩავარდნას.
> - კარანტინში მოთავსებული ტესტების წაკითხვა მოითხოვს სერთიფიკატებს, მაშინაც კი, თუ პროექტი საჯაროა. გაშვება `TUIST_TOKEN`-ის, `mix tuist.login` სესიის, ან უწყვეტი ინტეგრაციის იდენტობის ტოკენის გარეშე არ ავრცელებს კარანტინს. ეს მოიცავს pull request-ებს fork-ებიდან, რომლებიც ჩვეულებრივ სექრეტების გარეშე ეშვებიან.
> - `--cover`-ით, გამოტოვებული ტესტი ითვლება როგორც ამოღებული: ხაზები, რომლებსაც მხოლოდ ის ფარავდა, მოიხსენიება როგორც დაუფარავი.
>
> `mix test` ასახელებს ტესტებს, რომლებიც გამოტოვებამ შეცდომით დატოვა, და გამოტოვებულ ტესტებს, რომლებიც მაინც ეშვებოდნენ, მისი შეჯამების შემდეგ.

### როგორ ირჩევს გამოტოვება ტესტებს {#how-skipping-selects-tests}

გამოტოვებული ტესტი გამოიტოვება ExUnit ფილტრით მისი სრული სახელის მიხედვით, როგორიცაა `--exclude "test:test create_order/2 times out"`. ExUnit ფილტრებს ასევე არ შეუძლიათ მოდულის დამთხვევა, ამიტომ:

- ტესტი იმავე describe ბლოკითა და სახელით სხვა მოდულში ასევე გამოიტოვება. `mix test` ასახელებს იმ ტესტებს გაშვების შემდეგ.
- ტესტი, რომელსაც ირჩევთ `--only`-ით, `--include`-ით ან `path:line`-ით, ეშვება მაშინაც კი, თუ ის გამოტოვებულია, რადგან ExUnit include ფილტრებს exclude ფილტრების შემდეგ ავრცელებს. ასევე ეშვება ტესტი, რომელიც არ არის გამოცხადებული `test`-ით, როგორიცაა StreamData `property`. `mix test` ასახელებს ამ ტესტებს გაშვების შემდეგ.

### კარანტინში მოთავსებული ტესტების ხელახლა გაშვება {#running-quarantined-tests-again}

გადაეცით `--no-quarantine`, რათა გაუშვათ ყველა ტესტი და დაითვალოთ ყველა ჩავარდნა, მაგალითად, შესწორების შესამოწმებლად:

```bash
mix test --no-quarantine
```

დააბრუნეთ ტესტი მის გვერდზე მდგომარეობაში **Enabled**, რათა ის მოიცვას მომავალმა გაშვებებმა. გამოტოვებული ტესტი ახალ შედეგებს არ წარმოქმნის, სანამ ის ხელახლა არ გაეშვება.

თუ `mix test` ვერ კითხულობს კარანტინში მოთავსებულ ტესტებს, ის ბეჭდავს გაფრთხილებას და უშვებს ყველა ტესტს მათ გარეშე. სერთიფიკატების ან კონფიგურირებული პროექტის გარეშე, ის უშვებს ყველა ტესტს გაფრთხილების გარეშე.

Hex პაკეტი ჯერჯერობით არ ატარებს ახალი ტესტების სტრეს-ტესტირებას.

## არასტაბილური მდგომარეობის კითხვა {#querying}

მონაცემები ხელმისაწვდომია HTTP-ით. სრული სიისთვის მარშრუტების, ფილტრების და პასუხის ველების შესახებ, იხილეთ [Test Cases endpoints](https://tuist.dev/api/docs#tag/test-cases) API ცნობარში. სატესტო შემთხვევის არასტაბილურად აღსანიშნავად ან ნიშნის მოსახსნელად, გაგზავნეთ `PATCH /api/projects/{account_handle}/{project_handle}/tests/test-cases/{test_case_id}` `is_flaky`-ით, ან გამოიყენეთ `update_test_case` Model Context Protocol ინსტრუმენტი.
