# Elixir-ის არასტაბილური ტესტები {#elixir-flaky-tests}

არასტაბილური ტესტებია ისეთი ტესტები, რომლებიც ერთი და იმავე კოდით რამდენიმეჯერ გაშვებისას განსხვავებულ შედეგებს (წარმატება ან შეცდომა) აჩვენებენ. ისინი ამცირებენ ნდობას თქვენი ტესტების სუიტის მიმართ და ფუჭად ხარჯავენ დეველოპერების დროს ცრუ შეცდომების გამოკვლევაში. Tuist ავტომატურად აღმოაჩენს არასტაბილურ ტესტებს და გეხმარებათ მათ თვალყურის დევნაში.

> [!IMPORTANT] REQUIREMENTS
> - დაასრულეთ <.localized_link href="/guides/get-started/elixir-project">Elixir-ის საერთო კონფიგურაცია</.localized_link>, რათა შეატყობინოთ თქვენი ტესტების გაშვებები

![Phoenix აპლიკაციის არასტაბილური ტესტები](/images/guides/features/elixir/flaky-tests.png)

## როგორ მუშაობს არასტაბილურობის აღმოჩენა {#how-it-works}

Tuist არასტაბილურ ტესტებს ორი გზით აღმოაჩენს:

### ტესტების ხელახალი გაშვება {#test-retries}

ExUnit თითოეულ ტესტს ერთხელ უშვებს, ამიტომ პერიოდულად მარცხდებადი ტესტი იგივედ ჩანს, როგორც გაუმართავი. ხელახალი გაშვების ჩართვისას Hex-ის პაკეტი კიდევ ერთხელ უშვებს წარუმატებელ ტესტებს, თქვენ მიერ მითითებული რაოდენობის ჯერამდე. ტესტი, რომელიც ხელახალი გაშვებისას გადის, მონიშნულია როგორც არასტაბილური, ხოლო გაშვება წარმატებით სრულდება, თუ ყველა წარუმატებელი ტესტი საბოლოოდ გადის.

ხელახალი გაშვება ნაგულისხმევად გამორთულია. მათ ჩასართავად დაამატეთ `test_retries` თქვენს არსებულ Tuist-ის პარამეტრებში `mix.exs`-ში:

```elixir
tuist: [project: "account/project", cache: true, test_retries: 2]
```

ან ერთი გაშვებისთვის, ფლაგის ან გარემოს ცვლადის გამოყენებით:

```bash
mix test --retries 2
TUIST_TEST_RETRIES=2 mix test
```

ფლაგს აქვს უპირატესობა გარემოს ცვლადთან მიმართებაში, ხოლო გარემოს ცვლადს — `mix.exs`-თან მიმართებაში.

მხოლოდ წარუმატებელი ტესტები გაეშვება ხელახლა, ისევე როგორც `mix test --failed` უშვებს მათ, ხოლო დაშბორდი აჩვენებს ტესტის თითოეულ მცდელობას და მის ხანგრძლივობას. გაშვება, რომელიც ExUnit-მა ადრე შეწყვიტა `--max-failures`-ის გამო, არ გაეშვება ხელახლა. ასევე არ გაეშვება ხელახლა გაშვება, რომლის წარუმატებელი ტესტებიც ყველა დროის ამოწურვას ექვემდებარება, რადგან ყოველი ხელახალი გაშვება კვლავ დაელოდება ყველა დროის ამოწურვას. ხელახალი გაშვება ასევე გამოიტოვება `--warnings-as-errors`-ით, რასაც `mix test` აღარ აღასრულებს, და umbrella პროექტის ფესვიდან; ტესტების ხელახლა გასაშვებად გაუშვით ისინი მისი ერთ-ერთი აპლიკაციის შიგნით.

![არასტაბილური ExUnit ტესტი და მისი ისტორია](/images/guides/features/elixir/flaky-test-case.png)

### ჯვარედინი გაშვებების აღმოჩენა {#cross-run-detection}

ტესტების ხელახალი გაშვების გარეშეც, Tuist-ს შეუძლია არასტაბილური ტესტების აღმოჩენა ერთი და იმავე კომიტზე სხვადასხვა CI გაშვებების შედეგების შედარებით. თუ ტესტი გადის ერთ CI გაშვებაში, მაგრამ მარცხდება იმავე კომიტის სხვა გაშვებაში, ორივე გაშვება მონიშნულია როგორც არასტაბილური.

ეს განსაკუთრებით სასარგებლოა იმ არასტაბილური ტესტების დასაჭერად, რომლებიც საკმარისად თანმიმდევრულად არ მარცხდებიან, რათა ხელახალი გაშვებებით დაფიქსირდნენ, მაგრამ მაინც იწვევენ პერიოდულ CI შეცდომებს.

## არასტაბილური ტესტების მართვა {#managing-flaky-tests}

### ავტომატური გასუფთავება

აღმოჩენა და გასუფთავება ხდება პროექტზე არსებული **ავტომატიზაციის ალერტის** მეშვეობით. ყოველ პროექტს აქვს ნაგულისხმევი „არასტაბილური ტესტების აღმოჩენის“ ავტომატიზაცია, რომლის *ტრიგერი* მონიშნავს ტესტს როგორც არასტაბილურს, ხოლო *აღდგენა* ხსნის ამ ნიშანს, როცა ტესტი გადის კონფიგურირებულ აღდგენის პერიოდს (ნაგულისხმევი **14 დღე**) ხელახალი ტრიგერის გარეშე. ჩაასწორეთ ის **პარამეტრები → ავტომატიზაციები** განყოფილებაში, რათა შეცვალოთ აღდგენის ფანჯარა ან სრულად გამორთოთ აღდგენა, ისე რომ ტესტები დარჩეს მონიშნული როგორც არასტაბილური, სანამ ხელით არ გაასუფთავებთ მათ.

### ხელით მართვა

ასევე შეგიძლიათ ხელით მონიშნოთ ან მოხსნათ ტესტების არასტაბილურობა სატესტო შემთხვევის დეტალური გვერდიდან. ეს სასარგებლოა, როდესაც:
- გსურთ აღიაროთ ცნობილი არასტაბილური ტესტი, სანამ მუშაობთ მის გამოსწორებაზე
- ტესტი არასწორად იყო მონიშნული ინფრასტრუქტურის პრობლემების გამო

## არასტაბილური ტესტების კარანტინში მოქცევა {#quarantining}

კარანტინი უშლის ხელს არასტაბილურ ტესტს CI-ის ბლოკირებაში, სანამ მას შეასწორებთ. დაფის ტესტის გვერდზე შეცვალეთ მისი მდგომარეობა **ჩუმად**-ზე ან **გამოტოვებულ**-ზე, ან მოაწყვეთ ავტომატიზაცია **პარამეტრები → ავტომატიზაციები** განყოფილებაში, რომელიც ჩააჩუმებს ან გამოტოვებს ტესტს, როცა ის ხდება არასტაბილური და ხელახლა ჩართავს მას აღდგენის შემდეგ. სანამ ტესტებს გაუშვებს, `mix test` კითხულობს პროექტის ყველა კარანტინში მყოფ ტესტს და ავრცელებს მათ:

- **ჩუმად**: ტესტი გადის და მისი შეცდომა კვლავ იგზავნება, მაგრამ გაშვება წარმატებით სრულდება, თუ ერთადერთი შეცდომები ჩუმად მყოფი ტესტებია. ხელახალი ცდები კვლავ ახდენენ ჩუმად მყოფი ვერ მუშაობდი ტესტის ხელახალ გაშვებას, ასე რომ არასტაბილურმა ტესტმა შეიძლება გაიაროს და იყოს მონიშნული როგორც არასტაბილური.
- **გამოტოვებული**: ტესტი არ გადის. `mix test` აჩვენებს გამოტოვებულ ტესტებს გაშვების დაწყებამდე.

```text
Tuist: skipping 1 quarantined test:
  MyApp.CheckoutTest: create_order/2 times out
Tuist: 1 muted test run, and their failures do not fail the run.
```

გაშვება მარცხდება ჩვეულებრივად, როდესაც ნებისმიერი ტესტი, რომელიც არ არის ჩაჩუმებული, მარცხდება, ან როდესაც ExUnit ადრე წყვეტს `--max-failures`-ის გამო.

> [!WARNING]
> **შეზღუდვები**
>
> - კარანტინს მხოლოდ Hex-ის პაკეტის ბოლო ვერსიები ავრცელებენ. ადრეული ვერსიები ჩაჩუმებულ და გამოტოვებულ ტესტებს ისევე უშვებენ, როგორც სხვებს, ამიტომ ჩაჩუმებული ტესტის შეცდომა კვლავ აცდენს გაშვებას. განაახლეთ `tuist_ex`, სანამ მას დაეყრდნობით.
> - ჩაჩუმებული ტესტები არ ვრცელდება `--warnings-as-errors`-ით, ან umbrella პროექტის ფესვიდან. მათი შეცდომები მაშინ აცდენენ გაშვებას. ნაცვლად ამისა, გაუშვით ტესტები umbrella-ის თითოეული აპლიკაციის შიგნით.
> - გამოტოვება ემთხვევა ტესტს მისი describe ბლოკისა და სახელის მიხედვით, არა მოდულის. ტესტი იგივე describe ბლოკითა და სახელით სხვა მოდულში ასევე გამოტოვებული იქნება. იხილეთ [როგორ ირჩევს გამოტოვება ტესტებს](#how-skipping-selects-tests).
> - გამოტოვებული ტესტი მაინც გაეშვება, როდესაც მას ირჩევთ `--only`, `--include` ან `path:line`-ით, ან როდესაც ის არ არის განცხადებული `test`-ით, მაგალითად StreamData `property`.
> - თუ `mix test` ვერ კითხულობს კარანტინში მოქცეულ ტესტებს, ის უშვებს ყველა ტესტს და ითვლის ყველა შეცდომას.
> - კარანტინში მოქცეული ტესტების წაკითხვა საჭიროებს სერთიფიკატებს, მაშინაც კი, თუ პროექტი საჯაროა. გაშვება `TUIST_TOKEN`-ის, `mix tuist.login` სესიის ან უწყვეტი ინტეგრაციის იდენტობის ტოკენის გარეშე არ ავრცელებს კარანტინს. ეს მოიცავს pull request-ებს fork-ებიდან, რომლებიც ჩვეულებრივ გაეშვება საიდუმლოებების გარეშე.
> - `--cover`-ით, გამოტოვებული ტესტი ითვლება როგორც ამოღებული: ხაზები, რომლებსაც მხოლოდ ის ფარავდა, მოხსენებულია როგორც დაუფარავი.
>
> `mix test` ასახელებს ტესტებს, რომლებიც გამოტოვებამ შეცდომით გამოტოვა, და გამოტოვებულ ტესტებს, რომლებიც მაინც გაეშვა, თავისი შეჯამების შემდეგ.

### როგორ ირჩევს გამოტოვება ტესტებს {#how-skipping-selects-tests}

გამოტოვებული ტესტი გამოიტოვება ExUnit-ის ფილტრით მისი სრული სახელის მიხედვით, მაგალითად `--exclude "test:test create_order/2 times out"`. ExUnit-ის ფილტრებს ასევე არ შეუძლიათ მოდულის დამთხვევა, ამიტომ:

- ტესტი იმავე describe ბლოკითა და სახელით სხვა მოდულში ასევე გამოიტოვება. `mix test` ასახელებს იმ ტესტებს გაშვების შემდეგ.
- ტესტი, რომელსაც ირჩევთ `--only`, `--include` ან `path:line`-ით, მაინც გაეშვება, თუნდაც გამოტოვებულად იყოს მონიშნული, რადგან ExUnit include ფილტრებს exclude ფილტრების შემდეგ ავრცელებს. ასევე ხდება ტესტთან, რომელიც არ არის განცხადებული `test`-ით, მაგალითად StreamData `property`. `mix test` ასახელებს ამ ტესტებს გაშვების შემდეგ.

### კარანტინში მოქცეული ტესტების ხელახლა გაშვება {#running-quarantined-tests-again}

გადაეცით `--no-quarantine` ყველა ტესტის გასაშვებად და ყველა შეცდომის დასათვლელად, მაგალითად, შესწორების შესამოწმებლად:

```bash
mix test --no-quarantine
```

დააბრუნეთ ტესტი მის გვერდზე მდგომარეობაში **Enabled**, რათა ის მომავალ გაშვებებში ჩაირთოს. გამოტოვებული ტესტი ახალ შედეგებს არ გამოიმუშავებს, სანამ ხელახლა არ გაეშვება.

თუ `mix test` ვერ კითხულობს კარანტინში მოქცეულ ტესტებს, ის ბეჭდავს გაფრთხილებას და უშვებს ყველა ტესტს მათ გარეშე. სერთიფიკატების ან კონფიგურირებული პროექტის გარეშე, ის უშვებს ყველა ტესტს გაფრთხილების გარეშე.

Hex პაკეტი ჯერჯერობით ახალ ტესტებს სტრეს-ტესტირებას არ უკეთებს.

## არასტაბილური მდგომარეობის გამოკითხვა {#querying}

მონაცემები ხელმისაწვდომია HTTP-ით. სრული სიისთვის მარშრუტების, ფილტრების და პასუხის ველების შესახებ, იხილეთ [სატესტო შემთხვევების ბოლოწერტილები](https://tuist.dev/api/docs#tag/test-cases) API ცნობარში. სატესტო შემთხვევის არასტაბილურად მონიშვნის ან ნიშნის მოხსნისთვის, გაგზავნეთ `PATCH /api/projects/{account_handle}/{project_handle}/tests/test-cases/{test_case_id}` `is_flaky`-ით, ან გამოიყენეთ `update_test_case` Model Context Protocol ინსტრუმენტი.
