# Bazel-ის არასტაბილური ტესტები {#bazel-flaky-tests}

> [!IMPORTANT]
> **მოთხოვნები**
>
> - <.localized_link href="/guides/features/test-insights/bazel">Bazel-ის ტესტების ანალიტიკა</.localized_link> კონფიგურირებულია `tuist bazel setup`-ით.

<!-- @snippet: ./_intro -->

## როგორ მუშაობს არასტაბილურობის აღმოჩენა {#how-it-works}

Tuist იყენებს ცალკეულ ტესტ-ქეისებს Bazel-ის `test.xml` ანგარიშებიდან, რათა აღმოაჩინოს შეუსაბამო შედეგები ხელახლა ცდებისა და უწყვეტი ინტეგრაციის დროს ერთი და იმავე კომიტისა და სამიზნე შერჩევის გაშვებებს შორის. ლოკალური გაშვებები ჩანს, მაგრამ ავტომატურად არ ნიშნავს ტესტ-ქეისებს როგორც არასტაბილურს.

### ტესტის ხელახლა ცდები {#test-retries}

ხელახლა ცდები სავალდებულო არ არის და დამოუკიდებელია კარანტინისგან. `--flaky_test_attempts=3` საშუალებას აძლევს **სამ სრულ Bazel ცდას** თითოეულ ტესტზე, და არა სამ დამატებით ხელახლა ცდას. შეინახეთ თქვენი არსებული ხელახლა ცდების კონფიგურაცია `.bazelrc`-ში ან გადაეცით ის პირდაპირ:

```sh
tuist bazel test -- --flaky_test_attempts=3 //app:tests
```

ხელახლა ცდები რეალურად უნდა შესრულდეს, რომ Tuist-მა დააკვირდეს მათ შედეგებს. Bazel-ის სამიზნის არასტაბილურობის შეჯამება მარტო ვერ განსაზღვრავს, რომელი კონკრეტული ქეისი იყო არასტაბილური.

### ჯვარედინი გაშვებების აღმოჩენა {#cross-run-detection}

გაშვებების შედარებას სჭირდება კომიტისა და ბრენჩის მეტამონაცემები. მიუთითეთ ისინი, თუ თქვენი აგების გარემო უკვე არ აქვეყნებს მათ:

```sh
tuist bazel test -- \
  --build_metadata=CI=true \
  --build_metadata=GIT_COMMIT="$GIT_COMMIT" \
  --build_metadata=GIT_BRANCH="$GIT_BRANCH" //app:tests
```

ქეისები იდენტიფიცირდება სამიზნის ლეიბლით, კლასის სახელით (საჭიროების შემთხვევაში სუიტის სახელზე გადასვლით) და ტესტის სახელით, როგორც ეს აღწერილია <.localized_link href="/guides/features/test-insights/bazel">Bazel-ის ტესტების ანალიტიკაში</.localized_link>.

## არასტაბილური ტესტების კარანტინში მოქცევა {#quarantining}

<!-- @snippet: ./_quarantine-intro -->

`tuist bazel test` იღებს კარანტინის პოლიტიკას ყოველ გამოძახებამდე და ავრცელებს მას ძირითად `bazel test` გაშვებაზე. ჩვეულებრივი `bazel test` კვლავ აჩვენებს ტესტების შედეგებს, მაგრამ არ ავრცელებს კარანტინს:

```sh
tuist bazel test -- //app:tests
```

არგუმენტები `--`-ის შემდეგ გადაეცემა `bazel test`-ს. გამოიყენეთ `--path` პროექტისა და სამუშაო დირექტორიის შესარჩევად, და `--bazel` სხვა შესრულებადი ფაილის შესარჩევად, მაგალითად `bazelisk`. სახელიანი Bazel კონფიგურაცია, როგორიცაა `--config=ci`, სავალდებულო არ არის და იგივენაირად მუშაობს.

### დადუმება {#mute}

გამოიყენეთ **დადუმება** როგორც ძირითადი კარანტინის სამუშაო ნაკადი. დადუმებული ქეისები კვლავ ეშვება, მათი შეცდომები ჩანს და ჯანსაღი დაძმობილებული ქეისები კვლავ ახდენენ გავლენას შედეგზე. Tuist Bazel-ის ტესტის შეცდომით დასრულებას წარმატებად აქცევს მხოლოდ მაშინ, როცა ანგარიშები თითოეულ ჩავარდნილ სამიზნეში ყოველ შეცდომას მიაწერენ დადუმებულ ქეისს. აგების შეცდომები, დროის ამოწურვა, გაწყვეტილი გაშვებები, დაკარგული ან არასრული ანგარიშები და დადუმებული ნაკრების გარეთ არსებული შეცდომები ინარჩუნებენ Bazel-ის შეცდომის სტატუსს.

### გამოტოვება {#skip}

გამოტოვება მუშაობს თითოეული Bazel სამიზნისთვის: ერთი ქეისის გამოტოვება გამორიცხავს მთელ სამიზნეს, ჯანსაღი ქეისების ჩათვლით, რადგან Bazel ვერ ფილტრავს ცალკეულ ქეისებს ყოველი ტესტის ფრეიმვორკისთვის. უპირატესობა მიანიჭეთ **დადუმებას**, თუ არ აპირებთ მთელი სამიზნის გამორიცხვას. ბრძანება ბეჭდავს ყოველ გამორიცხულ სამიზნის ლეიბლს, რათა აგების ჟურნალებში ჩანდეს, რა გამოტოვა კარანტინის პოლიტიკამ.

თუ გამოტოვებული სამიზნე აღარ არსებობს, Tuist ასახელებს მას გაფრთხილებაში და ასრულებს გაშვებას ამ გამორიცხვის გარეშე. დააბრუნეთ მოძველებული ქეისები **ჩართულ** მდგომარეობაში, რათა სამუდამოდ წაშალოთ მათი პოლიტიკები. თუ ტესტის სამიზნეები აღარ დარჩა, Bazel ინარჩუნებს თავის ჩვეულებრივ „ტესტები ვერ მოიძებნა“ დასრულების სტატუსს.

### კარანტინში მყოფი ტესტების ხელახლა გაშვება {#running-quarantined-tests-again}

შეცდომის შესასწავლად ან შესწორების დასადასტურებლად, აუარეთ გვერდი კარანტინის პოლიტიკას:

```sh
tuist bazel test --no-quarantine -- --nocache_test_results //app:tests
```

დააბრუნეთ ქეისი **ჩართულ** მდგომარეობაში, რათა ჩართოთ მისი სამიზნე შემდგომ ჩვეულებრივ გაშვებებში. გამოტოვებული ქეისები არ წარმოქმნიან ახალ შესრულებებს, სანამ არ იქნებიან ცხადად ჩართული, ამიტომ ავტომატიზაციას, რომელიც ეყრდნობა წარმატებულ ახალ გაშვებებს, სჭირდება ვალიდაციის გაშვება, სანამ მათ აღდგენას შეძლებს.

### შეზღუდვები {#limitations}

- ცხადად მითითებული `--build_event_json_file` ან `--target_pattern_file` ვერ იქნება გაერთიანებული აქტიურ კარანტინთან. გადაეცით სამიზნის შაბლონები პირდაპირ.
- თუ Tuist ვერ იღებს კარანტინის პოლიტიკას, ბრძანება ჩერდება ტესტების გაშვებამდე. ის არასდროს ავრცელებს ნაწილობრივ პოლიტიკას. გამოიყენეთ `--no-quarantine`, როცა განზრახვით გსურთ გაშვება მის გარეშე.
- შეცდომა, რომელიც ემთხვევა დადუმებას, ჩაწერილს ძველი სუიტაზე დაფუძნებული იდენტობით, რჩება ბლოკირებად და ბრძანება ასახელებს პოლიტიკას ხელახლა გამოსაყენებლად.

იხილეთ Bazel-ის [ტესტის ფილტრები](https://bazel.build/docs/user-manual#test-filter), [ბრძანების პარამეტრები](https://bazel.build/reference/command-line-reference) და [აგების მოვლენების აღწერები](https://bazel.build/remote/bep-glossary) საბაზისო ქცევის შესახებ.
