# Bazel-ის არასტაბილური ტესტები {#bazel-flaky-tests}

> [!IMPORTANT]
> **მოთხოვნები**
>
> - <.localized_link href="/guides/features/test-insights/bazel">Bazel-ის ტესტების ანალიტიკა</.localized_link> კონფიგურირებულია `tuist bazel setup`-ით.

<!-- @snippet: ./_intro -->

## როგორ მუშაობს არასტაბილურობის აღმოჩენა {#how-it-works}

Tuist იყენებს ცალკეულ ტესტ-ქეისებს Bazel-ის `test.xml` ანგარიშებიდან, რათა აღმოაჩინოს შეუსაბამო შედეგები ხელახალი გაშვებებისას და უწყვეტი ინტეგრაციის პროცესში ერთი და იმავე კომიტისა და სამიზნე შერჩევის სხვადასხვა გაშვებისას. ლოკალური გაშვებები ჩანს, მაგრამ ისინი ავტომატურად არ მონიშნავენ ტესტ-ქეისებს როგორც არასტაბილურს.

### ტესტების ხელახალი გაშვება {#test-retries}

ხელახალი გაშვებები არის არასავალდებულო და დამოუკიდებელია კარანტინისგან. `--flaky_test_attempts=3` საშუალებას იძლევა თითოეული ტესტისთვის გამოიყენოთ **სულ სამი Bazel-ის მცდელობა**, და არა სამი დამატებითი ხელახალი გაშვება. შეინარჩუნეთ თქვენი არსებული ხელახალი გაშვების კონფიგურაცია `.bazelrc`-ში ან გადაეცით ის პირდაპირ:

```sh
tuist bazel test -- --flaky_test_attempts=3 //app:tests
```

იმისათვის, რომ Tuist-მა დააკვირდეს შედეგებს, ხელახალი გაშვებები რეალურად უნდა შესრულდეს. Bazel-ის სამიზნის არასტაბილურობის შეჯამება მარტო ვერ განსაზღვრავს, რომელი კონკრეტული ქეისი იყო არასტაბილური.

### გაშვებებს შორის აღმოჩენა {#cross-run-detection}

გაშვებების შედარებას სჭირდება კომიტისა და ბრენჩის მეტამონაცემები. მიუთითეთ ისინი, თუ თქვენი აგების გარემო მათ ავტომატურად არ აქვეყნებს:

```sh
tuist bazel test -- \
  --build_metadata=CI=true \
  --build_metadata=GIT_COMMIT="$GIT_COMMIT" \
  --build_metadata=GIT_BRANCH="$GIT_BRANCH" //app:tests
```

ქეისები იდენტიფიცირდება სამიზნის ლეიბლით, კლასის სახელით (სუიტის სახელზე გადასვლის შემთხვევაში) და ტესტის სახელით, როგორც ეს აღწერილია <.localized_link href="/guides/features/test-insights/bazel">Bazel-ის ტესტების ანალიტიკაში</.localized_link>.

## არასტაბილური ტესტების კარანტინში მოქცევა {#quarantining}

<!-- @snippet: ./_quarantine-intro -->

`tuist bazel test` იღებს კარანტინის პოლიტიკას ყოველი გამოძახების წინ და ავრცელებს მას ძირითად `bazel test` გაშვებაზე. ჩვეულებრივი `bazel test` კვლავ აჩვენებს ტესტების შედეგებს, მაგრამ არ ავრცელებს კარანტინს:

```sh
tuist bazel test -- //app:tests
```

არგუმენტები `--`-ის შემდეგ გადაეცემა `bazel test`-ს. გამოიყენეთ `--path` პროექტისა და სამუშაო დირექტორიის არჩევასთვის, ხოლო `--bazel` — სხვა შესრულებადი ფაილის, მაგალითად `bazelisk`-ის, არჩევასთვის. სახელიანი Bazel-ის კონფიგურაცია, როგორიცაა `--config=ci`, არის არასავალდებულო და მუშაობს იგივე პრინციპით.

### ჩუმი რეჟიმი {#mute}

გამოიყენეთ **ჩუმი რეჟიმი** როგორც კარანტინის ძირითადი სამუშაო ნაკადი. ჩუმ რეჟიმში მყოფი ქეისები კვლავ გაშვებადი რჩება, მათი შეცდომები ჩანს და ჯანსაღი დაძმობილებული ქეისები კვლავ ახდენენ გავლენას შედეგზე. Tuist Bazel-ის ტესტის შეცდომის სტატუსს წარმატებად ცვლის მხოლოდ მაშინ, როცა ანგარიშები თითოეული შეცდომიანი სამიზნის ყველა შეცდომას მიაწერენ ჩუმ რეჟიმში მყოფ ქეისს. აგების შეცდომები, დროის ამოწურვა, შეწყვეტილი გაშვებები, დაკარგული ან არასრული ანგარიშები და ჩუმი რეჟიმის გარეთ მყოფი შეცდომები ინარჩუნებენ Bazel-ის შეცდომის სტატუსს.

### გამოტოვება {#skip}

გამოტოვება მუშაობს Bazel-ის თითოეული სამიზნის მიხედვით: ერთი ქეისის გამოტოვება გამორიცხავს მთელ სამიზნეს, ჯანსაღი ქეისების ჩათვლით, რადგან Bazel ვერ ფილტრავს ცალკეულ ქეისებს ყოველი ტესტ-ფრეიმვორკისთვის. უპირატესობა მიანიჭეთ **ჩუმ რეჟიმს**, თუ არ აპირებთ მთელი სამიზნის გამორიცხვას. ბრძანება ბეჭდავს ყველა გამორიცხულ სამიზნის ლეიბლს, რათა აგების ჟურნალებში ჩანდეს, რა გამოტოვა კარანტინის პოლიტიკამ.

თუ გამოტოვებული სამიზნე აღარ არსებობს, Tuist აჩვენებს მას გაფრთხილებაში და ასრულებს გაშვებას ამ გამორიცხვის გარეშე. დააბრუნეთ მოძველებული ქეისები **ჩართულ** მდგომარეობაში, რათა სამუდამოდ წაშალოთ მათი პოლიტიკები. თუ არ დარჩა ტესტ-სამიზნეები, Bazel ინარჩუნებს თავის ჩვეულებრივ „ტესტები ვერ მოიძებნა“ გასვლის სტატუსს.

### კარანტინში მყოფი ტესტების ხელახლა გაშვება {#running-quarantined-tests-again}

გასწორების შესასწავლად ან დასადასტურებლად, აუარეთ გვერდი კარანტინის პოლიტიკას:

```sh
tuist bazel test --no-quarantine -- --nocache_test_results //app:tests
```

დააბრუნეთ ქეისი **ჩართულ** მდგომარეობაში, რათა მისი სამიზნე ჩაერთოს შემდგომ ჩვეულებრივ გაშვებებში. გამოტოვებული ქეისები არ წარმოქმნიან ახალ გაშვებებს, სანამ ისინი ცალსახად არ ჩაირთვებიან, ამიტომ ავტომატიზაციას, რომელიც ეფუძნება წარმატებულ ახალ გაშვებებს, სჭირდება დასადასტურებელი გაშვება, სანამ შეძლებს მათ აღდგენას.

### შეზღუდვები {#limitations}

- ცალსახა `--build_event_json_file` ან `--target_pattern_file` ვერ კომბინირდება აქტიურ კარანტინთან. გადაეცით სამიზნის შაბლონები პირდაპირ.
- თუ Tuist ვერ იღებს კარანტინის პოლიტიკას, ბრძანება ჩერდება ტესტების გაშვებამდე. ის არასდროს ავრცელებს ნაწილობრივ პოლიტიკას. გამოიყენეთ `--no-quarantine`, როცა განზრახვით გსურთ გაშვება მის გარეშე.
- შეცდომა, რომელიც ემთხვევა ჩუმ რეჟიმს, ჩაწერილს ძველი სუიტაზე დაფუძნებული იდენტიფიკატორით, რჩება ბლოკირებად და ბრძანება ასახელებს პოლიტიკას ხელახლა გამოყენებისთვის.

Bazel-ის [ტესტების ფილტრები](https://bazel.build/docs/user-manual#test-filter), [ბრძანების პარამეტრები](https://bazel.build/reference/command-line-reference) და [აგების მოვლენების აღწერები](https://bazel.build/remote/bep-glossary) იხილეთ ძირითადი ქცევის გასაგებად.
