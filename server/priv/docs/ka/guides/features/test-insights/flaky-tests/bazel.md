# Bazel-ის არასტაბილური ტესტები {#bazel-flaky-tests}

> [!IMPORTANT]
> **მოთხოვნები**
>
> - <.localized_link href="/guides/features/test-insights/bazel">Bazel-ის ტესტების ინსაიტები</.localized_link> კონფიგურირებულია `tuist bazel setup`-ით.

<!-- @snippet: ./_intro -->

## როგორ მუშაობს არასტაბილურობის აღმოჩენა {#how-it-works}

Tuist იყენებს ცალკეულ ტესტქეისებს Bazel-ის `test.xml` ანგარიშებიდან, რათა აღმოაჩინოს შეუსაბამო შედეგები ხელახალი ცდებისა და ერთი და იგივე კომიტისა და სამიზნის შერჩევის გაშვებების მიხედვით უწყვეტი ინტეგრაციის დროს. ლოკალური გაშვებები ჩანს, მაგრამ ავტომატურად არ მონიშნავს ტესტქეისებს როგორც არასტაბილურს.

### ტესტების ხელახალი ცდები {#test-retries}

ხელახალი ცდები არის სურვილისამებრ და დამოუკიდებელია კარანტინისგან. `--flaky_test_attempts=3` საშუალებას იძლევა თითოეული ტესტისთვის **სულ სამი Bazel-ის ცდა**, და არა სამი დამატებითი ცდა. შეინახეთ თქვენი არსებული ხელახალი ცდების კონფიგურაცია `.bazelrc`-ში ან გადაეცით ის პირდაპირ:

```sh
tuist bazel test -- --flaky_test_attempts=3 //app:tests
```

ხელახალი ცდები რეალურად უნდა შესრულდეს, რომ Tuist-მა დააკვირდეს მათ შედეგებს. Bazel-ის სამიზნის არასტაბილურობის შეჯამება მარტო არ ასახელებს, რომელი კონკრეტული ტესტქეისი იყო არასტაბილური.

### გაშვებებს შორის აღმოჩენა {#cross-run-detection}

გაშვებების შედარებას სჭირდება კომიტისა და ბრენჩის მეტამონაცემები. მიეცით ისინი, თუ თქვენი აგების გარემო ჯერ არ აქვეყნებს მათ:

```sh
tuist bazel test -- \
  --build_metadata=CI=true \
  --build_metadata=GIT_COMMIT="$GIT_COMMIT" \
  --build_metadata=GIT_BRANCH="$GIT_BRANCH" //app:tests
```

ტესტქეისები იდენტიფიცირდება სამიზნის ლეიბლით, კლასის სახელით (სუიტის სახელზე დაბრუნებით) და ტესტის სახელით, როგორც აღწერილია <.localized_link href="/guides/features/test-insights/bazel">Bazel-ის ტესტების ინსაიტებში</.localized_link>.

## არასტაბილური ტესტების კარანტინში მოთავსება {#quarantining}

<!-- @snippet: ./_quarantine-intro -->

`tuist bazel test` იღებს კარანტინის პოლიტიკას ყოველ გამოძახებამდე და ავრცელებს მას ძირითად `bazel test` გაშვებაზე. ჩვეულებრივი `bazel test` კვლავ აჩვენებს ტესტების შედეგებს, მაგრამ არ ავრცელებს კარანტინს:

```sh
tuist bazel test -- //app:tests
```

არგუმენტები `--`-ის შემდეგ გადაეცემა `bazel test`-ს. გამოიყენეთ `--path` პროექტისა და სამუშაო დირექტორიის შერჩევისთვის და `--bazel` სხვა შესრულებადი ფაილის, მაგალითად `bazelisk`-ის, შერჩევისთვის. სახელიანი Bazel-ის კონფიგურაცია, როგორიცაა `--config=ci`, არის სურვილისამებრ და მუშაობს იგივე გზით.

### მიჩქმალვა {#mute}

გამოიყენეთ **Mute** როგორც ძირითადი კარანტინის სამუშაო ნაკადი. მიჩქმალული ტესტქეისები განაგრძობენ გაშვებას, მათი შეცდომები ჩანს და ჯანსაღი დაძმობილებული ტესტქეისები კვლავ ახდენენ გავლენას შედეგზე. Tuist Bazel-ის ტესტის შეცდომის გამოსვლას წარმატებად აქცევს მხოლოდ მაშინ, როდესაც ანგარიშები თითოეული შეცდომიანი სამიზნის ყველა შეცდომას მიანიჭებენ მიჩქმალულ ტესტქეისს. აგების შეცდომები, დროის ამოწურვა, შეწყვეტილი გაშვებები, დაკარგული ან არასრული ანგარიშები და მიჩქმალული სიმრავლის გარეთ არსებული შეცდომები ინარჩუნებენ Bazel-ის შეცდომის სტატუსს.

### გამოტოვება {#skip}

გამოტოვება მუშაობს თითოეული Bazel-ის სამიზნის მიხედვით: ერთი ტესტქეისის გამოტოვება გამორიცხავს მთელ მის სამიზნეს, ჯანსაღი ტესტქეისების ჩათვლით, რადგან Bazel-ს არ შეუძლია ცალკეული ტესტქეისების ფილტრაცია ყოველი ტესტის ფრეიმვორკისთვის. უპირატესობა მიანიჭეთ **Mute**-ს, თუ არ აპირებთ მთელი სამიზნის გამორიცხვას. ბრძანება ბეჭდავს ყოველ გამორიცხულ სამიზნის ლეიბლს, რათა აგების ჟურნალებში ჩანდეს, რა გამოტოვა კარანტინის პოლიტიკამ.

თუ გამოტოვებული სამიზნე აღარ არსებობს, Tuist ასახელებს მას გაფრთხილებაში და ასრულებს გაშვებას ამ გამორიცხვის გარეშე. დააბრუნეთ ძველი ტესტქეისები **Enabled**-ში, რათა სამუდამოდ წაშალოთ მათი პოლიტიკები. თუ ტესტის სამიზნეები აღარ დარჩა, Bazel ინარჩუნებს თავის ჩვეულებრივ „ტესტები ვერ მოიძებნა“ გამოსვლის სტატუსს.

<!-- @snippet: ./_quarantined-passing -->

### კარანტინში მოთავსებული ტესტების ხელახლა გაშვება {#running-quarantined-tests-again}

გასწორების შესასწავლად ან დასადასტურებლად, აუარეთ გვერდი კარანტინის პოლიტიკას:

```sh
tuist bazel test --no-quarantine -- --nocache_test_results //app:tests
```

დააბრუნეთ ტესტქეისი **Enabled**-ში, რათა მისი სამიზნე ჩაერთოს მომდევნო ჩვეულებრივ გაშვებებში. გამოტოვებული ტესტქეისები არ წარმოქმნიან ახალ შესრულებებს მანამ, სანამ ცალსახად არ ჩაერთვებიან, ამიტომ ავტომატიზაციას, რომელიც ეფუძნება წარმატებულ ახალ გაშვებებს, სჭირდება დადასტურების გაშვება, სანამ მათ აღდგენას შეძლებს.

### შეზღუდვები {#limitations}

- ცალსახა `--build_event_json_file` ან `--target_pattern_file` არ შეიძლება გაერთიანდეს აქტიურ კარანტინთან. გადაეცით სამიზნის შაბლონები პირდაპირ.
- თუ Tuist-ს არ შეუძლია კარანტინის პოლიტიკის მიღება, ბრძანება ჩერდება ტესტების გაშვებამდე. ის არასდროს ავრცელებს ნაწილობრივ პოლიტიკას. გამოიყენეთ `--no-quarantine`, როდესაც განზრახვით გსურთ გაშვება მის გარეშე.
- შეცდომა, რომელიც ემთხვევა მიჩქმალვას, ჩაწერილს ძველი სუიტაზე დაფუძნებული იდენტობით, რჩება ბლოკირებად და ბრძანება ასახელებს პოლიტიკას ხელახლა გამოყენებისთვის.

Bazel-ის [ტესტების ფილტრები](https://bazel.build/docs/user-manual#test-filter), [ბრძანების პარამეტრები](https://bazel.build/reference/command-line-reference) და [აგების მოვლენების აღწერები](https://bazel.build/remote/bep-glossary) იხილეთ ძირითადი ქცევის გასაცნობად.
