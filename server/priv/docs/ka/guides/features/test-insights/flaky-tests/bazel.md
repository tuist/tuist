# Bazel-ის არასტაბილური ტესტები {#bazel-flaky-tests}

`tuist bazel test` იღებს Tuist-ის კარანტინის პოლიტიკას თითოეული გამოძახების წინ და ავრცელებს მას საბაზისო `bazel test` გაშვებაზე.

## კარანტინის გამოყენება {#applying-quarantine}

ტესტის გვერდზე შეცვალეთ მისი სტატუსი **Muted**-ზე, შემდეგ გაუშვით:

```sh
tuist bazel test -- //app:tests
```

არგუმენტები `--`-ის შემდეგ გადაეცემა `bazel test`-ს. გამოიყენეთ `--path` პროექტისა და სამუშაო დირექტორიის არჩევასთვის და `--bazel` სხვა შესრულებადი ფაილის, მაგალითად `bazelisk`-ის, არჩევასთვის. ჩვეულებრივი `bazel test` მაინც აჩვენებს ტესტების შედეგებს, მაგრამ არ იღებს და არ ავრცელებს Tuist-ის კარანტინის პოლიტიკებს.

კარანტინისთვის არ არის საჭირო არც Bazel-ის სახელიანი კონფიგურაცია და არც განმეორებითი ცდები. **Flaky Tests**, **Quarantined Tests** და ინდივიდუალური ტესტების გვერდები მხარდაჭერენ იგივე ხელით შესრულებად სტატუსის ცვლილებებს, როგორც სხვა აწყობის სისტემები. გამოიყენეთ **Settings → Automations** არასტაბილურობის ზღვრების, კარანტინის ქმედებების და აღდგენის ქმედებების კონფიგურაციისთვის.

### Mute {#mute}

გამოიყენეთ **Mute** როგორც ძირითადი კარანტინის სამუშაო ნაკადი. Muted საქმეები განაგრძობენ გაშვებას, მათი შეცდომები რჩება ხილული და ჯანსაღი დობილი საქმეები მაინც ახდენენ გავლენას შედეგზე. ახალი გაშვებები უზრუნველყოფენ აღდგენის მტკიცებულებას სამიზნისგან რომელიმე საქმის გამორიცხვის გარეშე.

Tuist კითხულობს დროებით ადგილობრივ build-event ფაილს და მითითებულ `test.xml` ანგარიშებს. ის ცვლის Bazel-ის ტესტის შეცდომის გასვლის კოდს წარმატებად მხოლოდ მაშინ, როდესაც სრული ანგარიშები თითოეული ჩავარდნილი სამიზნის ყველა შეტყობინებულ შეცდომას მიანიჭებენ muted საქმეს.

აწყობის შეცდომები, ვადის ამოწურვა, შეწყვეტილი გაშვებები, დაკარგული ან არასწორი ანგარიშები, არასრული მოვლენათა ნაკადები და muted სიმრავლის გარეთ არსებული შეცდომები ინარჩუნებენ Bazel-ის შეცდომის სტატუსს. ადგილობრივი მოვლენათა ფაილი შემოიფარგლება 64 მებიბაიტით, ხოლო ინდივიდუალური ანგარიშები — 5 მებიბაიტით. Tuist-ს სჭირდება საკუთარი ადგილობრივი build-event ფაილი muted შეცდომების დასადასტურებლად და ძველი გამოტოვებული სამიზნებიდან აღდგენისთვის, ამიტომ ცალსახა `--build_event_json_file` ვერ იქნება კომბინირებული აქტიურ muted ან გამოტოვებულ საქმეებთან. დაშორებული build-event ანგარიშგება რჩება კონფიგურირებული `tuist bazel setup`-ის მეშვეობით.

ორიგინალური Bazel-ის გამოძახება და ანგარიშები ინარჩუნებენ რეალურ შედეგებს. Tuist-ის სერვერი აღრიცხავს, იყო თუ არა საქმე კარანტინში გამოძახების დაწყებისას, მაშინაც კი, თუ მისი სტატუსი იცვლება ანგარიშის დამუშავებამდე.

### Skip {#skip}

გამოიყენეთ **Skip** მხოლოდ მაშინ, როდესაც გსურთ **მთლიანი Bazel სამიზნის** გამორიცხვა, მათ შორის იმ სამიზნის შიგნით არსებული ჯანსაღი საქმეებისაც. ერთი საქმის **Skipped**-ად მონიშვნა იწვევს ამ ეფექტს მთელ სამიზნეზე. Bazel-ის ინდივიდუალური საქმის ფილტრის სინტაქსი დამოკიდებულია ტესტის ფრეიმვორქზე და არ არის უნივერსალურად მხარდაჭერილი. ამიტომ Tuist იყენებს ნატიურ უარყოფით სამიზნე შაბლონებს ჩართული test-suite გაფართოებით. ცალსახა სამიზნეები, ვაილდქარდ შერჩევები და ტესტები `test_suite` წესების შიგნით ინარჩუნებენ Bazel-ის ჩვეულებრივ შერჩევის ქცევას.

ბრძანება იღებს ყველა კარანტინის გვერდს და აშორებს დუბლიკატებს სამიზნეებს შორის. თუ Bazel-ის სრული მოვლენათა ჟურნალი ადგენს დაკარგულ გამოტოვებულ სამიზნეს სამიზნის კონფიგურაციამდე ან შესრულებამდე, Tuist ასახელებს მას გაფრთხილებაში და ახდენს განმეორებით ცდას ამ ძველი გამორიცხვის გარეშე. თავდაპირველად მოთხოვნილი შაბლონები და ყველა სხვა გამორიცხვა ნარჩუნდება. აღდგენა შემოიფარგლება ხუთი განმეორებითი ცდით; სხვა ჩატვირთვის შეცდომები და არასრული მტკიცებულებები ინარჩუნებენ Bazel-ის შეცდომას. დააბრუნეთ ძველი საქმეები **Enabled**-ზე მათი პოლიტიკების სამუდამოდ წასაშლელად. გადაეცით სამიზნე შაბლონები პირდაპირ; `--target_pattern_file` ვერ იქნება კომბინირებული კარანტინის გამორიცხვებთან. თუ არ დარჩა ტესტის სამიზნეები, Bazel ინარჩუნებს ჩვეულებრივ „ტესტები ვერ მოიძებნა“ გასვლის სტატუსს, რაც ასევე იჭერს შემთხვევით ცარიელ ტესტის შერჩევას.

ბრძანება ბეჭდავს ყველა გამორიცხულ სამიზნე ლეიბლს, რათა აწყობის ჟურნალებში ჩანდეს, რომელ სამიზნეებს, მათ შორის მათ ჯანსაღ საქმეებს, გამორიცხავს კარანტინის პოლიტიკა.

### კარანტინში მყოფი ტესტების ხელახლა გაშვება {#running-quarantined-tests-again}

შესწორების შესასწავლად ან დასადასტურებლად, გააუქმეთ ორივე კარანტინის პოლიტიკა:

```sh
tuist bazel test --no-quarantine -- --nocache_test_results //app:tests
```

დააბრუნეთ საქმე **Enabled**-ზე, რათა ჩართოთ მისი სამიზნე მომდევნო ჩვეულებრივ გაშვებებში. გამოტოვებული საქმეები არ წარმოქმნიან ახალ გაშვებებს მანამ, სანამ ცალსახად არ იქნებიან ჩართული, ამიტომ ახალ წარმატებულ გაშვებებზე დაფუძნებულ ავტომატიზაციას სჭირდება ვალიდაციის გაშვება, სანამ შეძლებს მათ აღდგენას.

კარანტინის მიღების შეცდომები აჩერებენ ბრძანებას ტესტების გაშვებამდე. ბრძანება ასევე უარყოფს პოლიტიკებს 20,000 საქმეზე მეტით ან სამიზნე არგუმენტებს მისი შემოფარგლული ზომის ზემოთ; ის არასდროს ავრცელებს ნაწილობრივ პოლიტიკას. გამოიყენეთ `--no-quarantine`, როდესაც განზრახვით გსურთ გაშვება პოლიტიკის გარეშე.

## არასავალდებულო კონფიგურაცია და განმეორებითი ცდები {#optional-configuration-and-retries}

თუ თქვენი რეპოზიტორია განსაზღვრავს სახელიან `ci` კონფიგურაციას `.bazelrc`-ში, შეგიძლიათ აირჩიოთ ის `--config=ci`-ით:

```sh
tuist bazel test -- --config=ci //app:tests
```

ეს არის რეპოზიტორიით განსაზღვრული კონფიგურაცია და არა Tuist-ის წინაპირობა. გამოტოვეთ ეს ოფცია, თუ თქვენი რეპოზიტორია არ განსაზღვრავს მას.

განმეორებითი ცდები ასევე არასავალდებულოა და დამოუკიდებელია კარანტინისგან. `--flaky_test_attempts=3` აძლევს უფლებას **სამ სრულ Bazel ცდას** თითოეულ ტესტზე და არა სამ დამატებით განმეორებით ცდას. გუნდებს შეუძლიათ შეინარჩუნონ არსებული განმეორებითი ცდების კონფიგურაცია `.bazelrc`-ში ან გადასცენ ის ცალსახად:

```sh
tuist bazel test -- --flaky_test_attempts=3 //app:tests
```

რეპოზიტორიებისთვის, რომლებიც განსაზღვრავენ `ci`, ოფციები შეიძლება იყოს კომბინირებული:

```sh
tuist bazel test -- --config=ci --flaky_test_attempts=3 //app:tests
```

## არასტაბილურობის აღმოჩენა {#detecting-flakiness}

Tuist იყენებს ინდივიდუალურ საქმეებს Bazel-ის `test.xml` ანგარიშებიდან, რათა აღმოაჩინოს არათანმიმდევრული შედეგები განმეორებითი ცდებისა და უწყვეტი ინტეგრაციისას ერთი და იგივე კომიტისა და სამიზნე შერჩევის გაშვებებში. ადგილობრივი გაშვებები რჩება ხილული, მაგრამ არ ნიშნავს ავტომატურად ტესტის საქმეებს როგორც არასტაბილურს. მიუთითეთ კომიტისა და ტოტის მეტამონაცემები, როდესაც თქვენი აწყობის გარემო უკვე არ აქვეყნებს მას:

```sh
tuist bazel test -- \
  --build_metadata=CI=true \
  --build_metadata=GIT_COMMIT="$GIT_COMMIT" \
  --build_metadata=GIT_BRANCH="$GIT_BRANCH" //app:tests
```

განმეორებითმა ცდებმა რეალურად უნდა გაიარონ, რათა Tuist-მა დააკვირდეს მათ შედეგებს. Bazel სამიზნის არასტაბილურობის შეჯამება მარტო ვერ ადგენს, რომელი ინდივიდუალური საქმე იყო არასტაბილური. ანგარიშები, რომლებიც მიუწვდომელია ან ვერ იქნება პარსირებული, ვერ უზრუნველყოფენ საქმის დონის მტკიცებულებას.
