# Bazel-ის არასტაბილური ტესტები {#bazel-flaky-tests}

`tuist bazel test` იღებს Tuist-ის კარანტინის პოლიტიკას ყოველ გამოძახებამდე და ავრცელებს მას ძირითად `bazel test` გაშვებაზე.

## კარანტინის გამოყენება {#applying-quarantine}

ტესტის გვერდზე შეცვალეთ მისი მდგომარეობა **Muted**-ზე, შემდეგ გაუშვით:

```sh
tuist bazel test -- //app:tests
```

არგუმენტები `--`-ის შემდეგ გადაეცემა `bazel test`-ს. გამოიყენეთ `--path` პროექტისა და სამუშაო დირექტორიის არჩევასთვის და `--bazel` სხვა შესრულებადი ფაილის, მაგალითად `bazelisk`-ის, არჩევასთვის. ჩვეულებრივი `bazel test` კვლავ აჩვენებს ტესტების შედეგებს, მაგრამ არ იღებს და არ ავრცელებს Tuist-ის კარანტინის პოლიტიკებს.

კარანტინისთვის არ არის საჭირო არც Bazel-ის სახელიანი კონფიგურაცია, არც ხელახლა ცდები. **Flaky Tests**, **Quarantined Tests** და ინდივიდუალური ტესტების გვერდები უჭერენ მხარს იგივე ხელით შესრულებულ მდგომარეობის ცვლილებებს, რასაც სხვა ბილდის სისტემები. გამოიყენეთ **Settings → Automations** არასტაბილურობის ზღვრების, კარანტინის ქმედებების და აღდგენის ქმედებების კონფიგურაციისთვის.

### დადუმება {#mute}

გამოიყენეთ **Mute** როგორც ძირითადი კარანტინის სამუშაო ნაკადი. დადუმებული შემთხვევები განაგრძობენ გაშვებას, მათი შეცდომები რჩება ხილული და ჯანსაღი დობილი შემთხვევები კვლავ ახდენენ გავლენას შედეგზე. ახალი შესრულებები უზრუნველყოფენ აღდგენის მტკიცებულებას მიზნის რომელიმე შემთხვევის გამორიცხვის გარეშე.

Tuist კითხულობს დროებით ადგილობრივ ბილდის მოვლენების ფაილს და მითითებულ `test.xml` ანგარიშებს. ის ცვლის Bazel-ის ტესტის შეცდომის გასვლის კოდს წარმატებად მხოლოდ მაშინ, როდესაც სრული ანგარიშები თითოეულ ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლში ვერცხლ......

ბილდის შეცდომები, დროის ამოწურვა, შეწყვეტილი გაშვებები, დაკარგული ან არასწორად ფორმატირებული ანგარიშები, არასრული მოვლენების ნაკადები და დადუმებული სიმრავლის გარეთ არსებული შეცდომები ინარჩუნებენ Bazel-ის შეცდომის სტატუსს. ადგილობრივი მოვლენების ფაილი შემოიფარგლება 64 მეbibიტამდე, ხოლო ინდივიდუალური ანგარიშები — 5 მეbibიტამდე. Tuist-ს სჭირდება საკუთარი ადგილობრივი ბილდის მოვლენების ფაილი დადუმებული შეცდომების დასადასტურებლად და ძველი გამოტოვებული მიზნებიდან აღსადგენად, ამიტომ ცხადი `--build_event_json_file` ვერ იქნება კომბინირებული აქტიურად დადუმებულ ან გამოტოვებულ შემთხვევებთან. დაშორებული ბილდის მოვლენების ანგარიშგება რჩება კონფიგურირებული `tuist bazel setup`-ის მეშვეობით.

ორიგინალური Bazel-ის გამოძახება და ანგარიშები ინარჩუნებენ რეალურ შედეგებს. Tuist-ის სერვერი იწერს, იყო თუ არა შემთხვევა კარანტინში გამოძახების დაწყებისას, მაშინაც კი, თუ მისი მდგომარეობა შეიცვლება ანგარიშის დამუშავებამდე.

### გამოტოვება {#skip}

გამოიყენეთ **Skip** მხოლოდ მაშინ, როდესაც განზრახული გაქვთ **მთელი Bazel-ის მიზნის** გამორიცხვა, მათ შორის ჯანსაღი შემთხვევებისა ამ მიზნის შიგნით. ერთი შემთხვევის **Skipped**-ად მონიშვნა იწვევს ამ ეფექტს მთელ მიზანზე. Bazel-ის ინდივიდუალური შემთხვევის ფილტრის სინტაქსი დამოკიდებულია ტესტის ჩარჩოზე და არ არის უნივერსალურად მხარდაჭერილი. ამიტომ Tuist იყენებს ნეგატიურ სამიზნე შაბლონებს ტესტის სუიტის გაფართოების ჩართვით. ცხადი მიზნები, ვილდქარდის შერჩევები და ტესტები `test_suite` წესების შიგნით ინარჩუნებენ Bazel-ის ჩვეულებრივ შერჩევის ქცევას.

ბრძანება იღებს ყველა კარანტინის გვერდს და აშორებს დუბლიკატურ მიზნებს. თუ Bazel-ის სრული მოვლენების ჟურნალი აღმოაჩენს დაკარგულ გამოტოვებულ მიზანს მიზნის კონფიგურაციამდე ან შესრულებამდე, Tuist ასახელებს მას გაფრთხილებაში და ცდილობს ხელახლა ამ ძველი გამორიცხვის გარეშე. თავდაპირველად მოთხოვნილი შაბლონები და ყველა სხვა გამორიცხვა ნარჩუნდება. აღდგენა შემოიფარგლება ხუთი ხელახალი ცდით; სხვა ჩატვირთვის შეცდომები და არასრული მტკიცებულებები ინარჩუნებენ Bazel-ის შეცდომას. დააბრუნეთ ძველი შემთხვევები **Enabled**-ზე მათი პოლიტიკების სამუდამოდ წასაშლელად. გადაეცით სამიზნე შაბლონები პირდაპირ; `--target_pattern_file` ვერ იქნება კომბინირებული კარანტინის გამორიცხვებთან. თუ ტესტის მიზნები აღარ დარჩა, Bazel ინარჩუნებს ჩვეულებრივ „ტესტები ვერ მოიძებნა“ გასვლის სტატუსს, რაც ასევე იჭერს შემთხვევითად ცარიელ ტესტის შერჩევას.

ბრძანება ბეჭდავს ყველა გამორიცხული მიზნის ლეიბლს, რათა ბილდის ჟურნალებში ჩანდეს, რომელ მიზნებს, მათ შორის მათ ჯანსაღ შემთხვევებს, გამორიცხავს კარანტინის პოლიტიკა.

### კარანტინში მყოფი ტესტების ხელახლა გაშვება {#running-quarantined-tests-again}

გასწორების გამოსაკვლევად ან დასადასტურებლად, გვერდი აუარეთ ორივე კარანტინის პოლიტიკას:

```sh
tuist bazel test --no-quarantine -- --nocache_test_results //app:tests
```

დააბრუნეთ შემთხვევა **Enabled**-ზე, რათა მისი მიზანი ჩაერთოს შემდგომ ჩვეულებრივ გაშვებებში. გამოტოვებული შემთხვევები არ წარმოქმნიან ახალ შესრულებებს მანამ, სანამ ისინი ცხადად არ იქნება ჩართული, ამიტომ ავტომატიზაციას, რომელიც ეფუძნება წარმატებულ ახალ გაშვებებს, სჭირდება ვალიდაციის გაშვება მათ აღსადგენად.

კარანტინის მიღების შეცდომები აჩერებენ ბრძანებას ტესტების გაშვებამდე. ბრძანება ასევე უარყოფს პოლიტიკებს 20,000 შემთხვევაზე მეტით ან სამიზნე არგუმენტებს მისი შემოფარგული ზომის ზემოთ; ის არასდროს ავრცელებს ნაწილობრივ პოლიტიკას. გამოიყენეთ `--no-quarantine`, როდესაც განზრახვით გსურთ გაშვება პოლიტიკის გარეშე.

## არასავალდებულო კონფიგურაცია და ხელახალი ცდები {#optional-configuration-and-retries}

თუ თქვენი რეპოზიტორია განსაზღვრავს სახელიან `ci` კონფიგურაციას `.bazelrc`-ში, შეგიძლიათ აირჩიოთ ის `--config=ci`-ით:

```sh
tuist bazel test -- --config=ci //app:tests
```

ეს არის რეპოზიტორიის მიერ განსაზღვრული კონფიგურაცია, არა Tuist-ის წინაპირობა. გამოტოვეთ ეს პარამეტრი, თუ თქვენი რეპოზიტორია არ განსაზღვრავს მას.

ხელახალი ცდები ასევე არასავალდებულოა და დამოუკიდებელია კარანტინისგან. `--flaky_test_attempts=3` აძლევს საშუალებას **სამი სრული Bazel-ის ცდის** ჩატარების თითოეულ ტესტზე, არა სამი დამატებითი ხელახალი ცდის. გუნდებს შეუძლიათ შეინარჩუნონ არსებული ხელახალი ცდების კონფიგურაცია `.bazelrc`-ში ან გადასცენ ის ცხადად:

```sh
tuist bazel test -- --flaky_test_attempts=3 //app:tests
```

რეპოზიტორიებისთვის, რომლებიც განსაზღვრავენ `ci`, პარამეტრები შეიძლება იყოს კომბინირებული:

```sh
tuist bazel test -- --config=ci --flaky_test_attempts=3 //app:tests
```

## არასტაბილურობის აღმოჩენა {#detecting-flakiness}

Tuist იყენებს ინდივიდუალურ შემთხვევებს Bazel-ის `test.xml` ანგარიშებიდან, რათა აღმოაჩინოს არათანმიმდევრული შედეგები ხელახალი ცდების და უწყვეტი ინტეგრაციის ერთი და იგივე კომიტისა და სამიზნე შერჩევის გაშვებების განმავლობაში. ადგილობრივი გაშვებები რჩება ხილული, მაგრამ არ ნიშნავს ავტომატურად ტესტის შემთხვევებს როგორც არასტაბილურს. მიეცით კომიტისა და შტოს მეტამონაცემები, როდესაც თქვენი ბილდის გარემო არ აქვეყნებს მას:

```sh
tuist bazel test -- \
  --build_metadata=CI=true \
  --build_metadata=GIT_COMMIT="$GIT_COMMIT" \
  --build_metadata=GIT_BRANCH="$GIT_BRANCH" //app:tests
```

ხელახალი ცდები რეალურად უნდა შესრულდეს, რათა Tuist-მა დააკვირდეს მათ შედეგებს. Bazel-ის მიზნის არასტაბილურობის შეჯამება მარტო ვერ განსაზღვრავს, რომელი ინდივიდუალური შემთხვევა იყო არასტაბილური. ანგარიშები, რომლებიც ხელმიუწვდომელია ან ვერ იპარსება, ვერ უზრუნველყოფენ შემთხვევის დონის მტკიცებულებას.

შემთხვევები იდენტიფიცირდება სამიზნე ლეიბლით, კლასის სახელით (სუიტის სახელზე დაბრუნებით) და ტესტის სახელით. ეს ინარჩუნებს ერთნაირად სახელდარქმეულ მეთოდებს სხვადასხვა კლასში განცალკევებულად. უფრო ძველი ანგარიშები, რომლებიც იყენებდნენ განსხვავებულ შემომფარგველ სუიტის სახელს, ინარჩუნებენ ისტორიას ძველი იდენტობის ქვეშ; მათი კარანტინის მდგომარეობა უნდა იქნას გამოყენებული ახალ იდენტობაზე. როდესაც შეცდომა ემთხვევა ძველ სუიტაზე დაფუძნებულ დადუმებას მისი მიმდინარე კლასის იდენტობის ნაცვლად, ბრძანება აფრთხილებს, რომელი პოლიტიკა უნდა იქნას ხელახლა გამოყენებული და ინარჩუნებს შეცდომის ბლოკირებას. პოლიტიკები არ გადაიცემა ავტომატურად, რადგან რამდენიმე კლასს შეიძლება ჰქონოდა საერთო ძველი იდენტობა.

ძირითადი ქცევის შესახებ იხილეთ Bazel-ის [ტესტების ფილტრები](https://bazel.build/docs/user-manual#test-filter), [ბრძანების პარამეტრები](https://bazel.build/reference/command-line-reference) და [აგების მოვლენების აღწერები](https://bazel.build/remote/bep-glossary).
