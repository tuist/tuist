# Bazel-ის არასტაბილური ტესტები {#bazel-flaky-tests}

`tuist bazel test` იღებს Tuist-ის კარანტინის პოლიტიკას ყოველი გამოძახების წინ და ავრცელებს მას ძირითად `bazel test` გაშვებაზე.

## კარანტინის გამოყენება {#applying-quarantine}

ტესტის გვერდზე შეცვალეთ მისი სტატუსი **Muted**-ზე, შემდეგ გაუშვით:

```sh
tuist bazel test -- //app:tests
```

არგუმენტები `--`-ის შემდეგ გადაეცემა `bazel test`-ს. გამოიყენეთ `--path` პროექტისა და სამუშაო დირექტორიის არჩევასთვის და `--bazel` სხვა შესრულებადი ფაილის, მაგალითად `bazelisk`-ის, არჩევასთვის. ჩვეულებრივი `bazel test` კვლავ აჩვენებს ტესტის შედეგებს, მაგრამ არ იღებს და არ ავრცელებს Tuist-ის კარანტინის პოლიტიკებს.

კარანტინისთვის არ არის საჭირო არც სახელიანი Bazel-ის კონფიგურაცია და არც ხელახლა ცდები. **Flaky Tests**, **Quarantined Tests** და ინდივიდუალური ტესტების გვერდები უჭერენ მხარს იგივე ხელით სტატუსის ცვლილებებს, რასაც სხვა აწყობის სისტემები. გამოიყენეთ **Settings → Automations** არასტაბილურობის ზღვრების, კარანტინის მოქმედებების და აღდგენის მოქმედებების კონფიგურაციისთვის.

### ჩუმი რეჟიმი {#mute}

გამოიყენეთ **Mute**, როგორც ძირითადი კარანტინის სამუშაო ნაკადი. Muted საქმეები განაგრძობენ გაშვებას, მათი შეცდომები რჩება ხილული და ჯანსაღი დაძმობილებული საქმეები კვლავ ახდენენ გავლენას შედეგზე. ახალი გაშვებები უზრუნველყოფენ აღდგენის მტკიცებულებას მიზნიდან რომელიმე საქმის გამორიცხვის გარეშე.

Tuist კითხულობს დროებით ადგილობრივ build-event ფაილს და მითითებულ `test.xml` ანგარიშებს. ის ცვლის Bazel-ის ტესტის შეცდომის გასვლას წარმატებად მხოლოდ მაშინ, როდესაც სრული ანგარიშები თითოეულ ვერცხლისფერ მიზანში ყოველ მოხსენებულ შეცდომას მიაწერენ muted საქმეს.

აწყობის შეცდომები, დროის ამოწურვა, შეწყვეტილი გაშვებები, დაკარგული ან არასწორი ანგარიშები, არასრული მოვლენათა ნაკადები და muted ნაკრების გარეთ არსებული შეცდომები ინარჩუნებენ Bazel-ის შეცდომის სტატუსს. ადგილობრივი მოვლენათა ფაილი შემოიფარგლება 64 მებიბაიტით, ხოლო ინდივიდუალური ანგარიშები — 5 მებიბაიტით. Tuist-ს სჭირდება საკუთარი ადგილობრივი build-event ფაილი muted შეცდომების დასადასტურებლად და ძველი გამოტოვებული მიზნებიდან აღსადგენად, ამიტომ ცალსახა `--build_event_json_file` არ შეიძლება იყოს გაერთიანებული აქტიურ muted ან გამოტოვებულ საქმეებთან. დაშორებული build-event ანგარიშგება რჩება კონფიგურირებული `tuist bazel setup`-ის მეშვეობით.

ორიგინალური Bazel-ის გამოძახება და ანგარიშები ინარჩუნებენ თავიანთ რეალურ შედეგებს. Tuist-ის სერვერი იწერს, იყო თუ არა საქმე კარანტინში გამოძახების დაწყებისას, მაშინაც კი, თუ მისი სტატუსი იცვლება ანგარიშის დამუშავებამდე.

### გამოტოვება {#skip}

გამოიყენეთ **Skip** მხოლოდ მაშინ, როდესაც გსურთ გამორიცხოთ **მთლიანი Bazel-ის მიზანი**, მათ შორის ჯანსაღი საქმეები ამ მიზნის შიგნით. ერთი საქმის **Skipped**-ად მონიშვნას აქვს ეს მიზნის მასშტაბის ეფექტი. Bazel-ის ინდივიდუალური საქმის ფილტრის სინტაქსი დამოკიდებულია ტესტის ჩარჩოზე და არ არის უნივერსალურად მხარდაჭერილი. ამიტომ Tuist იყენებს ნატიურ უარყოფით მიზნის შაბლონებს ჩართული ტესტის სუიტის გაფართოებით. ცალსახა მიზნები, ვაილდქარდის შერჩევები და ტესტები `test_suite` წესების შიგნით ინარჩუნებენ Bazel-ის ჩვეულებრივ შერჩევის ქცევას.

ბრძანება იღებს ყოველ კარანტინის გვერდს და ახდენს მიზნების დედუპლიკაციას. თუ Bazel-ის სრული მოვლენათა ჟურნალი აიდენტიფიცირებს დაკარგულ გამოტოვებულ მიზანს მიზნის კონფიგურაციამდე ან შესრულებამდე, Tuist ასახელებს მას გაფრთხილებაში და ცდის ხელახლა ამ ძველი გამორიცხვის გარეშე. ორიგინალური მოთხოვნილი შაბლონები და ყველა სხვა გამორიცხვა ინახება. აღდგენა შემოიფარგლება ხუთი ხელახლა ცდით; სხვა ჩატვირთვის შეცდომები და არასრული მტკიცებულებები ინარჩუნებენ Bazel-ის შეცდომას. დააბრუნეთ ძველი საქმეები **Enabled**-ზე მათი პოლიტიკების სამუდამოდ წასაშლელად. გადაეცით მიზნის შაბლონები პირდაპირ; `--target_pattern_file` არ შეიძლება იყოს გაერთიანებული კარანტინის გამორიცხვებთან. თუ არ დარჩა ტესტის მიზნები, Bazel ინარჩუნებს თავის ჩვეულებრივ „ტესტები ვერ მოიძებნა“ გასვლის სტატუსს, რაც ასევე იჭერს შემთხვევით ცარიელ ტესტის შერჩევას.

ბრძანება ბეჭდავს ყოველ გამორიცხულ მიზნის ლეიბლს, რათა აწყობის ჟურნალებმა აჩვენონ, რომელ მიზნებს, მათ შორის მათ ჯანსაღ საქმეებს, გამორიცხავს კარანტინის პოლიტიკა.

### კარანტინში მოთავსებული ტესტების ხელახლა გაშვება {#running-quarantined-tests-again}

გამოსწორების შესასწავლად ან დასადასტურებლად, გააუქმეთ ორივე კარანტინის პოლიტიკა:

```sh
tuist bazel test --no-quarantine -- --nocache_test_results //app:tests
```

დააბრუნეთ საქმე **Enabled**-ზე, რათა ჩართოთ მისი მიზანი შემდგომ ჩვეულებრივ გაშვებებში. გამოტოვებული საქმეები არ წარმოქმნიან ახალ გაშვებებს მანამ, სანამ ისინი ცალსახად არ იქნებიან ჩართული, ამიტომ ავტომატიზაციას, რომელიც ეფუძნება წარმატებულ ახალ გაშვებებს, სჭირდება ვალიდაციის გაშვება, სანამ მათ აღადგენს.

კარანტინის მიღების შეცდომები აჩერებენ ბრძანებას ტესტების გაშვებამდე. ბრძანება ასევე უარყოფს პოლიტიკებს 20,000 საქმეზე მეტით ან მიზნის არგუმენტებს მისი შემოფარგლული ზომის ზემოთ; ის არასდროს ავრცელებს ნაწილობრივ პოლიტიკას. გამოიყენეთ `--no-quarantine`, როდესაც განზრახვით გსურთ გაშვება პოლიტიკის გარეშე.

## არასავალდებულო კონფიგურაცია და ხელახალი ცდები {#optional-configuration-and-retries}

თუ თქვენი რეპოზიტორი განსაზღვრავს სახელიან `ci` კონფიგურაციას `.bazelrc`-ში, შეგიძლიათ აირჩიოთ ის `--config=ci`-ით:

```sh
tuist bazel test -- --config=ci //app:tests
```

ეს არის რეპოზიტორის მიერ განსაზღვრული კონფიგურაცია და არა Tuist-ის წინაპირობა. გამოტოვეთ ეს პარამეტრი, თუ თქვენი რეპოზიტორი არ განსაზღვრავს მას.

ხელახლა ცდები ასევე არის არასავალდებულო და დამოუკიდებელი კარანტინისგან. `--flaky_test_attempts=3` აძლევს შესაძლებლობას **სამი სრული Bazel-ის ცდის** თითოეული ტესტისთვის და არა სამი დამატებითი ხელახლა ცდის. გუნდებს შეუძლიათ შეინარჩუნონ თავიანთი არსებული ხელახლა ცდების კონფიგურაცია `.bazelrc`-ში ან გადასცენ ის ცალსახად:

```sh
tuist bazel test -- --flaky_test_attempts=3 //app:tests
```

რეპოზიტორებისთვის, რომლებიც განსაზღვრავენ `ci`, პარამეტრები შეიძლება იყოს გაერთიანებული:

```sh
tuist bazel test -- --config=ci --flaky_test_attempts=3 //app:tests
```

## არასტაბილურობის აღმოჩენა {#detecting-flakiness}

Tuist იყენებს ინდივიდუალურ საქმეებს Bazel-ის `test.xml` ანგარიშებიდან, რათა აღმოაჩინოს არათანმიმდევრული შედეგები ხელახლა ცდების განმავლობაში და ერთი და იგივე კომიტისა და მიზნის შერჩევის გაშვებებისას უწყვეტი ინტეგრაციის პროცესში. ადგილობრივი გაშვებები რჩება ხილული, მაგრამ არ ანიშნებს ავტომატურად ტესტის საქმეებს, როგორც არასტაბილურს. მიუთითეთ კომიტისა და ბრენჩის მეტამონაცემები, როდესაც თქვენი აწყობის გარემო არ აქვეყნებს მას:

```sh
tuist bazel test -- \
  --build_metadata=CI=true \
  --build_metadata=GIT_COMMIT="$GIT_COMMIT" \
  --build_metadata=GIT_BRANCH="$GIT_BRANCH" //app:tests
```

ხელახლა ცდები უნდა შესრულდეს რეალურად, რათა Tuist-მა დააკვირდეს მათ შედეგებს. Bazel-ის მიზნის არასტაბილურობის შეჯამება მარტო ვერ აიდენტიფიცირებს, რომელი ინდივიდუალური საქმე იყო არასტაბილური. ანგარიშები, რომლებიც არ არის ხელმისაწვდომი ან ვერ იქნება გაპარსული, ვერ უზრუნველყოფენ საქმის დონის მტკიცებულებას.

საქმეები იდენტიფიცირდება მიზნის ლეიბლით, კლასის სახელით (სუიტის სახელზე გადასვლით) და ტესტის სახელით. ეს ინარჩუნებს ერთნაირად სახელდარქმეულ მეთოდებს სხვადასხვა კლასებში განცალკევებულად. უფრო ძველ ანგარიშებს, რომლებიც იყენებდნენ განსხვავებულ შემომსაზღვრელ სუიტის სახელს, ინარჩუნებენ თავიანთ ისტორიას ძველი იდენტობის ქვეშ; მათი კარანტინის სტატუსი უნდა იქნას გამოყენებული ახალ იდენტობაზე. როდესაც შეცდომა ემთხვევა ძველ სუიტაზე დაფუძნებულ mute-ს მისი მიმდინარე კლასის იდენტობის ნაცვლად, ბრძანება აფრთხილებს, რომელი პოლიტიკა უნდა იქნას ხელახლა გამოყენებული და ინარჩუნებს შეცდომას ბლოკირებულად. პოლიტიკები არ გადაეცემა ავტომატურად, რადგან რამდენიმე კლასს შეიძლება ჰქონოდა საერთო ძველი იდენტობა.
