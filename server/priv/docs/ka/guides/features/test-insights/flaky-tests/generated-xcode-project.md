# გენერირებული Xcode პროექტი {#generated-xcode-project-flaky-tests}

> [!WARNING]
> **მოთხოვნები**
>
> - <.localized_link href="/guides/features/test-insights/xcode">Xcode ტესტების ინსაიტები</.localized_link> კონფიგურირებული (ავტომატურად გენერირებული სქემები მოიცავს `tuist inspect test` post-action-ს; მორგებულ სქემებს ეს უნდა დაემატოს).

არასტაბილური ტესტები არის ტესტები, რომლებიც ერთი და იგივე კოდით რამდენჯერმე გაშვებისას განსხვავებულ შედეგებს (წარმატება ან ჩავარდნა) იძლევა. ისინი ამცირებენ ნდობას თქვენი ტესტების ნაკრების მიმართ და ფუჭად ხარჯავენ დეველოპერის დროს ცრუ ჩავარდნების გამოკვლევაში. Tuist ავტომატურად აღმოაჩენს არასტაბილურ ტესტებს და გეხმარებათ მათ თვალყურის დევნაში დროთა განმავლობაში.

![არასტაბილური ტესტების გვერდი](/images/guides/features/test-insights/flaky-tests-page.png)

## როგორ მუშაობს არასტაბილურობის აღმოჩენა {#how-it-works}

Tuist არასტაბილურ ტესტებს ორი გზით აღმოაჩენს:

### ტესტების გამეორება {#test-retries}

როდესაც ტესტებს გამეორების ფუნქციონალით აშვებთ, Tuist აანალიზებს თითოეული მცდელობის შედეგებს. თუ ტესტი ზოგიერთ მცდელობაზე ვარდება, მაგრამ სხვებზე გადის, ის მონიშნულია როგორც არასტაბილური.

გაატარეთ `-retry-tests-on-failure` ან `-test-iterations` `tuist test`-ის მეშვეობით:

```sh
tuist test --scheme MyScheme -- -retry-tests-on-failure -test-iterations 3
```

![არასტაბილური სატესტო შემთხვევის დეტალები](/images/guides/features/test-insights/flaky-test-case-detail.png)

### გაშვებებს შორის აღმოჩენა {#cross-run-detection}

ტესტების გამეორების გარეშეც, Tuist-ს შეუძლია აღმოაჩინოს არასტაბილური ტესტები იმავე კომიტზე და იმავე სქემაზე სხვადასხვა CI გაშვებების შედეგების შედარებით. თუ ტესტი ერთ CI გაშვებაზე გადის, მაგრამ იმავე კომიტისა და სქემისთვის სხვა გაშვებაზე ვარდება, ორივე გაშვება მონიშნულია როგორც არასტაბილური.

სქემა შედარების გასაღების ნაწილია, რადგან ერთი და იგივე ტესტი შეიძლება განსხვავებულად იქცეოდეს სხვადასხვა სქემებში — მაგალითად, snapshot ტესტი, რომელიც მართებულია მხოლოდ კონკრეტული სიმულატორის მიმართულებისთვის, ან სატესტო სამიზნე, რომელიც კომპილირებულია სხვადასხვა ფლაგებით. ერთი და იმავე კომიტის ორი გაშვება სხვადასხვა სქემებზე განიხილება როგორც შესრულების ცალკე ვარიანტები და ერთმანეთს არასტაბილურად არ მონიშნავენ.

ეს განსაკუთრებით სასარგებლოა ისეთი არასტაბილური ტესტების დასაჭერად, რომლებიც არ ვარდებიან საკმარისად თანმიმდევრულად, რომ გამეორებებმა დაიჭიროს, მაგრამ მაინც იწვევენ პერიოდულ CI ჩავარდნებს.

## არასტაბილური ტესტების მართვა {#managing-flaky-tests}

### ავტომატური გასუფთავება

აღმოჩენა და გასუფთავება ხდება პროექტზე **ავტომატიზაციის შეტყობინების** მეშვეობით. ყოველ პროექტს აქვს ნაგულისხმევი „არასტაბილური ტესტების აღმოჩენის“ ავტომატიზაცია, რომლის *ტრიგერი* ტესტს არასტაბილურად მონიშნავს, ხოლო *აღდგენა* ასუფთავებს ნიშანს, როდესაც ტესტი გაივლის კონფიგურირებულ აღდგენის ფანჯარას (ნაგულისხმევი **14 დღე**) ხელახალი ტრიგერის გარეშე. შეცვალეთ ის **პარამეტრები → ავტომატიზაციები**-ში, რათა შეცვალოთ აღდგენის ფანჯარა, შეცვალოთ აღდგენის ქმედებები (მაგ., ასევე მოხსნა კარანტინიდან) ან სრულად გათიშოთ აღდგენა, რათა ტესტები დარჩეს არასტაბილურად მონიშნული, სანამ ხელით არ გაასუფთავებთ.

### ხელით მართვა

ასევე შეგიძლიათ ხელით მონიშნოთ ან მოხსნათ ტესტები როგორც არასტაბილური სატესტო შემთხვევის დეტალების გვერდიდან. ეს სასარგებლოა, როდესაც:
- გსურთ აღიაროთ ცნობილი არასტაბილური ტესტი, სანამ მუშაობთ გამოსწორებაზე
- ტესტი არასწორად იყო მონიშნული ინფრასტრუქტურის პრობლემების გამო

## არასტაბილური ტესტების კარანტინში მოქცევა {#quarantining}

კარანტინში მოქცევა იზოლირებს არასტაბილურ ტესტს, რათა მან არ დაბლოკოს CI, სანამ მას ასწორებთ. ნაგულისხმევად ეს არის **ხელით შესრულებადი ქმედება** — თქვენ ათავსებთ კარანტინში, ხსნით კარანტინს და ცვლით რეჟიმებს დაფის სატესტო შემთხვევის დეტალების გვერდიდან — მაგრამ ასევე შეგიძლიათ ჩართოთ ის **ავტომატიზაციის შეტყობინებაში** **პარამეტრები → ავტომატიზაციები**-ში, რათა ტესტი ავტომატურად იყოს დახშული (ან გამოტოვებული), როდესაც გადალახავს არასტაბილურობის ზღვარს, და ამოღებული იყოს კარანტინიდან, როდესაც აღდგება. ყოველი გადასვლა, ხელით თუ ავტომატური, იწერება სატესტო შემთხვევის აუდიტის ჟურნალში.

კარანტინში მყოფი ტესტი არის ერთ-ერთ ორ რეჟიმში:

- **დახშული**: ტესტი მაინც გადის, მაგრამ `tuist test` ფარავს ჩავარდნას. ჩავარდნები მაინც კვებავს არასტაბილური ტესტების დეტექტორს, ასე რომ შეგიძლიათ აკვირდეთ ტესტს ბილდის გაფუჭების გარეშე. აირჩიეთ ეს იმ ტესტისთვის, რომელსაც აქტიურად იკვლევთ.
- **გამოტოვებული**: xcodebuild იღებს `-skip-testing <identifier>`, ასე რომ ტესტი არასდროს იწყება. ის არ წარმოქმნის ახალ შედეგებს და ქრება არასტაბილური ტესტების დაფიდან, სანამ ხელახლა არ ჩართავთ. აირჩიეთ ეს, როდესაც ტესტი გაფუჭებულია, ნელია, ან იმდენად მუდმივად არასტაბილური, რომ მისი გაშვება უბრალოდ ფუჭად ხარჯავს CI წუთებს.

### რატომ შეიძლება კარანტინში მყოფი ტესტები გამოჩნდნენ როგორც წარმატებული {#quarantined-passing}

- **დახშული ტესტები** მაინც სრულდება. დახშული ტესტი, რომელიც ვარდება, იწერება როგორც **ჩავარდნილი** სატესტო შემთხვევის გაშვებაზე და მონიშნულია როგორც არასტაბილური — ტესტის სტატუსი არ გადაიწერება. რაც გადაიწერება, არის **მთლიანი ტესტების გაშვება**: თუ გაშვებაში ყოველი ჩავარდნილი სატესტო შემთხვევა დახშულია, გაშვება მთლიანად იტყობინება როგორც წარმატებული, ასე რომ დახშული ჩავარდნები არ აფუჭებენ CI-ს.
- **გამოტოვებული ტესტები** საერთოდ არ გადის, ასე რომ დაფა აგრძელებს ტესტის ბოლო რეალური შესრულების სტატუსის ჩვენებას — ეს სნეპშოტი შეიძლება კვირების ძველი იყოს.

### ტესტების გაშვება {#running-tests}

`tuist test` ავტომატურად ითვალისწინებს ორივე რეჟიმს:

```sh
tuist test
```

გამოტოვებული ტესტები გადაეცემა xcodebuild-ს როგორც `-skip-testing` და არასდროს იწყება. დახშული ტესტები ჩვეულებრივად გადის; თუ ისინი ვარდებიან, ჩავარდნა ფარულია მიღებულ ბილდის სტატუსში.

კარანტინის სრულად გვერდის ავლით და ყველაფრის გასაშვებად, დახშული და გამოტოვებული ტესტების ჩათვლით:

```sh
tuist test --skip-quarantine
```

## ახალი ტესტების სტრეს-ტესტირება {#stress-testing-new-tests}

სტრესის გეიტი ხელახლა აშვებს თქვენი ბრენჩის მიერ დამატებულ სატესტო შემთხვევებს, თითოეულს რამდენჯერმე ახალ პროცესში, და იტყობინება იმას, რომლებიც არასტაბილური აღმოჩნდება. თქვენ ხედავთ ახალ არასტაბილურ ტესტს pull request-ზე, რომელმაც ის შემოიტანა, არა კვირების შემდეგ.

სატესტო შემთხვევა ითვლება ახლად, თუ ის ბოლო 90 დღის განმავლობაში არ გაშვებულა CI-ზე პროექტის ნაგულისხმევ ბრენჩზე, ან კომიტზე, რომელიც შემდეგ მასზე მოხვდა. შერწყმის რიგით, სატესტო შემთხვევა, რომელიც რიგმა გაუშვა, ცნობილი ხდება, როდესაც რიგის კომიტი მოხვდება, და რჩება ახალი, თუ რიგი მას ტოვებს. კომიტები შეესაბამება <.localized_link href="/guides/features/test-insights/xcode#git-history">Git ისტორიას</.localized_link>, რომელსაც Tuist აგროვებს CI-ზე.

### მისი ჩართვა

გეიტი ნაგულისხმევად გამორთულია. დააყენეთ რეჟიმი:

- **`report`**: აფრთხილებს ყოველ არასტაბილურ სატესტო შემთხვევაზე. გაშვება მაინც გადის თავისი შედეგის მიხედვით.
- **`enforce`**: არასტაბილური სატესტო შემთხვევა აცდენს გაშვებას, იგივე გასვლის კოდით, რაც ჩავარდნილ ტესტს.

ორივე რეჟიმში, <.localized_link href="/guides/features/selective-testing/generated-xcode-project">შერჩევითი ტესტირება</.localized_link> არ ტოვებს სატესტო მიზანს ახალი არასტაბილური სატესტო შემთხვევით შემდეგ გაშვებაზე. მიზანი ისევ გადის, და გეიტი ისევ აკეთებს სტრეს-ტესტს სატესტო შემთხვევაზე, სანამ ის ყველა ხელახალ გაშვებას არ გაივლის.

დაიწყეთ `report`-ით რამდენიმე კვირის განმავლობაში, რომ ნახოთ, რას დაბლოკავდა `enforce`.

გადაეცით ის პასთროუ არგუმენტებამდე, ან დააყენეთ `TUIST_TEST_STRESS_NEW_TESTS`, რომ შეცვალოთ რეჟიმი თითოეული CI ლეინისთვის:

```sh
tuist test --stress-new-tests report
```

### როდესაც გეიტი არ გადის

- პირველი გაშვება უკვე ჩავარდა. ჯერ ეს ტესტები გაასწორეთ.
- პროექტს არ აქვს ნაგულისხმევი ბრენჩი, ან მასზე ჯერ არაფერი გაშვებულა CI-ზე.
- პროექტის სატესტო შემთხვევების 30%-ზე მეტი ახალი ჩანს. იმდენის ხელახლა გაშვება უფრო დიდხანს გაგრძელდება, ვიდრე ღირს. ელოდეთ ამას პროექტზე, რომელიც ახლახან დაიწყო Tuist-თან ანგარიშგებას, ან გადასახელების შემდეგ, რომელიც ბევრ ტესტს ერთდროულად გადაიტანს.

## არასტაბილური და კარანტინში მყოფი მდგომარეობის გამოკითხვა {#querying}

### CLI

`tuist test case` ბრძანებების ხე აჩვენებს ყველაფერს, რასაც Tuist აკონტროლებს სატესტო შემთხვევის შესახებ:

```sh
tuist test case list --flaky                       # only flaky test cases
tuist test case list --quarantined                 # only muted or skipped test cases
tuist test case show <test_case_id>                # detail: flakiness rate, last status, run counts
tuist test case events <test_case_id>              # audit log: marked_flaky, muted, skipped, ...
tuist test case run list <test_case_id>            # run history with status and duration
tuist test case run show <test_case_run_id>        # single run, including failure breakdown
```

ყველა ეს იღებს `--json`-ს სკრიპტინგისთვის.

### REST API

იგივე მონაცემები ხელმისაწვდომია HTTP-ით — იხილეთ [სატესტო შემთხვევების endpoint-ები](https://tuist.dev/api/docs#tag/test-cases) API ცნობარში სრული სიისთვის მარშრუტების, ფილტრების და პასუხის ველების შესახებ. სატესტო შემთხვევის მდგომარეობის შესაცვლელად (არასტაბილურად მონიშვნა ან მოხსნა, დახშვა, გამოტოვება), გაგზავნეთ `PATCH /api/projects/{account_handle}/{project_handle}/tests/test-cases/{test_case_id}` `is_flaky`-ით ან `state`-ით. იგივე ცვლილება ხელმისაწვდომია როგორც `tuist test case update` და როგორც `update_test_case` Model Context Protocol ინსტრუმენტი.
