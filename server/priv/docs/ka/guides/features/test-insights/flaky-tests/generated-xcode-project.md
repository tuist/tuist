# გენერირებული Xcode პროექტი {#generated-xcode-project-flaky-tests}

> [!WARNING]
> **მოთხოვნები**
>
> - <.localized_link href="/guides/features/test-insights/xcode">Xcode ტესტების ინსაიტები</.localized_link> კონფიგურირებული (ავტომატურად გენერირებული სქემები შეიცავს `tuist inspect test` post-action-ს; მორგებული სქემებისთვის ის ხელით უნდა დაამატოთ).

არასტაბილური ტესტებია ტესტები, რომლებიც ერთი და იგივე კოდის რამდენჯერმე გაშვებისას განსხვავებულ შედეგებს (წარმატება ან ჩავარდნა) აჩვენებენ. ისინი ამცირებენ ნდობას თქვენი სატესტო ნაკრების მიმართ და ფუჭად ხარჯავენ დეველოპერის დროს ცრუ ჩავარდნების გამოძიებაზე. Tuist ავტომატურად აღმოაჩენს არასტაბილურ ტესტებს და გეხმარებათ მათ თვალყურის დევნაში დროთა განმავლობაში.

![არასტაბილური ტესტების გვერდი](/images/guides/features/test-insights/flaky-tests-page.png)

## როგორ მუშაობს არასტაბილურობის აღმოჩენა {#how-it-works}

Tuist არასტაბილურ ტესტებს ორი გზით აღმოაჩენს:

### ტესტების ხელახალი გაშვება {#test-retries}

როდესაც ტესტებს ხელახალი გაშვების ფუნქციით აწარმოებთ, Tuist აანალიზებს თითოეული მცდელობის შედეგებს. თუ ტესტი ზოგიერთ მცდელობაზე ჩავარდება, მაგრამ სხვებზე წარმატებით შესრულდება, ის მონიშნული იქნება როგორც არასტაბილური.

გაატარეთ `-retry-tests-on-failure` ან `-test-iterations` `tuist test`-ის მეშვეობით:

```sh
tuist test --scheme MyScheme -- -retry-tests-on-failure -test-iterations 3
```

![არასტაბილური სატესტო შემთხვევის დეტალები](/images/guides/features/test-insights/flaky-test-case-detail.png)

### გაშვებებს შორის აღმოჩენა {#cross-run-detection}

ტესტების ხელახალი გაშვების გარეშეც, Tuist-ს შეუძლია აღმოაჩინოს არასტაბილური ტესტები ერთი და იგივე კომიტისა და სქემის სხვადასხვა CI გაშვებების შედეგების შედარებით. თუ ტესტი ერთ CI გაშვებაზე წარმატებით სრულდება, მაგრამ იგივე კომიტისა და სქემის სხვა გაშვებაზე ჩავარდება, ორივე გაშვება მონიშნული იქნება როგორც არასტაბილური.

სქემა შედარების გასაღების ნაწილია, რადგან ერთი და იგივე ტესტი შეიძლება განსხვავებულად იქცეოდეს სხვადასხვა სქემებში — მაგალითად, snapshot ტესტი, რომელიც მხოლოდ კონკრეტული სიმულატორის დანიშნულებისთვისაა ვალიდური, ან სატესტო target, რომელიც სხვადასხვა ფლაგებით კომპილირდება. ერთი და იგივე კომიტის ორი გაშვება სხვადასხვა სქემებზე განიხილება როგორც ცალკე შესრულების ვარიანტები და ერთმანეთს არასტაბილურად არ მონიშნავენ.

ეს განსაკუთრებით სასარგებლოა იმ არასტაბილური ტესტების დასაჭერად, რომლებიც საკმარისად თანმიმდევრულად არ ჩავარდებიან, რომ ხელახალი გაშვებით აღმოჩენილიყვნენ, მაგრამ მაინც იწვევენ პერიოდულ CI ჩავარდნებს.

## არასტაბილური ტესტების მართვა {#managing-flaky-tests}

### ავტომატური გასუფთავება

აღმოჩენა და გასუფთავება ხორციელდება პროექტზე **ავტომატიზაციის გაფრთხილების** მეშვეობით. ყოველ პროექტს აქვს ნაგულისხმევი „არასტაბილური ტესტების აღმოჩენის“ ავტომატიზაცია, რომლის *ტრიგერი* ტესტს არასტაბილურად მონიშნავს, ხოლო *აღდგენა* ასუფთავებს ნიშანს, როდესაც ტესტი კონფიგურირებული აღდგენის ფანჯარაში (ნაგულისხმევი **14 დღე**) ხელახლა არ გაააქტიურებს ტრიგერს. შეცვალეთ ის **პარამეტრები → ავტომატიზაციები**-ში, რათა შეცვალოთ აღდგენის ფანჯარა, შეცვალოთ აღდგენის ქმედებები (მაგ., ასევე მოხსნათ კარანტინი) ან სრულიად გამორთოთ აღდგენა, რათა ტესტები დარჩეს არასტაბილურად მონიშნული, სანამ ხელით არ გაასუფთავებთ.

### ხელით მართვა

ასევე შეგიძლიათ ხელით მონიშნოთ ან მოხსნათ ტესტები როგორც არასტაბილური სატესტო შემთხვევის დეტალების გვერდიდან. ეს სასარგებლოა, როდესაც:
- გსურთ აღიაროთ ცნობილი არასტაბილური ტესტი, სანამ მის გამოსწორებაზე მუშაობთ
- ტესტი არასწორად იყო მონიშნული ინფრასტრუქტურის პრობლემების გამო

## არასტაბილური ტესტების კარანტინში მოქცევა {#quarantining}

კარანტინი იზოლირებს არასტაბილურ ტესტს, რათა მან არ დაბლოკოს CI, სანამ მას ასწორებთ. ნაგულისხმევად ეს არის **ხელით შესრულებადი ქმედება** — თქვენ ათავსებთ კარანტინში, ხსნით კარანტინს და ცვლით რეჟიმებს სატესტო შემთხვევის დეტალების გვერდიდან დაშბორდზე — მაგრამ ასევე შეგიძლიათ მიამაგროთ ის **ავტომატიზაციის გაფრთხილებას** **პარამეტრები → ავტომატიზაციები**-ში, რათა ტესტი ავტომატურად იყოს დადუმებული (ან გამოტოვებული), როდესაც გადაკვეთს არასტაბილურობის ზღვარს, და მოხსნილი იყოს კარანტინიდან, როდესაც აღდგება. ყოველი გადასვლა, ხელით თუ ავტომატური, ფიქსირდება სატესტო შემთხვევის აუდიტის ჟურნალში.

კარანტინში მყოფი ტესტი ერთ-ერთ ორ რეჟიმშია:

- **დადუმებული**: ტესტი მაინც სრულდება, მაგრამ `tuist test` ფარავს ჩავარდნას. ჩავარდნები მაინც ეწოდება არასტაბილური ტესტების დეტექტორს, ასე რომ შეგიძლიათ აკვირდეთ ტესტს ბილდის გაწყვეტის გარეშე. აირჩიეთ ეს იმ ტესტისთვის, რომელსაც აქტიურად იკვლევთ.
- **გამოტოვებული**: xcodebuild იღებს `-skip-testing <identifier>`, ასე რომ ტესტი საერთოდ არ იწყება. ის არ წარმოქმნის ახალ შედეგებს და ქრება არასტაბილური ტესტების დაშბორდიდან, სანამ ხელახლა არ ჩართავთ. აირჩიეთ ეს, როდესაც ტესტი გაფუჭებულია, ნელია, ან იმდენად მუდმივად არასტაბილურია, რომ მისი გაშვება უბრალოდ ფუჭად ხარჯავს CI წუთებს.

### რატომ შეიძლება კარანტინში მყოფი ტესტები წარმატებულად გამოიყურებოდეს {#quarantined-passing}

- **დადუმებული ტესტები** მაინც სრულდება. დადუმებული ტესტი, რომელიც ჩავარდა, ფიქსირდება როგორც **ჩავარდნილი** სატესტო შემთხვევის გაშვებაზე და მონიშნულია როგორც არასტაბილური — ტესტის სტატუსი არ გადაიწერება. რაც გადაიწერება, არის **მთლიანი ტესტების გაშვება**: თუ გაშვებაში ყოველი ჩავარდნილი სატესტო შემთხვევა დადუმებულია, გაშვება მთლიანად მოიხსენიება როგორც წარმატებული, ასე რომ დადუმებული ჩავარდნები არ წყვეტენ CI-ს.
- **გამოტოვებული ტესტები** საერთოდ არ სრულდება, ამიტომ დაშბორდი აჩვენებს სტატუსს ტესტის ბოლო რეალური შესრულებიდან — ეს სნეპშოტი შეიძლება კვირების წინანდელი იყოს.

### ტესტების გაშვება {#running-tests}

`tuist test` ავტომატურად ითვალისწინებს ორივე რეჟიმს:

```sh
tuist test
```

გამოტოვებული ტესტები გადაეცემა xcodebuild-ს როგორც `-skip-testing` და საერთოდ არ იწყება. დადუმებული ტესტები ჩვეულებრივად სრულდება; თუ ისინი ჩავარდებიან, ჩავარდნა ფარულია მიღებულ ბილდის სტატუსში.

კარანტინის სრულად გვერდის ავლით ყველაფრის გასაშვებად, დადუმებული და გამოტოვებული ტესტების ჩათვლით:

```sh
tuist test --skip-quarantine
```

## ახალი ტესტების სტრეს-ტესტირება {#stress-testing-new-tests}

სტრესის კარიბჭე ხელახლა აწარმოებს თქვენი ბრენჩის მიერ დამატებულ სატესტო შემთხვევებს, თითოეულს რამდენჯერმე ახალ პროცესში, და აცნობებს იმ შემთხვევებს, რომლებიც არასტაბილური აღმოჩნდება. თქვენ ხედავთ ახალ არასტაბილურ ტესტს pull request-ზე, რომელმაც ის შემოიტანა, და არა კვირების შემდეგ.

სატესტო შემთხვევა ითვლება ახლად, თუ ის ბოლო 90 დღის განმავლობაში არ გაშვებულა CI-ზე პროექტის ნაგულისხმევ ბრენჩზე, ან კომიტზე, რომელიც მას შემდეგ მოხვდა იქ. merge queue-სთან, სატესტო შემთხვევა, რომელიც queue-მ გაუშვა, ცნობილი ხდება, როდესაც queue-ს კომიტი მოხვდება ბრენჩზე, და რჩება ახლად, თუ queue მას ტოვებს. კომიტები შეესაბამება <.localized_link href="/guides/features/test-insights/xcode#git-history">Git ისტორიის</.localized_link> მეშვეობით, რომელსაც Tuist აგროვებს CI-ზე.

### მისი ჩართვა

კარიბჭე ნაგულისხმევად გამორთულია. დააყენეთ რეჟიმი:

- **`report`**: აფრთხილებს ყოველ არასტაბილურ სატესტო შემთხვევაზე. გაშვება მაინც სრულდება თავისი შედეგის მიხედვით.
- **`enforce`**: არასტაბილური სატესტო შემთხვევა აფერხებს გაშვებას, იმავე გამოსვლის კოდით, რაც ჩავარდნილ ტესტს.

ორივე რეჟიმში <.localized_link href="/guides/features/selective-testing/generated-xcode-project">შერჩევითი ტესტირება</.localized_link> არ ტოვებს სატესტო სამიზნეს, რომელსაც აქვს ახალი არასტაბილური სატესტო შემთხვევა, შემდეგ გაშვებაზე. სამიზნე ხელახლა სრულდება და კარიბჭე ისევ ატარებს სტრეს-ტესტირებას სატესტო შემთხვევაზე, სანამ ის ყველა ხელახალ გაშვებას არ გაივლის წარმატებით.

დაიწყეთ `report` რეჟიმით რამდენიმე კვირის განმავლობაში, რათა ნახოთ, რას დაბლოკავდა `enforce`.

გადაეცით ის პასტროუ არგუმენტებამდე, ან დააყენეთ `TUIST_TEST_STRESS_NEW_TESTS`, რათა შეცვალოთ რეჟიმი CI ლეინის მიხედვით:

```sh
tuist test --stress-new-tests report
```

### რამდენჯერ მეორდება თითოეული ტესტი

ეს დამოკიდებულია იმაზე, თუ რამდენი დრო დასჭირდა სატესტო შემთხვევას პირველ გაშვებაზე:

| პირველი გაშვება | ხელახალი გაშვებები |
| --- | --- |
| 5 წმ-მდე | 10 |
| 10 წმ-მდე | 5 |
| 30 წმ-მდე | 3 |
| 5 წთ-მდე | 2 |
| 5 წთ-ზე მეტი | არ მეორდება |

ხელახალი გაშვებები იყენებენ პირველი გაშვების შედეგად აგებულს. გაშვება ჩერდება 200 სატესტო შემთხვევის ან 10 წუთის შემდეგ, იმის მიხედვით, რომელიც ადრე დადგება, და მიუთითებს, რომელი ზღვარი მიაღწია.

### როდესაც კარიბჭე არ სრულდება

- პირველი გაშვება უკვე ჩავარდა. ჯერ შეასწორეთ ეს ტესტები.
- პროექტს არ აქვს ნაგულისხმევი ბრენჩი, ან მასზე ჯერ არაფერი გაშვებულა CI-ში.
- პროექტის სატესტო შემთხვევების 30%-ზე მეტი ახლად ჩანს. ამდენის ხელახლა გაშვება უფრო დიდხანს გაგრძელდება, ვიდრე ღირს. ეს მოსალოდნელია პროექტზე, რომელიც ახლახან დაიწყო Tuist-თან ანგარიშგება, ან გადასახელების შემდეგ, რომელიც ერთდროულად ბევრ ტესტს გადაადგილებს.

## არასტაბილური და კარანტინში მყოფი მდგომარეობის გამოკითხვა {#querying}

### CLI

`tuist test case` ბრძანებების ხე აჩვენებს ყველაფერს, რასაც Tuist აკონტროლებს სატესტო შემთხვევის შესახებ:

```sh
tuist test case list --flaky                       # only flaky test cases
tuist test case list --quarantined                 # only muted or skipped test cases
tuist test case show <test_case_id>                # detail: flakiness rate, last status, run counts
tuist test case events <test_case_id>              # audit log: marked_flaky, muted, skipped, ...
tuist test case run list <test_case_id>            # run history with status and duration
tuist test case run show <test_case_run_id>        # single run, including failure breakdown
```

ყველა ეს იღებს `--json` სკრიპტინგისთვის.

### REST API

იგივე მონაცემები ხელმისაწვდომია HTTP-ით — იხილეთ [სატესტო შემთხვევების endpoint-ები](https://tuist.dev/api/docs#tag/test-cases) API ცნობარში მარშრუტების, ფილტრების და პასუხის ველების სრული სიისთვის. სატესტო შემთხვევის მდგომარეობის შესაცვლელად (არასტაბილურად მონიშვნა ან მოხსნა, დადუმება, გამოტოვება), გააგზავნეთ `PATCH /api/projects/{account_handle}/{project_handle}/tests/test-cases/{test_case_id}` `is_flaky` ან `state` პარამეტრებით. იგივე ცვლილება ხელმისაწვდომია როგორც `tuist test case update`, ასევე `update_test_case` Model Context Protocol ინსტრუმენტის სახით.
