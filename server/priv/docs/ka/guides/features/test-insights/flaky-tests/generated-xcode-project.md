# გენერირებული Xcode პროექტი {#generated-xcode-project-flaky-tests}

> [!WARNING]
> **მოთხოვნები**
>
> - <.localized_link href="/guides/features/test-insights/xcode">Xcode ტესტების ინსაიტები</.localized_link> კონფიგურირებული (ავტომატურად გენერირებული სქემები შეიცავს `tuist inspect test` post-action-ს; მორგებულ სქემებს ის ხელით უნდა დაემატოს).

არასტაბილური ტესტები არის ტესტები, რომლებიც ერთი და იგივე კოდით რამდენჯერმე გაშვებისას განსხვავებულ შედეგებს (წარმატება ან ჩავარდნა) იძლევა. ისინი ამცირებენ ნდობას თქვენი ტესტების ნაკრების მიმართ და ფუჭად ხარჯავენ დეველოპერის დროს ცრუ ჩავარდნების გამოკვლევაში. Tuist ავტომატურად აღმოაჩენს არასტაბილურ ტესტებს და გეხმარებათ მათ თვალყურის დევნაში დროთა განმავლობაში.

![არასტაბილური ტესტების გვერდი](/images/guides/features/test-insights/flaky-tests-page.png)

## როგორ მუშაობს არასტაბილურობის აღმოჩენა {#how-it-works}

Tuist ორი გზით აღმოაჩენს არასტაბილურ ტესტებს:

### ტესტების ხელახლა გაშვება {#test-retries}

როდესაც ტესტებს ხელახლა გაშვების ფუნქციით ასრულებთ, Tuist აანალიზებს თითოეული მცდელობის შედეგებს. თუ ტესტი ზოგიერთ მცდელობაზე ვერდება, მაგრამ სხვებზე გადის, ის არასტაბილურად მონიშნება.

გაატარეთ `-retry-tests-on-failure` ან `-test-iterations` `tuist test`-ის მეშვეობით:

```sh
tuist test --scheme MyScheme -- -retry-tests-on-failure -test-iterations 3
```

![არასტაბილური სატესტო შემთხვევის დეტალები](/images/guides/features/test-insights/flaky-test-case-detail.png)

### გაშვებებს შორის აღმოჩენა {#cross-run-detection}

ტესტების ხელახლა გაშვების გარეშეც, Tuist-ს შეუძლია აღმოაჩინოს არასტაბილური ტესტები სხვადასხვა CI გაშვების შედეგების შედარებით ერთსა და იმავე კომიტზე და ერთსა და იმავე სქემაზე. თუ ტესტი გადის ერთ CI გაშვებაზე, მაგრამ ვერდება იმავე კომიტისა და სქემის სხვა გაშვებაზე, ორივე გაშვება არასტაბილურად მონიშნება.

სქემა შედარების გასაღების ნაწილია, რადგან ერთი და იგივე ტესტი შეიძლება განსხვავებულად მოიქცეს სხვადასხვა სქემებში — მაგალითად, snapshot ტესტი, რომელიც მხოლოდ კონკრეტული სიმულატორის მიმართულებისთვისაა ვალიდური, ან სატესტო სამიზნე, რომელიც სხვადასხვა ფლაგებით კომპილირდება. ერთი და იმავე კომიტის ორი გაშვება სხვადასხვა სქემებზე განიხილება როგორც შესრულების ცალკეული ვარიანტები და ერთმანეთს არასტაბილურად არ მონიშნავენ.

ეს განსაკუთრებით სასარგებლოა იმ არასტაბილური ტესტების დასაჭერად, რომლებიც საკმარისად თანმიმდევრულად არ ვერდებიან, რათა ხელახლა გაშვებამ დაიჭიროს, მაგრამ მაინც იწვევენ პერიოდულ CI ჩავარდნებს.

## არასტაბილური ტესტების მართვა {#managing-flaky-tests}

### ავტომატური გასუფთავება

აღმოჩენა და გასუფთავება მიმდინარეობს პროექტზე **ავტომატიზაციის გაფრთხილების** მეშვეობით. ყოველ პროექტს აქვს ნაგულისხმევი „არასტაბილური ტესტების აღმოჩენის“ ავტომატიზაცია, რომლის *ტრიგერი* ტესტს არასტაბილურად მონიშნავს, ხოლო *აღდგენა* ასუფთავებს ნიშანს, როგორც კი ტესტი გაივლის კონფიგურირებულ აღდგენის ფანჯარას (ნაგულისხმევი **14 დღე**) ხელახალი ტრიგერის გარეშე. ჩაასწორეთ ის **პარამეტრები → ავტომატიზაციები**-ის ქვეშ, რათა შეცვალოთ აღდგენის ფანჯარა, შეცვალოთ აღდგენის მოქმედებები (მაგ., ასევე მოხსნათ კარანტინი) ან სრულიად გათიშოთ აღდგენა, რათა ტესტები არასტაბილურად დარჩნენ მონიშნული, სანამ ხელით არ გაასუფთავებთ.

### ხელით მართვა

ასევე შეგიძლიათ ხელით მონიშნოთ ან მოხსნათ ტესტების არასტაბილურობა სატესტო შემთხვევის დეტალების გვერდიდან. ეს სასარგებლოა, როდესაც:
- გსურთ აღიაროთ ცნობილი არასტაბილური ტესტი მისი გამოსწორების მუშაობისას
- ტესტი არასწორად მონიშნა ინფრასტრუქტურის პრობლემების გამო

## არასტაბილური ტესტების კარანტინში მოქცევა {#quarantining}

კარანტინი იზოლირებს არასტაბილურ ტესტს, რათა მან არ დაბლოკოს CI, სანამ მას ასწორებთ. ნაგულისხმევად ეს არის **ხელით შესრულებადი მოქმედება** — თქვენ ათავსებთ კარანტინში, ხსნით კარანტინს და ცვლით რეჟიმებს დაფის სატესტო შემთხვევის დეტალების გვერდიდან — მაგრამ ასევე შეგიძლიათ ჩართოთ ის **ავტომატიზაციის გაფრთხილებაში** **პარამეტრები → ავტომატიზაციები**-ის ქვეშ, რათა ტესტი ავტომატურად დადუმდეს (ან გამოიტოვოს), როდესაც გადალახავს არასტაბილურობის ზღვარს, და მოხსნას კარანტინი, როდესაც აღდგება. ყოველი გადასვლა, ხელით თუ ავტომატური, იწერება სატესტო შემთხვევის აუდიტის ჟურნალში.

ნაგულისხმევად, აღდგენა ელოდება, სანამ ტრიგერის პირობა აღარ შესრულდება, ამიტომ ტესტი რჩება კარანტინში, სანამ მისი ძველი არასტაბილური გაშვებები არ დატოვებენ ტრიგერის ფანჯარას. უფრო სწრაფად აღდგენისთვის, დააყენეთ **აღდგენა, როდესაც** მნიშვნელობაზე **არ არის ახალი არასტაბილური გაშვებები**: ტესტი აღდგება, როგორც კი აღდგენის ფანჯარა (დღეები ან გაშვებები) გაივლის ახალი არასტაბილური გაშვების გარეშე, ყოველი ახალი არასტაბილური გაშვება თავიდან იწყებს ამ ლოდინს, და აღდგენის შემდეგ მხოლოდ ახალი არასტაბილური გაშვება თავიდან ათავსებს მას კარანტინში.

კარანტინში მყოფი ტესტი ერთ-ერთ ორ რეჟიმშია:

- **დადუმებული**: ტესტი მაინც სრულდება, მაგრამ `tuist test` ფარავს ჩავარდნას. ჩავარდნები მაინც კვებავს არასტაბილური ტესტების დეტექტორს, ამიტომ შეგიძლიათ აკვირდეთ ტესტს ბილდის გატეხვის გარეშე. აირჩიეთ ეს იმ ტესტისთვის, რომელსაც აქტიურად იკვლევთ.
- **გამოტოვებული**: xcodebuild იღებს `-skip-testing <identifier>`, ამიტომ ტესტი არასდროს იწყება. ის არ წარმოქმნის ახალ შედეგებს და ქრება არასტაბილური ტესტების დაფიდან, სანამ ხელახლა არ ჩართავთ. აირჩიეთ ეს, როდესაც ტესტი გაფუჭებულია, ნელია, ან იმდენად მუდმივად არასტაბილურია, რომ მისი გაშვება უბრალოდ ფუჭად ხარჯავს CI წუთებს.

### რატომ შეიძლება კარანტინში მყოფი ტესტები წარმატებულად გამოიყურებოდეს {#quarantined-passing}

- **დადუმებული ტესტები** მაინც სრულდება. დადუმებული ტესტი, რომელიც ვერდება, იწერება როგორც **ვერდა** სატესტო შემთხვევის გაშვებაზე და მონიშნულია როგორც არასტაბილური — თითოეული ტესტის სტატუსი არ გადაიწერება. რაც იცვლება, არის **მთლიანი ტესტების გაშვება**: თუ გაშვებაში ყოველი ვერდებული სატესტო შემთხვევა დადუმებულია, გაშვება მთლიანად მოიხსენიება როგორც წარმატებული, ამიტომ დადუმებული ჩავარდნები არ ტეხენ CI-ს.
- **გამოტოვებული ტესტები** საერთოდ არ სრულდება, ამიტომ დაფა აჩვენებს სტატუსს ტესტის ბოლო რეალური შესრულებიდან — ეს სნაპშოტი შეიძლება კვირების წინანდელი იყოს.

### ტესტების გაშვება {#running-tests}

`tuist test` ავტომატურად ითვალისწინებს ორივე რეჟიმს:

```sh
tuist test
```

გამოტოვებული ტესტები გადაეცემა xcodebuild-ს როგორც `-skip-testing` და არასდროს იწყება. დადუმებული ტესტები ჩვეულებრივად სრულდება; თუ ისინი ვერდებიან, ჩავარდნა იფარება მიღებულ ბილდის სტატუსში.

კარანტინის სრულად გვერდის ავლით და ყველაფრის გასაშვებად, დადუმებული და გამოტოვებული ტესტების ჩათვლით:

```sh
tuist test --skip-quarantine
```

## ახალი ტესტების სტრეს-ტესტირება {#stress-testing-new-tests}

სტრესის გეიტი ხელახლა ასრულებს თქვენი ბრენჩის მიერ დამატებულ სატესტო შემთხვევებს, თითოეულს რამდენჯერმე ახალ პროცესში, და აცნობებს იმას, რაც არასტაბილური აღმოჩნდება. თქვენ ხედავთ ახალ არასტაბილურ ტესტს pull request-ზე, რომელმაც ის შემოიტანა, და არა კვირების შემდეგ.

სატესტო შემთხვევა ითვლება ახლად, თუ ის ბოლო 90 დღის განმავლობაში არ გაშვებულა CI-ზე პროექტის ნაგულისხმევ ბრენჩზე, ან კომიტზე, რომელიც მას შემდეგ შევიდა მასში. შერწყმის რიგით, სატესტო შემთხვევა, რომელიც რიგმა გაუშვა, ცნობილი ხდება, როგორც კი რიგის კომიტი შევა, და რჩება ახლად, თუ რიგი მას ჩამოაგდებს. კომიტები შეესაბამება <.localized_link href="/guides/features/test-insights/xcode#git-history">Git ისტორიის</.localized_link> მეშვეობით, რომელსაც Tuist აგროვებს CI-ზე.

### მისი ჩართვა

გეიტი ნაგულისხმევად გამორთულია. დააყენეთ რეჟიმი:

- **`report`**: აფრთხილებს თითოეული არასტაბილური სატესტო შემთხვევის შესახებ. გაშვება მაინც სრულდება საკუთარი შედეგის მიხედვით.
- **`enforce`**: არასტაბილური სატესტო შემთხვევა აჩერებს გაშვებას, იმავე გასვლის კოდით, რაც ჩავარდნილ ტესტს აქვს.

ორივე რეჟიმში, <.localized_link href="/guides/features/selective-testing/generated-xcode-project">შერჩევითი ტესტირება</.localized_link> არ გამოტოვებს სატესტო სამიზნეს ახალი არასტაბილური სატესტო შემთხვევით შემდეგ გაშვებაზე. სამიზნე ხელახლა სრულდება და გეიტი კვლავ ამოწმებს სატესტო შემთხვევას, სანამ ის ყველა ხელახალ გაშვებას არ გაივლის.

დაიწყეთ `report`-ით რამდენიმე კვირის განმავლობაში, რომ ნახოთ, რას დაბლოკავდა `enforce`.

გადაეცით ის პირდაპირი არგუმენტების წინ, ან დააყენეთ `TUIST_TEST_STRESS_NEW_TESTS`, რათა შეცვალოთ რეჟიმი CI-ის თითოეული არხისთვის:

```sh
tuist test --stress-new-tests report
```

### რამდენჯერ სრულდება ხელახლა თითოეული ტესტი

დამოკიდებულია იმაზე, თუ რამდენი ხანი დასჭირდა სატესტო შემთხვევას პირველ გაშვებაზე:

| პირველი გაშვება | ხელახალი გაშვებები |
| --- | --- |
| 5 წმ-მდე | 10 |
| 10 წმ-მდე | 5 |
| 30 წმ-მდე | 3 |
| 5 წთ-მდე | 2 |
| 5 წთ-ზე მეტი | არ სრულდება ხელახლა |

ხელახალი გაშვებები იყენებენ პირველი გაშვების შედეგებს. გაშვება ჩერდება 200 სატესტო შემთხვევის ან 10 წუთის შემდეგ, იმის მიხედვით, თუ რომელი ლიმიტი მიიღწევა პირველად, და აღნიშნავს, თუ რომელი ლიმიტი შეხვდა.

### როდესაც გეიტი არ სრულდება

- პირველი გაშვება უკვე ჩავარდა. ჯერ ეს ტესტები გაასწორეთ.
- პროექტს არ აქვს ნაგულისხმევი ბრენჩი, ან მასზე CI-ზე ჯერ არაფერი გაშვებულა.
- პროექტის სატესტო შემთხვევების 30%-ზე მეტი ახალი ჩანს. ამდენის ხელახლა გაშვებას მეტი დრო დასჭირდება, ვიდრე ღირს. ეს მოსალოდნელია პროექტზე, რომელიც ახლახანს დაიწყო Tuist-ზე მონიტორინგი, ან სახელის შეცვლის შემდეგ, რამაც ბევრი ტესტი ერთდროულად გადაიტანა.

## არასტაბილური და კარანტინში მყოფი მდგომარეობის მოთხოვნა {#querying}

### CLI

`tuist test case` ბრძანებების ხე აჩვენებს ყველაფერს, რასაც Tuist აკვირდება სატესტო შემთხვევის შესახებ:

```sh
tuist test case list --flaky                       # only flaky test cases
tuist test case list --quarantined                 # only muted or skipped test cases
tuist test case show <test_case_id>                # detail: flakiness rate, last status, run counts
tuist test case events <test_case_id>              # audit log: marked_flaky, muted, skipped, ...
tuist test case run list <test_case_id>            # run history with status and duration
tuist test case run show <test_case_run_id>        # single run, including failure breakdown
```

ყველა ეს იღებს `--json` სკრიპტინგისთვის.

### REST API

იგივე მონაცემები ხელმისაწვდომია HTTP-ით — იხილეთ [სატესტო შემთხვევების ბოლოწერტილები](https://tuist.dev/api/docs#tag/test-cases) API ცნობარში სრული სიისთვის მარშრუტების, ფილტრების და პასუხის ველების შესახებ. სატესტო შემთხვევის მდგომარეობის შესაცვლელად (არასტაბილურად მონიშვნა ან მოხსნა, დადუმება, გამოტოვება), გაგზავნეთ `PATCH /api/projects/{account_handle}/{project_handle}/tests/test-cases/{test_case_id}` `is_flaky` ან `state`-ით. იგივე ცვლილება ხელმისაწვდომია როგორც `tuist test case update` და როგორც `update_test_case` Model Context Protocol ინსტრუმენტი.
