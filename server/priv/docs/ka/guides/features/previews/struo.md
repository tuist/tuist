# Struo-ს პრევიუები {#struo-previews}

<a id="once-previews"></a>

[Struo](https://struo.run/docs/guide/infrastructure/tuist#publish-application-previews)-ს შეუძლია გამოაქვეყნოს აპლიკაციის არტიფაქტები Tuist-ში, რათა გუნდის წევრებმა შეძლონ ბილდის გამოცდა მისი ლოკალურად ხელახლა აწყობის გარეშე. გამოიყენეთ [Struo 1.0.0](https://github.com/tuist/struo/releases/tag/1.0.0) ან უფრო ახალი ვერსია და Tuist სერვერი არტიფაქტების მიმღებით.

## დანიშნულების კონფიგურაცია

შეასრულეთ <.localized_link href="/guides/get-started/struo-project">დაიწყეთ Struo-სთან მუშაობა</.localized_link>, შემდეგ დაამატეთ არტიფაქტის მიბმა სამუშაო სივრცის `struo.toml` ფაილში. ხელახლა გამოიყენეთ პროვაიდერი, თუ ის უკვე კონფიგურირებულია ქეშირებისთვის:

```toml
[infrastructures.tuist]
kind = "tuist"
account = "acme"
project = "app"

[infrastructure.artifacts]
name = "tuist"
```

```bash
struo auth login --provider tuist
struo artifact publish MyApplication --track review
```

მიმღები ინახავს სრულ ნაკრებს, წევრთა მანიფესტებს და სატვირთო მონაცემებს, უცნობი ინტერფეისების ჩათვლით. მხარდაჭერილი ნატიური ინტერფეისები ასინქრონულად პროეცირდება პრევიუებში პროექტის ნაგულისხმევი ხილვადობის, წვდომისა და განაწილების პარამეტრების გამოყენებით. ზოგადი არტიფაქტის შინაარსი კერძო რჩება, მაშინაც კი, საჯარო პროექტებში. ქვითარი ადასტურებს არტიფაქტის შენახვას და არა პრევიუს დამუშავების დასრულებას; მისი URL ხსნის პროექტის პრევიუების სიას.

## შესაბამისი აპლიკაციები

Apple-ის პროექცია იღებს `dev.struo.apple-install.v2` მეტამონაცემებს macOS-ზე ექსპორტირებული ad-hoc ხელმოწერილი macOS და სიმულატორის აპლიკაციებისთვის. ფიზიკურ მოწყობილობებზე გაშვებული აპლიკაციები არ არის შესაბამისი. Android-ის პროექცია იღებს `dev.struo.android-install.v1` მეტამონაცემებს ვერიფიცირებული ხელმოწერით. Struo ამტკიცებს ავტომატურ გამოქვეყნებას მხოლოდ debug-ხელმოწერილი, არა-ინსტრუმენტული APK-ებისთვის. უცნობი ინტერფეისები რჩება ჩამოსატვირთად როგორც არტიფაქტები პრევიუების შექმნის გარეშე. Android-ის ინსტალაციის ბმულები ინარჩუნებენ `.apk` ფაილის სახელს, მიუხედავად იმისა, რომ სატვირთო მონაცემები ინახება შინაარსის დაიჯესტების ქვეშ.

## ჩართეთ გამოქვეყნება ბილდების შემდეგ

```toml
[infrastructure]
publish_on_build = ["MyApplication"]
```

```bash
struo artifact publish MyApplication --allow-on-build
struo build MyApplication
```

ყველა მოთხოვნილი ბილდი უნდა წარმატებით დასრულდეს. ავტომატური გამოქვეყნება ასევე მოითხოვს პროდიუსერის მიერ მთლიანი ჩაკეტვის (closure) დამტკიცებას და ამ მანქანის, სამუშაო სივრცის, ზუსტი ბოლოწერტილის, მიზნისა და სტაბილური Tuist პროექტის დანიშნულებისთვის ლოკალურ ავტორიზაციას. პოლიტიკის ან ავტორიზაციის გარეშე არტიფაქტების გამოქვეყნების ქსელური მოთხოვნები არ ხორციელდება. ჩვეულებრივი Struo ბილდები რჩება იმპლიციური გამოქვეყნების გვერდითი ეფექტების გარეშე.

იგივე შენახული გამოქვეყნების განმეორებითი შესრულება ამოწმებს დისტანციურ ქვითარს და თავს არიდებს ხელახლა ატვირთვას. ეს განსხვავდება `tuist share`-ის მიერ დუბლიკატური ბილდის ქცევისგან.

## შენახვა

არტიფაქტების გამოქვეყნებები იწურება 30 დღის შემდეგ hosted Tuist-ზე. Self-hosted ინსტანციები იყენებენ `TUIST_APP_PREVIEW_RETENTION_DAYS`-ს; მისი დაუყენებლად დატოვება თიშავს ვადაგასვლას ამ ოჯახისთვის. ვადაგასული ჩანაწერები რჩებიან როგორც სამარეები (tombstones) და მათი ხელახლა აქტივაცია იგივე განზრახვის განმეორებით შესრულებით შეუძლებელია. არსებული `tuist share` ხელმოწერის, ხილვადობისა და განაწილების სამუშაო პროცესები უცვლელი რჩება.

იხილეთ <.localized_link href="/guides/features/previews#run-a-preview">პრევიუს გაშვება</.localized_link> გამოქვეყნებული ბილდების გასაშვებად, წვდომის, ტრეკებისა და README ბეჯებისთვის.

## Apple-ის პრევიუები

შესაბამისი Apple სიმულატორისა და macOS პრევიუებისთვის, იხილეთ <.localized_link href="/guides/features/previews/run/macos">Tuist macOS დამხმარე აპლიკაციის ინსტრუქციები</.localized_link>. ფიზიკურ მოწყობილობებზე გაშვებული აპლიკაციები კვლავ არ არის შესაბამისი Struo-ს მეშვეობით გამოქვეყნებისთვის.
