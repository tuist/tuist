# Struo-ს პრევიუები {#struo-previews}

<a id="once-previews"></a>

[Struo](https://struo.run/docs/guide/infrastructure/tuist#publish-application-previews)-ს შეუძლია გამოაქვეყნოს აპლიკაციის არტიფაქტები Tuist-ში, რათა გუნდის წევრებმა შეძლონ ბილდის გამოცდა მისი ლოკალურად ხელახლა აწყობის გარეშე. გამოიყენეთ [Struo 1.0.0](https://github.com/tuist/struo/releases/tag/1.0.0) ან უფრო ახალი ვერსია და Tuist სერვერი არტიფაქტების მიმღებით.

## დანიშნულების ადგილის კონფიგურაცია

დაასრულეთ <.localized_link href="/guides/get-started/struo-project">Struo-სთან მუშაობის დაწყება</.localized_link>, შემდეგ დაამატეთ არტიფაქტის ბმული სამუშაო სივრცის `struo.toml` ფაილში. ხელახლა გამოიყენეთ პროვაიდერი, თუ ის უკვე კონფიგურირებულია ქეშირებისთვის:

```toml
[infrastructures.tuist]
kind = "tuist"
account = "acme"
project = "app"

[infrastructure.artifacts]
name = "tuist"
```

```bash
struo auth login --provider tuist
struo artifact publish MyApplication --track review
```

მიმღები ინახავს სრულ ნაკრებს, წევრთა მანიფესტებს და შინაარსს, უცნობი ინტერფეისების ჩათვლით. მხარდაჭერილი ნატიური ინტერფეისები ასინქრონულად პროეცირდება პრევიუებში პროექტის ნაგულისხმევი ხილვადობის, წვდომისა და განაწილების პარამეტრების გამოყენებით. ზოგადი არტიფაქტის შინაარსი რჩება კონფიდენციალური, მაშინაც კი, თუ პროექტი საჯაროა. ქვითარი ადასტურებს არტიფაქტის შენახვას და არა პრევიუს დამუშავების დასრულებას; მისი URL ხსნის პროექტის პრევიუების სიას.

## შესაბამისი აპლიკაციები

Apple-ის პროექცია იღებს `dev.struo.apple-install.v2` მეტამონაცემებს macOS-ზე ექსპორტირებული ad-hoc ხელმოწერილი macOS და სიმულატორის აპლიკაციებისთვის. ფიზიკურ მოწყობილობებზე გათვლილი აპლიკაციები არ არის შესაბამისი. Android-ის პროექცია იღებს `dev.struo.android-install.v1` მეტამონაცემებს დადასტურებული ხელმოწერით. Struo ამტკიცებს ავტომატურ გამოქვეყნებას მხოლოდ debug-ხელმოწერილი, არა-ინსტრუმენტული APK-ებისთვის. უცნობი ინტერფეისები რჩება ჩამოსატვირთად არტიფაქტების სახით პრევიუების შექმნის გარეშე. Android-ის ინსტალაციის ბმულები ინარჩუნებენ `.apk` ფაილის სახელს, მიუხედავად იმისა, რომ შინაარსი ინახება კონტენტის დაიჯესტების ქვეშ.

## აირჩიეთ გამოქვეყნება ბილდების შემდეგ

```toml
[infrastructure]
publish_on_build = ["MyApplication"]
```

```bash
struo artifact publish MyApplication --allow-on-build
struo build MyApplication
```

ყველა მოთხოვნილი ბილდი უნდა წარმატებით დასრულდეს. ავტომატური გამოქვეყნება ასევე მოითხოვს პროდიუსერის მიერ მთლიანი დახურვის (closure) დამტკიცებას და ლოკალურ ავტორიზაციას ამ მანქანის, სამუშაო სივრცის, ზუსტი ბოლოწერტილის, სამიზნისა და სტაბილური Tuist პროექტის დანიშნულების ადგილისთვის. პოლიტიკის ან ავტორიზაციის გარეშე არტიფაქტების გამოქვეყნების ქსელური მოთხოვნები არ ხორციელდება. ჩვეულებრივი Struo ბილდები რჩებიან თავისუფალი არაცხადი გამოქვეყნების გვერდითი ეფექტებისგან.

იგივე შენახული გამოქვეყნების გამეორება ამოწმებს დისტანციურ ქვითარს და თავიდან აცილებს კიდევ ერთ ატვირთვას. ეს განსხვავდება `tuist share`-ის ორმაგი ბილდის ქცევისგან.

## შენახვა

არტიფაქტების გამოქვეყნებები იწურება 30 დღის შემდეგ Tuist-ის ჰოსტინგზე. თვითმასპინძელი ინსტანციები იყენებენ `TUIST_APP_PREVIEW_RETENTION_DAYS`-ს; მისი დაყენების გარეშე ვადა ამ ოჯახისთვის ითიშება. ვადაგასული ჩანაწერები რჩებიან როგორც „საფლავები“ (tombstones) და მათი გააქტიურება იგივე მოქმედების გამეორებით შეუძლებელია. არსებული `tuist share` ხელმოწერის, ხილვადობისა და განაწილების სამუშაო პროცესები უცვლელი რჩება.

იხილეთ <.localized_link href="/guides/features/previews#run-a-preview">პრევიუს გაშვება</.localized_link> გამოქვეყნებული ბილდების გასაშვებად, წვდომის, ტრეკების და README ბეჯებისთვის.

## Apple-ის პრევიუები

შესაბამისი Apple სიმულატორისა და macOS პრევიუებისთვის იხილეთ <.localized_link href="/guides/features/previews/run/macos">Tuist macOS თანმხლები აპლიკაციის ინსტრუქციები</.localized_link>. ფიზიკურ მოწყობილობებზე გათვლილი აპლიკაციები კვლავ არ არის შესაბამისი Struo-ში გამოქვეყნებისთვის.
