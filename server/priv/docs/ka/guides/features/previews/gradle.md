# Gradle-ის პრევიუები

ააწყვეთ და გააზიარეთ Android აპლიკაციები და ნატიური ბრძანების ხაზის ინსტრუმენტები პირდაპირ Gradle-დან. დაიწყეთ <.localized_link href="/guides/get-started/gradle-project">Gradle-ის პროექტის სახელმძღვანელოთი</.localized_link> პროექტის დასაკავშირებლად და ავტორიზაციისთვის.

## Android აპლიკაციები

```bash
./gradlew :app:tuistShareDebug
```

`dev.tuist` პარამეტრების პლაგინი რეგისტრირებს `tuistShare<Variant>` ამოცანას თითოეული აპლიკაციის ვარიანტისთვის Android Gradle Plugin-იდან (8.8.2 ან უფრო ახალი). შეცვალეთ `app` და `Debug` თქვენი აპლიკაციის მოდულითა და ვარიანტით, მაგალითად, `:app:tuistShareDemoDebug` პროდუქტის გემოსთვის. ამოცანა ქმნის APK-ს Gradle-ის მიერ განცხადებული არტიფაქტების დამოკიდებულებების მეშვეობით გამოქვეყნებამდე. ის ასევე მუშაობს, როდესაც აწყობის შედეგები აქტუალურია ან აღდგენილია აწყობის ქეშიდან.

მხარდაჭერილია მხოლოდ ერთი, ხელმოწერილი, უნივერსალური აპლიკაციის APK. Android-ის debug ვარიანტი ჩვეულებრივ იყენებს debug ხელმოწერის გასაღებს; release ვარიანტებს სჭირდებათ თქვენი საკუთარი ხელმოწერის კონფიგურაცია. ამოცანა ამოწმებს APK ხელმოწერას ავტორიზაციამდე ან ატვირთვამდე. ხელმოუწერელი, არასწორი, ინსტრუმენტული და გაყოფილი APK-ები უარყოფილია. ბიბლიოთეკის მოდულები, ტესტის APK-ები და Android App Bundles (`.aab`) არ არის გამოქვეყნების სამიზნეები.

## ნატიური ბრძანების ხაზის ინსტრუმენტები

პროექტები, რომლებიც იყენებენ Gradle-ის `cpp-application` ან `swift-application` პლაგინს, იღებენ გაზიარების ამოცანას თითოეული ნატიური ბინარული ფაილისთვის:

```bash
./gradlew :app:tuistShareMainDebug
```

ამოცანა ქმნის და აფუთებს ინსტალირებულ დისტრიბუციას, მისი გამშვებისა და დროებითი ბიბლიოთეკების ჩათვლით. გამოიყენეთ `tuistShareMainRelease` release ბინარული ფაილისთვის. პროექტებს, რომლებიც მიმართულია მრავალ მანქანაზე, აქვთ ამოცანა თითოეული ბინარული ფაილისთვის; გაუშვით `./gradlew :app:tasks --all` მათი სახელების საპოვნელად.

მხარდაჭერილია ნატიური macOS და Linux შესრულებადი ფაილები arm64 ან x86_64-ისთვის. ააწყვეთ სამიზნე პლატფორმაზე თქვენი Gradle პლაგინისთვის საჭირო ინსტრუმენტთა ჯაჭვით. JVM აპლიკაციები და მათი გენერირებული გამშვების სკრიპტები არ არის მხარდაჭერილი ამ ინტეგრაციით.

## გამოქვეყნების ქცევა

გაზიარების ამოცანები აქვეყნებენ პლაგინის არსებული Tuist სერთიფიკატების გამოყენებით, Tuist CLI-ის გამოძახების გარეშე. ჩვეულებრივი `assemble`, `build` და ტესტის ამოცანები არასდროს აქვეყნებენ პრევიუებს.

გაზიარების შემდეგ, გახსენით **პრევიუები** თქვენს პროექტში ბმულის დასაკოპირებლად. იგივე აწყობისა და ტრეკის გაზიარების განმეორება ხელახლა იყენებს მის გამოქვეყნებას, აწყობის ქეშში მოხვედრის შემდეგაც კი. წარუმატებელი ან დაუდასტურებელი ატვირთვები აფერხებენ გაზიარების ამოცანას; ისინი არ არის მოხსენიებული, როგორც წარმატებული პრევიუები.

## CI და ტრეკები

დააკონფიგურირეთ <.localized_link href="/guides/integrations/continuous-integration">CI ავტორიზაცია</.localized_link> იმავე სერთიფიკატებით, რომლებსაც იყენებთ პლაგინის სხვა ავტორიზებულ ფუნქციებისთვის, შემდეგ მოითხოვეთ გამოქვეყნება ცალსახად:

```bash
./gradlew :app:tuistShareDebug --track nightly
```

დაამატეთ `--track nightly` ნატიური გაზიარების ამოცანას იმავე გზით. ამოცანები იყენებენ კონფიგურირებულ Tuist პროექტს, სერვერის URL-სა და პროქსის პარამეტრებს. პრევიუს გამოქვეყნება ყოველთვის მოითხოვს ავტორიზაციას. Git რევიზიის მეტამონაცემები, გამოშვების შენიშვნები და ავტომატური pull-request კომენტარები არ არის მიმაგრებული ამ ამოცანების მიერ.

არტიფაქტების გამოქვეყნებები იწურება 30 დღის შემდეგ hosted Tuist-ზე. Self-hosted ინსტანციები იყენებენ `TUIST_APP_PREVIEW_RETENTION_DAYS`; მისი დაყენების გარეშე დატოვება თიშავს ვადას ამ ოჯახისთვის. ვადაგასული გამოქვეყნებების აღდგენა შეუძლებელია იმავე მოქმედების განმეორებით.

## არსებული APK-ის გაზიარება

APK-ისთვის, რომელიც აწყობილია ამ სამუშაო პროცესის გარეთ, ან გამოშვების შენიშვნების ჩასართავად legacy ატვირთვის ნაკადთან ერთად, CLI კვლავ ხელმისაწვდომია:

```bash
tuist share app/build/outputs/apk/debug/app-debug.apk \
  --track nightly --release-notes "Improve checkout"
```
