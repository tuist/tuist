# Rust-ის ბილდების ანალიტიკა {#rust-build-insights}

Build Insights გეხმარებათ იპოვოთ, რა ანელებს თქვენს Cargo ბილდებს და აღმოაჩინოთ რეგრესიები მანამ, სანამ ისინი გუნდს შეეხება. შეგიძლიათ შეადაროთ ლოკალური ბილდები CI-სთან, ნახოთ, როგორ იცვლება ბილდის დრო და შეისწავლოთ თითოეულ ბილდში კომპილირებული კრეიტები.

> [!IMPORTANT]
> **მოთხოვნები**
>
> - მიჰყევით <.localized_link href="/guides/get-started/rust-project">Rust პროექტის დაყენებას</.localized_link>, რათა დააკავშიროთ თქვენი პროექტი და გაიაროთ ავთენტიკაცია.

## ბილდების ანგარიშგება {#report-your-builds}

ჩვეულებრივი Cargo ბრძანებები გაუშვით Tuist-ის მეშვეობით:

```sh
tuist cargo build --workspace
tuist cargo check --all-targets
tuist cargo +nightly build --features tracing
```

თუ იყენებთ mise-ს, <.localized_link href="/guides/get-started/rust-project#keep-typing-cargo">დააყენეთ Cargo wrapper</.localized_link>, რათა განაგრძოთ ჩვეულებრივი `cargo` ბრძანებების გამოყენება. არგუმენტები, toolchain-ის შერჩევა, გამომავალი მონაცემები და გასვლის კოდი უცვლელი რჩება.

## იპოვეთ, რა ანელებს ბილდს {#explore-your-builds}

გახსენით ბილდი დэшბორდზე **Builds → Build Runs**-დან. გამოიყენეთ თარიღის, გარემოს და Rust-ის ვერსიის ფილტრები მსგავსი ბილდების შესადარებლად. ბილდები და მათი ქეშის მრიცხველები ასევე ხელმისაწვდომია `tuist build cargo list`-ის და `tuist build cargo show`-ის, `GET /api/projects/{account_handle}/{project_handle}/cargo/builds`-ის, ასევე `list_cargo_builds` და `get_cargo_build` <.localized_link href="/guides/features/agentic-coding/mcp">MCP ინსტრუმენტების</.localized_link> მეშვეობით.

**Overview**-ზე გამოიყენეთ **Compiler jobs** ნელი კრეიტების საპოვნელად. დაალაგეთ **Duration**-ის ან **Started after**-ის (დრო Cargo ბრძანების დაწყებიდან) მიხედვით, ან მოძებნეთ კრეიტის სახელით ან ძირითადი საწყისი ფაილით.

ყოველი სტრიქონი წარმოადგენს ერთ `rustc` გამოძახებას კრეიტისთვის, რომელიც შეიძლება შეიცავდეს მრავალ საწყის ფაილს. **Crate root** განსაზღვრავს მის ძირითად საწყის ფაილს; ხანგრძლილობა ეხება მთლიან კომპილატორის სამუშაოს, არა მხოლოდ ამ ფაილს. კრეიტი შეიძლება გამოჩნდეს ერთზე მეტჯერ სხვადასხვა target-ების ან კონფიგურაციებისთვის. კომპილატორის შეტყობინებები დაჯგუფებულია **Warnings**-ში და **Errors**-ში.

### კრეიტების თვალყურის დევნა ბილდებს შორის {#crate-history}

როცა თქვენი პროექტისთვის ხელმისაწვდომია, **Builds → Crates** აჩვენებს დაფიქსირებულ კრეიტებს და მათ კომპილაციის ისტორიას. გახსენით კრეიტი, რათა შეადაროთ მისი ჩაწერილი ხანგრძლივობა და შედეგები ბილდებს შორის, შემდეგ კი მიჰყევით კომპილაციას უკან მის Cargo ბილდამდე. იგივე ინვენტარი ხელმისაწვდომია `/cargo/crates`-ის მეშვეობით პროექტის API-ში და საერთო MCP build-entity ინსტრუმენტებში `kind: cargo_crates`-ით.

კრეიტები დაჯგუფებულია მათი ზუსტად ჩაწერილი ძირითადი გზის, სახელის და ტიპის მიხედვით. Checkout გზების ცვლილებამ შეიძლება გაყოს ისტორიები; პროფილები, features და target triples არ განირჩევა. ეს არის დაფიქსირებული კომპილატორის სამუშაოების ინვენტარი, არა თქვენი workspace-ის ყოველი კრეიტი. ქეშირებული ან აქტუალური კრეიტები არ ქმნიან კომპილაციის ნიმუშებს.

### ბილდის ანგარიშების მიკუთვნება {#report-attribution}

ავთენტიკირებული ანგარიშები აიდენტიფიცირებენ პირს პირადი სერთიფიკატების უკან. გაზიარებულ სერთიფიკატებს არ სჭირდებათ ინდივიდის იდენტიფიცირება. სურვილისამებრ, დააყენეთ `TUIST_ACTOR_ID` სტაბილურ opaque იდენტიფიკატორზე ანგარიშგების მანქანაზე; ის გამორთულია ნაგულისხმევად და ჩანს როგორც დაუდასტურებელი განცხადება, არასოდეს გამოიყენება ავტორიზაციისთვის. ძველმა სერვერებმა შეიძლება უგულებელყონ განცხადება. არ ჩადოთ მასში საიდუმლოებები.

## დროის მაჩვენებლების წაკითხვა {#timing-boundaries}

ბილდის ხანგრძლივობა არის დრო, რაც მთლიანმა Cargo ბრძანებამ წაიღო. კომპილატორის სამუშაოები შეიძლება პარალელურად შესრულდეს, ამიტომ მათი ხანგრძლივობა არ ჯამდება ბილდის ხანგრძლივობასთან.

Cargo აკომპილირებს მხოლოდ იმ კრეიტებს, რომლებსაც გადაკომპილაცია სჭირდებათ. კრეიტები, რომლებიც უკვე აქტუალურია, არ გამოჩნდებიან კომპილატორის სიაში. Tuist-ის კომპილაციის ქეშით, აღდგენილი სამუშაოები ჩანს ქეშის გაზომვებში, არა როგორც კომპილატორის შესრულებები.

Tuist არ ზომავს build scripts-ებს ცალკე და არ აჩვენებს ბილდის Timeline-ს. დიდ ბილდზე ჩანს პირველი 500 კომპილატორის სამუშაო, შეტყობინებით, თუ მეტი იყო ჩაწერილი.

## ქეშის გაზომვების წაკითხვა {#cache-measurements}

`tuist cargo` შეიცავს ექსპერიმენტულ კომპილაციის ქეშს, რომელიც განხორციელებულია Tuist CLI-ში. მიჰყევით <.localized_link href="/guides/features/cache/rust">Rust ქეშის სახელმძღვანელოს</.localized_link> დაყენების, Kura-ს მეშვეობით დისტანციური წაკითხვებისა და ჩაწერების, მხარდაჭერილი კომპილაციების და პრობლემების გადაჭრისთვის.

გახსენით **Cargo Cache** პროექტის გვერდითა პანელზე, რათა თვალყური ადევნოთ ქეშში მოხვედრის მაჩვენებლებს და ჩაწერილ გადაცემის, დაყოვნებისა და გამტარუნარიანობის გაზომვებს ბილდებს შორის. გაფილტრეთ თარიღით ან გარემოთი, გადაერთეთ ყოველდღიურ ტენდენციებსა და ინდივიდუალური ბილდის ქეშში მოხვედრის მაჩვენებლებს შორის, ან გახსენით ბოლო ბილდი მისი ქეშის აქტივობის შესასწავლად. ბილდები ქეშის გაზომვების გარეშე რჩება მიუწვდომლად, ნულის ნაცვლად.

გახსენით ბილდის **Cache** ჩანართი, რათა ნახოთ task hits, task misses, hit rate და ჩამოტვირთული და ატვირთული ბაიტები. ჩანართი ჩანს, როცა ბილდი ანგარიშგებს ქეშის მონაცემებს.

- **Cacheable Tasks** აჩვენებს, რომელმა კომპილატორის და build-script ამოცანებმა გამოიყენეს ქეშირებული გამომავალი მონაცემები. მოძებნეთ ან გაფილტრეთ ამოცანები, შეისწავლეთ ქეშის წაკითხვის/ჩაწერის დაყოვნება და გაშალეთ სტრიქონი მისი გამომავალი მონაცემების სანახავად.
- **CAS Outputs** აჩვენებს artifact-ების ჩამოტვირთვებს და ატვირთვებს, მათი ზომებით, ხანგრძლივობით და გამტარუნარიანობით. დიაგრამა ითვლის დასრულებულ გადაცემებს; უკვე არსებული artifact-ები და წარუმატებელი მცდელობები რჩება ცხრილში.

**Hit** ნიშნავს, რომ ქეშირებული გამომავალი მონაცემები ხელახლა იქნა გამოყენებული. **Missed** ნიშნავს, რომ ამოცანა კომპილირდა. Hits არ იყოფა ლოკალურ და დისტანციურად; CAS Outputs აჩვენებს ჩაწერილ artifact ოპერაციებს.

თუ დეტალური ჩანაწერები აკლია ან არასრულია, გვერდი აჩვენებს შეტყობინებას. შეჯამება მაინც მოიცავს მთლიან ბილდს. თავიდან აცილებული სავარაუდო კომპილატორის სამუშაო **არ არის დაზოგილი ბილდის დრო**.

ინკრემენტული კომპილაციები ჩვეულებრივად სრულდება.

### ბილდები, რომლებიც ტესტებს ასრულებენ {#builds-that-run-tests}

`tuist cargo test` ანგარიშგებს მთლიანი ბრძანების ხანგრძლივობას, მისი ტესტების ჩათვლით. ის ასევე ანგარიშგებს ინდივიდუალურ ტესტების შედეგებს, doctests-ების ჩათვლით, <.localized_link href="/guides/features/test-insights/rust">Rust Test Insights</.localized_link>-ის მეშვეობით. ინდივიდუალური ტესტების შედეგები ჩანს **Tests**-ის ქვეშ; ბრძანების ხანგრძლივობა ჩანს ბილდის ანალიტიკაში.

## სხვა კომპილატორის ინსტრუმენტები {#other-compiler-tools}

Tuist ინარჩუნებს არსებულ კომპილატორის wrappers-ებს, კონფიგურირებულს `RUSTC_WRAPPER`-ის, `CARGO_BUILD_RUSTC_WRAPPER`-ის ან Cargo კონფიგურაციის მეშვეობით, და ტოვებს `RUSTC_WORKSPACE_WRAPPER`-ს უცვლელად. წინასწარ არსებული გლობალური wrapper თიშავს Tuist-ის ქეშს და კომპილატორის დამკვირვებელს: Tuist ვერ ადგენს, ნამდვილად გაუშვა თუ არა ამ wrapper-მა rustc. მორგებული workspace wrappers-ები ასევე შეიძლება დატოვონ ნაკლები კომპილატორის სამუშაო ანგარიშში.

Tuist პოულობს Cargo-ს rustup-ის მეშვეობით. თუ იყენებთ მორგებულ ინსტალაციას, დააყენეთ `TUIST_CARGO_EXECUTABLE` მის executable გზაზე. Cargo-ს გამოძახება პირდაპირი toolchain გზით აცილებს mise-ის wrapper-ს. Cargo alias ვერ ჩაანაცვლებს ჩაშენებულ ბრძანებას, როგორიცაა `build`.

თუ იყენებთ Cargo-ს nightly `-C` ოფციას, ჯერ გადადით workspace-ში: Tuist გადასცემს `-C` ბრძანებებს, მაგრამ არ აგროვებს მათ ბილდის დროის მაჩვენებლებს.

## პრობლემების გადაჭრა {#troubleshooting}

თუ ბილდი არ ჩანს დэшბორდზე, ჩართეთ debug გამომავალი, რათა ნახოთ, რატომ არ გაიგზავნა მისი ანგარიში:

```sh
TUIST_DEBUG=1 tuist cargo build --workspace
```

ანგარიშგება არ ცვლის თქვენი ბილდის შედეგს.
