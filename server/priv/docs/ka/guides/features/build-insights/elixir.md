# Elixir-ის ბილდის ანალიტიკა {#elixir-build-insights}

Tuist-ის Hex პაკეტს შეუძლია ბილდის ანალიტიკის გაგზავნა Tuist-ში. ბილდის დრო, ფაილებს შორის დამოკიდებულების გრაფი და მათი ცვლილება დროთა განმავლობაში გაძლევთ იმ ინფორმაციას, რომელიც საჭიროა თქვენი ბილდის გრაფის ოპტიმიზაციისთვის და კომპილაციის გარემოში ხელმისაწვდომი ყველა ბირთვის მაქსიმალურად ეფექტური გამოყენებისთვის.

> [!IMPORTANT] REQUIREMENTS
> - დაასრულეთ <.localized_link href="/guides/get-started/elixir-project">Elixir-ით დაწყება</.localized_link>

## ბილდების ანგარიშგება {#report-your-builds}

საერთო კონფიგურაცია აინსტალირებს კომპილაციის ინტეგრაციას. განაგრძეთ ჩვეულებრივი ბრძანებების გამოყენება:

```bash
mix compile
```

ინტეგრაცია მოიცავს `mix compile` და ყოველ კომპილაციას, რომელსაც სხვა ამოცანა იწვევს, მაგალითად `mix test` ან `mix phx.server`. კომპილაცია, რომელიც არაფერს ასრულებს, არ ანგარიშდება, ამიტომ დაფზე ჩამოთვლილია მხოლოდ ის ბილდები, რომლებმაც რეალურად იმუშავეს.

## აქტორის იდენტიფიკატორის ანგარიშგება {#report-actor-claim}

Mix-ის ბილდისა და ტესტის ანგარიშის მოთხოვნები შეიცავს optional `x-tuist-actor-id` ჰედერს მხოლოდ მაშინ, როცა თქვენ ცალსახად აკონფიგურირებთ label-ს. დააყენეთ `TUIST_ACTOR_ID` ორგანიზაციის მასშტაბის label-ზე ან დაამატეთ `actor_id: "developer-label"` პროექტის `tuist` კონფიგურაციაში. გადაწყვეტისას უპირატესობა ენიჭება გარემოს ცვლადს, შემდეგ runtime `:actor_id` პარამეტრებს და ბოლოს პროექტის კონფიგურაციას. ნაგულისხმევად label არ იგზავნება და პაკეტი არ აღმოაჩენს ოპერაციული სისტემის მომხმარებლის სახელებს. ფიქსირებული პროექტის label ვრცელდება ყველაზე, ვინც იყენებს ამ კონფიგურაციას. ცარიელი ან არასწორი გადაფარვები გამოტოვებენ იდენტიფიკატორს ნაცვლად fallback-ის; ეს არ აშორებს credentials-ზე დაფუძნებულ ვერიფიცირებულ იდენტობას. თუ custom proxy უარყოფს უცნობ ჰედერებს, გამორთეთ ის `TUIST_ACTOR_ID=""`-ით.

იდენტიფიკატორები უნდა იყოს 1–128 ბაიტი არა-სpace ბეჭდვადი ASCII სიმბოლოებისგან. არასწორი გადაფარვები გამოტოვებულია fallback-ის გარეშე. ვერიფიცირებულ ინდივიდუალურ credentials-ს აქვს უპირატესობა; სხვა client-ის მიერ მოწოდებული იდენტიფიკატორები ჩანს როგორც **Unverified**, არასდროს ანიჭებს წვდომას და არასდროს ბმავს ავტომატურად მომხმარებლებთან. ნებისმიერს, ვისაც შეუძლია ნახოს პროექტის ანგარიშები, შეუძლია დაინახოს ეს იდენტიფიკატორები, მათ შორის საჯარო მაყურებლებს, როცა პროექტი საჯაროა, და ისინი შედიან მონაცემთა ექსპორტში, ამიტომ არ ჩართოთ საიდუმლოებები. ძველი სერვერები იგნორირებენ optional ჰედერს, ხოლო ახალი სერვერები იღებენ ძველ clients-ს მის გარეშე. ახალი shared-token ანგარიშები იდენტიფიკატორის გარეშე აჩვენებენ **Unknown**-ს, გამომცემი ორგანიზაციის ნაცვლად; ისტორიული ანგარიშები ინარჩუნებენ წინა მიკუთვნებას. ბილდისა და ტესტის ანგარიშგება ნაგულისხმევად მოითხოვს ავთენტიკაციას. Self-hosted ინსტალაციებს შეუძლიათ ცალსახად ჩართონ credential-free ანგარიშგება, როგორც ქვემოთაა აღწერილი.

## Credential-free ანგარიშგება private ქსელში {#network-trusted-publishing}

მას შემდეგ, რაც ოპერატორი დააკონფიგურირებს `TUIST_NETWORK_TRUSTED_INSIGHTS_ACCESS=true` ინსტანციაზე და გადატვირთავს მას, როგორც აღწერილია <.localized_link href="/guides/server/self-host/server#network-trusted-access">self-hosting სახელმძღვანელოში</.localized_link>, დააკონფიგურირეთ თქვენი destination. SDK ავტომატურად აღმოაჩენს, ნებავს თუ არა ინსტანციას credential-free ანგარიშგება, როცა credentials არ არის. ინსტანციის პარამეტრი მოიცავს ყველა მხარდაჭერილ პროექტს და არ აქვს dashboard toggle:

```elixir
tuist: [
  url: "https://tuist.internal.example",
  project: "account/project"
]
```

`mix tuist.compile` და `mix tuist.test` აქვეყნებენ სტრუქტურირებულ ანგარიშებს sign-in-ის გარეშე, როცა credentials ნამდვილად არ არის და აღმოჩენა ადასტურებს, რომ სერვერი ამას ნებავს. არ არის საჭირო არც client flag და არც პროექტის opt-in. არსებული credentials, მათ შორის მოწოდებული CI OIDC იდენტობა, გამოიყენება ან უარყოფილი იქნება, არასდროს იგნორირდება unsigned ანგარიშგებაზე დასაწევად. მხოლოდ whitespace-ისგან შემდგარი `TUIST_TOKEN` არის შეცდომა. ცარიელი `TUIST_TOKEN` შეიძლება გადავიდეს valid შენახულ credentials-ზე ან მოწოდებულ OIDC-ზე, ხოლო ძველი შენახული credentials შეიძლიან გადავიდნენ მოწოდებულ OIDC-ზე; ორივე გზა რჩება ავთენტიფიცირებული და არასდროს ჩართავს unsigned ანგარიშგებას. გამოუსადეგარი credentials ინახება და მარცხდება, როცა არცერთი ავთენტიფიცირებული fallback არ მუშაობს. განაახლეთ ყველა სერვერის replica discovery-ის შესაძლებლობის მქონე ვერსიამდე credential-free clients-ის განახლებამდე; უფრო ძველ სერვერებს discovery-ს გარეშე, გამორთულ ინსტანციებს და discovery-ს შეცდომებს კვლავ სჭირდებათ ავთენტიკაცია.

Unsigned გაშვებები არის telemetry, არა სანდო flakiness, quarantine, coverage ან selective-execution მტკიცებულება. Shard planning, build archives და coverage/artifact endpoints კვლავ მოითხოვს credentials. დააყენეთ `TUIST_ACTOR_ID=""` დამოუკიდებლად configured actor claim-ის გამოსატოვებლად; ვერიფიცირებული credential იდენტობა უცვლელი რჩება.

## რა თვალყურს ადევნებს {#what-is-tracked}

ყოველი ბილდისთვის პაკეტი აგროვებს:
- მის ხანგრძლივობას, წარმატებით დასრულდა თუ არა და Elixir, Erlang/OTP და Mix გარემოს, რომელშიც გაშვებული იყო
- ყოველ გაფრთხილებასა და შეცდომას, მისი ფაილითა და ხაზით
- რამდენი დრო დასჭირდა თითოეული ფაილის კომპილაციას და რომელ მოდულებს განსაზღვრავს ის
- ფაილებს, რომლებზეც თითოეული ფაილია დამოკიდებული და სჭირდება თუ არა ისინი კომპილაციის დროს თუ მხოლოდ runtime-ზე
- რას აკეთებდა ბილდი ფაილების კომპილაციის გარდა, მაგალითად type checking, დისკზე ჩაწერა და სხვა Mix კომპილატორები
- მანქანის პროცესორის, მეხსიერების, ქსელისა და დისკის გამოყენებას ბილდის დროს
- branch-სა და commit-ს, ხოლო continuous integration-ზე — provider-სა და გაშვებას

## იპოვეთ, რა ანელებს ბილდს {#find-what-slows-a-build-down}

გახსენით ბილდი **Builds → Build Runs**-დან dashboard-ზე. ბილდები, მათი დიაგნოსტიკის რაოდენობა და დამოკიდებულების cache-ის შეჯამებები ასევე ხელმისაწვდომია `tuist build mix list` და `tuist build mix show`-ით, `GET /api/projects/{account_handle}/{project_handle}/mix/builds`-ით და `list_mix_builds` და `get_mix_build` <.localized_link href="/guides/features/agentic-coding/mcp">MCP tools</.localized_link>-ით.

**Overview** ტაბი ჩამოთვლის ფაილებს, რომლებიც ბილდმა დააკომპილირა. შეგიძლიათ დააჯგუფოთ ისინი მოდულის მიხედვით, მოძებნოთ და დაალაგოთ:
- **Compilation duration**, რათა იპოვოთ ფაილები, რომლებიც თავისთავად ნელია.
- **Compile-time dependents**, ფაილების რაოდენობა, რომლებიც ვერ დააკომპილირებენ მანამ, სანამ ეს ერთი არ დასრულდება. ნელი ფაილი ბევრი დამოკიდებულებით აფერხებს ბილდის დანარჩენ ნაწილს და მისი ცვლილება ხელახლა აკომპილირებს მათ ყველას.
- **Compile-time dependencies**, ფაილების რაოდენობა, რომლებსაც ეს ერთი ელოდება.

![Phoenix აპლიკაციის Mix ბილდის მიმოხილვა](/images/guides/features/elixir/build.png)

**Timeline** ტაბი აჩვენებს იმავე ბილდს დროთა განმავლობაში: რომელი ფაილები კომპილირდებოდა პარალელურად, სად აკეთებდა ბილდი type check-ს და დისკზე ჩაწერას და როგორ იყო მანქანა დატვირთული ყოველ მომენტში. მონაკვეთი ერთი ზოლით არის მონაკვეთი, სადაც ბილდს არ შეეძლო ხელმისაწვდომი ბირთვების გამოყენება.

![Phoenix აპლიკაციის სრული Mix ბილდის დროითი ხაზი](/images/guides/features/elixir/build-timeline.png)

**Warnings** და **Errors** ტაბები ჩამოთვლიან ბილდის დიაგნოსტიკას.

## Custom metadata {#custom-metadata}

მიამაგრეთ tags და key-value მონაცემები Mix ბილდებს, რათა განასხვავოთ გაშვებები სხვადასხვა გუნდების, hardware-ის ან workflows-ის მიხედვით. ორივე ჩანს თითოეული ბილდის დეტალურ გვერდზე.

დააყენეთ metadata გარემოს ცვლადებით:

```sh
export TUIST_TAGS="nightly,release"
export TUIST_VALUES="ticket=TUIST-123,runner=linux-arm64"
```

ასევე შეგიძლიათ დააკონფიგურიროთ metadata `mix.exs`-ში:

```elixir
tuist: [
  project: "account/project",
  tags: ["nightly", "release"],
  values: %{"ticket" => "TUIST-123", "runner" => "linux-arm64"}
]
```

ორივე წყაროდან მიღებული Tags ერთიანდება. როდესაც იგივე key ორივე ადგილას არის დაკონფიგურირებული, უპირატესობა ენიჭება გარემოს ცვლადში მითითებულ მნიშვნელობას.

Tags-მა უნდა შეიცავდეს მხოლოდ ასოებს, რიცხვებს, დეფისებსა და underscore-ებს. ბილდს შეიძლება ჰქონდეს მაქსიმუმ 50 tag და თითოეული tag შეიძლება შეიცავდეს მაქსიმუმ 50 სიმბოლოს. ბილდს შეიძლება ჰქონდეს მაქსიმუმ 20 key-value ჩანაწერი, თითოეული key შეიძლება შეიცავდეს მაქსიმუმ 50 სიმბოლოს, ხოლო თითოეული value — მაქსიმუმ 500 სიმბოლოს. ეს იგივე server-side ლიმიტებია, რომლებიც გამოიყენება Xcode build metadata-სთვის. პაკეტი აგზავნის ანგარიშამდე ტოვებს არასწორ tags-ებსა და ზომით გადაჭარბებულ ან ცარიელ metadata ჩანაწერებს, ამიტომ არასწორმა კონფიგურაციამ ვერ შეუშლის ხელი build insights ანგარიშის დანარჩენი ნაწილის შენახვას. გამოიყენეთ key-value metadata იმ მნიშვნელობებისთვის, რომლებიც არ აკმაყოფილებენ tag-ის შეზღუდვას.

Custom metadata მიმაგრებულია builds-ზე და არა test runs-ზე.

Custom metadata ჩანს პროექტის წევრებისთვის dashboard-ში. არ გამოიყენოთ ის credentials, access tokens ან სხვა მგრძნობიარე მონაცემებისთვის. Tuist ინახავს Mix ბილდის მონაცემებს, ამ metadata-ს ჩათვლით, 90 დღის განმავლობაში. დეტალებისთვის იხილეთ <.localized_link href="/guides/server/data-retention">data retention policy</.localized_link>.

## Troubleshooting {#troubleshooting}

Reporting არასდროს ცვლის თქვენი ბილდის შედეგს: თუ ანგარიშის გაგზავნა ვერ ხერხდება, ბილდი მთავრდება ისე, როგორც უნდა დასრულებულიყო და არაფერი ბეჭდება. იმის საჩვენებლად, რატომ არ გაიგზავნა ანგარიში, დააყენეთ `TUIST_DEBUG=1`:

```bash
TUIST_DEBUG=1 mix compile --force
```
