# Elixir-ის ბილდის ანალიტიკა {#elixir-build-insights}

Tuist-ის Hex პაკეტს შეუძლია ბილდის ანალიტიკა Tuist-ზე გაგზავნოს. კომპილაციის დრო, ფაილებს შორის დამოკიდებულების გრაფი და მათი ცვლილება დროთა განმავლობაში გაძლევთ საჭირო ინფორმაციას ბილდის გრაფის ოპტიმიზაციისთვის და იმ გარემოში არსებული ყველა ბირთვის მაქსიმალურად გამოყენებისთვის, სადაც კომპილაცია მიმდინარეობს.

> [!IMPORTANT] REQUIREMENTS
> - დაასრულეთ <.localized_link href="/guides/get-started/elixir-project">Elixir-ის დაწყება</.localized_link>

## ბილდების ანგარიშგება {#report-your-builds}

საერთო კონფიგურაცია აყენებს კომპილაციის ინტეგრაციას. განაგრძეთ ჩვეული ბრძანებების გამოყენება:

```bash
mix compile
```

ინტეგრაცია მოიცავს `mix compile` და ყოველ კომპილაციას, რომელსაც სხვა ამოცანა იწვევს, მაგალითად `mix test` ან `mix phx.server`. კომპილაცია, რომელიც არაფერს ასრულებს, არ იგზავნება, ამიტომ დაფაზე მხოლოდ ის ბილდები ჩანს, რომლებმაც რეალური სამუშაო შეასრულეს.

## აქტორის იდენტიფიკატორის ანგარიშგება {#report-actor-claim}

Mix-ის ბილდისა და ტესტის ანგარიშების მოთხოვნები შეიცავს არასავალდებულო `x-tuist-actor-id` ჰედერს მხოლოდ მაშინ, როცა თქვენ ცალსახად აკონფიგურირებთ ლეიბლს. დააყენეთ `TUIST_ACTOR_ID` ორგანიზაციის ფარგლებში უნიკალურ ლეიბლზე ან დაამატეთ `actor_id: "developer-label"` პროექტის `tuist` კონფიგურაციაში. გადაწყვეტისას უპირატესობა ენიჭება გარემოს ცვლადს, შემდეგ შესრულების დროის `:actor_id` პარამეტრებს და ბოლოს პროექტის კონფიგურაციას. ლეიბლი ნაგულისხმევად არ იგზავნება და პაკეტი არ ავტომატურად აღმოაჩენს ოპერაციული სისტემის მომხმარებლის სახელს. პროექტის ფიქსირებული ლეიბლი ვრცელდება ყველაზე, ვინც ამ კონფიგურაციას იყენებს. ცარიელი ან არასწორი გადაფარვები ტოვებენ იდენტიფიკატორს გამოტოვებულს და არ აბრუნებენ ნაგულისხმევ მნიშვნელობას; ეს არ შლის სარწმუნოებით დადასტურებულ იდენტობას. თუ მორგებული პროქსი უარყოფს უცნობ ჰედერებს, გამორთეთ ის `TUIST_ACTOR_ID=""`-ით.

იდენტიფიკატორები უნდა იყოს 1–128 ბაიტიანი, არა-თეთრი სივრცის ბეჭდვადი ASCII სიმბოლოები. არასწორი გადაფარვები გამოტოვებულია და არ ხდება ნაგულისხმევ მნიშვნელობაზე დაბრუნება. დადასტურებული ინდივიდუალური სარწმუნოებები აქვთ უპირატესობა; სხვა კლიენტის მიერ მოწოდებული იდენტიფიკატორები ჩანს როგორც **დაუდასტურებელი**, არასდროს ანიჭებენ წვდომას და არასდროს ავტომატურად არ უკავშირდებიან მომხმარებლებს. ნებისმიერს, ვისაც შეუძლია პროექტის ანგარიშების ნახვა, შეუძლია ამ იდენტიფიკატორების ნახვა, მათ შორის საჯარო მაყურებლებს, როცა პროექტი საჯაროა, და ისინი შედიან მონაცემთა ექსპორტში, ამიტომ არ ჩაწეროთ საიდუმლოებები. ძველი სერვერები იგნორირებენ ამ არასავალდებულო ჰედერს, ხოლო ახალი სერვერები იღებენ ძველ კლიენტებს მის გარეშე. ახალი საერთო-ტოკენის ანგარიშები იდენტიფიკატორის გარეშე აჩვენებს **უცნობი**-ს, გამომქვეყნებელი ორგანიზაციის ნაცვლად; ისტორიული ანგარიშები ინარჩუნებენ თავიანთ წინა მინიჭებას. ბილდისა და ტესტის ანგარიშგება ნაგულისხმევად მოითხოვს ავთენტიკაციას. თვითმასპინძელ ინსტალაციებს შეუძლიათ ცალსახად ჩართონ სარწმუნოების გარეშე ანგარიშგება, როგორც ქვემოთაა აღწერილი.

## სარწმუნოების გარეშე ანგარიშგება კერძო ქსელში {#network-trusted-publishing}

მას შემდეგ, რაც ოპერატორი დააკონფიგურირებს `TUIST_NETWORK_TRUSTED_INSIGHTS_ACCESS=true` ინსტანციაზე და გადატვირთავს მას, როგორც აღწერილია <.localized_link href="/guides/server/self-host/server#network-trusted-access">თვითმასპინძელობის სახელმძღვანელოში</.localized_link>, დააკონფიგურირეთ თქვენი დანიშნულების ადგილი. SDK ავტომატურად აღმოაჩენს, უშვებს თუ არა ინსტანცია სარწმუნოების გარეშე ანგარიშგებას, როცა სარწმუნოებები არ არის. ინსტანციის პარამეტრი ვრცელდება ყველა მხარდაჭერილ პროექტზე და არ აქვს დაფაზე გადამრთველი:

```elixir
tuist: [
  url: "https://tuist.internal.example",
  project: "account/project"
]
```

`mix tuist.compile` და `mix tuist.test` აქვეყნებენ სტრუქტურირებულ ანგარიშებს შესვლის გარეშე, როცა სარწმუნოებები ნამდვილად არ არის და აღმოჩენა ადასტურებს, რომ სერვერი ამას უშვებს. არ არის საჭირო არც კლიენტის ფლაგი და არც პროექტის ჩართვა. არსებული სარწმუნოებები, მათ შორის მოწოდებული CI OIDC იდენტობა, გამოიყენება ან უარყოფილი იქნება, არასდროს იგნორირდება არააუთენტიკურ ანგარიშგებაზე გადასვლისთვის. მხოლოდ თეთრი სივრცის შემცველი `TUIST_TOKEN` არის შეცდომა. ცარიელი `TUIST_TOKEN` შეიძლება დაუბრუნდეს ვალიდურ შენახულ სარწმუნოებებს ან მოწოდებულ OIDC-ს, ხოლო მოძველებული შენახული სარწმუნოებები შეიძლება დაუბრუნდნენ მოწოდებულ OIDC-ს; ორივე გზა რჩება აუთენტიკური და არასდროს ართავს არააუთენტიკურ ანგარიშგებას. გამოუსადეგარი სარწმუნოებები ინახება და მარცხდება, როცა არცერთი აუთენტიკური ალტერნატივა არ წარმატდება. განაახლეთ ყველა სერვერის რეპლიკა აღმოჩენის შესაძლებლობის მქონე ვერსიამდე, სანამ განაახლებთ სარწმუნოების გარეშე კლიენტებს; უფრო ძველ სერვერებს აღმოჩენის გარეშე, გათიშულ ინსტანციებს და აღმოჩენის შეცდომებს კვლავ სჭირდებათ აუთენტიკაცია.

არააუთენტიკური გაშვებები არის ტელემეტრია, არა სანდო ფლეიკობის, კარანტინის, დაფარვის ან შერჩევითი შესრულების მტკიცებულება. შარდების დაგეგმვა, ბილდის არქივები და დაფარვის/არტეფაქტების endpoint-ები კვლავ მოითხოვს სარწმუნოებებს. დააყენეთ `TUIST_ACTOR_ID=""` დამოუკიდებლად, რათა გამოტოვოთ კონფიგურირებული აქტორის იდენტიფიკატორი; დადასტურებული სარწმუნოების იდენტობა უცვლელი რჩება.

## რა ფიქსირდება {#what-is-tracked}

ყოველი ბილდისთვის პაკეტი აგროვებს:
- მის ხანგრძლივობას, წარმატებას თუ არა, და Elixir, Erlang/OTP და Mix გარემოს, რომელშიც ის გაშვებული იყო
- ყოველ გაფრთხილებას და შეცდომას, მათი ფაილით და ხაზით
- რამდენ ხანს იკომპილირებოდა თითოეული ფაილი და რომელ მოდულებს განსაზღვრავს
- ფაილებს, რომლებზეც თითოეული ფაილია დამოკიდებული, და სჭირდება თუ არა ისინი კომპილაციის დროს თუ მხოლოდ შესრულების დროს
- რას აკეთებდა ბილდი ფაილების კომპილაციის გარდა, მაგალითად ტიპების შემოწმებას, დისკზე ჩაწერას და სხვა Mix კომპილატორებს
- მანქანის პროცესორის, მეხსიერების, ქსელის და დისკის გამოყენებას ბილდის დროს
- ბრენჩს და კომიტს, ხოლო უწყვეტი ინტეგრაციის დროს — პროვაიდერს და გაშვებას

## იპოვეთ, რა ანელებს ბილდს {#find-what-slows-a-build-down}

გახსენით ბილდი დაფაზე **ბილდები → ბილდის გაშვებები**-დან. ბილდები, მათი დიაგნოსტიკის რაოდენობა და მათი დამოკიდებულების ქეშის შეჯამებები ასევე ხელმისაწვდომია `tuist build mix list` და `tuist build mix show`-ით, `GET /api/projects/{account_handle}/{project_handle}/mix/builds`-ით, და `list_mix_builds` და `get_mix_build` <.localized_link href="/guides/features/agentic-coding/mcp">MCP ინსტრუმენტებით</.localized_link>.

**მიმოხილვა** ჩანართი ჩამოთვლის ფაილებს, რომლებიც ბილდმა აკომპილირა. შეგიძლიათ დააჯგუფოთ ისინი მოდულის მიხედვით, მოძებნოთ ისინი და დაალაგოთ:
- **კომპილაციის ხანგრძლივობით**, რათა იპოვოთ ფაილები, რომლებიც თავისთავად ნელია.
- **კომპილაციის დროის დამოკიდებულებებით**, იმ ფაილების რაოდენობით, რომლებიც ვერ აკომპილირდებიან, სანამ ეს არ აკომპილირდება. ნელი ფაილი ბევრი დამოკიდებულებით აფერხებს ბილდის დანარჩენ ნაწილს და მისი ცვლილება ყველა მათგანის ხელახლა კომპილაციას იწვევს.
- **კომპილაციის დროის დამოკიდებულებებით**, იმ ფაილების რაოდენობით, რომლებსაც ეს ელოდება.

![Phoenix აპლიკაციის Mix ბილდის მიმოხილვა](/images/guides/features/elixir/build.png)

**დროის ხაზი** ჩანართი აჩვენებს იგივე ბილდს დროთა განმავლობაში: რომელი ფაილები აკომპილირდა პარალელურად, სად შეამოწმა ბილდმა ტიპები და ჩაწერა დისკზე, და როგორ იყო მანქანა დატვირთული ყოველ მომენტში. მონაკვეთი ერთი ზოლით არის მონაკვეთი, სადაც ბილდს არ შეეძლო არსებული ბირთვების გამოყენება.

![Phoenix აპლიკაციის სრული Mix ბილდის დროის ხაზი](/images/guides/features/elixir/build-timeline.png)

**გაფრთხილებები** და **შეცდომები** ჩანართები ჩამოთვლიან ბილდის დიაგნოსტიკას.

## მორგებული მეტამონაცემები {#custom-metadata}

მიამაგრეთ ტეგები და გასაღებ-მნიშვნელობის მონაცემები Mix ბილდებს, რათა განასხვავოთ გაშვებები სხვადასხვა გუნდების, აღჭურვილობის ან სამუშაო პროცესების მიხედვით. ორივე ჩანს თითოეული ბილდის დეტალურ გვერდზე.

დააყენეთ მეტამონაცემები გარემოს ცვლადებით:

```sh
export TUIST_TAGS="nightly,release"
export TUIST_VALUES="ticket=TUIST-123,runner=linux-arm64"
```

ასევე შეგიძლიათ დააკონფიგურიროთ მეტამონაცემები `mix.exs`-ში:

```elixir
tuist: [
  project: "account/project",
  tags: ["nightly", "release"],
  values: %{"ticket" => "TUIST-123", "runner" => "linux-arm64"}
]
```

ტეგები ორივე წყაროდან ერთიანდება. როდესაც ერთი და იგივე გასაღები ორივე ადგილას არის კონფიგურირებული, უპირატესობა ენიჭება გარემოს ცვლადში მითითებულ მნიშვნელობას.

ტეგები უნდა შეიცავდეს მხოლოდ ასოებს, ციფრებს, დეფისებს და ქვეტირეებს. ბილდს შეიძლება ჰქონდეს მაქსიმუმ 50 ტეგი, და თითოეული ტეგი შეიძლება შეიცავდეს მაქსიმუმ 50 სიმბოლოს. ბილდს შეიძლება ჰქონდეს მაქსიმუმ 20 გასაღებ-მნიშვნელობის ჩანაწერი, თითოეული გასაღები შეიძლება შეიცავდეს მაქსიმუმ 50 სიმბოლოს, და თითოეული მნიშვნელობა შეიძლება შეიცავდეს მაქსიმუმ 500 სიმბოლოს. ეს იგივე სერვერის მხარის ლიმიტებია, რომლებიც გამოიყენება Xcode ბილდის მეტამონაცემებისთვის. პაკეტი გამოტოვებს არასწორ ტეგებს და ზედმეტად დიდ ან ცარიელ მეტამონაცემთა ჩანაწერებს ანგარიშის გაგზავნამდე, ამიტომ არასწორმა კონფიგურაციამ ვერ შეუშლის ხელი ბილდის ინსაიტების ანგარიშის დანარჩენი ნაწილის შენახვას. გამოიყენეთ გასაღებ-მნიშვნელობის მეტამონაცემები იმ მნიშვნელობებისთვის, რომლებიც არ აკმაყოფილებენ ტეგის შეზღუდვას.

მორგებული მეტამონაცემები მიმაგრებულია ბილდებს და არა ტესტების გაშვებებს.

მორგებული მეტამონაცემები ხილულია პროექტის წევრებისთვის დაშბორდზე. არ გამოიყენოთ ის სერთიფიკატების, წვდომის ტოკენების ან სხვა მგრძნობიარე მონაცემებისთვის. Tuist ინახავს Mix ბილდის მონაცემებს, მათ შორის ამ მეტამონაცემებს, 90 დღის განმავლობაში. დეტალური ინფორმაციისთვის იხილეთ <.localized_link href="/guides/server/data-retention">მონაცემთა შენახვის პოლიტიკა</.localized_link>.

## პრობლემების გადაჭრა {#troubleshooting}

ანგარიშგება არასდროს ცვლის თქვენი ბილდის შედეგს: თუ ანგარიშის გაგზავნა ვერ ხერხდება, ბილდი სრულდება ისე, როგორც უნდა დასრულებულიყო და არაფერი ბეჭდება. იმის სანახავად, რატომ არ გაიგზავნა ანგარიში, დააყენეთ `TUIST_DEBUG=1`:

```bash
TUIST_DEBUG=1 mix compile --force
```
