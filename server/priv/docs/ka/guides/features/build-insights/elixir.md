# Elixir-ის ბილდის ანალიტიკა {#elixir-build-insights}

Tuist-ის Hex პაკეტს შეუძლია ბილდის ანალიტიკის გაგზავნა Tuist-ში. ბილდის დრო, თქვენს ფაილებს შორის არსებული დამოკიდებულების გრაფი და მათი ცვლილება დროთა განმავლობაში გაძლევთ იმ ინფორმაციას, რაც საჭიროა ბილდის გრაფის ოპტიმიზაციისთვის და კომპილაციის გარემოში ხელმისაწვდომი ყველა ბირთვის მაქსიმალურად გამოყენებისთვის.

> [!IMPORTANT]
> **მოთხოვნები**
>
> - დაასრულეთ <.localized_link href="/guides/get-started/elixir-project">Elixir-ით დაწყება</.localized_link>

## ბილდების ანგარიშგება {#report-your-builds}

გაზიარებული კონფიგურაცია აყენებს კომპილაციის ინტეგრაციას. განაგრძეთ ჩვეული ბრძანებების გამოყენება:

```bash
mix compile
```

ინტეგრაცია მოიცავს `mix compile` და ყოველ კომპილაციას, რომელიც სხვა ამოცანამ გამოიწვია, მაგალითად `mix test` ან `mix phx.server`. კომპილაცია, რომელიც ვერ პოულობს შესასრულებელ სამუშაოს, არ აისახება ანგარიშში, ამიტომ დაფარდაზე ჩამოთვლილია მხოლოდ ის ბილდები, რომლებმაც რეალურად იმუშავეს.

## აქტორის იდენტიფიკატორის მიკუთვნება {#report-actor-claim}

Mix-ის ბილდისა და ტესტის ანგარიშის მოთხოვნები მოიცავენ არასავალდებულო `x-tuist-actor-id` ჰედერს მხოლოდ მაშინ, როცა თქვენ ცალსახად აყენებთ ლეიბლს. დააყენეთ `TUIST_ACTOR_ID` ორგანიზაციის ფარგლებში არსებულ ლეიბლზე ან დაამატეთ `actor_id: "developer-label"` პროექტის `tuist` კონფიგურაციაში. გადაწყვეტის თანმიმდევრობა უპირატესობას ანიჭებს გარემოს ცვლადს, შემდეგ runtime-ის `:actor_id` პარამეტრებს და ბოლოს პროექტის კონფიგურაციას. ლეიბლი ნაგულისხმევად არ იგზავნება და პაკეტი არ ავლენს ოპერაციული სისტემის მომხმარებლის სახელებს. ფიქსირებული პროექტის ლეიბლი ვრცელდება ყველაზე, ვინც იყენებს ამ კონფიგურაციას. ცარიელი ან არასწორი გადაფარვები ტოვებენ იდენტიფიკატორის მიკუთვნებას (claim) და არ ახდენენ დაბრუნებას (fallback); ეს არ შლის სარწმუნოებით დადასტურებულ იდენტობას. თუ მორგებული პროქსი უარყოფს უცნობ ჰედერებს, გამორთეთ ის `TUIST_ACTOR_ID=""`-ით.

იდენტიფიკატორები უნდა შედგებოდეს 1–128 ბაიტისგან, რომლებიც წარმოადგენენ ASCII-ს ბეჭდვად სიმბოლოებს (გამოკლებულია space). არასწორი გადაფარვები გამოტოვებულია დაბრუნების (fallback) გარეშე. დადასტურებული ინდივიდუალური სარწმუნოებები აქვთ უპირატესობა; სხვა კლიენტის მიერ მოწოდებული იდენტიფიკატორები გამოისახება როგორც **დაუდასტურებელი**, არასდროს ანიჭებენ წვდომას და არასდროს ბმავს მომხმარებლებთან ავტომატურად. ნებისმიერს, ვისაც შეუძლია ნახოს პროექტის ანგარიშები, შეუძლია დაინახოს ეს იდენტიფიკატორები, მათ შორის საჯარო დამთვალიერებლებს, როცა პროექტი საჯაროა, და ისინი შედიან მონაცემთა ექსპორტში, ამიტომ არ ჩართოთ საიდუმლოებები. ძველი სერვერები იგნორირებენ არასავალდებულო ჰედერს, ხოლო ახალი სერვერები იღებენ ძველ კლიენტებს მის გარეშე. ახალი გაზიარებული-ტოკენის ანგარიშები იდენტიფიკატორის გარეშე აჩვენებენ **უცნობი**-ს, გამომქვეყნებელი ორგანიზაციის ნაცვლად; ისტორიული ანგარიშები ინარჩუნებენ წინა მიკუთვნებას. ბილდისა და ტესტის ანგარიშგება ნაგულისხმევად მოითხოვს ავთენტიკაციას. თვითმასპინძელ ინსტალაციებს შეუძლიათ ცალსახად ჩართონ სარწმუნოების გარეშე ანგარიშგება, როგორც ქვემოთაა აღწერილი.

## სარწმუნოების გარეშე ანგარიშგება კერძო ქსელში {#network-trusted-publishing}

მას შემდეგ, რაც ოპერატორი დააყენებს `TUIST_NETWORK_TRUSTED_INSIGHTS_ACCESS=true`-ს ინსტანციაზე და გადატვირთავს მას, როგორც აღწერილია <.localized_link href="/guides/server/self-host/server#network-trusted-access">თვითმასპინძლობის სახელმძღვანელოში</.localized_link>, დააკონფიგურირეთ თქვენი დანიშნულების ადგილი. SDK ავტომატურად ამოიცნობს, ნებას აძლევს თუ არა ინსტანცია სარწმუნოების გარეშე ანგარიშგებას, როცა სარწმუნოებები არ არის. ინსტანციის პარამეტრი მოიცავს ყველა მხარდაჭერილ პროექტს და არ აქვს დაფარდაზე გადამრთველი:

```elixir
tuist: [
  url: "https://tuist.internal.example",
  project: "account/project"
]
```

`mix tuist.compile` და `mix tuist.test` აქვეყნებენ სტრუქტურირებულ ანგარიშებს შესვლის გარეშე, როცა სარწმუნოებები რეალურად არ არის და აღმოჩენა ადასტურებს, რომ სერვერი ნებას აძლევს ამას. არ არის საჭირო არც კლიენტის ფლაგი და არც პროექტის opt-in. არსებული სარწმუნოებები, მათ შორის მოწოდებული CI OIDC იდენტობა, გამოიყენება ან უარყოფილი იქნება, არასდროს იგნორირდება ხელმოუწერელი ანგარიშგებისკენ დასაწევად. მხოლოდ თეთრი სივრცისგან შემდგარი `TUIST_TOKEN` არის შეცდომა. ცარიელი `TUIST_TOKEN` შეიძლება დაუბრუნდეს ვალიდურ შენახულ სარწმუნოებებს ან მოწოდებულ OIDC-ს, ხოლო მოძველებული შენახული სარწმუნოებები შეიძლება დაუბრუნდნენ მოწოდებულ OIDC-ს; ორივე გზა რჩება ავთენტიფიცირებული და არასდროს აძლევს ხელმოუწერელი ანგარიშგების უფლებას. გამოუყენებელი სარწმუნოებები ინახება და მარცხდება, როცა არცერთი ავთენტიფიცირებული დაბრუნება (fallback) არ წარმატდება. განაახლეთ სერვერის ყველა რეპლიკა აღმოჩენის შესაძლებლობის მქონე ვერსიამდე, სანამ განაახლებთ სარწმუნოების გარეშე კლიენტებს; უფრო ძველ სერვერებს აღმოჩენის გარეშე, გამორთულ ინსტანციებს და აღმოჩენის შეცდომებს კვლავ სჭირდებათ ავთენტიკაცია.

ხელმოუწერელი გაშვებები არის ტელემეტრია, არა სანდო flakiness-ის, კარანტინის, დაფარვის ან შერჩევითი შესრულების მტკიცებულება. Shard-ების დაგეგმვა, ბილდის არქივები და დაფარვის/არტეფაქტის endpoint-ები კვლავ მოითხოვენ სარწმუნოებებს. დააყენეთ `TUIST_ACTOR_ID=""` დამოუკიდებლად, რომ გამოტოვოთ კონფიგურირებული აქტორის მიკუთვნება; დადასტურებული სარწმუნოების იდენტობა უცვლელი რჩება.

## რა ფიქსირდება {#what-is-tracked}

ყოველი ბილდისთვის პაკეტი აგროვებს:
- მის ხანგრძლივობას, წარმატებას თუ არა, და Elixir, Erlang/OTP და Mix გარემოს, რომელშიც ის გაშვებული იყო
- ყოველ გაფრთხილებასა და შეცდომას, მისი ფაილითა და ხაზით
- რამდენ ხანს იკომპილირებოდა თითოეული ფაილი და რომელ მოდულებს განსაზღვრავს ის
- ფაილებს, რომლებზეც თითოეული ფაილია დამოკიდებული, და სჭირდება თუ არა ისინი კომპილაციის დროს თუ მხოლოდ runtime-ში
- რას აკეთებდა ბილდი ფაილების კომპილაციის გარდა, მაგალითად ტიპების შემოწმებას, დისკზე ჩაწერას და სხვა Mix კომპილატორებს
- მანქანის პროცესორის, მეხსიერების, ქსელისა და დისკის გამოყენებას ბილდის დროს
- ბრენჩსა და კომიტს, ხოლო უწყვეტი ინტეგრაციის დროს — პროვაიდერსა და გაშვებას

## იპოვეთ, რა ანელებს ბილდს {#find-what-slows-a-build-down}

გახსენით ბილდი დაფაზე **Builds → Build Runs**-დან. ბილდები, მათი დიაგნოსტიკის რაოდენობა და დამოკიდებულების ქეშის შეჯამებები ასევე ხელმისაწვდომია `tuist build mix list`-ისა და `tuist build mix show`-ის საშუალებით, `GET /api/projects/{account_handle}/{project_handle}/mix/builds`-ის მეშვეობით, ისევე როგორც `list_mix_builds` და `get_mix_build` <.localized_link href="/guides/features/agentic-coding/mcp">MCP ინსტრუმენტების</.localized_link> გამოყენებით.

**მიმოხილვა** ჩანართი ჩამოთვლის ფაილებს, რომლებიც ბილდმა აკომპილირა. შეგიძლიათ დააჯგუფოთ ისინი მოდულის მიხედვით, მოძებნოთ ისინი და დაალაგოთ:
- **კომპილაციის ხანგრძლივობა**, რათა იპოვოთ ფაილები, რომლებიც თავისთავად ნელია.
- **კომპილაციის დროის დამოკიდებულებები**, იმ ფაილების რაოდენობა, რომლებსაც არ შეუძლიათ კომპილაცია, სანამ ეს ერთი არ დასრულდება. ნელ ფაილს ბევრი დამოკიდებულებით შეუძლია შეაფერხოს ბილდის დანარჩენი ნაწილი და მისი ცვლილება ხელახლა აკომპილირებს მათ ყველას.
- **კომპილაციის დროის დამოკიდებულებები**, იმ ფაილების რაოდენობა, რომლებსაც ეს ერთი ელოდება.

**დროის ხაზი** ჩანართი აჩვენებს იმავე ბილდს დროთა განმავლობაში: რომელი ფაილები კომპილირდებოდა პარალელურად, სად აკეთებდა ბილდი ტიპების შემოწმებას და დისკზე ჩაწერას, და როგორ იყო მანქანა დატვირთული ყოველ მომენტში. მონაკვეთი ერთი ზოლით არის მონაკვეთი, სადაც ბილდს არ შეეძლო ხელმისაწვდომი ბირთვების გამოყენება.

![Phoenix აპლიკაციის სრული Mix ბილდის დროის ხაზი](/images/guides/features/elixir/build-timeline.png)

**გაფრთხილებები** და **შეცდომები** ჩანართები ჩამოთვლიან ბილდის დიაგნოსტიკას.

## მორგებული მეტამონაცემები {#custom-metadata}

მიამაგრეთ ტეგები და key-value მონაცემები Mix ბილდებს, რათა განასხვავოთ გაშვებები სხვადასხვა გუნდების, აპარატურის ან სამუშაო ნაკადების მიხედვით. ორივე ჩანს თითოეული ბილდის დეტალურ გვერდზე.

დააყენეთ მეტამონაცემები გარემოს ცვლადებით:

```sh
export TUIST_TAGS="nightly,release"
export TUIST_VALUES="ticket=TUIST-123,runner=linux-arm64"
```

ასევე შეგიძლიათ დააკონფიგურიროთ მეტამონაცემები `mix.exs`-ში:

```elixir
tuist: [
  project: "account/project",
  tags: ["nightly", "release"],
  values: %{"ticket" => "TUIST-123", "runner" => "linux-arm64"}
]
```

ტეგები ორივე წყაროდან ერთიანდება. როდესაც ერთი და იგივე გასაღები ორივე ადგილას არის კონფიგურირებული, გარემოს ცვლადში მითითებული მნიშვნელობა აქვს უპირატესობა.

ტეგებმა უნდა შეიცავდნენ მხოლოდ ასოებს, რიცხვებს, დეფისებს და ქვედა ტირეებს. ბილდს შეიძლება ჰქონდეს 50-მდე ტეგი და თითოეული ტეგი შეიძლება შეიცავდეს 50 სიმბოლომდე. ბილდს შეიძლება ჰქონდეს 20-მდე key-value ჩანაწერი, თითოეული გასაღები შეიძლება შეიცავდეს 50 სიმბოლომდე, ხოლო თითოეული მნიშვნელობა — 500 სიმბოლომდე. ეს იგივე სერვერის მხარეს არსებული ლიმიტებია, რომლებიც გამოიყენება Xcode ბილდის მეტამონაცემებისთვის. პაკეტი გამოტოვებს არასწორ ტეგებს და ზომით გადაჭარბებულ ან ცარიელ მეტამონაცემთა ჩანაწერებს ანგარიშის გაგზავნამდე, ამიტომ არასწორმა კონფიგურაციამ ვერ შეუშლის ხელი ბილდის ანალიტიკის ანგარიშის დანარჩენი ნაწილის შენახვას. გამოიყენეთ key-value მეტამონაცემები ისეთი მნიშვნელობებისთვის, რომლებიც არ აკმაყოფილებენ ტეგის შეზღუდვას.

მორგებული მეტამონაცემები მიმაგრებულია ბილდებს და არა ტესტების გაშვებებს.

მორგებული მეტამონაცემები ხილულია პროექტის წევრებისთვის დაფაზე. არ გამოიყენოთ ის სერთიფიკატების, წვდომის ტოკენების ან სხვა მგრძნობიარე მონაცემებისთვის. Tuist ინახავს Mix ბილდის მონაცემებს, მათ შორის ამ მეტამონაცემებს, 90 დღის განმავლობაში. დეტალებისთვის იხილეთ <.localized_link href="/guides/server/data-retention">მონაცემთა შენახვის პოლიტიკა</.localized_link>.

## პრობლემების აღმოფხვრა {#troubleshooting}

ანგარიშგება არასდროს ცვლის თქვენი ბილდის შედეგს: თუ ანგარიშის გაგზავნა ვერ ხერხდება, ბილდი სრულდება ისე, როგორც უნდა დასრულებულიყო და არაფერი იბეჭდება. იმის სანახავად, თუ რატომ არ გაიგზავნა ანგარიში, დააყენეთ `TUIST_DEBUG=1`:

```bash
TUIST_DEBUG=1 mix compile --force
```
