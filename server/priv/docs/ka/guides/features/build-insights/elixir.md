# Elixir-ის ბილდის ანალიტიკა {#elixir-build-insights}

Tuist-ის Hex პაკეტს შეუძლია ბილდის ანალიტიკის Tuist-ზე გაგზავნა. კომპილაციის დრო, თქვენს ფაილებს შორის დამოკიდებულების გრაფი და მათი ცვლილება დროში გაძლევთ იმ ინფორმაციას, რაც საჭიროა ბილდის გრაფის ოპტიმიზაციისთვის და კომპილაციის გარემოში ხელმისაწვდომი ყველა ბირთვის მაქსიმალურად გამოყენებისთვის.

> [!IMPORTANT] REQUIREMENTS
> - დაასრულეთ <.localized_link href="/guides/get-started/elixir-project">Elixir-ით დაწყება</.localized_link>

## ბილდების მოხსენება {#report-your-builds}

ერთობრივი კონფიგურაცია აყენებს კომპილაციის ინტეგრაციას. განაგრძეთ ჩვეული ბრძანებების გამოყენება:

```bash
mix compile
```

ინტეგრაცია მოიცავს `mix compile`-ს და ყოველ კომპილაციას, რომელსაც სხვა ამოცანა იწვევს, მაგალითად `mix test` ან `mix phx.server`. კომპილაცია, რომელიც ვერ პოულობს შესასრულებელ სამუშაოს, არ მოიხსენიება, ამიტომ დაფისზე მხოლოდ ის ბილდები ჩანს, რომლებმაც რეალურად იმუშავეს.

## აქტორის მიკუთვნების მოხსენება {#report-actor-claim}

Mix-ის ბილდისა და ტესტის მოხსენების მოთხოვნები მოიცავს არასავალდებულო `x-tuist-actor-id` ჰედერს მხოლოდ მაშინ, როცა თქვენ ცალსახად მიუთითებთ ლეიბლს. დააყენეთ `TUIST_ACTOR_ID` ორგანიზაციის ფარგლებში უნიკალურ ლეიბლზე ან დაამატეთ `actor_id: "developer-label"` პროექტის `tuist` კონფიგურაციაში. პრიორიტეტი ენიჭება გარემოს ცვლადს, შემდეგ შესრულების დროს მითითებულ `:actor_id` პარამეტრებს და ბოლოს პროექტის კონფიგურაციას. ლეიბლი ნაგულისხმევად არ იგზავნება და პაკეტი არ ავტომატურად ადგენს ოპერაციული სისტემის მომხმარებლის სახელს. პროექტისთვის ფიქსირებული ლეიბლი ვრცელდება ყველაზე, ვინც ამ კონფიგურაციას იყენებს. ცარიელი ან არასწორი გადაფარვები ტოვებენ მიკუთვნებას (claim) გაუგზავნელად ნაცვლად იმისა, რომ დაუბრუნდნენ წინა მნიშვნელობას; ეს არ შლის სერთიფიკატებით დადასტურებულ იდენტობას. თუ მორგებული პროქსი უარყოფს უცნობ ჰედერებს, გამორთეთ ეს ფუნქცია `TUIST_ACTOR_ID=""`-ით.

იდენტიფიკატორები უნდა შედგებოდეს 1–128 ბაიტისგან, რომლებიც არიან ბეჭდვადი ASCII სიმბოლოები (გამოკლებულია space). არასწორი გადაფარვები გამოტოვებულია დაწინაურების გარეშე. დადასტურებული ინდივიდუალური სერთიფიკატები აქვთ უპირატესობა; სხვა კლიენტის მიერ მოხსენებული იდენტიფიკატორები ჩანს როგორც **Unverified**, არასდროს ანიჭებენ წვდომას და არასდროს ბმავს მომხმარებლებთან ავტომატურად. ნებისმიერს, ვისაც შეუძლია ნახოს პროექტის მოხსენებები, შეუძლია დაინახოს ეს იდენტიფიკატორები, მათ შორის საჯარო მომხმარებლებს, როცა პროექტი საჯაროა, და ისინი შედიან მონაცემთა ექსპორტში, ამიტომ არ ჩაწეროთ საიდუმლოები. ძველი სერვერები იგნორირებენ ამ არასავალდებულო ჰედერს, ხოლო ახალი სერვერები იღებენ ძველ კლიენტებს მის გარეშე. ახალი საერთო-ტოკენის მოხსენებები იდენტიფიკატორის გარეშე აჩვენებს **Unknown**-ს გამომქვეყნებელი ორგანიზაციის ნაცვლად; ისტორიული მოხსენებები ინარჩუნებენ თავიანთ წინა მიკუთვნებას. ბილდისა და ტესტის მოხსენებას ნაგულისხმევად სჭირდება ავთენტიკაცია. თვითმასპინძელ ინსტალაციებს შეუძლიათ ცალსახად ჩართონ სერთიფიკატების გარეშე მოხსენება, როგორც ქვემოთაა აღწერილი.

## სერთიფიკატების გარეშე მოხსენება კერძო ქსელში {#network-trusted-publishing}

მას შემდეგ, რაც ოპერატორი დააყენებს `TUIST_NETWORK_TRUSTED_INSIGHTS_ACCESS=true`-ს ინსტანსზე და გადატვირთავს მას, როგორც აღწერილია <.localized_link href="/guides/server/self-host/server#network-trusted-access">თვითმასპინძლობის სახელმძღვანელოში</.localized_link>, დააკონფიგურირეთ თქვენი დანიშნულება. SDK ავტომატურად ამოწმებს, ნებას რთავს თუ არა ინსტანსი სერთიფიკატების გარეშე მოხსენებას, როცა სერთიფიკატები არ არის. ინსტანსის პარამეტრი მოიცავს ყველა მხარდაჭერილ პროექტს და არ აქვს დაფის გადამრთველი:

```elixir
tuist: [
  url: "https://tuist.internal.example",
  project: "account/project"
]
```

`mix tuist.compile` და `mix tuist.test` აქვეყნებს სტრუქტურირებულ მოხსენებებს შესვლის გარეშე, როცა სერთიფიკატები ნამდვილად არ არის და აღმოჩენა ადასტურებს, რომ სერვერი ამას ნებას რთავს. კლიენტის დროშა ან პროექტის თანხმობა არ არის საჭირო. არსებული სერთიფიკატები, მათ შორის მიწოდებული CI OIDC იდენტობა, გამოიყენება ან უარყოფილია, არასდროს იგნორირდება ხელმოუწერილი მოხსენებისთვის დაწევის მიზნით. მხოლოდ თეთრი სივრცისგან შემდგარი `TUIST_TOKEN` არის შეცდომა. ცარიელი `TUIST_TOKEN` შეიძლება დაუბრუნდეს ვალიდურ შენახულ სერთიფიკატებს ან მიწოდებულ OIDC-ს, ხოლო მოძველებული შენახული სერთიფიკატები შეიძლება დაუბრუნდნენ მიწოდებულ OIDC-ს; ორივე გზა რჩება ავთენტიფიცირებული და არასდროს რთავს ხელმოუწერელ მოხსენებას. გამოუსადეგარი სერთიფიკატები ინახება და ვერ ასრულებენ მოქმედებას, როცა ავთენტიფიცირებული ალტერნატივა ვერ მუშაობს. განაახლეთ ყველა სერვერის რეპლიკა აღმოჩენის მხარდაჭერის მქონე ვერსიამდე სერთიფიკატების გარეშე კლიენტების განახლებამდე; უფრო ძველ სერვერებს აღმოჩენის გარეშე, გათიშულ ინსტანსებს და აღმოჩენის შეცდომებს კვლავ სჭირდებათ ავთენტიკაცია.

ხელმოუწერილი გაშვებები არის ტელემეტრია, არა სანდო ფლეიკობის, კარანტინის, დაფარვის ან შერჩევითი შესრულების მტკიცებულება. შარდების დაგეგმვა, ბილდის არქივები და დაფარვის/არტეფაქტების endpoint-ები კვლავ მოითხოვს სერთიფიკატებს. დააყენეთ `TUIST_ACTOR_ID=""` დამოუკიდებლად, რათა გამოტოვოთ კონფიგურირებული აქტორის მიკუთვნება; დადასტურებული სერთიფიკატის იდენტობაზე ეს გავლენას არ ახდენს.

## რა ფიქსირდება {#what-is-tracked}

ყოველი ბილდისთვის პაკეტი აგროვებს:
- მის ხანგრძლივობას, წარმატებით დასრულდა თუ არა, და Elixir-ის, Erlang/OTP-ისა და Mix-ის გარემოს, რომელშიც გაშვებული იყო
- ყოველ გაფრთხილებასა და შეცდომას, მისი ფაილითა და ხაზით
- რამდენი დრო დასჭირდა ყოველი ფაილის კომპილაციას და რა მოდულებს განსაზღვრავს ის
- ფაილებს, რომლებზეც ყოველი ფაილია დამოკიდებული, და სჭირდება თუ არა ისინი კომპილაციის დროს თუ მხოლოდ შესრულების დროს
- რას აკეთებდა ბილდი ფაილების კომპილაციის გარდა, მაგალითად ტიპების შემოწმებას, დისკზე ჩაწერას და სხვა Mix კომპილატორებს
- მანქანის პროცესორის, მეხსიერების, ქსელისა და დისკის გამოყენებას ბილდის დროს
- ბრენჩსა და კომიტს, ხოლო უწყვეტი ინტეგრაციის შემთხვევაში — პროვაიდერსა და გაშვებას

## იპოვეთ, რა ანელებს ბილდს {#find-what-slows-a-build-down}

გახსენით ბილდი დაფის **Builds → Build Runs** განყოფილებიდან. ბილდები, მათი დიაგნოსტიკის რაოდენობა და დამოკიდებულების ქეშის შეჯამებები ასევე ხელმისაწვდომია `tuist build mix list`-ისა და `tuist build mix show`-ის, `GET /api/projects/{account_handle}/{project_handle}/mix/builds`-ის, ასევე `list_mix_builds`-ისა და `get_mix_build` <.localized_link href="/guides/features/agentic-coding/mcp">MCP ხელსაწყოების</.localized_link> მეშვეობით.

**Overview** ჩანართი ჩამოთვლის ფაილებს, რომლებიც ბილდმა დააკომპილირა. შეგიძლიათ დააჯგუფოთ ისინი მოდულის მიხედვით, მოძებნოთ და დაალაგოთ:
- **კომპილაციის ხანგრძლივობის** მიხედვით, რათა იპოვოთ ფაილები, რომლებიც თავისთავად ნელია.
- **კომპილაციის დროის დამოკიდებულებების** მიხედვით, ანუ იმ ფაილების რაოდენობა, რომლებიც ვერ დაკომპილირდებიან, სანამ ეს ერთი არ დასრულდება. ნელი ფაილი ბევრი დამოკიდებულებით აფერხებს ბილდის დანარჩენ ნაწილს და მისი ცვლილება ყველა მათგანის ხელახლა კომპილაციას იწვევს.
- **კომპილაციის დროის დამოკიდებულებების** მიხედვით, ანუ იმ ფაილების რაოდენობა, რომელსაც ეს ფაილი ელოდება.

![Phoenix აპლიკაციის Mix ბილდის მიმოხილვა](/images/guides/features/elixir/build.png)

**Timeline** ჩანართი აჩვენებს იმავე ბილდს დროში: რომელი ფაილები კომპილირდებოდა პარალელურად, სად ხდებოდა ტიპების შემოწმება და დისკზე ჩაწერა, და როგორ იყო დატვირთული მანქანა ყოველ მომენტში. მონაკვეთი ერთი ზოლით არის პერიოდი, როცა ბილდს არ შეეძლო ხელმისაწვდომი ბირთვების გამოყენება.

![Phoenix აპლიკაციის სრული Mix ბილდის დროითი გრაფიკი](/images/guides/features/elixir/build-timeline.png)

**Warnings** და **Errors** ჩანართები ჩამოთვლიან ბილდის დიაგნოსტიკას.

## მორგებული მეტამონაცემები {#custom-metadata}

მიამაგრეთ ტეგები და key-value მონაცემები Mix ბილდებს, რათა განასხვავოთ გაშვებები სხვადასხვა გუნდების, აპარატურის ან სამუშაო პროცესების მიხედვით. ორივე ჩანს ყოველი ბილდის დეტალურ გვერდზე.

დააყენეთ მეტამონაცემები გარემოს ცვლადებით:

```sh
export TUIST_TAGS="nightly,release"
export TUIST_VALUES="ticket=TUIST-123,runner=linux-arm64"
```

ასევე შეგიძლიათ დააკონფიგურიროთ მეტამონაცემები `mix.exs`-ში:

```elixir
tuist: [
  project: "account/project",
  tags: ["nightly", "release"],
  values: %{"ticket" => "TUIST-123", "runner" => "linux-arm64"}
]
```

ტეგები ორივე წყაროდან ერთიანდება. როდესაც ერთი და იგივე გასაღები ორივე ადგილას არის კონფიგურირებული, უპირატესობა ენიჭება გარემოს ცვლადში მითითებულ მნიშვნელობას.

ტეგები შეიძლება შეიცავდნენ მხოლოდ ასოებს, რიცხვებს, დეფისებს და ქვედა ტირეებს. ბილდს შეიძლება ჰქონდეს 50-მდე ტეგი და თითოეული ტეგი შეიძლება შეიცავდეს 50-მდე სიმბოლოს. ბილდს შეიძლება ჰქონდეს 20-მდე key-value ჩანაწერი, თითოეული გასაღები შეიძლება შეიცავდეს 50-მდე სიმბოლოს, ხოლო თითოეული მნიშვნელობა — 500-მდე სიმბოლოს. ეს იგივე სერვერის მხარეს მოქმედი ლიმიტებია, რომლებიც გამოიყენება Xcode ბილდის მეტამონაცემებისთვის. პაკეტი აგდებს არასწორ ტეგებს და ზედმეტად დიდ ან ცარიელ მეტამონაცემთა ჩანაწერებს ანგარიშის გაგზავნამდე, ამიტომ არასწორმა კონფიგურაციამ ვერ შეუშლის ხელი ბილდის ანალიტიკის დანარჩენი ნაწილის შენახვას. გამოიყენეთ key-value მეტამონაცემები ისეთი მნიშვნელობებისთვის, რომლებიც არ აკმაყოფილებენ ტეგის შეზღუდვებს.

მორგებული მეტამონაცემები მიბმულია ბილდებზე და არა ტესტების გაშვებებზე.

მორგებული მეტამონაცემები ჩანს პროექტის წევრებისთვის დაფლაში. არ გამოიყენოთ ის სერთიფიკატების, წვდომის ტოკენების ან სხვა მგრძნობიარე მონაცემებისთვის. Tuist ინახავს Mix ბილდის მონაცემებს, მათ შორის ამ მეტამონაცემებს, 90 დღის განმავლობაში. დეტალური ინფორმაციისთვის იხილეთ <.localized_link href="/guides/server/data-retention">მონაცემთა შენახვის პოლიტიკა</.localized_link>.

## პრობლემების გადაჭრა {#troubleshooting}

ანგარიშის გაგზავნა არასდროს ცვლის თქვენი ბილდის შედეგს: თუ ანგარიშის გაგზავნა ვერ ხერხდება, ბილდი სრულდება ისე, როგორც უნდა დასრულებულიყო და არაფერი ბეჭდავს. იმის სანახავად, თუ რატომ არ გაიგზავნა ანგარიში, დააყენეთ `TUIST_DEBUG=1`:

```bash
TUIST_DEBUG=1 mix compile --force
```
