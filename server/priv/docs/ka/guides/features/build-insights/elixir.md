# Elixir ბილდის ანალიტიკა {#elixir-build-insights}

Tuist-ის Hex პაკეტს შეუძლია ბილდის ანალიტიკა Tuist-ზე გაგზავნოს. ბილდის დრო, თქვენს ფაილებს შორის არსებული დამოკიდებულების გრაფი და მათი ცვლილება დროთა განმავლობაში გაძლევთ იმას, რაც გჭირდებათ ბილდის გრაფის ოპტიმიზაციისთვის და კომპილაციის გარემოში ხელმისაწვდომი ყველა ბირთვის მაქსიმალურად გამოყენებისთვის.

> [!IMPORTANT]
> **მოთხოვნები**
>
> - დაასრულეთ <.localized_link href="/guides/get-started/elixir-project">Elixir-ით დაწყება</.localized_link>

## ბილდების ანგარიშგება {#report-your-builds}

გაზიარებული კონფიგურაცია აინსტალირებს კომპილაციის ინტეგრაციას. განაგრძეთ ჩვეული ბრძანებების გამოყენება:

```bash
mix compile
```

ინტეგრაცია მოიცავს `mix compile`-ს და ყოველ კომპილაციას, რომელიც სხვა ამოცანამ გამოიწვია, მაგალითად `mix test` ან `mix phx.server`. კომპილაცია, რომელიც სამუშაოს ვერ პოულობს, არ იგზავნება ანგარიშში, ამიტომ დაფზე ჩამოთვლილია მხოლოდ ის ბილდები, რომლებმაც რეალური სამუშაო შეასრულეს.

## აქტორის მითითების ანგარიშგება {#report-actor-claim}

Mix-ის ბილდისა და ტესტის ანგარიშის მოთხოვნები მოიცავს ოპციონალურ `x-tuist-actor-id` ჰედერს მხოლოდ მაშინ, როცა თქვენ ცალსახად მიუთითებთ ნიშნულს. დააყენეთ `TUIST_ACTOR_ID` ორგანიზაციის ფარგლებში არსებულ ნიშნულზე ან დაამატეთ `actor_id: "developer-label"` პროექტის `tuist` კონფიგურაციაში. უპირატესობა ენიჭება გარემოს ცვლადს, შემდეგ შესრულების დროს მითითებულ `:actor_id` პარამეტრებს და ბოლოს პროექტის კონფიგურაციას. ნიშნული ნაგულისხმევად არ იგზავნება და პაკეტი არ ავლენს ოპერაციული სისტემის მომხმარებლის სახელებს. ფიქსირებული პროექტის ნიშნული ვრცელდება ყველაზე, ვინც ამ კონფიგურაციას იყენებს. ცარიელი ან არასწორი გადაფარვები ტოვებენ მითითებას უკან დახევის გარეშე; ეს არ შლის სერთიფიკატებზე დაფუძნებულ დადასტურებულ იდენტურობას. თუ მორგებული პროქსი უცნობ ჰედერებს უარყოფს, გამოთიშეთ ის `TUIST_ACTOR_ID=""`-ით.

იდენტიფიკატორები უნდა იყოს 1–128 ბაიტიანი, არა-სიცარიელე დაბეჭდილი ASCII სიმბოლოები. არასწორი გადაფარვები გამოიტოვება უკან დახევის გარეშე. დადასტურებული ინდივიდუალური სერთიფიკატები უპირატესობით სარგებლობენ; სხვა კლიენტის მიერ მოწოდებული იდენტიფიკატორები ჩანს როგორც **დაუდასტურებელი**, არასდროს ანიჭებენ წვდომას და არასდროს ბმავს ავტომატურად მომხმარებლებთან. ნებისმიერს, ვისაც შეუძლია ნახოს პროექტის ანგარიშები, შეუძლია დაინახოს ეს იდენტიფიკატორები, მათ შორის საჯარო დამთვალიერებლებს, როცა პროექტი საჯაროა, და ისინი შედიან მონაცემთა ექსპორტში, ამიტომ არ შეიტანოთ საიდუმლოები. ძველი სერვერები იგნორირებენ ოპციონალურ ჰედერს, ხოლო ახალი სერვერები იღებენ ძველ კლიენტებს მის გარეშე. ახალი გაზიარებული-ტოკენის ანგარიშები იდენტიფიკატორის გარეშე აჩვენებენ **უცნობი**-ს, გამომქვეყნებელი ორგანიზაციის ნაცვლად; ისტორიული ანგარიშები ინარჩუნებენ წინა მითითებას. ბილდისა და ტესტის ანგარიშგება ნაგულისხმევად მოითხოვს ავთენტიკაციას. თვითმასპინძელ ინსტალაციებს შეუძლიათ ცალსახად ჩართონ სერთიფიკატების გარეშე ანგარიშგება ქვემოთ აღწერილი წესით.

## სერთიფიკატების გარეშე ანგარიშგება კერძო ქსელში {#network-trusted-publishing}

მას შემდეგ, რაც ოპერატორი დააყენებს `TUIST_NETWORK_TRUSTED_INSIGHTS_ACCESS=true`-ს ინსტანციაზე და გადატვირთავს მას, როგორც აღწერილია <.localized_link href="/guides/server/self-host/server#network-trusted-access">თვითმასპინძლობის სახელმძღვანელოში</.localized_link>, დააკონფიგურირეთ თქვენი დანიშნულება. SDK ავტომატურად ადგენს, ნებას რთავს თუ არა ინსტანცია სერთიფიკატების გარეშე ანგარიშგებას, როცა სერთიფიკატები არ არის. ინსტანციის პარამეტრი მოიცავს ყველა მხარდაჭერილ პროექტს და არ აქვს დაფზე გადამრთველი:

```elixir
tuist: [
  url: "https://tuist.internal.example",
  project: "account/project"
]
```

`mix tuist.compile` და `mix tuist.test` აქვეყნებენ სტრუქტურირებულ ანგარიშებს შესვლის გარეშე, როცა სერთიფიკატები ნამდვილად არ არის და აღმოჩენა ადასტურებს, რომ სერვერი ამას ნებას რთავს. არ არის საჭირო არც კლიენტის ნიშანი და არც პროექტის თანხმობა. არსებული სერთიფიკატები, მათ შორის მოწოდებული CI OIDC იდენტურობა, გამოიყენება ან უარყოფილი იქნება, არასდროს იგნორირდება ხელმოუწერილი ანგარიშგებისთვის დასაწევად. მხოლოდ სიცარიელეებისგან შემდგარი `TUIST_TOKEN` არის შეცდომა. ცარიელ `TUIST_TOKEN`-ს შეუძლია გადავიდეს მოქმედ შენახულ სერთიფიკატებზე ან მოწოდებულ OIDC-ზე, ხოლო მოძველებულ შენახულ სერთიფიკატებს შეუძლიათ გადავიდნენ მოწოდებულ OIDC-ზე; ორივე გზა რჩება ავთენტიფიცირებული და არასდროს რთავს ხელმოუწერელ ანგარიშგებას. გამოუყენებელი სერთიფიკატები ინახება და ვერ ასრულებენ მოთხოვნას, როცა ავთენტიფიცირებული უკან დახევა ვერ ხერხდება. განაახლეთ სერვერის ყველა რეპლიკა აღმოჩენის შესაძლებლობის მქონე ვერსიამდე, სანამ განაახლებთ სერთიფიკატების გარეშე მომუშავე კლიენტებს; ძველ სერვერებს აღმოჩენის გარეშე, გათიშულ ინსტანციებს და აღმოჩენის შეცდომებს კვლავ სჭირდებათ ავთენტიკაცია.

ხელმოუწერილი გაშვებები არის ტელემეტრია, არა სანდო flakiness-ის, კარანტინის, დაფარვის ან შერჩევითი შესრულების მტკიცებულება. Shard-ის დაგეგმვა, ბილდის არქივები და დაფარვის/არტეფაქტის endpoint-ები კვლავ მოითხოვენ სერთიფიკატებს. დააყენეთ `TUIST_ACTOR_ID=""` დამოუკიდებლად, რათა გამოტოვოთ კონფიგურირებული აქტორის მითითება; დადასტურებული სერთიფიკატის იდენტურობა უცვლელი რჩება.

## რა ფიქსირდება {#what-is-tracked}

ყოველი ბილდისთვის პაკეტი აგროვებს:
- მის ხანგრძლივობას, წარმატებით დასრულდა თუ არა და Elixir-ის, Erlang/OTP-ის და Mix-ის გარემოს, რომელშიც გაშვებული იყო
- ყოველ გაფრთხილებას და შეცდომას, მისი ფაილით და ხაზით
- რამდენი დრო დასჭირდა ყოველი ფაილის კომპილაციას და რომელ მოდულებს განსაზღვრავს ის
- ფაილებს, რომლებზეც ყოველი ფაილია დამოკიდებული და სჭირდება თუ არა ისინი კომპილაციის დროს თუ მხოლოდ შესრულების დროს
- რას აკეთებდა ბილდი ფაილების კომპილაციის გარდა, მაგალითად ტიპების შემოწმებას, დისკზე ჩაწერას და სხვა Mix კომპილატორებს
- მანქანის პროცესორის, მეხსიერების, ქსელის და დისკის გამოყენებას ბილდის დროს
- ბრენჩს და კომიტს, ხოლო უწყვეტი ინტეგრაციისას – პროვაიდერს და გაშვებას

## იპოვეთ, რა ანელებს ბილდს {#find-what-slows-a-build-down}

გახსენით ბილდი დაფის **ბილდები → ბილდის გაშვებები** მენიუდან. ბილდები, მათი დიაგნოსტიკის რაოდენობა და მათი დამოკიდებულების ქეშის შეჯამებები ასევე ხელმისაწვდომია `tuist build mix list`-ის და `tuist build mix show`-ის, `GET /api/projects/{account_handle}/{project_handle}/mix/builds`-ის და `list_mix_builds` და `get_mix_build` <.localized_link href="/guides/features/agentic-coding/mcp">MCP ინსტრუმენტების</.localized_link> საშუალებით.

**მიმოხილვის** ჩანართი ჩამოთვლის ფაილებს, რომლებიც ბილდმა დააკომპილირა. შეგიძლიათ დააჯგუფოთ ისინი მოდულის მიხედვით, მოძებნოთ ისინი და დაალაგოთ:
- **კომპილაციის ხანგრძლივობით**, რათა იპოვოთ ფაილები, რომლებიც თავისთავად ნელია.
- **კომპილაციის დროის დამოკიდებულებებით**, ფაილების რაოდენობით, რომლებიც ვერ დაკომპილირდებიან, სანამ ეს ერთი არ დასრულდება. ნელი ფაილი ბევრი დამოკიდებულებით აფერხებს ბილდის დანარჩენ ნაწილს და მისი ცვლილება ყველა მათგანს გადააკომპილირებს.
- **კომპილაციის დროის დამოკიდებულებებით**, ფაილების რაოდენობით, რომლებსაც ეს ერთი ელოდება.

![Phoenix აპლიკაციის Mix ბილდის მიმოხილვა](/images/guides/features/elixir/build.png)

**დროის ხაზის** ჩანართი აჩვენებს იმავე ბილდს დროში: რომელი ფაილები დაკომპილირდა პარალელურად, სად შეამოწმა ბილდმა ტიპები და ჩაწერა დისკზე და როგორი იყო მანქანის მდგომარეობა ყოველ მომენტში. მონაკვეთი ერთი ზოლით არის მონაკვეთი, სადაც ბილდს არ შეეძლო ხელმისაწვდომი ბირთვების გამოყენება.

![Phoenix აპლიკაციის სრული Mix ბილდის დროის ხაზი](/images/guides/features/elixir/build-timeline.png)

**გაფრთხილებების** და **შეცდომების** ჩანართები ჩამოთვლიან ბილდის დიაგნოსტიკას.

## მორგებული მეტამონაცემები {#custom-metadata}

მიამაგრეთ ტეგები და key-value მონაცემები Mix ბილდებს, რათა განასხვავოთ გაშვებები სხვადასხვა გუნდების, აპარატურის ან სამუშაო პროცესების მიხედვით. ორივე ჩანს ყოველი ბილდის დეტალურ გვერდზე.

დააყენეთ მეტამონაცემები გარემოს ცვლადებით:

```sh
export TUIST_TAGS="nightly,release"
export TUIST_VALUES="ticket=TUIST-123,runner=linux-arm64"
```

ასევე შეგიძლიათ დააკონფიგურიროთ მეტამონაცემები `mix.exs`-ში:

```elixir
tuist: [
  project: "account/project",
  tags: ["nightly", "release"],
  values: %{"ticket" => "TUIST-123", "runner" => "linux-arm64"}
]
```

ტეგები ორივე წყაროდან ერთიანდება. როდესაც ერთი და იგივე გასაღები კონფიგურირებულია ორივე ადგილას, უპირატესობა ენიჭება გარემოს ცვლადში მითითებულ მნიშვნელობას.

ტეგები უნდა შეიცავდეს მხოლოდ ასოებს, რიცხვებს, დეფისებს და ქვედა ტირეებს. ბილდს შეიძლება ჰქონდეს 50-მდე ტეგი და თითოეული ტეგი შეიძლება შეიცავდეს 50 სიმბოლომდე. ბილდს შეიძლება ჰქონდეს 20-მდე key-value ჩანაწერი, თითოეული გასაღები შეიძლება შეიცავდეს 50 სიმბოლომდე და თითოეული მნიშვნელობა შეიძლება შეიცავდეს 500 სიმბოლომდე. ეს იგივე სერვერის მხარის ლიმიტებია, რომლებიც გამოიყენება Xcode ბილდის მეტამონაცემებისთვის. პაკეტი ტოვებს არასწორ ტეგებს და ზედმეტად დიდ ან ცარიელ მეტამონაცემთა ჩანაწერებს ანგარიშის გაგზავნამდე, ამიტომ არასწორმა კონფიგურაციამ ვერ შეუშლის ხელი ბილდის ინსაიტების ანგარიშის დანარჩენი ნაწილის შენახვას. გამოიყენეთ key-value მეტამონაცემები იმ მნიშვნელობებისთვის, რომლებიც არ აკმაყოფილებენ ტეგის შეზღუდვას.

მორგებული მეტამონაცემები მიმაგრებულია ბილდებს და არა ტესტების გაშვებებს.

მორგებული მეტამონაცემები ჩანს პროექტის წევრებისთვის დაფაზე. არ გამოიყენოთ ის სერთიფიკატების, წვდომის ტოკენების ან სხვა საიდუმლო მონაცემებისთვის. Tuist ინახავს Mix ბილდის მონაცემებს, მათ შორის ამ მეტამონაცემებს, 90 დღის განმავლობაში. დეტალებისთვის იხილეთ <.localized_link href="/guides/server/data-retention">მონაცემთა შენახვის პოლიტიკა</.localized_link>.

## პრობლემების გადაჭრა {#troubleshooting}

ანგარიშგება არასდროს ცვლის თქვენი ბილდის შედეგს: თუ ანგარიშის გაგზავნა ვერ ხერხდება, ბილდი სრულდება ისე, როგორც უნდა მომხდარიყო და არაფერი ბეჭდებავს. იმის სანახავად, რატომ არ გაიგზავნა ანგარიში, დააყენეთ `TUIST_DEBUG=1`:

```bash
TUIST_DEBUG=1 mix compile --force
```
