# Gradle-ის ბილდის ანალიტიკა {#gradle-build-insights}

Tuist-ის Gradle პლაგინს შეუძლია ბილდის ანალიტიკა Tuist-ზე გაგზავნოს, რაც თასქების შესრულებისა და ბილდის წარმადობის ხილვადობას უზრუნველყოფს.

## ატვირთვის ქცევის კონფიგურაცია {#configure-upload-behavior}

ნაგულისხმევად:
- ლოკალური ბილდებისთვის ანალიტიკა ფონურად აიტვირთება.
- CI-ში გაშვებებისთვის ანალიტიკა წინა პლანზე აიტვირთება, რათა მოკლე სიცოცხლის მქონე აგენტებზე ტელემეტრიის დაკარგვა ავიცილოთ თავიდან.

ამ ქცევის კონტროლი შესაძლებელია `tuist` გაფართოებაში `uploadInBackground`-ის გამოყენებით:

```kotlin
tuist {
    uploadInBackground = false // always upload in the foreground
}
```

## კონფიგურაციის ცნობარი {#configuration-reference}

`tuist` გაფართოების ბლოკში `settings.gradle.kts`-ში ხელმისაწვდომია `uploadInBackground` პარამეტრი:

| პარამეტრი | ტიპი | ნაგულისხმევი | აღწერა |
| --- | --- | --- | --- |
| `uploadInBackground` | `Boolean?` | `null` (ლოკალურად — ფონურად, CI-ზე — წინა პლანზე) | ატვირთოს თუ არა ბილდის ანალიტიკა ფონურად ლოკალური ბილდებისთვის. |

ეს პარამეტრი არ მოქმედებს `buildCache` ბლოკში მითითებულ დისტანციური ქეშის პარამეტრებზე.

## მოქმედის იდენტიფიკაციის მოთხოვნა {#report-actor-claim}

ბილდისა და ტესტის ანგარიშების მოთხოვნები მოიცავს არასავალდებულო `x-tuist-actor-id` ჰედერს მხოლოდ მაშინ, როცა `TUIST_ACTOR_ID`-ს ორგანიზაციის დონის ნიშნულად ან `buildInsights.actorId`-ს თქვენს პარამეტრებში ცხადად მიუთითებთ. ნაგულისხმევად ნიშნული არ იგზავნება და პლაგინი ოპერაციული სისტემის მომხმარებლის სახელებს არ ავლენს. გარემოს გადაფარვას აქვს უპირატესობა. ნებისმიერი გადაფარვა ცარიელ სტრიქონად დააყენეთ, რათა გაგზავნილი იდენტიფიკატორი გამოტოვოთ; ეს არ შლის ინდივიდუალური კრედენციალებით დადგენილ იდენტობას. არასწორი გადაფარვები მოთხოვნას გამოტოვებენ, ნაცვლად უკან დაბრუნებისა. თუ მორგებული პროქსი უცნობ ჰედერებს უარყოფს, გამორთეთ `TUIST_ACTOR_ID=""`-ით.

```kotlin
tuist {
    buildInsights {
        actorId = providers.environmentVariable("CORPORATE_ACTOR_ID").getOrElse("")
    }
}
```

მოქმედის იდენტიფიკატორები არის 1–128 ბაიტიანი, არა-სპეისიანი, ბეჭდვადი ASCII სიმბოლოები. ისინი ჩანს ყველასთვის, ვისაც პროექტის ანგარიშების ნახვა შეუძლია, მათ შორის საჯარო მაყურებლებისთვის, როცა პროექტი საჯაროა, და ექსპორტირდება ანგარიშებთან ერთად. არ ჩართოთ საიდუმლოები ან პირადი ინფორმაცია, რომლის გამოქვეყნებაც არ გსურთ. დადასტურებულ ინდივიდუალურ კრედენციალს აქვს უპირატესობა დაშბორდზე; კლიენტების მიერ გაგზავნილი იდენტიფიკატორები სხვა შემთხვევებში ცხადად **დაუდასტურებელია**. ისინი არასდროს ანიჭებენ ნებართვებს ან ავტომატურად არ აკავშირებენ Tuist-ის მომხმარებელთან. ძველი სერვერები იგნორირებენ ატრიბუციის ჰედერს, ხოლო ახალი სერვერები აგრძელებენ ძველი კლიენტების მიღებას მის გარეშე. ახალი საერთო-ტოკენის ანგარიშები იდენტიფიკატორის გარეშე აჩვენებენ **უცნობია**-ს, გამომქვეყნებელი ორგანიზაციის ნაცვლად; ისტორიული ანგარიშები ინარჩუნებენ წინა ატრიბუციას. ბილდებისა და ტესტების სიები გამოყოფენ დადასტურებული მომხმარებლის ფილტრებს დაუდასტურებელი გაგზავნილი იდენტიფიკატორის ფილტრებისგან.

## ქსელის სანდოობით გამოქვეყნება {#network-trusted-publishing}

თვითმასპინძლებული განლაგებები შეუძლიათ ცხადად დაუშვან Gradle-ის ბილდისა და ტესტის ანგარიშები მათი სანდო ქსელიდან დეველოპერის კრედენციალების გარეშე. ოპერატორმა ჯერ უნდა დააკონფიგურიროს `TUIST_NETWORK_TRUSTED_INSIGHTS_ACCESS=true` ინსტანციაზე და გადატვირთოს ის. ეს ვრცელდება ყველა მხარდაჭერილ პროექტზე; დაშბორდზე პარამეტრი არ არსებობს. იხილეთ <.localized_link href="/guides/server/self-host/server#network-trusted-access">თვითმასპინძლობის სახელმძღვანელო</.localized_link>.

რეპოზიტორიაში ერთხელ დააკონფიგურეთ დანიშნულება:

```kotlin
tuist {
    project = "organization/project"
    url = "https://tuist.internal.example"
    buildCache { enabled = false }
}
```

ბილდისა და ტესტის ანგარიშგება არ საჭიროებს ავთენტიკაციით ქეშის ენდპოინტის აღმოჩენას. გამორთეთ ქეში, თუ ინსტანცია ცალკე არ ააქტიურებს ქსელის სანდოობით ქეშზე წვდომას ან დეველოპერები ტოკენებს არ ამზადებენ. ხელმოუწერი ტესტის ანგარიშები გამოტოვებენ shard-ისა და არსებული ბილდის მითითებებს და არ ამუშავებენ კარანტინის ან ფლაკინესის ავტომატიზაციებს. კარანტინის ძიება გამოტოვებულია, როცა კრედენციალები ნამდვილად არ არსებობს; ვალიდური კრედენციალებით არსებული ავთენტიკაციის ქცევა ინარჩუნდება. თუ კრედენციალები არსებობს, ისინი მაინც გამოიყენება და არასწორი კრედენციალები ვერ ასრულებენ ოპერაციას, ნაცვლად კრედენციალების გარეშე გამოქვეყნებაზე გადასვლისა. როცა კრედენციალები არ არსებობს, პლაგინი ავტომატურად ადგენს, ნებას რთავს თუ არა თვითმასპინძლებული სერვერი კრედენციალების გარეშე ანგარიშგებას. არ არის საჭირო არც კლიენტის ფლაგი და არც `buildInsights` პარამეტრი. კრედენციალების გარეშე კლიენტების განახლებამდე ყველა სერვერის რეპლიკა განაახლეთ აღმოჩენის შესაძლებლობის მქონე ვერსიამდე. ძველი სერვერები აღმოჩენის გარეშე, გამორთული ინსტანციები და აღმოჩენის შეცდომები კვლავ მოითხოვენ ავთენტიკაციას; ავთენტიკაციით გამოქვეყნება რჩება თავსებადი. ცხადად ცარიელი `TUIST_TOKEN` იწვევს შეცდომას, ნაცვლად კრედენციალების გარეშე გამოქვეყნების ჩართვისა. ფორკის ან Dependabot-ის ჯობებისთვის საიდუმლოების გარეშე, წაშალეთ ეს ცვლადი, ნაცვლად მისი ცარიელ სტრიქონად განსაზღვრისა.

სერვერი ანიჭებს კრედენციალების გარეშე ანგარიშის ID-ებს. გაგზავნის გამეორებამ შეიძლება მეორე ანგარიში შექმნას; ეს რეჟიმი არ იძლევა იდემპოტენტური განმეორებების ან ავთენტიკაციით ტესტის ანგარიშებთან კორელაციის გარანტიას. ასეთ ანგარიშებს არ შეუძლიათ VCS კომენტარების ან ავტომატური შეცდომის-აგენტის მოვლენების გამოწვევა. ქსელზე წვდომა არის გამოქვეყნების ნდობის საზღვარი, არა გაგზავნილი მოქმედის იდენტობის დადასტურება.

## მორგებული მეტამონაცემები {#custom-metadata}

Gradle-ის ბილდებს მიუმაგრეთ ტეგები და გასაღები-მნიშვნელობის მონაცემები, რათა შეადაროთ სხვადასხვა გუნდების, აპარატურის ან სამუშაო პროცესების გაშვებები. ტეგები ხელმისაწვდომია დაშბორდის ფილტრებში, ხოლო მნიშვნელობები ჩანს თითოეული ბილდის დეტალურ გვერდზე, აპლიკაციის პროგრამირების ინტერფეისში და Model Context Protocol-ის ინსტრუმენტებში.

მეტამონაცემები დააყენეთ გარემოს ცვლადებით:

```sh
export TUIST_BUILD_TAGS="nightly,android"
export TUIST_BUILD_VALUE_TICKET="TUIST-123"
export TUIST_BUILD_VALUE_RUNNER="macos-14"
```

მეტამონაცემების კონფიგურაცია ასევე შესაძლებელია `settings.gradle.kts`-ში:

```kotlin
tuist {
    buildInsights {
        tag("nightly")
        tag("android")
        value("ticket", "TUIST-123")
        value("runner", "macos-14")
    }
}
```

როცა ერთი და იგივე მნიშვნელობა ორივე ადგილას არის კონფიგურირებული, უპირატესობა ენიჭება `settings.gradle.kts`-ში მითითებულ მნიშვნელობას.

ტეგები შეიძლება შეიცავდნენ მხოლოდ ასოებს, რიცხვებს, დეფისებსა და ქვედა ხაზებს. ბილდს შეიძლება ჰქონდეს მაქსიმუმ 50 ტეგი და თითოეულ ტეგს შეიძლება ჰქონდეს მაქსიმუმ 50 სიმბოლო. ბილდს შეიძლება ჰქონდეს მაქსიმუმ 20 გასაღები-მნიშვნელობის ჩანაწერი, თითოეულ გასაღებს შეიძლება ჰქონდეს მაქსიმუმ 50 სიმბოლო, ხოლო თითოეულ მნიშვნელობას — მაქსიმუმ 500 სიმბოლო. ეს იგივე სერვერის მხარის ლიმიტებია, რომლებიც Xcode-ის ბილდის მეტამონაცემებისთვის გამოიყენება. პლაგინი ანგარიშის გაგზავნამდე გამოტოვებს არასწორ ტეგებსა და ზედმეტად დიდ ან ცარიელ მეტამონაცემების ჩანაწერებს, ამიტომ არასწორმა კონფიგურაციამ ვერ შეუშლის ხელი ბილდის ანალიტიკის ანგარიშის დანარჩენი ნაწილის შენახვას. გამოიყენეთ გასაღები-მნიშვნელობის მეტამონაცემები იმ მნიშვნელობებისთვის, რომლებიც არ აკმაყოფილებენ ტეგის შეზღუდვას.

მორგებული მეტამონაცემები ჩანს პროექტის წევრებისთვის დაშბორდზე, აპლიკაციის პროგრამირების ინტერფეისისა და Model Context Protocol-ის ინსტრუმენტების მეშვეობით. არ გამოიყენოთ ის კრედენციალების, წვდომის ტოკენების ან სხვა მგრძნობიარე მონაცემებისთვის. Tuist ინარჩუნებს Gradle-ის ბილდის მონაცემებს, მათ შორის ამ მეტამონაცემებს, 90 დღის განმავლობაში. დეტალებისთვის იხილეთ <.localized_link href="/guides/server/data-retention">მონაცემთა შენახვის პოლიტიკა</.localized_link>.
