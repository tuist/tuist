# Gradle ბილდის ანალიტიკა {#gradle-build-insights}

Tuist-ის Gradle პლაგინს შეუძლია ბილდის ანალიტიკა გაუგზავნოს Tuist-ს, რაც საშუალებას გაძლევთ დაინახოთ ამოცანების შესრულება და ბილდის წარმადობა.

## ატვირთვის ქცევის კონფიგურაცია {#configure-upload-behavior}

ნაგულისხმევად:
- ლოკალური ბილდებისთვის ანალიტიკა ფონურად იტვირთება.
- CI გაშვებებისთვის ანალიტიკა წინა პლანზე იტვირთება, რათა მოკლე სიცოცხლის მქონე აგენტებზე ტელემეტრიის დაკარგვა თავიდან აიცილოთ.

ამ ქცევის კონტროლი შესაძლებელია `tuist` გაფართოებაში `uploadInBackground`-ის გამოყენებით:

```kotlin
tuist {
    uploadInBackground = false // always upload in the foreground
}
```

## კონფიგურაციის ცნობარი {#configuration-reference}

`uploadInBackground` ოფცია ხელმისაწვდომია `settings.gradle.kts`-ში მდებარე `tuist` გაფართოების ბლოკში:

| ოფცია | ტიპი | ნაგულისხმევი | აღწერა |
| --- | --- | --- | --- |
| `uploadInBackground` | `Boolean?` | `null` (ლოკალურად — ფონურად, CI-ზე — წინა პლანზე) | იტვირთება თუ არა ბილდის ანალიტიკა ფონურად ლოკალური ბილდებისთვის. |

ეს პარამეტრი არ მოქმედებს დისტანციური ქეშის პარამეტრებზე `buildCache` ბლოკში.

## მოქმედის იდენტიფიკაციის განცხადება {#report-actor-claim}

ბილდისა და ტესტის ანგარიშების მოთხოვნები მოიცავს არასავალდებულო `x-tuist-actor-id` ჰედერს მხოლოდ მაშინ, როდესაც `TUIST_ACTOR_ID`-ს ცალსახად მიანიჭებთ ორგანიზაციის დონის ნიშანულს ან კონფიგურაციით დააყენებთ `buildInsights.actorId`-ს თქვენს პარამეტრებში. ნიშანული ნაგულისხმევად არ იგზავნება და პლაგინი არ ავლენს ოპერაციული სისტემის მომხმარებლის სახელებს. გარემოს გადაფარვა უპირატესობას იღებს. რომელიმე გადაფარვის ცარიელ სტრიქონად დაყენებით გამოტოვებთ მოხსენებულ იდენტიფიკატორს; ეს არ შლის ინდივიდუალური სერთიფიკატებით დამყარებულ იდენტურობას. არასწორი გადაფარვები გამოტოვებენ განცხადებას ნაცვლად უკან დაბრუნებისა. თუ მორგებული პროქსი უცნობ ჰედერებს უარყოფს, გამორთეთ ის `TUIST_ACTOR_ID=""`-ით.

```kotlin
tuist {
    buildInsights {
        actorId = providers.environmentVariable("CORPORATE_ACTOR_ID").getOrElse("")
    }
}
```

მოქმედის იდენტიფიკატორები არის 1–128 ბაიტიანი, სივრცის გარდა ბეჭდვადი ASCII სიმბოლოები. ისინი ხილულია ყველასთვის, ვისაც შეუძლია პროექტის ანგარიშების ნახვა, მათ შორის საჯარო მაყურებლებისთვის, როცა პროექტი საჯაროა, და ექსპორტირდება ანგარიშებთან ერთად. არ ჩართოთ საიდუმლოებები ან პირადი ინფორმაცია, რომლის გამოქვეყნებაც არ გსურთ. დადასტურებული ინდივიდუალური სერთიფიკატი იღებს უპირატესობას დაფაზე; კლიენტების მიერ გაგზავნილი იდენტიფიკატორები წინააღმდეგ შემთხვევაში ცალსახად **დაუდასტურებელი**ა. ისინი არასდროს ანიჭებენ ნებართვებს ან ავტომატურად არ უკავშირდებიან Tuist-ის მომხმარებელს. ძველი სერვერები იგნორირებენ ატრიბუციის ჰედერს, ხოლო ახალი სერვერები აგრძელებენ ძველი კლიენტების მიღებას მის გარეშე. ახალი საერთო-ტოკენის ანგარიშები იდენტიფიკატორის გარეშე აჩვენებენ **უცნობი**-ს, გამომქვეყნებელი ორგანიზაციის ნაცვლად; ისტორიული ანგარიშები ინარჩუნებენ წინა ატრიბუციას. ბილდებისა და ტესტების სიებში დადასტურებული მომხმარებლის ფილტრები გამოყოფილია დაუდასტურებელი მოხსენებული იდენტიფიკატორის ფილტრებისგან.

## ქსელის ნდობით გამოქვეყნება {#network-trusted-publishing}

თვითმასპინძელ განლაგებებს შეუძლიათ ცალსახად დაუშვან Gradle ბილდისა და ტესტის ანგარიშები მათი ნდობით ქსელიდან დეველოპერის სერთიფიკატების გარეშე. ოპერატორმა ჯერ უნდა დააყენოს `TUIST_NETWORK_TRUSTED_INSIGHTS_ACCESS=true` ინსტანსზე და გადატვირთოს ის. ეს ვრცელდება ყველა მხარდაჭერილ პროექტზე; დაფაზე შესაბამისი პარამეტრი არ არსებობს. იხილეთ <.localized_link href="/guides/server/self-host/server#network-trusted-access">თვითმასპინძლობის სახელმძღვანელო</.localized_link>.

დანიშნულების ადგილი რეპოზიტორიაში ერთხელ დააკონფიგურირეთ:

```kotlin
tuist {
    project = "organization/project"
    url = "https://tuist.internal.example"
    buildCache { enabled = false }
}
```

ბილდისა და ტესტის ანგარიშგება არ საჭიროებს ავთენტიკირებულ ქეშის ბოლოწერტილის აღმოჩენას. გამორთეთ ქეში, თუ ინსტანსი ცალკე არ ააქტიურებს ქსელის ნდობით ქეშზე წვდომას ან დეველოპერები არ ამზადებენ ტოკენებს. ხელმოუწერი ტესტის ანგარიშები გამოტოვებენ shard-ისა და არსებული ბილდის მითითებებს და არ ამუშავებენ კარანტინის ან არამდგრადობის ავტომატიზაციებს. კარანტინის ძიება გამოტოვებულია, როცა სერთიფიკატები ნამდვილად არ არსებობს; მოქმედი სერთიფიკატებით არსებული ავთენტიკირებული ქცევა ნარჩუნდება. თუ სერთიფიკატები არსებობს, ისინი კვლავ გამოიყენება და არასწორი სერთიფიკატები ასრულებენ შეცდომით, ნაცვლად სერთიფიკატების გარეშე გამოქვეყნებაზე გადასვლისა. როცა სერთიფიკატები არ არსებობს, პლაგინი ავტომატურად ადგენს, ნებართვას აძლევს თუ არა თვითმასპინძელი სერვერი სერთიფიკატების გარეშე ანგარიშგებას. არ არის საჭირო არც კლიენტის ფლაგი და არც `buildInsights` პარამეტრი. სანამ განაახლებთ სერთიფიკატების გარეშე მომუშავე კლიენტებს, განაახლეთ სერვერის ყველა რეპლიკა აღმოჩენის შესაძლებლობის მქონე ვერსიამდე. ძველ სერვერებს აღმოჩენის გარეშე, გამორთულ ინსტანსებსა და აღმოჩენის შეცდომებს კვლავ სჭირდებათ ავთენტიკაცია; ავთენტიკირებული გამოქვეყნება თავსებადი რჩება. ცალსახად ცარიელი `TUIST_TOKEN` იწვევს შეცდომას, ნაცვლად სერთიფიკატების გარეშე გამოქვეყნების ჩართვისა. ფორკის ან Dependabot სამუშაოებისთვის საიდუმლოებების გარეშე, წაშალეთ ეს ცვლადი, ნაცვლად მისი ცარიელ სტრიქონად განსაზღვრისა.

სერვერი ანიჭებს სერთიფიკატების გარეშე ანგარიშის ID-ებს. გაგზავნის გამეორებამ შეიძლება შექმნას მეორე ანგარიში; ეს რეჟიმი არ იძლევა იდემპოტენტური გამეორებების ან ავთენტიკირებულ ტესტის ანგარიშებთან კორელაციის გარანტიას. ასეთ ანგარიშებს არ შეუძლიათ VCS კომენტარების ან ავტომატური შეცდომის-აგენტის მოვლენების გამოწვევა. ქსელზე წვდომა არის გამოქვეყნების ნდობის საზღვარი და არა მოხსენებული მოქმედის იდენტურობის დადასტურება.

## მორგებული მეტამონაცემები {#custom-metadata}

Gradle ბილდებს მიამაგრეთ ტეგები და გასაღები-მნიშვნელობის მონაცემები, რათა შეადაროთ გაშვებები სხვადასხვა გუნდების, აპარატურის ან სამუშაო ნაკადების მიხედვით. ტეგები ხელმისაწვდომია დაფის ფილტრებად, ხოლო მნიშვნელობები ჩანს თითოეული ბილდის დეტალურ გვერდზე, ასევე აპლიკაციის პროგრამირების ინტერფეისში და Model Context Protocol ინსტრუმენტებში.

მეტამონაცემები დააყენეთ გარემოს ცვლადებით:

```sh
export TUIST_BUILD_TAGS="nightly,android"
export TUIST_BUILD_VALUE_TICKET="TUIST-123"
export TUIST_BUILD_VALUE_RUNNER="macos-14"
```

მეტამონაცემების კონფიგურირება ასევე შესაძლებელია `settings.gradle.kts`-ში:

```kotlin
tuist {
    buildInsights {
        tag("nightly")
        tag("android")
        value("ticket", "TUIST-123")
        value("runner", "macos-14")
    }
}
```

როცა ერთი და იგივე მნიშვნელობა კონფიგურირებულია ორივე ადგილას, უპირატესობას იღებს `settings.gradle.kts`-ში მითითებული მნიშვნელობა.

ტეგები უნდა შეიცავდნენ მხოლოდ ასოებს, ციფრებს, დეფისებს და ქვედა ტირეებს. ბილდს შეიძლება ჰქონდეს მაქსიმუმ 50 ტეგი და თითოეული ტეგი შეიძლება შეიცავდეს მაქსიმუმ 50 სიმბოლოს. ბილდს შეიძლება ჰქონდეს მაქსიმუმ 20 გასაღები-მნიშვნელობის ჩანაწერი, თითოეული გასაღები შეიძლება შეიცავდეს მაქსიმუმ 50 სიმბოლოს, ხოლო თითოეული მნიშვნელობა — მაქსიმუმ 500 სიმბოლოს. ეს იგივე სერვერის მხარის ლიმიტებია, რომლებიც გამოიყენება Xcode ბილდის მეტამონაცემებისთვის. პლაგინი გამოტოვებს არასწორ ტეგებსა და ზედმეტად დიდ ან ცარიელ მეტამონაცემთა ჩანაწერებს ანგარიშის გაგზავნამდე, ამიტომ არასწორმა კონფიგურაციამ ვერ შეუშლის ხელი ბილდის ანალიტიკის ანგარიშის დანარჩენი ნაწილის შენახვას. გამოიყენეთ გასაღები-მნიშვნელობის მეტამონაცემები იმ მნიშვნელობებისთვის, რომლებიც არ აკმაყოფილებენ ტეგის შეზღუდვას.

მორგებული მეტამონაცემები ხილულია პროექტის წევრებისთვის დაფაზე, ასევე აპლიკაციის პროგრამირების ინტერფეისისა და Model Context Protocol ინსტრუმენტების მეშვეობით. არ გამოიყენოთ ის სერთიფიკატების, წვდომის ტოკენების ან სხვა მგრძნობიარე მონაცემებისთვის. Tuist ინარჩუნებს Gradle ბილდის მონაცემებს, მათ შორის ამ მეტამონაცემებს, 90 დღის განმავლობაში. დეტალებისთვის იხილეთ <.localized_link href="/guides/server/data-retention">მონაცემთა შენახვის პოლიტიკა</.localized_link>.

## შეცდომის დეტალები {#failure-details}

როდესაც ბილდი ვერ ხერხდება, პლაგინი იუწყება, რატომ ჩავარდა თითოეული შეცდომის მქონე ამოცანა ან კონფიგურაციის ნაბიჯი: გამონაკლისის შეტყობინებას და მიზეზთა ჯაჭვს ისე, როგორც Gradle-ის კონსოლი ბეჭდავს მათ, მაგალითად, ვერჩაშლილი `compileJava` ამოცანის კომპილატორის შეცდომებს ან შეცდომას ბილდის სკრიპტში. სტეკის ტრეისები და ამოცანის გამოტანა არ გროვდება. პლაგინი პროექტის შიგნით არსებულ გზებს ადარებს ფარდობითს ანგარიშის გაგზავნამდე, ხოლო Tuist ფარავს სერთიფიკატებს და სხვა ცნობილ ადგილობრივ გზებს. თითოეული შეტყობინება შემოიფარგლება 16 KiB-ით, ხოლო ბილდი ინახავს მაქსიმუმ 32 ვერჩაშლილი ნაბიჯის შეტყობინებებს.

ვერჩაშლის შეტყობინებები ხილულია პროექტის წევრებისთვის აპლიკაციის პროგრამირების ინტერფეისის, Model Context Protocol ინსტრუმენტების (`get_gradle_build`, `list_gradle_build_tasks` და `get_gradle_build_step`) და CLI-ის მეშვეობით:

```bash
tuist build gradle failure list <build-id>
```

შეტყობინებებმა შეიძლება შეიცავდნენ წყაროს ფრაგმენტებს და პროექტის დეტალებს. ანგარიშები, რომლებიც გამოქვეყნებულია სერთიფიკატების გარეშე [ქსელის სანდოობაზე დაფუძნებული გამოქვეყნების](#network-trusted-publishing) გზით, არ შეიცავენ მათ. Tuist ინარჩუნებს მათ Gradle ბილდის დანარჩენ მონაცემებთან ერთად 90 დღის განმავლობაში.
