# Gradle-ის ბილდის ინსაიტები {#gradle-build-insights}

Tuist-ის Gradle პლაგინს შეუძლია ბილდის ანალიტიკა გაგზავნოს Tuist-ში, რაც საშუალებას გაძლევთ დაინახოთ ამოცანების შესრულება და ბილდის წარმადობა.

## ატვირთვის ქცევის კონფიგურაცია {#configure-upload-behavior}

ნაგულისხმევად:
- ლოკალური ბილდებისთვის ბილდის ანალიტიკა ფონურად აიტვირთება.
- CI-ს გაშვებებისთვის ბილდის ანალიტიკა წინა პლანზე აიტვირთება, რათა თავიდან აიცილოთ ტელემეტრიის დაკარგვა მოკლე სიცოცხლის მქონე აგენტებზე.

ამ ქცევის კონტროლი შეგიძლიათ `tuist` გაფართოებაში `uploadInBackground`-ის გამოყენებით:

```kotlin
tuist {
    uploadInBackground = false // always upload in the foreground
}
```

## კონფიგურაციის ცნობარი {#configuration-reference}

`uploadInBackground` პარამეტრი ხელმისაწვდომია `settings.gradle.kts`-ში `tuist` გაფართოების ბლოკში:

| პარამეტრი | ტიპი | ნაგულისხმევი | აღწერა |
| --- | --- | --- | --- |
| `uploadInBackground` | `Boolean?` | `null` (ლოკალურად ფონურად, CI-ზე წინა პლანზე) | ატვირთოს თუ არა ბილდის ინსაიტები ფონურად ლოკალური ბილდებისთვის. |

ეს პარამეტრი არ მოქმედებს დისტანციური ქეშის პარამეტრებზე `buildCache` ბლოკში.

## მოქმედის იდენტიფიკაციის მოთხოვნა {#report-actor-claim}

ბილდისა და ტესტის ანგარიშების მოთხოვნები მოიცავს არასავალდებულო `x-tuist-actor-id` ჰედერს მხოლოდ მაშინ, როცა ცალსახად მიანიჭებთ `TUIST_ACTOR_ID`-ს ორგანიზაციის მასშტაბის იარლიყს ან აკონფიგურირებთ `buildInsights.actorId`-ს თქვენს პარამეტრებში. ნაგულისხმევად იარლიყი არ იგზავნება და პლაგინი არ აღმოაჩენს ოპერაციული სისტემის მომხმარებლის სახელებს. გარემოს გადაფარვა აქვს უპირატესობა. დააყენეთ რომელიმე გადაფარვა ცარიელ სტრიქონად, რათა გამოტოვოთ მოხსენებული იდენტიფიკატორი; ეს არ შლის ინდივიდუალური მონაცემებით დამყარებულ იდენტურობას. არასწორი გადაფარვები გამოტოვებენ მოთხოვნას ნაცვლად უკან დაბრუნების. თუ მორგებული პროქსი უარყოფს უცნობ ჰედერებს, გამორთეთ ის `TUIST_ACTOR_ID=""`-ით.

```kotlin
tuist {
    buildInsights {
        actorId = providers.environmentVariable("CORPORATE_ACTOR_ID").getOrElse("")
    }
}
```

მოქმედის იდენტიფიკატორები არის 1–128 ბაიტიანი არა-სpace ბეჭდავადი ASCII. ისინი ხილულია ნებისმიერი პირისთვის, ვისაც შეუძლია ნახოს პროექტის ანგარიშები, მათ შორის საჯარო მაყურებლებისთვის, როცა პროექტი საჯაროა, და ექსპორტირდება ანგარიშებთან ერთად. არ ჩართოთ საიდუმლოები ან პირადი ინფორმაცია, რომლის გამოქვეყნებაც არ გსურთ. დადასტურებულ ინდივიდუალურ მონაცემებს აქვს უპირატესობა დაშბორდზე; კლიენტების მიერ გაგზავნილი იდენტიფიკატორები სხვა შემთხვევაში ცალსახად **დაუდასტურებელი**ა. ისინი არასდროს ანიჭებენ ნებართვებს ან ავტომატურად არ აკავშირებენ Tuist-ის მომხმარებელთან. ძველი სერვერები იგნორირებენ მიკუთვნების ჰედერს, ხოლო ახალი სერვერები აგრძელებენ ძველი კლიენტების მიღებას მის გარეშე. ახალი გაზიარებული-ტოკენის ანგარიშები იდენტიფიკატორის გარეშე აჩვენებენ **უცნობი**-ს, გამომქვეყნებელი ორგანიზაციის ნაცვლად; ისტორიული ანგარიშები ინარჩუნებენ წინა მიკუთვნებას. ბილდისა და ტესტის სიები გამოყოფენ დადასტურებული მომხმარებლის ფილტრებს დაუდასტურებელი მოხსენებული იდენტიფიკატორის ფილტრებისგან.

## ქსელის ნდობით გამოქვეყნება {#network-trusted-publishing}

თვითმასპინძელი განლაგებები შეუძლიათ ცალსახად დაუშვან Gradle-ის ბილდისა და ტესტის ანგარიშები მათი სანდო ქსელიდან დეველოპერის მონაცემების გარეშე. ოპერატორმა ჯერ უნდა აკონფიგურიროს `TUIST_NETWORK_TRUSTED_INSIGHTS_ACCESS=true` ინსტანციაზე და გადატვირთოს ის. ეს ვრცელდება ყველა მხარდაჭერილ პროექტზე; დაშბორდის პარამეტრი არ არსებობს. იხილეთ <.localized_link href="/guides/server/self-host/server#network-trusted-access">თვითმასპინძლობის სახელმძღვანელო</.localized_link>.

აკონფიგურეთ დანიშნულება ერთხელ რეპოზიტორიაში:

```kotlin
tuist {
    project = "organization/project"
    url = "https://tuist.internal.example"
    buildCache { enabled = false }
}
```

ბილდისა და ტესტის ანგარიშგება არ საჭიროებს ავთენტიკირებულ ქეშის endpoint-ის აღმოჩენას. გამორთეთ ქეში, თუ ინსტანცია ცალკე არ ააქტიურებს ქსელის ნდობით ქეშზე წვდომას ან დეველოპერები არ ამზადებენ ტოკენებს. ხელმოუწერი ტესტის ანგარიშები გამოტოვებენ shard-ისა და არსებული ბილდის მითითებებს და არ ამუშავებენ კარანტინის ან flakiness-ის ავტომატიზაციებს. კარანტინის ძიება გამოიტოვება, როცა მონაცემები ნამდვილად არ არის; მოქმედი მონაცემებით არსებული ავთენტიკირებული ქცევა ნარჩუნდება. თუ მონაცემები არსებობს, ისინი მაინც გამოიყენება და არასწორი მონაცემები ასრულებენ შეცდომით, ნაცვლად მონაცემების გარეშე გამოქვეყნებაზე დაბრუნების. როცა მონაცემები არ არის, პლაგინი ავტომატურად აღმოაჩენს, ნებართვას თუ იძლევა თვითმასპინძელი სერვერი მონაცემების გარეშე ანგარიშგებაზე. არ არის საჭირო არც კლიენტის flag და არც `buildInsights` პარამეტრი. განაახლეთ ყველა სერვერის რეპლიკა აღმოჩენის მხარდაჭერის მქონე ვერსიამდე, სანამ განაახლებთ მონაცემების გარეშე კლიენტებს. უფრო ძველ სერვერებს აღმოჩენის გარეშე, გამორთულ ინსტანციებს და აღმოჩენის შეცდომებს კვლავ სჭირდებათ ავთენტიკაცია; ავთენტიკირებული გამოქვეყნება რჩება თავსებადი. ცალსახად ცარიელი `TUIST_TOKEN` იწვევს უსაფრთხო შეცდომას, ნაცვლად მონაცემების გარეშე გამოქვეყნების ჩართვის. fork ან Dependabot სამუშაოებისთვის საიდუმლოების გარეშე, წაშალეთ ეს ცვლადი, ნაცვლად მისი ცარიელ სტრიქონად განსაზღვრის.

სერვერი ანიჭებს მონაცემების გარეშე ანგარიშის ID-ებს. გაგზავნის განმეორებამ შეიძლება შექმნას მეორე ანგარიში; ეს რეჟიმი არ იძლევა idempotent განმეორებების ან ავთენტიკირებულ ტესტის ანგარიშებთან კორელაციის გარანტიას. ასეთ ანგარიშებს არ შეუძლიათ VCS კომენტარების ან ავტომატური failure-agent მოვლენების გამოწვევა. ქსელზე წვდომა არის გამოქვეყნების ნდობის საზღვარი, არა მოხსენებული მოქმედის იდენტურობის დამამტკიცებელი.

## მორგებული მეტამონაცემები {#custom-metadata}

მიამაგრეთ ტეგები და key-value მონაცემები Gradle ბილდებს, რათა შეადაროთ გაშვებები სხვადასხვა გუნდების, აპარატურის ან სამუშაო ნაკადებისგან. ტეგები ხელმისაწვდომია დაშბორდის ფილტრებში, ხოლო მნიშვნელობები ჩანს თითოეული ბილდის დეტალურ გვერდზე და application programming interface-სა და Model Context Protocol ინსტრუმენტებში.

დააყენეთ მეტამონაცემები გარემოს ცვლადებით:

```sh
export TUIST_BUILD_TAGS="nightly,android"
export TUIST_BUILD_VALUE_TICKET="TUIST-123"
export TUIST_BUILD_VALUE_RUNNER="macos-14"
```

ასევე შეგიძლიათ აკონფიგურიროთ მეტამონაცემები `settings.gradle.kts`-ში:

```kotlin
tuist {
    buildInsights {
        tag("nightly")
        tag("android")
        value("ticket", "TUIST-123")
        value("runner", "macos-14")
    }
}
```

როცა ერთი და იგივე მნიშვნელობა კონფიგურირებულია ორივე ადგილას, უპირატესობა აქვს `settings.gradle.kts`-ში მითითებულ მნიშვნელობას.

ტეგებმა უნდა შეიცავდნენ მხოლოდ ასოებს, რიცხვებს, დეფისებს და ქვედა ტირეებს. ბილდს შეიძლება ჰქონდეს 50-მდე ტეგი და თითოეულ ტეგს შეიძლება ჰქონდეს 50-მდე სიმბოლო. ბილდს შეიძლება ჰქონდეს 20-მდე key-value ჩანაწერი, თითოეულ გასაღებს შეიძლება ჰქონდეს 50-მდე სიმბოლო და თითოეულ მნიშვნელობას შეიძლება ჰქონდეს 500-მდე სიმბოლო. ეს იგივე სერვერის მხარის ლიმიტებია, რომლებიც გამოიყენება Xcode ბილდის მეტამონაცემებისთვის. პლაგინი გამოტოვებს არასწორ ტეგებს და ზომით აღმატებულ ან ცარიელ მეტამონაცემების ჩანაწერებს ანგარიშის გაგზავნამდე, ამიტომ არასწორმა კონფიგურაციამ ვერ შეუშლის ხელი ბილდის ინსაიტების ანგარიშის დანარჩენი ნაწილის შენახვას. გამოიყენეთ key-value მეტამონაცემები მნიშვნელობებისთვის, რომლებიც არ აკმაყოფილებენ ტეგის შეზღუდვას.

მორგებული მეტამონაცემები ხილულია პროექტის წევრებისთვის დაშბორდში და application programming interface-სა და Model Context Protocol ინსტრუმენტების მეშვეობით. არ გამოიყენოთ ის მონაცემების, access token-ების ან სხვა მგრძნობიარე მონაცემებისთვის. Tuist ინარჩუნებს Gradle ბილდის მონაცემებს, მათ შორის ამ მეტამონაცემებს, 90 დღის განმავლობაში. დეტალებისთვის იხილეთ <.localized_link href="/guides/server/data-retention">მონაცემთა შენახვის პოლიტიკა</.localized_link>.
