# Gradle-ის ბილდების ანალიტიკა {#gradle-build-insights}

Tuist-ის Gradle პლაგინს შეუძლია ბილდის ანალიტიკის Tuist-ზე გაგზავნა, რაც საშუალებას გაძლევთ დაინახოთ ამოცანების შესრულება და ბილდის წარმადობა.

## ატვირთვის ქცევის კონფიგურაცია {#configure-upload-behavior}

ნაგულისხმევად:
- ლოკალური ბილდებისთვის ბილდის ანალიტიკა ფონურად იტვირთება.
- CI-ს გაშვებებისთვის ბილდის ანალიტიკა წინა პლანზე იტვირთება, რათა თავიდან ავიცილოთ ტელემეტრიის დაკარგვა ხანმოკლე აგენტებზე.

ამ ქცევის კონტროლი შეგიძლიათ `uploadInBackground`-ის გამოყენებით `tuist` გაფართოებაში:

```kotlin
tuist {
    uploadInBackground = false // always upload in the foreground
}
```

## კონფიგურაციის ცნობარი {#configuration-reference}

`uploadInBackground` პარამეტრი ხელმისაწვდომია `tuist` გაფართოების ბლოკში `settings.gradle.kts`-ში:

| პარამეტრი | ტიპი | ნაგულისხმევი | აღწერა |
| --- | --- | --- | --- |
| `uploadInBackground` | `Boolean?` | `null` (ლოკალურად — ფონურად, CI-ზე — წინა პლანზე) | ატვირთოს თუ არა ბილდის ანალიტიკა ფონურად ლოკალური ბილდებისთვის. |

ეს პარამეტრი არ მოქმედებს დისტანციური ქეშის პარამეტრებზე `buildCache` ბლოკში.

## მოქმედის იდენტიფიკაციის განცხადება {#report-actor-claim}

ბილდისა და ტესტის ანგარიშების მოთხოვნები შეიცავს არასავალდებულო `x-tuist-actor-id` ჰედერს მხოლოდ მაშინ, როცა `TUIST_ACTOR_ID`-ს ცალსახად ანიჭებთ ორგანიზაციის დონის იარლიყს ან კონფიგურირებთ `buildInsights.actorId`-ს თქვენს პარამეტრებში. ნაგულისხმევად იარლიყი არ იგზავნება და პლაგინი არ აღმოაჩენს ოპერაციული სისტემის მომხმარებლის სახელებს. გარემოს გადაფარვა უპირატესია. გამოტოვეთ მოხსენებული იდენტიფიკატორი ერთ-ერთი გადაფარვის ცარიელ სტრიქონად დაყენებით; ეს არ შლის ინდივიდუალური მოწმობებით დამყარებულ იდენტობას. არასწორი გადაფარვები გამოტოვებენ განცხადებას ნაცვლად უკან დაბრუნებისა. თუ მორგებული პროქსი უარყოფს უცნობ ჰედერებს, გამოირიცხეთ `TUIST_ACTOR_ID=""`-ით.

```kotlin
tuist {
    buildInsights {
        actorId = providers.environmentVariable("CORPORATE_ACTOR_ID").getOrElse("")
    }
}
```

მოქმედის იდენტიფიკატორები არის 1–128 ბაიტიანი, გამოტოვებული ადგილების გარეშე, ბეჭდვადი ASCII. ისინი ჩანს ყველას, ვისაც შეუძლია პროექტის ანგარიშების ნახვა, მათ შორის საჯარო მაყურებლებს, როცა პროექტი საჯაროა, და ექსპორტირდება ანგარიშებთან ერთად. არ ჩაწეროთ საიდუმლოებები ან პირადი ინფორმაცია, რომლის გამოქვეყნებაც არ გსურთ. დადასტურებული ინდივიდუალური მოწმობა უპირატესია დაფაზე; კლიენტების მიერ გაგზავნილი იდენტიფიკატორები სხვა შემთხვევაში ცალსახად **დაუდასტურებელი**-ია. ისინი არასდროს ანიჭებენ უფლებებს ან ავტომატურად არ უკავშირდებიან Tuist-ის მომხმარებელს. ძველი სერვერები იგნორირებენ ატრიბუციის ჰედერს, ხოლო ახალი სერვერები აგრძელებენ ძველი კლიენტების მიღებას მის გარეშე. ახალი საერთო-ტოკენის ანგარიშები იდენტიფიკატორის გარეშე აჩვენებენ **უცნობი**-ს, გამომქვეყნებელი ორგანიზაციის ნაცვლად; ისტორიული ანგარიშები ინარჩუნებენ წინა ატრიბუციას. ბილდებისა და ტესტების სიები გამოყოფენ დადასტურებული მომხმარებლის ფილტრებს დაუდასტურებელი მოხსენებული იდენტიფიკატორის ფილტრებისგან.

## ქსელის ნდობით გამოქვეყნება {#network-trusted-publishing}

თვითგანთავსებულ განლაგებებს შეუძლიათ ცალსახად ნება დართონ Gradle-ის ბილდისა და ტესტის ანგარიშებზე მათი სანდო ქსელიდან დეველოპერის მოწმობების გარეშე. ოპერატორმა უნდა დააყენოს `TUIST_NETWORK_TRUSTED_INSIGHTS_ACCESS=true` ინსტანციაზე და ჯერ გადატვირთოს ის. ეს ვრცელდება ყველა მხარდაჭერილ პროექტზე; დაფაზე პარამეტრი არ არსებობს. იხილეთ <.localized_link href="/guides/server/self-host/server#network-trusted-access">თვითგანთავსების სახელმძღვანელო</.localized_link>.

დანიშნულების ადგილი ერთხელ დააკონფიგურირეთ რეპოზიტორიაში:

```kotlin
tuist {
    project = "organization/project"
    url = "https://tuist.internal.example"
    buildCache { enabled = false }
}
```

ბილდისა და ტესტის ანგარიშგება არ საჭიროებს ავთენტიფიცირებულ ქეშის endpoint-ის აღმოჩენას. გათიშეთ ქეში, თუ ინსტანცია ცალკე არ ააქტიურებს ქსელის ნდობით ქეშზე წვდომას ან დეველოპერები არ ამზადებენ ტოკენებს. ხელმოუწერი ტესტის ანგარიშები გამოტოვებენ shard-ისა და არსებული ბილდის მითითებებს და არ ამუშავებენ კარანტინის ან არამდგრადობის ავტომატიზაციებს. კარანტინის ძიება გამოტოვებულია, როცა მოწმობები ნამდვილად არ არის; მოქმედი მოწმობებით არსებული ავთენტიფიცირებული ქცევა ნარჩუნდება. თუ მოწმობები არსებობს, ისინი მაინც გამოიყენება და არასწორი მოწმობები ასრულებენ შეცდომით, ნაცვლად მოწმობისგან თავისუფალი გამოქვეყნებისა. როცა მოწმობები არ არის, პლაგინი ავტომატურად აღმოაჩენს, ნებას რთავს თუ არა თვითგანთავსებული სერვერი მოწმობისგან თავისუფალ ანგარიშგებას. კლიენტის ფლაგი ან `buildInsights` პარამეტრი არ არის საჭირო. განაახლეთ სერვერის ყველა რეპლიკა აღმოჩენის შესაძლებლობის მქონე ვერსიამდე, სანამ განაახლებთ მოწმობისგან თავისუფალ კლიენტებს. უფრო ძველი სერვერები აღმოჩენის გარეშე, გათიშული ინსტანციები და აღმოჩენის შეცდომები მაინც საჭიროებენ ავთენტიფიკაციას; ავთენტიფიცირებული გამოქვეყნება რჩება თავსებადი. ცალსახად ცარიელი `TUIST_TOKEN` იწვევს უსაფრთხო შეცდომას, ნაცვლად მოწმობისგან თავისუფალი გამოქვეყნების ჩართვისა. ფორკის ან Dependabot-ის სამუშაოებისთვის საიდუმლოების გარეშე, წაშალეთ ეს ცვლადი, ნაცვლად მისი ცარიელ სტრიქონად განსაზღვრისა.

სერვერი ანიჭებს მოწმობისგან თავისუფალ ანგარიშის ID-ებს. გაგზავნის გამეორებამ შეიძლება შექმნას მეორე ანგარიში; ეს რეჟიმი არ იძლევა იდემპოტენტური განმეორებების ან ავთენტიფიცირებულ ტესტის ანგარიშებთან კორელაციის გარანტიას. ასეთ ანგარიშებს არ შეუძლიათ VCS კომენტარების ან ავტომატური შეცდომის აგენტის მოვლენების გამოწვევა. ქსელზე წვდომა არის გამოქვეყნების ნდობის საზღვარი, არა მოხსენებული მოქმედის იდენტობის მტკიცებულება.

## მორგებული მეტამონაცემები {#custom-metadata}

მიამაგრეთ ტეგები და გასაღები-მნიშვნელობის მონაცემები Gradle-ის ბილდებს, რათა შეადაროთ გაშვებები სხვადასხვა გუნდების, აპარატურის ან სამუშაო ნაკადებისგან. ტეგები ხელმისაწვდომია დაფის ფილტრებად, ხოლო მნიშვნელობები ჩანს თითოეული ბილდის დეტალურ გვერდზე და API-სა და Model Context Protocol-ის ინსტრუმენტებში.

დააყენეთ მეტამონაცემები გარემოს ცვლადებით:

```sh
export TUIST_BUILD_TAGS="nightly,android"
export TUIST_BUILD_VALUE_TICKET="TUIST-123"
export TUIST_BUILD_VALUE_RUNNER="macos-14"
```

ასევე შეგიძლიათ დააკონფიგურიროთ მეტამონაცემები `settings.gradle.kts`-ში:

```kotlin
tuist {
    buildInsights {
        tag("nightly")
        tag("android")
        value("ticket", "TUIST-123")
        value("runner", "macos-14")
    }
}
```

როცა ერთი და იგივე მნიშვნელობა დაკონფიგურირებულია ორივე ადგილას, უპირატესობა ენიჭება `settings.gradle.kts`-ში მითითებულ მნიშვნელობას.

ტეგები უნდა შეიცავდეს მხოლოდ ასოებს, რიცხვებს, დეფისებს და ქვედა ხაზებს. ბილდს შეიძლება ჰქონდეს 50-მდე ტეგი და თითოეული ტეგი შეიძლება შეიცავდეს 50-მდე სიმბოლოს. ბილდს შეიძლება ჰქონდეს 20-მდე გასაღები-მნიშვნელობის ჩანაწერი, თითოეული გასაღები შეიძლება შეიცავდეს 50-მდე სიმბოლოს, ხოლო თითოეული მნიშვნელობა — 500-მდე სიმბოლოს. ეს იგივე სერვერის მხარეს არსებული ლიმიტებია, რომლებიც გამოიყენება Xcode-ის ბილდის მეტამონაცემებისთვის. პლაგინი გამოტოვებს არასწორ ტეგებს და ზედმეტად დიდ ან ცარიელ მეტამონაცემების ჩანაწერებს ანგარიშის გაგზავნამდე, ამიტომ არასწორმა კონფიგურაციამ ვერ შეუშლის ხელი ბილდის ანალიტიკის ანგარიშის დანარჩენი ნაწილის შენახვას. გამოიყენეთ გასაღები-მნიშვნელობის მეტამონაცემები მნიშვნელობებისთვის, რომლებიც არ აკმაყოფილებენ ტეგის შეზღუდვას.

მორგებული მეტამონაცემები ჩანს პროექტის წევრებისთვის დაფაზე და API-სა და Model Context Protocol-ის ინსტრუმენტების მეშვეობით. არ გამოიყენოთ ის მოწმობების, წვდომის ტოკენების ან სხვა მგრძნობიარე მონაცემებისთვის. Tuist ინახავს Gradle-ის ბილდის მონაცემებს, მათ შორის ამ მეტამონაცემებს, 90 დღის განმავლობაში. დეტალებისთვის იხილეთ <.localized_link href="/guides/server/data-retention">მონაცემთა შენახვის პოლიტიკა</.localized_link>.
