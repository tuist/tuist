# API {#api}

<!-- @snippet: ./_invite-only -->

Git-ფორჯები, შერწყმის რიგები და აგენტების ორკესტრატორები, რომლებსაც საკუთარი რანერის პროტოკოლი არ გააჩნიათ, შეუძლიათ პირდაპირ Tuist Runners-ზე გაუშვან დავალებები. თქვენ ქმნით დავალებას ერთი მოთხოვნით, Tuist-ის მანქანა თქვენ მიერ არჩეული <.localized_link href="/guides/features/runners/profiles">პროფილის</.localized_link> შესაბამისად ახდენს კომიტის ჩექაუთს და ასრულებს თქვენს სკრიპტს, ხოლო Tuist აგზავნის შედეგს თქვენს ვებჰუკის ენდპოინტზე.

## დავალების გაშვება {#run-a-job}

1. **შექმენით ანგარიშის ტოკენი** `account:runners:write` სკოპით:

   ```bash
   tuist account tokens create my-org --scopes account:runners:write --name forge
   ```

2. **შექმენით დავალება.** ტიპური გამომძახებელი ამას აკეთებს თავისი push ჰუკიდან, ხმოკლედიანი ტოკენით, რომელიც მანქანას საშუალებას აძლევს დააკლონოს რეპოზიტორია:

   ```bash
   curl -X POST https://tuist.dev/api/accounts/my-org/runners/jobs \
     -H "Authorization: Bearer $TUIST_TOKEN" \
     -H "Content-Type: application/json" \
     -d '{
       "profile": "tuist-macos",
       "repository_url": "https://git.example.com/acme/app.git",
       "clone_token": "<short-lived token>",
       "commit_sha": "4f1c2d0e9b8a7c6d5e4f3a2b1c0d9e8f7a6b5c4d",
       "ref": "refs/heads/main",
       "name": "test",
       "script": "mise install\nmise run test",
       "secrets": { "SIGNING_KEY": "..." },
       "timeout_minutes": 30,
       "idempotency_key": "acme/app:4f1c2d0e:test"
     }'
   ```

   პასუხი არის დავალება თავისი `workflow_job_id`-ით. ის მაშინვე ჩნდება თქვენი Tuist დაშბორდის **Runners** სექციაში და იწყება მაშინვე, როგორც კი პროფილის შესაბამისი მანქანა თავისუფალი იქნება. „თბილი“ მანქანები ჩვეულებრივ რამდენიმე წამში იწყებენ მას.

3. **მიჰყევით დავალებას.** გამოიწერეთ <.localized_link href="/guides/integrations/webhooks">ვებჰუკის ენდპოინტი</.localized_link> `runner_job.started` და `runner_job.completed`-ზე. დასრულებული მოვლენა შეიცავს დავალების `conclusion`-ს: `success`, `failure` ან `cancelled`. ასევე შეგიძლიათ გამოიკითხოთ `GET /api/accounts/my-org/runners/jobs/{workflow_job_id}` და წაიკითხოთ ლოგი `GET /api/accounts/my-org/runners/jobs/{workflow_job_id}/logs`-დან.

## git-ფორჯის ინტეგრაცია {#integrate-a-git-forge}

ფორჯი, რომელსაც რანერის პროტოკოლი არ გააჩნია, უკავშირდება მცირე ხიდის მეშვეობით, რომელიც შეიძლება იყოს თავად ფორჯის სერვისი ან ფუნქცია, რომელსაც ის თავისი ჰუკებიდან იძახებს:

1. **push-ის დროს**, ფორჯის push ჰუკი აღწევს ხიდამდე. ხიდი ამოწმებს ჰუკს, განსაზღვრავს, თუ რომელი შემოწმებებია საჭირო კომიტისთვის და გამოსცემს რეპოზიტორიისთვის მხოლოდ წაკითხვის უფლების მქონე კლონის ტოკენს, რომელიც იწურება დავალების таймаუტის შემდეგ.
2. **თითოეული შემოწმებისთვის**, ხიდი ქმნის დავალებას `idempotency_key`-ით, დაყენებული `<repository>:<commit>:<check>`-ზე, ისე რომ ხელახლა მიწოდებულმა ჰუკმა არაფერი ახალი არ შექმნას. ის ინახავს დაბრუნებულ `workflow_job_id`-ს და შეუძლია ფორჯში შემოწმება მონიშნოს როგორც მოლოდინში.
3. **`runner_job.started` და `runner_job.completed`-ის დროს**, ხიდი ამოწმებს `Tuist-Signature` ჰედერს ენდპოინტის საიდუმლოთი, პოულობს შემოწმებას `workflow_job_id` ან `idempotency_key`-ით და ანახლებს ფორჯის კომიტის სტატუსს `conclusion`-ით. მას შეუძლია სტატუსი დააკავშიროს დავალების გვერდთან Tuist დაშბორდში.
4. **როდესაც push ცვლის კომიტს**, ხიდი აუქმებს დავალებებს, რომლებიც მან შექმნა ძველი კომიტისთვის.

## როგორ მუშაობს დავალება {#how-the-job-runs}

მანქანა HTTPS-ით იღებს `commit_sha`-ს `repository_url`-დან. როდესაც სერვერი არ ემსახურება კომიტს მისი SHA-ით, ის ნაცვლად იღებს `ref`-ს, რომელიც უნდა შეიცავდეს კომიტს. `clone_token`, თუ მას მიუთითებთ, იგზავნება როგორც `Authorization: Bearer <token>` მხოლოდ რეპოზიტორიის ჰოსტისთვის. ის არასდროს აღწევს თქვენს სკრიპტს ან დავალების ლოგს.

თქვენი სკრიპტი ეშვება Bash-ით login shell-ში, `set -eo pipefail`-ით, ჩექაუთის ფესვიდან. დავალება მარცხდება, როდესაც სკრიპტი მთავრდება არანულოვანი სტატუსით ან მუშაობს `timeout_minutes`-ზე მეტ ხანს, რომლის ნაგულისხმები მნიშვნელობაა 60 და შეიძლება იყოს 360-მდე. თქვენი `env` და `secrets`-ის გარდა, სკრიპტი ხედავს `CI=true`-ს, `TUIST_JOB_ID`-ს, `TUIST_JOB_NAME`-ს, `TUIST_JOB_REPOSITORY_URL`-ს, `TUIST_JOB_REF`-ს და `TUIST_JOB_COMMIT_SHA`-ს. `secrets`-ის მნიშვნელობები დამალულია დავალების ლოგში.

## ხელახლა ცდები და იდემპოტენტურობა {#idempotency}

მიანიჭეთ თითოეულ დავალებას `idempotency_key`, რომელიც აღწერს, თუ რისთვისაა ის, მაგალითად `<repository>:<commit>:<check>`. მოთხოვნა გასაღებით, რომელიც უკვე გამოყენებულია თქვენს ანგარიშში, აბრუნებს არსებულ დავალებას, სტატუსით 200 201-ის ნაცვლად, და არაფერს ქმნის. ეს საშუალებას აძლევს თქვენს push ჰუკს გადასცეს მოთხოვნა ხელახლა ცდის რიგს, განმეორებითი დავალებების რისკის გარეშე.

ვებჰუკის მიწოდებები მეორდება მანამ, სანამ თქვენი ენდპოინტი არ უპასუხებს 2xx სტატუსით, ამიტომ მოვლენა შეიძლება ერთზე მეტჯერ მოვიდეს. გამოიყენეთ კონვერტის `id` ან დავალების `workflow_job_id` მოვლენის ტიპთან ერთად დუბლიკატების აღმოსაფხვრელად.

## დავალების გაუქმება {#cancel-a-job}

```bash
curl -X POST https://tuist.dev/api/accounts/my-org/runners/jobs/{workflow_job_id}/cancel \
  -H "Authorization: Bearer $TUIST_TOKEN"
```

დავალება, რომელიც არცერთ მანქანას არ დაუწყია, მაშინვე უქმდება. მიმდინარე დავალება რამდენიმე წამში ჩერდება და მისი დასრულების მოვლენა აცხადებს `cancelled`-ს. დავალება, რომელიც 24 საათის განმავლობაში არცერთ მანქანას არ დაუწყია, ავტომატურად უქმდება.

## ქეშირება და ნდობა {#trust}

ნებისმიერს, ვისაც შეუძლია რეპოზიტორიაში push-ის გაკეთება, შეუძლია შეცვალოს, თუ რას ასრულებს დავალება, ამიტომ API დავალებები განიხილება როგორც არასანდო: ისინი არ იღებენ თქვენი ანგარიშის საერთო <.localized_link href="/guides/features/runners/cache-volumes">ქეშის ტომებს</.localized_link> ან მის ქეშის ხელმოწერის უფლებას. დავალების საიდუმლოები, სკრიპტი და კლონის ტოკენი ინახება დაშიფრული და იშლება დავალების დასრულების შემდეგ.
