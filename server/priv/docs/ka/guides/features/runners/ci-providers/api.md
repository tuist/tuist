# API {#api}

Git-ფორჯებს, შერწყმის რიგებსა და აგენტების ორკესტრატორებს, რომლებსაც საკუთარი რანერის პროტოკოლი არ გააჩნიათ, შეუძლიათ პირდაპირ Tuist Runners-ზე ამოქმედონ სამუშაოები. თქვენ ქმნით სამუშაოს ერთი მოთხოვნით, თქვენ მიერ შერჩეული <.localized_link href="/guides/features/runners/profiles">პროფილის</.localized_link> შესაბამისი Tuist-მანქანა იღებს კომიტს და ასრულებს თქვენს სკრიპტს, ხოლო Tuist აგზავნის შედეგს თქვენს webhook-ბოლოწერტილში.

## სამუშაოს გაშვება {#run-a-job}

1. **შექმენით ანგარიშის ტოკენი** `account:runners:write` სკოუპით:

   ```bash
   tuist account tokens create my-org --scopes account:runners:write --name forge
   ```

2. **შექმენით სამუშაო.** ჩვეულებრივ, გამომძახებელი ამას აკეთებს push-ჰუკიდან, მოკლევადიანი ტოკენით, რომელიც მანქანას საშუალებას აძლევს დააკლონოს რეპოზიტორია:

   ```bash
   curl -X POST https://tuist.dev/api/accounts/my-org/runners/jobs \
     -H "Authorization: Bearer $TUIST_TOKEN" \
     -H "Content-Type: application/json" \
     -d '{
       "profile": "tuist-macos",
       "repository_url": "https://git.example.com/acme/app.git",
       "clone_token": "<short-lived token>",
       "commit_sha": "4f1c2d0e9b8a7c6d5e4f3a2b1c0d9e8f7a6b5c4d",
       "ref": "refs/heads/main",
       "name": "test",
       "script": "mise install\nmise run test",
       "secrets": { "SIGNING_KEY": "..." },
       "timeout_minutes": 30,
       "idempotency_key": "acme/app:4f1c2d0e:test"
     }'
   ```

   პასუხი არის სამუშაო თავისი `workflow_job_id`-ით. ის მაშინვე ჩნდება თქვენი Tuist დაშბორდის **Runners** განყოფილებაში და იწყება მაშინვე, როგორც კი პროფილის შესაბამისი მანქანა თავისუფალია. „თბილი“ მანქანები მას ჩვეულებრივ წამებში იწყებენ.

3. **მიჰყევით სამუშაოს.** გამოიწერეთ <.localized_link href="/guides/integrations/webhooks">webhook-ბოლოწერტილი</.localized_link> `runner_job.started`-ზე და `runner_job.completed`-ზე. დასრულების მოვლენა შეიცავს სამუშაოს `conclusion`-ს: `success`, `failure` ან `cancelled`. ასევე შეგიძლიათ გამოიკითხოთ `GET /api/accounts/my-org/runners/jobs/{workflow_job_id}` და წაიკითხოთ ლოგი `GET /api/accounts/my-org/runners/jobs/{workflow_job_id}/logs`-დან.

## git-ფორჯის ინტეგრაცია {#integrate-a-git-forge}

ფორჯი, რომელსაც რანერის პროტოკოლი არ გააჩნია, უკავშირდება მცირე ხიდის მეშვეობით, რომელიც შეიძლება იყოს თავად ფორჯის სერვისი ან ფუნქცია, რომელსაც ის თავისი ჰუკებიდან იძახებს:

1. **push-ის დროს**, ფორჯის push-ჰუკი აღწევს ხიდამდე. ხიდი ამოწმებს ჰუკს, გადაწყვეტს, თუ რომელი შემოწმებებია საჭირო კომიტისთვის და გასცემს რეპოზიტორიისთვის მხოლოდ-წაკითხვად კლონის ტოკენს, რომელიც იწურება სამუშაოს таймаუტის შემდეგ.
2. **თითოეული შემოწმებისთვის**, ხიდი ქმნის სამუშაოს `idempotency_key`-ით, დაყენებული `<repository>:<commit>:<check>`-ზე, ისე, რომ ხელახლა მიწოდებულმა ჰუკმა არაფერი ახალი არ შექმნას. ის ინახავს დაბრუნებულ `workflow_job_id`-ს და შეუძლია ფორჯში შემოწმება მონიშნოს როგორც მოლოდინში.
3. **`runner_job.started`-ისა და `runner_job.completed`-ის დროს**, ხიდი ამოწმებს `Tuist-Signature` ჰედერს ბოლოწერტილის საიდუმლოთი, პოულობს შემოწმებას `workflow_job_id`-ით ან `idempotency_key`-ით და ანახლებს ფორჯის კომიტის სტატუსს `conclusion`-ით. მას შეუძლია სტატუსი დააკავშიროს სამუშაოს გვერდთან Tuist დაშბორდზე.
4. **როდესაც push ცვლის კომიტს**, ხიდი აუქმებს სამუშაოებს, რომლებიც მან შექმნა ძველი კომიტისთვის.

## როგორ მუშაობს სამუშაო {#how-the-job-runs}

მანქანა იღებს `commit_sha`-ს `repository_url`-დან HTTPS-ის მეშვეობით. როდესაც სერვერი არ გასცემს კომიტს მისი SHA-ით, ის ნაცვლად იღებს `ref`-ს, რომელიც უნდა შეიცავდეს კომიტს. `clone_token`, თუ მას მიუთითებთ, იგზავნება როგორც `Authorization: Bearer <token>` მხოლოდ რეპოზიტორიის ჰოსტისთვის. ის არასდროს აღწევს თქვენს სკრიპტამდე ან სამუშაოს ლოგამდე.

თქვენი სკრიპტი ეშვება Bash-ით login shell-ში, `set -eo pipefail`-ით, checkout-ის ფესვიდან. სამუშაო ვერდება, როდესაც სკრიპტი ბრუნდება არანულოვანი სტატუსით ან გადის `timeout_minutes`-ს, რომლის ნაგულისხმები მნიშვნელობაა 60 და შეიძლება იყოს 360-მდე. თქვენი `env`-ისა და `secrets`-ის გარდა, სკრიპტი ხედავს `CI=true`-ს, `TUIST_JOB_ID`-ს, `TUIST_JOB_NAME`-ს, `TUIST_JOB_REPOSITORY_URL`-ს, `TUIST_JOB_REF`-ს და `TUIST_JOB_COMMIT_SHA`-ს. `secrets`-ის მნიშვნელობები დაფარულია სამუშაოს ლოგში.

## გამეორებები და იდემპოტენტობა {#idempotency}

მიანიჭეთ თითოეულ სამუშაოს `idempotency_key`, რომელიც აღწერს, თუ რისთვისაა ის, მაგალითად `<repository>:<commit>:<check>`. მოთხოვნა გასაღებით, რომელიც უკვე გამოყენებულია თქვენს ანგარიშში, აბრუნებს არსებულ სამუშაოს 200 სტატუსით 201-ის ნაცვლად და არაფერს ქმნის. ეს საშუალებას აძლევს თქვენს push-ჰუკს გადასცეს მოთხოვნა განმეორების რიგს დუბლირებული სამუშაოების რისკის გარეშე.

Webhook-მიწოდებები მეორდება, სანამ თქვენი ბოლოწერტილი არ უპასუხებს 2xx სტატუსით, ამიტომ მოვლენა შეიძლება ერთზე მეტჯერ მოვიდეს. გამოიყენეთ კონვერტის `id` ან სამუშაოს `workflow_job_id` მოვლენის ტიპთან ერთად დუბლიკატების აღმოსაფხვრელად.

## სამუშაოს გაუქმება {#cancel-a-job}

```bash
curl -X POST https://tuist.dev/api/accounts/my-org/runners/jobs/{workflow_job_id}/cancel \
  -H "Authorization: Bearer $TUIST_TOKEN"
```

სამუშაო, რომელიც არცერთ მანქანას არ დაუწყია, მაშინვე უქმდება. მიმდინარე სამუშაო ჩერდება რამდენიმე წამში და მისი დასრულების მოვლენა იუწყება `cancelled`-ს. სამუშაო, რომელიც 24 საათის განმავლობაში არცერთ მანქანას არ დაუწყია, ავტომატურად უქმდება.

## ქეშირება და ნდობა {#trust}

ნებისმიერს, ვისაც შეუძლია რეპოზიტორიაში push-ის გაკეთება, შეუძლია შეცვალოს ის, რასაც სამუშაო ასრულებს, ამიტომ API სამუშაოები განიხილება როგორც არასანდო: მათ არ აქვთ თქვენი ანგარიშის საერთო <.localized_link href="/guides/features/runners/cache-volumes">ქეშის ტომები</.localized_link> ან მისი ქეშის ხელმოწერის უფლება. სამუშაოს საიდუმლოები, სკრიპტი და კლონის ტოკენი ინახება დაშიფრული და იშლება სამუშაოს დასრულების შემდეგ.
