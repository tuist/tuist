# API {#api}

<!-- @snippet: ./_invite-only -->

Git-ფორჯებს, შერწყმის რიგებსა და აგენტების ორკესტრატორებს, რომლებსაც საკუთარი რანერის პროტოკოლი არ გააჩნიათ, შეუძლიათ პირდაპირ Tuist Runners-ზე სამუშაოების შესრულება. თქვენ ქმნით სამუშაოს ერთი მოთხოვნით, Tuist-ის მანქანა თქვენ მიერ შერჩეული <.localized_link href="/guides/features/runners/profiles">პროფილის</.localized_link> შესაბამისად იღებს კომიტს და ასრულებს თქვენს სკრიპტს, ხოლო Tuist აგზავნის შედეგს თქვენს ვებჰუკის ენდპოინტზე.

## სამუშაოს შესრულება {#run-a-job}

1. **შექმენით ანგარიშის ტოკენი** `account:runners:write` სკოპით:

   ```bash
   tuist account tokens create my-org --scopes account:runners:write --name forge
   ```

2. **შექმენით სამუშაო.** ჩვეულებრივ, გამომძახებელი ამას აკეთებს push ჰუკიდან, მოკლევადიანი ტოკენით, რომელიც მანქანას საშუალებას აძლევს დააკლონოს რეპოზიტორია:

   ```bash
   curl -X POST https://tuist.dev/api/accounts/my-org/runners/jobs \
     -H "Authorization: Bearer $TUIST_TOKEN" \
     -H "Content-Type: application/json" \
     -d '{
       "profile": "tuist-macos",
       "repository_url": "https://git.example.com/acme/app.git",
       "clone_token": "<short-lived token>",
       "commit_sha": "4f1c2d0e9b8a7c6d5e4f3a2b1c0d9e8f7a6b5c4d",
       "ref": "refs/heads/main",
       "name": "test",
       "script": "mise install\nmise run test",
       "secrets": { "SIGNING_KEY": "..." },
       "timeout_minutes": 30,
       "idempotency_key": "acme/app:4f1c2d0e:test"
     }'
   ```

   პასუხი არის სამუშაო თავისი `workflow_job_id`-ით. ის მაშინვე ჩნდება თქვენი Tuist დაშბორდის **Runners** განყოფილებაში და იწყება მაშინვე, როგორც კი პროფილის შესაბამისი მანქანა თავისუფალი გახდება. „თბილი“ მანქანები მას ჩვეულებრივ წამებში იწყებენ.

3. **მიჰყევით სამუშაოს.** გამოიწერეთ <.localized_link href="/guides/integrations/webhooks">ვებჰუკის ენდპოინტი</.localized_link> `runner_job.started` და `runner_job.completed` მოვლენებზე. დასრულების მოვლენა შეიცავს სამუშაოს `conclusion`-ს: `success`, `failure` ან `cancelled`. ასევე შეგიძლიათ პერიოდულად გამოიძახოთ `GET /api/accounts/my-org/runners/jobs/{workflow_job_id}` და წაიკითხოთ ლოგი `GET /api/accounts/my-org/runners/jobs/{workflow_job_id}/logs`-დან.

## git-ფორჯის ინტეგრაცია {#integrate-a-git-forge}

ფორჯი, რომელსაც რანერის პროტოკოლი არ გააჩნია, უკავშირდება მცირე ხიდის მეშვეობით, რომელიც შეიძლება იყოს თავად ფორჯის სერვისი ან ფუნქცია, რომელსაც ის თავისი ჰუკებიდან იძახებს:

1. **Push-ის დროს**, ფორჯის push ჰუკი აღწევს ხიდამდე. ხიდი ამოწმებს ჰუკს, გადაწყვეტს, თუ რა შემოწმებები სჭირდება კომიტს და გასცემს რეპოზიტორიისთვის მხოლოდ წაკითხვის უფლების მქონე კლონის ტოკენს, რომელიც იწურება სამუშაოს таймаუტის შემდეგ.
2. **თითოეული შემოწმებისთვის**, ხიდი ქმნის სამუშაოს `idempotency_key`-ით, რომელიც დაყენებულია `<repository>:<commit>:<check>`-ზე, ისე რომ ხელახლა მიწოდებულმა ჰუკმა არაფერი ახალი არ შექმნას. ის ინახავს დაბრუნებულ `workflow_job_id`-ს და შეუძლია ფორჯში შემოწმება მონიშნოს როგორც მოლოდინში.
3. **`runner_job.started` და `runner_job.completed` მოვლენების დროს**, ხიდი ამოწმებს `Tuist-Signature` ჰედერს ენდპოინტის საიდუმლოებით, პოულობს შემოწმებას `workflow_job_id`-ის ან `idempotency_key`-ის მიხედვით და ანახლებს ფორჯის კომიტის სტატუსს `conclusion`-ით. მას შეუძლია სტატუსი დააკავშიროს Tuist დაშბორდზე სამუშაოს გვერდთან.
4. **როდესაც push ანაცვლებს კომიტს**, ხიდი აუქმებს ძველი კომიტისთვის შექმნილ სამუშაოებს.

## როგორ სრულდება სამუშაო {#how-the-job-runs}

მანქანა იღებს `commit_sha`-ს `repository_url`-დან HTTPS-ის მეშვეობით. როდესაც სერვერი არ გასცემს კომიტს მისი SHA-ით, ის ნაცვლად იღებს `ref`-ს, რომელიც უნდა შეიცავდეს კომიტს. `clone_token`, თუ მას მიუთითებთ, იგზავნება როგორც `Authorization: Bearer <token>` მხოლოდ რეპოზიტორიის ჰოსტისთვის. ის არასდროს აღწევს თქვენს სკრიპტს ან სამუშაოს ლოგს.

თქვენი სკრიპტი სრულდება Bash-ით login shell-ში, `set -eo pipefail` პარამეტრით, checkout-ის ფესვიდან. სამუშაო მარცხდება, როდესაც სკრიპტი ბრუნდება არანულოვანი სტატუსით ან აღემატება `timeout_minutes`-ს, რომლის ნაგულისხმები მნიშვნელობაა 60 და შეიძლება იყოს 360-მდე. თქვენი `env` და `secrets` გარდა, სკრიპტი ხედავს `CI=true`-ს, `TUIST_JOB_ID`-ს, `TUIST_JOB_NAME`-ს, `TUIST_JOB_REPOSITORY_URL`-ს, `TUIST_JOB_REF`-ს და `TUIST_JOB_COMMIT_SHA`-ს. `secrets`-ის მნიშვნელობები დამალულია სამუშაოს ლოგში.

## ხელახლა ცდები და იდემპოტენტობა {#idempotency}

მიანიჭეთ თითოეულ სამუშაოს `idempotency_key`, რომელიც აღწერს მის დანიშნულებას, მაგალითად `<repository>:<commit>:<check>`. მოთხოვნა, რომელსაც უკვე გამოყენებული გასაღები აქვს თქვენს ანგარიშში, აბრუნებს არსებულ სამუშაოს 201-ის ნაცვლად 200 სტატუსით და არაფერს ქმნის. ეს საშუალებას აძლევს თქვენს push ჰუკს მოთხოვნა გადასცეს ხელახლა ცდის რიგს დუბლირებული სამუშაოების რისკის გარეშე.

ვებჰუკის მიწოდებები მეორდება მანამ, სანამ თქვენი ენდპოინტი არ უპასუხებს 2xx სტატუსით, ამიტომ მოვლენა შეიძლება ერთზე მეტჯერ მოვიდეს. გამოიყენეთ გარსის `id` ან სამუშაოს `workflow_job_id` მოვლენის ტიპთან ერთად დუბლიკატების აღმოსაფხვრელად.

## სამუშაოს გაუქმება {#cancel-a-job}

```bash
curl -X POST https://tuist.dev/api/accounts/my-org/runners/jobs/{workflow_job_id}/cancel \
  -H "Authorization: Bearer $TUIST_TOKEN"
```

სამუშაო, რომელიც არცერთ მანქანას არ დაუწყია, მაშინვე უქმდება. მიმდინარე სამუშაო რამდენიმე წამში ჩერდება და მისი დასრულების მოვლენა იუწყება `cancelled`-ს. სამუშაო, რომელიც 24 საათის განმავლობაში არცერთ მანქანას არ დაუწყია, ავტომატურად უქმდება.

## ქეშირება და ნდობა {#trust}

ნებისმიერს, ვისაც რეპოზიტორიაში push-ის უფლება აქვს, შეუძლია შეცვალოს ის, რასაც სამუშაო ასრულებს, ამიტომ API სამუშაოები განიხილება როგორც არასანდო: მათ არ აქვთ თქვენი ანგარიშის გაზიარებული <.localized_link href="/guides/features/runners/cache-volumes">ქეშის ტომები</.localized_link> ან მისი ქეშის ხელმოწერის ნებართვა. სამუშაოს საიდუმლოებები, სკრიპტი და კლონის ტოკენი ინახება დაშიფრული და იშლება სამუშაოს დასრულების შემდეგ.
