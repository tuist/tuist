# GitLab CI {#gitlab-ci}

თქვენი პაიპლაინები რჩება GitLab-ში. Tuist უზრუნველყოფს იზოლირებულ Linux ან macOS მანქანას თითოეული ჯობისთვის და აგზავნის მის ლოგებსა და შედეგებს GitLab-ში და Tuist-ის დაშბორდზე. საჭიროა GitLab 19.3 ან უფრო ახალი ვერსია. მხარდაჭერილია GitLab.com და საჯარო HTTPS-ით ხელმისაწვდომი თვითმართვადი ინსტანციები.

1. **შექმენით GitLab რანერი.** თქვენი პროექტის **Settings → CI/CD → Runners** განყოფილებაში შექმენით პროექტის რანერი. ასევე შეგიძლიათ გამოიყენოთ ჯგუფური რანერი. დაამატეთ ყველა Tuist პროფილის ლეიბლი, რომელთაც გსურთ გამოყენება როგორც რანერის ტეგები, მაგალითად `tuist-linux` და `tuist-macos`, და გათიშეთ **Run untagged jobs**. შეინახეთ ავტორიზაციის ტოკენი, რომელსაც GitLab გაჩვენებთ და რომელიც იწყება `glrt-`-ით. თქვენ არ გჭირდებათ რანერის ინსტალაცია თქვენს საკუთარ მანქანაზე.
2. **ერთხელ დააკავშირეთ Tuist-თან.** **Settings → Integrations** განყოფილებაში, GitLab CI ბარათზე აირჩიეთ **Connect**. შეიყვანეთ თქვენი GitLab URL და რანერის ავტორიზაციის ტოკენი. კავშირს შეუძლია მოემსახუროს სხვადასხვა პროფილის მქონე ჯობებს. ტოკენები ინახება დაშიფრული და აღარასდროს გამოისახება. სურვილისამებრ, დაამატეთ API წვდომის ტოკენი, რათა merge request პაიპლაინებმა შეძლონ ქეშის ტომების შენახვა; იხილეთ [Merge request pipelines](#merge-request-pipelines).
3. **აირჩიეთ მანქანა თითოეულ ჯობაში.** ჯობის `tags`-ში მიუთითეთ ზუსტად ერთი <.localized_link href="/guides/features/runners/profiles">Tuist პროფილის ლეიბლი</.localized_link>. სხვა ტეგები დაშვებულია, იმ პირობით, რომ დარეგისტრირებულ GitLab რანერსაც აქვს ისინი:

   ```yaml
   # .gitlab-ci.yml
   linux-check:
     tags: [tuist-linux]
     script:
       - uname -a

   test:
     tags: [tuist-macos]
     script:
       - tuist test
     retry:
       max: 2
       when: runner_system_failure
   ```

4. **გაუშვით და დააკვირდით.** Tuist იწყებს გამოკითხვას ერთი წუთის განმავლობაში. ჯობები ჩნდება **Runners** განყოფილებაში, GitLab ჯობაზე, ლოგებზე და მანქანის მეტრიკებზე დამბრუნებელი ბმულით. GitLab იღებს ლოგებს ჯობის შესრულებისას; Tuist იღებს დაფარულ ლოგს მისი დასრულების შემდეგ.

Tuist კითხულობს `CI_JOB_TAGS`-ს თითოეული დანიშვნისგან და ადგენს პროფილს დაკავშირებულ Tuist ანგარიშში. ის არ განსაზღვრავს მანქანას `CI_RUNNER_TAGS`-დან და არ იყენებს ნაგულისხმევ პროფილს. Tuist პროფილის ტეგების არარსებობა, უცნობობა ან მრავლობითობა იწვევს მიღებული ჯობის შეცდომას ახსნით მის GitLab ლოგში. არ გადაფაროთ `CI_JOB_TAGS` თქვენს პაიპლაინის ცვლადებში.

## შესრულების გარემო {#execution-environment}

ჯობები იყენებენ GitLab-ის **shell executor**-ს იზოლირებულ მანქანაში. Checkout, CI ცვლადები, `before_script`, `script`, `after_script`, არტიფაქტები და გაუქმება მუშავდება GitLab Runner-ის მიერ. პაიპლაინის `image:` და `services:` პარამეტრები არ აკონფიგურირებენ ამ shell გარემოს; გამოიყენეთ <.localized_link href="/guides/features/runners/profiles">runner image</.localized_link>-ზე ინსტალირებული ინსტრუმენტები ან დააინსტალირეთ ისინი თქვენს სკრიპტში.

ხელახლა გამოსაყენებელი რანერის ავტორიზაციის ტოკენი რჩება Tuist სერვერზე. მანქანები იღებენ მხოლოდ მათთვის განკუთვნილი ჯობის სერთიფიკატებს. ქეშის ხელმოწერის უფლებები ამჟამად შეჩერებულია GitLab ჯობებისთვის. მორგებული Linux ქეშის ტომები ამოწმებენ ჯობის იდენტურობას და შენახვის უფლებას GitLab-ის API-ს მეშვეობით; გადაფარვადი CI ცვლადები არ ამყარებენ ნდობას.

GitLab ნიშნავს ჯობას როგორც შესრულებადს და იწყებს მის დროის ამოწურვას, როგორც კი Tuist მიიღებს მას. სანამ Tuist-ის მიერ უკვე მიღებული ჯობები იყენებენ თქვენი ანგარიშის კონკურენტულობის ლიმიტს, დამატებითი ჯობები რჩებიან მოლოდინის რეჟიმში GitLab-ში. მიღებული ჯობა ელოდება მანქანას მისი ჯობის დროის ამოწურვამდე, მაქსიმუმ 12 საათის განმავლობაში. თუ ამ დროისთვის მანქანა არ გახდება ხელმისაწვდომი, Tuist აფრუშებს დანიშვნას `runner_system_failure`-ით და ზემოთ მოყვანილი ხელახლა ცდის პოლიტიკა საშუალებას აძლევს GitLab-ს ხელახლა სცადოს ის. იგივე პოლიტიკა ვრცელდება დაკარგულ რანერ მანქანაზეც.

## ტოკენების როტაცია და გათიშვა {#rotating-tokens-and-disconnecting}

განაახლეთ კავშირის ტოკენები და აირჩიეთ **Save changes** მათი როტაციისთვის. ტოკენის ველის ცარიელად დატოვება ინარჩუნებს არსებულ სერთიფიკატს.

**Disconnect** აჩერებს მიღებას და აფრუშებს მოლოდინში მყოფ დანიშვნებს. შესრულებადი ჯობები გრძელდება საკუთარი სერთიფიკატებით. თუ GitLab-თან მიღწევა შეუძლებელია, Tuist ინარჩუნებს გათიშულ კავშირს, სანამ ხელახლა სცდის მოლოდინში მყოფი დანიშვნების გაუქმებას. კავშირი იშლება მას შემდეგ, რაც ეს დანიშვნები დასრულდება.

## ქეშის ტომები {#cache-volumes}

შეინარჩუნეთ Xcode, მოდულის და Gradle ქეშები და სხვა დირექტორიები ჯობებს შორის <.localized_link href="/guides/features/runners/cache-volumes">cache volumes</.localized_link>-ის მეშვეობით. დაამატეთ ისინი checkout-ის შემდეგ და იმ ბრძანებებამდე, რომლებიც მათ იყენებენ.

### Merge request პაიპლაინები {#merge-request-pipelines}

პროექტის push, schedule და web პაიპლაინები ინახავენ თავიანთ ცვლილებებს ქეშის ტომებში. Merge request პაიპლაინები იყენებენ ქეშს და ინახავენ თავიანთ ცვლილებებს მხოლოდ მაშინ, როცა კავშირს აქვს API წვდომის ტოკენი:

1. GitLab-ში შექმენით პროექტის ან ჯგუფის წვდომის ტოკენი **Reporter** როლით და `read_api` სკოპით. ჯგუფური ტოკენი ფარავს ჯგუფის ყველა პროექტს, რომელიც მუშაობს Tuist რანერებზე.
2. **Settings → Integrations** განყოფილებაში, ჩასვით ის GitLab CI ბარათზე **API access token** ველში და აირჩიეთ **Save changes**.

შემდეგ Tuist კითხულობს თითოეული merge request პაიპლაინის merge request-ს. პროექტის საკუთარი ბრენჩიდან გახსნილი merge request-ების პაიპლაინები ინახავენ თავიანთ ცვლილებებს merge request-ის საწყისი ბრენჩის ქვეშ, ამიტომ რანერის პროფილის <.localized_link href="/guides/features/runners/cache-volumes#choose-which-branches-save">branch settings</.localized_link> ვრცელდება ამ ბრენჩზე. Fork-ებიდან შემოსული merge request-ები არასდროს ინახავენ ცვლილებებს. თუ Tuist ვერ კითხულობს merge request-ს, ჯობა მაინც სრულდება და იყენებს ქეშს, მაგრამ მისი ცვლილებები იკარგება.
