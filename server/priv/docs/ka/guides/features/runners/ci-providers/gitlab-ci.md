# GitLab CI {#gitlab-ci}

> [!IMPORTANT]
> **მხოლოდ მოწვევით**
>
> Tuist Runners ამჟამად მხოლოდ მოწვევითაა ხელმისაწვდომი. [დაგვიკავშირდით](mailto:contact@tuist.dev), რათა მიიღოთ წვდომა თქვენს ანგარიშზე.

თქვენი პაიპლაინები GitLab-ში რჩება. Tuist უზრუნველყოფს იზოლირებულ Linux ან macOS მანქანას თითოეული ჯობისთვის და აგზავნის ლოგებსა და შედეგს GitLab-სა და Tuist-ის დაშბორდზე. საჭიროა GitLab 19.3 ან უფრო ახალი ვერსია. მხარდაჭერილია GitLab.com და საჯარო HTTPS-ით ხელმისაწვდომი თვითმართვადი ინსტანციები.

1. **შექმენით GitLab runner.** თქვენი პროექტის **Settings → CI/CD → Runners** განყოფილებაში შექმენით პროექტის runner. ასევე შეგიძლიათ გამოიყენოთ ჯგუფის runner. დაამატეთ ყველა Tuist პროფილის ლეიბლი, რომლებიც გსურთ გამოიყენოთ როგორც runner-ის ტეგები, მაგალითად `tuist-linux` და `tuist-macos`, და გათიშეთ **Run untagged jobs**. შეინახეთ ავტორიზაციის ტოკენი, რომელსაც GitLab აჩვენებს და რომელიც იწყება `glrt-`-ით. თქვენს მანქანაზე runner-ის ინსტალაცია არ არის საჭირო.
2. **ერთხელ დააკავშირეთ Tuist-თან.** **Settings → Integrations** განყოფილებაში აირჩიეთ **Connect** GitLab CI ბარათზე. შეიყვანეთ თქვენი GitLab URL და runner-ის ავტორიზაციის ტოკენი. კავშირს შეუძლია მოემსახუროს სხვადასხვა პროფილის მქონე ჯობებს. ტოკენები ინახება დაშიფრული და აღარასდროს ჩანს. სურვილისამებრ, დაამატეთ API წვდომის ტოკენი, რათა merge request პაიპლაინებმა შეძლონ cache volume-ების შენახვა; იხილეთ [Merge request pipelines](#merge-request-pipelines).
3. **აირჩიეთ მანქანა თითოეულ ჯობაში.** ჯობის `tags` ველში მიუთითეთ ზუსტად ერთი <.localized_link href="/guides/features/runners/profiles">Tuist პროფილის ლეიბლი</.localized_link>. სხვა ტეგები დაშვებულია, იმ პირობით, რომ დარეგისტრირებულ GitLab runner-საც აქვს ისინი:

   ```yaml
   # .gitlab-ci.yml
   linux-check:
     tags: [tuist-linux]
     script:
       - uname -a

   test:
     tags: [tuist-macos]
     script:
       - tuist test
     retry:
       max: 2
       when: runner_system_failure
   ```

4. **გაუშვით და დააკვირდით.** Tuist იწყებს გამოკითხვას ერთი წუთის განმავლობაში. ჯობები ჩნდება **Runners** განყოფილებაში, GitLab ჯობაზე, ლოგებზე და მანქანის მეტრიკებზე დამბრუნებელი ბმულით. GitLab იღებს ლოგებს ჯობის შესრულებისას; Tuist იღებს დაფარულ ლოგს მისი დასრულების შემდეგ.

Tuist კითხულობს `CI_JOB_TAGS` თითოეული დანიშვნისთვის და ადგენს პროფილს დაკავშირებულ Tuist ანგარიშში. ის არ ადგენს მანქანას `CI_RUNNER_TAGS`-დან და არ იყენებს ნაგულისხმევ პროფილს. დაკარგული, უცნობი ან მრავალი Tuist პროფილის ტეგი აუქმებს მიღებულ ჯობას ახსნით მის GitLab ლოგში. არ გადაწეროთ `CI_JOB_TAGS` თქვენს პაიპლაინის ცვლადებში.

## შესრულების გარემო {#execution-environment}

ჯობები იყენებენ GitLab-ის **shell executor**-ს იზოლირებულ მანქანაში. Checkout, CI ცვლადები, `before_script`, `script`, `after_script`, არტიფაქტები და გაუქმება მუშავდება GitLab Runner-ის მიერ. პაიპლაინის `image:` და `services:` პარამეტრები არ აკონფიგურირებენ ამ shell გარემოს; გამოიყენეთ ინსტრუმენტები, რომლებიც დაინსტალირებულია <.localized_link href="/guides/features/runners/profiles">runner image</.localized_link>-ზე, ან დააინსტალირეთ ისინი თქვენს სკრიპტში.

გამოყენებადი runner-ის ავტორიზაციის ტოკენი რჩება Tuist სერვერზე. მანქანები იღებენ მხოლოდ მათთვის განკუთვნილი ჯობის სერთიფიკატებს. Cache-signing ნებართვები ამჟამად შეჩერებულია GitLab ჯობებისთვის. მორგებული Linux cache volume-ები ამოწმებენ ჯობის იდენტურობას და შენახვის ნებართვას GitLab-ის API-ს მეშვეობით; გადაწერადი CI ცვლადები ნდობას არ ამყარებენ.

GitLab ნიშნავს ჯობას როგორც შესრულებადს და იწყებს მის დროის ამოწურვას, როგორც კი Tuist იღებს მას. სანამ Tuist-ის მიერ უკვე მიღებული ჯობები იყენებენ თქვენი ანგარიშის პარალელურობის ლიმიტს, დამატებითი ჯობები რჩებიან მოლოდინის რეჟიმში GitLab-ში. მიღებული ჯობა ელოდება მანქანას მისი ჯობის დროის ამოწურვამდე, მაქსიმუმ 12 საათის განმავლობაში. თუ ამ დროისთვის მანქანა არ ხდება ხელმისაწვდომი, Tuist აუქმებს დანიშვნას `runner_system_failure`-ით, და ზემოთ მოცემული განმეორების პოლიტიკა საშუალებას აძლევს GitLab-ს განაახლოს ის. იგივე პოლიტიკა ვრცელდება დაკარგულ runner მანქანაზე.

## ტოკენების როტაცია და გათიშვა {#rotating-tokens-and-disconnecting}

განაახლეთ კავშირის ტოკენები და აირჩიეთ **Save changes** მათი როტაციისთვის. ტოკენის ველის ცარიელად დატოვება ინარჩუნებს არსებულ სერთიფიკატს.

**Disconnect** აჩერებს მიღებას და აუქმებს მოლოდინში მყოფ დანიშვნებს. შესრულებადი ჯობები გრძელდება თავიანთი სერთიფიკატებით. თუ GitLab-თან წვდომა შეუძლებელია, Tuist ინარჩუნებს გათიშულ კავშირს, სანამ ცდილობს მოლოდინში მყოფი დანიშვნების გაუქმებას. კავშირი იშლება მას შემდეგ, რაც ეს დანიშვნები დასრულდება.

## Cache volume-ები {#cache-volumes}

შეინახეთ Xcode, მოდულის და Gradle ქეშები და სხვა დირექტორიები ჯობებს შორის <.localized_link href="/guides/features/runners/cache-volumes">cache volume-ების</.localized_link> გამოყენებით. დაამატეთ ისინი checkout-ის შემდეგ და იმ ბრძანებებამდე, რომლებიც მათ იყენებენ.

### Merge request პაიპლაინები {#merge-request-pipelines}

პროექტის push, schedule და web პაიპლაინები ინახავენ ცვლილებებს cache volume-ებში. Merge request პაიპლაინები იყენებენ ქეშს და ინახავენ ცვლილებებს მხოლოდ მაშინ, როცა კავშირს აქვს API წვდომის ტოკენი:

1. GitLab-ში შექმენით პროექტის ან ჯგუფის წვდომის ტოკენი **Reporter** როლით და `read_api` სკოპით. ჯგუფის ტოკენი ფარავს ჯგუფის ყველა პროექტს, რომელიც მუშაობს Tuist runner-ებზე.
2. **Settings → Integrations** განყოფილებაში ჩასვით ის **API access token** ველში GitLab CI ბარათზე და აირჩიეთ **Save changes**.

Tuist შემდეგ კითხულობს თითოეული merge request პაიპლაინის merge request-ს. პროექტის საკუთარი ბრენჩიდან გახსნილი merge request-ების პაიპლაინები ინახავენ ცვლილებებს merge request-ის საწყის ბრენჩის ქვეშ, ასე რომ runner პროფილის <.localized_link href="/guides/features/runners/cache-volumes#choose-which-branches-save">ბრენჩის პარამეტრები</.localized_link> ვრცელდება ამ ბრენჩზე. Fork-ებიდან მოსული merge request-ები არასდროს ინახავენ. თუ Tuist ვერ კითხულობს merge request-ს, ჯობა მაინც მუშაობს და იყენებს ქეშს, მაგრამ მისი ცვლილებები იკარგება.
