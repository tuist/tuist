# GitLab CI {#gitlab-ci}

<!-- @snippet: ./_invite-only -->

თქვენი პაიპლაინები რჩება GitLab-ში. Tuist უზრუნველყოფს იზოლირებულ Linux ან macOS მანქანას თითოეული სამუშაოსთვის და აგზავნის ლოგებსა და შედეგებს როგორც GitLab-ში, ისე Tuist-ის დაფაზე. საჭიროა GitLab 19.3 ან უფრო ახალი ვერსია. მხარდაჭერილია GitLab.com და საჯარო HTTPS-ით ხელმისაწვდომი თვითმართვადი ინსტანციები.

1. **შექმენით GitLab runner.** თქვენი პროექტის **Settings → CI/CD → Runners** განყოფილებაში შექმენით პროექტის runner. ასევე შეგიძლიათ გამოიყენოთ ჯგუფის runner. დაამატეთ ყველა Tuist პროფილის ლეიბლი, რომელთაც გსურთ გამოყენება როგორც runner-ის ტეგები, მაგალითად `tuist-linux` და `tuist-macos`, და გათიშეთ **Run untagged jobs**. შეინახეთ GitLab-ის მიერ ნაჩვენები ავთენტიკაციის ტოკენი, რომელიც იწყება `glrt-`-ით. თქვენს მანქანაზე runner-ის დაყენება არ არის საჭირო.
2. **ერთხელ დააკავშირეთ Tuist-თან.** **Settings → Integrations** განყოფილებაში, GitLab CI ბარათზე აირჩიეთ **Connect**. შეიყვანეთ თქვენი GitLab URL და runner-ის ავთენტიკაციის ტოკენი. კავშირს შეუძლია მოემსახუროს სხვადასხვა პროფილის მქონე სამუშაოებს. ტოკენები ინახება დაშიფრული და აღარასდროს გამოჩნდება. სურვილის შემთხვევაში, დაამატეთ API წვდომის ტოკენი, რათა merge request პაიპლაინებმა შეძლონ cache ტომების შენახვა; იხილეთ [Merge request pipelines](#merge-request-pipelines).
3. **აირჩიეთ მანქანა თითოეულ სამუშაოში.** სამუშაოს `tags`-ში მიუთითეთ ზუსტად ერთი <.localized_link href="/guides/features/runners/profiles">Tuist პროფილის ლეიბლი</.localized_link>. სხვა ტეგები დაშვებულია, იმ პირობით, რომ რეგისტრირებულ GitLab runner-საც აქვს ისინი:

   ```yaml
   # .gitlab-ci.yml
   linux-check:
     tags: [tuist-linux]
     script:
       - uname -a

   test:
     tags: [tuist-macos]
     script:
       - tuist test
     retry:
       max: 2
       when: runner_system_failure
   ```

4. **გაგზავნეთ და დააკვირდით.** Tuist იწყებს გამოკითხვას ერთი წუთის განმავლობაში. სამუშაოები ჩნდება **Runners** განყოფილებაში, GitLab-ის სამუშაოზე, ლოგებზე და მანქანის მეტრიკებზე დამბრუნებელი ბმულით. GitLab იღებს ლოგებს სამუშაოს შესრულებისას; Tuist იღებს დაფარულ ლოგს მისი დასრულებისას.

Tuist კითხულობს `CI_JOB_TAGS`-ს თითოეული დანიშვნისგან და ადგენს პროფილს დაკავშირებულ Tuist ანგარიშში. ის არ გამოიტანს მანქანას `CI_RUNNER_TAGS`-დან და არ იყენებს ნაგულისხმევ პროფილს. ნაკლული, უცნობი ან მრავალი Tuist პროფილის ტეგი აცდენს მიღებულ სამუშაოს ახსნით მის GitLab ლოგში. არ გადაფაროთ `CI_JOB_TAGS` თქვენს პაიპლაინის ცვლადებში.

## შესრულების გარემო {#execution-environment}

სამუშაოები იყენებენ GitLab-ის **shell executor**-ს იზოლირებულ მანქანაში. Checkout, CI ცვლადები, `before_script`, `script`, `after_script`, არტეფაქტები და გაუქმება მუშავდება GitLab Runner-ის მიერ. პაიპლაინის `image:` და `services:` პარამეტრები არ აკონფიგურირებენ ამ shell გარემოს; გამოიყენეთ <.localized_link href="/guides/features/runners/profiles">runner image</.localized_link>-ზე დაყენებული ინსტრუმენტები ან დააყენეთ ისინი თქვენს სკრიპტში.

გამოყენებადი runner-ის ავთენტიკაციის ტოკენი რჩება Tuist სერვერზე. მანქანები იღებენ მხოლოდ მათთვის მინიჭებული სამუშაოს სერთიფიკატებს. Cache-ის ხელმოწერის უფლებები ამჟამად შეჩერებულია GitLab სამუშაოებისთვის. მორგებული Linux cache ტომები ამოწმებენ სამუშაოს იდენტურობას და შენახვის უფლებას GitLab-ის API-ს მეშვეობით; გადაფარვადი CI ცვლადები ნდობას არ ამყარებენ.

GitLab აღნიშნავს სამუშაოს როგორც შესრულებადს და იწყებს მის დროის ამოწურვას, როგორც კი Tuist მიიღებს მას. სანამ Tuist-ის მიერ უკვე მიღებული სამუშაოები იყენებენ თქვენი ანგარიშის კონკურენტულობის ლიმიტს, დამატებითი სამუშაოები რჩებიან მოლოდინის რეჟიმში GitLab-ში. მიღებული სამუშაო ელოდება მანქანას მისი სამუშაოს დროის ამოწურვამდე, მაქსიმუმ 12 საათის განმავლობაში. თუ ამ დროისთვის მანქანა არ გახდება ხელმისაწვდომი, Tuist აცდენს დანიშვნას `runner_system_failure`-ით და ზემოთ მოყვანილი ხელახლა ცდის პოლიტიკა საშუალებას აძლევს GitLab-ს ხელახლა სცადოს ის. იგივე პოლიტიკა ფარავს დაკარგულ runner მანქანას.

## ტოკენების როტაცია და გათიშვა {#rotating-tokens-and-disconnecting}

განაახლეთ კავშირის ტოკენები და აირჩიეთ **Save changes** მათი როტაციისთვის. ტოკენის ველის ცარიელად დატოვება ინარჩუნებს არსებულ სერთიფიკატს.

**Disconnect** აჩერებს მიღებას და აცდენს მოლოდინში მყოფ დანიშვნებს. შესრულებადი სამუშაოები გრძელდება თავიანთი სერთიფიკატებით. თუ GitLab-თან მიღწევა შეუძლებელია, Tuist ინარჩუნებს გათიშულ კავშირს, სანამ ხელახლა სცდის მოლოდინში მყოფი დანიშვნების გაუქმებას. კავშირი იშლება მას შემდეგ, რაც ეს დანიშვნები დასრულდება.

## Cache ტომები {#cache-volumes}

შეინახეთ Xcode, მოდულის და Gradle cache-ები და სხვა დირექტორიები სამუშაოებს შორის <.localized_link href="/guides/features/runners/cache-volumes">cache ტომების</.localized_link> გამოყენებით. დაამატეთ ისინი checkout-ის შემდეგ და მათი გამომყენებელი ბრძანებების წინ.

### Merge request პაიპლაინები {#merge-request-pipelines}

პროექტის push, განრიგის და web პაიპლაინები ინახავენ ცვლილებებს cache ტომებში. Merge request პაიპლაინები იყენებენ cache-ს და ინახავენ ცვლილებებს მხოლოდ მაშინ, როცა კავშირს აქვს API წვდომის ტოკენი:

1. GitLab-ში შექმენით პროექტის ან ჯგუფის წვდომის ტოკენი **Reporter** როლით და `read_api` სკოპით. ჯგუფის ტოკენი ფარავს ჯგუფის ყველა პროექტს, რომელიც მუშაობს Tuist runner-ებზე.
2. **Settings → Integrations** განყოფილებაში, ჩასვით ის GitLab CI ბარათზე **API access token** ველში და აირჩიეთ **Save changes**.

შემდეგ Tuist კითხულობს თითოეული merge request პაიპლაინის merge request-ს. პროექტის საკუთარი ბრენჩიდან გახსნილი merge request-ების პაიპლაინები ინახავენ ცვლილებებს merge request-ის საწყის ბრენჩის ქვეშ, ამიტომ runner პროფილის <.localized_link href="/guides/features/runners/cache-volumes#choose-which-branches-save">branch settings</.localized_link> ვრცელდება ამ ბრენჩზე. Fork-ებიდან წამოსული merge request-ები არასდროს ინახავენ. თუ Tuist ვერ კითხულობს merge request-ს, სამუშაო მაინც სრულდება და იყენებს cache-ს, მაგრამ მისი ცვლილებები იკარგება.
