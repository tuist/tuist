# GitLab CI {#gitlab-ci}

> [!IMPORTANT]
> **მხოლოდ მოწვევით**
>
> Tuist Runners ამჟამად მხოლოდ მოწვევითაა ხელმისაწვდომი. [დაგვიკავშირდით](mailto:contact@tuist.dev), რათა მიიღოთ წვდომა თქვენს ანგარიშზე.

თქვენი პაიპლაინები GitLab-ში რჩება. Tuist უზრუნველყოფს იზოლირებულ Linux ან macOS მანქანას თითოეული სამუშაოსთვის და აგზავნის ლოგებსა და შედეგებს GitLab-სა და Tuist-ის დაფაზე. საჭიროა GitLab 19.3 ან უფრო ახალი ვერსია. მხარდაჭერილია GitLab.com და საჯარო HTTPS-ით ხელმისაწვდომი თვითმართვადი ინსტანციები.

1. **შექმენით GitLab runner.** თქვენი პროექტის **Settings → CI/CD → Runners** განყოფილებაში შექმენით პროექტის runner. ასევე შეგიძლიათ გამოიყენოთ ჯგუფური runner. დაამატეთ ყველა Tuist პროფილის ლეიბლი, რომელთაც გსურთ გამოყენება როგორც runner-ის ტეგები, მაგალითად `tuist-linux` და `tuist-macos`, და გათიშეთ **Run untagged jobs**. შეინახეთ ავთენტიფიკაციის ტოკენი, რომელსაც GitLab აჩვენებს და რომელიც იწყება `glrt-`-ით. თქვენ არ გჭირდებათ runner-ის ინსტალაცია თქვენს მანქანაზე.
2. **ერთხელ დააკავშირეთ Tuist-თან.** **Settings → Integrations** განყოფილებაში აირჩიეთ **Connect** GitLab CI ბარათზე. შეიყვანეთ თქვენი GitLab URL და runner-ის ავთენტიფიკაციის ტოკენი. კავშირს შეუძლია მოემსახუროს სხვადასხვა პროფილის მქონე სამუშაოებს. ტოკენები ინახება დაშიფრული სახით და აღარასდროს ჩანს. სურვილისამებრ, დაამატეთ API წვდომის ტოკენი, რათა merge request პაიპლაინებმა შეძლონ cache volumes-ის შენახვა; იხილეთ [Merge request pipelines](#merge-request-pipelines).
3. **აირჩიეთ მანქანა თითოეულ სამუშაოში.** დააყენეთ ზუსტად ერთი <.localized_link href="/guides/features/runners/profiles">Tuist პროფილის ლეიბლი</.localized_link> სამუშაოს `tags`-ში. სხვა ტეგები დაშვებულია, იმ პირობით, რომ დარეგისტრირებულ GitLab runner-საც აქვს ისინი:

   ```yaml
   # .gitlab-ci.yml
   linux-check:
     tags: [tuist-linux]
     script:
       - uname -a

   test:
     tags: [tuist-macos]
     script:
       - tuist test
     retry:
       max: 2
       when: runner_system_failure
   ```

4. **გაუშვით და დააკვირდით.** Tuist იწყებს გამოკითხვას ერთი წუთის განმავლობაში. სამუშაოები ჩნდება **Runners** განყოფილებაში, GitLab-ის სამუშაოზე, ლოგებზე და მანქანის მეტრიკებზე დამბრუნებელი ბმულით. GitLab იღებს ლოგებს სამუშაოს შესრულებისას; Tuist იღებს დამალულ ლოგს მისი დასრულების შემდეგ.

Tuist კითხულობს `CI_JOB_TAGS` თითოეული დანიშვნისგან და ადგენს პროფილს დაკავშირებულ Tuist ანგარიშში. ის არ ადგენს მანქანას `CI_RUNNER_TAGS`-დან და არ იყენებს ნაგულისხმევ პროფილს. დაკარგული, უცნობი ან მრავალი Tuist პროფილის ტეგი აცდენს მიღებულ სამუშაოს ახსნით მის GitLab ლოგში. არ გადააწეროთ `CI_JOB_TAGS` თქვენს პაიპლაინის ცვლადებში.

## შესრულების გარემო {#execution-environment}

სამუშაოები იყენებენ GitLab-ის **shell executor**-ს იზოლირებულ მანქანაში. Checkout, CI ცვლადები, `before_script`, `script`, `after_script`, არტეფაქტები და გაუქმება მუშავდება GitLab Runner-ის მიერ. პაიპლაინის `image:` და `services:` პარამეტრები არ აკონფიგურირებენ ამ shell გარემოს; გამოიყენეთ <.localized_link href="/guides/features/runners/profiles">runner image</.localized_link>-ზე ინსტალირებული ინსტრუმენტები ან დააინსტალირეთ ისინი თქვენს სკრიპტში.

გამოყენებადი runner-ის ავთენტიფიკაციის ტოკენი რჩება Tuist სერვერზე. მანქანები იღებენ მხოლოდ მათთვის დანიშნული სამუშაოს კრედენციალებს. Cache-signing ნებართვები ამჟამად შეჩერებულია GitLab სამუშაოებისთვის. მორგებული Linux cache volumes ამოწმებენ სამუშაოს იდენტურობას და შენახვის ნებართვას GitLab-ის API-ს მეშვეობით; გადაწერადი CI ცვლადები არ ამყარებენ ნდობას.

GitLab ნიშნავს სამუშაოს როგორც მიმდინარეს და იწყებს მის დროის ამოწურვას, როგორც კი Tuist მიიღებს მას. სანამ Tuist-ის მიერ უკვე მიღებული სამუშაოები იყენებენ თქვენი ანგარიშის კონკურენტულობის ლიმიტს, დამატებითი სამუშაოები რჩებიან მოლოდინის რეჟიმში GitLab-ში. მიღებული სამუშაო ელოდება მანქანას მისი სამუშაოს დროის ამოწურვამდე, მაქსიმუმ 12 საათი. თუ ამ დროისთვის მანქანა არ გახდება ხელმისაწვდომი, Tuist აცდენს დანიშვნას `runner_system_failure`-ით და ზემოთ მოცემული ხელახლა ცდის პოლიტიკა საშუალებას აძლევს GitLab-ს ხელახლა სცადოს ის. იგივე პოლიტიკა ვრცელდება დაკარგულ runner მანქანაზე.

## ტოკენების როტაცია და გათიშვა {#rotating-tokens-and-disconnecting}

განაახლეთ კავშირის ტოკენები და აირჩიეთ **Save changes** მათი როტაციისთვის. ტოკენის ველის ცარიელად დატოვება ინარჩუნებს არსებულ კრედენციალს.

**Disconnect** აჩერებს მიღებას და აცდენს მოლოდინში მყოფ დანიშვნებს. მიმდინარე სამუშაოები გრძელდება საკუთარი კრედენციალებით. თუ GitLab-თან მიღწევა შეუძლებელია, Tuist ინარჩუნებს გათიშულ კავშირს, სანამ ხელახლა სცადის მოლოდინში მყოფი დანიშვნების გაუქმებას. კავშირი იშლება მას შემდეგ, რაც ეს დანიშვნები დასრულდება.

## Cache volumes {#cache-volumes}

შეინარჩუნეთ Xcode, მოდულის და Gradle cache-ები და სხვა დირექტორიები სამუშაოებს შორის <.localized_link href="/guides/features/runners/cache-volumes">cache volumes</.localized_link>-ის გამოყენებით. დაამატეთ ისინი checkout-ის შემდეგ და მათი გამომყენებელი ბრძანებების წინ.

### Merge request პაიპლაინები {#merge-request-pipelines}

პროექტის push, დაგეგმილი და web პაიპლაინები ინახავენ ცვლილებებს cache volumes-ში. Merge request პაიპლაინები იყენებენ cache-ს და ინახავენ ცვლილებებს მხოლოდ მაშინ, როდესაც კავშირს აქვს API წვდომის ტოკენი:

1. GitLab-ში შექმენით პროექტის ან ჯგუფის წვდომის ტოკენი **Reporter** როლით და `read_api` სკოპით. ჯგუფური ტოკენი ფარავს ჯგუფის ყველა პროექტს, რომელიც მუშაობს Tuist runners-ზე.
2. **Settings → Integrations** განყოფილებაში ჩასვით ის **API access token** ველში GitLab CI ბარათზე და აირჩიეთ **Save changes**.

Tuist შემდეგ კითხულობს თითოეული merge request პაიპლაინის merge request-ს. პროექტის საკუთარი ბრენჩიდან გახსნილი merge request-ების პაიპლაინები ინახავენ ცვლილებებს merge request-ის source ბრენჩის ქვეშ, ამიტომ runner პროფილის <.localized_link href="/guides/features/runners/cache-volumes#choose-which-branches-save">branch settings</.localized_link> ვრცელდება ამ ბრენჩზე. Fork-ებიდან მოსული merge request-ები არასდროს ინახავენ. თუ Tuist ვერ კითხულობს merge request-ს, სამუშაო მაინც მუშაობს და იყენებს cache-ს, მაგრამ მისი ცვლილებები იკარგება.
