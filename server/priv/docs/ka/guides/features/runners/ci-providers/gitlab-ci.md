# GitLab CI {#gitlab-ci}

<!-- @snippet: ./_invite-only -->

თქვენი პაიპლაინები რჩება GitLab-ში. Tuist თითოეული სამუშაოსთვის უზრუნველყოფს იზოლირებულ Linux ან macOS მანქანას და აგზავნის ლოგებსა და შედეგებს როგორც GitLab-ში, ისე Tuist-ის დაშბორდზე. საჭიროა GitLab 19.3 ან უფრო ახალი ვერსია. მხარდაჭერილია GitLab.com და საჯარო HTTPS-ით ხელმისაწვდომი თვითმართვადი ინსტანციები.

1. **შექმენით GitLab რანერი.** თქვენი პროექტის **Settings → CI/CD → Runners** განყოფილებაში შექმენით პროექტის რანერი. ასევე შეგიძლიათ გამოიყენოთ ჯგუფის რანერი. დაამატეთ ყველა Tuist პროფილის ლეიბლი, რომელთაც გსურთ გამოყენება რანერის ტეგებად, მაგალითად `tuist-linux` და `tuist-macos`, და გათიშეთ **Run untagged jobs**. შეინახეთ GitLab-ის მიერ ნაჩვენები აუთენტიკაციის ტოკენი, რომელიც იწყება `glrt-`-ით. თქვენ არ გჭირდებათ რანერის ინსტალაცია თქვენს საკუთარ მანქანაზე.
2. **ერთხელ დაუკავშირდით Tuist-ს.** **Settings → Integrations** განყოფილებაში, GitLab CI ბარათზე აირჩიეთ **Connect**. შეიყვანეთ თქვენი GitLab URL და რანერის აუთენტიკაციის ტოკენი. კავშირი შეუძლია მოემსახუროს სხვადასხვა პროფილის მქონე სამუშაოებს. ტოკენები ინახება დაშიფრული სახით და აღარასდროს გამოჩნდება. სურვილისამებრ, დაამატეთ API წვდომის ტოკენი, რათა merge request პაიპლაინებმა შეძლონ cache volume-ების შენახვა; იხილეთ [Merge request pipelines](#merge-request-pipelines).
3. **აირჩიეთ მანქანა თითოეულ სამუშაოში.** სამუშაოს `tags`-ში მიუთითეთ ზუსტად ერთი <.localized_link href="/guides/features/runners/profiles">Tuist profile label</.localized_link>. სხვა ტეგები დაშვებულია, იმ პირობით, რომ რეგისტრირებულ GitLab რანერსაც აქვს ისინი:

   ```yaml
   # .gitlab-ci.yml
   linux-check:
     tags: [tuist-linux]
     script:
       - uname -a

   test:
     tags: [tuist-macos]
     script:
       - tuist test
     retry:
       max: 2
       when: runner_system_failure
   ```

4. **გაუშვით და დააკვირდით.** Tuist ერთი წუთის განმავლობაში იწყებს გამოკითხვას. სამუშაოები ჩნდება **Runners** განყოფილებაში, GitLab სამუშაოზე, ლოგებზე და მანქანის მეტრიკებზე დამბრუნებელი ბმულით. GitLab იღებს ლოგებს სამუშაოს შესრულებისას; Tuist იღებს დამალულ ლოგს მისი დასრულების შემდეგ.

Tuist კითხულობს `CI_JOB_TAGS`-ს თითოეული დანიშვნისგან და ახდენს პროფილის ამოცნობას დაკავშირებულ Tuist ანგარიშში. ის არ განსაზღვრავს მანქანას `CI_RUNNER_TAGS`-დან და არ იყენებს ნაგულისხმევ პროფილს. ნაკლული, უცნობი ან მრავალი Tuist პროფილის ტეგი აფერხებს მიღებულ სამუშაოს და GitLab ლოგში ტოვებს ახსნას. არ გადაწეროთ `CI_JOB_TAGS` თქვენს პაიპლაინის ცვლადებში.

## შესრულების გარემო {#execution-environment}

სამუშაოები იყენებენ GitLab-ის **shell executor**-ს იზოლირებულ მანქანაში. Checkout, CI ცვლადები, `before_script`, `script`, `after_script`, არტიფაქტები და გაუქმება მუშავდება GitLab Runner-ის მიერ. პაიპლაინის `image:` და `services:` პარამეტრები არ აკონფიგურირებენ ამ shell გარემოს; გამოიყენეთ <.localized_link href="/guides/features/runners/profiles">runner image</.localized_link>-ზე ინსტალირებული ინსტრუმენტები ან დააინსტალირეთ ისინი თქვენს სკრიპტში.

გამოყენებადი რანერის აუთენტიკაციის ტოკენი რჩება Tuist სერვერზე. მანქანები იღებენ მხოლოდ მათთვის მინიჭებული სამუშაოს სერთიფიკატებს. Cache-signing უფლებები ამჟამად შეჩერებულია GitLab სამუშაოებისთვის. მორგებული Linux cache volume-ები ამოწმებენ სამუშაოს იდენტურობას და შენახვის უფლებას GitLab-ის API-ს მეშვეობით; გადაწერადი CI ცვლადები არ ქმნიან ნდობას.

GitLab სამუშაოს აღნიშნავს როგორც შესრულებადს და იწყებს მის таймаუტს, როგორც კი Tuist მიიღებს მას. სანამ Tuist-ის მიერ უკვე მიღებული სამუშაოები იყენებენ თქვენი ანგარიშის კონკურენტულობის ლიმიტს, დამატებითი სამუშაოები რჩებიან მოლოდინის რეჟიმში GitLab-ში. მიღებული სამუშაო ელოდება მანქანას მისი სამუშაოს таймаუტის ფარგლებში, მაქსიმუმ 12 საათის განმავლობაში. თუ ამ დროისთვის მანქანა არ გახდება ხელმისაწვდომი, Tuist აფერხებს დანიშვნას `runner_system_failure`-ით და ზემოთ მოცემული განმეორების პოლიტიკა საშუალებას აძლევს GitLab-ს განაახლოს ის. იგივე პოლიტიკა ვრცელდება დაკარგულ რანერის მანქანაზეც.

## ტოკენების როტაცია და გათიშვა {#rotating-tokens-and-disconnecting}

განაახლეთ კავშირის ტოკენები და აირჩიეთ **Save changes** მათი როტაციისთვის. ტოკენის ველის ცარიელად დატოვება ინარჩუნებს არსებულ სერთიფიკატს.

**Disconnect** აჩერებს მიღებას და აფერხებს მოლოდინში მყოფ დანიშვნებს. შესრულებადი სამუშაოები გრძელდება თავიანთი სერთიფიკატებით. თუ GitLab-თან წვდომა შეუძლებელია, Tuist ინარჩუნებს გათიშულ კავშირს, სანამ ცდილობს მოლოდინში მყოფი დანიშვნების გაუქმებას. კავშირი იშლება მას შემდეგ, რაც ეს დანიშვნები დასრულდება.

## Cache volumes {#cache-volumes}

შეინახეთ Xcode, მოდულის და Gradle cache-ები და სხვა დირექტორიები სამუშაოებს შორის <.localized_link href="/guides/features/runners/cache-volumes">cache volumes</.localized_link>-ის გამოყენებით. დაამატეთ ისინი checkout-ის შემდეგ და იმ ბრძანებებამდე, რომლებიც მათ იყენებენ.

### Merge request პაიპლაინები {#merge-request-pipelines}

პროექტის push, schedule და web პაიპლაინები ინახავენ ცვლილებებს cache volume-ებში. Merge request პაიპლაინები იყენებენ cache-ს და ინახავენ ცვლილებებს მხოლოდ მაშინ, როცა კავშირს აქვს API წვდომის ტოკენი:

1. GitLab-ში შექმენით პროექტის ან ჯგუფის წვდომის ტოკენი **Reporter** როლით და `read_api` scope-ით. ჯგუფის ტოკენი ფარავს ჯგუფის ყველა პროექტს, რომელიც მუშაობს Tuist რანერებზე.
2. **Settings → Integrations** განყოფილებაში, ჩასვით ის GitLab CI ბარათზე **API access token** ველში და აირჩიეთ **Save changes**.

შემდეგ Tuist კითხულობს თითოეული merge request პაიპლაინის merge request-ს. პროექტის საკუთარი ბრენჩიდან გახსნილი merge request-ების პაიპლაინები ინახავენ ცვლილებებს merge request-ის საწყისი ბრენჩის ქვეშ, ამიტომ რანერის პროფილის <.localized_link href="/guides/features/runners/cache-volumes#choose-which-branches-save">branch settings</.localized_link> ვრცელდება ამ ბრენჩზე. Fork-ებიდან მოსული merge request-ები არასდროს ინახავენ. თუ Tuist ვერ კითხულობს merge request-ს, სამუშაო მაინც შესრულდება და გამოიყენებს cache-ს, მაგრამ მისი ცვლილებები გაუქმდება.
