# GitLab CI {#gitlab-ci}

> [!IMPORTANT]
> **მხოლოდ მიწვევით**
>
> Tuist Runners ამჟამად მხოლოდ მიწვევითაა ხელმისაწვდომი. [დაგვიკავშირდით](mailto:contact@tuist.dev), რათა მოითხოვოთ თქვენი ანგარიშისთვის წვდომა.

თქვენი პაიპლაინები GitLab-ში რჩება. Tuist უზრუნველყოფს იზოლირებულ Linux ან macOS მანქანას თითოეული სამუშაოსთვის და აგზავნის ლოგებსა და შედეგებს GitLab-სა და Tuist-ის დაშბორდზე. საჭიროა GitLab 19.3 ან უფრო ახალი ვერსია. მხარდაჭერილია GitLab.com და საჯარო HTTPS-ით ხელმისაწვდომი თვითმართვადი ინსტანციები.

1. **შექმენით GitLab-ის რანერი.** თქვენი პროექტის **Settings → CI/CD → Runners** განყოფილებაში შექმენით პროექტის რანერი. ასევე შეგიძლიათ გამოიყენოთ ჯგუფური რანერი. დაამატეთ ყველა Tuist-ის პროფილის ლეიბლი, რომელიც გსურთ გამოიყენოთ როგორც რანერის ტეგები, მაგალითად `tuist-linux` და `tuist-macos`, და გათიშეთ **Run untagged jobs**. შეინახეთ ავთენტიკაციის ტოკენი, რომელსაც GitLab აჩვენებს და რომელიც იწყება `glrt-`-ით. თქვენ არ გჭირდებათ რანერის დაყენება თქვენს საკუთარ მანქანაზე.
2. **ერთხელ დააკავშირეთ Tuist-თან.** **Settings → Integrations** განყოფილებაში, GitLab CI ბარათზე აირჩიეთ **Connect**. შეიყვანეთ თქვენი GitLab URL და რანერის ავთენტიკაციის ტოკენი. კავშირი შეუძლია ემსახუროს სხვადასხვა პროფილის მქონე სამუშაოებს. ტოკენები ინახება დაშიფრული და აღარასდროს ჩანს. სურვილისამებრ, დაამატეთ API წვდომის ტოკენი, რათა merge request-ების პაიპლაინებმა შეძლონ ქეშის ტომების შენახვა; იხილეთ [Merge request pipelines](#merge-request-pipelines).
3. **აირჩიეთ მანქანა თითოეულ სამუშაოში.** სამუშაოს `tags`-ში მიუთითეთ ზუსტად ერთი <.localized_link href="/guides/features/runners/profiles">Tuist-ის პროფილის ლეიბლი</.localized_link>. სხვა ტეგები დაშვებულია, იმ პირობით, რომ რეგისტრირებულ GitLab-ის რანერსაც აქვს ისინი:

   ```yaml
   # .gitlab-ci.yml
   linux-check:
     tags: [tuist-linux]
     script:
       - uname -a

   test:
     tags: [tuist-macos]
     script:
       - tuist test
     retry:
       max: 2
       when: runner_system_failure
   ```

4. **გაგზავნეთ და დააკვირდით.** Tuist იწყებს გამოკითხვას ერთი წუთის განმავლობაში. სამუშაოები ჩანს **Runners** განყოფილებაში, ბმულით GitLab-ის სამუშაოზე, ლოგებითა და მანქანის მეტრიკებით. GitLab იღებს ლოგებს სამუშაოს შესრულებისას; Tuist იღებს დამალულ ლოგს მისი დასრულებისას.

Tuist კითხულობს `CI_JOB_TAGS` თითოეული დანიშვნისგან და ადგენს პროფილს დაკავშირებულ Tuist-ის ანგარიშში. ის არ განსაზღვრავს მანქანას `CI_RUNNER_TAGS`-დან და არ იყენებს ნაგულისხმევ პროფილს. ნაკლული, უცნობი ან მრავალი Tuist-ის პროფილის ტეგი აცდენს მიღებულ სამუშაოს ახსნით მის GitLab-ის ლოგში. არ გადაწეროთ `CI_JOB_TAGS` თქვენს პაიპლაინის ცვლადებში.

## შესრულების გარემო {#execution-environment}

სამუშაოები იყენებენ GitLab-ის **shell executor**-ს იზოლირებულ მანქანაში. Checkout, CI ცვლადები, `before_script`, `script`, `after_script`, არტეფაქტები და გაუქმება მუშავდება GitLab Runner-ის მიერ. პაიპლაინის `image:` და `services:` პარამეტრები არ აკონფიგურირებენ ამ shell გარემოს; გამოიყენეთ <.localized_link href="/guides/features/runners/profiles">რანერის გამოსახულებაზე</.localized_link> დაყენებული ინსტრუმენტები ან დააყენეთ ისინი თქვენს სკრიპტში.

გამოყენებადი რანერის ავთენტიკაციის ტოკენი რჩება Tuist-ის სერვერზე. მანქანები იღებენ მხოლოდ მათთვის მინიჭებული სამუშაოს კრედენციალებს. ქეშის ხელმოწერის უფლებები ამჟამად შეჩერებულია GitLab-ის სამუშაოებისთვის. მორგებული Linux ქეშის ტომები ამოწმებენ სამუშაოს იდენტურობას და შენახვის უფლებას GitLab-ის API-ს მეშვეობით; გადაწერადი CI ცვლადები არ ამყარებენ ნდობას.

GitLab ნიშნავს სამუშაოს როგორც შესრულებადს და იწყებს მის დროის ლიმიტს, როგორც კი Tuist იღებს მას. სანამ Tuist-ის მიერ უკვე მიღებული სამუშაოები იყენებენ თქვენი ანგარიშის პარალელურობის ლიმიტს, დამატებითი სამუშაოები რჩებიან მოლოდინის რეჟიმში GitLab-ში. მიღებული სამუშაო ელოდება მანქანას მისი სამუშაოს დროის ლიმიტამდე, მაქსიმუმ 12 საათი. თუ ამ დროისთვის მანქანა არ გახდება ხელმისაწვდომი, Tuist აცდენს დანიშვნას `runner_system_failure`-ით, და ზემოთ მოყვანილი ხელახლა ცდის პოლიტიკა საშუალებას აძლევს GitLab-ს ხელახლა სცადოს ის. იგივე პოლიტიკა ვრცელდება დაკარგულ რანერის მანქანაზე.

## ტოკენების განახლება და გათიშვა {#rotating-tokens-and-disconnecting}

განაახლეთ კავშირის ტოკენები და აირჩიეთ **Save changes** მათი როტაციისთვის. ტოკენის ველის ცარიელად დატოვება ინარჩუნებს არსებულ კრედენციალს.

**Disconnect** აჩერებს მიღებას და აცდენს მოლოდინში მყოფ დანიშვნებს. შესრულებადი სამუშაოები გრძელდება საკუთარი კრედენციალებით. თუ GitLab-თან მიღწევა შეუძლებელია, Tuist ინარჩუნებს გათიშულ კავშირს, სანამ ხელახლა ცდილობს მოლოდინში მყოფი დანიშვნების გაუქმებას. კავშირი იშლება მას შემდეგ, რაც ეს დანიშვნები დასრულდება.

## ქეშის ტომები {#cache-volumes}

შეინარჩუნეთ Xcode, მოდულის და Gradle ქეშები და სხვა დირექტორიები სამუშაოებს შორის <.localized_link href="/guides/features/runners/cache-volumes">ქეშის ტომების</.localized_link> მეშვეობით. დაამატეთ ისინი checkout-ის შემდეგ და მათი გამოყენების ბრძანებებამდე.

### Merge request პაიპლაინები {#merge-request-pipelines}

პროექტის push, დაგეგმილი და web პაიპლაინები ინახავენ ცვლილებებს ქეშის ტომებში. Merge request პაიპლაინები იყენებენ ქეშს და ინახავენ ცვლილებებს მხოლოდ მაშინ, როცა კავშირს აქვს API წვდომის ტოკენი:

1. GitLab-ში შექმენით პროექტის ან ჯგუფის წვდომის ტოკენი **Reporter** როლით და `read_api` სკოპით. ჯგუფური ტოკენი ფარავს ჯგუფის ყველა პროექტს, რომელიც მუშაობს Tuist რანერებზე.
2. **Settings → Integrations** განყოფილებაში, ჩასვით ის GitLab CI ბარათზე **API access token** ველში და აირჩიეთ **Save changes**.

Tuist შემდეგ კითხულობს თითოეული merge request პაიპლაინის merge request-ს. პროექტის საკუთარი ბრენჩიდან გახსნილი merge request-ების პაიპლაინები ინახავენ ცვლილებებს merge request-ის საწყის ბრენჩის ქვეშ, ასე რომ რანერის პროფილის <.localized_link href="/guides/features/runners/cache-volumes#choose-which-branches-save">ბრენჩის პარამეტრები</.localized_link> ვრცელდება იმ ბრენჩზე. Fork-ებიდან შემოსული merge request-ები არასდროს ინახავენ. თუ Tuist ვერ კითხულობს merge request-ს, სამუშაო მაინც სრულდება და იყენებს ქეშს, მაგრამ მისი ცვლილებები იკარგება.
