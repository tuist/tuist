# Struo-ს ტესტების დაყოფა {#struo-test-sharding}

<a id="once-test-sharding"></a>

როდესაც თქვენი ტესტების ნაკრები ერთ მანქანას აღემატება, Struo-მ შეუძლია Tuist-ს სთხოვოს, აღმოჩენილი ტესტების პარტიები CI სამუშაოებს შორის გაანაწილოს. სამუშაოები თავიანთ დავალებებს Struo-ს მეშვეობით ასრულებენ, ხოლო Tuist მათ ანგარიშებს ერთ ტესტების გაშვებაში აერთიანებს.

> [!IMPORTANT]
> **მოთხოვნები**
>
> - დაასრულეთ <.localized_link href="/guides/get-started/struo-project">დაწყება Struo-თან</.localized_link>.
> - გამოიყენეთ [Struo 1.0.0](https://github.com/tuist/struo/releases/tag/1.0.0) ან უფრო გვიანი ვერსია, `struo query test-plan --shards` და `struo test --shard-plan` ფლაგებით.
> - უზრუნველყავით სრული აღმოჩენა შერჩეული ტესტების მიზნებისთვის და იგივე checkout და ტესტირების გარემო ხელმისაწვდომი იყოს სამუშაოებზე.

Tuist CLI შემფუთავი არ არის საჭირო. Struo იყენებს თავის ნატიურ Tuist პროვაიდერს და სერთიფიკატებს.

## აღმოაჩინეთ თქვენი ტესტები {#discover-your-tests}

გაუშვით შერჩეული ტესტები დაგეგმვამდე აღმოჩენის დასადგენად:

```bash
struo test MyTests --format json
```

ხელმისაწვდომი პარტიების დეტალიზაცია დამოკიდებულია გამშვებზე. ზოგიერთი ტესტის მიზანი მხარს უჭერს ფაილის ან შემთხვევის პარტიებს; სხვები რჩებიან მიზნის დონეზე. აღმოჩენისა და პარტიებად დაყოფის შესაძლებლობებისთვის მიჰყევით [Struo-ს ტესტირების სახელმძღვანელოს](https://struo.run/docs/guide/graph/testing).

## შექმენით ჰოსტინგული გეგმა {#create-a-hosted-plan}

დაგეგმვის სამუშაოში გამოიყენეთ ბმული, რომელიც გაზიარებულია ამ CI შესრულების მიერ:

```bash
struo query test-plan --shards 4 --reference "$CI_EXECUTION_ID" --format json
```

პასუხი შეიცავს ჰოსტინგული გეგმის ID-ს და სამუშაოების რეალურ ინდექსებს:

```json
{"shard_plan_id":"<UUID>","shards":[0,1,2,3]}
```

ააგეთ თქვენი CI მატრიცა `shards`-დან, ნაცვლად იმის ვარაუდისა, რომ ის ოთხ ჩანაწერს შეიცავს. ცარიელი გეგმა აბრუნებს ცარიელ ID-ს და მასივს, ამიტომ არცერთი სამუშაო არ უნდა დაიწყოს. გადაეცით `--target` გეგმის შესავიწროებლად ან გაიმეორეთ `--changed-path` Struo-ს გრაფზე დაფუძნებული შერჩევის გამოსაყენებლად.

ბმული ნაგულისხმევად არის `TUIST_SHARD_REFERENCE` ან აღმოჩენილი CI გაშვება. გადაეცით ის ცალსახად, როდესაც გარემოს არ აქვს მხარდაჭერილი CI იდენტიფიკატორი.

## გაუშვით თითოეული ნაწილი {#execute-each-shard}

მიეცით ყოველ სამუშაოს დაბრუნებული გეგმის ID და მისი საკუთარი ინდექსი:

```bash
struo test --shard-plan "$SHARD_PLAN_ID" --shard-index "$SHARD_INDEX" --jobs 4
```

ალტერნატიულად, დააყენეთ `TUIST_SHARD_PLAN_ID` და `TUIST_SHARD_INDEX`. სამუშაოები ჩამოტვირთავენ ზუსტად UUID-ით შეკრულ გეგმას და შეასრულებენ მხოლოდ მათთვის განკუთვნილ პარტიებს. ცარიელი დანიშვნა ვერაფერს გაუშვებს; დაკარგული შედეგები, წარუმატებელი პროცესები და შეწყვეტილი სამუშაო ვერ გაივლიან განაწილებას.

ეს ანაწილებს ტესტების გეგმას, არა წინასწარ კომპილირებულ ტესტ-ბილდის არქივს. მოამზადეთ საჭირო წყაროები, ინსტრუმენტები და აღმოჩენა სამუშაოებზე; გაზიარებულმა ქეშირებამ შეიძლება თავიდან აიცილოს შესაბამისი ბილდის სამუშაოს გამეორება.

## განმეორებითი გაშვებები და შედეგები {#reruns-and-results}

განმეორებითი გაშვებისთვის, გაზარდეთ `--shard-attempt`, ან დააყენეთ `TUIST_SHARD_ATTEMPT`. წინააღმდეგ შემთხვევაში, Struo იყენებს GitHub გაშვების მცდელობას, შემდეგ ნაგულისხმევად 1-ს. `--shard-report-revision` ნაგულისხმევად არის 0 და შეიძლება გაიზარდოს, როდესაც იგივე მცდელობის ფარგლებში ასწორებთ ანგარიშს. ეს მრიცხველები ცალკეა ტესტის განმეორებებისგან.

გახსენით **ტესტები → ნაწილები** გეგმის, ბალანსისა და მოხსენებული სამუშაოების შესამოწმებლად, შემდეგ გახსენით გაერთიანებული ტესტების გაშვება ინდივიდუალური შედეგებისთვის. Struo-ს დაგეგმვის ერთეულები მონიშნულია როგორც **პარტიები**; შემთხვევები ინარჩუნებენ თავიანთ ნატიურ მიზნის, სუიტისა და ტესტის სახელებს.
