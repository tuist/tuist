# Struo-ს ტესტების დაყოფა {#struo-test-sharding}

<a id="once-test-sharding"></a>

როდესაც თქვენი ტესტების ნაკრები ერთ მანქანას სცდება, Struo-მ შეუძლია Tuist-ს სთხოვოს აღმოჩენილი ტესტების პარტიების განაწილება CI-ის სამუშაოებზე. სამუშაოები ასრულებენ თავიანთ დავალებებს Struo-ს მეშვეობით, ხოლო Tuist აერთიანებს მათ ანგარიშებს ერთ ტესტების გაშვებად.

> [!IMPORTANT]
> **მოთხოვნები**
>
> - დაასრულეთ <.localized_link href="/guides/get-started/struo-project">Struo-ს დაწყება</.localized_link>.
> - გამოიყენეთ [Struo 1.0.0](https://github.com/tuist/struo/releases/tag/1.0.0) ან უფრო ახალი ვერსია, `struo query test-plan --shards` და `struo test --shard-plan` პარამეტრებით.
> - უზრუნველყავით სრული აღმოჩენა შერჩეული ტესტების მიზნებისთვის და იგივე checkout და ტესტირების გარემო ხელმისაწვდომი იყოს სამუშაოებზე.

Tuist CLI-ის გარსაცმის გამოყენება არ არის საჭირო. Struo იყენებს თავის ნატიურ Tuist პროვაიდერს და რწმუნებათა სიგელებს.

## აღმოაჩინეთ თქვენი ტესტები {#discover-your-tests}

გაუშვით შერჩეული ტესტები დაგეგმვამდე აღმოჩენის დასადგენად:

```bash
struo test MyTests --format json
```

ხელმისაწვდომი პარტიების დეტალიზაცია დამოკიდებულია გამშვებზე. ზოგიერთი ტესტის მიზანი მხარს უჭერს ფაილის ან შემთხვევის პარტიებს; სხვები რჩებიან მიზნის დონეზე. მიჰყევით [Struo-ს ტესტირების სახელმძღვანელოს](https://struo.run/docs/guide/graph/testing) აღმოჩენისა და პარტიებად დაყოფის შესაძლებლობებისთვის.

## შექმენით ჰოსტინგული გეგმა {#create-a-hosted-plan}

დაგეგმვის სამუშაოში გამოიყენეთ მითითება, რომელიც გაზიარებულია ამ CI-ის შესრულების მიერ:

```bash
struo query test-plan --shards 4 --reference "$CI_EXECUTION_ID" --format json
```

პასუხი შეიცავს ჰოსტინგული გეგმის ID-ს და სამუშაოების რეალურ ინდექსებს:

```json
{"shard_plan_id":"<UUID>","shards":[0,1,2,3]}
```

ააწყვეთ თქვენი CI-ის მატრიცა `shards`-დან, ნაცვლად იმის ვარაუდისა, რომ ის ოთხ ჩანაწერს შეიცავს. ცარიელი გეგმა აბრუნებს ცარიელ ID-ს და მასივს, ამიტომ არ არის საჭირო სამუშაოების დაწყება. გადაეცით `--target` გეგმის შესავიწროებლად ან გაიმეორეთ `--changed-path` Struo-ს გრაფზე დაფუძნებული შერჩევის გამოყენებისთვის.

მითითება ნაგულისხმევად იღებს `TUIST_SHARD_REFERENCE`-ს ან აღმოჩენილ CI-ის გაშვებას. გადაეცით ის ცალსახად, როდესაც გარემოს არ აქვს მხარდაჭერილი CI-ის იდენტიფიკატორი.

## გაუშვით თითოეული ნაწილი {#execute-each-shard}

მიეცით ყოველ სამუშაოს დაბრუნებული გეგმის ID და მისი საკუთარი ინდექსი:

```bash
struo test --shard-plan "$SHARD_PLAN_ID" --shard-index "$SHARD_INDEX" --jobs 4
```

ალტერნატიულად, დააყენეთ `TUIST_SHARD_PLAN_ID` და `TUIST_SHARD_INDEX`. სამუშაოები ჩამოტვირთავენ ზუსტად UUID-ით შეკრულ გეგმას და გაუშვებენ მხოლოდ მათთვის განკუთვნილ პარტიებს. ცარიელი დანიშვნა არაფერს გაუშვებს; დაკარგული შედეგები, წარუმატებელი პროცესები და შეწყვეტილი სამუშაო ვერ გაივლიან განაწილებას.

ეს ანაწილებს ტესტების გეგმას, არა წინასწარ კომპილირებულ ტესტ-ბილდის არქივს. მოამზადეთ საჭირო წყაროები, ინსტრუმენტები და აღმოჩენა სამუშაოებზე; გაზიარებულმა ქეშირებამ შეიძლება თავიდან აიცილოს შესაბამისი ბილდის სამუშაოს განმეორება.

## განმეორებითი გაშვებები და შედეგები {#reruns-and-results}

განმეორებითი გაშვებისთვის, გაზარდეთ `--shard-attempt`, ან დააყენეთ `TUIST_SHARD_ATTEMPT`. წინააღმდეგ შემთხვევაში, Struo იყენებს GitHub-ის გაშვების მცდელობას, შემდეგ ნაგულისხმევად 1-ს. `--shard-report-revision` ნაგულისხმევად 0-ია და შეიძლება გაიზარდოს, როდესაც ასწორებთ ანგარიშს იმავე მცდელობის ფარგლებში. ეს მრიცხველები ცალკეა ტესტის განმეორებებისგან.

გახსენით **ტესტები → ნაწილები** გეგმის, ბალანსისა და მოხსენებული სამუშაოების შესამოწმებლად, შემდეგ გახსენით გაერთიანებული ტესტების გაშვება ინდივიდუალური შედეგებისთვის. Struo-ს დაგეგმვის ერთეულები მონიშნულია როგორც **პარტიები**; შემთხვევები ინარჩუნებენ თავიანთ ნატიურ მიზანს, სიუიტსა და ტესტის სახელებს.
