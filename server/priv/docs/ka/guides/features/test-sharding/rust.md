# Rust ტესტების დაყოფა {#rust-test-sharding}

Tuist ანაწილებს Cargo-ს ტესტის სამიზნეებს CI მუშაკებზე ისტორიული სამიზნე ხანგრძლივობების გამოყენებით. ერთეულოვანი ტესტების სამიზნეები, ინტეგრაციული ტესტების სამიზნეები და თითოეული ბიბლიოთეკის doctests ცალკე მოდულებია. ერთი სამიზნის ფარგლებში არსებული ტესტები ერთად რჩება.

> [!IMPORTANT]
> **მოთხოვნები**
>
> - დააკონფიგურირეთ <.localized_link href="/guides/features/test-insights/rust">Rust Test Insights</.localized_link> და გაიარეთ CLI-ის ავთენტიკაცია დაგეგმვის სამუშაოზე და მუშაკებზე.
> - აირჩიეთ ერთი პაკეტი, ვორქსპეისში `-p <package>`-ის გამოყენებით. მრავალი პაკეტის დაყოფა არ არის მხარდაჭერილი.
> - გამოიყენეთ იგივე რევიზია, Rust-ის ინსტრუმენტების ჯაჭვი, პაკეტის შერჩევა, ფუნქციები და ტესტის ფილტრები ყოველ სამუშაოში.

## გეგმის შექმნა {#create-a-plan}

დაამატეთ shard-ების რაოდენობა `--no-run`-ში, რათა დააკომპილიროთ და ჩამოთვალოთ სამიზნეები ტესტების შესრულების გარეშე:

```sh
TUIST_SHARD_REFERENCE=my-ci-run tuist cargo test -p store --no-run --shard-max 4
```

ბრძანება ბეჭდავს JSON-ს, რომელიც შეიცავს `shard_plan_id`-ს და ნულიდან დაწყებულ `shards` მასივს. GitHub Actions-ში ის ასევე წერს `shard-plan-id`-ს და `shards`-ს `GITHUB_OUTPUT`-ში. ცხადი მითითების გარეშე, Tuist გამოჰყავს მას მხარდაჭერილი CI გარემოდან.

| პარამეტრი | აღწერა |
| --- | --- |
| `--shard-max N` | Shard-ების მაქსიმალური რაოდენობა |
| `--shard-min N` | Shard-ების მინიმალური რაოდენობა |
| `--shard-total N` | ზუსტი რაოდენობა, ხელმისაწვდომი სამიზნეების ფარგლებში |
| `--shard-max-duration N` | Shard-ის მაქსიმალური ხანგრძლივობა მილიწამებში |

გამოიყენეთ `--shard-total` ცალკე ან გააერთიანეთ `--shard-min` და `--shard-max`. ისტორიული ხანგრძლივობების გარეშე, დამგეგმავი იყენებს სამიზნეების ნაგულისხმევ შეფასებებს. ჩვეულებრივი `--no-run` shard-ის პარამეტრების გარეშე რჩება მხოლოდ აგების ბრძანებად.

## თითოეული shard-ის შესრულება {#execute-each-shard}

დააყენეთ გეგმის ID და shard-ის ინდექსი თითოეულ მუშაკზე, შემდეგ გამოიყენეთ იგივე Cargo ტესტის არგუმენტები:

```sh
TUIST_SHARD_PLAN_ID=<plan-id> TUIST_SHARD_INDEX=0 tuist cargo test -p store
```

ალტერნატიულად, დააყენეთ `TUIST_SHARD_REFERENCE` დაგეგმვის სამუშაოს მითითებაზე გეგმის ID-ის გადაცემის ნაცვლად. Tuist იღებს განაწილებას და სთხოვს Cargo-ს მხოლოდ ამ სამიზნეების შესრულებას. არასწორი ან შეუთავსებელი განაწილებები აფერხებენ ბრძანებას ყველა ტესტის გაშვების ნაცვლად. ცარიელი განაწილებები არ ასრულებენ ტესტებს. მუშაკების შედეგები უკავშირდება გეგმას Test Insights-ში და <.localized_link href="/guides/features/test-insights/flaky-tests/rust#quarantining">კარანტინი</.localized_link> ვრცელდება თითოეულ shard-ში.

## შეზღუდვები {#limits}

ეს არის სამიზნის დონის დაყოფა, არა ერთჯერადი აგების განაწილება. თითოეულ მუშაკს სჭირდება წყაროს კოპია და თავად აგებს საკუთარ სამიზნეებს; <.localized_link href="/guides/features/cache/rust">Cargo კომპილაციის ქეში</.localized_link> შეუძლია ხელახლა გამოიყენოს შესაბამისი კომპილაციის შედეგები. Tuist არ ტვირთავს ტესტის შესრულებად ფაილებს და არ ითხოვს სხვა Rust ტესტის გამშვებს.

დაყოფა მოითხოვს ერთ შერჩეულ პაკეტს. მრავალპაკეტიანი ბრძანების შევიწროვებამ შეიძლება შეცვალოს Cargo-ს გაერთიანებული დამოკიდებულების ფუნქციები, ამიტომ Tuist უარყოფს მას სხვა ფუნქციების გრაფით ტესტების გაშვების ნაცვლად. დაგეგმეთ თითოეული პაკეტი ცალკე, სანამ მრავალპაკეტიანი დაყოფა არ იქნება მხარდაჭერილი.

დაყოფა მოითხოვს სტანდარტულ libtest harness-ებს და ჩაჭერილ ნაგულისხმევ გამოტანას. Quiet, verbose, alternate-format, uncaptured-output და custom-harness ბრძანებები უარყოფილია. თუ Cargo ვერ ახდენს სამიზნის უნიკალურ იდენტიფიცირებას, აირჩიეთ ზუსტი ვორქსპეისის პაკეტი `-p <package>`-ით. დამოკიდებულების პაკეტები, ვერსიით კვალიფიცირებული სელექტორები, პაკეტის/სამიზნის სახელის გლობები და Cargo-ს ღამის `-C` პარამეტრი არ არის მხარდაჭერილი დაყოფისთვის. შეინარჩუნეთ ტესტის შერჩევა იდენტური დაგეგმვასა და შესრულებას შორის.
