# Rust ტესტების დაყოფა {#rust-test-sharding}

Tuist ანაწილებს Cargo-ს ტესტის მიზნებს CI სამუშაოებზე ისტორიული ხანგრძლივობების გამოყენებით. ერთეულოვანი ტესტების მიზნები, ინტეგრაციული ტესტების მიზნები და თითოეული ბიბლიოთეკის doctests ცალკე მოდულებია. ერთი მიზნის ფარგლებში არსებული ტესტები ერთად რჩება.

> [!IMPORTANT]
> **მოთხოვნები**
>
> - დააკონფიგურირეთ <.localized_link href="/guides/features/test-insights/rust">Rust Test Insights</.localized_link> და გაიარეთ CLI-ის ავთენტიკაცია დაგეგმვის სამუშაოსა და სამუშაოებზე.
> - აირჩიეთ ერთი პაკეტი, გამოიყენეთ `-p <package>` workspace-ში. მრავალი პაკეტის დაყოფა მხარდაჭერილი არ არის.
> - გამოიყენეთ იგივე რევიზია, Rust-ის ინსტრუმენტების ნაკრები, პაკეტის შერჩევა, ფუნქციები და ტესტის ფილტრები ყოველ სამუშაოში.

## შექმენით გეგმა {#create-a-plan}

დაამატეთ shard-ების რაოდენობა `--no-run`-ს, რათა კომპილირდეს და ჩამოთვლილ იქნას მიზნები ტესტების შესრულების გარეშე:

```sh
TUIST_SHARD_REFERENCE=my-ci-run tuist cargo test -p store --no-run --shard-max 4
```

ბრძანება ბეჭდავს JSON-ს, რომელიც შეიცავს `shard_plan_id`-ს და ნულიდან დაწყებულ `shards` მასივს. GitHub Actions-ში ის ასევე წერს `shard-plan-id`-ს და `shards`-ს `GITHUB_OUTPUT`-ში. აშკარა მითითების გარეშე, Tuist გამოიყვანს მას მხარდაჭერილი CI გარემოდან.

| პარამეტრი | აღწერა |
| --- | --- |
| `--shard-max N` | Shard-ების მაქსიმალური რაოდენობა |
| `--shard-min N` | Shard-ების მინიმალური რაოდენობა |
| `--shard-total N` | ზუსტი რაოდენობა, ხელმისაწვდომი მიზნების ფარგლებში |
| `--shard-max-duration N` | მიზნის მაქსიმალური shard-ის ხანგრძლივობა მილიწამებში |

გამოიყენეთ `--shard-total` ცალკე ან გააერთიანეთ `--shard-min` და `--shard-max`. ისტორიული ხანგრძლივობების გარეშე, დამგეგმავი იყენებს მიზნის ნაგულისხმევ შეფასებებს. ჩვეულებრივი `--no-run` shard-ის პარამეტრების გარეშე რჩება მხოლოდ აგების ბრძანებად.

## შეასრულეთ თითოეული shard {#execute-each-shard}

დააყენეთ გეგმის ID და shard-ის ინდექსი თითოეულ სამუშაოზე, შემდეგ გამოიყენეთ იგივე Cargo ტესტის არგუმენტები:

```sh
TUIST_SHARD_PLAN_ID=<plan-id> TUIST_SHARD_INDEX=0 tuist cargo test -p store
```

ალტერნატიულად, დააყენეთ `TUIST_SHARD_REFERENCE` დაგეგმვის სამუშაოს მითითებაზე გეგმის ID-ის გადაცემის ნაცვლად. Tuist იღებს დანიშნულებას და სთხოვს Cargo-ს მხოლოდ ამ მიზნების შესრულება. არასწორი ან შეუთავსებელი დანიშნულებები აფრთხობენ ბრძანებას ყველა ტესტის გაშვების ნაცვლად. ცარიელი დანიშნულებები არ ასრულებენ ტესტებს. შედეგები სამუშაოებიდან დაკავშირებულია გეგმასთან Test Insights-ში, და <.localized_link href="/guides/features/test-insights/flaky-tests/rust#quarantining">კარანტინი</.localized_link> ვრცელდება თითოეულ shard-ში.

## შეზღუდვები {#limits}

ეს არის მიზნის დონის დაყოფა, არა ერთხელ აგების განაწილება. თითოეულ სამუშაოს სჭირდება წყაროს ჩეკაუტი და თავისი მიზნების აგება; <.localized_link href="/guides/features/cache/rust">Cargo კომპილაციის ქეში</.localized_link> შეუძლია ხელახლა გამოიყენოს შესაბამისი კომპილაციის გამონატანები. Tuist არ ტვირთავს ტესტის executable-ებს და არ საჭიროებს სხვა Rust ტესტის გამშვებს.

დაყოფას სჭირდება ერთი შერჩეული პაკეტი. მრავალი პაკეტის ბრძანების შევიწროვებამ შეიძლება შეცვალოს Cargo-ს გაერთიანებული დამოკიდებულების ფუნქციები, ამიტომ Tuist უარყოფს მას სხვა ფუნქციების გრაფით ტესტების გაშვების ნაცვლად. დაგეგმეთ თითოეული პაკეტი ცალკე, სანამ მრავალი პაკეტის დაყოფა მხარდაჭერილი იქნება.

დაყოფას სჭირდება სტანდარტული libtest harness-ები და ჩაჭერილი ნაგულისხმევი გამონატანი. ჩუმი, verbose, ალტერნატიული ფორმატი, არაჩაჭერილი გამონატანი და custom-harness ბრძანებები უარყოფილია. თუ Cargo ვერ შეძლებს მიზნის უნიკალურ იდენტიფიცირებას, აირჩიეთ ზუსტი workspace პაკეტი `-p <package>`-ით. დამოკიდებულების პაკეტები, ვერსიით კვალიფიცირებული სელექტორები, პაკეტის/მიზნის სახელის globs და Cargo-ს ღამის `-C` პარამეტრი მხარდაჭერილი არ არის დაყოფისთვის. შეინარჩუნეთ ტესტის შერჩევა იდენტური დაგეგმვასა და შესრულებას შორის.
