# Once-ის ტესტების შარდინგი {#once-test-sharding}

როდესაც თქვენი ტესტების ნაკრები ერთ მანქანაზე აღარ ეტევა, Once-ს შეუძლია Tuist-ს სთხოვოს აღმოჩენილი ტესტების პაკეტების განაწილება CI worker-ებზე. Worker-ები ასრულებენ თავიანთ დავალებებს Once-ის მეშვეობით, ხოლო Tuist აერთიანებს მათ ანგარიშებს ერთ ტესტების გაშვებაში.

> [!IMPORTANT]
> **მოთხოვნები**
>
> - დაასრულეთ <.localized_link href="/guides/get-started/once-project">Once-თან მუშაობის დაწყება</.localized_link>.
> - გამოიყენეთ Once-ის ის ვერსია, რომელიც უზრუნველყოფს `once query test-plan --shards` და `once test --shard-plan` ფლაგებს. Once 0.71.0 მხარს უჭერს მხოლოდ პორტატულ გეგმებს და არა ამ ჰოსტინგულ სამუშაო პროცესს.
> - შეარჩიეთ ტესტების მიზნების სრული აღმოჩენა და დარწმუნდით, რომ worker-ებზე ხელმისაწვდომია იგივე checkout და ტესტირების გარემო.

Tuist CLI wrapper არ არის საჭირო. Once იყენებს თავის ნატიურ Tuist პროვაიდერს და სერთიფიკატებს.

## აღმოაჩინეთ თქვენი ტესტები {#discover-your-tests}

გაუშვით შერჩეული ტესტები დაგეგმვამდე აღმოჩენის დასადგენად:

```bash
once test MyTests --format json
```

ხელმისაწვდომი პაკეტების დეტალიზაცია დამოკიდებულია runner-ზე. ზოგიერთი ტესტის მიზანი მხარს უჭერს ფაილის ან შემთხვევის პაკეტებს; სხვები რჩებიან მიზნის დონეზე. მიჰყევით [Once-ის ტესტირების სახელმძღვანელოს](https://buildonce.dev/docs/guide/graph/testing) აღმოჩენისა და პაკეტირების შესაძლებლობებისთვის.

## შექმენით ჰოსტინგული გეგმა {#create-a-hosted-plan}

დაგეგმვის სამუშაოში გამოიყენეთ მითითება, რომელიც გაზიარებულია ამ CI შესრულების მიერ:

```bash
once query test-plan --shards 4 --reference "$CI_EXECUTION_ID" --format json
```

პასუხი შეიცავს ჰოსტინგული გეგმის ID-ს და worker-ების რეალურ ინდექსებს:

```json
{"shard_plan_id":"<UUID>","shards":[0,1,2,3]}
```

ააწყვეთ თქვენი CI მატრიცა `shards`-დან, ნაცვლად იმის ვარაუდისა, რომ ის ოთხ ჩანაწერს შეიცავს. ცარიელი გეგმა აბრუნებს ცარიელ ID-ს და მასივს, ამიტომ worker-ების გაშვება არ არის საჭირო. გადაეცით `--target` გეგმის შესავიწროებლად ან გაიმეორეთ `--changed-path` Once-ის გრაფზე დაფუძნებული შერჩევის გამოსაყენებლად.

მითითება ნაგულისხმევად იღებს `TUIST_SHARD_REFERENCE`-ს ან აღმოჩენილ CI გაშვებას. გადაეცით ის ცალსახად, როდესაც გარემოს არ აქვს მხარდაჭერილი CI იდენტიფიკატორი.

## გაუშვით თითოეული შარდი {#execute-each-shard}

მიეცით ყოველ worker-ს დაბრუნებული გეგმის ID და მისი საკუთარი ინდექსი:

```bash
once test --shard-plan "$SHARD_PLAN_ID" --shard-index "$SHARD_INDEX" --jobs 4
```

ალტერნატიულად, დააყენეთ `TUIST_SHARD_PLAN_ID` და `TUIST_SHARD_INDEX`. Worker-ები ჩამოტვირთავენ ზუსტად UUID-ით შეკრულ გეგმას და გაუშვებენ მხოლოდ მათთვის განკუთვნილ პაკეტებს. ცარიელი დავალება არაფერს გაუშვებს; დაკარგული შედეგები, შეცდომები პროცესებში და შეწყვეტილი სამუშაო ვერ გადალახავს პარტიციას.

ეს ანაწილებს ტესტების გეგმას და არა წინასწარ კომპილირებულ ტესტ-ბილდის არქივს. მოამზადეთ საჭირო წყაროები, ინსტრუმენტები და აღმოჩენა worker-ებზე; გაზიარებულმა ქეშირებამ შეიძლება თავიდან აიცილოს შესაბამისი ბილდის სამუშაოს განმეორება.

## განმეორებითი გაშვებები და შედეგები {#reruns-and-results}

განმეორებითი გაშვებისთვის გაზარდეთ `--shard-attempt`, ან დააყენეთ `TUIST_SHARD_ATTEMPT`. სხვა შემთხვევაში Once იყენებს GitHub გაშვების მცდელობას, შემდეგ კი ნაგულისხმევად 1-ს. `--shard-report-revision` ნაგულისხმევად არის 0 და შეიძლება გაიზარდოს, როდესაც იმავე მცდელობის ფარგლებში ასწორებთ ანგარიშს. ეს მრიცხველები ცალკეა ტესტის განმეორებებისგან.

გახსენით **ტესტები → შარდები** გეგმის, ბალანსის და მოხსენებული worker-ების შესამოწმებლად, შემდეგ კი გახსენით გაერთიანებული ტესტების გაშვება ინდივიდუალური შედეგებისთვის. Once-ის დაგეგმვის ერთეულები მონიშნულია როგორც **პაკეტები**; შემთხვევები ინარჩუნებენ თავიანთ ნატიურ მიზანს, სიუიტს და ტესტის სახელებს.
