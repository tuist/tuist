# Elixir ტესტების დაყოფა {#elixir-test-sharding}

Tuist-ის Hex პაკეტი შეიცავს ჩაშენებულ მხარდაჭერას Elixir პროექტის ტესტების დაყოფისთვის. ის იყენებს Tuist სერვერს, რათა შექმნას დაბალანსებული დაყოფის გეგმები ისტორიული დროის მონაცემებზე დაყრდნობით, და აკომპილირებს თქვენს პროექტს ერთხელ, რათა ყოველმა გამშვებმა (runner) პირდაპირ გადავიდეს ტესტების გაშვებაზე.

> [!IMPORTANT]
> **მოთხოვნები**
>
> - დაასრულეთ <.localized_link href="/guides/get-started/elixir-project">გაზიარებული Elixir კონფიგურაცია</.localized_link> თქვენი CI დაყოფის სამუშაოების კონფიგურაციამდე

## როგორ მუშაობს {#how-it-works}

ტესტების დაყოფა მიჰყვება ორეტაპიან სამუშაო პროცესს:

1. **აგების ეტაპი:** Tuist აკომპილირებს თქვენს პროექტს ტესტირებისთვის, აღრიცხავს თქვენს ტესტ ფაილებს და ქმნის **დაყოფის გეგმას** სერვერზე. სერვერი იყენებს ბოლო 30 დღის ისტორიულ ტესტების დროის მონაცემებს, რათა გაანაწილოს ტესტები დაყოფებში ისე, რომ თითოეულ დაყოფას დაახლოებით ერთი და იგივე დრო დასჭირდეს. აგების ეტაპი ატვირთავს აგებას და გამოიტანს **დაყოფის მატრიცას**, რომელსაც თქვენი CI სისტემა იყენებს პარალელური გამშვებების შესაქმნელად.
2. **ტესტირების ეტაპი:** თითოეული CI გამშვები იღებს **დაყოფის ინდექსს**, ჩამოტვირთავს აგებას და ასრულებს მხოლოდ იმ ტესტებს, რომლებიც ამ დაყოფას მიეკუთვნება.

> [!NOTE]
> ჩარიცხულ Tuist Linux გამშვებებზე, დაყოფის აგებებს შეუძლიათ გამოიყენონ ლოკალური არტიფაქტების საცავი. ყველა დაყოფამ, რომელიც მოიხმარს ასეთ აგებას, უნდა გაეშვას ჩარიცხულ გამშვებებზე ერთსა და იმავე ადგილზე; ხელახლა გაუშვით აგება ლოკალური საცავის გათიშვით, როდესაც სამუშაო პროცესს სხვა გამშვებებზე გადაიტანთ.

ტესტები ნაწილდება ფაილების მიხედვით: ფაილის ყოველი ტესტი ერთსა და იმავე დაყოფაზე გაეშვება. ტესტებს, რომლებიც Tuist-მა ჯერ არ ნახა, ენიჭებათ სავარაუდო შეფასება, ამიტომ პროექტის პირველი გეგმები ნაკლებად დაბალანსებულია, ვიდრე მოგვიანებით შექმნილი.

## აგების ეტაპი {#build-phase}

მოამზადეთ ტესტების დაყოფები `tuist.test.build` ამოცანის გამოყენებით:

```sh
MIX_ENV=test mix compile --warnings-as-errors
MIX_ENV=test mix tuist.test.build --shard-max 5
```

აკომპილირეთ იმ ალიასის მეშვეობით, რომელიც გაზიარებულმა კონფიგურაციამ დააინსტალირა, სანამ დაყოფის ამოცანას გამოიძახებთ. ცივ checkout-ზე, Mix-ს შეუძლია დააკომპილიროს დამოკიდებულებები `tuist.test.build`-ის აღმოჩენისას, სანამ Tuist-ის დამოკიდებულებების ქეში მათ აღდგენას მოასწრებს. ცხადი კომპილაცია ეშვება იმავე სატესტო გარემოში, რაშიც დაყოფის ამოცანა.

ეს ამოცანა:
1. აკომპილირებს პროექტს სატესტო გარემოში
2. ქმნის დაყოფის გეგმას Tuist სერვერზე ისტორიული დროის მონაცემების გამოყენებით
3. ატვირთავს აგებას, რათა დაყოფებმა ხელახლა არ დააკომპილირონ
4. გამოიტანს დაყოფის მატრიცას თქვენი CI სისტემისთვის

### აგების პარამეტრები {#build-options}

| პარამეტრი | აღწერა |
|--------|-------------|
| `--shard-max <N>` | დაყოფების მაქსიმალური რაოდენობა (ნაგულისხმები: 2) |
| `--shard-min <N>` | დაყოფების მინიმალური რაოდენობა |
| `--shard-total <N>` | დაყოფების ზუსტი რაოდენობა, დიაპაზონის ნაცვლად |
| `--shard-max-duration <MS>` | მიზნობრივი მაქსიმალური ხანგრძლივობა თითოეული დაყოფისთვის მილიწამებში |
| `--shard-reference <REF>` | სახელი, რომლითაც დაყოფები პოულობენ გეგმას |
| `--no-upload` | დაგეგმეთ დაყოფები აგების ატვირთვის გარეშე; თითოეული დაყოფა შემდეგ თავისთვის აკომპილირებს |

ყველა სხვა არგუმენტი გადაეცემა `mix compile`-ს.

დაყოფის მითითება ავტომატურად მიიღება CI გარემოს ცვლადებიდან (`GITHUB_RUN_ID`, `CI_PIPELINE_ID`, `CIRCLE_WORKFLOW_ID`, `BUILDKITE_BUILD_ID`) ან შეიძლება ცხადად დაყენდეს `TUIST_SHARD_REFERENCE` გარემოს ცვლადის მეშვეობით. ამ პროვაიდერების გარეთ თქვენ უნდა დააყენოთ ის მნიშვნელობაზე, რომელსაც ერთი pipeline-ის გაშვების აგების ეტაპი და დაყოფები იზიარებენ. GitHub Actions-ზე, მითითებები ასევე მოიცავს გაშვების მცდელობას: როდესაც ხელახლა უშვებთ მხოლოდ წარუმატებელ სამუშაოებს, გადაეცით საწყისი აგების სამუშაოს მითითება, ნაცვლად ახლის მიღებისა დაყოფის სამუშაოებში.

## ტესტირების ეტაპი {#test-phase}

როდესაც `TUIST_SHARD_INDEX` დაყენებულია, პაკეტი იღებს დაყოფის განაწილებას სერვერიდან, ჩამოტვირთავს აგებას და ასრულებს მხოლოდ მინიჭებულ სატესტო ფაილებს კომპილაციის გარეშე. ცივ გამშვებზე, მოამზადეთ SDK და ჩატვირთეთ მისი ბილიკები ამოცანის გამოძახებამდე:

```sh
MIX_ENV=test TUIST_SHARD_INDEX=0 mix do deps.compile tuist_ex --include-children + deps.loadpaths --no-compile --no-deps-check + tuist.test
```

SDK-ის კომპილაცია Mix-ის სამუშაო პროცესებში არ ტვირთავს მას მშობელ პროცესში. ცხადი `deps.loadpaths` ნაბიჯი ხელს უშლის ამოცანების აღმოჩენას, დააკომპილიროს დარჩენილი დამოკიდებულებები აგების ჩამოტვირთვამდე. ეს ერთბრძანებიანი ფორმა ინარჩუნებს თქვენი პროექტის ტესტების მომზადების ალიასს. თუ მისი კონფიგურაციის ბრძანებები იწვევენ კომპილაციას, გამოიყენეთ ქვემოთ მოცემული ცალკეული კონფიგურაციის თანმიმდევრობა.

ნებისმიერი სატესტო ფაილი ან დირექტორია, რომელსაც გადასცემთ, კიდევ უფრო ამცირებს დაყოფას: ეშვება მხოლოდ ის ფაილები, რომლებიც ერთდროულად არიან დაყოფაშიც და თქვენს შერჩევაშიც. დაყოფა, რომელიც საბოლოოდ ტესტების გარეშე რჩება, წარმატებით სრულდება.

ყველა დაყოფის შედეგები დაშბორდზე მოდის როგორც ერთი ტესტების გაშვება, და მისი **დაყოფები** სექცია აჩვენებს, თუ რამდენი ხანი დასჭირდა თითოეულს.

თუ კონფიგურაცია უნდა გაეშვას ტესტებამდე, ჯერ ჩამოტვირთეთ აგება აპლიკაციის გაშვების გარეშე:

```sh
MIX_ENV=test TUIST_SHARD_INDEX=0 mix do deps.compile tuist_ex --include-children + deps.loadpaths --no-compile --no-deps-check + tuist.test --prepare-only
```

გაუშვით თქვენი კონფიგურაცია ცალკეულ პროცესში კომპილაციის გათიშვით. მაგალითად, Ecto პროექტს შეუძლია შექმნას და გადაიტანოს (migrate) მისი მონაცემთა ბაზები შემდეგი გზით:

```sh
MIX_ENV=test mix run --no-start --no-compile --no-deps-check -e 'Mix.Tasks.Ecto.Create.run([]); Mix.Tasks.Ecto.Migrate.run([])'
```

შეინარჩუნეთ ნებისმიერი სხვა პროექტისთვის სპეციფიკური მომზადება ამ ეტაპზე. თქვენმა კომპილაციის ალიასმა ასევე უნდა გაითვალისწინოს `--no-compile` საწყისი სამუშაოების შესრულებამდე: Mix მხოლოდ ბოლო ამოცანას გადასცემს ფლაგებს სიის ალიასში, ამიტომ ადრეული უპირობო `deps.compile` მაინც ეშვება. იხილეთ დაცული ალიასი <.localized_link href="/guides/features/cache/elixir-advanced#manual-compile-integration">ხელით კომპილაციის ინტეგრაციაში</.localized_link>.

შემდეგ ჩატვირთეთ აღდგენილი SDK კომპილაციის გარეშე დაყოფის შესრულებამდე. ეს ასევე ხელს უშლის ამოცანების აღმოჩენას, დააკომპილიროს ბილიკის დამოკიდებულება, როდესაც მისი წყაროები უფრო ახალია, ვიდრე ჩამოტვირთული აგება:

```sh
MIX_ENV=test TUIST_SHARD_INDEX=0 mix do deps.loadpaths --no-compile --no-deps-check + tuist.test --no-download
```

ორივე ბრძანებას სჭირდება ერთი და იგივე დაყოფის მითითება. `--prepare-only` მოითხოვს ატვირთულ აგებას, და `--no-download` ვერ ხერხდება, თუ მომზადებული აპლიკაციის არტიფაქტი არ არსებობს. `--no-download` ცხადად ტოვებს თქვენი პროექტის ტესტების მომზადების ალიასს, ხელახალი ცდების ჩათვლით, და ბეჭდავს შეტყობინებას, როდესაც კონფიგურაციის ნაბიჯებს ტოვებს. ჩვეულებრივი გაშვებები ინარჩუნებენ თავიანთ ალიასებს, მაშინაც კი, როდესაც გადასცემთ `--no-compile --no-deps-check`. მონაცემთა ბაზების მიგრაციების ცალკეულ პროცესში შენარჩუნება ასევე თავიდან აცილებს მოდულის ხელახალი განსაზღვრის გაფრთხილებებს, როდესაც მიგრაციის რეგრესიის ტესტები თვითონ ტვირთავენ ამ მოდულებს.

სხვადასხვა გარემოების ტესტირებისას, გადაეცით სტაბილური `--scheme` იარლიყი, როგორიცაა `--scheme clickhouse-current` ან `--scheme clickhouse-floor`. სხვადასხვა იარლიყების შედეგები არ განიხილება როგორც იმავე კონფიგურაციის არასტაბილური ხელახალი გაშვებები.

### რა სჭირდება დაყოფებს {#what-the-shards-need}

ატვირთული აგება არის `_build/test` დირექტორია. თითოეულ დაყოფის გამშვებს კვლავ სჭირდება:
- იგივე გადმოწერა, რაც აგების ეტაპზე
- Elixir-ის და Erlang/OTP-ის იგივე ვერსიები
- დამოკიდებულებების წყაროები, `mix deps.get`-დან

umbrella პროექტის ფესვიდან დაყოფა ჯერჯერობით მხარდაჭერილი არ არის. ორივე ეტაპი გაუშვით მის ერთ-ერთ აპლიკაციაში.

## უწყვეტი ინტეგრაცია {#continuous-integration}

### GitHub Actions {#github-actions}

GitHub Actions-ზე აგების ეტაპი წერს დაყოფის ინდექსებს თავისი ნაბიჯის `matrix` შედეგად. გამოიყენეთ მატრიცის სტრატეგია დაყოფების პარალელურად გასაშვებად:

```yaml
name: Tests
on: [pull_request]

env:
  MIX_ENV: test
  TUIST_TOKEN: ${{ secrets.TUIST_TOKEN }}

jobs:
  build:
    name: Build test shards
    runs-on: ubuntu-latest
    outputs:
      matrix: ${{ steps.build.outputs.matrix }}
    steps:
      - uses: actions/checkout@v4
      - uses: erlef/setup-beam@v1
        with:
          elixir-version: '1.18'
          otp-version: '27'
      - run: mix deps.get
      - run: mix compile --warnings-as-errors
      - id: build
        run: mix tuist.test.build --shard-max 5

  test:
    name: "Shard #${{ matrix.shard }}"
    needs: build
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        shard: ${{ fromJson(needs.build.outputs.matrix).shard }}
    env:
      TUIST_SHARD_INDEX: ${{ matrix.shard }}
    steps:
      - uses: actions/checkout@v4
      - uses: erlef/setup-beam@v1
        with:
          elixir-version: '1.18'
          otp-version: '27'
      - run: mix deps.get
      - run: mix do deps.compile tuist_ex --include-children + deps.loadpaths --no-compile --no-deps-check + tuist.test --prepare-only
      # Ecto example: keep all project-specific test preparation here.
      # The project's compile alias must honor --no-compile (see above).
      - run: mix run --no-start --no-compile --no-deps-check -e 'Mix.Tasks.Ecto.Create.run([]); Mix.Tasks.Ecto.Migrate.run([])'
      - run: mix do deps.loadpaths --no-compile --no-deps-check + tuist.test --no-download
```

### სხვა პროვაიდერები {#other-providers}

GitHub Actions-ის გარეთ აგების ეტაპი წერს გეგმას `.tuist-shard-matrix.json`-ში:

```json
{
  "reference": "gitlab-1234",
  "shard_count": 2,
  "shards": [
    {
      "index": 0,
      "test_targets": ["MyApp.AccountsTest", "MyApp.CheckoutTest"],
      "estimated_duration_ms": 41000
    },
    {
      "index": 1,
      "test_targets": ["MyAppWeb.PageControllerTest"],
      "estimated_duration_ms": 39500
    }
  ]
}
```

გამოიყენეთ `shard_count` თქვენი პარალელური სამუშაოების დასაყენებლად და მიანიჭეთ თითოეულ სამუშაოს მისი `TUIST_SHARD_INDEX`, `0`-დან `shard_count - 1`-მდე. ისეთ პროვაიდერზე, საიდანაც Tuist არ იღებს მითითებას, ასევე მიანიჭეთ ყველა სამუშაოს ერთი და იგივე `TUIST_SHARD_REFERENCE`.
