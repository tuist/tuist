# Elixir-ის ტესტების დაყოფა {#elixir-test-sharding}

Tuist-ის Hex პაკეტი შეიცავს ჩაშენებულ მხარდაჭერას Elixir-ის პროექტის ტესტების დასაყოფად. ის იყენებს Tuist-ის სერვერს, რათა შექმნას დაბალანსებული დაყოფის გეგმები ისტორიული დროის მონაცემებზე დაყრდნობით, და კომპილირებს თქვენს პროექტს ერთხელ, რათა ყოველმა გამშვებმა პირდაპირ გადავიდეს ტესტების გაშვებაზე.

> [!IMPORTANT] REQUIREMENTS
> - დაასრულეთ <.localized_link href="/guides/get-started/elixir-project">Elixir-ის საერთო კონფიგურაცია</.localized_link> CI-ის დაყოფის ჯობების კონფიგურაციამდე

## როგორ მუშაობს {#how-it-works}

ტესტების დაყოფა მიჰყვება ორეტაპიან სამუშაო ნაკადს:

1. **კომპილაციის ეტაპი:** Tuist კომპილირებს თქვენს პროექტს ტესტირებისთვის, აღრიცხავს თქვენს ტესტ ფაილებს და ქმნის **დაყოფის გეგმას** სერვერზე. სერვერი იყენებს ბოლო 30 დღის ისტორიულ ტესტების დროის მონაცემებს, რათა გაანაწილოს ტესტები დაყოფებში ისე, რომ თითოეულ დაყოფას დაახლოებით ერთი და იგივე დრო დასჭირდეს. კომპილაციის ეტაპი ატვირთავს ბილდს და გამოიტანს **დაყოფის მატრიცას**, რომელსაც თქვენი CI სისტემა იყენებს პარალელური გამშვებების შესაქმნელად.
2. **ტესტირების ეტაპი:** თითოეული CI გამშვები იღებს **დაყოფის ინდექსს**, ჩამოტვირთავს ბილდს და ასრულებს მხოლოდ იმ ტესტებს, რომლებიც ამ დაყოფას ეკუთვნის.

ბილდის ატვირთვა ერთდროულად აგზავნის ოთხამდე ნაწილს და აკეთებს სამამდე მცდელობას დროებითი ნაწილის შეცდომებისთვის. რეგისტრირებულ Tuist Linux გამშვებებზე, დაყოფის ბილდებს შეუძლიათ გამოიყენონ ლოკალური არტიფაქტების საცავი. ყველა დაყოფამ, რომელიც იყენებს ასეთ ბილდს, უნდა გაეშვას ერთსა და იმავე ადგილმდებარეობაზე რეგისტრირებულ გამშვებებზე; გადაიტანეთ სამუშაო ნაკადი სხვა გამშვებებზე ბილდის ხელახლა გაშვებით ლოკალური საცავის გათიშული მდგომარეობით.

ტესტები ნაწილდება ფაილების მიხედვით: ერთი ფაილის ყველა ტესტი გაეშვება ერთსა და იმავე დაყოფაში. ტესტებს, რომლებიც Tuist-ს ჯერ არ უნახავს, ენიჭებათ სავარაუდო დრო, ამიტომ პროექტის პირველი გეგმები ნაკლებად დაბალანსებულია, ვიდრე მოგვიანებითი.

## კომპილაციის ეტაპი {#build-phase}

მოამზადეთ ტესტების დაყოფები `tuist.test.build` task-ის გამოყენებით:

```sh
MIX_ENV=test mix compile --warnings-as-errors
MIX_ENV=test mix tuist.test.build --shard-max 5
```

კომპილირება მოახდინეთ საერთო კონფიგურაციის მიერ დამონტაჟებული ალიასის მეშვეობით დაყოფის task-ის გამოძახებამდე. ცივ checkout-ზე, Mix-ს შეუძლია კომპილირება დამოკიდებულებების აღმოჩენის დროს `tuist.test.build`-ის, სანამ Tuist-ის დამოკიდებულებების ქეში მათ აღდგენას შეძლებს. ცალსახა კომპილირება გაეშვება იმავე ტესტის გარემოში, რაშიც დაყოფის task-ი.

ეს task-ი:
1. კომპილირებს პროექტს ტესტის გარემოში
2. ქმნის დაყოფის გეგმას Tuist-ის სერვერზე ისტორიული დროის მონაცემების გამოყენებით
3. ატვირთავს ბილდს, რათა დაყოფებმა ხელახლა არ კომპილირდნენ
4. გამოიტანს დაყოფის მატრიცას თქვენი CI სისტემისთვის

### კომპილაციის პარამეტრები {#build-options}

| პარამეტრი | აღწერა |
|--------|-------------|
| `--shard-max <N>` | დაყოფების მაქსიმალური რაოდენობა (ნაგულისხმები: 2) |
| `--shard-min <N>` | დაყოფების მინიმალური რაოდენობა |
| `--shard-total <N>` | დაყოფების ზუსტი რაოდენობა, დიაპაზონის ნაცვლად |
| `--shard-max-duration <MS>` | მიზნობრივი მაქსიმალური ხანგრძლივობა თითოეული დაყოფისთვის მილიწამებში |
| `--shard-reference <REF>` | სახელი, რომლითაც დაყოფები პოულობენ გეგმას |
| `--no-upload` | დაგეგმეთ დაყოფები ბილდის ატვირთვის გარეშე; თითოეული დაყოფა შემდეგ კომპილირდება თავისთვის |

ყველა სხვა არგუმენტი გადაეცემა `mix compile`-ს.

დაყოფის მითითება ავტომატურად მიიღება CI გარემოს ცვლადებიდან (`GITHUB_RUN_ID`, `CI_PIPELINE_ID`, `CIRCLE_WORKFLOW_ID`, `BUILDKITE_BUILD_ID`) ან შეიძლება ცალსახად დაყენდეს `TUIST_SHARD_REFERENCE` გარემოს ცვლადის მეშვეობით. ამ პროვაიდერების გარეთ თქვენ უნდა დააყენოთ ის მნიშვნელობა, რომელსაც იზიარებენ ერთი pipeline-ის გაშვების კომპილაციის ეტაპი და დაყოფები. GitHub Actions-ზე, მითითებები ასევე მოიცავს გაშვების მცდელობას: როდესაც ხელახლა აშვებთ მხოლოდ ჩავარდნილ ჯობებს, გადაეცით საწყისი ბილდის ჯობის მითითება ახლის გამოყვანის ნაცვლად დაყოფის ჯობებში.

## ტესტირების ეტაპი {#test-phase}

როდესაც `TUIST_SHARD_INDEX` დაყენებულია, პაკეტი იღებს დაყოფის განაწილებას სერვერიდან, ჩამოტვირთავს ბილდს და ასრულებს მხოლოდ მინიჭებულ ტესტ ფაილებს კომპილაციის გარეშე. ცივ გამშვებზე, მოამზადეთ SDK და ჩატვირთეთ მისი გზები task-ის გამოძახებამდე:

```sh
MIX_ENV=test TUIST_SHARD_INDEX=0 mix do deps.compile tuist_ex --include-children + deps.loadpaths --no-compile --no-deps-check + tuist.test
```

SDK-ის კომპილირება Mix-ის worker პროცესებში არ ტვირთავს მას მშობელ პროცესში. ცალსახა `deps.loadpaths` ეტაპი ხელს უშლის task-ის აღმოჩენას დარჩენილი დამოკიდებულებების კომპილირებაში ბილდის ჩამოტვირთვამდე. ეს ერთბრძანებიანი ფორმა ინარჩუნებს თქვენი პროექტის ტესტის მომზადების ალიასს. თუ მისი კონფიგურაციის ბრძანებები იწვევენ კომპილაციას, გამოიყენეთ ქვემოთ მოცემული ცალკეული კონფიგურაციის თანმიმდევრობა.

ნებისმიერი ტესტ ფაილი ან დირექტორია, რომელსაც გადასცემთ, კიდევ უფრო ამცირებს დაყოფას: გაეშვება მხოლოდ ის ფაილები, რომლებიც ერთდროულად არიან დაყოფაში და თქვენს შერჩევაში. დაყოფა, რომელსაც არ დარჩება ტესტები, წარმატებით სრულდება.

ყველა დაყოფის შედეგები დაშბორდზე ჩნდება ერთი ტესტების გაშვების სახით, და მისი **დაყოფები** სექცია აჩვენებს, თუ რამდენი დრო დასჭირდა თითოეულს.

თუ კონფიგურაცია უნდა გაეშვას ტესტებამდე, ჯერ ჩამოტვირთეთ ბილდი აპლიკაციის გაშვების გარეშე:

```sh
MIX_ENV=test TUIST_SHARD_INDEX=0 mix do deps.compile tuist_ex --include-children + deps.loadpaths --no-compile --no-deps-check + tuist.test --prepare-only
```

გაუშვით თქვენი კონფიგურაცია ცალკეულ პროცესში კომპილაციის გათიშული მდგომარეობით. მაგალითად, Ecto პროექტს შეუძლია შექმნას და მიგრაცია გაუკეთოს მის მონაცემთა ბაზებს:

```sh
MIX_ENV=test mix run --no-start --no-compile --no-deps-check -e 'Mix.Tasks.Ecto.Create.run([]); Mix.Tasks.Ecto.Migrate.run([])'
```

შეინარჩუნეთ ნებისმიერი სხვა პროექტისთვის სპეციფიკური მომზადება ამ ეტაპზე. თქვენმა კომპილაციის ალიასმა ასევე უნდა გაითვალისწინოს `--no-compile` bootstrap სამუშაოს შესრულებამდე: Mix მხოლოდ ბოლო task-ს გადასცემს ფლაგებს სიის ალიასში, ამიტომ ადრეული უპირობო `deps.compile` მაინც გაეშვება. იხილეთ დაცული ალიასი <.localized_link href="/guides/features/cache/elixir-advanced#manual-compile-integration">ხელით კომპილაციის ინტეგრაციაში</.localized_link>.

შემდეგ ჩატვირთეთ აღდგენილი SDK კომპილაციის გარეშე დაყოფის შესრულებამდე. ეს ასევე ხელს უშლის task-ის აღმოჩენას path დამოკიდებულების კომპილირებაში, როდესაც მისი წყაროები უფრო ახალია, ვიდრე ჩამოტვირთული ბილდი:

```sh
MIX_ENV=test TUIST_SHARD_INDEX=0 mix do deps.loadpaths --no-compile --no-deps-check + tuist.test --no-download
```

ორივე ბრძანებას სჭირდება ერთი და იგივე დაყოფის მითითება. `--prepare-only` მოითხოვს ატვირთულ ბილდს, და `--no-download` ვერ ხერხდება, თუ მომზადებული აპლიკაციის არტიფაქტი არ არის. `--no-download` ცალსახად ტოვებს თქვენი პროექტის ტესტის მომზადების ალიასს, ხელახლა ცდებზეც კი, და ბეჭდავს შეტყობინებას, როდესაც ტოვებს კონფიგურაციის ეტაპებს. ჩვეულებრივი გაშვებები ინარჩუნებენ თავიანთ ალიასებს, მაშინაც კი, როდესაც გადასცემთ `--no-compile --no-deps-check`. მონაცემთა ბაზის მიგრაციების ცალკეულ პროცესში შენარჩუნება ასევე თავიდან იცილებს მოდულის ხელახლა განსაზღვრის გაფრთხილებებს, როდესაც მიგრაციის რეგრესიის ტესტები თავად ტვირთავენ ამ მოდულებს.

სხვადასხვა გარემოს ტესტირებისას, გადაეცით სტაბილური `--scheme` ლეიბლი, როგორიცაა `--scheme clickhouse-current` ან `--scheme clickhouse-floor`. სხვადასხვა ლეიბლის შედეგები არ განიხილება ერთი და იგივე კონფიგურაციის არასტაბილური ხელახლა გაშვებებად.

### რა სჭირდებათ დაყოფებს {#what-the-shards-need}

ატვირთული ბილდი არის `_build/test` დირექტორია. თითოეულ დაყოფის გამშვებს კვლავ სჭირდება:
- იგივე ჩეკაუტი, რაც ბილდის ეტაპზე
- Elixir-ის და Erlang/OTP-ის იგივე ვერსიები
- დამოკიდებულობების წყაროები, `mix deps.get`-დან

დაყოფა umbrella პროექტის ფესვიდან ჯერჯერობით მხარდაჭერილი არ არის. გაუშვით ორივე ეტაპი მის ერთ-ერთ აპლიკაციაში.

## უწყვეტი ინტეგრაცია {#continuous-integration}

### GitHub Actions {#github-actions}

GitHub Actions-ზე ბილდის ეტაპი წერს დაყოფის ინდექსებს თავისი ეტაპის `matrix` გამოსავალში. გამოიყენეთ მატრიცის სტრატეგია დაყოფების პარალელურად გასაშვებად:

```yaml
name: Tests
on: [pull_request]

env:
  MIX_ENV: test
  TUIST_TOKEN: ${{ secrets.TUIST_TOKEN }}

jobs:
  build:
    name: Build test shards
    runs-on: ubuntu-latest
    outputs:
      matrix: ${{ steps.build.outputs.matrix }}
    steps:
      - uses: actions/checkout@v4
      - uses: erlef/setup-beam@v1
        with:
          elixir-version: '1.18'
          otp-version: '27'
      - run: mix deps.get
      - run: mix compile --warnings-as-errors
      - id: build
        run: mix tuist.test.build --shard-max 5

  test:
    name: "Shard #${{ matrix.shard }}"
    needs: build
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        shard: ${{ fromJson(needs.build.outputs.matrix).shard }}
    env:
      TUIST_SHARD_INDEX: ${{ matrix.shard }}
    steps:
      - uses: actions/checkout@v4
      - uses: erlef/setup-beam@v1
        with:
          elixir-version: '1.18'
          otp-version: '27'
      - run: mix deps.get
      - run: mix do deps.compile tuist_ex --include-children + deps.loadpaths --no-compile --no-deps-check + tuist.test --prepare-only
      # Ecto example: keep all project-specific test preparation here.
      # The project's compile alias must honor --no-compile (see above).
      - run: mix run --no-start --no-compile --no-deps-check -e 'Mix.Tasks.Ecto.Create.run([]); Mix.Tasks.Ecto.Migrate.run([])'
      - run: mix do deps.loadpaths --no-compile --no-deps-check + tuist.test --no-download
```

### სხვა პროვაიდერები {#other-providers}

GitHub Actions-ის გარეთ ბილდის ეტაპი წერს გეგმას `.tuist-shard-matrix.json`-ში:

```json
{
  "reference": "gitlab-1234",
  "shard_count": 2,
  "shards": [
    {
      "index": 0,
      "test_targets": ["MyApp.AccountsTest", "MyApp.CheckoutTest"],
      "estimated_duration_ms": 41000
    },
    {
      "index": 1,
      "test_targets": ["MyAppWeb.PageControllerTest"],
      "estimated_duration_ms": 39500
    }
  ]
}
```

გამოიყენეთ `shard_count` პარალელური სამუშაოების დასაყენებლად და მიანიჭეთ თითოეულ სამუშაოს მისი `TUIST_SHARD_INDEX`, `0`-დან `shard_count - 1`-მდე. პროვაიდერზე, საიდანაც Tuist არ იღებს მითითებას, ასევე მიანიჭეთ ყველა სამუშაოს ერთი და იგივე `TUIST_SHARD_REFERENCE`.
