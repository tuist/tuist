# Elixir ტესტების დაყოფა {#elixir-test-sharding}

Tuist Hex პაკეტი შეიცავს ჩაშენებულ მხარდაჭერას Elixir პროექტის ტესტების დასაყოფად. ის იყენებს Tuist სერვერს, რათა შექმნას დაბალანსებული დაყოფის გეგმები ისტორიული დროის მონაცემების საფუძველზე, და აკომპილირებს თქვენს პროექტს ერთხელ, რათა ყოველმა გამშვებმა პირდაპირ გადავიდეს ტესტების გაშვებაზე.

> [!IMPORTANT] REQUIREMENTS
> - დაასრულეთ <.localized_link href="/guides/get-started/elixir-project">Elixir-ის საერთო კონფიგურაცია</.localized_link> CI დაყოფის სამუშაოების კონფიგურაციამდე

## როგორ მუშაობს {#how-it-works}

ტესტების დაყოფა მიჰყვება ორეტაპიან სამუშაო ნაკადს:

1. **აკომპილაციის ეტაპი:** Tuist აკომპილირებს თქვენს პროექტს ტესტირებისთვის, აღრიცხავს თქვენს ტესტ ფაილებს და ქმნის **დაყოფის გეგმას** სერვერზე. სერვერი იყენებს ბოლო 30 დღის ისტორიულ ტესტის დროის მონაცემებს, რათა გაანაწილოს ტესტები დაყოფებში ისე, რომ თითოეულ დაყოფას დაახლოებით ერთი და იგივე დრო დასჭირდეს. აკომპილაციის ეტაპი ტვირთავს აწყობას და გამოიტანს **დაყოფის მატრიცას**, რომელსაც თქვენი CI სისტემა იყენებს პარალელური გამშვებების შესაქმნელად.
2. **ტესტირების ეტაპი:** თითოეული CI გამშვები იღებს **დაყოფის ინდექსს**, ჩამოტვირთავს აწყობას და ასრულებს მხოლოდ იმ ტესტებს, რომლებიც ამ დაყოფას მიეკუთვნება.

ტესტები ნაწილდება ფაილების მიხედვით: ფაილის ყოველი ტესტი ერთსა და იმავე დაყოფაზე სრულდება. ტესტებს, რომლებიც Tuist-მა ჯერ არ ნახა, ენიჭებათ სავარაუდო დრო, ამიტომ პროექტის პირველი გეგმები ნაკლებად დაბალანსებულია, ვიდრე მოგვიანებითი.

## აკომპილაციის ეტაპი {#build-phase}

მოამზადეთ ტესტების დაყოფები `tuist.test.build` ამოცანის გამოყენებით:

```sh
MIX_ENV=test mix compile --warnings-as-errors
MIX_ENV=test mix tuist.test.build --shard-max 5
```

აკომპილირეთ საერთო კონფიგურაციის მიერ დამონტაჟებული ალიასის მეშვეობით დაყოფის ამოცანის გამოძახებამდე. ცივ checkout-ზე, Mix-ს შეუძლია დამოკიდებულებების აკომპილირება `tuist.test.build`-ის აღმოჩენისას, სანამ Tuist-ის დამოკიდებულებების ქეშს მათი აღდგენის შანსი ექნება. ცხადი აკომპილაცია სრულდება იმავე სატესტო გარემოში, რაშიც დაყოფის ამოცანა.

ეს ამოცანა:
1. აკომპილირებს პროექტს სატესტო გარემოში
2. ქმნის დაყოფის გეგმას Tuist სერვერზე ისტორიული დროის მონაცემების გამოყენებით
3. ტვირთავს აწყობას, რათა დაყოფებმა ხელახლა არ აკომპილირონ
4. გამოიტანს დაყოფის მატრიცას თქვენი CI სისტემისთვის

### აკომპილაციის პარამეტრები {#build-options}

| პარამეტრი | აღწერა |
|--------|-------------|
| `--shard-max <N>` | დაყოფების მაქსიმალური რაოდენობა (ნაგულისხმები: 2) |
| `--shard-min <N>` | დაყოფების მინიმალური რაოდენობა |
| `--shard-total <N>` | დაყოფების ზუსტი რაოდენობა, დიაპაზონის ნაცვლად |
| `--shard-max-duration <MS>` | მიზნობრივი მაქსიმალური ხანგრძლივობა თითოეული დაყოფისთვის მილიწამებში |
| `--shard-reference <REF>` | სახელი, რომლითაც დაყოფები პოულობენ გეგმას |
| `--no-upload` | დაგეგმეთ დაყოფები აწყობის ატვირთვის გარეშე; თითოეული დაყოფა შემდეგ თავისთვის აკომპილირებს |

ყველა სხვა არგუმენტი გადაეცემა `mix compile`-ს.

დაყოფის მითითება ავტომატურად მიიღება CI გარემოს ცვლადებიდან (`GITHUB_RUN_ID`, `CI_PIPELINE_ID`, `CIRCLE_WORKFLOW_ID`, `BUILDKITE_BUILD_ID`) ან შეიძლება ცხადად დაყენდეს `TUIST_SHARD_REFERENCE` გარემოს ცვლადის მეშვეობით. ამ პროვაიდერების გარეთ თქვენ უნდა დააყენოთ ის მნიშვნელობაზე, რომელსაც აკომპილაციის ეტაპი და ერთი pipeline-ის გაშვების დაყოფები იზიარებენ. GitHub Actions-ზე, მითითებები ასევე მოიცავს გაშვების მცდელობას: როდესაც მხოლოდ ჩავარდნილი სამუშაოების ხელახლა გაშვება ხდება, გადაეცით საწყისი აწყობის სამუშაოს მითითება, ნაცვლად იმისა, რომ დაყოფის სამუშაოებში ახალი მიიღოთ.

## ტესტირების ეტაპი {#test-phase}

როდესაც `TUIST_SHARD_INDEX` დაყენებულია, პაკეტი იღებს დაყოფის განაწილებას სერვერიდან, ჩამოტვირთავს აწყობას და ასრულებს მხოლოდ მინიჭებულ ტესტ ფაილებს აკომპილაციის გარეშე. ცივ გამშვებზე, გაუშვით SDK-ის ინიციალიზაცია და ჩატვირთეთ მისი გზები ამოცანის გამოძახებამდე:

```sh
MIX_ENV=test TUIST_SHARD_INDEX=0 mix do deps.compile tuist_ex --include-children + deps.loadpaths --no-compile --no-deps-check + tuist.test
```

SDK-ის აკომპილირება Mix-ის სამუშაო პროცესებში არ ტვირთავს მას მშობელ პროცესში. ცხადი `deps.loadpaths` ნაბიჯი ხელს უშლის ამოცანის აღმოჩენას დარჩენილი დამოკიდებულებების აკომპილირებაში აწყობის ჩამოტვირთვამდე. ეს ერთბრძანებიანი ფორმა ინარჩუნებს თქვენი პროექტის ტესტის მომზადების ალიასს. თუ მისი კონფიგურაციის ბრძანებები იწვევენ აკომპილაციას, გამოიყენეთ ქვემოთ მოცემული ცალკეული კონფიგურაციის თანმიმდევრობა.

ნებისმიერი ტესტ ფაილი ან დირექტორია, რომელსაც გადასცემთ, კიდევ უფრო ავიწროებს დაყოფას: სრულდება მხოლოდ ის ფაილები, რომლებიც ერთდროულად არიან დაყოფაში და თქვენს შერჩევაში. დაყოფა, რომელიც საბოლოოდ ტესტების გარეშე რჩება, წარმატებით სრულდება.

ყველა დაყოფის შედეგები დაშბორდზე ერთიანი ტესტის გაშვების სახით ჩნდება, და მისი **დაყოფები** სექცია აჩვენებს, თუ რამდენი ხანი დასჭირდა თითოეულს.

თუ კონფიგურაცია უნდა შესრულდეს ტესტებამდე, ჯერ ჩამოტვირთეთ აწყობა აპლიკაციის გაშვების გარეშე:

```sh
MIX_ENV=test TUIST_SHARD_INDEX=0 mix do deps.compile tuist_ex --include-children + deps.loadpaths --no-compile --no-deps-check + tuist.test --prepare-only
```

გაუშვით თქვენი კონფიგურაცია ცალკე პროცესში აკომპილაციის გამორთვით. მაგალითად, Ecto პროექტს შეუძლია შექმნას და გადაიტანოს მისი მონაცემთა ბაზები შემდეგი ბრძანებით:

```sh
MIX_ENV=test mix run --no-start --no-compile --no-deps-check -e 'Mix.Tasks.Ecto.Create.run([]); Mix.Tasks.Ecto.Migrate.run([])'
```

შეინარჩუნეთ ნებისმიერი სხვა პროექტისთვის სპეციფიკური მომზადება ამ ეტაპზე. თქვენმა აკომპილაციის ალიასმა ასევე უნდა გაითვალისწინოს `--no-compile` ბუტსტრაპის სამუშაოს შესრულებამდე: Mix მხოლოდ ბოლო ამოცანას გადასცემს ფლაგებს სიის ალიასში, ამიტომ ადრეული უპირობო `deps.compile` მაინც სრულდება. იხილეთ დაცული ალიასი <.localized_link href="/guides/features/cache/elixir-advanced#manual-compile-integration">ხელით აკომპილაციის ინტეგრაციაში</.localized_link>.

შემდეგ ჩატვირთეთ აღდგენილი SDK აკომპილაციის გარეშე დაყოფის შესრულებამდე. ეს ასევე ხელს უშლის ამოცანის აღმოჩენას path დამოკიდებულების აკომპილირებაში, როდესაც მისი წყაროები უფრო ახალია, ვიდრე ჩამოტვირთული აწყობა:

```sh
MIX_ENV=test TUIST_SHARD_INDEX=0 mix do deps.loadpaths --no-compile --no-deps-check + tuist.test --no-download
```

ორივე ბრძანებას სჭირდება ერთი და იგივე დაყოფის მითითება. `--prepare-only` მოითხოვს ატვირთულ აწყობას, და `--no-download` ჩავარდება, თუ მომზადებული აპლიკაციის არტიფაქტი არ არის. `--no-download` ცხადად ტოვებს თქვენი პროექტის ტესტის მომზადების ალიასს, ხელახლა ცდებზეც კი, და აბეჭდებს შეტყობინებას, როდესაც კონფიგურაციის ნაბიჯებს ტოვებს. ჩვეულებრივი გაშვებები ინარჩუნებენ თავიანთ ალიასებს, მაშინაც კი, როდესაც გადასცემთ `--no-compile --no-deps-check`. მონაცემთა ბაზის მიგრაციების ცალკე პროცესში შენარჩუნება ასევე თავიდან აცილებს მოდულის ხელახლა განსაზღვრის გაფრთხილებებს, როდესაც მიგრაციის რეგრესიული ტესტები თავად ტვირთავენ ამ მოდულებს.

სხვადასხვა გარემოების ტესტირებისას, გადაეცით სტაბილური `--scheme` ლეიბლი, როგორიცაა `--scheme clickhouse-current` ან `--scheme clickhouse-floor`. სხვადასხვა ლეიბლის შედეგები არ განიხილება, როგორც იმავე კონფიგურაციის არასტაბილური ხელახლა გაშვებები.

### რას საჭიროებენ დაყოფები {#what-the-shards-need}

ატვირთული აწყობა არის `_build/test` დირექტორია. თითოეულ დაყოფის გამშვებს კვლავ სჭირდება:
- იგივე ჩეკაუტი, რაც აწყობის ფაზაში
- Elixir-ის და Erlang/OTP-ის იგივე ვერსიები
- დამოკიდებულობების წყაროები, `mix deps.get`-დან

დაყოფა umbrella პროექტის ფესვიდან ჯერჯერობით მხარდაჭერილი არ არის. გაუშვით ორივე ფაზა მის ერთ-ერთ აპლიკაციაში.

## უწყვეტი ინტეგრაცია {#continuous-integration}

### GitHub Actions {#github-actions}

GitHub Actions-ზე აწყობის ფაზა წერს დაყოფის ინდექსებს თავისი ნაბიჯის `matrix` გამომავალში. გამოიყენეთ მატრიცული სტრატეგია დაყოფების პარალელურად გასაშვებად:

```yaml
name: Tests
on: [pull_request]

env:
  MIX_ENV: test
  TUIST_TOKEN: ${{ secrets.TUIST_TOKEN }}

jobs:
  build:
    name: Build test shards
    runs-on: ubuntu-latest
    outputs:
      matrix: ${{ steps.build.outputs.matrix }}
    steps:
      - uses: actions/checkout@v4
      - uses: erlef/setup-beam@v1
        with:
          elixir-version: '1.18'
          otp-version: '27'
      - run: mix deps.get
      - run: mix compile --warnings-as-errors
      - id: build
        run: mix tuist.test.build --shard-max 5

  test:
    name: "Shard #${{ matrix.shard }}"
    needs: build
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        shard: ${{ fromJson(needs.build.outputs.matrix).shard }}
    env:
      TUIST_SHARD_INDEX: ${{ matrix.shard }}
    steps:
      - uses: actions/checkout@v4
      - uses: erlef/setup-beam@v1
        with:
          elixir-version: '1.18'
          otp-version: '27'
      - run: mix deps.get
```

### სხვა პროვაიდერები {#other-providers}

GitHub Actions-ის გარეთ აწყობის ფაზა წერს გეგმას `.tuist-shard-matrix.json`-ში:

```json
{
  "reference": "gitlab-1234",
  "shard_count": 2,
  "shards": [
    {
      "index": 0,
      "test_targets": ["MyApp.AccountsTest", "MyApp.CheckoutTest"],

    },
    {
      "index": 1,
      "test_targets": ["MyAppWeb.PageControllerTest"],
      "estimated_duration_ms": 39500
    }
  ]
}
```

გამოიყენეთ `shard_count` თქვენი პარალელური სამუშაოების დასაყენებლად და მიანიჭეთ თითოეულ სამუშაოს მისი `TUIST_SHARD_INDEX`, `0`-დან `shard_count - 1`-მდე. პროვაიდერზე, საიდანაც Tuist არ იღებს მითითებას, ასევე მიანიჭეთ ყველა სამუშაოს ერთი და იგივე `TUIST_SHARD_REFERENCE`.
