# Elixir ტესტების შარდირება {#elixir-test-sharding}

Tuist Hex პაკეტი შეიცავს ჩაშენებულ მხარდაჭერას Elixir პროექტის ტესტების შარდირებისთვის. ის იყენებს Tuist სერვერს, რათა შექმნას დაბალანსებული შარდების გეგმები ისტორიული დროის მონაცემებზე დაყრდნობით, და აკომპილირებს თქვენს პროექტს ერთხელ, რათა ყოველმა გამშვებმა პირდაპირ ტესტების გაშვება შეძლოს.

> [!IMPORTANT]
> **მოთხოვნები**
>
> - დაასრულეთ <.localized_link href="/guides/get-started/elixir-project">Elixir-ის საერთო კონფიგურაცია</.localized_link> CI შარდების სამუშაოების კონფიგურაციამდე

## როგორ მუშაობს {#how-it-works}

ტესტების შარდირება მიჰყვება ორეტაპიან სამუშაო პროცესს:

1. **აგების ეტაპი:** Tuist აკომპილირებს თქვენს პროექტს ტესტირებისთვის, აღრიცხავს თქვენს ტესტ ფაილებს და ქმნის **შარდების გეგმას** სერვერზე. სერვერი იყენებს ბოლო 30 დღის ისტორიულ ტესტების დროის მონაცემებს, რათა გაანაწილოს ტესტები შარდებში ისე, რომ თითოეულ შარდს დაახლოებით თანაბარი დრო დასჭირდეს. აგების ეტაპი ტვირთავს აგებას და გამოაქვს **შარდების მატრიცა**, რომელსაც თქვენი CI სისტემა იყენებს პარალელური გამშვებების შესაქმნელად.
2. **ტესტირების ეტაპი:** თითოეული CI გამშვები იღებს **შარდის ინდექსს**, ჩამოტვირთავს აგებას და ასრულებს მხოლოდ იმ ტესტებს, რომლებიც ამ შარდს მიეკუთვნება.

> [!NOTE]
> ჩართულ Tuist Linux გამშვებებზე, შარდების აგებებს შეუძლიათ გამოიყენონ ლოკალური არტიფაქტების საცავი. ყველა შარდი, რომელიც მოიხმარს ასეთ აგებას, უნდა გაეშვას ჩართულ გამშვებებზე ერთსა და იმავე ადგილას; გადაიტანეთ სამუშაო პროცესი სხვა გამშვებებზე აგების ხელახლა გაშვებით ლოკალური საცავის გათიშვის პირობებში.

ტესტები ნაწილდება ფაილების მიხედვით: ფაილის ყოველი ტესტი ერთსა და იმავე შარდზე გაეშვება. ტესტებს, რომლებიც Tuist-მა ჯერ არ ნახა, ენიჭებათ სავარაუდო დრო, ამიტომ პროექტის პირველი გეგმები ნაკლებად დაბალანსებულია, ვიდრე მოგვიანებითი.

## აგების ეტაპი {#build-phase}

მოამზადეთ ტესტების შარდები `tuist.test.build` ამოცანის გამოყენებით:

```sh
MIX_ENV=test mix compile --warnings-as-errors
MIX_ENV=test mix tuist.test.build --shard-max 5
```

აკომპილირეთ საერთო კონფიგურაციის მიერ დამონტაჟებული ალიასის მეშვეობით შარდირების ამოცანის გამოძახებამდე. ცივ checkout-ზე, Mix-ს შეუძლია დააკომპილიროს დამოკიდებულებები `tuist.test.build`-ის აღმოჩენისას, სანამ Tuist-ის დამოკიდებულებების ქეში მათ აღდგენას მოასწრებს. ცალსახა კომპილაცია გაეშვება იმავე სატესტო გარემოში, რაშიც შარდირების ამოცანა.

ეს ამოცანა:
1. აკომპილირებს პროექტს სატესტო გარემოში
2. ქმნის შარდების გეგმას Tuist სერვერზე ისტორიული დროის მონაცემების გამოყენებით
3. ტვირთავს აგებას, რათა შარდებმა ხელახლა არ დააკომპილირონ
4. გამოაქვს შარდების მატრიცა თქვენი CI სისტემისთვის

### აგების პარამეტრები {#build-options}

| პარამეტრი | აღწერა |
|--------|-------------|
| `--shard-max <N>` | შარდების მაქსიმალური რაოდენობა (ნაგულისხმები: 2) |
| `--shard-min <N>` | შარდების მინიმალური რაოდენობა |
| `--shard-total <N>` | შარდების ზუსტი რაოდენობა, დიაპაზონის ნაცვლად |
| `--shard-max-duration <MS>` | მიზნობრივი მაქსიმალური ხანგრძლივობა თითოეული შარდისთვის მილიწამებში |
| `--shard-reference <REF>` | სახელი, რომლითაც შარდები პოულობენ გეგმას |
| `--no-upload` | დაგეგმეთ შარდები აგების ატვირთვის გარეშე; თითოეული შარდი შემდეგ თავისთვის აკომპილირებს |

ყოველი სხვა არგუმენტი გადაეცემა `mix compile`-ს.

შარდის მითითება ავტომატურად მიიღება CI გარემოს ცვლადებიდან (`GITHUB_RUN_ID`, `CI_PIPELINE_ID`, `CIRCLE_WORKFLOW_ID`, `BUILDKITE_BUILD_ID`) ან შეიძლება ცალსახად დაყენდეს `TUIST_SHARD_REFERENCE` გარემოს ცვლადის მეშვეობით. ამ პროვაიდერების გარეთ თქვენ უნდა დააყენოთ ის მნიშვნელობა, რომელსაც იზიარებენ აგების ეტაპი და ერთი pipeline-ის გაშვების შარდები. GitHub Actions-ზე, მითითებები ასევე მოიცავს გაშვების მცდელობას: როდესაც ხელახლა აშვებთ მხოლოდ ჩავარდნილ სამუშაოებს, გადაეცით საწყისი აგების სამუშაოს მითითება, ნაცვლად ახლის მიღებისა შარდების სამუშაოებში.

## ტესტირების ეტაპი {#test-phase}

როდესაც `TUIST_SHARD_INDEX` დაყენებულია, პაკეტი იღებს შარდის განაწილებას სერვერიდან, ჩამოტვირთავს აგებას და ასრულებს მხოლოდ მინიჭებულ სატესტო ფაილებს კომპილაციის გარეშე. ცივ გამშვებზე, დააინიციალიზეთ SDK და ჩატვირთეთ მისი ბილიკები ამოცანის გამოძახებამდე:

```sh
MIX_ENV=test TUIST_SHARD_INDEX=0 mix do deps.compile tuist_ex --include-children + deps.loadpaths --no-compile --no-deps-check + tuist.test
```

SDK-ის კომპილაცია Mix-ის სამუშაო პროცესებში არ ტვირთავს მას მშობელ პროცესში. ცალსახა `deps.loadpaths` ნაბიჯი ხელს უშლის ამოცანების აღმოჩენას დარჩენილი დამოკიდებულებების კომპილაციაში აგების ჩამოტვირთვამდე. ეს ერთბრძანებიანი ფორმა ინარჩუნებს თქვენი პროექტის ტესტების მომზადების ალიასს. თუ მისი კონფიგურაციის ბრძანებები იწვევენ კომპილაციას, გამოიყენეთ ქვემოთ მოცემული ცალკეული კონფიგურაციის თანმიმდევრობა.

ნებისმიერი სატესტო ფაილი ან დირექტორია, რომელსაც გადასცემთ, კიდევ უფრო ამცირებს შარდს: გაეშვება მხოლოდ ის ფაილები, რომლებიც ერთდროულად არიან შარდში და თქვენს შერჩევაში. შარდი, რომელსაც საბოლოოდ ტესტები არ დარჩება, წარმატებით სრულდება.

ყველა შარდის შედეგები დაშბორდზე მოდის ერთიანი ტესტების გაშვების სახით, და მისი **შარდები** სექცია აჩვენებს, თუ რამდენი დრო დასჭირდა თითოეულს.

თუ კონფიგურაცია უნდა გაეშვას ტესტებამდე, ჯერ ჩამოტვირთეთ აგება აპლიკაციის გაშვების გარეშე:

```sh
MIX_ENV=test TUIST_SHARD_INDEX=0 mix do deps.compile tuist_ex --include-children + deps.loadpaths --no-compile --no-deps-check + tuist.test --prepare-only
```

გაუშვით თქვენი კონფიგურაცია ცალკეულ პროცესში კომპილაციის გათიშვით. მაგალითად, Ecto პროექტს შეუძლია შექმნას და მიგრაცია გაუკეთოს მის მონაცემთა ბაზებს შემდეგნაირად:

```sh
MIX_ENV=test mix run --no-start --no-compile --no-deps-check -e 'Mix.Tasks.Ecto.Create.run([]); Mix.Tasks.Ecto.Migrate.run([])'
```

შეინარჩუნეთ ნებისმიერი სხვა პროექტისთვის სპეციფიკური მომზადება ამ ეტაპზე. თქვენმა კომპილაციის ალიასმა ასევე უნდა გაითვალისწინოს `--no-compile` ბუტსტრაპის სამუშაოს შესრულებამდე: Mix მხოლოდ ბოლო ამოცანას გადასცემს ფლაგებს სიის ალიასში, ამიტომ ადრეული უპირობო `deps.compile` მაინც გაეშვება. იხილეთ დაცული ალიასი <.localized_link href="/guides/features/cache/elixir-advanced#manual-compile-integration">ხელით კომპილაციის ინტეგრაციაში</.localized_link>.

შემდეგ ჩატვირთეთ აღდგენილი SDK კომპილაციის გარეშე შარდის შესრულებამდე. ეს ასევე ხელს უშლის ამოცანების აღმოჩენას დააკომპილიროს ბილიკის დამოკიდებულება, როდესაც მისი წყაროები უფრო ახალია, ვიდრე ჩამოტვირთული აგება:

```sh
MIX_ENV=test TUIST_SHARD_INDEX=0 mix do deps.loadpaths --no-compile --no-deps-check + tuist.test --no-download
```

ორივე ბრძანებას სჭირდება ერთი და იგივე შარდის მითითება. `--prepare-only` საჭიროებს ატვირთულ აგებას, და `--no-download` ვერხერხდება, თუ მომზადებული აპლიკაციის არტიფაქტი არ არსებობს. `--no-download` ცალსახად ტოვებს თქვენი პროექტის ტესტების მომზადების ალიასს, ხელახალი ცდების ჩათვლით, და ბეჭდავს შეტყობინებას, როდესაც ტოვებს კონფიგურაციის ნაბიჯებს. ჩვეულებრივი გაშვებები ინარჩუნებენ თავიანთ ალიასებს, მაშინაც კი, როდესაც გადასცემთ `--no-compile --no-deps-check`. მონაცემთა ბაზების მიგრაციების ცალკეულ პროცესში შენარჩუნება ასევე თავიდან აცილებს მოდულის ხელახლა განსაზღვრის გაფრთხილებებს, როდესაც მიგრაციის რეგრესიული ტესტები თავად ტვირთავენ ამ მოდულებს.

სხვადასხვა გარემოების ტესტირებისას, გადაეცით სტაბილური `--scheme` ჭდე, როგორიცაა `--scheme clickhouse-current` ან `--scheme clickhouse-floor`. სხვადასხვა ჭდეების შედეგები არ განიხილება, როგორც იმავე კონფიგურაციის არასტაბილური ხელახალი გაშვებები.

### რა სჭირდება შარდებს {#what-the-shards-need}

ატვირთული აგება არის `_build/test` დირექტორია. თითოეულ შარდის გამშვებს კვლავ სჭირდება:
- იგივე გადმოწერა, რაც აგების ეტაპზე
- Elixir-ის და Erlang/OTP-ის იგივე ვერსიები
- დამოკიდებულობების წყაროები, `mix deps.get`-დან

ქოლგის პროექტის ფესვის შარდინგი ჯერჯერობით მხარდაჭერილი არ არის. ორივე ეტაპი გაუშვით ერთ-ერთი მისი აპლიკაციის შიგნით.

## უწყვეტი ინტეგრაცია {#continuous-integration}

### GitHub Actions {#github-actions}

GitHub Actions-ზე აგების ეტაპი წერს შარდების ინდექსებს თავისი ნაბიჯის `matrix` გამოსავალში. გამოიყენეთ მატრიცული სტრატეგია შარდების პარალელურად გასაშვებად:

```yaml
name: Tests
on: [pull_request]

env:
```

### სხვა პროვაიდერები {#other-providers}

GitHub Actions-ის გარეთ აგების ეტაპი წერს გეგმას `.tuist-shard-matrix.json`-ში:

```json
{
  "reference": "gitlab-1234",
  "shard_count": 2,
  "shards": [
    {
      "index": 0,
      "test_targets": ["MyApp.AccountsTest", "MyApp.CheckoutTest"],
      "estimated_duration_ms": 41000
    },
    {
      "index": 1,
      "test_targets": ["MyAppWeb.PageControllerTest"],
      "estimated_duration_ms": 39500
    }
  ]
}
```

გამოიყენეთ `shard_count` თქვენი პარალელური სამუშაოების დასაყენებლად და მიანიჭეთ თითოეულ სამუშაოს მისი `TUIST_SHARD_INDEX`, `0`-დან `shard_count - 1`-მდე. პროვაიდერზე, საიდანაც Tuist არ იღებს მითითებას, ასევე მიანიჭეთ ყველა სამუშაოს ერთი და იგივე `TUIST_SHARD_REFERENCE`.
