# Elixir-ის ტესტების დაშლა {#elixir-test-sharding}

Tuist Hex პაკეტი შეიცავს ჩაშენებულ მხარდაჭერას Elixir პროექტის ტესტების დაშლისთვის. ის იყენებს Tuist სერვერს, რათან შექმნას დაბალანსებული დაშლის გეგმები ისტორიული დროის მონაცემების საფუძველზე, და კომპილირებს თქვენს პროექტს ერთხელ, რათა ყოველმა გამშვებმა პირდაპირ გადავიდეს ტესტების გაშვებაზე.

> [!IMPORTANT] REQUIREMENTS
> - დაასრულეთ <.localized_link href="/guides/get-started/elixir-project">გაზიარებული Elixir-ის კონფიგურაცია</.localized_link> CI დაშლის სამუშაოების კონფიგურაციამდე

## როგორ მუშაობს {#how-it-works}

ტესტების დაშლა მიჰყვება ორეტაპიან სამუშაო პროცესს:

1. **კომპილაციის ეტაპი:** Tuist კომპილირებს თქვენს პროექტს ტესტირებისთვის, ათვლის თქვენს ტესტ ფაილებს და ქმნის **დაშლის გეგმას** სერვერზე. სერვერი იყენებს ბოლო 30 დღის ისტორიულ ტესტის დროის მონაცემებს, რათა გაანაწილოს ტესტები დაშლებში ისე, რომ თითოეულ დაშლას დაახლოებით ერთი და იგივე დრო დასჭირდეს. კომპილაციის ეტაპი ტვირთავს აწყობას და გამოაქვს **დაშლის მატრიცა**, რომელსაც თქვენი CI სისტემა იყენებს პარალელური გამშვებების შესაქმნელად.
2. **ტესტირების ეტაპი:** თითოეული CI გამშვები იღებს **დაშლის ინდექსს**, ჩამოტვირთავს აწყობას და ასრულებს მხოლოდ იმ ტესტებს, რომლებიც ამ დაშლას მიეკუთვნება.

ტესტები ნაწილდება ფაილების მიხედვით: ერთი ფაილის ყველა ტესტი ერთსა და იმავე დაშლაზე გაეშვება. ტესტებს, რომლებიც Tuist-მა ჯერ არ ნახა, ენიჭება სავარაუდო დრო, ამიტომ პროექტის პირველი გეგმები ნაკლებად დაბალანსებულია, ვიდრე მოგვიანებითი.

## კომპილაციის ეტაპი {#build-phase}

მოამზადეთ ტესტების დაშლა `tuist.test.build` ამოცანის გამოყენებით:

```sh
MIX_ENV=test mix compile --warnings-as-errors
MIX_ENV=test mix tuist.test.build --shard-max 5
```

კომპილაცია გაუშვით გაზიარებული კონფიგურაციის მიერ დამონტაჟებული ალიასის მეშვეობით დაშლის ამოცანის გამოძახებამდე. ცივ checkout-ზე Mix-ს შეუძლია დამოკიდებულებების კომპილაცია `tuist.test.build`-ის აღმოჩენისას, სანამ Tuist-ის დამოკიდებულებების ქეში მათ აღდგენას მოახერხებს. ცხადი კომპილაცია იგივე ტესტის გარემოში გაეშვება, როგორც დაშლის ამოცანა.

ეს ამოცანა:
1. კომპილირებს პროექტს ტესტის გარემოში
2. ქმნის დაშლის გეგმას Tuist სერვერზე ისტორიული დროის მონაცემების გამოყენებით
3. ტვირთავს აწყობას, რათა დაშლებმა ხელახლა არ კომპილირდნენ
4. გამოაქვს დაშლის მატრიცა თქვენი CI სისტემისთვის

### კომპილაციის პარამეტრები {#build-options}

| პარამეტრი | აღწერა |
|--------|-------------|
| `--shard-max <N>` | დაშლების მაქსიმალური რაოდენობა (ნაგულისხმები: 2) |
| `--shard-min <N>` | დაშლების მინიმალური რაოდენობა |
| `--shard-total <N>` | დაშლების ზუსტი რაოდენობა, დიაპაზონის ნაცვლად |
| `--shard-max-duration <MS>` | მიზნობრივი მაქსიმალური ხანგრძლივობა თითოეული დაშლისთვის მილიწამებში |
| `--shard-reference <REF>` | სახელი, რომლითაც დაშლები პოულობენ გეგმას |
| `--no-upload` | დაგეგმეთ დაშლები აწყობის ატვირთვის გარეშე; ამ შემთხვევაში თითოეული დაშლა თავისთვის კომპილირდება |

ყველა სხვა არგუმენტი გადაეცემა `mix compile`-ს.

დაშლის მითითება ავტომატურად მიიღება CI გარემოს ცვლადებიდან (`GITHUB_RUN_ID`, `CI_PIPELINE_ID`, `CIRCLE_WORKFLOW_ID`, `BUILDKITE_BUILD_ID`) ან შეიძლება ცხადად დაყენდეს `TUIST_SHARD_REFERENCE` გარემოს ცვლადის მეშვეობით. ამ პროვაიდერების გარეთ თქვენ უნდა დააყენოთ ის მნიშვნელობაზე, რომელსაც იზიარებს კომპილაციის ეტაპი და ერთი პაიპლაინის გაშვების დაშლები. GitHub Actions-ზე, მითითებები ასევე მოიცავს გაშვების მცდელობას: მხოლოდ წარუმატებელი სამუშაოების ხელახლა გაშვებისას, გადაეცით თავდაპირველი კომპილაციის სამუშაოს მითითება და არ გამოიყვანოთ ახალი დაშლის სამუშაოებში.

## ტესტირების ეტაპი {#test-phase}

როდესაც `TUIST_SHARD_INDEX` დაყენებულია, პაკეტი იღებს დაშლის განაწილებას სერვერიდან, ჩამოტვირთავს აწყობას და ასრულებს მხოლოდ მინიჭებულ ტესტ ფაილებს კომპილაციის გარეშე. ცივ გამშვებზე, მოამზადეთ SDK და ჩატვირთეთ მისი გზები ამოცანის გამოძახებამდე:

```sh
MIX_ENV=test TUIST_SHARD_INDEX=0 mix do deps.compile tuist_ex --include-children + deps.loadpaths --no-compile --no-deps-check + tuist.test
```

SDK-ის კომპილაცია Mix-ის სამუშაო პროცესებში არ ტვირთავს მას მშობელ პროცესში. ცხადი `deps.loadpaths` ნაბიჯი ხელს უშლის ამოცანების აღმოჩენას დარჩენილი დამოკიდებულებების კომპილაციას აწყობის ჩამოტვირთვამდე. ეს ერთბრძანებიანი ფორმა ინარჩუნებს თქვენი პროექტის ტესტის მომზადების ალიასს. თუ მისი კონფიგურაციის ბრძანებები იწვევენ კომპილაციას, გამოიყენეთ ქვემოთ მოცემული ცალკეული კონფიგურაციის თანმიმდევრობა.

ნებისმიერი ტესტის ფაილი ან დირექტორია, რომელსაც გადასცემთ, კიდევ უფრო ამცირებს დაშლას: გაეშვება მხოლოდ ის ფაილები, რომლებიც ერთდროულად არიან დაშლასა და თქვენს შერჩევაში. დაშლა, რომელსაც ტესტები არ დარჩება, წარმატებით სრულდება.

ყველა დაშლის შედეგები დაშბორდზე ჩნდება ერთიანი ტესტის გაშვების სახით, და მისი **დაშლები** სექცია აჩვენებს, თუ რამდენი დრო დასჭირდა თითოეულს.

თუ კონფიგურაცია უნდა გაეშვას ტესტებამდე, ჯერ ჩამოტვირთეთ აწყობა აპლიკაციის გაშვების გარეშე:

```sh
MIX_ENV=test TUIST_SHARD_INDEX=0 mix do deps.compile tuist_ex --include-children + deps.loadpaths --no-compile --no-deps-check + tuist.test --prepare-only
```

გაუშვით თქვენი კონფიგურაცია ცალკე პროცესში კომპილაციის გათიშვით. მაგალითად, Ecto პროექტს შეუძლია შექმნას და მიგრაცია გაუკეთოს მის მონაცემთა ბაზებს შემდეგი ბრძანებით:

```sh
MIX_ENV=test mix run --no-start --no-compile --no-deps-check -e 'Mix.Tasks.Ecto.Create.run([]); Mix.Tasks.Ecto.Migrate.run([])'
```

შეინარჩუნეთ ნებისმიერი სხვა პროექტისთვის სპეციფიკური მომზადება ამ ეტაპზე. თქვენმა კომპილაციის ალიასმა ასევე უნდა გაითვალისწინოს `--no-compile` საწყისი სამუშაოების შესრულებამდე: Mix მხოლოდ ბოლო ამოცანას გადასცემს ფლაგებს სიის ალიასში, ამიტომ ადრეული უპირობო `deps.compile` მაინც გაეშვება. იხილეთ დაცული ალიასი <.localized_link href="/guides/features/cache/elixir-advanced#manual-compile-integration">ხელით კომპილაციის ინტეგრაცია</.localized_link>.

შემდეგ ჩატვირთეთ აღდგენილი SDK კომპილაციის გარეშე დაშლის შესრულებამდე. ეს ასევე ხელს უშლის ამოცანების აღმოჩენას გზის დამოკიდებულების კომპილაციას, როდესაც მისი წყაროები უფრო ახალია, ვიდრე ჩამოტვირთული აწყობა:

```sh
MIX_ENV=test TUIST_SHARD_INDEX=0 mix do deps.loadpaths --no-compile --no-deps-check + tuist.test --no-download
```

ორივე ბრძანებას სჭირდება ერთი და იგივე დაშლის მითითება. `--prepare-only` მოითხოვს ატვირთულ აწყობას, და `--no-download` ვერ ხერხდება, თუ მომზადებული აპლიკაციის არტიფაქტი არ არსებობს. `--no-download` ცხადად ტოვებს თქვენი პროექტის ტესტის მომზადების ალიასს, ხელახალი ცდების ჩათვლით, და ბეჭდავს შეტყობინებას, როდესაც კონფიგურაციის ნაბიჯებს ტოვებს. ჩვეულებრივი გაშვებები ინარჩუნებენ თავიანთ ალიასებს, მაშინაც კი, როდესაც გადასცემთ `--no-compile --no-deps-check`. მონაცემთა ბაზის მიგრაციების ცალკე პროცესში შენარჩუნება ასევე თავს არიდებს მოდულის ხელახლა განსაზღვრის გაფრთხილებებს, როდესაც მიგრაციის რეგრესიული ტესტები თავად ტვირთავენ ამ მოდულებს.

სხვადასხვა გარემოების ტესტირებისას, გადაეცით სტაბილური `--scheme` ლეიბლი, როგორიცაა `--scheme clickhouse-current` ან `--scheme clickhouse-floor`. სხვადასხვა ლეიბლის შედეგები არ განიხილება, როგორც იგივე კონფიგურაციის არასტაბილური ხელახალი გაშვებები.

### რა სჭირდებათ დაშლებს {#what-the-shards-need}

ატვირთული აწყობა არის `_build/test` დირექტორია. თითოეულ დაშლის გამშვებს კვლავ სჭირდება:
- იგივე ჩეკაუტი, რაც აწყობის ფაზაში
- Elixir-ის და Erlang/OTP-ის იგივე ვერსიები
- დამოკიდებულებების წყაროები `mix deps.get`-დან

umbrella პროექტის ძირიდან დაშლა ჯერჯერობით არ არის მხარდაჭერილი. გაუშვით ორივე ფაზა მის ერთ-ერთ აპლიკაციაში.

## უწყვეტი ინტეგრაცია {#continuous-integration}

### GitHub Actions {#github-actions}

GitHub Actions-ზე აწყობის ფაზა წერს დაშლის ინდექსებს თავისი ნაბიჯის `matrix` გამოსავალში. გამოიყენეთ მატრიცული სტრატეგია დაშლების პარალელურად გასაშვებად:

```yaml
name: Tests
on: [pull_request]

env:
  MIX_ENV: test
  TUIST_TOKEN: ${{ secrets.TUIST_TOKEN }}

jobs:
  build:
    name: Build test shards
    runs-on: ubuntu-latest
    outputs:
      matrix: ${{ steps.build.outputs.matrix }}
    steps:
      - uses: actions/checkout@v4
      - uses: erlef/setup-beam@v1
        with:
          elixir-version: '1.18'
          otp-version: '27'
      - run: mix deps.get
      - run: mix compile --warnings-as-errors
      - id: build
        run: mix tuist.test.build --shard-max 5

  test:
    name: "Shard #${{ matrix.shard }}"
    needs: build
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        shard: ${{ fromJson(needs.build.outputs.matrix).shard }}
    env:
      TUIST_SHARD_INDEX: ${{ matrix.shard }}
    steps:
      - uses: actions/checkout@v4
      - uses: erlef/setup-beam@v1
        with:
          elixir-version: '1.18'
          otp-version: '27'
```

### სხვა პროვაიდერები {#other-providers}

GitHub Actions-ის გარეთ აწყობის ფაზა წერს გეგმას `.tuist-shard-matrix.json`-ში:

```json
{
  "reference": "gitlab-1234",
  "shard_count": 2,
  "shards": [
    {
      "index": 0,
      "test_targets": ["MyApp.AccountsTest", "MyApp.CheckoutTest"],
      "estimated_duration_ms": 41000
    },
    {
      "index": 1,
      "test_targets": ["MyAppWeb.PageControllerTest"],
      "estimated_duration_ms": 39500
    }
  ]
}
```

გამოიყენეთ `shard_count` თქვენი პარალელური სამუშაოების დასაყენებლად და მიანიჭეთ თითოეულ სამუშაოს მისი `TUIST_SHARD_INDEX`, `0`-დან `shard_count - 1`-მდე. იმ პროვაიდერზე, საიდანაც Tuist არ იღებს მითითებას, ასევე მიანიჭეთ ყველა სამუშაოს ერთი და იგივე `TUIST_SHARD_REFERENCE`.
