# Elixir ტესტების შარდირება {#elixir-test-sharding}

Tuist Hex პაკეტი შეიცავს ჩაშენებულ მხარდაჭერას Elixir პროექტის ტესტების შარდებად დაყოფისთვის. ის იყენებს Tuist სერვერს, რათა შექმნას დაბალანსებული შარდ-გეგმები ისტორიული დროის მონაცემებზე დაყრდნობით, და ერთხელ აკომპილირებს თქვენს პროექტს, რათა ყოველმა გამშვებმა პირდაპირ გადავიდეს ტესტების გაშვებაზე.

> [!IMPORTANT] REQUIREMENTS
> - დაასრულეთ <.localized_link href="/guides/get-started/elixir-project">გაზიარებული Elixir კონფიგურაცია</.localized_link> CI შარდ-ამოცანების კონფიგურაციამდე

## როგორ მუშაობს {#how-it-works}

ტესტების შარდირება მიჰყვება ორეტაპიან სამუშაო ნაკადს:

1. **აგების ეტაპი:** Tuist აკომპილირებს თქვენს პროექტს ტესტირებისთვის, ჩამოთვლის თქვენს ტესტ-ფაილებს და ქმნის **შარდ-გეგმას** სერვერზე. სერვერი იყენებს ბოლო 30 დღის ისტორიულ ტესტ-დროის მონაცემებს, რათა გაანაწილოს ტესტები შარდებში ისე, რომ თითოეულ შარდს დაახლოებით თანაბარი დრო დასჭირდეს. აგების ეტაპი ატვირთავს აგებას და გამოაქვს **შარდ-მატრიცა**, რომელსაც თქვენი CI სისტემა იყენებს პარალელური გამშვებების შესაქმნელად.
2. **ტესტირების ეტაპი:** თითოეული CI გამშვები იღებს **შარდ-ინდექსს**, ჩამოტვირთავს აგებას და ასრულებს მხოლოდ იმ ტესტებს, რომლებიც ამ შარდს მიეკუთვნება.

აგების ატვირთვა ერთდროულად გზავნის ოთხამდე ნაწილს და აკეთებს სამამდე მცდელობას ნაწილების დროებითი შეცდომების შემთხვევაში. რეგისტრირებულ Tuist Linux გამშვებებზე შარდ-აგებებს შეუძლიათ გამოიყენონ ლოკალური არტიფაქტების საცავი. ყველა შარდი, რომელიც იყენებს ასეთ აგებას, უნდა გაეშვას ერთსა და იმავე ადგილმდებარეობაზე რეგისტრირებულ გამშვებებზე; გადაიტანეთ სამუშაო ნაკადი სხვა გამშვებებზე აგების ხელახლა გაშვებით ლოკალური საცავის გათიშვით.

ტესტები ნაწილდება ფაილების მიხედვით: ერთი ფაილის ყველა ტესტი ერთსა და იმავე შარდზე გაეშვება. ტესტებს, რომლებსაც Tuist ჯერ არ შეხვედრია, ენიჭებათ სავარაუდო დრო, ამიტომ პროექტის პირველი გეგმები ნაკლებად დაბალანსებულია, ვიდრე მოგვიანებითი.

## აგების ეტაპი {#build-phase}

მოამზადეთ ტესტ-შარდები `tuist.test.build` ამოცანის გამოყენებით:

```sh
MIX_ENV=test mix compile --warnings-as-errors
MIX_ENV=test mix tuist.test.build --shard-max 5
```

აკომპილირეთ გაზიარებული კონფიგურაციის მიერ დაყენებული ალიასის მეშვეობით შარდირების ამოცანის გამოძახებამდე. ცივ გადმოწერაზე Mix-ს შეუძლია აკომპილიროს დამოკიდებულებები `tuist.test.build`-ის აღმოჩენისას, სანამ Tuist-ის დამოკიდებულებების ქეში მათ აღდგენას მოასწრებს. ცხადი კომპილაცია გაეშვება იმავე ტესტ-გარემოში, რაშიც შარდირების ამოცანა.

ეს ამოცანა:
1. აკომპილირებს პროექტს ტესტ-გარემოში
2. ქმნის შარდ-გეგმას Tuist სერვერზე ისტორიული დროის მონაცემების გამოყენებით
3. ატვირთავს აგებას, რათა შარდებმა ხელახლა არ აკომპილირონ
4. გამოაქვს შარდ-მატრიცა თქვენი CI სისტემისთვის

### აგების პარამეტრები {#build-options}

| პარამეტრი | აღწერა |
|--------|-------------|
| `--shard-max <N>` | შარდების მაქსიმალური რაოდენობა (ნაგულისხმები: 2) |
| `--shard-min <N>` | შარდების მინიმალური რაოდენობა |
| `--shard-total <N>` | შარდების ზუსტი რაოდენობა დიაპაზონის ნაცვლად |
| `--shard-max-duration <MS>` | მიზნობრივი მაქსიმალური ხანგრძლივობა თითო შარდზე მილიწამებში |
| `--shard-reference <REF>` | სახელი, რომლითაც შარდები პოულობენ გეგმას |
| `--no-upload` | დაგეგმეთ შარდები აგების ატვირთვის გარეშე; თითოეული შარდი მაშინ თავისთვის აკომპილირებს |

ყველა სხვა არგუმენტი გადაეცემა `mix compile`-ს.

შარდის მითითება ავტომატურად მიიღება CI გარემოს ცვლადებიდან (`GITHUB_RUN_ID`, `CI_PIPELINE_ID`, `CIRCLE_WORKFLOW_ID`, `BUILDKITE_BUILD_ID`) ან შეიძლება ცხადად დაყენდეს `TUIST_SHARD_REFERENCE` გარემოს ცვლადის მეშვეობით. ამ პროვაიდერების გარეთ თქვენ უნდა დააყენოთ ის მნიშვნელობაზე, რომელსაც ერთი პაიპლაინის გაშვების აგების ეტაპი და შარდები იზიარებენ. GitHub Actions-ზე მითითებები ასევე მოიცავს გაშვების მცდელობას: როდესაც ხელახლა აშვებთ მხოლოდ ჩავარდნილ ამოცანებს, გადაეცით საწყისი აგების ამოცანის მითითება ახლის გამოყვანის ნაცვლად შარდ-ამოცანებში.

## ტესტირების ეტაპი {#test-phase}

როდესაც `TUIST_SHARD_INDEX` დაყენებულია, პაკეტი იღებს შარდ-განაწილებას სერვერიდან, ჩამოტვირთავს აგებას და ასრულებს მხოლოდ მინიჭებულ ტესტ-ფაილებს კომპილაციის გარეშე. ცივ გამშვებზე, ამოცანის გამოძახებამდე მოამზადეთ SDK და ჩატვირთეთ მისი ბილიკები:

```sh
MIX_ENV=test TUIST_SHARD_INDEX=0 mix do deps.compile tuist_ex --include-children + deps.loadpaths --no-compile --no-deps-check + tuist.test
```

SDK-ს კომპილაცია Mix-ის სამუშაო პროცესებში არ ტვირთავს მას მშობელ პროცესში. ცხადი `deps.loadpaths` ნაბიჯი ხელს უშლის ამოცანების აღმოჩენას დარჩენილი დამოკიდებულებების კომპილაციაში აგების ჩამოტვირთვამდე. ეს ერთბრძანებიანი ფორმა ინარჩუნებს თქვენი პროექტის ტესტ-მომზადების ალიასს. თუ მისი კონფიგურაციის ბრძანებები იწვევენ კომპილაციას, გამოიყენეთ ქვემოთ მოცემული ცალკეული კონფიგურაციის თანმიმდევრობა.

ნებისმიერი ტესტ-ფაილი ან დირექტორია, რომელსაც გადასცემთ, კიდევ უფრო ავიწროებს შარდს: გაეშვება მხოლოდ ის ფაილები, რომლებიც ერთდროულად არიან შარდშიც და თქვენს შერჩევაშიც. შარდი, რომელსაც ტესტები არ დარჩება, წარმატებით სრულდება.

ყველა შარდის შედეგები დაშბორდზე მოდის როგორც ერთი ტესტების გაშვება, და მისი **შარდები** სექცია აჩვენებს, თუ რამდენი ხანი დასჭირდა თითოეულს.

თუ კონფიგურაცია უნდა გაეშვას ტესტებამდე, ჯერ ჩამოტვირთეთ აგება აპლიკაციის გაშვების გარეშე:

```sh
MIX_ENV=test TUIST_SHARD_INDEX=0 mix do deps.compile tuist_ex --include-children + deps.loadpaths --no-compile --no-deps-check + tuist.test --prepare-only
```

გაუშვით თქვენი კონფიგურაცია ცალკე პროცესში კომპილაციის გათიშვით. მაგალითად, Ecto პროექტს შეუძლია შექმნას და განაახლოს მისი მონაცემთა ბაზები:

```sh
MIX_ENV=test mix run --no-start --no-compile --no-deps-check -e 'Mix.Tasks.Ecto.Create.run([]); Mix.Tasks.Ecto.Migrate.run([])'
```

შეინარჩუნეთ ნებისმიერი სხვა პროექტ-სპეციფიკური მომზადება ამ ეტაპზე. თქვენმა კომპილაციის ალიასმა ასევე უნდა გაითვალისწინოს `--no-compile` ბუტსტრაპის სამუშაოს შესრულებამდე: Mix მხოლოდ ბოლო ამოცანას გადასცემს ფლაგებს სიის ალიასში, ამიტომ ადრეული უპირობო `deps.compile` მაინც გაეშვება. იხილეთ დაცული ალიასი <.localized_link href="/guides/features/cache/elixir-advanced#manual-compile-integration">ხელით კომპილაციის ინტეგრაციაში</.localized_link>.

შემდეგ ჩატვირთეთ აღდგენილი SDK კომპილაციის გარეშე შარდის შესრულებამდე. ეს ასევე ხელს უშლის ამოცანების აღმოჩენას ბილიკის დამოკიდებულების კომპილაციაში, როდესაც მისი წყაროები უფრო ახალია, ვიდრე ჩამოტვირთული აგება:

```sh
MIX_ENV=test TUIST_SHARD_INDEX=0 mix do deps.loadpaths --no-compile --no-deps-check + tuist.test --no-download
```

ორივე ბრძანებას სჭირდება ერთი და იგივე შარდ-მითითება. `--prepare-only` მოითხოვს ატვირთულ აგებას, და `--no-download` ვერ ხერხდება, თუ მომზადებული აპლიკაციის არტიფაქტი არ არის. `--no-download` ცხადად ტოვებს თქვენი პროექტის ტესტ-მომზადების ალიასს, მათ შორის ხელახლა ცდებისას, და ბეჭდავს შეტყობინებას, როდესაც კონფიგურაციის ნაბიჯებს ტოვებს. ჩვეულებრივი გაშვებები ინარჩუნებენ თავიანთ ალიასებს, მაშინაც კი, როდესაც გადასცემთ `--no-compile --no-deps-check`. მონაცემთა ბაზის მიგრაციების ცალკე პროცესში შენარჩუნება ასევე თავიდან იცილებს მოდულის ხელახლა განსაზღვრის გაფრთხილებებს, როდესაც მიგრაციის რეგრესიული ტესტები თავად ტვირთავენ ამ მოდულებს.

სხვადასხვა გარემოების ტესტირებისას, გადაეცით სტაბილური `--scheme` ლეიბლი, როგორიცაა `--scheme clickhouse-current` ან `--scheme clickhouse-floor`. სხვადასხვა ლეიბლის შედეგები არ განიხილება როგორც იმავე კონფიგურაციის არასტაბილური ხელახლა გაშვებები.

### რას საჭიროებენ შარდები {#what-the-shards-need}

ატვირთული აგება არის `_build/test` დირექტორია. თითოეულ შარდ-აგენტს კვლავ სჭირდება:
- იგივე ჩეკაუტი, რაც აგების ფაზაში
- Elixir-ის და Erlang/OTP-ის იგივე ვერსიები
- დამოკიდებულებების წყაროები, `mix deps.get`-დან

შარდინგი umbrella პროექტის ძირიდან ჯერჯერობით მხარდაჭერილი არ არის. გაუშვით ორივე ფაზა მის ერთ-ერთ აპლიკაციაში.

## უწყვეტი ინტეგრაცია {#continuous-integration}

### GitHub Actions {#github-actions}

GitHub Actions-ზე აგების ფაზა შარდების ინდექსებს წერს თავისი ნაბიჯის `matrix` გამომავალ მნიშვნელობაში. გამოიყენეთ მატრიცული სტრატეგია შარდების პარალელურად გასაშვებად:

```yaml
name: Tests
on: [pull_request]

env:
  MIX_ENV: test
  TUIST_TOKEN: ${{ secrets.TUIST_TOKEN }}

jobs:
  build:
    name: Build test shards
    runs-on: ubuntu-latest
    outputs:
      matrix: ${{ steps.build.outputs.matrix }}
    steps:
      - uses: actions/checkout@v4
      - uses: erlef/setup-beam@v1
        with:
          elixir-version: '1.18'
          otp-version: '27'
      - run: mix deps.get
      - run: mix compile --warnings-as-errors
      - id: build
        run: mix tuist.test.build --shard-max 5

  test:
    name: "Shard #${{ matrix.shard }}"
    needs: build
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        shard: ${{ fromJson(needs.build.outputs.matrix).shard }}
    env:
      TUIST_SHARD_INDEX: ${{ matrix.shard }}
    steps:
      - uses: actions/checkout@v4
      - uses: erlef/setup-beam@v1
        with:
          elixir-version: '1.18'
          otp-version: '27'
      - run: mix deps.get
      - run: mix do deps.compile tuist_ex --include-children + deps.loadpaths --no-compile --no-deps-check + tuist.test --prepare-only
      # Ecto example: keep all project-specific test preparation here.
      # The project's compile alias must honor --no-compile (see above).
      - run: mix run --no-start --no-compile --no-deps-check -e 'Mix.Tasks.Ecto.Create.run([]); Mix.Tasks.Ecto.Migrate.run([])'
      - run: mix do deps.loadpaths --no-compile --no-deps-check + tuist.test --no-download
```

### სხვა პროვაიდერები {#other-providers}

GitHub Actions-ის გარეთ აგების ფაზა გეგმას წერს `.tuist-shard-matrix.json`-ში:

```json
{
  "reference": "gitlab-1234",
  "shard_count": 2,
  "shards": [
    {
      "index": 0,
      "test_targets": ["MyApp.AccountsTest", "MyApp.CheckoutTest"],
      "estimated_duration_ms": 41000
    },
    {
      "index": 1,
      "test_targets": ["MyAppWeb.PageControllerTest"],
      "estimated_duration_ms": 39500
    }
  ]
}
```

გამოიყენეთ `shard_count` თქვენი პარალელური სამუშაოების დასაყენებლად და მიანიჭეთ თითოეულ სამუშაოს მისი `TUIST_SHARD_INDEX`, `0`-დან `shard_count - 1`-მდე. პროვაიდერზე, საიდანაც Tuist არ გამოიყვანს მითითებას, ასევე მიანიჭეთ ყველა სამუშაოს ერთი და იგივე `TUIST_SHARD_REFERENCE`.
