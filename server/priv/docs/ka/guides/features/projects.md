# გენერირებული პროექტები {#generated-projects}

Tuist-ის გენერირებული პროექტები არის საიმედო ალტერნატივა, რომელიც ეხმარება ამ გამოწვევების გადალახვას სირთულისა და ხარჯების მისაღებ დონეზე შენარჩუნებით. ის Xcode-ის პროექტებს ფუნდამენტურ ელემენტად მიიჩნევს, რაც უზრუნველყოფს მდგრადობას Xcode-ის მომავალი განახლებების მიმართ, და იყენებს Xcode-ის პროექტების გენერაციას, რათა გუნდებს მიაწოდოს მოდულარიზაციაზე ორიენტირებული დეკლარატიული API. Tuist იყენებს პროექტის დეკლარაციას მოდულარიზაციის სირთულეების გასამარტივებლად, აშენებისა და ტესტირების მსგავსი სამუშაო ნაკადების ოპტიმიზაციისთვის სხვადასხვა გარემოში, და ხელს უწყობს Xcode-ის პროექტების ევოლუციის გამარტივებასა და დემოკრატიზაციას.

## როგორ მუშაობს? {#how-does-it-work}

გენერირებულ პროექტებთან სამუშაოს დასაწყებად, თქვენ უბრალოდ უნდა განსაზღვროთ თქვენი პროექტი **Tuist-ის დომენური სპეციფიკური ენის (DSL)** გამოყენებით. ეს გულისხმობს ისეთი მანიფესტური ფაილების გამოყენებას, როგორიცაა `Workspace.swift` ან `Project.swift`. თუ ადრე მუშაობდით Swift Package Manager-თან, მიდგომა ძალიან მსგავსია.

პროექტის განსაზღვრის შემდეგ, Tuist გთავაზობთ მის მართვისა და ურთიერთქმედების სხვადასხვა სამუშაო ნაკადს:

- **გენერირება:** ეს არის საბაზისო სამუშაო ნაკადი. გამოიყენეთ ის Xcode-თან თავსებადი Xcode-ის პროექტის შესაქმნელად.
- **<.localized_link href="/cli/build">აშენება</.localized_link>:** ეს სამუშაო ნაკადი არა მხოლოდ ქმნის Xcode-ის პროექტს, არამედ იყენებს `xcodebuild`-ს მის კომპილაციისთვის.
- **<.localized_link href="/cli/test">ტესტირება</.localized_link>:** აშენების სამუშაო ნაკადის მსგავსად, ეს არა მხოლოდ ქმნის Xcode-ის პროექტს, არამედ იყენებს `xcodebuild`-ს მის ტესტირებისთვის.

## გამოწვევები Xcode-ის პროექტებთან {#challenges-with-xcode-projects}

Xcode-ის პროექტების ზრდასთან ერთად, **ორგანიზაციებმა შეიძლება წარმოქმნან პროდუქტიულობის ვარდნა** რამდენიმე ფაქტორის გამო, მათ შორის არასანდო ინკრემენტული აშენებები, Xcode-ის გლობალური ქეშის ხშირი გასუფთავება პრობლემების შემხვედრი დეველოპერების მიერ და მყიფე პროექტის კონფიგურაციები. სწრაფი ფუნქციების განვითარების შესანარჩუნებლად, ორგანიზაციები ჩვეულებრივ სხვადასხვა სტრატეგიას იკვლევენ.

ზოგიერთი ორგანიზაცია ირჩევს კომპილატორის გვერდის ავლით პლატფორმის აბსტრაქციას JavaScript-ზე დაფუძნებული დინამიური გარემოების გამოყენებით, მაგალითად [React Native](https://reactnative.dev/). მიუხედავად იმისა, რომ ეს მიდგომა შეიძლება ეფექტური იყოს, ის [ართულებს პლატფორმის ნატიურ ფუნქციებზე წვდომას](https://shopify.engineering/building-app-clip-react-native). სხვა ორგანიზაციები ირჩევენ **კოდის ბაზის მოდულარიზაციას**, რაც ეხმარება ცხადი საზღვრების დამყარებას, კოდის ბაზასთან მუშაობას ამარტივებს და აშენების დროის საიმედოობას აუმჯობესებს. თუმცა, Xcode-ის პროექტის ფორმატი არ არის განკუთვნილი მოდულარობისთვის და იწვევს იმპლიციტურ კონფიგურაციებს, რომლებსაც ცოტა ვინ ესმის და ხშირ კონფლიქტებს. ეს იწვევს ცუდ „bus factor“-ს და მიუხედავად იმისა, რომ ინკრემენტული აშენებები შეიძლება გაუმჯობესდეს, დეველოპერებმა შეიძლება მაინც ხშირად გაასუფთაონ Xcode-ის აშენების ქეში (ე.ი. derived data), როდესაც აშენებები ვერ ხერხდება. ამის მოსაგვარებლად, ზოგიერთი ორგანიზაცია ირჩევს **Xcode-ის აშენების სისტემის მიტოვებას** და ისეთი ალტერნატივების მიღებას, როგორიცაა [Buck](https://buck.build/) ან [Bazel](https://bazel.build/). თუმცა, ეს თან ახლავს [მაღალ სირთულესა და შენარჩუნების ტვირთს](https://bazel.build/migrate/xcode).


## ალტერნატივები {#alternatives}

### Swift Package Manager {#swift-package-manager}

მიუხედავად იმისა, რომ Swift Package Manager (SPM) ძირითადად დამოკიდებულებებზეა ორიენტირებული, Tuist სხვა მიდგომას გთავაზობთ. Tuist-ით თქვენ არა მხოლოდ განსაზღვრავთ პაკეტებს SPM-თან ინტეგრაციისთვის; თქვენ აყალიბებთ თქვენს პროექტებს ისეთი ნაცნობი კონცეფციების გამოყენებით, როგორიცაა პროექტები, სამუშაო სივრცეები, სამიზნეები და სქემები.

### XcodeGen {#xcodegen}

[XcodeGen](https://github.com/yonaskolb/XcodeGen) არის სპეციალიზებული პროექტის გენერატორი, რომელიც შექმნილია კოლაბორატიულ Xcode-ის პროექტებში კონფლიქტების შესამცირებლად და Xcode-ის შიდა მუშაობის ზოგიერთი სირთულის გასამარტივებლად. თუმცა, პროექტები განისაზღვრება სერიალიზებადი ფორმატების გამოყენებით, როგორიცაა [YAML](https://yaml.org/). Swift-ისგან განსხვავებით, ეს არ აძლევს დეველოპერებს საშუალებას ააშენონ აბსტრაქციები ან შემოწმებები დამატებითი ინსტრუმენტების ჩართვის გარეშე. მიუხედავად იმისა, რომ XcodeGen გთავაზობთ დამოკიდებულებების შიდა წარმოდგენაზე ასახვის გზას ვალიდაციისა და ოპტიმიზაციისთვის, ის მაინც აქვეყნებს დეველოპერებს Xcode-ის ნიუანსებისთვის. ეს შეიძლება XcodeGen-ს შესაფერის საფუძვლად აქციოს [ინსტრუმენტების აშენებისთვის](https://github.com/MobileNativeFoundation/rules_xcodeproj), როგორც ეს ჩანს Bazel-ის საზოგადოებაში, მაგრამ ის არ არის ოპტიმალური ინკლუზიური პროექტის ევოლუციისთვის, რომელიც მიზნად ისახავს ჯანსაღი და პროდუქტიული გარემოს შენარჩუნებას. თუ დღეს იყენებთ XcodeGen-ს, [XcodeGen vs Tuist](https://tuist.dev/compare/xcodegen) ხსნის, თუ რომელი Tuist-ის ფუნქციები მუშაობს თქვენს არსებულ XcodeGen-ის პროექტთან; Tuist-ის გენერირებულ პროექტებზე გადასასვლელად, იხილეთ <.localized_link href="/guides/features/projects/adoption/migrate/xcodegen-project">მიგრაციის სახელმძღვანელო</.localized_link>.

### Bazel {#bazel}

[Bazel](https://bazel.build) არის მოწინავე აშენების სისტემა, რომელიც ცნობილია თავისი დისტანციური ქეშირების ფუნქციებით და ძირითადად ამ შესაძლებლობის გამო იძენს პოპულარობას Swift-ის საზოგადოებაში. თუმცა, Xcode-ისა და მისი აშენების სისტემის შეზღუდული გაფართოებადობის გათვალისწინებით, მისი Bazel-ის სისტემით ჩანაცვლება მნიშვნელოვან ძალისხმევასა და შენარჩუნებას მოითხოვს. მხოლოდ რამდენიმე კომპანიას, რომელსაც აქვს მდიდარი რესურსები, შეუძლია ამ დამატებითი ხარჯის ატანა, რაც ჩანს იმ შერჩეული კომპანიების სიიდან, რომლებიც მნიშვნელოვნად ინვესტირებენ Bazel-ის Xcode-თან ინტეგრირებაში. საინტერესოა, რომ საზოგადოებამ შექმნა [ინსტრუმენტი](https://github.com/MobileNativeFoundation/rules_xcodeproj), რომელიც იყენებს Bazel-ის XcodeGen-ს Xcode-ის პროექტის გენერირებისთვის. ეს იწვევს კონვერტაციების რთულ ჯაჭვს: Bazel-ის ფაილებიდან XcodeGen YAML-მდე და საბოლოოდ Xcode-ის პროექტებამდე. ასეთი მრავალშრიანი არაპირდაპირობა ხშირად ართულებს პრობლემების აღმოჩენას, რაც პრობლემების დიაგნოსტიკასა და გადაწყვეტას უფრო რთულს ხდის.
