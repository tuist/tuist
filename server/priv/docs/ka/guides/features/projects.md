# გენერირებული პროექტები {#generated-projects}

Tuist-ის გენერირებული პროექტები არის საიმედო ალტერნატივა, რომელიც ეხმარება ამ გამოწვევების დაძლევაში სირთულისა და ხარჯების მისაღებ დონეზე შენარჩუნებით. ის Xcode-ის პროექტებს განიხილავს როგორც ფუნდამენტურ ელემენტს, უზრუნველყოფს მდგრადობას Xcode-ის მომავალი განახლებების მიმართ და იყენებს Xcode-ის პროექტების გენერაციას, რათა გუნდებს მიაწოდოს მოდულარიზაციაზე ორიენტირებული დეკლარატიული API. Tuist იყენებს პროექტის დეკლარაციას მოდულარიზაციის სირთულეების გასამარტივებლად, აშენების ან ტესტირების მსგავსი სამუშაო ნაკადების ოპტიმიზაციისთვის სხვადასხვა გარემოში და ხელს უწყობს Xcode-ის პროექტების ევოლუციის გამარტივებასა და დემოკრატიზაციას.

## როგორ მუშაობს? {#how-does-it-work}

გენერირებულ პროექტებთან სამუშაოს დასაწყებად, საჭიროა მხოლოდ თქვენი პროექტის განსაზღვრა **Tuist-ის დომენური სპეციფიკური ენის (DSL)** გამოყენებით. ეს გულისხმობს ისეთი მანიფესტური ფაილების გამოყენებას, როგორიცაა `Workspace.swift` ან `Project.swift`. თუ ადრე მუშაობდით Swift Package Manager-თან, მიდგომა ძალიან მსგავსია.

პროექტის განსაზღვრის შემდეგ, Tuist გთავაზობთ სხვადასხვა სამუშაო ნაკადს მის მართვისა და ურთიერთქმედებისთვის:

- **გენერირება:** ეს არის საბაზისო სამუშაო ნაკადი. გამოიყენეთ ის Xcode-თან თავსებადი Xcode-ის პროექტის შესაქმნელად.
- **<.localized_link href="/cli/build">აშენება</.localized_link>:** ეს სამუშაო ნაკადი არა მხოლოდ აგენერირებს Xcode-ის პროექტს, არამედ იყენებს `xcodebuild`-ს მის კომპილაციისთვის.
- **<.localized_link href="/cli/test">ტესტირება</.localized_link>:** აშენების სამუშაო ნაკადის მსგავსად, ეს არა მხოლოდ აგენერირებს Xcode-ის პროექტს, არამედ იყენებს `xcodebuild`-ს მის ტესტირებისთვის.

## გამოწვევები Xcode-ის პროექტებთან {#challenges-with-xcode-projects}

Xcode-ის პროექტების ზრდასთან ერთად, **ორგანიზაციებმა შეიძლება წარმოქმნან პროდუქტიულობის ვარდნა** რამდენიმე ფაქტორის გამო, მათ შორის არასანდო ინკრემენტული ბილდების, პრობლემების წინაშე მდგარი დეველოპერების მიერ Xcode-ის გლობალური ქეშის ხშირი გასუფთავების და მყიფე პროექტის კონფიგურაციების გამო. სწრაფი ფუნქციების განვითარების შესანარჩუნებლად, ორგანიზაციები ჩვეულებრივ იკვლევენ სხვადასხვა სტრატეგიას.

ზოგიერთი ორგანიზაცია ირჩევს კომპილატორის გვერდის ავლით პლატფორმის აბსტრაქციას JavaScript-ზე დაფუძნებული დინამიური რანთაიმების გამოყენებით, როგორიცაა [React Native](https://reactnative.dev/). მიუხედავად იმისა, რომ ეს მიდგომა შეიძლება იყოს ეფექტური, ის [ართულებს პლატფორმის ნატიური ფუნქციების წვდომას](https://shopify.engineering/building-app-clip-react-native). სხვა ორგანიზაციები ირჩევენ **კოდბაზის მოდულარიზაციას**, რაც ეხმარება ცხადი საზღვრების დადგენაში, კოდბაზასთან მუშაობას ამარტივებს და აუმჯობესებს აშენების დროის საიმედოობას. თუმცა, Xcode-ის პროექტის ფორმატი არ არის განკუთვნილი მოდულარობისთვის და იწვევს იმპლიციტურ კონფიგურაციებს, რომელთა გაგება ცოტას შეუძლია და ხშირ კონფლიქტებს. ეს იწვევს ცუდ „bus factor“-ს და მიუხედავად იმისა, რომ ინკრემენტული ბილდები შეიძლება გაუმჯობესდეს, დეველოპერებმა მაინც შეიძლება ხშირად გაასუფთაონ Xcode-ის ბილდის ქეში (ე.ი. derived data), როდესაც ბილდები ვერ ხერხდება. ამის გადასაჭრელად, ზოგიერთი ორგანიზაცია ირჩევს **Xcode-ის ბილდის სისტემის მიტოვებას** და ალტერნატივების, როგორიცაა [Buck](https://buck.build/) ან [Bazel](https://bazel.build/), ათვისებას. თუმცა, ეს მოჰყვება [მაღალ სირთულესა და მოვლის ტვირთს](https://bazel.build/migrate/xcode).


## ალტერნატივები {#alternatives}

### Swift Package Manager {#swift-package-manager}

მიუხედავად იმისა, რომ Swift Package Manager (SPM) ძირითადად ფოკუსირდება დამოკიდებულებებზე, Tuist სხვა მიდგომას გთავაზობთ. Tuist-ით თქვენ არა მხოლოდ განსაზღვრავთ პაკეტებს SPM-თან ინტეგრაციისთვის; თქვენ აყალიბებთ თქვენს პროექტებს ისეთი ნაცნობი კონცეფციების გამოყენებით, როგორიცაა პროექტები, სამუშაო სივრცეები, სამიზნეები და სქემები.

### XcodeGen {#xcodegen}

[XcodeGen](https://github.com/yonaskolb/XcodeGen) არის სპეციალიზებული პროექტის გენერატორი, რომელიც შექმნილია კოლაბორატიულ Xcode-ის პროექტებში კონფლიქტების შესამცირებლად და Xcode-ის შიდა მუშაობის ზოგიერთი სირთულის გასამარტივებლად. თუმცა, პროექტები განისაზღვრება სერიალიზებადი ფორმატების გამოყენებით, როგორიცაა [YAML](https://yaml.org/). Swift-ისგან განსხვავებით, ეს არ აძლევს დეველოპერებს საშუალებას ააგონ აბსტრაქციები ან შემოწმებები დამატებითი ინსტრუმენტების ჩართვის გარეშე. მიუხედავად იმისა, რომ XcodeGen გვთავაზობს დამოკიდებულებების შიდა წარმოდგენაზე ასახვის გზას ვალიდაციისა და ოპტიმიზაციისთვის, ის მაინც აქვეყნებს დეველოპერებს Xcode-ის ნიუანსების წინაშე. ეს შეიძლება XcodeGen-ს გახადოს შესაფერის საფუძვლად [ინსტრუმენტების აგებისთვის](https://github.com/MobileNativeFoundation/rules_xcodeproj), როგორც ეს ჩანს Bazel-ის საზოგადოებაში, მაგრამ ის არ არის ოპტიმალური ინკლუზიური პროექტის ევოლუციისთვის, რომელიც მიზნად ისახავს ჯანსაღი და პროდუქტიული გარემოს შენარჩუნებას.

### Bazel {#bazel}

[Bazel](https://bazel.build) არის მოწინავე ბილდის სისტემა, რომელიც ცნობილია თავისი დისტანციური ქეშირების ფუნქციებით და პოპულარობას იძენს Swift-ის საზოგადოებაში ძირითადად ამ შესაძლებლობის გამო. თუმცა, Xcode-ისა და მისი ბილდის სისტემის შეზღუდული გაფართოებადობის გათვალისწინებით, მისი Bazel-ის სისტემით ჩანაცვლება მნიშვნელოვან ძალისხმევასა და მოვლას მოითხოვს. მხოლოდ რამდენიმე კომპანიას, რომელსაც აქვს საკმარისი რესურსები, შეუძლია ამ დანახარჯის ატანა, რაც ჩანს იმ შერჩეული ფირმების სიიდან, რომლებიც მნიშვნელოვნად ინვესტირებენ Bazel-ის Xcode-თან ინტეგრირებაში. საინტერესოა, რომ საზოგადოებამ შექმნა [ინსტრუმენტი](https://github.com/MobileNativeFoundation/rules_xcodeproj), რომელიც იყენებს Bazel-ის XcodeGen-ს Xcode-ის პროექტის გენერირებისთვის. ეს იწვევს კონვერტაციების რთულ ჯაჭვს: Bazel-ის ფაილებიდან XcodeGen YAML-ში და საბოლოოდ Xcode-ის პროექტებში. ასეთი მრავალშრიანი არაპირდაპირობა ხშირად ართულებს პრობლემების აღმოჩენას, რაც პრობლემების დიაგნოსტიკასა და გადაწყვეტას უფრო რთულს ხდის.
