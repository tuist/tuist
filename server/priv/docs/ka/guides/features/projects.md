# გენერირებული პროექტები {#generated-projects}

Tuist-ის გენერირებული პროექტები არის საიმედო ალტერნატივა, რომელიც ეხმარება ამ გამოწვევების დაძლევაში სირთულისა და ხარჯების მისაღებ დონეზე შენარჩუნებით. ის Xcode-ის პროექტებს ფუნდამენტურ ელემენტად მიიჩნევს, უზრუნველყოფს მდგრადობას Xcode-ის მომავალი განახლებების მიმართ და იყენებს Xcode-ის პროექტების გენერაციას, რათა გუნდებს მიაწოდოს მოდულარიზაციაზე ორიენტირებული დეკლარატიული API. Tuist იყენებს პროექტის დეკლარაციას მოდულარიზაციის სირთულეების გასამარტივებლად, აშენების ან ტესტირების მსგავსი სამუშაო ნაკადების ოპტიმიზაციისთვის სხვადასხვა გარემოში და ხელს უწყობს Xcode-ის პროექტების ევოლუციის ხელმისაწვდომობას.

## როგორ მუშაობს? {#how-does-it-work}

გენერირებულ პროექტებთან სამუშაოს დასაწყებად, საჭიროა მხოლოდ თქვენი პროექტის განსაზღვრა **Tuist-ის დომენზე სპეციფიკური ენის (DSL)** გამოყენებით. ეს გულისხმობს ისეთი მანიფესტური ფაილების გამოყენებას, როგორიცაა `Workspace.swift` ან `Project.swift`. თუ ადრე მუშაობდით Swift Package Manager-თან, მიდგომა ძალიან მსგავსია.

პროექტის განსაზღვრის შემდეგ, Tuist გთავაზობთ სხვადასხვა სამუშაო ნაკადს მისი მართვისა და ურთიერთქმედებისთვის:

- **გენერირება:** ეს არის საბაზისო სამუშაო ნაკადი. გამოიყენეთ ის Xcode-თან თავსებადი Xcode-ის პროექტის შესაქმნელად.
- **<.localized_link href="/cli/build">აშენება</.localized_link>:** ეს სამუშაო ნაკადი არა მხოლოდ ქმნის Xcode-ის პროექტს, არამედ იყენებს `xcodebuild`-ს მის კომპილირებისთვის.
- **<.localized_link href="/cli/test">ტესტირება</.localized_link>:** აშენების სამუშაო ნაკადის მსგავსად, ეს არა მხოლოდ ქმნის Xcode-ის პროექტს, არამედ იყენებს `xcodebuild`-ს მის ტესტირებისთვის.

## გამოწვევები Xcode-ის პროექტებთან {#challenges-with-xcode-projects}

Xcode-ის პროექტების ზრდასთან ერთად, **ორგანიზაციებმა შეიძლება შეამჩნიონ პროდუქტიულობის კლება** რამდენიმე ფაქტორის გამო, მათ შორის არასანდო ინკრემენტული ბილდები, Xcode-ის გლობალური ქეშის ხშირი გასუფთავება პრობლემების წინაშე მდგომი დეველოპერების მიერ და არამდგრადი პროექტის კონფიგურაციები. სწრაფი ფუნქციების განვითარების შესანარჩუნებლად, ორგანიზაციები ჩვეულებრივ სხვადასხვა სტრატეგიას იკვლევენ.

ზოგიერთი ორგანიზაცია ირჩევს კომპილატორის გვერდის ავლით პლატფორმის აბსტრაქციას JavaScript-ზე დაფუძნებული დინამიური გარემოების გამოყენებით, როგორიცაა [React Native](https://reactnative.dev/). მიუხედავად იმისა, რომ ეს მიდგომა შეიძლება ეფექტური იყოს, ის [ართულებს პლატფორმის ნატიურ ფუნქციებზე წვდომას](https://shopify.engineering/building-app-clip-react-native). სხვა ორგანიზაციები ირჩევენ **კოდის ბაზის მოდულარიზაციას**, რაც ეხმარება ცხადი საზღვრების დადგენას, კოდის ბაზასთან მუშაობას ამარტივებს და აშენების დროის საიმედოობას აუმჯობესებს. თუმცა, Xcode-ის პროექტის ფორმატი არ არის შექმნილი მოდულარობისთვის და იწვევს იმპლიციტურ კონფიგურაციებს, რომელთა გაგებაც ცოტას შეუძლია და ხშირ კონფლიქტებს. ეს იწვევს ცუდ „bus factor“-ს და მიუხედავად იმისა, რომ ინკრემენტული ბილდები შეიძლება გაუმჯობესდეს, დეველოპერები მაინც ხშირად ასუფთავებენ Xcode-ის აშენების ქეშს (ე.ი. derived data), როდესაც ბილდები ვერ ხერხდება. ამის გადასაჭრელად, ზოგიერთი ორგანიზაცია ირჩევს **Xcode-ის აშენების სისტემის მიტოვებას** და ისეთი ალტერნატივების აპნებას, როგორიცაა [Buck](https://buck.build/) ან [Bazel](https://bazel.build/). თუმცა, ეს თან ახლავს [მაღალ სირთულესა და შენარჩუნების ტვირთს](https://bazel.build/migrate/xcode).


## ალტერნატივები {#alternatives}

### Swift Package Manager {#swift-package-manager}

მიუხედავად იმისა, რომ Swift Package Manager (SPM) ძირითადად დამოკიდებულებებზეა ორიენტირებული, Tuist სხვა მიდგომას გთავაზობთ. Tuist-ით თქვენ არა მხოლოდ განსაზღვრავთ პაკეტებს SPM-თან ინტეგრაციისთვის; თქვენ ქმნით თქვენს პროექტებს ისეთი ნაცნობი კონცეფციების გამოყენებით, როგორიცაა პროექტები, სამუშაო სივრცეები, სამიზნეები და სქემები.

### XcodeGen {#xcodegen}

[XcodeGen](https://github.com/yonaskolb/XcodeGen) არის სპეციალიზებული პროექტის გენერატორი, შექმნილი კოლაბორატიულ Xcode-ის პროექტებში კონფლიქტების შესამცირებლად და Xcode-ის შიდა მუშაობის ზოგიერთი სირთულის გასამარტივებლად. თუმცა, პროექტები განისაზღვრება სერიალიზებადი ფორმატების გამოყენებით, როგორიცაა [YAML](https://yaml.org/). Swift-ისგან განსხვავებით, ეს არ აძლევს დეველოპერებს საშუალებას ააგონ აბსტრაქციები ან შემოწმებები დამატებითი ინსტრუმენტების ჩართვის გარეშე. მიუხედავად იმისა, რომ XcodeGen გთავაზობთ დამოკიდებულებების შიდა წარმოდგენაზე ასახვის გზას ვალიდაციისა და ოპტიმიზაციისთვის, ის მაინც აქვეყნებს დეველოპერებს Xcode-ის ნიუანსების წინაშე. ეს შეიძლება XcodeGen-ს შესაფერის საფუძვლად აქციოს [ინსტრუმენტების აგებისთვის](https://github.com/MobileNativeFoundation/rules_xcodeproj), როგორც ეს Bazel-ის საზოგადოებაში ჩანს, მაგრამ ის არ არის ოპტიმალური ინკლუზიური პროექტის ევოლუციისთვის, რომელიც მიზნად ისახავს ჯანსაღი და პროდუქტიული გარემოს შენარჩუნებას.

### Bazel {#bazel}

[Bazel](https://bazel.build) არის მოწინავე აშენების სისტემა, ცნობილი თავისი დისტანციური ქეშირების ფუნქციებით, რომელიც პოპულარობას იძენს Swift-ის საზოგადოებაში ძირითადად ამ შესაძლებლობის გამო. თუმცა, Xcode-ისა და მისი აშენების სისტემის შეზღუდული გაფართოებადობის გათვალისწინებით, მისი Bazel-ის სისტემით ჩანაცვლება მნიშვნელოვან ძალისხმევასა და შენარჩუნებას მოითხოვს. მხოლოდ რამდენიმე კომპანიას, რომელსაც აქვს საკმარისი რესურსები, შეუძლია ამ დანახარჯის გაწევა, რაც ჩანს Bazel-ის Xcode-თან ინტეგრირებაში მნიშვნელოვნად ინვესტირებადი ფირმების შერჩეული სიიდან. საინტერესოა, რომ საზოგადოებამ შექმნა [ინსტრუმენტი](https://github.com/MobileNativeFoundation/rules_xcodeproj), რომელიც იყენებს Bazel-ის XcodeGen-ს Xcode-ის პროექტის გენერირებისთვის. ეს იწვევს გადაყვანების რთულ ჯაჭვს: Bazel-ის ფაილებიდან XcodeGen YAML-ზე და საბოლოოდ Xcode-ის პროექტებზე. ასეთი მრავალშრიანი არაპირდაპირობა ხშირად ართულებს პრობლემების აღმოჩენას, რაც პრობლემების დიაგნოსტიკასა და გადაჭრას უფრო რთულს ხდის.
