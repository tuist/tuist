# გენერირებული პროექტები {#generated-projects}

Tuist-ის გენერირებული პროექტები არის სიცოცხლისუნარიანი ალტერნატივა, რომელიც ეხმარება ამ გამოწვევების გადალახვას, სირთულისა და ხარჯების მისაღებ დონეზე შენარჩუნებით. ის Xcode-ის პროექტებს ფუნდამენტურ ელემენტად მიიჩნევს, რაც უზრუნველყოფს მდგრადობას მომავალი Xcode-ის განახლებების მიმართ, და იყენებს Xcode-ის პროექტების გენერაციას, რათა გუნდებს მიაწოდოს მოდულარიზაციაზე ორიენტირებული დეკლარატიული API. Tuist იყენებს პროექტის დეკლარაციას მოდულარიზაციის სირთულეების გასამარტივებლად, აშენების ან ტესტირების მსგავსი სამუშაო ნაკადების ოპტიმიზაციისთვის სხვადასხვა გარემოში და ხელს უწყობს Xcode-ის პროექტების ევოლუციის გამარტივებასა და დემოკრატიზაციას.

## როგორ მუშაობს? {#how-does-it-work}

გენერირებულ პროექტებთან სამუშაოს დასაწყებად, საჭიროა მხოლოდ თქვენი პროექტის განსაზღვრა **Tuist-ის დომენური სპეციფიკური ენის (DSL)** გამოყენებით. ეს გულისხმობს ისეთი მანიფესტური ფაილების გამოყენებას, როგორიცაა `Workspace.swift` ან `Project.swift`. თუ ადრე მუშაობდით Swift Package Manager-თან, მიდგომა ძალიან მსგავსია.

მას შემდეგ, რაც განსაზღვრავთ თქვენს პროექტს, Tuist გთავაზობთ მის მართვისა და ურთიერთქმედების სხვადასხვა სამუშაო ნაკადს:

- **გენერირება:** ეს არის საბაზისო სამუშაო ნაკადი. გამოიყენეთ ის Xcode-თან თავსებადი Xcode-ის პროექტის შესაქმნელად.
- **<.localized_link href="/cli/build">აშენება</.localized_link>:** ეს სამუშაო ნაკადი არა მხოლოდ აგენერირებს Xcode-ის პროექტს, არამედ იყენებს `xcodebuild`-ს მის კომპილაციისთვის.
- **<.localized_link href="/cli/test">ტესტირება</.localized_link>:** აშენების სამუშაო ნაკადის მსგავსად, ეს არა მხოლოდ აგენერირებს Xcode-ის პროექტს, არამედ იყენებს `xcodebuild`-ს მის ტესტირებისთვის.

## გამოწვევები Xcode-ის პროექტებთან {#challenges-with-xcode-projects}

Xcode-ის პროექტების ზრდასთან ერთად, **ორგანიზაციებმა შეიძლება წარმოქმნან პროდუქტიულობის ვარდნა** რამდენიმე ფაქტორის გამო, მათ შორის არასანდო ინკრემენტული ბილდები, პრობლემების შემთხვევაში Xcode-ის გლობალური ქეშის ხშირი გასუფთავება დეველოპერების მიერ და მყიფე პროექტის კონფიგურაციები. სწრაფი ფუნქციების განვითარების შესანარჩუნებლად, ორგანიზაციები ჩვეულებრივ იკვლევენ სხვადასხვა სტრატეგიას.

ზოგიერთი ორგანიზაცია ირჩევს კომპილატორის გვერდის ავლით პლატფორმის აბსტრაქციას JavaScript-ზე დაფუძნებული დინამიური გარშემოწერილობების გამოყენებით, როგორიცაა [React Native](https://reactnative.dev/). მიუხედავად იმისა, რომ ეს მიდგომა შეიძლება ეფექტური იყოს, ის [ართულებს პლატფორმის ნატიური ფუნქციების გამოყენებას](https://shopify.engineering/building-app-clip-react-native). სხვა ორგანიზაციები ირჩევენ **კოდის ბაზის მოდულარიზაციას**, რაც ეხმარება ცხადი საზღვრების დამყარებას, კოდის ბაზასთან მუშაობას ამარტივებს და აუმჯობესებს აშენების დროის სანდოობას. თუმცა, Xcode-ის პროექტის ფორმატი არ არის განკუთვნილი მოდულარობისთვის და იწვევს იმპლიციტურ კონფიგურაციებს, რომელთა გაგება ცოტას შეუძლია და ხშირ კონფლიქტებს. ეს იწვევს ცუდ „bus factor“-ს და მიუხედავად იმისა, რომ ინკრემენტული ბილდები შეიძლება გაუმჯობესდეს, დეველოპერებმა მაინც შეიძლება ხშირად გაასუფთაონ Xcode-ის აშენების ქეში (ე.ი. derived data), როდესაც ბილდები ვერ ხერხდება. ამის გადასაჭრელად, ზოგიერთი ორგანიზაცია ირჩევს **Xcode-ის აშენების სისტემის მიტოვებას** და ალტერნატივების, როგორიცაა [Buck](https://buck.build/) ან [Bazel](https://bazel.build/), აპნებას. თუმცა, ეს მოჰყვება [მაღალ სირთულეს და მოვლის ტვირთს](https://bazel.build/migrate/xcode).


## ალტერნატივები {#alternatives}

### Swift Package Manager {#swift-package-manager}

მიუხედავად იმისა, რომ Swift Package Manager (SPM) ძირითადად დამოკიდებულებებზეა ორიენტირებული, Tuist სხვა მიდგომას სთავაზობს. Tuist-ით თქვენ არა მხოლოდ განსაზღვრავთ პაკეტებს SPM-თან ინტეგრაციისთვის; თქვენ აყალიბებთ თქვენს პროექტებს ნაცნობი კონცეფციების გამოყენებით, როგორიცაა პროექტები, სამუშაო სივრცეები, სამიზნეები და სქემები.

### XcodeGen {#xcodegen}

[XcodeGen](https://github.com/yonaskolb/XcodeGen) არის სპეციალიზებული პროექტის გენერატორი, რომელიც შექმნილია თანამშრომლობით Xcode-ის პროექტებში კონფლიქტების შესამცირებლად და Xcode-ის შიდა მუშაობის ზოგიერთი სირთულის გასამარტივებლად. თუმცა, პროექტები განისაზღვრება სერიალიზებადი ფორმატების გამოყენებით, როგორიცაა [YAML](https://yaml.org/). Swift-ისგან განსხვავებით, ეს არ აძლევს დეველოპერებს საშუალებას ააგონ აბსტრაქციები ან შემოწმებები დამატებითი ინსტრუმენტების ჩართვის გარეშე. მიუხედავად იმისა, რომ XcodeGen გთავაზობთ დამოკიდებულებების შიდა წარმოდგენაზე ასახვის გზას ვალიდაციისა და ოპტიმიზაციისთვის, ის მაინც აცნობს დეველოპერებს Xcode-ის ნიუანსებს. ეს შეიძლება XcodeGen-ს შეუფერებელ საფუძვლად აქციოს [ინსტრუმენტების აგებისთვის](https://github.com/MobileNativeFoundation/rules_xcodeproj), როგორც ეს ჩანს Bazel-ის საზოგადოებაში, მაგრამ ის არ არის ოპტიმალური ინკლუზიური პროექტის ევოლუციისთვის, რომელიც მიზნად ისახავს ჯანსაღი და პროდუქტიული გარემოს შენარჩუნებას. თუ დღეს იყენებთ XcodeGen-ს, [XcodeGen vs Tuist](https://tuist.dev/compare/xcodegen) ხსნის, თუ რომელი Tuist-ის შესაძლებლობები მუშაობს თქვენს არსებულ XcodeGen-ის პროექტთან; Tuist-ის გენერირებულ პროექტებზე გადასასვლელად, იხილეთ <.localized_link href="/guides/features/projects/adoption/migrate/xcodegen-project">მიგრაციის სახელმძღვანელო</.localized_link>.

### Bazel {#bazel}

[Bazel](https://bazel.build) არის გადმოწმული აშენების სისტემა, რომელიც ცნობილია თავისი დისტანციური ქეშირების ფუნქციებით და პოპულარობას იძენს Swift-ის საზოგადოებაში ძირითადად ამ შესაძლებლობის გამო. თუმცა, Xcode-ისა და მისი აშენების სისტემის შეზღუდული გაფართოებადობის გათვალისწინებით, მისი Bazel-ის სისტემით ჩანაცვლება მნიშვნელოვან ძალისხმევასა და მოვლას მოითხოვს. მხოლოდ რამდენიმე კომპანიას, რომელსაც აქვს საკმარისი რესურსები, შეუძლია ამ ტვირთის ატანა, რაც ჩანს იმ შერჩეული ფირმების სიიდან, რომლებიც მნიშვნელოვნად ინვესტირებენ Bazel-ის Xcode-თან ინტეგრაციაში. საინტერესოა, რომ საზოგადოებამ შექმნა [ინსტრუმენტი](https://github.com/MobileNativeFoundation/rules_xcodeproj), რომელიც იყენებს Bazel-ის XcodeGen-ს Xcode-ის პროექტის გენერირებისთვის. ეს იწვევს გადაქცევების რთულ ჯაჭვს: Bazel-ის ფაილებიდან XcodeGen YAML-მდე და საბოლოოდ Xcode-ის პროექტებამდე. ასეთი ფენოვანი არაპირდაპირობა ხშირად ართულებს პრობლემების აღმოფხვრას, რაც პრობლემების დიაგნოსტიკასა და გადაჭრას უფრო რთულს ხდის.
