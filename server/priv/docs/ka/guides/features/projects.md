# გენერირებული პროექტები {#generated-projects}

Tuist Generated Projects არის საიმედო ალტერნატივა, რომელიც ეხმარება ამ გამოწვევების გადალახვას სირთულისა და ხარჯების მისაღებ დონეზე შენარჩუნებით. ის Xcode-ის პროექტებს ფუნდამენტურ ელემენტად მიიჩნევს, რაც უზრუნველყოფს მდგრადობას Xcode-ის მომავალი განახლებების მიმართ, და იყენებს Xcode-ის პროექტების გენერაციას, რათა გუნდებს მიაწოდოს მოდულარიზაციაზე ორიენტირებული დეკლარატიული API. Tuist იყენებს პროექტის დეკლარაციას მოდულარიზაციის სირთულეების გასამარტივებლად, ბილდის ან ტესტის მსგავსი სამუშაო ნაკადების ოპტიმიზაციისთვის სხვადასხვა გარემოში და ხელს უწყობს Xcode-ის პროექტების ევოლუციის გამარტივებასა და დემოკრატიზაციას.

## როგორ მუშაობს? {#how-does-it-work}

გენერირებულ პროექტებთან სამუშაოს დასაწყებად, საჭიროა მხოლოდ თქვენი პროექტის განსაზღვრა **Tuist-ის დომენზე სპეციფიკური ენის (DSL)** გამოყენებით. ეს გულისხმობს ისეთი მანიფესტური ფაილების გამოყენებას, როგორიცაა `Workspace.swift` ან `Project.swift`. თუ ადრე მუშაობდით Swift Package Manager-თან, მიდგომა ძალიან მსგავსია.

მას შემდეგ, რაც განსაზღვრავთ თქვენს პროექტს, Tuist გთავაზობთ სხვადასხვა სამუშაო ნაკადს მისი მართვისა და მასთან ურთიერთქმედებისთვის:

- **გენერირება:** ეს არის საბაზო სამუშაო ნაკადი. გამოიყენეთ ის Xcode-თან თავსებადი Xcode-ის პროექტის შესაქმნელად.
- **<.localized_link href="/cli/build">ბილდი</.localized_link>:** ეს სამუშაო ნაკადი არა მხოლოდ ქმნის Xcode-ის პროექტს, არამედ ასევე იყენებს `xcodebuild` მის კომპილირებისთვის.
- **<.localized_link href="/cli/test">ტესტი</.localized_link>:** ბილდის სამუშაო ნაკადის მსგავსად, ეს არა მხოლოდ ქმნის Xcode-ის პროექტს, არამედ იყენებს `xcodebuild` მის ტესტირებისთვის.

## გამოწვევები Xcode-ის პროექტებთან {#challenges-with-xcode-projects}

Xcode-ის პროექტების ზრდასთან ერთად, **ორგანიზაციებმა შეიძლება წარმოქმნან პროდუქტიულობის ვარდნა** რამდენიმე ფაქტორის გამო, მათ შორის არასანდო ინკრემენტული ბილდები, პრობლემების შემთხვევაში Xcode-ის გლობალური ქეშის ხშირი გასუფთავება დეველოპერების მიერ და არამდგრადი პროექტის კონფიგურაციები. სწრაფი ფუნქციების განვითარების შესანარჩუნებლად, ორგანიზაციები ჩვეულებრივ იკვლევენ სხვადასხვა სტრატეგიას.

ზოგიერთი ორგანიზაცია ირჩევს კომპილატორის გვერდის ავლით პლატფორმის აბსტრაქციას JavaScript-ზე დაფუძნებული დინამიური გარემოების გამოყენებით, მაგალითად [React Native](https://reactnative.dev/). მიუხედავად იმისა, რომ ეს მიდგომა შეიძლება იყოს ეფექტური, ის [ართულებს პლატფორმის ნატიურ ფუნქციებზე წვდომას](https://shopify.engineering/building-app-clip-react-native). სხვა ორგანიზაციები ირჩევენ **კოდის ბაზის მოდულარიზაციას**, რაც ეხმარება ცხადი საზღვრების დადგენაში, კოდის ბაზასთან მუშაობას ამარტივებს და ბილდის დროის საიმედოობას აუმჯობესებს. თუმცა, Xcode-ის პროექტის ფორმატი არ არის განკუთვნილი მოდულარობისთვის და იწვევს იმპლიციტურ კონფიგურაციებს, რომლებსაც ცოტა ვინ ესმის და ხშირ კონფლიქტებს. ეს იწვევს ცუდ „bus factor“-ს და მიუხედავად იმისა, რომ ინკრემენტული ბილდები შეიძლება გაუმჯობესდეს, დეველოპერები მაინც ხშირად ასუფთავებენ Xcode-ის ბილდის ქეშს (ე.ი. derived data), როდესაც ბილდები ვერ ხერხდება. ამის გადასაჭრელად, ზოგიერთი ორგანიზაცია ირჩევს **Xcode-ის ბილდის სისტემის მიტოვებას** და ალტერნატივების, როგორიცაა [Buck](https://buck.build/) ან [Bazel](https://bazel.build/), აპნებას. თუმცა, ეს მოჰყვება [მაღალ სირთულესა და მოვლასთან დაკავშირებულ ტვირთს](https://bazel.build/migrate/xcode).


## ალტერნატივები {#alternatives}

### Swift Package Manager {#swift-package-manager}

მიუხედავად იმისა, რომ Swift Package Manager (SPM) ძირითადად დამოკიდებულებებზეა ორიენტირებული, Tuist სხვა მიდგომას გთავაზობთ. Tuist-ით თქვენ არა მხოლოდ განსაზღვრავთ პაკეტებს SPM-თან ინტეგრაციისთვის; თქვენ აყალიბებთ თქვენს პროექტებს ისეთი ნაცნობი კონცეფციების გამოყენებით, როგორიცაა პროექტები, სამუშაო სივრცეები, სამიზნეები და სქემები.

### XcodeGen {#xcodegen}

[XcodeGen](https://github.com/yonaskolb/XcodeGen) არის სპეციალიზებული პროექტის გენერატორი, რომელიც შექმნილია კოლაბორატიულ Xcode-ის პროექტებში კონფლიქტების შესამცირებლად და Xcode-ის შიდა მუშაობის ზოგიერთი სირთულის გასამარტივებლად. თუმცა, პროექტები განისაზღვრება სერიალიზებადი ფორმატების გამოყენებით, როგორიცაა [YAML](https://yaml.org/). Swift-ისგან განსხვავებით, ეს არ აძლევს დეველოპერებს საშუალებას ააშენონ აბსტრაქციები ან შემოწმებები დამატებითი ინსტრუმენტების ჩართვის გარეშე. მიუხედავად იმისა, რომ XcodeGen გთავაზობთ დამოკიდებულებების შიდა წარმოდგენაზე ასახვის გზას ვალიდაციისა და ოპტიმიზაციისთვის, ის მაინც აცნობს დეველოპერებს Xcode-ის ნიუანსებს. ეს შეიძლება გახადოს XcodeGen შესაფერის საფუძვლად [ინსტრუმენტების აგებისთვის](https://github.com/MobileNativeFoundation/rules_xcodeproj), როგორც ეს ჩანს Bazel-ის საზოგადოებაში, მაგრამ ის არ არის ოპტიმალური ინკლუზიური პროექტის ევოლუციისთვის, რომელიც მიზნად ისახავს ჯანსაღი და პროდუქტიული გარემოს შენარჩუნებას. თუ დღეს იყენებთ XcodeGen-ს, [XcodeGen vs Tuist](https://tuist.dev/compare/xcodegen) ხსნის, რომელი Tuist-ის შესაძლებლობები მუშაობს თქვენს არსებულ XcodeGen-ის პროექტთან; Tuist-ის გენერირებულ პროექტებზე გადასასვლელად, იხილეთ <.localized_link href="/guides/features/projects/adoption/migrate/xcodegen-project">მიგრაციის სახელმძღვანელო</.localized_link>.

### Bazel {#bazel}

[Bazel](https://bazel.build) არის მოწინავე ბილდის სისტემა, რომელიც ცნობილია თავისი დისტანციური ქეშირების ფუნქციებით და სწორედ ამ შესაძლებლობის გამო იძენს პოპულარობას Swift-ის საზოგადოებაში. თუმცა, Xcode-ისა და მისი ბილდის სისტემის შეზღუდული გაფართოებადობის გათვალისწინებით, მისი Bazel-ის სისტემით ჩანაცვლება მნიშვნელოვან ძალისხმევასა და მოვლას მოითხოვს. მხოლოდ რამდენიმე კომპანიას, რომელსაც აქვს საკმარისი რესურსები, შეუძლია ამ დანახარჯის გაწევა, რაც ჩანს Bazel-ის Xcode-თან ინტეგრირებაში მნიშვნელოვანი ინვესტიციების ჩამდებ ფირმების შერჩეული სიიდან. საინტერესოა, რომ საზოგადოებამ შექმნა [ინსტრუმენტი](https://github.com/MobileNativeFoundation/rules_xcodeproj), რომელიც იყენებს Bazel-ის XcodeGen-ს Xcode-ის პროექტის გენერირებისთვის. ეს იწვევს გარდაქმნების რთულ ჯაჭვს: Bazel-ის ფაილებიდან XcodeGen YAML-ში და საბოლოოდ Xcode-ის პროექტებში. ასეთი მრავალშრიანი არაპირდაპირობა ხშირად ართულებს პრობლემების აღმოფხვრას, რაც პრობლემების დიაგნოსტიკასა და გადაჭრას უფრო რთულს ხდის.
