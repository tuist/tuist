# Model Context Protocol

[Model Context Protocol (MCP)](https://modelcontextprotocol.io/docs/getting-started/intro) არის ღია სტანდარტი, რომელიც საშუალებას აძლევს ხელოვნური ინტელექტის აგენტებს ურთიერთქმედონ გარე სერვისებთან და მონაცემთა წყაროებთან. ის უზრუნველყოფს ისეთი აპლიკაციების თავსებადობას Tuist-თან, როგორიცაა [Claude](https://claude.ai/), [Claude Code](https://docs.anthropic.com/en/docs/claude-code), [Codex](https://developers.openai.com/codex/), და რედაქტორები, მაგალითად [Zed](https://zed.dev), [Cursor](https://www.cursor.com) ან [Visual Studio Code](https://code.visualstudio.com).

Tuist განათავსებს Model Context Protocol-ის სერვერის ბოლოწერტილს მისამართზე `https://tuist.dev/mcp`. თქვენი კლიენტის ამ ბოლოწერტილთან დაკავშირებით, აგენტებს შეეძლებათ თქვენს Tuist პროექტის მონაცემებზე წვდომა, მათ შორის ტესტების ანალიტიკაზე, არასტაბილური ტესტების ანალიზზე და სხვა. ინსტრუმენტების უმეტესობა მხოლოდ კითხვის რეჟიმშია და შეზღუდულია ავტორიზებული Tuist პროექტის მონაცემებით. ანგარიშის მოწყობის ინსტრუმენტებს შეუძლიათ ანგარიშების ჩამოთვლა, ორგანიზაციების შექმნა, პროექტების შექმნა და არსებული მომხმარებლების დამატება ორგანიზაციებში, თუ ავტორიზებულ მომხმარებელს აქვს შესაბამისი ნებართვები. ყოველი ინსტრუმენტი აქვეყნებს ანოტაციებს, რომლებიც მიუთითებს, არის თუ არა ის მხოლოდ კითხვის რეჟიმში, შეუძლია თუ არა მას გამოიწვიოს რთულად შექცევადი ცვლილება და შეუძლია თუ არა შეცვალოს საჯარო ინტერნეტის მდგომარეობა. ანგარიშის მოწყობის ინსტრუმენტები მოითხოვს მომხმარებლის ავტორიზაციას. ისინი არ არის ხელმისაწვდომი პროექტის ტოკენებისთვის ან ჩვეულებრივი ანგარიშის ტოკენებისთვის. როდესაც მომხმარებელი ბრაუზერში ავტორიზებს კლიენტს ან ადასტურებს `auth.md` რეგისტრაციას, Tuist ამ სერთიფიკატს ასოცირდება მომხმარებელთან მხოლოდ Model Context Protocol-ის ბოლოწერტილზე, რათა მოწყობის ინსტრუმენტებმა შეძლონ მოთხოვნილი სამუშაო პროცესის დასრულება.

Tuist ახორციელებს [2026-07-28 პროტოკოლს](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http). მოთხოვნები უმდგომარეოა: კლიენტები ყოველ მოთხოვნასთან ერთად აგზავნიან პროტოკოლის მეტამონაცემებს და შეუძლიათ ინსტრუმენტების პირდაპირ გამოძახება ინიციალიზაციის გარეშე. `server/discover` აბრუნებს სერვერის იდენტიფიკატორს, შესაძლებლობებს, მხარდაჭერილ ვერსიებს და ინსტრუქციებს. არ არსებობს სესიის იდენტიფიკატორები ან დამოუკიდებელი მოვლენათა ნაკადები. კლიენტები, რომლებიც იყენებენ 2025-06-18 ან 2025-03-26 ინიციალიზაციის ნაკადს, კვლავ მხარდაჭერილია; ისინიც მუშაობენ სერვერის სესიების გარეშე.

## Model Context Protocol უნარების წინააღმდეგ

Model Context Protocol-ის ინსტრუმენტებს და <.localized_link href="/guides/features/agentic-coding/skills">უნარებს</.localized_link> შეიძლება ჰქონდეთ გადახურვა ფუნქციებში. ამჟამინდელი გადახურვის გათვალისწინებით, აირჩიეთ ერთი მიდგომა თითოეული სამუშაო პროცესისთვის და გამოიყენეთ ის თანმიმდევრულად, ნაცვლად ორივეს ერთ ნაკადში შერევისა.

კლიენტებისთვის, რომლებიც მხარს უჭერენ პლაგინების ინსტალაციას, გამოიყენეთ <.localized_link href="/guides/features/agentic-coding/plugins">Tuist პლაგინები</.localized_link> ორივეს ერთად დასაყენებლად.

## კონფიგურაცია

დაამატეთ `https://tuist.dev/mcp` როგორც დაშორებული Model Context Protocol სერვერი თქვენს კლიენტში. სერვერის ინიციალიზაციის ინსტრუქციები და საჯარო სერვერის ბარათი აღწერს OAuth 2.0-ს დინამიური კლიენტის რეგისტრაციით და სტანდარტული ბრაუზერის ავტორიზაციის ნაკადით უშუალოდ, აგენტებისგან გარე ავტორიზაციის დოკუმენტების მოთხოვნის ან მათი შემოწმების გარეშე. ეს სერვერის დონის ინსტრუქციები ინარჩუნებს სამუშაო პროცესის მითითებებს ზოგადს: ინსტრუმენტის ავტორიზაცია არ ავტორიზებს ადგილობრივ ბრძანების სტრიქონის ინსტრუმენტებს ან აგების სისტემის ინტეგრაციებს, და აგენტებმა უნდა გადაამოწმონ მოთხოვნილი ცვლილებები შესაბამისი Tuist ინსტრუმენტების მეშვეობით. აგების სისტემის სპეციფიკური მოწყობა და ავტორიზაციის შემოწმებები დოკუმენტირებულია ინტეგრაციის სახელმძღვანელოებში და მოთხოვნებში. Tuist კვლავ აქვეყნებს როგორც [Open Authorization](https://oauth.net/2/) აღმოჩენის მეტამონაცემებს, ასევე მიმდინარე [auth.md პროტოკოლს](https://workos.com/auth-md) მისამართზე `https://tuist.dev/auth.md` ცალ-ცალკე.

ბოლოწერტილი იღებს უმდგომარეო `2026-07-28` Model Context Protocol მოთხოვნის სიცოცხლის ციკლს, მათ შორის `server/discover`-ს, ძველი სესიაზე დაფუძნებული ციკლის გვერდით. არსებულ კლიენტებს შეუძლიათ გააგრძელონ მათი მიმდინარე კავშირის მეთოდის გამოყენება.

კლიენტები, რომლებიც მხარს უჭერენ Model Context Protocol მოვლენებს, შეუძლიათ გამოიწერონ პროექტის მოვლენები. იხილეთ [მოვლენები](#events) ხელმისაწვდომი მოვლენებისა და მიწოდების მოთხოვნებისთვის.

კლიენტები, რომლებიც უკვე მხარს უჭერენ დაშორებულ ბრაუზერის ავტორიზაციას, შეუძლიათ გააგრძელონ ავტორიზაცია ბრაუზერში. კლიენტებსა და აგენტებს, რომლებიც მხარს უჭერენ `auth.md`-ს, შეუძლიათ ანონიმურად რეგისტრაცია, სანდო პროვაიდერის იდენტიფიკატორის დამტკიცების წარდგენა ან სერვისით ავტორიზებული ელფოსტის მოთხოვნის დაწყება. რეგისტრაცია აბრუნებს Tuist-ით ხელმოწერილ იდენტიფიკატორის დამტკიცებას, რომელსაც აგენტი ცვლის სტანდარტულ ტოკენის ბოლოწერტილზე ერთსაათიანი წვდომის ტოკენის სანაცვლოდ. Tuist აქვეყნებს თავის საჯარო ხელმოწერის გასაღებს და მხარს უჭერს სტანდარტულ ტოკენის გაუქმებასა და პროვაიდერის უსაფრთხოების მოვლენების მიწოდებას.

არაავტორიზებულმა აგენტმა უნდა წაიკითხოს `WWW-Authenticate` ჰედერი, რომელიც დაბრუნდა Model Context Protocol-ის ბოლოწერტილიდან, მიიღოს დაცული რესურსის მეტამონაცემები, მიიღოს ავტორიზაციის სერვერის მეტამონაცემები და მიჰყვეს მის `agent_auth.skill` URL-ს. Tuist ასევე აბრუნებს იგივე ადგილობრივ `auth_md` URL-ს არაავტორიზებული პასუხის სხეულში, რათა ენის მოდელზე დაფუძნებულმა კლიენტებმა შეძლონ ნაკადის აღმოჩენა ნატიური კლიენტის ინტეგრაციაზე დამოკიდებულების გარეშე. განლაგების ადგილობრივი დოკუმენტი არის სიმართლის წყარო ბოლოწერტილის სახელების, მოთხოვნის სხეულების, მოთხოვნის გამოკითხვისა და დამტკიცების გაცვლისთვის.

სანამ აგენტი დაიწყებს ელფოსტის მოთხოვნას, მან უნდა სთხოვოს მომხმარებელს დაადასტუროს ელფოსტის მისამართი მათი Tuist ანგარიშისთვის. მან არ უნდა გამოიტანოს ეს მისამართი პროვაიდერის პროფილიდან, Git კონფიგურაციიდან, გარემოს ცვლადიდან ან სესიის მეტამონაცემებიდან.

ბოლოწერტილი იყენებს `mcp` სკოპის ჯგუფს. ანონიმურმა წინასწარი მოთხოვნის სერთიფიკატს შეუძლია აღმოაჩინოს შესაძლებლობები და წაიკითხოს საჯარო ინტეგრაციის მითითებები, მაგრამ ის არ განიხილება როგორც შესული მომხმარებელი. ბრაუზერის ავტორიზაციის ან მოთხოვნის შემდეგ, სერთიფიკატი არის მომხმარებელზე შეზღუდული და თითოეული ინსტრუმენტი იყენებს იგივე ავტორიზაციის შემოწმებებს, რასაც დაფა. დეტალებისთვის იხილეთ <.localized_link href="/guides/server/authentication#scope-groups">სკოპის ჯგუფების დოკუმენტაცია</.localized_link>.

ხელსაწყოები წვდომას ახდენენ იმ პროექტებზე, რომლებსაც ავთენტიკირებული მომხმარებელი უკვე კითხულობს. Xcode-ისა და Gradle-ის ბილდინგის ხელსაწყოები იღებენ ბილდის UUID-ს ან დაშბორდის URL-ს. UUID-მ ზუსტად ერთი პროექტი უნდა განსაზღვროს; თუ ის რამდენიმე პროექტში ჩანს, ხელსაწყო აბრუნებს „არ არის ნაპოვნი“-ს, ნაცვლად სხვა პროექტის ანგარიშის შერჩევისა. პროექტის ფარგლებში დაშბორდისა და API-ს კითხვები ხელმისაწვდომი რჩება. შეტყობინებული აქტორების იდენტიფიკატორები არიან დაუდასტურებელი წარწერები და არა სერთიფიკატები ან დამატებითი წვდომის უფლებები.

ბილდების სიისა და დეტალური ინფორმაციის ხელსაწყოები აჩვენებენ არასავალდებულო `tuist_version` მეტამონაცემებს: Xcode-ისა და Cargo-სთვის – Tuist CLI, Gradle-ისთვის – Tuist Gradle პლაგინი, ხოლო Mix-ისთვის – `tuist_ex` ბიბლიოთეკა. Xcode ასევე აჩვენებს `tuist_generation_version`-ს თავის დაკავშირებული პროექტის გენერაციის მოვლენიდან, რომელიც შეიძლება განსხვავდებოდეს ატვირთვადი CLI-სგან. გამოტოვებული მნიშვნელობები არის null და არა გამოყვანილი სერვერიდან ან სხვა ანგარიშიდან. Bazel იყენებს თავის არსებულ `bazel_version`-ს; Once-ის გაშვების დეტალები კი აჩვენებს `once_version`-ს. ეს ველები აღწერენ შეტყობინებულ ვერსიებს და არა დადასტურებულ იდენტობას ან სადენის კონტრაქტის ვერსიებს. REST ბილდის ბოლოწერტილებიც აჩვენებენ იგივე მეტამონაცემებს. არსებულ ინტეგრაციასა და რხევადი ტესტების უნარებს არ სჭირდებათ ვერსიის ველები და არ საჭიროებენ სამუშაო ნაკადის ცვლილებებს.

Tuist-ის ოპერატორები, რომლებიც იკვლევენ მომხმარებლის ანგარიშს, ამას აკეთებენ Tuist-ის შიდა ოპერაციული ხელსაწყოების მეშვეობით, რომელიც იწერს ყოველ ზარს; ამ ბოლოწერტილთან პირდაპირი კავშირი არ იძლევა წვდომას მომხმარებლის საკუთარი წევრობის ფარგლებს გარეთ.

## ბილდის სისტემის ინტეგრაციები იყენებენ ორ სერთიფიკატს

Model Context Protocol ხელსაწყოებისთვის გამოყენებული სერთიფიკატი არ ავთენტიკირებს Gradle პლაგინს ან Bazel-ის დისტანციურ სერვისებს. სანამ აგენტი ჩაასწორებს ან დაადასტურებს Gradle ან Bazel ინტეგრაციას, მან უნდა გაუშვას:

```bash
tuist auth whoami --url https://tuist.dev
```

თუ ეს ბრძანება არ არის ავთენტიკირებული, აგენტმა უნდა შეწყვიტოს მუშაობა და სთხოვოს მომხმარებელს გაუშვას:

```bash
tuist auth login --url https://tuist.dev
```

ლოკალური ან თვითმასპინძელი განლაგებისთვის, შეცვალეთ URL ორივე ბრძანებაში და `tuist.toml`-ში. შეინარჩუნეთ ჰოსტის სახელის წერა იდენტური ყველგან. მაგალითად, `localhost` და `127.0.0.1` იყენებენ ცალკე შენახულ სერთიფიკატებს.

Gradle და Bazel ნაბიჯების სიები ნაგულისხმევად აბრუნებენ 20 შედეგს (მაქსიმუმ 100), მხარდაჭერილია `search`, ზუსტი `project`, `target`, `category` და `status`, გადაფარვის `start_ms` / `end_ms` ფილტრები (ბოლო არ არის ჩათვლილი) და `duration_ms` ან `start_ms` დალაგება. გადასცეთ დაბრუნებული ID-ები უცვლელად; ისინი შეზღუდულია მათი ბილდის ფარგლებში. სიები ავლენენ `time_origin`-ს და `coverage`-ს. ძველი Gradle ანგარიშები იყენებენ `first_recorded_timestamp`-ს, რადგან ბილდის დაწყება არ ატვირთულა. Bazel დეტალები შეიცავს სანიტიზებულ მოქმედების ლოგებს, როდესაც ისინი გამოქვეყნებულია; Gradle დეტალის `log` არის null. `compare_builds` მოთხოვნა იყენებს ამ დაფარვას სრული Bazel ტრეისების განსასხვავებლად შენახული შეჯამებებისგან და მიმართავს აგენტებს ნაბიჯის დეტალებისკენ მოქმედების შედეგებისა და ლოგებისთვის, სანამ ფართო გამოძახების გამომავალს შეამოწმებენ.

Gradle ნაბიჯების სიები შეიცავს ნულოვანი ხანგრძლივობის ქეშირებულ და გამოტოვებულ ოპერაციებს.

ეს ინსტრუმენტები თანდათანობით ვრცელდება და აბრუნებენ მონაცემებს მხოლოდ იმ პროექტებისთვის, სადაც ისინი ჩართულია; სხვა პროექტებისთვის ისინი აბრუნებენ შეცდომას ცარიელი შედეგის ნაცვლად. სახე ხელმისაწვდომია მხოლოდ იმ პროექტებისთვის, რომლებიც იყენებენ შესაბამის ბილდის ინსტრუმენტების ჯაჭვს. ინსტრუმენტები იღებენ შემოსაზღვრულ `start_at`/`end_at` ფილტრებს, `environment` (`any`, `ci` ან `local`) და ზუსტ `branch`. `list_build_entities` იღებს `q`-ს; `list_build_entity_history` მხარდაჭერს გამჭვირვალე `after`/`before` კურსორებს. უცნობი დროის ან ქეშის დაკვირვებები რჩება მიუწვდომელი ნულის ან გამოტოვების ნაცვლად. ისტორია მიუთითებს ჩაწერილ მშობელზე და ნეიტიურ გაშვებაზე დეტალური ანალიზისთვის არსებული გაშვების ინსტრუმენტების გამოყენებით.

`get_build_entity` მეტრიკები მოიცავს `duration_samples`-ს, დაკვირვებების რაოდენობას ჩაწერილი დროით: რეალური ნულოვანი ხანგრძლივობები ითვლება, გამოტოვებული დრო — არა. ეს რაოდენობა შეიძლება იყოს დაკვირვებების რაოდენობაზე ნაკლები; მიუწვდომელი ხანგრძლივობის სტატისტიკა რჩება null.

Xcode-ის მოდულების ხანგრძლივობა მოდის ბილდის ლოგებში გაზომილი სამიზნე კომპილაციებიდან. მოდულის ქეშის გარჩევები და სამიზნეები კომპილაციის მუშაობის გარეშე არ მონაწილეობენ ხანგრძლივობის ნიმუშებში. კომპილაციის დაკვირვებები მიუთითებენ Xcode-ის ბილდზე; ქეშის მოვლენები მიუთითებენ გენერაციის ან ქეშის ბრძანებაზე.

Bazel-ის მოქმედებები იდენტიფიცირდება სამიზნის ლეიბლით, მნემონიკით და კონფიგურირებული ძირითადი გამოტანით, რაც ცალკეულ მოქმედებებსა და კონფიგურაციებს განცალკევებულს ტოვებს შეყვანაზე დამოკიდებული ქეშის დაიჯესტების გარეშე. ისტორია იწერს BEP-ით შეტყობინებულ გაშვებებს, არა ქეშის ძიებებს ან ტრეისის პროფილის ფაზებს. სრული გაშვების დაფარვა მოითხოვს `--build_event_publish_all_actions`-ს; არტიფაქტების მიწოდება საუკეთესო ძალისხმევით ხდება, ამიტომ გამოტოვებული დაკვირვებები არ არის იმის მტკიცებულება, რომ მუშაობა არ შესრულებულა. უფრო ძველი Kura-ს პაკეტები სტაბილური იდენტობის ან გაშვების დასაწყისის გარეშე რჩება მიღებული, მაგრამ არაინდექსირებული. დასრულების დროის გაზომვების არარსებობა რჩება მიუწვდომელი და რეალური ნულოვანი ხანგრძლივობები ითვლება.

Mix-ის მოდულების ხანგრძლივობა ზომავს შემცველი ფაილის კომპილაციას, არა დამოუკიდებლად გაზომილ მოდულის მუშაობას. Once-ის მოქმედებები იყენებენ გამოცხადებულ სამიზნე/შესაძლებლობა/ინდექსის სლოტებს, როდესაც კლიენტმა შეატყობინა სამიზნის ასახვები; დიაგნოსტიკური ლეიბლები მარტო არ არის სტაბილური იდენტობები. არსებული კლიენტები და გაშვების დონის ინსტრუმენტები რჩება მხარდაჭერილი უცვლელად.

Cargo-ის კრეიტები დაჯგუფებულია ზუსტად ჩაწერილი კრეიტის ფესვის, სახელისა და სახის მიხედვით. ### მოვლენები

კლიენტები, რომლებიც იყენებენ უმდგომარეობიან `2026-07-28` Model Context Protocol ლაიფციკლს, შეუძლიათ გამოიძახონ `events/list` მოვლენებისა და მათი payload-ის სქემების აღმოსაჩენად:

| მოვლენა | როდის იგზავნება | გამოწერის ფილტრი |
|-------|-----------------|---------------------|
| `test_case.marked_flaky` | სატესტო შემთხვევა იცვლება არაარასტაბილურიდან არასტაბილურზე. | `account_handle`, `project_handle` |
| `build.failed` | ლოკალური ან უწყვეტი ინტეგრაციის Xcode, Gradle ან Bazel ბილდი სრულდება შეცდომით. | `account_handle`, `project_handle` |
| `test_run.failed` | ლოკალური ან უწყვეტი ინტეგრაციის ტესტების გაშვება სრულდება შეცდომით, შერწყმული დაშლილი გაშვების ან მიტოვებული გაშვების ჩათვლით. | `account_handle`, `project_handle` |
| `ci_job.failed` | Tuist runner-ის სამუშაო სრულდება შეცდომით. | `account_handle` |

გამოწერისთვის კლიენტი იძახებს `events/subscribe` მოვლენის სახელით, ზემოთ ჩამოთვლილი handle-ებით `arguments`-ში და `webhook` მიწოდებით, რომელიც შეიცავს `https://` callback URL-ს და `whsec_` ხელმოწერის საიდუმლოს. პროექტის მოვლენები მოითხოვს ანგარიშის წევრობას და შესაბამის ტესტის ან ბილდის მონაცემებზე წვდომას; runner-ის სამუშაოს მოვლენები მოითხოვს ანგარიშის წევრობას და runner-ზე წვდომას. მოპოვებულმა [`auth.md`](https://workos.com/auth-md) წვდომის ტოკენებმა, მოპოვებულმა ანგარიშის ტოკენებმა და ბრაუზერის ავტორიზაციის გრანტებმა შეუძლიათ შექმნან გამოწერები; მიწოდება ჩერდება, როდესაც შესაბამისი სერთიფიკატი აღარ არის აქტიური. თითოეულ მომხმარებელს შეუძლია ჰქონდეს 25-მდე აქტიური გამოწერა. Tuist აგზავნის ვერიფიკაციის გამოწვევას callback-ზე გამოწერის შენახვამდე. callback-მა უნდა დააბრუნოს ობიექტი, რომელიც შეიცავს იგივე `challenge` მნიშვნელობას. გამოწერა ძალაშია შვიდი დღის განმავლობაში, შეიძლება განახლდეს ხელახლა გამოწერით და ჩერდება მიწოდება, როდესაც მომხმარებლის წვდომა ან სერთიფიკატი იხსნება. არასავალდებულო `ttlMs` შეზღუდულია ერთ საათსა და 30 დღეს შორის. Tuist ცდის დროში ამოვარდნილ callback-ს და აუქმებს მას სამი ზედიზედ ამოვარდნის შემდეგ, რომლებიც ხუთ წუთს მოიცავს; გამოიწერეთ ხელახლა callback-ის აღდგენის შემდეგ.

როდესაც მოვლენა ხდება, Tuist აგზავნის მის რესურსის იდენტიფიკატორს და dashboard-ის URL-ს callback-ზე. ბილდისა და ტესტების გაშვების შეცდომები ასევე შეიცავს `is_ci`-ს და `git_branch`-ს, რათა კლიენტებმა შეძლონ ლოკალური შეცდომების იგნორირება ან ფილტრაცია branch-ის მიხედვით. ბილდის მოვლენები შეიცავს `build_system`-ს; runner-ის სამუშაოს მოვლენები შეიცავს როგორც `workflow_job_id`-ს, ასევე `workflow_run_id`-ს. მოთხოვნა შეიცავს გამოწერის იდენტიფიკატორს და [Standard Webhooks](https://www.standardwebhooks.com/) ხელმოწერის ჰედერებს, რათა კლიენტმა შეძლოს მისი წარმოშობის ვერიფიცირება. Tuist ცდის წარუმატებელ მიწოდებებს, ამიტომ კლიენტებმა უნდა გამოიყენონ სტაბილური `eventId` დუბლიკატების გამოსარიცხად. Payload არ შეიცავს ტესტების სახელებს, ლოგებს და შეცდომის შეტყობინებებს; კლიენტს შეუძლია მიიღოს ეს დეტალები ზემოთ ჩამოთვლილი ინსტრუმენტების მეშვეობით და გადაწყვიტოს, შეატყობინოს თუ არა გუნდს ან დაიწყოს დებაგინგი. კლიენტებს შეუძლიათ შეაჩერონ მიწოდება `events/unsubscribe`-ით.

| `test_insights` | აყენებს Tuist Gradle პლაგინს, რათა Gradle `Test` task-ის შედეგები ავტომატურად აიტვირთოს. |
| `flaky_tests` | გვიჩვენებს, როგორ დავაყენოთ არასტაბილური ტესტების აღმოჩენა, Gradle Test Retry პლაგინის სურვილისამებრ გამოყენება და ტესტების კარანტინში მოქცევის კონფიგურაცია. |
| `test_sharding` | ამატებს უწყვეტი ინტეგრაციის სამუშაო პროცესს `tuistPrepareTestShards`-თვის, shard-ების მატრიცის გენერირებას და `TUIST_SHARD_INDEX`-ზე დაფუძნებულ ტესტების შესრულებას. |

როდესაც `features` გამოტოვებულია, მითითება სთხოვს აგენტს, გაარკვიოს, რომელი ინტეგრაციები სურს მომხმარებელს, ან მოთხოვნის საფუძველზე გამოიტანოს უმცირესი სასარგებლო ნაკრები, სანამ Gradle პროექტში ცვლილებები შეიტანოს.

#### Xcode ინტეგრაციის მითითების ფუნქციები

`integrate_xcode_project` მითითება აღწერს ყველა Xcode ინტეგრაციას, რომელსაც Tuist მხარდაჭერს:

| ფუნქცია | რას აკონფიგურირებს აგენტი |

| `xcode_cache` | აკონფიგურირებს `tuist setup cache`-ს, გენერირებული პროექტის ქეშის პარამეტრებს, Xcode ქეშის ბილდის ხელით მითითებულ პარამეტრებს და ატვირთვის პოლიტიკას, რომელიც შემოიფარგლება მხოლოდ უწყვეტი ინტეგრაციის runner-ებით. |
