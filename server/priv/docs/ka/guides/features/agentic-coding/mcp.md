# Model Context Protocol

[Model Context Protocol (MCP)](https://modelcontextprotocol.io/docs/getting-started/intro) არის ღია სტანდარტი, რომელიც საშუალებას აძლევს ხელოვნური ინტელექტის აგენტებს ურთიერთქმედებდნენ გარე სერვისებთან და მონაცემთა წყაროებთან. ის უზრუნველყოფს [Claude](https://claude.ai/), [Claude Code](https://docs.anthropic.com/en/docs/claude-code), [Codex](https://developers.openai.com/codex/)-ისა და რედაქტორების, როგორიცაა [Zed](https://zed.dev), [Cursor](https://www.cursor.com) ან [Visual Studio Code](https://code.visualstudio.com), თავსებადობას Tuist-თან.

Tuist განათავსებს Model Context Protocol-ის სერვერულ წერტილს `https://tuist.dev/mcp` მისამართზე. მასზე თქვენი კლიენტის მიერთებით, აგენტებს შეუძლიათ მიიღონ წვდომა თქვენს Tuist პროექტის მონაცემებზე, მათ შორის ტესტების ანალიტიკაზე, არასტაბილური ტესტების ანალიზზე და სხვა. უმეტესი ინსტრუმენტი მხოლოდ კითხვის რეჟიმშია და შეზღუდულია ავტორიზებული Tuist პროექტის მონაცემებით. ანგარიშის კონფიგურაციის ინსტრუმენტებს შეუძლიათ ჩამოთვალონ ანგარიშები, შექმნან ორგანიზაციები, შექმნან პროექტები და დაამატონ არსებული მომხმარებლები ორგანიზაციებში, თუ ავტორიზებულ მომხმარებელს აქვს შესაბამისი ნებართვები. ყოველი ინსტრუმენტი ასახავს ანოტაციებს, რომლებიც მიუთითებს, არის თუ არა ის მხოლოდ კითხვის რეჟიმში, შეუძლია თუ არა გამოიწვიოს რთულად შექცევადი ცვლილება და შეუძლია თუ არა შეცვალოს საჯარო ინტერნეტის მდგომარეობა. ანგარიშის კონფიგურაციის ინსტრუმენტებს სჭირდებათ მომხმარებლის ავტორიზაცია. ისინი არ არის ხელმისაწვდომი პროექტის ტოკენებისთვის ან ჩვეულებრივი ანგარიშის ტოკენებისთვის. როდესაც მომხმარებელი ავტორიზებს კლიენტს ბრაუზერში ან ადასტურებს `auth.md` რეგისტრაციას, Tuist ამ სერთიფიკატს აკავშირებს მომხმარებელთან მხოლოდ Model Context Protocol-ის წერტილზე, რათა კონფიგურაციის ინსტრუმენტებმა შეასრულონ მოთხოვნილი სამუშაო ნაკადი.

Tuist ახორციელებს [2026-07-28 პროტოკოლს](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http). მოთხოვნები არის უსესიო: კლიენტები აგზავნიან თავიანთ პროტოკოლის მეტამონაცემებს ყოველ მოთხოვნასთან ერთად და შეუძლიათ პირდაპირ გამოიძახონ ინსტრუმენტები ინიციალიზაციის გარეშე. `server/discover` აბრუნებს სერვერის იდენტობას, შესაძლებლობებს, მხარდაჭერილ ვერსიებს და ინსტრუქციებს. არ არსებობს სესიის იდენტიფიკატორები ან დამოუკიდებელი მოვლენათა ნაკადები. კლიენტები, რომლებიც იყენებენ 2025-06-18 ან 2025-03-26 ინიციალიზაციის ნაკადს, კვლავ მხარდაჭერილია; ისინიც მუშაობენ სერვერის სესიების გარეშე.

## Model Context Protocol უნარების წინააღმდეგ

Model Context Protocol-ის ინსტრუმენტებსა და <.localized_link href="/guides/features/agentic-coding/skills">უნარებს</.localized_link> შორის შესაძლოა იყოს გადაკვეთა ფუნქციებში. ამჟამინდელი გადაკვეთის გათვალისწინებით, აირჩიეთ ერთი მიდგომა თითოეული სამუშაო ნაკადისთვის და გამოიყენეთ ის თანმიმდევრულად, ნაცვლად ორივეს ერთ ნაკადში შერევისა.

კლიენტებისთვის, რომლებიც მხარდაჭერენ პლაგინების ინსტალაციას, გამოიყენეთ <.localized_link href="/guides/features/agentic-coding/plugins">Tuist პლაგინები</.localized_link> ორივეს ერთად ინსტალაციისთვის.

## კონფიგურაცია

დაამატეთ `https://tuist.dev/mcp` როგორც დისტანციური Model Context Protocol სერვერი თქვენს კლიენტში. სერვერის ინიციალიზაციის ინსტრუქციები და საჯარო სერვერის ბარათი აღწერენ OAuth 2.0-ს დინამიური კლიენტის რეგისტრაციით და სტანდარტული ბრაუზერის ავტორიზაციის ნაკადით პირდაპირ, აგენტებისგან გარე ავტორიზაციის დოკუმენტების მოთხოვნის ან მათი მიყოლების გარეშე. ეს სერვერის მასშტაბის ინსტრუქციები ინარჩუნებენ სამუშაო ნაკადის მითითებებს ზოგადს: ინსტრუმენტის ავტორიზაცია არ ავტორიზებს ადგილობრივ კომანდური ხაზის ინსტრუმენტებს ან აწყობის სისტემის ინტეგრაციებს და აგენტებმა უნდა შეამოწმონ მოთხოვნილი ცვლილებები შესაბამისი Tuist ინსტრუმენტების მეშვეობით. აწყობის სისტემის სპეციფიკური კონფიგურაცია და ავტორიზაციის შემოწმებები აღწერილია ინტეგრაციის სახელმძღვანელოებში და მოთხოვნებში. Tuist კვლავ აქვეყნებს როგორც [Open Authorization](https://oauth.net/2/)-ის აღმოჩენის მეტამონაცემებს, ასევე მიმდინარე [auth.md პროტოკოლს](https://workos.com/auth-md) `https://tuist.dev/auth.md` მისამართზე ცალ-ცალკე.

წერტილი იღებს უსესიო `2026-07-28` Model Context Protocol მოთხოვნის სიცოცხლის ციკლს, მათ შორის `server/discover`-ს, ძველ სესიაზე დაფუძნებულ ციკლთან ერთად. არსებულმა კლიენტებმა შეიძლება გააგრძელონ თავიანთი მიმდინარე მიერთების მეთოდის გამოყენება.

კლიენტებს, რომლებიც მხარდაჭერენ Model Context Protocol მოვლენებს, შეუძლიათ გამოიწერონ პროექტის მოვლენები. იხილეთ [მოვლენები](#events) ხელმისაწვდომი მოვლენებისა და მიწოდების მოთხოვნებისთვის.

კლიენტებს, რომლებიც უკვე მხარდაჭერენ დისტანციურ ბრაუზერის ავტორიზაციას, შეუძლიათ გააგრძელონ ავტორიზაცია ბრაუზერში. კლიენტებსა და აგენტებს, რომლებიც მხარდაჭერენ `auth.md`-ს, შეუძლიათ დარეგისტრირდნენ ანონიმურად, წარადგინონ სანდო პროვაიდერის იდენტობის დადასტურება ან დაიწყონ სერვისით ავტორიზებული ელფოსტის მოთხოვნა. რეგისტრაცია აბრუნებს Tuist-ით ხელმოწერილ იდენტობის დადასტურებას, რომელსაც აგენტი ცვლის სტანდარტულ ტოკენის წერტილზე ერთსაათიანი წვდომის ტოკენისთვის. Tuist აქვეყნებს თავის საჯარო ხელმოწერის გასაღებს და მხარდაჭერს სტანდარტულ ტოკენის გაუქმებასა და პროვაიდერის უსაფრთხოების მოვლენების მიწოდებას.

არაავტორიზებულმა აგენტმა უნდა წაიკითხოს `WWW-Authenticate` ჰედერი, რომელიც დაბრუნდა Model Context Protocol-ის წერტილიდან, მიიღოს დაცული რესურსის მეტამონაცემები, მიიღოს ავტორიზაციის სერვერის მეტამონაცემები და მიჰყვეს მის `agent_auth.skill` URL-ს. Tuist ასევე აბრუნებს იმავე ადგილობრივ `auth_md` URL-ს არაავტორიზებული პასუხის სხეულში, რათა ენის მოდელზე დაფუძნებულმა კლიენტებმა შეძლონ ნაკადის აღმოჩენა ნატიური კლიენტის ინტეგრაციაზე დაყრდნობის გარეშე. განლაგების ადგილობრივი დოკუმენტი არის ჭეშმარიტი წყარო წერტილის სახელების, მოთხოვნის სხეულების, მოთხოვნის გამოკითხვისა და დადასტურების გაცვლისთვის.

სანამ აგენტი დაიწყებს ელფოსტის მოთხოვნას, მან უნდა სთხოვოს მომხმარებელს დაადასტუროს ელფოსტის მისამართი მათი Tuist ანგარიშისთვის. მან არ უნდა გამოიტანოს ეს მისამართი პროვაიდერის პროფილიდან, Git კონფიგურაციიდან, გარემოს ცვლადიდან ან სესიის მეტამონაცემებიდან.

წერტილი იყენებს `mcp` სკოპის ჯგუფს. ანონიმურმა წინასწარი მოთხოვნის სერთიფიკატმა შეიძლება აღმოაჩინოს შესაძლებლობები და წაიკითხოს საჯარო ინტეგრაციის მითითებები, მაგრამ ის არ განიხილება როგორც შესული მომხმარებელი. ბრაუზერის ავტორიზაციის ან მოთხოვნის შემდეგ, სერთიფიკატი არის მომხმარებელზე შეზღუდული და თითოეული ინსტრუმენტი იყენებს იმავე ავტორიზაციის შემოწმებებს, რაც დაშბორდი. იხილეთ <.localized_link href="/guides/server/authentication#scope-groups">სკოპის ჯგუფების დოკუმენტაცია</.localized_link> დეტალებისთვის.

ინსტრუმენტები წყდებიან იმ პროექტებზე, რომლებსაც ავტორიზებულ მომხმარებელს უკვე აქვს წვდომა. Xcode და Gradle აწყობის ინსტრუმენტები იღებენ აწყობის UUID-ს ან დაშბორდის URL-ს. UUID-მ უნდა განსაზღვროს ზუსტად ერთი პროექტი; თუ ის ჩნდება რამდენიმე პროექტში, ინსტრუმენტი აბრუნებს „არ არის ნაპოვნი“-ს, ნაცვლად სხვა პროექტის ანგარიშის არჩევისა. პროექტზე შეზღუდული დაშბორდისა და API-ის კითხვები რჩება ხელმისაწვდომი. მოხსენებული აქტორის იდენტიფიკატორები არის შეუმოწმებელი ნიშნულები, არა სერთიფიკატები ან დამატებითი წვდომის უფლებები.

აწყობის სიისა და დეტალური ინფორმაციის ინსტრუმენტები აჩვენებენ არასავალდებულო `tuist_version` მეტამონაცემებს: Xcode-ისა და Cargo-სთვის — Tuist CLI, Gradle-ისთვის — Tuist Gradle პლაგინი, ხოლო Mix-ისთვის — `tuist_ex` ბიბლიოთეკა. Xcode ასევე აჩვენებს `tuist_generation_version`-ს მის დაკავშირებული პროექტის გენერაციის მოვლენიდან, რაც შეიძლება განსხვავდებოდეს ატვირთვის CLI-ისგან. გამოტოვებული მნიშვნელობები არის null, ისინი არ არის გამოყვანილი სერვერიდან ან სხვა ანგარიშიდან. Bazel იყენებს არსებულ `bazel_version`-ს; Once-ის გაშვების დეტალები აჩვენებენ `once_version`-ს. ეს ველები აღწერენ მოხსენებულ ვერსიებს, არა დადასტურებულ იდენტობას ან სადენის კონტრაქტის ვერსიებს. ## აწყობის სისტემის ინტეგრაციები იყენებენ ორ სერთიფიკატს

Model Context Protocol ინსტრუმენტებისთვის გამოყენებული სერთიფიკატი არ ავტორიზებს Gradle პლაგინს ან Bazel-ის remote სერვისებს. სანამ აგენტი შეცვლის ან შეამოწმებს Gradle ან Bazel ინტეგრაციას, მან უნდა გაუშვას:

```bash
tuist auth whoami --url https://tuist.dev
```

თუ ეს ბრძანება არ არის ავტორიზებული, აგენტმა უნდა შეწყვიტოს და სთხოვოს მომხმარებელს გაუშვას:

```bash
tuist auth login --url https://tuist.dev
```

ლოკალური ან self-hosted განთავსებისთვის, შეცვალეთ URL ორივე ბრძანებაში და `tuist.toml`-ში. შეინარჩუნეთ hostname-ის მართლწერა იდენტური ყველგან. მაგალითად, `localhost` და `127.0.0.1` იყენებენ ცალკე შენახულ სერთიფიკატებს.

### ინსტრუმენტები

შემდეგი ინსტრუმენტები ხელმისაწვდომია Tuist Model Context Protocol სერვერის მეშვეობით:

ყველა ინსტრუმენტი აქვეყნებს ადამიანისთვის წასაკითხ აღწერას ცალსახა შეყვანისა და გამოტანის სქემებთან ერთად. წარმატებული გამოძახებები აბრუნებენ სტრუქტურირებულ კონტენტს, რომელიც შეესაბამება გამოცხადებულ გამოტანის სქემას, ასევე იმავე შედეგს ტექსტურად სერიალიზებულს იმ კლიენტებისთვის, რომლებიც ჯერ არ მოიხმარენ სტრუქტურირებულ კონტენტს.

ინსტრუმენტები, რომლებიც იღებენ ერთი ჩანაწერის იდენტიფიკატორს, როგორიცაა `build_run_id`, `test_run_id`, `test_case_id`, `bundle_id`, `run_id`, `generation_id` ან `cache_run_id`, ასევე იღებენ ამ ჩანაწერის Tuist dashboard-ის URL-ს. ჩასვით URL პირდაპირ ბრაუზერიდან, ნაცვლად მისგან იდენტიფიკატორის ამოღებისა.

#### წყაროზე დაფუძნებული პასუხები

ეს მხოლოდ-წაკითხვის ინსტრუმენტები საშუალებას აძლევს აგენტებს გამოიყენონ ზუსტი საჯარო Tuist წყაროს რევიზია, რომელიც განთავსებულია hosted სერვერთან ერთად, როგორც ჭეშმარიტების წყარო პასუხებისთვის, რომლებიც დამოკიდებულია მიმდინარე ქცევაზე. ისინი ხელმისაწვდომია მხოლოდ `https://tuist.dev/mcp`-ზე.

თავსებადი კლიენტები იღებენ ფაქტობრივ აღწერებს ინსტრუმენტების წყაროს რევიზიის, ბმულებისა და შედეგის ლიმიტების შესახებ ინიციალიზაციის დროს, inline OAuth ავტორიზაციის ინფორმაციასთან ერთად. ეს აღწერები არ განსაზღვრავენ პასუხის სტილს ან შემოწმების სამუშაო პროცესს. მომხმარებლებს შეუძლიათ პირდაპირ დასვან კითხვა `ask_tuist` prompt-ის გამოძახების გარეშე; prompt რჩება ხელმისაწვდომი ცალსახა წყაროზე დაფუძნებული სამუშაო პროცესისთვის.

`list_xcode_build_steps` ნაგულისხმევად აბრუნებს 20 ნაბიჯის გვერდებს (მაქსიმუმ 100 `page_size`-ით), `page` და `pagination_metadata`-ით ნავიგაციისთვის. გამოიყენეთ `search` სათაურების, პროექტების ან სამიზნეების შესატყვისად, ან გაფილტრეთ ზუსტი `project`, `target`, `category` (მაგალითად, `swiftCompilation`) და `status` (`success` ან `failure`). დაალაგეთ `duration_ms`-ით ყველაზე ნელიდან (ნაგულისხმევი) ან `start_ms`-ით ქრონოლოგიური თანმიმდევრობით. ნაბიჯის ID-ები არღვევენ ტოლობას და ბრუნდება ათობითი სტრიქონების სახით მათი სრული 64-ბიტიანი სიზუსტის შესანარჩუნებლად. ID-ები შეზღუდულია ერთი build-ით და არ უნდა შეესაბამებოდეს სხვა build-ებს.

არასავალდებულო `start_ms` და `end_ms` ირჩევს ნაბიჯებს, რომლებიც ემთხვევა დროის დიაპაზონს მილიწამებში build-ის დაწყებიდან; ბოლო არ არის შემცველი. ორივე ინსტრუმენტი იღებს build UUID-ს ან dashboard URL-ს როგორც `build_run_id`. გადასცეთ დაბრუნებული ნაბიჯის `id` უცვლელად როგორც `step_id` მისი ლოგის მისაღებად. ლოგები ინახავენ 64 KiB-მდე თითო ნაბიჯზე, `log_truncated` მიუთითებს გამოტოვებულ გამოსავალზე.

ნაბიჯები ნაგულისხმევად იკრიბება Xcode build-ების დამუშავებისას. ჩაწერილი ნაბიჯის მონაცემები ინახება 90 დღის განმავლობაში. სიის პასუხი შეიცავს `availability`-ს: `available`, როცა ჩაწერილი ნაბიჯები არსებობს, მაშინაც კი, თუ ფილტრები არაფერს ემთხვევა; `processing`, როცა build ჯერ კიდევ მუშავდება და ნაბიჯები ჯერ არ აქვს; ან `unavailable`, როცა ნაბიჯები არ ჩაწერილა ან ვადა გაუვიდათ.

იგივე ოპერაციები ხელმისაწვდომია HTTP API-ზე `GET /api/projects/{account_handle}/{project_handle}/xcode/builds/{build_id}/steps` და `GET /api/projects/{account_handle}/{project_handle}/xcode/builds/{build_id}/steps/{step_id}` მისამართებზე, იგივე ფილტრებითა და დაგვერდებით. ორივეს სჭირდება წვდომა build-ის პროექტის წაკითხვისთვის.

შენახული შეჯამებებიდან დაბრუნებული Bazel ნაბიჯის ID-ები რჩება წასაკითხად, თუ სრული პროფილი მოდის ნაბიჯის ჩამოთვლასა და მიღებას შორის. ინდექსირებული პროფილი, რომლის ნაბიჯის მონაცემების ვადა გაუვიდა, აცხადებს მიუწვდომლობას. ეს ინსტრუმენტები თანდათანობით ხდება ხელმისაწვდომი და აბრუნებენ მონაცემებს მხოლოდ იმ პროექტებისთვის, სადაც ისინი ჩართულია; სხვა პროექტებისთვის ისინი აბრუნებენ შეცდომას ცარიელი შედეგის ნაცვლად. სახეობა ხელმისაწვდომია მხოლოდ იმ პროექტებისთვის, რომლებიც იყენებენ შესაბამის build toolchain-ს. ინსტრუმენტები იღებენ შეზღუდულ `start_at`/`end_at` ფილტრებს, `environment` (`any`, `ci` ან `local`) და ზუსტ `branch`. `list_build_entities` იღებს `q`-ს; `list_build_entity_history` უჭერს მხარს გამჭვირვალე `after`/`before` კურსორებს. უცნობი დროის ან cache დაკვირვებები რჩება მიუწვდომელი, ნულის ან გამოტოვების ნაცვლად. ისტორია მიუთითებს ჩაწერილ მშობელზე და native execution-ზე არსებული run ინსტრუმენტების გამოყენებით დეტალური ანალიზისთვის.

`get_build_entity` მეტრიკები მოიცავს `duration_samples`-ს, დაკვირვებების რაოდენობას ჩაწერილი დროით: რეალური ნულოვანი ხანგრძლივობები ითვლება, არაკმარისი დრო — არა. ეს რაოდენობა შეიძლება იყოს დაკვირვებების რაოდენობაზე ნაკლები; მიუწვდომელი ხანგრძლივობის სტატისტიკა რჩება null.

Xcode module-ების ხანგრძლივობა მოდის გაზომილი target compilations-დან build ჟურნალებში. Module-cache გადაწყვეტები და targets კომპილაციის სამუშაოს გარეშე არ წვლილობენ ხანგრძლივობის ნიმუშებში. კომპილაციის დაკვირვებები მიუთითებენ Xcode build-ზე; cache მოვლენები მიუთითებენ generation ან cache ბრძანებაზე.

Bazel actions იდენტიფიცირდება target label-ით, mnemonic-ით და კონფიგურირებული primary output-ით, რაც ინარჩუნებს ცალკეულ actions და configurations განცალკევებულს input-ზე დამოკიდებული cache digests-ის გარეშე. ისტორია აღრიცხავს BEP-ით შეტყობინებულ executions-ს, არა cache ძიებებს ან trace-profile ფაზებს. სრული execution დაფარვა მოითხოვს `--build_event_publish_all_actions`-ს; artifact მიწოდება არის საუკეთესო ძალისხმევა, ამიტომ არარსებული დაკვირვებები არ არის მტკიცებულება, რომ სამუშაო არ შესრულებულა. უფრო ძველი Kura payloads სტაბილური იდენტობის ან execution start-ის გარეშე რჩება მიღებული, მაგრამ არაინდექსირებული. არარსებული end-time გაზომვები რჩება მიუწვდომელი და რეალური ნულოვანი ხანგრძლივობები ითვლება.

Mix module-ების ხანგრძლივობა ზომავს შემცველი ფაილის კომპილაციას, არა დამოუკიდებლად გაზომილ module სამუშაოს. Once actions იყენებენ გამოცხადებულ target/capability/index სლოტებს, როდესაც კლიენტმა შეატყობინა target mapping; დიაგნოსტიკური ლეიბლები მხოლოდ არ არის სტაბილური იდენტობები. არსებული კლიენტები და run-level ინსტრუმენტები რჩება უცვლელად მხარდაჭერილი.

ანალიტიკის წაკითხვებს აქვს შეზღუდული მეხსიერება და შესრულების დრო. თუ მოთხოვნა აღემატება ამ ლიმიტებს, ინსტრუმენტი აბრუნებს შეცდომას ცარიელი შედეგის გამოგონების ნაცვლად.

ახალი დაკვირვებები ინდექსირდება განლაგების შემდეგ; ეს ფუნქცია არ ავსებს არსებულ run ტელემეტრიას. იდენტობის მეტამონაცემები რჩება ინდივიდუალურ დაკვირვებებზე უფრო დიდხანს <.localized_link href="/guides/server/data-retention">მონაცემთა შენახვის პოლიტიკის</.localized_link> მიხედვით.

### Events

კლიენტები, რომლებიც იყენებენ stateless `2026-07-28` Model Context Protocol lifecycle-ს, შეუძლიათ გამოიძახონ `events/list` მოვლენებისა და მათი payload schemas-ის აღმოჩენისთვის:

| მოვლენა | როდის იგზავნება | გამოწერის ფილტრი |
|-------|-----------------|---------------------|
| `test_case.marked_flaky` | test case იცვლება არა-flaky-დან flaky-ზე. | `account_handle`, `project_handle` |
| `build.failed` | ადგილობრივი ან continuous integration Xcode, Gradle ან Bazel build სრულდება შეცდომით. | `account_handle`, `project_handle` |
| `test_run.failed` | ადგილობრივი ან continuous integration test run სრულდება შეცდომით, შერწყმული sharded run-ის ან მიტოვებული run-ის ჩათვლით. | `account_handle`, `project_handle` |
| `ci_job.failed` | Tuist runner job სრულდება შეცდომით. | `account_handle` |

გამოწერისთვის, კლიენტი იძახებს `events/subscribe` მოვლენის სახელით, ზემოთ ჩამოთვლილი handles-ით `arguments`-ში და `webhook` მიწოდებით, რომელიც შეიცავს `https://` callback URL-ს და `whsec_` signing secret-ს. პროექტის მოვლენებს სჭირდება ანგარიშის წევრობა და შესაბამისი test ან build მონაცემების წაკითხვის წვდომა; runner job მოვლენებს სჭირდება ანგარიშის წევრობა და runner-ის წაკითხვის წვდომა. Claimed [`auth.md`](https://workos.com/auth-md) access tokens, claimed account tokens და browser authorization grants შეუძლიათ შექმნან გამოწერები; მიწოდება ჩერდება, როდესაც შესაბამისი credential აღარ არის აქტიური. თითოეულ მომხმარებელს შეუძლია ჰქონდეს 25-მდე აქტიური გამოწერა. Tuist აგზავნის verification challenge-ს callback-ზე გამოწერის შენახვამდე. callback-მა უნდა დააბრუნოს ობიექტი იგივე `challenge` მნიშვნელობით. გამოწერა ძალაშია შვიდი დღის განმავლობაში ნაგულისხმევად, შეიძლება განახლდეს ხელახლა გამოწერით და წყვეტს მიწოდებას, როდესაც მომხმარებლის წვდომა ან credential იხსნება. არასავალდებულო `ttlMs` შემოიფარგლება ერთ საათსა და 30 დღეს შორის. Tuist ცდილობს timed-out callback-ს და აუქმებს მას სამი თანმიმდევრული timeout-ის შემდეგ, რომლებიც მოიცავს ხუთ წუთს; გამოიწერეთ ხელახლა callback-ის აღდგენის შემდეგ.

როდესაც მოვლენა ხდება, Tuist აგზავნის მის რესურსის იდენტიფიკატორს და dashboard URL-ს callback-ზე. Build-ისა და test run-ის შეცდომები ასევე შეიცავს `is_ci`-ს და `git_branch`-ს, რათა კლიენტებმა შეძლონ ადგილობრივი შეცდომების იგნორირება ან ფილტრაცია branch-ის მიხედვით. Build მოვლენები შეიცავს `build_system`-ს; runner job მოვლენები შეიცავს როგორც `workflow_job_id`-ს, ისე `workflow_run_id`-ს. მოთხოვნა შეიცავს გამოწერის იდენტიფიკატორს და [Standard Webhooks](https://www.standardwebhooks.com/) ხელმოწერის ჰედერებს, რათა კლიენტმა შეძლოს მისი წყაროს ვერიფიცირება. Tuist ცდილობს ჩავარდნილი მიწოდებების გამეორებას, ამიტომ კლიენტებმა უნდა გამოიყენონ სტაბილური `eventId` დუბლიკატების გასაფილტრად. Payload არ შეიცავს ტესტების სახელებს, ლოგებს და შეცდომის შეტყობინებებს; კლიენტს შეუძლია მიიღოს ეს დეტალები ზემოთ ჩამოთვლილი ინსტრუმენტების მეშვეობით და გადაწყვიტოს, შეატყობინოს თუ არა გუნდს ან დაიწყოს debugging. კლიენტებს შეუძლიათ შეწყვიტონ მიწოდება `events/unsubscribe`-ით.
