# Model Context Protocol

[Model Context Protocol (MCP)](https://modelcontextprotocol.io/docs/getting-started/intro) არის ღია სტანდარტი, რომელიც საშუალებას აძლევს ხელოვნური ინტელექტის აგენტებს ურთიერთქმედონ გარე სერვისებთან და მონაცემთა წყაროებთან. ის უზრუნველყოფს ისეთი აპლიკაციების, როგორიცაა [Claude](https://claude.ai/), [Claude Code](https://docs.anthropic.com/en/docs/claude-code), [Codex](https://developers.openai.com/codex/), და რედაქტორების, როგორიცაა [Zed](https://zed.dev), [Cursor](https://www.cursor.com) ან [Visual Studio Code](https://code.visualstudio.com), თავსებადობას Tuist-თან.

Tuist განათავსებს Model Context Protocol-ის სერვერულ ბოლოწერტილს მისამართზე `https://tuist.dev/mcp`. თქვენი კლიენტის მასთან მიერთებით, აგენტებს შეუძლიათ მიიღონ წვდომა თქვენს Tuist პროექტის მონაცემებზე, მათ შორის ტესტების ანალიტიკაზე, არასტაბილური ტესტების ანალიზზე და სხვა. უმეტესი ინსტრუმენტი მხოლოდ კითხვის რეჟიმშია და შეზღუდულია ავტორიზებული Tuist პროექტის მონაცემებით. ანგარიშის მოწყობის ინსტრუმენტებს შეუძლიათ ჩამოთვალონ ანგარიშები, შექმნან ორგანიზაციები, შექმნან პროექტები და დაამატონ არსებული მომხმარებლები ორგანიზაციებში, როდესაც ავტორიზებულ მომხმარებელს აქვს საჭირო ნებართვები. ყოველი ინსტრუმენტი აცხადებს ანოტაციებს, რომლებიც მიუთითებს, არის თუ არა ის მხოლოდ კითხვის რეჟიმში, შეუძლია თუ არა გამოიწვიოს ძნელად შექცევადი ცვლილება და შეუძლია თუ არა შეცვალოს საჯარო ინტერნეტის მდგომარეობა. ანგარიშის მოწყობის ინსტრუმენტები მოითხოვს მომხმარებლის ავტორიზაციას. ისინი არ არის ხელმისაწვდომი პროექტის ტოკენებისთვის ან ჩვეულებრივი ანგარიშის ტოკენებისთვის. როდესაც მომხმარებელი ავტორიზებს კლიენტს ბრაუზერში ან აცხადებს `auth.md` რეგისტრაციას, Tuist აკავშირებს ამ სერთიფიკატს მომხმარებელთან მხოლოდ Model Context Protocol-ის ბოლოწერტილზე, რათა მოწყობის ინსტრუმენტებმა შეძლონ მოთხოვნილი სამუშაო პროცესის დასრულება.

Tuist ახორციელებს [2026-07-28 პროტოკოლს](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http). მოთხოვნები არის უსესიო: კლიენტები აგზავნიან თავიანთ პროტოკოლის მეტამონაცემებს ყოველ მოთხოვნასთან ერთად და შეუძლიათ პირდაპირ გამოიძახონ ინსტრუმენტები ინიციალიზაციის გარეშე. `server/discover` აბრუნებს სერვერის იდენტობას, შესაძლებლობებს, მხარდაჭერილ ვერსიებს და ინსტრუქციებს. არ არსებობს სესიის იდენტიფიკატორები ან დამოუკიდებელი მოვლენათა ნაკადები. კლიენტები, რომლებიც იყენებენ 2025-06-18 ან 2025-03-26 ინიციალიზაციის ნაკადს, კვლავ მხარდაჭერილია; ისინიც მუშაობენ სერვერის სესიების გარეშე.

## Model Context Protocol უნარების წინააღმდეგ

Model Context Protocol-ის ინსტრუმენტებსა და <.localized_link href="/guides/features/agentic-coding/skills">უნარებს</.localized_link> შორის შესაძლოა იყოს გადაფარვა ფუნქციებში. არსებული გადაფარვის გათვალისწინებით, აირჩიეთ ერთი მიდგომა თითოეული სამუშაო პროცესისთვის და გამოიყენეთ ის თანმიმდევრულად, ნაცვლად ორივეს ერთ ნაკადში შერევისა.

კლიენტებისთვის, რომლებიც მხარს უჭერენ პლაგინების ინსტალაციას, გამოიყენეთ <.localized_link href="/guides/features/agentic-coding/plugins">Tuist პლაგინები</.localized_link> ორივეს ერთად ინსტალაციისთვის.

## კონფიგურაცია

დაამატეთ `https://tuist.dev/mcp` როგორც დაშორებული Model Context Protocol სერვერი თქვენს კლიენტში. სერვერის ინიციალიზაციის ინსტრუქციები და საჯარო სერვერის ბარათი აღწერენ OAuth 2.0-ს დინამიური კლიენტის რეგისტრაციით და სტანდარტული ბრაუზერის ავტორიზაციის ნაკადით პირდაპირ, აგენტებისგან გარე ავტორიზაციის დოკუმენტების მოთხოვნის ან მათზე გადასვლის გარეშე. ეს სერვერის მასშტაბის ინსტრუქციები ინარჩუნებენ სამუშაო პროცესის მითითებებს ზოგადს: ინსტრუმენტის ავტორიზაცია არ ავტორიზებს ადგილობრივ ბრძანების ხაზის ინსტრუმენტებს ან აგების სისტემის ინტეგრაციებს და აგენტებმა უნდა დაადასტურონ მოთხოვნილი ცვლილებები შესაბამისი Tuist ინსტრუმენტების მეშვეობით. აგების სისტემის სპეციფიკური მოწყობა და ავტორიზაციის შემოწმებები დოკუმენტირებულია ინტეგრაციის სახელმძღვანელოებში და მოთხოვნებში. Tuist კვლავ აცხადებს როგორც [Open Authorization](https://oauth.net/2/)-ის აღმოჩენის მეტამონაცემებს, ასევე მიმდინარე [auth.md პროტოკოლს](https://workos.com/auth-md) მისამართზე `https://tuist.dev/auth.md` ცალ-ცალკე.

ბოლოწერტილი იღებს უსესიო `2026-07-28` Model Context Protocol მოთხოვნის სიცოცხლის ციკლს, მათ შორის `server/discover`-ს, უფრო ძველ სესიაზე დაფუძნებულ ციკლთან ერთად. არსებულმა კლიენტებმა შეიძლება გააგრძელონ თავიანთი მიმდინარე შეერთების მეთოდის გამოყენება.

კლიენტები, რომლებიც მხარს უჭერენ Model Context Protocol-ის მოვლენებს, შეუძლიათ გამოიწერონ პროექტის მოვლენები. იხილეთ [მოვლენები](#events) ხელმისაწვდომი მოვლენებისა და მიწოდების მოთხოვნებისთვის.

კლიენტები, რომლებიც უკვე მხარს უჭერენ დაშორებულ ბრაუზერის ავტორიზაციას, შეუძლიათ გააგრძელონ ავტორიზაცია ბრაუზერში. კლიენტებსა და აგენტებს, რომლებიც მხარს უჭერენ `auth.md`-ს, შეუძლიათ დარეგისტრირდნენ ანონიმურად, წარმოადგინონ სანდო პროვაიდერის იდენტობის დამტკიცება ან დაიწყონ სერვისით ავტორიზებული ელფოსტის მოთხოვნა. რეგისტრაცია აბრუნებს Tuist-ით ხელმოწერილ იდენტობის დამტკიცებას, რომელსაც აგენტი ცვლის სტანდარტულ ტოკენის ბოლოწერტილზე ერთსაათიანი წვდომის ტოკენისთვის. Tuist აქვეყნებს თავის საჯარო ხელმოწერის გასაღებს და მხარს უჭერს სტანდარტულ ტოკენის გაუქმებასა და პროვაიდერის უსაფრთხოების მოვლენების მიწოდებას.

არაავტორიზებულმა აგენტმა უნდა წაიკითხოს `WWW-Authenticate` ჰედერი, რომელიც დაბრუნდა Model Context Protocol-ის ბოლოწერტილის მიერ, მიიღოს დაცული რესურსის მეტამონაცემები, მიიღოს ავტორიზაციის სერვერის მეტამონაცემები და გადავიდეს მის `agent_auth.skill` URL-ზე. Tuist ასევე აბრუნებს იმავე ადგილობრივ `auth_md` URL-ს არაავტორიზებული პასუხის სხეულში, რათა ენის მოდელზე დაფუძნებულმა კლიენტებმა შეძლონ ნაკადის აღმოჩენა ნატიური კლიენტის ინტეგრაციაზე დამოკიდებულების გარეშე. განლაგების ადგილობრივი დოკუმენტი არის ჭეშმარიტების წყარო ბოლოწერტილების სახელების, მოთხოვნის სხეულების, მოთხოვნის გამოკითხვისა და დამტკიცების გაცვლისთვის.

სანამ აგენტი დაიწყებს ელფოსტის მოთხოვნას, მან უნდა სთხოვოს მომხმარებელს დაადასტუროს ელფოსტის მისამართი თავისი Tuist ანგარიშისთვის. მან არ უნდა გამოიტანოს ეს მისამართი პროვაიდერის პროფილიდან, Git კონფიგურაციიდან, გარემოს ცვლადიდან ან სესიის მეტამონაცემებიდან.

ბოლოწერტილი იყენებს `mcp` სკოპის ჯგუფს. ანონიმურმა წინასწარ-მოთხოვნის სერთიფიკატმა შეიძლება აღმოაჩინოს შესაძლებლობები და წაიკითხოს საჯარო ინტეგრაციის მითითებები, მაგრამ ის არ განიხილება როგორც შესული მომხმარებელი. ბრაუზერის ავტორიზაციის ან მოთხოვნის შემდეგ, სერთიფიკატი არის მომხმარებლის სკოპით შეზღუდული და თითოეული ინსტრუმენტი იყენებს იმავე ავტორიზაციის შემოწმებებს, რასაც დაშბორდი. იხილეთ <.localized_link href="/guides/server/authentication#scope-groups">სკოპის ჯგუფების დოკუმენტაცია</.localized_link> დეტალებისთვის.

ინსტრუმენტები გადაიჭრებიან იმ პროექტებზე, რომელთა წაკითხვაც ავტორიზებულ მომხმარებელს უკვე შეუძლია. Xcode და Gradle აგების ინსტრუმენტები იღებენ აგების UUID-ს ან დაშბორდის URL-ს. UUID-მ უნდა მიუთითოს ზუსტად ერთ პროექტზე; თუ ის ჩნდება რამდენიმე პროექტში, ინსტრუმენტი აბრუნებს „არ არის ნაპოვნი“-ს, ნაცვლად სხვა პროექტის ანგარიშის არჩევისა. პროექტის სკოპით შეზღუდული დაშბორდისა და API-ის წაკითხვები რჩება ხელმისაწვდომი. მოხსენებული აქტორის იდენტიფიკატორები არიან შეუმოწმებელი ეტიკეტები, არა სერთიფიკატები ან დამატებითი წვდომის უფლებები.

Tuist ოპერატორები, რომლებიც იკვლევენ მომხმარებლის ანგარიშს, აკეთებენ ამას Tuist-ის შიდა ოპერაციული ინსტრუმენტების მეშვეობით, რომელიც იწერს ყოველ გამოძახებას; პირდაპირი შეერთება ამ ბოლოწერტილთან არ იძლევა წვდომას მომხმარებლის საკუთარი წევრობის გარდა.

ID-ები შეზღუდულია ბილდის ფარგლებში და არ უნდა შეესაბამებოდეს სხვადასხვა ბილდს.

არასავალდებულო `start_ms` და `end_ms` ირჩევს ეტაპებს, რომლებიც ემთხვევა დროის დიაპაზონს მილიწამებში ბილდის დაწყებიდან; ბოლო არ არის ჩართული. ორივე ინსტრუმენტი იღებს ბილდის UUID-ს ან დაფის URL-ს როგორც `build_run_id`. გადასცეთ დაბრუნებული ეტაპის `id` უცვლელად როგორც `step_id` მისი ჟურნალის მისაღებად. ჟურნალები ინახავს 64 KiB-მდე თითოეულ ეტაპზე, `log_truncated` მიუთითებს გამოტოვებულ გამოსავალზე.

ეტაპები ნაგულისხმევად იკრიბება Xcode ბილდების დამუშავებისას. ჩაწერილი ეტაპის მონაცემები ინახება 90 დღის განმავლობაში. სიის პასუხი შეიცავს `availability`-ს: `available`, როცა ჩაწერილი ეტაპები არსებობს, მაშინაც კი, თუ ფილტრები არაფერს ემთხვევა; `processing`, როცა ბილდი ჯერ კიდევ მუშავდება და ჯერ არ აქვს ეტაპები; ან `unavailable`, როცა ეტაპები არ ჩაწერილა ან ვადა გაუვიდათ.

იგივე ოპერაციები ხელმისაწვდომია HTTP API-ის მეშვეობით `GET /api/projects/{account_handle}/{project_handle}/xcode/builds/{build_id}/steps`-ზე და `GET /api/projects/{account_handle}/{project_handle}/xcode/builds/{build_id}/steps/{step_id}`-ზე, იგივე ფილტრებითა და დაფურცვლით. ორივეს სჭირდება წაკითხვის წვდომა ბილდის პროექტზე.

ეს ინსტრუმენტები თანდათანობით ხდება ხელმისაწვდომი და აბრუნებენ მონაცემებს მხოლოდ იმ პროექტებისთვის, სადაც ისინი ჩართულია; სხვა პროექტებისთვის ისინი აბრუნებენ შეცდომას ცარიელი შედეგის ნაცვლად. სახეობა ხელმისაწვდომია მხოლოდ იმ პროექტებისთვის, რომლებიც იყენებენ შესაბამის ბილდის ხელსაწყოთა ჯაჭვს. ინსტრუმენტები იღებენ შემოსაზღვრულ `start_at`/`end_at` ფილტრებს, `environment` (`any`, `ci` ან `local`) და ზუსტ `branch`. `list_build_entities` იღებს `q`-ს; `list_build_entity_history` მხარდაჭერს გამჭვირვალე `after`/`before` კურსორებს. უცნობი დროის ან cache დაკვირვებები რჩება მიუწვდომლად, ნულის ან გამოტოვების ნაცვლად. ისტორია ეხება ჩაწერილ მშობელსა და ნატიურ შესრულებას დეტალური შესწავლისთვის არსებული გაშვების ინსტრუმენტების გამოყენებით.

`get_build_entity` მეტრიკები მოიცავს `duration_samples`-ს, ანუ ჩაწერილი დროის მქონე დაკვირვებების რაოდენობას: ნამდვილი ნულოვანი ხანგრძლივობები ითვლება, გამოტოვებული დრო — არა. ეს რაოდენობა შეიძლება იყოს დაკვირვებების რაოდენობაზე ნაკლები; მიუწვდომელი ხანგრძლივობის სტატისტიკა რჩება null.

Xcode მოდულების ხანგრძლივობა მოდის ბილდის ლოგებში გაზომილი სამიზნე კომპილაციებიდან. მოდულის cache გადაწყვეტები და სამიზნეები კომპილაციის გარეშე არ მონაწილეობენ ხანგრძლივობის ნიმუშებში. კომპილაციის დაკვირვებები ეხება Xcode ბილდს; cache მოვლენები ეხება გენერაციას ან cache ბრძანებას.

Bazel მოქმედებები იდენტიფიცირდება სამიზნე ლეიბლით, მნემონიკით და კონფიგურირებული ძირითადი გამოტანით, რაც ცალკეულ მოქმედებებსა და კონფიგურაციებს განცალკევებულს ტოვებს input-ზე დამოკიდებული cache digest-ების გარეშე. ისტორია აღრიცხავს BEP-ით შეტყობინებულ შესრულებებს, არა cache ძიებებს ან trace-profile ფაზებს. სრული შესრულების დაფარვა მოითხოვს `--build_event_publish_all_actions`-ს; არტიფაქტების მიწოდება ხდება მაქსიმალური ძალისხმევით, ამიტომ გამოტოვებული დაკვირვებები არ არის იმის მტკიცებულება, რომ სამუშაო არ შესრულებულა. ძველი Kura payload-ები სტაბილური იდენტობის ან შესრულების დასაწყისის გარეშე რჩება მიღებულად, მაგრამ არაინდექსირებულად. დასრულების დროის გაზომვების არარსებობა რჩება მიუწვდომლად და ნამდვილი ნულოვანი ხანგრძლივობები ითვლება.

Mix მოდულების ხანგრძლივობა ზომავს შემცველი ფაილის კომპილაციას, არა დამოუკიდებლად გაზომილ მოდულურ სამუშაოს. Once მოქმედებები იყენებენ გამოცხადებულ სამიზნე/შესაძლებლობა/ინდექს სლოტებს, როდესაც კლიენტმა შეატყობინა სამიზნე მიბმები; მხოლოდ დიაგნოსტიკური ლეიბლები არ არის სტაბილური იდენტობები. არსებული კლიენტები და გაშვების დონის ინსტრუმენტები რჩება მხარდაჭერილი უცვლელად.

ანალიტიკის წაკითხვებს აქვს შემოსაზღვრული მეხსიერება და შესრულების დრო. თუ მოთხოვნა აღემატება ამ ლიმიტებს, ინსტრუმენტი აბრუნებს შეცდომას ცარიელი შედეგის გამოგონების ნაცვლად.

ახალი დაკვირვებები ინდექსირდება განლაგების შემდეგ; ეს ფუნქცია არ ავსებს არსებულ გაშვების ტელემეტრიას. იდენტობის მეტამონაცემები ინახება ინდივიდუალურ დაკვირვებებზე უფრო დიდხანს <.localized_link href="/guides/server/data-retention">მონაცემთა შენახვის პოლიტიკის</.localized_link> შესაბამისად.

### მოვლენები

კლიენტები, რომლებიც იყენებენ stateless `2026-07-28` Model Context Protocol ლაიფციკლს, შეუძლიათ გამოიძახონ `events/list` მოვლენებისა და მათი payload სქემების აღმოსაჩენად:

| მოვლენა | როდის იგზავნება | გამოწერის ფილტრი |
|-------|-----------------|---------------------|
| `test_case.marked_flaky` | სატესტო შემთხვევა იცვლება არა-flaky-დან flaky-ზე. | `account_handle`, `project_handle` |
| `build.failed` | ლოკალური ან უწყვეტი ინტეგრაციის Xcode, Gradle ან Bazel ბილდი სრულდება შეცდომით. | `account_handle`, `project_handle` |
| `test_run.failed` | ლოკალური ან უწყვეტი ინტეგრაციის ტესტების გაშვება სრულდება შეცდომით, შერწყმული sharded გაშვების ან მიტოვებული გაშვების ჩათვლით. | `account_handle`, `project_handle` |
| `ci_job.failed` | Tuist runner-ის სამუშაო სრულდება შეცდომით. | `account_handle` |

გამოსაწერად, კლიენტი იძახებს `events/subscribe` მოვლენის სახელით, ზემოთ ჩამოთვლილი handle-ებით `arguments`-ში და `webhook` მიწოდებით, რომელიც შეიცავს `https://` callback URL-ს და `whsec_` ხელმოწერის საიდუმლოს. პროექტის მოვლენები მოითხოვს ანგარიშის წევრობას და შესაბამისი ტესტის ან ბილდის მონაცემებზე წვდომას; runner-ის სამუშაოს მოვლენები მოითხოვს ანგარიშის წევრობას და runner-ზე წვდომას. დადასტურებულმა [`auth.md`](https://workos.com/auth-md) access token-ებმა, დადასტურებულმა ანგარიშის token-ებმა და ბრაუზერის ავტორიზაციის გრანტებმა შეუძლიათ შექმნან გამოწერები; მიწოდება ჩერდება, როდესაც შესაბამისი სერთიფიკატი აღარ არის აქტიური. თითოეულ მომხმარებელს შეუძლია ჰქონდეს 25-მდე აქტიური გამოწერა. Tuist აგზავნის ვერიფიკაციის გამოწვევას callback-ზე გამოწერის შენახვამდე. Callback-მა უნდა დააბრუნოს ობიექტი, რომელიც შეიცავს იგივე `challenge` მნიშვნელობას. გამოწერა ნაგულისხმევად გრძელდება შვიდი დღე, შეიძლება განახლდეს ხელახლა გამოწერით და წყვეტს მიწოდებას, როდესაც მომხმარებლის წვდომა ან სერთიფიკატი იხსნება. არასავალდებულო `ttlMs` შეზღუდულია ერთ საათსა და 30 დღეს შორის. Tuist ცდილობს დროში ამოწურულ callback-ს და აუქმებს მას ხუთი წუთის განმავლობაში სამი თანმიმდევრული ამოწურვის შემდეგ; ხელახლა გამოიწერეთ callback-ის აღდგენის შემდეგ.

მოვლენის მოხდენისას, Tuist აგზავნits მის რესურსის იდენტიფიკატორს და დაფის URL-ს callback-ზე. ბილდისა და ტესტების გაშვების შეცდომები ასევე შეიცავს `is_ci` და `git_branch`-ს, რათა კლიენტებმა შეძლონ ლოკალური შეცდომების იგნორირება ან შტოს მიხედვით ფილტრაცია. ბილდის მოვლენები შეიცავს `build_system`-ს; runner-ის სამუშაოს მოვლენები შეიცავს როგორც `workflow_job_id`-ს, ასევე `workflow_run_id`-ს. მოთხოვნა შეიცავს გამოწერის იდენტიფიკატორს და [Standard Webhooks](https://www.standardwebhooks.com/) ხელმოწერის ჰედერებს, რათა კლიენტმა შეძლოს მისი წყაროს ვერიფიკაცია. Tuist ცდილობს წარუმატებელ მიწოდებებს, ამიტომ კლიენტებმა უნდა გამოიყენონ სტაბილური `eventId` დუბლიკატების გასაფილტრად. Payload გამოტოვებს ტესტების სახელებს, ლოგებსა და შეცდომის შეტყობინებებს; კლიენტს შეუძლია მიიღოს ეს დეტალები ზემოთ ჩამოთვლილი ინსტრუმენტების მეშვეობით და გადაწყვიტოს, შეატყობინოს თუ არა გუნდს ან დაიწყოს დებაგინგი. კლიენტებს შეუძლიათ შეაჩერონ მიწოდება `events/unsubscribe`-ით.

| `remote_cache` | ააქტიურებს Gradle-ის ბილდის ქეშს, აკონფიგურირებს Tuist remote cache-ის ატვირთვის პოლიტიკას და რეკომენდაციას უწევს ატვირთვას მხოლოდ continuous integration runner-ებიდან ლოკალური მხოლოდ-კითხვადი გამოყენებით. |
| `build_insights` | აყენებს Tuist Gradle პლაგინს და საჭიროების შემთხვევაში აკონფიგურირებს ბილდის ანალიტიკის ატვირთვის ქცევას. |
| `test_insights` | აყენებს Tuist Gradle პლაგინს, რათა Gradle `Test` task-ის შედეგები ავტომატურად აიტვირთოს. |
| `flaky_tests` | გეხმარებათ არასტაბილური ტესტების აღმოჩენის კონფიგურაციაში, Gradle Test Retry პლაგინის არასავალდებულო გამოყენებაში და ტესტების კარანტინის კონფიგურაციაში. |
| `test_sharding` | ამატებს continuous integration სამუშაო ნაკადს `tuistPrepareTestShards`-თვის, shard მატრიცის გენერაციას და `TUIST_SHARD_INDEX`-ზე დაფუძნებულ ტესტების გაშვებას. |

როდესაც `features` გამოტოვებულია, მოთხოვნა სთხოვს აგენტს, განმარტოს, რომელი ინტეგრაციები სურს მომხმარებელს, ან მოთხოვნიდან გამოიტანოს ყველაზე მცირე სასარგებლო ნაკრამი Gradle პროექტის რედაქტირებამდე.

#### Xcode ინტეგრაციის მოთხოვნის ფუნქციები

`integrate_xcode_project` მოთხოვნა აღწერს Xcode-ის ყველა ინტეგრაციას, რომელსაც Tuist მხარდაჭერს:

| ფუნქცია | რას აკონფიგურირებს აგენტი |
|---------|---------------------------|
| `xcode_cache` | აკონფიგურირებს `tuist setup cache`-ს, გენერირებული პროექტის ქეშის პარამეტრებს, Xcode ქეშის ხელით ბილდის პარამეტრებს და ატვირთვის პოლიტიკას, რომელიც შემოიფარგლება continuous integration runner-ებით. |
| `build_insights` | აკონფიგურირებს `tuist inspect build`-ს, `tuist xcodebuild`-ს, `-resultBundlePath`-ს და არასავალდებულო მანქანის მეტრიკებს `tuist setup insights`-ის მეშვეობით. |
| `test_insights` | აკონფიგურირებს `tuist inspect test`-ს, scheme-ის ტესტის post-actions-ებს და შედეგის ბანდლის გენერაციას continuous integration ტესტების გაშვებისთვის. |
| `test_sharding` | ამატებს Xcode-ის ან გენერირებული პროექტის shard-ების დაგეგმვას და shard-ების გაშვების სამუშაო ნაკადს `TUIST_SHARD_INDEX`-ით. |

როდესაც `features` გამოტოვებულია, მოთხოვნა სთხოვს აგენტს, განმარტოს, რომელი ინტეგრაციები სურს მომხმარებელს, ან მოთხოვნიდან გამოიტანოს ყველაზე მცირე სასარგებლო ნაკრამი Xcode პროექტის რედაქტირებამდე.
