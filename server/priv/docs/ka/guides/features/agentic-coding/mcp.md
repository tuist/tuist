# Model Context Protocol

[Model Context Protocol (MCP)](https://modelcontextprotocol.io/docs/getting-started/intro) არის ღია სტანდარტი, რომელიც საშუალებას აძლევს ხელოვნური ინტელექტის აგენტებს ურთიერთქმედებდნენ გარე სერვისებთან და მონაცემთა წყაროებთან. ის უზრუნველყოფს ისეთი აპლიკაციების, როგორიცაა [Claude](https://claude.ai/), [Claude Code](https://docs.anthropic.com/en/docs/claude-code), [Codex](https://developers.openai.com/codex/), და რედაქტორების, როგორიცაა [Zed](https://zed.dev), [Cursor](https://www.cursor.com) ან [Visual Studio Code](https://code.visualstudio.com), თავსებადობას Tuist-თან.

Tuist განათავსებს Model Context Protocol-ის სერვერულ წერტილს მისამართზე `https://tuist.dev/mcp`. თქვენი კლიენტის მასთან დაკავშირებით, აგენტებს შეუძლიათ მიიღონ წვდომა თქვენს Tuist პროექტის მონაცემებზე, მათ შორის ტესტების ანალიზზე, არასტაბილური ტესტების ანალიზზე და სხვა. ინსტრუმენტების უმეტესობა მხოლოდ წაკითხვადია და შეზღუდულია ავტორიზებული Tuist პროექტის მონაცემებით. ანგარიშის დაყენების ინსტრუმენტებს შეუძლიათ ჩამოთვალონ ანგარიშები, შექმნან ორგანიზაციები, შექმნან პროექტები და დაამატონ არსებული მომხმარებლები ორგანიზაციებში, როდესაც ავტორიზებულ მომხმარებელს აქვს შესაბამისი ნებართვები. ყოველი ინსტრუმენტი აქვეყნებს ანოტაციებს, რომლებიც მიუთითებს, არის თუ არა ის მხოლოდ წაკითხვადი, შეუძლია თუ არა გამოიწვიოს ძნელად შექცევადი ცვლილება და შეუძლია თუ არა შეცვალოს საჯარო ინტერნეტის მდგომარეობა. ანგარიშის დაყენების ინსტრუმენტებს სჭირდებათ მომხმარებლის ავტორიზაცია. ისინი არ არის ხელმისაწვდომი პროექტის ტოკენებისთვის ან ჩვეულებრივი ანგარიშის ტოკენებისთვის. როდესაც მომხმარებელი ბრაუზერში ავტორიზებს კლიენტს ან აცხადებს `auth.md` რეგისტრაციას, Tuist ასოცირებს ამ საიდენტიფიკაციო მონაცემს მომხმარებელთან მხოლოდ Model Context Protocol-ის წერტილზე, რათა დაყენების ინსტრუმენტებმა შეძლონ მოთხოვნილი სამუშაო პროცესის დასრულება.

Tuist ახორციელებს [2026-07-28 პროტოკოლს](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http). მოთხოვნები არის უსესიო: კლიენტები აგზავნიან თავიანთ პროტოკოლის მეტამონაცემებს ყოველ მოთხოვნასთან ერთად და შეუძლიათ პირდაპირ გამოიძახონ ინსტრუმენტები ინიციალიზაციის გარეშე. `server/discover` აბრუნებს სერვერის იდენტობას, შესაძლებლობებს, მხარდაჭერილ ვერსიებს და ინსტრუქციებს. არ არსებობს სესიის იდენტიფიკატორები ან დამოუკიდებელი მოვლენათა ნაკადები. კლიენტები, რომლებიც იყენებენ 2025-06-18 ან 2025-03-26 ინიციალიზაციის ნაკადს, კვლავ მხარდაჭერილია; ისინიც მუშაობენ სერვერის სესიების გარეშე.

## Model Context Protocol უნარების წინააღმდეგ

Model Context Protocol-ის ინსტრუმენტები და <.localized_link href="/guides/features/agentic-coding/skills">უნარები</.localized_link> შეიძლება ემთხვეოდნენ ფუნქციურად. მოცემული გადაკვეთის გათვალისწინებით, აირჩიეთ ერთი მიდგომა თითოეული სამუშაო პროცესისთვის და გამოიყენეთ ის თანმიმდევრულად, ნაცვლად ორივეს ერთ ნაკადში შერევისა.

კლიენტებისთვის, რომლებიც მხარს უჭერენ პლაგინების ინსტალაციას, გამოიყენეთ <.localized_link href="/guides/features/agentic-coding/plugins">Tuist პლაგინები</.localized_link> ორივეს ერთად დასაყენებლად.

## კონფიგურაცია

დაამატეთ `https://tuist.dev/mcp` როგორც დაშორებული Model Context Protocol სერვერი თქვენს კლიენტში. სერვერის ინიციალიზაციის ინსტრუქციები და საჯარო სერვერის ბარათი აღწერს OAuth 2.0-ს დინამიური კლიენტის რეგისტრაციით და სტანდარტული ბრაუზერის ავტორიზაციის ნაკადით პირდაპირ, აგენტებისგან გარე ავტორიზაციის დოკუმენტების მოთხოვნის ან მათზე გადასვლის მოთხოვნის გარეშე. ეს სერვერის მასშტაბის ინსტრუქციები ინარჩუნებს სამუშაო პროცესის სახელმძღვანელოს ზოგადს: ინსტრუმენტის ავტორიზაცია არ ავტორიზებს ადგილობრივ ბრძანების სტრიქონის ინსტრუმენტებს ან აგების სისტემის ინტეგრაციებს, და აგენტებმა უნდა დაადასტურონ მოთხოვნილი ცვლილებები შესაბამისი Tuist ინსტრუმენტების მეშვეობით. აგების სისტემის სპეციფიკური დაყენება და ავტორიზაციის შემოწმებები დოკუმენტირებულია ინტეგრაციის სახელმძღვანელოებსა და მოთხოვნებში. Tuist კვლავ აქვეყნებს როგორც [Open Authorization](https://oauth.net/2/) აღმოჩენის მეტამონაცემებს, ასევე მიმდინარე [auth.md პროტოკოლს](https://workos.com/auth-md) მისამართზე `https://tuist.dev/auth.md` ცალ-ცალკე.

წერტილი იღებს უსესიო `2026-07-28` Model Context Protocol მოთხოვნის სიცოცხლის ციკლს, მათ შორის `server/discover`, ძველ სესიაზე დაფუძნებულ ციკლთან ერთად. არსებულმა კლიენტებმა შეიძლება გააგრძელონ თავიანთი მიმდინარე კავშირის მეთოდის გამოყენება.

კლიენტები, რომლებიც მხარს უჭერენ Model Context Protocol მოვლენებს, შეუძლიათ გამოიწერონ პროექტის მოვლენები. იხილეთ [მოვლენები](#events) ხელმისაწვდომი მოვლენებისა და მიწოდების მოთხოვნებისთვის.

კლიენტები, რომლებიც უკვე მხარს უჭერენ დაშორებულ ბრაუზერის ავტორიზაციას, შეუძლიათ გააგრძელონ ავტორიზაცია ბრაუზერში. კლიენტებსა და აგენტებს, რომლებიც მხარს უჭერენ `auth.md`, შეუძლიათ ანონიმურად დარეგისტრირდნენ, წარმოადგინონ სანდო პროვაიდერის იდენტობის დამტკიცება ან დაიწყონ სერვისით ავტორიზებული ელფოსტის პრეტენზია. რეგისტრაცია აბრუნებს Tuist-ით ხელმოწერილ იდენტობის დამტკიცებას, რომელსაც აგენტი ცვლის სტანდარტულ ტოკენის წერტილზე ერთსაათიანი წვდომის ტოკენისთვის. Tuist აქვეყნებს თავის საჯარო ხელმოწერის გასაღებს და მხარს უჭერს სტანდარტულ ტოკენის გაუქმებასა და პროვაიდერის უსაფრთხოების მოვლენების მიწოდებას.

არაავტორიზებულმა აგენტმა უნდა წაიკითხოს `WWW-Authenticate` ჰედერი, რომელიც დაბრუნდა Model Context Protocol-ის წერტილიდან, მიიღოს დაცული რესურსის მეტამონაცემები, მიიღოს ავტორიზაციის სერვერის მეტამონაცემები და მიჰყვეს მის `agent_auth.skill` URL-ს. Tuist ასევე აბრუნებს იმავე ადგილობრივ `auth_md` URL-ს არაავტორიზებული პასუხის სხეულში, რათა ენის მოდელზე დაფუძნებულმა კლიენტებმა შეძლონ ნაკადის აღმოჩენა ნატიური კლიენტის ინტეგრაციაზე დაყრდნობის გარეშე. განლაგების ადგილობრივი დოკუმენტი არის ჭეშმარიტების წყარო წერტილების სახელების, მოთხოვნის სხეულების, პრეტენზიის გამოკითხვისა და დამტკიცების გაცვლისთვის.

სანამ აგენტი დაიწყებს ელფოსტის პრეტენზიას, მან უნდა სთხოვოს მომხმარებელს დაადასტუროს ელფოსტის მისამართი თავისი Tuist ანგარიშისთვის. მან არ უნდა გამოიტანოს ეს მისამართი პროვაიდერის პროფილიდან, Git კონფიგურაციიდან, გარემოს ცვლადიდან ან სესიის მეტამონაცემებიდან.

წერტილი იყენებს `mcp` სკოპის ჯგუფს. ანონიმურმა პრეტენზიამდელმა საიდენტიფიკაციო მონაცემმა შეიძლება აღმოაჩინოს შესაძლებლობები და წაიკითხოს საჯარო ინტეგრაციის სახელმძღვანელო, მაგრამ ის არ განიხილება როგორც შესული მომხმარებელი. ბრაუზერის ავტორიზაციის ან პრეტენზიის შემდეგ, საიდენტიფიკაციო მონაცემი არის მომხმარებელზე შეზღუდული და თითოეული ინსტრუმენტი იყენებს იმავე ავტორიზაციის შემოწმებებს, რასაც დაფის ინტერფეისი. იხილეთ <.localized_link href="/guides/server/authentication#scope-groups">სკოპის ჯგუფების დოკუმენტაცია</.localized_link> დეტალებისთვის.

ინსტრუმენტები წყდებიან პროექტებზე, რომლებსაც ავტორიზებულ მომხმარებელს უკვე აქვს წვდომა. Xcode და Gradle აგების ინსტრუმენტები იღებენ აგების UUID-ს ან დაფის URL-ს. UUID-მ უნდა დაადგინოს ზუსტად ერთი პროექტი; თუ ის ჩანს რამდენიმე პროექტში, ინსტრუმენტი აბრუნებს „ნაპოვნი არ არის“-ს, ნაცვლად სხვა პროექტის ანგარიშის არჩევისა. პროექტზე შეზღუდული დაფისა და API წაკითხვები რჩება ხელმისაწვდომი. მოხსენებული აქტორის იდენტიფიკატორები არის დაუდასტურებელი ეტიკეტები, არა საიდენტიფიკაციო მონაცემები ან დამატებითი წვდომის უფლებები.

აგების სიისა და დეტალური ინფორმაციის ინსტრუმენტები აჩვენებენ არასავალდებულო `tuist_version` მეტამონაცემებს: Xcode-ისა და Cargo-სთვის — Tuist CLI, Gradle-ისთვის — Tuist Gradle პლაგინი, ხოლო Mix-ისთვის — `tuist_ex` ბიბლიოთეკა. Xcode ასევე აჩვენებს `tuist_generation_version`-ს მის მიერ დაკავშირებული პროექტის გენერაციის მოვლენიდან, რაც შეიძლება განსხვავდებოდეს ატვირთული CLI-სგან. გამოტოვებული მნიშვნელობები არის null, ისინი არ გამოიტანება სერვერიდან ან სხვა ანგარიშიდან. Bazel იყენებს არსებულ `bazel_version`-ს; Once-ის გაშვების დეტალები კი აჩვენებს `once_version`-ს. ეს ველები აღწერენ მოხსენებულ ვერსიებს და არა დადასტურებულ იდენტობას ან ქსელური პროტოკოლის ვერსიებს. REST აგების endpoint-ები აჩვენებენ იგივე მეტამონაცემებს. არსებულ ინტეგრაციებსა და ფლეიკი ტესტების უნარებს არ სჭირდებათ ვერსიის ველები და სამუშაო ნაკადის ცვლილებები.

Tuist-ის ოპერატორები, რომლებიც იკვლევენ მომხმარებლის ანგარიშს, ამას აკეთებენ Tuist-ის შიდა ოპერაციული ინსტრუმენტების საშუალებით, რომელიც იწერს ყოველ ზარს; პირდაპირი კავშირი ამ endpoint-თან არ იძლევა წვდომას მომხმარებლის საკუთარი წევრობის ფარგლებს გარეთ.

თავსებადი კლიენტები იღებენ ფაქტობრივ აღწერებს ინსტრუმენტების წყაროს რევიზიის, ბმულებისა და შედეგის ლიმიტების შესახებ ინიციალიზაციის დროს, inline OAuth ავთენტიკაციის ინფორმაციასთან ერთად. ეს აღწერები არ განსაზღვრავენ პასუხის სტილს ან ვერიფიკაციის სამუშაო ნაკადს. მომხმარებლებს შეუძლიათ პირდაპირ დასვან კითხვა `ask_tuist` მოთხოვნის გამოძახების გარეშე; მოთხოვნა კვლავ ხელმისაწვდომია წყაროზე დაფუძნებული ცხადი სამუშაო ნაკადისთვის.

თითოეულ ოპერაციას აქვს ფიქსირებული ლიმიტები კონკურენტულობის, ხანგრძლივობის, გადაადგილების, წაკითხული ბაიტებისა და პასუხის ზომისთვის. ძებნისა და ჩამონათვალის შედეგები მოიცავს `truncated` და `truncation_reason` ველებს. როდესაც შედეგი შემცირებულია, შეავიწროეთ გზა, ფაილის ნიმუში ან საძიებო სიტყვა, ნაცვლად შედეგის ამომწურავად მიჩნევისა.

არასავალდებულო `start_ms` და `end_ms` ირჩევენ ნაბიჯებს, რომლებიც ემთხვევა დროის დიაპაზონს მილიწამებში ბილდის დაწყებიდან; ბოლო არ არის შემავალი. ორივე ინსტრუმენტი იღებს ბილდის UUID-ს ან დაშბორდის URL-ს როგორც `build_run_id`. გადასცეთ დაბრუნებული ნაბიჯის `id` უცვლელად როგორც `step_id` მისი ჟურნალის მისაღებად. ჟურნალები ინახავენ 64 KiB-მდე თითოეული ნაბიჯისთვის, `log_truncated`-ით მიუთითებს გამოტოვებულ გამომავალ მონაცემებს.

ნაბიჯები გროვდება ნაგულისხმევად, როცა Xcode-ის ბილდები მუშავდება. ჩაწერილი ნაბიჯის მონაცემები ინახება 90 დღის განმავლობაში. სიის პასუხი შეიცავს `availability`-ს: `available`, როცა ჩაწერილი ნაბიჯები არსებობს, მაშინაც კი, თუ ფილტრები არაფერს ემთხვევა; `processing`, როცა ბილდი ჯერ კიდევ მუშავდება და ჯერ არ აქვს ნაბიჯები; ან `unavailable`, როცა ნაბიჯები არ ჩაწერილა ან ვადა გაუვიდათ.

იგივე ოპერაციები ხელმისაწვდომია HTTP API-ზე `GET /api/projects/{account_handle}/{project_handle}/xcode/builds/{build_id}/steps` და `GET /api/projects/{account_handle}/{project_handle}/xcode/builds/{build_id}/steps/{step_id}` მისამართებზე, იგივე ფილტრებითა და პაგინაციით. ორივეს სჭირდება წვდომა ბილდის პროექტის წაკითხვისთვის.

ეს ინსტრუმენტები ეტაპობრივად ნერგდება და აბრუნებს მონაცემებს მხოლოდ იმ პროექტებისთვის, სადაც ისინი ჩართულია; სხვა პროექტებისთვის ისინი აბრუნებენ შეცდომას ცარიელი შედეგის ნაცვლად. ტიპი ხელმისაწვდომია მხოლოდ იმ პროექტებისთვის, რომლებიც იყენებენ შესაბამის ბილდის ხელსაწყოთა ჯაჭვს. ინსტრუმენტები იღებენ შემოსაზღვრულ `start_at`/`end_at` ფილტრებს, `environment` (`any`, `ci` ან `local`) და ზუსტ `branch`. `list_build_entities` იღებს `q`-ს; `list_build_entity_history` მხარს უჭერს გაუმჭვირვალე `after`/`before` კურსორებს. უცნობი დროის ან ქეშის დაკვირვებები რჩება მიუწვდომელი ნულის ან გამოტოვების ნაცვლად. ისტორია მიუთითებს ჩაწერილ მშობელზე და ნატიურ შესრულებაზე დეტალური შესწავლისთვის არსებული გაშვების ინსტრუმენტების გამოყენებით.

`get_build_entity` მეტრიკა მოიცავს `duration_samples`-ს, დაკვირვებების რაოდენობას ჩაწერილი დროით: რეალური ნულოვანი ხანგრძლივობები ითვლება, დაკარგული დრო — არა. ეს რაოდენობა შეიძლება იყოს დაკვირვებების რაოდენობაზე ნაკლები; მიუწვდომელი ხანგრძლივობის სტატისტიკა რჩება null.

Xcode-ის მოდულების ხანგრძლივობა მოდის ბილდის ჟურნალებში გაზომილი სამიზნე კომპილაციებიდან. მოდულის ქეშის გარჩევები და სამიზნეები კომპილაციის სამუშაოს გარეშე არ მონაწილეობენ ხანგრძლივობის შერჩევაში. კომპილაციის დაკვირვებები მიუთითებენ Xcode-ის ბილდზე; ქეშის მოვლენები მიუთითებენ გენერაციის ან ქეშის ბრძანებაზე.

Bazel-ის მოქმედებები იდენტიფიცირდება სამიზნის ლეიბლით, მნემონიკით და კონფიგურირებული პირველადი გამომავალით, რაც ცალკეულ მოქმედებებსა და კონფიგურაციებს განცალკევებულს ტოვებს შეყვანაზე დამოკიდებული ქეშის დაიჯესტების გარეშე. ისტორია აღრიცხავს BEP-ით შეტყობინებულ შესრულებებს, არა ქეშის ძიებებს ან trace-profile ფაზებს. სრული შესრულების დაფარვა მოითხოვს `--build_event_publish_all_actions`-ს; არტეფაქტების მიწოდება ხდება მაქსიმალური ძალისხმევით, ამიტომ დაკარგული დაკვირვებები არ არის იმის მტკიცებულება, რომ სამუშაო არ შესრულებულა. ძველი Kura-ს პეილოადები სტაბილური იდენტობის ან შესრულების დაწყების გარეშე რჩება მიღებული, მაგრამ არაინდექსირებული. დასრულების დროის გაზომვების არარსებობა რჩება მიუწვდომელი და რეალური ნულოვანი ხანგრძლივობები ითვლება.

Mix-ის მოდულების ხანგრძლივობა ზომავს შემცველი ფაილის კომპილაციას, არა დამოუკიდებლად გაზომილ მოდულის სამუშაოს. Once-ის მოქმედებები იყენებენ გამოცხადებულ სამიზნე/შესაძლებლობა/ინდექსის სლოტებს, როდესაც კლიენტმა შეატყობინა სამიზნეების ასახვა; მხოლოდ დიაგნოსტიკური ლეიბლები არ არის სტაბილური იდენტობები. არსებული კლიენტები და გაშვების დონის ინსტრუმენტები რჩება მხარდაჭერილი უცვლელად.

ანალიტიკის წაკითხვებს აქვს შემოსაზღვრული მეხსიერება და შესრულების დრო. თუ მოთხოვნა აღემატება ამ ლიმიტებს, ინსტრუმენტი აბრუნებს შეცდომას ცარიელი შედეგის გამოგონების ნაცვლად.

ახალი დაკვირვებები ინდექსირდება განლაგების შემდეგ; ეს ფუნქცია არ ავსებს არსებულ გაშვების ტელემეტრიას. იდენტობის მეტამონაცემები ინახება ინდივიდუალურ დაკვირვებებზე უფრო დიდხანს <.localized_link href="/guides/server/data-retention">მონაცემთა შენახვის პოლიტიკის</.localized_link> მიხედვით.

### მოვლენები

კლიენტები, რომლებიც იყენებენ უმდგომარეობიან `2026-07-28` Model Context Protocol ციკლს, შეუძლიათ გამოიძახონ `events/list` მოვლენებისა და მათი payload სქემების აღმოსაჩენად:

| მოვლენა | როდის იგზავნება | გამოწერის ფილტრი |
|-------|-----------------|---------------------|
| `test_case.marked_flaky` | სატესტო შემთხვევა იცვლება არაარასტაბილურიდან არასტაბილურზე. | `account_handle`, `project_handle` |
| `build.failed` | ლოკალური ან უწყვეტი ინტეგრაციის Xcode, Gradle ან Bazel ბილდი მთავრდება შეცდომით. | `account_handle`, `project_handle` |
| `test_run.failed` | ლოკალური ან უწყვეტი ინტეგრაციის ტესტების გაშვება მთავრდება შეცდომით, შერწყმული დაყოფილი გაშვების ან მიტოვებული გაშვების ჩათვლით. | `account_handle`, `project_handle` |
| `ci_job.failed` | Tuist გამშვების სამუშაო მთავრდება შეცდომით. | `account_handle` |

გამოსაწერად, კლიენტი იძახებს `events/subscribe`-ს მოვლენის სახელით, ზემოთ ჩამოთვლილი handle-ებით `arguments`-ში და `webhook` მიწოდებით, რომელიც შეიცავს `https://` callback URL-ს და `whsec_` ხელმოწერის საიდუმლოს. პროექტის მოვლენები მოითხოვს ანგარიშის წევრობას და წვდომას შესაბამის ტესტის ან ბილდის მონაცემებზე; გამშვების სამუშაოს მოვლენები მოითხოვს ანგარიშის წევრობას და გამშვების წაკითხვის წვდომას. [`auth.md`](https://workos.com/auth-md) access token-ები, ანგარიშის token-ები და ბრაუზერის ავტორიზაციის გრანტები შეუძლიათ შექმნან გამოწერები; მიწოდება ჩერდება, როდესაც შესაბამისი credential აღარ არის აქტიური. თითოეულ მომხმარებელს შეუძლია ჰქონდეს 25-მდე აქტიური გამოწერა. Tuist აგზავნის ვერიფიკაციის გამოწვევას callback-ზე გამოწერის შენახვამდე. Callback-მა უნდა დააბრუნოს ობიექტი იგივე `challenge` მნიშვნელობით. გამოწერა ძალაშია შვიდი დღე ნაგულისხმევად, შეიძლება განახლდეს ხელახლა გამოწერით და ჩერდება მიწოდება, როდესაც მომხმარებლის წვდომა ან credential იხსნება. არასავალდებულო `ttlMs` შეზღუდულია ერთ საათსა და 30 დღეს შორის. Tuist ახდენს გადაცილებული callback-ის ხელახლა ცდას და აუქმებს მას სამი თანმიმდევრული გადაცილების შემდეგ, რომლებიც ხუთ წუთს მოიცავს; გამოიწერეთ ხელახლა callback-ის აღდგენის შემდეგ.

როდესაც მოვლენა ხდება, Tuist აგზავნის მის რესურსის იდენტიფიკატორს და dashboard URL-ს callback-ზე. ბილდის და ტესტების გაშვების შეცდომები ასევე შეიცავს `is_ci`-ს და `git_branch`-ს, რათა კლიენტებმა შეძლონ ლოკალური შეცდომების იგნორირება ან ფილტრაცია ბრენჩის მიხედვით. ბილდის მოვლენები შეიცავს `build_system`-ს; გამშვების სამუშაოს მოვლენები შეიცავს როგორც `workflow_job_id`-ს, ასევე `workflow_run_id`-ს. მოთხოვნა შეიცავს გამოწერის იდენტიფიკატორს და [Standard Webhooks](https://www.standardwebhooks.com/) ხელმოწერის ჰედერებს, რათა კლიენტმა შეძლოს მისი წყაროს ვერიფიცირება. Tuist ახდენს ჩავარდნილი მიწოდებების ხელახლა ცდას, ამიტომ კლიენტებმა უნდა გამოიყენონ სტაბილური `eventId` დუბლიკატების გასაფილტრად. პეილოდი არ შეიცავს ტესტების სახელებს, ლოგებს და შეცდომის შეტყობინებებს; კლიენტს შეუძლია მიიღოს ეს დეტალები ზემოთ ჩამოთვლილი ინსტრუმენტების მეშვეობით და გადაწყვიტოს, შეატყობინოს თუ არა გუნდს ან დაიწყოს დებაგიנגი. კლიენტებს შეუძლიათ შეაჩერონ მიწოდება `events/unsubscribe`-ის მეშვეობით.

#### Gradle ინტეგრაციის პრომპტის ფუნქციები

`integrate_gradle_project` პრომპტი და `get_gradle_integration_guide` ინსტრუმენტი აღწერს სრულ დაყენების სამუშაო ნაკადს. ინსტრუმენტზე ასევე არის მითითება სერვერის ინიციალიზაციის ინსტრუქციებში, რაც მას აღმოჩენადს ხდის ისეთი აგენტებისთვის, რომლებიც არ ჩამოთვლიან პრომპტებს.

| ფუნქცია | რას აკონფიგურირებს აგენტი |
|---------|---------------------------|
| `remote_cache` | ააქტიურებს Gradle-ის ბილდის ქეშს, აკონფიგურირებს Tuist remote cache ატვირთვის პოლიტიკას და რეკომენდაციას აძლევს ატვირთვას მხოლოდ continuous integration გამშვებებიდან ლოკალური მხოლოდ-წაკითხვის გამოყენებით. |
| `build_insights` | აყენებს Tuist Gradle პლაგინს და საჭიროების შემთხვევაში აკონფიგურირებს ბილდის ანალიტიკის ატვირთვის ქცევას. |
| `test_insights` | აყენებს Tuist Gradle პლაგინს, რათა Gradle `Test` task-ის შედეგები ავტომატურად აიტვირთოს. |
| `flaky_tests` | გასწავლით არასტაბილური ტესტების აღმოჩენის დაყენებას, Gradle Test Retry პლაგინის არასავალდებულო გამოყენებას და ტესტების კარანტინის კონფიგურაციას. |
| `test_sharding` | ამატებს continuous integration სამუშაო ნაკადს `tuistPrepareTestShards`-ისთვის, shard მატრიცის გენერაციას და `TUIST_SHARD_INDEX`-ზე დაფუძნებულ ტესტების შესრულებას. |

როდესაც `features` გამოტოვებულია, პრომპტი სთხოვს აგენტს გაარკვიოს, რომელი ინტეგრაციები სურს მომხმარებელს ან გამოიტანოს უმცირესი სასარგებლო ნაკრები მოთხოვნიდან Gradle პროექტის რედაქტირებამდე.

#### Xcode ინტეგრაციის პრომპტის ფუნქციები

`integrate_xcode_project` პრომპტი აღწერს ყველა Xcode ინტეგრაციას, რომელსაც Tuist მხარს უჭერს:

| ფუნქცია | რას აკონფიგურირებს აგენტი |
|---------|---------------------------|
| `xcode_cache` | აკონფიგურირებს `tuist setup cache`-ს, გენერირებული პროექტის ქეშის პარამეტრებს, Xcode ქეშის ბილდის ხელით მითითებულ პარამეტრებს და ატვირთვის პოლიტიკას, რომელიც შეზღუდულია continuous integration გამშვებებით. |
| `build_insights` | აკონფიგურირებს `tuist inspect build`-ს, `tuist xcodebuild`-ს, `-resultBundlePath`-ს და არასავალდებულო მანქანის მეტრიკებს `tuist setup insights`-ის მეშვეობით. |
| `test_insights` | აკონფიგურირებს `tuist inspect test`-ს, სქემის ტესტის post-actions-ებს და შედეგების ბანდლის გენერაციას continuous integration ტესტების გაშვებისთვის. |
| `test_sharding` | ამატებს Xcode ან გენერირებული პროექტის shard დაგეგმვის და shard შესრულების სამუშაო ნაკადს `TUIST_SHARD_INDEX`-ით. |

როდესაც `features` გამოტოვებულია, პრომპტი სთხოვს აგენტს გაარკვიოს, რომელი ინტეგრაციები სურს მომხმარებელს ან გამოიტანოს უმცირესი სასარგებლო ნაკრები მოთხოვნიდან Xcode პროექტის რედაქტირებამდე.
