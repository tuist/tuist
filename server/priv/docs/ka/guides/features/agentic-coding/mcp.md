# Model Context Protocol

[Model Context Protocol (MCP)](https://modelcontextprotocol.io/docs/getting-started/intro) არის ღია სტანდარტი, რომელიც საშუალებას აძლევს ხელოვნური ინტელექტის აგენტებს ურთიერთქმედება გარე სერვისებთან და მონაცემთა წყაროებთან. ის უზრუნველყოფს [Claude](https://claude.ai/), [Claude Code](https://docs.anthropic.com/en/docs/claude-code), [Codex](https://developers.openai.com/codex/)-ისა და რედაქტორების, როგორიცაა [Zed](https://zed.dev), [Cursor](https://www.cursor.com) ან [Visual Studio Code](https://code.visualstudio.com), თავსებადობას Tuist-თან.

Tuist განათავსებს Model Context Protocol-ის სერვერულ ბოლოწერტილს `https://tuist.dev/mcp`-ზე. მასზე თქვენი კლიენტის მიერთებით, აგენტებს შეუძლიათ წვდომა თქვენს Tuist პროექტის მონაცემებზე, მათ შორის ტესტების ანალიტიკაზე, არასტაბილური ტესტების ანალიზზე და სხვა. უმეტესი ინსტრუმენტი მხოლოდ წაკითხვის რეჟიმშია და შეზღუდულია ავტორიზებული Tuist პროექტის მონაცემებით. ანგარიშის კონფიგურაციის ინსტრუმენტებს შეუძლიათ ანგარიშების ჩამოთვლა, ორგანიზაციების შექმნა, პროექტების შექმნა და არსებული მომხმარებლების დამატება ორგანიზაციებში, როდესაც ავტორიზებულ მომხმარებელს აქვს შესაბამისი ნებართვები. ყოველი ინსტრუმენტი ასახავს ანოტაციებს, რომლებიც მიუთითებს, არის თუ არა ის მხოლოდ წაკითხვის რეჟიმში, შეუძლია თუ არა მას გამოიწვიოს ძნელად შექცევადი ცვლილება და შეუძლია თუ არა საჯარო ინტერნეტის მდგომარეობის შეცვლა. ანგარიშის კონფიგურაციის ინსტრუმენტები მოითხოვს მომხმარებლის ავტორიზაციას. ისინი არ არის ხელმისაწვდომი პროექტის ტოკენებისთვის ან ჩვეულებრივი ანგარიშის ტოკენებისთვის. როდესაც მომხმარებელი ავტორიზებს კლიენტს ბრაუზერში ან ითხოვს `auth.md` რეგისტრაციას, Tuist ამ სერთიფიკატს აკავშირებს მომხმარებელთან მხოლოდ Model Context Protocol-ის ბოლოწერტილზე, რათა კონფიგურაციის ინსტრუმენტებმა შეასრულონ მოთხოვნილი სამუშაო პროცესი.

Tuist ახორციელებს [2026-07-28 პროტოკოლს](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http). მოთხოვნები უმდგომარეოა: კლიენტები აგზავნიან პროტოკოლის მეტამონაცემებს ყოველ მოთხოვნასთან ერთად და შეუძლიათ ინსტრუმენტების პირდაპირ გამოძახება ინიციალიზაციის გარეშე. `server/discover` აბრუნებს სერვერის იდენტიფიკატორს, შესაძლებლობებს, მხარდაჭერილ ვერსიებს და ინსტრუქციებს. არ არსებობს სესიის იდენტიფიკატორები ან დამოუკიდებელი მოვლენათა ნაკადები. 2025-06-18 ან 2025-03-26 ინიციალიზაციის ნაკადის გამომყენებელი კლიენტები კვლავ მხარდაჭერილია; ისინიც მუშაობენ სერვერის სესიების გარეშე.

## Model Context Protocol უნარების წინააღმდეგ

Model Context Protocol-ის ინსტრუმენტებსა და <.localized_link href="/guides/features/agentic-coding/skills">უნარებს</.localized_link> შორის შესაძლოა ფუნქციური გადაკვეთა იყოს. არსებული გადაკვეთის გათვალისწინებით, აირჩიეთ ერთი მიდგომა სამუშაო პროცესისთვის და გამოიყენეთ ის თანმიმდევრულად, ნაცვლად ორივეს ერთ ნაკადში შერევისა.

კლიენტებისთვის, რომლებიც მხარდაჭერენ პლაგინების ინსტალაციას, გამოიყენეთ <.localized_link href="/guides/features/agentic-coding/plugins">Tuist პლაგინები</.localized_link> ორივეს ერთად ინსტალაციისთვის.

## კონფიგურაცია

დაამატეთ `https://tuist.dev/mcp` როგორც დაშორებული Model Context Protocol სერვერი თქვენს კლიენტში. სერვერის ინიციალიზაციის ინსტრუქციები და საჯარო სერვერის ბარათი აღწერს OAuth 2.0-ს დინამიური კლიენტის რეგისტრაციით და სტანდარტული ბრაუზერის ავტორიზაციის ნაკადით პირდაპირ, აგენტებისგან გარე ავტორიზაციის დოკუმენტების მოთხოვნის ან მათი მიყოლის გარეშე. ეს სერვერის მასშტაბის ინსტრუქციები ინარჩუნებს სამუშაო პროცესის მითითებებს ზოგადს: ინსტრუმენტის ავტორიზაცია არ ავტორიზებს ადგილობრივ ბრძანების სტრიქონის ინსტრუმენტებს ან აგების სისტემის ინტეგრაციებს და აგენტებმა უნდა დაადასტურონ მოთხოვნილი ცვლილებები შესაბამისი Tuist ინსტრუმენტების მეშვეობით. აგების სისტემის სპეციფიკური კონფიგურაცია და ავტორიზაციის შემოწმებები დოკუმენტირებულია ინტეგრაციის სახელმძღვანელოებში და მოთხოვნებში. Tuist კვლავ ასახავს როგორც [Open Authorization](https://oauth.net/2/)-ის აღმოჩენის მეტამონაცემებს, ასევე მიმდინარე [auth.md პროტოკოლს](https://workos.com/auth-md) `https://tuist.dev/auth.md`-ზე ცალ-ცალკე.

თუ თქვენი ერთ-ერთი ორგანიზაცია აიძულებს ერთჯერად შესვლას, ბრაუზერში კლიენტის ავტორიზაცია მოითხოვს იმ ორგანიზაციის მეშვეობით შესულ სესიას და Tuist საჭიროების შემთხვევაში ჯერ პროვაიდერთან გაგზავნით. იხილეთ <.localized_link href="/guides/integrations/authentication/sso#choose-an-enrollment-policy">ერთჯერადი შესვლა</.localized_link>.

ბოლოწერტილი იღებს უმდგომარეო `2026-07-28` Model Context Protocol მოთხოვნის ციკლს, `server/discover`-ის ჩათვლით, ძველ სესიაზე დაფუძნებულ ციკლთან ერთად. არსებულ კლიენტებს შეუძლიათ განაგრძონ მიმდინარე მიერთების მეთოდის გამოყენება.

კლიენტებს, რომლებიც მხარდაჭერენ Model Context Protocol მოვლენებს, შეუძლიათ გამოიწერონ პროექტის მოვლენები. იხილეთ [მოვლენები](#events) ხელმისაწვდომი მოვლენებისა და მიწოდების მოთხოვნებისთვის.

კლიენტებს, რომლებიც უკვე მხარდაჭერენ დაშორებულ ბრაუზერის ავტორიზაციას, შეუძლიათ განაგრძონ ბრაუზერში ავტორიზაცია. კლიენტებსა და აგენტებს, რომლებიც მხარდაჭერენ `auth.md`-ს, შეუძლიათ ანონიმური რეგისტრაცია, წარადგინონ სანდო პროვაიდერის იდენტიფიკატორის დამტკიცება ან დაიწყონ სერვისით ავტორიზებული ელფოსტის მოთხოვნა. რეგისტრაცია აბრუნებს Tuist-ით ხელმოწერილ იდენტიფიკატორის დამტკიცებას, რომელსაც აგენტი ცვლის სტანდარტულ ტოკენის ბოლოწერტილზე ერთსაათიანი წვდომის ტოკენისთვის. Tuist აქვეყნებს თავის საჯარო ხელმოწერის გასაღებს და მხარდაჭერს სტანდარტულ ტოკენის გაუქმებასა და პროვაიდერის უსაფრთხოების მოვლენების მიწოდებას.

არაავტორიზებულმა აგენტმა უნდა წაიკითხოს `WWW-Authenticate` ჰედერი, რომელიც დაბრუნდა Model Context Protocol-ის ბოლოწერტილიდან, მოიძიოს დაცული რესურსის მეტამონაცემები, მოიძიოს ავტორიზაციის სერვერის მეტამონაცემები და მიჰყვეს მის `agent_auth.skill` URL-ს. Tuist ასევე აბრუნებს იმავე ადგილობრივ `auth_md` URL-ს არაავტორიზებული პასუხის სხეულში, რათა ენის მოდელზე დაფუძნებულმა კლიენტებმა აღმოაჩინონ ნაკადი ნატიური კლიენტის ინტეგრაციაზე დაყრდნობის გარეშე. განლაგება-ადგილობრივი დოკუმენტი არის სიმართლის წყარო ბოლოწერტილის სახელების, მოთხოვნის სხეულების, მოთხოვნის გამოკითხვისა და დამტკიცების გაცვლისთვის.

სანამ აგენტი დაიწყებს ელფოსტის მოთხოვნას, მან უნდა სთხოვოს მომხმარებელს დაადასტუროს ელფოსტის მისამართი მათი Tuist ანგარიშისთვის. მან არ უნდა გამოიტანოს ეს მისამართი პროვაიდერის პროფილიდან, Git კონფიგურაციიდან, გარემოს ცვლადიდან ან სესიის მეტამონაცემებიდან.

ბოლოწერტილი იყენებს `mcp` სკოპების ჯგუფს. ანონიმურმა წინასწარ-მოთხოვნის სერთიფიკატმა შეიძლება აღმოაჩინოს შესაძლებლობები და წაიკითხოს საჯარო ინტეგრაციის მითითებები, მაგრამ ის არ განიხილება როგორც შესული მომხმარებელი. ბრაუზერის ავტორიზაციის ან მოთხოვნის შემდეგ, სერთიფიკატი არის მომხმარებელზე შეზღუდული და ყოველი ინსტრუმენტი იყენებს იმავე ავტორიზაციის შემოწმებებს, რასაც დაფა. დეტალებისთვის იხილეთ <.localized_link href="/guides/server/authentication#scope-groups">სკოპების ჯგუფების დოკუმენტაცია</.localized_link>.

ინსტრუმენტები მიმართავენ იმ პროექტებს, რომელთა წაკითხვაც ავტორიზებულ მომხმარებელს უკვე შეუძლია. Xcode-ისა და Gradle-ის ბილდის ინსტრუმენტები იღებენ ბილდის UUID-ს ან დაშბორდის URL-ს. UUID-მ ზუსტად ერთი პროექტი უნდა განსაზღვროს; თუ ის რამდენიმე პროექტში გვხვდება, ინსტრუმენტი „არ არის ნაპოვნი“ პასუხს აბრუნებს სხვა პროექტის ანგარიშის შერჩევის ნაცვლად. პროექტის ფარგლებში დაშბორდისა და API-ს წაკითხვა ხელმისაწვდომი რჩება. მოხსენებული აქტორების იდენტიფიკატორები არიან დაუდასტურებელი სახელები და არა სერთიფიკატები ან დამატებითი წვდომის უფლებები.

ბილდის სიისა და დეტალური ინფორმაციის ინსტრუმენტები ავლენენ არასავალდებულო `tuist_version` მეტამონაცემებს: Xcode-ისა და Cargo-სთვის — Tuist CLI, Gradle-ისთვის — Tuist Gradle პლაგინი, ხოლო Mix-ისთვის — `tuist_ex` ბიბლიოთეკა. Xcode ასევე ავლენს `tuist_generation_version`-ს მის მიერ დაკავშირებული პროექტის გენერაციის მოვლენიდან, რომელიც შეიძლება განსხვავდებოდეს ატვირთვის CLI-ისგან. გამოტოვებული მნიშვნელობები არის null და არ გამოიტანება სერვერიდან ან სხვა ანგარიშიდან. Bazel იყენებს თავის არსებულ `bazel_version`-ს; Once-ის გაშვების დეტალები ავლენს `once_version`-ს. ეს ველები აღწერენ მოხსენებულ ვერსიებს და არა დადასტურებულ იდენტობას ან სადენის კონტრაქტის ვერსიებს. REST ბილდის ბოლოწერტილები ასევე ავლენენ იგივე მეტამონაცემებს. არსებულ ინტეგრაციასა და ფლეიკი ტესტების უნარებს არ სჭირდებათ ვერსიის ველები და არ საჭიროებენ სამუშაო ნაკადის ცვლილებებს.

Tuist-ის ოპერატორები, რომლებიც იკვლევენ მომხმარებლის ანგარიშს, ამას აკეთებენ Tuist-ის შიდა ოპერაციული ინსტრუმენტების მეშვეობით, რომელიც იწერს ყოველ ზარს; ამ ბოლოწერტილთან პირდაპირი კავშირი არ იძლევა წვდომას მომხმარებლის საკუთარი წევრობის ფარგლებს გარეთ.

## WebMCP

ბრაუზერებში, რომლებიც მხარს უჭერენ [WebMCP](https://webmachinelearning.github.io/webmcp)-ს, Tuist-ის გვერდები აფიქსირებენ ინსტრუმენტებს `document.modelContext`-ით, ასე რომ ბრაუზერში ჩაშენებულ აგენტებს შეუძლიათ მათი გამოძახება დამატებითი კონფიგურაციის გარეშე. ზარები სრულდება Tuist სერვერზე.

- **ვებგვერდისა და დოკუმენტაციის გვერდები** აფიქსირებენ დოკუმენტაციისა და წყაროს ინსტრუმენტებს (`search_tuist`, `search_tuist_code`, `list_tuist_files` და `read_tuist_file`). მათ არ სჭირდებათ თქვენგან სისტემაში შესვლა.
- **ანგარიშის დაშბორდის გვერდები**, როდესაც სისტემაში ხართ შესული, აფიქსირებენ Tuist-ის მხოლოდ წაკითხვის ინსტრუმენტებს ამ ანგარიშისთვის. ყოველი გვერდი აფიქსირებს მხოლოდ იმ ინსტრუმენტებს, რასაც ის აჩვენებს, პროექტის ბილდის სისტემის მიხედვით: Gradle პროექტის ბილდების გვერდი იღებს Gradle ბილდის ინსტრუმენტებს, მისი ტესტების გვერდები — ტესტებისა და დაფარვის ინსტრუმენტებს, ხოლო რანერების გვერდები — რანერის ინსტრუმენტებს. ყოველ გვერდს ასევე აქვს დოკუმენტაციის ინსტრუმენტები, `list_projects` და `get_project`. ინსტრუმენტები მუშაობენ სისტემაში შესული მომხმარებლის სახელით, ამიტომ ისინი მხოლოდ იმ მონაცემებს სწვდებიან, რასაც თქვენ შეგიძლიათ წაიკითხოთ დაშბორდზე, და მხოლოდ იმ ანგარიშს, რომელსაც უყურებთ. როდესაც გადადიხართ სხვა გვერდზე ან ანგარიშზე, ინსტრუმენტები იცვლება იმ გვერდის ინსტრუმენტებით.

ინსტრუმენტები, რომლებიც ქმნიან, ცვლიან ან შლიან მონაცემებს, არ არის ხელმისაწვდომი WebMCP-ის მეშვეობით, რადგან ბრაუზერის აგენტი იღებს ინსტრუმენტებს თქვენგან დამატების გარეშე და კითხულობს ბილდებისა და ტესტების მიერ წარმოქმნილ კონტენტს. დაუკავშირეთ MCP კლიენტი `/mcp` ბოლოწერტილს ამ ინსტრუმენტების გამოსაყენებლად.

თუ ორგანიზაცია იყენებს ერთიან შესვლას (SSO), დაშბორდში შესვლა მოხდეთ მისი პროვაიდერის მეშვეობით, რათა გამოიყენოთ მისი ინსტრუმენტები.

## ბილდის სისტემის ინტეგრაციები იყენებენ ორ კრედენციალს

კრედენციალი, რომელიც გამოიყენება Model Context Protocol-ის ინსტრუმენტებისთვის, არ ახდენს Gradle პლაგინის ან Bazel-ის დისტანციური სერვისების ავტორიზაციას. სანამ აგენტი შეცვლის ან გადაამოწმებს Gradle ან Bazel ინტეგრაციას, უნდა გაუშვას:

```bash
tuist auth whoami --url https://tuist.dev
```

თუ ეს ბრძანება არ არის ავტორიზებული, აგენტმა უნდა შეწყვიტოს მუშაობა და სთხოვოს მომხმარებელს გაუშვას:

```bash
tuist auth login --url https://tuist.dev
```

ლოკალური ან თვითმასპინძელი განლაგებისთვის, ჩაანაცვლეთ URL ორივე ბრძანებაში და `tuist.toml`-ში. ყველგან შეინარჩუნეთ ზუსტად იგივე ჰოსტნეიმის დაწერა. მაგალითად, `localhost` და `127.0.0.1` იყენებენ ცალკე შენახულ კრედენციალებს.


## შესაძლებლობები

### ინსტრუმენტები

შემდეგი ინსტრუმენტები ხელმისაწვდომია Tuist Model Context Protocol სერვერის მეშვეობით:

ყოველი ინსტრუმენტი აქვეყნებს ადამიანისთვის გასაგებ აღწერას ცხადი შეყვანისა და გამოტანის სქემებთან ერთად. წარმატებული გამოძახებები აბრუნებენ სტრუქტურირებულ კონტენტს, რომელიც შეესაბამება გამოცხადებულ გამოტანის სქემას, ასევე იმავე შედეგს ტექსტურად სერიალიზებულს იმ კლიენტებისთვის, რომლებიც ჯერ არ იყენებენ სტრუქტურირებულ კონტენტს.

ინსტრუმენტები, რომლებიც იღებენ ერთი ჩანაწერის იდენტიფიკატორს, როგორიცაა `build_run_id`, `test_run_id`, `test_case_id`, `bundle_id`, `run_id`, `generation_id`, ან `cache_run_id`, ასევე იღებენ ამ ჩანაწერის Tuist დაშბორდის URL-ს. ჩასვით URL პირდაპირ ბრაუზერიდან, ნაცვლად მისგან იდენტიფიკატორის ამოღებისა.

#### დოკუმენტაციისა და საზოგადოების ძებნა

ეს მხოლოდ წაკითხვის ინსტრუმენტი ეძებს Tuist-ის დოკუმენტაციას, [გამოყენების პროგრამული ინტერფეისის](https://en.wikipedia.org/wiki/API) ცნობარს, GitHub გამოშვებებს, საზოგადოების ფორუმს და GitHub პრობლემებს იმავე საძიებო სისტემის მეშვეობით, რომელიც ამუშავებს დოკუმენტაციის ვებსაიტს. გამოშვების შედეგები მოიცავს პროდუქტს, ვერსიას, გამოქვეყნების თარიღს და პრერელიზის სტატუსს. ნაგულისხმევად ეძებენ სტაბილურ გამოშვებებს, ხოლო პრერელიზების ჩართვა შესაძლებელია `include_prereleases`-ით. ინსტრუმენტი ხელმისაწვდომია მხოლოდ Tuist-ის მიერ მასპინძლობულ სერვერზე `https://tuist.dev/mcp`.

#### უკუკავშირი

აგენტებს შეუძლიათ შეატყობინონ Tuist-ის გუნდს, თუ Tuist-ის ინსტრუმენტი ან მოთხოვნა არ მუშაობდა ისე, როგორც ელოდნენ, მაგალითად, გაუგებარი შედეგი, შეცდომა, მონაცემების არარსებობა ან შესაძლებლობის ნაკლებობა. აგენტებს სთხოვენ შესთავაზონ ანგარიში და გაგზავნონ იგი მხოლოდ თქვენი თანხმობის შემდეგ. ყოველი ანგარიში ხსნის დიალოგს Tuist-ის მხარდაჭერასთან, რომელმაც შეიძლება გიპასუხოთ ელფოსტით. ანგარიში მოიცავს იმას, რასაც აგენტი ელოდა, რა მოხდა, არჩევით შეთავაზებას, თქვენს Tuist მომხმარებლის ID-ს, სახელსა და ელფოსტას, ასევე ორგანიზაციებს, რომლებსაც ეკუთვნით. აგენტებს ასევე შეუძლიათ მიუთითონ ანგარიში და პროექტი, სადაც პრობლემა მოხდა, რათა გუნდმა იცოდეს, რომელ ორგანიზაციასთან დაუკავშირდეს; მიიღება მხოლოდ ის ანგარიშები, რომლებსაც თქვენ ეკუთვნით. ანგარიშების გაგზავნა შეუძლიათ მხოლოდ Tuist მომხმარებლად შესულ აგენტებს და ყოველ მომხმარებელს შეუძლია გახსნას საათში 10-მდე ანგარიში. ინსტრუმენტი ხელმისაწვდომია მხოლოდ Tuist-ის მიერ მასპინძლობულ სერვერზე `https://tuist.dev/mcp`.

#### წყაროზე დაფუძნებული პასუხები

ეს მხოლოდ წაკითხვის ინსტრუმენტები საშუალებას აძლევს აგენტებს გამოიყენონ ზუსტი საჯარო Tuist წყაროს რევიზია, რომელიც განლაგებულია მასპინძლობულ სერვერთან ერთად, როგორც სანდო წყარო პასუხებისთვის, რომლებიც დამოკიდებულია მიმდინარე ქცევაზე. ისინი ხელმისაწვდომია მხოლოდ `https://tuist.dev/mcp`-ზე.

თავსებადი კლიენტები იღებენ ფაქტობრივ აღწერებს ინსტრუმენტების წყაროს რევიზიის, ბმულებისა და შედეგის ლიმიტების შესახებ ინიციალიზაციის დროს, inline OAuth ავტორიზაციის ინფორმაციასთან ერთად. ეს აღწერები არ განსაზღვრავენ პასუხის სტილს ან გადამოწმების სამუშაო ნაკადს. მომხმარებლებს შეუძლიათ პირდაპირ დასვან კითხვა `ask_tuist` მოთხოვნის გამოძახების გარეშე; მოთხოვნა რჩება ხელმისაწვდომი ცხადი წყაროზე დაფუძნებული სამუშაო ნაკადისთვის.

ყოველ ოპერაციას აქვს ფიქსირებული ლიმიტები კონკურენტულობის, ხანგრძლივობის, გადაადგილების, წაკითხული ბაიტებისა და პასუხის ზომისთვის. ძებნისა და ჩამონათვალის შედეგები მოიცავს `truncated` და `truncation_reason` ველებს. როდესაც შედეგი შემცირებულია, შეავიწროვეთ გზა, ფაილის ნიმუში ან საძიებო ტერმინი, ნაცვლად შედეგის ამოწურულად ჩათვლისა.

არასავალდებულო `start_ms` და `end_ms` ირჩევენ ნაბიჯებს, რომლებიც ემთხვევა დროის დიაპაზონს მილიწამებში ბილდის დაწყებიდან; ბოლო არ არის ჩათვლილი. ორივე ინსტრუმენტი იღებს ბილდის UUID-ს ან დაშბორდის URL-ს როგორც `build_run_id`. გადასცეთ დაბრუნებული ნაბიჯის `id` უცვლელად როგორც `step_id` მისი ლოგის მისაღებად. ლოგები ინახავენ 64 KiB-მდე თითო ნაბიჯზე, `log_truncated` მიუთითებს გამოტოვებულ გამოტანაზე.

ნაბიჯები ნაგულისხმევად იკრიბება Xcode ბილდების დამუშავებისას. ჩაწერილი ნაბიჯის მონაცემები ინახება 90 დღის განმავლობაში. სიის პასუხი შეიცავს `availability`-ს: `available`, როდესაც არსებობს ჩაწერილი ნაბიჯები, მაშინაც კი, თუ ფილტრები არაფერს ემთხვევა; `processing`, როდესაც ბილდი ჯერ კიდევ მუშავდება და ჯერ არ აქვს ნაბიჯები; ან `unavailable`, როდესაც ნაბიჯები არ ჩაწერილა ან ამოიწურა.

Bazel დეტალები მოიცავს სანიტიზებულ ქმედების ლოგებს, როცა ისინი გამოქვეყნებულია; Gradle დეტალური `log` არის null. `compare_builds` მოთხოვნა იყენებს ამ დაფარვას სრული Bazel ტრეისების შესანახი შეჯამებებისგან განსასხვავებლად და მიმართავს აგენტებს ნაბიჯის დეტალებისკენ ქმედების შედეგებისა და ლოგებისთვის, სანამ ფართო გამოძახების შედეგებს შეამოწმებენ.

ეს ინსტრუმენტები ეტაპობრივად იწერება და აბრუნებენ მონაცემებს მხოლოდ იმ პროექტებისთვის, სადაც ისინი ჩართულია; სხვა პროექტებისთვის ისინი აბრუნებენ შეცდომას ცარიელი შედეგის ნაცვლად. სახე ხელმისაწვდომია მხოლოდ იმ პროექტებისთვის, რომლებიც იყენებენ მის ბილდის ინსტრუმენტთა ჯაჭვს. ინსტრუმენტები იღებენ შეზღუდულ `start_at`/`end_at` ფილტრებს, `environment` (`any`, `ci` ან `local`) და ზუსტ `branch`-ს. `list_build_entities` იღებს `q`-ს; `list_build_entity_history` მხარდაჭერს გამჭვირვალე `after`/`before` კურსორებს. უცნობი დროის ან ქეშის დაკვირვებები რჩება მიუწვდომლად, ნულის ან გამოტოვების ნაცვლად. ისტორია მიუთითებს ჩაწერილ მშობელსა და ნატიურ გაშვებაზე დეტალური ანალიზისთვის არსებული გაშვების ინსტრუმენტების გამოყენებით.

`get_build_entity` მეტრიკები მოიცავს `duration_samples`-ს, რაც არის დაკვირვებების რაოდენობა ჩაწერილი დროით: ნამდვილი ნულოვანი ხანგრძლივობები ითვლება, გამოტოვებული დრო — არა. ეს რაოდენობა შეიძლება იყოს დაკვირვებების რაოდენობაზე ნაკლები; მიუწვდომელი ხანგრძლივობის სტატისტიკა რჩება null.

Xcode მოდულების ხანგრძლივობები მოდის ბილდის ლოგებში გაზომილი სამიზნე კომპილაციებიდან. მოდულის ქეშის გადაწყვეტები და სამიზნეები კომპილაციის გარეშე არ მონაწილეობენ ხანგრძლივობის ნიმუშებში. კომპილაციის დაკვირვებები მიუთითებენ Xcode ბილდზე; ქეშის მოვლენები მიუთითებენ გენერაციის ან ქეშის ბრძანებაზე.

Bazel მოქმედებები იდენტიფიცირდება სამიზნის ლეიბლით, მნემონიკით და კონფიგურირებული ძირითადი გამომავალით, რაც ინარჩუნებს ცალკეულ მოქმედებებსა და კონფიგურაციებს განცალკევებულად, შეყვანაზე დამოკიდებული ქეშის დაიჯესტების გარეშე. ისტორია იწერს BEP-ით შეტყობინებულ გაშვებებს, არა ქეშის ძიებებს ან ტრეის-პროფილის ფაზებს. სრული გაშვების დაფარვა მოითხოვს `--build_event_publish_all_actions`-ს; არტეფაქტების მიწოდება საუკეთესო ძალისხმევით ხდება, ამიტომ გამოტოვებული დაკვირვებები არ არის იმის მტკიცებულება, რომ სამუშაო არ შესრულებულა. უფრო ძველი Kura payload-ები სტაბილური იდენტიფიკატორის ან გაშვების დაწყების გარეშე რჩება მიღებულად, მაგრამ არაინდექსირებულად. დასრულების დროის გაზომვების არარსებობა რჩება მიუწვდომლად და ნამდვილი ნულოვანი ხანგრძლივობები ითვლება.

Mix მოდულების ხანგრძლივობები ზომავენ შემცველი ფაილის კომპილაციას, არა დამოუკიდებლად გაზომილ მოდულის სამუშაოს. Once მოქმედებები იყენებენ გამოცხადებულ სამიზნე/შესაძლებლობა/ინდექსის სლოტებს, როცა კლიენტმა შეატყობინა სამიზნეების ასახვა; დიაგნოსტიკის ლეიბლები მარტო არ არის სტაბილური იდენტიფიკატორები. არსებული კლიენტები და გაშვების დონის ინსტრუმენტები რჩება მხარდაჭერილი უცვლელად.

Cargo ყუთები (crates) დაჯგუფებულია ზუსტად ჩაწერილი ყუთის ფესვით, სახელით და სახეობით. Checkout-ის გზის ცვლილებებმა შეიძლება გაყოს ისტორიები, ხოლო ბილდის პროფილები, ფუნქციები და სამიზნე ტრიპლეტები არ განირჩევა. ისტორია ზომავს rustc გამოძახებებს, არა ფაილზე დამოკიდებულ სამუშაოს ან ქეშის მოხვედრებს; არარსებული სამუშაოები არ ამყარებს წაშლებს ან სამუშაო სივრცის სრულ ინვენტარს.

ანალიტიკის წაკითხვებს აქვს შეზღუდული მეხსიერება და შესრულების დრო. თუ მოთხოვნა აღემატება ამ ლიმიტებს, ინსტრუმენტი აბრუნებს შეცდომას ცარიელი შედეგის გამოგონების ნაცვლად.

ახალი დაკვირვებები ინდექსირდება განლაგების შემდეგ; ეს ფუნქცია არ ავსებს არსებულ გაშვების ტელემეტრიას. იდენტიფიკატორის მეტამონაცემები ცოცხლობს ინდივიდუალურ დაკვირვებებზე მეტხანს <.localized_link href="/guides/server/data-retention">მონაცემთა შენახვის პოლიტიკის</.localized_link> შესაბამისად.

### მოვლენები

კლიენტები, რომლებიც იყენებენ უმდგომარე `2026-07-28` Model Context Protocol-ის ციკლს, შეუძლიათ გამოიძახონ `events/list` მოვლენებისა და მათი შინაარსის სქემების აღმოსაჩენად:

| მოვლენა | როდის იგზავნება | გამოწერის ფილტრი |
|-------|-----------------|---------------------|
| `test_case.marked_flaky` | სატესტო შემთხვევა იცვლება არაარასტაბილურიდან არასტაბილურად. | `account_handle`, `project_handle` |
| `build.failed` | ლოკალური ან უწყვეტი ინტეგრაციის Xcode, Gradle ან Bazel ბილდი მთავრდება შეცდომით. | `account_handle`, `project_handle` |
| `test_run.failed` | ლოკალური ან უწყვეტი ინტეგრაციის ტესტების გაშვება მთავრდება შეცდომით, შერწყმული დაყოფილი გაშვების ან მიტოვებული გაშვების ჩათვლით. | `account_handle`, `project_handle` |
| `ci_job.failed` | Tuist-ის გამშვების სამუშაო მთავრდება შეცდომით. | `account_handle` |

გამოწერისთვის კლიენტი იძახებს `events/subscribe` მოვლენის სახელით, ზემოთ ჩამოთვლილი ხელსაწყოებით `arguments`, და `webhook` მიწოდებით, რომელიც შეიცავს `https://` callback URL-ს და `whsec_` ხელმოწერის საიდუმლოს. პროექტის მოვლენები მოითხოვენ ანგარიშის წევრობას და შესაბამის ტესტის ან ბილდის მონაცემებზე წვდომას; გამშვების სამუშაოების მოვლენები მოითხოვენ ანგარიშის წევრობას და გამშვებზე წვდომას. დამოწმებულმა [`auth.md`](https://workos.com/auth-md) წვდომის ტოკენებმა, დამოწმებულმა ანგარიშის ტოკენებმა და ბრაუზერის ავტორიზაციის გრანტებმა შეუძლიათ შექმნან გამოწერები; მიწოდება ჩერდება, როდესაც შესაბამისი სერთიფიკატი აღარ არის აქტიური. თითოეულ მომხმარებელს შეუძლია ჰქონდეს მაქსიმუმ 25 აქტიური გამოწერა. Tuist აგზავნის ვერიფიკაციის გამოწვევას callback-ზე გამოწერის შენახვამდე. callback-მა უნდა დააბრუნოს ობიექტი, რომელიც შეიცავს იგივე `challenge` მნიშვნელობას. გამოწერა ძალაშია შვიდი დღის განმავლობაში, შეიძლება განახლდეს ხელახლა გამოწერით და წყვეტს მიწოდებას, როდესაც მომხმარებლის წვდომა ან სერთიფიკატი ამოიღება. არასავალდებულო `ttlMs` შეზღუდულია ერთ საათსა და 30 დღეს შორის. Tuist თავიდან ცდის დროის ამოწურულ callback-ს და აუქმებს მას სულ მცირე სამი თანმიმდევრული დროის ამოწურვის შემდეგ, რომლებიც მოიცავს ხუთ წუთს; ხელახლა გამოიწერეთ callback-ის აღდგენის შემდეგ.

როდესაც მოვლენა ხდება, Tuist აგზავნის მის რესურსის იდენტიფიკატორს და დაფის URL-ს callback-ზე. ბილდისა და ტესტების გაშვების შეცდომები ასევე შეიცავს `is_ci`-ს და `git_branch`-ს, რათა კლიენტებმა შეძლონ ლოკალური შეცდომების იგნორირება ან შტოს მიხედვით ფილტრაცია. ბილდის მოვლენები შეიცავს `build_system`-ს; გამშვების სამუშაოების მოვლენები შეიცავს როგორც `workflow_job_id`-ს, ასევე `workflow_run_id`-ს. მოთხოვნა შეიცავს გამოწერის იდენტიფიკატორს და [Standard Webhooks](https://www.standardwebhooks.com/)-ის ხელმოწერის ჰედერებს, რათა კლიენტმა შეძლოს მისი წარმოშობის ვერიფიცირება. Tuist თავიდან ცდის წარუმატებელ მიწოდებებს, ამიტომ კლიენტებმა უნდა გამოიყენონ სტაბილური `eventId` დუბლიკატების გასაფილტრად. შინაარსი არ შეიცავს ტესტების სახელებს, ლოგებს და შეცდომის შეტყობინებებს; კლიენტმა შეუძლია მიიღოს ეს დეტალები ზემოთ ჩამოთვლილი ინსტრუმენტების მეშვეობით და გადაწყვიტოს, შეატყობინოს თუ არა გუნდს ან დაიწყოს დებაგინგი. კლიენტებმა შეუძლიათ შეაჩერონ მიწოდება `events/unsubscribe`-ით.

პროექტის მონაცემების მოთხოვნები იღებენ `account_handle`-ს და `project_handle`-ს კვლევის კონკრეტულ პროექტზე შესაზღუდვად. შედარების მოთხოვნები ასევე იღებენ `base` და `head` არგუმენტებს ორი შესადარებელი ელემენტის მითითებისთვის (ID-ით, დაფის URL-ით ან შტოს სახელით). `ask_tuist` იღებს `question`-ს პროექტის პარამეტრების ნაცვლად. `integrate_gradle_project` ასევე იღებს `features`-ს, Gradle ინტეგრაციების კომებით გამოყოფილ სიას გამოყენებისთვის: `remote_cache`, `build_insights`, `test_insights`, `flaky_tests` და `test_sharding`. `integrate_bazel_project` იღებს არასავალდებულო `server_url`-ს თვითმასპინძელი ან ლოკალური ინსტალაციებისთვის. `integrate_xcode_project` იღებს `features`-ს `xcode_cache`-ით, `build_insights`-ით, `test_insights`-ით და `test_sharding`-ით.

#### Gradle ინტეგრაციის მოთხოვნის ფუნქციები

`integrate_gradle_project` მოთხოვნა და `get_gradle_integration_guide` ინსტრუმენტი აღწერს სრულ დაყენების სამუშაო ნაკადს. ინსტრუმენტზე ასევე არის მითითება სერვერის ინიციალიზაციის ინსტრუქციებში, რაც მას აგენტებისთვის საპოვნელს ხდის მაშინაც კი, როცა ისინი მოთხოვნებს არ ჩამოთვლიან.

| ფუნქცია | რას აკონფიგურირებს აგენტი |
|---------|---------------------------|
| `remote_cache` | ააქტიურებს Gradle-ის ბილდის ქეშს, აკონფიგურირებს Tuist-ის დისტანციური ქეშის ატვირთვის პოლიტიკას და რეკომენდაციას უწევს ატვირთვას მხოლოდ უწყვეტი ინტეგრაციის გამშვებიდან ლოკალური მხოლოდ-წასაკითხი გამოყენებით. |
| `build_insights` | აყენებს Tuist Gradle პლაგინს და საჭიროების შემთხვევაში აკონფიგურირებს ბილდის ანალიტიკის ატვირთვის ქცევას. |
| `test_insights` | აყენებს Tuist Gradle პლაგინს, რათა Gradle `Test` ამოცანის შედეგები ავტომატურად აიტვირთოს. |
| `flaky_tests` | გიწევთ ხელმძღვანელობას არამდგრადი ტესტების აღმოჩენის დაყენებაში, Gradle Test Retry პლაგინის არასავალდებულო გამოყენებაში და ტესტის კარანტინის კონფიგურაციაში. |
| `test_sharding` | ამატებს უწყვეტი ინტეგრაციის სამუშაო ნაკადს `tuistPrepareTestShards`-თვის, შარდების მატრიცის გენერირებას და `TUIST_SHARD_INDEX`-ზე დაფუძნებულ ტესტის შესრულებას. |

როცა `features` გამოტოვებულია, მოთხოვნა სთხოვს აგენტს გაარკვიოს, რომელი ინტეგრაციები სურს მომხმარებელს, ან მოთხოვნიდან გამოიტანოს ყველაზე მცირე სასარგებლო ნაკრები Gradle პროექტის რედაქტირებამდე.

#### Xcode ინტეგრაციის მოთხოვნის ფუნქციები

`integrate_xcode_project` მოთხოვნა აღწერს ყველა Xcode ინტეგრაციას, რომელსაც Tuist მხარს უჭერს:

| ფუნქცია | რას აკონფიგურირებს აგენტი |
|---------|---------------------------|
| `xcode_cache` | აკონფიგურირებს `tuist setup cache`-ს, გენერირებული პროექტის ქეშის პარამეტრებს, Xcode ქეშის ბილდის ხელით მითითებულ პარამეტრებს და ატვირთვის პოლიტიკას, რომელიც შეზღუდულია უწყვეტი ინტეგრაციის გამშვებებზე. |
| `build_insights` | აკონფიგურირებს `tuist inspect build`-ს, `tuist xcodebuild`-ს, `-resultBundlePath`-ს და არასავალდებულო მანქანურ მეტრიკებს `tuist setup insights`-ის მეშვეობით. |
| `test_insights` | აკონფიგურირებს `tuist inspect test`-ს, სქემის ტესტის post-actions-ებს და შედეგების ბანდლის გენერირებას უწყვეტი ინტეგრაციის ტესტის გაშვებებისთვის. |
| `test_sharding` | ამატებს Xcode-ის ან გენერირებული პროექტის შარდების დაგეგმვას და შარდების შესრულების სამუშაო ნაკადს `TUIST_SHARD_INDEX`-ით. |

როცა `features` გამოტოვებულია, მოთხოვნა სთხოვს აგენტს გაარკვიოს, რომელი ინტეგრაციები სურს მომხმარებელს, ან მოთხოვნიდან გამოიტანოს ყველაზე მცირე სასარგებლო ნაკრები Xcode პროექტის რედაქტირებამდე.
