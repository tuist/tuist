# Model Context Protocol

[Model Context Protocol (MCP)](https://modelcontextprotocol.io/docs/getting-started/intro) არის ღია სტანდარტი, რომელიც საშუალებას აძლევს ხელოვნური ინტელექტის აგენტებს ურთიერთქმედონ გარე სერვისებთან და მონაცემთა წყაროებთან. ის უზრუნველყოფს ისეთი აპლიკაციების, როგორიცაა [Claude](https://claude.ai/), [Claude Code](https://docs.anthropic.com/en/docs/claude-code), [Codex](https://developers.openai.com/codex/), და რედაქტორების, მაგალითად [Zed](https://zed.dev), [Cursor](https://www.cursor.com) ან [Visual Studio Code](https://code.visualstudio.com), თავსებადობას Tuist-თან.

Tuist განათავსებს Model Context Protocol-ის სერვერის ენდპოინტს მისამართზე `https://tuist.dev/mcp`. თქვენი კლიენტის მასთან დაკავშირებით, აგენტებს შეუძლიათ მიუწვდეთ თქვენს Tuist პროექტის მონაცემებს, მათ შორის ტესტების ანალიტიკას, არასტაბილური ტესტების ანალიზს და სხვა. ინსტრუმენტების უმეტესობა მხოლოდ კითხვის რეჟიმშია და შეზღუდულია ავტორიზებული Tuist პროექტის მონაცემებით. ანგარიშის კონფიგურაციის ინსტრუმენტებს შეუძლიათ ჩამოთვალონ ანგარიშები, შექმნან ორგანიზაციები, შექმნან პროექტები და დაამატონ არსებული მომხმარებლები ორგანიზაციებში, თუ ავტორიზებულ მომხმარებელს აქვს საჭირო ნებართვები. ყოველი ინსტრუმენტი აქვეყნებს ანოტაციებს, რომლებიც მიუთითებს, არის თუ არა ის მხოლოდ კითხვის რეჟიმში, შეუძლია თუ არა გამოიწვიოს ძნელად შექცევადი ცვლილება და შეუძლია თუ არა შეცვალოს საჯარო ინტერნეტის მდგომარეობა. ანგარიშის კონფიგურაციის ინსტრუმენტები მოითხოვს მომხმარებლის ავტორიზაციას. ისინი არ არის ხელმისაწვდომი პროექტის ტოკენებისთვის ან ჩვეულებრივი ანგარიშის ტოკენებისთვის. როდესაც მომხმარებელი ბრაუზერში ავტორიზებს კლიენტს ან აცხადებს `auth.md` რეგისტრაციას, Tuist ამ სერთიფიკატს ასოცირდება მომხმარებელთან მხოლოდ Model Context Protocol-ის ენდპოინტზე, რათა კონფიგურაციის ინსტრუმენტებმა შეძლონ მოთხოვნილი სამუშაო პროცესის დასრულება.

Tuist ახორციელებს [2026-07-28 პროტოკოლს](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http). მოთხოვნები არის უსესიო: კლიენტები აგზავნიან თავიანთ პროტოკოლის მეტამონაცემებს ყოველ მოთხოვნასთან ერთად და შეუძლიათ პირდაპირ გამოიძახონ ინსტრუმენტები ინიციალიზაციის გარეშე. `server/discover` აბრუნებს სერვერის იდენტობას, შესაძლებლობებს, მხარდაჭერილ ვერსიებს და ინსტრუქციებს. არ არსებობს სესიის იდენტიფიკატორები ან დამოუკიდებელი მოვლენათა ნაკადები. კლიენტები, რომლებიც იყენებენ 2025-06-18 ან 2025-03-26 ინიციალიზაციის ნაკადს, კვლავ მხარდაჭერილია; ისინიც მუშაობენ სერვერის სესიების გარეშე.

## Model Context Protocol უნარების წინააღმდეგ

Model Context Protocol-ის ინსტრუმენტებსა და <.localized_link href="/guides/features/agentic-coding/skills">უნარებს</.localized_link> შორის შესაძლოა ფუნქციური გადაფარვა იყოს. არსებული გადაფარვის გათვალისწინებით, აირჩიეთ ერთი მიდგომა თითოეული სამუშაო პროცესისთვის და გამოიყენეთ ის თანმიმდევრულად, ნაცვლად იმისა, რომ ორივე ერთსა და იმავე ნაკადში აურიოთ.

კლიენტებისთვის, რომლებიც მხარს უჭერენ პლაგინების ინსტალაციას, გამოიყენეთ <.localized_link href="/guides/features/agentic-coding/plugins">Tuist პლაგინები</.localized_link> ორივეს ერთად ინსტალაციისთვის.

## კონფიგურაცია

დაამატეთ `https://tuist.dev/mcp` როგორც დაშორებული Model Context Protocol სერვერი თქვენს კლიენტში. სერვერის ინიციალიზაციის ინსტრუქციები და საჯარო სერვერის ბარათი აღწერს OAuth 2.0-ს დინამიური კლიენტის რეგისტრაციით და სტანდარტული ბრაუზერის ავტორიზაციის ნაკადით პირდაპირ, აგენტებისგან გარე ავტორიზაციის დოკუმენტების მოთხოვნის ან მათზე გადასვლის მოთხოვნის გარეშე. ეს სერვერის დონის ინსტრუქციები ინარჩუნებს სამუშაო პროცესის მითითებებს ზოგადს: ინსტრუმენტის ავტორიზაცია არ ავტორიზებს ადგილობრივ ბრძანების სტრიქონის ინსტრუმენტებს ან აწყობის სისტემის ინტეგრაციებს და აგენტებმა უნდა შეამოწმონ მოთხოვნილი ცვლილებები შესაბამისი Tuist ინსტრუმენტების მეშვეობით. აწყობის სისტემის სპეციფიკური კონფიგურაცია და ავტორიზაციის შემოწმებები დოკუმენტირებულია ინტეგრაციის სახელმძღვანელოებში და მოთხოვნებში. Tuist კვლავ აქვეყნებს როგორც [Open Authorization](https://oauth.net/2/)-ის აღმოჩენის მეტამონაცემებს, ასევე მიმდინარე [auth.md პროტოკოლს](https://workos.com/auth-md) მისამართზე `https://tuist.dev/auth.md` ცალ-ცალკე.

ენდპოინტი იღებს უსესიო `2026-07-28` Model Context Protocol-ის მოთხოვნის ციკლს, `server/discover`-ის ჩათვლით, ძველ სესიაზე დაფუძნებულ ციკლთან ერთად. არსებულმა კლიენტებმა შეიძლება გააგრძელონ თავიანთი მიმდინარე კავშირის მეთოდის გამოყენება.

კლიენტებს, რომლებიც მხარს უჭერენ Model Context Protocol-ის მოვლენებს, შეუძლიათ გამოიწერონ პროექტის მოვლენები. იხილეთ [მოვლენები](#events) ხელმისაწვდომი მოვლენებისა და მიწოდების მოთხოვნებისთვის.

კლიენტებს, რომლებიც უკვე მხარს უჭერენ დაშორებულ ბრაუზერის ავტორიზაციას, შეუძლიათ გააგრძელონ ავტორიზაცია ბრაუზერში. კლიენტებსა და აგენტებს, რომლებიც მხარს უჭერენ `auth.md`-ს, შეუძლიათ დარეგისტრირდნენ ანონიმურად, წარმოადგინონ სანდო პროვაიდერის იდენტობის დამტკიცება ან დაიწყონ სერვისით ავტორიზებული ელფოსტის მოთხოვნა. რეგისტრაცია აბრუნებს Tuist-ის მიერ ხელმოწერილ იდენტობის დამტკიცებას, რომელსაც აგენტი ცვლის სტანდარტულ ტოკენის ენდპოინტზე ერთსაათიანი წვდომის ტოკენისთვის. Tuist აქვეყნებს თავის საჯარო ხელმოწერის გასაღებს და მხარს უჭერს სტანდარტულ ტოკენის გაუქმებასა და პროვაიდერის უსაფრთხოების მოვლენების მიწოდებას.

არაავტორიზებულმა აგენტმა უნდა წაიკითხოს `WWW-Authenticate` ჰედერი, რომელიც დაბრუნდა Model Context Protocol-ის ენდპოინტის მიერ, მიიღოს დაცული რესურსის მეტამონაცემები, მიიღოს ავტორიზაციის სერვერის მეტამონაცემები და გადავიდეს მის `agent_auth.skill` URL-ზე. Tuist ასევე აბრუნებს იმავე ადგილობრივ `auth_md` URL-ს არაავტორიზებული პასუხის სხეულში, რათა ენის მოდელზე დაფუძნებულმა კლიენტებმა შეძლონ ნაკადის აღმოჩენა ნატიური კლიენტის ინტეგრაციაზე დამოკიდებულების გარეშე. განლაგების ადგილობრივი დოკუმენტი არის ჭეშმარიტობის წყარო ენდპოინტის სახელების, მოთხოვნის სხეულების, მოთხოვნის გამოკითხვისა და დამტკიცების გაცვლისთვის.

სანამ აგენტი დაიწყებს ელფოსტის მოთხოვნას, მან უნდა სთხოვოს მომხმარებელს დაადასტუროს ელფოსტის მისამართი მათი Tuist ანგარიშისთვის. მან არ უნდა გამოიტანოს ეს მისამართი პროვაიდერის პროფილიდან, Git კონფიგურაციიდან, გარემოს ცვლადიდან ან სესიის მეტამონაცემებიდან.

ენდპოინტი იყენებს `mcp` სკოპის ჯგუფს. ანონიმურმა წინასწარ მოთხოვნის სერთიფიკატმა შეიძლება აღმოაჩინოს შესაძლებლობები და წაიკითხოს საჯარო ინტეგრაციის მითითებები, მაგრამ ის არ განიხილება როგორც შესული მომხმარებელი. ბრაუზერის ავტორიზაციის ან მოთხოვნის შემდეგ, სერთიფიკატი არის მომხმარებლის სკოპით შეზღუდული და თითოეული ინსტრუმენტი იყენებს იმავე ავტორიზაციის შემოწმებებს, რასაც დაშბორდი. იხილეთ <.localized_link href="/guides/server/authentication#scope-groups">სკოპის ჯგუფების დოკუმენტაცია</.localized_link> დეტალებისთვის.

ინსტრუმენტები წყვეტენ პროექტებს, რომლებსაც ავტორიზებულ მომხმარებელს უკვე შეუძლია წაიკითხოს. Xcode-ისა და Gradle-ის აწყობის ინსტრუმენტები იღებენ აწყობის UUID-ს ან დაშბორდის URL-ს. UUID-მ უნდა მოახდინოს ზუსტად ერთი პროექტის იდენტიფიცირება; თუ ის რამდენიმე პროექტში ჩანს, ინსტრუმენტი აბრუნებს „არ არის ნაპოვნი“-ს, ნაცვლად იმისა, რომ აირჩიოს სხვა პროექტის ანგარიში. პროექტის სკოპით შეზღუდული დაშბორდისა და API-ს კითხვები კვლავ ხელმისაწვდომია. მოხსენებული აქტორის იდენტიფიკატორები არის დაუდასტურებელი ლეიბლები, არა სერთიფიკატები ან დამატებითი წვდომის უფლებები.

აწყობის სიისა და დეტალური ინფორმაციის ინსტრუმენტები აჩვენებენ არასავალდებულო `tuist_version` მეტამონაცემებს: Xcode-ისა და Cargo-სთვის — Tuist CLI, Gradle-ისთვის — Tuist Gradle პლაგინი, ხოლო Mix-ისთვის — `tuist_ex` ბიბლიოთეკა. Xcode ასევე აჩვენებს `tuist_generation_version`-ს მის მიერთებული პროექტის გენერაციის მოვლენიდან, რომელიც შეიძლება განსხვავდებოდეს ატვირთვის CLI-სგან. გამოტოვებული მნიშვნელობები არის null და არ გამოიტანება სერვერიდან ან სხვა ანგარიშიდან. ეს მხოლოდ-კითხვის ინსტრუმენტები საშუალებას აძლევენ აგენტებს გამოიყენონ ზუსტად ის საჯარო Tuist წყაროს რევიზია, რომელიც განთავსებულია ჰოსტინგულ სერვერთან ერთად, როგორც ჭეშმარიტების წყარო პასუხებისთვის, რომლებიც დამოკიდებულია მიმდინარე ქცევაზე. ისინი ხელმისაწვდომია მხოლოდ `https://tuist.dev/mcp`-ზე.

თავსებადი კლიენტები იღებენ ფაქტობრივ აღწერებს ინსტრუმენტების წყაროს რევიზიის, ბმულებისა და შედეგის ლიმიტების შესახებ ინიციალიზაციის დროს, inline OAuth ავტორიზაციის ინფორმაციასთან ერთად. ეს აღწერები არ განსაზღვრავენ პასუხის სტილს ან ვერიფიკაციის სამუშაო პროცესს. მომხმარებლებს შეუძლიათ პირდაპირ დასვან კითხვა `ask_tuist` მოთხოვნის გამოძახების გარეშე; მოთხოვნა კვლავ ხელმისაწვდომია ცხადი წყაროზე დაფუძნებული სამუშაო პროცესისთვის.

ყოველ ოპერაციას აქვს ფიქსირებული ლიმიტები კონკურენტულობის, ხანგრძლივობის, გადაადგილების, წაკითხული ბაიტებისა და პასუხის ზომისთვის. ძებნისა და ჩამონათვალის შედეგები მოიცავს `truncated` და `truncation_reason` ველებს. როდესაც შედეგი შეკვეცილია, შეავიწროვეთ გზა, ფაილის ნიმუში ან საძიებო ტერმინი, ნაცვლად შედეგის ამოწურულად განხილვისა.

ნაბიჯები გროვდება ნაგულისხმევად, როცა Xcode-ის ბილდები მუშავდება. ჩაწერილი ნაბიჯის მონაცემები ინახება 90 დღის განმავლობაში. სიის პასუხი შეიცავს `availability`-ს: `available`, როცა ჩაწერილი ნაბიჯები არსებობს, მაშინაც კი, თუ ფილტრები არაფერს ემთხვევა; `processing`, როცა ბილდი ჯერ კიდევ მუშავდება და ჯერ არ აქვს ნაბიჯები; ან `unavailable`, როცა ნაბიჯები არ ჩაწერილა ან ამოიწურა.

ეს ინსტრუმენტები თანდათანობით იწერება და აბრუნებენ მონაცემებს მხოლოდ იმ პროექტებისთვის, სადაც ისინი ჩართულია; სხვა პროექტებისთვის ისინი აბრუნებენ შეცდომას ცარიელი შედეგის ნაცვლად. ტიპი ხელმისაწვდომია მხოლოდ იმ პროექტებისთვის, რომლებიც იყენებენ შესაბამის ბილდის ინსტრუმენტთა ნაკრებს. ინსტრუმენტები იღებენ შეზღუდულ `start_at`/`end_at` ფილტრებს, `environment` (`any`, `ci` ან `local`) და ზუსტ `branch`. `list_build_entities` იღებს `q`-ს; `list_build_entity_history` მხარდაჭერს გაუმჭვირვალე `after`/`before` კურსორებს. უცნობი დროის ან კეშის დაკვირვებები რჩება მიუწვდომლად, ნულის ან გამოტოვების ნაცვლად. ისტორია ეხება ჩაწერილ მშობელს და ნატიურ შესრულებას დეტალური შესწავლისთვის არსებული გაშვების ინსტრუმენტების გამოყენებით.

`get_build_entity` მეტრიკები მოიცავს `duration_samples`-ს, დაკვირვებების რაოდენობას ჩაწერილი დროით: ნამდვილი ნულოვანი ხანგრძლივობები ითვლება, გამოტოვებული დრო — არა. ეს რაოდენობა შეიძლება იყოს დაკვირვებების რაოდენობაზე ნაკლები; მიუწვდომელი ხანგრძლივობის სტატისტიკა რჩება null-ად.

Xcode-ის მოდულების ხანგრძლივობები მოდის ბილდის ჟურნალებში გაზომილი სამიზნე კომპილაციებიდან. მოდულის კეშის ამოხსნები და სამიზნეები კომპილაციის გარეშე არ უმატებენ ხანგრძლივობის ნიმუშებს. კომპილაციის დაკვირვებები ეხმიანება Xcode-ის ბილდს; კეშის მოვლენები ეხმიანება გენერაციის ან კეშის ბრძანებას.

Bazel-ის ქმედებები იდენტიფიცირდება სამიზნის ლეიბლით, მნემონიკით და კონფიგურირებული ძირითადი გამომავალით, რაც ინარჩუნებს ცალკეულ ქმედებებსა და კონფიგურაციებს განცალკევებულად, შეყვანაზე დამოკიდებული კეშის დაიჯესტების გარეშე. ისტორია იწერს BEP-ით მოხსენებულ შესრულებებს, არა კეშის ძიებებს ან ტრეისის პროფილის ფაზებს. სრული შესრულების დაფარვა მოითხოვს `--build_event_publish_all_actions`-ს; არტიფაქტების მიწოდება საუკეთესო ძალისხმევით ხდება, ამიტომ გამოტოვებული დაკვირვებები არ არის იმის მტკიცებულება, რომ სამუშაო არ შესრულებულა. უფრო ძველი Kura-ს პაკეტები სტაბილური იდენტობის ან შესრულების დაწყების გარეშე რჩება მიღებულად, მაგრამ არაინდექსირებულად. დასრულების დროის გაზომვების არარსებობა რჩება მიუწვდომლად და ნამდვილი ნულოვანი ხანგრძლივობები ითვლება.

Mix-ის მოდულების ხანგრძლივობები ზომავენ შემცველი ფაილის კომპილაციას, არა დამოუკიდებლად გაზომილ მოდულის სამუშაოს. Once-ის ქმედებები იყენებენ გამოცხადებულ სამიზნე/შესაძლებლობა/ინდექსის სლოტებს, როდესაც კლიენტმა მოახსენა სამიზნეების ასოციაციები; მხოლოდ დიაგნოსტიკური ლეიბლები არ არის სტაბილური იდენტობები. არსებული კლიენტები და გაშვების დონის ინსტრუმენტები რჩება მხარდაჭერილი უცვლელად.

ანალიტიკის წაკითხვებს აქვს შეზღუდული მეხსიერება და შესრულების დრო. თუ მოთხოვნა აღემატება ამ ლიმიტებს, ინსტრუმენტი აბრუნებს შეცდომას ცარიელი შედეგის გამოგონების ნაცვლად.

ახალი დაკვირვებები ინდექსირდება განლაგების შემდეგ; ეს ფუნქცია არ ავსებს უკვე არსებულ გაშვების ტელემეტრიას. იდენტობის მეტამონაცემები ინარჩუნებს სიცოცხლეს ინდივიდუალურ დაკვირვებებზე მეტხანს <.localized_link href="/guides/server/data-retention">მონაცემთა შენახვის პოლიტიკის</.localized_link> ფარგლებში.

| `test_run.failed` | ლოკალური ან უწყვეტი ინტეგრაციის ტესტების გაშვება სრულდება შეცდომით, მათ შორის გაერთიანებული შარდირებული გაშვება ან მიტოვებული გაშვება. | `account_handle`, `project_handle` |

გამოწერისთვის კლიენტი იძახებს `events/subscribe` მოვლენის სახელით, ზემოთ ჩამოთვლილი `arguments`-ით და `webhook` მიწოდებით, რომელიც შეიცავს `https://` callback URL-ს და `whsec_` ხელმოწერის საიდუმლოს. პროექტის მოვლენები მოითხოვს ანგარიშის წევრობას და შესაბამისი ტესტის ან აგების მონაცემებზე წვდომას; runner-ის სამუშაოს მოვლენები მოითხოვს ანგარიშის წევრობას და runner-ზე წვდომას. გამოყენებულმა [`auth.md`](https://workos.com/auth-md) წვდომის ტოკენებმა, ანგარიშის ტოკენებმა და ბრაუზერის ავტორიზაციის გრანტებმა შეიძლება შექმნან გამოწერები; მიწოდება წყდება, როდესაც შესაბამისი სერთიფიკატი აღარ არის აქტიური. თითოეულ მომხმარებელს შეუძლია ჰქონდეს მაქსიმუმ 25 აქტიური გამოწერა. Tuist აგზავნის ვერიფიკაციის გამოწვევას callback-ზე გამოწერის შენახვამდე. callback-მა უნდა დააბრუნოს ობიექტი, რომელიც შეიცავს იგივე `challenge` მნიშვნელობას. გამოწერა ნაგულისხმევად შვიდი დღე ძალაშია, შეიძლება განახლდეს ხელახლა გამოწერით და წყდება მიწოდება, როდესაც მომხმარებლის წვდომა ან სერთიფიკატი იხსნება. არასავალდებულო `ttlMs` შეზღუდულია ერთ საათსა და 30 დღეს შორის. Tuist ცდის ვადაგასული callback-ის გამეორებას და აუქმებს გამოწერას მინიმუმ სამი თანმიმდევრული ვადაგასულების შემდეგ, რომლებიც ხუთ წუთს ფარავს; გამოიწერეთ ხელახლა callback-ის აღდგენის შემდეგ.

როდესაც მოვლენა ხდება, Tuist აგზავნის მის რესურსის იდენტიფიკატორს და დაფის URL-ს callback-ზე. აგების და ტესტების გაშვების შეცდომები ასევე შეიცავს `is_ci`-ს და `git_branch`-ს, რათა კლიენტებმა შეძლონ ლოკალური შეცდომების იგნორირება ან ფილტრაცია ტოტის მიხედვით. აგების მოვლენები შეიცავს `build_system`-ს; runner-ის სამუშაოს მოვლენები შეიცავს როგორც `workflow_job_id`-ს, ისე `workflow_run_id`-ს. მოთხოვნა შეიცავს გამოწერის იდენტიფიკატორს და [Standard Webhooks](https://www.standardwebhooks.com/) ხელმოწერის ჰედერებს, რათა კლიენტმა შეძლოს მისი წყაროს ვერიფიკაცია. Tuist ცდის შეუძლებელი მიწოდებების გამეორებას, ამიტომ კლიენტებმა უნდა გამოიყენონ სტაბილური `eventId` დუბლიკატების გასაფილტრად. payload არ შეიცავს ტესტების სახელებს, ჟურნალებს და შეცდომის შეტყობინებებს; კლიენტმა შეიძლება მიიღოს ეს დეტალები ზემოთ ჩამოთვლილი ინსტრუმენტების მეშვეობით და გადაწყვიტოს, შეატყობინოს თუ არა გუნდს ან დაიწყოს დებაგინგი. კლიენტებმა შეიძლება შეაჩერონ მიწოდება `events/unsubscribe`-ით.

#### Gradle ინტეგრაციის მოთხოვნის ფუნქციები

`integrate_gradle_project` მოთხოვნა და `get_gradle_integration_guide` ინსტრუმენტი აღწერს სრულ დაყენების სამუშაო ნაკადს. ინსტრუმენტი ასევე მოხსენიებულია სერვერის ინიციალიზაციის ინსტრუქციებში, რაც მას აღმოჩენადს ხდის აგენტებისთვის, რომლებიც არ ჩამოთვლიან მოთხოვნებს.

| ფუნქცია | რას აკონფიგურირებს აგენტი |
|---------|---------------------------|
| `remote_cache` | ააქტიურებს Gradle-ის აგების ქეშს, აკონფიგურირებს Tuist-ის დაშორებული ქეშის ატვირთვის პოლიტიკას და რეკომენდაციას აძლევს ატვირთვას მხოლოდ უწყვეტი ინტეგრაციის runner-ებიდან ლოკალური მხოლოდ-წაკითხვის გამოყენებით. |
| `build_insights` | აყენებს Tuist Gradle პლაგინს და აკონფიგურირებს აგების ანალიტიკის ატვირთვის ქცევას საჭიროების შემთხვევაში. |
| `test_insights` | აყენებს Tuist Gradle პლაგინს, რათა Gradle `Test` ამოცანის შედეგები ავტომატურად აიტვირთოს. |
| `flaky_tests` | გეხმარებათ არასტაბილური ტესტების აღმოჩენის დაყენებაში, Gradle Test Retry პლაგინის არასავალდებულო გამოყენებაში და ტესტების კარანტინის კონფიგურაციაში. |
| `test_sharding` | ამატებს უწყვეტი ინტეგრაციის სამუშაო ნაკადს `tuistPrepareTestShards`-ისთვის, შარდების მატრიცის გენერაციას და `TUIST_SHARD_INDEX`-ზე დაფუძნებულ ტესტების შესრულებას. |

როდესაც `features` გამოტოვებულია, მოთხოვნა სთხოვს აგენტს გაარკვიოს, რომელი ინტეგრაციები სურს მომხმარებელს ან გამოიტანოს უმცირესი სასარგებლო ნაკრები მოთხოვნიდან Gradle პროექტის რედაქტირებამდე.

#### Xcode ინტეგრაციის მოთხოვნის ფუნქციები

`integrate_xcode_project` მოთხოვნა აღწერს ყველა Xcode ინტეგრაციას, რომელსაც Tuist მხარდაჭერს:

| ფუნქცია | რას აკონფიგურირებს აგენტი |
|---------|---------------------------|
| `xcode_cache` | აკონფიგურირებს `tuist setup cache`-ს, გენერირებული პროექტის ქეშის პარამეტრებს, ხელით Xcode ქეშის აგების პარამეტრებს და ატვირთვის პოლიტიკას, შეზღუდულს უწყვეტი ინტეგრაციის runner-ებით. |
| `build_insights` | აკონფიგურირებს `tuist inspect build`-ს, `tuist xcodebuild`-ს, `-resultBundlePath`-ს და არასავალდებულო მანქანის მეტრიკებს `tuist setup insights`-ის მეშვეობით. |
| `test_insights` | აკონფიგურირებს `tuist inspect test`-ს, სქემის ტესტის post-actions-ებს და შედეგის ბანდლის გენერაციას უწყვეტი ინტეგრაციის ტესტების გაშვებისთვის. |
| `test_sharding` | ამატებს Xcode ან გენერირებული პროექტის შარდების დაგეგმვას და შარდების შესრულების სამუშაო ნაკადს `TUIST_SHARD_INDEX`-ით. |

როდესაც `features` გამოტოვებულია, მოთხოვნა სთხოვს აგენტს გაარკვიოს, რომელი ინტეგრაციები სურს მომხმარებელს ან გამოიტანოს უმცირესი სასარგებლო ნაკრები მოთხოვნიდან Xcode პროექტის რედაქტირებამდე.
