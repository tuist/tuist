# Model Context Protocol

[Model Context Protocol (MCP)](https://modelcontextprotocol.io/docs/getting-started/intro) არის ღია სტანდარტი, რომელიც საშუალებას აძლევს ხელოვნური ინტელექტის აგენტებს ურთიერთქმედება გარე სერვისებთან და მონაცემთა წყაროებთან. ის უზრუნველყოფს ისეთი აპლიკაციების, როგორიცაა [Claude](https://claude.ai/), [Claude Code](https://docs.anthropic.com/en/docs/claude-code), [Codex](https://developers.openai.com/codex/), და რედაქტორების, როგორიცაა [Zed](https://zed.dev), [Cursor](https://www.cursor.com) ან [Visual Studio Code](https://code.visualstudio.com), თავსებადობას Tuist-თან.

Tuist განათავსებს Model Context Protocol-ის სერვერულ ბოლოწერტილს მისამართზე `https://tuist.dev/mcp`. თქვენი კლიენტის მასთან დაკავშირებით, აგენტებს შეუძლიათ მიიღონ წვდომა თქვენს Tuist პროექტის მონაცემებზე, მათ შორის ტესტების ინსაიტებზე, არასტაბილური ტესტების ანალიზზე და სხვა. უმეტესი ინსტრუმენტი კითხულობს Tuist-ის მონაცემებს, რომლებსაც ავტორიზებული მომხმარებელი უკვე ხედავს დაშბორდზე. ყოველი ინსტრუმენტი აცხადებს ანოტაციებს, რომლებიც მიუთითებს, არის თუ არა ის მხოლოდ წაკითხვისთვის, შეუძლია თუ არა გამოიწვიოს ძნელად შექცევადი ცვლილება (`destructiveHint`), და შეუძლია თუ არა გასვლა Tuist-ის ფარგლებს გარეთ (`openWorldHint`). ინსტრუმენტები, რომლებიც ცვლიან მდგომარეობას, თითოეული შემოიფარგლება მომხმარებლის ნებართვებით ანგარიშზე ან პროექტზე, არის:

- **ორგანიზაციები და წევრები**: `create_organization`, `add_organization_member` (ამატებს არსებულ მომხმარებელს ან ცვლის წევრის როლს), `invite_organization_member` (აგზავნის მოწვევას ელფოსტაზე ნებისმიერ მისამართზე) და `cancel_organization_invitation`.
- **პროექტები**: `create_project`, `start_project_logo_upload` და `complete_project_logo_upload` (ცვლის ლოგოს), `connect_project_repository` და `disconnect_project_repository` (GitHub რეპოზიტორიის ბმულები).
- **ტესტები**: `update_test_case` (აჩუმებს, ტოვებს, ხელახლა ააქტიურებს ან მონიშნავს სატესტო შემთხვევას როგორც არასტაბილურს; ცვლილება შეიძლება მიაღწიოს ანგარიშის webhook ბოლოწერტილებს).
- **შეტყობინებების წესები**: `create_notification_rule`, `update_notification_rule` და `delete_notification_rule`.
- **უწყვეტი ინტეგრაციის გამშვებები**: `create_runner_profile`, `update_runner_profile` (იმ სამუშაოების შევიწროება, რომლებიც ინახავენ ქეშის ტომებს, ასუფთავებს მოლოდინში მყოფ შენახვებს), `delete_runner_profile` და `delete_runner_volume` (შლის ტომის შენახულ შინაარსს).
- **სენდბოქსები**: `create_sandbox`, `pause_sandbox`, `resume_sandbox`, `archive_sandbox` და `delete_sandbox` (შლის მის დისკებს).
- **უკუკავშირი**: `report_feedback` (აგზავნის ანგარიშს ინსტრუმენტის ან მოთხოვნის შესახებ Tuist-ის გუნდს; მხოლოდ tuist.dev-ზე).
- **ორგანიზაციის AI**: `save_organization_ai_model`, `remove_organization_ai_model`, `set_organization_ai_default_model`, `save_organization_ai_task_route`, `remove_organization_ai_task_route` და `remove_organization_ai_provider` (შლის პროვაიდერის გასაღებს და მოდელებს, და წყვეტს Claude ორგანიზაციის კავშირს Anthropic-ზე).
- **აგენტის ინტეგრაციები**: `connect_amp_workspace` (ანიჭებს სამუშაო სივრცის orbs CI წვდომას ანგარიშზე), `disconnect_amp_workspace` და `connect_claude_environment` (საშუალებას აძლევს Claude Managed Agents გარემოს ჩაატაროს სესიები Tuist სენდბოქსებში).

`add_organization_member`, `cancel_organization_invitation`, `complete_project_logo_upload`, `disconnect_project_repository`, `update_test_case`, `update_notification_rule`, `delete_notification_rule`, `update_runner_profile`, `delete_runner_profile`, `delete_runner_volume`, `delete_sandbox`, `disconnect_amp_workspace`, `remove_organization_ai_provider`, `remove_organization_ai_model` და `remove_organization_ai_task_route` აცხადებენ `destructiveHint: true`-ს, რადგან ისინი ცვლიან ან აშორებენ არსებულ მდგომარეობას. `invite_organization_member`, `update_test_case`, `connect_claude_environment`, `remove_organization_ai_provider` და `report_feedback` აცხადებენ `openWorldHint: true`-ს, რადგან ისინი აგზავნიან ელფოსტას, ამცნობენ გარე webhook ბოლოწერტილებს, უკავშირდებიან Anthropic-ს ან აგზავნიან ანგარიშს Tuist-ის გუნდს.

პირადი Claude და ChatGPT გამოწერები დაკავშირებულია მხოლოდ დაშბორდის AI პარამეტრებში, ამიტომ გამოწერის ტოკენები და შესვლები არასდროს გადის Model Context Protocol კლიენტის მეშვეობით. ანგარიშის მორგების ინსტრუმენტები მოითხოვს მომხმარებლის ავტორიზაციას. ისინი არ არის ხელმისაწვდომი პროექტის ტოკენებისთვის ან ჩვეულებრივი ანგარიშის ტოკენებისთვის. როდესაც მომხმარებელი ანიჭებს ნებართვას კლიენტს ბრაუზერში ან ითხოვს `auth.md` რეგისტრაციას, Tuist აკავშირებს ამ სერთიფიკატს მომხმარებელთან მხოლოდ Model Context Protocol ბოლოწერტილზე, რათა მორგების ინსტრუმენტებმა შეძლონ მოთხოვნილი სამუშაო პროცესის დასრულება.

Tuist ახორციელებს [2026-07-28 პროტოკოლს](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http). მოთხოვნები არის უსესიო: კლიენტები აგზავნიან თავიანთ პროტოკოლის მეტამონაცემებს ყოველ მოთხოვნასთან ერთად და შეუძლიათ პირდაპირ გამოიძახონ ინსტრუმენტები ინიციალიზაციის გარეშე. `server/discover` აბრუნებს სერვერის იდენტობას, შესაძლებლობებს, მხარდაჭერილ ვერსიებს და ინსტრუქციებს. არ არსებობს სესიის იდენტიფიკატორები ან დამოუკიდებელი მოვლენების ნაკადები. კლიენტები, რომლებიც იყენებენ 2025-06-18 ან 2025-03-26 ინიციალიზაციის ნაკადს, კვლავ მხარდაჭერილია; ისინიც მუშაობენ სერვერის სესიების გარეშე.

## Model Context Protocol უნარების წინააღმდეგ

Model Context Protocol ინსტრუმენტებს და <.localized_link href="/guides/features/agentic-coding/skills">უნარებს</.localized_link> შეიძლება ჰქონდეთ გადახურვა შესრულებულ ფუნქციებში. ამჟამინდელი გადახურვის გათვალისწინებით, აირჩიეთ ერთი მიდგომა თითოეული სამუშაო პროცესისთვის და გამოიყენეთ ის თანმიმდევრულად, ნაცვლად ორივეს ერთ ნაკადში შერევისა.

კლიენტებისთვის, რომლებიც მხარს უჭერენ პლაგინების ინსტალაციას, გამოიყენეთ <.localized_link href="/guides/features/agentic-coding/plugins">Tuist პლაგინები</.localized_link> ორივეს ერთად ინსტალაციისთვის.

## კონფიგურაცია

დაამატეთ `https://tuist.dev/mcp` როგორც დისტანციური Model Context Protocol სერვერი თქვენს კლიენტში. სერვერის ინიციალიზაციის ინსტრუქციები და საჯარო სერვერის ბარათი აღწერს OAuth 2.0-ს დინამიური კლიენტის რეგისტრაციით და სტანდარტული ბრაუზერის ავტორიზაციის ნაკადით პირდაპირ, აგენტებისგან გარე ავთენტიკაციის დოკუმენტების მოთხოვნის ან მიყოლების გარეშე. ეს სერვერის მასშტაბის ინსტრუქციები ინარჩუნებს სამუშაო პროცესის მითითებებს ზოგადს: ინსტრუმენტის ავთენტიკაცია არ ავთენტიკაციებს ადგილობრივ ბრძანების ხაზის ინსტრუმენტებს ან აგების სისტემის ინტეგრაციებს, და აგენტებმა უნდა გადაამოწმონ მოთხოვნილი ცვლილებები შესაბამისი Tuist ინსტრუმენტების მეშვეობით. აგების სისტემისთვის სპეციფიკური მორგება და ავთენტიკაციის შემოწმებები დოკუმენტირებულია ინტეგრაციის სახელმძღვანელოებში და მოთხოვნებში. Tuist კვლავ აცხადებს როგორც [Open Authorization](https://oauth.net/2/) აღმოჩენის მეტამონაცემებს, ასევე მიმდინარე [auth.md პროტოკოლს](https://workos.com/auth-md) მისამართზე `https://tuist.dev/auth.md` ცალ-ცალკე.

თუ თქვენი ერთ-ერთი ორგანიზაცია აიძულებს ერთიანი შესვლის (SSO) გამოყენებას, კლიენტის ავტორიზაცია ბრაუზერში მოითხოვს სესიას, რომელიც შესულია ამ ორგანიზაციის მეშვეობით, და Tuist საჭიროების შემთხვევაში ჯერ პროვაიდერზე გაგზავნით. იხილეთ <.localized_link href="/guides/integrations/authentication/sso#choose-an-enrollment-policy">ერთიანი შესვლა</.localized_link>.

ბოლოწერტილი იღებს უსესიო `2026-07-28` Model Context Protocol მოთხოვნის ციკლს, `server/discover`-ის ჩათვლით, ძველ სესიაზე დაფუძნებულ ციკლთან ერთად. არსებულმა კლიენტებმა შეიძლება გააგრძელონ თავიანთი მიმდინარე კავშირის მეთოდის გამოყენება.

კლიენტებს, რომლებიც მხარს უჭერენ Model Context Protocol მოვლენებს, შეუძლიათ გამოიწერონ პროექტის მოვლენები. იხილეთ [მოვლენები](#events) ხელმისაწვდომი მოვლენებისა და მიწოდების მოთხოვნებისთვის.

კლიენტებს, რომლებიც უკვე მხარს უჭერენ დისტანციურ ბრაუზერის ავთენტიკაციას, შეუძლიათ გააგრძელონ ავთენტიკაცია ბრაუზერში. კლიენტებს და აგენტებს, რომლებიც მხარს უჭერენ `auth.md`-ს, შეუძლიათ დარეგისტრირდნენ ანონიმურად, წარმოადგინონ სანდო პროვაიდერის იდენტობის დადასტურება ან დაიწყონ სერვისით ავთენტიკირებული ელფოსტის მოთხოვნა. რეგისტრაცია აბრუნებს Tuist-ით ხელმოწერილ იდენტობის დადასტურებას, რომელსაც აგენტი ცვლის სტანდარტულ ტოკენის ბოლოწერტილზე ერთსაათიანი წვდომის ტოკენისთვის. Tuist აქვეყნებს თავის საჯარო ხელმოწერის გასაღებს და მხარს უჭერს სტანდარტულ ტოკენის გაუქმებას და პროვაიდერის უსაფრთხოების მოვლენების მიწოდებას.

არაავთენტიკირებულმა აგენტმა უნდა წაიკითხოს Model Context Protocol ბოლოწერტილის მიერ დაბრუნებული `WWW-Authenticate` ჰედერი, მოიძიოს დაცული რესურსის მეტამონაცემები, მოიძიოს ავტორიზაციის სერვერის მეტამონაცემები და მიჰყვეს მის `agent_auth.skill` URL-ს. Tuist ასევე აბრუნებს იგივე ლოკალურ `auth_md` URL-ს არაავტორიზებული პასუხის სხეულში, რათა ენის მოდელზე დაფუძნებულმა კლიენტებმა შეძლონ ნაკადის აღმოჩენა ნატიური კლიენტის ინტეგრაციაზე დამოკიდებულების გარეშე. განლაგების ლოკალური დოკუმენტია ჭეშმარიტების ერთადერთი წყარო ბოლოწერტილების სახელების, მოთხოვნის სხეულების, მოთხოვნის გამოკითხვისა და დადასტურების გაცვლისთვის.

სანამ აგენტი ელფოსტის მოთხოვნას დაიწყებს, მან მომხმარებელს უნდა სთხოვოს Tuist ანგარიშის ელფოსტის მისამართის დადასტურება. მან არ უნდა გამოიტანოს ეს მისამართი პროვაიდერის პროფილიდან, Git კონფიგურაციიდან, გარემოს ცვლადიდან ან სესიის მეტამონაცემებიდან.

ბოლოწერტილი იყენებს `mcp` სკოპების ჯგუფს. ანონიმურმა წინასწარ მოთხოვნის კრედენციალს შეუძლია აღმოაჩინოს შესაძლებლობები და წაიკითხოს საჯარო ინტეგრაციის მითითებები, მაგრამ ის არ განიხილება როგორც შესული მომხმარებელი. ბრაუზერის ავტორიზაციის ან მოთხოვნის შემდეგ, კრედენციალი არის მომხმარებელზე ორიენტირებული და თითოეული ინსტრუმენტი ახორციელებს იგივე ავტორიზაციის შემოწმებებს, რასაც დაფა. დეტალებისთვის იხილეთ <.localized_link href="/guides/server/authentication#scope-groups">სკოპების ჯგუფების დოკუმენტაცია</.localized_link>.

ინსტრუმენტები გადაჰყავთ იმ პროექტებზე, რომელთა წაკითხვაც ავთენტიკირებულ მომხმარებელს უკვე შეუძლია. Xcode-ისა და Gradle-ის აგების ინსტრუმენტები იღებენ აგების UUID-ს ან დაფის URL-ს. UUID-მ უნდა ამოიცნოს ზუსტად ერთი პროექტი; თუ ის რამდენიმე პროექტში ჩანს, ინსტრუმენტი აბრუნებს „ვერ მოიძებნა“-ს, ნაცვლად სხვა პროექტის ანგარიშის არჩევისა. პროექტზე ორიენტირებული დაფისა და API-ს წაკითხვები ხელმისაწვდომი რჩება. მოხსენებული აქტორის იდენტიფიკატორები არიან შეუმოწმებელი ლეიბლები, არა კრედენციალები ან დამატებითი წვდომის უფლებები.

აგების სიისა და დეტალების ინსტრუმენტები ავლენენ არასავალდებულო `tuist_version` მეტამონაცემებს: Tuist CLI-ს Xcode-ისა და Cargo-სთვის, Tuist Gradle პლაგინს Gradle-ისთვის და `tuist_ex` ბიბლიოთეკას Mix-ისთვის. Xcode ასევე ავლენს `tuist_generation_version`-ს თავის დაკავშირებული პროექტის გენერაციის მოვლენიდან, რომელიც შეიძლება განსხვავდებოდეს ატვირთვადი CLI-სგან. გამოტოვებული დაკვირვებები არის null, არა გამოტანილი სერვერიდან ან სხვა ანგარიშიდან. Bazel იყენებს თავის არსებულ `bazel_version`-ს; Struo გაშვების დეტალები ავლენენ `once_version`-ს. ეს ველები აღწერენ მოხსენებულ ვერსიებს, არა შემოწმებულ იდენტობას ან სადენის კონტრაქტის ვერსიებს. REST აგების ბოლოწერტილები ავლენენ იგივე მეტამონაცემებს. არსებული ინტეგრაციისა და ფლეიკი ტესტის უნარები არ არიან დამოკიდებული ვერსიის ველებზე და არ საჭიროებენ სამუშაო ნაკადის ცვლილებებს.

Tuist ოპერატორები, რომლებიც იკვლევენ მომხმარებლის ანგარიშს, აკეთებენ ამას Tuist-ის შიდა ოპერაციული ინსტრუმენტების მეშვეობით, რომელიც იწერს ყოველ ზარს; პირდაპირი კავშირი ამ ბოლოწერტილთან არ იძლევა წვდომას მომხმარებლის საკუთარი წევრობის ფარგლებს გარეთ.

### Pulse

Pulse ავლენს მხოლოდ წასაკითხ ინსტრუმენტებს ანგარიშის ოპერაციული მეტრიკების, ჟურნალების, ტრეისებისა და შეცდომებისთვის, რომლებიც ყველა მიმართულია `account_handle`-ით. პირველი სამი ასახავს Pulse გვერდებსა და მათ REST API-ს; დანარჩენი ხუთი საშუალებას აძლევს აგენტს პირდაპირ შეისწავლოს ტელემეტრია და არ აქვთ REST ეკვივალენტი:

| ინსტრუმენტი | მიზანი | REST ეკვივალენტი `/api/accounts/:account_handle/pulse` ქვეშ |
| --- | --- | --- |
| `query_pulse` | Pulse გვერდის ცხრილები | `GET /:signal` |
| `get_pulse_analytics` | Pulse გვერდის ვიჯეტები | `GET /:signal/analytics` |
| `get_pulse_error_issue` | ერთი შეცდომის საკითხი და მისი მოვლენები | `GET /errors/issues/:fingerprint` |
| `query_pulse_metrics` | მყისიერი ან დიაპაზონის PromQL | არ არის |
| `list_pulse_labels` | ლეიბლის სახელები, ან ერთი ლეიბლის მნიშვნელობები | არ არის |
| `search_pulse_logs` | ფილტრირებული ჟურნალის ჩანაწერები | არ არის |
| `search_pulse_traces` | ფილტრირებული სპენები | არ არის |
| `get_pulse_trace` | ერთი ტრეისის ყოველი სპენი | არ არის |

Pulse შეზღუდულია სერვერით კონფიგურირებული ორგანიზაციის მიმდინარე წევრებისთვის, მაშინაც კი, თუ ანგარიში ან პროექტი საჯაროა. ის მოითხოვს მომხმარებლის ავთენტიკაციას ან მომხმარებელთან დაკავშირებულ `mcp` კრედენციალს და ანგარიშის წაკითხვის ავტორიზაციას. პროექტის ტოკენები, ჩვეულებრივი ანგარიშის ტოკენები, ანონიმური რეგისტრაციები და ოპერატორის წვდომა ორგანიზაციის წევრობის გარეშე არ იძლევა Pulse-ის წვდომას. კრედენციალებს არ შეუძლიათ აირჩიონ სხვა ბექენდი ან ტელემეტრიის მომხმარებელი, და მხოლოდ სერვერით კონფიგურირებულ ანგარიშს აქვს Pulse ტელემეტრია, ამიტომ არცერთ ინსტრუმენტს არ შეუძლია წაიკითხოს სხვა ანგარიშის მონაცემები. ბრაუზერის აგენტები იღებენ ამ ინსტრუმენტებს მხოლოდ Pulse გვერდებზე, იმ გვერდის ანგარიშის სკოპის ფარგლებში.

REST მოითხოვს მომხმარებლის კრედენციალს. OAuth და `auth.md` მომხმარებლის ასოციაციები ხელმისაწვდომია მხოლოდ `/mcp` ბოლოწერტილზე; ანგარიშის კრედენციალი მიმდინარე მომხმარებლის გარეშე უარყოფილია, მიუხედავად დაკავშირებული ანგარიშის წევრობისა ან ხილვადობისა.

`query_pulse` იღებს `signal`-ს (`metrics`, `logs`, `traces`, ან `errors`), არასავალდებულო `query`-ს და `range`-ს (`15m`, `1h`, `6h`, ან `24h`, ნაგულისხმევი `1h`). მეტრიკები იღებენ PromQL გამოსახულებებს. ჟურნალები, ტრეისები და შეცდომები იღებენ ლიტერალურ, რეგისტრის მიმართ მგრძნობიარე ტექსტს, რომელიც ემთხვევა ჟურნალის სხეულებს, სპენების სახელებს და შეცდომის საკითხის სათაურებს; `*`, ნაგულისხმევი, ირჩევს ყველაფერს. ტრეისის სტრიქონები არის ინდივიდუალური სპენები. შეცდომის სტრიქონები არის საკითხები: მოვლენები დაჯგუფებული სერვისისა და თითის ანაბეჭდის მიხედვით, მათი მოვლენების რაოდენობით, დაზარალებული ანგარიშებით, პირველი და ბოლო გამოჩენა ფანჯარაში, და მათი უახლესი მოვლენის სათაური, დამნაშავე, დონე და პლატფორმა. ცხრილები იღებენ `search`-ს, `page`-ს (ნაგულისხმევი `1`), `page_size`-ს (`1`–`100`, ნაგულისხმევი `20`), `sort_by`-ს და `sort_order`-ს (`asc` ან `desc`). დალაგების სვეტები დამოკიდებულია სიგნალზე და ჩამოთვლილია ინსტრუმენტის სქემაში. ფილტრები მოიცავს `service`-ს და `level`-ს ჟურნალებისა და შეცდომებისთვის. ფილტრის ოპერატორები იყენებენ შესაბამის `_op` არგუმენტს (`eq`, `contains`, ან `not_contains`), ნაგულისხმევად ზუსტი ტოლობით.

დალაგების სვეტებია `name`/`value` მეტრიკებისთვის; `timestamp`/`service`/`level`/`message`/`trace_id` ჟურნალებისთვის; `timestamp`/`service`/`name`/`duration_ms`/`trace_id` ტრეისებისთვის; და `last_seen`/`first_seen`/`events`/`accounts`/`title`/`service`/`level` შეცდომებისთვის. დაფა განზრახ ავლენს ქვესიმრავლეს; API და ინსტრუმენტები იღებენ სრულ სიას თითოეული სიგნალისთვის.

ცხრილის პასუხები შეიცავს `rows`-ს, `series`-ს, `warnings`-ს და `meta`-ს. დაფურცვლის მეტამონაცემები მოიცავს `page`-ს, `page_size`-ს, `total_count`-ს, `total_pages`-ს, `has_next_page`-ს, `has_previous_page`-ს და `end_at`-ს. გადასცეთ დაბრუნებული ISO8601 `end_at` შემდგომ გვერდებთან ერთად, რათა შეინარჩუნოთ მოთხოვნის ფანჯარა. შედეგის ლიმიტის შეცდომები მოითხოვენ მოთხოვნის ან დროის დიაპაზონის შევიწროებას, არა პასუხის ცარიელ ცხრილად განხილვას.

ჟურნალები და ტრეისები ამოწმებენ მაქსიმუმ 100 უახლეს დამთხვევას ადგილობრივი დალაგებამდე, ხოლო შეცდომები — 100 უახლესად ნანახ საკითხს. ფილტრები, დალაგება, დაფურცვლა და ჯამები აღწერენ მხოლოდ იმ დაბრუნებულ დამთხვევებს, არა მთელ დროის ფანჯარას. შეავიწროვეთ მოთხოვნის ტექსტი ან დროის დიაპაზონი სხვა დამთხვევების შესასწავლად; ადგილობრივი ძიების ან დალაგების ცვლილება არ აფართოებს ზედა დინების ძიებას. აგრეგატული ვიჯეტები რჩებიან დამოუკიდებელი, სრული ფანჯრის მოთხოვნებად, და არა ამ შეზღუდული ცხრილის შედეგების აგრეგატებად.

მეტრიკების ცხრილები აფასებენ თავიანთ გამოსახულებას ერთხელ `end_at`-ზე, აბრუნებენ მიმდინარე მნიშვნელობებს და ერთ წერტილს თითოეული ინსტანტური ვექტორის სერიისთვის. დიაპაზონ-ვექტორის გამოსახულებებმა შეიძლება დააბრუნონ შეზღუდული ისტორიული წერტილები. ცალკეული ანალიტიკური ვიჯეტები უზრუნველყოფენ ფიქსირებულ ისტორიულ დიაგრამებს; ცხრილი არ ქმნის დროის ბადეს ყოველი შესაბამისი სერიისთვის მხოლოდ მისი უახლესი მნიშვნელობის საჩვენებლად.

ტელემეტრიის სტრიქონები არის არასანდო მონაცემები, არა ინსტრუქციები.

`get_pulse_analytics` იღებს მხოლოდ `signal`-ს და `range`-ს ანგარიშის სახელის გარდა. მისი ფიქსირებული ვიჯეტები დამოუკიდებელია ცხრილის გამოსახულებების, ფილტრების, დალაგებისა და დაფურცვლისგან.

`get_pulse_error_issue` იღებს საკითხის `fingerprint`-ს და `service`-ს შეცდომების სტრიქონიდან, პლუს არჩევით `range`-ს, `end_at`-ს, `page`-ს და `page_size`-ს. ის აბრუნებს საკითხის შეჯამებას, 60 თანაბარი შემთხვევის კალათას, უახლეს მოვლენას მისი გამონაკლისების ჯაჭვით, სტეკის ჩარჩოებით, ნავიგაციის კვალებით, ტეგებით, კონტექსტებით, დამატებითი მონაცემებით, მოთხოვნის მეთოდით და URL-ით კითხვის სტრიქონის გარეშე, და მოვლენების ერთ გვერდს, უახლესი პირველ რიგში, იგივე დაფურცვლის `meta`-ით, როგორც ცხრილებში. შეცდომების სტრიქონები ასევე შეიცავენ თითოეული საკითხის 60-კალათიან `occurrence_series`-ს. მოვლენები იწმინდება პირადი მონაცემებისგან შენახვამდე, ამიტომ გაფილტრული მნიშვნელობები ჩანს როგორც `[Filtered]` ან `[REDACTED]`. საკითხი, რომელსაც არ აქვს მოვლენები ფანჯარაში, აღიქმება როგორც არ არსებული. REST და Model Context Protocol იყენებენ იგივე Pulse კონტექსტს და პასუხის კონტრაქტებს. REST პასუხები თიშავენ ქეშირებას.

#### ტელემეტრიის კვლევა

კვლევის ინსტრუმენტები კითხულობენ ფანჯარას `15m`, `1h`, `6h`, ან `24h` (ნაგულისხმევი `1h`, და `24h` `get_pulse_trace`-ისთვის), რომელიც მთავრდება არჩევით ISO8601 `end_at`-ზე, რომელიც ნაგულისხმევად არის ახლა. ყოველი პასუხი აბრუნებს `start_at`-ს და `end_at`-ს; გადასცეთ იგივე `end_at` ხელახლა ფანჯრის შესანარჩუნებლად. ამ ინსტრუმენტებიდან არცერთი არ იღებს SQL-ს.

- `query_pulse_metrics` აფასებს `query`-ს, PromQL გამოსახულებას, `end_at`-ზე (`type: instant`, ნაგულისხმევი) ან ყოველ `step` წამში ფანჯრის განმავლობაში (`type: range`). ნაბიჯი ნაგულისხმევად არის და არ შეიძლება იყოს უფრო მცირე, ვიდრე ფანჯარა გაყოფილი 360-ზე, ამიტომ სერიას აქვს მაქსიმუმ 361 წერტილი. შედეგებს აქვს მაქსიმუმ 5,000 სერია. წერტილებია `[unix_seconds, value]`, ხოლო `NaN` და უსასრულო მნიშვნელობები არის სტრიქონები. ინსტანტური მოთხოვნები უარყოფენ `range`-ს და `step`-ს.
- `list_pulse_labels` იღებს `signal`-ს. `label`-ის გარეშე, ის ჩამოთვლის ლეიბლების სახელებს; `label`-ით, ის ჩამოთვლის იმ ლეიბლის მნიშვნელობებს. მეტრიკებისთვის, `__name__` ჩამოთვლის მეტრიკების სახელებს, და ნებისმიერი სხვა ლეიბლის მნიშვნელობები მოითხოვენ `match`-ს, სერიის სელექტორს, როგორიცაა `up`. ჟურნალების და ტრეისების ლეიბლების მნიშვნელობები იღებენ `filters`-ს; ტრეისების ლეიბლების სახელები მოდის ტრეისის სქემიდან და არა. ჟურნალების და ტრეისების მნიშვნელობები შეიცავენ მათ ჩანაწერთა რაოდენობას ფანჯარაში, ყველაზე ხშირი პირველ რიგში, ამიტომ ისინი ასევე ემსახურებიან როგორც დაშლა, მაგალითად, შეცდომები სერვისის მიხედვით. `search` ტოვებს მხოლოდ სახელებს ან მნიშვნელობებს, რომლებიც შეიცავენ ლიტერალურ ტექსტს, და `limit` იღებს `1`–`1000` (ნაგულისხმევი `100`). ჟურნალების ლეიბლის სახელის აღმოჩენა ამოწმებს მაქსიმუმ 1,000 განსხვავებულ ატრიბუტთა ნაკრებს თითოეული ტიპისთვის და ჩამოთვლის მხოლოდ იმ გასაღებებს, რომლებსაც ფილტრები იღებენ.
- `search_pulse_logs` აბრუნებს მაქსიმუმ `limit` ჩანაწერს (`1`–`100`, ნაგულისხმევი `50`), `newest` ან `oldest` პირველ რიგში, რომელთა სხეული შეიცავს `text`-ს და რომლებიც ემთხვევა ყოველ ფილტრს. თითოეული ჩანაწერი შეიცავს მის `severity_text`-ს, `body`-ს, `trace_id`-ს, `span_id`-ს, `scope_name`-ს და მის გაერთიანებულ რესურსს და ჟურნალის `attributes`-ს. `span_id` და `scope_name` არის `null` Kubernetes-იდან შეგროვებული ჟურნალებისთვის, რომელსაც მხოლოდ OTLP ჟურნალის გამგზავნები აყენებენ.
- `search_pulse_traces` აბრუნებს მაქსიმუმ `limit` სპანს, `newest`, `oldest`, ან `slowest` პირველ რიგში, რომლებიც ემთხვევა ყოველ ფილტრს, არჩევით `min_duration_ms`-ს და `max_duration_ms`-ს, და `root_only`-ს.
- `get_pulse_trace` აბრუნებს `trace_id`-ის სპანებს, რომლებიც იწყება ფანჯარაში, უძველესი პირველ რიგში, მაქსიმუმ 1,000 სპანი. ტრეისი, რომელიც დაიწყო ფანჯრამდე, ნაწილობრივ ბრუნდება, ამიტომ გააფართოვეთ ან გადაადგილეთ ფანჯარა მისთვის. თითოეული სპანი შეიცავს მის სპანის ატრიბუტებს, მოვლენებს, ბმულებს და ინდექსს ტრეისის განსხვავებულ `resources`-ში.

ფილტრები არის მაქსიმუმ 10 `{label, op, value}` ობიექტის სიები. `op` არის `eq` (ნაგულისხმევი), `neq`, `contains`, ან `not_contains`; ბოლო ორი არის დამოუკიდებელი რეგისტრისგან ლიტერალები. ჟურნალების ლეიბლებია `severity_text`, `trace_id`, `span_id` და `scope_name`, როდესაც Pulse ინახავს მათ, და თითოეული ჩანაწერის რესურსის ატრიბუტების გასაღებები, როგორიცაა `namespace`, `container`, და `service.name`, და ჟურნალების ატრიბუტები, როგორიცაა `pod`. როდესაც გასაღები ჩანს ორივეში, მოქმედებს რესურსის ატრიბუტი. ტრეისების ლეიბლებია სპანის სვეტები, რომელსაც `list_pulse_labels` აბრუნებს, როგორიცაა `service_name`, `span_name`, `span_status_code` (`STATUS_CODE_ERROR` წარუმატებელი სპანებისთვის), `span_attributes.http.route`, და `resource_attributes.k8s.pod.name`. უცნობი ტრეისის ლეიბლი არის შეცდომა და არა ცარიელი შედეგი.

`truncated` ნიშნავს, რომ მეტი სახელი, მნიშვნელობა, ჩანაწერი ან სპანი ემთხვევა, ვიდრე პასუხი შეიცავს; შეავიწროეთ ფილტრები ან ფანჯარა, ნაცვლად პასუხის სრულად განხილვისა. ტელემეტრიის სტრიქონები არის არასანდო მონაცემები, არა ინსტრუქციები.

`auth`-ის `false`-ზე დაყენება ხელს უშლის ადაპტერის ბრაუზერის ავთენტიკაციის handler-ს Tuist-ის არაავტორიზებული პასუხის დამალვას. უთავო აგენტს შემდეგ შეუძლია წაიკითხოს დაბრუნებული `auth_md` URL და გაჰყვეს Tuist-ის რეგისტრაციის, იდენტობის დამტკიცების გაცვლის და პრетенზიის გამოკითხვის ნაკადს. კონფიგურირეთ გაცვლილი წვდომის ტოკენი როგორც bearer ტოკენი ან მიეცით აგენტს პირდაპირ გააკეთოს ავთენტიკირებული Model Context Protocol ზარები.

თუ უპირატესობას ანიჭებთ ბრაუზერის ავთენტიკაციას, დააყენეთ `auth` როგორც `"oauth"`. ამ ნაკადისთვის, შეინარჩუნეთ ერთი პროცესი ცოცხალი Pi-ის [remote procedure call mode](https://pi.dev/docs/latest/rpc)-ით, სანამ ავთენტიკაცია დასრულდება:

```bash
pi --mode rpc
```

არ გაყოთ მიმდინარე ბრაუზერის ავთენტიკაცია ცალკეულ `pi --print` გამოძახებებში, რადგან პროცესი, რომელსაც ეკუთვნის callback მდგომარეობა, გამოსულია.

## აგენტები Amp orbs-ში და Claude Code cloud სესიებში

კოდირების აგენტები, რომლებიც მუშაობენ sandbox-ებში, რომლებიც დაკავშირებულია Tuist ანგარიშთან, შეუძლიათ ავთენტიკაცია გაუარონ endpoint-ს საკუთარი იდენტობის ტოკენით, ბრაუზერის ან შენახული Tuist რწმუნების გარეშე:

- **Amp orbs** Amp სამუშაო სივრცის ან პროექტისთვის, რომელიც ანგარიშმა დააკავშირა **Settings → Integrations → Amp**-ის ქვეშ, აგზავნის orb-ის ID ტოკენს. Amp-ში დააყენეთ სერვერის `Authorization` ჰედერი როგორც `Bearer ${amp:id-token}`. Amp აყალიბებს ტოკენს სერვერის URL-ის წარმოშობისთვის, ამიტომ URL უნდა იყოს ამ Tuist ინსტანციის საკუთარი მისამართი და აახლებს მას ვადის გასვლამდე. სხვა წარმოშობისთვის გამოშვებული ტოკენები უარყოფილია.
- **Claude Code cloud sessions** დაკავშირებული Claude Code გარემოსი აგზავნის სესიის ტოკენს, რომელსაც Tuist გადასცემს მათ როგორც `TUIST_OIDC_TOKEN`. დააყენეთ ჰედერი როგორც `Bearer ${TUIST_OIDC_TOKEN}`.

Tuist-ის Linux sandbox-ები არ ამატებენ სერვერს თქვენთვის: ისინი შეიცავენ Tuist CLI-ს, რომელიც შედის სისტემაში იგივე იდენტობით, და უნარს, რომელიც ეუბნება აგენტს, როდის შეამოწმოს შედეგები პროექტის ისტორიის მიმართ. აგენტებს MCP ხელსაწყოების მისაცემად, დაამატეთ სერვერი თქვენს Amp ან Claude Code პარამეტრებში, ან პროექტის `.mcp.json`-ში, ზემოთ მოცემული ჰედერით.

ეს ტოკენები იძლევა მხოლოდ წაკითხვის უფლებას დაკავშირებული ანგარიშის ყველა პროექტზე: ისინი შეიცავენ `mcp` ჯგუფის წაკითხვის სფეროებს და არაფერს, რაც ქმნის, ცვლის ან შლის მონაცემებს, როგორიცაა ტესტების ჩუმად დატოვება ან გამოტოვება. სამუშაო სივრცის ან გარემოს გათიშვა წყვეტს წვდომას შემდეგ მოთხოვნაზე და წვდომა არასდროს ძლებს ტოკენზე მეტხანს. Amp სამუშაო სივრცე, რომელიც დაკავშირებულია რამდენიმე Tuist ანგარიშთან, უარყოფილია, რადგან მის ტოკენს ერთი არ უთითია. როცა კავშირი არ არსებობს, არაავტორიზებული პასუხის `error_description` ამბობს ამას.

ეს მხოლოდ წაკითხვის წვდომა ვრცელდება მხოლოდ Model Context Protocol endpoint-ზე. ბრძანების ხაზის ხელსაწყო და build-system ინტეგრაციები იმავე sandbox-ში მაინც ცვლიან ტოკენს კავშირის CI წვდომისთვის.

## WebMCP

ბრაუზერებში, რომლებიც მხარს უჭერენ [WebMCP](https://webmachinelearning.github.io/webmcp)-ს, Tuist-ის გვერდები რეგისტრირებენ ხელსაწყოებს `document.modelContext`-ით, ასე რომ ბრაუზერში ჩაშენებულ აგენტებს შეუძლიათ გამოიძახონ ისინი დამატებითი კონფიგურაციის გარეშე. ზარები მუშაობენ Tuist სერვერზე.

- **Website and documentation pages** რეგისტრირებენ დოკუმენტაციისა და წყაროს ხელსაწყოებს (`search_tuist`, `search_tuist_code`, `list_tuist_files` და `read_tuist_file`). მათ არ სჭირდებათ თქვენგან სისტემაში შესვლა.
- **An account's dashboard pages**, როცა სისტემაში ხართ შესული, რეგისტრირებენ Tuist-ის მხოლოდ წაკითხვის ხელსაწყოებს ამ ანგარიშისთვის. თითოეული გვერდი რეგისტრირებს მხოლოდ იმ ხელსაწყოებს, რასაც ის აჩვენებს, პროექტის build system-ისთვის: Gradle პროექტის builds გვერდი იღებს Gradle build ხელსაწყოებს, მისი test გვერდები — test და coverage ხელსაწყოებს, runners გვერდები — runner ხელსაწყოებს, sandboxes გვერდები — sandbox ხელსაწყოებს. ყველა გვერდი ასევე იღებს დოკუმენტაციის ხელსაწყოებს, `list_projects` და `get_project`. ხელსაწყოები მუშაობენ სისტემაში შესული მომხმარებლის სახელით, ამიტომ ისინი მხოლოდ იმ მონაცემებს აღწევენ, რასაც თქვენ კითხულობთ dashboard-ში და მხოლოდ იმ ანგარიშს, რომელსაც უყურებთ. როცა გადადიხართ სხვა გვერდზე ან ანგარიშზე, ხელსაწყოები იცვლება იმ გვერდის ხელსაწყოებით.

ხელსაწყოები, რომლებიც ქმნიან, ცვლიან ან შლიან მონაცემებს, არ არის ხელმისაწვდომი WebMCP-ით, რადგან ბრაუზერის აგენტი იღებს ხელსაწყოებს თქვენს მიერ დამატების გარეშე და კითხულობს შინაარსს, რომელსაც builds და tests წარმოქმნიან. დააკავშირეთ MCP კლიენტი `/mcp` endpoint-თან ამ ხელსაწყოების გამოსაყენებლად.

თუ ორგანიზაცია აიძულებს ერთჯერად შესვლას (single sign-on), შედით dashboard-ში მისი პროვაიდერით, რათა გამოიყენოთ მისი ხელსაწყოები.

## Build-system ინტეგრაციები იყენებენ ორ რწმუნებას

რწმუნება, რომელიც გამოიყენება Model Context Protocol ხელსაწყოებისთვის, არ ავთენტიკირებს Gradle პლაგინს ან Bazel-ის remote სერვისებს. სანამ აგენტი შეცვლის ან შეამოწმებს Gradle ან Bazel ინტეგრაციას, მან უნდა გაუშვას:

```bash
tuist auth whoami --url https://tuist.dev
```

თუ ეს ბრძანება არ არის ავთენტიკირებული, აგენტმა უნდა შეწყვიტოს და სთხოვოს მომხმარებელს გაუშვას:

```bash
tuist auth login --url https://tuist.dev
```

ლოკალური ან self-hosted განლაგებისთვის, შეცვალეთ URL ორივე ბრძანებაში და `tuist.toml`-ში. შეინარჩუნეთ hostname-ის მართლწერა იდენტური ყველგან. მაგალითად, `localhost` და `127.0.0.1` იყენებენ ცალკე შენახულ რწმუნებებს.


## შესაძლებლობები

### ხელსაწყოები

შემდეგი ხელსაწყოები ხელმისაწვდომია Tuist Model Context Protocol სერვერის მეშვეობით:

ყველა ხელსაწყო აქვეყნებს ადამიანისთვის წასაკითხ აღწერას ცალსახა input და output სქემებთან ერთად. წარმატებული ზარები აბრუნებენ სტრუქტურირებულ შინაარსს, რომელიც შეესაბამება გამოცხადებულ output სქემას, პლუს იგივე შედეგი ტექსტად სერიალიზებული იმ კლიენტებისთვის, რომლებიც ჯერ არ მოიხმარენ სტრუქტურირებულ შინაარსს.

ხელსაწყოები, რომლებიც იღებენ ერთი ჩანაწერის იდენტიფიკატორს, როგორიცაა `build_run_id`, `test_run_id`, `test_case_id`, `bundle_id`, `run_id`, `generation_id`, ან `cache_run_id`, ასევე იღებენ იმ ჩანაწერის Tuist dashboard URL-ს. ჩასვით URL პირდაპირ ბრაუზერიდან იდენტიფიკატორის ამოღების ნაცვლად.

| ID | ხელსაწყო | რეკომენდებულია, როცა |

ID-ები შეზღუდულია აწყობის ფარგლებში და არ უნდა შეესაბამებოდეს სხვა აწყობებს.

არასავალდებულო `start_ms` და `end_ms` ირჩევენ ნაბიჯებს, რომლებიც ემთხვევა დროის დიაპაზონს მილიწამებში აწყობის დაწყებიდან; ბოლო არ არის ჩათვლილი. ორივე ხელსაწყო იღებს აწყობის UUID-ს ან დაშბორდის URL-ს, როგორც `build_run_id`. გადაეცით დაბრუნებული ნაბიჯის `id` უცვლელად, როგორც `step_id` მისი ლოგის მისაღებად. ლოგები ინახავენ 64 KiB-მდე თითო ნაბიჯზე, `log_truncated` მიუთითებს გამოტოვებულ გამოტანაზე.

ნაბიჯები გროვდება ნაგულისხმევად, როცა Xcode აწყობები მუშავდება. ჩაწერილი ნაბიჯების მონაცემები ინახება 90 დღის განმავლობაში. სიის პასუხი შეიცავს `availability`-ს: `available`, როცა ჩაწერილი ნაბიჯები არსებობს, მაშინაც კი, თუ ფილტრები არაფერს ემთხვევა; `processing`, როცა აწყობა კვლავ მუშავდება და ჯერ არ აქვს ნაბიჯები; ან `unavailable`, როცა ნაბიჯები არ ჩაწერილა ან ამოიწურა.

იგივე ოპერაციები ხელმისაწვდომია HTTP API-ზე `GET /api/projects/{account_handle}/{project_handle}/xcode/builds/{build_id}/steps` და `GET /api/projects/{account_handle}/{project_handle}/xcode/builds/{build_id}/steps/{step_id}` მისამართებზე, იგივე ფილტრებით და პაგინაციით. ორივეს სჭირდება წვდომა აწყობის პროექტის საკითხავად.

Gradle-ის და Bazel-ის ნაბიჯების სიები ნაგულისხმევად აბრუნებენ 20 შედეგს (მაქსიმუმ 100), მხარდაჭერილია `search`, ზუსტი `project`, `target`, `category` და `status`, გადაფარვის `start_ms` / `end_ms` ფილტრები (ბოლო არ არის ჩათვლილი) და `duration_ms` ან `start_ms` დალაგება. გადაეცით დაბრუნებული ID-ები უცვლელად; ისინი მიბმულია მათ აწყობაზე. სიები ასახავენ `time_origin`-ს და `coverage`-ს. უფრო ძველი Gradle ანგარიშები იყენებენ `first_recorded_timestamp`-ს, რადგან აწყობის დაწყება არ აიტვირთა. Bazel პროფილები ასახავენ ყველა ჩაწერილ ინტერვალს `trace_profile` დაფარვით და `profile_start`-ს, როგორც დროის საწყისს. უფრო ძველი აწყობები ეყრდნობიან შენარჩუნებულ BEP შეჯამებებს. წყაროს ჩანაწერები იწურება 90 დღის შემდეგ. Bazel-ის დეტალები მოიცავს სანიტიზებულ ქმედების ლოგებს, როცა ისინი გამოქვეყნებულია. Gradle-ის დეტალები შეცდომიანი ამოცანის ან კონფიგურაციის ნაბიჯის შესახებ მოიცავს შეცდომის შეტყობინებას, რომელიც Tuist Gradle პლაგინმა დააბრუნა, როგორც `log`: გამონაკლისის შეტყობინება და მისი მიზეზების ჯაჭვი, როგორც Gradle-ის კონსოლი ბეჭდავს მათ, სტეკის ტრეისების ან ამოცანის გამოტანის გარეშე, პროექტის შიგნით არსებული გზები გადაყვანილია ფარდობით ფორმატში, ხოლო სერთიფიკატები და სხვა ადგილობრივი გზები დაფარულია, მაქსიმუმ 16 KiB თითო ნაბიჯზე და 32 შეცდომიანი ნაბიჯი აწყობაზე. სხვა Gradle ნაბიჯებს, პლაგინის ძველი ვერსიებით მოხსენებულ აწყობებს და სერთიფიკატების გარეშე მოხსენებებს აქვთ null `log`. კონფიგურაციის ნაბიჯები ანგარიშგებენ `failure`-ს, როცა ისინი ვერ შესრულდნენ და `unknown`-ს სხვა შემთხვევაში. `compare_builds` მოთხოვნა იყენებს ამ დაფარვას სრული Bazel ტრეისების განსასხვავებლად შენარჩუნებული შეჯამებებისგან და მიმართავს აგენტებს ნაბიჯის დეტალებისკენ ქმედების შედეგების და ლოგებისთვის, სანამ უფრო ფართო გამოძახების შედეგებს შეამოწმებენ.

ერთი ნაბიჯის ხელსაწყოები `get_gradle_build_step` და `get_bazel_build_step` იღებენ ნაბიჯს ID-ით და არ იღებენ დროის ფილტრებს; გამოიყენეთ შესაბამისი სიის ხელსაწყოები ნაბიჯების ფილტრაციისთვის დროის დიაპაზონით.

Bazel ნაბიჯის ID-ები, რომლებიც დაბრუნებულია შენარჩუნებული შეჯამებებიდან, რჩება წასაკითხად, თუ სრული პროფილი მოვა სიის ჩვენებასა და ნაბიჯის მიღებას შორის. ინდექსირებული პროფილი, რომლის ნაბიჯის მონაცემები ამოიწურა, ანგარიშგებს, როგორც ხელმიუწვდომელი. Gradle ნაბიჯების სიები მოიცავს ნულოვანი ხანგრძლივობის ქეშირებულ და გამოტოვებულ ოპერაციებს.

დააყენეთ `remote_execution: true` `list_bazel_build_steps`-ზე, რათა დააბრუნოთ მხოლოდ ქმედებები უსაფრთხოდ დაკავშირებული სერვერის ფაზის დროებით ინდექსირებული პროფილებიდან. სიის და დეტალური პასუხები ასახავენ არასავალდებულო nullable `remote_queue_ms`, `remote_input_fetch_ms`, `remote_execution_ms` და `remote_output_upload_ms`-ს. მნიშვნელობები აჯამებს ჩაწერილ ფაზებს, მათ შორის ხელახლა ცდებს ქმედების შიგნით; არარსებული ან null მნიშვნელობები ნიშნავს ხელმიუწვდომლობას, არა ნულს. ისინი არის პროფილის დაკვირვებები, არა გადასახდელი გამოყენება ან ახალი შესრულების მტკიცებულება, რადგან ქეშირებულმა სერვერის შედეგებმა შეიძლება შეიცავდნენ შესრულების მეტამონაცემებს. კლიენტის ატვირთვები გამორიცხულია. უფრო ძველმა ან ბუნდოვანმა პროფილებმა შეიძლება არ დააბრუნონ შესაბამისი ქმედებები, მაშინაც კი, თუ დისტანციური სამუშაო შესრულდა. ნაბიჯის REST ბოლოწერტილი იღებს იგივე `remote_execution=true` ფილტრს. დაშბორდის Remote execution ჩანართი იყენებს იგივე მოთხოვნას და 90-დღიან შენარჩუნებას.

ტესტის ლოგები შეიცავს `target_label`-ს და ცდის `status`-ს იმ ტესტის შედეგიდან, საიდანაც ისინი მოვიდნენ, ასე რომ `target_label: "//foo:bar_test"` აბრუნებს მხოლოდ იმ სამიზნის ტესტის ლოგებს. `errors: true` აბრუნებს შეცდომიანი ცდების ტესტის ლოგებს და stderr პროგრესის ნაწილებს, რომლებიც შეიცავს ხაზს, რომლითაც Bazel-ის მომხსენებელი იწყება: `ERROR:`, `FAIL:` ან `TIMEOUT:`. პროგრესის გამოტანა არ არის მიკუთვნებული სამიზნეებისთვის და ლოგებს, რომლებიც დაიწერა მიკუთვნების ჩაწერამდე, აქვთ ცარიელი ველები. შეცდომიანი ქმედებები და მათი საკუთარი გამოტანა ხელმისაწვდომია სამიზნის მიხედვით `list_bazel_build_steps`-დან, და თითოეული ტესტის საქმის შეცდომები ტესტების გაშვების ხელსაწყოებიდან.

`get_build_entity` მეტრიკები მოიცავს `duration_samples`-ს, დაკვირვებების რაოდენობას ჩაწერილი დროით: ნამდვილი ნულოვანი ხანგრძლივობები ითვლება, გამოტოვებული დრო — არა. ეს რაოდენობა შეიძლება იყოს დაკვირვებების რაოდენობაზე ნაკლები; მიუწვდომელი ხანგრძლივობის სტატისტიკა რჩება null-ად.

Xcode მოდულების ხანგრძლივობები მოდის აწყობის ჟურნალებში გაზომილი სამიზნე კომპილაციებიდან. მოდულის კეშის ამოხსნები და სამიზნეები კომპილაციის სამუშაოს გარეშე არ შეიტანენ წვლილს ხანგრძლივობის შერჩევებში. კომპილაციის დაკვირვებები ეხება Xcode აწყობას; კეშის მოვლენები ეხება გენერაციას ან კეშის ბრძანებას.

Bazel ქმედებები იდენტიფიცირდება სამიზნის იარლიყით, მნემონიკით და კონფიგურირებული ძირითადი გამომავალით, რაც ინარჩუნებს ცალკეულ ქმედებებსა და კონფიგურაციებს განცალკევებულად, შეყვანაზე დამოკიდებული კეშის დაიჯესტების გარეშე. ისტორია აღრიცხავს BEP-ით მოხსენებულ შესრულებებს, არა კეშის ძიებებს ან ტრეისის პროფილის ფაზებს. სრული შესრულების დაფარვა მოითხოვს `--build_event_publish_all_actions`-ს; არტეფაქტების მიწოდება ხდება მაქსიმალური ძალისხმევით, ამიტომ გამოტოვებული დაკვირვებები არ არის იმის მტკიცებულება, რომ სამუშაო არ შესრულებულა. ძველი Kura პაკეტები სტაბილური იდენტობის ან შესრულების დაწყების გარეშე რჩება მიღებულად, მაგრამ არაინდექსირებულად. დასრულების დროის გაზომვების არარსებობა რჩება მიუწვდომლად და ნამდვილი ნულოვანი ხანგრძლივობები ითვლება.

Mix მოდულების ხანგრძლივობები ზომავენ შემცველი ფაილის კომპილაციას, არა დამოუკიდებლად გაზომილ მოდულის სამუშაოს. Struo ქმედებები იყენებენ გამოცხადებულ სამიზნე/შესაძლებლობა/ინდექსის სლოტებს, როდესაც კლიენტმა მოახსენა სამიზნეების ასახვა; დიაგნოსტიკური იარლიყები მხოლოდ არ არის სტაბილური იდენტობები. არსებული კლიენტები და გაშვების დონის ხელსაწყოები რჩებიან მხარდაჭერილად უცვლელად.

Cargo კრეიტები დაჯგუფებულია ზუსტად ჩაწერილი კრეიტის ფესვით, სახელით და სახეობით. Checkout-ბილიკის ცვლილებებმა შეიძლება გაყონ ისტორიები, ხოლო აწყობის პროფილები, ფუნქციები და სამიზნე ტრიპლეტები არ განირჩევა. ისტორია ზომავს rustc გამოძახებებს, არა ფაილზე დამოკიდებულ სამუშაოს ან კეშის მოხვედრებს; არარსებული სამუშაოები არ ამყარებენ წაშლებს ან სამუშაო სივრცის სრულ ინვენტარს.

ანალიტიკის წაკითხვებს აქვს შემოსაზღვრული მეხსიერება და შესრულების დრო. თუ მოთხოვნა აღემატება ამ ლიმიტებს, ხელსაწყო აბრუნებს შეცდომას ცარიელი შედეგის გამოგონების ნაცვლად.

### მოვლენები

კლიენტები, რომლებიც იყენებენ უმდგომარეობიან `2026-07-28` Model Context Protocol-ის ციკლს, შეუძლიათ გამოიძახონ `events/list` მოვლენებისა და მათი პეილოადის სქემების აღმოსაჩენად:

| მოვლენა | როდის იგზავნება | გამოწერის ფილტრი |
|-------|-----------------|---------------------|
| `test_case.marked_flaky` | სატესტო შემთხვევა იცვლება არასტაბილურიდან სტაბილურზე. | `account_handle`, `project_handle` |
| `build.failed` | ლოკალური ან უწყვეტი ინტეგრაციის Xcode, Gradle ან Bazel ბილდი მთავრდება შეცდომით. | `account_handle`, `project_handle` |
| `test_run.failed` | ლოკალური ან უწყვეტი ინტეგრაციის ტესტების გაშვება მთავრდება შეცდომით, შერწყმული შარდირებული გაშვების ან მიტოვებული გაშვების ჩათვლით. | `account_handle`, `project_handle` |
| `ci_job.failed` | Tuist-ის რანერის სამუშაო მთავრდება შეცდომით. | `account_handle` |

გამოსაწერად კლიენტი იძახებს `events/subscribe` მოვლენის სახელით, ზემოთ ჩამოთვლილი ხელყოფებით `arguments`-ში და `webhook` მიწოდებით, რომელიც შეიცავს `https://` callback URL-ს და `whsec_` ხელმოწერის საიდუმლოს. პროექტის მოვლენები მოითხოვს ანგარიშის წევრობას და შესაბამისი ტესტის ან ბილდის მონაცემებზე წვდომას; რანერის სამუშაოს მოვლენები მოითხოვს ანგარიშის წევრობას და რანერზე წვდომას. ნამდვილყოფილმა [`auth.md`](https://workos.com/auth-md) წვდომის ტოკენებმა, ნამდვილყოფილმა ანგარიშის ტოკენებმა და ბრაუზერის ავტორიზაციის გრანტებმა შეუძლიათ შექმნან გამოწერები; მიწოდება ჩერდება, როდესაც შესაბამისი კრედენციალი აღარ არის აქტიური. თითოეულ მომხმარებელს შეუძლია ჰქონდეს 25-მდე აქტიური გამოწერა. Tuist აგზავნის ვერიფიკაციის გამოწვევას callback-ზე გამოწერის შენახვამდე. Callback-მა უნდა დააბრუნოს ობიექტი, რომელიც შეიცავს იგივე `challenge` მნიშვნელობას. გამოწერა ნაგულისხმევად გრძელდება შვიდი დღე, შეიძლება განახლდეს ხელახლა გამოწერით და ჩერდება, როდესაც მომხმარებლის წვდომა ან კრედენციალი ამოიღება. არასავალდებულო `ttlMs` შეზღუდულია ერთ საათსა და 30 დღეს შორის. Tuist ხელახლა ცდილობს დროში ამოწურულ callback-ს და აუქმებს გამოწერას მინიმუმ სამი თანმიმდევრული დროში ამოწურვის შემდეგ, რომლებიც მოიცავს ხუთ წუთს; ხელახლა გამოიწერეთ callback-ის აღდგენის შემდეგ.

როდესაც მოვლენა ხდება, Tuist აგზავნის მის რესურსის იდენტიფიკატორს და დაფის URL-ს callback-ზე. ბილდისა და ტესტების გაშვების შეცდომები ასევე შეიცავს `is_ci`-ს და `git_branch`-ს, რათა კლიენტებმა შეძლონ ლოკალური შეცდომების იგნორირება ან ფილტრაცია განშტოების მიხედვით. ბილდის მოვლენები შეიცავს `build_system`-ს; რანერის სამუშაოს მოვლენები შეიცავს როგორც `workflow_job_id`-ს, ისე `workflow_run_id`-ს. მოთხოვნა შეიცავს გამოწერის იდენტიფიკატორს და [Standard Webhooks](https://www.standardwebhooks.com/) ხელმოწერის ჰედერებს, რათა კლიენტმა შეძლოს მისი წარმომავლობის ვერიფიკაცია. Tuist ხელახლა ცდილობს წარუმატებელ მიწოდებებს, ამიტომ კლიენტებმა უნდა გამოიყენონ სტაბილური `eventId` დუბლიკატების გასაფილტრად. პეილოადი გამორიცხავს ტესტების სახელებს, ლოგებსა და შეცდომის შეტყობინებებს; კლიენტმა შეუძლია მიიღოს ეს დეტალები ზემოთ ჩამოთვლილი ინსტრუმენტების მეშვეობით და გადაწყვიტოს, შეატყობინოს თუ არა გუნდს ან დაიწყოს დებაგინგი. კლიენტებმა შეუძლიათ შეწყვიტონ მიწოდება `events/unsubscribe`-ით.

| `compare_generations` | გეხმარებათ ორი გენერაციის გაშვების შედარებაში შესრულების რეგრესიებისა და მოდულის ქეშის ცვლილებების იდენტიფიცირებისთვის. |
| `compare_cache_runs` | გეხმარებათ ორი ქეშის გაშვების შედარებაში ქეშის ეფექტურობის ცვლილებებისა და სამიზნე დონის რეგრესიების იდენტიფიცირებისთვის. |
| `integrate_gradle_project` | გეხმარებათ Tuist-ის ინტეგრაციაში არსებულ Gradle პროექტში. მოიცავს ცალკეულ ინსტრუმენტსა და Gradle-ის ავთენტიკაციას, ანგარიშის აღმოჩენას, პროექტის შექმნას, დისტანციური ქეშის პოლიტიკას, ბილდის ინსაიტებსა და უკუკავშირის ვერიფიკაციას. |
| `integrate_bazel_project` | გეხმარებათ Bazel პროექტის შექმნაში ან შერჩევაში, ბრძანების სტრიქონის ავთენტიკაციაში, დისტანციური ქეშისა და ბილდის ინსაიტების კონფიგურირებაში და ინტეგრაციის ვერიფიკაციაში Tuist-ის ბილდის მონაცემების მეშვეობით. |
| `integrate_xcode_project` | გეხმარებათ Tuist-ის ინტეგრაციაში არსებულ Xcode პროექტში. მხარდაჭერილია Xcode ქეში, ბილდის ინსაიტები, ტესტის ინსაიტები და ტესტის შარდირება. |
| `ask_tuist` | პასუხობს Tuist-ის კითხვას საჯარო მასალების გამოყენებით კონტექსტისთვის და ფოკუსირებული იმპლემენტაციისა და ტესტის მტკიცებულებებით, როგორც მიმდინარე ქცევის სანდო წყარო. მოითხოვს `question`-ს და ასახელებს რევიზიით მიმაგრებულ მტკიცებულებას. |

პროექტის მონაცემების მოთხოვნები იღებენ `account_handle`-ს და `project_handle`-ს კვლევის კონკრეტულ პროექტზე შემოსაზღვრად. შედარების მოთხოვნები ასევე იღებენ `base` და `head` არგუმენტებს შესადარებელი ორი ელემენტის მითითებისთვის (ID-ით, დაფის URL-ით ან განშტოების სახელით). `ask_tuist` იღებს `question`-ს პროექტის პარამეტრების ნაცვლად. `integrate_gradle_project` ასევე იღებს `features`-ს, Gradle-ის ინტეგრაციების მძიმით გამოყოფილ სიას გამოსაყენებლად: `remote_cache`, `build_insights`, `test_insights`, `flaky_tests` და `test_sharding`. `integrate_bazel_project` იღებს არასავალდებულო `server_url`-ს თვითმასპინძლებელი ან ლოკალური ინსტალაციებისთვის. `integrate_xcode_project` იღებს `features`-ს `xcode_cache`-ით, `build_insights`-ით, `test_insights`-ით და `test_sharding`-ით.

#### Gradle-ის ინტეგრაციის მოთხოვნის ფუნქციები

`integrate_gradle_project` მოთხოვნა და `get_gradle_integration_guide` ინსტრუმენტი აღწერს სრულ დაყენების სამუშაო ნაკადს. ინსტრუმენტი ასევე არის მითითებული სერვერის ინიციალიზაციის ინსტრუქციებში, რაც მას აღმოჩენადს ხდის აგენტებისთვის, რომლებიც არ ჩამოთვლიან მოთხოვნებს.

| ფუნქცია | რას აკონფიგურირებს აგენტი |
|---------|---------------------------|
| `remote_cache` | ააქტიურებს Gradle-ის ბილდის ქეშს, აკონფიგურირებს Tuist-ის დისტანციური ქეშის ატვირთვის პოლიტიკას და ურჩევს ატვირთვას მხოლოდ უწყვეტი ინტეგრაციის რანერებიდან ლოკალური მხოლოდ-წაკითხვადი გამოყენებით. |
| `build_insights` | აყენებს Tuist Gradle პლაგინს და აკონფიგურირებს ბილდის ანალიტიკის ატვირთვის ქცევას საჭიროების შემთხვევაში. |
| `test_insights` | აყენებს Tuist Gradle პლაგინს, რათა Gradle `Test` ამოცანის შედეგები ავტომატურად აიტვირთოს. |
| `flaky_tests` | გეხმარებათ არასტაბილური ტესტების აღმოჩენის დაყენებაში, Gradle Test Retry პლაგინის არასავალდებულო გამოყენებაში და ტესტის კარანტინის კონფიგურაციაში. |
| `test_sharding` | ამატებს უწყვეტი ინტეგრაციის სამუშაო ნაკადს `tuistPrepareTestShards`-ისთვის, შარდის მატრიცის გენერირებისთვის და `TUIST_SHARD_INDEX`-ზე დაფუძნებული ტესტის შესრულებისთვის. |

როდესაც `features` გამოტოვებულია, მოთხოვნა სთხოვს აგენტს დააზუსტოს, რომელი ინტეგრაციები სურს მომხმარებელს ან გამოიტანოს უმცირესი სასარგებლო ნაკრები მოთხოვნიდან Gradle პროექტის რედაქტირებამდე.

#### Xcode-ის ინტეგრაციის მოთხოვნის ფუნქციები

`integrate_xcode_project` მოთხოვნა აღწერს ყველა Xcode ინტეგრაციას, რომელსაც Tuist მხარს უჭერს:

| ფუნქცია | რას აკონფიგურირებს აგენტი |
|---------|---------------------------|
| `xcode_cache` | აკონფიგურირებს `tuist setup cache`, გენერირებული პროექტის ქეშის პარამეტრებს, Xcode-ის ქეშის ბილდის ხელით მითითებულ პარამეტრებს და ატვირთვის პოლიტიკას, რომელიც შემოიფარგლება მხოლოდ უწყვეტი ინტეგრაციის რანერებით. |
| `build_insights` | აკონფიგურირებს `tuist inspect build`-ს, `tuist xcodebuild`-ს, `-resultBundlePath`-ს და არასავალდებულო მანქანურ მეტრიკებს `tuist setup insights`-ის საშუალებით. |
| `test_insights` | აკონფიგურირებს `tuist inspect test`-ს, სქემის ტესტის post-actions-ებს და შედეგების ბანდლის გენერირებას უწყვეტი ინტეგრაციის ტესტების გაშვებისთვის. |
| `test_sharding` | ამატებს Xcode-ის ან გენერირებული პროექტის შარდების დაგეგმვისა და შარდების შესრულების სამუშაო ნაკადს `TUIST_SHARD_INDEX`-ის გამოყენებით. |

როდესაც `features` გამოტოვებულია, მოთხოვნა სთხოვს აგენტს დააზუსტოს, რომელი ინტეგრაციები სურს მომხმარებელს ან გამოიტანოს უმცირესი სასარგებლო ნაკრები მოთხოვნიდან Xcode პროექტის რედაქტირებამდე.
