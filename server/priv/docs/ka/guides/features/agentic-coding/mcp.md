# Model Context Protocol

[Model Context Protocol (MCP)](https://modelcontextprotocol.io/docs/getting-started/intro) არის ღია სტანდარტი, რომელიც საშუალებას აძლევს ხელოვნური ინტელექტის აგენტებს ურთიერთქმედება გარე სერვისებთან და მონაცემთა წყაროებთან. ის უზრუნველყოფს ისეთი აპლიკაციების, როგორიცაა [Claude](https://claude.ai/), [Claude Code](https://docs.anthropic.com/en/docs/claude-code), [Codex](https://developers.openai.com/codex/), და რედაქტორების, როგორიცაა [Zed](https://zed.dev), [Cursor](https://www.cursor.com) ან [Visual Studio Code](https://code.visualstudio.com), თავსებადობას Tuist-თან.

Tuist მასპინძლობს Model Context Protocol-ის სერვერულ ბოლოწერტილს მისამართზე `https://tuist.dev/mcp`. მასზე თქვენი კლიენტის მიერთებით, აგენტებს შეუძლიათ წვდომა თქვენს Tuist პროექტის მონაცემებზე, მათ შორის ტესტების ინსაიტებზე, არასტაბილური ტესტების ანალიზზე და სხვა. უმეტესი ინსტრუმენტი კითხულობს Tuist-ის მონაცემებს, რომლებსაც ავტორიზებული მომხმარებელი უკვე ხედავს დაფლაზე. ყოველი ინსტრუმენტი ასახავს ანოტაციებს, რომლებიც მიუთითებს, არის თუ არა ის მხოლოდ წაკითხვისთვის, შეუძლია თუ არა მას გამოიწვიოს რთულად შექცევადი ცვლილება (`destructiveHint`) და შეუძლია თუ არა მას Tuist-ის ფარგლებს გარეთ გასვლა (`openWorldHint`). ინსტრუმენტები, რომლებიც ცვლიან მდგომარეობას, თითოეული შეზღუდულია მომხმარებლის ნებართვებით ანგარიშზე ან პროექტზე:

- **ორგანიზაციები და წევრები**: `create_organization`, `add_organization_member` (ამატებს არსებულ მომხმარებელს ან ცვლის წევრის როლს), `invite_organization_member` (აგზავნის მოწვევას ნებისმიერ ელფოსტაზე) და `cancel_organization_invitation`.
- **პროექტები**: `create_project`, `start_project_logo_upload` და `complete_project_logo_upload` (ცვლის ლოგოს), `connect_project_repository` და `disconnect_project_repository` (GitHub რეპოზიტორიის ბმულები).
- **ტესტები**: `update_test_case` (აჩუმებს, ტოვებს, ხელახლა ჩართავს ან აღნიშნავს სატესტო შემთხვევას, როგორც არასტაბილურს; ცვლილებამ შეიძლება მიაღწიოს ანგარიშის webhook ბოლოწერტილებს).
- **შეტყობინებების წესები**: `create_notification_rule`, `update_notification_rule` და `delete_notification_rule`.
- **უწყვეტი ინტეგრაციის გამშვებები**: `create_runner_profile`, `update_runner_profile` (კეშის ტომების შენახვის სამუშაოების შევიწროება აუქმებს ლოდინში მყოფ შენახვებს), `delete_runner_profile` და `delete_runner_volume` (შლის ტომის შენახულ შინაარსს).
- **სენდბოქსები**: `create_sandbox`, `pause_sandbox`, `resume_sandbox`, `archive_sandbox` და `delete_sandbox` (შლის მის დისკებს).
- **უკუკავშირი**: `report_feedback` (აგზავნის ანგარიშს ინსტრუმენტის ან მოთხოვნის შესახებ Tuist-ის გუნდს; მხოლოდ tuist.dev-ზე).
- **ორგანიზაციის AI**: `save_organization_ai_model`, `remove_organization_ai_model`, `set_organization_ai_default_model`, `save_organization_ai_task_route`, `remove_organization_ai_task_route` და `remove_organization_ai_provider` (შლის პროვაიდერის გასაღებს და მოდელებს და წყვეტს Anthropic-ზე დაკავშირებულ Claude ორგანიზაციას).
- **აგენტის ინტეგრაციები**: `connect_amp_workspace` (ანიჭებს სამუშაო სივრცის orbs CI-ს წვდომას ანგარიშზე), `disconnect_amp_workspace` და `connect_claude_environment` (საშუალებას აძლევს Claude Managed Agents გარემოს გაუშვას სესიები Tuist სენდბოქსებში).

`add_organization_member`, `cancel_organization_invitation`, `complete_project_logo_upload`, `disconnect_project_repository`, `update_test_case`, `update_notification_rule`, `delete_notification_rule`, `update_runner_profile`, `delete_runner_profile`, `delete_runner_volume`, `delete_sandbox`, `disconnect_amp_workspace`, `remove_organization_ai_provider`, `remove_organization_ai_model` და `remove_organization_ai_task_route` ასახავს `destructiveHint: true`-ს, რადგან ისინი ცვლიან ან აშორებენ არსებულ მდგომარეობას. `invite_organization_member`, `update_test_case`, `connect_claude_environment`, `remove_organization_ai_provider` და `report_feedback` ასახავს `openWorldHint: true`-ს, რადგან ისინი აგზავნიან ელფოსტას, ატყობინებენ გარე webhook ბოლოწერტილებს, ურეკავენ Anthropic-ს ან აგზავნიან ანგარიშს Tuist-ის გუნდს.

პირადი Claude და ChatGPT გამოწერები დაკავშირებულია მხოლოდ დაფის AI პარამეტრებში, ამიტომ გამოწერის ტოკენები და შესვლები არასდროს გადის Model Context Protocol კლიენტის მეშვეობით. ანგარიშის დაყენების ინსტრუმენტებს სჭირდებათ მომხმარებლის ავტორიზაცია. ისინი არ არის ხელმისაწვდომი პროექტის ტოკენების ან ჩვეულებრივი ანგარიშის ტოკენებისთვის. როდესაც მომხმარებელი ავტორიზებს კლიენტს ბრაუზერში ან ითხოვს `auth.md` რეგისტრაციას, Tuist აკავშირებს ამ სარწმუნოებას მომხმარებელთან მხოლოდ Model Context Protocol ბოლოწერტილზე, რათა დაყენების ინსტრუმენტებმა შეძლონ მოთხოვნილი სამუშაო პროცესის დასრულება.

Tuist ახორციელებს [2026-07-28 პროტოკოლს](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http). მოთხოვნები არის უსტატუსო: კლიენტები აგზავნიან თავიანთ პროტოკოლის მეტამონაცემებს ყოველ მოთხოვნასთან ერთად და შეუძლიათ პირდაპირ გამოიძახონ ინსტრუმენტები ინიციალიზაციის გარეშე. `server/discover` აბრუნებს სერვერის იდენტობას, შესაძლებლობებს, მხარდაჭერილ ვერსიებს და ინსტრუქციებს. არ არსებობს სესიის იდენტიფიკატორები ან დამოუკიდებელი მოვლენების ნაკადები. კლიენტები, რომლებიც იყენებენ 2025-06-18 ან 2025-03-26 ინიციალიზაციის ნაკადს, კვლავ მხარდაჭერილია; ისინიც მუშაობენ სერვერის სესიების გარეშე.

## Model Context Protocol უნარების წინააღმდეგ

Model Context Protocol-ის ინსტრუმენტებს და <.localized_link href="/guides/features/agentic-coding/skills">უნარებს</.localized_link> შეიძლება ჰქონდეთ გადაფარვა შესრულებულ ფუნქციებში. ამჟამინდელი გადაფარვის გათვალისწინებით, აირჩიეთ ერთი მიდგომა თითოეული სამუშაო პროცესისთვის და გამოიყენეთ ის თანმიმდევრულად, ნაცვლად ორივეს ერთ ნაკადში შერევისა.

კლიენტებისთვის, რომლებიც მხარს უჭერენ პლაგინების ინსტალაციას, გამოიყენეთ <.localized_link href="/guides/features/agentic-coding/plugins">Tuist პლაგინები</.localized_link> ორივეს ერთად ინსტალაციისთვის.

## კონფიგურაცია

დაამატეთ `https://tuist.dev/mcp` როგორც დაშორებული Model Context Protocol სერვერი თქვენს კლიენტში. სერვერის ინიციალიზაციის ინსტრუქციები და საჯარო სერვერის ბარათი აღწერს OAuth 2.0-ს დინამიური კლიენტის რეგისტრაციით და სტანდარტული ბრაუზერის ავტორიზაციის ნაკადით პირდაპირ, იმის მოთხოვნის გარეშე, რომ აგენტებმა მიიღონ ან გაჰყვნენ გარე ავტორიზაციის დოკუმენტებს. ეს სერვერის მასშტაბის ინსტრუქციები ინარჩუნებს სამუშაო პროცესის მითითებებს ზოგადს: ინსტრუმენტის ავტორიზაცია არ ავტორიზებს ადგილობრივ ბრძანების სტრიქონის ინსტრუმენტებს ან აგების სისტემის ინტეგრაციებს და აგენტებმა უნდა შეამოწმონ მოთხოვნილი ცვლილებები შესაბამისი Tuist ინსტრუმენტების მეშვეობით. აგების სისტემის სპეციფიკური დაყენება და ავტორიზაციის შემოწმებები დოკუმენტირებულია ინტეგრაციის სახელმძღვანელოებში და მოთხოვნებში. Tuist კვლავ ასახავს როგორც [Open Authorization](https://oauth.net/2/) აღმოჩენის მეტამონაცემებს, ასევე მიმდინარე [auth.md პროტოკოლს](https://workos.com/auth-md) მისამართზე `https://tuist.dev/auth.md` ცალკე.

თუ თქვენი რომელიმე ორგანიზაცია აიძულებს ერთჯერად შესვლას, ბრაუზერში კლიენტის ავტორიზაცია მოითხოვს სესიას, რომელიც შესულია ამ ორგანიზაციის მეშვეობით და Tuist საჭიროების შემთხვევაში ჯერ პროვაიდერთან გაგზავნით. იხილეთ <.localized_link href="/guides/integrations/authentication/sso#choose-an-enrollment-policy">ერთჯერადი შესვლა</.localized_link>.

ბოლოწერტილი იღებს უსტატუსო `2026-07-28` Model Context Protocol მოთხოვნის სასიცოცხლო ციკლს, `server/discover`-ის ჩათვლით, ძველ სესიაზე დაფუძნებულ ციკლთან ერთად. არსებულმა კლიენტებმა შეიძლება განაგრძონ მათი მიმდინარე მიერთების მეთოდის გამოყენება.

კლიენტები, რომლებიც მხარს უჭერენ Model Context Protocol მოვლენებს, შეიძლება გამოიწერონ პროექტის მოვლენები. იხილეთ [მოვლენები](#events) ხელმისაწვდომი მოვლენებისა და მიწოდების მოთხოვნებისთვის.

კლიენტები, რომლებიც უკვე მხარს უჭერენ დაშორებულ ბრაუზერის ავტორიზაციას, შეიძლება განაგრძონ ავტორიზაცია ბრაუზერში. კლიენტები და აგენტები, რომლებიც მხარს უჭერენ `auth.md`-ს, შეიძლება დარეგისტრირდნენ ანონიმურად, წარმოადგინონ სანდო პროვაიდერის იდენტობის დამტკიცება ან დაიწყონ სერვისით ავტორიზებული ელფოსტის მოთხოვნა. რეგისტრაცია აბრუნებს Tuist-ით ხელმოწერილ იდენტობის დამტკიცებას, რომელსაც აგენტი ცვლის სტანდარტულ ტოკენის ბოლოწერტილზე ერთსაათიან წვდომის ტოკენზე. Tuist აქვეყნებს თავის საჯარო ხელმოწერის გასაღებს და მხარს უჭერს სტანდარტულ ტოკენის გაუქმებას და პროვაიდერის უსაფრთხოების მოვლენების მიწოდებას.

არაავტორიზებულმა აგენტმა უნდა წაიკითხოს Model Context Protocol ბოლოწერტილის მიერ დაბრუნებული `WWW-Authenticate` ჰედერი, მოიძიოს დაცული რესურსის მეტამონაცემები, მოიძიოს ავტორიზაციის სერვერის მეტამონაცემები და გადავიდეს მის `agent_auth.skill` URL-ზე. Tuist ასევე აბრუნებს იგივე ლოკალურ `auth_md` URL-ს არაავტორიზებული პასუხის სხეულში, რათა ენის მოდელებზე დაფუძნებულმა კლიენტებმა აღმოაჩინონ ნაკადი ნატიური კლიენტის ინტეგრაციაზე დამოკიდებულების გარეშე. განლაგების ლოკალური დოკუმენტი არის საიმედო წყარო ბოლოწერტილების სახელების, მოთხოვნის სხეულების, მოთხოვნის გამოკითხვისა და დამტკიცების გაცვლისთვის.

სანამ აგენტი დაიწყებს ელფოსტის მოთხოვნას, მან უნდა სთხოვოს მომხმარებელს დაადასტუროს თავისი Tuist ანგარიშის ელფოსტის მისამართი. მან არ უნდა გამოიტანოს ეს მისამართი პროვაიდერის პროფილიდან, Git კონფიგურაციიდან, გარემოს ცვლადიდან ან სესიის მეტამონაცემებიდან.

ბოლოწერტილი იყენებს `mcp` სკოპის ჯგუფს. ანონიმურმა წინასწარ-მოთხოვნის კრედალმა შეიძლება აღმოაჩინოს შესაძლებლობები და წაიკითხოს საჯარო ინტეგრაციის სახელმძღვანელო, მაგრამ ის არ განიხილება როგორც შესული მომხმარებელი. ბრაუზერის ავტორიზაციის ან მოთხოვნის შემდეგ, კრედალი არის მომხმარებლის სკოპით და თითოეული ინსტრუმენტი იყენებს იგივე ავტორიზაციის შემოწმებებს, რასაც დაშბორდი. დეტალებისთვის იხილეთ <.localized_link href="/guides/server/authentication#scope-groups">სკოპის ჯგუფების დოკუმენტაცია</.localized_link>.

ინსტრუმენტები გადაჰყავთ პროექტებზე, რომელთა წაკითხვაც ავტორიზებულ მომხმარებელს უკვე შეუძლია. Xcode-ისა და Gradle-ის აგების ინსტრუმენტები იღებენ აგების UUID-ს ან დაშბორდის URL-ს. UUID-მ უნდა მიუთითოს ზუსტად ერთ პროექტზე; თუ ის ჩნდება რამდენიმე პროექტში, ინსტრუმენტი აბრუნებს „არ არის ნაპოვნი“-ს სხვა პროექტის ანგარიშის არჩევის ნაცვლად. პროექტის სკოპით დაშბორდისა და API-ს წაკითხვა რჩება ხელმისაწვდომი. მოხსენებული აქტორის იდენტიფიკატორები არის დაუდასტურებელი ლეიბლები, არა კრედალები ან დამატებითი წვდომის უფლებები.

აგების სიისა და დეტალების ინსტრუმენტები ავლენენ ოფციონალურ `tuist_version` მეტამონაცემებს: Xcode-ისა და Cargo-სთვის მომხსენებელი Tuist CLI, Tuist Gradle პლაგინი Gradle-ისთვის და `tuist_ex` ბიბლიოთეკა Mix-ისთვის. Xcode ასევე ავლენს `tuist_generation_version`-ს მის დაკავშირებული პროექტის გენერაციის მოვლენიდან, რომელიც შეიძლება განსხვავდებოდეს ატვირთვადი CLI-სგან. დაკარგული დაკვირვებები არის null, არა გამოტანილი სერვერიდან ან სხვა ანგარიშიდან. Bazel იყენებს თავის არსებულ `bazel_version`-ს; Struo გაშვების დეტალები ავლენენ `once_version`-ს. ეს ველები აღწერენ მოხსენებულ ვერსიებს, არა დადასტურებულ იდენტობას ან სადენის კონტრაქტის ვერსიებს. REST აგების ბოლოწერტილები ავლენენ იგივე მეტამონაცემებს. არსებული ინტეგრაციისა და ფლაკი-ტესტის უნარები არ არიან დამოკიდებული ვერსიის ველებზე და არ საჭიროებენ სამუშაო ნაკადის ცვლილებებს.

Tuist ოპერატორები, რომლებიც იკვლევენ მომხმარებლის ანგარიშს, ამას აკეთებენ Tuist-ის შიდა ოპერაციული ინსტრუმენტების მეშვეობით, რომელიც იწერს ყოველ ზარს; პირდაპირი კავშირი ამ ბოლოწერტილთან არ იძლევა წვდომას მომხმარებლის საკუთარი წევრობის გარდა.

### Pulse

Pulse ავლენს მხოლოდ წაკითხვად ინსტრუმენტებს ანგარიშის ოპერაციული მეტრიკების, ლოგების, ტრეისებისა და შეცდომებისთვის, ყველა მიმართული `account_handle`-ით. პირველი სამი ასახავს Pulse გვერდებსა და მათ REST API-ს; დანარჩენი ხუთი საშუალებას აძლევს აგენტს პირდაპირ შეისწავლოს ტელემეტრია და არ აქვთ REST ეკვივალენტი:

| ინსტრუმენტი | მიზანი | REST ეკვივალენტი `/api/accounts/:account_handle/pulse` ქვეშ |
| --- | --- | --- |
| `query_pulse` | Pulse გვერდის ცხრილები | `GET /:signal` |
| `get_pulse_analytics` | Pulse გვერდის ვიჯეტები | `GET /:signal/analytics` |
| `get_pulse_error_issue` | ერთი შეცდომის საკითხი და მისი მოვლენები | `GET /errors/issues/:fingerprint` |
| `query_pulse_metrics` | მყისიერი ან დიაპაზონის PromQL | არ არის |
| `list_pulse_labels` | ლეიბლის სახელები, ან ერთი ლეიბლის მნიშვნელობები | არ არის |
| `search_pulse_logs` | ფილტრული ლოგის ჩანაწერები | არ არის |
| `search_pulse_traces` | ფილტრული სპანები | არ არის |
| `get_pulse_trace` | ერთი ტრეისის ყოველი სპანი | არ არის |

Pulse შეზღუდულია სერვერით კონფიგურირებული ორგანიზაციის მიმდინარე წევრებზე, მაშინაც კი, თუ ანგარიში ან პროექტი საჯაროა. ის მოითხოვს მომხმარებლის ავტორიზაციას ან მომხმარებელთან დაკავშირებულ `mcp` კრედალსა და ანგარიშის წაკითხვის ავტორიზაციას. პროექტის ტოკენები, ჩვეულებრივი ანგარიშის ტოკენები, ანონიმური რეგისტრაციები და ოპერატორის წვდომა ორგანიზაციის წევრობის გარეშე არ იძლევა Pulse წვდომას. კრედალებს არ შეუძლიათ აირჩიონ სხვა ბექენდი ან ტელემეტრიის არენდატორი და მხოლოდ სერვერით კონფიგურირებულ ანგარიშს აქვს Pulse ტელემეტრია, ამიტომ არცერთ ინსტრუმენტს არ შეუძლია წაიკითხოს სხვა ანგარიშის მონაცემები. ბრაუზერის აგენტები იღებენ ამ ინსტრუმენტებს მხოლოდ Pulse გვერდებზე, ამ გვერდის ანგარიშის სკოპის ფარგლებში.

REST მოითხოვს მომხმარებლის კრედალს. OAuth და `auth.md` მომხმარებლის ასოციაციები ხელმისაწვდომია მხოლოდ `/mcp` ბოლოწერტილზე; ანგარიშის კრედალი მიმდინარე მომხმარებლის გარეშე უარყოფილია, მიუხედავად დაკავშირებული ანგარიშის წევრობისა ან ხილვადობის.

`query_pulse` იღებს `signal` (`metrics`, `logs`, `traces`, ან `errors`), ოფციონალურ `query` და `range` (`15m`, `1h`, `6h`, ან `24h`, ნაგულისხმევი `1h`). მეტრიკები იღებენ PromQL გამოსახულებებს. ლოგები, ტრეისები და შეცდომები იღებენ ლიტერალურ, რეგისტრის მიმართ უმჯრუნ ტექსტს, რომელიც ემთხვევა ლოგის სხეულებს, სპანის სახელებსა და შეცდომის საკითხის სათაურებს; `*`, ნაგულისხმევი, ირჩევს ყველაფერს. ტრეისის სტრიქონები არის ინდივიდუალური სპანები. შეცდომის სტრიქონები არის საკითხები: მოვლენები დაჯგუფებული სერვისისა და თითის ანაბეჭდის მიხედვით, მათი მოვლენების რაოდენობით, დაზარალებული ანგარიშებით, პირველი და ბოლო გამოჩენა ფანჯარაში, და მათი ბოლო მოვლენის სათაური, დამნაშავე, დონე და პლატფორმა. ცხრილები იღებენ `search`-ს, `page`-ს (ნაგულისხმევი `1`), `page_size`-ს (`1`–`100`, ნაგულისხმევი `20`), `sort_by`-ს და `sort_order`-ს (`asc` ან `desc`). დალაგების სვეტები დამოკიდებულია სიგნალზე და ჩამოთვლილია ინსტრუმენტის სქემაში. ფილტრები მოიცავს `service`-ს და `level`-ს ლოგებისა და შეცდომებისთვის. ფილტრის ოპერატორები იყენებენ შესაბამის `_op` არგუმენტს (`eq`, `contains`, ან `not_contains`), ნაგულისხმევად ზუსტი ტოლობით.

დალაგების სვეტებია `name`/`value` მეტრიკებისთვის; `timestamp`/`service`/`level`/`message`/`trace_id` ლოგებისთვის; `timestamp`/`service`/`name`/`duration_ms`/`trace_id` ტრეისებისთვის; და `last_seen`/`first_seen`/`events`/`accounts`/`title`/`service`/`level` შეცდომებისთვის. დაშბორდი განზრახ ავლენს ქვესიმრავლეს; API და ინსტრუმენტები იღებენ სრულ სიას თითოეული სიგნალისთვის.

ცხრილის პასუხები შეიცავს `rows`-ს, `series`-ს, `warnings`-ს და `meta`-ს. დაფურცვლის მეტამონაცემები მოიცავს `page`-ს, `page_size`-ს, `total_count`-ს, `total_pages`-ს, `has_next_page`-ს, `has_previous_page`-ს და `end_at`-ს. გადასცეთ დაბრუნებული ISO8601 `end_at` მომდევნო გვერდებთან ერთად მოთხოვნის ფანჯრის შესანარჩუნებლად. შედეგის ლიმიტის შეცდომები მოითხოვენ მოთხოვნის ან დროის დიაპაზონის შევიწროვებას, არა პასუხის ცარიელ ცხრილად განხილვას.

ლოგები და ტრეისები ამოწმებენ მაქსიმუმ 100 უახლეს დამთხვევას ადგილობრივი დალაგებამდე, ხოლო შეცდომები — 100 უახლეს ნანახ საკითხს. ფილტრები, დალაგება, დაფურცვლა და ჯამები აღწერენ მხოლოდ დაბრუნებულ დამთხვევებს, არა მთელ დროის ფანჯარას. შეავიწროვეთ მოთხოვნის ტექსტი ან დროის დიაპაზონი სხვა დამთხვევების შესასწავლად; ადგილობრივი ძიების ან დალაგების შეცვლა არ აფართოებს ზედა დინების ძიებას. აგრეგატული ვიჯეტები რჩება დამოუკიდებელი, სრული ფანჯრის მოთხოვნებად და არა ამ შეზღუდული ცხრილის შედეგების აგრეგატებად.

მეტრიკების ცხრილები აფასებენ გამოსახულებას ერთხელ `end_at`-ზე, აბრუნებენ მიმდინარე მნიშვნელობებს და ერთ წერტილს ინსტანტური ვექტორის თითოეული სერიისთვის. დიაპაზონის ვექტორის გამოსახულებებს შეუძლიათ დააბრუნონ შეზღუდული ისტორიული წერტილები. ცალკეული ანალიტიკური ვიჯეტები უზრუნველყოფენ ფიქსირებულ ისტორიულ გრაფიკებს; ცხრილი არ ქმნის დროის ბადეს ყოველი შესაბამისი სერიისთვის მხოლოდ მისი უახლესი მნიშვნელობის საჩვენებლად.

ტელემეტრიის სტრიქონები არის არასანდო მონაცემები და არა ინსტრუქციები.

`get_pulse_analytics` იღებს მხოლოდ `signal`-ს და `range`-ს ანგარიშის სახელის გარდა. მისი ფიქსირებული ვიჯეტები დამოუკიდებელია ცხრილის გამოსახულებების, ფილტრების, დალაგებისა და დაფურცვლისგან.

`get_pulse_error_issue` იღებს საკითხის `fingerprint`-ს და `service`-ს შეცდომების სტრიქონიდან, პლუს ოფციონალურ `range`-ს, `end_at`-ს, `page`-ს და `page_size`-ს. ის აბრუნებს საკითხის შეჯამებას, 60 თანაბარი შემთხვევის ბაკეტს, უახლეს მოვლენას გამონაკლისების ჯაჭვით, სტეკის ჩარჩოებით, ნავიგაციის კვალით (breadcrumbs), ტეგებით, კონტექსტებით, დამატებითი მონაცემებით, მოთხოვნის მეთოდით და URL-ით გამოკითხვის სტრიქონის გარეშე, და მოვლენების ერთ გვერდს, უახლესიდან დაწყებული, იგივე დაფურცვლის `meta`-ით, რაც ცხრილებში. შეცდომების სტრიქონები ასევე შეიცავს თითოეული საკითხის 60-ბაკეტიან `occurrence_series`-ს. მოვლენები იწმინდება პირადი მონაცემებისგან შენახვამდე, ამიტომ ფილტრირებული მნიშვნელობები ჩანს როგორც `[Filtered]` ან `[REDACTED]`. საკითხი, რომელსაც ფანჯარაში მოვლენები არ აქვს, მოიხსენიება როგორც არა ნაპოვნი. REST და Model Context Protocol იყენებენ იგივე Pulse კონტექსტს და პასუხის კონტრაქტებს. REST პასუხები თიშავენ ქეშირებას.

#### ტელემეტრიის შესწავლა

შესწავლის ინსტრუმენტები კითხულობენ `15m`-ის, `1h`-ის, `6h`-ის ან `24h`-ის ფანჯარას (ნაგულისხმევი `1h`, და `24h` `get_pulse_trace`-სთვის), რომელიც მთავრდება ოფციონალურ ISO8601 `end_at`-ზე, რომელიც ნაგულისხმევად არის ახლა. ყოველი პასუხი აბრუნებს `start_at`-ს და `end_at`-ს; გადასცეთ იგივე `end_at` ხელახლა ფანჯრის შესანარჩუნებლად. ამ ინსტრუმენტებიდან არცერთი არ იღებს SQL-ს.

- `query_pulse_metrics` აფასებს `query`-ს, PromQL გამოსახულებას, `end_at`-ზე (`type: instant`, ნაგულისხმევი) ან ყოველ `step` წამში ფანჯრის განმავლობაში (`type: range`). ნაბიჯი ნაგულისხმევად არის და არ შეიძლება იყოს ფანჯარა გაყოფილი 360-ზე ნაკლები, ამიტომ სერიას მაქსიმუმ 361 წერტილი აქვს. შედეგებს მაქსიმუმ 5,000 სერია აქვს. წერტილები არის `[unix_seconds, value]`, ხოლო `NaN` და უსასრულო მნიშვნელობები არის სტრიქონები. ინსტანტური მოთხოვნები უარყოფენ `range`-ს და `step`-ს.
- `list_pulse_labels` იღებს `signal`-ს. `label`-ის გარეშე, ის ჩამოთვლის ლეიბლების სახელებს; `label`-ით, ის ჩამოთვლის იმ ლეიბლის მნიშვნელობებს. მეტრიკებისთვის, `__name__` ჩამოთვლის მეტრიკების სახელებს, ხოლო ნებისმიერი სხვა ლეიბლის მნიშვნელობები მოითხოვს `match`-ს, სერიის სელექტორს, როგორიცაა `up`. ლოგების და ტრეისის ლეიბლის მნიშვნელობები იღებენ `filters`-ს; ტრეისის ლეიბლის სახელები მოდის ტრეისის სქემიდან და არა. ლოგების და ტრეისის მნიშვნელობები შეიცავს მათი ჩანაწერების რაოდენობას ფანჯარაში, ყველაზე ხშირი პირველ რიგზე, ამიტომ ისინი ასევე ემსახურებიან დაშლას, მაგალითად, შეცდომები სერვისის მიხედვით. `search` ინარჩუნებს მხოლოდ სახელებს ან მნიშვნელობებს, რომლებიც შეიცავენ ლიტერალურ ტექსტს, და `limit` იღებს `1`–`1000`-ს (ნაგულისხმევი `100`). ლოგის ლეიბლის სახელის აღმოჩენა ამოწმებს მაქსიმუმ 1,000 განსხვავებულ ატრიბუტთა სიმრავლეს თითოეული სახისა და ჩამოთვლის მხოლოდ იმ გასაღებებს, რომლებსაც ფილტრები იღებენ.
- `search_pulse_logs` აბრუნებს მაქსიმუმ `limit` ჩანაწერს (`1`–`100`, ნაგულისხმევი `50`), `newest` ან `oldest` პირველ რიგზე, რომელთა სხეული შეიცავს `text`-ს და რომლებიც ემთხვევა ყოველ ფილტრს. თითოეული ჩანაწერი შეიცავს მის `severity_text`-ს, `body`-ს, `trace_id`-ს, `span_id`-ს, `scope_name`-ს და მის გაერთიანებულ რესურსისა და ლოგის `attributes`-ს. `span_id` და `scope_name` არის `null` Kubernetes-იდან შეგროვებული ლოგებისთვის, რომლებსაც მხოლოდ OTLP ლოგის გამგზავნები აყენებენ.
- `search_pulse_traces` აბრუნებს მაქსიმუმ `limit` სპანს, `newest`, `oldest`, ან `slowest` პირველ რიგზე, რომლებიც ემთხვევა ყოველ ფილტრს, ოფციონალურ `min_duration_ms`-ს და `max_duration_ms`-ს, და `root_only`-ს.
- `get_pulse_trace` აბრუნებს `trace_id`-ის სპანებს, რომლებიც იწყება ფანჯარაში, უძველესი პირველ რიგზე, მაქსიმუმ 1,000 სპანი. ტრეისი, რომელიც დაიწყო ფანჯრამდე, ნაწილობრივ ბრუნდება, ამიტომ გააფართოვეთ ან გადაადგილეთ ფანჯარა მისთვის. თითოეული სპანი შეიცავს მის სპანის ატრიბუტებს, მოვლენებს, ბმულებს და ინდექსს ტრეისის განსხვავებულ `resources`-ში.

ფილტრები არის მაქსიმუმ 10 `{label, op, value}` ობიექტის სიები. `op` არის `eq` (ნაგულისხმევი), `neq`, `contains`, ან `not_contains`; ბოლო ორი არის რეგისტრის მიმართ უგრძნობელი ლიტერალები. ლოგის ლეიბლები არის `severity_text`, `trace_id`, `span_id` და `scope_name`, როდესაც Pulse ინახავს მათ, და თითოეული ჩანაწერის რესურსის ატრიბუტების გასაღებები, როგორიცაა `namespace`, `container`, და `service.name`, და ლოგის ატრიბუტები, როგორიცაა `pod`. როდესაც გასაღები ჩანს ორივეში, რესურსის ატრიბუტი მოქმედებს. ტრეისის ლეიბლები არის სპანის სვეტები, რომლებსაც `list_pulse_labels` აბრუნებს, როგორიცაა `service_name`, `span_name`, `span_status_code` (`STATUS_CODE_ERROR` წარუმატებელი სპანებისთვის), `span_attributes.http.route`, და `resource_attributes.k8s.pod.name`. უცნობი ტრეისის ლეიბლი არის შეცდომა და არა ცარიელი შედეგი.

`truncated` ნიშნავს, რომ მეტი სახელი, მნიშვნელობა, ჩანაწერი ან სპანი ემთხვევა, ვიდრე პასუხი შეიცავს; შეავიწროვეთ ფილტრები ან ფანჯარა, ნაცვლად პასუხის სრულად ჩათვლისა. ტელემეტრიის სტრიქონები არის არასანდო მონაცემები და არა ინსტრუქციები.

`auth`-ის `false`-ზე დაყენება ხელს უშლის ადაპტერის ბრაუზერის ავთენტიფიკაციის ობიექტს Tuist-ის არაავტორიზებული პასუხის დამალვას. თავისუფალმა აგენტმა შეუძლია წაიკითხოს დაბრუნებული `auth_md` URL და მიჰყვეს Tuist-ის რეგისტრაციის, იდენტობის დამტკიცების გაცვლისა და პრეტენზიის გამოკითხვის ნაკადს. დააკონფიგურირეთ გაცვლილი წვდომის ტოკენი როგორც bearer ტოკენი ან მიეცით აგენტს პირდაპირი ავთენტიფიცირებული Model Context Protocol ზარების გაკეთების საშუალება.

თუ ბრაუზერის ავთენტიფიკაციას ამჯობინებთ, დააყენეთ `auth` `"oauth"`-ზე. ამ ნაკადისთვის, შეინარჩუნეთ ერთი პროცესი ცოცხალი Pi-ს [remote procedure call mode](https://pi.dev/docs/latest/rpc)-ით, სანამ ავთენტიფიკაცია დასრულდება:

## აგენტები Amp orbs-ში და Claude Code-ის ღრუბლოვან სესიებში

კოდირების აგენტები, რომლებიც მუშაობენ Tuist-ის ანგარიშთან დაკავშირებულ სენდბოქსებში, შეუძლიათ ავთენტიფიცირება წერტილში საკუთარი იდენტობის ტოკენით, ბრაუზერის ან შენახული Tuist-ის რწმუნების გარეშე:

- **Amp orbs** Amp-ის სამუშაო სივრცის ან პროექტისთვის, რომელიც ანგარიშმა დააკავშირა **Settings → Integrations → Amp**-ის ქვეშ, აგზავნის orb-ის ID ტოკენს. Amp-ში დააყენეთ სერვერის `Authorization` ჰედერი მნიშვნელობაზე `Bearer ${amp:id-token}`. Amp გამოსცემს ტოკენს სერვერის URL-ის წარმოშობისთვის, ამიტომ URL უნდა იყოს ამ Tuist-ის ინსტანციის საკუთარი მისამართი და აახლებს მას ვადის გასვლამდე. სხვა წარმოშობისთვის გამოცემული ტოკენები უარყოფილია.
- **Claude Code cloud sessions** დაკავშირებული Claude Code-ის გარემოდან აგზავნის სესიის ტოკენს, რომელსაც Tuist გადასცემს მათ როგორც `TUIST_OIDC_TOKEN`. დააყენეთ ჰედერი მნიშვნელობაზე `Bearer ${TUIST_OIDC_TOKEN}`.

Tuist-ის Linux სენდბოქსები არ ამატებენ სერვერს თქვენთვის: ისინი შეიცავენ Tuist CLI-ს, რომელიც შედის სისტემაში იგივე იდენტობით, და უნარს, რომელიც ეუბნება აგენტს, როდის შეამოწმოს შედეგები პროექტის ისტორიის მიხედვით. აგენტებს MCP ინსტრუმენტების მისაცემად, დაამატეთ სერვერი თქვენს Amp ან Claude Code პარამეტრებში, ან პროექტის `.mcp.json`-ში, ზემოთ მითითებული ჰედერით.

ეს ტოკენები იძლევა მხოლოდ წაკითხვის უფლებას დაკავშირებული ანგარიშის ყველა პროექტზე: ისინი შეიცავენ `mcp` ჯგუფის წაკითხვის სკოპებს და არაფერს, რაც ქმნის, ცვლის ან შლის მონაცემებს, მაგალითად, ტესტების ჩუმად დატოვება ან გამოტოვება. სამუშაო სივრცის ან გარემოს გათიშვა წყვეტს წვდომას შემდეგ მოთხოვნაზე და წვდომა არასდროს ძლებს ტოკენზე მეტ ხანს. Amp-ის სამუშაო სივრცე, რომელიც დაკავშირებულია რამდენიმე Tuist-ის ანგარიშთან, უარყოფილია, რადგან მისი ტოკენი არ ასახელებს ერთს. როდესაც კავშირი არ არსებობს, არაავტორიზებული პასუხის `error_description` ამას აღნიშნავს.

ეს მხოლოდ წაკითხვის წვდომა ვრცელდება მხოლოდ Model Context Protocol წერტილზე. ბრძანების სტრიქონის ინსტრუმენტი და აგების სისტემის ინტეგრაციები იმავე სენდბოქსში კვლავ ცვლიან ტოკენს კავშირის CI წვდომისთვის.

## WebMCP

ბრაუზერებში, რომლებიც მხარს უჭერენ [WebMCP](https://webmachinelearning.github.io/webmcp)-ს, Tuist-ის გვერდები რეგისტრირებენ ინსტრუმენტებს `document.modelContext`-ით, რათა ბრაუზერში ჩაშენებულმა აგენტებმა შეძლონ მათი გამოძახება დამატებითი კონფიგურაციის გარეშე. გამოძახებები სრულდება Tuist-ის სერვერზე.

- **Website and documentation pages** რეგისტრირებენ დოკუმენტაციისა და წყაროს ინსტრუმენტებს (`search_tuist`, `search_tuist_code`, `list_tuist_files` და `read_tuist_file`). მათ არ სჭირდებათ თქვენი შესვლა.
- **An account's dashboard pages**, როდესაც შესული ხართ, რეგისტრირებენ Tuist-ის მხოლოდ წაკითხვის ინსტრუმენტებს ამ ანგარიშისთვის. თითოეული გვერდი რეგისტრირებს მხოლოდ იმ ინსტრუმენტებს, რასაც ის აჩვენებს, პროექტის აგების სისტემისთვის: Gradle პროექტის აგებების გვერდი იღებს Gradle-ის აგების ინსტრუმენტებს, მისი ტესტების გვერდები — ტესტისა და დაფარვის ინსტრუმენტებს, გამშვებების გვერდები — გამშვებების ინსტრუმენტებს, ხოლო სენდბოქსების გვერდები — სენდბოქსის ინსტრუმენტებს. ყოველ გვერდს ასევე აქვს დოკუმენტაციის ინსტრუმენტები, `list_projects` და `get_project`. ინსტრუმენტები მუშაობენ შესული მომხმარებლის სახელით, ამიტომ ისინი მხოლოდ იმ მონაცემებს ეწვდებიან, რომელთა წაკითხვაც შეგიძლიათ დაფლატაზე, და მხოლოდ იმ ანგარიშს, რომელსაც უყურებთ. როდესაც გადადიხართ სხვა გვერდზე ან ანგარიშზე, ინსტრუმენტები იცვლება იმ გვერდის ინსტრუმენტებით.

ინსტრუმენტები, რომლებიც ქმნიან, ცვლიან ან შლიან მონაცემებს, არ არის ხელმისაწვდომი WebMCP-ით, რადგან ბრაუზერის აგენტი იღებს ინსტრუმენტებს თქვენი დამატების გარეშე და კითხულობს აგებებისა და ტესტების მიერ წარმოქმნილ კონტენტს. დააკავშირეთ MCP კლიენტი `/mcp` წერტილთან ამ ინსტრუმენტების გამოყენებისთვის.

თუ ორგანიზაცია აიძულებს ერთჯერად შესვლას (single sign-on), შედით დაფლატაზე მისი პროვაიდერით მისი ინსტრუმენტების გამოსაყენებლად.

## აგების სისტემის ინტეგრაციები იყენებენ ორ რწმუნებას

Model Context Protocol ინსტრუმენტებისთვის გამოყენებული რწმუნება არ ავთენტიფიცირებს Gradle პლაგინს ან Bazel-ის დაშორებულ სერვისებს. სანამ აგენტი შეცვლის ან შეამოწმებს Gradle ან Bazel ინტეგრაციას, მან უნდა გაუშვას:

```bash
tuist auth whoami --url https://tuist.dev
```

თუ ეს ბრძანება არ არის ავთენტიფიცირებული, აგენტმა უნდა შეწყვიტოს მუშაობა და სთხოვოს მომხმარებელს გაუშვას:

```bash
tuist auth login --url https://tuist.dev
```

ლოკალური ან თვითმასპინძელი განლაგებისთვის, შეცვალეთ URL ორივე ბრძანებაში და `tuist.toml`-ში. შეინარჩუნეთ ჰოსტის სახელის წერა იდენტური ყველგან. მაგალითად, `localhost` და `127.0.0.1` იყენებენ ცალკე შენახულ რწმუნებებს.


## შესაძლებლობები

### ინსტრუმენტები

შემდეგი ინსტრუმენტები ხელმისაწვდომია Tuist Model Context Protocol სერვერის მეშვეობით:

ყოველი ინსტრუმენტი აქვეყნებს ადამიანისთვის წასაკითხ აღწერას ცხადი შეყვანისა და გამოტანის სქემებთან ერთად. წარმატებული გამოძახებები აბრუნებენ სტრუქტურირებულ კონტენტს, რომელიც შეესაბამება გამოცხადებულ გამოტანის სქემას, პლუს იგივე შედეგი ტექსტად სერიალიზებული კლიენტებისთვის, რომლებიც ჯერ არ მოიხმარენ სტრუქტურირებულ კონტენტს.

ინსტრუმენტები, რომლებიც იღებენ ერთი ჩანაწერის იდენტიფიკატორს, როგორიცაა `build_run_id`, `test_run_id`, `test_case_id`, `bundle_id`, `run_id`, `generation_id`, ან `cache_run_id`, ასევე იღებენ ამ ჩანაწერის Tuist დაფლატის URL-ს. ჩასვით URL პირდაპირ ბრაუზერიდან იდენტიფიკატორის მისგან ამოღების ნაცვლად.

#### უკუკავშირი

აგენტებს შეუძლიათ აცნობონ Tuist-ის გუნდს, როდესაც Tuist-ის ინსტრუმენტი ან მოთხოვნა არ მუშაობდა ისე, როგორც მოელოდნენ, მაგალითად, დამაბნეველი შედეგი, შეცდომა, მონაცემების ნაკლებობა ან შესაძლებლობის არარსებობა. აგენტებს ეთხოვებათ შესთავაზონ ანგარიში და გააგზავნონ ის მხოლოდ თქვენი თანხმობის შემდეგ. თითოეული ანგარიში ხსნის დიალოგს Tuist-ის მხარდაჭერასთან, რომელმაც შეიძლება პასუხი მოგწეროთ ელფოსტით. ანგარიში მოიცავს იმას, რასაც აგენტი ელოდა, რა მოხდა, არჩევით შეთავაზებას, თქვენს Tuist მომხმარებლის ID-ს, სახელსა და ელფოსტას, ასევე ორგანიზაციებს, რომლებსაც ეკუთვნით. აგენტებს ასევე შეუძლიათ მიუთითონ ანგარიში და პროექტი, სადაც პრობლემა მოხდა, რათა გუნდმა იცოდეს, რომელ ორგანიზაციას დაუკავშირდეს; მიღებულია მხოლოდ ის ანგარიშები, რომლებსაც თქვენ ეკუთვნით. ანგარიშების გაგზავნა შეუძლიათ მხოლოდ Tuist მომხმარებლად შესულ აგენტებს და თითოეულ მომხმარებელს შეუძლია გახსნას საათში 10-მდე ანგარიში. ინსტრუმენტი ხელმისაწვდომია მხოლოდ Tuist-ის მიერ განთავსებულ სერვერზე `https://tuist.dev/mcp`-ზე.

#### წყაროზე დაფუძნებული პასუხები

ეს მხოლოდ-წაკითხვის ინსტრუმენტები აგენტებს საშუალებას აძლევს გამოიყენონ ზუსტად ის საჯარო Tuist წყაროს რევიზია, რომელიც განთავსებულია ჰოსტინგულ სერვერთან ერთად, როგორც ჭეშმარიტების წყარო პასუხებისთვის, რომლებიც დამოკიდებულია მიმდინარე ქცევაზე. ისინი ხელმისაწვდომია მხოლოდ `https://tuist.dev/mcp`-ზე.

#### Xcode builds

Xcode, Gradle, Bazel, Mix და Cargo-სთვის შექმნილი ბილდის დეტალური ინსტრუმენტები აჩვენებენ არსებულ `custom_metadata: {tags, values}` სტრუქტურას, ინფრასტრუქტურის დაკვირვებების ჩათვლით, თუ ისინი მოწოდებულია. მნიშვნელობები რჩება სტრიქონებად და უცნობი გასაღებები ინახება. მაგალითად, `tuist.cpu.available_processors` აღწერს შესრულების დროს ხელმისაწვდომ ლოგიკურ პროცესორებს, ხოლო `tuist.gradle.max_workers` არის Gradle worker-ის ლიმიტი და `tuist.jvm.max_heap_bytes` არის JVM heap-ის ლიმიტი, არა ჰოსტის მეხსიერება. ეს არის არასანდო კლიენტის დაკვირვებები, არა ვერიფიცირებული runner-ების იდენტობები. არარსებული დაკვირვებები რჩება არარსებულად; იმპორტირებულ ლოგებს და ძველ კლიენტებს შეიძლება არ ჰქონდეთ ინფრასტრუქტურის მეტამონაცემები. ნაბიჯები ნაგულისხმევად იკრიბება Xcode ბილდების დამუშავებისას. ჩაწერილი ნაბიჯის მონაცემები ინახება 90 დღის განმავლობაში. სიის პასუხი შეიცავს `availability`-ს: `available`, როცა არსებობს ჩაწერილი ნაბიჯები, მაშინაც კი, თუ ფილტრებს არაფერი ემთხვევა; `processing`, როცა ბილდი ჯერ კიდევ მუშავდება და ნაბიჯები ჯერ არ არის; ან `unavailable`, როცა ნაბიჯები არ ჩაწერილა ან ვადა გაუვიდა.

Gradle და Bazel ნაბიჯების სიები ნაგულისხმევად აბრუნებენ 20 შედეგს (მაქსიმუმ 100), მხარდაჭერილია `search`, ზუსტი `project`, `target`, `category` და `status`, გადაფარვადი `start_ms` / `end_ms` ფილტრები (ბოლო არ არის შემცველი) და `duration_ms` ან `start_ms` დალაგება. გადასცით მიღებული ID-ები უცვლელად; ისინი შეზღუდულია მათი ბილდის ფარგლებში. სიები აჩვენებენ `time_origin`-ს და `coverage`-ს. ძველი Gradle ანგარიშები იყენებენ `first_recorded_timestamp`-ს, რადგან ბილდის დაწყება არ აიტვირთა. Bazel პროფილები აჩვენებენ ყველა ჩაწერილ ინტერვალს `trace_profile` დაფარვით და `profile_start`-ს როგორც დროის საწყისს. ძველი ბილდები ეყრდნობიან შენახულ BEP შეჯამებებს. წყაროს ჩანაწერები ვადა გაუდის 90 დღის შემდეგ. Bazel დეტალები შეიცავს სანიტიზებულ ქმედებების ლოგებს, როცა ისინი გამოქვეყნებულია. Gradle დეტალები შეცდომის შემცველი ამოცანის ან კონფიგურაციის ნაბიჯის შესახებ შეიცავს შეცდომის შეტყობინებას, რომელიც Tuist Gradle პლაგინმა დააბრუნა როგორც `log`: გამონაკლისის შეტყობინება და მისი მიზეზების ჯაჭვი, როგორც Gradle-ის კონსოლი ბეჭდავს მათ, სტეკის ტრეისების ან ამოცანის გამოტანის გარეშე, პროექტის შიგნით არსებული გზები გადაყვანილია ფარდობითად, ხოლო სერთიფიკატები და სხვა ადგილობრივი გზები დაფარულია, მაქსიმუმ 16 KiB ნაბიჯზე და 32 შეცდომის შემცველი ნაბიჯი ბილდზე. სხვა Gradle ნაბიჯებს, ძველი პლაგინის ვერსიებით მოხსენებულ ბილდებს და სერთიფიკატების გარეშე მოხსენებებს აქვთ null `log`. კონფიგურაციის ნაბიჯები აბრუნებენ `failure`-ს, როცა ისინი ვერ შესრულდნენ და `unknown`-ს სხვა შემთხვევაში. `compare_builds` მოთხოვნა იყენებს ამ დაფარვას სრული Bazel ტრეისების განსასხვავებლად შენახული შეჯამებებისგან და მიმართავს აგენტებს ნაბიჯის დეტალებისკენ ქმედებების შედეგებისა და ლოგებისთვის, სანამ ფართო გამოძახების გამოტანას შეამოწმებენ.

#### Remote execution

| ინსტრუმენტი | აღწერა | სავალდებულო პარამეტრები |
|------|-------------|---------------------|
| `get_remote_execution_activity` | ჩამოთვალეთ პროექტის მიმდინარე Bazel გამოძახებები და მისი remote ქმედებები, რომლებიც ახლა მიმდინარეობს ან რიგშია, თითოეული ქმედების გამოძახებით, მნემონიკით, სამიზნით, ქმედების digest-ით, მანქანის ზომით და დროით, როცა ის ამ მდგომარეობაში შევიდა. ქმედებები, რომლებსაც შესრულების გეიტვეი აწარმოებს VM-ზე, რომელიც წინასწარ მოამზადა, არ ჩამოითვლება მათ დასრულებამდე. | `account_handle`, `project_handle` |

`list_bazel_invocations` ფილტრები არის ზუსტი შესაბამისობები და გამოძახებები, რომლებიც ერთსა და იმავე წამში სრულდება, დალაგებულია გამოძახების ID-ით. ბოლო შეცდომის შემცველი გამოძახების საპოვნელად ბრენჩზე, გამოიძახეთ ის `status: "failure"`-ით, `git_branch`-ით და `page_size: 1`-ით. REST endpoint `GET /api/projects/{account_handle}/{project_handle}/bazel/invocations` იღებს იგივე ფილტრებს.

დააყენეთ `remote_execution: true` `list_bazel_build_steps`-ზე, რათა დაბრუნდეს მხოლოდ ის ქმედებები, რომლებსაც უსაფრთხოდ აქვთ მიბმული სერვერის ფაზების დროები ინდექსირებული პროფილებიდან. ჩამონათვალისა და დეტალური პასუხები შეიცავს არასავალდებულო nullable `remote_queue_ms`-ს, `remote_input_fetch_ms`-ს, `remote_execution_ms`-ს და `remote_output_upload_ms`-ს. მნიშვნელობები ჯამში აღებულად ითვლის ჩაწერილ ფაზებს, მათ შორის ქმედების ფარგლებში განმეორებით ცდებს; არარსებული ან null მნიშვნელობები ნიშნავს ხელმიუწვდომლობას და არა ნულს. ისინი წარმოადგენენ პროფილის დაკვირვებებს და არა გადასახადის საფუძველს ან ახალი შესრულების მტკიცებულებას, რადგან კეშირებულმა სერვერის შედეგებმა შეიძლება შეიცავდეს შესრულების მეტამონაცემებს. კლიენტის ატვირთვები გამორიცხულია. ძველმა ან გაურკვეველმა პროფილებმა შეიძლება არ დააბრუნოს შესაბამისი ქმედებები მაშინაც კი, თუ remote სამუშაო შესრულდა. step REST endpoint იღებს იგივე `remote_execution=true` ფილტრს. დაფარდის Remote execution ტაბი იყენებს იგივე მოთხოვნას და 90-დღიან შენახვას.

ტესტის ლოგები შეიცავს `target_label`-ს და ცდის `status`-ს იმ ტესტის შედეგიდან, საიდანაც ისინი მოვიდნენ, ამიტომ `target_label: "//foo:bar_test"` აბრუნებს მხოლოდ იმ სამიზნის ტესტის ლოგებს. `errors: true` აბრუნებს წარუმატებელი ცდების ტესტის ლოგებს და stderr პროგრესის ფრაგმენტებს, რომლებიც შეიცავს ხაზს Bazel-ის რეპორტიორის დასაწყისით `ERROR:`, `FAIL:` ან `TIMEOUT:`. პროგრესის გამოტანა არ მიეკუთვნება სამიზნეებს და ლოგებს, რომლებიც დაწერილია მიკუთვნების ჩაწერამდე, აქვთ ცარიელი ველები. წარუმატებელი ქმედებები და მათი საკუთარი გამოტანა ხელმისაწვდომია თითოეული სამიზნისთვის `list_bazel_build_steps`-დან, ხოლო თითოეული ტესტის შემთხვევის წარუმატებლობები — ტესტების გაშვების ინსტრუმენტებიდან.

ეს ინსტრუმენტები თანდათანობით იწყება და აბრუნებს მონაცემებს მხოლოდ იმ პროექტებისთვის, სადაც ისინი ჩართულია; სხვა პროექტებისთვის ისინი აბრუნებენ შეცდომას ცარიელი შედეგის ნაცვლად. სახე ხელმისაწვდომია მხოლოდ იმ პროექტებისთვის, რომლებიც იყენებენ მის ბილდის ინსტრუმენტთა ჯაჭვს. ინსტრუმენტები იღებენ შემოსაზღვრულ `start_at`/`end_at` ფილტრებს, `environment` (`any`, `ci`, ან `local`) და ზუსტ `branch`. `list_build_entities` იღებს `q`-ს; `list_build_entity_history` მხარს უჭერს გამჭვირვალე `after`/`before` კურსორებს. უცნობი დროის ან კეშის დაკვირვებები რჩება მიუწვდომელი ნულის ან გამოტოვების ნაცვლად. ისტორია მიუთითებს ჩაწერილ მშობელზე და ნატიურ შესრულებაზე დეტალური შესწავლისთვის არსებული გაშვების ინსტრუმენტების გამოყენებით.

`get_build_entity` მეტრიკები მოიცავს `duration_samples`-ს, დაკვირვებების რაოდენობას ჩაწერილი დროით: ნამდვილი ნულოვანი ხანგრძლივობები ითვლება, დაკარგული დრო — არა. ეს რაოდენობა შეიძლება იყოს დაკვირვებების რაოდენობაზე ნაკლები; მიუწვდომელი ხანგრძლივობის სტატისტიკა რჩება null.

Xcode მოდულების ხანგრძლივობა მოდის გაზომილი სამიზნე კომპილაციებიდან ბილდის ჟურნალებში. მოდულის კეშის გადაწყვეტები და სამიზნეები კომპილაციის გარეშე არ ამატებენ ხანგრძლივობის ნიმუშებს. კომპილაციის დაკვირვებები მიუთითებენ Xcode ბილდზე; კეშის მოვლენები მიუთითებენ გენერაციის ან კეშის ბრძანებაზე.

Bazel actions იდენტიფიცირდება სამიზნის ლეიბლით, მნემონიკით და კონფიგურირებული პირველადი გამოტანით, რაც ცალკე ქმედებებს და კონფიგურაციებს განცალკევებულს ტოვებს შეყვანაზე დამოკიდებული კეშის დიჯესტების გარეშე. ისტორია აღრიცხავს BEP-ით მოხსენებულ შესრულებებს, არა კეშის ძიებებს ან trace-profile ფაზებს. სრული შესრულების დაფარვა მოითხოვს `--build_event_publish_all_actions`-ს; არტეფაქტების მიწოდება საუკეთესო ძალისხმევით ხდება, ამიტომ დაკარგული დაკვირვებები არ არის მტკიცებულება, რომ სამუშაო არ შესრულებულა. ძველი Kura payload-ები სტაბილური იდენტობის ან შესრულების დაწყების გარეშე რჩება მიღებული, მაგრამ არაინდექსირებული. დასრულების დროის გაზომვების არარსებობა რჩება მიუწვდომელი და ნამდვილი ნულოვანი ხანგრძლივობები ითვლება.

Mix მოდულების ხანგრძლივობა ზომავს შემცველი ფაილის კომპილაციას, არა დამოუკიდებლად გაზომილ მოდულის სამუშაოს. Struo actions იყენებს გამოცხადებულ სამიზნე/შესაძლებლობა/ინდექს სლოტებს, როდესაც კლიენტმა მოახსენა სამიზნე ასოციაციები; დიაგნოსტიკური ლეიბლები მარტო არ არის სტაბილური იდენტობები. არსებული კლიენტები და გაშვების დონის ინსტრუმენტები რჩება მხარდაჭერილი უცვლელად.

Cargo crates დაჯგუფებულია ზუსტად ჩაწერილი crate root-ით, სახელით და სახით. Checkout-path ცვლილებებმა შეიძლება გაყოს ისტორიები, ხოლო ბილდის პროფილები, ფუნქციები და სამიზნე triples არ განირჩევა. ისტორია ზომავს rustc გამოძახებებს, არა ფაილზე დამოკიდებულ სამუშაოს ან კეშის მოხვედრებს; არარსებული სამუშაოები არ ამყარებს წაშლებს ან სრულ workspace ინვენტარს.

ანალიტიკის წაკითხვებს აქვს შემოსაზღვრული მეხსიერება და შესრულების დრო. თუ მოთხოვნა აღემატება ამ ლიმიტებს, ინსტრუმენტი აბრუნებს შეცდომას ცარიელი შედეგის გამოგონების ნაცვლად.

ახალი დაკვირვებები ინდექსირდება განლაგების შემდეგ; ეს ფუნქცია არ ავსებს არსებულ გაშვების ტელემეტრიას. იდენტობის მეტამონაცემები უფრო დიდხანს რჩება ვიდრე ინდივიდუალური დაკვირვებები <.localized_link href="/guides/server/data-retention">მონაცემთა შენახვის პოლიტიკის</.localized_link> ფარგლებში.

### მოვლენები

კლიენტები, რომლებიც იყენებენ უმდგომარეობიან `2026-07-28` Model Context Protocol ციკლს, შეუძლიათ გამოიძახონ `events/list` მოვლენებისა და მათი payload-ის სქემების აღმოსაჩენად:

| მოვლენა | როდის იგზავნება | გამოწერის ფილტრი |
|-------|-----------------|---------------------|
| `test_case.marked_flaky` | სატესტო შემთხვევა იცვლება არაარასტაბილურიდან არასტაბილურზე. | `account_handle`, `project_handle` |
| `build.failed` | ლოკალური ან უწყვეტი ინტეგრაციის Xcode, Gradle ან Bazel ბილდი მთავრდება შეცდომით. | `account_handle`, `project_handle` |
| `test_run.failed` | ლოკალური ან უწყვეტი ინტეგრაციის ტესტების გაშვება მთავრდება შეცდომით, შერწყმული დაყოფილი გაშვების ან მიტოვებული გაშვების ჩათვლით. | `account_handle`, `project_handle` |
| `ci_job.failed` | Tuist-ის გამშვები სამუშაო მთავრდება შეცდომით. | `account_handle` |

გამოსაწერად კლიენტი იძახებს `events/subscribe` მოვლენის სახელით, ზემოთ ჩამოთვლილი handle-ებით `arguments`-ში და `webhook` მიწოდებით, რომელიც შეიცავს `https://` callback URL-ს და `whsec_` ხელმოწერის საიდუმლოს. პროექტის მოვლენებს სჭირდება ანგარიშის წევრობა და შესაბამისი ტესტის ან ბილდის მონაცემებზე წვდომა; გამშვები სამუშაოს მოვლენებს სჭირდება ანგარიშის წევრობა და გამშვებზე წვდომა. დამოწმებულმა [`auth.md`](https://workos.com/auth-md) წვდომის ტოკენებმა, დამოწმებულმა ანგარიშის ტოკენებმა და ბრაუზერის ავტორიზაციის გრანტებმა შეუძლიათ შექმნან გამოწერები; მიწოდება ჩერდება, როდესაც შესაბამისი სერთიფიკატი აღარ არის აქტიური. თითოეულ მომხმარებელს შეუძლია ჰქონდეს 25 აქტიური გამოწერა. Tuist აგზავნის ვერიფიკაციის გამოწვევას callback-ზე გამოწერის შენახვამდე. Callback-მა უნდა დააბრუნოს ობიექტი იგივე `challenge` მნიშვნელობით. გამოწერა ძალაშია შვიდი დღის განმავლობაში ნაგულისხმევად, შეიძლება განახლდეს ხელახლა გამოწერით და წყვეტს მიწოდებას, როდესაც მომხმარებლის წვდომა ან სერთიფიკატი ამოღებულია. არასავალდებულო `ttlMs` შეზღუდულია ერთ საათსა და 30 დღეს შორის. Tuist ახდენს ვადაგასული callback-ის ხელახლა ცდას და აუქმებს გამოწერას ხუთი წუთის განმავლობაში სამი ზედიზედ ვადაგასვის შემდეგ; გამოიწერეთ ხელახლა callback-ის აღდგენის შემდეგ.

როდესაც მოვლენა ხდება, Tuist აგზავნის მის რესურსის იდენტიფიკატორს და დაფის URL-ს callback-ზე. ბილდისა და ტესტების გაშვების შეცდომები ასევე შეიცავს `is_ci`-ს და `git_branch`-ს, რათა კლიენტებმა შეძლონ ლოკალური შეცდომების იგნორირება ან ფილტრაცია ბრენჩის მიხედვით. ბილდის მოვლენები შეიცავს `build_system`-ს; გამშვები სამუშაოს მოვლენები შეიცავს როგორც `workflow_job_id`-ს, ასევე `workflow_run_id`-ს. მოთხოვნა შეიცავს გამოწერის იდენტიფიკატორს და [Standard Webhooks](https://www.standardwebhooks.com/) ხელმოწერის ჰედერებს, რათა კლიენტმა შეძლოს მისი წყაროს ვერიფიცირება. Tuist ახდენს შეცდომიანი მიწოდებების ხელახლა ცდას, ამიტომ კლიენტებმა უნდა გამოიყენონ სტაბილური `eventId` დუბლიკატების გასაფილტრად. Payload არ შეიცავს ტესტების სახელებს, ლოგებს და შეცდომის შეტყობინებებს; კლიენტს შეუძლია მიიღოს ეს დეტალები ზემოთ ჩამოთვლილი ინსტრუმენტების მეშვეობით და გადაწყვიტოს, შეატყობინოს თუ არა გუნდს ან დაიწყოს დებაგინგი. კლიენტებს შეუძლიათ შეაჩერონ მიწოდება `events/unsubscribe`-ით.

#### Gradle ინტეგრაციის მოთხოვნის ფუნქციები

`integrate_gradle_project` მოთხოვნა და `get_gradle_integration_guide` ინსტრუმენტი აღწერს სრულ დაყენების სამუშაო ნაკადს. ინსტრუმენტი ასევე არის მითითებული სერვერის ინიციალიზაციის ინსტრუქციებში, რაც მას აღმოჩენადს ხდის აგენტებისთვის, რომლებიც არ ჩამოთვლიან მოთხოვნებს.

| ფუნქცია | რას აკონფიგურირებს აგენტი |
|---------|---------------------------|
| `remote_cache` | ააქტიურებს Gradle-ის ბილდის ქეშს, აკონფიგურირებს Tuist-ის დაშორებული ქეშის ატვირთვის პოლიტიკას და რეკომენდაციას უწევს ატვირთვას მხოლოდ უწყვეტი ინტეგრაციის გამშვებებიდან ლოკალური მხოლოდ-წაკითხვის გამოყენებით. |
| `build_insights` | აყენებს Tuist Gradle პლაგინს და აკონფიგურირებს ბილდის ანალიტიკის ატვირთვის ქცევას საჭიროების შემთხვევაში. |
| `test_insights` | აყენებს Tuist Gradle პლაგინს, რათა Gradle `Test` ამოცანის შედეგები ავტომატურად აიტვირთოს. |
| `flaky_tests` | გაგიწევთ ხელმძღვანელობას არასტაბილური ტესტების აღმოჩენის დაყენებაში, Gradle Test Retry პლაგინის არასავალდებულო გამოყენებაში და ტესტების კარანტინის კონფიგურაციაში. |
| `test_sharding` | ამატებს უწყვეტი ინტეგრაციის სამუშაო ნაკადს `tuistPrepareTestShards`-ისთვის, shard-ების მატრიცის გენერაციასა და `TUIST_SHARD_INDEX`-ზე დაფუძნებულ ტესტების შესრულებას. |

როდესაც `features` გამოტოვებულია, მოთხოვნა სთხოვს აგენტს დააზუსტოს, რომელი ინტეგრაციები სურს მომხმარებელს ან გამოიტანოს უმცირესი სასარგებლო ნაკრები მოთხოვნიდან Gradle პროექტის რედაქტირებამდე.

#### Xcode-ის ინტეგრაციის მოთხოვნის ფუნქციები

`integrate_xcode_project` მოთხოვნა აღწერს ყველა Xcode-ის ინტეგრაციას, რომელსაც Tuist მხარდაჭერს:

| ფუნქცია | რას აკონფიგურირებს აგენტი |
|---------|---------------------------|
| `xcode_cache` | აკონფიგურირებს `tuist setup cache`-ს, გენერირებული პროექტის ქეშის პარამეტრებს, Xcode-ის ქეშის ხელით შედგენის პარამეტრებს და ატვირთვის პოლიტიკას, რომელიც შემოიფარგლება უწყვეტი ინტეგრაციის გამშვებებით. |
| `build_insights` | აკონფიგურირებს `tuist inspect build`-ს, `tuist xcodebuild`-ს, `-resultBundlePath`-ს და არასავალდებულო მანქანურ მეტრიკებს `tuist setup insights`-ის საშუალებით. |
| `test_insights` | აკონფიგურირებს `tuist inspect test`-ს, სქემის ტესტის post-actions-ებს და შედეგების ბანდლის გენერაციას უწყვეტი ინტეგრაციის ტესტების გაშვებებისთვის. |
| `test_sharding` | ამატებს Xcode-ის ან გენერირებული პროექტის shard-ების დაგეგმვისა და shard-ების შესრულების სამუშაო ნაკადს `TUIST_SHARD_INDEX`-ით. |

როდესაც `features` გამოტოვებულია, მოთხოვნა სთხოვს აგენტს დააზუსტოს, რომელი ინტეგრაციები სურს მომხმარებელს ან გამოიტანოს უმცირესი სასარგებლო ნაკრები მოთხოვნიდან Xcode პროექტის რედაქტირებამდე.
