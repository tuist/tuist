# Model Context Protocol

[Model Context Protocol (MCP)](https://modelcontextprotocol.io/docs/getting-started/intro) არის ღია სტანდარტი, რომელიც საშუალებას აძლევს ხელოვნური ინტელექტის აგენტებს ურთიერთქმედონ გარე სერვისებთან და მონაცემთა წყაროებთან. ის უზრუნველყოფს ისეთი აპლიკაციების, როგორიცაა [Claude](https://claude.ai/), [Claude Code](https://docs.anthropic.com/en/docs/claude-code), [Codex](https://developers.openai.com/codex/), და რედაქტორების, როგორიცაა [Zed](https://zed.dev), [Cursor](https://www.cursor.com) ან [Visual Studio Code](https://code.visualstudio.com), თავსებადობას Tuist-თან.

Tuist მასპინძლობს Model Context Protocol-ის სერვერულ ბოლოწერტილს მისამართზე `https://tuist.dev/mcp`. მასზე თქვენი კლიენტის მიერთებით, აგენტებს შეუძლიათ წვდომა ჰქონდეთ თქვენს Tuist პროექტის მონაცემებზე, მათ შორის ტესტების ანალიტიკაზე, არასტაბილური ტესტების ანალიზზე და სხვა. ინსტრუმენტების უმეტესობა მხოლოდ წაკითხვის რეჟიმშია და შემოსაზღვრულია ავთენტიკირებული Tuist პროექტის მონაცემებით. ანგარიშის კონფიგურაციის ინსტრუმენტებს შეუძლიათ ანგარიშების ჩამოთვლა, ორგანიზაციების შექმნა, პროექტების შექმნა და არსებული მომხმარებლების დამატება ორგანიზაციებში, როდესაც ავთენტიკირებულ მომხმარებელს აქვს საჭირო ნებართვები. ყოველი ინსტრუმენტი აცხადებს ანოტაციებს, რომლებიც მიუთითებს, არის თუ არა ის მხოლოდ წაკითხვის რეჟიმში, შეუძლია თუ არა მას გამოიწვიოს ძნელად შექცევადი ცვლილება და შეუძლია თუ არა შეცვალოს საჯარო ინტერნეტის მდგომარეობა. ანგარიშის კონფიგურაციის ინსტრუმენტები მოითხოვს მომხმარებლის ავთენტიკაციას. ისინი არ არის ხელმისაწვდომი პროექტის ტოკენებისთვის ან ჩვეულებრივი ანგარიშის ტოკენებისთვის. როდესაც მომხმარებელი ავტორიზებს კლიენტს ბრაუზერში ან ითხოვს `auth.md` რეგისტრაციას, Tuist ამ სერთიფიკატს ასოცირდება მომხმარებელთან მხოლოდ Model Context Protocol-ის ბოლოწერტილზე, რათა კონფიგურაციის ინსტრუმენტებმა შეძლონ მოთხოვნილი სამუშაო პროცესის დასრულება.

Tuist ახორციელებს [2026-07-28 პროტოკოლს](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http). მოთხოვნები არის stateless: კლიენტები აგზავნიან თავიანთ პროტოკოლის მეტამონაცემებს ყოველ მოთხოვნასთან ერთად და შეუძლიათ პირდაპირ გამოიძახონ ინსტრუმენტები ინიციალიზაციის გარეშე. `server/discover` აბრუნებს სერვერის იდენტობას, შესაძლებლობებს, მხარდაჭერილ ვერსიებს და ინსტრუქციებს. არ არსებობს სესიის იდენტიფიკატორები ან დამოუკიდებელი მოვლენების ნაკადები. კლიენტები, რომლებიც იყენებენ 2025-06-18 ან 2025-03-26 ინიციალიზაციის ნაკადს, კვლავ მხარდაჭერილია; ისინიც მუშაობენ სერვერის სესიების გარეშე.

## Model Context Protocol versus skills

Model Context Protocol-ის ინსტრუმენტები და <.localized_link href="/guides/features/agentic-coding/skills">skills</.localized_link> შეიძლება ემთხვეოდნენ ფუნქციებით. ამჟამინდელი გადაკვეთის გათვალისწინებით, აირჩიეთ ერთი მიდგომა სამუშაო პროცესისთვის და გამოიყენეთ ის თანმიმდევრულად, ნაცვლად იმისა, რომ ორივე აურიოთ ერთსა და იმავე ნაკადში.

კლიენტებისთვის, რომლებიც მხარს უჭერენ პლაგინების ინსტალაციას, გამოიყენეთ <.localized_link href="/guides/features/agentic-coding/plugins">Tuist plugins</.localized_link> ორივეს ერთად ინსტალაციისთვის.

## კონფიგურაცია

დაამატეთ `https://tuist.dev/mcp` როგორც დისტანციური Model Context Protocol სერვერი თქვენს კლიენტში. სერვერის ინიციალიზაციის ინსტრუქციები და საჯარო სერვერის ბარათი აღწერს OAuth 2.0-ს დინამიური კლიენტის რეგისტრაციით და სტანდარტული ბრაუზერის ავტორიზაციის ნაკადით პირდაპირ, აგენტებისგან გარე ავთენტიკაციის დოკუმენტების მოთხოვნის ან მათზე მიმართვის გარეშე. ეს სერვერის მასშტაბის ინსტრუქციები ინარჩუნებს სამუშაო პროცესის მითითებებს ზოგადს: ინსტრუმენტის ავთენტიკაცია არ ავთენტიკაციებს ლოკალურ ბრძანების ხაზის ინსტრუმენტებს ან აგების სისტემის ინტეგრაციებს და აგენტებმა უნდა გადაამოწმონ მოთხოვნილი ცვლილებები შესაბამისი Tuist ინსტრუმენტების მეშვეობით. აგების სისტემის სპეციფიკური კონფიგურაცია და ავთენტიკაციის შემოწმებები დოკუმენტირებულია ინტეგრაციის სახელმძღვანელოებში და მოთხოვნებში. Tuist კვლავ აცხადებს როგორც [Open Authorization](https://oauth.net/2/)-ის აღმოჩენის მეტამონაცემებს, ასევე მიმდინარე [auth.md პროტოკოლს](https://workos.com/auth-md) მისამართზე `https://tuist.dev/auth.md` ცალ-ცალკე.

ბოლოწერტილი იღებს stateless `2026-07-28` Model Context Protocol მოთხოვნის სიცოცხლის ციკლს, `server/discover`-ის ჩათვლით, ძველ სესიაზე დაფუძნებულ სიცოცხლის ციკლთან ერთად. არსებულ კლიენტებს შეუძლიათ განაგრძონ თავიანთი მიმდინარე მიერთების მეთოდის გამოყენება.

კლიენტებს, რომლებიც მხარს უჭერენ Model Context Protocol-ის მოვლენებს, შეუძლიათ გამოიწერონ პროექტის მოვლენები. იხილეთ [მოვლენები](#events) ხელმისაწვდომი მოვლენებისა და მიწოდების მოთხოვნებისთვის.

კლიენტებს, რომლებიც უკვე მხარს უჭერენ დისტანციურ ბრაუზერის ავთენტიკაციას, შეუძლიათ განაგრძონ ავთენტიკაცია ბრაუზერში. კლიენტებს და აგენტებს, რომლებიც მხარს უჭერენ `auth.md`, შეუძლიათ ანონიმურად დარეგისტრირდნენ, წარადგინონ სანდო პროვაიდერის იდენტობის დამტკიცება ან დაიწყონ სერვისით ავთენტიკირებული ელფოსტის მოთხოვნა. რეგისტრაცია აბრუნებს Tuist-ით ხელმოწერილ იდენტობის დამტკიცებას, რომელსაც აგენტი ცვლის სტანდარტულ ტოკენის ბოლოწერტილზე ერთსაათიანი წვდომის ტოკენისთვის. Tuist აქვეყნებს თავის საჯარო ხელმოწერის გასაღებს და მხარს უჭერს სტანდარტულ ტოკენის გაუქმებას და პროვაიდერის უსაფრთხოების მოვლენების მიწოდებას.

არაავთენტიკირებულმა აგენტმა უნდა წაიკითხოს `WWW-Authenticate` ჰედერი, რომელიც დაბრუნდა Model Context Protocol-ის ბოლოწერტილიდან, მიიღოს დაცული რესურსის მეტამონაცემები, მიიღოს ავტორიზაციის სერვერის მეტამონაცემები და მიჰყვეს მის `agent_auth.skill` URL-ს. Tuist ასევე აბრუნებს იგივე ლოკალურ `auth_md` URL-ს არაავტორიზებული პასუხის სხეულში, რათა ენის მოდელზე დაფუძნებულმა კლიენტებმა შეძლონ ნაკადის აღმოჩენა ნატიური კლიენტის ინტეგრაციაზე დაყრდნობის გარეშე. განლაგების ლოკალური დოკუმენტი არის ჭეშმარიტების წყარო ბოლოწერტილის სახელების, მოთხოვნის სხეულების, მოთხოვნის polling-ისა და დამტკიცების გაცვლისთვის.

სანამ აგენტი დაიწყებს ელფოსტის მოთხოვნას, მან უნდა სთხოვოს მომხმარებელს დაადასტუროს ელფოსტის მისამართი მათი Tuist ანგარიშისთვის. მან არ უნდა გამოიტანოს ეს მისამართი პროვაიდერის პროფილიდან, Git კონფიგურაციიდან, გარემოს ცვლადიდან ან სესიის მეტამონაცემებიდან.

ბოლოწერტილი იყენებს `mcp` scope-ების ჯგუფს. ანონიმურმა pre-claim სერთიფიკატმა შეიძლება აღმოაჩინოს შესაძლებლობები და წაიკითხოს საჯარო ინტეგრაციის მითითებები, მაგრამ ის არ განიხილება როგორც შესული მომხმარებელი. ბრაუზერის ავტორიზაციის ან მოთხოვნის შემდეგ, სერთიფიკატი არის მომხმარებელზე ორიენტირებული და თითოეული ინსტრუმენტი იყენებს იგივე ავტორიზაციის შემოწმებებს, რაც dashboard-ზე. დეტალებისთვის იხილეთ <.localized_link href="/guides/server/authentication#scope-groups">scope-ების ჯგუფების დოკუმენტაცია</.localized_link>.

ინსტრუმენტები წვდომას ახდენენ იმ პროექტებზე, რომლებსაც ავთორიზებული მომხმარებელი უკვე კითხულობს. Xcode-ისა და Gradle-ის ბილდის ინსტრუმენტები იღებენ ბილდის UUID-ს ან დაშბორდის URL-ს. UUID-მ ზუსტად ერთი პროექტი უნდა განსაზღვროს; თუ ის რამდენიმე პროექტში ჩანს, ინსტრუმენტი აბრუნებს „არ არის ნაპოვნი“-ს სხვა პროექტის ანგარიშის შერჩევის ნაცვლად. პროექტის ფარგლებში შეზღუდული დაშბორდისა და API-ის წაკითხვა კვლავ ხელმისაწვდომია. მოხსენებული აქტორის იდენტიფიკატორები არიან დაუდასტურებელი სახელები, არა სერთიფიკატები ან დამატებითი წვდომის უფლებები.

ბილდის სიისა და დეტალური ინფორმაციის ინსტრუმენტები აჩვენებენ არასავალდებულო `tuist_version` მეტამონაცემებს: Xcode-ისა და Cargo-სთვის — Tuist CLI, Gradle-ისთვის — Tuist Gradle პლაგინი, ხოლო Mix-ისთვის — `tuist_ex` ბიბლიოთეკა. Xcode ასევე აჩვენებს `tuist_generation_version`-ს თავის დაკავშირებული პროექტის გენერაციის მოვლენიდან, რომელიც შეიძლება განსხვავდებოდეს ატვირთვის CLI-სგან. გამოტოვებული მნიშვნელობები არის null, არა სერვერიდან ან სხვა ანგარიშიდან გამოყვანილი. Bazel იყენებს თავის არსებულ `bazel_version`-ს; Once-ის გაშვების დეტალები აჩვენებენ `once_version`-ს. ეს ველები აღწერენ მოხსენებულ ვერსიებს, არა დადასტურებულ იდენტობას ან სადენის კონტრაქტის ვერსიებს. ## ბილდის სისტემის ინტეგრაციები იყენებენ ორ სერთიფიკატს

Model Context Protocol ინსტრუმენტებისთვის გამოყენებული სერთიფიკატი არ ახდენს Gradle პლაგინის ან Bazel-ის დისტანციური სერვისების ავთენტიკაციას. სანამ აგენტი შეცვლის ან შეამოწმებს Gradle ან Bazel ინტეგრაციას, მან უნდა გაუშვას:

```bash
tuist auth whoami --url https://tuist.dev
```

თუ ეს ბრძანება არ არის ავთენტიკირებული, აგენტმა უნდა შეწყვიტოს მოქმედება და სთხოვოს მომხმარებელს გაუშვას:

```bash
tuist auth login --url https://tuist.dev
```

ლოკალური ან თვითდაჰოსტული განლაგებისთვის, შეცვალეთ URL ორივე ბრძანებაში და `tuist.toml`-ში. შეინარჩუნეთ ჰოსტის სახელის წერა იდენტური ყველგან. მაგალითად, `localhost` და `127.0.0.1` იყენებენ ცალკე შენახულ სერთიფიკატებს.

თავსებადი კლიენტები იღებენ ფაქტობრივ აღწერილობებს ინსტრუმენტების წყაროს რევიზიის, ბმულებისა და შედეგის ლიმიტების შესახებ ინიციალიზაციის დროს, inline OAuth ავთენტიკაციის ინფორმაციასთან ერთად. ეს აღწერილობები არ განსაზღვრავენ პასუხის სტილს ან ვერიფიკაციის სამუშაო ნაკადს. მომხმარებლებს შეუძლიათ პირდაპირ დასვან კითხვა `ask_tuist` მოთხოვნის გამოძახების გარეშე; მოთხოვნა რჩება ხელმისაწვდომი ცალსახა წყაროზე დაფუძნებული სამუშაო ნაკადისთვის.

ყველა ოპერაციას აქვს ფიქსირებული ლიმიტები კონკურენტულობის, ხანგრძლივობის, გადაადგილების, წაკითხული ბაიტებისა და პასუხის ზომისთვის. ძიებისა და ჩამონათვალის შედეგები მოიცავს `truncated` და `truncation_reason` ველებს. როდესაც შედეგი შემოკლებულია, შეავიწროვეთ გზა, ფაილის ნიმუში ან საძიებო ტერმინი შედეგის ამომწურავად მიჩნევის ნაცვლად.

ნაბიჯები ნაგულისხმევად იკრიბება Xcode-ის ბილდების დამუშავებისას. ჩაწერილი ნაბიჯის მონაცემები ინახება 90 დღის განმავლობაში. სიის პასუხი შეიცავს `availability`: `available`, როცა ჩაწერილი ნაბიჯები არსებობს, მაშინაც კი, თუ ფილტრები არაფერს ემთხვევა; `processing`, როცა ბილდი ჯერ კიდევ მუშავდება და ნაბიჯები ჯერ არ აქვს; ან `unavailable`, როცა ნაბიჯები არ ჩაწერილა ან ვადა გაუვიდა.

ეს ინსტრუმენტები თანდათანობით იწერება და აბრუნებენ მონაცემებს მხოლოდ იმ პროექტებისთვის, სადაც ისინი ჩართულია; სხვა პროექტებისთვის ისინი ცარიელი შედეგის ნაცვლად შეცდომას აბრუნებენ. ტიპი ხელმისაწვდომია მხოლოდ იმ პროექტებისთვის, რომლებიც იყენებენ შესაბამის ბილდის ხელსაწყოთა ნაკრებს. ინსტრუმენტები იღებენ შემოსაზღვრულ `start_at`/`end_at` ფილტრებს, `environment` (`any`, `ci` ან `local`) და ზუსტ `branch`. `list_build_entities` იღებს `q`-ს; `list_build_entity_history` მხარს უჭერს გამჭვირვალე `after`/`before` კურსორებს. უცნობი დროის ან ქეშის დაკვირვებები რჩება მიუწვდომელი, ნულის ან გამოტოვების ნაცვლად. ისტორია მიუთითებს ჩაწერილ მშობელზე და ნატიურ შესრულებაზე, რათა არსებული გაშვების ინსტრუმენტების გამოყენებით შესაძლებელი იყოს დეტალური ანალიზი.

`get_build_entity` მეტრიკები მოიცავს `duration_samples`-ს, დაკვირვებების რაოდენობას ჩაწერილი დროით: რეალური ნულოვანი ხანგრძლივობები ითვლება, ხოლო დაკარგული დრო — არა. ეს რაოდენობა შეიძლება იყოს დაკვირვებების რაოდენობაზე ნაკლები; მიუწვდომელი ხანგრძლივობის სტატისტიკა რჩება null.

Xcode-ის მოდულების ხანგრძლივობა მოდის ბილდის ჟურნალებში გაზომილი სამიზნე კომპილაციებიდან. მოდულის ქეშის ამოხსნები და სამიზნეები კომპილაციის გარეშე არ მონაწილეობენ ხანგრძლივობის ნიმუშებში. კომპილაციის დაკვირვებები მიუთითებენ Xcode-ის ბილდზე; ქეშის მოვლენები მიუთითებენ გენერაციის ან ქეშის ბრძანებაზე.

Bazel-ის მოქმედებები იდენტიფიცირდება სამიზნის ლეიბლით, მნემონიკით და კონფიგურირებული ძირითადი გამომავალით, რაც ცალკეულ მოქმედებებსა და კონფიგურაციებს განცალკევებულს ტოვებს შეყვანაზე დამოკიდებული ქეშის დაიჯესტების გარეშე. ისტორია იწერს BEP-ით მოხსენებულ შესრულებებს, არა ქეშის ძიებებს ან trace-profile ფაზებს. სრული შესრულების დაფარვა მოითხოვს `--build_event_publish_all_actions`-ს; არტეფაქტების მიწოდება საუკეთესო ძალისხმევით ხდება, ამიტომ დაკარგული დაკვირვებები არ არის იმის მტკიცებულება, რომ სამუშაო არ შესრულებულა. უფრო ძველი Kura პეილოადები სტაბილური იდენტობის ან შესრულების დაწყების გარეშე რჩება მიღებული, მაგრამ არაინდექსირებული. დასრულების დროის გაზომვების არარსებობა რჩება მიუწვდომელი და რეალური ნულოვანი ხანგრძლივობები ითვლება.

Mix-ის მოდულების ხანგრძლივობა ზომავს შემცველი ფაილის კომპილაციას, არა დამოუკიდებლად გაზომილ მოდულურ სამუშაოს. Once-ის მოქმედებები იყენებენ გამოცხადებულ სამიზნე/შესაძლებლობა/ინდექსის სლოტებს, როდესაც კლიენტმა მოახსენა სამიზნე ასოციაციები; მხოლოდ დიაგნოსტიკური ლეიბლები არ არის სტაბილური იდენტობები. არსებული კლიენტები და გაშვების დონის ინსტრუმენტები რჩება უცვლელად მხარდაჭერილი.

ანალიტიკის წაკითხვებს აქვს შემოსაზღვრული მეხსიერება და შესრულების დრო. თუ მოთხოვნა აღემატება ამ ლიმიტებს, ინსტრუმენტი აბრუნებს შეცდომას ცარიელი შედეგის გამოგონების ნაცვლად.

ახალი დაკვირვებები ინდექსირდება განლაგების შემდეგ; ეს ფუნქცია არ ავსებს არსებულ გაშვების ტელემეტრიას. იდენტობის მეტამონაცემები ინდივიდუალურ დაკვირვებებზე უფრო დიდხანს რჩება <.localized_link href="/guides/server/data-retention">მონაცემთა შენახვის პოლიტიკის</.localized_link> შესაბამისად.

### მოვლენები

კლიენტები, რომლებიც იყენებენ უმდგომარეობიან `2026-07-28` Model Context Protocol სიცოცხლის ციკლს, შეუძლიათ გამოიძახონ `events/list` მოვლენებისა და მათი payload სქემების აღმოსაჩენად:

| მოვლენა | როდის იგზავნება | გამოწერის ფილტრი |
|-------|-----------------|---------------------|
| `test_case.marked_flaky` | სატესტო შემთხვევა იცვლება არაარასტაბილურიდან არასტაბილურად. | `account_handle`, `project_handle` |
| `build.failed` | ლოკალური ან უწყვეტი ინტეგრაციის Xcode, Gradle ან Bazel ბილდი სრულდება შეცდომით. | `account_handle`, `project_handle` |
| `test_run.failed` | ლოკალური ან უწყვეტი ინტეგრაციის ტესტების გაშვება სრულდება შეცდომით, შერწყმული შარდირებული გაშვების ან მიტოვებული გაშვების ჩათვლით. | `account_handle`, `project_handle` |
| `ci_job.failed` | Tuist runner-ის სამუშაო სრულდება შეცდომით. | `account_handle` |

გამოწერისთვის, კლიენტი იძახებს `events/subscribe` მოვლენის სახელით, ზემოთ ჩამოთვლილი handle-ებით `arguments`-ში და `webhook` მიწოდებით, რომელიც შეიცავს `https://` callback URL-ს და `whsec_` ხელმოწერის საიდუმლოს. პროექტის მოვლენები საჭიროებს ანგარიშის წევრობას და წვდომას შესაბამის ტესტის ან ბილდის მონაცემებზე; runner-ის სამუშაოს მოვლენები საჭიროებს ანგარიშის წევრობას და runner-ის წაკითხვის წვდომას. დადასტურებულმა [`auth.md`](https://workos.com/auth-md) წვდომის ტოკენებმა, დადასტურებულმა ანგარიშის ტოკენებმა და ბრაუზერის ავტორიზაციის გრანტებმა შეიძლება შექმნან გამოწერები; მიწოდება ჩერდება, როდესაც შესაბამისი სერთიფიკატი აღარ არის აქტიური. თითოეულ მომხმარებელს შეუძლია შეინარჩუნოს 25-მდე აქტიური გამოწერა. Tuist აგზავნის ვერიფიკაციის გამოწვევას callback-ზე გამოწერის შენახვამდე. callback-მა უნდა დააბრუნოს ობიექტი, რომელიც შეიცავს იგივე `challenge` მნიშვნელობას. გამოწერა ნაგულისხმევად შვიდი დღე გრძელდება, შეიძლება განახლდეს ხელახლა გამოწერით და წყვეტს მიწოდებას, როდესაც მომხმარებლის წვდომა ან სერთიფიკატი იხსნება. არასავალდებულო `ttlMs` შეზღუდულია ერთ საათსა და 30 დღეს შორის. Tuist ახდენს დროის ამოწურული callback-ის ხელახლა ცდას და აუქმებს მას მინიმუმ სამი თანმიმდევრული დროის ამოწურვის შემდეგ, რომლებიც ხუთ წუთს მოიცავს; გამოიწერეთ ხელახლა callback-ის აღდგენის შემდეგ.

როდესაც ხდება მოვლენა, Tuist აგზავნის მის რესურსის იდენტიფიკატორს და დაშბორდის URL-ს callback-ზე. ბილდისა და ტესტების გაშვების შეცდომები ასევე შეიცავს `is_ci`-ს და `git_branch`-ს, რათა კლიენტებმა შეძლონ ლოკალური შეცდომების იგნორირება ან ფილტრაცია ბრენჩის მიხედვით. ბილდის მოვლენები შეიცავს `build_system`-ს; რანერის სამუშაოს მოვლენები შეიცავს როგორც `workflow_job_id`-ს, ასევე `workflow_run_id`-ს. მოთხოვნა შეიცავს გამოწერის იდენტიფიკატორს და [Standard Webhooks](https://www.standardwebhooks.com/) ხელმოწერის ჰედერებს, რათა კლიენტმა შეძლოს მისი წარმომავლობის ვერიფიკაცია. Tuist ახდენს ჩავარდნილი მიწოდებების ხელახლა ცდას, ამიტომ კლიენტებმა უნდა გამოიყენონ სტაბილური `eventId` დუბლიკატების გამოსარიცხად. პეილოდი არ შეიცავს ტესტების სახელებს, ლოგებს და შეცდომის შეტყობინებებს; კლიენტს შეუძლია მიიღოს ეს დეტალები ზემოთ ჩამოთვლილი ინსტრუმენტების მეშვეობით და გადაწყვიტოს, შეატყობინოს თუ არა გუნდს ან დაიწყოს დებაგინგი. კლიენტებმა შეუძლიათ შეაჩერონ მიწოდება `events/unsubscribe`-ის მეშვეობით.

#### Gradle ინტეგრაციის პრომპტის ფუნქციები

`integrate_gradle_project` პრომპტი და `get_gradle_integration_guide` ინსტრუმენტი აღწერს სრულ დაყენების სამუშაო ნაკადს. ინსტრუმენტი ასევე არის მითითებული სერვერის ინიციალიზაციის ინსტრუქციებში, რაც მას აღმოჩენადს ხდის აგენტებისთვის, რომლებიც არ აკეთებენ პრომპტების ჩამონათვალს.

| ფუნქცია | რას აკონფიგურირებს აგენტი |
|---------|---------------------------|
| `remote_cache` | ააქტიურებს Gradle-ის ბილდის ქეშს, აკონფიგურირებს Tuist-ის შორეული ქეშის ატვირთვის პოლიტიკას და ურჩევს ატვირთვას მხოლოდ უწყვეტი ინტეგრაციის რანერებიდან ლოკალური მხოლოდ-წაკითხვადი გამოყენებით. |
| `build_insights` | აყენებს Tuist Gradle პლაგინს და აკონფიგურირებს ბილდის ანალიტიკის ატვირთვის ქცევას საჭიროების შემთხვევაში. |
| `test_insights` | აყენებს Tuist Gradle პლაგინს, რათა Gradle `Test` ამოცანის შედეგები აიტვირთოს ავტომატურად. |
| `flaky_tests` | მიმართავს არასტაბილური ტესტების აღმოჩენის დაყენებაში, Gradle Test Retry პლაგინის არააუცილებელ გამოყენებაში და ტესტების კარანტინის კონფიგურაციაში. |
| `test_sharding` | ამატებს უწყვეტი ინტეგრაციის სამუშაო ნაკადს `tuistPrepareTestShards`-ისთვის, შარდების მატრიცის გენერაციისთვის და `TUIST_SHARD_INDEX`-ზე დაფუძნებული ტესტების შესრულებისთვის. |

როდესაც `features` გამოტოვებულია, პრომპტი სთხოვს აგენტს განაზღუროს, თუ რომელი ინტეგრაციები სურს მომხმარებელს ან გამოიტანოს უმცირესი სასარგებლო ნაკრები მოთხოვნიდან Gradle პროექტის რედაქტირებამდე.

#### Xcode ინტეგრაციის პრომპტის ფუნქციები

`integrate_xcode_project` პრომპტი აღწერს ყველა Xcode ინტეგრაციას, რომელსაც Tuist მხარს უჭერს:

| ფუნქცია | რას აკონფიგურირებს აგენტი |
|---------|---------------------------|
| `xcode_cache` | აკონფიგურირებს `tuist setup cache`-ს, გენერირებული პროექტის ქეშის პარამეტრებს, Xcode ქეშის ხელით ბილდის პარამეტრებს და ატვირთვის პოლიტიკას, რომელიც შემოიფარგლება უწყვეტი ინტეგრაციის რანერებით. |
| `build_insights` | აკონფიგურირებს `tuist inspect build`-ს, `tuist xcodebuild`-ს, `-resultBundlePath`-ს და არააუცილებელ მანქანურ მეტრიკებს `tuist setup insights`-ის მეშვეობით. |
| `test_insights` | აკონფიგურირებს `tuist inspect test`-ს, სქემის ტესტის post-actions-ებს და შედეგების ბანდლის გენერაციას უწყვეტი ინტეგრაციის ტესტების გაშვებისთვის. |
| `test_sharding` | ამატებს Xcode-ის ან გენერირებული პროექტის შარდების დაგეგმვისა და შარდების შესრულების სამუშაო ნაკადს `TUIST_SHARD_INDEX`-ით. |

როდესაც `features` გამოტოვებულია, პრომპტი სთხოვს აგენტს განაზღუროს, თუ რომელი ინტეგრაციები სურს მომხმარებელს ან გამოიტანოს უმცირესი სასარგებლო ნაკრები მოთხოვნიდან Xcode პროექტის რედაქტირებამდე.
