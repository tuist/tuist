# Model Context Protocol

[Model Context Protocol (MCP)](https://modelcontextprotocol.io/docs/getting-started/intro) არის ღია სტანდარტი, რომელიც საშუალებას აძლევს ხელოვნური ინტელექტის აგენტებს ურთიერთქმედონ გარე სერვისებთან და მონაცემთა წყაროებთან. ის უზრუნველყოფს [Claude](https://claude.ai/), [Claude Code](https://docs.anthropic.com/en/docs/claude-code), [Codex](https://developers.openai.com/codex/)-ისა და ისეთი რედაქტორების, როგორიცაა [Zed](https://zed.dev), [Cursor](https://www.cursor.com) ან [Visual Studio Code](https://code.visualstudio.com), თავსებადობას Tuist-თან.

Tuist განათავსებს Model Context Protocol-ის სერვერულ ბოლოწერტილს `https://tuist.dev/mcp` მისამართზე. მასზე თქვენი კლიენტის მიერთებით, აგენტებს შეუძლიათ მიიღონ წვდომა თქვენს Tuist პროექტის მონაცემებზე, მათ შორის ტესტების ანალიზზე, არასტაბილური ტესტების ანალიზზე და სხვა. უმეტესი ინსტრუმენტი მხოლოდ კითხვის რეჟიმშია და მოქმედებს მხოლოდ ავტორიზებული Tuist პროექტის მონაცემებზე. ანგარიშის კონფიგურაციის ინსტრუმენტებს შეუძლიათ ჩამოთვალონ ანგარიშები, შექმნან ორგანიზაციები, შექმნან პროექტები და დაამატონ არსებული მომხმარებლები ორგანიზაციებში, როდესაც ავტორიზებულ მომხმარებელს აქვს საჭირო ნებართვები. ყოველი ინსტრუმენტი აცხადებს ანოტაციებს, რომლებიც მიუთითებს, არის თუ არა ის მხოლოდ კითხვის რეჟიმში, შეუძლია თუ არა გამოიწვიოს რთულად შესაბრუნებელი ცვლილება და შეუძლია თუ არა შეცვალოს საჯარო ინტერნეტის მდგომარეობა. ანგარიშის კონფიგურაციის ინსტრუმენტები მოითხოვს მომხმარებლის ავტორიზაციას. ისინი არ არის ხელმისაწვდომი პროექტის ტოკენებისთვის ან ჩვეულებრივი ანგარიშის ტოკენებისთვის. როდესაც მომხმარებელი ავტორიზებს კლიენტს ბრაუზერში ან ითხოვს `auth.md` რეგისტრაციას, Tuist ამ სერთიფიკატს ასოცირდება მხოლოდ მომხმარებელთან Model Context Protocol ბოლოწერტილზე, რათა კონფიგურაციის ინსტრუმენტებმა შეასრულონ მოთხოვნილი სამუშაო ნაკადი.

Tuist ახორციელებს [2026-07-28 პროტოკოლს](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http). მოთხოვნები არის stateless: კლიენტები აგზავნიან თავიანთ პროტოკოლის მეტამონაცემებს ყოველ მოთხოვნასთან ერთად და შეუძლიათ პირდაპირ გამოიძახონ ინსტრუმენტები ინიციალიზაციის გარეშე. `server/discover` აბრუნებს სერვერის იდენტობას, შესაძლებლობებს, მხარდაჭერილ ვერსიებს და ინსტრუქციებს. არ არსებობს სესიის იდენტიფიკატორები ან დამოუკიდებელი მოვლენათა ნაკადები. კლიენტები, რომლებიც იყენებენ 2025-06-18 ან 2025-03-26 ინიციალიზაციის ნაკადს, კვლავ მხარდაჭერილია; ისინიც მუშაობენ სერვერის სესიების გარეშე.

## Model Context Protocol უნარების წინააღმდეგ

Model Context Protocol-ის ინსტრუმენტებსა და <.localized_link href="/guides/features/agentic-coding/skills">უნარებს</.localized_link> შორის შეიძლება იყოს გადაკვეთა ფუნქციებში. ამჟამინდელი გადაკვეთის გათვალისწინებით, აირჩიეთ ერთი მიდგომა თითოეული სამუშაო ნაკადისთვის და გამოიყენეთ ის თანმიმდევრულად, ნაცვლად იმისა, რომ ერთსა და იმავე ნაკადში აურიოთ ორივე.

კლიენტებისთვის, რომლებიც მხარს უჭერენ პლაგინების ინსტალაციას, გამოიყენეთ <.localized_link href="/guides/features/agentic-coding/plugins">Tuist პლაგინები</.localized_link> ორივეს ერთად ინსტალაციისთვის.

## კონფიგურაცია

დაამატეთ `https://tuist.dev/mcp` როგორც დისტანციური Model Context Protocol სერვერი თქვენს კლიენტში. სერვერის ინიციალიზაციის ინსტრუქციები და საჯარო სერვერის ბარათი აღწერს OAuth 2.0-ს დინამიური კლიენტის რეგისტრაციით და სტანდარტული ბრაუზერის ავტორიზაციის ნაკადით პირდაპირ, იმის გარეშე, რომ აგენტებს სთხოვონ გარე ავტორიზაციის დოკუმენტების მოძიება ან მიყოლა. ეს სერვერის დონის ინსტრუქციები ინარჩუნებს სამუშაო ნაკადის მითითებებს ზოგადს: ინსტრუმენტის ავტორიზაცია არ ავტორიზებს ადგილობრივ ბრძანების ხაზის ინსტრუმენტებს ან აგების სისტემის ინტეგრაციებს და აგენტებმა უნდა დაადასტურონ მოთხოვნილი ცვლილებები შესაბამისი Tuist ინსტრუმენტების მეშვეობით. აგების სისტემის სპეციფიკური კონფიგურაცია და ავტორიზაციის შემოწმებები დოკუმენტირებულია ინტეგრაციის სახელმძღვანელოებში და მოთხოვნებში. Tuist კვლავ აცხადებს როგორც [Open Authorization](https://oauth.net/2/) აღმოჩენის მეტამონაცემებს, ასევე მიმდინარე [auth.md პროტოკოლს](https://workos.com/auth-md) `https://tuist.dev/auth.md` მისამართზე ცალ-ცალკე.

თუ თქვენი ერთ-ერთი ორგანიზაცია აიძულებს ერთიანი შესვლის (SSO) გამოყენებას, კლიენტის ბრაუზერში ავტორიზაცია მოითხოვს სესიას, რომელიც შესულია ამ ორგანიზაციის მეშვეობით და Tuist საჭიროების შემთხვევაში ჯერ პროვაიდერთან გაგზავნით. იხილეთ <.localized_link href="/guides/integrations/authentication/sso#choose-an-enrollment-policy">ერთიანი შესვლა</.localized_link>.

ბოლოწერტილი იღებს stateless `2026-07-28` Model Context Protocol მოთხოვნის სიცოცხლის ციკლს, მათ შორის `server/discover`, ძველ სესიაზე დაფუძნებულ ციკლთან ერთად. არსებულმა კლიენტებმა შეიძლება განაგრძონ თავიანთი მიმდინარე მიერთების მეთოდის გამოყენება.

კლიენტებს, რომლებიც მხარს უჭერენ Model Context Protocol მოვლენებს, შეუძლიათ გამოიწერონ პროექტის მოვლენები. იხილეთ [მოვლენები](#events) ხელმისაწვდომი მოვლენებისა და მიწოდების მოთხოვნებისთვის.

კლიენტებს, რომლებიც უკვე მხარს უჭერენ დისტანციურ ბრაუზერის ავტორიზაციას, შეუძლიათ განაგრძონ ბრაუზერში ავტორიზაცია. კლიენტებსა და აგენტებს, რომლებიც მხარს უჭერენ `auth.md`, შეუძლიათ ანონიმურად რეგისტრაცია, წარმოადგინონ სანდო პროვაიდერის იდენტობის დამტკიცება ან დაიწყონ სერვისით ავტორიზებული ელფოსტის მოთხოვნა. რეგისტრაცია აბრუნებს Tuist-ით ხელმოწერილ იდენტობის დამტკიცებას, რომელსაც აგენტი ცვლის სტანდარტულ ტოკენის ბოლოწერტილზე ერთსაათიანი წვდომის ტოკენისთვის. Tuist აქვეყნებს თავის საჯარო ხელმოწერის გასაღებს და მხარს უჭერს სტანდარტულ ტოკენის გაუქმებასა და პროვაიდერის უსაფრთხოების მოვლენების მიწოდებას.

არაავტორიზებულმა აგენტმა უნდა წაიკითხოს `WWW-Authenticate` ჰედერი, რომელიც დაბრუნდა Model Context Protocol ბოლოწერტილის მიერ, მოიძიოს დაცული რესურსის მეტამონაცემები, მოიძიოს ავტორიზაციის სერვერის მეტამონაცემები და მიჰყვეს მის `agent_auth.skill` URL-ს. Tuist ასევე აბრუნებს იმავე ადგილობრივ `auth_md` URL-ს არაავტორიზებული პასუხის სხეულში, რათა ენის მოდელზე დაფუძნებულმა კლიენტებმა შეძლონ ნაკადის აღმოჩენა ნატიური კლიენტის ინტეგრაციაზე დამოკიდებულების გარეშე. განლაგების ადგილობრივი დოკუმენტი არის ჭეშმარიტების წყარო ბოლოწერტილის სახელების, მოთხოვნის სხეულების, მოთხოვნის გამოკითხვისა და დამტკიცების გაცვლისთვის.

სანამ აგენტი დაიწყებს ელფოსტის მოთხოვნას, მან უნდა სთხოვოს მომხმარებელს დაადასტუროს ელფოსტის მისამართი მათი Tuist ანგარიშისთვის. მან არ უნდა გამოიტანოს ეს მისამართი პროვაიდერის პროფილიდან, Git კონფიგურაციიდან, გარემოს ცვლადიდან ან სესიის მეტამონაცემებიდან.

ბოლოწერტილი იყენებს `mcp` სკოპის ჯგუფს. ანონიმურმა pre-claim სერთიფიკატს შეუძლია აღმოაჩინოს შესაძლებლობები და წაიკითხოს საჯარო ინტეგრაციის მითითებები, მაგრამ ის არ განიხილება როგორც შესული მომხმარებელი. ბრაუზერის ავტორიზაციის ან მოთხოვნის შემდეგ, სერთიფიკატი არის მომხმარებლის სკოპის და თითოეული ინსტრუმენტი იყენებს იმავე ავტორიზაციის შემოწმებებს, რასაც დაშბორდი. იხილეთ <.localized_link href="/guides/server/authentication#scope-groups">სკოპის ჯგუფების დოკუმენტაცია</.localized_link> დეტალებისთვის.

ინსტრუმენტები წყდებიან პროექტებზე, რომელთა წაკითხვაც ავტორიზებულ მომხმარებელს უკვე შეუძლია. Xcode და Gradle აგების ინსტრუმენტები იღებენ აგების UUID-ს ან დაშბორდის URL-ს. UUID-მ უნდა მიუთითოს ზუსტად ერთ პროექტზე; თუ ის ჩნდება რამდენიმე პროექტში, ინსტრუმენტი აბრუნებს „ვერ მოიძებნა“-ს, ნაცვლად იმისა, რომ აირჩიოს სხვა პროექტის ანგარიში. პროექტის სკოპის დაშბორდისა და API-ს წაკითხვები რჩება ხელმისაწვდომი. მოხსენებული აქტორის იდენტიფიკატორები არიან დაუდასტურებელი ეტიკეტები, არა სერთიფიკატები ან დამატებითი წვდომის უფლებები.

აგების სიისა და დეტალური ინფორმაციის ინსტრუმენტები აჩვენებენ არასავალდებულო `tuist_version` მეტამონაცემებს: Xcode-ისა და Cargo-სთვის — Tuist CLI, Gradle-ისთვის — Tuist Gradle პლაგინი, ხოლო Mix-ისთვის — `tuist_ex` ბიბლიოთეკა. Xcode ასევე აჩვენებს `tuist_generation_version`-ს თავის დაკავშირებული პროექტის გენერაციის მოვლენიდან, რომელიც შეიძლება განსხვავდებოდეს ატვირთვის CLI-სგან. გამოტოვებული მნიშვნელობები არის null და არ გამოიტანება სერვერიდან ან სხვა ანგარიშიდან. Bazel იყენებს არსებულ `bazel_version`-ს; Once-ის გაშვების დეტალები კი აჩვენებს `once_version`-ს. ეს ველები აღწერენ მოხსენებულ ვერსიებს და არა დადასტურებულ იდენტობას ან სადენის კონტრაქტის ვერსიებს. REST აგების ბოლოწერტილები აჩვენებენ იგივე მეტამონაცემებს. არსებული ინტეგრაციისა და ფლაკი ტესტების უნარები არ არის დამოკიდებული ვერსიის ველებზე და არ საჭიროებს სამუშაო ნაკადის ცვლილებებს.

Tuist-ის ოპერატორები, რომლებიც იკვლევენ მომხმარებლის ანგარიშს, ამას აკეთებენ Tuist-ის შიდა ოპერაციული ინსტრუმენტების მეშვეობით, რომელიც იწერს ყოველ ზარს; ამ ბოლოწერტილთან პირდაპირი კავშირი არ იძლევა წვდომას მომხმარებლის საკუთარი წევრობების გარდა.

## აგების სისტემის ინტეგრაციები იყენებენ ორ სერთიფიკატს

Model Context Protocol ინსტრუმენტებისთვის გამოყენებული სერთიფიკატი არ ავტორიზებს Gradle პლაგინს ან Bazel-ის დაშორებულ სერვისებს. სანამ აგენტი შეცვლის ან დაადასტურებს Gradle ან Bazel ინტეგრაციას, მან უნდა გაუშვას:

```bash
tuist auth whoami --url https://tuist.dev
```

თუ ეს ბრძანება არ არის ავტორიზებული, აგენტმა უნდა შეწყვიტოს მუშაობა და სთხოვოს მომხმარებელს გაუშვას:

```bash
tuist auth login --url https://tuist.dev
```

ლოკალური ან თვითმასპინძლი განლაგებისთვის, შეცვალეთ URL ორივე ბრძანებაში და `tuist.toml`-ში. შეინარჩუნეთ ჰოსტის სახელის იდენტური დაწერა ყველგან. მაგალითად, `localhost` და `127.0.0.1` იყენებენ ცალკე შენახულ სერთიფიკატებს.

შემდეგი ინსტრუმენტები ხელმისაწვდომია Tuist Model Context Protocol სერვერის მეშვეობით:

Gradle და Bazel ნაბიჯების სიები ნაგულისხმევად აბრუნებენ 20 შედეგს (მაქსიმუმ 100), მხარდაჭერილია `search`, ზუსტი `project`, `target`, `category` და `status`, გადაფარვის `start_ms` / `end_ms` ფილტრები (ბოლო არ არის შემცველი), და `duration_ms` ან `start_ms` დალაგება. გადასცეთ დაბრუნებული ID-ები უცვლელად; ისინი შეზღუდულია მათი ბილდის ფარგლებში. სიები აჩვენებენ `time_origin` და `coverage`. ძველი Gradle ანგარიშები იყენებენ `first_recorded_timestamp`-ს, რადგან ბილდის დაწყება არ აიტვირთა. Bazel პროფილები აჩვენებენ ყველა ჩაწერილ ინტერვალს `trace_profile` დაფარვით და `profile_start`-ით, როგორც დროის საწყისით. ძველი ბილდები ბრუნდებიან შენახულ BEP შეჯამებებზე. წყაროს ჩანაწერების ვადა გადის 90 დღის შემდეგ. Bazel დეტალები შეიცავს სანიტიზირებულ ქმედებების ჟურნალებს, როცა გამოქვეყნებულია; Gradle დეტალის `log` არის null. `compare_builds` მოთხოვნა იყენებს ამ დაფარვას სრული Bazel ტრეისების განსასხვავებლად შენახული შეჯამებებისგან და მიმართავს აგენტებს ნაბიჯის დეტალებისკენ ქმედებების შედეგებისა და ჟურნალებისთვის, სანამ უფრო ფართო გამოძახების გამომავალს შეამოწმებენ.

Bazel ნაბიჯის ID-ები, რომლებიც დაბრუნდა შენახული შეჯამებებიდან, რჩება წასაკითხად, თუ სრული პროფილი მოვა სიის ჩამოთვლასა და ნაბიჯის მიღებას შორის. ინდექსირებული პროფილი, რომლის ნაბიჯის მონაცემების ვადა გაუვიდა, აცხადებს ხელმისაწვდომობის არქონას. Gradle ნაბიჯების სიები შეიცავს ნულოვანი ხანგრძლივობის ქეშირებულ და გამოტოვებულ ოპერაციებს.

ეს ინსტრუმენტები თანდათანობით იწყებს მუშაობას და აბრუნებს მონაცემებს მხოლოდ იმ პროექტებისთვის, სადაც ისინი ჩართულია; სხვა პროექტებისთვის ისინი აბრუნებენ შეცდომას ცარიელი შედეგის ნაცვლად. ტიპი ხელმისაწვდომია მხოლოდ იმ პროექტებისთვის, რომლებიც იყენებენ შესაბამის ბილდის ინსტრუმენტების ჯაჭვს. ინსტრუმენტები იღებენ შემოსაზღვრულ `start_at`/`end_at` ფილტრებს, `environment` (`any`, `ci` ან `local`) და ზუსტ `branch`. `list_build_entities` იღებს `q`-ს; `list_build_entity_history` მხარს უჭერს გამჭვირვალე `after`/`before` კურსორებს. უცნობი დროის ან ქეშის დაკვირვებები რჩება მიუწვდომლად ნულის ან გამოტოვების ნაცვლად. ისტორია მიუთითებს ჩაწერილ მშობელზე და ნატიურ გაშვებაზე დეტალური ანალიზისთვის არსებული გაშვების ინსტრუმენტების გამოყენებით.

`get_build_entity` მეტრიკები მოიცავს `duration_samples`-ს, დაკვირვებების რაოდენობას ჩაწერილი დროით: რეალური ნულოვანი ხანგრძლივობები ითვლება, დაკარგული დრო კი არა. ეს რაოდენობა შეიძლება იყოს დაკვირვებების რაოდენობაზე ნაკლები; მიუწვდომელი ხანგრძლივობის სტატისტიკა რჩება null-ად.

Xcode მოდულების ხანგრძლივობა მოდის ბილდის ლოგებში გაზომილი სამიზნე კომპილაციებიდან. მოდულის ქეშის გარჩევები და სამიზნეები კომპილაციის სამუშაოს გარეშე არ მონაწილეობენ ხანგრძლივობის ნიმუშებში. კომპილაციის დაკვირვებები მიუთითებენ Xcode ბილდზე; ქეშის მოვლენები მიუთითებენ გენერაციის ან ქეშის ბრძანებაზე.

Bazel მოქმედებები იდენტიფიცირდება სამიზნე ლეიბლით, მნემონიკით და კონფიგურირებული ძირითადი გამომავალით, რაც ინარჩუნებს ცალკეულ მოქმედებებსა და კონფიგურაციებს განცალკევებულად შეყვანაზე დამოკიდებული ქეშის დაიჯესტების გარეშე. ისტორია იწერს BEP-ით შეტყობინებულ გაშვებებს, არა ქეშის ძიებებს ან ტრეისის პროფილის ფაზებს. სრული გაშვების დაფარვა მოითხოვს `--build_event_publish_all_actions`-ს; არტიფაქტების მიწოდება საუკეთესო ძალისხმევით ხდება, ამიტომ დაკარგული დაკვირვებები არ არის იმის მტკიცებულება, რომ სამუშაო არ შესრულებულა. ძველი Kura პეილოადები სტაბილური იდენტობის ან გაშვების დაწყების გარეშე რჩება მიღებულად, მაგრამ არაინდექსირებულად. დასრულების დროის გაზომვების არარსებობა რჩება მიუწვდომლად და რეალური ნულოვანი ხანგრძლივობები ითვლება.

Mix მოდულების ხანგრძლივობა ზომავს შემცველი ფაილის კომპილაციას, არა დამოუკიდებლად გაზომილ მოდულის სამუშაოს. Once მოქმედებები იყენებენ გამოცხადებულ სამიზნე/შესაძლებლობა/ინდექსის სლოტებს, როდესაც კლიენტმა შეატყობინა სამიზნე ასოციაციები; მხოლოდ დიაგნოსტიკური ლეიბლები არ არის სტაბილური იდენტობები. არსებული კლიენტები და გაშვების დონის ინსტრუმენტები რჩება მხარდაჭერილად უცვლელად.

Cargo ყუთები (crates) დაჯგუფებულია ზუსტად ჩაწერილი ყუთის ფესვით, სახელით და ტიპით. Checkout-ბილიკის ცვლილებებმა შეიძლება გაყოს ისტორიები, ხოლო ბილდის პროფილები, ფუნქციები და სამიზნე ტრიპლეტები არ განირჩევა. ისტორია ზომავს rustc გამოძახებებს, არა ფაილის დონის სამუშაოს ან ქეშის მოხვედრებს; არარსებული სამუშაოები არ ამყარებენ წაშლას ან სრულ workspace ინვენტარს.

ანალიტიკის წაკითხვებს აქვს შემოსაზღვრული მეხსიერება და შესრულების დრო. თუ მოთხოვნა აღემატება ამ ლიმიტებს, ინსტრუმენტი აბრუნებს შეცდომას ცარიელი შედეგის გამოგონების ნაცვლად.

ახალი დაკვირვებები ინდექსირდება განლაგების შემდეგ; ეს ფუნქცია არ ავსებს არსებულ გაშვების ტელემეტრიას. იდენტობის მეტამონაცემები ინახება ინდივიდუალურ დაკვირვებებზე უფრო დიდხანს <.localized_link href="/guides/server/data-retention">მონაცემთა შენახვის პოლიტიკის</.localized_link> შესაბამისად.

### მოვლენები

კლიენტები, რომლებიც იყენებენ სტეიტლეს `2026-07-28` Model Context Protocol ლაიფციკლს, შეუძლიათ გამოიძახონ `events/list` მოვლენებისა და მათი payload-ის სქემების აღმოსაჩენად:

| მოვლენა | როდის იგზავნება | გამოწერის ფილტრი |
|-------|-----------------|---------------------|
| `test_case.marked_flaky` | სატესტო შემთხვევა იცვლება არაარასტაბილურიდან არასტაბილურზე. | `account_handle`, `project_handle` |
| `build.failed` | ლოკალური ან უწყვეტი ინტეგრაციის Xcode, Gradle ან Bazel ბილდი მთავრდება შეცდომით. | `account_handle`, `project_handle` |
| `test_run.failed` | ლოკალური ან უწყვეტი ინტეგრაციის ტესტების გაშვება მთავრდება შეცდომით, შერწყმული შარდირებული გაშვების ან მიტოვებული გაშვების ჩათვლით. | `account_handle`, `project_handle` |
| `ci_job.failed` | Tuist runner-ის სამუშაო მთავრდება შეცდომით. | `account_handle` |

გამოწერისთვის კლიენტი იძახებს `events/subscribe` მოვლენის სახელით, ზემოთ ჩამოთვლილი handle-ებით `arguments`, და `webhook` მიწოდებით, რომელიც შეიცავს `https://` callback URL-ს და `whsec_` ხელმოწერის საიდუმლოს. პროექტის მოვლენები მოითხოვს ანგარიშის წევრობას და შესაბამისი ტესტის ან ბილდის მონაცემების წაკითხვის უფლებას; runner-ის სამუშაოების მოვლენები მოითხოვს ანგარიშის წევრობას და runner-ის წაკითხვის უფლებას. დამოწმებულმა [`auth.md`](https://workos.com/auth-md) access token-ებმა, დამოწმებულმა ანგარიშის token-ებმა და ბრაუზერის ავტორიზაციის გრანტებმა შეუძლიათ შექმნან გამოწერები; მიწოდება ჩერდება, როდესაც შესაბამისი credential აღარ არის აქტიური. თითოეულ მომხმარებელს შეუძლია ჰქონდეს 25-მდე აქტიური გამოწერა. Tuist აგზავნის ვერიფიკაციის challenge-ს callback-ზე გამოწერის შენახვამდე. callback-მა უნდა დააბრუნოს ობიექტი, რომელიც შეიცავს იგივე `challenge` მნიშვნელობას. გამოწერა ძალაშია შვიდი დღე ნაგულისხმევად, შეიძლება განახლდეს ხელახლა გამოწერით და წყვეტს მიწოდებას, როდესაც მომხმარებლის წვდომა ან credential ამოღებულია. არასავალდებულო `ttlMs` შემოიფარგლება ერთ საათსა და 30 დღეს შორის. Tuist ცდილობს გადაცილებულ callback-ს და აუქმებს გამოწერას სამი თანმიმდევრული გადაცილების შემდეგ, რომლებიც ხუთ წუთს ფარავს; გამოიწერეთ ხელახლა callback-ის აღდგენის შემდეგ.

როდესაც მოვლენა ხდება, Tuist აგზავნits მის რესურსის იდენტიფიკატორსა და დაშბორდის URL-ს callback-ზე. ბილდისა და ტესტების გაშვების შეცდომები ასევე შეიცავს `is_ci`-ს და `git_branch`-ს, რათა კლიენტებმა შეძლონ ლოკალური შეცდომების იგნორირება ან ფილტრაცია branch-ით. ბილდის მოვლენები შეიცავს `build_system`-ს; runner-ის სამუშაოების მოვლენები შეიცავს როგორც `workflow_job_id`-ს, ასევე `workflow_run_id`-ს. მოთხოვნა შეიცავს გამოწერის იდენტიფიკატორსა და [Standard Webhooks](https://www.standardwebhooks.com/) ხელმოწერის header-ებს, რათა კლიენტმა შეძლოს მისი წარმოშობის ვერიფიკაცია. Tuist ცდილობს წარუმატებელ მიწოდებებს, ამიტომ კლიენტებმა უნდა გამოიყენონ სტაბილური `eventId` დუბლიკატების გასაფილტრად. payload არ შეიცავს ტესტების სახელებს, ლოგებსა და შეცდომის შეტყობინებებს; კლიენტს შეუძლია მიიღოს ეს დეტალები ზემოთ ჩამოთვლილი ინსტრუმენტების მეშვეობით და გადაწყვიტოს, შეატყობინოს თუ არა გუნდს ან დაიწყოს დებაგინგი. კლიენტებს შეუძლიათ შეაჩერონ მიწოდება `events/unsubscribe`-ით.

| `test_insights` | აყენებს Tuist Gradle პლაგინს, რათა Gradle `Test` task-ის შედეგები აიტვირთოს ავტომატურად. |
| `flaky_tests` | გაივლის flaky ტესტების დეტექციის setup-ს, Gradle Test Retry პლაგინის ოფციურ გამოყენებას და ტესტების კარანტინში მოქცევის კონფიგურაციას. |
| `test_sharding` | ამატებს უწყვეტი ინტეგრაციის workflow-ს `tuistPrepareTestShards`-თვის, shard მატრიცის გენერირებას და `TUIST_SHARD_INDEX`-ზე დაფუძნებულ ტესტების შესრულებას. |

როდესაც `features` გამოტოვებულია, მოთხოვნა სთხოვს აგენტს, გაარკვიოს, რომელი ინტეგრაციები სურს მომხმარებელს, ან მოთხოვნიდან გამოიტანოს ყველაზე მცირე სასარგებლო ნაკრები Gradle პროექტის რედაქტირებამდე.

#### Xcode ინტეგრაციის მოთხოვნის ფუნქციები

`integrate_xcode_project` მოთხოვნა აღწერს ყველა Xcode ინტეგრაციას, რომელსაც Tuist მხარდაჭერს:
