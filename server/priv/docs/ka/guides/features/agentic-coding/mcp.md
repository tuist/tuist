# Model Context Protocol

[Model Context Protocol (MCP)](https://modelcontextprotocol.io/docs/getting-started/intro) არის ღია სტანდარტი, რომელიც საშუალებას აძლევს ხელოვნური ინტელექტის აგენტებს ურთიერთქმედონ გარე სერვისებთან და მონაცემთა წყაროებთან. ის უზრუნველყოფს ისეთი აპლიკაციების, როგორიცაა [Claude](https://claude.ai/), [Claude Code](https://docs.anthropic.com/en/docs/claude-code), [Codex](https://developers.openai.com/codex/), და რედაქტორების, როგორიცაა [Zed](https://zed.dev), [Cursor](https://www.cursor.com) ან [Visual Studio Code](https://code.visualstudio.com), თავსებადობას Tuist-თან.

Tuist განათავსებს Model Context Protocol-ის სერვერულ ენდპოინტს მისამართზე `https://tuist.dev/mcp`. მასზე თქვენი კლიენტის მიერთებით, აგენტებს შეუძლიათ წვდომა მიიღონ თქვენს Tuist პროექტის მონაცემებზე, მათ შორის ტესტების ანალიტიკაზე, არასტაბილური ტესტების ანალიზზე და სხვა. უმეტესი ინსტრუმენტი კითხულობს Tuist-ის მონაცემებს, რომლებსაც ავტორიზებული მომხმარებელი უკვე ხედავს დაფლაზე. ყოველი ინსტრუმენტი აცხადებს ანოტაციებს, რომლებიც მიუთითებს, არის თუ არა ის მხოლოდ წაკითხვადი, შეუძლია თუ არა მას გამოიწვიოს ძნელად შექცევადი ცვლილება (`destructiveHint`) და შეუძლია თუ არა მას Tuist-ის გარეთ გასვლა (`openWorldHint`). ინსტრუმენტები, რომლებიც ცვლიან მდგომარეობას და თითოეული მათგანი შემოიფარგლება მომხმარებლის ნებართვებით ანგარიშზე ან პროექტზე, არის:

- **ორგანიზაციები და წევრები**: `create_organization`, `add_organization_member` (ამატებს არსებულ მომხმარებელს ან ცვლის წევრის როლს), `invite_organization_member` (აგზავნის მოწვევას ნებისმიერ ელფოსტის მისამართზე) და `cancel_organization_invitation`.
- **პროექტები**: `create_project`, `start_project_logo_upload` და `complete_project_logo_upload` (ცვლის ლოგოს), `connect_project_repository` და `disconnect_project_repository` (GitHub-ის რეპოზიტორიის ბმულები).
- **ტესტები**: `update_test_case` (აჩუმებს, ტოვებს, ხელახლა ააქტიურებს ან სატესტო შემთხვევას არასტაბილურად მონიშნავს; ცვლილება შეიძლება მიაღწიოს ანგარიშის webhook-ის ენდპოინტებს).
- **შეტყობინების წესები**: `create_notification_rule`, `update_notification_rule` და `delete_notification_rule`.
- **უწყვეტი ინტეგრაციის გამშვები აგენტები**: `create_runner_profile`, `update_runner_profile` (კეშის ტომების შენახვის სამუშაოების შევიწროება აუქმებს ლოდინში მყოფ შენახვებს), `delete_runner_profile` და `delete_runner_volume` (შლის ტომის შენახულ შინაარსს).
- **სენდბოქსები**: `create_sandbox`, `pause_sandbox`, `resume_sandbox`, `archive_sandbox` და `delete_sandbox` (შლის მის დისკებს).
- **უკუკავშირი**: `report_feedback` (აგზავნის ანგარიშს ინსტრუმენტის ან მოთხოვნის შესახებ Tuist-ის გუნდისთვის; მხოლოდ tuist.dev-ზე).
- **აგენტის ინტეგრაციები**: `connect_amp_workspace` (ანიჭებს სამუშაო სივრცის orbs-ს CI წვდომას ანგარიშზე), `disconnect_amp_workspace` და `connect_claude_environment` (საშუალებას აძლევს Claude Managed Agents-ის გარემოს გაუშვას სესიები Tuist-ის სენდბოქსებში).

`add_organization_member`, `cancel_organization_invitation`, `complete_project_logo_upload`, `disconnect_project_repository`, `update_test_case`, `update_notification_rule`, `delete_notification_rule`, `update_runner_profile`, `delete_runner_profile`, `delete_runner_volume`, `delete_sandbox` და `disconnect_amp_workspace` აცხადებენ `destructiveHint: true`, რადგან ისინი ცვლიან ან აშორებენ არსებულ მდგომარეობას. `invite_organization_member`, `update_test_case`, `connect_claude_environment` და `report_feedback` აცხადებენ `openWorldHint: true`, რადგან ისინი აგზავნიან ელფოსტას, აცნობებენ გარე webhook-ის ენდპოინტებს, უკავშირდებიან Anthropic-ს ან აგზავნიან ანგარიშს Tuist-ის გუნდისთვის.

პირადი Claude და ChatGPT გამოწერები დაკავშირებულია მხოლოდ დაფას AI პარამეტრებში, ამიტომ გამოწერის ტოკენები და შესვლები არასდროს გადის Model Context Protocol-ის კლიენტში. ანგარიშის დაყენების ინსტრუმენტები მოითხოვს მომხმარებლის ავტორიზაციას. ისინი არ არის ხელმისაწვდომი პროექტის ტოკენებისთვის ან ჩვეულებრივი ანგარიშის ტოკენებისთვის. როდესაც მომხმარებელი ავტორიზებს კლიენტს ბრაუზერში ან ითხოვს `auth.md` რეგისტრაციას, Tuist აკავშირებს ამ სერთიფიკატს მომხმარებელთან მხოლოდ Model Context Protocol-ის ენდპოინტზე, რათა დაყენების ინსტრუმენტებმა შეასრულონ მოთხოვნილი სამუშაო პროცესი.

Tuist ახორციელებს [2026-07-28 პროტოკოლს](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http). მოთხოვნები არის უსესიო: კლიენტები აგზავნიან თავიანთ პროტოკოლის მეტამონაცემებს ყოველ მოთხოვნასთან ერთად და შეუძლიათ პირდაპირ გამოიძახონ ინსტრუმენტები ინიციალიზაციის გარეშე. `server/discover` აბრუნებს სერვერის იდენტობას, შესაძლებლობებს, მხარდაჭერილ ვერსიებს და ინსტრუქციებს. არ არსებობს სესიის იდენტიფიკატორები ან დამოუკიდებელი მოვლენების ნაკადები. კლიენტები, რომლებიც იყენებენ 2025-06-18 ან 2025-03-26 ინიციალიზაციის ნაკადს, კვლავ მხარდაჭერილია; ისინიც მუშაობენ სერვერის სესიების გარეშე.

## Model Context Protocol უნარების წინააღმდეგ

Model Context Protocol-ის ინსტრუმენტებს და <.localized_link href="/guides/features/agentic-coding/skills">უნარებს</.localized_link> შეიძლება ჰქონდეთ გადაფარვა ფუნქციებში. არსებული გადაფარვის გათვალისწინებით, აირჩიეთ ერთი მიდგომა სამუშაო პროცესისთვის და გამოიყენეთ ის თანმიმდევრულად, ნაცვლად ორივეს ერთ ნაკადში შერევისა.

კლიენტებისთვის, რომლებიც მხარს უჭერენ პლაგინების ინსტალაციას, გამოიყენეთ <.localized_link href="/guides/features/agentic-coding/plugins">Tuist პლაგინები</.localized_link> ორივეს ერთად დასაყენებლად.

## კონფიგურაცია

დაამატეთ `https://tuist.dev/mcp` როგორც დაშორებული Model Context Protocol სერვერი თქვენს კლიენტში. სერვერის ინიციალიზაციის ინსტრუქციები და საჯარო სერვერის ბარათი აღწერს OAuth 2.0-ს დინამიური კლიენტის რეგისტრაციით და სტანდარტული ბრაუზერის ავტორიზაციის ნაკადით პირდაპირ, აგენტებისგან გარე ავტორიზაციის დოკუმენტების მოთხოვნის ან მათი მიყოლის გარეშე. ეს სერვერის მასშტაბის ინსტრუქციები ინარჩუნებს სამუშაო პროცესის მითითებებს ზოგადს: ინსტრუმენტის ავტორიზაცია არ ავტორიზებს ადგილობრივ ბრძანების ხაზის ინსტრუმენტებს ან აგების სისტემის ინტეგრაციებს და აგენტებმა უნდა დაადასტურონ მოთხოვნილი ცვლილებები შესაბამისი Tuist-ის ინსტრუმენტების მეშვეობით. აგების სისტემის სპეციფიკური დაყენება და ავტორიზაციის შემოწმებები დოკუმენტირებულია ინტეგრაციის სახელმძღვანელოებში და მოთხოვნებში. Tuist კვლავ აცხადებს როგორც [Open Authorization](https://oauth.net/2/)-ის აღმოჩენის მეტამონაცემებს, ასევე მიმდინარე [auth.md პროტოკოლს](https://workos.com/auth-md) მისამართზე `https://tuist.dev/auth.md` ცალკე.

თუ თქვენი ერთ-ერთი ორგანიზაცია აიძულებს ერთჯერად შესვლას, ბრაუზერში კლიენტის ავტორიზაცია მოითხოვს სესიას, რომელიც შესულია ამ ორგანიზაციის მეშვეობით და Tuist საჭიროების შემთხვევაში ჯერ პროვაიდერზე გაგზავნით. იხილეთ <.localized_link href="/guides/integrations/authentication/sso#choose-an-enrollment-policy">ერთჯერადი შესვლა</.localized_link>.

ენდპოინტი იღებს უსესიო `2026-07-28` Model Context Protocol-ის მოთხოვნის ციკლს, მათ შორის `server/discover`-ს, უფრო ძველ სესიაზე დაფუძნებულ ციკლთან ერთად. არსებულმა კლიენტებმა შეიძლება გააგრძელონ მათი მიმდინარე კავშირის მეთოდის გამოყენება.

კლიენტებს, რომლებიც მხარს უჭერენ Model Context Protocol-ის მოვლენებს, შეუძლიათ გამოიწერონ პროექტის მოვლენები. იხილეთ [მოვლენები](#events) ხელმისაწვდომი მოვლენებისა და მიწოდების მოთხოვნებისთვის.

კლიენტებს, რომლებიც უკვე მხარს უჭერენ დაშორებულ ბრაუზერის ავტორიზაციას, შეუძლიათ გააგრძელონ ბრაუზერში ავტორიზაცია. კლიენტებსა და აგენტებს, რომლებიც მხარს უჭერენ `auth.md`-ს, შეუძლიათ ანონიმურად დარეგისტრირდნენ, წარადგინონ სანდო პროვაიდერის იდენტობის დამტკიცება ან დაიწყონ სერვისით ავტორიზებული ელფოსტის მოთხოვნა. რეგისტრაცია აბრუნებს Tuist-ით ხელმოწერილ იდენტობის დამტკიცებას, რომელსაც აგენტი ცვლის სტანდარტულ ტოკენის ენდპოინტზე ერთსაათიანი წვდომის ტოკენისთვის. Tuist აქვეყნებს თავის საჯარო ხელმოწერის გასაღებს და მხარს უჭერს სტანდარტულ ტოკენის გაუქმებასა და პროვაიდერის უსაფრთხოების მოვლენების მიწოდებას.

ავტორიზაციის გარეშე მოქმედმა აგენტმა უნდა წაიკითხოს Model Context Protocol-ის ენდპოინტის მიერ დაბრუნებული `WWW-Authenticate` ჰედერი, მოიძიოს დაცული რესურსის მეტამონაცემები, მოიძიოს ავტორიზაციის სერვერის მეტამონაცემები და გადავიდეს მის `agent_auth.skill` URL-ზე. Tuist ასევე აბრუნებს იგივე ლოკალურ `auth_md` URL-ს არაავტორიზებული პასუხის სხეულში, რათა ენის მოდელებზე დაფუძნებულმა კლიენტებმა აღმოაჩინონ ნაკადი ნატიური კლიენტის ინტეგრაციაზე დამოკიდებულების გარეშე. განლაგების ლოკალური დოკუმენტი არის საიმედო წყარო ენდპოინტების სახელების, მოთხოვნის სხეულების, მოთხოვნის გამოკითხვისა და დამტკიცების გაცვლისთვის.

სანამ აგენტი დაიწყებს ელფოსტის მოთხოვნას, მან უნდა სთხოვოს მომხმარებელს დაადასტუროს თავისი Tuist ანგარიშის ელფოსტის მისამართი. მას არ შეუძლია ამ მისამართის გამოტანა პროვაიდერის პროფილიდან, Git-ის კონფიგურაციიდან, გარემოს ცვლადიდან ან სესიის მეტამონაცემებიდან.

ენდპოინტი იყენებს `mcp` სკოპების ჯგუფს. ანონიმურმა, მოთხოვნამდელმა კრედენციალმა შეიძლება აღმოაჩინოს შესაძლებლობები და წაიკითხოს საჯარო ინტეგრაციის სახელმძღვანელო, მაგრამ ის არ განიხილება როგორც შესული მომხმარებელი. ბრაუზერში ავტორიზაციის ან მოთხოვნის შემდეგ, კრედენციალი ხდება მომხმარებელზე მორგებული და თითოეული ინსტრუმენტი ატარებს იგივე ავტორიზაციის შემოწმებებს, რასაც დაშბორდი. დეტალებისთვის იხილეთ <.localized_link href="/guides/server/authentication#scope-groups">სკოპების ჯგუფების დოკუმენტაცია</.localized_link>.

ინსტრუმენტები მიმართავენ პროექტებს, რომლებსაც ავტორიზებულ მომხმარებელს უკვე აქვს წვდომა. Xcode-ისა და Gradle-ის აგების ინსტრუმენტები იღებენ აგების UUID-ს ან დაშბორდის URL-ს. UUID-მ უნდა იდენტიფიციროს ზუსტად ერთი პროექტი; თუ ის ჩნდება რამდენიმე პროექტში, ინსტრუმენტი აბრუნებს „ნაპოვნი არ არის“-ს სხვა პროექტის ანგარიშის არჩევის ნაცვლად. პროექტზე მორგებული დაშბორდისა და API-ს წაკითხვები რჩება ხელმისაწვდომი. მოხსენებული აქტორის იდენტიფიკატორები არის დაუდასტურებელი ნიშნულები, არა კრედენციალები ან დამატებითი წვდომის უფლებები.

აგების სიისა და დეტალების ინსტრუმენტები აჩვენებენ optional `tuist_version` მეტამონაცემებს: Xcode-ისა და Cargo-სთვის – მომხსენებელი Tuist CLI, Gradle-ისთვის – Tuist Gradle პლაგინი, ხოლო Mix-ისთვის – `tuist_ex` ბიბლიოთეკა. Xcode ასევე აჩვენებს `tuist_generation_version`-ს მის დაკავშირებული პროექტის გენერაციის მოვლენიდან, რაც შეიძლება განსხვავდებოდეს ატვირთვადი CLI-სგან. დაკარგული დაკვირვებები არის null, არა გამოტანილი სერვერიდან ან სხვა ანგარიშიდან. Bazel იყენებს თავის არსებულ `bazel_version`-ს; Once-ის გაშვების დეტალები აჩვენებენ `once_version`-ს. ეს ველები აღწერენ მოხსენებულ ვერსიებს, არა დადასტურებულ იდენტობას ან სადენის კონტრაქტის ვერსიებს. REST აგების ენდპოინტები აჩვენებენ იგივე მეტამონაცემებს. არსებულ ინტეგრაციასა და ფლაკი-ტესტის უნარებს არ სჭირდებათ ვერსიის ველები და არ საჭიროებენ სამუშაო ნაკადის ცვლილებებს.

Tuist-ის ოპერატორები, რომლებიც იკვლევენ მომხმარებლის ანგარიშს, აკეთებენ ამას Tuist-ის შიდა ოპერაციული ინსტრუმენტების მეშვეობით, რომელიც იწერს ყოველ ზარს; ამ ენდპოინტთან პირდაპირი კავშირი არ იძლევა წვდომას მომხმარებლის საკუთარი წევრობის ფარგლებს გარეთ.

### Pulse

Pulse აჩვენებს მხოლოდ წაკითხვის ინსტრუმენტებს ანგარიშის ოპერაციული მეტრიკების, ლოგების, ტრეისებისა და შეცდომებისთვის, რომლებიც ყველა მიმართულია `account_handle`-ით. პირველი სამი ასახავს Pulse-ის გვერდებსა და მათ REST API-ს; დანარჩენი ხუთი აგენტს საშუალებას აძლევს პირდაპირ შეისწავლოს ტელემეტრია და არ აქვთ REST ეკვივალენტი:

| ინსტრუმენტი | მიზანი | REST ეკვივალენტი `/api/accounts/:account_handle/pulse`-ის ქვეშ |
| --- | --- | --- |
| `query_pulse` | Pulse-ის გვერდის ცხრილები | `GET /:signal` |
| `get_pulse_analytics` | Pulse-ის გვერდის ვიჯეტები | `GET /:signal/analytics` |
| `get_pulse_error_issue` | ერთი შეცდომის საკითხი და მისი მოვლენები | `GET /errors/issues/:fingerprint` |
| `query_pulse_metrics` | მყისიერი ან დიაპაზონის PromQL | არ არის |
| `list_pulse_labels` | ნიშნულის სახელები, ან ერთი ნიშნულის მნიშვნელობები | არ არის |
| `search_pulse_logs` | ფილტრული ლოგის ჩანაწერები | არ არის |
| `search_pulse_traces` | ფილტრული სპანები | არ არის |
| `get_pulse_trace` | ერთი ტრეისის ყოველი სპანი | არ არის |

Pulse შეზღუდულია სერვერზე კონფიგურირებული ორგანიზაციის მიმდინარე წევრებისთვის, მაშინაც კი, თუ ანგარიში ან პროექტი საჯაროა. ის მოითხოვს მომხმარებლის ავტორიზაციას ან მომხმარებელთან დაკავშირებულ `mcp` კრედენციალსა და ანგარიშის წაკითხვის ავტორიზაციას. პროექტის ტოკენები, ჩვეულებრივი ანგარიშის ტოკენები, ანონიმური რეგისტრაციები და ოპერატორის წვდომა ორგანიზაციის წევრობის გარეშე არ იძლევა Pulse-ის წვდომას. კრედენციალებს არ შეუძლიათ აირჩიონ სხვა ბექენდი ან ტელემეტრიის არენდატორი, და მხოლოდ სერვერზე კონფიგურირებულ ანგარიშს აქვს Pulse ტელემეტრია, ამიტომ არცერთ ინსტრუმენტს არ შეუძლია წაიკითხოს სხვა ანგარიშის მონაცემები. ბრაუზერის აგენტები იღებენ ამ ინსტრუმენტებს მხოლოდ Pulse-ის გვერდებზე, ამ გვერდის ანგარიშის სკოპის ფარგლებში.

REST მოითხოვს მომხმარებლის კრედენციალს. OAuth და `auth.md` მომხმარებლის ასოციაციები ხელმისაწვდომია მხოლოდ `/mcp` ენდპოინტზე; ანგარიშის კრედენციალი მიმდინარე მომხმარებლის გარეშე უარყოფილია, მიუხედავად დაკავშირებული ანგარიშის წევრობისა ან ხილვადობისა.

`query_pulse` იღებს `signal`-ს (`metrics`, `logs`, `traces` ან `errors`), optional `query`-ს და `range`-ს (`15m`, `1h`, `6h` ან `24h`, ნაგულისხმევი `1h`). მეტრიკები იღებენ PromQL გამოსახულებებს. ლოგები, ტრეისები და შეცდომები იღებენ ლიტერალურ, რეგისტრის მიმართ უმჯავნო ტექსტს, რომელიც ემთხვევა ლოგის სხეულებს, სპანების სახელებსა და შეცდომის საკითხების სათაურებს; `*`, ნაგულისხმევი, ირჩევს ყველაფერს. ტრეისის სტრიქონები არის ინდივიდუალური სპანები. შეცდომის სტრიქონები არის საკითხები: მოვლენები დაჯგუფებული სერვისისა და თითის ანაბეჭდის მიხედვით, მათი მოვლენების რაოდენობით, დაზარალებული ანგარიშებით, პირველი და ბოლო გამოჩენა ფანჯარაში, და მათი ბოლო მოვლენის სათაური, დამნაშავე, დონე და პლატფორმა. ცხრილები იღებენ `search`-ს, `page`-ს (ნაგულისხმევი `1`), `page_size`-ს (`1`–`100`, ნაგულისხმევი `20`), `sort_by`-ს და `sort_order`-ს (`asc` ან `desc`). დალაგების სვეტები დამოკიდებულია სიგნალზე და ჩამოთვლილია ინსტრუმენტის სქემაში. ფილტრები მოიცავს `service`-ს და `level`-ს ლოგებისა და შეცდომებისთვის. ფილტრის ოპერატორები იყენებენ შესაბამის `_op` არგუმენტს (`eq`, `contains` ან `not_contains`), ნაგულისხმევად ზუსტი ტოლობით.

დალაგების სვეტებია `name`/`value` მეტრიკებისთვის; `timestamp`/`service`/`level`/`message`/`trace_id` ლოგებისთვის; `timestamp`/`service`/`name`/`duration_ms`/`trace_id` ტრეისებისთვის; და `last_seen`/`first_seen`/`events`/`accounts`/`title`/`service`/`level` შეცდომებისთვის. დაშბორდი განზრახ აჩვენებს ქვესიმრავლეს; API და ინსტრუმენტები იღებენ სრულ სიას თითოეული სიგნალისთვის.

ცხრილის პასუხები შეიცავს `rows`-ს, `series`-ს, `warnings`-ს და `meta`-ს. პაგინაციის მეტამონაცემები მოიცავს `page`-ს, `page_size`-ს, `total_count`-ს, `total_pages`-ს, `has_next_page`-ს, `has_previous_page`-ს და `end_at`-ს. გადაეცით დაბრუნებული ISO8601 `end_at` შემდგომ გვერდებთან ერთად, რათა შეინარჩუნოთ მოთხოვნის ფანჯარა. შედეგის ლიმიტის შეცდომები მოითხოვენ მოთხოვნის ან დროის დიაპაზონის შევიწროვებას, არა პასუხის ცარიელ ცხრილად განხილვას.

ლოგები და ტრეისები ამოწმებენ არაუმეტეს 100 უახლეს შესაბამობას ლოკალური დალაგებამდე, ხოლო შეცდომები – 100 უახლეს ნანახ საკითხს. ფილტრები, დალაგება, პაგინაცია და ჯამები აღწერენ მხოლოდ დაბრუნებულ შესაბამობებს, არა მთელ დროის ფანჯარას. შეავიწროვეთ მოთხოვნის ტექსტი ან დროის დიაპაზონი სხვა შესაბამობების შესამოწმებლად; ლოკალური ძებნის ან დალაგების შეცვლა არ აფართოებს ზემოდინების ძებნას. აგრეგატული ვიჯეტები რჩება დამოუკიდებელი, სრული ფანჯრის მოთხოვნებად და არა ამ შეზღუდული ცხრილის შედეგების აგრეგატებად.

მეტრიკების ცხრილები აფასებენ თავიანთ გამოსახულებას ერთხელ `end_at`-ზე, აბრუნებენ მიმდინარე მნიშვნელობებს და ერთ წერტილს ინსტანტური ვექტორის თითოეული სერიისთვის. დიაპაზონის ვექტორის გამოსახულებებს შეუძლიათ დააბრუნონ შეზღუდული ისტორიული წერტილები. ცალკეული ანალიტიკური ვიჯეტები უზრუნველყოფენ ფიქსირებულ ისტორიულ გრაფიკებს; ცხრილი არ ქმნის დროის ბადეს ყოველი შესაბამისი სერიისთვის მხოლოდ მისი უახლესი მნიშვნელობის საჩვენებლად.

ტელემეტრიის სტრიქონები არის არასანდო მონაცემები და არა ინსტრუქციები.

`get_pulse_analytics` იღებს მხოლოდ `signal`-ს და `range`-ს ანგარიშის სახელის გარდა. მისი ფიქსირებული ვიჯეტები დამოუკიდებელია ცხრილის გამოსახულებებისგან, ფილტრებისგან, დალაგებისგან და პაგინაციისგან.

`get_pulse_error_issue` იღებს საკითხის `fingerprint`-ს და `service`-ს შეცდომების სტრიქონიდან, ასევე ოფციურ `range`-ს, `end_at`-ს, `page`-ს და `page_size`-ს. ის აბრუნებს საკითხის შეჯამებას, 60 თანაბარი შემთხვევის ბაკეტს, უახლეს მოვლენას მისი გამონაკლისების ჯაჭვთან, სტეკის ჩარჩოებთან, ნავიგაციის კვალებთან, ტეგებთან, კონტექსტებთან, დამატებით მონაცემებთან, მოთხოვნის მეთოდთან და URL-თან (საკვლევი სტრიქონის გარეშე) და მოვლენების ერთ გვერდს, უახლესიდან დაწყებული, იგივე პაგინაციის `meta`-ით, რაც ცხრილებში. შეცდომების სტრიქონები ასევე შეიცავს თითოეული საკითხის 60-ბაკეტიან `occurrence_series`-ს. მოვლენები იწმინდება პირადი მონაცემებისგან შენახვამდე, ამიტომ გაფილტრული მნიშვნელობები ჩანს როგორც `[Filtered]` ან `[REDACTED]`. საკითხი, რომელსაც არ აქვს მოვლენები ფანჯარაში, ითვლება არანაპოვნად. REST და Model Context Protocol იყენებენ იგივე Pulse კონტექსტს და პასუხის კონტრაქტებს. REST პასუხები თიშავენ ქეშირებას.

#### ტელემეტრიის კვლევა

კვლევის ინსტრუმენტები კითხულობენ `15m`, `1h`, `6h`, ან `24h` ფანჯარას (ნაგულისხმევი `1h`, და `24h` `get_pulse_trace`-სთვის), რომელიც მთავრდება ოფციური ISO8601 `end_at`-ზე, რომელიც ნაგულისხმევად არის ახლა. ყოველი პასუხი აბრუნებს `start_at`-ს და `end_at`-ს; გადაეცით იგივე `end_at` ხელახლა, რათა შეინარჩუნოთ ფანჯარა. ამ ინსტრუმენტებიდან არცერთი არ იღებს SQL-ს.

- `query_pulse_metrics` აფასებს `query`-ს, PromQL გამოსახულებას, `end_at`-ზე (`type: instant`, ნაგულისხმევი) ან ყოველ `step` წამში ფანჯრის განმავლობაში (`type: range`). ნაბიჯი ნაგულისხმევად არის და არ შეიძლება იყოს ნაკლები ფანჯარაზე გაყოფილი 360-ზე, ამიტომ სერიას აქვს მაქსიმუმ 361 წერტილი. შედეგებს აქვთ მაქსიმუმ 5,000 სერია. წერტილები არის `[unix_seconds, value]`, ხოლო `NaN` და უსასრულო მნიშვნელობები არის სტრიქონები. ინსტანტური მოთხოვნები უარყოფენ `range`-ს და `step`-ს.
- `list_pulse_labels` იღებს `signal`-ს. `label`-ის გარეშე, ის ჩამოთვლის ლეიბლების სახელებს; `label`-ით, ის ჩამოთვლის იმ ლეიბლის მნიშვნელობებს. მეტრიკებისთვის, `__name__` ჩამოთვლის მეტრიკების სახელებს, ხოლო ნებისმიერი სხვა ლეიბლის მნიშვნელობები მოითხოვს `match`-ს, სერიის სელექტორს, როგორიცაა `up`. ლოგებისა და ტრეისების ლეიბლების მნიშვნელობები იღებენ `filters`-ს; ტრეისების ლეიბლების სახელები მოდის ტრეისის სქემიდან და არა. ლოგებისა და ტრეისების მნიშვნელობები შეიცავს მათ ჩანაწერთა რაოდენობას ფანჯარაში, ყველაზე ხშირი პირველად, ამიტომ ისინი ასევე ემსახურებიან როგორც დაშლა, მაგალითად, შეცდომები სერვისის მიხედვით. `search` ინარჩუნებს მხოლოდ სახელებს ან მნიშვნელობებს, რომლებიც შეიცავს ლიტერალურ ტექსტს, და `limit` იღებს `1`–`1000`-ს (ნაგულისხმევი `100`). ლოგების ლეიბლის სახელის აღმოჩენა ამოწმებს მაქსიმუმ 1,000 განსხვავებულ ატრიბუტთა ნაკრებს თითოეული ტიპისთვის და ჩამოთვლის მხოლოდ იმ გასაღებებს, რომლებსაც ფილტრები იღებენ.
- `search_pulse_logs` აბრუნებს მაქსიმუმ `limit` ჩანაწერს (`1`–`100`, ნაგულისხმევი `50`), `newest` ან `oldest` პირველად, რომელთა სხეული შეიცავს `text`-ს და რომლებიც ემთხვევა ყოველ ფილტრს. თითოეული ჩანაწერი შეიცავს მის `severity_text`-ს, `body`-ს, `trace_id`-ს, `span_id`-ს, `scope_name`-ს და მის გაერთიანებულ რესურსსა და ლოგის `attributes`-ს. `span_id` და `scope_name` არის `null` Kubernetes-იდან შეკრებილი ლოგებისთვის, რომელსაც მხოლოდ OTLP ლოგის გამგზავნები აყენებენ.
- `search_pulse_traces` აბრუნებს მაქსიმუმ `limit` სპანს, `newest`, `oldest`, ან `slowest` პირველად, რომლებიც ემთხვევა ყოველ ფილტრს, ოფციურ `min_duration_ms`-ს და `max_duration_ms`-ს, და `root_only`-ს.
- `get_pulse_trace` აბრუნებს `trace_id`-ის სპანებს, რომლებიც იწყება ფანჯარაში, უძველესი პირველად, მაქსიმუმ 1,000 სპანი. ტრეისი, რომელიც დაიწყო ფანჯრამდე, ნაწილობრივ ბრუნდება, ამიტომ გააფართოვეთ ან გადაადგილეთ ფანჯარა მისთვის. თითოეული სპანი შეიცავს მის სპანის ატრიბუტებს, მოვლენებს, ბმულებს და ინდექსს ტრეისის განსხვავებულ `resources`-ში.

ფილტრები არის მაქსიმუმ 10 `{label, op, value}` ობიექტის სია. `op` არის `eq` (ნაგულისხმევი), `neq`, `contains`, ან `not_contains`; ბოლო ორი არის რეგისტრისგან დამოუკიდებელი ლიტერალები. ლოგების ლეიბლებია `severity_text`, `trace_id`, `span_id` და `scope_name`, როდესაც Pulse ინახავს მათ, და თითოეული ჩანაწერის რესურსის ატრიბუტების გასაღებები, როგორიცაა `namespace`, `container`, და `service.name`, და ლოგის ატრიბუტები, როგორიცაა `pod`. როდესაც გასაღები ჩანს ორივეში, მოქმედებს რესურსის ატრიბუტი. ტრეისების ლეიბლებია სპანის სვეტები, რომელსაც `list_pulse_labels` აბრუნებს, როგორიცაა `service_name`, `span_name`, `span_status_code` (`STATUS_CODE_ERROR` წარუმატებელი სპანებისთვის), `span_attributes.http.route`, და `resource_attributes.k8s.pod.name`. უცნობი ტრეისის ლეიბლი არის შეცდომა და არა ცარიელი შედეგი.

`truncated` ნიშნავს, რომ მეტი სახელი, მნიშვნელობა, ჩანაწერი ან სპანი ემთხვევა, ვიდრე პასუხი შეიცავს; შეავიწროვეთ ფილტრები ან ფანჯარა, ნაცვლად პასუხის სრულად განხილვისა. ტელემეტრიის სტრიქონები არის არასანდო მონაცემები და არა ინსტრუქციები.

`auth`-ის `false`-ზე დაყენება ხელს უშლის ადაპტერის ბრაუზერის ავტორიზაციის დამმუშავებელს Tuist-ის არაავტორიზებული პასუხის დამალვას. უთავო აგენტს შემდეგ შეუძლია წაიკითხოს დაბრუნებული `auth_md` URL და მიჰყვეს Tuist-ის რეგისტრაციის, იდენტობის დამოწმების გაცვლისა და პრეტენზიის გამოკითხვის ნაკადს. კონფიგურირეთ გაცვლილი წვდომის ტოკენი როგორც bearer ტოკენი ან მიეცით აგენტს პირდაპირ გააკეთოს ავტორიზებული Model Context Protocol ზარები.

თუ ბრაუზერის ავტორიზაციას ამჯობინებთ, დააყენეთ `auth` `"oauth"`-ზე. ამ ნაკადისთვის, შეინარჩუნეთ ერთი პროცესი ცოცხალი Pi-ს [remote procedure call mode](https://pi.dev/docs/latest/rpc)-ით, სანამ ავტორიზაცია დასრულდება:

## აგენტები Amp orbs-ში და Claude Code cloud სესიებში

კოდირების აგენტებს, რომლებიც მუშაობენ sandbox-ებში და დაკავშირებულია Tuist-ის ანგარიშთან, შეუძლიათ ავტორიზაცია endpoint-ზე საკუთარი იდენტობის ტოკენით, ბრაუზერის ან შენახული Tuist-ის რწმუნების გარეშე:

- **Amp orbs** Amp workspace-ის ან პროექტისთვის, რომელთანაც ანგარიში დაკავშირებულია **Settings → Integrations → Amp**-ის ქვეშ, აგზავნის orb-ის ID ტოკენს. Amp-ში, დააყენეთ სერვერის `Authorization` ჰედერი `Bearer ${amp:id-token}`-ზე. Amp აფორმებს ტოკენს სერვერის URL-ის წყაროსთვის, ამიტომ URL უნდა იყოს ამ Tuist ინსტანციის საკუთარი მისამართი და ანახლებს მას ვადის გასვლამდე. სხვა წყაროსთვის გამოშვებული ტოკენები უარყოფილია.
- **Claude Code cloud sessions** დაკავშირებული Claude Code გარემოდან აგზავნის სესიის ტოკენს, რომელსაც Tuist გადასცემს მათ როგორც `TUIST_OIDC_TOKEN`. დააყენეთ ჰედერი `Bearer ${TUIST_OIDC_TOKEN}`-ზე.

Tuist-ის Linux sandbox-ები არ ამატებენ სერვერს თქვენთვის: ისინი შეიცავენ Tuist CLI-ს, რომელიც შედის სისტემაში იგივე იდენტობით, და უნარს, რომელიც ეუბნება აგენტს, როდის შეამოწმოს შედეგები პროექტის ისტორიის მიმართ. აგენტებისთვის MCP ხელსაწყოების მისაცემად, დაამატეთ სერვერი თქვენს Amp ან Claude Code პარამეტრებში, ან პროექტის `.mcp.json`-ში, ზემოთ მოცემული ჰედერით.

ეს ტოკენები იძლევა მხოლოდ წაკითხვის უფლებას დაკავშირებული ანგარიშის ყველა პროექტზე: ისინი შეიცავენ `mcp` ჯგუფის წაკითხვის სფეროებს და არაფერს, რაც ქმნის, ცვლის ან შლის მონაცემებს, მაგალითად, ტესტების ჩუმად დატოვებას ან გამოტოვებას. workspace-ის ან გარემოს გათიშვა წყვეტს წვდომას შემდეგ მოთხოვნაზე და წვდომა არასდროს ძლებს თავად ტოკენზე მეტხანს. Amp workspace, რომელიც დაკავშირებულია რამდენიმე Tuist ანგარიშთან, უარყოფილია, რადგან მისი ტოკენი არ ასახელებს ერთს. როდესაც კავშირი არ არსებობს, არაავტორიზებული პასუხის `error_description` ამას აღნიშნავს.

ეს მხოლოდ წაკითხვის წვდომა ვრცელდება მხოლოდ Model Context Protocol endpoint-ზე. ბრძანების ხაზის ხელსაწყო და build-system ინტეგრაციები იმავე sandbox-ში კვლავ ცვლიან ტოკენს კავშირის CI წვდომისთვის.

## WebMCP

ბრაუზერებში, რომლებიც მხარს უჭერენ [WebMCP](https://webmachinelearning.github.io/webmcp)-ს, Tuist-ის გვერდები რეგისტრირებენ ხელსაწყოებს `document.modelContext`-ით, ასე რომ ბრაუზერში ჩაშენებულ აგენტებს შეუძლიათ გამოიძახონ ისინი დამატებითი კონფიგურაციის გარეშე. ზარები სრულდება Tuist სერვერზე.

- **Website and documentation pages** რეგისტრირებენ დოკუმენტაციისა და წყაროს ხელსაწყოებს (`search_tuist`, `search_tuist_code`, `list_tuist_files` და `read_tuist_file`). მათ არ სჭირდებათ თქვენი შესვლა სისტემაში.
- **An account's dashboard pages**, როდესაც სისტემაში ხართ შესული, რეგისტრირებენ Tuist-ის მხოლოდ წაკითხვის ხელსაწყოებს ამ ანგარიშისთვის. თითოეული გვერდი რეგისტრირებს მხოლოდ იმ ხელსაწყოებს, რასაც ის აჩვენებს, პროექტის build system-ისთვის: Gradle პროექტის builds გვერდი იღებს Gradle build ხელსაწყოებს, მისი test გვერდები — test და coverage ხელსაწყოებს, runners გვერდები — runner ხელსაწყოებს, ხოლო sandboxes გვერდები — sandbox ხელსაწყოებს. ყველა გვერდი ასევე იღებს დოკუმენტაციის ხელსაწყოებს, `list_projects` და `get_project`. ხელსაწყოები მუშაობენ სისტემაში შესული მომხმარებლის სახელით, ამიტომ ისინი წვდებიან მხოლოდ იმ მონაცემებს, რომელთა წაკითხვაც შეგიძლიათ dashboard-ში და მხოლოდ იმ ანგარიშს, რომელსაც უყურებთ. როდესაც გადადიხართ სხვა გვერდზე ან ანგარიშზე, ხელსაწყოები იცვლება იმ გვერდის ხელსაწყოებით.

ხელსაწყოები, რომლებიც ქმნიან, ცვლიან ან შლიან მონაცემებს, არ არის ხელმისაწვდომი WebMCP-ით, რადგან ბრაუზერის აგენტი იღებს ხელსაწყოებს თქვენი დამატების გარეშე და კითხულობს კონტენტს, რომელსაც builds და tests წარმოქმნიან. დააკავშირეთ MCP კლიენტი `/mcp` endpoint-თან ამ ხელსაწყოების გამოსაყენებლად.

თუ ორგანიზაცია აიძულებს ერთჯერად შესვლას (single sign-on), შედით dashboard-ზე მისი პროვაიდერით, რათა გამოიყენოთ მისი ხელსაწყოები.

## Build-system ინტეგრაციები იყენებენ ორ რწმუნებას

რწმუნება, რომელიც გამოიყენება Model Context Protocol ხელსაწყოებისთვის, არ ავტორიზებს Gradle პლაგინს ან Bazel-ის remote სერვისებს. სანამ აგენტი შეცვლის ან შეამოწმებს Gradle ან Bazel ინტეგრაციას, მან უნდა გაუშვას:

```bash
tuist auth whoami --url https://tuist.dev
```

თუ ეს ბრძანება არ არის ავტორიზებული, აგენტმა უნდა შეწყვიტოს და სთხოვოს მომხმარებელს გაუშვას:

```bash
tuist auth login --url https://tuist.dev
```

ლოკალური ან self-hosted განლაგებისთვის, შეცვალეთ URL ორივე ბრძანებაში და `tuist.toml`-ში. შეინარჩუნეთ hostname-ის მართლწერა იდენტური ყველგან. მაგალითად, `localhost` და `127.0.0.1` იყენებენ ცალკე შენახულ რწმუნებებს.


## შესაძლებლობები

### ხელსაწყოები

შემდეგი ხელსაწყოები ხელმისაწვდომია Tuist Model Context Protocol სერვერის მეშვეობით:

ყველა ხელსაწყო აქვეყნებს ადამიანისთვის წასაკითხ აღწერას ცხადი input და output სქემებთან ერთად. წარმატებული ზარები აბრუნებენ სტრუქტურირებულ კონტენტს, რომელიც შეესაბამება გამოცხადებულ output სქემას, პლიუს იგივე შედეგი ტექსტად სერიალიზებული იმ კლიენტებისთვის, რომლებიც ჯერ არ იყენებენ სტრუქტურირებულ კონტენტს.

ხელსაწყოები, რომლებიც იღებენ ერთი ჩანაწერის იდენტიფიკატორს, როგორიცაა `build_run_id`, `test_run_id`, `test_case_id`, `bundle_id`, `run_id`, `generation_id`, ან `cache_run_id`, ასევე იღებენ ამ ჩანაწერის Tuist dashboard URL-ს. ჩასვით URL პირდაპირ ბრაუზერიდან, ნაცვლად იმისა, რომ ამოიღოთ იდენტიფიკატორი მისგან.

| ID | ხელსაწყო | შეთავაზებულია, როდესაც |

ID-ები შეზღუდულია ბილდის ფარგლებში და არ უნდა შეესაბამებოდეს სხვა ბილდებს.

არასავალდებულო `start_ms` და `end_ms` ირჩევს ნაბიჯებს, რომლებიც ემთხვევა დროის დიაპაზონს მილიწამებში ბილდის დაწყებიდან; ბოლო არ არის ჩართული. ორივე ხელსაწყო იღებს ბილდის UUID-ს ან dashboard URL-ს როგორც `build_run_id`. გადასცით მიღებული ნაბიჯის `id` უცვლელად როგორც `step_id` მისი ლოგის მისაღებად. ლოგები ინახავს მაქსიმუმ 64 KiB-ს ნაბიჯზე, `log_truncated` მიუთითებს გამოტოვებულ გამოტანაზე.

ნაბიჯები ნაგულისხმევად იკრიბება Xcode ბილდების დამუშავებისას. ჩაწერილი ნაბიჯის მონაცემები ინახება 90 დღის განმავლობაში. სიის პასუხი შეიცავს `availability`-ს: `available`, როცა ჩაწერილი ნაბიჯები არსებობს, მაშინაც კი, თუ ფილტრები არაფერს ემთხვევა; `processing`, როცა ბილდი ჯერ კიდევ მუშავდება და ნაბიჯები ჯერ არ აქვს; ან `unavailable`, როცა ნაბიჯები არ ჩაწერილა ან ამოიწურა.

იგივე ოპერაციები ხელმისაწვდომია HTTP API-ზე `GET /api/projects/{account_handle}/{project_handle}/xcode/builds/{build_id}/steps` და `GET /api/projects/{account_handle}/{project_handle}/xcode/builds/{build_id}/steps/{step_id}` მისამართებზე, იგივე ფილტრებითა და პაგინაციით. ორივეს სჭირდება წვდომა ბილდის პროექტის წასაკითხად.

Gradle-ისა და Bazel-ის ნაბიჯების სიები ნაგულისხმევად აბრუნებენ 20 შედეგს (მაქსიმუმ 100), მხარდაჭერილია `search`, ზუსტი `project`, `target`, `category` და `status`, თანხვედრილი `start_ms` / `end_ms` ფილტრები (ბოლო არ შედის) და დალაგება `duration_ms` ან `start_ms` მიხედვით. გადაეცით დაბრუნებული ID-ები უცვლელად; ისინი შეზღუდულია კონკრეტული ბილდის ფარგლებში. სიები ასახავენ `time_origin` და `coverage`. ძველი Gradle ანგარიშები იყენებენ `first_recorded_timestamp`-ს, რადგან ბილდის დაწყების დრო არ აიტვირთა. Bazel პროფილები ასახავს ყველა ჩაწერილ ინტერვალს `trace_profile` დაფარვით და `profile_start`-ს როგორც დროის საწყისს. ძველი ბილდები ეყრდნობიან შენახულ BEP შეჯამებებს. წყაროს ჩანაწერები იწურება 90 დღის შემდეგ. Bazel დეტალები მოიცავს გასუფთავებულ action ლოგებს, როცა ისინი გამოქვეყნებულია. შეცდომიანი ამოცანის ან კონფიგურაციის ნაბიჯის Gradle დეტალები მოიცავს Tuist Gradle პლაგინის მიერ `log`-ად მოწოდებულ შეცდომის შეტყობინებას: გამონაკლისის ტექსტს და მისი მიზეზების ჯაჭვს, როგორც Gradle კონსოლი ბეჭდავს, სტეკის კვალისა და ამოცანის გამოტანის გარეშე, პროექტის შიგნით არსებული გზები ქცეულია ფარდობითად, ხოლო სერთიფიკატები და სხვა ადგილობრივი გზები დაფარულია, მაქსიმუმ 16 KiB თითო ნაბიჯზე და 32 შეცდომიანი ნაბიჯი ბილდზე. სხვა Gradle ნაბიჯებს, პლაგინის ძველი ვერსიებით მოწოდებულ ბილდებსა და სერთიფიკატების გარეშე ანგარიშებს აქვთ null `log`. კონფიგურაციის ნაბიჯები ანგარიშობენ `failure`-ს შეცდომის შემთხვევაში და `unknown`-ს სხვა შემთხვევებში. `compare_builds` მოთხოვნა იყენებს ამ დაფარვას სრული Bazel ტრეისების შესანახი შეჯამებებისგან განსასხვავებლად და მიმართავს აგენტებს ნაბიჯის დეტალებზე action შედეგებისა და ლოგებისთვის, სანამ უფრო ფართო გამოძახების შედეგებს შეამოწმებენ.

ერთი ნაბიჯის ხელსაწყოები `get_gradle_build_step` და `get_bazel_build_step` იღებენ ნაბიჯს ID-ით და არ იღებენ დროის ფილტრებს; გამოიყენეთ შესაბამისი სიის ხელსაწყოები ნაბიჯების დროის დიაპაზონით გასაფილტრად.

შენახული შეჯამებებიდან დაბრუნებული Bazel ნაბიჯის ID-ები რჩება წასაკითხად, თუ სრული პროფილი მოვა სიის ჩამოთვლასა და ნაბიჯის მიღებას შორის. ინდექსირებული პროფილი, რომლის ნაბიჯის მონაცემები ამოიწურა, ანგარიშობს ხელმიუწვდომლობას. Gradle ნაბიჯების სიები მოიცავს ნულოვანი ხანგრძლივობის cached და გამოტოვებულ ოპერაციებს.

`list_bazel_invocations` ფილტრები არის ზუსტი დამთხვევები და ერთსა და იმავე წამში დასრულებული გამოძახებები დალაგებულია გამოძახების ID-ით. ბრენჩზე უახლესი შეცდომიანი გამოძახების საპოვნელად, გამოიძახეთ ის `status: "failure"`, `git_branch` და `page_size: 1` პარამეტრებით. REST endpoint `GET /api/projects/{account_handle}/{project_handle}/bazel/invocations` იღებს იგივე ფილტრებს.

დააყენეთ `remote_execution: true` `list_bazel_build_steps`-ზე, რათა დაბრუნდეს მხოლოდ ის action-ები, რომლებსაც უსაფრთხოდ აქვთ მიბმული სერვერის ფაზების დრო ინდექსირებული პროფილებიდან. სიისა და დეტალური პასუხები ასახავენ არასავალდებულო nullable `remote_queue_ms`, `remote_input_fetch_ms`, `remote_execution_ms` და `remote_output_upload_ms`-ს. მნიშვნელობები ჯამავს ჩაწერილ ფაზებს, action-ის შიგნით განმეორებების ჩათვლით; არარსებული ან null მნიშვნელობები ნიშნავს ხელმიუწვდომლობას, არა ნულს. ისინი არის პროფილის დაკვირვებები, არა გადასახდელი გამოყენება ან ახალი შესრულების დამტკიცება, რადგან cached სერვერის შედეგებს შეიძლება ჰქონდეთ შესრულების მეტამონაცემები. კლიენტის ატვირთვები გამოტოვებულია. ძველმა ან ბუნდოვანმა პროფილებმა შეიძლება არ დააბრუნონ შესაბამისი action-ები მაშინაც კი, როცა remote სამუშაო შესრულდა. ნაბიჯის REST endpoint იღებს იგივე `remote_execution=true` ფილტრს. დაშბორდის Remote execution ტაბი იყენებს იგივე მოთხოვნას და 90-დღიან შენახვას.

ტესტის ლოგებს აქვს `target_label` და ცდის `status` იმ ტესტის შედეგიდან, საიდანაც ისინი მოდიან, ამიტომ `target_label: "//foo:bar_test"` აბრუნებს მხოლოდ იმ target-ის ტესტის ლოგებს. `errors: true` აბრუნებს შეცდომიანი ცდების ტესტის ლოგებს და stderr პროგრესის ნაწილებს, რომლებიც შეიცავენ ხაზს, რომლითაც Bazel-ის მომხსენებელი იწყება: `ERROR:`, `FAIL:` ან `TIMEOUT:`. პროგრესის გამოტანა არ არის მიკუთვნებული target-ებზე და მიკუთვნების ჩაწერამდე დაწერილ ლოგებს აქვთ ცარიელი ველები. შეცდომიანი action-ები და მათი საკუთარი გამოტანა ხელმისაწვდომია თითო target-ზე `list_bazel_build_steps`-დან, ხოლო თითო-ტესტ-ქეისის შეცდომები ტესტების გაშვების ხელსაწყოებიდან.

Trace შეიცავს ჩაწერილ ნაბიჯებს, რომლებიც პარალელიზმის მიხედვით ზოლებად არის დალაგებული, ტრეკს, რომელიც მოიცავს მთელ ბილდს, და CPU და მეხსიერების მრიცხველებს, როცა ბილდი იწერდა მანქანურ მეტრიკებს. ის ინახავს იგივე მონაცემებს, რაც ზემოთ აღნიშნული ნაბიჯის ხელსაწყოები, ლოგების გარეშე. Dashboard გთავაზობთ იგივე ფაილს თითოეული ბილდის Timeline ტაბიდან.

ეს ხელსაწყოები ეტაპობრივად ნაწილდება და აბრუნებენ მონაცემებს მხოლოდ იმ პროექტებისთვის, სადაც ისინი ჩართულია; სხვა პროექტებისთვის ისინი აბრუნებენ შეცდომას ცარიელი შედეგის ნაცვლად. სახე ხელმისაწვდომია მხოლოდ იმ პროექტებისთვის, რომლებიც იყენებენ მის ბილდის ხელსაწყოთა ჯაჭვს. ხელსაწყოები იღებენ შეზღუდულ `start_at`/`end_at` ფილტრებს, `environment` (`any`, `ci` ან `local`) და ზუსტ `branch`. `list_build_entities` იღებს `q`-ს; `list_build_entity_history` მხარდაჭერს გამჭვირვალე `after`/`before` კურსორებს. უცნობი დროის ან cache დაკვირვებები რჩება ხელმიუწვდომელი ნულის ან გამოტოვების ნაცვლად. ისტორია მიუთითებს ჩაწერილ მშობელს და ნატიურ შესრულებას დეტალური შესწავლისთვის არსებული გაშვების ხელსაწყოების გამოყენებით.

`get_build_entity` მეტრიკები მოიცავს `duration_samples`-ს, დაკვირვებების რაოდენობას ჩაწერილი დროით: ნამდვილი ნულოვანი ხანგრძლივობები ითვლება, დაკარგული დრო — არა. ეს რაოდენობა შეიძლება იყოს დაკვირვებების რაოდენობაზე ნაკლები; ხელმიუწვდომელი ხანგრძლივობის სტატისტიკა რჩება null.

Xcode მოდულების ხანგრძლივობა მოდის ბილდის ლოგებში გაზომილი სამიზნე კომპილაციებიდან. მოდულის cache გადაწყვეტები და სამიზნეები კომპილაციის სამუშაოს გარეშე არ მონაწილეობენ ხანგრძლივობის ნიმუშებში. კომპილაციის დაკვირვებები მიუთითებენ Xcode ბილდზე; cache მოვლენები მიუთითებენ გენერაციის ან cache ბრძანებაზე.

Bazel მოქმედებები იდენტიფიცირდება სამიზნე ლეიბლით, მნემონიკით და კონფიგურირებული ძირითადი გამომავალით, რაც ინარჩუნებს ცალკეულ მოქმედებებს და კონფიგურაციებს განცალკევებულს შეყვანაზე დამოკიდებული cache digest-ების გარეშე. ისტორია იწერს BEP-ით მოხსენებულ შესრულებებს, არა cache ძიებებს ან trace-profil-ის ფაზებს. სრული შესრულების დაფარვა მოითხოვს `--build_event_publish_all_actions`-ს; არტეფაქტების მიწოდება საუკეთესო ძალისხმევით ხდება, ამიტომ დაკარგული დაკვირვებები არ არის მტკიცებულება, რომ სამუშაო არ შესრულებულა. ძველი Kura payload-ები სტაბილური იდენტობის ან შესრულების დასაწყისის გარეშე რჩება მიღებული, მაგრამ არაინდექსირებული. დასასრულის დროის გაზომვების არარსებობა რჩება ხელმიუწვდომელი და ნამდვილი ნულოვანი ხანგრძლივობები ითვლება.

Mix მოდულების ხანგრძლივობა ზომავს შემცველი ფაილის კომპილაციას, არა დამოუკიდებლად გაზომილ მოდულის სამუშაოს. Once მოქმედებები იყენებენ გამოცხადებულ სამიზნე/შესაძლებლობა/ინდექს სლოტებს, როცა კლიენტმა მოახსენა სამიზნე ასოციაციები; დიაგნოსტიკური ლეიბლები მარტო არ არის სტაბილური იდენტობები. არსებული კლიენტები და გაშვების დონის ხელსაწყოები რჩება მხარდაჭერილი უცვლელად.

Cargo კრეიტები დაჯგუფებულია ზუსტად ჩაწერილი კრეიტის root-ის, სახელის და სახის მიხედვით. Checkout-ბილიკის ცვლილებებმა შეიძლება გაყოს ისტორიები და ბილდის პროფილები, ფუნქციები და სამიზნე triples არ განირჩევა. ისტორია ზომავს rustc გამოძახებებს, არა ფაილზე დამოკიდებულ სამუშაოს ან cache hits; არარსებული სამუშაოები არ ამყარებს წაშლებს ან სრულ workspace ინვენტარს.

ანალიტიკის წაკითხვებს აქვს შეზღუდული მეხსიერება და შესრულების დრო. თუ მოთხოვნა აღემატება ამ ლიმიტებს, ხელსაწყო აბრუნებს შეცდომას ცარიელი შედეგის გამოგონების ნაცვლად.

ახალი დაკვირვებები ინდექსირდება განლაგების შემდეგ; ეს ფუნქცია არ ავსებს არსებულ გაშვების ტელემეტრიას. იდენტობის მეტამონაცემები ცოცხლობს ინდივიდუალურ დაკვირვებებზე მეტხანს <.localized_link href="/guides/server/data-retention">data-retention policy</.localized_link>-ის შესაბამისად.

### მოვლენები

კლიენტები, რომლებიც იყენებენ stateless `2026-07-28` Model Context Protocol ლაიფციკლს, შეუძლიათ გამოიძახონ `events/list` მოვლენების და მათი payload სქემების აღმოსაჩენად:

| მოვლენა | როდის იგზავნება | გამოწერის ფილტრი |
|-------|-----------------|---------------------|
| `test_case.marked_flaky` | სატესტო შემთხვევა იცვლება არაფლაკიდან ფლაკზე. | `account_handle`, `project_handle` |
| `build.failed` | ლოკალური ან უწყვეტი ინტეგრაციის Xcode, Gradle ან Bazel ბილდი სრულდება შეცდომით. | `account_handle`, `project_handle` |
| `test_run.failed` | ლოკალური ან უწყვეტი ინტეგრაციის ტესტების გაშვება სრულდება შეცდომით, შერწყმული შარდირებული გაშვების ან მიტოვებული გაშვების ჩათვლით. | `account_handle`, `project_handle` |
| `ci_job.failed` | Tuist runner-ის სამუშაო სრულდება შეცდომით. | `account_handle` |

გამოსაწერად, კლიენტი იძახებს `events/subscribe` მოვლენის სახელით, ზემოთ ჩამოთვლილი handles-ით `arguments`-ში და `webhook` მიწოდებით, რომელიც შეიცავს `https://` callback URL-ს და `whsec_` ხელმოწერის საიდუმლოს. პროექტის მოვლენები მოითხოვს ანგარიშის წევრობას და შესაბამის ტესტ ან ბილდ მონაცემებზე წვდომას; runner-ის სამუშაოს მოვლენები მოითხოვს ანგარიშის წევრობას და runner-ზე წვდომას. Claimed [`auth.md`](https://workos.com/auth-md) access tokens, claimed account tokens და ბრაუზერის ავტორიზაციის გრანტები შეუძლიათ შექმნან გამოწერები; მიწოდება ჩერდება, როდესაც შესაბამისი credential აღარ არის აქტიური. თითოეულ მომხმარებელს შეუძლია ჰქონდეს მაქსიმუმ 25 აქტიური გამოწერა. Tuist აგზავნის ვერიფიკაციის challenge-ს callback-ზე გამოწერის შენახვამდე. Callback-მა უნდა დააბრუნოს ობიექტი, რომელიც შეიცავს იგივე `challenge` მნიშვნელობას. გამოწერა ძალაშია შვიდი დღის განმავლობაში ნაგულისხმევად, შეიძლება განახლდეს ხელახლა გამოწერით და ჩერდება მიწოდება, როდესაც მომხმარებლის წვდომა ან credential ამოღებულია. არასავალდებულო `ttlMs` შეზღუდულია ერთ საათსა და 30 დღეს შორის. Tuist ახდენს timed-out callback-ის ხელახლა ცდას და აუქმებს მას სამი თანმიმდევრული timeout-ის შემდეგ, რომლებიც მოიცავს ხუთ წუთს; ხელახლა გამოიწერეთ callback-ის აღდგენის შემდეგ.

როდესაც მოვლენა ხდება, Tuist აგზავნის მის რესურსის იდენტიფიკატორს და დაშბორდის URL-ს callback-ზე. ბილდის და ტესტების გაშვების შეცდომები ასევე შეიცავს `is_ci`-ს და `git_branch`-ს, რათა კლიენტებმა შეძლონ ლოკალური შეცდომების იგნორირება ან ბრენჩის მიხედვით გაფილტვრა. ბილდის მოვლენები შეიცავს `build_system`-ს; runner-ის სამუშაოს მოვლენები შეიცავს როგორც `workflow_job_id`-ს, ასევე `workflow_run_id`-ს. მოთხოვნა შეიცავს გამოწერის იდენტიფიკატორს და [Standard Webhooks](https://www.standardwebhooks.com/) ხელმოწერის ჰედერებს, რათა კლიენტმა შეძლოს მისი წარმოშობის ვერიფიცირება. Tuist ახდენს შეუძლებელი მიწოდებების ხელახლა ცდას, ამიტომ კლიენტებმა უნდა გამოიყენონ სტაბილური `eventId` დუბლიკატების გასაფილტრად. Payload გამოტოვებს ტესტების სახელებს, ლოგებს და შეცდომის შეტყობინებებს; კლიენტმა შეუძლია მიიღოს ეს დეტალები ზემოთ ჩამოთვლილი ხელსაწყოების მეშვეობით და გადაწყვიტოს, შეატყობინოს თუ არა გუნდს ან დაიწყოს დებაგინგი. კლიენტებმა შეუძლიათ შეაჩერონ მიწოდება `events/unsubscribe`-ით.

#### Gradle ინტეგრაციის პრომპტის ფუნქციები

`integrate_gradle_project` პრომპტი და `get_gradle_integration_guide` ხელსაწყო აღწერენ სრულ დაყენების სამუშაო ნაკადს. ხელსაწყო ასევე არის მითითებული სერვერის ინიციალიზაციის ინსტრუქციებში, რაც მას აღმოჩენადს ხდის აგენტებისთვის, რომლებიც არ ჩამოთვლიან პრომპტებს.

| ფუნქცია | რას აკონფიგურირებს აგენტი |
|---------|---------------------------|
| `remote_cache` | ააქტიურებს Gradle-ის ბილდ ქეშს, აკონფიგურირებს Tuist დაშორებული ქეშის ატვირთვის პოლიტიკას და რეკომენდაციას უწევს ატვირთვას მხოლოდ უწყვეტი ინტეგრაციის რანერებიდან ლოკალური მხოლოდ-წაკითხვის გამოყენებით. |
| `build_insights` | აყენებს Tuist Gradle პლაგინს და აკონფიგურირებს ბილდის ანალიტიკის ატვირთვის ქცევას საჭიროების შემთხვევაში. |
| `test_insights` | აყენებს Tuist Gradle პლაგინს, რათა Gradle `Test` ამოცანის შედეგები ავტომატურად აიტვირთოს. |
| `flaky_tests` | გიძღვებათ არასტაბილური ტესტების აღმოჩენის დაყენებაში, Gradle Test Retry პლაგინის არასავალდებულო გამოყენებაში და ტესტის კარანტინის კონფიგურაციაში. |
| `test_sharding` | ამატებს უწყვეტი ინტეგრაციის სამუშაო ნაკადს `tuistPrepareTestShards`-თვის, შარდის მატრიცის გენერაციას და `TUIST_SHARD_INDEX`-ზე დაფუძნებულ ტესტის შესრულებას. |

როდესაც `features` გამოტოვებულია, პრომპტი სთხოვს აგენტს განაზომოს, რომელი ინტეგრაციები სურს მომხმარებელს ან გამოიტანოს ყველაზე მცირე სასარგებლო ნაკრები მოთხოვნის მიხედვით Gradle პროექტის რედაქტირებამდე.

#### Xcode ინტეგრაციის პრომპტის ფუნქციები

`integrate_xcode_project` პრომპტი აღწერს ყველა Xcode ინტეგრაციას, რომელსაც Tuist უჭერს მხარს:

| ფუნქცია | რას აკონფიგურირებს აგენტი |

| `xcode_cache` | აკონფიგურირებს `tuist setup cache`, გენერირებული პროექტის ქეშის პარამეტრებს, Xcode ქეშის ბილდის ხელით მითითებულ პარამეტრებს და ატვირთვის პოლიტიკას, რომელიც შეზღუდულია უწყვეტი ინტეგრაციის რანერებით. |

| `test_sharding` | ამატებს Xcode ან გენერირებული პროექტის შარდის დაგეგმვის და შარდის შესრულების სამუშაო ნაკადს `TUIST_SHARD_INDEX`-თან ერთად. |

როდესაც `features` გამოტოვებულია, პრომპტი სთხოვს აგენტს განაზომოს, რომელი ინტეგრაციები სურს მომხმარებელს ან გამოიტანოს ყველაზე მცირე სასარგებლო ნაკრები მოთხოვნის მიხედვით Xcode პროექტის რედაქტირებამდე.
