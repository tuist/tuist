# Model Context Protocol

[Model Context Protocol (MCP)](https://modelcontextprotocol.io/docs/getting-started/intro) არის ღია სტანდარტი, რომელიც საშუალებას აძლევს ხელოვნური ინტელექტის აგენტებს ურთიერთქმედონ გარე სერვისებთან და მონაცემთა წყაროებთან. ის უზრუნველყოფს [Claude](https://claude.ai/)-ის, [Claude Code](https://docs.anthropic.com/en/docs/claude-code)-ის, [Codex](https://developers.openai.com/codex/)-ისა და ისეთი რედაქტორების, როგორიცაა [Zed](https://zed.dev), [Cursor](https://www.cursor.com) ან [Visual Studio Code](https://code.visualstudio.com), თავსებადობას Tuist-თან.

Tuist განათავსებს Model Context Protocol-ის სერვერულ ენდპოინტს მისამართზე `https://tuist.dev/mcp`. თქვენი კლიენტის მასთან დაკავშირებით, აგენტებს შეუძლიათ მიიღონ წვდომა თქვენს Tuist პროექტის მონაცემებზე, მათ შორის ტესტების ანალიტიკაზე, არასტაბილური ტესტების ანალიზზე და სხვა. უმეტესი ინსტრუმენტი კითხულობს Tuist-ის მონაცემებს, რომელთა ნახვაც ავტორიზებულ მომხმარებელს უკვე შეუძლია დაფაზე. ყოველი ინსტრუმენტი ასახავს ანოტაციებს, რომლებიც მიუთითებს, არის თუ არა ის მხოლოდ წაკითხვისთვის, შეუძლია თუ არა გამოიწვიოს რთულად შექცევადი ცვლილება (`destructiveHint`), და შეუძლია თუ არა გასვლა Tuist-ის ფარგლებს გარეთ (`openWorldHint`). ინსტრუმენტები, რომლებიც ცვლიან მდგომარეობას და თითოეული შეზღუდულია მომხმარებლის ანგარიშის ან პროექტის ნებართვებით, არის:

- **ორგანიზაციები და წევრები**: `create_organization`, `add_organization_member` (ამატებს არსებულ მომხმარებელს ან ცვლის წევრის როლს), `invite_organization_member` (გზავნის მოწვევას ნებისმიერ ელფოსტის მისამართზე) და `cancel_organization_invitation`.
- **პროექტები**: `create_project`, `start_project_logo_upload` და `complete_project_logo_upload` (ცვლის ლოგოს), `connect_project_repository` და `disconnect_project_repository` (GitHub რეპოზიტორიის ბმულები).
- **ტესტები**: `update_test_case` (აჩუმებს, ატოვებს, ხელახლა ააქტიურებს ან მონიშნავს სატესტო შემთხვევას არასტაბილურად; ცვლილება შეიძლება მიაღწიოს ანგარიშის webhook ენდპოინტებს).
- **შეტყობინებების წესები**: `create_notification_rule`, `update_notification_rule` და `delete_notification_rule`.
- **უწყვეტი ინტეგრაციის გამშვები აგენტები**: `create_runner_profile`, `update_runner_profile` (კეშის დაცვის მოცულობების შენახვის სამუშაოების შევიწროება აუქმებს ლოდინში მყოფ შენახვებს), `delete_runner_profile` და `delete_runner_volume` (შლის მოცულობაში შენახულ შიგთავსს).
- **საიდუმლო გარემოები (Sandboxes)**: `create_sandbox`, `pause_sandbox`, `resume_sandbox`, `archive_sandbox` და `delete_sandbox` (შლის მის დისკებს).
- **უკუკავშირი**: `report_feedback` (გზავნის ანგარიშს ინსტრუმენტის ან მოთხოვნის შესახებ Tuist-ის გუნდს; მხოლოდ tuist.dev-ზე).
- **ორგანიზაციის AI**: `save_organization_ai_model`, `remove_organization_ai_model`, `set_organization_ai_default_model`, `save_organization_ai_task_route`, `remove_organization_ai_task_route` და `remove_organization_ai_provider` (შლის პროვაიდერის გასაღებს და მოდელებს, და ხსნის Anthropic-ში დაკავშირებულ Claude ორგანიზაციას).
- **აგენტის ინტეგრაციები**: `connect_amp_workspace` (ანიჭებს სამუშაო სივრცის orbs CI-ს წვდომას ანგარიშზე), `disconnect_amp_workspace` და `connect_claude_environment` (საშუალებას აძლევს Claude Managed Agents გარემოს გაუშვას სესიები Tuist-ის საიდუმლო გარემოებში).

`add_organization_member`, `cancel_organization_invitation`, `complete_project_logo_upload`, `disconnect_project_repository`, `update_test_case`, `update_notification_rule`, `delete_notification_rule`, `update_runner_profile`, `delete_runner_profile`, `delete_runner_volume`, `delete_sandbox`, `disconnect_amp_workspace`, `remove_organization_ai_provider`, `remove_organization_ai_model` და `remove_organization_ai_task_route` ასახავენ `destructiveHint: true`-ს, რადგან ისინი ცვლიან ან აშორებენ არსებულ მდგომარეობას. `invite_organization_member`, `update_test_case`, `connect_claude_environment`, `remove_organization_ai_provider` და `report_feedback` ასახავენ `openWorldHint: true`-ს, რადგან ისინი გზავნიან ელფოსტას, აცნობებენ გარე webhook ენდპოინტებს, უკავშირდებიან Anthropic-ს ან გზავნიან ანგარიშს Tuist-ის გუნდს.

პირადი Claude და ChatGPT გამოწერები დაკავშირებულია მხოლოდ დაფის AI პარამეტრებში, ამიტომ გამოწერის ტოკენები და შესვლები არასდროს გადის Model Context Protocol კლიენტის მეშვეობით. ანგარიშის დაყენების ინსტრუმენტები მოითხოვს მომხმარებლის ავტორიზაციას. ისინი არ არის ხელმისაწვდომი პროექტის ტოკენების ან ჩვეულებრივი ანგარიშის ტოკენებისთვის. როდესაც მომხმარებელი ავტორიზებს კლიენტს ბრაუზერში ან ითხოვს `auth.md` რეგისტრაციას, Tuist აკავშირებს ამ სერთიფიკატს მომხმარებელთან მხოლოდ Model Context Protocol ენდპოინტზე, რათა დაყენების ინსტრუმენტებმა შეძლონ მოთხოვნილი სამუშაო პროცესის დასრულება.

Tuist ახორციელებს [2026-07-28 პროტოკოლს](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http). მოთხოვნები არის უმდგომარეობო: კლიენტები აგზავნიან თავიანთ პროტოკოლის მეტამონაცემებს ყოველ მოთხოვნასთან ერთად და შეუძლიათ პირდაპირ გამოიძახონ ინსტრუმენტები ინიციალიზაციის გარეშე. `server/discover` აბრუნებს სერვერის იდენტურობას, შესაძლებლობებს, მხარდაჭერილ ვერსიებს და ინსტრუქციებს. არ არსებობს სესიის იდენტიფიკატორები ან დამოუკიდებელი მოვლენათა ნაკადები. კლიენტები, რომლებიც იყენებენ 2025-06-18 ან 2025-03-26 ინიციალიზაციის ნაკადს, კვლავ მხარდაჭერილია; ისინიც მუშაობენ სერვერის სესიების გარეშე.

## Model Context Protocol უნარების წინააღმდეგ

Model Context Protocol-ის ინსტრუმენტებს და <.localized_link href="/guides/features/agentic-coding/skills">უნარებს</.localized_link> შეიძლება ჰქონდეთ გადახურვა შესრულებულ ფუნქციებში. არსებული გადახურვის გათვალისწინებით, აირჩიეთ ერთი მიდგომა თითოეული სამუშაო პროცესისთვის და გამოიყენეთ ის თანმიმდევრულად, ნაცვლად ორივეს ერთ ნაკადში შერევისა.

კლიენტებისთვის, რომლებიც მხარს უჭერენ პლაგინების დაყენებას, გამოიყენეთ <.localized_link href="/guides/features/agentic-coding/plugins">Tuist პლაგინები</.localized_link> ორივეს ერთად დასაყენებლად.

## კონფიგურაცია

დაამატეთ `https://tuist.dev/mcp` როგორც დაშორებული Model Context Protocol სერვერი თქვენს კლიენტში. სერვერის ინიციალიზაციის ინსტრუქციები და საჯარო სერვერის ბარათი აღწერს OAuth 2.0-ს დინამიური კლიენტის რეგისტრაციით და სტანდარტული ბრაუზერის ავტორიზაციის ნაკადით პირდაპირ, აგენტებისგან გარე ავთენტიკაციის დოკუმენტების მოთხოვნის ან მათი მიყოლის გარეშე. ეს სერვერის მასშტაბის ინსტრუქციები ინარჩუნებს სამუშაო პროცესის მითითებებს ზოგადს: ინსტრუმენტის ავთენტიკაცია არ ავთენტიკაციებს ადგილობრივ ბრძანების სტრიქონის ინსტრუმენტებს ან აგების სისტემის ინტეგრაციებს, და აგენტებმა უნდა გადაამოწმონ მოთხოვნილი ცვლილებები შესაბამისი Tuist ინსტრუმენტების მეშვეობით. აგების სისტემის სპეციფიკური დაყენება და ავთენტიკაციის შემოწმებები დოკუმენტირებულია ინტეგრაციის სახელმძღვანელოებში და მოთხოვნებში. Tuist კვლავ ასახავს როგორც [Open Authorization](https://oauth.net/2/) აღმოჩენის მეტამონაცემებს, ასევე მიმდინარე [auth.md პროტოკოლს](https://workos.com/auth-md) მისამართზე `https://tuist.dev/auth.md` ცალკე.

თუ თქვენი ერთ-ერთი ორგანიზაცია აიძულებს ერთჯერად შესვლას (SSO), ბრაუზერში კლიენტის ავტორიზაცია მოითხოვს სესიას, რომელიც შესულია ამ ორგანიზაციის მეშვეობით, და Tuist საჭიროების შემთხვევაში ჯერ პროვაიდერზე გაგზავნით. იხილეთ <.localized_link href="/guides/integrations/authentication/sso#choose-an-enrollment-policy">ერთჯერადი შესვლა</.localized_link>.

ენდპოინტი იღებს უმდგომარეობო `2026-07-28` Model Context Protocol მოთხოვნის სიცოცხლის ციკლს, მათ შორის `server/discover`-ს, ძველ სესიაზე დაფუძნებულ ციკლთან ერთად. არსებულმა კლიენტებმა შეიძლება განაგრძონ თავიანთი მიმდინარე დაკავშირების მეთოდის გამოყენება.

კლიენტებს, რომლებიც მხარს უჭერენ Model Context Protocol მოვლენებს, შეუძლიათ გამოიწერონ პროექტის მოვლენები. იხილეთ [მოვლენები](#events) ხელმისაწვდომი მოვლენებისა და მიწოდების მოთხოვნებისთვის.

კლიენტებს, რომლებიც უკვე მხარს უჭერენ დაშორებულ ბრაუზერის ავთენტიკაციას, შეუძლიათ განაგრძონ ბრაუზერში ავთენტიკაცია. კლიენტებს და აგენტებს, რომლებიც მხარს უჭერენ `auth.md`-ს, შეუძლიათ დარეგისტრირდნენ ანონიმურად, წარადგინონ სანდო პროვაიდერის იდენტურობის დამოწმება ან დაიწყონ სერვისით ავთენტიკირებული ელფოსტის მოთხოვნა. რეგისტრაცია აბრუნებს Tuist-ით ხელმოწერილ იდენტურობის დამოწმებას, რომელსაც აგენტი ცვლის სტანდარტულ ტოკენის ენდპოინტზე ერთსაათიანი წვდომის ტოკენისთვის. Tuist აქვეყნებს თავის საჯარო ხელმოწერის გასაღებს და მხარს უჭერს სტანდარტულ ტოკენის გაუქმებასა და პროვაიდერის უსაფრთხოების მოვლენების მიწოდებას.

არაავთენტიკირებულმა აგენტმა უნდა წაიკითხოს `WWW-Authenticate` ჰედერი, რომელსაც Model Context Protocol ენდპოინტი აბრუნებს, მოიძიოს დაცული რესურსის მეტამონაცემები, მოიძიოს ავტორიზაციის სერვერის მეტამონაცემები და მიჰყვეს მის `agent_auth.skill` URL-ს. Tuist ასევე აბრუნებს იგივე ადგილობრივ `auth_md` URL-ს არაავტორიზებული პასუხის სხეულში, რათა ენის მოდელებზე დაფუძნებულმა კლიენტებმა აღმოაჩინონ ნაკადი ნატიური კლიენტის ინტეგრაციაზე დამოკიდებულების გარეშე. განლაგებისთვის ადგილობრივი დოკუმენტი არის საიმედო წყარო ენდპოინტების სახელების, მოთხოვნის სხეულების, მოთხოვნის გამოკითხვისა და დამოწმების გაცვლისთვის.

სანამ აგენტი ელფოსტის მოთხოვნას დაიწყებს, მან უნდა სთხოვოს მომხმარებელს დაადასტუროს თავისი Tuist ანგარიშის ელფოსტის მისამართი. მას არ უნდა გამოიტანოს ეს მისამართი პროვაიდერის პროფილიდან, Git კონფიგურაციიდან, გარემოს ცვლადიდან ან სესიის მეტამონაცემებიდან.

ენდპოინტი იყენებს `mcp` სკოუპების ჯგუფს. ანონიმურმა წინასწარი მოთხოვნის კრედენციალმა შეიძლება აღმოაჩინოს შესაძლებლობები და წაიკითხოს საჯარო ინტეგრაციის სახელმძღვანელო, მაგრამ ის არ განიხილება როგორც შესული მომხმარებელი. ბრაუზერის ავტორიზაციის ან მოთხოვნის შემდეგ, კრედენციალი არის მომხმარებელზე ორიენტირებული და თითოეული ხელსაწყო ახორციელებს იგივე ავტორიზაციის შემოწმებებს, რასაც დაშბორდი. დეტალებისთვის იხილეთ <.localized_link href="/guides/server/authentication#scope-groups">სკოუპების ჯგუფების დოკუმენტაცია</.localized_link>.

ხელსაწყოები გადაჰყავთ პროექტებზე, რომელთა წაკითხვაც ავთენტიკირებულ მომხმარებელს უკვე შეუძლია. Xcode და Gradle აგების ხელსაწყოები იღებენ აგების UUID-ს ან დაშბორდის URL-ს. UUID-მ უნდა განსაზღვროს ზუსტად ერთი პროექტი; თუ ის რამდენიმე პროექტში ჩანს, ხელსაწყო აბრუნებს „არ არის ნაპოვნი“-ს სხვა პროექტის ანგარიშის შერჩევის ნაცვლად. პროექტზე ორიენტირებული დაშბორდისა და API წაკითხვები რჩება ხელმისაწვდომი. მოხსენებული აქტორის იდენტიფიკატორები არის დაუდასტურებელი ეტიკეტები, არა კრედენციალები ან დამატებითი წვდომის უფლებები.

აგების სიისა და დეტალური ინფორმაციის ხელსაწყოები აჩვენებენ არააუცილებელ `tuist_version` მეტამონაცემებს: Xcode-ისა და Cargo-სთვის მომხსენებელი Tuist CLI, Tuist Gradle პლაგინი Gradle-ისთვის და `tuist_ex` ბიბლიოთეკა Mix-ისთვის. Xcode ასევე აჩვენებს `tuist_generation_version`-ს თავისი დაკავშირებული პროექტის გენერაციის მოვლენიდან, რომელიც შეიძლება განსხვავდებოდეს ატვირთვადი CLI-სგან. დაკარგული დაკვირვებები არის null, არა გამოტანილი სერვერიდან ან სხვა ანგარიშიდან. Bazel იყენებს თავის არსებულ `bazel_version`-ს; Struo გაშვების დეტალები აჩვენებენ `once_version`-ს. ეს ველები აღწერენ მოხსენებულ ვერსიებს, არა დადასტურებულ იდენტურობას ან სადენის კონტრაქტის ვერსიებს. REST აგების ენდპოინტები აჩვენებენ იგივე მეტამონაცემებს. არსებული ინტეგრაციისა და არასტაბილური ტესტების უნარები არ არის დამოკიდებული ვერსიის ველებზე და არ საჭიროებს სამუშაო ნაკადის ცვლილებებს.

Tuist ოპერატორები, რომლებიც იკვლევენ მომხმარებლის ანგარიშს, ამას აკეთებენ Tuist-ის შიდა ოპერაციული ხელსაწყოების მეშვეობით, რომელიც იწერს ყოველ ზარს; ამ ენდპოინტთან პირდაპირი კავშირი არ იძლევა წვდომას მომხმარებლის საკუთარი წევრობის ფარგლებს გარეთ.

### Pulse

Pulse აჩვენებს მხოლოდ წაკითხვად ხელსაწყოებს ანგარიშის ოპერაციული მეტრიკების, ლოგების, ტრეისებისა და შეცდომებისთვის, რომლებიც ყველა მიმართულია `account_handle`-ით. პირველი სამი ასახავს Pulse გვერდებსა და მათ REST API-ს; დანარჩენი ხუთი საშუალებას აძლევს აგენტს პირდაპირ შეისწავლოს ტელემეტრია და არ აქვთ REST ეკვივალენტი:

| ხელსაწყო | მიზანი | REST ეკვივალენტი `/api/accounts/:account_handle/pulse` ქვეშ |
| --- | --- | --- |
| `query_pulse` | Pulse გვერდის ცხრილები | `GET /:signal` |
| `get_pulse_analytics` | Pulse გვერდის ვიჯეტები | `GET /:signal/analytics` |
| `get_pulse_error_issue` | ერთი შეცდომის პრობლემა და მისი მოვლენები | `GET /errors/issues/:fingerprint` |
| `query_pulse_metrics` | მყისიერი ან დიაპაზონის PromQL | არ არის |
| `list_pulse_labels` | ეტიკეტების სახელები, ან ერთი ეტიკეტის მნიშვნელობები | არ არის |
| `search_pulse_logs` | ფილტრული ლოგის ჩანაწერები | არ არის |
| `search_pulse_traces` | ფილტრული სპენები | არ არის |
| `get_pulse_trace` | ერთი ტრეისის ყოველი სპენი | არ არის |

Pulse შეზღუდულია სერვერზე კონფიგურირებული ორგანიზაციის მიმდინარე წევრებისთვის, მაშინაც კი, თუ ანგარიში ან პროექტი საჯაროა. ის მოითხოვს მომხმარებლის ავთენტიკაციას ან მომხმარებელთან დაკავშირებულ `mcp` კრედენციალსა და ანგარიშის წაკითხვის ავტორიზაციას. პროექტის ტოკენები, ჩვეულებრივი ანგარიშის ტოკენები, ანონიმური რეგისტრაციები და ოპერატორის წვდომა ორგანიზაციის წევრობის გარეშე არ იძლევა Pulse წვდომას. კრედენციალებს არ შეუძლიათ აირჩიონ სხვა ბექენდი ან ტელემეტრიის მომხმარებელი, და მხოლოდ სერვერზე კონფიგურირებულ ანგარიშს აქვს Pulse ტელემეტრია, ამიტომ არცერთ ხელსაწყოს არ შეუძლია წაიკითხოს სხვა ანგარიშის მონაცემები. ბრაუზერის აგენტები იღებენ ამ ხელსაწყოებს მხოლოდ Pulse გვერდებზე, ამ გვერდის ანგარიშის სკოუპის ფარგლებში.

REST მოითხოვს მომხმარებლის კრედენციალს. OAuth და `auth.md` მომხმარებლის ასოციაციები ხელმისაწვდომია მხოლოდ `/mcp` ენდპოინტზე; ანგარიშის კრედენციალი მიმდინარე მომხმარებლის გარეშე უარყოფილია, მიუხედავად დაკავშირებული ანგარიშის წევრობისა ან ხილვადობის.

`query_pulse` იღებს `signal` (`metrics`, `logs`, `traces`, ან `errors`), არააუცილებელ `query`-ს და `range`-ს (`15m`, `1h`, `6h`, ან `24h`, ნაგულისხმევი `1h`). მეტრიკები იღებენ PromQL გამოსახულებებს. ლოგები, ტრეისები და შეცდომები იღებენ ლიტერალურ, დამოუკიდებელ რეგისტრისგან ტექსტს, რომელიც შეესაბამება ლოგის სხეულებს, სპენის სახელებსა და შეცდომის პრობლემის სათაურებს; `*`, ნაგულისხმევი, ირჩევს ყველაფერს. ტრეისის სტრიქონები არის ინდივიდუალური სპენები. შეცდომის სტრიქონები არის პრობლემები: მოვლენები დაჯგუფებული სერვისისა და თითის ანაბეჭდის მიხედვით, მათი მოვლენების რაოდენობით, დაზარალებული ანგარიშებით, პირველი და ბოლო გამოჩენა ფანჯარაში, და მათი უახლესი მოვლენის სათაური, დამნაშავე, დონე და პლატფორმა. ცხრილები იღებენ `search`-ს, `page`-ს (ნაგულისხმევი `1`), `page_size`-ს (`1`–`100`, ნაგულისხმევი `20`), `sort_by`-ს და `sort_order`-ს (`asc` ან `desc`). დალაგების სვეტები დამოკიდებულია სიგნალზე და ჩამოთვლილია ხელსაწყოს სქემაში. ფილტრები მოიცავს `service`-ს და `level`-ს ლოგებისა და შეცდომებისთვის. ფილტრის ოპერატორები იყენებენ შესაბამის `_op` არგუმენტს (`eq`, `contains`, ან `not_contains`), ზუსტი ტოლობით ნაგულისხმევად.

დალაგების სვეტებია `name`/`value` მეტრიკებისთვის; `timestamp`/`service`/`level`/`message`/`trace_id` ლოგებისთვის; `timestamp`/`service`/`name`/`duration_ms`/`trace_id` ტრეისებისთვის; და `last_seen`/`first_seen`/`events`/`accounts`/`title`/`service`/`level` შეცდომებისთვის. დაშბორდი განზრახ აჩვენებს ქვესიმრავლეს; API და ხელსაწყოები იღებენ სრულ სიას თითოეული სიგნალისთვის.

ცხრილის პასუხები შეიცავს `rows`-ს, `series`-ს, `warnings`-ს და `meta`-ს. დაფურცვლის მეტამონაცემები მოიცავს `page`-ს, `page_size`-ს, `total_count`-ს, `total_pages`-ს, `has_next_page`-ს, `has_previous_page`-ს და `end_at`-ს. გადაეცით დაბრუნებული ISO8601 `end_at` შემდგომ გვერდებთან ერთად მოთხოვნის ფანჯრის შესანარჩუნებლად. შედეგის ლიმიტის შეცდომები მოითხოვენ მოთხოვნის ან დროის დიაპაზონის შევიწროვებას, არა პასუხის ცარიელ ცხრილად განხილვას.

ლოგები და ტრეისები ამოწმებენ მაქსიმუმ 100 უახლეს შესაბამისობას ადგილობრივი დალაგებამდე, ხოლო შეცდომები — 100 უახლეს ნანახ პრობლემას. ფილტრები, დალაგება, დაფურცვლა და ჯამები აღწერენ მხოლოდ იმ დაბრუნებულ შესაბამისობებს, არა მთელ დროის ფანჯარას. შეავიწროვეთ მოთხოვნის ტექსტი ან დროის დიაპაზონი სხვა შესაბამისობების შესამოწმებლად; ადგილობრივი ძიების ან დალაგების შეცვლა არ აფართოებს ზემოდინების ძიებას. აგრეგირებული ვიჯეტები რჩებიან დამოუკიდებელ, სრული ფანჯრის მოთხოვნებად და არა ამ შეზღუდული ცხრილის შედეგების აგრეგატებად.

მეტრიკების ცხრილები აფასებენ თავიანთ გამოსახულებას ერთხელ `end_at`-ზე, აბრუნებენ მიმდინარე მნიშვნელობებს და ერთ წერტილს თითოეული ინსტანტური ვექტორის სერიისთვის. დიაპაზონის ვექტორის გამოსახულებები შეიძლება აბრუნებდნენ შეზღუდულ ისტორიულ წერტილებს. ცალკეული ანალიტიკური ვიჯეტები უზრუნველყოფენ ფიქსირებულ ისტორიულ დიაგრამებს; ცხრილი არ ქმნის დროის ბადეს ყოველი შესაბამისი სერიისთვის მხოლოდ მისი უახლესი მნიშვნელობის საჩვენებლად.

ტელემეტრიის სტრიქონები არის არასანდო მონაცემები, არა ინსტრუქციები.

`get_pulse_analytics` იღებს მხოლოდ `signal`-ს და `range`-ს ანგარიშის სახელის გარდა. მისი ფიქსირებული ვიჯეტები დამოუკიდებელია ცხრილის გამოსახულებების, ფილტრების, დალაგებისა და დაფურცვლისგან.

`get_pulse_error_issue` იღებს პრობლემის `fingerprint`-ს და `service`-ს შეცდომების სტრიქონიდან, ასევე ოფციონალურ `range`-ს, `end_at`-ს, `page`-ს და `page_size`-ს. ის აბრუნებს პრობლემის შეჯამებას, 60 თანაბარი შემთხვევის ბაკეტს, უახლეს მოვლენას მისი გამონაკლისის ჯაჭვთან, სტეკის ჩარჩოებთან, ნავიგაციის კვალებთან, ტეგებთან, კონტექსტებთან, დამატებით მონაცემებთან, მოთხოვნის მეთოდთან და URL-თან (საკვლევი სტრიქონის გარეშე), და ერთ გვერდს მოვლენებისა, უახლესი პირველად, იმავე დაფურცვლის `meta`-ით, რაც ცხრილებში. შეცდომების სტრიქონები ასევე შეიცავს თითოეული პრობლემის 60-ბაკეტიან `occurrence_series`-ს. მოვლენები იწმინდება პირადი მონაცემებისგან შენახვამდე, ამიტომ გაფილტრული მნიშვნელობები ჩანს როგორც `[Filtered]` ან `[REDACTED]`. პრობლემა, რომელსაც არ აქვს მოვლენები ფანჯარაში, მოიხსენიება როგორც არაპოვნილი. REST და Model Context Protocol იყენებენ იმავე Pulse კონტექსტს და პასუხის ხელშეკრულებებს. REST პასუხები თიშავენ ქეშირებას.

#### ტელემეტრიის შესწავლა

შესწავლის ხელსაწყოები კითხულობენ ფანჯარას `15m`, `1h`, `6h`, ან `24h` (ნაგულისხმევი `1h`, და `24h` `get_pulse_trace`-სთვის), რომელიც მთავრდება ოფციონალური ISO8601 `end_at`-ზე, რომელიც ნაგულისხმევად არის ახლა. ყოველი პასუხი აბრუნებს `start_at`-ს და `end_at`-ს; გადაეცით იგივე `end_at` კვლავ ფანჯრის შესანარჩუნებლად. ამ ხელსაწყოებიდან არცერთი არ იღებს SQL-ს.

- `query_pulse_metrics` აფასებს `query`-ს, PromQL გამოსახულებას, `end_at`-ზე (`type: instant`, ნაგულისხმევი) ან ყოველ `step` წამში ფანჯრის განმავლობაში (`type: range`). ნაბიჯი ნაგულისხმევად არის და არ შეიძლება იყოს ნაკლები ფანჯარაზე გაყოფილი 360-ზე, ამიტომ სერიას აქვს მაქსიმუმ 361 წერტილი. შედეგებს აქვთ მაქსიმუმ 5,000 სერია. წერტილები არის `[unix_seconds, value]`, და `NaN` და უსასრულო მნიშვნელობები არის სტრიქონები. ინსტანტური მოთხოვნები უარყოფენ `range`-ს და `step`-ს.
- `list_pulse_labels` იღებს `signal`-ს. `label`-ის გარეშე, ის ჩამოთვლის ლეიბლების სახელებს; `label`-ით, ის ჩამოთვლის იმ ლეიბლის მნიშვნელობებს. მეტრიკებისთვის, `__name__` ჩამოთვლის მეტრიკების სახელებს, და ნებისმიერი სხვა ლეიბლის მნიშვნელობები მოითხოვენ `match`-ს, სერიის სელექტორს, როგორიცაა `up`. ლოგების და ტრეისის ლეიბლის მნიშვნელობები იღებენ `filters`-ს; ტრეისის ლეიბლის სახელები მოდის ტრეისის სქემიდან და არა. ლოგების და ტრეისის მნიშვნელობები შეიცავს მათი ჩანაწერების რაოდენობას ფანჯარაში, ყველაზე ხშირი პირველად, ამიტომ ისინი ასევე ემსახურებიან როგორც დაშლა, მაგალითად, შეცდომები სერვისის მიხედვით. `search` ინახავს მხოლოდ სახელებს ან მნიშვნელობებს, რომლებიც შეიცავს ლიტერალურ ტექსტს, და `limit` იღებს `1`–`1000` (ნაგულისხმევი `100`). ლოგის ლეიბლის სახელის აღმოჩენა ამოწმებს მაქსიმუმ 1,000 განსხვავებულ ატრიბუტთა ნაკრებს თითოეული სახის და ჩამოთვლის მხოლოდ გასაღებებს, რომლებსაც ფილტრები იღებენ.
- `search_pulse_logs` აბრუნებს მაქსიმუმ `limit` ჩანაწერს (`1`–`100`, ნაგულისხმევი `50`), `newest` ან `oldest` პირველად, რომელთა სხეული შეიცავს `text`-ს და რომლებიც ემთხვევა ყოველ ფილტრს. თითოეული ჩანაწერი შეიცავს მის `severity_text`-ს, `body`-ს, `trace_id`-ს, `span_id`-ს, `scope_name`-ს, და მის გაერთიანებულ რესურსის და ლოგის `attributes`-ს. `span_id` და `scope_name` არის `null` ლოგებისთვის, რომლებიც შეგროვებულია Kubernetes-დან, რასაც მხოლოდ OTLP ლოგის გამგზავნები აყენებენ.
- `search_pulse_traces` აბრუნებს მაქსიმუმ `limit` სპანს, `newest`, `oldest`, ან `slowest` პირველად, რომლებიც ემთხვევა ყოველ ფილტრს, ოფციონალურ `min_duration_ms`-ს და `max_duration_ms`-ს, და `root_only`-ს.
- `get_pulse_trace` აბრუნებს `trace_id`-ის სპანებს, რომლებიც იწყება ფანჯარაში, უძველესი პირველად, მაქსიმუმ 1,000 სპანი. ტრეისი, რომელიც დაიწყო ფანჯრამდე, აბრუნებულია ნაწილობრივ, ამიტომ გააფართოვეთ ან გადაადგილეთ ფანჯარა მისთვის. თითოეული სპანი შეიცავს მის სპანის ატრიბუტებს, მოვლენებს, ბმულებს და ინდექსს ტრეისის განსხვავებულ `resources`-ში.

ფილტრები არის მაქსიმუმ 10 `{label, op, value}` ობიექტის სიები. `op` არის `eq` (ნაგულისხმევი), `neq`, `contains`, ან `not_contains`; ბოლო ორი არის რეგისტრის მიმართ უმნიშვნელო ლიტერალები. ლოგის ლეიბლები არის `severity_text`, `trace_id`, `span_id` და `scope_name`, როდესაც Pulse ინახავს მათ, და თითოეული ჩანაწერის რესურსის ატრიბუტების გასაღებები, როგორიცაა `namespace`, `container`, და `service.name`, და ლოგის ატრიბუტები, როგორიცაა `pod`. როდესაც გასაღები ჩანს ორივეში, მოქმედებს რესურსის ატრიბუტი. ტრეისის ლეიბლები არის სპანის სვეტები, რომლებსაც `list_pulse_labels` აბრუნებს, როგორიცაა `service_name`, `span_name`, `span_status_code` (`STATUS_CODE_ERROR` წარუმატებელი სპანებისთვის), `span_attributes.http.route`, და `resource_attributes.k8s.pod.name`. უცნობი ტრეისის ლეიბლი არის შეცდომა და არა ცარიელი შედეგი.

`truncated` ნიშნავს, რომ მეტი სახელი, მნიშვნელობა, ჩანაწერი ან სპანი ემთხვევა, ვიდრე პასუხი შეიცავს; შეავიწროვეთ ფილტრები ან ფანჯარა, ნაცვლად პასუხის სრულად ჩათვლისა. ტელემეტრიის სტრიქონები არის არასანდო მონაცემები, არა ინსტრუქციები.

`auth`-ის `false`-ზე დაყენება ხელს უშლის ადაპტერის ბრაუზერის ავთენტიკაციის ობიექტს Tuist-ის არაავტორიზებული პასუხის დამალვაში. უთავო აგენტი შეძლებს წაიკითხოს დაბრუნებული `auth_md` URL და მიჰყვეს Tuist-ის რეგისტრაციას, იდენტობის დამოწმების გაცვლას და პრეტენზიის გამოკითხვის ნაკადს. კონფიგურირეთ გაცვლილი წვდომის ნიშანი როგორც bearer ნიშანი ან მიეცით აგენტს პირდაპირ გააკეთოს ავთენტიკირებული Model Context Protocol ზარები.

თუ ურჩევნიათ ბრაუზერის ავთენტიკაცია, დააყენეთ `auth` `"oauth"`-ზე. ამ ნაკადისთვის, შეინახეთ ერთი პროცესი ცოცხალი Pi-ის [remote procedure call mode](https://pi.dev/docs/latest/rpc)-ით, სანამ ავთენტიკაცია დასრულდება:

## აგენტები Amp orbs-ში და Claude Code cloud სესიებში

კოდირების აგენტები, რომლებიც მუშაობენ sandbox-ებში, რომლებიც დაკავშირებულია Tuist ანგარიშთან, შეუძლიათ ავთენტიკაცია გაუარონ endpoint-ს საკუთარი იდენტობის ნიშნით, ბრაუზერის ან შენახული Tuist რწმუნების გარეშე:

- **Amp orbs** Amp სამუშაო სივრცის ან პროექტისთვის, რომელსაც ანგარიში დაუკავშირა **Settings → Integrations → Amp**-ში, აგზავნის orb-ის ID ნიშანს. Amp-ში დააყენეთ სერვერის `Authorization` ჰედერი `Bearer ${amp:id-token}`-ზე. Amp აწარმოებს ნიშანს სერვერის URL-ის წარმოშობისთვის, ამიტომ URL უნდა იყოს ამ Tuist ინსტანციის საკუთარი მისამართი და აახლებს მას ვადის გასვლამდე. სხვა წარმოშობისთვის გამოშვებული ნიშნები უარყოფილია.
- **Claude Code cloud sessions** დაკავშირებული Claude Code გარემოდან აგზავნის სესიის ნიშანს, რომელსაც Tuist გადასცემს მათ როგორც `TUIST_OIDC_TOKEN`. დააყენეთ ჰედერი `Bearer ${TUIST_OIDC_TOKEN}`-ზე.

Tuist-ის Linux sandbox-ები არ ამატებენ სერვერს თქვენთვის: ისინი შეიცავენ Tuist CLI-ს, რომელიც შედის სისტემაში იგივე იდენტობით, და უნარს, რომელიც ეუბნება აგენტს, როდის შეამოწმოს შედეგები პროექტის ისტორიის მიხედვით. აგენტებს MCP ინსტრუმენტების მისაცემად, დაამატეთ სერვერი თქვენს Amp ან Claude Code პარამეტრებში, ან პროექტის `.mcp.json`-ში, ზემოთ მოცემული ჰედერით.

ეს ნიშნები იძლევა მხოლოდ წაკითხვის უფლებას დაკავშირებული ანგარიშის ყველა პროექტზე: ისინი შეიცავენ `mcp` ჯგუფის წაკითხვის სკოპებს და არაერთს, რომელიც ქმნის, ცვლის ან შლის მონაცემებს, როგორიცაა ტესტების ჩუმი ან გამოტოვება. სამუშაო სივრცის ან გარემოს გათიშვა წყვეტს წვდომას შემდეგ მოთხოვნაზე და წვდომა არასდროს ძლებს თავად ნიშანზე მეტ ხანს. Amp სამუშაო სივრცე, რომელიც დაკავშირებულია რამდენიმე Tuist ანგარიშთან, უარყოფილია, რადგან მისი ნიშანი არ ასახელებს ერთს. როდესაც კავშირი არ არის, არაავტორიზებული პასუხის `error_description` ამას ამბობს.

ეს მხოლოდ წაკითხვის წვდომა ვრცელდება მხოლოდ Model Context Protocol endpoint-ზე. ბრძანების ხაზის ინსტრუმენტი და build-system ინტეგრაციები იმავე sandbox-ში მაინც ცვლიან ნიშანს კავშირის CI წვდომისთვის.

## WebMCP

ბრაუზერებში, რომლებიც მხარს უჭერენ [WebMCP](https://webmachinelearning.github.io/webmcp)-ს, Tuist-ის გვერდები რეგისტრირებენ ინსტრუმენტებს `document.modelContext`-ით, ასე რომ ბრაუზერში ჩაშენებულ აგენტებს შეუძლიათ მათი გამოძახება დამატებითი კონფიგურაციის გარეშე. ზარები მუშაობენ Tuist სერვერზე.

- **Website and documentation pages** რეგისტრირებენ დოკუმენტაციის და წყაროს ინსტრუმენტებს (`search_tuist`, `search_tuist_code`, `list_tuist_files` და `read_tuist_file`). მათ არ სჭირდებათ თქვენგან სისტემაში შესვლა.
- **An account's dashboard pages**, როდესაც სისტემაში ხართ შესული, რეგისტრირებენ Tuist-ის მხოლოდ წაკითხვის ინსტრუმენტებს ამ ანგარიშისთვის. თითოეული გვერდი რეგისტრირებს მხოლოდ იმ ინსტრუმენტებს, რასაც ის აჩვენებს, პროექტის build system-ისთვის: Gradle პროექტის builds გვერდი იღებს Gradle build ინსტრუმენტებს, მისი test გვერდები test და coverage ინსტრუმენტებს, runners გვერდები runner ინსტრუმენტებს და sandboxes გვერდები sandbox ინსტრუმენტებს. ყოველ გვერდს ასევე აქვს დოკუმენტაციის ინსტრუმენტები, `list_projects` და `get_project`. ინსტრუმენტები მუშაობენ სისტემაში შესული მომხმარებლის სახელით, ამიტომ ისინი მხოლოდ იმ მონაცემებს აღწევენ, რომელთა წაკითხვაც შეგიძლიათ dashboard-ში და მხოლოდ იმ ანგარიშს, რომელსაც უყურებთ. როდესაც გადადიხართ სხვა გვერდზე ან ანგარიშზე, ინსტრუმენტები იცვლება იმ გვერდის ინსტრუმენტებით.

ინსტრუმენტები, რომლებიც ქმნიან, ცვლიან ან შლიან მონაცემებს, არ არის ხელმისაწვდომი WebMCP-ით, რადგან ბრაუზერის აგენტი იღებს ინსტრუმენტებს თქვენგან დამატების გარეშე და კითხულობს შინაარსს, რომელსაც builds და tests აწარმოებენ. დაუკავშირეთ MCP კლიენტი `/mcp` endpoint-ს ამ ინსტრუმენტების გამოსაყენებლად.

თუ ორგანიზაცია აიძულებს ერთჯერად შესვლას (single sign-on), შედით dashboard-ში მისი პროვაიდერით, რათა გამოიყენოთ მისი ინსტრუმენტები.

## Build-system ინტეგრაციები იყენებენ ორ რწმუნებას

Model Context Protocol ინსტრუმენტებისთვის გამოყენებული რწმუნება არ ავთენტიკირებს Gradle პლაგინს ან Bazel-ის remote სერვისებს. სანამ აგენტი შეცვლის ან დაადასტურებს Gradle ან Bazel ინტეგრაციას, მან უნდა გაუშვას:

```bash
tuist auth whoami --url https://tuist.dev
```

თუ ეს ბრძანება არ არის ავთენტიკირებული, აგენტმა უნდა შეწყვიტოს და სთხოვოს მომხმარებელს გაუშვას:

```bash
tuist auth login --url https://tuist.dev
```

ლოკალური ან self-hosted განლაგებისთვის, შეცვალეთ URL ორივე ბრძანებაში და `tuist.toml`-ში. შეინარჩუნეთ hostname-ის მართლწერა იდენტური ყველგან. მაგალითად, `localhost` და `127.0.0.1` იყენებენ ცალკე შენახულ რწმუნებებს.


## შესაძლებლობები

### ინსტრუმენტები

შემდეგი ინსტრუმენტები ხელმისაწვდომია Tuist Model Context Protocol სერვერის მეშვეობით:

ყოველი ინსტრუმენტი აქვეყნებს ადამიანისთვის წასაკითხ აღწერილობას ცალსახა input და output სქემებთან ერთად. წარმატებული ზარები აბრუნებენ სტრუქტურირებულ შინაარსს, რომელიც შეესაბამება გამოცხადებულ output სქემას, პლიუს იგივე შედეგი ტექსტად სერიალიზებული კლიენტებისთვის, რომლებიც ჯერ არ იყენებენ სტრუქტურირებულ შინაარსს.

ინსტრუმენტები, რომლებიც იღებენ ერთი ჩანაწერის იდენტიფიკატორს, როგორიცაა `build_run_id`, `test_run_id`, `test_case_id`, `bundle_id`, `run_id`, `generation_id` ან `cache_run_id`, ასევე იღებენ ამ ჩანაწერის Tuist dashboard URL-ს. ჩასვით URL პირდაპირ ბრაუზერიდან მისგან იდენტიფიკატორის ამოღების ნაცვლად.

`get_xcode_build`, `get_test_run`, `get_gradle_build` და `get_project` შეიძლება შეიცავდნენ `side_quests`-ს: Tuist შესაძლებლობები, რომლებსაც პროექტი არ იყენებს, მაგრამ ჩანაწერი აჩვენებს, რომ დაეხმარებოდა. თითოეულს აქვს `id`, `tip`, რომელიც აღნიშნავს მტკიცებულებას, რომელზეცაა დაფუძნებული, და `docs` ბმული. აგენტებს სთხოვენ ჯერ დაასრულონ მომხმარებლის მოთხოვნა, აღნიშნონ შესაბამისი side quests და იმოქმედონ ერთზე მხოლოდ მაშინ, როცა მომხმარებელი თანხმდება. ისინი ბრუნდებიან მხოლოდ პროექტის ანგარიშის წევრებისთვის, მიუხედავად იმისა, უკავშირდებიან თუ არა ისინი მომხმარებლის სესიით, MCP ნიშნით ან აგენტის იდენტობით:

ID-ები შეზღუდულია ბილდის ფარგლებში და არ უნდა შეესაბამებოდეს სხვა ბილდებს.

არასავალდებულო `start_ms` და `end_ms` ირჩევენ ნაბიჯებს, რომლებიც ემთხვევა დროის დიაპაზონს მილიწამებში ბილდის დაწყებიდან; ბოლო არ არის ჩათვლილი. ორივე ინსტრუმენტი იღებს ბილდის UUID-ს ან დაშბორდის URL-ს, როგორც `build_run_id`. გადასცეთ დაბრუნებული ნაბიჯის `id` უცვლელად, როგორც `step_id` მისი ლოგის მისაღებად. ლოგები ინახავენ მაქსიმუმ 64 KiB-ს ნაბიჯზე, `log_truncated` მიუთითებს გამოტოვებულ გამონატანზე.

ნაბიჯები გროვდება ნაგულისხმევად, როცა Xcode ბილდები მუშავდება. ჩაწერილი ნაბიჯის მონაცემები ინახება 90 დღის განმავლობაში. სიის პასუხი შეიცავს `availability`-ს: `available`, როცა ჩაწერილი ნაბიჯები არსებობს, მაშინაც კი, თუ ფილტრები არაფერს ემთხვევა; `processing`, როცა ბილდი კვლავ მუშავდება და ჯერ არ აქვს ნაბიჯები; ან `unavailable`, როცა ნაბიჯები არ ჩაწერილა ან ამოიწურა.

იგივე ოპერაციები ხელმისაწვდომია HTTP API-ზე `GET /api/projects/{account_handle}/{project_handle}/xcode/builds/{build_id}/steps` და `GET /api/projects/{account_handle}/{project_handle}/xcode/builds/{build_id}/steps/{step_id}` მისამართებზე, იგივე ფილტრებითა და პაგინაციით. ორივეს სჭირდება წვდომა ბილდის პროექტის წასაკითხად.

Gradle-ისა და Bazel-ის ნაბიჯების სიები ნაგულისხმევად აბრუნებენ 20 შედეგს (მაქსიმუმ 100), მხარდაჭერილია `search`, ზუსტი `project`, `target`, `category` და `status`, გადაფარვის `start_ms` / `end_ms` ფილტრები (ბოლო არ არის ჩათვლილი) და `duration_ms` ან `start_ms` დალაგება. გადასცეთ დაბრუნებული ID-ები უცვლელად; ისინი მიბმულია კონკრეტულ ბილდზე. სიები აჩვენებენ `time_origin`-ს და `coverage`-ს. Gradle-ის უფრო ძველი ანგარიშები იყენებენ `first_recorded_timestamp`-ს, რადგან ბილდის დაწყება არ აიტვირთა. Bazel-ის პროფილები აჩვენებენ ყველა ჩაწერილ ინტერვალს `trace_profile` დაფარვით და `profile_start`-ს, როგორც დროის საწყისს. უფრო ძველი ბილდები ეყრდნობიან შენახულ BEP შეჯამებებს. წყაროს ჩანაწერები იწურება 90 დღის შემდეგ. Bazel-ის დეტალები მოიცავს სანიტიზებულ ქმედებების ლოგებს, როცა ისინი გამოქვეყნებულია. Gradle-ის დეტალები ჩავარდნილი ამოცანის ან კონფიგურაციის ნაბიჯის შესახებ მოიცავს შეცდომის შეტყობინებას, რომელიც Tuist Gradle პლაგინმა ანგარიშში მიუთითა, როგორც `log`: გამონაკლისის შეტყობინება და მისი მიზეზების ჯაჭვი, როგორც Gradle-ის კონსოლი ბეჭდავს მათ, სტეკის ტრეისების ან ამოცანის გამონატანის გარეშე, პროექტის შიგნით არსებული გზები გადაყვანილია ფარდობითად, ხოლო სერთიფიკატები და სხვა ადგილობრივი გზები დაფარულია, მაქსიმუმ 16 KiB თითო ნაბიჯზე და 32 ჩავარდნილი ნაბიჯი თითო ბილდზე. სხვა Gradle ნაბიჯებს, პლაგინის უფრო ძველი ვერსიებით ანგარიშგებულ ბილდებს და სერთიფიკატების გარეშე ანგარიშებს აქვთ null `log`. კონფიგურაციის ნაბიჯები ანგარიშობენ `failure`-ს, როცა ისინი ჩავარდნენ, და `unknown`-ს სხვა შემთხვევაში. `compare_builds` მოთხოვნა იყენებს ამ დაფარვას სრული Bazel ტრეისების განსასხვავებლად შენახული შეჯამებებისგან და მიმართავს აგენტებს ნაბიჯის დეტალებისკენ ქმედებების შედეგებისა და ლოგებისთვის, სანამ ფართო გამოძახების გამონატანს შეამოწმებენ.

ერთი ნაბიჯის ინსტრუმენტები `get_gradle_build_step` და `get_bazel_build_step` იღებენ ნაბიჯს ID-ით და არ იღებენ დროის ფილტრებს; გამოიყენეთ შესაბამისი სიის ინსტრუმენტები ნაბიჯების ფილტრაციისთვის დროის დიაპაზონით.

Bazel-ის ნაბიჯების ID-ები, რომლებიც დაბრუნებულია შენახული შეჯამებებიდან, რჩება წასაკითხად, თუ სრული პროფილი მიიღება სიის ჩამოთვლასა და ნაბიჯის მიღებას შორის. ინდექსირებული პროფილი, რომლის ნაბიჯის მონაცემები ამოიწურა, ანგარიშობს ხელმიუწვდომლობას. Gradle-ის ნაბიჯების სიები მოიცავს ნულოვანი ხანგრძლივობის ქეშირებულ და გამოტოვებულ ოპერაციებს.

`list_bazel_invocations` ფილტრები არის ზუსტი დამთხვევები, და გამოძახებები, რომლებიც ერთსა და იმავე წამში მთავრდება, დალაგებულია გამოძახების ID-ით. ტოტზე უახლესი ჩავარდნილი გამოძახების საპოვნელად, გამოიძახეთ ის `status: "failure"`, `git_branch` და `page_size: 1`-ით. დააყენეთ `remote_execution: true` `list_bazel_build_steps`-ზე, რათა დაბრუნდეს მხოლოდ ქმედებები ინდექსირებული პროფილებიდან უსაფრთხოდ ასოცირებული სერვერის ფაზის დროებით. სიისა და დეტალური პასუხები აჩვენებენ არასავალდებულო nullable `remote_queue_ms`, `remote_input_fetch_ms`, `remote_execution_ms` და `remote_output_upload_ms`-ს. მნიშვნელობები აჯამებს ჩაწერილ ფაზებს, ქმედების შიგნით განმეორებების ჩათვლით; არარსებული ან null მნიშვნელობები ნიშნავს ხელმიუწვდომლობას, არა ნულს. ისინი არიან პროფილის დაკვირვებები, არა გადასახდელი გამოყენება ან ახალი შესრულების მტკიცებულება, რადგან ქეშირებულ სერვერის შედეგებს შეიძლება ჰქონდეთ შესრულების მეტამონაცემები. კლიენტის ატვირთვები გამორიცხულია. უფრო ძველმა ან გაურკვეველმა პროფილებმა შეიძლება არ დააბრუნონ შესაბამისი ქმედებები მაშინაც კი, თუ удаленный სამუშაო შესრულდა. ნაბიჯის REST საბოლოო წერტილი იღებს იგივე `remote_execution=true` ფილტრს. დაშბორდის Remote execution ჩანართი იყენებს იგივე მოთხოვნას და 90-დღიან შენახვას.

ტესტის ლოგები შეიცავს `target_label`-ს და ცდის `status`-ს ტესტის შედეგიდან, საიდანაც ისინი მოვიდნენ, ამიტომ `target_label: "//foo:bar_test"` აბრუნებს მხოლოდ იმ სამიზნის ტესტის ლოგებს. `errors: true` აბრუნებს ჩავარდნილი ცდების ტესტის ლოგებს და stderr პროგრესის ფრაგმენტებს, რომლებიც შეიცავს ხაზს, რომლითაც Bazel-ის რეპორტიორი იწყება: `ERROR:`, `FAIL:` ან `TIMEOUT:`. პროგრესის გამონატანი არ არის მიკუთვნებული სამიზნეებისთვის, და ლოგები, რომლებიც დაიწერა მიკუთვნების ჩაწერამდე, აქვთ ცარიელი ველები. ჩავარდნილი ქმედებები და მათი საკუთარი გამონატანი ხელმისაწვდომია თითო სამიზნისთვის `list_bazel_build_steps`-დან, და თითო ტესტის შემთხვევის ჩავარდნები ტესტების გაშვების ინსტრუმენტებიდან.

`get_build_entity` მეტრიკები მოიცავს `duration_samples`-ს, დაკვირვებების რაოდენობას ჩაწერილი დროით: ნამდვილი ნულოვანი ხანგრძლივობები ითვლება, გამოტოვებული დრო — არა. ეს რაოდენობა შეიძლება იყოს დაკვირვებების რაოდენობაზე ნაკლები; მიუწვდომელი ხანგრძლივობის სტატისტიკა რჩება null-ად.

Xcode მოდულების ხანგრძლივობა მოდის ბილდის ჟურნალებში გაზომილი სამიზნე კომპილაციებიდან. მოდულის ქეშის ამოხსნები და სამიზნეები კომპილაციის გარეშე არ წარმოქმნიან ხანგრძლივობის ნიმუშებს. კომპილაციის დაკვირვებები მიუთითებენ Xcode ბილდზე; ქეშის მოვლენები მიუთითებენ გენერაციის ან ქეშის ბრძანებაზე.

Bazel ქმედებები იდენტიფიცირდება სამიზნის ლეიბლით, მნემონიკით და კონფიგურირებული ძირითადი გამომავალით, რაც ინარჩუნებს ცალკეულ ქმედებებსა და კონფიგურაციებს განცალკევებულად, შეყვანაზე დამოკიდებული ქეშის დაიჯესტების გარეშე. ისტორია აღრიცხავს BEP-ით მოხსენებულ შესრულებებს, არა ქეშის ძიებებს ან ტრეისის პროფილის ფაზებს. სრული შესრულების დაფარვა მოითხოვს `--build_event_publish_all_actions`-ს; არტიფაქტების მიწოდება ხდება მაქსიმალური ძალისხმევით, ამიტომ გამოტოვებული დაკვირვებები არ არის იმის მტკიცებულება, რომ სამუშაო არ შესრულებულა. ძველი Kura პეილოადები სტაბილური იდენტობის ან შესრულების დაწყების გარეშე რჩება მიღებული, მაგრამ არაინდექსირებული. დასრულების დროის გაზომვების არარსებობა რჩება მიუწვდომელი და ნამდვილი ნულოვანი ხანგრძლივობები ითვლება.

Mix მოდულების ხანგრძლივობა ზომავს შემცველი ფაილის კომპილაციას, არა დამოუკიდებლად გაზომილ მოდულის სამუშაოს. Struo ქმედებები იყენებენ გამოცხადებულ სამიზნე/შესაძლებლობა/ინდექს სლოტებს, როდესაც კლიენტმა მოახსენა სამიზნე ასოციაციები; მხოლოდ დიაგნოსტიკური ლეიბლები არ არის სტაბილური იდენტობები. არსებული კლიენტები და გაშვების დონის ინსტრუმენტები რჩება მხარდაჭერილი უცვლელად.

Cargo ყუთები დაჯგუფებულია ზუსტად ჩაწერილი ყუთის ფესვით, სახელით და სახეობით. Checkout-ის გზის ცვლილებებმა შეიძლება გაყოს ისტორიები, ხოლო ბილდის პროფილები, ფუნქციები და სამიზნე ტრიპლეტები არ განირჩევა. ისტორია ზომავს rustc გამოძახებებს, არა ფაილზე დამოკიდებულ სამუშაოს ან ქეშის მოხვედრებს; არარსებული სამუშაოები არ ამყარებს წაშლებს ან სამუშაო სივრცის სრულ ინვენტარს.

ანალიტიკის წაკითხვებს აქვს შემოსაზღვრული მეხსიერება და შესრულების დრო. თუ მოთხოვნა აღემატება ამ ლიმიტებს, ინსტრუმენტი აბრუნებს შეცდომას ცარიელი შედეგის გამოგონების ნაცვლად.

ახალი დაკვირვებები ინდექსირდება განლაგების შემდეგ; ეს ფუნქცია არ ავსებს არსებულ გაშვების ტელემეტრიას. იდენტობის მეტამონაცემები ინარჩუნებს სიცოცხლეს ინდივიდუალურ დაკვირვებებზე მეტ ხანს <.localized_link href="/guides/server/data-retention">მონაცემთა შენახვის პოლიტიკის</.localized_link> ფარგლებში.

### მოვლენები

კლიენტები, რომლებიც იყენებენ უმდგომარეობიან `2026-07-28` Model Context Protocol ციკლს, შეუძლიათ გამოიძახონ `events/list` მოვლენებისა და მათი პეილოადის სქემების აღმოსაჩენად:

| მოვლენა | როდის იგზავნება | გამოწერის ფილტრი |
|-------|-----------------|---------------------|
| `test_case.marked_flaky` | სატესტო შემთხვევა იცვლება არასტაბილურიდან სტაბილურზე. | `account_handle`, `project_handle` |
| `build.failed` | ლოკალური ან უწყვეტი ინტეგრაციის Xcode, Gradle ან Bazel ბილდი სრულდება შეცდომით. | `account_handle`, `project_handle` |
| `test_run.failed` | ლოკალური ან უწყვეტი ინტეგრაციის ტესტების გაშვება სრულდება შეცდომით, შერწყმული დაყოფილი გაშვების ან მიტოვებული გაშვების ჩათვლით. | `account_handle`, `project_handle` |
| `ci_job.failed` | Tuist-ის გამშვების სამუშაო სრულდება შეცდომით. | `account_handle` |

გამოსაწერად კლიენტი იძახებს `events/subscribe` მოვლენის სახელით, ზემოთ ჩამოთვლილი ხელმძღვანელებით `arguments`-ში და `webhook` მიწოდებით, რომელიც შეიცავს `https://` callback URL-ს და `whsec_` ხელმოწერის საიდუმლოს. პროექტის მოვლენები მოითხოვენ ანგარიშის წევრობას და შესაბამის ტესტ ან ბილდ მონაცემებზე წვდომას; გამშვების სამუშაოების მოვლენები მოითხოვენ ანგარიშის წევრობას და გამშვებზე წვდომას. დადასტურებულმა [`auth.md`](https://workos.com/auth-md) წვდომის ტოკენებმა, ანგარიშის ტოკენებმა და ბრაუზერის ავტორიზაციის ნებართვებმა შეიძლება შექმნან გამოწერები; მიწოდება ჩერდება, როდესაც შესაბამისი კრედენციალი აღარ არის აქტიური. თითოეულ მომხმარებელს შეუძლია ჰქონდეს 25-მდე აქტიური გამოწერა. Tuist აგზავნის ვერიფიკაციის გამოწვევას callback-ზე გამოწერის შენახვამდე. Callback-მა უნდა დააბრუნოს ობიექტი იგივე `challenge` მნიშვნელობით. გამოწერა ძალაშია შვიდი დღის განმავლობაში ნაგულისხმევად, შეიძლება განახლდეს ხელახლა გამოწერით და წყდება, როდესაც მომხმარებლის წვდომა ან კრედენციალი იხსნება. არასავალდებულო `ttlMs` შეზღუდულია ერთ საათსა და 30 დღეს შორის. Tuist თავიდან ცდილობს დროში ამოწურულ callback-ს და აუქმებს მას სამი თანმიმდევრული ამოწურვის შემდეგ, რომლებიც მოიცავს ხუთ წუთს; გამოიწერეთ ხელახლა callback-ის აღდგენის შემდეგ.

როდესაც მოვლენა ხდება, Tuist აგზავნის მის რესურსის იდენტიფიკატორს და დაფის URL-ს callback-ზე. ბილდისა და ტესტების გაშვების შეცდომები ასევე შეიცავს `is_ci`-ს და `git_branch`-ს, რათა კლიენტებმა შეძლონ ლოკალური შეცდომების იგნორირება ან ფილტრაცია ტოტის მიხედვით. ბილდის მოვლენები შეიცავს `build_system`-ს; გამშვების სამუშაოების მოვლენები შეიცავს როგორც `workflow_job_id`-ს, ისე `workflow_run_id`-ს. მოთხოვნა შეიცავს გამოწერის იდენტიფიკატორს და [Standard Webhooks](https://www.standardwebhooks.com/) ხელმოწერის ჰედერებს, რათა კლიენტმა შეძლოს მისი წარმომავლობის ვერიფიკაცია. Tuist თავიდან ცდილობს წარუმატებელ მიწოდებებს, ამიტომ კლიენტებმა უნდა გამოიყენონ სტაბილური `eventId` დუბლიკატების გასაფილტრად. პეილოადი არ შეიცავს ტესტების სახელებს, ლოგებსა და შეცდომის შეტყობინებებს; კლიენტს შეუძლია მიიღოს ეს დეტალები ზემოთ ჩამოთვლილი ინსტრუმენტების მეშვეობით და გადაწყვიტოს, შეატყობინოს თუ არა გუნდს ან დაიწყოს დებაგინგი. კლიენტებმა შეუძლიათ შეაჩერონ მიწოდება `events/unsubscribe`-ით.

| `compare_cache_runs` | გასწავლით ორი ქეშის გაშვების შედარებას ქეშის ეფექტურობის ცვლილებებისა და სამიზნე დონის რეგრესიების იდენტიფიცირებისთვის. |
| `integrate_gradle_project` | გასწავლით Tuist-ის ინტეგრირებას არსებულ Gradle პროექტში. მოიცავს ცალკეულ ინსტრუმენტსა და Gradle ავტორიზაციას, ანგარიშის აღმოჩენას, პროექტის შექმნას, დაშორებული ქეშის პოლიტიკას, ბილდის ინსაიტებსა და უკუვერიფიკაციას. |
| `integrate_bazel_project` | გასწავლით Bazel პროექტის შექმნას ან შერჩევას, ბრძანების ხაზის ავტორიზაციას, დაშორებული ქეშისა და ბილდის ინსაიტების კონფიგურაციას და ინტეგრაციის ვერიფიკაციას Tuist ბილდის მონაცემებით. |
| `integrate_xcode_project` | გასწავლით Tuist-ის ინტეგრირებას არსებულ Xcode პროექტში. მხარდაჭერილია Xcode ქეში, ბილდის ინსაიტები, ტესტის ინსაიტები და ტესტის დაყოფა. |
| `ask_tuist` | პასუხობს Tuist-ის კითხვას საჯარო მასალის გამოყენებით კონტექსტისთვის და ფოკუსირებული იმპლემენტაციისა და ტესტის მტკიცებულებების გამოყენებით, როგორც სიმართლის წყარო მიმდინარე ქცევისთვის. მოითხოვს `question`-ს და ასახელებს რევიზიაზე მიბმულ მტკიცებულებებს. |

პროექტის მონაცემების მოთხოვნები იღებენ `account_handle`-ს და `project_handle`-ს კვლევის სკოპირებისთვის კონკრეტულ პროექტზე. შედარების მოთხოვნები ასევე იღებენ `base` და `head` არგუმენტებს ორი შესადარებელი ელემენტის მითითებისთვის (ID-ით, დაფის URL-ით ან ტოტის სახელით). `ask_tuist` იღებს `question`-ს პროექტის პარამეტრების ნაცვლად. `integrate_gradle_project` ასევე იღებს `features`-ს, Gradle ინტეგრაციების კომებით გამოყოფილ სიას გამოყენებისთვის: `remote_cache`, `build_insights`, `test_insights`, `flaky_tests` და `test_sharding`. `integrate_bazel_project` იღებს არასავალდებულო `server_url`-ს თვითმასპინძელი ან ლოკალური ინსტალაციებისთვის. `integrate_xcode_project` იღებს `features`-ს `xcode_cache`, `build_insights`, `test_insights` და `test_sharding`-ით.

#### Gradle ინტეგრაციის მოთხოვნის ფუნქციები

`integrate_gradle_project` მოთხოვნა და `get_gradle_integration_guide` ინსტრუმენტი აღწერენ სრულ დაყენების სამუშაო ნაკადს. ინსტრუმენტი ასევე არის მითითებული სერვერის ინიციალიზაციის ინსტრუქციებში, რაც მას აღმოჩენადს ხდის აგენტებისთვის, რომლებიც არ ჩამოთვლიან მოთხოვნებს.

| ფუნქცია | რას აკონფიგურირებს აგენტი |
|---------|---------------------------|
| `remote_cache` | ააქტიურებს Gradle-ის ბილდის ქეშს, აკონფიგურირებს Tuist-ის დაშორებული ქეშის ატვირთვის პოლიტიკას და ურჩევს ატვირთვას მხოლოდ უწყვეტი ინტეგრაციის გამშვებებიდან ლოკალური მხოლოდ-წაკითხვის გამოყენებით. |
| `build_insights` | აყენებს Tuist Gradle პლაგინს და აკონფიგურირებს ბილდის ანალიტიკის ატვირთვის ქცევას საჭიროების შემთხვევაში. |
| `test_insights` | აყენებს Tuist Gradle პლაგინს, რათა Gradle `Test` ამოცანის შედეგები ავტომატურად აიტვირთოს. |
| `flaky_tests` | გასწავლით არასტაბილური ტესტების აღმოჩენის დაყენებას, Gradle Test Retry პლაგინის არასავალდებულო გამოყენებას და ტესტის კარანტინის კონფიგურაციას. |
| `test_sharding` | ამატებს უწყვეტი ინტეგრაციის სამუშაო ნაკადს `tuistPrepareTestShards`-ისთვის, ნაწილების მატრიცის გენერაციას და `TUIST_SHARD_INDEX`-ზე დაფუძნებულ ტესტის შესრულებას. |

როდესაც `features` გამოტოვებულია, მოთხოვნა სთხოვს აგენტს გაარკვიოს, თუ რომელი ინტეგრაციები სურს მომხმარებელს ან გამოიტანოს უმცირესი სასარგებლო ნაკრები მოთხოვნიდან Gradle პროექტის რედაქტირებამდე.

#### Xcode ინტეგრაციის მოთხოვნის ფუნქციები

`integrate_xcode_project` მოთხოვნა აღწერს ყველა Xcode ინტეგრაციას, რომელსაც Tuist მხარს უჭერს:

| ფუნქცია | რას აკონფიგურირებს აგენტი |
|---------|---------------------------|
| `xcode_cache` | აკონფიგურირებს `tuist setup cache`, გენერირებული პროექტის ქეშის პარამეტრებს, Xcode ქეშის ბილდის ხელით მითითებულ პარამეტრებს და ატვირთვის პოლიტიკას, რომელიც შემოიფარგლება მხოლოდ უწყვეტი ინტეგრაციის გამშვებებით. |
| `build_insights` | აკონფიგურირებს `tuist inspect build`-ს, `tuist xcodebuild`-ს, `-resultBundlePath`-ს და არჩევით მანქანურ მეტრიკებს `tuist setup insights`-ის საშუალებით. |
| `test_insights` | აკონფიგურირებს `tuist inspect test`-ს, სქემის ტესტის post-actions-ებს და შედეგების ბანდლის გენერაციას უწყვეტი ინტეგრაციის ტესტების გაშვებებისთვის. |
| `test_sharding` | ამატებს Xcode-ის ან გენერირებული პროექტის ნაწილების დაგეგმვისა და შესრულების სამუშაო ნაკადს `TUIST_SHARD_INDEX`-ის გამოყენებით. |

როდესაც `features` გამოტოვებულია, მოთხოვნა სთხოვს აგენტს გაარკვიოს, თუ რომელი ინტეგრაციები სურს მომხმარებელს ან გამოიტანოს უმცირესი სასარგებლო ნაკრები მოთხოვნიდან Xcode პროექტის რედაქტირებამდე.
