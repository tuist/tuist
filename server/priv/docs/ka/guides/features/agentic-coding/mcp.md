# Model Context Protocol

[Model Context Protocol (MCP)](https://modelcontextprotocol.io/docs/getting-started/intro) არის ღია სტანდარტი, რომელიც საშუალებას აძლევს ხელოვნური ინტელექტის აგენტებს ურთიერთქმედება გარე სერვისებთან და მონაცემთა წყაროებთან. ის უზრუნველყოფს ისეთი აპლიკაციების, როგორიცაა [Claude](https://claude.ai/), [Claude Code](https://docs.anthropic.com/en/docs/claude-code), [Codex](https://developers.openai.com/codex/), და რედაქტორების, მაგალითად [Zed](https://zed.dev), [Cursor](https://www.cursor.com) ან [Visual Studio Code](https://code.visualstudio.com), თავსებადობას Tuist-თან.

Tuist მასპინძლობს Model Context Protocol-ის სერვერულ ბოლოწერტილს მისამართზე `https://tuist.dev/mcp`. თქვენი კლიენტის მასთან დაკავშირებით, აგენტებს შეუძლიათ წვდომა მიიღონ თქვენს Tuist პროექტის მონაცემებზე, მათ შორის ტესტების ანალიტიკაზე, არასტაბილური ტესტების ანალიზზე და სხვა. ინსტრუმენტების უმეტესობა მხოლოდ წაკითხვის რეჟიმშია და შემოიფარგლება ავთენტიფიცირებული Tuist პროექტის მონაცემებით. ანგარიშის კონფიგურაციის ინსტრუმენტებს შეუძლიათ ანგარიშების ჩამოთვლა, ორგანიზაციების შექმნა, პროექტების შექმნა და არსებული მომხმარებლების დამატება ორგანიზაციებში, თუ ავთენტიფიცირებულ მომხმარებელს აქვს საჭირო ნებართვები. ყოველი ინსტრუმენტი აცხადებს ანოტაციებს, რომლებიც მიუთითებს, არის თუ არა ის მხოლოდ წაკითხვის რეჟიმში, შეუძლია თუ არა მას გამოიწვიოს ძნელად შექცევადი ცვლილება და შეუძლია თუ არა შეცვალოს საჯარო ინტერნეტის მდგომარეობა. `update_runner_profile`, `update_notification_rule` და `connect_claude_subscription` აცხადებენ `destructiveHint: true`, რადგან მათ შეუძლიათ ჩაანაცვლონ არსებული კონფიგურაცია ან სერთიფიკატები. ანგარიშის კონფიგურაციის ინსტრუმენტები მოითხოვს მომხმარებლის ავთენტიფიკაციას. ისინი არ არის ხელმისაწვდომი პროექტის ტოკენებისთვის ან ჩვეულებრივი ანგარიშის ტოკენებისთვის. როდესაც მომხმარებელი ავტორიზაციას ანიჭებს კლიენტს ბრაუზერში ან ითხოვს `auth.md` რეგისტრაციას, Tuist ამ სერთიფიკატს აკავშირებს მომხმარებელთან მხოლოდ Model Context Protocol-ის ბოლოწერტილზე, რათა კონფიგურაციის ინსტრუმენტებმა შეძლონ მოთხოვნილი სამუშაო პროცესის დასრულება.

Tuist ახორციელებს [2026-07-28 პროტოკოლს](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http). მოთხოვნები არის უმდგომარეო: კლიენტები აგზავნიან თავიანთ პროტოკოლის მეტამონაცემებს ყოველ მოთხოვნასთან ერთად და შეუძლიათ ინსტრუმენტების პირდაპირ გამოძახება ინიციალიზაციის გარეშე. `server/discover` აბრუნებს სერვერის იდენტობას, შესაძლებლობებს, მხარდაჭერილ ვერსიებს და ინსტრუქციებს. არ არსებობს სესიის იდენტიფიკატორები ან დამოუკიდებელი მოვლენათა ნაკადები. კლიენტები, რომლებიც იყენებენ 2025-06-18 ან 2025-03-26 ინიციალიზაციის ნაკადს, კვლავ მხარდაჭერილია; ისინიც მუშაობენ სერვერის სესიების გარეშე.

## Model Context Protocol უნარების წინააღმდეგ

Model Context Protocol-ის ინსტრუმენტებს და <.localized_link href="/guides/features/agentic-coding/skills">უნარებს</.localized_link> შეიძლება ჰქონდეთ გადახურვა ფუნქციონალში. არსებული გადახურვის გათვალისწინებით, აირჩიეთ ერთი მიდგომა თითოეული სამუშაო პროცესისთვის და გამოიყენეთ ის თანმიმდევრულად, ნაცვლად ორივეს ერთ ნაკადში შერევისა.

კლიენტებისთვის, რომლებიც მხარს უჭერენ პლაგინების ინსტალაციას, გამოიყენეთ <.localized_link href="/guides/features/agentic-coding/plugins">Tuist პლაგინები</.localized_link> ორივეს ერთად ინსტალაციისთვის.

## კონფიგურაცია

დაამატეთ `https://tuist.dev/mcp` როგორც დაშორებული Model Context Protocol სერვერი თქვენს კლიენტში. სერვერის ინიციალიზაციის ინსტრუქციები და საჯარო სერვერის ბარათი აღწერს OAuth 2.0-ს დინამიური კლიენტის რეგისტრაციით და სტანდარტული ბრაუზერის ავტორიზაციის ნაკადით პირდაპირ, აგენტებისგან გარე ავთენტიფიკაციის დოკუმენტების მოთხოვნის ან მათზე გადასვლის გარეშე. ეს სერვერის მასშტაბის ინსტრუქციები ინარჩუნებს სამუშაო პროცესის მითითებებს ზოგადს: ინსტრუმენტის ავთენტიფიკაცია არ ახდენს ადგილობრივი ბრძანების ხაზის ინსტრუმენტების ან აგების სისტემის ინტეგრაციების ავთენტიფიკაციას და აგენტებმა უნდა დაადასტურონ მოთხოვნილი ცვლილებები შესაბამისი Tuist ინსტრუმენტების მეშვეობით. აგების სისტემის სპეციფიკური კონფიგურაცია და ავთენტიფიკაციის შემოწმებები დოკუმენტირებულია ინტეგრაციის სახელმძღვანელოებში და მოთხოვნებში. Tuist კვლავ აცხადებს როგორც [Open Authorization](https://oauth.net/2/)-ის აღმოჩენის მეტამონაცემებს, ასევე მიმდინარე [auth.md პროტოკოლს](https://workos.com/auth-md) მისამართზე `https://tuist.dev/auth.md` ცალ-ცალკე.

თუ თქვენი რომელიმე ორგანიზაცია აიძულებს ერთიანი შესვლის (SSO) გამოყენებას, ბრაუზერში კლიენტის ავტორიზაცია მოითხოვს სესიას, რომელიც შესულია ამ ორგანიზაციის მეშვეობით, და Tuist საჭიროების შემთხვევაში ჯერ პროვაიდერთან გაგზავნით. იხილეთ <.localized_link href="/guides/integrations/authentication/sso#choose-an-enrollment-policy">ერთიანი შესვლა</.localized_link>.

ბოლოწერტილი იღებს უმდგომარეო `2026-07-28` Model Context Protocol მოთხოვნის სიცოცხლის ციკლს, მათ შორის `server/discover`-ს, უფრო ძველ სესიაზე დაფუძნებულ ციკლთან ერთად. არსებულმა კლიენტებმა შეიძლება განაგრძონ თავიანთი მიმდინარე კავშირის მეთოდის გამოყენება.

კლიენტებს, რომლებიც მხარს უჭერენ Model Context Protocol-ის მოვლენებს, შეუძლიათ გამოიწერონ პროექტის მოვლენები. იხილეთ [მოვლენები](#events) ხელმისაწვდომი მოვლენებისა და მიწოდების მოთხოვნებისთვის.

კლიენტებს, რომლებიც უკვე მხარს უჭერენ დაშორებულ ბრაუზერის ავთენტიფიკაციას, შეუძლიათ განაგრძონ ავთენტიფიკაცია ბრაუზერში. კლიენტებსა და აგენტებს, რომლებიც მხარს უჭერენ `auth.md`-ს, შეუძლიათ ანონიმურად რეგისტრაცია, სანდო პროვაიდერის იდენტობის დამტკიცების წარდგენა ან სერვისით ავთენტიფიცირებული ელფოსტის მოთხოვნის დაწყება. რეგისტრაცია აბრუნებს Tuist-ით ხელმოწერილ იდენტობის დამტკიცებას, რომელსაც აგენტი ცვლის სტანდარტულ ტოკენის ბოლოწერტილზე ერთსაათიანი წვდომის ტოკენისთვის. Tuist აქვეყნებს თავის საჯარო ხელმოწერის გასაღებს და მხარს უჭერს სტანდარტულ ტოკენის გაუქმებასა და პროვაიდერის უსაფრთხოების მოვლენების მიწოდებას.

არაავთენტიფიცირებულმა აგენტმა უნდა წაიკითხოს `WWW-Authenticate` ჰედერი, რომელიც დაბრუნდა Model Context Protocol-ის ბოლოწერტილის მიერ, მოიპოვოს დაცული რესურსის მეტამონაცემები, მოიპოვოს ავტორიზაციის სერვერის მეტამონაცემები და მიჰყვეს მის `agent_auth.skill` URL-ს. Tuist ასევე აბრუნებს იმავე ადგილობრივ `auth_md` URL-ს არაავტორიზებული პასუხის სხეულში, რათა ენის მოდელზე დაფუძნებულმა კლიენტებმა შეძლონ ნაკადის აღმოჩენა ნატიური კლიენტის ინტეგრაციაზე დაყრდნობის გარეშე. განლაგების ადგილობრივი დოკუმენტია ჭეშმარიტების წყარო ბოლოწერტილების სახელების, მოთხოვნის სხეულების, მოთხოვნის გამოკითხვისა და დამტკიცების გაცვლისთვის.

სანამ აგენტი ელფოსტის მოთხოვნას დაიწყებს, მან უნდა სთხოვოს მომხმარებელს დაადასტუროს ელფოსტის მისამართი მათი Tuist ანგარიშისთვის. მან არ უნდა გამოიტანოს ეს მისამართი პროვაიდერის პროფილიდან, Git კონფიგურაციიდან, გარემოს ცვლადიდან ან სესიის მეტამონაცემებიდან.

ბოლოწერტილი იყენებს `mcp` სკოპის ჯგუფს. ანონიმურმა წინასწარ მოთხოვნის სერთიფიკატმა შეიძლება აღმოაჩინოს შესაძლებლობები და წაიკითხოს საჯარო ინტეგრაციის მითითებები, მაგრამ ის არ განიხილება როგორც შესული მომხმარებელი. ბრაუზერის ავტორიზაციის ან მოთხოვნის შემდეგ, სერთიფიკატი არის მომხმარებელზე ორიენტირებული და თითოეული ინსტრუმენტი ატარებს იმავე ავტორიზაციის შემოწმებებს, რაც დაფის ინტერფეისი. დეტალებისთვის იხილეთ <.localized_link href="/guides/server/authentication#scope-groups">სკოპის ჯგუფების დოკუმენტაცია</.localized_link>.

ინსტრუმენტები წყდება პროექტებზე, რომლებსაც ავთენტიფიცირებულ მომხმარებელს უკვე აქვს წვდომა წაკითხვისთვის. Xcode და Gradle აგების ინსტრუმენტები იღებენ აგების UUID-ს ან დაფის URL-ს. UUID-მ უნდა მიუთითოს ზუსტად ერთ პროექტზე; თუ ის ჩანს რამდენიმე პროექტში, ინსტრუმენტი აბრუნებს „ნაპოვნი არაა“-ს, ნაცვლად სხვა პროექტის ანგარიშის არჩევისა. პროექტზე ორიენტირებული დაფისა და API-ს წაკითხვები კვლავ ხელმისაწვდომია. მოხსენებული აქტორის იდენტიფიკატორები არის დაუდასტურებელი ეტიკეტები, არა სერთიფიკატები ან დამატებითი წვდომის უფლებები.

აგების სიისა და დეტალური ინფორმაციის ინსტრუმენტები აჩვენებენ არასავალდებულო `tuist_version` მეტამონაცემებს: Xcode-ისა და Cargo-სთვის — Tuist CLI, Gradle-ისთვის — Tuist Gradle პლაგინი, ხოლო Mix-ისთვის — `tuist_ex` ბიბლიოთეკა. Xcode ასევე აჩვენებს `tuist_generation_version`-ს მის მიერ დაკავშირებული პროექტის გენერაციის მოვლენიდან, რომელიც შეიძლება განსხვავდებოდეს ატვირთვის CLI-ისგან. გამოტოვებული დაკვირვებები არის null, არა სერვერიდან ან სხვა ანგარიშიდან გამოყვანილი. Bazel იყენებს თავის არსებულ `bazel_version`-ს; Once-ის გაშვების დეტალები აჩვენებს `once_version`-ს. ეს ველები აღწერენ მოხსენებულ ვერსიებს, არა დადასტურებულ იდენტობას ან სადენის კონტრაქტის ვერსიებს. REST აგების ბოლოწერტილები აჩვენებენ იმავე მეტამონაცემებს. არსებული ინტეგრაციისა და არამდგრადი ტესტების უნარები არ არის დამოკიდებული ვერსიის ველებზე და არ საჭიროებს სამუშაო პროცესის ცვლილებებს.

Tuist-ის ოპერატორები, რომლებიც იკვლევენ მომხმარებლის ანგარიშს, ამას აკეთებენ Tuist-ის შიდა ოპერაციული ინსტრუმენტების მეშვეობით, რომელიც იწერს ყოველ ზარს; ამ ბოლოწერტილთან პირდაპირი კავშირი არ იძლევა წვდომას მომხმარებლის საკუთარი წევრობის ფარგლებს გარეთ.

### Pulse

Pulse აჩვენებს ორ მხოლოდ წაკითხვად ინსტრუმენტს, რომლებიც მიმართულია `account_handle`-ით:

| ინსტრუმენტი | REST ეკვივალენტი `/api/accounts/:account_handle/pulse` ქვეშ |
| --- | --- |
| `query_pulse` | `GET /:signal` |
| `get_pulse_analytics` | `GET /:signal/analytics` |

Pulse შეზღუდულია სერვერზე კონფიგურირებული ორგანიზაციის მიმდინარე წევრებისთვის, მაშინაც კი, თუ ანგარიში ან პროექტი საჯაროა. ის მოითხოვს მომხმარებლის ავთენტიფიკაციას ან მომხმარებელთან დაკავშირებულ `mcp` სერთიფიკატს და ანგარიშის წაკითხვის ავტორიზაციას. პროექტის ტოკენები, ჩვეულებრივი ანგარიშის ტოკენები, ანონიმური რეგისტრაციები და ოპერატორის წვდომა ორგანიზაციის წევრობის გარეშე არ იძლევა Pulse-ზე წვდომას. სერთიფიკატებს არ შეუძლიათ აირჩიონ სხვა ბექენდი ან ტელემეტრიის მომხმარებელი. ბრაუზერის აგენტები იღებენ ამ ინსტრუმენტებს მხოლოდ Pulse-ის გვერდებზე, ამ გვერდის ანგარიშის სკოპის ფარგლებში.

REST მოითხოვს მომხმარებლის სერთიფიკატს. OAuth და `auth.md` მომხმარებლის ასოციაციები ხელმისაწვდომია მხოლოდ `/mcp` ბოლოწერტილზე; ანგარიშის სერთიფიკატი მიმდინარე მომხმარებლის გარეშე უარყოფილია, მიუხედავად დაკავშირებული ანგარიშის წევრობისა ან ხილვადობისა.

`query_pulse` იღებს `signal` (`metrics`, `logs` ან `traces`), არასავალდებულო `query` და `range` (`15m`, `1h`, `6h` ან `24h`, ნაგულისხმევი `1h`). მეტრიკები იღებენ PromQL გამოსახულებებს. ლოგები და ტრეისები იღებენ ლიტერალურ, დამოუკიდებელ რეგისტრის ტექსტს, რომელიც ემთხვევა ლოგის სხეულებს და სპანის სახელებს; `*`, ნაგულისხმევი, ირჩევს ყველაფერს. ტრეისის სტრიქონები არის ინდივიდუალური სპანები. ცხრილები იღებენ `search`-ს, `page`-ს (ნაგულისხმევი `1`), `page_size`-ს (`1`–`100`, ნაგულისხმევი `20`), `sort_by`-ს და `sort_order`-ს (`asc` ან `desc`). დალაგების სვეტები დამოკიდებულია სიგნალზე და ჩამოთვლილია ინსტრუმენტის სქემაში. ფილტრები მოიცავს `service`-ს და ლოგის `level`-ს. ფილტრის ოპერატორები იყენებენ შესაბამის `_op` არგუმენტს (`eq`, `contains` ან `not_contains`), ნაგულისხმევად ზუსტი ტოლობით.

დალაგების სვეტებია `name`/`value` მეტრიკებისთვის; `timestamp`/`service`/`level`/`message`/`trace_id` ლოგებისთვის; და `timestamp`/`service`/`name`/`duration_ms`/`trace_id` ტრეისებისთვის. დაფა განზრახ აჩვენებს ქვესიმრავლეს; API და ინსტრუმენტები იღებენ სრულ სიას თითოეული სიგნალისთვის.

ცხრილის პასუხები შეიცავს `rows`-ს, `series`-ს, `warnings`-ს და `meta`-ს. პაგინაციის მეტამონაცემები მოიცავს `page`-ს, `page_size`-ს, `total_count`-ს, `total_pages`-ს, `has_next_page`-ს, `has_previous_page`-ს და `end_at`-ს. გადაეცით დაბრუნებული ISO8601 `end_at` შემდგომ გვერდებთან ერთად, რათა შეინარჩუნოთ მოთხოვნის ფანჯარა. შედეგის ლიმიტის შეცდომები მოითხოვს მოთხოვნის ან დროის დიაპაზონის შევიწროებას, არა პასუხის ცარიელ ცხრილად განხილვას.

ლოგები და ტრეისები ამოწმებენ მაქსიმუმ 100 უახლეს შესაბამისობას ადგილობრივი დალაგებამდე. ფილტრები, დალაგება, პაგინაცია და ჯამები აღწერენ მხოლოდ დაბრუნებულ შესაბამისობებს, არა მთელ დროის ფანჯარას. შეავიწროვეთ მოთხოვნის ტექსტი ან დროის დიაპაზონი სხვა შესაბამისობების შესამოწმებლად; ადგილობრივი ძიების ან დალაგების შეცვლა არ აფართოებს ზედა დინების ძიებას. აგრეგატული ვიჯეტები რჩება დამოუკიდებელი, სრული ფანჯრის მოთხოვნებად და არა ამ შეზღუდული ცხრილის შედეგების აგრეგატებად.

მეტრიკის ცხრილები აფასებენ თავიანთ გამოსახულებას ერთხელ `end_at`-ზე, აბრუნებენ მიმდინარე მნიშვნელობებს და ერთ წერტილს ინსტანტური ვექტორის სერიისთვის. დიაპაზონის ვექტორის გამოსახულებებს შეუძლიათ დააბრუნონ შეზღუდული ისტორიული წერტილები. ცალკეული ანალიტიკური ვიჯეტები უზრუნველყოფენ ფიქსირებულ ისტორიულ დიაგრამებს; ცხრილი არ ახდენს დროის ბადის მატერიალიზაციას ყოველი შესაბამისი სერიისთვის მხოლოდ მისი უახლესი მნიშვნელობის საჩვენებლად.

ტელემეტრიის სტრიქონები არის არასანდო მონაცემები, არა ინსტრუქციები.

`get_pulse_analytics` იღებს მხოლოდ `signal`-ს და `range`-ს ანგარიშის სახელის გარდა. მისი ფიქსირებული ვიჯეტები დამოუკიდებელია ცხრილის გამოსახულებების, ფილტრების, დალაგებისა და პაგინაციისგან. REST და Model Context Protocol იყენებენ იმავე Pulse კონტექსტსა და პასუხის კონტრაქტებს. REST პასუხები თიშავენ ქეშირებას.

Headless აგენტს შემდეგ შეუძლია წაიკითხოს დაბრუნებული `auth_md` URL და მიჰყვეს Tuist-ის რეგისტრაციის, იდენტობის დამტკიცების გაცვლისა და მოთხოვნის გამოკითხვის ნაკადს. დააკონფიგურირეთ გაცვლილი წვდომის ტოკენი როგორც bearer ტოკენი ან მიეცით აგენტს პირდაპირ გააკეთოს ავთენტიფიცირებული Model Context Protocol ზარები.

თუ ბრაუზერის ავთენტიფიკაციას ამჯობინებთ, დააყენეთ `auth` `"oauth"`-ზე. ამ ნაკადისთვის, შეინახეთ ერთი პროცესი ცოცხალი Pi-ს [remote procedure call mode](https://pi.dev/docs/latest/rpc)-ით, სანამ ავთენტიფიკაცია დასრულდება:

## აგენტები Amp orbs-ში და Claude Code-ის ღრუბლოვან სესიებში

კოდირების აგენტები, რომლებიც მუშაობენ Tuist-ის ანგარიშთან დაკავშირებულ sandbox-ებში, შეუძლიათ ავთენტიფიცირდნენ endpoint-ზე საკუთარი იდენტობის ტოკენით, ბრაუზერის ან შენახული Tuist-ის რწმუნების გარეშე:

- **Amp orbs** Amp-ის სამუშაო სივრცის ან პროექტისთვის, რომელიც ანგარიშმა დააკავშირა **Settings → Integrations → Amp**-ში, აგზავნის orb-ის ID ტოკენს. Amp-ში დააყენეთ სერვერის `Authorization` ჰედერი `Bearer ${amp:id-token}`-ზე. Amp აყალიბებს ტოკენს სერვერის URL-ის წარმოშობისთვის, ამიტომ URL უნდა იყოს ამ Tuist ინსტანციის საკუთარი მისამართი და აახლებს მას ვადის გასვლამდე. სხვა წარმოშობისთვის გამოშვებული ტოკენები უარყოფილია.
- **Claude Code cloud sessions** დაკავშირებული Claude Code გარემოდან აგზავნის სესიის ტოკენს, რომელსაც Tuist გადასცემს მათ როგორც `TUIST_OIDC_TOKEN`. დააყენეთ ჰედერი `Bearer ${TUIST_OIDC_TOKEN}`-ზე.

Tuist-ის Linux sandbox-ები მოდის ამ კონფიგურაციით: `tuist` სერვერი Amp-ის მომხმარებლის პარამეტრებში და Claude Code-ის მომხმარებლის კონფიგურაციაში, ორივე მიმართულია `${TUIST_URL}/mcp`-ზე, Tuist CLI-სთან ერთად და უნარით, რომელიც ეუბნება აგენტს, როდის შეამოწმოს შედეგები პროექტის ისტორიის მიხედვით. სხვაგან, თავად დაამატეთ სერვერი ზემოთ მოცემული ჰედერით.

ეს ტოკენები იძლევა მხოლოდ წაკითხვის უფლებას დაკავშირებული ანგარიშის ყველა პროექტზე: ისინი შეიცავენ `mcp` ჯგუფის წაკითხვის სფეროებს და არაფერს, რაც ქმნის, ცვლის ან შლის მონაცემებს, მაგალითად, ტესტების ჩუმად დატოვებას ან გამოტოვებას. სამუშაო სივრცის ან გარემოს გათიშვა წყვეტს წვდომას შემდეგი მოთხოვნისას და წვდომა არასდროს სცდება თავად ტოკენის ვადას. Amp სამუშაო სივრცე, რომელიც დაკავშირებულია რამდენიმე Tuist ანგარიშთან, უარყოფილია, რადგან მისი ტოკენი არ ასახელებს ერთს. როდესაც კავშირი არ არსებობს, არაავტორიზებული პასუხის `error_description` ამბობს ამას.

ეს მხოლოდ წაკითხვის უფლება ვრცელდება მხოლოდ Model Context Protocol endpoint-ზე. ბრძანების ხაზის ინსტრუმენტი და build-system ინტეგრაციები იმავე sandbox-ში კვლავ ცვლიან ტოკენს კავშირის CI წვდომისთვის.

## WebMCP

ბრაუზერებში, რომლებიც მხარდაჭერენ [WebMCP](https://webmachinelearning.github.io/webmcp)-ს, Tuist-ის გვერდები არეგისტრირებენ ინსტრუმენტებს `document.modelContext`-ით, ასე რომ ბრაუზერში ჩაშენებულ აგენტებს შეუძლიათ გამოიძახონ ისინი დამატებითი კონფიგურაციის გარეშე. ზარები შესრულდება Tuist-ის სერვერზე.

- **ვებსაიტისა და დოკუმენტაციის გვერდები** არეგისტრირებენ დოკუმენტაციისა და წყაროს ინსტრუმენტებს (`search_tuist`, `search_tuist_code`, `list_tuist_files` და `read_tuist_file`). მათ არ სჭირდებათ თქვენი შესვლა.
- **ანგარიშის dashboard გვერდები**, როდესაც შესული ხართ, არეგისტრირებენ Tuist-ის მხოლოდ წაკითხვის ინსტრუმენტებს ამ ანგარიშისთვის. თითოეული გვერდი არეგისტრირებს მხოლოდ იმ ინსტრუმენტებს, რასაც ის აჩვენებს, პროექტის build system-ისთვის: Gradle პროექტის builds გვერდი იღებს Gradle build ინსტრუმენტებს, მისი test გვერდები — test და coverage ინსტრუმენტებს, runners გვერდები — runner ინსტრუმენტებს, ხოლო sandboxes გვერდები — sandbox ინსტრუმენტებს. თქვენი პირადი ანგარიშის AI პარამეტრების გვერდის Subscriptions სექცია იღებს `list_ai_subscriptions`-ს, რომელიც პასუხობს მხოლოდ თქვენს საკუთარ ანგარიშზე. ყოველ გვერდს ასევე აქვს დოკუმენტაციის ინსტრუმენტები, `list_projects` და `get_project`. ინსტრუმენტები მუშაობენ შესული მომხმარებლის სახელით, ამიტომ ისინი მხოლოდ იმ მონაცემებს აღწევენ, რომელთა წაკითხვაც შეგიძლიათ dashboard-ში და მხოლოდ იმ ანგარიშს, რომელსაც უყურებთ. როდესაც გადადიხართ სხვა გვერდზე ან ანგარიშზე, ინსტრუმენტები იცვლება იმ გვერდის ინსტრუმენტებით.

ინსტრუმენტები, რომლებიც ქმნიან, ცვლიან ან შლიან მონაცემებს, არ არის ხელმისაწვდომი WebMCP-ის საშუალებით, რადგან ბრაუზერის აგენტი იღებს ინსტრუმენტებს თქვენი დამატების გარეშე და კითხულობს კონტენტს, რომელსაც builds და tests წარმოქმნიან. დააკავშირეთ MCP კლიენტი `/mcp` endpoint-თან ამ ინსტრუმენტების გამოყენებისთვის.

თუ ორგანიზაცია აიძულებს ერთჯერად შესვლას (single sign-on), შედით dashboard-ში მისი პროვაიდერის საშუალებით, რათა გამოიყენოთ მისი ინსტრუმენტები.

## Build-system ინტეგრაციები იყენებენ ორ რწმუნებას

რწმუნება, რომელიც გამოიყენება Model Context Protocol ინსტრუმენტებისთვის, არ ავთენტიფიცირებს Gradle პლაგინს ან Bazel-ის remote სერვისებს. სანამ აგენტი შეცვლის ან გადაამოწმებს Gradle ან Bazel ინტეგრაციას, მან უნდა გაუშვას:

```bash
tuist auth whoami --url https://tuist.dev
```

თუ ეს ბრძანება არ არის ავთენტიფიცირებული, აგენტმა უნდა შეწყვიტოს და სთხოვოს მომხმარებელს გაუშვას:

```bash
tuist auth login --url https://tuist.dev
```

ლოკალური ან self-hosted განლაგებისთვის, შეცვალეთ URL ორივე ბრძანებაში და `tuist.toml`-ში. შეინახეთ hostname-ის მართლწერა იდენტური ყველგან. მაგალითად, `localhost` და `127.0.0.1` იყენებენ ცალკე შენახულ რწმუნებებს.


## შესაძლებლობები

### ინსტრუმენტები

შემდეგი ინსტრუმენტები ხელმისაწვდომია Tuist Model Context Protocol სერვერის საშუალებით:

ყოველი ინსტრუმენტი აქვეყნებს ადამიანისთვის წასაკითხ აღწერას ცხადი input და output სქემებთან ერთად. წარმატებული ზარები აბრუნებენ სტრუქტურირებულ კონტენტს, რომელიც შეესაბამება გამოცხადებულ output სქემას, პლუს იგივე შედეგი ტექსტად სერიალიზებული იმ კლიენტებისთვის, რომლებიც ჯერ არ მოიხმარენ სტრუქტურირებულ კონტენტს.

ინსტრუმენტები, რომლებიც იღებენ ერთი ჩანაწერის იდენტიფიკატორს, როგორიცაა `build_run_id`, `test_run_id`, `test_case_id`, `bundle_id`, `run_id`, `generation_id`, ან `cache_run_id`, ასევე იღებენ ამ ჩანაწერის Tuist dashboard URL-ს. ჩასვით URL პირდაპირ ბრაუზერიდან მისგან იდენტიფიკატორის ამოღების ნაცვლად.

#### უკუკავშირი

აგენტებს შეუძლიათ შეატყობინონ Tuist-ის გუნდს, როდესაც Tuist-ის ინსტრუმენტი ან prompt არ მუშაობდა მოსალოდნელი გზით, მაგალითად, გაუგებარი შედეგი, შეცდომა, მონაცემების ნაკლებობა ან შესაძლებლობის არარსებობა. აგენტებს ეთხოვებათ შესთავაზონ ანგარიში და გაგზავნონ ის მხოლოდ თქვენი თანხმობის შემდეგ. თითოეული ანგარიში ხსნის საუბარს Tuist-ის მხარდაჭერასთან, რომელმაც შეიძლება პასუხი მოგწეროთ ელფოსტით. ანგარიში მოიცავს იმას, რასაც აგენტი ელოდა, რა მოხდა, სურვილისამებრ შეთავაზებას, თქვენს Tuist მომხმარებლის ID-ს, handle-ს და ელფოსტას, ასევე ორგანიზაციებს, რომლებსაც ეკუთვნით. აგენტებს ასევე შეუძლიათ მიუთითონ ანგარიში და პროექტი, სადაც პრობლემა მოხდა, რათა გუნდმა იცოდეს, რომელ ორგანიზაციას უნდა მიჰყვეს; მიღებულია მხოლოდ ის ანგარიშები, რომლებსაც თქვენ ეკუთვნით. ანგარიშების გაგზავნა შეუძლიათ მხოლოდ Tuist მომხმარებლად შესულ აგენტებს და თითოეულ მომხმარებელს შეუძლია გახსნას საათში 10-მდე ანგარიში. ინსტრუმენტი ხელმისაწვდომია მხოლოდ Tuist-ის მიერ დაჰოსტულ სერვერზე `https://tuist.dev/mcp`.

ნაბიჯები ნაგულისხმევად იკრიბება Xcode ბილდების დამუშავებისას. ჩაწერილი ნაბიჯის მონაცემები ინახება 90 დღის განმავლობაში. სიის პასუხი შეიცავს `availability`-ს: `available`, როცა ჩაწერილი ნაბიჯები არსებობს, მაშინაც კი, თუ ფილტრები არაფერს ემთხვევა; `processing`, როცა ბილდი ჯერ კიდევ მუშავდება და ნაბიჯები ჯერ არ აქვს; ან `unavailable`, როცა ნაბიჯები არ ჩაწერილა ან ვადა გაუვიდათ.

Gradle და Bazel ნაბიჯების სიები ნაგულისხმევად აბრუნებენ 20 შედეგს (მაქსიმუმ 100), მხარდაჭერილია `search`, ზუსტი `project`, `target`, `category` და `status`, გადაფარვის `start_ms` / `end_ms` ფილტრები (ბოლო არ არის ჩართული) და `duration_ms` ან `start_ms` დალაგება. გადაეცით მიღებული ID-ები უცვლელად; ისინი შეზღუდულია მათი ბილდის ფარგლებში. სიები ასახავენ `time_origin`-ს და `coverage`-ს. უფრო ძველი Gradle ანგარიშები იყენებენ `first_recorded_timestamp`-ს, რადგან ბილდის დაწყება არ აიტვირთა. Bazel პროფილები ასახავენ ყველა ჩაწერილ ინტერვალს `trace_profile` დაფარვით და `profile_start`-ს როგორც დროის საწყისს. უფრო ძველი ბილდები ეყრდნობიან შენახულ BEP შეჯამებებს. წყაროს ჩანაწერების ვადა გადის 90 დღის შემდეგ. Bazel დეტალები მოიცავს გასუფთავებულ მოქმედების ლოგებს, როცა ისინი გამოქვეყნებულია. წარუმატებელი ამოცანის ან კონფიგურაციის ნაბიჯის Gradle დეტალები მოიცავს შეცდომის შეტყობინებას, რომელიც Tuist Gradle პლაგინმა აღნიშნა როგორც `log`: გამონაკლისის შეტყობინება და მისი მიზეზების ჯაჭვი, როგორც Gradle-ის კონსოლი ბეჭდავს მათ, სტეკის ტრეისების ან ამოცანის გამოსავლის გარეშე, პროექტის შიგნით არსებული გზები გადაყვანილია ფარდობითად, ხოლო სერთიფიკატები და სხვა ლოკალური გზები დაფარულია, მაქსიმუმ 16 KiB ნაბიჯზე და 32 წარუმატებელი ნაბიჯი ბილდზე. სხვა Gradle ნაბიჯებს, პლაგინის უფრო ძველი ვერსიებით შეტყობინებულ ბილდებს და სერთიფიკატების გარეშე ანგარიშებს აქვთ null `log`. კონფიგურაციის ნაბიჯები ანგარიშობენ `failure`-ს, როცა ისინი წარუმატებელია და `unknown`-ს სხვა შემთხვევაში. `compare_builds` მოთხოვნა იყენებს ამ დაფარვას სრული Bazel ტრეისების განსასხვავებლად შენახული შეჯამებებისგან და მიმართავს აგენტებს ნაბიჯის დეტალებისკენ მოქმედების შედეგებისა და ლოგებისთვის, სანამ ფართო გამოძახების გამოსავალს შეამოწმებენ.

ეს ინსტრუმენტები თანდათანობით იშლება და აბრუნებენ მონაცემებს მხოლოდ იმ პროექტებისთვის, სადაც ისინი ჩართულია; სხვა პროექტებისთვის ისინი აბრუნებენ შეცდომას ცარიელი შედეგის ნაცვლად. ტიპი ხელმისაწვდომია მხოლოდ იმ პროექტებისთვის, რომლებიც იყენებენ შესაბამის ბილდის ხელსაწყოთა ჯაჭვს. ინსტრუმენტები იღებენ შემოსაზღვრულ `start_at`/`end_at` ფილტრებს, `environment` (`any`, `ci`, ან `local`) და ზუსტ `branch`. `list_build_entities` იღებს `q`-ს; `list_build_entity_history` მხარს უჭერს გაუმჭვირვალე `after`/`before` კურსორებს. უცნობი დროის ან ქეშის დაკვირვებები რჩება მიუწვდომლად, ნულის ან გამოტოვების ნაცვლად. ისტორია მიუთითებს ჩაწერილ მშობელზე და ნატიურ შესრულებაზე დეტალური ანალიზისთვის არსებული გაშვების ინსტრუმენტების გამოყენებით.

`get_build_entity` მეტრიკები მოიცავს `duration_samples`-ს, რაც არის ჩაწერილი დროის მქონე დაკვირვებების რაოდენობა: რეალური ნულოვანი ხანგრძლივობები ითვლება, ხოლო დაკარგული დრო — არა. ეს რაოდენობა შეიძლება იყოს დაკვირვებების რაოდენობაზე ნაკლები; მიუწვდომელი ხანგრძლივობის სტატისტიკა რჩება null.

Xcode მოდულების ხანგრძლივობა მოდის ბილდის ლოგებში გაზომილი სამიზნე კომპილაციებიდან. მოდულის ქეშის გადაწყვეტები და სამიზნეები კომპილაციის გარეშე არ წვლილობენ ხანგრძლივობის შერჩევებში. კომპილაციის დაკვირვებები მიუთითებენ Xcode ბილდზე; ქეშის მოვლენები მიუთითებენ გენერაციის ან ქეშის ბრძანებაზე.

Bazel მოქმედებები იდენტიფიცირდება სამიზნე ლეიბლით, მნიშვნელობით და კონფიგურირებული ძირითადი გამომავალით, რაც ინარჩუნებს ცალკეულ მოქმედებებსა და კონფიგურაციებს განცალკევებულად, შეყვანაზე დამოკიდებული ქეშის დაიჯესტების გარეშე. ისტორია აღრიცხავს BEP-ით მოხსენებულ შესრულებებს, არა ქეშის ძიებებს ან ტრეის-პროფილის ფაზებს. სრული შესრულების დაფარვა მოითხოვს `--build_event_publish_all_actions`-ს; არტიფაქტების მიწოდება ხდება მაქსიმალური ძალისხმევით, ამიტომ დაკარგული დაკვირვებები არ არის იმის მტკიცებულება, რომ სამუშაო არ შესრულებულა. უფრო ძველი Kura პეილოადები სტაბილური იდენტობის ან შესრულების დასაწყისის გარეშე კვლავ მიიღება, მაგრამ არ ინდექსირდება. დასასრულის დროის გაზომვების არარსებობა რჩება მიუწვდომლად და რეალური ნულოვანი ხანგრძლივობები ითვლება.

Mix მოდულების ხანგრძლივობა ზომავს შემცველი ფაილის კომპილაციას, არა დამოუკიდებლად გაზომილ მოდულურ სამუშაოს. Once მოქმედებები იყენებენ გამოცხადებულ მიზნის/შესაძლებლობის/ინდექსის სლოტებს, როდესაც კლიენტმა მოახსენა მიზნის შესაბამისობები; მხოლოდ დიაგნოსტიკური ლეიბლები არ არის სტაბილური იდენტობები. არსებული კლიენტები და გაშვების დონის ინსტრუმენტები უცვლელად რჩება მხარდაჭერილი.

Cargo კრეიტები დაჯგუფებულია ზუსტად ჩაწერილი კრეიტის ფესვის, სახელისა და ტიპის მიხედვით. Checkout-ბილიკის ცვლილებებმა შეიძლება გაყოს ისტორიები, ხოლო ბილდის პროფილები, ფუნქციები და მიზნის ტრიპლეტები არ განირჩევა. ისტორია ზომავს rustc გამოძახებებს, არა ფაილზე დამოკიდებულ სამუშაოს ან ქეშის მოხვედრებს; არარსებული სამუშაოები არ ამყარებს წაშლას ან სამუშაო სივრცის სრულ ინვენტარს.

ანალიტიკის წაკითხვებს აქვს შეზღუდული მეხსიერება და შესრულების დრო. თუ მოთხოვნა აღემატება ამ ლიმიტებს, ინსტრუმენტი აბრუნებს შეცდომას ცარიელი შედეგის გამოგონების ნაცვლად.

| `ci_job.failed` | Tuist-ის გამშვების სამუშაო სრულდება შეცდომით. | `account_handle` |

გამოსაწერად, კლიენტი იძახებს `events/subscribe` მოვლენის სახელით, ზემოთ ჩამოთვლილი ხელსაწყოებით `arguments`-ში და `webhook` მიწოდებით, რომელიც შეიცავს `https://` callback URL-ს და `whsec_` ხელმოწერის საიდუმლოს. პროექტის მოვლენები მოითხოვს ანგარიშის წევრობას და შესაბამისი ტესტის ან ბილდის მონაცემებზე წვდომას; გამშვების სამუშაოს მოვლენები მოითხოვს ანგარიშის წევრობას და გამშვებზე წვდომას. მოთხოვნილმა [`auth.md`](https://workos.com/auth-md) წვდომის ტოკენებმა, მოთხოვნილმა ანგარიშის ტოკენებმა და ბრაუზერის ავტორიზაციის გრანტებმა შეიძლება შექმნან გამოწერები; მიწოდება ჩერდება, როდესაც შესაბამისი სერთიფიკატი აღარ არის აქტიური. თითოეულ მომხმარებელს შეუძლია შეინარჩუნოს მაქსიმუმ 25 აქტიური გამოწერა. Tuist აგზავნის ვერიფიკაციის გამოწვევას callback-ზე გამოწერის შენახვამდე. callback-მა უნდა დააბრუნოს ობიექტი, რომელიც შეიცავს იგივე `challenge` მნიშვნელობას. გამოწერა ძალაშია შვიდი დღის განმავლობაში ნაგულისხმევად, შეიძლება განახლდეს ხელახალი გამოწერით და ჩერდება მიწოდება, როდესაც მომხმარებლის წვდომა ან სერთიფიკატი იხსნება. არასავალდებულო `ttlMs` შემოიფარგლება ერთ საათსა და 30 დღეს შორის. Tuist ხელახლა ცდილობს დროის ამოწურვის მქონე callback-ს და აუქმებს მას სამი თანმიმდევრული დროის ამოწურვის შემდეგ, რომლებიც მოიცავს ხუთ წუთს; ხელახლა გამოიწერეთ callback-ის აღდგენის შემდეგ.

როდესაც მოვლენა ხდება, Tuist აგზავნის მის რესურსის იდენტიფიკატორს და დაფის URL-ს callback-ზე. ბილდისა და ტესტების გაშვების შეცდომები ასევე მოიცავს `is_ci` და `git_branch`-ს, რათა კლიენტებმა შეძლონ ლოკალური შეცდომების იგნორირება ან შტოს მიხედვით ფილტრაცია. ბილდის მოვლენები მოიცავს `build_system`-ს; გამშვების სამუშაოს მოვლენები მოიცავს როგორც `workflow_job_id`-ს, ასევე `workflow_run_id`-ს. მოთხოვნა მოიცავს გამოწერის იდენტიფიკატორს და [Standard Webhooks](https://www.standardwebhooks.com/) ხელმოწერის ჰედერებს, რათა კლიენტმა შეძლოს მისი წყაროს ვერიფიკაცია. Tuist ხელახლა ცდილობს წარუმატებელ მიწოდებებს, ამიტომ კლიენტებმა უნდა გამოიყენონ სტაბილური `eventId` დუბლიკატების გასაფილტრად. Payload არ შეიცავს ტესტების სახელებს, ლოგებს და შეცდომის შეტყობინებებს; კლიენტმა შეიძლება მიიღოს ეს დეტალები ზემოთ ჩამოთვლილი ინსტრუმენტების მეშვეობით და გადაწყვიტოს, შეატყობინოს თუ არა გუნდს ან დაიწყოს დებაგინგი. კლიენტებმა შეუძლიათ შეაჩერონ მიწოდება `events/unsubscribe`-ით.

#### Gradle ინტეგრაციის მოთხოვნის ფუნქციები

`integrate_gradle_project` მოთხოვნა და `get_gradle_integration_guide` ინსტრუმენტი აღწერენ სრულ setup workflow-ს. ინსტრუმენტზე ასევე არის მითითება სერვერის ინიციალიზაციის ინსტრუქციებში, რაც მას აღმოჩენადს ხდის აგენტებისთვის, რომლებიც არ ჩამოთვლიან მოთხოვნებს.

| ფუნქცია | რას აკონფიგურირებს აგენტი |
|---------|---------------------------|
| `remote_cache` | ააქტიურებს Gradle-ის ბილდის ქეშს, აკონფიგურირებს Tuist remote cache ატვირთვის პოლიტიკას და ურჩევს ატვირთვას მხოლოდ continuous integration გამშვებებიდან ლოკალური მხოლოდ-წაკითხვადი გამოყენებით. |
| `build_insights` | აყენებს Tuist Gradle პლაგინს და საჭიროების შემთხვევაში აკონფიგურირებს ბილდის ანალიტიკის ატვირთვის ქცევას. |
| `test_insights` | აყენებს Tuist Gradle პლაგინს, რათა Gradle `Test` ამოცანის შედეგები ავტომატურად აიტვირთოს. |

| `test_sharding` | ამატებს continuous integration workflow-ს `tuistPrepareTestShards`-ისთვის, shard matrix-ის გენერაციისთვის და `TUIST_SHARD_INDEX`-ზე დაფუძნებული ტესტების გაშვებისთვის. |

როდესაც `features` გამოტოვებულია, მოთხოვნა სთხოვს აგენტს დააზუსტოს, რომელი ინტეგრაციები სურს მომხმარებელს ან გამოიტანოს უმცირესი სასარგებლო ნაკრები მოთხოვნიდან Gradle პროექტის რედაქტირებამდე.
