# Model Context Protocol

[Model Context Protocol (MCP)](https://modelcontextprotocol.io/docs/getting-started/intro) არის ღია სტანდარტი, რომელიც საშუალებას აძლევს ხელოვნური ინტელექტის აგენტებს ურთიერთქმედებდნენ გარე სერვისებთან და მონაცემთა წყაროებთან. ის უზრუნველყოფს [Claude](https://claude.ai/), [Claude Code](https://docs.anthropic.com/en/docs/claude-code), [Codex](https://developers.openai.com/codex/) და რედაქტორების, როგორიცაა [Zed](https://zed.dev), [Cursor](https://www.cursor.com) ან [Visual Studio Code](https://code.visualstudio.com), თავსებადობას Tuist-თან.

Tuist განათავსებს Model Context Protocol-ის სერვერულ ბოლოწერტილს მისამართზე `https://tuist.dev/mcp`. თქვენი კლიენტის მასთან მიერთებით, აგენტებს შეუძლიათ მიიღონ წვდომა თქვენს Tuist პროექტის მონაცემებზე, მათ შორის ტესტების ანალიტიკაზე, არასტაბილური ტესტების ანალიზზე და სხვა. უმეტესი ინსტრუმენტი მხოლოდ წაკითხვადია და შემოიფარგლება ავტორიზებული Tuist პროექტის მონაცემებით. ანგარიშის მოწყობის ინსტრუმენტებს შეუძლიათ ჩამოთვალონ ანგარიშები, შექმნან ორგანიზაციები, შექმნან პროექტები და დაამატონ არსებული მომხმარებლები ორგანიზაციებში, როდესაც ავტორიზებულ მომხმარებელს აქვს საჭირო ნებართვები. ყოველი ინსტრუმენტი აცხადებს ანოტაციებს, რომლებიც მიუთითებს, არის თუ არა ის მხოლოდ წაკითხვადი, შეუძლია თუ არა გამოიწვიოს ძნელად შექცევადი ცვლილება და შეუძლია თუ არა შეცვალოს საჯარო ინტერნეტის მდგომარეობა. ანგარიშის მოწყობის ინსტრუმენტები მოითხოვს მომხმარებლის ავტორიზაციას. ისინი არ არის ხელმისაწვდომი პროექტის ტოკენებისთვის ან ჩვეულებრივი ანგარიშის ტოკენებისთვის. როდესაც მომხმარებელი ანიჭებს კლიენტს ნებართვას ბრაუზერში ან ადასტურებს `auth.md` რეგისტრაციას, Tuist ამ სერთიფიკატს ასოცირებს მომხმარებელთან მხოლოდ Model Context Protocol-ის ბოლოწერტილზე, რათა მოწყობის ინსტრუმენტებმა შეძლონ მოთხოვნილი სამუშაო პროცესის დასრულება.

Tuist ახორციელებს [2026-07-28 პროტოკოლს](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http). მოთხოვნები უმდგომარეოა: კლიენტები აგზავნიან თავიანთ პროტოკოლის მეტამონაცემებს ყოველ მოთხოვნასთან ერთად და შეუძლიათ პირდაპირ გამოიძახონ ინსტრუმენტები ინიციალიზაციის გარეშე. `server/discover` აბრუნებს სერვერის იდენტობას, შესაძლებლობებს, მხარდაჭერილ ვერსიებს და ინსტრუქციებს. არ არსებობს სესიის იდენტიფიკატორები ან დამოუკიდებელი მოვლენათა ნაკადები. 2025-06-18 ან 2025-03-26 ინიციალიზაციის ნაკადის გამოყენებადი კლიენტები კვლავ მხარდაჭერილია; ისინიც მუშაობენ სერვერის სესიების გარეშე.

## Model Context Protocol უნარების წინააღმდეგ

Model Context Protocol-ის ინსტრუმენტებს და <.localized_link href="/guides/features/agentic-coding/skills">უნარებს</.localized_link> შეიძლება ჰქონდეთ გადახურვა ფუნქციებში. ამჟამინდელი გადახურვის გათვალისწინებით, აირჩიეთ ერთი მიდგომა სამუშაო პროცესისთვის და გამოიყენეთ ის თანმიმდევრულად, ნაცვლად ორივეს ერთდროულად გამოყენებისა იმავე ნაკადში.

კლიენტებისთვის, რომლებიც მხარდაჭერენ პლაგინების ინსტალაციას, გამოიყენეთ <.localized_link href="/guides/features/agentic-coding/plugins">Tuist პლაგინები</.localized_link> ორივეს ერთად ინსტალაციისთვის.

## კონფიგურაცია

დაამატეთ `https://tuist.dev/mcp` როგორც დისტანციური Model Context Protocol სერვერი თქვენს კლიენტში. სერვერის ინიციალიზაციის ინსტრუქციები და საჯარო სერვერის ბარათი აღწერენ OAuth 2.0-ს დინამიური კლიენტის რეგისტრაციით და სტანდარტული ბრაუზერის ავტორიზაციის ნაკადით პირდაპირ, აგენტებისგან გარე ავტორიზაციის დოკუმენტების მოთხოვნის ან მათი მიყოლის გარეშე. ეს სერვერის მასშტაბის ინსტრუქციები ინარჩუნებენ სამუშაო პროცესის სახელმძღვანელოს ზოგადს: ინსტრუმენტის ავტორიზაცია არ ავტორიზებს ადგილობრივ ბრძანების სტრიქონის ინსტრუმენტებს ან აგების სისტემის ინტეგრაციებს და აგენტებმა უნდა დაადასტურონ მოთხოვნილი ცვლილებები შესაბამისი Tuist ინსტრუმენტების მეშვეობით. აგების სისტემის სპეციფიკური მოწყობა და ავტორიზაციის შემოწმებები დოკუმენტირებულია ინტეგრაციის სახელმძღვანელოებსა და მოთხოვნებში. Tuist კვლავ აცხადებს როგორც [Open Authorization](https://oauth.net/2/) აღმოჩენის მეტამონაცემებს, ასევე მიმდინარე [auth.md პროტოკოლს](https://workos.com/auth-md) მისამართზე `https://tuist.dev/auth.md` ცალ-ცალკე.

თუ თქვენი რომელიმე ორგანიზაცია აიძულებს ერთჯერად შესვლას (SSO), კლიენტის ბრაუზერში ავტორიზება მოითხოვს იმ ორგანიზაციის მეშვეობით შესულ სესიას და Tuist საჭიროების შემთხვევაში ჯერ პროვაიდერთან გაგზავნით. იხილეთ <.localized_link href="/guides/integrations/authentication/sso#choose-an-enrollment-policy">ერთჯერადი შესვლა</.localized_link>.

ბოლოწერტილი იღებს უმდგომარეო `2026-07-28` Model Context Protocol მოთხოვნის სიცოცხლის ციკლს, მათ შორის `server/discover`-ს, უფრო ძველ სესიაზე დაფუძნებულ ციკლთან ერთად. არსებულ კლიენტებს შეუძლიათ განაგრძონ თავიანთი მიმდინარე შეერთების მეთოდის გამოყენება.

კლიენტებს, რომლებიც მხარდაჭერენ Model Context Protocol მოვლენებს, შეუძლიათ გამოიწერონ პროექტის მოვლენები. იხილეთ [მოვლენები](#events) ხელმისაწვდომი მოვლენებისა და მიწოდების მოთხოვნებისთვის.

კლიენტებს, რომლებიც უკვე მხარდაჭერენ დისტანციურ ბრაუზერის ავტორიზაციას, შეუძლიათ განაგრძონ ავტორიზაცია ბრაუზერში. კლიენტებსა და აგენტებს, რომლებიც მხარდაჭერენ `auth.md`-ს, შეუძლიათ ანონიმურად რეგისტრაცია, წარმოადგინონ სანდო პროვაიდერის იდენტობის დადასტურება ან დაიწყონ სერვისით ავტორიზებული ელფოსტის მოთხოვნა. რეგისტრაცია აბრუნებს Tuist-ით ხელმოწერილ იდენტობის დადასტურებას, რომელსაც აგენტი ცვლის სტანდარტულ ტოკენის ბოლოწერტილზე ერთსაათიანი წვდომის ტოკენისთვის. Tuist აქვეყნებს თავის საჯარო ხელმოწერის გასაღებს და მხარდაჭერს სტანდარტულ ტოკენის გაუქმებასა და პროვაიდერის უსაფრთხოების მოვლენების მიწოდებას.

არაავტორიზებულმა აგენტმა უნდა წაიკითხოს Model Context Protocol-ის ბოლოწერტილის მიერ დაბრუნებული `WWW-Authenticate` ჰედერი, მიიღოს დაცული რესურსის მეტამონაცემები, მიიღოს ავტორიზაციის სერვერის მეტამონაცემები და მიჰყვეს მის `agent_auth.skill` URL-ს. Tuist ასევე აბრუნებს იმავე ადგილობრივ `auth_md` URL-ს არაავტორიზებული პასუხის სხეულში, რათა ენის მოდელზე დაფუძნებულმა კლიენტებმა შეძლონ ნაკადის აღმოჩენა ნატიური კლიენტის ინტეგრაციაზე დაყრდნობის გარეშე. განლაგების ადგილობრივი დოკუმენტი არის ჭეშმარიტების წყარო ბოლოწერტილების სახელების, მოთხოვნის სხეულების, მოთხოვნის გამოკითხვისა და დადასტურების გაცვლისთვის.

სანამ აგენტი დაიწყებს ელფოსტის მოთხოვნას, მან უნდა სთხოვოს მომხმარებელს დაადასტუროს ელფოსტის მისამართი მათი Tuist ანგარიშისთვის. მან არ უნდა გამოიტანოს ეს მისამართი პროვაიდერის პროფილიდან, Git კონფიგურაციიდან, გარემოს ცვლადიდან ან სესიის მეტამონაცემებიდან.

ბოლოწერტილი იყენებს `mcp` სკოპის ჯგუფს. ანონიმურმა წინასწარ მოთხოვნის სერთიფიკატმა შეიძლება აღმოაჩინოს შესაძლებლობები და წაიკითხოს საჯარო ინტეგრაციის სახელმძღვანელო, მაგრამ ის არ განიხილება როგორც შესული მომხმარებელი. ბრაუზერის ავტორიზაციის ან მოთხოვნის შემდეგ, სერთიფიკატი მომხმარებლის სკოპისაა და თითოეული ინსტრუმენტი იყენებს იმავე ავტორიზაციის შემოწმებებს, რასაც დაშბორდი. დეტალებისთვის იხილეთ <.localized_link href="/guides/server/authentication#scope-groups">სკოპის ჯგუფების დოკუმენტაცია</.localized_link>.

ინსტრუმენტები წყდება პროექტებზე, რომელთა წაკითხვაც ავტორიზებულ მომხმარებელს უკვე შეუძლია. Xcode და Gradle აგების ინსტრუმენტები იღებენ აგების UUID-ს ან დაშბორდის URL-ს. UUID-მ უნდა მოახდინოს ზუსტად ერთი პროექტის იდენტიფიცირება; თუ ის რამდენიმე პროექტში ჩანს, ინსტრუმენტი აბრუნებს „არ არის ნაპოვნი“-ს, ნაცვლად სხვა პროექტის ანგარიშის არჩევისა. პროექტის სკოპის დაშბორდისა და API-ს წაკითხვები კვლავ ხელმისაწვდომია. მოხსენებული აქტორის იდენტიფიკატორები არიან დაუდასტურებელი ლეიბლები, არა სერთიფიკატები ან დამატებითი წვდომის უფლებები.

აგების სიისა და დეტალური ინფორმაციის ინსტრუმენტები აჩვენებენ არასავალდებულო `tuist_version` მეტამონაცემებს: Xcode-ისა და Cargo-სთვის – Tuist CLI, Gradle-ისთვის – Tuist Gradle პლაგინი, ხოლო Mix-ისთვის – `tuist_ex` ბიბლიოთეკა. Xcode ასევე აჩვენებს `tuist_generation_version`-ს მის მიერთებული პროექტის გენერაციის მოვლენიდან, რაც შეიძლება განსხვავდებოდეს ატვირთვის CLI-სგან. გამოტოვებული დაკვირვებები არის null, არა სერვერიდან ან სხვა ანგარიშიდან გამოყვანილი. Bazel იყენებს თავის არსებულ `bazel_version`-ს; Once გაშვების დეტალები აჩვენებს `once_version`-ს. ეს ველები აღწერენ მოხსენებულ ვერსიებს, არა დადასტურებულ იდენტობას ან სადენის კონტრაქტის ვერსიებს. REST აგების ბოლოწერტილები აჩვენებენ იმავე მეტამონაცემებს. არსებულ ინტეგრაციასა და ცვალებადი ტესტების უნარებს არ სჭირდებათ ვერსიის ველები და არ საჭიროებენ სამუშაო ნაკადის ცვლილებებს.

Tuist-ის ოპერატორები, რომლებიც იკვლევენ მომხმარებლის ანგარიშს, ამას აკეთებენ Tuist-ის შიდა ოპერაციული ინსტრუმენტების მეშვეობით, რომელიც იწერს ყოველ ზარს; ამ ბოლოწერტილთან პირდაპირი კავშირი არ იძლევა წვდომას მომხმარებლის საკუთარი წევრობის ფარგლებს გარეთ.

### Pulse

Pulse აჩვენებს ოთხ მხოლოდ წასაკითხ ინსტრუმენტს, რომლებიც ყველა მიმართულია `account_handle`-ით:

| ინსტრუმენტი | REST ექვივალენტი `/api/accounts/:account_handle/pulse` ქვეშ |
| --- | --- |
| `query_pulse` | `GET /:signal` |
| `get_pulse_analytics` | `GET /:signal/analytics` |
| `get_pulse_error_issue` | `GET /errors/issues/:issue_id` |
| `get_pulse_error_event` | `GET /errors/issues/:issue_id/events/:event_id` |

Pulse შეზღუდულია სერვერზე კონფიგურირებული ორგანიზაციის მიმდინარე წევრებისთვის, მაშინაც კი, თუ ანგარიში ან პროექტი საჯაროა. ის მოითხოვს მომხმარებლის ავთენტიკაციას ან მომხმარებელთან დაკავშირებულ `mcp` სერთიფიკატსა და ანგარიშის წაკითხვის ავტორიზაციას. პროექტის ტოკენები, ჩვეულებრივი ანგარიშის ტოკენები, ანონიმური რეგისტრაციები და ოპერატორის წვდომა ორგანიზაციის წევრობის გარეშე არ იძლევა Pulse-ის წვდომას. სერთიფიკატებს არ შეუძლიათ აირჩიონ სხვა backend ან ტელემეტრიის tenant. ბრაუზერის აგენტები იღებენ ამ ოთხ ინსტრუმენტს მხოლოდ Pulse-ის გვერდებზე, ამ გვერდის ანგარიშის სკოპის ფარგლებში.

REST მოითხოვს მომხმარებლის სერთიფიკატს. OAuth და `auth.md` მომხმარებლის ასოციაციები ხელმისაწვდომია მხოლოდ `/mcp` ბოლოწერტილზე; ანგარიშის სერთიფიკატი მიმდინარე მომხმარებლის გარეშე უარყოფილია, მიუხედავად დაკავშირებული ანგარიშის წევრობისა ან ხილვადობის.

`query_pulse` იღებს `signal`-ს (`metrics`, `logs`, `traces` ან `errors`), არასავალდებულო `query`-ს და `range`-ს (`15m`, `1h`, `6h` ან `24h`, ნაგულისხმევი `1h`). მეტრიკები, ჟურნალები და ტრეისები იღებენ ნატიურ PromQL, LogQL და TraceQL გამოსახულებებს. შეცდომები აბრუნებენ დაჯგუფებულ საკითხებს; მათი `query` არის სათაურის ლიტერალური ძიება, არა ნატიური გამოსახულება. ცხრილები იღებენ `search`-ს, `page`-ს (ნაგულისხმევი `1`), `page_size`-ს (`1`–`100`, ნაგულისხმევი `20`), `sort_by`-ს და `sort_order`-ს (`asc` ან `desc`). დალაგების სვეტები დამოკიდებულია სიგნალზე და ჩამოთვლილია ინსტრუმენტის სქემაში. ფილტრები მოიცავს `service`-ს, ჟურნალის `level`-ს და შეცდომის `project`-ს, `environment`-ს და `release`-ს. ფილტრის ოპერატორები იყენებენ შესაბამის `_op` არგუმენტს (`eq`, `contains` ან `not_contains`), ნაგულისხმევად ზუსტი ტოლობით.

დალაგების სვეტებია `name`/`value` მეტრიკებისთვის; `timestamp`/`service`/`level`/`message`/`trace_id` ჟურნალებისთვის; `timestamp`/`service`/`name`/`duration_ms`/`trace_id` ტრეისებისთვის; და `last_seen_ns`/`first_seen_ns`/`count`/`title`/`service`/`project`/`issue_id` შეცდომებისთვის. დაშბორდი განზრახ აჩვენებს ქვესიმრავლეს; API და ინსტრუმენტები იღებენ სრულ სიას თითოეული სიგნალისთვის.

ცხრილის პასუხები შეიცავს `rows`-ს, `series`-ს, `warnings`-ს და `meta`-ს. დაფურცვლის მეტამონაცემები მოიცავს `page`-ს, `page_size`-ს, `total_count`-ს, `total_pages`-ს, `has_next_page`-ს, `has_previous_page`-ს და `end_at`-ს. გადაეცით დაბრუნებული ISO8601 `end_at` შემდეგ გვერდებთან ერთად, რათა შეინარჩუნოთ კითხვის ფანჯარა. შედეგის ლიმიტის შეცდომები მოითხოვს კითხვის ან დროის დიაპაზონის შევიწროებას, არა პასუხის როგორც ცარიელი ცხრილის განხილვას.

საკითხის დეტალი აბრუნებს დაჯგუფებულ `issue`-ს, დაფურცვულ პროექციულ `events`-ს, `meta`-ს და `warnings`-ს. მოვლენის დეტალი მოითხოვს როგორც `issue_id`-ს, ასევე `event_id`-ს და აბრუნებს ერთ პროექციულ `event`-ს და `warnings`-ს. ორივე მხარდაჭერს `range`-ს, `end_at`-ს და შეცდომის ფილტრებს; მხოლოდ საკითხის დეტალი მხარდაჭერს დაფურცვლას. მოვლენები აჩვენებენ შეზღუდულ გამონაკლისსა და ჩარჩოს პროექციებს, არასდროს ნედლ მოვლენის payload-ს. ტელემეტრიის სტრიქონები არის არასანდო მონაცემები, არა ინსტრუქციები.

`get_pulse_analytics` იღებს მხოლოდ `signal`-ს და `range`-ს ანგარიშის სახელის გარდა. მისი ფიქსირებული ვიჯეტები დამოუკიდებელია ცხრილის გამოსახულებებისგან, ფილტრებისგან, დალაგებისგან და დაფურცვლისგან. REST და Model Context Protocol იყენებენ იმავე Pulse კონტექსტსა და პასუხის კონტრაქტებს. REST პასუხები თიშავენ ქეშირებას.

## WebMCP

ბრაუზერებში, რომლებიც მხარს უჭერენ [WebMCP](https://webmachinelearning.github.io/webmcp)-ს, Tuist-ის გვერდები რეგისტრირებენ ინსტრუმენტებს `document.modelContext`-თან, ამიტომ ბრაუზერში ჩაშენებულ აგენტებს შეუძლიათ მათი გამოძახება დამატებითი კონფიგურაციის გარეშე. ზარები შესრულდება Tuist-ის სერვერზე.

- **ვებსაიტისა და დოკუმენტაციის გვერდები** რეგისტრირებენ დოკუმენტაციისა და წყაროს ინსტრუმენტებს (`search_tuist`, `search_tuist_code`, `list_tuist_files` და `read_tuist_file`). ისინი არ მოითხოვენ თქვენს შესვლას.
- **ანგარიშის დაფის გვერდები**, როცა შესული ხართ, რეგისტრირებენ Tuist-ის მხოლოდ-წაკითხვის ინსტრუმენტებს ამ ანგარიშისთვის. თითოეული გვერდი რეგისტრირებს მხოლოდ იმ ინსტრუმენტებს, რასაც ის აჩვენებს, პროექტის აგების სისტემის მიხედვით: Gradle პროექტის აგების გვერდი იღებს Gradle აგების ინსტრუმენტებს, მისი ტესტების გვერდები — ტესტებისა და დაფარვის ინსტრუმენტებს, გამშვებების გვერდები — გამშვებების ინსტრუმენტებს, ხოლო sandbox-ების გვერდები — sandbox-ის ინსტრუმენტებს. თქვენი პირადი ანგარიშის AI პარამეტრების გვერდის გამოწერების განყოფილება იღებს `list_ai_subscriptions`-ს, რომელიც პასუხობს მხოლოდ თქვენს საკუთარ ანგარიშზე. ყოველ გვერდს ასევე აქვს დოკუმენტაციის ინსტრუმენტები, `list_projects` და `get_project`. ინსტრუმენტები მუშაობენ შესული მომხმარებლის სახელით, ამიტომ ისინი წვდებიან მხოლოდ იმ მონაცემებს, რომელთა წაკითხვაც შეგიძლიათ დაფაზე, და მხოლოდ იმ ანგარიშს, რომელსაც უყურებთ. როცა გადადიხართ სხვა გვერდზე ან ანგარიშზე, ინსტრუმენტები იცვლება იმ გვერდის ინსტრუმენტებით.

ინსტრუმენტები, რომლებიც ქმნიან, ცვლიან ან შლიან მონაცემებს, არ არის ხელმისაწვდომი WebMCP-ით, რადგან ბრაუზერის აგენტი იღებს ინსტრუმენტებს თქვენი დამატების გარეშე და კითხულობს შინაარსს, რომელსაც აგება და ტესტები ქმნიან. დააკავშირეთ MCP კლიენტი `/mcp` ბოლოწერტილთან ამ ინსტრუმენტების გამოსაყენებლად.

თუ ორგანიზაცია აიძულებს ერთჯერად შესვლას, შედით დაფაზე მისი პროვაიდერით, რათა გამოიყენოთ მისი ინსტრუმენტები.

## აგების სისტემის ინტეგრაციები იყენებენ ორ სერთიფიკატს

Model Context Protocol ინსტრუმენტებისთვის გამოყენებული სერთიფიკატი არ ავთენტიკირებს Gradle პლაგინს ან Bazel-ის შორეულ სერვისებს. სანამ აგენტი შეცვლის ან დაადასტურებს Gradle ან Bazel ინტეგრაციას, მან უნდა გაუშვას:

```bash
tuist auth whoami --url https://tuist.dev
```

თუ ეს ბრძანება არ არის ავთენტიკირებული, აგენტმა უნდა შეწყვიტოს და სთხოვოს მომხმარებელს გაუშვას:

```bash
tuist auth login --url https://tuist.dev
```

ლოკალური ან თვითმასპინძელი განლაგებისთვის, შეცვალეთ URL ორივე ბრძანებაში და `tuist.toml`-ში. შეინარჩუნეთ ჰოსტის სახელის წერა იდენტური ყველგან. მაგალითად, `localhost` და `127.0.0.1` იყენებენ ცალკე შენახულ სერთიფიკატებს.

არასავალდებულო `start_ms` და `end_ms` ირჩევენ ნაბიჯებს, რომლებიც ემთხვევიან დროის დიაპაზონს მილიწამებში ბილდის დაწყებიდან; ბოლო გამორიცხულია. ორივე ინსტრუმენტი იღებს ბილდის UUID-ს ან დაფის URL-ს როგორც `build_run_id`. გადასცით დაბრუნებული ნაბიჯის `id` უცვლელად როგორც `step_id` მისი ლოგის მისაღებად. ლოგები ინახავენ 64 KiB-მდე თითო ნაბიჯზე, `log_truncated` მიუთითებს გამოტოვებულ გამოტანაზე.

ნაბიჯები ავტომატურად გროვდება Xcode ბილდების დამუშავებისას. ჩაწერილი ნაბიჯის მონაცემები ინახება 90 დღის განმავლობაში. სიის პასუხი შეიცავს `availability`-ს: `available`, როცა ჩაწერილი ნაბიჯები არსებობს, მაშინაც კი, თუ ფილტრები არაფერს ემთხვევა; `processing`, როცა ბილდი ჯერ კიდევ მუშავდება და ნაბიჯები ჯერ არ არის; ან `unavailable`, როცა ნაბიჯები არ ჩაწერილა ან ვადა გაუვიდათ.

იგივე ოპერაციები ხელმისაწვდომია HTTP API-ზე `GET /api/projects/{account_handle}/{project_handle}/xcode/builds/{build_id}/steps`-ით და `GET /api/projects/{account_handle}/{project_handle}/xcode/builds/{build_id}/steps/{step_id}`-ით, იგივე ფილტრებით და პაგინაციით. ორივეს სჭირდება წვდომა ბილდის პროექტის წაკითხვისთვის.

ეს ინსტრუმენტები თანდათანობით ხდება ხელმისაწვდომი და აბრუნებენ მონაცემებს მხოლოდ იმ პროექტებისთვის, სადაც ისინი ჩართულია; სხვა პროექტებისთვის ისინი აბრუნებენ შეცდომას ცარიელი შედეგის ნაცვლად. ტიპი ხელმისაწვდომია მხოლოდ იმ პროექტებისთვის, რომლებიც იყენებენ შესაბამის ბილდის ხელსაწყოთა ჯაჭვს. ინსტრუმენტები იღებენ შემოსაზღვრულ `start_at`/`end_at` ფილტრებს, `environment` (`any`, `ci`, ან `local`) და ზუსტ `branch`. `list_build_entities` იღებს `q`-ს; `list_build_entity_history` მხარს უჭერს გამჭვირვალე `after`/`before` კურსორებს. უცნობი დროის ან კეშის დაკვირვებები რჩება მიუწვდომლად, ნულის ან გამოტოვების ნაცვლად. ისტორია მიუთითებს ჩაწერილ მშობელზე და ნატიურ შესრულებაზე დეტალური ანალიზისთვის არსებული გაშვების ინსტრუმენტების გამოყენებით.

`get_build_entity` მეტრიკები მოიცავს `duration_samples`-ს, დაკვირვებების რაოდენობას ჩაწერილი დროით: ნამდვილი ნულოვანი ხანგრძლივობები ითვლება, გამოტოვებული დრო — არა. ეს რაოდენობა შეიძლება იყოს დაკვირვებების რაოდენობაზე ნაკლები; მიუწვდომელი ხანგრძლივობის სტატისტიკა რჩება null-ად.

Xcode მოდულების ხანგრძლივობა მოდის ბილდის ჟურნალებში გაზომილი სამიზნე კომპილაციებიდან. მოდულის კეშის ამოხსნები და სამიზნეები კომპილაციის გარეშე არ უმატებენ ხანგრძლივობის ნიმუშებს. კომპილაციის დაკვირვებები მიუთითებენ Xcode ბილდზე; კეშის მოვლენები მიუთითებენ გენერაციის ან კეშის ბრძანებაზე.

Bazel ქმედებები იდენტიფიცირდება სამიზნის იარლიყით, მნიშვნელობით და კონფიგურირებული პირველადი გამოტანით, რაც ინარჩუნებს ცალკეულ ქმედებებსა და კონფიგურაციებს განცალკევებულად, შეყვანაზე დამოკიდებული კეშის დაიჯესტების გარეშე. ისტორია აღრიცხავს BEP-ით მოხსენებულ შესრულებებს, არა კეშის ძიებებს ან ტრეისის პროფილის ფაზებს. სრული შესრულების დაფარვა მოითხოვს `--build_event_publish_all_actions`-ს; არტეფაქტების მიწოდება საუკეთესო ძალისხმევით ხდება, ამიტომ გამოტოვებული დაკვირვებები არ არის იმის მტკიცებულება, რომ სამუშაო არ შესრულებულა. ძველი Kura პაკეტები სტაბილური იდენტობის ან შესრულების დაწყების გარეშე რჩება მიღებულად, მაგრამ არაინდექსირებულად. დასრულების დროის გაზომვების არარსებობა რჩება მიუწვდომლად და ნამდვილი ნულოვანი ხანგრძლივობები ითვლება.

Mix მოდულების ხანგრძლივობა ზომავს შემცველი ფაილის კომპილაციას, არა დამოუკიდებლად გაზომილ მოდულურ სამუშაოს. Once ქმედებები იყენებენ გამოცხადებულ სამიზნე/შესაძლებლობა/ინდექს სლოტებს, როდესაც კლიენტმა მოახსენა სამიზნე ასახვები; დიაგნოსტიკური იარლიყები მხოლოდ არ არის სტაბილური იდენტობები. არსებული კლიენტები და გაშვების დონის ინსტრუმენტები რჩებიან მხარდაჭერილად უცვლელად.

Cargo ყუთები დაჯგუფებულია ზუსტად ჩაწერილი ყუთის ფესვით, სახელით და ტიპით. Checkout-ბილიკის ცვლილებებმა შეიძლება გაყოს ისტორიები, ხოლო ბილდის პროფილები, ფუნქციები და სამიზნე ტრიპლეტები არ განასხვავდება. ისტორია ზომავს rustc გამოძახებებს, არა ფაილის დონის სამუშაოს ან კეშის მოხვედრებს; არარსებული სამუშაოები არ ამყარებენ წაშლებს ან სრულ სამუშაო სივრცის ინვენტარს.

ანალიტიკის კითხვებს აქვს შემოსაზღვრული მეხსიერება და შესრულების დრო. თუ მოთხოვნა აღემატება ამ ლიმიტებს, ინსტრუმენტი აბრუნებს შეცდომას ცარიელი შედეგის გამოგონების ნაცვლად.

ახალი დაკვირვებები ინდექსირდება განლაგების შემდეგ; ეს ფუნქცია არ ავსებს არსებულ გაშვების ტელემეტრიას. იდენტობის მეტამონაცემები ინარჩუნებს სიცოცხლეს ინდივიდუალურ დაკვირვებებზე უფრო დიდხანს <.localized_link href="/guides/server/data-retention">მონაცემთა შენახვის პოლიტიკის</.localized_link> შესაბამისად.

### მოვლენები

კლიენტები, რომლებიც იყენებენ უმდგომარეობო `2026-07-28` Model Context Protocol-ის სიცოცხლის ციკლს, შეუძლიათ გამოიძახონ `events/list` მოვლენებისა და მათი შინაარსის სქემების აღმოსაჩენად:

| მოვლენა | როდის იგზავნება | გამოწერის ფილტრი |
|-------|-----------------|---------------------|
| `test_case.marked_flaky` | სატესტო შემთხვევა იცვლება არაფლაკიდან ფლაკურზე. | `account_handle`, `project_handle` |
| `build.failed` | ლოკალური ან უწყვეტი ინტეგრაციის Xcode, Gradle ან Bazel ბილდი სრულდება შეცდომით. | `account_handle`, `project_handle` |
| `test_run.failed` | ლოკალური ან უწყვეტი ინტეგრაციის ტესტების გაშვება სრულდება შეცდომით, შერწყმული დაყოფილი გაშვების ან მიტოვებული გაშვების ჩათვლით. | `account_handle`, `project_handle` |
| `ci_job.failed` | Tuist-ის რანერის სამუშაო სრულდება შეცდომით. | `account_handle` |

გამოსაწერად, კლიენტი იძახებს `events/subscribe`-ს მოვლენის სახელით, ზემოთ ჩამოთვლილი ხელმძღვანელებით `arguments`-ში და `webhook` მიწოდებით, რომელიც შეიცავს `https://` callback URL-ს და `whsec_` ხელმოწერის საიდუმლოს. პროექტის მოვლენები მოითხოვს ანგარიშის წევრობას და შესაბამისი ტესტის ან ბილდის მონაცემებზე წვდომას; რანერის სამუშაოს მოვლენები მოითხოვს ანგარიშის წევრობას და რანერზე წვდომას. მოთხოვნილმა [`auth.md`](https://workos.com/auth-md) წვდომის ტოკენებმა, მოთხოვნილმა ანგარიშის ტოკენებმა და ბრაუზერის ავტორიზაციის გრანტებმა შეუძლიათ შექმნან გამოწერები; მიწოდება ჩერდება, როდესაც შესაბამისი სერთიფიკატი აღარ არის აქტიური. თითოეულ მომხმარებელს შეუძლია ჰქონდეს მაქსიმუმ 25 აქტიური გამოწერა. Tuist აგზავნის ვერიფიკაციის გამოწვევას callback-ზე გამოწერის შენახვამდე. callback-მა უნდა დააბრუნოს ობიექტი, რომელიც შეიცავს იგივე `challenge` მნიშვნელობას. გამოწერა ძალაშია შვიდი დღის განმავლობაში ნაგულისხმევად, შეიძლება განახლდეს ხელახლა გამოწერით და ჩერდება მიწოდება, როდესაც მომხმარებლის წვდომა ან სერთიფიკატი იხსნება. არასავალდებულო `ttlMs` შეზღუდულია ერთ საათსა და 30 დღეს შორის. Tuist ახდენს დროზე ამოწურული callback-ის ხელახლა ცდას და აუქმებს მას მინიმუმ სამი თანმიმდევრული დროის ამოწურვის შემდეგ, რომლებიც მოიცავს ხუთ წუთს; გამოიწერეთ ხელახლა callback-ის აღდგენის შემდეგ.

როდესაც მოვლენა ხდება, Tuist აგზავნის მის რესურსის იდენტიფიკატორს და დაფის URL-ს callback-ზე. ბილდისა და ტესტების გაშვების შეცდომები ასევე მოიცავს `is_ci`-ს და `git_branch`-ს, რათა კლიენტებმა შეძლონ ლოკალური შეცდომების იგნორირება ან შტოს მიხედვით ფილტრაცია. ბილდის მოვლენები მოიცავს `build_system`-ს; რანერის სამუშაოს მოვლენები მოიცავს როგორც `workflow_job_id`-ს, ასევე `workflow_run_id`-ს. მოთხოვნა მოიცავს გამოწერის იდენტიფიკატორს და [Standard Webhooks](https://www.standardwebhooks.com/) ხელმოწერის ჰედერებს, რათა კლიენტმა შეძლოს მისი წარმომავლობის ვერიფიკაცია. Tuist ახდენს შეცდომით დასრულებული მიწოდებების ხელახლა ცდას, ამიტომ კლიენტებმა უნდა გამოიყენონ სტაბილური `eventId` დუბლიკატების გასაფილტრად. შინაარსი არ მოიცავს ტესტების სახელებს, ლოგებს და შეცდომის შეტყობინებებს; კლიენტს შეუძლია მიიღოს ეს დეტალები ზემოთ ჩამოთვლილი ინსტრუმენტების მეშვეობით და გადაწყვიტოს, შეატყობინოს თუ არა გუნდს ან დაიწყოს დებაგინგი. კლიენტებმა შეუძლიათ შეაჩერონ მიწოდება `events/unsubscribe`-ით.

| `integrate_gradle_project` | გეხმარებათ Tuist-ის ინტეგრაციაში არსებულ Gradle პროექტში. მოიცავს ცალკეულ ინსტრუმენტს და Gradle-ის ავტორიზაციას, ანგარიშის აღმოჩენას, პროექტის შექმნას, დისტანციური ქეშის პოლიტიკას, ბილდის ინსაიტებს და უკან წაკითხვის ვერიფიკაციას. |
| `integrate_bazel_project` | გეხმარებათ Bazel პროექტის შექმნაში ან შერჩევაში, ბრძანების ხაზის ავტორიზაციაში, დისტანციური ქეშისა და ბილდის ინსაიტების კონფიგურაციაში და ინტეგრაციის ვერიფიკაციაში Tuist-ის ბილდის მონაცემების მეშვეობით. |
| `integrate_xcode_project` | გეხმარებათ Tuist-ის ინტეგრაციაში არსებულ Xcode პროექტში. მხარდაჭერილია Xcode ქეში, ბილდის ინსაიტები, ტესტების ინსაიტები და ტესტების შარდინგი. |
| `ask_tuist` | პასუხობს Tuist-ის კითხვას საჯარო მასალების გამოყენებით კონტექსტისთვის და ფოკუსირებული იმპლემენტაციისა და ტესტების მტკიცებულებებით, როგორც მიმდინარე ქცევის ჭეშმარიტების წყაროთი. საჭიროებს `question`-ს და ასახელებს რევიზიით მიმაგრებულ მტკიცებულებას. |

პროექტის მონაცემების მოთხოვნები იღებენ `account_handle`-ს და `project_handle`-ს, რათა გამოკვლევა შეიზღუდოს კონკრეტული პროექტით. შედარების მოთხოვნები ასევე იღებენ `base` და `head` არგუმენტებს, რათა მიუთითონ შესადარებელი ორი ელემენტი (ID-ით, დაფის URL-ით ან შტოს სახელით). `ask_tuist` იღებს `question`-ს პროექტის პარამეტრების ნაცვლად. `integrate_gradle_project` ასევე იღებს `features`-ს, Gradle ინტეგრაციების გამოყოფილ სიას გამოყენებისთვის: `remote_cache`, `build_insights`, `test_insights`, `flaky_tests` და `test_sharding`. `integrate_bazel_project` იღებს არასავალდებულო `server_url`-ს თვითმასპინძელი ან ლოკალური ინსტალაციებისთვის. `integrate_xcode_project` იღებს `features`-ს `xcode_cache`, `build_insights`, `test_insights` და `test_sharding`-ით.

#### Gradle ინტეგრაციის მოთხოვნის ფუნქციები

`integrate_gradle_project` მოთხოვნა და `get_gradle_integration_guide` ინსტრუმენტი აღწერენ სრულ დაყენების სამუშაო ნაკადს. ინსტრუმენტს ასევე მიუთითებს სერვერის ინიციალიზაციის ინსტრუქციები, რაც მას აღმოჩენადს ხდის აგენტებისთვის, რომლებიც არ ჩამოთვლიან მოთხოვნებს.

| ფუნქცია | რას აკონფიგურირებს აგენტი |
|---------|---------------------------|
| `remote_cache` | ააქტიურებს Gradle-ის ბილდის ქეშს, აკონფიგურირებს Tuist-ის დისტანციური ქეშის ატვირთვის პოლიტიკას და გირჩევთ ატვირთვას მხოლოდ უწყვეტი ინტეგრაციის რანერებიდან ლოკალური მხოლოდ-წაკითხვადი გამოყენებით. |
| `build_insights` | აყენებს Tuist Gradle პლაგინს და საჭიროების შემთხვევაში აკონფიგურირებს ბილდის ანალიტიკის ატვირთვის ქცევას. |
| `test_insights` | აყენებს Tuist Gradle პლაგინს, რათა Gradle `Test` ამოცანის შედეგები ავტომატურად აიტვირთოს. |
| `flaky_tests` | გეხმარებათ არასტაბილური ტესტების აღმოჩენის დაყენებაში, Gradle Test Retry პლაგინის არასავალდებულო გამოყენებაში და ტესტების კარანტინის კონფიგურაციაში. |
| `test_sharding` | ამატებს უწყვეტი ინტეგრაციის სამუშაო ნაკადს `tuistPrepareTestShards`-ისთვის, შარდების მატრიცის გენერაციისთვის და `TUIST_SHARD_INDEX`-ზე დაფუძნებული ტესტების შესრულებისთვის. |

როდესაც `features` გამოტოვებულია, მოთხოვნა სთხოვს აგენტს გაარკვიოს, თუ რომელი ინტეგრაციები სურს მომხმარებელს, ან მოთხოვნიდან გამოიყვანოს ყველაზე მცირე სასარგებლო ნაკრები Gradle პროექტის რედაქტირებამდე.

#### Xcode ინტეგრაციის მოთხოვნის ფუნქციები

`integrate_xcode_project` მოთხოვნა აღწერს ყველა Xcode ინტეგრაციას, რომელსაც Tuist მხარს უჭერს:

| ფუნქცია | რას აკონფიგურირებს აგენტი |
|---------|---------------------------|
| `xcode_cache` | აკონფიგურირებს `tuist setup cache`-ს, გენერირებული პროექტის ქეშის პარამეტრებს, Xcode ქეშის ხელით ბილდის პარამეტრებს და ატვირთვის პოლიტიკას, რომელიც შეზღუდულია უწყვეტი ინტეგრაციის რანერებით. |
| `build_insights` | აკონფიგურირებს `tuist inspect build`-ს, `tuist xcodebuild`-ს, `-resultBundlePath`-ს და არასავალდებულო მანქანურ მეტრიკებს `tuist setup insights`-ის მეშვეობით. |
| `test_insights` | აკონფიგურირებს `tuist inspect test`-ს, სქემის ტესტის post-actions-ებს და შედეგების ბანდლის გენერაციას უწყვეტი ინტეგრაციის ტესტების გაშვებებისთვის. |
| `test_sharding` | ამატებს Xcode-ის ან გენერირებული პროექტის შარდების დაგეგმვისა და შარდების შესრულების სამუშაო ნაკადს `TUIST_SHARD_INDEX`-ით. |

როდესაც `features` გამოტოვებულია, მოთხოვნა სთხოვს აგენტს გაარკვიოს, თუ რომელი ინტეგრაციები სურს მომხმარებელს, ან მოთხოვნიდან გამოიყვანოს ყველაზე მცირე სასარგებლო ნაკრები Xcode პროექტის რედაქტირებამდე.
