# Model Context Protocol

[Model Context Protocol (MCP)](https://modelcontextprotocol.io/docs/getting-started/intro) არის ღია სტანდარტი, რომელიც საშუალებას აძლევს ხელოვნური ინტელექტის აგენტებს ურთიერთქმედება გარე სერვისებთან და მონაცემთა წყაროებთან. ის უზრუნველყოფს [Claude](https://claude.ai/), [Claude Code](https://docs.anthropic.com/en/docs/claude-code), [Codex](https://developers.openai.com/codex/)-ისა და რედაქტორების, როგორიცაა [Zed](https://zed.dev), [Cursor](https://www.cursor.com) ან [Visual Studio Code](https://code.visualstudio.com), თავსებადობას Tuist-თან.

Tuist მასპინძლობს Model Context Protocol-ის სერვერულ წერტილს მისამართზე `https://tuist.dev/mcp`. მასზე თქვენი კლიენტის მიერთებით, აგენტებს შეუძლიათ წვდომა თქვენს Tuist პროექტის მონაცემებზე, მათ შორის ტესტების ანალიტიკაზე, არასტაბილური ტესტების ანალიზზე და სხვა. უმეტესი ინსტრუმენტი მხოლოდ წაკითხვადია და შემოიფარგლება ავტორიზებული Tuist პროექტის მონაცემებით. ანგარიშის დაყენების ინსტრუმენტებს შეუძლიათ ანგარიშების ჩამოთვლა, ორგანიზაციების შექმნა, პროექტების შექმნა და არსებული მომხმარებლების დამატება ორგანიზაციებში, როდესაც ავტორიზებულ მომხმარებელს აქვს საჭირო ნებართვები. ყოველი ინსტრუმენტი აცხადებს ანოტაციებს, რომლებიც მიუთითებს, არის თუ არა ის მხოლოდ წაკითხვადი, შეუძლია თუ არა გამოიწვიოს რთულად შექცევადი ცვლილება და შეუძლია თუ არა შეცვალოს საჯარო ინტერნეტის მდგომარეობა. ანგარიშის დაყენების ინსტრუმენტებს სჭირდებათ მომხმარებლის ავტორიზაცია. ისინი არ არის ხელმისაწვდომი პროექტის ტოკენებისთვის ან ჩვეულებრივი ანგარიშის ტოკენებისთვის. როდესაც მომხმარებელი ბრაუზერში ანიჭებს კლიენტს ნებართვას ან ითხოვს `auth.md` რეგისტრაციას, Tuist ასოცირებს ამ სერთიფიკატს მომხმარებელთან მხოლოდ Model Context Protocol-ის წერტილზე, რათა დაყენების ინსტრუმენტებმა შეძლონ მოთხოვნილი სამუშაო პროცესის დასრულება.

Tuist ახორციელებს [2026-07-28 პროტოკოლს](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http). მოთხოვნები უსესიოა: კლიენტები აგზავნიან თავიანთ პროტოკოლის მეტამონაცემებს ყოველ მოთხოვნასთან ერთად და შეუძლიათ პირდაპირ გამოიძახონ ინსტრუმენტები ინიციალიზაციის გარეშე. `server/discover` აბრუნებს სერვერის იდენტობას, შესაძლებლობებს, მხარდაჭერილ ვერსიებს და ინსტრუქციებს. არ არსებობს სესიის იდენტიფიკატორები ან დამოუკიდებელი მოვლენათა ნაკადები. კლიენტები, რომლებიც იყენებენ 2025-06-18 ან 2025-03-26 ინიციალიზაციის ნაკადს, კვლავ მხარდაჭერილია; ისინიც მუშაობენ სერვერის სესიების გარეშე.

## Model Context Protocol უნარების წინააღმდეგ

Model Context Protocol-ის ინსტრუმენტებსა და <.localized_link href="/guides/features/agentic-coding/skills">უნარებს</.localized_link> შორის შესაძლოა იყოს გადაკვეთა ფუნქციებში. ამჟამინდელი გადაკვეთის გათვალისწინებით, აირჩიეთ ერთი მიდგომა თითოეული სამუშაო პროცესისთვის და გამოიყენეთ ის თანმიმდევრულად, ნაცვლად ორივეს ერთ ნაკადში შერევისა.

კლიენტებისთვის, რომლებიც მხარს უჭერენ პლაგინების ინსტალაციას, გამოიყენეთ <.localized_link href="/guides/features/agentic-coding/plugins">Tuist პლაგინები</.localized_link> ორივეს ერთად ინსტალაციისთვის.

## კონფიგურაცია

დაამატეთ `https://tuist.dev/mcp` როგორც დისტანციური Model Context Protocol სერვერი თქვენს კლიენტში. სერვერის ინიციალიზაციის ინსტრუქციები და საჯარო სერვერის ბარათი აღწერს OAuth 2.0-ს დინამიური კლიენტის რეგისტრაციით და სტანდარტული ბრაუზერის ავტორიზაციის ნაკადით პირდაპირ, აგენტებისგან გარე ავტორიზაციის დოკუმენტების მოთხოვნის ან მათზე გადასვლის გარეშე. ეს სერვერის მასშტაბის ინსტრუქციები ინარჩუნებს სამუშაო პროცესის მითითებებს ზოგადს: ინსტრუმენტის ავტორიზაცია არ ავტორიზებს ადგილობრივ ბრძანების ხაზის ინსტრუმენტებს ან აგების სისტემის ინტეგრაციებს და აგენტებმა უნდა გადაამოწმონ მოთხოვნილი ცვლილებები შესაბამისი Tuist ინსტრუმენტების მეშვეობით. აგების სისტემის სპეციფიკური დაყენება და ავტორიზაციის შემოწმებები დოკუმენტირებულია ინტეგრაციის სახელმძღვანელოებში და მოთხოვნებში. Tuist კვლავ აცხადებს როგორც [Open Authorization](https://oauth.net/2/) აღმოჩენის მეტამონაცემებს, ასევე მიმდინარე [auth.md პროტოკოლს](https://workos.com/auth-md) მისამართზე `https://tuist.dev/auth.md` ცალ-ცალკე.

წერტილი იღებს უსესიო `2026-07-28` Model Context Protocol მოთხოვნის სიცოცხლის ციკლს, მათ შორის `server/discover`-ს, ძველ სესიაზე დაფუძნებულ ციკლთან ერთად. არსებულმა კლიენტებმა შეიძლება განაგრძონ თავიანთი მიმდინარე მიერთების მეთოდის გამოყენება.

კლიენტებს, რომლებიც მხარს უჭერენ Model Context Protocol-ის მოვლენებს, შეუძლიათ გამოიწერონ პროექტის მოვლენები. იხილეთ [მოვლენები](#events) ხელმისაწვდომი მოვლენებისა და მიწოდების მოთხოვნებისთვის.

კლიენტებს, რომლებიც უკვე მხარს უჭერენ დისტანციურ ბრაუზერის ავტორიზაციას, შეუძლიათ განაგრძონ ავტორიზაცია ბრაუზერში. კლიენტებსა და აგენტებს, რომლებიც მხარს უჭერენ `auth.md`-ს, შეუძლიათ ანონიმურად დარეგისტრირება, სანდო პროვაიდერის იდენტობის დამტკიცების წარდგენა ან სერვისით ავტორიზებული ელფოსტის მოთხოვნის დაწყება. რეგისტრაცია აბრუნებს Tuist-ით ხელმოწერილ იდენტობის დამტკიცებას, რომელსაც აგენტი ცვლის სტანდარტულ ტოკენის წერტილზე ერთსაათიანი წვდომის ტოკენისთვის. Tuist აქვეყნებს თავის საჯარო ხელმოწერის გასაღებს და მხარს უჭერს სტანდარტულ ტოკენის გაუქმებასა და პროვაიდერის უსაფრთხოების მოვლენათა მიწოდებას.

არაავტორიზებულმა აგენტმა უნდა წაიკითხოს `WWW-Authenticate` ჰედერი, რომელიც დაბრუნდა Model Context Protocol-ის წერტილისგან, მიიღოს დაცული რესურსის მეტამონაცემები, მიიღოს ავტორიზაციის სერვერის მეტამონაცემები და მიჰყვეს მის `agent_auth.skill` URL-ს. Tuist ასევე აბრუნებს იმავე ადგილობრივ `auth_md` URL-ს არაავტორიზებული პასუხის სხეულში, რათა ენის მოდელზე დაფუძნებულმა კლიენტებმა შეძლონ ნაკადის აღმოჩენა ნატიური კლიენტის ინტეგრაციაზე დაყრდნობის გარეშე. განლაგების ადგილობრივი დოკუმენტი არის ჭეშმარიტობის წყარო წერტილის სახელების, მოთხოვნის სხეულების, მოთხოვნის გამოკითხვისა და დამტკიცების გაცვლისთვის.

სანამ აგენტი დაიწყებს ელფოსტის მოთხოვნას, მან უნდა სთხოვოს მომხმარებელს დაადასტუროს ელფოსტის მისამართი მათი Tuist ანგარიშისთვის. მან არ უნდა გამოიტანოს ეს მისამართი პროვაიდერის პროფილიდან, Git კონფიგურაციიდან, გარემოს ცვლადიდან ან სესიის მეტამონაცემებიდან.

წერტილი იყენებს `mcp` სკოპის ჯგუფს. ანონიმურმა წინასწარ მოთხოვნის სერთიფიკატმა შეიძლება აღმოაჩინოს შესაძლებლობები და წაიკითხოს საჯარო ინტეგრაციის მითითებები, მაგრამ ის არ განიხილება როგორც შესული მომხმარებელი. ბრაუზერის ავტორიზაციის ან მოთხოვნის შემდეგ, სერთიფიკატი არის მომხმარებლის სკოპის და ყოველი ინსტრუმენტი იყენებს იმავე ავტორიზაციის შემოწმებებს, რასაც დაშბორდი. იხილეთ <.localized_link href="/guides/server/authentication#scope-groups">სკოპის ჯგუფების დოკუმენტაცია</.localized_link> დეტალებისთვის.

ინსტრუმენტები წყდებიან პროექტებზე, რომლებსაც ავტორიზებულ მომხმარებელს უკვე აქვს წვდომა. Xcode-ისა და Gradle-ის აგების ინსტრუმენტები იღებენ აგების UUID-ს ან დაშბორდის URL-ს. UUID-მ უნდა მოახდინოს ზუსტად ერთი პროექტის იდენტიფიცირება; თუ ის ჩნდება რამდენიმე პროექტში, ინსტრუმენტი აბრუნებს „არ არის ნაპოვნი“-ს, ნაცვლად სხვა პროექტის ანგარიშის არჩევისა. პროექტის სკოპის დაშბორდისა და API-ს წაკითხვები კვლავ ხელმისაწვდომია. მოხსენებული მოქმედის იდენტიფიკატორები არის დაუდასტურებელი ეტიკეტები, არა სერთიფიკატები ან დამატებითი წვდომის უფლებები.

აგების სიისა და დეტალური ინფორმაციის ინსტრუმენტები აჩვენებენ არასავალდებულო `tuist_version` მეტამონაცემებს: Xcode-ისა და Cargo-სთვის — Tuist CLI, Gradle-ისთვის — Tuist Gradle პლაგინი, ხოლო Mix-ისთვის — `tuist_ex` ბიბლიოთეკა. Xcode ასევე აჩვენებს `tuist_generation_version`-ს თავის დაკავშირებული პროექტის გენერაციის მოვლენიდან, რომელიც შეიძლება განსხვავდებოდეს ატვირთული CLI-ისგან. გამოტოვებული მნიშვნელობები არის null და არ გამოიტანება სერვერიდან ან სხვა ანგარიშიდან. ## აგების სისტემის ინტეგრაციები იყენებენ ორ სერთიფიკატს

Model Context Protocol ინსტრუმენტებისთვის გამოყენებული სერთიფიკატი არ ავტორიზებს Gradle პლაგინს ან Bazel-ის დისტანციურ სერვისებს. სანამ აგენტი შეცვლის ან შეამოწმებს Gradle ან Bazel ინტეგრაციას, მან უნდა გაუშვას:

```bash
tuist auth whoami --url https://tuist.dev
```

თუ ეს ბრძანება არ არის ავტორიზებული, აგენტმა უნდა შეწყვიტოს მუშაობა და სთხოვოს მომხმარებელს გაუშვას:

```bash
tuist auth login --url https://tuist.dev
```

ლოკალური ან თვითმასპინძელი განლაგებისთვის, შეცვალეთ URL ორივე ბრძანებაში და `tuist.toml`-ში. შეინახეთ ჰოსტის სახელის წერა იდენტური ყველგან. მაგალითად, `localhost` და `127.0.0.1` იყენებენ ცალკე შენახულ სერთიფიკატებს.

შემდეგი ინსტრუმენტები ხელმისაწვდომია Tuist Model Context Protocol სერვერის მეშვეობით:

Xcode მოდულის ხანგრძლივობები მოდის ბილდის ჟურნალებში გაზომილი სამიზნე კომპილაციებიდან. მოდულის ქეშის ამოხსნები და სამიზნეები კომპილაციის სამუშაოს გარეშე არ მონაწილეობენ ხანგრძლივობის შერჩევებში. კომპილაციის დაკვირვებები მიუთითებენ Xcode ბილდზე; ქეშის მოვლენები მიუთითებენ გენერაციის ან ქეშის ბრძანებაზე.

Bazel მოქმედებები იდენტიფიცირდება სამიზნის ლეიბლით, მნემონიკით და კონფიგურირებული ძირითადი გამომავალით, რაც ინარჩუნებს ცალკეულ მოქმედებებსა და კონფიგურაციებს განცალკევებულად, შეყვანაზე დამოკიდებული ქეშის დაიჯესტების გარეშე. ისტორია აღრიცხავს BEP-ით შეტყობინებულ შესრულებებს, არა ქეშის ძიებებს ან ტრეისის პროფილის ფაზებს. სრული შესრულების დაფარვა მოითხოვს `--build_event_publish_all_actions`-ს; არტიფაქტების მიწოდება საუკეთესო ძალისხმევით ხდება, ამიტომ გამოტოვებული დაკვირვებები არ არის იმის მტკიცებულება, რომ სამუშაო არ შესრულებულა. უფრო ძველი Kura პეილოადები სტაბილური იდენტობის ან შესრულების დაწყების გარეშე რჩება მიღებული, მაგრამ არაინდექსირებული. დასრულების დროის გაზომვების არარსებობა რჩება მიუწვდომელი და ნამდვილი ნულოვანი ხანგრძლივობები ითვლება.

Mix მოდულის ხანგრძლივობები ზომავენ შემცველი ფაილის კომპილაციას, არა დამოუკიდებლად გაზომილ მოდულის სამუშაოს. Once მოქმედებები იყენებენ გამოცხადებულ სამიზნე/შესაძლებლობა/ინდექს სლოტებს, როდესაც კლიენტმა შეატყობინა სამიზნე ასოციაციები; მხოლოდ დიაგნოსტიკური ლეიბლები არ არის სტაბილური იდენტობები. არსებული კლიენტები და გაშვების დონის ინსტრუმენტები რჩება უცვლელად მხარდაჭერილი.

Cargo კრეიტები დაჯგუფებულია ზუსტად ჩაწერილი კრეიტის ფესვის, სახელისა და სახის მიხედვით. Checkout-ბილიკის ცვლილებებმა შეიძლება გაყოს ისტორიები, ხოლო ბილდის პროფილები, ფუნქციები და სამიზნე ტრიპლეტები არ განიმარჩევა. ისტორია ზომავს rustc გამოძახებებს, არა ფაილის დონის სამუშაოს ან ქეშის მოხვედრებს; არარსებული სამუშაოები არ ამყარებენ წაშლებას ან სრულ სამუშაო სივრცის ინვენტარს.

ანალიტიკის წაკითხვებს აქვს შემოსაზღვრული მეხსიერება და შესრულების დრო. თუ მოთხოვნა აღემატება ამ ლიმიტებს, ინსტრუმენტი აბრუნებს შეცდომას ცარიელი შედეგის გამოგონების ნაცვლად.

### მოვლენები

კლიენტები, რომლებიც იყენებენ უმდგომარეობო `2026-07-28` Model Context Protocol სიცოცხლის ციკლს, შეუძლიათ გამოიძახონ `events/list` მოვლენებისა და მათი ტვირთის სქემების აღმოსაჩენად:

| მოვლენა | როდის იგზავნება | გამოწერის ფილტრი |
|-------|-----------------|---------------------|
| `test_case.marked_flaky` | სატესტო შემთხვევა იცვლება არაარასტაბილურიდან არასტაბილურზე. | `account_handle`, `project_handle` |
| `build.failed` | ლოკალური ან უწყვეტი ინტეგრაციის Xcode, Gradle ან Bazel ბილდი სრულდება შეცდომით. | `account_handle`, `project_handle` |
| `test_run.failed` | ლოკალური ან უწყვეტი ინტეგრაციის ტესტების გაშვება სრულდება შეცდომით, შერწყმული დაყოფილი გაშვების ან მიტოვებული გაშვების ჩათვლით. | `account_handle`, `project_handle` |
| `ci_job.failed` | Tuist-ის გამშვების სამუშაო სრულდება შეცდომით. | `account_handle` |

გამოწერისთვის კლიენტი იძახებს `events/subscribe` მოვლენის სახელით, ზემოთ ჩამოთვლილი ხელმისაწვდომობებით `arguments`-ში და `webhook` მიწოდებით, რომელიც შეიცავს `https://` callback URL-ს და `whsec_` ხელმოწერის საიდუმლოს. პროექტის მოვლენები მოითხოვენ ანგარიშის წევრობას და შესაბამის ტესტის ან ბილდის მონაცემებზე წვდომას; გამშვების სამუშაოს მოვლენები მოითხოვენ ანგარიშის წევრობას და გამშვებზე წვდომას. დადასტურებულმა [`auth.md`](https://workos.com/auth-md) წვდომის ტოკენებმა, დადასტურებულმა ანგარიშის ტოკენებმა და ბრაუზერის ავტორიზაციის გრანტებმა შეუძლიათ შექმნან გამოწერები; მიწოდება ჩერდება, როდესაც შესაბამისი სერთიფიკატი აღარ არის აქტიური. თითოეულ მომხმარებელს შეუძლია შეინარჩუნოს 25 აქტიური გამოწერა. Tuist აგზავნის ვერიფიკაციის გამოწვევას callback-ზე გამოწერის შენახვამდე. callback-მა უნდა დააბრუნოს ობიექტი, რომელიც შეიცავს იგივე `challenge` მნიშვნელობას. გამოწერა ძალაშია შვიდი დღის განმავლობაში ნაგულისხმევად, შეიძლება განახლდეს ხელახლა გამოწერით და ჩერდება მიწოდება, როდესაც მომხმარებლის წვდომა ან სერთიფიკატი იხსნება. არასავალდებულო `ttlMs` შეზღუდულია ერთ საათსა და 30 დღეს შორის. Tuist ცდის დროზე ამოწურულ callback-ს და აუქმებს მას სამი თანმიმდევრული დროის ამოწურვის შემდეგ, რომლებიც ხუთ წუთს ფარავს; ხელახლა გამოიწერეთ callback-ის აღდგენის შემდეგ.

როდესაც მოვლენა ხდება, Tuist აგზავნის მის რესურსის იდენტიფიკატორს და დაფის URL-ს callback-ზე. ბილდისა და ტესტების გაშვების შეცდომები ასევე შეიცავს `is_ci`-ს და `git_branch`-ს, რათა კლიენტებმა შეძლონ ლოკალური შეცდომების იგნორირება ან ფილტრაცია ტოტის მიხედვით. ბილდის მოვლენები შეიცავს `build_system`-ს; გამშვების სამუშაოს მოვლენები შეიცავს როგორც `workflow_job_id`-ს, ისე `workflow_run_id`-ს. მოთხოვნა შეიცავს გამოწერის იდენტიფიკატორს და [Standard Webhooks](https://www.standardwebhooks.com/) ხელმოწერის ჰედერებს, რათა კლიენტმა შეძლოს მისი წარმომავლობის ვერიფიკაცია. Tuist ცდის წარუმატებელ მიწოდებებს, ამიტომ კლიენტებმა უნდა გამოიყენონ სტაბილური `eventId` დუბლიკატების გასაფილტრად. ტვირთი არ შეიცავს ტესტების სახელებს, ჟურნალებს და შეცდომის შეტყობინებებს; კლიენტს შეუძლია მიიღოს ეს დეტალები ზემოთ ჩამოთვლილი ინსტრუმენტების მეშვეობით და გადაწყვიტოს, შეატყობინოს თუ არა გუნდს ან დაიწყოს დებაგინგი. კლიენტებს შეუძლიათ შეაჩერონ მიწოდება `events/unsubscribe`-ით.

| `remote_cache` | ააქტიურებს Gradle-ის ბილდის ქეშს, აკონფიგურირებს Tuist დისტანციური ქეშის ატვირთვის პოლიტიკას და რეკომენდაციას უწევს ატვირთვას მხოლოდ უწყვეტი ინტეგრაციის გამშვებებიდან ლოკალური მხოლოდ-კითხვის გამოყენებით. |
| `build_insights` | აყენებს Tuist Gradle პლაგინს და აკონფიგურირებს ბილდის ანალიტიკის ატვირთვის ქცევას საჭიროების შემთხვევაში. |
| `test_insights` | აყენებს Tuist Gradle პლაგინს, რათა Gradle `Test` ამოცანის შედეგები აიტვირთოს ავტომატურად. |
| `flaky_tests` | გიძღვებათ არასტაბილური ტესტების აღმოჩენის, არასავალდებულო Gradle Test Retry პლაგინის გამოყენებისა და ტესტის კარანტინის კონფიგურაციის მოწყობაში. |
| `test_sharding` | ამატებს უწყვეტი ინტეგრაციის სამუშაო ნაკადს `tuistPrepareTestShards`-თვის, ნაწილების მატრიცის გენერაციასა და `TUIST_SHARD_INDEX`-ზე დაფუძნებულ ტესტის შესრულებას. |

როდესაც `features` გამოტოვებულია, მოთხოვნა სთხოვს აგენტს გაარკვიოს, რომელი ინტეგრაციები სურს მომხმარებელს ან გამოიტანოს უმცირესი სასარგებლო ნაკრები მოთხოვნიდან Gradle პროექტის რედაქტირებამდე.

#### Xcode ინტეგრაციის მოთხოვნის ფუნქციები

`integrate_xcode_project` მოთხოვნა აღწერს ყველა Xcode ინტეგრაციას, რომელსაც Tuist მხარს უჭერს:

| ფუნქცია | რას აკონფიგურირებს აგენტი |
|---------|---------------------------|
| `xcode_cache` | აკონფიგურირებს `tuist setup cache`, გენერირებული პროექტის ქეშის პარამეტრებს, Xcode ქეშის ბილდის ხელით მითითებულ პარამეტრებს და ატვირთვის პოლიტიკას, რომელიც შემოიფარგლება მხოლოდ უწყვეტი ინტეგრაციის გამშვებებით. |
| `build_insights` | აკონფიგურირებს `tuist inspect build`-ს, `tuist xcodebuild`-ს, `-resultBundlePath`-ს და არასავალდებულო მანქანურ მეტრიკებს `tuist setup insights`-ის საშუალებით. |
| `test_insights` | აკონფიგურირებს `tuist inspect test`-ს, სქემის ტესტის post-actions-ებს და შედეგების ბანდლის გენერაციას უწყვეტი ინტეგრაციის ტესტების გაშვებისთვის. |
| `test_sharding` | ამატებს Xcode-ის ან გენერირებული პროექტის ნაწილების დაგეგმვისა და შესრულების სამუშაო ნაკადს `TUIST_SHARD_INDEX`-ის გამოყენებით. |

როდესაც `features` გამოტოვებულია, მოთხოვნა სთხოვს აგენტს გაარკვიოს, რომელი ინტეგრაციები სურს მომხმარებელს ან გამოიტანოს უმცირესი სასარგებლო ნაკრები მოთხოვნიდან Xcode პროექტის რედაქტირებამდე.
