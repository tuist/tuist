# Model Context Protocol

[Model Context Protocol (MCP)](https://modelcontextprotocol.io/docs/getting-started/intro) არის ღია სტანდარტი, რომელიც საშუალებას აძლევს ხელოვნური ინტელექტის აგენტებს ურთიერთქმედონ გარე სერვისებთან და მონაცემთა წყაროებთან. ის უზრუნველყოფს [Claude](https://claude.ai/), [Claude Code](https://docs.anthropic.com/en/docs/claude-code), [Codex](https://developers.openai.com/codex/) და რედაქტორების, როგორიცაა [Zed](https://zed.dev), [Cursor](https://www.cursor.com) ან [Visual Studio Code](https://code.visualstudio.com), თავსებადობას Tuist-თან.

Tuist განათავსებს Model Context Protocol-ის სერვერულ ენდპოინტს მისამართზე `https://tuist.dev/mcp`. კლიენტის ამ ენდპოინტთან მიერთებით, აგენტებს შეუძლიათ მიიღონ თქვენი Tuist პროექტის მონაცემები, მათ შორის ტესტების ანალიტიკა, არასტაბილური ტესტების ანალიზი და სხვა. ინსტრუმენტების უმეტესობა მხოლოდ წაკითხვადია და შეზღუდულია ავტორიზებული Tuist პროექტის მონაცემებზე. ანგარიშის მოწყობის ინსტრუმენტებს შეუძლიათ ჩამოთვალონ ანგარიშები, შექმნან ორგანიზაციები, შექმნან პროექტები და დაამატონ არსებული მომხმარებლები ორგანიზაციებში, როდესაც ავტორიზებულ მომხმარებელს აქვს შესაბამისი ნებართვები. ყოველი ინსტრუმენტი აქვეყნებს ანოტაციებს, რომლებიც მიუთითებს, არის თუ არა ის მხოლოდ წაკითხვადი, შეუძლია თუ არა გამოიწვიოს რთულად შექცევადი ცვლილება და შეუძლია თუ არა შეცვალოს საჯარო ინტერნეტის მდგომარეობა. ანგარიშის მოწყობის ინსტრუმენტებს სჭირდებათ მომხმარებლის ავტორიზაცია. ისინი არ არის ხელმისაწვდომი პროექტის ტოკენებისთვის ან ჩვეულებრივი ანგარიშის ტოკენებისთვის. როდესაც მომხმარებელი ავტორიზებს კლიენტს ბრაუზერში ან აცხადებს `auth.md` რეგისტრაციას, Tuist ასოცირებს იმ სერთიფიკატს მომხმარებელთან მხოლოდ Model Context Protocol-ის ენდპოინტზე, რათა მოწყობის ინსტრუმენტებმა შეასრულონ მოთხოვნილი სამუშაო პროცესი.

Tuist ახორციელებს [2026-07-28 პროტოკოლს](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http). მოთხოვნები უმდგომარეოა: კლიენტები აგზავნიან პროტოკოლის მეტამონაცემებს ყოველ მოთხოვნასთან ერთად და შეუძლიათ პირდაპირ გამოიძახონ ინსტრუმენტები ინიციალიზაციის გარეშე. `server/discover` აბრუნებს სერვერის იდენტიფიკატორს, შესაძლებლობებს, მხარდაჭერილ ვერსიებს და ინსტრუქციებს. არ არსებობს სესიის იდენტიფიკატორები ან დამოუკიდებელი მოვლენათა ნაკადები. 2025-06-18 ან 2025-03-26 ინიციალიზაციის ნაკადის გამომყენებელი კლიენტები კვლავ მხარდაჭერილია; ისინი ასევე მუშაობენ სერვერის სესიების გარეშე.

## Model Context Protocol უნარების წინააღმდეგ

Model Context Protocol-ის ინსტრუმენტებს და <.localized_link href="/guides/features/agentic-coding/skills">უნარებს</.localized_link> შეიძლება ჰქონდეთ გადაფარვა ფუნქციებში. არსებული გადაფარვის გათვალისწინებით, აირჩიეთ ერთი მიდგომა თითოეული სამუშაო პროცესისთვის და გამოიყენეთ ის თანმიმდევრულად, ნაცვლად ორივეს ერთ პროცესში შერევისა.

კლიენტებისთვის, რომლებიც მხარს უჭერენ პლაგინების ინსტალაციას, გამოიყენეთ <.localized_link href="/guides/features/agentic-coding/plugins">Tuist პლაგინები</.localized_link> ორივეს ერთად ინსტალაციისთვის.

## კონფიგურაცია

დაამატეთ `https://tuist.dev/mcp` როგორც დაშორებული Model Context Protocol სერვერი თქვენს კლიენტში. სერვერის ინიციალიზაციის ინსტრუქციები და საჯარო სერვერის ბარათი აღწერს OAuth 2.0-ს დინამიური კლიენტის რეგისტრაციით და სტანდარტული ბრაუზერის ავტორიზაციის ნაკადით პირდაპირ, აგენტებისგან გარე ავტორიზაციის დოკუმენტების მოთხოვნის ან მათი მიჸვების გარეშე. ეს სერვერის მასშტაბის ინსტრუქციები ინარჩუნებს სამუშაო პროცესის მითითებებს ზოგადს: ინსტრუმენტის ავტორიზაცია არ ავტორიზებს ადგილობრივ კომანდური ხაზის ინსტრუმენტებს ან აგების სისტემის ინტეგრაციებს და აგენტებმა უნდა შეამოწმონ მოთხოვნილი ცვლილებები შესაბამისი Tuist ინსტრუმენტების მეშვეობით. აგების სისტემის სპეციფიკური მოწყობა და ავტორიზაციის შემოწმებები დოკუმენტირებულია ინტეგრაციის სახელმძღვანელოებში და მოთხოვნებში. Tuist კვლავ აქვეყნებს როგორც [Open Authorization](https://oauth.net/2/)-ის აღმოჩენის მეტამონაცემებს, ასევე მიმდინარე [auth.md პროტოკოლს](https://workos.com/auth-md) მისამართზე `https://tuist.dev/auth.md` ცალ-ცალკე.

თუ თქვენი ერთ-ერთი ორგანიზაცია აიძულებს ერთიანი შესვლის გამოყენებას, კლიენტის ბრაუზერში ავტორიზაცია მოითხოვს იმ ორგანიზაციის მეშვეობით შესულ სესიას და Tuist საჭიროების შემთხვევაში ჯერ პროვაიდერთან გაგზავნით. იხილეთ <.localized_link href="/guides/integrations/authentication/sso#choose-an-enrollment-policy">ერთიანი შესვლა</.localized_link>.

ენდპოინტი იღებს უმდგომარეო `2026-07-28` Model Context Protocol-ის მოთხოვნის სიცოცხლის ციკლს, მათ შორის `server/discover`-ს, ძველ სესიაზე დაფუძნებულ ციკლთან ერთად. არსებულმა კლიენტებმა შეიძლება განაგრძონ მიმდინარე მიერთების მეთოდის გამოყენება.

კლიენტებს, რომლებიც მხარს უჭერენ Model Context Protocol-ის მოვლენებს, შეუძლიათ გამოიწერონ პროექტის მოვლენები. იხილეთ [მოვლენები](#events) ხელმისაწვდომი მოვლენებისა და მიწოდების მოთხოვნებისთვის.

კლიენტებს, რომლებიც უკვე მხარს უჭერენ დაშორებულ ბრაუზერის ავტორიზაციას, შეუძლიათ განაგრძონ ბრაუზერში ავტორიზაცია. კლიენტებს და აგენტებს, რომლებიც მხარს უჭერენ `auth.md`-ს, შეუძლიათ დარეგისტრირდნენ ანონიმურად, წარმოადგინონ სანდო პროვაიდერის იდენტიფიკატორის დამოწმება ან დაიწყონ სერვისით ავტორიზებული ელფოსტის პრეტენზია. რეგისტრაცია აბრუნებს Tuist-ით ხელმოწერილ იდენტიფიკატორის დამოწმებას, რომელსაც აგენტი ცვლის სტანდარტულ ტოკენის ენდპოინტზე ერთსაათიანი წვდომის ტოკენისთვის. Tuist აქვეყნებს თავის საჯარო ხელმოწერის გასაღებს და მხარს უჭერს სტანდარტულ ტოკენის გაუქმებას და პროვაიდერის უსაფრთხოების მოვლენების მიწოდებას.

არაავტორიზებულმა აგენტმა უნდა წაიკითხოს `WWW-Authenticate` ჰედერი, რომელიც დაბრუნდა Model Context Protocol-ის ენდპოინტის მიერ, მიიღოს დაცული რესურსის მეტამონაცემები, მიიღოს ავტორიზაციის სერვერის მეტამონაცემები და მიჸვეს მის `agent_auth.skill` URL-ს. Tuist ასევე აბრუნებს იმავე ადგილობრივ `auth_md` URL-ს არაავტორიზებული პასუხის სხეულში, რათა ენის მოდელზე დაფუძნებულმა კლიენტებმა შეძლონ ნაკადის აღმოჩენა ნატიური კლიენტის ინტეგრაციაზე დაყრდნობის გარეშე. განლაგების ადგილობრივი დოკუმენტი არის ჭეშმარიტების წყარო ენდპოინტის სახელების, მოთხოვნის სხეულების, პრეტენზიის გამოკითხვისა და დამოწმების გაცვლისთვის.

სანამ აგენტი დაიწყებს ელფოსტის პრეტენზიას, მან უნდა სთხოვოს მომხმარებელს დაადასტუროს ელფოსტის მისამართი მათი Tuist ანგარიშისთვის. მან არ უნდა გამოიტანოს ეს მისამართი პროვაიდერის პროფილიდან, Git კონფიგურაციიდან, გარემოს ცვლადიდან ან სესიის მეტამონაცემებიდან.

ენდპოინტი იყენებს `mcp` სკოპების ჯგუფს. ანონიმურმა პრეტენზიამდელმა სერთიფიკატმა შეიძლება აღმოაჩინოს შესაძლებლობები და წაიკითხოს საჯარო ინტეგრაციის მითითებები, მაგრამ ის არ განიხილება როგორც შესული მომხმარებელი. ბრაუზერის ავტორიზაციის ან პრეტენზიის შემდეგ, სერთიფიკატი არის მომხმარებლის სკოპირებული და თითოეული ინსტრუმენტი ატარებს იმავე ავტორიზაციის შემოწმებებს, რასაც დაშბორდი. დეტალებისთვის იხილეთ <.localized_link href="/guides/server/authentication#scope-groups">სკოპების ჯგუფების დოკუმენტაცია</.localized_link>.

ინსტრუმენტები გადაჰყავთ იმ პროექტებზე, რომელთა წაკითხვაც ავტორიზებულ მომხმარებელს უკვე შეუძლია. Xcode და Gradle აგების ინსტრუმენტები იღებენ აგების UUID-ს ან დაშბორდის URL-ს. UUID-მ უნდა განსაზღვროს ზუსტად ერთი პროექტი; თუ ის ჩნდება რამდენიმე პროექტში, ინსტრუმენტი აბრუნებს „არ არის ნაპოვნი“-ს, ნაცვლად სხვა პროექტის ანგარიშის არჩევისა. პროექტის სკოპირებული დაშბორდისა და API-ს წაკითხვები რჩება ხელმისაწვდომი. მოხსენებული აქტორის იდენტიფიკატორები არის შეუმოწმებელი ლეიბლები, არა სერთიფიკატები ან დამატებითი წვდომის უფლებები.

აგების სიისა და დეტალური ინფორმაციის ინსტრუმენტები აჩვენებენ არასავალდებულო `tuist_version` მეტამონაცემებს: Xcode-ისა და Cargo-სთვის — Tuist CLI, Gradle-ისთვის — Tuist Gradle პლაგინი, ხოლო Mix-ისთვის — `tuist_ex` ბიბლიოთეკა. Xcode ასევე აჩვენებს `tuist_generation_version`-ს მის მიერ დაკავშირებული პროექტის გენერაციის მოვლენიდან, რომელიც შეიძლება განსხვავდებოდეს ატვირთვის CLI-სგან. გამოტოვებული მონაცემები არის null, არა სერვერიდან ან სხვა ანგარიშიდან გამოყვანილი. Bazel იყენებს თავის არსებულ `bazel_version`-ს; Once გაშვების დეტალები აჩვენებს `once_version`-ს. ეს ველები აღწერენ მოხსენებულ ვერსიებს, არა დადასტურებულ იდენტობას ან სადენის კონტრაქტის ვერსიებს. REST აგების ენდპოინტები ასევე აჩვენებენ იმავე მეტამონაცემებს. არსებული ინტეგრაციისა და ფლაკი ტესტების უნარები არ არის დამოკიდებული ვერსიის ველებზე და არ საჭიროებს სამუშაო ნაკადის ცვლილებებს.

Tuist-ის ოპერატორები, რომლებიც იკვლევენ მომხმარებლის ანგარიშს, ამას აკეთებენ Tuist-ის შიდა ოპერაციული ინსტრუმენტებით, რომლებიც იწერენ ყოველ ზარს; ამ ენდპოინტთან პირდაპირი კავშირი არ იძლევა წვდომას მომხმარებლის საკუთარი წევრობის ფარგლებს გარეთ.

## WebMCP

ბრაუზერებში, რომლებიც მხარს უჭერენ [WebMCP](https://webmachinelearning.github.io/webmcp)-ს, Tuist-ის გვერდები აფიქსირებენ ინსტრუმენტებს `document.modelContext`-ით, ასე რომ ბრაუზერში ჩაშენებულ აგენტებს შეუძლიათ მათი გამოძახება დამატებითი კონფიგურაციის გარეშე. ზარები შესრულდება Tuist სერვერზე.

- **ვებსაიტისა და დოკუმენტაციის გვერდები** აფიქსირებენ დოკუმენტაციისა და წყაროს ინსტრუმენტებს (`search_tuist`, `search_tuist_code`, `list_tuist_files` და `read_tuist_file`). მათ არ სჭირდებათ თქვენგან სისტემაში შესვლა.
- **ანგარიშის დაშბორდის გვერდები**, როდესაც შესული ხართ, აფიქსირებენ Tuist-ის მხოლოდ წაკითხვად ინსტრუმენტებს ამ ანგარიშისთვის. თითოეული გვერდი აფიქსირებს მხოლოდ იმ ინსტრუმენტებს, რასაც ის აჩვენებს, პროექტის აგების სისტემის მიხედვით: Gradle პროექტის აგებების გვერდი იღებს Gradle აგების ინსტრუმენტებს, მისი ტესტების გვერდები — ტესტისა და დაფარვის ინსტრუმენტებს, ხოლო გამშვებების გვერდები — გამშვებების ინსტრუმენტებს. თქვენი პირადი ანგარიშის AI გამოწერების პარამეტრების გვერდი იღებს `list_ai_subscriptions`-ს, რომელიც პასუხობს მხოლოდ თქვენს საკუთარ ანგარიშზე. ყოველ გვერდს ასევე აქვს დოკუმენტაციის ინსტრუმენტები, `list_projects` და `get_project`. ინსტრუმენტები მუშაობენ შესული მომხმარებლის სახელით, ამიტომ ისინი მხოლოდ იმ მონაცემებთან ახდენენ წვდომას, რომელთა წაკითხვაც შეგიძლიათ დაშბორდზე, და მხოლოდ იმ ანგარიშთან, რომელსაც უყურებთ. როდესაც გადადიხართ სხვა გვერდზე ან ანგარიშზე, ინსტრუმენტები იცვლება იმ გვერდის ინსტრუმენტებით.

ინსტრუმენტები, რომლებიც ქმნიან, ცვლიან ან შლიან მონაცემებს, არ არის ხელმისაწვდომი WebMCP-ით, რადგან ბრაუზერის აგენტი იღებს ინსტრუმენტებს თქვენს მიერ მათი დამატების გარეშე და კითხულობს აგებებისა და ტესტების მიერ წარმოქმნილ კონტენტს. დაუკავშირეთ MCP კლიენტი `/mcp` ენდპოინტს ამ ინსტრუმენტების გამოყენებისთვის.

თუ ორგანიზაცია აიძულებს ერთჯერად შესვლას (SSO), შედით დაშბორდზე მისი პროვაიდერის მეშვეობით, რათა გამოიყენოთ მისი ინსტრუმენტები.

## აგების სისტემის ინტეგრაციები იყენებენ ორ სერთიფიკატს

სერთიფიკატი, რომელიც გამოიყენება Model Context Protocol-ის ინსტრუმენტებისთვის, არ ახდენს Gradle პლაგინის ან Bazel-ის დისტანციური სერვისების ავტორიზაციას. სანამ აგენტი შეცვლის ან გადაამოწმებს Gradle ან Bazel ინტეგრაციას, მან უნდა გაუშვას:

```bash
tuist auth whoami --url https://tuist.dev
```

თუ ეს ბრძანება არ არის ავტორიზებული, აგენტმა უნდა შეწყვიტოს მუშაობა და სთხოვოს მომხმარებელს გაუშვას:

```bash

```

`list_xcode_build_steps` აბრუნებს 20 ნაბიჯის გვერდებს ნაგულისხმევად (მაქსიმუმ 100 `page_size`-ით), `page` და `pagination_metadata`-ით ნავიგაციისთვის. გამოიყენეთ `search` სათაურების, პროექტების ან სამიზნეების შესაბამისობისთვის, ან ფილტრაცია ზუსტი `project`, `target`, `category` (მაგალითად, `swiftCompilation`), და `status` (`success` ან `failure`). დაალაგეთ `duration_ms`-ით ყველაზე ნელი პირველად (ნაგულისხმევი) ან `start_ms`-ით ქრონოლოგიური თანმიმდევრობით. ნაბიჯის ID-ები არღვევენ თანაბრობას და ბრუნდებათ ათობითი სტრიქონების სახით მათი სრული 64-ბიტიანი სიზუსტის შესანარჩუნებლად. ID-ები შეზღუდულია აგებით და არ უნდა შეესაბამებოდეს აგებებს შორის.

არჩევითი `start_ms` და `end_ms` ირჩევენ ნაბიჯებს, რომლებიც ემთხვევიან დროის დიაპაზონს მილიწამებში აგების დაწყებიდან; ბოლო წერტილი არ შედის. ორივე ინსტრუმენტი იღებს აგების UUID-ს ან დაშბორდის URL-ს როგორც `build_run_id`. გადასცეთ მიღებული ნაბიჯის `id` უცვლელად როგორც `step_id` მისი ლოგის მისაღებად. ლოგები ინახავს მაქსიმუმ 64 KiB თითო ნაბიჯზე, ხოლო `log_truncated` მიუთითებს გამოტოვებულ გამომავალ მონაცემებზე.

ნაბიჯები ნაგულისხმევად იკრიბება Xcode აგებების დამუშავებისას. ჩაწერილი ნაბიჯების მონაცემები ინახება 90 დღის განმავლობაში. სიის პასუხი შეიცავს `availability`-ს: `available`, როცა ჩაწერილი ნაბიჯები არსებობს, მაშინაც კი, თუ ფილტრები არაფერს ემთხვევა; `processing`, როცა აგება ჯერ კიდევ მუშავდება და ნაბიჯები ჯერ არ არსებობს; ან `unavailable`, როცა ნაბიჯები არ ჩაწერილა ან ვადა გაუვიდათ.

იგივე ოპერაციები ხელმისაწვდომია HTTP API-ზე `GET /api/projects/{account_handle}/{project_handle}/xcode/builds/{build_id}/steps` და `GET /api/projects/{account_handle}/{project_handle}/xcode/builds/{build_id}/steps/{step_id}` მისამართებზე, იგივე ფილტრებით და პაგინაციით. ორივეს სჭირდება წვდომა აგების პროექტის წაკითხვისთვის.

Dashboard გთავაზობთ იგივე ფაილს თითოეული აგების Timeline ტაბიდან.

ეს ინსტრუმენტები თანდათანობით ნერგდება და აბრუნებენ მონაცემებს მხოლოდ იმ პროექტებისთვის, სადაც ისინი ჩართულია; სხვა პროექტებისთვის ისინი აბრუნებენ შეცდომას ცარიელი შედეგის ნაცვლად. სახეობა ხელმისაწვდომია მხოლოდ იმ პროექტებისთვის, რომლებიც იყენებენ შესაბამის აგების ხელსაწყოთა ჯაჭვს. ინსტრუმენტები იღებენ შემოსაზღვრულ `start_at`/`end_at` ფილტრებს, `environment` (`any`, `ci`, ან `local`) და ზუსტ `branch`. `list_build_entities` იღებს `q`-ს; `list_build_entity_history` მხარს უჭერს გამჭვირვალე `after`/`before` კურსორებს. უცნობი დროის ან ქეშის დაკვირვებები რჩება მიუწვდომლად, ნულის ან გამოტოვების ნაცვლად. ისტორია მიუთითებს ჩაწერილ მშობელზე და ნატიურ შესრულებაზე დეტალური ანალიზისთვის არსებული გაშვების ინსტრუმენტების გამოყენებით.

`get_build_entity` მეტრიკები მოიცავს `duration_samples`-ს, დაკვირვებების რაოდენობას ჩაწერილი დროით: ნამდვილი ნულოვანი ხანგრძლივობები ითვლება, დაკარგული დრო კი — არა. ეს რაოდენობა შეიძლება იყოს დაკვირვებების რაოდენობაზე ნაკლები; მიუწვდომელი ხანგრძლივობის სტატისტიკა რჩება null-ად.

Xcode მოდულების ხანგრძლივობები მოდის გაზომილი სამიზნე კომპილაციებიდან აგების ჟურნალებში. მოდულის ქეშის ამოხსნები და სამიზნეები კომპილაციის გარეშე არ მონაწილეობენ ხანგრძლივობის შერჩევებში. კომპილაციის დაკვირვებები მიუთითებენ Xcode აგებაზე; ქეშის მოვლენები მიუთითებენ გენერაციის ან ქეშის ბრძანებაზე.

Bazel მოქმედებები იდენტიფიცირდება სამიზნის ლეიბლით, მნემონიკით და კონფიგურირებული პირველადი გამოტანით, რაც ინარჩუნებს ცალკეულ მოქმედებებსა და კონფიგურაციებს განცალკევებულად შეყვანაზე დამოკიდებული ქეშის დაიჯესტების გარეშე. ისტორია აღრიცხავს BEP-ით მოხსენებულ შესრულებებს, არა ქეშის ძიებებს ან ტრეის-პროფილის ფაზებს. სრული შესრულების დაფარვა მოითხოვს `--build_event_publish_all_actions`-ს; არტეფაქტების მიწოდება ხდება მაქსიმალური ძალისხმევით, ამიტომ დაკარგული დაკვირვებები არ არის იმის მტკიცებულება, რომ სამუშაო არ შესრულებულა. ძველი Kura პაკეტები სტაბილური იდენტობის ან შესრულების დაწყების გარეშე რჩება მიღებულად, მაგრამ არაინდექსირებულად. დასრულების დროის გაზომვების არარსებობა რჩება მიუწვდომლად და ნამდვილი ნულოვანი ხანგრძლივობები ითვლება.

Mix მოდულების ხანგრძლივობები ზომავენ შემცველი ფაილის კომპილაციას, არა დამოუკიდებლად გაზომილ მოდულურ სამუშაოს. Once მოქმედებები იყენებენ გამოცხადებულ სამიზნე/შესაძლებლობა/ინდექსის სლოტებს, როდესაც კლიენტმა მოახსენა სამიზნე ასახვები; დიაგნოსტიკური ლეიბლები მარტო არ არის სტაბილური იდენტობები. არსებული კლიენტები და გაშვების დონის ინსტრუმენტები რჩება მხარდაჭერილად უცვლელად.

Cargo კრეიტები დაჯგუფებულია ზუსტად ჩაწერილი კრეიტის ფესვის, სახელისა და სახეობის მიხედვით. Checkout-ბილიკის ცვლილებებმა შეიძლება გაყოს ისტორიები, ხოლო აგების პროფილები, ფუნქციები და სამიზნე ტრიპლეტები არ განირჩევა. ისტორია ზომავს rustc გამოძახებებს, არა ფაილის დონის სამუშაოს ან ქეშის მოხვედრებს; არარსებული სამუშაოები არ ამყარებენ წაშლებს ან სრულ სამუშაო სივრცის ინვენტარს.

ანალიტიკის კითხვებს აქვს შემოსაზღვრული მეხსიერება და შესრულების დრო. თუ მოთხოვნა აღემატება ამ ლიმიტებს, ინსტრუმენტი აბრუნებს შეცდომას ცარიელი შედეგის გამოგონების ნაცვლად.

ახალი დაკვირვებები ინდექსირდება განლაგების შემდეგ; ეს ფუნქცია არ ავსებს უკვე არსებულ გაშვების ტელემეტრიას. იდენტობის მეტამონაცემები უფრო დიდხანს ინახება, ვიდრე ცალკეული დაკვირვებები <.localized_link href="/guides/server/data-retention">მონაცემთა შენახვის პოლიტიკის</.localized_link> შესაბამისად.

### მოვლენები

კლიენტები, რომლებიც იყენებენ უმდგომარეობიან `2026-07-28` Model Context Protocol-ის ციკლს, შეუძლიათ გამოიძახონ `events/list` მოვლენებისა და მათი შინაარსის სქემების აღმოსაჩენად:

| მოვლენა | როდის იგზავნება | გამოწერის ფილტრი |
|-------|-----------------|---------------------|
| `test_case.marked_flaky` | სატესტო შემთხვევა იცვლება არაფლაკიდან ფლაკზე. | `account_handle`, `project_handle` |
| `build.failed` | ლოკალური ან უწყვეტი ინტეგრაციის Xcode, Gradle ან Bazel აგება სრულდება შეცდომით. | `account_handle`, `project_handle` |
| `test_run.failed` | ლოკალური ან უწყვეტი ინტეგრაციის ტესტების გაშვება სრულდება შეცდომით, შერწყმული შარდირებული გაშვების ან მიტოვებული გაშვების ჩათვლით. | `account_handle`, `project_handle` |

გამოსაწერად, კლიენტი იძახებს `events/subscribe`-ს მოვლენის სახელით, ზემოთ ჩამოთვლილი ხელსაწყოებით `arguments`-ში და `webhook` მიწოდებით, რომელიც შეიცავს `https://` callback URL-ს და `whsec_` ხელმოწერის საიდუმლოს. პროექტის მოვლენები მოითხოვს ანგარიშის წევრობას და შესაბამისი ტესტის ან აგების მონაცემებზე წვდომას; გამშვების სამუშაოს მოვლენები მოითხოვს ანგარიშის წევრობას და გამშვებზე წვდომას. მოთხოვნილმა [`auth.md`](https://workos.com/auth-md) წვდომის ტოკენებმა, მოთხოვნილმა ანგარიშის ტოკენებმა და ბრაუზერის ავტორიზაციის გრანტებმა შეიძლება შექმნან გამოწერები; მიწოდება ჩერდება, როდესაც შესაბამისი სერთიფიკატი აღარ არის აქტიური. თითოეულ მომხმარებელს შეუძლია ჰქონდეს მაქსიმუმ 25 აქტიური გამოწერა. Tuist აგზავნის ვერიფიკაციის გამოწვევას callback-ზე გამოწერის შენახვამდე. callback-მა უნდა დააბრუნოს ობიექტი, რომელიც შეიცავს იგივე `challenge` მნიშვნელობას. გამოწერა ნაგულისხმევად შვიდი დღე ძალაშია, შეიძლება განახლდეს ხელახლა გამოწერით და ჩერდება მიწოდება, როდესაც მომხმარებლის წვდომა ან სერთიფიკატი იხსნება. არასავალდებულო `ttlMs` შეზღუდულია ერთ საათსა და 30 დღეს შორის. Tuist ხელახლა ცდილობს დროში ამოწურულ callback-ს და აუქმებს მას მინიმუმ სამი თანმიმდევრული დროში ამოწურვის შემდეგ, რომლებიც ხუთ წუთს მოიცავს; გამოიწერეთ ხელახლა callback-ის აღდგენის შემდეგ.

როდესაც მოვლენა ხდება, Tuist აგზავნის მის რესურსის იდენტიფიკატორს და დაფის URL-ს callback-ზე. აგებისა და ტესტების გაშვების შეცდომები ასევე მოიცავს `is_ci`-ს და `git_branch`-ს, რათა კლიენტებმა შეძლონ ლოკალური შეცდომების იგნორირება ან ბრენჩით ფილტრაცია. აგების მოვლენები მოიცავს `build_system`-ს; გამშვების სამუშაოს მოვლენები მოიცავს როგორც `workflow_job_id`-ს, ასევე `workflow_run_id`-ს. მოთხოვნა მოიცავს გამოწერის იდენტიფიკატორს და [Standard Webhooks](https://www.standardwebhooks.com/) ხელმოწერის ჰედერებს, რათა კლიენტმა შეძლოს მისი წარმოშობის ვერიფიკაცია. Tuist ხელახლა ცდილობს წარუმატებელ მიწოდებებს, ამიტომ კლიენტებმა უნდა გამოიყენონ სტაბილური `eventId` დუბლიკატების გასაფილტრად. შინაარსი არ მოიცავს ტესტების სახელებს, ჟურნალებს და შეცდომის შეტყობინებებს; კლიენტმა შეიძლება მიიღოს ეს დეტალები ზემოთ ჩამოთვლილი ინსტრუმენტების მეშვეობით და გადაწყვიტოს, შეატყობინოს თუ არა გუნდს ან დაიწყოს დებაგი. კლიენტებმა შეიძლება შეაჩერონ მიწოდება `events/unsubscribe`-ით.

Cargo შედარებები ინარჩუნებენ კომპილატორის ნაწილობრივ დაფარვას და განასხვავებენ სავარაუდო კომპილატორის სამუშაოს გასულ დროში მიღებული დაზოგვისგან. |

| `compare_cache_runs` | გეხმარებათ ორი ქეშის გაშვების შედარებაში ქეშის ეფექტურობის ცვლილებებისა და სამიზნე დონის რეგრესიების აღმოსაჩენად. |

#### Gradle ინტეგრაციის მოთხოვნის ფუნქციები

`integrate_gradle_project` მოთხოვნა და `get_gradle_integration_guide` ინსტრუმენტი აღწერს სრულ კონფიგურაციის სამუშაო ნაკადს. ინსტრუმენტი ასევე მოხსენიებულია სერვერის ინიციალიზაციის ინსტრუქციებში, რაც მას აღმოჩენადს ხდის აგენტებისთვის, რომლებიც არ ჩამოთვლიან მოთხოვნებს.

| ფუნქცია | რას აკონფიგურირებს აგენტი |
|---------|---------------------------|
| `remote_cache` | ააქტიურებს Gradle-ის აგების ქეშს, აკონფიგურირებს Tuist-ის დისტანციური ქეშის ატვირთვის პოლიტიკას და ურჩევს ატვირთვას მხოლოდ უწყვეტი ინტეგრაციის გამშვებებიდან ლოკალური მხოლოდ-წაკითხვადი გამოყენებით. |
| `build_insights` | აყენებს Tuist Gradle პლაგინს და საჭიროების შემთხვევაში აკონფიგურირებს აგების ანალიტიკის ატვირთვის ქცევას. |
| `test_insights` | აყენებს Tuist Gradle პლაგინს, რათა Gradle `Test` ამოცანის შედეგები ავტომატურად აიტვირთოს. |
| `flaky_tests` | გეხმარებათ არასტაბილური ტესტების აღმოჩენის, Gradle Test Retry პლაგინის სურვილისამებრ გამოყენებისა და ტესტების კარანტინში მოქცევის კონფიგურაციაში. |
| `test_sharding` | ამატებს უწყვეტი ინტეგრაციის სამუშაო ნაკადს `tuistPrepareTestShards`-ისთვის, შარდების მატრიცის გენერაციასა და `TUIST_SHARD_INDEX`-ზე დაფუძნებულ ტესტების შესრულებას. |

როდესაც `features` გამოტოვებულია, მოთხოვნა სთხოვს აგენტს დააზუსტოს, რომელი ინტეგრაციები სურს მომხმარებელს, ან მოთხოვნიდან გამოიტანოს ყველაზე მცირე სასარგებლო ნაკრადი Gradle პროექტის რედაქტირებამდე.

#### Xcode ინტეგრაციის მოთხოვნის ფუნქციები

`integrate_xcode_project` მოთხოვნა აღწერს ყველა Xcode ინტეგრაციას, რომელსაც Tuist მხარს უჭერს:

| ფუნქცია | რას აკონფიგურირებს აგენტი |
|---------|---------------------------|
| `xcode_cache` | აკონფიგურირებს `tuist setup cache`-ს, გენერირებული პროექტის ქეშის პარამეტრებს, Xcode ქეშის ხელით აგების პარამეტრებსა და ატვირთვის პოლიტიკას, რომელიც შეზღუდულია უწყვეტი ინტეგრაციის გამშვებებზე. |
| `build_insights` | აკონფიგურირებს `tuist inspect build`-ს, `tuist xcodebuild`-ს, `-resultBundlePath`-ს და სურვილისამებრ მანქანის მეტრიკებს `tuist setup insights`-ის მეშვეობით. |
| `test_insights` | აკონფიგურირებს `tuist inspect test`-ს, სქემის ტესტის post-actions-ებსა და შედეგების ბანდლის გენერაციას უწყვეტი ინტეგრაციის ტესტების გაშვებისთვის. |
| `test_sharding` | ამატებს Xcode-ის ან გენერირებული პროექტის შარდების დაგეგმვისა და შარდების შესრულების სამუშაო ნაკადს `TUIST_SHARD_INDEX`-ით. |

როდესაც `features` გამოტოვებულია, მოთხოვნა სთხოვს აგენტს დააზუსტოს, რომელი ინტეგრაციები სურს მომხმარებელს, ან მოთხოვნიდან გამოიტანოს ყველაზე მცირე სასარგებლო ნაკრადი Xcode პროექტის რედაქტირებამდე.
