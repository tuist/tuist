# Model Context Protocol

[Model Context Protocol (MCP)](https://modelcontextprotocol.io/docs/getting-started/intro) არის ღია სტანდარტი, რომელიც საშუალებას აძლევს ხელოვნური ინტელექტის აგენტებს ურთიერთქმედონ გარე სერვისებთან და მონაცემთა წყაროებთან. ის უზრუნველყოფს ისეთი აპლიკაციების, როგორიცაა [Claude](https://claude.ai/), [Claude Code](https://docs.anthropic.com/en/docs/claude-code), [Codex](https://developers.openai.com/codex/), და რედაქტორების, როგორიცაა [Zed](https://zed.dev), [Cursor](https://www.cursor.com) ან [Visual Studio Code](https://code.visualstudio.com), თავსებადობას Tuist-თან.

Tuist განათავსებს Model Context Protocol-ის სერვერულ endpoint-ს მისამართზე `https://tuist.dev/mcp`. თქვენი კლიენტის მასთან მიერთებით, აგენტებს შეუძლიათ მიუწვდეთ თქვენს Tuist პროექტის მონაცემებზე, მათ შორის ტესტების ანალიტიკაზე, არასტაბილური ტესტების ანალიზზე და სხვა. უმეტესი ინსტრუმენტი კითხულობს Tuist-ის მონაცემებს, რომლებსაც ავტორიზებული მომხმარებელი უკვე ხედავს დაშბორდზე. ყოველი ინსტრუმენტი აცხადებს ანოტაციებს, რომლებიც მიუთითებს, არის თუ არა ის მხოლოდ წაკითხვადი, შეუძლია თუ არა გამოიწვიოს რთულად შექცევადი ცვლილება (`destructiveHint`), და შეუძლია თუ არა გასვლა Tuist-ის ფარგლებს გარეთ (`openWorldHint`). ინსტრუმენტები, რომლებიც ცვლიან მდგომარეობას, თითოეული შეზღუდულია მომხმარებლის ნებართვებით ანგარიშზე ან პროექტზე, არის:

- **ორგანიზაციები და წევრები**: `create_organization`, `add_organization_member` (ამატებს არსებულ მომხმარებელს ან ცვლის წევრის როლს), `invite_organization_member` (გზავნის მოწვევას ელფოსტაზე ნებისმიერ მისამართზე) და `cancel_organization_invitation`.
- **პროექტები**: `create_project`, `start_project_logo_upload` და `complete_project_logo_upload` (ცვლის ლოგოს), `connect_project_repository` და `disconnect_project_repository` (GitHub რეპოზიტორიის ბმულები).
- **ტესტები**: `update_test_case` (აყუჩებს, აკვეთებს, ხელახლა ააქტიურებს ან სატესტო შემთხევას არამდგრადად აღნიშნავს; ცვლილება შეიძლება მივიდეს ანგარიშის ვებჰუკების ბოლო წერტილებამდე).
- **შეტყობინებების წესები**: `create_notification_rule`, `update_notification_rule` და `delete_notification_rule`.
- **უწყვეტი ინტეგრაციის გამშვები აგენტები**: `create_runner_profile`, `update_runner_profile` (იმ სამუშაოების შევიწროება, რომლებიც ინახავენ ქეშის ტომებს, აუქმებს ლოდინში მყოფ შენახვებს), `delete_runner_profile` და `delete_runner_volume` (შლის ტომის შენახულ შინაარსს).
- **სენდბოქსები**: `create_sandbox`, `pause_sandbox`, `resume_sandbox`, `archive_sandbox` და `delete_sandbox` (შლის მის დისკებს).
- **უკუკავშირი**: `report_feedback` (გზავნის ანგარიშს ინსტრუმენტის ან მოთხოვნის შესახებ Tuist-ის გუნდს; მხოლოდ tuist.dev-ზე).
- **ორგანიზაციის AI**: `save_organization_ai_model`, `remove_organization_ai_model`, `set_organization_ai_default_model`, `save_organization_ai_task_route`, `remove_organization_ai_task_route` და `remove_organization_ai_provider` (შლის პროვაიდერის გასაღებს და მოდელებს, და წყვეტს ბმას Anthropic-ში დაკავშირებულ Claude ორგანიზაციასთან).
- **აგენტის ინტეგრაციები**: `connect_amp_workspace` (ანიჭებს სამუშაო სივრცის orbs-ს CI წვდომას ანგარიშზე), `disconnect_amp_workspace` და `connect_claude_environment` (საშუალებას აძლევს Claude Managed Agents გარემოს ჩაატაროს სესიები Tuist სენდბოქსებში).

`add_organization_member`, `cancel_organization_invitation`, `complete_project_logo_upload`, `disconnect_project_repository`, `update_test_case`, `update_notification_rule`, `delete_notification_rule`, `update_runner_profile`, `delete_runner_profile`, `delete_runner_volume`, `delete_sandbox`, `disconnect_amp_workspace`, `remove_organization_ai_provider`, `remove_organization_ai_model` და `remove_organization_ai_task_route` აცხადებენ `destructiveHint: true`-ს, რადგან ისინი ცვლიან ან შლიან არსებულ მდგომარეობას. `invite_organization_member`, `update_test_case`, `connect_claude_environment`, `remove_organization_ai_provider` და `report_feedback` აცხადებენ `openWorldHint: true`-ს, რადგან ისინი გზავნიან ელფოსტას, ამცნობენ გარე webhook endpoint-ებს, ურეკავენ Anthropic-ს ან გზავნიან ანგარიშს Tuist-ის გუნდს.

პირადი Claude და ChatGPT გამოწერები დაკავშირებულია მხოლოდ დაშბორდის AI პარამეტრებში, ამიტომ გამოწერის ტოკენები და შესვლები არასდროს გადის Model Context Protocol კლიენტში. ანგარიშის კონფიგურაციის ინსტრუმენტები მოითხოვს მომხმარებლის ავტორიზაციას. ისინი არ არის ხელმისაწვდომი პროექტის ტოკენებისთვის ან ჩვეულებრივი ანგარიშის ტოკენებისთვის. როდესაც მომხმარებელი ავტორიზებს კლიენტს ბრაუზერში ან ითხოვს `auth.md` რეგისტრაციას, Tuist აკავშირებს ამ სერთიფიკატს მომხმარებელთან მხოლოდ Model Context Protocol endpoint-ზე, რათა კონფიგურაციის ინსტრუმენტებმა შეძლონ მოთხოვნილი სამუშაო პროცესის დასრულება.

Tuist ახორციელებს [2026-07-28 პროტოკოლს](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http). მოთხოვნები არის უსესიო: კლიენტები აგზავნიან თავიანთ პროტოკოლის მეტამონაცემებს ყოველ მოთხოვნასთან ერთად და შეუძლიათ პირდაპირ გამოიძახონ ინსტრუმენტები ინიციალიზაციის გარეშე. `server/discover` აბრუნებს სერვერის იდენტურობას, შესაძლებლობებს, მხარდაჭერილ ვერსიებს და ინსტრუქციებს. არ არსებობს სესიის იდენტიფიკატორები ან დამოუკიდებელი მოვლენათა ნაკადები. კლიენტები, რომლებიც იყენებენ 2025-06-18 ან 2025-03-26 ინიციალიზაციის ნაკადს, კვლავ მხარდაჭერილია; ისინიც მუშაობენ სერვერის სესიების გარეშე.

## Model Context Protocol უნარების წინააღმდეგ

Model Context Protocol ინსტრუმენტები და <.localized_link href="/guides/features/agentic-coding/skills">უნარები</.localized_link> შეიძლება გადაიფარებოდნენ თავიანთი ფუნქციებით. ამჟამინდელი გადაფარვის გათვალისწინებით, აირჩიეთ ერთი მიდგომა თითოეული სამუშაო პროცესისთვის და გამოიყენეთ ის თანმიმდევრულად, ნაცვლად ორივეს ერთ ნაკადში შერევისა.

კლიენტებისთვის, რომლებიც მხარს უჭერენ პლაგინების ინსტალაციას, გამოიყენეთ <.localized_link href="/guides/features/agentic-coding/plugins">Tuist პლაგინები</.localized_link> ორივეს ერთად ინსტალაციისთვის.

## კონფიგურაცია

დაამატეთ `https://tuist.dev/mcp` როგორც დისტანციური Model Context Protocol სერვერი თქვენს კლიენტში. სერვერის ინიციალიზაციის ინსტრუქციები და საჯარო სერვერის ბარათი აღწერს OAuth 2.0-ს დინამიური კლიენტის რეგისტრაციით და სტანდარტული ბრაუზერის ავტორიზაციის ნაკადით პირდაპირ, აგენტებისგან გარე ავთენტიკაციის დოკუმენტების მოთხოვნის ან მათზე გადასვლის გარეშე. ეს სერვერის მასშტაბის ინსტრუქციები ინარჩუნებს სამუშაო პროცესის მითითებებს ზოგადს: ინსტრუმენტის ავთენტიკაცია არ ავთენტიკაციებს ადგილობრივ ბრძანების ხაზის ინსტრუმენტებს ან აგების სისტემის ინტეგრაციებს, და აგენტებმა უნდა შეამოწმონ მოთხოვნილი ცვლილებები შესაბამისი Tuist ინსტრუმენტების მეშვეობით. აგების სისტემის სპეციფიკური კონფიგურაცია და ავთენტიკაციის შემოწმებები დოკუმენტირებულია ინტეგრაციის სახელმძღვანელოებში და მოთხოვნებში. Tuist კვლავ აცხადებს როგორც [Open Authorization](https://oauth.net/2/) აღმოჩენის მეტამონაცემებს, ასევე მიმდინარე [auth.md პროტოკოლს](https://workos.com/auth-md) მისამართზე `https://tuist.dev/auth.md` ცალ-ცალკე.

თუ თქვენი რომელიმე ორგანიზაცია აიძულებს ერთჯერად შესვლას (SSO), ბრაუზერში კლიენტის ავტორიზაცია მოითხოვს სესიას, რომელიც შესულია ამ ორგანიზაციის მეშვეობით, და Tuist საჭიროების შემთხვევაში ჯერ პროვაიდერზე გაგზავნით. იხილეთ <.localized_link href="/guides/integrations/authentication/sso#choose-an-enrollment-policy">ერთჯერადი შესვლა</.localized_link>.

Endpoint იღებს უსესიო `2026-07-28` Model Context Protocol მოთხოვნის ციკლს, მათ შორის `server/discover`-ს, ძველ სესიაზე დაფუძნებულ ციკლთან ერთად. არსებულმა კლიენტებმა შეიძლება გააგრძელონ თავიანთი მიმდინარე მიერთების მეთოდის გამოყენება.

კლიენტებს, რომლებიც მხარს უჭერენ Model Context Protocol მოვლენებს, შეუძლიათ გამოიწერონ პროექტის მოვლენები. იხილეთ [მოვლენები](#events) ხელმისაწვდომი მოვლენებისა და მიწოდების მოთხოვნებისთვის.

კლიენტებს, რომლებიც უკვე მხარს უჭერენ დისტანციურ ბრაუზერის ავთენტიკაციას, შეუძლიათ გააგრძელონ ავთენტიკაცია ბრაუზერში. კლიენტებს და აგენტებს, რომლებიც მხარს უჭერენ `auth.md`-ს, შეუძლიათ დარეგისტრირდნენ ანონიმურად, წარადგინონ სანდო პროვაიდერის იდენტურობის დადასტურება ან დაიწყონ სერვისით ავთენტიკირებული ელფოსტის მოთხოვნა. რეგისტრაცია აბრუნებს Tuist-ით ხელმოწერილ იდენტურობის დადასტურებას, რომელსაც აგენტი ცვლის სტანდარტულ ტოკენის endpoint-ზე ერთსაათიანი წვდომის ტოკენისთვის. Tuist აქვეყნებს თავის საჯარო ხელმოწერის გასაღებს და მხარს უჭერს სტანდარტულ ტოკენის გაუქმებას და პროვაიდერის უსაფრთხოების მოვლენების მიწოდებას.

არაავთენტიკირებულმა აგენტმა უნდა წაიკითხოს `WWW-Authenticate` ჰედერი, რომელიც დაბრუნებულია Model Context Protocol endpoint-ის მიერ, მოიძიოს დაცული რესურსის მეტამონაცემები, მოიძიოს ავტორიზაციის სერვერის მეტამონაცემები და მიჰყვეს მის `agent_auth.skill` URL-ს. Tuist ასევე აბრუნებს იგივე ადგილობრივ `auth_md` URL-ს არაავტორიზებული პასუხის სხეულში, რათა ენის მოდელზე დაფუძნებულმა კლიენტებმა შეძლონ ნაკადის აღმოჩენა ნატიური კლიენტის ინტეგრაციაზე დამოკიდებულების გარეშე. განლაგების ადგილობრივი დოკუმენტია საიმედო წყარო endpoint-ების სახელების, მოთხოვნის სხეულების, მოთხოვნის გამოკითხვისა და დადასტურების გაცვლისთვის.

სანამ აგენტი დაიწყებს ელფოსტის მოთხოვნას, მან უნდა სთხოვოს მომხმარებელს დაადასტუროს თავისი Tuist ანგარიშის ელფოსტის მისამართი. მან არ უნდა გამოიტანოს ეს მისამართი პროვაიდერის პროფილიდან, Git კონფიგურაციიდან, გარემოს ცვლადიდან ან სესიის მეტამონაცემებიდან.

Endpoint იყენებს `mcp` სკოპების ჯგუფს. ანონიმურმა წინასწარი მოთხოვნის კრედენშალმა შეიძლება აღმოაჩინოს შესაძლებლობები და წაიკითხოს საჯარო ინტეგრაციის სახელმძღვანელო, მაგრამ ის არ განიხილება როგორც შესული მომხმარებელი. ბრაუზერის ავტორიზაციის ან მოთხოვნის შემდეგ, კრედენშალი არის მომხმარებლის სკოპში და თითოეული ხელსაწყო იყენებს იგივე ავტორიზაციის შემოწმებებს, რასაც დაშბორდი. დეტალებისთვის იხილეთ <.localized_link href="/guides/server/authentication#scope-groups">სკოპების ჯგუფების დოკუმენტაცია</.localized_link>.

ხელსაწყოები გადაჰყავს პროექტებზე, რომლებიც ავთენტიკირებულ მომხმარებელს უკვე შეუძლია წაიკითხოს. Xcode და Gradle აგების ხელსაწყოები იღებენ აგების UUID-ს ან დაშბორდის URL-ს. UUID-მ უნდა ამოიცნოს ზუსტად ერთი პროექტი; თუ ის ჩნდება რამდენიმე პროექტში, ხელსაწყო აბრუნებს „არ არის ნაპოვნი“-ს სხვა პროექტის ანგარიშის არჩევის ნაცვლად. პროექტის სკოპის დაშბორდისა და API-ს წაკითხვები რჩება ხელმისაწვდომი. მოხსენებული აქტორის იდენტიფიკატორები არის დაუდასტურებელი ლეიბლები, არა კრედენშალები ან დამატებითი წვდომის უფლებები.

აგების სიისა და დეტალების ხელსაწყოები აჩვენებენ არააუცილებელ `tuist_version` მეტამონაცემებს: Tuist CLI Xcode-ისა და Cargo-სთვის, Tuist Gradle პლაგინი Gradle-ისთვის და `tuist_ex` ბიბლიოთეკა Mix-ისთვის. Xcode ასევე აჩვენებს `tuist_generation_version`-ს თავის დაკავშირებული პროექტის გენერაციის მოვლენიდან, რომელიც შეიძლება განსხვავდებოდეს ატვირთვის CLI-სგან. დაკარგული დაკვირვებები არის null, არა გამოტანილი სერვერიდან ან სხვა ანგარიშიდან. Bazel იყენებს თავის არსებულ `bazel_version`-ს; Struo გაშვების დეტალები აჩვენებენ `once_version`-ს. ეს ველები აღწერენ მოხსენებულ ვერსიებს, არა დადასტურებულ იდენტურობას ან სადენის კონტრაქტის ვერსიებს. REST აგების endpoint-ები აჩვენებენ იგივე მეტამონაცემებს. არსებული ინტეგრაციისა და ფლაკი ტესტების უნარები არ არის დამოკიდებული ვერსიის ველებზე და არ საჭიროებს სამუშაო ნაკადის ცვლილებებს.

Tuist ოპერატორები, რომლებიც იკვლევენ მომხმარებლის ანგარიშს, აკეთებენ ამას Tuist-ის შიდა ოპერაციების ხელსაწყოების მეშვეობით, რომელიც იწერს ყოველ ზარს; პირდაპირი კავშირი ამ endpoint-თან არ იძლევა წვდომას მომხმარებლის საკუთარი წევრობის ფარგლებს გარეთ.

### Pulse

Pulse აჩვენებს მხოლოდ წაკითხვად ხელსაწყოებს ანგარიშის ოპერაციული მეტრიკების, ჟურნალების, ტრეისებისა და შეცდომებისთვის, რომლებიც ყველა მიმართულია `account_handle`-ით. პირველი სამი იმეორებს Pulse გვერდებსა და მათ REST API-ს; დანარჩენი ხუთი აგენტს საშუალებას აძლევს პირდაპირ შეისწავლოს ტელემეტრია და არ აქვთ REST ეკვივალენტი:

| ხელსაწყო | მიზანი | REST ეკვივალენტი `/api/accounts/:account_handle/pulse`-ის ქვეშ |
| --- | --- | --- |
| `query_pulse` | Pulse გვერდის ცხრილები | `GET /:signal` |
| `get_pulse_analytics` | Pulse გვერდის ვიჯეტები | `GET /:signal/analytics` |
| `get_pulse_error_issue` | ერთი შეცდომის პრობლემა და მისი მოვლენები | `GET /errors/issues/:fingerprint` |
| `query_pulse_metrics` | მყისიერი ან დიაპაზონის PromQL | არ არის |
| `list_pulse_labels` | ლეიბლის სახელები, ან ერთი ლეიბლის მნიშვნელობები | არ არის |
| `search_pulse_logs` | ფილტრული ჟურნალის ჩანაწერები | არ არის |
| `search_pulse_traces` | ფილტრული სპანები | არ არის |
| `get_pulse_trace` | ერთი ტრეისის ყველა სპანი | არ არის |

Pulse შეზღუდულია სერვერით კონფიგურირებული ორგანიზაციის მიმდინარე წევრებისთვის, მაშინაც კი, თუ ანგარიში ან პროექტი საჯაროა. ის მოითხოვს მომხმარებლის ავთენტიკაციას ან მომხმარებელთან დაკავშირებულ `mcp` კრედენშალსა და ანგარიშის წაკითხვის ავტორიზაციას. პროექტის ტოკენები, ჩვეულებრივი ანგარიშის ტოკენები, ანონიმური რეგისტრაციები და ოპერატორის წვდომა ორგანიზაციის წევრობის გარეშე არ იძლევა Pulse-ზე წვდომას. კრედენშალებს არ შეუძლიათ აირჩიონ სხვა ბექენდი ან ტელემეტრიის არენდატორი და მხოლოდ სერვერით კონფიგურირებულ ანგარიშს აქვს Pulse ტელემეტრია, ამიტომ არცერთ ხელსაწყოს არ შეუძლია წაიკითხოს სხვა ანგარიშის მონაცემები. ბრაუზერის აგენტები იღებენ ამ ხელსაწყოებს მხოლოდ Pulse გვერდებზე, ამ გვერდის ანგარიშის სკოპის ფარგლებში.

REST მოითხოვს მომხმარებლის კრედენშალს. OAuth და `auth.md` მომხმარებლის ასოციაციები ხელმისაწვდომია მხოლოდ `/mcp` endpoint-ზე; ანგარიშის კრედენშალი მიმდინარე მომხმარებლის გარეშე უარყოფილია, მიუხედავად დაკავშირებული ანგარიშის წევრობისა ან ხილვადობის.

`query_pulse` იღებს `signal`-ს (`metrics`, `logs`, `traces` ან `errors`), არააუცილებელ `query`-ს და `range`-ს (`15m`, `1h`, `6h` ან `24h`, ნაგულისხმევი `1h`). მეტრიკები იღებენ PromQL გამოსახულებებს. ჟურნალები, ტრეისები და შეცდომები იღებენ ლიტერალურ, რეგისტრის მიმართ უმნიშვნელო ტექსტს, რომელიც ემთხვევა ჟურნალის სხეულებს, სპანების სახელებსა და შეცდომის პრობლემების სათაურებს; `*`, ნაგულისხმევი, ირჩევს ყველაფერს. ტრეისის სტრიქონები არის ინდივიდუალური სპანები. შეცდომის სტრიქონები არის პრობლემები: მოვლენები დაჯგუფებულია სერვისისა და თითის ანაბეჭდის მიხედვით, მათი მოვლენების რაოდენობით, დაზარალებული ანგარიშებით, პირველი და ბოლო გამოჩენით ფანჯარაში, და მათი ბოლო მოვლენის სათაური, დამნაშავე, დონე და პლატფორმა. ცხრილები იღებენ `search`-ს, `page`-ს (ნაგულისხმევი `1`), `page_size`-ს (`1`–`100`, ნაგულისხმევი `20`), `sort_by`-ს და `sort_order`-ს (`asc` ან `desc`). დალაგების სვეტები დამოკიდებულია სიგნალზე და ჩამოთვლილია ხელსაწყოს სქემაში. ფილტრები მოიცავს `service`-ს და `level`-ს ჟურნალებისა და შეცდომებისთვის. ფილტრის ოპერატორები იყენებენ შესაბამის `_op` არგუმენტს (`eq`, `contains` ან `not_contains`), ნაგულისხმევად ზუსტი ტოლობით.

დალაგების სვეტებია `name`/`value` მეტრიკებისთვის; `timestamp`/`service`/`level`/`message`/`trace_id` ჟურნალებისთვის; `timestamp`/`service`/`name`/`duration_ms`/`trace_id` ტრეისებისთვის; და `last_seen`/`first_seen`/`events`/`accounts`/`title`/`service`/`level` შეცდომებისთვის. დაშბორდი განზრახ აჩვენებს ქვესიმრავლეს; API და ხელსაწყოები იღებენ სრულ სიას თითოეული სიგნალისთვის.

ცხრილის პასუხები შეიცავს `rows`-ს, `series`-ს, `warnings`-ს და `meta`-ს. დაფურცვლის მეტამონაცემები მოიცავს `page`-ს, `page_size`-ს, `total_count`-ს, `total_pages`-ს, `has_next_page`-ს, `has_previous_page`-ს და `end_at`-ს. გადასცეთ დაბრუნებული ISO8601 `end_at` შემდგომ გვერდებთან ერთად მოთხოვნის ფანჯრის შესანარჩუნებლად. შედეგის ლიმიტის შეცდომები მოითხოვენ მოთხოვნის ან დროის დიაპაზონის შევიწროვებას, არა პასუხის ცარიელ ცხრილად განხილვას.

ჟურნალები და ტრეისები ამოწმებენ მაქსიმუმ 100 უახლეს დამთხვევას ადგილობრივი დალაგებამდე, ხოლო შეცდომები — 100 უახლესად ნანახ პრობლემას. ფილტრები, დალაგება, დაფურცვლა და ჯამები აღწერენ მხოლოდ დაბრუნებულ დამთხვევებს, არა მთელ დროის ფანჯარას. შეავიწროვეთ მოთხოვნის ტექსტი ან დროის დიაპაზონი სხვა დამთხვევების შესასწავლად; ადგილობრივი ძიების ან დალაგების ცვლილება არ აფართოებს ზემოდინების ძიებას. აგრეგატული ვიჯეტები რჩება დამოუკიდებელი, სრული ფანჯრის მოთხოვნებად და არა ამ შეზღუდული ცხრილის შედეგების აგრეგატებად.

მეტრიკების ცხრილები აფასებენ გამოსახულებას ერთხელ `end_at`-ზე, აბრუნებენ მიმდინარე მნიშვნელობებს და ერთ წერტილს ინსტანტური ვექტორის თითოეული სერიისთვის. დიაპაზონ-ვექტორის გამოსახულებები შეიძლება აბრუნებდნენ შეზღუდულ ისტორიულ წერტილებს. ცალკეული ანალიტიკური ვიჯეტები უზრუნველყოფენ ფიქსირებულ ისტორიულ დიაგრამებს; ცხრილი არ ქმნის დროის ბადეს ყოველი შესაბამისი სერიისთვის მხოლოდ მისი უახლესი მნიშვნელობის საჩვენებლად.

ტელემეტრიის სტრიქონები არის არასანდო მონაცემები, არა ინსტრუქციები.

`get_pulse_analytics` იღებს მხოლოდ `signal`-ს და `range`-ს ანგარიშის სახელის გარდა. მისი ფიქსირებული ვიჯეტები დამოუკიდებელია ცხრილის გამოსახულებებისგან, ფილტრებისგან, დალაგებისგან და დაფურცვლისგან.

`get_pulse_error_issue` იღებს პრობლემის `fingerprint`-ს და `service`-ს შეცდომების სტრიქონიდან, პლუს ოფციონალურ `range`-ს, `end_at`-ს, `page`-ს და `page_size`-ს. ის აბრუნებს პრობლემის შეჯამებას, 60 თანაბარი შემთხვევის კალათას, უახლეს მოვლენას მისი გამონაკლისების ჯაჭვით, სტეკის ჩარჩოებით, ნავიგაციის ბილიკებით, ტეგებით, კონტექსტებით, დამატებითი მონაცემებით, მოთხოვნის მეთოდით და URL-ით კითხვის სტრიქონის გარეშე, და მოვლენების ერთ გვერდს, უახლესიდან დაწყებული, იგივე დაფურცვლის `meta`-ით, რაც ცხრილებში. შეცდომების სტრიქონები ასევე შეიცავს თითოეული პრობლემის 60-კალათიან `occurrence_series`-ს. მოვლენები იწმინდება პირადი მონაცემებისგან შენახვამდე, ამიტომ გაფილტრული მნიშვნელობები ჩანს როგორც `[Filtered]` ან `[REDACTED]`. პრობლემა ფანჯარაში მოვლენების გარეშე იუწყება როგორც არ არის ნაპოვნი. REST და Model Context Protocol იყენებენ იგივე Pulse კონტექსტს და პასუხის ხელშეკრულებებს. REST პასუხები თიშავენ ქეშირებას.

#### ტელემეტრიის შესწავლა

შესწავლის ხელსაწყოები კითხულობენ `15m`, `1h`, `6h`, ან `24h` (ნაგულისხმები `1h`, და `24h` `get_pulse_trace`-სთვის) ფანჯარას, რომელიც მთავრდება ოფციონალურ ISO8601 `end_at`-ზე, რომელიც ნაგულისხმევად არის ახლა. ყოველი პასუხი აბრუნებს `start_at`-ს და `end_at`-ს; გადასცეთ იგივე `end_at` ხელახლა ფანჯრის შესანარჩუნებლად. ამ ხელსაწყოებიდან არცერთი არ იღებს SQL-ს.

- `query_pulse_metrics` აფასებს `query`-ს, PromQL გამოსახულებას, `end_at`-ზე (`type: instant`, ნაგულისხმები) ან ყოველ `step` წამში ფანჯრის განმავლობაში (`type: range`). ნაბიჯი ნაგულისხმევად არის და არ შეიძლება იყოს უფრო მცირე, ვიდრე ფანჯარა გაყოფილი 360-ზე, ამიტომ სერიას მაქსიმუმ 361 წერტილი აქვს. შედეგებს მაქსიმუმ 5,000 სერია აქვს. წერტილები არის `[unix_seconds, value]`, და `NaN` და უსასრულო მნიშვნელობები არის სტრიქონები. ინსტანტური მოთხოვნები უარყოფენ `range`-ს და `step`-ს.
- `list_pulse_labels` იღებს `signal`-ს. `label`-ს გარეშე, ის ჩამოთვლის ლეიბლების სახელებს; `label`-თან ერთად, ის ჩამოთვლის იმ ლეიბლის მნიშვნელობებს. მეტრიკებისთვის, `__name__` ჩამოთვლის მეტრიკების სახელებს, და ნებისმიერი სხვა ლეიბლის მნიშვნელობები მოითხოვს `match`-ს, სერიის სელექტორს, როგორიცაა `up`. ჟურნალების და ტრეისის ლეიბლის მნიშვნელობები იღებენ `filters`-ს; ტრეისის ლეიბლის სახელები მოდის ტრეისის სქემიდან და არა. ჟურნალის და ტრეისის მნიშვნელობები შეიცავს მათ ჩანაწერთა რაოდენობას ფანჯარაში, ყველაზე ხშირი პირველად, ამიტომ ისინი ასევე ემსახურებიან როგორც დაშლა, მაგალითად, შეცდომები სერვისის მიხედვით. `search` ინარჩუნებს მხოლოდ სახელებს ან მნიშვნელობებს, რომლებიც შეიცავს ლიტერალურ ტექსტს, და `limit` იღებს `1`–`1000` (ნაგულისხმები `100`). ჟურნალის ლეიბლის სახელის აღმოჩენა ამოწმებს მაქსიმუმ 1,000 განსხვავებულ ატრიბუტთა ნაკრებს თითოეული სახისა და ჩამოთვლის მხოლოდ გასაღებებს, რომლებსაც ფილტრები იღებენ.
- `search_pulse_logs` აბრუნებს მაქსიმუმ `limit` ჩანაწერს (`1`–`100`, ნაგულისხმები `50`), `newest` ან `oldest` პირველად, რომელთა სხეული შეიცავს `text`-ს და რომლებიც ემთხვევა ყოველ ფილტრს. თითოეული ჩანაწერი შეიცავს მის `severity_text`-ს, `body`-ს, `trace_id`-ს, `span_id`-ს, `scope_name`-ს, და მის გაერთიანებულ რესურსს და ჟურნალის `attributes`-ს. `span_id` და `scope_name` არის `null` Kubernetes-იდან შეგროვებული ჟურნალებისთვის, რასაც მხოლოდ OTLP ჟურნალის გამგზავნები აყენებენ.
- `search_pulse_traces` აბრუნებს მაქსიმუმ `limit` სპანს, `newest`, `oldest`, ან `slowest` პირველად, რომლებიც ემთხვევა ყოველ ფილტრს, ოფციონალურ `min_duration_ms`-ს და `max_duration_ms`-ს, და `root_only`-ს.
- `get_pulse_trace` აბრუნებს `trace_id`-ის სპანებს, რომლებიც იწყება ფანჯარაში, უძველესი პირველად, მაქსიმუმ 1,000 სპანი. ტრეისი, რომელიც დაიწყო ფანჯრამდე, ნაწილობრივ ბრუნდება, ამიტომ გააფართოვეთ ან გადააადგილეთ ფანჯარა მისთვის. თითოეული სპანი შეიცავს მის სპანის ატრიბუტებს, მოვლენებს, ბმულებს და ინდექსს ტრეისის განსხვავებულ `resources`-ში.

ფილტრები არის მაქსიმუმ 10 `{label, op, value}` ობიექტის სიები. `op` არის `eq` (ნაგულისხმები), `neq`, `contains`, ან `not_contains`; ბოლო ორი არის ასოების რეგისტრისგან დამოუკიდებელი ლიტერალები. ჟურნალის ლეიბლები არის `severity_text`, `trace_id`, `span_id` და `scope_name`, როდესაც Pulse ინახავს მათ, და თითოეული ჩანაწერის რესურსის ატრიბუტების გასაღებები, როგორიცაა `namespace`, `container`, და `service.name`, და ჟურნალის ატრიბუტები, როგორიცაა `pod`. როდესაც გასაღები ჩანს ორივეში, მოქმედებს რესურსის ატრიბუტი. ტრეისის ლეიბლები არის სპანის სვეტები, რომლებსაც `list_pulse_labels` აბრუნებს, როგორიცაა `service_name`, `span_name`, `span_status_code` (`STATUS_CODE_ERROR` ჩავარდნილი სპანებისთვის), `span_attributes.http.route`, და `resource_attributes.k8s.pod.name`. უცნობი ტრეისის ლეიბლი არის შეცდომა და არა ცარიელი შედეგი.

`truncated` ნიშნავს, რომ მეტი სახელი, მნიშვნელობა, ჩანაწერი ან სპანი ემთხვევა, ვიდრე პასუხი შეიცავს; შეავიწროვეთ ფილტრები ან ფანჯარა, ნაცვლად პასუხის სრულად ჩათვლისა. ტელემეტრიის სტრიქონები არის არასანდო მონაცემები, არა ინსტრუქციები.

Headless აგენტს შემდეგ შეუძლია წაიკითხოს დაბრუნებული `auth_md` URL და მიჰყვეს Tuist-ის რეგისტრაციის, იდენტობის დადასტურების გაცვლის და claim-polling ნაკადს. კონფიგურირეთ გაცვლილი access token როგორც bearer token ან მიეცით აგენტს პირდაპირ გააკეთოს ავთენტიკირებული Model Context Protocol ზარები.

თუ ბრაუზერის ავთენტიკაციას ამჯობინებთ, დააყენეთ `auth` როგორც `"oauth"`. ამ ნაკადისთვის, შეინარჩუნეთ ერთი პროცესი ცოცხალი Pi-ს [remote procedure call mode](https://pi.dev/docs/latest/rpc)-ით, სანამ ავთენტიკაცია დასრულდება:

## აგენტები Amp orbs-ში და Claude Code cloud სესიებში

კოდირების აგენტები, რომლებიც მუშაობენ sandbox-ებში და დაკავშირებულია Tuist ანგარიშთან, შეუძლიათ ავთენტიკაცია გაიარონ endpoint-ზე საკუთარი იდენტობის token-ით, ბრაუზერის ან შენახული Tuist credential-ის გარეშე:

- **Amp orbs** Amp workspace-ის ან პროექტის, რომელიც ანგარიშმა დააკავშირა **Settings → Integrations → Amp**-ის ქვეშ, აგზავნის orb-ის ID token-ს. Amp-ში დააყენეთ სერვერის `Authorization` header როგორც `Bearer ${amp:id-token}`. Amp ქმნის token-ს სერვერის URL-ის origin-ისთვის, ამიტომ URL უნდა იყოს ამ Tuist ინსტანციის საკუთარი მისამართი, და აახლებს მას ვადის გასვლამდე. სხვა origin-ისთვის შექმნილი token-ები უარყოფილია.
- **Claude Code cloud sessions** დაკავშირებული Claude Code გარემოს აგზავნის სესიის token-ს, რომელსაც Tuist გადასცემს მათ როგორც `TUIST_OIDC_TOKEN`. დააყენეთ header როგორც `Bearer ${TUIST_OIDC_TOKEN}`.

Tuist-ის Linux sandbox-ები არ ამატებენ სერვერს თქვენთვის: ისინი შეიცავენ Tuist CLI-ს, რომელიც შედის სისტემაში იგივე იდენტობით, და skill-ს, რომელიც ეუბნება აგენტს, როდის შეამოწმოს შედეგები პროექტის ისტორიის მიხედვით. აგენტებს MCP ხელსაწყოების მისაცემად, დაამატეთ სერვერი თქვენს Amp ან Claude Code პარამეტრებში, ან პროექტის `.mcp.json`-ში, ზემოთ მოცემული header-ით.

ეს token-ები იძლევა მხოლოდ წაკითხვის უფლებას დაკავშირებული ანგარიშის ყველა პროექტზე: ისინი შეიცავენ `mcp` ჯგუფის წაკითხვის scope-ებს და არაერთს, რომელიც ქმნის, ცვლის ან შლის მონაცემებს, როგორიცაა ტესტების ჩუმად დაყენება ან გამოტოვება. workspace-ის ან გარემოს გათიშვა წყვეტს წვდომას შემდეგ მოთხოვნაზე, და წვდომა არასდროს ძლებს token-ზე მეტ ხანს. Amp workspace, რომელიც დაკავშირებულია რამდენიმე Tuist ანგარიშთან, უარყოფილია, რადგან მისი token არ ასახელებს ერთს. როცა კავშირი არ არის, არაავტორიზებული პასუხის `error_description` ამბობს ამას.

ეს მხოლოდ წაკითხვის წვდომა ვრცელდება მხოლოდ Model Context Protocol endpoint-ზე. ბრძანების ხაზის ხელსაწყო და build-system ინტეგრაციები იმავე sandbox-ში მაინც ცვლიან token-ს კავშირის CI წვდომისთვის.

## WebMCP

ბრაუზერებში, რომლებიც მხარს უჭერენ [WebMCP](https://webmachinelearning.github.io/webmcp)-ს, Tuist-ის გვერდები რეგისტრირებენ ხელსაწყოებს `document.modelContext`-ით, ასე რომ ბრაუზერში ჩაშენებულ აგენტებს შეუძლიათ გამოიძახონ ისინი დამატებითი კონფიგურაციის გარეშე. ზარები მუშაობენ Tuist სერვერზე.

- **Website and documentation pages** რეგისტრირებენ დოკუმენტაციის და წყაროს ხელსაწყოებს (`search_tuist`, `search_tuist_code`, `list_tuist_files` და `read_tuist_file`). მათ არ სჭირდებათ თქვენი შესვლა.
- **An account's dashboard pages**, როცა შესული ხართ, რეგისტრირებენ Tuist-ის მხოლოდ წაკითხვის ხელსაწყოებს ამ ანგარიშისთვის. თითოეული გვერდი რეგისტრირებს მხოლოდ იმ ხელსაწყოებს, რასაც ის აჩვენებს, პროექტის build system-ისთვის: Gradle პროექტის builds გვერდი იღებს Gradle build ხელსაწყოებს, მისი test გვერდები test და coverage ხელსაწყოებს, runners გვერდები runner ხელსაწყოებს, და sandboxes გვერდები sandbox ხელსაწყოებს. ყველა გვერდი ასევე იღებს დოკუმენტაციის ხელსაწყოებს, `list_projects` და `get_project`. ხელსაწყოები მუშაობენ შესული მომხმარებლის სახელით, ამიტომ ისინი მხოლოდ იმ მონაცემებს ეწვდებიან, რომელთა წაკითხვაც შეგიძლიათ dashboard-ში, და მხოლოდ იმ ანგარიშს, რომელსაც უყურებთ. როცა გადადიხართ სხვა გვერდზე ან ანგარიშზე, ხელსაწყოები იცვლება იმ გვერდის ხელსაწყოებით.

ხელსაწყოები, რომლებიც ქმნიან, ცვლიან ან შლიან მონაცემებს, არ არის ხელმისაწვდომი WebMCP-ით, რადგან ბრაუზერის აგენტი იღებს ხელსაწყოებს თქვენი დამატების გარეშე და კითხულობს შინაარსს, რომელსაც builds და tests ქმნიან. დაუკავშირეთ MCP კლიენტი `/mcp` endpoint-ს ამ ხელსაწყოების გამოსაყენებლად.

თუ ორგანიზაცია აიძულებს ერთჯერად შესვლას (single sign-on), შედით dashboard-ში მისი პროვაიდერით, რათა გამოიყენოთ მისი ხელსაწყოები.

## Build-system ინტეგრაციები იყენებენ ორ credential-ს

Model Context Protocol ხელსაწყოებისთვის გამოყენებული credential არ ავთენტიკირებს Gradle plugin-ს ან Bazel-ის remote სერვისებს. სანამ აგენტი ჩაასწორებს ან დაადასტურებს Gradle ან Bazel ინტეგრაციას, მან უნდა გაუშვას:

```bash
tuist auth whoami --url https://tuist.dev
```

თუ ეს ბრძანება არ არის ავთენტიკირებული, აგენტმა უნდა შეწყვიტოს და სთხოვოს მომხმარებელს გაუშვას:

```bash
tuist auth login --url https://tuist.dev
```

ლოკალური ან self-hosted განლაგებისთვის, შეცვალეთ URL ორივე ბრძანებაში და `tuist.toml`-ში. შეინარჩუნეთ hostname-ის მართლწერა იდენტური ყველგან. მაგალითად, `localhost` და `127.0.0.1` იყენებენ ცალკე შენახულ credential-ებს.

### ხელსაწყოები

შემდეგი ხელსაწყოები ხელმისაწვდომია Tuist Model Context Protocol სერვერის მეშვეობით:

ყველა ხელსაწყო აქვეყნებს ადამიანისთვის წასაკითხ აღწერას input და output სქემებთან ერთად. წარმატებული ზარები აბრუნებენ სტრუქტურირებულ შინაარსს, რომელიც შეესაბამება გამოცხადებულ output სქემას, პლუს იგივე შედეგი ტექსტად სერიალიზებული იმ კლიენტებისთვის, რომლებიც ჯერ არ იყენებენ სტრუქტურირებულ შინაარსს.

ნაბიჯები ნაგულისხმევად იკრიბება Xcode აგებების დამუშავებისას. ჩაწერილი ნაბიჯის მონაცემები ინახება 90 დღის განმავლობაში. სიის პასუხი შეიცავს `availability`-ს: `available`, როდესაც ჩაწერილი ნაბიჯები არსებობს, მაშინაც კი, თუ ფილტრები არაფერს ემთხვევა; `processing`, როდესაც აგება ჯერ კიდევ მუშავდება და ნაბიჯები ჯერ არ არსებობს; ან `unavailable`, როდესაც ნაბიჯები არ ჩაწერილა ან ვადა გაუვიდა.

იგივე ოპერაციები ხელმისაწვდომია HTTP API-ით `GET /api/projects/{account_handle}/{project_handle}/xcode/builds/{build_id}/steps` და `GET /api/projects/{account_handle}/{project_handle}/xcode/builds/{build_id}/steps/{step_id}` მისამართებზე, იგივე ფილტრებით და პაგინაციით. ორივე მოითხოვს წვდომას აგების პროექტის წაკითხვისთვის.

Gradle და Bazel ნაბიჯების სიები ნაგულისხმევად აბრუნებენ 20 შედეგს (მაქსიმუმ 100), მხარდაჭერილია `search`, ზუსტი `project`, `target`, `category` და `status`, გადახურული `start_ms` / `end_ms` ფილტრები (ბოლო არ არის ჩათვლილი) და `duration_ms` ან `start_ms` დალაგება. გადაეცით დაბრუნებული ID-ები უცვლელად; ისინი შეზღუდულია მათი აგებით. სიები აჩვენებენ `time_origin`-ს და `coverage`-ს. უფრო ძველი Gradle ანგარიშები იყენებენ `first_recorded_timestamp`-ს, რადგან აგების დაწყება არ ატვირთულა. Bazel პროფილები აჩვენებენ ყველა ჩაწერილ ინტერვალს `trace_profile` coverage-ით და `profile_start`-ით, როგორც დროის საწყისით. უფრო ძველი აგებები ბრუნდებიან შენახულ BEP შეჯამებებზე. წყაროს ჩანაწერები ვადას კარგავენ 90 დღის შემდეგ. Bazel დეტალები მოიცავს სანიტიზირებულ action logs-ს, როდესაც გამოქვეყნებულია. Gradle დეტალები წარუმატებელი ამოცანის ან კონფიგურაციის ნაბიჯის შესახებ მოიცავს შეცდომის შეტყობინებას, რომელიც Tuist Gradle პლაგინმა დააბრუნა როგორც `log`: გამონაკლისის შეტყობინება და მისი მიზეზების ჯაჭვი, როგორც Gradle-ის კონსოლი ბეჭდავს მათ, stack traces-ის ან ამოცანის output-ის გარეშე, პროექტის შიგნით არსებული გზები გაკეთებულია ფარდობით, ხოლო credentials და სხვა ლოკალური გზები დაფარულია, მაქსიმუმ 16 KiB ნაბიჯზე და 32 წარუმატებელი ნაბიჯი აგებაზე. სხვა Gradle ნაბიჯებს, პლაგინის უფრო ძველი ვერსიებით შეტყობინებულ აგებებს და credential-free ანგარიშებს აქვთ null `log`. კონფიგურაციის ნაბიჯები ანგარიშობენ `failure`-ს, როდესაც წარუმატებლად დასრულდნენ და `unknown`-ს სხვა შემთხვევაში. `compare_builds` prompt იყენებს ამ coverage-ს სრული Bazel trace-ების განსასხვავებლად შენახული შეჯამებებისგან და მიმართავს აგენტებს ნაბიჯის დეტალებისკენ action შედეგების და logs-ისთვის, სანამ ფართო invocation output-ს შეამოწმებენ.

ერთი ნაბიჯის ხელსაწყოები `get_gradle_build_step` და `get_bazel_build_step` იღებენ ნაბიჯს ID-ით და არ იღებენ დროის ფილტრებს; გამოიყენეთ შესაბამისი სიის ხელსაწყოები ნაბიჯების ფილტრაციისთვის დროის დიაპაზონით.

Bazel ნაბიჯის ID-ები, რომლებიც დაბრუნდა შენახული შეჯამებებიდან, რჩება წასაკითხად, თუ სრული პროფილი მოვა სიის ჩვენებასა და ნაბიჯის მიღებას შორის. ინდექსირებული პროფილი, რომლის ნაბიჯის მონაცემებს ვადა გაუვიდა, ანგარიშობს unavailable-ს. Gradle ნაბიჯების სიები მოიცავს ნულოვანი ხანგრძლივობის cached და skipped ოპერაციებს.

`list_bazel_invocations` ფილტრები არის ზუსტი შესაბამისობები და invocations, რომლებიც ერთსა და იმავე წამში მთავრდება, დალაგებულია invocation ID-ით. ტოტზე უახლესი წარუმატებელი invocation-ის საპოვნელად, გამოიძახეთ ის `status: "failure"`-ით, `git_branch`-ით და `page_size: 1`-ით. REST endpoint `GET /api/projects/{account_handle}/{project_handle}/bazel/invocations` იღებს იგივე ფილტრებს.

დააყენეთ `remote_execution: true` `list_bazel_build_steps`-ზე, რათა დააბრუნოთ მხოლოდ actions უსაფრთხოდ ასოცირებული server phase timings-ით ინდექსირებული პროფილებიდან. სიის და დეტალური პასუხები აჩვენებენ არასავალდებულო nullable `remote_queue_ms`, `remote_input_fetch_ms`, `remote_execution_ms` და `remote_output_upload_ms`-ს. მნიშვნელობები ჯამავს ჩაწერილ ფაზებს, მათ შორის retries-ს action-ის შიგნით; არარსებული ან null მნიშვნელობები ნიშნავს unavailable-ს, არა ნულს. ისინი არიან პროფილის დაკვირვებები, არა გადასახდელი გამოყენება ან ახალი შესრულების მტკიცებულება, რადგან cached server შედეგებს შეიძლება ჰქონდეთ შესრულების მეტამონაცემები. Client uploads გამოტოვებულია. უფრო ძველმა ან ბუნდოვანმა პროფილებმა შეიძლება არ დააბრუნონ შესაბამისი actions მაშინაც კი, თუ remote work შესრულდა. ნაბიჯის REST endpoint იღებს იგივე `remote_execution=true` ფილტრს. dashboard-ის Remote execution tab იყენებს იგივე query-ს და 90-დღიან შენახვას.

ტესტის ლოგები შეიცავს `target_label`-ს და ტესტის შედეგის მცდელობის `status`-ს, საიდანაც ისინი მოდიან, ამიტომ `target_label: "//foo:bar_test"` აბრუნებს მხოლოდ ამ სამიზნის ტესტის ლოგებს. `errors: true` აბრუნებს წარუმატებელი მცდელობების ტესტის ლოგებს და stderr პროგრესის ფრაგმენტებს, რომლებიც შეიცავს ხაზს, რომლითაც Bazel-ის რეპორტიორი იწყება: `ERROR:`, `FAIL:` ან `TIMEOUT:`. პროგრესის გამოსავალი არ არის მიკუთვნებული სამიზნეებისთვის და ლოგებს, რომლებიც დაიწერა მიკუთვნების ჩაწერამდე, აქვთ ცარიელი ველები. წარუმატებელი actions და მათი საკუთარი გამოსავალი ხელმისაწვდომია თითოეული სამიზნისთვის `list_bazel_build_steps`-დან, ხოლო თითოეული ტესტის შემთხვევის წარუმატებლობები — ტესტების გაშვების ინსტრუმენტებიდან.

ეს ინსტრუმენტები თანდათანობით იშლება და აბრუნებენ მონაცემებს მხოლოდ იმ პროექტებისთვის, სადაც ისინი ჩართულია; სხვა პროექტებისთვის ისინი აბრუნებენ შეცდომას ცარიელი შედეგის ნაცვლად. სახე ხელმისაწვდომია მხოლოდ იმ პროექტებისთვის, რომლებიც იყენებენ მის ბილდის toolchain-ს. ინსტრუმენტები იღებენ შეზღუდულ `start_at`/`end_at` ფილტრებს, `environment` (`any`, `ci` ან `local`) და ზუსტ `branch`. `list_build_entities` იღებს `q`-ს; `list_build_entity_history` მხარდაჭერს გამჭვირვალე `after`/`before` cursors-ს. უცნობი დროის ან cache დაკვირვებები რჩება მიუწვდომლად, ნულის ან გამოტოვების ნაცვლად. ისტორია ეხება ჩაწერილ მშობელს და native შესრულებას drill-down-ისთვის არსებული გაშვების ინსტრუმენტების გამოყენებით.

`get_build_entity` მეტრიკები მოიცავს `duration_samples`-ს, დაკვირვებების რაოდენობას ჩაწერილი დროით: ნამდვილი ნულოვანი ხანგრძლივობები ითვლება, გამოტოვებული დრო — არა. ეს რაოდენობა შეიძლება იყოს დაკვირვებების რაოდენობაზე ნაკლები; მიუწვდომელი ხანგრძლივობის სტატისტიკა რჩება null.

Xcode მოდულების ხანგრძლივობა მოდის ბილდის ჟურნალებში გაზომილი target კომპილაციებიდან. მოდულის-cache გადაწყვეტები და targets კომპილაციის სამუშაოს გარეშე არ წვლიან ხანგრძლივობის ნიმუშებში. კომპილაციის დაკვირვებები ეხება Xcode ბილდს; cache მოვლენები ეხება generation ან cache ბრძანებას.

Bazel actions იდენტიფიცირდება target label-ით, mnemonic-ით და კონფიგურირებული პირველადი output-ით, რაც ინარჩუნებს ცალკეულ actions და კონფიგურაციებს განცალკევებულად input-ზე დამოკიდებული cache digests-ის გარეშე. ისტორია იწერს BEP-ით მოხსენებულ შესრულებებს, არა cache ძიებებს ან trace-profile ფაზებს. სრული შესრულების დაფარვა მოითხოვს `--build_event_publish_all_actions`-ს; artifact მიწოდება არის best effort, ამიტომ გამოტოვებული დაკვირვებები არ არის იმის მტკიცებულება, რომ სამუშაო არ შესრულებულა. ძველი Kura payloads სტაბილური იდენტობის ან შესრულების დაწყების გარეშე რჩება მიღებული, მაგრამ არაინდექსირებული. დასრულების დროის გაზომვების არარსებობა რჩება მიუწვდომლად და ნამდვილი ნულოვანი ხანგრძლივობები ითვლება.

Mix მოდულების ხანგრძლივობა ზომავს შემცველი ფაილის კომპილაციას, არა დამოუკიდებლად გაზომილ მოდულის სამუშაოს. Struo actions იყენებს გამოცხადებულ target/capability/index slots-ს, როდესაც კლიენტმა მოახსენა target mapping-ები; დიაგნოსტიკური labels მარტო არ არის სტაბილური იდენტობები. არსებული კლიენტები და run-level ინსტრუმენტები რჩება მხარდაჭერილი უცვლელად.

Cargo crates დაჯგუფებულია ზუსტად ჩაწერილი crate root-ით, სახელით და სახით. Checkout-path ცვლილებებმა შეიძლება გაყოს ისტორიები, ხოლო ბილდის პროფილები, features და target triples არ განირჩევა. ისტორია ზომავს rustc invocations-ს, არა ფაილზე დამოკიდებულ სამუშაოს ან cache hits-ს; არარსებული jobs არ ამყარებს წაშლებას ან სრულ workspace ინვენტარს.

ანალიტიკის წაკითხვებს აქვს შეზღუდული მეხსიერება და შესრულების დრო. თუ query აღემატება ამ ლიმიტებს, ინსტრუმენტი აბრუნებს შეცდომას ცარიელი შედეგის გამოგონების ნაცვლად.

ახალი დაკვირვებები ინდექსირდება განლაგების შემდეგ; ეს ფუნქცია არ ავსებს არსებულ run telemetry-ს. იდენტობის მეტამონაცემები ცოცხლობს ინდივიდუალურ დაკვირვებებზე მეტხანს <.localized_link href="/guides/server/data-retention">მონაცემთა შენახვის პოლიტიკის</.localized_link> ფარგლებში.

### მოვლენები

კლიენტები, რომლებიც იყენებენ stateless `2026-07-28` Model Context Protocol lifecycle-ს, შეუძლიათ გამოიძახონ `events/list` მოვლენებისა და მათი payload სქემების აღმოსაჩენად:

| მოვლენა | როდის იგზავნება | გამოწერის ფილტრი |
|-------|-----------------|---------------------|
| `test_case.marked_flaky` | სატესტო შემთხვევა იცვლება არასტაბილურიდან არასტაბილურად. | `account_handle`, `project_handle` |
| `build.failed` | ლოკალური ან continuous integration Xcode, Gradle ან Bazel ბილდი მთავრდება შეცდომით. | `account_handle`, `project_handle` |
| `test_run.failed` | ლოკალური ან continuous integration ტესტების გაშვება მთავრდება შეცდომით, შერწყმული sharded run-ის ან მიტოვებული run-ის ჩათვლით. | `account_handle`, `project_handle` |
| `ci_job.failed` | Tuist runner job მთავრდება შეცდომით. | `account_handle` |

გამოსაწერად კლიენტი ურეკავს `events/subscribe`-ს მოვლენის სახელით, ზემოთ ჩამოთვლილი handles-ით `arguments`-ში და `webhook` მიწოდებით, რომელიც შეიცავს `https://` callback URL-ს და `whsec_` signing secret-ს. პროექტის მოვლენებს სჭირდება ანგარიშის წევრობა და შესაბამისი ტესტის ან ბილდის მონაცემებზე წვდომა; runner job მოვლენებს სჭირდება ანგარიშის წევრობა და runner-ზე წვდომა. Claimed [`auth.md`](https://workos.com/auth-md) access tokens, claimed account tokens და ბრაუზერის ავტორიზაციის გრანტები შეუძლიათ შექმნან გამოწერები; მიწოდება ჩერდება, როდესაც შესაბამისი credential აღარ არის აქტიური. თითოეულ მომხმარებელს შეუძლია ჰქონდეს მაქსიმუმ 25 აქტიური გამოწერა. Tuist აგზავნის verification challenge-ს callback-ზე გამოწერის შენახვამდე. Callback-მა უნდა დააბრუნოს ობიექტი, რომელიც შეიცავს იგივე `challenge` მნიშვნელობას. გამოწერა ძალაშია შვიდი დღის განმავლობაში, შეიძლება განახლდეს ხელახლა გამოწერით და წყვეტს მიწოდებას, როდესაც მომხმარებლის წვდომა ან credential მოიხსნება. არასავალდებულო `ttlMs` შეზღუდულია ერთ საათსა და 30 დღეს შორის. Tuist ახდენს timed-out callback-ის ხელახლა ცდას და აუქმებს გამოწერას სამი თანმიმდევრული timeout-ის შემდეგ, რომლებიც ხუთ წუთს ფარავს; გამოიწერეთ ხელახლა callback-ის აღდგენის შემდეგ.

როდესაც მოვლენა ხდება, Tuist აგზავნის მის resource identifier-სა და dashboard URL-ს callback-ზე. ბილდისა და ტესტების გაშვების შეცდომები ასევე შეიცავს `is_ci`-ს და `git_branch`-ს, რათა კლიენტებმა შეძლონ ლოკალური შეცდომების იგნორირება ან ფილტრაცია branch-ის მიხედვით. ბილდის მოვლენები შეიცავს `build_system`-ს; runner job მოვლენები შეიცავს როგორც `workflow_job_id`-ს, ისე `workflow_run_id`-ს. მოთხოვნა შეიცავს გამოწერის იდენტიფიკატორსა და [Standard Webhooks](https://www.standardwebhooks.com/) signature headers-ს, რათა კლიენტმა შეძლოს მისი წარმოშობის ვერიფიცირება. Tuist ახდენს შეცდომით დასრულებული მიწოდებების ხელახლა ცდას, ამიტომ კლიენტებმა უნდა გამოიყენონ სტაბილური `eventId` დუბლიკატების გასაფილტრად. Payload გამოტოვებს ტესტების სახელებს, logs-სა და შეცდომის შეტყობინებებს; კლიენტს შეუძლია მიიღოს ეს დეტალები ზემოთ ჩამოთვლილი ინსტრუმენტების მეშვეობით და გადაწყვიტოს, შეატყობინოს თუ არა გუნდს ან დაიწყოს debugging. კლიენტებმა შეუძლიათ შეწყვიტონ მიწოდება `events/unsubscribe`-ით.

#### Gradle ინტეგრაციის prompt ფუნქციები

`integrate_gradle_project` prompt და `get_gradle_integration_guide` ინსტრუმენტი აღწერს სრულ setup workflow-ს. ინსტრუმენტი ასევე არის მითითებული სერვერის initialization instructions-ში, რაც მას აღმოჩენადს ხდის აგენტებისთვის, რომლებიც არ აკეთებენ prompts-ის ჩამონათვალს.

| ფუნქცია | რას აკონფიგურირებს აგენტი |
|---------|---------------------------|
| `remote_cache` | ააქტიურებს Gradle-ის build cache-ს, აკონფიგურირებს Tuist remote cache upload policy-ს და ურჩევს ატვირთვას მხოლოდ continuous integration runners-დან ლოკალური read-only გამოყენებით. |
| `build_insights` | აყენებს Tuist Gradle plugin-ს და აკონფიგურირებს build analytics upload ქცევას საჭიროების შემთხვევაში. |
| `test_insights` | აყენებს Tuist Gradle plugin-ს, რათა Gradle `Test` task შედეგები ავტომატურად აიტვირთოს. |
| `flaky_tests` | გეხმარებათ არასტაბილური ტესტების აღმოჩენის setup-ში, optional Gradle Test Retry plugin-ის გამოყენებაში და test quarantine კონფიგურაციაში. |
| `test_sharding` | ამატებს continuous integration workflow-ს `tuistPrepareTestShards`-ისთვის, shard matrix გენერაციისა და `TUIST_SHARD_INDEX`-ზე დაფუძნებული ტესტების შესრულებისთვის. |

როდესაც `features` გამოტოვებულია, prompt სთხოვს აგენტს გაარკვიოს, რომელი ინტეგრაციები სურს მომხმარებელს ან გამოიტანოს უმცირესი სასარგებლო ნაკრები მოთხოვნიდან Gradle პროექტის რედაქტირებამდე.

`integrate_xcode_project` prompt აღწერს ყველა Xcode ინტეგრაციას, რომელსაც Tuist მხარდაჭერს:

| ფუნქცია | რას აკონფიგურირებს აგენტი |

| `xcode_cache` | აკონფიგურირებს `tuist setup cache`-ს, გენერირებული პროექტის cache პარამეტრებს, Xcode cache-ის ხელით მითითებულ build პარამეტრებს და upload policy-ს, რომელიც შემოიფარგლება მხოლოდ continuous integration runners-ით. |

| `test_insights` | აკონფიგურირებს `tuist inspect test`-ს, სქემის ტესტის post-actions-ს და result bundle გენერაციას continuous integration ტესტების შესრულებისთვის. |
| `test_sharding` | ამატებს Xcode-ის ან გენერირებული პროექტის shard დაგეგმვისა და shard შესრულების workflow-ს `TUIST_SHARD_INDEX`-ის გამოყენებით. |

როდესაც `features` გამოტოვებულია, prompt სთხოვს აგენტს გაარკვიოს, რომელი ინტეგრაციები სურს მომხმარებელს ან გამოიტანოს უმცირესი სასარგებლო ნაკრები მოთხოვნიდან Xcode პროექტის რედაქტირებამდე.
