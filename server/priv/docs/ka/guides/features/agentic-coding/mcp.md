# მოდელის კონტექსტის პროტოკოლი

[Model Context Protocol (MCP)](https://modelcontextprotocol.io/docs/getting-started/intro) არის ღია სტანდარტი, რომელიც საშუალებას აძლევს ხელოვნური ინტელექტის აგენტებს ურთიერთქმედება გარე სერვისებთან და მონაცემთა წყაროებთან. ის უზრუნველყოფს ისეთი აპლიკაციების თავსებადობას Tuist-თან, როგორიცაა [Claude](https://claude.ai/), [Claude Code](https://docs.anthropic.com/en/docs/claude-code), [Codex](https://developers.openai.com/codex/), ასევე რედაქტორების, მაგალითად [Zed](https://zed.dev), [Cursor](https://www.cursor.com) ან [Visual Studio Code](https://code.visualstudio.com).

Tuist განთავსებულია Model Context Protocol-ის სერვერული ბოლოწერტილი მისამართზე `https://tuist.dev/mcp`. მასზე თქვენი კლიენტის მიერთებით, აგენტებს შეუძლიათ წვდომა მოჰპოვონ თქვენს Tuist-ის პროექტის მონაცემებზე, მათ შორის ტესტების ანალიტიკაზე, არასტაბილური ტესტების ანალიზზე და სხვა. უმეტესი ინსტრუმენტი მხოლოდ წაკითხვის რეჟიმშია და შეზღუდულია ავტორიზებული Tuist-ის პროექტის მონაცემებზე. ანგარიშის დაყენების ინსტრუმენტებს შეუძლიათ ანგარიშების ჩამოთვლა, ორგანიზაციების შექმნა, პროექტების შექმნა და არსებული მომხმარებლების დამატება ორგანიზაციებში, თუ ავტორიზებულ მომხმარებელს აქვს შესაბამისი ნებართვები. ყოველი ინსტრუმენტი აცხადებს ანოტაციებს, რომლებიც მიუთითებს, არის თუ არა ის მხოლოდ წაკითხვის რეჟიმში, შეუძლია თუ არა გამოიწვიოს ძნელად შექცევადი ცვლილება და შეუძლია თუ არა შეცვალოს საჯარო ინტერნეტის მდგომარეობა. `update_runner_profile`, `update_notification_rule` და `connect_claude_subscription` აცხადებენ `destructiveHint: true`, რადგან მათ შეუძლიათ ჩაანაცვლონ არსებული კონფიგურაცია ან სერთიფიკატები. ანგარიშის დაყენების ინსტრუმენტები მოითხოვს მომხმარებლის ავტორიზაციას. ისინი არ არის ხელმისაწვდომი პროექტის ტოკენებისთვის ან ჩვეულებრივი ანგარიშის ტოკენებისთვის. როდესაც მომხმარებელი ავტორიზებს კლიენტს ბრაუზერში ან ითხოვს `auth.md` რეგისტრაციას, Tuist ამ სერთიფიკატს აკავშირებს მომხმარებელთან მხოლოდ Model Context Protocol-ის ბოლოწერტილზე, რათა დაყენების ინსტრუმენტებმა შეძლონ მოთხოვნილი სამუშაო პროცესის დასრულება.

Tuist ახორციელებს [2026-07-28 პროტოკოლს](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http). მოთხოვნები არის უმდგომარეო: კლიენტები აგზავნიან თავიანთ პროტოკოლის მეტამონაცემებს ყოველ მოთხოვნასთან ერთად და შეუძლიათ პირდაპირ გამოიძახონ ინსტრუმენტები ინიციალიზაციის გარეშე. `server/discover` აბრუნებს სერვერის იდენტურობას, შესაძლებლობებს, მხარდაჭერილ ვერსიებს და ინსტრუქციებს. არ არსებობს სესიის იდენტიფიკატორები ან დამოუკიდებელი მოვლენათა ნაკადები. კლიენტები, რომლებიც იყენებენ 2025-06-18 ან 2025-03-26 ინიციალიზაციის ნაკადს, კვლავ მხარდაჭერილია; ისინიც მუშაობენ სერვერის სესიების გარეშე.

## Model Context Protocol უნარების წინააღმდეგ

Model Context Protocol-ის ინსტრუმენტებს და <.localized_link href="/guides/features/agentic-coding/skills">უნარებს</.localized_link> შეიძლება ჰქონდეთ გადაფარვა ფუნქციებში. არსებული გადაფარვის გათვალისწინებით, აირჩიეთ ერთი მიდგომა თითოეული სამუშაო პროცესისთვის და გამოიყენეთ ის თანმიმდევრულად, ნაცვლად ორივეს ერთ ნაკადში შერევისა.

კლიენტებისთვის, რომლებიც მხარს უჭერენ პლაგინების ინსტალაციას, გამოიყენეთ <.localized_link href="/guides/features/agentic-coding/plugins">Tuist პლაგინები</.localized_link> ორივეს ერთად დასაყენებლად.

## კონფიგურაცია

დაამატეთ `https://tuist.dev/mcp` როგორც დაშორებული Model Context Protocol სერვერი თქვენს კლიენტში. სერვერის ინიციალიზაციის ინსტრუქციები და საჯარო სერვერის ბარათი აღწერს OAuth 2.0-ს დინამიური კლიენტის რეგისტრაციით და სტანდარტული ბრაუზერის ავტორიზაციის ნაკადით, აგენტებისგან გარე ავტორიზაციის დოკუმენტების მოთხოვნის ან მათი მიყოლის გარეშე. ეს სერვერის დონის ინსტრუქციები ინარჩუნებს სამუშაო პროცესის მითითებებს ზოგადს: ინსტრუმენტის ავტორიზაცია არ ავტორიზებს ადგილობრივ ბრძანების სტრიქონის ინსტრუმენტებს ან აგების სისტემის ინტეგრაციებს, და აგენტებმა უნდა დაადასტურონ მოთხოვნილი ცვლილებები შესაბამისი Tuist-ის ინსტრუმენტების მეშვეობით. აგების სისტემის სპეციფიკური დაყენება და ავტორიზაციის შემოწმებები დოკუმენტირებულია ინტეგრაციის სახელმძღვანელოებში და მოთხოვნებში. Tuist კვლავ აცხადებს როგორც [Open Authorization](https://oauth.net/2/)-ის აღმოჩენის მეტამონაცემებს, ასევე მიმდინარე [auth.md პროტოკოლს](https://workos.com/auth-md) მისამართზე `https://tuist.dev/auth.md` ცალ-ცალკე.

თუ თქვენი რომელიმე ორგანიზაცია აიძულებს ერთჯერად შესვლას (SSO), ბრაუზერში კლიენტის ავტორიზაცია მოითხოვს სესიას, რომელიც შესულია ამ ორგანიზაციის მეშვეობით, და Tuist საჭიროების შემთხვევაში ჯერ პროვაიდერთან გაგზავნით. იხილეთ <.localized_link href="/guides/integrations/authentication/sso#choose-an-enrollment-policy">ერთჯერადი შესვლა</.localized_link>.

ბოლოწერტილი იღებს უმდგომარეო `2026-07-28` Model Context Protocol მოთხოვნის სიცოცხლის ციკლს, მათ შორის `server/discover`-ს, ძველ სესიაზე დაფუძნებულ ციკლთან ერთად. არსებულმა კლიენტებმა შეიძლება გააგრძელონ თავიანთი მიმდინარე მიერთების მეთოდის გამოყენება.

კლიენტებს, რომლებიც მხარს უჭერენ Model Context Protocol მოვლენებს, შეუძლიათ გამოიწერონ პროექტის მოვლენები. იხილეთ [მოვლენები](#events) ხელმისაწვდომი მოვლენებისა და მიწოდების მოთხოვნებისთვის.

კლიენტებს, რომლებიც უკვე მხარს უჭერენ დაშორებულ ბრაუზერის ავტორიზაციას, შეუძლიათ გააგრძელონ ავტორიზაცია ბრაუზერში. კლიენტებს და აგენტებს, რომლებიც მხარს უჭერენ `auth.md`-ს, შეუძლიათ ანონიმურად დარეგისტრირება, წარმოადგინონ სანდო პროვაიდერის იდენტურობის დამტკიცება ან დაიწყონ სერვისით ავტორიზებული ელფოსტის მოთხოვნა. რეგისტრაცია აბრუნებს Tuist-ის მიერ ხელმოწერილ იდენტურობის დამტკიცებას, რომელსაც აგენტი ცვლის სტანდარტულ ტოკენის ბოლოწერტილზე ერთსაათიანი წვდომის ტოკენის სანაცვლოდ. Tuist აქვეყნებს თავის საჯარო ხელმოწერის გასაღებს და მხარს უჭერს სტანდარტულ ტოკენის გაუქმებასა და პროვაიდერის უსაფრთხოების მოვლენების მიწოდებას.

არაავტორიზებულმა აგენტმა უნდა წაიკითხოს `WWW-Authenticate` ჰედერი, რომელიც დაბრუნდა Model Context Protocol-ის ბოლოწერტილის მიერ, მოიძიოს დაცული რესურსის მეტამონაცემები, მოიძიოს ავტორიზაციის სერვერის მეტამონაცემები და მიჰყვეს მის `agent_auth.skill` URL-ს. Tuist ასევე აბრუნებს იგივე ადგილობრივ `auth_md` URL-ს არაავტორიზებული პასუხის სხეულში, რათა ენის მოდელზე დაფუძნებულმა კლიენტებმა შეძლონ ნაკადის აღმოჩენა ნატიური კლიენტის ინტეგრაციაზე დაყრდნობის გარეშე. განლაგების ადგილობრივი დოკუმენტი არის ჭეშმარიტების წყარო ბოლოწერტილების სახელების, მოთხოვნის სხეულების, მოთხოვნის გამოკითხვისა და დამტკიცების გაცვლისთვის.

სანამ აგენტი დაიწყებს ელფოსტის მოთხოვნას, მან უნდა სთხოვოს მომხმარებელს დაადასტუროს ელფოსტის მისამართი მათი Tuist ანგარიშისთვის. მან არ უნდა გამოიტანოს ეს მისამართი პროვაიდერის პროფილიდან, Git კონფიგურაციიდან, გარემოს ცვლადიდან ან სესიის მეტამონაცემებიდან.

ბოლოწერტილი იყენებს `mcp` სკოპის ჯგუფს. ანონიმურმა წინასწარ-მოთხოვნის სერთიფიკატს შეუძლია აღმოაჩინოს შესაძლებლობები და წაიკითხოს საჯარო ინტეგრაციის მითითებები, მაგრამ ის არ განიხილება როგორც შესული მომხმარებელი. ბრაუზერის ავტორიზაციის ან მოთხოვნის შემდეგ, სერთიფიკატი არის მომხმარებელზე შეზღუდული და ყოველი ინსტრუმენტი იყენებს იგივე ავტორიზაციის შემოწმებებს, რასაც დაფის ინტერფეისი. დეტალებისთვის იხილეთ <.localized_link href="/guides/server/authentication#scope-groups">სკოპის ჯგუფების დოკუმენტაცია</.localized_link>.

ინსტრუმენტები გარდაიქმნება იმ პროექტებზე, რომელთა წაკითხვაც ავტორიზებულ მომხმარებელს უკვე შეუძლია. Xcode და Gradle აგების ინსტრუმენტები იღებენ აგების UUID-ს ან დაფის URL-ს. UUID-მ უნდა მოახდინოს ზუსტად ერთი პროექტის იდენტიფიცირება; თუ ის ჩნდება რამდენიმე პროექტში, ინსტრუმენტი აბრუნებს „არ არის ნაპოვნი“-ს, ნაცვლად სხვა პროექტის ანგარიშის შერჩევისა. პროექტზე შეზღუდული დაფისა და API-ს წაკითხვები რჩება ხელმისაწვდომი. მოხსენებული მოქმედის იდენტიფიკატორები არის დაუდასტურებელი ლეიბლები, არა სერთიფიკატები ან დამატებითი წვდომის უფლებები.

აგების სიისა და დეტალური ინსტრუმენტები აჩვენებენ ოფციურ `tuist_version` მეტამონაცემებს: Xcode-ისა და Cargo-სთვის — მომხსენებელ Tuist CLI-ს, Gradle-ისთვის — Tuist Gradle პლაგინს, ხოლო Mix-ისთვის — `tuist_ex` ბიბლიოთეკას. Xcode ასევე აჩვენებს `tuist_generation_version`-ს მის დაკავშირებული პროექტის გენერაციის მოვლენიდან, რომელიც შეიძლება განსხვავდებოდეს ატვირთვის CLI-ისგან. გამოტოვებული დაკვირვებები არის null, არა სერვერიდან ან სხვა ანგარიშიდან გამოყვანილი. Bazel იყენებს თავის არსებულ `bazel_version`-ს; Once-ის გაშვების დეტალები აჩვენებს `once_version`-ს. ეს ველები აღწერენ მოხსენებულ ვერსიებს, არა დადასტურებულ იდენტობას ან სადენის კონტრაქტის ვერსიებს. REST აგების ბოლოწერტილები აჩვენებენ იგივე მეტამონაცემებს. არსებული ინტეგრაციისა და ციმციმა ტესტების უნარები არ არის დამოკიდებული ვერსიის ველებზე და არ საჭიროებს სამუშაო ნაკადის ცვლილებებს.

Tuist-ის ოპერატორები, რომლებიც იკვლევენ მომხმარებლის ანგარიშს, ამას აკეთებენ Tuist-ის შიდა ოპერაციული ინსტრუმენტების მეშვეობით, რომელიც იწერს ყოველ ზარს; ამ ბოლოწერტილთან პირდაპირი კავშირი არ იძლევა წვდომას მომხმარებლის საკუთარი წევრობის ფარგლებს გარეთ.

### Pulse

Pulse აჩვენებს ოთხ მხოლოდ წასაკითხ ინსტრუმენტს, რომლებიც მიმართულია `account_handle`-ით:

| ინსტრუმენტი | REST ეკვივალენტი `/api/accounts/:account_handle/pulse`-ის ქვეშ |
| --- | --- |
| `query_pulse` | `GET /:signal` |
| `get_pulse_analytics` | `GET /:signal/analytics` |
| `get_pulse_error_issue` | `GET /errors/issues/:issue_id` |
| `get_pulse_error_event` | `GET /errors/issues/:issue_id/events/:event_id` |

Pulse შეზღუდულია სერვერზე კონფიგურირებული ორგანიზაციის მიმდინარე წევრებისთვის, მაშინაც კი, თუ ანგარიში ან პროექტი საჯაროა. ის მოითხოვს მომხმარებლის ავტორიზაციას ან მომხმარებელთან დაკავშირებულ `mcp` სერთიფიკატს და ანგარიშის წაკითხვის ავტორიზაციას. პროექტის ტოკენები, ჩვეულებრივი ანგარიშის ტოკენები, ანონიმური რეგისტრაციები და ოპერატორის წვდომა ორგანიზაციის წევრობის გარეშე არ იძლევა Pulse-ზე წვდომას. სერთიფიკატებს არ შეუძლიათ აირჩიონ სხვა backend ან telemetry tenant. ბრაუზერის აგენტები იღებენ ამ ოთხ ინსტრუმენტს მხოლოდ Pulse-ის გვერდებზე, ამ გვერდის ანგარიშის სკოპის ფარგლებში.

REST მოითხოვს მომხმარებლის სერთიფიკატს. OAuth და `auth.md` მომხმარებლის ასოციაციები ხელმისაწვდომია მხოლოდ `/mcp` ბოლოწერტილზე; ანგარიშის სერთიფიკატი მიმდინარე მომხმარებლის გარეშე უარყოფილია, მიუხედავად დაკავშირებული ანგარიშის წევრობისა ან ხილვადობისა.

`query_pulse` იღებს `signal`-ს (`metrics`, `logs`, `traces` ან `errors`), ოფციურ `query`-ს და `range`-ს (`15m`, `1h`, `6h` ან `24h`, ნაგულისხმევი `1h`). მეტრიკები, ლოგები და ტრეისები იღებენ ნატიურ PromQL, LogQL და TraceQL გამოსახულებებს. შეცდომები აბრუნებენ დაჯგუფებულ საკითხებს; მათი `query` არის ლიტერალური სათაურის ძიება, არა ნატიური გამოსახულება. ცხრილები იღებენ `search`-ს, `page`-ს (ნაგულისხმევი `1`), `page_size`-ს (`1`–`100`, ნაგულისხმევი `20`), `sort_by`-ს და `sort_order`-ს (`asc` ან `desc`). დალაგების სვეტები დამოკიდებულია სიგნალზე და ჩამოთვლილია ინსტრუმენტის სქემაში. ფილტრები მოიცავს `service`-ს, ლოგის `level`-ს და შეცდომის `project`-ს, `environment`-ს და `release`-ს. ფილტრის ოპერატორები იყენებენ შესაბამის `_op` არგუმენტს (`eq`, `contains` ან `not_contains`), ნაგულისხმევად ზუსტი ტოლობით.

დალაგების სვეტებია `name`/`value` მეტრიკებისთვის; `timestamp`/`service`/`level`/`message`/`trace_id` ლოგებისთვის; `timestamp`/`service`/`name`/`duration_ms`/`trace_id` ტრეისებისთვის; და `last_seen_ns`/`first_seen_ns`/`count`/`title`/`service`/`project`/`issue_id` შეცდომებისთვის. დაფა განზრახ აჩვენებს ქვესიმრავლეს; API და ინსტრუმენტები იღებენ სრულ სიას თითოეული სიგნალისთვის.

ცხრილის პასუხები შეიცავს `rows`-ს, `series`-ს, `warnings`-ს და `meta`-ს. დაფურცვლის მეტამონაცემები მოიცავს `page`-ს, `page_size`-ს, `total_count`-ს, `total_pages`-ს, `has_next_page`-ს, `has_previous_page`-ს და `end_at`-ს. გადაეცით დაბრუნებული ISO8601 `end_at` შემდგომ გვერდებთან ერთად, რათა შეინარჩუნოთ კითხვის ფანჯარა. შედეგის ლიმიტის შეცდომები მოითხოვენ კითხვის ან დროის დიაპაზონის შევიწროვებას, არა პასუხის როგორც ცარიელი ცხრილის განხილვას.

ლოგები და ტრეისები ამოწმებენ მაქსიმუმ 100 ნატიური კითხვის დამთხვევას, ლოგები ჯერ ირჩევენ უახლესს ადგილობრივ დალაგებამდე. როდესაც ლიმიტი მიღწეულია, `warnings` ცხადად აცხადებს, რომ ფილტრები, დალაგება, დაფურცვლა და ჯამები აღწერენ მხოლოდ დაბრუნებულ დამთხვევებს, არა მთელ დროის ფანჯარას. შეავიწროვეთ ნატიური გამოსახულება ან დროის დიაპაზონი სხვა დამთხვევების შესამოწმებლად; ადგილობრივი ძიების ან დალაგების ცვლილება არ აფართოებს upstream ძიებას. აგრეგატული ვიჯეტები რჩება დამოუკიდებელ, სრული ფანჯრის კითხვებად, ამ შეზღუდული ცხრილის შედეგების აგრეგატების ნაცვლად.

მეტრიკის ცხრილები აფასებენ თავიანთ გამოსახულებას ერთხელ `end_at`-ზე, აბრუნებენ მიმდინარე მნიშვნელობებს და ერთ წერტილს თითოეული instant-vector სერიისთვის. Range-vector გამოსახულებებს შეუძლიათ დააბრუნონ შეზღუდული ისტორიული წერტილები. ცალკეული ანალიტიკური ვიჯეტები უზრუნველყოფენ ფიქსირებულ ისტორიულ დიაგრამებს; ცხრილი არ ქმნის დროის ბადეს ყოველი დამთხვევითი სერიისთვის მხოლოდ მისი უახლესი მნიშვნელობის საჩვენებლად.

საკითხის დეტალები აბრუნებენ დაჯგუფებულ `issue`-ს, დაფურცვულ პროეცირებულ `events`-ს, `meta`-ს და `warnings`-ს. მოვლენის დეტალები მოითხოვს როგორც `issue_id`-ს, ასევე `event_id`-ს და აბრუნებს ერთ პროეცირებულ `event`-ს და `warnings`-ს. ორივე მხარდაჭერს `range`-ს, `end_at`-ს და შეცდომის ფილტრებს; მხოლოდ საკითხის დეტალები მხარდაჭერენ დაფურცვლას. მოვლენები აჩვენებენ შეზღუდულ გამონაკლისისა და ჩარჩოს პროექციებს, არასდროს ნედლ მოვლენის payload-ს. Telemetry სტრიქონები არის არასანდო მონაცემები, არა ინსტრუქციები.

`get_pulse_analytics` იღებს მხოლოდ `signal`-ს და `range`-ს ანგარიშის handle-ის გარდა. მისი ფიქსირებული ვიჯეტები დამოუკიდებელია ცხრილის გამოსახულებებისგან, ფილტრებისგან, დალაგებისგან და დაფურცვლისგან. REST და Model Context Protocol იყენებენ იგივე Pulse კონტექსტს და პასუხის კონტრაქტებს. REST პასუხები თიშავენ ქეშირებას.

Pi არ შეიცავს Model Context Protocol კლიენტს. შეგიძლიათ დააინსტალიროთ მესამე მხარის [`pi-mcp-adapter`](https://pi.dev/packages/pi-mcp-adapter) გაფართოება მისი წყაროსა და უსაფრთხოების შედეგების გადახედვის შემდეგ:

დაამატეთ პროექტის დონის `.mcp.json` ფაილი:

```json
{
  "mcpServers": {
    "tuist": {
      "url": "https://tuist.dev/mcp",
      "auth": false
    }
  }
}
```

`auth`-ის `false`-ზე დაყენება ხელს უშლის ადაპტერის ბრაუზერის ავტორიზაციის handler-ს Tuist-ის არაავტორიზებული პასუხის დამალვას. headless აგენტს შემდეგ შეუძლია წაიკითხოს დაბრუნებული `auth_md` URL და მიჰყვეს Tuist-ის რეგისტრაციის, იდენტობის დამოწმების გაცვლისა და მოთხოვნის polling ნაკადს. დააკონფიგურირეთ გაცვლილი access token როგორც bearer token ან მიეცით აგენტს პირდაპირ გააკეთოს ავტორიზებული Model Context Protocol ზარები.

თუ ბრაუზერის ავტორიზაციას ამჯობინებთ, დააყენეთ `auth` მნიშვნელობად `"oauth"`. ამ ნაკადისთვის, შეინარჩუნეთ ერთი პროცესი ცოცხალი Pi-ს [remote procedure call mode](https://pi.dev/docs/latest/rpc)-ით, სანამ ავტორიზაცია დასრულდება:

```bash
pi --mode rpc
```

Tuist-ის ავტორიზაციის სერვერის მეტამონაცემები პირდაპირ მიუთითებს განლაგების საკუთარ `/auth.md`-ზე, რომელიც შეიცავს ზუსტ მოთხოვნისა და polling-ის სტრუქტურებს.

## აგენტები Amp orbs-ში და Claude Code cloud სესიებში

კოდირების აგენტები, რომლებიც მუშაობენ sandbox-ებში და დაკავშირებულია Tuist ანგარიშთან, შეუძლიათ ავტორიზაცია endpoint-ზე საკუთარი იდენტობის ტოკენით, ბრაუზერის ან შენახული Tuist მონაცემების გარეშე:

- **Amp orbs** Amp სამუშაო სივრცის ან პროექტისთვის, რომელიც ანგარიშმა დააკავშირა **Settings → Integrations → Amp** ქვეშ, აგზავნის orb-ის ID ტოკენს. Amp-ში, დააყენეთ სერვერის `Authorization` ჰედერი მნიშვნელობად `Bearer ${amp:id-token}`. Amp ქმნის ტოკენს სერვერის URL-ის წყაროსთვის, ამიტომ URL უნდა იყოს ამ Tuist ინსტანციის საკუთარი მისამართი და ანახლებს მას ვადის გასვლამდე. სხვა წყაროსთვის შექმნილი ტოკენები უარყოფილია.
- **Claude Code cloud sessions** დაკავშირებული Claude Code გარემოდან აგზავნის სესიის ტოკენს, რომელსაც Tuist გადასცემს მათ როგორც `TUIST_OIDC_TOKEN`. დააყენეთ ჰედერი მნიშვნელობად `Bearer ${TUIST_OIDC_TOKEN}`.

Tuist-ის Linux sandbox-ები მოდის ამ კონფიგურაციით: `tuist` სერვერი Amp-ის მომხმარებლის პარამეტრებში და Claude Code-ის მომხმარებლის კონფიგურაციაში, ორივე მიმართულია `${TUIST_URL}/mcp`-ზე, Tuist CLI-თან და უნართან ერთად, რომელიც ეუბნება აგენტს, როდის შეამოწმოს შედეგები პროექტის ისტორიის მიხედვით. სხვაგან, თავად დაამატეთ სერვერი ზემოთ მოცემული ჰედერით.

ეს ტოკენები იძლევა მხოლოდ წაკითხვის უფლებას დაკავშირებული ანგარიშის ყველა პროექტზე: ისინი ატარებენ `mcp` ჯგუფის წაკითხვის სკოპებს და არ აქვთ ისეთი სკოპები, რომლებიც ქმნიან, ცვლიან ან შლიან მონაცემებს, როგორიცაა ტესტების ჩუმად ჩატარება ან გამოტოვება. სამუშაო სივრცის ან გარემოს გათიშვა წყვეტს წვდომას შემდეგ მოთხოვნაზე, და წვდომა არასდროს ძლებს ტოკენზე მეტ ხანს. Amp სამუშაო სივრცე, რომელიც დაკავშირებულია რამდენიმე Tuist ანგარიშთან, უარყოფილია, რადგან მის ტოკენში ერთი კონკრეტული ანგარიში არ არის მითითებული. როდესაც კავშირი არ არსებობს, არაავტორიზებული პასუხის `error_description` აღნიშნავს ამას.

ეს მხოლოდ წაკითხვის უფლება ვრცელდება მხოლოდ Model Context Protocol endpoint-ზე. ბრძანების სტრიქონის ინსტრუმენტი და build-system ინტეგრაციები იმავე sandbox-ში კვლავ ცვლიან ტოკენს კავშირის CI წვდომისთვის.

## WebMCP

ბრაუზერებში, რომლებიც მხარს უჭერენ [WebMCP](https://webmachinelearning.github.io/webmcp)-ს, Tuist-ის გვერდები რეგისტრირებენ ინსტრუმენტებს `document.modelContext`-ით, რათა ბრაუზერში ჩაშენებულმა აგენტებმა შეძლონ მათი გამოძახება დამატებითი კონფიგურაციის გარეშე. ზარები სრულდება Tuist სერვერზე.

- **Website and documentation pages** რეგისტრირებენ დოკუმენტაციისა და წყაროს ინსტრუმენტებს (`search_tuist`, `search_tuist_code`, `list_tuist_files` და `read_tuist_file`). შესვლა არ არის საჭირო.
- **An account's dashboard pages**, როდესაც შესული ხართ, რეგისტრირებენ Tuist-ის მხოლოდ წაკითხვის ინსტრუმენტებს ამ ანგარიშისთვის. თითოეული გვერდი რეგისტრირებს მხოლოდ იმ ინსტრუმენტებს, რასაც ის აჩვენებს, პროექტის build system-ისთვის: Gradle პროექტის builds გვერდი იღებს Gradle build ინსტრუმენტებს, მისი test გვერდები — test და coverage ინსტრუმენტებს, runners გვერდები — runner ინსტრუმენტებს, ხოლო sandboxes გვერდები — sandbox ინსტრუმენტებს. თქვენი პირადი ანგარიშის AI settings გვერდის Subscriptions სექცია იღებს `list_ai_subscriptions`-ს, რომელიც პასუხობს მხოლოდ თქვენს საკუთარ ანგარიშზე. ყველა გვერდი ასევე იღებს დოკუმენტაციის ინსტრუმენტებს, `list_projects` და `get_project`. ინსტრუმენტები მუშაობენ შესული მომხმარებლის სახელით, ამიტომ ისინი წვდებიან მხოლოდ იმ მონაცემებს, რომელთა წაკითხვაც შეგიძლიათ dashboard-ში, და მხოლოდ იმ ანგარიშს, რომელსაც უყურებთ. როდესაც გადადიხართ სხვა გვერდზე ან ანგარიშზე, ინსტრუმენტები იცვლება იმ გვერდის შესაბამისი ინსტრუმენტებით.

ინსტრუმენტები, რომლებიც ქმნიან, ცვლიან ან შლიან მონაცემებს, არ არის ხელმისაწვდომი WebMCP-ით, რადგან ბრაუზერის აგენტი იღებს ინსტრუმენტებს თქვენი დამატების გარეშე და კითხულობს builds და tests-ის მიერ შექმნილ კონტენტს. დააკავშირეთ MCP კლიენტი `/mcp` endpoint-თან ამ ინსტრუმენტების გამოსაყენებლად.

თუ ორგანიზაცია აიძულებს ერთჯერად შესვლას (single sign-on), შედით dashboard-ში მისი პროვაიდერის მეშვეობით, რათა გამოიყენოთ მისი ინსტრუმენტები.

## Build-system ინტეგრაციები იყენებენ ორ მონაცემს

მონაცემი, რომელიც გამოიყენება Model Context Protocol ინსტრუმენტებისთვის, არ ავტორიზებს Gradle პლაგინს ან Bazel-ის remote სერვისებს. სანამ აგენტი შეცვლის ან შეამოწმებს Gradle ან Bazel ინტეგრაციას, მან უნდა გაუშვას:

```bash
tuist auth whoami --url https://tuist.dev
```

თუ ეს ბრძანება არ არის ავტორიზებული, აგენტმა უნდა შეწყვიტოს მუშაობა და სთხოვოს მომხმარებელს გაუშვას:

```bash
tuist auth login --url https://tuist.dev
```

ლოკალური ან self-hosted განლაგებისთვის, შეცვალეთ URL ორივე ბრძანებაში და `tuist.toml`-ში. შეინარჩუნეთ hostname-ის მართლწერა იდენტური ყველგან. მაგალითად, `localhost` და `127.0.0.1` იყენებენ ცალკე შენახულ მონაცემებს.


## შესაძლებლობები

### ინსტრუმენტები

შემდეგი ინსტრუმენტები ხელმისაწვდომია Tuist Model Context Protocol სერვერის მეშვეობით:

ყველა ინსტრუმენტი აქვეყნებს ადამიანისთვის წასაკითხ აღწერას ცალსახა input და output სქემებთან ერთად. წარმატებული ზარები აბრუნებენ სტრუქტურირებულ კონტენტს, რომელიც შეესაბამება გამოცხადებულ output სქემას, პლუს იგივე შედეგი ტექსტად სერიალიზებული იმ კლიენტებისთვის, რომლებიც ჯერ არ იყენებენ სტრუქტურირებულ კონტენტს.

ინსტრუმენტები, რომლებიც იღებენ ერთი ჩანაწერის იდენტიფიკატორს, როგორიცაა `build_run_id`, `test_run_id`, `test_case_id`, `bundle_id`, `run_id`, `generation_id`, ან `cache_run_id`, ასევე იღებენ ამ ჩანაწერის Tuist dashboard URL-ს. ჩასვით URL პირდაპირ ბრაუზერიდან, იდენტიფიკატორის ამოღების ნაცვლად.

#### დოკუმენტაციისა და საზოგადოების ძებნა

ნაბიჯები ნაგულისხმევად იკრიბება Xcode ბილდების დამუშავებისას. ჩაწერილი ნაბიჯის მონაცემები ინახება 90 დღის განმავლობაში. სიის პასუხი შეიცავს `availability`: `available`, როცა ჩაწერილი ნაბიჯები არსებობს, მაშინაც კი, თუ ფილტრები არაფერს ემთხვევა; `processing`, როცა ბილდი ჯერ კიდევ მუშავდება და ჯერ არ აქვს ნაბიჯები; ან `unavailable`, როცა ნაბიჯები არ ჩაწერილა ან ამოიწურა.

იგივე ოპერაციები ხელმისაწვდომია HTTP API-ზე `GET /api/projects/{account_handle}/{project_handle}/xcode/builds/{build_id}/steps` და `GET /api/projects/{account_handle}/{project_handle}/xcode/builds/{build_id}/steps/{step_id}` მისამართებზე, იგივე ფილტრებითა და pagination-ით. ორივე მოითხოვს წვდომას ბილდის პროექტის წაკითხვაზე.

Gradle და Bazel ნაბიჯების სიები ნაგულისხმევად აბრუნებენ 20 შედეგს (მაქსიმუმ 100), მხარდაჭერილია `search`, ზუსტი `project`, `target`, `category` და `status`, გადახურვადი `start_ms` / `end_ms` ფილტრები (ბოლო გამორიცხულია) და `duration_ms` ან `start_ms` დალაგება. გადაეცით დაბრუნებული ID-ები უცვლელად; ისინი შეზღუდულია მათი ბილდის ფარგლებში. სიები აჩვენებს `time_origin` და `coverage`. ძველი Gradle ანგარიშები იყენებენ `first_recorded_timestamp`-ს, რადგან ბილდის დაწყება არ ატვირთულა. Bazel პროფილები აჩვენებს ყველა ჩაწერილ ინტერვალს `trace_profile` დაფარვით და `profile_start`-ს როგორც დროის საწყისს. ძველი ბილდები მიმართავენ შენახულ BEP შეჯამებებს. წყაროს ჩანაწერები იწურება 90 დღის შემდეგ. Bazel დეტალები შეიცავს სანიტიზებულ action ლოგებს, როცა ისინი გამოქვეყნებულია. წარუმატებელი task-ის ან კონფიგურაციის ნაბიჯის Gradle დეტალები შეიცავს შეცდომის შეტყობინებას, რომელიც Tuist Gradle plugin-მა დააბრუნა როგორც `log`: გამონაკლისის შეტყობინება და მისი მიზეზების ჯაჭვი, როგორც Gradle-ის კონსოლი ბეჭდავს მათ, stack trace-ების ან task output-ის გარეშე, პროექტის შიგნით არსებული გზები გაკეთებულია ფარდობით, ხოლო credential-ები და სხვა ლოკალური გზები დამალულია, მაქსიმუმ 16 KiB ნაბიჯზე და 32 წარუმატებელი ნაბიჯი ბილდზე. სხვა Gradle ნაბიჯებს, ძველი plugin ვერსიების მიერ მოხსენებულ ბილდებს და credential-ების გარეშე ანგარიშებს აქვთ null `log`. კონფიგურაციის ნაბიჯები ანგარიშობენ `failure`-ს, როცა ისინი წარუმატებელია და `unknown`-ს სხვა შემთხვევაში. `compare_builds` prompt იყენებს ამ დაფარვას სრული Bazel trace-ების განსასხვავებლად შენახული შეჯამებებისგან და მიმართავს agent-ებს ნაბიჯის დეტალებისკენ action-ების შედეგებისა და ლოგებისთვის, სანამ უფრო ფართო invocation output-ს შეამოწმებენ.

ერთ-ნაბიჯიანი ინსტრუმენტები `get_gradle_build_step` და `get_bazel_build_step` იღებენ ნაბიჯს ID-ით და არ იღებენ დროის ფილტრებს; გამოიყენეთ შესაბამისი სიის ინსტრუმენტები ნაბიჯების ფილტრაციისთვის დროის დიაპაზონით.

შენახული შეჯამებებიდან დაბრუნებული Bazel ნაბიჯის ID-ები რჩება წასაკითხად, თუ სრული პროფილი მოდის სიის ჩამოთვლასა და ნაბიჯის მიღებას შორის. ინდექსირებული პროფილი, რომლის ნაბიჯის მონაცემები ამოიწურა, ანგარიშობს ხელმიუწვდომლობას. Gradle ნაბიჯების სიები შეიცავს ნულოვანი ხანგრძლივობის cached და გამოტოვებულ ოპერაციებს.

REST endpoint `GET /api/projects/{account_handle}/{project_handle}/bazel/invocations` იღებს იგივე ფილტრებს.

ტესტის ლოგები შეიცავს `target_label`-ს და მცდელობის `status`-ს იმ ტესტის შედეგიდან, საიდანაც ისინი მოვიდნენ, ასე რომ `target_label: "//foo:bar_test"` აბრუნებს მხოლოდ იმ სამიზნის ტესტის ლოგებს. `errors: true` აბრუნებს წარუმატებელი მცდელობების ტესტის ლოგებს და stderr პროგრესის ნაწილებს, რომლებიც შეიცავს ხაზს, რომელიც Bazel-ის მომხსენებელი იწყება `ERROR:`-ით, `FAIL:`-ით ან `TIMEOUT:`-ით. პროგრესის output არ არის მიკუთვნებული სამიზნეებისთვის და ლოგებს, რომლებიც დაიწერა მიკუთვნების ჩაწერამდე, აქვთ ცარიელი ველები. წარუმატებელი actions და მათი own output ხელმისაწვდომია თითოეული სამიზნისთვის `list_bazel_build_steps`-დან და თითოეული ტესტის საქმის წარუმატებლობები ტესტების გაშვების ინსტრუმენტებიდან.

#### ბილდის trace-ები

| ინსტრუმენტი | აღწერა | მოთხოვნილი პარამეტრები |

`build_id` არის ბილდის შესრულების ID (Bazel-ისთვის — invocation ID) ან ბილდის dashboard URL. დაბრუნებული `trace_url` ემსახურება [Chrome Trace Event](https://docs.google.com/document/d/1CvAClvFfyA5R-PhYUmn5OOQtYMH4h6I0nSsKchNAySU) JSON ფაილს. ნებისმიერს, ვინც ფლობს ამ ბმულს, შეუძლია ჩამოტვირთოს ამ ბილდის trace სხვა რწმუნებულებების გარეშე `expires_at`-მდე, რაც ზარის შემდეგ ერთ საათია. აგენტებს შეუძლიათ ჩამოტვირთონ ის `curl`-ით, გადასცენ თქვენ Perfetto-ში გასახსნელად ან მოიკვლიონ Perfetto-ს `trace_processor`-ით. Trace შეიცავს ჩაწერილ ნაბიჯებს, დალაგებულ ზოლებად პარალელიზმის მიხედვით, ტრეკს, რომელიც მოიცავს მთელ ბილდს, და CPU და მეხსიერების მრიცხველებს, როცა ბილდი იწერდა მანქანის მეტრიკებს. ის ინახავს იმავე მონაცემებს, რასაც ზემოთ მოყვანილი ნაბიჯის ინსტრუმენტები, ლოგების გარეშე. Dashboard გთავაზობთ იმავე ფაილს თითოეული ბილდის Timeline ტაბიდან.

ეს ინსტრუმენტები თანდათანობით იშლება და აბრუნებენ მონაცემებს მხოლოდ იმ პროექტებისთვის, სადაც ისინი ჩართულია; სხვა პროექტებისთვის ისინი აბრუნებენ შეცდომას ცარიელი შედეგის ნაცვლად. სახეობა ხელმისაწვდომია მხოლოდ იმ პროექტებისთვის, რომლებიც იყენებენ მის build toolchain-ს. ინსტრუმენტები იღებენ შეზღუდულ `start_at`/`end_at` ფილტრებს, `environment` (`any`, `ci` ან `local`) და ზუსტ `branch`-ს. `list_build_entities` იღებს `q`-ს; `list_build_entity_history` მხარდაჭერს opaque `after`/`before` cursors-ებს. უცნობი დროის ან cache დაკვირვებები რჩება ხელმიუწვდომელი ნულის ან გამოტოვების ნაცვლად. ისტორია მიუთითებს ჩაწერილ მშობელზე და native შესრულებაზე დეტალური კვლევისთვის არსებული run ინსტრუმენტების გამოყენებით.

`get_build_entity` მეტრიკები მოიცავს `duration_samples`-ს, დაკვირვებების რაოდენობას ჩაწერილი დროით: ნამდვილი ნულოვანი ხანგრძლივობები ითვლება, აკლია დრო — არა. ეს რაოდენობა შეიძლება იყოს დაკვირვებების რაოდენობაზე ნაკლები; ხელმიუწვდომელი ხანგრძლივობის სტატისტიკა რჩება null.

Xcode module-ის ხანგრძლივობები მოდის გაზომილი target კომპილაციებიდან ბილდის ლოგებში. Module-cache ამოხსნები და targets კომპილაციის სამუშაოს გარეშე არ მონაწილეობენ ხანგრძლივობის ნიმუშებში. კომპილაციის დაკვირვებები მიუთითებენ Xcode ბილდზე; cache მოვლენები მიუთითებენ გენერაციის ან cache ბრძანებაზე.

Bazel actions იდენტიფიცირდება target label-ით, mnemonic-ით და კონფიგურირებული primary output-ით, რაც ინარჩუნებს ცალკეულ actions და კონფიგურაციებს განცალკევებულს input-ზე დამოკიდებული cache digest-ების გარეშე. ისტორია იწერს BEP-ით მოხსენებულ შესრულებებს, არა cache ძიებებს ან trace-profile ფაზებს. სრული შესრულების დაფარვა მოითხოვს `--build_event_publish_all_actions`-ს; artifact მიწოდება არის best effort, ამიტომ აკლია დაკვირვებები არ არის მტკიცებულება, რომ სამუშაო არ შესრულებულა. უფრო ძველი Kura payloads სტაბილური იდენტობის ან შესრულების დასაწყისის გარეშე რჩება მიღებული, მაგრამ არაინდექსირებული. აკლია დასასრულის დროის გაზომვები რჩება ხელმიუწვდომელი და ნამდვილი ნულოვანი ხანგრძლივობები ითვლება.

Mix module-ის ხანგრძლივობები ზომავენ შემცველი ფაილის კომპილაციას, არა დამოუკიდებლად გაზომილ module სამუშაოს. Once actions იყენებენ გამოცხადებულ target/capability/index სლოტებს, როცა კლიენტმა მოახსენა target mapping-ები; დიაგნოსტიკის label-ები მარტო არ არის სტაბილური იდენტობები. არსებული კლიენტები და run-level ინსტრუმენტები რჩება მხარდაჭერილი უცვლელად.

Cargo crates დაჯგუფებულია ზუსტად ჩაწერილი crate root-ის, სახელის და სახეობის მიხედვით. Checkout-path ცვლილებებმა შეიძლება გაყოს ისტორიები, და ბილდის პროფილები, features და target triples არ განირჩევა. ისტორია ზომავს rustc invocations-ებს, არა ფაილზე სამუშაოს ან cache hits-ებს; აკლია სამუშაოები არ ამყარებს წაშლებს ან სრულ workspace ინვენტარს.

ანალიტიკის წაკითხვებს აქვს შეზღუდული მეხსიერება და შესრულების დრო. თუ მოთხოვნა აღემატება ამ ლიმიტებს, ინსტრუმენტი აბრუნებს შეცდომას ცარიელი შედეგის გამოგონების ნაცვლად.

ახალი დაკვირვებები ინდექსირდება განლაგების შემდეგ; ეს ფუნქცია არ ავსებს უკვე არსებულ run telemetry-ს. იდენტობის მეტამონაცემები ინდივიდუალურ დაკვირვებებზე უფრო დიდხანს რჩება <.localized_link href="/guides/server/data-retention">მონაცემთა შენახვის პოლიტიკის</.localized_link> შესაბამისად.

### მოვლენები

კლიენტები, რომლებიც იყენებენ stateless `2026-07-28` Model Context Protocol lifecycle-ს, შეუძლიათ გამოიძახონ `events/list` მოვლენებისა და მათი payload-ის სქემების აღმოსაჩენად:

| მოვლენა | როდის იგზავნება | გამოწერის ფილტრი |
|-------|-----------------|---------------------|
| `test_case.marked_flaky` | სატესტო შემთხვევა იცვლება არასტაბილურიდან სტაბილურზე. | `account_handle`, `project_handle` |
| `build.failed` | ლოკალური ან continuous integration Xcode, Gradle ან Bazel ბილდი მთავრდება შეცდომით. | `account_handle`, `project_handle` |
| `test_run.failed` | ლოკალური ან continuous integration ტესტების გაშვება მთავრდება შეცდომით, შერწყმული sharded გაშვების ან მიტოვებული გაშვების ჩათვლით. | `account_handle`, `project_handle` |
| `ci_job.failed` | Tuist runner job მთავრდება შეცდომით. | `account_handle` |

გამოწერისთვის კლიენტი იძახებს `events/subscribe` მოვლენის სახელით, ზემოთ ჩამოთვლილი handle-ებით `arguments`-ში და `webhook` მიწოდებით, რომელიც შეიცავს `https://` callback URL-ს და `whsec_` ხელმოწერის საიდუმლოს. პროექტის მოვლენებს სჭირდება ანგარიშის წევრობა და შესაბამისი ტესტის ან ბილდის მონაცემებზე წვდომა; runner job მოვლენებს სჭირდება ანგარიშის წევრობა და runner-ზე წვდომა. მოთხოვნილმა [`auth.md`](https://workos.com/auth-md) access token-ებმა, მოთხოვნილმა ანგარიშის token-ებმა და ბრაუზერის ავტორიზაციის გრანტებმა შეუძლიათ შექმნან გამოწერები; მიწოდება ჩერდება, როდესაც შესაბამისი credential აღარ არის აქტიური. თითოეულ მომხმარებელს შეუძლია ჰქონდეს მაქსიმუმ 25 აქტიური გამოწერა. Tuist აგზავნის verification challenge-ს callback-ზე გამოწერის შენახვამდე. Callback-მა უნდა დააბრუნოს ობიექტი იგივე `challenge` მნიშვნელობით. გამოწერა ნაგულისხმევად შვიდი დღე ძალაშია, შეიძლება განახლდეს ხელახლა გამოწერით და ჩერდება, როდესაც მომხმარებლის წვდომა ან credential იხსნება. არასავალდებულო `ttlMs` შემოიფარგლება ერთ საათსა და 30 დღეს შორის. Tuist ცდილობს ვადამოსულ callback-ს და აუქმებს გამოწერას მინიმუმ სამი თანმიმდევრული ვადამოსვლის შემდეგ, რომლებიც ხუთ წუთს მოიცავს; გამოიწერეთ ხელახლა callback-ის აღდგენის შემდეგ.

როდესაც მოვლენა ხდება, Tuist აგზავნits რესურსის იდენტიფიკატორს და dashboard URL-ს callback-ზე. ბილდისა და ტესტების გაშვების შეცდომები ასევე შეიცავს `is_ci` და `git_branch`-ს, რათა კლიენტებმა შეძლონ ლოკალური შეცდომების იგნორირება ან შტოს მიხედვით ფილტრაცია. ბილდის მოვლენები შეიცავს `build_system`-ს; runner job მოვლენები შეიცავს როგორც `workflow_job_id`-ს, ასევე `workflow_run_id`-ს. მოთხოვნა შეიცავს გამოწერის იდენტიფიკატორს და [Standard Webhooks](https://www.standardwebhooks.com/) ხელმოწერის ჰედერებს, რათა კლიენტმა შეძლოს მისი წარმოშობის ვერიფიკაცია. Tuist ცდილობს წარუმატებელ მიწოდებებს, ამიტომ კლიენტებმა უნდა გამოიყენონ სტაბილური `eventId` დუბლიკატების გამოსარიცხად. Payload არ შეიცავს ტესტების სახელებს, ლოგებსა და შეცდომის შეტყობინებებს; კლიენტმა შეუძლია მიიღოს ეს დეტალები ზემოთ ჩამოთვლილი ინსტრუმენტებით და გადაწყვიტოს, შეატყობინოს თუ არა გუნდს ან დაიწყოს დებაგინგი. კლიენტებმა შეუძლიათ შეწყვიტონ მიწოდება `events/unsubscribe`-ით.

| `flaky_tests` | გეხმარებათ არასტაბილური ტესტების აღმოჩენის კონფიგურაციაში, Gradle Test Retry პლაგინის არააუცილებელი გამოყენებაში და ტესტების კარანტინის კონფიგურაციაში. |

როდესაც `features` გამოტოვებულია, პრომპტი სთხოვს აგენტს განაზღვროს, თუ რომელი ინტეგრაციები სურს მომხმარებელს ან გამოიტანოს მოთხოვნიდან ყველაზე მცირე სასარგებლო ნაკრადი Gradle პროექტის რედაქტირებამდე.

#### Xcode ინტეგრაციის პრომპტის ფუნქციები

`integrate_xcode_project` პრომპტი აღწერს ყველა Xcode ინტეგრაციას, რომელსაც Tuist მხარს უჭერს:

| ფუნქცია | რას აკონფიგურირებს აგენტი |
|---------|---------------------------|
| `xcode_cache` | აკონფიგურირებს `tuist setup cache`-ს, გენერირებული პროექტის ქეშის პარამეტრებს, Xcode ქეშის ხელით ბილდის პარამეტრებს და ატვირთვის პოლიტიკას, რომელიც შეზღუდულია უწყვეტი ინტეგრაციის რანერებზე. |
| `build_insights` | აკონფიგურირებს `tuist inspect build`-ს, `tuist xcodebuild`-ს, `-resultBundlePath`-ს და არააუცილებელ მანქანურ მეტრიკებს `tuist setup insights`-ის მეშვეობით. |
| `test_insights` | აკონფიგურირებს `tuist inspect test`-ს, სქემის ტესტის post-actions-ებს და შედეგების ბანდლის გენერაციას უწყვეტი ინტეგრაციის ტესტების გაშვებებისთვის. |
| `test_sharding` | ამატებს Xcode-ის ან გენერირებული პროექტის შარდების დაგეგმვისა და შარდების შესრულების სამუშაო ნაკადს `TUIST_SHARD_INDEX`-ით. |

როდესაც `features` გამოტოვებულია, პრომპტი სთხოვს აგენტს განაზღვროს, თუ რომელი ინტეგრაციები სურს მომხმარებელს ან გამოიტანოს მოთხოვნიდან ყველაზე მცირე სასარგებლო ნაკრადი Xcode პროექტის რედაქტირებამდე.
