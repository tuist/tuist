# Model Context Protocol

[Model Context Protocol (MCP)](https://modelcontextprotocol.io/docs/getting-started/intro) არის ღია სტანდარტი, რომელიც საშუალებას აძლევს ხელოვნური ინტელექტის აგენტებს ურთიერთქმედება გარე სერვისებთან და მონაცემთა წყაროებთან. ის უზრუნველყოფს ისეთი აპლიკაციების, როგორიცაა [Claude](https://claude.ai/), [Claude Code](https://docs.anthropic.com/en/docs/claude-code), [Codex](https://developers.openai.com/codex/), და რედაქტორების, როგორიცაა [Zed](https://zed.dev), [Cursor](https://www.cursor.com) ან [Visual Studio Code](https://code.visualstudio.com), თავსებადობას Tuist-თან.

Tuist განათავსებს Model Context Protocol-ის სერვერულ წერტილს მისამართზე `https://tuist.dev/mcp`. მასზე თქვენი კლიენტის მიერთებით, აგენტებს შეუძლიათ წვდომა თქვენს Tuist პროექტის მონაცემებზე, მათ შორის ტესტების ინსაიტებზე, ცვალებადი ტესტების ანალიზზე და სხვა. უმეტესი ინსტრუმენტი კითხულობს Tuist-ის მონაცემებს, რომლებსაც ავტორიზებული მომხმარებელი უკვე ხედავს დაშბორდზე. ყოველი ინსტრუმენტი ასახავს ანოტაციებს, რომლებიც მიუთითებს, არის თუ არა ის მხოლოდ წაკითხვისთვის, შეუძლია თუ არა მას გამოიწვიოს ძნელად შექცევადი ცვლილება (`destructiveHint`), და შეუძლია თუ არა მას Tuist-ის ფარგლებს გარეთ გასვლა (`openWorldHint`). ინსტრუმენტები, რომლებიც ცვლიან მდგომარეობას, თითოეული შემოიფარგლება მომხმარებლის ნებართვებით ანგარიშზე ან პროექტზე, არის:

- **ორგანიზაციები და წევრები**: `create_organization`, `add_organization_member` (ამატებს არსებულ მომხმარებელს ან ცვლის წევრის როლს), `invite_organization_member` (აგზავნის მოწვევას ნებისმიერ ელფოსტის მისამართზე) და `cancel_organization_invitation`.
- **პროექტები**: `create_project`, `start_project_logo_upload` და `complete_project_logo_upload` (ცვლის ლოგოს), `connect_project_repository` და `disconnect_project_repository` (GitHub რეპოზიტორიის ბმულები).
- **ტესტები**: `update_test_case` (აჩუმებს, ტოვებს, ხელახლა ჩართავს ან აღნიშნავს სატესტო შემთხვევას, როგორც ცვალებადს; ცვლილება შეიძლება მიაღწიოს ანგარიშის ვებჰუკის წერტილებს).
- **შეტყობინებების წესები**: `create_notification_rule`, `update_notification_rule` და `delete_notification_rule`.
- **უწყვეტი ინტეგრაციის გამშვებები**: `create_runner_profile`, `update_runner_profile` (საშუალებების შეზღუდვა, რომელი სამუშაოები ინახავს ქეშის ტომებს, აუქმებს ლოდინში მყოფ შენახვებს), `delete_runner_profile` და `delete_runner_volume` (შლის ტომის შენახულ შიგთავსს).
- **სენდბოქსები**: `create_sandbox`, `pause_sandbox`, `resume_sandbox`, `extend_sandbox`, `archive_sandbox` და `delete_sandbox` (შლის მის დისკებს).
- **უკუკავშირი**: `report_feedback` (აგზავნის ანგარიშს ინსტრუმენტის ან მოთხოვნის შესახებ Tuist-ის გუნდს; მხოლოდ tuist.dev-ზე).
- **ორგანიზაციის AI**: `save_organization_ai_model`, `remove_organization_ai_model`, `set_organization_ai_default_model`, `save_organization_ai_task_route`, `remove_organization_ai_task_route` და `remove_organization_ai_provider` (შლის პროვაიდერის გასაღებს და მოდელებს, და წყვეტს დაკავშირებულ Claude ორგანიზაციას Anthropic-ზე).
- **აგენტის ინტეგრაციები**: `connect_amp_workspace` (ანიჭებს სამუშაო სივრცის orbs-ს CI წვდომას ანგარიშზე), `disconnect_amp_workspace` და `connect_claude_environment` (საშუალებას აძლევს Claude Managed Agents გარემოს გაუშვას სესიები Tuist სენდბოქსებში).

`add_organization_member`, `cancel_organization_invitation`, `complete_project_logo_upload`, `disconnect_project_repository`, `update_test_case`, `update_notification_rule`, `delete_notification_rule`, `update_runner_profile`, `delete_runner_profile`, `delete_runner_volume`, `delete_sandbox`, `disconnect_amp_workspace`, `remove_organization_ai_provider`, `remove_organization_ai_model` და `remove_organization_ai_task_route` ასახავენ `destructiveHint: true`-ს, რადგან ისინი ცვლიან ან აშორებენ არსებულ მდგომარეობას. `invite_organization_member`, `update_test_case`, `connect_claude_environment`, `remove_organization_ai_provider` და `report_feedback` ასახავენ `openWorldHint: true`-ს, რადგან ისინი აგზავნიან ელფოსტას, აცნობებენ გარე ვებჰუკის წერტილებს, უკავშირდებიან Anthropic-ს ან აგზავნიან ანგარიშს Tuist-ის გუნდს.

პირადი Claude და ChatGPT გამოწერები დაკავშირებულია მხოლოდ დაშბორდის AI პარამეტრებში, ამიტომ გამოწერის ტოკენები და შესვლები არასდროს გადის Model Context Protocol კლიენტის მეშვეობით. ანგარიშის დაყენების ინსტრუმენტებს სჭირდებათ მომხმარებლის ავტორიზაცია. ისინი არ არის ხელმისაწვდომი პროექტის ტოკენების ან ჩვეულებრივი ანგარიშის ტოკენებისთვის. როდესაც მომხმარებელი ავტორიზებს კლიენტს ბრაუზერში ან ითხოვს `auth.md` რეგისტრაციას, Tuist აკავშირებს ამ სერთიფიკატს მომხმარებელთან მხოლოდ Model Context Protocol წერტილზე, რათა დაყენების ინსტრუმენტებმა შეასრულონ მოთხოვნილი სამუშაო ნაკადი. რადგან ნებისმიერს შეუძლია დაარეგისტრიროს კლიენტი, ბრაუზერში ერთ-ერთის ავტორიზაცია აჩვენებს თანხმობის გვერდს, რომელიც ასახელებს კლიენტს და ჰოსტს, რომელზეც იგზავნება წვდომა, და Tuist გასცემს სერთიფიკატს მხოლოდ მას შემდეგ, რაც თქვენ იქ დაამტკიცებთ მას. კლიენტი, რომელიც არ ითხოვს სკოპს, იღებს `mcp` სკოპის ჯგუფს. კლიენტებმა უნდა გამოიყენონ PKCE `S256`-ით, და მათი გადამისამართების URI-ებმა უნდა გამოიყენონ HTTPS, HTTP loopback მისამართზე, ან აპლიკაციის საკუთარი სქემა.

Tuist ახორციელებს [2026-07-28 პროტოკოლს](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http). მოთხოვნები არის უმდგომარეობო: კლიენტები აგზავნიან თავიანთ პროტოკოლის მეტამონაცემებს ყოველ მოთხოვნასთან ერთად და შეუძლიათ პირდაპირ გამოიძახონ ინსტრუმენტები ინიციალიზაციის გარეშე. `server/discover` აბრუნებს სერვერის იდენტობას, შესაძლებლობებს, მხარდაჭერილ ვერსიებს და ინსტრუქციებს. არ არსებობს სესიის იდენტიფიკატორები ან დამოუკიდებელი მოვლენათა ნაკადები. კლიენტები, რომლებიც იყენებენ 2025-06-18 ან 2025-03-26 ინიციალიზაციის ნაკადს, კვლავ მხარდაჭერილია; ისინი ასევე მუშაობენ სერვერის სესიების გარეშე.

## Model Context Protocol უნარების წინააღმდეგ

Model Context Protocol ინსტრუმენტებს და <.localized_link href="/guides/features/agentic-coding/skills">უნარებს</.localized_link> შეიძლება ჰქონდეთ გადაფარვა შესრულებულ ფუნქციებში. არსებული გადაფარვის გათვალისწინებით, აირჩიეთ ერთი მიდგომა სამუშაო ნაკადისთვის და გამოიყენეთ ის თანმიმდევრულად, ნაცვლად ორივეს ერთ ნაკადში შერევისა.

კლიენტებისთვის, რომლებიც მხარდაჭერენ პლაგინების ინსტალაციას, გამოიყენეთ <.localized_link href="/guides/features/agentic-coding/plugins">Tuist პლაგინები</.localized_link> ორივეს ერთად ინსტალაციისთვის.

## კონფიგურაცია

დაამატეთ `https://tuist.dev/mcp` როგორც დაშორებული Model Context Protocol სერვერი თქვენს კლიენტში. სერვერის ინიციალიზაციის ინსტრუქციები და საჯარო სერვერის ბარათი აღწერს OAuth 2.0-ს დინამიური კლიენტის რეგისტრაციით და სტანდარტული ბრაუზერის ავტორიზაციის ნაკადით პირდაპირ, აგენტებისგან გარე ავთენტიკაციის დოკუმენტების მოთხოვნის ან მათი მიყოლების გარეშე. ეს სერვერის მასშტაბის ინსტრუქციები ინარჩუნებს სამუშაო ნაკადის მითითებებს ზოგადს: ინსტრუმენტის ავთენტიკაცია არ ავთენტიკაციებს ადგილობრივ ბრძანების ხაზის ინსტრუმენტებს ან აგების სისტემის ინტეგრაციებს, და აგენტებმა უნდა გადაამოწმონ მოთხოვნილი ცვლილებები შესაბამისი Tuist ინსტრუმენტების მეშვეობით. აგების სისტემის სპეციფიკური დაყენება და ავთენტიკაციის შემოწმებები დოკუმენტირებულია ინტეგრაციის სახელმძღვანელოებში და მოთხოვნებში. Tuist კვლავ ასახავს როგორც [Open Authorization](https://oauth.net/2/) აღმოჩენის მეტამონაცემებს, ასევე მიმდინარე [auth.md პროტოკოლს](https://workos.com/auth-md) მისამართზე `https://tuist.dev/auth.md` ცალკე.

თუ თქვენი ერთ-ერთი ორგანიზაცია აიძულებს ერთჯერად შესვლას, ბრაუზერში კლიენტის ავტორიზაცია მოითხოვს სესიას, რომელიც შესულია ამ ორგანიზაციის მეშვეობით, და Tuist საჭიროების შემთხვევაში ჯერ პროვაიდერზე გაგზავნით. იხილეთ <.localized_link href="/guides/integrations/authentication/sso#choose-an-enrollment-policy">ერთჯერადი შესვლა</.localized_link>.

წერტილი იღებს უმდგომარეობო `2026-07-28` Model Context Protocol მოთხოვნის სიცოცხლის ციკლს, მათ შორის `server/discover`-ს, უფრო ძველ სესიაზე დაფუძნებულ ციკლთან ერთად. არსებულმა კლიენტებმა შეიძლება გააგრძელონ თავიანთი მიმდინარე მიერთების მეთოდის გამოყენება.

კლიენტებს, რომლებიც მხარდაჭერენ Model Context Protocol მოვლენებს, შეუძლიათ გამოიწერონ პროექტის მოვლენები. იხილეთ [მოვლენები](#events) ხელმისაწვდომი მოვლენებისა და მიწოდების მოთხოვნებისთვის.

კლიენტებს, რომლებიც უკვე მხარდაჭერენ ბრაუზერის მეშვეობით დისტანციურ ავტორიზაციას, შეუძლიათ გააგრძელონ ავტორიზაცია ბრაუზერში. კლიენტებს და აგენტებს, რომლებიც მხარდაჭერენ `auth.md`, შეუძლიათ ანონიმურად რეგისტრაცია, სანდო პროვაიდერის იდენტობის დამოწმების წარდგენა ან მომსახურებით ავთენტიფიცირებული ელფოსტის მოთხოვნის დაწყება. რეგისტრაცია აბრუნებს Tuist-ით ხელმოწერილ იდენტობის დამოწმებას, რომელსაც აგენტი ცვლის სტანდარტულ ტოკენის წერტილზე ერთსაათიანი წვდომის ტოკენის საწინააღმდეგოდ. Tuist აქვეყნებს თავის ღია ხელმოწერის გასაღებს და მხარდაჭერს ტოკენის სტანდარტულ გაუქმებასა და პროვაიდერის უსაფრთხოების მოვლენების მიწოდებას.

ავთენტიფიცირებელმა აგენტმა უნდა წაიკითხოს Model Context Protocol წერტილის მიერ დაბრუნებული `WWW-Authenticate` ჰედერი, მიიღოს დაცული რესურსის მეტამონაცემები, მიიღოს ავტორიზაციის სერვერის მეტამონაცემები და გადავიდეს მის `agent_auth.skill` URL-ზე. Tuist ასევე აბრუნებს იგივე ლოკალურ `auth_md` URL-ს არაავტორიზებული პასუხის სხეულში, რათა ენის მოდელზე დაფუძნებულმა კლიენტებმა აღმოაჩინონ ნაკადი ნატიური კლიენტის ინტეგრაციაზე დამოკიდებულების გარეშე. განლაგების-ლოკალური დოკუმენტი არის საიმედო წყარო წერტილის სახელების, მოთხოვნის სხეულების, მოთხოვნის გამოკითხვისა და დამოწმების გაცვლისთვის.

სანამ აგენტი დაიწყებს ელფოსტის მოთხოვნას, მან უნდა სთხოვოს მომხმარებელს დაადასტუროს ელფოსტის მისამართი მათი Tuist ანგარიშისთვის. მას არ უნდა გამოიტანოს ეს მისამართი პროვაიდერის პროფილიდან, Git კონფიგურაციიდან, გარემოს ცვლადიდან ან სესიის მეტამონაცემებიდან.

წერტილი იყენებს `mcp` სკოპის ჯგუფს. ანონიმურმა წინასწარ-მოთხოვნის კრედენციალმა შეიძლება აღმოაჩინოს შესაძლებლობები და წაიკითხოს საჯარო ინტეგრაციის სახელმძღვანელო, მაგრამ ის არ განიხილება როგორც შესული მომხმარებელი. ბრაუზერის ავტორიზაციის ან მოთხოვნის შემდეგ, კრედენციალი არის მომხმარებელზე მორგებული და თითოეული ინსტრუმენტი ახორციელებს იგივე ავტორიზაციის შემოწმებებს, რასაც დაშბორდი. დეტალებისთვის იხილეთ <.localized_link href="/guides/server/authentication#scope-groups">სკოპის ჯგუფების დოკუმენტაცია</.localized_link>.

ინსტრუმენტები გადაჰყავს პროექტებზე, რომელთა წაკითხვაც ავთენტიფიცირებულ მომხმარებელს უკვე შეუძლია. Xcode-ისა და Gradle-ის აგების ინსტრუმენტები იღებენ აგების UUID-ს ან დაშბორდის URL-ს. UUID-მ უნდა ამოიცნოს ზუსტად ერთი პროექტი; თუ ის ჩნდება რამდენიმე პროექტში, ინსტრუმენტი აბრუნებს „არ არის ნაპოვნი“-ს სხვა პროექტის ანგარიშის არჩევის ნაცვლად. პროექტზე მორგებული დაშბორდისა და API-ს წაკითხვები რჩება ხელმისაწვდომი. მოხსენებული აქტორის იდენტიფიკატორები არის დაუდასტურებელი ჭდეები, არა კრედენციალები ან დამატებითი წვდომის უფლებები.

აგების სიისა და დეტალების ინსტრუმენტები აჩვენებენ არააუცილებელ `tuist_version` მეტამონაცემებს: Xcode-ისა და Cargo-სთვის მომხსენებელი Tuist CLI, Tuist Gradle პლაგინი Gradle-ისთვის და `tuist_ex` ბიბლიოთეკა Mix-ისთვის. Xcode ასევე აჩვენებს `tuist_generation_version`-ს მის დაკავშირებული პროექტის გენერაციის მოვლენიდან, რომელიც შეიძლება განსხვავდებოდეს ატვირთვადი CLI-სგან. დაკარგული დაკვირვებები არის null, არა გამოტანილი სერვერიდან ან სხვა ანგარიშიდან. Bazel იყენებს თავის არსებულ `bazel_version`-ს; Struo-ს გაშვების დეტალები აჩვენებენ `once_version`-ს. ეს ველები აღწერენ მოხსენებულ ვერსიებს, არა დადასტურებულ იდენტობას ან სადენის კონტრაქტის ვერსიებს. REST აგების წერტილები აჩვენებენ იგივე მეტამონაცემებს. არსებული ინტეგრაციისა და არამდგრადი ტესტების უნარები არ არიან დამოკიდებული ვერსიის ველებზე და არ საჭიროებენ სამუშაო ნაკადის ცვლილებებს.

Tuist ოპერატორები, რომლებიც იკვლევენ მომხმარებლის ანგარიშს, აკეთებენ ამას Tuist-ის შიდა ოპერაციების ინსტრუმენტების მეშვეობით, რომელიც იწერს ყოველ ზარს; პირდაპირი კავშირი ამ წერტილთან არ იძლევა წვდომას მომხმარებლის საკუთარი წევრობის ფარგლებს გარეთ.

### Pulse

Pulse აჩვენებს მხოლოდ წასაკითხ ინსტრუმენტებს ანგარიშის ოპერაციული მეტრიკების, ჟურნალების, ტრეისებისა და შეცდომებისთვის, რომლებიც ყველა მიმართულია `account_handle`-ით. პირველი სამი ასახავს Pulse გვერდებსა და მათ REST API-ს; დანარჩენი ხუთი აგენტს საშუალებას აძლევს პირდაპირ შეისწავლოს ტელემეტრია და არ აქვთ REST ეკვივალენტი:

| ინსტრუმენტი | მიზანი | REST ეკვივალენტი `/api/accounts/:account_handle/pulse`-ის ქვეშ |
| --- | --- | --- |
| `query_pulse` | Pulse გვერდის ცხრილები | `GET /:signal` |
| `get_pulse_analytics` | Pulse გვერდის ვიჯეტები | `GET /:signal/analytics` |
| `get_pulse_error_issue` | ერთი შეცდომის პრობლემა და მისი მოვლენები | `GET /errors/issues/:fingerprint` |
| `query_pulse_metrics` | მყისიერი ან დიაპაზონის PromQL | არ არის |
| `list_pulse_labels` | ჭდის სახელები, ან ერთი ჭდის მნიშვნელობები | არ არის |
| `search_pulse_logs` | ფილტრული ჟურნალის ჩანაწერები | არ არის |
| `search_pulse_traces` | ფილტრული სპანები | არ არის |
| `get_pulse_trace` | ერთი ტრეისის ყოველი სპანი | არ არის |

Pulse შეზღუდულია სერვერზე კონფიგურირებული ორგანიზაციის მიმდინარე წევრებისთვის, მაშინაც კი, თუ ანგარიში ან პროექტი საჯაროა. ის მოითხოვს მომხმარებლის ავთენტიფიკაციას ან მომხმარებელთან დაკავშირებულ `mcp` კრედენციალსა და ანგარიშის წაკითხვის ავტორიზაციას. პროექტის ტოკენები, ჩვეულებრივი ანგარიშის ტოკენები, ანონიმური რეგისტრაციები და ოპერატორის წვდომა ორგანიზაციის წევრობის გარეშე არ იძლევა Pulse-ზე წვდომას. კრედენციალებს არ შეუძლიათ აირჩიონ სხვა ბექენდი ან ტელემეტრიის არენდატორი და მხოლოდ სერვერზე კონფიგურირებულ ანგარიშს აქვს Pulse ტელემეტრია, ამიტომ არცერთ ინსტრუმენტს არ შეუძლია წაიკითხოს სხვა ანგარიშის მონაცემები. ბრაუზერის აგენტები იღებენ ამ ინსტრუმენტებს მხოლოდ Pulse გვერდებზე, ამ გვერდის ანგარიშის სკოპის ფარგლებში.

REST მოითხოვს მომხმარებლის კრედენციალს. OAuth და `auth.md` მომხმარებლის ასოციაციები ხელმისაწვდომია მხოლოდ `/mcp` წერტილზე; ანგარიშის კრედენციალი მიმდინარე მომხმარებლის გარეშე უარყოფილია, მიუხედავად დაკავშირებული ანგარიშის წევრობისა ან ხილვადობისა.

`query_pulse` იღებს `signal`-ს (`metrics`, `logs`, `traces` ან `errors`), არააუცილებელ `query`-ს და `range`-ს (`15m`, `1h`, `6h` ან `24h`, ნაგულისხმევი `1h`). მეტრიკები იღებენ PromQL გამოსახულებებს. ჟურნალები, ტრეისები და შეცდომები იღებენ ლიტერალურ, რეგისტრის მიმართ მგრძნობიარე ტექსტს, რომელიც ემთხვევა ჟურნალის სხეულებს, სპანების სახელებსა და შეცდომის პრობლემების სათაურებს; `*`, ნაგულისხმევი, ირჩევს ყველაფერს. ტრეისის სტრიქონები არის ინდივიდუალური სპანები. შეცდომის სტრიქონები არის პრობლემები: მოვლენები დაჯგუფებული სერვისისა და თითის ანაბეჭდის მიხედვით, მათი მოვლენების რაოდენობით, დაზარალებული ანგარიშებით, პირველი და ბოლო გამოჩენა ფანჯარაში, და მათი ბოლო მოვლენის სათაური, დამნაშავე, დონე და პლატფორმა. ცხრილები იღებენ `search`-ს, `page`-ს (ნაგულისხმევი `1`), `page_size`-ს (`1`–`100`, ნაგულისხმევი `20`), `sort_by`-ს და `sort_order`-ს (`asc` ან `desc`). დალაგების სვეტები დამოკიდებულია სიგნალზე და ჩამოთვლილია ინსტრუმენტის სქემაში. ფილტრები მოიცავს `service`-ს და `level`-ს ჟურნალებისა და შეცდომებისთვის. ფილტრის ოპერატორები იყენებენ შესაბამის `_op` არგუმენტს (`eq`, `contains` ან `not_contains`), ნაგულისხმევად ზუსტი ტოლობით.

დალაგების სვეტებია `name`/`value` მეტრიკებისთვის; `timestamp`/`service`/`level`/`message`/`trace_id` ჟურნალებისთვის; `timestamp`/`service`/`name`/`duration_ms`/`trace_id` ტრეისებისთვის; და `last_seen`/`first_seen`/`events`/`accounts`/`title`/`service`/`level` შეცდომებისთვის. დაშბორდი განზრახ აჩვენებს ქვესიმრავლეს; API და ინსტრუმენტები იღებენ სრულ სიას თითოეული სიგნალისთვის.

ცხრილის პასუხები შეიცავს `rows`-ს, `series`-ს, `warnings`-ს და `meta`-ს. დაგვერდების მეტამონაცემები მოიცავს `page`-ს, `page_size`-ს, `total_count`-ს, `total_pages`-ს, `has_next_page`-ს, `has_previous_page`-ს და `end_at`-ს. გადასცეთ დაბრუნებული ISO8601 `end_at` შემდგომ გვერდებთან ერთად მოთხოვნის ფანჯრის შესანარჩუნებლად. შედეგის ლიმიტის შეცდომები მოითხოვენ მოთხოვნის ან დროის დიაპაზონის შევიწროებას, არა პასუხის ცარიელ ცხრილად განხილვას.

ჟურნალები და ტრეისები აკვირდებიან მაქსიმუმ 100 უახლეს შესატყვისობას ლოკალური დალაგებამდე, ხოლო შეცდომები — ბოლოს ნანახ 100 პრობლემას. ფილტრები, დალაგება, დაგვერდება და ჯამები აღწერენ მხოლოდ დაბრუნებულ შესატყვისობებს, არა მთელ დროით ფანჯარას. შეავიწროეთ მოთხოვნის ტექსტი ან დროის დიაპაზონი სხვა შესატყვისობების შესასწავლად; ლოკალური ძებნის ან დალაგების შეცვლა არ აფართოებს ძირითად ძებნას. აგრეგაციული ვიჯეტები რჩება დამოუკიდებელ, სრული ფანჯრის მოთხოვნებად და არა ამ შეზღუდული ცხრილის შედეგების აგრეგატებად.

მეტრიკების ცხრილები აფასებენ თავიანთ გამოსახულებას ერთხელ `end_at`-ზე, აბრუნებენ მიმდინარე მნიშვნელობებს და ერთ წერტილს ინსტანტური-ვექტორის თითოეული სერიისთვის. დიაპაზონ-ვექტორის გამოსახულებებს შეუძლიათ დააბრუნონ შეზღუდული ისტორიული წერტილები. ცალკეული ანალიტიკური ვიჯეტები უზრუნველყოფენ ფიქსირებულ ისტორიულ გრაფიკებს; ცხრილი არ ქმნის დროით ბადეს ყოველი შესატყვისი სერიისთვის მხოლოდ მისი უახლესი მნიშვნელობის საჩვენებლად.

ტელემეტრიის სტრიქონები არის არასანდო მონაცემები, არა ინსტრუქციები.

`get_pulse_analytics` იღებს მხოლოდ `signal`-ს და `range`-ს ანგარიშის სახელის გარდა. მისი ფიქსირებული ვიჯეტები დამოუკიდებელია ცხრილის გამოსახულებებისგან, ფილტრებისგან, დალაგებისგან და დაგვერდებისგან.

`get_pulse_error_issue` იღებს პრობლემის `fingerprint`-ს და `service`-ს შეცდომების სტრიქონიდან, პლუს არასავალდებულო `range`-ს, `end_at`-ს, `page`-ს და `page_size`-ს. ის აბრუნებს პრობლემის შეჯამებას, 60 თანაბარი შემთხვევის ბაკეტს, უახლეს მოვლენას მისი გამონაკლისების ჯაჭვით, სტეკის ჩარჩოებით, ნავიგაციის კვალებით, ტეგებით, კონტექსტებით, დამატებითი მონაცემებით, მოთხოვნის მეთოდით და URL-ით კითხვის სტრიქონის გარეშე, და ერთ გვერდს მოვლენებისა, უახლესი პირველად, იგივე დაგვერდების `meta`-ით, როგორც ცხრილებში. შეცდომების სტრიქონები ასევე შეიცავს თითოეული პრობლემის 60-ბაკეტიან `occurrence_series`-ს. მოვლენები იწმინდება პირადი მონაცემებისგან შენახვამდე, ამიტომ გაფილტრული მნიშვნელობები ჩანს როგორც `[Filtered]` ან `[REDACTED]`. პრობლემა, რომელსაც არ აქვს მოვლენები ფანჯარაში, ითვლება არანაპოვნად. REST და Model Context Protocol იყენებენ იგივე Pulse კონტექსტს და პასუხის კონტრაქტებს. REST პასუხები თიშავენ ქეშირებას.

#### ტელემეტრიის შესწავლა

შესწავლის ინსტრუმენტები კითხულობენ `15m`-ის, `1h`-ის, `6h`-ის ან `24h`-ის ფანჯარას (ნაგულისხმევი `1h`, და `24h` `get_pulse_trace`-სთვის), რომელიც მთავრდება არასავალდებულო ISO8601 `end_at`-ზე, რომელიც ნაგულისხმევად არის ახლა. ყოველი პასუხი აბრუნებს `start_at`-ს და `end_at`-ს; გადასცეთ იგივე `end_at` კვლავ ფანჯრის შესანარჩუნებლად. ამ ინსტრუმენტებიდან არცერთი არ იღებს SQL-ს.

- `query_pulse_metrics` აფასებს `query`-ს, PromQL გამოსახულებას, `end_at`-ზე (`type: instant`, ნაგულისხმევი) ან ყოველ `step` წამში ფანჯრის განმავლობაში (`type: range`). ნაბიჯი ნაგულისხმევად არის და არ შეიძლება იყოს ფანჯარა გაყოფილი 360-ზე ნაკლები, ამიტომ სერიას აქვს მაქსიმუმ 361 წერტილი. შედეგებს აქვთ მაქსიმუმ 5,000 სერია. წერტილები არის `[unix_seconds, value]`, ხოლო `NaN` და უსასრულო მნიშვნელობები არის სტრიქონები. ინსტანტური მოთხოვნები უარყოფენ `range`-ს და `step`-ს.
- `list_pulse_labels` იღებს `signal`-ს. `label`-ის გარეშე, ის ჩამოთვლის ლეიბლების სახელებს; `label`-ით, ის ჩამოთვლის ამ ლეიბლის მნიშვნელობებს. მეტრიკებისთვის, `__name__` ჩამოთვლის მეტრიკების სახელებს, და ნებისმიერი სხვა ლეიბლის მნიშვნელობები მოითხოვენ `match`-ს, სერიის სელექტორს, როგორიცაა `up`. ჟურნალების და ტრეისის ლეიბლის მნიშვნელობები იღებენ `filters`-ს; ტრეისის ლეიბლის სახელები მოდის ტრეისის სქემიდან და არა. ჟურნალის და ტრეისის მნიშვნელობები შეიცავს მათი ჩანაწერების რაოდენობას ფანჯარაში, ყველაზე ხშირი პირველად, ამიტომ ისინი ასევე ემსახურებიან როგორც დაშლა, მაგალითად, შეცდომები სერვისის მიხედვით. `search` ინარჩუნებს მხოლოდ სახელებს ან მნიშვნელობებს, რომლებიც შეიცავს ლიტერალურ ტექსტს, და `limit` იღებს `1`–`1000`-ს (ნაგულისხმევი `100`). ჟურნალის ლეიბლის სახელის აღმოჩენა აკვირდევს მაქსიმუმ 1,000 განსხვავებულ ატრიბუტთა ნაკრებს თითოეული სახისა და ჩამოთვლის მხოლოდ გასაღებებს, რომლებსაც ფილტრები იღებენ.
- `search_pulse_logs` აბრუნებს მაქსიმუმ `limit` ჩანაწერს (`1`–`100`, ნაგულისხმევი `50`), `newest` ან `oldest` პირველად, რომელთა სხეული შეიცავს `text`-ს და რომლებიც ემთხვევა ყოველ ფილტრს. თითოეული ჩანაწერი შეიცავს მის `severity_text`-ს, `body`-ს, `trace_id`-ს, `span_id`-ს, `scope_name`-ს, და მის გაერთიანებულ რესურსს და ჟურნალის `attributes`-ს. `span_id` და `scope_name` არის `null` Kubernetes-დან შეგროვებული ჟურნალებისთვის, რომელსაც მხოლოდ OTLP ჟურნალის გამგზავნები აყენებენ.
- `search_pulse_traces` აბრუნებს მაქსიმუმ `limit` სპანს, `newest`, `oldest`, ან `slowest` პირველად, რომლებიც ემთხვევა ყოველ ფილტრს, არასავალდებულო `min_duration_ms`-ს და `max_duration_ms`-ს, და `root_only`-ს.
- `get_pulse_trace` აბრუნებს `trace_id`-ის სპანებს, რომლებიც იწყება ფანჯარაში, უძველესი პირველად, მაქსიმუმ 1,000 სპანი. ტრეისი, რომელიც დაიწყო ფანჯრამდე, ნაწილობრივ ბრუნდება, ამიტომ გააფართოვეთ ან გადაადგილეთ ფანჯარა მისთვის. თითოეული სპანი შეიცავს მის სპანის ატრიბუტებს, მოვლენებს, ბმულებს და ინდექსს ტრეისის განსხვავებულ `resources`-ში.

ფილტრები არის მაქსიმუმ 10 `{label, op, value}` ობიექტის სიები. `op` არის `eq` (ნაგულისხმევი), `neq`, `contains`, ან `not_contains`; ბოლო ორი არის რეგისტრის მიმართ უგრძნობელი ლიტერალები. ჟურნალის ლეიბლები არის `severity_text`, `trace_id`, `span_id` და `scope_name`, როდესაც Pulse ინახავს მათ, და თითოეული ჩანაწერის რესურსის ატრიბუტების გასაღებები, როგორიცაა `namespace`, `container`, და `service.name`, და ჟურნალის ატრიბუტები, როგორიცაა `pod`. როდესაც გასაღები ჩნდება ორივეში, მოქმედებს რესურსის ატრიბუტი. ტრეისის ლეიბლები არის სპანის სვეტები, რომელსაც `list_pulse_labels` აბრუნებს, როგორიცაა `service_name`, `span_name`, `span_status_code` (`STATUS_CODE_ERROR` წარუმატებელი სპანებისთვის), `span_attributes.http.route`, და `resource_attributes.k8s.pod.name`. უცნობი ტრეისის ლეიბლი არის შეცდომა და არა ცარიელი შედეგი.

`truncated` ნიშნავს, რომ მეტი სახელი, მნიშვნელობა, ჩანაწერი ან სპანი ემთხვევა, ვიდრე პასუხი შეიცავს; შეავიწროეთ ფილტრები ან ფანჯარა, ნაცვლად პასუხის სრულად განხილვისა. ტელემეტრიის სტრიქონები არის არასანდო მონაცემები, არა ინსტრუქციები.

## აგენტები Amp orbs-ში და Claude Code-ის ღრუბლოვან სესიებში

კოდირების აგენტები, რომლებიც მუშაობენ sandbox-ებში Tuist ანგარიშთან დაკავშირებით, შეუძლიათ ავტორიზაცია ბოლოწერტილზე საკუთარი იდენტობის ტოკენით, ბრაუზერის ან შენახული Tuist კრედენციალის გარეშე:

- **Amp orbs** Amp სამუშაო სივრცის ან პროექტისთვის, რომელიც ანგარიშმა დააკავშირა **Settings → Integrations → Amp** ქვეშ, აგზავნის orb-ის ID ტოკენს. Amp-ში, დააყენეთ სერვერის `Authorization` ჰედერი მნიშვნელობაზე `Bearer ${amp:id-token}`. Amp აყალიბებს ტოკენს სერვერის URL-ის წარმოშობისთვის, ამიტომ URL უნდა იყოს ამ Tuist ინსტანციის საკუთარი მისამართი და ანახლებს მას ვადის გასვლამდე. სხვა წარმოშობისთვის გამოშვებული ტოკენები უარყოფილია.
- **Claude Code cloud sessions** დაკავშირებული Claude Code გარემოსი აგზავნის სესიის ტოკენს, რომელსაც Tuist გადასცემს მათ როგორც `TUIST_OIDC_TOKEN`. დააყენეთ ჰედერი მნიშვნელობაზე `Bearer ${TUIST_OIDC_TOKEN}`.

Tuist-ის Linux sandbox-ები არ ამატებენ სერვერს თქვენთვის: ისინი შეიცავენ Tuist CLI-ს, რომელიც შედის სისტემაში იგივე იდენტობით, და უნარს, რომელიც ეუბნება აგენტს, როდის შეამოწმოს შედეგები პროექტის ისტორიის მიხედვით. რომ აგენტებსაც მიეცეთ MCP ინსტრუმენტები, დაამატეთ სერვერი თქვენს Amp ან Claude Code პარამეტრებში, ან პროექტის `.mcp.json`-ში, ზემოთ მითითებული ჰედერით.

ეს ტოკენები იძლევა მხოლოდ კითხვის უფლებას დაკავშირებული ანგარიშის ყველა პროექტზე: ისინი შეიცავენ `mcp` ჯგუფის კითხვის სფეროებს და არ შეიცავენ ისეთებს, რომლებიც ქმნიან, ცვლიან ან შლიან მონაცემებს, მაგალითად ტესტების ჩუმად დატოვებას ან გამოტოვებას. სამუშაო სივრცის ან გარემოს გათიშვა წყვეტს წვდომას შემდეგ მოთხოვნაზე და წვდომა არასდროს გრძელდება ტოკენის ვადაზე მეტხანს. Amp სამუშაო სივრცე, რომელიც დაკავშირებულია რამდენიმე Tuist ანგარიშთან, უარყოფილია, რადგან მისი ტოკენი არ ასახელებს ერთ კონკრეტულს. როდესაც კავშირი არ არსებობს, არაავტორიზებული პასუხის `error_description` აღნიშნავს ამას.

ეს მხოლოდ კითხვის წვდომა ვრცელდება მხოლოდ Model Context Protocol ბოლოწერტილზე. ბრძანების სტრიქონის ინსტრუმენტი და აგების სისტემის ინტეგრაციები იმავე sandbox-ში კვლავ ცვლიან ტოკენს კავშირის CI წვდომისთვის.

## WebMCP

ბრაუზერებში, რომლებიც მხარს უჭერენ [WebMCP](https://webmachinelearning.github.io/webmcp)-ს, Tuist-ის გვერდები აფიქსირებენ ინსტრუმენტებს `document.modelContext`-ით, ასე რომ ბრაუზერში ჩაშენებულ აგენტებს შეუძლიათ გამოიძახონ ისინი დამატებითი კონფიგურაციის გარეშე. ზარები სრულდება Tuist სერვერზე.

- **Website and documentation pages** აფიქსირებენ დოკუმენტაციისა და წყაროს ინსტრუმენტებს (`search_tuist`, `search_tuist_code`, `list_tuist_files` და `read_tuist_file`). მათ არ სჭირდებათ თქვენი შესვლა სისტემაში.
- **An account's dashboard pages**, როდესაც შესული ხართ სისტემაში, აფიქსირებენ Tuist-ის მხოლოდ კითხვის ინსტრუმენტებს ამ ანგარიშისთვის. თითოეული გვერდი აფიქსირებს მხოლოდ იმ ინსტრუმენტებს, რასაც ის აჩვენებს, პროექტის აგების სისტემისთვის: Gradle პროექტის აგებების გვერდი იღებს Gradle აგების ინსტრუმენტებს, მისი ტესტების გვერდები — ტესტებისა და დაფარვის ინსტრუმენტებს, გამშვებების გვერდები — გამშვებების ინსტრუმენტებს, ხოლო sandbox-ების გვერდები — sandbox-ის ინსტრუმენტებს. ყველა გვერდი ასევე იღებს დოკუმენტაციის ინსტრუმენტებს, `list_projects` და `get_project`. ინსტრუმენტები მუშაობენ შესული მომხმარებლის სახელით, ამიტომ ისინი მხოლოდ იმ მონაცემებთან ახდენენ წვდომას, რასაც თქვენ შეგიძლიათ წაიკითხოთ დაფაზე, და მხოლოდ იმ ანგარიშთან, რომელსაც უყურებთ. როდესაც გადადიხართ სხვა გვერდზე ან ანგარიშზე, ინსტრუმენტები იცვლება იმ გვერდის შესაბამისებით.

ინსტრუმენტები, რომლებიც ქმნიან, ცვლიან ან შლიან მონაცემებს, არ არის ხელმისაწვდომი WebMCP-ით, რადგან ბრაუზერის აგენტი იღებს ინსტრუმენტებს თქვენი დამატების გარეშე და კითხულობს კონტენტს, რომელსაც აგებები და ტესტები ქმნიან. დააკავშირეთ MCP კლიენტი `/mcp` ბოლოწერტილთან ამ ინსტრუმენტების გამოყენებისთვის.

თუ ორგანიზაცია აიძულებს ერთჯერად შესვლას (single sign-on), შედით დაფაზე მისი პროვაიდერის მეშვეობით, რათა გამოიყენოთ მისი ინსტრუმენტები.

## აგების სისტემის ინტეგრაციები იყენებენ ორ კრედენციალს

კრედენციალი, რომელიც გამოიყენება Model Context Protocol ინსტრუმენტებისთვის, არ ავტორიზებს Gradle პლაგინს ან Bazel-ის დაშორებულ სერვისებს. სანამ აგენტი შეცვლის ან დაადასტურებს Gradle ან Bazel ინტეგრაციას, მან უნდა გაუშვას:

```bash
tuist auth whoami --url https://tuist.dev
```

თუ ეს ბრძანება არ არის ავტორიზებული, აგენტმა უნდა შეწყვიტოს მუშაობა და სთხოვოს მომხმარებელს გაუშვას:

```bash
tuist auth login --url https://tuist.dev
```

ლოკალური ან თვითმასპინძლი განლაგებისთვის, შეცვალეთ URL ორივე ბრძანებაში და `tuist.toml`-ში. შეინარჩუნეთ ჰოსტის სახელის მართლწერა იდენტური ყველგან. მაგალითად, `localhost` და `127.0.0.1` იყენებენ ცალკე შენახულ კრედენციალებს.

### ინსტრუმენტები

შემდეგი ინსტრუმენტები ხელმისაწვდომია Tuist Model Context Protocol სერვერის მეშვეობით:

ყოველი ინსტრუმენტი აქვეყნებს ადამიანისთვის წასაკითხ აღწერას ცხადი შეყვანისა და გამოტანის სქემებთან ერთად. წარმატებული ზარები აბრუნებენ სტრუქტურირებულ კონტენტს, რომელიც შეესაბამება გამოცხადებულ გამოტანის სქემას, პლუს იგივე შედეგი ტექსტად სერიალიზებული იმ კლიენტებისთვის, რომლებიც ჯერ არ მოიხმარენ სტრუქტურირებულ კონტენტს.

ინსტრუმენტები, რომლებიც იღებენ ერთი ჩანაწერის იდენტიფიკატორს, როგორიცაა `build_run_id`, `test_run_id`, `test_case_id`, `bundle_id`, `run_id`, `generation_id` ან `cache_run_id`, ასევე იღებენ ამ ჩანაწერის Tuist დაფის URL-ს. ჩასვით URL პირდაპირ ბრაუზერიდან, ნაცვლად მისგან იდენტიფიკატორის ამოღებისა.

`get_xcode_build`, `get_test_run`, `get_gradle_build` და `get_project` შეიძლება შეიცავდეს `side_quests`: Tuist შესაძლებლობებს, რომლებსაც პროექტი არ იყენებს, მაგრამ ჩანაწერი აჩვენებს, რომ ისინი სასარგებლო იქნებოდა. თითოეულს აქვს `id`, `tip`, რომელიც აღნიშნავს მტკიცებულებას, რაზეც ის ეფუძნება, და `docs` ბმული. აგენტებს სთხოვენ ჯერ დაასრულონ მომხმარებლის მოთხოვნა, ახსენონ გამოყენებადი დამატებითი ამოცანები და იმოქმედონ მხოლოდ მაშინ, როცა მომხმარებელი დაეთანხმება. ისინი ბრუნდება მხოლოდ პროექტის ანგარიშის წევრებისთვის, მიუხედავად იმისა, უკავშირდებიან ისინი მომხმარებლის სესიით, MCP ტოკენით თუ აგენტის იდენტობით:

#### წყაროზე დაფუძნებული პასუხები

ეს მხოლოდ წაკითხვის ინსტრუმენტები აგენტებს საშუალებას აძლევს გამოიყენონ ზუსტი საჯარო Tuist წყაროს რევიზია, რომელიც განლაგებულია დაჰოსტებულ სერვერთან ერთად, როგორც ჭეშმარიტების წყარო პასუხებისთვის, რომლებიც დამოკიდებულია მიმდინარე ქცევაზე. ისინი ხელმისაწვდომია მხოლოდ `https://tuist.dev/mcp`-ზე.

თავსებადი კლიენტები იღებენ ფაქტობრივ აღწერებს ინსტრუმენტების წყაროს რევიზიის, ბმულების და შედეგების ლიმიტების შესახებ ინიციალიზაციის დროს, inline OAuth ავთენტიკაციის ინფორმაციასთან ერთად. ეს აღწერები არ განსაზღვრავენ პასუხის სტილს ან ვერიფიკაციის სამუშაო პროცესს. მომხმარებლებს შეუძლიათ პირდაპირ დასვან კითხვა `ask_tuist` მოთხოვნის გამოძახების გარეშე; მოთხოვნა რჩება ხელმისაწვდომი ცხადი წყაროზე დაფუძნებული სამუშაო პროცესისთვის.

ყველა ოპერაციას აქვს ფიქსირებული ლიმიტები კონკურენტულობის, ხანგრძლივობის, გადაადგილების, წაკითხული ბაიტების და პასუხის ზომისთვის. ძებნისა და ჩამონათვალის შედეგები მოიცავს `truncated` და `truncation_reason` ველებს. როცა შედეგი შეკვეცილია, შეავიწროვეთ გზა, ფაილის ნიმუში ან საძიებო სიტყვა, ნაცვლად შედეგის ამომწურავად ჩათვლისა.

ID-ები მიბმულია ბილდზე და არ უნდა შეესაბამებოდეს სხვადასხვა ბილდებს შორის.

არასავალდებულო `start_ms` და `end_ms` ირჩევენ ნაბიჯებს, რომლებიც ემთხვევიან დროის დიაპაზონს მილიწამებში ბილდის დაწყებიდან; ბოლო წერტილი არ არის ჩართული. ორივე ინსტრუმენტი იღებს ბილდის UUID-ს ან დაშბორდის URL-ს როგორც `build_run_id`. გადასცეთ მიღებული ნაბიჯის `id` უცვლელად როგორც `step_id` მისი ლოგის მისაღებად. ლოგები ინახავენ მაქსიმუმ 64 KiB-ს თითო ნაბიჯზე, ხოლო `log_truncated` მიუთითებს გამოტოვებულ გამოსავალზე.

ნაბიჯები ნაგულისხმევად იკრიბება Xcode ბილდების დამუშავებისას. ჩაწერილი ნაბიჯების მონაცემები ინახება 90 დღის განმავლობაში. სიის პასუხი შეიცავს `availability`-ს: `available`, როცა ჩაწერილი ნაბიჯები არსებობს, მაშინაც კი, თუ ფილტრები არაფერს ემთხვევა; `processing`, როცა ბილდი ჯერ კიდევ მუშავდება და ნაბიჯები ჯერ არ აქვს; ან `unavailable`, როცა ნაბიჯები არ ჩაწერილა ან ვადა გაუვიდათ.

იგივე ოპერაციები ხელმისაწვდომია HTTP API-ზე `GET /api/projects/{account_handle}/{project_handle}/xcode/builds/{build_id}/steps`-ზე და `GET /api/projects/{account_handle}/{project_handle}/xcode/builds/{build_id}/steps/{step_id}`-ზე, იგივე ფილტრებითა და პაგინაციით. ორივეს სჭირდება წაკითხვის წვდომა ბილდის პროექტზე.

Gradle და Bazel ნაბიჯების სიები ნაგულისხმევად აბრუნებენ 20 შედეგს (მაქსიმუმ 100), მხარდაჭერილია `search`, ზუსტი `project`, `target`, `category` და `status`, გადაფარვის `start_ms` / `end_ms` ფილტრები (ბოლო წერტილის გარეშე) და `duration_ms` ან `start_ms` დალაგება. გადასცეთ მიღებული ID-ები უცვლელად; ისინი მიბმულია მათ ბილდზე. სიები აჩვენებენ `time_origin`-ს და `coverage`-ს. ძველი Gradle ანგარიშები იყენებენ `first_recorded_timestamp`-ს, რადგან ბილდის დაწყება არ ატვირთულა. Bazel პროფილები აჩვენებენ ყველა ჩაწერილ ინტერვალს `trace_profile` დაფარვით და `profile_start`-ით, როგორც დროის საწყისით. ძველი ბილდები ბრუნდებიან შენახულ BEP შეჯამებებზე. წყაროს ჩანაწერების ვადა გადის 90 დღის შემდეგ. Bazel დეტალები შეიცავს სანიტიზებულ მოქმედების ლოგებს, როცა გამოქვეყნებულია. Gradle დეტალები წარუმატებელი ამოცანის ან კონფიგურაციის ნაბიჯის შესახებ შეიცავს შეცდომის შეტყობინებას, რომელიც Tuist Gradle პლაგინმა აღწერა როგორც `log`: გამონაკლისის შეტყობინება და მისი მიზეზების ჯაჭვი, როგორც Gradle-ის კონსოლი ბეჭდავს მათ, სტეკის ტრეისების ან ამოცანის გამოსავლის გარეშე, პროექტის შიგნით არსებული გზები გახდილია ფარდობითი, ხოლო სერთიფიკატები და სხვა ლოკალური გზები დაფარულია, მაქსიმუმ 16 KiB თითო ნაბიჯზე და 32 წარუმატებელი ნაბიჯი ბილდზე. სხვა Gradle ნაბიჯებს, პლაგინის ძველი ვერსიებით მოხსენებულ ბილდებს და სერთიფიკატების გარეშე მოხსენებებს აქვთ null `log`. კონფიგურაციის ნაბიჯები ანგარიშობენ `failure`-ს, როცა წარუმატებელია და `unknown`-ს სხვა შემთხვევაში. `compare_builds` მოთხოვნა იყენებს ამ დაფარვას სრული Bazel ტრეისების განსასხვავებლად შენახული შეჯამებებისგან და მიმართავს აგენტებს ნაბიჯის დეტალებისკენ მოქმედების შედეგებისა და ლოგებისთვის, სანამ ფართო გამოძახების გამოსავალს შეამოწმებენ.

ერთ-ნაბიჯიანი ინსტრუმენტები `get_gradle_build_step` და `get_bazel_build_step` იღებენ ნაბიჯს ID-ით და არ იღებენ დროის ფილტრებს; გამოიყენეთ შესაბამისი სიის ინსტრუმენტები ნაბიჯების ფილტრაციისთვის დროის დიაპაზონით.

Bazel ნაბიჯის ID-ები, რომლებიც დაბრუნებულია შენახული შეჯამებებიდან, რჩება წაკითხვადი, თუ სრული პროფილი მოდის ნაბიჯის ჩამოთვლასა და მიღებას შორის. ინდექსირებული პროფილი, რომლის ნაბიჯის მონაცემების ვადა გაუვიდა, ანგარიშობს ხელმიუწვდომლობას. Gradle ნაბიჯების სიები შეიცავს ნულოვანი ხანგრძლივობის ქეშირებულ და გამოტოვებულ ოპერაციებს.

`list_bazel_invocations` ფილტრები არის ზუსტი დამთხვევები, ხოლო გამოძახებები, რომლებიც ერთსა და იმავე წამში მთავრდება, დალაგებულია გამოძახების ID-ის მიხედვით. ტოტზე უახლესი შეცდომის შემცველი გამოძახების საპოვნელად, გამოიძახეთ ის `status: "failure"`, `git_branch` და `page_size: 1` პარამეტრებით. REST ბოლო წერტილი `GET /api/projects/{account_handle}/{project_handle}/bazel/invocations` იღებს იგივე ფილტრებს.

დააყენეთ `remote_execution: true` `list_bazel_build_steps`-ზე, რათა დაბრუნდეს მხოლოდ ის მოქმედებები, რომლებსაც უსაფრთხოდ არის მიბმული სერვერის ფაზის დროები ინდექსირებული პროფილებიდან. ჩამონათვალისა და დეტალური პასუხები აჩვენებს არასავალდებულო nullable `remote_queue_ms`, `remote_input_fetch_ms`, `remote_execution_ms` და `remote_output_upload_ms` მნიშვნელობებს. მნიშვნელობები ჯამდება ჩაწერილი ფაზებისთვის, მოქმედებაში განმეორებების ჩათვლით; არარსებული ან null მნიშვნელობები ნიშნავს ხელმიუწვდომლობას, არა ნულს. ისინი არის პროფილის დაკვირვებები, არა გადასახდელი გამოყენება ან ახალი შესრულების დადასტურება, რადგან ქეშირებულ სერვერის შედეგებს შეიძლება ჰქონდეთ შესრულების მეტამონაცემები. კლიენტის ატვირთვები გამორიცხულია. ძველმა ან ბუნდოვანმა პროფილებმა შეიძლება არ დააბრუნოს შესაბამისი მოქმედებები მაშინაც კი, თუ დისტანციური სამუშაო შესრულდა. ნაბიჯის REST ბოლო წერტილი იღებს იგივე `remote_execution=true` ფილტრს. დაფის დისტანციური შესრულების ჩანართი იყენებს იგივე მოთხოვნას და 90-დღიან შენახვას.

ტესტის ლოგები შეიცავს `target_label` და ცდის `status` იმ ტესტის შედეგიდან, საიდანაც ისინი მოვიდნენ, ამიტომ `target_label: "//foo:bar_test"` აბრუნებს მხოლოდ იმ სამიზნის ტესტის ლოგებს. `errors: true` აბრუნებს ჩავარდნილი ცდების ტესტის ლოგებს და stderr პროგრესის ნაწილებს, რომლებიც შეიცავს ხაზს, რომელიც Bazel-ის რეპორტიორს იწყება `ERROR:`, `FAIL:` ან `TIMEOUT:`-ით. პროგრესის გამოსავალი არ არის მიკუთვნებული სამიზნეებისთვის და ლოგებს, რომლებიც დაიწერა მიკუთვნების ჩაწერამდე, აქვთ ცარიელი ველები. ჩავარდნილი მოქმედებები და მათი საკუთარი გამოსავალი ხელმისაწვდომია თითოეული სამიზნისთვის `list_bazel_build_steps`-დან, ხოლო თითოეული ტესტის შემთხვევის ჩავარდნები — ტესტების გაშვების ინსტრუმენტებიდან.

ეს ინსტრუმენტები თანდათანობით იშლება და აბრუნებს მონაცემებს მხოლოდ იმ პროექტებისთვის, სადაც ისინი ჩართულია; სხვა პროექტებისთვის ისინი აბრუნებენ შეცდომას ცარიელი შედეგის ნაცვლად. სახე ხელმისაწვდომია მხოლოდ იმ პროექტებისთვის, რომლებიც იყენებენ მის ბილდის ხელსაწყოს ჯაჭვს. ინსტრუმენტები იღებენ შემოსაზღვრულ `start_at`/`end_at` ფილტრებს, `environment` (`any`, `ci` ან `local`) და ზუსტ `branch`. `list_build_entities` იღებს `q`-ს; `list_build_entity_history` მხარს უჭერს გაუმჭვირვალე `after`/`before` კურსორებს. უცნობი დროის ან ქეშის დაკვირვებები რჩება მიუწვდომელი ნულის ან გამოტოვების ნაცვლად. ისტორია ეხება ჩაწერილ მშობელს და ნატიურ შესრულებას დეტალური შესწავლისთვის არსებული გაშვების ინსტრუმენტების გამოყენებით.

`get_build_entity` მეტრიკები მოიცავს `duration_samples`-ს, დაკვირვებების რაოდენობას ჩაწერილი დროით: ნამდვილი ნულოვანი ხანგრძლივობები ითვლება, დაკარგული დრო არა. ეს რაოდენობა შეიძლება იყოს დაკვირვებების რაოდენობაზე ნაკლები; მიუწვდომელი ხანგრძლივობის სტატისტიკა რჩება null.

Xcode მოდულის ხანგრძლივობები მოდის ბილდის ლოგებში გაზომილი სამიზნე კომპილაციებიდან. მოდულის ქეშის გარჩევები და სამიზნეები კომპილაციის მუშაობის გარეშე არ მონაწილეობენ ხანგრძლივობის ნიმუშებში. კომპილაციის დაკვირვებები ეხება Xcode ბილდს; ქეშის მოვლენები ეხება გენერაციას ან ქეშის ბრძანებას.

Bazel მოქმედებები იდენტიფიცირდება სამიზნის იარლიყით, მნემონიკით და კონფიგურირებული ძირითადი გამომავალით, რაც ცალკე მოქმედებებს და კონფიგურაციებს განცალკევებულს ტოვებს შეყვანაზე დამოკიდებული ქეშის დაიჯესტების გარეშე. ისტორია აღრიცხავს BEP-ით მოხსენებულ შესრულებებს, არა ქეშის ძიებებს ან ტრეისის პროფილის ფაზებს. სრული შესრულების დაფარვა მოითხოვს `--build_event_publish_all_actions`-ს; არტეფაქტის მიწოდება საუკეთესო ძალისხმევით ხდება, ამიტომ დაკარგული დაკვირვებები არ არის მტკიცებულება, რომ მუშაობა არ შესრულებულა. უფრო ძველი Kura პეილოადები სტაბილური იდენტობის ან შესრულების დასაწყისის გარეშე რჩება მიღებული, მაგრამ არაინდექსირებული. დასრულების დროის გაზომვების არარსებობა რჩება მიუწვდომელი და ნამდვილი ნულოვანი ხანგრძლივობები ითვლება.

Mix მოდულის ხანგრძლივობები ზომავს შემცველი ფაილის კომპილაციას, არა დამოუკიდებლად გაზომილ მოდულის მუშაობას. Struo მოქმედებები იყენებენ გამოცხადებულ სამიზნე/შესაძლებლობა/ინდექსის სლოტებს, როდესაც კლიენტმა მოახსენა სამიზნე ასოციაციები; დიაგნოსტიკური იარლიყები მარტო არ არის სტაბილური იდენტობები. არსებული კლიენტები და გაშვების დონის ინსტრუმენტები რჩება მხარდაჭერილი უცვლელად.

Cargo ყუთები დაჯგუფებულია ზუსტად ჩაწერილი ყუთის ფესვით, სახელით და სახეობით. Checkout-ბილიკის ცვლილებებმა შეიძლება გაყოს ისტორიები, ხოლო ბილდის პროფილები, ფუნქციები და სამიზნე ტრიპლეტები არ განირჩევა. ისტორია ზომავს rustc გამოძახებებს, არა ფაილზე მუშაობას ან ქეშის მოხვედრებს; არარსებული სამუშაოები არ ამყარებს წაშლებს ან სრულ სამუშაო სივრცის ინვენტარს.

ანალიტიკის წაკითხვებს აქვს შემოსაზღვრული მეხსიერება და შესრულების დრო. თუ მოთხოვნა აღემატება ამ ლიმიტებს, ინსტრუმენტი აბრუნებს შეცდომას ცარიელი შედეგის გამოგონების ნაცვლად.

ახალი დაკვირვებები ინდექსირდება განლაგების შემდეგ; ეს ფუნქცია არ ავსებს არსებულ გაშვების ტელემეტრიას. იდენტობის მეტამონაცემები ინარჩუნებს სიცოცხლეს ინდივიდუალურ დაკვირვებებზე მეტხანს <.localized_link href="/guides/server/data-retention">მონაცემთა შენახვის პოლიტიკის</.localized_link> ფარგლებში.

| მოვლენა | როდის იგზავნება | გამოწერის ფილტრი |
|-------|-----------------|---------------------|
| `test_case.marked_flaky` | სატესტო შემთხვევა იცვლება არასტაბილურიდან არასტაბილურად. | `account_handle`, `project_handle` |
| `build.failed` | ლოკალური ან უწყვეტი ინტეგრაციის Xcode, Gradle ან Bazel ბილდი სრულდება შეცდომით. | `account_handle`, `project_handle` |
| `test_run.failed` | ლოკალური ან უწყვეტი ინტეგრაციის ტესტების გაშვება სრულდება შეცდომით, შერწყმული შარდირებული გაშვების ან მიტოვებული გაშვების ჩათვლით. | `account_handle`, `project_handle` |

გამოსაწერად კლიენტი იძახებს `events/subscribe` მოვლენის სახელით, ზემოთ ჩამოთვლილი სახელებით `arguments`-ში და `webhook` მიწოდებით, რომელიც შეიცავს `https://` callback URL-ს და `whsec_` ხელმოწერის საიდუმლოს. პროექტის მოვლენები მოითხოვენ ანგარიშის წევრობას და შესაბამის ტესტის ან ბილდის მონაცემებზე წვდომას; გამშვების სამუშაოების მოვლენები მოითხოვენ ანგარიშის წევრობას და გამშვებზე წვდომას. დამოწმებულმა [`auth.md`](https://workos.com/auth-md) წვდომის ტოკენებმა, დამოწმებულმა ანგარიშის ტოკენებმა და ბრაუზერის ავტორიზაციის გრანტებმა შეუძლიათ შექმნან გამოწერები; მიწოდება ჩერდება, როდესაც შესაბამისი სერთიფიკატი აღარ არის აქტიური. თითოეულ მომხმარებელს შეუძლია ჰქონდეს 25-მდე აქტიური გამოწერა. Tuist აგზავნის ვერიფიკაციის გამოწვევას callback-ზე გამოწერის შენახვამდე. callback-მა უნდა დააბრუნოს ობიექტი იგივე `challenge` მნიშვნელობით. გამოწერა ძალაშია შვიდი დღის განმავლობაში, შეიძლება განახლდეს ხელახლა გამოწერით და წყვეტს მიწოდებას, როდესაც მომხმარებლის წვდომა ან სერთიფიკატი ამოღებულია. არასავალდებულო `ttlMs` შემოიფარგლება ერთ საათსა და 30 დღეს შორის. Tuist ხელახლა ცდის ვადაგასულ callback-ს და აუქმებს მას სამი ზედიზედ ვადაგასულობის შემდეგ, რომლებიც ხუთ წუთს მოიცავს; ხელახლა გამოიწერეთ callback-ის აღდგენის შემდეგ.

როდესაც მოვლენა ხდება, Tuist აგზავნის მის რესურსის იდენტიფიკატორს და დაფის URL-ს callback-ზე. ბილდისა და ტესტების გაშვების შეცდომები ასევე შეიცავს `is_ci`-ს და `git_branch`-ს, რათა კლიენტებმა შეძლონ ლოკალური შეცდომების იგნორირება ან ფილტრაცია ტოტის მიხედვით. ბილდის მოვლენები შეიცავს `build_system`-ს; გამშვების სამუშაოების მოვლენები შეიცავს როგორც `workflow_job_id`-ს, ასევე `workflow_run_id`-ს. მოთხოვნა შეიცავს გამოწერის იდენტიფიკატორს და [Standard Webhooks](https://www.standardwebhooks.com/)-ის ხელმოწერის ჰედერებს, რათა კლიენტმა შეძლოს მისი წარმომავლობის ვერიფიცირება. Tuist ხელახლა ცდის წარუმატებელ მიწოდებებს, ამიტომ კლიენტებმა უნდა გამოიყენონ სტაბილური `eventId` დუბლიკატების გასაფილტრად. ტვირთი არ შეიცავს ტესტების სახელებს, ლოგებს და შეცდომის შეტყობინებებს; კლიენტმა შეიძლება მიიღოს ეს დეტალები ზემოთ ჩამოთვლილი ინსტრუმენტების მეშვეობით და გადაწყვიტოს, შეატყობინოს თუ არა გუნდს ან დაიწყოს დებაგინგი. კლიენტებმა შეუძლიათ შეაჩერონ მიწოდება `events/unsubscribe`-ით.

| `build_insights` | აყენებს Tuist Gradle პლაგინს და საჭიროების შემთხვევაში აკონფიგურირებს ბილდის ანალიტიკის ატვირთვის ქცევას. |
| `test_insights` | აყენებს Tuist Gradle პლაგინს, რათა Gradle `Test` ამოცანის შედეგები ავტომატურად აიტვირთოს. |
| `flaky_tests` | ეხმარება არამდგრადი ტესტების აღმოჩენის მოწყობაში, Gradle Test Retry პლაგინის არასავალდებულო გამოყენებაში და ტესტების კარანტინის კონფიგურაციაში. |
| `test_sharding` | ამატებს უწყვეტი ინტეგრაციის სამუშაო ნაკადს `tuistPrepareTestShards`-ისთვის, შარდების მატრიცის გენერირებას და `TUIST_SHARD_INDEX`-ზე დაფუძნებულ ტესტების შესრულებას. |

როდესაც `features` გამოტოვებულია, მოთხოვნა სთხოვს აგენტს გაარკვიოს, რომელი ინტეგრაციები სურს მომხმარებელს, ან მოთხოვნიდან გამოიტანოს უმცირესი სასარგებლო ნაკრები Gradle პროექტის რედაქტირებამდე.

#### Xcode ინტეგრაციის მოთხოვნის ფუნქციები

`integrate_xcode_project` მოთხოვნა აღწერს Xcode-ის ყველა ინტეგრაციას, რომელსაც Tuist მხარდაჭერს:

| ფუნქცია | რას აკონფიგურირებს აგენტი |
|---------|---------------------------|
| `xcode_cache` | აკონფიგურირებს `tuist setup cache`-ს, გენერირებული პროექტის ქეშის პარამეტრებს, Xcode ქეშის ხელით მითითებულ ბილდის პარამეტრებს და ატვირთვის პოლიტიკას, რომელიც შემოიფარგლება მხოლოდ უწყვეტი ინტეგრაციის გამშვებებით. |
| `build_insights` | აკონფიგურირებს `tuist inspect build`-ს, `tuist xcodebuild`-ს, `-resultBundlePath`-ს და არასავალდებულო მანქანურ მეტრიკებს `tuist setup insights`-ის მეშვეობით. |
| `test_insights` | აკონფიგურირებს `tuist inspect test`-ს, სქემის ტესტის post-actions-ებს და შედეგების ბანდლის გენერირებას უწყვეტი ინტეგრაციის ტესტების გაშვებისთვის. |
| `test_sharding` | ამატებს Xcode-ის ან გენერირებული პროექტის შარდების დაგეგმვისა და შარდების შესრულების სამუშაო ნაკადს `TUIST_SHARD_INDEX`-ით. |

როდესაც `features` გამოტოვებულია, მოთხოვნა სთხოვს აგენტს გაარკვიოს, რომელი ინტეგრაციები სურს მომხმარებელს, ან მოთხოვნიდან გამოიტანოს უმცირესი სასარგებლო ნაკრები Xcode პროექტის რედაქტირებამდე.
