# Model Context Protocol

[Model Context Protocol (MCP)](https://modelcontextprotocol.io/docs/getting-started/intro) არის ღია სტანდარტი, რომელიც საშუალებას აძლევს ხელოვნური ინტელექტის აგენტებს ურთიერთქმედონ გარე სერვისებთან და მონაცემთა წყაროებთან. ის უზრუნველყოფს [Claude](https://claude.ai/)-ის, [Claude Code](https://docs.anthropic.com/en/docs/claude-code)-ის, [Codex](https://developers.openai.com/codex/)-ისა და რედაქტორების, როგორიცაა [Zed](https://zed.dev), [Cursor](https://www.cursor.com) ან [Visual Studio Code](https://code.visualstudio.com), თავსებადობას Tuist-თან.

Tuist განათავსებს Model Context Protocol-ის სერვერულ ბოლოწერტილს მისამართზე `https://tuist.dev/mcp`. მასზე თქვენი კლიენტის მიერთებით, აგენტებს შეუძლიათ წვდომა ჰქონდეთ თქვენს Tuist პროექტის მონაცემებზე, მათ შორის ტესტების ანალიტიკაზე, არასტაბილური ტესტების ანალიზზე და სხვა. უმეტესი ინსტრუმენტი კითხულობს Tuist-ის მონაცემებს, რომელთა ნახვაც ავტორიზებულ მომხმარებელს უკვე შეუძლია დაფლაში. ყოველი ინსტრუმენტი აცხადებს ანოტაციებს, რომლებიც მიუთითებს, არის თუ არა ის მხოლოდ წაკითხვადი, შეუძლია თუ არა მას გამოიწვიოს ძნელად შესაქცევი ცვლილება (`destructiveHint`), და შეუძლია თუ არა მას Tuist-ის გარეთ გასვლა (`openWorldHint`). ინსტრუმენტები, რომლებიც ცვლიან მდგომარეობას, თითოეული შეზღუდულია მომხმარებლის ნებართვებით ანგარიშზე ან პროექტზე:

- **ორგანიზაციები და წევრები**: `create_organization`, `add_organization_member` (ამატებს არსებულ მომხმარებელს ან ცვლის წევრის როლს), `invite_organization_member` (აგზავნის მოწვევას ნებისმიერ ელფოსტის მისამართზე) და `cancel_organization_invitation`.
- **პროექტები**: `create_project`, `start_project_logo_upload` და `complete_project_logo_upload` (ცვლის ლოგოს), `connect_project_repository` და `disconnect_project_repository` (GitHub რეპოზიტორიის ბმულები).
- **ტესტები**: `update_test_case` (აჩუმებს, ტოვებს, ხელახლა ააქტიურებს ან სატესტო შემთხვევას აღნიშნავს როგორც არასტაბილურს; ცვლილება შეიძლება მიაღწიოს ანგარიშის webhook ბოლოწერტილებს).
- **შეტყობინებების წესები**: `create_notification_rule`, `update_notification_rule` და `delete_notification_rule`.
- **უწყვეტი ინტეგრაციის გამშვები აგენტები**: `create_runner_profile`, `update_runner_profile` (კეშის ტომების შენახვის სამუშაოების შევიწროება აუქმებს მოლოდინში მყოფ შენახვებს), `delete_runner_profile` და `delete_runner_volume` (შლის ტომის შენახულ შინაარსს).
- **სენდბოქსები**: `create_sandbox`, `pause_sandbox`, `resume_sandbox`, `archive_sandbox` და `delete_sandbox` (შლის მის დისკებს).
- **უკუკავშირი**: `report_feedback` (აგზავნის ანგარიშს ინსტრუმენტის ან მოთხოვნის შესახებ Tuist-ის გუნდს; მხოლოდ tuist.dev-ზე).
- **ორგანიზაციის AI**: `save_organization_ai_model`, `remove_organization_ai_model`, `set_organization_ai_default_model`, `save_organization_ai_task_route`, `remove_organization_ai_task_route` და `remove_organization_ai_provider` (შლის პროვაიდერის გასაღებს და მოდელებს, და ასცილებს Anthropic-ზე დაკავშირებულ Claude ორგანიზაციას).
- **აგენტის ინტეგრაციები**: `connect_amp_workspace` (ანიჭებს სამუშაო სივრცის orbs-ებს CI წვდომას ანგარიშზე), `disconnect_amp_workspace` და `connect_claude_environment` (საშუალებას აძლევს Claude Managed Agents გარემოს გაუშვას სესიები Tuist სენდბოქსებში).

`add_organization_member`, `cancel_organization_invitation`, `complete_project_logo_upload`, `disconnect_project_repository`, `update_test_case`, `update_notification_rule`, `delete_notification_rule`, `update_runner_profile`, `delete_runner_profile`, `delete_runner_volume`, `delete_sandbox`, `disconnect_amp_workspace`, `remove_organization_ai_provider`, `remove_organization_ai_model` და `remove_organization_ai_task_route` აცხადებენ `destructiveHint: true`-ს, რადგან ისინი ცვლიან ან აშორებენ არსებულ მდგომარეობას. `invite_organization_member`, `update_test_case`, `connect_claude_environment`, `remove_organization_ai_provider` და `report_feedback` აცხადებენ `openWorldHint: true`-ს, რადგან ისინი აგზავნიან ელფოსტას, აცნობებენ გარე webhook ბოლოწერტილებს, უკავშირდებიან Anthropic-ს ან აგზავნიან ანგარიშს Tuist-ის გუნდს.

პირადი Claude და ChatGPT გამოწერები დაკავშირებულია მხოლოდ დაფის AI პარამეტრებში, ამიტომ გამოწერის ტოკენები და შესვლები არასდროს გადის Model Context Protocol კლიენტის მეშვეობით. ანგარიშის მორგების ინსტრუმენტები მოითხოვს მომხმარებლის ავთენტიკაციას. ისინი არ არის ხელმისაწვდომი პროექტის ტოკენებისთვის ან ჩვეულებრივი ანგარიშის ტოკენებისთვის. როდესაც მომხმარებელი ავტორიზებს კლიენტს ბრაუზერში ან ითხოვს `auth.md` რეგისტრაციას, Tuist აკავშირებს ამ სერთიფიკატს მომხმარებელთან მხოლოდ Model Context Protocol ბოლოწერტილზე, რათა მორგების ინსტრუმენტებმა შეძლონ მოთხოვნილი სამუშაო პროცესის დასრულება.

Tuist ახორციელებს [2026-07-28 პროტოკოლს](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http). მოთხოვნები არის უმდგომარეობო: კლიენტები აგზავნიან თავიანთ პროტოკოლის მეტამონაცემებს ყოველ მოთხოვნასთან ერთად და შეუძლიათ პირდაპირ გამოიძახონ ინსტრუმენტები ინიციალიზაციის გარეშე. `server/discover` აბრუნებს სერვერის იდენტობას, შესაძლებლობებს, მხარდაჭერილ ვერსიებს და ინსტრუქციებს. არ არსებობს სესიის იდენტიფიკატორები ან დამოუკიდებელი მოვლენათა ნაკადები. კლიენტები, რომლებიც იყენებენ 2025-06-18 ან 2025-03-26 ინიციალიზაციის ნაკადს, კვლავ მხარდაჭერილია; ისინიც მუშაობენ სერვერის სესიების გარეშე.

## Model Context Protocol უნარების წინააღმდეგ

Model Context Protocol-ის ინსტრუმენტებს და <.localized_link href="/guides/features/agentic-coding/skills">უნარებს</.localized_link> შეიძლება ჰქონდეთ გადაფარვა შესრულებულ ფუნქციებში. არსებული გადაფარვის გათვალისწინებით, აირჩიეთ ერთი მიდგომა თითოეული სამუშაო პროცესისთვის და გამოიყენეთ ის თანმიმდევრულად, ნაცვლად ორივეს ერთ ნაკადში შერევისა.

კლიენტებისთვის, რომლებიც მხარდაჭერიან პლაგინების ინსტალაციას, გამოიყენეთ <.localized_link href="/guides/features/agentic-coding/plugins">Tuist პლაგინები</.localized_link> ორივეს ერთად ინსტალაციისთვის.

## კონფიგურაცია

დაამატეთ `https://tuist.dev/mcp` როგორც დისტანციური Model Context Protocol სერვერი თქვენს კლიენტში. სერვერის ინიციალიზაციის ინსტრუქციები და საჯარო სერვერის ბარათი აღწერს OAuth 2.0-ს დინამიური კლიენტის რეგისტრაციით და სტანდარტული ბრაუზერის ავტორიზაციის ნაკადით პირდაპირ, აგენტებისგან გარე ავთენტიკაციის დოკუმენტების მოთხოვნის ან მათზე გადასვლის გარეშე. ეს სერვერის დონის ინსტრუქციები ინარჩუნებს სამუშაო პროცესის მითითებებს ზოგადს: ინსტრუმენტის ავთენტიკაცია არ ავთენტიკირებს ადგილობრივ ბრძანების სტრიქონის ინსტრუმენტებს ან აგების სისტემის ინტეგრაციებს, და აგენტებმა უნდა გადაამოწმონ მოთხოვნილი ცვლილებები შესაბამისი Tuist ინსტრუმენტების მეშვეობით. აგების სისტემის სპეციფიკური მორგება და ავთენტიკაციის შემოწმებები დოკუმენტირებულია ინტეგრაციის სახელმძღვანელოებში და მოთხოვნებში. Tuist კვლავ აცხადებს როგორც [Open Authorization](https://oauth.net/2/) აღმოჩენის მეტამონაცემებს, ასევე მიმდინარე [auth.md პროტოკოლს](https://workos.com/auth-md) მისამართზე `https://tuist.dev/auth.md` ცალ-ცალკე.

თუ თქვენი რომელიმე ორგანიზაცია აიძულებს ერთჯერად შესვლას, ბრაუზერში კლიენტის ავტორიზაცია მოითხოვს სესიას, რომელიც შესულია ამ ორგანიზაციის მეშვეობით, და Tuist საჭიროების შემთხვევაში ჯერ პროვაიდერზე გაგზავნით. იხილეთ <.localized_link href="/guides/integrations/authentication/sso#choose-an-enrollment-policy">ერთჯერადი შესვლა</.localized_link>.

ბოლოწერტილი იღებს უმდგომარეობო `2026-07-28` Model Context Protocol მოთხოვნის სიცოცხლის ციკლს, მათ შორის `server/discover`-ს, უფრო ძველ სესიაზე დაფუძნებულ ციკლთან ერთად. არსებულმა კლიენტებმა შეიძლება განაგრძონ თავიანთი მიმდინარე მიერთების მეთოდის გამოყენება.

კლიენტებს, რომლებიც მხარდაჭერიან Model Context Protocol მოვლენებს, შეუძლიათ გამოიწერონ პროექტის მოვლენები. იხილეთ [მოვლენები](#events) ხელმისაწვდომი მოვლენებისა და მიწოდების მოთხოვნებისთვის.

კლიენტებს, რომლებიც უკვე მხარდაჭერიან დისტანციურ ბრაუზერის ავთენტიკაციას, შეუძლიათ განაგრძონ ავთენტიკაცია ბრაუზერში. კლიენტებს და აგენტებს, რომლებიც მხარდაჭერიან `auth.md`-ს, შეუძლიათ დარეგისტრირდნენ ანონიმურად, წარადგინონ სანდო პროვაიდერის იდენტობის დამოწმება ან დაიწყონ სერვისით ავთენტიკირებული ელფოსტის მოთხოვნა. რეგისტრაცია აბრუნებს Tuist-ით ხელმოწერილ იდენტობის დამოწმებას, რომელსაც აგენტი ცვლის სტანდარტულ ტოკენის ბოლოწერტილზე ერთსაათიანი წვდომის ტოკენისთვის. Tuist აქვეყნებს თავის საჯარო ხელმოწერის გასაღებს და მხარდაჭერს სტანდარტულ ტოკენის გაუქმებას და პროვაიდერის უსაფრთხოების მოვლენების მიწოდებას.

არაავთენტიკირებულმა აგენტმა უნდა წაიკითხოს Model Context Protocol ბოლოწერტილის მიერ დაბრუნებული `WWW-Authenticate` ჰედერი, მოიპოვოს დაცული რესურსის მეტამონაცემები, მოიპოვოს ავტორიზაციის სერვერის მეტამონაცემები და გადავიდეს მის `agent_auth.skill` URL-ზე. Tuist ასევე აბრუნებს იგივე ლოკალურ `auth_md` URL-ს არაავტორიზებული პასუხის სხეულში, რათა ენის მოდელზე დაფუძნებულმა კლიენტებმა შეძლონ ნაკადის აღმოჩენა ნატიური კლიენტის ინტეგრაციაზე დაყრდნობის გარეშე. განლაგების ლოკალური დოკუმენტი არის საიმედო წყარო ბოლოწერტილების სახელების, მოთხოვნის სხეულების, მოთხოვნის გამოკითხვისა და დამოწმების გაცვლისთვის.

სანამ აგენტი ელფოსტის მოთხოვნას დაიწყებს, მან მომხმარებელს უნდა სთხოვოს Tuist ანგარიშის ელფოსტის მისამართის დადასტურება. მან არ უნდა გამოიტანოს ეს მისამართი პროვაიდერის პროფილიდან, Git კონფიგურაციიდან, გარემოს ცვლადიდან ან სესიის მეტამონაცემებიდან.

ბოლოწერტილი იყენებს `mcp` სკოპის ჯგუფს. ანონიმურმა, მოთხოვნამდელმა სერთიფიკატმა შეიძლება აღმოაჩინოს შესაძლებლობები და წაიკითხოს საჯარო ინტეგრაციის სახელმძღვანელო, მაგრამ ის არ განიხილება როგორც შესული მომხმარებელი. ბრაუზერის ავტორიზაციის ან მოთხოვნის შემდეგ, სერთიფიკატი არის მომხმარებელზე ორიენტირებული და თითოეული ინსტრუმენტი იყენებს იგივე ავტორიზაციის შემოწმებებს, რასაც დაშბორდი. დეტალებისთვის იხილეთ <.localized_link href="/guides/server/authentication#scope-groups">სკოპის ჯგუფების დოკუმენტაცია</.localized_link>.

ინსტრუმენტები მიემართება პროექტებზე, რომლებსაც ავთენტიკირებულ მომხმარებელს უკვე აქვს წვდომა. Xcode და Gradle აგების ინსტრუმენტები იღებენ აგების UUID-ს ან დაშბორდის URL-ს. UUID-მ ზუსტად ერთი პროექტი უნდა ამოიცნოს; თუ ის რამდენიმე პროექტში ჩანს, ინსტრუმენტი აბრუნებს „არ არის ნაპოვნი“-ს, ნაცვლად იმისა, რომ სხვა პროექტის ანგარიში აირჩიოს. პროექტზე ორიენტირებული დაშბორდისა და API-ს წაკითხვები ხელმისაწვდომი რჩება. მოხსენებული მოქმედების იდენტიფიკატორები არიან დაუდასტურებელი ეტიკეტები, არა სერთიფიკატები ან დამატებითი წვდომის უფლებები.

აგების სიისა და დეტალების ინსტრუმენტები აჩვენებენ არააუცილებელ `tuist_version` მეტამონაცემებს: Tuist CLI-ს Xcode-ისა და Cargo-სთვის, Tuist Gradle პლაგინს Gradle-ისთვის და `tuist_ex` ბიბლიოთეკას Mix-ისთვის. Xcode ასევე აჩვენებს `tuist_generation_version`-ს თავის დაკავშირებული პროექტის გენერაციის მოვლენიდან, რომელიც შეიძლება განსხვავდებოდეს ატვირთვადი CLI-სგან. დაკარგული დაკვირვებები არის null, არა სერვერიდან ან სხვა ანგარიშიდან გამოტანილი. Bazel იყენებს თავის არსებულ `bazel_version`-ს; Struo გაშვების დეტალები აჩვენებენ `once_version`-ს. ეს ველები აღწერენ მოხსენებულ ვერსიებს, არა დადასტურებულ იდენტობას ან სადენის კონტრაქტის ვერსიებს. REST აგების ბოლოწერტილები აჩვენებენ იგივე მეტამონაცემებს. არსებული ინტეგრაციისა და ფლაკი ტესტის უნარები არ არიან დამოკიდებული ვერსიის ველებზე და არ საჭიროებენ სამუშაო ნაკადის ცვლილებებს.

Tuist ოპერატორები, რომლებიც იკვლევენ მომხმარებლის ანგარიშს, აკეთებენ ამას Tuist-ის შიდა ოპერაციული ინსტრუმენტების მეშვეობით, რომელიც იწერს ყოველ ზარს; ამ ბოლოწერტილთან პირდაპირი მიერთება არ იძლევა წვდომას მომხმარებლის საკუთარი წევრობების გარდა.

### Pulse

Pulse აჩვენებს მხოლოდ წაკითხვის ინსტრუმენტებს ანგარიშის ოპერაციული მეტრიკების, ლოგების, ტრეისებისა და შეცდომებისთვის, ყველა მიმართულია `account_handle`-ით. პირველი სამი ასახავს Pulse გვერდებსა და მათ REST API-ს; დანარჩენი ხუთი აგენტს საშუალებას აძლევს პირდაპირ შეისწავლოს ტელემეტრია და არ აქვთ REST ექვივალენტი:

| ინსტრუმენტი | მიზანი | REST ექვივალენტი `/api/accounts/:account_handle/pulse`-ის ქვეშ |
| --- | --- | --- |
| `query_pulse` | Pulse გვერდის ცხრილები | `GET /:signal` |
| `get_pulse_analytics` | Pulse გვერდის ვიჯეტები | `GET /:signal/analytics` |
| `get_pulse_error_issue` | ერთი შეცდომის საკითხი და მისი მოვლენები | `GET /errors/issues/:fingerprint` |
| `query_pulse_metrics` | მყისიერი ან დიაპაზონის PromQL | არ არის |
| `list_pulse_labels` | ეტიკეტის სახელები, ან ერთი ეტიკეტის მნიშვნელობები | არ არის |
| `search_pulse_logs` | ფილტრული ლოგის ჩანაწერები | არ არის |
| `search_pulse_traces` | ფილტრული სპანები | არ არის |
| `get_pulse_trace` | ერთი ტრეისის ყოველი სპანი | არ არის |

Pulse შეზღუდულია სერვერზე კონფიგურირებული ორგანიზაციის მიმდინარე წევრებზე, მაშინაც კი, თუ ანგარიში ან პროექტი საჯაროა. ის მოითხოვს მომხმარებლის ავთენტიკაციას ან მომხმარებელთან დაკავშირებულ `mcp` სერთიფიკატს და ანგარიშის წაკითხვის ავტორიზაციას. პროექტის ტოკენები, ჩვეულებრივი ანგარიშის ტოკენები, ანონიმური რეგისტრაციები და ოპერატორის წვდომა ორგანიზაციის წევრობის გარეშე არ იძლევა Pulse-ზე წვდომას. სერთიფიკატებს არ შეუძლიათ აირჩიონ სხვა ბექენდი ან ტელემეტრიის მომხმარებელი და მხოლოდ სერვერზე კონფიგურირებულ ანგარიშს აქვს Pulse ტელემეტრია, ამიტომ არცერთ ინსტრუმენტს არ შეუძლია წაიკითხოს სხვა ანგარიშის მონაცემები. ბრაუზერის აგენტები იღებენ ამ ინსტრუმენტებს მხოლოდ Pulse გვერდებზე, ამ გვერდის ანგარიშის სკოპში.

REST მოითხოვს მომხმარებლის სერთიფიკატს. OAuth და `auth.md` მომხმარებლის ასოციაციები ხელმისაწვდომია მხოლოდ `/mcp` ბოლოწერტილზე; ანგარიშის სერთიფიკატი მიმდინარე მომხმარებლის გარეშე უარყოფილია, მიუხედავად დაკავშირებული ანგარიშის წევრობისა ან ხილვადობისა.

`query_pulse` იღებს `signal`-ს (`metrics`, `logs`, `traces` ან `errors`), არააუცილებელ `query`-ს და `range`-ს (`15m`, `1h`, `6h` ან `24h`, ნაგულისხმევი `1h`). მეტრიკები იღებენ PromQL გამოსახულებებს. ლოგები, ტრეისები და შეცდომები იღებენ ლიტერალურ, დამოკიდებულის გარეშე ტექსტს, რომელიც ემთხვევა ლოგის სხეულებს, სპანის სახელებს და შეცდომის საკითხის სათაურებს; `*`, ნაგულისხმევი, ირჩევს ყველაფერს. ტრეისის სტრიქონები არის ინდივიდუალური სპანები. შეცდომის სტრიქონები არის საკითხები: მოვლენები დაჯგუფებულია სერვისისა და თითის ანაბეჭდის მიხედვით, მათი მოვლენების რაოდენობით, დაზარალებული ანგარიშებით, პირველი და ბოლო გამოჩენა ფანჯარაში, და მათი უახლესი მოვლენის სათაური, დამნაშავე, დონე და პლატფორმა. ცხრილები იღებენ `search`-ს, `page`-ს (ნაგულისხმევი `1`), `page_size`-ს (`1`–`100`, ნაგულისხმევი `20`), `sort_by`-ს და `sort_order`-ს (`asc` ან `desc`). დალაგების სვეტები დამოკიდებულია სიგნალზე და ჩამოთვლილია ინსტრუმენტის სქემაში. ფილტრები მოიცავს `service`-ს და `level`-ს ლოგებისა და შეცდომებისთვის. ფილტრის ოპერატორები იყენებენ შესაბამის `_op` არგუმენტს (`eq`, `contains` ან `not_contains`), ნაგულისხმევი ზუსტი ტოლობით.

დალაგების სვეტებია `name`/`value` მეტრიკებისთვის; `timestamp`/`service`/`level`/`message`/`trace_id` ლოგებისთვის; `timestamp`/`service`/`name`/`duration_ms`/`trace_id` ტრეისებისთვის; და `last_seen`/`first_seen`/`events`/`accounts`/`title`/`service`/`level` შეცდომებისთვის. დაშბორდი განზრახ აჩვენებს ქვესიმრავლეს; API და ინსტრუმენტები იღებენ სრულ სიას თითოეული სიგნალისთვის.

ცხრილის პასუხები შეიცავს `rows`-ს, `series`-ს, `warnings`-ს და `meta`-ს. დაფურცვლის მეტამონაცემები მოიცავს `page`-ს, `page_size`-ს, `total_count`-ს, `total_pages`-ს, `has_next_page`-ს, `has_previous_page`-ს და `end_at`-ს. გადაეცით დაბრუნებული ISO8601 `end_at` შემდგომ გვერდებთან ერთად, რათა შეინარჩუნოთ მოთხოვნის ფანჯარა. შედეგის ლიმიტის შეცდომები მოითხოვენ მოთხოვნის ან დროის დიაპაზონის შევიწროვებას, არა პასუხის ცარიელ ცხრილად განხილვას.

ლოგები და ტრეისები ამოწმებენ მაქსიმუმ 100 უახლეს დამთხვევას ლოკალური დალაგებამდე, ხოლო შეცდომები — 100 უახლესად ნანახ საკითხს. ფილტრები, დალაგება, დაფურცვლა და ჯამები აღწერენ მხოლოდ დაბრუნებულ დამთხვევებს, არა მთელ დროის ფანჯარას. შეავიწროვეთ მოთხოვნის ტექსტი ან დროის დიაპაზონი სხვა დამთხვევების შესამოწმებლად; ლოკალური ძიების ან დალაგების შეცვლა არ აფართოებს ზემოთ ნაკადის ძიებას. აგრეგატული ვიჯეტები რჩება დამოუკიდებელი, სრული ფანჯრის მოთხოვნებად, ნაცვლად ამ შეზღუდული ცხრილის შედეგების აგრეგატებისა.

მეტრიკების ცხრილები აფასებენ თავიანთ გამოსახულებას ერთხელ `end_at`-ზე, აბრუნებენ მიმდინარე მნიშვნელობებს და ერთ წერტილს თითოეული ინსტანტ-ვექტორის სერიისთვის. დიაპაზონ-ვექტორის გამოსახულებებს შეუძლიათ დააბრუნონ შეზღუდული ისტორიული წერტილები. ცალკეული ანალიტიკური ვიჯეტები უზრუნველყოფენ ფიქსირებულ ისტორიულ გრაფიკებს; ცხრილი არ ქმნის დროის ბადეს ყოველი შესაბამისი სერიისთვის მხოლოდ მისი უახლესი მნიშვნელობის საჩვენებლად.

ტელემეტრიის სტრიქონები არის არასანდო მონაცემები, არა ინსტრუქციები.

`get_pulse_analytics` იღებს მხოლოდ `signal`-ს და `range`-ს ანგარიშის სახელის გარდა. მისი ფიქსირებული ვიჯეტები დამოუკიდებელია ცხრილის გამოსახულებებისგან, ფილტრებისგან, დალაგებისგან და დაფურცვლისგან.

`get_pulse_error_issue` იღებს საკითხის `fingerprint`-ს და `service`-ს შეცდომების სტრიქონიდან, პლუს არაავტორიზებულ `range`-ს, `end_at`-ს, `page`-ს და `page_size`-ს. ის აბრუნებს საკითხის შეჯამებას, 60 თანაბარი შემთხვევის კალათას, უახლეს მოვლენას მისი გამონაკლისების ჯაჭვით, სტეკის ჩარჩოებით, ნავიგაციის ბილიკებით, ტეგებით, კონტექსტებით, დამატებითი მონაცემებით, მოთხოვნის მეთოდით და URL-ით გამოკითხვის სტრიქონის გარეშე, და მოვლენების ერთ გვერდს, უახლესიდან დაწყებული, იგივე დაფურცვლის `meta`-ით, რაც ცხრილებში. შეცდომების სტრიქონები ასევე შეიცავს თითოეული საკითხის 60-კალათიან `occurrence_series`-ს. მოვლენები იწმინდება პირადი მონაცემებისგან შენახვამდე, ამიტომ გაფილტრული მნიშვნელობები ჩანს როგორც `[Filtered]` ან `[REDACTED]`. საკითხი, რომელსაც არ აქვს მოვლენები ფანჯარაში, მოხსენიებულია როგორც არნაპოვნი. REST და Model Context Protocol იყენებენ იგივე Pulse კონტექსტს და პასუხის კონტრაქტებს. REST პასუხები თიშავენ ქეშირებას.

#### ტელემეტრიის კვლევა

კვლევის ინსტრუმენტები კითხულობენ `15m`, `1h`, `6h` ან `24h` დროის ფანჯარას (ნაგულისხმევად `1h`, ხოლო `get_pulse_trace`-ისთვის `24h`), რომელიც მთავრდება არასავალდებულო ISO8601 `end_at`-ზე, ნაგულისხმევად ახლანდელ მომენტზე. ყოველი პასუხი აბრუნებს `start_at`-ს და `end_at`-ს; იგივე `end_at`-ის გადაცემა ისევ შეინარჩუნებს ფანჯარას. ამ ინსტრუმენტებიდან არცერთი არ იღებს SQL-ს.

- `query_pulse_metrics` აფასებს `query`-ს, PromQL გამოსახულებას, `end_at`-ზე (`type: instant`, ნაგულისხმევი) ან ყოველ `step` წამში ფანჯრის განმავლობაში (`type: range`). ნაბიჯი ნაგულისხმევად არის და არ შეიძლება იყოს უფრო მცირე, ვიდრე ფანჯარა გაყოფილი 360-ზე, ამიტომ სერიას აქვს მაქსიმუმ 361 წერტილი. შედეგებს აქვთ მაქსიმუმ 5,000 სერია. წერტილებია `[unix_seconds, value]`, ხოლო `NaN` და უსასრულო მნიშვნელობები არის სტრიქონები. ინსტანტური მოთხოვნები უარყოფენ `range`-ს და `step`-ს.
- `list_pulse_labels` იღებს `signal`-ს. `label`-ს გარეშე, ის ჩამოთვლის ლეიბლების სახელებს; `label`-ით, ის ჩამოთვლის იმ ლეიბლის მნიშვნელობებს. მეტრიკებისთვის, `__name__` ჩამოთვლის მეტრიკების სახელებს, და ნებისმიერი სხვა ლეიბლის მნიშვნელობები მოითხოვენ `match`-ს, სერიის სელექტორს, როგორიცაა `up`. ლოგების და ტრეისების ლეიბლის მნიშვნელობები იღებენ `filters`-ს; ტრეისების ლეიბლის სახელები მოდის ტრეისის სქემიდან და არა. ლოგების და ტრეისების მნიშვნელობები შეიცავს მათი ჩანაწერების რაოდენობას ფანჯარაში, ყველაზე ხშირი პირველად, ამიტომ ისინი ასევე ემსახურებიან დაშლას, როგორიცაა შეცდომები სერვისის მიხედვით. `search` ინარჩუნებს მხოლოდ სახელებს ან მნიშვნელობებს, რომლებიც შეიცავენ ლიტერალურ ტექსტს, და `limit` იღებს `1`–`1000` (ნაგულისხმევი `100`). ლოგების ლეიბლის სახელის აღმოჩენა ამოწმებს მაქსიმუმ 1,000 განსხვავებულ ატრიბუტთა ნაკრებს თითოეული სახისა და ჩამოთვლის მხოლოდ გასაღებებს, რომლებსაც ფილტრები იღებენ.
- `search_pulse_logs` აბრუნებს მაქსიმუმ `limit` ჩანაწერს (`1`–`100`, ნაგულისხმევი `50`), `newest` ან `oldest` პირველად, რომელთა სხეული შეიცავს `text`-ს და რომლებიც ემთხვევა ყოველ ფილტრს. თითოეული ჩანაწერი შეიცავს მის `severity_text`-ს, `body`-ს, `trace_id`-ს, `span_id`-ს, `scope_name`-ს, და მის შერწყმულ რესურსის და ლოგის `attributes`-ს. `span_id` და `scope_name` არის `null` ლოგებისთვის, რომლებიც შეგროვებულია Kubernetes-დან, რომელსაც მხოლოდ OTLP ლოგის გამგზავნები აყენებენ.
- `search_pulse_traces` აბრუნებს მაქსიმუმ `limit` სპანს, `newest`, `oldest`, ან `slowest` პირველად, რომლებიც ემთხვევა ყოველ ფილტრს, არაავტორიზებულ `min_duration_ms`-ს და `max_duration_ms`-ს, და `root_only`-ს.
- `get_pulse_trace` აბრუნებს `trace_id`-ის სპანებს, რომლებიც იწყება ფანჯარაში, უძველესი პირველად, მაქსიმუმ 1,000 სპანი. ტრეისი, რომელიც დაიწყო ფანჯრამდე, ნაწილობრივ არის დაბრუნებული, ამიტომ გააფართოვეთ ან გადაადგილეთ ფანჯარა მისთვის. თითოეული სპანი შეიცავს მის სპანის ატრიბუტებს, მოვლენებს, ბმულებს, და ინდექსს ტრეისის განსხვავებულ `resources`-ში.

ფილტრები არის მაქსიმუმ 10 `{label, op, value}` ობიექტის სიები. `op` არის `eq` (ნაგულისხმევი), `neq`, `contains`, ან `not_contains`; ბოლო ორი არის ასოების რეგისტრის მიმართ უმგრძნობელი ლიტერალები. ლოგების ლეიბლებია `severity_text`, `trace_id`, `span_id` და `scope_name`, როდესაც Pulse ინახავს მათ, და თითოეული ჩანაწერის რესურსის ატრიბუტების გასაღებები, როგორიცაა `namespace`, `container`, და `service.name`, და ლოგის ატრიბუტები, როგორიცაა `pod`. როდესაც გასაღები ჩნდება ორივეში, მოქმედებს რესურსის ატრიბუტი. ტრეისების ლეიბლებია სპანის სვეტები, რომლებსაც `list_pulse_labels` აბრუნებს, როგორიცაა `service_name`, `span_name`, `span_status_code` (`STATUS_CODE_ERROR` წარუმატებელი სპანებისთვის), `span_attributes.http.route`, და `resource_attributes.k8s.pod.name`. უცნობი ტრეისის ლეიბლი არის შეცდომა და არა ცარიელი შედეგი.

`truncated` ნიშნავს, რომ მეტი სახელი, მნიშვნელობა, ჩანაწერი, ან სპანი ემთხვევა, ვიდრე პასუხი შეიცავს; შეავიწროვეთ ფილტრები ან ფანჯარა, ნაცვლად პასუხის სრულად განხილვისა. ტელემეტრიის სტრიქონები არის არასანდო მონაცემები, არა ინსტრუქციები.

`auth`-ის `false`-ზე დაყენება ხელს უშლის ადაპტერის ბრაუზერის ავტორიზაციის handler-ს Tuist-ის არაავტორიზებული პასუხის დამალვას. უსახურ აგენტს შეუძლია წაიკითხოს დაბრუნებული `auth_md` URL და მიჰყვეს Tuist-ის რეგისტრაციას, იდენტობის დამოწმების გაცვლას და პრეტენზიის გამოკითხვის ნაკადს. კონფიგურირეთ გაცვლილი წვდომის ტოკენი როგორც bearer ტოკენი ან მიეცით აგენტს პირდაპირ გააკეთოს ავტორიზებული Model Context Protocol ზარები.

თუ ბრაუზერის ავტორიზაციას ამჯობინებთ, დააყენეთ `auth` `"oauth"`-ზე. ამ ნაკადისთვის, შეინარჩუნეთ ერთი პროცესი ცოცხალი Pi-ს [remote procedure call mode](https://pi.dev/docs/latest/rpc)-ით, სანამ ავტორიზაცია დასრულდება:

## აგენტები Amp orbs-ში და Claude Code cloud სესიებში

კოდირების აგენტები, რომლებიც მუშაობენ sandbox-ებში, რომლებიც დაკავშირებულია Tuist ანგარიშთან, შეუძლიათ ავტორიზაცია endpoint-ზე თავიანთი იდენტობის ტოკენით, ბრაუზერის ან შენახული Tuist რწმუნების გარეშე:

- **Amp orbs** Amp workspace-ის ან პროექტისთვის, რომელიც ანგარიშმა დააკავშირა **Settings → Integrations → Amp**-ის ქვეშ, აგზავნის orb-ის ID ტოკენს. Amp-ში, დააყენეთ სერვერის `Authorization` ჰედერი `Bearer ${amp:id-token}`-ზე. Amp ქმნის ტოკენს სერვერის URL-ის წარმოშობისთვის, ამიტომ URL უნდა იყოს ამ Tuist ინსტანციის საკუთარი მისამართი და აახლებს მას ვადის გასვლამდე. სხვა წარმოშობისთვის შექმნილი ტოკენები უარყოფილია.
- **Claude Code cloud sessions** დაკავშირებული Claude Code გარემოდან აგზავნის სესიის ტოკენს, რომელსაც Tuist გადასცემს მათ როგორც `TUIST_OIDC_TOKEN`. დააყენეთ ჰედერი `Bearer ${TUIST_OIDC_TOKEN}`-ზე.

Tuist-ის Linux sandbox-ები არ ამატებენ სერვერს თქვენთვის: ისინი შეიცავენ Tuist CLI-ს, რომელიც შედის სისტემაში იგივე იდენტობით, და უნარს, რომელიც ეუბნება აგენტს, როდის შეამოწმოს შედეგები პროექტის ისტორიის მიხედვით. აგენტებისთვის MCP ხელსაწყოების მისაცემად, დაამატეთ სერვერი თქვენს Amp ან Claude Code პარამეტრებში, ან პროექტის `.mcp.json`-ში, ზემოთ მოცემული ჰედერით.

ეს ტოკენები იძლევა მხოლოდ წაკითხვის უფლებას დაკავშირებული ანგარიშის ყველა პროექტზე: ისინი შეიცავენ `mcp` ჯგუფის წაკითხვის სფეროებს და არაფერს, რაც ქმნის, ცვლის ან შლის მონაცემებს, როგორიცაა ტესტების ჩუმად დატოვება ან გამოტოვება. workspace-ის ან გარემოს გათიშვა წყვეტს წვდომას შემდეგ მოთხოვნაზე და წვდომა არასდროს ძლებს ტოკენზე მეტ ხანს. Amp workspace, რომელიც დაკავშირებულია რამდენიმე Tuist ანგარიშთან, უარყოფილია, რადგან მისი ტოკენი არ ასახელებს ერთს. როცა კავშირი არ არის, არაავტორიზებული პასუხის `error_description` ამბობს ამას.

ეს მხოლოდ წაკითხვის წვდომა ვრცელდება მხოლოდ Model Context Protocol endpoint-ზე. ბრძანების ხაზის ხელსაწყო და build-system ინტეგრაციები იმავე sandbox-ში მაინც ცვლიან ტოკენს კავშირის CI წვდომისთვის.

## WebMCP

ბრაუზერებში, რომლებიც მხარს უჭერენ [WebMCP](https://webmachinelearning.github.io/webmcp)-ს, Tuist-ის გვერდები რეგისტრირებენ ხელსაწყოებს `document.modelContext`-ით, ასე რომ ბრაუზერში ჩაშენებულ აგენტებს შეუძლიათ გამოიძახონ ისინი დამატებითი კონფიგურაციის გარეშე. ზარები მუშაობენ Tuist სერვერზე.

- **Website and documentation pages** რეგისტრირებენ დოკუმენტაციის და წყაროს ხელსაწყოებს (`search_tuist`, `search_tuist_code`, `list_tuist_files` და `read_tuist_file`). მათ არ სჭირდებათ თქვენგან სისტემაში შესვლა.
- **An account's dashboard pages**, როცა სისტემაში შეხვედით, რეგისტრირებენ Tuist-ის მხოლოდ წაკითხვის ხელსაწყოებს ამ ანგარიშისთვის. თითოეული გვერდი რეგისტრირებს მხოლოდ იმ ხელსაწყოებს, რასაც ის აჩვენებს, პროექტის build system-ისთვის: Gradle პროექტის builds გვერდი იღებს Gradle build ხელსაწყოებს, მისი test გვერდები test და coverage ხელსაწყოებს, runners გვერდები runner ხელსაწყოებს და sandboxes გვერდები sandbox ხელსაწყოებს. ყველა გვერდი ასევე იღებს დოკუმენტაციის ხელსაწყოებს, `list_projects` და `get_project`. ხელსაწყოები მუშაობენ სისტემაში შესული მომხმარებლის სახელით, ამიტომ ისინი მხოლოდ იმ მონაცემებს აღწევენ, რასაც შეგიძლიათ წაიკითხოთ dashboard-ში და მხოლოდ იმ ანგარიშს, რომელსაც უყურებთ. როცა გადადიხართ სხვა გვერდზე ან ანგარიშზე, ხელსაწყოები იცვლება იმ გვერდის ხელსაწყოებით.

ხელსაწყოები, რომლებიც ქმნიან, ცვლიან ან შლიან მონაცემებს, არ არის ხელმისაწვდომი WebMCP-ით, რადგან ბრაუზერის აგენტი იღებს ხელსაწყოებს თქვენი დამატების გარეშე და კითხულობს კონტენტს, რომელსაც builds და tests ქმნიან. დააკავშირეთ MCP კლიენტი `/mcp` endpoint-თან ამ ხელსაწყოების გამოსაყენებლად.

თუ ორგანიზაცია აიძულებს ერთჯერად შესვლას (single sign-on), შედით dashboard-ში მისი პროვაიდერით, რათა გამოიყენოთ მისი ხელსაწყოები.

## Build-system ინტეგრაციები იყენებენ ორ რწმუნებას

რწმუნება, რომელიც გამოიყენება Model Context Protocol ხელსაწყოებისთვის, არ ავტორიზებს Gradle პლაგინს ან Bazel-ის remote სერვისებს. სანამ აგენტი შეცვლის ან გადაამოწმებს Gradle ან Bazel ინტეგრაციას, მან უნდა გაუშვას:

```bash
tuist auth whoami --url https://tuist.dev
```

თუ ეს ბრძანება არ არის ავტორიზებული, აგენტმა უნდა შეწყვიტოს და სთხოვოს მომხმარებელს გაუშვას:

```bash
tuist auth login --url https://tuist.dev
```

ლოკალური ან self-hosted განლაგებისთვის, შეცვალეთ URL ორივე ბრძანებაში და `tuist.toml`-ში. შეინარჩუნეთ hostname-ის მართლწერა იდენტური ყველგან. მაგალითად, `localhost` და `127.0.0.1` იყენებენ ცალკე შენახულ რწმუნებებს.

### ხელსაწყოები

შემდეგი ხელსაწყოები ხელმისაწვდომია Tuist Model Context Protocol სერვერის მეშვეობით:

ID-ები შეზღუდულია ბილდის ფარგლებში და არ უნდა შეესაბამებოდეს სხვადასხვა ბილდებს.

არასავალდებულო `start_ms` და `end_ms` ირჩევენ ნაბიჯებს, რომლებიც ემთხვევა დროის დიაპაზონს მილიწამებში ბილდის დაწყებიდან; ბოლო არ არის ჩათვლილი. ორივე ხელსაწყო იღებს ბილდის UUID-ს ან დაშბორდის URL-ს როგორც `build_run_id`. გადასცეთ დაბრუნებული ნაბიჯის `id` უცვლელად როგორც `step_id` მისი ლოგის მისაღებად. ლოგები ინახავენ 64 KiB-მდე თითო ნაბიჯზე, `log_truncated` მიუთითებს გამოტოვებულ გამოსავალზე.

ნაბიჯები ნაგულისხმევად იკრიბება Xcode ბილდების დამუშავებისას. ჩაწერილი ნაბიჯის მონაცემები ინახება 90 დღის განმავლობაში. სიის პასუხი შეიცავს `availability`-ს: `available`, როცა ჩაწერილი ნაბიჯები არსებობს, მაშინაც კი, თუ ფილტრები არაფერს ემთხვევა; `processing`, როცა ბილდი ჯერ კიდევ მუშავდება და ნაბიჯები ჯერ არ არის; ან `unavailable`, როცა ნაბიჯები არ ჩაწერილა ან ვადა გაუვიდათ.

იგივე ოპერაციები ხელმისაწვდომია HTTP API-ზე მისამართებზე `GET /api/projects/{account_handle}/{project_handle}/xcode/builds/{build_id}/steps` და `GET /api/projects/{account_handle}/{project_handle}/xcode/builds/{build_id}/steps/{step_id}`, იგივე ფილტრებითა და პაგინაციით. ორივეს სჭირდება წვდომა ბილდის პროექტის წასაკითხად.

Gradle-ისა და Bazel-ის ნაბიჯების სიები ნაგულისხმევად აბრუნებენ 20 შედეგს (მაქსიმუმ 100), მხარდაჭერილია `search`, ზუსტი `project`, `target`, `category` და `status`, თანხვედრის `start_ms` / `end_ms` ფილტრები (ბოლო არ არის ჩათვლილი) და `duration_ms` ან `start_ms` დალაგება. გადასცეთ დაბრუნებული ID-ები უცვლელად; ისინი მიბმულია თავიანთ ბილდზე. სიები აჩვენებენ `time_origin`-ს და `coverage`-ს. უფრო ძველი Gradle ანგარიშები იყენებენ `first_recorded_timestamp`-ს, რადგან ბილდის დაწყება არ აიტვირთა. Bazel პროფილები აჩვენებენ ყველა ჩაწერილ ინტერვალს `trace_profile` დაფარვით და `profile_start`-ით, როგორც დროის საწყისით. უფრო ძველი ბილდები ეყრდნობიან შენახულ BEP შეჯამებებს. წყაროს ჩანაწერების ვადა გადის 90 დღის შემდეგ. Bazel დეტალები მოიცავს სანიტიზებულ მოქმედების ლოგებს, როცა ისინი გამოქვეყნებულია. Gradle დეტალები ჩავარდნილი ამოცანის ან კონფიგურაციის ნაბიჯის შესახებ მოიცავს შეცდომის შეტყობინებას, რომელიც Tuist Gradle პლაგინმა აღნიშნა როგორც `log`: გამონაკლისის შეტყობინება და მისი მიზეზების ჯაჭვი, როგორც Gradle-ის კონსოლი ბეჭდავს მათ, სტეკის ტრეისებისა და ამოცანის გამოსავლის გარეშე, პროექტის შიგნით არსებული გზები გადაქცეულია ფარდობითად, ხოლო სერთიფიკატები და სხვა ადგილობრივი გზები დაფარულია, მაქსიმუმ 16 KiB თითო ნაბიჯზე და 32 ჩავარდნილი ნაბიჯი ბილდზე. სხვა Gradle ნაბიჯებს, პლაგინის ძველი ვერსიებით მოხსენებულ ბილდებს და სერთიფიკატების გარეშე მოხსენებებს აქვთ null `log`. კონფიგურაციის ნაბიჯები ანგარიშობენ `failure`-ს, როცა ისინი ჩავარდნენ, და `unknown`-ს სხვა შემთხვევაში. `compare_builds` მოთხოვნა იყენებს ამ დაფარვას სრული Bazel ტრეისების განსასხვავებლად შენახული შეჯამებებისგან და მიმართავს აგენტებს ნაბიჯის დეტალებზე მოქმედების შედეგებისა და ლოგებისთვის, სანამ უფრო ფართო გამოძახების გამოსავალს შეამოწმებენ.

ერთი ნაბიჯის ხელსაწყოები `get_gradle_build_step` და `get_bazel_build_step` იღებენ ნაბიჯს ID-ით და არ იღებენ დროის ფილტრებს; გამოიყენეთ შესაბამისი სიის ხელსაწყოები ნაბიჯების ფილტრაციისთვის დროის დიაპაზონით.

Bazel ნაბიჯის ID-ები, რომლებიც დაბრუნებულია შენახული შეჯამებებიდან, რჩება წასაკითხად, თუ სრული პროფილი მოდის სიის ჩვენებასა და ნაბიჯის მიღებას შორის. ინდექსირებული პროფილი, რომლის ნაბიჯის მონაცემების ვადა გაუვიდა, ანგარიშობს მიუწვდომლობას. Gradle ნაბიჯების სიები მოიცავს ნულოვანი ხანგრძლივობის ქეშირებულ და გამოტოვებულ ოპერაციებს.

REST ბოლო წერტილი `GET /api/projects/{account_handle}/{project_handle}/bazel/invocations` იღებს იგივე ფილტრებს.

დააყენეთ `remote_execution: true` `list_bazel_build_steps`-ზე, რათა დააბრუნოთ მხოლოდ მოქმედებები ინდექსირებული პროფილებიდან უსაფრთხოდ დაკავშირებული სერვერის ფაზის დროებით. სიისა და დეტალური პასუხები აჩვენებენ არასავალდებულო nullable `remote_queue_ms`-ს, `remote_input_fetch_ms`-ს, `remote_execution_ms`-ს და `remote_output_upload_ms`-ს. მნიშვნელობები აჯამებენ ჩაწერილ ფაზებს, მათ შორის მოქმედების შიგნით განმეორებით ცდებს; არარსებული ან null მნიშვნელობები ნიშნავს მიუწვდომლობას, არა ნულს. ისინი არიან პროფილის დაკვირვებები, არა გადასახდელი გამოყენება ან ახალი შესრულების მტკიცებულება, რადგან ქეშირებულ სერვერის შედეგებს შეიძლება ჰქონდეთ შესრულების მეტამონაცემები. კლიენტის ატვირთვები გამორიცხულია. უფრო ძველმა ან გაურკვეველმა პროფილებმა შეიძლება არ დააბრუნონ შესაბამისი მოქმედებები მაშინაც კი, თუ დისტანციური მუშაობა მოხდა. ნაბიჯის REST ბოლო წერტილი იღებს იგივე `remote_execution=true` ფილტრს. დაშბორდის Remote execution ტაბი იყენებს იგივე მოთხოვნას და 90-დღიან შენახვას.

ტესტის ლოგები შეიცავენ `target_label`-ს და ცდის `status`-ს იმ ტესტის შედეგიდან, საიდანაც ისინი მოვიდნენ, ასე რომ `target_label: "//foo:bar_test"` აბრუნებს მხოლოდ იმ სამიზნის ტესტის ლოგებს. `errors: true` აბრუნებს ჩავარდნილი ცდების ტესტის ლოგებს და stderr პროგრესის ნაწილებს, რომლებიც შეიცავენ ხაზს, რომელიც Bazel-ის რეპორტიორი იწყება `ERROR:`-ით, `FAIL:`-ით ან `TIMEOUT:`-ით. პროგრესის გამოსავალი არ არის მიკუთვნებული სამიზნეებისთვის, და ლოგებს, რომლებიც დაიწერა მიკუთვნების ჩაწერამდე, აქვთ ცარიელი ველები. ჩავარდნილი მოქმედებები და მათი საკუთარი გამოსავალი ხელმისაწვდომია თითოეული სამიზნისთვის `list_bazel_build_steps`-დან, და თითოეული ტესტის საქმის ჩავარდნები ტესტების გაშვების ხელსაწყოებიდან.

`get_build_entity` მეტრიკები მოიცავს `duration_samples`-ს, დაკვირვებების რაოდენობას ჩაწერილი დროით: ნამდვილი ნულოვანი ხანგრძლივობები ითვლება, გამოტოვებული დრო — არა. ეს რაოდენობა შეიძლება იყოს დაკვირვებების რაოდენობაზე ნაკლები; მიუწვდომელი ხანგრძლივობის სტატისტიკა რჩება null.

Xcode მოდულების ხანგრძლივობები მოდის გაზომილი სამიზნე კომპილაციებიდან ბილდის ჟურნალებში. მოდულის ქეშის ამოხსნები და სამიზნეები კომპილაციის გარეშე არ მონაწილეობენ ხანგრძლივობის შერჩევებში. კომპილაციის დაკვირვებები მიუთითებენ Xcode ბილდზე; ქეშის მოვლენები მიუთითებენ გენერაციის ან ქეშის ბრძანებაზე.

Bazel მოქმედებები იდენტიფიცირდება სამიზნე წარწერით, მნემონიკით და კონფიგურირებული პირველადი გამომავალით, რაც ინარჩუნებს ცალკეულ მოქმედებებსა და კონფიგურაციებს განცალკევებულად, შეყვანაზე დამოკიდებული ქეშის დიჯესტების გარეშე. ისტორია იწერს BEP-ით მოხსენებულ შესრულებებს, არა ქეშის ძიებებს ან ტრეისის პროფილის ფაზებს. სრული შესრულების დაფარვა მოითხოვს `--build_event_publish_all_actions`-ს; არტეფაქტების მიწოდება საუკეთესო ძალისხმევით ხდება, ამიტომ გამოტოვებული დაკვირვებები არ არის იმის მტკიცებულება, რომ მუშაობა არ შესრულებულა. ძველი Kura პაკეტები სტაბილური იდენტობის ან შესრულების დაწყების გარეშე რჩება მიღებული, მაგრამ არაინდექსირებული. დასრულების დროის გაზომვების არარსებობა რჩება მიუწვდომელი და ნამდვილი ნულოვანი ხანგრძლივობები ითვლება.

Mix მოდულების ხანგრძლივობები ზომავენ შემცველი ფაილის კომპილაციას, არა დამოუკიდებლად გაზომილ მოდულის მუშაობას. Struo მოქმედებები იყენებენ გამოცხადებულ სამიზნე/შესაძლებლობა/ინდექსის სლოტებს, როდესაც კლიენტმა მოახსენა სამიზნე ასოციაციები; მხოლოდ დიაგნოსტიკური წარწერები არ არის სტაბილური იდენტობები. არსებული კლიენტები და გაშვების დონის ხელსაწყოები რჩება მხარდაჭერილი უცვლელად.

Cargo ყუთები დაჯგუფებულია ზუსტად ჩაწერილი ყუთის ფესვით, სახელით და სახეობით. Checkout-ის გზის ცვლილებებმა შეიძლება გაყოს ისტორიები, ხოლო ბილდის პროფილები, ფუნქციები და სამიზნე ტრიპლეტები არ განირჩევა. ისტორია ზომავს rustc გამოძახებებს, არა ფაილის დონის მუშაობას ან ქეშის მოხვედრებს; არარსებული სამუშაოები არ ადგენენ წაშლას ან სრულ სამუშაო სივრცის ინვენტარს.

ანალიტიკის წაკითხვებს აქვს შემოსაზღვრული მეხსიერება და შესრულების დრო. თუ მოთხოვნა აღემატება ამ ლიმიტებს, ხელსაწყო აბრუნებს შეცდომას ცარიელი შედეგის გამოგონების ნაცვლად.

ახალი დაკვირვებები ინდექსირდება განლაგების შემდეგ; ეს ფუნქცია არ ავსებს არსებულ გაშვების ტელემეტრიას. იდენტობის მეტამონაცემები ინახება ინდივიდუალურ დაკვირვებებზე უფრო დიდხანს <.localized_link href="/guides/server/data-retention">მონაცემთა შენახვის პოლიტიკის</.localized_link> შესაბამისად.

### მოვლენები

კლიენტები, რომლებიც იყენებენ უმდგომარეობიან `2026-07-28` Model Context Protocol ციკლს, შეუძლიათ გამოიძახონ `events/list` მოვლენებისა და მათი payload-ის სქემების აღმოსაჩენად:

| მოვლენა | როდის იგზავნება | გამოწერის ფილტრი |
|-------|-----------------|---------------------|
| `test_case.marked_flaky` | სატესტო შემთხვევა იცვლება არაარასტაბილურიდან არასტაბილურზე. | `account_handle`, `project_handle` |
| `build.failed` | ლოკალური ან უწყვეტი ინტეგრაციის Xcode, Gradle ან Bazel ბილდი მთავრდება შეცდომით. | `account_handle`, `project_handle` |
| `test_run.failed` | ლოკალური ან უწყვეტი ინტეგრაციის ტესტების გაშვება მთავრდება შეცდომით, შერწყმული დაყოფილი გაშვების ან მიტოვებული გაშვების ჩათვლით. | `account_handle`, `project_handle` |
| `ci_job.failed` | Tuist-ის გამშვების დავალება მთავრდება შეცდომით. | `account_handle` |

გამოსაწერად კლიენტი იძახებს `events/subscribe` მოვლენის სახელით, ზემოთ ჩამოთვლილი ხელსაწყოებით `arguments`-ში და `webhook` მიწოდებით, რომელიც შეიცავს `https://` callback URL-ს და `whsec_` ხელმოწერის საიდუმლოს. პროექტის მოვლენები მოითხოვს ანგარიშის წევრობას და შესაბამისი ტესტის ან ბილდის მონაცემებზე წვდომას; გამშვების დავალების მოვლენები მოითხოვს ანგარიშის წევრობას და გამშვებზე წვდომას. დადასტურებულმა [`auth.md`](https://workos.com/auth-md) წვდომის ტოკენებმა, ანგარიშის ტოკენებმა და ბრაუზერის ავტორიზაციის ნებართვებმა შეუძლიათ შექმნან გამოწერები; მიწოდება ჩერდება, როდესაც შესაბამისი სერთიფიკატი აღარ არის აქტიური. თითოეულ მომხმარებელს შეუძლია ჰქონდეს 25-მდე აქტიური გამოწერა. Tuist აგზავნის ვერიფიკაციის გამოწვევას callback-ზე გამოწერის შენახვამდე. callback-მა უნდა დააბრუნოს ობიექტი იგივე `challenge` მნიშვნელობით. გამოწერა ძალაშია შვიდი დღის განმავლობაში, შეიძლება განახლდეს ხელახლა გამოწერით და წყვეტს მიწოდებას, როდესაც მომხმარებლის წვდომა ან სერთიფიკატი წაიშლება. არასავალდებულო `ttlMs` შეზღუდულია ერთ საათსა და 30 დღეს შორის. Tuist ხელახლა ცდილობს დროში ამოწურულ callback-ს და აუქმებს მას სამი თანმიმდევრული დროის ამოწურვის შემდეგ, რომლებიც მოიცავს ხუთ წუთს; ხელახლა გამოიწერეთ callback-ის აღდგენის შემდეგ.

როდესაც მოვლენა ხდება, Tuist აგზავნის მის რესურსის იდენტიფიკატორს და დაფის URL-ს callback-ზე. ბილდისა და ტესტების გაშვების შეცდომები ასევე შეიცავს `is_ci`-ს და `git_branch`-ს, რათა კლიენტებმა შეძლონ ლოკალური შეცდომების იგნორირება ან ფილტრაცია განშტოების მიხედვით. ბილდის მოვლენები შეიცავს `build_system`-ს; გამშვების დავალების მოვლენები შეიცავს როგორც `workflow_job_id`-ს, ისე `workflow_run_id`-ს. მოთხოვნა შეიცავს გამოწერის იდენტიფიკატორს და [Standard Webhooks](https://www.standardwebhooks.com/) ხელმოწერის ჰედერებს, რათა კლიენტმა შეძლოს მისი წარმომავლობის ვერიფიცირება. Tuist ხელახლა ცდილობს შეცდომიან მიწოდებებს, ამიტომ კლიენტებმა უნდა გამოიყენონ სტაბილური `eventId` დუბლიკატების გასაფილტრად. Payload არ შეიცავს ტესტების სახელებს, ლოგებს და შეცდომის შეტყობინებებს; კლიენტს შეუძლია მიიღოს ეს დეტალები ზემოთ ჩამოთვლილი ინსტრუმენტების მეშვეობით და გადაწყვიტოს, შეატყობინოს თუ არა გუნდს ან დაიწყოს დებაგინგი. კლიენტებს შეუძლიათ შეაჩერონ მიწოდება `events/unsubscribe`-ით.

პროექტის მონაცემების პრომპტები იღებენ `account_handle`-ს და `project_handle`-ს კვლევის კონკრეტულ პროექტამდე შეზღუდვისთვის. შედარების პრომპტები ასევე იღებენ `base` და `head` არგუმენტებს ორი შესადარებელი ელემენტის მითითებისთვის (ID-ით, დაფის URL-ით ან განშტოების სახელით). `ask_tuist` იღებს `question`-ს პროექტის პარამეტრების ნაცვლად. `integrate_gradle_project` ასევე იღებს `features`-ს, Gradle ინტეგრაციების მძიმით გამოყოფილ სიას გამოსაყენებლად: `remote_cache`, `build_insights`, `test_insights`, `flaky_tests` და `test_sharding`. `integrate_bazel_project` იღებს არასავალდებულო `server_url`-ს თვითმასპინძლებელი ან ლოკალური ინსტალაციებისთვის. `integrate_xcode_project` იღებს `features`-ს `xcode_cache`-ით, `build_insights`-ით, `test_insights`-ით და `test_sharding`-ით.

#### Gradle ინტეგრაციის პრომპტის ფუნქციები

`integrate_gradle_project` პრომპტი და `get_gradle_integration_guide` ინსტრუმენტი აღწერენ სრულ მოწყობის სამუშაო ნაკადს. ინსტრუმენტს ასევე მიმართავს სერვერის ინიციალიზაციის ინსტრუქციები, რაც მას აღმოჩენადს ხდის აგენტებისთვის, რომლებიც არ ჩამოთვლიან პრომპტებს.

| ფუნქცია | რას აკონფიგურირებს აგენტი |
|---------|---------------------------|
| `remote_cache` | ააქტიურებს Gradle-ის ბილდის ქეშს, აკონფიგურირებს Tuist დისტანციური ქეშის ატვირთვის პოლიტიკას და გირჩევთ ატვირთვას მხოლოდ უწყვეტი ინტეგრაციის გამშვებებიდან ლოკალური მხოლოდ-წაკითხვის გამოყენებით. |
| `build_insights` | აყენებს Tuist Gradle პლაგინს და საჭიროების შემთხვევაში აკონფიგურირებს ბილდის ანალიტიკის ატვირთვის ქცევას. |
| `test_insights` | აყენებს Tuist Gradle პლაგინს, რათა Gradle `Test` დავალების შედეგები ავტომატურად აიტვირთოს. |
| `flaky_tests` | გასწავლით არასტაბილური ტესტების აღმოჩენის მოწყობას, Gradle Test Retry პლაგინის არასავალდებულო გამოყენებას და ტესტის კარანტინის კონფიგურაციას. |
| `test_sharding` | ამატებს უწყვეტი ინტეგრაციის სამუშაო ნაკადს `tuistPrepareTestShards`-თვის, shard მატრიცის გენერაციას და `TUIST_SHARD_INDEX`-ზე დაფუძნებულ ტესტების შესრულებას. |

როდესაც `features` გამოტოვებულია, პრომპტი სთხოვს აგენტს გაარკვიოს, რომელი ინტეგრაციები სურს მომხმარებელს ან გამოიტანოს უმცირესი სასარგებლო ნაკრები მოთხოვნიდან Gradle პროექტის რედაქტირებამდე.

#### Xcode ინტეგრაციის პრომპტის ფუნქციები

`integrate_xcode_project` პრომპტი აღწერს ყველა Xcode ინტეგრაციას, რომელსაც Tuist მხარს უჭერს:

| ფუნქცია | რას აკონფიგურირებს აგენტი |
|---------|---------------------------|
| `xcode_cache` | აკონფიგურირებს `tuist setup cache`, გენერირებული პროექტის ქეშის პარამეტრებს, Xcode ქეშის ბილდის ხელით მითითებულ პარამეტრებს და ატვირთვის პოლიტიკას, რომელიც შემოიფარგლება მხოლოდ უწყვეტი ინტეგრაციის გამშვებებით. |
| `build_insights` | აკონფიგურირებს `tuist inspect build`-ს, `tuist xcodebuild`-ს, `-resultBundlePath`-ს და არჩევით მანქანურ მეტრიკებს `tuist setup insights`-ის საშუალებით. |
| `test_insights` | აკონფიგურირებს `tuist inspect test`-ს, სქემის ტესტის post-actions-ებს და შედეგების ბანდლის გენერაციას უწყვეტი ინტეგრაციის ტესტების გაშვებისთვის. |
| `test_sharding` | ამატებს Xcode-ის ან გენერირებული პროექტის shard-ების დაგეგმვისა და shard-ების შესრულების სამუშაო ნაკადს `TUIST_SHARD_INDEX`-ით. |

როდესაც `features` გამოტოვებულია, პრომპტი სთხოვს აგენტს გაარკვიოს, რომელი ინტეგრაციები სურს მომხმარებელს ან გამოიტანოს უმცირესი სასარგებლო ნაკრები მოთხოვნიდან Xcode პროექტის რედაქტირებამდე.
