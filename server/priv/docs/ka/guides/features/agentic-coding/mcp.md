# Model Context Protocol

[Model Context Protocol (MCP)](https://modelcontextprotocol.io/docs/getting-started/intro) არის ღია სტანდარტი, რომელიც საშუალებას აძლევს ხელოვნური ინტელექტის აგენტებს ურთიერთქმედება გარე სერვისებთან და მონაცემთა წყაროებთან. ის უზრუნველყოფს ისეთი აპლიკაციების, როგორიცაა [Claude](https://claude.ai/), [Claude Code](https://docs.anthropic.com/en/docs/claude-code), [Codex](https://developers.openai.com/codex/), და რედაქტორების, მაგალითად [Zed](https://zed.dev), [Cursor](https://www.cursor.com) ან [Visual Studio Code](https://code.visualstudio.com), თავსებადობას Tuist-თან.

Tuist მასპინძლობს Model Context Protocol-ის სერვერულ წერტილს მისამართზე `https://tuist.dev/mcp`. თქვენი კლიენტის მიერთებით, აგენტებს შეუძლიათ მიუწვდომლობა თქვენს Tuist პროექტის მონაცემებზე, მათ შორის ტესტების ანალიტიკაზე, არასტაბილური ტესტების ანალიზზე და სხვა. უმეტესი ინსტრუმენტი მხოლოდ წაკითხვადია და შეზღუდულია ავტორიზებული Tuist პროექტის მონაცემებით. ანგარიშის მოწყობის ინსტრუმენტებს შეუძლიათ ანგარიშების ჩამოთვლა, ორგანიზაციების შექმნა, პროექტების შექმნა და არსებული მომხმარებლების დამატება ორგანიზაციებში, როდესაც ავტორიზებულ მომხმარებელს აქვს საჭირო ნებართვები. ყოველი ინსტრუმენტი აცხადებს ანოტაციებს, რომლებიც მიუთითებს, არის თუ არა ის მხოლოდ წაკითხვადი, შეუძლია თუ არა გამოიწვიოს ძნელად შექცევადი ცვლილება და შეუძლია თუ არა შეცვალოს საჯარო ინტერნეტის მდგომარეობა. ანგარიშის მოწყობის ინსტრუმენტები მოითხოვს მომხმარებლის ავტორიზაციას. ისინი არ არის ხელმისაწვდომი პროექტის ტოკენებისთვის ან ჩვეულებრივი ანგარიშის ტოკენებისთვის. როდესაც მომხმარებელი ბრაუზერში ავტორიზებს კლიენტს ან ითხოვს `auth.md` რეგისტრაციას, Tuist ასოცირებს ამ სერთიფიკატს მომხმარებელთან მხოლოდ Model Context Protocol-ის წერტილზე, რათა მოწყობის ინსტრუმენტებმა შეასრულონ მოთხოვნილი სამუშაო პროცესი.

Tuist ახორციელებს [2026-07-28 პროტოკოლს](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http). მოთხოვნები არის უსესიო: კლიენტები აგზავნიან პროტოკოლის მეტამონაცემებს ყოველ მოთხოვნასთან ერთად და შეუძლიათ პირდაპირ გამოიძახონ ინსტრუმენტები ინიციალიზაციის გარეშე. `server/discover` აბრუნებს სერვერის იდენტობას, შესაძლებლობებს, მხარდაჭერილ ვერსიებს და ინსტრუქციებს. არ არსებობს სესიის იდენტიფიკატორები ან დამოუკიდებელი მოვლენათა ნაკადები. კლიენტები, რომლებიც იყენებენ 2025-06-18 ან 2025-03-26 ინიციალიზაციის ნაკადს, კვლავ მხარდაჭერილია; ისინიც მუშაობენ სერვერის სესიების გარეშე.

## Model Context Protocol უნარების წინააღმდეგ

Model Context Protocol-ის ინსტრუმენტებსა და <.localized_link href="/guides/features/agentic-coding/skills">უნარებს</.localized_link> შორის შესაძლოა იყოს გადაფარვა ფუნქციებში. არსებული გადაფარვის გათვალისწინებით, აირჩიეთ ერთი მიდგომა სამუშაო პროცესისთვის და გამოიყენეთ ის თანმიმდევრულად, ნაცვლად ორივეს ერთდროულად გამოყენებისა.

კლიენტებისთვის, რომლებიც მხარდაჭერენ პლაგინების ინსტალაციას, გამოიყენეთ <.localized_link href="/guides/features/agentic-coding/plugins">Tuist პლაგინები</.localized_link> ორივეს ერთად ინსტალაციისთვის.

## კონფიგურაცია

დაამატეთ `https://tuist.dev/mcp` როგორც დაშორებული Model Context Protocol სერვერი თქვენს კლიენტში. სერვერის ინიციალიზაციის ინსტრუქციები და საჯარო სერვერის ბარათი აღწერს OAuth 2.0-ს დინამიური კლიენტის რეგისტრაციით და სტანდარტული ბრაუზერის ავტორიზაციის ნაკადით, აგენტებისგან გარე ავტორიზაციის დოკუმენტების მოთხოვნის ან მათზე გადასვლის გარეშე. ეს სერვერის დონის ინსტრუქციები ინარჩუნებს სამუშაო პროცესის მითითებებს ზოგადს: ინსტრუმენტის ავტორიზაცია არ ავტორიზებს ადგილობრივ ბრძანების სტრიქონის ინსტრუმენტებს ან აგების სისტემის ინტეგრაციებს, და აგენტებმა უნდა შეამოწმონ მოთხოვნილი ცვლილებები შესაბამისი Tuist ინსტრუმენტების მეშვეობით. აგების სისტემის სპეციფიკური მოწყობა და ავტორიზაციის შემოწმებები დოკუმენტირებულია ინტეგრაციის სახელმძღვანელოებში და მოთხოვნებში. Tuist კვლავ აცხადებს როგორც [Open Authorization](https://oauth.net/2/)-ის აღმოჩენის მეტამონაცემებს, ასევე მიმდინარე [auth.md პროტოკოლს](https://workos.com/auth-md) მისამართზე `https://tuist.dev/auth.md` ცალ-ცალკე.

თუ თქვენი რომელიმე ორგანიზაცია აიძულებს ერთჯერად შესვლას (SSO), ბრაუზერში კლიენტის ავტორიზაცია მოითხოვს სესიას, რომელიც შესულია ამ ორგანიზაციის მეშვეობით, და Tuist საჭიროების შემთხვევაში ჯერ პროვაიდერთან გაგზავნით. იხილეთ <.localized_link href="/guides/integrations/authentication/sso#choose-an-enrollment-policy">ერთჯერადი შესვლა</.localized_link>.

წერტილი იღებს უსესიო `2026-07-28` Model Context Protocol მოთხოვნის სიცოცხლის ციკლს, მათ შორის `server/discover`-ს, ძველ სესიაზე დაფუძნებულ ციკლთან ერთად. არსებულმა კლიენტებმა შეიძლება განაგრძონ მიმდინარე მიერთების მეთოდის გამოყენება.

კლიენტებს, რომლებიც მხარდაჭერენ Model Context Protocol-ის მოვლენებს, შეუძლიათ გამოიწერონ პროექტის მოვლენები. იხილეთ [მოვლენები](#events) ხელმისაწვდომი მოვლენებისა და მიწოდების მოთხოვნებისთვის.

კლიენტებს, რომლებიც უკვე მხარდაჭერენ დაშორებულ ბრაუზერის ავტორიზაციას, შეუძლიათ განაგრძონ ბრაუზერში ავტორიზაცია. კლიენტებსა და აგენტებს, რომლებიც მხარდაჭერენ `auth.md`-ს, შეუძლიათ ანონიმურად დარეგისტრირება, წარმოადგინონ სანდო პროვაიდერის იდენტობის დადასტურება ან დაიწყონ სერვისით ავტორიზებული ელფოსტის მოთხოვნა. რეგისტრაცია აბრუნებს Tuist-ით ხელმოწერილ იდენტობის დადასტურებას, რომელსაც აგენტი ცვლის სტანდარტულ ტოკენის წერტილზე ერთსაათიანი წვდომის ტოკენისთვის. Tuist აქვეყნებს თავის საჯარო ხელმოწერის გასაღებს და მხარდაჭერს სტანდარტულ ტოკენის გაუქმებასა და პროვაიდერის უსაფრთხოების მოვლენების მიწოდებას.

არაავტორიზებულმა აგენტმა უნდა წაიკითხოს `WWW-Authenticate` ჰედერი, რომელიც დაბრუნდა Model Context Protocol-ის წერტილიდან, მიიღოს დაცული რესურსის მეტამონაცემები, მიიღოს ავტორიზაციის სერვერის მეტამონაცემები და მიჰყვეს მის `agent_auth.skill` URL-ს. Tuist ასევე აბრუნებს იმავე ადგილობრივ `auth_md` URL-ს არაავტორიზებული პასუხის სხეულში, რათა ენის მოდელზე დაფუძნებულმა კლიენტებმა შეძლონ ნაკადის აღმოჩენა ნატიური კლიენტის ინტეგრაციაზე დამოკიდებულების გარეშე. განლაგების ადგილობრივი დოკუმენტი არის სიმართლის წყარო წერტილის სახელების, მოთხოვნის სხეულების, მოთხოვნის გამოკითხვისა და დადასტურების გაცვლისთვის.

სანამ აგენტი დაიწყებს ელფოსტის მოთხოვნას, მან უნდა სთხოვოს მომხმარებელს დაადასტუროს ელფოსტის მისამართი მათი Tuist ანგარიშისთვის. მან არ უნდა გამოიტანოს ეს მისამართი პროვაიდერის პროფილიდან, Git კონფიგურაციიდან, გარემოს ცვლადიდან ან სესიის მეტამონაცემებიდან.

წერტილი იყენებს `mcp` სკოპის ჯგუფს. ანონიმურმა წინასწარ მოთხოვნის სერთიფიკატმა შეიძლება აღმოაჩინოს შესაძლებლობები და წაიკითხოს საჯარო ინტეგრაციის მითითებები, მაგრამ ის არ განიხილება როგორც შესული მომხმარებელი. ბრაუზერის ავტორიზაციის ან მოთხოვნის შემდეგ, სერთიფიკატი არის მომხმარებელზე ორიენტირებული და ყოველი ინსტრუმენტი ახორციელებს იმავე ავტორიზაციის შემოწმებებს, რასაც დაფა. იხილეთ <.localized_link href="/guides/server/authentication#scope-groups">სკოპის ჯგუფების დოკუმენტაცია</.localized_link> დეტალებისთვის.

ინსტრუმენტები წყდება პროექტებზე, რომლებსაც ავტორიზებულ მომხმარებელს უკვე შეუძლია წაკითხვა. Xcode და Gradle აგების ინსტრუმენტები იღებენ აგების UUID-ს ან დაფის URL-ს. UUID-მ უნდა აიდენტიფიციროს ზუსტად ერთი პროექტი; თუ ის ჩნდება რამდენიმე პროექტში, ინსტრუმენტი აბრუნებს „არ არის ნაპოვნი“-ს, ნაცვლად სხვა პროექტის ანგარიშის არჩევისა. პროექტზე ორიენტირებული დაფისა და API-ის წაკითხვები რჩება ხელმისაწვდომი. მოხსენებული აქტორის იდენტიფიკატორები არიან დაუდასტურებელი ლეიბლები, არა სერთიფიკატები ან დამატებითი წვდომის უფლებები.

აგების სიისა და დეტალების ინსტრუმენტები აჩვენებენ არასავალდებულო `tuist_version` მეტამონაცემებს: Xcode-ისა და Cargo-სთვის — Tuist CLI, Gradle-ისთვის — Tuist Gradle პლაგინი, ხოლო Mix-ისთვის — `tuist_ex` ბიბლიოთეკა. Xcode ასევე აჩვენებს `tuist_generation_version`-ს მის მიერ დაკავშირებული პროექტის გენერაციის მოვლენიდან, რაც შეიძლება განსხვავდებოდეს ატვირთვის CLI-ისგან. გამოტოვებული მონაცემები არის null, არა სერვერიდან ან სხვა ანგარიშიდან გამოყვანილი. Bazel იყენებს თავის არსებულ `bazel_version`-ს; Once-ის გაშვების დეტალები აჩვენებს `once_version`-ს. ეს ველები აღწერენ მოხსენებულ ვერსიებს, არა დადასტურებულ იდენტობას ან სადენის კონტრაქტის ვერსიებს. REST აგების წერტილები აჩვენებენ იმავე მეტამონაცემებს. არსებული ინტეგრაციისა და ცვალებადი ტესტების უნარები არ არის დამოკიდებული ვერსიის ველებზე და არ საჭიროებს სამუშაო ნაკადის ცვლილებებს.

Tuist-ის ოპერატორები, რომლებიც იკვლევენ მომხმარებლის ანგარიშს, ამას აკეთებენ Tuist-ის შიდა ოპერაციული ინსტრუმენტების მეშვეობით, რომელიც იწერს ყოველ ზარს; ამ წერტილთან პირდაპირი კავშირი არ იძლევა წვდომას მომხმარებლის საკუთარი წევრობების გარდა.

## WebMCP

ბრაუზერებში, რომლებიც მხარს უჭერენ [WebMCP](https://webmachinelearning.github.io/webmcp)-ს, Tuist-ის გვერდები რეგისტრირებენ ინსტრუმენტებს `document.modelContext`-ით, ასე რომ ბრაუზერში ჩაშენებულ აგენტებს შეუძლიათ მათი გამოძახება დამატებითი კონფიგურაციის გარეშე. ზარები სრულდება Tuist სერვერზე.

- **ვებგვერდისა და დოკუმენტაციის გვერდები** რეგისტრირებენ დოკუმენტაციისა და წყაროს ინსტრუმენტებს (`search_tuist`, `search_tuist_code`, `list_tuist_files` და `read_tuist_file`). მათ არ სჭირდებათ თქვენგან სისტემაში შესვლა.
- **ანგარიშის დაფის გვერდები**, როდესაც სისტემაში ხართ შესული, რეგისტრირებენ Tuist-ის მხოლოდ წასაკითხ ინსტრუმენტებს ამ ანგარიშისთვის. ისინი სრულდება როგორც შესული მომხმარებელი, ამიტომ მხოლოდ იმ მონაცემებთან აქვთ წვდომა, რომელთა წაკითხვაც შეგიძლიათ დაფაზე, და მხოლოდ იმ ანგარიშთან, რომელსაც უყურებთ. როდესაც გადადიხართ სხვა ანგარიშის გვერდებზე, ინსტრუმენტები იცვლება იმ ანგარიშის ინსტრუმენტებით.

ინსტრუმენტები, რომლებიც ქმნიან, ცვლიან ან შლიან მონაცემებს, არ არის ხელმისაწვდომი WebMCP-ით, რადგან ბრაუზერის აგენტი იღებს ინსტრუმენტებს თქვენს მიერ დამატების გარეშე და კითხულობს აგებისა და ტესტების მიერ წარმოქმნილ შინაარსს. დაუკავშირეთ MCP კლიენტი `/mcp` წერტილს ამ ინსტრუმენტების გამოსაყენებლად.

თუ ორგანიზაცია აიძულებს ერთჯერად შესვლას (SSO), შედით დაფაზე მისი პროვაიდერის მეშვეობით, რათა გამოიყენოთ მისი ინსტრუმენტები.

## აგების სისტემის ინტეგრაციები იყენებენ ორ კრედენციალს

კრედენციალი, რომელიც გამოიყენება Model Context Protocol ინსტრუმენტებისთვის, არ ამოწმებს Gradle პლაგინს ან Bazel-ის დისტანციურ სერვისებს. სანამ აგენტი ჩაასწორებს ან გადაამოწმებს Gradle ან Bazel ინტეგრაციას, მან უნდა გაუშვას:

```bash
tuist auth whoami --url https://tuist.dev
```

თუ ეს ბრძანება არ არის ავტორიზებული, აგენტმა უნდა შეწყვიტოს მუშაობა და სთხოვოს მომხმარებელს გაუშვას:

```bash
tuist auth login --url https://tuist.dev
```

ლოკალური ან თვითმასპინძელი განლაგებისთვის, შეცვალეთ URL ორივე ბრძანებაში და `tuist.toml`-ში. ყველგან შეინარჩუნეთ ზუსტად იგივე ჰოსტის სახელი. მაგალითად, `localhost` და `127.0.0.1` იყენებენ ცალკეულ შენახულ კრედენციალებს.


## შესაძლებლობები

### ინსტრუმენტები

შემდეგი ინსტრუმენტები ხელმისაწვდომია Tuist Model Context Protocol სერვერის მეშვეობით:

ყოველი ინსტრუმენტი აქვეყნებს ადამიანისთვის წასაკითხ აღწერას შესაბამისი შეყვანისა და გამოტანის სქემებთან ერთად. წარმატებული ზარები აბრუნებენ სტრუქტურირებულ შინაარსს, რომელიც შეესაბამება გამოცხადებულ გამოტანის სქემას, პლუს იგივე შედეგი ტექსტის სახით სერიალიზებული კლიენტებისთვის, რომლებიც ჯერ არ იყენებენ სტრუქტურირებულ შინაარსს.

არასავალდებულო `start_ms` და `end_ms` ირჩევენ ნაბიჯებს, რომლებიც ემთხვევა დროის დიაპაზონს მილიწამებში ბილდის დაწყებიდან; ბოლო გამორიცხულია. ორივე ინსტრუმენტი იღებს ბილდის UUID-ს ან დაფის URL-ს როგორც `build_run_id`. გადაეცით დაბრუნებული ნაბიჯის `id` უცვლელად როგორც `step_id` მისი ლოგის მისაღებად. ლოგები ინახავენ 64 KiB-მდე თითო ნაბიჯზე, `log_truncated` მიუთითებს გამოტოვებულ გამომავალ მონაცემებზე.

ნაბიჯები გროვდება ნაგულისხმევად, როცა Xcode ბილდები მუშავდება. ჩაწერილი ნაბიჯის მონაცემები ინახება 90 დღის განმავლობაში. სიის პასუხი შეიცავს `availability`-ს: `available`, როცა ჩაწერილი ნაბიჯები არსებობს, მაშინაც კი, თუ ფილტრები არაფერს ემთხვევა; `processing`, როცა ბილდი ჯერ კიდევ მუშავდება და ნაბიჯები ჯერ არ არის; ან `unavailable`, როცა ნაბიჯები არ ჩაწერილა ან ამოიწურა.

Gradle და Bazel ნაბიჯების სიები ნაგულისხმევად აბრუნებენ 20 შედეგს (მაქსიმუმ 100), მხარდაჭერილია `search`, ზუსტი `project`, `target`, `category` და `status`, გადაფარვითი `start_ms` / `end_ms` ფილტრები (ბოლო არ შედის) და დალაგება `duration_ms` ან `start_ms` მიხედვით. დააბრუნეთ მიღებული IDs უცვლელად; ისინი მიბმულია კონკრეტულ ბილდზე. სიები ასახავს `time_origin`-ს და `coverage`-ს. ძველი Gradle ანგარიშები იყენებენ `first_recorded_timestamp`-ს, რადგან ბილდის დაწყების დრო არ აიტვირთა. Bazel პროფილები ასახავს ყველა ჩაწერილ ინტერვალს `trace_profile` დაფარვით და `profile_start`-ს როგორც დროის საწყისს. ძველი ბილდები ეყრდნობიან შენახულ BEP შეჯამებებს. წყაროს ჩანაწერები იშლება 90 დღის შემდეგ. Bazel დეტალები მოიცავს გასუფთავებულ ქმედების ლოგებს, როცა ისინი გამოქვეყნებულია; Gradle დეტალში `log` არის null. `compare_builds` მოთხოვნა იყენებს ამ დაფარვას სრული Bazel ტრეისების შესანახი შეჯამებებისგან განსასხვავებლად და მიმართავს აგენტებს ნაბიჯის დეტალებისკენ ქმედების შედეგებისა და ლოგებისთვის, სანამ ფართო გამოძახების შედეგებს შეამოწმებენ.

Bazel ნაბიჯების IDs, რომლებიც დაბრუნდა შენახული შეჯამებებიდან, რჩება წაკითხვადი, თუ სრული პროფილი მიიღება სიის ჩვენებისა და ნაბიჯის მიღების შუალედში. ინდექსირებული პროფილი, რომლის ნაბიჯის მონაცემები ამოიწურა, აბრუნებს ხელმიუწვდომლობას. Gradle ნაბიჯების სიები მოიცავს ნულოვანი ხანგრძლივობის ქეშირებულ და გამოტოვებულ ოპერაციებს.

ეს ინსტრუმენტები ეტაპობრივად ვრცელდება და აბრუნებენ მონაცემებს მხოლოდ იმ პროექტებისთვის, სადაც ისინი ჩართულია; სხვა პროექტებისთვის ისინი აბრუნებენ შეცდომას ცარიელი შედეგის ნაცვლად. ტიპი ხელმისაწვდომია მხოლოდ იმ პროექტებისთვის, რომლებიც იყენებენ შესაბამის ბილდის ხელსაწყოთა ჯაჭვს. ინსტრუმენტები იღებენ შეზღუდულ `start_at`/`end_at` ფილტრებს, `environment` (`any`, `ci` ან `local`) და ზუსტ `branch`. `list_build_entities` იღებს `q`-ს; `list_build_entity_history` მხარს უჭერს გამჭვირვალე `after`/`before` კურსორებს. უცნობი დროის ან ქეშის დაკვირვებები რჩება მიუწვდომელი ნულის ან გამოტოვების ნაცვლად. ისტორია მიუთითებს ჩაწერილ მშობელსა და ნატიურ გაშვებაზე დაწვრილებითი შესწავლისთვის არსებული გაშვების ინსტრუმენტების გამოყენებით.

`get_build_entity` მეტრიკები მოიცავს `duration_samples`-ს, დაკვირვებების რაოდენობას ჩაწერილი დროით: რეალური ნულოვანი ხანგრძლივობები ითვლება, გამოტოვებული დრო — არა. ეს რაოდენობა შეიძლება იყოს დაკვირვებების რაოდენობაზე ნაკლები; მიუწვდომელი ხანგრძლივობის სტატისტიკა რჩება null.

Xcode მოდულების ხანგრძლივობები მოდის ბილდის ლოგებში გაზომილი სამიზნე კომპილაციებიდან. მოდულის ქეშის გადაწყვეტები და სამიზნეები კომპილაციის სამუშაოს გარეშე არ შეიტანენ ხანგრძლივობის ნიმუშებს. კომპილაციის დაკვირვებები მიუთითებენ Xcode ბილდზე; ქეშის მოვლენები მიუთითებენ გენერაციის ან ქეშის ბრძანებაზე.

Bazel მოქმედებები იდენტიფიცირდება სამიზნის ლეიბლით, მნემონიკით და კონფიგურირებული ძირითადი გამოტანით, რაც ინარჩუნებს ცალკეულ მოქმედებებსა და კონფიგურაციებს განცალკევებულად შეყვანაზე დამოკიდებული ქეშის დაიჯესტების გარეშე. ისტორია აღრიცხავს BEP-ით მოხსენებულ გაშვებებს, არა ქეშის ძიებებს ან ტრეის-პროფილის ფაზებს. სრული გაშვების დაფარვა მოითხოვს `--build_event_publish_all_actions`-ს; არტიფაქტების მიწოდება ხდება მაქსიმალური ძალისხმევით, ამიტომ გამოტოვებული დაკვირვებები არ არის იმის მტკიცებულება, რომ სამუშაო არ შესრულებულა. ძველი Kura პეილოადები სტაბილური იდენტობის ან გაშვების დასაწყისის გარეშე რჩება მიღებული, მაგრამ არაინდექსირებული. დასრულების დროის გაზომვების არარსებობა რჩება მიუწვდომელი და რეალური ნულოვანი ხანგრძლივობები ითვლება.

Mix მოდულების ხანგრძლივობები ზომავს შემცველი ფაილის კომპილაციას, არა დამოუკიდებლად გაზომილ მოდულის სამუშაოს. Once მოქმედებები იყენებენ გამოცხადებულ სამიზნე/შესაძლებლობა/ინდექს სლოტებს, როცა კლიენტმა მოახსენა სამიზნეების ასოციაციები; მხოლოდ დიაგნოსტიკის ლეიბლები არ არის სტაბილური იდენტობები. არსებული კლიენტები და გაშვების დონის ინსტრუმენტები რჩება უცვლელად მხარდაჭერილი.

Cargo ყუთები (crates) დაჯგუფებულია ზუსტად ჩაწერილი ყუთის ფესვის, სახელისა და ტიპის მიხედვით. Checkout-ის გზის ცვლილებებმა შეიძლება გაყოს ისტორიები, ხოლო ბილდის პროფილები, შესაძლებლობები და სამიზნე ტრიპლეტები არ განირჩევა. ისტორია ზომავს rustc გამოძახებებს, არა ფაილის დონის სამუშაოს ან ქეშის მოხვედრებს; არარსებული სამუშაოები არ ამყარებენ წაშლებს ან სამუშაო სივრცის სრულ ინვენტარს.

ანალიტიკის წაკითხვებს აქვს შეზღუდული მეხსიერება და შესრულების დრო. თუ მოთხოვნა აღემატება ამ ლიმიტებს, ინსტრუმენტი აბრუნებს შეცდომას ცარიელი შედეგის გამოგონების ნაცვლად.

### მოვლენები

კლიენტები, რომლებიც იყენებენ უმდგომარეობო `2026-07-28` Model Context Protocol ციკლს, შეუძლიათ გამოიძახონ `events/list` მოვლენებისა და მათი შინაარსის სქემების აღმოსაჩენად:

| მოვლენა | როდის იგზავნება | გამოწერის ფილტრი |
|-------|-----------------|---------------------|
| `test_case.marked_flaky` | სატესტო შემთხვევა იცვლება არაარასტაბილურიდან არასტაბილურზე. | `account_handle`, `project_handle` |
| `build.failed` | ლოკალური ან უწყვეტი ინტეგრაციის Xcode, Gradle ან Bazel ბილდი სრულდება შეცდომით. | `account_handle`, `project_handle` |
| `test_run.failed` | ლოკალური ან უწყვეტი ინტეგრაციის ტესტების გაშვება სრულდება შეცდომით, შერწყმული შარდირებული გაშვების ან მიტოვებული გაშვების ჩათვლით. | `account_handle`, `project_handle` |
| `ci_job.failed` | Tuist რანერის სამუშაო სრულდება შეცდომით. | `account_handle` |

გამოსაწერად, კლიენტი იძახებს `events/subscribe` მოვლენის სახელით, ზემოთ ჩამოთვლილი `arguments`-ით და `webhook` მიწოდებით, რომელიც შეიცავს `https://` callback URL-ს და `whsec_` ხელმოწერის საიდუმლოს. პროექტის მოვლენები მოითხოვს ანგარიშის წევრობას და შესაბამის ტესტ ან ბილდ მონაცემებზე წვდომას; რანერის სამუშაოს მოვლენები მოითხოვს ანგარიშის წევრობას და რანერზე წვდომას. დადასტურებულმა [`auth.md`](https://workos.com/auth-md) წვდომის ტოკენებმა, დადასტურებულმა ანგარიშის ტოკენებმა და ბრაუზერის ავტორიზაციის გრანტებმა შეუძლიათ შექმნან გამოწერები; მიწოდება ჩერდება, როდესაც შესაბამისი კრედენციალი აღარ არის აქტიური. თითოეულ მომხმარებელს შეუძლია ჰქონდეს მაქსიმუმ 25 აქტიური გამოწერა. Tuist აგზავნის ვერიფიკაციის გამოწვევას callback-ზე გამოწერის შენახვამდე. callback-მა უნდა დააბრუნოს ობიექტი, რომელიც შეიცავს იგივე `challenge` მნიშვნელობას. გამოწერა ნაგულისხმევად ძლებს შვიდ დღეს, შეიძლება განახლდეს ხელახლა გამოწერით და ჩერდება, როდესაც მომხმარებლის წვდომა ან კრედენციალი იხსნება. არასავალდებულო `ttlMs` შეზღუდულია ერთ საათსა და 30 დღეს შორის. Tuist ხელახლა ცდილობს დროში ამოწურულ callback-ს და აუქმებს მას მინიმუმ სამი თანმიმდევრული დროის ამოწურვის შემდეგ, რომლებიც ხუთ წუთს მოიცავს; გამოიწერეთ ხელახლა callback-ის აღდგენის შემდეგ.

როდესაც მოვლენა ხდება, Tuist აგზავნის მის რესურსის იდენტიფიკატორსა და დაშბორდის URL-ს callback-ზე. ბილდისა და ტესტების გაშვების შეცდომები ასევე შეიცავს `is_ci`-ს და `git_branch`-ს, რათა კლიენტებმა შეძლონ ლოკალური შეცდომების იგნორირება ან ბრენჩით ფილტრაცია. ბილდის მოვლენები შეიცავს `build_system`-ს; რანერის სამუშაოს მოვლენები შეიცავს როგორც `workflow_job_id`-ს, ასევე `workflow_run_id`-ს. მოთხოვნა შეიცავს გამოწერის იდენტიფიკატორს და [Standard Webhooks](https://www.standardwebhooks.com/) ხელმოწერის ჰედერებს, რათა კლიენტმა შეძლოს მისი წარმოშობის ვერიფიკაცია. Tuist ხელახლა ცდილობს შეცდომით დასრულებულ მიწოდებებს, ამიტომ კლიენტებმა უნდა გამოიყენონ სტაბილური `eventId` დუბლიკატების გამოსარიცხად. შინაარსი არ შეიცავს ტესტების სახელებს, ლოგებსა და შეცდომის შეტყობინებებს; კლიენტმა შეუძლია მიიღოს ეს დეტალები ზემოთ ჩამოთვლილი ინსტრუმენტების მეშვეობით და გადაწყვიტოს, შეატყობინოს თუ არა გუნდს ან დაიწყოს დებაგინგი. კლიენტებმა შეუძლიათ შეაჩერონ მიწოდება `events/unsubscribe`-ით.

| `remote_cache` | ააქტიურებს Gradle-ის ბილდ ქეშს, აკონფიგურირებს Tuist-ის დისტანციური ქეშის ატვირთვის პოლიტიკას და ურჩევს ატვირთვას მხოლოდ უწყვეტი ინტეგრაციის გამშვებიდან (runner) ლოკალური მხოლოდ-წასაკითხი გამოყენებით. |
| `build_insights` | აყენებს Tuist Gradle პლაგინს და საჭიროების შემთხვევაში აკონფიგურირებს ბილდის ანალიტიკის ატვირთვის ქცევას. |
| `test_insights` | აყენებს Tuist Gradle პლაგინს, რათა Gradle `Test` ამოცანის შედეგები ავტომატურად აიტვირთოს. |
| `flaky_tests` | მიმართავს არამდგრადი ტესტების აღმოჩენის მოწყობას, Gradle Test Retry პლაგინის არასავალდებულო გამოყენებას და ტესტის კარანტინის კონფიგურაციას. |
| `test_sharding` | ამატებს უწყვეტი ინტეგრაციის სამუშაო ნაკადს `tuistPrepareTestShards`-სთვის, შარდების მატრიცის გენერირებას და `TUIST_SHARD_INDEX`-ზე დაფუძნებულ ტესტის შესრულებას. |

როდესაც `features` გამოტოვებულია, მითითება სთხოვს აგენტს განმარტოს, თუ რომელი ინტეგრაციები სურს მომხმარებელს, ან გამოიტანოს მოთხოვნის საფუძველზე ყველაზე მცირე სასარგებლო ნაკრამი Gradle პროექტის რედაქტირებამდე.

#### Xcode ინტეგრაციის მითითების ფუნქციები

`integrate_xcode_project` მითითება აღწერს Xcode-ის ყველა ინტეგრაციას, რომელსაც Tuist მხარდაჭერს:

| ფუნქცია | რას აკონფიგურირებს აგენტი |
|---------|---------------------------|
| `xcode_cache` | აკონფიგურირებს `tuist setup cache`-ს, გენერირებული პროექტის ქეშის პარამეტრებს, Xcode ქეშის ბილდის ხელით მითითებულ პარამეტრებს და ატვირთვის პოლიტიკას, რომელიც შეზღუდულია უწყვეტი ინტეგრაციის გამშვებებით. |
| `build_insights` | აკონფიგურირებს `tuist inspect build`-ს, `tuist xcodebuild`-ს, `-resultBundlePath`-ს და არასავალდებულო მანქანურ მეტრიკებს `tuist setup insights`-ის საშუალებით. |
| `test_insights` | აკონფიგურირებს `tuist inspect test`-ს, სქემის ტესტის post-actions-ებს და შედეგების ბანდლის გენერირებას უწყვეტი ინტეგრაციის ტესტების გაშვებისთვის. |
| `test_sharding` | ამატებს Xcode-ის ან გენერირებული პროექტის შარდების დაგეგმვისა და შარდების შესრულების სამუშაო ნაკადს `TUIST_SHARD_INDEX`-ით. |

როდესაც `features` გამოტოვებულია, მითითება სთხოვს აგენტს განმარტოს, თუ რომელი ინტეგრაციები სურს მომხმარებელს, ან გამოიტანოს მოთხოვნის საფუძველზე ყველაზე მცირე სასარგებლო ნაკრამი Xcode პროექტის რედაქტირებამდე.
