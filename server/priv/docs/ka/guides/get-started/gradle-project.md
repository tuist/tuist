მიჰყევით ამ გზას, რომ არსებული Gradle პროექტი Tuist-ზე მიამართოთ. `dev.tuist` Gradle პლაგინი აკავშირებს Gradle-ის ლოკალურ ბილდის ქეშს Tuist-ის დისტანციურ ქეშთან და ატვირთავს ბილდისა და ტესტების მონაცემებს დაფაზე, ერთი `./gradlew` ბრძანების შეცვლის გარეშე.

ქვემოთ მოცემული თითოეული განყოფილება იწყება იმით, რაც დღეს აკლია, შემდეგ კი გაჩვენებთ ფუნქციას, რომელიც ამ ნაკლოვანებას აღმოფხვრის.

## წინაპირობები

- Gradle პროექტი `settings.gradle.kts`-ით (ან `settings.gradle`-ით).
- <.localized_link href="/guides/install-tuist">Tuist-ის ბრძანების ხაზის ინტერფეისი</.localized_link>.

## პროექტის დაკავშირება

Gradle პროექტის ფესვიდან გაუშვით `tuist init`. აირჩიეთ **Gradle პროექტის ინტეგრაცია**, შემდეგ გაიარეთ ავტორიზაცია ბრაუზერში და აირჩიეთ ანგარიში, რომელსაც უნდა ეკუთვნოდეს პროექტი.

```bash
tuist init
```

თუ ამას კოდირების აგენტით ან სკრიპტით აკეთებთ, ჯერ გაუშვით `tuist auth login` (ბრაუზერის ნაკადი ელოდება Enter-ის დაჭერას), შემდეგ გამოიყენეთ არაინტერაქტიული ფორმა:

```bash
tuist init --build-system gradle --name <project-handle> --account <account>
```

Tuist წერს `tuist.toml`-ს რეპოზიტორიის ფესვში პროექტის სახელით და ბეჭდავს `plugins { ... }` ბლოკს. ჩასვით ის `settings.gradle.kts`-ის თავში:

<!-- @snippet: ../_gradle-plugin-block -->

შეამოწმეთ `./gradlew help`-ით. Gradle უნდა ჩაიტვირთოს შეცდომების გარეშე. თუ პლაგინს ვერ პოულობს, დარწმუნდით, რომ ბლოკი `settings.gradle.kts`-შია, არა `build.gradle.kts`-ში.

ქვემოთ მოცემული ყველაფერი არის სურვილისამებრ და დამოუკიდებელი.

## დისტანციური ბილდის ქეში

Gradle-ის ლოკალური ბილდის ქეში ინახავს ამოცანების შედეგებს იმ მანქანაზე, რომელმაც ისინი წარმოქმნა. ერთსა და იმავე ბრენჩზე მყოფი ორი დეველოპერი ეცემა ქეშს საკუთარ `~/.gradle`-ში და არა ერთმანეთისაში, ხოლო CI ყოველ ჯობზე ეცემა ახალ, ცარიელ ქეშს.

Tuist-ის დისტანციური ქეში აფართოებს იმავე key/value პროტოკოლს, რომელსაც Gradle უკვე იყენებს მანქანებს შორის. ამოცანის შედეგები აიტვირთება იმ მანქანაზე, რომელმაც პირველად შეასრულა ის, და ჩამოიტვირთება ნებისმიერი სხვის მიერ, ვინც იმავე შეყვანებს გადააწყდება. ჩართეთ ის `gradle.properties`-ში:

```properties
org.gradle.caching=true
```

შემდეგ ააწყვეთ ორ გარემოში:

```bash
./gradlew clean build --build-cache --info
```

ქეშირებადი ამოცანები მეორე გაშვებაზე ანგარიშგებენ `FROM-CACHE`-ს. გახსენით **Cache** დაფაზე, რათა ნახოთ მოხვედრის მაჩვენებლები დროთა განმავლობაში.

## ბილდის ანალიტიკა

Gradle ასხივებს ამოცანების დროებს ბილდის ბოლოს და `--profile`-ით წერს ბილდზე HTML ანგარიშს. არცერთი არ აჯამებს გაშვებებს შორის. ამოცანა, რომელიც კომიტების სერიის განმავლობაში შენელდა, ნებისმიერი ცალკეული ბილდის ანგარიშზე ისევე გამოიყურება, როგორც ყოველთვის.

`dev.tuist` პლაგინი ატვირთავს ამოცანების დროებს ყოველი ბილდისთვის დაფაზე ავტომატურად, როგორც კი პლაგინი გამოიყენება. არაფერი დამატებითი არ არის საჭირო კონფიგურაციისთვის. გახსენით **Builds** დაფაზე თქვენი შემდეგი `./gradlew build`-ის შემდეგ, რათა ნახოთ ტენდენცია.

## ტესტების ანალიტიკა

Gradle-ის ტესტების ანგარიშები ცხოვრობენ ბილდზე `build/reports/tests/`-ის ქვეშ. ტესტი, რომელიც პერიოდულად მარცხდება ათი CI გაშვების განმავლობაში, ნებისმიერ კონკრეტულ ანგარიშში გამოიყურება, როგორც სტაბილური ტესტი, რომელიც ერთხელ შემთხვევით ჩავარდა.

ტესტების ანალიტიკა იწერს ყოველი ამოცანის შედეგსა და ხანგრძლივობას ყოველი `./gradlew test` გაშვებისთვის და აკორელირებს შედეგებს გაშვებებს შორის. არასტაბილური ტესტები, ნელი ტესტები და ჩავარდნები ჩნდებიან დაფის **Tests** ჩანართზე. როდესაც არასტაბილურობა გროვდება, მოათავსეთ ისინი კარანტინში დაფიდან, რათა შეწყვიტონ მერჯების ბლოკირება.

პლაგინი ასევე მხარს უჭერს **სტრეს-ტესტირების რეჟიმს**, რომელიც ხელახლა უშვებს ბილდის მიერ შემოტანილ ტესტების საქმეებს და მონიშნავს ნებისმიერს, რომელიც არასტაბილურად აღმოჩნდება, სანამ ისინი მიწვდებიან. დაამატეთ ის `tuist` გაფართოებაში `settings.gradle.kts`-ში:

```kotlin
tuist {
    stressNewTests {
        mode = "report" // or "enforce"
    }
}
```

## ბანდლის ანალიტიკა

Android Gradle Plugin ანგარიშგებს წარმოქმნილი `.aab`-ის ზომას ბილდის გამონატანში. ეს რიცხვი ქრება ბრენჩთან ერთად და ზომების შედარება რელიზებს შორის ხელით შესრულებული აღრიცხვის სამუშაოა. Play Console ანგარიშგებს იმავე რიცხვებს, მაგრამ მხოლოდ არტიფაქტის ატვირთვის შემდეგ.

ბანდლის ანალიტიკა იწერს ინსტალაციისა და ჩამოტვირთვის ზომებს ყოველი `.aab`-ისთვის (რეკომენდებული) ან `.apk`-ისთვის და შეუძლია ჩააგდოს PR შემოწმება, როდესაც ბრენჩზე ზღვარი ირღვევა. დაამატეთ ეს თქვენს CI-ში პირდაპირ ბილდის ნაბიჯის შემდეგ:

```bash
tuist inspect bundle App.aab
```

გახსენით **Bundle insights → Android** დაფაზე, რათა ნახოთ ტენდენცია და კონფიგურირება ზღვრები.

## პრევიუები

Play Console-ის შიდა ტესტების ტრეკი ყოველ გაზიარებაზე ამატებს მიმოხილვისა და გავრცელების დაყოვნებას. raw `.apk`-ის Slack-ით ან ელფოსტით გაგზავნა უფრო სწრაფია, მაგრამ კარგავს თვალყურს, თუ რომელ ბილდს ეხება კონკრეტული შეტყობინება.

პლაგინს შეუძლია ააწყოს და გამოაქვეყნოს აპლიკაციის ვარიანტი პირდაპირ, ცალკე CLI ატვირთვის გარეშე:

```bash
./gradlew :app:tuistShareDebug --track nightly
```

`tuistShare<Variant>` ამოცანის მოთხოვნა ანიჭებს იმ გამოძახებას გამოქვეყნებას; ჩვეულებრივი ბილდები არასდროს ატვირთავენ პრევიუებს. ნახეთ <.localized_link href="/guides/features/previews/gradle">Gradle previews</.localized_link> მხარდაჭერილი APK-ების, ხელმოწერისა და ინსტალაციისთვის.

## გუნდის ჩართვა

ქეშის მოხვედრები, ანალიტიკა და სტრეს-ტესტირება ყველა მრავლდება პროექტთან დაკავშირებული ადამიანების რაოდენობით. მიიწვიეთ თქვენი გუნდის წევრები ორგანიზაციაში ანგარიშის პარამეტრებიდან დაფაზე და დააყენეთ <.localized_link href="/guides/integrations/authentication/sso">Single Sign-On</.localized_link> (Google, Okta, Microsoft), რათა დარეგისტრირება იყოს ერთი დაწკაპუნება და არა თითოეული ადამიანისთვის `tuist auth login`.

CI-ისთვის არ გამოიყენოთ პირადი შესვლა. გაიარეთ ავტორიზაცია თქვენი CI პროვაიდერის OIDC იდენტობით, ან შექმენით ანგარიშის ტოკენი **CI** პრესეტით დაფაზე და დააყენეთ ის, როგორც `TUIST_TOKEN`. ნახეთ <.localized_link href="/guides/server/authentication#gradle-plugin-authentication">Gradle plugin authentication</.localized_link>.

## პლაგინის სრული ცნობარი

აქ მოცემული ყველაფერი არის მინიმუმი, რათა მიიღოთ სარგებელი Tuist-ისგან Gradle პროექტზე. კონფიგურაციის პარამეტრები `tuist` გაფართოების ბლოკისთვის, `stressNewTests` რეჟიმისთვის და CI ავტორიზაციისთვის მოცემულია [Install the Gradle plugin](https://tuist.dev/en/docs/guides/install-gradle-plugin) ცნობარში.
