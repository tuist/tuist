მიჰყევით ამ გზას, რათა არსებული Gradle-ის პროექტი Tuist-ზე მიამართოთ. `dev.tuist` Gradle-ის პლაგინი აკავშირებს Gradle-ის ლოკალურ ბილდის ქეშს Tuist-ის დისტანციურ ქეშთან და ტვირთავს ბილდისა და ტესტების მონაცემებს დაშბორდზე, ერთი `./gradlew` ბრძანების შეცვლის გარეშე.

ქვემოთ მოცემული თითოეული განყოფილება იწყება იმის აღწერით, თუ რა აკლია დღეს, და შემდეგ გაგიძღვებათ ფუნქციისკენ, რომელიც ამ ნაკლოვანებას აღმოფხვრის.

## წინაპირობები

- Gradle-ის პროექტი `settings.gradle.kts`-ით (ან `settings.gradle`-ით).
- <.localized_link href="/guides/install-tuist">Tuist-ის კომანდური ხაზის ინტერფეისი</.localized_link>.

## პროექტის დაკავშირება

Gradle-ის პროექტის ძირიდან გაუშვით `tuist init`. აირჩიეთ **Gradle-ის პროექტის ინტეგრაცია**, შემდეგ გაიარეთ ავთენტიკაცია ბრაუზერში და აირჩიეთ ის ანგარიში, რომელსაც უნდა ეკუთვნოდეს პროექტი.

```bash
tuist init
```

თუ ამას კოდირების აგენტით ან სკრიპტით აკეთებთ, ჯერ გაუშვით `tuist auth login` (ბრაუზერის ნაკადი ელოდება Enter-ის დაჭერას), შემდეგ გამოიყენეთ არაინტერაქტიული ფორმა:

```bash
tuist init --build-system gradle --name <project-handle> --account <account>
```

Tuist წერს `tuist.toml`-ს რეპოზიტორიის ძირში პროექტის სახელით და ბეჭდავს `plugins { ... }` ბლოკს. ჩასვით ის `settings.gradle.kts`-ის თავში:

```kotlin
plugins {
    id("dev.tuist") version "0.10.0"
}
```

შეამოწმეთ `./gradlew help`-ით. Gradle უნდა ჩაიტვირთოს შეცდომების გარეშე. თუ პლაგინს ვერ პოულობს, დარწმუნდით, რომ ბლოკი `settings.gradle.kts`-შია, არა `build.gradle.kts`-ში.

ქვემოთ მოცემული ყველაფერი არის სავალდებულო და დამოუკიდებელი.

## დისტანციური ბილდის ქეში

Gradle-ის ლოკალური ბილდის ქეში ინახავს ამოცანების გამომავალ მონაცემებს იმ მანქანაზე, რომელმაც ისინი წარმოქმნა. ერთსა და იმავე ბრენჩზე მყოფი ორი დეველოპერი ეხება ქეშს საკუთარ `~/.gradle`-ში და არა ერთმანეთისაში, ხოლო CI ყოველ ჯობზე ხვდება ახალ, ცარიელ ქეშს.

Tuist-ის დისტანციური ქეში აფართოებს იმავე გასაღები/მნიშვნელობის პროტოკოლს, რომელსაც Gradle უკვე იყენებს მანქანებს შორის. ამოცანის გამომავალი მონაცემები იტვირთება იმ მანქანაზე, რომელმაც პირველად შეასრულა ის, და იწერება ნებისმიერი სხვის მიერ, ვინც იმავე შესავალ მონაცემებს გადააწყდება. ჩართეთ ის `gradle.properties`-ში:

```properties
org.gradle.caching=true
```

შემდეგ ააწყვეთ ორ გარემოში:

```bash
./gradlew clean build --build-cache --info
```

ქეშირებადი ამოცანები მეორე გაშვებაზე ანგარიშგებენ `FROM-CACHE`-ს. გახსენით **Cache** დაშბორდზე, რათა ნახოთ მოხმარების მაჩვენებლები დროთა განმავლობაში.

## ბილდის ანალიტიკა

Gradle ასხივებს ამოცანების დროებით მონაცემებს ბილდის დასასრულს და `--profile`-ით წერს თითოეული ბილდის HTML ანგარიშს. არცერთი არ აჯამებს მონაცემებს გაშვებებს შორის. ამოცანა, რომელიც კომიტების სერიის განმავლობაში გახდა უფრო ნელი, ნებისმიერი ცალკეული ბილდის ანგარიშში ისევე გამოიყურება, როგორც ყოველთვის.

`dev.tuist` პლაგინი ავტომატურად ტვირთავს ამოცანების დროებით მონაცემებს ყოველი ბილდისთვის დაშბორდზე, როგორც კი პლაგინი გამოიყენება. დამატებითი კონფიგურაცია არ არის საჭირო. გახსენით **Builds** დაშბორდზე თქვენი შემდეგი `./gradlew build`-ის შემდეგ, რათა ნახოთ ტენდენცია.

## ტესტების ანალიტიკა

Gradle-ის ტესტების ანგარიშები ინახება თითოეული ბილდისთვის `build/reports/tests/`-ქვეშ. ტესტი, რომელიც პერიოდულად მარცხდება ათი CI გაშვების განმავლობაში, ნებისმიერ კონკრეტულ ანგარიშში გამოიყურება როგორც სტაბილური ტესტი, რომელიც ერთხელ ჩავარდა.

ტესტების ანალიტიკა იწერს ყოველი ამოცანის შედეგსა და ხანგრძლივობას ყოველი `./gradlew test` გაშვებისთვის და აკორელირებს შედეგებს გაშვებებს შორის. არასტაბილური ტესტები, ნელი ტესტები და შეცდომები ჩნდება დაშბორდის **Tests** ჩანართზე. როდესაც არასტაბილურობა გროვდება, იზოლირეთ ისინი დაშბორდიდან, რათა შეწყვიტონ შერწყმების ბლოკირება.

პლაგინი ასევე მხარს უჭერს **სტრეს-ტესტირების რეჟიმს**, რომელიც ხელახლა ატარებს ბილდის მიერ შემოტანილ ტესტების შემთხვევებს და აღნიშნავს ნებისმიერს, რომელიც არასტაბილურად აღმოჩნდება, სანამ ისინი ჩაერთვებიან. დაამატეთ ის `tuist` გაფართოებაში `settings.gradle.kts`-ში:

```kotlin
tuist {
    stressNewTests {
        mode = "report" // or "enforce"
    }
}
```

## ბანდლის ანალიტიკა

Android Gradle Plugin ანგარიშგებს წარმოქმნილი `.aab`-ის ზომას ბილდის გამომავალში. ეს რიცხვი ქრება ბრენჩთან ერთად, და ზომების შედარება რელიზებს შორის ხელით შესრულებული აღრიცხვის სამუშაოა. Play Console ანგარიშგებს იმავე რიცხვებს, მაგრამ მხოლოდ არტიფაქტის ატვირთვის შემდეგ.

ბანდლის ანალიტიკა იწერს ინსტალაციისა და ჩამოტვირთვის ზომებს ყოველი `.aab`-ისთვის (რეკომენდებული) ან `.apk`-ისთვის და შეუძლია ჩააგდოს PR-ის შემოწმება, როდესაც ბრენჩის ზღვარი გადაილახება. დაამატეთ ეს თქვენს CI-ში ბილდის ნაბიჯის შემდეგ:

```bash
tuist inspect bundle App.aab
```

გახსენით **Bundle insights → Android** დაშბორდზე, რათა ნახოთ ტენდენცია და დააყენოთ ზღვრები.

## პრევიუები

Play Console-ის შიდა ტესტის ტრეკი ყოველ გაზიარებაზე ამატებს მიმოხილვისა და გავრცელების დაყოვნებას. raw `.apk`-ის Slack-ით ან ელფოსტით გაგზავნა უფრო სწრაფია, მაგრამ კარგავს იმას, თუ რომელ ბილდს ეხება კონკრეტული შეტყობინება.

პრევიუები ბილდს აქცევს გაზიარებად ბმულად, რომლის ინსტალაციასაც მიმღებები ერთი ბრძანებით ახდენენ:

```bash
tuist share App.apk
```

## გუნდის ჩართვა

ქეშის გამოყენება, ინსაიტები და სტრეს-ტესტირება პროექტთან დაკავშირებული ადამიანების რაოდენობის ზრდასთან ერთად მატულობს. მიიწვიეთ თქვენი გუნდის წევრები ორგანიზაციაში დაფარდიდან ანგარიშის პარამეტრებში და დააყენეთ <.localized_link href="/guides/integrations/authentication/sso">ერთჯერადი შესვლა</.localized_link> (Google, Okta, Microsoft), რომ დარეგისტრება იყოს ერთი დაწკაპუნებით და არა თითოეული პირისთვის ცალ-ცალკე `tuist auth login`.

CI-სთვის არ გამოიყენოთ პირადი შესვლა. დააყენეთ `TUIST_TOKEN` თქვენს პროექტზე შეზღუდული (შექმენით ის პროექტის პარამეტრებიდან დაშბორდზე).

## პლაგინის სრული ცნობარი

აქ მოცემული ყველაფერი არის მინიმუმი, რათა მიიღოთ სარგებელი Tuist-დან Gradle-ის პროექტზე. კონფიგურაციის პარამეტრები `tuist` გაფართოების ბლოკისთვის, `stressNewTests` რეჟიმისთვის და CI ავთენტიკაციისთვის მოცემულია [Gradle-ის პლაგინის ინსტალაცია](https://tuist.dev/en/docs/guides/install-gradle-plugin) ცნობარში.
