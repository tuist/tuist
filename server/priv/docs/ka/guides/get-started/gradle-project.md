მიჰყევით ამ გზას, რათა არსებული Gradle პროექტი Tuist-ზე მიამართოთ. `dev.tuist` Gradle პლაგინი აკავშირებს Gradle-ის ლოკალურ ბილდის ქეშს Tuist-ის დისტანციურ ქეშთან და ტვირთავს ბილდისა და ტესტების მონაცემებს დაშბორდზე, ერთი `./gradlew` ბრძანების შეცვლის გარეშე.

ქვემოთ მოცემული თითოეული განყოფილება იწყება იმის აღწერით, რაც დღეს აკლია, შემდეგ კი გაგივლით ფუნქციას, რომელიც ამ ნაკლოვანებას აღმოფხვრის.

## წინაპირობები

- Gradle პროექტი `settings.gradle.kts`-ით (ან `settings.gradle`-ით).
- <.localized_link href="/guides/install-tuist">Tuist-ის ბრძანების სტრიქონის ინტერფეისი</.localized_link>.

## პროექტის დაკავშირება

Gradle პროექტის ძირიდან გაუშვით `tuist init`. აირჩიეთ **Gradle პროექტის ინტეგრაცია**, შემდეგ გაიარეთ ავთენტიკაცია ბრაუზერში და აირჩიეთ ის ანგარიში, რომელსაც უნდა ეკუთვნოდეს პროექტი.

```bash
tuist init
```

თუ ამას კოდირების აგენტით ან სკრიპტით აკეთებთ, ჯერ გაუშვით `tuist auth login` (ბრაუზერის ნაკადი ელოდება Enter-ის დაჭერას), შემდეგ გამოიყენეთ არაინტერაქტიული ფორმა:

```bash
tuist init --build-system gradle --name <project-handle> --account <account>
```

Tuist წერს `tuist.toml`-ს რეპოზიტორიის ძირში პროექტის სახელით და ბეჭდავს `plugins { ... }` ბლოკს. ჩასვით ის `settings.gradle.kts`-ის თავში:

<!-- @snippet: ../_gradle-plugin-block -->

შეამოწმეთ `./gradlew help`-ით. Gradle უნდა ჩაიტვირთოს შეცდომების გარეშე. თუ პლაგინს ვერ პოულობს, დარწმუნდით, რომ ბლოკი `settings.gradle.kts`-შია და არა `build.gradle.kts`-ში.

ქვემოთ მოცემული ყველაფერი არის არასავალდებულო და დამოუკიდებელი.

## დისტანციური ბილდის ქეში

Gradle-ის ლოკალური ბილდის ქეში ინახავს ამოცანების გამომავალ მონაცემებს იმ მანქანაზე, რომელმაც ისინი წარმოქმნა. ერთი და იმავე ბრენჩზე მყოფი ორი დეველოპერი ეხება ქეშს საკუთარ `~/.gradle`-ში და არა ერთმანეთისაში, ხოლო CI ყოველ ჯობზე ხვდება ახალ, ცარიელ ქეშს.

Tuist-ის დისტანციური ქეში აფართოებს იმავე გასაღები/მნიშვნელობის პროტოკოლს, რომელსაც Gradle უკვე იყენებს მანქანებს შორის. ამოცანის გამომავალი მონაცემები იტვირთება იმ მანქანაზე, რომელმაც პირველად შეასრულა ის და იწერება ნებისმიერი სხვის მიერ, ვინც იმავე შესავალ მონაცემებს შეხვდება. ჩართეთ ის `gradle.properties`-ში:

```properties
org.gradle.caching=true
```

შემდეგ ააწყვეთ ორ გარემოში:

```bash
./gradlew clean build --build-cache --info
```

ქეშირებადი ამოცანები მეორე გაშვებაზე ანგარიშგებენ `FROM-CACHE`-ს. გახსენით **Cache** დაშბორდზე, რათა ნახოთ მოხმარების მაჩვენებლები დროთა განმავლობაში.

## ბილდის ინსაითები

Gradle ასხივებს ამოცანების დროებით მონაცემებს ბილდის ბოლოს და `--profile`-ით წერს თითოეული ბილდის HTML ანგარიშს. არცერთი არ აჯამებს მონაცემებს გაშვებებს შორის. ამოცანა, რომელიც კომიტების სერიის განმავლობაში შენელდა, ნებისმიერი ცალკეული ბილდის ანგარიშში ისევე გამოიყურება, როგორც ყოველთვის.

`dev.tuist` პლაგინი ავტომატურად ტვირთავს ამოცანების დროებით მონაცემებს ყოველი ბილდისთვის დაშბორდზე, როგორც კი პლაგინი გამოიყენება. არაფერია დამატებითი კონფიგურაციისთვის. გახსენით **Builds** დაშბორდზე თქვენი შემდეგი `./gradlew build`-ის შემდეგ, რათა ნახოთ ტენდენცია.

## ტესტების ინსაითები

Gradle-ის ტესტების ანგარიშები ინახება თითოეული ბილდისთვის `build/reports/tests/`-ში. ტესტი, რომელიც პერიოდულად მარცხდება ათი CI გაშვების განმავლობაში, ნებისმიერ კონკრეტულ ანგარიშში გამოიყურება როგორც სტაბილური ტესტი, რომელიც ერთხელ ჩავარდა.

ტესტების ინსაითები იწერს თითოეული ამოცანის შედეგს და ხანგრძლივობას ყოველი `./gradlew test` გაშვებისთვის და აკორელირებს შედეგებს გაშვებებს შორის. არასტაბილური ტესტები, ნელი ტესტები და ჩავარდნები ჩნდება დაშბორდის **Tests** ჩანართზე. როდესაც არასტაბილურობა გროვდება, იზოლირეთ ისინი დაშბორდიდან, რათა შეწყვიტონ მერჯების ბლოკირება.

პლაგინი ასევე მხარდაჭერს **სტრეს-ტესტირების რეჟიმს**, რომელიც ხელახლა უშვებს ბილდის მიერ შემოტანილ ტესტის საქმეებს და მონიშნავს ნებისმიერს, რომელიც არასტაბილურად აღმოჩნდება, სანამ ისინი მიიღებენ. დაამატეთ ის `tuist` გაფართოებაში `settings.gradle.kts`-ში:

```kotlin
tuist {
    stressNewTests {
        mode = "report" // or "enforce"
    }
}
```

## კოდის დაფარვა

JaCoCo წერს დაფარვის ანგარიშს თითოეული ტესტის ამოცანისთვის და თითოეული მანქანისთვის. არაფერი აერთიანებს კომიტის CI ჯობების ანგარიშებს ან აჩვენებს, გაიზარდა თუ შემცირდა ბრენჩის დაფარვა.

პლაგინს შეუძლია გაზომოს თქვენი JVM და Android ერთეულოვანი ტესტები JaCoCo-ით და ატვირთოს დაფარვა ყოველ ტესტის გაშვებასთან ერთად. Tuist აერთიანებს კომიტის გაშვებებს, შარდების ჩათვლით, ერთ რიცხვად. ჩართეთ ის `tuist` გაფართოებაში `settings.gradle.kts`-ში:

```kotlin
tuist {
    coverage {
        enabled = true
    }
}
```

გახსენით **Code Coverage** დაშბორდზე, რათა ნახოთ ის თითოეული კომიტისა და ფაილის მიხედვით. იხილეთ <.localized_link href="/guides/features/test-code-coverage/gradle">Gradle code coverage</.localized_link> CI-ზე კომიტის დასასრულებლად და Robolectric-ის დაყენებისთვის.

## ბანდლის ინსაითები

Android Gradle Plugin ანგარიშგებს წარმოქმნილი `.aab`-ის ზომას ბილდის გამომავალში. ეს რიცხვი ქრება ბრენჩთან ერთად და ზომების შედარება რელიზებს შორის ხელით შესრულებული აღრიცხვის სამუშაოა. Play Console ანგარიშგებს იმავე რიცხვებს, მაგრამ მხოლოდ არტიფაქტის ატვირთვის შემდეგ.

ბანდლის ინსაითები იწერს ინსტალაციისა და ჩამოტვირთვის ზომებს ყოველი `.aab`-ისთვის (რეკომენდებული) ან `.apk`-ისთვის და შეუძლია ჩააგდოს PR შემოწმება, როდესაც ბრენჩის ზღვარი გადაიჭრება. დაამატეთ ეს თქვენს CI-ში პირდაპირ ბილდის ნაბიჯის შემდეგ:

```bash
tuist inspect bundle App.aab
```

გახსენით **Bundle insights → Android** დაშბორდზე, რათა ნახოთ ტენდენცია და დააკონფიგურიროთ ზღვრები.

## პრევიუები

Play Console-ის შიდა ტესტის ტრეკი ყოველ გაზიარებაზე ამატებს გადახედვისა და გავრცელების დაყოვნებას. ნედლი `.apk`-ის გაგზავნა Slack-ით ან ელფოსტით უფრო სწრაფია, მაგრამ კარგავს თვალყურს, თუ რომელ ბილდს ეხება კონკრეტული შეტყობინება.

პლაგინს შეუძლია ააწყოს და გამოაქვეყნოს აპლიკაციის ვარიანტი პირდაპირ, ცალკე CLI ატვირთვის გარეშე:

```bash
./gradlew :app:tuistShareDebug --track nightly
```

`tuistShare<Variant>` ამოცანის მოთხოვნა აყენებს იმ გამოძახებას გამოქვეყნების რეჟიმში; ჩვეულებრივი ბილდები არასდროს ტვირთავენ პრევიუებს. იხილეთ <.localized_link href="/guides/features/previews/gradle">Gradle previews</.localized_link> მხარდაჭერილი APK-ების, ხელმოწერისა და ინსტალაციისთვის.

## გუნდის ჩართვა

ქეშის მოხმარება, ინსაითები და სტრეს-ტესტირება ყველა იზრდება პროექტთან დაკავშირებული ადამიანების რაოდენობასთან ერთად. მიიწვიეთ თქვენი გუნდის წევრები ორგანიზაციაში დაშბორდის ანგარიშის პარამეტრებიდან და დააყენეთ <.localized_link href="/guides/integrations/authentication/sso">Single Sign-On</.localized_link> (Google, Okta, Microsoft), რათა onboard-ing იყოს ერთი დაწკაპუნება და არა თითოეული პირისთვის `tuist auth login`.

CI-ისთვის არ გამოიყენოთ პირადი შესვლა. გაიარეთ ავთენტიკაცია თქვენი CI პროვაიდერის OIDC იდენტობით, ან შექმენით ანგარიშის ტოკენი დაშბორდზე **CI** პრესეტით და დააყენეთ ის როგორც `TUIST_TOKEN`. იხილეთ <.localized_link href="/guides/server/authentication#gradle-plugin-authentication">Gradle plugin authentication</.localized_link>.

## პლაგინის სრული ცნობარი

აქ მოცემული ყველაფერი არის მინიმუმი, რაც საჭიროა Tuist-ის სარგებლის მიღებისთვის Gradle პროექტზე. `tuist` გაფართოების ბლოკის კონფიგურაციის პარამეტრები, `stressNewTests` რეჟიმი და CI ავთენტიკაცია აღწერილია [Install the Gradle plugin](https://tuist.dev/en/docs/guides/install-gradle-plugin) ცნობარში.
