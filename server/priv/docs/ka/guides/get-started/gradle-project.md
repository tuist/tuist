მიჰყევით ამ გზას, რათა არსებული Gradle-ის პროექტი Tuist-ზე მიამართოთ. `dev.tuist` Gradle-ის პლაგინი აკავშირებს Gradle-ის ლოკალურ ბილდის ქეშს Tuist-ის დისტანციურ ქეშთან და ტვირთავს ბილდისა და ტესტების მონაცემებს დაშბორდზე, ერთი `./gradlew` ბრძანების შეცვლის გარეშე.

ქვემოთ მოცემული ყოველი სექცია იწყება იმის აღწერით, თუ რა აკლია დღეს, და შემდეგ გაგივლით ფუნქციას, რომელიც ამ ნაკლს ავსებს.

## წინაპირობები

- Gradle-ის პროექტი `settings.gradle.kts`-ით (ან `settings.gradle`-ით).
- <.localized_link href="/guides/install-tuist">Tuist-ის კომანდური ხაზის ინტერფეისი</.localized_link>.

## პროექტის დაკავშირება

Gradle-ის პროექტის ფესვიდან გაუშვით `tuist init`. აირჩიეთ **Gradle-ის პროექტის ინტეგრაცია**, შემდეგ გაიარეთ ავთენტიკაცია ბრაუზერში და აირჩიეთ ის ანგარიში, რომელსაც უნდა ეკუთვნოდეს პროექტი.

```bash
tuist init
```

თუ ამას კოდირების აგენტით ან სკრიპტით აკეთებთ, ჯერ გაუშვით `tuist auth login` (ბრაუზერის ნაკადი ელოდება Enter-ის დაჭერას), შემდეგ გამოიყენეთ არაინტერაქტიული ფორმა:

```bash
tuist init --build-system gradle --name <project-handle> --account <account>
```

Tuist წერს `tuist.toml`-ს რეპოზიტორიის ფესვში პროექტის სახელით და ბეჭდავს `plugins { ... }` ბლოკს. ჩასვით ის `settings.gradle.kts`-ის თავში:

```kotlin
plugins {
    id("dev.tuist") version "0.10.0"
}
```

შეამოწმეთ `./gradlew help`-ით. Gradle უნდა ჩაიტვირთოს შეცდომების გარეშე. თუ პლაგინს ვერ პოულობს, დარწმუნდით, რომ ბლოკი `settings.gradle.kts`-შია, არა `build.gradle.kts`-ში.

ქვემოთ მოცემული ყველაფერი არჩევითია და დამოუკიდებელი.

## დისტანციური ბილდის ქეში

Gradle-ის ლოკალური ბილდის ქეში ინახავს ამოცანების გამომავალ მონაცემებს იმ მანქანაზე, რომელმაც ისინი წარმოქმნა. ერთი და იმავე ბრენჩზე მყოფი ორი დეველოპერი ეხება ქეშს საკუთარ `~/.gradle`-ში და არა ერთმანეთისაში, ხოლო CI ყოველ ჯობზე ხვდება ახალ, ცარიელ ქეშს.

Tuist-ის დისტანციური ქეში აფართოებს იმავე key/value პროტოკოლს, რომელსაც Gradle უკვე იყენებს მანქანებს შორის. ამოცანის გამომავალი მონაცემები იტვირთება იმ მანქანაზე, რომელმაც პირველად შეასრულა ის, და იწერება ნებისმიერი სხვის მიერ, ვინც იმავე შეყვანის მონაცემებს შეხვდება. ჩართეთ ის `gradle.properties`-ში:

```properties
org.gradle.caching=true
```

შემდეგ ააწყვეთ ორ გარემოში:

```bash
./gradlew clean build --build-cache --info
```

ქეშირებადი ამოცანები მეორე გაშვებაზე ანგარიშგებენ `FROM-CACHE`-ს. გახსენით **Cache** დაშბორდზე, რათა ნახოთ მოხვედრის მაჩვენებლები დროთა განმავლობაში.

## ბილდის ინსაიტები

Gradle ასხივებს ამოცანების დროებით მონაცემებს ბილდის ბოლოს და `--profile`-ით წერს თითოეული ბილდის HTML ანგარიშს. არცერთი არ აჯამებს მონაცემებს გაშვებებს შორის. ამოცანა, რომელიც კომიტების სერიის განმავლობაში შენელდა, ნებისმიერი ცალკეული ბილდის ანგარიშში ისევე გამოიყურება, როგორც ყოველთვის.

`dev.tuist` პლაგინი ტვირთავს ამოცანების დროებით მონაცემებს ყოველი ბილდისთვის დაშბორდზე ავტომატურად, როგორც კი პლაგინი გამოიყენება. დამატებითი კონფიგურაცია არ არის საჭირო. გახსენით **Builds** დაშბორდზე თქვენი შემდეგი `./gradlew build`-ის შემდეგ, რათა ნახოთ ტენდენცია.

## ტესტების ინსაიტები

Gradle-ის ტესტების ანგარიშები ინახება თითოეული ბილდისთვის `build/reports/tests/`-ში. ტესტი, რომელიც პერიოდულად მარცხდება ათი CI გაშვების განმავლობაში, ნებისმიერ კონკრეტულ ანგარიშში გამოიყურება როგორც სტაბილური ტესტი, რომელიც ერთხელ მარცხდა.

ტესტების ინსაიტები იწერს ყოველი ამოცანის შედეგსა და ხანგრძლივობას ყოველი `./gradlew test` გაშვებისთვის და აკორელირებს შედეგებს გაშვებებს შორის. არასტაბილური ტესტები, ნელი ტესტები და მარცხები ჩნდება დაშბორდის **Tests** ჩანართზე. როდესაც არასტაბილურობა გროვდება, იზოლირეთ ისინი დაშბორდიდან, რათა შეწყვიტონ მერჯების ბლოკირება.

პლაგინი ასევე უჭერს მხარს **სტრეს-ტესტირების რეჟიმს**, რომელიც ხელახლა უშვებს ბილდის მიერ შემოტანილ ტესტის შემთხვევებს და აღნიშნავს ნებისმიერს, რომელიც არასტაბილურად აღმოჩნდება, სანამ ისინი ძირითად ბრენჩში მოხვდებიან. დაამატეთ ის `tuist` გაფართოებაში `settings.gradle.kts`-ში:

```kotlin
tuist {
    stressNewTests {
        mode = "report" // or "enforce"
    }
}
```

## ბანდლის ინსაიტები

Android Gradle Plugin ანგარიშგებს წარმოქმნილი `.aab`-ის ზომას ბილდის გამომავალ მონაცემებში. ეს რიცხვი ქრება ბრენჩთან ერთად და ზომების შედარება რელიზებს შორის ხელით შესრულებული აღრიცხვის სამუშაოა. Play Console ანგარიშგებს იმავე რიცხვებს, მაგრამ მხოლოდ არტიფაქტის ატვირთვის შემდეგ.

ბანდლის ინსაიტები იწერს ინსტალაციისა და ჩამოტვირთვის ზომებს ყოველი `.aab`-ისთვის (რეკომენდებულია) ან `.apk`-ისთვის და შეუძლია PR-ის შემოწმების ჩაშლა, როდესაც ბრენჩის ზღვარი გადაიჭრება. დაამატეთ ეს თქვენს CI-ში ბილდის ნაბიჯის შემდეგ:

```bash
tuist inspect bundle App.aab
```

გახსენით **Bundle insights → Android** დაშბორდზე, რათა ნახოთ ტენდენცია და დააყენოთ ზღვრები.

## პრევიუები

Play Console-ის შიდა ტესტის ტრეკი ყოველ გაზიარებაზე ამატებს მიმოხილვისა და გავრცელების დაყოვნებას. raw `.apk`-ის Slack-ით ან ელფოსტით გაგზავნა უფრო სწრაფია, მაგრამ კარგავს კონტროლს იმაზე, თუ რომელ ბილდს ეხება კონკრეტული შეტყობინება.

პრევიუები ბილდს აქცევს გაზიარებად ბმულად, რომელსაც მიმღებები ერთი ბრძანებით აყენებენ:

```bash
tuist share App.apk
```

## გადაიყვანეთ გუნდი პროექტზე

ქეშის მოხვედრები, ინსაიტები და სტრეს-ტესტირება ყველა იზრდება პროექტთან დაკავშირებული ადამიანების რაოდენობის მიხედვით. მიიწვიეთ თქვენი გუნდის წევრები ორგანიზაციაში დაშბორდის ანგარიშის პარამეტრებიდან და დააყენეთ <.localized_link href="/guides/integrations/authentication/sso">Single Sign-On</.localized_link> (Google, Okta, Microsoft), რათა დარეგისტრირება იყოს ერთი დაწკაპუნება და არა თითოეული ადამიანისთვის `tuist auth login`.

CI-ისთვის არ გამოიყენოთ პირადი შესვლა. დააყენეთ `TUIST_TOKEN` თქვენს პროექტზე მორგებული (შექმენით ის დაშბორდის პროექტის პარამეტრებიდან).

## პლაგინის სრული ცნობარი

აქ მოცემული ყველაფერი არის მინიმუმი, რათა მიიღოთ სარგებელი Tuist-ისგან Gradle-ის პროექტზე. `tuist` გაფართოების ბლოკის, `stressNewTests` რეჟიმისა და CI ავთენტიკაციის კონფიგურაციის პარამეტრები მოცემულია [Gradle-ის პლაგინის ინსტალაცია](https://tuist.dev/en/docs/guides/install-gradle-plugin) ცნობარში.
