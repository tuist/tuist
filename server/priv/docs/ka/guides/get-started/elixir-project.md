# Elixir-ის პროექტი {#elixir-project}

::: code-group

```text [Agent prompt]
Help me get started with Tuist. Follow the setup at:
https://tuist.dev/en/docs/guides/get-started/elixir-project
```

:::

ერთხელ დააყენეთ Tuist, შემდეგ კი განაგრძეთ `mix compile`-ისა და `mix test`-ის გამოყენება. `tuist_ex` Hex პაკეტი აქვეშებს მხარდაჭერილ დამოკიდებულებებს და თქვენს დაფზე აგზავნის ბილდებისა და ტესტების გაშვების შესახებ ინფორმაციას.

## წინაპირობები

- Elixir-ის პროექტი, აგებული Mix-ით, Elixir 1.18 ან უფრო ახალ ვერსიაზე.
- Tuist-ის ანგარიში.

## Tuist-ის დაყენება {#set-up-tuist}

შექმენით პროექტი Tuist-ის დაფზე და აირჩიეთ **Mix (Elixir)** როგორც მისი ბილდის სისტემა. დაამატეთ პაკეტი დამოკიდებულებებში თქვენს `mix.exs`-ში:

<!-- @snippet: ../_tuist-ex-dependency -->

ჩამოტვირთეთ ის, დააკონფიგურირეთ თქვენი პროექტი და შედით სისტემაში:

```bash
mix deps.get
mix tuist.setup --project account/project
mix tuist.login
```

დაყენება აახლებს `mix.exs`-ს თქვენი პროექტის იდენტიფიკატორით, რთავს დამოკიდებულებების ქეშირებას და აყენებს კომპილაციისა და ტესტირების ალიასებს. ის ინარჩუნებს სხვა პარამეტრებს და სტანდარტულ ტესტების მომზადებას, მაგალითად, Phoenix-ის მონაცემთა ბაზის კონფიგურაციას. თუ ის უსაფრთხოდ ვერ აინტეგრირებს მორგებულ ალიასს, ის ჩერდება ფაილის შეცვლის გარეშე.

შეინახეთ განახლებული `mix.exs`, რათა თქვენმა გუნდმა და CI-მ ერთი და იგივე კონფიგურაცია გამოიყენონ. არ არის საჭირო სკრიპტების ან გამოთვლის კოდის კოპირება. შესვლა ხსნის ბრაუზერს; ნახეთ <.localized_link href="/guides/install-hex-package#authenticate">ავტორიზაცია</.localized_link> headless შესვლისა და CI-ის სერთიფიკატებისთვის.

ახლა გაუშვით თქვენი ჩვეული ბრძანებები:

```bash
mix compile
mix test
```

ბილდები ჩანს **Builds**-ში, ტესტების გაშვებები **Tests**-ში, ხოლო დამოკიდებულებების ქეშის აქტივობა **Mix cache**-ში. ეს არის საერთო კონფიგურაცია სამივესთვის. არასტაბილური ტესტების აღმოჩენა იყენებს გაგზავნილ გაშვებებს; ხელახალი ცდები და CI-ის შარდინგი არის არასავალდებულო.

## დამოკიდებულებების ქეშირება

Tuist ავტომატურად ირჩევს მხარდაჭერილ Hex და Git დამოკიდებულებებს, დამოკიდებულებების სიის გარეშე. ქეშში არყოფნის შემთხვევაში კომპილაცია ჩვეულებრივად ხდება და შედეგი ინახება; ქეშში ყოფნის შემთხვევაში ის აღდგება. ნატიური/მორგებული კომპილაცია და ლოკალური დამოკიდებულებები რჩება Mix-თან.

კომპილაცია უნდა იყოს აღწარმოებადი: გამოაცხადეთ დამატებითი კომპილაციის დროის შეყვანები და გამორიცხეთ დამოკიდებულებები, რომლებსაც აქვთ არამოდელირებული შეყვანები ან საჭირო გვერდითი ეფექტები. ნახეთ <.localized_link href="/guides/features/cache/elixir">Elixir cache</.localized_link> მხარდაჭერილი შეყვანების, ქეშის ვერიფიკაციისა და მორგებისთვის.

## ბილდის ანალიტიკა

ბილდის დროები, დამოკიდებულებების გრაფი თქვენს ფაილებს შორის და ორივეს ევოლუცია დროთა განმავლობაში გაძლევთ იმას, რაც გჭირდებათ ბილდის გრაფის ოპტიმიზაციისთვის და კომპილაციის გარემოში ხელმისაწვდომი ყველა ბირთვის მაქსიმალურად გამოყენებისთვის.

`compile` ალიასის არსებობისას, Tuist იტყობინება ყოველ ბილდს: რამდენი დრო დასჭირდა, მისი გაფრთხილებები და შეცდომები, რამდენი დრო დასჭირდა თითოეული ფაილის კომპილაციას და ფაილები, რომლებზეც ის არის დამოკიდებული. გახსენით **Builds** დაფზე თქვენი შემდეგი `mix compile`-ის შემდეგ, რათა ნახოთ ის.

## ტესტების ანალიტიკა

Tuist იწერს ყოველი ტესტის შედეგსა და ხანგრძლივობას ყოველ `mix test` გაშვებაში, რათა შეძლოთ ნახოთ, როგორ ვითარდება თქვენი ტესტების ნაკრები დროთა განმავლობაში, იპოვოთ ნელი ან შენელებული ტესტები და გაიგოთ, რატომ ჩავარდა გაშვება CI-ში. თქვენ იპოვით მათ **Tests**-ში დაფზე, მოდულის, `describe` ბლოკისა და ტესტის დონემდე.

## არასტაბილური ტესტები

არასტაბილური ტესტი გადის და ვარდება ერთი და იგივე კოდით. Tuist მონიშნავს ტესტს როგორც არასტაბილურს, როცა ის ვარდება და გადის ერთსა და იმავე კომიტზე CI-ში. ასევე შეგიძლიათ აიძულოთ პაკეტმა ხელახლა სცადოს ვარდნილი ტესტები, რაც აღმოაჩენს მათ ერთ გაშვებაში:

```elixir
tuist: [project: "account/project", cache: true, test_retries: 2]
```

ტესტი, რომელიც გადის ხელახალი ცდისას, იტყობინება როგორც არასტაბილური და გაშვება წარმატებულია. **Flaky Tests** გვერდი ჩამოთვლის მათ.

## ტესტების შარდინგი

ტესტების შარდინგი ანაწილებს თქვენს ტესტების ნაკრებს CI-ის გამშვებებზე. Tuist აბალანსებს შარდებს იმის მიხედვით, თუ რამდენი დრო დასჭირდა თითოეულ ტესტის ფაილს წინა გაშვებებში, და ის კომპილირებს პროექტს ერთხელ და უზიარებს ამ ბილდს ყოველ გამშვებს. ერთი ბრძანება გეგმავს შარდებს:

```bash
mix tuist.test.build --shard-max 4
```

შემდეგ თითოეული გამშვი უშვებს თავის წილს `TUIST_SHARD_INDEX`-ის მითითებით, და შედეგები დაფზე მოდის როგორც ერთიანი ტესტების გაშვება:

```bash
TUIST_SHARD_INDEX=0 mix test
```

## ჩართეთ გუნდი

ანალიტიკა მრავლდება პროექტთან დაკავშირებული ადამიანების რაოდენობის ზრდასთან. მიიწვიეთ თქვენი გუნდის წევრები ორგანიზაციაში ანგარიშის პარამეტრებიდან დაფზე, და დააყენეთ <.localized_link href="/guides/integrations/authentication/sso">Single Sign-On</.localized_link> (Google, Okta, Microsoft), რათა დარეგისტრირება იყოს ერთი დაწკაპუნება და არა თითოეული ადამიანისთვის `mix tuist.login`.

CI-ისთვის, არ გამოიყენოთ პირადი შესვლა. GitHub Actions, CircleCI და Bitrise-ს შეუძლიათ ავტორიზაცია OpenID Connect-ის მეშვეობით; სხვა პროვაიდერებზე, დააყენეთ შეზღუდული `TUIST_TOKEN`. მიჰყევით <.localized_link href="/guides/install-hex-package#authenticate">CI ავტორიზაციის ნაბიჯებს</.localized_link>.
