# Elixir-პროექტი {#elixir-project}

::: code-group

```text [Agent prompt]
Help me get started with Tuist. Follow the setup at:
```

ერთხელ დააყენეთ Tuist, შემდეგ კი გააგრძელეთ `mix compile`-ის და `mix test`-ის გამოყენება. `tuist_ex` Hex-პაკეტი აკეთებს მხარდაჭერილი დამოკიდებულებების ქეშირებას და აგზავნის ბილდებისა და ტესტების გაშვების შესახებ ინფორმაციას თქვენს დაშბორდზე.

## წინაპირობები

- Elixir-პროექტი, აგებული Mix-ით, Elixir 1.18 ან უფრო ახალ ვერსიაზე.
- Tuist-ის ანგარიში.

## Tuist-ის დაყენება {#set-up-tuist}

შექმენით პროექტი Tuist-ის დაშბორდზე და აირჩიეთ **Mix (Elixir)** როგორც ბილდის სისტემა. დაამატეთ პაკეტი დამოკიდებულებებში თქვენს `mix.exs`-ში:

<!-- @snippet: ../_tuist-ex-dependency -->

ჩამოტვირთეთ ის, დააკონფიგურირეთ თქვენი პროექტი და შედით სისტემაში:

```bash
mix deps.get
mix tuist.setup --project account/project
mix tuist.login
```

დაყენება აახლებს `mix.exs`-ს თქვენი პროექტის იდენტიფიკატორით, რთავს დამოკიდებულებების ქეშირებას და აყენებს კომპილაციისა და ტესტირების ალიასებს. ის ინარჩუნებს სხვა პარამეტრებს და სტანდარტულ სატესტო მომზადებას, როგორიცაა Phoenix-ის მონაცემთა ბაზის დაყენება. თუ უსაფრთხოდ ვერ ახდენს მორგებას მორგებულ ალიასთან, ის ჩერდება ფაილის შეცვლის გარეშე.

დააკომიტეთ განახლებული `mix.exs`, რათა თქვენმა გუნდმა და CI-მ გამოიყენონ ერთი და იგივე კონფიგურაცია. არ არის საჭირო სკრიპტების ან შეფასების კოდის კოპირება. შესვლა ხსნის ბრაუზერს; headless შესვლისა და CI-სთვის საჭირო მონაცემებისთვის იხილეთ <.localized_link href="/guides/install-hex-package#authenticate">ავტორიზაცია</.localized_link>.

ახლა გაუშვით თქვენი ჩვეული ბრძანებები:

```bash
mix compile
mix test
```

ბილდები ჩანს **Builds**-ში, ტესტების გაშვებები — **Tests**-ში, ხოლო დამოკიდებულებების ქეშის აქტივობა — **Mix cache**-ში. ეს არის საერთო კონფიგურაცია სამივესთვის. არასტაბილური ტესტების აღმოჩენა იყენებს გაგზავნილ გაშვებებს; ხელახალი ცდები და CI-ში შარდინგი არის არასავალდებულო.

## დამოკიდებულებების ქეშირება

Tuist ავტომატურად ირჩევს მხარდაჭერილ Hex და Git დამოკიდებულებებს, დამოკიდებულებების სიის გარეშე. ქეშში არყოფნის შემთხვევაში კომპილაცია მიმდინარეობს ჩვეულებრივად და შედეგი ინახება; ქეშში ყოფნის შემთხვევაში ის აღდგება. ნატიური/მორგებული კომპილაცია და ლოკალური დამოკიდებულებები რჩება Mix-თან.

კომპილაცია უნდა იყოს აღწარმოებადი: განაცხადეთ დამატებითი კომპილაციის დროის შეყვანები და გამორიცხეთ დამოკიდებულებები, რომლებსაც აქვთ არამოდელირებული შეყვანები ან საჭირო გვერდითი ეფექტები. მხარდაჭერილი შეყვანების, ქეშის ვერიფიკაციისა და მორგებისთვის იხილეთ <.localized_link href="/guides/features/cache/elixir">Elixir cache</.localized_link>.

## ბილდის ანალიტიკა

ბილდის დრო, თქვენს ფაილებს შორის დამოკიდებულების გრაფი და მათი ცვლილება დროთა განმავლობაში გაძლევთ იმას, რაც საჭიროა ბილდის გრაფის ოპტიმიზაციისთვის და კომპილაციის გარემოში ხელმისაწვდომი ყველა ბირთვის მაქსიმალურად გამოყენებისთვის.

`compile` ალიასის არსებობისას, Tuist აგზავნის ინფორმაციას ყოველი ბილდის შესახებ: რამდენ ხანს გაგრძელდა, რა გაფრთხილებები და შეცდომები იყო, რამდენ ხანს კომპილირდებოდა თითოეული ფაილი და რა ფაილებზეა ის დამოკიდებული. თქვენი შემდეგი `mix compile`-ის შემდეგ გახსენით **Builds** დაშბორდზე, რომ ნახოთ ის.

## ტესტების ანალიტიკა

Tuist იწერს ყოველი ტესტის შედეგს და ხანგრძლივობას ყოველ `mix test` გაშვებაში, რათა დაინახოთ, როგორ იცვლება თქვენი სატესტო ნაკრები დროთა განმავლობაში, იპოვოთ ნელი ან შენელებული ტესტები და გაიგოთ, რატომ ჩაიშალა გაშვება CI-ში. მათ ნახავთ **Tests**-ში დაშბორდზე, მოდულის, `describe` ბლოკის და ტესტის დონეზე.

## არასტაბილური ტესტები

არასტაბილური ტესტი ერთი და იგივე კოდით ზოგჯერ გადის, ზოგჯერ კი ჩავარდება. Tuist მონიშნავს ტესტს როგორც არასტაბილურს, თუ ის ჩაიშალა და გადაიარა ერთსა და იმავე კომიტზე CI-ში. ასევე შეგიძლიათ აიძულოთ პაკეტს ხელახლა სცადოს ჩაშლილი ტესტები, რაც აღმოაჩენს მათ ერთ გაშვებაში:

```elixir
tuist: [project: "account/project", cache: true, test_retries: 2]
```

ტესტი, რომელიც ხელახალი ცდისას გადის, მონიშნულია როგორც არასტაბილური და გაშვება წარმატებით სრულდება. **Flaky Tests** გვერდი ჩამოთვლის მათ.

## ტესტების შარდინგი

ტესტების შარდინგი ანაწილებს თქვენს სატესტო ნაკრებს CI-რანერებზე. Tuist აბალანსებს შარდებს იმის მიხედვით, თუ რამდენ ხანს გაგრძელდა თითოეული სატესტო ფაილის შესრულება წინა გაშვებებში, და აკომპილირებს პროექტს ერთხელ და უზიარებს ამ ბილდს ყველა რანერს. ერთი ბრძანება გეგმავს შარდებს:

```bash
mix tuist.test.build --shard-max 4
```

შემდეგ თითოეული რანერი ასრულებს თავის წილს `TUIST_SHARD_INDEX`-ის მითითებით, და შედეგები დაშბორდზე ჩანს როგორც ერთიანი ტესტების გაშვება:

```bash
TUIST_SHARD_INDEX=0 mix test
```

## ჩართეთ გუნდი

ანალიტიკა მრავლდება პროექტთან დაკავშირებული ადამიანების რაოდენობის ზრდასთან ერთად. მიიწვიეთ თქვენი გუნდის წევრები ორგანიზაციაში დაშბორდის ანგარიშის პარამეტრებიდან და დააყენეთ <.localized_link href="/guides/integrations/authentication/sso">Single Sign-On</.localized_link> (Google, Okta, Microsoft), რათა ახალი წევრის დამატება იყოს ერთი დაწკაპუნება და არა თითოეული პირისთვის `mix tuist.login`-ის შესრულება.

CI-სთვის არ გამოიყენოთ პირადი შესვლა. GitHub Actions, CircleCI და Bitrise შეუძლიათ ავტორიზაცია OpenID Connect-ის მეშვეობით; სხვა პროვაიდერებზე დააყენეთ შეზღუდული `TUIST_TOKEN`. მიჰყევით <.localized_link href="/guides/install-hex-package#authenticate">CI ავტორიზაციის ნაბიჯებს</.localized_link>.
