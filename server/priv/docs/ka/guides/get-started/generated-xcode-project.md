# გენერირებული Xcode პროექტი {#generated-xcode-project}

::: code-group

აირჩიეთ ეს გზა, როდესაც გსურთ, რომ Tuist-მა აღწეროს და შექმნას თქვენი Xcode პროექტი Swift მანიფესტებიდან. გენერირებული პროექტი კომპაქტურ, დეკლარატიულ გრაფის აღწერად აქცევს მოდულური Xcode პროექტის სირთულეს. ის ასევე მკაცრი წინაპირობაა მოდულების ქეშისა და შერჩევითი ტესტირებისთვის.

ქვემოთ მოცემული თითოეული განყოფილება იწყება იმის აღწერით, რაც დღეს აკლია, შემდეგ კი გაგივლით ფუნქციას, რომელიც ამ ნაკლოვანებას ავსებს.

## წინაპირობები

- macOS დაყენებული Xcode-ით.
- <.localized_link href="/guides/install-tuist">Tuist-ის ბრძანებების ხაზის ინტერფეისი</.localized_link>.

## პროექტის შექმნა

მუშაობის სანახავად ყველაზე სწრაფი გზა ახალი პროექტია. ცარიელ საქაღალდეში გაუშვით `tuist init` და აირჩიეთ **გენერირებული პროექტის შექმნა**, მიუთითეთ პლატფორმა, დაადასტურეთ სახელი, შემდეგ გაიარეთ ავთენტიკაცია და აირჩიეთ ანგარიში, რომელსაც უნდა ეკუთვნოდეს პროექტი.

```bash
mkdir MyApp && cd MyApp
tuist init
```

თუ ამას კოდირების აგენტით ან სკრიპტით აკეთებთ, ჯერ გაუშვით `tuist auth login` (ბრაუზერის ნაკადი ელოდება Enter-ის დაჭერას), შემდეგ გამოიყენეთ არაინტერაქტიული ფორმა:

```bash
tuist init --build-system generated-xcode --name MyApp --platform ios --account <account>
```

init-ის დასრულების შემდეგ გაუშვით `tuist generate`. Tuist ქმნის `.xcworkspace`-ს თქვენს მანიფესტებთან ერთად და ხსნის მას Xcode-ში. ააწყვეთ და გაუშვით სამიზნე. სიმულატორში უნდა დაინახოთ მაგალითის აპლიკაციის გაშვება.

ეს არის „მიერთებული + გენერირების“ მდგომარეობა. ქვემოთ მოცემული ყველაფერი არჩევითია და დამოუკიდებელი.

თუ არსებულ აპლიკაციას გადაიტანთ, ჯერ მიუერთეთ ის [Xcode პროექტის მიგრაციის სახელმძღვანელოს](https://tuist.dev/en/docs/guides/features/projects/adoption/migrate/xcode-project) მიხედვით, შემდეგ დაბრუნდით და გააგრძელეთ იმ განყოფილებებით, რომლებიც თქვენს პრობლემას შეესაბამება.

## პროექტის გენერაცია

`.xcodeproj` აჯამებს თქვენი აპლიკაციის სტრუქტურას XML-ში: ფაილის მითითებები, აწყობის ეტაპები, სამიზნე დამოკიდებულებები, სქემები და აწყობის პარამეტრები ერთსა და იმავე ხეშია განთავსებული, გრაფის, როგორც გრაფის, ანალიზის პრიმიტივის გარეშე. პროექტის ზრდასთან ერთად, ამ სტრუქტურის თავში შენარჩუნება რთულდება, Xcode-ს კი არ აქვს სტაბილური სახელური, რათა ინსტრუმენტებმა მისი ჰეშირება შეძლონ და სამუშაო გამოტოვონ, როცა არაფერი შეცვლილა.

გენერირებული პროექტები გრაფს დეკლარატიულ Swift-ად აკომპაქტებენ. `Project.swift` პირდაპირ აღწერს სამიზნეებს, დამოკიდებულებებსა და რესურსებს, Tuist კი ინარჩუნებს მის უკან გრაფის სტაბილურ მოდელს. სწორედ ეს მოდელი ხსნის ქვემოთ მოცემულ განყოფილებებს: მოდულების ქეშირება მას ჰეშირებს ბინარების ხელახლა გამოყენებისთვის, ხოლო შერჩევითი ტესტირება — იმ ტესტების გამოტოვებისთვის, რომელთა შესავალი მონაცემები არ შეცვლილა.

```swift
import ProjectDescription

let project = Project(
    name: "MyApp",
    targets: [
        .target(
            name: "MyApp",
            destinations: .iOS,
            product: .app,
            bundleId: "dev.tuist.MyApp",
            sources: ["MyApp/Sources/**"],
            dependencies: []
        )
    ]
)
```

ყოველი `tuist generate` წარმოქმნის დეტერმინისტულ სამუშაო სივრცეს მანიფესტებიდან. დაამატეთ `.xcodeproj` და `.xcworkspace` `.gitignore`-ში.

## მოდულების ქეში

მოდულური Xcode პროექტის ნულიდან კომპილაცია თითოეული მანქანისთვის ხარჯია. ყოველი თანამშრომელი და ყოველი CI გამშვები ქმნის იმავე ობიექტური ფაილების საკუთარ ასლს. Xcode-ის კომპილაციის ქეში ამცირებს შიდა ციკლს, მაგრამ არ აშორებს თითოეული სამიზნის თითოეულ მანქანაზე აწყობას და ვერ ცვლის მთელ ჩარჩოს წინასწარ აწყობილი ბინარით.

მოდულების ქეში ამას აკეთებს. ის ერთხელ აწყობს თქვენს გრაფში ყოველ ქეშირებად დამოკიდებულებას (ჩარჩოები, ბიბლიოთეკები, ბანდლები), ინახავს მიღებულ ბინარებს სამიზნის შესავალი მონაცემების ჰეშის მიხედვით და მომდევნო გენერაციებზე სამიზნეს მისი ბინარით ცვლის. შეუცვლელი მოდულები აღარ კომპილირდება:

```bash
tuist cache
```

პირველი გაშვება ყველაფერს აკომპილირებს და ბინარებს თქვენს ანგარიშზე ატვირთავს. შემდეგ `tuist generate`-ზე შეუცვლელი დამოკიდებულებები მათი ქეშირებული ბინარებით იცვლება და Xcode კომპილაციის ნაცვლად `.xcframework`-ებთან აკავშირებს.

## შერჩევითი ტესტირება

`xcodebuild test` არ იცის, რომელ ტესტებს ეხება ცვლილება, ამიტომ CI ყოველ push-ზე მთელ სუიტს უშვებს. სუიტის ზრდასთან ერთად, სხვაობა იმას შორის, რაც რეალურად უნდა გაეშვას და იმას შორის, რაც ეშვება, წუთებიდან ათეულ წუთებამდე იზრდება.

შერჩევითი ტესტირება უშვებს მხოლოდ იმ ტესტებს, რომლებზეც გავლენა იქონია ბოლო წარმატებული ტესტების გაშვების შემდეგ მომხდარმა ცვლილებებმა, პროექტის გრაფისა და იმავე ჰეშირების ალგორითმის გამოყენებით, რომელზეც მოდულების ქეშია დაფუძნებული:

```bash
tuist test
```

პირველი `tuist test` ყველაფერს უშვებს და ინახავს თითოეული სამიზნის ჰეშებს. მომდევნო გაშვებები ტოვებს სამიზნეებს, რომელთა შესავალი მონაცემები არ შეცვლილა. გადაიტანეთ `tuist test` CI-ში `xcodebuild test`-ის ნაცვლად და უკუკავშირი წუთების ნაცვლად წამებში მიიღებთ.

## პაკეტების რეესტრი

Swift Package Manager აგვარებს დამოკიდებულებებს თითოეული პაკეტის git ისტორიის ღრმა კლონირებით, რადგან პაკეტებზე მისამართება ხდება URL-ით და არა რეესტრით. ათეულობით ტრანზიტული პაკეტის მქონე პროექტზე აგვარება სუფთა checkout-ზე წუთებს მოიცავს და ყოველ CI დავალებაზე მეორდება.

Tuist Package Registry ემსახურება იმავე პაკეტებს, რომლებსაც Swift Package Index აკონტროლებს, მაგრამ როგორც რეალური რეესტრი, ასე რომ SwiftPM მხოლოდ იმ კომიტს იღებს, რომელიც რეალურად გჭირდებათ. ჩართეთ ის ერთხელ `registryEnabled: true`-ის დაყენებით თქვენს `Tuist.swift`-ში:

```swift
let tuist = Tuist(
    project: .tuist(
        generationOptions: .options(
            registryEnabled: true
        )
    )
)
```

ხელახლა შექმენით. პაკეტების აგვარება წუთებიდან წამებამდე ეცემა.

## აწყობის ანალიტიკა

Xcode იწერს თითოეული სამიზნის აწყობის ხანგრძლივობას ჟურნალში და აწყობის ანგარიშში. არცერთი არ არის აგრეგირებული გაშვებებსა თუ მანქანებს შორის, ამიტომ აწყობის დროის რეგრესია ჩვეულებრივ მხოლოდ CI-ის საერთო შენელებად ვლინდება.

აწყობის ანალიტიკა ავტომატურად იწერს ყოველი აწყობის ხანგრძლივობასა და ფაზების დროს გენერირებული სქემებისთვის. დამატებითი კონფიგურაცია არ არის საჭირო. გახსენით დაფის **აწყობები** ჩანართი თქვენი შემდეგი `tuist generate` + აწყობის ციკლის შემდეგ.

## ტესტების ანალიტიკა

Xcode იტყობინება თითოეული ტესტის შედეგებს ერთი გაშვებით ერთდროულად. ის არ აჯამებს გაშვებებს შორის სიგნალს, რომელიც რეალურად გჭირდებათ: არასტაბილურობის სიხშირე, კვირიდან კვირამდე ხანგრძლივობა, რომელი სიმულატორის ვარიანტები ვერ ხერხდება.

ტესტების ანალიტიკა ავტომატურად იწერს ყოველი ტესტის შედეგსა და ხანგრძლივობას გენერირებული სქემებისთვის და აკორელირებს შედეგებს გაშვებებს შორის. არასტაბილური ტესტები, ნელი ტესტები და შეცდომები ჩანს დავაფის **ტესტები** ჩანართზე. როცა არასტაბილურობა გროვდება, კარანტინში მოათავსეთ ისინი დაფიდან, რათა შერწყმების ბლოკირება შეწყვიტონ.

## გუნდის ჩართვა

მოდულების ქეში და შერჩევითი ტესტირება ყველაზე მეტად მაშინ იძლევა შედეგს, როცა ყველა ერთსა და იმავე საერთო ზედაპირზე მუშაობს. მიიწვიეთ თქვენი თანაგუნდელები ორგანიზაციაში დაფის ანგარიშის პარამეტრებიდან და მოაწყვეთ <.localized_link href="/guides/integrations/authentication/sso">ერთჯერადი შესვლა</.localized_link> (Google, Okta, Microsoft), რათა დარეგისტრირება იყოს ერთი დაწკაპუნება და არა თითოეული პირისთვის `tuist auth login`.
