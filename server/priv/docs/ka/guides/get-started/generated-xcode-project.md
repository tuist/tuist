# გენერირებული Xcode პროექტი {#generated-xcode-project}

::: code-group

მიჰყევით ამ გზას, როცა გსურთ, რომ Tuist-მა აღწეროს და შექმნას თქვენი Xcode პროექტი Swift მანიფესტებიდან. გენერირებული პროექტი კომპაქტურად აჯამებს მოდულური Xcode პროექტის სირთულეს გრაფის მოკლე, დეკლარატიულ აღწერაში. ის ასევე მკაცრი წინაპირობაა მოდულის ქეშისა და შერჩევითი ტესტირებისთვის.

ქვემოთ მოცემული ყოველი განყოფილება იწყება იმით, რაც დღეს აკლია, შემდეგ კი გაგივლით ფუნქციას, რომელიც ამ ხარვეზს ავსებს.

## წინაპირობები

- macOS დაყენებული Xcode-ით.
- <.localized_link href="/guides/install-tuist">Tuist ბრძანების ინტერფეისი</.localized_link>.

## პროექტის შექმნა

მუშაობის სანახავად ყველაზე სწრაფი გზაა ახალი პროექტი. ცარიელ საქაღალდეში გაუშვით `tuist init` და აირჩიეთ **გენერირებული პროექტის შექმნა**, აირჩიეთ პლატფორმა, დაადასტურეთ სახელი, შემდეგ გაიარეთ ავთენტიკაცია და აირჩიეთ ანგარიში, რომელსაც უნდა ეკუთვნოდეს პროექტი.

```bash
mkdir MyApp && cd MyApp
tuist init
```

თუ ამას კოდირების აგენტით ან სკრიპტით აკეთებთ, ჯერ გაუშვით `tuist auth login` (ბრაუზერის ნაკადი ელოდება Enter-ის დაჭერას), შემდეგ გამოიყენეთ არაინტერაქტიული ფორმა:

```bash
tuist init --build-system generated-xcode --name MyApp --platform ios --account <account>
```

როცა init დასრულდება, გაუშვით `tuist generate`. Tuist წერს `.xcworkspace` თქვენს მანიფესტებთან ერთად და ხსნის მას Xcode-ში. ააწყვეთ და გაუშვით სამიზნე. სიმულატორში უნდა დაინახოთ მაგალითის აპლიკაციის გაშვება.

ეს არის „დაკავშირებული + გენერირების“ მდგომარეობა. ქვემოთ მოცემული ყველაფერი არის სურვილისამებრ და დამოუკიდებელი.

თუ არსებულ აპლიკაციას გადაიტანთ, ჯერ დააკავშირეთ ის [Xcode პროექტის მიგრაციის სახელმძღვანელოს](https://tuist.dev/en/docs/guides/features/projects/adoption/migrate/xcode-project) მიხედვით, შემდეგ დაბრუნდით და გააგრძელეთ ის განყოფილებებით, რომლებიც თქვენს პრობლემას შეესაბამება.

## პროექტის გენერაცია

`.xcodeproj` აჯამებს თქვენი აპლიკაციის სტრუქტურას XML-ში: ფაილის მითითებები, აწყობის ეტაპები, სამიზნე დამოკიდებულებები, სქემები და აწყობის პარამეტრები ერთსა და იმავე ხეშია, გრაფის როგორც გრაფის ანალიზისთვის საჭირო პრიმიტივის გარეშე. პროექტის ზრდასთან ერთად, ამ სტრუქტურის თავში დაჭერა რთულდება და Xcode-ს არ აქვს სტაბილური იდენტიფიკატორი, რათა ინსტრუმენტებმა დააჰეშონ ის და გამოტოვონ სამუშაო, როცა არაფერი შეცვლილა.

გენერირებული პროექტები გრაფს კომპაქტურად აჯამებენ დეკლარატიულ Swift-ში. `Project.swift` პირდაპირ აღწერს სამიზნეებს, დამოკიდებულებებს და რესურსებს, ხოლო Tuist ინარჩუნებს გრაფის სტაბილურ მოდელს მის უკან. ეს მოდელი ხსნის ქვემოთ მოცემულ განყოფილებებს: მოდულის ქეშირება აჰეშებს მას ბინარების ხელახლა გამოყენებისთვის, ხოლო შერჩევითი ტესტირება აჰეშებს მას იმ ტესტების გამოსატოვებლად, რომელთა შეყვანები არ შეცვლილა.

```swift
import ProjectDescription

let project = Project(
    name: "MyApp",
    targets: [
        .target(
            name: "MyApp",
            destinations: .iOS,
            product: .app,
            bundleId: "dev.tuist.MyApp",
            sources: ["MyApp/Sources/**"],
            dependencies: []
        )
    ]
)
```

ყოველი `tuist generate` ქმნის დეტერმინისტულ სამუშაო სივრცეს მანიფესტებიდან. დაამატეთ `.xcodeproj` და `.xcworkspace` ფაილში `.gitignore`.

## მოდულის ქეში

მოდულური Xcode პროექტის ნულიდან კომპილაცია არის თითოეული მანქანის ხარჯი. ყოველი თანაგუნდელი და ყოველი CI გამშვები ქმნის იმავე ობიექტური ფაილების საკუთარ ასლს. Xcode კომპილაციის ქეში ამცირებს შიდა ციკლს, მაგრამ არ აშორებს ყოველი სამიზნის თითოეულ მანქანაზე აწყობას და ვერ ჩაანაცვლებს მთელ ფრეიმვორკს წინასწარ აწყობილი ბინარით.

მოდულის ქეში ამას აკეთებს. ის ერთხელ აწყობს თქვენს გრაფში ყოველ ქეშირებად დამოკიდებულებას (ფრეიმვორკები, ბიბლიოთეკები, ბანდლები), ინახავს მიღებულ ბინარებს სამიზნის შეყვანების ჰეშის მიხედვით და შემდგომ გენერაციებზე სამიზნეს ცვლის მისი ბინარით. შეუცვლელი მოდულები აღარ კომპილირდება:

```bash
tuist cache
```

პირველი გაშვება ყველაფერს აკომპილირებს და ბინარებს ტვირთავს თქვენს ანგარიშზე. შემდეგ `tuist generate`-ზე შეუცვლელი დამოკიდებულებები ჩანაცვლდება მათი ქეშირებული ბინარებით და Xcode აკავშირებს `.xcframework`s-ს წყაროდან კომპილაციის ნაცვლად.

## შერჩევითი ტესტირება

`xcodebuild test`-ს არ იცის, რომელ ტესტებს ეხება ცვლილება, ამიტომ CI ყოველ push-ზე მთელ სუიტს უშვებს. სუიტის ზრდასთან ერთად, სხვაობა იმას შორის, რაც რეალურად უნდა გაეშვას და იმას შორის, რაც ეშვება, იზრდება წუთებიდან ათეულობით წუთამდე.

შერჩევითი ტესტირება უშვებს მხოლოდ იმ ტესტებს, რომლებზეც იმოქმედა ბოლო წარმატებული ტესტების გაშვების შემდეგ მომხდარმა ცვლილებებმა, პროექტის გრაფისა და იმავე ჰეშინგის ალგორითმის გამოყენებით, რომელზეც მოდულის ქეშია დამოკიდებული:

```bash
tuist test
```

პირველი `tuist test` ყველაფერს უშვებს და ინახავს თითოეული სამიზნის ჰეშებს. შემდგომი გაშვებები ტოვებს სამიზნეებს, რომელთა შეყვანები არ შეცვლილა. გადაიტანეთ `tuist test` CI-ში `xcodebuild test`-ის ნაცვლად და უკუკავშირი წუთების ნაცვლად წამებში მიიღებთ.

## პაკეტების რეესტრი

Swift Package Manager აგვარებს დამოკიდებულებებს თითოეული პაკეტის git ისტორიის სრული კლონირებით, რადგან პაკეტებს მიმართავენ URL-ით და არა რეესტრით. პროექტში, რომელსაც ათეულობით ტრანზიტული პაკეტი აქვს, აგვარება სუფთა checkout-ზე წუთებში მიდის და ყოველ CI სამუშაოზე მეორდება.

Tuist Package Registry ემსახურება იმავე პაკეტებს, რომლებსაც Swift Package Index აკვირდება, მაგრამ როგორც რეალური რეესტრი, ასე რომ SwiftPM მხოლოდ იმ კომიტს იღებს, რომელიც რეალურად გჭირდებათ. ჩართეთ ის ერთხელ `registryEnabled: true`-ის დაყენებით თქვენს `Tuist.swift`-ში:

```swift
let tuist = Tuist(
    project: .tuist(
        generationOptions: .options(
            registryEnabled: true
        )
    )
)
```

ხელახლა შექმენით. პაკეტების აგვარება წუთებიდან წამებამდე ეცემა.

## აწყობის ინსაიტები

Xcode იწერს თითოეული სამიზნის აწყობის ხანგრძლივობას ლოგში და აწყობის ანგარიშში. არცერთი არ არის აგრეგირებული გაშვებებსა თუ მანქანებს შორის, ამიტომ აწყობის დროის რეგრესია ჩვეულებრივ მხოლოდ როგორც უფრო ნელი CI საერთოდ ვლინდება.

Build insights ავტომატურად იწერს ყოველი აწყობის ხანგრძლივობას და ფაზების დროს გენერირებული სქემებისთვის. დამატებითი კონფიგურაცია არ არის საჭირო. გახსენით დაფის **Builds** ჩანართი თქვენი შემდეგი `tuist generate` + აწყობის ციკლის შემდეგ.

## ტესტების ინსაიტები

Xcode ანგარიშობს თითოეული ტესტის შედეგებს ერთი გაშვებით ერთდროულად. ის არ აგრეგირებს გაშვებებს შორის სიგნალს, რომელიც რეალურად გჭირდებათ: არასტაბილურობის მაჩვენებელი, კვირიდან კვირამდე ხანგრძლივობა, რომელი სიმულატორის ვარიანტები ვერ ხერხდება.

Test insights ავტომატურად იწერს ყოველი ტესტის შედეგს და ხანგრძლივობას გენერირებული სქემებისთვის და აკორელირებს შედეგებს გაშვებებს შორის. არასტაბილური ტესტები, ნელი ტესტები და შეცდომები ჩანს დაფის **Tests** ჩანართზე. როცა არასტაბილურობა გროვდება, იზოლირეთ ისინი დაფიდან, რათა შეწყვიტონ შერწყმების ბლოკირება.

## გუნდის ჩართვა

მოდულის ქეში და შერჩევითი ტესტირება ყველაზე მეტად მაშინ იძლევა შედეგს, როცა ყველა ერთსა და იმავე საერთო ზედაპირს ეხება. მიიწვიეთ თქვენი თანაგუნდელები ორგანიზაციაში დაფის ანგარიშის პარამეტრებიდან და დააყენეთ <.localized_link href="/guides/integrations/authentication/sso">ერთიანი შესვლა</.localized_link> (Google, Okta, Microsoft), რათა onboard-ინგი იყოს ერთი დაწკაპუნება და არა თითოეული პირისთვის `tuist auth login`.
