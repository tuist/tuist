მიჰყევით ამ გზას, როდესაც გსურთ, რომ Tuist-მა აღწეროს და შექმნას თქვენი Xcode პროექტი Swift მანიფესტებიდან. გენერირებული პროექტი კომპაქტურად აჯამებს მოდულური Xcode პროექტის სირთულეს გრაფის მოკლე, დეკლარატიულ აღწერაში. ეს ასევე მკაცრი წინაპირობაა მოდულის ქეშისა და შერჩევითი ტესტირებისთვის.

ყოველი ქვემოთ მოცემული განყოფილება იწყება იმით, რაც დღეს აკლია, და შემდეგ გაგივლით ფუნქციას, რომელიც ამ ნაკლს ავსებს.

## წინაპირობები

- macOS დაყენებული Xcode-ით.
- <.localized_link href="/guides/install-tuist">Tuist-ის ბრძანების ხაზის ინტერფეისი</.localized_link>.

## პროექტის შექმნა

სამუშაოს ნახვის ყველაზე სწრაფი გზა ახალი პროექტია. ცარიელ დირექტორიაში გაუშვით `tuist init` და აირჩიეთ **გენერირებული პროექტის შექმნა**, აირჩიეთ პლატფორმა, დაადასტურეთ სახელი, შემდეგ გაიარეთ ავთენტიკაცია და აირჩიეთ ანგარიში, რომელსაც უნდა ეკუთვნოდეს პროექტი.

```bash
mkdir MyApp && cd MyApp
tuist init
```

თუ ამას კოდირების აგენტით ან სკრიპტით აკეთებთ, ჯერ გაუშვით `tuist auth login` (ბრაუზერის ნაკადი ელოდება Enter-ის დაჭერას), შემდეგ გამოიყენეთ არაინტერაქტიული ფორმა:

```bash
tuist init --build-system generated-xcode --name MyApp --platform ios --account <account>
```

როდესაც init დასრულდება, გაუშვით `tuist generate`. Tuist წერს `.xcworkspace` თქვენს მანიფესტებთან ერთად და ხსნის მას Xcode-ში. ააწყვეთ და გაუშვით სამიზნე. თქვენ უნდა ნახოთ მაგალითის აპლიკაციის გაშვება სიმულატორში.

ეს არის "დაკავშირებული + გენერირების" მდგომარეობა. ყველაფერი ქვემოთ არის არასავალდებულო და დამოუკიდებელი.

თუ არსებულ აპლიკაციას გადაიტანთ, ჯერ დააკავშირეთ ის [Xcode პროექტის მიგრაციის სახელმძღვანელოს](https://tuist.dev/en/docs/guides/features/projects/adoption/migrate/xcode-project) მიხედვით, შემდეგ დაბრუნდით და გააგრძელეთ იმ განყოფილებებით, რომლებიც თქვენს პრობლემას შეესაბამება.

## პროექტის გენერაცია

`.xcodeproj` აჯამებს თქვენი აპლიკაციის სტრუქტურას XML-ში: ფაილის მითითებები, აწყობის ეტაპები, სამიზნე დამოკიდებულებები, სქემები და აწყობის პარამეტრები ყველა ერთ ხეში ცხოვრობს, გრაფის, როგორც გრაფის, ანალიზისთვის პრიმიტივის გარეშე. პროექტის ზრდასთან ერთად, ამ სტრუქტურის თავში დაჭერა რთულდება და Xcode-ს არ აქვს სტაბილური სახელური ინსტრუმენტებისთვის, რომ დააჰეშონ ის და გამოტოვონ სამუშაო, როდესაც არაფერი შეცვლილა.

გენერირებული პროექტები კომპაქტურად აჯამებენ გრაფს დეკლარატიულ Swift-ში. `Project.swift` პირდაპირ აღწერს სამიზნეებს, დამოკიდებულებებს და რესურსებს, ხოლო Tuist ინარჩუნებს მის უკან გრაფის სტაბილურ მოდელს. ეს მოდელია ის, რაც ხსნის ქვემოთ მოცემულ განყოფილებებს: მოდულის ქეშირება აჰეშებს მას ბინარების ხელახლა გამოსაყენებლად, ხოლო შერჩევითი ტესტირება აჰეშებს მას იმ ტესტების გამოსატოვებლად, რომელთა შეყვანები არ შეცვლილა.

```swift
import ProjectDescription

let project = Project(
    name: "MyApp",
    targets: [
        .target(
            name: "MyApp",
            destinations: .iOS,
            product: .app,
            bundleId: "dev.tuist.MyApp",
            sources: ["MyApp/Sources/**"],
            dependencies: []
        )
    ]
)
```

ყოველი `tuist generate` ქმნის დეტერმინისტულ სამუშაო სივრცეს მანიფესტებიდან. დაამატეთ `.xcodeproj` და `.xcworkspace` `.gitignore`-ში.

## მოდულის ქეში

მოდილური Xcode პროექტის ნულიდან კომპილირება თითოეული მანქანისთვის ხარჯია. ყოველი გუნდის წევრი და ყოველი CI გამშვები ქმნის იგივე ობიექტური ფაილების საკუთარ ასლს. Xcode-ის კომპილაციის ქეში ამცირებს შიდა ციკლს, მაგრამ არ აშორებს თითოეული სამიზნის თითოეულ მანქანაზე აწყობას და ვერ ცვლის მთელ ფრეიმვორკს წინასწარ აწყობილი ბინარით.

მოდულის ქეში აკეთებს ამას. ის ერთხელ აწყობს თქვენს გრაფში ყოველ ქეშირებად დამოკიდებულებას (ფრეიმვორკები, ბიბლიოთეკები, ბანდლები), ინახავს მიღებულ ბინარებს სამიზნის შეყვანების ჰეშის მიხედვით და ცვლის სამიზნეს მისი ბინარით შემდგომ გენერაციებზე. შეუცვლელი მოდულები წყვეტენ კომპილირებას:

```bash
tuist cache
```

პირველი გაშვება კომპილირებს ყველაფერს და ტვირთავს ბინარებს თქვენს ანგარიშზე. შემდეგ `tuist generate`-ზე, შეუცვლელი დამოკიდებულებები იცვლება მათი ქეშირებული ბინარებით და Xcode აკავშირებს `.xcframework`-ებს წყაროდან კომპილირების ნაცვლად.

## შერჩევითი ტესტირება

`xcodebuild test` არ იცის, რომელ ტესტებს ეხება ცვლილება, ამიტომ CI ყოველ push-ზე მთელ სიუიტს უშვებს. სიუიტის ზრდასთან ერთად, სხვაობა იმას შორის, რაც რეალურად უნდა გაშვებულიყო და რაც გაშვებულია, იზრდება წუთებიდან ათეულობით წუთამდე.

შერჩევითი ტესტირება უშვებს მხოლოდ იმ ტესტებს, რომლებზეც გავლენა იქონია ბოლო წარმატებული ტესტის გაშვების შემდეგ მომხდარმა ცვლილებებმა, პროექტის გრაფისა და იმავე ჰეშინგის ალგორითმის გამოყენებით, რომელზეც მოდულის ქეშია დამოკიდებული:

```bash
tuist test
```

პირველი `tuist test` უშვებს ყველაფერს და ინახავს თითოეული სამიზნის ჰეშებს. შემდგომი გაშვებები ტოვებს სამიზნეებს, რომელთა შეყვანები არ შეცვლილა. გადაიტანეთ `tuist test` CI-ში `xcodebuild test`-ის ნაცვლად და უკუკავშირი წამებში მიიღება წუთების ნაცვლად.

## პაკეტების რეესტრი

Swift Package Manager აგვარებს დამოკიდებულებებს თითოეული პაკეტის git ისტორიის ღრმა კლონირებით, რადგან პაკეტები მიმართულია URL-ით და არა რეესტრით. ათეულობით ტრანზიტული პაკეტის მქონე პროექტზე, გარჩევა სუფთა checkout-ზე წუთებს მოიცავს და მეორდება ყოველ CI სამუშაოზე.

Tuist Package Registry ემსახურება იმავე პაკეტებს, რომლებსაც Swift Package Index აკონტროლებს, მაგრამ როგორც რეალური რეესტრი, ასე რომ SwiftPM მხოლოდ იმ კომიტს იღებს, რომელიც რეალურად გჭირდებათ. ჩართეთ ის ერთხელ `registryEnabled: true`-ის დაყენებით თქვენს `Tuist.swift`-ში:

```swift
let tuist = Tuist(
    project: .tuist(
        generationOptions: .options(
            registryEnabled: true
        )
    )
)
```

ხელახლა შექმენით. პაკეტების გარჩევა წუთებიდან წამებამდე ეცემა.

## აწყობის ინსაიტები

Xcode იწერს თითოეული სამიზნის აწყობის ხანგრძლივობას ჟურნალში და აწყობის ანგარიშში. არცერთი არ არის აგრეგირებული გაშვებებსა თუ მანქანებს შორის, ამიტომ აწყობის დროის რეგრესია ჩვეულებრივ მხოლოდ როგორც ნელი CI ჯამურად ჩნდება.

Build insights ავტომატურად იწერს ყოველი აწყობის ხანგრძლივობას და ფაზების დროს გენერირებული სქემებისთვის. არაფერია დამატებითად დასაკონფიგურირებელი. გახსენით დაშბორდის **აწყობები** ჩანართი თქვენი შემდეგი `tuist generate` + აწყობის ციკლის შემდეგ.

## ტესტის ინსაიტები

Xcode იუწყება თითოეული ტესტის შედეგებს ერთი გაშვებით ერთდროულად. ის არ აგრეგირებს გაშვებებს შორის სიგნალს, რომელიც რეალურად გჭირდებათ: ფლაკიობის სიხშირე, კვირიდან კვირამდე ხანგრძლივობა, რომელი სიმულატორის ვარიანტები ვერხერხდება.

Test insights ავტომატურად იწერს ყოველი ტესტის შედეგსა და ხანგრძლივობას გენერირებული სქემებისთვის და აკორელირებს შედეგებს გაშვებებს შორის. ფლაკიური ტესტები, ნელი ტესტები და შეცდომები ჩნდება დაშბორდის **ტესტები** ჩანართზე. როდესაც ფლაკიები გროვდება, იზოლირეთ ისინი დაშბორდიდან, რათა შეწყვიტონ შერწყმების ბლოკირება.

## გუნდის ჩართვა

მოდულის ქეში და შერჩევითი ტესტირება ყველაზე მეტად იხდის თავს, როდესაც ყველა ერთსა და იმავე გაზიარებულ ზედაპირზე მუშაობს. მიიწვიეთ თქვენი გუნდის წევრები ორგანიზაციაში დაშბორდის ანგარიშის პარამეტრებიდან და დააყენეთ <.localized_link href="/guides/integrations/authentication/sso">ერთჯერადი შესვლა</.localized_link> (Google, Okta, Microsoft), რათა დარეგისტრება იყოს ერთი დაწკაპუნება და არა თითოეული პირისთვის `tuist auth login`.
