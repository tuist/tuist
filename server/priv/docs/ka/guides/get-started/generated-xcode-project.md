# გენერირებული Xcode პროექტი {#generated-xcode-project}

მიჰყევით ამ გზას, როდესაც გსურთ, რომ Tuist-მა აღწეროს და შექმნას თქვენი Xcode პროექტი Swift მანიფესტებიდან. გენერირებული პროექტი აჯამებს მოდულური Xcode პროექტის სირთულეს გრაფის მოკლე, დეკლარატიულ აღწერაში. ის ასევე არის მკაცრი წინაპირობა მოდულების ქეშისა და შერჩევითი ტესტირებისთვის.

ყოველი ქვემოთ მოცემული განყოფილება იწყება იმის აღწერით, რაც დღეს აკლია, და შემდეგ გაგივლით ფუნქციას, რომელიც ამ ნაკლოვანებას ავსებს.

## წინაპირობები

- macOS დაყენებული Xcode-ით.
- <.localized_link href="/guides/install-tuist">Tuist-ის ბრძანების ხაზის ინტერფეისი</.localized_link>.

## პროექტის შექმნა

მუშაობის სანახავად ყველაზე სწრაფი გზა ახალი პროექტია. ცარიელ დირექტორიაში გაუშვით `tuist init` და აირჩიეთ **გენერირებული პროექტის შექმნა**, აირჩიეთ პლატფორმა, დაადასტურეთ სახელი, შემდეგ გაიარეთ ავთენტიკაცია და აირჩიეთ ანგარიში, რომელსაც უნდა ეკუთვნოდეს პროექტი.

```bash
mkdir MyApp && cd MyApp
tuist init
```

თუ ამას კოდირების აგენტით ან სკრიპტით აკეთებთ, ჯერ გაუშვით `tuist auth login` (ბრაუზერის ნაკადი ელოდება Enter-ის დაჭერას), შემდეგ გამოიყენეთ არაინტერაქტიული ფორმა:

```bash
tuist init --build-system generated-xcode --name MyApp --platform ios --account <account>
```

როდესაც init დასრულდება, გაუშვით `tuist generate`. Tuist წერს `.xcworkspace`-ს თქვენს მანიფესტებთან ერთად და ხსნის მას Xcode-ში. ააწყვეთ და გაუშვით სამიზნე. სიმულატორში უნდა დაინახოთ მაგალითის აპლიკაციის გაშვება.

ეს არის „დაკავშირებული + გენერირების“ მდგომარეობა. ქვემოთ მოცემული ყველაფერი არის არასავალდებულო და დამოუკიდებელი.

თუ არსებულ აპლიკაციას გადაიტანთ, ჯერ დააკავშირეთ ის [Xcode პროექტის მიგრაციის სახელმძღვანელოს](https://tuist.dev/en/docs/guides/features/projects/adoption/migrate/xcode-project) მიხედვით, შემდეგ დაბრუნდით და გააგრძელეთ იმ განყოფილებებით, რომლებიც თქვენს პრობლემას შეესაბამება.

## პროექტის გენერაცია

`.xcodeproj` აჯამებს თქვენი აპლიკაციის სტრუქტურას XML-ში: ფაილის მითითებები, აწყობის ეტაპები, სამიზნე დამოკიდებულებები, სქემები და აწყობის პარამეტრები ყველა ერთ ხეშია, გრაფის, როგორც გრაფის, ანალიზისთვის არ არსებობს პრიმიტივი. პროექტის ზრდასთან ერთად, ამ სტრუქტურის თავში შენახვა რთულდება და Xcode-ს არ აქვს სტაბილური სახელური იმისთვის, რომ ინსტრუმენტებმა მისი ჰეშირება მოახდინონ და სამუშაო გამოტოვონ, როცა არაფერი შეცვლილა.

გენერირებული პროექტები გრაფს აჯამებენ დეკლარატიულ Swift-ში. `Project.swift` პირდაპირ აღწერს სამიზნეებს, დამოკიდებულებებს და რესურსებს, ხოლო Tuist ინარჩუნებს გრაფის სტაბილურ მოდელს მის უკან. ეს მოდელი ხსნის ქვემოთ მოცემულ განყოფილებებს: მოდულების ქეშირება ჰეშირებს მას ბინარების ხელახლა გამოსაყენებლად, ხოლო შერჩევითი ტესტირება ჰეშირებს მას იმ ტესტების გამოტოვებისთვის, რომელთა შეყვანები არ შეცვლილა.

```swift
import ProjectDescription

let project = Project(
    name: "MyApp",
    targets: [
        .target(
            name: "MyApp",
            destinations: .iOS,
            product: .app,
            bundleId: "dev.tuist.MyApp",
            sources: ["MyApp/Sources/**"],
            dependencies: []
        )
    ]
)
```

ყოველი `tuist generate` ქმნის დეტერმინისტულ სამუშაო სივრცეს მანიფესტებიდან. დაამატეთ `.xcodeproj` და `.xcworkspace` `.gitignore`-ში.

## მოდულების ქეში

მოდულური Xcode პროექტის ნულიდან კომპილაცია არის თითოეული მანქანის ხარჯი. ყოველი თანამშრომელი და ყოველი CI გამშვები ქმნის იმავე ობიექტური ფაილების საკუთარ ასლს. Xcode-ის კომპილაციის ქეში ამცირებს შიდა ციკლს, მაგრამ არ აშორებს თითოეული სამიზნის თითოეულ მანქანაზე აწყობას და ვერ ჩაანაცვლებს მთელ ფრეიმვორკს წინასწარ აწყობილი ბინარით.

მოდულების ქეში ამას აკეთებს. ის ერთხელ აწყობს თქვენს გრაფში ყოველ ქეშირებად დამოკიდებულებას (ფრეიმვორკები, ბიბლიოთეკები, ბანდლები), ინახავს მიღებულ ბინარებს სამიზნის შეყვანების ჰეშის მიხედვით და ცვლის სამიზნეს მისი ბინარით შემდგომ გენერაციებზე. შეუცვლელი მოდულები წყვეტენ კომპილაციას:

```bash
tuist cache
```

პირველი გაშვება აკომპილირებს ყველაფერს და ტვირთავს ბინარებს თქვენს ანგარიშზე. შემდეგ `tuist generate`-ზე, შეუცვლელი დამოკიდებულებები ჩანაცვლდება მათი ქეშირებული ბინარებით და Xcode აკავშირებს `.xcframework`-ებს წყაროდან კომპილაციის ნაცვლად.

## შერჩევითი ტესტირება

`xcodebuild test` არ იცის, რომელ ტესტებს ეხება ცვლილება, ამიტომ CI ყოველ push-ზე მთელ ნაკრებს აწარმოებს. ნაკრების ზრდასთან ერთად, სხვაობა იმას შორის, რაც რეალურად უნდა გაშვებულიყო და რაც გაშვებულია, იზრდება წუთებიდან ათეულობით წუთამდე.

შერჩევითი ტესტირება აწარმოებს მხოლოდ იმ ტესტებს, რომლებზეც იმოქმედა ბოლო წარმატებული ტესტების გაშვების შემდეგ მომხდარმა ცვლილებებმა, პროექტის გრაფის და იმავე ჰეშირების ალგორითმის გამოყენებით, რომელზეც მოდულების ქეშია დაფუძნებული:

```bash
tuist test
```

პირველი `tuist test` აწარმოებს ყველაფერს და ინახავს სამიზნეების ჰეშებს. შემდგომი გაშვებები ტოვებს სამიზნეებს, რომელთა შეყვანები არ შეცვლილა. გადაიტანეთ `tuist test` CI-ში `xcodebuild test`-ის ნაცვლად და უკუკავშირი წამებში მიიღებთ წუთების ნაცვლად.

## პაკეტების რეესტრი

Swift Package Manager აგვარებს დამოკიდებულებებს თითოეული პაკეტის git ისტორიის ღრმა კლონირებით, რადგან პაკეტებს URL-ით მიმართავენ და არა რეესტრით. ათეულობით ტრანზიტული პაკეტის მქონე პროექტზე, აგვარება სუფთა checkout-ზე წუთებს მოითხოვს და მეორდება ყოველ CI სამუშაოზე.

Tuist-ის პაკეტების რეესტრი ემსახურება იმავე პაკეტებს, რომლებსაც Swift Package Index აკონტროლებს, მაგრამ როგორც რეალური რეესტრი, ასე რომ SwiftPM იღებს მხოლოდ იმ კომიტს, რომელიც რეალურად გჭირდებათ. ჩართეთ ის ერთხელ `registryEnabled: true`-ის დაყენებით თქვენს `Tuist.swift`-ში:

```swift
let tuist = Tuist(
    project: .tuist(
        generationOptions: .options(
            registryEnabled: true
        )
    )
)
```

ხელახლა გენერირება. პაკეტების აგვარება წუთებიდან წამებამდე ეცემა.

## აწყობის ინსაიტები

Xcode იწერს სამიზნეების აწყობის ხანგრძლივობას ჟურნალში და აწყობის ანგარიშში. არცერთი არ არის აგრეგირებული გაშვებებსა თუ მანქანებს შორის, ამიტომ აწყობის დროის რეგრესია ჩვეულებრივ მხოლოდ როგორც ნელი CI საერთოდ ვლინდება.

აწყობის ინსაიტები ავტომატურად იწერს ყოველი აწყობის ხანგრძლივობას და ფაზების დროს გენერირებული სქემებისთვის. არაფერი დამატებითი არ არის საკონფიგურაციო. გახსენით დაფის **აწყობები** ჩანართი თქვენი შემდეგი `tuist generate` + აწყობის ციკლის შემდეგ.

## ტესტების ინსაიტები

Xcode იტყობინება ტესტების შედეგებს ერთი გაშვებით ერთდროულად. ის არ აგროვებს გაშვებებს შორის სიგნალს, რომელიც რეალურად გჭირდებათ: არასტაბილურობის მაჩვენებელი, კვირიდან კვირამდე ხანგრძლივობა, რომელი სიმულატორის ვარიანტები მარცხდება.

ტესტების ინსაიტები ავტომატურად იწერს ყოველი ტესტის შედეგს და ხანგრძლივობას გენერირებული სქემებისთვის და აკორელირებს შედეგებს გაშვებებს შორის. არასტაბილური ტესტები, ნელი ტესტები და შეცდომები ჩანსახავდება დაფის **ტესტები** ჩანართზე. როდესაც არასტაბილურობა გროვდება, გამოყავით ისინი კარანტინში დაფიდან, რათა შეწყვიტონ შერწყმების ბლოკირება.

## გუნდის ჩართვა

მოდულების ქეში და შერჩევითი ტესტირება ყველაზე მეტად მაშინ იძლევა შედეგს, როდესაც ყველა ერთსა და იმავე გაზიარებულ ზედაპირს ეხება. მიიწვიეთ თქვენი თანაგუნდელები ორგანიზაციაში დაფის ანგარიშის პარამეტრებიდან და დააყენეთ <.localized_link href="/guides/integrations/authentication/sso">ერთჯერადი შესვლა</.localized_link> (Google, Okta, Microsoft), რათა დარეგისტრირება იყოს ერთი დაწკაპუნება და არა თითოეული პირისთვის `tuist auth login`.
