# სერვერი {#server}

ჩვენ გთავაზობთ Tuist სერვერის საკუთარ ინფრასტრუქტურაზე განთავსების ვერსიას იმ ორგანიზაციებისთვის, რომლებსაც საჭიროებენ მეტ კონტროლს თავიანთ ინფრასტრუქტურაზე. ეს ვერსია საშუალებას გაძლევთ განათავსოთ Tuist თქვენს საკუთარ ინფრასტრუქტურაზე, რაც უზრუნველყოფს თქვენი მონაცემების უსაფრთხოებას და კონფიდენციალურობას.

> [!WARNING]
> **ლიცენზია სავალდებულოა**
>
> Tuist-ის საკუთარ ინფრასტრუქტურაზე განთავსება მოითხოვს იურიდიულად ძალის მქონე გადახდილ ლიცენზიას. Tuist-ის ადგილობრივი (on-premise) ვერსია ხელმისაწვდომია მხოლოდ Enterprise გეგმაზე მყოფი ორგანიზაციებისთვის. თუ დაინტერესებული ხართ ამ ვერსიით, გთხოვთ, დაუკავშირდეთ [contact@tuist.dev](mailto:contact@tuist.dev)-ს.

>
> არსებულ დეპლოიმენტებს შეუძლიათ კვლავ მიმართონ მოძველებულ წყაროს დოკუმენტაციას GitHub-ის markdown ვიუერში: [ქეშ-კვანძები](https://github.com/tuist/tuist/blob/main/server/priv/docs/en/guides/cache/self-host.md) და [ქეშის არქიტექტურა](https://github.com/tuist/tuist/blob/main/server/priv/docs/en/guides/cache/architecture.md).

## გამოშვების სიხშირე {#release-cadence}

Tuist სერვერი და Kura ქეშის სერვერი ნაწილდება GHCR სამი იმიჯის არხის მეშვეობით: **canary** (ყოველი კომიტი `main`-ზე), **გამოშვების კანდიდატი** (იჭრება ყოველ ორშაბათს, ერთი კვირის განმავლობაში მოწმდება) და **სტაბილური** (წინა ორშაბათს პრომოტირებული). მხოლოდ სტაბილური გამოშვებები გადააადგილებენ `:latest`-ს და ნაგულისხმევად იხსნებიან; canary და გამოშვების კანდიდატები არის GitHub-ის პრერელიზები, რომლებშიც ჩართვა ხდება მათი ტეგის მიმაგრებით. სერვერი და Kura ერთსა და იმავე ყოველკვირეულ ციკლს გადიან, სინქრონულად <.localized_link href="/cli/release/channels">Tuist CLI-ის გამოშვების გრაფიკთან</.localized_link>.

ჩვენ ვიცავთ [სემანტიკურ ვერსირებას](https://semver.org/) პროგნოზირებადი ვერსირებისა და თავსებადობის უზრუნველსაყოფად. მთავარი კომპონენტი გამოიყენება Tuist სერვერში იმ ცვლილებების აღსანიშნავად, რომლებიც საჭიროებს კოორდინაციას საკუთარ ინფრასტრუქტურაზე განთავსების მომხმარებლებთან; არ უნდა ელოდოთ, რომ ჩვენ მას გამოვიყენებთ, და თუ საჭირო გახდა, დარწმუნებული იყავით, რომ თქვენთან ერთად ვიმუშავებთ გადასვლის შესაბამისად გასამარტივებლად.

იხილეთ <.localized_link href="/guides/server/self-host/release/channels">გამოშვების არხები</.localized_link> გვერდი იმის გასაგებად, თუ როგორ იჭრება თითოეული არხი, როგორ მივაბათ ის თქვენს დეპლოიმენტში და რა არის რეკომენდებული სტრატეგია პროდაქშენის ნელი სტაბილური ხაზის შენარჩუნებისთვის, ხოლო სტეიჯინგის გარემო ამოწმებს მომავალ გამოშვებას.

## ბრაუზერის სესიის განახლება {#browser-session-upgrade}

ბრაუზერის სესიები იწურება შვიდი დღის შემდეგ, თუ არ არის ავთენტიფიცირებული გვერდის მოთხოვნები ან LiveView ურთიერთქმედება, და არა უგვიანეს 30 დღისა ავთენტიფიკაციის შემდეგ. „დამიმახსოვრე“ აღადგენს იმავე სერვერის მხარეს არსებულ სესიას და ვერ აგრძელებს ვადას. აქტივობა ფიქსირდება წუთში ერთხელ, ამიტომ უმოქმედო სესია შეიძლება ამოიწუროს 59 წამით ადრე. WebSocket გულისცემები, ავტომატური ხელახლა დაკავშირებები და ფონური განახლებები არ აახლებენ აქტივობას. ეს ვადები არ ცვლის მანქანის სერთიფიკატებს ან API-ტოკენების სიცოცხლის ხანგრძლივობას.

გაუშვით დამატებითი `users_tokens` მიგრაცია განახლებული აპლიკაციის პროცესების დაწყებამდე. არსებული ჩანაწერები არ ივსება უკან: მათი შექმნის დრო ზღუდავს უმოქმედობას და აბსოლუტურ ვადას, და მათ უნდა გაიარონ ახალი ავთენტიფიკაცია SSO-ით დაცული ორგანიზაციის წვდომამდე. callback-ის პროვაიდერი, გამომცემელი ან დადასტურებული Workspace, და მორგებული SSO კავშირი ინახება სერვერის მხარეს და შედარებულია ორგანიზაციის მიმდინარე პარამეტრებთან. დაკავშირებული ანგარიში არ არის სესიის ავთენტიფიკაციის დადასტურება.

განაახლეთ ყოველი მომსახურე ვებ-რეპლიკა, სანამ პოლიტიკას აღასრულებად ჩათვლით. ძველ ბინარებს შეუძლიათ კვლავ მიიღონ მათი ყოფილი 60-დღიანი სესიები და არ ასრულებენ ახალ LiveView საზღვარს; შერეული ვერსიები თავსებადია სქემის მიხედვით, მაგრამ არა პოლიტიკის მიხედვით. მოელით, რომ მომხმარებლებმა ხელახლა შეასრულონ შესვლა. ძველ ბინარებზე დაბრუნება ასუსტებს ამ კონტროლებს; თუ სქემის დაბრუნებაა საჭირო, შეაჩერეთ ყველა ბინარი, რომელიც კითხულობს ახალ ველებს, სანამ მათ წაშლით. არასდროს გაახანგრძლივოთ ძველი სესიები ან არ გამოიყვანოთ წყარო ხელახალი ავთენტიფიკაციის თავიდან ასაცილებლად.

## Authenticator-app MFA {#authenticator-app-mfa}

სერვერი მოიცავს ნატიურ authenticator-app (TOTP) ორფაქტორიან ავთენტიფიკაციას. დაშბორდი ჯერ არ აქვს ბმული მასზე; მომავალი გამოშვება დაამატებს პარამეტრების შესვლის წერტილს. არ საჭიროებს აქტივაციის ფლაგს, ჰოსტინგის სერვისის დამოკიდებულებას ან იდენტობის პროვაიდერის სერთიფიკატებს: მხოლოდ PostgreSQL, ქვემოთ მოცემული მიგრაცია, TOTP ავთენტიფიკატორი და სტაბილური დაშიფვრის გასაღები, რომელიც გაზიარებულია ყველა მომსახურე რეპლიკას შორის (`TUIST_SECRET_KEY_ENCRYPTION`, გადადის `TUIST_SECRET_KEY_BASE`-ზე). შეინარჩუნეთ სერვერისა და ავთენტიფიკატორის საათები სინქრონიზებული. MFA ვერიფიკაცია და მისი გაზიარებული ლიმიტი ხუთი წარუმატებელი კოდისა ხუთ წუთში იყენებს PostgreSQL-ის სტრიქონულ ბლოკირებებს, არა Redis-ს.

მოწყობა მოითხოვს შესვლას ბოლო ხუთი წუთის განმავლობაში, მოწყობის გასაღების შეყვანას TOTP ავთენტიფიკატორის აპში და აპის მიერ გენერირებული კოდის დადასტურებას. ათი ერთჯერადი აღდგენის კოდი ნაჩვენებია ერთხელ; შეინახეთ ისინი უსაფრთხოდ. ფაქტორის გათიშვა ასევე მოითხოვს ბოლოდროინდელ შესვლას და გამოუყენებელ ავთენტიფიკატორს ან აღდგენის კოდს. ფაქტორის ცვლილებები აუქმებს სხვა ბრაუზერის სესიებს. პაროლის აღდგენა არ აშორებს MFA-ს, და ეს იმპლემენტაცია არ უზრუნველყოფს მხოლოდ ელფოსტით ან ადმინისტრატორის გვერდის ავლას დაკარგული ფაქტორისთვის.

ერთხელ ჩართვის შემდეგ, ყოველი ახალი ბრაუზერის შესვლა — ფედერირებული შესვლის ჩათვლით — მოითხოვს ნატიურ მეორე ფაქტორს სესიის მიღებამდე ან ბრაუზერზე დაფუძნებული CLI/მოწყობილობის ავტორიზაციის დასრულებამდე. პირდაპირი პაროლით და Apple API შესვლა უარყოფს ჩართულ მომხმარებლებს და აძლევს მითითებას გამოიყენონ ბრაუზერის შესვლა. ახალი ელფოსტის აგენტის პრეტენზიები ჩართული მომხმარებლებისთვის მოითხოვს MFA-ით დადასტურებულ ბრაუზერის სესიას; მხოლოდ საფოსტო ყუთის ძველი პრეტენზიები უარყოფილია. არსებული API ტოკენები, მანქანის სერთიფიკატები, სამუშაო იდენტობები და მათი განახლების წესები უცვლელია. ეს არის სურვილისამებრ მომხმარებლის მხარდაჭერა, არა ორგანიზაციის მასშტაბით MFA-ის ბრძანება, ან იდენტობის პროვაიდერის საკუთარი MFA პოლიტიკის ვერიფიკაცია. ორგანიზაციის SSO კვლავ მოითხოვს სწორად კონფიგურირებულ პროვაიდერს/გამომცემელს ნატიურ ფაქტორთან ერთად.

ელფოსტა არ არის საჭირო ჩართვის, შესვლის, აღდგენის კოდის გამოყენების ან MFA-ის გათიშვისთვის. ფაქტორის ცვლილების შეტყობინებები საუკეთესო ძალისხმევით არის; მიწოდების შეცდომა არ აუქმებს დასრულებულ ცვლილებას.

გაუშვით ცალკეული დამატებითი `user_mfa`/`users_tokens.mfa_verified_at` მიგრაცია ახალი ბინარის წინ. TOTP საიდუმლო იყენებს არსებულ Vault დაშიფვრის გასაღებს; შეინახეთ ეს გასაღები და მისი სარეზერვო ასლები. დაასრულეთ **ყველა ავტორიზაციის მომსახურე რეპლიკის განახლება MFA ჩართვის ნებართვის მიცემამდე**. ძველმა ბინარებმა შეიძლება გვერდი აუარონ ნატიურ MFA-ს, ამიტომ ისინი არ არიან პოლიტიკასთან თავსებადი დაბრუნების სამიზნე ჩართვის შემდეგ. MFA სქემის წაშლა ანადგურებს ჩართვისა და აღდგენის მდგომარეობას; ჯერ შეაჩერეთ მკითხველები და შეინახეთ დაშიფრული სარეზერვო ასლი. შერეული ვერსიების სქემის თავსებადობა არ არის იმის მტკიცებულება, რომ MFA ან ბრაუზერის სესიის კონტროლი გამოიყენება.

## OAuth განახლებისა და დაბრუნების საზღვარი {#oauth-upgrade-and-rollback-boundary}

OAuth ობიექტების ქეშის წაშლა მოითხოვს ეტაპობრივ განახლებას არსებული ინსტალაციებისთვის. ვერსიის განთავსებამდე, რომელიც აჩერებს OAuth ქეშის გაუქმებებს, ჯერ განათავსეთ ავტორიტეტული წაკითხვის თავსებადობის რელიზი [#14040](https://github.com/tuist/tuist/pull/14040)-დან **ყველა OAuth მკითხველისა და მწერლისთვის**. ეს თავსებადობის ეტაპი პირველად ჩნდება **1.355** რელიზის ხაზში: `ghcr.io/tuist/tuist:1.355.0-rc.1` შეიცავს მას; პროდუქციის განთავსებებმა უნდა გამოიყენონ სტაბილური `1.355.x` რელიზი მისი წარმოჩენის შემდეგ. 1.354 ან უფრო ადრეულ ვერსიებზე ინსტალაციებმა უნდა დაასრულონ ეს ეტაპი მოგვიანებით რელიზზე გადასვლამდე, რომელიც შეიცავს წაშლას. შეინარჩუნეთ 1.355 ხაზი მხოლოდ თავსებადობისთვის: არ გადმოიტანოთ გაუქმების წაშლა მასში.

ორიგინალური თავსებადობის კომიტი ასევე ხელმისაწვდომია როგორც `ghcr.io/tuist/tuist:sha-c8e54471a425`. სხვა გამოსახულება შესაფერისია თავსებადობის ეტაპად მხოლოდ მაშინ, თუ ის ინარჩუნებს ავტორიტეტულ წაკითხვებს **და ინარჩუნებს ძველ გაუქმებებს**, სანამ ძველი მომხმარებლები დარჩებიან. გაუშვით ამ ეტაპის ჩვეულებრივი მონაცემთა ბაზის მიგრაციები ტრაფიკის მომსახურებამდე, რეფრეშ-ტოკენის ძებნის ინდექსის ჩათვლით.

შეამოწმეთ ყველა ვებ-რეპლიკა, ფონური მუშაკი, დაგეგმილი დავალებები და ცალკე მიმაგრებული პროცესორის გამოსახულებები თითოეულ გარემოში. დაელოდეთ თავსებადობის განლაგების დასრულებას და დარწმუნდით, რომ არ დარჩა ქეშის მკითხველი ბინარები გაუქმებების წაშლამდე. არ დაუშვათ, რომ მოტივტივე გამოსახულების თეგმა გამოტოვოს ეს ეტაპი ავტომატური განახლების დროს. ახალ ინსტალაციებს ძველი მომხმარებლების გარეშე არ სჭირდებათ შუალედური განთავსება.

> [!WARNING]
> **შეინარჩუნეთ ავტორიტეტული წაკითხვის დაბრუნების სამიზნე**
>
> გაუქმებების წაშლის შემდეგ, ჩვეულებრივმა მორევით დაბრუნებამ უნდა მიზნად ისახოს #14040 ან სხვა ავტორიტეტული წაკითხვის ვერსია. შენარჩუნებული OAuth ქეშის ჩანაწერები შეიძლება იყოს მოძველებული მაშინაც კი, როდესაც ყველა გაუქმების გარეშე პროცესი შეჩერდა, და გადატვირთულმა ქეშის მკითხველმა რეპლიკამ შეიძლება შემოიტანოს ისინი მეგობრებისგან.
>
> უფრო შორს დაბრუნება მოითხოვს **ყველა** გაუქმების გარეშე OAuth მომხმარებლის შეჩერებას და დაცლას, შემდეგ კი **ყოველი** შენარჩუნებული Boruta ქეშის მონაწილის გასუფთავებას ან შეცვლას ნებისმიერი ქეშის მკითხველი მომხმარებლის დაწყებამდე. ხელი შეუშალეთ შენარჩუნებულ მონაწილეებს ხელახლა შეერთებაში. მხოლოდ შესვლის დაცლა ან მხოლოდ ვებ-რეპლიკების გადატვირთვა არასაკმარისია; შეათანხმეთ ეს აღდგენა თქვენს Tuist მხარდაჭერის კონტაქტთან, ვიდრე ავტომატურად გაასუფთავოთ ქეშები ან დააბრუნოთ მონაცემთა ბაზის მიგრაციები.

## მრავალრეპლიკური კლასტერიზაცია {#multi-replica-clustering}

მხარდაჭერილი მრავალრეპლიკური ვებ განთავსებები მოითხოვს Erlang კლასტერიზაციას რეპლიკებს შორის Phoenix PubSub და Oban PG შეტყობინებებისთვის, არა როგორც ავტორიტეტს ავტორიზაციისთვის. დიაგრამა უარყოფს მრავალ რეპლიკას, ავტოსკალერის ჩათვლით, რომელსაც შეუძლია ერთ რეპლიკაზე მეტად გაიზარდოს, როდესაც `server.cluster.enabled` არის false. ადრე მიღებულმა არაკლასტერულმა განთავსებებმა უნდა დაგეგმონ ეს განახლება, ვიდრე გვერდი აუარონ დაცვას. დაასრულეთ <.localized_link href="/guides/server/self-host/server#oauth-upgrade-and-rollback-boundary">OAuth განახლების თანმიმდევრობა</.localized_link>, გაუქმების წაშლის ჩათვლით, წევრობის შეცვლამდე.

შექმენით პირადი cookie Secret გამოშვების სივრცეში თქვენი საიდუმლოების მენეჯერის გამოყენებით, შემდეგ კი დააკონფიგურირეთ მისი სახელი და გასაღები:

```yaml
server:
  replicaCount: 2
  cluster:
    enabled: true
    distributionPort: 9100
    cookieExistingSecret: tuist-server-cluster
    cookieExistingSecretKey: release-cookie
```

cookie უნდა იყოს მაღალი ენტროპიის და გაზიარებული ყველა მონაწილე ვებ-რეპლიკას შორის. არასოდეს გამოიყენოთ cookie, რომელიც ჩაშენებულია გამოქვეყნებულ გამოსახულებაში: განაწილების cookie-ის ფლობა იძლევა დისტანციურ შესრულებას მის კვანძებზე. განაწილებული გამოშვების დაწყება ახლა უარყოფს დაკარგულ პირად `RELEASE_COOKIE`-ს ან არასწორ პორტს, ცალსახად კონფიგურირებული `RELEASE_DISTRIBUTION=name`-ის ან `sname`-ის ჩათვლით DNS აღმოჩენის გარეშე. არადიაგრამულმა განთავსებებმა ასევე უნდა დააკონფიგურირონ `TUIST_CLUSTER_DNS_SERVICE`, `TUIST_CLUSTER_APP_NAME` და pod IP/კვანძის სახელი თანმიმდევრულად. აღმოჩენა ამჟამად იყენებს IPv4 A ჩანაწერებს.

ჩვეულებრივი სერვერთან დაკავშირებული `helm upgrade`-ით, `cookieExistingSecret`-ის ცარიელად დატოვება ქმნის cookie Secret-ს და ხელახლა იყენებს მის მიმდინარე მნიშვნელობას მოგვიანებით განახლებებზე. ოფლაინ `helm template`, Argo CD და სხვა GitOps რენდერერები ცოცხალი Secret ძებნის გარეშე ვერ შეინარჩუნებენ იმ გენერირებულ მნიშვნელობას; მათ უნდა გამოიყენონ `cookieExistingSecret`, რომელიც ეყრდნობა ცალკე მართულ, სტაბილურ Secret-ს. არ შეცვალოთ cookie გასაღები კლასტერის იმპლიციტურად როტაციისთვის. Cookie როტაცია მოითხოვს ყველა მონაწილის კოორდინირებულ მიგრაციას/გადატვირთვას; მხოლოდ Secret-ის განახლება არ ანახლებს არსებულ პროცესებს.

პირველი განლაგება გამოსახულებაში ჩაშენებული cookie-ებიდან ქმნის ცალკეულ ძველ/ახალ წევრობის კუნძულებს, სანამ ყველა ვებ-რეპლიკა არ გამოიყენებს პირად Secret-ს. დაგეგმეთ მიგრაციის ფანჯარა რეალური დროის განახლებებისთვის. მომდევნო მორევითი განთავსებები ქმნიან შერეული ვერსიების კლასტერებს, ამიტომ შეაფასეთ PubSub, Oban შეტყობინებები და მეგობრის შეცვლა ფაქტობრივ ძველ/ახალ ვერსიებში. ეს შეტყობინებები არ არის მდგრადი მიწოდების გარანტიები. შეინარჩუნეთ ავტორიტეტული წაკითხვის დაბრუნების გამოსახულება და შეინარჩუნეთ იგივე პირადი cookie თავსებადი ვერსიის დაბრუნებისას.

EPMD (TCP 4369) და კონფიგურირებული განაწილების პორტი დაუშვით მხოლოდ სანდო სერვერის მეგობრებს შორის, არასოდეს არენდატორის სამუშაო დატვირთვებიდან ან საჯარო ქსელიდან. შეამოწმეთ ფაქტობრივი შესვლის/გასვლის იზოლაცია თქვენს გარემოში; NetworkPolicy-ის რენდერინგი არ ამტკიცებს გამოყენებას ან backend-ის ხელმისაწვდომობას. ორრეპლიკიანი კანარეულმა მუდმივი დატვირთვის ქვეშ უნდა გაიაროს შეერთება, მორევითი შეცვლა და შეცდომა/აღდგენა წარმოჩენამდე. DNS გამოიყენება მეგობრების აღმოჩენისთვის, არა ჯანსაღი კვანძების გათიშვისთვის დროებითი შეცდომის ან ნაწილობრივი პასუხის გამო; რეალური კვანძის დაკარგვა და OTP პარტიციის პრევენცია კვლავ მოქმედებს. libcluster-მა შეიძლება კვლავ ჩაწეროს წარმატებული "გათიშვის" ოპერაცია შენარჩუნების callback-ისთვის კავშირის დახურვის გარეშე; დაადგინეთ ფაქტობრივი წევრობა კვანძის აწევ/ჩამოწევ მოვლენებიდან ან `Node.list()`-დან, არა მხოლოდ იმ ლოგის ხაზიდან.

## უწყვეტი განთავსება {#continuous-deployment}

## ქსელში სანდო წვდომა {#network-trusted-access}

თვითმასპინძელი ინსტალაციები სანდო ქსელში მყოფ დეველოპერებს საშუალებას აძლევს, წარმოადგინონ ინსაიტები, გამოიყენონ ქეში ან ორივე შესაძლებლობა ავტორიზაციის გარეშე. დაფა და ადმინისტრირება კვლავ მოითხოვს ავტორიზაციას.

ჩართეთ მხოლოდ ის შესაძლებლობები, რომლებიც გჭირდებათ:

| სერვერის გარემოს ცვლადი | საშუალებას იძლევა ავტორიზაციის გარეშე |
| --- | --- |
| `TUIST_NETWORK_TRUSTED_INSIGHTS_ACCESS=true` | ბილდისა და ტესტების ინსაიტების წარდგენა |
| `TUIST_NETWORK_TRUSTED_CACHE_ACCESS=true` | ქეშირებული ბილდის შედეგების წაკითხვა და ჩაწერა |

ორივე პარამეტრი **გამორთულია ნაგულისხმევად**, დამოუკიდებელია და ვრცელდება ეგზემპლარის მასშტაბით ყველა ანგარიშსა და პროექტზე, მათ შორის კერძო პროექტებზე. ისინი ხელმიუწვდომელია Tuist-ის ჰოსტინგულ ვერსიაში და არ ცვლის თვითმასპინძლობის ლიცენზიას.

წინა სახელი `TUIST_NETWORK_TRUSTED_REPORT_PUBLISHING` რჩება თავსებადობის სათადარიგოდ, როცა `TUIST_NETWORK_TRUSTED_INSIGHTS_ACCESS` არ არის დაყენებული.

> [!WARNING]
> ეს პარამეტრები ჩართეთ მხოლოდ იძულებითი ოფისის ქსელის ან VPN საზღვრის შიგნით. ნებისმიერს, ვისაც შეუძლია ჩართული ენდპოინტის მიღწევა, შეუძლია წარადგინოს ანგარიშები ან, ქეშზე წვდომის ჩართვის შემთხვევაში, წაიკითხოს და გადაწეროს ქეშირებული შედეგები. ეს საშუალებას იძლევა გაყალბებული ტელემეტრიის, ქეშის მოწამვლისა და სიმძლავრის ამოწურვის. ანგარიშგების პასუხებმა ასევე შეიძლება გაამჟავნოს კერძო პროექტების სახელები და ბილდის სისტემები. Tuist არ ამოწმებს VPN-ის წევრობას და არ ენდობა გადამისამართებულ IP სათაურებს წევრობის დასტურად.

### ეგზემპლარის კონფიგურაცია {#network-trusted-instance-configuration}

1. შეზღუდეთ Tuist სერვერი, ყველა Kura HTTP/gRPC მსმენელი და ნებისმიერი Bazel BES შესვლა თქვენს სანდო ქსელში სახანძრო კედლის ან კერძო ingress-ის გამოყენებით.
2. კლიენტების განახლებამდე განაახლეთ ყველა სერვერისა და Kura რეპლიკა. დატოვეთ Kura ავტორიზაცია ჩართული `KURA_AUTH_TUIST_URL`-ით და მისი control-plane სერთიფიკატებით; მისი გამორთვა არღვევს ამ შეზღუდვებს. დააკონფიგურირეთ თქვენი ქეშის ენდპოინტი <.localized_link href="/guides/features/cache/self-hosting">თვითმასპინძელი ქეშის სახელმძღვანელოს</.localized_link> მიხედვით.
3. დააყენეთ ზემოთ აღნიშნული სასურველი ცვლადები ყველა შესაბამის Tuist სერვერის რეპლიკაზე, შემდეგ გადატვირთეთ ან ხელახლა განათავსეთ ისინი. პარამეტრს რთავს მხოლოდ ზუსტი მნიშვნელობა `true`. არ არსებობს დაფის გადამრთველი ან ცალკე Kura ფლაგი.

### კლიენტების კონფიგურაცია {#network-trusted-client-configuration}

დააკონფიგურირეთ საბოლოო თვითმასპინძელი სერვერის URL და პროექტი თითოეულ თავსებად კლიენტზე. კლიენტები ავტომატურად აღმოაჩენენ, რომელი შესაძლებლობებია ჩართული, როცა სერთიფიკატები არ არის; კლიენტის ცალკე ჩართვა არ არის საჭირო. აღმოჩენა არ მიჰყვება გადამისამართებებს. არსებული სერთიფიკატები რჩება გამოყენებაში, ხოლო არასწორი ან განახლების შეცდომის მქონე სერთიფიკატები იწვევს შეცდომას ანონიმური სათადარიგოს ნაცვლად. აღდგენისთვის ხელახლა შედით ან ცალსახად გამოდით.

ინსაიტებზე წვდომის ჩართვამდე, განაახლეთ სერთიფიკატების გამზიარებელი ყველა ინსტრუმენტი ისეთ ვერსიებამდე, რომლებიც ინარჩუნებენ დაზიანებულ ან უარყოფილ სერთიფიკატებს, უარყოფენ წაუკითხავ სერთიფიკატების დირექტორიებს და გამორიცხავენ Git წყაროებს ხელმოუწერელი ანგარიშებიდან. ძველ ინსტრუმენტებს შეუძლიათ სერთიფიკატების წაშლა და ანონიმურ სათადარიგოზე გადასვლის შეუნიშნავად დაშვება; მხოლოდ სერვერის განახლება ამას ვერ გამოასწორებს. თუ სერვერს არ აქვს აღმოჩენის მხარდაჭერა ან დაბრუნებულია ძველ ვერსიაზე, კლიენტებმა უნდა გაიარონ ავტორიზაცია. ყოფილი კლიენტის პარამეტრი `TUIST_NETWORK_TRUSTED_PUBLISHING` აღარ მოქმედებს.

- **ინსაიტები:** წარადგინეთ მხოლოდ დასრულებული Xcode, Gradle, Elixir/Mix და Bazel ანგარიშები, არქივის, დანართის, დაფარვის, shard-გეგმარების ან არსებული ანგარიშის წვდომის გარეშე. მოქმედის მოთხოვნები არ არის ვერიფიცირებული; ხელმოუწერელი ტელემეტრია არ ქმნის სანდო ტესტის მტკიცებულებას ან ავტომატიზაციას. კლიენტის დაყენებისა და კონფიდენციალურობის დეტალებისთვის იხილეთ <.localized_link href="/guides/features/build-insights/xcode#network-trusted-publishing">Xcode</.localized_link>, <.localized_link href="/guides/features/build-insights/gradle#network-trusted-publishing">Gradle</.localized_link> და <.localized_link href="/guides/features/build-insights/elixir#network-trusted-publishing">Elixir</.localized_link> სახელმძღვანელოები.
- **ქეში:** მხარდაჭერილია CLI კომპილაციის/მოდულის ქეშირება, Bazel ქეშირება და Gradle task-ების ქეშირება. ქეშის გაწმენდა და Remote Asset-ების ჩამოტვირთვა კვლავ მოითხოვს სერთიფიკატებს. მხარდაჭერის გარეშე კლიენტებმა უნდა გააგრძელონ ავტორიზაცია.
- **Bazel:** ანგარიშგება მოითხოვს ცალსახა `TUIST_BAZEL_BES_BACKEND` და თავსებად Kura-ს. ქეშისა და ანგარიშგების პარამეტრები ჩართულია დამოუკიდებლად. სერთიფიკატების ან რომელიმე პარამეტრის შეცვლის შემდეგ ხელახლა გაუშვით `tuist bazel setup`; კომპილაციის ქეშის კონფიგურაციის ცვლილებებისთვის ხელახლა გაუშვით `tuist cache config`.

ანგარიშის მოთხოვნები შეზღუდულია 8 MB-ით, 60 მოთხოვნით წუთში და 10,000-ით დღეში თითო პროექტზე. რამდენიმე რეპლიკის მქონე განთავსების მასშტაბის კვოტებისთვის დააკონფიგურირეთ გაზიარებული Valkey; წინააღმდეგ შემთხვევაში ლიმიტები მოქმედებს პროცესის მიხედვით. თუ კონფიგურირებული გაზიარებული კვოტის backend ხელმიუწვდომელია, ხელმოუწერელი ანგარიშგება უარყოფილი იქნება. დაამატეთ ingress კავშირის, სხეულისა და სიჩქარის ლიმიტებიც.

### ქსელში სანდო წვდომის გამორთვა {#disable-network-trusted-publishing}

შესაბამისი ცვლადი დააყენეთ `false`-ზე, შემდეგ გადატვირთეთ **ყველა შესაბამისი სერვერის რეპლიკა**. ძველ რეპლიკებს შეუძლიათ სერთიფიკატების გარეშე მოთხოვნების მიღება შეცვლამდე. ქეშზე წვდომა ახალი მოთხოვნებისთვის ჩერდება ბოლო რეპლიკის გადართვიდან 60 წამის განმავლობაში; მიმდინარე გადაცემები არ ჩერდება. დაუყოვნებელი გაუქმების საჭიროების შემთხვევაში ჯერ შეზღუდეთ ტრაფიკი ingress-ზე. არსებული ანგარიშები ინარჩუნებენ ჩვეულებრივ ხილვადობასა და შენარჩუნებას, ხოლო ავტორიზებული კლიენტები განაგრძობენ მუშაობას.

### Docker-ვირტუალიზებული ასლების გაშვება {#running-dockervirtualized-images}

ჩვენ ვავრცელებთ სერვერს [Docker](https://www.docker.com/) ასლის სახით [GitHub-ის Container Registry](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry)-ის მეშვეობით.

მის გასაშვებად, თქვენმა ინფრასტრუქტურამ უნდა მხარდაუჭიროს Docker ასლების გაშვება. გაითვალისწინეთ, რომ ინფრასტრუქტურის უმეტესი პროვაიდერი მხარს უჭერს მას, რადგან ის გახდა სტანდარტული კონტეინერი პროდაქშენ გარემოში პროგრამული უზრუნველყოფის გასავრცელებლად და გასაშვებად.

### Postgres მონაცემთა ბაზა {#postgres-database}

Docker ასლების გაშვების გარდა, დაგჭირდებათ [Postgres მონაცემთა ბაზა](https://www.postgresql.org/) რელაციური მონაცემების შესანახად. ინფრასტრუქტურის უმეტესი პროვაიდერი Postgres მონაცემთა ბაზებს შეიცავს თავის შეთავაზებაში (მაგ., [AWS](https://aws.amazon.com/rds/postgresql/) & [Google Cloud](https://cloud.google.com/sql/docs/postgres)).

> [!NOTE]
> **მიგრაციები**
>
> Docker ასლის entrypoint ავტომატურად ასრულებს ყველა მოლოდინში მყოფ სქემის მიგრაციას სერვისის გაშვებამდე.


### ClickHouse მონაცემთა ბაზა {#clickhouse-database}

Tuist იყენებს [ClickHouse](https://clickhouse.com/)-ს დიდი რაოდენობით ანალიტიკური მონაცემების შესანახად და მოსაძებნად. ClickHouse **აუცილებელია** ისეთი ფუნქციებისთვის, როგორიცაა ბილდის ინსაიტები. შეგიძლიათ აირჩიოთ, თვითონ ჰოსტინგზე განათავსოთ ClickHouse თუ გამოიყენოთ მათი ჰოსტინგული სერვისი.

> [!NOTE]
> **მიგრაციები**
>
> Docker ასლის entrypoint ავტომატურად ასრულებს ყველა მოლოდინში მყოფ ClickHouse სქემის მიგრაციას სერვისის გაშვებამდე.

შეკვრაში ჩართული Docker Compose და Helm-ის ჩაშენებული ClickHouse კონფიგურაციები ამცირებენ ClickHouse ტექსტური ლოგის დონეს ასლის `trace` ნაგულისხმევიდან `information`-მდე, საიდანაც მოდის `system.text_log` მოცულობის უმეტესი ნაწილი. ორივე ასევე შეუძლია შემოაფაროს ზღვარი ClickHouse-ის საკუთარ `system.*` ოპერაციულ ლოგის ცხრილებს, რომლებიც წინააღმდეგ შემთხვევაში შეუზღუდავია, მაგრამ ეს ნაგულისხმევად გამორთულია — იხილეთ ქვემოთ. გარე ClickHouse განლაგებებმა უნდა კონფიგურირონ ეს ოპერაციული ლოგები პირდაპირ თავიანთ ClickHouse სერვისში.

#### ClickHouse რეპლიკაციის ტოპოლოგია {#clickhouse-replication-topology}

Tuist-ის უკან მრავალრეპლიკიანი ClickHouse მხარდაჭერილია მხოლოდ ClickHouse Cloud-ზე. თვითმართვადი ClickHouse არის ერთრეპლიკიანი.

შემომავალი მონაცემების მიგრაციები ქმნიან ჩვეულებრივ `MergeTree` ძრავას. Cloud-ზე ეს გამჭვირვალედ ხდება `SharedMergeTree`-დ, ამიტომ ჩაწერები ხდება გაზიარებულ ობიექტურ საცავში და ნებისმიერი რეპლიკების რაოდენობა მუშაობს. თვითმართვად ClickHouse-ზე, `MergeTree` წერს ლოკალურ დისკზე მხოლოდ ერთ რეპლიკაზე; მრავალრეპლიკიანი კონფიგურაცია ან უხმოდ გაყოფს შემომავალ მონაცემებს რეპლიკებს შორის, ან უარყოფს CREATE-ს `UNKNOWN_STORAGE: Only tables with a Replicated engine or tables which do not store data on disk are allowed in a Replicated database.`-ით, იმის მიხედვით, თუ როგორ არის `database_replicated_allow_only_replicated_engine` დაყენებული შემერთებულ მომხმარებელზე.

გაუშვით ერთი შარდი ერთი რეპლიკით თვითმართვად ClickHouse-ზე და რეგულარულად შექმენით ClickHouse მონაცემთა დირექტორიის სარეზერვო ასლები. კვანძის დაკარგვის შემთხვევაში არ არსებობს მეორე რეპლიკა, რომელზეც გადასვლა შეიძლება.

#### ოპერაციული ლოგის შენახვის ვადის შეზღუდვა {#capping-operational-log-retention}

შენახვის ვადა შეიძლება გამოყენებულ იქნას `system.text_log`, `system.query_log`, `system.query_thread_log`, `system.query_views_log`, `system.trace_log`, `system.metric_log`, `system.asynchronous_metric_log` და `system.part_log`-ზე.

მისი ჩართვა არის ერთჯერადი, ერთმხრივი ნაბიჯი ეგზემპლარზე, რომელსაც უკვე აქვს მონაცემები, რის გამოც არცერთი შეკვრა არ აკეთებს ამას თქვენთვის. ნებისმიერი შენახვის ფანჯარა იწვევს იმას, რომ ეს ცხრილების განსაზღვრებები აღარ ემთხვევა მათ კონფიგურაციას, ამიტომ ClickHouse თითოეულს გადაარქმევს სახელს და ქმნის ახალ ცხრილს, როგორც აღწერილია [ჩანაცვლებული ლოგის ცხრილები](#superseded-log-tables) ქვეშ. დარჩენილი გენერაცია ინახავს ყველაფერს, რაც ამ დრომდე დაგროვდა და არ აქვს საკუთარი შენახვის ვადა, ამიტომ თუ არ დაიბრუნებთ მას იმავე ნაბიჯში, ის დისკზე სამუდამოდ დარჩება და ახალი ფანჯარა მხოლოდ იმ სტრიქონებს შეზღუდავს, რომლებიც მაშინ დაიწერება. ჩართეთ ორივე ერთად:

```yaml
clickhouse:
  embedded:
    systemLogs:
      ttlDays: 14
      supersededTables: delete
```

ეს ერთი `helm upgrade` არის თვითშემცველი, რადგან `ttlDays`-ის ცარიელიდან დაყენებულ მდგომარეობაში გადაყვანა ამატებს drop-in mount-ს და ახდენს ClickHouse pod-ის გადატვირთვას: ის იწყება თავიდან, ანაცვლებს ცხრილებს და განახლების შემდგომი Job შემდეგ შლის მათ. განათავსეთ `helm upgrade --wait`-ით, რათა pod გადაიტვირთოს Job-ის გაშვებამდე; წინააღმდეგ შემთხვევაში, გენერაციები გამოჩნდება მისი შემოწმების შემდეგ და შემდეგი `helm upgrade` დაიბრუნებს მათ.

Docker Compose-ით, გააკომენტარეთ `clickhouse-log-ttl.xml` ტომი `clickhouse` სერვისზე `docker-compose.yml`-ში და დააყენეთ ორივე ცვლადი `.env`-ში:

```bash
CLICKHOUSE_SYSTEM_LOG_TTL_DAYS=14
CLICKHOUSE_SUPERSEDED_LOG_TABLES=delete
```

სივრცის დაბრუნების შემდეგ შეგიძლიათ `supersededTables`/`CLICKHOUSE_SUPERSEDED_LOG_TABLES` დააბრუნოთ `ignore`-ზე, რათა მოგვიანებით ClickHouse-ის განახლებამ არ წაშალოს ისტორია.

#### ჩანაცვლებული ლოგის ცხრილები {#superseded-log-tables}

ClickHouse გაშვებისას ამოწმებს, ემთხვევა თუ არა თითოეული სისტემური ლოგის ცხრილი თავის კონფიგურაციას. როცა არ ემთხვევა, ის არსებულ ცხრილს გადაარქმევს სახელს `system.<name>_0`-დ, შემდეგ `_1`-დ, `_2`-დ და ასე შემდეგ, და ქმნის ახალს. ეს ხდება შენახვის ფანჯრის შეცვლისას და ნებისმიერ ClickHouse განახლებაზე, რომელიც ცვლის სისტემური ლოგის სქემას.

ცხრილის სახელის შეცვლა არ აკოპირებს მის მონაცემებს, ამიტომ ეს არ მოიხმარს დამატებით დისკის სივრცეს. რა ხდება ჩანაცვლებულ ცხრილთან შემდეგ, დამოკიდებულია იმ ცხრილზე, საიდანაც მოვიდა, რადგან ის ინარჩუნებს იმ შენახვის ვადას, რაც ცოცხალ ცხრილს ჰქონდა ჩანაცვლების მომენტში. პირველად, როცა ჩართავთ შენახვის ვადას, ჩანაცვლებულ ცხრილს არ აქვს ის, ამიტომ ის ინახავს ყველა დაგროვილ ისტორიას და ინარჩუნებს მას უვადოდ. ფანჯრის მოგვიანებითი ცვლილება ანაცვლებს ცხრილს, რომელსაც უკვე აქვს TTL, ამიტომ ისინი თავისთავად იწურება და ტოვებენ ცარიელ ცხრილს. ClickHouse არასდროს შლის თავად ცხრილებს, ამიტომ ხანგრძლივად მოქმედ ეგზემპლარზე ისინი ნებისმიერ შემთხვევაში გროვდება.

ჩანაცვლებული ცხრილები ნაგულისხმევად ინახება, რათა განახლებამ არასდროს წაშალოს ოპერაციული ისტორია. დააყენეთ პოლიტიკა `delete`-ზე, რათა წაშალოთ ისინი, რაც ხდება `docker compose up`-ზე და ყოველ `helm upgrade`-ზე:

```bash
CLICKHOUSE_SUPERSEDED_LOG_TABLES=delete
```

Helm chart-ით, კონფიგურირეთ იგივე პოლიტიკა მნიშვნელობად:

```yaml
clickhouse:
  embedded:
    systemLogs:
      supersededTables: delete
```

ჩანაცვლებული ცხრილის წაშლა აბრუნებს მის დისკის სივრცეს. ცოცხალ ცხრილს არასდროს ეხება და არც იმ სტრიქონებს, რომლებიც ჩაიწერა მისი ჩანაცვლების შემდეგ.

სივრცის ერთხელ დასაბრუნებლად პოლიტიკის შეცვლის გარეშე, წაშალეთ ცხრილები ხელით:

```sql
SELECT name FROM system.tables WHERE database = 'system' AND match(name, '_log_[0-9]+$');
DROP TABLE IF EXISTS system.text_log_0 SYNC;
```

`system` მონაცემთა ბაზა იყენებს `Atomic` ძრავას, რომელიც აგვიანებს ჩვეულებრივ `DROP TABLE`-ს `database_atomic_delay_before_drop_table_sec`-ით (ნაგულისხმევად რვა წუთი). `SYNC` შლის მონაცემებს მაშინვე, რაც გჭირდებათ, როცა შლით მათ დისკის სივრცის ამოწურვის გამო.


### საცავი {#storage}

ასევე დაგჭირდებათ ფაილების შესანახი გადაწყვეტა (მაგ., ფრეიმვორკებისა და ბიბლიოთეკების ბინარები). Tuist სერვერი მხარს უჭერს S3-თან თავსებად საცავს და Azure Blob Storage-ს სერვერის საკუთრებაში არსებული არტეფაქტებისთვის.

> [!TIP]
> **ოპტიმიზირებული ქეშირება**
>
> თუ თქვენი მიზანი ძირითადად ქეშის ლატენტობის შემცირებაა, შესაძლოა არ დაგჭირდეთ მთელი სერვერის თვითჰოსტინგი. შეგიძლიათ განათავსოთ თვითჰოსტინგული Kura კვანძები თქვენს CI ან დეველოპერულ ქსელთან ახლოს და დააკავშიროთ ისინი ჰოსტინგულ Tuist სერვერთან ან თქვენს თვითჰოსტინგულ სერვერთან.
>
> იხილეთ <.localized_link href="/guides/cache/self-host">თვითჰოსტინგული ქეშის სახელმძღვანელო</.localized_link>.


### თვითჰოსტინგული Kura კვანძები {#self-hosted-cache-nodes}

თვითჰოსტინგული Kura კვანძების გამოყენებისთვის თვითჰოსტინგულ Tuist სერვერთან:

1. კონფიგურირეთ `KURA_CONTROL_PLANE_CLIENT_ID` და `KURA_CONTROL_PLANE_CLIENT_SECRET` Tuist სერვერზე. კლიენტის ID **უნდა იყოს UUID**. შექმენით UUID და შემთხვევითი საიდუმლო <.localized_link href="/guides/cache/self-host#control-plane-client">თვითჰოსტინგული ქეშის სახელმძღვანელოში</.localized_link> მოცემული ბრძანებებით და შეინახეთ ისინი თქვენს განლაგების საიდუმლოებში.
2. განათავსეთ Kura კვანძები <.localized_link href="/guides/cache/self-host">თვითჰოსტინგული ქეშის სახელმძღვანელოს</.localized_link> მიხედვით, იგივე საკონტროლო-სიბრტყის სერთიფიკატის გამოყენებით.
3. კონფიგურირეთ თითოეული Kura კვანძი `KURA_REGISTRATION_URL`-ით და `KURA_ADVERTISED_HTTP_URL`-ით. რეგისტრაციის heartbeat-ები ეუბნება სერვერს, რომელი მზა, კლიენტისთვის ხელმისაწვდომი Kura endpoint-ები შეუძლია CLI-სთვის რეკლამირება.

## კონფიგურაცია {#configuration}

სერვისის კონფიგურაცია ხდება გარემოს ცვლადების მეშვეობით შესრულების დროს. ამ ცვლადების მგრძნობიარე ბუნებიდან გამომდინარე, გირჩევთ მათ დაშიფვრას და უსაფრთხო პაროლის მენეჯმენტის გადაწყვეტილებებში შენახვას. იყავით მშვიდად, Tuist უკიდურესი სიფრთხილით ეპყრობა ამ ცვლადებს და უზრუნველყოფს, რომ ისინი არასდროს გამოჩნდეს ლოგებში.

| `TUIST_CLICKHOUSE_FLUSH_INTERVAL_MS` | დროის ინტერვალი მილიწამებში ClickHouse ბუფერის გასუფთავებებს შორის | არა | `5000` | `5000` |
| `TUIST_CLICKHOUSE_MAX_BUFFER_SIZE` | ClickHouse ბუფერის მაქსიმალური ზომა ბაიტებში გასუფთავების იძულებამდე | არა | `1000000` | `1000000` |
| `TUIST_CLICKHOUSE_BUFFER_POOL_SIZE` | გასაშვები ClickHouse ბუფერის პროცესების რაოდენობა | არა | `5` | `5` |

ნაგულისხმევად, Tuist აშიფრავს მონაცემთა ბაზასთან კავშირს, მაგრამ არ ამოწმებს სერვერის სერტიფიკატს, ამიტომ ქსელში თავდამსხმელს შეუძლია წარმოადგინოს თავი მონაცემთა ბაზად. დააყენეთ `TUIST_DATABASE_SSL_VERIFY=1` მისი შესამოწმებლად. თუ თქვენი პროვაიდერი ხელს აწერს სერტიფიკატებს საკუთარი CA-თი, როგორც Amazon RDS და Google Cloud SQL აკეთებენ, ჩამოტვირთეთ მისი CA პაკეტი, დაამაგრეთ ის კონტეინერში და მიუთითეთ `TUIST_DATABASE_SSL_CA_CERT_FILE` მასზე. ჰოსტი `DATABASE_URL`-ში უნდა ემთხვეოდეს სახელს ან IP მისამართს სერტიფიკატში. ვერიფიკაციის ჩართვისას, სერტიფიკატი, რომელიც ვერ აკმაყოფილებს ამ შემოწმებებს, გამოიწვევს ყველა მონაცემთა ბაზასთან კავშირის შეცდომას, ამიტომ ჩართვის შემდეგ შეამოწმეთ სერვერის ლოგები `Bad Certificate` ან `Unknown CA` შეცდომებზე.

როცა `TUIST_DATABASE_SCHEMA` არ არის `public`, რელიზის მიგრაციები ქმნიან სქემას, თუ ის ჯერ არ არსებობს, Ecto მიგრაციების ჯაჭვის გაშვებამდე. თუ მიგრაციის როლს არ შეუძლია სქემების შექმნა, წინასწარ შექმენით სქემა და გახადეთ მიგრაციის როლი მის owner-ად.

Tuist მიმართავს კავშირს მითითებულ სქემაზე სესიის `search_path`-ის დაყენებით. ზოგიერთი პულირებული ან პროქსირებული Postgres კონფიგურაცია (მაგალითად PgBouncer, ან მართული მონაცემთა ბაზები, რომლებიც ზღუდავენ გაშვების პარამეტრებს) არ ავრცელებენ ამას და სესია ბრუნდება `public`-ზე, რაც მიგრაციების დროს ვლინდება როგორც `permission denied for schema public`. ასეთ კონფიგურაციაზე შეერთებისას, მიამაგრეთ სქემა უშუალოდ როლზე, რათა ყოველი სესია მასში დაიწყოს პროქსის მიუხედავად:

```sql
CREATE SCHEMA IF NOT EXISTS tuist AUTHORIZATION <migration_role>;
ALTER ROLE <migration_role> IN DATABASE <database> SET search_path = tuist;
-- If the web server connects as a separate runtime role (TUIST_DATABASE_RUNTIME_ROLE):
ALTER ROLE <runtime_role> IN DATABASE <database> SET search_path = tuist;
```

### ავთენტიფიკაციის გარემოს კონფიგურაცია {#authentication-environment-configuration}

ჩვენ ვუწყობთ ხელს ავთენტიფიკაციას [იდენტობის პროვაიდერების (IdP)](https://en.wikipedia.org/wiki/Identity_provider) მეშვეობით. ამის გამოსაყენებლად, დარწმუნდით, რომ არჩეული პროვაიდერისთვის საჭირო ყველა გარემოს ცვლადი არსებობს სერვერის გარემოში. **გამოტოვებული ცვლადები** გამოიწვევს Tuist-ის მიერ ამ პროვაიდერის გამოტოვებას.

#### ელფოსტა და პაროლი {#email-and-password}

ელფოსტით და პაროლით შესვლა და თვითმომსახურე რეგისტრაცია ჩაშენებულია და ნაგულისხმევად ჩართულია. იმ ეგზემპლარზე, სადაც გსურთ მოითხოვოთ იდენტობის პროვაიდერი (მაგალითად, SSO-ის იძულებისას), შეგიძლიათ სრულად გამორთოთ ისინი. ეს აშორებს ელფოსტა/პაროლის ფორმას, რეგისტრაციის ბმულს და პაროლის აღდგენის პროცესს შესვლის ინტერფეისიდან და კეტავს ყველა შესაბამის სერვერის მხარის endpoint-ს, მათ შორის ელფოსტა/პაროლის endpoint-ს, რომელსაც CLI იყენებს (`tuist auth`).

#### GitHub {#github}

ჩვენ გირჩევთ ავტორიზაციას [GitHub App](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/about-creating-github-apps)-ის გამოყენებით, მაგრამ ასევე შეგიძლიათ გამოიყენოთ [OAuth App](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/creating-an-oauth-app). დარწმუნდით, რომ სერვერის გარემოში ჩართულია GitHub-ის მიერ მითითებული ყველა აუცილებელი გარემოს ცვლადი. ცვლადების არარსებობა გამოიწვევს იმას, რომ Tuist უგულებელყოფს GitHub ავტორიზაციას. GitHub აპლიკაციის სწორად დასაყენებლად:
- GitHub აპლიკაციის ზოგად პარამეტრებში:
    - დააკოპირეთ `Client ID` და დააყენეთ როგორც `TUIST_GITHUB_APP_CLIENT_ID`
    - შექმენით და დააკოპირეთ ახალი `client secret` და დააყენეთ როგორც `TUIST_GITHUB_APP_CLIENT_SECRET`
    - დააყენეთ `Callback URL` როგორც `http://YOUR_APP_URL/users/auth/github/callback`. `YOUR_APP_URL` ასევე შეიძლება იყოს თქვენი სერვერის IP მისამართი.
- მოცემული ნებართვებია საჭირო:
  - რეპოზიტორიები:
    - Pull requests: წაკითხვა და ჩაწერა
  - ანგარიშები:
    - ელფოსტის მისამართები: მხოლოდ წაკითხვა

`Permissions and events`-ის `Account permissions` განყოფილებაში, დააყენეთ `Email addresses` ნებართვა `Read-only`-ზე.

შემდეგ დაგჭირდებათ შემდეგი გარემოს ცვლადების გამოტანა იმ გარემოში, სადაც Tuist სერვერი მუშაობს:

| გარემოს ცვლადი | აღწერა | აუცილებელია | ნაგულისხმევი | მაგალითი |
| --- | --- | --- | --- | --- |
| `TUIST_GITHUB_APP_CLIENT_ID` | GitHub აპლიკაციის Client ID | დიახ | | `Iv1.a629723000043722` |
| `TUIST_GITHUB_APP_CLIENT_SECRET` | აპლიკაციის Client Secret | დიახ | | `232f972951033b89799b0fd24566a04d83f44ccc` |
| `TUIST_GITHUB_AUTH_ENABLED` | შეიძლება თუ არა GitHub-ის გამოყენება შესასვლელად. GitHub App, რომელსაც აკონფიგურირებთ პლატფორმის ინტეგრაციებისთვის (PR კომენტარები და ა.შ.), იზიარებს თავის client მონაცემებს შესვლასთან, ამიტომ ის სხვაგვარად ჩნდება შესვლის ვარიანტად. დააყენეთ `0`-ზე, რათა შეინარჩუნოთ App, მაგრამ ამოიღოთ GitHub შესვლის გვერდიდან | არა | `1` | `0` |

#### Google {#google}

შეგიძლიათ დააყენოთ ავტორიზაცია Google-თან [OAuth 2](https://developers.google.com/identity/protocols/oauth2)-ის გამოყენებით. ამისთვის დაგჭირდებათ ახალი OAuth client ID ტიპის მონაცემის შექმნა. მონაცემების შექმნისას, აირჩიეთ "Web Application" როგორც აპლიკაციის ტიპი, დაარქვით მას `Tuist` და დააყენეთ redirect URI როგორც `{base_url}/users/auth/google/callback`, სადაც `base_url` არის URL, რომელზეც თქვენი hosted-service მუშაობს. აპლიკაციის შექმნის შემდეგ, დააკოპირეთ client ID და secret და დააყენეთ ისინი შესაბამისად გარემოს ცვლადებად `GOOGLE_CLIENT_ID` და `GOOGLE_CLIENT_SECRET`.

> [!NOTE]
> **Consent screen scopes**
>
> შესაძლოა დაგჭირდეთ consent screen-ის შექმნა. როცა ამას გააკეთებთ, დარწმუნდით, რომ დაამატეთ `userinfo.email` და `openid` scopes და მონიშნეთ აპლიკაცია როგორც internal.

დაგჭირდებათ შემდეგი გარემოს ცვლადების დაყენება, როცა Okta აპლიკაციის დაყენებისას მიიღებთ client id-ს და secret-ს:

| გარემოს ცვლადი | აღწერა | აუცილებელია | ნაგულისხმევი | მაგალითი |
| --- | --- | --- | --- | --- |
| `TUIST_OKTA_1_CLIENT_ID` | Client ID Okta-თან ავტორიზაციისთვის. რიცხვი უნდა იყოს თქვენი ორგანიზაციის ID | კი | | |
| `TUIST_OKTA_1_CLIENT_SECRET` | Client secret Okta-თან ავტორიზაციისთვის | კი | | |

რიცხვი `1` უნდა ჩაანაცვლოთ თქვენი ორგანიზაციის ID-ით. ჩვეულებრივ, ეს არის 1, მაგრამ შეამოწმეთ თქვენს მონაცემთა ბაზაში.

### საწყობის გარემოს კონფიგურაცია {#storage-environment-configuration}

 Tuist-ს სჭირდება საწყობი API-ის მეშვეობით ატვირთული არტიფაქტების შესანახად. Tuist-ის ეფექტური მუშაობისთვის **აუცილებელია მხარდაჭერილი საწყობის ერთ-ერთი გადაწყვეტის კონფიგურირება**.

დააყენეთ `TUIST_OBJECT_STORAGE_PROVIDER` სერვერის არტიფაქტების backend-ის არჩევასთვის:

#### არტიფაქტების შენახვა {#artifact-retention}

არტიფაქტების გასუფთავება ნაგულისხმევად გამორთულია self-hosted ინსტანციებზე. თითოეულ მხარდაჭერილ არტიფაქტის ტიპს აქვს საკუთარი გარემოს ცვლადი. დააყენეთ ცვლადი დადებით მთელ რიცხვად დღეებში, რათა ჩართოთ გასუფთავება ამ არტიფაქტის ტიპისთვის. ცვლადის დაუყენებლობა ან ცარიელი დატოვება თიშავს გასუფთავებას მხოლოდ შესაბამისი არტიფაქტის ტიპისთვის.

```bash
TUIST_CACHE_ARTIFACT_RETENTION_DAYS=30
TUIST_APP_PREVIEW_RETENTION_DAYS=30
TUIST_BUILD_ARCHIVE_RETENTION_DAYS=60
TUIST_RUN_ARTIFACT_RETENTION_DAYS=30
TUIST_TEST_ATTACHMENT_RETENTION_DAYS=30
TUIST_SHARD_BUNDLE_RETENTION_DAYS=14
```

Helm chart-ის გამოყენებისას, კონფიგურირეთ იგივე პერიოდები როგორც map:

```yaml
server:
  artifactRetentionDays:
    cacheArtifacts: 30
    appPreviews: 30
    buildArchives: 60
    runArtifacts: 30
    testAttachments: 30
    shardBundles: 14
```

ყველა ექვსი გასაღები ოფციონალურია. ეს მაგალითი რთავს ყველა მხარდაჭერილ არტიფაქტის ტიპს დამოუკიდებელი შენახვის ფანჯრით. გამოტოვეთ გასაღები ან დატოვეთ მისი მნიშვნელობა ცარიელი, რათა გასუფთავება დარჩეს გამორთული ამ არტიფაქტის ტიპისთვის. Self-hosted შენახვის ფანჯრებს არ აქვთ 30-დღიანი მაქსიმუმი. კონფიგურირებული მნიშვნელობები, რომლებიც არ არის დადებითი მთელი რიცხვები, იწვევენ სერვერის ჩავარდნას გაშვებისას.

გაუშვით სერვერი ხელახლა შენახვის ცვლადის შეცვლის შემდეგ. ყოველი რიგში მყოფი self-hosted გასუფთავების პაკეტი ამოწმებს მიმდინარე კონფიგურაციას ფაილების წაშლამდე, ამიტომ ცვლადის მოხსნა ან ცარიელად დატოვება, ან მისი ფანჯრის გაზრდა, ასევე იცავს ფაილებს გადაუდებელი სამუშაოებისგან ხელახალი გაშვების შემდეგ.

| გარემოს ცვლადი | არტიფაქტების ფაილები, რომლებიც წაიშლება object storage-დან |
| --- | --- |
| `TUIST_CACHE_ARTIFACT_RETENTION_DAYS` | Xcode cache, legacy content-addressable storage cache, module cache და Gradle cache ფაილები |
| `TUIST_APP_PREVIEW_RETENTION_DAYS` | App preview ბილდები და ხატულები |
| `TUIST_BUILD_ARCHIVE_RETENTION_DAYS` | მიმდინარე და legacy build არქივები |
| `TUIST_RUN_ARTIFACT_RETENTION_DAYS` | ყველა ობიექტი, რომელიც შენახულია ვადაგასული run-ის არტიფაქტის პრეფიქსის ქვეშ, შედეგების bundles-ის, invocation ჩანაწერების და session არქივების ჩათვლით |
| `TUIST_TEST_ATTACHMENT_RETENTION_DAYS` | ტესტების გაშვების დანართები |
| `TUIST_SHARD_BUNDLE_RETENTION_DAYS` | ტესტების shard bundles |

დაგეგმილი გასუფთავება შლის მხოლოდ არტიფაქტების blobs-ებს. ის ინარჩუნებს შესაბამის PostgreSQL და ClickHouse ჩანაწერებს, ასე რომ build, test, run, preview და shard მეტამონაცემები შეიძლება დარჩეს ხილვადი dashboards-ზე მათი გადმოწერების ვადის გასვლის შემდეგაც. ეს კონფიგურაცია არ ცვლის ClickHouse ცხრილების შენახვის წესებს.

> **Air-gapped განლაგებები**
>
> on-premise ინსტალაციებისთვის ინტერნეტთან წვდომის ან ელფოსტის პროვაიდერის კონფიგურაციის გარეშე, ელფოსტის დადასტურება ნაგულისხმევად ავტომატურად გამოიტოვება. მომხმარებლებს შეუძლიათ შესვლა რეგისტრაციის შემდეგ მყისიერად. თუ გაქვთ ელფოსტა კონფიგურირებული, მაგრამ მაინც გსურთ დადასტურების გამოტოვება, დააყენეთ `TUIST_SKIP_EMAIL_CONFIRMATION=true`. ელფოსტის დადასტურების მოსათხოვნად, როცა ელფოსტა კონფიგურირებულია, დააყენეთ `TUIST_SKIP_EMAIL_CONFIRMATION=false`.

> [!NOTE]
> **ელფოსტის ლიმიტები და პაროლის აღდგენის ბმულები**
>
> როცა ელფოსტა კონფიგურირებულია, მიწვევის ელფოსტები (შექმნილი, მასობრივი ან ხელახლა გაგზავნილი) შეზღუდულია ერთით თითოეულ მიმღებზე ყოველ ხუთ წუთში, და 50-იანი აფეთქებებით, რომლებიც ივსება 50-ით საათში თითოეული ორგანიზაციისა და მიმწვევისთვის. მიწვევის გაუქმება არ აღადგენს ლიმიტს, და მიწვევების API პასუხობს ამოწურულ ლიმიტზე `429`-ით და `Retry-After`-ით. მრავალი replica-ს შემთხვევაში, კონფიგურირეთ გაზიარებული Valkey განლაგების მასშტაბის ლიმიტებისთვის; თუ ის კონფიგურირებულია, მაგრამ მიუწვდომელია, მიწვევის ელფოსტები უარყოფილი იქნება. პაროლის აღდგენის ბმულები იწურება 15 წუთის შემდეგ.

#### GitHub {#platform-github}

საკუთარ სერვერზე განთავსებული Tuist ვერ დააყენებს GitHub App-ს, რომელიც მუშაობს `https://tuist.dev`-ზე. GitHub Apps მიბმულია იმ სერვერთან, რომელმაც ისინი დაარეგისტრირა, ამიტომ თქვენს განლაგებას სჭირდება საკუთარი App github.com-ზე.

##### App-ის რეგისტრაცია {#platform-github-registering-the-app}

[შექმენით GitHub App](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/about-creating-github-apps), რომელიც ეკუთვნის თქვენს GitHub ორგანიზაციას. შეგიძლიათ ხელახლა გამოიყენოთ აპლიკაცია, რომელიც შექმენით ავთენტიკაციისთვის, თუ არ შექმენით OAuth App. კონფიგურირეთ ის შემდეგი პარამეტრებით, ჩაანაცვლეთ `YOUR_APP_URL` `TUIST_APP_URL`-ის მნიშვნელობით:

| --- | --- |
| Callback URL-ები | `YOUR_APP_URL/users/auth/github/callback` და `YOUR_APP_URL/integrations/github/authorize` |
| Setup URL | `YOUR_APP_URL/integrations/github/setup` |
| გადამისამართება განახლებისას | ჩართულია |

| Webhook საიდუმლო | ნებისმიერი შემთხვევითი სტრინგი. დააყენებთ მას როგორც `TUIST_GITHUB_APP_WEBHOOK_SECRET` |

მიანიჭეთ შემდეგი რეპოზიტორიის ნებართვები:

| Metadata | მხოლოდ კითხვა |

##### GitHub Enterprise Server {#platform-github-enterprise-server}

ზემოთ მოცემული გარემოს ცვლადები მხოლოდ Tuist-ის github.com App-ს აკონფიგურირებენ. Tuist-ის GitHub Enterprise Server (GHES) ინსტანსთან ინტეგრირებისთვის, ორგანიზაციის ადმინისტრატორები გადადიან ინტეგრაციების გვერდზე **Enterprise server** ჩანართზე და შეჰყავთ GHES საბაზო URL — Tuist მათ გაივლის GitHub-ის [App manifest flow](https://docs.github.com/en/apps/sharing-github-apps/registering-a-github-app-from-a-manifest)-ს, რათა დარეგისტრიროს ახალი Tuist App მათ GHES ინსტანსზე. ახალი App-ის სერთიფიკატები ინახება დაშიფრული თითოეული ინსტალაციისთვის; დამატებითი `TUIST_GITHUB_APP_*` გარემოს ცვლადები არ არის საჭირო.

#### Origin {#platform-origin}

თვითმასპინძელ Tuist სერვერს სჭირდება საკუთარი Origin app, რომელიც კონფიგურირებულია თქვენი განლაგების URL-ებით და ხელმოწერის გასაღებით. დაარეგისტრირეთ ცალკე app თითოეული Tuist გარემოსთვის, რათა ინსტალაციები და სერთიფიკატები დარჩეს დამოუკიდებელი.

##### App-ის რეგისტრაცია {#platform-origin-registering-the-app}

1. შექმენით Ed25519 ხელმოწერის გასაღებების წყვილი OpenSSL-ის გამოყენებით, რომელსაც აქვს Ed25519 მხარდაჭერა:

   ```sh
   umask 077
   openssl genpkey -algorithm ED25519 -out origin-app-private.pem
   openssl pkey -in origin-app-private.pem -pubout -out origin-app-public.pem
   ```

2. შექმენით app [Origin app settings](https://cursor.com/codebase/settings/apps)-ში. დაარეგისტრირეთ `origin-app-public.pem`-ის შიგთავსი, როგორც მისი საჯარო ხელმოწერის გასაღები. შეინახეთ `origin-app-private.pem` საიდუმლოდ; თქვენ მიაწვდით მას Tuist სერვერს და არ ატვირთავთ Cursor-ზე.
3. დააკონფიგურირეთ შემდეგი პარამეტრები, `YOUR_APP_URL`-ის ჩანაცვლებით თქვენი Tuist განლაგების HTTPS საბაზო URL-ით:

   | პარამეტრი | მნიშვნელობა |
   | --- | --- |
   | Homepage URL | `YOUR_APP_URL` |
   | Redirect URI | `YOUR_APP_URL/integrations/origin/setup` |
   | Webhook URL | `YOUR_APP_URL/webhooks/origin` |

4. დააკოპირეთ დარეგისტრირებული App ID, რომელიც იწყება `app_`-ით.

ინსტალაციის დროს Tuist ითხოვს შემდეგ ნებართვებს:

| მოცულობა | გამოიყენება |
| --- | --- |
| `repository:pull_requests:read` | pull requests-ის და მათი მიმდინარე head commit-ის პოვნა. |
| `repository:pull_requests:reviews:write` | ანგარიშის კომენტარების კითხვა, გამოქვეყნება და განახლება. Origin შეიცავს შესაბამის review-read ნებართვას. |
| `repository:metadata:read` | რეპოზიტორიების აღმოჩენა და მათი ნაგულისხმევი შტოების კითხვა. ენიჭება ავტომატურად Origin-ის მიერ. |

დატოვეთ არჩეული რეპოზიტორის webhook-მოვლენები მონიშნვის გარეშე. ინსტალაციის სიცოცხლის ციკლის შეტყობინებები საკმარისია; წყაროს კოდზე წვდომა, merge-ნებართვები და check-run ნებართვები არ არის საჭირო.

| გარემოს ცვლადი | აღწერა | სავალდებულო | ნაგულისხმევი | მაგალითი |
| --- | --- | --- | --- | --- |
| `TUIST_ORIGIN_APP_ID` | App ID, დაკოპირებული Origin app settings-დან. | კი | | `app_...` |
| `TUIST_ORIGIN_APP_PRIVATE_KEY` | `origin-app-private.pem`-ის სრული შიგთავსი, `BEGIN PRIVATE KEY` და `END PRIVATE KEY` ხაზების ჩათვლით და ყველა ახალი ხაზით. | კი | | `-----BEGIN PRIVATE KEY-----...` |

შეინახეთ პირადი გასაღები თქვენი განლაგების საიდუმლოებების მენეჯერში. შეინარჩუნეთ მისი მრავალხაზიანი PEM ფორმატი; ეს პარამეტრი არ იღებს base64-კოდირებულ ჩანაცვლებას. არასდროს დააკომიტოთ გასაღები წყაროს კონტროლში ან არ გამოააშკარაოთ ლოგებში. ორივე ცვლადი უნდა ეკუთვნოდეს ერთსა და იმავე დარეგისტრირებულ app-ს.

თქვენს Tuist სერვერს სჭირდება გამავალი HTTPS წვდომა `api.cursor.com`-ზე. Cursor-მა უნდა შეძლოს მოთხოვნების მიწოდება webhook URL-ზე და ადმინისტრატორებმა უნდა შეძლონ redirect URI-ზე დაბრუნება ბრაუზერში. ორივე დარეგისტრირებული URL უნდა ემთხვეოდეს თქვენი განლაგების HTTPS საბაზო URL-ს.

##### App-ის ინსტალაცია {#platform-origin-installing-the-app}

სერვერის გადატვირთვის შემდეგ, ადმინისტრატორი ხსნის **Settings → Integrations**, ირჩევს **Connect**-ს Origin-ის ქვეშ და ამტკიცებს app-ის წვდომას შესაბამის Origin ანგარიშთან და რეპოზიტორიებთან. Tuist ორგანიზაცია ინარჩუნებს ამ პროცესის განმავლობაში. ინსტალაციები, რომლებიც პირდაპირ Origin-დან იწყება, სთხოვენ ადმინისტრატორს შესვლას და Tuist ორგანიზაციის არჩევას დასაკავშირებლად. შემდეგ ისინი ირჩევენ **Add new project connection**-ს, რათა დააკავშირონ Tuist პროექტი native რეპოზიტორიასთან.

მიჰყევით <.localized_link href="/guides/integrations/gitforge/origin">Origin integration guide</.localized_link>-ს პროექტების დაკავშირებისა და შედეგების ატვირთვის მოთხოვნებისთვის. app-ის ინსტალაცია არ იწყებს build ან test სამუშაო ნაკადებს; ეს სამუშაო ნაკადები აგრძელებენ შედეგების reporting-ს თქვენს Tuist სერვერზე.

## Kubernetes Helm-ით {#kubernetes-with-helm}

Tuist უზრუნველყოფს ოფიციალურ Helm chart-ს Kubernetes-ზე განსათავსებლად. Chart შეიცავს Tuist სერვერსა და cache სერვისს, ასევე ჩაშენებულ ინფრასტრუქტურულ დამოკიდებულებებს, რომლებიც საჭიროებისამებრ შეგიძლიათ შეცვალოთ გარე პროვაიდერებით.

### chart-ის ინსტალაცია {#installing-the-chart}

```bash
helm install tuist oci://ghcr.io/tuist/charts/tuist \
  --set server.license.key="YOUR_LICENSE_KEY"
```

კონკრეტული chart ვერსიის დასაფიქსირებლად:

```bash
helm install tuist oci://ghcr.io/tuist/charts/tuist \
  --set server.license.key="YOUR_LICENSE_KEY" \
  --version 0.1.0
```

### ლიცენზია {#helm-license}

`server.license.key` მნიშვნელობა იღებს როგორც სტანდარტულ ლიცენზიის გასაღებს, ასევე, იზოლირებული (air-gapped) ინსტალაციებისთვის, Base64-ში დაკოდირებულ ლიცენზიის სერთიფიკატს; სერვერი ავტომატურად ამოიცნობს, რომელია ის.

ლიცენზიის `--set`-ით გადაცემა მუშაობს სწრაფი ინსტალაციისთვის. თუ მნიშვნელობებს ვერსიების კონტროლში ინახავთ, შეინახეთ ლიცენზია Kubernetes Secret-ში, რომელსაც Helm-ის გარეთ მართავთ, მაგალითად Vault-ით, Sealed Secrets-ით ან SOPS-ით, და მიმართეთ chart-ი მასზე:

```yaml
# values.yaml
server:
  license:
    existingSecret: tuist-license
    existingSecretKeys:
      key: TUIST_LICENSE
      certificateBase64: ""
```

ჩანაწერი `existingSecretKeys.key`-ის ქვეშ ასახელებს ველს თქვენს Secret-ში, რომელიც შეიცავს ლიცენზიის მნიშვნელობას, რაც შეიძლება იყოს ლიცენზიის გასაღები ან, იზოლირებული (air-gapped) ინსტალაციებისთვის, Base64-ში დაკოდირებული ლიცენზიის სერთიფიკატი. `existingSecretKeys`-ის ქვეშ თითოეული ჩანაწერი ნაგულისხმევად იღებს chart-ის საკუთარ გასაღების სახელს, ამიტომ დააყენეთ ის ჩანაწერები, რომლებსაც თქვენი Secret არ შეიცავს, ცარიელ სტრიქონად, როგორც ზემოთ არის `certificateBase64`. წინააღმდეგ შემთხვევაში, pods მიმართავენ არარსებულ გასაღებებს და ვერ გაეშვებიან. შექმენით Secret რელიზის namespace-ში chart-ის ინსტალაციამდე ან განახლებამდე.

ლიცენზია დააკონფიგურირეთ მხოლოდ ერთი წყაროდან: `server.license.key` ან `server.license.existingSecret`. chart ვერ გამოისახება, თუ არცერთია დაყენებული ან თუ წყაროები გაერთიანებულია. `server.extraEnv`-ით გადაცემული ლიცენზია არ ითვლება წყაროდ, ამიტომ გამოიყენეთ `existingSecret`.

### ინფრასტრუქტურული დამოკიდებულებები {#helm-infrastructure-dependencies}

chart მართავს სამ ინფრასტრუქტურულ დამოკიდებულებას: `postgresql`, `clickhouse` და `objectStorage`. თითოეული ნაგულისხმევად არის **ჩაშენებული** რეჟიმში, რაც ნიშნავს, რომ chart მათ კლასტერის შიგნით ათავსებს. თქვენი გარე ინსტანციების გამოყენებისთვის, დააყენეთ დამოკიდებულების `mode` მნიშვნელობად `external` და შეავსეთ კავშირის დეტალები თქვენს `values.yaml`-ში. მაგალითად, გარე PostgreSQL მონაცემთა ბაზის გამოყენებისთვის:

```yaml
# values.yaml
postgresql:
  mode: external
  external:
    host: your-db-host
    port: 5432
    database: tuist
    username: tuist
    password: your-password
```

თუ PostgreSQL საიდენტიფიკაციო მონაცემებს Helm-ის გარეთ მართავთ, მიმართეთ chart-ი არსებულ Kubernetes Secret-ზე:

```yaml
# values.yaml
postgresql:
  mode: external
  external:
    port: 5432
    database: tuist
    existingSecret: tuist-postgresql
    existingSecretKeys:
      host: host
      username: username
      password: password
```

chart კითხულობს ჰოსტს, მომხმარებლის სახელს და პაროლს Secret-დან და აწყობს `DATABASE_URL`-ს Kubernetes გარემოს ცვლადების ჩანაცვლებით, ამიტომ პაროლი არ შედის Helm მანიფესტში. Secret-ის პაროლის მნიშვნელობა უნდა იყოს URL-უსაფრთხო, რადგან ის ჩაჯდება მონაცემთა ბაზის URL-ში.

იგივე ნიმუში ვრცელდება `clickhouse`-ზე და `objectStorage`-ზე. სრული კონფიგურირებადი ველების ნახვისთვის იხილეთ `external` ბლოკი chart-ის `values.yaml`-ის თითოეულ სექციაში.

### გაზიარებული დაგეგმვა და ჭდეები {#helm-shared-scheduling-and-labels}

chart აჩენს pod-ების გაზიარებული პარამეტრების მცირე ნაკრებს `global`-ის ქვეშ, რათა ოპერატორებმა შეძლონ განლაგების მორგება თავიანთ კლასტერზე ყოველი workload-ისთვის იგივე მნიშვნელობების გამეორების გარეშე:

```yaml
global:
  podLabels:
    environment: production
  imagePullSecrets:
    - name: ghcr-pull-secret
  nodeSelector:
    nodepool: apps
  tolerations:
    - key: dedicated
      operator: Equal
      value: apps
      effect: NoSchedule
```

გამოიყენეთ ეს პარამეტრები, როცა გჭირდებათ:

- კლასტერის სპეციფიკური ჭდეების დამატება ყოველ pod-ზე
- ასახული image-ების ამოღება კერძო რეესტრიდან
- მიმართვა dedicated node pool-ზე
- pod-ების დაშვება taint-ით მონიშნულ კვანძებზე, რომლებიც Tuist workload-ებისთვისაა გამოყოფილი

### Workload იდენტობა და სერვისის ანგარიშები {#helm-workload-identity}

chart განსაზღვრავს სერვისის ანგარიშებს თითოეული აპლიკაციის workload-ის მიხედვით, რათა იდენტობა მხოლოდ იქ მიანიჭოთ, სადაც ის საჭიროა:

- `server.serviceAccount` ვრცელდება Tuist სერვერის განლაგებაზე და მიგრაციის სამუშაოზე
- `cache.serviceAccount` ვრცელდება cache-ის განლაგებაზე

მაგალითად, როცა cache იყენებს გარე S3 ბაკეტს EKS-ზე, შეგიძლიათ ჩართოთ IRSA cache workload-ისთვის იმის გარეშე, რომ იგივე IAM როლი მიამაგროთ ჩაშენებულ მონაცემთა ბაზებს:

```yaml
cache:
  serviceAccount:
    create: true
    annotations:
      eks.amazonaws.com/role-arn: arn:aws:iam::123456789012:role/tuist-cache
```

### თავსებადობის გადაფარვა {#helm-compatibility-overrides}

chart ინახავს storage-ისა და mesh-ის სპეციფიკურ ცვლილებებს opt-in რეჟიმში, რათა ნაგულისხმები პარამეტრები დარჩეს პორტატული:

```yaml
cache:
  podSecurityContext:
    fsGroup: 990

clickhouse:
  embedded:
    service:
      nativePort: 9100
    systemLogs:
      ttlDays: 7
      supersededTables: delete
      level: warning
```

გამოიყენეთ ეს გადაფარვები მხოლოდ მაშინ, როცა თქვენი კლასტერი მოითხოვს მათ:

- `cache.podSecurityContext` ნაგულისხმევად ცარიელია. დააყენეთ `fsGroup`, თუ თქვენს storage class-ს ან CSI დრაივერს სჭირდება გაზიარებული ჯგუფური მფლობელობა mounted volume-ებზე.
- `clickhouse.embedded.service.nativePort` ნაგულისხმევად არის ClickHouse-ის სტანდარტული `9000` native სერვისის პორტი და შეიძლება შეიცვალოს, როცა service mesh ან პლატფორმის რეზერვი ეწინააღმდეგება ამ პორტს.
- `clickhouse.embedded.systemLogs.ttlDays` ნაგულისხმევად ცარიელია, რაც ტოვებს ClickHouse-ის შეუზღუდავ შენახვას ჩაშენებულ შიდა ლოგების ცხრილებზე, როგორიცაა `system.text_log`, `system.query_log`, `system.trace_log`, `system.metric_log` და `system.part_log`. მისი დაყენება ერთხელ ანაცვლებს ამ ცხრილებს, ამიტომ მიიღეთ ის `supersededTables: delete`-თან ერთად — იხილეთ <.localized_link href="/guides/server/self-host/server#capping-operational-log-retention">ოპერაციული ლოგების შენახვის შეზღუდვა</.localized_link>.
- `clickhouse.embedded.systemLogs.level` ნაგულისხმევად არის `information` ჩაშენებული ClickHouse სერვერის logger-ისა და `system.text_log`-ისთვის. `ttlDays`-ისგან განსხვავებით, ის არ არის ნებისმიერი ცხრილის განმარტების ნაწილი, ამიტომ მისი შეცვლა არასდროს ანაცვლებს ცხრილს.
- `clickhouse.embedded.systemLogs.supersededTables` ნაგულისხმევად არის `ignore` და განსაზღვრავს, რა ხდება `<name>_N` ცხრილებთან, რომლებსაც ClickHouse ტოვებს სისტემური ლოგების ცხრილის ჩანაცვლებისას. დააყენეთ ის `delete`-ზე, რათა წაშალოთ ისინი ყოველ `helm upgrade`-ზე.
- `ttlDays`-ისა და `level`-ის ცვლილებები აღწევს ClickHouse pod-ს შემდეგი გადატვირთვისას, რადგან ორივე არის `subPath` mount და chart არ აკეთებს StatefulSet-ის rolling update-ს, როცა მისი ConfigMap იცვლება.

### დაკვირვებადობა {#helm-observability}

chart შეიცავს არჩევით დაკვირვებადობის სტექს (OpenTelemetry Collector, Prometheus, Grafana, Loki და Tempo). ის არის **ნაგულისხმევად გამორთული**. მის ჩასართავად თქვენს `values.yaml`-ში:

```yaml
# values.yaml
observability:
  enabled: true
```

ჩართვისას, Grafana ხელმისაწვდომია წინასწარ კონფიგურირებული Logs, Traces და Metrics drilldown-ებით. გარე დაკვირვებადობისთვის, დატოვეთ ეს გამორთული და კონფიგურირება endpoint-ების მეშვეობით `server.extraEnv`-ით:

```yaml
# values.yaml
server:
  extraEnv:
    - name: TUIST_OTEL_EXPORTER_OTLP_ENDPOINT
      value: "http://your-otel-collector:4317"
    - name: TUIST_LOKI_URL
      value: "http://your-loki:3100"
```

### მნიშვნელობების ცნობარი {#helm-values-reference}

კონფიგურირებადი მნიშვნელობების სრული სიისთვის, იხილეთ chart-ის [`values.yaml`](https://github.com/tuist/tuist/blob/main/infra/helm/tuist/values.yaml).

## განლაგება {#deployment}

Tuist-ის ოფიციალური Docker image ხელმისაწვდომია:
```
ghcr.io/tuist/tuist
```

გამოქვეყნებული image შეიცავს ჩაშენებულ Linux build დამუშავებას `.xcactivitylog` არქივებისთვის, ამიტომ self-hosted განლაგებებს შეუძლიათ დაამუშაონ builds ნებისმიერი დამატებითი სერვისის გაშვების გარეშე — `ProcessBuildWorker` Oban სამუშაო მუშაობს in-process თითოეულ server pod-ზე. თუ გსურთ build დამუშავების გადატანა dedicated replica set-ზე (მაგალითად, parse throughput-ის დამოუკიდებლად მასშტაბირებისთვის web tier-ისგან), დააყენეთ `processor.enabled: true` Helm chart-ში: chart განალაგებს იგივე image-ს როგორც queue-only მომხმარებელს (`TUIST_PROCESSOR_MODE=true`). სრული კონტროლის პარამეტრების სიისთვის იხილეთ [`values.yaml`](https://github.com/tuist/tuist/blob/main/infra/helm/tuist/values.yaml).

> [!NOTE]
> `.xcresult` parsing ეყრდნობა Xcode-ის `xcresulttool`-ს, ამიტომ მას შეუძლია მუშაობა მხოლოდ macOS-ზე. CLI ამას გამჭვირვალედ უმკლავდება self-hosted განლაგებებისთვის: `tuist test` ნაგულისხმევად არის **ლოკალური** დამუშავების რეჟიმი ნებისმიერი არა-`tuist.dev` სერვერის წინააღმდეგ, xcresult-ის პარსინგით დეველოპერის მანქანაზე (რომელსაც უკვე აქვს Xcode build-ისთვის) და სტრუქტურირებული შედეგების ატვირთვით. ტესტის შედეგები შეიწოვება ნებისმიერი დამატებითი ინფრასტრუქტურის გარეშე.

### Docker image-ის ამოღება {#pulling-the-docker-image}

image-ის მიღება შეგიძლიათ შემდეგი ბრძანების შესრულებით:

```bash
docker pull ghcr.io/tuist/tuist:latest
```

image გამოქვეყნებულია როგორც `linux/amd64`, ასევე `linux/arm64`-ისთვის, ამიტომ Docker ავტომატურად ირჩევს ჰოსტისთვის ნატიურ Linux არქიტექტურას.

ან ამოიღეთ კონკრეტული ვერსია:
```bash
docker pull ghcr.io/tuist/tuist:0.1.0
```

### Docker image-ის განლაგება {#deploying-the-docker-image}

Docker image-ის განლაგების პროცესი განსხვავდება თქვენი არჩეული cloud პროვაიდერისა და თქვენი ორგანიზაციის continuous deployment მიდგომის მიხედვით. რადგან cloud გადაწყვეტილებებისა და ინსტრუმენტების უმეტესობა, როგორიცაა [Kubernetes](https://kubernetes.io/), იყენებს Docker image-ებს როგორც ფუნდამენტურ ერთეულებს, ამ სექციაში მოყვანილი მაგალითები კარგად შეესაბამება თქვენს არსებულ კონფიგურაციას.

> [!WARNING]
> თუ თქვენს განლაგების pipeline-ს სჭირდება სერვერის მუშაობის ვალიდაცია, შეგიძლიათ გაგზავნოთ `GET` HTTP მოთხოვნა `/ready`-ზე და დაადასტუროთ `200` სტატუსის კოდი პასუხში.


#### Fly {#fly}

აპლიკაციის [Fly](https://fly.io/)-ზე განსალაგებლად, დაგჭირდებათ `fly.toml` კონფიგურაციის ფაილი. განიხილეთ მისი დინამიურად გენერირება თქვენს Continuous Deployment (CD) pipeline-ში. ქვემოთ მოყვანილია საცნობარო მაგალითი თქვენი გამოყენებისთვის:

```toml
app = "tuist"
primary_region = "fra"
kill_signal = "SIGINT"
kill_timeout = "5s"

[experimental]
  auto_rollback = true

[env]
  # Your environment configuration goes here
  # Or exposed through Fly secrets

[processes]
  app = "/usr/local/bin/hivemind /app/Procfile"

[[services]]
  protocol = "tcp"
  internal_port = 8080
  auto_stop_machines = false
  auto_start_machines = false
  processes = ["app"]
  http_options = { h2_backend = true }

  [[services.ports]]
    port = 80
    handlers = ["http"]
    force_https = true

  [[services.ports]]
    port = 443
    handlers = ["tls", "http"]
  [services.concurrency]
    type = "connections"
    hard_limit = 100
    soft_limit = 80

  [[services.http_checks]]
    interval = 10000
    grace_period = "10s"
    method = "get"
    path = "/ready"
    protocol = "http"
    timeout = 2000
    tls_skip_verify = false
    [services.http_checks.headers]

[[statics]]
  guest_path = "/app/public"
  url_prefix = "/"
```

შემდეგ შეგიძლიათ გაუშვათ `fly launch --local-only --no-deploy` აპლიკაციის დასაწყებად. შემდგომი განლაგებებისას, `fly launch --local-only`-ის გაშვების ნაცვლად, დაგჭირდებათ `fly deploy --local-only`-ის გაშვება. Fly.io არ იძლევა კერძო Docker image-ების ამოღების საშუალებას, რის გამოც უნდა გამოვიყენოთ `--local-only` ფლაგი.


## Prometheus მეტრიკები {#prometheus-metrics}

Tuist აჩენს Prometheus მეტრიკებს `/metrics`-ზე, რათა დაგეხმაროთ თქვენი self-hosted ინსტანციის მონიტორინგში. ეს მეტრიკები მოიცავს:

### Finch HTTP კლიენტის მეტრიკები {#finch-metrics}

Tuist იყენებს [Finch](https://github.com/sneako/finch)-ს როგორც HTTP კლიენტს და აჩენს დეტალურ მეტრიკებს HTTP მოთხოვნების შესახებ:

#### მოთხოვნის მეტრიკები
- `tuist_prom_ex_finch_request_count_total` - Finch მოთხოვნების საერთო რაოდენობა (მრიცხველი)
  - ლეიბლები: `finch_name`, `method`, `scheme`, `host`, `port`, `status`
- `tuist_prom_ex_finch_request_duration_milliseconds` - HTTP მოთხოვნების ხანგრძლივობა (ჰისტოგრამა)
  - ლეიბლები: `finch_name`, `method`, `scheme`, `host`, `port`, `status`
  - ბაკეტები: 10ms, 50ms, 100ms, 250ms, 500ms, 1s, 2.5s, 5s, 10s
- `tuist_prom_ex_finch_request_exception_count_total` - Finch მოთხოვნის გამონაკლისების საერთო რაოდენობა (მრიცხველი)
  - ლეიბლები: `finch_name`, `method`, `scheme`, `host`, `port`, `kind`, `reason`

#### კავშირების პულის რიგის მეტრიკები
- `tuist_prom_ex_finch_queue_duration_milliseconds` - დრო, რომელიც დაიხარჯა კავშირების პულის რიგში ლოდინზე (ჰისტოგრამა)
  - ლეიბლები: `finch_name`, `scheme`, `host`, `port`, `pool`
  - ბაკეტები: 1ms, 5ms, 10ms, 25ms, 50ms, 100ms, 250ms, 500ms, 1s
- `tuist_prom_ex_finch_queue_idle_time_milliseconds` - დრო, როდესაც კავშირი იყო არააქტიური გამოყენებამდე (ჰისტოგრამა)
  - ლეიბლები: `finch_name`, `scheme`, `host`, `port`, `pool`
  - ბაკეტები: 10ms, 50ms, 100ms, 250ms, 500ms, 1s, 5s, 10s
- `tuist_prom_ex_finch_queue_exception_count_total` - Finch რიგის გამონაკლისების საერთო რაოდენობა (მრიცხველი)
  - ლეიბლები: `finch_name`, `scheme`, `host`, `port`, `kind`, `reason`

#### კავშირის მეტრიკები
- `tuist_prom_ex_finch_connect_duration_milliseconds` - დრო, რომელიც დაიხარჯა კავშირის დამყარებაზე (ჰისტოგრამა)
  - ლეიბლები: `finch_name`, `scheme`, `host`, `port`, `error`
  - ბაკეტები: 10ms, 50ms, 100ms, 250ms, 500ms, 1s, 2.5s, 5s
- `tuist_prom_ex_finch_connect_count_total` - კავშირის სცადების საერთო რაოდენობა (მრიცხველი)
  - ლეიბლები: `finch_name`, `scheme`, `host`, `port`

#### გაგზავნის მეტრიკები
- `tuist_prom_ex_finch_send_duration_milliseconds` - დრო, რომელიც დაიხარჯა მოთხოვნის გაგზავნაზე (ჰისტოგრამა)
  - ლეიბლები: `finch_name`, `method`, `scheme`, `host`, `port`, `error`
  - ბაკეტები: 1ms, 5ms, 10ms, 25ms, 50ms, 100ms, 250ms, 500ms, 1s
- `tuist_prom_ex_finch_send_idle_time_milliseconds` - დრო, როდესაც კავშირი იყო არააქტიური გაგზავნამდე (ჰისტოგრამა)
  - ლეიბლები: `finch_name`, `method`, `scheme`, `host`, `port`, `error`
  - ბაკეტები: 1ms, 5ms, 10ms, 25ms, 50ms, 100ms, 250ms, 500ms

ყველა ჰისტოგრამის მეტრიკა უზრუნველყოფს `_bucket`, `_sum` და `_count` ვარიანტებს დეტალური ანალიზისთვის.

### სხვა მეტრიკები

Finch-ის მეტრიკების გარდა, Tuist ასევე აჩენს მეტრიკებს:

## ოპერაციები {#operations}

Tuist გთავაზობთ უტილიტების ნაკრებს `/ops/` ქვეშ, რომლის გამოყენებაც შეგიძლიათ თქვენი ინსტანციის სამართავად.

> [!WARNING]
> **ავტორიზაცია**
>
> `TUIST_OPERATOR_EMAIL_DOMAIN` ენდპოინტებზე წვდომა მხოლოდ იმ მომხმარებლებს შეუძლიათ, რომელთა ელფოსტის დომენი ემთხვევა `/ops/`-ს. თუ ცვლადი დაყენებული არ არის, არავის აქვს წვდომა. დააყენეთ ის დომენზე, რომლის საფოსტო ყუთებსაც თქვენ აკონტროლებთ.
>
> მომხმარებელმა ასევე უნდა დაადასტუროს თავისი მისამართის კონტროლი: დაადასტუროს ელფოსტა ან პაროლის აღდგენის ბმული, შევიდეს Google, GitHub ან Apple-ით, ან შეიყვანოს ერთჯერადი კოდი ან წარმოადგინოს აგენტის შესვლის ვერიფიცირებული ელფოსტა. ანგარიშები, რომლებიც ავტომატურად დადასტურდა (რაც ნაგულისხმევია საფოსტო პროვაიდერის გარეშე), არ შეესაბამება მოთხოვნას, სანამ ეს არ მოხდება. ანგარიშის შექმნის შემდეგ, დადასტურება ფიქსირდება მხოლოდ მაშინ, როდესაც მისამართი არის `TUIST_OPERATOR_EMAIL_DOMAIN`-ში, ამიტომ ცვლადის დაყენების ან შეცვლის შემდეგ, ოპერატორებმა, რომლებმაც არ დაადასტურეს თავიანთი მისამართი მის ქვეშ, ეს კვლავ უნდა გააკეთონ. ანგარიშები, რომლებიც შეიქმნა ერთ-ერთი პროვაიდერით შესვლით ან აგენტის შესვლით, ატარებენ დადასტურებას შექმნიდან. საფოსტო პროვაიდერის გარეშე, პაროლით რეგისტრირებულ ანგარიშს არ შეუძლია ერთ-ერთი პროვაიდერის მიბმა, ამიტომ შექმენით ოპერატორის ანგარიშები Google, GitHub ან Apple-ით შესვლით, ან დააკონფიგურირეთ საფოსტო პროვაიდერი.
>
> ანგარიშები, რომლებიც შეიქმნა ამ შემოწმების არსებობამდე, ჯერ არ ჩაუწერიათ ეს დადასტურება, ამიტომ არსებულ ოპერატორს წვდომა უბრუნდება პაროლის გადაყენების ან ერთ-ერთი პროვაიდერით ერთხელ შესვლის შემდეგ.
>
> როდესაც ოპერატორის დომენში არსებული ანგარიში, რომელსაც ეს დადასტურება არ აქვს, პირველად ამ გზით ადასტურებს მისამართს, Tuist შლის მის პაროლს, passkeys-ებს და კავშირებს ორგანიზაციის ერთიანი შესვლის (SSO) პროვაიდერებთან, ასევე გამოაქვს ის ბრაუზერიდან და CLI-დან, რადგან მისამართის დარეგისტრირებელი შეიძლება არ იყოს მისი მფლობელი. ასეთ ანგარიშზე პაროლის გადაყენება იგივეს აკეთებს, ახალი პაროლის დაყენების გარდა. ანგარიშზე დაყენებული აუთენტიფიკატორის აპლიკაცია რჩება; თუ ის მფლობელს არ ეკუთვნის, წაშალეთ მისთვის. ოპერატორის დომენის გარეთ დადასტურებული ანგარიშები ინარჩუნებენ თავიანთ სერთიფიკატებს. მფლობელი განაგრძობს პროვაიდერით შესვლას ან აყენებს ახალ პაროლს გადაყენების გზით.
>
