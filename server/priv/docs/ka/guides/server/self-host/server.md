# სერვერი {#server}

ჩვენ გთავაზობთ Tuist სერვერის თვითგანთავსებულ ვერსიას იმ ორგანიზაციებისთვის, რომლებსაც საკუთარ ინფრასტრუქტურაზე მეტი კონტროლი სჭირდებათ. ეს ვერსია საშუალებას გაძლევთ განათავსოთ Tuist თქვენს საკუთარ ინფრასტრუქტურაზე, რაც უზრუნველყოფს თქვენი მონაცემების უსაფრთხოებას და კონფიდენციალურობას.

> [!WARNING]
> **ლიცენზია სავალდებულოა**
>
> Tuist-ის თვითგანთავსება მოითხოვს იურიდიულად ძალისმოსილ ფასიან ლიცენზიას. Tuist-ის ადგილობრივი (on-premise) ვერსია ხელმისაწვდომია მხოლოდ Enterprise პაკეტზე მყოფი ორგანიზაციებისთვის. თუ დაინტერესებული ხართ ამ ვერსიით, გთხოვთ, დაუკავშირდეთ [contact@tuist.dev](mailto:contact@tuist.dev)-ს.

> [!WARNING]
> **მოძველებული ქეშის სერვისი**
>
> ძველი თვითგანთავსებული ქეშ-კვანძის ტექნოლოგია აღარ არის რეკომენდებული ახალი ინსტალაციებისთვის. მიმდინარე თვითგანთავსებული ქეშის ინფრასტრუქტურისთვის გამოიყენეთ <.localized_link href="/guides/features/cache/self-hosting">თვითგანთავსებული ქეშის სახელმძღვანელო</.localized_link>.
>
> არსებულ განთავსებებს შეუძლიათ კვლავ მიმართონ მოძველებულ წყაროს დოკუმენტაციას GitHub-ის markdown პროგრამაში: [ქეშ კვანძები](https://github.com/tuist/tuist/blob/main/server/priv/docs/en/guides/cache/self-host.md) და [ქეშის არქიტექტურა](https://github.com/tuist/tuist/blob/main/server/priv/docs/en/guides/cache/architecture.md).

## გამოშვების ციკლი {#release-cadence}

Tuist სერვერი და Kura ქეშის სერვერი ვრცელდება GHCR გამოსახულების სამი არხის მეშვეობით: **canary** (`main`-ზე ყოველი კომიტი), **გამოშვების კანდიდატი** (ყოველ ორშაბათს იჭრება, ერთი კვირა იტესტება) და **სტაბილური** (შემდეგ ორშაბათს ხდება სტაბილური). მხოლოდ სტაბილური გამოშვებები გადააადგილებენ `:latest`-ს და ნაგულისხმევად ირჩევენ; canary და გამოშვების კანდიდატები არის GitHub-ის წინასწარი გამოშვებები, რომლებშიც ჩართვა ხდება მათი ტეგის მიმაგრებით. სერვერი და Kura ერთსა და იმავე ყოველკვირეულ განახლებაზე მოძრაობენ, [Tuist CLI-ის გამოშვების გრაფიკთან](/en/cli/release-channels) სინქრონიზებულად.

ჩვენ ვიცავთ [სემანტიკურ ვერსიებს](https://semver.org/) ვერსიების პროგნოზირებადობისა და თავსებადობის უზრუნველსაყოფად. მთავარი კომპონენტი გამოიყენება Tuist სერვერში ისეთი ცვლილებების აღსანიშნავად, რომლებიც მოითხოვს კოორდინაციას თვითგანთავსებულ მომხმარებლებთან; არ უნდა ელოდოთ, რომ ჩვენ მას გამოვიყენებთ, მაგრამ თუ საჭირო გახდა, დარწმუნებული იყავით, რომ გადასვლას გლუვად შევასრულებთ თქვენთან ერთად.

იხილეთ <.localized_link href="/guides/server/self-host/release-channels">გამოშვების არხები</.localized_link> გვერდი, რათა გაიგოთ, როგორ იჭრება თითოეული არხი, როგორ მივაბათ ერთ-ერთი თქვენს განთავსებას და რა არის რეკომენდებული სტრატეგია პროდაქშენის ნელი სტაბილური ხაზის შენარჩუნებისთვის, ხოლო სტეიჯინგის გარემოში მომავალი გამოშვება იტესტება.

## OAuth განახლებისა და დაბრუნების საზღვარი {#oauth-upgrade-and-rollback-boundary}

OAuth ერთეულების ქეშის წაშლა მოითხოვს ეტაპობრივ განახლებას არსებული ინსტალაციებისთვის. სანამ განათავსებთ ვერსიას, რომელიც აჩერებს OAuth ქეშის გაუქმებებს, ჯერ განათავსეთ ავტორიტეტული წაკითხვის თავსებადობის გამოშვება [#14040](https://github.com/tuist/tuist/pull/14040)-დან **ყველა OAuth მკითხველსა და მწერალზე**. ეს თავსებადობის ეტაპი პირველად ჩნდება **1.355** გამოშვების ხაზში: `ghcr.io/tuist/tuist:1.355.0-rc.1` შეიცავს მას; პროდაქშენის განთავსებებმა უნდა გამოიყენონ სტაბილური `1.355.x` გამოშვება მისი პრომოციის შემდეგ. 1.354 ან უფრო ადრეულ ვერსიებზე მყოფმა ინსტალაციებმა უნდა დაასრულონ ეს ეტაპი, სანამ განაახლებენ მოგვიანებით გამოშვებაზე, რომელიც შეიცავს წაშლას. შეინარჩუნეთ 1.355 ხაზი მხოლოდ თავსებადობისთვის: არ გადმოიტანოთ მასში გაუქმების წაშლა.

ორიგინალური თავსებადობის კომიტი ასევე ხელმისაწვდომია როგორც `ghcr.io/tuist/tuist:sha-c8e54471a425`. სხვა გამოსახულება შესაფერისია თავსებადობის ეტაპისთვის მხოლოდ მაშინ, თუ ის ინარჩუნებს ავტორიტეტულ წაკითხვებს **და ინარჩუნებს მოძველებულ გაუქმებებს**, სანამ ძველი მომხმარებლები დარჩებიან. გაუშვით ამ ეტაპის ჩვეულებრივი მონაცემთა ბაზის მიგრაციები ტრაფიკის მიწოდებამდე, რეფრეშ-ტოკენის ძიების ინდექსის ჩათვლით.

შეამოწმეთ ყველა ვებ-რეპლიკა, ფონური მუშაკები, დაგეგმილი სამუშაოები და ცალკე მიმაგრებული პროცესორის გამოსახულებები თითოეულ გარემოში. დაელოდეთ თავსებადობის გაშვების დასრულებას და დარწმუნდით, რომ ქეშის წამკითხველი ბინარები აღარ დარჩა, სანამ გაუქმებებს წაშლით. არ დაუშვათ, რომ მოტივტივე გამოსახულების ტეგმა გამოტოვოს ეს ეტაპი ავტომატური განახლების დროს. ახალ ინსტალაციებს, რომლებსაც არ ჰყავთ ძველი მომხმარებლები, შუალედური განთავსება არ სჭირდებათ.

> [!WARNING]
> **შეინარჩუნეთ ავტორიტეტული წაკითხვის დაბრუნების სამიზნე**
>
> გაუქმებების წაშლის შემდეგ, ჩვეულებრივმა როლინგ დაბრუნებამ უნდა მიმართოს #14040-ს ან სხვა ავტორიტეტული წაკითხვის ვერსიას. შენარჩუნებული OAuth ქეშის ჩანაწერები შეიძლება იყოს მოძველებული მაშინაც კი, როცა ყველა არაგაუქმების პროცესი შეწყდა, და ხელახლა გაშვებულმა ქეშის წამკითხველმა რეპლიკამ შეიძლება ისინი პირებისგან შემოიტანოს.
>
> უფრო შორს დაბრუნება მოითხოვს **ყველა** არაგაუქმების OAuth მომხმარებლის შეჩერებას და დაცლას, შემდეგ კი **ყველა** შენარჩუნებული Boruta ქეშის მონაწილის გასუფთავებას ან ჩანაცვლებას, სანამ რაიმე ქეშის წამკითხველ მომხმარებელს გაუშვებთ. შეუშალეთ შენარჩუნებულ მონაწილეებს ხელახლა შეერთება. მხოლოდ შემავალი ტრაფიკის დაცლა ან მხოლოდ ვებ-რეპლიკების ხელახლა გაშვება არასაკმარისია; შეათანხმეთ ეს აღდგენა თქვენს Tuist მხარდაჭერის კონტაქტთან, ნაცვლად ქეშების ავტომატური გასუფთავების ან მონაცემთა ბაზის მიგრაციების დაბრუნების.

## მრავალრეპლიკური კლასტერიზაცია {#multi-replica-clustering}

მხარდაჭერილი მრავალრეპლიკური ვებ-განთავსებები მოითხოვს Erlang კლასტერიზაციას რეპლიკებს შორის Phoenix PubSub და Oban PG შეტყობინებებისთვის, არა როგორც ავტორიტეტს ავთენტიკაციისთვის. დიაგრამა უარყოფს მრავალ რეპლიკას, ავტოსკალერის ჩათვლით, რომელსაც შეუძლია ერთ რეპლიკაზე მეტად გაიზარდოს, როცა `server.cluster.enabled` არის false. ადრე მიღებულმა არაკლასტერულმა განთავსებებმა უნდა დაგეგმონ ეს განახლება, ნაცვლად დაცვის გვერდის ავლისა. დაასრულეთ <.localized_link href="/guides/server/self-host/server#oauth-upgrade-and-rollback-boundary">OAuth განახლების თანმიმდევრობა</.localized_link>, გაუქმების წაშლის ჩათვლით, სანამ წევრობას შეცვლით.

შექმენით პირადი cookie Secret გამოშვების namespace-ში თქვენი საიდუმლოებების მენეჯერის გამოყენებით, შემდეგ კი დააკონფიგურირეთ მისი სახელი და გასაღები:

```yaml
server:
  replicaCount: 2
  cluster:
    enabled: true
    distributionPort: 9100
    cookieExistingSecret: tuist-server-cluster
    cookieExistingSecretKey: release-cookie
```

cookie უნდა იყოს მაღალი ენტროპიის და გაზიარებული ყველა მონაწილე ვებ-რეპლიკას შორის. არასდროს გამოიყენოთ გამოქვეყნებულ გამოსახულებაში ჩაშენებული cookie: დისტრიბუციის cookie-ის ფლობა ანიჭებს დისტანციურ შესრულებას მის კვანძებზე. დისტრიბუციული გამოშვების გაშვება ახლა უარყოფს დაკარგულ პირად `RELEASE_COOKIE`-ს ან არასწორ პორტს, ჩათვლით აშკარად კონფიგურირებულ `RELEASE_DISTRIBUTION=name`-ს ან `sname`-ს DNS აღმოჩენის გარეშე. არადიაგრამულმა განთავსებებმა ასევე უნდა დააკონფიგურირონ `TUIST_CLUSTER_DNS_SERVICE`, `TUIST_CLUSTER_APP_NAME` და pod IP/კვანძის სახელი თანმიმდევრულად. აღმოჩენა ამჟამად იყენებს IPv4 A ჩანაწერებს.

ჩვეულებრივი სერვერთან დაკავშირებული `helm upgrade`-ით, `cookieExistingSecret`-ის ცარიელად დატოვება ქმნის cookie Secret-ს და ხელახლა იყენებს მის მიმდინარე მნიშვნელობას მოგვიანებით განახლებებზე. ოფლაინ `helm template`, Argo CD და სხვა GitOps რენდერერები ცოცხალი Secret ძიების გარეშე ვერ შეინარჩუნებენ იმ გენერირებულ მნიშვნელობას; მათ უნდა გამოიყენონ `cookieExistingSecret`, რომელიც ეყრდნობა ცალკე მართვად, სტაბილურ Secret-ს. არ შეცვალოთ cookie გასაღები ცოცხალი კლასტერის იმპლიციტურად როტაციისთვის. Cookie როტაცია საჭიროებს ყოველი მონაწილის კოორდინირებულ მიგრაციას/ხელახლა გაშვებას; მხოლოდ Secret-ის განახლება არ ანახლებს არსებულ პროცესებს.

გამოსახულებაში ჩაშენებული cookie-ებიდან პირველი განლაგება ქმნის ცალკეულ ძველ/ახალ წევრობის კუნძულებს, სანამ ყველა ვებ-რეპლიკა არ გამოიყენებს პირად Secret-ს. დაგეგმეთ მიგრაციის ფანჯარა რეალური დროის განახლებებისთვის. მომდევნო თანდათანობითი განლაგებები ქმნიან შერეული ვერსიების კლასტერებს, ამიტომ შეაფასეთ PubSub, Oban შეტყობინებები და მეზობლის ჩანაცვლება ფაქტობრივ ძველ/ახალ ვერსიებზე. ეს შეტყობინებები არ არის საიმედო მიწოდების გარანტიები. შეინარჩუნეთ ავტორიტეტული-წაკითხვის rollback გამოსახულება და შეინარჩუნეთ იგივე პირადი cookie თავსებადი ვერსიის rollback-ის დროს.

EPMD-ს (TCP 4369) და კონფიგურირებულ დისტრიბუციის პორტს ნება დართეთ მხოლოდ სანდო სერვერის პირებს შორის, არასდროს მომხმარებლის სამუშაო დატვირთვებიდან ან საჯარო ქსელიდან. შეამოწმეთ თქვენს გარემოში შესვლა/გასვლის რეალური იზოლაცია; NetworkPolicy-ის რენდერი არ ამტკიცებს აღსრულებას ან backend-ზე მიღწევადობას. ორ-რეპლიკიანმა canary-მ უწყვეტი დატვირთვის პირობებში უნდა გაიაროს შეერთება, როლირებით ჩანაცვლება და წარუმატებლობა/აღდგენა პრომოციამდე. DNS გამოიყენება პირების აღმოსაჩენად, არა ჯანსაღი კვანძების გასათიშად დროებითი წარუმატებელი ან ნაწილობრივი პასუხის შემთხვევაში; რეალური კვანძის დაკარგვა და OTP partition-ის პრევენცია კვლავ მოქმედებს. libcluster-მა შეიძლება მაინც ჩაწეროს წარმატებული „გათიშვის“ ოპერაცია შენარჩუნების callback-ისთვის კავშირის დახურვის გარეშე; დაადგინეთ რეალური წევრობა კვანძის აწევა/ჩამოწევის მოვლენებიდან ან `Node.list()`-დან, არა მხოლოდ იმ ლოგის ხაზიდან.

## უწყვეტი განლაგება {#continuous-deployment}

ჩვენ გირჩევთ პროდაქშენი მიამაგროთ სტაბილურ მცირე ხაზზე (მაგალითად `ghcr.io/tuist/tuist:1.351`), ისე რომ ყოველდღიური განახლებები მოიცავდეს მხოლოდ უკან გადატანილ შესწორებებს. სტაბილური ხაზები ყოველ ორშაბათს 06:00 UTC-ზე გადადის წინ, release-candidate არხზე ერთკვირიანი ტესტირების შემდეგ; staging გარემო canary-ზე ან მიმდინარე release-candidate ტეგზე აღმოაჩენს რეგრესიებს, სანამ ისინი თქვენს მომხმარებლებს მიაღწევენ. იხილეთ <.localized_link href="/guides/server/self-host/release-channels">Release channels</.localized_link> რეკომენდებული მიმაგრების სტრატეგიისთვის.

თუ გირჩევნიათ ახალი ფუნქციების მიღება მათი სტაბილიზაციისთანავე თქვენი მანიფესტების შეცვლის გარეშე, მიამაგრეთ `:latest`. ტეგი იცვლება კვირაში ერთხელ ორშაბათ დილით, ამიტომ დაგეგმეთ თქვენი განლაგების ფანჯარა შესაბამისად. აქ არის GitHub Actions სამუშაო ნაკადის მაგალითი, რომელიც ამ რიტმით ამოწმებს და ანაწილებს უახლეს სტაბილურ გამოსახულებას:

## ქსელის სანდო წვდომა {#network-trusted-access}

თვითმასპინძელ ინსტალაციებში შესაძლებელია სანდო ქსელის დეველოპერებისთვის ინსაიტების გაგზავნა, cache-ის გამოყენება ან ორივე შესაძლებლობის გამოყენება ავტორიზაციის გარეშე. დაშბორდი და ადმინისტრირება კვლავ მოითხოვს ავტორიზაციას.

ჩართეთ მხოლოდ ის შესაძლებლობები, რომლებიც გჭირდებათ:

| სერვერის გარემოს ცვლადი | ნებას რთავს ავტორიზაციის გარეშე |
| --- | --- |
| `TUIST_NETWORK_TRUSTED_INSIGHTS_ACCESS=true` | ბილდისა და ტესტების ინსაიტების გაგზავნა |
| `TUIST_NETWORK_TRUSTED_CACHE_ACCESS=true` | cache-ში შენახული ბილდის შედეგების წაკითხვა და ჩაწერა |

ორივე პარამეტრი **გამორთულია ნაგულისხმევად**, დამოუკიდებელია და ვრცელდება მთელ ინსტანციაზე ყველა ანგარიშსა და პროექტზე, პირადი პროექტების ჩათვლით. ისინი ხელმიუწვდომელია Tuist-ის ჰოსტინგზე და არ ცვლის თვითმასპინძლობის ლიცენზიას.

ყოფილი `TUIST_NETWORK_TRUSTED_REPORT_PUBLISHING` სახელი რჩება თავსებადობის სათადარიგოდ, როცა `TUIST_NETWORK_TRUSTED_INSIGHTS_ACCESS` არ არის დაყენებული.

> [!WARNING]
> ჩართეთ ეს პარამეტრები მხოლოდ იძულებითი ოფისის ქსელის ან VPN საზღვრის შიგნით. ნებისმიერს, ვისაც შეუძლია მიუწვდებლობა ჩართულ endpoint-თან, შეუძლია გაგზავნოს ანგარიშები ან, cache-ზე წვდომის ჩართვის შემთხვევაში, წაიკითხოს და გადაწეროს cache-ში შენახული შედეგები. ეს საშუალებას აძლევს გაყალბებულ ტელემეტრიას, cache-ის მოწამვლას და სიმძლავრის ამოწურვას. ანგარიშების პასუხებმა ასევე შეიძლება გაამჟავლოს პირადი პროექტების სახელები და ბილდის სისტემები. Tuist არ ამოწმებს VPN წევრობას ან არ ენდობა გადაგზავნილ IP ჰედერებს როგორც წევრობის მტკიცებულებას.

### ინსტანციის კონფიგურაცია {#network-trusted-instance-configuration}

1. შეზღუდეთ Tuist სერვერი, ყოველი Kura HTTP/gRPC listener და ნებისმიერი Bazel BES ingress თქვენს სანდო ქსელამდე firewall-ის ან პირადი ingress-ის გამოყენებით.
2. განაახლეთ ყოველი სერვერისა და Kura რეპლიკა კლიენტების განახლებამდე. შეინარჩუნეთ Kura ავტორიზაცია ჩართული `KURA_AUTH_TUIST_URL`-ით და მისი control-plane მონაცემებით; მისი გამორთვა არღვევს ამ შეზღუდვებს. დააკონფიგურეთ თქვენი cache endpoint <.localized_link href="/guides/features/cache/self-hosting">self-hosted cache guide</.localized_link>-ის გამოყენებით.
3. დააყენეთ ზემოთ მოცემული სასურველი ცვლადები ყოველ შესაბამის Tuist სერვერის რეპლიკაზე, შემდეგ გადატვირთეთ ან ხელახლა განალაგეთ ისინი. პარამეტრს რთავს მხოლოდ ზუსტი მნიშვნელობა `true`. არ არსებობს დაშბორდის გადამრთველი ან ცალკე Kura flag.

### კლიენტების კონფიგურაცია {#network-trusted-client-configuration}

დააკონფიგურეთ საბოლოო თვითმასპინძელი სერვერის URL და პროექტი თითოეულ თავსებად კლიენტზე. კლიენტები ავტომატურად აღმოაჩენენ, რომელი შესაძლებლობებია ჩართული, როცა მონაცემები არ არის; კლიენტის opt-in არ არის საჭირო. აღმოჩენა არ მიჰყვება გადამისამართებებს. არსებული მონაცემები რჩება გამოყენებაში, ხოლო არასწორი ან განახლების შეცდომის მქონე მონაცემები იწვევს შეცდომას ანონიმური სათადარიგოს ნაცვლად. ხელახლა შედით ან აშკარად გამოდით აღდგენისთვის.

ინსაიტებზე წვდომის ჩართვამდე, განაახლეთ ყველა ინსტრუმენტი, რომელიც იზიარებს მონაცემებს, ისეთ ვერსიებამდე, რომლებიც ინარჩუნებენ დაზიანებულ ან უარყოფილ მონაცემებს, უარყოფენ წაუკითხავ მონაცემთა დირექტორიებს და გამორიცხავენ Git origins ხელმოუწერელი ანგარიშებიდან. უფრო ძველმა ინსტრუმენტებმა შეიძლება წაშალონ მონაცემები და შეუგნებლად დაუშვან ანონიმური სათადარიგო; მხოლოდ სერვერის განახლება ამას ვერ შეასწორებს. თუ სერვერს არ აქვს აღმოჩენის მხარდაჭერა ან დაბრუნებულია უფრო ძველ ვერსიაზე, კლიენტებმა უნდა გაიარონ ავტორიზაცია. ყოფილი `TUIST_NETWORK_TRUSTED_PUBLISHING` კლიენტის პარამეტრი აღარ მოქმედებს.

- **Insights:** გაგზავნეთ მხოლოდ დასრულებული Xcode, Gradle, Elixir/Mix და Bazel ანგარიშები, archive-ის, დანართის, coverage-ის, shard-planning-ის ან არსებული ანგარიშის წვდომის გარეშე. მსახიობის პრეტენზიები არ არის გადამოწმებული; ხელმოუწერელი ტელემეტრია არ ქმნის სანდო ტესტის მტკიცებულებას ან ავტომატიზაციას. იხილეთ <.localized_link href="/guides/features/build-insights/xcode#network-trusted-publishing">Xcode</.localized_link>, <.localized_link href="/guides/features/build-insights/gradle#network-trusted-publishing">Gradle</.localized_link> და <.localized_link href="/guides/features/build-insights/elixir#network-trusted-publishing">Elixir</.localized_link> სახელმძღვანელოები კლიენტის დაყენებისა და კონფიდენციალურობის დეტალებისთვის.
- **Cache:** მხარდაჭერილია CLI კომპილაციის/მოდულის caching, Bazel caching და Gradle task caching. Cache-ის გასუფთავება და Remote Asset ჩამოტვირთვები კვლავ მოითხოვს მონაცემებს. მხარდაჭერის გარეშე კლიენტებმა უნდა გააგრძელონ ავტორიზაცია.
- **Bazel:** ანგარიშგება მოითხოვს აშკარა `TUIST_BAZEL_BES_BACKEND`-ს და თავსებად Kura-ს. Cache-ისა და ანგარიშგების პარამეტრები ჩართულია დამოუკიდებლად. ხელახლა გაუშვით `tuist bazel setup` მონაცემების ან რომელიმე პარამეტრის შეცვლის შემდეგ; ხელახლა გაუშვით `tuist cache config` კომპილაციის-cache კონფიგურაციის ცვლილებებისთვის.

ანგარიშის მოთხოვნები შეზღუდულია 8 MB-ით, 60 მოთხოვნა წუთში და 10,000 დღეში თითო პროექტზე. დააკონფიგურეთ გაზიარებული Valkey განლაგების მასშტაბის квოტებისთვის მრავალი რეპლიკით; წინააღმდეგ შემთხვევაში ლიმიტები მოქმედებს პროცესის მიხედვით. თუ კონფიგურირებული გაზიარებული квოტის backend ხელმიუწვდომელია, ხელმოუწერელი ანგარიშგება უარყოფილია. დაამატეთ ingress კავშირის, სხეულის და სიჩქარის ლიმიტებიც.

### ქსელის სანდო წვდომის გამორთვა {#disable-network-trusted-publishing}

დააყენეთ შესაბამისი ცვლადი მნიშვნელობაზე `false`, შემდეგ კი გადატვირთეთ **ყველა შესაბამისი სერვერის რეპლიკა**. ძველ რეპლიკებს შეუძლიათ გააგრძელონ უმონაცემო მოთხოვნების მიღება ჩანაცვლებამდე. Cache-ზე წვდომის ახალი მოთხოვნები იბლოკება ბოლო რეპლიკის გადართვიდან 60 წამის განმავლობაში; მიმდინარე ტრანსფერები არ წყდება. თუ საჭიროა დაუყოვნებელი გაუქმება, ჯერ დაბლოკეთ ტრაფიკი ingress-ზე. არსებული ანგარიშები ინარჩუნებენ ჩვეულებრივ ხილვადობასა და შენახვის პერიოდს, ხოლო ავტორიზებული კლიენტები განაგრძობენ მუშაობას.

### Postgres მონაცემთა ბაზა {#postgres-database}

### ClickHouse მონაცემთა ბაზა {#clickhouse-database}

Tuist იყენებს [ClickHouse](https://clickhouse.com/)-ს ანალიტიკის დიდი რაოდენობით მონაცემების შესანახად და მოსაძიებლად. ClickHouse **აუცილებელია** ისეთი ფუნქციებისთვის, როგორიცაა build insights. შეგიძლიათ აირჩიოთ, თვითონ განათავსოთ ClickHouse თუ გამოიყენოთ მათი ჰოსტინგის სერვისი.

> [!NOTE]
> **მიგრაციები**
>
> Docker გამოსახულების entrypoint ავტომატურად ასრულებს ნებისმიერ დარჩენილ ClickHouse სქემის მიგრაციას სერვისის გაშვებამდე.

ჩაშენებული Docker Compose და Helm embedded ClickHouse კონფიგურაციები ამცირებენ ClickHouse ტექსტური ლოგის დონეს გამოსახულების `trace` ნაგულისხმევიდან `information`-მდე, საიდანაც მოდის `system.text_log` ტომის უმეტესი ნაწილი. ორივე ასევე შეუძლია შეზღუდოს ClickHouse-ის საკუთარი `system.*` ოპერაციული ლოგის ცხრილები, რომლებიც სხვა შემთხვევაში შეუზღუდავია, მაგრამ ეს ნაგულისხმევად გამორთულია — იხილეთ ქვემოთ. გარე ClickHouse განლაგებებმა უნდა დააკონფიგურირონ ეს ოპერაციული ლოგები პირდაპირ მათ ClickHouse სერვისში.

#### ClickHouse რეპლიკაციის ტოპოლოგია {#clickhouse-replication-topology}

მრავალრეპლიკიანი ClickHouse Tuist-ის უკან მხარდაჭერილია მხოლოდ ClickHouse Cloud-ზე. თვითმართვადი ClickHouse არის ერთრეპლიკიანი.

შემომავალი მიგრაციები გამოყოფენ ჩვეულებრივ `MergeTree` engine-ს. Cloud-ზე ის ხდება `SharedMergeTree` გამჭვირვალედ, ასე რომ ჩაწერები ხვდება საერთო object storage-ში და ნებისმიერი რეპლიკების რაოდენობა მუშაობს. თვითმართვად ClickHouse-ზე, `MergeTree` წერს მხოლოდ ერთ რეპლიკაზე ლოკალურ დისკზე; მრავალრეპლიკიანი დაყენება ან უხმოდ გაყოფს შემომავალ მონაცემებს რეპლიკებს შორის, ან უარყოფს CREATE-ს `UNKNOWN_STORAGE: Only tables with a Replicated engine or tables which do not store data on disk are allowed in a Replicated database.`-ით, იმის მიხედვით, თუ როგორ არის დაყენებული `database_replicated_allow_only_replicated_engine` შემერთებულ მომხმარებელზე.

გაუშვით ერთი shard ერთი რეპლიკით თვითმართვად ClickHouse-ზე და რეგულარულად გააკეთეთ ClickHouse მონაცემთა დირექტორიის სარეზერვო ასლები. არ არსებობს მეორე რეპლიკა, რომელზეც გადასვლა შეიძლება, თუ კვანძი დაიკარგა.

#### ოპერაციული ლოგის შენახვის შეზღუდვა {#capping-operational-log-retention}

შენახვა შეიძლება გამოყენებულ იქნას `system.text_log`-ზე, `system.query_log`-ზე, `system.query_thread_log`-ზე, `system.query_views_log`-ზე, `system.trace_log`-ზე, `system.metric_log`-ზე, `system.asynchronous_metric_log`-ზე და `system.part_log`-ზე.

მის ჩართვა არის ერთჯერადი, ერთმხრივი ნაბიჯი ეგზემპლარზე, რომელსაც უკვე აქვს მონაცემები, რის გამოც არცერთი bundle არ აკეთებს ამას თქვენთვის. ნებისმიერი შენახვის ფანჯარა იწვევს იმას, რომ ეს ცხრილის განსაზღვრებები აღარ ემთხვევა მათ კონფიგურაციას, ამიტომ ClickHouse გადაარქმევს თითოეულს და იწყებს ახალ ცხრილს, როგორც აღწერილია [ჩანაცვლებული ლოგის ცხრილების](#superseded-log-tables) ქვეშ. დარჩენილი თაობა ინახავს ყველაფერს, რაც დაგროვდა ამ დრომდე და არ აქვს საკუთარი შენახვის პოლიტიკა, ამიტომ თუ არ დაიბრუნებთ ადგილს იმავე ნაბიჯში, ის დისკზე სამუდამოდ დარჩება და ახალი ფანჯარა მხოლოდ შემდგომში ჩაწერილ სტრიქონებს შეზღუდავს. ჩართეთ ორივე ერთად:

```yaml
clickhouse:
  embedded:
    systemLogs:
      ttlDays: 14
      supersededTables: delete
```

ეს ერთი `helm upgrade` არის თვითკმარე, რადგან `ttlDays`-ის ცარიელიდან მნიშვნელობაზე გადაყვანა ამატებს drop-in mount-ს და აკეთებს ClickHouse pod-ის rolling restart-ს: ის გადაიტვირთება, ანაცვლებს ცხრილებს და post-upgrade Job შემდეგ შლის მათ. განათავსეთ `helm upgrade --wait`-ით, რათა pod გადაიტვირთოს Job-ის გაშვებამდე; წინააღმდეგ შემთხვევაში თაობები ჩნდება მისი შემოწმების შემდეგ და შემდეგი `helm upgrade` დაიბრუნებს მათ.

Docker Compose-ით, გააკომენტარეთ `clickhouse-log-ttl.xml` ტომი `clickhouse` სერვისზე `docker-compose.yml`-ში და დააყენეთ ორივე ცვლადი `.env`-ში:

```bash
CLICKHOUSE_SYSTEM_LOG_TTL_DAYS=14
CLICKHOUSE_SUPERSEDED_LOG_TABLES=delete
```

ადგილის დაბრუნების შემდეგ შეგიძლიათ დააბრუნოთ `supersededTables`/`CLICKHOUSE_SUPERSEDED_LOG_TABLES` უკან `ignore`-ზე, რათა მოგვიანებით ClickHouse-ის განახლებამ არ წაშალოს ისტორია.

#### ჩანაცვლებული ლოგის ცხრილები {#superseded-log-tables}

ClickHouse ამოწმებს გაშვებისას, ემთხვევა თუ არა თითოეული სისტემური ლოგის ცხრილი მის კონფიგურაციას. როდესაც არ ემთხვევა, ის გადაარქმევს არსებულ ცხრილს `system.<name>_0`-ად, შემდეგ `_1`-ად, `_2`-ად და ა.შ., და იწყებს ახალს. ეს ხდება შენახვის ფანჯრის შეცვლისას და ნებისმიერ ClickHouse განახლებაზე, რომელიც ცვლის სისტემური ლოგის სქემას.

ცხრილის სახელის შეცვლა არ ასკოპირებს მის მონაცემებს, ამიტომ ეს არ მოიხმარს დამატებით დისკს. რა ხდება ჩანაცვლებულ ცხრილთან შემდეგ, დამოკიდებულია ცხრილზე, საიდანაც მოვიდა, რადგან ის ინარჩუნებს იმ შენახვას, რაც ცოცხალ ცხრილს ჰქონდა ჩანაცვლების მომენტში. პირველად, როდესაც ჩართავთ შენახვას, ჩანაცვლებულ ცხრილს არ აქვს ის, ამიტომ ის ინახავს ყველა დაგროვილ ისტორიას უვადოდ. ფანჯრის მოგვიანებითი ცვლილება ანაცვლებს ცხრილს, რომელსაც უკვე აქვს TTL, ამიტომ ისინი თავისთავად იწურებიან და ტოვებენ ცარიელ ცხრილს. ClickHouse არასდროს შლის თავად ცხრილებს, ამიტომ ხანგრძლივად მოქმედ ეგზემპლარზე ისინი გროვდება ნებისმიერ შემთხვევაში.

ჩანაცვლებული ცხრილები ნაგულისხმევად ინახება, რათა განახლებამ არასდროს წაშალოს ოპერაციული ისტორია. დააყენეთ პოლიტიკა `delete`-ზე მათ წასაშლელად, რაც ხდება `docker compose up`-ზე და ყოველ `helm upgrade`-ზე:

```bash
CLICKHOUSE_SUPERSEDED_LOG_TABLES=delete
```

Helm chart-ით, დააკონფიგურირეთ იგივე პოლიტიკა როგორც მნიშვნელობა:

```yaml
clickhouse:
  embedded:
    systemLogs:
      supersededTables: delete
```

ჩანაცვლებული ცხრილის წაშლა აბრუნებს მის დისკის ადგილს. ცოცხალ ცხრილს არასდროს ეხება, ისევე როგორც მასში ჩაწერილ სტრიქონებს ჩანაცვლების შემდეგ.

ადგილის ერთხელ დასაბრუნებლად პოლიტიკის შეცვლის გარეშე, წაშალეთ ცხრილები ხელით:

```sql
SELECT name FROM system.tables WHERE database = 'system' AND match(name, '_log_[0-9]+$');
DROP TABLE IF EXISTS system.text_log_0 SYNC;
```

`system` მონაცემთა ბაზა იყენებს `Atomic` ძრავას, რომელიც გადადებს ჩვეულებრივ `DROP TABLE`-ს `database_atomic_delay_before_drop_table_sec`-ით (ნაგულისხმევად რვა წუთი). `SYNC` მონაცემებს მაშინვე შლის, რაც სასურველია, როდესაც ამ ცხრილებს შლით დისკის სივრცის ამოწურვის გამო.


### შენახვა {#storage}

ასევე დაგჭირდებათ ფაილების შესანახი გადაწყვეტა (მაგალითად, ჩარჩოებისა და ბიბლიოთეკების ბინარული ფაილები). Tuist სერვერი უჭერს მხარს S3-თან თავსებად შენახვას და Azure Blob Storage-ს სერვერის მიერ მართული არტეფაქტებისთვის.

> [!TIP]
> **ოპტიმიზებული კეშირება**
>
> თუ თქვენი მთავარი მიზანი კეშის ლატენტობის შემცირებაა, შესაძლოა არ დაგჭირდეთ მთლიანი სერვერის თვითმასპინძლობა. შეგიძლიათ განათავსოთ თვითმასპინძელი Kura კვანძები თქვენს CI ან დეველოპერულ ქსელთან ახლოს და დააკავშიროთ ისინი Tuist-ის ჰოსტინგულ სერვერთან ან თქვენს თვითმასპინძელ სერვერთან.
>
> იხილეთ <.localized_link href="/guides/cache/self-host">თვითმასპინძელი კეშის სახელმძღვანელო</.localized_link>.


### თვითმასპინძელი Kura კვანძები {#self-hosted-cache-nodes}

თვითმასპინძელი Kura კვანძების გამოსაყენებლად თვითმასპინძელ Tuist სერვერთან ერთად:

1. დააკონფიგურირეთ `KURA_CONTROL_PLANE_CLIENT_ID` და `KURA_CONTROL_PLANE_CLIENT_SECRET` Tuist სერვერზე. კლიენტის ID **უნდა იყოს UUID**. შექმენით UUID და შემთხვევითი საიდუმლო <.localized_link href="/guides/cache/self-host#control-plane-client">თვითმასპინძელი კეშის სახელმძღვანელოში</.localized_link> მოცემული ბრძანებებით და შეინახეთ ისინი თქვენს განლაგების საიდუმლოებში.
2. განათავსეთ Kura კვანძები <.localized_link href="/guides/cache/self-host">თვითმასპინძელი კეშის სახელმძღვანელოს</.localized_link> მიხედვით, იგივე control-plane კრედენციალის გამოყენებით.
3. დააკონფიგურირეთ თითოეული Kura კვანძი `KURA_REGISTRATION_URL` და `KURA_ADVERTISED_HTTP_URL` პარამეტრებით. რეგისტრაციის heartbeat-ები აცნობებენ სერვერს, რომელი მზა, კლიენტისთვის ხელმისაწვდომი Kura endpoint-ები შეუძლია CLI-სთვის რეკლამირება.

როცა `TUIST_DATABASE_SCHEMA` არ არის `public`, release მიგრაციები ქმნიან სქემას, თუ ის ჯერ არ არსებობს, Ecto მიგრაციების ჯაჭვის გაშვებამდე. თუ მიგრაციის როლს არ შეუძლია სქემების შექმნა, წინასწარ შექმენით სქემა და გახადეთ მიგრაციის როლი მის მფლობელად.

Tuist მიმართავს კავშირს მორგებულ სქემაზე სესიის `search_path`-ის დაყენებით. ზოგიერთი პულირებული ან პროქსირებული Postgres კონფიგურაცია (მაგალითად, PgBouncer, ან მართვადი მონაცემთა ბაზები, რომლებიც ზღუდავენ გაშვების პარამეტრებს) არ იყენებს ამას და სესია ბრუნდება `public`-ზე, რაც მიგრაციების დროს ვლინდება როგორც `permission denied for schema public`. ასეთ კონფიგურაციაზე დაკავშირებისას, მიამაგრეთ სქემა თავად როლზე, რათა ყოველი სესია მასში დაიწყოს პროქსის მიუხედავად:

```sql
CREATE SCHEMA IF NOT EXISTS tuist AUTHORIZATION <migration_role>;
ALTER ROLE <migration_role> IN DATABASE <database> SET search_path = tuist;
-- If the web server connects as a separate runtime role (TUIST_DATABASE_RUNTIME_ROLE):
ALTER ROLE <runtime_role> IN DATABASE <database> SET search_path = tuist;
```

  - რეპოზიტორიები:

> **Consent Screen Scopes**

| გარემოს ცვლადი | აღწერა | სავალდებულო | ნაგულისხმევი | მაგალითი |

#### არტიფაქტების შენახვა {#artifact-retention}

არტიფაქტების გასუფთავება ნაგულისხმევად გამორთულია self-hosted ინსტანციებზე. თითოეულ მხარდაჭერილ არტიფაქტის ტიპს აქვს საკუთარი გარემოს ცვლადი. დააყენეთ ცვლადი დადებით მთელ რიცხვზე (დღეების რაოდენობა), რათა ჩართოთ გასუფთავება ამ არტიფაქტის ტიპისთვის. ცვლადის დაუყენებლობა ან ცარიელი დატოვება თიშავს გასუფთავებას მხოლოდ მისი არტიფაქტის ტიპისთვის.

```bash
TUIST_CACHE_ARTIFACT_RETENTION_DAYS=30
TUIST_APP_PREVIEW_RETENTION_DAYS=30
TUIST_BUILD_ARCHIVE_RETENTION_DAYS=60
TUIST_RUN_ARTIFACT_RETENTION_DAYS=30
TUIST_TEST_ATTACHMENT_RETENTION_DAYS=30
TUIST_SHARD_BUNDLE_RETENTION_DAYS=14
```

Helm chart-ით, მოაწყვეთ იგივე ფანჯრები როგორც map:

```yaml
server:
  artifactRetentionDays:
    cacheArtifacts: 30
    appPreviews: 30
    buildArchives: 60
    runArtifacts: 30
    testAttachments: 30
    shardBundles: 14
```

ყველა ექვსი გასაღები არჩევითია. ეს მაგალითი ჩართავს ყველა მხარდაჭერილ არტიფაქტის ტიპს დამოუკიდებელი შენახვის ფანჯრით. გამოტოვეთ გასაღები ან დატოვეთ მისი მნიშვნელობა ცარიელი, რათა გასუფთავება დარჩეს გამორთული ამ არტიფაქტის ტიპისთვის. Self-hosted შენახვის ფანჯრებს არ აქვთ 30-დღიანი მაქსიმუმი. კონფიგურირებული მნიშვნელობები, რომლებიც არ არის დადებითი მთელი რიცხვები, იწვევს სერვერის გაშვებისას შეცდომას.

გადატვირთეთ სერვერი შენახვის ცვლადის შეცვლის შემდეგ. ყოველი რიგში მყოფი self-hosted გასუფთავების ბატჩი ამოწმებს მიმდინარე კონფიგურაციას ფაილების წაშლამდე, ასე რომ ცვლადის გაუქმება ან ცარიელი დატოვება, ან მისი ფანჯრის გაზრდა, ასევე იცავს ფაილებს გადატვირთვის შემდეგ დარჩენილი სამუშაოებისგან.

| გარემოს ცვლადი | არტიფაქტის ფაილები, რომლებიც წაიშლება object storage-დან |
| --- | --- |
| `TUIST_CACHE_ARTIFACT_RETENTION_DAYS` | Xcode cache, legacy content-addressable storage cache, module cache და Gradle cache ფაილები |
| `TUIST_APP_PREVIEW_RETENTION_DAYS` | აპლიკაციის preview აწყობები და ხატულები |
| `TUIST_BUILD_ARCHIVE_RETENTION_DAYS` | მიმდინარე და legacy აწყობის არქივები |
| `TUIST_RUN_ARTIFACT_RETENTION_DAYS` | ყველა ობიექტი, რომელიც შენახულია ვადაგასული run-ის არტიფაქტის პრეფიქსის ქვეშ, მათ შორის შედეგის bundles, გამოძახების ჩანაწერები და სესიის არქივები |
| `TUIST_TEST_ATTACHMENT_RETENTION_DAYS` | ტესტების გაშვება დანართები |
| `TUIST_SHARD_BUNDLE_RETENTION_DAYS` | ტესტის shard bundles |

დაგეგმილი გასუფთავება შლის მხოლოდ არტიფაქტის blobs. ის ინარჩუნებს შესაბამის PostgreSQL და ClickHouse სტრიქონებს, ასე რომ აწყობის, ტესტის, გაშვების, preview და shard მეტამონაცემები შეიძლება დარჩეს ხილული dashboards-ში მათი ჩამოტვირთვების ვადის გასვლის შემდეგაც. ეს კონფიგურაცია არ ცვლის ClickHouse ცხრილის შენახვის წესებს.

##### App-ის რეგისტრაცია {#platform-github-registering-the-app}

[შექმენით GitHub App](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/about-creating-github-apps), რომელიც ეკუთვნის თქვენს GitHub ორგანიზაციას. შეგიძლიათ ხელახლა გამოიყენოთ ავტორიზაციისთვის შექმნილი App, თუ არ შეგიქმნიათ OAuth App. დააკონფიგურირეთ ის შემდეგი პარამეტრებით, ჩაანაცვლეთ `YOUR_APP_URL` მნიშვნელობით `TUIST_APP_URL`-დან:

| გადამისამართება განახლებისას | ჩართულია |

მიანიჭეთ შემდეგი რეპოზიტორიის ნებართვები:

| ნებართვა | წვდომა |
| --- | --- |
| შემცველობა | მხოლოდ კითხვა |
| მეტამონაცემები | მხოლოდ კითხვა |

##### GitHub Enterprise Server {#platform-github-enterprise-server}

ზემოთ მოყვანილი გარემოს ცვლადები მხოლოდ Tuist-ის github.com App-ს აკონფიგურირებენ. Tuist-ის GitHub Enterprise Server (GHES) ეგზემპლართან ინტეგრირებისთვის, ორგანიზაციის ადმინისტრატორები გადადიან ინტეგრაციების გვერდზე **Enterprise server** ჩანართზე და შეჰყავთ GHES-ის საბაზო URL — Tuist მათ GitHub-ის [App manifest flow](https://docs.github.com/en/apps/sharing-github-apps/registering-a-github-app-from-a-manifest)-ში ატარებს, რათა მათ GHES ეგზემპლარზე ახალი Tuist App დარეგისტრირდეს. ახალი App-ის სერთიფიკატები ინახება დაშიფრული თითოეული ინსტალაციისთვის; დამატებითი `TUIST_GITHUB_APP_*` გარემოს ცვლადები არ არის საჭირო.

#### Origin {#platform-origin}

თვითმასპინძელ Tuist სერვერს სჭირდება საკუთარი Origin app, რომელიც კონფიგურირებულია თქვენი განლაგების URL-ებით და ხელმოწერის გასაღებით. დაარეგისტრირეთ ცალკე app თითოეული Tuist გარემოსთვის, რათა ინსტალაციები და სერთიფიკატები დარჩეს დამოუკიდებელი.

##### App-ის რეგისტრაცია {#platform-origin-registering-the-app}

1. გენერირეთ Ed25519 ხელმოწერის გასაღებების წყვილი OpenSSL-ით Ed25519 მხარდაჭერით:

   ```sh
   umask 077
   openssl genpkey -algorithm ED25519 -out origin-app-private.pem
   openssl pkey -in origin-app-private.pem -pubout -out origin-app-public.pem
   ```

2. შექმენით app [Origin app settings](https://cursor.com/codebase/settings/apps)-ში. დაარეგისტრირეთ `origin-app-public.pem`-ის შემცველობა, როგორც მისი საჯარო ხელმოწერის გასაღები. შეინახეთ `origin-app-private.pem` საიდუმლოდ; თქვენ მიაწვდით მას Tuist სერვერს და არ ატვირთავთ Cursor-ზე.
3. კონფიგურირეთ შემდეგი პარამეტრები, `YOUR_APP_URL`-ის ჩანაცვლებით თქვენი Tuist განლაგების HTTPS საბაზო URL-ით:

   | პარამეტრი | მნიშვნელობა |
   | --- | --- |
   | მთავარი გვერდის URL | `YOUR_APP_URL` |
   | გადამისამართების URI | `YOUR_APP_URL/integrations/origin/setup` |
   | Webhook URL | `YOUR_APP_URL/webhooks/origin` |

4. დააკოპირეთ დარეგისტრირებული App ID, რომელიც იწყება `app_`-ით.

ინსტალაციის დროს Tuist ითხოვს შემდეგ ნებართვებს:

| სკოუპი | გამოიყენება |
| --- | --- |
| `repository:pull_requests:read` | მოძებნეთ pull request-ები და მათი მიმდინარე head კომიტი. |
| `repository:pull_requests:reviews:write` | წაიკითხეთ, გამოაქვეყნეთ და განაახლეთ ანგარიშის კომენტარები. Origin შეიცავს შესაბამის review-read ნებართვას. |
| `repository:metadata:read` | აღმოაჩინეთ რეპოზიტორიები და წაიკითხეთ მათი ნაგულისხმები ბრენჩები. ნებართვა გაიცემა ავტომატურად Origin-ის მიერ. |

დატოვეთ არჩეული რეპოზიტორის webhook ღონისძიებები. ინსტალაციის სიცოცხლის ციკლის შეტყობინებები საკმარისია; წყაროს კოდზე წვდომა, merge ნებართვები და check-run ნებართვები არ არის საჭირო.

##### სერვერის კონფიგურაცია {#platform-origin-configuring-the-server}

დააყენეთ შემდეგი გარემოს ცვლადები, შემდეგ გადატვირთეთ სერვერი:

| გარემოს ცვლადი | აღწერა | სავალდებულო | ნაგულისხმები | მაგალითი |
| --- | --- | --- | --- | --- |
| `TUIST_ORIGIN_APP_ID` | App ID, დაკოპირებული Origin app settings-დან. | კი | | `app_...` |
| `TUIST_ORIGIN_APP_PRIVATE_KEY` | `origin-app-private.pem`-ის სრული შემცველობა, `BEGIN PRIVATE KEY` და `END PRIVATE KEY` ხაზების ჩათვლით და ყველა ხაზის გადატანით. | კი | | `-----BEGIN PRIVATE KEY-----...` |

შეინახეთ პირადი გასაღები თქვენი განლაგების საიდუმლო მენეჯერში. შეინარჩუნეთ მისი მრავალხაზიანი PEM ფორმატი; ეს პარამეტრი არ იღებს base64-კოდირებულ ჩანაცვლებას. არასდროს დააკომიტეთ გასაღები წყაროს კონტროლში ან არ გამოააშკარაოთ ის ლოგებში. ორივე ცვლადი უნდა ეკუთვნოდეს ერთსა და იმავე დარეგისტრირებულ app-ს.

თქვენს Tuist სერვერს სჭირდება გამომავალი HTTPS წვდომა `api.cursor.com`-ზე. Cursor-მა უნდა შეძლოს მოთხოვნების მიწოდება webhook URL-ზე, ხოლო ადმინისტრატორებმა უნდა შეძლონ ბრაუზერში redirect URI-ზე დაბრუნება. ორივე დარეგისტრირებული URL უნდა ემთხვეოდეს თქვენი განლაგების HTTPS საბაზო URL-ს.

##### App-ის ინსტალაცია {#platform-origin-installing-the-app}

სერვერის გადატვირთვის შემდეგ, ადმინისტრატორი ხსნის **Settings → Integrations**, ირჩევს **Connect**-ს Origin-ის ქვეშ და ამტკიცებს app-ის წვდომას შესაბამის Origin ანგარიშთან და რეპოზიტორიებთან. Tuist ორგანიზაცია ინახება ამ პროცესის განმავლობაში. პირდაპირ Origin-დან ინიცირებული ინსტალაციების დროს ადმინისტრატორს სთხოვენ შესვლას და Tuist ორგანიზაციის არჩევას დასაკავშირებლად. შემდეგ ისინი ირჩევენ **Add new project connection**-ს Tuist პროექტის ნატიურ რეპოზიტორთან დასაკავშირებლად.

მიჰყევით <.localized_link href="/guides/integrations/gitforge/origin">Origin integration guide</.localized_link> პროექტების დაკავშირებისა და შედეგების ატვირთვის მოთხოვნებისთვის. ## Kubernetes Helm-ით {#kubernetes-with-helm}

Tuist უზრუნველყოფს ოფიციალურ Helm chart-ს Kubernetes-ზე განლაგებისთვის. Chart შეიცავს Tuist სერვერსა და cache სერვისს, ასევე ჩაშენებულ ინფრასტრუქტურულ დამოკიდებულებებს, რომელთა გარე პროვაიდერებით ჩანაცვლება შეგიძლიათ საჭიროებისამებრ.

### Chart-ის ინსტალაცია {#installing-the-chart}

```bash
helm install tuist oci://ghcr.io/tuist/charts/tuist \
  --set server.license.key="YOUR_LICENSE_KEY"
```

კონკრეტული chart ვერსიის დასაფიქსირებლად:

```bash
helm install tuist oci://ghcr.io/tuist/charts/tuist \
  --set server.license.key="YOUR_LICENSE_KEY" \
  --version 0.1.0
```

### ლიცენზია {#helm-license}

`server.license.key` მნიშვნელობა იღებს როგორც სტანდარტულ ლიცენზიის გასაღებს, ასევე, იზოლირებული ინსტალაციებისთვის, Base64-ით კოდირებულ ლიცენზიის სერტიფიკატს; სერვერი ავტომატურად ამოიცნობს, რომელია ის.

ლიცენზიის გადაცემა `--set`-ით მუშაობს სწრაფი ინსტალაციისთვის. თუ თქვენს მნიშვნელობებს version control-ში ინახავთ, შეინახეთ ლიცენზია Kubernetes Secret-ში, რომელსაც Helm-ის გარეთ მართავთ, მაგალითად Vault-ით, Sealed Secrets-ით ან SOPS-ით, და მიუთითეთ chart-ზე:

```yaml
# values.yaml
server:
  license:
    existingSecret: tuist-license
    existingSecretKeys:
      key: TUIST_LICENSE
      certificateBase64: ""
```

ჩანაწერი `existingSecretKeys.key`-ის ქვეშ ასახელებს ველს თქვენს Secret-ში, რომელიც შეიცავს ლიცენზიის მნიშვნელობას, რაც შეიძლება იყოს ლიცენზიის გასაღები ან, იზოლირებული ინსტალაციებისთვის, Base64-ით კოდირებული ლიცენზიის სერტიფიკატი. თითოეული ჩანაწერი `existingSecretKeys`-ის ქვეშ ნაგულისხმევად იღებს chart-ის საკუთარ გასაღების სახელს, ამიტომ დააყენეთ ის ჩანაწერები, რომლებსაც თქვენი Secret არ შეიცავს, ცარიელ სტრინგად, როგორც ზემოთ არის `certificateBase64`. წინააღმდეგ შემთხვევაში pod-ები მიმართავენ არარსებულ გასაღებებს და ვერ გაეშვებიან. შექმენით Secret release namespace-ში chart-ის ინსტალაციამდე ან განახლებამდე.

კონფიგურირეთ ლიცენზია მხოლოდ ერთი წყაროდან: `server.license.key` ან `server.license.existingSecret`. Chart ვერ განიმარტება, თუ არცერთია დაყენებული ან წყაროები გაერთიანებულია. ლიცენზია, რომელიც გადაეცემა `server.extraEnv`-ით, არ ითვლება წყაროდ, ამიტომ გამოიყენეთ `existingSecret`.

### ინფრასტრუქტურული დამოკიდებულებები {#helm-infrastructure-dependencies}

Chart მართავს სამ ინფრასტრუქტურულ დამოკიდებულებას: `postgresql`, `clickhouse` და `objectStorage`. თითოეული ნაგულისხმევად არის **ჩაშენებული** რეჟიმში, რაც ნიშნავს, რომ chart მათ კლასტერში ანაწილებს. თქვენი გარე ეგზემპლარების გამოყენების ნაცვლად, დააყენეთ დამოკიდებულების `mode` მნიშვნელობად `external` და შეავსეთ კავშირის დეტალები თქვენს `values.yaml`-ში. მაგალითად, გარე PostgreSQL მონაცემთა ბაზის გამოყენებისთვის:

```yaml
# values.yaml
postgresql:
  mode: external
  external:
    host: your-db-host
    port: 5432
    database: tuist
    username: tuist
    password: your-password
```

თუ PostgreSQL მონაცემებს Helm-ის გარეთ მართავთ, მიუთითეთ chart-ზე არსებული Kubernetes Secret:

```yaml
# values.yaml
postgresql:
  mode: external
  external:
    port: 5432
    database: tuist
    existingSecret: tuist-postgresql
    existingSecretKeys:
      host: host
      username: username
      password: password
```

Chart კითხულობს host-ს, მომხმარებლის სახელსა და პაროლს Secret-დან და ქმნის `DATABASE_URL`-ს Kubernetes env-var ჩანაცვლების მეშვეობით, ამიტომ პაროლი არ ჩანს Helm manifest-ში. Secret-ის პაროლის მნიშვნელობა უნდა იყოს URL-უსაფრთხო, რადგან ის ჩასმულია მონაცემთა ბაზის URL-ში.

იგივე ნიმუში ვრცელდება `clickhouse`-ზე და `objectStorage`-ზე. სრული კონფიგურირებადი ველების ნახვისთვის იხილეთ `external` ბლოკი chart-ის `values.yaml`-ის თითოეულ სექციაში.

### გაზიარებული დაგეგმვა და ლეიბლები {#helm-shared-scheduling-and-labels}

Chart-ს აქვს პოდების გაზიარებული პარამეტრების მცირე ნაკრები `global`-ის ქვეშ, რაც ოპერატორებს საშუალებას აძლევს შეასაბამონ განლაგება თავიანთ კლასტერთან ყოველი სამუშაოსთვის იგივე მნიშვნელობების გამეორების გარეშე:

```yaml
global:
  podLabels:
    environment: production
  imagePullSecrets:
    - name: ghcr-pull-secret
  nodeSelector:
    nodepool: apps
  tolerations:
    - key: dedicated
      operator: Equal
      value: apps
      effect: NoSchedule
```

გამოიყენეთ ეს პარამეტრები, როდესაც საჭიროა:

- კლასტერის სპეციფიკური ლეიბლების დამატება ყოველ პოდზე
- არეკლილი იმიჯების ჩამოტვირთვა კერძო რეესტრიდან
- მიზნობრივი გამოყოფილი კვანძების პულის (node pool) გამოყენება
- პოდების დაშვება Tuist-ის სამუშაოებისთვის შენახულ tainted კვანძებზე

### სამუშაოების იდენტობა და სერვისის ანგარიშები {#helm-workload-identity}

Chart აკონტროლებს სერვისის ანგარიშებს თითოეული აპლიკაციის სამუშაოს მიხედვით, რათა იდენტობა მიანიჭოთ მხოლოდ იქ, სადაც ის საჭიროა:

- `server.serviceAccount` ვრცელდება Tuist-ის სერვერის განლაგებაზე და მიგრაციის დავალებაზე
- `cache.serviceAccount` ვრცელდება ქეშის განლაგებაზე

მაგალითად, როდესაც ქეში იყენებს გარე S3 ბაკეტს EKS-ზე, შეგიძლიათ ჩართოთ IRSA ქეშის სამუშაოსთვის იმავე IAM როლის ჩაშენებულ მონაცემთა ბაზებზე მიბმის გარეშე:

```yaml
cache:
  serviceAccount:
    create: true
    annotations:
      eks.amazonaws.com/role-arn: arn:aws:iam::123456789012:role/tuist-cache
```

### თავსებადობის გადაფარვები {#helm-compatibility-overrides}

Chart ინახავს შენახვასა და mesh-თან დაკავშირებულ ცვლილებებს opt-in რეჟიმში, რათა ნაგულისხმევი პარამეტრები დარჩეს პორტაბელურად:

```yaml
cache:
  podSecurityContext:
    fsGroup: 990

clickhouse:
  embedded:
    service:
      nativePort: 9100
    systemLogs:
      ttlDays: 7
      supersededTables: delete
      level: warning
```

გამოიყენეთ ეს გადაფარვები მხოლოდ მაშინ, როდესაც თქვენი კლასტერი მოითხოვს მათ:

- `cache.podSecurityContext` ნაგულისხმევად ცარიელია. დააყენეთ `fsGroup`, თუ თქვენს storage class-ს ან CSI დრაივერს სჭირდება საერთო ჯგუფური მფლობელობა მიმაგრებულ ტომებზე.
- `clickhouse.embedded.service.nativePort` ნაგულისხმევად არის ClickHouse-ის სტანდარტული `9000` native სერვისის პორტი და შეიძლება შეიცვალოს, როდესაც სერვისის mesh ან პლატფორმის რეზერვი ეწინააღმდეგება ამ პორტს.
- `clickhouse.embedded.systemLogs.ttlDays` ნაგულისხმევად ცარიელია, რაც ტოვებს ClickHouse-ის შეუზღუდავ შენახვას ჩაშენებულ შიდა ლოგების ცხრილებზე, როგორიცაა `system.text_log`, `system.query_log`, `system.trace_log`, `system.metric_log` და `system.part_log`. მისი დაყენება ერთხელ ანაცვლებს ამ ცხრილებს, ამიტომ მიიღეთ ის `supersededTables: delete`-თან ერთად — იხილეთ <.localized_link href="/guides/server/self-host/server#capping-operational-log-retention">ოპერაციული ლოგების შენახვის შეზღუდვა</.localized_link>.
- `clickhouse.embedded.systemLogs.level` ნაგულისხმევად არის `information` ჩაშენებული ClickHouse სერვერის ლოგერისა და `system.text_log`-ისთვის. `ttlDays`-ისგან განსხვავებით, ის არ არის ნებისმიერი ცხრილის განმარტების ნაწილი, ამიტომ მისი შეცვლა არასდროს ანაცვლებს ცხრილს.
- `clickhouse.embedded.systemLogs.supersededTables` ნაგულისხმევად არის `ignore` და განსაზღვრავს, რა ხდება `<name>_N` ცხრილებთან, რომლებსაც ClickHouse ტოვებს სისტემური ლოგების ცხრილის ჩანაცვლებისას. დააყენეთ ის `delete`-ზე, რათა წაშალოთ ისინი ყოველ `helm upgrade`-ზე.
- `ttlDays`-ისა და `level`-ის ცვლილებები ClickHouse-ის პოდს აღწევს შემდეგი გადატვირთვისას, რადგან ორივე არის `subPath` მიმაგრება და chart არ აკეთებს StatefulSet-ის rolling update-ს, როდესაც მისი ConfigMap იცვლება.

### დაკვირვებადობა {#helm-observability}

Chart მოიცავს დაკვირვებადობის სტეკის (OpenTelemetry Collector, Prometheus, Grafana, Loki და Tempo) არჩევით ვარიანტს. ის ნაგულისხმევად **გამორთულია**. მის ჩასართავად თქვენს `values.yaml`-ში:

```yaml
# values.yaml
observability:
  enabled: true
```

ჩართვისას, Grafana ხელმისაწვდომია წინასწარ კონფიგურირებული Logs, Traces და Metrics drilldown-ებით. გარე დაკვირვებადობისთვის, დატოვეთ ეს გამორთული და კონფიგურირეთ endpoint-ები `server.extraEnv`-ის მეშვეობით:

```yaml
# values.yaml
server:
  extraEnv:
    - name: TUIST_OTEL_EXPORTER_OTLP_ENDPOINT
      value: "http://your-otel-collector:4317"
    - name: TUIST_LOKI_URL
      value: "http://your-loki:3100"
```

### მნიშვნელობების ცნობარი {#helm-values-reference}

კონფიგურირებადი მნიშვნელობების სრული სიისთვის, იხილეთ chart-ის [`values.yaml`](https://github.com/tuist/tuist/blob/main/infra/helm/tuist/values.yaml).

## განლაგება {#deployment}

Tuist-ის ოფიციალური Docker იმიჯი ხელმისაწვდომია:
```
ghcr.io/tuist/tuist
```

გამოქვეყნებული იმიჯი მოიცავს ჩაშენებულ Linux ბილდის დამუშავებას `.xcactivitylog` არქივებისთვის, ასე რომ self-hosted განლაგებებს შეუძლიათ ბილდების დამუშავება დამატებითი სერვისის გაშვების გარეშე — `ProcessBuildWorker` Oban დავალება მუშაობს პროცესში თითოეულ სერვერის პოდზე. თუ გსურთ ბილდის დამუშავება გადაიტანოთ გამოყოფილ replica set-ზე (მაგალითად, parsing-ის throughput-ის მასშტაბირება web tier-ისგან დამოუკიდებლად), დააყენეთ `processor.enabled: true` Helm chart-ში: chart ანაწილებს იმავე იმიჯს, როგორც მხოლოდ რიგის მომხმარებელს (`TUIST_PROCESSOR_MODE=true`). სრული კონფიგურაციის პარამეტრების ნახვისთვის იხილეთ [`values.yaml`](https://github.com/tuist/tuist/blob/main/infra/helm/tuist/values.yaml).

> [!NOTE]
> `.xcresult` parsing ეყრდნობა Xcode-ის `xcresulttool`-ს, ამიტომ მას შეუძლია მუშაობა მხოლოდ macOS-ზე. CLI გამჭვირვალედ უმკლავდება ამას self-hosted განლაგებებისთვის: `tuist test` ნაგულისხმევად არის **ლოკალური** დამუშავების რეჟიმი ნებისმიერი არა-`tuist.dev` სერვერის წინააღმდეგ, ახდენს xcresult-ის პარსინგს დეველოპერის მანქანაზე (რომელსაც უკვე აქვს Xcode ბილდისთვის) და ატვირთავს სტრუქტურირებულ შედეგებს. ტესტის შედეგები შედის სისტემაში დამატებითი ინფრასტრუქტურის გარეშე.

### Docker იმიჯის ჩამოტვირთვა {#pulling-the-docker-image}

იმიჯის მიღება შეგიძლიათ შემდეგი ბრძანების შესრულებით:

```bash
docker pull ghcr.io/tuist/tuist:latest
```

იმიჯი გამოქვეყნებულია როგორც `linux/amd64`-ისთვის, ასევე `linux/arm64`-ისთვის, ამიტომ Docker ავტომატურად ირჩევს ჰოსტისთვის ნატიურ Linux არქიტექტურას.

ან ჩამოტვირთეთ კონკრეტული ვერსია:
```bash
docker pull ghcr.io/tuist/tuist:0.1.0
```

### Docker იმიჯის განლაგება {#deploying-the-docker-image}

Docker იმიჯის განლაგების პროცესი განსხვავდება თქვენი არჩეული cloud პროვაიდერისა და თქვენი ორგანიზაციის უწყვეტი განლაგების მიდგომის მიხედვით. ვინაიდან cloud გადაწყვეტილებებისა და ინსტრუმენტების უმეტესობა, როგორიცაა [Kubernetes](https://kubernetes.io/), იყენებს Docker იმიჯებს, როგორც ფუნდამენტურ ერთეულებს, ამ სექციაში მოცემული მაგალითები კარგად შეესაბამება თქვენს არსებულ კონფიგურაციას.

> [!WARNING]
> თუ თქვენს განლაგების pipeline-ს სჭირდება სერვერის მუშაობის ვალიდაცია, შეგიძლიათ გაგზავნოთ `GET` HTTP მოთხოვნა `/ready`-ზე და დააფიქსიროთ `200` სტატუსის კოდი პასუხში.


#### Fly {#fly}

აპლიკაციის [Fly](https://fly.io/)-ზე განსალაგებლად, დაგჭირდებათ `fly.toml` კონფიგურაციის ფაილი. გაითვალისწინეთ მისი დინამიურად გენერირება თქვენს Continuous Deployment (CD) pipeline-ში. ქვემოთ მოცემულია საცნობარო მაგალითი თქვენი გამოყენებისთვის:

```toml
app = "tuist"
primary_region = "fra"
kill_signal = "SIGINT"
kill_timeout = "5s"

[experimental]
  auto_rollback = true

[env]
  # Your environment configuration goes here
  # Or exposed through Fly secrets

[processes]
  app = "/usr/local/bin/hivemind /app/Procfile"

[[services]]
  protocol = "tcp"
  internal_port = 8080
  auto_stop_machines = false
  auto_start_machines = false
  processes = ["app"]
  http_options = { h2_backend = true }

  [[services.ports]]
    port = 80
    handlers = ["http"]
    force_https = true

  [[services.ports]]
    port = 443
    handlers = ["tls", "http"]
  [services.concurrency]
    type = "connections"
    hard_limit = 100
    soft_limit = 80

  [[services.http_checks]]
    interval = 10000
    grace_period = "10s"
    method = "get"
    path = "/ready"
    protocol = "http"
    timeout = 2000
    tls_skip_verify = false
    [services.http_checks.headers]

[[statics]]
  guest_path = "/app/public"
  url_prefix = "/"
```

შემდეგ შეგიძლიათ გაუშვათ `fly launch --local-only --no-deploy` აპლიკაციის გასაშვებად. მომდევნო განლაგებებზე, `fly launch --local-only`-ის გაშვების ნაცვლად, დაგჭირდებათ `fly deploy --local-only`-ის გაშვება. Fly.io არ იძლევა კერძო Docker იმიჯების ჩამოტვირთვის საშუალებას, რის გამოც უნდა გამოვიყენოთ `--local-only` ფლაგი.


## Prometheus მეტრიკები {#prometheus-metrics}

Tuist გთავაზობთ Prometheus მეტრიკებს `/metrics`-ზე, რათა დააკვირდეთ თქვენს self-hosted ინსტანციას. ეს მეტრიკები მოიცავს:

### Finch HTTP კლიენტის მეტრიკები {#finch-metrics}

Tuist იყენებს [Finch](https://github.com/sneako/finch)-ს, როგორც HTTP კლიენტს და გთავაზობთ დეტალურ მეტრიკებს HTTP მოთხოვნების შესახებ:

#### მოთხოვნის მეტრიკები
- `tuist_prom_ex_finch_request_count_total` - Finch მოთხოვნების საერთო რაოდენობა (მრიცხველი)
  - ლეიბლები: `finch_name`, `method`, `scheme`, `host`, `port`, `status`
- `tuist_prom_ex_finch_request_duration_milliseconds` - HTTP მოთხოვნების ხანგრძლივობა (ჰისტოგრამა)
  - ლეიბლები: `finch_name`, `method`, `scheme`, `host`, `port`, `status`
  - ბაკეტები: 10ms, 50ms, 100ms, 250ms, 500ms, 1s, 2.5s, 5s, 10s
- `tuist_prom_ex_finch_request_exception_count_total` - Finch მოთხოვნის გამონაკლისების საერთო რაოდენობა (მრიცხველი)
  - ლეიბლები: `finch_name`, `method`, `scheme`, `host`, `port`, `kind`, `reason`

#### კავშირის პულის რიგის მეტრიკები
- `tuist_prom_ex_finch_queue_duration_milliseconds` - კავშირის პულის რიგში ლოდინის დრო (ჰისტოგრამა)
  - ლეიბლები: `finch_name`, `scheme`, `host`, `port`, `pool`
  - ბაკეტები: 1ms, 5ms, 10ms, 25ms, 50ms, 100ms, 250ms, 500ms, 1s
- `tuist_prom_ex_finch_queue_idle_time_milliseconds` - დრო, როდესაც კავშირი უმოქმედო იყო გამოყენებამდე (ჰისტოგრამა)
  - ლეიბლები: `finch_name`, `scheme`, `host`, `port`, `pool`
  - ბაკეტები: 10ms, 50ms, 100ms, 250ms, 500ms, 1s, 5s, 10s
- `tuist_prom_ex_finch_queue_exception_count_total` - Finch რიგის გამონაკლისების საერთო რაოდენობა (მრიცხველი)
  - ლეიბლები: `finch_name`, `scheme`, `host`, `port`, `kind`, `reason`

#### კავშირის მეტრიკები
- `tuist_prom_ex_finch_connect_duration_milliseconds` - კავშირის დამყარებისთვის დახარჯული დრო (ჰისტოგრამა)
  - ლეიბლები: `finch_name`, `scheme`, `host`, `port`, `error`
  - ბაკეტები: 10ms, 50ms, 100ms, 250ms, 500ms, 1s, 2.5s, 5s
- `tuist_prom_ex_finch_connect_count_total` - კავშირის მცდელობების საერთო რაოდენობა (მრიცხველი)
  - ლეიბლები: `finch_name`, `scheme`, `host`, `port`

#### გაგზავნის მეტრიკები
- `tuist_prom_ex_finch_send_duration_milliseconds` - მოთხოვნის გაგზავნისთვის დახარჯული დრო (ჰისტოგრამა)
  - ლეიბლები: `finch_name`, `method`, `scheme`, `host`, `port`, `error`
  - ბაკეტები: 1ms, 5ms, 10ms, 25ms, 50ms, 100ms, 250ms, 500ms, 1s
- `tuist_prom_ex_finch_send_idle_time_milliseconds` - დრო, როდესაც კავშირი უმოქმედო იყო გაგზავნამდე (ჰისტოგრამა)
  - ლეიბლები: `finch_name`, `method`, `scheme`, `host`, `port`, `error`
  - ბაკეტები: 1ms, 5ms, 10ms, 25ms, 50ms, 100ms, 250ms, 500ms

ყველა ჰისტოგრამის მეტრიკა გთავაზობთ `_bucket`, `_sum` და `_count` ვარიანტებს დეტალური ანალიზისთვის.

### სხვა მეტრიკები

Finch მეტრიკების გარდა, Tuist გთავაზობთ მეტრიკებს:
- BEAM ვირტუალური მანქანის წარმადობა
- მომხმარებლის ბიზნეს-ლოგიკის მეტრიკები (შენახვა, ანგარიშები, პროექტები და ა.შ.)

> [!WARNING]
> **ავტორიზაცია**
