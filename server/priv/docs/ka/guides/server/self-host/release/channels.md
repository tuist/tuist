# გამოშვების არხები {#release-channels}

Tuist-ის სერვერი და Kura-ს ქეშის სერვერი ვრცელდება GHCR-ის სამი გამოსახულების არხის მეშვეობით, რომლებსაც განსხვავებული სტაბილურობის გარანტიები აქვთ. რეკომენდებული ინსტალაციაა **stable**, რომელიც კვირაში ერთხელ გადაინაცვლებს: ის არ ადიანს ყოველ ჯერზე, როცა ფუნქცია ერწყმება `main`-ში, ამიტომ განახლება აღარ ნიშნავს დაკავშირებულ ცვლილებების პაკეტის შეთვისებას. ადრეული მომხმარებლები მაინც შეუძლიათ გაუშვან კომიტზე დაფუძნებული ბილდები **canary**-ზე, ხოლო **release candidate** არხი საშუალებას გაძლევთ წინასწარ შეამოწმოთ მომავალი ხაზი, სანამ ის სტაბილური გახდება.

სერვერი და Kura ერთსა და იმავე კვირეულ „მატარებელს“ მიჰყვებიან და ორივე სინქრონულად ემთხვევა <.localized_link href="/cli/release/channels">Tuist CLI-ის გამოშვების გრაფიკს</.localized_link>.

## მიმდინარე გამოშვებები {#live-release-status}

თითოეული კომპონენტის მიმდინარე გამოშვებები ნაჩვენებია ქვემოთ. მომავალი ფანჯრებისა და ბოლოდროინდელი გამოშვებების, მათ შორის პატჩებისა და ბექპორტების სანახავად, იხილეთ <.localized_link href="/guides/server/self-host/release/calendar">გამოშვების კალენდარი</.localized_link>.

## არხები {#the-channels}

| არხი | ვერსიის ფორმატი | სიხშირე | გადადის `:latest`? |
| --- | --- | --- | --- |
| Canary | `X.Y.0-canary.N` (მაგ., `1.351.0-canary.5`) | ყოველი კომიტი `main`-ში | არა, მხოლოდ ცხადად ჩართვის შემთხვევაში |
| Release candidate | `X.Y.0-rc.N` (მაგ., `1.351.0-rc.1`) | ჭრა `main`-დან ყოველ ორშაბათს, ~1 კვირა სიმშრალე | არა, მხოლოდ ცხადად ჩართვის შემთხვევაში |
| Stable | `X.Y.Z` (მაგ., `1.350.2`, `1.351.0`) | ყოველ ორშაბათს პრომოცია სუფთა სიმშრალის შემდეგ | **კი** |

Canary-სა და release-candidate-ის ბილდები ქვეყნდება GitHub-ის პრერელიზებად. ნებისმიერი ინსტრუმენტი, რომელიც გამორიცხავს პრერელიზებს `:latest`-ის რეზოლუციის დროს, გამოტოვებს მათ, ამიტომ მათზე მოხვდებით მხოლოდ მაშინ, როცა ცხადად მოითხოვთ.

### Canary {#canary}

ყოველი კომიტი `main`-ში აქვეყნებს canary-ის გამოსახულებას. Canary ყოველთვის წარმოადგენს **შემდეგ გამოუშვებელ მინორულ ვერსიას**: როგორც კი ხაზი გამოშვებისთვის იჭრება, `main` გადადის შემდეგ მინორულზე (მაგალითად, `1.350.0-canary.42`-დან `1.351.0-canary.1`-მდე). Canary სწორი არხია სტეიჯინგის გარემოსთვის, რომელიც ასახავს პროდაქშენს და გაძლევთ რეგრესიებზე ყველაზე ადრეულ სიგნალს, ან იმის დასადასტურებლად, რომ თქვენს მიერ შეტყობინებული შესწორება მოქმედებს მოსალოდნელად, სანამ ის stable-ს მიაღწევს.

```
ghcr.io/tuist/tuist:1.351.0-canary.5
ghcr.io/tuist/kura:0.55.0-canary.5
```

### Release candidate {#release-candidate}

როცა მინორული ვერსია მზადაა გამოშვებისთვის, მისი ხაზი იყინება დაცულ `releases/server-<major>.<minor>.x` (ან `releases/kura-<major>.<minor>.x`) ბრენჩზე და ქვეყნდება როგორც `X.Y.0-rc.1`. ხაზი ფუნქციურად გაყინულია; მასზე მხოლოდ კრიტიკული შესწორებები და რეგრესიები აირჩევა cherry-pick-ით, და ყოველი მიღებული შესწორება აუმჯობესებს release candidate-ს (`-rc.2`, `-rc.3` და ა.შ.). სუფთა სიმშრალის პერიოდის დასრულების შემდეგ, ხაზი მომდევნო ორშაბათს პრომოცირდება stable-ად.

```
ghcr.io/tuist/tuist:1.351.0-rc.1
ghcr.io/tuist/kura:0.55.0-rc.1
```

### Stable {#stable}

Stable რეკომენდებული არხია და ყველა დოკუმენტაცია მასზე მიუთითებს. სტაბილური მინორული ვერსია (`X.Y.0`) ქვეყნდება მხოლოდ მაშინ, როცა release candidate-მა სუფთად გაიარა სიმშრალე, და ის **არ** ადიანს, როცა ახალი ფუნქციები ერწყმება `main`-ში. პატჩები (`X.Y.1`, `X.Y.2` და ა.შ.) სტაბილურ ხაზზე შეიცავს მხოლოდ ბექპორტებულ შესწორებებს, არასდროს ახალ ფუნქციებს. `:latest` გადადის მხოლოდ სტაბილურ პრომოციაზე.

```
ghcr.io/tuist/tuist:1.351.0
ghcr.io/tuist/kura:0.55.0
ghcr.io/tuist/tuist:latest
ghcr.io/tuist/kura:latest
```

## ორშაბათის მატარებელი {#the-monday-train}

ყოველ ორშაბათს 06:00 UTC-ზე, სამი კომპონენტის გამოშვების მატარებლები სინქრონულად იწყება:

1. **06:00 UTC** — პრომოციის ჯობები გადის. თითოეული აკეთებს პრომოციას უახლესი release-candidate ხაზისა, რომელიც ჯერ არ არის სტაბილური (ჩვეულებრივ, წინა ორშაბათს მოჭრილი ხაზი) და არაფერს აკეთებს, თუ ასეთი არ არსებობს.
2. **ყოველი პრომოციის დასრულების შემდეგ** — release-candidate ჯობი ჭრის შემდეგ ხაზს `main`-დან, ამიტომ ახლადმოჭრილი ხაზი არასდროს პრომოცირდება იმავე გაშვებაში.

ჩაშლილი პრომოცია აკავებს ჭრას: ყოველთვის ირჩევა მხოლოდ უმაღლესი release-candidate ხაზი უახლეს სტაბილურზე, ამიტომ შემდეგი ხაზის ჭრა ჩაშლის თავზე დატოვებს იმას, რომელიც არ გამოვიდა. მომდევნო ორშაბათს შეკავებული ხაზი ავტომატურად თავიდან სცდება.

## არხის მიმაგრება {#pinning-a-channel}

მიამაგრეთ სასურველი კონკრეტული ტეგი თქვენს დეპლოიმენტის მანიფესტში, Helm-ის მნიშვნელობებში ან Docker Compose-ის ფაილში. მაგალითი, Helm-ის ჩარტის გამოყენებით:

```yaml
server:
  image:
    repository: ghcr.io/tuist/tuist
    tag: "1.350.2"          # Pinned to a stable patch
    # tag: "1.351.0-rc.1"   # Or opt into a release candidate to soak it
    # tag: "1.351.0-canary.5" # Or opt into a specific canary build

kuraRuntime:
  image:
    repository: ghcr.io/tuist/kura
    tag: "0.54.0"           # Same three channels apply to Kura
```

`:latest` ორივეზე `ghcr.io/tuist/tuist` და `ghcr.io/tuist/kura` თვალყურს ადევნებს უახლეს სტაბილურს, რომელიც გადადის მხოლოდ ორშაბათის პრომოციაზე. `:latest`-ის მიმაგრება გაძლევთ კვირეულ სტაბილურ სიხშირეს ტეგის განახლების გარეშე; კონკრეტული ვერსიის მიმაგრება გაძლევთ სრულ კონტროლს განახლების დროზე.

## რეკომენდებული სტრატეგია {#recommended-strategy}

არხები არსებობს იმისთვის, რომ „უახლესი შესწორებების მიღება“ გააცალკევოთ „უახლესი ფუნქციების მიღებისგან“. უსაფრთხო, დაბალი ძალისხმევის ნაგულისხმევი ვარიანტია:

1. **მიამაგრეთ პროდაქშენი სტაბილურ მინორულ ხაზზე**, მაგალითად `ghcr.io/tuist/tuist:1.351`. ეს ხაზი იღებს მხოლოდ ბექპორტებულ შესწორებებს, არასდროს ახალ ფუნქციებს, ამიტომ ყოველდღიური განახლებები დაბალი რისკისაა. გაზარდეთ მიმაგრება, როცა მზად იქნებით შემდეგი მინორულის ათვისებისთვის.
2. **გაუშვით სტეიჯინგის გარემო canary-ზე ან კონკრეტულ release-candidate ტეგზე.** სტეიჯინგი იჭერს რეგრესიებს, რომლებიც წინააღმდეგ შემთხვევაში თქვენს მომხმარებლებს მიაღწევდნენ, და რაც უფრო ახლოს არის `main`-თან სტეიჯინგის ტრეკი, მით უფრო ადრე აღმოაჩენთ მათ. მიმდინარე release-candidate ხაზზე სტეიჯინგის გარემო კარგი შუალედური ვარიანტია: ის ამოწმებს ზუსტად იმ ბაიტებს, რომლებიც მომავალ ორშაბათს სტაბილური გახდება.
3. **მიჰყევით [სერვერის ცვლილებების ჟურნალს](/changelog), რათა ნახოთ, რა გამოვიდა რეალურად.** ყოველი სტაბილური პრომოცია აქ ცხადდება იმ pull request-ების სიით, რომლებიც შევიდა.

თუ გირჩევნიათ, რომ ახალი ფუნქციები ავტომატურად გადავიდეს პროდაქშენში, როგორც კი სტაბილური გახდებიან, პროდაქშენი დატოვეთ `:latest`-ზე. უბრალოდ გაითვალისწინეთ, რომ ტეგი ყოველ ორშაბათ დილით გადადის, ამიტომ შესაბამისად დაგეგმეთ დეპლოიმენტის ფანჯარა.

## ბექპორტები {#backports}

ნებისმიერ დროს აქტიურად მხარდაჭერილია ორი სტაბილური სერვერის (და Kura-ს) ხაზი: მიმდინარე ხაზი იღებს რეგრესიებსა და უსაფრთხოების შესწორებებს ბექპორტის pull request-ების სახით, ხოლო წინა ხაზი — მხოლოდ კრიტიკულ და უსაფრთხოების შესწორებებს. ძველ ხაზებს ბექპორტები არ უკეთდებათ; შესწორებების მიღებისთვის გადადით მხარდაჭერილ ხაზზე. როდესაც ახალი ხაზი პრომოცირდება სტაბილურად, მიმდინარე ხაზი ხდება „წინა“, ხოლო „წინა“ ხაზი წყვეტს ბექპორტების მიღებას.

ბექპორტები იჭრება მოთხოვნის შესაბამისად `X.Y.(Z+1)` პატჩ-გამოშვებების სახით. ისინი არასდროს გადაადგილებენ `:latest`-ს.
