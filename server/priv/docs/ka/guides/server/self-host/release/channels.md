# გამოშვების არხები {#release-channels}

Tuist-ის სერვერი და Kura-ს ქეშის სერვერი ვრცელდება GHCR-ის სამი სახის იმიჯის არხით, რომლებსაც განსხვავებული სტაბილურობის გარანტიები აქვთ. რეკომენდებული ინსტალაციაა **stable**, რომელიც კვირაში ერთხელ ახლდება: ის არ გადადის წინ ყოველ ჯერზე, როცა ფუნქცია ერწყმება `main`-ს, ამიტომ განახლება აღარ ნიშნავს არასაკავშირო ცვლილებების პაკეტის მიღებას. ადრეულმა მომხმარებლებს შეუძლიათ გაუშვან კომიტზე დაფუძნებული ბილდები **canary**-ზე, ხოლო **release candidate** არხი საშუალებას გაძლევთ წინასწარ შეამოწმოთ მომავალი ხაზი, სანამ ის სტაბილური გახდება.

სერვერი და Kura ერთსა და იმავე კვირეულ მატარებელზე მოძრაობენ და ორივე სინქრონიზირებულად მოქმედებს <.localized_link href="/cli/release/channels">Tuist CLI-ის გამოშვების გრაფიკთან</.localized_link>.

## მიმდინარე გამოშვებები {#live-release-status}

ქვემოთ ნაჩვენებია თითოეული კომპონენტის მიმდინარე გამოშვებები. მომავალი ფანჯრებისა და ბოლო დროის გამოშვებების, მათ შორის პატჩებისა და ბექპორტების სანახავად, იხილეთ <.localized_link href="/guides/server/self-host/release/calendar">გამოშვების კალენდარი</.localized_link>.

## არხები {#the-channels}

| არხი | ვერსიის ფორმატი | სიხშირე | აახლებს `:latest`-ს? |
| --- | --- | --- | --- |
| Canary | `X.Y.0-canary.N` (მაგ., `1.351.0-canary.5`) | ყოველი კომიტი `main`-ზე | არა, მხოლოდ ცხადი opt-in |
| Release candidate | `X.Y.0-rc.N` (მაგ., `1.351.0-rc.1`) | ჭრა `main`-დან ყოველ ორშაბათს, ტესტირება ~1 კვირა | არა, მხოლოდ ცხადი opt-in |
| Stable | `X.Y.Z` (მაგ., `1.350.2`, `1.351.0`) | წინ წაწევა ყოველ ორშაბათს წარმატებული ტესტირების შემდეგ | **დიახ** |

Canary-სა და release-candidate ბილდები ქვეყნდება GitHub-ის prerelease-ებად. ნებისმიერი ინსტრუმენტი, რომელიც გამორიცხავს prerelease-ებს `:latest`-ის რეზოლუციისას, გამოტოვებს მათ, ამიტომ მათზე მოხვედრა მხოლოდ ცხადი მოთხოვნით არის შესაძლებელი.

### Canary {#canary}

ყოველი კომიტი `main`-ზე აქვეყნებს canary იმიჯს. Canary ყოველთვის წარმოადგენს **შემდეგ გამოუქვეყნებელ მინორს**: როგორც კი ხაზი გამოშვებისთვის მომზადდება, `main` გადადის შემდეგ მინორზე (მაგალითად, `1.350.0-canary.42`-დან `1.351.0-canary.1`-მდე). Canary სწორი არხია staging გარემოსთვის, რომელიც ასახავს პროდაქშენს და გაძლევთ რეგრესიების შესახებ უადრეს სიგნალს, ან საშუალებას გაძლევთ შეამოწმოთ, რომ თქვენს მიერ შეტყობინებული გამოსწორება მოქმედებს მოსალოდნელად, სანამ ის stable-ში მოხვდება.

```
ghcr.io/tuist/tuist:1.351.0-canary.5
ghcr.io/tuist/kura:0.55.0-canary.5
```

### Release candidate {#release-candidate}

როდესაც მინორი მზადაა გამოშვებისთვის, მისი ხაზი იყინება დაცულ `releases/server-<major>.<minor>.x` (ან `releases/kura-<major>.<minor>.x`) ბრენჩზე და ქვეყნდება როგორც `X.Y.0-rc.1`. ხაზი ფუნქციებით გაყინულია; მასზე cherry-pick-ით ემატება მხოლოდ კრიტიკული გამოსწორებები და რეგრესიები, ხოლო თითოეული მიღებული გამოსწორება ზრდის release candidate-ის ნომერს (`-rc.2`, `-rc.3` და ა.შ.). ტესტირების პერიოდის წარმატებით დასრულების შემდეგ, ხაზი მომდევნო ორშაბათს stable-ში გადადის.

```
ghcr.io/tuist/tuist:1.351.0-rc.1
ghcr.io/tuist/kura:0.55.0-rc.1
```

### Stable {#stable}

Stable რეკომენდებული არხია და ყველა დოკუმენტაცია მასზე მიუთითებს. სტაბილური მინორი (`X.Y.0`) ქვეყნდება მხოლოდ მაშინ, როცა release candidate წარმატებით გაივლის ტესტირებას, და ის **არ** გადადის წინ, როცა ახალი ფუნქციები ერწყმება `main`-ს. პატჩები (`X.Y.1`, `X.Y.2` და ა.შ.) სტაბილურ ხაზზე შეიცავს მხოლოდ ბექპორტებულ გამოსწორებებს, არასდროს ახალ ფუნქციებს. `:latest` გადადის წინ მხოლოდ სტაბილურად წაწევისას.

```
ghcr.io/tuist/tuist:1.351.0
ghcr.io/tuist/kura:0.55.0
ghcr.io/tuist/tuist:latest
ghcr.io/tuist/kura:latest
```

## ორშაბათის მატარებელი {#the-monday-train}

ყოველ ორშაბათს 06:00 UTC-ზე, სამი კომპონენტის გამოშვების მატარებლები სინქრონიზირებულად მოქმედებენ:

1. **06:00 UTC** — promote-ის ჯობები იწყება. თითოეული აწინაურებს უახლეს release-candidate ხაზს, რომელიც ჯერ არ არის სტაბილური (ჩვეულებრივ, წინა ორშაბათს მომზადებულ ხაზს) და არაფერს აკეთებს, თუ ასეთი არ არის.
2. **ყოველი promote-ის დასრულების შემდეგ** — release-candidate ჯობი ჭრის შემდეგ ხაზს `main`-დან, ამიტომ ახლად მომზადებული ხაზი იმავე გაშვებაში არ წაიწევს წინ.

წარუმატებელი promote აჩერებს ჭრას: ირჩევა მხოლოდ უმაღლესი release-candidate ხაზი უახლეს stable-ზე, ამიტომ შემდეგი ხაზის ჭრა წარუმატებლობის ფონზე დატოვებდა იმას, რომელიც არ გამოქვეყნდა. მომდევნო ორშაბათს შეჩერებული ხაზი ავტომატურად თავიდან ცდება.

## არხის მიმაგრება {#pinning-a-channel}

მიამაგრეთ სასურველი კონკრეტული ტეგი თქვენს განლაგების მანიფესტში, Helm-ის მნიშვნელობებში ან Docker Compose ფაილში. მაგალითი, Helm chart-ის გამოყენებით:

```yaml
server:
  image:
    repository: ghcr.io/tuist/tuist
    tag: "1.350.2"          # Pinned to a stable patch
    # tag: "1.351.0-rc.1"   # Or opt into a release candidate to soak it
    # tag: "1.351.0-canary.5" # Or opt into a specific canary build

kuraRuntime:
  image:
    repository: ghcr.io/tuist/kura
    tag: "0.54.0"           # Same three channels apply to Kura
```

`:latest` როგორც `ghcr.io/tuist/tuist`-ზე, ისე `ghcr.io/tuist/kura`-ზე მიჰყვება უახლეს სტაბილურს, რომელიც გადადის წინ მხოლოდ ორშაბათის წაწევისას. `:latest`-ის მიმაგრება გაძლევთ კვირეულ სტაბილურ სიხშირეს ტეგის განახლების გარეშე; კონკრეტული ვერსიის მიმაგრება გაძლევთ სრულ კონტროლს განახლების დროზე.

## რეკომენდებული სტრატეგია {#recommended-strategy}

არხები არსებობს იმისთვის, რომ "უახლესი გამოსწორებების მიღება" გამოყოთ "უახლესი ფუნქციების მიღებისგან". უსაფრთხო, მცირე ძალისხმევის მომთხოვნი ნაგულისხმები ვარიანტია:

1. **მიამაგრეთ პროდაქშენი სტაბილურ მინორ ხაზზე**, მაგალითად `ghcr.io/tuist/tuist:1.351`. ეს ხაზი იღებს მხოლოდ ბექპორტებულ გამოსწორებებს, არასდროს ახალ ფუნქციებს, ამიტომ ყოველდღიური განახლებები დაბალი რისკის მქონე რჩება. გაზარდეთ მიმაგრება, როცა მზად იქნებით შემდეგი მინორის ასაღებად.
2. **გაუშვით სტეიჯინგის გარემო canary-ზე ან კონკრეტულ release-candidate ტეგზე.** სტეიჯინგი იჭერს რეგრესიებს, რომლებიც წინააღმდეგ შემთხვევაში თქვენს მომხმარებლებამდე მიაღწევდნენ, და რაც უფრო ახლოსაა სტეიჯინგი `main`-თან, მით უფრო ადრე აღმოაჩენთ მათ. მიმდინარე release-candidate ხაზზე განლაგებული სტეიჯინგის გარემო კარგი შუალედური ვარიანტია: ის ამოწმებს ზუსტად იმ ბაიტებს, რომლებიც მომავალ ორშაბათს სტაბილური გახდება.
3. **მიჰყევით [სერვერის ცვლილებების ჟურნალს](/changelog), რათა ნახოთ, რა გამოქვეყნდა რეალურად.** ყოველი სტაბილური წაწევა აქ анонсируется pull request-ების სიით, რომლებიც შევიდა.

თუ გირჩევნიათ, რომ ახალი ფუნქციები პროდაქშენში ავტომატურად გადავიდეს, როგორც კი სტაბილური გახდება, პროდაქშენი დატოვეთ `:latest`-ზე. უბრალოდ გაითვალისწინეთ, რომ ტეგი ყოველ კვირას, ორშაბათ დილით გადადის წინ, ამიტომ შესაბამისად დაგეგმეთ განლაგების ფანჯარა.

## ბექპორტები {#backports}

ნებისმიერ დროს აქტიურად მხარდაჭერილია ორი სტაბილური სერვერის (და Kura-ს) ხაზი: მიმდინარე ხაზი იღებს რეგრესიებსა და უსაფრთხოების გამოსწორებებს ბექპორტის pull request-ების სახით, ხოლო წინა ხაზი იღებს მხოლოდ კრიტიკულ და უსაფრთხოების გამოსწორებებს. ძველ ხაზებს ბექპორტი არ უკეთდებათ; განაახლეთ მხარდაჭერილ ხაზზე გამოსწორებების მისაღებად. როდესაც ახალი ხაზი გადადის სტაბილურში, მიმდინარე ხაზი ხდება „წინა“, ხოლო „წინა“ ხაზი წყვეტს ბექპორტების მიღებას.

ბექპორტები იჭრება მოთხოვნის შესაბამისად `X.Y.(Z+1)` პატჩ რელიზების სახით. ისინი არასდროს გადააადგილებენ `:latest`-ს.
