# გამოშვების არხები {#release-channels}

Tuist-ის სერვერი და Kura-ს ქეშირების სერვერი ვრცელდება GHCR-ის სამი იმიჯის არხის მეშვეობით, რომლებსაც სტაბილურობის განსხვავებული გარანტიები აქვთ. რეკომენდებული ინსტალაციაა **stable**, რომელიც კვირაში ერთხელ გადაინაცვლებს: ის არ მოძრაობს ყოველ ჯერზე, როცა ფუნქცია ერწყმება `main`-ს, ამიტომ განახლება აღარ ნიშნავს შეუსაბამო ცვლილებების პაკეტის შთანთქმას. ადრეულმა მომხმარებლებს შეუძლიათ გაუშვან კომიტზე დაფუძნებული ბილდები **canary**-ზე, ხოლო **release candidate** არხი საშუალებას გაძლევთ წინასწარ შეამოწმოთ მომავალი ხაზი, სანამ ის სტაბილური გახდება.

სერვერი და Kura ერთსა და იმავე კვირეულ „მატარებელს“ ემყარებიან და ორივე მოქმედებს სინქრონულად [Tuist CLI-ის გამოშვების გრაფიკთან](/en/cli/release-channels).

## არხები {#the-channels}

| არხი | ვერსიის ფორმატი | სიხშირე | გადადის `:latest`? |
| --- | --- | --- | --- |
| Canary | `X.Y.0-canary.N` (მაგ., `1.351.0-canary.5`) | ყოველი კომიტი `main`-ზე | არა, მხოლოდ ცალსახა ჩართვისას |
| Release candidate | `X.Y.0-rc.N` (მაგ., `1.351.0-rc.1`) | ჭრა `main`-დან ყოველ ორშაბათს, ტესტირება ~1 კვირა | არა, მხოლოდ ცალსახა ჩართვისას |
| Stable | `X.Y.Z` (მაგ., `1.350.2`, `1.351.0`) | წინ წაწევა ყოველ ორშაბათს წარმატებული ტესტირების შემდეგ | **კი** |

Canary და release-candidate ბილდები ქვეყნდება GitHub-ის პრერელიზებად. ნებისმიერი ინსტრუმენტი, რომელიც გამორიცხავს პრერელიზებს `:latest`-ის რეზოლუციის დროს, გამოტოვებს მათ, ამიტომ მათზე მოხვედრა მხოლოდ ცალსახა მოთხოვნით არის შესაძლებელი.

### Canary {#canary}

ყოველი კომიტი `main`-ზე აქვეყნებს canary იმიჯს. Canary ყოველთვის წარმოადგენს **შემდეგ გამოუშვებელ მინორულ ვერსიას**: როგორც კი ხაზი გამოშვებისთვის მომზადდება, `main` გადადის შემდეგ მინორულ ვერსიაზე (მაგალითად, `1.350.0-canary.42`-დან `1.351.0-canary.1`-მდე). Canary სწორი არხია სტეიჯინგის გარემოსთვის, რომელიც ასახავს პროდაქშენს და გაძლევთ რეგრესიებზე ადრეულ სიგნალს, ან საშუალებას გაძლევთ შეამოწმოთ, რომ თქვენს მიერ შეტყობინებულმა გამოსწორებამ მოსალოდნელად იმუშაოს, სანამ stable-ს მიაღწევს.

```
ghcr.io/tuist/tuist:1.351.0-canary.5
ghcr.io/tuist/kura:0.55.0-canary.5
```

### Release candidate {#release-candidate}

როცა მინორული ვერსია მზადაა გამოშვებისთვის, მისი ხაზი იყინება დაცულ `releases/server-<major>.<minor>.x` (ან `releases/kura-<major>.<minor>.x`) ბრენჩზე და ქვეყნდება როგორც `X.Y.0-rc.1`. ხაზი ფუნქციურად გაყინულია; მასზე მხოლოდ კრიტიკული გამოსწორებები და რეგრესიები გადააქვთ, და ყოველი მიღებული გამოსწორება ზრდის release candidate-ის ნომერს (`-rc.2`, `-rc.3` და ა.შ.). ტესტირების პერიოდის წარმატებით დასრულების შემდეგ, ხაზი შემდეგ ორშაბათს stable-ად წინ იწევს.

```
ghcr.io/tuist/tuist:1.351.0-rc.1
ghcr.io/tuist/kura:0.55.0-rc.1
```

### Stable {#stable}

Stable რეკომენდებული არხია და ყველა დოკუმენტაცია მასზე მიუთითებს. სტაბილური მინორული ვერსია (`X.Y.0`) ქვეყნდება მხოლოდ მაშინ, როცა release candidate წარმატებით გაივლის ტესტირებას, და ის **არ** გადადის, როცა ახალი ფუნქციები ერწყმება `main`-ს. პატჩები (`X.Y.1`, `X.Y.2` და ა.შ.) სტაბილურ ხაზზე შეიცავს მხოლოდ უკანპორტირებულ გამოსწორებებს, არასდროს ახალ ფუნქციებს. `:latest` გადადის მხოლოდ სტაბილურად წინ წაწევისას.

```
ghcr.io/tuist/tuist:1.351.0
ghcr.io/tuist/kura:0.55.0
ghcr.io/tuist/tuist:latest
ghcr.io/tuist/kura:latest
```

## ორშაბათის „მატარებელი“ {#the-monday-train}

ყოველ ორშაბათს 06:00 UTC-ზე, სამი კომპონენტის გამოშვების „მატარებლები“ სინქრონულად იწყება:

1. **06:00 UTC** — წინ წაწევის ჯობები იწყება. თითოეული წინ სწევს უახლეს release-candidate ხაზს, რომელიც ჯერ არ არის სტაბილური (ჩვეულებრივ, წინა ორშაბათს ამოჭრილ ხაზს) და არაფერს აკეთებს, თუ ასეთი არ არსებობს.
2. **ყოველი წინ წაწევის დასრულების შემდეგ** — release-candidate ჯობი ჭრის შემდეგ ხაზს `main`-დან, ამიტომ ახლად ამოჭრილი ხაზი იმავე გაშვებაში არ წინ იწევს.

წარუმატებელი წინ წაწევა აჩერებს ჭრას: ყოველთვის ირჩევა მხოლოდ უმაღლესი release-candidate ხაზი უახლეს stable-ზე, ამიტომ შემდეგი ხაზის ჭრა წარუმატებლობის ფონზე დატოვებდა იმას, რომელიც არ გამოვიდა. შემდეგ ორშაბათს შეჩერებული ხაზი ავტომატურად თავიდან სცდება.

## არხის მიმაგრება {#pinning-a-channel}

მიამაგრეთ სასურველი კონკრეტული ტეგი თქვენს განლაგების მანიფესტში, Helm-ის მნიშვნელობებში ან Docker Compose ფაილში. მაგალითი, Helm-ის ჩარტის გამოყენებით:

```yaml
server:
  image:
    repository: ghcr.io/tuist/tuist
    tag: "1.350.2"          # Pinned to a stable patch
    # tag: "1.351.0-rc.1"   # Or opt into a release candidate to soak it
    # tag: "1.351.0-canary.5" # Or opt into a specific canary build

kuraRuntime:
  image:
    repository: ghcr.io/tuist/kura
    tag: "0.54.0"           # Same three channels apply to Kura
```

`:latest` ორივეზე `ghcr.io/tuist/tuist` და `ghcr.io/tuist/kura` თვალყურს ადევნებს უახლეს სტაბილურს, რომელიც გადადის მხოლოდ ორშაბათის წინ წაწევისას. `:latest`-ის მიმაგრება გაძლევთ კვირეულ სტაბილურ სიხშირეს ტეგის განახლების საჭიროების გარეშე; კონკრეტული ვერსიის მიმაგრება გაძლევთ სრულ კონტროლს განახლების დროზე.

## რეკომენდებული სტრატეგია {#recommended-strategy}

არხები არსებობს იმისთვის, რომ „უახლესი გამოსწორებების მიღება“ გააცალკევოთ „უახლესი ფუნქციების მიღებისგან“. უსაფრთხო, დაბალი ძალისხმევის მქონე ნაგულისხმები ვარიანტია:

1. **პროდაქშენი მიამაგრეთ სტაბილურ მინორულ ხაზს**, მაგალითად `ghcr.io/tuist/tuist:1.351`. ეს ხაზი იღებს მხოლოდ უკანპორტირებულ გამოსწორებებს, არასდროს ახალ ფუნქციებს, ამიტომ ყოველდღიური განახლებები დაბალი რისკის მქონე რჩება. გაზარდეთ მიმაგრება, როცა მზად იქნებით შემდეგი მინორული ვერსიის მიღებისთვის.
2. **გაუშვით სტეიჯინგის გარემო canary-ზე ან კონკრეტულ release-candidate ტეგზე.** სტეიჯინგი იჭერს რეგრესიებს, რომლებიც სხვა შემთხვევაში მომხმარებლებს მიაღწევდა, და რაც უფრო ახლოსაა სტეიჯინგი `main`-თან, მით ადრე აღმოაჩენთ მათ. სტეიჯინგის გარემო მიმდინარე release-candidate ხაზზე კარგი შუალედური ვარიანტია: ის ტესტირებს ზუსტად იმ ბაიტებს, რომლებიც შემდეგ ორშაბათს სტაბილური გახდება.
3. **მიჰყევით [სერვერის ცვლილებების ჟურნალს](/changelog) იმის გასარკვევად, რა რეალურად გამოვიდა.** ყოველი სტაბილური წინ წაწევა იქ ანონსდება იმ pull request-ების სიით, რომლებიც შევიდა.

თუ გირჩევნიათ, რომ ახალი ფუნქციები პროდაქშენში ავტომატურად გადმოვიდეს მათი სტაბილურად ქცევისთანავე, პროდაქშენი დატოვეთ `:latest`-ზე. უბრალოდ გაითვალისწინეთ, რომ ტეგი ყოველ ორშაბათს დილით წინ მიიწევს, ამიტომ შესაბამისად დაგეგმეთ განთავსების ფანჯარა.

## უკანპორტირება {#backports}

ნებისმიერ დროს აქტიურად მხარდაჭერილია ორი სტაბილური სერვერის (და Kura) ხაზი: მიმდინარე ხაზი იღებს რეგრესიებსა და უსაფრთხოების გამოსწორებებს უკანპორტირებული pull request-ების სახით, ხოლო წინა ხაზი — მხოლოდ კრიტიკულ და უსაფრთხოების გამოსწორებებს. ძველ ხაზებზე უკანპორტირება არ ხდება; გამოსწორებების მისაღებად გადადით მხარდაჭერილ ხაზზე. როდესაც ახალი ხაზი სტაბილურად წინ იწევს, ის ხაზი, რომელიც „მიმდინარე“ იყო, ხდება „წინა“, ხოლო „წინა“ ხაზი წყვეტს უკანპორტირებების მიღებას.

უკანპორტირებები მოთხოვნის შესაბამისად იჭრება როგორც `X.Y.(Z+1)` პატჩ-გამოცემები. ისინი არასდროს აწინაურებენ `:latest`-ს.
