# ავთენტიკაცია {#authentication}

სერვერთან ურთიერთობისთვის CLI-მ მოთხოვნები უნდა დააავთენტიკოს [bearer ავთენტიკაციის](https://swagger.io/docs/specification/authentication/bearer-authentication/) გამოყენებით. CLI მხარდაჭერილია მომხმარებლის, ანგარიშის ან OIDC ტოკენის სახელით ავთენტიკაციას.

## როგორც მომხმარებელი {#as-a-user}

როდესაც CLI-ს იყენებთ თქვენს მანქანაზე ლოკალურად, გირჩევთ ავთენტიკაცია მომხმარებლის სახელით. მომხმარებლის სახელით ავთენტიკაციისთვის უნდა გაუშვათ შემდეგი ბრძანება:

```bash
tuist auth login
```

ბრძანება გაგივლით ვებზე დაფუძნებულ ავთენტიკაციის ნაკადს. ავთენტიკაციის შემდეგ CLI შეინახავს ხანგრძლივი ვადის განახლების ტოკენს და მოკლე ვადის წვდომის ტოკენს `~/.config/tuist/credentials` ქვეშ. დირექტორიაში თითოეული ფაილი წარმოადგენს დომენს, რომლის მიმართაც მოხდა ავთენტიკაცია, რაც ნაგულისხმევად უნდა იყოს `tuist.dev.json`. ამ დირექტორიაში შენახული ინფორმაცია მგრძნობიარეა, ამიტომ **დარწმუნდით, რომ ის უსაფრთხოდ შეინახეთ**.

CLI ავტომატურად მოიძიებს სერთიფიკატებს სერვერზე მოთხოვნების გაკეთებისას. თუ წვდომის ტოკენი ამოიწურა, CLI გამოიყენებს განახლების ტოკენს ახალი წვდომის ტოკენის მისაღებად.

> [!NOTE]
> თუ თქვენი ორგანიზაცია იყენებს ერთჯერად შესვლას (SSO), ბრაუზერში აირჩიეთ საწარმოს შესვლის ვარიანტი და შეიყვანეთ სამუშაო ელფოსტის მისამართი. Tuist-ს შეუძლია პროვაიდერის პოვნა თქვენი არსებული ორგანიზაციის წევრობიდან ან <.localized_link href="/guides/integrations/authentication/sso#verify-a-login-email-domain">დადასტურებული შესვლის ელფოსტის დომენიდან</.localized_link>.

## OIDC ტოკენები {#oidc-tokens}

CI გარემოებისთვის, რომლებიც მხარს უჭერენ OpenID Connect-ს (OIDC), Tuist-ს შეუძლია ავტომატური ავთენტიკაცია ხანგრძლივი ვადის საიდუმლოების მართვის საჭიროების გარეშე. მხარდაჭერილ CI გარემოში გაშვებისას CLI ავტომატურად აღმოაჩენს OIDC ტოკენის პროვაიდერს და ცვლის CI-ს მიერ მოწოდებულ ტოკენს Tuist-ის წვდომის ტოკენზე.

### მხარდაჭერილი პროვაიდერები {#supported-ci-providers}

Tuist ცნობს ამ CI პროვაიდერებს და მათ ტოკენებს რეპოზიტორიის კავშირის მეშვეობით პროექტებს უკავშირებს:

- GitHub Actions
- CircleCI
- Bitrise

[Amp](#amp-orbs) orbs ავთენტიკდება Amp სამუშაო სივრცეების მეშვეობით, რომლებსაც თქვენს Tuist ანგარიშს უკავშირებთ, ხოლო [Claude Code სესიები](#claude-code-sessions) — Claude Code გარემოების მეშვეობით, რომლებსაც Tuist Sandboxes-ზე გასაშვებად უკავშირებთ.

ნებისმიერი სხვა იდენტობის პროვაიდერი, რომელიც გამოსცემს OpenID Connect ტოკენებს, შეუძლია ავთენტიკაცია [სამუშაო დატვირთვის იდენტობის ნდობის პოლიტიკის](#workload-identity-trust-policies) მეშვეობით, რომელსაც ერთხელ აკონფიგურირებთ თქვენი ანგარიშის ყველა არსებული და მომავალი პროექტისთვის, მაგალითად [Fly.io Machines](#flyio-machines).

### OIDC ავთენტიკაციის დაყენება {#setting-up-oidc-authentication}

GitHub Actions-ის, CircleCI-ის და Bitrise-ისთვის:

1. **დაუკავშირეთ თქვენი რეპოზიტორია Tuist-ს**: მიჰყევით <.localized_link href="/guides/integrations/gitforge/github">GitHub ინტეგრაციის სახელმძღვანელოს</.localized_link>, რათა დაუკავშიროთ თქვენი GitHub რეპოზიტორია თქვენს Tuist პროექტს.

2. **მიანიჭეთ იდენტობის ტოკენი**: GitHub Actions-ზე მიანიჭეთ სამუშაოს `permissions: id-token: write`; CircleCI-ზე და Bitrise-ზე ჩართეთ OIDC პროექტისთვის. Tuist 4.218.0-დან, როდესაც CLI არ არის შესული და `TUIST_TOKEN` არ არის დაყენებული, ის აღმოაჩენს CI გარემოს და ცვლის იდენტობის ტოკენს თავის პირველ მოთხოვნაზე, ამიტომ შესვლის ნაბიჯი არ არის საჭირო. ადრეულ ვერსიებს სჭირდებათ ჯერ `tuist auth login`, და მაინც შეგიძლიათ მისი გაშვება ცხადი შესვლისთვის და ადრეული შეცდომის მიღებისთვის, თუ გაცვლა უარყოფილია.

იხილეთ <.localized_link href="/guides/integrations/continuous-integration">უწყვეტი ინტეგრაციის სახელმძღვანელო</.localized_link> პროვაიდერის სპეციფიკური კონფიგურაციის მაგალითებისთვის.

### Amp orbs {#amp-orbs}

[Amp](https://ampcode.com) orbs-ს შეუძლია გამოსცეს OIDC ტოკენები, რომლებიც აიდენტიფიცირებს მათ Amp სამუშაო სივრცეს. ერთხელ დაუკავშირეთ სამუშაო სივრცე თქვენს Tuist ანგარიშს და Tuist CLI და `tuist_ex` Mix ამოცანები ამ სამუშაო სივრცის ნებისმიერ orb-ში თავისთავად შედიან, შენახული ტოკენის ან შესვლის ნაბიჯის გარეშე:

1. იპოვეთ ID-ები: სამუშაო სივრცის ნაკადში, რომელიც orb-ში გადის, გაუშვით `echo $AMP_WORKSPACE_ID $AMP_PROJECT_ID`.
2. თქვენს Tuist ანგარიშში გახსენით **Settings → Integrations**, აირჩიეთ **Connect workspace** Amp ბარათზე და ჩასვით სამუშაო სივრცის ID. მხოლოდ ერთი Amp პროექტის orbs-ის დაშვებისთვის ასევე ჩასვით მისი პროექტის ID. თქვენ უნდა იყოთ ანგარიშის ადმინისტრატორი ან მფლობელი.
3. გამოიყენეთ Tuist სამუშაო სივრცის orbs-ში. როდესაც ის არ არის შესული, CLI ან Mix ამოცანა აღმოაჩენს orb-ს, გამოსცემს ტოკენს `amp orb id-token --audience https://tuist.dev`-ით და ცვლის მას Tuist სესიაზე. `tuist auth login` და `mix tuist.login` აკეთებენ იგივე გაცვლას ცხადად.

[Amp-ის OIDC სახელმძღვანელოს](https://ampcode.com/manual/orbs/oidc) ნდობის კონფიგურაციების მსგავსად, Tuist ამოწმებს Amp-ის ხელმოწერას ყოველ ტოკენზე და იღებს მას მხოლოდ მაშინ, როდესაც მისი აუდიტორიაა `https://tuist.dev`, მისი `token_use` არის `exchanged`, მისი `workspace_id` ემთხვევა დაკავშირებულ სამუშაო სივრცეს და, პროექტამდე შეზღუდული კავშირისთვის, მისი `project_id` ემთხვევა იმ პროექტს. მისმა `sub`-მა უნდა დაასახელოს იგივე სამუშაო სივრცე, ხოლო პროექტის კავშირისთვის — იგივე პროექტი, როგორც ამ პრეტენზიებში: `workspace:<workspace-id>:project:<project-id>:…`, რომელსაც `amp orb id-token` ნაგულისხმევად გამოსცემს.

ყველა orb, რომელსაც კავშირი უშვებს, იღებს CI წვდომას ანგარიშის მფლობელობაში არსებულ ყველა არსებულ და მომავალ პროექტზე, კეშის ატვირთვების ჩათვლით. ის ასევე იღებს `account:sandboxes:write` სკოუპს, რათა შექმნას <.localized_link href="/guides/features/sandboxes">sandboxes</.localized_link> და გაუშვას მათში ბრძანებები ანგარიშის წევრის მსგავსად, მაგალითად macOS sandbox-ზე აგებისთვის Linux orb-დან. დაუკავშირეთ მხოლოდ ისეთი სამუშაო სივრცეები, რომელთა წევრებსაც ენდობით ამ წვდომით. ყურადღებით შეამოწმეთ ID: Tuist-ს არ შეუძლია დაადასტუროს, რომ თქვენ ეკუთვნით იმ სამუშაო სივრცეს, რომელსაც უკავშირებთ. თუ სამუშაო სივრცე დაკავშირებულია რამდენიმე Tuist ანგარიშთან, orbs-მა უნდა დააყენოს `TUIST_OIDC_ACCOUNT` იმ ანგარიშზე, რომელშიც შესვლაა საჭირო; მისი Amp პროექტის გარემოში დაყენება ასევე ინარჩუნებს შესვლას თქვენს ანგარიშზე მიბმულს. ნაკადებს სამუშაო სივრცის გარეთ არ აქვთ სამუშაო სივრცის იდენტობა და არ შეუძლიათ კავშირის გამოყენება. გათიშეთ სამუშაო სივრცე Amp ბარათიდან ახალი შესვლების შეჩერებისთვის; უკვე გაცემული სესიები ძალაში რჩებიან ერთი საათის შემდეგ ამოწურვამდე. სესიებს არ სჭირდებათ განახლების ტოკენი: როდესაც ერთ-ერთი იწურება, CLI orb-ში გამოსცემს ახალ Amp ტოკენს და კვლავ ცვლის მას, ასე რომ ხანგრძლივად მომუშავე orbs რჩებიან შესულები, სანამ სამუშაო სივრცე დაკავშირებულია.

ნდობის პოლიტიკები Amp გამომცემლისთვის, რომლებიც შექმენით სამუშაო სივრცის დაკავშირებამდე, აგრძელებენ მუშაობას, როდესაც აყენებთ `TUIST_OIDC_ACCOUNT`.

### Claude Code სესიები {#claude-code-sessions}

ყოველი Claude Code ღრუბლოვანი სესია თვითმასპინძელ გარემოში ატარებს იდენტობის ტოკენს, რომელსაც Anthropic აწერს ხელს (`CLAUDE_CODE_SESSION_ACCESS_TOKEN`). გარემოებში, რომლებსაც <.localized_link href="/guides/features/sandboxes/claude#claude-code">უკავშირებთ Tuist Sandboxes-ზე გასაშვებად</.localized_link>, Tuist გადასცემს მას სესიას როგორც `TUIST_OIDC_TOKEN`, ასე რომ Tuist CLI და `tuist_ex` Mix ამოცანები თავისთავად შედიან.

Tuist ამოწმებს Anthropic-ის ხელმოწერას და იღებს ტოკენს მხოლოდ მაშინ, როცა ის სესიის ტოკენია (`ccr:role` არის `session_worker`), რომლის გარემო, სახელდებული მის audience-ში, დაკავშირებულია Tuist ანგარიშთან და ჩართულია. დაკავშირებული გარემოს ყოველი სესია იღებს CI წვდომას ანგარიშის მიერ ფლობილ ყველა მიმდინარე და მომავალ პროექტზე, კეშის ატვირთვების ჩათვლით, ასე რომ ნებისმიერს, ვისაც თქვენი Claude ორგანიზაცია აძლევს გარემოს გამოყენების უფლებას, შეუძლია გამოაქვეყნოს თქვენს კეშში. სესიის Tuist სესიები იწურება ერთი საათის შემდეგ ან მის იდენტობის ტოკენთან ერთად, რაც უფრო ადრე მოხდება; ტოკენი არის ის, რითაც სესია დაიწყო და ნაგულისხმევად ოთხი საათი ძლებს, ასე რომ ხანგრძლივი სესია კარგავს Tuist წვდომას, სანამ მისი შემდეგი შეტყობინება განაახლებს მას ახალ runner-ზე. გათიშეთ ან გამორთეთ გარემო ახალი შესვლების შესაჩერებლად.

### Workload identity ნდობის პოლიტიკები {#workload-identity-trust-policies}

ნდობის პოლიტიკა საშუალებას აძლევს სხვა იდენტობის პროვაიდერის სამუშაო დატვირთვებს, როგორიცაა დეპლოიმენტის პლატფორმა, Kubernetes კლასტერი ან თვითმართვადი CI სისტემა, მიუწვდებოდნენ პროექტს გრძელვადიანი Tuist საიდუმლოს გარეშე. პროვაიდერმა უნდა:

- იყოს ხელმისაწვდომი HTTPS-ით საჯარო მისამართზე. Tuist არ მიჰყვება გადამისამართებებს და არ უკავშირდება პირად ან შიდა ქსელის მისამართებს, თვითმასპინძელი Tuist სერვერებიდანაც კი.
- გამოსცეს JWT-ები ასიმეტრიული გასაღებით ხელმოწერილი, მაგალითად `RS256` ან `ES256`. ხელმოუწერილი ტოკენები და საერთო საიდუმლოთი ხელმოწერილი ტოკენები (`HS256` და მსგავსი) უარყოფილია.
- გამოაქვეყნოს თავისი ხელმოწერის გასაღებები JSON Web Key Set (JWKS)-ის სახით ფიქსირებულ HTTPS URL-ზე. პასუხი უნდა იყოს მაქსიმუმ 64 KiB და შეიცავდეს მაქსიმუმ 20 გასაღებს.
- შეიცავდეს ვადის გასვლას (`exp`) ყოველ ტოკენში.

GitHub Actions, CircleCI და Bitrise გამომცემლები დაცულია ზემოთ აღწერილი რეპოზიტორიაზე დაფუძნებული ნაკადისთვის და არ შეიძლება გამოყენებულ იქნას ნდობის პოლიტიკაში.

> [!NOTE]
> თვითმასპინძელი განლაგებისთვის, გამოიყენეთ მონაცემთა ბაზის მიგრაციები და განაახლეთ Tuist სერვერის ყოველი მომსახურე რეპლიკა, სანამ დააკონფიგურიროთ workload identities ან გადაიტანთ მათზე ამოცანებს. შემდეგ განაახლეთ CLI ან Elixir ინტეგრაცია ვერსიამდე, რომელიც მხარდაჭერს `TUIST_OIDC_TOKEN` და `TUIST_OIDC_ACCOUNT`. არსებული GitHub Actions, CircleCI და Bitrise ამოცანები აგრძელებენ რეპოზიტორიაზე დაფუძნებული ავტორიზაციის გამოყენებას და არ საჭიროებენ ანგარიშის handle-ს. წარმოების ამოცანებზე გადასვლამდე, შეამოწმეთ ხანმოკლე ტოკენის გაცვლა და კეშის ოპერაცია სასურველ სამუშაო დატვირთვასთან. ახალი გაცვლების შესაჩერებლად, წაშალეთ პოლიტიკა; მისცეთ უკვე გაცემულ Tuist წვდომის ტოკენებს ერთ საათამდე ვადა გაუვიდეთ. პოლიტიკის წაშლა არ აუქმებს იმ ტოკენებს დაუყოვნებლივ.

#### პოლიტიკის შექმნა {#create-a-trust-policy}

Tuist dashboard-ში, გახსენით თქვენი ანგარიშის **Settings** > **Authentication** და იპოვეთ **Workload identities** სექცია. თქვენ უნდა იყოთ ანგარიშის ადმინისტრატორი (ან პირადი ანგარიშის მფლობელი). ყოველ ანგარიშს შეიძლება ჰქონდეს მაქსიმუმ 20 პოლიტიკა. დააკონფიგურეთ იდენტობა ერთხელ ანგარიშის მასშტაბით CI წვდომისთვის; პროექტის შერჩევა არ არის საჭირო.

გამოიყენეთ გადამრთველი **Workload identities**-ის გვერდით პოლიტიკის ფორმის გასახსნელად. გადამრთველი იწყება ჩართულ მდგომარეობაში, როცა ანგარიშს აქვს შენახული იდენტობები და რჩება ჩართული შენახვის შემდეგ. ის იწყება გამორთულ მდგომარეობაში ანგარიშებისთვის იდენტობების გარეშე. სექცია ჩანს **SCIM provisioning**-ის ქვემოთ ორგანიზაციებისთვის. ფორმის დამალვა ინარჩუნებს თქვენს ნახაზს და არ თიშავს სამუშაო დატვირთვის ავთენტიკაციას: შენახული იდენტობის ბარათები და მორგების დოკუმენტაციის ბმული რჩება ხილული. ყოველი ბარათი აჩვენებს იდენტობის სახელს, გამომცემლისა და JWKS URL-ებს, audience-ს, ზუსტ JSON claims-ებს, ანგარიშის მასშტაბით მოქმედების სფეროს და შექმნის დროს. წაშალეთ იდენტობა მის ბარათზე არსებული ქმედების გამოყენებით.

აირჩიეთ **Custom provider** ქვემოთ მოცემული ველების შესაყვანად, ან **Fly.io Machines** მათი გენერირებისთვის თქვენი ორგანიზაციის slug-ისა და რიცხვითი ორგანიზაციისა და აპლიკაციის ID-ების მიხედვით. Fly შაბლონი ინარჩუნებს გენერირებულ გამომცემელს, JWKS URL-ს და claims-ებს რედაქტირებადს **Advanced configuration**-ის ქვეშ. შაბლონების ან დამხმარე მნიშვნელობების შეცვლა ინარჩუნებს ხელით რედაქტირებულ ველებს. თუ თქვენი გამომცემელი, JWKS URL ან claims გადაფარავს შაბლონს, Tuist აფართოებს **Advanced configuration**-ს და აჩვენებს გაფრთხილებას, რათა გადახედოთ შენახვად პოლიტიკას. დაუბრუნდით **Custom provider**-ს Fly დამხმარეების გარეშე გასაგრძელებლად. შაბლონები მხოლოდ ავსებენ კონფიგურაციას და არ ცვლიან იმას, თუ როგორ ამოწმებს Tuist ტოკენებს.

| ველი | აღწერა |
| --- | --- |
| სახელი | ლეიბლი პოლიტიკის ამოსაცნობად, უნიკალური ანგარიშის ფარგლებში. |
| გამომცემლის URL | ტოკენის `iss` claim. ის უნდა ემთხვეოდეს ზუსტად, ნებისმიერი ბოლო სლეშის ჩათვლით. |
| JWKS URL | პროვაიდერის ხელმოწერის გასაღებების HTTPS URL. Tuist იყენებს ამ URL-ს პირდაპირ და არ კითხულობს პროვაიდერის OpenID Connect აღმოჩენის დოკუმენტს, ასე რომ დააკოპირეთ `jwks_uri` პროვაიდერის დოკუმენტაციიდან ან `<issuer>/.well-known/openid-configuration`-დან. |
| Audience | audience, რომლისთვისაც უნდა იყოს ტოკენი გაცემული, ნაგულისხმევად `tuist`. ტოკენის `aud` უნდა უდრიდეს მას ან, როცა `aud` არის სია, შეიცავდეს მას. გამოიყენეთ მნიშვნელობა, რომელსაც მხოლოდ Tuist იღებს, რათა სხვა სერვისებისთვის შექმნილი ტოკენები ვერ განმეორდეს აქ. |
| Claims | JSON ობიექტი 1-დან 10-მდე claim-ით, რომელიც ტოკენმა უნდა შეიცავდეს, მაგალითად `{"sub": "system:serviceaccount:ci:builder"}`. JSON შეყვანა შეზღუდულია 8 KiB-მდე. მნიშვნელობები უნდა იყოს სტრიქონები, ნიშნიანი 64-ბიტიანი მთელი რიცხვები ან ბულიანები, და ისინი უნდა ემთხვეოდნენ ზუსტად, მათი ტიპის ჩათვლით: `"123"` არ ემთხვევა `123`-ს. ჩადგმული ობიექტები, სიები და დროის ან ტოკენის claims, როგორიცაა `iss`, `aud`, `exp`, `nbf`, `iat` და `jti`, არ არის დაშვებული. |

ყოველი პოლიტიკა ანიჭებს CI წვდომას **ანგარიშის მიერ ფლობილ ყველა მიმდინარე და მომავალ პროექტზე**, ინდივიდუალური პროექტების შერჩევის გარეშე. შეგიძლიათ დააკონფიგურიროთ იდენტობა პირველი პროექტის შექმნამდე. ეს არ ანიჭებს ანგარიშის ადმინისტრირებას ან წვდომას სხვა ანგარიშზე.

ყოველ სამუშაო დატვირთვას, რომელსაც შეუძლია მიიღოს ტოკენი დამთხვევი claims-ებით, შეუძლია მიუწვდეს ყველა იმ პროექტს, ასე რომ აირჩიეთ claims, რომლებსაც პროვაიდერი გარანტირებს და რომელთა განმეორებითი გამოყენება არავის შეუძლია. უპირატესობა მიანიჭეთ სტაბილურ რიცხვით ID-ებს სახელებზე, რომლებიც შეიძლება გადაერქვას ან ხელახლა დარეგისტრირდეს წაშლის შემდეგ.

> [!WARNING]
> გაზიარებულ იდენტობის პროვაიდერზე, მიამაგრეთ პოლიტიკა თქვენს ორგანიზაციას ან ტენანტს **და** სასურველ აპლიკაციას, პროექტს ან სერვისის ანგარიშს. ისეთი მონაცემები, როგორიცაა ბრენჩის სახელი `main`, გარემო `production` ან ზოგადი როლი, არ წარმოადგენს იდენტობის საზღვარს: სხვა ტენანტმა შეიძლება მიიღოს ტოკენი იგივე მნიშვნელობებით. მაგალითად, GitLab.com-ის პოლიტიკა უნდა შეიცავდეს სასურველი პროექტის სტაბილურ `project_id`-ს და არა მხოლოდ `ref`-ს. დამთხვევი ტოკენი ანიჭებს CI წვდომას მთელ ანგარიშზე, cache-ში ჩაწერის ჩათვლით, ამიტომ პოლიტიკა, რომელიც ენდობა არარელევანტურ სამუშაო დატვირთვებს, შეიძლება დაუშვას cache-ის მოწამვლას.

Tuist ანიჭებს წვდომას მხოლოდ იმ პოლიტიკებისთვის, რომელთა საკუთარ JWKS URL-ს აქვს ტოკენის ხელმომწერი გასაღები, გამომცემლის, აუდიტორიის, ვადის, not-before დროის (60 წამამდე საათის ცდომილებით) და ყოველი claim-ის შემოწმების შემდეგ. გაცემული ერთსაათიანი CI ტოკენი მოქმედებს მთელ ანგარიშზე და არ არის პროექტების ID-ების სნეპშოტი: ის მოიცავს პროექტებს, რომლებიც შეიქმნა ან გადაიტანეს ანგარიშზე გაცემის შემდეგ. პროექტის ავტორიზაცია კვლავ მოითხოვს ანგარიშის მიმდინარე ფლობას, ამიტომ პროექტის გადატანა ანგარიშიდან აშორებს მას წვდომას ამ ანგარიშის ტოკენით.

#### სამუშაო დატვირთვის ავთენტიკაცია {#authenticate-a-workload}

1. მოითხოვეთ იდენტობის ტოკენი თქვენი პროვაიდერისგან პოლიტიკის აუდიტორიით.
2. დააყენეთ `TUIST_OIDC_TOKEN` ამ ტოკენზე და `TUIST_OIDC_ACCOUNT` Tuist ანგარიშის handle-ზე, რომელიც ფლობს პროექტს. ანგარიში აუცილებელია ნდობის პოლიტიკის ყოველი გაცვლისთვის. ის მხოლოდ განსაზღვრავს სად უნდა მოხდეს ძიება და თავისთავად არაფერს ანიჭებს.
3. გაუშვით Tuist. როდესაც არ არის ხელმისაწვდომი `TUIST_TOKEN` ან მოქმედი შენახული სერთიფიკატები, CLI და Elixir ინტეგრაცია ავტომატურად ცვლიან ტოკენს. `tuist auth login` და `mix tuist.login` ასრულებენ იგივე გაცვლას ცალსახად.

მიღებულ Tuist წვდომის ტოკენს აქვს მხოლოდ `ci` სკოუპების ჯგუფი და მოიცავს არჩეული ანგარიშის მიერ ფლობილ ყველა მიმდინარე და მომავალ პროექტს. გაცვლა ვერ ხერხდება, თუ ანგარიშში 20-ზე მეტი პოლიტიკა ემთხვევა ერთსა და იმავე ტოკენს ან თუ ისინი იყენებენ ორზე მეტ განსხვავებულ JWKS URL-ს.

Tuist არ აახლებს ამ სესიებს. წვდომის ტოკენები იწურება ერთი საათის შემდეგ და არ აქვთ განახლების ტოკენი. პროვაიდერის იდენტობის ტოკენები ხშირად მოქმედებს მხოლოდ რამდენიმე წუთის განმავლობაში, ამიტომ ძველი `TUIST_OIDC_TOKEN`-ის შენახვა არ არის განახლების სტრატეგია: ერთ საათზე ხანგრძლივად მომუშავე დავალებებისთვის, მოითხოვეთ ახალი იდენტობის ტოკენი და შედით სისტემაში ხელახლა Tuist სესიის ამოწურვამდე. პოლიტიკის წაშლა აჩერებს ახალ გაცვლებს, მაგრამ უკვე გაცემული წვდომის ტოკენები ძალაში რჩება მათ ამოწურვამდე.

Tuist აკეთებს პროვაიდერის ხელმომწერი გასაღებების cache-ს 15 წუთის განმავლობაში წარმატებული მიღების შემდეგ სპეციალურ, ზომით შეზღუდულ cache-ში. ჩანაწერები შეიძლება ამოიღონ უფრო ადრე და ხელახლა მიიღონ. წარუმატებელი მიღებები არ ინახება cache-ში. თუ თქვენი პროვაიდერი ატრიალებს გასაღებებს, მან უნდა გამოაქვეყნოს ახალი გასაღები თავის JWKS-ში ტოკენებით ხელმოწერამდე სულ მცირე 15 წუთით ადრე, რადგან cache-ში არარსებული გასაღებით ხელმოწერილი ტოკენები იბლოკება cache-ის ამოწურვამდე. ტოკენები გასაღების ID-ის (`kid`) გარეშე მიიღება მხოლოდ მაშინ, როდესაც JWKS შეიცავს ერთ შესაბამის ხელმომწერ გასაღებს. როდესაც JWKS-ში არის გასაღების ID, ის უნდა იყოს სტრიქონი არაუმეტეს 256 ბაიტისა.

> [!NOTE]
> `TUIST_OIDC_TOKEN` არის ზოგადი ტოკენის შეყვანა და არა სერვერის ნდობის გვერდის ავლის საშუალება. ის უპირატესობას ანიჭებს CI პროვაიდერის აღმოჩენას და სერვერი კვლავ იღებს მხოლოდ ჩაშენებულ პროვაიდერებს და იდენტობებს შესაბამისი ნდობის პოლიტიკით. არ ჩასვათ იდენტობის ტოკენი `TUIST_TOKEN`-ში, რომელიც ელის Tuist სერთიფიკატს.

თუ გაცვლა ვერ მოხერხდა, შეამოწმეთ, რომ გამომცემელი, აუდიტორია და პოლიტიკის ყოველი claim ზუსტად ემთხვევა ტოკენს, რომ JWKS URL ემსახურება ტოკენის ხელმომწერ გასაღებს, რომ პოლიტიკა არ არის წაშლილი და რომ `TUIST_OIDC_ACCOUNT` მიუთითებს ანგარიშს, რომელიც ფლობს პროექტს. იმის თავიდან ასაცილებლად, თუ რომელი იდენტობებია სანდო, Tuist აბრუნებს ერთსა და იმავე შეცდომას ყველა ამ შემთხვევისთვის.

### Fly.io Machines {#flyio-machines}

[Fly.io მხარდაჭერას უწევს OIDC სამუშაო იდენტობას](https://docs.fly.io/reference/openid-connect/). Machine-ს შეუძლია მოითხოვოს ხანმოკლე, ხელმოწერილი იდენტობის ტოკენი თავისი ლოკალური `/.fly/api` Unix socket-იდან, Fly API ტოკენის ან ხანგრძლივი Tuist საიდუმლოს გარეშე. Fly ტოკენები აიდენტიფიცირებენ ორგანიზაციას და აპლიკაციას, არა წყაროს რეპოზიტორიას, ამიტომ გამოიყენეთ ნდობის პოლიტიკა GitHub რეპოზიტორიის მიერთების ნაცვლად:

1. მიიღეთ გამომცემელი (`iss`), ორგანიზაციის ID (`org_id`) და აპლიკაციის ID (`app_id`) თქვენს Fly Machine-ში გაცემული იდენტობის ტოკენიდან. გამომცემელია `https://oidc.fly.io/<organization-slug>`. გამოიყენეთ რიცხვითი ID-ები და არა ორგანიზაციის ან აპის სახელები.
2. [შექმენით ნდობის პოლიტიკა](#create-a-trust-policy) **Fly.io Machines** შაბლონის გამოყენებით და შეიყვანეთ ორგანიზაციის slug და ორივე რიცხვითი ID. ის ავსებს ქვემოთ მოცემულ მნიშვნელობებს და ინახავს ID-ებს როგორც სტრიქონებს. ასევე შეგიძლიათ შეიყვანოთ ისინი ხელით **Custom provider**-ის გამოყენებით; შეინარჩუნეთ ბრჭყალები ID-ების გარშემო claims-ში.

   | ველი | მნიშვნელობა |
   | --- | --- |
   | გამომცემლის URL | `https://oidc.fly.io/<organization-slug>` |
   | JWKS URL | `https://oidc.fly.io/<organization-slug>/.well-known/jwks` |
   | აუდიტორია | `tuist` |
   | Claims | `{"org_id": "<organization-id>", "app_id": "<application-id>"}` |

3. Machine-ის შიგნით, დააყენეთ `TUIST_OIDC_ACCOUNT` Tuist ანგარიშის handle-ზე, რომელიც ფლობს პროექტს (არა Fly ორგანიზაციის slug), მოითხოვეთ ტოკენი აუდიტორიით `tuist` და გადაეცით ის `tuist auth login`-ს `TUIST_OIDC_TOKEN`-ის გამოყენებით:

```bash
set -euo pipefail
export TUIST_OIDC_ACCOUNT="my-tuist-account"

TUIST_OIDC_TOKEN="$(curl --fail --silent --show-error \
  --unix-socket /.fly/api \
  -X POST http://localhost/v1/tokens/oidc \
  -H 'Content-Type: application/json' \
  --data '{"aud":"tuist"}')"
export TUIST_OIDC_TOKEN

tuist auth login
unset TUIST_OIDC_TOKEN
```

საწყისი კონფიგურაციისთვის, შეგიძლიათ შეამოწმოთ მხოლოდ იდენტობის ველები ლოკალურად, ტოკენის ექსპორტირების შემდეგ და მისი გაუქმებამდე. ეს აკოდირებს claims-ებს კონფიგურაციისთვის; Tuist ცალკე ამოწმებს ხელმოწერას ავთენტიკაციის დროს:

```bash
python3 - <<'PY'
import base64, json, os
payload = os.environ["TUIST_OIDC_TOKEN"].split(".")[1]
claims = json.loads(base64.urlsafe_b64decode(payload + "=" * (-len(payload) % 4)))
print(json.dumps({key: claims[key] for key in ("iss", "org_id", "app_id")}, indent=2))
PY
```

არ დაბეჭდოთ ან არ ჩააკომიტოთ თავად ტოკენი. ავტორიზებულ Fly აპლიკაციაში ყოველ Machine-ს შეუძლია ავთენტიკაცია Tuist ანგარიშის ყველა მიმდინარე და მომავალ პროექტზე. შექმენით ცალკე პოლიტიკა ყოველი დამატებითი აპისთვის. Fly იდენტობის ტოკენები იწურება დაახლოებით ათი წუთის შემდეგ, ამიტომ ხანგრძლივად მომუშავე Machine-ებზე მოითხოვეთ ახალი და გაუშვით `tuist auth login` ხელახლა ერთსაათიანი Tuist სესიის ამოწურვამდე.

### OIDC ტოკენის სკოუპები {#oidc-token-scopes}

OIDC ტოკენებს ენიჭებათ `ci` სკოუპების ჯგუფი. GitHub Actions-ის, CircleCI-ის და Bitrise-ისთვის, ეს უზრუნველყოფს წვდომას რეპოზიტორიასთან დაკავშირებულ ყველა პროექტზე. დაკავშირებული Amp სამუშაო სივრცეების, დაკავშირებული Claude Code გარემოების და სამუშაო იდენტობის ნდობის პოლიტიკებისთვის, ეს უზრუნველყოფს წვდომას არჩეული ანგარიშის მიერ ფლობილ ყველა მიმდინარე და მომავალ პროექტზე, პროექტის შექმნის, პროექტის ადმინისტრირების, runner-ის ადმინისტრირების ან ანგარიშის წევრების ადმინისტრირების გაცემის გარეშე. იხილეთ [სკოუპების ჯგუფები](#scope-groups) დეტალებისთვის, თუ რას მოიცავს `ci` სკოუპი.

> [!TIP]
> **უსაფრთხოების უპირატესობები**
>
> OIDC ავთენტიკაცია უფრო უსაფრთხოა, ვიდრე ხანგრძლივი ტოკენები, რადგან:
> - არ არის საიდუმლოები, რომლებიც უნდა შეიცვალოს ან იმართოს
> - ტოკენები ხანმოკლეა
> - ავთენტიკაცია მიბმულია თქვენს რეპოზიტორიის იდენტობაზე ან ცალსახად ავტორიზებულ სამუშაო იდენტობაზე


## Gradle პლაგინის ავთენტიკაცია {#gradle-plugin-authentication}

Gradle პლაგინი იყენებს Tuist CLI-ის ავთენტიკაციის მდგომარეობას და არ განსაზღვრავს ცალკე შესვლის პროცესს. გაიარეთ ავთენტიკაცია ერთხელ CLI-ით და პლაგინი ხელახლა გამოიყენებს ამ მონაცემებს.

პროექტისა და სერვერის კონფიგურაციისთვის, `project`-ისა და `url`-ის ჩათვლით, გამოიყენეთ კანონიკური <.localized_link href="/references/tuist-toml">tuist.toml საცნობარი</.localized_link>.

ლოკალური გამოყენებისთვის, გაუშვით:

```bash
tuist auth login
```

CI-ისთვის, გამოიყენეთ ერთ-ერთი:

- <.localized_link href="/guides/server/authentication#setting-up-oidc-authentication">OIDC ავთენტიკაცია</.localized_link> (რეკომენდებულია, თუ ხელმისაწვდომია)
- <.localized_link href="/guides/server/authentication#continuous-integration">ანგარიშის ტოკენით ავთენტიკაცია</.localized_link> `TUIST_TOKEN`-ის მეშვეობით

თვითმასპინძელი Tuist სერვერებისთვის, განსაზღვრეთ სერვერის URL `tuist.toml`-ში (მაგალითად, `url = "https://tuist.your-company.com"`) და გაუშვით სტანდარტული შესვლის პროცესი. URL მიიღება იგივე კონფიგურაციის ფაილიდან, რომელსაც პლაგინი იყენებს.

ავთენტიკაციის კონფიგურირების შემდეგ, ჩვეულებრივად გაუშვით Gradle ქეშირების ბრძანებები და დავალებები.

## ანგარიშის ტოკენები {#account-tokens}

CI გარემოებისთვის, რომლებიც არ უჭერენ მხარს OIDC-ს, ან როდესაც საჭიროა ნებართვებზე ზუსტი კონტროლი, შეგიძლიათ გამოიყენოთ ანგარიშის ტოკენები. ანგარიშის ტოკენები საშუალებას გაძლევთ ზუსტად მიუთითოთ, თუ რომელ სკოუპებსა და პროექტებზე აქვს ტოკენს წვდომა.

### ანგარიშის ტოკენის შექმნა {#creating-an-account-token}

ანგარიშის ტოკენის შექმნის ყველაზე მარტივი გზა დაფის მეშვეობითაა:

1. გახსენით ორგანიზაცია Tuist დაფზე.
2. გადადით **პარამეტრებში** > **ტოკენები**.
3. აირჩიეთ **ტოკენის გენერირება**.
4. აირჩიეთ სახელი, ვადის გასვლის არასავალდებულო პარამეტრი, პროექტზე წვდომა და სკოუპები, რომლებიც ტოკენს სჭირდება.
5. დახურვამდე დააკოპირეთ გენერირებული ტოკენის მნიშვნელობა. ტოკენის მნიშვნელობები მხოლოდ ერთხელ ჩანს.

ასევე შეგიძლიათ შექმნათ ანგარიშის ტოკენები CLI-დან, რაც სასარგებლოა სკრიპტინგისთვის ან ავტომატიზაციისთვის:

```bash
tuist account tokens create account-handle \
  --scopes account:cache:write project:cache:read project:cache:write \
  --name ci-cache-token \
  --expires 1y
```

> [!IMPORTANT]
> ჩაანაცვლეთ `account-handle` იმ ანგარიშის handle-ით, რომელიც ფლობს პროექტებს, რომლებზეც ტოკენს წვდომა გსურთ. ეს შეიძლება იყოს ორგანიზაციის ანგარიში და არა აუცილებლად თქვენი პირადი ანგარიში.

ბრძანება იღებს შემდეგ პარამეტრებს:

| პარამეტრი | აღწერა |
| --- | --- |
| `--scopes` | სავალდებულო. სკოუპების სია, რომლებიც ტოკენს მიენიჭება, გამოყოფილია შუალედებით. |
| `--name` | სავალდებულო. ტოკენის უნიკალური იდენტიფიკატორი (1-32 სიმბოლო, მხოლოდ ალფანუმერული, დეფისები და ქვედა ტირეები). |
| `--expires` | არასავალდებულო. როდის უნდა ამოიწუროს ტოკენმა. გამოიყენეთ ფორმატი, როგორიცაა `30d` (დღეები), `6m` (თვეები) ან `1y` (წლები). თუ არ არის მითითებული, ტოკენი არასდროს ამოიწურება. |
| `--projects` | შეზღუდეთ ტოკენი კონკრეტული პროექტების handle-ებით. თუ არ არის მითითებული, ტოკენს აქვს წვდომა ყველა პროექტზე. |

| `account:cache:write` | ანგარიშის სკოუპით ქეშირებული ბინარული ფაილების ატვირთვა |
| `account:members:read` | ანგარიშის წევრების წაკითხვა |

| `account:registry:write` | Swift პაკეტების რეესტრში გამოქვეყნება |

| `project:previews:write` | პრევიუების ატვირთვა |
| `project:admin:read` | პროექტებისა და მათი პარამეტრების წაკითხვა |
| `project:admin:write` | პროექტების შექმნა, განახლება და წაშლა. პროექტის შესაქმნელად საჭიროა ტოკენი, რომელსაც აქვს წვდომა ყველა პროექტზე |

| `project:bundles:read` | ბანდლების ნახვა |
| `project:bundles:write` | ბანდლების ატვირთვა |
| `project:tests:read` | ტესტების შედეგების წაკითხვა |
| `project:tests:write` | ტესტების შედეგების ატვირთვა |
| `project:builds:read` | ბილდის ანალიტიკის წაკითხვა |
| `project:builds:write` | ბილდის ანალიტიკის ატვირთვა |
| `project:runs:read` | ბრძანებების გაშვებების წაკითხვა |

### სკოუპების ჯგუფები {#scope-groups}

სკოუპების ჯგუფები საშუალებას გაძლევთ მოსახერხებლად მიანიჭოთ რამდენიმე დაკავშირებული სკოუპი ერთი იდენტიფიკატორით. როდესაც იყენებთ სკოუპების ჯგუფს, ის ავტომატურად ფართოვდება და მოიცავს ყველა ინდივიდუალურ სკოუპს, რომელიც მასში შედის.

| სკოუპების ჯგუფი | ჩართული სკოუპები |
| --- | --- |
| `ci` | `account:cache:write`, `project:cache:write`, `project:previews:write`, `project:bundles:write`, `project:tests:write`, `project:builds:write`, `project:runs:write` |
| `mcp` | `project:cache:read`, `project:previews:read`, `project:bundles:read`, `project:tests:read`, `project:builds:read`, `project:runs:read` |

### უწყვეტი ინტეგრაცია {#continuous-integration}

CI გარემოებისთვის, რომლებიც არ უჭერენ მხარს OIDC-ს, შექმენით ანგარიშის ტოკენი `ci` სკოუპების ჯგუფით თქვენი CI სამუშაო ნაკადების ავტორიზაციისთვის. დაფარდაზე ტოკენის გენერირებისას აირჩიეთ **CI** პრესეტი.

ასევე შეგიძლიათ შექმნათ იგივე ტოკენი CLI-დან:

```bash
tuist account tokens create account-handle --scopes ci --name ci
```

ეს ქმნის ტოკენს ყველა იმ სკოუპით, რომელიც საჭიროა ტიპური CI ოპერაციებისთვის (ქეში, პრევიუები, ბანდლები, ტესტები, ბილდები და გაშვებები). შეინახეთ გენერირებული ტოკენი როგორც საიდუმლო თქვენს CI გარემოში და დააყენეთ ის როგორც `TUIST_TOKEN` გარემოს ცვლადი.

### ანგარიშის ტოკენების მართვა {#managing-account-tokens}

გახსენით **პარამეტრები** > **ტოკენები** ანგარიშის დაფარდაზე, რათა ნახოთ ანგარიშის ტოკენები, შეამოწმოთ ტოკენის სკოუპები და პროექტებზე წვდომა, და გააუქმოთ ტოკენები როტაციის დროს.

ანგარიშის ყველა ტოკენის სიის სანახავად:

```bash
tuist account tokens list account-handle
```

ტოკენის სახელით გასაუქმებლად:

```bash
tuist account tokens revoke account-handle ci-cache-token
```

### ანგარიშის ტოკენების გამოყენება {#using-account-tokens}

ანგარიშის ტოკენები უნდა იყოს განსაზღვრული როგორც გარემოს ცვლადი `TUIST_TOKEN`:

```bash
export TUIST_TOKEN=your-account-token
```

> [!TIP]
> **როდის გამოვიყენოთ ანგარიშის ტოკენები**
>
> გამოიყენეთ ანგარიშის ტოკენები, როდესაც გჭირდებათ:
> - ავტორიზაცია CI გარემოებში, რომლებიც არ უჭერენ მხარს OIDC-ს
> - დაწვრილებითი კონტროლი იმაზე, თუ რა ოპერაციების შესრულება შეუძლია ტოკენს
> - ტოკენი, რომელსაც შეუძლია წვდომა ანგარიშის ფარგლებში მრავალ პროექტზე
> - დროით შეზღუდული ტოკენები, რომლებიც ავტომატურად ამოიწურება
