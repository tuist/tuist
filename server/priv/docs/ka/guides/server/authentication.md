# ავთენტიკაცია {#authentication}

სერვერთან ურთიერთობისთვის CLI-მ მოთხოვნები უნდა ავთენტიფიცირდეს [bearer authentication](https://swagger.io/docs/specification/authentication/bearer-authentication/)-ის გამოყენებით. CLI მხარდაჭერილია როგორც მომხმარებლის, ისე ანგარიშის სახელით ავთენტიკაციას, ან OIDC ტოკენის გამოყენებით.

## როგორც მომხმარებელი {#as-a-user}

როდესაც CLI-ს იყენებთ თქვენს კომპიუტერზე, ჩვენ გირჩევთ ავთენტიკაცია მომხმარებლის სახელით. მომხმარებლის სახელით ავთენტიკაციისთვის უნდა შეასრულოთ შემდეგი ბრძანება:

```bash
tuist auth login
```

ბრძანება გაგივლით ვებზე დაფუძნებულ ავთენტიკაციის პროცესში. ავთენტიკაციის შემდეგ, CLI შეინახავს ხანგრძლივი ვადის განახლების ტოკენს და ხანმოკლე ვადის წვდომის ტოკენს `~/.config/tuist/credentials` საქაღალდეში. დირექტორიაში არსებული თითოეული ფაილი წარმოადგენს დომენს, რომლის მიმართაც ავთენტიკაცია გაიარეთ, რაც ნაგულისხმევად უნდა იყოს `tuist.dev.json`. ამ დირექტორიაში შენახული ინფორმაცია მგრძნობიარეა, ამიტომ **დარწმუნდით, რომ ის უსაფრთხოდ ინახება**.

CLI ავტომატურად მოიძიებს სერთიფიკატებს სერვერთან მოთხოვნების შესრულებისას. თუ წვდომის ტოკენი ამოიწურა, CLI გამოიყენებს განახლების ტოკენს ახალი წვდომის ტოკენის მისაღებად.

> [!NOTE]
> თუ თქვენი ორგანიზაცია იყენებს ერთჯერად შესვლას (SSO), ბრაუზერში აირჩიეთ საწარმოს შესვლის ვარიანტი და შეიყვანეთ თქვენი სამუშაო ელფოსტის მისამართი. Tuist-ს შეუძლია პოვნა პროვაიდერის თქვენი არსებული ორგანიზაციის წევრობიდან ან <.localized_link href="/guides/integrations/authentication/sso#verify-a-login-email-domain">დადასტურებული შესვლის ელფოსტის დომენიდან</.localized_link>.

## OIDC ტოკენები {#oidc-tokens}

CI გარემოებისთვის, რომლებიც მხარს უჭერენ OpenID Connect-ს (OIDC), Tuist-ს შეუძლია ავტომატური ავთენტიკაცია გრძელვადიანი საიდუმლოების მართვის საჭიროების გარეშე. მხარდაჭერილ CI გარემოში გაშვებისას, CLI ავტომატურად აღმოაჩენს OIDC ტოკენის პროვაიდერს და ცვლის CI-ს მიერ მოწოდებულ ტოკენს Tuist-ის წვდომის ტოკენზე.

### მხარდაჭერილი პროვაიდერები {#supported-ci-providers}

Tuist აღიარებს ამ CI პროვაიდერებს და ასახავს მათ ტოკენებს პროექტებზე თქვენი რეპოზიტორიის კავშირის მეშვეობით:

- GitHub Actions
- CircleCI
- Bitrise

ნებისმიერი სხვა იდენტობის პროვაიდერი, რომელიც გასცემს OpenID Connect ტოკენებს, შეუძლია ავთენტიკაცია [სამუშაო დატვირთვის იდენტობის ნდობის პოლიტიკის](#workload-identity-trust-policies) მეშვეობით, რომელსაც ერთხელ აკონფიგურირებთ თქვენი ანგარიშის ყველა არსებული და მომავალი პროექტისთვის, მაგალითად [Fly.io Machines](#flyio-machines).

### OIDC ავთენტიკაციის დაყენება {#setting-up-oidc-authentication}

GitHub Actions-ის, CircleCI-ის და Bitrise-ისთვის:

1. **დააკავშირეთ თქვენი რეპოზიტორია Tuist-თან**: მიჰყევით <.localized_link href="/guides/integrations/gitforge/github">GitHub ინტეგრაციის სახელმძღვანელოს</.localized_link>, რათა დააკავშიროთ თქვენი GitHub რეპოზიტორია თქვენს Tuist პროექტთან.

2. **შეასრულეთ `tuist auth login`**: თქვენს CI სამუშაო ნაკადში, შეასრულეთ `tuist auth login` ნებისმიერ ბრძანებამდე, რომელიც მოითხოვს ავთენტიკაციას. CLI ავტომატურად აღმოაჩენს CI გარემოს და ავთენტიკაციას გაივლის OIDC-ის გამოყენებით.

იხილეთ <.localized_link href="/guides/integrations/continuous-integration">უწყვეტი ინტეგრაციის სახელმძღვანელო</.localized_link> პროვაიდერისთვის სპეციფიკური კონფიგურაციის მაგალითებისთვის.

### სამუშაო დატვირთვის იდენტობის ნდობის პოლიტიკები {#workload-identity-trust-policies}

ნდობის პოლიტიკა საშუალებას აძლევს სხვა იდენტობის პროვაიდერის სამუშაო დატვირთვებს, როგორიცაა განთავსების პლატფორმა, Kubernetes კლასტერი ან თვითმართვადი CI სისტემა, ჰქონდეთ წვდომა პროექტზე გრძელვადიანი Tuist საიდუმლოს გარეშე. პროვაიდერმა უნდა:

- იყოს ხელმისაწვდომი HTTPS-ით საჯარო მისამართზე. Tuist არ მიჰყვება გადამისამართებებს და არ უკავშირდება პირად ან შიდა ქსელის მისამართებს, მათ შორის თვითმასპინძელი Tuist სერვერებიდან.
- გასცეს JWT-ები, ხელმოწერილი ასიმეტრიული გასაღებით, მაგალითად `RS256` ან `ES256`. ხელმოუწერილი ტოკენები და ტოკენები, ხელმოწერილი საერთო საიდუმლოთი (`HS256` და მსგავსი), უარყოფილია.
- გამოაქვეყნოს თავისი ხელმოწერის გასაღებები JSON Web Key Set-ის (JWKS) სახით ფიქსირებულ HTTPS URL-ზე. პასუხი უნდა იყოს მაქსიმუმ 64 KiB და შეიცავდეს მაქსიმუმ 20 გასაღებს.
- შეიცავდეს ვადის ამოწურვას (`exp`) ყოველ ტოკენში.

GitHub Actions-ის, CircleCI-ის და Bitrise-ის გამცემები შენახულია ზემოთ აღწერილი რეპოზიტორიაზე დაფუძნებული ნაკადისთვის და არ შეიძლება მათი გამოყენება ნდობის პოლიტიკაში.

> [!NOTE]
> თვითმასპინძელი განთავსებისთვის, გამოიყენეთ მონაცემთა ბაზის მიგრაციები და განაახლეთ Tuist სერვერის ყოველი მომსახურე რეპლიკა სამუშაო დატვირთვების იდენტიფიკატორების კონფიგურაციამდე ან სამუშაოების გადატანამდე. შემდეგ განაახლეთ CLI ან Elixir ინტეგრაცია ვერსიამდე, რომელიც მხარს უჭერს `TUIST_OIDC_TOKEN` და `TUIST_OIDC_ACCOUNT`. არსებული GitHub Actions-ის, CircleCI-ის და Bitrise-ის სამუშაოები განაგრძობენ რეპოზიტორიაზე დაფუძნებული ავტორიზაციის გამოყენებას და არ მოითხოვენ ანგარიშის სახელს. წარმოების სამუშაოებზე გადასვლამდე, შეამოწმეთ ხანმოკლე ვადის ტოკენის გაცვლა და ქეშის ოპერაცია სასურველ სამუშაო დატვირთვასთან. ახალი გაცვლების შეჩერებისთვის, წაშალეთ პოლიტიკა; დაუშვით ერთ საათამდე უკვე გაცემული Tuist წვდომის ტოკენების ამოწურვა. პოლიტიკის წაშლა არ აუქმებს დაუყოვნებლივ ამ ტოკენებს.

#### პოლიტიკის შექმნა {#create-a-trust-policy}

Tuist დაფისზე, გახსენით თქვენი ანგარიშის **პარამეტრები** > **ავთენტიკაცია** და იპოვეთ **სამუშაო დატვირთვების იდენტიფიკატორები** სექცია. თქვენ უნდა იყოთ ანგარიშის ადმინისტრატორი (ან პირადი ანგარიშის მფლობელი). თითოეულ ანგარიშს შეიძლება ჰქონდეს მაქსიმუმ 20 პოლიტიკა. კონფიგურაცია იდენტიფიკატორის ერთხელ ანგარიშის მასშტაბით CI წვდომისთვის; პროექტის შერჩევა არ არის საჭირო.

გამოიყენეთ გადამრთველი **სამუშაო დატვირთვების იდენტიფიკატორების** გვერდით პოლიტიკის ფორმის გასახსნელად. გადამრთველი იწყება ჩართულ მდგომარეობაში, როდესაც ანგარიშს აქვს შენახული იდენტიფიკატორები და რჩება ჩართული შენახვის შემდეგ. ის იწყება გამორთულ მდგომარეობაში ანგარიშებისთვის იდენტიფიკატორების გარეშე. სექცია ჩნდება **SCIM მიწოდების** ქვემოთ ორგანიზაციებისთვის. ფორმის დამალვა ინარჩუნებს თქვენს ნახაზს და არ თიშავს სამუშაო დატვირთვების ავთენტიკაციას: შენახული იდენტიფიკატორების ბარათები და დაყენების დოკუმენტაციის ბმული რჩება ხილული. თითოეული ბარათი აჩვენებს იდენტიფიკატორის სახელს, გამცემის და JWKS URL-ებს, აუდიენციას, ზუსტ JSON მოთხოვნებს, ანგარიშის მასშტაბით მოცულობას და შექმნის დროს. წაშალეთ იდენტიფიკატორი მის ბარათზე არსებული ქმედების გამოყენებით.

აირჩიეთ **მორგებული პროვაიდერი** ქვემოთ მოცემული ველების შესაყვანად, ან **Fly.io Machines** მათი გენერირებისთვის თქვენი ორგანიზაციის slug-ის და რიცხვითი ორგანიზაციის და აპლიკაციის ID-ების მიხედვით. Fly შაბლონი ინარჩუნებს გენერირებულ გამცემს, JWKS URL-ს და მოთხოვნებს რედაქტირებად **დამატებითი კონფიგურაციის** ქვეშ. შაბლონების ან დამხმარე მნიშვნელობების შეცვლა ინარჩუნებს ხელით რედაქტირებულ ველებს. თუ თქვენი გამცემი, JWKS URL ან მოთხოვნები გადაფარავს შაბლონს, Tuist აფართოებს **დამატებით კონფიგურაციას** და აჩვენებს გაფრთხილებას, რათა შეამოწმოთ შენახული პოლიტიკა. გადადით უკან **მორგებულ პროვაიდერზე** გაგრძელებისთვის Fly დამხმარეების გარეშე. შაბლონები მხოლოდ ავსებენ კონფიგურაციას და არ ცვლიან Tuist-ის მიერ ტოკენების ვერიფიკაციის წესს.

| ველი | აღწერა |
| --- | --- |
| სახელი | პოლიტიკის ამოსაცნობი ნიშანი, უნიკალური ანგარიშის ფარგლებში. |
| გამცემის URL | ტოკენის `iss` მოთხოვნა. ის უნდა ემთხვეოდეს ზუსტად, ნებისმიერი ბოლო სლეშის ჩათვლით. |
| JWKS URL | პროვაიდერის ხელმოწერის გასაღებების HTTPS URL. Tuist იყენებს ამ URL-ს პირდაპირ და არ კითხულობს პროვაიდერის OpenID Connect აღმოჩენის დოკუმენტს, ამიტომ დააკოპირეთ `jwks_uri` პროვაიდერის დოკუმენტაციიდან ან `<issuer>/.well-known/openid-configuration`-დან. |
| აუდიტორია | აუდიტორია, რომლისთვისაც უნდა გაიცეს ტოკენი, ნაგულისხმევად `tuist`. ტოკენის `aud` უნდა ემთხვეოდეს მას ან, როცა `aud` სიაა, შეიცავდეს მას. გამოიყენეთ მნიშვნელობა, რომელსაც მხოლოდ Tuist იღებს, რათა სხვა სერვისებისთვის გამოშვებული ტოკენები აქ ვერ განმეორდეს. |
| მოთხოვნები | JSON ობიექტი 1-დან 10-მდე მოთხოვნით, რომელიც ტოკენმა უნდა შეიცავდეს, მაგალითად `{"sub": "system:serviceaccount:ci:builder"}`. JSON შეყვანა შემოიფარგლება 8 KiB-ით. მნიშვნელობები უნდა იყოს სტრინგები, ნიშნიანი 64-ბიტიანი მთელი რიცხვები ან ბულიანები და ისინი ზუსტად უნდა ემთხვეოდეს, მათი ტიპის ჩათვლით: `"123"` არ ემთხვევა `123`-ს. ჩადგმული ობიექტები, სიები და დროის ან ტოკენის მოთხოვნები, როგორიცაა `iss`, `aud`, `exp`, `nbf`, `iat` და `jti`, არ არის დაშვებული. |

თითოეული პოლიტიკა ანიჭებს CI წვდომას **ანგარიშის ყველა მიმდინარე და მომავალ პროექტზე**, ინდივიდუალური პროექტების შერჩევის გარეშე. თქვენ შეგიძლიათ კონფიგურაცია გაუკეთოთ იდენტობას პირველი პროექტის შექმნამდე. ეს არ ანიჭებს ანგარიშის ადმინისტრირებას ან წვდომას სხვა ანგარიშზე.

ყველა სამუშაო გარემოს, რომელსაც შეუძლია მიიღოს ტოკენი შესაბამისი მოთხოვნებით, შეუძლია წვდომა ჰქონდეს ყველა ამ პროექტზე, ამიტომ აირჩიეთ მოთხოვნები, რომლებსაც პროვაიდერი გარანტირებულად უზრუნველყოფს და რომელთა განმეორებითი გამოყენება შეუძლებელია. სასურველია სტაბილური რიცხვითი ID-ები იმ სახელების ნაცვლად, რომლებიც შეიძლება გადაერქვას ან ხელახლა დარეგისტრირდეს წაშლის შემდეგ.

> [!WARNING]
> გაზიარებულ იდენტობის პროვაიდერზე, დააკავშირეთ პოლიტიკა თქვენს ორგანიზაციასთან ან ტენანტთან **და** სასურველ აპლიკაციასთან, პროექტთან ან სერვისის ანგარიშთან. ტოტის სახელი, როგორიცაა `main`, გარემო, როგორიცაა `production`, ან ზოგადი როლი მარტო არ არის იდენტობის საზღვარი: სხვა ტენანტმა შეიძლება მიიღოს ტოკენი იგივე მნიშვნელობებით. მაგალითად, GitLab.com პოლიტიკა უნდა შეიცავდეს სასურველი პროექტის სტაბილურ `project_id`-ს, არა მხოლოდ `ref`-ს. შესაბამისი ტოკენი ანიჭებს ანგარიშის მასშტაბით CI წვდომას, ქეშში ჩაწერის ჩათვლით, ამიტომ პოლიტიკამ, რომელიც ენდობა არარელევანტურ სამუშაო გარემოებს, შეიძლება დაუშვას ქეშის მოწამვლა.

Tuist ანიჭებს წვდომას მხოლოდ იმ პოლიტიკებისთვის, რომელთა საკუთარ JWKS URL-ზე ინახება ტოკენის ხელმომწერი გასაღები, გამცემის, აუდიტორიის, ვადის, არა-ადრე დროის (60 წამამდე საათის ცდომილებით) და ყველა მოთხოვნის შემოწმების შემდეგ. გაცემული ერთსაათიანი CI ტოკენი მოქმედებს ანგარიშის მასშტაბით და არ არის პროექტების ID-ების სნაპშოტი: ის მოიცავს პროექტებს, რომლებიც შეიქმნა ან გადაიტანეს ანგარიშზე გაცემის შემდეგ. პროექტის ავტორიზაცია კვლავ მოითხოვს ანგარიშის მიმდინარე მფლობელობას, ამიტომ პროექტის გადატანა ანგარიშიდან აშორებს მის წვდომას ამ ანგარიშის ტოკენის ქვეშ.

#### სამუშაო გარემოს ავტორიზაცია {#authenticate-a-workload}

1. მოითხოვეთ იდენტობის ტოკენი თქვენი პროვაიდერისგან პოლიტიკის აუდიტორიით.
2. დააყენეთ `TUIST_OIDC_TOKEN` ამ ტოკენზე და `TUIST_OIDC_ACCOUNT` იმ Tuist ანგარიშის handle-ზე, რომელიც ფლობს პროექტს. ანგარიში საჭიროა ყოველი ნდობის პოლიტიკის გაცვლისთვის. ის მხოლოდ განსაზღვრავს, სად უნდა მოხდეს ძიება და თავისთავად არაფერს ანიჭებს.
3. გაუშვით `tuist auth login`. Elixir პროექტებისთვის, შეგიძლიათ გამოიყენოთ `mix tuist.login` ნაცვლად, ან მიანდოთ Elixir ინტეგრაციას ტოკენის ავტომატური გაცვლა, როცა არ არის ხელმისაწვდომი `TUIST_TOKEN` ან მოქმედი შენახული კრედენციალები.

მიღებულ Tuist წვდომის ტოკენს აქვს მხოლოდ `ci` სკოუპების ჯგუფი და მოიცავს არჩეული ანგარიშის ყველა მიმდინარე და მომავალ პროექტს. გაცვლები ვერ ხერხდება, თუ ანგარიშში 20-ზე მეტი პოლიტიკა ემთხვევა ერთსა და იმავე ტოკენს ან თუ ისინი იყენებენ ორზე მეტ განსხვავებულ JWKS URL-ს.

Tuist არ აახლებს ამ სესიებს. წვდომის ტოკენები იწურება ერთი საათის შემდეგ და არ აქვთ განახლების ტოკენი. პროვაიდერის იდენტობის ტოკენები ხშირად მოქმედებს მხოლოდ რამდენიმე წუთის განმავლობაში, ამიტომ ძველი `TUIST_OIDC_TOKEN`-ის შენახვა არ არის განახლების სტრატეგია: სამუშაოებისთვის, რომლებიც ერთ საათზე მეტხანს გრძელდება, მოითხოვეთ ახალი იდენტობის ტოკენი და შედით ხელახლა Tuist სესიის ამოწურვამდე. პოლიტიკის წაშლა აჩერებს ახალ გაცვლებს, მაგრამ უკვე გაცემული წვდომის ტოკენები ძალაში რჩება მათ ამოწურვამდე.

Tuist აქეშებს პროვაიდერის ხელმოწერის გასაღებებს 15 წუთის განმავლობაში წარმატებული მიღების შემდეგ სპეციალურ, ზომით შეზღუდულ ქეშში. ჩანაწერები შეიძლება ადრე ამოიღონ და ხელახლა მიიღონ. წარუმატებელი მიღებები არ აქეშდება. თუ თქვენი პროვაიდერი აბრუნებს გასაღებებს, მან უნდა გამოაქვეყნოს ახალი გასაღები თავის JWKS-ში ტოკენებით ხელმოწერამდე სულ მცირე 15 წუთით ადრე, რადგან ტოკენები, რომლებიც ხელმოწერილია გასაღებით, რომელიც არ არის აქეშებულ ნაკრებში, უარყოფილი იქნება ქეშის ამოწურვამდე. ტოკენები გასაღების ID-ის (`kid`) გარეშე მიღებულია მხოლოდ მაშინ, როცა JWKS შეიცავს ერთადერთ შესაბამის ხელმოწერის გასაღებს. როცა გასაღების ID არის JWKS-ში, ის უნდა იყოს სტრინგი არაუმეტეს 256 ბაიტისა.

> [!NOTE]
> `TUIST_OIDC_TOKEN` არის ზოგადი ტოკენის შეყვანა და არა სერვერის ნდობის გვერდის ავლის საშუალება. ის უპირატესობას ანიჭებს CI პროვაიდერის აღმოჩენას და სერვერი კვლავ იღებს მხოლოდ ჩაშენებულ პროვაიდერებს და იდენტობებს შესაბამისი ნდობის პოლიტიკით. არ ჩასვათ იდენტობის ტოკენი `TUIST_TOKEN`-ში, რომელიც ელის Tuist კრედენციალს.

თუ გაცვლა ვერ ხერხდება, შეამოწმეთ, რომ გამცემი, აუდიტორია და პოლიტიკის ყველა მოთხოვნა ზუსტად ემთხვევა ტოკენს, რომ JWKS URL ემსახურება ტოკენის ხელმომწერ გასაღებს, რომ პოლიტიკა არ არის წაშლილი და რომ `TUIST_OIDC_ACCOUNT` ასახელებს ანგარიშს, რომელიც ფლობს პროექტს. იმისთვის, რომ არ გაამჟავნოს, რომელი იდენტობებია სანდო, Tuist აბრუნებს ერთსა და იმავე შეცდომას ყველა ამ შემთხვევისთვის.

### Fly.io Machines {#flyio-machines}

[Fly.io მხარდაჭერას უწევს OIDC სამუშაო იდენტობას](https://docs.fly.io/reference/openid-connect/). Machine-ს შეუძლია მოითხოვოს მოკლე ვადიანი, ხელმოწერილი იდენტობის ტოკენი თავისი ლოკალური `/.fly/api` Unix სოკეტიდან, Fly API ტოკენის ან ხანგრძლივი Tuist საიდუმლოს გარეშე. Fly ტოკენები აიდენტიფიცირებენ ორგანიზაციას და აპლიკაციას, არა წყაროს რეპოზიტორიას, ამიტომ გამოიყენეთ ნდობის პოლიტიკა GitHub რეპოზიტორიის დაკავშირების ნაცვლად:

1. მიიღეთ გამცემი (`iss`), ორგანიზაციის ID (`org_id`) და აპლიკაციის ID (`app_id`) თქვენს Fly Machine-ში გაცემული იდენტობის ტოკენიდან. გამცემი არის `https://oidc.fly.io/<organization-slug>`. გამოიყენეთ რიცხვითი ID-ები, არა ორგანიზაციის ან აპის სახელები.
2. [შექმენით ნდობის პოლიტიკა](#create-a-trust-policy) **Fly.io Machines** შაბლონის გამოყენებით და შეიყვანეთ ორგანიზაციის slug და ორივე რიცხვითი ID. ის ავსებს ქვემოთ მოცემულ მნიშვნელობებს და ინარჩუნებს ID-ებს სტრინგებად. ასევე შეგიძლიათ შეიყვანოთ ისინი ხელით **მორგებული პროვაიდერის** გამოყენებით; შეინარჩუნეთ ბრჭყალები ID-ების გარშემო მოთხოვნებში.

   | ველი | მნიშვნელობა |
   | --- | --- |
   | გამცემის URL | `https://oidc.fly.io/<organization-slug>` |
   | JWKS URL | `https://oidc.fly.io/<organization-slug>/.well-known/jwks` |
   | აუდიტორია | `tuist` |
   | მოთხოვნები | `{"org_id": "<organization-id>", "app_id": "<application-id>"}` |

3. Machine-ის შიგნით, დააყენეთ `TUIST_OIDC_ACCOUNT` Tuist ანგარიშის handle-ზე, რომელიც ფლობს პროექტს (არა Fly ორგანიზაციის slug), მოითხოვეთ ტოკენი აუდიტორიით `tuist` და გადაეცით ის `tuist auth login`-ს `TUIST_OIDC_TOKEN`-ის გამოყენებით:

```bash
set -euo pipefail
export TUIST_OIDC_ACCOUNT="my-tuist-account"

TUIST_OIDC_TOKEN="$(curl --fail --silent --show-error \
  --unix-socket /.fly/api \
  -X POST http://localhost/v1/tokens/oidc \
  -H 'Content-Type: application/json' \
  --data '{"aud":"tuist"}')"
export TUIST_OIDC_TOKEN

tuist auth login
unset TUIST_OIDC_TOKEN
```

საწყისი კონფიგურაციისთვის შეგიძლიათ ლოკალურად შეამოწმოთ მხოლოდ იდენტობის ველები ტოკენის ექსპორტირების შემდეგ და მისი გაუქმებამდე. ეს დეკოდირებს მოთხოვნებს კონფიგურაციისთვის; Tuist ცალკე ამოწმებს ხელმოწერას ავტორიზაციის დროს:

```bash
python3 - <<'PY'
import base64, json, os
payload = os.environ["TUIST_OIDC_TOKEN"].split(".")[1]
claims = json.loads(base64.urlsafe_b64decode(payload + "=" * (-len(payload) % 4)))
print(json.dumps({key: claims[key] for key in ("iss", "org_id", "app_id")}, indent=2))
PY
```

არ დაბეჭდოთ ან არ ჩააკომიტოთ თავად ტოკენი. ნებისმიერ Machine-ს ავტორიზებულ Fly აპში შეუძლია ავტორიზაცია Tuist ანგარიშის ყველა მიმდინარე და მომავალ პროექტზე. შექმენით ცალკე პოლიტიკა თითოეული დამატებითი აპისთვის. Fly იდენტობის ტოკენები იწურება დაახლოებით ათ წუთში, ამიტომ ხანგრძლივად მომუშავე Machine-ებზე მოითხოვეთ ახალი და გაუშვით `tuist auth login` კვლავ ერთსაათიანი Tuist სესიის ამოწურვამდე.

### OIDC ტოკენის სკოუპები {#oidc-token-scopes}

GitHub Actions-ის, CircleCI-ის და Bitrise-ისთვის ეს უზრუნველყოფს წვდომას რეპოზიტორიასთან დაკავშირებულ ყველა პროექტზე. სამუშაო იდენტობის ნდობის პოლიტიკებისთვის ეს უზრუნველყოფს წვდომას შერჩეული ანგარიშის მიერ ფლობილ ყველა მიმდინარე და მომავალ პროექტზე, პროექტის შექმნის, პროექტის ადმინისტრირების, runner-ების ადმინისტრირების ან ანგარიშის წევრების ადმინისტრირების უფლების მინიჭების გარეშე. დეტალებისთვის, თუ რას მოიცავს `ci` სკოუპი, იხილეთ [სკოუპების ჯგუფები](#scope-groups).

> - არ არის საიდუმლოები, რომლებიც უნდა შეიცვალოს ან იმართოს
> - ტოკენები მოკლე ვადიანია

Gradle პლაგინი იყენებს Tuist CLI ავტორიზაციის მდგომარეობას და არ განსაზღვრავს ცალკე შესვლის ნაკადს. ავტორიზაცია ერთხელ CLI-ით და პლაგინი ხელახლა გამოიყენებს ამ მონაცემებს.

პროექტის და სერვერის კონფიგურაციისთვის, `project`-ის და `url`-ის ჩათვლით, გამოიყენეთ კანონიკური <.localized_link href="/references/tuist-toml">tuist.toml მითითება</.localized_link>.

ლოკალური გამოყენებისთვის, გაუშვით:

```bash
tuist auth login
```

CI-ისთვის, გამოიყენეთ ერთ-ერთი:

- <.localized_link href="/guides/server/authentication#setting-up-oidc-authentication">OIDC ავტორიზაცია</.localized_link> (რეკომენდებულია, როცა ხელმისაწვდომია)
- <.localized_link href="/guides/server/authentication#continuous-integration">ანგარიშის ტოკენით ავტორიზაცია</.localized_link> `TUIST_TOKEN`-ის მეშვეობით

თვითმასპინძელი Tuist სერვერებისთვის, განსაზღვრეთ სერვერის URL `tuist.toml`-ში (მაგალითად `url = "https://tuist.your-company.com"`) და გაუშვით სტანდარტული შესვლის ნაკადი. URL იხსნება იმავე კონფიგურაციის ფაილიდან, რომელსაც პლაგინი იყენებს.

ავტორიზაციის კონფიგურაციის შემდეგ, ჩვეულებრივად გაუშვით თქვენი Gradle ქეშირების ბრძანებები და ამოცანები.

## ანგარიშის ტოკენები {#account-tokens}

CI გარემოებისთვის, რომლებიც არ უჭერენ მხარს OIDC-ს, ან როცა გჭირდებათ წვდომებზე ზუსტი კონტროლი, შეგიძლიათ გამოიყენოთ ანგარიშის ტოკენები. ანგარიშის ტოკენები საშუალებას გაძლევთ ზუსტად მიუთითოთ, თუ რომელ სკოუპებსა და პროექტებზე აქვს ტოკენს წვდომა.

### ანგარიშის ტოკენის შექმნა {#creating-an-account-token}

ანგარიშის ტოკენის შექმნის ყველაზე მარტივი გზა დაშბორდიდან არის:

1. გახსენით ორგანიზაცია Tuist დაშბორდზე.
2. გადადით **პარამეტრებში** > **ტოკენები**.
3. აირჩიეთ **ტოკენის გენერირება**.
4. აირჩიეთ სახელი, არასავალდებულო ვადა, პროექტის წვდომა და სკოუპები, რომლებიც ტოკენს სჭირდება.
5. დააკოპირეთ გენერირებული ტოკენის მნიშვნელობა დიალოგის დახურვამდე. ტოკენის მნიშვნელობები მხოლოდ ერთხელ ჩანს.

ასევე შეგიძლიათ შექმნათ ანგარიშის ტოკენები CLI-დან, რაც სასარგებლოა სკრიპტინგისთვის ან ავტომატიზაციისთვის:

```bash
tuist account tokens create account-handle \
  --scopes account:cache:write project:cache:read project:cache:write \
  --name ci-cache-token \
  --expires 1y
```

> [!IMPORTANT]
> ჩაანაცვლეთ `account-handle` იმ ანგარიშის handle-ით, რომელიც ფლობს პროექტებს, რომლებზეც გსურთ ტოკენს ჰქონდეს წვდომა. ეს შეიძლება იყოს ორგანიზაციის ანგარიში, არა აუცილებლად თქვენი პირადი ანგარიში.

ბრძანება იღებს შემდეგ პარამეტრებს:

| პარამეტრი | აღწერა |
| --- | --- |
| `--scopes` | სავალდებულო. სკოუპების მძიმით გამოყოფილი სია ტოკენისთვის მისანიჭებლად. |
| `--name` | სავალდებულო. ტოკენის უნიკალური იდენტიფიკატორი (1-32 სიმბოლო, მხოლოდ ალფანუმერული, დეფისები და ქვედა ტირეები). |
| `--expires` | არასავალდებულო. როდის უნდა ამოიწუროს ტოკენი. გამოიყენეთ ფორმატი, როგორიცაა `30d` (დღეები), `6m` (თვეები) ან `1y` (წლები). თუ არ არის მითითებული, ტოკენი არასდროს იწურება. |
| `--projects` | შეზღუდეთ ტოკენი კონკრეტული პროექტის handle-ებზე. ტოკენს აქვს წვდომა ყველა პროექტზე, თუ არ არის მითითებული. |

### სკოუპების ჯგუფები {#scope-groups}

სკოუპების ჯგუფები უზრუნველყოფს მოსახერხებელ გზას რამდენიმე დაკავშირებული სკოუპის მისანიჭებლად ერთი იდენტიფიკატორით. როდესაც იყენებთ სკოუპების ჯგუფს, ის ავტომატურად ფართოვდება და მოიცავს ყველა ინდივიდუალურ სკოუპს, რომელიც მასში შედის.

| სკოუპების ჯგუფი | შემავალი სკოუპები |
| --- | --- |
| `ci` | `account:cache:write`, `project:cache:write`, `project:previews:write`, `project:bundles:write`, `project:tests:write`, `project:builds:write`, `project:runs:write` |
| `mcp` | `project:cache:read`, `project:previews:read`, `project:bundles:read`, `project:tests:read`, `project:builds:read`, `project:runs:read` |

### უწყვეტი ინტეგრაცია {#continuous-integration}

CI გარემოებისთვის, რომლებიც არ უჭერენ მხარს OIDC-ს, შექმენით ანგარიშის ტოკენი `ci` სკოუპების ჯგუფით თქვენი CI workflow-ების ავთენტიკაციისთვის. დაფარდაზე ტოკენის გენერირებისას აირჩიეთ **CI** პრესეტი.

ასევე შეგიძლიათ შექმნათ იგივე ტოკენი CLI-დან:

```bash
tuist account tokens create account-handle --scopes ci --name ci
```

ეს ქმნის ტოკენს ყველა იმ სკოუპით, რაც საჭიროა ტიპური CI ოპერაციებისთვის (ქეში, პრევიუები, ბანდლები, ტესტები, აგებები და გაშვებები). შეინახეთ გენერირებული ტოკენი როგორც საიდუმლო თქვენს CI გარემოში და დააყენეთ ის როგორც `TUIST_TOKEN` გარემოს ცვლადი.

### ანგარიშის ტოკენების მართვა {#managing-account-tokens}

გახსენით **Settings** > **Tokens** ანგარიშის დაფარდაზე ანგარიშის ტოკენების სანახავად, ტოკენის სკოუპების და პროექტის წვდომის შესამოწმებლად და ტოკენების გაუქმებისთვის როტაციის დროს.

ანგარიშის ყველა ტოკენის სიის სანახავად:

```bash
tuist account tokens list account-handle
```

ტოკენის სახელით გაუქმებისთვის:

```bash
tuist account tokens revoke account-handle ci-cache-token
```

### ანგარიშის ტოკენების გამოყენება {#using-account-tokens}

ანგარიშის ტოკენები უნდა იყოს განსაზღვრული როგორც გარემოს ცვლადი `TUIST_TOKEN`:

```bash
export TUIST_TOKEN=your-account-token
```

> [!TIP]
> **როდის გამოვიყენოთ ანგარიშის ტოკენები**
>
> გამოიყენეთ ანგარიშის ტოკენები, როცა გჭირდებათ:
> - ავთენტიკაცია CI გარემოებში, რომლებიც არ უჭერენ მხარს OIDC-ს
