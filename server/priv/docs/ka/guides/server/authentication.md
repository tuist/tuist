# ავტორიზაცია {#authentication}

სერვერთან ურთიერთობისთვის CLI-მ მოთხოვნები უნდა დაამოწმოს [bearer ავტორიზაციის](https://swagger.io/docs/specification/authentication/bearer-authentication/) გამოყენებით. CLI მხარდაჭერილია მომხმარებლის, ანგარიშის ან OIDC ტოკენის სახელით ავტორიზაცია.

## მომხმარებლის სახელით {#as-a-user}

როდესაც CLI-ს იყენებთ თქვენს მანქანაზე ლოკალურად, გირჩევთ ავტორიზება მომხმარებლის სახელით. მომხმარებლის სახელით ავტორიზებისთვის უნდა გაუშვათ შემდეგი ბრძანება:

```bash
tuist auth login
```

ბრძანება გაგივლით ვებზე დაფუძნებულ ავტორიზაციის ნაკადს. ავტორიზაციის შემდეგ CLI შეინახავს ხანგრძლივი ვადის განახლების ტოკენს და ხანმოკლე ვადის წვდომის ტოკენს `~/.config/tuist/credentials` საქაღალდეში. დირექტორიის თითოეული ფაილი წარმოადგენს დომენს, რომლის მიმართაც მოხდა ავტორიზაცია; ნაგულისხმევად ეს უნდა იყოს `tuist.dev.json`. ამ დირექტორიაში შენახული ინფორმაცია კონფიდენციალურია, ამიტომ **აუცილებლად დაიცავით ის**.

CLI ავტომატურად მოიძიებს სერთიფიკატებს სერვერთან მოთხოვნების შესრულებისას. თუ წვდომის ტოკენი ვადაგასულია, CLI გამოიყენებს განახლების ტოკენს ახალი წვდომის ტოკენის მისაღებად.

> [!NOTE]
> თუ თქვენი ორგანიზაცია იყენებს ერთჯერად შესვლას (SSO), ბრაუზერში აირჩიეთ საწარმოს შესვლის ვარიანტი და შეიყვანეთ სამუშაო ელფოსტის მისამართი. Tuist-ს შეუძლია პროვაიდერის პოვნა თქვენი არსებული ორგანიზაციის წევრობიდან ან <.localized_link href="/guides/integrations/authentication/sso#verify-a-login-email-domain">ვერიფიცირებული შესვლის ელფოსტის დომენიდან</.localized_link>.

## OIDC ტოკენები {#oidc-tokens}

CI გარემოებისთვის, რომლებიც მხარს უჭერენ OpenID Connect-ს (OIDC), Tuist-ს შეუძლია ავტომატური ავტორიზაცია ხანგრძლივი ვადის საიდუმლოების მართვის საჭიროების გარეშე. მხარდაჭერილ CI გარემოში გაშვებისას CLI ავტომატურად აღმოაჩენს OIDC ტოკენის პროვაიდერს და ცვლის CI-ს მიერ მოწოდებულ ტოკენს Tuist-ის წვდომის ტოკენზე.

### მხარდაჭერილი პროვაიდერები {#supported-ci-providers}

Tuist ცნობს ამ CI პროვაიდერებს და ასახავს მათ ტოკენებს პროექტებზე თქვენი რეპოზიტორიის კავშირის მეშვეობით:

- GitHub Actions
- CircleCI
- Bitrise

[Amp](#amp-orbs) orbs ავტორიზდება Amp სამუშაო სივრცეების მეშვეობით, რომლებსაც თქვენს Tuist ანგარიშს უკავშირებთ, ხოლო [Claude Code სესიები](#claude-code-sessions) — Claude Code გარემოების მეშვეობით, რომლებსაც Tuist Sandboxes-ზე გასაშვებად უკავშირებთ.

ნებისმიერი სხვა იდენტობის პროვაიდერი, რომელიც გასცემს OpenID Connect ტოკენებს, შეუძლია ავტორიზაცია [სამუშაო დატვირთვის იდენტობის ნდობის პოლიტიკის](#workload-identity-trust-policies) მეშვეობით, რომელსაც ერთხელ აკონფიგურირებთ თქვენი ანგარიშის ყველა არსებული და მომავალი პროექტისთვის, მაგალითად [Fly.io Machines](#flyio-machines).

### OIDC ავტორიზაციის მორგება {#setting-up-oidc-authentication}

GitHub Actions-ის, CircleCI-ის და Bitrise-ისთვის:

1. **დაუკავშირეთ თქვენი რეპოზიტორია Tuist-ს**: მიჰყევით <.localized_link href="/guides/integrations/gitforge/github">GitHub ინტეგრაციის სახელმძღვანელოს</.localized_link>, რათა დაუკავშიროთ თქვენი GitHub რეპოზიტორია თქვენს Tuist პროექტს.

2. **მიანიჭეთ იდენტობის ტოკენი**: GitHub Actions-ზე მიანიჭეთ ჯობს `permissions: id-token: write`; CircleCI-ზე და Bitrise-ზე ჩართეთ OIDC პროექტისთვის. Tuist 4.218.0-დან, როდესაც CLI არ არის შესული და `TUIST_TOKEN` არ არის დაყენებული, ის აღმოაჩენს CI გარემოს და ცვლის იდენტობის ტოკენს პირველ მოთხოვნაზე, ამიტომ შესვლის ეტაპი არ არის საჭირო. ადრეულ ვერსიებს სჭირდებათ ჯერ `tuist auth login`, და მაინც შეგიძლიათ მისი გაშვება აშკარა შესვლისთვის და ადრეული შეცდომის მიღებისთვის, თუ გაცვლა უარყოფილია.

პროვაიდერისთვის სპეციფიკური კონფიგურაციის მაგალითებისთვის იხილეთ <.localized_link href="/guides/integrations/continuous-integration">უწყვეტი ინტეგრაციის სახელმძღვანელო</.localized_link>.

### Amp orbs {#amp-orbs}

[Amp](https://ampcode.com) orbs-ს შეუძლია გამოსცეს OIDC ტოკენები, რომლებიც აიდენტიფიცირებს მათ Amp სამუშაო სივრცეს. ერთხელ დაუკავშირეთ სამუშაო სივრცე თქვენს Tuist ანგარიშს და Tuist CLI და `tuist_ex` Mix ამოცანები ამ სამუშაო სივრცის ნებისმიერ orb-ში თვითნებურად შედიან, შენახული ტოკენის ან შესვლის ეტაპის გარეშე:

1. იპოვეთ ID-ები: სამუშაო სივრცის ნაკადში, რომელიც orb-ში მუშაობს, გაუშვით `echo $AMP_WORKSPACE_ID $AMP_PROJECT_ID`.
2. თქვენს Tuist ანგარიშში გახსენით **პარამეტრები → ინტეგრაციები**, Amp ბარათზე აირჩიეთ **სამუშაო სივრცის დაკავშირება** და ჩასვით სამუშაო სივრცის ID. მხოლოდ ერთი Amp პროექტის orbs-ის დასაშვებად, ასევე ჩასვით მისი პროექტის ID. თქვენ უნდა იყოთ ანგარიშის ადმინისტრატორი ან მფლობელი.
3. გამოიყენეთ Tuist სამუშაო სივრცის orbs-ში. როდესაც ის არ არის შესული, CLI ან Mix ამოცანა აღმოაჩენს orb-ს, გამოსცემს ტოკენს `amp orb id-token --audience https://tuist.dev`-ით და ცვლის მას Tuist სესიაზე. `tuist auth login` და `mix tuist.login` აკეთებენ იმავე გაცვლას აშკარად.

ისევე, როგორც [Amp-ის OIDC სახელმძღვანელოში](https://ampcode.com/manual/orbs/oidc) ნდობის კონფიგურაციებში, Tuist ამოწმებს Amp-ის ხელმოწერას ყოველ ტოკენზე და იღებს მას მხოლოდ მაშინ, როდესაც მისი აუდიტორია არის `https://tuist.dev`, მისი `token_use` არის `exchanged`, მისი `workspace_id` ემთხვევა დაკავშირებულ სამუშაო სივრცეს და, პროექტამდე შეზღუდული კავშირისთვის, მისი `project_id` ემთხვევა ამ პროექტს. მისმა `sub`-მა უნდა მიუთითოს იგივე სამუშაო სივრცე, ხოლო პროექტის კავშირისთვის — იგივე პროექტი, როგორც ამ პრეტენზიებში: `workspace:<workspace-id>:project:<project-id>:…`, რომელსაც `amp orb id-token` ნაგულისხმევად გამოსცემს.

ყველა orb, რომელსაც კავშირი უშვებს, იღებს CI წვდომას ანგარიშის მფლობელობაში არსებულ ყველა არსებულ და მომავალ პროექტზე, ქეშის ატვირთვების ჩათვლით. ის ასევე იღებს `account:sandboxes:write` სკოპს, რათა შექმნას <.localized_link href="/guides/features/sandboxes">sandboxes</.localized_link> და მათში გაუშვას ბრძანებები ანგარიშის წევრის მსგავსად, მაგალითად Linux orb-დან macOS sandbox-ზე აშენებისთვის. დაუკავშირეთ მხოლოდ ისეთი სამუშაო სივრცეები, რომელთა წევრებსაც ენდობით ამ წვდომით. ყურადღებით შეამოწმეთ ID: Tuist-ს არ შეუძლია დაადასტუროს, რომ თქვენ ეკუთვნით იმ სამუშაო სივრცეს, რომელსაც უკავშირებთ. თუ სამუშაო სივრცე დაკავშირებულია რამდენიმე Tuist ანგარიშთან, orbs-მა უნდა დააყენოს `TUIST_OIDC_ACCOUNT` იმ ანგარიშზე, რომელშიც შესვლაა საჭირო; მისი Amp პროექტის გარემოში დაყენება ასევე ინარჩუნებს შესვლას თქვენს ანგარიშზე მიბმულს. სამუშაო სივრცის გარეთ მყოფ ნაკადებს არ აქვთ სამუშაო სივრცის იდენტობა და არ შეუძლიათ კავშირის გამოყენება. გათიშეთ სამუშაო სივრცე Amp ბარათიდან ახალი შესვლების შესაჩერებლად; უკვე გაცემული სესიები ძალაში რჩებიან ერთი საათის შემდეგ ვადის გასვლამდე. სესიებს არ სჭირდებათ განახლების ტოკენი: როდესაც ერთ-ერთი ვადას ეწურება, orb-ში მყოფი CLI გამოსცემს ახალ Amp ტოკენს და ისევ ცვლის მას, რათან ხანგრძლივად მომუშავე orbs დარჩნენ შესულები, სანამ სამუშაო სივრცე დაკავშირებულია.

ნდობის პოლიტიკები Amp გამომცემლისთვის, რომლებიც შექმენით სამუშაო სივრცის დაკავშირებამდე, განაგრძობენ მუშაობას, როდესაც აყენებთ `TUIST_OIDC_ACCOUNT`-ს.

### Claude Code სესიები {#claude-code-sessions}

თვითმასპინძელ გარემოში თითოეული Claude Code ღრუბლოვანი სესია ატარებს იდენტობის ტოკენს, რომელსაც Anthropic აწერს ხელს (`CLAUDE_CODE_SESSION_ACCESS_TOKEN`). გარემოებში, რომლებსაც <.localized_link href="/guides/features/sandboxes/claude#claude-code">უკავშირებთ Tuist Sandboxes-ზე გასაშვებად</.localized_link>, Tuist გადასცემს მას სესიას როგორც `TUIST_OIDC_TOKEN`, რათა Tuist CLI-მ და `tuist_ex` Mix ამოცანებმა თვითნებურად შევიდნენ.

Tuist ამოწმებს Anthropic-ის ხელმოწერას და იღებს ტოკენს მხოლოდ მაშინ, როდესაც ის სესიის ტოკენია (`ccr:role` არის `session_worker`), რომლის გარემოც, სახელად აუდიენციაში, დაკავშირებულია Tuist ანგარიშთან და გააქტიურებულია. დაკავშირებული გარემოს თითოეული სესია იღებს CI წვდომას ანგარიშის ყველა მიმდინარე და მომავალ პროექტზე, კეშის ატვირთვების ჩათვლით, და შეუძლია შექმნას და გამოიყენოს ანგარიშის sandbox-ები, როგორც ანგარიშის წევრმა. შესაბამისად, ნებისმიერს, ვისაც თქვენი Claude ორგანიზაცია აძლევს გარემოს გამოყენების უფლებას, შეუძლია გამოაქვეყნოს თქვენს კეშში და დაიწყოს sandbox-ები, მაგალითად Mac აგებისთვის. სესიის Tuist სესიები იწურება ერთი საათის შემდეგ ან მის იდენტობის ტოკენთან ერთად, რაც უფრო ადრე მოხდება; ტოკენი არის ის, რითიც სესია დაიწყო და ნაგულისხმევად ოთხი საათი ძლებს, ამიტომ უფრო ხანგრძლივი სესია კარგავს Tuist-ზე წვდომას, სანამ მისი შემდეგი შეტყობინება არ განაახლებს მას ახალ runner-ზე. გათიშეთ ან დააინვალიდეთ გარემო ახალი შესვლების შესაჩერებლად.

### Workload identity ნდობის პოლიტიკები {#workload-identity-trust-policies}

ნდობის პოლიტიკა საშუალებას აძლევს workload-ებს სხვა იდენტობის პროვაიდერიდან, როგორიცაა დეპლოიმენტის პლატფორმა, Kubernetes კლასტერი ან თვითმართვადი CI სისტემა, მიიღონ წვდომა პროექტზე Tuist-ის ხანგრძლივი საიდუმლოს გარეშე. პროვაიდერმა უნდა:

- იყოს ხელმისაწვდომი HTTPS-ით საჯარო მისამართზე. Tuist არ მიჰყვება გადამისამართებებს და არ უკავშირდება პირად ან შიდა ქსელის მისამართებს, მათ შორის თვითმასპინძელი Tuist სერვერებიდან.
- გამოსცეს JWT-ები ასიმეტრიული გასაღებით ხელმოწერილი, მაგალითად `RS256` ან `ES256`. ხელმოუწერილი ტოკენები და ტოკენები, რომლებიც ხელმოწერილია გაზიარებული საიდუმლოთი (`HS256` და მსგავსი), უარყოფილია.
- გამოაქვეყნოს თავისი ხელმოწერის გასაღებები JSON Web Key Set-ის (JWKS) სახით ფიქსირებულ HTTPS URL-ზე. პასუხი უნდა იყოს მაქსიმუმ 64 KiB და შეიცავდეს მაქსიმუმ 20 გასაღებს.
- შეიცავდეს ვადის გასვლას (`exp`) თითოეულ ტოკენში.

GitHub Actions, CircleCI და Bitrise გამომცემლები შენახულია ზემოთ აღნიშნული რეპოზიტორიაზე დაფუძნებული ნაკადისთვის და არ შეიძლება მათი გამოყენება ნდობის პოლიტიკაში.

> [!NOTE]
> თვითმასპინძელი განლაგებისთვის, გამოიყენეთ მონაცემთა ბაზის მიგრაციები და განაახლეთ Tuist სერვერის ყველა მოქმედი რეპლიკა workload იდენტობების კონფიგურაციამდე ან მათზე სამუშაოების გადატანამდე. შემდეგ განაახლეთ CLI ან Elixir ინტეგრაცია ვერსიამდე, რომელიც მხარს უჭერს `TUIST_OIDC_TOKEN`-ს და `TUIST_OIDC_ACCOUNT`-ს. არსებული GitHub Actions, CircleCI და Bitrise სამუშაოები განაგრძობენ რეპოზიტორიაზე დაფუძნებული ავტორიზაციის გამოყენებას და არ საჭიროებენ ანგარიშის handle-ს. პროდუქციის სამუშაოებზე გადასვლამდე, შეამოწმეთ ხანმოკლე ტოკენის გაცვლა და კეშის ოპერაცია განკუთვნილ workload-თან. ახალი გაცვლების შესაჩერებლად, წაშალეთ პოლიტიკა; მისცეთ უკვე გაცემულ Tuist წვდომის ტოკენებს ვადის გასვლის დრო ერთ საათამდე. პოლიტიკის წაშლა არ აუქმებს იმ ტოკენებს დაუყოვნებლივ.

#### პოლიტიკის შექმნა {#create-a-trust-policy}

Tuist დაფაზე, გახსენით თქვენი ანგარიშის **Settings** > **Authentication** და იპოვეთ **Workload identities** სექცია. თქვენ უნდა იყოთ ანგარიშის ადმინისტრატორი (ან პირადი ანგარიშის მფლობელი). თითოეულ ანგარიშს შეიძლება ჰქონდეს მაქსიმუმ 20 პოლიტიკა. კონფიგურირეთ იდენტობა ერთხელ ანგარიშის მასშტაბით CI წვდომისთვის; პროექტის შერჩევა არ არის საჭირო.

გამოიყენეთ გადამრთველი **Workload identities**-ის გვერდით პოლიტიკის ფორმის გასახსნელად. გადამრთველი ჩართულია, როდესაც ანგარიშს აქვს შენახული იდენტობები და რჩება ჩართული შენახვის შემდეგ. ის იწყება გამორთული ანგარიშებისთვის იდენტობების გარეშე. სექცია ჩნდება **SCIM provisioning**-ის ქვემოთ ორგანიზაციებისთვის. ფორმის დამალვა ინარჩუნებს თქვენს პროექტს და არ თიშავს workload ავთენტიკაციას: შენახული იდენტობის ბარათები და დაყენების დოკუმენტაციის ბმული რჩება ხილული. თითოეული ბარათი აჩვენებს იდენტობის სახელს, გამომცემლის და JWKS URL-ებს, აუდიენციას, ზუსტ JSON პრეტენზიებს, ანგარიშის მასშტაბით მოცულობას და შექმნის დროს. წაშალეთ იდენტობა მის ბარათზე მოქმედების გამოყენებით.

აირჩიეთ **Custom provider** ქვემოთ მოცემული ველების შესაყვანად, ან **Fly.io Machines** მათი გენერირებისთვის თქვენი ორგანიზაციის slug-ის და რიცხვითი ორგანიზაციის და აპლიკაციის ID-ების მიხედვით. Fly შაბლონი ინარჩუნებს გენერირებულ გამომცემელს, JWKS URL-ს და პრეტენზიებს რედაქტირებადს **Advanced configuration**-ის ქვეშ. შაბლონების ან დამხმარე მნიშვნელობების ცვლილება ინარჩუნებს ველებს, რომლებიც ხელით დაარედაქტირეთ. თუ თქვენი გამომცემელი, JWKS URL ან პრეტენზიები გადაფარავს შაბლონს, Tuist აფართოებს **Advanced configuration**-ს და აჩვენებს გაფრთხილებას, რათა შეამოწმოთ პოლიტიკა, რომელიც შეინახება. გადადით უკან **Custom provider**-ზე Fly-ის დამხმარეების გარეშე გასაგრძელებლად. შაბლონები მხოლოდ ავსებენ კონფიგურაციას და არ ცვლიან იმას, თუ როგორ ამოწმებს Tuist ტოკენებს.

| ველი | აღწერა |
| --- | --- |
| სახელი | პოლიტიკის ამოსაცნობი ეტიკეტი, უნიკალური ანგარიშის ფარგლებში. |
| გამომცემლის URL | ტოკენის `iss` პრეტენზია. ის უნდა ემთხვეოდეს ზუსტად, ბოლო სლეშის ჩათვლით. |
| JWKS URL | პროვაიდერის ხელმოწერის გასაღებების HTTPS URL. Tuist იყენებს ამ URL-ს პირდაპირ და არ კითხულობს პროვაიდერის OpenID Connect აღმოჩენის დოკუმენტს, ამიტომ დააკოპირეთ `jwks_uri` პროვაიდერის დოკუმენტაციიდან ან `<issuer>/.well-known/openid-configuration`-დან. |

JSON შეყვანა შეზღუდულია 8 KiB-ით. მნიშვნელობები უნდა იყოს სტრინგები, ნიშნიანი 64-ბიტიანი მთელი რიცხვები ან ბულის ტიპის, და ისინი უნდა ემთხვეოდნენ ზუსტად, მათი ტიპის ჩათვლით: `"123"` არ ემთხვევა `123`-ს. ჩადგმული ობიექტები, სიები და დროის ან ტოკენის პრეტენზიები, როგორიცაა `iss`, `aud`, `exp`, `nbf`, `iat` და `jti`, არ არის დაშვებული. |

თითოეული პოლიტიკა ანიჭებს CI წვდომას **ანგარიშის ყველა მიმდინარე და მომავალ პროექტზე**, ინდივიდუალური პროექტების შერჩევის გარეშე. შეგიძლიათ კონფიგურირება იდენტობის პირველი პროექტის შექმნამდე. ეს არ ანიჭებს ანგარიშის ადმინისტრირებას ან წვდომას სხვა ანგარიშზე.

ნებისმიერ workload-ს, რომელსაც შეუძლია მიიღოს ტოკენი შესაბამისი პრეტენზიებით, შეუძლია წვდომა ჰქონდეს ყველა იმ პროექტზე, ამიტომ აირჩიეთ პრეტენზიები, რომლებსაც პროვაიდერი გარანტიას აძლევს და რომელთა ხელახლა გამოყენება არავის შეუძლია. უპირატესობა მიანიჭეთ სტაბილურ რიცხვით ID-ებს სახელების ნაცვლად, რომლებიც შეიძლება გადაერქვათ ან ხელახლა დარეგისტრირდნენ წაშლის შემდეგ.

> [!WARNING]
> საერთო იდენტობის პროვაიდერზე, დააკავშირეთ პოლიტიკა თქვენს ორგანიზაციასთან ან არენდატორთან **და** სასურველ აპლიკაციასთან, პროექტთან ან სერვისის ანგარიშთან. ტოტის სახელი, როგორიცაა `main`, გარემო, როგორიცაა `production`, ან ზოგადი როლი მხოლოდ არ არის იდენტობის საზღვარი: სხვა არენდატორმა შეიძლება მიიღოს ტოკენი იგივე მნიშვნელობებით. მაგალითად, GitLab.com-ის პოლიტიკამ უნდა შეიცავდეს სასურველი პროექტის სტაბილურ `project_id`-ს, არა მხოლოდ `ref`-ს. შესაბამისი ტოკენი ანიჭებს ანგარიშის მასშტაბით CI წვდომას, კეშში ჩაწერის ჩათვლით, ამიტომ პოლიტიკამ, რომელიც ენდობა არარელევანტურ workload-ებს, შეიძლება დაუშვას კეშის მოწამვლა.

Tuist ანიჭებს წვდომას მხოლოდ იმ პოლიტიკებისთვის, რომელთა საკუთარი JWKS URL შეიცავს ტოკენის ხელმომწერ გასაღებს, გამომცემლის, აუდიენციის, ვადის, not-before დროის (60 წამამდე საათის ცდომილებით) და ყოველი პრეტენზიის შემოწმების შემდეგ. გაცემული ერთსაათიანი CI ტოკენი მოქმედებს ანგარიშის მასშტაბით და არ არის პროექტების ID-ების სნეპშოტი: ის მოიცავს პროექტებს, რომლებიც შეიქმნა ან გადაიტანეს ანგარიშში გაცემის შემდეგ. პროექტის ავტორიზაცია კვლავ მოითხოვს ანგარიშის მიმდინარე მფლობელობას, ამიტომ პროექტის გადატანა ანგარიშიდან შლის მის წვდომას ამ ანგარიშის ტოკენის ქვეშ.

#### workload-ის ავთენტიკაცია {#authenticate-a-workload}

1. მოითხოვეთ იდენტობის ტოკენი თქვენი პროვაიდერისგან პოლიტიკის აუდიენციით.
2. დააყენეთ `TUIST_OIDC_TOKEN` ამ ტოკენზე და `TUIST_OIDC_ACCOUNT` Tuist-ის ანგარიშის handle-ზე, რომელიც ფლობს პროექტს. ანგარიში აუცილებელია ნდობის პოლიტიკის ყოველი გაცვლისთვის. ის მხოლოდ განსაზღვრავს სად უნდა მოხდეს ძებნა და თავისთავად არაფერს ანიჭებს.
3. გაუშვით Tuist. როდესაც `TUIST_TOKEN` ან მოქმედი შენახული სერთიფიკატები არ არის ხელმისაწვდომი, CLI და Elixir ინტეგრაცია ავტომატურად ახდენენ ტოკენის გაცვლას. `tuist auth login` და `mix tuist.login` აკეთებენ იგივე გაცვლას ცალსახად.

მიღებულ Tuist-ის წვდომის ტოკენს აქვს მხოლოდ `ci` სკოპების ჯგუფი და მოიცავს შერჩეული ანგარიშის ყველა მიმდინარე და მომავალ პროექტს. გაცვლა ვერ ხერხდება, თუ ანგარიშში 20-ზე მეტი პოლიტიკა ემთხვევა იგივე ტოკენს ან თუ ისინი იყენებენ ორზე მეტ განსხვავებულ JWKS URL-ს.

Tuist არ აახლებს ამ სესიებს. წვდომის ტოკენები იწურება ერთი საათის შემდეგ და არ აქვთ განახლების ტოკენი. პროვაიდერის იდენტობის ტოკენები ხშირად მოქმედებს მხოლოდ რამდენიმე წუთის განმავლობაში, ამიტომ ძველი `TUIST_OIDC_TOKEN`-ის შენახვა არ არის განახლების სტრატეგია: სამუშაოებისთვის, რომლებიც ერთ საათზე მეტხანს გრძელდება, მოითხოვეთ ახალი იდენტობის ტოკენი და გაიარეთ ავტორიზაცია ხელახლა Tuist-ის სესიის ამოწურვამდე. პოლიტიკის წაშლა აჩერებს ახალ გაცვლებს, მაგრამ უკვე გაცემული წვდომის ტოკენები ძალაში რჩება მათ ამოწურვამდე.

Tuist ათავსებს კეშში პროვაიდერის ხელმომწერ გასაღებს 15 წუთის განმავლობაში წარმატებული მოთხოვნის შემდეგ სპეციალურ, ზომით შეზღუდულ კეშში. ჩანაწერები შეიძლება ადრე ამოიღონ და ხელახლა მოითხოვონ. წარუმატებელი მოთხოვნები არ თავსდება კეშში. თუ თქვენი პროვაიდერი ატრიალებს გასაღებს, მან უნდა გამოაქვეყნოს ახალი გასაღები თავის JWKS-ში ტოკენებით ხელმოწერამდე სულ მცირე 15 წუთით ადრე, რადგან ტოკენები, რომლებიც ხელმოწერილია გასაღებით, რომელიც არ არის კეშირებულ ნაკრებში, უარყოფილი იქნება კეშის ამოწურვამდე. ტოკენები გასაღების ID-ის (`kid`) გარეშე მიიღება მხოლოდ მაშინ, როდესაც JWKS შეიცავს ერთ შესაბამის ხელმომწერ გასაღებს. როდესაც JWKS-ში არის გასაღების ID, ის უნდა იყოს სტრინგი არაუმეტეს 256 ბაიტისა.

> [!NOTE]
> `TUIST_OIDC_TOKEN` არის ზოგადი ტოკენის შეყვანა და არა სერვერის ნდობის გვერდის ავლის გზა. ის უპირატესობას ანიჭებს CI პროვაიდერის აღმოჩენას და სერვერი კვლავ იღებს მხოლოდ ჩაშენებულ პროვაიდერებს და იდენტობებს შესაბამისი ნდობის პოლიტიკით. არ ჩასვათ იდენტობის ტოკენი `TUIST_TOKEN`-ში, რომელიც ელოდება Tuist-ის სერთიფიკატს.

თუ გაცვლა ვერ მოხერხდა, შეამოწმეთ, რომ გამომცემელი, აუდიენცია და პოლიტიკის ყოველი პრეტენზია ზუსტად ემთხვევა ტოკენს, რომ JWKS URL ემსახურება ტოკენის ხელმომწერ გასაღებს, რომ პოლიტიკა არ არის წაშლილი და რომ `TUIST_OIDC_ACCOUNT` ასახელებს ანგარიშს, რომელიც ფლობს პროექტს. იმის თავიდან ასაცილებლად, რომელი იდენტობებია სანდო, Tuist აბრუნებს იგივე შეცდომას ყველა ამ შემთხვევისთვის.

### Fly.io Machines {#flyio-machines}

[Fly.io მხარს უჭერს OIDC workload იდენტობას](https://docs.fly.io/reference/openid-connect/). Machine-ს შეუძლია მოითხოვოს ხანმოკლე, ხელმოწერილი იდენტობის ტოკენი თავისი ლოკალური `/.fly/api` Unix სოკეტიდან, Fly API ტოკენის ან ხანგრძლივი Tuist საიდუმლოს გარეშე. Fly ტოკენები აიდენტიფიცირებენ ორგანიზაციას და აპლიკაციას, არა წყაროს რეპოზიტორიას, ამიტომ გამოიყენეთ ნდობის პოლიტიკა GitHub რეპოზიტორიის დაკავშირების ნაცვლად:

1. მიიღეთ გამომცემელი (`iss`), ორგანიზაციის ID (`org_id`) და აპლიკაციის ID (`app_id`) თქვენს Fly Machine-ში გაცემული იდენტობის ტოკენიდან. გამომცემელია `https://oidc.fly.io/<organization-slug>`. გამოიყენეთ რიცხვითი ID-ები, არა ორგანიზაციის ან აპის სახელები.
2. [შექმენით ნდობის პოლიტიკა](#create-a-trust-policy) **Fly.io Machines** შაბლონის გამოყენებით და შეიყვანეთ ორგანიზაციის slug და ორივე რიცხვითი ID. ის ავსებს ქვემოთ მოცემულ მნიშვნელობებს და ინარჩუნებს ID-ებს როგორც სტრინგებს. ასევე შეგიძლიათ შეიყვანოთ ისინი ხელით **Custom provider**-ის გამოყენებით; შეინარჩუნეთ ბრჭყალები ID-ების გარშემო პრეტენზიებში.

   | ველი | მნიშვნელობა |
   | --- | --- |
   | გამომცემლის URL | `https://oidc.fly.io/<organization-slug>` |
   | JWKS URL | `https://oidc.fly.io/<organization-slug>/.well-known/jwks` |
   | აუდიენცია | `tuist` |
   | პრეტენზიები | `{"org_id": "<organization-id>", "app_id": "<application-id>"}` |

3. Machine-ის შიგნით, დააყენეთ `TUIST_OIDC_ACCOUNT` Tuist-ის ანგარიშის handle-ზე, რომელიც ფლობს პროექტს (არა Fly ორგანიზაციის slug), მოითხოვეთ ტოკენი აუდიენციით `tuist` და გადაეცით ის `tuist auth login`-ს `TUIST_OIDC_TOKEN`-ის გამოყენებით:

```bash
set -euo pipefail
export TUIST_OIDC_ACCOUNT="my-tuist-account"

TUIST_OIDC_TOKEN="$(curl --fail --silent --show-error \
  --unix-socket /.fly/api \
  -X POST http://localhost/v1/tokens/oidc \
  -H 'Content-Type: application/json' \
  --data '{"aud":"tuist"}')"
export TUIST_OIDC_TOKEN

tuist auth login
unset TUIST_OIDC_TOKEN
```

საწყისი კონფიგურაციისთვის, შეგიძლიათ შეამოწმოთ მხოლოდ იდენტობის ველები ლოკალურად, ტოკენის ექსპორტირების შემდეგ და მის გაუქმებამდე. ეს აკოდირებს პრეტენზიებს კონფიგურაციისთვის; Tuist ცალკე ამოწმებს ხელმოწერას ავთენტიკაციის დროს:

```bash
python3 - <<'PY'
import base64, json, os
payload = os.environ["TUIST_OIDC_TOKEN"].split(".")[1]
claims = json.loads(base64.urlsafe_b64decode(payload + "=" * (-len(payload) % 4)))
print(json.dumps({key: claims[key] for key in ("iss", "org_id", "app_id")}, indent=2))
PY
```

არ დაბეჭდოთ ან არ დააკომიტოთ თავად ტოკენი. ნებისმიერ Machine-ს ავტორიზებულ Fly აპში შეუძლია ავთენტიკაცია გაიაროს Tuist ანგარიშის ყველა მიმდინარე და მომავალ პროექტზე. შექმენით ცალკე პოლიტიკა ყოველი დამატებითი აპისთვის. Fly იდენტობის ტოკენები იწურება დაახლოებით ათი წუთის შემდეგ, ამიტომ ხანგრძლივად მომუშავე Machine-ებზე მოითხოვეთ ახალი და გაუშვით `tuist auth login` ხელახლა ერთსაათიანი Tuist სესიის ამოწურვამდე.

### OIDC ტოკენის სკოპები {#oidc-token-scopes}

OIDC ტოკენებს ენიჭებათ `ci` სკოპების ჯგუფი. GitHub Actions-ის, CircleCI-ის და Bitrise-ისთვის, ეს უზრუნველყოფს წვდომას რეპოზიტორიასთან დაკავშირებულ ყველა პროექტზე. დაკავშირებული Amp სამუშაო სივრცეების, დაკავშირებული Claude Code გარემოების და workload იდენტობის ნდობის პოლიტიკებისთვის, ეს უზრუნველყოფს წვდომას შერჩეული ანგარიშის ყველა მიმდინარე და მომავალ პროექტზე, პროექტის შექმნის, პროექტის ადმინისტრირების, runner-ის ადმინისტრირების ან ანგარიშის წევრების ადმინისტრირების მინიჭების გარეშე. იხილეთ [სკოპების ჯგუფები](#scope-groups) დეტალებისთვის, რას მოიცავს `ci` სკოპი.

## Gradle პლაგინის ავთენტიკაცია {#gradle-plugin-authentication}

Gradle პლაგინი იყენებს Tuist CLI-ის ავთენტიკაციის მდგომარეობას და არ განსაზღვრავს ცალკე შესვლის პროცესს. ერთხელ გაიარეთ ავთენტიკაცია CLI-ით და პლაგინი ხელახლა გამოიყენებს ამ სერთიფიკატებს.

პროექტისა და სერვერის კონფიგურაციისთვის, მათ შორის `project` და `url`, გამოიყენეთ ოფიციალური <.localized_link href="/references/tuist-toml">tuist.toml-ის საცნობარო</.localized_link>.

ლოკალური გამოყენებისთვის, გაუშვით:

```bash
tuist auth login
```

CI-ისთვის, გამოიყენეთ ერთ-ერთი:

- <.localized_link href="/guides/server/authentication#setting-up-oidc-authentication">OIDC ავთენტიკაცია</.localized_link> (რეკომენდებულია, როცა ხელმისაწვდომია)
- <.localized_link href="/guides/server/authentication#continuous-integration">ანგარიშის ტოკენით ავთენტიკაცია</.localized_link> `TUIST_TOKEN`-ის მეშვეობით

თვითმასპინძელი Tuist სერვერებისთვის, განსაზღვრეთ სერვერის URL `tuist.toml`-ში (მაგალითად `url = "https://tuist.your-company.com"`) და გაუშვით სტანდარტული შესვლის პროცესი. URL მიიღება იმავე კონფიგურაციის ფაილიდან, რომელსაც პლაგინი იყენებს.

ავთენტიკაციის კონფიგურირების შემდეგ, ჩვეულებრივად გაუშვით თქვენი Gradle ქეშირების ბრძანებები და დავალებები.

## ანგარიშის ტოკენები {#account-tokens}

CI გარემოებისთვის, რომლებიც არ უჭერენ მხარს OIDC-ს, ან როცა საჭიროა ნებართვებზე ზუსტი კონტროლი, შეგიძლიათ გამოიყენოთ ანგარიშის ტოკენები. ანგარიშის ტოკენები საშუალებას გაძლევთ ზუსტად მიუთითოთ, თუ რომელ სკოპებსა და პროექტებზე აქვს ტოკენს წვდომა.

### ანგარიშის ტოკენის შექმნა {#creating-an-account-token}

ანგარიშის ტოკენის შექმნის ყველაზე მარტივი გზა არის დაშბორდიდან:

1. გახსენით ორგანიზაცია Tuist-ის დაშბორდში.
2. გადადით **პარამეტრებში** > **ტოკენები**.
3. აირჩიეთ **ტოკენის გენერირება**.
4. აირჩიეთ სახელი, ვადის გასვლის არასავალდებულო პარამეტრი, პროექტზე წვდომა და სკოპები, რომლებიც ტოკენს სჭირდება.
5. დახურვამდე დააკოპირეთ გენერირებული ტოკენის მნიშვნელობა. ტოკენის მნიშვნელობები მხოლოდ ერთხელ ჩანს.

ასევე შეგიძლიათ შექმნათ ანგარიშის ტოკენები CLI-დან, რაც სასარგებლოა სკრიპტინგისთვის ან ავტომატიზაციისთვის:

```bash
tuist account tokens create account-handle \
  --scopes account:cache:write project:cache:read project:cache:write \
  --name ci-cache-token \
  --expires 1y
```

> [!IMPORTANT]
> ჩაანაცვლეთ `account-handle` იმ ანგარიშის handle-ით, რომელსაც ეკუთვნის პროექტები, რომლებზეც ტოკენს წვდომა უნდა ჰქონდეს. ეს შეიძლება იყოს ორგანიზაციის ანგარიში და არა აუცილებლად თქვენი პირადი ანგარიში.

ბრძანება იღებს შემდეგ პარამეტრებს:

| პარამეტრი | აღწერა |
| --- | --- |
| `--scopes` | სავალდებულო. სკოპების სია, გამოყოფილი გამოტოვებით, რომლებიც ტოკენს მიენიჭება. |
| `--name` | სავალდებულო. ტოკენის უნიკალური იდენტიფიკატორი (1-32 სიმბოლო, მხოლოდ ალფანუმერული, დეფისები და ქვედა ხაზები). |
| `--expires` | არასავალდებულო. როდის უნდა გაუვიდეს ტოკენს ვადა. გამოიყენეთ ფორმატი, როგორიცაა `30d` (დღეები), `6m` (თვეები) ან `1y` (წლები). თუ არ არის მითითებული, ტოკენს ვადა არასდროს გაუვა. |
| `--projects` | შეზღუდეთ ტოკენი კონკრეტული პროექტების handle-ებით. თუ არ არის მითითებული, ტოკენს აქვს წვდომა ყველა პროექტზე. |

### სკოპების ჯგუფები {#scope-groups}

სკოპების ჯგუფები მოხერხებულ გზას გთავაზობთ რამდენიმე დაკავშირებული სკოპის მინიჭებისთვის ერთი იდენტიფიკატორით. როდესაც იყენებთ სკოპების ჯგუფს, ის ავტომატურად ფართოვდება და მოიცავს ყველა ინდივიდუალურ სკოპს, რომელიც მასში შედის.

| სკოპების ჯგუფი | შემავალი სკოპები |
| --- | --- |
| `ci` | `account:cache:write`, `project:cache:write`, `project:previews:write`, `project:bundles:write`, `project:tests:write`, `project:builds:write`, `project:runs:write` |
| `mcp` | `project:cache:read`, `project:previews:read`, `project:bundles:read`, `project:tests:read`, `project:builds:read`, `project:runs:read` |

### უწყვეტი ინტეგრაცია {#continuous-integration}

CI გარემოებისთვის, რომლებიც არ უჭერენ OIDC-ს მხარს, შექმენით ანგარიშის ტოკენი `ci` სკოპების ჯგუფით თქვენი CI სამუშაო ნაკადების ავთენტიკაციისთვის. დაფარდაზე ტოკენის გენერირებისას აირჩიეთ **CI** პრესეტი.

იგივე ტოკენის შექმნა CLI-დანაც შეგიძლიათ:

```bash
tuist account tokens create account-handle --scopes ci --name ci
```

ეს ქმნის ტოკენს ყველა იმ სკოპით, რომელიც საჭიროა ტიპური CI ოპერაციებისთვის (ქეში, პრივიუები, ბანდლები, ტესტები, ბილდები და გაშვებები). შეინახეთ გენერირებული ტოკენი როგორც საიდუმლო თქვენს CI გარემოში და დააყენეთ ის როგორც `TUIST_TOKEN` გარემოს ცვლადი.

### ანგარიშის ტოკენების მართვა {#managing-account-tokens}

გახსენით **Settings** > **Tokens** ანგარიშის დაფარდაზე, რათა ნახოთ ანგარიშის ტოკენები, შეამოწმოთ ტოკენის სკოპები და პროექტებზე წვდომა, და გააუქმოთ ტოკენები როტაციის დროს.

ანგარიშის ყველა ტოკენის ჩამოსათვლელად:

```bash
tuist account tokens list account-handle
```

ტოკენის სახელით გასაუქმებლად:

```bash
tuist account tokens revoke account-handle ci-cache-token
```

### ანგარიშის ტოკენების გამოყენება {#using-account-tokens}

ანგარიშის ტოკენები უნდა იყოს განსაზღვრული როგორც გარემოს ცვლადი `TUIST_TOKEN`:

```bash
export TUIST_TOKEN=your-account-token
```

> [!TIP]
> **როდის გამოვიყენოთ ანგარიშის ტოკენები**
>
> გამოიყენეთ ანგარიშის ტოკენები, როდესაც გჭირდებათ:
> - ავთენტიკაცია CI გარემოებში, რომლებიც არ უჭერენ OIDC-ს მხარს
> - დაწვრილებითი კონტროლი იმ ოპერაციებზე, რომელთა შესრულებაც ტოკენს შეუძლია
> - ტოკენი, რომელსაც შეუძლია წვდომა ანგარიშში არსებულ მრავალ პროექტზე
> - დროში შეზღუდული ტოკენები, რომლებსაც ავტომატურად ეწურებათ ვადა
