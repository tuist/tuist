# ავტორიზაცია {#authentication}

სერვერთან ურთიერთობისთვის CLI-ს მოთხოვნების ავტორიზაცია სჭირდება [bearer authentication](https://swagger.io/docs/specification/authentication/bearer-authentication/)-ის გამოყენებით. CLI მხარდაჭერს ავტორიზაციას როგორც მომხმარებლის, ისე ანგარიშის სახელით, ან OIDC ტოკენის გამოყენებით.

## როგორც მომხმარებელი {#as-a-user}

როდესაც CLI-ს იყენებთ თქვენს კომპიუტერზე ლოკალურად, გირჩევთ ავტორიზაციას მომხმარებლის სახელით. მომხმარებლად ავტორიზაციისთვის უნდა გაუშვათ შემდეგი ბრძანება:

```bash
tuist auth login
```

ბრძანება გაგიყვანთ ვებზე დაფუძნებულ ავტორიზაციის ნაკადში. ავტორიზაციის შემდეგ CLI შეინახავს ხანგრძლივი ვადის განახლების ტოკენს და ხანმოკლე ვადის წვდომის ტოკენს `~/.config/tuist/credentials` საქაღალდეში. დირექტორიაში თითოეული ფაილი წარმოადგენს დომენს, რომლის მიმართაც ავტორიზაცია გაიარეთ; ნაგულისხმევად ეს უნდა იყოს `tuist.dev.json`. ამ დირექტორიაში შენახული ინფორმაცია მგრძნობიარეა, ამიტომ **აუცილებლად შეინახეთ ის უსაფრთხოდ**.

CLI ავტომატურად მოიძიებს სერთიფიკატებს სერვერზე მოთხოვნების შესრულებისას. თუ წვდომის ტოკენი ვადაგასულია, CLI გამოიყენებს განახლების ტოკენს ახალი წვდომის ტოკენის მისაღებად.

> [!NOTE]
> თუ თქვენი ორგანიზაცია იყენებს ერთჯერად შესვლას (SSO), ბრაუზერში აირჩიეთ საწარმოს შესვლის ვარიანტი და შეიყვანეთ სამუშაო ელფოსტის მისამართი. Tuist-ს შეუძლია პროვაიდერის პოვნა თქვენი არსებული ორგანიზაციის წევრობიდან ან <.localized_link href="/guides/integrations/authentication/sso#verify-a-login-email-domain">ვერიფიცირებული შესვლის ელფოსტის დომენიდან</.localized_link>.

## OIDC ტოკენები {#oidc-tokens}

CI გარემოებისთვის, რომლებიც მხარს უჭერენ OpenID Connect-ს (OIDC), Tuist-ს შეუძლია ავტომატური ავტორიზაცია ხანგრძლივი ვადის საიდუმლოების მართვის საჭიროების გარეშე. მხარდაჭერილ CI გარემოში გაშვებისას CLI ავტომატურად აღმოაჩენს OIDC ტოკენის პროვაიდერს და ცვლის CI-ს მიერ მოწოდებულ ტოკენს Tuist-ის წვდომის ტოკენზე.

### მხარდაჭერილი პროვაიდერები {#supported-ci-providers}

Tuist ცნობს შემდეგ CI პროვაიდერებს და ასახავს მათ ტოკენებს პროექტებზე თქვენი რეპოზიტორიის კავშირის მეშვეობით:

- GitHub Actions
- CircleCI
- Bitrise

[Amp](#amp-orbs) orbs ავტორიზაციას გადიან Amp სამუშაო სივრცეების მეშვეობით, რომლებსაც თქვენს Tuist ანგარიშს უკავშირებთ, ხოლო [Claude Code სესიები](#claude-code-sessions) — Claude Code გარემოების მეშვეობით, რომლებსაც Tuist Sandboxes-ზე გასაშვებად აკავშირებთ.

ნებისმიერი სხვა იდენტობის პროვაიდერი, რომელიც გამოსცემს OpenID Connect ტოკენებს, შეუძლია ავტორიზაცია [workload identity trust policy](#workload-identity-trust-policies)-ის მეშვეობით, რომელსაც ერთხელ აკონფიგურირებთ თქვენი ანგარიშის ყველა არსებული და მომავალი პროექტისთვის, მაგალითად [Fly.io Machines](#flyio-machines).

### OIDC ავტორიზაციის დაყენება {#setting-up-oidc-authentication}

GitHub Actions-ის, CircleCI-ის და Bitrise-ისთვის:

1. **დაუკავშირეთ თქვენი რეპოზიტორია Tuist-ს**: მიჰყევით <.localized_link href="/guides/integrations/gitforge/github">GitHub ინტეგრაციის სახელმძღვანელოს</.localized_link>, რათა დაუკავშიროთ თქვენი GitHub რეპოზიტორია თქვენს Tuist პროექტს.

2. **მიანიჭეთ იდენტობის ტოკენი**: GitHub Actions-ზე მიანიჭეთ სამუშაოს `permissions: id-token: write`; CircleCI-ზე და Bitrise-ზე ჩართეთ OIDC პროექტისთვის. Tuist 4.218.0-დან, როდესაც CLI არ არის შესული და `TUIST_TOKEN` არ არის დაყენებული, ის აღმოაჩენს CI გარემოს და ცვლის იდენტობის ტოკენს პირველ მოთხოვნაზე, ამიტომ შესვლის ნაბიჯი არ არის საჭირო. ადრეულ ვერსიებს სჭირდებათ ჯერ `tuist auth login`, და შეგიძლიათ მაინც გაუშვათ ის ცხადი შესვლისთვის და ადრეული შეცდომის მიღებისთვის, თუ გაცვლა უარყოფილია.

პროვაიდერისთვის სპეციფიკური კონფიგურაციის მაგალითების სანახავად იხილეთ <.localized_link href="/guides/integrations/continuous-integration">უწყვეტი ინტეგრაციის სახელმძღვანელო</.localized_link>.

### Amp orbs {#amp-orbs}

[Amp](https://ampcode.com) orbs-ს შეუძლია გამოსცეს OIDC ტოკენები, რომლებიც აიდენტიფიცირებენ მათ Amp სამუშაო სივრცეს. ერთხელ დაუკავშირეთ სამუშაო სივრცე თქვენს Tuist ანგარიშს და Tuist CLI და `tuist_ex` Mix ამოცანები იმ სამუშაო სივრცის ნებისმიერ orb-ში თვითონ შევლენ, შენახული ტოკენის ან შესვლის ნაბიჯის გარეშე:

1. იპოვეთ ID-ები: სამუშაო სივრცის ნაკადში, რომელიც orb-ში გადის, გაუშვით `echo $AMP_WORKSPACE_ID $AMP_PROJECT_ID`.
2. თქვენს Tuist ანგარიშში გახსენით **Settings → Integrations**, Amp ბარათზე აირჩიეთ **Connect workspace** და ჩასვით სამუშაო სივრცის ID. მხოლოდ ერთი Amp პროექტის orbs-ის დასაშვებად, ასევე ჩასვით მისი პროექტის ID. თქვენ უნდა იყოთ ანგარიშის ადმინისტრატორი ან მფლობელი.
3. გამოიყენეთ Tuist სამუშაო სივრცის orbs-ში. როდესაც ის არ არის შესული, CLI ან Mix ამოცანა აღმოაჩენს orb-ს, გამოსცემს ტოკენს `amp orb id-token --audience https://tuist.dev`-ით და ცვლის მას Tuist სესიაზე. `tuist auth login` და `mix tuist.login` აკეთებენ იგივე გაცვლას ცხადად.

ისევე, როგორც [Amp-ის OIDC სახელმძღვანელოში](https://ampcode.com/manual/orbs/oidc) მითითებულ ნდობის კონფიგურაციებში, Tuist ამოწმებს Amp-ის ხელმოწერას ყოველ ტოკენზე და იღებს მას მხოლოდ მაშინ, როდესაც მისი audience არის `https://tuist.dev`, მისი `token_use` არის `exchanged`, მისი `workspace_id` ემთხვევა დაკავშირებულ სამუშაო სივრცეს და, პროექტამდე შეზღუდული კავშირის შემთხვევაში, მისი `project_id` ემთხვევა იმ პროექტს. მის `sub`-ში უნდა ეწეროს იგივე სამუშაო სივრცე, ხოლო პროექტის კავშირის შემთხვევაში — იგივე პროექტი, რაც ამ მოთხოვნებშია: `workspace:<workspace-id>:project:<project-id>:…`, რომელსაც `amp orb id-token` ნაგულისხმევად გამოსცემს.

ყველა orb, რომელსაც კავშირი უშვებს, იღებს CI წვდომას ანგარიშის მფლობელობაში არსებულ ყველა არსებულ და მომავალ პროექტზე, cache-ში ატვირთვის ჩათვლით. ასევე იღებს `account:sandboxes:write` scope-ს, რათა შექმნას <.localized_link href="/guides/features/sandboxes">sandboxes</.localized_link> და მათში გაუშვას ბრძანებები ანგარიშის წევრის მსგავსად, მაგალითად macOS sandbox-ზე Linux orb-დან აგებისთვის. დაუკავშირეთ მხოლოდ ისეთი სამუშაო სივრცეები, რომელთა წევრებსაც ენდობით ამ წვდომით. ყურადღებით შეამოწმეთ ID: Tuist-ს არ შეუძლია დაადასტუროს, რომ თქვენ ეკუთვნით იმ სამუშაო სივრცეს, რომელსაც აკავშირებთ. თუ სამუშაო სივრცე რამდენიმე Tuist ანგარიშთან არის დაკავშირებული, orbs-მა უნდა დააყენოს `TUIST_OIDC_ACCOUNT` იმ ანგარიშზე, რომელშიც შესვლა სურთ; მისი Amp პროექტის გარემოში დაყენება ასევე ინარჩუნებს შესვლას თქვენს ანგარიშზე მიბმულად. ნაკადებს სამუშაო სივრცის გარეთ არ აქვთ სამუშაო სივრცის იდენტობა და არ შეუძლიათ კავშირის გამოყენება. გაათიშეთ სამუშაო სივრცე Amp ბარათიდან ახალი შესვლების შესაჩერებლად; უკვე გაცემული სესიები ძალაში რჩებიან ერთი საათის შემდეგ ვადის გასვლამდე. სესიებს არ სჭირდებათ განახლების ტოკენი: როდესაც ერთ-ერთი ვადა ეწურება, orb-ში არსებული CLI გამოსცემს ახალ Amp ტოკენს და ისევ ცვლის მას, ამიტომ ხანგრძლივად მომუშავე orbs რჩებიან შესულები, სანამ სამუშაო სივრცე დაკავშირებულია.

Amp გამომცემლისთვის ნდობის პოლიტიკები, რომლებიც სამუშაო სივრცის დაკავშირებამდე შექმენით, განაგრძობენ მუშაობას, როდესაც აყენებთ `TUIST_OIDC_ACCOUNT`-ს.

### Claude Code სესიები {#claude-code-sessions}

ყოველ Claude Code ღრუბლოვან სესიას თვითმასპინძელ გარემოში აქვს იდენტობის ტოკენი, რომელსაც Anthropic აწერს ხელს (`CLAUDE_CODE_SESSION_ACCESS_TOKEN`). გარემოებში, რომლებსაც <.localized_link href="/guides/features/sandboxes/claude#claude-code">Tuist Sandboxes-ზე გასაშვებად აკავშირებთ</.localized_link>, Tuist გადასცემს მას სესიას როგორც `TUIST_OIDC_TOKEN`, ამიტომ Tuist CLI და `tuist_ex` Mix ამოცანები თვითონ შევლენ.

Tuist ამოწმებს Anthropic-ის ხელმოწერას და იღებს ტოკენს მხოლოდ მაშინ, როცა ის სესიის ტოკენია (`ccr:role` არის `session_worker`), რომლის გარემო, სახელით აუდიენციაში, დაკავშირებულია Tuist ანგარიშთან და გააქტიურებულია. დაკავშირებული გარემოს ყოველ სესიას ეძლევა CI წვდომა ანგარიშის მიერ ფლობად ყველა არსებულ და მომავალ პროექტზე, კეშის ატვირთვის ჩათვლით, და შეუძლია შექმნას და გამოიყენოს ანგარიშის sandbox-ები, როგორც ანგარიშის წევრს. ამიტომ ნებისმიერს, ვისაც თქვენი Claude ორგანიზაცია აძლევს გარემოს გამოყენების უფლებას, შეუძლია გამოაქვეყნოს თქვენს კეშში და დაიწყოს sandbox-ები, მაგალითად Mac ბილდისთვის. სესიის Tuist სესიები იწურება ერთი საათის შემდეგ ან მის იდენტობის ტოკენთან ერთად, რაც უფრო ადრე მოხდება; ტოკენი არის ის, რითიც სესია დაიწყო და ნაგულისხმევად ოთხი საათი ძლებს, ამიტომ უფრო ხანგრძლივი სესია კარგავს Tuist წვდომას, სანამ მისი შემდეგი შეტყობინება განაახლებს მას ახალ runner-ზე. გათიშეთ ან დაბლოკეთ გარემო ახალი შესვლების შეჩერებისთვის.

### Workload identity ნდობის პოლიტიკები {#workload-identity-trust-policies}

ნდობის პოლიტიკა საშუალებას აძლევს workload-ებს სხვა იდენტობის პროვაიდერიდან, როგორიცაა განლაგების პლატფორმა, Kubernetes კლასტერი ან თვითმართვადი CI სისტემა, მიუწვდეთ პროექტს გრძელვადიანი Tuist საიდუმლოს გარეშე. პროვაიდერმა უნდა:

- იყოს ხელმისაწვდომი HTTPS-ით საჯარო მისამართზე. Tuist არ მიჰყვება გადამისამართებებს და არ უკავშირდება პირად ან შიდა ქსელის მისამართებს, თვითმასპინძელი Tuist სერვერებიდანაც კი.
- გამოსცეს JWT-ები ასიმეტრიული გასაღებით ხელმოწერილი, მაგალითად `RS256` ან `ES256`. ხელმოუწერილი ტოკენები და საერთო საიდუმლოთი ხელმოწერილი ტოკენები (`HS256` და მსგავსი) უარყოფილია.
- გამოაქვეყნოს თავისი ხელმოწერის გასაღებები JSON Web Key Set-ის (JWKS) სახით ფიქსირებულ HTTPS URL-ზე. პასუხი უნდა იყოს მაქსიმუმ 64 KiB და შეიცავდეს მაქსიმუმ 20 გასაღებს.
- შეიცავდეს ვადას (`exp`) ყოველ ტოკენში.

GitHub Actions, CircleCI და Bitrise გამომცემლები დაცულია ზემოთ აღწერილი რეპოზიტორიაზე დაფუძნებული ნაკადისთვის და არ შეიძლება მათი გამოყენება ნდობის პოლიტიკაში.

> [!NOTE]
> თვითმასპინძელი განლაგებისთვის, გამოიყენეთ მონაცემთა ბაზის მიგრაციები და განაახლეთ Tuist სერვერის ყოველი მომსახურე რეპლიკა workload იდენტობების კონფიგურაციამდე ან მათზე სამუშაოების გადატანამდე. შემდეგ განაახლეთ CLI ან Elixir ინტეგრაცია ვერსიამდე, რომელიც მხარს უჭერს `TUIST_OIDC_TOKEN`-ს და `TUIST_OIDC_ACCOUNT`-ს. არსებული GitHub Actions, CircleCI და Bitrise სამუშაოები განაგრძობენ რეპოზიტორიაზე დაფუძნებული ავტორიზაციის გამოყენებას და არ საჭიროებენ ანგარიშის handle-ს. წარმოების სამუშაოებზე გადასვლამდე, შეამოწმეთ მოკლევადიანი ტოკენის გაცვლა და კეშის ოპერაცია განსაზღვრულ workload-თან. ახალი გაცვლების შეჩერებისთვის, წაშალეთ პოლიტიკა; მისცეთ უკვე გაცემულ Tuist წვდომის ტოკენებს ერთ საათამდე ვადა გასვლისთვის. პოლიტიკის წაშლა არ აუქმებს მაშინვე ამ ტოკენებს.

#### პოლიტიკის შექმნა {#create-a-trust-policy}

Tuist დაფაზე, გახსენით თქვენი ანგარიშის **Settings** > **Authentication** და იპოვეთ **Workload identities** სექცია. თქვენ უნდა იყოთ ანგარიშის ადმინისტრატორი (ან პირადი ანგარიშის მფლობელი). ყოველ ანგარიშს შეიძლება ჰქონდეს მაქსიმუმ 20 პოლიტიკა. კონფიგურაცია იდენტობის ერთხელ ანგარიშის მასშტაბით CI წვდომისთვის; პროექტის შერჩევა არ არის საჭირო.

გამოიყენეთ გადამრთველი **Workload identities**-ის გვერდით პოლიტიკის ფორმის გასახსნელად. გადამრთველი ჩართულია, როცა ანგარიშს აქვს შენახული იდენტობები და რჩება ჩართული შენახვის შემდეგ. ის იწყება გამორთული ანგარიშებისთვის იდენტობების გარეშე. სექცია ჩანს **SCIM provisioning**-ის ქვემოთ ორგანიზაციებისთვის. ფორმის დამალვა ინარჩუნებს თქვენს ნახაზს და არ თიშავს workload ავთენტიკაციას: შენახული იდენტობის ბარათები და დაყენების დოკუმენტაციის ბმული რჩება ხილული. ყოველი ბარათი აჩვენებს იდენტობის სახელს, გამომცემლის და JWKS URL-ებს, აუდიენციას, ზუსტ JSON პრეტენზიებს, ანგარიშის მასშტაბის მოცულობას და შექმნის დროს. წაშალეთ იდენტობა მის ბარათზე არსებული მოქმედების გამოყენებით.

აირჩიეთ **Custom provider** ქვემოთ მოცემული ველების შესაყვანად, ან **Fly.io Machines** მათი გენერირებისთვის თქვენი ორგანიზაციის slug-ის და რიცხვითი ორგანიზაციის და აპლიკაციის ID-ების მიხედვით. Fly შაბლონი ინარჩუნებს გენერირებულ გამომცემელს, JWKS URL-ს და პრეტენზიებს რედაქტირებადს **Advanced configuration**-ის ქვეშ. შაბლონების ან დამხმარე მნიშვნელობების შეცვლა ინარჩუნებს ხელით რედაქტირებულ ველებს. თუ თქვენი გამომცემელი, JWKS URL ან პრეტენზიები გადაფარავს შაბლონს, Tuist აფართოებს **Advanced configuration**-ს და აჩვენებს გაფრთხილებას, რათა შეამოწმოთ პოლიტიკა, რომელიც შეინახება. გადადით უკან **Custom provider**-ზე Fly დამხმარეების გარეშე გასაგრძელებლად. შაბლონები მხოლოდ ავსებენ კონფიგურაციას და არ ცვლიან იმას, თუ როგორ ამოწმებს Tuist ტოკენებს.

| ველი | აღწერა |
| --- | --- |
| სახელი | ლეიბლი პოლიტიკის ამოსაცნობად, უნიკალური ანგარიშის ფარგლებში. |
| გამომცემლის URL | ტოკენის `iss` პრეტენზია. ის უნდა ემთხვეოდეს ზუსტად, ბოლო დახრილი ხაზის ჩათვლით. |
| JWKS URL | HTTPS URL პროვაიდერის ხელმოწერის გასაღებებისთვის. Tuist იყენებს ამ URL-ს პირდაპირ და არ კითხულობს პროვაიდერის OpenID Connect აღმოჩენის დოკუმენტს, ამიტომ დააკოპირეთ `jwks_uri` პროვაიდერის დოკუმენტაციიდან ან `<issuer>/.well-known/openid-configuration`-დან. |

JSON შეყვანა შეზღუდულია 8 KiB-მდე. მნიშვნელობები უნდა იყოს სტრინგები, ნიშნიანი 64-ბიტიანი მთელი რიცხვები ან ბულიანები, და ისინი უნდა ემთხვეოდნენ ზუსტად, მათი ტიპის ჩათვლით: `"123"` არ ემთხვევა `123`-ს. ჩადგმული ობიექტები, სიები და დროის ან ტოკენის პრეტენზიები, როგორიცაა `iss`, `aud`, `exp`, `nbf`, `iat`, და `jti` არ არის დაშვებული. |

ყოველი პოლიტიკა ანიჭებს CI წვდომას **ანგარიშის მიერ ფლობად ყველა არსებულ და მომავალ პროექტზე**, ინდივიდუალური პროექტების შერჩევის გარეშე. შეგიძლიათ კონფიგურაცია იდენტობის პირველი პროექტის შექმნამდე. ეს არ ანიჭებს ანგარიშის ადმინისტრაციას ან წვდომას სხვა ანგარიშზე.

ყოველ workload-ს, რომელსაც შეუძლია მიიღოს ტოკენი დამთხვევი პრეტენზიებით, შეუძლია მიუწვდეს ყველა ამ პროექტს, ამიტომ აირჩიეთ პრეტენზიები, რომლებსაც პროვაიდერი გარანტიას აძლევს და რომელთა განმეორებითი გამოყენება არავის შეუძლია. უპირატესობა მიანიჭეთ სტაბილურ რიცხვით ID-ებს სახელებზე, რომლებიც შეიძლება გადაერქვათ ან ხელახლა დარეგისტრირდეს წაშლის შემდეგ.

> საერთო იდენტობის პროვაიდერზე მიუბმეთ პოლიტიკა თქვენს ორგანიზაციას ან ტენანტს **და** სასურველ აპლიკაციას, პროექტს ან სერვისის ანგარიშს. მხოლოდ ბრენჩის სახელი, როგორიცაა `main`, გარემო, როგორიცაა `production`, ან ზოგადი როლი არ წარმოადგენს იდენტობის საზღვარს: სხვა ტენანტმა შეიძლება მიიღოს ტოკენი იგივე მნიშვნელობებით. მაგალითად, GitLab.com-ის პოლიტიკა უნდა შეიცავდეს სასურველი პროექტის სტაბილურ `project_id`-ს და არა მხოლოდ `ref`-ს. დამთხვევი ტოკენი ანიჭებს ანგარიშის მასშტაბით CI წვდომას, კეშში ჩაწერის ჩათვლით, ამიტომ პოლიტიკა, რომელიც ენდობა არარელევანტურ workload-ებს, შეიძლება დაუშვას კეშის მოწამვლა.

Tuist ანიჭებს წვდომას მხოლოდ ისეთი პოლიტიკებისთვის, რომელთა საკუთარი JWKS URL შეიცავს გასაღებს, რომელმაც ხელი მოაწერა ტოკენს, გამომცემლის, აუდიენციის, ვადის, not-before დროის (60 წამამდე საათის ცდომილებით) და ყოველი პრეტენზიის შემოწმების შემდეგ. გაცემული ერთსაათიანი CI ტოკენი მოქმედებს ანგარიშის მასშტაბით და არ წარმოადგენს პროექტის ID-ების სნეპშოტს: ის მოიცავს პროექტებს, რომლებიც შეიქმნა ან გადაიტანეს ანგარიშში გაცემის შემდეგ. პროექტის ავტორიზაცია კვლავ მოითხოვს ანგარიშის მიმდინარე ფლობას, ამიტომ პროექტის გადატანა ანგარიშიდან აშორებს მას წვდომას ამ ანგარიშის ტოკენით.

#### workload-ის ავთენტიკაცია {#authenticate-a-workload}

1. მოითხოვეთ იდენტობის ტოკენი თქვენი პროვაიდერიდან პოლიტიკის აუდიენციით.
2. დააყენეთ `TUIST_OIDC_TOKEN` ამ ტოკენზე და `TUIST_OIDC_ACCOUNT` — იმ Tuist ანგარიშის handle-ზე, რომელიც ფლობს პროექტს. ანგარიში აუცილებელია ნდობის პოლიტიკის ყოველი გაცვლისთვის. ის მხოლოდ განსაზღვრავს სად უნდა მოხდეს ძიება და თავისთავად არაფერს ანიჭებს.
3. გაუშვით Tuist. როდესაც არ არის ხელმისაწვდომი `TUIST_TOKEN` ან მოქმედი შენახული რწმუნებები, CLI და Elixir ინტეგრაცია ავტომატურად ცვლის ტოკენს. `tuist auth login` და `mix tuist.login` ასრულებენ იგივე გაცვლას ცალსახად.

მიღებულ Tuist წვდომის ტოკენს აქვს მხოლოდ `ci` სკოუპების ჯგუფი და მოიცავს შერჩეული ანგარიშის მიერ ფლობად ყველა არსებულ და მომავალ პროექტს. გაცვლა ვერ ხერხდება, თუ ანგარიშში 20-ზე მეტი პოლიტიკა ემთხვევა ერთსა და იმავე ტოკენს ან თუ ისინი იყენებენ ორზე მეტ განსხვავებულ JWKS URL-ს.

Tuist არ აახლებს ამ სესიებს. წვდომის ტოკენები ვადა გაუდის ერთი საათის შემდეგ და არ აქვთ განახლების ტოკენი. პროვაიდერის იდენტობის ტოკენები ხშირად მოქმედებს მხოლოდ რამდენიმე წუთის განმავლობაში, ამიტომ ძველი `TUIST_OIDC_TOKEN`-ის შენახვა არ არის განახლების სტრატეგია: სამუშაოებისთვის, რომლებიც ერთ საათზე მეტხანს გრძელდება, მოითხოვეთ ახალი იდენტობის ტოკენი და ხელახლა შედით სისტემაში Tuist სესიის ვადის გასვლამდე. პოლიტიკის წაშლა აჩერებს ახალ გაცვლებს, მაგრამ უკვე გაცემული წვდომის ტოკენები მოქმედებს მათი ვადის გასვლამდე.

Tuist აკეშავს პროვაიდერის ხელმოწერის გასაღებებს 15 წუთის განმავლობაში წარმატებული მიღების შემდეგ სპეციალურ, ზომით შეზღუდულ კეშში. ჩანაწერები შეიძლება ადრე ამოიღონ და ხელახლა მიიღონ. წარუმატებელი მიღებები არ ინახება კეშში. თუ თქვენი პროვაიდერი ატრიალებს გასაღებებს, მან უნდა გამოაქვეყნოს ახალი გასაღები თავის JWKS-ში ტოკენებზე ხელმოწერამდე სულ მცირე 15 წუთით ადრე, რადგან ტოკენები, რომლებზეც ხელი მოწერილია გასაღებით, რომელიც არ არის კეშირებულ ნაკრებში, უარყოფილი იქნება კეშის ვადის გასვლამდე. ტოკენები გასაღების ID-ის (`kid`) გარეშე მიღებულია მხოლოდ მაშინ, როდესაც JWKS შეიცავს ერთ შესაბამის ხელმოწერის გასაღებს. როდესაც გასაღების ID არის JWKS-ში, ის უნდა იყოს სტრინგი მაქსიმუმ 256 ბაიტის სიგრძის.

> [!NOTE]
> `TUIST_OIDC_TOKEN` არის ზოგადი ტოკენის შეყვანა და არა სერვერის ნდობის გვერდის ავლის გზა. ის უპირატესობას ანიჭებს CI პროვაიდერის აღმოჩენას და სერვერი კვლავ იღებს მხოლოდ ჩაშენებულ პროვაიდერებს და იდენტობებს შესაბამისი ნდობის პოლიტიკით. არ ჩადოთ იდენტობის ტოკენი `TUIST_TOKEN`-ში, რომელიც ელის Tuist რწმუნებას.

თუ გაცვლა ვერ მოხერხდა, შეამოწმეთ, რომ გამომცემელი, აუდიენცია და პოლიტიკის ყოველი პრეტენზია ზუსტად ემთხვევა ტოკენს, რომ JWKS URL ემსახურება გასაღებს, რომელმაც ხელი მოაწერა ტოკენს, რომ პოლიტიკა არ არის წაშლილი და რომ `TUIST_OIDC_ACCOUNT` ასახელებს ანგარიშს, რომელიც ფლობს პროექტს. იმის თავიდან ასაცილებლად, რომ გამოაშკარავდეს, თუ რომელ იდენტობებს ენდობიან, Tuist აბრუნებს ერთსა და იმავე შეცდომას ყველა ამ შემთხვევისთვის.

### Fly.io Machines {#flyio-machines}

[Fly.io მხარს უჭერს OIDC workload იდენტობას](https://docs.fly.io/reference/openid-connect/). Machine-ს შეუძლია მოითხოვოს ხანმოკლე, ხელმოწერილი იდენტობის ტოკენი თავისი ლოკალური `/.fly/api` Unix სოკეტიდან, Fly API ტოკენის ან ხანგრძლივი Tuist საიდუმლოს გარეშე. Fly ტოკენები აიდენტიფიცირებენ ორგანიზაციას და აპლიკაციას და არა საწყის რეპოზიტორიას, ამიტომ გამოიყენეთ ნდობის პოლიტიკა GitHub რეპოზიტორიის დაკავშირების ნაცვლად:

1. მიიღეთ გამომცემელი (`iss`), ორგანიზაციის ID (`org_id`) და აპლიკაციის ID (`app_id`) თქვენს Fly Machine-ში გაცემული იდენტობის ტოკენიდან. გამომცემელია `https://oidc.fly.io/<organization-slug>`. გამოიყენეთ რიცხვითი ID-ები და არა ორგანიზაციის ან აპის სახელები.
2. [შექმენით ნდობის პოლიტიკა](#create-a-trust-policy) **Fly.io Machines** შაბლონის გამოყენებით და შეიყვანეთ ორგანიზაციის slug და ორივე რიცხვითი ID. ის ავსებს ქვემოთ მოცემულ მნიშვნელობებს და ინარჩუნებს ID-ებს სტრინგებად. ასევე შეგიძლიათ შეიყვანოთ ისინი ხელით **Custom provider**-ის გამოყენებით; შეინარჩუნეთ ბრჭყალები ID-ების გარშემო პრეტენზიებში.

   | ველი | მნიშვნელობა |
   | --- | --- |
   | გამომცემლის URL | `https://oidc.fly.io/<organization-slug>` |
   | JWKS URL | `https://oidc.fly.io/<organization-slug>/.well-known/jwks` |
   | აუდიენცია | `tuist` |
   | პრეტენზიები | `{"org_id": "<organization-id>", "app_id": "<application-id>"}` |

3. Machine-ის შიგნით, დააყენეთ `TUIST_OIDC_ACCOUNT` იმ Tuist ანგარიშის handle-ზე, რომელიც ფლობს პროექტს (არა Fly ორგანიზაციის slug), მოითხოვეთ ტოკენი აუდიენციით `tuist` და გადაეცით ის `tuist auth login`-ს `TUIST_OIDC_TOKEN`-ის გამოყენებით:

```bash
set -euo pipefail
export TUIST_OIDC_ACCOUNT="my-tuist-account"

TUIST_OIDC_TOKEN="$(curl --fail --silent --show-error \
  --unix-socket /.fly/api \
  -X POST http://localhost/v1/tokens/oidc \
  -H 'Content-Type: application/json' \
  --data '{"aud":"tuist"}')"
export TUIST_OIDC_TOKEN

tuist auth login
unset TUIST_OIDC_TOKEN
```

საწყისი კონფიგურაციისთვის შეგიძლიათ შეამოწმოთ მხოლოდ იდენტობის ველები ლოკალურად, ტოკენის ექსპორტირების შემდეგ და მისი გაუქმებამდე. ეს დეკოდირებს პრეტენზიებს კონფიგურაციისთვის; Tuist ცალკე ამოწმებს ხელმოწერას ავთენტიკაციის დროს:

```bash
python3 - <<'PY'
import base64, json, os
payload = os.environ["TUIST_OIDC_TOKEN"].split(".")[1]
claims = json.loads(base64.urlsafe_b64decode(payload + "=" * (-len(payload) % 4)))
print(json.dumps({key: claims[key] for key in ("iss", "org_id", "app_id")}, indent=2))
PY
```

არ დაბეჭდოთ ან არ დააკომიტოთ თავად ტოკენი. ავტორიზებულ Fly აპში ყოველ Machine-ს შეუძლია ავთენტიკაცია Tuist ანგარიშის ყველა არსებულ და მომავალ პროექტზე. შექმენით ცალკე პოლიტიკა ყოველი დამატებითი აპისთვის. Fly იდენტობის ტოკენებს ვადა გაუდის დაახლოებით ათი წუთის შემდეგ, ამიტომ ხანგრძლივად მომუშავე Machine-ებზე მოითხოვეთ ახალი და ხელახლა გაუშვით `tuist auth login` ერთსაათიანი Tuist სესიის ვადის გასვლამდე.

### OIDC ტოკენის სკოუპები {#oidc-token-scopes}

OIDC ტოკენებს ენიჭებათ `ci` სკოუპების ჯგუფი. GitHub Actions-ის, CircleCI-ის და Bitrise-ისთვის ეს უზრუნველყოფს წვდომას რეპოზიტორიასთან დაკავშირებულ ყველა პროექტზე. დაკავშირებული Amp სამუშაო სივრცეების, დაკავშირებული Claude Code გარემოებისა და workload იდენტობის ნდობის პოლიტიკებისთვის ეს უზრუნველყოფს წვდომას შერჩეული ანგარიშის მიერ ფლობად ყველა არსებულ და მომავალ პროექტზე, პროექტის შექმნის, პროექტის ადმინისტრირების, runner-ის ადმინისტრირების ან ანგარიშის წევრების ადმინისტრირების მინიჭების გარეშე. იხილეთ [სკოუპების ჯგუფები](#scope-groups) დეტალებისთვის, თუ რას მოიცავს `ci` სკოუპი.

## Gradle პლაგინის ავთენტიკაცია {#gradle-plugin-authentication}

Gradle პლაგინი იყენებს Tuist CLI-ის ავთენტიკაციის მდგომარეობას და არ განსაზღვრავს ცალკე შესვლის პროცესს. ერთხელ გაიარეთ ავთენტიკაცია CLI-ით და პლაგინი ხელახლა გამოიყენებს ამ მონაცემებს.

პროექტისა და სერვერის კონფიგურაციისთვის, მათ შორის `project` და `url`, გამოიყენეთ კანონიკური <.localized_link href="/references/tuist-toml">tuist.toml მითითება</.localized_link>.

ლოკალური გამოყენებისთვის, გაუშვით:

```bash
tuist auth login
```

CI-ისთვის, გამოიყენეთ ერთ-ერთი:

- <.localized_link href="/guides/server/authentication#setting-up-oidc-authentication">OIDC ავთენტიკაცია</.localized_link> (რეკომენდებულია, თუ ხელმისაწვდომია)
- <.localized_link href="/guides/server/authentication#continuous-integration">ანგარიშის ტოკენით ავთენტიკაცია</.localized_link> გზით `TUIST_TOKEN`

თვითნაკერი Tuist სერვერებისთვის, განსაზღვრეთ სერვერის URL `tuist.toml`-ში (მაგალითად `url = "https://tuist.your-company.com"`) და გაუშვით სტანდარტული შესვლის პროცესი. URL იხსნება იმავე კონფიგურაციის ფაილიდან, რომელსაც პლაგინი იყენებს.

ავთენტიკაციის კონფიგურირების შემდეგ, ჩვეულებრივად გაუშვით თქვენი Gradle ქეშირების ბრძანებები და ამოცანები.

## ანგარიშის ტოკენები {#account-tokens}

CI გარემოებისთვის, რომლებიც არ უჭერენ მხარს OIDC-ს, ან როცა საჭიროა ნებართვებზე ზუსტი კონტროლი, შეგიძლიათ გამოიყენოთ ანგარიშის ტოკენები. ანგარიშის ტოკენები საშუალებას გაძლევთ ზუსტად მიუთითოთ, თუ რომელ სკოუპებსა და პროექტებზე აქვს ტოკენს წვდომა.

### ანგარიშის ტოკენის შექმნა {#creating-an-account-token}

ანგარიშის ტოკენის შექმნის ყველაზე მარტივი გზა დაშბორდიდანაა:

1. გახსენით ორგანიზაცია Tuist დაშბორდზე.
2. გადადით **პარამეტრებში** > **ტოკენები**.
3. აირჩიეთ **ტოკენის გენერირება**.
4. აირჩიეთ სახელი, ვადის გასვლის ოფციონალური პარამეტრი, პროექტზე წვდომა და სკოუპები, რომლებიც ტოკენს სჭირდება.
5. დახურვამდე დააკოპირეთ გენერირებული ტოკენის მნიშვნელობა. ტოკენის მნიშვნელობები მხოლოდ ერთხელ ჩანს.

ასევე შეგიძლიათ შექმნათ ანგარიშის ტოკენები CLI-დან, რაც სასარგებლოა სკრიპტინგის ან ავტომატიზაციისთვის:

```bash
tuist account tokens create account-handle \
  --scopes account:cache:write project:cache:read project:cache:write \
  --name ci-cache-token \
  --expires 1y
```

> [!IMPORTANT]
> ჩაანაცვლეთ `account-handle` იმ ანგარიშის handle-ით, რომელიც ფლობს პროექტებს, რომლებზეც ტოკენს წვდომა უნდა ჰქონდეს. ეს შეიძლება იყოს ორგანიზაციის ანგარიში და არა აუცილებლად თქვენი პირადი ანგარიში.

ბრძანება იღებს შემდეგ ოფციებს:

| ოფცია | აღწერა |
| --- | --- |
| `--scopes` | სავალდებულო. სკოუპების სია, რომლებიც ტოკენს უნდა მიენიჭოს, გამოყოფილია space-ებით. |
| `--name` | სავალდებულო. ტოკენის უნიკალური იდენტიფიკატორი (1-32 სიმბოლო, მხოლოდ ალფანუმერული, დეფისები და underscore). |
| `--expires` | ოფციონალური. როდის უნდა გაუვიდეს ვადა ტოკენს. გამოიყენეთ ფორმატი, როგორიცაა `30d` (დღეები), `6m` (თვეები) ან `1y` (წლები). თუ არ არის მითითებული, ტოკენს ვადა არასდროს გაუვა. |
| `--projects` | შეზღუდეთ ტოკენი კონკრეტული პროექტების handle-ებით. თუ არ არის მითითებული, ტოკენს აქვს წვდომა ყველა პროექტზე. |

### სკოუპების ჯგუფები {#scope-groups}

სკოუპების ჯგუფები იძლევა მოსახერხებელ გზას, რათა ერთი იდენტიფიკატორით მიანიჭოთ რამდენიმე დაკავშირებული სკოუპი. როდესაც იყენებთ სკოუპების ჯგუფს, ის ავტომატურად ფართოვდება და მოიცავს ყველა ინდივიდუალურ სკოუპს, რომელიც მასში შედის.

| სკოუპების ჯგუფი | შემავალი სკოუპები |
| --- | --- |
| `ci` | `account:cache:write`, `project:cache:write`, `project:previews:write`, `project:bundles:write`, `project:tests:write`, `project:builds:write`, `project:runs:write` |
| `mcp` | `project:cache:read`, `project:previews:read`, `project:bundles:read`, `project:tests:read`, `project:builds:read`, `project:runs:read` |

### უწყვეტი ინტეგრაცია {#continuous-integration}

CI გარემოებისთვის, რომლებიც არ უჭერენ მხარს OIDC-ს, შექმენით ანგარიშის ტოკენი `ci` სკოუპების ჯგუფით თქვენი CI workflow-ების ავთენტიკაციისთვის. დაფარდაზე ტოკენის გენერირებისას აირჩიეთ **CI** პრესეტი.

იგივე ტოკენის შექმნა CLI-დანაც შეგიძლიათ:

```bash
tuist account tokens create account-handle --scopes ci --name ci
```

ეს ქმნის ტოკენს ყველა იმ სკოუპით, რაც საჭიროა ტიპური CI ოპერაციებისთვის (ქეში, პრივიუები, ბანდლები, ტესტები, ბილდები და გაშვებები). შეინახეთ გენერირებული ტოკენი როგორც საიდუმლო თქვენს CI გარემოში და დააყენეთ ის როგორც `TUIST_TOKEN` გარემოს ცვლადი.

### ანგარიშის ტოკენების მართვა {#managing-account-tokens}

გახსენით **პარამეტრები** > **ტოკენები** ანგარიშის დაფარდაზე, რათა ნახოთ ანგარიშის ტოკენები, შეამოწმოთ ტოკენის სკოუპები და პროექტებზე წვდომა, ასევე გააუქმოთ ტოკენები როტაციის დროს.

ანგარიშის ყველა ტოკენის სიის სანახავად:

```bash
tuist account tokens list account-handle
```

ტოკენის სახელით გასაუქმებლად:

```bash
tuist account tokens revoke account-handle ci-cache-token
```

### ანგარიშის ტოკენების გამოყენება {#using-account-tokens}

ანგარიშის ტოკენები უნდა იყოს განსაზღვრული როგორც გარემოს ცვლადი `TUIST_TOKEN`:

```bash
export TUIST_TOKEN=your-account-token
```

> [!TIP]
> **როდის გამოვიყენოთ ანგარიშის ტოკენები**
>
> გამოიყენეთ ანგარიშის ტოკენები, როდესაც გჭირდებათ:
> - ავთენტიკაცია CI გარემოებში, რომლებიც არ უჭერენ მხარს OIDC-ს
> - წვრილმანი კონტროლი იმაზე, თუ რა ოპერაციების შესრულება შეუძლია ტოკენს
> - ტოკენი, რომელსაც შეუძლია წვდომა ანგარიშში შემავალ რამდენიმე პროექტზე
> - დროში შეზღუდული ტოკენები, რომლებსაც ავტომატურად გაუვათ ვადა
