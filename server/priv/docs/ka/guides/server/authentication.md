# ავთენტიკაცია {#authentication}

სერვერთან ურთიერთობისთვის CLI-მ მოთხოვნები უნდა დააავთენტიკოს [bearer ავთენტიკაციის](https://swagger.io/docs/specification/authentication/bearer-authentication/) გამოყენებით. CLI მხარდაჭერას უწევს ავთენტიკაციას როგორც მომხმარებლის, ისე ანგარიშის სახელით, ან OIDC ტოკენის გამოყენებით.

## როგორც მომხმარებელი {#as-a-user}

როდესაც CLI-ს იყენებთ თქვენს მანქანაზე ლოკალურად, გირჩევთ ავთენტიკაცია მომხმარებლის სახელით. მომხმარებლად ავთენტიკაციისთვის უნდა გაუშვათ შემდეგი ბრძანება:

```bash
tuist auth login
```

ბრძანება გაგიყვანთ ვებზე დაფუძნებული ავთენტიკაციის ნაკადში. ავთენტიკაციის შემდეგ CLI შეინახავს ხანგრძლივი ვადის განახლების ტოკენს და ხანმოკლე ვადის წვდომის ტოკენს `~/.config/tuist/credentials` საქაღალდეში. დირექტორიის თითოეული ფაილი წარმოადგენს დომენს, რომლის მიმართაც ავთენტიკაცია მოხდა; ნაგულისხმევად ეს უნდა იყოს `tuist.dev.json`. ამ დირექტორიაში შენახული ინფორმაცია კონფიდენციალურია, ამიტომ **აუცილებლად დაიცავით ის**.

CLI ავტომატურად მოიძიებს სერთიფიკატებს სერვერთან მოთხოვნების შესრულებისას. თუ წვდომის ტოკენი ამოიწურა, CLI გამოიყენებს განახლების ტოკენს ახალი წვდომის ტოკენის მისაღებად.

> [!NOTE]
> თუ თქვენი ორგანიზაცია იყენებს ერთჯერად შესვლას (SSO), ბრაუზერში აირჩიეთ საწარმოს შესვლის ვარიანტი და შეიყვანეთ სამუშაო ელფოსტის მისამართი. Tuist-ს შეუძლია პროვაიდერის პოვნა თქვენი არსებული ორგანიზაციის წევრობიდან ან <.localized_link href="/guides/integrations/authentication/sso#verify-a-login-email-domain">დადასტურებული შესვლის ელფოსტის დომენიდან</.localized_link>.

## OIDC ტოკენები {#oidc-tokens}

CI გარემოებისთვის, რომლებიც მხარს უჭერენ OpenID Connect-ს (OIDC), Tuist-ს შეუძლია ავტომატური ავთენტიკაცია ხანგრძლივი ვადის საიდუმლოებების მართვის საჭიროების გარეშე. მხარდაჭერილ CI გარემოში გაშვებისას CLI ავტომატურად აღმოაჩენს OIDC ტოკენის პროვაიდერს და ცვლის CI-ს მიერ მოწოდებულ ტოკენს Tuist-ის წვდომის ტოკენზე.

### მხარდაჭერილი პროვაიდერები {#supported-ci-providers}

Tuist ცნობს ამ CI პროვაიდერებს და მათ ტოკენებს ასახავს პროექტებზე თქვენი რეპოზიტორიის კავშირის მეშვეობით:

- GitHub Actions
- CircleCI
- Bitrise

[Amp](#amp-orbs) orbs ავთენტიკაციას გადიან Amp workspace-ების მეშვეობით, რომლებსაც თქვენს Tuist ანგარიშთან აკავშირებთ, ხოლო [Claude Code სესიები](#claude-code-sessions) — Claude Code გარემოების მეშვეობით, რომლებსაც აკავშირებთ Tuist Sandboxes-ზე გასაშვებად.

ნებისმიერი სხვა იდენტობის პროვაიდერი, რომელიც გამოსცემს OpenID Connect ტოკენებს, შეუძლია ავთენტიკაცია [workload identity trust policy](#workload-identity-trust-policies)-ის მეშვეობით, რომელსაც ერთხელ აკონფიგურირებთ თქვენი ანგარიშის ყველა არსებული და მომავალი პროექტისთვის, მაგალითად [Fly.io Machines](#flyio-machines).

### OIDC ავთენტიკაციის დაყენება {#setting-up-oidc-authentication}

GitHub Actions-ის, CircleCI-ის და Bitrise-ისთვის:

1. **დააკავშირეთ თქვენი რეპოზიტორია Tuist-თან**: მიჰყევით <.localized_link href="/guides/integrations/gitforge/github">GitHub ინტეგრაციის სახელმძღვანელოს</.localized_link>, რათა დააკავშიროთ თქვენი GitHub რეპოზიტორია თქვენს Tuist პროექტთან.

2. **მიანიჭეთ იდენტობის ტოკენი**: GitHub Actions-ზე მიანიჭეთ სამუშაოს `permissions: id-token: write`; CircleCI-ზე და Bitrise-ზე ჩართეთ OIDC პროექტისთვის. Tuist 4.218.0-დან, როდესაც CLI არ არის შესული და `TUIST_TOKEN` არ არის დაყენებული, ის აღმოაჩენს CI გარემოს და ცვლის იდენტობის ტოკენს თავის პირველ მოთხოვნაზე, ამიტომ შესვლის ნაბიჯი არ არის საჭირო. ადრეულ ვერსიებს სჭირდებათ ჯერ `tuist auth login`, და თქვენ მაინც შეგიძლიათ მისი გაშვება ცხადი შესვლისთვის და ადრეული შეცდომის მიღებისთვის, თუ გაცვლა უარყოფილია.

პროვაიდერისთვის სპეციფიკური კონფიგურაციის მაგალითებისთვის იხილეთ <.localized_link href="/guides/integrations/continuous-integration">უწყვეტი ინტეგრაციის სახელმძღვანელო</.localized_link>.

### Amp orbs {#amp-orbs}

[Amp](https://ampcode.com) orbs-ს შეუძლია გამოსცეს OIDC ტოკენები, რომლებიც აიდენტიფიცირებენ მათ Amp workspace-ს. ერთხელ დააკავშირეთ workspace თქვენს Tuist ანგარიშთან და Tuist CLI და `tuist_ex` Mix ამოცანები ამ workspace-ის ნებისმიერ orb-ში დამოუკიდებლად შევლენ, შენახული ტოკენის ან შესვლის ნაბიჯის გარეშე:

1. იპოვეთ ID-ები: workspace-ის ნაკადში, რომელიც orb-ში მუშაობს, გაუშვით `echo $AMP_WORKSPACE_ID $AMP_PROJECT_ID`.
2. თქვენს Tuist ანგარიშში გახსენით **Settings → Integrations**, Amp ბარათზე აირჩიეთ **Connect workspace** და ჩასვით workspace ID. მხოლოდ ერთი Amp პროექტის orbs-ის დასაშვებად, ასევე ჩასვით მისი project ID. თქვენ უნდა იყოთ ანგარიშის ადმინისტრატორი ან მფლობელი.
3. გამოიყენეთ Tuist workspace-ის orbs-ში. როდესაც ის არ არის შესული, CLI ან Mix ამოცანა აღმოაჩენს orb-ს, გამოსცემს ტოკენს `amp orb id-token --audience https://tuist.dev`-ით და ცვლის მას Tuist სესიაზე. `tuist auth login` და `mix tuist.login` იმავე გაცვლას ცხადად ასრულებენ.

როგორც [Amp-ის OIDC სახელმძღვანელოში](https://ampcode.com/manual/orbs/oidc) ნდობის კონფიგურაციებში, Tuist ამოწმებს Amp-ის ხელმოწერას ყოველ ტოკენზე და იღებს მას მხოლოდ მაშინ, როდესაც მისი audience არის `https://tuist.dev`, მისი `token_use` არის `exchanged`, მისი `workspace_id` ემთხვევა დაკავშირებულ workspace-ს და, პროექტამდე შეზღუდული კავშირისთვის, მისი `project_id` ემთხვევა იმ პროექტს. მისმა `sub`-მ უნდა მიუთითოს იგივე workspace, ხოლო პროექტის კავშირისთვის იგივე პროექტი, როგორც ამ პრეტენზიებში: `workspace:<workspace-id>:project:<project-id>:…`, რომელსაც `amp orb id-token` ნაგულისხმევად გამოსცემს.

კავშირის მიერ დაშვებული ყოველი orb იღებს CI წვდომას ანგარიშის მფლობელობაში არსებულ ყველა არსებულ და მომავალ პროექტზე, cache-ში ატვირთვების ჩათვლით. ის ასევე იღებს `account:sandboxes:write` scope-ს, რათა შექმნას <.localized_link href="/guides/features/sandboxes">sandboxes</.localized_link> და მათში ბრძანებები გაუშვას ანგარიშის წევრის მსგავსად, მაგალითად macOS sandbox-ზე აგებისთვის Linux orb-დან. დააკავშირეთ მხოლოდ ისეთი workspace-ები, რომელთა წევრებსაც ენდობით ამ წვდომით. ყურადღებით შეამოწმეთ ID: Tuist-ს არ შეუძლია დაადასტუროს, რომ თქვენ ეკუთვნით workspace-ს, რომელსაც აკავშირებთ. თუ workspace დაკავშირებულია რამდენიმე Tuist ანგარიშთან, orbs-მა უნდა დააყენოს `TUIST_OIDC_ACCOUNT` იმ ანგარიშზე, რომელშიც შესვლა სურთ; მისი Amp პროექტის გარემოში დაყენება ასევე ინარჩუნებს შესვლას თქვენს ანგარიშზე მიბმულს. workspace-ს გარეთ მყოფ ნაკადებს არ აქვთ workspace იდენტობა და არ შეუძლიათ კავშირის გამოყენება. გათიშეთ workspace Amp ბარათიდან ახალი შესვლების შესაჩერებლად; უკვე გაცემული სესიები ძალაში რჩება ერთი საათის შემდეგ ამოწურვამდე. სესიებს არ სჭირდებათ განახლების ტოკენი: როდესაც ერთ-ერთი იწურება, orb-ში მყოფი CLI გამოსცემს ახალ Amp ტოკენს და კვლავ ცვლის მას, ასე რომ ხანგრძლივად მომუშავე orbs რჩებიან შესულები, სანამ workspace დაკავშირებულია.

ნდობის პოლიტიკები Amp გამომცემლისთვის, რომლებიც შექმენით workspace-ის დაკავშირებამდე, განაგრძობენ მუშაობას, როდესაც აყენებთ `TUIST_OIDC_ACCOUNT`-ს.

### Claude Code სესიები {#claude-code-sessions}

Claude Code-ის ყოველი cloud სესია self-hosted გარემოში ატარებს იდენტობის ტოკენს, რომელსაც Anthropic აწერს ხელს (`CLAUDE_CODE_SESSION_ACCESS_TOKEN`). გარემოებში, რომლებსაც <.localized_link href="/guides/features/sandboxes/claude#claude-code">აკავშირებთ Tuist Sandboxes-ზე გასაშვებად</.localized_link>, Tuist გადასცემს მას სესიას როგორც `TUIST_OIDC_TOKEN`, ასე რომ Tuist CLI და `tuist_ex` Mix ამოცანები დამოუკიდებლად შევლენ.

Tuist ამოწმებს Anthropic-ის ხელმოწერას და იღებს ტოკენს მხოლოდ მაშინ, როდესაც ის სესიის ტოკენია (`ccr:role` არის `session_worker`), რომლის გარემოც, სახელით მითითებული audience-ში, დაკავშირებულია Tuist ანგარიშთან და ჩართულია. დაკავშირებული გარემოს ყოველი სესია იღებს CI წვდომას ანგარიშის კუთვნილ ყველა მიმდინარე და მომავალ პროექტზე, cache-ში ატვირთვის ჩათვლით, და შეუძლია შექმნას და გამოიყენოს ანგარიშის sandboxes, როგორც ანგარიშის წევრმა. შესაბამისად, ნებისმიერს, ვისაც თქვენი Claude ორგანიზაცია აძლევს გარემოს გამოყენების უფლებას, შეუძლია გამოაქვეყნოს თქვენს cache-ში და გაუშვას sandboxes, მაგალითად Mac ბილდისთვის. სესიის Tuist სესიები იწურება ერთი საათის შემდეგ ან მის იდენტობის ტოკენთან ერთად, რაც უფრო ადრე მოხდება; ტოკენი არის ის, რითიც სესია დაიწყო და ნაგულისხმევად ოთხი საათი ძლებს, ასე რომ ხანგრძლივი სესია კარგავს Tuist წვდომას, სანამ მისი შემდეგი შეტყობინება არ აღადგენს მას ახალ runner-ზე. გათიშეთ ან გამორთეთ გარემო ახალი შესვლების შესაჩერებლად.

### Workload identity ნდობის პოლიტიკები {#workload-identity-trust-policies}

ნდობის პოლიტიკა საშუალებას აძლევს workload-ებს სხვა იდენტობის პროვაიდერიდან, როგორიცაა განთავსების პლატფორმა, Kubernetes კლასტერი ან თვითმართვადი CI სისტემა, მიუწვდნენ პროექტს ხანგრძლივი Tuist საიდუმლოს გარეშე. პროვაიდერმა უნდა:

- იყოს ხელმისაწვდომი HTTPS-ით საჯარო მისამართზე. Tuist არ მიჰყვება გადამისამართებებს და არ უკავშირდება პირად ან შიდა ქსელის მისამართებს, მათ შორის self-hosted Tuist სერვერებიდან.
- გამოსცეს JWTs, ხელმოწერილი ასიმეტრიული გასაღებით, მაგალითად `RS256` ან `ES256`. ხელმოუწერილი ტოკენები და ტოკენები, ხელმოწერილი საერთო საიდუმლოთი (`HS256` და მსგავსი), უარყოფილია.
- გამოაქვეყნოს თავისი ხელმოწერის გასაღებები JSON Web Key Set-ად (JWKS) ფიქსირებულ HTTPS URL-ზე. პასუხი უნდა იყოს არაუმეტეს 64 KiB და შეიცავდეს არაუმეტეს 20 გასაღებს.
- შეიცავდეს ვადის გასვლას (`exp`) ყოველ ტოკენში.

GitHub Actions, CircleCI და Bitrise გამომცემლები შენახულია ზემოთ აღწერილი რეპოზიტორიაზე დაფუძნებული ნაკადისთვის და არ შეიძლება გამოყენებულ იქნას ნდობის პოლიტიკაში.

> [!NOTE]
> self-hosted განთავსებისთვის, გამოიყენეთ მონაცემთა ბაზის მიგრაციები და განაახლეთ Tuist სერვერის ყოველი მომსახურე რეპლიკა, სანამ დააკონფიგურიროთ workload იდენტობები ან გადაიტანთ მათზე სამუშაოებს. შემდეგ განაახლეთ CLI ან Elixir ინტეგრაცია ვერსიამდე, რომელიც მხარს უჭერს `TUIST_OIDC_TOKEN` და `TUIST_OIDC_ACCOUNT`-ს. არსებული GitHub Actions, CircleCI და Bitrise სამუშაოები განაგრძობენ რეპოზიტორიაზე დაფუძნებული ავტორიზაციის გამოყენებას და არ საჭიროებენ ანგარიშის handle-ს. პროდუქციის სამუშაოებზე გადასვლამდე, შეამოწმეთ ხანმოკლე ტოკენის გაცვლა და cache ოპერაცია განსაზღვრულ workload-თან. ახალი გაცვლების შესაჩერებლად, წაშალეთ პოლიტიკა; დაუთმეთ ერთ საათამდე დრო უკვე გაცემული Tuist წვდომის ტოკენების ვადის გასვლას. პოლიტიკის წაშლა არ აუქმებს დაუყოვნებლივ ამ ტოკენებს.

#### პოლიტიკის შექმნა {#create-a-trust-policy}

Tuist dashboard-ში, გახსენით თქვენი ანგარიშის **Settings** > **Authentication** და იპოვეთ **Workload identities** სექცია. თქვენ უნდა იყოთ ანგარიშის ადმინისტრატორი (ან პირადი ანგარიშის მფლობელი). ყოველ ანგარიშს შეიძლება ჰქონდეს 20-მდე პოლიტიკა. დააკონფიგურეთ იდენტობა ერთხელ ანგარიშის მასშტაბით CI წვდომისთვის; პროექტის შერჩევა არ არის საჭირო.

გამოიყენეთ გადამრთველი **Workload identities**-ის გვერდით პოლიტიკის ფორმის გასახსნელად. გადამრთველი ჩართულია, როდესაც ანგარიშს აქვს შენახული იდენტობები და რჩება ჩართული შენახვის შემდეგ. ის გამოირთვება ანგარიშებისთვის იდენტობების გარეშე. სექცია ჩანს **SCIM provisioning**-ის ქვემოთ ორგანიზაციებისთვის. ფორმის დამალვა ინარჩუნებს თქვენს ნახაზს და არ თიშავს workload ავთენტიკაციას: შენახული იდენტობის ბარათები და მორგების დოკუმენტაციის ბმული რჩება ხილული. ყოველი ბარათი აჩვენებს იდენტობის სახელს, გამომცემლისა და JWKS URL-ებს, audience-ს, ზუსტ JSON claims-ებს, ანგარიშის მასშტაბით მოქმედების სფეროს და შექმნის დროს. წაშალეთ იდენტობა მის ბარათზე არსებული მოქმედების გამოყენებით.

აირჩიეთ **Custom provider** ქვემოთ მოცემული ველების შესაყვანად, ან **Fly.io Machines** მათი გენერირებისთვის თქვენი ორგანიზაციის slug-ისა და რიცხვითი ორგანიზაციისა და აპლიკაციის ID-ების მიხედვით. Fly შაბლონი ინარჩუნებს გენერირებულ გამომცემელს, JWKS URL-ს და claims-ებს რედაქტირებადს **Advanced configuration**-ის ქვეშ. შაბლონების ან დამხმარე მნიშვნელობების შეცვლა ინარჩუნებს ხელით რედაქტირებულ ველებს. თუ თქვენი გამომცემელი, JWKS URL ან claims გადაფარავს შაბლონს, Tuist აფართოებს **Advanced configuration**-ს და აჩვენებს გაფრთხილებას, რათა შეამოწმოთ შესანახი პოლიტიკა. გადადით უკან **Custom provider**-ზე Fly დამხმარეების გარეშე გასაგრძელებლად. შაბლონები მხოლოდ ავსებენ კონფიგურაციას და არ ცვლიან იმას, თუ როგორ ამოწმებს Tuist ტოკენებს.

| ველი | აღწერა |
| --- | --- |
| სახელი | პოლიტიკის ამოსაცნობი ეტიკეტი, უნიკალური ანგარიშის ფარგლებში. |
| გამომცემლის URL | ტოკენის `iss` claim. ის უნდა ემთხვეოდეს ზუსტად, ბოლოში არსებული slash-ის ჩათვლით. |
| JWKS URL | პროვაიდერის ხელმოწერის გასაღებების HTTPS URL. Tuist იყენებს ამ URL-ს პირდაპირ და არ კითხულობს პროვაიდერის OpenID Connect აღმოჩენის დოკუმენტს, ასე რომ დააკოპირეთ `jwks_uri` პროვაიდერის დოკუმენტაციიდან ან `<issuer>/.well-known/openid-configuration`-დან. |
| Audience | audience, რომლისთვისაც უნდა იყოს გაცემული ტოკენი, ნაგულისხმევად `tuist`. ტოკენის `aud` უნდა უდრიდეს მას ან, როდესაც `aud` არის სია, შეიცავდეს მას. გამოიყენეთ მნიშვნელობა, რომელსაც მხოლოდ Tuist იღებს, რათა სხვა სერვისებისთვის გაცემული ტოკენები აქ არ განმეორდეს. |
| Claims | JSON ობიექტი 1-დან 10-მდე claim-ით, რომელიც ტოკენმა უნდა შეიცავდეს, მაგალითად `{"sub": "system:serviceaccount:ci:builder"}`. JSON შეყვანა შემოიფარგლება 8 KiB-ით. მნიშვნელობები უნდა იყოს სტრინგები, ნიშნიანი 64-ბიტიანი მთელი რიცხვები ან ბულის მნიშვნელობები, და ისინი უნდა ემთხვეოდნენ ზუსტად, მათი ტიპის ჩათვლით: `"123"` არ ემთხვევა `123`-ს. ჩადგმული ობიექტები, სიები და დროის ან ტოკენის claims, როგორიცაა `iss`, `aud`, `exp`, `nbf`, `iat` და `jti`, არ არის დაშვებული. |

ყოველი პოლიტიკა ანიჭებს CI წვდომას **ანგარიშის კუთვნილ ყველა მიმდინარე და მომავალ პროექტზე**, ინდივიდუალური პროექტების შერჩევის გარეშე. შეგიძლიათ დააკონფიგურიროთ იდენტობა პირველი პროექტის შექმნამდე. ეს არ ანიჭებს ანგარიშის ადმინისტრირებას ან წვდომას სხვა ანგარიშზე.

ყოველ workload-ს, რომელსაც შეუძლია მიიღოს ტოკენი შესაბამისი claims-ებით, შეუძლია მიუწვდეს ყველა ამ პროექტს, ასე რომ აირჩიეთ claims, რომლებსაც პროვაიდერი გარანტირებს და რომელთა განმეორებითი გამოყენება არავის შეუძლია. უპირატესობა მიანიჭეთ სტაბილურ რიცხვით ID-ებს სახელებზე, რომლებიც შეიძლება გადაერქვას ან ხელახლა დარეგისტრირდეს წაშლის შემდეგ.

> [!WARNING]
> გაზიარებულ იდენტობის პროვაიდერზე, დააკავშირეთ პოლიტიკა თქვენს ორგანიზაციასთან ან არენდატორთან **და** სასურველ აპლიკაციასთან, პროექტთან ან სერვისის ანგარიშთან. ტოტის სახელი, როგორიცაა `main`, გარემო, როგორიცაა `production`, ან ზოგადი როლი მხოლოდ არ არის იდენტობის საზღვარი: სხვა არენდატორმა შეიძლება მიიღოს ტოკენი იგივე მნიშვნელობებით. მაგალითად, GitLab.com-ის პოლიტიკამ უნდა შეიცავდეს სასურველი პროექტის სტაბილურ `project_id`-ს, არა მხოლოდ `ref`-ს. შესაბამისი ტოკენი ანიჭებს ანგარიშის დონეზე CI წვდომას, ქეშში ჩაწერის ჩათვლით, ამიტომ პოლიტიკამ, რომელიც ენდობა დაუკავშირებელ workload-ებს, შეიძლება დაუშვას ქეშის მოწამვლა.

Tuist ანიჭებს წვდომას მხოლოდ იმ პოლიტიკებისთვის, რომელთა საკუთარ JWKS URL-ს აქვს გასაღები, რომელმაც ხელი მოაწერა ტოკენს, გამომცემლის, აუდიენციის, ვადის გასვლის, not-before დროის (მაქსიმუმ 60 წამიანი საათის ცდომილებით) და ყოველი claim-ის შემოწმების შემდეგ. გაცემული ერთსაათიანი CI ტოკენი მოქმედებს ანგარიშის დონეზე, არა პროექტების ID-ების სნეფშოტი: ის მოიცავს პროექტებს, რომლებიც შეიქმნა ან გადაიტანეს ანგარიშში გაცემის შემდეგ. პროექტის ავტორიზაცია კვლავ მოითხოვს ანგარიშის მიმდინარე მფლობელობას, ამიტომ პროექტის გადატანა აშორებს მის წვდომას ამ ანგარიშის ტოკენის ქვეშ.

#### workload-ის ავტენტიკაცია {#authenticate-a-workload}

1. მოითხოვეთ იდენტობის ტოკენი თქვენი პროვაიდერისგან პოლიტიკის აუდიენციით.
2. დააყენეთ `TUIST_OIDC_TOKEN` ამ ტოკენზე და `TUIST_OIDC_ACCOUNT` Tuist ანგარიშის handle-ზე, რომელიც ფლობს პროექტს. ანგარიში აუცილებელია ნდობის პოლიტიკის ყოველი გაცვლისთვის. ის მხოლოდ ირჩევს სად უნდა მოხდეს ძიება და თავისთავად არაფერს ანიჭებს.
3. გაუშვით Tuist. როდესაც `TUIST_TOKEN` ან მოქმედი შენახული სერთიფიკატები არ არის ხელმისაწვდომი, CLI და Elixir ინტეგრაცია ავტომატურად ახდენენ ტოკენის გაცვლას. `tuist auth login` და `mix tuist.login` აკეთებენ იგივე გაცვლას ცალსახად.

მიღებულ Tuist წვდომის ტოკენს აქვს მხოლოდ `ci` სკოპების ჯგუფი და მოიცავს შერჩეული ანგარიშის კუთვნილ ყველა მიმდინარე და მომავალ პროექტს. გაცვლები ვერ ხერხდება, თუ ანგარიშში 20-ზე მეტი პოლიტიკა ემთხვევა იგივე ტოკენს ან თუ ისინი იყენებენ ორზე მეტ განსხვავებულ JWKS URL-ს.

Tuist არ აახლებს ამ სესიებს. წვდომის ტოკენები იწურება ერთი საათის შემდეგ და არ აქვთ განახლების ტოკენი. პროვაიდერის იდენტობის ტოკენები ხშირად მოქმედებს მხოლოდ რამდენიმე წუთის განმავლობაში, ამიტომ ძველი `TUIST_OIDC_TOKEN`-ის შენახვა არ არის განახლების სტრატეგია: სამუშაოებისთვის, რომლებიც გრძელდება ერთ საათზე მეტხანს, მოითხოვეთ ახალი იდენტობის ტოკენი და გაიარეთ ავტორიზაცია ხელახლა Tuist სესიის ამოწურვამდე. პოლიტიკის წაშლა აჩერებს ახალ გაცვლებს, მაგრამ უკვე გაცემული წვდომის ტოკენები რჩება მოქმედი მათ ამოწურვამდე.

Tuist ინახავს პროვაიდერის ხელმოწერის გასაღებებს მაქსიმუმ 15 წუთის განმავლობაში წარმატებული მიღების შემდეგ სპეციალურ, ზომით შეზღუდულ ქეშში. ჩანაწერები შეიძლება ადრე ამოიღონ და ხელახლა მიიღონ. წარუმატებელი მიღებები არ ინახება ქეშში. თუ თქვენი პროვაიდერი აბრუნავს გასაღებებს, მან უნდა გამოაქვეყნოს ახალი გასაღები თავის JWKS-ში ტოკენებზე ხელმოწერამდე მინიმუმ 15 წუთით ადრე, რადგან ტოკენები, რომლებზეც ხელი მოაწერა გასაღებით, რომელიც არ არის ქეშირებულ ნაკრებში, უარყოფილია ქეშის ამოწურვამდე. ტოკენები გასაღების ID-ის (`kid`) გარეშე მიიღება მხოლოდ მაშინ, როდესაც JWKS შეიცავს ერთ შესაბამის ხელმოწერის გასაღებს. როდესაც JWKS-ში არის გასაღების ID, ის უნდა იყოს სტრინგი მაქსიმუმ 256 ბაიტისა.

> [!NOTE]
> `TUIST_OIDC_TOKEN` არის ზოგადი ტოკენის შეყვანა, არა სერვერის ნდობის გვერდის ავლის გზა. ის უპირატესობას ანიჭებს CI პროვაიდერის აღმოჩენას და სერვერი კვლავ იღებს მხოლოდ ჩაშენებულ პროვაიდერებს და იდენტობებს შესაბამისი ნდობის პოლიტიკით. არ ჩასვათ იდენტობის ტოკენი `TUIST_TOKEN`-ში, რომელიც ელოდება Tuist სერთიფიკატს.

თუ გაცვლა ვერ ხერხდება, შეამოწმეთ, რომ გამომცემელი, აუდიენცია და პოლიტიკის ყოველი claim ზუსტად ემთხვევა ტოკენს, რომ JWKS URL ემსახურება გასაღებს, რომელმაც ხელი მოაწერა ტოკენს, რომ პოლიტიკა არ არის წაშლილი და რომ `TUIST_OIDC_ACCOUNT` ასახელებს ანგარიშს, რომელიც ფლობს პროექტს. იმის თავიდან ასაცილებლად, თუ რომელი იდენტობებია სანდო, Tuist აბრუნებს იგივე შეცდომას ყველა ამ შემთხვევისთვის.

### Fly.io Machines {#flyio-machines}

[Fly.io მხარდაჭერას უწევს OIDC workload იდენტობას](https://docs.fly.io/reference/openid-connect/). Machine-ს შეუძლია მოითხოვოს ხანმოკლე, ხელმოწერილი იდენტობის ტოკენი თავისი ლოკალური `/.fly/api` Unix socket-იდან, Fly API ტოკენის ან ხანგრძლივი Tuist საიდუმლოს გარეშე. Fly ტოკენები აიდენტიფიცირებენ ორგანიზაციას და აპლიკაციას, არა საწყის რეპოზიტორიას, ამიტომ გამოიყენეთ ნდობის პოლიტიკა GitHub რეპოზიტორიის დაკავშირების ნაცვლად:

1. მიიღეთ გამომცემელი (`iss`), ორგანიზაციის ID (`org_id`) და აპლიკაციის ID (`app_id`) თქვენს Fly Machine-ში გაცემული იდენტობის ტოკენიდან. გამომცემელი არის `https://oidc.fly.io/<organization-slug>`. გამოიყენეთ რიცხვითი ID-ები, არა ორგანიზაციის ან აპის სახელები.
2. [შექმენით ნდობის პოლიტიკა](#create-a-trust-policy) **Fly.io Machines** შაბლონის გამოყენებით და შეიყვანეთ ორგანიზაციის slug და ორივე რიცხვითი ID. ის ავსებს ქვემოთ მოცემულ მნიშვნელობებს და ინარჩუნებს ID-ებს როგორც სტრინგებს. ასევე შეგიძლიათ შეიყვანოთ ისინი ხელით **Custom provider**-ის გამოყენებით; შეინარჩუნეთ ბრჭყალები ID-ების გარშემო claims-ში.

   | ველი | მნიშვნელობა |
   | --- | --- |
   | გამომცემლის URL | `https://oidc.fly.io/<organization-slug>` |
   | JWKS URL | `https://oidc.fly.io/<organization-slug>/.well-known/jwks` |
   | აუდიენცია | `tuist` |
   | Claims | `{"org_id": "<organization-id>", "app_id": "<application-id>"}` |

3. Machine-ის შიგნით, დააყენეთ `TUIST_OIDC_ACCOUNT` Tuist ანგარიშის handle-ზე, რომელიც ფლობს პროექტს (არა Fly ორგანიზაციის slug), მოითხოვეთ ტოკენი აუდიენციით `tuist` და გადაეცით ის `tuist auth login`-ს `TUIST_OIDC_TOKEN`-ის გამოყენებით:

```bash
set -euo pipefail
export TUIST_OIDC_ACCOUNT="my-tuist-account"

TUIST_OIDC_TOKEN="$(curl --fail --silent --show-error \
  --unix-socket /.fly/api \
  -X POST http://localhost/v1/tokens/oidc \
  -H 'Content-Type: application/json' \
  --data '{"aud":"tuist"}')"
export TUIST_OIDC_TOKEN

tuist auth login
unset TUIST_OIDC_TOKEN
```

საწყისი კონფიგურაციისთვის, შეგიძლიათ შეამოწმოთ მხოლოდ იდენტობის ველები ლოკალურად, ტოკენის ექსპორტირების შემდეგ და მისი გაუქმებამდე. ეს აკოდირებს claims-ს კონფიგურაციისთვის; Tuist ცალკე ამოწმებს ხელმოწერას ავტენტიკაციის დროს:

```bash
python3 - <<'PY'
import base64, json, os
payload = os.environ["TUIST_OIDC_TOKEN"].split(".")[1]
claims = json.loads(base64.urlsafe_b64decode(payload + "=" * (-len(payload) % 4)))
print(json.dumps({key: claims[key] for key in ("iss", "org_id", "app_id")}, indent=2))
PY
```

არ დაბეჭდოთ ან არ ჩააკომიტოთ თავად ტოკენი. ყოველ Machine-ს ავტორიზებულ Fly აპში შეუძლია ავტენტიკაცია Tuist ანგარიშის ყველა მიმდინარე და მომავალ პროექტზე. შექმენით ცალკე პოლიტიკა ყოველი დამატებითი აპისთვის. Fly იდენტობის ტოკენები იწურება დაახლოებით ათი წუთის შემდეგ, ამიტომ ხანგრძლივად მომუშავე Machine-ებზე მოითხოვეთ ახალი და გაუშვით `tuist auth login` ხელახლა ერთსაათიანი Tuist სესიის ამოწურვამდე.

### OIDC ტოკენის სკოპები {#oidc-token-scopes}

OIDC ტოკენებს ენიჭებათ `ci` სკოპების ჯგუფი. GitHub Actions-ის, CircleCI-ის და Bitrise-ისთვის, ეს უზრუნველყოფს წვდომას რეპოზიტორიასთან დაკავშირებულ ყველა პროექტზე. დაკავშირებული Amp workspace-ების, დაკავშირებული Claude Code გარემოების და workload იდენტობის ნდობის პოლიტიკებისთვის, ეს უზრუნველყოფს წვდომას შერჩეული ანგარიშის კუთვნილ ყველა მიმდინარე და მომავალ პროექტზე, პროექტის შექმნის, პროექტის ადმინისტრირების, runner-ის ადმინისტრირების ან ანგარიშის წევრების ადმინისტრირების მინიჭების გარეშე. იხილეთ [სკოპების ჯგუფები](#scope-groups) დეტალებისთვის, თუ რას მოიცავს `ci` სკოპი.

> [!TIP]
> **უსაფრთხოების უპირატესობები**
>
> OIDC ავტენტიკაცია უფრო უსაფრთხოა ვიდრე ხანგრძლივი ტოკენები, რადგან:
> - არ არის საიდუმლოები, რომლებიც უნდა შეიცვალოს ან იმართოს

> - ავტენტიკაცია დაკავშირებულია თქვენს რეპოზიტორიის იდენტობასთან ან ცალსახად ავტორიზებულ workload იდენტობასთან


## Gradle პლაგინის ავტენტიკაცია {#gradle-plugin-authentication}

Gradle პლაგინი იყენებს Tuist CLI-ის ავტენტიკაციის მდგომარეობას და არ განსაზღვრავს ცალკე შესვლის პროცესს. ერთხელ გაიარეთ ავტენტიკაცია CLI-ით და პლაგინი ხელახლა გამოიყენებს ამ რწმუნებათა სიგელებს.

პროექტისა და სერვერის კონფიგურაციისთვის, მათ შორის `project` და `url`, გამოიყენეთ კანონიკური <.localized_link href="/references/tuist-toml">tuist.toml მითითება</.localized_link>.

ლოკალური გამოყენებისთვის, გაუშვით:

```bash
tuist auth login
```

CI-ისთვის, გამოიყენეთ ერთ-ერთი:

- <.localized_link href="/guides/server/authentication#setting-up-oidc-authentication">OIDC ავტენტიკაცია</.localized_link> (რეკომენდებულია, თუ ხელმისაწვდომია)
- <.localized_link href="/guides/server/authentication#continuous-integration">ანგარიშის ტოკენით ავტენტიკაცია</.localized_link> `TUIST_TOKEN`-ის მეშვეობით

თვითმასპინძელი Tuist სერვერებისთვის, განსაზღვრეთ სერვერის URL `tuist.toml`-ში (მაგალითად `url = "https://tuist.your-company.com"`) და გაუშვით სტანდარტული შესვლის პროცესი. URL იგივე კონფიგურაციის ფაილიდან იხსნება, რომელსაც პლაგინი იყენებს.

ავტენტიკაციის კონფიგურაციის შემდეგ, ჩვეულებრივად გაუშვით თქვენი Gradle ქეშირების ბრძანებები და დავალებები.

## ანგარიშის ტოკენები {#account-tokens}

CI გარემოებისთვის, რომლებიც არ უჭერენ მხარს OIDC-ს, ან როდესაც საჭიროა ნებართვებზე ზუსტი კონტროლი, შეგიძლიათ გამოიყენოთ ანგარიშის ტოკენები. ანგარიშის ტოკენები საშუალებას გაძლევთ ზუსტად მიუთითოთ, თუ რომელ სკოპებსა და პროექტებზე აქვს ტოკენს წვდომა.

### ანგარიშის ტოკენის შექმნა {#creating-an-account-token}

ანგარიშის ტოკენის შექმნის ყველაზე მარტივი გზა დაფიცხიდან არის:

1. გახსენით ორგანიზაცია Tuist დაფიცხში.
2. გადადით **პარამეტრები** > **ტოკენები**.
3. აირჩიეთ **ტოკენის გენერირება**.
4. აირჩიეთ სახელი, ვადის გასვლის არასავალდებულო პარამეტრი, პროექტზე წვდომა და სკოპები, რომლებიც ტოკენს სჭირდება.
5. დახურვამდე დააკოპირეთ გენერირებული ტოკენის მნიშვნელობა. ტოკენის მნიშვნელობები მხოლოდ ერთხელ ჩანს.

ანგარიშის ტოკენების შექმნა ასევე შეგიძლიათ CLI-დან, რაც სასარგებლოა სკრიპტინგის ან ავტომატიზაციისთვის:

```bash
tuist account tokens create account-handle \
  --scopes account:cache:write project:cache:read project:cache:write \
  --name ci-cache-token \
  --expires 1y
```

> [!IMPORTANT]
> ჩაანაცვლეთ `account-handle` იმ ანგარიშის handle-ით, რომელსაც ეკუთვნის პროექტები, რომლებზეც ტოკენს წვდომა უნდა ჰქონდეს. ეს შეიძლება იყოს ორგანიზაციის ანგარიში და არა აუცილებლად თქვენი პირადი ანგარიში.

ბრძანება იღებს შემდეგ პარამეტრებს:

| პარამეტრი | აღწერა |
| --- | --- |
| `--scopes` | სავალდებულო. სკოპების სია, გამოყოფილი გამოტოვებით, რომლებიც ტოკენს მიენიჭება. |
| `--name` | სავალდებულო. ტოკენის უნიკალური იდენტიფიკატორი (1-32 სიმბოლო, მხოლოდ ალფანუმერული, დეფისები და ქვედა ტირეები). |
| `--expires` | არასავალდებულო. როდის უნდა გაუვიდეს ტოკენს ვადა. გამოიყენეთ ფორმატი, როგორიცაა `30d` (დღეები), `6m` (თვეები) ან `1y` (წლები). თუ არ არის მითითებული, ტოკენს ვადა არასდროს გაუვა. |
| `--projects` | შეზღუდეთ ტოკენი კონკრეტული პროექტების handle-ებით. თუ არ არის მითითებული, ტოკენს აქვს წვდომა ყველა პროექტზე. |

### სკოპების ჯგუფები {#scope-groups}

სკოპების ჯგუფები საშუალებას გაძლევთ ერთი იდენტიფიკატორით მიანიჭოთ რამდენიმე დაკავშირებული სკოპი. როდესაც იყენებთ სკოპების ჯგუფს, ის ავტომატურად ფართოვდება და მოიცავს ყველა ინდივიდუალურ სკოპს, რომელიც მასში შედის.

| სკოპების ჯგუფი | ჩართული სკოპები |
| --- | --- |
| `ci` | `account:cache:write`, `project:cache:write`, `project:previews:write`, `project:bundles:write`, `project:tests:write`, `project:builds:write`, `project:runs:write` |
| `mcp` | `project:cache:read`, `project:previews:read`, `project:bundles:read`, `project:tests:read`, `project:builds:read`, `project:runs:read` |

### უწყვეტი ინტეგრაცია {#continuous-integration}

CI გარემოებისთვის, რომლებიც არ უჭერენ მხარს OIDC-ს, შექმენით ანგარიშის ტოკენი `ci` სკოპების ჯგუფით თქვენი CI სამუშაო ნაკადების ავტორიზაციისთვის. დაფიცზე ტოკენის გენერირებისას აირჩიეთ **CI** პრესეტი.

იგივე ტოკენის შექმნა CLI-დანაც შეგიძლიათ:

```bash
tuist account tokens create account-handle --scopes ci --name ci
```

ეს ქმნის ტოკენს ყველა იმ სკოპით, რაც საჭიროა ტიპური CI ოპერაციებისთვის (cache, previews, bundles, tests, builds და runs). შეინახეთ გენერირებული ტოკენი როგორც საიდუმლო თქვენს CI გარემოში და დააყენეთ ის როგორც `TUIST_TOKEN` გარემოს ცვლადი.

### ანგარიშის ტოკენების მართვა {#managing-account-tokens}

გახსენით **Settings** > **Tokens** ანგარიშის დაფიცზე, რათა ნახოთ ანგარიშის ტოკენები, შეამოწმოთ ტოკენის სკოპები და პროექტებზე წვდომა, და გააუქმოთ ტოკენები როტაციის დროს.

ანგარიშის ყველა ტოკენის სიისთვის:

```bash
tuist account tokens list account-handle
```

ტოკენის სახელით გასაუქმებლად:

```bash
tuist account tokens revoke account-handle ci-cache-token
```

### ანგარიშის ტოკენების გამოყენება {#using-account-tokens}

ანგარიშის ტოკენები უნდა იყოს განსაზღვრული როგორც გარემოს ცვლადი `TUIST_TOKEN`:

```bash
export TUIST_TOKEN=your-account-token
```

> [!TIP]
> **როდის გამოვიყენოთ ანგარიშის ტოკენები**
>
> გამოიყენეთ ანგარიშის ტოკენები, როდესაც გჭირდებათ:
> - ავტორიზაცია CI გარემოებში, რომლებიც არ უჭერენ მხარს OIDC-ს
> - ზუსტი კონტროლი იმაზე, თუ რა ოპერაციების შესრულება შეუძლია ტოკენს
> - ტოკენი, რომელსაც შეუძლია წვდომა ანგარიშში არსებულ რამდენიმე პროექტზე
> - დროით შეზღუდული ტოკენები, რომლებიც ავტომატურად იწურება
