# 原則 {#principles}

本頁說明 Tuist 設計與開發的核心原則。這些原則會隨著專案演進，確保成長可持續，並與專案基礎保持一致。

## 預設採用約定 {#default-to-conventions}

Tuist 存在的原因之一，是 Xcode 在約定方面較弱，導致專案複雜、難以擴展與維護。因此，Tuist 採取不同的做法，預設採用簡單且經過仔細設計的約定。**開發者可以選擇不遵循這些約定，但這是一項刻意決定，感覺並不自然。**

例如，有一個約定是使用提供的公開介面來定義目標之間的相依性。如此一來，Tuist 能確保產生的專案具備正確的設定，讓連結順利運作。開發者也可以透過建置設定來定義相依性，但這樣做屬於隱式行為，會破壞依賴這些約定的 Tuist 功能，例如 `tuist graph` 或 `tuist cache`。

我們預設採用約定的原因是：能替開發者做的決定越多，他們就越能專注於為應用程式打造功能。當許多專案缺乏約定時，我們必須做出與其他決定不一致的選擇，進而產生難以管理的意外複雜性。

## 清單檔案是唯一真相來源 {#manifests-are-the-source-of-truth}

多層設定與其間的契約會讓專案設定變得難以理解與維護。想像一個典型的專案：專案定義位於 `.xcodeproj` 目錄中，CLI 邏輯寫在腳本裡（例如 `Fastfiles`），CI 邏輯則放在管線中。這三層之間存在需要維護的契約。*你有多常遇到這種情況：修改了專案內容，過了一週才發現發布腳本壞掉了？*

我們可以透過單一真相來源——清單檔案——來簡化這一點。這些檔案提供 Tuist 生成 Xcode 專案所需的資訊，讓開發者能用來編輯檔案。此外，它也支援從本機或 CI 環境執行標準的專案建置指令。

**Tuist 應承擔複雜性，並提供簡單、安全且令人愉悅的介面，讓開發者盡可能明確地描述他們的專案。**

## 將隱式行為顯式化 {#make-the-implicit-explicit}

Xcode 支援隱式設定。一個很好的例子是推斷隱式定義的相依性。雖然隱式行為在設定簡單的小型專案中尚可接受，但隨著專案變大，可能會導致速度變慢或出現異常行為。

Tuist 應為隱式的 Xcode 行為提供顯式 API。它也應支援定義 Xcode 的隱式行為，但以鼓勵開發者選擇顯式方式實作。支援 Xcode 的隱式行為與細微之處有助於團隊採用 Tuist，之後團隊可以再花時間逐步移除隱式設定。

相依性的定義就是一個好例子。雖然開發者可以透過建置設定與階段來定義相依性，但 Tuist 提供了優雅的 API，鼓勵大家採用。

**將 API 設計為顯式，讓 Tuist 能夠對專案執行一些否則無法進行的檢查與最佳化。** 此外，它也啟用诸如 `tuist graph`（匯出相依圖的表示）或 `tuist cache`（將所有目標快取為二進位檔）等功能。

> [!TIP]
> 我們應將每個從 Xcode 移植功能的需求視為機會，以簡單且顯式的 API 簡化概念。


## 保持簡單 {#keep-it-simple}

擴展 Xcode 專案的主要挑戰之一在於：**Xcode 向使用者暴露了大量複雜性。** 因此，團隊的關鍵人員風險很高，只有少數人理解專案以及建置系統拋出的錯誤。這對團隊來說是不利的狀況，因為團隊過度依賴少數人。

Xcode 是個出色的工具，但多年的改進、新平台與程式語言都反映在其表面上，使其難以保持簡單。

Tuist 應把握機會保持簡單，因為處理簡單的事物既有趣又能激勵我們。沒人想把時間花在除錯編譯過程最後階段發生的錯誤，或搞懂為何無法在裝置上執行應用程式。Xcode 將任務委派給底層建置系統，而在某些情況下，它在將錯誤轉化為可執行的項目方面做得很差。你是否曾遇到 *「找不到 framework X」* 的錯誤卻不知如何處理？想像一下，如果我們能提供潛在根本原因的清單，情況會好很多。

## 從開發者體驗出發 {#start-from-the-developers-experience}

Xcode 周邊缺乏創新（或者換句話說，不如其他程式環境那麼多）的部分原因在於：**我們經常從既有解決方案開始分析問題。** 結果，如今找到的大多數解決方案都圍繞著相同的想法與工作流程。雖然將既有解決方案納入考量是好事，但不應讓它們限制我們的創意。

我們喜歡像 [Tom Preston](https://tom.preston-werner.com/) 在 [這集 podcast](https://tom.preston-werner.com/) 中所說的那樣思考：*「大多數事情都能達成，只要在你腦海中的想法在宇宙的限制內可行，你就很可能用程式碼實現它。」* 如果 **我們想像理想的開發者體驗應該是什麼樣子**，實現它只是時間問題——從開發者體驗出發分析問題，能給我們獨特的視角，引導我們打造出使用者喜愛的解決方案。

我們可能會忍不住跟風，即使那意味著繼續忍受眾人抱怨的不便。別這麼做。我期望如何封存我的應用程式？我希望程式碼簽署的流程是什麼樣子？我能用 Tuist 協助簡化哪些流程？例如，新增對 [Fastlane](https://fastlane.tools/) 的支援是某個問題的解決方案，但我們需要先理解該問題。透過不斷追問「為什麼」，我們可以找到問題的根本原因。一旦釐清動機來源，就能思考 Tuist 如何提供最佳協助。也許解決方案是與 Fastlane 整合，但在做出取捨之前，務必不要忽視其他同樣可行的方案。

## 錯誤不可避免 {#errors-can-and-will-happen}

身為開發者，我們天生容易忽視錯誤發生的可能性。結果，我們在設計與測試軟體時，往往只考慮理想情境。

Swift、其型別系統以及架構良好的程式碼有助於防止某些錯誤，但無法防止所有錯誤，因為有些因素超出我們的控制範圍。我們不能假設使用者永遠有網路連線，或系統指令一定會成功執行。Tuist 執行的環境並非我們可控的沙箱，因此我們必須努力了解這些環境可能如何變化並影響 Tuist。

錯誤處理不當會導致糟糕的使用者體驗，使用者也可能因此對專案失去信任。我們希望使用者喜愛 Tuist 的每一個環節，就連我們呈現錯誤的方式也不例外。

我們應換位思考，想像自己期望錯誤訊息提供什麼內容。如果程式語言是錯誤傳播的溝通管道，而使用者是錯誤的接收端，那麼錯誤訊息就應該以目標對象（使用者）熟悉的語言撰寫。它們應包含足夠資訊讓使用者了解發生了什麼事，並隱藏不相關的資訊。此外，錯誤訊息應具備可操作性，告訴使用者可以採取哪些步驟來恢復。

最後但同樣重要的是，我們的測試案例應涵蓋失敗情境。這不僅能確保我們按預期處理錯誤，也能防止未來的開發者破壞這項邏輯。
