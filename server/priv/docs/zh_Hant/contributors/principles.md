# 原則 {#principles}

本頁說明構成 Tuist 設計與開發核心的原則。這些原則會隨著專案演進，以確保成長可持續，並與專案基礎保持一致。

## 預設採用約定 {#default-to-conventions}

Tuist 存在的原因之一，是 Xcode 在約定方面較弱，導致專案複雜、難以擴展與維護。因此，Tuist 採取不同做法，預設採用簡單且經過周全設計的約定。**開發者可以選擇不遵循這些約定，但這屬於刻意決定，感覺並不自然。**

例如，我們有一項約定：透過提供的公開介面來定義目標之間的相依性。如此一來，Tuist 能確保專案以正確的設定產生，讓連結正常運作。開發者也可以透過建置設定來定義相依性，但這種做法屬於隱式定義，因而會破壞依賴這些約定的 Tuist 功能，例如 `tuist graph` 或 `tuist cache`。

我們之所以預設採用約定，是因為能替開發者做出的決定越多，他們就能越專注於為應用程式打造功能。若像許多專案那樣缺乏約定，我們就必須做出彼此不一致的決定，進而產生難以管理的意外複雜度。

## Manifest 檔案為唯一真相來源 {#manifests-are-the-source-of-truth}

當設定層級繁多且彼此之間存在合約時，專案設定會變得難以理解與維護。試想一個一般專案：專案定義位於 `.xcodeproj` 目錄中，CLI 邏輯放在腳本裡（例如 `Fastfiles`），而 CI 邏輯則寫在管線中。這三層之間存在需要維護的合約。*你是否曾遇過修改專案後，過了一週才發現發布腳本出錯的情況？*

我們可以透過單一真相來源（即 manifest 檔案）來簡化這一點。這些檔案提供 Tuist 所需的資訊，用以產生 Xcode 專案，讓開發者能夠編輯檔案。此外，它也支援從本機或 CI 環境執行標準的專案建置命令。

**Tuist 應承擔複雜度，並提供簡單、安全且令人愉悅的介面，讓開發者盡可能以明確的方式描述其專案。**

## 將隱式行為轉為顯式 {#make-the-implicit-explicit}

Xcode 支援隱式設定。一個典型的例子是推斷隱式定義的相依性。雖然隱式設定在小型專案中尚可接受（因為設定較為簡單），但隨著專案規模擴大，可能會導致速度變慢或出現異常行為。

Tuist 應為 Xcode 的隱式行為提供顯式 API。它也應支援定義 Xcode 的隱式行為，但以鼓勵開發者選擇顯式做法的方式實作。支援 Xcode 的隱式特性與細節有助於團隊採用 Tuist，之後團隊可以逐步移除這些隱式設定。

相依性的定義就是個好例子。雖然開發者可以透過建置設定與階段來定義相依性，但 Tuist 提供了優雅的 API，鼓勵大家採用。

**將 API 設計為顯式，讓 Tuist 能夠對專案執行一些否則無法進行的檢查與最佳化。** 此外，它也啟用了如 `tuist graph`（匯出相依圖的表示）或 `tuist cache`（將所有目標快取為二進位檔）等功能。

> [!TIP]
> 我們應將每個從 Xcode 移植功能的要求，視為以簡單且顯式的 API 簡化概念的機會。


## 保持簡單 {#keep-it-simple}

擴展 Xcode 專案時的主要挑戰之一，來自於**Xcode 向使用者暴露了大量複雜度。** 因此，團隊的關鍵人員風險很高，只有少數人真正了解專案以及建置系統拋出的錯誤。這對團隊而言是不利的狀況，因為過度依賴少數人。

Xcode 是個強大的工具，但多年的改進、新平台與程式語言的累積都反映在其表面上，使其難以維持簡單。

Tuist 應把握機會保持簡單，因為處理簡單的事物既有趣又能激勵我們。沒有人願意花時間去除錯編譯過程末端發生的錯誤，或搞懂為何無法在裝置上執行應用程式。Xcode 將工作委派給底層的建置系統，而在某些情況下，它將錯誤轉換為可執行動作的效果很差。你是否曾遇到 *「找不到 framework X」* 的錯誤卻不知該如何處理？想像一下，如果我們能得到一份潛在根本原因的清單。

## 從開發者體驗出發 {#start-from-the-developers-experience}

Xcode 周邊缺乏創新（或者換句話說，不如其他程式環境那麼多）的部分原因，在於**我們常常從既有解決方案出發來分析問題。** 結果是，如今找到的大多數解決方案都圍繞著相同的想法與工作流程。雖然將既有解決方案納入考量是好事，但不應讓它們限制我們的創意。

我們喜歡像[Tom Preston](https://tom.preston-werner.com/)在[這集 podcast](https://tom.preston-werner.com/)中所說的那樣思考：*「大多數事情都能達成；只要在你腦海中的想法符合宇宙的限制，你大概都能用程式碼實現。」* 如果**我們想像理想的開發者體驗應該是什麼樣子**，實現它只是時間問題——從開發者體驗出發分析問題，能帶來獨特的視角，引導我們打造出使用者喜愛的解決方案。

我們可能會忍不住跟隨大眾的做法，即使這意味著要忍受大家持續抱怨的不便。讓我們不要這麼做。我期望如何封存我的應用程式？我希望程式碼簽署的流程是什麼樣子？我能用 Tuist 協助簡化哪些流程？例如，加入對 [Fastlane](https://fastlane.tools/) 的支援是針對某個問題的解決方案，而我們需要先理解該問題。我們可以透過不斷詢問「為什麼」來找出問題的根本原因。一旦釐清動機的來源，我們就能思考 Tuist 如何提供最佳協助。也許解決方案是與 Fastlane 整合，但在做出取捨之前，務必不要忽視其他同樣可行、可納入考量的方案。

## 錯誤確實會發生 {#errors-can-and-will-happen}

我們開發者天生容易忽視錯誤可能發生的事實。結果，我們在設計與測試軟體時，往往只考慮理想情境。

Swift、其型別系統以及架構良好的程式碼或許能防止部分錯誤，但無法防止所有錯誤，因為有些錯誤超出我們的控制範圍。我們不能假設使用者永遠擁有網路連線，或系統指令一定會成功執行。Tuist 執行的環境並非我們可控管的沙箱，因此我們必須努力了解這些環境可能如何變化，以及它們對 Tuist 的影響。

錯誤處理不當會導致糟糕的使用者體驗，使用者也可能因此對專案失去信任。我們希望使用者享受 Tuist 的每一個環節，甚至包括我們呈現錯誤的方式。

我們應設身處地為使用者著想，想像我們期望錯誤訊息告訴我們什麼。如果程式語言是錯誤傳遞的溝通管道，而使用者是錯誤的接收端，那麼錯誤訊息就應該以目標對象（使用者）熟悉的語言撰寫。它們應包含足夠的資訊讓使用者了解發生了什麼事，並隱藏不相關的資訊。此外，它們應具備可操作性，明確告知使用者可以採取哪些步驟來恢復。

最後但同樣重要的是，我們的測試案例應涵蓋失敗情境。這不僅能確保我們按照預期處理錯誤，也能防止未來的開發者破壞這項邏輯。
