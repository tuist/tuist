# 什麼是建置快取？{#what-is-a-build-cache}

建置快取會將各個建置步驟的輸出（例如編譯後的物件檔、模組、程式庫或測試結果）存放在一個金鑰之下，該金鑰是根據產生這些輸出所需的一切因素計算而來：原始碼檔案、編譯器旗標、相依性、環境變數以及工具鏈版本。當後續建置需要某個步驟，且其輸入產生的金鑰與先前相同時，建置系統會直接採用已儲存的輸出，而非再次執行該步驟。**本機建置快取**位於單一機器上，可加速該機器後續的建置作業。**遠端建置快取**則是一個共享伺服器，供多台機器讀取與寫入，讓 CI 工作、團隊成員或程式碼代理程式能夠重複使用他人已建置完成的輸出。

## 建置快取、增量建置與 CI 目錄快取{#build-cache-incremental-build-and-ci-cache}

有三種概念常被統稱為「快取」，但它們的行為各不相同：

- **增量建置**會重複使用已存在於你本機建置目錄中的輸出，並僅重新建置自上次建置以來發生變更的部分。它們通常依賴檔案時間戳記或與建置產物一同保存的相依性圖譜。切換分支、移動檢出目錄，或從全新的機器開始，都會導致這些狀態遺失。
- **建置快取**會依據輸入內容來查詢輸出，而非依據同一目錄中最後一次建置的內容。這使得輸出可以在不同分支、檢出目錄與機器之間重複使用，只要輸入相符即可。
- **CI 目錄快取**（例如 GitHub Actions 上的 `actions/cache`）會在工作結束時儲存某個目錄，並在下一個工作開始時將其還原，所使用的金鑰由你自行選擇（例如鎖定檔案的雜湊值）。這是一種檔案傳輸機制，並非建置快取：建置系統仍會決定需要重新建置哪些部分，而還原的目錄可能部分或完全過時。

相依性快取（例如下載的套件，或 Gradle 與 Swift 套件快取）則是另一回事：它們節省的是網路下載時間，而非編譯時間。

## 建置快取的運作方式{#how-a-build-cache-works}

支援快取的建置系統會將建置流程拆分為多個步驟（Bazel 稱之為 action，Gradle 稱之為 task），並對每個步驟執行相同的操作：

1. **計算快取金鑰。** 建置系統會對所有可能影響輸出的輸入進行雜湊處理：輸入檔案的內容、命令列或任務設定、相關環境變數，以及工具鏈。
2. **查詢金鑰。** 它會先檢查本機快取，若已設定遠端快取，也會一併檢查。
3. **命中或未命中。** 若命中，它會下載或複製已儲存的輸出，並跳過該步驟。若未命中，它會執行該步驟，並在允許的情況下將輸出以上述金鑰上傳。

大多數快取會將輸出儲存在**內容定址儲存空間**（CAS）中，其中每個資料區塊都以其自身內容的雜湊值作為儲存鍵，另外還有一個獨立的索引，將快取金鑰對應到其所產生的輸出。相同的檔案只會儲存一次，客戶端可以驗證下載的內容。

此模型有一項嚴格要求：金鑰必須包含所有會改變輸出的輸入。如果某個步驟讀取了建置系統未知的輸入（例如未宣告的檔案、環境變數、當前時間，或機器上安裝的工具），快取可能會回傳與目前輸入不符的輸出。建置系統將僅依賴已宣告輸入的步驟稱為**封閉性（hermetic）** 步驟。相反的問題更為常見且風險較低：若金鑰包含了無關資訊（例如絕對路徑或時間戳記），每台機器產生的金鑰都會不同，導致快取永遠無法命中。

## 各建置系統的快取運作方式{#how-it-works-per-build-system}

### Gradle 建置快取{#gradle}

[Gradle 建置快取](https://docs.gradle.org/current/userguide/build_cache.html)會儲存可快取任務的輸出（例如 Java 與 Kotlin 編譯以及測試執行），並以任務類型、實作方式、輸入屬性及標準化後的輸入檔案作為金鑰。預設情況下此功能為關閉狀態。你可以在 `gradle.properties` 中使用 `org.gradle.caching=true` 啟用，或在單一建置中使用 `--build-cache` 啟用。

- **本機。** 內建的本機快取是 Gradle 使用者主目錄中的一個目錄（預設為 `~/.gradle`）。一旦啟用建置快取，此功能即會生效，且 Gradle 會定期移除近期未使用的項目。
- **遠端。** 遠端快取在 `settings.gradle(.kts)` 中設定，例如使用 `HttpBuildCache`。當本機未命中時，Gradle 會從遠端快取下載輸出，並在本機儲存以供下次使用。預設情況下，遠端快取不接受上傳；常見的設定是讓 CI 進行推送（在 CI 中執行時設定 `isPush = true`），而開發者機器僅能讀取。

Gradle 會將從快取還原的任務回報為 `FROM-CACHE`，這與 `UP-TO-DATE` 不同：up-to-date 表示 Gradle 的增量建置發現任務輸出已就緒，無需查詢快取。設定快取（configuration cache）是第三項獨立功能，它快取的是設定階段的結果，而非任務輸出。

### Bazel 遠端快取{#bazel}

Bazel 會快取每個 action。它的 action 快取將 action 的金鑰（由其命令列、環境變數及輸入檔案的摘要組成）對應到 action 的輸出，而輸出本身則儲存在內容定址儲存空間中。

- **本機。** Bazel 會在其輸出基礎目錄中維護 action 快取與建置輸出，讓你在單一工作區中能進行快速的增量建置。`--disk_cache=<path>` 則新增了一個磁碟快取，可在同一台機器上的不同工作區與分支之間共享。
- **遠端。**`--remote_cache=grpcs://…`（或 `https://…`）會將 Bazel 指向實作了 [Remote Execution API](https://github.com/bazelbuild/remote-apis) 或純 HTTP 快取的遠端快取。`--remote_upload_local_results=false` 可將機器設為唯讀模式，許多團隊藉此防止開發者機器寫入共享快取。`--remote_download_minimal` 或 `--remote_download_toplevel`（「build without the bytes」）可避免下載本機建置從未需要的中間輸出。

Bazel 也會快取測試結果：若測試的輸入未發生變更，則會回報為 `(cached) PASSED` 而不實際執行。遠端快取不同於遠端執行（remote execution），後者會讓 action 也在遠端機器上執行；快取僅儲存結果。

### 什麼是 Xcode 快取？{#xcode}

Xcode 使用了數種容易混淆的快取與目錄。會影響建置時間的包括：

- **DerivedData**（`~/Library/Developer/Xcode/DerivedData/<Project>-<hash>/`）儲存每個專案的建置產出、中繼檔案、索引、日誌，以及已解析的 Swift 套件。這是增量建置所重複使用的狀態。刪除它是安全的，但該專案的下一次建置將會是完整重建，且索引與套件解析會再次執行。
- **Clang 模組快取**（`~/Library/Developer/Xcode/DerivedData/ModuleCache.noindex/`）儲存用於匯入 C 與 Objective-C 模組及 SDK 框架的預編譯 Clang 模組（`.pcm` 檔案），並在專案間共享。若啟用明確建置模組功能，Xcode 會改為將模組作為一般建置任務來建置，並將其保存在各專案的中繼目錄中。刪除它是安全的；模組會在需要時重新建置。
- **編譯快取**（Xcode 26 及更新版本，預設位於 DerivedData 內的 `CompilationCache.noindex`，可透過 `COMPILATION_CACHE_CAS_PATH` 設定）在 `COMPILATION_CACHE_ENABLE_CACHING = YES` 時，儲存 Swift、C 與 Objective-C 的內容定址編譯輸出。刪除它是安全的；原本可重放的編譯作業會再次執行。
- **Swift Package Manager 快取**（`~/Library/Caches/org.swift.swiftpm/`）儲存下載的套件儲存庫與資訊清單，並在專案間共享。刪除它是安全的；套件會再次抓取。

`~/Library/Developer` 下的其他大型目錄並非建置快取，但在清理磁碟空間時經常出現：`Xcode/Archives` 儲存歸檔的 App 建置及其除錯符號（保留你可能需要用於符號化崩潰記錄的項目）、`Xcode/iOS DeviceSupport` 儲存已連接裝置作業系統版本的符號，而 `CoreSimulator/Devices` 則儲存模擬器及其資料（`xcrun simctl delete unavailable` 會移除已不再安裝之執行環境對應的模擬器）。

DerivedData 是 Xcode 的增量建置狀態，而非內容定址快取：它與專案在磁碟上的位置及檔案時間戳記綁定。從 CI 快取還原 DerivedData 到不同路徑，或在全新檢出後因所有檔案修改時間變更而還原，通常仍會導致完整重建。

**編譯快取**於 Xcode 26 引入，是本頁所指意義下的 Xcode 建置快取。它依據輸入內容儲存編譯結果，並在命中時重放結果，因此輸出不會因切換分支或清除建置產出而遺失。它快取的是編譯作業，而非每個建置步驟：連結、資源處理與腳本階段仍會執行。預設情況下，儲存空間僅限於單一機器並位於 DerivedData 內，因此刪除整個 DerivedData 會一併移除它；若僅刪除專案的建置產出，則會保留它。Xcode 也可透過外掛程式將編譯快取連接至遠端快取服務（`COMPILATION_CACHE_ENABLE_PLUGIN` 與 `COMPILATION_CACHE_REMOTE_SERVICE_PATH`），使其成為共享的遠端快取。

在編譯快取出現之前，Xcode 專案主要透過 **二進位快取** 整個模組來跨機器重複使用工作：將相依性建置為預先建置的 Framework 或 XCFramework，並連結這些檔案而非編譯原始碼。這種方式作用於模組層級而非編譯層級，並會改變專案的建置方式。

## 延遲、Blob 大小與 Blob 數量{#latency-blob-size-and-blob-count}

遠端快取命中並非免費。擷取輸出會產生固定延遲，因為每個請求必須等待前一個請求完成，再加上傳輸其位元組所需的時間：

**time ≈ R × L + S / B**

其中 *R* 是無法重疊的往返次數，*L* 是往返快取的延遲，*S* 是傳輸的位元組數，而 *B* 是頻寬。哪一項佔主導地位，取決於建置系統如何將工作切割成 blob：

- **少量大型 blob 受頻寬限制。** 儲存粗粒度輸出（例如 Gradle 任務的打包輸出或二進位模組快取中的預先建置 Framework）的快取，發出的請求較少，但每個請求傳輸的資料量達數 MB。在 100 Mbit/s 下，一組 200 MB 的輸出約需 16 秒，而在 1 Gbit/s 下則不到 2 秒，此時額外幾毫秒的延遲幾乎無關緊要。
- **大量小型 blob 受延遲限制。** 細粒度快取（例如 Bazel 的每 action 快取與 Xcode 的編譯快取）會發出數千次請求以獲取數 KB 大小的 blob，其中許多請求僅用於確認金鑰是否存在。若有 2,000 次查找、同時進行 8 次請求，且延遲為 40 ms，則建置僅因往返就會等待約 10 秒，無論 blob 多麼小。若延遲為 2 ms，同樣的查找則約需半秒。增加頻寬在此無濟於事；縮短快取距離才有幫助。
- **未命中也會產生往返成本。** 每次未命中的查找都會增加延遲，卻無法節省任何工作。命中率低的遠端快取可能讓建置比完全沒有遠端快取更慢。
- **數量會放大兩者影響。** Blob 數量隨專案結構增長：由許多小型模組或目標組成的圖形，會產生比少數大型模組更多且更小的輸出。拆分專案能提升平行處理與失效效率，但會讓建置對快取延遲更為敏感。

唯有當擷取輸出比重新計算更快時，命中才具價值，而此比較會隨距離變化。在本機耗時 50 ms 的編譯作業，若來自同一網路的快取則是良好的命中，但若來自另一大洲的快取則效果不佳。這就是為什麼遠端快取的調整重點主要在延遲與請求數量，而非原始頻寬：

- **將快取部署在建置執行處附近**，與 CI 執行器位於相同區域或網路，並盡可能靠近開發者。
- **重疊請求。** Bazel 的 Remote Execution API 會批次處理存在性檢查（`FindMissingBlobs`）與小型讀取，而 `--remote_max_connections` 則限制並行連線數。Xcode 的 `COMPILATION_CACHE_ENABLE_DETACHED_KEY_QUERIES` 會讓編譯快取查找與建置的其他部分同時進行，而非佔用其執行通道。HTTP/2 可在單一連線上多工處理許多請求。
- **減少下載量。** Bazel 的 `--remote_download_minimal` 會跳過中間輸出，而本機快取層（例如 Bazel 的 `--disk_cache` 或 Gradle 的本機建置快取）可在無需網路請求的情況下服務重複命中。
- **壓縮大型 blob。** 當快取支援時，Bazel 的 `--remote_cache_compression` 會使用 zstd，這有助於受頻寬限制的傳輸，但對受延遲限制的傳輸幫助有限。

## 常見陷阱{#common-pitfalls}

- **未宣告的輸入。** 某個步驟讀取了不屬於其金鑰一部分的檔案、環境變數或工具。快取隨後可能回傳由不同輸入建置的輸出。在 Gradle 中，請宣告自訂任務的所有輸入；在 Bazel 中，請保持動作具封閉性，並考慮使用 `--incompatible_strict_action_env`，以免主機 `PATH` 滲漏進來。
- **機器專屬的金鑰。** 嵌入輸入或輸出中的絕對路徑、使用者名稱與建置時間戳記，會導致金鑰在不同機器間產生差異，使遠端快取永遠無法命中。Gradle 的路徑敏感性、Bazel 的相對執行路徑，以及 Xcode 中的 Clang 與 Swift 前綴對應設定，都是為了消除這些差異。
- **靠近圖形根節點的易變輸入。** 將建置編號、提交雜湊或日期印入所有模組都相依的模組中，會在每次建置時使該模組之上的所有內容失效。請盡可能延後注入易變值，理想情況下僅注入至發行版建置。
- **工具鏈不相符。** 不同的編譯器、JDK 或 Xcode 版本會產生不同的金鑰。這是正確行為，但混合版本的機器群組實際上會分割快取。
- **受污染或不受信任的寫入。** 擁有未提交變更或非封閉設定的開發者機器，可能會上傳讓其他人重複使用的輸出。許多團隊僅允許受信任分支上的 CI 寫入遠端快取，並將其他所有機器設為唯讀。不受信任的拉取請求建置不應寫入受信任建置所讀取的快取。
- **忽略傳輸成本。** 執行耗時 50 毫秒的步驟，從遠端快取擷取可能花費更長時間。請參閱[延遲、blob 大小與 blob 數量](#latency-blob-size-and-blob-count)。
- **隱藏的測試執行。** 當測試具備決定性時，快取測試結果是正確的作法，但這也意味著曾經通過的不穩定測試會持續顯示通過，而無需再次執行。請參閱<.localized_link href="/references/concepts/flaky-test">什麼是不穩定測試？</.localized_link>。

## 如何衡量建置快取{#how-to-measure-a-build-cache}

快取的價值在於端到端節省的時間，而非僅看命中率：

- **按工作量加權的命中率。** 統計每個步驟的命中與未命中次數，但應依各步驟的執行時間加權。在低成本步驟上達到 95% 的命中率，其節省效果可能低於在最慢編譯作業上達到 50% 的命中率。
- **冷啟動、暖機與典型建置。** 比較空快取時的建置、完全暖機快取時的建置，以及人們實際執行的建置（例如小幅變更後拉取請求上的 CI）。最後一項才是關鍵數字。
- **花在快取本身的時間。** 測量請求數量、延遲、位元組數，以及下載與上傳所花費的時間。若大部分時間都在等待許多小型請求，則較近的快取比增加頻寬更有幫助；若主要在移動少數大型 blob，則頻寬與壓縮更為重要。
- **未命中的原因。** 比較兩台機器上相同步驟的快取金鑰。Gradle 可使用 `-Dorg.gradle.caching.debug=true` 印出每個金鑰背後的輸入，Bazel 可寫入執行日誌（`--execution_log_compact_file`）供您在兩次建置間進行差異比較，而當 `COMPILATION_CACHE_ENABLE_DIAGNOSTIC_REMARKS = YES` 時，Xcode 會在建置日誌中回報編譯快取的命中與未命中。

## 何時不值得使用{#when-it-isnt-worth-it}

建置快取會增加基礎設施、安全邊界，以及新一類的錯誤。它並非總是合適的工具：

- **小型或快速的建置。** 若乾淨建置只需一分鐘，遠端快取節省的效果有限，且網路往返可能使其更慢。
- **設計上就會未命中的建置。** 若大多數建置都會變更靠近圖形根節點的輸入，在修正此問題前，快取無法提供幫助。請先修正失效機制；快取僅能跳過輸入相符的工作。
- **持久的建置機器。** 在同一分支的不同工作之間保留建置目錄的 CI 機器，已能獲得增量建置。當機器為暫時性、存在許多分支，或開發者與 CI 應重複使用彼此的工作時，共用快取才能發揮幫助。
- **尚無法修正的非封閉建置。** 偶爾回傳錯誤輸出的快取，所消耗的信任超過其節省的時間。請先確保您快取的步驟具備可重現性，或讓有問題的步驟不使用快取（例如使用 Bazel 的 `no-remote-cache` 標籤）。
- **緩慢或遙遠的網路。** 若快取距離建置執行處遙遠，請在向所有人推廣前先測量傳輸時間。

## 使用 Tuist 進行建置快取{#build-caching-with-tuist}

[Tuist](https://tuist.dev)提供可插入各建置系統自身快取機制的遠端快取，讓開發者機器、CI 與編碼代理程式能夠重複使用彼此的輸出，並記錄命中、未命中與傳輸時間，以便您衡量效果：

- <.localized_link href="/guides/features/cache/xcode-cache">Xcode 快取</.localized_link>將 Xcode 的編譯快取連接至共用的遠端快取，適用於 Xcode 26 或更新版本的任何 Xcode 專案。
- <.localized_link href="/guides/features/cache/module-cache">模組快取</.localized_link>在使用 Tuist 產生的專案中，以預先建置的二進位檔取代整個模組。
- <.localized_link href="/guides/features/cache/gradle-cache">Gradle 快取</.localized_link>與<.localized_link href="/guides/features/cache/bazel-cache">Bazel 快取</.localized_link>分別作為 Gradle 的遠端建置快取與 Bazel 的 Remote Execution API 快取。
- <.localized_link href="/guides/features/cache">快取</.localized_link>列出所有支援的建置系統，包括 Elixir 與 Struo。
- [緩慢建置](https://tuist.dev/solutions/slow-builds)是一份實用指南，協助您在選擇快取前找出值得移除的工作。
- [建置系統的物理學](https://tuist.dev/blog/2026/08/25/the-physics-of-build-systems)與[Kura](https://tuist.dev/blog/2026/09/14/kura)透過 Tuist 快取的測量數據，說明模組快取、Xcode 編譯快取、Bazel 與 Gradle 之間的構件大小與請求量差異。
