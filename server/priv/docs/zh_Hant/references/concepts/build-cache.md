# 什麼是建置快取？ {#what-is-a-build-cache}

建置快取會將個別建置步驟的輸出（例如編譯後的物件檔、模組、函式庫或測試結果）儲存起來，並根據產生這些輸出所需的一切因素（原始碼檔案、編譯器旗標、相依性、環境與工具鏈版本）計算出一個金鑰。當後續建置需要某個步驟，且其輸入產生的金鑰相同時，建置系統會直接採用儲存的輸出，而非再次執行該步驟。**本機建置快取**存在於單一機器上，可加速該機器後續的建置。**遠端建置快取**則是一個共享伺服器，可供多台機器讀寫，讓 CI 工作、團隊成員或程式碼代理程式能夠重複使用他人已建置完成的輸出。

## 建置快取、增量建置與 CI 快取 {#build-cache-incremental-build-and-ci-cache}

有三種概念常被統稱為「快取」，但它們的行為各不相同：

- **增量建置**會重複使用已存在於你本機建置目錄中的輸出，並僅重新建置自上次建置以來有變更的部分。它們通常依賴檔案時間戳記或與建置產物一起保存的相依圖。切換分支、移動檢出目錄，或從全新機器開始，都會導致這些狀態遺失。
- **建置快取**是根據輸入的內容來查找輸出，而非依據同一目錄中最後建置了什麼。這使得輸出可以在不同分支、檢出目錄和機器之間重複使用，只要輸入相符即可。
- **CI 目錄快取**（例如 GitHub Actions 上的 `actions/cache`）會在工作結束時儲存一個目錄，並在下一個工作開始時將其還原，使用的金鑰由你選擇（例如鎖定檔的雜湊值）。這是一種檔案傳輸，並非建置快取：建置系統仍會決定要重新建置哪些部分，而還原的目錄可能部分或完全過時。

相依性快取（例如下載的套件或 Gradle 或 Swift 套件快取）則又是另一回事：它們節省的是網路抓取的時間，而非編譯時間。

## 建置快取的運作方式 {#how-a-build-cache-works}

支援快取的建置系統會將建置拆分為多個步驟（Bazel 稱之為 actions，Gradle 稱之為 tasks），並對每個步驟執行相同的操作：

1. **計算快取金鑰。** 建置系統會對所有可能影響輸出的輸入進行雜湊處理：輸入檔案的內容、命令列或任務設定、相關環境變數以及工具鏈。
2. **查找金鑰。** 它會先檢查本機快取，如果已設定，也會檢查遠端快取。
3. **命中或未命中。** 若命中，它會下載或複製儲存的輸出並跳過該步驟。若未命中，它會執行該步驟，並在允許的情況下將輸出以上述金鑰上傳。

大多數快取將輸出儲存在 **內容定址儲存區** (CAS) 中，其中每個資料區塊都以其自身內容的雜湊值儲存，另有一個獨立的索引將快取金鑰對應到其產生的輸出。相同的檔案只會儲存一次，用戶端可以驗證其下載的內容。

此模型有一個嚴格要求：金鑰必須包含所有會改變輸出的輸入。如果某個步驟讀取了建置系統不知道的輸入（例如未宣告的檔案、環境變數、當前時間或機器上安裝的工具），快取可能會傳回與當前輸入不符的輸出。建置系統將僅依賴已宣告輸入的步驟稱為 **封閉性 (hermetic)**。相反的問題更常見且危險性較低：金鑰包含了無關緊要的資訊（例如絕對路徑或時間戳記），導致每台機器產生的金鑰都不同，因此快取永遠無法命中。

## 各建置系統的快取運作方式 {#how-it-works-per-build-system}

### Gradle 建置快取 {#gradle}

[Gradle 建置快取](https://docs.gradle.org/current/userguide/build_cache.html) 會儲存可快取任務的輸出（例如 Java 和 Kotlin 編譯及測試執行），並根據任務類型、實作、輸入屬性和標準化後的輸入檔案作為金鑰。預設情況下它是關閉的。你可以在 `gradle.properties` 中使用 `org.gradle.caching=true` 啟用，或在單一建置中使用 `--build-cache` 啟用。

- **本機。** 內建的本機快取是 Gradle 使用者主目錄中的一個目錄（預設為 `~/.gradle`）。一旦啟用建置快取，它就會生效，且 Gradle 會定期移除近期未使用的項目。
- **遠端。** 遠端快取在 `settings.gradle(.kts)` 中設定，例如使用 `HttpBuildCache`。當本機未命中時，Gradle 會從遠端快取下載輸出並在本機儲存以供下次使用。預設情況下，遠端快取不接受上傳；常見的設定是讓 CI 推送（在 CI 中執行時 `isPush = true`），而開發者機器僅能讀取。

Gradle 將從快取還原的任務回報為 `FROM-CACHE`，這與 `UP-TO-DATE` 不同：up-to-date 表示 Gradle 的增量建置發現任務的輸出已就緒，無需查詢快取。設定快取是第三個獨立的功能，它快取的是設定階段的結果，而非任務輸出。

### Bazel 遠端快取 {#bazel}

Bazel 會快取每個 action。它的 action 快取將 action 的金鑰（其命令列、環境和輸入檔案的摘要）對應到 action 的輸出，而輸出本身則儲存在內容定址儲存區中。

- **本機。** Bazel 將其 action 快取和建置輸出保留在其輸出基礎目錄中，這讓你在單一工作區中能獲得快速的增量建置。`--disk_cache=<path>` 會新增一個磁碟快取，可在同一台機器上的不同工作區和分支之間共享。
- **遠端。** `--remote_cache=grpcs://…`（或 `https://…`）將 Bazel 指向一個實作了 [Remote Execution API](https://github.com/bazelbuild/remote-apis) 或純 HTTP 快取的遠端快取。`--remote_upload_local_results=false` 使機器成為唯讀模式，這是許多團隊防止開發者機器寫入共享快取的方式。`--remote_download_minimal` 或 `--remote_download_toplevel`（「build without the bytes」）可避免下載本機建置永遠不需要的中間輸出。

Bazel 也會快取測試結果：輸入未變更的測試會被回報為 `(cached) PASSED` 而不實際執行。遠端快取不同於遠端執行，後者會在遠端機器上執行 actions；快取僅儲存結果。

### 什麼是 Xcode 快取？ {#xcode}

Xcode 使用了數種容易混淆的快取和目錄。影響建置時間的主要有以下幾種：

- **DerivedData**（`~/Library/Developer/Xcode/DerivedData/<Project>-<hash>/`）包含每個專案的建置產物、中間檔案、索引、日誌以及已解析的 Swift 套件。這是增量建置所重複使用的狀態。刪除它是安全的，但該專案的下一次建置將成為完整重建，且索引與套件解析會再次執行。
- **Clang 模組快取**（`~/Library/Developer/Xcode/DerivedData/ModuleCache.noindex/`）包含用於匯入 C 和 Objective-C 模組及 SDK 框架的預編譯 Clang 模組（`.pcm` 檔案），這些模組在專案間共享。若啟用明確建構的模組，Xcode 會將模組作為一般建置任務進行建構，並將其保留在每個專案的中間檔案中。刪除它是安全的；模組會在需要時重新建構。
- **編譯快取**（Xcode 26 及更高版本，預設位於 DerivedData 內的 `CompilationCache.noindex`，可透過 `COMPILATION_CACHE_CAS_PATH` 設定）在 `COMPILATION_CACHE_ENABLE_CACHING = YES` 時，儲存 Swift、C 和 Objective-C 的內容定址編譯輸出。刪除它是安全的；原本可以重放的編譯將再次執行。
- **Swift Package Manager 快取**（`~/Library/Caches/org.swift.swiftpm/`）包含下載的套件儲存庫和 manifest，這些資料在專案間共享。刪除它是安全的；套件會再次抓取。

`~/Library/Developer` 下的其他大型目錄並非建置快取，但在清理磁碟空間時經常出現：`Xcode/Archives` 包含歸檔的 App 建置及其除錯符號（保留你可能需要用於符號化崩潰記錄的符號），`Xcode/iOS DeviceSupport` 包含已連接裝置作業系統版本的符號，而 `CoreSimulator/Devices` 則包含模擬器及其資料（`xcrun simctl delete unavailable` 會移除已不再安裝的執行環境對應的模擬器）。

DerivedData 是 Xcode 的增量建置狀態，而非內容定址快取：它與專案在磁碟上的位置以及檔案時間戳記綁定。從 CI 快取還原 DerivedData 到不同路徑，或在全新檢出後因所有檔案修改時間變更而還原，通常仍會導致完整重建。

Xcode 26 引入的 **編譯快取**，即本頁面所指 Xcode 的建置快取。它根據輸入內容儲存編譯結果，並在命中時重放結果，因此輸出能在切換分支或清理建置產物後依然保留。它快取的是編譯，而非每個建置步驟：連結、資源處理和腳本階段仍會執行。預設情況下，儲存區位於單一機器本機並存放在 DerivedData 內，因此刪除整個 DerivedData 會將其移除；僅刪除專案的建置產物則會保留它。Xcode 也可以透過外掛程式將編譯快取連線至遠端快取服務（`COMPILATION_CACHE_ENABLE_PLUGIN` 和 `COMPILATION_CACHE_REMOTE_SERVICE_PATH`），從而將其轉變為共享的遠端快取。

在編譯快取出現之前，Xcode 專案主要透過 **二進位快取** 整個模組來跨機器重複使用工作：將相依性建構為預先建構的框架或 XCFrameworks，並連結這些檔案而非編譯原始碼。這種方式作用於模組層級而非編譯層級，並改變了專案的建構方式。

## 延遲、Blob 大小與 Blob 數量 {#latency-blob-size-and-blob-count}

遠端快取命中並非免費。取得輸出需要為每個必須等待前一個請求完成的請求付出固定延遲，加上傳輸其位元組所需的時間：

**time ≈ R × L + S / B**

其中 *R* 是無法重疊的往返次數，*L* 是前往快取的往返延遲，*S* 是傳輸的位元組數，而 *B* 是頻寬。哪一項佔主導地位，取決於建置系統如何將工作切割為 blob：

- **少量大型 blob 受限於頻寬。** 儲存粗粒度輸出的快取（例如 Gradle 任務的打包輸出或二進位模組快取中的預先建構框架）發出的請求較少，但每個請求傳輸數 MB 資料。在 100 Mbit/s 下，一組 200 MB 的輸出約需 16 秒，而在 1 Gbit/s 下則不到 2 秒，此時幾毫秒的額外延遲幾乎無關緊要。
- **大量小型 blob 受限於延遲。** 細粒度快取（例如 Bazel 的每 action 快取和 Xcode 的編譯快取）會發出數千個請求以獲取幾 KB 大小的 blob，其中許多請求僅用於查詢金鑰是否存在。若有 2,000 次查找，同時進行 8 次，且延遲為 40 ms，則建置僅在往返上就會等待約 10 秒，無論 blob 多麼小。若延遲為 2 ms，同樣的查找約需半秒。增加頻寬在此無濟於事；縮短與快取的距離才有幫助。
- **未命中也會產生往返成本。** 每次未命中的查找都會增加延遲，卻無法節省任何工作。命中率低且距離遙遠的快取，可能使建置速度比完全沒有遠端快取更慢。
- **數量會放大兩者影響。** Blob 數量隨專案結構增長：由許多小型模組或目標組成的圖形，會產生比少數大型模組更多、更小的輸出。拆分專案能改善平行處理和失效機制，但也會使建置對快取延遲更為敏感。

只有當取得輸出比重新計算更快時，命中才具有價值，而這種比較會隨距離變化。在本機耗時 50 ms 的編譯，對於同一網路上的快取而言是良好的命中，但對於另一大洲的快取則是糟糕的命中。這就是為什麼遠端快取的調整槓桿主要在於延遲和請求數量，而非原始頻寬：

- **將快取放置在靠近建置執行的位置**，與 CI runner 位於相同區域或網路，並盡可能靠近開發者。
- **重疊請求。** Bazel 的 Remote Execution API 會批次處理存在性檢查（`FindMissingBlobs`）和小型讀取，而 `--remote_max_connections` 則限制併發數。Xcode 的 `COMPILATION_CACHE_ENABLE_DETACHED_KEY_QUERIES` 會在其餘建置過程旁執行編譯快取查找，而非佔用其執行通道。HTTP/2 可在單一連線之上多工處理許多請求。
- **減少下載量。** Bazel 的 `--remote_download_minimal` 會跳過中間輸出，而本機快取層（例如 Bazel 的 `--disk_cache` 或 Gradle 的本機建置快取）可在無需網路請求的情況下提供重複命中。
- **壓縮大型 blob。** 當快取支援時，Bazel 的 `--remote_cache_compression` 會使用 zstd，這有助於受限於頻寬的傳輸，但對受限於延遲的傳輸幫助不大。

## 常見陷阱 {#common-pitfalls}

- **未宣告的輸入。** 某個步驟讀取了不屬於其金鑰一部分的檔案、環境變數或工具。快取隨後可能回傳由不同輸入建置的輸出。在 Gradle 中，請宣告自訂任務的所有輸入；在 Bazel 中，請保持動作隔離，並考慮使用 `--incompatible_strict_action_env`，以免主機的 `PATH` 滲漏進來。
- **機器專屬的金鑰。** 嵌入於輸入或輸出中的絕對路徑、使用者名稱和建置時間戳記，會導致金鑰在不同機器間產生差異，使遠端快取永遠無法命中。Gradle 的路徑敏感度設定、Bazel 的相對執行路徑，以及 Xcode 中的 Clang 與 Swift 前綴對應設定，皆旨在消除這些差異。
- **圖形根節點附近的不穩定輸入。** 將建置編號、提交雜湊或日期印入所有模組相依的模組中，會在每次建置時使該模組之上的所有內容失效。請盡可能延後注入不穩定值，理想情況下僅注入至發行版建置。
- **工具鏈不相符。** 不同的編譯器、JDK 或 Xcode 版本會產生不同的金鑰。這是正確的行為，但混用版本的機器群組實際上會分割快取。
- **受污染或不受信任的寫入。** 擁有未提交變更或非隔離設定的開發者機器，可能會上傳讓其他人重複使用的輸出。許多團隊僅允許受信分支上的 CI 寫入遠端快取，並將其他所有機器設為唯讀。不受信任的拉取請求建置不應寫入受信建置所讀取的快取。
- **忽略傳輸成本。** 執行耗時 50 毫秒的步驟，從遙遠的快取取得輸出可能耗時更長。請參閱[延遲、blob 大小與 blob 數量](#latency-blob-size-and-blob-count)。
- **隱藏的測試執行。** 當測試具有決定性時，快取測試結果是正確的作法，但這也意味著曾經通過的不穩定測試會在不執行的情況下持續顯示通過。請參閱<.localized_link href="/references/concepts/flaky-test">什麼是不穩定測試？</.localized_link>。

## 如何衡量建置快取 {#how-to-measure-a-build-cache}

快取的價值在於端到端節省的時間，而非僅看命中率：

- **按工作量加權的命中率。** 統計每個步驟的命中與未命中次數，但應根據每個步驟的執行時間進行加權。在低成本步驟上達到 95% 的命中率，其節省效果可能低於在最慢編譯步驟上達到 50% 的命中率。
- **冷啟動、暖機與典型建置。** 比較空快取時的建置、完全暖機快取時的建置，以及人們實際執行的建置（例如小幅變更後拉取請求上的 CI）。最後一項才是關鍵數據。
- **花在快取本身的時間。** 測量請求數量、延遲、位元組數，以及下載和上傳所花費的時間。如果大部分時間都在等待許多小型請求，則縮短快取距離比增加頻寬更有幫助；如果是在移動少數大型 blob，則頻寬和壓縮更為重要。
- **未命中的原因。** 比較兩台機器上相同步驟的快取金鑰。Gradle 可使用 `-Dorg.gradle.caching.debug=true` 列印每個金鑰背後的輸入，Bazel 可寫入執行日誌（`--execution_log_compact_file`）供您在兩次建置間進行差異比較，而當 `COMPILATION_CACHE_ENABLE_DIAGNOSTIC_REMARKS = YES` 時，Xcode 會在建置日誌中回報編譯快取的命中與未命中。

## 何時不值得使用 {#when-it-isnt-worth-it}

建置快取會增加基礎設施、安全邊界以及新一類的錯誤。它並非總是正確的工具：

- **小型或快速的建置。** 如果乾淨建置僅需一分鐘，遠端快取節省的效果有限，且網路往返可能使其更慢。
- **設計上就會未命中的建置。** 如果大多數建置都會變更圖形根節點附近的輸入，在修正此問題之前，快取無法提供幫助。請先修正失效機制；快取僅能跳過輸入相符的工作。
- **持久的建置機器。** 在同一分支的不同作業之間保留建置目錄的 CI 機器，已經能獲得增量建置。當機器是暫存的、存在許多分支，或者開發者與 CI 應該重複使用彼此的工作時，共用快取才能發揮作用。
- **尚無法修正的非隔離建置。** 偶爾回傳錯誤輸出的快取，所消耗的信任成本高於其節省的時間。請先確保您快取的步驟具備可重现性，或讓有問題的步驟不使用快取（例如使用 Bazel 的 `no-remote-cache` 標籤）。
- **緩慢或遙遠的網路。** 如果快取距離建置執行位置遙遠，請在向所有人推廣前先測量傳輸時間。

## 使用 Tuist 進行建置快取 {#build-caching-with-tuist}

[Tuist](https://tuist.dev) 提供可插入各建置系統自身快取機制的遠端快取，讓開發者機器、CI 和編碼代理程式能夠重複使用彼此的輸出，並記錄命中、未命中和傳輸時間，以便您衡量效果：

- <.localized_link href="/guides/features/cache/xcode-cache">Xcode 快取</.localized_link> 將 Xcode 的編譯快取連接至共用的遠端快取，適用於 Xcode 26 或更新版本的任何 Xcode 專案。
- <.localized_link href="/guides/features/cache/module-cache">模組快取</.localized_link> 在使用 Tuist 產生的專案中，以預建二進位檔取代整個模組。
- <.localized_link href="/guides/features/cache/gradle-cache">Gradle 快取</.localized_link> 和 <.localized_link href="/guides/features/cache/bazel-cache">Bazel 快取</.localized_link> 分別作為 Gradle 的遠端建置快取和 Bazel 的 Remote Execution API 快取。
- <.localized_link href="/guides/features/cache">快取</.localized_link> 列出所有支援的建置系統，包括 Elixir 和 Once。
- [緩慢的建置](https://tuist.dev/solutions/slow-builds) 是一份實用指南，協助您在選擇快取之前找出值得移除的工作。
- [建置系統的物理學](https://tuist.dev/blog/2026/08/25/the-physics-of-build-systems) 和 [Kura](https://tuist.dev/blog/2026/09/14/kura) 透過 Tuist 快取的測量數據，解釋模組快取、Xcode 編譯快取、Bazel 和 Gradle 之間的構件大小與請求量差異。
