# 什麼是不穩定測試？ {#what-is-a-flaky-test}

不穩定測試是指在針對相同程式碼執行時，有時通過、有時失敗的自動化測試，且被測程式碼或測試本身並未發生任何變更。其結果取決於測試無法控制的變數，例如時間點、測試執行的順序、其他測試遺留的狀態、執行測試的機器，或是透過網路呼叫的服務。因此，不穩定的失敗無法提供關於所測試變更的任何可靠資訊，這正是造成不穩定測試成本高昂的原因：在任何人能信任結果之前，必須調查或重試每一個紅色（失敗）結果。

不穩定性在任何規模下都很常見。Google 報告指出，約有 1.5% 的測試執行產生了不穩定的結果，且將近 16% 的測試表現出某種程度的不穩定性（[Flaky Tests at Google and How We Mitigate Them](https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html)，2016 年）。

## 不穩定測試如何呈現 {#how-flaky-tests-show-up}

只有當測試針對相同輸入產生兩種不同結果時，才能確定它是不穩定的。實際上，這些證據來自以下三個來源之一：

- **單一執行中的重試。** 測試失敗後，執行器（runner）對其進行重試，而重試通過了。這是成本最低的訊號，且大多數測試執行器都能產生此訊號。
- **相同提交的執行結果不一致。** 針對相同提交和設定的兩次 CI 執行，回報了不同的測試結果，例如拉取請求（pull request）上的一次執行，以及有人點擊重試後的再次執行。
- **刻意重複執行。** 故意連續多次執行測試，以觀察是否會失敗。團隊藉此確認疑似的不穩定測試，或在合併新測試前檢查其穩定性。

只有當所有關鍵因素都相同時，結果才算作不穩定性的證據：提交、建置設定、裝置或模擬器、作業系統版本以及工具鏈。若在 iOS 17 上失敗而在 iOS 18 上通過的測試，可能在其中一個版本中存在真實且具決定性的錯誤。

## 各建置系統如何偵測不穩定測試 {#how-it-works-per-build-system}

每種工具鏈都可以重試和重複執行測試，但它們記錄和回報結果的方式各不相同。

### Xcode {#xcode}

`xcodebuild` 和測試計畫支援測試重複執行。`-retry-tests-on-failure` 會重新執行失敗的測試，`-test-iterations <n>` 設定允許的嘗試次數，而 `-run-tests-until-failure` 則重複執行測試直到失敗為止，這對於復現疑似的不穩定測試很有用。測試計畫公開了與測試重複模式相同的選項，並提供隨機順序執行測試的選項，從而揭露隱藏的順序相依性。

每次嘗試都會儲存在 `.xcresult` 套件中，因此失敗後重試通過的測試可在其中查看。Xcode 不會保留跨執行的歷史記錄，因此要偵測從未在同一執行中重試的不穩定測試，需要比較同一提交在不同執行中的結果套件。

### Gradle {#gradle}

Gradle 的 `Test` 任務本身不會重試失敗的測試。[Test Retry plugin](https://github.com/gradle/test-retry-gradle-plugin) (`org.gradle.test-retry`) 為 `Test` 任務新增 `retry` 區塊，並提供如 `maxRetries` 和 `failOnPassedAfterRetry` 等選項。失敗後重試通過的測試會在測試報告和 JUnit XML 中顯示兩次嘗試。測試框架會加入各自的重複執行工具，例如 JUnit 5 的 `@RepeatedTest`。

Gradle 的建置快取也可能掩蓋不穩定性：具有未變更輸入的可快取 `Test` 任務會從快取還原而非實際執行，導致曾經通過的測試在未經執行的情況下持續顯示通過。當你要測量不穩定性時，請使用 `--rerun-tasks` 強制執行測試，或在停用建置快取的情況下執行 `Test` 任務。

### Bazel {#bazel}

Bazel 內建支援。將測試目標標記為 `flaky = True` 會讓 Bazel 最多執行三次，僅在所有嘗試都失敗時才判定為失敗。`--flaky_test_attempts` 旗標可在不變更目標的情況下設定嘗試次數，當測試在失敗嘗試後通過時，目標結果會回報為 `FLAKY`。若要刻意測量不穩定性，`--runs_per_test=<n>` 會多次執行測試，而 `--runs_per_test_detects_flakes` 會在至少一次執行通過且一次執行失敗時，將分片回報為 `FLAKY`。

Bazel 快取測試結果的方式與快取建置輸出相同。使用相同輸入通過的測試會回報為 `(cached) PASSED` 而不再次執行，無論是本機還是從遠端快取。當你需要全新執行時，請使用 `--cache_test_results=no`（或 `--nocache_test_results`）。Bazel 文件也不建議依賴 `flaky = True`，因為它會永久隱藏其重試的失敗。

### 其他測試執行器 {#other-test-runners}

這種模式幾乎無處不在：pytest 擁有 `pytest-rerunfailures` 外掛，Jest 擁有 `jest.retryTimes()`，而 Elixir 的 ExUnit 擁有 `mix test --repeat-until-failure` 並列印其所使用的隨機種子，以便使用 `--seed` 重現依賴順序的失敗。

## 不穩定測試的常見原因 {#common-causes}

一項針對開源專案中不穩定測試的實證研究（[Luo et al., FSE 2014](https://doi.org/10.1145/2635868.2635920)）發現，非同步等待、併發性以及測試順序相依性是最常見的根本原因。下列清單涵蓋了這些原因以及團隊最常遇到的其他原因。

- **非同步等待與固定休眠。** 測試等待固定的時間讓工作完成，例如 `sleep(1)` 或具有短超時的預期，但工作有時會花費更長時間，特別是在負載較高的 CI 機器上。應直接等待條件本身達成，並設定寬鬆的上限。
- **併發性。** 兩個執行緒或任務在共享資料上競爭，或者測試在背景作業完成前就進行斷言。這些失敗通常取決於 CPU 核心數和負載，因此它們出現在 CI 環境中，而不會在快速的筆記型電腦上出現。
- **測試順序相依性與共享狀態。** 測試依賴另一個測試建立或忘記清理的狀態：單例物件、資料庫列、磁碟上的檔案、`UserDefaults`、環境變數或模擬的全域變數。以隨機順序或平行方式執行測試會揭露此問題。
- **時間與日期。** 使用真實時鐘的測試會在午夜、月底、跨越夏令時變更或在其他時區時失敗。改為注入時鐘物件。
- **未設定種子的隨機性與無序集合。** 沒有記錄種子的隨機資料，或依賴雜湊映射或集合迭代順序的斷言。
- **網路與外部服務。** 當這些服務緩慢或無法使用時，對真實 API、套件註冊表或共享暫存環境的呼叫會失敗。在邊界處將它們替換為模擬物件，並保留少量明確的整合測試。
- **資源壓力與環境狀態。** 機器緩慢或過載、未重設的模擬器或模擬環境、磁碟已滿，或另一個工作已使用的通訊埠。當許多不相關的測試同時失敗時，應先懷疑環境問題而非測試本身。
- **UI 測試。** 端到端和 UI 測試將上述大多數原因與動畫、渲染時機以及系統對話框結合在一起，因此它們比單元測試更常出現不穩定情況。

在變更後持續失敗的測試並非不穩定；這是回歸錯誤。「不穩定」標籤應保留給那些在同一份程式碼上產生兩種結果的測試。

## 修復、重試與隔離 {#fixing-retrying-and-quarantining}

團隊通常會結合三種應對方式，將它們區分開來會有所幫助：

- **修復**根本原因。這是唯一能恢復測試價值的應對方式。記錄的嘗試次數、失敗訊息以及每次失敗執行的條件，都是指向原因的證據。
- **重試**以維持流程運作。重試是有用的偵測信號，但全面性的重試會掩蓋問題，並為每次失敗的執行增加機器時間。通過的重試仍應記錄為不穩定結果，而非靜默丟棄。
- **隔離**已知不穩定的測試，使其在修復期間不再阻礙合併。被隔離的測試要麼繼續執行但忽略其失敗（靜音），這會持續產生證據；要麼完全不執行（跳過），這會移除其涵蓋範圍。隔離需要指定負責人與退出條件，否則被隔離的測試會累積，導致涵蓋範圍悄然縮減。

## 如何衡量不穩定性 {#how-to-measure-flakiness}

追蹤每個測試的不穩定性，而不僅是每個流程：

- **不穩定率。** 產生不穩定結果的測試執行比例：失敗後接著通過的重試，或與同一提交和設定的另一次執行結果不一致。
- **影響。** 測試阻礙或延緩了多少流程、拉取請求或合併佇列項目，以及其重試消耗了多少機器時間。一個不穩定率低但在每個流程中都運行的測試，其成本可能高於一個極不穩定但很少運行的測試。
- **趨勢。** 新引入的不穩定測試是否比舊測試的修復速度更快。在合併前多次重複執行新的或已變更的測試，可以從源頭捕捉許多不穩定問題。

確認測試穩定所需的執行次數比直覺認為的更多。如果測試在每次執行中失敗的機率為 *p*，那麼在 *n* 次執行中至少看到一次失敗的機率為 1 − (1 − p)ⁿ。對於失敗率為 1% 的測試，10 次執行僅有大約 10% 的機率捕捉到它，而需要大約 300 次執行才能以 95% 的信心水準捕捉到它。少數幾次成功的重試是修復有效的微弱證據。

## 何時不值得投入 {#when-it-isnt-worth-it}

並非每個不穩定測試都值得調查，也並非每個團隊都需要不穩定測試工具：

- **低價值測試。** 如果不穩定測試重複了其他測試已提供的涵蓋範圍，刪除它可能是正確的修復方式。無人信任的測試反正也不提供涵蓋範圍。
- **基礎設施問題。** 當失敗集中在單一機器、執行器映像檔或特定時段時，修復環境比逐一修復測試更划算。
- **小型、快速的測試套件。** 對於擁有快速測試套件且只有一個已知不穩定測試的小型團隊，一份共享筆記和本週內的修復勝過追蹤系統。當測試套件規模、貢獻者數量或流程數量使得無人能記住哪些失敗是雜訊時，專用的偵測與隔離措施才會帶來回報。
- **關鍵路徑。** 對於保護付款、資料完整性或安全性的測試，隔離是錯誤的工具。這些測試應持續阻礙直到修復完成，即使這會造成不便。
