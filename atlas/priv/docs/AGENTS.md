# Atlas documentation source

These English Markdown pages are public at `/docs`. They describe Atlas for people evaluating or operating their own organizational workspace.

- The MCPs guide covers upstream tool servers with per-user OAuth or encrypted shared bearer API keys; shared keys give all permitted callers the same upstream access. Keep AI account setup out of that guide.
- The standalone `ai-accounts` guide, titled "Connect Claude or ChatGPT", describes web and native iOS/Android setup and connection management using the UI names "AI accounts" and "Connect account". Keep it short and task-oriented, with the sidebar label "AI accounts". Orbit uses the acting person's connected ChatGPT account, then Claude, then the explicit workspace Orbit fallback; disclose provider sharing on fallback and never imply that another participant's credentials can be used. The `ai-account-tools` reference is titled "AI accounts" under References → MCP and documents owner-scoped MCP tools and credential-entry privacy tradeoffs; name reference pages after their domain rather than appending "tools". Group MCP references by domain, with one page per domain rather than one combined catalog; administrator-only ChatGPT client provisioning belongs in self-hosting. Distinguish personal accounts from tool servers and global inference. Never include real keys in examples.
- Publish the overview, AI accounts guide, MCPs guide, Automation guide, AI account and Automation MCP references, and self-hosting guide. Other draft guides remain under `plans/atlas-documentation-drafts/` until their implementation and validation are ready.
- `automation` is the web/native workflow guide, with a runnable task plan and explicit operation/configuration/workflow version distinctions. `automation-tools` is the domain MCP/API reference. Keep the sample plan covered by compilation/reference tests and keep the reference aligned with `Atlas.Automations.Interfaces`. Document exact approvals, current domain grants, pinned triggers, uncertain-admission reconciliation, Linux-only JavaScript, and the absence of background push rather than implying unsupported capabilities.
- Keep installation instructions consistent with the implemented configuration and release commands. Clearly distinguish implemented behavior from planned self-hosting work.
- Write guides around the reader's sequence of decisions and actions. Explain why a setting or command is needed where the reader uses it, and keep optional services separate from the initial installation.
- Link named tools and services to their official documentation when introducing them in a section, so readers can follow unfamiliar terms.
- Register a new page in `AtlasWeb.DocsHTML` alongside its title, category, sidebar section, and description. Guides and References have separate sidebars selected from the header, with the same selector in the mobile menu. The overview belongs to Guides. A page's short `sidebar_title` can differ from its descriptive article title. Regenerate social preview images with `mix atlas.docs.images` after changing page titles or descriptions. The module tracks source files and compiles sanitized markup into the release; do not read the source from disk on each request.
- Use unique, plain-text second-level headings for the table of contents. Their identifiers are lowercase words separated by hyphens. Link to other documentation pages using `/docs/...` paths.
- Keep public content free of private credentials, customer examples, and internal operational destinations. Explain provider configuration using organizational examples.
- Verify anonymous access, heading targets, mobile navigation, and theme rendering when changing structure. Documentation has a separate Noora bundle under `assets/css/docs/` and `assets/js/docs.js`.
