# Orbit

Agentic threads between people and the Atlas assistant. The thread is the agentic session: human messages, tool cards, assistant replies and notices form one ordered log (`orbit_messages`). Native clients use the bearer routes and channels in [the controller contract](../../atlas_web/controllers/AGENTS.md#native-orbit); there is no web UI or MCP surface yet. MCP exposure is deferred deliberately: an external client reading thread history is another audience the ratchet would have to cover.

## Naming and upgrades

Orbit is the feature/context (`Atlas.Orbit`), Thread is the persistent entity (`Atlas.Orbit.Thread`), and Run is one durable assistant execution. Messages, participants, tool calls and result cards retain their distinct meanings. The native surface uses `/api/native/orbit/threads`, `assistant`/`threads`/`thread` payload keys, `orbit:thread:<uuid>`/`orbit:me` channels and the `orbit_session` bridge. The inference role, Oban queue and application configuration use `orbit`; the optional assistant-name setting is `ATLAS_ORBIT_AGENT_NAME`.

The original draft migration remains historical. `RenameConversationsToOrbit` reversibly renames its tables, foreign-key columns, constraints, indexes and inference binding, and transfers role tokens, Oban worker/queue names and redacted agent-session labels without changing IDs, token hashes, job arguments, checkpoint bytes or tool results. It requires draining old workers before migration, then deploying the renamed server and clients together; this is not a mixed-version/zero-downtime schema rename. Legacy draft API/channel/bridge names are not parallel aliases. Message content and historical audit events stay unchanged. Unrelated Slack/support conversations are not Orbit threads.

## Model

- Every person has exactly one pinned private thread (`kind: "private"`, unique per owner). Nobody else can read it, including administrators; there is no admin override.
- Shared threads have an owner and participants. Only the owner adds people; members may leave; the owner cannot. `origin` is `manual` or `signal`.
- The assistant is one general agent (`Atlas.Orbit.Agent`) named by `ATLAS_ORBIT_AGENT_NAME` (default "Atlas"). Nothing in prompts, tools or defaults names an organization, person or service.
- `orbit_threads.last_seq` is the revision. Every append or tool status change takes the next sequence under the thread row lock. `position` is a message's stable creation order (served as `seq`); a message's own `seq` column records its last change.

## Access and the sensitivity ratchet

- A participant can read a thread only while holding every scope in `required_scopes`. The audience is the set of current readers. `Access` recomputes it from database state on every call; nothing is cached for a run's lifetime.
- `ToolPolicy` is a default-deny allowlist of read-only MCP tools with the scopes their output requires, covering every area the output draws from (`get_account` embeds contract-document service levels, so it requires `documents:read`). A tool is offered only when every reader holds its scopes, and a successful or failed call adds them to `required_scopes` in the same transaction that stores its result, because error text can disclose domain state too. People added later must already hold them.
- "Read-only" is verified, not assumed: `tool_side_effects_test.exs` executes every allowed tool and asserts, through PostgreSQL's per-transaction statistics, that it writes no rows besides its own audit event. The same check flags `list_gtm_research_topics`, which upserts signal queries, so it is excluded. Semantic search tools still send the query to the operator's embedding provider.
- Excluded from v1, and listed in `ToolPolicy.never/0`: write-on-read tools, credential and login tools, MCP administration, DSNs, license keys, signed or upload URLs, raw SQL, web egress, Apollo search, shared memory (read and write), argument-dependent federated search, viewer-dependent time-off data, upstream MCP proxy tools, and anything that sends email, messages or letters. There are no write tools; future writes must be approval items that never execute automatically.
- Tools run in-process through `Atlas.MCP.Server` as the acting user, so each tool's own checks still apply. The acting user is the author of the triggering message. Signal runs act as the owner, limited by the participant intersection. Tool-call audit events carry the thread and run IDs but omit arguments.

## Runs

- A run is queued in the same transaction as the triggering message and executed by `Workers.RunThread` on the `orbit` queue. One active run per thread is enforced by a partial unique index. Messages addressed during a run start a follow-up when it finishes. Shared threads reply only when `address_agent` is true; private threads always do.
- Runs use the inference profile bound to the `orbit` role through the in-process relay (`Runner.profile_client_opts/2` → `LocalTransport` with an explicit role). There is no fallback to another profile. Without one, messages are kept and a system notice explains that the assistant is not configured.
- **Leases and fencing.** Each start is an attempt identified by `resume_count`. The worker renews a lease (`heartbeat_at`, database clock) every five seconds. The sweeper may transfer a run only after 60 seconds without a renewal. A worker that has not renewed within 45 seconds of starting its last successful renewal fences itself without touching the database, so it is gone before its lease can move. Every write runs through `Runs.with_attempt/3`: lock the thread, then the run (the order used everywhere), and write only while the run is `running` under that attempt. Superseded attempts cannot write tool cards, ratchet, reply, checkpoint or finish their successor.
- **No second worker beside a successor.** The run task is linked to the Oban job process and the Condukt session to the task. Condukt 1.13 runs the model loop in an unlinked `Task.start` that its API cannot reach, so `ModelFence` wraps every model request. It links that loop to the worker, reports it so the worker can kill it, and refuses requests from an attempt that no longer owns the run or was cancelled. `ModelFence.wrap/3` raises if the client options carry no plug, so a run can never be unfenced. This stops further model requests and all state writes; it is not exactly-once inference, since a request already dispatched can still finish and bill.
- **Final-reply fence.** The reply is written only if the attempt still owns the run, the run was not cancelled, and the acting user can still read the thread. Readers are recomputed under the lock from the ratcheted scopes. Adding a participant cancels the active run, because its context was gathered for the previous audience.
- **Deploys and lost replicas.** The job process traps exits. On a deploy shutdown, or when `Atlas.TaskSupervisor` (which stops before Oban) takes the run task down, the attempt is checkpointed. The run returns to `queued` with the next attempt number and a resume job is enqueued. The job is unique on `[run_id, resume]` across incomplete states only, so a lost job can be replaced. The notifier sweep checkpoints runs whose lease expired, re-checking expiry under the locks, and re-enqueues queued runs that have had no pending job for a minute. Duplicate jobs are harmless because only one can move a queued run to running. After three checkpoints the run is `interrupted`. A crash that is not a shutdown fails the run, and the run deadline stops a stuck model call. Every terminal transition starts a follow-up when addressed messages are pending, so queued human work is never dropped.
- **Resumption.** Condukt persists snapshots only at run completion, so `Checkpoints` records a versioned `Condukt.SessionStore.Snapshot` of the exact protocol messages at every `[:condukt, :llm_turn, :start]`. It is encrypted on the run and written only for the owning attempt's session ID. A resumed attempt restores it through the load-only `Checkpoints.Store` and re-issues the model call that was in flight. Tool calls are keyed per run by tool and arguments. A completed call's model result is stored encrypted on its card (`tool_result`) and answered from that record when the resumed attempt makes the same call, after re-authorization, without executing it again or adding a card. Interrupted calls reuse their card and execute again; that is acceptable only because every tool is read-only. Future write tools need approval items and idempotency keys, not replay. The system prompt is always rebuilt from the current audience. Without a usable snapshot the run restarts from the last 40 messages plus every message addressed since its trigger, with this run's completed tool calls. That is a restart with context, not an exact continuation. Terminal statuses clear the snapshot and recorded tool results.

## Privacy boundaries

- Agent session rows for this agent store only an `orbit_run:<id>` label, `%{"redacted" => true}` results and fixed error categories, including for raised exceptions (`Atlas.Agents.Sessions`). Their telemetry events keep only names, status and timings. `/admin/sessions` therefore never shows thread content.
- Tool cards store redacted, bounded renderings (`Rendering`): keys that look like credentials or signed links are replaced, input is capped at 2,000 characters and output at 4,000. The model's copy (24,000 characters) is never stored outside the encrypted checkpoint.
- `Components.for_message/1` is the authoritative, data-only `result_table` v1 projection of a succeeded tool message's existing redacted `tool_output`. It never reads encrypted model results or live business data. The optional API component contains bounded title/columns/rows, one `show_evidence` presentation action and text fallback. No new content is stored; history/access/retention remain those of the source message. Native clients validate and render this projection with a bundled NSH component, never infer cards or run state themselves. No executable UI or remote package is sent. Future business actions require server authorization and persistence, not local callbacks.
- Logs from runs and checkpoints carry fixed categories only, never exception messages or query parameters.
- Viewer leases (`orbit_viewers`) and typing are not audited and are not history. Notifications carry IDs only. The list channel receives an ID-free invalidation and recomputes its own authorized fingerprint.

## Signals

`Orbit.open_for_signal/1` is the generic entry point for monitored signals. It takes an owner, participants, a source type and ID, a title, a bounded summary, and the scopes the summary itself requires. Everyone must hold those scopes; nobody is silently dropped. Repeated signals for the same active source append to the same thread. No monitor calls it yet. Alert-rule and nudge integrations are follow-up work.

## Tests

`rename_migration_test.exs` runs the original and rename migrations in an isolated PostgreSQL schema, seeds legacy history/execution/credentials/jobs, and checks up/down/up preservation plus constraint/index names. It never rolls back or resets the shared test database.

`test/atlas/orbit_test.exs` (context), `orbit/durability_test.exs` (leases, lease transfer, self-fencing, model fence, checkpoints, tool replay, lost-job recovery, final-reply fence), `runs_test.exs`, `tool_policy_test.exs`, `tool_side_effects_test.exs`, `inference_role_test.exs`, `session_privacy_test.exs`, plus `test/atlas_web/controllers/native_orbit_controller_test.exs` and `test/atlas_web/orbit_thread_channel_test.exs`. Tests that bind the singleton Orbit role run synchronously.
