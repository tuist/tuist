# Time off

- `Atlas.TimeOff` owns full-day holiday requests, approvals, location assignments, public holidays, paginated lists, and the bounded team-calendar query. `/people/time-off` defaults to upcoming team leave, the caller's own requests, and upcoming public holidays, each paginated independently with Flop (10 rows by default, capped at 50). Ongoing leave is included; future leave is not bounded by the selected calendar month. The dashboard assumes one shared Berlin calendar (`DE`, `DE-BE`): no location filters, per-person assignment controls, calendar switch link, or public-holiday management link. The old monthly calendar (`?view=calendar`) and administrator settings (`/people/time-off/settings`) remain compatibility routes, not primary navigation. All authenticated users can see team availability and request/change/cancel their own leave through a Noora modal in `AtlasWeb.TimeOffComponents`. Calendar creation, assignments, imports, and holiday edits require `admin:write`, enforced in the context as well as adapters. There are no allowances, accruals, half-days, or Factorial sync.
- The request/edit modal uses Noora's date-range picker (Monday-first, custom ranges only), not two native date fields. Retain Noora's intrinsic trigger-button width; stretching it to full width separates the icon and label because the trigger uses `justify-content: space-between`. Editing preselects the original range; opening a new modal remounts the picker to clear prior drafts. The Atlas `date_only_date_picker` hook adapter opts in with `data-date-only`, sends the selected calendar dates instead of Noora's UTC analytics timestamps, and updates hidden form inputs synchronously before submission. Do not truncate UTC timestamps to dates: that shifts holidays in positive/negative offsets and around DST. Other Noora date pickers retain their existing timestamp behavior. Keep team-calendar grid styles on the namespaced `team-calendar-grid` part directly inside `calendar-scroll`, and page-header styles on the page's direct header. Broad descendant `calendar` or `header` rules leak into the nested Noora picker/modal: the picker calendar must retain Noora's column layout, with its footer below the months rather than in a seven-column page grid.
- Statuses use Noora badges. Active personal requests use a Noora split dropdown (edit / cancel); rejected requests offer edit only, and cancelled requests have no mutation controls. Approval split dropdowns (approve / reject) are rendered only for pending requests belonging to somebody else and only for persisted `time_off_approvals:write` holders. Read-only approval and administrator permissions alone do not reveal those controls. Forged events still go through domain authorization.
- Requests start `pending`. Another user with `time_off_approvals:write` can approve or reject them; there is no manager or reporting hierarchy and no implicit administrator override. Executives receive this permission by default, including through a migration for existing installations. The built-in Member role excludes the approval area. Custom roles can delegate approvals without granting administration. Self-review is forbidden. Review and cancellation lock the request row, accept only their allowed source states, and cannot overwrite each other. Permission checks read current persisted scopes for every decision.
- Only the owner may edit a request, with no administrator override. Pending/approved dates may be changed; rejected requests may be resubmitted, even with unchanged dates; cancelled requests cannot be edited. Changed dates reset status to pending and clear reviewer metadata, while saving unchanged approved dates preserves approval. Edits retain the original location, validate overlap excluding themselves, and lock the user before the booking to serialize against new requests and reviews. Update audits retain the previous dates, status, reviewer, and review timestamp.
- Pending requests remain visible on the calendar with a separate label and dashed marker; only approved requests are confirmed leave. Rejected/cancelled dates do not occupy the calendar or prevent new requests. The request list retains those decisions for the owner and callers with `time_off_approvals:read` (implied by write), never exposing private rejected/cancelled history to ordinary teammates. Read-only approval roles can audit history but cannot make decisions. The bounded calendar query takes the actor for this visibility check; a query without an actor returns active availability only.
- A migration creates Berlin, assigns it to existing unassigned users, and sets it as the database default for new users. The user schema reads this database default back after writes so returned user structs match subsequent loads. Reporting also falls back to Berlin if an explicitly null assignment exists. The schema and context retain explicit location support for future use, but the current dashboard and automatic sync use Berlin only. Locations use ISO country and optional subdivision codes. Definitions are immutable; create another location and reassign users when a region changes. Bookings snapshot the assigned location so reassignment does not rewrite existing leave. Counts are computed from the current configured dates for that snapshot, not stored balances. Saturdays/Sundays are non-working days. A reported range is inclusive, limited to 366 days, and cannot overlap another pending or approved request for that person. User-row locking serializes reports and edits with assignment updates.
- `PublicHolidays` imports a requested year from Nager.Date over Req, accepting only `Public` holidays that are national or match the location subdivision. Country-only calendars exclude regional holidays. Provider coverage varies and is not authoritative for municipal holidays; administrators add those manually. `Atlas.TimeOff.SyncPublicHolidays` refreshes Berlin's current and next year at Oban cron startup (`@reboot`) and daily at 02:00 UTC, with unique in-flight jobs and five retry attempts. User-triggered `sync_public_holidays` requires `admin:write`; worker-triggered sync is internal, actorless, and audited as `worker`. Nager.Date is the maintained provider, not a claim of legal governmental authority. Explicit per-year imports remain available for administrative compatibility. They replace only the requested year's `nager` rows, retain manual rows, and update `synced_years` in one transaction. A failed import preserves previous dates and coverage. Missing import years appear as a warning, not a guaranteed complete day count. Removing imported dates is temporary until reimport.
- Cancellation retains the booking and cancellation timestamp and is permitted for pending or approved requests only. Only the owner can cancel, including through MCP; administrators do not get an implicit override. Audits originate in the context and include actor, interface, resource, dashboard path, decision, and reviewer ID. The team page reconciles persisted state every 30 seconds without discarding form drafts.
- The twelve MCP tools are registered in Atlas's existing authenticated OAuth MCP server at `/mcp`, not a separate unauthenticated service. They cover the same read/request/update/review/cancel/setup capabilities. `sync_public_holidays` refreshes Berlin's current and next year and is discovered/callable only with `admin:write`. Setup tools are in the admin write/discovery group; requesting, owner-only `update_holiday`, paginated `get_time_off_overview`, and the bounded team calendar are authenticated default-group tools. `review_holiday` is discovered and callable only with `time_off_approvals:write`, without requiring admin access. MCP responses must conform to `Atlas.MCP.Serializers.TimeOff` schemas.

- Native iOS/Android employee screens use the bearer-authenticated `/api/me/time-off` list/create and `/api/me/time-off/:id` update/cancel routes. These thin controllers reuse this context and the existing serializers, whitelist date parameters, derive ownership only from the bearer identity, and mark all responses `no-store`. They expose paginated personal history/public holidays, not other employees' history or approval controls. Mutation failures use bounded error codes. The existing MCP tools already cover the same domain capabilities. Mobile clients live in `atlas-native/`; coverage includes `test/atlas_web/controllers/time_off_controller_test.exs`.

## Personal data, retention, and export

- PostgreSQL `users.time_off_location_id` stores the assigned public-holiday calendar (currently Berlin by default), not a verified physical location or address. `time_off_locations` stores location name, country, optional region, and imported years. `time_off_holidays` stores configured holiday names, dates, location references, and manual/provider provenance. There is no address, medical reason, free-text leave reason, or external employee identifier.
- `time_off_bookings` stores user/location references, inclusive dates, pending/approved/rejected/cancelled status, cancellation time, reviewer user reference (`reviewed_by_id`), review timestamp (`reviewed_at`), and creation/update timestamps. Existing pre-approval booked records migrate to approved without inventing a reviewer. Records remain until explicit database retention/deletion; no automatic expiry is configured. Deleting a user cascades their bookings. Calendar definitions and public holidays remain shared organizational data. Audit activity follows the existing Atlas audit retention policy and may outlive the booking.
- For a person's export, select their user location assignment and **all** `time_off_bookings` by `user_id`, including cancelled entries. Join each referenced location plus the user's current location to `time_off_locations` and export the corresponding `time_off_holidays`. Include relevant `audit_activities` by booking target IDs and user assignment events. The calendar query bounds the visible window and applies actor-dependent history visibility, so it is not a complete legal export. Include review metadata, approval/rejection audit activity, and the previous-value metadata from `time_off.updated` events in the export. Neither the paginated overview nor the bounded calendar is a complete export.

## Validation

- Domain coverage: `test/atlas/time_off_test.exs` and `test/atlas/time_off/public_holidays_test.exs`.
- Dashboard coverage: `test/atlas_web/live/time_off_live_test.exs` (range selection, preselection/reset, validation, draft preservation, permissions).
- Date-only hook coverage: `node --test assets/js/hooks/date_only_date_picker.test.mjs` from `atlas/`.
- MCP coverage: the corresponding tests under `test/atlas/mcp/tools/`.
- Local seeds use fictional Atlas users sharing Berlin, with personal and overlapping teammate requests. They normalize only those fictional users' old seed bookings to Berlin and remove the two old manual holiday fixtures; real public holidays arrive through the independent Oban sync. Seeds never fetch holidays or claim full imported coverage.
