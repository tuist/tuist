# Cross-instance notifications

- `Atlas.PubSub.Postgres` implements Phoenix's adapter callbacks and supervises a separate `Postgres.Listener` with one PostgreSQL `LISTEN` connection per application instance. Immutable instance/channel metadata lives in a supervisor-owned ETS record, not a request/session store; publishers and `node_name` never call the potentially blocked socket process. Listener reconnects/restarts retain the adapter's identity, and adapter shutdown removes the metadata.
- Broadcasts use the caller's repository connection; remote delivery occurs only after commit. Regular local delivery follows the publication attempt. Remote query errors/exceptions are logged without payloads or exception details and treated as best-effort failures so they do not suppress local delivery or crash an already-committed mutation. Oversized payloads still return an explicit error and are not delivered locally. Direct broadcasts depend on remote publication, including when targeting the current instance; use local broadcasts for that case.
- Instance IDs are random per adapter startup, not BEAM node names. Self-originated broadcasts are suppressed remotely to avoid duplicate local delivery; direct broadcasts use the target instance ID. Do not require Distributed Erlang or sticky sessions.
- Messages are version-tagged, base64-encoded Erlang terms decoded with `[:safe]`. Unknown versions/shapes, invalid topics/targets, and modules without the dispatcher callback are ignored. Only application code with database credentials may publish on this channel. Keep messages small invalidations (IDs/state flags), never documents, credentials, user payloads, or durable work. The adapter returns an explicit error if the encoded payload exceeds PostgreSQL's 7,999-byte limit.
- `Postgrex.SimpleConnection` reissues LISTEN after reconnect. Notifications missed during disconnection are not replayed. Consumers must read durable PostgreSQL state and reconcile periodically. Account handles, open support threads, and pending POC access requests reload every 30 seconds, repairing missed notifications without treating message contents as authority. Oban is the durable work transport, not PubSub.
- The repository connection details must resolve directly to PostgreSQL or a session pool. Transaction/statement pooling cannot maintain LISTEN subscriptions. This is also required by Oban's PostgreSQL notifier.
- Integration tests start two independent PubSub instances and publish through unboxed repository queries, so commit/rollback and routing are exercised through real PostgreSQL without shared database rows or Erlang clustering.
