# S3-backed alerting implementation plan

Status: design reviewed with Claude, including an adversarial correctness/simplicity review and follow-up; the first native runtime slice is implemented, including native Slack outboxes and live resource hints, but Grafana execution and notification-policy parity are not. See [current functionality](../docs/alerting.md) and the [review decisions](alerting/adversarial-review.md). Named behavior-capture fixtures still gate migration. The goal is to model every current Grafana rule and notification behavior without adding a database, durable local queue, leader election, or stateful MCP sessions. Native query support and operational migration are separate acceptance gates, not consequences of accepting a rule's JSON.

Read `docs/architecture.md` first. This plan expands the alerting section and milestone 7 of `plans/tuist-deployment-plan.md`. Deployment-specific observations belong here, not in operator documentation.

Completeness requires a per-UID migration manifest: original definition, imported definition, source binding, required features, semantic fixtures, delivery targets, and status. Every one of the 115 entries must be accounted for. Nothing may be dropped because it is a recording rule, SQL, a Grafana-managed usage rule, or synthetic monitoring. Inventory scope is this connected organization's provisioned rules; audit datasource-managed rules and any other organizations separately before claiming global completeness.

Acceptance has three distinct levels:

1. **Representable:** import preserves all behavior-relevant settings and rejects unknown constructs with a UID/ref-specific error; every entry has a validated model.
2. **Executable:** each entry has a configured, authorized source and passes semantic fixtures. Retaining a read-only external source is an explicit binding, not native Pulse support.
3. **Migrated:** shadow comparison and notification recovery gates pass; only then may Grafana stop evaluating/notifying it.

Track execution target and approval per UID: `planned-native`, `planned-external-binding`, `shadow`, `migrated`, or explicitly owner-approved `retained-in-grafana` / `retired-with-grafana`. All 115 remain in modeling scope. No rule is automatically retired, retained elsewhere, or excluded by this plan. Seven usage-source rules (five billing-group entries plus cardinality and duplicate-timestamp rules) and two synthetic rules have external producers; their future migration/retirement requires a product decision, not a grammar workaround.

Residency must be tracked PER SELECTOR and computed over expression/recording dependency closures. The current checklist identifies observed sources, not confirmed Pulse ingestion. Native execution is blocked until each selector has a producer, tenant residency, labels, history/freshness and ingestion contract. Preserve `kura:pod_region -> kura:pool_region -> kura:node_region` and `kura:node_pool -> kura:pool_region/node_region`; 29 Cache query nodes consume the recorded outputs. A native recording cannot satisfy an expression still running against external Prometheus. The failed-check synthetic rule joins Loki executions with external Prometheus thresholds/check metadata; that cross-source graph must remain explicit.

## Current notification behavior

- Default receiver `Slack #notifications 2` fans out to Slack `#notifications` and an Atlas Grafana-alert webhook.
- Staging routes match `cluster=tuist-staging` or `env=staging` and use `#notifications-non-prod`.
- `Kura instance has no ready replicas` uses non-production Slack when `cluster!=tuist-production`; production sends both default Slack/webhook and OnCall `Incidents` using a continuing route followed by the incident route.
- Five application rules override routing directly to `Incidents`: discarded build jobs, discarded XCResult jobs, ingestion queue not draining, high production 403 ratio, and insufficient Tuist server replicas.
- Other direct overrides select the default receiver. Preserve direct overrides rather than treating every rule as a notification-policy match.
- Root grouping is `grafana_folder, alertname`. Group/repeat timing was omitted/null in both provisioned and runtime policy trees. Grafana's [documented defaults](https://grafana.com/docs/grafana/latest/alerting/fundamentals/notifications/group-alert-notifications/) are group wait 30s, group interval 5m and repeat interval 4h; materialize these during import and verify deployed behavior in shadow fixtures. Null never means zero. Resolving before the initial group wait suppresses that notification; repeat timing is checked at group-interval boundaries.
- Slack `#clickhouse`, Adaptive Traces, and email are configured contact points but were not referenced by the inspected rule overrides/user policy tree. Runtime autogenerated routes advertise these receivers for direct overrides; this is not evidence that a current rule uses them. Keep contact inventory separate from proven alert routing.
- Provisioned custom notification templates, configured time intervals, and silences returned by Atlas were all empty at inspection. Active Slack, Atlas webhook and OnCall integrations allow resolved messages; the unreferenced Adaptive Traces webhook disables them. Slack title/text overrides were absent, so version-pinned default rendering needs fixtures rather than an invented Pulse format being called identical.
- OnCall escalation behavior and the Atlas/Hive payload/authentication contract remain un-inventoried. Slack-first cannot remove existing OnCall responsibilities or Atlas consumers.

A contact-point response exposed unredacted webhook authentication. Never include that value in fixtures, code, the inventory, or review prompts. Rotate the credential separately and correct redaction upstream. No external configuration has been changed by this investigation.

## Rule and query model

Use one tenant-scoped `Pulse.Alerting` service for HTTP, MCP, background evaluation, import, and preview. Proposed components are rule validation/import, object repository, scheduling/ownership, condition evaluation, notification routing, and delivery adapters. Do not duplicate alert semantics in controllers or tools.

A rule contains a stable ID, schema version, revision, enabled/paused flags, folder UID and full display path, group, cadence, `for`, explicit keep-firing duration, labels and label templates, annotations, expression DAG, terminal reference, no-data/error/missing-series policy, receiver override and audit metadata. Preserve the 13 nonzero `keep_firing_for` values, including the 5h HTTP-duration hold. Recording rules have an explicit output metric/target, no alert lifecycle, and no inherited defaults for their blank health fields. IDs never derive from titles. Updates use revision/ETag preconditions; IDs, tenant prefixes and paths are validated/encoded. Resolve synthesized labels using full folder paths (`Alerts`, `GrafanaCloud/Usage Alerts`, `Grafana Synthetic Monitoring`), never UID or just the leaf title. Keep Grafana compatibility labels/fingerprints separate from Pulse's internal identity.

Query nodes declare source reference and language (`promql`, metric-producing `logql`, or read-only `clickhouse_sql`), instant/range/table mode, relative window, resolution and bounded execution policy. Preserve all refs and validate the full DAG. Stable internal identity uses tenant, rule ID and canonical effective labels; hashes accelerate lookup but never replace canonical-label comparison. Values, annotations and timestamps do not change identity.

### Grafana server-side expressions (SSE)

Implementation checkpoint: a pure bounded kernel now compiles every inventoried
expression model (99 thresholds, seven math nodes and one strict-last reducer).
Disabled imports can be previewed through explicit tenant-local native Prometheus
instant and metric-producing LogQL instant/range bindings, with one query
worker/deadline and cumulative cross-language source budgets. Static selector
counts partition the smaller scan ceilings; logs charge raw selected input before
pipeline filtering. Range queries preserve explicit resolution and sparse native
frames, without claiming Grafana gap filling or source-frame conversion.
The 968 checked-in independent parser/IEEE/union-shim cases target public Grafana
v12.3.0, not the inventoried Cloud 13.3 build or its full server/datasource path.
No automatic source residency, external adapters, full Loki parity, recording ordering,
lifecycle/template/delivery parity or enabling imports follows from this increment.
Original query labels are retained, including metric names; actual Grafana source
frame conversion still needs its own capture gate.

SSE is its own version-pinned evaluator, not PromQL or LogQL:

- Seven math nodes use boolean conjunction/comparisons, `$A - $B`, and `${executions} >= ${threshold}`. Model Grafana's equal/subset-label joins, unmatched inputs, absent/mixed labels, metric-name treatment and scalar propagation. Accept both `$A` and `${named_ref}` syntax.
- 99 threshold nodes use `gt` (80), `lt` (18), and `eq` (one). Keep legacy condition/reducer/operator fields for round-tripping, but only execute the fields Grafana actually uses for threshold nodes. Capture NaN/infinity behavior.
- One reduction (`cache-nginx 502`) uses `last` with default strict mode over a Loki RANGE query (600s relative window, 1s resolution). Legacy `conditions` mention `avg`; they are not the actual reducer. Preserve query mode and distinguish range-node values from instant-node values.
- Six alerts use a source-query node directly as their terminal condition. Capture nonzero/zero, NaN, empty result and range-input behavior from Grafana fixtures; do not force an extra threshold that changes it.

### Templates and deliberate defects in imported rules

Implement a bounded, non-executable Go-template-compatible subset: `$labels`, `$value`, `$values.A.Value`, bare `$values.A`, named refs, `printf` (prefix and pipeline), `humanizePercentage`, `humanizeDuration`, nested `divf`, `urlquery`, pipeline last-argument passing, and missing-key/error behavior. Bare value structs are not automatically numbers. Keep `$__all` URLs and `$1,500` label text literal. Preserve plain-text runbooks independently of template interpretation. Do not run arbitrary Elixir or create atoms from input.

Independent validation found six missing-reference occurrences across FIVE rules: `bfoinizezjim8c`, `bfoitfmli7im8d`, `afoitkr3lm48wf`, `dfoitn3wti3nkb`, `efoits4looikgb` refer to `$values.B` without a B node. Preserve Grafana's actual rendered error/missing-value behavior in fixtures, or fix each as an explicit approved rule change; a lossless importer must not silently repair it. Default notifications must handle missing summaries. Escape untrusted labels such as SQL `query_preview` for Slack and bound template input/output without truncating away the triggering value invisibly.

### All sources, not just metrics

1. **Main Prometheus:** native coverage is substantial query-engine work, not a small parser extension. Implement scalar/vector arithmetic, comparisons and `bool`, set operators (`and/or/unless`), `on/ignoring`, `group_left/group_right`, metric-name/label propagation, `topk`, `histogram_quantile`, `label_replace`, `sgn`, `timestamp`, `floor`, `absent`, `absent_over_time`, `time`, `predict_linear`, `clamp_min`, statistical over-time functions, functions over expression arguments, and subqueries including `[3d:30m]` and `[6h:5m]`. Bound inner steps and total work. Expand the paused rule's `$__rate_interval` using the captured 60s datasource scrape interval and actual Grafana query-resolution formula, not arbitrary substitution. Preserve stale-marker and regex restrictions as explicit migration blockers until conformance tests cover required behavior. Lexical feature scans are only hints, not an AST/conformance report.
2. **Loki:** modules existing does not imply compatibility. The native foundation now parses and validates all 16 imported source expressions, supports range suffix grouping, removes the unwrapped label from identity, interpolates quantiles and omits empty-window samples instead of zeros. Typed shared binary operations repair set unions, scalar/range arithmetic and ambiguous matching. Sample/work/point budgets are shared across selectors, including repeated window visits. Invalid unwrapped values fail the whole query; unsupported counters, at modifiers and post-unwrap stages reject explicitly. Synthetic native tests and 63 public Loki v3.6.6 extracted-quantile cases cover this scope, not the complete Loki engine or deployed version. The HTTP instant path now honors integer seconds/nanoseconds and nanosecond-precision RFC3339 `time`, defaults to now and rejects malformed/overflowing/reversed bounds; range defaults are a one-hour window. Remaining gates include deployed timestamp/client envelopes (including scalar and decimal-seconds forms), label regex anchoring, full parser/error-label behavior, reducer ULP/signed-zero ties, native/Grafana frame conversion, long-window capacity and source residency. Read-only preview bindings now support native Prometheus instant and metric-producing LogQL instant/range queries with shared tenant admission/deadline/heap/counters and static scan partitioning. Native range frames remain sparse; this does not establish Grafana datasource conversion or enable imports. Verify logfmt/regexp, extracted labels, offsets, no-series behavior and exact errors across ALL 16 source nodes with independent full-query fixtures before enabling any graph.
3. **ClickHouse:** two rules are actual SQL, not PromQL. `Slow ClickHouse query` reads `system.query_log`; `Xcode cache - CI remote reads slow for an account` queries application tables and a seven-day baseline. Use a read-only external query adapter with a deployment-configured source, least-privilege database user, limits, deadline and bounded tabular conversion (string columns become labels, one numeric column becomes value). ClickHouse is an existing signal source, never Pulse's coordinator or alert-state store. Use Req through its HTTP interface. Arbitrary SQL is restricted to authorized operators and server-enforced read-only settings, not regex-based safety checks. Long-running upstream work needs cancellation/query identity and its own limits, not the public ten-second query default. Both SQL definitions use server-side `now()`; treat them as live-only unless a separately validated time-bound adapter exists. Never claim historical tick replay is deterministic by rewriting arbitrary SQL strings or repeatedly executing a live `now()` query.
4. **Grafana usage metrics:** seven nodes across seven rules depend on Grafana billing/usage telemetry. Bind these explicitly to a read-only external Prometheus source while Grafana is in use. Supporting their evaluation does not mean Pulse can synthesize Grafana spend. Later replacements need explicit definitions for Pulse costs/usage and comparable baselines, not renamed metric strings.
5. **Synthetic monitoring:** preserve both rules and their mixed-source graph. Probe/check-threshold series (`sm_*`, `probe_*`) and synthetic-agent logs are produced by Grafana's synthetic service, not automatically by Alloy. Retain authorized external reads unless those producers/inputs are explicitly replicated. Pulse evaluates alerts; it does not silently acquire responsibility for executing probes.
6. **Recording rules:** preserve all four `kura:*` outputs, labels, timestamps, schedule and full consumer closure. The compatibility target reads samples already durably published before an evaluation, within lookback, not a new same-tick topological guarantee. Verify actual Grafana group ordering/remote-write lag rather than inventing ordering. Outputs are gauge-like info series. Prepare an immutable result and first commit the winning `(generation, rule, revision, scheduled_timestamp)` recording intent via rule-head CAS; a bounded publisher appends ONLY that payload. Overlapping owners cannot append competing uncommitted values. Before each append, re-read the committed intent and verify the exact payload digest/identity; reject altered bytes before calling storage. Retry only that immutable payload under the same ingest key. Existing storage deduplicates matching key+content but accepts different content under the same key as a separate segment; it does NOT enforce conflicting-payload rejection. Test the publisher guard, not a nonexistent storage guarantee. Recheck generation/revision immediately before append and bound the deadline: the metrics manifest is a separate CAS, so late visibility of an already committed pre-edit intent is a documented bounded stale-write window, not an atomic disable fence. Persist receipts/recover through the rule head. On error/no-data, emit no samples. Existing ingest drops staleness markers, so verify recorded-series disappearance against Grafana before migrating. No missed-tick backfill by default. Moving recordings and all selectors/consumers together, or retaining explicit external copies, is a per-closure gate.

Temporary external Prometheus/Loki bindings can preserve complex rules while native conformance is built. They are named, operator-configured sources with `:base_url` overrides, secrets outside rule JSON, authorization, SSRF restrictions and no arbitrary caller URLs. They must never become an undocumented permanent dependency or hide a failed native execution behind automatic fallback.

## Alert modification history

Keep two distinct histories: **configuration changes** (who changed the rule and why) and **alert lifecycle** (pending/firing/recovering/resolved). Every lifecycle event references the exact committed configuration revision that produced it, so an investigation can reconstruct both timelines.

Each successful create/import/update/pause/resume/disable/delete/restore publishes ONE immutable full revision snapshot containing:

- Rule ID/generation, schema version and committed change sequence; parent revision reference (including an older generation when re-created); operation ID and canonical request digest.
- Server-recorded publication time (not an exact object-store commit timestamp), authenticated principal ID/type, API/MCP/import origin and bounded correlation references. Identity comes from configured per-principal credentials; a shared Atlas/service credential identifies that service, not the human behind it. Delegated identities are deferred, not accepted as caller-supplied names.
- Complete configuration: queries/DAG, thresholds, cadence/for/keep-firing, labels/templates, routing and enabled/paused/deleted state. This snapshot is BOTH the audit record and the change-resource data; there is no separate audit journal, index or duplicate administrative event.
- A bounded reason (import records an explicit baseline reason) and validated impact information about pending resets, recording/output changes and paging-affecting edits. Reason/context is untrusted, never an agent instruction.

Prepare the content-addressed revision, then publish its pointer and any lifecycle impact in the SAME rule-head CAS. Only the committed chain establishes history. A crash cannot acknowledge an unaudited modification, and conflicting/orphan candidates are not successful edits. Compute structural diffs on read from two authorized snapshots; bound/paginate large output rather than storing another journal or silently truncating it.

List changes newest-first through parent references, freezing the initial committed tip for pagination. Each page carries an authenticated body-only continuation that advances the walk; reads reauthorize and check current retention. For subscription catch-up, walk from that frozen tip toward the consumer's last-seen revision, then checkpoint the tip only after durable acceptance of that batch. Traversal-budget exhaustion returns continuation, NOT a gap or a restart at the newest head. This optional administrative feed has no chronological forward-replay or cross-rule-order guarantee and is not an automatic-action trigger. A missing in-horizon revision is an availability error; only a published retention floor establishes expiry. Historical lookup/operation status cannot infer nonexistence from an incomplete bounded walk.

Audit retention/floors are independent of shorter alert-event replay/delivery receipts and longer-lived unless explicitly configured otherwise. Publish floor advancement before GC, retain a read grace period, and protect snapshots/parents/generation references required by retained changes. Delete/re-create links to previous committed history, not to orphan objects. GC respects BOTH audit and lifecycle horizons. Imports establish an observed baseline, not fabricated historical Grafana edits/actors.

Snapshot content and change metadata have separate immutable classifications: removing SQL may lower today's configuration sensitivity, but does not lower old SQL snapshots or the removing edit's before/after audit sensitivity. Diffs/change metadata require the union of before/after permissions, including reason/context. Credentials stay secret references, never stored token values. Hash-linked snapshots aid integrity checking, not tamper-proof/compliance guarantees against bucket administrators; Object Lock is a separate policy.

Provide shared API/MCP operations to list changes (cursor-paginated, optionally actor/time filtered), read a historical revision, compare two authorized revisions, and restore one. Proposed HTTP routes under `/api/v1/alerting/rules/:id` are `GET /changes`, `GET /revisions/:revision`, `GET /diff`, and `POST /restore`; proposed tools are `list_alert_rule_changes`, `get_alert_rule_revision`, `compare_alert_rule_revisions`, and `restore_alert_rule_revision`. Generation is explicit when revisions span re-creation. Audit reads require an audit-read capability and historical source permissions.

Restore is an explicitly authorized NEW modification with current-revision precondition, operation identity and reason, not moving the head backwards or deleting later edits. Revalidate historical source bindings, query support, destinations and current permissions; restoring does not resurrect removed credentials, historical alert state, silences or delivery receipts. Re-enabling a paused/deleted rule must be explicit, not an accidental side effect of rollback. Diff/impact preview is read-only. A concurrently edited head yields conflict rather than overwriting the newer rule.

Configuration changes are a separate opt-in MCP `alert-rule-changes` resource/event class, not default proactive firing triggers. An agent can answer “who raised this threshold, when, and what was it before?” or subscribe to changes without reacting to its own edits. Acknowledgements, silences, annotations and shared routing/contact changes retain their own audit histories under their own CAS authorities, linked where relevant; no cross-object transaction is claimed.

## Object-store model and atomicity

Use a separate versioned alert namespace, not the telemetry manifest:

```
tenants/<encoded-tenant>/alerting/v1/config.json
tenants/<encoded-tenant>/alerting/v1/rules/<id>/head.json
tenants/<encoded-tenant>/alerting/v1/rules/<id>/g/<creation-nonce>/revisions/<revision-digest>.json
tenants/<encoded-tenant>/alerting/v1/rules/<id>/g/<creation-nonce>/events/live/<event-digest>.json
tenants/<encoded-tenant>/alerting/v1/rules/<id>/g/<creation-nonce>/history/date=<UTC-date>/<page-digest>.json
tenants/<encoded-tenant>/alerting/v1/rules/<id>/g/<creation-nonce>/drain-descriptor.json
tenants/<encoded-tenant>/alerting/v1/rules/<id>/g/<creation-nonce>/drain-head.json
tenants/<encoded-tenant>/alerting/v1/delivery/<group-id>/head.json
```

S3 is the only durable shared state. Configuration changes use conditional writes and immutable referenced revisions; no local WAL or durable broker. Caches/tasks/ownership views are disposable. Paginated tenant/rule prefix discovery is sufficient; no independently published catalog is required. A discovered prefix must have a valid authority head before it counts as a rule; candidate-only prefixes are not committed creations. Acknowledge creation after the head publication is durable. Deletion/disable use conditional head tombstones, never an unfenced DELETE. Every creation gets a fresh random 128-bit generation nonce, not a counter dependent on permanent tombstones. Generation scopes revision/event/payload paths, recording identities and `(rule_id, generation)` cursors. Re-creation CASs the tombstone immediately with a new nonce and carries retained-generation history/drain references forward; old draining work does not block creation except explicit storage/churn quotas. A generation-scoped drain descriptor is committed by deletion and its separate drain-head CAS progresses independently. Lifecycle registry entries may be conditionally removed only after terminal drain and expired lifecycle replay. Audit ancestry is protected separately by the revision parent chain/floor and does not pin lifecycle registry quotas. GC eligibility is PER OBJECT CLASS: events/pages behind their lifecycle floor, revisions behind the cross-generation audit floor, and live payloads only after terminal delivery/recording evidence. Never delete a generation prefix while any retained revision remains reachable through the audit chain. Orphan GC requires unreachability evidence and publication/read grace, not absence from LIST or the lifecycle registry alone.

The rule head atomically publishes active rule revision, lifecycle checkpoint, completed UTC evaluation timestamp, bounded inline event-reference tail, bounded sealed-page range/reference list and replay floor, retained-generation registry and BOUNDED per-target transition references/acknowledgements. Timestamp ordering survives cadence edits; tick indices alone do not. API edits/disable/delete contend on this same head, fencing old evaluators. Prepare immutable candidate transition events, then CAS the head against exact prior revision/state. Only events referenced by a committed outbox are actionable; losing candidates are orphans. Logical event IDs derive from generation, canonical instance, transition sequence/type and notification ordinal; writer identity is not logical alert identity. Candidate storage keys are content-addressed, never logical event/revision IDs or sequence ranges: overlapping evaluations may prepare the same next logical ID with different bytes. Heads reference exact keys/digests/sizes, and readers validate bytes and embedded identity before use. Apply this to revisions, events, pages and recording payloads. Stable recording append identities remain separate; the publisher rejects bytes that differ from the committed intent before append. Existing storage's key+content deduplication is not a conflicting-payload guard. Config edits preserve unconsumed outbox entries.

Every conditional attempt has an operation identity and content digest. API operation IDs bind a canonical request digest including tenant/principal, action, target/generation, expected configuration revision and payload/reason. Exact same-ID/same-request retries are idempotent; changed input returns operation_reused conflict. Rebase onto a NEW configuration revision requires a NEW operation ID. Evaluator-only head updates may retry the internal CAS while the expected configuration revision is unchanged. The current Rust client retries internally, so ANY non-success, including `:precondition_failed` and `:already_exists`, may follow a successful write. Read back on every failure: matching operation/digest means success; a different winner means conflict and requires revalidation; unavailable/indeterminate read-back remains an explicit ambiguous outcome. For a head already advanced, consult bounded durable receipts or committed revision ancestry. A mutation expected at revision E can commit only as E's unique child: finding that child proves success or a competing winner. An incomplete walk returns continuation/ambiguous status, not failure; beyond the published status/idempotency horizon return unknown_expired and do not blindly recreate the operation. Immutable create conflicts also compare content, not just existence. Fault-inject commit-then-5xx and commit-then-412 in tests. Evaluate removing automatic retries for conditional NIF operations, but keep read-back regardless.

Persist the monotonic completed-tick watermark on EVERY committed evaluation, including unchanged normal results; otherwise an older delayed evaluation could still publish a false transition after an uncheckpointed newer result. Keep only a bounded summary ring in the head and immutable events for transitions, not one immutable snapshot per tick. The captured schedule produces 90,576 ticks/day: budget roughly that many successful head PUTs plus reads, changes, conflicts, delivery and recording writes. Reject lower-frequency checkpointing unless it has a proven stale-publication fencing design. This intentionally differs from the review's suggested sparse checkpoint optimization.

Targets have independent bounded lag limits over the committed event journal. Overflow coalesces ONLY that target to a durable gap marker (generation, skipped notification-delta range, latest-state snapshot/digest and degradation reason); lifecycle publication, completed timestamps and other targets continue. The group resynchronizes current membership instead of pretending all intermediate notifications were delivered. Exact committed transition history for MCP/history reads is separate from coalescing notification queues. Failure to publish the authoritative head is an uncommitted/skipped evaluation, never an acknowledged lost transition.

Set instance/head byte limits, per-target lag, summary/receipt and history/retry budgets. Immutable live event/payload objects are outside bucket TTL; historical pages expire only beyond the advertised replay floor. Live GC requires final consumption/cancellation/retirement evidence and no retained history references, with grace for unresolved responses. API mutation receipts have an age-based horizon independent of frequent evaluator receipts; client idempotency/status guarantees expire explicitly. Measure head bytes/day as well as PUT count.

## Scheduling and alert state machine

Reuse `Pulse.Rendezvous` with an alert-specific purpose and process-group eligibility scoped to object-store identity. One node is expected to evaluate each rule; partitions or membership disagreement may overlap. No singleton correctness assumption and no leader election. Check eligibility/ownership before admitting work and before publication, but use CAS as the fencing backstop.

Choose a stable logical tick schedule with persisted phase/jitter, monotonic local deadlines and bounded cross-node clock skew. Grafana's base-tick/jitter offsets mean shadow comparisons need a bounded time tolerance; UTC alignment is not exact Grafana scheduling parity. Persist last tick, pending-since, firing-since, recovery/keep-firing deadlines, missing-series counters and health. Do not replay missed ticks by default. Evaluate the current eligible tick, record the gap, and preserve durable pending timers through ordinary restart/failover. A long-gap reset policy must be separately approved and documented; do not reset pending on every deployment or pretend missed predicates were observed. Fire only on eligible evaluations: `for=1m` with cadence=5m fires at a later evaluation, not via an independent minute timer. Pause/delete/edit behavior and which edits reset pending require pinned Grafana fixtures.

Lifecycle per effective labels: normal -> pending -> firing -> recovering (keep-firing) -> resolved. The 13 holds require F-KFF-1..8 fixtures: disappearing series versus wholly empty results (OK/KeepLast), errors, hold equal to cadence, re-trigger/StartsAt, recovering annotation values and notifier emission. Nine held rules recover through filtered-series disappearance; hold-versus-missing-series/no-data precedence is a first-phase BLOCKER. Recovering is head-only and externally still firing unless pinned fixtures require notification intents. Act on absolute hold deadlines only at eligible evaluations. Query health is orthogonal:

- `OK`, `Alerting`, `KeepLast`, `NoData`, `Error` are explicit imported behaviors, not generic empty-result defaults.
- Whole-query empty result is rule-level no-data. One series disappearing while others remain is missing-series handling; track per-instance successful-missing evaluation count and resolution reason separately. The original API has no `missing_series_evals_to_resolve` field. Materialize the expected two-evaluation default only after validating it against the pinned deployment.
- `DatasourceNoData` / `DatasourceError` are independent alert instances, with version-pinned label sets (`datasource_uid`, `ref_id`, `rulename`, rule labels, etc.), pending/resolve semantics and cross-rule grouping. The regular instance is not silently resolved as a side effect of creating a health alert.

## Routing, suppression and durable delivery

Implement matching order, `continue`, inherited grouping/timing and integration fan-out. Direct overrides bypass the user route tree: even a staging-labelled rule with a direct production receiver remains there. There are 13 direct overrides, five to Incidents and eight to default Slack/webhook. Runtime autogenerated receiver routes must not be imported twice. Synthesize full-path `grafana_folder`, `alertname` and compatibility labels correctly.

Group owners commit membership, per-`(rule_id,generation)` cursors and timers in ONE group-head CAS. Read only committed events and advance the cursor WITH membership/current snapshot, including explicit gap resynchronization. No standalone cursor writes. Current normal groups are one-rule, but DatasourceError can span 57 rules and DatasourceNoData 16; generic user grouping also merges rules. Backpressure isolation is per target, never one health group freezing all source lifecycles.

Pinned targets include routing and integration generations. Config removals durably create retirement/cancellation records covering the removed target generation and old route revisions; they count as terminal consumption even for late publication against an old snapshot. Publish a retiring configuration phase before asynchronous per-head cutoff/drain work and expose progress. New generations remain unaffected. Delete commits retained history and a drain descriptor; F-DEL-1 determines removal/resolution events. Generation-scoped drain workers finish independently while a fresh generation may already occupy the rule head. API/evaluator/retention writers CAS the CURRENT-generation head; old drain workers write only their generation's detached drain head. Group/channel workers never write rule heads. Permanently failed target materialization becomes explicit retirement/dead-letter/gap state, never an eternal source pin.

Group-member indexes and coalesced local invalidation are hints; paginated discovery/conditional GET remains the backstop. Polling all 115 heads every 5s approaches two million reads/day/tenant: share bounded node-local polling across consumers, retain ETags from own commits, and measure read cost/freshness.

Notification channels hold a coalescing LATEST GROUP SNAPSHOT, not a delta queue. CAS the pending snapshot and consumed group version together; keep any in-flight attempt identity separate. Last-confirmed digest/time controls repeat/group timers (F-NFLOG-1). New snapshots suppress launching old retries, but an in-flight remote effect may still arrive late: claims do not guarantee external order/exactly-once. Preserve resolved-only flush and repeats during holds. Cancellation/dead letters remain inspectable. Recheck silences, ack suppression, binding permissions and destination disable at send time; these suppress delivery, not evaluation/history.

Start with Slack, then Grafana-compatible webhook payloads and the retained OnCall integration. Hive threads by fingerprint: preserve the actual algorithm and effective label set, or approve an explicit remapping at migration. Do not assume Pulse's metrics StableHash is Grafana's alert fingerprint. Preserve existing Grafana/Atlas links or define empty/API links deliberately; Pulse does not gain a UI. Confirm OnCall accepts the chosen payload and resolves/deduplicates correctly before any paging responsibility moves. No infrastructure remediation belongs here.

Delivery uses a durable S3 CAS head for each group/channel, recording payload reference, stable notification ID, attempt count, next retry, in-flight claim expiry, and confirmed outcome. Ownership or expiring claims reduce concurrent sends but cannot guarantee exactly-once external effects. A Slack success followed by a crash before recording the receipt can be replayed: document at-least-once delivery and use supported provider deduplication where verified. Claims fence S3 commits, not remote HTTP requests. Honor Retry-After, exponential backoff with jitter, permanent failures, bounded retries/dead-letter inspection and operator requeue. One failed channel must not block another channel or later resolved delivery indefinitely; specify per-channel ordering and stale firing-versus-resolution handling.

All HTTP clients use Req. Destination references resolve from operator-controlled source/secret configuration; prevent SSRF, strip secrets from logs/API/MCP responses, bound payloads and prevent Slack mention amplification. Test notifications are separately authorized, explicit side effects, never part of preview/import.
